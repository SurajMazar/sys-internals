CONTAINER INTERNALS · CHAPTER 07

Capabilities: Splitting
Root Into 40 Pieces

Every container that runs as UID 0 inside its namespace is, by default, missing about twenty-six thirty-seconds of what "root" used to mean. This chapter derives why the kernel stopped treating privilege as a single bit, walks the exact five-set bitmask machinery that replaced it, and shows precisely which of the ~40 capabilities Docker and Podman grant a container by default — and why they agree almost exactly on the list.

ARC 01 · THE PROBLEM

Root is not a permission — it's the absence of permission checks

Every namespace you met in chapters 2–4 answers "what can this process see?" Every cgroup limit in chapter 5 answers "how much can this process consume?" Neither one touches a question that matters just as much for a process running as UID 0 inside a container: what privileged kernel operations can this process invoke? On classical Unix the answer was a single comparison. Deep inside the kernel, the permission check behind mount(), reboot(), raw sockets, changing any file's owner, tracing any process, and dozens of other operations was the same three lines: is the caller's effective UID zero? If yes, allowed. If no, EPERM. There was no partial credit.

That binary model creates a specific, acute problem for containers. A huge fraction of container images run their main process as root inside the container — not out of laziness, but because decades of Unix tooling assumes it: package managers write to /usr, web servers want to bind port 80 (privileged, <1024), backup agents need to read files regardless of owner, init-style processes need to chown freshly-created device nodes. Namespaces (chapters 2–4) make that root look harmless by hiding the rest of the host filesystem, process tree, and network from it. But namespaces are a visibility boundary, not a privilege boundary — nothing about "you can't see /etc/shadow on the host" stops UID 0 inside an unconstrained container from loading a kernel module, rewriting the system clock, or attaching a debugger to any process it can see. If root is still monolithic, "give the container root" is never a scoped grant — it's the entire kernel's privileged surface, handed to a process because it needed one sliver of it.

  • Compatibility pressure. Most container images still assume UID 0 for legitimate, mundane reasons — not because the workload needs the whole of root's power.
  • Heterogeneous need. An nginx container needs exactly one privileged thing (bind <1024). A backup agent needs a different one (bypass file-owner checks). Nothing in a normal container workload needs to load kernel modules or reboot the host.
  • The boundary must be kernel-enforced. A convention ("please don't call reboot()") is not a security boundary; only a check the kernel itself performs on every privileged syscall counts.
  • It has to compose with namespaces. Visibility isolation and privilege reduction are orthogonal — a process can be namespaced within an inch of its life and still, with full capabilities, threaten the host kernel directly.
  • It has to be expressible identically by every engine. Docker and Podman must describe "which slice of root" in one shared, spec-defined vocabulary, or portability between them breaks at exactly this layer.
WHERE THIS SITS IN THE STACK

Capabilities are the second of three privilege-reduction layers a container engine stacks on top of a root-equivalent UID: namespaces (chapters 2–4) bound what the process can see; capabilities (this chapter) bound which privileged operations UID 0 may still perform; seccomp and LSMs (chapter 8) bound which raw syscalls it may even attempt, and layer mandatory access control on top of the discretionary checks capabilities perform. All three are orthogonal, all three are usually needed, and a container hardened in only one dimension is not hardened.

ARC 02 · HISTORICAL CONTEXT

Thirty years of trying to make root divisible

The idea of splitting root predates Linux containers by two decades and was motivated by exactly the problem in §1: setuid-root binaries that only needed one sliver of privilege but got all of it. Click through the events that produced today's five-set model.

DEEP CONTEXT · A STANDARD THAT DIED BUT WON

POSIX.1e ("POSIX capabilities") never became a ratified standard — the IEEE working group withdrew the draft in 1997 after years of stalled consensus. Linux implemented it anyway, informally, and every capability name you will use this chapter (CAP_CHOWN, CAP_NET_BIND_SERVICE, CAP_SYS_ADMIN…) traces directly to that abandoned draft's bit layout. It is a rare case of a failed standard winning by becoming the only serious implementation left standing — much like how cgroup v1's multi-hierarchy design (chapter 5) lost to v2 by simply being replaced rather than voted down.

ARC 03 · NAIVE SOLUTION

Attempt #1: one bit, checked everywhere

Derive it honestly, the way the actual kernel did for its first two decades. Every privileged operation's entry point performed the same test:

Clinux ~2.0 era — the pattern behind dozens of syscalls
/* fs/super.c — sys_mount(), pre-capabilities kernel */
asmlinkage int sys_mount(char *dev_name, char *dir_name, ...)
{
    if (!suser())              /* suser(): current->euid == 0 ?           */
        return -EPERM;          /* one bit, checked, nothing in between    */
    ...                            /* mount proceeds fully trusted            */
}

/* net/ipv4/raw.c — raw socket creation, same shape */
if (protocol == IPPROTO_ICMP && !suser())
    return -EACCES;             /* → this is why /bin/ping was setuid-root */

/* kernel/sys.c — reboot(), same shape again */
if (!suser())
    return -EPERM;

This is not a strawman built to be knocked down for entertainment — it is the correct starting point, and it got real things right. One comparison, one bit to protect, no separate policy engine to misconfigure, and it composed trivially with the rest of Unix's permission model (file modes, setuid). For a single-user workstation or a small trusted server fleet, "root can do anything, nobody untrusted is root" was a coherent, defensible security model for a very long time.

It breaks down exactly where Unix tooling meets least privilege: /bin/ping needs one thing — a raw ICMP socket — and the only way to grant it under the binary model is to make the whole binary setuid-root, so that any ordinary user executing it briefly becomes root for the duration of the process.

ARC 04 · WHY IT FAILS

One sliver of root, purchased with all of it

Quantify the over-grant precisely. /bin/ping needs exactly one of the kernel's roughly forty independent privilege gates — CAP_NET_RAW, in the vocabulary this chapter is about to introduce. Under the binary model, the only way to grant that one sliver is chmod u+s /bin/ping; chown root /bin/ping — which, the instant it runs, also hands the process the power to load kernel modules (CAP_SYS_MODULE), bypass every file permission check on the system (CAP_DAC_OVERRIDE), attach a debugger to any process (CAP_SYS_PTRACE), and reboot the machine (CAP_SYS_BOOT) — none of which ping has ever needed to send an ICMP echo request.

THE NUMBERS

Of the kernel's roughly 40 independent privileged-operation gates, a task like "bind a listening socket on port 80" needs exactly 1 — about 2.5% of root's total surface. The binary model has no unit smaller than "all of it," so satisfying that 2.5% need means over-granting by roughly 40×. That gap is not theoretical: it is the reason "local privilege escalation via a memory-safety bug in a setuid-root utility" was, for two decades, one of the single most common severe vulnerability classes in Unix history — a bug that should only let an attacker forge one ICMP packet instead handed over the entire kernel, because the binary carrying the bug had been granted the entire kernel to satisfy a 2.5% need.

Containers make this worse by concentrating the problem: a container's main process usually runs as UID 0 for the whole lifetime of the container, not just for one setuid'd syscall. Without a finer-grained model, "containerize a legacy app that assumes root" and "give an attacker who compromises that app the whole host kernel's privileged surface" become the same sentence. The industry needed a privilege unit smaller than "all of root" decades before containers existed — and one already existed by the time Docker shipped in 2013.

ARC 05 · BETTER SOLUTION, DERIVED

Replace one bit with forty independent bits

The fix, in outline, is almost embarrassingly direct: instead of one bit (euid==0) guarding every privileged operation, assign each coherent slice of root's power its own bit, and have every one of the kernel's ~40 privileged-operation check sites test its own specific bit instead of the shared UID-zero test. Step through the transformation:

Applied to containers, this is the entire mechanism behind "safer default": instead of a container's root process holding a single all-or-nothing bit, it holds a 40-bit vector, and both Docker and Podman ship an identical default vector with 14 bits set and the rest cleared — including, deliberately, leaving CAP_SYS_ADMIN, CAP_SYS_MODULE, CAP_SYS_RAWIO, and CAP_NET_ADMIN unset. A compromised nginx container with the default capability set literally cannot call mount(), insmod, or manipulate network interfaces — not because a policy says not to, but because the kernel's capable(CAP_SYS_ADMIN) check returns false for that process, full stop.

THE 14 KEPT BY DEFAULT

CAP_CHOWN · CAP_DAC_OVERRIDE · CAP_FOWNER · CAP_FSETID · CAP_KILL · CAP_SETGID · CAP_SETUID · CAP_SETPCAP · CAP_NET_BIND_SERVICE · CAP_NET_RAW · CAP_SYS_CHROOT · CAP_MKNOD · CAP_AUDIT_WRITE · CAP_SETFCAP. Every one of the roughly 26 others — including all of the ones that can reach the host kernel or hardware directly — is dropped before your container's first instruction runs.

ARC 06 · WHY THAT STILL COSTS

CAP_SYS_ADMIN: the bit that became root again

Splitting root into forty independent bits works cleanly when each bit guards one coherent idea. It broke down for exactly one bit, and the story of that breakdown is worth understanding because it is still ongoing. When the original POSIX.1e authors ran out of an obvious existing category for a new privileged operation, the path of least resistance was to gate it behind CAP_SYS_ADMIN — and for roughly fifteen years, kernel developers took that path constantly. Step through what accreted onto one bit:

Everything CAP_SYS_ADMIN still gatesSTEP-BY-STEP

Three other costs compound the CAP_SYS_ADMIN problem:

  • Capabilities are Linux-only. There is no POSIX ratification (§2) and no direct analogue on BSD or macOS — tooling and mental models don't transfer, unlike namespaces' rough conceptual cousins (FreeBSD jails) or cgroups' rough cousins (Solaris resource controls).
  • A capability is a host-kernel-wide notion unless paired with a user namespace. CAP_SYS_ADMIN granted to a process in the host's user namespace is, for nearly every practical purpose, equivalent to CAP_SYS_ADMIN on the host — the capability boundary and the namespace boundary are orthogonal, not layered for safety by default. Chapter 4's rootless model changes this precisely by making the capability meaningful only inside a private user namespace, which is why rootless Podman's threat model is genuinely different from rootful Docker's capability-only defense.
  • The list still grows the wrong direction sometimes. Kernel 5.8 finally split CAP_BPF and CAP_PERFMON out of CAP_SYS_ADMIN's historical territory, and 5.9 added CAP_CHECKPOINT_RESTORE — a tacit admission, thirty years in, that "when in doubt, gate it behind SYS_ADMIN" was a mistake worth slowly unwinding.

A real Linux process doesn't carry one 40-bit vector — it carries five, each answering a different question about how capabilities may be gained, kept, or lost across a lifetime that includes fork() and execve(). All five sets are fields of struct cred (include/linux/cred.h): cap_permitted, cap_effective, cap_inheritable, cap_bset, and cap_ambient, each a kernel_cap_t — currently a single 64-bit word, though only ~40 bits are assigned. Every task's struct task_struct points at a struct cred; fork() copies the pointer (copy-on-write, same as the rest of a task's credentials), and it is this same struct that also carries the UID/GID and — foreshadowing chapter 4 — the user-namespace pointer that determines which namespace's "root" a given CAP_SYS_ADMIN actually means.

The exact formula the kernel runs on every execve()

Now the mechanism precisely enough to predict any container's post-execve() capability set by hand. Three pieces: (a) the transition formula and a worked example, (b) a live calculator you can drive with sliders, (c) the real syscalls involved.

OPERATIONAL GOTCHA WORTH KNOWING

File capabilities live in an extended attribute, tied to the inode, not the file's bytes. That means a naive tar without --xattrs, or a cp without --preserve=xattr, silently drops security.capability — a binary that worked perfectly in a build stage can lose its capability and fail with a bare EPERM after being copied into a final image layer, with no error at copy time. It is one of the more surprising multi-stage-build (chapter 10) failure modes in practice, and it looks nothing like a capability problem until you check getcap on the copy.

ARC 09 · TRADEOFFS

Capabilities among the other privilege-reduction levers

APPROACHWHAT IT BUYSWHAT IT COSTS
Full root, no restriction zero compatibility friction every privileged syscall reachable 1 bug = full host risk
Default capability set (14/40) blocks mount/module-load/raw-io/net-admin by default near-zero runtime cost still trusts UID 0's other checks (DAC) unless paired with more
--privileged / add ALL back unblocks legitimate edge cases (nested containers, some device access) reintroduces exactly the §4 over-grant, deliberately
+ user namespace (chapter 4) a granted capability is scoped to the container's own userns — host-meaningless some filesystem/device operations still need real host privilege
+ seccomp / LSM (chapter 8) blocks the syscall itself, independent of whether the capability check would pass separate policy surface to author and keep in sync

Read that table as layered defense, not a menu to pick one from: a hardened container typically stacks every row from the second down — reduced capabilities, ideally inside a user namespace, with seccomp and an LSM profile on top. Each layer catches what the one below it would have let through if misconfigured.

The honest takeaway: at the "which 14 capabilities" question, Docker and Podman are not just similar — they are the same, because both ultimately express the answer as an OCI-shaped process.capabilities array (chapter 9) consumed by runc or crun. The genuine difference is not the list; it's what a granted capability means, which depends entirely on whose user namespace the process runs in — Podman's rootless default and Docker's rootful default answer that question differently before capabilities even enter the picture.

ARC 10 · PERFORMANCE & ATTACK SURFACE

The cheapest check in the security stack — and the surface it still leaves

Capability checks are, computationally, almost free. capable(CAP_X) compiles down to a single bitmask test (cap_raised(), an inline AND against one 64-bit word) plus an LSM hook call that, with no LSM capability module loaded, is a no-op. Compare that to the mandatory-access-control checks chapter 8 covers — SELinux and AppArmor evaluate a label or path against a loaded policy on every relevant operation — and capabilities are by a wide margin the cheapest privilege gate in the entire container security stack. The cost that matters here isn't runtime overhead; it's how much attack surface a given profile still exposes.

"Privileged ops reachable" is an illustrative per-capability weighting (most capabilities gate a small, coherent handful of operations; CAP_SYS_ADMIN alone is weighted heavily per §6's list) — it is a teaching approximation of relative blast radius, not a count anyone has published as a formal metric. The shape is the point: adding capabilities back one at a time costs roughly linearly, until CAP_SYS_ADMIN specifically is added, which jumps the curve disproportionately — exactly the asymmetry that makes it the one capability every hardening guide singles out by name.

ARC 11 · REAL-WORLD INCIDENTS

Three times the capability boundary was the whole story

Incident 1: CVE-2022-0492 — release_agent + CAP_SYS_ADMIN

cgroup v1's release_agent file — a hook the kernel runs (as root, in the host's initial namespace) when a cgroup with notification enabled becomes empty — could be written and armed by any process holding CAP_SYS_ADMIN, even inside a container, letting that process specify an arbitrary host-executed command. Root cause analysis distills to one sentence: this is a host-wide root-execution primitive gated behind a single capability bit. The reason it was a headline rather than routine noise is precisely this chapter's default list — a container running Docker's or Podman's default 14 capabilities was never exposed, because CAP_SYS_ADMIN is one of the ~26 dropped by default. Every real-world exploitation required either --privileged or an explicit --cap-add=SYS_ADMIN, which is exactly the deliberate, auditable decision §5's model is designed to force into the open.

Incident 2: the 2014 "Shocker" container-breakout proof of concept

A widely circulated 2014 write-up demonstrated escaping an early, less-hardened container configuration by combining CAP_MKNOD (create a device node) with CAP_DAC_OVERRIDE (bypass file permission checks): create a block-device node inside the container pointing at the host's underlying disk device, then read it directly — a raw block read bypasses the mount namespace's view of the filesystem entirely, since it never goes through a mount point at all. It remains one of the clearest illustrations that capability grants must be reasoned about in combination, not one at a time — neither CAP_MKNOD nor CAP_DAC_OVERRIDE alone is that dangerous; together, against a device node, they are a namespace bypass. Both are still in the default 14 today, which is defensible only because default engine configuration also denies raw device-node access through other layers (device cgroup controller policy, chapter 5) — a reminder that the capability list is never the only control in force.

Incident 3: CAP_NET_RAW and the case for dropping engine defaults anyway

CAP_NET_RAW is in the default 14 for a mundane reason — ping needs it — but it also permits crafting and sniffing raw packets, including spoofed ARP frames, against any interface the container's network namespace can see. On a shared bridge network (chapter 3), that is enough for one container to spoof traffic toward a sibling container sharing the bridge. This is well-documented enough that Kubernetes's Restricted Pod Security Standard requires every container to explicitly drop: ["ALL"] and permits adding back only NET_BIND_SERVICE — deliberately stricter than either engine's own default. The lesson generalizes: an engine's default profile is a reasonable baseline for compatibility, not a security ceiling — production hardening regularly starts from --cap-drop=ALL and adds back only what a specific workload has actually been shown to need.

Csecurity/commoncap.c — cap_bprm_creds_from_file(), simplified
/* Runs during execve(). Implements the exact §8 formula. */
int cap_bprm_creds_from_file(struct linux_binprm *bprm, struct file *file)
{
    kernel_cap_t new_permitted, p_ambient;
    struct cred *new = bprm->cred;
    kernel_cap_t fP = get_file_caps_permitted(file);
    kernel_cap_t fI = get_file_caps_inheritable(file);
    bool file_is_privileged = fP || fI || is_setuid_root(file);

    p_ambient = file_is_privileged ? CAP_EMPTY_SET() : old->cap_ambient;

    new_permitted = cap_intersect(old->cap_inheritable, fI);
    new_permitted = cap_combine(new_permitted,
                     cap_intersect(fP, old->cap_bset));
    new_permitted = cap_combine(new_permitted, p_ambient);

    new->cap_permitted   = new_permitted;
    new->cap_effective   = get_file_caps_effective(file) ? new_permitted : p_ambient;
    new->cap_ambient     = p_ambient;
    new->cap_inheritable = old->cap_inheritable;   /* unchanged */
    return 0;
}

WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. The bounding set only ever shrinks. PR_CAPBSET_DROP has no inverse — once gone from a process's bounding set, a capability cannot be regained by that process or any descendant, even via execve of a file with file capabilities set. A one-way ratchet is a stronger guarantee than a reversible flag precisely because no code path, buggy or malicious, can undo it. 2. Ambient capabilities exist to solve one narrow problem, on purpose. Before Linux 4.3, a non-root process could never retain a capability across execve() unless the target file had capabilities set on it — painful for container init systems and systemd services that want to drop to a non-root UID while keeping one specific capability. Ambient sets exist for exactly that case and nothing broader. 3. Capabilities are expressed identically by every OCI-compliant engine. Docker and Podman both lower to the same five-array config.json shape (chapter 9) before runc or crun ever runs — the capability model achieves portability by being boring and literal, not by each engine reinventing a policy DSL.
