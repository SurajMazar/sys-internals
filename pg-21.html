ARC 01 · THE PROBLEM

You understand every piece. Can you assemble the whole?

Chapters 1 through 20 each isolated one subsystem — the process model, memory contexts, the page format, MVCC, the lock manager, the buffer pool, the WAL, the planner, indexes, replication, and finally how to diagnose all of them in production. That isolation was pedagogically necessary and is, in a specific sense, a lie: none of those subsystems works alone. A page format means nothing without a buffer pool to cache it. MVCC means nothing without a WAL to make its commits durable. A B-tree means nothing without a planner that knows when to use it. This chapter's job is to stop isolating and start assembling — to build a small but genuinely working storage engine and prove, by running real transactions against it, that you understand not just each piece but how they depend on each other.

"Working" means exactly three properties, and they are the three hardest properties to get right together, which is why this is the capstone and not chapter 3:

  • Durability across crashes. A transaction that returned "commit successful" must have its data survive an actual, simulated crash — not because we promise it will, but because a WAL replay mechanism reconstructs it from a durable log, byte for byte.
  • Correct MVCC isolation between concurrent transactions. Two sessions, open at the same time, making different changes, must each see a consistent snapshot of the data — genuinely different rows for genuinely different transactions, not a shared mutable object underneath a thin coat of paint.
  • A planner that picks the cheaper of two real access paths. Given a table, a predicate, and an index, the engine must compute actual costs from actual statistics and choose — not hardcode "always use the index," which is wrong exactly often enough to matter.
THE RULE FOR THIS CHAPTER

Every component below is REAL, RUNNABLE JavaScript — the same functions the console in §15 calls when you type a command. Nothing here is a diagram pretending to be code. Where the toy simplifies something away from real PostgreSQL, that simplification is named explicitly, so you leave this chapter knowing not just what a mini-Postgres looks like, but exactly how much harder the real thing is and why.

ARC 03 · NAIVE SOLUTION

Attempt #1: an array of objects and JSON.stringify

The honest starting point, the way every one of this course's naive solutions has been honest: if you needed a "database" in a JavaScript program with no other constraints, you'd reach for this.

jsnaive-db.js — the strawman, annotated
let table = [];                       // the "table" — a plain array of objects

function insert(row) { table.push(row); }
function selectWhere(pred) { return table.filter(pred); }   // O(n) every time, always

function save() {
  // "durability": serialize EVERYTHING and overwrite the file. No partial
  // writes considered — if the process dies mid-write, the file is corrupt.
  fs.writeFileSync("db.json", JSON.stringify(table));
}
function load() {
  table = JSON.parse(fs.readFileSync("db.json"));  // "recovery": read it back. Nothing else.
}

This is not stupid — it is exactly right for a huge class of programs (config files, small caches, prototypes) and it is, not coincidentally, how a first draft of almost every "let's build a database" tutorial on the internet starts. The question, as always, is what it costs once you demand the three properties from §1.

ARC 04 · WHY IT FAILS

Every property from §1 fails, and fails in a specific, informative way

  • No crash safety. fs.writeFileSync writing the WHOLE serialized table is not atomic at the OS level for large files — a crash mid-write leaves a truncated, invalid JSON file, and there is no way to recover the PREVIOUS good state because it was already overwritten. There is no WAL, so there is nothing to replay.
  • No concurrency. Two "transactions" racing to call save() at once will interleave their writes to the same file descriptor in undefined order — the last writer wins, silently discarding the other's changes, with no lock, no queue, no error.
  • O(n) on every operation. selectWhere scans the entire array every time, and save() rewrites the ENTIRE table to disk on every single change — an insert of one row costs O(n) disk I/O, because there is no concept of a page, so there is no concept of writing only what changed.
  • No MVCC. There is exactly one mutable array. Two "transactions" see the same object at the same time; there is no way to ask "what did this row look like 5ms ago from MY point of view" because there is only ever one point of view.
  • No index. A range query or an equality lookup on a large table means a full linear scan — there is no structure that lets you skip to the answer.
THE PATTERN, AGAIN

Notice this is the SAME shape of failure every naive solution in this course has had: correctness is fine at toy scale, and every missing property maps to exactly one component this chapter is about to build. That mapping IS the roadmap for §5 — each elimination below adds back exactly the piece the previous attempt was missing.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three intermediate designs, each deriving the next missing piece

Step through the derivation. Each candidate fixes the previous one's worst problem and immediately reveals the next one — this IS how you arrive at the final architecture, not a list handed down from above.

Deriving the architecture, one elimination at a timeSTEP-BY-STEP

Candidate A: one big in-memory object, with locking

Fix the concurrency race with a mutex around every read/write. This genuinely solves the "two writers corrupt each other" problem — but durability is still all-or-nothing: the ENTIRE database lives in RAM until an explicit save, so a crash between saves loses everything since the last one, and there's still no notion of "this specific committed change is safe" independent of "the whole database got serialized recently." Rejected: durability granularity is wrong — it should be per-transaction, not per-manual-checkpoint.

Candidate B: an append-only log, replayed on load

Closer. Instead of overwriting a snapshot, APPEND every operation to a log file; on startup, replay the whole log from the beginning to reconstruct state. This is genuinely WAL-shaped — durability is now per-operation (append is far more crash-safe than overwrite) — but it has a fatal scaling flaw: after a million operations, startup means replaying a million log entries from the very beginning, every time. Real systems solve this with a CHECKPOINT — a periodic snapshot of current state plus a marker for "you only need to replay the log AFTER this point." Correct instinct, missing the checkpoint that makes it practical — motivating chapter 10/11's mechanism directly.

Candidate C: pages + a WAL, but no buffer pool (write straight through)

Add real pages (fixed-size, with a header, so a page can be checkpointed and recovered independently) and a proper WAL-before-data discipline: log the operation, then write the affected page straight to "disk" (in our case, a durable in-memory map standing in for a filesystem). This FIXES durability and checkpointing correctly — but every single operation now does a synchronous "disk" write, with no caching: reading the same hot page twice in a row means "reading from disk" twice. Correct durability model, no performance — motivating the buffer pool directly: cache pages in memory, obey WAL-before-data on eviction, and only then does caching not compromise durability.

WHAT'S STILL MISSING AFTER ALL THREE

Even with pages + WAL + a buffer pool, there is still no isolation between concurrent transactions (two sessions still see the literal same mutable page), no way to avoid a full scan for a lookup, and no way to choose between two different access paths. §6 names these costs explicitly; §7 assembles the final seven-piece architecture that answers all of them.

ARC 06 · WHY THAT STILL HURTS

Pages, WAL, and a buffer pool are necessary — and still not sufficient

  • No isolation. Even with correctly cached, correctly durable pages, two concurrent transactions reading and writing the SAME row still see each other's uncommitted changes immediately — there's one current version of each tuple and no concept of "as of MY snapshot." This directly motivates MVCC: tag every tuple with the transaction that created it and the one that deleted it, and let a snapshot decide what's visible.
  • No way to avoid a full scan. Every SELECT, even an equality lookup on a huge table, must walk every page. This motivates the B+Tree: a structure that turns "scan everything" into "descend O(log n) levels."
  • No way to choose between access paths. Once a B-tree exists, a NEW problem appears: for any given query, is the index actually cheaper than a sequential scan? Sometimes yes (a highly selective predicate on a huge table), sometimes no (a predicate matching half the table, where the extra random I/O of an index scan costs more than just reading every page in order). This motivates a planner: compute both costs from real statistics, and choose.

Closing these three gaps — MVCC, a B-tree, and a planner — plus proving the whole assembly survives a crash, is the rest of this chapter.

ARC 08 · COMPONENT 1 — chapter 3 in miniature

The paged heap file

Every table is a sequence of fixed-size 8,192-byte pages, each a real Uint8Array(8192) backed by a DataView for typed reads/writes — not a JS object pretending to have byte offsets, but actual bytes with actual offsets. The header is simplified from PostgreSQL's real 24-byte PageHeaderData down to the fields that matter for this chapter: pd_lsn (the page's last-modifying WAL position — §10's hook), pd_lower and pd_upper (the two moving boundaries that divide the page), and pd_special (reserved for index pages, chapter 13's real analog to §12's B-tree). Line pointers (ItemIds) grow FORWARD from just after the header; tuple data grows BACKWARD from the end of the page. Free space is exactly pd_upper - pd_lower, and every tuple start is MAXALIGNed — rounded up to the next multiple of 8 — because unaligned access is slower on essentially all real hardware and PostgreSQL, like this toy, simply never allows it to happen.

WHAT REAL POSTGRESQL DOES THAT THIS TOY SKIPS

Real PageHeaderData is 24 bytes and includes a real checksum and a full infomask bit-field per tuple (HeapTupleHeaderData is itself ~23 bytes before any column data) covering HOT-update chains, combo command IDs, and null bitmaps — our tuple header is 8 bytes (xmin+xmax only). Real Postgres also has TOAST: any value too large to fit reasonably in a page gets compressed and/or sliced into a side table, which this toy has no equivalent of at all — a value here that doesn't fit on a fresh page simply fails to insert (§15 lets you see this happen). And real heap pages support HOT updates (chapter 3/5's optimization where an update whose indexed columns didn't change can create the new tuple version on the SAME page without touching any index) — our updateRow always does a plain delete-then-insert and updates every index unconditionally.

ARC 09 · COMPONENT 2 — chapter 9 in miniature

The buffer pool: a fixed frame array and a clock hand

A fixed number of frames, each holding at most one page, indexed by a hash map from (fileId, pageNum) to frame index — exactly chapter 9's BufTable. Each frame tracks a pin count (how many callers currently hold a reference; a pinned frame can never be evicted) and a usage count capped at 5, mirroring real PostgreSQL's BufferDesc.usagecount. Eviction is CLOCK-SWEEP: a hand sweeps the frame array in a ring; on each pass, a frame with usageCount > 0 gets it decremented and is spared, while a frame with usageCount === 0 AND pinCount === 0 is evicted — flushed to disk first if dirty, obeying WAL-before-data (§10).

WHAT REAL POSTGRESQL DOES THAT THIS TOY SKIPS

Real PostgreSQL partitions the buffer mapping table across many LWLocks (chapter 20's BufferMapping wait event) so concurrent backends on different partitions never contend; our toy uses one implicit global sequence of operations (JavaScript is single-threaded, so this is "free," but real Postgres has to engineer it). Real eviction also has a background writer proactively cleaning dirty buffers ahead of the clock hand so foreground backends rarely have to write one themselves (chapter 11); our toy always flushes synchronously, in the foreground, at the moment of eviction. And real buffer pins interact with vacuum (a scan holding a pin blocks vacuum from cleaning that exact page, chapter 20's BufferPin wait event) — a subtlety with no equivalent here since this toy has no vacuum at all.

ARC 10 · COMPONENT 3 — chapter 10 in miniature

The write-ahead log: LSNs, fsync, and full-page writes

Every mutating operation appends a record to an ever-growing array before it touches a page: a monotonically increasing LSN (log sequence number — here just an integer, standing in for real Postgres's byte offset into a WAL segment file), a type (INSERT/UPDATE_OLD/DELETE/ COMMIT/ABORT/CHECKPOINT), and a payload with enough information to redo the operation. fsync is simulated as a separate fsynced boolean per record and a flushedLsn watermark: appending a record is cheap and immediate (like writing into the OS's WAL buffer), but a record only becomes truly durable when wal.flush(lsn) is called — which happens at every COMMIT, every ABORT, and every CHECKPOINT, exactly mirroring when real PostgreSQL's XLogFlush() is invoked. The WAL-before-data rule is enforced at exactly one choke point: flushFrameToDisk(), which — before letting a page's bytes reach the durable disk map — checks whether the WAL has already been flushed at least as far as that page's own pd_lsn, and forces the flush if not.

WHAT REAL POSTGRESQL DOES THAT THIS TOY SKIPS

Real WAL lives in 16 MB segment files that get recycled (renamed and reused) rather than growing forever, has timeline IDs for tracking history across failovers and point-in-time-recovery branches, and every record includes a resource-manager ID and CRC so a partially-written record at the tail (a genuine torn write) can be detected and treated as "the log ends here" during replay. Our toy's array-of-objects log can never be torn — a JS array push is atomic from the runtime's point of view — which quietly skips one of the trickiest correctness properties of a real WAL implementation.

ARC 11 · COMPONENT 4 — chapter 5/6 in miniature

MVCC: xmin, xmax, snapshots, and the visibility rule

Every tuple carries two transaction IDs baked directly into its 8-byte header: xmin (who inserted it) and xmax (who deleted it, or 0 if it's still live). A transaction manager hands out monotonically increasing XIDs and tracks each one's status — in-progress, committed, or aborted — in a clog map (a JS Map standing in for real Postgres's disk-resident pg_xact SLRU pages). A snapshot, captured at BEGIN, is exactly the triple real Postgres uses: {xmin, xmax, xip[]} — the oldest transaction still active, the next XID not yet handed out, and the explicit list of XIDs that were in progress at that exact moment. The visibility function answers one question — is this tuple version visible to this snapshot — using the same logic chapter 5/6 derives: a tuple is visible if its inserting transaction committed AND that transaction wasn't still in-progress (or hadn't even started) relative to the snapshot, AND ITS DELETER, if any, does NOT satisfy that same "committed and visible" test.

WHAT REAL POSTGRESQL DOES THAT THIS TOY SKIPS

Real visibility checks also handle subtransactions (savepoints, tracked via a subtransaction parent map so an aborted savepoint doesn't roll back the whole transaction), combo command IDs (so a transaction can see its own earlier command's inserts but not a later command's, within the SAME transaction — our toy just always sees its own writes unconditionally, which is close but not identical), and clog itself is paged through SLRU (Simple LRU) buffers on disk rather than living forever in one unbounded in-memory map the way our clog does — real transaction history is far too large to keep resident, and SLRU is precisely the mechanism that lets old clog pages age out to disk. There is also no serializable snapshot isolation (SSI) here — our engine offers exactly the semantics of PostgreSQL's default READ COMMITTED (fresh snapshot per statement, in autocommit) or a REPEATABLE-READ-like single-snapshot mode inside an explicit BEGIN, with no anomaly detection beyond what that snapshot rule gives you for free.

ARC 12 · COMPONENT 5 — chapter 13 in miniature

The B+Tree: splits, right-links, and O(log n) lookups

An order-4 B+Tree (each node holds up to 4 keys before splitting — deliberately small so splits happen often enough to watch). Only LEAF nodes hold values (arrays of {pageNum, itemId} references back into the heap — the index never stores the row itself, exactly like real PostgreSQL's nbtree); internal nodes hold only routing keys. Every leaf carries a right pointer to its sibling — the same right-link idea from Lehman & Yao's classic B-link-tree paper that real nbtree uses, which is what makes a range scan possible without re-descending the tree for every key: find the first leaf once, then just follow right pointers.

WHAT REAL POSTGRESQL DOES THAT THIS TOY SKIPS

Real nbtree pages ARE heap-shaped pages too (same 8 KB page format, using pd_special for btree-specific metadata) — our toy tree is plain JS objects with no byte layout at all, which is the single biggest simplification in this chapter. Real btree also needs index vacuuming (dead index entries pointing at heap tuples that were vacuumed away must themselves be removed, chapter 12), a real unique constraint enforcement path distinct from a plain non-unique index, and page-level locking during concurrent splits far more sophisticated than "JavaScript is single-threaded so there's no race." Our B+Tree also has no covering-index (INCLUDE) columns and no support for multi-column keys — equality and range on exactly one column only, and a real unique-constraint index rejects a duplicate key at insert time, which ours does not.

ARC 13 · COMPONENTS 6 & 7 — chapter 16 and chapter 11 in miniature

The mini planner, and crash recovery — the two components that prove the rest

Component 6: the mini planner

For a scan with an equality predicate, the planner computes TWO real costs from statistics the engine gathers from its own tables — page count and row count, both read live off the actual heap, not hardcoded — and picks the cheaper: seqCost = pages·seq_page_cost + rows·cpu_tuple_cost against idxCost = log2(rows)·cpu_index_cost·5 + matches·(cpu_tuple_cost + random_page_cost·pages/rows), where matches is the estimated row count times a selectivity estimate. This is PostgreSQL's real cost model in miniature — the same seq_page_cost/random_page_cost/cpu_tuple_cost GUCs chapter 16 covers, just with fixed defaults instead of a configurable planner. For a JOIN between two known row counts, it computes nested-loop cost (outer × inner × cpu_tuple_cost) against hash-join cost (roughly (outer + inner) × cpu_tuple_cost, since a hash join is linear in both inputs rather than quadratic) and picks the smaller. Watch the winner flip as table size changes in §15's console — a tiny table will correctly prefer a sequential scan even with an index present, because the fixed cost of a random-access index descent isn't worth paying for so few pages.

Component 7: crash recovery — the capstone's actual proof

The CRASH command does something no other button in this course's simulators has done: it GENUINELY discards state. It throws away the entire buffer pool object (any dirty, unflushed page changes are simply gone — there is no way to get them back except by replaying WAL), and it filters the WAL's own record array down to only the records that were marked fsynced — anything appended but never flushed is discarded too, because that's exactly what "not durable yet" means. It also resets the transaction table (clog) back to whatever was durably snapshotted at the last CHECKPOINT, because transaction status is itself durable state that a real crash would need to reconstruct, not an oracle the engine gets to keep for free.

RECOVER then replays every surviving WAL record with an LSN greater than the last checkpoint, in order, applying exactly one of: restore a full-page image (if this was the first touch to that page since the checkpoint), or replay the logical operation (insert a tuple / patch an xmax) otherwise — with one guard on every single record: if (page.pdLsn >= record.lsn) skip. This is chapter 11's REAL idempotency rule, verbatim: a page that's already durably at or past a given LSN must never have that record re-applied, because doing so could double-insert a tuple or otherwise corrupt state that was already correct. COMMIT and ABORT records are replayed by writing directly into the freshly-reset clog — which is precisely how a row inserted by an transaction that never got a chance to log its COMMIT ends up correctly invisible after recovery, even if the row's raw bytes physically made it back onto the page.

THE BUG THIS COURSE FOUND WHILE BUILDING THIS VERY ENGINE

Worth telling on ourselves: an early version of this exact engine reset each page's "dirtied since checkpoint" flag on the durable disk copies at CHECKPOINT time, but forgot to reset it on still-resident, cached buffer-pool frames — which are DIFFERENT objects. The result: the first insert after a checkpoint failed to capture a full-page image, and recovery silently lost every row written before that checkpoint. This is precisely the class of bug real full-page-write logic exists to prevent, and precisely the class of bug that is invisible until you write an assertion that actually crashes the engine and checks the data — which is exactly what §15 lets you do yourself, right now.

WHAT REAL POSTGRESQL DOES THAT THIS TOY SKIPS

Real query planning also considers parallel workers, partitioned tables, foreign-data-wrapper pushdown, and a genetic algorithm for join order once a query has too many tables to exhaustively enumerate (chapter 16) — our planner only ever compares exactly two strategies for exactly one table or one join. Real crash recovery also handles timeline switches (recovering to a point in time on a DIFFERENT historical branch after a failover), archive-based WAL fetching when local segments have been recycled, and hot-standby query conflicts during replay (chapter 18) — none of which a single-process, single-machine toy has any reason to model.

WHERE TO GO NEXT

Read the real source. Subscribe to and lurk on pgsql-hackers. It is the actual design conversation for everything in this course, in real time — threads discussing exactly the kind of tradeoffs chapters 1, 9, and 20 walked you through, argued by the people who made the calls. The commitfest app (commitfest.postgresql.org) is where patches queue for review each development cycle; reading a commitfest thread end to end, even without posting, teaches more about how a mature open-source project actually ships correctness-critical code than any single blog post can.

Find a first patch. The PostgreSQL wiki's "Todo" list and "Reviewing a Patch" pages are the conventional entry points; reviewing someone else's patch — testing it, reading the diff against the source files you now recognize, and posting honest feedback — is a lower-stakes and often more educational first contribution than writing original code. Once you're ready to write something, small, well-scoped documentation or test-coverage patches are the traditional first step into a codebase this large; the engine you built in this chapter is a map of where in that codebase your next question will already have an answer.
