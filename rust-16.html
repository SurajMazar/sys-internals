Async/Await Internals:
The State Machine Underneath

Every time you write .await in Rust, the compiler quietly rewrites your straight-line-looking function into a hand-rolled state machine — an enum with one variant per suspension point, a poll method that resumes exactly where it left off, and zero scheduling logic of its own. Nothing in that sentence involves a new thread, a callback registry, or a promise resolving somewhere in the background. This chapter derives why that design exists, shows you the literal shape the compiler generates for a real two-.await function, and introduces the two things the standard library deliberately does not ship: a way to actually run a Future, and a precise understanding of where async code compiles cleanly and where it doesn't.

ARC 01 · THE PROBLEM

A server with 50,000 open sockets and almost nothing to do

Chapter 15 gave you the tools for CPU-bound concurrency: spawn a thread per unit of work, synchronize with channels or a Mutex. Now point that same toolkit at a different shape of problem — a chat server, an API gateway, a websocket relay — holding tens of thousands of long-lived connections that are idle almost all the time, each one occasionally waking up to send or receive a few hundred bytes. The natural instinct, armed with chapter 15, is std::thread::spawn once per connection. It is worth taking that instinct completely seriously and following the arithmetic to where it actually breaks.

Start with what a thread costs. Rust's std::thread::spawn reserves a 2 MiB stack by default (overridable via std::thread::Builder::stack_size or the RUST_MIN_STACK environment variable) on top of the OS thread the kernel must create — on Linux that's a real pthread, whose glibc default stack is a separate, larger 8 MiB when spawned directly, plus a task_struct, a pinned (non-swappable) kernel-mode stack of several kilobytes, and scheduler bookkeeping the kernel now carries for the life of that thread — whether or not it ever does anything.

THE ARITHMETIC AT 50,000 CONNECTIONS

50,000 threads × 2 MiB (Rust's default stack) ≈ 97.7 GiB of reserved address space for stacks alone. On a 64-bit machine that number by itself isn't fatal — user-space address space on x86-64 Linux is 128 TiB, and stack pages are only committed to physical memory as they're actually touched. What is fatal, well before RAM runs out, are the parts that aren't lazy: kernel per-thread structures that are pinned and non-swappable, and the kernel scheduler having to track 50,000 runnable-or-blocked entities. Most production systems hit a wall long before the RAM math would predict one — ulimit -u (max user processes/threads) defaults to numbers in the low thousands to ~15,000 on many distributions, and container/systemd cgroups often impose an even lower TasksMax. Cross that line and thread::spawn doesn't slow down — it starts failing outright (§4).

And even below that ceiling, cost isn't the only problem: a context switch between threads costs roughly 1–5 µs, and the CPU pays cache and TLB pressure switching between thousands of independent stacks and register files — overhead that scales with the number of waiting threads, not the amount of real work being done. This exact wall has a name: the C10K problem, coined by Dan Kegel in 1999 for the point (then, ~10,000 concurrent connections) where thread-per-connection architectures visibly stopped scaling on commodity hardware. Modern hardware moved the wall — but it did not remove it, and cloud-native workloads now routinely target C100K to C1M: a single modest box holding a million concurrent, mostly-idle connections.

So the real requirement, stated precisely: you need tens of thousands to millions of independently suspendable, independently resumable units of work, where the cost of one sitting idle is close to zero, and where a single OS thread (or a small pool of them) can efficiently ask "which of you actually has work to do right now?" and only spend CPU on those. That question — "which of these ten thousand sockets are ready?" — already has a cheap, real answer at the OS level: epoll on Linux, kqueue on BSD/macOS, IOCP on Windows. One syscall, thousands of watched file descriptors, a short list of the ones that are actually ready back. What's missing is a way to write ordinary-looking Rust code on top of that primitive without manually juggling callbacks for every socket. That missing piece is async/.await, and the rest of this chapter derives exactly what it compiles into.

ARC 02 · HISTORICAL CONTEXT

Async Rust's rocky decade: 2014 → 2023

Unlike ownership and borrowing — which shipped essentially complete at Rust 1.0 in 2015 — async Rust was assembled over roughly a decade, in public, with real false starts. Understanding the timeline explains design decisions that otherwise look arbitrary, especially "why doesn't std just give me a way to run a Future?" (spoiler: it never will, on purpose — see the callout below).

DEEP CONTEXT · WHY DID std NEVER SHIP AN EXECUTOR?

This is a deliberate, debated, and still-controversial decision. std ships the Future trait, Poll, Context, Waker, and Pin — the vocabulary — but never a scheduler to drive them. The reasoning: a no_std embedded target has no allocator to spawn tasks onto a heap-allocated queue; WebAssembly historically had no real threads; a single-threaded UI event loop and a work-stealing multi-core server scheduler are legitimately incompatible designs, not two configurations of one design. Baking in any one choice would be wrong for a large fraction of Rust's users. The cost of that restraint is exactly what §2's later timeline entries show: years of ecosystem fragmentation while tokio and async-std competed for the role Go simply built into its language.

ARC 03 · NAIVE SOLUTION

Attempt #1: thread-per-connection, taken to its logical scale

Derive the architecture honestly, the way §1 set it up. The simplest possible concurrent server in Rust is exactly what chapter 15 taught: one OS thread per connection. This is real, idiomatic, compiling Rust — not a strawman written to fail:

Rustthread_per_conn.rs — real, compiles, correct — until it doesn't scale
use std::io::{Read, Write};
use std::net::TcpListener;
use std::thread;

fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind("0.0.0.0:7000")?;

    for stream in listener.incoming() {
        let mut stream = stream?;
        // One OS thread per connection. `stream` is MOVED into the closure —
        // each thread owns its socket outright, so there is no shared state
        // between connections at all, and therefore no locks, no races.
        thread::spawn(move || {
            let mut buf = [0u8; 4096];
            loop {
                match stream.read(&mut buf) {
                    Ok(0) => return,                 // client closed
                    Ok(n) => { if stream.write_all(&buf[..n]).is_err() { return; } }
                    Err(_) => return,
                }
            }
        });
    }
    Ok(())
}

This deserves real respect, not mockery — it already gets several things right. Ownership makes it trivially correct: each thread's closure captures its own stream by move, so there is architecturally no way for two threads to race on the same socket. For tens or low hundreds of connections, this is genuinely how you should write a small Rust network tool — it is simple, it is safe by construction, and it needs none of the machinery this chapter is about to introduce.

Watch it fail as connection count climbs — not because any query is slow this time (that was chapter 15's problem shape), but purely because these connections are long-lived and mostly idle, like real websockets: nobody's socket ever closes, so nobody's thread ever exits.

ARC 04 · WHY IT FAILS

The failure isn't a bug in your code — it's arithmetic hitting a wall

Notice what kind of failure this is: the code above has no logic error, no data race, nothing the borrow checker could have caught. std::thread::spawn itself doesn't even return a Result you could mishandle — its real signature is pub fn spawn<F, T>(f: F) -> JoinHandle<T>, and internally it calls Builder::new().spawn(f).expect(...). When the OS refuses to create one more thread — ulimit -u exhausted, or the address-space/kernel-memory pressure from tens of thousands of stacks — that expect panics the whole process:

WHAT YOU ACTUALLY SEE IN PRODUCTION

thread '<unnamed>' panicked at 'failed to spawn thread: Os { code: 11, kind: WouldBlock, message: "Resource temporarily unavailable" }' — EAGAIN from the kernel's pthread_create, wrapped in Rust's io::Error. This is a real, commonly reported failure mode, and the fact that it's a panic rather than a graceful degradation is itself instructive: the naive architecture has no fallback path for "too many connections" — it either accepts one more thread or it doesn't exist as a program anymore. A second, equally common trigger is entirely orthogonal to Rust: services deployed under systemd or inside containers often inherit a TasksMax/cgroup thread-count limit (frequently in the low thousands by default) that bites long before any language-level limit does — the exact same EAGAIN, for a reason that has nothing to do with the code at all.

Quantify the ceiling honestly, the way §1 promised:

  • Address space: rarely the actual limit on 64-bit hosts — the numbers are large enough that other limits bite first.
  • ulimit -u / RLIMIT_NPROC: Linux counts threads against the same limit as processes; distribution defaults commonly sit in the low thousands to ~15,000 for a regular user.
  • cgroup TasksMax: systemd units and container runtimes often cap total tasks per unit — a production-grade way to accidentally reproduce §1's wall inside a box that technically has plenty of RAM.
  • Kernel-resident cost per thread: a pinned (non-swappable) kernel stack (commonly several KiB to 16 KiB), plus task_struct and scheduler bookkeeping — real memory the kernel spends whether or not the thread does anything, unlike the lazily-paged user-space stack.
  • Scheduling overhead: every additional blocked-or-runnable thread is one more entity the kernel's scheduler tracks on every scheduling decision — a cost with no analogue for a suspended Future, which is just inert data the kernel doesn't know exists.

None of this is a defect in thread-per-connection's logic — it is a mismatch between the unit of concurrency (a full OS thread, several kilobytes of kernel state minimum) and the actual workload (a task that is asleep 99.9% of the time and needs, in principle, only enough memory to remember where it was). §5 derives the fix from that mismatch directly.

ARC 06 · WHY THAT STILL HURTS

What async/await doesn't fix, and what it costs you

Be honest about the bill, the way every chapter in this course has been. Async Rust solves the memory-per-idle-task problem decisively — and introduces a genuinely steeper set of costs than thread-per-connection ever had:

  • Function coloring. An async fn and a plain fn are different kinds of thing — you cannot write .await inside a non-async function, and calling an async function from ordinary synchronous code requires an executor to actually drive it (block_on). Every function on the path to an async call either becomes async itself or explicitly bridges the boundary — a real, well-known pain point across every language that has added this feature (the name "function coloring" predates Rust; it applies here without modification).
  • No default runtime, ever. §2's callout wasn't a throwaway remark: you must choose tokio, async-std, smol, or an embedded-specific executor, and code written assuming one runtime's I/O types often does not run under another's — a real, still-current practical headache, not a solved problem from the "runtime wars" era.
  • Compile times and error messages. Deeply chained .awaits produce large, compiler-generated, effectively anonymous Future types (§8 shows why); heavily generic async code is a documented contributor to slow builds, and a failed trait bound on one of these types can print screens of nested generic noise before naming the actual problem.
  • Debuggability. A stack trace captured inside an executor shows the executor's own poll loop, not your logical call chain — which is precisely why a dedicated diagnostic tool (tokio-console, §11) had to be built rather than relying on ordinary debuggers.
  • A steeper hill to climb. Pin, Send bounds on futures, and the runtime-choice decision are concepts a purely synchronous Rust programmer never has to learn. This is real cost, not a rite of passage to be dismissed — weigh it honestly against the workload in §9.

Executor calls poll. poll either finishes (Poll::Ready) or returns Poll::Pending after stashing the Waker it was handed with whatever will know when to call it (the reactor, a timer, another task). The reactor eventually calls that Waker, which re-queues the task with the executor. The executor calls poll again. That is the entire mechanism — no OS thread is ever suspended and resumed the way §1's threads were; the Future's own state, sitting as ordinary data, is the suspended computation. §8 shows you exactly what that data looks like.

ARC 08 · INTERNAL IMPLEMENTATION

What the compiler actually generates

This is the center of the chapter. Take the two-.await function this whole chapter uses as its running example:

Rustthe async fn you write
async fn fetch_user_profile(id: u64) -> Profile {
    let user  = fetch_user(id).await;         // await point #1
    let posts = fetch_posts(user.id).await;   // await point #2
    Profile { user, posts }
}

The compiler does not generate a callback chain, and it does not spawn anything. It generates a state machine — an enum with exactly one variant per suspension point (plus a start state and a finished state), and a single poll method whose body is a match on the current variant. The shape below is illustrative — real compiler-generated types are anonymous and compiler-internal, not writable in surface syntax — but it is semantically exact, field for field:

Rustillustrative — the shape rustc's desugaring produces
enum FetchUserProfileState {
    Start          { id: u64 },
    AwaitingFirst  { fut: FetchUserFuture },
    AwaitingSecond { user: User, fut: FetchPostsFuture },
    Done,
}

impl Future for FetchUserProfileState {
    type Output = Profile;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Profile> {
        loop {
            match &mut *self {
                Self::Start { id } => {
                    let fut = fetch_user(*id);            // build 1st sub-future
                    *self = Self::AwaitingFirst { fut };  // no poll needed to advance here
                }
                Self::AwaitingFirst { fut } => {
                    let fut = unsafe { Pin::new_unchecked(fut) };
                    match fut.poll(cx) {
                        Poll::Pending      => return Poll::Pending,
                        Poll::Ready(user) => {
                            let fut = fetch_posts(user.id);
                            *self = Self::AwaitingSecond { user, fut };
                        }
                    }
                }
                Self::AwaitingSecond { user, fut } => {
                    let fut = unsafe { Pin::new_unchecked(fut) };
                    match fut.poll(cx) {
                        Poll::Pending       => return Poll::Pending,
                        Poll::Ready(posts) => {
                            let profile = Profile { user: user.clone(), posts };
                            *self = Self::Done;
                            return Poll::Ready(profile);
                        }
                    }
                }
                Self::Done => panic!("polled after completion"),
            }
        }
    }
}

Read the variants as a direct answer to "what must survive this suspension point, and nothing more" — the exact liveness question the borrow checker's own dataflow analysis already answers elsewhere in the compiler (rust-19 will show you that machinery directly). Start needs only the argument, id. Once fetch_user(id) is constructed, id has been consumed into fut and is never read again — so AwaitingFirst doesn't carry it. Once fetch_user resolves, user must survive all the way to the final Profile construction, so AwaitingSecond carries user alongside the second sub-future. Done needs nothing at all. This is "capturing exactly the locals needed across each suspension," made completely literal.

Why Pin<&mut Self> and not just &mut Self?

This is the one piece of the puzzle that isn't optional ceremony. A more elaborate async function can end up holding, in one state, a reference into data stored in an earlier field of the very same generated struct — for example, a local buffer declared before an .await and then borrowed by a sub-future that reads into it. That is a self-referential struct: one field pointing at another field's address inside the same value. Ordinary move semantics (rust-04) only track "is this value still valid," not "is this pointer inside it still pointing at the right address" — if the whole struct is moved (its bytes copied to a new location, the old one freed or reused), a self-reference computed against the old address is now a real dangling pointer, and nothing about "value used after move" fires to catch it.

Pin<P> closes exactly that hole. For a pointee that is !Unpin (opted out of the auto-trait that means "safe to move even while pinned" — every compiler-generated async state machine capable of being self-referential is !Unpin), holding a Pin<P> to it is a promise, enforced by the type system, that the value will never move again for the rest of its life. Future::poll takes self: Pin<&mut Self> specifically so an executor can never accidentally move a suspended state machine mid-flight — which is also exactly why Pin (stabilized 1.33) had to exist before async/.await could stabilize (1.39): §2's ordering was never a coincidence. In practice you rarely write Pin by hand — Box::pin, the tokio::pin! macro, and every executor's internals handle it for you.

How big is this thing, actually?

Rust enums are sized like a tagged union: a small discriminant tag, plus room for the largest variant's payload — not the sum of every variant. An async state machine's largest variant is whatever suspension point has the most live data at once, so a function with many sequential, small .awaits can still end up with a surprisingly large Future if even one suspension point happens to be holding a lot. The same problem, five ways

Every ecosystem serious about massive I/O concurrency has faced §1's exact arithmetic. The spread of answers is a proof by exhaustion, same as chapter 15's concurrency-primitives table: there is no dominant strategy, only different placements of the same underlying costs.

Rust's specific bet, read off this table: zero runtime cost while idle, purchased by pushing the scheduling decision (and the Pin/Send bookkeeping that makes it sound) onto the programmer at compile time, rather than hiding it inside a language-mandated runtime the way Go and the BEAM do. Neither choice is wrong — they are priced differently for different constraints (embedded and WASM targets in particular could not have afforded a mandatory scheduler and GC, which is exactly why Rust's answer looks the way it does).

ARC 10 · PERFORMANCE / SAFETY CHARACTERISTICS

The number that justifies all of this: bytes per idle unit of work

  • Idle OS thread: ~2 MiB reserved stack (Rust default) plus kernel-resident structures — real RSS once touched commonly runs from tens of KB into low MB per thread.
  • Idle async task: a state machine with a handful of small fields is commonly tens to a few hundred bytes (§8's slider makes the exact number concrete) — routinely a four-to-five-order-of-magnitude difference from a thread, which is the entire reason C1M (a million concurrent connections on one modest box) is achievable with async and effectively impossible with thread-per-connection.
  • poll() call cost: a no-op state check is a few to a few tens of nanoseconds — a pointer comparison and a jump table, nothing more — versus a thread context switch at roughly 1–5 µs: two to three orders of magnitude apart when a task is woken very frequently.
  • Where async buys nothing: be honest about the other side. Purely CPU-bound work with no real .await has nothing to suspend on — the state machine's match-in-a-loop overhead and the larger stack frames from every captured local (§8) can make it a strict loss versus a plain function call. Async is a tool for I/O-bound waiting, not for making computation faster.
  • A compile-time safety win, not just a performance one: whether a given Future implements Send is computed structurally, transitively, from every type it captures — the compiler either proves the whole state machine is safe to move across threads or it doesn't, entirely at compile time, with zero runtime check. Compare that to Go, Node, or plain Java threads, where a cross-thread data hazard is a runtime concern you find with a race detector (if you're lucky) rather than a compiler diagnostic you get before the code ever runs.

ARC 11 · REAL-WORLD PRODUCTION

Three footguns you will eventually meet

1. Blocking the executor: the reason tokio-console exists

Polling is cooperative — the executor cannot preempt a poll() call the way the OS preempts a thread. If any task's poll() calls something genuinely blocking — a synchronous file read, a CPU-heavy parse with no .await inside it, std::thread::sleep — it occupies the OS thread running the executor for the entire duration, and every other task assigned to that thread stalls, even ones the reactor has already marked ready to make progress. On a single-threaded ("current-thread") executor this freezes the whole program; on a multi-threaded one it starves whatever happened to land on that worker until work-stealing (if any) rebalances. This class of bug is common enough, and hard enough to spot from a stack trace (§6), that the tokio team built and shipped a dedicated diagnostic tool — tokio-console — specifically to surface tasks that hog a worker thread's poll loop for too long. Its existence is itself the incident report: ordinary debugging tools weren't enough.

2. Holding a MutexGuard across .await

std::sync::MutexGuard<T> deliberately does not implement Send — on some platforms, unlocking a mutex must happen on the same OS thread that locked it, so the type is built to make moving a held guard to another thread impossible. A multi-threaded executor may resume a suspended task on a different worker thread than the one that last polled it — so a Future that still holds a MutexGuard across an .await point is transitively non-Send, and tokio::spawn (whose real signature you'll see in §13 requires F: Future + Send + 'static) refuses to compile it:

Rustfails to compile — guard alive across .await
use std::sync::Mutex;

async fn increment(counter: &Mutex<i64>) {
    let mut guard = counter.lock().unwrap();
    *guard += 1;
    some_async_io().await;   // ← guard is still alive right here
}                                // guard drops here — AFTER the await point

// tokio::spawn(increment(&counter));   // ← rejected at compile time
error[E0277]: `MutexGuard<'_, i64>` cannot be sent between threads safely
   --> src/main.rs:9:5
    |
9   |     tokio::spawn(increment(&counter));
    |     ^^^^^^^^^^^^ `MutexGuard<'_, i64>` cannot be sent between threads safely
    |

            implemented for `MutexGuard<'_, i64>`

The compiler is not being pedantic — it has found a real hazard: without this check, an executor could legitimately move that in-flight state machine to another OS thread while the guard thinks it's still on the thread that locked it. The fix is exactly what §6 warned you async introduces: use tokio::sync::Mutex instead, whose .lock().await returns a guard that is Send (it's designed for exactly this), or restructure the code so the guard is dropped before the .await line. Tokio's own official tutorial dedicates an entire callout to this exact pattern, precisely because so many people hit it in production before ever reading the docs.

3. Mixing runtimes and nested block_on

Because std ships no executor (§2), every crate doing real async I/O must pick one, and calling a blocking bridge like Runtime::block_on from inside code that is already running on that same runtime is a common, specific mistake with a specific, real panic message: "Cannot start a runtime from within a runtime. This happens because a function (like `block_on`) attempted to block the current thread while the thread is being used to drive asynchronous tasks." The fix is architectural, not a one-line patch: never call a blocking-runtime-driver from code that might already be running inside one — use tokio::task::spawn_blocking to hand genuinely blocking work to a dedicated thread pool instead, and keep async and sync entry points cleanly separated at your program's boundary.

Reading the real thing: core::future, std::task, and tokio's shape

The vocabulary this whole chapter has been using is not hypothetical — it is a small, stable, precisely specified corner of the standard library, plus one real crate's runtime built on top of it.

The trait itself — this is the entire contract, verbatim in shape:

Rustcore::future::Future — the real, stable definition
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),
    Pending,
}

A Waker is deliberately type-erased so any executor can build one for any task type without Future knowing anything about executors — internally it's a fat pointer to task data plus a vtable of clone/wake/drop functions (RawWaker/RawWakerVTable). The ergonomic surface most code actually uses is the Wake trait, stable since Rust 1.51:

Ruststd::task::Wake — the ergonomic path most executors use
pub trait Wake {
    fn wake(self: Arc<Self>);
    fn wake_by_ref(self: &Arc<Self>) { /* default: clone + wake */ }
}

// blanket impl in std — this is how Arc<YourTaskHandle> becomes a real Waker:
impl<W: Wake + Send + Sync + 'static> From<Arc<W>> for Waker { /* .. */ }

And a real, complete, single-threaded executor — under 30 lines, no crates, actually compiles — to make "executors are the thing that calls poll in a loop" completely concrete:

Rustmini_executor.rs — real, minimal, busy-polling on purpose
use std::collections::VecDeque;
use std::future::Future;
use std::pin::Pin;
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};

struct NoopWaker;
impl Wake for NoopWaker {
    fn wake(self: Arc<Self>) {} // a real executor would re-queue the task here
}

struct MiniExecutor {
    tasks: VecDeque<Pin<Box<dyn Future<Output = ()>>>>,
}

impl MiniExecutor {
    fn spawn(&mut self, fut: impl Future<Output = ()> + 'static) {
        self.tasks.push_back(Box::pin(fut));
    }

    fn run(&mut self) {
        let waker: Waker = Arc::new(NoopWaker).into();
        let mut cx = Context::from_waker(&waker);
        while let Some(mut task) = self.tasks.pop_front() {
            match task.as_mut().poll(&mut cx) {
                Poll::Ready(()) => {}                          // done — drop it
                Poll::Pending   => self.tasks.push_back(task), // not ready — back of the line
            }
        }
    }
}

This is deliberately the crudest possible executor — it never sleeps, it just spins the whole queue forever (a real reactor-backed executor uses the Waker to know exactly when to wake, instead of busy-polling). But it satisfies the entire Future contract, and it is exactly the loop §7's callout described: pop a task, call poll, reschedule on Pending, drop on Ready. tokio::spawn's real signature shows what a production-grade version demands of the futures you hand it, tying directly back to §11's MutexGuard incident:

Rusttokio::task::spawn.rs — the real, current signature
pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
where
    F: Future + Send + 'static,
    F::Output: Send + 'static,

Every word of that where clause is load-bearing: Send because tokio's multi-threaded scheduler may resume this future on a different worker thread than the one that last polled it (§11); 'static because the spawned task must be able to outlive the function that spawned it — it runs independently, on its own schedule, until it completes.
