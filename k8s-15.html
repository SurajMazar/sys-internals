ARC 01 · THE PROBLEM

You cannot debug a system you cannot see

Take a cluster with 200 nodes running 6,000 Pods that are constantly being created, rescheduled, and destroyed by the reconciliation loops covered in chapter 9. Every assumption that host-based monitoring quietly relies on — a stable hostname, a process that outlives your SSH session, a log file that stays on the same disk — is false here by design. A Pod's IP, name suffix, and even the node it runs on are all treated as disposable (chapter 2). If your observability strategy assumes stability, it breaks the moment the scheduler does its job correctly.

Unpack "observability" into the three questions an operator actually needs answered, continuously, without logging into a node:

  • Metrics — numeric time series: how much CPU and memory is this container using right now, and how has that changed? This is what feeds autoscaling decisions and capacity dashboards.
  • Logs — discrete text records your application emits. Kubernetes does not build you a log aggregation pipeline (that's Fluent Bit/Loki/ELK territory, deliberately out of scope for the core project) — but it does guarantee a place kubelet writes stdout/stderr to, which every log shipper reads from.
  • Control-plane record-keeping — Events (what a controller observed and decided) and the audit log (what the API server was asked to do, by whom). These are not your application's story — they are Kubernetes' own account of itself, and they exist independently of whatever you build on top.

This chapter goes deep on the two axes Kubernetes itself instruments precisely and natively — the resource-metrics pipeline built on cAdvisor, and the probe state machine and control-plane record-keeping built into kubelet and the API server — because every third-party observability stack you will ever operate is layered on top of exactly these primitives, not a replacement for them.

WHY THIS MATTERS FOR PRODUCTION

Almost every "Kubernetes is flaky" incident report resolves to one of three root causes covered in this chapter: a misconfigured probe restarting a healthy container faster than it can boot (§11), an unbounded metric label turning a monitoring stack into the outage (§6, §10), or an operator discovering after an incident that the audit log they needed wasn't being written at the level they assumed (§8c). None of these are exotic — they are the direct, predictable consequence of the mechanisms in this chapter, misunderstood.

DEEP CONTEXT · WHY METRICS AND EVENTS EVOLVED SEPARATELY

cAdvisor answers "how much" (a number), Events answer "what happened and why" (a sentence with structure). They were never the same problem: cAdvisor's ancestry runs through Google's internal per-container resource accounting tooling and became a piece of infrastructure every node needs locally; Events are an API-server-native object type that controllers write to as a side effect of reconciling, going all the way back to Kubernetes' earliest releases. The two pipelines only started sharing a UI surface (kubectl describe pod shows both) once operators needed a single place to correlate "usage spiked" with "and here's what the scheduler/kubelet did about it."

ARC 03 · NAIVE SOLUTION

Attempt #1: SSH, docker stats, and a curl loop

Derive it honestly, the way an operator would before reading any of this. You have a fleet of nodes and need three things: resource numbers, log tails, and "is my app up." The obvious first move uses tools you already know:

bashnaive-observe.sh — the strawman, annotated
#!/usr/bin/env bash
# "monitoring" before you have a monitoring stack

# 1. resource usage: SSH into every node, one at a time
for node in $(cat nodes.txt); do
  ssh "$node" 'docker stats --no-stream'          # per-node snapshot
  ssh "$node" 'docker ps -a --filter status=exited' # crashed containers?
done

# 2. logs: tail whatever container kubectl currently thinks exists
for pod in $(kubectl get pods -o name); do
  kubectl logs "$pod" --tail=50 | grep -i error
done

# 3. "liveness": a hand-rolled curl loop
while true; do
  curl -sf http://$APP_IP:8080/healthz || \
    ssh "$node" "docker restart $container_id"       # restart on failure
  sleep 30
done

Every line here is defensible in isolation — it is exactly what you'd reach for with nothing installed. Step through what happens when this script meets a real, churning cluster instead of the three static nodes it was written against.

ARC 04 · WHY IT FAILS

Ephemeral identity breaks every assumption, quantified

The naive script isn't merely slow — it is structurally wrong for a system whose entire value proposition (chapter 1) is churning Pods across nodes without asking you. Three failure modes, each with real numbers:

  • SSH fan-out doesn't scale linearly, and worse, it doesn't scale at all past a point. 200 nodes × ~150–300 ms per SSH round-trip (auth negotiation, not the command itself) run serially is 30–60 seconds per sweep — during which the cluster you're inspecting has already changed. Run it in parallel and you've built an ad hoc fleet-wide fan-out tool with no backpressure, hitting every node's sshd simultaneously — itself a load-generation event.
  • Pod identity is a moving target. A ReplicaSet-managed Pod that OOMs and gets rescheduled comes back with a new name and a new IP, typically on a different node (chapter 8's scheduler doesn't prefer the old one). A script holding a stale nodes.txt/pod-name list silently checks nothing — no error, no signal, just quietly wrong data, which is worse than an outage because nobody notices.
  • External HTTP checks can't see internal state. The curl loop proves a socket accepted a TCP handshake and returned 200. It cannot tell you the event loop behind that response is deadlocked, that the process leaked every file descriptor, or that a thread pool is exhausted while the health endpoint happens to be served by an unrelated, still-healthy thread. This is precisely the class of failure real probes are built to close — and precisely the class of failure a naive external check cannot.
THE NUMBERS, AT SCALE

Extrapolate to the SLO envelope this course cites repeatedly: a 5,000-node cluster running near its documented ~150,000-Pod ceiling. A serial SSH sweep at 200 ms/node is 1,000 seconds — over 16 minutes — per "snapshot," by which time a meaningful fraction of those Pods have already been rescheduled at least once. This is not a tuning problem; it is proof that polling from outside the cluster, keyed by identity that changes underneath you, cannot converge. The fix has to live inside the system that owns Pod identity — which is exactly where cAdvisor, the prober, and the API server's own event/audit machinery live.

THE PATTERN, NAMED

Every fix above is the same move: stop asking from outside, start reporting from inside. cAdvisor lives inside kubelet, which already owns the container. The prober's goroutines live inside kubelet, which already has permission to kill and restart the container it's checking. Events and audit records are written by the components (controllers, the API server itself) that already know the fact being recorded, at the moment they know it. Nothing in this chapter's "final architecture" involves a new process reaching in from outside to ask a question the system could instead answer proactively.

ARC 06 · WHY THAT STILL COSTS

The bill: history, cardinality, and best-effort delivery

Moving the collector inside the system fixes identity and fan-out — it does not make observability free. Four costs you operate against every day:

  • metrics-server has no memory. It is deliberately in-memory-only, holding roughly one scrape window per node (tens of seconds). Restart it and every historical number is gone — by design, because its only customer is the Metrics API feeding live autoscaling decisions, not a dashboard. "What was CPU usage two hours ago" is a question metrics-server structurally cannot answer.
  • Prometheus turns "how much" into "how much, sliced by every label," and cardinality is a cost you pay per unique combination. Add one high-cardinality label — a raw Pod name, a request path with an embedded ID, a customer ID — and you don't add one metric, you multiply your active series by however many distinct values that label takes. This is quantifiable; play with it below.
  • Events are best-effort and short-lived on purpose. The client-side recorder coalesces identical events (bumping a count field rather than writing N objects) and the API server expires them after a default --event-ttl of one hour. They were designed for a human staring at kubectl describe minutes after something went wrong, not for compliance retention.
  • Audit logging at the wrong level is a self-inflicted disk-and-CPU tax. The RequestResponse level captures full request and response bodies for every matched request — a list of every Pod in a busy namespace can be megabytes, logged on every poll.

THE INDUSTRY'S ANSWER — AND ITS ADMISSION

Nobody runs a single unbounded Prometheus at real scale: the standard fix is federation or a remote-write long-term-storage layer (Thanos, Cortex, Mimir) that shards and compacts what a single Prometheus process can't hold — plus sample_limit on scrape configs and relabeling rules that drop dangerous labels before they become series. Every one of these is an admission that pull-based, unbounded-label metrics collection has a real cost ceiling, the same way the connection pooler admission works in the PostgreSQL course's process-model chapter.

ARC 08 · INTERNAL IMPLEMENTATION

The real mechanism, byte and counter by counter

Three pieces, in the order you'd need them to debug a real incident: (a) the probe state machine — the exact math this chapter's simulator implements, (b) the metrics pipeline's real wire shapes, (c) Events and audit logging's real object shapes.

(a) Probes: the real counter-based state machine

A probe is not "run a check every N seconds and act on the result." It's a per-container state machine with five configurable inputs, and kubelet's prober worker evaluates it exactly the same way for every container in the cluster:

YAMLPod spec — the five fields that drive the state machine
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: web
    image: web:1.4
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      initialDelaySeconds: 20   # wait before the FIRST probe ever fires
      periodSeconds: 10          # default 10 — time between probes
      timeoutSeconds: 2           # default 1 — no response by then = Failure
      failureThreshold: 3         # default 3 — consecutive fails to act
      successThreshold: 1         # MUST be 1 for liveness & startup
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
      failureThreshold: 3
      successThreshold: 1         # readiness may set this > 1
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30        # slow-boot budget: 30 × 10s = 300s
      periodSeconds: 10

The API server's validation rejects successThreshold != 1 for livenessProbe and startupProbe — a container is either healthy or it isn't; there's no meaningful "half-recovered" state that should suppress a restart decision. Only readinessProbe lets you require several consecutive successes before rejoining traffic, which is exactly what you want for an app that briefly returns 200 while still warming a cache.

Now the mechanism, worked through second by second on the liveness example above. This is the same algorithm — resultRun counting consecutive identical outcomes, threshold-gated state changes — that §15's simulator lets you drive interactively:

kubelet's prober worker, tick by tickSTEP-BY-STEP

The startup probe adds one more rule worth stating precisely: while a startupProbe is configured and has not yet recorded a success, kubelet does not run the liveness or readiness probes for that container at all. This is why a slow-booting JVM app with a 90-second warm-up doesn't need a 90-second initialDelaySeconds on its liveness probe (which would also mean 90 seconds of not restarting a container that crashes 2 seconds after boot) — the startup probe absorbs the boot-time budget and liveness/readiness only begin once it's proven the app is actually up.

(c) Events and the audit log: the control plane's own account of itself

An Event is an ordinary API object, written by a controller's EventRecorder the instant it makes a decision — it is not derived or reconstructed after the fact:

YAMLv1/Event — as `kubectl get events -o yaml` shows it
apiVersion: v1
kind: Event
involvedObject: { kind: Pod, name: web-7f9c8d6b5-abcde, namespace: default }
reason: Unhealthy
message: 'Liveness probe failed: HTTP probe failed with statuscode: 503'
source: { component: kubelet, host: node-3 }
firstTimestamp: "2026-08-11T10:14:40Z"
lastTimestamp: "2026-08-11T10:15:10Z"
count: 3
type: Warning

Audit logging is a different animal: it is generated by the API server itself, for every request that reaches it, independent of whether any controller ever notices. A policy assigns one of exactly four levels per matching rule, evaluated top-to-bottom, first match wins:

YAMLaudit.k8s.io/v1 Policy — the four levels in practice
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  - level: None                      # drop this traffic entirely — cheapest, evaluated first
    users: ["system:kube-proxy"]
    verbs: ["watch"]
    resources: [{ resources: ["endpoints", "services"] }]
  - level: RequestResponse            # request AND response bodies — expensive, scope narrowly
    resources: [{ group: "", resources: ["secrets", "configmaps"] }]
  - level: Request                    # request body, no response body
    verbs: ["create", "update", "patch", "delete"]
  - level: Metadata                   # who/what/when only — the default catch-all
JSONaudit.k8s.io/v1 Event — one line the log backend actually writes

PROBE TYPES: WHAT EACH ONE ACTUALLY EXERCISES

httpGet needs an HTTP server in the container and proves a 2xx/3xx response. tcpSocket is cheapest — it proves a listener accepted a connection, nothing about application correctness. exec runs a process inside the container's namespaces via the CRI — the same namespace-entry mechanism kubectl exec uses (one-sentence cross-reference to the Container Internals course) — and is the most expensive per-check, since it forks a process every period. A native grpc probe type (graduating to GA in Kubernetes 1.27) speaks the standard gRPC health-checking protocol directly, finally retiring the common pre-1.24 hack of shipping a grpc-health-probe binary into the image just so exec could call it.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Numbers you can predict before you provision anything

  • Probe overhead is purely per-node, never control-plane. At the course's cited 5,000-node / 150,000-Pod SLO envelope, with roughly 1.5 probes/Pod at the 10s default periodSeconds, that's on the order of ~22,500 probe executions per second cluster-wide — entirely local kubelet↔container traffic. The API server never sees a single probe request; this is a scaling axis that is flat with respect to control-plane load, unlike almost everything else in this course.
  • Metrics scraping is not. A Prometheus instance targeting kubelet/cAdvisor endpoints across 5,000 nodes, plus node-exporter and any per-namespace kube-state-metrics shards, is tens of thousands of scrape targets — real deployments at this size are federated or split across multiple Prometheus instances precisely because a single binary's WAL and query engine have a practical ceiling well below that.
  • Cardinality memory, roughly. A commonly cited operational rule of thumb is ~1–3 KB of resident memory per active Prometheus time series (index + in-memory head chunk). The calculator in §6 turns any pods × metrics × label-combos figure directly into a memory number — this is not a hypothetical, it is the dominant capacity-planning input for any Prometheus deployment on Kubernetes.
  • Events share etcd's real constraints. An Event is an ordinary object subject to etcd's recommended <8 KB-per-value guidance (chapter 7) — a verbose, repeatedly-updated message field can approach it — and high Pod churn multiplies Event write volume, one of several reasons --event-ttl (default 1h) exists rather than retaining everything.

ARC 11 · REAL-WORLD PRODUCTION PATTERNS

Three incidents you will eventually meet

Incident 1: The liveness-probe death spiral

An app's /healthz handler checks downstream dependency connectivity — including the database. The database has a brief network blip. Every replica's liveness probe fails simultaneously (they all share the same dependency), each crosses its failureThreshold within seconds of each other, and kubelet restarts every replica at once. The restarted processes all hit cold caches and reconnect pools simultaneously, generating a connection storm against a database that had only briefly hiccupped — turning a transient blip into a full outage that outlasts the original cause by minutes. This is exactly why the Kubernetes documentation is explicit that liveness probes should never check downstream dependencies — liveness should answer "is this process itself deadlocked," a question with no correct answer that depends on another service's health. Readiness probes are the right place to check dependencies, because a readiness failure only removes a Pod from rotation — it never restarts a process that a moment of correlated bad luck didn't actually break.

Incident 2: The unbounded label that quietly 40×'d cardinality

An application exporter adds a label carrying something effectively unbounded — a raw Pod name/UID, an HTTP path with an embedded resource ID, a customer ID — to a counter that already exists on every request. Because Pods are ephemeral, every restart mints a brand-new label value and therefore a brand-new time series that Prometheus never garbage-collects until its retention window rolls over; existing series aren't reused, they accumulate. Active series climb for weeks with no corresponding traffic growth until query latency and memory pressure make the monitoring stack itself the thing paging on-call. The fix is always the same: relabeling rules or sample_limit to catch it mechanically, plus an application-level rule that metric labels must have a small, enumerable value space — never an identifier.

Incident 3: The audit policy that filled the control-plane disk

A compliance requirement says "log everything" and a well-meaning operator sets a single blanket RequestResponse rule with no resource scoping. Every list/watch from every controller and every kubectl get -o wide across a large namespace now logs full response bodies — for collections, potentially megabytes per request, dozens of times a second across a busy cluster. The audit log volume outpaces log rotation, the disk backing the API server fills, and the API server itself starts failing writes — a monitoring requirement becoming a control-plane outage. The fix, shown structurally in §8c's example policy, is layered scoping: RequestResponse only for specifically sensitive resources (Secrets, RBAC objects), Request for mutating verbs broadly, Metadata as the default, and explicit None rules — evaluated first, since policy rules are first-match-wins — for known-noisy, low-value traffic like the system components' own watches.

The core algorithm — simplified from the real kubelet source but faithful in structure and naming — is the exact logic §8a's deck stepped through and §15's simulator implements:

Gopkg/kubelet/prober/worker.go — doProbe(), the counter that decides everything
func (w *worker) doProbe(ctx context.Context) (keepGoing bool) {
    result, err := w.probeManager.prober.probe(ctx, w.probeType, w.pod, w.container, w.containerID)
    if err != nil { return true } // transient error: try again next period

    // resultRun = how many times IN A ROW the same outcome has occurred.
    // A different outcome than last time resets the run to 1 — no partial credit.
    if w.lastResult == result {
        w.resultRun++
    } else {
        w.lastResult = result
        w.resultRun = 1
    }

    // Below threshold on either side: the RECORDED status does not change yet.
    if (result == results.Failure && w.resultRun < w.spec.FailureThreshold) ||
       (result == results.Success && w.resultRun < w.spec.SuccessThreshold) {
        return true
    }

    w.resultsManager.Set(w.containerID, result, w.pod) // ← the flip actually takes effect here

    if (w.probeType == liveness || w.probeType == startup) && result == results.Failure {
        w.onHold = true       // stop probing until a NEW container ID appears
        w.resultRun = 0
    }
    return true
}

    e.sink.Create(event) // first occurrence: a genuinely new Event object
}
Goapiserver/pkg/audit/policy/checker.go — first rule that matches, wins
func (c *policyChecker) LevelAndStages(attrs authorizer.Attributes) (Level, []Stage) {
    for _, rule := range c.policy.Rules {
        if ruleMatches(rule, attrs) {   // user, verb, group/resource, namespace...
            return rule.Level, rule.Stages // STOP at the first match — order is meaning
        }
    }
    return LevelNone, nil  // no rule matched: don't audit at all
}
WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Count consecutive identical results, not a rolling failure percentage. A simple counter that resets on any different outcome is trivial to reason about and trivial to test — you can predict the exact tick an action fires from four numbers, which is precisely what §8's calculator and §15's simulator do. 2. Separate "detected" from "acted." resultsManager.Set() only records a status change; a completely different code path (kubelet's SyncPod, or the endpoints controller for readiness) decides what to do about it — the same separation-of-concerns pattern chapter 9's reconciliation loops use everywhere. 3. Policy is a list evaluated in order, not a set of independent rules merged somehow. First-match-wins means the order you write rules in is part of the policy's meaning — exactly like a firewall ruleset, and for the same reason: cheap, high-volume exclusions must be reachable before an expensive catch-all rule gets a chance to match them.
