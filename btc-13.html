Taproot: Schnorr, MAST &
Key Aggregation

A 2020 soft fork made three separately-old ideas — a 1989 signature scheme, a merkle-tree trick for hiding unused branches, and a one-line elliptic-curve tweak — ship together as a single upgrade, and the result is that a 5-of-5 multisig cooperatively closing today is a run of bytes indistinguishable from your aunt paying you back for lunch. This chapter derives each piece from first principles, shows exactly where the pre-taproot design broke, and implements real BIP340 Schnorr signatures and a real taproot tweak in JavaScript — genuine elliptic-curve arithmetic, genuine tagged hashes, a genuine Merkle tree of scripts, verified against Bitcoin Core's own published test vectors.

ARC 01 · THE PROBLEM

A 2-of-3 multisig looks nothing like a coffee payment — and it always will

Before this chapter's upgrade, every Bitcoin output that wanted more than "exactly one key signs" had to say so, in public, forever. A 2-of-3 cold-storage wallet, a Lightning channel's 2-of-2 funding output, a corporate treasury's 5-of-7 policy, an escrow with a timelocked refund path — each one announces its exact structure on the blockchain the moment it is spent, whether or not that structure was ever exercised in any interesting way. This chapter is about removing the announcement without removing the policy.

Concretely: pre-taproot, a multisig lives inside a P2SH or P2WSH output. The funding transaction is quiet — it only publishes a hash. But the moment you spend, you must reveal the full redeemScript: every one of the N public keys, the M-of-N threshold, and the exact OP_CHECKMULTISIG shape, permanently, in a block that will exist for as long as Bitcoin does. An observer — a chain-analysis firm, a curious neighbor running a block explorer, a regulator — can now say with certainty: "this UTXO was secured by these three specific public keys, requiring any two." That is true even if the same two signers used the same wallet for years and never once needed the third key.

Unpack why that specific leak matters, and you get five requirements pulling in different directions:

  • Privacy by default — a spend should not announce that it came from a complex policy at all; ideally, every kind of spend looks like every other kind of spend.
  • Succinctness — you should pay (in transaction weight, hence in fees) only for the branch of the policy you actually used, not for every branch you could have used.
  • Flexibility — real policies are not just "M-of-N": timelocked refunds, hash-locked escrows, federation-plus-emergency-key structures, and Lightning's revocation logic all need to coexist with the simple case.
  • Soft-fork compatibility — old nodes must keep validating new-format blocks as "anyone can spend" until they upgrade; you cannot require a flag day (chapter 12 derives this constraint in detail for SegWit).
  • Verifiability without trust — a validator who has never seen the policy before must still be able to check, cheaply, that whichever branch was used really was one of the branches originally committed to.

Two of Bitcoin's building blocks are already positioned to solve pieces of this. Elliptic-curve signatures (chapter 4 of the Blockchain Fundamentals course; ECDSA specifically in Bitcoin) already hide which private key produced a given signature — a signature does not visually differ based on who made it. And Merkle trees (Blockchain Fundamentals, chapter 3) already let you commit to many things while revealing only one, with a proof that costs O(log N) instead of O(N). Taproot's entire trick is combining those two primitives — plus a specific mechanism for making multiple signers collapse into one signature — into a single Bitcoin output. Getting there requires first replacing ECDSA with a signature scheme that has an algebraic property ECDSA structurally lacks.

WHY THIS MATTERS FOR THE NEXT 3 CHAPTERS

Everything from here to the capstone rests on three composable ideas you're about to derive: (1) Schnorr signatures are linear, so N private keys can produce one signature under one aggregate public key (§5); (2) a Merkle tree of scripts lets you commit to arbitrarily many spending conditions while revealing only the one you use (§5–7); (3) a single elliptic-curve addition — the "tweak" — lets one public key serve as both a signature target and a commitment to that hidden tree (§7–8). Chapter 14's Lightning channels use exactly this stack for cooperative closes; chapter 16's capstone validates real taproot spends against mainnet blocks.

DEEP CONTEXT · WHY 2009 BITCOIN SHIPPED WITH ECDSA, NOT SCHNORR

Claus-Peter Schnorr's signature scheme (1989) is, on paper, strictly simpler and more useful than ECDSA — it has the linearity property this chapter is about, and ECDSA was largely designed to route around Schnorr's patent. That patent didn't expire until February 2008 — months before the Bitcoin whitepaper. Satoshi built on OpenSSL's existing, unencumbered, widely-audited ECDSA implementation instead of writing a fresh Schnorr implementation for a brand-new currency. It was the conservative engineering choice in 2009. By 2018, with a decade of ECDSA's costs now measured in real fee data, the calculus flipped.

ARC 03 · NAIVE SOLUTION

Attempt #1: since Schnorr signatures are linear, just add the keys and add the signatures

Start from the property that makes this whole chapter possible. An ECDSA signature is the pair (r, s) where s = k⁻¹(z + rd) mod n — private key d is wrapped inside a modular inverse of the nonce k. A Schnorr signature is the pair (R, s) where s = k + e·d mod n — private key d appears linearly, multiplied only by the public challenge e = H(R‖P‖m). That one algebraic difference is the entire reason this chapter exists: a linear equation is closed under addition. If two signers each compute sᵢ = kᵢ + e·dᵢ against the same challenge e, then s₁+s₂ = (k₁+k₂) + e·(d₁+d₂) — which is exactly the Schnorr signature that a single hypothetical signer with private key d₁+d₂ and nonce k₁+k₂ would have produced. Nothing comparable falls out of ECDSA's s equation; the modular inverse of k is applied to the whole sum, not distributed over it.

So the first thing anyone tries, on paper, is the obvious naive scheme: let the aggregate public key be the literal elliptic-curve sum of everyone's public key, and let each signer independently produce their own partial signature the normal way, then add the pieces.

pseudocodenaive_n_of_n_aggregation.js — the strawman, annotated
// n-of-n "just sum it" multisignature — looks correct, is not.
function naiveAggregateKey(pubkeys) {
  // P_agg = P1 + P2 + ... + Pn   (plain EC point addition, no weighting)
  return pubkeys.reduce((sum, P) => pointAdd(sum, P), null);
}

function naivePartialSign(privkey, aggNonce, challenge) {
  // s_i = k_i + e * d_i mod n   — each signer, independently, no coordination
  return mod(myNonceScalar + challenge * privkey, N);
}

function combine(partialSigs) {
  // s = s_1 + s_2 + ... + s_n mod n — just add them up
  return partialSigs.reduce((s, si) => mod(s + si, N), 0n);
}
// This verifies correctly against P_agg for HONEST participants.
// Section 4 shows exactly how a dishonest one turns it into a total break.

This is not a silly strawman — it is the correct first step, and the linearity insight behind it is real and load-bearing. Every signer really can compute their own partial signature in isolation and the sums really do compose into a single valid Schnorr signature under the summed key, as long as every participant is honest. That caveat is where naive aggregation dies.

ARC 04 · WHY IT FAILS

The rogue-key attack: one dishonest participant, total unilateral control

The naive scheme above has a name for its failure mode: the rogue-key attack (also called key-cancellation), first analyzed rigorously by Bellare and Neven in "Multi-Signatures in the Plain Public-Key Model" (2006), building on earlier rogue-key findings against related aggregate-signature schemes. The attack is not probabilistic and does not require breaking any cryptographic assumption — it is pure linear algebra over the group, available to an attacker who is simply allowed to choose their public key after seeing everyone else's, which naive aggregation does not forbid.

Suppose Alice publishes her honest public key P_A. An attacker, Mallory, wants the two-party aggregate key P_agg = P_A + P_M to equal some point she alone controls — call it P_target = x_target · G for a secret scalar x_target she picked herself. She computes, using ordinary EC point subtraction:

P_M  =  P_target − P_A  =  P_target + (−P_A)

and registers P_M as "her" public key. She never needed to know the discrete log of P_M itself — only of P_target, which she generated. Now:

P_agg  =  P_A + P_M  =  P_A + (P_target − P_A)  =  P_target

The "2-of-2" aggregate key is, algebraically, a key Mallory alone controls. She can produce a valid Schnorr signature for P_agg completely unilaterally, using nothing but x_target — Alice's cooperation, her nonce, her signature share, all of it is decorative. A wallet that believed it required two parties to move funds is secured by exactly one, and that one is the attacker. Nothing about this exploits a bug in Schnorr's math; it exploits the absence of any constraint on how a public key may be chosen relative to the others in the group.

QUANTIFIED: THIS IS NOT A PROBABILISTIC WEAKNESS

Compare this to breaking the discrete-log problem directly, which costs roughly 2¹²⁸ group operations on secp256k1 (chapter 4 of Blockchain Fundamentals; the whole security budget of every signature in this chapter). The rogue-key attack against naive aggregation costs one EC subtraction — a handful of modular arithmetic operations, microseconds on a laptop — and succeeds with probability 1, every time, against every naive n-of-n scheme, for any number of honest participants. The fix cannot be "bigger keys" or "more rounds of communication"; it has to change what an aggregate key structurally is.

The fix that survived scrutiny does not require signers to prove, in a separate protocol step, that they know the private key behind their public key (a "proof of possession" — the other academically valid defense Bellare–Neven describe). Instead it changes the aggregation formula itself so that no participant can predict, in advance, how their chosen key will be weighted — which is exactly what MuSig's key-aggregation coefficients do, derived next.

ARC 05 · SCHNORR & MUSIG2

BIP340, and the coefficients that make aggregation honest

Before fixing aggregation, fix the signature scheme itself into a Bitcoin-shaped standard. BIP340 ("Schnorr Signatures for secp256k1", Wuille/Nick/Ruffing, 2020) makes three deliberate, non-obvious choices:

  • 32-byte x-only public keys. A secp256k1 point has two possible y-coordinates for every x (they are negatives of each other, y and p−y). BIP340 keys drop the y entirely and adopt a convention: given an x-coordinate, the "real" point is always the one with even y (lift_x in the spec). This removes a whole byte of encoding (33→32) and, more importantly, removes an entire class of ambiguity from every downstream protocol — scripts, tweaks, and aggregation never have to carry or check a parity bit for a public key, only compute one when needed.
  • 64-byte fixed-size signatures. (r, s), each a raw 32-byte big-endian integer — no DER encoding, no variable length. An ECDSA DER signature is ~70–72 bytes purely from encoding overhead around two integers that are themselves 32 bytes each.
  • Tagged hashes. Every hash BIP340/341/342 compute is SHA256(SHA256(tag) ‖ SHA256(tag) ‖ msg) for a domain-specific ASCII tag ("BIP0340/challenge", "TapLeaf", "TapTweak", …). This is domain separation: it guarantees a hash computed for one purpose (say, a Merkle leaf) can never collide, by construction, with a hash computed for a different purpose (say, a signature challenge) — closing off an entire category of cross-protocol type-confusion attacks for the cost of one extra double-SHA256 of a short constant, which implementations precompute once.

BIP340's security reduces to the same hard problem as everything else in this course: the discrete logarithm problem on secp256k1, proven in the random-oracle model. No new cryptographic assumption is introduced — the entire upgrade is a change of encoding and algebra, not a change of trust.

Fixing aggregation: MuSig and MuSig2

The 2018 MuSig paper (Maxwell, Poelstra, Seurin, Wuille) closes the rogue-key hole from §4 with exactly the mechanism Bellare–Neven proved sufficient: weight every participant's public key by a coefficient that depends on everyone's public key, computed after the full set is fixed, so no one can solve for a rogue contribution in advance.

L  =  H(P₁ ‖ P₂ ‖ … ‖ Pₙ) // "KeyAgg list" — hash of every pubkey, in order
aᵢ  =  H(L ‖ Pᵢ) mod n     // "KeyAgg coefficient" — this signer's weight
P_agg  =  a₁P₁ + a₂P₂ + … + aₙPₙ

Re-run Mallory's attack against this formula: she still picks P_M to try to cancel Alice's contribution, but a_A and a_M both depend on L, which depends on P_M itself — a circular dependency she cannot solve around without first breaking the discrete-log problem to find a P_M satisfying the resulting nonlinear equation. The coefficients turn "pick any point" into "solve a discrete-log-hard equation," which is precisely the security margin the naive scheme lacked entirely.

MuSig2 (Nick, Ruffing, Seurin, 2020/2021) then fixes the interactive part: an earlier, naive two-round version of Schnorr multisignatures (round 1 exchange nonces, round 2 exchange partial signatures) was shown by Drijvers et al. (IEEE S&P 2019) to be forgeable via a Wagner-style generalized birthday attack, because malicious co-signers who see honest nonces before committing to their own can adaptively bias the aggregate nonce. MuSig2's fix is for each signer to contribute two nonces per session (not one), combined with a binding factor computed from all of them — this closes the adaptive-bias attack while still needing only two communication rounds, and the first round (which doesn't depend on the message) can be precomputed offline, leaving only one genuinely interactive round at signing time. Step through the protocol:

NEVER REUSE A NONCE — THIS IS NOT A STYLE PREFERENCE

Two Schnorr signatures from the same signer that reuse a nonce k against two different challenges e₁, e₂ give an attacker two linear equations, s₁=k+e₁d and s₂=k+e₂d, in two unknowns. Subtract: d = (s₁−s₂)/(e₁−e₂) mod n — the private key falls out in one modular division. This is not hypothetical: it is exactly the bug that let fail0verflow recover Sony's PlayStation 3 code-signing ECDSA private key in 2010 (§11), and it is precisely why MuSig2's nonce-generation and nonce-never-reuse discipline is treated as a correctness requirement, not an operational nicety — a single accidental nonce reuse across two signing sessions leaks every private key that touched it.

ARC 06 · WHY THAT STILL HURTS

MuSig2 fixes the math; it does not make signing easy

Coefficients and two-round nonce discipline close the rogue-key hole, but the resulting protocol has real, operational costs that a plain OP_CHECKMULTISIG script never had:

  • n-of-n, not k-of-n. Plain MuSig2 aggregates a fixed set of signers into one key that needs all of them online and cooperating. A legacy 2-of-3 multisig tolerates one absent key by design; a naive MuSig2 aggregate of three keys tolerates none. Getting threshold flexibility back means either falling back to script-path leaves (§7, one leaf per allowed subset — which re-reveals structure at spend time) or adopting a genuinely different protocol, threshold Schnorr (FROST), covered in §12.
  • Liveness, twice. Round 1 (nonce commitments) can be precomputed and cached before anyone knows the message, but round 2 (partial signatures) cannot start until every signer has seen the actual transaction — a single offline hardware wallet blocks the whole signature, with no partial-progress fallback.
  • Nonce management is now safety-critical infrastructure. §5's callout is not decorative: a signer that reuses a nonce, or whose randomness is predictable, or whose two-round state machine can be tricked into signing twice with the same commitment, leaks the private key outright. Production implementations lean on audited libraries (libsecp256k1's MuSig2 module) rather than ad-hoc code specifically because this history of academic breaks (Drijvers et al., §11) is real and repeatable.
  • Aggregation alone does not hide policy. MuSig2 makes the happy path — everyone cooperates — look like a single signer. It says nothing about what happens when a cosigner disappears, a timelock needs to fire, or a policy has conditions no signature scheme can express (a hash preimage, a specific script hash). Something else has to carry the unhappy paths without forcing every spend to reveal them upfront. That something is a Merkle tree of scripts — MAST — assembled in §7–8.

So the final architecture is not "MuSig2 replaces multisig scripts." It's "MuSig2 handles the cooperative case as a single aggregated key, and a hidden script tree handles every other case as a fallback that only needs to be revealed if it's actually used" — bound together by one more piece of arithmetic: the tweak.

ARC 07 · FINAL ARCHITECTURE

One output, two spending paths, bound by a single elliptic-curve addition

Here is the complete shape. Start from an internal key P — a single key, or a MuSig2 aggregate of several. Separately, build a Merkle tree of scripts ("tapleaves") for every alternative spending condition you want to allow — a timelocked refund, an emergency key, a federation threshold, anything Script can express. Compute the tree's merkle root. Then compute one tagged hash committing the internal key to that root, and add it to the internal key as an elliptic-curve point:

Q  =  P  +  HTapTweak(P ‖ merkle_root) · G

The output published on-chain is just Q's x-coordinate — 32 bytes, syntactically identical to any other single-key taproot output. Two ways to spend it, both valid, both checked against the same Q:

  • Key path. Whoever controls the tweaked private key q (derived from P's private key plus the same tweak scalar) signs the spending transaction directly with an ordinary BIP340 signature over Q. The witness is one 64-byte signature. Nothing about the script tree, or whether one existed, is ever revealed.
  • Script path. Anyone holding a satisfying witness for one specific leaf script reveals: that script, its Merkle path back to the root (siblings only — not the other leaves' contents), and the internal key P. A verifier recomputes the root from the leaf and path, recomputes the tweak, checks that P + tG really does equal the output's Q, and then executes the script normally.

What if you want a script-only output — no key path should ever be spendable, by design (a federation that wants provable absence of a backdoor, for instance)? You can't just omit the internal key; the tweak formula needs some point P. BIP341 defines a standard NUMS point ("nothing up my sleeve") — a point derived by hashing a fixed public constant until you land on a valid x-coordinate, so that nobody plausibly knows its discrete log. Using it as the internal key proves, publicly, that the key path is unspendable by construction — not merely unused.

The real byte layouts: tagged hashes, tapleaves, control blocks, the tweak

function taggedHash(tag, ...parts) {
  // SHA256(SHA256(tag) || SHA256(tag) || parts...)

(b) A tapleaf, a tapbranch, and the control block

A tapleaf commits to one script and its version byte (0xc0 for the tapscript version used by every leaf in this chapter):

leaf_hash  =  taggedHash("TapLeaf", leaf_version ‖ compact_size(len(script)) ‖ script)

Two nodes combine into a branch by sorting the pair lexicographically before hashing — this is what makes the tree's root independent of which child you call "left":

branch_hash  =  taggedHash("TapBranch", min(a,b) ‖ max(a,b))

To spend via script path you reveal the script, then a control block: one byte (leaf version, with the output key's y-parity packed into its low bit), the 32-byte internal key, and one 32-byte hash per level of the tree — the siblings you need to walk back up to the root, and nothing else. For a balanced tree of N leaves that's ⌈log₂N⌉ hashes, not N scripts.

FROST is the honest answer to "why not just make k-of-n itself invisible" — it exists, is specified, and remains newer, less standardized, and less deployed than the MuSig2 + MAST combination this chapter builds.

For calibration, contrast with two systems solving adjacent problems differently: Ethereum's smart-contract multisigs (e.g. Gnosis Safe) make the opposite bet — the policy is public EVM bytecode by design, trading privacy for on-chain verifiability of arbitrary logic without a merkle-tree indirection. Ethereum's consensus layer uses BLS aggregate signatures for validator attestations — also linear and aggregatable, over a pairing-friendly curve — but in a closed, permissioned setting (a fixed validator set) rather than for arbitrary end-user spending policies, so it never needed a MAST-equivalent fallback tree.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Where the bytes go, and what an attack actually costs

Key-path aggregation's headline benefit is constant witness size: no matter how many cosigners produced the signature, the witness is always one 64-byte (or 65 with a non-default sighash byte) Schnorr signature. Legacy multisig witnesses grow linearly — every additional required signature is another ~72-byte ECDSA signature the spend must carry. Drag the cosigner count:

Security-wise, the numbers to internalize:

  • Discrete-log security is unchanged. BIP340 and taproot spend no new cryptographic budget — forging a signature or finding a colliding tweak still costs ~2¹²⁸ group operations, same as ECDSA on the same curve. The upgrade is entirely about encoding and composability, not about raising or lowering the hardness of the underlying problem.
  • Naive rogue-key forgery: instant, deterministic. As quantified in §4, an unweighted aggregation scheme is broken with a handful of EC operations, not a cryptographic budget at all — this is why the coefficient defense is not optional hardening but a load-bearing part of the design.
  • Batch verification. Because Schnorr's verification equation (sG = R + eP) is linear, many signatures can be checked together far more cheaply than one-at-a-time — a random linear combination of many verification equations still holds iff every individual one does, letting a validator amortize the expensive scalar multiplications across a whole block. ECDSA's verification equation does not admit the same trick as cleanly. This is a real, measured win for nodes and is one of the reasons Bitcoin Core's libsecp256k1 batch-verifies Schnorr signatures where it can.
  • Tapscript's removed limits shift, not remove, the cost model. Dropping the 520-byte push limit and the 201-opcode-per-script limit (§13) doesn't mean scripts are free — resource accounting moves to an explicit sigop budget tied to witness weight, so the cost is paid in fees rather than enforced by an arbitrary constant that 2010-era Script authors picked without taproot's weight-based fee model in mind.
ARC 11 · REAL-WORLD INCIDENTS

Four events that shaped — or tested — this design

Incident 1: the Sony PlayStation 3 nonce-reuse disaster (December 2010)

fail0verflow's "Console Hacking 2010" CCC talk showed Sony's PS3 firmware signed every code update with ECDSA using the same nonce k every time — the exact algebraic mistake §5's callout derives. With two signatures over two different messages sharing one k, the private key falls out of one modular subtraction and division. Sony's entire code-signing root key leaked, permanently, from a handful of public firmware signatures. It predates MuSig2 by a decade, but it is the canonical, real-world proof that "never reuse a nonce" is not academic caution — it is the difference between a working signature scheme and a fully broken one, and it is exactly the failure mode MuSig2's careful two-round, multi-nonce protocol exists to make hard to stumble into.

Incident 2: the 2019 academic break of naive two-round Schnorr multisignatures

Drijvers, Edalatnejad, Ford, Kiltz, Loss, Neven, and Stepanovs ("On the Security of Two-Round Multi-Signatures", IEEE S&P 2019) showed that a natural, widely-assumed-safe two-round Schnorr multisignature protocol — round 1 nonce exchange, round 2 partial signatures, no commitment step — was forgeable by malicious co-signers running a Wagner-style generalized birthday search over adaptively chosen nonces. This is a caught-before- deployment academic finding, not a production breach, but it directly determined MuSig2's final shape: multiple nonces per signer, combined with a public binding factor, specifically to block this class of attack while keeping the practical two-round structure. It is a clean example of cryptographic peer review doing its job before a billion-dollar network depended on the result.

Incident 3: Speedy Trial — the calmest activation in Bitcoin's history (2021)

Contrast this with SegWit's 2017 activation fight (BIP148 UASF, the SegWit2x collapse — chapter 12). Taproot's activation used "Speedy Trial": a fixed, roughly three-month signaling window in which miners could lock in the upgrade early by reaching a 90% threshold within any single difficulty period, with a hard deadline if they didn't. Signaling crossed the threshold well within the window in mid-2021, and the new rules became mandatory at block height 709,632 (November 14, 2021) — with no chain split, no dueling implementations, and none of the miner-vs-user brinkmanship that defined SegWit. The mechanism change (a short, bounded trial instead of an open-ended signaling period) is as much a governance lesson as the cryptography is a technical one.

Incident 4: Ordinals inscriptions quietly eroded the privacy story (2023–)

Starting in early 2023, "Ordinals" inscriptions — arbitrary data embedded in tapscript witnesses via OP_FALSE OP_IF … OP_ENDIF envelopes — became a large share of all script-path taproot spends. Because inscriptions are, definitionally, script-path spends with a recognizable witness shape, they are more self-identifying than the multisig closes this chapter uses as its motivating example, and for a period they meant that a large fraction of "taproot script-path activity" observed on-chain was inscriptions, not hidden multisig policies. This doesn't break anything cryptographically — it's the herd-privacy argument from §6 playing out in public: the anonymity set a technique provides depends on what real traffic looks like, not only on what the technique is capable of hiding.

Three excerpts, simplified from the real 2020/2021 sources but faithful in structure and naming. First, BIP340 signing as the real library actually shapes it — note the aux-rand XOR step and the two parity flips, exactly as derived in §8(a) of this chapter:

Csecp256k1/src/modules/schnorrsig/main_impl.h — sign32(), simplified
int secp256k1_schnorrsig_sign32(const secp256k1_context *ctx,
                                unsigned char *sig64,
                                const unsigned char *msg32,
                                const secp256k1_keypair *keypair,
                                const unsigned char *aux_rand32) {
    secp256k1_ge pk;
    secp256k1_scalar sk, k, e;
    secp256k1_keypair_load(&sk, &pk, keypair);

    /* Negate the secret key if the pubkey's y is odd — every BIP340
     * pubkey is assumed even-y by convention (§8a). */
    if (secp256k1_fe_is_odd(&pk.y)) secp256k1_scalar_negate(&sk, &sk);

    /* nonce_function_bip340: t = (sk XOR tagged_hash("BIP0340/aux", aux_rand))
     *                        rand = tagged_hash("BIP0340/nonce", t || pk.x || msg32) */
    secp256k1_nonce_function_bip340(&k, msg32, sk_bytes, pk_x_bytes, aux_rand32);

    secp256k1_gej rj; secp256k1_ecmult_gen(&ctx->ecmult_gen_ctx, &rj, &k);
    secp256k1_ge r; secp256k1_ge_set_gej(&r, &rj);
    if (secp256k1_fe_is_odd(&r.y)) secp256k1_scalar_negate(&k, &k);   /* R must be even-y too */

    /* e = tagged_hash("BIP0340/challenge", r.x || pk.x || msg32) mod n */
    secp256k1_schnorrsig_challenge(&e, r.x, pk.x, msg32);

    secp256k1_fe_get_b32(sig64, r.x);
    secp256k1_scalar_mul(&e, &e, &sk);
    secp256k1_scalar_add(&e, &e, &k);              /* s = k + e*d mod n — the linear equation, §3 */
    secp256k1_scalar_get_b32(sig64 + 32, &e);
    return 1;
}

Second, Tapscript's replacement for OP_CHECKMULTISIG — one signature/pubkey pair consumed and counted per opcode, instead of the old scheme's order-sensitive matching:

C++script/interpreter.cpp — OP_CHECKSIGADD, simplified
case OP_CHECKSIGADD: {
    // stack, top to bottom: [ ... sig  pubkey  n ]
    if (stack.size() < 3) return set_error(serror, SCRIPT_ERR_INVALID_STACK_OPERATION);
    const valtype& sig    = stacktop(-3);
    const valtype& pubkey = stacktop(-2);
    const CScriptNum n(stacktop(-1), 4);

    // Tapscript pubkeys are x-only (32 bytes) — Schnorr verify path, not ECDSA.
    bool success = sig.empty() ? false
        : CheckSchnorrSignature(sig, pubkey, execdata, serror);
    if (!sig.empty() && !success) return false;   // NULLFAIL: non-empty sig MUST verify

    popstack(stack); popstack(stack); popstack(stack);
    stack.push_back(CScriptNum(n.getint() + (success ? 1 : 0)).getvch());
    break;
}
// A k-of-n script is now:  OP_CHECKSIG  OP_CHECKSIGADD  OP_CHECKSIGADD ...  OP_NUMEQUAL
// Linear cost, no dummy stack element, and every check is an independent Schnorr
// verification — batch-verification-friendly (§10), unlike CHECKMULTISIG's
// order-sensitive O(sigs × keys) matching loop.

Third, the control-block walk that verifies a script-path spend really was committed to by the output — this is the check that makes MAST binding, not just obfuscating:

C++script/interpreter.cpp — VerifyTaprootCommitment, simplified
bool VerifyTaprootCommitment(const std::vector<unsigned char>& control,
                             const std::vector<unsigned char>& program,   // = Q.x, from the scriptPubKey
                             const CScript& script) {
    int path_len = (control.size() - 33) / 32;
    XOnlyPubKey p(Span(control).subspan(1, 32));       // internal key P

    uint256 k = ComputeTapleafHash(control[0] & TAPROOT_LEAF_MASK, script);
    for (int i = 0; i < path_len; ++i) {
        auto sibling = Span(control).subspan(33 + 32*i, 32);
        k = ComputeTapbranchHash(k, sibling);      // sorted concat + tagged hash, §8b
    }
    // k is now the recomputed merkle root — recompute the tweak exactly as at
    // output-creation time, and check it reproduces the ACTUAL scriptPubKey.
    return p.CheckTapTweak(p, program, k, control[0] & 1);
}
WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Put the resource limit in the fee market, not in a magic constant. Removing the 520-byte push and 201-opcode limits (replaced by weight-proportional sigop budgets) means Tapscript's ceiling scales with what you pay, not with a number chosen in 2010 for a very different fee environment. 2. Reserve room to grow without another soft fork of this size. Unassigned Tapscript opcodes are defined as OP_SUCCESS — encountering one makes the script immediately valid, so a future soft fork can give any of them real meaning without a new script version, mirroring how OP_NOPs were repurposed for CLTV/CSV pre-taproot, but with the semantics made explicit from day one. 3. Let the interpreter, not the wallet, be the source of truth for "is this the committed script." VerifyTaprootCommitment is pure function of public data — control block, program, script — so any node can independently confirm a script-path spend is legitimate without trusting the spender's claim about which policy the output was created under.
