From Scratch

Thirteen chapters gave you the primitives one at a time: a hash function, a Merkle tree, a signature scheme, a hash chain, a consensus problem, a Sybil-resistance mechanism, a mining puzzle, a fork rule, a gossip network. Each was correct in isolation and, on its own, useless — a signature scheme doesn't stop a double-spend, a hash chain doesn't stop a rewrite, a mining puzzle doesn't resolve a fork by itself. This chapter builds all eight, as real, runnable JavaScript that executes in this page, wires them into one working chain, and then attacks it — a double-spend, a network partition, a 51% hashrate majority — to prove, mechanically, that the assembly holds where the pieces alone did not.

ARC 01 · THE PROBLEM

You have every part. Can you assemble a system a stranger can't cheat?

Chapters 1 through 13 each isolated one mechanism, and that isolation was necessary and, in a specific sense, incomplete: none of those mechanisms does anything by itself. A hash function commits to data but does not order it. A signature proves authorization but does not prevent the same authorized spend from being submitted twice. Proof-of-work makes rewriting history expensive but says nothing about which of two simultaneously-valid histories a newcomer should believe. This chapter's job is to stop isolating and start assembling: build a small, complete chain, run it across several simulated nodes that do not trust each other, and prove — by attacking your own assembly — that it survives exactly the failure modes each prior chapter named and no others.

"Survives" means exactly three properties, and getting all three together is the entire difficulty — any one alone is easy:

  • Tamper evidence that costs real work to defeat. Editing a historical transaction must not just be detectable (a hash-chain check, ch.5) — it must require redoing the proof-of-work for that block and every block after it (ch.8), so that "the truth is whatever cost the most energy to produce" replaces "the truth is whatever a trusted party says," which was the entire point of chapter 1.
  • No double-spend, enforced by math, not by asking nicely. Two transactions that spend the same coin must not both be able to confirm — not because a server refuses the second one (there is no server), but because every node independently runs the same signature check and the same first-seen-wins mempool rule (ch.1, ch.13) and only one node's proposed block can ever reference each unspent output.
  • Agreement without a referee. Two honest nodes that temporarily see different histories — because they mined at the same height at the same time, or because a partition split the network (ch.10, ch.11) — must converge on the same history once they can talk again, using a rule computable from the data alone: whichever chain represents more cumulative proof-of-work.
THE RULE FOR THIS CHAPTER

Every component below is real, runnable JavaScript — the exact functions the console in §15 calls when you type a command. SHA-256 hashes real bytes through 64 real compression rounds. The signatures are real secp256k1 points computed with BigInt, not placeholder strings. Mining performs a real nonce grind against a real target and can take real, visible time. Where the toy simplifies something away from a production chain, that simplification is named explicitly, so you finish this chapter knowing not just how a minimal chain works, but precisely how much harder the real thing is, and why — with chapter 16 of Bitcoin Internals waiting as the concrete, byte-exact answer to "what does production actually do differently."

ARC 03 · NAIVE SOLUTION

Attempt #1: the "naivechain" shape — hash-linking with nothing behind it

Be honest about the starting point, the way every naive solution in this course has been honest: if you wanted a "blockchain" in fifteen minutes with no other constraints, this is what you would write, and it is exactly the shape of the 2017-era "build your own blockchain in 200 lines" tutorial genre.

jsnaive-chain.js — the strawman, annotated
let chain = [{ index: 0, data: "genesis", prevHash: "0", hash: "GENESIS" }];

function addBlock(data) {
  const prev = chain[chain.length - 1];
  const block = { index: prev.index + 1, data, prevHash: prev.hash };
  block.hash = simpleHash(block.index + block.data + block.prevHash); // no PoW: instant
  chain.push(block);
}
function send(from, to, amount) {
  // "sender" is a self-reported string. No signature. Anyone can claim to be anyone.
  addBlock({ from, to, amount });
}

This gets exactly one thing right — later blocks' hashes depend on earlier blocks' contents — and stops there. There is no proof-of-work, no signature, and, critically, no second party: this is one JavaScript array in one process. Two people running this exact script produce two unrelated "truths" with no mechanism to reconcile them, which is precisely the problem chapter 1 opened with and this naive version has not touched.

ARC 04 · WHY IT FAILS

Every property from §1 fails, and each failure names its own fix

  • Tamper evidence without a cost is not tamper evidence. Editing chain[5].data and recomputing simpleHash() for every block after it is a few milliseconds of work on a laptop — rewriting history costs the same as writing it the first time. Chapter 5's hash-linking is necessary but, alone, purely cosmetic.
  • "from: 'alice'" is not authorization. Nothing stops any caller from writing send("alice", "mallory", 1000000) regardless of who is actually running the code. Ownership needs a signature only the real Alice can produce (ch.4), not a self-reported label.
  • Scarcity is absent, so Sybil resistance is absent. There is no cost to producing a block, so there is no cost to producing a thousand contradictory ones — exactly the gap chapters 6 and 7 named: open membership plus free block production equals no defensible notion of "the" history.
  • There is no second node. A blockchain's entire reason to exist is coordinating parties who do not trust each other (ch.1). A single mutable array has, structurally, nobody to disagree with — and therefore nothing that deserves to be called consensus.
THE NUMBERS

Rewriting block 5 of a 1,000-block naive chain: one field write plus 995 cheap re-hashes, all on one machine, in well under a second — call it O(1) in any cost that matters to an attacker. §8's real SHA-256 and §12's real proof-of-work exist specifically to turn that into "redo 995 real nonce grinds," each one an expected 2d hash attempts at difficulty d — the exact mechanism that makes §1's "costs real work to defeat" a measurable number instead of a slogan.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates, each fixing one gap and exposing the next

Step through the derivation. This is not a list handed down from a paper — it is what you arrive at by fixing the naive chain's worst problem, watching a new one appear, and fixing that.

Deriving the architecture, one elimination at a timeSTEP-BY-STEP

Candidate A: hash-link the blocks, nothing else

Fix tamper-evidence honestly: make each header commit to the previous block's real hash (ch.5). Now editing history is at least detectable — every downstream hash breaks. But detectable is not expensive: a modern laptop recomputes a thousand SHA-256 hashes before you finish reading this sentence. Rejected: tamper evidence without a cost to defeat it is a smoke alarm with no fire department.

Candidate B: add signed transactions, still no scarcity

Fix authorization: every transaction must carry a valid ECDSA signature from the key that owns the coin (ch.4), checked against the real curve, not a string comparison. Ownership is now real. But nothing yet says who is allowed to decide the order transactions confirm in, or what happens when two parties disagree about that order. Correct primitive, no consensus — motivating proof-of-work directly.

Candidate C: add proof-of-work, one miner, no network

Fix scarcity: block creation now requires a real nonce grind against a real target (ch.7's Sybil-resistance argument made concrete, ch.8's mechanism). Rewriting is now provably expensive. But run this on a single machine and there is still nobody to disagree with — the instant you add a second miner, two valid blocks can legitimately appear at the same height at the same moment, and nothing yet says which one the network should build on. Correct mechanism, no rule for resolving disagreement — motivating fork choice and gossip directly (ch.10, ch.11).

WHAT'S LEFT AFTER ALL THREE

Hash-linked blocks (A) + signed UTXO transactions (B) + proof-of-work (C) still lack: a rule for choosing between two valid chains, a way for that rule's inputs (blocks, transactions) to actually reach every node, and a mempool discipline that stops a double-spend from reaching two different miners' next blocks at once. §6 prices what's built so far; §7 assembles the full eight-component architecture that closes every remaining gap.

ARC 06 · WHY THAT STILL COSTS

Even fully assembled, the bill does not go to zero

  • Proof-of-work spends real energy in proportion to the security it buys. Chapter 8's "security budget" argument is not a metaphor here: §12's mining widget will burn real wall-clock CPU time, and raising the difficulty slider raises that cost exactly exponentially, with no shortcut.
  • Fork choice gives probabilistic, not absolute, finality. A block your own node just accepted as the new tip can still be orphaned by a heavier competing chain minutes later (ch.8's exponential-decay confirmation math) — §13's fork-choice widget will produce a real reorg live, on data you built.
  • Every node pays full validation cost. There is no shortcut here for "trust the last node's answer" — each of §15's simulated nodes independently re-verifies every signature and re-derives every UTXO balance, which is exactly why chapter 12's scaling trilemma exists: this cost is paid by everyone, every time, and does not shrink as the network grows.
  • Gossip has a delay, and delay has a cost. §13's propagation-delay slider is not cosmetic — every millisecond a block takes to reach a miner is a millisecond that miner might waste extending a soon-to-be-orphaned tip (ch.11's direct link between propagation delay and orphan rate).

None of this is a flaw in the design below — it is the honest price of coordination without a trusted referee, paid in the currencies chapters 6 through 12 predicted: energy, latency, and redundant computation. §7 now assembles the eight pieces that pay that price on purpose.

ARC 08 · COMPONENT 1 — chapter 2 in miniature

SHA-256, implemented from scratch

The full FIPS 180-4 algorithm, not a shortened teaching version: a message is padded with a single 0x80 byte, zero-padded, and terminated with its own 64-bit big-endian bit length; it is then processed in 64-byte chunks, each expanded into a 64-word message schedule (W[0..63]) and run through 64 compression rounds using the real round constants K[0..63] (the first 32 bits of the fractional cube roots of the first 64 primes) and the real Σ/Ch/Maj bitwise functions chapter 2 derived. The eight 32-bit working variables a..h rotate through every round and feed back into eight running hash words, initialized to the fractional square roots of the first eight primes. Nothing here is approximated — this is a complete, correct SHA-256, verified live below against the official NIST test vector.

WHAT REAL SHA-256 IMPLEMENTATIONS DO THAT THIS ONE DOESN'T NEED TO

Unlike most of this chapter's components, this one is close to complete as written — the algorithm itself has no shortcuts. What production libraries add on top is performance and side-channel engineering: hardware SHA extensions (Intel SHA-NI, ARMv8 crypto extensions) process a full round in a single instruction, and libraries like OpenSSL hand-tune assembly per microarchitecture — our loop is plain, portable, and roughly a hundred times slower per hash than hardware-accelerated code, which is exactly why §12's mining widget measures its attempt rate in the tens of thousands per second rather than the hundreds of millions a real ASIC manages. The one place timing matters for security — constant-time execution to prevent side-channel leaks — does not apply to hashing non-secret data like a block header, but reappears with teeth in §10's ECDSA signing.

ARC 09 · COMPONENT 2 — chapter 3 in miniature

The Merkle tree: one root, O(log n) inclusion proofs

Transaction hashes are paired and hashed upward until one root remains. An inclusion proof for leaf i is just the sibling hash at every level on the path from that leaf to the root — log2(n) hashes that let anyone recompute the root from a single leaf and confirm it matches, without seeing any other transaction. This implementation makes one deliberate choice worth naming: when a level has an odd number of nodes, the leftover hash is promoted unchanged to the next level rather than duplicated against itself. The historical Bitcoin Core implementation instead duplicated the odd node — which is exactly what made CVE-2012-2459 possible: an attacker could append a duplicate of the last transaction to a block, and a node computing the root the naive way would compute the same root for two different transaction lists, letting a malformed block pass as identical to a valid one. Promoting instead of duplicating isn't a simplification here — it's the actual fix.

WHAT REAL MERKLE TREES DO THAT THIS ONE SKIPS

Production trees typically domain-separate leaf hashes from internal-node hashes (prefixing each with a distinct tag before hashing) specifically to prevent second-preimage attacks where an attacker presents an internal node's hash as if it were a valid leaf — our toy tree has no such tag, which is safe only because nothing in this sandbox ever needs to distinguish the two. Ethereum's state commitment (ch.3's reference) is a Merkle-Patricia trie, not a plain Merkle tree at all — it commits to a full mutable key-value map with efficient updates and non-inclusion proofs, neither of which this toy's static, append-only leaf list supports.

ARC 10 · COMPONENT 3 — chapter 4 in miniature

secp256k1 and ECDSA, over real BigInt arithmetic

The real curve: y² = x³ + 7 (mod p) with p = 2²⁵⁶ − 2³² − 977, base point G, and order n — the exact constants Bitcoin and Ethereum both use. Point addition and doubling are computed with the real field-arithmetic formulas (a modular inverse via the extended Euclidean algorithm stands in for the division the curve equations require), and scalar multiplication — computing k·G for a huge scalar k — uses real double-and-add: walk the scalar's bits, doubling the running point every step and adding the base point whenever a bit is set, turning an operation that looks like it needs up to 2²⁵⁶ additions into one that needs at most 256 doublings and 256 conditional additions. A private key is a random scalar; the public key is that scalar times G. Signing solves s = k⁻¹(z + r·priv) mod n for a fresh random nonce k per signature — chapter 4's warning about nonce reuse applies here exactly as written: reusing k across two signatures leaks the private key algebraically, which is why k below is redrawn fresh every single time.

WHAT REAL WALLETS DO THAT THIS ONE DELIBERATELY DOESN'T

This sandbox draws its signing nonce k from Math.random() — a fast, convenient, cryptographically insecure source, flagged explicitly at the point it's generated. Production signers use either a real CSPRNG or, better, RFC 6979 deterministic nonces: derive k from a keyed hash of the private key and the message itself, so the same message always signs to the same signature and a weak system RNG can never repeat a k value across two different messages — which chapter 4 showed is enough to recover the private key outright (the 2010–2013 Android SecureRandom bug that drained real Bitcoin wallets exploited exactly this). Real implementations also run field arithmetic in constant time to prevent timing side-channels from leaking bits of the private key; our BigInt operations make no such guarantee and should never be used outside this teaching sandbox.

ARC 11 · COMPONENTS 4 & 5 — chapter 5 and chapters 1/13 in miniature

The ledger layer: hash-linked blocks, then a UTXO mempool on top

Component 4: hash-linked blocks with a real header

Every block header is exactly Bitcoin's real 80-byte layout — version(4) · prevHash(32) · merkleRoot(32) · timestamp(4) · bits(4) · nonce(4) — packed into a real Uint8Array via DataView, and the block's hash is the real double-SHA256 of those 80 bytes. Because prevHash is baked into the bytes that get hashed, changing anything in block N changes block N's hash, which invalidates block N+1's prevHash field, cascading forward — exactly chapter 5's tamper-evidence mechanism, now running on the same blockHash() function §12's miner calls.

WHAT REAL BLOCK VALIDATION DOES THAT THIS ONE SKIPS

Real headers also carry version bits signaling which consensus rules a miner supports (BIP9, ch.10's soft-fork activation), and a full node checks block size/weight limits, sigop counts, and every transaction's script — a tiny stack machine (Bitcoin Internals ch. btc-04) — not just a flat address-equality check. Chapter btc-08's full validation gauntlet lists every one of these rules in the order Bitcoin Core actually checks them; this toy checks exactly four: PoW, hash-matches-header, merkle-root-matches-transactions, and per-transaction validity.

Component 5: the UTXO mempool

Every transaction input names a previous transaction's output by (txid, vout) and carries a compressed public key plus a signature; a transaction is valid only if every input's public key hashes to the address that actually owns the referenced output, every signature verifies against the real ECDSA verify() from §10, and the sum of outputs does not exceed the sum of inputs. The mempool adds one more rule that lives above individual-transaction validity: it tracks which outpoints are already reserved by a pending transaction, and rejects any second transaction that names an outpoint someone else already claimed — mechanically closing the exact gap chapter 1 opened with sending the same coin to two merchants.

WHAT REAL MEMPOOLS DO THAT THIS ONE SKIPS

There is no fee market here — no sat/vB, no replace-by-fee, no eviction under memory pressure (Bitcoin Internals ch. btc-11 covers all three). Ownership here is a flat address-equality check; real Bitcoin's "can this input spend this output" question is answered by actually executing a script (btc-04), which is what makes multisig, timelocks, and Taproot possible and a plain address check cannot express. And this toy's coinbase output is spendable the instant it's mined — real chains impose a coinbase maturity rule (100 confirmations on Bitcoin) specifically because a freshly-mined reward sits on a chain tip that is still statistically likely to be reorganized away.

ARC 12 · COMPONENT 6 — chapter 8 in miniature

Proof-of-work mining: a real nonce grind against a real target

The difficulty target uses Bitcoin's real compact representation (nBits): a one-byte exponent and a three-byte mantissa that together encode a 256-bit target without spending 32 bytes on every header. Mining is exactly the loop chapter 8 describes: hold the header's other fields fixed, try nonce = 0, 1, 2, …, recompute the real double-SHA256 block hash each time, and stop the instant that hash — read as a 256-bit integer — is less than or equal to the target. There is no shortcut; the expected number of attempts is target_max / target, which is exactly 2ⁿ for a target requiring n leading zero bits, so every extra bit of difficulty doubles the expected work. Difficulty retargeting runs the identical formula Bitcoin uses at every 2016-block boundary, just compressed to every 5 blocks here: compare the actual time the last interval took against the expected time, and scale the target by that ratio, clamped to a 4× move in either direction per retarget.

WHAT REAL MINERS DO THAT THIS ONE SKIPS

A real header's nonce field is only 32 bits — at modern hashrates, ASICs exhaust all four billion values in a fraction of a second, so real miners roll additional entropy through an extranonce field inside the coinbase transaction, which changes the merkle root and effectively extends the searchable nonce space indefinitely (Bitcoin Internals ch. btc-09). This toy's timescale is also compressed on purpose: a 5-second target block time and a 5-block retarget window preserve Bitcoin's exact retargeting formula while shrinking its real 10-minute/2016-block constants down to classroom patience.

ARC 13 · COMPONENTS 7 & 8 — chapter 10 and chapter 11 in miniature

Consensus at the network layer: fork choice, reorg, and gossip

Component 7: fork choice by cumulative work

Every block's individual "work" is 2²⁵⁶ / (target + 1) — a harder target (smaller number) means more work. A chain's cumulative work is the sum of every ancestor block's work back to genesis. When a node receives a new block, it compares that block's branch's cumulative work against its current tip's; if the new branch is heavier, the node walks both branches back to their common ancestor, switches its tip to the new branch, and — this is the step naive reorg implementations get wrong — takes every non-coinbase transaction from the now-orphaned blocks and re-offers each one to the mempool, where it is re-validated against the new tip's UTXO set (a transaction whose inputs no longer exist on the new branch is silently dropped; everything else becomes pending again, ready to be mined into the winning chain).

There is no finality gadget here and no bound on reorg depth — a heavier branch of any length will win, whereas some production systems refuse extremely deep reorgs as a deliberate DoS defense (Bitcoin Internals ch. btc-15 covers real incidents this protects against). Ethereum's proof-of-stake chain additionally includes uncle/ommer blocks — near-misses that still earn partial reward and count toward fork choice — a refinement chapter 9's GHOST/Casper material covers that this simple heaviest-chain rule has no equivalent of.

Component 8: the P2P gossip layer

Several simulated nodes, each running the full validation stack above independently, connected by a configurable propagation delay. When a node accepts a new transaction or block it hasn't seen before, it relays that exact object to every neighbor it hasn't already sent it to — a "seen" set per node prevents infinite re-broadcast loops, mirroring the real INV/GETDATA relay chapter 11 describes. A network partition simply removes the link between two groups of nodes: gossip within each group continues normally, but nothing crosses the cut, so the two sides can legitimately mine two different "heaviest" chains until heal() restores the link and the two sides reconcile.
