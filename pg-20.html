Incidents, Profiling & Tuning

Nineteen chapters have given you the processes, the memory contexts, the buffer pool, the lock manager, the WAL, MVCC, vacuum, the planner, indexes, replication. This chapter is the synthesis: a live cluster in trouble, and a disciplined way to find out which of those nineteen subsystems is actually at fault. The method is not a checklist. It starts from one question — where is time being spent? — and every answer resolves to a structure you already know.

ARC 01 · THE PROBLEM

A cluster in trouble is a cluster you must explain, not just restart

Every subsystem in this course fails eventually, in production, at the worst time. The postmaster's crash protocol (chapter 1) fires. Autovacuum falls behind (chapter 12). A lock queue backs up (chapter 8). A checkpoint bursts I/O (chapter 11). The question this chapter answers is not "what can go wrong" — you already know that — it is: given a cluster that is slow or down right now, with no prior knowledge of the cause, how do you find the true root in minutes instead of hours?

The instinctive answer in most organizations is a checklist: check CPU, check disk, check replication lag, restart the app tier, bump shared_buffers, add an index, page someone senior. Checklists feel productive because they generate action. They are also, structurally, guessing — a sequence of GUCs and metrics assembled from past incidents and blog posts, applied without a model of why THIS system is slow THIS time. Two incidents with identical symptoms — say, elevated CPU and rising p99 latency — can have completely different root causes (a JIT-compilation storm versus a spinlock convoy versus a plan regression), and a checklist has no way to distinguish them; it just runs down the list and hopes something matches.

This chapter's thesis, stated once so you can hold it in your head for every section that follows: diagnosis starts from where time is spent, not from a list of configuration knobs. PostgreSQL instruments exactly this — every backend, at every moment it is not actively running on a CPU doing useful work, records why it isn't, in a single shared-memory field. That field is pg_stat_activity.wait_event_type / wait_event, and it is the single most under-used column in the entire catalog of observability views. Once you know which subsystem backends are waiting on, the rest of this chapter's views — pg_stat_statements, pg_stat_bgwriter, pg_locks, pg_stat_replication — stop being a grab-bag of metrics and become instrumentation of the internals you already learned: each one is a window into a specific chapter's mechanism, and reading it correctly means recalling that mechanism.

THE METHOD IN ONE SENTENCE

Find where backends are waiting → identify which chapter's subsystem produces that wait → read that subsystem's dedicated stat view to confirm the hypothesis → apply the fix that subsystem's own architecture predicts will work → measure, because your model, not the incident, is what's on trial.

PostgreSQL didn't always know why it was slow

Observability in PostgreSQL was built incrementally, and mostly in response to operators who couldn't answer "why is this query slow" without attaching a debugger. Click through the timeline — each release added one more piece of the instrumentation this chapter depends on.

DEEP CONTEXT · WHY OBSERVABILITY LAGGED CORRECTNESS

For its first two decades PostgreSQL's engineering effort went almost entirely into correctness and durability — MVCC, WAL, replication. Observability was comparatively neglected because it doesn't change what answers a query returns; it only changes how fast you can find out why an answer is slow. The wait-event taxonomy (9.6, 2016) is the inflection point: for the first time, every blocking wait in the entire backend process — not just lock waits, which had partial visibility earlier — became a single queryable field. Everything in this chapter downstream of that field exists because 9.6 made it possible to ask.

ARC 03 · NAIVE SOLUTION

Attempt #1: the checklist runbook

Derive the naive approach honestly, the way §3 always does in this course. Faced with "the database is slow," most teams reach for a runbook: a sequence of checks and blind remediations, executed top to bottom regardless of what the first few checks actually found.

bashrunbook.sh — the strawman, annotated
#!/bin/bash
# "the database is slow" — standard runbook, step 1 of 9
top -bn1 | head -20            # eyeball CPU%  — but WHICH subsystem is burning it?
iostat -x 1 5                    # eyeball disk %util — but is it checkpoint writes or reads?
df -h                              # disk full? almost never the actual cause
psql -c "SELECT count(*) FROM pg_stat_activity"   # "there are a lot of connections" — so what?
# nothing obvious → apply folklore fixes, in order, hoping one sticks:
psql -c "ALTER SYSTEM SET shared_buffers='16GB'"   # a blog post said bigger is better
psql -c "ALTER SYSTEM SET work_mem='256MB'"       # another blog post, different symptom
systemctl restart app-tier                # "turn it off and on again"
psql -c "VACUUM ANALYZE"                    # cargo-culted; runs on EVERY table, no ordering
# if still slow: page whoever wrote the query planner chapter of this course

This is not stupidity — it is where every engineer starts, and several of its steps are legitimately useful as evidence: high CPU, high disk %util, and connection counts are all real signals. The naive approach's flaw is not "checking the wrong things." It's that it treats every check as independent and every fix as low-risk, running down a fixed list instead of forming and testing a hypothesis about which of PostgreSQL's internal subsystems — the ones from chapters 1 through 19 — is the actual bottleneck.

ARC 04 · WHY IT FAILS

Checklists don't compose, don't distinguish, and often make things worse

Three concrete failure modes, each one costing real incident time:

  • Identical symptoms, different causes. "High CPU, rising p99" is consistent with at least four internally unrelated conditions: an LLVM JIT-compilation storm (chapter 16/17's executor doing more work compiling expressions than evaluating them), a spinlock convoy (many backends busy-waiting on s_lock for a buffer-pool partition lock — chapter 9), a plan regression (the planner picked a nested loop where a hash join was needed, chapter 16), or simply more legitimate query volume. A checklist that says "check CPU" cannot tell these apart — it needs the NEXT layer of instrumentation, which is exactly what §8 builds.
  • Fixes applied without a mechanism make things worse. Bumping shared_buffers when the real bottleneck is checkpoint I/O (chapter 11) does nothing for the symptom and, worse, means a *larger* dirty-buffer pool for the checkpointer to flush at the next checkpoint — the fix increases the blast radius of the very failure mode it was meant to cure. Restarting the app tier during a connection-storm incident (chapter 1) forks hundreds of new backends into a cold catalog cache exactly when the system can least afford it.
  • Checklists don't compose across incidents. A checklist tuned for last quarter's incident (say, a lock pileup) gets applied to this quarter's incident (an XID wraparound emergency) because the *symptom* ("everything is slow") looks similar, and half the checklist's steps are simply irrelevant to a wraparound condition — burning minutes an emergency freeze window doesn't have.
THE COST, QUANTIFIED

A mid-size incident-response postmortem corpus (informal, but consistent with what every experienced PostgreSQL operator will tell you) shows the same pattern: time-to-mitigate for wait-event-first diagnosis clusters around 5–15 minutes for common failure modes; checklist-first diagnosis for the SAME failure modes routinely runs 45 minutes to several hours, because each irrelevant checklist step consumes real wall-clock time and each wrong "fix" has to be undone before the next attempt. The gap is not effort — it's the absence of a model that lets you stop looking once you've confirmed a hypothesis instead of working through a fixed list regardless of what earlier steps found.

So — analogous to every other chapter's arc — we need something better than "check things in order." The candidates, examined next, all point toward the same conclusion: start from where time is spent, not from a symptom.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates, each necessary and each insufficient alone

Before arriving at wait-event-first diagnosis, it's worth taking seriously the tools operators reach for next, because each one really does help — just not on its own.

Candidate diagnostic strategiesSTEP-BY-STEP

Candidate A: watch the OS graphs (CPU / RAM / disk)

Grafana dashboards built on node_exporter or equivalent tell you the machine is busy. They cannot tell you which PostgreSQL subsystem is consuming that busyness. 90% disk utilization could be checkpoint writes (chapter 11), WAL flushes (chapter 10), or cold cache reads (chapter 9) — three different fixes, one graph. CPU-bound is even worse: the kernel scheduler doesn't know the difference between a backend doing useful planner work and a backend spinning on a spinlock waiting for another backend to release it. Necessary context, insufficient resolution.

Candidate B: read the logs

log_min_duration_statement, log_lock_waits, and log_checkpoints surface exactly what you configured them to surface — and nothing you didn't think to log in advance. A systemic wait condition (say, every backend spending 40% of its time in LWLock:BufferMapping) produces no log line at all unless you specifically instrumented for it; logs are built for known-unknowns, and an incident is frequently an unknown-unknown. Necessary for confirming specific slow statements, blind to systemic waits.

Candidate C: application-layer tracing (APM)

Distributed tracing (spans around each query call from the app) tells you a query took 4 seconds from the application's point of view. It is blind to everything that happens once the query crosses into the backend process — it cannot distinguish "4 seconds of actual execution" from "4 seconds queued behind a lock, only 3 milliseconds of which was real work." Necessary for attributing latency to a code path, blind to what happens inside PostgreSQL.

WHAT ALL THREE ARE MISSING

None of the three answers the one question that actually localizes a bottleneck to a subsystem: for the backends that ARE slow right now, what are they doing instead of running? That is precisely wait_event_type/wait_event — and it's the missing layer between "the machine looks busy" (Candidate A) and "this specific query was slow" (Candidates B/C).

ARC 06 · WHY THAT STILL HURTS

The bill for skipping the wait-event layer

Even armed with OS graphs, logs, and APM traces, an operator without the wait-event habit pays a specific, recurring cost: they can narrow a problem to "the database," and even to "this query," but not to "this subsystem" — which is the level of resolution a fix actually requires. The symptoms below are all real, all commonly seen, and all indistinguishable without wait-event sampling:

  • "CPU is at 100% but there's no slow query in the logs." Could be JIT compilation overhead exceeding execution time (chapter 16/17), could be a spinlock convoy (chapter 9), could be genuinely legitimate load. Only wait_event — or its absence, meaning the backend is actually ON CPU — plus a flamegraph (§8) tells them apart.
  • "Everything got slow at the same instant." Classic signature of either a lock-queue pileup (chapter 8 — one strong lock request blocks a FIFO queue) or a checkpoint I/O storm (chapter 11) — both produce a simultaneous, cluster-wide slowdown, and engineers under pressure often guess wrong and add an index (irrelevant to both) before checking pg_locks or pg_stat_bgwriter.
  • "Autovacuum is running constantly and nothing's improving." Without checking the actual xmin horizon (chapter 6/12), this reads as "autovacuum is broken" and gets tuned more aggressively — more workers, shorter naptime — which does nothing if a stale replication slot or forgotten serializable transaction is pinning the horizon and vacuum can never free a single dead tuple no matter how often it runs.

Each of these costs the same thing: minutes to hours of applying plausible-sounding fixes that cannot possibly work, because the fix was chosen from the symptom rather than derived from the mechanism. The final architecture closes this gap by making the wait-event taxonomy the FIRST thing you look at, not the last.

ARC 07 · FINAL ARCHITECTURE

The methodology: wait events as a map back to chapters 1–19

Every wait a backend can experience falls into one of a small number of wait_event_type categories, and PostgreSQL assigns each backend's current wait to exactly one wait_event name within that category, visible live in pg_stat_activity. The categories are not arbitrary — each one names a specific kind of internal blocking, and each maps onto a subsystem you've already studied. Click through them below; this map IS the diagnostic methodology.

Notice the structure this creates: a wait_event_type tells you the CLASS of blocking mechanism; a specific wait_event tells you the exact resource; and that resource always belongs to one chapter's subsystem. The entire diagnostic loop is: sample pg_stat_activity → find the dominant wait → look up which subsystem owns it → go confirm with that subsystem's own stat view (§8) → apply the fix that subsystem's architecture predicts.

WHY THIS GENERALIZES

This isn't a lookup table you memorize — it's a consequence of PostgreSQL's own source layout. Every blocking primitive in the backend (an LWLock acquire, a heavyweight lock wait, a buffer pin wait, a read/write syscall, a latch wait) is wrapped by pgstat_report_wait_start()/pgstat_report_wait_end() (§8), so the taxonomy is exhaustive by construction: if a backend isn't on CPU doing useful work, it is always wrapped in one of these categories. There is no fifth kind of wait hiding somewhere.

ARC 08 · INTERNAL IMPLEMENTATION

Reading the views as instrumentation of the internals

(a) How a wait gets recorded — pgstat_report_wait_start/_end

Every backend has a PGPROC entry in shared memory (chapter 1's fixed-size-at-boot slot array). One field in it, wait_event_info, packs both the wait_event_type and the specific wait_event into a single 32-bit value. When a backend is about to block — acquiring an LWLock via LWLockAcquire(), waiting on a heavyweight lock in LockAcquireExtended(), waiting on a buffer pin, or issuing a blocking read()/write()/fsync() — it calls pgstat_report_wait_start(wait_event_info), which does nothing more than write that packed value into its OWN PGPROC slot. When the wait ends, pgstat_report_wait_end() writes it back to zero. This is deliberately a single, unlocked 32-bit store — no spinlock, no LWLock, no memory barrier more than the platform gives you for free on an aligned word write — because the only writer is the backend itself, and any number of readers (other backends' pg_stat_activity queries) can tolerate reading a slightly stale or torn value; a wait sample is a probabilistic instrument, not a transactional one. This is precisely why sampling pg_stat_activity at high frequency has near-zero overhead on the system being observed — you are reading words other backends were writing anyway.

Cpgstat_report_wait_start() — simplified from src/backend/utils/activity/pgstat_wait_event.c-era code
void
pgstat_report_wait_start(uint32 wait_event_info)
{
    if (!pgstat_track_activities || !MyProc)
        return;

    /* One unlocked store. No lock is needed: MyProc->wait_event_info
     * is written ONLY by this backend, and any other backend reading
     * it via pg_stat_activity tolerates a torn or stale read — it's
     * a best-effort instrument, not a source of truth for correctness. */
    MyProc->wait_event_info = wait_event_info;
}

void
pgstat_report_wait_end(void)
{
    if (!pgstat_track_activities || !MyProc)
        return;
    MyProc->wait_event_info = 0;   /* 0 == "not waiting", i.e. actually running */
}

A "poor man's profiler" falls directly out of this: repeatedly sample the field and count occurrences.

SQLthe cheapest useful profiler you will ever run
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE state = 'active'
GROUP BY 1, 2
ORDER BY 3 DESC;
-- run this once a second for 30 seconds and you have a histogram of where
-- every active backend spent its time, with ZERO added instrumentation.

The rigorous version of the same idea is the pg_wait_sampling extension: a background worker that samples every backend's wait_event_info at a configurable frequency (default 10 ms) and accumulates a proper histogram in shared memory, avoiding the overhead and imprecision of issuing a real SQL query in a tight client-side loop. It is the closest thing PostgreSQL has to Oracle's Active Session History (§9), and it is the tool to reach for once ad-hoc sampling has told you which subsystem to watch closely.

(b) pg_stat_statements — chapter 9 and chapter 10's cost, attributed per query

pg_stat_statements (contrib since 8.4) normalizes queries by structure (constants replaced with placeholders) and accumulates, per normalized query: calls, total_exec_time, mean_exec_time, stddev_exec_time (PG13 renamed these from total_time/ mean_time to make the plan-time/execute-time split explicit alongside total_plan_time), rows, and critically shared_blks_hit/shared_blks_read — this pair IS chapter 9's buffer cache, exposed per query: a hit means the page was already resident in shared_buffers, a read means a page-table miss that went to the OS (and possibly disk). A query with a low hit ratio relative to its peers is a direct signal that its working set doesn't fit the cache or that it's scanning cold data. The wal_bytes column is chapter 10's WAL volume, attributed per query — the tool that turns "why is WAL volume so high" into "which specific query is generating it."

The single most common misuse of this view: sorting by mean_exec_time. A query that takes 2ms but runs 50 million times a day contributes 100,000 seconds of aggregate backend time — dwarfing a query that takes 4 seconds but runs twice. mean_exec_time answers "is any single execution slow"; total_exec_time answers "what is actually consuming this system's capacity," which is almost always the question you mean to ask during capacity work. Sort by total_exec_time first, always.

SQLthe query that actually finds your load, not your outliers
SELECT query, calls, total_exec_time,
       total_exec_time / NULLIF(calls,0) AS mean_ms,
       100.0 * shared_blks_hit / NULLIF(shared_blks_hit + shared_blks_read, 0) AS cache_hit_pct,
       wal_bytes
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

(c) pg_stat_user_tables and pg_statio_* — chapter 12 and chapter 9, per relation

n_dead_tup, n_live_tup, last_autovacuum, and autovacuum_count are chapter 12's vacuum instrumentation exposed per table. A table whose n_dead_tup keeps climbing despite recent last_autovacuum timestamps is telling you autovacuum ran but couldn't reclaim anything — which almost always means the xmin horizon (chapter 6) hasn't advanced, not that vacuum itself is misconfigured (§11's first postmortem is exactly this). pg_statio_user_tables/ pg_statio_user_indexes give the same hit/read split as pg_stat_statements' buffer columns, but per relation instead of per query — useful for asking "which TABLE has a bad cache-fit problem" rather than "which query."

(d) pg_stat_bgwriter / PG17's pg_stat_checkpointer — chapter 11's warning light

PostgreSQL 17 split checkpoint-related counters out of pg_stat_bgwriter into a dedicated pg_stat_checkpointer view; conceptually both expose the same signal. buffers_checkpoint and buffers_clean count pages written by the checkpointer and the background writer respectively — the SYSTEM's own I/O scheduling, spread out on purpose (chapter 11's checkpoint_completion_target). buffers_backend counts pages a client backend had to write ITSELF because it needed a free buffer and the clock sweep (chapter 9) landed on a dirty page that neither the checkpointer nor bgwriter had gotten to yet. A rising buffers_backend relative to buffers_checkpoint+buffers_clean is the single clearest "the checkpointer can't keep up" signal in the entire system — it means foreground query latency is now paying for background I/O that should have been invisible.

(e) pg_locks joined to pg_stat_activity — chapter 8's queue, made visible

pg_locks lists every lock request in the system, granted or not, tagged with the requesting pid. Joined to pg_stat_activity you get the query text and wait time for each holder and waiter. Finding the ROOT blocker in a chain — session A blocks B blocks C — needs the self-join below, which walks the FIFO queue chapter 8 describes until it finds a lock that is granted with no un-granted requester ahead of it on the same relation.

SQLfinding the root of a blocking chain
WITH RECURSIVE chain AS (
  SELECT blocked_locks.pid AS blocked_pid,
         blocking_locks.pid AS blocking_pid,
         1 AS depth
  FROM pg_locks blocked_locks
  JOIN pg_locks blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
   AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
   AND blocking_locks.relation  IS NOT DISTINCT FROM blocked_locks.relation
   AND blocking_locks.pid != blocked_locks.pid
   AND blocking_locks.granted
  WHERE NOT blocked_locks.granted
)
-- walk `chain` upward; the row whose blocking_pid never appears as a
-- blocked_pid elsewhere in the chain is the root — usually one old,
-- boring session holding ACCESS SHARE that everyone else queued behind.
SELECT * FROM chain;

(f) pg_stat_replication — chapter 18's lag, in four LSNs

sent_lsn, write_lsn, flush_lsn, replay_lsn mark four distinct points in a standby's pipeline: how far the primary has SENT WAL, how far the standby has WRITTEN it to its own disk, how far it has FSYNCED that write, and how far the startup process has actually REPLAYED it into the standby's buffer pool. Subtracting replay_lsn from sent_lsn (via pg_wal_lsn_diff) gives true end-to-end replication lag in bytes; the gap between any two adjacent columns tells you WHICH stage is behind — a sent/write gap is network, a write/flush gap is the standby's disk, and a flush/replay gap is the startup process's own replay throughput (chapter 11's redo loop, running forever on a standby).

(g) Flamegraphs and CPU profiling

When wait-event sampling shows a backend that is NOT waiting — wait_event is null, meaning it's genuinely on-CPU — the next tool is a CPU profiler. perf record -p <backend_pid> -g -- sleep 30 samples the call stack at a fixed frequency and perf report/a flamegraph renderer turns it into a visual stack. Reading a PostgreSQL flamegraph requires recognizing a small vocabulary of shapes: tall, repeating ExecProcNode towers are the volcano executor's recursive pull-based model (chapters 16–17) — normal and expected, their WIDTH tells you which executor node dominates; wide flat plateaus of s_lock mean a spinlock convoy — backends busy-waiting (not sleeping!) for a very short critical section, usually a sign that a spinlock-protected structure (a buffer header, a LWLock's own wait-list spinlock) is under far more contention than it was designed for; frequent hash_search_with_hash_value is catalog/syscache or relcache probing — normal in small amounts, a red flag in large amounts, since it means a backend is repeatedly resolving catalog metadata it should have cached; and unusually WIDE, otherwise unlabeled frames appearing only when jit=on are LLVM-compiled expression evaluation functions — the classic PG11+ regression where JIT's own compilation cost (not its output's execution cost) dominates a short OLTP query, because jit_above_cost's default threshold was tuned for the analytical queries JIT was designed for, not point lookups.

Debug symbols are mandatory for any of this to be legible: a release build stripped of symbols resolves every frame to a hex address. Distro -dbgsym/debuginfo packages, or building PostgreSQL yourself with --enable-debug (accepting a modest performance cost from disabled inlining/optimization in some configurations), are the price of a readable flamegraph.

(h) eBPF/bpftrace for I/O latency you cannot see any other way

iostat reports AVERAGES — a device at "12ms average latency" can be hiding a bimodal distribution where 95% of I/Os complete in 1ms and 5% take 200ms, and the average tells you nothing about which backends are actually experiencing the tail. A bpftrace script hooking block:block_rq_issue and block:block_rq_complete (or the packaged biolatency tool from the BCC/bpftrace toolkit) builds a true latency HISTOGRAM of every I/O the block layer issues, letting you see that tail directly and correlate it against PostgreSQL's own DataFileRead wait-event samples from the same window — the moment a query blocked on DataFileRead for 180ms is a moment you can go find in the histogram and confirm it wasn't an artifact of sampling.

Every database answers "why is it slow" differently

PostgreSQL's design bets the same way its process model did (chapter 1): keep the core mechanism minimal and nearly free (one unlocked word per backend), and let the ecosystem build richer tooling (pg_wait_sampling, pgBadger, commercial APMs) on top rather than baking a heavyweight historical repository into core. Oracle's ASH is the acknowledged ancestor of this entire idea — Oracle shipped 1-second-granularity historical wait sampling, retained and queryable, over a decade before pg_wait_sampling existed as an extension, and its taxonomy of wait classes maps almost one-to-one onto PostgreSQL's wait_event_type categories.

ARC 10 · PERFORMANCE CHARACTERISTICS

The cost of watching, and the discipline of predicting before measuring

Observability is not free — every layer of instrumentation this chapter relies on has a real, quantifiable cost, and knowing that cost is itself part of using the tools responsibly:

  • track_io_timing adds a clock_gettime() (or platform equivalent) call around every I/O operation to populate pg_stat_statements' timing columns and pg_stat_bgwriter's write-time fields. On hardware with a fast vDSO clock source this is sub-microsecond and invisible; on older or virtualized platforms without a fast clock path it can be a measurable percentage of small-I/O-heavy workloads — always benchmark before enabling it broadly in a latency-sensitive OLTP fleet.
  • pg_stat_statements tracking costs one extra hash-table lookup (keyed on a normalized query fingerprint) plus a handful of atomic counter increments per statement execution. pg_stat_statements.track = top (only top-level statements) is materially cheaper than all (every statement inside functions too) on PL/pgSQL-heavy workloads with deep call nesting.
  • perf sampling at typical frequencies (99Hz–999Hz) is a few percent of CPU at most and safe to run against a live production backend for a bounded window; CONTINUOUS profiling (always-on, fleet-wide) is a different cost model entirely and needs its own capacity budget.
  • Sampling frequency vs statistical confidence. Wait-event sampling is a Monte Carlo estimate of where time goes: sampling at 1Hz for 30 seconds gives you ~30 samples per backend — enough to find a wait that dominates 50%+ of a backend's time, not enough to reliably characterize a wait that occurs 2% of the time. pg_wait_sampling's default 10ms interval buys roughly 100x the samples per unit time versus a manual 1-second poll loop, at a correspondingly higher (but still small) fixed cost.

THE ACTUAL TUNING METHODOLOGY

Everything in this section supports one discipline, worth stating explicitly because it's the difference between engineering and guessing: before you flip a GUC, write down — from the mechanism, not from intuition — which direction you expect the metric to move and why. Raising checkpoint_completion_target from 0.5 to 0.9 should, mechanically, REDUCE buffers_backend and REDUCE the variance (not necessarily the mean) of write-heavy query latency, because the checkpointer is spreading the same total I/O over a longer window. If you raise it and buffers_backend goes UP, your model of what's happening is wrong somewhere — probably a second checkpoint is now starting before the first one's spread-out window finished, which is itself a diagnosable, mechanistic condition (§11 case 3), not a mystery. Change one variable. Measure with pgbench and pg_stat_statements deltas. A confirmed prediction is evidence your mental model is right; a surprising result is a bug in your model, not a "huh, weird."

ARC 11 · REAL-WORLD PRODUCTION

Three postmortems, traced to internals, with the fix and the prevention

Postmortem 1: the XID wraparound emergency

The pager fires at 3am: ERROR: database is not accepting commands to avoid wraparound data loss. The cluster is now effectively read-only. Reconstructing the timeline afterward always looks the same shape: weeks earlier, a logical replication slot was created for a since-decommissioned consumer and never dropped, or an analytics job opened a transaction and left it idle (a runaway BEGIN with no COMMIT, often via a connection pool that never closed a session cleanly). Chapter 6 established that every tuple's visibility is decided relative to the OLDEST transaction any backend might still need to see — the xmin horizon — and chapter 12 established that autovacuum can only reclaim, and only FREEZE, tuples older than that horizon. A stale replication slot pins the horizon at the slot's own xmin/catalog_xmin forever, because the slot represents a promise ("I have not yet consumed changes older than this") that PostgreSQL keeps even after the consumer stopped listening. An idle transaction pins it at its own snapshot's xmin for as long as it stays open.

With the horizon frozen, autovacuum's freeze workers run — CPU and I/O go into them constantly, exactly as designed — but relfrozenxid on every table stays put, because vacuum cannot advance a table's frozen point past a transaction ID that some backend (or slot) might still need to see as not-yet-happened. Every table's age(relfrozenxid) keeps climbing along with global transaction throughput, and it crosses autovacuum_freeze_max_age (default 200 million, prompting more urgent forced autovacuums), then crosses the harder emergency thresholds near 2 billion where PostgreSQL — correctly, because XIDs are a 32-bit circular space and wraparound would make old committed rows silently appear to be from the future, i.e. invisible — refuses new transactions outright rather than risk data loss.

The recovery procedure has a strict, non-obvious ordering, because the emergency window is finite and wasted motion costs real minutes: first, find and neutralize whatever is pinning the horizon — pg_replication_slots.xmin/catalog_xmin for a stale slot (drop it, or advance it if the consumer is coming back), and pg_stat_activity's oldest xact_start for a runaway transaction (terminate it). Second, and this is the step people get backwards under pressure: run VACUUM (FREEZE, VERBOSE) on the tables CLOSEST to the wraparound threshold first — ordered by age(relfrozenxid) descending against pg_class, joined to table size, since a huge table that's merely close to the threshold is a bigger emergency than a tiny one further from it. Freezing tables in the wrong order (say, alphabetically, or smallest-first out of habit) burns the emergency window on low-priority tables while the actual clock — global XID consumption, which does not pause for your vacuum run — keeps ticking toward the hard limit. Single-user mode (starting the postmaster with --single) is the true last resort: it exists for the case where even the read-only-safe emergency mode won't let a VACUUM proceed, and it works by bypassing the normal connection machinery entirely — no concurrency, no other backends to coordinate with, just one session doing the minimum VACUUM FREEZE needed to push relfrozenxid back under the limit so normal operation can resume.

Prevention: alert on age(datfrozenxid) and on replication-slot lag well before the emergency thresholds (a rising trend over days is a slow-motion version of this same incident, always catchable early); treat an unused replication slot as an active production liability, not a harmless leftover; and never let application code open a transaction it doesn't control the lifetime of.

Postmortem 2: lock pileup behind a schema migration

A deploy runs a routine-looking ALTER TABLE orders ADD COLUMN status_detail text during business hours. Within seconds, every query against orders — including plain SELECTs that share no actual conflict with each other — is blocked, and the on-call sees a wall of "still waiting" queries with no single obviously slow statement anywhere. The mechanism is chapter 8's lock manager taken exactly at its word: ALTER TABLE ... ADD COLUMN (when it isn't the PG11+ fast-path for a constant default, see below) requires ACCESS EXCLUSIVE — the strongest lock mode, incompatible with every other mode including plain ACCESS SHARE. If one long-running SELECT is already holding ACCESS SHARE when the ALTER TABLE arrives, the DDL must queue and wait for that SELECT to finish. That alone would be a minor, contained wait. The actual outage comes from what happens NEXT: every subsequent SELECT that arrives while the ACCESS EXCLUSIVE request is still queued must ALSO wait — even though a plain SELECT's ACCESS SHARE is perfectly compatible with every other ACCESS SHARE already granted. PostgreSQL's lock queue is FIFO per relation specifically to prevent starvation: granting a weaker, compatible lock to a request that arrived AFTER a still-waiting stronger request would let a steady stream of readers starve the writer indefinitely. The correct fairness guarantee (no request waits forever) converts one slow reader plus one blocked migration into a queue that swallows the entire table's traffic.

The fix, in the moment: find and terminate the long-running SELECT (via the blocking-chain query from §8) so the ALTER TABLE can proceed, unblocking the queue behind it. The fix, so it never queues dangerously again: wrap DDL in an explicit lock_timeout plus a retry loop — set lock_timeout to a few seconds, attempt the ALTER TABLE, and on a lock-timeout error simply retry after a short backoff; this bounds the WORST case to "the migration takes a few extra minutes to land" instead of "the migration parks an ACCESS EXCLUSIVE request in the queue for the duration of a slow analytics query and takes the table down with it." And since PostgreSQL 11, ADD COLUMN ... DEFAULT <constant> no longer needs ACCESS EXCLUSIVE for a table rewrite at all: the default value is stored directly in the catalog (pg_attribute.atthasmissing/attmissingval, chapter 3's tuple-layout machinery) and materialized lazily for pre-existing rows the first time they're read, rather than rewriting every existing tuple up front. A VOLATILE default expression (e.g. now(), or anything not reducible to a single constant at DDL time) still forces the old rewrite-and-lock-everything path, which is why "is this default actually constant" is the first thing to check before a migration, not an afterthought.

Postmortem 3: checkpoint I/O storm meets a connection-storm

A primary fails over. Within seconds, thousands of application connections that were pointed at the old primary reconnect — to the new primary, or briefly to nowhere and then everywhere at once — and every one of those reconnects is chapter 1's fork-plus-cold-cache cost multiplied by however many connections your pool allows. Ordinarily this is survivable; it becomes an outage here because it lands during a checkpoint that was already poorly paced. If checkpoint_completion_target is low (historically defaulted to 0.5, and even 0.9 doesn't help if checkpoint_timeout/max_wal_size force checkpoints to happen too often for the completion target to matter — chapter 11), the checkpointer's writes cluster into a burst near the end of each checkpoint interval rather than spreading evenly across it. That burst saturates disk write bandwidth at the exact moment hundreds of freshly forked, cold-cache backends need to ISSUE READS for pages that aren't resident anywhere yet (chapter 9's cache-miss path). Reads and the checkpoint's writes compete for the same disk queue; DataFileRead wait times climb into the hundreds of milliseconds; new connections time out during authentication or their very first query, some clients retry immediately, and the retry traffic compounds the storm rather than relieving it.

The fix: raise checkpoint_completion_target toward 0.9 so the checkpointer spreads writes across nearly the whole interval instead of bursting; size max_wal_size generously enough (chapter 10) that checkpoints are triggered by TIME (checkpoint_timeout) rather than by WAL VOLUME under normal load, giving the completion-target spreading room to actually matter; and separately, decouple the failover reconnect storm from the cache-cold problem by keeping application connections behind a pooler (chapter 1) so failover multiplies pooler-side reconnects, not backend forks, and by adding jitter to client-side reconnect logic so ten thousand clients don't retry in the same 100ms window.

Capacity planning: the math you should do before you provision, not after you page someone

Working set vs shared_buffers vs OS cache. A page not found in shared_buffers still might be resident in the OS page cache — PostgreSQL relies on this deliberately (it never bypasses the kernel's own buffering with O_DIRECT by default), which means the SAME hot page can genuinely exist in memory twice: once in PostgreSQL's buffer pool, once in the kernel's cache, wasting RAM proportional to how much they overlap. effective_cache_size does not allocate anything — it's purely a planner hint (chapter 16) estimating how much of the working set is LIKELY resident somewhere in RAM (shared_buffers + OS cache combined), used to decide whether an index scan's extra random I/O is likely to hit cache or disk. Setting shared_buffers to roughly 25% of RAM and letting the OS cache the rest is the standard heuristic precisely because double-buffering the entire working set in both places wastes memory without buying anything.

WAL volume estimation. Bytes of WAL generated per transaction scale with rows changed × (row width + per-tuple overhead) — and immediately after every checkpoint, the FIRST modification to any given page must emit a full-page image (chapter 10's full_page_writes) rather than a delta, because torn-page protection requires a complete "before" reference if a crash happens mid-write. This means WAL volume is not uniform across a checkpoint interval — it spikes right after each checkpoint and tapers as pages that were already full-page-written get touched again. Multiply expected transaction rate by expected bytes-per-transaction (measured directly via pg_stat_statements.wal_bytes, not guessed) to get a required WAL write bandwidth, and provision WAL storage I/O headroom for the post-checkpoint spike, not the interval average.

Connection budget from cores. Chapter 1 established that active, CPU-bound backends beyond roughly 2–4× core count buy latency, not throughput — the kernel scheduler and lock contention start dominating past that point. The number to budget is ACTIVE backends, not total connections; a pooler (PgBouncer in transaction mode) is what lets you accept far more CLIENT connections than that budget while keeping ACTIVE backend count near the sweet spot.

The methodology, restated as a rule you can actually follow under pressure: change exactly one variable; before you re-measure, write down which direction the change should move which metric, and why, from the mechanism; then measure with pgbench (for a controlled synthetic load) and pg_stat_statements deltas (for real production traffic, before/after). A confirmed prediction builds confidence in your mental model of the system; a surprising result means the model — not the incident — is what needs fixing.

The wraparound emergency from §11 is enforced here — the actual gate PostgreSQL refuses to cross:

Cvarsup.c — GetNewTransactionId(), simplified but faithful
TransactionId
GetNewTransactionId(bool isSubXact)
{
    TransactionId xid;

    /* xidStopLimit is computed from the oldest relfrozenxid still
     * live in any database, minus a safety margin. Crossing it would
     * risk a committed row's xmin looking like it's "in the future"
     * once the 32-bit XID space wraps — silent, catastrophic data loss. */
    if (TransactionIdFollowsOrEquals(ShmemVariableCache->nextXid, xidStopLimit))
        ereport(ERROR,
            (errmsg("database is not accepting commands to avoid wraparound data loss"),
             errhint("Execute a database-wide VACUUM in that database.\n"
                      "You might also need to commit or roll back old prepared transactions,"
                      " or drop stale replication slots.")));

    /* xidWarnLimit fires much earlier — a WARNING, not a hard stop —
     * specifically so operators get days of runway before the ERROR path
     * above becomes reachable at all. */
    else if (TransactionIdFollowsOrEquals(ShmemVariableCache->nextXid, xidWarnLimit))
        ereport(WARNING,
            (errmsg("database must be vacuumed within %u transactions", ...)));

    xid = ShmemVariableCache->nextXid;
    TransactionIdAdvance(&ShmemVariableCache->nextXid);
    return xid;
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Wait-event reporting is a single unlocked word, not a queue or a log — any synchronization primitive heavier than an aligned store would make the observability mechanism itself a source of contention, defeating its purpose. 2. The wraparound check is a HARD ERROR, not a warning, at the stop limit — because the alternative (letting a transaction through and silently corrupting visibility for the entire cluster) is categorically worse than temporary unavailability; PostgreSQL always prefers a loud, safe stop to a quiet, unsafe continuation, the same philosophy chapter 1's crash protocol embodies. 3. The WARNING limit exists purely to buy operators lead time — it's a deliberately generous early-warning threshold precisely because the failure mode it's warning about is catastrophic and the fix (vacuum) takes real wall-clock time to run.
