Chapter 1 named the exchange/binding/queue model as the fix for producer-consumer coupling. This chapter opens the box: routing is not one algorithm, it's four different data-structure decisions, each solving a different filtering problem at a different cost. You'll derive direct, fanout, topic, and headers exchanges from the requirement each one satisfies — not memorize them as a list — and go deep on the one that actually deserves the depth: the trie rabbit_exchange_type_topic walks word by word, and the pathological patterns that make it slow.

ARC 01 · THE PROBLEM

One publish, an unknown number of interested parties

Chapter 1 established that a producer must never reference a consumer directly — it publishes to an exchange with a routing key and walks away. That requirement, taken seriously, creates a genuinely hard question that this chapter is entirely about: given a routing key (and possibly a set of message headers), which of the potentially tens of thousands of queues bound to this exchange should receive a copy of this message — decided in the hot path, on every single publish, without the producer's help?

Unpack what "decided in the hot path" actually demands, and four sub-requirements fall out, each pulling in a different direction:

  • Exact addressing, when that's all you need. A work-queue producer that always wants exactly one named worker pool doesn't need pattern matching — it needs the cheapest possible exact lookup.
  • Broadcast, when you don't want filtering at all. A "notify every subscriber" producer shouldn't pay for key comparisons it doesn't need — ignoring the key entirely should be the cheapest path, not an afterthought bolted onto a general matcher.
  • Hierarchical, pattern-based addressing. A market-data feed with routing keys like stock.usd.nyse needs subscribers who can say "give me everything under stock.usd.*" or "everything under stock.#" without enumerating every instrument that will ever exist.
  • Structured, non-hierarchical predicates. Sometimes the thing you want to filter on isn't a dot-separated string at all — it's a set of key/value properties (format=pdf, region=eu) with no natural single-string hierarchy to encode them into.

A single "one true matching algorithm" trying to satisfy all four badly serves all four: exact-match doesn't need pattern overhead, broadcast doesn't need comparisons at all, hierarchical wildcards need a structure regex wasn't designed to be cheap at, and property matching needs neither strings nor hierarchy. RabbitMQ's answer — four independent exchange types, each a distinct routing function against the same binding-table shape — is a direct, unapologetic consequence of refusing to force one data structure to do all four jobs adequately rather than doing each job well.

WHAT rabbit_exchange:route/2 ACTUALLY IS

Strip away the AMQP ceremony and every exchange is one function: route(Exchange, RoutingKeyAndHeaders) -> [QueueNames]. The exchange's type selects which implementation module — rabbit_exchange_type_direct, _fanout, _topic, or _headers — supplies that function. Nothing else about the broker changes based on exchange type; publishing, delivery, and queue mechanics are identical downstream of whatever list of queue names comes back. This chapter is about what happens inside that one function call, for each of the four implementations, and what it costs.

DEEP CONTEXT · WHY THE WIRE PROTOCOL FIXES THE TYPES BUT NOT THE ROUTING FUNCTION

AMQP 0-9-1 standardizes the existence and declared behavior of direct, fanout, topic, and headers exchanges — any compliant client can declare one and expect the same semantics from any compliant broker. It says nothing about how a broker must implement the matching internally: a hash table, a trie, or a linear scan are all spec-compliant as long as the observable routing decisions match. That gap is exactly where this chapter lives — the protocol guarantees behavior, and RabbitMQ's implementation choices (ETS-backed hash lookups, a Mnesia/Khepri-backed trie) are what make that behavior fast enough to matter at production binding counts.

ARC 03 · NAIVE SOLUTION

Attempt #1: one global list, one linear scan, exact string equality

Derive it the way an engineer would who hadn't yet split routing into four types. The simplest thing that could possibly route messages: keep one flat list of every binding ever created, broker-wide — each entry just a (queue, exact_key) pair — and on every publish, walk the entire list, comparing the message's routing key against each entry's key with plain string equality, delivering to every queue whose entry matches.

pseudocodenaive_router.py — the strawman, annotated
class NaiveBroker:
    def __init__(self):
        # one global, unindexed list — no notion of "exchange" at all
        self.bindings = []  # list of (queue_name, exact_routing_key)

    def bind(self, queue_name, exact_routing_key):
        self.bindings.append((queue_name, exact_routing_key))

    def publish(self, routing_key, message):
        matched = []
        for queue_name, key in self.bindings:      # O(total bindings), every publish
            if key == routing_key:                    # exact string equality only
                matched.append(queue_name)
        for q in matched:
            deliver(q, message)
        # no wildcards, no header predicates, no "ignore the key" mode —
        # and this scan runs in full even for a message with one true match.

ARC 04 · WHY IT FAILS

The math: O(B) per publish, and hierarchy is simply inexpressible

Formalize what the deck just showed, then go further than raw scan cost — the naive model's expressive limits are worse than its performance limits.

  • Cost scales with total bindings, not relevant bindings. With B bindings broker-wide, every publish costs O(B) string comparisons, even when only one binding could conceivably match. There is no per-exchange scoping, let alone per-key indexing — a publish to a barely-used queue pays the same scan cost as a publish into the busiest exchange on the node.
  • Hierarchical subscriptions require combinatorial enumeration. Suppose routing keys look like stock.<currency>.<venue> with 8 currencies and 40 venues — 320 concrete keys. A subscriber who wants "everything in USD, any venue" cannot express that as one exact-match binding; they'd need 40 separate bindings, one per venue, and every time a new venue is added, every "any venue" subscriber's binding set must be updated out-of-band. Scale that to a real feed with thousands of instruments and the naive model requires tens of thousands of individually maintained literal bindings to emulate what a single wildcard pattern should express in one line.
  • Broadcast is unbounded enumeration, not "ignore the key." There is no way to say "every routing key, forever" in an exact-match model except literally binding every future key value in advance — which is impossible for keys that don't exist yet. Fanout needs a fundamentally different rule (ignore the key entirely), not a very large set of exact-match bindings.
  • Structured predicates don't fit a single string at all. "Route to compliance if format=pdf AND region=eu" has no faithful single-string routing-key encoding without inventing an ad hoc concatenation convention ("pdf.eu") that every producer and consumer must agree on by hand — exactly the kind of implicit, undocumented coupling the exchange model exists to eliminate.
THE NUMBERS, AT PRODUCTION SCALE

A moderately busy RabbitMQ node running dozens of services can easily accumulate tens of thousands of bindings — one per queue per routing pattern per exchange, multiplied across every service. At 50,000 bindings, a naive O(B) linear scan performing 50,000 string comparisons on every single publish is not a rounding error — it is the dominant cost of the publish path, applied uniformly whether the exchange in question has three bindings or thirty thousand. The fix has to do two things at once: scope work to the publishing exchange (chapter 1's binding already implies this) and choose a matching structure whose cost is a function of the pattern language actually in use — not one algorithm forced to serve exact match, broadcast, hierarchy, and predicates equally badly.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Four candidates, evaluated against the four sub-requirements

Walk through the actual design space RabbitMQ's routing model occupies, in the order a careful engineer would eliminate candidates:

Candidate A: a hash table keyed by exact routing key (direct exchange) ✓ for exact match

If a binding's key must equal the publish's routing key exactly, there's no reason to scan anything — index bindings in a hash table keyed by (exchange, routing_key), and a publish becomes a single O(1) lookup returning the (possibly empty) list of bound queues for that exact key. This is strictly better than the naive scan for exact-match workloads and costs nothing extra for the broadcast, hierarchy, or predicate cases — it just doesn't solve them. Adopted for exact match; solves nothing else by design.

Candidate B: ignore the key, return every bound queue (fanout exchange) ✓ for broadcast

For "every subscriber gets everything," there is no key to index at all — the fastest possible routing function is the one that does no comparison whatsoever and simply returns the exchange's full list of bound queues. This is the cheapest of the four exchange types precisely because it does the least work: no hashing, no pattern evaluation, just a table scan of already-known destinations. Adopted for broadcast.

Candidate C: evaluate every binding as a general regex (rejected)

For hierarchical wildcards, the obvious next idea is "let each binding be an arbitrary regex, and test the routing key against every regex on publish." This genuinely supports arbitrary patterns — but it inherits the naive model's O(B) scan (now with per-comparison cost far higher than string equality), and general regex engines admit catastrophic backtracking: a pathologically constructed pattern can make a single match attempt take exponential time in the input length, on the broker's hot path, for every publish. Rejected: unindexable, and the pattern language is more powerful than the problem needs, at a real security/availability cost (a ReDoS-shaped binding is a denial-of-service vector against your own broker).

Candidate D: restrict the pattern language, then build a trie over it (topic exchange) ✓ for hierarchy

The fix is to deliberately shrink the pattern language until it's structurally indexable: routing keys are dot-separated words, and a binding pattern may contain literal words, * (exactly one word), or # (zero or more words) — nothing else, no character classes, no backreferences, no general alternation. That restriction is precisely what makes a trie over words a valid index: at each trie node, you branch on the next routing-key word using literal, *, or # edges, walking forward one word at a time instead of re-testing every binding's full pattern from scratch. The pattern language was narrowed specifically to admit this data structure — this is the deliberate trade AMQP's designers made, and §8 walks the algorithm itself in full.

Candidate E: match on structured key/value properties (headers exchange) ✓ for predicates, by elimination

When the filter isn't naturally a hierarchy at all — a set of independent properties like format=pdf, priority=high — force-fitting it into a dot-separated routing key is itself the wrong move (you'd be reinventing headers-as-strings). The headers exchange instead ignores the routing key completely and matches a binding's declared header spec against the message's actual headers table, with an explicit x-match: all (every declared key must match) or x-match: any (at least one must) rule. It's adopted last, and reluctantly: as §6 and §8 make precise, there is no general way to index an arbitrary set of key/value predicates the way a hash table indexes exact strings or a trie indexes hierarchical words — so this candidate keeps the naive model's O(bindings) scan, just scoped to one exchange instead of the whole broker. Adopted only because some filtering needs genuinely don't fit strings.

THE PATTERN ACROSS ALL FOUR

Every adopted candidate is the cheapest structure that correctly serves its own sub-requirement — not a general matcher configured four ways. Direct is a hash table because exact match needs nothing richer. Fanout is a bare list because broadcast needs no comparison at all. Topic is a trie because the pattern language was narrowed until a trie became valid. Headers is a linear scan because arbitrary predicates genuinely resist indexing. Picking the wrong one for your workload — headers when you meant topic, topic when you meant direct — doesn't just cost elegance; §6 makes the price concrete.

ARC 06 · WHY THAT STILL COSTS

Four different bills, and one of them can blow up

Adopting the right structure per exchange type doesn't make routing free — it makes each type's cost proportional to the problem it solves, which is a very different claim from "cheap." Each type's residual cost, honestly stated:

  • Direct's hash lookup is O(1) per key, but still O(1) × publish rate. At extreme publish rates, even a single hash lookup and the surrounding channel-process bookkeeping is real, measurable CPU — it's just the cheapest possible version of that cost, not zero.
  • Fanout's cost is O(N) in bound queues, not O(1) — cheapest per comparison, not free in aggregate. Delivering to 500 bound queues means 500 delivery operations no matter how trivial the routing decision was; fanout moved the cost from "deciding who" to "delivering to everyone," and at high queue-fanout counts that delivery cost dominates.
  • The topic trie's cost is near O(words) for well-behaved patterns — and can become exponential for pathological ones. This is the one genuinely nonlinear risk in the whole chapter, and it deserves the honest version, not the marketing version: a plain literal or single-* pattern set walks the trie in a small number of steps proportional to the routing key's word count. But # matches zero-or-more words, so at a trie node with a #-edge, the matcher must try every possible number of words consumed before continuing — and if the pattern set contains multiple chained # edges sharing a prefix, each one multiplies the number of continuations the matcher must explore. A handful of overlapping #-heavy bindings on a hierarchy with many words is a real, documented way to make one exchange's routing decision measurably, disproportionately expensive.
  • Headers matching is O(bindings) with no indexing possible in the general case, and it's the slowest of the four by construction. Because a binding's header spec is an arbitrary set of key/value pairs with no guaranteed shared structure across bindings, there's no hash key or trie edge to build an index around — the broker must compare the message's headers against every single binding's spec, one at a time, for every publish to that exchange. This isn't an implementation oversight; it is the genuine cost of a matching model general enough to express arbitrary predicates.
DON'T CONFUSE BINDING-TABLE COST WITH ROUTING COST

Everything above is about the cost of routing a message that's already being published — a read-mostly, hot-path operation. Creating or deleting a binding is a different, much rarer operation that goes through the cluster's metadata store — historically Mnesia, migrating to Khepri (chapter 10) — and pays a real replication/commit cost across cluster nodes. Operators sometimes conflate the two: "adding a binding felt slow" is a metadata-write observation; "publishing got slower as bindings grew" is a routing-algorithm observation. They have different causes and different fixes.

So the final architecture has to do three things simultaneously: keep each exchange type's routing function scoped to its own binding set (not the whole broker), give operators an escape hatch for messages that don't match anything (§7's alternate exchanges and the mandatory flag), and let routing topologies compose into more than a two-level tree (§7's exchange-to-exchange bindings) — all while keeping the underlying metadata durable and cluster-replicated.

DEEP CONTEXT · THE DIRECTION ROUTING DECISIONS FLOW

Note what never appears as an arrow: nothing routes backward from a queue into an exchange, and nothing lets a consumer influence which exchange a message enters through. Even exchange-to-exchange bindings and alternate exchanges only extend the forward path — a message can hop through several exchanges before landing in a queue, but the graph stays a DAG with the publisher at the root. That invariant is what keeps "which exchange routed this?" a question with a traceable answer even in elaborate topologies.

ARC 08 · INTERNAL IMPLEMENTATION

Four routing functions, in full

This is the section the rest of the chapter has been building toward. Each exchange type below is a real Erlang module implementing the same one-function contract from §1 — route(Exchange, Message) -> [QueueNames] — against data read from the binding table.

(a) Direct — rabbit_exchange_type_direct.erl, O(1)

The direct exchange's bindings live in the rabbit_route table (Mnesia historically, Khepri-backed going forward — chapter 10), keyed so a lookup for {exchange_name, routing_key} is a direct index seek, not a scan — conceptually and in practice the same shape as a hash-table lookup: give it the exact key, it either finds a small already-computed list of destination queues or finds nothing. There is no pattern evaluation step at all — the entire "algorithm" is table lookup plus building the result list. This is why direct is the right default for the common case AMQP was actually designed around: one worker pool, one queue, one exact routing key — a work queue's classic shape.

(b) Fanout — rabbit_exchange_type_fanout.erl, O(N) in bound queues, cheapest per-message CPU

Fanout's route/2 doesn't inspect the routing key at all — it returns the exchange's full, already-materialized list of bound queue names, unconditionally. There is no per-binding comparison of any kind, which is precisely why fanout is the cheapest routing decision of the four: the cost is proportional only to how many queues you've chosen to bind, never to how many bindings exist elsewhere or how cleverly a key is structured. The classic use is a pure broadcast topology — log aggregation, cache invalidation notices — where every consumer wants every message and filtering happens (if at all) client-side after delivery.

(c) The default (nameless) exchange — a special-cased direct exchange

Every vhost has a pre-declared exchange named "" (the empty string) that is, mechanically, a direct exchange with one property no user-created exchange has: every queue is implicitly bound to it at declare time, with a binding key equal to the queue's own name — an implicit binding the broker maintains, not one an application creates or can remove. That single fact is the entire explanation for the pattern every RabbitMQ tutorial teaches without justifying: basic_publish("", "myqueue", msg) works because "" resolves to the default exchange, "myqueue" is the exact routing key, and the default exchange's implicit binding table already contains {"myqueue" -> queue myqueue} before your application ever ran. It is not a broker special-case in the routing algorithm — it's an ordinary direct exchange O(1) lookup against bindings nobody had to write.

(d) Topic — rabbit_exchange_type_topic.erl, the trie, in full

The topic exchange's state is not one table but three, mirroring a classic trie's node/edge/leaf shape, historically Mnesia records and migrating to Khepri (chapter 10 covers the migration mechanics; the algorithm below is identical either way):

  • rabbit_topic_trie_node — one row per trie node: {exchange_name, node_id}, just an existence record for a reachable state in the walk.
  • rabbit_topic_trie_edge — one row per edge: {exchange_name, parent_node_id, word} -> child_node_id, where word is either a literal routing-key word, the atom for *, or the atom for #.
  • rabbit_topic_trie_binding — one row per binding that terminates at a node: {exchange_name, node_id} -> {destination, binding_key}, associating a fully-walked pattern with the queue (or exchange, for e2e bindings) it delivers to.

Matching walks the routing key word by word (split on .), starting at the trie's root node for that exchange, and at each node tries up to three kinds of outgoing edge:

  • Literal edge — if an edge exists for the exact current word, descend into it consuming exactly that one word. Cheapest, most common case.
  • * edge — matches exactly one word, whatever it is; descend into it consuming the current word, no comparison needed beyond "does this edge exist."
  • # edge — matches zero or more words, which is the one case that can't be resolved by looking at just the current word: the matcher must try consuming 0, then 1, then 2, ... words down that edge, exploring every possible split until either a continuation succeeds (reaches a binding with no words left) or every split has been exhausted. This is where backtracking enters: it isn't a bug or a fallback path, it's the mechanical consequence of # being a variable-length match with no way to know the right length in advance.

A routing key can legally satisfy multiple distinct paths through the trie (a literal-heavy binding and a #-heavy binding can both match the same key) — the final result is the union of every destination reachable by every successful path, not just the first one found. State the complexity honestly, because this is the fact every "RabbitMQ is fast" claim glosses over: for binding sets that are mostly literal words and isolated */# edges, the walk is near O(words in the routing key) — a handful of hash-like edge lookups, independent of how many total bindings exist elsewhere in the trie. But when multiple bindings share a prefix and each contributes its own # edge along that shared path, the number of splits the matcher must explore multiplies at each such node — a trie with k chained, overlapping # edges along one path can force exploring on the order of 2k continuations for a single publish. That's not a hypothetical edge case; it's a direct consequence of the same variable-length-match mechanism that makes # useful in the first place, and §15's simulator lets you construct exactly this pathology and watch the walk branch.

(e) Headers — rabbit_exchange_type_headers.erl, O(N) over bindings, slowest by construction

The routing key is ignored entirely (conventionally published as empty). Instead, each binding declares a header spec — a set of key/value pairs plus an x-match argument of all (every declared key must be present in the message headers with a matching value) or any (at least one declared key must match). There is no shared structure across bindings to build an index around — one binding might care about format and region, another about priority alone — so the broker's only option is to walk every binding on the exchange and evaluate its predicate against this message's headers, one binding at a time. This is genuinely the slowest of the four exchange types and the least used in production, for exactly that reason — it's adopted, per §5, only when the filter truly doesn't fit a dot-separated key.

(f) Alternate exchanges and exchange-to-exchange bindings — composing the topology

Two extensions, both RabbitMQ-specific (not in the AMQP spec), turn the two-level exchange→queue model into something closer to an arbitrary routing graph:

  • Alternate exchange (x-alternate-exchange declared on the source exchange): if an exchange's own route/2 returns an empty queue list for a given message, the broker republishes that message to the configured alternate exchange instead of dropping it — and the alternate exchange runs the exact same routing algorithm all over again (it can itself be direct, fanout, topic, or headers, and it can itself have its own alternate exchange, bounded by RabbitMQ's own cycle-guard). This is the mechanism for "catch anything that didn't match a more specific rule" without relying on every publisher setting mandatory and handling Basic.Return itself.
  • Exchange-to-exchange binding: an ordinary binding whose destination is another exchange instead of a queue. When a routing function matches such a binding, the message is routed again through the destination exchange's own algorithm. This turns "publish to one topic exchange, fan out through several downstream exchanges with their own independent binding sets" into a first-class topology — a hub exchange bound onward into several per-tenant or per-region exchanges, each with bindings only its own operators manage.

(g) The mandatory flag and Basic.Return

If, after alternate-exchange resolution, a message still resolves to zero destination queues, the broker's default behavior is to silently discard it — which is often exactly the wrong thing during development or for a misconfigured topology. Setting the mandatory flag on Basic.Publish changes that: an unroutable message is instead sent back to the publishing channel as a Basic.Return, carrying a reply code (312 NO_ROUTE) the application can act on — log it, alert on it, redirect it — rather than losing it invisibly. It costs nothing when the message does route successfully; it's pure insurance against topology drift.

(h) Plugin exchange types — new routing functions, same contract

Because every exchange type is just a module implementing the same route/2 contract, RabbitMQ's plugin mechanism lets community and first-party plugins add entirely new routing functions without touching broker core:

  • consistent-hash exchange (rabbitmq_consistent_hash_exchange) — hashes the routing key (or a configured header) onto a ring of virtual points pre-assigned to bound queues at bind time, giving you deterministic, roughly-even partitioning across a worker pool without any client-side hashing logic — the routing decision is still O(1)-ish (a hash plus a ring lookup), but the destination set is chosen by hash bucket rather than pattern match.
  • random exchange — routes every message to exactly one uniformly-random bound queue, ignoring the key entirely; useful for simple load-balancing across identical workers where consistent-hash's determinism (same key always same queue) isn't a requirement.
  • delayed-message exchange (rabbitmq_delayed_message_exchange) — wraps any of the four base types: on publish, if an x-delay header is present, the message is held internally (backed by Mnesia) and only handed to the wrapped exchange's real route/2 after the delay elapses, giving you "deliver this later" without a separate scheduler service.
WHAT ALL FOUR CORE TYPES SHARE

Every routing decision described in this section executes synchronously, inside the publishing channel's own process, using data already resident in ETS-backed tables — there is no message sent to a separate "router process" and no disk access on the routing hot path. The channel process pays whatever reduction cost the chosen algorithm demands (chapter 1's reduction-counting scheduler bounds how long any one channel can dominate a core doing this), and the result — a list of queue names — is handed off to rabbit_amqqueue:deliver/2 for each destination, which is where chapter 4's process-per-queue material picks up.

ARC 09 · TRADEOFFS

Broker-side content routing, priced against everyone else's answer

No other widely-deployed messaging system offers four independently-optimized, broker-side routing algorithms behind one publish call. Most either push routing decisions to the producer/consumer, or offer one general (and therefore compromise) matching strategy:

Neither bet is wrong — they're optimized for different failure domains, and NATS's subject trie is the closest thing to a direct competitor to the topic exchange's trie specifically.

ARC 10 · PERFORMANCE CHARACTERISTICS

From the module boundaries in §8, several further properties follow directly:

  • Routing never touches disk on the hot path. Binding data is read from ETS-backed in-memory tables regardless of whether the underlying source of truth is Mnesia or Khepri; only binding creation and deletion incurs a metadata commit and cluster-wide replication, not routing itself.
  • Routing runs inside the publishing channel's own reduction budget. A pathological topic match consuming an outsized number of reductions slows that channel, bounded by chapter 1's preemptive, reduction-counted scheduler — it does not stall other channels' publishes on the same node, though it can visibly raise p99 latency for whichever producer happens to be publishing through the expensive pattern.
  • Per-process memory for routing state is dominated by binding count, not message volume. The binding table (and, for topic exchanges, the trie's node/edge/binding rows) grows with how many bindings operators create, entirely independent of how many messages ever flow through — a topology with 50,000 bindings and zero traffic still holds 50,000 bindings' worth of routing state.
  • Message rate ceilings differ meaningfully by exchange type at high binding counts. Direct and fanout sustain their throughput largely independent of binding count (O(1) and O(N)-in-queues respectively, not O(N)-in-bindings); topic degrades gracefully with well-designed patterns but not with pathological ones; headers is, in practice, the first of the four to become a bottleneck as binding count grows into the thousands on one exchange.

ARC 11 · REAL-WORLD PRODUCTION

Where routing choices actually bite in production

Story 1: the official guidance to avoid headers exchanges at scale

RabbitMQ's own documentation and team-authored material have long steered users away from headers exchanges for anything throughput-sensitive, for exactly the reason §8(e) derives: there is no general index to build around an arbitrary key/value predicate, so the exchange falls back to scanning every binding on every publish. It's telling that of the four AMQP-mandated exchange types, headers is the one virtually absent from RabbitMQ tutorials, quickstarts, and the vast majority of production topologies discussed publicly — not because it's hard to use, but because direct, fanout, or topic almost always turn out to fit the actual filtering need more cheaply once teams look for a hierarchical or exact-match encoding of what they were trying to express as properties.

Story 2: wildcard-heavy topic topologies as a recurring performance complaint

Operators running large topic-exchange topologies with many overlapping wildcard subscriptions — market-data and IoT-telemetry-shaped systems especially, where routing keys are naturally deep hierarchies like region.site.device.metric — are a recurring theme in RabbitMQ community discussion and hosting providers' own performance write-ups (CloudAMQP's engineering blog, among others that operate large multi-tenant RabbitMQ fleets, has published general guidance on this): a small number of broad, overlapping # bindings sharing a long common prefix can dominate an exchange's routing cost far out of proportion to their count, exactly as §6 and §8(d) predict from the algorithm itself. The standard fix in that guidance is not "stop using topic exchanges" — it's "prefer narrower, more literal-heavy patterns and push broad catch-alls to a dedicated low-traffic exchange," which is a direct, practical application of understanding the trie's backtracking cost rather than treating routing as a black box.

Story 3: mandatory + Basic.Return as the standard defense against silent message loss

"Where did my message go?" is one of the most common RabbitMQ operational questions, and the answer is frequently a misconfigured or since-removed binding — a queue that used to exist, a routing key typo, a topic pattern that doesn't cover a new hierarchy level. Because the broker's default behavior for an unroutable message is silent discard, RabbitMQ's own publishing guidance (and virtually every serious client library's higher-level wrapper) recommends setting the mandatory flag specifically to convert that silent loss into an observable Basic.Return event applications can alert on — a direct, deliberate application of §8(g) that shows up in essentially every "how to not lose messages" production checklist for RabbitMQ.

Story 4: consistent-hash exchange as the standard way to shard a worker pool

Teams that need partitioned, ordered-per-key processing across a fixed pool of workers — the same shape Kafka's partition-key hashing solves natively — without giving up RabbitMQ's routing model entirely, commonly reach for the rabbitmq_consistent_hash_exchange plugin specifically to get deterministic, roughly-even key-to-queue assignment without hand-rolling client-side hashing logic in every producer. Its existence as a first-party-adjacent plugin (rather than something every team reinvents) is itself evidence that "shard by hash of the key" is common enough a routing need to deserve a dedicated exchange type, sitting alongside — not replacing — the four core types this chapter covers in depth.

First, the direct exchange's entire routing function — genuinely this short, because O(1) lookup needs nothing more:

Erlangrabbit_exchange_type_direct.erl — route/2, simplified
route(#exchange{name = X}, #delivery{message = #basic_message{routing_keys = Routes}}) ->
    %% For each routing key on the message (usually just one), do an
    %% indexed lookup against the route table — no scan, no pattern test.
    lists:append([rabbit_router:match_routing_key(X, [RKey]) || RKey <- Routes]).

%% match_routing_key/2 reads rabbit_route entries whose key already
%% encodes {exchange, routing_key} — the Mnesia/ETS lookup itself IS
%% the O(1) step; there is no further comparison in this function.

Second, the topic exchange's actual trie walk — the recursive shape, with the # branch's variable-length exploration made explicit:

Erlangrabbit_exchange_type_topic.erl — trie walk, simplified but structurally faithful
walk(X, NodeId, Words) ->
    %% Literal edge: consumes exactly Words's head, if an edge for that
    %% exact word exists from this node.
    Literal = case Words of
        [W | Rest] ->
            case trie_child(X, NodeId, W) of
                {ok, Child} -> walk(X, Child, Rest);
                error       -> []
            end;
        [] -> []
    end,

    %% '*' edge: consumes exactly one word, whatever it is.
    Star = case Words of
        [_ | Rest2] ->
            case trie_child(X, NodeId, '*') of
                {ok, SChild} -> walk(X, SChild, Rest2);
                error        -> []
            end;
        [] -> []
    end,

    %% '#' edge: consumes ZERO OR MORE words — this is the branch that
    %% backtracks. Try every possible split point, not just one.
    Hash = case trie_child(X, NodeId, '#') of
        {ok, HChild} ->
            lists:append([walk(X, HChild, lists:nthtail(K, Words))
                          || K <- lists:seq(0, length(Words))]);
            %% ^ K=0 means "consume nothing and try continuing from here";
            %%   K=length(Words) means "the # swallows every remaining word."
            %%   Every K in between is a genuine backtrack attempt.
        error -> []
    end,

    Terminal = case Words of
        [] -> trie_bindings(X, NodeId);  %% no words left: collect bindings here
        _  -> []
    end,

    Literal ++ Star ++ Hash ++ Terminal.

Third, headers matching — the honest O(N) scan, with the x-match semantics made explicit:

Erlangrabbit_exchange_type_headers.erl — route/2, simplified
route(#exchange{name = X}, #delivery{message = #basic_message{content = Content}}) ->
    MsgHeaders = extract_headers(Content),
    Bindings = rabbit_binding:list_for_source(X),  %% every binding, no index — O(N)
    [Dest || #binding{destination = Dest, args = BindArgs} <- Bindings,
             headers_match(BindArgs, MsgHeaders)].

headers_match(BindArgs, MsgHeaders) ->
    MatchAll = get_arg("x-match", BindArgs) =/= "any",  %% default: all
    Keys = [K || {K, _} <- BindArgs, K =/= "x-match"],
    Results = [value_matches(K, BindArgs, MsgHeaders) || K <- Keys],
    case MatchAll of
        true  -> lists:all(fun(R) -> R end, Results);   %% every declared key must match
        false -> lists:any(fun(R) -> R end, Results)    %% at least one must match
    end.
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Restrict the pattern language until the data structure becomes obvious. Topic patterns aren't regex specifically so a trie is a valid, complete index for them — the language was designed backward from the data structure that needed to serve it cheaply, not the other way around. 2. Let the routing function's complexity honestly reflect what it promises. Headers exchange wasn't given a fake index to look faster — its O(N) scan is the truthful cost of a genuinely general predicate match, and hiding that behind a misleading optimization would just move the surprise to production. 3. Keep every exchange type's state in the same replicated metadata store, behind the same lookup contract. Whether it's a flat route table or three trie tables, all of it is read the same way by the publishing channel, which is what let RabbitMQ migrate the underlying store from Mnesia to Khepri (chapter 10) without touching a single exchange type's routing algorithm.
