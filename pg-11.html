POSTGRESQL INTERNALS · CHAPTER 11

Checkpoints &
Crash Recovery

Chapter 10 gave you WAL: every change is durable the instant its record is flushed, long before the data file itself is touched. That leaves two problems completely unsolved. First, if recovery always had to replay WAL from the beginning of time, restart after a crash would take as long as the cluster's entire history. Second, if no WAL segment could ever be deleted, pg_wal would grow forever. Checkpoints are the single mechanism that solves both — and understanding them precisely is what lets you predict recovery time, diagnose "checkpoints are occurring too frequently," and never again delete a backup_label file.

ARC 01 · THE PROBLEM

A durable log is not the same thing as a fast restart

By the end of chapter 10 you accepted a specific bargain: a backend never has to fsync a data page to be durable — it only has to get its XLogRecord flushed. Dirty pages sit in shared_buffers for as long as the buffer manager likes, written back lazily, opportunistically, whenever it's convenient. That bargain is what makes commits cheap. It is also what creates this chapter's problem.

If the server is killed at an arbitrary instruction — kill -9, a power cut, an OOM SIGKILL — every byte of shared_buffers is gone. The only surviving truth is whatever made it to the WAL and whatever made it to the data files before the crash, and those two are wildly out of sync with each other: some committed changes exist only in WAL, some in-memory pages are ahead of what's on disk, and there is no flag anywhere saying which is which. Recovery's job is to replay WAL forward until the data files catch up to what WAL proves was durable. Two questions immediately matter more than anything else in this chapter:

  • Where does replay start? If you don't know, you must start at the very first WAL record the cluster ever wrote — which means recovery time is unbounded and grows with the age of the installation, not with how long ago the crash happened.
  • When can WAL be deleted? Every WAL segment is a real file on real disk. If nothing ever certifies that a segment's changes are no longer needed for recovery, pg_wal grows without limit until the disk fills — a data-corrupting event in its own right, since PostgreSQL cannot durably commit anything once it can't write WAL.

A checkpoint answers both questions with one artifact: a promise, stamped with a single Log Sequence Number. "Every change with an earlier LSN than this is already sitting in the data files. Redo may start here, and WAL before here may be discarded." Everything else in this chapter — the algorithm, the pacing, the pg_control file, the entire redo loop — exists to make that one sentence true, cheaply, without ever stopping the database to say it.

WHY THIS MATTERS FOR THE NEXT 10 CHAPTERS

Every operational fact you know about PostgreSQL crash behavior traces back to this chapter: why restart after a crash sometimes takes seconds and sometimes takes twenty minutes; why max_wal_size is a disk-space knob and a recovery-time knob at once; why physical backups ship a file called backup_label and why deleting it is one of the most quietly destructive things an operator can do. Chapter 12 assumes you have this model cold before it can explain why vacuum's freezing behavior can't simply be "eventually consistent."

ARC 02 · HISTORICAL CONTEXT

From ARIES to checkpoint_completion_target=0.9

PostgreSQL's recovery design is a direct, if simplified, descendant of a single 1992 IBM paper — and almost every subsequent change to it has been about making the checkpoint itself less disruptive, not about changing the fundamental redo contract. DEEP CONTEXT · WHY NO UNDO?

ARIES is a redo/undo algorithm: because it overwrites rows in place, an aborted transaction's changes must be physically rolled back during recovery, using compensation log records to make even the undo pass idempotent. PostgreSQL never overwrites a row in place — MVCC (chapter 5) always creates a new tuple version — so an aborted transaction simply has no committed transaction ID pointing at its tuples; nothing needs to be undone on disk, ever. PostgreSQL borrowed ARIES's redo machinery (the LSN-guarded, idempotent replay you'll study in §8) and discarded the entire undo half, because MVCC already does that job for free. This is the single biggest simplification separating PostgreSQL's recovery from the textbook algorithm it's taught alongside.

ARC 03 · NAIVE SOLUTION

Attempt #1: never checkpoint, just replay everything

Derive it honestly, the way chapter 10 derived WAL. If you already have a durable, ordered log of every change since the cluster was created, the simplest possible recovery algorithm requires no new machinery at all:

pseudocodenaive_recovery.c — the strawman
void RecoverDatabase(void)
{
    /* Start of time. Literally: WAL segment 1, byte 0.
     * No pg_control, no "last checkpoint" bookkeeping needed —
     * there is nothing to look up.                            */
    XLogRecPtr replayFrom = FIRST_WAL_RECORD_EVER_WRITTEN;

    for (record = ReadRecord(replayFrom); record; record = ReadRecord(NULL))
        ApplyRecordToDataFiles(record);  /* every insert, update,
                                                    * delete, index split,
                                                    * since the cluster
                                                    * was initdb'd         */

    OpenForBusiness();
}

/* And the corollary: because we might need ANY WAL segment ever
 * written to recover, none may ever be deleted.                  */
void RemoveOldXlogFiles(void) { /* no-op, forever */ }

This is not a joke architecture — it is correct, and it is the honest baseline every real design must beat. There are no redo-point subtleties to get wrong, no pacing to tune, no pg_control format to keep stable across versions. If you initdb a cluster and crash it five minutes later, this works fine. The naive design fails for exactly the reason chapter 10's iterative server failed: it looks great until the workload accumulates, and then the cost is unbounded.

ARC 04 · WHY IT FAILS

Two unbounded quantities, and neither one is optional

Quantify both failures precisely — they are the two axes every checkpoint tuning decision in this chapter ultimately balances.

  • Recovery time grows with cluster age, not with outage duration. A cluster that has been running for three years and generates 50 GB of WAL/day has accumulated on the order of 54 terabytes of WAL. Replaying all of it — even at a generous, fully-sequential 300 MB/s single-process redo rate — is ~50 hours. A crash that happened ten seconds ago now costs two days of downtime to recover from. This is not a tuning problem to fix later; it makes the naive design operationally unusable past the first few weeks of any real deployment.
  • Disk grows without bound, deterministically. With RemoveOldXlogFiles() a permanent no-op, pg_wal accumulates every segment the cluster has ever written. At 16 MB per segment and any sustained write rate, this is not a slow leak — it is a guaranteed, calendar-predictable disk-full event, and PostgreSQL cannot accept new commits once it cannot allocate a new WAL segment. The naive design turns "the database is durable" into "the database will eventually refuse all writes," on a schedule you can compute from disk size and write rate alone.
THE MATH THAT MOTIVATES EVERYTHING BELOW

Recovery time is not proportional to how long the server was down. It is proportional to WAL volume since the last point recovery is allowed to start from. Shrink that distance and you shrink recovery time, on a schedule you control. That single insight — bound the redo distance — is the entire reason checkpoints exist. Everything from here to §8 is about how to advance that starting point without periodically freezing the whole database to do it.

So we need a mechanism that periodically certifies "recovery may start here" and lets old WAL go. The obvious next question is how you make that certification true — and the honest answer takes three attempts to get right.

ARC 06 · THE PACING PROBLEM

Fuzzy checkpoints are correct immediately — and expensive immediately after

Candidate C from §5 is correct the moment you accept the redo-pointer trick: writers never stop, and recovery still has a valid, provable starting point. But "flush every currently-dirty buffer as fast as the storage will go" has a cost that has nothing to do with correctness: for however long that flush takes, it is competing with every foreground backend for the same disk bandwidth and the same I/O queue depth. On spinning disks this was brutal; on SSDs and network-attached storage it is gentler but still very real, especially against a background of synchronous commits waiting on fsync() to the same device.

PostgreSQL's answer is checkpoint_completion_target: instead of writing dirty buffers as fast as possible, the checkpointer deliberately paces itself to finish at roughly target fraction of the way through the interval until the next checkpoint is expected. The default was 0.5 for most of the project's history and was changed to 0.9 in PostgreSQL 14 — spreading the same total I/O across nearly the entire interval instead of just half of it, on the reasoning that finishing "early" buys you nothing (the next checkpoint can't start any sooner) but finishing in a burst hurts foreground latency measurably.

What actually triggers a checkpoint

A checkpoint is not purely a clock. Four independent triggers exist, and in practice the first two do almost all of the work:

  • checkpoint_timeout (default 5 minutes) — a pure wall-clock ceiling: no more than this long may elapse between checkpoints, regardless of write volume.
  • max_wal_size — a WAL-volume ceiling: once WAL generated since the last checkpoint approaches this size, a checkpoint is forced early, because letting WAL grow further would blow past the disk budget you've allotted it.
  • An explicit CHECKPOINT command — synchronous, runs immediately, mostly used by administrators before a planned shutdown or a filesystem-level backup step.
  • A clean shutdown — writes a XLOG_CHECKPOINT_SHUTDOWN record so the next startup needs no recovery at all.
"CHECKPOINTS ARE OCCURRING TOO FREQUENTLY" — WHAT IT ACTUALLY MEANS

This warning fires specifically when checkpoints are being forced by the WAL-volume trigger (max_wal_size) more often than checkpoint_warning seconds apart (default 30s) — i.e. write volume is outrunning the size budget you configured, not the time budget. The fix that actually addresses the cause is raising max_wal_size (letting more WAL accumulate between checkpoints), possibly paired with more pg_wal disk headroom to hold it. Frequent checkpoints are not merely "extra work" — §10 shows they also inflate WAL volume itself, because full_page_writes re-arms after every single one.

So the real mechanism has two knobs pulling in opposite directions: how often you checkpoint, and how gently each one spreads its I/O. Both matter, and §15's simulator lets you feel both at once. First, meet the whole architecture these knobs live inside.

Every one of these pieces exists to protect one sentence: a page is never allowed to reach disk before the WAL record describing the change that produced it. FlushBuffer() enforces this directly — it calls XLogFlush() up to the buffer's LSN before the write, every time. The REDO pointer, the sorted buffer scan, the fsync queue, and pg_control are all just bookkeeping built on top of that one ordering rule. §8 shows exactly where in the code this happens.

ARC 08 · INTERNAL IMPLEMENTATION

CreateCheckPoint(), the redo loop, and the LSN guard

Now the mechanism at the level you'd need to patch it. Three pieces: (a) the checkpoint algorithm step by step, (b) how its I/O is paced, and (c) the recovery redo loop that consumes what the checkpoint produced.

(a) CreateCheckPoint(), step by step

Step through the real sequence from src/backend/access/transam/xlog.c, simplified but faithful. Step 2 is the one subtlety worth re-reading twice.

CreateCheckPoint() → CheckPointGuts()STEP-BY-STEP
Cxlog.c — CreateCheckPoint(), simplified
void
CreateCheckPoint(int flags)
{
    LWLockAcquire(CheckpointLock, LW_EXCLUSIVE);

    /* THE SUBTLE STEP. Captured BEFORE a single buffer is
     * flushed. WAL-before-data ordering (FlushBuffer() never
     * writes a page whose LSN hasn't reached disk yet) means
     * every buffer this checkpoint is about to write is already
     * covered by WAL at or after this exact point.             */
    checkPoint.redo = GetInsertRecPtr();

    LogCheckpointStart(flags, false);

    /* Flush every dirty buffer, sorted for locality, paced by
     * checkpoint_completion_target. See CheckPointBuffers().   */
    CheckPointGuts(checkPoint.redo, flags);

    /* Every file touched above has a pending fsync request in
     * the checkpointer's queue. Drain it now — this is where
     * durability for THIS checkpoint's writes actually happens. */
    ProcessSyncRequests();

    /* Only now write the checkpoint record. Its own LSN is NOT
     * checkPoint.redo — redo is a FIELD inside it, pointing
     * backward to step 1.                                       */
    recptr = XLogInsert(RM_XLOG_ID, XLOG_CHECKPOINT_ONLINE);
    XLogFlush(recptr);

    /* Persist the new frontier. Only after this line is a crash
     * recoverable from THIS checkpoint instead of the previous
     * one.                                                       */
    UpdateControlFile();

    /* WAL strictly before checkPoint.redo can never be needed
     * again.                                                     */
    RemoveOldXlogFiles(checkPoint.redo, ...);

    LWLockRelease(CheckpointLock);
}

(b) Pacing: CheckpointWriteDelay()

BufferSync() (in src/backend/storage/buffer/bufmgr.c) tags every currently-dirty buffer BM_CHECKPOINT_NEEDED — so a buffer dirtied after the scan starts is correctly left for the next checkpoint, not confused with this one — sorts the tagged list by tablespace/relfilenode/block (turning a scan of scattered dirty pages into long, mostly-sequential per-file runs), and writes them out one at a time. Between writes, CheckpointWriteDelay() compares how far through the buffer list it is against how far through the paced interval it should be, and sleeps only when it's ahead of schedule. WHY IDEMPOTENCE IS NOT OPTIONAL

Recovery may replay a record whose effect is already on the page — for two completely ordinary reasons, not just corruption scenarios. First, the redo point is conservative by construction: it's captured before the flush, so some of the records after it describe buffers that the checkpoint (or the background writer, opportunistically) already wrote out before the crash happened. Second, recovery itself can crash and restart — the second attempt replays from the same starting point and must re-apply records the first attempt already finished. Every redo function therefore follows the same rule: if (PageGetLSN(page) >= record's LSN) skip — the change is already durably reflected, and applying it again would corrupt the page or double-apply the delta. This single guard, checked by every resource manager's rm_redo, is what makes "redo from the same point twice" a safe operation instead of a corruption bug.

FULL-PAGE WRITES SIDESTEP THE PROBLEM ENTIRELY

If a record carries a full-page image — captured the first time a page is touched after each checkpoint, specifically to survive a torn page (a partial 8 KB write split across a crash, at the OS or storage layer) — redo doesn't even check the page's LSN. A torn page's own header, including its LSN, might itself be garbage; the only safe move is to reinstall the entire page unconditionally from the WAL-embedded image. This is also precisely why frequent checkpoints inflate WAL volume: every checkpoint re-arms "first write since redo," forcing the next touch to every hot page to pay for a full image again.

End-of-WAL detection deserves its own sentence because it surprises people: when XLogReadRecord() hits a record whose header doesn't validate — usually because it's reading all-zero bytes that were never written — that is not corruption. It is the expected, normal shape of the end of the log, and recovery simply stops there, treating that position as the new insertion point.

ARC 09 · TRADEOFFS

Every log-structured system reinvents this checkpoint

The "advance a durable frontier, discard what's behind it" shape recurs everywhere logs meet storage. What differs is what triggers the advance and what it costs to compute:

Read this as proof by exhaustion, the way §9 of chapter 1 read the process-model table: every system pays for "recovery starts near now" somewhere — either in WAL volume (PostgreSQL's full-page images), in a hard ceiling that forces emergency work under load (InnoDB's redo log size), or in giving up in-place updates entirely (LSM engines). PostgreSQL's choice — redo-only recovery, fuzzy checkpoints, tunable pacing — is the one that keeps ordinary heap and btree access patterns simple, at the cost of a WAL-volume tax you can see directly in pg_stat_bgwriter and tune directly with checkpoint_completion_target.

ARC 10 · PERFORMANCE CHARACTERISTICS

Recovery time and checkpoint cost, from first principles

Two Big-O statements you can derive without benchmarking anything:

  • Recovery time is O(WAL bytes since the last completed checkpoint's redo pointer) — not O(downtime), not O(database size). A 50 TB database that crashed 30 seconds after its last checkpoint recovers in roughly the time to replay 30 seconds of WAL. A 50 GB database that hasn't checkpointed in an hour under heavy write load can recover slower than the giant, freshly-checkpointed one.
  • Checkpoint wall-clock cost is O(dirty buffers at scan time) for the write, and O(distinct files touched) for fsyncs — not O(shared_buffers). A mostly-read workload with a huge buffer pool but few dirty pages checkpoints almost instantly; a small buffer pool under constant heavy writes churns through its entire contents every checkpoint.

Two second-order effects worth internalizing: the initial buffer scan touches every BufferDesc in the pool (~64 bytes each) linearly — at 64 GB of shared_buffers and 8 KB pages that's roughly 8 million descriptors, a single sequential sweep run by one process (the checkpointer), so it doesn't thrash other backends' CPU caches directly but does compete for memory bandwidth. And sorting dirty buffers by tablespace/relfilenode/block before writing converts what would otherwise be effectively random 8 KB writes scattered across the whole pool into long runs per file — a bigger win on rotational media, but still meaningfully reduces the number of distinct fsync targets (and OS write-back queue entries) even on SSD and network storage.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: "checkpoints are occurring too frequently"

A batch ingestion job starts loading years of historical data at high throughput. Within minutes, the logs fill with LOG: checkpoints are occurring too frequently (14 seconds apart) followed by HINT: Consider increasing the configuration parameter "max_wal_size". The write volume is blowing past the WAL-size trigger far faster than checkpoint_timeout would ever have fired on its own — every checkpoint completes only to immediately re-trigger, each one re-arming full-page writes on the same hot pages the batch job keeps touching, multiplying WAL volume on top of an already WAL-heavy workload. Fix: raise max_wal_size (and provision the pg_wal disk headroom to match it) so checkpoints space out to something closer to checkpoint_timeout's cadence during bulk operations; some teams additionally raise it only for the duration of known bulk-load windows.

Incident 2: an hour of recovery nobody budgeted for

A team running a write-heavy analytics ingestion pipeline set checkpoint_timeout to 60 minutes and a very large max_wal_size specifically to minimize steady-state I/O overhead — a reasonable-looking choice under §10's model, if you only look at the I/O curve. A host-level fault killed the primary roughly 50 minutes into a checkpoint interval. Recovery had to replay 50 minutes of a high-volume WAL stream, and the contractual failover SLA was 5 minutes. Root cause: the team tuned for steady-state throughput and never computed the other half of §10's tradeoff — worst-case WAL-since-redo at their write rate. Fix: derive max_wal_size/checkpoint_timeout from the RTO backward (§12 walks the exact calculation), then validate by actually crashing a non-production replica under peak load and timing the real replay.

Incident 3: deleting backup_label "to fix a stuck recovery"

An operator restores a physical base backup, PostgreSQL starts up and reports it is in recovery, and — reading it as stuck rather than working as designed — the operator deletes backup_label from the data directory to "let it start normally." The server does start, quickly, and appears healthy. Weeks later, checksum failures and unreadable index blocks start surfacing, seemingly at random. Root cause: without backup_label, the startup process falls back to trusting pg_control's own last-checkpoint pointer — but that file was copied as part of the backup and can describe a checkpoint that completed after the backup started copying files, which is later than the true point recovery needed to start from. Recovery silently skipped WAL the backup actually required to fix up pages that were mid-write when they were copied — classic torn-page corruption, invisible until the affected block is actually read. Fix: never manually delete backup_label; if recovery genuinely appears stuck, diagnose the actual redo target and WAL availability instead of removing the file that makes the restore correct.

The dirty-buffer scan and its pacing, simplified from bufmgr.c:

Cbufmgr.c — BufferSync() + CheckpointWriteDelay()
static void
BufferSync(int flags)
{
    /* Snapshot which buffers are dirty NOW. Tag them so a
     * buffer dirtied by a backend AFTER this scan starts is
     * left for the NEXT checkpoint, not confused with this one. */
    for (buf_id = 0; buf_id < NBuffers; buf_id++)
        if (buf_state & BM_DIRTY)
        {
            buf_state |= BM_CHECKPOINT_NEEDED;
            CkptBufferIds[num_to_scan++] = (buf, tsId, relNode, blockNum);
        }

    /* Sort by tablespace/relfilenode/block: turns a scattered
     * scan into long per-file runs — locality, not randomness.  */
    qsort(CkptBufferIds, num_to_scan, sizeof(CkptSortItem),
          ckpt_buforder_comparator);

    for (i = 0; i < num_to_scan; i++)
    {
        SyncOneBuffer(CkptBufferIds[i].buf_id, ...);
        CheckpointWriteDelay(flags, (double) i / num_to_scan);
    }
}

static void
CheckpointWriteDelay(int flags, double progress)
{
    /* progress: fraction of THIS checkpoint's buffer list done.
     * Compare against fraction of the PACED INTERVAL elapsed
     * (elapsed_time / (checkpoint_timeout * completion_target)).
     * Behind schedule → write immediately, no sleep. Ahead →
     * sleep a little. That comparison IS the pacing algorithm.  */
    if (progress < elapsed_fraction_of_target)
        return;
    pg_usleep(...);
}

The recovery redo loop, simplified from xlogrecovery.c, and the LSN guard every redo function goes through via xlogutils.c:

Cxlogrecovery.c + xlogutils.c — redo loop and the LSN guard
void
PerformWalRecovery(void)
{
    record = ReadRecord(xlogreader, InvalidXLogRecPtr, LOG, false);

    while (record != NULL)
    {
        RmgrTable[record->xl_rmid].rm_redo(xlogreader);
        LastRec = ReadPtr;
        record = ReadRecord(xlogreader, InvalidXLogRecPtr, LOG, false);
    }
    /* record == NULL is NOT corruption — it's an unparseable
     * header, exactly what unwritten WAL looks like. THIS is
     * end of log.                                               */
    EndOfLog = LastRec;
}

XLogRedoAction
XLogReadBufferForRedo(XLogReaderState *record, uint8 block_id, Buffer *buf)
{
    if (XLogRecHasBlockImage(record, block_id))
    {
        /* torn page's own LSN can't be trusted — don't even
         * check it, just reinstall the full image.              */
        *buf = RestoreBlockImage(record, block_id);
        return BLK_RESTORED;
    }

    *buf = ReadBufferForRedo(record, block_id);
    page = BufferGetPage(*buf);

    if (PageGetLSN(page) >= record->EndRecPtr)
        return BLK_DONE;         /* already durable — SKIP */

    return BLK_NEEDS_REDO;      /* apply the delta */
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Push the fsync decision out of the backend. A backend that writes a dirty buffer never calls fsync() itself — it registers a request with the checkpointer, which de-duplicates requests against the same file from many backends into one fsync() call. This is the same "flags, not work, in the hot path" instinct chapter 1's signal handlers used, applied to I/O instead of signals. 2. Make the correctness argument a pointer comparison, not a distributed protocol. PageGetLSN(page) >= record's LSN is a single integer comparison that replaces an entire class of "did this already happen?" coordination problems — because LSNs are monotonically increasing and every page remembers the last one applied to it. 3. Discard undo entirely rather than port ARIES faithfully. The team could have implemented compensation log records and a real undo pass; instead they leaned on MVCC (already required for concurrency) to make aborted-transaction cleanup a non-problem for recovery. Simpler code, fewer bugs, at the cost of relying on vacuum (chapter 12) to eventually reclaim what undo would have removed immediately.

EXPERIMENTS TO RUN

1. Drag completion_target to 0.1 and watch the I/O chart spike into bursts; drag it to 0.9 and watch the same total writes smooth into a trickle. 2. Crash mid-checkpoint (watch the buffer grid for blue "flushing" cells, then hit crash) — notice recovery still starts from the previous completed checkpoint, not the interrupted one. 3. Step through redo and find a SKIPPED record — that's a page the background writer or a completed checkpoint already flushed before the crash. 4. Slide checkpoint frequency to its most infrequent setting, run the workload a while, then crash — watch "worst-case recovery" climb and count how many more redo steps it takes to reach the end of WAL.
