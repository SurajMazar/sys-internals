RABBITMQ INTERNALS · CHAPTER 10

Clustering, Federation
& Shovel

"Make two brokers talk to each other" is not one problem — it is at least three, and RabbitMQ ships a dedicated, purpose-built mechanism for each. Clustering turns several nodes into one logical broker over Erlang's own distribution protocol, replicating metadata but never message content. Federation links independently-administered brokers across a WAN without merging them into anything. Shovel is a dumb, reliable pump for moving messages from one place to another and forgetting about it. This chapter derives all three from the failure modes of the naive alternative, then goes deep on the two hardest internal questions: what happens to your cluster's metadata during a network partition, and why a classic queue's home node is a fact about your cluster you cannot outsource to a load balancer.

ARC 01 · THE PROBLEM

"Make brokers work together" is three unrelated problems wearing one name

A single RabbitMQ node is both a capacity ceiling and a single point of failure: every classic queue, every channel, every connection is an Erlang process living in exactly one BEAM VM on exactly one machine, and if that machine dies, every process on it dies with it (chapter 4 covered the durable-recovery half of that story; this chapter covers the multi-node half). The instinctive fix is "run more than one broker" — but that phrase hides at least three genuinely different requirements, each with a different correct answer, and conflating them is the single most common RabbitMQ operational mistake this course covers.

Pull the three apart explicitly, because the rest of this chapter is organized around exactly this separation:

  • Requirement 1 — one logical broker that survives a machine failure. Your application should see one set of vhosts, one set of users and permissions, one set of exchanges and queues — a single broker's worth of address space — but that address space needs to keep serving traffic if any one machine hosting it goes down. This is a high-availability problem, scoped to one administrative domain, one deployment, usually one datacenter or availability zone.
  • Requirement 2 — specific data flowing between independently-run brokers. Two teams, two regions, or two companies each run their own RabbitMQ, with their own users, their own upgrade schedules, their own on-call rotations — and some subset of messages published in one needs to show up in the other. Neither side wants to be pulled into the other's administrative domain, and the network between them is a WAN: slower, less reliable, sometimes crossing the public internet.
  • Requirement 3 — move messages from A to B, once or continuously, then stop caring. A migration between RabbitMQ versions, decommissioning a queue, or moving a workload's messages from an old cluster to a new one. There is no ongoing topological relationship to maintain afterward — you just need every message currently sitting in a source location to end up in a destination location, reliably, and possibly never run again once it's done.

RabbitMQ ships one mechanism engineered for each: clustering for requirement 1, the federation plugin for requirement 2, and the Shovel plugin for requirement 3. All three move bytes between Erlang nodes, and all three get called "clustering" by engineers who haven't yet been burned by picking the wrong one — the most expensive version of that mistake is running an actual RabbitMQ cluster across two AWS regions because someone wanted requirement 2 and reached for the requirement-1 tool. §5 derives why that specific mistake fails, in enough mechanical detail that you'll recognize it in a design review.

THE ONE FACT THAT UNIFIES THIS CHAPTER

Clustering answers "how do many nodes agree on what exists" (exchanges, bindings, users, policies, queue names) — it is fundamentally a metadata replication problem. It does not, by itself, answer "how do many nodes agree on what a queue's messages are" — that's a data replication problem, solved separately by quorum queues and streams (chapters 6–7), which happen to run on top of a cluster but are not the same mechanism as clustering itself. Keeping those two words — metadata and data — separate in your head is the single highest-leverage idea in this chapter, and it's where §4 starts.

DEEP CONTEXT · CLUSTERING WAS NEARLY FREE, AND THAT WAS THE TRAP

Because Erlang/OTP ships distributed node-to-node messaging and Mnesia, a distributed database, as standard library features (chapter 1 covers why RabbitMQ is built on Erlang at all), joining RabbitMQ nodes into a cluster in the earliest releases required almost no bespoke engineering — a few lines wiring Mnesia table replication to RabbitMQ's own metadata records. That's a gift for a young project, but it meant RabbitMQ inherited Mnesia's actual consistency model — one built for 1990s telecom systems that assumed partitions were rare and operators were watching — rather than a model designed from scratch for the partition-heavy reality of cloud networking. The entire Mnesia→Khepri migration this chapter covers in depth is RabbitMQ paying down that original, mostly-invisible design debt two decades later.

ARC 03 · NAIVE SOLUTION

Attempt #1: independent standalone brokers behind a load balancer

Derive it the way most teams actually arrive here: you already run one RabbitMQ node, it works, and now you need more capacity or some failure tolerance. The simplest thing that could possibly work, if you've never read RabbitMQ's clustering documentation, is to stand up two more completely standalone nodes — no shared cookie, no rabbitmqctl join_cluster, nothing — put a TCP load balancer or round-robin DNS entry in front of all three, and declare the same exchanges and queues by name on each one via your application's startup code.

pseudocodenaive_ha.py — the strawman, annotated
class OrderService:
    def __init__(self):
        # the LB VIP resolves to node1, node2, or node3 — no client control
        # over which one a given TCP connection actually lands on
        self.conn = amqp.connect("amqp://orders-lb.internal:5672")
        ch = self.conn.channel()
        # every node runs this exact line at startup — three INDEPENDENT
        # brokers each end up with their own "orders" queue object,
        # identical in name, unrelated in content
        ch.queue_declare("orders", durable=True)

    def publish_order(self, order):
        # whichever node THIS connection happened to land on
        # receives the message into ITS OWN "orders" queue only
        self.conn.channel().basic_publish(exchange="", routing_key="orders", body=order)

This isn't a strawman built to be knocked down for sport — it gets one thing half-right: three nodes really can absorb more total connections than one, and a load balancer really does route around a node that stops answering health checks. What it gets catastrophically wrong is assuming that "same queue name" means "same queue" across three completely separate broker processes that have never exchanged a byte of metadata with each other. ARC 04 · WHY IT FAILS

The math: 1/N visibility, zero shared identity, and a silent SPOF per node

Formalize what the deck just showed. With N independent, unclustered nodes behind a load balancer that distributes connections roughly uniformly, a producer and a consumer that each open a fresh connection land on the same node with probability 1/N — for three nodes, roughly a third of the time. The other two-thirds of the time, a message published on node B sits in node B's private "orders" queue forever, because no mechanism told node A or node C that it exists.

  • Metadata isn't shared, so "the same queue" is a fiction. Three queue_declare calls against three unclustered nodes create three distinct rabbit_amqqueue_process instances with no relationship whatsoever — same name, same durability flag, completely independent backing stores. There is no broker-side concept linking them; the illusion of "one orders queue" exists only in your team's head.
  • Administrative state diverges immediately. A user created via node A's management UI, a policy applied via node B's CLI, a permission grant on node C — none of it propagates. Within a day, three "the same" brokers have three different answers to "who is allowed to publish to this vhost."
  • A node failure is unconditional data loss for whatever that node was holding, with nothing automatically stepping in — there's no second copy anywhere, because nothing ever coordinated a copy. The load balancer routing around a dead node doesn't recover the dead node's messages; it just stops making the problem worse for new connections.
  • Scaling reads and writes doesn't actually happen — work isn't shared, it's randomly and invisibly partitioned across N unrelated queues that each need independent monitoring, independent capacity planning, and independent alerting, multiplying operational burden by N instead of dividing load by N.
THE NUMBERS

At N=3 unclustered nodes behind a naive round-robin LB, roughly 67% of publish/consume pairs miss each other entirely under uniform random connection placement — not as a rare edge case, but as the steady-state behavior of the architecture. Teams that hit this in production usually don't see it as "messages are disappearing" at first; they see it as "our consumer is randomly slow to pick up new orders," because a third of the time it does work, by luck, and two-thirds of the time nothing is listening to the queue a given message actually landed in.

So the fix needs, at minimum, a way for nodes to agree on what exists — vhosts, exchanges, bindings, users, policies, and which node is home to which queue — without every team member having to manually keep three (or thirty) management consoles in sync. §5 walks through the two real candidates for building that agreement, and why full clustering is the answer for requirement 1 specifically, not for all three requirements from §1.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Shared metadata, yes — but replicated how, and does every problem need it?

Candidate A: one broker process, shared disk underneath (the "SAN failover" shape)

Point every application at one node, but put its data directory on shared, replicated network storage, and keep a cold standby node ready to mount that same storage and start the broker process if the primary dies. This looks appealing because it sidesteps metadata-replication entirely — there's only ever one logical copy of the data on disk. But it doesn't solve the actual problem: a live BEAM VM holds enormous amounts of state in process memory (every channel, every queue's in-memory message buffer, every binding-table ETS entry) that isn't on disk at any given instant, and Mnesia/queue-index files are not designed for two separate BEAM instances to safely touch concurrently — a botched failover risks corrupting the very files the standby needs to recover from. Rejected: trades a process-level SPOF for a scarier, slower, storage-level one, and buys no actual concurrency.

Candidate B: full Erlang-distribution clustering with metadata replicated to every node ✓

Instead of sharing disk, share the fact of what exists: every node runs its own full broker process, joins the others over Erlang's built-in distribution protocol (the same node-to-node messaging chapter 1 introduced, now used between machines instead of just between local processes), and a designated metadata store — historically Mnesia, now migrating to Khepri — replicates vhosts, exchanges, bindings, users, permissions, policies, and queue definitions to every member. Any node can now answer "what queues exist and who can publish to them" identically. This is accepted as the fix for §1's requirement 1, and only requirement 1.

THE CRUCIAL CONSEQUENCE, STATED EARLY BECAUSE EVERYTHING ELSE DEPENDS ON IT

Clustering replicates metadata — the shape of your broker — to every node. It does not replicate message data as part of the clustering mechanism itself. A classic queue, once declared, has its content living in exactly one node's process and one node's disk files — clustering just means every other node knows that queue exists and where, and can transparently forward operations to it. That single fact — metadata everywhere, message bodies in exactly one place unless you opt into quorum queues or streams — is the mechanical root of nearly every "clustering surprised me" incident this course's production stories draw from, and §8 derives exactly why RabbitMQ was built this way rather than replicating everything.

ARC 06 · WHY THAT STILL COSTS

The bill for one logical broker: latency, blast radius, and Mnesia's fragility

Clustering fixes §4's metadata-divergence problem, and the cost of that fix is not free — understanding it precisely is what lets you draw the line between "cluster this" and "federate or shovel this instead."

  • Metadata replication is synchronous and cluster-wide, so it wants a low-latency LAN. Declaring a queue, adding a user, or setting a policy is a metadata write that (under both Mnesia and its successor Khepri) needs acknowledgment from other nodes before it's considered durable and visible — over a WAN link with 80–150ms of round-trip latency, every such operation pays that latency, repeatedly, and under load the pile-up of pending metadata transactions can stall unrelated operations cluster-wide. §8 derives exactly why this pushes clustering toward "a handful of nodes in one datacenter," never "one node per continent."
  • A full mesh is a real network and security requirement, not a config checkbox. Every node needs a direct TCP connection to every other node's Erlang distribution port, authenticated by a shared secret (the Erlang cookie) — that's O(n²) connections to provision, firewall, and monitor, and a leaked cookie is effectively a master key to join hostile processes to your cluster as a trusted peer.
  • Clustering alone does not give you message-level durability across a node loss — the crucial consequence from §5 means a node crash still loses whatever classic-queue content lived only on that node. Real message-level HA requires layering quorum queues or streams (chapters 6–7) on top of the cluster, which is a separate design decision with its own costs.
  • Mnesia's partition behavior was never built around consensus — it has no concept of "majority," no leader election, and no principled way to decide which side of a split network is allowed to keep writing. That gap is exactly what the network-partition and Khepri material in §8 is about, and it's the single biggest reason clustering has a genuinely bad reputation among engineers who ran it through the 2010s.
THE HONEST TRADE

None of this argues against clustering — it's the correct, purpose-built answer to §1's requirement 1, and a well-run 3-to-7-node cluster on a fast LAN with quorum queues for anything that must survive a node loss is exactly what most teams should run. The point is narrower: clustering was never meant to solve requirements 2 and 3 from §1, and every one of the costs above gets sharply worse the more you try to stretch it across a WAN or an administrative boundary it wasn't designed for. §7 lays out the final shape of all three mechanisms side by side, so the boundary is visible at a glance instead of learned the hard way.

DEEP CONTEXT · WHY FEDERATION AND SHOVEL BOTH SPEAK PLAIN AMQP

Every arrow crossing the outer boundary in the diagram above is an ordinary AMQP 0-9-1 client connection — the exact same connection type your application code opens. That's deliberate: it means a federation link or a Shovel worker needs nothing from the far side except valid AMQP credentials and network reachability, the same bar any external client must clear. Contrast that with the inner boundary, where a node needs the Erlang distribution cookie — a much stronger, much more dangerous form of trust, appropriate only within a single administrative domain that fully trusts every member to run arbitrary code against every other member's BEAM VM.

ARC 08 · INTERNAL IMPLEMENTATION

Erlang distribution, the metadata store, the proxy hop, and the partition problem

(a) Erlang distribution: the substrate every cluster mechanism rides on

When you run rabbitmqctl join_cluster rabbit@node1, RabbitMQ isn't inventing a networking layer — it's asking the underlying BEAM VM to become a member of a distributed Erlang system, the exact mechanism chapter 1 introduced for local process messaging, now extended across machines. Three pieces make that work: epmd (the Erlang Port Mapper Daemon, listening on TCP 4369 on every node) maps a node name like rabbit@node1 to whatever ephemeral distribution port that node's BEAM is actually listening on; the Erlang cookie — a shared secret, identical on every intended member, normally found in /var/lib/rabbitmq/.erlang.cookie — is exchanged during connection setup and is the only authentication distributed Erlang performs, so a leaked cookie lets an attacker's node join as a fully-trusted peer; and peer discovery (rabbit_peer_discovery, with pluggable backends — a static node list, DNS, AWS, Kubernetes, Consul, etcd) is how a booting node learns which existing members to dial.

Once connected, every node maintains a direct TCP link to every other node — a genuine full mesh, not a ring or a gossip overlay — because RabbitMQ's metadata store needs every replica to be directly reachable for its own consistency protocol (Mnesia's transaction manager historically required this; Khepri's Raft protocol technically only needs a leader-to-majority path, but RabbitMQ still establishes full mesh distribution links regardless, since all inter-node traffic — not just metadata — rides these same links, including the cross-node message deliveries in part (c) below).

(b) Metadata replication: what actually gets copied, and to how many nodes

The records replicated cluster-wide are specifically: virtual hosts, exchange and binding definitions, users and permissions, runtime parameters and policies, and queue metadata — name, durability flag, arguments, and (crucially) which node is that queue's home. None of this is your message bodies. Historically these lived in Mnesia tables (rabbit_vhost, rabbit_exchange, rabbit_durable_route, rabbit_user, rabbit_policy, and more), each configured as ram_copies or disc_copies per node; writes went through Mnesia's own distributed transaction manager, which requires every node holding a copy of the affected table to participate and agree — a protocol built for "everyone is reachable, partitions are rare," not for "assume the network fails routinely," which is exactly the assumption a cloud-era system needs. §8(e) below covers Khepri, the fix.

(c) Where a classic queue actually lives, and the hop most people don't know they pay

When a client declares a classic queue, RabbitMQ picks exactly one node to be its home — by default, the node the declaring channel's connection happens to be on (so whichever node your client's TCP connection landed on decides where a brand-new queue's process gets spawned), or, for classic queues specifically, an operator-configured queue_master_locator policy (client-local — the default behavior just described; min-masters — place it on whichever node currently hosts the fewest queue processes, for basic load spreading; random). Once chosen, rabbit_amqqueue_process spawns on that node and never moves for the rest of that queue's life, short of the node itself going away or an operator's manual intervention.

Every subsequent operation against that queue from any other node in the cluster is now a message send across the Erlang distribution link from part (a). Because Erlang pids are location transparent, the code inside rabbit_channel that calls rabbit_amqqueue:deliver(QPid, Content) is textually identical whether QPid is local or remote — but physically, a remote deliver serializes the message and its routing decision over a TCP socket to another machine, adding a real network round trip that a same-node delivery never pays. This is the extra hop most engineers don't know they're paying: your load balancer or client library's connection strategy can silently place a consumer's channel on a different node than every queue it's consuming from, and every single delivery now crosses the cluster network it wouldn't have to if the client had simply connected to that queue's home node directly.

(d) Detecting a partition: net_ticktime and the heartbeat that decides "is that node still there?"

A network partition isn't announced — it has to be inferred, and Erlang distribution infers it the same way TCP keepalives infer a dead peer: with periodic heartbeat "ticks" between connected nodes, governed by the net_ticktime setting (default: 60 seconds). Roughly every quarter of that interval, each node sends a tick to every peer it's connected to; if a peer produces no traffic — ticks or otherwise — for approximately one full net_ticktime window, distributed Erlang gives up and tears the connection down, and rabbit_node_monitor on the surviving nodes reacts to that nodedown event by invoking whatever cluster_partition_handling strategy is configured. Set net_ticktime too low and ordinary GC pauses or transient network jitter get misdiagnosed as a full node failure — a false positive that triggers unnecessary pausing or autoheal restarts; set it too high and a genuine partition goes undetected for uncomfortably long, during which both sides may already be diverging under a permissive handling strategy.

(e) The four partition-handling strategies, mechanically

Once a partition is detected, cluster_partition_handling decides what each side does next. §15's simulator lets you play all four out live; here is what each one mechanically does:

  • ignore (the historical default) — every side keeps running exactly as before, fully accepting new connections, declares, and publishes. If both sides accept incompatible metadata writes (two different users both named the same, two conflicting policies) during the split, nothing detects or prevents that — the divergence is only discovered when the network heals and Mnesia notices two histories that don't agree, at which point an operator typically has to manually pick a winner, often via rabbitmqctl forget_cluster_node on the loser, and restart it to rejoin clean.
  • pause_minority — every node that computes itself to be on the smaller side of the split (by counting how many previously-known cluster members it can still reach) pauses itself: it stops accepting client connections and effectively goes offline until it can rejoin a majority. The majority side keeps running untouched. This only produces a well-defined answer when the total node count is odd — §8(f) derives why.
  • autoheal — instead of pausing, the cluster picks a single winning partition (by a deterministic rule — the side with more client connections at the moment of detection, ties broken by node name) and every node on the losing side is restarted by rabbit_autoheal, rejoining fresh and empty. Any queue that was homed on a losing node, and any in-memory state that wasn't durable, is gone — the losing side doesn't just pause, it loses transient state and comes back clean.
  • pause_if_all_down — a more surgical variant: a node pauses only if a specifically configured list of "witness" nodes are all simultaneously unreachable, regardless of whether it's technically in a majority or minority by raw count. It takes a node list plus a fallback strategy (autoheal or ignore) for once those nodes are confirmed reachable again — useful when you know in advance which nodes matter most for deciding "is this really a split."

(f) Why pause_minority needs an odd node count, derived

"Minority" only has a well-defined meaning when a strict majority is possible. With 3 nodes split 2-1, the side with 2 is an unambiguous majority — it keeps running, the lone node pauses, and the cluster stays available for clients that can reach the majority. With 4 nodes split 2-2, neither side has more than half — both sides compute themselves as "not a majority," and under pause_minority's literal rule, both pause, producing a full outage where a well-chosen 3-node cluster would have stayed up. Odd node counts (3, 5, 7…) guarantee every possible even split still leaves one side with a strict majority; even counts introduce a tie scenario that defeats the entire mechanism. This is precisely why RabbitMQ's own operational guidance recommends odd-sized clusters, and it's the exact scenario §15's two-node toggle lets you trigger and watch fail live.

THE TWO-NODE CLUSTER IS FUNDAMENTALLY UNSAFE

A 2-node cluster split by any network partition leaves each side with exactly one node — 1 out of 2, which is precisely 50%, neither a majority nor a minority by any meaningful definition. Under pause_minority, both nodes conclude they lack a majority and both pause: the mechanism built specifically to keep a majority serving traffic instead takes the entire cluster offline, which is worse than not clustering at all. Under ignore, both nodes keep running independently and can diverge with nothing stopping them — also worse. There is no configuration of cluster_partition_handling that makes a 2-node cluster behave safely under a network partition; the only real fixes are running an odd number of full members (3+) or introducing a witness/arbitrator node that never itself holds queues but participates in majority counting.

Systems that skip the second half of that pair — Redis Streams among them — simply push the problem onto application teams, who end up reinventing something Shovel-shaped by hand.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

From the mechanics in §8 alone, several performance properties follow directly:

  • Full-mesh connection count is O(n²). An n-node cluster maintains n(n-1)/2 live distribution links, each carrying periodic heartbeat ticks even when totally idle — this is exactly why RabbitMQ's own guidance treats clustering as appropriate for a handful to a few dozen nodes, not hundreds; the background chatter alone grows quadratically.
  • Metadata size is bounded by the smallest node, not summed across nodes — because every vhost, exchange, binding, user, and policy record is fully replicated to every member, cluster-wide metadata capacity is a copy problem, not a sharding problem. Adding nodes buys you failure tolerance and connection capacity, never more metadata capacity.
  • Metadata writes pay a majority-durable-commit cost; message publishes to an already-declared queue do not. Declaring a queue, adding a binding, or setting a policy under Khepri is a Raft log append that needs a majority of members to persist it before it's committed — real, per-operation latency. Publishing a message to a queue that already exists never touches Khepri or Mnesia at all; only topology changes pay the metadata-consensus cost, not steady-state traffic.
  • A cross-node proxy hop costs one real network round trip per operation — sub-millisecond on a healthy LAN, but strictly additive versus a co-located channel and queue, and it multiplies under fan-out: one publish routed to five queues homed on four different remote nodes pays four concurrent hops instead of zero.

ARC 11 · REAL-WORLD PRODUCTION

Four stories: a public postmortem, a resync trap, a migration pattern, and a WAN mistake avoided

Story 1: GitHub's 2014 cluster-partition incident, mechanically revisited

GitHub publicly documented a production incident in which network flakiness between clustered RabbitMQ nodes produced exactly the split-brain mechanics §8(e) describes: nodes lost contact with each other, each side kept its own view of cluster membership, and — under the partition-handling configuration in place at the time — queues mirrored across the split could diverge rather than cleanly failing over. The postmortem became one of the most-cited real-world arguments for treating cluster_partition_handling as a decision to make deliberately rather than leave at a historical default, and for preferring odd-numbered clusters with pause_minority specifically because it converts a silent divergence risk into a loud, visible, and far more recoverable partial outage. It's also one of the incidents that, downstream, helped justify investing in a real consensus protocol (quorum queues' ra/Raft, chapter 6) rather than continuing to patch Mnesia-based mirroring.

Story 2: the mirrored-queue full-resync stall (cross-referenced from chapter 1, deepened here)

Teams running large mirrored-classic-queue fleets during the 2010s hit a specific, well-documented operational trap: when a follower node rejoined after being offline, RabbitMQ's mirroring mechanism could require a full state resynchronization of the queue's entire content to bring the follower current — and during that resync, the queue's master could stall accepting new publishes until the copy completed. This is a direct consequence of mirroring being built on ad hoc replication over the same Mnesia-adjacent machinery as cluster metadata, rather than a real replicated log with incremental catch-up — exactly the gap quorum queues' Raft log closes, since a rejoining Raft member catches up by replaying missed log entries incrementally, never by blocking the leader on a full-content copy.

Story 3: Shovel and federation as the standard "blue-green" major-version migration pattern

RabbitMQ's own upgrade guidance has long recommended, for major-version jumps too large for in-place rolling upgrade (moving off a mirrored-classic-queue-era cluster onto a fresh quorum-queue cluster on current RabbitMQ, for instance), standing up the new cluster fully independently and using Shovel or federation to drain traffic across rather than attempting to upgrade nodes in place. This is precisely requirement 3 from §1: no ongoing topological relationship is wanted once the migration completes, durability and simplicity matter more than routing sophistication, and Shovel's dumb-pump design is a feature here, not a limitation — there's exactly one job (move everything from the old queue to the new one, reliably, then be decommissioned) and Shovel does nothing else.

Story 4: why "just cluster across regions" is the WAN mistake this chapter exists to prevent

Teams operating in multiple cloud regions who reach for full clustering across those regions — instead of per-region independent clusters linked by federation — consistently rediscover §6's cost the hard way: every metadata operation anywhere in the cluster now pays cross-region round-trip latency, and (worse) a network blip between regions is indistinguishable from a real partition to rabbit_node_monitor, triggering pause/autoheal cycles far more often than a LAN deployment ever would. The documented, recommended pattern — independent regional clusters, each internally fast and local, linked by federation for the specific exchanges or queues that actually need cross-region visibility — exists specifically because it was tried the other way first, repeatedly, across the ecosystem.

First, the mechanical heart of pause_minority: a node deciding, from its own local view of the cluster, whether it is on the minority side of a split.

Erlangrabbit_node_monitor.erl — pause_minority decision, simplified
handle_dead_node(Node, State = #state{partition_handling = pause_minority}) ->
    AllMembers  = rabbit_nodes:all_running(),      %% last known full membership
    Reachable   = rabbit_nodes:still_reachable(AllMembers),
    HalfOrLess  = length(Reachable) =< length(AllMembers) div 2,
    case HalfOrLess of
        true ->
            %% we cannot see a strict majority of the LAST KNOWN cluster —
            %% pause ourselves rather than risk serving a diverged view
            rabbit_log:warning("Cluster minority detected; pausing this node", []),
            pause_node(State);
        false ->
            %% we can still see a strict majority — keep serving clients
            State
    end.

Second, exchange federation's loop prevention — the hop-count check that keeps a bidirectional or ring topology from forwarding the same message forever:

Erlangrabbit_federation_link.erl — hop-count / max-hops check, simplified
maybe_forward(Msg = #basic_message{content = Content}, Upstream) ->
    Headers  = rabbit_basic:extract_headers(Content),
    HopsSeen = rabbit_misc:table_lookup_int(Headers, "x-received-from-hops", 0),
    MaxHops  = Upstream#upstream.max_hops,           %% default: 1
    case HopsSeen >= MaxHops of
        true  ->
            %% this message has already crossed as many federation links as
            %% this topology permits — stop here, or a ring/mesh loops forever
            {stop, loop_prevented};
        false ->
            NewHeaders = rabbit_misc:set_table_value(Headers, "x-received-from-hops", HopsSeen + 1),
            {forward, Msg#basic_message{content = rabbit_basic:replace_headers(Content, NewHeaders)}}
    end.

Third, Shovel's worker loop — deliberately the simplest of the three mechanisms, with no routing awareness and no loop protection, because it isn't meant to run in a mesh:

Erlangrabbit_shovel_worker.erl — the whole job, simplified
handle_info({#'basic.deliver'{delivery_tag = Tag}, Content}, State = #state{dest = Dest}) ->
    %% no routing decision, no hop-count header, no exchange type to consult —
    %% just: republish this exact message to the configured destination
    amqp_channel:call(Dest#dest.channel,
                     #'basic.publish'{exchange = Dest#dest.exchange, routing_key = Dest#dest.routing_key},
                     Content),
    ack_source(Tag, State),         %% on-confirm ack mode: only after dest confirms receipt
    {noreply, State}.
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Push consensus decisions to the boundary that actually needs them, and nowhere else. rabbit_node_monitor's minority check only runs on a detected partition — it does not run per message, per publish, or per delivery; the cost of consensus is paid exactly where correctness requires it, never on the hot path. 2. Make loop prevention a header, not a topology restriction. Federation could have simply forbidden bidirectional or ring links; instead it tags every forwarded message with how many hops it's made and lets any topology — including ones the original author never anticipated — work correctly as long as max-hops is set sensibly. 3. Resist the urge to make the simple tool smart. Shovel could have grown exchange-aware routing, deduplication, and loop detection over the years — it deliberately didn't, because the moment it needs that sophistication, federation already exists and is the right tool. Keeping Shovel dumb is what keeps it trustworthy for one-shot migrations where you want the fewest possible moving parts between "message existed at the source" and "message exists at the destination."
