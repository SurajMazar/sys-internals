BLOCKCHAIN FUNDAMENTALS · CHAPTER 07

Sybil Resistance:
Why Voting Doesn't Work

Chapter 6 proved that Byzantine agreement is achievable at n ≥ 3f+1 — but only because every node in that proof already knows n. Open networks have no membership office: anyone can join, leave, or multiply, anonymously, for free. This chapter asks the question that makes an open ledger possible at all — how do you count votes when anyone can manufacture unlimited voters? — and derives the answer that every subsequent chapter depends on: stop counting identities and start counting a resource that cannot be forged.

You will be able toState the Sybil attack (Douceur, 2002) precisely and prove why one-identity-one-vote cannot survive an open network.
You will understandWhy IP limits, CAPTCHAs, reputation, and trusted identity providers all fail — and what property a fix actually needs.
You will predictWhy splitting a fixed compute or capital budget across more identities never increases an attacker's vote share.
You will simulateA cheap identity flood against a naive vote, then the same flood against real proof-of-work.
ARC 01 · THE PROBLEM

The assumption chapter 6 quietly made

Go back and look at the Byzantine Generals bound: agreement is possible with n generals as long as fewer than n/3 are traitors. That theorem is airtight — and it is also, for an open currency network, almost useless as stated, because it takes n as a given. Lamport, Shostak and Pease were reasoning about a fixed committee: named generals, a known roster, a traitor who is one of a specific, enumerated set of people. Classical BFT protocols (chapter 6) inherit this: every one of them needs to know, in advance, the full list of participants and how many there are, because f is defined as a fraction of that list.

A public blockchain has no list. Anyone with a laptop and an internet connection can become a "node." There is no office that hands out membership numbers, no roster to check f against, and — this is the part that breaks everything — no cost to appearing on the network more than once. If "one node, one vote" is the rule, and nodes are free to create, then the rule does not describe a vote at all. It describes whoever is willing to run the most copies of a program.

  • Open membership — anyone may join or leave at any time, with no admission process.
  • Free identity — a new public key, a new IP-facing process, a new "peer" costs nothing but a few milliseconds of CPU and a few dozen bytes of storage.
  • No global roster — no participant can even enumerate the honest population, let alone verify that each entry corresponds to one distinct, independent party.
  • Adversarial cost — an attacker who can create identities faster than the system can validate them controls the vote in the limit, regardless of how small a fraction of real, distinct participants they are.

This chapter is the hinge of the course. Every consensus mechanism from here on — proof-of-work (ch. 8), proof-of-stake (ch. 9), the fork-choice rule (ch. 10) — is, underneath its own vocabulary, an answer to one question: if you cannot count identities, what do you count instead? Get this chapter wrong and Nakamoto consensus looks like an arbitrary, wasteful trick. Get it right and proof-of-work stops looking like "a puzzle miners solve" and starts looking like exactly what it is: a Sybil filter that a consensus rule was built on top of.

WHY THIS MATTERS FOR THE NEXT SEVEN CHAPTERS

Every mechanism you study from chapter 8 onward is doing the same two jobs at once, and courses that teach them as one job produce confused engineers. Job one — Sybil resistance — decides who gets to have a voice at all, and how loud. Job two — consensus — decides how those voices agree on one history. This chapter is entirely about job one. Chapter 8 is mostly about job two, built on top of the specific Sybil filter (computation) this chapter derives. Keep the two jobs separate in your head and the rest of the course assembles itself.

DEEP CONTEXT · WHERE THE NAME COMES FROM

Microsoft researcher John R. Douceur named the attack after Sybil, the 1973 book (and 1976 film) about a woman diagnosed with what was then called multiple personality disorder — a single person presenting as sixteen distinct identities. Douceur credits colleague Brian Zill with the suggestion in his 2002 paper. The metaphor is exact: a Sybil attack is not a network being infiltrated by many attackers, it is a network being infiltrated by one attacker wearing many faces, and every face is, from the network's point of view, indistinguishable from a genuine independent participant.

ARC 03 · NAIVE SOLUTION

Attempt #1: count the peers, take the majority

Derive it honestly, the way an engineer meeting the problem for the first time would. You need the network to agree on one value — the next block, a configuration change, whatever. You have no central authority. The obvious democratic instinct: ask every peer for its opinion and go with the majority.

pseudo-codenaive_vote.py — one identity, one vote
def register(peer_pubkey):
    # Anyone can call this. No admission check exists because
    # there is no authority to check against.
    known_peers.add(peer_pubkey)

def cast_vote(peer_pubkey, proposal, signature):
    if peer_pubkey not in known_peers:
        return False
    if not verify_sig(peer_pubkey, proposal, signature):
        return False          # ch. 4: the signature is genuinely unforgeable
    votes[proposal].add(peer_pubkey)         # ...but proving WHO signed says nothing about
    return True                        # whether that "who" is a distinct person.

def tally():
    return max(votes, key=lambda p: len(votes[p]))  # majority of KNOWN_PEERS wins

Notice what this code gets right: the cryptography is not the weak point. Chapter 4's ECDSA/Schnorr signatures genuinely prove that whoever holds a private key authorized this exact vote — nobody can forge Alice's signature. The weak point is a question signatures were never designed to answer: is this public key a distinct, independent participant, or is it the fortieth key the same person generated this morning? register() has no way to tell, because nothing about a fresh keypair carries any information about who or what generated it.

ARC 04 · WHY IT FAILS

The Sybil attack, precisely — and why the obvious patches don't survive it

State it the way Douceur did in 2002, formally enough to reason about: in a distributed system, a Sybil attack occurs whenever a single faulty entity presents multiple identities to a peer-to-peer network, and the protocol in question grants influence in proportion to identity count. Douceur's paper proves something stronger and more useful than "this is possible": absent a logically centralized authority that certifies one identity per real entity, a large-scale Sybil attack is always possible unless every participant is forced to prove possession of tightly-bounded, verifiably-equal resources simultaneously and continuously — a condition he shows is unrealistic for any sizeable, asynchronous, heterogeneous peer-to-peer network. In plain terms: you either trust someone to hand out identities one-per-customer, or you stop counting identities.

Run the numbers on the naive scheme. Registering an Ed25519/secp256k1 keypair costs microseconds of CPU and under 100 bytes of storage; there is no rate limit an honest protocol imposes, because imposing one requires exactly the identity check that doesn't exist. With 10 honest voters split 6-4 on a proposal, an attacker needs only 3 additional identities to flip the majority — three register() calls, sub-second, zero marginal dollars. Scale the honest population to 10,000 and the attacker needs perhaps 3,001 sybils: still a script that finishes before this paragraph would take you to read it. The cost of attack does not scale with the size of the honest network at all — it scales with nothing, because identity manufacture is not resource-constrained in the naive design.

So the instinct is: make identity cost something. History tried four patches, roughly in this order, and each one is worth deriving to failure — because the failure mode of each is the exact shape of the fix chapter 5 needs to avoid repeating.

Patch 1: rate-limit by IP address

Allow one identity per IP address. This assumes an IP address is scarce and tied to a real party — both false at scale. A single /24 cloud allocation gives an attacker 256 addresses for the price of one instance-hour each (fractions of a cent on spot pricing); IPv6's typical /64 customer allocation hands out 2^64 addresses that all route to one machine. Rented botnets — commodity criminal infrastructure, priced by the thousand-bot-day in underground markets — turn "one identity per IP" into "one identity per few cents." The scarcity the patch assumes was never there.

Patch 2: CAPTCHA / proof-of-humanity

Require a human-solvable puzzle per identity. Two independent failures. First, it is farmable: CAPTCHA- solving services, staffed by low-wage human labor, have priced human attention at roughly a tenth of a cent per solve for over a decade — an attacker with a $50 budget buys tens of thousands of "proofs of humanity." Biometric variants (iris scans, liveness checks) raise the farming cost but don't eliminate it, and introduce a worse problem: someone must issue and vouch for the biometric enrollment, which brings us to Patch 4. Second, even a perfect proof-of-humanity check only proves "a human was involved once" — it says nothing about whether that human controls one identity or is being paid to enroll a thousand.

Patch 3: reputation, earned over time

Let new identities start with zero trust and earn influence through good behavior — the approach academic systems like EigenTrust (Kamvar, Schlosser & Garcia-Molina, 2003) formalized for peer-to-peer file sharing. This has a genuine bootstrapping problem baked in: a brand-new honest node and a brand-new Sybil node are, on day one, bit-for-bit identical. Any rule generous enough to let real newcomers participate is equally generous to fresh sybils; any rule strict enough to slow down sybils also locks out real newcomers, permanently disadvantaging exactly the organic growth the network needs. Worse, reputation is attackable retroactively: an identity that accumulates trust, then defects, then discards itself and re-enters as a new "trusted-looking" identity — the whitewashing attack Friedman & Resnick described in 2001 — resets the clock for free whenever the accumulated reputation stops being useful.

Patch 4: a trusted identity provider

Require government ID, a notarized certificate, or a KYC'd exchange account per identity. This one actually works — and that is precisely the problem. It works by reintroducing a single trusted party who decides who gets to exist on the network, which is the exact centralization the whole exercise was trying to remove. It also fails on its own terms in practice: verified accounts are bought and sold on secondary markets, a compromised or coerced issuer can mint unlimited "verified" sybils at will, and the scheme cannot function pseudonymously or across jurisdictions — disqualifying it for any network that wants permissionless, global, censorship-resistant participation.

THE PATTERN BEHIND ALL FOUR FAILURES

Every patch tried to make identity expensive. Every one failed because identity is information, and information is the cheapest thing in a computer to duplicate. IP addresses, CAPTCHA solutions, and reputation scores are all still just data attached to an identity — an attacker who can fabricate the identity can usually fabricate or purchase the attachment too, because nothing about the attachment is provably scarce. The fourth patch finally introduces real scarcity — trust in an issuer — but pays for it with the one thing an open network cannot spend: a central authority. Chapter 5 asks what else could be scarce.

ARC 05 · THE REAL FIX

Stop counting identities. Count a resource that cannot be forged.

Here is the insight the whole course pivots on. Every patch in §4 failed because it tried to attach a cost to identity — a piece of information, freely copyable by construction. The fix is to stop weighting votes by identity at all, and instead weight them by expenditure of a resource that is genuinely scarce outside the protocol: computation, capital, storage, or specialized hardware. An identity, in the final design, is not a voter. It is a receipt for resource already spent — and receipts don't multiply just because you photocopy them.

THE REFRAME THAT MAKES EVERYTHING ELSE IN THIS COURSE MAKE SENSE

Proof-of-work is a Sybil-resistance mechanism first, and a consensus mechanism only second. Nakamoto's 2008 whitepaper says this almost verbatim, in section 4, and most explanations of Bitcoin get the emphasis backwards by leading with the consensus story: "The proof-of-work also solves the problem of determining representation in majority decision making. If the majority were based on one-IP-address-one-vote, it could be subverted by anyone able to allocate many IPs. Proof-of-work is essentially one-CPU-one-vote." Read that sentence again with §4 fresh in your head — Satoshi is explicitly rejecting Patch 1 (one-IP-one-vote) and replacing "one-identity-one-vote" with "one-unit-of-scarce-resource-one-vote." Chapter 8 will show you the mining puzzle and the difficulty target; this is the reason those things exist at all.

Why does this actually work where §4's patches didn't? Because manufacturing more identities no longer helps the attacker — the resource pool an attacker controls is fixed by the real world, and splitting it across more receipts does not create more of it. One identity spending a fixed compute budget produces the same expected voting weight as a thousand identities splitting that identical budget. The vulnerability Douceur described requires that identity count be correlated with influence; resource-weighting severs that correlation by definition. THE DIRECT ANCESTOR: HASHCASH, 1997

Adam Back proposed hashcash in 1997 for a problem that had nothing to do with currency: email spam. Force every sender to compute a partial hash collision — find a value whose hash has some number of leading zero bits — before a message is accepted. Spammers, who profit from sending millions of messages, are hurt by a per-message CPU tax; a person sending one email barely notices it. The technique was, from day one, exactly "make the cheap thing (an email, an identity) expensive by tying it to a genuinely scarce resource (CPU time)." Nakamoto's 2008 whitepaper cites Back's work directly — Bitcoin's mining puzzle is hashcash, repurposed from rationing inboxes to rationing votes.

ARC 06 · WHY THAT STILL COSTS

Resource-weighting defeats Sybils. It does not defeat economics.

Replacing identity with resource genuinely solves the problem Douceur described. It introduces three new problems of its own, and an honest chapter names all three before moving on.

1. Who bears the cost — external vs. internal-but-forfeitable

Proof-of-work's cost is external: real electricity, burned in the physical world, unrecoverable whether or not the attacker wins. That's a genuine security property — a failed attack cannot get its spend back — but it means the honest majority is also burning real energy every single day just to keep voting. Estimates from outlets like the Cambridge Centre for Alternative Finance have repeatedly put Bitcoin's annualized electricity draw in the range of a mid-sized country — a cost with no analog in the naive scheme from §3, which cost approximately nothing to run honestly, only to attack. Proof-of-stake's cost is internal but forfeitable: capital locked inside the system itself, at risk of slashing — programmatic destruction — if the staker misbehaves. Nothing is burned merely to participate honestly, which is the efficiency win; but the "scarce resource" is now an asset whose value the system itself partly determines, and a staker who is slashed can, in principle, have contributed nothing physical to the world in exchange for the security bought. Chapter 9 works through exactly how far that circularity goes and where it's actually resolved.

2. Mining and staking pools: the re-centralization pressure

Individual participation in either scheme has brutal reward variance. A miner controlling 0.01% of Bitcoin's hashrate expects to find a block roughly once every 10,000 blocks — at 10 minutes per block, on the order of 1,000 days between paydays, an unbankable variance for anyone but the largest operations. The economically rational response is to pool: combine hashrate (or stake) with others, share the smoothed-out reward proportionally, and accept a small fee. Nothing here is a Sybil attack — every participant still contributes real, honestly-owned resource — but pooling reconcentrates decision-making in the pool operator, who chooses which transactions to include, which software version to run, and, historically, has occasionally approached the majority threshold a single operator was never supposed to hold (§11 has the receipts). Resource-weighting defeats the specific attack Douceur named; it does not repeal the economics that make concentration attractive.

3. The "just don't be open" answer: proof-of-authority and permissioned chains

There is a fifth patch this chapter hasn't named yet, and it deserves to be named honestly rather than dismissed: stop being an open network. A consortium of five named banks, a private supply-chain ledger among known participants, an enterprise chain with a fixed validator set elected out-of-band — these systems have a real membership roster, which means chapter 6's classical BFT machinery (3f+1, known n) applies directly, with no Sybil problem to solve at all, because the "who is a distinct participant" question was answered administratively before the protocol ever ran. Proof-of-authority (fixed, identified signers) and permissioned chains (membership-service-provider gated) are not inferior engineering — they are the correct choice whenever open, permissionless, pseudonymous participation is not actually a requirement. What they give up is exactly what §4's Patch 4 gave up: censorship resistance and permissionless entry now depend entirely on trusting whoever controls the roster. There is no way to have open membership, Sybil resistance, and zero ongoing cost simultaneously — you always pay in one of those three currencies.

WHY THIS IS "CHEAP TO VERIFY, EXPENSIVE TO PRODUCE"

Finding a nonce at difficulty 5 (five leading hex zeros) takes on the order of 16^5 ≈ 1,048,576 expected SHA-256 evaluations — real work your CPU actually performs, which is why the counter above climbs visibly. Checking a claimed solution costs exactly one SHA-256 evaluation, regardless of the difficulty used to find it — hash the challenge and nonce once, look at the leading characters. This asymmetry (expensive to produce, trivial to verify) is the property every scarce-resource scheme in §5 needs and the naive scheme in §3 never had: verifying a claimed identity there cost the same near-zero amount as forging one.

ARC 10 · ATTACK ECONOMICS

Pricing an attack: identity count vs. real resource

The naive scheme's attack cost is flat near zero no matter how big the honest network gets — you saw that in §4's canvas. A resource-weighted scheme's attack cost instead scales with how much of the resource the attacker must out-acquire. Drag the attacker's budget and watch three curves diverge: identity-count voting (still nearly free), proof-of-work (linear in hardware + energy spend), and proof-of-stake (linear in market value, with the added twist that buying that much of an asset on the open market moves its own price).

Real numbers anchor the curves. Analyses in the spirit of the "cost of a 51% attack" calculators that emerged around 2018–2019 (built on rentable-hashrate marketplaces such as NiceHash) price a one-hour majority-hashrate rental on smaller proof-of-work chains at anywhere from a few hundred to a few hundred thousand dollars, depending entirely on how much of the coin's total hashrate is available to rent versus dedicated to it — which is precisely why §11's incidents cluster on chains with small, rentable hashrate rather than Bitcoin's roughly 600+ exahash/second network, where acquiring a bare majority would mean out-buying and out-running a global industrial base of purpose-built ASICs. Proof-of-stake's equivalent question — the market value of the stake needed to violate safety (commonly a 33%+ or 51%+ threshold depending on the exact BFT variant, chapter 9) — is usually priced in billions of dollars for a large chain, and buying that much on the open market before anyone notices is a security assumption in itself, not a free property.

ARC 11 · REAL-WORLD INCIDENTS

When the resource wasn't as scarce as assumed

Incident 1: GHash.io approaches 51% (July 2014)

No sybil identities were involved — that's the point. The mining pool GHash.io briefly exceeded 50% of Bitcoin's total network hashrate, drawing public alarm because a single pool operator, coordinating thousands of honestly-owned machines, had reassembled the exact majority-control threshold proof-of-work is supposed to make prohibitively expensive for any one party. GHash.io publicly pledged to cap its share below 40%. Root cause: §6's pooling pressure (variance reduction) concentrated decision rights over honestly-earned hashrate, even though no individual miner cheated.

Incident 2 & 3: Ethereum Classic's rented-hashrate reorgs (Jan 2019, Aug 2020)

Ethereum Classic split from Ethereum after the 2016 DAO fork and kept proof-of-work at a fraction of Ethereum's (and Bitcoin's) hashrate. In January 2019, an attacker rented sufficient hashrate — largely through NiceHash-style marketplaces that let anyone point rented mining capacity at any compatible chain by the hour — to reorganize the chain and double-spend an estimated ~$1.1M in exchange deposits. A larger episode in August 2020 produced multiple reorganizations, one reportedly exceeding 4,000 blocks, with total double-spends across that month estimated in the low millions of dollars. Root cause: proof-of-work's Sybil resistance assumes the scarce resource (hashrate) is expensive to acquire; rental marketplaces let an attacker rent it by the hour instead of owning it, which is cheap precisely on chains whose total hashrate is small relative to the rentable pool aimed at algorithm-compatible coins.

Incident 4: Bitcoin Gold's 51% attacks (May 2018, Jan 2020)

Bitcoin Gold, an Equihash-based Bitcoin fork, suffered a majority-hashrate double-spend attack in May 2018 with losses reported around $18M, and a smaller repeat in January 2020. Same mechanism as Incident 2/3: a chain whose proof-of-work algorithm is shared with a much larger rentable hashrate market inherits none of the "expensive to acquire" property that gives large, algorithm-dedicated chains their security margin.

Incident 5: a pure, non-financial Sybil attack — Tor's "KAX17" relays (reported 2021)

Not every Sybil attack is about money, and not every one is about blockchains — which is worth remembering before assuming this chapter's problem is currency-specific. Independent Tor researcher Nusenu documented an operator, dubbed KAX17, that had been running a large number of malicious relays — researchers' estimates ranged into the hundreds to over a thousand simultaneous relays — since around 2017, seemingly attempting to control both the entry and exit points of Tor circuits to deanonymize users. This is Douceur's attack in its original, identity-only form: no cryptocurrency, no proof-of-work, just an entity presenting many "independent" relay identities to a network whose privacy guarantees depend on those relays actually being run by unrelated parties.

Incident 6: the Steem governance takeover (February 2020) — a different failure of "voting"

Worth including precisely because it is not a classic Sybil attack, and the distinction sharpens this chapter's point. When Steemit's founder sold the company — along with roughly a fifth of all STEEM in pre-mined "ninja-mined" stake — to Justin Sun, the community pushed a soft fork to freeze that stake pending negotiation. Sun responded by coordinating with several major exchanges to vote using customer-deposited STEEM — balances the exchanges custodied but did not own — electing a slate of witnesses that reversed the freeze. No fake identities were manufactured. The lesson is the mirror image of §6's honest warning about proof-of-stake: "one-token-one-vote" resists Sybils perfectly (you cannot manufacture tokens for free), but it does not guarantee that voting power tracks independent, distinct stakeholders when custody is concentrated — the same failure mode Douceur described, arrived at through concentration rather than counterfeiting.

def sybil_flood(target_proposal, n_identities):
    # Zero admission check exists to stop this. Each iteration is
    # a keypair generation (~microseconds) + one signed vote.
    for _ in range(n_identities):
        sk, pk = generate_keypair()          # ch. 4 — genuinely fresh, genuinely unforgeable
        register(pk)                          # naive_vote.py has no way to reject this
        sig = sign(sk, target_proposal)
        cast_vote(pk, target_proposal, sig)

# Wall-clock on a laptop: well under a second. Marginal dollar cost: ~$0.
pseudo-coderesource/pow_vote.py — a vote is now a receipt, not an identity
def grind_receipt(voter_pubkey, proposal, difficulty):
    # The "identity" no longer matters for weight — only this loop's
    # output does. Splitting your hash budget across more pubkeys
    # produces the same TOTAL expected receipts, never more.
    nonce = 0
    challenge = hash(voter_pubkey + proposal)
    while True:
        digest = sha256(challenge + str(nonce))
        if leading_zero_bits(digest) >= difficulty:
            return Receipt(voter_pubkey, proposal, nonce, digest)
        nonce += 1

def tally_by_resource(receipts, difficulty):
    # Weight = 1 per VALID receipt, not 1 per identity that showed up.
    # A thousand identities producing zero valid receipts contribute zero.
    valid = [r for r in receipts if verify(r, difficulty)]  # O(1) per check — §8b
    return Counter(r.proposal for r in valid).most_common(1)

def cast_stake_vote(voter_pubkey, proposal, signature):
    stake = locked_balances.get(voter_pubkey, 0)
    if stake == 0 or not verify_sig(voter_pubkey, proposal, signature):
        return                              # zero stake ⇒ zero weight, however many keys you mint
    votes[proposal] += stake                  # weight = locked capital, not identity count

WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Decouple "who" from "how much." Both resource schemes keep chapter 4's signatures for authenticity (proving who cast a receipt) while making weight a function of something signatures can't provide — proven expenditure. 2. Make verification asymmetric to production on purpose. Both verify() calls above are O(1); production is deliberately expensive. Any scheme where verification cost approaches production cost degenerates back toward §3's free-identity problem, because cheap-to-fake creeps back in. 3. Tie the receipt to the specific vote it authorizes. The challenge in grind_receipt hashes in the proposal itself — a receipt ground for one proposal can't be replayed against another, closing off a cheap reuse attack that would otherwise let one unit of real work buy influence over unrelated decisions.
