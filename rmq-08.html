RABBITMQ INTERNALS · CHAPTER 08

Dead Lettering, TTL &
Priority Queues

Three features that every RabbitMQ tutorial covers in a paragraph each, and every production incident report covers in a page each. Dead lettering looks like "failed messages go somewhere safe" until you ask exactly which four events trigger it, where the routing key comes from, and what happens the second time a message bounces through the same two queues. TTL looks like "messages that get old go away" until you discover the broker only ever looks at the head of the queue to decide that. Priority queues look like "important messages jump the line" until the memory bill for 255 priority levels arrives, or a consumer's prefetch window quietly ignores priority entirely. This chapter builds all three from first principles, then hands you a lab where you can construct a real dead-letter topology, watch a message accumulate an x-death header across hops, watch RabbitMQ drop a message mid-retry because of cycle detection, watch a long-TTL message block an entire queue behind it, and watch a starved low-priority lane never get served.

ARC 01 · THE PROBLEM

What happens to a message that isn't simply "delivered"?

Every chapter so far has assumed the happy path: a message is published, routed, delivered, and acknowledged. Real systems are full of messages that don't follow that path — a message whose handler throws on a malformed field, a message that represents a price quote nobody should trust after two seconds, a message carrying a VIP customer's cancellation request that should jump ahead of a bulk newsletter unsubscribe. None of these are exotic; they are the ordinary shape of production traffic. What's exotic is how many engineers ship systems handling all three without ever precisely defining what the broker is contractually obligated to do about them.

"Dead lettering" sounds like it should mean "failed messages go to a safe place" — and broadly it does — but that safe place is reached through exactly four distinct trigger conditions, not one generic notion of "failure," and the routing decision for how a message gets there has a specific, learnable algorithm with at least one surprise most engineers discover only in production: omit one configuration key and the message keeps its original routing key rather than getting a sensible default. "TTL" sounds like it should mean "old messages disappear" — and it does, eventually — but the mechanism that decides when "eventually" arrives is not what most engineers assume, and the gap between assumption and mechanism has genuinely surprised operators watching a queue's memory usage climb despite a short TTL being configured correctly. "Priority queues" sound like they should mean "important messages get served first" — and they do, faithfully — but that faithfulness has a real, unavoidable cost in memory and CPU, and a real, by-design failure mode: starvation of low-priority work that never lets up as long as high-priority work keeps arriving.

All three features share a structural similarity worth naming up front: each one asks the broker to make a decision about a message's fate that goes beyond "hand it to whichever consumer is next in line, in the order it arrived." Each decision needs its own piece of process state, its own algorithm, and its own well-defined edge case — and each edge case, unaddressed, turns into either silent message loss, a queue that quietly never drains, or a consumer that quietly never gets served. This chapter derives all three mechanisms from the problems they solve, not from the configuration keys that happen to control them.

WHY THESE THREE FEATURES BELONG IN ONE CHAPTER

Dead lettering, TTL, and priority queues are usually taught as three unrelated bullet points in a features list. They belong together because they are the three places where RabbitMQ's core delivery model — "a queue is a strict FIFO of ready messages, handed out to consumers in arrival order until acked" (chapters 4 and 5) — is deliberately broken, on purpose, for a good reason, with a specific mechanism, and a specific price. Understanding the price is the actual content of this chapter; the configuration keys are just how you pay it.

DEEP CONTEXT · WHY DEAD LETTERING SHIPPED BEFORE TTL FELT FINISHED

Dead lettering arrived first because it answers the more urgent operational question: "a message was explicitly rejected — where does it go so it isn't just gone?" TTL's early implementations existed but the combination of per-message expiration and per-queue x-message-ttl interacting with dead lettering (an expired message needs a destination too) took longer to settle into the head-of-queue semantics this chapter derives in §8 — it is not a coincidence that the mental model for "what happens to an expired message" only became fully coherent once dead lettering already existed as its destination.

ARC 03 · NAIVE SOLUTION

Attempt #1: handle all three problems entirely in application code

Before reaching for x-dead-letter-exchange, x-message-ttl, or x-max-priority, it's a reasonable instinct to solve all three problems the way you'd solve them in any other queueing system that didn't offer broker-side help: catch the failure and requeue by hand, stamp a timestamp and filter in the consumer, and run separate queues per priority level.

pythonnaive_consumer.py — hand-rolled retry, expiry, and priority
def on_message(channel, method, properties, body):
    payload = json.loads(body)

    # naive TTL: trust a client-stamped timestamp, filter after the fact
    if time.time() - payload["published_at"] > 30:
        channel.basic_ack(method.delivery_tag)     # "expired" — just drop it, silently
        return

    try:
        process(payload)
        channel.basic_ack(method.delivery_tag)
    except Exception:
        # naive dead-lettering: nack with requeue=True and hope it eventually works
        channel.basic_nack(method.delivery_tag, requeue=True)

# naive priority: three separate queues, consumer polls high before low
for qname in ["orders.high", "orders.med", "orders.low"]:
    channel.basic_consume(queue=qname, on_message_callback=on_message)

Every piece of this is a reasonable first move, and every piece has a broker-level replacement this chapter derives. Before deriving them, it's worth playing the naive retry path all the way forward — because the failure mode it produces (chapter 5 touched this briefly; this chapter completes it) is exactly the gap dead lettering was built to close.

ARC 04 · WHY IT FAILS

Three independent failures, each quantifiable

Each of the three naive approaches above fails for a different, precise reason — not "it's inelegant," but a concrete cost or an outright correctness bug.

  • Naive retry has no exit condition. As chapter 5 established, nack(requeue=true) on a deterministically-failing message is an unbounded loop by construction: no counter, no backoff, no terminal state. Measured in wall-clock terms, a poison message with a 5ms deliver→fail→nack round trip burns 200 attempts/second of one consumer's capacity, forever, until an operator intervenes by hand — that's not a tail-latency problem, it's 100% of a worker's throughput redirected at zero completed work indefinitely.
  • Naive TTL filtering costs a full dequeue for every expired message, and trusts the wrong clock. The consumer still had to receive, deserialize, and inspect every "expired" message before discarding it — work proportional to however many stale messages accumulated ahead of real ones, i.e. O(messages received), not O(messages actually processed). Worse, it trusts a timestamp the publisher stamped, which silently breaks the moment publisher and consumer clocks drift, or a publisher's retry logic re-stamps a message with a fresh timestamp on resend, defeating the entire point of the check.
  • Naive priority-via-separate-queues doesn't actually get you priority — it gets you three independent FIFOs and a manual scheduling problem. "Poll high before low" sounds like it enforces priority, but each queue has its own message store, its own prefetch window, and no shared credit accounting: a consumer that's mid-poll on the low queue when a high-priority message arrives doesn't preempt anything, and running three separate basic_consume registrations means three times the per-consumer bookkeeping and no single place the broker can answer "what's the single next message across all three, by priority."
THE COMMON THREAD

All three naive approaches move a broker-level policy decision into application code that has to be written correctly on every consumer, every time, with no protocol-level enforcement. A single consumer that forgets the naive TTL check, or nacks with requeue=true instead of false, or subscribes to the queues in the wrong order, silently breaks the guarantee for the entire system — with nothing in the broker's own bookkeeping able to detect it. The fix in each case is the same shape: move the decision into the queue's own declared arguments, where the broker enforces it uniformly regardless of which consumer code happens to be running.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three broker-enforced mechanisms, derived one at a time

Each mechanism replaces one piece of the naive consumer above with a declared queue argument the broker itself enforces — no client cooperation required, no way for one misbehaving consumer to silently violate the policy for everyone else.

Dead lettering: from "requeue and hope" to a declared destination

Deriving x-dead-letter-exchange and the routing-key surpriseSTEP-BY-STEP

The deck's end state is the real mechanism: a queue declared with x-dead-letter-exchange gives the broker a destination for exactly four situations (full detail in §8): a message rejected or nacked with requeue=false; a message whose TTL expired; a message dropped because the queue exceeded x-max-length (or x-max-length-bytes); and, on quorum queues, a message whose x-delivery-limit was exceeded. In every case the broker republishes the message to the configured exchange using x-dead-letter-routing-key if one was declared — and, if it wasn't, using the message's original routing key, unchanged. That last clause is the surprise the deck ends on: engineers who assume an omitted routing key means "the DLX's default binding will catch it" are implicitly relying on the original key still making sense as a binding key against the dead-letter exchange's bindings, which is often not what they intended.

TTL: two independent knobs, not one

RabbitMQ actually gives you two separate TTL mechanisms that happen to produce the same visible effect (message eventually vanishes from the queue) through different configuration surfaces: x-message-ttl is a per-queue policy applied uniformly to every message that queue ever holds; expiration is a per-message property the publisher sets, different for every message if it wants. Both are milliseconds, both are optional, and — critically, foreshadowing §6 — both are enforced the same way, which is the actual subject of this chapter's central derivation.

Priority: N sub-queues wearing one queue's declaration

Declaring a queue with x-max-priority=N doesn't create N separate AMQP-visible queues — it creates one queue that internally partitions its ready messages into N+1 priority classes (0 through N) and, on every dispatch, drains the highest non-empty class first. A single basic_consume registration now sees a stream that's already priority-ordered, with none of the naive approach's manual polling.

WHY ALL THREE ARE QUEUE-DECLARATION-TIME DECISIONS, NOT RUNTIME TOGGLES

x-dead-letter-exchange, x-message-ttl, and x-max-priority are all set when the queue is declared (or via a policy matched against the queue's name — the operationally preferred approach, since policies can be changed without redeclaring the queue) and are immutable properties of that queue's identity for its lifetime otherwise. This is a deliberate design constraint, not a limitation someone forgot to lift: each of these mechanisms requires the queue process to maintain additional internal state structures from the moment messages start arriving (a dead-letter destination to check on every rejection, a priority-partitioned internal structure instead of a flat FIFO) — retrofitting that state onto a queue that's already accumulated messages under a different internal representation is exactly the kind of migration RabbitMQ sidesteps by making you declare a new queue instead.

ARC 06 · WHY THAT STILL COSTS

Cycle detection, head-of-queue blocking, and starvation-by-design

Each of the three mechanisms just derived is correct — and each has a sharp, well-defined edge most engineers only meet in production.

1. The classic retry-with-backoff topology, and exactly how it loses messages

A very common pattern, reinvented independently by countless teams: give the source queue's DLX a delay/retry queue instead of a terminal dead-letter queue. The retry queue has its own x-message-ttl (the backoff interval) and its own x-dead-letter-exchange pointing back at the source queue — so a failed message waits out the TTL in the retry queue, then automatically reappears in the source queue for another attempt. It looks like free, broker-native retry-with-backoff, and for exactly one bounce, it is.

Why the retry-to-source topology silently drops the messageSTEP-BY-STEP

The precise rule (implemented in full in §8): RabbitMQ will not dead-letter a message into a queue that it has already been dead-lettered from, earlier in the same unbroken chain of automatic dead-letterings — it drops the message instead of republishing it. "Unbroken" is the key word: if a consumer explicitly requeues the message in between (a real basic.nack(requeue=true), a real redelivery it then fails again by itself, anything that constitutes an actual new delivery attempt rather than an automatic broker-side bounce), the cycle memory resets. A source→retry→source topology with no consumer ever touching the message in between hits this rule on the very first automatic bounce back to the source queue — because the source queue is, definitionally, already recorded as a queue this message was dead-lettered from. The message vanishes, with no error, no log line at the application layer, nothing — exactly the kind of silent loss this whole chapter has been building toward avoiding.

2. TTL's head-of-queue rule: the actual reason "old messages disappear" is more subtle than it sounds

Preview ahead of §8's full derivation: RabbitMQ does not scan a queue for expired messages. It checks whether the message at the very head of the queue has expired, and only the head. If the head message's TTL (or per-message expiration) hasn't elapsed yet, nothing behind it is inspected — even if a message three positions back was published with a much shorter TTL that elapsed minutes ago. That message is not gone; it is not being processed; it is sitting in the queue, counted in the queue's depth, consuming memory, waiting for every message ahead of it to be consumed or expire first.

3. Priority queues: real memory/CPU cost, and starvation as a designed-in property

Every additional priority level is another internal partition the queue process must maintain — more internal bookkeeping structures, more work per dispatch decision (checking "is the next-highest class non-empty" costs something proportional to how many classes there are), and more memory overhead per queue, multiplied across however many priority queues a cluster runs. x-max-priority=255 because "priority 0-255 sounds thorough" is a common, expensive mistake — 5 is enough resolution for the overwhelming majority of real prioritization schemes, and the marginal value of level 200 over level 20 is essentially never realized in practice, while the marginal memory/CPU cost is paid on every single message dispatch regardless.

Starvation is not a bug in this design — it's the necessary consequence of what "priority" means. If higher-priority messages keep arriving faster than the consumer can drain them, the highest non-empty class is, by definition, never empty, and lower classes never get a turn. A system that guaranteed low-priority messages eventually get served regardless of high-priority arrival rate wouldn't be a priority queue — it would be a fairness queue with priority as a tiebreaker, a different (and also valid) design RabbitMQ does not implement. §15's simulator makes this concrete: watch a low-priority lane's counter climb while it never once gets drained.

One more interaction worth internalizing before §8: priority does not override prefetch (chapter 5). A consumer holding an unacked low-priority message inside its prefetch window is still occupying that window's capacity — the broker cannot deliver a new higher-priority message to that consumer until it acks (or nacks) what it's already holding, no matter how urgent the new arrival is. Priority reorders what the queue offers next; it does not reach into a consumer's hands and swap out work already delivered.

DEEP CONTEXT · WHY x-max-length OVERFLOW HAS TWO BEHAVIOURS

x-overflow controls what happens once a queue at its x-max-length (or x-max-length-bytes) ceiling receives one more message. The default, drop-head, drops (and, if a DLX is configured, dead-letters) the oldest ready message to make room — the new publish always succeeds. The alternative, reject-publish, instead rejects the incoming publish itself (the publisher sees a basic.nack if using confirms) and nothing is dead-lettered, because nothing was ever enqueued in the first place — the message that would have overflowed never entered the queue's bookkeeping at all. Confusing these two is a real source of "why isn't my overflow showing up in the dead-letter queue" debugging sessions: under reject-publish, that's expected — check the publisher's confirm channel, not the DLX.

ARC 08 · INTERNAL IMPLEMENTATION

The four triggers, the x-death header, cycle detection, head-of-queue TTL, and priority sub-queues

(a) The four triggers, precisely

TRIGGERWHO DECIDESQUEUE TYPES
Reject / Nack, requeue=falseConsumer, explicitlyClassic, quorum
TTL expiry (queue or per-message)Broker, on head-of-queue checkClassic, quorum
x-max-length / x-max-length-bytes exceeded, overflow=drop-headBroker, at enqueue timeClassic, quorum
x-delivery-limit exceededBroker, tracking delivery count in the Raft logQuorum only

Every one of these four converges on the same republish mechanism once triggered: rabbit_dead_letter takes the message, looks up the source queue's x-dead-letter-exchange argument, and republishes to that exchange using x-dead-letter-routing-key if declared, or the message's original routing key if not. Nothing about which of the four triggers fired changes this routing step — the reason is recorded separately, in the header covered next.

(b) The x-death header: one entry per (queue, reason) pair, not per hop

A common misreading is that x-death grows by one array entry every single time a message is dead-lettered. The actual rule is more precise and more useful for debugging: each entry is keyed by the pair (queue, reason) — the queue the message was dead-lettered from, and why. If a message is dead-lettered from the same queue for the same reason more than once (which, per §6, can only happen if a consumer explicitly broke the cycle in between), the existing entry's count increments and its time updates, rather than a new entry being appended. A genuinely new (queue, reason) pair — moving to a different queue, or failing for a different reason at the same queue — gets its own entry, most recent first. Each entry carries: count, reason (rejected, expired, maxlen, or delivery_limit_exceeded), queue, exchange (the exchange the message was originally published through before this hop), routing-keys, and time. Reading this array top-to-bottom, in a debugger or a dead letter queue's inspector, tells you the entire dead-letter history of a message without any application-level logging.

(c) Cycle detection, exactly

The rule from §6, stated precisely: before dead-lettering a message into queue T, the broker checks whether T already appears among the queues this message has been automatically dead-lettered from since the last explicit requeue (a real consumer nack(requeue=true), or an equivalent genuine redelivery). If it does, the message is dropped instead of republished — routing it into T again would, by construction, produce the exact same outcome that already happened, forever. An explicit requeue is treated as a fresh delivery attempt and clears this memory, because a human or application decision intervened, not because the broker assumes anything got fixed.

(d) TTL: why only the head is ever checked

Both TTL mechanisms are enforced by the same queue process (chapter 4's rabbit_amqqueue_process / backing queue) at the same decision point: whenever the queue is about to consider its head message ready for delivery (a new consumer polls, an existing consumer's prefetch frees a slot, a periodic internal check fires), it first asks "has the head message's TTL elapsed?" If yes, it's dropped (dead-lettered if configured) and the new head is checked the same way, in a loop, until a non-expired head is found or the queue empties — this is exactly why a long-blocked backlog can vanish all at once the moment its blocker is finally removed (§15 makes this visible). If no, delivery proceeds normally and nothing behind the head is ever inspected.

Derive why this is the only design that scales: a single Erlang process owns each queue (chapter 4's central constraint), and that process is also handling every publish, every delivery, and every ack for that queue serially. Scanning the entire ready-message list on every check to find "any" expired message, rather than just the head, would cost O(queue depth) work per check, on the one process already doing everything else for that queue — for a queue carrying tens of thousands of ready messages, that's tens of thousands of comparisons paid repeatedly, on the critical path of ordinary delivery, to catch a case a head-only check will eventually catch anyway once those messages reach the head. Checking only the head is O(1) per check, at the cost of exactly the surprise this chapter keeps returning to: a message can be logically expired for an arbitrarily long time while sitting, counted, in memory, behind a head message with a longer TTL.

Separately, x-expires (queue TTL, not message TTL) auto-deletes the entire queue once it has gone unused — no consumers, no basic.get, no redeclare — for the configured duration. It solves a different problem entirely (leaked reply-to queues, abandoned temporary queues) and is checked on a much coarser timer than per-message TTL, since it's a whole-queue lifecycle decision, not a per-message one.

(e) Priority queues: N sub-queues inside one queue process

Deriving priority sub-queues from the naive separate-queues approachSTEP-BY-STEP

rabbit_priority_queue wraps the ordinary backing queue machinery from chapter 4 with one backing queue per declared priority level, 0 through x-max-priority. A publish is routed into the sub-queue matching its priority property (clamped into range, or into level 0 if unset); a dispatch walks from the highest level downward and serves the first non-empty one. Nothing about message storage, persistence, or the message store (chapter 4) changes — only which internal queue a given message's reference lives in, and which internal queue dispatch consults first. This is why the memory/CPU cost scales with levels declared, not messages held: an empty level-200 sub-queue still exists as a structure the dispatch loop has to check on every delivery decision, and it costs exactly the same whether zero or a thousand messages ever use it.

(f) The delayed-message-exchange plugin: a different way to get a delay

Rather than hand-building the retry/delay-queue topology from §6, the community rabbitmq-delayed-message-exchange plugin implements an exchange type (x-delayed-type) that stores a scheduled-for-later message internally (backed by Mnesia) and republishes it to its real destination once the delay elapses — no separate delay queue, no TTL-triggered dead lettering, no cycle detection to reason about. The tradeoffs are real: the delayed message lives in the exchange process's own scheduling state until it fires, which is not replicated the way a quorum queue's Raft log is, so a node failure before the delay elapses can lose the scheduled message entirely on classic-queue-equivalent durability terms; timer-based delivery on a single Erlang process also means many thousands of simultaneously-scheduled delayed messages compete for the same timer-management data structure, and delivery jitter grows under load in a way a plain TTL+DLX topology (whose queue-level TTL degrades more predictably) generally does not.

The pattern: RabbitMQ is unusually complete across all three axes simultaneously — most systems pick one or two to support natively and leave the rest to application code. The price for that completeness is exactly what this chapter has been deriving: more configuration surface, more edge cases (cycle detection, head-of-queue blocking, per-level overhead) than a system that only solved one of the three problems would ever need to expose.

ARC 10 · PERFORMANCE CHARACTERISTICS

What scales with levels, what scales with depth, what's free

  • TTL enforcement is O(1) per delivery decision regardless of queue depth — §8(d)'s head-only check, the reason RabbitMQ can carry very deep queues with per-message TTL without a background scanning cost.
  • Priority-queue overhead is O(x-max-priority), not O(messages) — declared levels cost memory and per-dispatch CPU whether or not messages ever occupy them; this is why "5 is plenty, 255 is a mistake" is a quantifiable claim, not a style preference.
  • Dead lettering adds exactly one extra internal republish per triggered message — cheap relative to an unbounded naive retry loop, but not free, and it happens on the queue process's ordinary critical path.
  • The x-death header itself is bounded by distinct (queue, reason) pairs actually visited, not by total dead-lettering events (§8(b)) — a message ping-ponging between the same two queues under cycle detection is stopped after one bounce specifically so this header (and the underlying loop) can't grow without bound.

ARC 11 · REAL-WORLD PRODUCTION

Three stories: a blocked head, 255 priority levels, and a retry loop that lost messages quietly

Story 1: memory kept climbing despite a five-second TTL

A commonly reported shape (echoed across RabbitMQ community forum threads and CloudAMQP's operational writeups): a queue configured with a short per-message expiration for most traffic occasionally received a small number of messages carrying a deliberately long TTL (a "hold for review" workflow, or simply a publisher bug setting the wrong property). Once one of those long-TTL messages reached the head, every short-TTL message published afterward queued up behind it — already logically expired, still fully counted in queue depth and memory — until the long-TTL head message was finally consumed or timed out. Operators watching a memory graph climb despite "TTL is set to five seconds everywhere" discovered, only after reading the head-of-queue semantics closely, that a five-second TTL is not a promise about when a message disappears, only about when it becomes eligible to disappear once it's at the front of the line.

Story 2: x-max-priority=255, because "why not use the whole range"

A team building an order-processing pipeline reasoned that since x-max-priority accepts values up to 255, using the full range would give them "maximum flexibility" to fine-tune ordering later. In practice only about four priority tiers were ever actually assigned to real messages — the other 250-odd declared levels sat permanently empty, still costing memory and still being walked by every dispatch decision on that queue. The team's own load testing eventually attributed a measurable fraction of per-message dispatch latency and per-queue memory overhead directly to the unused priority levels, and the fix was exactly the guidance in §6: collapse to five meaningful tiers, which is what community operational guidance has recommended since priority queues shipped.

Story 3: a retry queue that quietly ate messages instead of retrying them

A team implemented the exact retry-with-backoff topology described in §6 — source queue's DLX pointing at a delay queue with its own TTL and its own DLX pointing back at the source — expecting free, automatic retry-with-backoff. For weeks it appeared to work: messages that failed once were retried once and usually succeeded on the second attempt. The failures that didn't succeed on the second attempt, however, simply disappeared — no error, no dead-letter queue entry, nothing — because the topology had no third destination: every bounce back to the source queue hit cycle detection on the very next automatic dead-lettering attempt, since nothing in the topology ever constituted an explicit consumer requeue to reset the chain. The postmortem's conclusion, once the team read RabbitMQ's cycle-detection documentation closely, was the same one this chapter reaches: an automatic retry-to-source topology needs an explicit, counted escape hatch to a genuinely separate terminal dead-letter queue — the delivery-limit-based route quorum queues offer natively, or a client-side attempt counter — not an assumption that bouncing forever is what "automatic retry" means.

First, the core dead-letter routing decision — choosing the exchange and routing key, and merging the x-death entry for this hop:

Erlangrabbit_dead_letter.erl — routing + x-death merge, simplified
dead_letter(Msg, Reason, SourceQueue) ->
    Args = rabbit_amqqueue:arguments(SourceQueue),
    DLX  = arg(Args, <<"x-dead-letter-exchange">>),
    %% No dlx-routing-key declared? Keep the message's ORIGINAL routing key.
    RK   = case arg(Args, <<"x-dead-letter-routing-key">>) of
             undefined -> Msg#basic_message.routing_keys;
             Explicit         -> [Explicit]
           end,

    Entry = #{queue => SourceQueue, reason => Reason,
              exchange => Msg#basic_message.exchange_name,
              'routing-keys' => Msg#basic_message.routing_keys,
              time => now_ms()},
    XDeath1 = merge_or_increment(Msg#basic_message.x_death, Entry),

    case would_cycle(XDeath1, DLX_target_queue(DLX, RK)) of
        true  -> drop_silently(Msg);         %% §6/§8(c): the cycle-detection rule
        false -> rabbit_exchange:route_and_publish(DLX, RK, Msg#basic_message{x_death = XDeath1})
    end.

Second, the x-death merge rule itself — why a repeated (queue, reason) pair increments rather than appends:

Erlangrabbit_dead_letter.erl — merge_or_increment, simplified
merge_or_increment(XDeath, NewEntry) ->
    Key = {maps:get(queue, NewEntry), maps:get(reason, NewEntry)},
    case lists:keyfind(Key, 1, XDeath) of
        {Key, Existing} ->
            %% same (queue, reason) seen before in this header — bump count, refresh time
            Updated = Existing#{count => maps:get(count, Existing) + 1, time => now_ms()},
            [ {Key, Updated} | lists:keydelete(Key, 1, XDeath) ];
        false ->
            %% genuinely new (queue, reason) pair — a fresh entry, most-recent first
            [ {Key, NewEntry#{count => 1}} | XDeath ]
    end.

Third, the head-of-queue TTL loop — checked on the same process, only ever at the front:

Erlangrabbit_variable_queue.erl — drop_expired, simplified
drop_expired(BQS) ->
    case peek_head(BQS) of
        empty ->
            BQS;
        {value, Msg} when ttl_elapsed(Msg) ->
            %% only the head is ever inspected — O(1) per check, not O(queue depth)
            BQS1 = maybe_dead_letter(Msg, expired, BQS),
            drop_expired(pop_head(BQS1));   %% loop: the NEW head might also already be expired
        {value, _NotExpiredYet} ->
            BQS   %% stop — nothing behind an unexpired head is ever examined
    end.
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Encode the surprising default in the routing step itself, not a comment. The undefined -> original routing keys branch in dead_letter/1 reads, in the source, as the exact behavior operators are surprised by — making the surprise a one-line pattern match rather than buried prose keeps the implementation and the documentation in sync by construction. 2. Key the x-death merge by (queue, reason), not by event. This keeps the header's size bounded by the number of distinct places a message has actually failed, not by how many times it failed there — a direct structural defense against the same unbounded-growth problem cycle detection solves at the routing layer. 3. Make the TTL check recursive on the new head, not a single check per call. A single check-then-stop would leave a backlog of already-expired messages sitting behind a just-removed blocker until the next unrelated trigger happened to call drop_expired again — looping immediately is what produces §15's "they all vanish at once" behavior instead of a slow trickle.
