The 16 theory chapters derive what a "container" actually is: namespaces, cgroups, capabilities, OverlayFS, seccomp, and an OCI spec binding them together. STEP 01 · SETUP

A Linux host, not a laptop VM you can't see inside

Everything here needs a real Linux kernel — WSL2 works, a cloud VM works, a bare-metal box works; Docker Desktop's hidden Linux VM does not, because half this lab is inspecting /proc and /sys/fs/cgroup directly. You need root or sudo, about 1 GB of free disk, and both engines installed side by side — they coexist fine.

util-linux and iproute2 — you likely already have them

unshare and nsenter ship in util-linux, a base-system package on every mainstream distro; ip, bridge, and tc ship in iproute2 (package name iproute on Fedora/RHEL). This lab builds namespaces and networking with these tools directly against the kernel — no Docker Compose, no engine, just the syscalls a container engine itself calls.

bashverify, don't assume
unshare --version   # util-linux 2.3x+
nsenter --version
ip -V               # iproute2

# only if missing:
sudo apt-get install -y util-linux iproute2   # Debian/Ubuntu
sudo dnf install -y util-linux iproute        # Fedora/RHEL/CentOS Stream

Podman — dnf/apt, rootless by default

Podman ships in Debian 11+/Ubuntu 20.10+ and is the default container tool on modern Fedora — no separate daemon, no separate rootless package, nothing extra to enable.

bash
sudo apt-get install -y podman slirp4netns fuse-overlayfs   # Debian/Ubuntu
sudo dnf install -y podman slirp4netns fuse-overlayfs        # Fedora/RHEL

podman info --format '{{.Host.Security.Rootless}}'   # true, as your normal user
podman unshare cat /proc/self/uid_map                # your subuid range mapped in
WHY ROOTLESS PODMAN "JUST WORKS"

Podman is a fork-exec CLI, not a client talking to a root-owned daemon socket (ch.12) — there is no privileged process to grant yourself access to. It needs only your /etc/subuid//etc/subgid ranges, which useradd allocates automatically on most distros. Check with grep "$USER" /etc/subuid /etc/subgid.

Troubleshooting

SYMPTOMCAUSE & FIX
unshare: unshare failed: Operation not permitted on unshare -U Unprivileged user namespaces are disabled. On Debian/Ubuntu check sysctl kernel.unprivileged_userns_clone — set to 1: sudo sysctl -w kernel.unprivileged_userns_clone=1. On Ubuntu 24.04+, AppArmor also restricts this by default; check sysctl kernel.apparmor_restrict_unprivileged_userns. RHEL/Fedora use no such sysctl — they gate it via user.max_user_namespaces, enabled by default.
cgroup v1 vs v2 confusion — memory.max "no such file" You're on v1 or hybrid. Check: cat /sys/fs/cgroup/cgroup.controllers — if that file exists, you're on unified v2 (this lab's assumption). If it doesn't, v1 splits controllers into /sys/fs/cgroup/memory/, /sys/fs/cgroup/cpu/, etc., each with differently-named files (memory.limit_in_bytes, not memory.max). Nearly every current distro defaults to v2; if not, boot with systemd.unified_cgroup_hierarchy=1.
permission denied while trying to connect to the Docker daemon socket Your user isn't in the docker group (rootful Docker) — note that group is root-equivalent, since anyone in it can mount the host filesystem via a container. Prefer the rootless context above where possible.
Rootless Podman: newuidmap: write to uid_map failed: Operation not permitted /etc/subuid//etc/subgid has no entry for your user. Add one: sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 "$USER", then log out and back in.
Rootless networking fails — "slirp4netns not found" or containers can't reach the internet Install slirp4netns (and optionally passt/pasta, its faster successor). Rootless containers cannot own a real bridge interface, so they need a userspace network stack (experiment 16).
Both docker.io and docker-ce installed — apt errors on conflicting files Purge one before installing the other: sudo apt-get purge -y docker.io then install docker-ce. They cannot coexist.
STEP 02 · ORIENTATION

Ten minutes with the raw primitives

Before touching Docker or Podman, see what they're built on. Every command below talks to the kernel directly.

1 · A PID namespace, live

bash
ps aux | wc -l                              # your real process count, probably 100+

sudo unshare --pid --fork --mount-proc bash
ps aux                                       # run this INSIDE the new shell
EXPECTED — inside the namespace, almost nothing exists
USER   PID  %CPU %MEM COMMAND
root     1   0.0  0.1 bash
root    12   0.0  0.1 ps aux

--mount-proc matters: without a fresh /proc mount, ps would still read the host's real /proc and show everything. The namespace only isolates the PID numbering — bash really is PID 1 in here, and it really is PID something-else on the host.

2 · Instant root — -r/--map-root-user

bash
whoami                          # your real, unprivileged user
unshare -U -r whoami            # -U: new user namespace, -r: map current uid to 0 inside
EXPECTED
suraj
root

No sudo was used for the second command. -r writes your real UID to uid_map as the namespace's UID 0 in one step — this is the whole mechanism rootless containers run on (ch.4).

3 · The namespace files under /proc/self/ns

bash
ls -la /proc/self/ns/
readlink /proc/self/ns/pid

sudo unshare --pid --fork --mount-proc bash -c 'readlink /proc/self/ns/pid'
EXPECTED — different inode numbers = different namespaces
lrwxrwxrwx 1 suraj suraj 0 ns/cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 suraj suraj 0 ns/ipc    -> 'ipc:[4026531839]'
lrwxrwxrwx 1 suraj suraj 0 ns/mnt    -> 'mnt:[4026531840]'
lrwxrwxrwx 1 suraj suraj 0 ns/net    -> 'net:[4026531992]'
lrwxrwxrwx 1 suraj suraj 0 ns/pid    -> 'pid:[4026531836]'
lrwxrwxrwx 1 suraj suraj 0 ns/user   -> 'user:[4026531837]'
lrwxrwxrwx 1 suraj suraj 0 ns/uts    -> 'uts:[4026531838]'

pid:[4026531836]     ← your shell's PID namespace
pid:[4026532648]     ← a DIFFERENT inode, inside unshare — a real, separate namespace

The inode number, not a name, is the namespace's identity. Two processes are in the same namespace iff these inodes match — that's exactly what nsenter --target <pid> --pid ... uses to jump into someone else's namespace by PID.

4 · Your cgroup v2 tree

bash
cat /sys/fs/cgroup/cgroup.controllers        # confirms unified v2 and lists available controllers
systemd-cgls                                  # the whole tree, systemd's view
cat /proc/self/cgroup                         # which leaf YOUR shell sits in right now
EXPECTED
cpuset cpu io memory pids          ← controllers this machine supports

Control group /:
-.slice
├─user.slice
│ └─user-1000.slice
│   └─user@1000.service
│     └─app.slice
│       └─vte-spawn-....scope
│         ├─  1234 bash
│         └─  5678 systemd-cgls
├─system.slice
│ ├─docker.service
│ └─podman.service (only if using podman.socket)

0::/user.slice/user-1000.slice/user@1000.service/app.slice/vte-spawn-....scope

Every process on the box is in exactly one cgroup leaf right now, whether or not you ever run a container — systemd itself is built entirely on cgroups. Docker and Podman just create their own subtree and write the same interface files you're about to write by hand in section 3.

5 · Enter a running container's namespaces from outside

This is the move you'll use constantly once containers exist: attach to a live one without docker exec.

bash
docker run -d --name orient alpine sleep 300
PID=$(docker inspect -f '{{.State.Pid}}' orient)
echo "container's PID 1, as seen by the host: $PID"

sudo nsenter --target "$PID" --pid --mount --uts --ipc --net hostname
sudo nsenter --target "$PID" --pid --mount --uts --ipc --net ps aux
EXPECTED
container's PID 1, as seen by the host: 48213
orient
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 300

docker exec and podman exec are just wrappers around exactly this nsenter call — there is no separate "attach" mechanism, only namespace re-entry by PID.

STEP 04 · PRODUCTION BEST PRACTICES

A cookbook where every default has a mechanism behind it

Rootful vs rootless — the decision that matters most

USEWHENMECHANISM
RootlessDefault wherever it's supported. Desktop dev, CI runners, most application workloads. No root-owned daemon to compromise (ch.4, ch.12) — a container breakout lands in an unprivileged user namespace, not on real root. Costs: no real bridge networking (slirp4netns/pasta overhead), sub-1024 ports need net.ipv4.ip_unprivileged_port_start or a cap grant, some storage drivers need fuse-overlayfs instead of native overlayfs.
RootfulKernel-level workloads that need real capabilities host-wide: CNI plugins configuring host networking, storage drivers needing native OverlayFS performance, some CSI-style volume plugins. Full capability set is available to drop from selectively. On Docker this is the historical default; on Podman it's an explicit choice (sudo podman run ...).
Neither — use a Kubernetes node's CRI-O/containerdProduction Kubernetes. Nodes don't run "Docker" or "Podman" as the workload runtime at all (ch.9, ch.12) — kubelet talks CRI to containerd or CRI-O, which call runc/crun directly. Podman and Buildah remain useful there only as build tools.

Capability-dropping checklist by workload

WORKLOADCAPS IT ACTUALLY NEEDS
Stateless API / web app, no privileged portnone — --cap-drop=ALL with no adds. This should be most of your fleet.
Web server binding <1024 as non-root insideNET_BIND_SERVICE only. (Better: bind ≥1024 inside and publish/remap the port instead.)
Database (Postgres/MySQL) fixing data-dir ownership on first bootCHOWN, FOWNER transiently; drop them after the entrypoint's chown step if you can split it into an init container.
ICMP ping / basic network diagnosticsNET_RAW — or better, unprivileged ping via net.ipv4.ping_group_range on the host, needing no capability at all.
VPN client, custom routing, tc shapingNET_ADMIN (+ NET_RAW usually).
Nested container builds ("Docker-in-Docker")avoid --privileged entirely — use rootless nested Podman/Buildah instead, which needs no elevated caps at all.
Anything claiming it needs SYS_ADMINnearly always wrong — CAP_SYS_ADMIN covers dozens of unrelated privileged operations (mount, some ioctls, keyring management) and is close to full root. Find the specific narrower capability instead.

Both engines already start from a reduced default — not "all ~40 capabilities minus a few," but roughly 14: CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, SETGID, SETUID, SETPCAP, SETFCAP, NET_BIND_SERVICE, NET_RAW, SYS_CHROOT, MKNOD, AUDIT_WRITE. --cap-drop=ALL starts from zero and is stricter still.

cgroup limits — memory.max vs memory.high

FILEBEHAVIOURUSE FOR
memory.maxHard ceiling. Crossing it invokes the OOM killer against the cgroup — the process dies, no warning.The absolute limit you never want exceeded — treat it as the blast-radius boundary, not the tuning target.
memory.highSoft ceiling. Crossing it throttles the cgroup hard via reclaim/stalling — the process slows down instead of dying, as long as it can free memory.Set 10–20% below memory.max to give the workload a chance to shed memory (GC, cache eviction) before the hard kill. This is the headroom production should always configure.
memory.eventsRead-only counters: low, high, max, oom, oom_kill.Alerting — a rising oom_kill counter on a cgroup that never hard-restarted means the app is catching SIGKILL for a child and self-healing; don't miss it just because the container looks fine.

Docker vs Podman — by deployment context

CONTEXTPICKWHY
Desktop devEither — Podman if you want rootless-by-default and no background daemonDocker's daemon runs whether or not you're using it; Podman's fork-exec model has no idle process at all (ch.12).
CI runners (ephemeral, one job per VM)Podman, or rootless DockerNo shared root daemon between jobs to leak state across builds; rootless is a natural sandboxing boundary for untrusted job code.
systemd-managed services on a hostPodmanpodman generate systemd / native Quadlet unit files integrate a container directly into systemctl — restart policy, dependency ordering, and logs all become systemd's job, with no daemon supervising a supervisor (ch.14).
Kubernetes worker nodesNeither, directlyThe kubelet speaks CRI to containerd or CRI-O. Podman/Buildah are still common as the image-build tool in CI pipelines that produce what the cluster runs.
Long-running orchestration platform needing one stable API socket for many clientsDockerA single long-lived daemon genuinely is the right shape when many unrelated processes need to share one container-management API (ch.12) — the daemon isn't wrong, it's a trade-off that fits multi-tenant tooling better than single-user CLIs.

Anti-patterns and their specific damage

ANTI-PATTERNWHAT IT COSTS
--privilegedworst offender Grants every capability, disables the default seccomp and AppArmor/SELinux confinement, and exposes host devices — a breakout from this is a full host compromise, not a contained one (ch.7, ch.8). Almost nothing that seems to need it actually needs all of it; find the one or two specific capabilities instead.
Pulling :latest in productionThe tag is a mutable pointer (experiment 14) — the same deploy command can silently pull different bytes tomorrow. Pin by digest for anything that must be reproducible.
Baking secrets into an image layerA layer is a permanent, content-addressed blob (ch.10) — deleting the file in a later layer hides it from the final filesystem but the secret is still sitting in the earlier layer's blob in the registry, retrievable by anyone who can pull it.
Running the container's main process as root with no USER instructionCombined with a container breakout, this hands the attacker uid 0 immediately. Costs nothing to avoid: set USER in the image, or --user at run time.
Bind-mounting /var/run/docker.sock into a containerEquivalent to giving that container root on the host — the Docker socket has no fine-grained authorization, only "can talk to it at all" (ch.12). This is the single most common way a "just one container" compromise becomes a host compromise.
Mixing rootful-created volumes with rootless containersFiles created by a rootful container are host-uid-owned; a rootless container's mapped uid range usually can't write them. Fix ownership explicitly with podman unshare chown (runbook 5.3) rather than guessing at permissions.
No memory.max at allAn unbounded container can pressure the whole host's memory and trigger the SYSTEM-WIDE oom killer, which picks a victim by heuristic — possibly an unrelated process, not the misbehaving container (ch.5). Always set a limit.
Treating docker inspect's CapAdd/CapDrop as the effective capability setIt's only the delta you specified, not the resolved set after defaults are applied (runbook 5.2). Read /proc/<pid>/status or Podman's .EffectiveCaps for the real answer.

STEP 05 · OPERATIONAL RUNBOOKS

  
Procedures for when a container is already misbehaving


  
5.1 · Diagnosing an OOM-killed container

  
Precondition: you can read host dmesg/journalctl — this is a host-level kernel event, not something the container's own logs will ever show.

  
    
    
  1. Confirm from the engine first: docker inspect <ctr> --format '{{.State.OOMKilled}}' or podman inspect <ctr> --format '{{.State.OOMKilled}}'. true confirms the cgroup OOM killer fired, not a normal exit.
    2. 
    
  2. Find the exact cgroup and process from the kernel log: sudo dmesg -T | grep -i "killed process" or sudo journalctl -k | grep -iE "oom|killed process" — the line names the exact PID, process, and cgroup path.
    3. 
    
  3. Read the cgroup's own counter to see how many times, not just the last time: cat /sys/fs/cgroup/<path-from-dmesg>/memory.events | grep oom_kill.
    4. 
    
  4. Check what limit was actually set: cat .../memory.max vs the peak usage right before the kill, cat .../memory.peak if your kernel exposes it.
    5. 
    
  5. Fix direction: if usage was near but under a reasonable limit, look for a leak or an unbounded cache inside the app before raising the limit — raising memory.max without understanding growth just delays the same incident.
    6. 
  


  
5.2 · Auditing what capabilities a running container actually has

  
    
    
  1. What was requested: docker inspect <ctr> --format '{{.HostConfig.CapAdd}} {{.HostConfig.CapDrop}}' — this shows only the delta from default, not the effective set.
    2. 
    
  2. Podman gives you the effective set directly: podman inspect <ctr> --format '{{.EffectiveCaps}}'.
    3. 
    
  3. For Docker, or to double-check Podman, read the kernel's own view of the running process: sudo cat /proc/$(docker inspect -f '{{.State.Pid}}' <ctr>)/status | grep ^Cap.
    4. 
    
  4. Decode the hex bitmask into names: capsh --decode=00000000a80425fb.
    5. 
    
  5. Compare CapEff (effective) against CapBnd (bounding). A capability absent from CapBnd cannot be regained even via setcap inside the container — that's the real ceiling, stronger than whatever the app process currently holds in CapEff.
    6. 
  


  
5.3 · Migrating a rootful Docker workload to rootless Podman

  
Precondition: inventory every bind mount, published port, and volume ownership assumption before starting — most migration pain is UID mapping, not the container runtime itself.

  
    
    
  1. List what the rootful workload actually touches: docker inspect <ctr> --format '{{json .Mounts}} {{json .HostConfig.PortBindings}}'.
    2. 
    
  2. Flag ports <1024. Rootless can't bind them directly — either remap to ≥1024 and let a host-level proxy forward, or set sudo sysctl net.ipv4.ip_unprivileged_port_start=80 host-wide.
    3. 
    
  3. Fix volume ownership. Files owned by host UID 0 are invisible as writable to a rootless container's mapped UID range. Use podman unshare chown -R 0:0 ./data — run inside Podman's own user-namespace shell so the chown lands correctly on the mapped IDs.
    4. 
    
  4. Translate the run command — most flags are identical (-v, -p, -e, --cap-add); drop sudo.
    5. 
    
  5. Generate a systemd unit for production instead of a bare podman run: podman generate systemd --new --name mytest > ~/.config/containers/systemd/mytest.container-style Quadlet, or the legacy .service form, then systemctl --user daemon-reload && systemctl --user enable --now mytest.
    6. 
    
  6. Verify with loginctl enable-linger $USER so the rootless service keeps running after you log out — without it, the user's systemd instance (and everything in it) stops at logout.
    7. 
  


  
5.4 · Debugging a container that can't reach the network

  
Walk the chain in order — netns → veth → bridge → iptables/nftables. Stop at the first broken hop.

  
    
    
  1. Inside the container's namespace, does it even have an address? nsenter --target $(docker inspect -f '{{.State.Pid}}' <ctr>) --net ip addr and ip route. No address or no default route stops here.
    2. 
    
  2. Find its veth peer on the host: nsenter ... --net cat /sys/class/net/eth0/iflink gives the peer's host-side ifindex; match it with ip link | grep ^<ifindex>:.
    3. 
    
  3. Is that veth peer actually enslaved to the bridge? bridge link show — it should list the veth with master docker0 (or Podman's podman0/netavark bridge).
    4. 
    
  4. Is the bridge itself up with an IP and forwarding enabled? ip addr show docker0, and sysctl net.ipv4.ip_forward must be 1.
    5. 
    
  5. For outbound/NAT failures, check the NAT table: sudo iptables -t nat -L POSTROUTING -n (or nft list ruleset on nftables-based hosts) — a missing MASQUERADE rule for the bridge subnet is the classic silent failure after a firewall reload wipes Docker's/Podman's chains.
    6. 
    
  6. Rootless specifically: if there's no real bridge/veth at all, you're on slirp4netns/pasta — check its own process is alive (ps aux | grep slirp4netns) rather than looking for kernel-level networking that was never created.
    7. 
  


  
5.5 · Cleaning up orphaned namespaces and cgroups after an engine crash

  
Precondition: the engine (dockerd, or a podman-managed conmon) died or was force-killed mid-run, leaving kernel state behind that the engine no longer tracks.

  
    
    
  1. Find leaked network namespaces: ip netns list — engines occasionally leave a netns behind with no owning process. Cross-check against docker ps -a/podman ps -a; anything not accounted for is orphaned.
    2. 
    
  2. Find leaked cgroup leaves with no live process: find /sys/fs/cgroup -name cgroup.procs -empty lists empty leaves — an empty, otherwise-unreferenced directory under the engine's own cgroup slice is safe to rmdir (cgroup directories can only be removed when empty and unpopulated).
    3. 
    
  3. Don't delete a namespace or cgroup that still has a live PID in it — confirm with ip netns pids <name> or by reading cgroup.procs before removing anything.
    4. 
    
  4. Restart the engine before deep cleanup, not after — a fresh dockerd/podman system service often reconciles and removes what it recognizes as its own leaked state automatically, which is safer than manual deletion.
    5. 
    
  5. Last resort: docker system prune / podman system prune to reclaim unused images, networks, and stopped containers in one pass — read the confirmation prompt, this is destructive.
    6. 
  


  
5.6 · Verifying an image before you run it

  
    
    
  1. Never trust a tag alone. Resolve it to a digest first: docker inspect --format '{{index .RepoDigests 0}}' <image> or skopeo inspect docker://<image> before pulling into anything sensitive.
    2. 
    
  2. Check the manifest's platform and layer list for anything unexpected: docker manifest inspect <image> — a surprising extra layer at the end of an otherwise-familiar image is worth investigating before running it.
    3. 
    
  3. Verify a signature if the publisher provides one: cosign verify --key <pubkey> <image>@<digest>, or Podman's native podman image trust / --sign-by flow, which enforces a signature policy at pull time rather than as a manual side-check.
    4. 
    
  4. Pin the digest in whatever deploys it — a Compose file, a Podman Quadlet, or a Kubernetes manifest — so the exact bytes verified are the exact bytes that run, immune to a tag being repointed later.
    5. 
  







  
STEP 06 · GUIDED BUILD PROJECTS

  
Three runtimes, in increasing order of "real"


  
Project 1 · A ~100-line container launcher: unshare + cgroups + chroot

  
No pivot_root yet, no images — just enough to run one isolated, memory-bounded process. Root or sudo required.

  
bashminibox.sh — starter skeleton


#!/usr/bin/env bash
set -euo pipefail
NAME="$1"; ROOTFS="$2"; MEM_MAX="$3"; shift 3

CG="/sys/fs/cgroup/minibox-$NAME"
sudo mkdir -p "$CG"
echo "$MEM_MAX" | sudo tee "$CG/memory.max" > /dev/null

sudo unshare --pid --mount --uts --ipc --fork --mount-proc --map-root-user -- bash -c '
  echo $$ > "'"$CG"'/cgroup.procs"
  hostname "'"$NAME"'"
  mount --bind "'"$ROOTFS"'" "'"$ROOTFS"'"
  cd "'"$ROOTFS"'"
  mount -t proc proc proc
  exec chroot . "$@"
' -- "$@"

  
bashtry it


mkdir -p /tmp/box && docker export $(docker create alpine) | tar -x -C /tmp/box
chmod +x minibox.sh
sudo ./minibox.sh test1 /tmp/box 50M /bin/sh

# from another terminal, while it's running:
cat /sys/fs/cgroup/minibox-test1/memory.current
cat /sys/fs/cgroup/minibox-test1/cgroup.procs

  
What proves this works: hostname inside shows test1 while the host's is
  unchanged; ps inside sees only its own tree; running yes | tr \\n x | head -c 100000000 > /dev/null
  inside gets SIGKILLed the moment memory.current would cross 50 MB — confirm with
  dmesg | grep -i "killed process" naming your cgroup path.

  
Extensions: add a pids.max write alongside memory.max and prove a
  fork-bomb inside the box dies with EAGAIN on fork() instead of taking down the host;
  add a second invocation with a different NAME and confirm the two boxes' cgroups and PID
  namespaces are fully independent of each other.


  
Project 2 · Upgrade to real pivot_root and capability dropping

  
chroot is escapable (experiment 1); pivot_root isn't, because it moves the old
  root out of the mount namespace entirely rather than merely changing a path prefix. There's no shell builtin
  for the syscall, so this needs a small C helper.

  
cpivot.c — starter skeleton


#define _GNU_SOURCE
#include <sys/mount.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: pivot NEWROOT -- CMD...\n"); return 1; }
    char *new_root = argv[1];

    // a mount point must be a mount point — bind it to itself
    if (mount(new_root, new_root, NULL, MS_BIND | MS_REC, NULL)) { perror("bind"); return 1; }

    char old_put[256];
    snprintf(old_put, sizeof(old_put), "%s/.oldroot", new_root);
    mkdir(old_put, 0700);

    if (chdir(new_root)) { perror("chdir"); return 1; }
    // syscall(), not a glibc wrapper: pivot_root(2) has none on many toolchains
    if (syscall(SYS_pivot_root, ".", ".oldroot")) { perror("pivot_root"); return 1; }
    if (chdir("/")) { perror("chdir /"); return 1; }

    umount2("/.oldroot", MNT_DETACH);   // detach lazily, then it's gone
    rmdir("/.oldroot");

    execvp(argv[3], &argv[3]);           // argv[2] is "--"
    perror("exec");
    return 1;
}

A minimal seccomp-bpf filter via libseccomp, then the exact same workload run three ways.

  
cseccomp_filter.c — starter skeleton


#include <seccomp.h>
#include <unistd.h>
#include <stdio.h>

int main(int argc, char **argv) {
    // default-allow, deny a specific handful — invert this (default-deny,
    // allow a short list) for anything resembling a production profile
    scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_ALLOW);

    int denied[] = { SCMP_SYS(mount), SCMP_SYS(reboot), SCMP_SYS(ptrace) };
    for (unsigned i = 0; i < sizeof(denied)/sizeof(*denied); i++)
        seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), denied[i], 0);

    seccomp_load(ctx);       // filter is now active — no going back for this process
    execvp(argv[1], &argv[1]);
    perror("exec");
    return 1;
}
