ARC 01 · THE PROBLEM

A cluster in trouble is a cluster you must explain, not just restart

Every subsystem in this course fails eventually, in production, at the worst time. A follower falls out of the ISR (chapter 5). A consumer group thrashes through rebalance after rebalance (chapter 7). A log directory fills up faster than compaction can reclaim it (chapters 10–11). A broker's request-handler pool saturates under load it was sized for six months ago (chapter 13). The question this chapter answers is not "what can go wrong" — you already know that in exhaustive detail — it is: given a cluster that is slow or unavailable right now, with no prior hypothesis, how do you find the true root cause in minutes instead of hours?

The instinctive answer in most organizations is a runbook: check CPU, check disk, check consumer lag, bounce the broker, bump the heap, page someone senior. Runbooks feel productive because they generate action. They are also, structurally, guessing — a sequence of commands and folklore fixes assembled from past incidents, applied without a model of why this cluster is unhealthy this time. Two incidents with an identical top-line symptom — say, produce-request p99 latency spiking from 8 ms to 900 ms — can have completely unrelated root causes: a GC pause starving the request-handler thread pool (chapters 2 and 13), a slow disk stalling the local log append (chapter 10), or a follower falling behind and stretching the replication fan-out wait on an acks=all produce (chapter 5). A runbook has no way to distinguish these; it just runs down a list and hopes something matches.

This chapter's thesis, stated once so you can hold it for every section that follows: diagnosis starts from the metric taxonomy that instruments the internals, not from a list of commands. Every broker exposes, via JMX, a set of counters and gauges that map — deliberately, by design — onto the exact mechanisms chapters 2, 5, 7, 10, 11, and 13 built. UnderReplicatedPartitions is not an abstract health score; it is ReplicaManager reporting the literal size of an ISR set you studied in chapter 5. RequestHandlerAvgIdlePercent is not "CPU usage"; it is the exact thread pool from chapter 2's network layer telling you how saturated it is. Once you can read the taxonomy this way, an incident stops being a mystery and becomes a lookup.

THE METHOD IN ONE SENTENCE

Find which metric is abnormal → identify which chapter's mechanism produces that metric → read that subsystem's broker logs / CLI tooling to confirm the hypothesis → apply the fix that subsystem's own design predicts will work → verify the metric recovers, because your model — not the incident — is what's on trial.

DEEP CONTEXT · WHY KRAFT MATTERS TO THIS CHAPTER SPECIFICALLY

KIP-500's removal of the ZooKeeper dependency is not a footnote for an incident-response chapter — it eliminated an entire historical failure class. Under the old design, controller election was a race for a ZooKeeper ephemeral znode, and a GC pause or network blip on the controller broker could, in narrow windows, produce ambiguity about who was really in charge while the old controller's session hadn't yet expired. Under KRaft, ActiveControllerCount reflects Raft quorum leadership — a majority-committed log, not a lock — which makes split-brain on the control plane architecturally prevented rather than merely rare. You will use this distinction directly in §7's metric taxonomy.

ARC 03 · NAIVE SOLUTION

Attempt #1: the checklist runbook

Derive the naive approach honestly, the way §3 always does in this course. Faced with "the pipeline is falling behind," most teams reach for a runbook: a fixed sequence of checks and remediations, executed top to bottom regardless of what the first few checks actually found.

bashrunbook.sh — the strawman, annotated
#!/bin/bash
# "producer errors are spiking" — standard runbook, step 1 of 9
kafka-topics.sh --bootstrap-server $BS --describe --under-replicated-partitions
top -bn1 | head -20                      # eyeball CPU% — but WHICH thread pool is saturated?
iostat -x 1 5                                # eyeball disk %util — checkpoint-style write, or a cold read?
kafka-consumer-groups.sh --bootstrap-server $BS --describe --group orders-consumer
jstat -gcutil $(pgrep -f kafka.Kafka) 1000 5  # eyeball GC — is this even the affected broker?
# nothing conclusive → apply folklore fixes, in order, hoping one sticks:
# "more memory can't hurt" — a blog post, wrong subsystem
export KAFKA_HEAP_OPTS="-Xmx16G -Xms16G"
systemctl restart kafka                      # "turn it off and on again" — no controlled shutdown wait
kafka-leader-election.sh --bootstrap-server $BS --election-type preferred --all-topic-partitions
# if still broken: page whoever wrote the replication chapter of this course

This is not stupidity — it is where every engineer starts, and several of its steps are legitimately useful as evidence: under-replicated-partition counts, disk %util, consumer lag, and GC stats are all real signals. The naive approach's flaw is not "checking the wrong things." It's that it treats every check as independent and every fix as low-risk, running down a fixed list instead of forming and testing a hypothesis about which of chapters 2, 5, 7, 10, 11, or 13's mechanisms is the actual bottleneck — and, as §4 shows, several of those "harmless" fixes are not harmless at all.

ARC 04 · WHY IT FAILS

Checklists don't distinguish causes, and naive fixes compound them

Three concrete failure modes, each one costing real incident time:

  • Identical symptoms, unrelated causes. "Produce p99 spiked 100×" is consistent with at least four internally unrelated conditions: a G1 stop-the-world pause starving the request-handler pool (chapters 2/13), a slow disk stalling LogSegment.append() (chapter 10), an ISR shrink stretching the acks=all replication-fan-out wait (chapter 5), or a quota throttling a noisy client on purpose (chapter 13). A checklist that says "check CPU" cannot tell these apart — it needs the per-request latency breakdown built in §8.
  • Fixes applied without a mechanism make things worse. Bumping KAFKA_HEAP_OPTS to "give Kafka more memory" directly fights chapter 10's design bet — Kafka relies on the OS page cache, not the JVM heap, for the hot read/write path. A larger heap means longer G1 pauses, which is likely to worsen exactly the ISR-flapping failure mode from postmortem 1 in §11, not fix it. A naive systemctl restart without waiting for controlled.shutdown.enable's graceful leadership handoff forces the controller into emergency elections under duress — the opposite of the safe rolling-restart procedure §11 teaches.
  • Checklists don't compose across incidents. A runbook tuned for last quarter's incident (a rebalance storm) gets applied to this quarter's incident (a disk-full cascade) because the symptom — "consumers are falling behind" — looks superficially similar, and half the runbook's steps (heap bumps, preferred-leader elections) are simply irrelevant to a full disk, burning minutes an urgent incident does not have.
THE NUMBERS: A NAIVE RESTART STORM, QUANTIFIED

Consider a 20-broker cluster with 50,000 partitions (2,500 per broker on average). An operator, unsure what's wrong, SIGKILLs one broker instead of using a controlled shutdown. Failure detection under KRaft's broker.session.timeout.ms (default 9s pre-3.x tuning, commonly configured ~9–18s) must elapse before the controller acts; then it must elect new leaders for every partition that broker led — commonly a few thousand partitions on a broker this size — a serial-ish metadata operation the controller processes at a bounded rate. Even at an optimistic few thousand elections per second, that is real, measurable seconds of OfflinePartitionsCount > 0 for those partitions: producers with acks=all blocked, consumers stalled. A controlled shutdown moves leadership for every partition on that broker before the process exits — the same broker leaving the cluster produces a fraction of the unavailability window, because the expensive part (electing N new leaders) happened proactively instead of reactively under a failure-detection timeout.

So — analogous to every other chapter's arc — we need something better than "check things in order and hope." The candidates, examined next, all point toward the same conclusion: start from where the specific mechanism is instrumented, not from a generic system-health dashboard.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates, each necessary and each insufficient alone

Before arriving at the metric-taxonomy method, it's worth taking seriously the tools operators reach for next, because each one really does help — just not on its own.

Candidate diagnostic strategiesSTEP-BY-STEP

Candidate A: watch the OS graphs (CPU / RAM / disk / NIC)

Node-level dashboards tell you the machine is busy. They cannot tell you which broker subsystem is consuming that busyness. 90% disk utilization could be the log-flush path (chapter 10), replica-fetcher catch-up reads after a restart (chapter 5), or log-cleaner I/O during compaction (chapter 11) — three different fixes, one graph. High CPU is worse: the kernel scheduler doesn't distinguish a request-handler thread doing genuine decompression work from one blocked moments away from a page-cache fault. Necessary context, insufficient resolution.

Candidate B: read the broker logs

Broker logs surface exactly what was logged — ISR shrink/expand events, controller state transitions, log-dir failures — and nothing you didn't anticipate. They are excellent for confirming a hypothesis (a "Shrinking ISR" line is unambiguous) but useless for forming one when the incident manifests purely as elevated latency with no ERROR/WARN lines at all — a saturated but functioning request-handler pool logs nothing, because nothing is technically wrong yet. Necessary for confirmation, blind to systemic saturation.

Candidate C: client-side / application metrics

Producer and consumer client metrics (request-latency-avg, records-lag-max) tell you the application's experience is bad. They cannot distinguish "the broker is genuinely slow" from "my producer's acks=all request is waiting on a slow follower" from "I'm being throttled by a quota on purpose" (chapter 13) — three completely different remediations, one client-side latency number. Necessary for detecting user impact, blind to the broker-side mechanism.

WHAT ALL THREE ARE MISSING

None of the three localizes a bottleneck to a specific broker subsystem. That is precisely what the per-stage JMX request metrics and subsystem gauges do — the missing layer between "the machine looks busy" (Candidate A) and "the client sees latency" (Candidate C). §7 builds that map explicitly.

ARC 06 · WHY THAT STILL FAILS / COSTS

The bill for skipping the metric-taxonomy layer

Even armed with OS graphs, broker logs, and client metrics, an operator without the taxonomy habit pays a specific, recurring cost: they can narrow a problem to "the cluster," and even to "this topic," but not to "this subsystem" — the resolution a real fix requires. These are all real, commonly seen, and indistinguishable without the right JMX bean:

  • "CPU is high but no broker log line explains it." Could be a request-handler pool doing legitimate compression/decompression work at high throughput, could be a GC pause pattern eating CPU in stop-the-world cycles (chapter 13), could be a client sending oversized batches. Only RequestHandlerAvgIdlePercent plus a per-stage latency breakdown (§8) tells them apart.
  • "Every partition on this broker slowed down at once." Classic signature of either a GC pause (chapter 13, and this chapter's postmortem 1) or a saturated request queue (chapter 2) — both produce a simultaneous, broker-wide slowdown, and engineers under pressure often guess wrong and bump num.replica.fetchers (irrelevant to both) before checking RequestQueueTimeMs or a GC log.
  • "Consumer lag keeps climbing and adding consumers isn't helping." Without checking whether the group is stuck in PreparingRebalance/CompletingRebalance (chapter 7), this reads as "we need more consumers" and gets over-provisioned — which does nothing if the real problem is a rebalance storm where added consumers just enlarge the group that has to re-converge on every eviction (postmortem 2, §11).

Each of these costs the same thing: minutes to hours applying plausible-sounding fixes that cannot possibly work, because the fix was chosen from the symptom rather than derived from the mechanism. The final architecture closes this gap by making the metric taxonomy the FIRST thing you look at, not the last.

ARC 08 · INTERNAL IMPLEMENTATION

Where the four latency stages actually come from, and how ISR shrink really triggers

Two mechanisms deserve a full derivation, because nearly every incident in §11 reduces to one of them: (a) exactly what a produce request's four latency stages measure inside KafkaApis, and (b) the exact arithmetic that turns a slow follower into an ISR shrink.

(a) A produce request's life, stage by stage

WHY FOUR SEPARATE STAGES, NOT ONE "REQUEST LATENCY" NUMBER

Because each stage is owned by a different subsystem with a different fix. Queue time is purely thread-pool sizing (chapter 2) — add num.io.threads or reduce per-request cost. Local time is disk/page-cache health (chapter 10) — a storage problem, not a Kafka bug. Remote time is follower replication health (chapter 5) — an ISR/network problem on some OTHER broker. Throttle time is deliberate policy (chapter 13's quotas) — not a health signal at all. Collapsing these into one number is precisely what makes the naive checklist from §3 unable to route the incident to the right owner.

(b) ISR shrink: the exact threshold arithmetic

Partition.maybeShrinkIsr() (chapter 5) removes a follower from the ISR when that follower's lastCaughtUpTimeMs — the last time it had fully caught up to the leader's log-end-offset — is older than now − replica.lag.time.max.ms. A GC pause on the follower (or the leader — either can stall the fetch/response cycle) directly feeds this clock. ARC 10 · PERFORMANCE CHARACTERISTICS

The numbers a diagnosis should already predict

Performance framing applied to diagnosis, not benchmarking — the same physics chapter 13 taught you to design for is what tells you, before you page anyone, roughly where a symptom's ceiling should sit:

  • Offset lookup is O(log n) then a bounded scan. Finding a record by offset means a binary search over a segment's sparse offset index (chapter 10), then a short linear scan within the located batch — not a full segment scan. If a "slow consumer" incident shows fetch latency scaling with segment count rather than staying flat, the index itself is suspect, not generic "disk is slow."
  • Sequential fetch is effectively O(1) per record via zero-copy. sendfile() moves bytes from the page cache straight to the socket buffer with no userspace copy and no per-record broker-side deserialization in the common case. This is why a healthy broker's heap stays small (chapter 13's ~6 GB guidance) — the hot path barely touches it, which is exactly why bumping heap size to "fix" a throughput incident is usually fighting the architecture, not helping it.
  • Sequential-append disks turn random past a partition-density limit. Many partitions sharing one disk still look sequential per-partition up to a point (chapter 10); past that point the device sees an interleaved, effectively random write pattern. This is precisely why partition-count-per-broker/per-disk limits exist (chapter 13) — and why "just add more partitions" is a common root cause disguised as a capacity fix.
  • The NIC throughput budget is arithmetic, not a graph you stare at. Every produced byte leaves the NIC again (replicationFactor − 1) times for followers, plus once per active consumer group reading it. BytesInPerSec × replicationFactor + BytesOutPerSec(consumers) approaching NIC capacity predicts a throughput ceiling before you hit it (chapter 13) — the interactive chart below makes this concrete.
  • GC pause distribution sets your latency floor. No amount of thread-pool or disk tuning beats a broker that periodically stops for hundreds of milliseconds to seconds (chapter 13) — and as postmortem 1 shows, it does far more damage than local latency: it can eject the broker from other partitions' ISRs entirely.

ARC 11 · REAL-WORLD PRODUCTION

Four postmortems, each traced to a chapter you already know

Every postmortem below follows the same shape — symptom, investigation, root cause in internals, immediate fix, prevention — because that shape is the method from §1, applied for real.

Postmortem 1: ISR flapping from GC pauses

Symptom. Intermittent NotEnoughReplicasException on a handful of partitions, correlated with nothing obvious in application logs. UnderReplicatedPartitions oscillates rather than staying at zero or climbing steadily — partitions drop out of ISR and rejoin minutes later, repeatedly.

Investigation. Cross-referencing UnderReplicatedPartitions spikes against per-broker GC logs shows an exact timestamp correlation: every ISR shrink coincides with a multi-second G1 stop-the-world pause on one specific broker. That broker was recently given a larger heap "to be safe."

Root cause in internals. During the pause, the broker cannot service fetch requests — as a follower, it misses the leader's fetch deadline, so the leader's Partition.maybeShrinkIsr() (chapter 5) evicts it once lastCaughtUpTimeMs exceeds replica.lag.time.max.ms; as a leader for other partitions, its own followers can't get timely fetch responses either, and its ISRs shrink from the other side. Once ISR size drops below min.insync.replicas, acks=all produces are rejected. The heap increase directly fights chapter 10's design bet — Kafka relies on the page cache, not the heap, for the data path — so a broker with a bloated heap is fighting its own architecture, and a bigger heap under G1 means longer worst-case pauses, not fewer.

Immediate fix. Reduce heap back toward chapter 13's ~6 GB guidance, and tune G1 for a realistic MaxGCPauseMillis target rather than an aspirational one; monitor GC pause p99 alongside UnderReplicatedPartitions until the correlation disappears.

Prevention. Heap-size and GC alerting tied directly to ISR metrics (not just raw pause duration), and a standing rule: never resize the heap without re-reading chapter 13's sizing math first.

Postmortem 2: the rebalance storm

Symptom. Consumer lag climbs steadily on one group despite the team adding consumers; the group's state in kafka-consumer-groups.sh --describe flickers between Stable and PreparingRebalance.

Investigation. Coordinator logs show a repeating pattern: "Attempt to heartbeat failed since group is rebalancing" followed shortly by "member ... left the group" for a rotating cast of members, not the same one twice.

Root cause in internals. A downstream dependency (the database the consumer writes to) slowed down. Total time to process a max.poll.records-sized batch started exceeding max.poll.interval.ms. This is specifically not a session-timeout/heartbeat-thread problem — the heartbeat thread runs independently and keeps reporting the member alive — it is the GroupCoordinator enforcing the processing-time-vs-poll-interval contract (chapter 7): if a member hasn't called poll() again within max.poll.interval.ms, it is presumed stuck and evicted regardless of heartbeats. That eviction triggers a rebalance; under the legacy eager protocol every consumer in the group stops consuming for the duration of the rebalance, which grows the backlog every other consumer must catch up on afterward — making them, too, more likely to miss their own poll interval on the next round. One slow batch cascades into a self-sustaining storm.

Immediate fix. Lower max.poll.records so a batch's total processing time reliably fits inside max.poll.interval.ms even during a downstream slowdown.

Prevention. Adopt cooperative rebalancing (cooperative-sticky assignor, KIP-429) so only the revoked partitions pause, not the whole group; adopt static membership (group.instance.id) so rolling restarts don't trigger a rebalance at all (chapter 7). Both changes shrink the blast radius of the same underlying eviction instead of trying to prevent every possible downstream slowdown.

Postmortem 3: unclean leader election data loss

Symptom. A rack loses power, taking every in-sync replica down except one — and that survivor becomes briefly unavailable too, leaving only an out-of-ISR replica reachable. Minutes later, consumers report reading data that "disappears" on the next fetch from a different offset than expected.

Investigation. Controller logs show "Shrinking ISR ... to [1]" followed by broker 1 going unreachable, then, with unclean.leader.election.enable=true, a line naming a replica that was not in the last known ISR as the new leader.

Root cause in internals. With no in-sync replica reachable, the controller faced a binary choice: leave the partition offline until an ISR member returns (data safe, unavailable), or promote a known-stale replica (available, unsafe). unclean.leader.election.enable=true chose availability. Concretely: any offset committed to the old leader beyond what the promoted stale replica had actually replicated is gone — it existed on disk on the dead leader and nowhere else. Consumers that had already read those offsets read data that no longer exists on any replica; the log has effectively rewound underneath them. Leader epochs (KIP-101, chapter 5) ensure the followers that reattach later truncate consistently to the new leader's history — they prevent silent divergence — but they do not prevent the loss itself; that is a durability-vs-availability policy decision, not a bug leader epochs are meant to fix.

Immediate fix. Halt producers writing to the affected topic, audit which consumer offsets are now ahead of the promoted leader's log-end-offset, and treat every one of those offsets as lost — there is no reconstruction path once the old leader's disk is gone.

Prevention. Set unclean.leader.election.enable=false: the partition simply stays unavailable until an actual in-sync replica returns, trading availability for zero silent data loss. Pair this with acks=all and a min.insync.replicas ≥ 2 on the producer side (chapter 5's durability model) so that "committed" genuinely means "durable on more than one replica" before this scenario can even begin.

Postmortem 4: disk-full cascade

Symptom. One broker's disk usage climbs steadily toward 100%; shortly after, a burst of partitions across several other brokers go under-replicated, and overall cluster latency degrades broadly.

Investigation. The broker's own logs show "Log directory ... is offline due to IOException: No space left on device"; kafka-topics.sh --describe shows every partition that had a replica in that directory now missing that replica from its ISR (or missing a leader entirely if it was the leader there).

Root cause in internals. Two possible upstream causes converge on the same failure: retention misconfigured relative to actual volume (retention.bytes/retention.ms too generous for the disk provisioned), or — on a compacted topic — the log cleaner falling behind. Chapter 11's dedupe-buffer problem is exactly this: the cleaner's offset map (sized by log.cleaner.dedupe.buffer.size) can be too small for the number of distinct keys in a segment, forcing multiple cleaning passes and letting obsolete records accumulate instead of being reclaimed. Either way, the log directory fills, and rather than crash the whole process, the broker's LogDirFailureHandler takes that one directory offline. Every partition whose replica lived there goes under-replicated (or loses its leader if it led there); leadership for those partitions shifts to other brokers, concentrating load — and, if those brokers were already near their own disk ceiling, their disks now fill faster too. One full disk becomes a spreading failure.

Immediate fix. Identify the actual blocker — expired segments not deleting because of a retention misconfiguration, or a cleaner stuck behind an undersized dedupe buffer — free space, restart the affected log directory, and let the rebalanced replicas re-sync via chapter 5's normal fetch-and-catch-up mechanics.

Prevention. Per-broker disk-usage alerting well before 100% (not at it), periodic retention-config audits against actual per-topic volume, and dedicated monitoring on compaction lag specifically — not just deletion-based retention headroom — since a stalled cleaner on a compacted topic gives no warning through retention metrics at all.

Chaos practice, rolling restarts, and rebalancing after recovery

All four postmortems above are best caught in a controlled game day, not discovered live. A good Kafka-specific chaos exercise deliberately: kills a broker process (SIGKILL, not SIGTERM) to rehearse ISR shrink and leader election under the real detection timeout; partitions the network between two brokers (not just kills one) to rehearse a scenario the controller must resolve differently than a clean death; throttles a disk (via cgroups or a blkio limit) to rehearse the disk-full cascade without actually filling a disk; and separately partitions a broker from the KRaft quorum to rehearse controller failover specifically. Each exercise should have a predicted metric signature written down before running it — if the taxonomy from §7 is right, you should be able to predict which beans move before you break anything.

Rolling restarts are the single most common self-inflicted incident vector, and the fix is procedural: controlled.shutdown.enable=true (default) means a broker being restarted first asks the controller to move its leaderships elsewhere gracefully before it exits, instead of forcing the controller into emergency elections under a failure-detection timeout — exactly the arithmetic from §4's naive-restart numbers. Between each broker restart in a rolling upgrade, wait for UnderReplicatedPartitions to return to zero before proceeding to the next broker; restarting broker N+1 while broker N's partitions are still catching up can turn a routine upgrade into a real under-replication incident if both brokers happen to host replicas of the same partitions.

After brokers recover from any of the above, leadership does not automatically move back to the preferred replica (the first replica listed for a partition, chosen for balanced leadership distribution) — it stays wherever it failed over to. Left alone, this silently skews load toward whichever brokers happened to survive longest. Trigger kafka-leader-election.sh --election-type preferred (or enable auto.leader.rebalance.enable) after a recovery to restore the intended distribution. Similarly, moving data with kafka-reassign-partitions.sh after a capacity change should always set an explicit throttle — an unthrottled reassignment can itself saturate the NIC or disk budget from §10's arithmetic and turn a planned maintenance action into a second incident layered on top of the first.

First, the ISR shrink check — postmortems 1 and 3's shared mechanism, simplified from real Kafka source but faithful in structure and naming:

Scalacluster/Partition.scala — maybeShrinkIsr()
def maybeShrinkIsr(): Unit = {
  inWriteLock(leaderIsrUpdateLock) {
    leaderLogIfLocal.foreach { _ =>
      // "out of sync" = hasn't fetched up to the leader's LEO for
      // longer than replica.lag.time.max.ms — a GC pause on either
      // side stalls the fetch/response cycle and feeds this clock.
      val outOfSyncReplicaIds = getOutOfSyncReplicas(replicaLagTimeMaxMs)
      if (outOfSyncReplicaIds.nonEmpty) {
        val newIsr = inSyncReplicaIds -- outOfSyncReplicaIds
        shrinkIsr(newIsr)   // writes new ISR to the controller/metadata log
      }
    }
  }
}

def getOutOfSyncReplicas(maxLagMs: Long): Set[Int] = {
  val candidates = inSyncReplicaIds - localBrokerId
  val now = time.milliseconds()
  candidates.filter { replicaId =>
    val replica = getReplica(replicaId)
    replica.lastCaughtUpTimeMs < now - maxLagMs
  }
}

Next, the point where a shrunk ISR becomes a producer-visible error — ReplicaManager's append path checking min.insync.replicas:

Scalaserver/ReplicaManager.scala + cluster/Partition.scala (simplified)
// Partition.scala
def checkEnoughReplicasReachOffset(requiredOffset: Long): Unit = {
  val minIsr = log.config.minInSyncReplicas
  if (inSyncReplicaIds.size < minIsr) {
    // Rejected DELIBERATELY: the write already reached the local
    // log, but cannot be acknowledged as durable across enough
    // replicas — this is a correctness guarantee, not a bug.
    throw new NotEnoughReplicasException(
      s"The size of the current ISR ${inSyncReplicaIds} is insufficient to satisfy min.insync.replicas of $minIsr")
  }
}

Postmortem 2's trigger — the GroupCoordinator distinguishing "member unreachable" (heartbeat/session timeout) from "member busy processing" (rebalance timeout, tied to max.poll.interval.ms):

Scalacoordinator/group/GroupCoordinator.scala (simplified)
def onExpireTimeout(member: MemberMetadata): Unit = {
  // Fires from the REBALANCE TIMEOUT (== max.poll.interval.ms),
  // NOT the session timeout / heartbeat thread — the heartbeat
  // thread has been reporting this member alive the whole time.
  if (group.has(member.memberId)) {
    warn(s"Member ${member.memberId} failed to poll within max.poll.interval.ms, removing")
    removeMemberAndUpdateGroup(group, member, s"removed on rebalance-timeout expiry")
    maybePrepareRebalance(group, s"removed member ${member.memberId}")
  }
}

Finally, postmortem 4's isolation mechanism — one bad disk takes down one directory, not the process:

Scalalog/LogManager.scala + server/LogDirFailureChannel.scala (simplified)
def handleLogDirFailure(dir: String): Unit = {
  warn(s"Stopping serving logs in dir $dir")
  logDirFailureChannel.maybeAddOfflineLogDir(dir, s"$dir failed", ioException)
  // Every partition whose replica lived here goes offline for THIS
  // broker only. If we led any of them, the controller must elect
  // a new leader elsewhere — but this broker keeps running.
  val affected = logsInDir(dir)
  affected.foreach(_.closeHandlers())
  _liveLogDirs.remove(new File(dir))
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Reject at acknowledgment time, not at write time. checkEnoughReplicasReachOffset lets the local append succeed and only refuses to acknowledge it — the alternative (blocking the write entirely until ISR recovers) would turn a replication problem into a producer-side stall with no data written anywhere. 2. Two independent timeout clocks in the coordinator. Session/heartbeat timeout answers "is this process alive"; rebalance timeout answers "is this process making progress" — conflating them would either evict healthy-but-busy consumers too eagerly or fail to evict genuinely stuck ones. 3. Isolate the failure domain to a directory, not the process. Contrast this with PostgreSQL's philosophy (from the sibling course) of killing every backend on any single corruption risk — Kafka's LogDirFailureHandler makes the opposite bet, because a broker's other log directories and other partitions are provably uncorrelated with one disk's I/O error, so there's no reason to sacrifice them too.
