Core Objects: Pods,
ReplicaSets & Deployments

Chapter 1 showed why a single host running docker run by hand collapses once you have more than one machine. This chapter builds the three objects that replace your hands: the Pod, the atomic thing Kubernetes actually schedules; the ReplicaSet, a reconciliation loop that keeps a count of Pods alive; and the Deployment, which turns "change the image tag" into a controlled, mathematically bounded rollout instead of an outage. By the end you will be able to read the exact arithmetic that decides how many old and new Pods exist at every instant of a rolling update — because you will have implemented it.

ARC 01 · THE PROBLEM

What, exactly, does the cluster run?

Chapter 1 ended with a declarative promise: you write down "5 copies of this container image, always running," and Kubernetes makes that true, forever, without you SSHing anywhere. Delivering on that promise requires answering three questions that docker run my-image never had to answer, because Docker's world only ever had one machine and one container in front of you:

  • What is "one copy"? A web application container almost never runs alone in production — it usually ships with a log-shipping sidecar, a service-mesh proxy, or an init step that must run first. Are those five separate things to schedule, or one thing?
  • What keeps a copy alive? Processes crash, nodes reboot, kernels panic (the exact mechanisms are the Container Internals course's territory — cgroup OOM kills, segfaults, kernel panics; this course starts one layer up, at the question of who notices and restarts a replacement.
  • What happens when you change your mind? "5 copies of v1" becoming "5 copies of v2" is not a single atomic operation on real infrastructure — it is dozens of individual container replacements that must happen in some order, without ever taking capacity to zero.

A Pod answers the first question. A ReplicaSet answers the second. A Deployment answers the third. None of them are optional scaffolding you can skip past — they are the direct, derivable answer to "what does a fleet manager need to track, and how does it track it," and every later chapter (the scheduler in chapter 8, the reconciliation pattern in chapter 9, StatefulSets in chapter 11) is a variation on the same shape you build here.

A NOTE ON SCOPE — WHAT THIS CHAPTER IS NOT

This chapter does not re-derive how a shared network namespace is constructed at the kernel level, or how cgroups enforce a container's resource limits — the Container Internals course covers that in full, and a Pod's shared namespace is exactly the primitive that course describes, used by a higher-level scheduler. Here, a "namespace" is a black box with one property that matters: containers inside the same Pod share one, containers in different Pods do not. If you have not taken that course, the one fact to hold onto is: sharing a network namespace means sharing one IP address and one localhost — nothing more is needed to follow this chapter.

DEEP CONTEXT · WHY THE POD DOESN'T EXIST IN BORG THE SAME WAY

Borg's closest analog is the "alloc set" — a reserved bundle of resources on a machine that multiple tasks could share. Kubernetes' designers (several of them ex-Borg and ex-Omega engineers) promoted that idea from an internal scheduling trick into a first-class, user-facing API object with its own YAML, its own lifecycle, and its own IP address. That promotion is the single biggest usability decision in the whole system: instead of telling users "your sidecar is a scheduling annotation," Kubernetes tells them "your sidecar is a second container in the same Pod object you already wrote" — a small change in framing with a large effect on how approachable the system turned out to be.

ARC 03 · NAIVE SOLUTION

Attempt #1: extend chapter 1's shell script to "groups of containers"

Chapter 1's naive fleet manager kept one container alive per host with a polling loop. Real applications need more than one container working together — say, a web server plus a sidecar that tails its logs to a central collector. Extend the naive script the obvious way: list both containers, and loop over both.

bashkeepalive-v2.sh — the strawman, annotated
#!/usr/bin/env bash
# One line per "logical app": web server + its logging sidecar.
APP_CONTAINERS=("web:my-web:v1" "logshipper:my-logshipper:v1")

while true; do
  for entry in "${APP_CONTAINERS[@]}"; do
    name=$(cut -d: -f1 <<< "$entry")
    image=$(cut -d: -f2- <<< "$entry")
    if ! docker ps --format '{{.Names}}' | grep -q "^${name}$"; then
      echo "$name missing, restarting"
      # PROBLEM: web and logshipper each get their OWN network namespace.
      # To let logshipper read web's local log socket we'd need --net=container:web —
      # a manual, undocumented, easy-to-forget wiring step per pair.
      docker run -d --name "$name" "$image"
    fi
  done
  sleep 10
done # ← runs on ONE host; "5 copies across 4 hosts" means 4 copies of this script

Watch this script's actual behavior when the web container and its sidecar start independently, and when a second copy of the same script (a second operator, or a cron duplicate) runs concurrently on the same host.

ARC 04 · WHY IT FAILS

Three failures, quantified

Each failure mode above is not a bug you patch — it is a structural gap that grows with fleet size. Put numbers on it:

  • Grouping is manual and per-pair. Wiring web and logshipper to share a network namespace needs one --net=container:web flag, remembered correctly, for every one of the N "logical apps" you run. Miss it once and the sidecar silently can't reach localhost — a class of bug that shows up as "it works on my machine" because a developer typed the flag by hand there and forgot it in the deploy script.
  • Detection latency is a coin flip you can't win cheaply. With a 10-second poll interval, a crash can go undetected for up to 10 seconds and averages 5. Halving that to 5 seconds doubles the polling load across every one of your N hosts — for N=200 hosts checking 2 containers each, that is 40 docker ps invocations/sec at 5-second intervals just to answer "is anything down," before you've restarted a single thing.
  • Concurrent restarts race with no coordination. Two invocations of the loop (a stuck cron job plus a fresh manual run, which happens constantly in real incidents) can both observe "container missing" in the same window and both issue docker run — now you have two containers claiming the same name, and whichever docker run loses restarts in a crash loop against the winner. Nothing in the script detects or prevents this: the check-then-act sequence has a time-of-check-to-time-of-use race with no lock around it.
THE ROLLING-UPDATE FAILURE IS THE ONE THAT MATTERS MOST

Now add "ship v2." The honest naive extension is: stop all N copies of v1, start N copies of v2. For a 5-replica service that is 100% capacity lost for the whole cutover window — call it 5–30 seconds of total outage, multiplied by every deploy, forever. The alternative — hand-write a loop that replaces copies one at a time — requires the script itself to track "how many v1 vs v2 are currently up," to stop early if v2 crashes on startup, and to never let available capacity drop below some floor. That is not a shell-script feature; it is a small distributed control system, and building it correctly, per application, by hand, is exactly the job a Deployment exists to do once, generically, for everyone.

ARC 05 · THE REAL SOLUTION, BUILT IN THREE LAYERS

Pod → ReplicaSet → Deployment, derived in order

Kubernetes does not solve all three problems from §1 with one object. It layers three objects, each solving exactly one problem and delegating the rest downward — a pattern you will see again with Services (chapter 3) and controllers generally (chapter 9). Step through the build-up:

Building the abstraction, one layer at a timeSTEP-BY-STEP

What a Pod actually is, precisely

A Pod (apiVersion: v1, kind: Pod) is a group of one or more containers that the kubelet (the per-node agent; chapter 6 covers it fully) guarantees are always co-scheduled on the same node and share, by construction: one network namespace (one Pod IP, one localhost every container can use to reach every other container in the Pod), and optionally one or more shared volumes. Under the hood the kubelet creates a hidden "pause" container first, purely to hold that network namespace open — your app containers can crash and restart individually without the Pod losing its IP, because the pause container, not your app container, owns the namespace. That single implementation detail is why a Pod's IP survives a container restart but not a Pod replacement.

MINIMAL REAL POD MANIFEST

A bare Pod is a legal, schedulable object entirely on its own — nothing below requires a ReplicaSet or Deployment to exist:

yamlpod.yaml — two containers, one shared namespace
apiVersion: v1
kind: Pod
metadata:
  name: web-7f3a
  labels: { app: web }
spec:
  containers:
    - name: web
      image: my-web:v1
      ports: [{ containerPort: 8080 }]
    - name: logshipper           # sidecar — reaches web via localhost:8080,
      image: my-logshipper:v1    # NO --net flag needed: same Pod = same netns

Run that manifest and you get exactly one Pod. It has no self-healing property whatsoever: if its node dies, or a scheduling decision needs to be reversed, or you simply kubectl delete it, nothing recreates it — a bare Pod is precisely as fragile as chapter 1's hand-run container, just with better container grouping. That fragility is deliberate: the Pod's only job is to define "what runs together." Something else has to own "how many, and keep it that way."

ARC 06 · WHAT THE LAYERING STILL COSTS

Three objects instead of one is not free

Before chapter 3 lets you take this design for granted, be precise about what it costs — each cost below is a direct, physical consequence of the layered design, not an implementation oversight:

  • Three API objects per logical application, not one. A Deployment creates a ReplicaSet, which creates Pods — a "simple" 5-replica web service is 1 Deployment + 1 (or, mid-rollout, 2) ReplicaSets + 5–6 Pods, each a full object with its own metadata, status, resourceVersion, and watch stream. At cluster scale this is real API server and etcd load (etcd's <8 KB-per-value guidance and multi-GB practical ceiling, from chapter 7, is exactly the kind of limit this object multiplication bumps into first).
  • The coordination logic that used to live in your one shell script now lives in a separate, asynchronous controller you cannot single-step. When something looks wrong, you are debugging a reconciliation loop running somewhere in the control plane (chapter 6), not a script you can bash -x — you diagnose it through kubectl describe events and controller logs, an indirection the naive script never had.
  • Pod IPs are still not stable identities. Layering ReplicaSet and Deployment on top of Pod does nothing to fix the fact that every replacement Pod gets a brand-new IP address — chapter 3 exists entirely because this chapter's objects deliberately do not solve that problem.
  • A bare Pod's labels can collide with a ReplicaSet's selector by accident. Because ReplicaSets find "their" Pods purely by label match (not by who created them), a hand-created Pod whose labels happen to match an existing ReplicaSet's selector gets silently adopted into that ReplicaSet's count — a real, well-documented footgun that §11 covers as a named incident pattern.

None of this is a reason to prefer the naive script — §4's math already ruled that out permanently. It is the honest price of the correct design, and knowing the price is what lets you reason about it in production instead of being surprised by it.

ARC 08 · INTERNAL IMPLEMENTATION

The real shapes and the real arithmetic

Now the mechanism, precisely. Three pieces: (a) the real Deployment/ReplicaSet YAML shapes and fields, (b) the ReplicaSet controller's reconcile loop, (c) the rounding rules that turn maxSurge: 25% into an actual integer — the exact function the simulator in §15 reimplements.

(a) The real objects, field by field

yamldeployment.yaml — apps/v1, every field this chapter uses
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 10                    # desired count — defaults to 1 if omitted
  selector: { matchLabels: { app: web } }  # IMMUTABLE after creation
  revisionHistoryLimit: 10       # how many old ReplicaSets to keep for rollback (default 10)
  progressDeadlineSeconds: 600   # mark the rollout "Failed" if no progress in this window (default 600)
  strategy:
    type: RollingUpdate           # the other legal value is "Recreate" — see §9
    rollingUpdate:
      maxSurge: 25%            # extra Pods ALLOWED above `replicas` mid-rollout (default 25%)
      maxUnavailable: 25%      # Pods ALLOWED below `replicas` mid-rollout (default 25%)
  template:                        # ← a Pod spec, verbatim; changing this is what triggers a rollout
    metadata: { labels: { app: web } }
    spec:
      containers: [{ name: web, image: my-web:v2 }]

A ReplicaSet is almost the same shape minus the rollout machinery — replicas, a selector, and a template, nothing else. That similarity is not an accident: a Deployment is, mechanically, a thing that writes ReplicaSet objects on your behalf and then manages two of them at once during a transition. maxSurge and maxUnavailable are both typed as IntOrString in the real API — either an absolute integer (maxSurge: 2) or a percentage string (maxSurge: 25%), which is exactly the ambiguity part (c) below resolves.

(c) Resolving the fenceposts: how 25% becomes an integer

The rule, faithful to the real controller's shape though simplified in naming: maxSurge always rounds up (more scheduling headroom is the safe direction to round), maxUnavailable always rounds down (fewer Pods taken away is the safe direction to round) — both biases favor keeping more capacity available during the transition, never less. And because a rollout with zero surge room and zero tolerated unavailability could never swap a single Pod, the controller forces at least one unit of movement:

godeployment/util/deployment_util.go — ResolveFenceposts() (faithful in shape and rounding rules)
func ResolveFenceposts(maxSurge, maxUnavailable *IntOrString, desired int32) (surge, unavailable int32) {
    surge       = getValueOrPercent(maxSurge,       desired, roundUp: true)   // ceil()
    unavailable = getValueOrPercent(maxUnavailable, desired, roundUp: false)  // floor()

    if surge == 0 && unavailable == 0 {
        unavailable = 1   // guarantee at least ONE pod of headroom to make progress
    }
    return surge, unavailable
}

Once surge and unavailable are plain integers, the rollout's operating envelope is fixed for the rest of the update: the total Pod count (old + new) may never exceed desired + surge, and the count of Ready Pods (old + new) may never fall below desired − unavailable. Every tick of the rollout, forever, obeys those two inequalities — that is the entire rolling-update algorithm, and §15's simulator computes both bounds live and shows you never violating either one.

WORKED EXAMPLE — DO THE MATH YOURSELF

replicas: 10, maxSurge: 25%, maxUnavailable: 25%: surge = ⌈10 × 0.25⌉ = 3, unavailable = ⌊10 × 0.25⌋ = 2. So during the update, total Pods may reach as high as 13, and Ready Pods may drop as low as 8 — never simultaneously worse than both. Change maxSurge: 0% and the same formula gives surge = 0, forcing the rollout to shrink the old ReplicaSet before it can grow the new one at all — a materially slower, but zero-extra-capacity, rollout. Try both in §15.

ARC 09 · TRADEOFFS

Four ways to keep N copies running, compared honestly

APPROACHWHAT IT BUYSWHAT IT COSTS
Naive script (ch. 1/§3) simple to read zero extra objects no atomic grouping race conditions manual, unsafe rollouts
Bare Pod correct container grouping shared netns for free zero self-healing no scaling concept
Pod + ReplicaSet self-healing horizontal scale via one field no safe way to change the Pod template selector-collision footgun
Pod + ReplicaSet + Deployment ✓ controlled rolling updates automatic rollback via revision history bounded capacity loss (maxUnavailable) extra API objects async, harder to single-step debug

Within the Deployment row itself there is a second, smaller tradeoff worth naming: strategy.type can be RollingUpdate (the default, described above) or Recreate (kill every old Pod, then create every new Pod — no surge, no partial availability, full downtime for the cutover window). Recreate exists precisely for workloads that cannot tolerate two Pod template versions running simultaneously — most commonly a singleton with an exclusive-lock-holding pattern, or an application that cannot survive a schema-incompatible version of itself serving requests next to the new one. Neither native strategy gives you blue/green or canary releases — those require a separate controller (Argo Rollouts, Flagger) layered on top, which is itself a fact worth knowing: the Deployment object's rollout vocabulary is deliberately small.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Numbers and boundaries you can predict before deploying

  • Rollout duration scales with desired and inversely with surge+unavailable. Each tick can move at most surge Pods up and (once they're Ready) unavailable Pods down; a bigger combined budget converges faster at the cost of more simultaneous capacity change.
  • Pods-per-node is a hard-configured ceiling, not a soft guideline. The kubelet's default --max-pods is 110 — a cluster autoscaler or capacity plan that assumes otherwise will hit a wall exactly at that number, regardless of how much CPU/RAM headroom remains on the node.
  • Cluster-wide, Kubernetes' documented scaling envelope is ~5,000 nodes and ~150,000 Pods total — well past that, the control plane's watch/list traffic (chapters 6–7) becomes the bottleneck long before compute does.
  • Every Pod gets a mounted service-account token by default — even one with zero declared permissions still gets a token mounted at a well-known path unless you explicitly set automountServiceAccountToken: false. Chapter 13 covers what that token can and can't do; for now, know that it exists on every Pod you have ever created, whether you asked for it or not.
  • Sharing a network namespace means sharing an attack surface. Any container in a Pod can reach any port any other container in that Pod binds on localhost — Kubernetes enforces no isolation between containers within one Pod; isolation is a between-Pods property, enforced (or not) by NetworkPolicy in chapter 10, not by anything in this chapter's objects.

ARC 11 · REAL-WORLD INCIDENTS

Three ways these objects bite in production

Incident 1: CVE-2019-11253 — a Deployment manifest as a denial-of-service payload

CVE-2019-11253 is a "Billion Laughs"-style YAML/JSON expansion attack against the API server: a deeply self-referential document (a handful of anchors expanding exponentially on parse) submitted as the body of a request — including, concretely, as the body of a kubectl apply -f against a Pod, ReplicaSet, or Deployment manifest — could force the API server to allocate memory far beyond the payload's wire size, exhausting the node running the API server and denying service cluster-wide. The fix constrained YAML/JSON document size and nesting depth before full deserialization. The lesson for this chapter specifically: the objects you have been writing YAML for all chapter are also an attack surface the moment anyone other than you can submit one.

Incident 2: the selector-collision Pod massacre

A team runs a Deployment managing a ReplicaSet with selector app=web. A developer, debugging locally against the real cluster, applies a hand-written, one-off Pod manifest that also carries the label app=web (copy-pasted from the Deployment's own template, minus the owner). The ReplicaSet controller's reconcile loop — which finds "its" Pods purely by label selector match, exactly as §8(b) showed — immediately adopts the new Pod into its count. If the ReplicaSet was already at its desired count, the controller now sees one Pod too many and deletes one to compensate — and there is no guarantee it deletes the newcomer rather than an existing, healthy replica, because from the controller's point of view they are indistinguishable members of the same set. This is precisely why the Kubernetes documentation explicitly warns against creating bare Pods whose labels match any ReplicaSet's selector, and why label schemes in real organizations tend toward unique, auto-generated values rather than short human-typed ones.

Incident 3: the "instant 100% Ready" rollout that wasn't

A Deployment rollout proceeds, new Pods reach the Running phase, the ReplicaSet controller counts them and the Deployment controller's maxUnavailable budget lets it scale down old Pods — and 502s spike anyway. Root cause, seen repeatedly across real production postmortems: the new Pods had no readinessProbe configured. Without one, the kubelet marks a container Ready as soon as its process starts, regardless of whether the application has finished loading its config, warming caches, or opening a database pool. The rollout's arithmetic in §8(c) was entirely correct — it genuinely never dropped below the computed minimum available count — but "available" was measuring a Pod that could accept a TCP connection and immediately fail the request, not a Pod that could actually serve one. The fix is always the same: define readinessProbe against a real health endpoint, so "Ready" and "actually able to serve traffic" become the same fact. (Chapter 15 covers the exact failure-threshold/period arithmetic that governs probes.)

Simplified from the real controllers but faithful in structure and naming. First, the ReplicaSet controller's diff — the entire mechanism behind "keep N replicas running," in about a dozen lines:

gopkg/controller/replicaset/replica_set.go — manageReplicas()
func (rsc *ReplicaSetController) manageReplicas(activePods []*Pod, rs *ReplicaSet) error {
    diff := len(activePods) - int(*rs.Spec.Replicas)

    switch {
    case diff < 0:                       // too FEW pods — create the shortfall
        toCreate := -diff
        slowStartBatch(toCreate, func() error {
            return rsc.podControl.CreatePod(rs.Namespace, &rs.Spec.Template, rs)
        })
    case diff > 0:                       // too MANY pods — delete the surplus
        toDelete := getPodsToDelete(activePods, diff)   // not-Ready first, then youngest
        for _, pod := range toDelete {
            rsc.podControl.DeletePod(rs.Namespace, pod.Name, rs)
        }
    }
    return nil   // diff == 0: nothing to do, exactly as §8(b)'s deck showed
}

Second, the Deployment controller's rolling-update tick — this is the loop §15's simulator runs by hand, step by step, in your browser:

gopkg/controller/deployment/rolling.go — rolloutRolling(), one reconcile tick
func (dc *DeploymentController) rolloutRolling(d *Deployment, newRS, oldRS *ReplicaSet) error {
    surge, unavailable := ResolveFenceposts(d.Spec.Strategy.RollingUpdate.MaxSurge,
                                              d.Spec.Strategy.RollingUpdate.MaxUnavailable, *d.Spec.Replicas)
    maxTotal     := *d.Spec.Replicas + surge
    minAvailable := *d.Spec.Replicas - unavailable

    // 1. Grow the NEW ReplicaSet, bounded by remaining surge room.
    total := *oldRS.Spec.Replicas + *newRS.Spec.Replicas
    room  := maxTotal - total
    if room > 0 {
        newRS.Spec.Replicas += min(room, *d.Spec.Replicas - *newRS.Spec.Replicas)
    }

    // 2. Shrink the OLD ReplicaSet, bounded by minAvailable — only once new Pods are Ready.
    available := oldRS.Status.AvailableReplicas + newRS.Status.AvailableReplicas
    scaleDown := min(*oldRS.Spec.Replicas, available - minAvailable)
    if scaleDown > 0 {
        oldRS.Spec.Replicas -= scaleDown
    }
    return dc.syncRolloutStatus(d, newRS, oldRS)  // re-runs on every informer tick until oldRS reaches 0
}
WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. State lives in the objects, not in the controller process. Every quantity above — surge room, available count, both ReplicaSets' current sizes — is read from and written back to API objects in etcd. If the controller-manager process restarts mid-rollout, a fresh instance recomputes the exact same tick from the same persisted state and continues, exactly where the old kubectl rolling-update's client-side loop could not (chapter 9 generalizes this into "level-triggered reconciliation" as a named pattern). 2. Grow before you shrink. The order in the pseudocode — surge up first, then scale down old — is deliberate: it means capacity only ever increases before it decreases within a tick, biasing every rollout toward "more available" rather than "less," consistent with §8(c)'s rounding rules.
