APPLIED CRYPTOGRAPHY · CHAPTER 05

Block Cipher Modes: ECB, CBC, CTR
& Why Mode Choice Is Not Optional

Chapters 2 and 3 gave you a block cipher: a keyed permutation that scrambles exactly one 16-byte block, and only one. Almost nothing you encrypt is 16 bytes. A mode of operation is the construction that turns that single-block primitive into something that can encrypt a gigabyte — and it turns out the naive way to do it, ECB, leaks the shape of your data through the ciphertext in a way that is now infamous as the "ECB penguin." This chapter derives CBC and CTR from ECB's failure, builds a real deterministic block cipher in JavaScript to drive every live computation on the page, and ends with a simulator that encrypts genuine pixel data under all three modes so you can watch the leak happen with your own eyes, live, on data you control.

ARC 01 · THE PROBLEM

A permutation of 16 bytes is not an encryption scheme

AES, as chapter 3 built it, is a pseudorandom permutation (PRP): feed it a 128-bit key and exactly 16 bytes of plaintext, and it deterministically produces exactly 16 bytes of ciphertext, invertible only by someone holding the key. That is a precise, well-studied, and — as far as 60 years of public cryptanalysis can tell — extremely strong guarantee. It is also, by itself, useless for encrypting almost anything real. A JPEG is millions of bytes. A database row is a few dozen. A TLS record is up to 16 KB. None of them arrive as a single 16-byte block, and the vast majority are not an exact multiple of 16 bytes either.

A mode of operation is the missing piece: an algorithm that calls the block cipher — possibly many times, possibly with extra bookkeeping like an IV or a counter — to encrypt a message of arbitrary length. The mode does not touch the cipher's internals at all; it treats E_k(·) as a black box and only decides what to feed it and how to combine the outputs. That separation is the entire reason this chapter is possible without re-deriving AES: everything below applies identically whether the box is AES-128, AES-256, or the small demonstration cipher this page builds for its own live widgets.

THE PROPERTY THAT MAKES THIS HARD

A block cipher's defining strength — same key, same plaintext block, same ciphertext block, every single time — is precisely the property a naive mode will expose to an attacker. Confidentiality for an arbitrary-length message requires a construction where identical plaintext content does not reliably produce identical ciphertext content. Getting that right, without breaking correctness or performance, is the whole design problem this chapter walks through — and mode choice turns out to carry security consequences at least as large as key length, which is why "just pick one, they're all AES underneath" is one of the most expensive sentences in applied cryptography.

DEEP CONTEXT · WHY A CARTOON PENGUIN OUTPERFORMED THE MATH

The formal statement — "ECB is not IND-CPA secure because it leaks equality of plaintext blocks" — is correct and has been in textbooks since the 1980s. It took a 2013-era blog illustration, encrypting a bitmap of Tux the Linux penguin under ECB mode and rendering the ciphertext bytes back as pixels, to make the leak visible to people who had never sat through an IND-CPA game. The image spread far enough that "the ECB penguin" is now the standard shorthand for this entire vulnerability class in code review comments and security training decks — proof that a correctly chosen picture can out-teach a correctly chosen proof. Section 15 has you reconstruct the same effect yourself, from real pixel bytes, not a static picture.

ARC 03 · NAIVE SOLUTION

Attempt #1: just call the block cipher on every 16 bytes

The obvious first move, and the one nearly every engineer reinvents independently the first time they hold a block-cipher API: split the message into 16-byte chunks and encrypt each one independently with the same key. This is Electronic Codebook mode (ECB) — the name is apt, because it really does behave like a giant, fixed codebook mapping every possible 16-byte plaintext value to one fixed 16-byte ciphertext value, for as long as the key doesn't change.

C-like pseudocodeecb_naive.c — the entire mode, annotated
void ecb_encrypt(const uint8_t *key, uint8_t *data, size_t nblocks) {
    for (size_t i = 0; i < nblocks; i++)
        block_cipher_encrypt(key, &data[i * 16]);  /* independent — no state carried between blocks */
}
/* Notice what's ABSENT: no IV, no counter, no memory of any previous block.
 * Block i's ciphertext depends on exactly two things: the key, and block i's
 * own 16 bytes of plaintext. That is the entire mode, and it is also the bug. */

It compiles, it round-trips correctly, it is trivially parallelizable in both directions, and it needs no extra input beyond the key — no IV to generate, no padding-adjacent state to manage across blocks. For a functional-correctness test it looks perfect. Section 4 shows exactly what that independence costs.

A NOTE ON THIS CHAPTER'S LIVE MATH

Every computed value on this page — every hex string, every pixel in section 15's simulator — comes from a real, deterministic, invertible 16-byte block cipher this page implements in JavaScript (TOYBLOCK-128, introduced in full in section 8). It is a genuine Feistel construction, built the same way DES was in chapter 2, using an S-box derived from real GF(2⁸) inversion — the identical finite-field math chapter 3 used for AES's SubBytes. It is deliberately smaller than AES so this page's widgets can run thousands of block operations per second without leaving JavaScript's main thread. The mode logic you are about to learn — ECB, CBC, CTR — is exactly what a real library does with real AES; only the internals of the single-block primitive differ. ARC 04 · WHY IT FAILS

Determinism is a feature of the cipher and a bug in the mode

State the failure precisely, because "ECB is insecure" is true but too vague to act on. ECB fails the standard security definition for encryption — semantic security under chosen-plaintext attack (IND-CPA) — for one exact, mechanical reason: identical 16-byte plaintext blocks always produce identical ciphertext blocks under the same key. An adversary needs no cryptanalysis, no knowledge of the key, and no weakness in the underlying cipher to exploit this — only the ability to compare ciphertext bytes.

Formally: in the IND-CPA game, an adversary picks two messages M₀ and M₁ of equal length and receives an encryption of one of them at random; if the adversary can guess which one with probability meaningfully above 50%, the scheme is broken. Under ECB, let M₀ = "AAAAAAAAAAAAAAAA" repeated twice (two identical 16-byte blocks) and M₁ = two different 16-byte blocks. The adversary wins with probability 1, every time, by checking whether the two ciphertext blocks are equal — no key, no oracle queries beyond the one challenge ciphertext, nothing but block-wise comparison. That is a complete, unconditional break of the security definition, regardless of how strong the underlying block cipher is.

Real data is nowhere near as adversarially convenient as that example, but it is still full of repeated 16-byte blocks: runs of zero bytes in sparse files, repeated header fields in structured formats, identical rows in a column-encrypted database, and — the case section 15 makes visible — large uniform regions in a bitmap image. ARC 05 · A REAL FIX, DERIVED

Break the determinism by chaining blocks together

ECB's flaw is that block i's ciphertext is a pure function of block i's plaintext and the key — nothing else. The fix, then, is to make each block's ciphertext also depend on something that differs from block to block, even when the plaintext repeats. Cipher Block Chaining (CBC), standardized in NIST SP 800-38A, does this with one extra XOR: before encrypting block i, XOR it with the previous ciphertext block. The first block, having no predecessor, is XORed with a fresh random value called the initialization vector (IV).

THE CONSTRUCTION

C_0 = IV    C_i = E_k(P_i ⊕ C_{i-1}) for i = 1..n

Decryption reverses it using the cipher's inverse direction, which ECB never needed: P_i = D_k(C_i) ⊕ C_{i-1}. Notice the IV must travel with the ciphertext (it is not secret, only unpredictable) so the receiver has C_0 to XOR against when recovering P_1.

Requirement to hold onto: the IV must be unpredictable to an attacker before it's used (a monotonic counter shared in advance is not good enough — chapter 11 revisits exactly this failure in TLS 1.0/1.1's BEAST attack) and it must be transmitted alongside the ciphertext, since the receiver needs it to decrypt the first block.

ARC 06 · WHY THAT STILL COSTS

CBC fixed the leak. It did not fix tampering — or throughput.

Be exact about what chaining bought and what it left on the table. CBC defeats the block-equality leak from §4 completely: the same plaintext block encrypted twice in the same message (or under a fresh IV in a new message) produces unrelated-looking ciphertext, because each block's input now depends on everything before it. But three costs remain, and one of them is a structural vulnerability class, not a performance tax:

  • Encryption is inherently sequential. Computing C_i requires C_{i-1}, which doesn't exist until the previous block finishes encrypting. A message cannot be encrypted faster by adding cores. (Decryption has no such dependency — every C_i is already known up front, so D_k(C_i) ⊕ C_{i-1} can run for every block in parallel. The asymmetry is worth remembering; it surprises people in interviews.)
  • Messages must be padded to a block multiple. A message that isn't an exact multiple of 16 bytes needs padding (PKCS#7 is the near-universal choice: pad with N bytes of value N). That padding must be validated and stripped on decrypt — and a server that reveals whether padding was valid, even just via a different error message or timing, opens the padding-oracle vulnerability class explored fully in chapter 10.
  • CBC ciphertext is malleable in a precisely predictable way. Because decryption XORs D_k(C_i) with C_{i-1}, flipping bit j of ciphertext block C_{i-1} flips bit j of the decrypted plaintext block P_i — with no key required. This is not a corner case; it is algebra, and it is exploitable whenever a message has no separate integrity check.

WHY THIS IS NOT A CORNER CASE

Any protocol that encrypts structured data (a byte at a known offset means "role", "amount", or "admin flag") with CBC and no separate authentication is vulnerable to this exact primitive: an attacker who knows or guesses the plaintext at a target offset can flip it to any value they want, in the block after the one they tamper with, without the key. This is precisely why chapter 6 exists: CBC (and CTR, which is malleable in an even more direct way — flip a ciphertext bit, flip the same plaintext bit, same block) both need a MAC layered on top before they can be trusted with adversarial input. Confidentiality and authenticity are different properties, bought separately, and mode design alone never delivers both.

THE UNIFYING VIEW

Every mode in this chapter answers exactly two questions: (1) what 16 bytes get fed into E_k for block i, and (2) how does the output of E_k combine with the plaintext to produce ciphertext. ECB answers "the plaintext itself" and "that's the ciphertext, directly." CBC answers "plaintext XOR previous ciphertext" and "that's the ciphertext, directly." CTR answers "a counter, not the plaintext at all" and "XOR the cipher's output with the plaintext" — which is why CTR turns a block cipher into a stream cipher with exactly the shape chapter 4 built for ChaCha20. Every mode NIST SP 800-38A defines (CFB, OFB included) is a variation on this same two-question template.

(b) CTR: the counter block, and why decryption never calls D_k

Counter mode (CTR) never feeds the plaintext into the block cipher at all. It builds a counter block — conventionally a fixed nonce concatenated with a monotonically increasing counter — encrypts that, and XORs the result (the "keystream") with the plaintext:

THE CONSTRUCTION

keystream_i = E_k(nonce ‖ i)    C_i = P_i ⊕ keystream_i

Decryption is the identical computation: recompute keystream_i (same nonce, same counter, same key) and XOR it with C_i. CTR mode never calls the block cipher's decryption direction, even to decrypt — a real, practical benefit for hardware and libraries that only need to implement E_k, and precisely the shape chapter 4's ChaCha20 (a dedicated stream cipher, not a mode) already showed you.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

The birthday bound is a real ceiling, not a rule of thumb

Brute-forcing a 128-bit AES key is 2¹²⁸ operations — roughly 3.4×10³⁸, a number so large that even at 10¹⁸ guesses/second (a generous nation-state estimate) it would take longer than the age of the universe many times over. Key length is not where CBC's real numeric risk lives. It lives in the birthday bound on the block size, and it is a concrete, computable attack — not a theoretical curiosity.

In CBC mode, ciphertext blocks that happen to collide leak the XOR of their corresponding plaintext blocks (the same algebra as chapter 4's two-time pad, arising from the chaining structure rather than nonce reuse). With an n-bit block cipher, encrypting q blocks under one key gives a collision probability that rises sharply once q approaches 2^(n/2) — the classic birthday approximation P(collision) ≈ 1 − e^(−q(q−1) / 2^(n+1)). For AES's 128-bit block that threshold is 2⁶⁴ blocks (roughly 256 exabytes) — not a concern in practice. For a 64-bit block cipher (3DES, Blowfish) the threshold is 2³² blocks — about 32 GiB, a volume a single long-lived HTTPS or VPN session can reach in hours. This exact gap is what CVE-2016-2183, "Sweet32," weaponized in 2016.

READING THE CURVE

The 64-bit curve is not a gentle slope — it is nearly flat until around 2²⁸ blocks, then rises to near-certainty by 2³⁴, a span of about 64× in data volume. That steepness is exactly why Sweet32 was a genuine, practical attack against real HTTPS and OpenVPN sessions using 3DES cipher suites, and exactly why "we only use it for legacy compatibility" is not a defense once a connection runs long enough to cross that knee. The 128-bit curve, over the same x-axis range, is indistinguishable from zero — which is the entire numeric argument for why AES's larger block size matters independently of its key length.

ARC 11 · REAL-WORLD INCIDENTS

Three incidents, three different ways mode choice went wrong

Incident 1: Adobe's 2013 password database (ECB, no CVE — but the canonical case study)

In October 2013, Adobe disclosed a breach exposing roughly 150 million user records. The passwords were not stored in plaintext, but they were encrypted — with 3DES in ECB mode, under a single key shared across every user, rather than salted and hashed as a password field should be. Because ECB is deterministic, every user with the identical password produced the identical ciphertext block. Researchers and later security teams built frequency tables of the most common ciphertext blocks, cross-referenced them against known common-password lists, and cracked huge swaths of the database without ever attacking the cipher — the same block-equality leak from §4, at the scale of 150 million rows, plus a password-hint field stored alongside in plaintext that made confirmation trivial. The lesson generalizes past ECB specifically: this is what happens when encryption is substituted for a purpose-built password hash (chapter 8 covers bcrypt/Argon2 properly), and ECB's determinism turned an already-wrong design choice into a mass-crackable one.

Incident 2: BEAST — CVE-2011-3389 (2011)

TLS 1.0's CBC-mode cipher suites had a subtle IV flaw: each record's IV was the last ciphertext block of the previous record, not a fresh unpredictable value — meaning an attacker who could see ciphertext in transit could predict the IV that would be used for the next record before it was sent. Duong and Rizzo's BEAST attack (Browser Exploit Against SSL/TLS) combined that predictability with a way to inject attacker-chosen bytes into the same connection as a victim's cookie (via malicious JavaScript in the browser), letting them run a byte-by-byte chosen-plaintext attack: guess a byte, encrypt a probe block whose XOR-with-predicted-IV matches the guess, and check whether the resulting ciphertext matches the real encrypted cookie block. Repeated across the cookie's length, this recovered session cookies from an HTTPS connection believed secure. Root cause: an IV that failed the "unpredictable to an attacker" requirement CBC's security proof depends on. TLS 1.1 fixed it by requiring an explicit, fresh, unpredictable IV per record instead of chaining across records.

Incident 3: Sweet32 — CVE-2016-2183 / CVE-2016-6329 (2016)

Bhargavan and Leurent's Sweet32 attack directly weaponized §10's birthday-bound math: force a browser to make enough requests over a long-lived HTTPS or OpenVPN connection using a 64-bit-block cipher (3DES) in CBC mode to cross the ~2³² block (~32 GiB) threshold, wait for a ciphertext block collision, and recover a few bytes of a secret cookie carried alongside the colliding blocks via the same XOR-leak structure BEAST exploited differently. The practical fix was not a CBC patch — it was retiring 64-bit-block ciphers from TLS and VPN cipher suites entirely, which major browsers and OpenSSL did in the wake of the disclosure. It is the cleanest real-world proof that "block size" is a security parameter engineers must reason about explicitly, not an implementation detail abstracted away by "we're using CBC."

ARC 13 · CODE WALKTHROUGH

Where modes actually live in a real TLS/crypto stack

Modes are deliberately implemented as a layer above the block cipher, dispatched generically, so a library can add a new mode without touching cipher internals — and so a new cipher automatically gets every existing mode for free. Files marked ● are this section's core reading; the shapes below are structurally faithful to OpenSSL's real module layout.

crypto/
├── modes/
│ ├── ● cbc128.c — CRYPTO_cbc128_encrypt()/_decrypt(): the reference chaining loop this section's deck mirrors
│ ├── ● ctr128.c — CRYPTO_ctr128_encrypt(): counter-block keystream generation, 128-bit counter increment with carry
│ ├── ecb128.c — the direct block-at-a-time wrapper; kept mostly for test vectors, not shipped for general use
│ └── gcm128.c — chapter 7's AEAD construction, built directly on top of this directory's counter-mode code
├── evp/
│ └── ● evp_enc.c — EVP_EncryptUpdate()/EVP_CipherUpdate(): the mode-agnostic entry point every real caller uses
├── aes/aes_core.c — the block cipher itself (chapter 3); modes/ never reaches into AES internals
└── rand/rand_lib.c — CSPRNG backing RAND_bytes(), used to generate every IV/nonce this chapter requires

First, the mode-agnostic dispatch every real caller goes through — notice it decides nothing about mode semantics itself, only routes to the right implementation:

C-like pseudocodeevp_enc.c — EVP_EncryptUpdate(), the shape every OpenSSL caller hits
int EVP_EncryptUpdate(EVP_CIPHER_CTX *ctx, uint8_t *out, int *outl,
                      const uint8_t *in, int inl) {
    /* The context carries a function pointer set when the cipher+mode was
     * chosen (EVP_aes_256_cbc(), EVP_aes_256_ctr(), ...). This function
     * never branches on "which mode" — that decision was made once, at
     * EVP_EncryptInit, and baked into ctx->cipher->do_cipher.            */
    return ctx->cipher->do_cipher(ctx, out, in, inl);
}

Second, the CBC chaining loop itself — the C shape behind §5's derivation and §8(a)'s live deck:

C-like pseudocodecbc128.c — CRYPTO_cbc128_encrypt(), structurally faithful
void CRYPTO_cbc128_encrypt(const uint8_t *in, uint8_t *out, size_t len,
                            const void *key, uint8_t ivec[16], block128_f block) {
    size_t n;
    while (len >= 16) {
        for (n = 0; n < 16; n++)
            out[n] = in[n] ^ ivec[n];              /* XOR with chaining value */
        (*block)(out, out, key);                    /* E_k, in place            */
        memcpy(ivec, out, 16);                   /* THIS block's ciphertext becomes
                                                      * next block's chaining value —
                                                      * the entire chain, one line     */
        len -= 16; in += 16; out += 16;
    }
}

Third, CTR's counter-increment, the detail that trips up hand-rolled implementations: real libraries increment the entire 128-bit counter block, with carry propagation across all 16 bytes — not just a 32-bit sub-field — so the construction is correct even for callers who don't reserve dedicated nonce/counter byte ranges:

C-like pseudocodectr128.c — the 128-bit counter increment, carry included
static void ctr128_inc(uint8_t counter[16]) {
    uint32_t n = 16;
    do {
        --n;
        if (++counter[n] != 0) return;   /* no carry needed, done      */
    } while (n);                            /* carry into byte n-1, repeat */
}                                                /* wraps silently at 2^128 — callers must
                                                  * ensure they never reuse (key, nonce, ctr) */
WHY IT WAS BUILT THIS WAY

Treating the counter as one 128-bit big-endian integer, rather than splitting it into a fixed "nonce field" and "counter field" inside the increment logic itself, keeps ctr128_inc mode-agnostic and reusable by GCM (chapter 7), which needs the exact same counter machinery for its own internal keystream. The nonce/counter split is a convention enforced by the caller (typically 96 bits of nonce + 32 bits of counter, per RFC 8439's convention for ChaCha20 and common practice for AES-CTR) — the increment function itself doesn't need to know or care where that boundary is, which is precisely why one well-tested function backs every counter-based mode in the library.

Every mode in this chapter — including the AEAD preview in §9 — is malleable: an attacker with no key at all can flip predictable bits of plaintext, or forge a bit-flipped ciphertext, and nothing in ECB, CBC, or CTR will notice or object.
