Mining: Hardware, Pools &
the Difficulty Engine

Chapter 7 showed you the 80-byte header and the nonce field a miner grinds to satisfy proof of work. This chapter starts from an uncomfortable fact about that field: it is only four bytes wide, and any ASIC built in the last decade exhausts its entire 4.3-billion-value range in a fraction of a second. Everything mining infrastructure has become — extranonces, version rolling, warehouses of purpose-built silicon, pools, Stratum, a difficulty algorithm with a bug nobody can fix — exists because that one field ran out.

ARC 01 · THE PROBLEM

Four bytes is not a search space, it's a rounding error

Recall the header field from chapter 7: nNonce, a 32-bit unsigned integer sitting in the last four bytes of the 80-byte block header. The mining loop increments it, hashes the header with double SHA-256, and checks whether the result is numerically below the current target. That is the entire proof-of-work primitive. The question this chapter opens with is arithmetic, not cryptography: how large is that search space, and how long does it last?

232 = 4,294,967,296 — about 4.3 billion distinct nonce values. In 2009, on Satoshi's CPU doing perhaps 10 million double-SHA-256 hashes per second, exhausting that space took roughly seven minutes — a real constraint that shaped early mining. Today a single modern ASIC does not measure its hashrate in millions of hashes per second; it measures it in hundreds of trillions. At 200 TH/s, one chip alone burns through all four billion nonce values in:

THE NUMBER THAT FORCES EVERYTHING ELSE IN THIS CHAPTER

232 hashes ÷ 200,000,000,000,000 hashes/sec ≈ 0.0000215 seconds ≈ 21.5 microseconds. One chip, one header, exhausted in under a fortieth of a millisecond. A modern mining farm running thousands of such chips in parallel would need a fresh nonce space roughly that often just to keep every chip fed with unique work. The nonce field alone cannot possibly describe enough distinct header variations to keep even one chip busy for a meaningful interval, let alone a warehouse of them.

This is not a design flaw to be patched — Satoshi's original code never anticipated hash rates six orders of magnitude higher than a 2009 CPU. It is a hard constraint that the entire mining ecosystem has had to route around without ever touching consensus: miners need vastly more distinct 80-byte headers to try than the nonce field alone can enumerate, and they need to get them without asking every full node on the network to change a single validation rule. Three techniques emerged to manufacture that extra space — extranonce, timestamp rolling, and version rolling — and understanding exactly how each works, and what each costs, is the spine of this chapter. From there we follow the hardware that grinds this space (CPU → GPU → FPGA → ASIC) and the pools that aggregate it, because both are direct consequences of the same underlying fact: one honest attempt at a block is astronomically unlikely, and the only way to compete is to try astronomically many of them, as fast and as cheaply per attempt as physically possible.

DEEP CONTEXT · WHY THE ERAS ARE SO SHORT

Each hardware transition (§4) roughly obsoletes the previous one's economics within 12–18 months, because mining is a zero-economic-profit competition at equilibrium: block reward and fees are fixed by the protocol and split in proportion to hashrate, so any hardware advantage translates directly into market share until the old hardware's electricity cost exceeds its share of the reward. There is no way to "hold back" a superior chip once it exists — using it earns real money immediately, and competitors must match it or exit.

ARC 03 · NAIVE SOLUTION

Attempt #1: just loop the nonce, faster

The naive answer to "the nonce space is too small" is: don't fix the space, fix the speed — build faster and faster hardware to search the same 4.3 billion values, over and over, hoping the current header (fixed transaction set, fixed previous-block hash, fixed timestamp) eventually produces a hash under target before you have to ask for a new one. Here is that loop, unmodified from how Satoshi's original CPU miner worked:

C++naive_miner.cpp — the strawman: nonce-only search
bool MineBlock(CBlockHeader& header, const uint256& target)
{
    for (uint32_t nonce = 0;; ++nonce)
    {
        header.nNonce = nonce;
        uint256 hash = Hash256(header);       /* SHA256(SHA256(header)) */

        if (hash <= target)
            return true;              /* found it — extremely rare */

        if (nonce == UINT32_MAX)
            return false;             /* exhausted 2^32 values — now what? */
    }
}

This is exactly right as a first step: it is the literal mechanism the consensus rules describe, and every miner that has ever existed runs some variant of this inner loop at the silicon level. The strawman isn't wrong about what to compute — it's incomplete about what happens when the loop reaches UINT32_MAX and still hasn't found a hash under target, which for any hardware built after roughly 2011 happens before the loop is a measurable fraction of a second old.

ARC 04 · WHY IT FAILS

The loop runs out before it can possibly succeed

Whether the nonce-only loop can find a block before exhausting 232 depends entirely on the relationship between hashrate and target. At the current network difficulty, the probability that a single random 256-bit hash falls under target is roughly one in tens of trillions — so exhausting 4.3 billion attempts gets you nowhere near a solution most of the time. Once you exhaust the nonce field with the header otherwise unchanged, hashing the identical 80 bytes again produces the identical hash: you have not tried a tenth of what you need to, and there is nothing left to increment.

THE NUMBERS, LAID OUT

CPU (~10 MH/s, 2009): 2³² hashes takes ~429 seconds — over 7 minutes, comparable to the target block interval itself, which is why CPU mining was ever viable at all. GPU (~200 MH/s, 2010): ~21.5 seconds. FPGA (~1 GH/s, 2011): ~4.3 seconds. First-generation ASIC (~60 GH/s, 2013): ~72 milliseconds. Modern ASIC (~200 TH/s, today): ~21.5 microseconds. Across four hardware generations the exhaustion time fell by a factor of roughly twenty million — from "comparable to a block interval" to "over sixteen thousand times per second." A field that once bounded a meaningful chunk of a miner's work now bounds nothing at all.

So a real miner needs one of two things: an externally-supplied fresh header every few tens of microseconds (impossible — someone has to build that header, and rebuilding the Merkle root and re-fetching the previous block hash is not free), or a way to manufacture many distinct valid headers from a single block template without going back to the network for each one. That is exactly what extranonce, timestamp rolling, and version rolling do — §5 derives each.

ARC 05 · BETTER SOLUTION

Three ways to manufacture a fresh header without asking the network

Every field in the 80-byte header is consensus-fixed except the ones a miner is explicitly allowed to choose: the nonce (trivially), the coinbase transaction's contents (which feed into the Merkle root), the timestamp (within bounds), and — since 2016 — sixteen otherwise-unused bits of the version field. Step through how each one manufactures new search space, and at what cost:

Manufacturing search spaceSTEP-BY-STEP
WHY THIS ORDER, IN REAL HARDWARE

ASICs roll these in a strict cost order because SHA-256 processes the 80-byte header as two 64-byte blocks, and the nonce sits in the second one. The chip can cache the intermediate compression state (the midstate) after hashing the first 64 bytes once, then iterate only the second block's compression function for every nonce — the cheapest possible operation. Version and the bulk of the Merkle root sit in the first 64 bytes, so changing them forces a fresh midstate computation: roughly double the work per trial header. That asymmetry is precisely why nonce is rolled fastest, extranonce/version are rolled far less often, and — as §6 shows — why someone eventually tried to exploit the asymmetry itself.

ARC 06 · WHY THAT STILL COSTS

Rolling isn't free, and one form of rolling became a political fight

Each of §5's three techniques has a real cost, and one of them — version rolling — became the center of one of Bitcoin's more genuinely contentious episodes. Take the costs first, then the controversy.

  • Extranonce costs a Merkle recomputation. Changing the coinbase transaction changes its txid, which is a leaf of the Merkle tree, which changes every hash on the path from that leaf to the root. For a block with 4,096 transactions that's about 12 hash operations (log₂ 4096) — cheap compared to grinding nonces, but not free, and it must happen every time extranonce2 increments (typically every few billion nonce attempts, i.e. very frequently on modern hardware).
  • Timestamp rolling is bounded and semantically loaded. A block's timestamp must exceed the median of the previous eleven blocks' timestamps and must not exceed the network-adjusted time by more than two hours (Bitcoin Core's MAX_FUTURE_BLOCK_TIME). That gives at most a few thousand seconds of legitimate slack — a rounding error next to 2³² — and because timestamps also feed the difficulty retarget calculation (§8), aggressively front-loading them skews that calculation for everyone, not just the miner doing it.
  • Version rolling is nearly free — which is exactly why it was tempting to hide. BIP320 designates the mask 0x1fffe000 (bits 13–28 of the 4-byte version field, 16 bits) as general-purpose: a pool or miner may set any value in those bits without affecting a node's interpretation of the block, because those bits are unrelated to BIP9 soft-fork signaling (which uses the top 3 bits and a small low range). Sixteen bits is 65,536× more header combinations, and unlike extranonce it touches the first SHA-256 block — which is precisely the piece that motivated ASICBoost.

ASICBoost: exploiting the midstate, not the search space

ASICBoost (Timo Hanke, 2016) is not really about extra nonce space — it's about avoiding redundant work. Recall from §5 that changing anything in the header's first 64 bytes forces a fresh midstate computation. Hanke observed that if you can find several different candidate headers whose first 64 bytes hash to the same intermediate state — a specific kind of collision in the version/prevhash/partial-Merkle-root bytes — an ASIC can compute that midstate once and reuse it across all of them, skipping roughly one SHA-256 compression per trial and recovering on the order of a 20% efficiency gain. Version rolling is one legitimate, standardized way to search for such collisions: you're allowed to vary those 16 bits freely, so you search across them for values that produce a favorable midstate collision, then declare that you're doing so — this is overt ASICBoost, and BIP320 exists specifically to standardize it so Stratum pools and firmware could support it without ambiguity.

COVERT ASICBOOST AND THE SEGWIT ACTIVATION FIGHT — STATED CAREFULLY

A miner can also search for the same kind of midstate collision without using the standardized version bits — by grinding the coinbase transaction (via extranonce) to find Merkle roots that happen to produce a favorable first-block hash, an approach that leaves no visible signal in the version field and is therefore called covert ASICBoost. In March 2017, Bitcoin Core contributor Gregory Maxwell published an analysis ("An Extraordinary Claim") arguing that patterns in historical block version bits were consistent with covert ASICBoost having been used in production mining, and that the manufacturer most plausibly responsible — widely reported to be Bitmain, though this was disputed at the time and never fully confirmed — had a financial incentive to oppose Segregated Witness. The proposed mechanism: certain implementations of covert ASICBoost benefit from being able to freely restructure a block's transaction set and coinbase without constraint, and SegWit's mandatory witness commitment (a fixed-format commitment that must appear in the coinbase output, chapter 12) was argued to interfere with some of that freedom, giving a large ASIC vendor a reason — beyond the publicly stated technical objections — to resist SegWit's activation. This causal claim was contested by the parties involved and is not something this course can adjudicate with certainty; what is not disputed is that overt ASICBoost via BIP320 version rolling is fully compatible with SegWit, is standardized, and is in routine legitimate use today across most mining pools and firmware.

The episode matters for a reason bigger than the specific accusation: it's a clean example of how a purely technical optimization (skip a redundant hash) can become entangled with protocol governance once enough value is on the line, and of why "no privileged party can act unilaterally" (chapter 7's soft-fork discussion) is easier to state as a principle than to keep true in practice when one class of participant controls specialized, concentrated hardware.

Notice what the pool cannot do: it cannot make a full node accept an invalid block, no matter how much hashrate it controls, because every full node re-validates from scratch (chapter 8) regardless of who mined it or how. ARC 08 · INTERNAL IMPLEMENTATION

The retarget algorithm, exactly — including the bug

Every 2016 blocks, every full node independently recomputes the target using only data already in its own chain — no oracle, no external clock dependency beyond the timestamps miners themselves committed to. The formula:

THE FORMULA

new_target = old_target × (actual_timespan / 1,209,600), where 1,209,600 seconds is exactly 14 days — the intended time for 2016 blocks at 10 minutes each. actual_timespan is clamped to [expected_timespan / 4, expected_timespan × 4] before the multiplication, so difficulty can change by at most 4× in either direction per adjustment, regardless of how extreme the observed hashrate swing was.

The off-by-one bug: measuring 2015 intervals, dividing by 2016

Here is the part that surprises people who assume the algorithm is exactly what its name implies. Bitcoin Core's retarget code walks backward from the last block of the outgoing 2016-block window to compute actual_timespan — but it walks back only 2015 blocks, not 2016, to find the window's start:

Why the timespan measures 2015 intervals, not 2016STEP-BY-STEP
THE PERMANENT CONSEQUENCE

The algorithm divides the measured span (2015 real intervals) by the constant 1,209,600 — which encodes an assumption of 2016 intervals. If the network's true hashrate were perfectly stable, the timespan measured would consistently be 2015 × (true average interval), and dividing that by 2016 × 600 yields a new target implicitly targeting a mean interval of 600 × 2015/2016 ≈ 599.702 seconds — roughly 9 minutes 59.7 seconds, not an even ten minutes. The effect is tiny (about 0.05%) but structural: fixing it would change what every node considers a valid block's implied timing, which makes it a consensus rule. It has shipped in every Bitcoin release since 2009 and can never be corrected without a coordinated hard fork that no one has ever proposed for a discrepancy this small.

Difficulty is a display convenience, not what nodes actually check

Nodes only ever compare a candidate hash against the raw compact-encoded target from chapter 7's nBits field. "Difficulty" is a human-friendly derived ratio: difficulty = difficulty_1_target / current_target, where difficulty_1_target is the target corresponding to nBits = 0x1d00ffff — the genesis-era maximum-possible target. A difficulty of 90 trillion simply means the current target is about 90 trillion times smaller (harder) than that original ceiling. From difficulty you can estimate network hashrate with no other information: hashrate ≈ difficulty × 2³² / 600 hashes/sec, because a target that is D times harder than difficulty-1 requires, on expectation, D × 2³² hash attempts per block, and blocks arrive roughly every 600 seconds by construction.

Stratum: how a job actually reaches an ASIC

Bitcoin Core has no built-in pool server; it exposes getblocktemplate (BIP22/23) over RPC and lets external software do the rest. Pool software (ckpool, Braiins Pool's server, public-pool) calls that RPC, builds a coinbase transaction crediting itself, computes the Merkle branch, and pushes a job to every connected miner over Stratum — a line-delimited JSON-RPC protocol running over a persistent TCP socket, deliberately simple because ASIC firmware has to parse it in a resource-constrained embedded environment.

JSONStratum V1 wire protocol (external pool software, not Bitcoin Core) — mining.notify
{"id":null,"method":"mining.notify","params":[
  "bf",                     // job_id — miners echo this back on submit
  "4d16b6f...c8b8",          // prevhash (byte-swapped per Stratum convention)
  "01000000010000...",       // coinb1 — coinbase bytes BEFORE extranonce
  "0d2f4254...ffffffff",     // coinb2 — coinbase bytes AFTER extranonce
  ["c7f...1a2","9be...0f3"], // merkle_branch — hashes to fold with the coinbase
  "20000000",                // version (miner may roll bits per BIP320)
  "1a44b9f2",                // nbits — current compact target
  "4dd7f5c7",                // ntime — pool-assigned timestamp (limited rolling)
  true                       // clean_jobs — discard in-flight work, a new block arrived
]}

The miner fills in its own extranonce2 (assigned an extranonce1 prefix at connect time so no two miners on the pool ever try the identical coinbase), recomputes the Merkle root by folding the coinbase hash up through merkle_branch, assembles the 80-byte header, and grinds nonces. Crucially, the pool sets a pool difficulty via mining.set_difficulty that is far easier than the real network target — the miner is asked to find and submit shares, not full blocks, which is exactly what §9 turns into a payout mechanism.

ARC 09 · TRADEOFFS

Variance is why pools exist — and how they price it

A share is a solution to the same header-hashing problem as a real block, just against a much easier target. If the pool's target is, say, 1000× easier than the network's, a miner finds a share roughly 1000× more often than it would find an actual block — and the ratio of network-difficulty to pool-difficulty is an unbiased, verifiable estimator of that miner's fraction of the pool's total hashrate, because both quantities are measuring the same underlying Poisson process at different thresholds. That's the entire trick: shares let a pool measure contributed work continuously and grant proportionally, without waiting for the rare event of an actual block.

Why does anyone need that? A solo miner with 0.01% of network hashrate finds a block, on average, once every 10 min / 0.0001 = 100,000 blocks ≈ 1.9 years — and because block discovery is a Poisson process (memoryless, exponentially distributed inter-arrival times), the standard deviation of that wait is also about 1.9 years. You could go three or four years without a single block and be entirely within normal variance. A pool aggregates thousands of such miners; the pool's own combined hashrate finds blocks constantly, and the reward-splitting scheme decides how that steady stream gets divided back out.

PPLNS pushes some of that variance back onto miners (payouts depend on being actively hashing right before a block lands, and leaving a PPLNS pool right after a lucky block forfeits nothing, but leaving right before one forfeits a share of a reward you helped earn) in exchange for a smaller fee and — crucially — for making pool-hopping unprofitable, since your payout depends on shares submitted before the block you're hoping to catch, not shares submitted the instant you arrive.

SHA-256 was uniquely suited to this progression because its compression function is fixed (no configuration or per-instance memory footprint to design around), memory-free (every hash attempt is self-contained arithmetic on 32-bit words — no cache, no DRAM access, no latency to hide), and embarrassingly parallel (every nonce is an independent trial, so you can tile thousands of identical hashing cores across a single die with no coordination overhead between them). An ASIC designer's entire job becomes "pack the smallest possible SHA-256 core at the lowest possible voltage and repeat it as many times as the die allows" — a problem with a genuine, reachable optimum, which is exactly why manufacture concentrated into a handful of firms (dominated for years by Bitmain, MicroBT, and Canaan) rather than remaining a diffuse hobbyist activity: designing and fabricating a competitive chip requires capital and process-node access that only a few companies command.

The honest lesson across three attempts: memory-hardness raises the cost of specialization, it does not eliminate the incentive. Anywhere real money rewards a faster hash, someone will eventually price out whether custom silicon clears the bar — the only algorithms that have avoided ASICs so far are the ones where crossing that bar remains, for now, not worth the capital and forking risk.

ARC 10 · PERFORMANCE / SECURITY

Variance, quantified — and why concentration is the real risk

Block discovery for any fixed hashrate share is a Poisson process: discoveries happen independently, at a constant expected rate proportional to your share of total hashrate. The defining property of an exponential inter-arrival distribution is that its standard deviation equals its mean — there is no "usually close to average" regime; the distribution is genuinely as spread out as its own expectation. POOLS AS INSURANCE, MADE PRECISE

A pool operator running PPS is doing textbook actuarial pooling: they collect a fee (their margin), take on the aggregate variance of thousands of independent Poisson processes (which — by the same mathematics that makes insurance companies solvent — has a coefficient of variation that shrinks as the square root of the number of pooled participants grows), and pay each miner a de-randomized, proportional share. The fee is the price of converting "1.9-year variance" into "predictable daily income," and it is not a scam or inefficiency — it is the correct market price for risk transfer, exactly as it is in traditional insurance.

Concentration is the systemic risk this buys you

The same aggregation that smooths variance for individual miners concentrates decision-making power in pool operators and, one level further back, in ASIC manufacturers. A pool that controls a majority of hashrate can, in principle, execute the double-spend and censorship attacks chapter 8 analyzed for "an attacker with 51%," except the attacker here isn't a shadowy adversary — it's the operator of infrastructure thousands of honest miners voluntarily pointed their hardware at. And because only a handful of firms have ever fabricated competitive SHA-256 ASICs, a supply-chain compromise, an export-control action, or a single firmware bug can affect a disproportionate fraction of global hashrate simultaneously — a fragility with no equivalent in a world of interchangeable commodity CPUs. §11 covers two incidents that turned each of these risks from a hypothetical into a headline.

ARC 11 · REAL-WORLD INCIDENTS

Four incidents, four different failure modes

Incident 1: GHash.io crosses 51% (July 2014)

For a sustained period in July 2014, the mining pool GHash.io's share of total network hashrate exceeded 50% — the threshold chapter 8 identifies as sufficient, in principle, to attempt double-spends and selective transaction censorship. No attack was ever carried out or even credibly alleged; the incident's significance is precisely that nothing had to go wrong for the risk to be real. GHash.io publicly pledged to voluntarily cap its share below 39.99% and asked participants to redistribute to other pools, and the episode remains the canonical case study cited whenever pool concentration is discussed — proof that "someone crossed the line" and "an attack happened" are different events, and the first one alone is a legitimate five-alarm concern.

Incident 2: covert ASICBoost and the SegWit fight (2016–2017)

Covered in depth in §6: on-chain evidence of anomalous version-bit patterns, published by Gregory Maxwell in March 2017, was used to argue that a major ASIC manufacturer had a hidden financial motive to oppose SegWit activation. The root-cause lesson generalizes beyond the specific dispute: when one class of participant holds concentrated, specialized infrastructure, an optimization invisible to everyone else can quietly become a governance stake, and "the technical objections are the real objections" cannot be assumed by default.

Incident 3: Antbleed — a remote kill switch in ASIC firmware (2017)

Independent researchers disclosed in April 2017 that firmware shipped on a widely deployed line of Bitmain Antminer units periodically phoned home to a manufacturer-controlled server and could, in principle, be remotely disabled in bulk by whoever controlled that infrastructure — a capability with no operational justification and obvious systemic-risk implications if a large enough fraction of hashrate ran the same closed-source firmware. Bitmain characterized it as an unused diagnostic feature and patched it after disclosure, but the incident crystallized a risk this chapter's hardware section only implies in the abstract: ASIC firmware is closed, vendor-controlled software running critical consensus infrastructure, and the manufacturing concentration from §9 means a single vendor's firmware choices can matter at a genuinely systemic scale.

Incident 4: block withholding as sabotage, not just theory

Academically, block withholding is well understood — a rogue miner submits ordinary shares to collect a PPS payout but deliberately never submits any share that would actually solve a full block, quietly draining the pool's expected revenue while the attacker suffers no cost (Rosenfeld's 2011 analysis and Courtois & Bahack's 2014 "On Subversive Miner Strategies" both formalize the attack and its economics). In 2015, an anonymous poster publicly claimed to have run exactly this attack against several public pools, including Eligius, for an extended period, motivated by personal grievance rather than profit — a claim consistent with irregularities independent researchers had already noted in some pools' block-discovery statistics. The mechanism requires no special privilege beyond ordinary pool membership, which is precisely what makes it hard to prevent and easy to deny.

    // Walk back 2015 blocks — NOT 2016 — to find the window's first block.
     * pindexLast IS the 2016th block of the outgoing window, so its
     * ancestor 2015 blocks back is the window's 1st block. The gap
     * between them is 2015 inter-block intervals, not 2016.          
    int nHeightFirst = pindexLast->nHeight - (params.DifficultyAdjustmentInterval()-1);
    const CBlockIndex* pindexFirst = pindexLast->GetAncestor(nHeightFirst);

    return CalculateNextWorkRequired(pindexLast, pindexFirst->GetBlockTime(), params);
}
C++src/pow.cpp — CalculateNextWorkRequired(): the formula and the 4× clamp
unsigned int CalculateNextWorkRequired(const CBlockIndex* pindexLast,
                                     int64_t nFirstBlockTime,
                                     const Consensus::Params& params)
{
    if (params.fPowNoRetargeting) return pindexLast->nBits;   // regtest escape hatch

    int64_t nActualTimespan = pindexLast->GetBlockTime() - nFirstBlockTime;  // spans 2015 intervals

    // Clamp to ±4× so no single window can move difficulty more than 4x
    if (nActualTimespan < params.nPowTargetTimespan / 4)
        nActualTimespan = params.nPowTargetTimespan / 4;
    if (nActualTimespan > params.nPowTargetTimespan * 4)
        nActualTimespan = params.nPowTargetTimespan * 4;

    arith_uint256 bnNew;
    bnNew.SetCompact(pindexLast->nBits);
    bnNew *= nActualTimespan;
    bnNew /= params.nPowTargetTimespan;   // divides by 2016*600 — the source of the 2015-vs-2016 skew

    const arith_uint256 bnPowLimit = UintToArith256(params.powLimit);
    if (bnNew > bnPowLimit) bnNew = bnPowLimit;

    return bnNew.GetCompact();
}
C++src/node/miner.cpp — IncrementExtraNonce(): the Merkle-root recompute from §6
void IncrementExtraNonce(CBlock* pblock, const CBlockIndex* pindexPrev, unsigned int& nExtraNonce)
{
    static uint256 hashPrevBlock;
    if (hashPrevBlock != pblock->hashPrevBlock) { nExtraNonce = 0; hashPrevBlock = pblock->hashPrevBlock; }
    ++nExtraNonce;

    unsigned int nHeight = pindexPrev->nHeight + 1;
    CMutableTransaction txCoinbase(*pblock->vtx[0]);
    txCoinbase.vin[0].scriptSig = (CScript() << nHeight << CScriptNum(nExtraNonce)) + COINBASE_FLAGS;

    pblock->vtx[0] = MakeTransactionRef(std::move(txCoinbase));
    pblock->hashMerkleRoot = BlockMerkleRoot(*pblock);  // full recompute — cheap (§6): O(log n) hashes
}
WHY THE SEPARATION OF CONCERNS — A CHOICE WORTH STEALING

Bitcoin Core builds candidate blocks and validates proof of work, full stop. It has never shipped a built-in pool server, a Stratum implementation, or ASIC-specific tooling — getblocktemplate is the entire interface, a stable RPC that any external program can call to get a valid, spendable template and hand back a solved header. That boundary means the consensus-critical code (small, heavily reviewed, rarely changed) never has to absorb the churn of pool-protocol iteration (Stratum V1 → V2, new reward schemes, new fee-estimation heuristics) — exactly the kind of interface discipline that keeps a security-critical core reviewable while an entire external industry iterates around it at its own pace.
