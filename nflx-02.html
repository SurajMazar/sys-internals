NETFLIX STREAMING INTERNALS · CHAPTER 02

Video Fundamentals:
Why Raw Video Is Too Big

Chapter 1 cited a "2.2 Mbps stream" as if it were a natural unit. It isn't — it's the output of throwing away, deliberately and by a factor of a thousand or more, almost all of the data a camera sensor actually captured. This chapter does the arithmetic no one skipped in chapter 1: exactly how big raw digital video is, exactly why that size makes streaming it directly impossible at any bandwidth realistically available to a household, and exactly which two kinds of redundancy — spatial and temporal — every modern video codec exploits to close that gap. Everything in chapter 3 (real codecs) is a specific engineering answer to the problem this chapter makes numerically undeniable.

ARC 01 · THE PROBLEM

A video is just numbers — an enormous number of numbers

Strip away codecs, containers, and players and a digital video is nothing more than a sequence of still images — frames — shown fast enough that human vision perceives continuous motion, where each frame is itself a grid of picture elements (pixels), and each pixel is a small number of bytes encoding a color. There is no magic in "video" as a format — it is arithmetic applied at enormous scale: width × height pixels, each pixel some number of bytes, repeated some number of times per second, for however many seconds the title runs.

The engineering problem this chapter exists to solve is exactly that arithmetic getting out of hand. Multiply a modest resolution by a modest frame rate by a modest color depth and the result is a bitrate no consumer network in this course's entire twenty-year timeline could carry raw. Compression is not an optimization applied to video — it is the precondition for video existing as an internet product at all, and this chapter derives exactly why, with numbers you can reproduce yourself.

WHY THIS MATTERS FOR THE NEXT 16 CHAPTERS

Every subsequent chapter assumes compressed video as a given and builds on top of it: codecs (ch. 3) are the specific, standardized algorithms that perform the compression this chapter shows is mandatory; adaptive bitrate (ch. 4–5) exists to pick among already-compressed renditions; Open Connect (ch. 7–8) moves compressed bytes efficiently, not raw ones. If the arithmetic in §4 didn't come out the way it does, none of the rest of this course's architecture would need to exist — streaming would just be "send the file."

DEEP CONTEXT · THE SAMPLING GRID EVERY BITRATE CALCULATION STILL USES

Modern raw-bitrate math (§4, §8) still traces back to ITU-R BT.601, the 1982 standard that defined how analog video is sampled into a digital grid of pixels with a specified color-sampling scheme. Every "raw bitrate" number this chapter computes — and every codec's starting point in chapter 3 — inherits that basic sampling-grid idea: video is a fixed-size numeric array, repeated at a fixed rate, and its uncompressed size is simply the product of its dimensions.

ARC 03 · NAIVE SOLUTION

Attempt #1: just send every pixel of every frame

The most obvious possible design: capture frames, and transmit each one's raw pixel data, uncompressed, in order. No cleverness, no redundancy removal — just numbers, sent honestly.

pseudocodenaive_raw_stream.txt — the strawman, annotated
// send every frame's full pixel grid, every time, no redundancy removed
function sendFrame(frame):
    for row in frame.pixels:
        for pixel in row:
            transmit(pixel.r, pixel.g, pixel.b)  // 3 bytes, honestly, every single pixel

function sendVideo(frames, fps):
    for frame in frames:
        sendFrame(frame)                  // repeat, fps times per second,
                                              // for the full runtime

This is not a design flaw born of laziness — it is the logically simplest possible representation of "moving pictures," and it is exactly correct in one sense: it loses zero information. Every pixel of every frame arrives perfectly. §4 puts a number on what that honesty costs.

ARC 04 · WHY IT FAILS

The raw-bitrate formula, computed all the way out

The formula behind every number in this chapter is simple multiplication:

THE FORMULA

raw bitrate = width × height × bits-per-pixel × frames-per-second

For a standard 1080p frame at 24-bit color (8 bits each for red, green, blue) and 30 frames per second:

1920 × 1080 × 24 bits × 30 fps = 1,492,992,000 bits/sec ≈ 1.49 Gbps

That is one and a half gigabits, every second, for a single 1080p30 stream — before a single byte of audio, metadata, or container overhead. In bytes: roughly 186 MB every second, which is about 671 GB for a single one-hour episode, uncompressed.

Now put that next to chapter 1's real numbers. A 2007-era home connection at a generous 5 Mbps is short of the raw requirement by a factor of roughly 300×. A very good 2016-era connection at 50 Mbps is still short by a factor of roughly 30×. There is no realistic consumer bandwidth figure anywhere in this course's timeline that closes this gap — this is not a "wait a few years for faster internet" problem the way chapter 1's margin was; it is a fundamentally different order of magnitude that no plausible near-term bandwidth growth erases on its own.

Scale confirms it's structural, not anecdotal. Multiply that one stream's raw bitrate by even a modest fraction of Netflix's real subscriber base watching concurrently, and required backbone capacity would run into the hundreds of terabits per second — a figure with no relationship to actual global internet backbone capacity, then or now. Raw video isn't merely inconvenient to stream; it is categorically incompatible with internet delivery at any scale beyond a handful of simultaneous viewers on a local, dedicated, oversized pipe.

ARC 05 · BETTER SOLUTION

Two kinds of redundancy, and the frame types built to exploit them

The fix isn't a clever transmission trick — it's noticing that raw video, as honestly encoded by §3's naive approach, contains an enormous amount of redundant information that carries little or no additional visual meaning. There are exactly two kinds worth exploiting, and modern codecs are built entirely out of techniques targeting each:

Every modern codec — H.264, VP9, HEVC, AV1 — is built on exactly this I/P/B foundation, refined with better prediction, better transforms, and better entropy coding. Nothing in chapter 3 replaces this model; it only makes each of these three frame types squeeze out more redundancy per bit spent.

ARC 06 · WHY THAT STILL COSTS

Prediction isn't free: the costs I/P/B frames introduce

Exploiting redundancy converts a delivery problem into a set of new engineering costs — real ones, that later chapters directly address:

  • Lossy by construction. Real compression (ch. 3's transform-and-quantize step) throws away information the eye is less likely to notice — it is not merely "clever packing" of the exact same data, it is a genuine, deliberate quality/size trade that must be tuned per title and per use case (ch. 5's per-title encoding).
  • Decode dependency chains. A P-frame is meaningless without the frame(s) it predicts from; a B-frame needs frames from both directions. Lose or corrupt an I-frame and every frame that depends on it, directly or transitively, becomes undecodable until the next I-frame arrives.
  • Seeking and channel-changing get harder. A player can only start decoding cleanly at an I-frame — you cannot jump to an arbitrary P- or B-frame and decode it correctly without first decoding everything it depends on. This is precisely why "seek points" in a stream are I-frame boundaries, not arbitrary timestamps.
  • Encoding is now genuinely expensive computation. Finding good motion vectors (where in a reference frame does this block of pixels come from?) is a real search problem, and doing it well is far more computationally expensive than simply reading and transmitting raw pixels — a cost that chapter 3 shows scales dramatically with codec sophistication (AV1 encoding is markedly more expensive than H.264).
THE ENGINEERING TRADE, STATED PLAINLY

You cannot get "raw-video honesty" (§3), "internet-deliverable size" (this section's fix), and "trivial, dependency-free playback" simultaneously. Every real codec design (ch. 3) is a specific, negotiated point on this three-way trade — more aggressive prediction buys smaller files at the cost of longer, more fragile decode dependency chains and heavier encode computation.

A DETAIL THAT SURPRISES PEOPLE THE FIRST TIME

B-frames predict from frames after them in display order, which means the decoder must already have decoded a "future" frame before it can decode the B-frame that comes before it on screen. Streams are therefore transmitted and decoded in a different order than they are displayed — the decoder reorders frames internally before handing them to the display. §13's code walkthrough shows this reordering concretely.

WHY LONGER GOPS AREN'T A FREE LUNCH

A longer GOP means fewer expensive I-frames per second of video — great for compression efficiency. It also means a bigger blast radius if a packet carrying part of that GOP is lost (more frames depend, directly or transitively, on the one I-frame at the start) and coarser seek granularity (you can only start clean playback at an I-frame boundary). Real encoders pick a GOP length as a deliberate trade, often aligned to segment boundaries in chunked delivery — a connection to chapter 6's manifest-driven streaming that will make more sense once you've seen both halves.

ARC 09 · TRADEOFFS

I-frame-only vs. P-heavy vs. B-heavy encoding

There is no universally correct GOP composition — only a different placement of the same costs:

STRATEGYCOMPRESSION EFFICIENCYSEEK / ERROR RESILIENCEENCODE COST
I-frame only worst — no redundancy removed between frames best — every frame independently decodable cheapest — no motion search needed
I + P frames good — exploits temporal redundancy one direction moderate — dependency chains, but only forward moderate — one motion search per P-frame
I + P + B frames best — exploits redundancy from both directions worst — longest dependency chains, reordering required highest — motion search against multiple references

Streaming video overwhelmingly chooses the third row: the compression win is large enough, and encoding is a one-time (or few-time) cost paid once per title, amortized across every subsequent playback — while playback happens far more often than encoding, so shifting cost toward encode time and away from bits-on-the-wire is almost always the right trade for a service with Netflix's scale of concurrent viewership.

ARC 11 · REAL-WORLD INCIDENTS / HISTORY

This exact wall was hit before the internet needed to care

Raw video's size problem is not a streaming-era discovery. It is a genuinely older, real, and well-documented constraint from physical digital media, which is instructive because it shows the same equation forcing the same answer in a completely different context:

VideoCD (1993): the same equation, applied to a disc instead of a network

The Video CD format, standardized in 1993, aimed to deliver roughly 74 minutes of video on an ordinary 650 MB compact disc — a real, hard physical storage ceiling, not a variable network constraint. Doing that required MPEG-1 compression, one of the first mainstream formats to use the I/P/B-frame motion-compensation model this chapter derives, because uncompressed video for that runtime would have needed vastly more capacity than any affordable consumer disc of the era could hold. The lesson generalizes directly to streaming a decade later: any time the available capacity (disc space then, bandwidth now) is dramatically smaller than raw video's size, the compression techniques this chapter introduces stop being optional and become the entire mechanism that makes the product possible at all.

Industry pattern: undercompressed early online video

Before internet-video codecs and bitrates matured, early attempts at streaming video over dial-up and early broadband connections in the 1990s and early 2000s were widely and publicly criticized for small, blocky, low-frame-rate playback — a direct, visible symptom of trying to fit too much raw information through too small a pipe, and a real, general industry pattern rather than a single Netflix-specific incident (Netflix's own 2007 launch, covered in chapter 1, deliberately targeted a bitrate its era's codecs could make watchable, informed by exactly this earlier, publicly visible failure pattern elsewhere in the industry).

Reconstructing the core arithmetic and the reorder step

pseudocoderawBitrate.* — the §4 formula as code
function rawBitrateBps(width, height, bitsPerPixel, fps):
    pixelsPerFrame = width * height
    bitsPerFrame = pixelsPerFrame * bitsPerPixel
    return bitsPerFrame * fps          // e.g. 1920*1080*24*30 ≈ 1.49 Gbps

function rawBytesForDuration(bitrateBps, seconds):
    return (bitrateBps / 8) * seconds   // e.g. one hour at 1.49 Gbps ≈ 671 GB
pseudocodemotionCompensate.* — the core idea behind P/B-frames
// Illustrative simplification of motion-compensated prediction.
function predictBlock(currentBlock, referenceFrame, searchRange):
    bestVector = (0,0); bestCost = INFINITY
    for (dx, dy) in searchRange:               // motion search: expensive, real computation
        candidate = referenceFrame.blockAt(currentBlock.x+dx, currentBlock.y+dy)
        cost = pixelDifference(currentBlock, candidate)
        if cost < bestCost:
            bestCost = cost; bestVector = (dx, dy)
    residual = currentBlock - referenceFrame.blockAt(currentBlock.x+bestVector.x, currentBlock.y+bestVector.y)
    return { vector: bestVector, residual: residual }   // transmit vector + small residual,
                                                     // NOT the block's raw pixels
pseudocodereorderForDecode.* — why decode order ≠ display order
// display order:  I0 B1 B2 P3 B4 B5 P6
// B1 and B2 predict from BOTH I0 (past) and P3 (future) — so P3 must be
// decoded before B1/B2, even though it displays AFTER them.
function decodeOrder(displayOrderFrames):
    return ["I0", "P3", "B1", "B2", "P6", "B4", "B5"]
    // decoder holds P3 in memory while decoding B1/B2, THEN releases
    // frames to the display in the original I0 B1 B2 P3 B4 B5 P6 order
WHY IT'S BUILT THIS WAY

1. Vectors + residuals, not raw blocks. A motion vector plus a small correction is almost always smaller than a block's raw pixels whenever motion is smooth and coherent — which most real video is, most of the time. 2. Reordering is the decoder's problem, not the network's. Frames are transmitted in decode order (so every dependency is already available when needed) and the decoder itself re-sorts them into display order — pushing the complexity into one well-tested component instead of the wire format. 3. Search range is a deliberate cost knob. A wider motion-search range finds better matches (smaller residuals, better compression) at higher encode-time computational cost — exactly the encode-complexity-vs-efficiency trade chapter 3 revisits for entire codecs, not just this one step.
