POSTGRESQL INTERNALS · CHAPTER 07

Transactions & Isolation:
From Read Committed to SSI

Chapter 6 gave you the byte-level machinery of tuple versions — xmin, xmax, HOT chains, freezing. This chapter answers the question that machinery exists to serve: when two transactions run at the same time against the same rows, what is each one actually allowed to see, and what can go wrong that the SQL standard never quite defines precisely enough to protect you? You'll derive the anomaly taxonomy from first principles, watch snapshot isolation quietly fail on a case the standard doesn't even name, and then meet the algorithm — Serializable Snapshot Isolation — that closes the gap without reverting to a global lock.

ARC 01 · THE PROBLEM

Concurrency is a promise you can only half keep

Every transactional database sells the same fiction: your transaction runs alone against the database. It's a fiction because dozens of other transactions are, in fact, reading and writing the same rows at the same instant — for correctness and for performance, you cannot actually run them one at a time (chapter 1's Little's Law argument applies here too). So the real question a database answers isn't "do transactions run in isolation" — none genuinely do — it's how much of the illusion do you get, and what breaks when the illusion has a crack in it.

Define the crack precisely, because "isolation" is a word people use loosely. Two transactions run concurrently against overlapping rows. Depending on exactly what each is allowed to observe of the other's in-flight or recently-committed work, you get a specific, nameable anomaly — a result that could not have happened if the two transactions had truly run one after the other. The anomaly taxonomy, derived from first principles rather than memorized as SQL-standard trivia:

  • Dirty read — you see a write from a transaction that hasn't committed yet, and might never commit.
  • Non-repeatable read — you read the same row twice in one transaction and get two different values, because someone else committed a change in between.
  • Phantom read — you run the same predicate query twice and get a different set of rows, because someone else inserted or deleted a matching row in between.
  • Lost update — two transactions each read a value, each compute a new value based on what they read, and one's write silently overwrites the other's — the first writer's update is lost as if it never happened.
  • Read skew — you read two related rows that are supposed to satisfy some invariant together, but you catch them at different points in someone else's multi-row update, seeing a combination that never actually existed at any single instant.
  • Write skew — the one that will take the rest of this chapter to earn: two transactions each read an overlapping set of rows, each writes to a disjoint row based on what they read, both commit, and the combined result violates an invariant that either transaction alone would have preserved.
WHY THIS MATTERS FOR THE REST OF THE COURSE

Every anomaly above is a specific failure of a general promise: that the concurrent schedule is equivalent to some serial (one-at-a-time) execution of the same transactions. That promise, called serializability, is the actual gold standard — the SQL standard's four named levels are four different, partial approximations of it, and PostgreSQL implements exactly three distinct behaviors (not four) to realize them. Chapter 8's lock manager is the mechanism that makes any of this enforceable; this chapter is about what guarantee you're buying with it.

DEEP CONTEXT · WHY THE STANDARD'S DEFINITIONS FAIL FOR POSTGRESQL

SQL-92 defines isolation levels purely in terms of which of three phenomena (dirty read, non-repeatable read, phantom) they forbid. That framing implicitly assumes a locking implementation, where "does this schedule ever expose an uncommitted write" is the right question. MVCC systems don't expose uncommitted writes to snapshot-based readers at ANY level above Read Uncommitted — so by the standard's own phenomena, PostgreSQL's Read Committed already looks like it satisfies most of what the standard asks of much stronger levels, while still permitting write skew, an anomaly the standard's three named phenomena don't even describe. Berenson et al.'s 1995 Microsoft Research paper, "A Critique of ANSI SQL Isolation Levels," is the paper that named this gap precisely and introduced write skew and other phenomena the standard had simply missed.

ARC 03 · NAIVE SOLUTION

Attempt #1: strict two-phase locking, textbook correct

Derive it the way a first course in concurrency control would: if the danger is two transactions touching the same data unsafely, make every read and write acquire a lock, and never release any lock until commit (strict two-phase locking, S2PL). This is provably serializable — it is, in fact, the textbook proof technique for why locking protocols work at all — and several production databases genuinely run something close to it under "serializable" mode.

SQL / pseudocodestrict_2pl.pseudo — the textbook-correct strawman
-- Every statement acquires a lock before touching a row, and EVERY lock
-- (read or write) is held until COMMIT or ROLLBACK. No exceptions.

BEGIN;
  SELECT balance FROM accounts WHERE id = 1;   -- acquire SHARED lock on row 1, held to commit
  SELECT on_call  FROM doctors  WHERE id = 7;   -- acquire SHARED lock on row 7, held to commit
  -- ... application logic decides what to write ...
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- upgrade to EXCLUSIVE, held to commit
COMMIT;                                            -- ALL locks released only now

This gets the correctness proof for free: any schedule S2PL permits is provably equivalent to some serial order of the same transactions, because the two-phase discipline (acquire-only, then release-only, no interleaving) prevents exactly the interleavings that would make the schedules diverge. ARC 04 · WHY IT FAILS

Readers block writers, writers block readers — the cost is structural, not incidental

S2PL's correctness proof is airtight; its throughput is not. Three structural costs, each a direct consequence of "every read takes a lock held to commit":

  • Readers and writers queue behind each other. A long-running read holds a shared lock for its entire duration; any writer touching the same row queues behind it, and vice versa. This is precisely the cost MVCC (chapter 5) was invented to eliminate — under pure S2PL you have reintroduced it deliberately, in exchange for the correctness proof.
  • Deadlocks are a normal, expected event, not an edge case. Two transactions acquiring locks on the same two rows in opposite orders will deadlock at some nonzero rate under any real concurrent workload; the database must detect the cycle and abort one participant — an abort born purely of lock-acquisition order, unrelated to any actual data conflict.
  • Lock-table contention scales with concurrency, not with data conflict. Every row touched, read or written, registers in a shared lock manager that every other transaction's lock requests must check. At high connection counts (chapter 1's territory again) the lock manager itself becomes a shared bottleneck even when transactions rarely conflict on actual data.
THE NUMBERS

Take a workload where 95% of transactions are read-only reporting queries averaging 200 ms, and 5% are short OLTP writes averaging 2 ms, both touching a shared "settings" row. Under pure S2PL, every write queues behind whichever reads are mid-flight holding a shared lock on that row — a single 200 ms report can delay dozens of 2 ms writes behind it, and p99 write latency inherits the tail of report latency, not of write latency. This is the same head-of-line problem chapter 1 diagnosed in the iterative server, relocated from the process scheduler to the lock manager. MVCC's entire pitch is eliminating exactly this coupling for the common read/write mix — which is why almost nobody runs pure S2PL as their default isolation mechanism, PostgreSQL included.

So the fix has to preserve MVCC's readers-never-block-writers property while still answering the isolation question honestly. That means picking, deliberately, how much of the serializability promise you give up for concurrency — and living with the specific anomaly that choice reopens.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three real levels, and exactly what each one buys back

PostgreSQL implements three distinct isolation behaviors, not four — READ UNCOMMITTED is accepted syntax that silently behaves as READ COMMITTED, because MVCC makes true dirty reads structurally impossible without extra work to expose them; there's no cheaper, weaker mode to fall back to. Step through what each of the other three actually does, mechanically:

Read Committed's re-check dance: EvalPlanQual

Read Committed's per-statement snapshot creates a subtle problem: what should UPDATE ... WHERE balance > 100 do if, between when the statement started and when it reaches a particular row, some other transaction concurrently updated that exact row and committed? The row your statement's snapshot sees might already be stale. PostgreSQL's answer is EvalPlanQual (EPQ): when an UPDATE or DELETE finds that the row it's about to touch was concurrently modified by a transaction that has since committed, it re-fetches the latest committed version, re-evaluates the statement's WHERE clause and any relevant expressions against that version, and only then proceeds — silently, from the application's point of view, except for the latency of the re-check.

THE CLINCHING ARGUMENT FOR MVCC-BASED LEVELS OVER S2PL

Read Committed and Repeatable Read both deliver their entire guarantee using snapshots built from data chapter 5 and 6 already maintain (xmin/xmax visibility) — no lock is held on a row merely because it was read. Only actual writes take row locks, and only for as long as needed to serialize with other writers, never with readers. This is the direct payoff of paying MVCC's versioning cost (chapter 6): two of PostgreSQL's three isolation levels are essentially free concurrency-wise, funded entirely by infrastructure you already understand.

ARC 06 · WHY THAT STILL FAILS

Snapshot isolation's hole: write skew, made concrete

Repeatable Read (PostgreSQL's implementation of snapshot isolation) prevents every anomaly in §1's list except one — and that one isn't a corner case, it's a routine invariant-violation waiting to happen anywhere a business rule spans more than one row. The canonical example, due to Fekete et al. and repeated in every SSI paper since: a hospital rule requires at least one doctor on call at all times. Two doctors, both on call, each independently decide they're free to go home because "someone else is still on call":

SQLwrite_skew.sql — two transactions, snapshot isolation, invariant violated
-- invariant: COUNT(*) FROM doctors WHERE on_call = true AND shift = 'today' >= 1

-- Transaction A (Dr. Alice)                    Transaction B (Dr. Bob)
BEGIN ISOLATION LEVEL REPEATABLE READ;         BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors                      SELECT count(*) FROM doctors
  WHERE on_call AND shift='today';                WHERE on_call AND shift='today';
-- sees 2 (both Alice and Bob)                  -- sees 2 (both Alice and Bob)
--   -- both snapshots were taken before either write --
UPDATE doctors SET on_call=false
  WHERE name='Alice';                          UPDATE doctors SET on_call=false
                                                  WHERE name='Bob';
COMMIT;  -- succeeds, no conflict detected          COMMIT;  -- succeeds, no conflict detected -- SAME ROW never touched by both!

-- Result: BOTH doctors are now off call. Zero doctors on call. Invariant violated.
-- Neither transaction wrote a row the other transaction wrote OR read in the
-- write/write sense snapshot isolation actually checks -- Alice wrote Alice's
-- row, Bob wrote Bob's row. Snapshot isolation's conflict detection (first-
-- committer-wins on the SAME row) has nothing to say about this at all.

WHY THIS ISN'T A CORNER CASE

Write skew's shape — read a set of rows, decide based on their aggregate state, write a different row based on that decision — is the shape of an enormous fraction of real business logic: inventory checks before decrementing a different SKU's count, seat availability checks before booking a different seat, balance checks across accounts before a transfer. Under Repeatable Read alone, every one of these is a latent invariant violation waiting for the right (or wrong) concurrent timing. The traditional workaround — SELECT ... FOR UPDATE on the rows you merely read, converting a read into a write-lock acquisition — works, but it requires the application developer to correctly identify every such read in advance. §7's mechanism is PostgreSQL's answer for when you'd rather the database catch this automatically.

ARC 07 · FINAL ARCHITECTURE

SSI: catch write skew without ever blocking a reader

Serializable Snapshot Isolation (Cahill, Röhm & Fekete, University of Sydney, landed in PostgreSQL 9.1 by Kevin Grittner and Dan Ports) starts from ordinary snapshot isolation — nothing about the read path changes, no reader ever blocks or is blocked — and adds a second, independent tracking system purely to detect the pattern write skew requires, then abort one participant before the damage commits. THE CENTRAL DESIGN BET: DETECT A PATTERN, NOT A CYCLE

True serializability violations correspond to a cycle in the graph of conflicts between committed transactions (the classical theory: a schedule is serializable iff its conflict graph is acyclic). Tracking full cycles across arbitrarily many transactions is expensive and requires seeing the whole graph. Cahill's thesis proves something narrower and far cheaper to check: every cycle that can actually occur under snapshot isolation must contain two consecutive rw-antidependency edges sharing a "pivot" transaction. PostgreSQL only ever needs to notice that local, three-transaction pattern — not reconstruct or search a graph — to catch every real violation. The cost of the shortcut: it sometimes fires on a structure that, traced through to the full graph, wasn't actually part of a cycle. That's an accepted, deliberate false-positive rate in exchange for O(1) bookkeeping per conflict instead of global cycle detection.

ARC 08 · INTERNAL IMPLEMENTATION

SIREAD locks, conflict edges, and the moment PostgreSQL decides to abort

Three pieces, in the order a transaction actually encounters them: (a) the struct that represents a serializable transaction's state, (b) how a read registers a predicate lock and how a write checks for conflicts against one, and (c) the exact rule for recognizing a dangerous structure.

(a) The bookkeeping struct — real fields, simplified

Cstorage/lmgr/predicate.c (via include/storage/predicate_internals.h) — simplified but structurally faithful
typedef struct SERIALIZABLEXACT
{
    VirtualTransactionId vxid;
    SerCommitSeqNo prepareSeqNo;
    SerCommitSeqNo commitSeqNo;      /* assigned at commit; orders xacts for conflict checks */

    struct SERIALIZABLEXACT *finishedLink;

    SHM_QUEUE outConflicts;          /* rw-edges where I am the READER (I read something someone else later wrote) */
    SHM_QUEUE inConflicts;           /* rw-edges where I am the WRITER (I wrote something someone else earlier read) */

    bool didWrite;                /* read-only xacts are cheaper to reason about -- see §10 */
    bool possibleUnsafeConflict;
    bool pendingRoConflictOut;

    int flags;                     /* SXACT_FLAG_DOOMED, SXACT_FLAG_ROLLED_BACK, ... */
} SERIALIZABLEXACT;

/* One SIREAD lock: "this xact read (or would-have-matched) this target" */
typedef struct PREDICATELOCK
{
    PREDICATELOCKTARGETTAG tag;      /* identifies relation, page, or specific tuple */
    SERIALIZABLEXACT *sxact;
} PREDICATELOCK;

Notice what's absent: no blocking primitive anywhere in this struct. A SERIALIZABLEXACT doesn't wait on anything to acquire a SIREAD lock — taking one is pure bookkeeping, cheap enough to do on every row a serializable transaction reads.

(c) The dangerous structure, precisely

Given three transactions T1, T2, T3 (T1 and T3 may be the same transaction in the two-transaction write-skew case, or distinct in the general case), a dangerous structure is: T1 →rw T2 →rw T3, where T2 is the pivot, and T1 has not yet committed before T3 commits (the precise commit-order condition from Cahill's proof — a dangerous structure only becomes an actual violation if it's possible for T1 to still be in-flight when T3 commits). PostgreSQL doesn't wait to see if a full cycle materializes; the instant this local pattern is confirmed, it aborts either the pivot or one of its neighbors with SQLSTATE 40001.

Predicate locks must not exhaust shared memory the way an unbounded per-row lock table would under a large scan — so, like the ordinary lock manager, SSI promotes granularity upward when a transaction's tuple-level locks on one page (or one relation) get too numerous:

WHY GRANULARITY PROMOTION MEANS MORE FALSE POSITIVES UNDER LOAD

max_pred_locks_per_page and max_pred_locks_per_relation (both default 64, alongside max_pred_locks_per_transaction governing total SIREAD locks) force a promotion from tuple-level to page-level, or page-level to relation-level, once a transaction's own lock count on that granularity gets too high. A relation-level SIREAD lock conflicts with any write to any row in that relation — not just the rows actually read — which is exactly the false-positive tradeoff from §7's callout, now driven by memory pressure rather than by the theoretical dangerous-structure shortcut. A large sequential scan under SERIALIZABLE is measurably more abort-prone than an index lookup touching three rows, for this reason specifically.

The Oracle row is the one worth dwelling on precisely because it's a trap for anyone reasoning by product-name analogy: an engineer who has used Oracle's SERIALIZABLE and assumes PostgreSQL's behaves the same way is right about most anomalies and wrong about exactly the one — write skew — this chapter spent §6 making concrete. "Serializable" is a claim about a guarantee, not a fixed implementation, and verifying which anomalies a specific product's specific level actually forecloses is the only way to know what you're really buying.

ARC 10 · PERFORMANCE CHARACTERISTICS

What SSI costs, and the optimizations that claw it back

  • Per-read cost: O(1) amortized SIREAD lock acquisition per row read under SERIALIZABLE — cheap, but not free; Read Committed and Repeatable Read pay none of this.
  • Per-write cost: checking a write against existing SIREAD locks on the target is O(locks on that target), bounded by the granularity-promotion limits from §8.
  • Memory: bounded by max_pred_locks_per_transaction (default 64) — promotion to page/relation granularity is precisely the mechanism that keeps this from growing unboundedly with scan size, at the cost of coarser (more false-positive-prone) conflict detection, exactly as §8's slider showed.
  • Read-only optimization: a transaction that never writes cannot be the pivot of a dangerous structure requiring it to abort for a write-skew reason in the same way a writer can — PostgreSQL specifically recognizes read-only transactions and, combined with DEFERRABLE, can grant them a safe snapshot — at the cost of the transaction blocking briefly at BEGIN until such a snapshot is available, in exchange for running its entire duration with zero further SSI overhead and zero abort risk.
  • Abort/retry cost: the one SSI cost that dominates in practice under heavy write contention — every 40001 is a transaction that did real work and must be retried by the application from scratch; designing retry loops is a mandatory part of using SERIALIZABLE correctly, not an edge case to handle defensively.

ARC 11 · REAL-WORLD PRODUCTION

Where isolation-level choice actually bites

Incident pattern 1: the silent lost update in a "read-then-write" balance check

A recurring shape across financial and inventory systems built on Read Committed by default: application code reads a balance or stock count, computes a new value in the application tier, then writes it back with a plain UPDATE — no WHERE balance = :original_value guard, no SELECT ... FOR UPDATE. Under Read Committed, two concurrent instances of this pattern each get their own per-statement snapshot for the read, compute independently, and the second write simply clobbers the first — a textbook lost update, invisible in testing (which rarely has real concurrency) and visible only under production load, typically discovered as "the numbers don't add up" rather than as an exception. The fix, in order of correctness guarantee: push the read-modify-write into a single atomic statement (UPDATE ... SET balance = balance - 100 needs no read at all); failing that, SELECT ... FOR UPDATE to take a row lock at read time; failing that, move the whole transaction to SERIALIZABLE and add a retry loop.

Incident pattern 2: write skew surviving code review because nobody looked for it

Booking and scheduling systems are the most common real-world home for write skew: two concurrent requests each check "is there still capacity" against an aggregate (seats remaining, on-call staff, available inventory bucketed by category) and then write to a different specific row (a specific seat, a specific staff member's shift, a specific SKU) than the one they aggregated over. Because the two transactions' write sets never intersect, ordinary snapshot-isolation conflict detection (first-committer-wins on the same row) has nothing to catch, and the invariant violation ships to production, discovered only when the business rule it broke becomes visible externally (double-booked capacity, zero on-call coverage — exactly §6's example). Teams that catch this in design review are the ones that explicitly ask, for every "check an aggregate, then write a row" pattern, "what if two of these run at the exact same instant" — and either serialize the check with FOR UPDATE against every row the aggregate depends on, or move the transaction to SERIALIZABLE and let SSI's conflict graph do that reasoning automatically.

Incident pattern 3: retry-storm amplification after adopting SERIALIZABLE

A team migrates a contended, business-critical code path to SERIALIZABLE to eliminate a class of correctness bugs, ships it, and discovers that at peak load a meaningful fraction of transactions now fail with 40001 — expected and by design — but the application's retry logic retries immediately, in a tight loop, with no backoff. Under sustained contention this manufactures a self-inflicted retry storm: each retry re-does the transaction's full work, re-acquires SIREAD locks, and has a nontrivial chance of hitting another dangerous structure immediately, multiplying load precisely when the system is already contended enough to be aborting transactions. The fix is the same lesson every optimistic-concurrency system eventually teaches its adopters: retry with jittered exponential backoff, treat 40001 as an expected, budgeted outcome in capacity planning (not an exceptional error), and — where the write-skew risk is narrow and well-understood — prefer a targeted SELECT ... FOR UPDATE over blanket SERIALIZABLE, which trades a small amount of explicit locking discipline for a much lower abort rate under load.

First, where a read registers itself — every serializable-mode heap/index fetch passes through this:

Cstorage/lmgr/predicate.c — PredicateLockTuple(), simplified
void
PredicateLockTuple(Relation relation, HeapTuple tuple, Snapshot snapshot)
{
    if (!SerializationNeededForRead(relation, snapshot))
        return;             /* not a SERIALIZABLE xact -- zero cost for RC/RR */

    PREDICATELOCKTARGETTAG tag;
    SET_PREDICATELOCKTARGETTAG_TUPLE(tag, relation, tuple->t_self);

    /* Pure bookkeeping: register "MyXact read this tuple." No lock
     * is acquired against any OTHER transaction here -- this cannot
     * block, and nothing else can block on it either.               */
    CheckAndPromotePredicateLockRequest(&tag);   /* may upgrade to page/relation granularity */
    CreatePredicateLock(&tag, MySerializableXact);
}

Then, where a write discovers it collided with something a still-active (or already-committed) transaction read — this is the function that actually creates an rw-antidependency edge:

Cstorage/lmgr/predicate.c — CheckForSerializableConflictOut(), simplified
void
CheckForSerializableConflictOut(Relation relation, HeapTuple tuple, Snapshot snapshot)
{
    if (!SerializationNeededForRead(relation, snapshot))
        return;

    /* Find every SERIALIZABLEXACT holding a SIREAD lock on this tuple
     * (or its page/relation, if promoted) that is NOT me.            */
    foreach(reader, PredicateLockConflictingXacts(relation, tuple))
    {
        if (reader == MySerializableXact)
            continue;

        /* MySerializableXact is about to WRITE something 'reader' READ:
         * that's an rw-antidependency edge, reader -> MySerializableXact.  */
        SetRWConflict(reader, MySerializableXact);

        /* THE ONLY CHECK THAT MATTERS: does this new edge complete a
         * dangerous structure -- i.e. does 'reader' ALSO have an incoming
         * rw-edge from some xact that hasn't committed yet? If so, abort
         * NOW rather than wait to see if a full cycle ever closes.        */
        if (MightConstituteDangerousStructure(reader, MySerializableXact))
            ereport(ERROR,
                (errcode(ERRCODE_T_R_SERIALIZATION_FAILURE),
                 errmsg("could not serialize access due to read/write dependencies among transactions")));
    }
}
WHY THE DEVELOPERS WROTE IT THIS WAY — TWO CHOICES TO STEAL

1. Keep SSI's bookkeeping entirely orthogonal to the ordinary lock manager. predicate.c shares no code path with lock.c's object locks or deadlock.c's cycle detection — SIREAD locks never block anything, so they need none of the wait-queue or deadlock-detection machinery real locks require. Keeping the two systems separate meant SSI could be added in 9.1 without touching the lock manager other people's code already depended on. 2. Check for the danger the instant an edge forms, not later. MightConstituteDangerousStructure() runs synchronously inside the write that created the new edge — no background scanner, no periodic graph walk. The cost of the check is paid exactly once, by exactly the transaction whose action made it necessary, which is the same "attribute the cost to the party that caused it" instinct you'll see repeated in the lock manager's own deadlock detection (chapter 8).
