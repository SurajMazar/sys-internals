UBER ENGINEERING INTERNALS · CHAPTER 07

Trip Lifecycle:
State Machines Across a Distributed System

Chapters 1 through 6 each assumed a trip, once matched and priced, simply "happens." This chapter opens that assumption. A trip is a long-lived object that must move through a precise sequence of states — requested, matched, en route, arrived, in progress, completed — while three or more independently deployed services (dispatch, payments, notifications) all need a consistent view of exactly which state it's in, at every moment, even while machines crash, networks drop packets, and clients retry. Get this wrong and the failure mode isn't a glitchy progress bar — it's a rider charged twice, or a driver stranded mid-trip with no system aware anything is wrong.

ARC 01 · THE PROBLEM

A trip is a distributed, long-lived transaction with money attached

Everything upstream of this chapter — matching (chapter 4), routing (chapter 5), pricing (chapter 6) — resolves in seconds and hands off a decision. A trip itself does not resolve in seconds. It lives for minutes to hours, crosses a rider's phone, a driver's phone, and a fleet of backend services, and at the end of it a real payment moves and a real record is written that both parties may dispute later. That combination — long-lived, distributed, and financially consequential — is what makes the trip's state the hardest state in this course to get wrong.

Unpack it into concrete requirements:

  • Many independent services must agree. Dispatch needs to know a trip is still "matched" to avoid double-assigning the driver. Payments needs to know the exact moment a trip becomes "completed" to charge exactly once. Notifications needs every transition to tell the rider and driver apps what to show. None of these run in the same process, and none of them can be allowed to hold a private, divergent opinion about what state the trip is in.
  • The state must outlive any single machine. A trip that started five minutes ago must still be trackable if the exact server that recorded "driver arrived" crashes one second later. State that lives only in one process's memory is state that a routine deploy, an OOM kill, or a hardware fault can simply erase.
  • Transitions are not always driven by clean, first-time events. Mobile networks retry. A phone that thinks its "trip completed" call failed will call again — Uber's own driver and rider apps run on exactly the unreliable networks chapter 3 described. Some transitions carry money, so a retried event must produce the identical effect as the original, not the effect twice.
  • Silence must be a first-class transition, not an unhandled case. A driver's phone loses signal in a tunnel or the app is killed by the OS mid-trip. Nothing "happens" — no event arrives at all. A correct system must notice the absence of an expected signal and act, on a timer, rather than waiting forever for an event that may never come.
  • Almost every state needs an exit ramp. Riders cancel. Drivers cancel. Matches expire. A trip's state machine is not a straight line with one on-ramp; it is a graph with cancellation and timeout edges leaving nearly every node, each with its own real-world consequence (a cancellation fee, a re-match, a support ticket).
WHY THIS MATTERS FOR THE NEXT 11 CHAPTERS

This chapter is the hinge between the two arcs of this course. Everything before it (chapters 1–6) is about deciding something — a match, a route, a price. Everything from chapter 8 onward is about the distributed-systems machinery that makes decisions like that survive at Uber's scale: services instead of one process (chapter 8), RPC and service meshes connecting them (chapter 9), an event backbone carrying their messages (chapter 10), and datastores durable enough to hold the state itself (chapters 14–17). The trip state machine is the first place in this course where you can't hand-wave "the backend handles it" — you have to say exactly which service owns the state, exactly how it survives a crash, and exactly why a retry can't cost a rider twice. Every later chapter's machinery exists, in part, to make this one correct.

DEEP CONTEXT · WHY "IDEMPOTENCY KEY" BECAME STANDARD VOCABULARY

The general technique this chapter leans on hardest — attaching a client-generated idempotency key to any request that has a side effect, so a retried request produces the original effect exactly once — is not unique to Uber. It became industry-standard vocabulary largely through payments APIs (Stripe's public API documentation popularized the exact term "idempotency key" for this purpose in the mid-2010s), for the obvious reason that payments are where a duplicate side effect is most visible and most damaging. Any company moving money over an unreliable network converges on the same mechanism independently, because the alternative — trusting that every client only ever calls you once — is simply false at scale. This chapter teaches the general mechanism precisely because it's general: the same pattern appears in streaming-event consumer processing (chapter 10's event backbone), in payment-gateway integrations everywhere, and in this trip service.

ARC 03 · NAIVE SOLUTION

Attempt #1: one variable, one process, trust every message once

Start honestly, the way any engineer would on day one. A trip has an obvious, small set of states. The simplest possible implementation is a single in-memory object, mutated directly as events arrive, living inside whichever process happens to be handling this trip right now:

pseudocodenaive_trip.py — the strawman, annotated
class Trip:
    def __init__(self, trip_id):
        self.id = trip_id
        self.state = "requested"          # just a string, in RAM
        self.driver_id = None
        self.fare_charged = False

    def on_event(self, event):
        # whatever event shows up, just apply it — no history, no check
        if event.type == "matched":
            self.state = "matched"; self.driver_id = event.driver_id
        elif event.type == "driver_arrived":
            self.state = "driver_arrived"
        elif event.type == "trip_completed":
            self.state = "completed"
            charge_rider(self.id)             # fires again on every retry!
            self.fare_charged = True

# one dict, in the memory of whichever server instance is handling requests right now
trips = {}   # trip_id -> Trip

This is not a silly starting point — for a demo, or a single-city pilot with a few hundred concurrent trips, it is genuinely adequate. Every state transition is a plain function call, there is no serialization overhead, and reasoning about "what happens next" is as simple as reading the function top to bottom. Watch what happens once more than one thing can go wrong at once.

ARC 04 · WHY IT FAILS

Quantify it: retries, crashes, and the cost of "just apply the event"

Three independent failure modes, each provable with arithmetic rather than intuition:

  • Duplicate side effects at real retry rates. Mobile clients on real networks retry failed requests — that is correct client behavior, not a bug. Even a conservative 0.3% effective retry rate on the single "trip completed" call, across a platform completing on the order of tens of millions of trips a day, is tens of thousands of duplicate completion events landing on backend services every single day. The naive handler above charges the rider again on every one of them, because nothing distinguishes "the same event, redelivered" from "a second, genuine event."
  • State loss on crash, at in-flight scale. At any given moment, a platform this size has on the order of hundreds of thousands of trips in some active, non-terminal state. If that dictionary lives in one process's memory, every deploy, OOM kill, or hardware fault doesn't just interrupt one request — it erases the current state of every trip that process happened to be holding, with no record of what state they were in a moment before the crash.
  • No cross-service agreement, ever. Dispatch, payments, and notifications each need their own copy of "what state is this trip in." If each service keeps its own in-memory guess, updated by whichever events happen to reach it, there is no mechanism forcing those guesses to agree — and a network partition or message reordering (chapter 3's whole subject, applied here to trip events instead of location pings) makes disagreement the default, not the exception.
THE CONCRETE FAILURE, IN DOLLARS

Say a completion event is retried because the acknowledgment to the driver app was lost on a flaky connection (the driver app never learns the first call succeeded, so it retries). The naive handler runs charge_rider() a second time. At an average fare of roughly $15–20, a duplicate-charge rate of even one in ten thousand completions, at tens of millions of trips a day, is thousands of double-charged riders daily — each one a support ticket, a refund, and a trust cost with the rider that a system-design review should have caught for free. This is precisely the class of bug an idempotency key exists to make structurally impossible, not merely unlikely.

So the fix must attack two separate problems at once: make the state durable and shared across services, and make transitions with side effects idempotent against redelivery. Section 5 builds both.

ARC 05 · BETTER SOLUTION

A durable, versioned state machine — with an idempotency ledger alongside it

Two changes, layered on top of each other. First: stop keeping the trip's state in any one process's memory. Persist it in a shared, durable store, keyed by trip id, with an explicit version number that increments on every transition — the same optimistic-concurrency pattern any system needs when more than one writer might touch the same row. Second: alongside the trip's state, keep a separate durable table of idempotency keys already processed, so any side-effecting event can be checked against "have I already done this?" before it's applied a second time.

From a variable to a durable, versioned recordSTEP-BY-STEP

Note precisely what each piece buys, because they solve different problems and neither one alone is sufficient: durability plus versioning solves "the state survives a crash and two writers can't silently clobber each other"; the idempotency ledger solves "a retried request can't repeat a side effect." A system with only the first still double-charges on retry; a system with only the second still loses all state the instant a process dies holding it in memory.

ARC 06 · WHY THAT STILL HURTS

Durability and idempotency are necessary — they are not the whole system

Be precise about what section 5's fix still leaves unsolved, because each gap is a real cost you pay, not a tuning oversight:

  • Every transition now costs a durable write. A read of the current state and version, a compare-and-swap write of the new state, and — for side-effecting transitions — a check-and-insert against the idempotency ledger. That is real latency (single-digit to double-digit milliseconds per hop, chapter 14–17's subject) on every single state change, paid by every trip, all the time — nothing here is free versus the naive in-memory version.
  • Concurrent writers still collide. Two services racing to transition the same trip (dispatch marking "driver arrived" at the same instant a timeout job marks "expired" because the driver's last location ping was stale) will have one of their compare-and-swap writes rejected by the version check. That's correct — it prevents corruption — but it means the losing service must detect the rejection and decide whether to retry, re-read, or give up, which is real application logic you now must write for every transition.
  • Durability doesn't detect silence. Persisting state changes says nothing about what to do when an expected event simply never arrives — a driver's phone dies mid-trip and no "trip completed" event is ever sent. A purely reactive, event-driven state machine sits in "in progress" forever unless something is actively watching the clock.
  • Someone still has to own the row. Persisting to "a shared datastore" doesn't answer which service is allowed to write it, under what locking discipline, or what happens when two teams' services both believe they own a transition. Durability is a storage property; ownership is an architecture decision — section 7 makes it.
THE PATTERN THIS IS CONVERGING ON

What's emerging is a version of the saga / orchestrator pattern: a single service that owns the trip's canonical state and is the only writer of it, coordinating the other services (dispatch, payments, notifications) by publishing what changed rather than letting them all write to the same row. Sections 7 and 8 build exactly that, plus the piece durability alone can't provide: an active timeout mechanism watching for silence.

WHY THIS IS AN ORCHESTRATOR, NOT A FREE-FOR-ALL

The alternative — letting dispatch, payments, and notifications each hold a copy of the trip's state and reconcile via events, with no single owner — is a real pattern (choreography, see chapter 10's fan-out consumers) and it is not wrong, but it trades a hard problem (who's allowed to write?) for a different hard problem (whose copy is authoritative when two disagree?). For state this consequential — money moves on it — this course's design keeps one explicit owner. ARC 08 · INTERNAL IMPLEMENTATION

The transition table, the handler, and the watchdog timer

Three pieces make this concrete: (a) an explicit table of which transitions are even legal, so illegal ones are rejected before they can corrupt anything; (b) the handler that applies an event exactly once; and (c) the timeout mechanism that fires when an expected event never shows up.

(a) The transition table — the real graph, not just the happy path

Every state has a small number of legal next states. Everything not listed is rejected outright — this is the cheapest possible defense against a corrupt or out-of-order event ever reaching the stored state.

(b) The watchdog: turning silence into a timer, not a hang

For every non-terminal state with a real-world expectation attached ("a matched driver should start moving within N seconds," "an in-progress trip should complete within a bounded multiple of its estimated duration"), the trip service schedules a timeout job when it enters that state, and cancels it the moment a legitimate transition fires first. If the timer fires before a transition arrives, the timeout event itself is just another input to the same handleEvent() — silence is not a special code path, it's a scheduled event like any other.

ARC 09 · TRADEOFFS

Four ways to own distributed, long-lived state

APPROACHWHAT IT BUYSWHAT IT COSTS
In-memory, single process (§3) zero latency per transition trivial to write state dies with the process no cross-service agreement duplicate side effects on retry
Durable row + idempotency ledger, single owner (this chapter) survives crashes one source of truth retries are safe a durable write per transition requires a watchdog for silence
Choreography — every service keeps its own copy, reconciled via events no single owner to overload or become a bottleneck whose copy wins on disagreement is genuinely hard debugging requires reconstructing global state from scattered events
Full workflow-engine orchestration (e.g. a durable-execution framework) timeouts, retries, and compensation steps are handled by the framework another piece of infrastructure to run and understand framework's execution model becomes a hard dependency
Client-side state (trust the app) no backend cost at all a rider's phone dying mid-trip loses the only copy of the truth — not viable when money is involved

The pattern to notice: every row that is viable at Uber's scale pays a real, ongoing cost — either latency per transition, architectural complexity in reconciliation, or a dependency on more infrastructure. There is no row that is simultaneously fast, simple, and safe when the state is long-lived, distributed, and has money attached; this chapter's choice (durable row, single owner, explicit watchdog) is a specific, defensible point on that tradeoff curve, not the only correct one.

ARC 10 · PERFORMANCE / SCALE CHARACTERISTICS

What the watchdog and the ledger actually cost at scale

Every non-terminal trip carries at least one live, scheduled timeout job; every side-effecting transition carries one idempotency-ledger lookup. Neither is free, and both must be budgeted explicitly:

  • Watchdog job volume scales linearly with in-flight trips. With roughly six non-terminal states each carrying a timer, a fleet with hundreds of thousands of concurrent trips is scheduling and cancelling on the order of a million timer operations at any given moment — this needs to be a purpose-built scheduling service (chapter 12 covers Uber's real internal scheduling infrastructure, Peloton, though that specific system targets compute jobs rather than per-trip timers), not a naive one-thread-per-timer implementation.
  • The idempotency ledger's lookup cost is the whole game. Every side-effecting transition pays one check-and-insert against the ledger before doing anything real. That lookup must stay O(1) regardless of how many keys have ever been recorded — an indexed key-value store (this course's chapters 15–16 cover exactly this shape of datastore), not a table scan.
  • Ledger entries must expire, or they grow forever. A completed trip's idempotency keys only need to be retained long enough to catch realistic redelivery windows (minutes, generously hours) — not forever. A TTL on ledger entries keeps the store's size bounded by recent traffic rather than all-time trip count.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

Where trip-state bugs actually surface

Uber has not published a detailed public postmortem specifically naming an internal trip-state-machine incident, so this section teaches the realistic, industry-standard incident pattern this class of system produces — the same pattern that has surfaced publicly, in some form, at essentially every company that moves money over unreliable mobile networks — and says so plainly rather than inventing a specific internal Uber event.

Pattern 1: the double-charge, traced to a missing idempotency key

The single most common incident in this category, across the payments industry broadly: a client-side retry (triggered by a timeout on the client's end, even though the server-side request actually succeeded) reaches a side-effecting endpoint a second time, and the endpoint — lacking an idempotency check — repeats the charge. The fix is always structural, not a patch: every endpoint with a financial side effect requires a client-generated idempotency key, checked against a durable ledger before the effect runs, exactly as this chapter builds it. This is precisely why payment APIs across the industry converged on the same "idempotency key" header as a first-class, documented concept rather than an internal implementation detail.

Pattern 2: the trip stuck forever, traced to a missing timeout

A purely event-driven, reactive state machine has an inherent blind spot: it can only react to events that arrive. Any real fleet of mobile clients will occasionally produce a client that dies, loses network, or has its app killed by the OS at exactly the wrong moment, and the backend that only reacts to events will leave that trip "in progress" indefinitely — a support burden and, if payment is gated on completion, a lost or delayed charge. The general industry fix is exactly section 8(b)'s watchdog: every state with a real-world expectation attached gets an active timer, so silence itself becomes an input the system can act on rather than an unhandled case.

Pattern 3: the race between a legitimate transition and a timeout

A driver's "trip completed" event and a "driver silent" timeout can, in principle, arrive within milliseconds of each other — the driver's phone regains signal and sends the real event just as the watchdog decides it's been silent too long. This is exactly what optimistic-concurrency versioning (section 5) exists to adjudicate cleanly: whichever write wins the compare-and-swap is authoritative, and the loser's handler must recognize the version conflict and back off rather than silently overwriting a state transition that already happened for a good reason.

Reading the trip service: illustrative reference implementation

The transition table, enforced as data rather than scattered if chains — the same defense named in §8(a):

Go (illustrative)fsm/transitions.go
var LegalTransitions = map[State][]Edge{
    StateRequested:   {{Event: EvMatched, Next: StateMatched},
                        {Event: EvRiderCancel, Next: StateCancelled},
                        {Event: EvNoDriversTimeout, Next: StateUnmatched}},
    StateMatched:     {{Event: EvDriverEnRoute, Next: StateEnRoute},
                        {Event: EvRiderCancel, Next: StateCancelled},
                        {Event: EvDriverCancel, Next: StateRequested}}, // rematch
    StateEnRoute:     {{Event: EvDriverArrived, Next: StateArrived},
                        {Event: EvEtaTimeout, Next: StateRequested}},
    StateArrived:     {{Event: EvTripStarted, Next: StateInProgress},
                        {Event: EvNoShowTimeout, Next: StateCancelled}},
    StateInProgress:  {{Event: EvTripCompleted, Next: StateCompleted},
                        {Event: EvDriverSilentTimeout, Next: StateNeedsReview}},
    StateNeedsReview: {{Event: EvManualResolve, Next: StateCompleted},
                        {Event: EvLateCompletion, Next: StateCompleted}}, // idempotent no-op if already resolved
}

func IsLegal(from State, ev Event) (State, bool) {
    for _, edge := range LegalTransitions[from] {
        if edge.Event == ev { return edge.Next, true }
    }
    return StateUnknown, false  // reject — never silently apply an unlisted edge
}

The handler that ties the idempotency ledger, the transition table, and optimistic concurrency together:

Go (illustrative)fsm/handle_event.go
func HandleEvent(ctx Context, tripID string, ev Event, idemKey string) error {
    if ev.HasSideEffect() {
        applied, err := ledger.CheckAndReserve(ctx, idemKey) // atomic check-and-insert
        if err != nil { return err }
        if applied {
            return nil // already handled this exact request — safe no-op
        }
    }

    trip, version, err := store.Load(ctx, tripID) // current state + version
    if err != nil { return err }

    next, ok := fsm.IsLegal(trip.State, ev)
    if !ok {
        return ErrIllegalTransition // reject — e.g. a stale or out-of-order event
    }

    err = store.CompareAndSwap(ctx, tripID, version, next) // optimistic concurrency
    if err == ErrVersionConflict {
        return HandleEvent(ctx, tripID, ev, idemKey) // re-read and retry once
    }
    if err != nil { return err }

    watchdog.Reschedule(tripID, next)              // cancel old timer, arm the new state's
    publisher.Publish(TripStateChanged{tripID, next}) // fan-out to payments, notifications
    return nil
}
WHY IT WAS BUILT THIS WAY

Notice the order of operations: the idempotency check happens before any state is loaded, so a redelivered request short-circuits as cheaply as possible. The transition table is checked before any write is attempted, so illegal transitions never reach storage. And the compare-and-swap failure path retries the whole function rather than attempting a partial patch — re-reading fresh state and re-validating the transition against it, because the world may have changed underneath the first read. Every one of these choices trades a small amount of extra latency for eliminating an entire category of corruption bug — the same trade this whole chapter has been making since section 5.
