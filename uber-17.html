UBER ENGINEERING INTERNALS · CHAPTER 17

One Database Cannot
Serve Every City On Earth

Chapter 16 built a single-node storage engine capable of native secondary indexes and multi-region replication. This chapter asks the fleet-level question those capabilities were built for: how do you actually distribute data across thousands of cities and multiple continents so that most queries stay fast and local, an incident in one region can't take down every other region, and the whole system can still fail over when an entire region goes dark? The answer is a genuine tension — between strong global consistency and regional autonomy — and this chapter derives, honestly, which side of that tension a company at Uber's shape leans toward, and exactly what it costs to lean that way.

ARC 01 · THE PROBLEM

Data locality and blast-radius isolation pull in the same direction — usually

A rider in São Paulo requesting a trip has essentially no reason to touch data belonging to a rider in Singapore — different city, different drivers, different regulatory jurisdiction, different everything except the software running underneath. Once you accept that, the question stops being "how do we build one database big enough for the whole world" and becomes "how do we partition data so most requests only ever need to talk to the partition that's actually relevant to them" — and, just as importantly, "how do we make sure a bad day in one partition doesn't become a bad day everywhere."

Two forces, worth separating even though they usually agree:

  • Data locality. A trip in São Paulo, its driver's location updates, and its fare calculation are all naturally scoped to one geography. Keeping that data physically close to where it's used keeps read and write latency low and keeps the working set any one query touches small.
  • Blast-radius isolation. Independent of latency, there is a second, equally important reason to keep regions separate: an incident — a bad deploy, a storage-engine write stall (chapter 16), an operator error — that is contained to one region's data should not be able to propagate and take down every other region's traffic at the same time. This is the exact same argument chapter 8 made for microservices and chapter 9 made for the mesh's sidecar isolation, applied one more time at the data layer.
WHY THIS CHAPTER TEACHES TECHNIQUE, NOT A SPECIFIC INTERNAL BLUEPRINT

Uber has publicly and reasonably described geographic sharding by city/region as both a locality and an isolation decision, and that framing is the honest, public starting point for this chapter. The exact internal shard-key scheme, the precise replica-count and consensus parameters any specific Uber service runs today, and the fine details of its conflict-resolution logic for cross-region writes are not public knowledge. This chapter teaches the general, well-documented distributed-systems technique — consistent hashing, async replication, CAP- theorem tradeoffs, and failover mechanics — that any company operating at this shape has to build some version of, and says plainly where it is generalizing rather than reporting an exact internal fact.

DEEP CONTEXT · RINGPOP, AND WHAT IT DOES NOT CLAIM TO BE

Ringpop is real, public, Uber-built infrastructure: a library implementing a gossip-based membership protocol (in the SWIM family) plus consistent hashing, designed to let a fleet of stateful nodes agree on which node owns which shard of a keyspace without a central coordinator being consulted on every request. It is exactly the kind of building block a sharded, horizontally-scaled system at Uber's shape would need — this chapter treats it as real evidence that this general technique matters at this scale, without claiming Ringpop is necessarily the literal mechanism behind any specific present-day Uber storage system's sharding (that internal detail isn't public).

ARC 03 · NAIVE SOLUTION

Attempt #1: one global database, one region, synchronously consistent

Start from the simplest possible answer: run a single database cluster, in a single region, that serves every city on Earth, with every read and write going through that one place. Global consistency is trivial — there is only ever one copy of the truth.

pseudocodenaive_single_region.py — the strawman, annotated
def write_trip(trip):
    # every write, from every city on Earth, goes to the same single-region cluster
    single_region_db.put(shard_key=trip.city_id, row_key=trip.trip_id, blob=trip.to_json())

def read_trip(trip_id, city_id):
    # a rider in Manila and a rider in São Paulo hit the exact same cluster
    return single_region_db.get(shard_key=city_id, row_key=trip_id)

This is a completely reasonable starting point — it's exactly what you'd build first, and for a company operating in one metro area it may never need to change. The trouble is what happens once "every city on Earth" stops being a hypothetical.

ARC 04 · WHY IT FAILS

Speed of light latency, and a blast radius the size of the entire company

  • Latency is bounded by physics, not engineering effort. A rider in Manila whose request must reach a single database cluster in, say, the United States pays a real, unavoidable round-trip time commonly in the 150–250 ms range on real intercontinental backbone routes — before any actual query execution happens. For a request budget measured in tens to low hundreds of milliseconds (chapters 4, 5, and 7 all assumed budgets in this range), that single fixed cost can already consume most of it, for every single city that isn't near the cluster.
  • The blast radius is the entire company, everywhere, all the time. Any incident that takes down the single region — a bad deploy, a storage-engine write stall (chapter 16), a regional cloud-provider outage, a fiber cut — takes down every city's traffic simultaneously, with no isolation boundary anywhere in the system. There is no version of "Manila is having a bad day but São Paulo is fine," because there is only one database for both.
  • A single shard key with no locality also destroys the working-set benefit locality was supposed to buy. Even if you shard within that one region by, say, a naive hash(trip_id) mod N, trips from every city end up scattered uniformly across every shard — a query scoped to "this city's trips" now has to fan out to potentially every shard in the cluster instead of one.
THE NUMBERS

At a 200 ms round trip and a request budget of, say, 300 ms total, two-thirds of the entire budget is consumed by network transit before a single query executes — leaving almost nothing for dispatch (chapter 4), routing (chapter 5), and pricing (chapter 6) to actually do their work within. And because there is exactly one region, the probability that some incident affects all traffic is the probability of that one region having a bad day — there is no independent, uncorrelated second region to fail over to.

ARC 05 · BETTER SOLUTION

Shard by city/region, replicate asynchronously, accept eventual cross-region consistency

The fix addresses both failures at once: partition data so a city's traffic is served by a nearby regional cluster (fixing locality and giving each region an independent blast-radius boundary), and replicate data asynchronously toward other regions rather than requiring every write to be acknowledged everywhere before it completes (fixing the latency floor §4 quantified).

THE CAP-THEOREM ARGUMENT, MADE CONCRETE

Once a network partition between regions is possible — and at global scale, it always eventually is — the CAP theorem says you cannot have both full Consistency and full Availability across that partition; you must choose. Choosing regional autonomy with asynchronous replication is choosing Availability (and low, region-local latency) over strict cross-region Consistency, on the reasoning that most reads and writes for a São Paulo trip never actually need to be consistent with Manila's copy of unrelated data in the first place. That's not a universal answer — a banking ledger might reasonably choose the opposite trade — but it is the right answer for the overwhelming majority of ride-hailing data, which is naturally, physically scoped to one city at a time.

ARC 06 · WHY THAT STILL HURTS

Async replication's honest bill: lag, conflicts, and a harder failover

  • Replication lag is real and must be monitored, not assumed away. Between the moment a write commits in its home region and the moment it's visible in a replica region, there is a real window — growing whenever write rate outpaces replication bandwidth, exactly the same queueing shape chapter 16's compaction backlog followed. Any region-failover decision has to reckon with exactly how much data is in that window and might not have replicated yet.
  • Conflicting writes to related keys from different regions need a resolution rule. If two regions can both accept writes (rather than one strict primary per shard), the system needs an honest answer for what happens when both touch overlapping data before either replication catches up — last-write-wins by timestamp, an application-level merge rule, or simply preventing the situation by keeping one authoritative region per shard are all real, general strategies, each with real tradeoffs.
  • Failover is now a genuine operational procedure, not a configuration flag. Promoting a replica region to primary for a shard means deciding what to do about writes that were in flight or unreplicated at the moment of failure — accept a bounded window of data loss (a real RPO), or block until you can prove nothing is at risk, trading availability for that guarantee.
  • Running N regions is N times the operational surface. Every region needs its own capacity planning, its own on-call awareness, its own failure modes to test — multi-region isn't a free upgrade any more than the mesh (chapter 9) or the fleet-wide event backbone (chapter 10) were.
THE HONEST FRAME

Regional sharding with async replication doesn't eliminate the tension between consistency and availability — it resolves it in a specific, considered direction (favor regional availability and locality, accept bounded cross-region staleness) that fits a workload where almost all data is naturally, physically scoped to one region at a time. A workload without that natural locality — a single global ledger of account balances, say — would reasonably resolve the same tension differently.

(b) Replication lag: write rate versus replication bandwidth

pseudocode (illustrative)replication/lag_monitor.go
func EstimateLagSeconds(writeRateBytesPerSec, replBandwidthBytesPerSec float64) float64 {
    backlogGrowthRate := writeRateBytesPerSec - replBandwidthBytesPerSec
    if backlogGrowthRate <= 0 {
        return 0                         // replication keeps up; lag stays near zero
    }
    // lag grows without bound the longer write rate exceeds bandwidth — same shape as ch.16's compaction backlog
    return backlogGrowthRate / replBandwidthBytesPerSec  // simplified: seconds of backlog per second elapsed
}
ARC 09 · TRADEOFFS

Four points on the consistency/availability spectrum

STRATEGYWHAT IT BUYSWHAT IT COSTS
Single global region, one cluster trivial global consistency simplest to operate latency floor set by physics for distant cities company-wide blast radius
Sharded by region, ASYNC replication (this chapter's endpoint) low, region-local latency blast-radius isolation per region bounded cross-region staleness conflict handling + failover complexity
Sharded by region, SYNCHRONOUS cross-region consensus strong global consistency even across regions every write pays cross-region round-trip latency, always
Fully independent per-region deployments, no replication at all maximum isolation simplest failure model per region no disaster-recovery copy if a region is permanently lost no cross-region visibility at all

Read this the way every tradeoffs table in this course has asked you to: there is no dominant strategy, only a different placement of the same underlying cost between latency, consistency, and operational complexity. Regional sharding with async replication is the specific point on that spectrum that fits a workload where almost all data is naturally scoped to one region — it is a considered bet, not a universally correct default.

ARC 10 · PERFORMANCE / SCALE CHARACTERISTICS

RPO, RTO, and what replication lag actually threatens

Two numbers define a multi-region strategy's real behavior under failure: RPO (how much recently-written data you can afford to lose on failover) and RTO (how long it takes to actually complete a failover once triggered). Both are direct functions of replication lag and failover procedure, not marketing numbers.

  • RPO ≈ current replication lag at the moment of failure. If a region goes dark with 4 seconds of unreplicated writes sitting in its outbound replication stream, those 4 seconds of writes are the realistic worst-case data-loss window unless the failover procedure has another way to recover them.
  • RTO ≈ detection time + promotion time + traffic-manager propagation time. None of these are free: detecting a region is genuinely down (not just slow) takes real time to avoid false positives; promoting a replica to primary means it must first be sure it has applied everything it's going to receive; and updating DNS/traffic-manager routing takes real propagation time before all clients see the change.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

Region failovers: a well-documented industry-wide operational pattern

Uber has not published a chapter-specific postmortem naming an internal multi-region failover incident, so this section is honest about that and instead teaches the realistic, industry-standard pattern that region-level outages and failovers follow across the industry of every company operating at multi-region scale — a pattern publicly documented in postmortems from many large cloud-scale operators.

Pattern 1: the failover that outruns its own replication lag

A region degrades — not cleanly down, but slow and unreliable, the same "worse than a clean failure" pattern chapter 9 described for a slow-not-down downstream dependency. An automated failover triggers before the team has confirmed the actual replication-lag window, and traffic is redirected to a replica region that turns out to be missing more recent writes than expected — the realistic industry pattern behind the well-known operational lesson "measure your actual RPO before you need it, not during."

Pattern 2: a failover that succeeds technically but overloads the healthy region

All traffic from a failed region gets redirected to the remaining healthy region(s), which were provisioned for their own normal load, not for double or triple that load arriving suddenly — a documented, common industry pattern where a region failover, if capacity isn't pre-provisioned for exactly this scenario, turns one region's outage into a second, capacity-driven outage in the region that was supposed to absorb it.

Pattern 3: split-brain during a partial network partition

If a network partition between regions is itself the failure (rather than one region being cleanly down), and both regions believe they should now accept writes for the same shard, you get the general, well-documented split-brain problem: two regions independently accepting conflicting writes for a period, requiring exactly the conflict-resolution strategy §6 named honestly as a real, unresolved-by-magic cost of multi-region operation.

ARC 13 · CODE WALKTHROUGH

Reading a sharding/failover layer: illustrative reference implementation

No single company's exact internal sharding and failover source is fully public. What follows is precise, representative pseudocode of how consistent hashing, replication-lag monitoring, and region failover are genuinely built in production systems of this shape — labeled as illustrative throughout.

sharding/
├── ● ring/consistent_hash.go — virtual-node ring; maps a shard key to its owning physical shard (§8a)
├── ring/rebalance.go — redistributes virtual nodes when a physical shard is added/removed
├── ● replication/lag_monitor.go — tracks per-shard replication lag against every region (§8b)
├── replication/conflict_resolver.go — last-write-wins or app-level merge for concurrent cross-region writes
└── ● failover/coordinator.go — detects a dead region, promotes a replica, updates the traffic manager (§13, §15)

The consistent-hashing lookup, matching §8(a)'s virtual-node shape:

Go (illustrative)ring/consistent_hash.go
func (r *Ring) OwnerOf(shardKey string) ShardID {
    h := hash(shardKey)
    // binary search the sorted virtual-node positions for the first one >= h (wrapping around)
    idx := sort.Search(len(r.sortedPositions), func(i int) bool { return r.sortedPositions[i] >= h })
    if idx == len(r.sortedPositions) { idx = 0 }              // wrap to the first position on the ring
    return r.virtualNodeOwner[r.sortedPositions[idx]]
}

The failover coordinator's decision loop:

Go (illustrative)failover/coordinator.go
func (f *Coordinator) EvaluateRegion(region *Region) {
    if !region.ConsecutiveHealthChecksFailed(f.threshold) {
        return                                        // avoid a false-positive failover on a brief blip
    }
    lag := f.lagMonitor.CurrentLag(region)
    replica := f.pickBestReplica(region)             // the one with the LOWEST recorded lag
    log.Warn("promoting replica, estimated RPO = %v", lag)
    replica.PromoteToPrimary()
    f.trafficManager.RepointTraffic(region.ID, replica.ID)  // DNS/traffic-manager update — has its own propagation delay
}
WHY IT WAS BUILT THIS WAY

The coordinator requires consecutive failed health checks, not a single one — exactly the discipline chapter 9's circuit breaker used to avoid tripping on ordinary noise. And it logs the estimated RPO before promoting, not after — because the failover decision and the data-loss estimate are the same decision, made with the same information, and an operator needs that number in the moment, not reconstructed afterward from logs.
