ARC 01 · THE PROBLEM

"It compiles" is not "it ships"

Every earlier chapter ended when your code compiled and ran correctly in a terminal. A real desktop product asks for more than that, and the gap between the two is exactly what this chapter closes. A shippable app needs: a persistent process that holds state across many separate user interactions, not just across one function call; a user interface a non-programmer can operate, which today almost always means HTML, CSS, and JavaScript rendered by a real browser engine; a boundary between that UI and your Rust logic that is untyped on one side (JavaScript has no i32) and strictly typed on the other; a way for work happening in the background — a file download, a timer, a long computation — to reach the UI without the UI polling for it; and, at the very end, an artifact — a .msi, a .dmg, a .deb — that a stranger's operating system will actually agree to run without a wall of security warnings.

Tauri, introduced last chapter, is the framework that answers all five of these with a specific, opinionated shape: your compiled Rust binary is the process; the OS's own installed web-rendering engine (WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux) draws the UI in a separate rendering surface; a JSON-serializing message channel called IPC connects the two; and a CLI (cargo tauri build) produces the final installer. Everything in this chapter is about turning that shape into working code, in the order a real developer would write it, including the part everyone's tutorial skips: what happens when the two sides of the IPC bridge disagree about a type.

WHAT "REAL" MEANS FOR THIS CHAPTER

Every code sample in this chapter is written to actually compile under a current-stable Rust toolchain and a current Tauri v2 project, and every claimed compiler/runtime error is the literal shape Rust or Tauri would produce — including the real rustc diagnostic code where one exists (E0133 shows up in §3–4). The simulator in §15 is not a slideshow: it runs a small but genuine command dispatcher in JavaScript that mirrors Tauri's real argument-deserialization behavior closely enough that the state it tracks, and the error it throws when you send the wrong type, are the actual shapes you'd see with a real #[tauri::command] and a real invoke() call — not a scripted animation with pre-baked outcomes.

ARC 02 · HISTORICAL CONTEXT

How "web tech for desktop apps" got from Electron to Tauri

The idea of shipping a desktop app as a bundled browser plus your own JavaScript is not new, and Tauri's design decisions only make sense against what came before. Click through the timeline — each event is a response to a specific pain point in the one before it.

Interactive timeline — web-tech desktop appsCLICK EVENTS
DEEP CONTEXT · WHY RUST, SPECIFICALLY

Electron's shell needed a language that could do low-level OS work (window management, native menus, file dialogs) while staying memory-safe enough to trust with untrusted web content next to it — Node.js filled that role in 2013 because it was the obvious scripting layer for a company (GitHub) already all-in on JavaScript. Tauri's founders made a different bet in 2019: use Rust for that same native layer instead. The payoff compounds with everything you've learned in this course — no garbage collector pause in the native core, no whole class of use-after-free bugs in the code that has raw OS access, and a compiled, ahead-of-time-checked IPC layer where a mismatched type is caught by serde at the boundary instead of silently becoming NaN or undefined deep inside your business logic.

ARC 03 · NAIVE SOLUTION

Attempt #1: a global counter, no state manager in sight

Before reaching for tauri::State, derive the need for it honestly. Say your app's first feature is a counter button: click it, a number increments, and it has to keep incrementing correctly no matter how many times the button is clicked or how many browser-side JavaScript calls arrive. The obviously-simplest way to give a Rust command function some memory that outlives a single call is a static mut variable — Rust's most primitive form of global mutable state.

RUSTsrc-tauri/src/main.rs — the strawman
static mut COUNTER: i32 = 0;

#[tauri::command]
fn increment_counter(amount: i32) -> i32 {
    unsafe {
        COUNTER += amount;   // direct read-modify-write of a mutable static
        COUNTER
    }
}

This is not a strawman built to look foolish — it is exactly what a programmer coming from a garbage-collected, single-threaded scripting language reaches for first, and under a very specific reading of the rules it even compiles: accessing a static mut requires an unsafe block (that's the compiler's real diagnostic E0133, "use of mutable static is unsafe and requires unsafe function or block," and it fires the moment you touch COUNTER without one), and a direct compound assignment like COUNTER += amount inside that block is legal Rust — no reference is created, just a plain memory read followed by a plain memory write, both permitted under unsafe.

So it compiles, it runs, single-threaded testing shows the counter going up correctly, and it ships. §4 quantifies exactly what breaks the moment this command is called from more than one place at once — which, in a real webview, happens constantly.

ARC 04 · WHY IT FAILS

The bug class is a data race — and the compiler eventually agrees

A Tauri command is not guaranteed to run to completion before the next one starts. Async commands, multiple windows, and Tauri's own multi-threaded command dispatcher (built on Tokio) all mean two invocations of increment_counter can genuinely execute concurrently on different OS threads. Trace what happens to the naive static mut when that occurs:

  • Thread A reads COUNTER (value 10), computes 10 + amount_A.
  • Thread B reads COUNTER (also 10, because A hasn't written back yet), computes 10 + amount_B.
  • Thread A writes its result back.
  • Thread B writes its result back, overwriting A's update.

One increment is silently lost — the classic data race, the exact bug class Rust's ownership and borrow-checking rules (chapters 4, 5, and 15's Send/Sync) exist to make unrepresentable in safe code. The naive counter only compiled because unsafe is a promise to the compiler — "trust me, I've checked the invariants by hand" — and here that promise was false. This is not a hypothetical: Miri, rustc's own interpreter for detecting undefined behavior (cargo +nightly miri test), ships a genuine data-race detector for exactly this pattern, and running a concurrent version of this counter under it produces a real, specific diagnostic:

WHAT MIRI ACTUALLY SAYS

error: Undefined Behavior: Data race detected between (1) non-atomic write on thread `unnamed-1` and (2) non-atomic read on thread `unnamed-2` at ALLOC, memory(size=4, align=4) — Miri doesn't say "your counter is sometimes wrong"; it says the program has undefined behavior, meaning the compiler is now permitted to assume this path is unreachable and optimize accordingly. A wrong count is the best case outcome of this bug.

There is a second, independent way the compiler pushes back, and it shows up even in single-threaded code the moment the naive pattern grows past a bare compound assignment — say, you refactor to pass the counter by reference into a helper function, log_counter(&COUNTER). Since Rust 1.73 (August 2023), creating any reference to a mutable static — shared or exclusive — triggers the static_mut_refs lint, which is deny-by-default, and under the 2024 edition it is a hard compile error, not a warning: rustc's own message is "creating a shared reference to mutable static is discouraged, as it is easy to accidentally create undefined behavior." The language is closing the door on this pattern entirely, edition by edition, precisely because the UB it enables is real and has shipped in production C and C++ code for decades as the bug class behind CVE entries for corrupted counters, lost updates in reference-counting logic, and TOCTOU races in permission checks. Rust's answer, reached honestly rather than by decree, is in §5.

ARC 05 · BETTER SOLUTION

Tauri's managed state: tauri::State<Mutex<AppState>>

Step through the fix the way you'd actually arrive at it — not as a fact to memorize, but as the forced consequence of two requirements: the state must be reachable from any command, and every access must be synchronized so concurrent calls interleave safely instead of racing.

From a wild global to managed stateSTEP-BY-STEP

The idiomatic result reads almost boringly simple, which is the point — the hard part (synchronization) is now a type the compiler enforces, not a discipline you have to remember:

RUSTsrc-tauri/src/main.rs — the real pattern
use std::sync::Mutex;

#[derive(Default)]
struct AppState {
    counter: i32,
    todos: Vec<String>,
}

#[tauri::command]
fn increment_counter(amount: i32, state: tauri::State<'_, Mutex<AppState>>) -> i32 {
    let mut s = state.lock().unwrap();  // blocks until exclusive access
    s.counter += amount;
    s.counter
}

fn main() {
    tauri::Builder::default()
        .manage(Mutex::new(AppState::default()))
        .invoke_handler(tauri::generate_handler![increment_counter])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}

.manage(value) hands ownership of value to the Tauri runtime, which stores it once and makes it retrievable by type in any command via the tauri::State<'_, T> extractor argument — Tauri inspects each command's parameter list at compile time (via the #[tauri::command] macro) and wires up the right managed value automatically; you never pass it explicitly from the frontend. Wrapping AppState in a std::sync::Mutex is what makes concurrent access safe: .lock() blocks the calling thread until it has exclusive access, and the MutexGuard it returns behaves like a smart pointer to the data. Two commands racing to increment the counter now genuinely serialize — the race from §4 becomes structurally impossible, not just unlikely.

ARC 06 · WHY THAT STILL HAS COSTS

Managed state is correct — it is not free

Be honest about what you paid to get here, because every one of these costs will bite a real Tauri codebase eventually:

  • Everything crossing the IPC boundary is serialized to JSON. A Vec<String> of a thousand todos gets encoded to a JSON array, sent as a string, and parsed back into a JS array on every single invoke() call — there is no shared memory between the webview and your Rust process the way chapter 15's threads shared an address space. For large or frequently-updated state, this is a real, measurable cost (§10 puts a number on it).
  • Holding a std::sync::MutexGuard across an .await point is a trap. If a command is async fn (needed the moment it does any real I/O — a network call, a file read) and you keep the guard alive across an .await, the resulting future is not Send, because MutexGuard is deliberately !Send — and Tokio's multi-threaded runtime (which Tauri uses) requires spawned futures to be Send. The fix is to scope the lock so it drops before the .await, or switch to tokio::sync::Mutex, which is designed to be held across await points — but nothing in the type signature warns you until the compiler rejects the whole function with a dense trait-bound error. §12 has the interview-grade version of this gotcha.
  • Lock contention is now your problem, and it's invisible in the UI. Every command touching AppState — even ones with nothing to do with the counter — serializes on the same mutex unless you deliberately split state into finer-grained pieces. A slow command holding the lock stalls every other command silently; nothing in the frontend tells you why a button feels laggy.
  • Boilerplate scales linearly with your command count. Every command needs its own #[tauri::command] function, its own entry in generate_handler![...], and (if it can fail) its own error type that implements serde::Serialize so it can cross the IPC boundary as JSON too — plain anyhow::Error or Box<dyn Error> won't compile as a command return type without a wrapper.
  • Compile times grow. A Tauri project pulls in wry (the webview-embedding crate), platform bindings (webview2-com on Windows, Objective-C bridging on macOS, gtk/ webkit2gtk bindings on Linux), and Tokio — a clean build is measured in minutes, not seconds, on a modest machine, which is a real tax on the fast edit-compile-check loop chapters 1–20 trained you to expect.

None of this is a reason to avoid the pattern — it is the honest bill for correctness and cross-platform reach. §7 draws the whole architecture so every one of these costs has a home.

Nothing in the webview can touch AppState directly — not because of a firewall rule, but because it is physically a different process's memory, rendered by a different engine, with no shared address space. Every single interaction, no matter how small, is a serialized message. Internalizing that one fact explains almost every design decision in the rest of this chapter: why state must be JSON-serializable, why errors need their own serializable type, why events (not direct calls) are the only way for Rust-initiated work to reach the UI, and why the security model in §9/§11 is built entirely around controlling what crosses that one narrow channel.

ARC 08 · INTERNAL IMPLEMENTATION

Building the real thing, five stages

This is the chapter's spine: the exact sequence a working Tauri app is built in, with real commands and real code at each stage. §15's simulator lets you click through a live version of every stage below; first, the overview:

The five-stage build, overviewSTEP-BY-STEP

Stage 1 — scaffold: cargo tauri init

Assuming a Rust project already exists (or was created with cargo tauri init from scratch, which also offers to scaffold a plain HTML/JS frontend for you), the command generates a src-tauri/ directory sitting alongside your web frontend:

my-tauri-app/
├── src/ — the frontend: plain HTML/CSS/JS (no framework required)
│ ├── index.html
│ ├── main.js
│ └── styles.css
└── src-tauri/ — the Rust core, generated by `cargo tauri init`
    ├── Cargo.toml — depends on the `tauri` crate + build-time `tauri-build`
    ├── build.rs — calls tauri_build::build(), embeds icons + metadata
    ├── tauri.conf.json — window size, bundle identifier, capabilities/permissions
    ├── icons/ — per-platform icon sizes, generated by `tauri icon`
    └── src/main.rs — your Rust entry point

tauri.conf.json is the file every other stage below reads from — it names the frontend's build output directory, the window's default title and size, and (Tauri v2) the capabilities that scope exactly which native APIs the webview is allowed to reach:

JSONsrc-tauri/tauri.conf.json — trimmed
{
  "productName": "my-tauri-app",
  "identifier": "com.example.my-tauri-app",
  "build": { "frontendDist": "../src" },
  "app": {
    "windows": [ { "title": "my-tauri-app", "width": 800, "height": 600 } ],
    "security": { "csp": null }
  },
  "bundle": { "active": true, "targets": "all" }
}

Stage 2 — the backend: commands over managed state

From §5, extended with the second piece of state a real app needs — a small todo list, to show that managed state isn't limited to a single primitive:

RUSTsrc-tauri/src/main.rs — commands.rs inlined for clarity
#[tauri::command]
fn add_todo(text: String, state: tauri::State<'_, Mutex<AppState>>) -> Vec<String> {
    let mut s = state.lock().unwrap();
    s.todos.push(text);
    s.todos.clone()   // returned value crosses IPC as a JSON array of strings
}

#[tauri::command]
fn get_state(state: tauri::State<'_, Mutex<AppState>>) -> (i32, Vec<String>) {
    let s = state.lock().unwrap();
    (s.counter, s.todos.clone())
}

Notice what doesn't appear: no networking code, no manual JSON parsing. The #[tauri::command] macro generates a wrapper that deserializes the incoming call's arguments (using serde, matching each named JSON field to a typed parameter) and serializes the return value back to JSON — this generated wrapper is exactly where §15's deliberate bug lives.

Stage 3 — the frontend: invoke()

Plain JavaScript, no framework required — Tauri exposes its JS API as importable modules that any bundler (or no bundler at all, via a <script type="module">) can pull in:

JAVASCRIPTsrc/main.js
import { invoke } from "@tauri-apps/api/core";

document.querySelector("#inc-btn").addEventListener("click", async () => {
  const newValue = await invoke("increment_counter", { amount: 1 });
  document.querySelector("#counter").textContent = newValue;
});

invoke(name, args) serializes args to JSON, sends it across the IPC bridge, and returns a Promise that resolves with the command's (also deserialized) return value — or rejects if anything about the call was invalid, including a type that doesn't match what the Rust command expects. That rejection path is not an edge case you can ignore; it's the one you'll deliberately trigger in §15.

Stage 4 — events: Rust talks back without being asked

invoke() only covers the frontend asking Rust for something. The other direction — Rust telling the frontend something happened, on its own schedule — uses a separate, one-way event system: emit() on the Rust side, listen() on the JS side.

RUSTsrc-tauri/src/main.rs — a background task
use tauri::{AppHandle, Emitter};

fn spawn_progress_task(app: AppHandle) {
    tauri::async_runtime::spawn(async move {
        for pct in (0..=100).step_by(10) {
            tokio::time::sleep(std::time::Duration::from_millis(300)).await;
            app.emit("progress", serde_json::json!({ "percent": pct })).unwrap();
        }
    });
}
JAVASCRIPTsrc/main.js — subscribing
import { listen } from "@tauri-apps/api/event";

await listen("progress", (event) => {
  document.querySelector("#progress").value = event.payload.percent;
});

Note the trait name: Emitter. Tauri v2 unified event emission behind one trait implemented by AppHandle, Window, and a few other handles, replacing v1's separate emit_all/emit_to methods — a real, citable API change between the two major versions (§2's timeline covers the release), and a good example of the framework's own churn as it matured.

Stage 5 — package: cargo tauri build

The bundler compiles your Rust binary in release mode, runs your frontend's own build step if configured, embeds the result, and produces platform-native installers — the real, correctly-named formats, not generic zip files: .msi and NSIS-based .exe on Windows, .app plus a .dmg on macOS, and .deb plus .AppImage on Linux. Two independent signing steps matter here, and conflating them is a common production mistake: OS code signing (a Windows Authenticode certificate, or an Apple Developer ID certificate plus notarization via xcrun notarytool) is what stops the OS itself from showing an "unidentified developer" warning; Tauri's own updater signing (a separate minisign keypair generated with tauri signer generate) is unrelated — it only verifies that an auto-update payload really came from you, and has nothing to do with whether Gatekeeper or SmartScreen trusts the binary.

THE FULL STAGE ORDER, ONE MORE TIME

scaffold → define AppState + wrap in Mutex → .manage() it → write #[tauri::command] fns that take tauri::State → register them in generate_handler![...] → frontend calls invoke() and renders the real response → background work emit()s events the frontend listen()s for → cargo tauri build produces a signed, platform-correct installer. §14's ordering quiz tests exactly this sequence; §15 lets you run it.

ARC 10 · PERFORMANCE & SIZE CHARACTERISTICS

The number every stakeholder actually asks about: installer size

Bundle size is the single most publicly cited Tauri-vs-Electron number, and it's real: a minimal Tauri "hello world" app typically lands in the low single-digit megabytes (Tauri's own documentation has demonstrated builds under 1 MB for the absolute floor case), because the installer only needs to contain your compiled Rust binary plus your web assets — the rendering engine itself is already on the user's machine. A minimal Electron app starts around 50 MB and commonly clears 100–150 MB in practice, because it bundles an entire copy of Chromium and Node.js. The same "shared vs. bundled" logic applies to memory: an idle Tauri window's extra RSS over the OS webview process it's riding on is typically tens of megabytes; an idle Electron window pays for a private Chromium renderer process plus a Node.js runtime, commonly landing in the 100–300 MB range per window — the reason "why is this Electron app using 2 GB of RAM with six tabs open" became a recurring public complaint about chat and editor apps built on it (§11).

ARC 11 · REAL-WORLD INCIDENTS

Three stories that justify this chapter's paranoia about the IPC boundary

Incident 1: Discord's custom-protocol RCE (Electron, 2018)

Tracked as CVE-2018-1000006, security researchers found that Electron apps registering a custom URL protocol handler (Discord's own discord:// being the widely reported case) on Windows could be tricked into launching with attacker-controlled command-line switches — because the OS passes the entire protocol-invocation string to the app's launch, and Electron's Chromium layer honored certain switches from it. A malicious link, opened once, could achieve remote code execution with no further user action. The fix required both an Electron-level patch and app-level hardening. The lesson generalizes past Electron: any bridge where one side treats input from the other as instructions rather than data is a standing invitation for exactly this class of bug — the same principle behind why this chapter insists Tauri's IPC arguments are validated data, not trusted commands.

Incident 2: the WebView2 dependency, and what "shared" costs you

Tauri's small-installer story rests on an assumption: the OS's webview is present and reasonably current. On Windows specifically, that's Microsoft's WebView2 runtime — present by default on modern Windows 11 and 10 installs, but not guaranteed on locked-down enterprise images where update policies freeze system components. An app that assumes WebView2 is always there can fail to launch entirely on such a machine; Tauri's own documentation addresses this directly by offering a bundling option for the WebView2 "Evergreen Bootstrapper" as a fallback, at the cost of a few extra megabytes — a real, documented tradeoff between the "shared dependency" model's size advantage and its deployment-environment risk, mirroring the exact shared-vs-private tradeoff this course's PostgreSQL chapters draw around shared memory (different domain, identical shape of argument).

Incident 3: the public backlash over Electron memory usage

Slack's and early Visual Studio Code's Electron-based memory footprint became a recurring, widely covered public complaint through the late 2010s — multiple tabs, plugins, or long-running sessions routinely pushed RAM usage into the gigabytes for what users perceived as "a chat app" or "a text editor," precisely because each window carries a private Chromium renderer process and Node.js runtime rather than sharing one with the OS. The criticism was public and persistent enough that it became a standard talking point in comparisons with lighter-weight alternatives — exactly the gap Tauri was founded in 2019 to close, and exactly the number §10's chart puts in front of you.

Incident 4: what "capabilities" actually replaced, and why

Tauri v1's original security model was a single, coarse allowlist in tauri.conf.json: turn an entire API category (filesystem, shell, HTTP) on or off for the whole app, with limited per-path scoping. In practice this meant a developer who needed one command to read one config file often granted filesystem access far more broadly than the feature required, because the granularity to do otherwise barely existed — precisely the "differently defaulted, not differently shaped" problem §16 asks you to reason about. Tauri v2's capabilities/permissions rewrite (§2's 2024 timeline entry) directly answers this: permissions are now scoped per-command and per-window, composed from small named permission sets you opt into deliberately, which is a real, shipped response to exactly the class of over-broad-scope incident described generically in §12's filesystem interview question — not a hypothetical concern invented for this chapter.

    s.todos.clone()
}

#[tauri::command]
fn get_state(state: State<'_, SharedState>) -> (i32, Vec<String>) {
    let s = state.lock().unwrap();
    (s.counter, s.todos.clone())
}

pub fn spawn_progress_task(app: AppHandle) {
    tauri::async_runtime::spawn(async move {
        for pct in (0..=100).step_by(10) {
            tokio::time::sleep(std::time::Duration::from_millis(300)).await;
            let _ = app.emit("progress", serde_json::json!({ "percent": pct }));
        }
    });
}

Compare this shape to a real crate you may already know: serde itself follows the identical "derive generates the boilerplate, you write the shape" philosophy — #[derive(Serialize, Deserialize)] generates exactly the kind of trait impl that #[tauri::command] generates for argument extraction, and both are procedural macros doing compile-time code generation rather than runtime reflection (which Rust, unlike languages with a runtime, doesn't have).
