RUST · CHAPTER 03 BEGINNER

Variables, Types &
Control Flow

Every value in a Rust program has an exact, known-at-compile-time size and alignment, and every binding is immutable unless you say otherwise. Neither is an accident. This chapter derives both decisions from first principles — let vs let mut, the full scalar and compound type system with real widths, and the control-flow forms (if, loop, while, for) that read like any C-family language but are, underneath, expressions all the way down.

ARC 01 · THE PROBLEM

A program is data plus the paths through it

Strip any program down and two things remain: values sitting in named places (variables) and the order operations happen in (control flow). Every language answers two questions about the first — can this named place change what it holds, and how big is what it holds — and one question about the second — which of these constructs produce a value I can use, and which are just instructions I obey. Get sloppy answers to those questions and you get a real, well-documented category of bugs that has cost real money and, in at least one case this chapter will return to, a real rocket.

Rust's answers are stricter than almost any language a working programmer has used before, and stricter than they need to be for the program to merely run. That strictness is the entire subject of this chapter:

  • Can this variable change? Most languages say "yes, unless you mark it otherwise" (const in JS, final in Java — both opt-in immutability). Rust says "no, unless you mark it otherwise" — let bindings are immutable by default; you opt in to mutation with mut.
  • How big is this number, exactly? Python's int is arbitrary-precision and never overflows; JavaScript's Number is always a 64-bit float, even for things that look like integers; C's int is "whatever the platform says," which for decades meant genuinely different answers on different machines. Rust requires you to pick a width — i32, u8, i64 — and that width is part of the type, checked at compile time, with no silent platform-dependent surprises.
  • Does this control-flow construct hand back a value? In C, if is a statement; you can never write x = if (cond) 1 else 2;. In Rust, if, match, and even bare { } blocks are expressions that evaluate to a value, and the language leans on that constantly.
WHY THIS MATTERS FOR THE NEXT 19 CHAPTERS

Every later chapter assumes you're fluent in this vocabulary without thinking about it. Chapter 4 (Ownership) talks about "moving a String" and assumes you already know a String is a heap-backed compound value, not a scalar. Chapter 9 (Traits & Generics) writes functions generic over T: Copy and assumes you know which of today's types are Copy and which aren't — and why. Get today's material solid and the rest of the beginner tier moves fast; skim it and you'll be reverse-engineering "why doesn't this compile" for weeks.

DEEP CONTEXT · TWO LINEAGES COLLIDING

Rust's type and binding syntax reads like C — braces, semicolons, fn instead of def — but its semantics in this chapter are borrowed almost entirely from the ML family (ML, 1973; Standard ML, 1983; OCaml, 1996; Haskell, 1990): immutable bindings by default, expression-oriented control flow, and a static type system with no implicit numeric widening. Graydon Hoare's original Rust design notes explicitly cite this influence. The result is a language that looks approachable to a C or Java programmer and then, in the first ten minutes, quietly asks them to think like a functional programmer about what a variable even is.

ARC 04 · WHY IT FAILS

"It compiled, but did what I meant" is not a low bar

Loosen any one of the four rules from §3 and you don't get a crash — you get a program that keeps running while quietly doing the wrong thing, which is worse. Two named weakness categories from MITRE's CWE catalog cover exactly the ground Rust's type rules close off, and both have appeared in essentially every edition of the CWE Top 25 Most Dangerous Software Weaknesses since MITRE started publishing it:

  • CWE-190, Integer Overflow or Wraparound. A computation produces a number too large for its storage type, and the value silently wraps to something small or negative instead of erroring. In a language that lets you add two numbers of different, implicit widths (C) or never tells you a width at all (JS's float-backed Number losing precision past 253), this bug class is structurally invited in. §11 covers a real incident caused by exactly this.
  • CWE-704, Incorrect Type Conversion or Cast. A value is silently reinterpreted as a different type — C's implicit int-to-char truncation, JavaScript's "5" + 3 === "53" but "5" - 3 === 2 coercion rules, or treating any non-zero integer as "truthy" in an if. MISRA C, the coding standard used in automotive and aerospace software, bans assignment inside a condition (if (x = 5)) for exactly this reason — it's valid C, it's "truthy," and it is almost never what the author meant.
THE NUMBERS

Neither of these is a rare edge case. CWE-190 and CWE-704 are perennial entries in MITRE's annual "most dangerous" list precisely because the languages most infrastructure is written in (C, C++) make both mistakes the path of least resistance: an unchecked + is shorter to type than a checked one, and an implicit cast requires no syntax at all. Rust inverts the incentive. The checked, safe path (checked_add, an explicit as cast, a real bool condition) is never shorter than the naive one — but the naive one, in Rust, doesn't compile. You cannot accidentally take the fast, wrong path; you have to ask for it by name.

So what does asking for the safe path by name actually look like once you fix all four naive attempts? §5 walks through it.

ARC 06 · THE COSTS

Be honest: none of this is free

A chapter that only sold the benefits would be lying by omission. Explicitness has a real, daily cost, and you will pay every item on this list within your first week of writing Rust:

  • Type annotations you can't always dodge. let n = "42".parse(); doesn't compile — parse() is generic over its return type, and with no context to infer from, rustc has nothing to pick. You write "42".parse::<i32>() (the "turbofish") or annotate the binding: let n: i32 = "42".parse().unwrap();. Type inference is very good in Rust, but it is not Python — it never asks "what type is this at runtime," only "what's the single type this could be, given everything else in scope."
  • The as cast is a loaded gun you're handed on purpose. Fixing the naive examples in §5 required an explicit cast — but explicit casts can still truncate silently. 300i32 as u8 compiles cleanly and produces 44 (300 mod 256), with no panic, no warning, in both debug and release builds. as is not a safety feature; it's an escape hatch that says "I know what I'm doing" whether or not that's true. (The safe alternatives — u8::try_from(300i32), which returns a Result — exist and are one extra import away; §13 shows why they aren't the default.)
  • Debug and release can legitimately disagree. Arithmetic overflow panics in a debug build and silently wraps in a release build (§8b makes this precise). Code that "worked in testing" can wrap silently the moment it ships, which is the single most-cited "gotcha" first-year Rust programmers report.
  • Shadowing is powerful and occasionally confusing. let x = 5; let x = "five"; is legal — shadowing creates an entirely new binding, so it may even change type — but it means the meaning of x at line 40 can differ from its meaning at line 10 with no mut in sight. Linters (clippy) flag suspicious shadowing, but the language permits it freely.
  • Choice paralysis on day one. Twelve integer types (i8 through i128, u8 through u128, plus isize/usize) is a real decision surface for someone used to "just use int." The practical default — i32 unless you have a specific reason, usize for anything indexing a collection — resolves 90% of cases, but you do have to learn that default exists.

None of this is a reason to avoid the language — it's a reason to know, honestly, what you're signing up for. §7 gives you the mental model that makes the rest of these costs predictable instead of surprising.

ARC 07 · MENTAL MODEL

Where does this value actually live?

Every binding you write lands in one of two places: a slot in the current stack frame, sized and laid out entirely at compile time — or a small, fixed-size stack header pointing at a separately allocated region of the heap. Click each declaration below to see which, and why. This is a preview: chapter 4 (Ownership) is the chapter that explains who is responsible for freeing the heap side of this picture, and exactly what happens when you assign one heap-backed variable to another.

THE RULE OF THUMB THAT SURVIVES TO ADVANCED RUST

If a type's size is knowable purely from its type — no runtime information required — it can live entirely on the stack: every scalar, every tuple and array of stack types, and (chapter 6) every plain enum and struct built from them. The moment a value's size can only be known at runtime (a String's length depends on what the user typed; a Vec's length depends on how many times you pushed), Rust puts a small, fixed-size header on the stack — always a pointer, a length, sometimes a capacity, each usize-sized — and moves the variable-sized data to the heap, reached through that header's pointer. You'll re-derive this same split independently when chapter 8 introduces trait objects and chapter 9 introduces lifetimes on struct fields.

THE FOUR NAMED ESCAPE HATCHES

Relying on the debug/release discrepancy is how overflow bugs ship. When overflow is a real, expected possibility, name your intent instead of hoping: a.checked_add(b) returns Option<u8> (None on overflow); a.wrapping_add(b) always wraps, explicitly, in both profiles; a.saturating_add(b) clamps at u8::MAX; a.overflowing_add(b) returns (u8, bool) — the wrapped value and whether it overflowed. All four exist on every integer type and all four are unaffected by the debug/release overflow-checks profile setting, which is exactly why library code that cares about correctness uses them instead of a bare +.

ARC 09 · TRADEOFFS

The same five questions, five languages' answers

Rust's choices aren't objectively "more correct" in a vacuum — they're a specific point in a design space every language occupies somewhere. Read this honestly, including the columns where Rust pays a real cost:

Read the pattern: Rust and Go agree that implicit numeric conversion is a mistake worth banning outright — and both are right, by the CWE-704 argument from §4. They disagree sharply on overflow: Go wraps silently, unconditionally, in every build; Rust makes overflow a loud debug-time bug and a silent release-time behavior, betting that most overflow bugs get caught in testing before they reach a release binary. Neither choice is free: Go's is fast and simple but never catches an overflow bug for you; Rust's runs a check on every arithmetic operation in debug builds, which is part of why debug builds are measurably slower than release builds beyond just missing optimizations.

The safety/performance story generalizes beyond overflow checks. Because every scalar type in Rust has a size fixed at compile time and known to the compiler with no runtime tag, storing a million of them costs exactly 1,000,000 × size_of::<T>() bytes, contiguous, with zero per-element bookkeeping. ARC 11 · REAL-WORLD INCIDENTS

When the bug classes from §4 shipped for real

Incident 1: Ariane 5 Flight 501 (June 4, 1996)

Thirty-seven seconds after launch, both the primary and backup Inertial Reference Systems of Ariane 5's maiden flight shut themselves down, the rocket's guidance went to an incorrect diagnostic value, and the launcher broke apart under aerodynamic forces — a loss of roughly $370 million. The root cause: a piece of Ariane 4 software, reused unchanged, converted a 64-bit floating-point "horizontal bias" value into a 16-bit signed integer. On Ariane 5, whose flight profile produces a larger horizontal velocity than Ariane 4 ever could, that value exceeded what a 16-bit signed integer can hold — 32,767 — and the conversion raised an exception that no handler caught, by design, because the original engineers had proven the overflow was impossible on Ariane 4's trajectory. This is CWE-704 (incorrect type conversion) at the scale of a national space program: an unchecked narrowing cast from a wide type to a narrow one, reused outside the context that made it safe.

Incident 2: Bitcoin's Value Overflow Incident (August 15, 2010)

A single transaction, recorded in block 74,638, created roughly 184.467 billion bitcoin out of nothing — more than eight thousand times the protocol's entire eventual 21 million supply. The bug: the reference client summed a transaction's output values using a signed 64-bit integer without checking whether the individual outputs, added together, overflowed that type; two outputs were crafted so their sum wrapped around to a tiny positive number, passing the "outputs don't exceed inputs" check. It is textbook CWE-190. The fix shipped within about five hours as an emergency soft fork, and the offending block was orphaned by a chain reorganization once enough of the network upgraded — but for those five hours, the ledger's core invariant (you cannot create money) was false.

Incident 3: RUSTSEC-2021-0003, even Rust isn't immune

Rust's overflow checks don't extend automatically into hand-written unsafe code that computes raw memory offsets. The smallvec crate's insert_many method had a capacity-arithmetic bug: under certain iterator inputs, an internal length/capacity calculation could be wrong, leading the function to write past the end of its allocated buffer — a genuine out-of-bounds write, reachable from perfectly safe calling code. It was fixed in smallvec 1.6.1 and tracked as RUSTSEC-2021-0003. The lesson isn't "Rust failed" — it's that Rust's type system prevents the silent, unnoticed version of these bug classes in ordinary code, but a library author who drops into unsafe to hand-manage a buffer takes back every guarantee this chapter has described, and has to re-derive the arithmetic correctness themselves. Chapter 17 (Unsafe Rust & FFI) returns to exactly this boundary.

ARC 13 · CODE WALKTHROUGH

Where "checked_add" and "char" actually live in the standard library

Every method you called in §8 and every fact about char from §7 is implemented in library/core — the allocation-free heart of the standard library that even #![no_std] embedded programs can use. The shapes below are simplified for readability but faithful to the real source tree and its macro-driven structure.

library/core/src/
├── num/
│ ├── ● mod.rs — shared numeric docs/helpers used by every integer width
│ ├── ● int_macros.rs — int_impl! macro; generates checked_add/wrapping_add/… once per signed width
│ ├── ● uint_macros.rs — uint_impl! macro; the unsigned mirror (u8..u128, usize)
│ └── mod.rs → invokes both macros once per concrete type (i8, i16, … u128)
├── char/
│ ├── ● convert.rs — char::from_u32(): the Unicode Scalar Value validity check from §1/§7
│ └── methods.rs — is_alphabetic(), to_uppercase(), etc.
└── ops/arith.rs — the Add/Sub/Mul traits that give meaning to +, -, *

(1) One macro, twelve types. Rust doesn't hand-write checked_add twelve times — it writes the logic once as a macro and invokes it once per width, so i8 and i128 share identical, tested logic:

Rustnum/int_macros.rs — checked_add, simplified
// This body is generated once per signed width by int_impl!,
// so this exact logic backs i8::checked_add through i128::checked_add.
pub const fn checked_add(self, rhs: Self) -> Option<Self> {
    // add_with_overflow is a compiler intrinsic: one hardware add,
    // plus a read of the CPU's overflow flag — not a second pass.
    let (a, b) = self.overflowing_add(rhs);
    if b { None } else { Some(a) }
}

(2) char is a validated u32, not a free-for-all one. This is exactly why char::from_u32 returns an Option<char> instead of a plain char — not every u32 is a legal Unicode Scalar Value:

Rustchar/convert.rs — from_u32, simplified
pub const fn from_u32(i: u32) -> Option<char> {
    // A Unicode Scalar Value is any code point in 0..=0x10FFFF
    // EXCEPT the surrogate range 0xD800..=0xDFFF, which UTF-16
    // reserves for encoding code points above the Basic Multilingual
    // Plane. That's the entire reason char can't just be "a u32".
    if (i > 0x10FFFF) || (0xD800..=0xDFFF).contains(&i) {
        None
    } else {
        // SAFETY: just checked i is a valid Unicode Scalar Value.
        Some(unsafe { transmute(i) })
    }
}

(3) Where the debug/release overflow check from §8b actually lives. It is not a branch int_macros.rs writes by hand — the plain + operator lowers to the same add_with_overflow intrinsic used above, and the compiler flag -C overflow-checks (on by default in the dev profile, off by default in release) decides whether the generated machine code branches on the overflow flag and panics, or discards it and keeps only the wrapped result:

conceptualwhat `a + b` compiles to, per profile
// dev profile (overflow-checks = true, the cargo default):
let (result, overflowed) = a.overflowing_add(b);
if overflowed { panic!("attempt to add with overflow"); }
result

// release profile (overflow-checks = false, the cargo default):
a.wrapping_add(b)   // the overflow flag is computed and discarded
WHY NOT JUST ALWAYS CHECK?

Because the check isn't free at scale: a tight numeric loop that runs the overflow check on every iteration measurably loses out to one that doesn't, and much of Rust's numeric code (parsers, codecs, game and graphics math) runs in exactly that shape. The dev/release split is a bet that overflow bugs are development-time bugs — caught by running your test suite in debug mode, where they're loud — and that correctly-tested code in production doesn't need to pay a per-operation tax for a condition that shouldn't occur. You can override the default in Cargo.toml with [profile.release] overflow-checks = true if you'd rather pay the cost everywhere.
