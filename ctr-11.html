Chapter 10 showed you what an image is: a manifest, a config blob, and a stack of content-addressed layer blobs. ARC 01 · THE PROBLEM

Two strangers' processes must agree on a wire format

A registry is the least glamorous, most load-bearing piece of container infrastructure: a stateless HTTP server, usually backed by an object store, holding immutable content-addressed blobs and a layer of mutable pointers on top. Almost nothing about it is specific to containers — it's a generic content-addressed blob store with one addition — but every property it must satisfy is forced by the same five requirements:

  • No shared code between client and server. Docker Desktop on a laptop, containerd on a Kubernetes node, Podman on a workstation, and GitHub Actions' runner must all push and pull against Docker Hub, GHCR, Quay, ECR, and self-hosted Harbor instances — a matrix of N clients × M registries that only a published wire protocol can make tractable.
  • Integrity across an untrusted network. A layer pulled onto a production node must be provably the exact bytes that were pushed — no truncation, no bit flip, no man-in-the-middle substitution.
  • Don't re-transfer what's already there. Base-image layers (debian:bookworm-slim, node:20) are shared by thousands of derived images. Re-uploading a shared 80 MB layer on every CI push does not scale.
  • Atomicity of "the image now exists." A puller must never observe a manifest that references a layer blob that hasn't finished uploading — there is no useful notion of a half-pushed image.
  • Access control on a shared, multi-tenant service. Docker Hub serves millions of repositories to millions of clients; public reads and gated, per-repository writes must be enforceable without the registry holding a persistent, stateful session per client.

The OCI Distribution Spec is the industry's converged answer to exactly this problem — a small set of REST endpoints under /v2/, content addressing by SHA-256 digest, and a token-based auth scheme layered on top of plain HTTP. Docker and Podman implement it identically — not because one copied the other, but because the spec they both consume was, historically, Docker's own API, donated to the Linux Foundation's Open Container Initiative in 2018 as-is. There is effectively zero protocol-level difference between the two engines here; the divergence, where it exists, is in which client library speaks the protocol (containerd's remotes/docker package for Docker, containers/image for Podman and skopeo) and in the optional signing story layered on top — which is where this chapter's Docker-vs-Podman comparisons live.

WHERE THIS SITS IN THE STACK

Chapter 10 answered "what bytes make up an image" — manifest, config, layers, all addressed by digest. ARC 02 · HISTORICAL CONTEXT

From a mutable Python service to a governed open standard

The registry protocol you use today did not arrive as a clean design — it was rewritten once, under real production pain, and then handed to a neutral standards body almost unchanged. Click through the timeline.

Interactive timeline — how the wire protocol convergedCLICK EVENTS
DEEP CONTEXT · A SPEC THAT WAS A CODEBASE FIRST

Most standards are written before implementations compete to match them. The Distribution Spec ran backwards: Docker shipped docker/distribution (the "Registry v2" server) in 2015, the whole ecosystem — GitHub, Quay, Amazon, Google, every private registry vendor — implemented compatible clients and servers against its de facto behavior for three years, and only in 2018 did the OCI publish the prose specification and the conformance test suite. That ordering explains why the spec still uses header names like Docker-Content-Digest and media types prefixed vnd.docker.* alongside the newer vnd.oci.* ones — backward compatibility with a codebase, not a whiteboard.

ARC 03 · NAIVE SOLUTION

Attempt #1: a file server with a PUT and a tag

Derive it honestly. If you didn't know the real protocol, the obvious first cut is: images are just tarballs, so store each one under a name, and overwrite it on every push.

bashnaive_push.sh — the strawman
# "push": always upload the WHOLE image, every layer, every time,
# keyed only by a human-chosen, mutable name. No hashing, no auth.
tar czf /tmp/image.tar.gz ./image-rootfs/
curl -X PUT --data-binary @/tmp/image.tar.gz \
  http://registry.internal/images/myapp:latest

# "pull": just GET it back and trust whatever bytes arrive.
curl -o /tmp/image.tar.gz \
  http://registry.internal/images/myapp:latest
tar xzf /tmp/image.tar.gz -C ./image-rootfs/

This "works" for a demo: one client, one server, a trusted network, a handful of pushes a day. It even gets something right by accident — a PUT to a fixed URL is at least simple to reason about. It falls apart the moment you add the things every real fleet has on day one: more than one image sharing a base layer, more than one person pushing, and a network you don't fully trust.

ARC 04 · WHY IT FAILS

The math of re-uploading everything, every time

Three failures, each quantifiable, each a direct consequence of "no content addressing, no dedup, no atomicity, no auth":

THE BANDWIDTH BILL

Assume a 5-layer image built FROM debian:bookworm-slim whose shared layers total ~80 MB, with a 4 MB application layer on top. A monorepo CI pipeline with 40 services, each pushing 15 times a day, all sharing that base: naive push transfers 80 MB × 40 × 15 ≈ 48 GB/day of pure duplicate bytes for a base layer that changed zero times. The real protocol (§5) transfers it once, ever, per registry — every subsequent push is a single HEAD request, a few hundred bytes.

  • No integrity check. The naive PUT/GET never verifies what arrived matches what was sent. A truncated upload, a proxy that mangles bytes, or a compromised mirror can silently hand a corrupted or substituted rootfs to every puller — and nothing in the protocol would ever notice.
  • No atomicity. Two CI jobs racing to push myapp:latest can interleave: reader B might GET a response constructed from bytes written by job A's PUT and job C's still-in-flight PUT, depending on how the naive file server buffers writes. There is no notion of "the push either fully happened or didn't."
  • No access control. Anyone who can route a packet to the naive endpoint can overwrite myapp:latest in production. There is no way to make reads public and writes gated without bolting on an entire second system.

Fixing all four — content addressing, dedup, atomic publish, and auth — without inventing a bespoke protocol per registry vendor is exactly what the Distribution Spec is for.

ARC 05 · BETTER SOLUTION

Building the real protocol, one requirement at a time

Step through the derivation. Each step below fixes exactly one failure from §4, and by the end you have (almost) the real OCI Distribution Spec.

Deriving the Distribution SpecSTEP-BY-STEP
THE ONE-SENTENCE VERSION

A registry is a key-value store where blobs are keyed by the SHA-256 hash of their own bytes (so "do you have this?" is a single stateless HEAD, and "give me this" can be verified on arrival) and manifests are the one mutable-by-tag pointer allowed to reference those otherwise-immutable keys — and a manifest push is rejected outright unless everything it points to already exists. Everything else in this chapter is detail hanging off that one sentence.

ARC 06 · WHY THAT STILL COSTS

The bill for a stateless, multi-tenant, public API

The real protocol is a genuine improvement, not a free one. Three costs are structural, not implementation bugs:

  • Auth has to be re-derived per request, because HTTP is stateless. A registry cannot keep a logged-in session the way an SSH server can — every request must independently prove authorization, which is why authentication here is a token-issuing dance (§8) rather than a single login. That dance costs an extra round trip to an auth server before the first real request to a new repository.
  • Tiny blobs pay the same round-trip tax as huge ones. A config blob might be 2 KB, but the chunked-upload machinery still costs a POST-to-open-session and a PUT-to-finalize — two round trips for 2 KB of payload. Registries mitigate this with an optional monolithic single-PUT fast path (§8), but not every registry implementation honors it.
  • Content negotiation adds a decision the naive design never had. Since multi-arch manifest lists (chapter 10) exist, a single tag can resolve to different bytes depending on the requester's Accept header and target platform — correct, but it means "GET the manifest" is no longer a context-free operation.
THE ECOSYSTEM'S ANSWER — AND ITS ADMISSION

In November 2020, Docker Hub began enforcing anonymous pull rate limits (100 pulls per 6 hours per IP at launch; 200/6h for free authenticated accounts) specifically because a stateless, public, content-addressed API is cheap to call and expensive to serve at scale — the same design that makes the protocol simple makes it trivially poll-able by every container restart in every Kubernetes cluster on Earth. The industry's fix — pull-through caching mirrors, and registries baked into cloud providers (ECR, GCR, ACR) that customers are already inside the trust boundary of — is a standing admission that a public, unauthenticated-by-default registry API has a real operating cost, not just a theoretical one. §11 covers the incident in more depth.

WHY THE REGISTRY ITSELF STAYS DUMB

The reference server implementation, distribution/distribution, has no concept of a user account, a password, or a signature format baked in. It validates digests and enforces the manifest-references-existing-blobs rule — that's the entire "business logic." Authorization is delegated to whatever issues Bearer tokens (Docker Hub runs its own; GHCR ties into GitHub's identity; a private Harbor instance can plug in LDAP or OIDC) and signing is delegated entirely outside the spec. This is the same "do one thing, compose the rest" instinct you saw in chapter 9's OCI Runtime Spec: a minimal, auditable contract in the middle, with pluggable systems on both sides.

ARC 08 · INTERNAL IMPLEMENTATION

The actual bytes on the wire

Now the mechanism at the level you'd need to debug a failed push. Three pieces: (a) the Bearer-token auth dance every single request goes through, (b) the exact HTTP sequence for uploading one blob, and (c) the cost of chunking, which you can tune with the slider below.

(a) The Bearer-token challenge/response — identical in Docker and Podman

Neither engine implements its own auth scheme. Both hit a 401, read the same header, and follow the same three-request dance defined by the Distribution Spec's companion token authentication specification.

The auth challenge, request by requestSTEP-BY-STEP
WHY SCOPE IS THE WHOLE SECURITY MODEL HERE

The token's scope claim — e.g. repository:library/ubuntu:pull or repository:acme/api:pull,push — is checked on every request against exactly the repository and verb it names. A token minted for pull on one repository is useless for pushing to a different one, and tokens are typically short-lived (Docker Hub: 300 seconds). This is the same "narrow, time-boxed grant instead of a standing credential" instinct as capability sets (chapter 7) and rootless UID mapping (chapter 4) — applied to HTTP instead of the kernel.

(b) One blob, start to finish: HEAD, POST, PATCH, PUT

This is the sequence a client runs for every layer and the config blob during a push. The dedup check is the first move, and it's the one that makes most real-world pushes fast.

Uploading one blobSTEP-BY-STEP

Once every blob a manifest will reference exists in the repository — confirmed either by a fresh upload or by the earlier HEAD hit — the client issues exactly one more call:

The registry rejects this PUT with 404 MANIFEST_BLOB_UNKNOWN if any referenced digest is missing — that check, and only that check, is the atomicity guarantee from §5: an image either fully exists (manifest accepted) or does not exist at all (manifest rejected, tag unchanged). The Docker-Content-Digest response header is the canonical, content-derived identity of what you just pushed — the value you should pin in production manifests instead of a mutable tag (§10, §12).

(c) Chunk size is a real knob: round trips vs. retry cost

A registry's PATCH step can be called once with the whole blob, or many times with small chunks. Smaller chunks mean a failed chunk costs less to retry on a flaky link, but every chunk is its own HTTP round trip. Drag the sliders — this is the actual tradeoff a client library like containers/image or containerd's puller has to pick a default for.

CROSS-REPOSITORY BLOB MOUNTING — DEDUP THAT SKIPS THE UPLOAD ENTIRELY

If a blob already exists somewhere in the same registry — even in a different repository than the one you're pushing to — a client can request POST /v2/<name>/blobs/uploads/?mount=<digest>&from=<source-repo>. If the registry has that digest under source-repo and the caller's token also grants pull access to source-repo — the one security check the spec mandates here, to prevent using mount as an oracle for "does this private repo have this blob" — it links the blob into the new repository and returns 201 Created immediately, with zero bytes transferred. This is why pushing forty microservice images that all share one base layer, into forty separate repositories in the same registry, is still just forty single HEAD-or-mount calls for that layer — not forty uploads.

Security surface: what a registry actually protects, and what it can't

  • Integrity is airtight, provenance is not. A digest guarantees the bytes you pulled are exactly the bytes someone pushed. It says nothing about whether that someone should be trusted — that's what signing (§8, §11) exists to add on top.
  • Tags are attacker-movable if push access is compromised. myapp:prod is a label a compromised CI credential can silently repoint. Digest-pinning (myapp@sha256:...) in production deploy manifests converts "trust whoever controls this tag right now" into "trust this exact, already-audited content" — the single highest-leverage practice this chapter teaches.
  • The registry is a confused-deputy risk if token scope is too broad. A CI token scoped to push on an entire organization's namespace, instead of one repository, turns a leaked secret from "attacker can tamper with one service" into "attacker can tamper with everything the org ships."
  • Anonymous pull is, by design, unauthenticated and thus unmetered — which is precisely the property that made the 2020 Docker Hub rate limiting both necessary and disruptive (§11).
ARC 11 · REAL-WORLD INCIDENTS

Three incidents that are really about registries, not runtimes

Incident 1: The November 2020 Docker Hub rate-limit rollout

Docker Hub began enforcing pull rate limits — 100 pulls/6h anonymous, 200/6h free authenticated, keyed by IP or account — against a decade of tooling that treated anonymous, unauthenticated pulls as an unlimited resource. The blast radius was enormous precisely because the protocol makes pulling so cheap: base images baked into thousands of CI pipelines, Kubernetes clusters that re-pull an unchanged image: nginx:latest on every pod restart (no local cache check before the registry round trip, by default), and countless FROM node:20 Dockerfiles all hit the same anonymous quota from shared NAT egress IPs — sometimes an entire company's CI fleet sharing one IP and one quota. Root cause, precisely stated: the Distribution Spec has no concept of "this puller already has an equivalent copy" baked into its authorization layer — dedup happens at the blob level during a *push*, not as a pull-avoidance mechanism — so metering pulls required bolting rate limiting onto an API designed to be cheap to call. Fixes that stuck: pull-through caching mirrors (registry-as-a-cache in front of Docker Hub), moving base images to registries you're already authenticated against (ECR/GCR/ACR for cloud-native fleets), and imagePullPolicy: IfNotPresent hygiene in Kubernetes to stop re-pulling unchanged tags at all.

Incident 2: Public registries as a free CDN for malware

Multiple documented campaigns (security research from Palo Alto Unit 42, Aqua Security, and others, 2019–2021) found cryptomining and backdoor payloads published as ordinary, unauthenticated public images on Docker Hub — some with millions of pulls before takedown. Root cause: the Distribution Spec verifies integrity (the bytes you pulled match the digest that was pushed) but has no opinion whatsoever about provenance (whether the pusher should be trusted, or whether the image's process tree does anything malicious). Anonymous push to public namespaces plus anonymous, rate-limited-but-otherwise-unrestricted pull is a serviceable, resilient distribution channel for anyone — legitimate or not. This is the exact gap image signing (§8, §12) exists to close, and it is why registries increasingly ship native vulnerability scanning and provenance attestation support (the OCI 1.1 referrers API, §8) rather than leaving trust entirely to the puller's judgment.

Incident 3: Deleted secrets that were never actually deleted

Recurring security research (independent scans of public Docker Hub layers by multiple firms) has found live cloud credentials, SSH private keys, and API tokens baked into published image layers — including cases where a later Dockerfile instruction (RUN rm /app/.env) removed the file from the final filesystem view, but the secret remained permanently recoverable because it was written to disk in an earlier, already-pushed layer. Root cause, and it's specific to this chapter's content model: layers are immutable, content-addressed blobs — chapter 6's whiteout mechanism hides a deleted file from the merged overlay view, but the underlying layer blob containing the secret is already sitting in the registry, addressable by its digest, forever (or until explicit blob garbage collection, which most operators never run). Deleting a tag doesn't help either — it only unlinks the pointer; the manifest and every blob it referenced can remain reachable by digest, or via another manifest that references the same blob, until a registry-side garbage collection pass with no live references finds and reclaims them. The fix is entirely upstream of the registry: multi-stage builds (chapter 10) that never let a secret-containing layer reach the final image, and BuildKit/Buildah secret-mount features that inject credentials at build time without writing them to any layer at all.

First, the blob-existence check — the handler behind every dedup HEAD you've seen this chapter:

Goregistry/handlers/blob.go — simplified, faithful to real structure
func (bh *blobHandler) GetBlob(w http.ResponseWriter, r *http.Request) {
    dgst := digest.Digest(mux.Vars(r)["digest"])
    if err := dgst.Validate(); err != nil {
        respond(w, http.StatusBadRequest, v2.ErrorCodeDigestInvalid)
        return
    }

    // The whole "does the registry already have this?" check is one
    // stateless lookup into the content-addressed store — no session,
    // no per-repo lock. This is what makes dedup a single HEAD.
    desc, err := bh.repository.Blobs(r.Context()).Stat(r.Context(), dgst)
    if err == distribution.ErrBlobUnknown {
        respond(w, http.StatusNotFound, v2.ErrorCodeBlobUnknown)   // → client uploads
        return
    }
    w.Header().Set("Docker-Content-Digest", dgst.String())
    w.Header().Set("Content-Length", strconv.FormatInt(desc.Size, 10))
    if r.Method == "HEAD" {
        w.WriteHeader(http.StatusOK)   // → client skips uploading, links existing blob
        return
    }
    serveBlobContent(w, r, bh.repository, desc)
}

Then the finalize step — the moment a chunked upload becomes a permanent blob, and where digest fraud gets caught:

Goregistry/handlers/blobupload.go — PutBlobUploadComplete, simplified
func (buh *blobUploadHandler) PutBlobUploadComplete(w http.ResponseWriter, r *http.Request) {
    dgst := digest.Digest(r.URL.Query().Get("digest"))

    // Any bytes sent as the PUT body are the FINAL chunk, appended first.
    if r.ContentLength > 0 {
        buh.Upload.Write(r.Context(), r.Body)
    }

    // The registry hashes everything it has received so far — every
    // prior PATCH plus this final write — and compares to the digest
    // the CLIENT is claiming. This is the entire integrity guarantee:
    // the server recomputes, it never trusts a client-supplied hash.
    desc, err := buh.Upload.Commit(r.Context(), distribution.Descriptor{Digest: dgst})
    if err == distribution.ErrBlobInvalidDigest {
        buh.Upload.Cancel(r.Context())               // upload session destroyed
        respond(w, http.StatusBadRequest, v2.ErrorCodeDigestInvalid)
        return                                        // client must start over from POST
    }

    w.Header().Set("Docker-Content-Digest", desc.Digest.String())
    w.Header().Set("Location", buildBlobURL(buh.Repository.Named(), desc.Digest))
    w.WriteHeader(http.StatusCreated)
}

Finally, the manifest handler's atomicity check — the code that makes half-pushed images structurally impossible to publish:

Goregistry/handlers/manifests.go — PutManifest, simplified
func (imh *manifestHandler) PutManifest(w http.ResponseWriter, r *http.Request) {
    manifest, desc, err := unmarshalManifest(r)
    // ... media-type / schema validation elided ...

    // THE atomicity check: every blob this manifest names — config AND
    // every layer — must already be stat()-able in THIS repository.
    // Skip even one, and the whole publish is rejected. No partial state
    // is ever observable by a concurrent puller.
    for _, ref := range manifest.References() {
        if _, err := imh.Repository.Blobs(r.Context()).Stat(r.Context(), ref.Digest); err != nil {
            respond(w, http.StatusNotFound, v2.ErrorCodeManifestBlobUnknown)
            return
        }
    }

    revision, err := imh.Repository.Manifests(r.Context()).Put(r.Context(), manifest)
    // The TAG is just a mutable link written AFTER the immutable manifest
    // blob is stored — repoint it, and nothing already-pushed changes.
    if isTag(mux.Vars(r)["reference"]) {
        imh.Repository.Tags(r.Context()).Tag(r.Context(), reference, distribution.Descriptor{Digest: revision})
    }
    w.Header().Set("Docker-Content-Digest", revision.String())
    w.WriteHeader(http.StatusCreated)
}
WHY IT WAS BUILT THIS WAY

1. The server never trusts a client-supplied digest for anything except addressing. Every write is re-hashed server-side before being accepted — a client claiming a false digest gets 400 DIGEST_INVALID, not a stored lie. 2. Atomicity lives entirely in ordering, not in a transaction. Blobs are written and committed before the manifest that references them is even considered — there's no two-phase commit, just a topological constraint (dependencies before dependents) that the manifest handler enforces by refusing to proceed otherwise. 3. Tags are cosmetic. The manifest blob and everything it references form the actual, permanent, content-addressed object; a tag is a small mutable record pointing at one — which is exactly why digest-pinning (§10, §12) sidesteps every tag-related trust problem by referencing the permanent object directly.
