BLOCKCHAIN FUNDAMENTALS · CHAPTER 11

The P2P Network:
Gossip, Propagation & Eclipse Attacks

A block mined in Reykjavik has no address book telling it who else exists. It must reach every other node on Earth — including nodes run by people who would profit from it arriving late, or never — over a network that anyone can join, anonymously, without permission, and that no single party operates or can even fully enumerate. This chapter derives the network Bitcoin actually runs on: an unstructured gossip overlay that trades bandwidth for resilience, the announce-then-fetch protocol that makes flooding tolerable, the address manager that decides who you talk to, and the eclipse attack that exploits exactly the part of the design you'd be tempted to skip.

ARC 01 · THE PROBLEM

Broadcast, not lookup, with no directory and no admission control

Chapter 6 established that Byzantine agreement requires every honest participant to eventually observe the same messages. Chapter 10 showed that fork races are decided by whose block arrives first at the miners who matter. Both chapters quietly assumed a mechanism that gets a block from the node that produced it to every other node in the system. This chapter builds that mechanism, and shows it is far from quiet: it is a distinct, adversarial networking problem with its own impossibility-flavored tensions.

State the requirements precisely, because each one eliminates entire families of solutions before you write a line of code:

  • Permissionless join. Any machine, anywhere, with no approval from any operator, must be able to become a full participant. There is no signup, no certificate authority, no allowlist — chapter 7 already established that identity itself is free and therefore meaningless as a gatekeeping mechanism.
  • No central directory. A single "list of all nodes" server is a single point of failure, a single point of censorship, and a single subpoena target. Whatever answers "who do I talk to?" must itself be decentralized, or the entire threat model collapses to "attack the directory."
  • Partition resistance. Nodes join and leave constantly (churn), links fail, ISPs misbehave, and the network must stay connected — probabilistically — through all of it, without any node needing a complete map of the topology.
  • Resistance to targeted attack. It is not enough for the network to survive random failures; it must be hard for an adversary who is willing to spend real resources to isolate one specific victim node from the honest majority. §11 shows exactly what happens to a victim who loses this property.
  • Eventual delivery, bounded in practice. Every block or transaction broadcast by any honest node must reach every other honest node — not "with probability 1 given infinite time" but in a number of seconds small enough that chapter 10's fork-choice rule converges before the next block is found roughly one time in ten minutes.

Notice what is not on this list: efficient point-to-point lookup. Nobody needs to ask "which node has transaction X?" — the goal is the opposite of a lookup service. Every node must eventually have everything. That single observation is the entire chapter in miniature, and §5 will use it to eliminate the most obvious candidate architecture.

WHY THIS MATTERS FOR THE NEXT THREE CHAPTERS

Chapter 10's orphan-rate math had a free variable it never explained: propagation delay. That number is not a physical constant — it is an engineering outcome of exactly the design decisions in this chapter: how many peers you gossip to, how large your messages are, and whether you send full data or just an announcement. Chapter 12's scaling trilemma will lean on this chapter's bandwidth numbers directly: a bigger block is a slower-propagating block, and a slower-propagating block is measurably more centralizing. Nothing in this course after this point can be reasoned about honestly without this chapter's vocabulary.

ARC 02 · HISTORICAL CONTEXT

Gossip is older than blockchains — Bitcoin inherited it, then hardened it under fire

Nothing about Bitcoin's networking is novel in isolation; every piece has a lineage in distributed systems research and in the file-sharing networks of the previous decade. What is novel is the adversarial pressure — file-sharing networks had freeloaders and lawsuits; Bitcoin's network has attackers with a direct financial incentive to double-spend, censor, or deanonymize. DEEP CONTEXT · GOSSIP HAS A FORMAL NAME

What this chapter calls "flooding" is, in the distributed-systems literature, an epidemic algorithm — the term comes from Demers et al.'s 1987 Xerox PARC paper on replicated database maintenance, which modeled message spread on random graphs using the same differential equations epidemiologists use for disease spread. The result that matters here: on a random graph where each node forwards to d random peers per round, the expected number of rounds to reach all N nodes is O(log N / log d) — logarithmic, not linear, in network size. That single fact is why gossip scales to tens of thousands of Bitcoin nodes without anyone coordinating a broadcast tree. §10 turns this into a live formula.

ARC 03 · NAIVE SOLUTION

Attempt #1: push everything to everyone, immediately

Derive it honestly, the way §1 demands. You have a handful of connections to other nodes (never mind for now how you found them — §7 answers that). A new block arrives, or you mine one. The simplest possible thing to do is shove the entire block down every connection you have, right now, and let each recipient do the same:

pythonnaive_flood.py — the strawman, annotated
def on_new_block(node, block):
    # block just arrived on some connection, or we mined it ourselves
    for peer in node.connections:          # ALL of them — no exceptions
        peer.send("block", block)          # push the FULL 1-4 MB payload
        # no check: does peer already have this? is it even valid?
        # no announce step, no request step — just send

This is not a strawman built to be laughed at — it is the correct first answer, and it already gets the hard part right: with no coordination at all, a message dropped anywhere in the graph reaches everywhere reachable from it, and it degrades gracefully — no single node's failure stops delivery, because every node that received the block already forwarded it before it could fail. Gnutella (1999) worked exactly this way and successfully replaced Napster's central index for years.

ARC 04 · WHY IT FAILS

Redundant transmission is fine for text; it is not fine for megabytes

The naive flood's problem is not correctness — every reachable node does receive the block. Its problem is that it pays for delivery with redundant transmission that scales with connectivity, not with information content. Quantify it, because the number is the entire argument:

  • Every edge carries the payload at least twice. If A and B are both connected to C, and A sends C the block, C's naive handler forwards it back out to every connection — including, in a symmetric gossip implementation, right back toward A if A is also in C's peer list along another path, and always onward to B, who most likely already got it from someone else in the same few hundred milliseconds.
  • The waste is proportional to average node degree, not to network size. On a graph where the mean degree is d, a node that receives a block from one neighbor blindly resends it to the other d−1 — most of whom have, or are about to have, a copy already. For Bitcoin's actual ~8–10 outbound × up to 125 total peers per node (§7), naive full-block push multiplies total network bytes transferred by roughly d compared to a scheme that never resends known data.
  • No validation gate before relay. The naive handler forwards before checking proof-of-work, before checking a single signature. An attacker connected to you can hand you 4 MB of syntactic garbage and watch you dutifully forward it to everyone you know, burning their bandwidth and CPU on data that fails validation on arrival — a trivial amplification attack with a built-in botnet: your own peers.
THE NUMBERS

Take a modest simulation: 15,000 reachable nodes (roughly Bitcoin's public-node count in recent years), mean out-degree 10, a 1.4 MB block. Naive full push, no deduplication: each of the ~150,000 directed edges in the graph carries the full block essentially once per hop it's forwarded across, and because nodes don't know what their neighbors already hold, blocks continue circulating in loops until a TTL or a deduplication cache (itself an admission the naive model is incomplete) stops them. Even a conservative estimate — one full transmission per edge — is ~1.4 MB × 150,000 ≈ 210 GB of traffic for one block. At one block per ~600 seconds that is a permanent, unbounded upload tax on every participant, scaling with everyone else's connectivity, not just their own.

The fix is not to abandon flooding — §5 will show flooding survives, because its redundancy is precisely what buys partition resistance. The fix is to stop sending payloads blindly and start announcing them, so a peer can say "I already have that" before a single byte of block data crosses the wire.

ARC 05 · GOSSIP VS. A STRUCTURED OVERLAY

Two ways to organize peers — and why the efficient one loses

By 2008 there was a well-developed alternative to unstructured flooding: the distributed hash table. BitTorrent's trackerless mode (2005) already used Kademlia to answer "which peers have piece X of this torrent?" in logarithmic hops. It is the obvious modern candidate, and Satoshi's design explicitly does not use it. Derive why, by examining what a DHT optimizes for and what it costs.

Candidate A: a structured overlay (DHT / Kademlia-style)

Give every node an identifier (say, hash of its IP or a random ID) and arrange the overlay so each node's neighbor set is determined by distance in ID-space to that node's own ID. Lookups route toward the target ID, halving the remaining distance each hop — O(log n) hops to find whoever "owns" a given key. This is precisely the right tool when the question is "who has this specific piece of data?" — exactly BitTorrent's problem, and exactly not Bitcoin's. §1 already established the requirement: every node needs every block, not the answer to a lookup. Worse, the very property that makes DHT lookups efficient — a small, structured, ID-determined neighbor set — is a gift to an attacker: if you know (or can compute) a victim's node ID, you know exactly which small set of IDs must be controlled to surround it in ID-space. Sit & Morris's 2002 analysis of DHT security and Douceur's 2002 Sybil-attack paper both make this precise: structured routing tables convert "isolate one node" from a search problem into an arithmetic one. Rejected: efficient routing and eclipse-resistance are close to opposites.

Candidate B: unstructured gossip + announce-before-send ✓

Keep peer selection close to arbitrary — a node's neighbor set has no relationship to its identity, its address, or the data it holds. There is no "correct" set of neighbors to compute, so there is no small target set for an attacker to occupy analytically; the only way to control a node's neighbors is to physically fill its actual connection slots (§8's addrman, §11's eclipse attack). And because the goal is broadcast, not lookup, the redundant fan-out that looked wasteful in §4 is the mechanism that makes partition genuinely hard: with mean degree d, an adversary must sever a large fraction of ~d·N/2 edges to split the graph, where a DHT's sparse, structured edges can sometimes be cut in far fewer places. THE CENTRAL DESIGN DECISION OF THIS CHAPTER

Every subsequent section is a variation on one trade: Bitcoin buys eclipse-resistance and partition tolerance by accepting redundant, bandwidth-expensive flooding, rather than buying bandwidth efficiency by accepting a structured topology an attacker can compute. §8 through §10 are all about clawing back the bandwidth cost (compact blocks, relay networks) without ever giving up the unstructured shape that makes the cost worth paying.

ARC 06 · WHY THAT STILL COSTS

Announce-then-fetch fixes bandwidth; it adds a round trip you now owe

inv/getdata is a strict improvement on §4's bandwidth bill — a node that already has a block spends a few dozen bytes (a 36-byte inventory vector) instead of megabytes to say "I already have that." But nothing is free, and the costs that remain are exactly the ones the rest of this chapter has to solve:

  • You paid a round trip for every hop. The naive push transferred data in one leg. Announce-fetch needs three: inv out, getdata back, then the block. Each hop across the gossip graph now costs roughly one full network round-trip-time in addition to the transfer time — and that RTT is pure latency tax, paid even when both ends have gigabit links. Across a network diameter of several hops, this compounds directly into the propagation delay that chapter 10 measures.
  • The redundancy that buys resilience still costs bandwidth. Even with no wasted payload transfers, every node still relays every inv to every peer, and every peer still requests and validates the block once. The marginal waste of full flooding is gone; the structural cost of gossip — O(N·d) total messages for a broadcast to N nodes at degree d — is not, and cannot be, without abandoning the design decision from §5.
  • It does nothing about peer discovery or eclipse risk. inv/getdata assumes you already have a set of peers to gossip with. It says nothing about how you found them, whether an adversary can predict or control that set, or what happens if every one of your connections happens to be the same attacker wearing different IP addresses. That is a separate, harder problem — §7 and §8 build the machinery for it, and §11 shows what happens when that machinery is missing or defeated.

So the final architecture is: unstructured gossip for resilience, announce-before-send for bandwidth, a purpose-built address manager for peer discovery that resists prediction and manipulation, and — because even optimized flooding is still flooding — a further layer of protocol optimization (compact blocks, relay networks) to push propagation delay down toward the physical minimum. Meet the whole thing.

THE ASYMMETRY THAT MAKES THIS DEFENSIBLE: OUTBOUND VS INBOUND

A node trusts its outbound connections far more than its inbound ones, for one structural reason: you chose your outbound peers, by your own node's addrman selection, using your own randomness. Your inbound peers chose you — anyone can open a TCP connection to your listening port, including an attacker who has done nothing but scan the internet for open 8333s. Bitcoin Core's default of ~8–10 automatic outbound connections against up to ~117 inbound slots is not an oversight; it reflects that a handful of self-selected peers are worth more, defensively, than a hundred self-selected-by-strangers ones. §11's eclipse attack targets outbound connections specifically because that is the set an attacker has to work to control — and where control is most valuable once achieved.

ARC 08 · INTERNAL IMPLEMENTATION

From cold boot to steady-state relay: the real mechanics

Three pieces, at the level you'd need to modify them: (a) how a node with zero peers finds its first ones and builds a peer table it can trust, (b) the exact byte-level relay protocol, and (c) the optimization that removes most of §6's remaining bandwidth cost.

(a) Bootstrap → addrman → first connections

The address manager's internal structure is the part worth understanding in byte-level detail, because §11's entire attack is a manipulation of exactly this data structure. It holds two tables:

TABLECAPACITY (BITCOIN CORE)WHAT GOES IN ITBUCKET KEY
new1024 buckets × 64 entries ≈ 65,536addresses heard about via addr gossip but never successfully connected to — unverified rumor. hash(secret nonce, source-group, address-group) — deterministic per node instance, unpredictable to an outside observer.
tried256 buckets × 64 entries ≈ 16,384addresses this node has personally completed a version/verack handshake with at least once — verified reachable. hash(secret nonce, address-group) — same idea, smaller and higher-trust table.

Two design details in that key are load-bearing. First, the hash is seeded with a random secret generated at node startup — an attacker cannot precompute which bucket their addresses will land in, because they don't know your node's key. Second, the key incorporates the /16 network group of the address's source, not just the address itself — capping how many entries one operator's IP range can occupy in any single bucket regardless of how many distinct IPs they present. §11 explains exactly why both of these details exist: neither was there in 2015.

(b) The relay protocol, and what compact blocks remove from it

The steady-state relay cycle is the concrete realization of §5's inv/getdata design:

wire formatone relay hop, byte-accurate
-- announcer, upon validating a new block locally --
inv        {type: MSG_BLOCK, hash: 32 bytes}                    // ~37 bytes total incl. header

-- receiver, if hash not already known --
getdata    {type: MSG_BLOCK (or MSG_CMPCT_BLOCK), hash: 32 bytes}

-- announcer --
block      {80-byte header, varint tx count, full serialized txs} // full weight, up to ~4M weight units
-- OR, for BIP152 peers --
cmpctblock {80-byte header, nonce: 8B, shortid[]: 6B each, prefilled_tx[]}

A BIP152 cmpctblock replaces "here are 2,000 full transactions" with "here are 2,000 six-byte fingerprints" — because the receiver's mempool very likely already has almost every one of those transactions from ordinary tx-relay gossip that happened before the block was found. HIGH-BANDWIDTH VS LOW-BANDWIDTH MODE

BIP152 defines two relay modes per connection. A node designates up to 3 peers as high-bandwidth — chosen by who has historically delivered valid blocks fastest — and unicasts a cmpctblock to them immediately, unsolicited, the instant it validates a block: no inv/getdata round trip at all. Every other peer stays low-bandwidth: normal header announcement, then an explicit getdata for the compact block. High-bandwidth mode trades a small amount of extra unsolicited traffic (occasionally to peers who already have the block from elsewhere) for removing an entire round trip on the paths that matter most for propagation speed.

(c) Headers-first: bounding what a stranger can make you buffer

Before requesting any block body, a syncing node requests and validates a chain of headers — 80 bytes each, cheap to verify (check the proof-of-work, check it links to a known chain). Only after a header chain with sufficient cumulative work validates does the node request the actual block bodies behind it. This closes a real 2013 pathology (§11 doesn't cover this one, but it's worth stating precisely): a "blocks-first" node could be handed a long, low-difficulty alternate chain's full block bodies before its work was checked, filling memory and disk with data that was always going to be rejected. Headers-first makes the cheap check — proof-of-work — the gate before the expensive one — full validation.

ARC 09 · TRADEOFFS

Five ways to move data through a P2P network

Every large P2P system answers "how do messages find every node?" differently, and the spread is a proof by exhaustion that there is no dominant design — only different prices for the same set of properties:

SYSTEMTOPOLOGYWHAT THEY BOUGHTWHAT THEY PAID
BitcoinUnstructured gossip, announce-then-fetch eclipse-resistant by default no single cut point O(N·d) messages per block needs compact blocks to stay fast
BitTorrent (trackerless)Kademlia DHT for peer discovery, direct swarm exchange for data O(log n) peer lookup scales to huge swarms cheaply structured routing table is a known attack surface fine for BitTorrent — no attacker profits from eclipsing one downloader

Read the pattern: whenever the goal shifts from "everyone must get everything, resiliently" (Bitcoin blocks) to "find one specific thing efficiently" (BitTorrent piece lookup) or "hide who originated this" (Dandelion++ transaction relay), the right topology changes with it. There is no single correct answer to "how should peers be arranged" — only the right answer for what you are trying to make hard for an attacker to break.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

From propagation delay to orphan rate to attack cost — the numbers

Chapter 10 left "propagation delay" as an input to its orphan-rate formula. Here is where that number comes from, and what it costs to attack the system that produces it.

  • Measured propagation, pre-optimization. Decker & Wattenhofer's 2013 measurement study found a median delay of roughly 6.5 seconds to reach 50% of measured nodes and up to ~40 seconds to reach 95%, for blocks of that era's typical size, before compact blocks existed. They also showed propagation delay rising with block size — the direct empirical seed for chapter 12's scaling trilemma.
  • Post-BIP152 (2016), and with relay networks. Compact blocks cut the dominant cost — re-transmitting transaction data the receiver already had — to a low-single-digit-percent tail. Among large pools running FIBRE/Falcon, propagation to the top of the mining-hashrate distribution is commonly sub-second to a couple of seconds — the redundant fan-out from §5 combined with a fast, trusted core.
  • Propagation delay → orphan rate, directly. The Decker–Wattenhofer relationship (refined in later work) is close to P(orphan) ≈ 1 − e−λd, where λ is the network-wide block-finding rate (1/600 s on Bitcoin) and d is the propagation delay to the hashrate that matters. At d = 6.5 s that's ≈1.1%; at d = 40 s, ≈6.5%. Compact blocks pushing d toward ~1 s takes the same formula below 0.2% — the entire practical justification for BIP152 in one number.
  • Bandwidth cost per honest node. A well-connected full node with default settings commonly uploads several GB/day just relaying blocks and transactions it will never use itself — the direct, ongoing price of §5's redundancy, paid by every full node so that no single one is load-bearing.

Cost to eclipse a victim, concretely

Heilman et al.'s 2015 measurements against pre-fix Bitcoin Core found that filling a victim's tried and new tables convincingly took on the order of a few thousand distinct IP addresses (the paper's own figure is roughly 4,600) — trivially affordable by renting IP ranges from cloud providers, and entirely below any threshold that would look like an unusual event to the victim. §11 walks through exactly what that attack does and what closed it.

ARC 11 · REAL-WORLD INCIDENTS

Three papers that rewrote the network layer

Incident 1: The Heilman–Kendler–Zohar–Goldberg eclipse attack (2015)

"Eclipse Attacks on Bitcoin's Peer-to-Peer Network" (Heilman, Kendler, Zohar, Goldberg — USENIX Security 2015) found that pre-fix Bitcoin Core's addrman had three simultaneous weaknesses: bucket selection wasn't keyed by a per-node secret strongly enough to stop an outside attacker from steering where their own addresses landed; the tried table's eviction logic could be manipulated to push out honest entries in favor of attacker-supplied ones; and there was no protection against a single source flooding many addresses into the same node's tables. Combining these, an attacker controlling roughly 4,600 IP addresses — cheap on cloud infrastructure — could, over time or by forcing the victim to restart, ensure that every one of the victim's next outbound connections went to an attacker-controlled address, fully occupying its ~8 outbound slots with zero honest peers left. Once eclipsed: the attacker can feed the victim a fabricated view of the chain (enabling a double-spend specifically against that victim, since it sees a fake "confirmed" state), can amplify a selfish-mining strategy by controlling what the victim relays and when, and — for an eclipsed miner — can silently discard the victim's found blocks, wasting its hashrate on a chain nobody else ever sees.

Fixes that shipped (Bitcoin Core 0.14–0.21, mostly 2017–2020): bucket selection keyed by a secret, node-generated random value combined with the /16 source group, so an outside attacker cannot predict or steer bucket placement; caps on entries per network group per bucket; feeler connections — short-lived, low-cost outbound test connections to addresses from the new table specifically to verify reachability before promoting an address to tried, closing the "just claim to be reachable" hole; anchor connections — a node persists two of its current block-relay-only peers to disk and reconnects to them first on restart, specifically because restart is when an addrman rebuild is most vulnerable; and block-relay-only outbound connections, which never gossip addr messages or relay transactions, shrinking the surface an eclipse attacker can use to also correlate transaction origin.

Incident 2: BGP hijacking of Bitcoin traffic (Apostolaki, Zohar, Vanbever — 2017)

"Hijacking Bitcoin: Routing Attacks on Cryptocurrencies" (IEEE S&P 2017) observed that Bitcoin nodes were heavily concentrated in a small number of Autonomous Systems — the paper found roughly a third of Bitcoin's reachable nodes hosted behind under 20 ASes — and that an attacker capable of a BGP hijack (advertising false, more-specific routes to reroute internet traffic, a capability real-world ISPs and state actors have demonstrably used) could intercept traffic to and from a large fraction of mining hashrate by hijacking well under 100 IP prefixes. Two attack variants: a partition attack that splits the network into two chains that cannot see each other's blocks until the hijack is lifted, and a subtler delay attack that doesn't sever connectivity at all but manipulates TCP segment boundaries to stall block delivery on chosen links by tens of minutes — invisible to naive monitoring, and capable of measurably increasing the target's stale-block rate without ever showing up as a network partition.

Mitigations proposed and partially adopted: increasing the diversity of a node's peer set across ASes and prefixes rather than picking connections that happen to cluster; monitoring round-trip-time and traceroute anomalies as a routing-attack signal; shorter-lived, more frequently rotated peer selections; and, more recently, BIP324's encrypted and authenticated ("v2") transport (2023), which does not stop a BGP-level reroute but does close off some of the delay attack's specific packet-manipulation tricks by making the stream tamper-evident. Full defense against a nation-state-capable BGP attacker remains, honestly, an open problem — it is a routing-layer attack against an application-layer protocol, and no amount of peer-selection cleverness fully substitutes for a trustworthy underlying network.

Incident 3: Sybil-based transaction deanonymization and the Dandelion++ response

Biryukov, Khovratovich & Pustogarov ("Deanonymisation of Clients in Bitcoin P2P Network," CCS 2014) showed that a modest Sybil presence — around a hundred purpose-built nodes maintaining connections across a large fraction of the reachable network — could observe, for almost any transaction, a small, near-stable set of "entry nodes" that first relayed it. Because ordinary transaction relay is the same flood-and-forward gossip used for blocks, the first-seen pattern leaks a strong statistical signal about which IP the transaction actually originated from, even for users connecting over Tor, since the leak happens at the P2P layer above the transport. This directly informed Dandelion++ (Fanti et al., 2018): before a transaction enters ordinary flood ("fluff") relay, it first travels along a single, randomly chosen "stem" path — one peer to the next, no broadcast — for a random number of hops, so that by the time diffusion begins there is no clean broadcast tree rooted near the true origin for a Sybil observer to trace backward. It is deployed as an opt-in privacy enhancement for transaction relay specifically, not for blocks — blocks have no origin to hide; they are meant to be attributed to whoever mined them.

        # the /16 group, not the raw IP, is hashed — caps one operator's
        # influence over a bucket regardless of how many distinct IPs they use
        group      = net_group(addr)            # e.g. first two octets of an IPv4
        src_group  = net_group(source_addr)
        n_buckets  = 256 if table == "tried" else 1024
        # the secret key is the whole point: an outside attacker who does not
        # know it cannot predict, and therefore cannot steer, this result
        h = sha256(self.secret_key + group + src_group)
        return int.from_bytes(h[:8], "little") % n_buckets

    def add_new(self, addr, source_addr):
        b = self._bucket_for(addr, source_addr, "new")
        slot = self.new_buckets[b]
        if len(slot) >= 64:                       # bucket full: probabilistic eviction, NOT
            self._maybe_evict(slot, addr)          # a blind overwrite — see feeler note below
        else:
            slot.append(addr)

Second, promotion from rumor to trust — the feeler mechanism that closed the "just claim reachability" gap:

pythonconnection_manager.py — feeler connections
def feeler_tick(node):
    # run roughly once every couple of minutes, independent of normal relay traffic
    candidate = node.addrman.pick_random("new")   # unverified — from addr gossip only
    if candidate is None:
        return
    conn = node.try_connect(candidate, short_timeout=True)
    if conn.handshake_ok:                       # version/verack actually completed
        node.addrman.promote_to_tried(candidate)   # NOW it's trustworthy — we proved it ourselves
    conn.close()                                    # feeler connections are never used for real relay

Third, the compact block reconstruction that removes most of §8(b)'s bandwidth:

pythoncompact_block.py — reconstruct a block from short IDs
def reconstruct(cmpct, mempool):
    txs, missing = [], []
    for i, short_id in enumerate(cmpct.short_ids):
        match = mempool.find_by_short_id(short_id, cmpct.nonce)  # SipHash-2-4 keyed by a per-message nonce
        if match is None:
            missing.append(i)              # ~1-5% of a well-connected node's mempool overlap
            txs.append(None)
        else:
            txs.append(match)
    for idx, tx in cmpct.prefilled_tx:   # coinbase is always prefilled — never in anyone's mempool
        txs[idx] = tx
    if missing:
        request_missing(cmpct.peer, missing)   # getblocktxn / blocktxn — ONE more round trip, only for the gaps
        return None                       # block completes once the follow-up arrives
    return assemble_block(cmpct.header, txs)
WHY IT WAS BUILT THIS WAY

1. Secrets, not obscurity, defeat prediction. Bucket hashing was always deterministic — the 2015 fix didn't make it "more random," it made the seed unknown to outsiders, which is the actual property that defeats a targeted attacker. 2. Never trust a claim you haven't verified yourself. The new→tried promotion path requires this node to have completed a real handshake — an attacker asserting "I'm reachable" via gossiped addr messages alone can never reach the trusted table. 3. Optimize the common case, fall back correctly on the rare one. Compact blocks assume high mempool overlap and are simply, cheaply wrong when they're not — the getblocktxn fallback costs one extra round trip only for the actual misses, never for the whole block. All three are instances of the same engineering habit: design for the adversarial case, then optimize for the common one on top.
