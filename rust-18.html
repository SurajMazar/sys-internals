ADVANCED

Macros: Declarative
& Procedural

Somewhere between println!("{} + {} = {}", a, b, a + b) and #[derive(Debug)], Rust runs a second, smaller compiler pass entirely before the one you are used to thinking about: macro expansion rewrites your source code into more source code — as plain token trees — before a single type is checked or a single borrow is verified. This chapter derives why that pass exists (functions cannot be variadic or syntax-aware; the C preprocessor's alternative is a genuine, well-documented bug class), builds a real macro_rules! macro up from its pattern-matching grammar, hand-traces its expansion token by token, and then opens the door procedural macros walk through: three flavors, one shared contract — a TokenStream in, a TokenStream out — that lets ordinary compiled Rust code write Rust code for you.

ARC 01 · THE PROBLEM

A function can't see its own call site

A function is a value-level abstraction. Its signature fixes, once and for all, how many parameters it takes and what type each one is — every call site must conform to that shape, and the function body has no way to know or care how it was spelled at the call site. That shape covers an enormous fraction of what you want to abstract over. It does not cover everything:

  • Variable argument count with heterogeneous types. println!("{} {} {}", 1, "two", 3.0) takes three arguments of three unrelated types, and the count changes from call to call. A function signature cannot express "any number of arguments, of any types, decided per call."
  • Code shaped by a type's structure, not its value. Implementing Debug by printing every field of a specific struct requires code that is different for every struct — there is no function generic enough to be "generic over the list of a struct's field names," because Rust has no runtime reflection.
  • New syntax, scoped to one call site. matches!(x, Some(1) | Some(2)), vec![1, 2, 3], and a hypothetical html! { <div>...</div> } do not look like ordinary expressions being evaluated — they look like Rust growing new grammar for exactly one invocation.
  • Mechanical, zero-runtime-cost code generation. A set of trait impls for a dozen numeric types, a state machine's transition table, a schema description — text you want expanded into real code once, at compile time, with no function-call indirection left behind at runtime.

A macro is Rust's answer to all four: a piece of code that runs during compilation, before your program has even been fully parsed into its final shape, that consumes some of your literal source syntax — a token tree, not a value — and produces more source syntax to compile in its place.

YOU HAVE ALREADY BEEN USING MACROS

Every prior chapter used several: println!, vec!, assert_eq!, #[derive(Debug)], and #[test] are all macros — two different kinds of macro, in fact, which this chapter distinguishes precisely. None of them could be plain functions, for exactly the reasons above. By the end of this chapter you will be able to write your own of both kinds, and — via §15's simulator — watch the compiler's own pattern-matching algorithm decide what your macro expands to.

ARC 02 · HISTORICAL CONTEXT

Fifty years of "code that writes code," before Rust existed

Rust's macro system did not appear from nowhere. It is the direct intellectual descendant of a decades-long argument in programming-language theory about how to let programs manipulate their own syntax safely — an argument C's preprocessor sat out entirely, and one Rust's designers deliberately re-entered forty years later with the benefit of the answer. DEEP CONTEXT · WHAT "HYGIENE" MEANS, AND WHY IT NEEDED A PAPER

Kohlbecker, Friedman, Felleisen & Duba's 1986 paper Hygienic Macro Expansion gave a precise, checkable definition of a property working Lisp programmers had wanted for a decade: a macro's expansion should never accidentally capture, or be captured by, an identifier at its call site — purely because both happen to use the same spelling. Before that paper, hygiene was folklore and naming convention (prefix your macro's internal variables with underscores and hope). After it, hygiene became something a macro system could guarantee mechanically, by tracking which expansion each identifier came from. Scheme's syntax-rules (also 1986) was the first widely-used system built on that guarantee — and it is the closest ancestor, in both shape and spirit, of Rust's macro_rules!.

ARC 03 · NAIVE SOLUTION

Attempt #1: just write more functions

Derive the need honestly before reaching for a macro. Say you want a convenient way to build a Vec from a handful of literal values, without first declaring a mutable variable and calling .push() N times. The function-only toolkit gives you two real, compiling options — and both fall short in an instructive way.

Rustnaive.rs — fixed-arity helper functions (this compiles)
fn vec2<T>(a: T, b: T) -> Vec<T> { vec![].into_iter().chain([a, b]).collect() }
fn vec3<T>(a: T, b: T, c: T) -> Vec<T> { vec![].into_iter().chain([a, b, c]).collect() }
fn vec4<T>(a: T, b: T, c: T, d: T) -> Vec<T> { vec![].into_iter().chain([a, b, c, d]).collect() }
// ...and vec5, vec6, vec7, forever, one function per argument count you'll ever need.

fn main() {
    let v = vec3(10, 20, 30);
}

This compiles and works, but it is not a solution — it is an admission of defeat with extra steps. Rust has no function overloading and no variadic generics, so "one function per argument count" is the only way to keep every call type-checked, and it requires guessing every arity a caller will ever want in advance.

Rustnaive2.rs — the "just take a slice" escape hatch (this also compiles)
fn make_vec<T: Clone>(items: &[T]) -> Vec<T> { items.to_vec() }

fn main() {
    let v = make_vec(&[10, 20, 30]);   // works for any length...
    // ...but you had to build an array literal `[10, 20, 30]` to call it —
    // which is EXACTLY the syntax you wanted `make_vec!` to give you for free,
    // now just wearing different brackets and paying a Clone bound + copy.
}

The slice version handles arbitrary length, but only by pushing the actual problem — "write a literal list of values" — onto array-literal syntax that Rust already had, adding a Clone bound and a copy for free. Neither attempt gets you println!'s harder problem at all: heterogeneous argument types, decided per call, with compile-time-checked formatting. No signature — generic, sliced, or otherwise — expresses "any number of arguments of any types."

ARC 04 · WHY IT FAILS

Two failures, not one: what functions can't do, and what naive text-substitution does wrong

It is tempting to conclude "fine, give user code a variadic escape hatch, the way C does with ... and va_list." That escape hatch is real, and it is also a textbook, catalogued vulnerability class: a C variadic function has no compile-time connection between the format string and the arguments actually passed, so a mismatched printf("%s", user_controlled_int) reads memory as a pointer that was never one — CWE-134, Uncontrolled Format String, still a live bug class in C codebases today. Rust deliberately does not give ordinary code an unsafe variadic mechanism for exactly this reason — println!'s argument/format-string agreement is checked at compile time, which is only possible because it is a macro, not a function.

So a macro system is necessary. But "textually substitute the macro's arguments into its body" — the approach the C preprocessor took in 1972 — is a second, independent failure, and it is worth tracing precisely because Rust's design directly engineers around it. Two classic bugs, both real and both catalogued:

Cdouble evaluation — CERT C rule PRE31-C, "avoid side effects in macro arguments"
#define MAX(a, b) ((a) > (b) ? (a) : (b))

int x = 5;
int hi = MAX(x++, 10);
/* expands, by pure text substitution, to:
     ((x++) > (10) ? (x++) : (10))
   `x++` appears TWICE in the expansion because it appeared once in the
   macro body's template. If x++ > 10 is true, x is incremented AGAIN by
   the true-branch — x ends up incremented 0, 1, or 2 times depending on
   which branch the comparison takes, for ONE syntactic use of `x++`. */
Chygiene failure — the textbook capture bug
#define SWAP(a, b) { int tmp = a; a = b; b = tmp; }

int tmp = 1, other = 2;
SWAP(tmp, other);
/* expands to:  { int tmp = tmp; tmp = other; other = tmp; }
   The macro's OWN internal variable is spelled `tmp` — the same spelling
   as the caller's variable. Textual substitution can't tell them apart:
   the caller's `tmp` is silently shadowed by the macro's `tmp`, and
   `int tmp = tmp;` reads an uninitialized value instead of the caller's 1. */

Both bugs share one root cause: the preprocessor treats macro arguments as raw text to paste, with no awareness that x++ is one expression that should be evaluated once, or that the caller's tmp and the macro's tmp are different names that happen to collide. Rust's declarative macros close both classes structurally rather than by convention: a captured expr fragment is parsed into one indivisible expression node before it is ever substituted (so accidental precedence corruption from raw pasting is categorically impossible), and every identifier introduced by a macro's expansion carries hygiene information that keeps it distinct from same-spelled identifiers at the call site — the SWAP bug is not possible to write by accident in macro_rules!. §5 builds the real mechanism.

ARC 05 · BETTER SOLUTION

Building my_vec!: pattern, repetition, template

macro_rules! macros are built from one or more arms, each shaped like a tiny function from syntax to syntax: (MATCHER) => { TEMPLATE };. The matcher is not a value pattern — it is a pattern over token trees, written with special metavariables of the form $name:fragspec, where the fragment specifier tells the matcher what kind of syntax to capture there — the three you'll use constantly are expr (a full expression), ident (one identifier), and ty (a type). A trailing $( ... ) sep OP group means "repeat this sub-pattern," where OP is * (zero or more), + (one or more), or ? (zero or one, no separator allowed), and sep is an optional literal separator token between repetitions — , almost always.

ARC 06 · WHY THAT STILL HAS COSTS

The bill: what macro_rules! and proc macros cost you, honestly

Declarative macros solve the hygiene and evaluation-order problems structurally — but they are not free, and the costs are worth knowing before you reach for one:

  • Debuggability drops. A type error inside macro-generated code is reported in terms of the expanded code, which you never typed — reading it often requires the third-party cargo expand tool (not built into cargo) to see what your macro actually produced. This is a genuine, widely-felt tax on every macro-heavy dependency.
  • No string-built identifiers. macro_rules! cannot concatenate two captured idents into a new one (there is no $a ## $b the way C's preprocessor has ##) — generating a name like get_ + a field name requires the third-party paste crate or the still-unstable concat_idents!.
  • Item-level hygiene is weaker than you'd guess. Local let bindings are fully hygienic, but two invocations of macro_rules! make_fn { () => { fn helper() {} } } in the same module genuinely collide with "duplicate definitions of `helper`" — item names are not automatically renamed the way local variables are. §14's quiz tests this exact surprise.
  • Recursion has a hard ceiling. A macro that expands by calling itself again (rather than using $(...)* repetition) can hit the compiler's recursion_limit (128 by default) on large inputs — §11 shows a real, commonly-hit instance of this.
  • Procedural macros add a second compiled crate to every build. Writing one means learning syn, quote, and proc-macro2 — three additional dependencies with their own compile cost, paid by every downstream crate (§10 quantifies this).

The community's own guidance reflects this honestly: reach for a macro only after a plain function, a generic function, and a trait have all failed to express what you need — not as a first resort. §9 makes that ordering precise.

ARC 07 · FINAL ARCHITECTURE / MENTAL MODEL

Four flavors, one shared idea: syntax in, syntax out

Rust ships exactly four macro flavors. All four run during the same compiler pass (macro expansion, before name resolution completes); all four consume some of your literal syntax and produce more syntax to splice in its place; none of them can see types, run the borrow checker, or do anything a later compiler phase is responsible for. Click each to see its real invocation syntax, its exact input/output contract, and what it is and is not allowed to do.

Every flavor's contract reduces to: some number of TokenStreams in, exactly one TokenStream out. A TokenStream is an opaque, ordered sequence of token trees — not an AST, not typed, not name-resolved. Whatever comes out is spliced into the source at the invocation point and re-parsed as if you had typed it. That is the entire mental model; the four cards above differ only in how many streams go in and what the compiler does with the one that comes out.

ARC 08 · INTERNAL IMPLEMENTATION

What the compiler actually does, in order

Two genuinely different mechanisms hide behind "macro expansion," depending on which flavor you invoked.

(a) macro_rules!: matcher, transcriber, hygiene contexts

The compiler tokenizes your source, groups matched delimiters into token trees, and then — interleaved with name resolution, since resolving a macro invocation's own name may itself require partial resolution — repeatedly looks for macro invocations and expands them: for each candidate arm, in declaration order, it tries to match the invocation's token trees against that arm's matcher; the first arm that matches has its template transcribed, substituting each captured metavariable and re-emitting each repetition group once per capture. The result is spliced back in and the process repeats until no macro calls remain (a fixpoint) or recursion_limit is hit. Every token the transcriber emits is tagged with a syntax context recording which expansion produced it — the mechanism that makes hygiene automatic rather than a naming convention.

(b) Procedural macros: a compiled function, called mid-compile

A proc-macro crate ([lib] proc-macro = true) is compiled first, then loaded by the compiler as a dynamic library. When the compiler meets a matching invocation, it serializes the relevant tokens into a proc_macro::TokenStream, calls the macro's exported function inside the compiler process, running arbitrary compiled Rust code, and receives a new TokenStream back, which is spliced in exactly like a macro_rules! expansion. Because writing a raw token-stream parser by hand is miserable, almost every real proc-macro crate depends on three crates by David Tolnay: proc-macro2 (re-implements TokenStream so macro code is unit-testable outside a real macro invocation), syn (parses tokens into a full, typed Rust AST — DeriveInput, ItemFn, etc.), and quote! (turns an AST back into tokens using #interpolation syntax that looks like the Rust you're generating).

ARC 10 · PERFORMANCE & SAFETY CHARACTERISTICS

  
Zero runtime cost, non-zero compile-time cost, zero bypassed safety

  
Runtime: a macro's expanded code costs exactly what hand-written equivalent code would cost — full
  stop. Unlike, say, a decorator in a dynamic language, there is no leftover wrapper call, no indirection, no
  trace at all in the compiled binary that a macro was ever involved. By the time codegen runs, "this came from a
  macro" is not a fact the compiler is even tracking anymore.

  
Safety: the exact same borrow checker, type checker, and privacy rules run over macro-generated code
  as over code you typed by hand — a macro can make it easier (or harder!) to accidentally write code that fails
  those checks, but it cannot skip them. This is a direct, structural consequence of macro expansion finishing
  before type checking and borrow checking even begin (chapter 19 makes this ordering concrete at the MIR
  level).

  
Compile time is where the real cost lives. Every proc-macro crate is a second compiled artifact your
  build must produce before it can even start compiling code that uses it, and — unlike a plain dependency — its
  generated code must be re-processed by the rest of the compiler for every invocation site. Drag the sliders
  below to see the shape of that cost (a modeled curve tuned to match the qualitative pattern reported by
  cargo build --timings on real proc-macro-heavy crate graphs, not a live measurement):

ARC 11 · REAL-WORLD PRODUCTION

  
Three incidents you will eventually meet


  
Incident 1: the recursion-limit wall on large schemas

  
Diesel's table! macro generates a substantial amount of code per database table via a
  macro_rules!-based DSL. On real-world schemas with hundreds of columns or tables, users have long
  hit error: recursion limit reached while expanding the macro — Diesel's own documentation
  recommends raising #![recursion_limit = "..."] above the default (128) as a direct, expected fix
  for large schemas. The lesson generalizes: a macro that recurses by re-invoking itself (rather than using
  $(...)* repetition to process a list in one pass) pays one unit of recursion depth per element,
  and a compiler-wide default ceiling exists specifically because unbounded recursive expansion is otherwise
  indistinguishable from an infinite loop to the compiler.


  
Incident 2: the serde/syn/quote tax shows up in every timing report

  
Run cargo build --timings on almost any real-world web service or CLI tool and
  serde_derive — and, transitively, syn, quote, and
  proc-macro2 — routinely appears among the largest single contributors to the build graph's
  critical path, a pattern discussed at length in the Rust community's compile-time-focused writing (matklad's
  widely-read posts on Rust compile times among them). It is not that serde_derive is poorly
  written; it is the structural cost §10 quantified, paid by nearly every crate in the ecosystem because nearly
  every crate needs (de)serialization somewhere in its dependency tree. It is also the direct motivation for
  lighter-weight alternatives like miniserde and nanoserde, which trade serde's feature
  breadth for a smaller compile-time footprint.


  
Incident 3: compiling a crate already means running its code

  
In 2022, a crate published to crates.io under a name deceptively similar to the popular
  rust_decimal shipped a build script that downloaded and executed a cryptominer the moment anyone
  ran cargo build against it — a widely reported supply-chain incident, since removed from the
  registry. The mechanism generalizes directly to procedural macros: a proc-macro crate is compiled and then
  executed, as arbitrary Rust code, on your machine, during your own build — the exact same trust boundary a
  malicious build.rs crosses, just reached through [lib] proc-macro = true instead.
  "This code type-checks" and "this code is memory-safe" say nothing about what a proc macro's compiled function
  actually does when the compiler calls it. Mitigations that real teams use: cargo vet/cargo
  crev for reviewed-dependency attestation, --locked to pin exact versions in CI, and treating
  a new transitive proc-macro dependency as a genuine, reviewable trust decision rather than a routine
  cargo add.

  
A smaller, ecosystem-wide version of the same "trust and ergonomics" theme resolved happily: before the 2018
  edition, using a macro_rules! macro from another crate required a textual
  #[macro_use] extern crate foo; plus definition-before-use ordering — real, common friction. Edition
  2018 made macros importable via ordinary use crate::foo::my_macro; paths, folding macros into the
  same namespace and import system as every other item.

Ruststd's vec! — simplified from the real source

    
macro_rules! vec {
    // vec![]  — empty, nothing to infer an element type from except context
    () => (
        $crate::vec::Vec::new()
    );

    // vec![0; 5]  — one value repeated N times; needs its OWN arm because it
    // requires $elem: Clone, not "move it N times" the way the next arm works
    ($elem:expr; $n:expr) => (
        $crate::vec::from_elem($elem, $n)
    );

    // vec![1, 2, 3]  — the form §5 hand-traces, trailing comma optional
    ($($x:expr),+ $(,)?) => (
        <[_]>::into_vec(
            $crate::boxed::Box::new([$($x),+])
        )
    );
}

  

  
Every occurrence of $crate above resolves — regardless of which crate calls vec! —
  to the standard library itself, never to whatever crate happens to be calling the macro. Without it, a macro
  that expands to a bare path like vec::Vec::new() would break the instant it was called from a
  crate that doesn't have vec in scope, or (worse) silently resolve to a same-named item the caller
  happens to have shadowed. $crate is hygiene applied to paths, exactly as call-site tagging
  is hygiene applied to local identifiers.


  

    
Rustgreet-derive/src/lib.rs — a real, minimal derive macro

    
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(Greet)]
pub fn derive_greet(input: TokenStream) -> TokenStream {
    // 1. Parse the raw TokenStream into a structured AST node.
    let input = parse_macro_input!(input as DeriveInput);
    let name = input.ident;                 // e.g. `Dog`

    // 2. quote! is a normal function from Rust values to a TokenStream —
    //    it is NOT a macro_rules! template, just #-interpolation syntax.
    let expanded = quote! {
        impl Greet for #name {
            fn greet(&self) {
                println!("Hi, I'm {}", stringify!(#name));
            }
        }
    };

    // 3. Hand the new tokens back. `struct Dog;` itself is untouched —
    //    a derive macro can only ADD, never remove or rewrite (§7, §8).
    expanded.into()
}

  


  

    
Rustan attribute macro, for contrast — #[timed] wraps a whole function

    
#[proc_macro_attribute]
pub fn timed(_attr: TokenStream, item: TokenStream) -> TokenStream {
    let f = parse_macro_input!(item as syn::ItemFn);
    let (name, block, sig, vis) = (&f.sig.ident, &f.block, &f.sig, &f.vis);

    // `_attr` is a REAL second TokenStream — #[timed(unit = "ms")] would
    // put `unit = "ms"` there. Ignored here, but it exists (§7's contract).
    quote! {
        #vis #sig {
            let __start = std::time::Instant::now();
            let __result = (|| #block)();
            println!("{} took {:?}", stringify!(#name), __start.elapsed());
            __result
        }
    }.into()
}

ONE HONEST SIMPLIFICATION

    
Real rustc parses an :expr/:ty capture with its FULL expression/type grammar. This
    engine instead uses the same boundary-finding rule rustc's matcher uses to decide where a capture ends
    (consume tokens up to the next separator or literal, respecting nested delimiters) but does not further
    validate that the captured span is a grammatically complete expression. For well-formed Rust input the result
    is exactly right; a malformed fragment like 1 2 3 would be captured here but rejected by a real
    compiler at a later parsing stage. Everything about pattern matching, repetition counting, and substitution
    itself is the real algorithm.
