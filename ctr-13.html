CONTAINER INTERNALS · CHAPTER 13

Networking: Bridges,
CNI & libnetwork

Chapter 3 gave one container a wire to nowhere — a veth pair with nothing plugged into the other end. This chapter builds the thing that is plugged in: a shared virtual switch, a naming service so containers can find each other, a tunnel format that stretches that switch across hosts, and — because none of it works for an unprivileged user — an entirely separate userspace path that gets a rootless container onto the network without ever touching CAP_NET_ADMIN on the host. DOCKER calls its model the Container Network Model (CNM), built on libnetwork. PODMAN spent its first four years on the CNI plugin-chain model it inherited from Kubernetes' ecosystem, then in 2022 replaced it wholesale with its own netavark + aardvark-dns stack — and the reasons why are a case study in what happens when your problem and your borrowed tool's problem quietly diverge.

ARC 01 · THE PROBLEM

A wire to one place is not a network

Chapter 3 solved a narrower problem than it looked like: it got one isolated network namespace connected to one other namespace, with a veth pair standing in for an Ethernet cable. Real deployments need something categorically bigger — an addressable, multi-tenant domain that dozens or thousands of containers can join and leave, find each other by name inside, reach the internet through, and be reached from outside on published ports — and it has to work identically whether the engine runs as a root daemon or as an unprivileged user's own process.

Unpack "a network" into the concrete requirements a real container platform has to satisfy, because each one eliminates a naive design in turn:

  • Group reachability. Every container in a logical group must reach every other one, without the operator hand-wiring a link for every pair.
  • Service discovery. Containers restart with new IPs constantly; something must let curl http://db:5432 keep working when db's address changes underneath it.
  • Tenant isolation. Two unrelated applications' containers on the same host should not, by default, be able to reach each other's ports at all.
  • Egress and ingress. Containers need a path out to the internet, and operators need a controlled path in — a published port — without exposing the container's whole network stack.
  • Multi-host span. A cluster spans machines; "the same network" has to mean something even when two containers on it are on physically different hosts connected only by an ordinary IP network between them.
  • No host root required. An unprivileged user running Podman rootless has none of the host-level network privileges a root daemon takes for granted, and the design must not quietly assume otherwise.

No single primitive from chapters 2–4 satisfies all six. Namespaces isolate; veth crosses a boundary once. This chapter derives, in order, the pieces that turn "one wire" into "a network": the bridge, the naming layer on top of it, the tunnel that stretches it across hosts, and the rootless escape hatch that avoids it altogether.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Every remaining networking concept you will meet in production — Docker Compose's per-project network, Kubernetes' one-IP-per-pod model, a service mesh's sidecar proxy — is an application built on exactly the layers this chapter derives: a namespace boundary (chapter 3), a shared switch (this chapter's bridge), a naming layer (this chapter's DNS), and, when the tenants aren't privileged, a userspace NAT process instead of a kernel bridge. Chapter 14's pods share one of these Sandboxes among several containers — you cannot judge whether that's a clever reuse or a leaky abstraction until you know, from this chapter, exactly what a Sandbox already provides on its own.

ARC 02 · HISTORICAL CONTEXT

Two networking models, born from two different pressures

Container networking's history is really two parallel stories that later collided: Docker outgrowing its own ad hoc --link flag, and a separate Kubernetes-driven ecosystem (CNI) that Podman borrowed and then outgrew in turn. DEEP CONTEXT · WHY CNI NEVER GREW CONTAINER-NAME DNS

It is tempting to read Podman's 2022 move away from CNI as "CNI was bad." The more precise read: CNI was built to answer Kubernetes' question — "wire up this pod's one interface, then let kube-proxy and CoreDNS handle service discovery at a layer above CNI entirely" — and it answered that question well for nearly a decade. podman run --network mynet has no kube-proxy, no CoreDNS, and no controller loop sitting above it; the CLI itself has to provide name resolution, or nothing will. Podman's own maintainers plugged that gap first with a bolted-on dnsname CNI plugin, then concluded that a plugin ecosystem optimized for Kubernetes' assumptions was the wrong foundation for a single-host CLI tool, and wrote netavark — same lesson chapter 12 taught about daemons: borrowing someone else's control plane works only until your control problem stops matching theirs.

ARC 03 · NAIVE SOLUTION

Attempt #1: wire every container straight to every other one

Derive it the way chapter 3 derived veth: you already know how to connect exactly two network namespaces — a veth pair, one end in each. Scaling from "two containers" to "N containers, fully connected" looks like it just needs more of the same primitive, applied pairwise.

bashnaive_mesh.sh — the strawman, annotated
# Connect every pair of containers directly with its own veth pair.
# For containers c1..cN this is one veth pair per UNORDERED pair (i, j).
for i in $(seq 1 $N); do
  for j in $(seq $((i+1)) $N); do
    ip link add veth-$i-$j type veth peer name veth-$j-$i
    ip link set veth-$i-$j netns c$i
    ip link set veth-$j-$i netns c$j
    # ...then assign a /30 to EACH pair and add an explicit route
    # in c$i for c$j's address via veth-$i-$j, and vice versa.
  done
done

This is not a strawman built to be knocked down cheaply — it is the honest first idea, and for exactly two containers (chapter 3's example) it is the correct answer: no bridge, no shared broadcast domain, no extra moving parts, minimum attack surface. The naive approach's problem only appears once you ask it to scale, and the next section quantifies precisely where it breaks.

ARC 04 · WHY IT FAILS

O(N²) links for O(N) containers — and it still doesn't reach the internet

Count what full-mesh wiring actually costs. Connecting every pair of N containers directly needs one veth pair per unordered pair — that's the handshake-counting formula from combinatorics, and it is exactly as unforgiving here as it is in distributed systems:

THE NUMBERS

Full mesh needs N(N−1)/2 veth pairs. At N=10, that's 45 links. At N=50, 1,225 links. At N=100, 4,950 links — and every one of those links needs its own /30 subnet, its own pair of explicit routes (there is no shared broadcast domain, so nothing can ARP for anything — every peer must be statically routed), and its own lifecycle tracking. Worse: adding one new container costs N−1 new links — joining container #51 to an existing 50-container mesh means 50 new veth pairs, 50 new subnets, 100 new route entries, applied to 50 already-running containers. The cost of joining the group grows with the group's size, forever.

Drag the slider below to feel the curve rather than just read it — it draws every pairwise link for N containers arranged in a circle, and the O(N²) shape becomes visually obvious well before N reaches double digits:

And even a fully wired mesh solves only one of §1's six requirements — group reachability inside the mesh. It has no service discovery (every peer's route is a hardcoded IP), no isolation model beyond "physically unwired" (which doesn't compose — a container in two overlapping meshes leaks both), and critically no path to the internet at all: a mesh of private point-to-point links has no default gateway, because there is no single node designated to translate and forward traffic outward. Every one of these gaps has the same shape of fix: stop connecting containers to each other, and instead connect every container to one shared thing.

ARC 05 · BETTER SOLUTION

The bridge: one shared virtual switch, O(N) links

Linux has had an in-kernel software Ethernet switch since the 2.2 era: the bridge device (brctl historically, ip link add type bridge today). A bridge behaves like a physical switch — it learns which MAC address lives behind which port and forwards frames accordingly — except its "ports" can be veth ends belonging to containers on the very same host. Plug every container's host-side veth end into one bridge instead of into each other, and you get a real broadcast domain: ARP works, one link per container instead of one link per pair, and one designated point (the bridge's own IP) that can be a default gateway with NAT behind it. This is precisely what Docker's docker0 bridge — and every Docker user-defined bridge network created since — has always been.

N containers on one bridge need exactly N veth pairs (one per container, host end into the bridge), one subnet for the whole network, and zero explicit routes — the bridge's own address is every container's single default gateway, and ARP/the bridge's forwarding database handles peer discovery for free. Joining container N+1 costs exactly one new veth pair, regardless of how many containers are already on the network. "Stop connecting peers pairwise, connect everyone to one shared thing" is a completely general networking-topology argument — a star beats a mesh anywhere the same physical constraint applies.

ARC 06 · WHY THAT STILL HURTS

One flat switch is not a platform

A single bridge answers "how do N containers on one host reach each other" — and stops there. Four gaps remain, and each one is the direct motivation for something covered later in this chapter:

  • No name-based discovery on the legacy default bridge. Early Docker's answer was --link — inject the linked container's IP as environment variables and an /etc/hosts entry at start time. It's fragile: the mapping is frozen at container-creation time, breaks the moment the linked container restarts with a new IP, and doesn't compose (you must declare every link explicitly, both directions). The classic default bridge (docker0 itself) never grew real DNS — which is precisely why user-defined bridge networks exist as a separate, newer concept with an embedded DNS server (§8).
  • All-or-nothing tenant isolation. Every container on the default bridge can reach every other container's every port by default (icc=true, inter-container communication, is the historical default) — one flat switch has no concept of "these five containers are one application and those three are a different one." A shared host running unrelated projects on the default bridge is one compromised container away from lateral movement into all the others.
  • It stops at the host's edge. A Linux bridge is host-local kernel state — there is no way for a container on host A to reach a container on host B through docker0 alone. Multi-host clusters need something layered on top of the bridge idea, not instead of it (§7's overlay driver).
  • It is fundamentally a root-only design. Creating a bridge device, attaching a veth to it (ip link set vethX master br0), and writing the NAT/forwarding iptables rules that make it reach the internet are all operations on the host's own root network namespace — and that is exactly the one namespace an unprivileged user's capabilities (chapter 4) do not extend into. A rootless Podman user cannot build this architecture at all, no matter how correctly it's designed. That single sentence is the reason rootless networking (§8d) exists as an entirely separate code path rather than a restricted version of the bridge path.

Broadening the bridge into something that solves naming, isolation, and multi-host span — while keeping a second, entirely bridge-free path for when the caller has no host root at all — is the final architecture both engines converge on, by different implementations of the same ideas.

ARC 07 · FINAL ARCHITECTURE

CNM's pluggable drivers vs. netavark's single declarative binary

Docker's answer, formalized in 2015 when networking was extracted from the engine into libnetwork, is the Container Network Model (CNM): three abstractions — a Sandbox (a container's private network stack — concretely, its network namespace), an Endpoint (a virtual interface, usually a veth end, joining a Sandbox to a Network), and a Network (a group of Endpoints that can reach each other, implemented by a swappable Driver). Everything below is "just" a driver behind that same three-noun model. Podman keeps the same three concepts informally but implements them with netavark (a single Rust binary configured declaratively over stdin) plus aardvark-dns (its per-network name resolver) — replacing the CNI plugin-chain model it used from 2018–2021. Nothing above the "rootless escape hatch" row needs root for a fundamentally different reason than what makes rootless hard: every driver in the CNM/netavark rows assumes it can freely manipulate the host's root network namespace — create bridges, attach veths, write iptables rules, bind raw sockets for VXLAN. The rootless row exists because that assumption is false for an unprivileged caller, and it solves the same problem (get a Sandbox onto a network) with zero host privilege by never touching the host namespace at all. §8 makes that boundary precise down to the exact capability check that blocks it.

ARC 08 · INTERNAL IMPLEMENTATION

DNS, VXLAN, declarative setup, and the CAP_NET_ADMIN wall

Four mechanisms, each load-bearing: (a) how a container resolves another container's name to an IP on a shared bridge, (b) how a bridge is stretched across hosts with VXLAN, (c) why netavark's single declarative call replaced CNI's plugin chain, and (d) the exact privilege boundary that forces rootless networking into userspace.

(a) DNS-based service discovery on a user-defined bridge

Both engines solve "resolve container name → current IP" the same way in spirit: run an authoritative resolver inside the network's own address space that every member container is pointed at, and have the engine's own bookkeeping feed it answers. Docker runs one embedded DNS server per daemon, reachable at the fixed loopback-range address 127.0.0.11:53 inside every container on a user-defined bridge — each container's own /etc/resolv.conf is rewritten at start time to list only that address. A lookup for another container's name or --network-alias is answered directly from the daemon's live network-membership table; anything else is forwarded upstream to whatever resolvers the host itself uses. Critically, this only exists on user-defined networks — the legacy default bridge never received it, which is the real, mechanical reason operators are told to stop using --link/the default bridge and create a named network instead. Podman's netavark stack does the same job with aardvark-dns: a small, per-network authoritative forwarder (also written in Rust) that netavark starts and keeps updated as containers join and leave — architected from day one to run entirely unprivileged, since a rootless user can't share a single privileged daemon process the way dockerd shares its embedded resolver.

(b) Stretching the bridge across hosts: VXLAN

A Linux bridge cannot span two machines by itself — an overlay network fakes it by wrapping each Ethernet frame from the "virtual" network inside a real UDP packet on the underlay network, and unwrapping it at the other end. VXLAN (Virtual Extensible LAN, RFC 7348) is the encapsulation format both Docker swarm overlay networks and most Kubernetes CNI overlay plugins use: an 8-byte VXLAN header (carrying a 24-bit VNI, the virtual network identifier — 16.7 million possible segments, versus the classic 802.1Q VLAN's 12-bit / 4,094-segment ceiling) sits inside an 8-byte UDP header (destination port 4789) inside a normal IP packet between the two hosts' VTEPs (VXLAN Tunnel Endpoints). THE 50-BYTE TAX, EXACTLY

Outer frame = inner frame + 14 (new outer Ethernet header) + 20 (outer IPv4) + 8 (outer UDP) + 8 (VXLAN header) = +50 bytes per packet (IPv6 underlay adds another 20). At the default 1500-byte Ethernet MTU, a container sending full-size 1500-byte frames produces 1550-byte outer frames — over the underlay's own 1500-byte limit, forcing IP fragmentation (slow, and silently dropped by any middlebox that blocks fragments) unless the operator either lowers the container's MTU to 1450 or raises the underlay to jumbo frames. This single arithmetic fact is the most common VXLAN-overlay production surprise, and it recurs identically in Kubernetes CNI overlay plugins that use the same encapsulation.

(c) Declarative netavark vs. the CNI plugin chain

CNI configures one container's network by exec-ing a chain of separate binaries, each doing one narrow job and handing the (possibly modified) result to the next: bridge (create/attach the veth, assign the IP), then portmap (add hostport DNAT rules), then firewall (isolation rules), then tuning (per-interface sysctls) — and, in Podman's CNI era, a bolted-on dnsname plugin for name resolution, since core CNI never shipped one. Every step in that chain is a fresh fork()+exec() of a whole new process, fed its config as JSON on stdin and told which of ADD/DEL/CHECK to perform via environment variables — for one container, that can mean five or six process spawns before the network is usable. netavark collapses the entire chain into one process: it receives one JSON document describing the whole desired network state on stdin, performs every step (interface creation, IP assignment, NAT rules, DNS registration) inside a single invocation, and returns structured JSON describing what it did. Fewer process spawns is not a micro-optimization here — at high container density (a CI runner starting hundreds of short-lived containers per minute, or a large Kubernetes node) the CNI chain's per-container process-spawn tax measurably dominates network setup latency; it's the direct, mechanical reason netavark benchmarks faster at scale, not a marketing claim.

(d) Why rootless containers cannot get a real bridge — and what replaces it

Chapter 4 showed that an unprivileged user's unshare(CLONE_NEWUSER|CLONE_NEWNET) grants a full capability set, including CAP_NET_ADMIN — but only with respect to the namespaces that call owns. The kernel's capability check, ns_capable(), walks up the user-namespace hierarchy from the object being operated on and asks "does the caller hold this capability in the user namespace that owns this object?" A freshly created network namespace is owned by the calling (unprivileged) user's own new user namespace — so the caller has full CAP_NET_ADMIN inside it: bringing up loopback, assigning IPs, adding routes, all unrestricted. But attaching a veth to the host's bridge means writing into the host's root-owned network namespace — an object owned by the initial user namespace — and ns_capable() correctly reports that the caller holds no capability there at all. No mapping, no configuration flag, and no version bump changes this: it is the same boundary that makes rootless containers safe in the first place, working exactly as designed.

Both userspace replacements solve "get packets in and out of my own network namespace" without ever touching the host's root namespace — they just do it at very different levels of the stack:

  • slirp4netns (2018) creates a tun device inside the container's own namespace (fully unprivileged — the user owns that namespace) and runs a complete userspace TCP/IP + NAT stack (libslirp, descended from the original 1995 SLIRP project, built to fake a network connection over a dumb dial-up shell account) that reads every outgoing packet off the tun device, reimplements the protocol logic in userspace, and re-emits translated packets on an ordinary host socket. Every packet crosses the user/kernel boundary multiple times with a full copy each time, and TCP's state machine itself is partially re-run in userspace rather than left to the kernel's already-optimized implementation — measured throughput commonly lands well under 1 Gbps even on hardware capable of line-rate 10 GbE, and small-packet workloads suffer disproportionately from the per-packet syscall tax.
  • pasta (passt project, Red Hat, first shipped as Podman's newer default around the 4.4/5.0 era) takes a narrower, faster approach: instead of reimplementing TCP/IP in userspace, it translates at layer 4 between the namespace's tap device and ordinary host sockets, handing the actual byte-shuffling to splice()-style zero-copy kernel paths wherever available and letting the host kernel's own TCP stack do the real protocol work on both sides of the translation. It also observes which ports the guest binds and forwards them automatically, without slirp4netns's more manual port-mapping syntax. Net effect: throughput close to a native bridge for TCP, materially lower latency and CPU per byte than slirp4netns, while remaining exactly as unprivileged.

Read the last four rows as the chapter's real thesis: Docker's CNM and Podman's netavark solve the same problem — pluggable network drivers behind a Sandbox/Endpoint/Network model — with different control-plane software, while both engines share the identical answer to the rootless problem underneath (slirp4netns/pasta are engine-agnostic userspace tools, not Podman-specific or Docker-specific inventions).

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

The real cost curve, and the security corollary that goes with each mode

Every mode's performance profile has a matching security story, and they're not independent — the modes that skip the most machinery for speed are usually the ones that skip an isolation boundary along with it:

  • Bridge + NAT costs a small, roughly constant per-packet conntrack/NAT lookup — but that same NAT layer is an implicit firewall: nothing on the internet can reach a container unless a port is explicitly published (a DNAT rule exists for it). Security and performance point the same direction here.
  • Host mode is the fastest possible path (no extra namespace hop, no NAT) precisely because it is the host's own network stack — meaning a compromised container's process can bind, sniff, and interact with every other process's sockets on the host as if it weren't containerized at all.
  • Macvlan is nearly as fast as host mode for a different reason — frames go straight to the physical NIC with no bridge or NAT hop — but that speed comes from bypassing the host's own network stack and firewall entirely. A famous, genuinely confusing side effect: in macvlan's default (bridge sub-mode), the physical NIC usually can't deliver frames addressed to a macvlan container back to the host's own IP stack, so the host itself often cannot reach containers it's running — a routing quirk that has cost countless engineers a debugging session before they learn to add a macvlan shim interface on the host side specifically to route around it.
  • Overlay/VXLAN pays the +50-byte encapsulation tax on every packet (§8b) plus real CPU for encap/decap on every hop — and, unencrypted, every container's traffic between hosts is plaintext on the underlay network; Docker swarm overlay networks support IPsec ESP encryption of the VXLAN tunnel specifically because "it's just tunneled Ethernet" is also true from an eavesdropper's perspective.
  • slirp4netns vs. pasta is the sharpest performance/security pairing in the chapter: slirp4netns's slower path is a full userspace reimplementation of IP/TCP parsing — more code, in a less-audited codebase, parsing untrusted bytes, than pasta's much thinner translation layer that leaves the actual protocol work to the kernel. §11's CVE is a direct consequence of that extra parsing surface.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents that map straight onto this chapter's mechanisms

Incident 1: docker0's default subnet collides with the corporate VPN

Docker's default bridge, and each subsequent auto-created network, historically claims addresses out of the 172.17.0.0/16–172.30.0.0/16 range. A huge fraction of enterprise VPN and internal RFC 1918 address plans also live inside 172.16.0.0/12. The failure mode is silent and confusing: once a host has a bridge attached to (say) 172.18.0.0/16, the kernel's routing table now has a locally attached, higher-priority route for that whole prefix — any packet the host tries to send to a real VPN-side resource inside that same prefix is delivered straight to the local bridge instead of ever reaching the VPN tunnel, with no error, just a connection that mysteriously times out or hits the wrong host. Root cause: two independent address plans (Docker's IPAM defaults and the corporate VPN's subnet) drawing from the same private range with no coordination. Fix: configure the daemon's bip/default-address-pools (or netavark's equivalent subnet config) to an address range known not to overlap with anything the host also needs to reach — a one-line config change that an entire generation of "Docker broke my VPN" support threads exists because operators didn't know to make.

Incident 2: CVE-2020-13401 — spoofed router advertisements on macvlan/ipvlan networks

Moby's (Docker's underlying project) macvlan and ipvlan drivers place every container directly on the physical L2 segment with no bridge and, critically, none of a real managed switch's protections — no RA-guard, no DHCP snooping. A malicious container on the same macvlan network could send a crafted IPv6 Router Advertisement that other containers on that network would accept at face value, silently redirecting their default route through the attacker's container and enabling a man-in-the-middle position. Root cause: exactly the tradeoff §10 names explicitly — macvlan's speed comes from skipping the host's own network stack and the protections a bridge (or a real switch) would otherwise enforce; nothing was filtering unsolicited router advertisements between "peer" containers that macvlan treats as equally trusted L2 neighbors. It is not a bug in the strict sense so much as an architectural blind spot the driver doesn't warn users about — a live instance of "no vendor boosterism": macvlan's own tradeoff table entry in §9 is the correct mental model for deciding whether this risk is acceptable for a given deployment.

Incident 3: CVE-2019-14378 — a heap overflow in libslirp's fragment reassembly

libslirp, the userspace TCP/IP implementation both QEMU's usermode networking and slirp4netns are built on, had a heap-based buffer overflow in its IP fragment reassembly code (ip_reass()): a peer sending specially crafted, overlapping IP fragments could corrupt heap memory inside the slirp process, with a credible path to remote code execution in that unprivileged helper. Root cause: exactly the extra attack surface §10 flagged — a full userspace reimplementation of IP parsing is C code parsing untrusted, adversary-controlled bytes, with none of the decades of kernel fuzzing and hardening that the real in-kernel IP stack has absorbed. The blast radius was bounded by design (a compromised slirp4netns process runs as the unprivileged calling user, not root, and only owns that one container's network path) — but it is a concrete, shipped example of the class of bug that only exists because rootless networking has to reimplement protocol logic in userspace at all, and it is precisely the class of bug pasta's kernel-delegating design was built to avoid by not reimplementing that logic in the first place.

First, the shape of the driver contract every CNM driver — including bridge, overlay, and macvlan — implements, simplified but faithful to libnetwork's real structure:

Golibnetwork/driverapi — the interface every driver satisfies
type Driver interface {
    // Allocate whatever the driver needs for a new logical network:
    // e.g. bridge driver creates the Linux bridge device + subnet;
    // overlay driver registers the VNI with the gossip control plane.
    CreateNetwork(nid string, options map[string]interface{}) error

    // Allocate one Endpoint (an interface) within that network, but
    // do NOT yet move it into the container's Sandbox — see Join().
    CreateEndpoint(nid, eid string, ifInfo InterfaceInfo, options map[string]interface{}) error

    // Wire the already-created Endpoint into a specific Sandbox
    // (network namespace) — for bridge, this is the "move veth into
    // netns, assign IP, add default route" sequence from §5's deck.
    Join(nid, eid string, sboxKey string, jinfo JoinInfo, options map[string]interface{}) error

    Leave(nid, eid string) error
    DeleteEndpoint(nid, eid string) error
    DeleteNetwork(nid string) error
}

Second, the real shape of the iptables rules a user-defined bridge network's NAT and port publishing come from — this is what "Docker writes firewall rules for you" concretely means:

bashrules the bridge driver installs for `docker run -p 8080:80` on network mynet (172.20.0.0/16)
# Outbound: hide every container behind the host's own address (NAT/MASQUERADE)
iptables -t nat -A POSTROUTING -s 172.20.0.0/16 ! -o br-mynet -j MASQUERADE

# Inbound: host:8080 -> container:80 (this line is WHY the published port works)
iptables -t nat -A DOCKER -p tcp --dport 8080 -j DNAT --to-destination 172.20.0.5:80

# Without an explicit -p, NOTHING routes inbound traffic to the container —
# the NAT layer IS the implicit firewall §10 described.
iptables -A DOCKER-ISOLATION-STAGE-2 -o br-mynet -j DROP   # cross-network isolation

fn setup(config: NetavarkConfig) -> Result<NetworkStatusReport> {
    let ns = open_netns(config.netns_path)?;
    create_veth_pair_and_move_into(&ns, &config)?;      // was: CNI "bridge" plugin
    assign_ip_and_route(&ns, &config)?;
    write_nat_and_portmap_rules(&config)?;         // was: CNI "portmap" + "firewall" plugins

WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. Collapse a chain into one atomic call whenever every step in the chain always has to run together anyway. CNI's chain model earns its complexity when different steps are genuinely optional and independently composable (Kubernetes really does mix and match bridge + bandwidth-shaping + custom firewall plugins across different clusters); netavark's insight was that a single CLI tool's "give this container a network" almost always needs the same fixed sequence, so paying a process-spawn per step buys flexibility nobody was using. 2. Design the privileged and unprivileged path to share as much code as possible, rather than forking the codebase. netavark and aardvark-dns run unmodified under both rootful and rootless Podman; the fork only happens one layer down, in whether the network setup targets a real bridge or hands off to slirp4netns/pasta — keeping the DNS and declarative-config layer identical regardless of privilege was a deliberate design choice, not an accident of the rewrite.
