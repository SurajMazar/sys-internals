CONTAINER INTERNALS · CHAPTER 04

User Namespaces:
Rootless Containers

Every container you have run since chapter 2 shares one uncomfortable fact with every other process on the host: unless something intervenes, UID 0 inside the container is UID 0 on the host. The PID, mount, and network namespaces from chapters 2–3 hide the host's view of processes, filesystems, and interfaces — but they do nothing to the identity plane. This chapter derives the one namespace that actually changes who you are: CLONE_NEWUSER, the file format that implements it byte for byte (/proc/<pid>/uid_map), and why Podman made it the default while Docker left it opt-in.

ARC 01 · THE PROBLEM

"Isolated" is not the same as "not root"

Chapters 2 and 3 gave a process its own PID tree, its own hostname, its own mount table, its own network stack. None of that touches identity. The kernel object that decides whether a syscall is allowed — struct cred, attached to every task_struct — carries a UID, a GID, a set of supplementary groups, and a capability set. Namespaces from the previous two chapters never touch struct cred at all. A process born inside a fresh PID+mount+UTS+network namespace bundle, running as UID 0, is exactly as privileged on the host as a UID-0 process running with no namespaces whatsoever — it simply can't see most of what its privilege would otherwise reach, because the other namespaces have hidden the view.

That distinction is not academic. "Can't see it" and "can't touch it" collapse the instant an attacker finds a bug that steps outside the view — a bind-mount escape, a /proc/self/exe race (CVE-2019-5736, chapter 15), a symlink traversal in an image extractor. The namespace hid the target; it never revoked the permission. If the escaping process is still UID 0 in the initial user namespace — the one the host kernel itself runs in — the escape is a full host compromise. If it is not, the same bug lands the attacker as an ordinary, unprivileged, disposable UID.

  • Rootful-by-default (classic Docker): the daemon runs as UID 0, and unless you opt in to userns-remap, every container's UID 0 is the host's UID 0. A container escape is a root shell on the node.
  • No daemon, but still root (early rootless attempts): even a daemonless fork-exec model doesn't help if the fork-exec is itself invoked by root and no identity remapping happens.
  • The actual fix has nothing to do with daemons. It is a fourth namespace type — CLONE_NEWUSER — that intercepts UID/GID lookups before every other permission check, and it can be created by a completely unprivileged, ordinary user.
THE INVARIANT THIS CHAPTER ESTABLISHES

A user namespace does not add security controls — it relabels identity. Once labeled, every other security mechanism in the kernel (capability checks, DAC permission bits, LSM hooks) evaluates against the mapped id, not the number the process believes it has. "Root inside" becomes a claim the container makes about itself that the host does not have to believe — because the host never stored that claim as true in the first place.

ARC 02 · HISTORICAL CONTEXT

A decade from patch to default

User namespaces are the slowest-cooked primitive in this course. CLONE_NEWNS (mount) and CLONE_NEWUTS existed years before anyone could safely let an unprivileged user create a user namespace — because doing so unlocks capabilities inside it, and every capability check in the kernel had to be individually re-audited to ask "capable relative to which namespace?" DEEP CONTEXT · WHY IT TOOK SO LONG

Every one of the ~300 places in the kernel that calls capable(CAP_X) had to be reconsidered as ns_capable(user_ns, CAP_X) — "does the caller have this capability with respect to the user namespace that owns the resource being touched?" Get even one of those checks wrong and an unprivileged user can create a user namespace, gain a full capability set inside it, and use a missed check to reach out and touch real host state. This is precisely the shape of the CVEs in §11 — the feature's history and its incident history are the same story told twice.

ARC 03 · NAIVE SOLUTION

Attempt #1: just don't run as root

The obvious, cheap fix predates user namespaces entirely and needs no kernel feature at all: put a USER line in the Dockerfile, or pass --user 1000:1000 at run time, so the process inside the container never has UID 0 to begin with.

Dockerfilethe strawman — non-root by convention, not by mapping
FROM alpine:3.20
RUN adduser -D -u 1000 appuser
USER appuser                  # no more UID 0 inside the container...
CMD ["./server"]           # ...but there is only ONE UID namespace in play

Run it and inspect from both sides — no user namespace has been created, so there is exactly one UID space in the whole system, shared by host and container alike:

One UID space, two vantage pointsSTATIC — NO REMAPPING
INSIDE THE CONTAINER — id
uid=1000(appuser) gid=1000(appuser)"I am appuser, 1000."
ON THE HOST — ps -eo pid,uid,cmd
PID 41822 UID 1000 ./serverthe SAME 1000 — no translation happened

This looks safe, and for one specific threat — "don't let the app's own bugs run arbitrary code as root" — it genuinely is a real improvement over running as UID 0. But notice what it did not do: there is no translation layer. The number 1000 means the exact same principal on both sides of the namespace boundary. §4 shows precisely what that leaves open.

ARC 04 · WHY IT FAILS

Identity mapping is not identity isolation

--user 1000 without a user namespace fixes exactly one thing — the container process no longer starts with UID 0 — and leaves two much larger problems completely untouched:

  • Host UID collisions are real, not cosmetic. If the host also has a real account at UID 1000 (a common default for a machine's first login user, or another tenant's service account), the container process and that host account are the same principal as far as the kernel's DAC checks are concerned. A container that mounts a host path with weak permissions, or a bind-mounted volume owned by host UID 1000, is fully readable/writable by "appuser" — because it isn't actually a different user.
  • It solves nothing about the daemon or the escape path. If the runtime that launched the container (classic dockerd) runs as host root, and the container process finds a kernel bug that lets it manipulate the runtime's state (a shared mount namespace leak, a symlink race during image extraction, a /proc/pid/root traversal), the attacker was never actually confined by the container's own UID — they attack the privileged thing standing next to them, not through their own credentials at all.
  • Capabilities are untouched. By default, dropping to a non-root UID also drops most capabilities (chapter 7) — but any capability explicitly re-added with --cap-add, or any setuid binary baked into the image, still operates against real host identities, because there is only one identity space. A setuid-root helper inside the image is still setuid-host-root.
THE NUMBER THAT MATTERS

Of the container-escape CVEs catalogued in chapter 15, the overwhelming majority assume the escaping process can reach host UID 0 — because in the default rootful configuration, that's exactly what a container's root process already is. Running as a non-root UID inside the container shrinks the blast radius of the app's own bugs, but it does nothing about the runtime's privilege or about any container that legitimately needs UID 0 semantics inside (installing packages, binding to files it must own, running its own internal su). What's missing is a way to let a process believe — correctly, for everything it can observe — that it is UID 0, while the host simultaneously and truthfully believes it is some unprivileged UID nobody else is using. That requires translation, not convention.

ARC 05 · BETTER SOLUTION

A namespace for identity: CLONE_NEWUSER

The kernel's answer is a namespace exactly like the others in shape, but applied to the credential struct instead of a resource table: unshare(CLONE_NEWUSER) (or the equivalent clone() flag) creates a new UID/GID translation domain. Inside it, a process can be told it is UID 0 — and every syscall that asks "what is my UID" will answer 0 — while a translation table, visible from the parent namespace as two small pseudo-files, defines what that 0 actually corresponds to outside.

THE FILE FORMAT, PRECISELY

/proc/<pid>/uid_map and its GID twin hold up to five lines, each exactly three whitespace-separated unsigned integers: ID-INSIDE ID-OUTSIDE LENGTH. 0 100000 65536 reads as "the namespace's UIDs 0 through 65535 map to host UIDs 100000 through 165535." The kernel enforces the five-extent cap (UID_GID_MAP_MAX_EXTENTS) so that every UID lookup — which happens on nearly every permission check in the system — stays a short, cache-friendly linear scan rather than an open-ended one. §8 writes and reads this file for real.

ARC 06 · WHY THAT STILL COSTS

The bill: what rootless containers give up

User namespaces are not a free win. Three classes of real, operational limitation follow directly from "root inside" being an unprivileged UID outside — each one is the honest price of the isolation, not a bug:

  • You need delegated ID ranges before any of this works. An unprivileged user cannot invent a mapping to host UIDs it doesn't own — that would let any user claim to be any other user. The host administrator must first delegate a range in /etc/subuid//etc/subgid (chapter-scope detail in §8); without an entry there, newuidmap/newgidmap refuse outright.
  • Privileged ports need an explicit grant. CAP_NET_BIND_SERVICE is scoped to the user namespace it was granted in — a mapped-root process has it inside, but the kernel's port-binding check additionally consults net.ipv4.ip_unprivileged_port_start in the sysctl namespace it inherited, which on stock distros is 1024. A rootless container binding port 80 fails with EACCES unless the host administrator lowers that threshold or a specific port-forward is punched from a privileged proxy.
  • Some filesystem and device operations are still out of reach. Native OverlayFS mounts inside an unprivileged user namespace only became possible in Linux 5.11 (2021); on older kernels rootless engines fall back to fuse-overlayfs, which is slower because every filesystem operation makes a userspace round trip through FUSE instead of running natively in the kernel. Raw block-device access, most kernel module loading, and changing ownership to a UID/GID that has no entry in the map at all are unavailable no matter the kernel version — chown() to an unmapped id returns EINVAL, by design (§8).

THE INDUSTRY'S ANSWER — AND ITS OWN TAX

Reverse proxies (nginx, HAProxy, cloud load balancers) already sit in front of most containerized services and already own port 80/443 as a privileged (or capability-holding) process — so this "limitation" rarely reaches application teams in practice. Where it does bite is single-binary tools that assume they can bind() low ports directly; the fix is either setcap cap_net_bind_service+ep on the specific binary (works even for a mapped, unprivileged UID, because the capability is evaluated inside the container's own user namespace) or simply running the service on a high port and mapping externally. Neither is free — both are one more line of operational config that a rootful daemon never asked for.

DOCKER'S userns-remap VS PODMAN'S ROOTLESS — THE SAME PRIMITIVE, OPPOSITE DEFAULTS

DOCKER ships CLONE_NEWUSER support as userns-remap: an opt-in daemon-wide setting where every container gets the same single mapping, sourced from one dockremap entry in /etc/subuid. The daemon itself still runs as host root — the remap only affects the containers it launches. PODMAN has no daemon to begin with (chapter 12): it fork-execs directly as the invoking user, so rootless is the natural default rather than a mode bolted onto a root process — each user gets their own delegated range from their own /etc/subuid line, and containers from different users are unprivileged relative to each other, not just relative to root.

ARC 08 · INTERNAL IMPLEMENTATION

Reading and writing the real files

Three real artifacts, in the order a rootless container actually touches them: (a) the subuid/subgid delegation database, (b) the exact uid_map/gid_map write sequence and its permission rules, (c) what a mapped-root process can and cannot then do.

(a) The delegation database: /etc/subuid and /etc/subgid

Before any unprivileged user can map anything, the host administrator (or the distro's useradd defaults) must grant them a range they're allowed to claim. Format: username:start:count, one grant per line, non-overlapping between users by convention:

text/etc/subuid — delegated ranges (subgid is byte-identical in format)
alice:100000:65536
bob:165536:65536
appuser:231072:65536

This is the entire trust boundary. newuidmap and newgidmap — the two setuid-root helpers that perform the actual privileged write — refuse to map any ID outside the calling user's own granted range. Everything downstream of this file is unprivileged by construction.

(b) The write sequence, and the rules the kernel enforces

Step through the exact call sequence Podman's fork-exec model runs when alice (host UID 1000, granted 100000:65536) starts a rootless container:

unshare → newuidmap → setresuid(0)STEP-BY-STEP

Three hard rules the kernel enforces on every write to uid_map/gid_map, verbatim from user_namespaces(7) and kernel/user_namespace.c:

  • Write-once. Once a map has been written, it is immutable for the lifetime of that namespace — a second write returns EPERM. This closes a whole class of "widen my mapping after the fact" attacks.
  • setgroups must be set to deny before an unprivileged process may write gid_map. This was a deliberate hardening added in kernel 3.19 (2015) after a real vulnerability class: an unprivileged process that could keep setgroups enabled and control its own GID map could make itself appear to belong to a privileged supplementary group (e.g. one that owns a sensitive device file) it was never actually a member of. Writing "deny" first closes the hole; only then may gid_map be written by a non-root writer.
  • The writer must own the range, or be privileged. A process can write its own single-extent identity map (getuid() getuid() 1) with no help. Anything wider requires either real CAP_SETUID/CAP_SETGID in the parent namespace, or going through newuidmap/newgidmap, which check /etc/subuid//etc/subgid on the caller's behalf.

(c) What a mapped-root process can and cannot then do

Inside the namespace, capable() checks report the full set — the process genuinely holds CAP_SYS_ADMIN, CAP_CHOWN, CAP_NET_BIND_SERVICE, all of it, with respect to that namespace. Whether an operation actually succeeds depends on whether the kernel's per-syscall check also asks "and does this affect a resource owned by the initial namespace?"

OPERATIONRESULT AS MAPPED ROOTWHY
mount("tmpfs", ...)succeedstmpfs, proc, sysfs, and (5.11+) overlay are flagged FS_USERNS_MOUNT — their mount handlers check capable against the namespace that owns the mount point, which the caller controls.
mount("ext4", /dev/sdb1, ...)EPERMBlock-device-backed filesystems require real CAP_SYS_ADMIN in the initial user namespace — the device itself is a host resource no mapping can grant access to.
chown(f, 5000, -1) where 5000 has no map entryEINVALThe kernel cannot represent an id it cannot translate back out of the namespace; per user_namespaces(7) this returns EINVAL rather than silently doing nothing.

load a kernel moduleEPERMCAP_SYS_MODULE is deliberately excluded from what an unprivileged user namespace can ever meaningfully exercise — the kernel image is global state with no per-namespace concept at all.

HARDWARE/KERNEL COROLLARY: nested namespaces and depth

User namespaces nest — a process inside one can create another, mapping its own (already mapped) ids further. The kernel bounds nesting at 32 levels (MAX_USER_NS_LEVELde facto, enforced via user_ns->level) purely to keep the permission-check walk (each check may have to walk up the chain asking "capable in an ancestor namespace?") bounded and fast. Rootless-in-rootless — running Podman inside a rootless Podman container, a real pattern for CI runners — exercises exactly this nesting.

ARC 09 · TRADEOFFS

Docker vs Podman, layer by layer

User namespaces are where the two engines' philosophies diverge most sharply, because one made rootless the exception and the other made it the rule:

DIMENSIONDOCKERPODMAN
Default postureRootful; userns-remap is opt-in daemon configRootless by default since 1.0 (2019); --privileged/root mode is the opt-in
Mapping granularityOne mapping for the whole daemon (all containers share the dockremap range) unless per-container remap is separately configuredOne mapping per invoking user, sourced from that user's own /etc/subuid line — naturally multi-tenant
Privileged component still requireddockerd itself runs as host root regardless of container-side remapOnly newuidmap/newgidmap (small, audited, setuid-root helpers) — no long-lived root daemon at all
Identity-preserving bind mountsRequires manual UID arithmetic against the daemon's fixed offset--userns=keep-id — a three-extent map that keeps the invoking user's own UID identical inside and out, so bind-mounted files "just work" without chown gymnastics (§8's slider demonstrates the exact extents)
Where they agreeBoth consume the identical kernel primitive — the same CLONE_NEWUSER, the same uid_map format, the same newuidmap helper and /etc/subuid convention. Neither engine invented anything here; both are clients of one kernel feature.

Read the divergence as strategic, not technical: Docker's architecture (chapter 12) puts a privileged daemon in the critical path regardless, so full rootless operation buys it comparatively less and was retrofitted; Podman's daemonless design has no privileged process to protect in the first place, so rootless was free to make the default and became the headline feature that justified the project's existence.

ARC 10 · PERFORMANCE & SECURITY

What rootless costs in milliseconds, and buys in blast radius

Performance cost is concentrated almost entirely in the storage layer, not in the identity mapping itself — a uid_map lookup is a five-entry linear scan, effectively free. The real cost is which overlay implementation a given kernel version forces a rootless container into:

Container start latency by modeMODEL, TUNED TO PUBLISHED BENCHMARKS
10
■ rootful (native overlay2) ■ rootless, kernel ≥5.11 (native overlay) ■ rootless, kernel <5.11 (fuse-overlayfs)

Security is the mirror image — a fixed, small identity-mapping cost buys a large reduction in what any single escape can reach:

  • Attack surface, quantified. A rootful container escape reaching the runtime's process has host root available immediately. The identical escape against a rootless, mapped container lands the attacker as an ordinary UID with no /etc/shadow access, no ability to read other users' files, and no path to any other container's mapped range (different users → non-overlapping subuid grants).
  • No privileged daemon to pivot through (Podman). Because there is no long-lived root process at all, compromising the CLI invocation compromises only that invocation's own unprivileged process tree — there's no always-on, high-value target analogous to dockerd sitting on the same host.
  • What rootless does not fix. A kernel bug reachable without elevated privilege — one that any unprivileged process (containerized or not) could trigger — is not mitigated by user namespaces at all. This is why some distributions restrict unprivileged user-namespace creation itself (§11): the namespace is not a sandbox against kernel bugs, it's a sandbox against identity abuse, and unprivileged access to CLONE_NEWUSER is itself additional attack surface for kernel exploitation.
ARC 11 · REAL-WORLD INCIDENTS

Where the theory met production

CVE-2013-1858 / the setgroups hole that shaped kernel 3.19

Before the mandatory setgroups=deny-before-gid_map rule (§8b) existed, an unprivileged process that created a user namespace and controlled its own GID map, while setgroups remained enabled, could cause itself to appear to hold membership in an arbitrary supplementary group from the parent namespace's perspective for certain permission checks — enough to reach group-owned device files it had no business touching. The kernel fix (3.19, 2015) is exactly the ordering rule this chapter's implementation section now treats as unremarkable: it took a real vulnerability, and a coordinated fix across every distro shipping user namespaces, to make it a rule.

Ubuntu/Debian's default-restrictive stance on unprivileged user namespaces

Since 2013, Ubuntu has shipped an AppArmor-enforced restriction narrowing which unprivileged processes may call unshare(CLONE_NEWUSER) at all (formalized as kernel.apparmor_restrict_unprivileged_userns in newer releases; Debian carries an analogous kernel.unprivileged_userns_clone sysctl, off by default on some images). The rationale is exactly §10's closing point: user namespaces measurably expand the kernel's unprivileged attack surface, because they hand ordinary users the ability to exercise capability-gated code paths (network stack internals, filesystem mount handlers) that would otherwise require real root — and several kernel privilege-escalation CVEs (including issues in legacy filesystem parsing and cgroup handling) were reachable specifically because they could be triggered from inside an unprivileged user namespace. This creates a genuine, unglamorous operational tension: rootless Podman needs exactly the syscall these distros restrict by default, so rootless container deployments on hardened Ubuntu/Debian hosts require deliberately re-enabling it — a decision that should be made consciously, not by copy-pasting a "fix" from a forum post.

CVE-2022-0185 (a kernel heap overflow reachable from an unprivileged user namespace)

A heap buffer overflow in the kernel's legacy filesystem-context parameter parser (legacy_parse_param) was exploitable by any process that could mount a filesystem — including, critically, from inside an unprivileged user namespace with a mount namespace, exactly the combination a rootless container creates. Distributions that had disabled unprivileged user namespace creation were not exploitable via this specific path; distributions that left it enabled (the common case for developer workstations and many container-hosting VMs) were. It is the concrete case study behind §10's caveat: the feature that enables rootless containers is, simultaneously, exposed kernel surface that a hardened host might reasonably choose to gate.

The canonical parent/child dance — this is the shape of the real sample code in man 7 user_namespaces, adapted to show the exact write sequence:

Cuserns_child_exec() — the pattern every rootless runtime follows
static int
child_fn(void *arg)
{
    /* We exist inside the new user (+ mount, +pid, ...) namespace
     * already, courtesy of the clone() flags below — but uid_map
     * is NOT written yet. Until it is, we appear as the overflow
     * uid (65534, "nobody") to anything that asks.              */
    close(pipe_fd[1]);
    char buf;
    read(pipe_fd[0], &buf, 1);      /* block until parent has mapped us */

    execve("/bin/sh", argv, envp); /* now getuid() == 0, and it's REAL   */
}

int
main(int argc, char *argv[])
{
    pipe(pipe_fd);
    pid = clone(child_fn, stack_top,
                 CLONE_NEWUSER | CLONE_NEWNS | CLONE_NEWPID | SIGCHLD, NULL);

    /* Parent writes the maps from OUTSIDE — this is the only
     * legal way to grant a range wider than "myself, alone".    */
    snprintf(path, sizeof(path), "/proc/%d/setgroups", pid);
    write_file(path, "deny");              /* MUST precede gid_map write   */

    snprintf(path, sizeof(path), "/proc/%d/uid_map", pid);
    write_file(path, "0 100000 65536");   /* via newuidmap if not our own uid */

    snprintf(path, sizeof(path), "/proc/%d/gid_map", pid);
    write_file(path, "0 100000 65536");   /* via newgidmap                */

    close(pipe_fd[1]);   /* release the child — maps are now final */
    waitpid(pid, NULL, 0);
}

The kernel side that makes write-once and the extent cap real, simplified from kernel/user_namespace.c:

Cuser_namespace.c — map_write(), the validation path every write() to uid_map runs
static ssize_t
map_write(struct file *file, const char __user *buf, size_t count, struct uid_gid_map *map)
{
    /* Rule 1: WRITE ONCE. */
    if (map->nr_extents != 0)
        return -EPERM;

    /* Rule 2: gid_map requires setgroups=deny first, unless caller
     * has real CAP_SETGID in the parent namespace.               */
    if (map == &ns->gid_map && !ns->flags & USERNS_SETGROUPS_ALLOWED)
        if (!ns->proc_setgroups_denied)
            return -EPERM;

    /* Rule 3: at most 5 extents — keeps every downstream from_kuid()/
     * make_kuid() lookup a short, bounded linear scan.            */
    if (nr_extents > UID_GID_MAP_MAX_EXTENTS)
        return -EINVAL;

    /* Rule 4: the writer must own the outside range — verified via
     * CAP_SETUID/CAP_SETGID in the parent ns, which is exactly what
     * newuidmap/newgidmap hold as setuid-root, after checking
     * /etc/subuid on the real caller's behalf.                    */
    if (!privileged_wrt_userns(ns->parent, extents))
        return -EPERM;

    memcpy(map->extent, extents, sizeof(extents));
    map->nr_extents = nr_extents;   /* now permanent for this ns's lifetime */
    return count;
}
WHY IT WAS BUILT THIS WAY

1. Validation lives in the kernel, not in a helper. Even though newuidmap is the usual entry point, the actual safety rules (write-once, setgroups ordering, extent cap, range ownership) are enforced by the kernel itself on every write — a buggy or malicious userspace helper cannot bypass them. 2. The privileged surface is minimized to two tiny setuid binaries whose entire job is "check one file, then make one syscall" — dramatically smaller than a privileged daemon, and independently auditable. 3. The five-extent cap trades expressiveness for a guarantee: every UID lookup in the entire system — which happens on nearly every permission check — stays O(5) instead of risking an attacker-controlled, unbounded scan on a hot path.
