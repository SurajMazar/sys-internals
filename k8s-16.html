ARC 01 · THE PROBLEM

The control plane you trust is also the thing that can betray you

Every previous chapter assumed the machinery worked: the API server validates and stores what you send it, the scheduler places Pods correctly, kube-proxy programs the exact rules it claims to, etcd never loses a committed write, CoreDNS answers every query. That assumption is necessary to teach mechanism — you cannot reason about a reconciliation loop while also doubting whether Get() returns the truth. But it is also false often enough, and expensively enough, that "the control plane has bugs and operational cliffs of its own" deserves its own chapter with the same rigor as any other.

This chapter studies five real, dated, mechanically-understood failures, chosen because together they cover the whole failure taxonomy a production operator meets:

  • A privilege-escalation vulnerability (CVE-2018-1002105) — the control plane's own request-proxying code confused "the backend didn't upgrade this connection" with "the backend did," and a low-privileged, fully authenticated user turned that confusion into an unauthenticated tunnel to any backend the API server could reach.
  • A denial-of-service vulnerability (CVE-2019-11253) — proof that authorization is not the same guarantee as availability. A user allowed to submit a five-line YAML manifest could crash every API server replica in the cluster, because the danger was in how the bytes expand during parsing, not in their size on the wire.
  • A network-isolation vulnerability (CVE-2020-8558) — proof that "bound to 127.0.0.1" is a promise the kernel keeps only if every layer above it agrees, and that kube-proxy's own plumbing for a legitimate feature (NodePort hairpin traffic) had reopened a path the kernel would otherwise have closed.
  • etcd disk exhaustion — not a CVE at all, but a slow-motion, entirely self-inflicted outage pattern: an MVCC store that never forgets a revision unless told to, running without a maintenance schedule, until the backend file's growth collides with a hard quota and every write in the cluster stops.
  • CoreDNS meltdown under load — a kernel resource (the connection-tracking table) shared by every Service in the cluster, quietly exhausted by DNS traffic's own volume and amplification, producing the specific, maddening symptom of five-second lookups instead of clean failures.

None of these are exotic. Two are CVEs with public CVSS scores you can look up right now; the other three are patterns experienced operators recognize on sight. The throughline, and the reason this chapter earns a place next to the derivation chapters rather than being an appendix of trivia, is that each failure is explainable by the exact mechanisms chapters 6–15 already gave you — the aggregation layer's proxying, the API server's decode path, kube-proxy's iptables programming, etcd's revision model, and the Service/DNS/conntrack stack. You are not learning new components. You are learning where the components you already understand have edges.

THE PATTERN TO WATCH FOR

Read the five incidents side by side and a single sentence covers all of them: a request that is correctly authenticated, and sometimes even correctly authorized, still did something unsafe because a downstream component made an assumption about what "authorized" or "small" or "local" meant that the upstream component did not actually guarantee. Authentication answers "who are you." Authorization answers "are you allowed." Neither one answers "is this safe to process," and every incident in this chapter lives in that gap.

WHY A SECURITY COMMITTEE HAD TO EXIST BEFORE A CRITICAL CVE COULD BE HANDLED WELL

Notice the ordering: the Kubernetes Product Security Committee and a private, embargoed disclosure process were established in 2017, before CVE-2018-1002105 landed in December 2018. That sequencing was not luck. A pre-9.0-CVSS-score-critical vulnerability disclosed to a project with no coordinated patch process becomes a second incident on top of the first — patches leak, exploits get built against unpatched clusters faster than operators can upgrade, and vendors ship inconsistent fixes. The committee's job during the actual incident was almost entirely logistics: coordinate a fix across every supported release branch (1.10, 1.11, 1.12), get downstream distributions (the major clouds, OpenShift, Rancher) patches simultaneously, and hold the CVE number until patches were available — the opposite of "publish and hope." You will see this same discipline show up again in this chapter's own incidents: how a fix ships is as much engineering as what the fix is.

ARC 03 · NAIVE SOLUTION

Attempt #1: a watchdog that restarts whatever crashes

Before reaching for CVE databases and admission controllers, derive the naive operator's instinct honestly. Most teams' first production-hardening move is some version of: monitor the obvious signals, and automatically restart or scale whatever looks unhealthy. In shell form, deployed as a cron job on a bastion host before anyone has heard of an admission webhook, it looks like this:

bashnaive_watchdog.sh — the strawman, annotated
#!/usr/bin/env bash
# Runs every 30s from cron. "If it looks broken, restart it."
while true; do
  # Is any node's kubelet unresponsive? Reboot it.
  for node in $(kubectl get nodes -o name); do
    kubectl get --raw "/api/v1/nodes/${node}/proxy/healthz" || reboot_node "$node"
  done
  # Is API server latency high? Restart the pod.
  check_apiserver_latency || kubectl -n kube-system delete pod -l component=kube-apiserver
  # Is etcd disk over 80%? Page someone, eventually.
  df /var/lib/etcd | awk '{if ($5+0 > 80) print "etcd disk high"}'
  sleep 30
done

This is not a strawman built to be laughed at — it is close to what many clusters actually run in their first year, and it catches real problems: a wedged kubelet, an obviously OOM-killed API server, a slowly filling disk if someone reads the alert before it fires at 3 a.m. Watch it meet each of this chapter's five incidents in turn.

ARC 04 · WHY IT FAILS

Health checks answer "is it up," not "is it being abused"

Generalize what the deck just showed. A liveness-probe-and-restart strategy is built on a single implicit assumption: badness announces itself as a crash, a timeout, or a full disk you already have a threshold for. Three of this chapter's five incidents violate that assumption directly, and the other two expose a narrower failure inside it — the threshold existed, but arrived after the damage was already unrecoverable.

  • Privilege escalation produces no symptom at all. CVE-2018-1002105's exploit is a perfectly normal-looking authenticated HTTP request that the API server serves without error, at normal latency, returning a normal-looking response. There is no metric to threshold — the "incident" is a policy violation, not a performance event, and a watchdog that only watches performance is structurally blind to it.
  • A YAML bomb crashes the process a health check is checking. By the time check_apiserver_latency would fail, the API server has already OOM-killed or CPU-starved itself processing the payload — the watchdog's "fix" (restart) is exactly what happens automatically anyway, and it does nothing to stop the next identical request from repeating the crash seconds later, because there is no rate limit or depth limit being enforced anywhere in this design.
  • CVE-2020-8558 has no local symptom by definition. The service on 127.0.0.1 is answering exactly as designed to legitimate local callers; the bug is that other machines can also reach it. No single-node health check will ever observe "a service is reachable from somewhere it shouldn't be" — that requires an adjacent-host's perspective the watchdog never takes.
  • etcd's disk fills on a curve, not a cliff — until it is a cliff. The 80%-threshold check looks reasonable until you do the arithmetic in §4's math box below: on a moderately busy cluster the gap between "80% full" and "0 bytes free, every write rejected" can be single-digit hours, and defragmentation (the actual fix) takes the member offline for the duration on some etcd versions — exactly the moment nobody wants to run it.
  • Conntrack exhaustion is a shared kernel resource, not a per-pod metric. No single container's health check will ever see nf_conntrack: table full, dropping packet in its logs — that line goes to the node's kernel log, and the symptom clients actually see (a 5-second stall, then success) is easy to misdiagnose as "the app is slow" rather than "the node's connection tracker is full."
THE MATH ON ETCD'S DISK CLIFF

etcd defaults to an 2 GiB backend quota (--quota-backend-bytes). A cluster taking 3,000 writes/sec across all keys (busy, but not exotic for a large multi-tenant cluster with heavy Event and status-update churn) with an average value size of ~1 KB adds roughly 3 MB/sec of new revision data to the backend file if compaction is disabled or lagging. At that rate the file grows from "looks fine" (500 MB) to the 2 GiB quota in under nine minutes of sustained write pressure — and once the NOSPACE alarm fires, etcd rejects every write cluster-wide, including the ones your controllers need to remediate anything, until an operator runs compaction and defragmentation by hand. A watchdog polling disk usage every 30 seconds with an 80% threshold catches this in principle — the problem is the runbook after the alert fires is manual, and manual runbooks executed under page-duty pressure at 3 a.m. are where defragmentation debt turns into a multi-hour outage. §11 walks the full anatomy.

So the naive answer — watch obvious signals, restart obvious failures — is not wrong, it is necessary but radically incomplete. What's missing in every failure above is validation and containment applied before the dangerous request is fully processed, plus scheduled maintenance that runs whether or not anyone remembers to run it. §5 builds that layer.

THE COMMON SHAPE, NAMED PRECISELY

Look at the five fixes side by side and a pattern appears: every one of them adds a check at the exact boundary where trust changes hands — where an authenticated request becomes a raw byte stream (the 101 status check), where wire bytes become an in-memory object graph (the decode depth limit), where a packet crosses from network to loopback (the martian-packet rule), where a logical delete becomes reclaimed disk (compaction versus defragmentation, as two separate, both-required steps), and where a DNS query becomes a kernel conntrack entry (a local cache that intercepts most queries before they need one). None of these fixes make the component "smarter" in a general sense — they each add one specific, narrow validation at one specific boundary that a previous version trusted implicitly.

ARC 06 · WHY THAT STILL COSTS

Hardening is not free, and pretending it is causes its own incidents

Each of §5's fixes is unambiguously correct to ship. None of them are free to operate, and a chapter that pretends otherwise would be lying by omission:

  • Patching is a continuous tax, not a one-time event. Every supported Kubernetes minor version needed its own backport for CVE-2018-1002105 (1.10.11, 1.11.5, 1.12.3) and CVE-2019-11253 (1.13.12, 1.14.8, 1.15.5, 1.16.2) — running an unsupported minor version means a fix simply does not exist for you to apply, full stop. "We'll upgrade later" converts every future critical CVE into a fire drill instead of a scheduled maintenance window.
  • Decode-depth and size limits can reject legitimate-but-unusual manifests. A generated Custom Resource with genuinely deep nesting (some Helm-templated CRDs, deeply nested Terraform-generated configs) can trip the same guard that stops a Billion-Laughs payload — the fix trades a small false-positive rate for closing an unbounded-severity hole, which is the correct trade, but it is a trade, not a free lunch.
  • etcd defragmentation is not free to run — it blocks the member being defragmented. Running it cluster-wide requires rolling through members one at a time, watching quorum at every step; running it during peak traffic on the wrong member can itself cause a latency spike serious enough to be its own minor incident.
  • NodeLocal DNSCache is another daemon to operate. It removes most DNS-driven conntrack churn, but it is now a per-node process with its own crash mode, its own upgrade cadence, and its own dashboards — solving "too much load on CoreDNS" by adding a new component that itself needs care.
  • Every added validation is added latency and added attack surface of its own. Admission webhooks, depth-limited decoders, and firewall rules are all more code in a hot path. The 2018 aggregation-layer proxy bug is itself a reminder that "add another layer that inspects traffic" is not automatically safer than no layer at all — the layer has to be built at least as carefully as everything below it.
THE HONEST CONCLUSION

Hardening a cluster against this chapter's five incidents does not converge to "done." It converges to a maintained posture: a patch cadence that tracks upstream security releases, a maintenance schedule for etcd that runs whether or not it's exciting, and monitoring that watches the specific signals each incident actually produces (conntrack utilization, etcd db size versus quota, admission webhook rejection rates) rather than only the generic ones (CPU, memory, restart count) a naive watchdog checks. §7 assembles that posture into one architecture diagram.

ARC 08 · INTERNAL IMPLEMENTATION

The exact mechanism behind each incident

This is the section worth re-reading twice. Five subsections, one per incident, each showing the real shape of the vulnerable code, the real shape of the fix, and — where the incident is operational rather than a CVE — the real data structures and commands involved. Everything below is simplified from the actual upstream source for clarity but faithful to its structure and naming; nothing here is invented behavior.

(a) CVE-2018-1002105 — the aggregation proxy's upgrade confusion

Kubernetes lets you extend the API surface two ways that both rely on the same proxying machinery: the aggregation layer (an APIService object like v1beta1.metrics.k8s.io tells the API server "requests for this group go to that backend Service"), and the node proxy subresource used by kubectl exec, attach, and port-forward (requests to /api/v1/nodes/<node>/proxy/..., forwarded to the kubelet). Both cases need the same unusual capability: sometimes the request is a normal HTTP call, and sometimes it needs to become a raw, bidirectional byte stream — an HTTP Upgrade — because exec needs to carry stdin/stdout/stderr and terminal resize events over one live connection, not one request/response pair.

The shared code for this, UpgradeAwareHandler, works by dialing the backend on the client's behalf, forwarding the original request including its Upgrade header, and then deciding what to do with whatever the backend sends back. The only correct decision tree is: if, and only if, the backend replies 101 Switching Protocols, hijack the client's TCP connection and relay raw bytes in both directions from then on. Any other status code means the backend declined the upgrade, and the proxy's job is to hand that ordinary HTTP response back to the client and stop — no hijack, no raw relay, nothing further.

The vulnerable code skipped the "if, and only if" — it hijacked the connection regardless of what the backend actually replied with, whenever the client's original request had asked for an upgrade. Step through the exploit and the fix:

Request smuggling through an unvalidated upgradeSTEP-BY-STEP
Gostaging/src/k8s.io/apiserver/pkg/util/proxy/upgradeaware.go — VULNERABLE shape
func (h *UpgradeAwareHandler) tryUpgrade(w http.ResponseWriter, req *http.Request) bool {
    if !httpstream.IsUpgradeRequest(req) {
        return false  // not an upgrade attempt at all — proxy normally
    }
    backendConn, resp, err := h.dialer.Dial(req)     // forwards Upgrade header to backend
    if err != nil { http.Error(w, err.Error(), 502); return true }
    defer backendConn.Close()

    // BUG: no check on resp.StatusCode here. Whatever the backend said,
    // this code hijacks the CLIENT's connection and starts relaying raw
    // bytes both ways — even if resp.StatusCode is 200, 403, or anything
    // else that means "I will NOT upgrade this connection."
    clientConn, _, _ := w.(http.Hijacker).Hijack()
    go io.Copy(backendConn, clientConn)          // client → backend, unchecked
    io.Copy(clientConn, backendConn)             // backend → client, unchecked
    return true
}

The consequence, precisely: the client's follow-on bytes are now raw TCP payload flowing straight into the backend's socket. If the backend is a kubelet, or another aggregated API server, it typically trusts that connection as already-authenticated — the API server dialed it using its own TLS client credentials, the same identity it uses for every legitimate proxy connection. NVD's own description of this CVE names that detail explicitly: the smuggled requests are processed "authenticated with the Kubernetes API server's TLS credentials used to establish the backend connection" — not the low-privileged user's identity, and not subject to that user's RBAC grant at all, because as far as the backend can tell, every byte after the handshake came from the trusted proxy.

Goupgradeaware.go — PATCHED shape (the fix that shipped in 1.10.11 / 1.11.5 / 1.12.3)
func (h *UpgradeAwareHandler) tryUpgrade(w http.ResponseWriter, req *http.Request) bool {
    if !httpstream.IsUpgradeRequest(req) {
        return false
    }
    backendConn, resp, err := h.dialer.Dial(req)
    if err != nil { http.Error(w, err.Error(), 502); return true }
    defer backendConn.Close()

    // FIX: only ever hijack when the backend genuinely agreed to upgrade.
    if resp.StatusCode != http.StatusSwitchingProtocols {
        // Not an upgrade. Copy the backend's ACTUAL response back to the
        // client verbatim — status, headers, body — and stop. No hijack.
        copyResponse(w, resp)
        return true
    }
    clientConn, _, _ := w.(http.Hijacker).Hijack()
    go io.Copy(backendConn, clientConn)
    io.Copy(clientConn, backendConn)
    return true
}
WHY THIS FIX DOESN'T BREAK REAL kubectl exec

A legitimate exec session's backend (the kubelet) genuinely does reply 101 Switching Protocols when it agrees to start streaming stdin/stdout — the check adds zero friction to that path. The fix closes exactly one thing: the case where the backend said no, and the proxy pretended it said yes. That precision — one status-code check, at the one place trust actually changes hands — is why the patch is a few lines, not a redesign. §15 lets you build and break this exact state machine yourself.

(b) CVE-2019-11253 — expansion, not size, is the danger

The API server already limited request body size before this CVE (--max-request-body-bytes, 3 MB by default) — and that limit did nothing to stop this attack, because the danger is not how many bytes arrive on the wire, it is how many objects those bytes decode into. YAML supports anchors and aliases — a way to define a value once and reference it repeatedly — and nothing in a naive decoder stops you from aliasing an alias:

YAMLa minimal expansion bomb — legal YAML, catastrophic decode
a: &a ["lol","lol","lol","lol","lol","lol","lol","lol","lol","lol"]
b: &b [*a,*a,*a,*a,*a,*a,*a,*a,*a,*a]
c: &c [*b,*b,*b,*b,*b,*b,*b,*b,*b,*b]
d: &d [*c,*c,*c,*c,*c,*c,*c,*c,*c,*c]
e: [*d,*d,*d,*d,*d,*d,*d,*d,*d,*d]  # 10^5 leaf strings from ~200 bytes of source

Five levels of ten-way aliasing turns roughly 200 bytes of source text into 100,000 decoded string values — the classic "Billion Laughs" attack, first named against XML in 2003, applied here to a YAML/JSON decoder inside the API server's request-handling path. Push the nesting a little deeper (the slider below shows exactly how little) and the decoded object graph exceeds available memory or CPU time before the request is ever rejected for being unauthorized or malformed — because structurally, it is neither. It is a well-formed manifest an authorized user is allowed to submit.

The fix could not simply lower the byte-size limit — legitimate manifests with genuinely large, deeply nested structures exist. Instead, the patched decode path in k8s.io/apimachinery tracks nesting depth and cumulative decoded-node count during conversion, aborting the moment either exceeds a fixed bound — catching the exponential blowup before it materializes fully in memory, regardless of how small the source bytes were:

Gostaging/src/k8s.io/apimachinery/pkg/util/yaml — depth-guarded decode, simplified
const maxDecodeDepth = 10000  // fixed, generous bound — real manifests never approach it

func decodeNode(n *yamlNode, depth int) (interface{}, error) {
    if depth > maxDecodeDepth {
        return nil, fmt.Errorf("yaml: exceeded max nesting depth of %d", maxDecodeDepth)
    }
    switch n.Kind {
    case AliasNode:
        // Follow the alias, but the recursive call still carries depth+1 —
        // an alias chain can no longer hide unbounded recursion from the counter.
        return decodeNode(n.Alias, depth+1)
    case SequenceNode:
        out := make([]interface{}, 0, len(n.Content))
        for _, child := range n.Content {
            v, err := decodeNode(child, depth+1)
            if err != nil { return nil, err }
            out = append(out, v)
        }
        return out, nil
    }
    /* ...scalar / mapping cases unchanged... */
    return n.Value, nil
}
A SHARP EDGE THE NVD RECORD ITSELF FLAGS

NVD's description of CVE-2019-11253 includes a detail worth internalizing: "Prior to v1.14.0, default RBAC policy authorized anonymous users to submit requests that could trigger this vulnerability. Clusters upgraded from a version prior to v1.14.0 keep the more permissive policy by default for backwards compatibility." That is a second, independent bug class riding along with the first: a cluster can be running a patched API server binary and still be exploitable by a fully anonymous, unauthenticated caller, because the RBAC bindings it inherited from an old cluster's bootstrap were never tightened. Patching the code and auditing default RBAC bindings are two different remediation steps — this incident is why both are on every serious hardening checklist.

(c) CVE-2020-8558 — a legitimate feature reopens a door the kernel had closed

Linux, by default, drops any packet arriving on a real network interface whose destination address is inside 127.0.0.0/8 — the kernel calls this a martian packet and silently discards it, because "reachable only via loopback" is meant to be a hardware-level guarantee, not a software policy. kube-proxy needs to defeat that guarantee on purpose for one legitimate reason: NodePort and hairpin traffic. When a Pod calls its own Service's NodePort on the node's external IP, the packet gets DNAT'd and, depending on the path taken, can end up looping back through 127.0.0.1 before reaching the real backend — normal, intended behavior that requires the sysctl net.ipv4.conf.all.route_localnet=1 to even function, because without it the kernel's own martian filter would drop that legitimate looped-back packet too.

Setting route_localnet=1 is a blunt instrument: it doesn't just permit kube-proxy's own, intended loopback traffic — it disables the martian check for 127.0.0.0/8 entirely, for every packet on the node, from any source. Without a compensating rule, any host on the same L2 network segment (or any other Pod on the same node) can now send a packet with destination 127.0.0.1:<port> and have the kernel accept it as if it had genuinely arrived via loopback — reaching a TCP or UDP service that was bound to 127.0.0.1 specifically because its owner believed that binding meant "only this machine, only local processes."

A packet's path with and without the martian-drop ruleSTEP-BY-STEP
iptablespkg/proxy/iptables/proxier.go — the KUBE-FIREWALL compensating rule
# Added to the KUBE-FIREWALL chain, evaluated on every packet:
-A KUBE-FIREWALL -m comment --comment "block incoming localnet connections" \
  -d 127.0.0.0/8 ! -s 127.0.0.0/8 \
  -m conntrack ! --ctstate RELATED,ESTABLISHED \
  -j DROP

Read the rule the way the kernel evaluates it: destination inside 127.0.0.0/8, source not inside 127.0.0.0/8 (i.e. this did not genuinely originate on loopback), and not part of an already- established connection the node itself initiated — drop it. This restores the martian guarantee for everyone except the one legitimate case (the node's own established, already-permitted hairpin flows), which is precisely the scalpel this bug needed: route_localnet stays on (NodePort still works), but the blanket exposure it created is closed back down to the one flow that needs it.

(d) etcd disk exhaustion — the difference between compaction and defragmentation

etcd is a MVCC store: every write to every key creates a new revision, and old revisions are kept — on purpose, so that Kubernetes' watch streams can resume from any past revision number without gaps — until something explicitly tells etcd to discard them. Two separate, both-necessary operations govern that, and confusing them is exactly how clusters end up with a multi-gigabyte backend file holding almost no live data:

  • Compaction (etcdctl compact <revision>) marks every revision older than the given one as eligible for garbage collection inside etcd's own key-space. It does not shrink anything on disk by itself — it just stops those old revisions from being reachable, which lets etcd's internal boltdb pages holding them be reused for future writes.
  • Defragmentation (etcdctl defrag) is the step that actually returns freed pages to the underlying boltdb file and, in some deployment modes, to the filesystem — without it, compacted revisions leave "holes" that boltdb happily reuses for new writes, but the file on disk never gets smaller, and can even keep growing if write-churn outpaces reuse.

Running only compaction (common — many clusters enable --auto-compaction-mode=periodic --auto-compaction-retention=1h and stop there) prevents unbounded logical growth but not unbounded file growth under fragmentation pressure. Running neither is worse and more common than it should be: it is simply the etcd default unless an operator (or, on kubeadm-managed clusters, the bootstrap tooling) explicitly configures it.

(e) CoreDNS meltdown — a shared kernel table, spent on amplified traffic

Every UDP packet that Linux's netfilter needs to NAT — and kube-proxy's iptables/IPVS rules NAT nearly everything, because every ClusterIP is a DNAT target — gets an entry in the kernel's connection-tracking table, even though UDP itself has no concept of a connection. That table has a fixed maximum size (net.netfilter.nf_conntrack_max, commonly in the low hundreds of thousands of entries depending on node memory) and a per-entry timeout. DNS is disproportionately hard on this table for a specific, avoidable reason: a Pod's default resolv.conf ships with ndots:5, meaning the resolver tries every entry in its search-domain list before trying your query as an absolute name — a single lookup for my-svc can fan out into 4-5 sequential UDP queries, each opening its own conntrack entry, before one finally resolves.

THE SPECIFIC "5-SECOND" SYMPTOM — A REAL, WIDELY-REPRODUCED KUBERNETES ISSUE

Under load, two distinct kernel-level problems compound. First, sheer volume: enough concurrent DNS flows from enough Pods can approach nf_conntrack_max, and once the table is full the kernel starts dropping new connections of any protocol — not just DNS — logging nf_conntrack: table full, dropping packet. Second, and specifically for UDP DNAT: a documented kernel race lets two packets for the same new flow, processed on different CPU cores at nearly the same instant, both try to insert a conntrack entry — the loser's packet is silently dropped rather than delivered. glibc's resolver does not retry quickly on a dropped UDP query; it waits its full timeout, 5 seconds by default, before trying the next nameserver or giving up. That is the exact, widely-reported "every so often a DNS lookup takes 5 seconds" symptom operators have filed against Kubernetes for years — it is a real race condition in the kernel's NAT path, not an application bug, and it gets dramatically more likely exactly when DNS volume (and therefore concurrent new-flow insertion) is highest.

The industry-standard mitigation, NodeLocal DNSCache, does not fix the kernel race — it makes the race overwhelmingly unlikely to matter by removing most DNS traffic from the DNAT path entirely. It runs a caching DNS proxy as a DaemonSet, listening on a dummy network interface at a link-local address on every node, and rewrites Pods' resolv.conf (or the kubelet's cluster-DNS setting) to point there instead of directly at the ClusterIP for the CoreDNS Service. A query that hits the node-local cache never gets DNAT'd at all — no conntrack entry, no race — and only cache misses forward on to CoreDNS proper, over a connection that can be kept alive and reused instead of opened fresh per query.

ARC 11 · REAL-WORLD PRODUCTION INCIDENTS

Five incidents, told as an on-call engineer would tell them

Incident 1: CVE-2018-1002105 — the first Critical Kubernetes CVE

Disclosed December 3–5, 2018, this was the first vulnerability in Kubernetes to receive a CVSS score of 9.8 (Critical) — no privileges beyond a valid, narrowly-scoped authenticated identity required, no user interaction, network-exploitable, full compromise of confidentiality, integrity, and availability of anything the API server could reach as a proxy. Because the bug lived in code shared by the aggregation layer and the kubelet proxy subresource, the practical blast radius was "any cluster running an unpatched API server with any aggregated API service or any RBAC grant touching nodes/proxy," which in practice was nearly every cluster of the era. The community response is the textbook case study: backports landed simultaneously across 1.10, 1.11, and 1.12; every major distribution (the primary clouds, OpenShift, Rancher) shipped patched images within days; and the disclosure explicitly named the fix's shape (validate the upgrade response) rather than leaving operators to guess whether a version bump alone was sufficient. The lesson operators took away, still valid: audit exactly which RBAC identities can reach proxy subresources and aggregated APIs, because that surface — not "cluster-admin," which is comparatively easy to audit — is where this exact class of bug tends to reappear.

Incident 2: CVE-2019-11253 — a five-line YAML file, cluster-wide

Disclosed October 17, 2019, this incident is a favorite teaching example precisely because the payload is so small. A user with permission to submit almost any namespaced object — in some cases, thanks to the pre-1.14 default RBAC bindings NVD calls out explicitly, an unauthenticated caller — could submit a manifest whose YAML expanded exponentially during decode, driving one or more API server replicas to exhaust CPU or memory and crash. Because API servers are typically run as a Deployment behind a load balancer with several replicas, the practical outage pattern was a rolling one: a malicious or even accidentally-malformed (some early triggers were found by fuzzing, not malice) request could crash the replica that happened to receive it, the load balancer would route around it while it restarted, and a repeated or automated submission could keep multiple replicas crash-looping simultaneously — a real denial of service against the entire control plane, not just one process. The fix (depth and node-count limits during decode) plus an RBAC audit of default bindings inherited from pre-1.14 clusters were both required; teams that only upgraded the binary and never checked their inherited RBAC policy remained exposed to unauthenticated exploitation even after patching.

Incident 3: CVE-2020-8558 — the node that could see too much

Disclosed July 27, 2020, this bug is quieter than the previous two — a MEDIUM/HIGH severity network-isolation failure rather than a full compromise — but it is the one most likely to still be silently present today, because "my service is bound to localhost, it's fine" is such a common, reasonable-sounding assumption that teams rarely revisit it. The realistic production scenario: a team runs a debugging or metrics sidecar bound to 127.0.0.1 specifically because it exposes something sensitive (unauthenticated pprof endpoints, internal cache statistics, an admin API with no auth of its own) and reasons, correctly under normal Linux semantics, that binding to loopback is sufficient isolation. On an unpatched node, any other host on the same L2 segment — including, in cloud environments, other tenants' instances on a shared subnet in some configurations, or simply other nodes in the same cluster — could reach that "local-only" service directly. The fix required no application changes at all; it lived entirely in kube-proxy's iptables programming, which is itself the lesson: the vulnerability was never in anyone's YAML or RBAC policy, it was in infrastructure code everyone trusted implicitly and nobody was auditing.

Incident 4: the etcd disk-exhaustion outage pattern

Not a CVE — a pattern, reproduced independently across countless clusters, that follows an almost identical timeline every time. A cluster runs fine for months on etcd's defaults. Write volume grows — more controllers, more CRDs, more Events, more status-subresource churn from increasingly chatty operators — and nobody notices the backend file's slow climb because dashboards watch CPU, memory, and pod counts, not etcd DB size against quota. Eventually a burst of write activity (a bad deploy triggering thousands of Pod status updates, a misbehaving controller in a hot-reconcile loop, a batch job creating and deleting tens of thousands of Jobs) pushes the backend past quota-backend-bytes within minutes rather than the weeks the slow climb suggested was available. The NOSPACE alarm fires, every write in the cluster starts failing — including the writes any automated remediation would need to make — and the on-call engineer's first etcdctl compact and defrag commands, run for the first time under page pressure rather than as a rehearsed runbook, take the cluster through a tense multi-minute-to-multi-hour recovery window depending on backend file size and disk I/O. The durable fix industry-wide has been to stop treating compaction and defragmentation as manual, reactive commands and instead schedule both — --auto-compaction-mode=periodic with a bounded retention window, plus a recurring, off-peak, one-member-at-a-time defrag job — so the alarm simply never fires.

Incident 5: CoreDNS meltdown under load

The signature version of this incident: a cluster scales up — a marketing event, a batch of new tenants, a traffic spike — and application teams start reporting "our service is randomly slow," with request traces showing the delay sitting entirely inside a DNS lookup, and specifically clustering around almost exactly 5 seconds. Nothing in CoreDNS's own metrics looks unhealthy — request rate is up, but latency and error rate on CoreDNS's side look normal, because the drop is happening beneath CoreDNS, in the node's kernel, before the query ever reaches it. Teams that don't know to look at conntrack -S or node kernel logs spend hours suspecting the application, then the CoreDNS Deployment's replica count, before finding the actual signal. The resolution that actually holds under further scale is not "add more CoreDNS replicas" (it does not reduce conntrack pressure — more replicas just means more DNAT targets for the same query volume) but NodeLocal DNSCache, which removes the DNAT hop for the large majority of queries entirely. Clusters that adopted it report the symptom disappearing, not merely becoming rarer — consistent with the mechanism, since eliminating the DNAT path eliminates the race that causes it, rather than just reducing how often the race is triggered.

func (s *store) Compact(rev int64) (int64, error) {
    // Every key's revision history below `rev` becomes unreachable —
    // but the bytes are still sitting in boltdb pages until defrag runs.
    for key, revs := range s.keyIndex {
        revs.CompactBelow(rev)              // drop index entries, not disk pages
    }
    s.currentRev = rev
    return s.currentRev, nil
}

// A SEPARATE call, on a SEPARATE schedule, does the disk-reclaiming work:
func (b *backend) Defrag() error {
    // Copies all LIVE pages into a fresh file, drops the old one —
    // this is the operation that blocks the member while it runs.
    return b.defrag()
}

WHY THIS CHAPTER'S FIXES LOOK SO DIFFERENT FROM EACH OTHER — AND THAT'S THE LESSON

Three of these five fixes are a handful of lines in Go. One is a single iptables rule. One is not code at all — it's a cron schedule and an operational habit.
