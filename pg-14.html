POSTGRESQL INTERNALS · CHAPTER 14

Beyond B-Tree:
GIN, GiST, SP-GiST, BRIN & Hash

A B-tree gives you exactly one thing: a total order over keys, and the ability to prune search space for any predicate expressible as a contiguous range on that order. Containment, spatial overlap, nearest-neighbor, and "megabyte index over a terabyte table" are not that shape. This chapter derives the IndexAmRoutine abstraction that lets PostgreSQL host five structurally different index types behind one executor interface, then goes inside each one: GIN's inverted posting lists, GiST's lossy bounding predicates, SP-GiST's unbalanced space partitions, BRIN's tiny block summaries, and hash's cautionary history.

ARC 01 · THE PROBLEM

A total order can only answer total-order questions

Every B-tree access method PostgreSQL ships — the default btree — is built on one guarantee: its opclass exposes a total order over the indexed type, via exactly five strategies (<, <=, =, >=, >) registered in pg_amop against a btree opfamily. That single guarantee is what makes a B-tree's search correct and fast: at every internal page the tree can ask "is my target less than, equal to, or greater than this separator key?" and throw away half the remaining space. It is a beautiful, general algorithm for exactly one predicate shape: is this key inside a contiguous interval of the ordering?

Now try to make that algorithm answer questions that are not interval questions. tags @> ARRAY['urgent'] asks "does this row's multi-valued column contain a specific element" — there is no single scalar ordering of arrays for which "contains element X" collapses to a contiguous range. box1 && box2 asks "do these two 2-D regions overlap" — impose any single total order on 2-D space (row-major, Z-order, whatever) and points that are physically adjacent get scattered arbitrarily far apart in that order, so a range scan of the ordering does not correspond to a spatial neighborhood. tsvector @@ tsquery asks "does this document contain these lexemes" — same shape as array containment, at a much larger fan-out (hundreds of keys per row instead of a handful). And a query like WHERE created_at BETWEEN a AND b against a 4 TB append-only table is a perfectly good interval question that a B-tree answers correctly — but at a size cost (an entry for every one of billions of rows) that is wasteful when the answer "which physical blocks could possibly contain this range" is knowable from a structure a thousand times smaller.

Two different failures are bundled together here, and the chapter is organized around teasing them apart: wrong algorithm (B-tree literally cannot represent containment or spatial adjacency, no matter how it's tuned) and wrong cost model (B-tree can represent range-over-huge-correlated-data, but pays per-row when per-block would do). PostgreSQL's answer to both is the same abstraction: an IndexAmRoutine dispatch table, instantiated five different ways.

WHY THIS MATTERS FOR THE NEXT SIX CHAPTERS

Every index type this chapter covers is not hardcoded into the query executor. The executor calls amgettuple() or amgetbitmap() through a function pointer and does not know or care whether the code behind that pointer is walking a B-tree, decoding a posting list, or testing a bounding box. That indirection is what let GIN, GiST, SP-GiST, and BRIN ship as ordinary PostgreSQL releases — and let PostGIS ship an entire spatial database as an out-of-core extension, registering nothing but SQL-level catalog rows against machinery that already existed.

DEEP CONTEXT · THE THESIS BEHIND THE FRAMEWORK

Hellerstein, Naughton, and Pfeffer's 1995 VLDB paper "Generalized Search Trees for Database Systems" made an argument that is easy to underrate in hindsight: instead of writing a new balanced-tree implementation for every new predicate shape (R-trees for boxes, tries for text, signature trees for documents), factor out the one thing every balanced tree implementation was re-deriving — page splits, concurrency, recovery — and let the data-type author supply only the handful of functions that encode what makes their predicate special. That's consistent, union, penalty, and picksplit. Everything generic (locking, WAL, page layout) lives once, in src/backend/access/gist/gist.c, forever.

ARC 03 · NAIVE SOLUTION

Attempt #1: no index, or a fake one

Derive it honestly, the way the naive attempt actually happens in production. A team stores each document's words as a text[] and needs "find documents containing word X." The first thing anyone tries is the index they already understand:

SQLnaive_1.sql — no supporting index at all
CREATE TABLE docs (id bigint primary key, tags text[]);
-- 10 million rows loaded, ~8 tags each, no index on tags

SELECT id FROM docs WHERE tags @> ARRAY['urgent'];
-- EXPLAIN: Seq Scan on docs  (cost=0.00..312000.00 rows=1 width=8)
--            Filter: (tags @> '{urgent}'::text[])
-- every one of 10,000,000 rows is fetched from the heap and tested

The second naive attempt tries to reuse the one index shape that exists — B-tree — by faking an inverted structure at the SQL level: explode every row into one row per element, then B-tree that:

SQLnaive_2.sql — hand-rolled inverted index over a B-tree
CREATE TABLE doc_tags AS
  SELECT id AS doc_id, unnest(tags) AS tag FROM docs;

CREATE INDEX ON doc_tags (tag, doc_id);   -- a plain B-tree, "faking" GIN

SELECT doc_id FROM doc_tags WHERE tag = 'urgent';
-- fast! B-tree equality on `tag` prunes to the matching leaf run.
-- but: this is a SECOND TABLE, kept in sync by hand, and every
-- multi-tag query becomes an application-level or SQL-level
-- intersection across doc_id sets, not a single index operation.

This is not a foolish first move — it already reveals the right intuition (invert the relationship between document and element), it is exactly how you'd hand-build an inverted index in any general-purpose language, and it is genuinely fast for a single-tag equality lookup. Its failure mode only shows up at the two axes that matter in production: write amplification and multi-key query cost. Section 4 quantifies both.

ARC 04 · WHY IT FAILS

The arithmetic of exploding a multi-valued column

Take the numbers from naive_2.sql and make them concrete. 10 million documents, ~8 tags each: doc_tags has 80 million rows — an 8× explosion over the base table before the B-tree even starts, and the B-tree itself needs an entry per row, so the index is roughly 8× the size of a hypothetical single-column index on docs. For a tsvector-shaped workload the multiplier is far worse: a few hundred distinct lexemes per document is normal, so "one B-tree entry per (doc, lexeme) pair" is a 100–300× explosion, not 8×. At 10M documents × 150 lexemes that is 1.5 billion index entries for data that started as 10M rows.

Write cost compounds the size cost. Updating one document's tag set under the naive scheme means deleting its old rows from doc_tags and inserting its new ones — N physical B-tree operations (delete + insert, each an index-page descent) where GIN, as section 8 will show, does one logical insert that appends to a pending list in amortized O(1). And multi-key queries (tags @> ARRAY['urgent','billing']) need an explicit intersection of two B-tree scans' doc_id sets — either as a SQL-level join the planner has to construct and execute, or, with no supporting index at all, a full Seq Scan costing O(N) heap-page fetches regardless of how selective the predicate actually is; a query matching 1 row in 10 million still touches every one of the table's heap pages, because nothing about a sequential scan's access pattern depends on the predicate's selectivity.

THE NUMBERS

Seq Scan cost is O(N) pages, full stop — a query that will match one row in ten million still reads every page. The hand-rolled inverted B-tree turns O(1) logical writes into O(D) physical ones, where D is lexemes-per-document (100–300 for prose), and turns a single index into an entire second table with its own bloat, its own vacuum, and its own consistency-with-the-source-of-truth problem. Neither of these is a tuning oversight — they are what you get from forcing a data structure whose only trick is "prune a contiguous range" to represent a fundamentally different question, "does this bag contain this element."

So the industry needed either a purpose-built inverted-index access method, or — since spatial, full-text, and block-summary problems all share the same "wrong shape for B-tree" root cause — a way to add several new index shapes without rewriting the executor once per shape. Section 5 walks the elimination.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates, and why only the third one survives contact with reality

Given the failure modes in §4, there are three plausible next moves. Step through them in order — each is a reasonable engineering instinct, and each gets eliminated for a specific, quantifiable reason rather than vague dissatisfaction.

THE ACTUAL DECISION POSTGRESQL MADE

Not "add an inverted-index access method." Add an abstraction that any number of access methods can implement: a struct of function pointers (IndexAmRoutine), resolved once per access method via a handler function registered in pg_am, and a catalog layer (pg_opclass/pg_opfamily/ pg_amop/pg_amproc) that binds a data type's operators to whichever access method can serve them. GIN, GiST, SP-GiST, and BRIN are four instances of that one decision, not four separate special cases bolted onto the executor. §7 explores the dispatch table directly.

ARC 06 · WHY THAT STILL COSTS

Pluggability doesn't repeal the cost — it relocates it

A generalized framework is not a free lunch; it moves cost from "core has to write a new index type" to two other places, and both show up later in this chapter as concrete, nameable failure modes rather than abstractions:

  • Correctness risk moves to the opclass author. GiST's penalty and picksplit are ordinary C functions supplied per data type — core cannot verify that a third-party picksplit produces well-separated, non-overlapping children. A bad picksplit compiles, runs, and returns correct query results; it just returns them slowly, because every sibling ends up needing to be visited (§8b, §11 incident 3). The framework guarantees a balanced tree, never a balanced partition of the key space — those are different properties, and only the second one determines query speed.
  • Write cost moves to key extraction. GIN must decompose every inserted row into potentially hundreds of keys (lexemes, array elements, jsonb path/value pairs), sort them, and maintain a compressed posting structure per key — work a B-tree insert never does, because a B-tree's "key" is the row's value as-is, not a derived multiset. §8a quantifies this as the reason GIN builds and inserts are measurably slower than B-tree's, in exchange for reads that are correspondingly faster.
  • BRIN's entire value proposition is an assumption the index cannot enforce. A block-range summary is only useful if physical row order correlates with the summarized value — and nothing about the BRIN access method can make that true. An UPDATE-heavy workload, or a table that was never loaded in sorted order, silently converts a BRIN index from "prunes 99% of ranges" to "prunes nothing," with no error, no warning, and no change to query correctness — only to query cost. §11 incident 2 is exactly this failure in production.
  • Hash paid for its narrowness with two decades of not being trustworthy. Restricting yourself to equality-only, single-column, unordered buckets should in principle be a smaller, faster structure than a B-tree — and it is smaller, per entry. But PostgreSQL's hash access method went un-WAL-logged for over 20 years (§2), meaning the "faster, narrower" index also happened to be the one you could lose to a crash. That specific cost had nothing to do with hashing as an algorithm and everything to do with which subsystem got engineering investment first — a reminder that a framework's five instances are not required to mature at the same rate.

None of this is an argument against the framework — GIN, GiST, SP-GiST, and BRIN each solve real problems B-tree structurally cannot. It is the honest accounting the rest of the chapter is built on: pick the right AM for your data's shape, and then respect the specific cost each one relocated onto you.

ARC 07 · FINAL ARCHITECTURE

The IndexAmRoutine dispatch table and its five tenants

src/include/access/amapi.h defines IndexAmRoutine: a plain C struct of booleans (capability flags like amcanorder, amcanmulticol, amsearcharray) and function pointers. pg_am.amhandler names a C function — bthandler(), ginhandler(), gisthandler(), spghandler(), brinhandler(), hashhandler() — that GetIndexAmRoutine() calls once per planning/execution need; that function allocates and fills in the struct and returns it. Everything downstream — the planner's cost comparisons, the executor's scans, VACUUM's bulk-delete pass — talks only to this struct, never to GIN- or GiST-specific code directly. ARC 08 · INTERNAL IMPLEMENTATION

Five structures, at the level you'd need to patch them

(a) GIN: entry tree, posting lists, and the pending-list tradeoff

A GIN index is two structures glued together. The entry tree is an ordinary B-tree (built with GIN's own page format, but conceptually a B-tree) keyed on extracted keys — lexemes, array elements, jsonb path/value pairs — produced by the opclass's extractValue support function. Each entry-tree leaf either stores a small compressed posting list inline (the matching row TIDs, if there are few) or a pointer to a posting tree — itself a small B-tree of TID ranges — once the list would be too large to keep inline. Traversal state through the entry tree during insert/vacuum is kept in a GinBtreeStack, a linked list of page/offset pairs mirroring the descent, defined in src/include/access/gin_private.h and pushed/popped in ginbtree.c exactly the way any B-tree descent needs a stack to know how to propagate a split upward.

Posting lists are not arrays of raw 6-byte ItemPointerData values. ginpostinglist.c's ginCompressPostingList() stores them delta-encoded and varbyte-compressed: TIDs within one key's posting list are already sorted, so each entry is stored as the difference from the previous TID rather than an absolute block/offset pair, and that difference is encoded in as few bytes as fit (a varint scheme — 1 byte for small deltas, more only when needed). Consecutive matches in a dense table compress to roughly a byte or two each instead of 6 fixed bytes — a compression ratio that is exactly why GIN's read path stays cheap even though its key space is large: decoding is a tight sequential loop, not pointer chasing.

The expensive part is staying up to date. fastupdate (default on) exists because inserting directly into the entry tree per row means: extract keys, then for each key, descend the entry tree, possibly split pages, possibly grow a posting tree — expensive, and worse under concurrent writers who all want the same hot keys. Instead, a new tuple's extracted keys are appended to an unsorted pending list — cheap, append-only pages, no entry-tree descent at all. The cost is deferred, not eliminated: every scan must now also linearly scan the entire pending list (it isn't sorted, so it can't be searched, only scanned) in addition to using the real entry tree. gin_pending_list_limit (default 4 MB) is the cliff: once the pending list would exceed it, an insert triggers a synchronous merge (ginInsertCleanup() in ginfast.c) that sorts the pending list and folds it into the main structure — which is why some inserts, seemingly at random, take far longer than their neighbors: whichever one crosses the size threshold pays for everyone's deferred work.

Support functions round out the entry-tree side: consistent() takes the query's extracted keys and a bitmap of which ones matched this candidate row, and returns whether the row satisfies the original predicate — necessary because a @> ARRAY['x','y'] needs AND-logic across two keys' posting lists, not just "some key matched." triConsistent() (added in 9.4) extends this to a genuine three-valued logic — true, false, or maybe (needs recheck) — letting GIN answer AND/OR/NOT combinations without first decompressing every candidate key's full posting list, and comparePartial() supports partial-match operators like tsquery's prefix search (foo:*) directly against the entry tree's sorted keys.

(b) GiST: bounding predicates, penalty-driven insert, and the recheck contract

A GiST index is a balanced tree where every internal entry is a bounding predicate — a summary, produced by the opclass's union function, of everything beneath it. For PostGIS geometry that's a bounding box; for btree_gist over a range or scalar type it's an interval; for the built-in tsvector_ops GiST opclass it's a fixed-length superimposed-code signature (a Bloom-filter-like bitstring per document). GISTSTATE (built once per scan/insert in gist.c from the opclass's pg_amproc rows) holds the resolved function pointers for consistent, union, compress, decompress, penalty, picksplit, equal, and optionally distance (KNN — ORDER BY geom <-> point) and fetch (reconstructing an original value for an index-only scan, when possible).

Insert descends the tree by repeatedly calling penalty() on each child and choosing the one that would need to grow its bounding predicate least to accommodate the new entry — a greedy heuristic, not an optimal one. When a leaf page overflows, picksplit() divides its entries into two new pages, and the parent's bounding predicates are recomputed via union(); if the parent itself overflows, the split propagates upward exactly like a B-tree split, just with predicates being unioned instead of separator keys being copied. Whether the resulting tree stays fast is entirely a function of picksplit's quality: a good picksplit produces children whose bounding boxes barely overlap, so a search predicate usually rules out one side entirely; a bad picksplit — or data whose natural shape defeats any splitting heuristic (long overlapping skinny polygons, for instance) — produces siblings whose boxes both contain the query, forcing the search to descend into every subtree, degrading toward a full index scan over years of inserts with no error or warning (§11 incident 3).

A bounding box is a lossy summary of the geometry inside it — many shapes share the same box. When compress() throws away information to make the stored predicate small and fast to test (the signature-based tsvector_ops GiST opclass is the extreme case: a fixed-length bitstring can never perfectly represent an unbounded document), amgettuple/amgetbitmap can return false positives — TIDs whose bounding predicate matched but whose actual value does not. The executor must recheck each one against the real heap tuple, which is exactly what Recheck Cond in EXPLAIN ANALYZE output — and its sibling line Rows Removed by Index Recheck — is reporting. This is not a defect to fix; it's the documented, load-bearing contract every lossy GiST opclass makes with the executor.

(c) SP-GiST: exact partitions instead of tolerated overlap

SpGistState (spgist_private.h, built in spgutils.c) resolves a different, smaller function set: config (declares the opclass's node-label and leaf-value types), choose (given a value and an existing inner tuple's partition scheme, decide which child it belongs in, or whether the node needs to be split first), picksplit (create a new partitioning scheme for a page whose values no longer fit one scheme — e.g., pick a new quadrant center), and inner_consistent/ leaf_consistent (the scan-side tests, split into an inner-page version that can prune whole subtrees and a leaf-page version that tests actual values). The structural difference from GiST is architectural, not cosmetic: an SP-GiST inner page can hold many partition labels (quadrants, radix-trie branches) whose children may live on entirely different pages, and — critically — a value belongs to exactly one partition, never two. There is no overlap to tolerate, so there is nothing for a bad picksplit to degrade into overlapping siblings; the tree also does not need to stay balanced in the B-tree/GiST sense, because depth follows wherever the data's own structure requires more discrimination (a quadtree over clustered points goes deep only in the dense clusters), not a global balance target.

(d) BRIN: revmap, summary tuples, and the bloom-filter opclass

A BrinTuple (brin_tuple.h) is not one per row — it is one per page range (pages_per_range, default 128 heap pages), holding one summary value per indexed column: for minmax, a (min, max) pair; for minmax_multi, up to several disjoint (min, max) intervals so a handful of outliers don't blow the whole range's summary out to "spans everything"; for bloom, a fixed-size Bloom filter bitmap. A separate structure, the revmap (reverse range map — a small, densely packed array of pointers, one per range, to that range's current summary tuple), lets a scan or an insert find "the summary for the range containing heap page P" in O(1) without touching the summary tuples themselves; a BrinMemTuple is just the in-memory, de-TOASTed, per-column-array working form of a BrinTuple that brin_minmax.c/brin_bloom.c's support functions actually read and update.

Building or updating a summary never touches memory outside the pages already being scanned — brin.c's summarization loop reads each page range once, sequentially, and folds each column's value into the range's running summary via the opclass's add_value function (widen the min/max; or-in the new value's hash bits into the Bloom filter). No random heap access, no extra I/O beyond what a sequential scan already does — this is the entire reason BRIN indexes are affordable to build and maintain even on tables too large to keep any other index type resident in cache.

The bloom opclass exists because minmax has one hard failure mode: equality lookups on a column with no ordering correlation at all (a UUID, a hashed customer ID) make every range's min/max span almost the entire domain — a min/max summary is only informative when nearby physical rows have nearby values, and equality on an uncorrelated column never gives you that. A per-range Bloom filter instead asks "could this range possibly contain this exact value?", and answers correctly regardless of ordering, at a quantifiable false-positive cost:

THE BLOOM FALSE-POSITIVE MATH

For a Bloom filter of m bits using k hash functions, after n distinct items have been inserted, the probability that a value not actually present tests as "maybe present" is approximately:

p ≈ (1 − e−kn/m)k

Every false positive costs one extra heap-page-range fetch that gets filtered out after the fact (never a wrong answer — Bloom filters never produce false negatives, only false positives) — so p is a pure performance dial, tunable via how many distinct values land in one range (smaller pages_per_range → smaller n per filter → lower p, at the cost of more summary tuples total) and via the per-range filter's bit width, which the opclass sizes from the range's expected cardinality at build time.

(e) Hash: buckets, overflow chains, and the WAL-logging wart

A hash index buckets rows by hash_uint32()-style hashing of the key, growing via incremental, linear-hashing-style bucket splits as HashMetaPageData's (hash.h) tracked tuple count crosses thresholds — hashm_maxbucket, hashm_lowmask/hashm_highmask record exactly which buckets have split so far, and hashm_ovflpoint tracks where new overflow pages get allocated when a bucket fills before its turn to split. hashinsert.c and hashsearch.c implement, respectively, "hash the key, find the bucket, chain into overflow pages if full" and "hash the key, find the bucket, scan its primary page and overflow chain for exact matches" — no ordering is maintained or even possible, since bucket assignment is a hash, not a comparison.

The honest historical wart: until PostgreSQL 10 (2017), hash index changes were not written to the WAL at all. That meant a hash index was not crash-safe — a crash between a hash-index page modification and the next checkpoint could leave it corrupted with no record to replay it from — and it could not be used on a streaming replica, since there was no WAL to stream. For over two decades, the documented, honest advice in the manual was effectively "don't rely on this in production; rebuild it after any crash." Amit Kapila's PG10 work made hash indexes fully WAL-logged, closing both gaps. What it didn't change: hash still can't do range scans, can't do ORDER BY, can't be multicolumn, and B-tree's superior cache locality (dense, ordered pages instead of scattered buckets) and support for covering/multicolumn indexes usually make B-tree at least as fast even for pure equality — which is why hash indexes remain, honestly, a mostly historical and niche-large-single-column choice rather than a routine one (§9, §10).

The size story is where GIN's "big index" reputation and "far smaller than the alternative" reality both live at once. Drag the table-size slider and watch four curves separate: a native B-tree over a single scalar column, a GIN index over a tsvector column (paying entry-tree + compressed-posting-list overhead per lexeme occurrence, but sharing one entry-tree node per distinct lexeme), a BRIN index over the same table (roughly flat — it barely grows with row count once pages_per_range is fixed), and the naive "one B-tree row per (document, lexeme) pair" scheme from §3/§4 that GIN exists to make unnecessary:

Cache and TLB effects layer on top of raw size. A B-tree's dense, ordered leaf pages mean a hot range of keys usually fits in a handful of buffer-pool pages that stay resident; GIN's entry tree is small enough to stay hot even when its posting lists are large, because posting-list decoding is a sequential varbyte scan — cache- and prefetcher-friendly — rather than pointer-chasing. GiST is the outlier: its cache behavior is not purely a function of tree depth but of bounding-box overlap, so two GiST indexes over the same row count can have wildly different page-visit counts depending purely on picksplit quality and data skew — a property none of the other four AMs share. Hash's scattered bucket/overflow chain is the one structurally worse-than-B-tree cache pattern in this table for the one workload (pure equality) hash is supposedly optimized for, which is the concrete mechanism behind §9's "B-tree is usually just as fast or faster" claim.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: the bulk-load hangover

A nightly batch job bulk-inserts 20 million rows into a table with a GIN index on a jsonb column, fastupdate left at its default (on). The load itself is fast — every insert is a cheap pending-list append. An hour later, morning-dashboard SELECTs against that table are randomly 5–10× slower than their historical baseline, then quietly return to normal over the next hour. Nothing in the logs mentions an error, a lock wait, or a plan change. The mechanism, once you know §8a: the pending list grew far past gin_pending_list_limit during the bulk load's overnight window before autovacuum got to it, so every morning query paid a linear scan of a multi-hundred-megabyte unsorted pending list on top of its normal entry-tree lookup — and the "returns to normal" part is autovacuum's amvacuumcleanup eventually folding the pending list into the main structure. Fix: run VACUUM (or explicitly SELECT gin_clean_pending_list('idx')) immediately after a known bulk load, before the query traffic resumes, rather than waiting for autovacuum's normal schedule to notice.

Incident 2: the BRIN index that stopped helping and nobody noticed

A 6 TB events table has a BRIN index on created_at, loaded originally in insertion (hence timestamp) order — correlation near 1.0, BRIN pruning nearly every range for typical "last 24 hours" queries. A data-retention job runs a bulk UPDATE to redact a column across most of the table's rows. Postgres's MVCC means that UPDATE doesn't modify rows in place — it writes new row versions whose physical location is wherever free space (or a fresh page) puts them, entirely decoupled from the table's original insertion order. pg_stats.correlation for created_at quietly drops from 0.98 to 0.1 the next time ANALYZE runs. Every range's (min, max) now spans nearly the full timestamp domain, because rows from every era got rewritten into whatever pages happened to be free at redaction time. Query plans don't change (BRIN is still "used"), and query correctness never wavered — but BRIN now excludes almost nothing, and the same "last 24 hours" query silently starts reading nearly the whole table through the bitmap heap scan. Fix: monitor pg_stats.correlation for BRIN-indexed columns as a first-class signal (not just after complaints); after any bulk rewrite, consider CLUSTER or a rebuild-via-reload to restore physical/value correlation, or switch to a minmax_multi/bloom opclass if the workload can tolerate the different tradeoff those make.

Incident 3: GiST bloat on skewed polygon data

A logistics company indexes delivery-zone polygons with PostGIS's GiST-based spatial opclass. Most zones are small, well-separated city neighborhoods — the index performs exactly as expected for years. Then a handful of enormous, overlapping "regional" zones get added (each one a bounding box the size of a state, deliberately overlapping dozens of city zones underneath it). picksplit, doing its best with a page that suddenly contains both tiny tight polygons and enormous sprawling ones, cannot separate them without one child's bounding box growing to cover most of the other — exactly the §8b failure mode. Point-in-polygon queries that used to touch a handful of pages start touching a large fraction of the index, with EXPLAIN ANALYZE showing a ballooning "Rows Removed by Index Recheck" as bounding-box false positives pile up. Fix: in the specific case of a few enormous outlier geometries alongside many small ones, split them into a separate table/index (or pre-clip/tile them) rather than let one GiST tree's picksplit try to reconcile wildly different size scales — a real, documented PostGIS operational pattern, not a workaround anyone should need to invent from scratch.

Datum
ginhandler(PG_FUNCTION_ARGS)
{
    IndexAmRoutine *amroutine = makeNode(IndexAmRoutine);
    amroutine->amcanorder    = false;   /* posting lists aren't row-ordered */
    amroutine->amcanmulticol = true;

    amroutine->amgettuple    = NULL;      /* GIN only supports bitmap scans */

}

The posting-list decode loop — the reason GIN scans stay fast despite large key spaces — simplified from ginpostinglist.c:

Cginpostinglist.c — decoding a delta-encoded, varbyte-compressed posting list
/* On disk: NOT an array of 6-byte ItemPointerData.
 * Instead: the first TID stored whole, every subsequent TID stored
 * as (this_tid - previous_tid), varbyte-encoded — small deltas cost
 * ONE byte, only large gaps cost more.                              */
ItemPointer
ginPostingListDecode(GinPostingList *plist, int *ndecoded)
{
    ItemPointer result = palloc(plist->nbytes * sizeof(ItemPointerData));
    unsigned char *ptr = plist->bytes;
    ItemPointerData current = plist->first;    /* stored whole, uncompressed */
    result[0] = current;
    int i = 1;

    while (ptr < plist->bytes + plist->nbytes)
    {
        uint64 delta = 0;
        int shift = 0;
        unsigned char b;
        do {                                /* varbyte: 7 payload bits + 1 continuation bit */
            b = *ptr++;
            delta |= (uint64)(b & 0x7F) << shift;
            shift += 7;
        } while (b & 0x80);
        current = ItemPointerAddOffset(current, delta);   /* reconstruct absolute TID */
        result[i++] = current;
    }
    *ndecoded = i;
    return result;                        /* sorted ascending, ready to intersect with other keys' lists */
}

BRIN's range-summarization loop — the reason a BRIN index is affordable to build even on a table too large to keep resident in cache, simplified from brin.c/brin_minmax.c, plus the bloom opclass's probe that the false-positive formula in §8d describes:

Cbrin.c / brin_minmax.c — sequential range summarization
void
brinbuild(Relation heap, Relation index, IndexInfo *indexInfo)
{
    BrinMemTuple *summary = NULL;
    BlockNumber   rangeStart = 0;

    /* ONE pass over the heap, in physical page order — no random access */
    table_index_build_scan(heap, index, indexInfo, true, false,
                            brinBuildCallback, (void *) &summary, NULL);
}

static void
brinBuildCallback(Relation index, ItemPointer tid, Datum *values, bool *isnull, ...)
{
    BlockNumber page = ItemPointerGetBlockNumber(tid);
    if (page / pagesPerRange != currentRange)
        brinSummarizeRange(index, currentRange);   /* flush the finished range's tuple */

    /* minmax opclass's add_value(): widen, never narrow */
    if (values[0] < summary->min) summary->min = values[0];
    if (values[0] > summary->max) summary->max = values[0];
}

/* bloom opclass's consistent(): can this range possibly contain `key`? */
bool
brinBloomConsistent(BloomFilter *filter, Datum key)
{
    for (int i = 0; i < filter->k; i++)          /* k hash functions */
        if (!bloom_bit_test(filter, bloom_hash(key, i) % filter->m))
            return false;               /* definitely NOT present — safe to skip range */
    return true;                        /* MAYBE present — false-positive rate ≈ (1-e^(-kn/m))^k */
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Function pointers, not virtual classes. C has no vtables, so an IndexAmRoutine is a literal struct of function pointers, filled in once by a handler function named in pg_am and cached for the lifetime of the plan/execution — dispatch cost is one indirect call per operation, not a lookup. 2. Delta+varbyte posting lists, not raw TID arrays. TIDs inside one key's posting list are already sorted by construction (they're appended/merged in TID order), so encoding them as small deltas turns what would be a fixed 6-bytes-per-TID array into a compressible stream — and decoding is a tight sequential loop, exactly the access pattern a modern CPU prefetches well, which is why GIN reads stay fast even though GIN writes are expensive. 3. BRIN summarization never leaves the pages it's already reading. No opclass's add_value is allowed to go fetch other pages — it only ever sees the values already streaming past during a normal sequential scan, which is exactly why building or maintaining a BRIN index costs almost nothing extra beyond a scan you were likely doing anyway (VACUUM, or the initial load).
