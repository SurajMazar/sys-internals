APPLIED CRYPTOGRAPHY · CHAPTER 11

Diffie-Hellman &
Elliptic Curve Key Exchange

Every chapter so far has assumed a shared secret key already exists in two places at once — chapters 2–7 encrypted and authenticated with it, chapter 8 stretched it into subkeys, chapter 9 used a keypair for one-directional secrecy. None of them explain how two computers that have never communicated before, talking only over a wire that a passive attacker can read in full, end up holding the same secret number without ever sending that number across the wire. That is the problem Whitfield Diffie, Martin Hellman, and Ralph Merkle solved in 1976, and it is arguably the single most important idea in applied cryptography: it is the reason HTTPS works without you and your bank having met in person. This chapter derives Diffie-Hellman from the discrete logarithm problem, implements it for real in JavaScript with BigInt modular exponentiation, watches it fail catastrophically the moment an active attacker shows up, and then builds the elliptic-curve version — ECDH and X25519 — that replaced it almost everywhere.

ARC 01 · THE PROBLEM

Two strangers, a public wire, no shared secret

Go back to chapter 2's very first sentence: a block cipher is a keyed permutation. Every primitive since — AES, ChaCha20, HMAC, GCM, HKDF — takes that key as a given. Nobody has yet asked the question that makes all of it possible in the real world: where does the key come from?

For two parties who can meet in person, or who share a corporate network with a hardware security module, the answer is boring — generate randomness locally, copy it over a trusted channel once. That does not describe your browser connecting to a bank's web server it has never touched before, over a network (the public internet) whose every router, ISP, and Wi-Fi access point is a potential eavesdropper. Before 1976 the honest answer was: you can't, not without an out-of-band trusted channel — a courier, a diplomatic pouch, a pre-printed codebook. Symmetric cryptography alone cannot solve this; by definition, encrypting a key under another key just moves the "how do you share that key" problem one level up, forever.

Precisely state the goal, because the precision matters for everything that follows:

  • Public channel. Alice and Bob can only exchange messages that a passive eavesdropper, Eve, reads in full — every bit, in real time.
  • No prior secret. Alice and Bob share no pre-existing key, password, or certificate before this exchange begins.
  • Shared output. At the end, Alice and Bob must both hold the identical value s — a number neither of them alone chose — suitable as an AES or ChaCha20 key (after chapter 8's KDF, since s itself is not uniformly random bytes).
  • Eve's failure. Eve, who saw every message Alice and Bob exchanged, must be computationally unable to derive s herself.

Notice the threat model is deliberately narrow for now: Eve is passive — she reads, she does not inject, drop, or alter messages. That restriction is not an oversight; it is the exact boundary this chapter is going to walk you into and then past. Diffie-Hellman solves the problem as stated. Section 6 removes the restriction and the whole scheme quietly collapses.

WHY THIS MATTERS FOR THE NEXT 5 CHAPTERS

Key exchange is the missing piece between "we have great symmetric primitives" (ch. 2–8) and "we have a usable secure channel between strangers" (TLS, ch. 13). This chapter supplies the math. Chapter 12 supplies the piece that turns "a shared secret with someone" into "a shared secret with the party whose name is on the certificate" — authentication. Chapter 13 wires both into the real TLS 1.3 handshake. Skip this chapter's derivation and chapter 13 will feel like memorized trivia instead of inevitable engineering.

DEEP CONTEXT · WHY "DIFFIE-HELLMAN-MERKLE"

Ralph Merkle's 1974 undergraduate project — "Merkle puzzles" — solved the same problem with an O(n) vs O(n²) asymmetry between legitimate parties and an eavesdropper, published only after Diffie and Hellman's 1976 paper credited him. Hellman has spent decades publicly insisting the scheme be called Diffie-Hellman-Merkle; most of the literature (and this chapter's title) still says "Diffie-Hellman" out of inertia, not accuracy. It is worth knowing whose names got attached to the idea and whose didn't — the same pattern (uncredited or delayed credit) recurs with GCHQ's Cocks and Williamson below.

ARC 03 · NAIVE SOLUTION

Attempt #1: just send the key

Derive this honestly, the way a working engineer under deadline pressure actually would. Alice needs Bob to have a symmetric key for the AES-GCM session they're about to open (chapter 7). The straight-line solution: generate the key locally and send it.

pseudocodenaive_handshake.js — the strawman
function naiveHandshake(socket) {
    // Alice generates a fresh, perfectly random AES-256 key locally.
    const sessionKey = randomBytes(32);

    // ...and just sends it to Bob, in the clear, over the same TCP
    // socket every router between them can already read.
    socket.send(sessionKey);

    return sessionKey;  // Bob receives the identical bytes. It "works."
}

This is not a joke architecture — it is the thing you must try and fail at before the real solution feels necessary rather than arbitrary. It satisfies three of this chapter's four requirements perfectly: no pre-shared secret needed, Alice and Bob end up with an identical key, and it costs one round trip. It fails the fourth requirement — Eve's failure — completely and instantly.

WHAT EVE SEES

Eve's attack is not cryptanalysis. It is tcpdump. She copies the 32 bytes Alice sent, and now she holds the exact same AES-256 key Bob does — not a related value, not a partial key, the literal key. Every subsequent GCM-encrypted record (chapter 7) decrypts for her exactly as it does for Bob. There is no cryptographic step here to attack because there is no cryptography here at all — just a plaintext key transfer that happens to be wrapped in a TLS-shaped conversation.

ARC 04 · WHY IT FAILS

What property would actually have to hold

State precisely what went wrong, because the fix falls directly out of the precise statement. Naive handshake sent a value k over the wire and then used k itself as the secret. For Eve to fail, whatever gets sent over the wire must be derivable from the secret but not the secret itself — and, critically, Alice and Bob's two separately-sent public values must combine into a shared secret using information only each of them privately holds.

This is a request for a specific mathematical structure: a function f such that:

  • Forward direction is cheap. Given a secret input, computing f(secret) is fast — otherwise nobody could use it at internet scale.
  • Reverse direction is (believed) infeasible. Given only f(secret), recovering secret must cost vastly more compute than anyone can afford — a one-way function.
  • It composes. There must be a way for Alice's f(a) and Bob's f(b), exchanged in the clear, to let each of them privately compute the same combined value — without either ever transmitting a, b, or the combined value itself.

Diffie and Hellman's insight was that modular exponentiation in a finite field has exactly this shape. Fix a large prime p and a generator g (both public, non-secret). Computing ga mod p for a random exponent a takes only O(log a) multiplications via repeated squaring (derived precisely in §8) — fast even for enormous a. Going backward — given g, p, and ga mod p, recovering a — is the discrete logarithm problem, and no efficient classical algorithm for it is known despite 45+ years of attack.

THE ASYMMETRY, QUANTIFIED

For a 2048-bit prime, computing ga mod p takes on the order of 3,000 modular multiplications — microseconds on any CPU built this century. Solving the discrete log for the same prime with the best known classical algorithm (the general number field sieve, index-calculus family) is estimated at roughly 2110 operations — NIST SP 800-57's own security-strength table equates a 2048-bit finite-field group with "112-bit security." That gap — microseconds to compute, ~1021 years' worth of compute to invert at global datacenter scale — is the entire security argument. It is a conjecture, not a theorem: nobody has proven no faster algorithm exists, only that decades of dedicated attack (including by intelligence agencies, per the Logjam researchers' own estimates, §11) have not found one for well-chosen parameters.

That asymmetry is precisely the missing ingredient. §5 turns it into a working protocol.

WHY THE EXPONENTS CANCEL — THE ONE LINE OF ALGEBRA THAT MAKES ALL OF THIS WORK

Alice computes Ba mod p = (gb)a mod p = gba mod p. Bob computes Ab mod p = (ga)b mod p = gab mod p. Since multiplication of exponents commutes (ab = ba), these are the same value, computed two different ways, by two parties who never told each other a or b. Nobody "sends" the shared secret — it is a mathematical coincidence engineered so that only the two people holding the private exponents can land on it.

ARC 06 · WHY THAT STILL FAILS

Diffie-Hellman authenticates nothing — and Logjam's cost math

Re-read §1's threat model: Eve was passive. Against a passive eavesdropper, raw Diffie-Hellman as just derived is genuinely secure (given a large enough prime). The moment you promote Eve to an active attacker — one who can intercept, drop, and inject her own messages, which describes any Wi-Fi access point, any compromised router, any ISP under legal or illegal compulsion — the scheme does not degrade gracefully. It fails completely, silently, and neither Alice nor Bob can tell.

Here is the mechanism. Nothing in the four messages of §5 (p, g, A, B) proves who sent them. Mallory, sitting on the wire, does not need to break the discrete logarithm problem at all — she simply runs the exact protocol from §5 twice, once against each victim, and relays nothing:

Anatomy of a silent man-in-the-middleSTEP-BY-STEP

Two more costs stack on top of the MITM vulnerability, and both are about parameter selection, not the algebra:

  • Weak or reused primes are catastrophic in bulk, not just individually. The 2015 Logjam attack (§11) exploited 1990s-era U.S. export controls that capped "export-grade" DHE ciphers at 512-bit primes. Worse: because generating a fresh safe prime is expensive, huge numbers of servers reused the same few hardcoded 512-bit and 1024-bit primes shipped as defaults in Apache and OpenSSL. An attacker who spends the (large, but one-time) cost to solve the discrete log for one popular prime can then break every connection that used it, in near-real-time, forever.
  • Static (non-ephemeral) keys erase forward secrecy. Nothing in §5 requires Alice or Bob to throw their private exponent away after one exchange. If a server reuses the same b for months, an attacker who ever steals it (server compromise, subpoena, key-extraction bug) can retroactively decrypt every recorded past session that used it. Ephemeral Diffie-Hellman — a fresh a/b generated per connection, discarded immediately after — is the fix, and it is the reason production protocols write "DHE" and "ECDHE" (the trailing E is not decorative) rather than plain "DH."
THE HONEST SUMMARY

Diffie-Hellman solves confidentiality-against-eavesdropping. It solves nothing about authentication. Every production use of DH/ECDH you will ever encounter — TLS, SSH, Signal, WireGuard — pairs it with a second, independent mechanism that proves identity: a digital signature over the ephemeral public value, verified against a certificate or known public key. That mechanism is chapter 12's entire subject. Until then, treat every DH exchange in this chapter's simulator as "confidential against a wiretap, worthless against an active attacker" — which is the literal truth about the bare algorithm.

ARC 08 · INTERNAL IMPLEMENTATION

The two mechanisms you must actually be able to implement

Two pieces of real machinery make Diffie-Hellman practical rather than theoretical: (a) fast modular exponentiation, without which even honest parties couldn't afford to run the protocol, and (b) the elliptic-curve analogue that replaces the finite-field group with a much more efficient one at equal security.

(a) Modular exponentiation by repeated squaring

Computing ga mod p the naive way — multiply by g, a−1 times — is useless for real exponents: a 256-bit private exponent would need ~1077 multiplications, more than there are atoms in the observable universe. The fix is square-and-multiply: scan the exponent's bits from most-significant to least-significant, squaring the running result every bit and multiplying in an extra factor of the base only where the bit is 1. That turns an O(a) algorithm into an O(log₂ a) one. Step through a real trace — computing 513 mod 23, the same base and modulus from §5:

(b) The elliptic-curve analogue — same algebra, a different group

Everything in §5 through §7 relied on one property of the multiplicative group mod p: it supports an operation (multiplication) that is easy to iterate (exponentiation) and believed hard to invert (discrete log). Elliptic-curve groups have the identical algebraic shape — an operation called "point addition," an easy iteration called "scalar multiplication" (k·G, computed by the same square-and-multiply idea, renamed "double-and-add"), and a believed-hard inverse called the elliptic-curve discrete logarithm problem (ECDLP). The Blockchain Internals course (chapter on secp256k1/ECDSA) derives the point-addition and point-doubling formulas over a short Weierstrass curve y² = x³ + ax + b mod p in full — this chapter does not re-derive that arithmetic, but the headline result matters here: the best known classical attack on ECDLP (Pollard's rho) is fully exponential, O(√n), unlike the finite-field DLP's sub-exponential index calculus. That single difference is why EC groups need far fewer bits for equivalent security (quantified with real NIST numbers in §10).

X25519 (RFC 7748), the curve behind most modern ECDH deployments, uses a Montgomery curve rather than short Weierstrass form specifically because its scalar-multiplication ladder can be written with no secret-dependent branches and no need to validate the input point — every possible 32-byte input, valid-looking or not, produces a well-defined output. Two implementation details make this work, and both are worth internalizing because chapter 15 revisits them as the textbook case for constant-time code:

  • Scalar clamping. Before use, a X25519 private key's bits are forced into a specific shape (clear the low 3 bits, clear the top bit, set the second-highest bit) — this fixes the scalar's bit-length and forces it to be a multiple of the curve's cofactor (8), closing off small-subgroup attacks without any runtime branch.
  • The Montgomery ladder. Each bit of the scalar performs the identical sequence of field operations regardless of whether the bit is 0 or 1 (a constant-time conditional swap selects which register feeds which operation) — so the time taken depends only on the scalar's length (fixed at 255 bits), never its value. §13 shows the real BoringSSL shape of this ladder.
PROTOCOL STATE MACHINE: WHERE THIS SITS IN A REAL HANDSHAKE

In TLS 1.3 (chapter 13 in full), the client generates an ephemeral X25519 or P-256 keypair before it sends anything, and places the public point directly in ClientHello's key_share extension. The server, on seeing a supported group, generates its own ephemeral keypair, computes the shared secret immediately, and returns its public point in ServerHello's key_share — the entire exchange from §5 completes in the first round trip, which is why TLS 1.3 can encrypt as early as the second flight. Every field on the wire is exactly the public value this chapter has been computing; nothing about the handshake format changes the math.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Why 256 elliptic-curve bits beat 3072 finite-field bits

The two families of discrete-log problem are attacked by algorithms of genuinely different complexity classes, and that difference is the entire reason key sizes look so lopsided:

  • Finite-field DLP (what breaks classic DH): best classical attack is the general number field sieve / index calculus family, sub-exponential in the bit-length of p — meaning it is much faster than brute force, and it gets relatively cheaper as computers get faster.
  • Elliptic-curve DLP (what breaks ECDH): best classical attack is Pollard's rho, fully exponential, O(√n) group operations for a group of order n — there is no known shortcut analogous to index calculus for a well-chosen curve.

NIST SP 800-57 Part 1's security-strength equivalence table (real published numbers, not an approximation this chapter invented) makes the gap concrete:

ATTACK COST IN REAL OPERATIONS — LOGJAM'S PRECOMPUTATION ECONOMICS

The 2015 "Imperfect Forward Secrecy" (Logjam) paper estimated that breaking a single 512-bit export-grade prime via the number field sieve costs about US$100 in cloud compute for the per-connection step — but only after a one-time per-prime precomputation the authors measured at roughly a week on an academic-sized cluster. For 1024-bit primes (common in non-export DHE, e.g. the built-in Apache/OpenSSL default) the authors extrapolated the precomputation to be within the reach of a well-funded nation-state — hundreds of millions of dollars and custom ASICs, comparable in scale to what the same paper argues is consistent with the NSA's documented "large-scale VPN decryption" capability. The precomputation is reusable across every connection using that prime, which is what makes attacking a handful of widely reused 1024-bit primes rational at nation-state budgets even though attacking one individual connection would not be.

ARC 11 · REAL-WORLD INCIDENTS

Three times key exchange broke in shipped software

Logjam (2015, CVE-2015-4000) — the export-grade downgrade

1990s U.S. cryptography export rules capped "exportable" TLS ciphers at 512-bit DHE. Those export cipher suites were never removed from most server and client codebases — they just went unused. Logjam's researchers showed that a MITM attacker could intercept a normal TLS handshake, rewrite the client's cipher-suite list to claim only export-grade DHE is offered, and many servers would comply and downgrade to a 512-bit prime even though both real endpoints supported strong ciphers. Once downgraded, the attacker breaks the discrete log in the ~$100/connection regime described in §10 and reads or forges the "secure" session in real time. Root cause: the TLS handshake did not authenticate the cipher-suite negotiation itself strongly enough to prevent a downgrade, and dead export-grade code paths were left reachable for two decades. The fix: removing export ciphers entirely, and mandating minimum DHE group sizes (RFC 7919's named groups exist specifically so servers stop generating — and reusing — arbitrary custom primes).

CVE-2016-2216 (socat) — a "prime" that wasn't prime

The socat relay tool shipped a hardcoded 1024-bit DH modulus for its DHE-based encryption mode. In 2016 researchers discovered the hardcoded value was not actually prime — it had a small factor, discovered by simple trial division, that a genuine safe prime would never have. A composite modulus collapses the discrete-log hardness assumption: subgroups of small order exist inside a composite modulus's multiplicative structure, and the Pohlig-Hellman algorithm solves discrete logs efficiently whenever the group order has only small prime factors. Root cause: a parameter that should have been generated (or at minimum, primality-tested) by a cryptographic library was instead hardcoded from an external, unverified source. The lesson generalizes directly from §6's algebra: Diffie-Hellman's entire security rests on p being a safe prime — nothing in the protocol itself checks that, so an implementation must.

The Raccoon Attack (2020, CVE-2020-1968) — a timing oracle on the shared secret's shape

TLS 1.2's specification says a finite-field DHE shared secret, when it happens to begin with one or more zero bytes, has those leading zero bytes stripped before being fed into the master-secret derivation — a detail inherited from an old ASN.1-adjacent big-integer encoding convention, not a security requirement (ECDH shared secrets use a fixed-length encoding and are not subject to this specific stripping step, which is why Raccoon's practical impact concentrated on finite-field DHE deployments). Raccoon showed that on servers that reused the same ephemeral (or worse, static) DH keypair across many connections, an attacker who could measure tiny timing differences in how fast the server processed a specially crafted handshake could infer whether the resulting shared secret's leading byte was zero — a single bit of oracle per measurement, in the same family as chapter 10's padding oracles. Repeated across enough connections (and combined with lattice techniques), this leaked enough information to recover the full premaster secret. Root cause: a spec-mandated data-dependent transformation (stripping leading zero bytes) that leaks timing, applied to a value an attacker can influence the distribution of by controlling their own DH contribution. The fix: TLS 1.3 changed the key schedule to avoid the zero-stripping behavior entirely, and RFC 8446 implementations are told to left-pad rather than strip.

First, the two functions that are §5's algebra in production C — key generation and shared-secret computation, simplified from OpenSSL's structure but faithful to the real call shape:

Cdh_key.c — DH_generate_key() and DH_compute_key()
int DH_generate_key(DH *dh)
{
    /* dh->p, dh->g are the public group parameters (fixed, e.g. ffdhe2048). */
    BIGNUM *priv_key = BN_new();

    /* Pick a in [2, p-2] using the library's CSPRNG — NOT Math.random()-grade
     * entropy. A weak RNG here is a total break: guess a, derive the whole
     * session key. (Chapter 14's Debian OpenSSL bug is this exact failure.) */
    BN_priv_rand_range(priv_key, dh->p);

    /* pub_key = g^priv_key mod p — the ONE exponentiation an honest party
     * does to generate their half of the exchange. BN_mod_exp is bn_exp.c's
     * square-and-multiply, generalized to arbitrary-precision BIGNUMs. */
    BIGNUM *pub_key = BN_new();
    BN_mod_exp(pub_key, dh->g, priv_key, dh->p, ctx);

    dh->priv_key = priv_key;   /* never serialized, never leaves this process */
    dh->pub_key  = pub_key;    /* this is what gets sent on the wire */
    return 1;
}

int DH_compute_key(unsigned char *shared_secret, const BIGNUM *peer_pub_key, DH *dh)
{
    /* THE VALIDATION STEP THAT MATTERS MOST — see the callout below. */
    if (!DH_check_pub_key(dh, peer_pub_key, &codes) || codes != 0)
        return -1;   /* refuse to compute a secret from a malicious-looking value */

    /* shared = peer_pub_key ^ priv_key mod p — the SAME exponentiation
     * function as DH_generate_key, just with the other party's public
     * value as the base instead of the fixed generator g. This is the
     * "exponents cancel" algebra from §5's callout, in the actual library. */
    BIGNUM *shared = BN_new();
    BN_mod_exp(shared, peer_pub_key, dh->priv_key, dh->p, ctx);

    return BN_bn2bin(shared, shared_secret);  /* raw bytes — MUST go through HKDF (§7) before use as a cipher key */
}
WHY DH_check_pub_key() EXISTS — A REAL ATTACK CLASS, NOT DEFENSIVE PARANOIA

If Mallory sends a public value of exactly 1, 0, or p−1, the resulting "shared secret" is forced to a fixed, trivially predictable value regardless of your private exponent: 1a mod p = 1 for any a, and (p−1)a mod p is always either 1 or p−1. More generally, a public value that lies in a small-order subgroup leaks bits of your private exponent through the resulting secret's limited range. DH_check_pub_key() rejects values outside [2, p−2] specifically to close this off — it is the finite-field-DH equivalent of an "invalid curve point" check on the elliptic-curve side, and skipping it is a real, exploitable vulnerability class, not paranoia.

Now the X25519 side — BoringSSL's constant-time ladder, annotated for the two properties §8(b) described (clamping and branch-free stepping):

Ccurve25519.c — X25519() scalar clamping + Montgomery ladder
static void x25519_scalar_mult(uint8_t out[32], const uint8_t scalar[32], const uint8_t point[32])
{
    uint8_t e[32];
    memcpy(e, scalar, 32);

    /* CLAMPING (RFC 7748 §5) — fixed, unconditional bit twiddling, no
     * secret-dependent branch. Clears the low 3 bits (forces the scalar
     * to a multiple of the curve's cofactor 8, neutralizing small-
     * subgroup contributions), clears bit 255, sets bit 254 (fixes the
     * bit-length so the ladder below always runs exactly 255 steps —
     * a variable-length loop would itself leak the scalar via timing). */
    e[0]  &= 248;
    e[31] &= 127;
    e[31] |= 64;

    /* MONTGOMERY LADDER — one iteration per bit, top to bottom. x2/z2 and
     * x3/z3 are two running (X,Z) projective points; swap is a
     * CONSTANT-TIME conditional swap (bitmask select, not an if), so the
     * instruction trace is IDENTICAL whether bit k is 0 or 1. Only the
     * DATA fed into the fixed sequence of adds/doubles differs. */
    for (int pos = 254; pos >= 0; --pos) {
        unsigned bit = 1 & (e[pos / 8] >> (pos & 7));
        cswap(swap ^ bit, x2, x3);   /* branch-free select, not "if (bit) swap();" */
        cswap(swap ^ bit, z2, z3);
        x25519_ladder_step(x2, z2, x3, z3, x1);  /* fixed field add+double, every iteration */
        swap = bit;
    }
    x25519_encode_output(out, x2, z2);  /* project back to a 32-byte affine u-coordinate */
}
WHY BUILT THIS WAY — TWO CHOICES TO STEAL

1. Validate every value that crosses a trust boundary, even ones with a fixed mathematical interpretation. A "public key" is just a number; nothing about its type guarantees it came from an honest exponentiation. Bernstein's Curve25519 sidesteps an entire class of these checks by design (any 32-byte string is accepted, clamped, and produces a well-defined, safe output) — OpenSSL's finite-field path has to check explicitly because its representation doesn't self-enforce the same guarantee. 2. Prefer algorithms whose safe implementation has no decision points on secret data, over algorithms that are merely "safe if you remember to add the right if checks in the right order." X25519 was designed after implementers had spent a decade getting NIST-curve point validation and timing subtly wrong; it treats "hard to misuse" as a first-class design goal, not an implementation afterthought — the same philosophy chapter 15 generalizes into a rule for all secret-dependent code.
