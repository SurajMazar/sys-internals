STEP 04 · PRODUCTION BEST PRACTICES

A cookbook where every recommendation names its mechanism

.clone() vs restructure — when each is actually right

SITUATIONDOWHY
A Copy type (i32, f64, bool, small fixed arrays of them) Just use it. There is no "clone" question. Copy types are bitwise-duplicated implicitly — no heap allocation, no ownership transfer to reason about at all.
A small struct needed briefly by two owners .clone() and move on. The runtime cost is a handful of field copies. Fighting the borrow checker over this is a worse trade than the allocation.
A large Vec<T> or String cloned inside a hot loop Restructure: borrow (&T) instead, or hoist the clone outside the loop. Each clone is a real heap allocation and a full copy of the buffer — O(n) work you're paying on every iteration for no reason.
You reached for .clone() specifically because the compiler complained Stop. Read the actual error first (runbook 5.1). A reflexive clone to silence the borrow checker is the single most common way real bugs and real slowdowns get hidden instead of fixed.
Genuinely need two independent owners of the same data (not just "the compiler is annoyed") Rc<T> (single-threaded) or Arc<T> (cross-thread) instead of duplicating the data Shared ownership without copying the payload — see the decision guide below.
Sending a value across an mpsc channel or into a spawned thread .clone() is often correct here, or a plain move Ownership must genuinely transfer or duplicate to cross that boundary — this isn't the borrow checker being difficult, it's a real concurrency requirement.

Rc vs Arc vs plain ownership — the decision guide

SCENARIOUSEMECHANISM
One owner, never sharedPlain ownership — move it No indirection, no refcount, no runtime cost. Always the default until proven otherwise.
Multiple owners, single-threaded, read-only sharingRc<T> Non-atomic reference count. Cheapest form of shared ownership — but Rc<T> is !Send, so it cannot cross a thread boundary; the compiler enforces that (experiment A2).
Multiple owners, single-threaded, need mutation through the shared handleRc<RefCell<T>> Interior mutability moves the aliasing check from compile time to a runtime borrow flag — a violation panics instead of failing to compile (experiment I3).
Multiple owners, across threads, read-onlyArc<T> Same idea as Rc but the refcount increments are atomic, which costs real cycles — that's the price of being Send + Sync.
Multiple owners, across threads, need mutationArc<Mutex<T>> or Arc<RwLock<T>> for read-heavy workloads The lock owns the data — you cannot touch T without holding the guard, so "forgot to lock" is not a category of bug that compiles (experiment A1).

unwrap()/expect() vs Result propagation

CONTEXTGUIDANCE
Prototyping, examples, testsfine Fast iteration matters more than graceful failure here.
Library code, on any input you don't fully control never unwrap Return Result<T, YourError> and let the caller decide whether a failure is fatal. A library that panics on bad input takes that decision away from every consumer.
Application code, a genuinely unrecoverable invariant violation expect() is fine — with a message describing the invariant, e.g. .expect("config was validated at startup"), not .unwrap() with no context.
Application code, a recoverable I/O / network / parse error propagate with ? into a Result-returning caller, up to a top-level handler that logs and decides retry/exit.
fn main() itself Let it return Result<(), Box<dyn std::error::Error>> — then ? works at the top level and a returned Err prints via Debug and exits non-zero automatically.

Tauri capabilities & permissions — least privilege checklist

  • Start from the default capability file and remove, don't just add. src-tauri/capabilities/default.json ships broader than most apps need — treat it as a starting point to prune, not a template to append to.
  • Scope every permission to exact paths and commands. A filesystem or shell permission scoped to $APPDATA/myapp/* is a completely different risk than an unscoped wildcard.
  • Bind capabilities to specific windows. A settings window and a "load arbitrary remote URL" preview window should not share one capability set just because it's less typing.
  • Never enable the shell plugin's execute permission on unsanitized input. If a command string or its arguments can be influenced by anything the webview received, you've built a remote-code-execution primitive, not a feature.
  • Treat the webview as attacker-controlled the moment it can load remote content. Capabilities are your real security boundary in that case, not the fact that "it's just our own app."
  • Set a real Content-Security-Policy in tauri.conf.json. An empty or overly permissive CSP lets injected script run in the webview even if your capabilities are otherwise tight — the two layers are complementary, not redundant.

Dependency hygiene

  • Run cargo audit in CI (from the cargo-audit crate) against the RustSec advisory database — it flags dependencies with published vulnerabilities before you ship them, not after.
  • Commit Cargo.lock for binaries, not for libraries. A binary needs a reproducible exact dependency graph; a library's downstream consumers resolve their own, and a committed lock file there just goes stale.
  • Prefer fewer, well-maintained dependencies over many small ones. Every crate in the graph is code you're trusting and code that can slow your build (runbook 5.3) — cargo tree shows you the real graph, which is often much larger than the direct dependency list in Cargo.toml suggests.
  • Pin with intent, not by accident. An unpinned * version requirement resolves to whatever's newest at build time; a caret requirement ("1.2", meaning ^1.2) is usually what you actually want — compatible updates only, controlled by Cargo.lock until you deliberately update.

Procedures for when the compiler — or the build — won't cooperate


  
5.1 · Diagnosing a stubborn borrow-checker error

  
    
    
  1. Read the whole message, not just the first line. The help: and note:
      sections usually contain the actual suggested fix, sometimes as a literal diff.
    2. 
    
  2. Find the two spans the compiler is actually pointing at. Every borrow conflict names both the
      existing borrow and the new one that collides with it — the fix lives at one of those two locations, not
      necessarily where the error is reported.
    3. 
    
  3. Check whether NLL already covers it. Since non-lexical lifetimes, a borrow ends at its last real
      use, not at the end of the enclosing block. If you think this "should" compile, you may just be looking at
      an actual overlap the compiler is right about (experiment A6).
    4. 
    
  4. Try re-scoping before cloning. Wrap the borrow in its own { } block, or reorder
      statements so the conflicting borrow's last use comes before the new borrow starts (experiment B2).
    5. 
    
  5. Clone as the pragmatic fallback — see the .clone() decision table above. It's a legitimate fix, not
      a failure, once you've confirmed the data isn't large or hot-path.
    6. 
    
  6. Restructure only if the above don't fit — split the struct so the borrow checker can see the two
      halves are independent, pass indices instead of references, or reach for split_at_mut when you
      need two disjoint &mut slices into one Vec.
    7. 
  


  
5.2 · Debugging a Tauri IPC serialization failure

  
    
    
  1. Check the argument names match, camelCase vs snake_case. Tauri automatically converts a Rust
      command's snake_case parameter names to camelCase for the JS side — a Rust command
      fn add_task(task_name: String) is called from the frontend as
      invoke("add_task", { taskName: "x" }). A mismatched key is the single most common cause of a
      silently-failing invoke().
    2. 
    
  2. Confirm every type crossing the boundary derives Serialize/Deserialize. Any custom struct or enum
      passed as a command argument or return value needs #[derive(Serialize, Deserialize)] from
      serde — a missing derive is a compile-time error on the Rust side, but a missing field rename can pass
      compilation and fail at runtime instead.
    3. 
    
  3. Check numeric type width against what the frontend actually sends. JSON has one number type;
      Rust's u32 will reject a negative number or a float with a fraction at deserialization time —
      that failure surfaces as an IPC rejection, not a Rust panic.
    4. 
    
  4. Open the webview devtools and read the actual rejection. A failed invoke() rejects its
      promise with the real serde error text — that message tells you exactly which field didn't match, but only
      the frontend console shows it; the Rust side often logs nothing.
    5. 
  


  
5.3 · Triaging a cargo build that suddenly got much slower

  
    
    
  1. Check for a newly added heavy dependency. git log -p -- Cargo.toml — proc-macro-heavy
      crates (anything built on syn/quote) and crates with many default features
      enabled are the usual culprits.
    2. 
    
  2. Confirm incremental compilation is actually on. It's the dev-profile default; check nothing set
      CARGO_INCREMENTAL=0 and that you're comparing dev builds to dev builds — --release
      is expected to be slower and doesn't use incremental by default.
    3. 
    
  3. Run the real profiler: cargo build --timings writes an HTML report under
      target/cargo-timings/ showing exactly which crate dominates wall-clock time and how much of the
      build is serialized versus parallel.
    4. 
    
  4. Check for expensive work in a build.rs or proc-macro that runs unconditionally on every build
      rather than caching its output.
    5. 
    
  5. Consider the linker. On Linux, swapping the default linker for lld or mold
      often cuts link time dramatically on large binaries — link time, not compile time, dominates many "slow
      build" complaints.
    6. 
  


  
5.4 · Recovering from a botched cargo update that broke the build

  
    
    
  1. See exactly what moved: git diff Cargo.lock.
    2. 
    
  2. Pin the offending crate back precisely without touching anything else:
      cargo update -p <crate> --precise <version>.
    3. 
    
  3. If several crates moved together and the interaction is unclear, revert wholesale:
      git checkout Cargo.lock, then cargo build to confirm the old lock still resolves
      against your current Cargo.toml.
    4. 
    
  4. Upgrade deliberately from there — one crate at a time with cargo update -p <crate>,
      running tests between each, rather than a blanket cargo update that moves the whole dependency
      graph at once.

Project 1 · BEGINNER INTERMEDIATE — a CLI todo-list manager

  
Vec<Task>, an enum for status, Result-based error handling throughout, and
  persistence to a JSON file with serde. This exact skeleton becomes the Tauri capstone in project 3.


  
tomlCargo.toml


[package]
name = "todo-cli"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"


  
rustsrc/main.rs — starter skeleton


use serde::{Deserialize, Serialize};
use std::{env, fs};

#[derive(Debug, Serialize, Deserialize, Clone, PartialEq)]
enum Status { Todo, InProgress, Done }

#[derive(Debug, Serialize, Deserialize, Clone)]
struct Task { id: u32, desc: String, status: Status }

#[derive(Debug)]
enum TodoError { Io(std::io::Error), Parse(serde_json::Error), NotFound(u32) }

impl From<std::io::Error> for TodoError {
    fn from(e: std::io::Error) -> Self { TodoError::Io(e) }
}
impl From<serde_json::Error> for TodoError {
    fn from(e: serde_json::Error) -> Self { TodoError::Parse(e) }
}

const FILE: &str = "tasks.json";

fn load() -> Result<Vec<Task>, TodoError> {
    match fs::read_to_string(FILE) {
        Ok(s) => Ok(serde_json::from_str(&s)?),
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => Ok(Vec::new()),
        Err(e) => Err(e.into()),
    }
}

fn save(tasks: &[Task]) -> Result<(), TodoError> {
    fs::write(FILE, serde_json::to_string_pretty(tasks)?)?;
    Ok(())
}

fn add(tasks: &mut Vec<Task>, desc: String) {
    let id = tasks.iter().map(|t| t.id).max().unwrap_or(0) + 1;
    tasks.push(Task { id, desc, status: Status::Todo });
}

fn complete(tasks: &mut [Task], id: u32) -> Result<(), TodoError> {
    let t = tasks.iter_mut().find(|t| t.id == id).ok_or(TodoError::NotFound(id))?;
    t.status = Status::Done;
    Ok(())
}

fn main() -> Result<(), TodoError> {
    let mut tasks = load()?;
    let args: Vec<String> = env::args().collect();
    match args.get(1).map(String::as_str) {
        Some("add") => { add(&mut tasks, args[2..].join(" ")); save(&tasks)?; }
        Some("complete") => {
            let id: u32 = args[2].parse().expect("id must be a number");
            complete(&mut tasks, id)?; save(&tasks)?;
        }
        Some("list") | None => {
            for t in &tasks {
                let mark = match t.status { Status::Done => "x", Status::InProgress => "~", Status::Todo => " " };
                println!("[{}] #{} {}", mark, t.id, t.desc);
            }
        }
        _ => eprintln!("usage: todo-cli <add DESC | complete ID | list>"),
    }
    Ok(())
}


  

    
WHAT PROVES THIS WORKS

    
cargo run -- add "buy milk" then cargo run -- list shows the task, and a real
    tasks.json exists on disk. Restarting the process and running list again still shows
    it — persistence, not just in-memory state. complete flips the mark from a blank to x
    and that survives a restart too. Renaming tasks.json to contain invalid JSON and re-running
    should return a handled TodoError::Parse, not a panic.

Project 2 · ADVANCED — a multithreaded work-queue processor

  
A fixed pool of worker threads pulling jobs off one mpsc channel, aggregating results behind a
  Mutex. mpsc::Receiver only supports a single consumer, so sharing it across worker
  threads needs Arc<Mutex<Receiver<Job>>> — the classic thread-pool pattern.


  
rustsrc/main.rs — starter skeleton


use std::sync::{mpsc, Arc, Mutex};
use std::thread;

type Job = Box<dyn FnOnce() -> i32 + Send + 'static>;

struct Worker { id: usize, handle: Option<thread::JoinHandle<()>> }

struct Pool { workers: Vec<Worker>, sender: Option<mpsc::Sender<Job>> }

impl Pool {
    fn new(size: usize, results: Arc<Mutex<Vec<i32>>>) -> Pool {
        let (sender, receiver) = mpsc::channel::<Job>();
        let receiver = Arc::new(Mutex::new(receiver));
        let mut workers = Vec::with_capacity(size);

        for id in 0..size {
            let receiver = Arc::clone(&receiver);
            let results = Arc::clone(&results);
            let handle = thread::spawn(move || loop {
                // Lock only long enough to receive; the job itself runs unlocked.
                let job = { receiver.lock().unwrap().recv() };
                match job {
                    Ok(job) => {
                        let out = job();
                        results.lock().unwrap().push(out);
                    }
                    Err(_) => break, // sender dropped: channel closed, no more work
                }
            });
            workers.push(Worker { id, handle: Some(handle) });
        }
        Pool { workers, sender: Some(sender) }
    }

    fn submit<F: FnOnce() -> i32 + Send + 'static>(&self, job: F) {
        self.sender.as_ref().unwrap().send(Box::new(job)).unwrap();
    }
}

impl Drop for Pool {
    fn drop(&mut self) {
        drop(self.sender.take());               // closes the channel
        for w in &mut self.workers {
            if let Some(h) = w.handle.take() { h.join().unwrap(); }
        }
    }
}

fn main() {
    let results = Arc::new(Mutex::new(Vec::new()));
    let pool = Pool::new(4, Arc::clone(&results));

    for i in 0..100 { pool.submit(move || i * i); }

    drop(pool); // blocks until every worker has drained the channel and exited
    let results = results.lock().unwrap();
    println!("processed {} jobs, sum of squares = {}", results.len(), results.iter().sum::<i32>());
}


  

    
THE Mutex POISONING GOTCHA

    
Note that job() runs outside the receiver's lock scope — deliberately. If a job panics,
    only its own worker thread unwinds; the results mutex is never held across the panic, so it can't
    be poisoned. If you instead called job() while still holding a lock and it panicked, every future
    .lock().unwrap() on that mutex would itself panic with PoisonError — locking scope
    boundaries are a correctness decision, not just style.

  

  

    
WHAT PROVES THIS WORKS

    
After drop(pool), results.len() == 100 with no duplicates and no missing entries,
    regardless of how the 4 workers happened to interleave. Every type crossing a thread boundary here — the
    Job closures, the Arcs — satisfies Send, and the compiler refuses to
    build this at all if you accidentally capture something that doesn't (experiment A2).

  

  
Extensions: wrap the job() call in std::panic::catch_unwind so one panicking
  job no longer permanently kills its worker thread, and prove it by submitting a mix of good and deliberately
  panicking jobs and confirming the pool still processes every good one; add a submit variant that
  returns a oneshot-style handle so the caller can await one specific job's result instead of only
  reading the shared aggregate; swap the hand-rolled pool for the rayon crate's
  par_iter() on the same 100 jobs and compare how much of this file rayon replaces.

use serde::{Deserialize, Serialize};
use std::fs;
use std::sync::Mutex;
use tauri::State;

#[derive(Debug, Serialize, Deserialize, Clone, PartialEq)]
enum Status { Todo, InProgress, Done }

#[derive(Debug, Serialize, Deserialize, Clone)]
struct Task { id: u32, desc: String, status: Status }

struct AppState(Mutex<Vec<Task>>);

const FILE: &str = "tasks.json";

fn load() -> Vec<Task> {
    fs::read_to_string(FILE).ok()
        .and_then(|s| serde_json::from_str(&s).ok())
        .unwrap_or_default()
}
fn persist(tasks: &[Task]) {
    let _ = fs::write(FILE, serde_json::to_string_pretty(tasks).unwrap());
}

#[tauri::command]
fn list_tasks(state: State<AppState>) -> Vec<Task> {
    state.0.lock().unwrap().clone()
}

#[tauri::command]
fn add_task(desc: String, state: State<AppState>) -> Vec<Task> {
    let mut tasks = state.0.lock().unwrap();
    let id = tasks.iter().map(|t| t.id).max().unwrap_or(0) + 1;
    tasks.push(Task { id, desc, status: Status::Todo });
    persist(&tasks);
    tasks.clone()
}

#[tauri::command]
fn complete_task(id: u32, state: State<AppState>) -> Vec<Task> {
    let mut tasks = state.0.lock().unwrap();
    if let Some(t) = tasks.iter_mut().find(|t| t.id == id) { t.status = Status::Done; }
    persist(&tasks);
    tasks.clone()
}

#[tauri::command]
fn delete_task(id: u32, state: State<AppState>) -> Vec<Task> {
    let mut tasks = state.0.lock().unwrap();
    tasks.retain(|t| t.id != id);
    persist(&tasks);
    tasks.clone()
}

fn main() {
    tauri::Builder::default()
        .manage(AppState(Mutex::new(load())))
        .invoke_handler(tauri::generate_handler![list_tasks, add_task, complete_task, delete_task])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
