ARC 01 · THE PROBLEM

A Pod's IP address is a lease, not an identity

In chapter 2 you watched a ReplicaSet's reconciliation loop notice a missing replica and create a replacement Pod. Do that experiment again, but this time write down the new Pod's IP address before and after. They are different. Every time. That single fact breaks almost every naive assumption you'd bring from non-orchestrated infrastructure.

A Pod IP in Kubernetes is allocated by the CNI plugin at the moment the Pod's network namespace is created (a one-sentence pointer to the Container Internals course's netns/veth chapter: that's the same shared-network-namespace machinery underneath every Pod — Kubernetes doesn't reinvent it, it schedules on top of it). The IP is returned to the pool the instant the Pod is deleted, for any reason: a node failure, a rolling update replacing old Pods with new ones, the scheduler evicting a low-priority Pod, or simply kubectl delete pod. A ReplicaSet's replacement Pod is a brand-new object with a brand-new IP — Kubernetes never "restarts" a Pod back into its old address.

Unpack what a client needs from a backend fleet and you get three requirements that a bag of ephemeral IPs cannot satisfy on its own:

  • A stable address. Something a client can hold onto for the lifetime of an application, not the lifetime of one Pod.
  • Load distribution. A Deployment with 6 replicas is pointless if every client happens to talk to the same one.
  • Membership that tracks reality. When a Pod dies and a replacement appears, traffic must find the new one and stop being sent to the old one — automatically, within seconds, without redeploying the client.

Kubernetes' answer is the Service: a stable virtual IP address (a ClusterIP) that a component called kube-proxy continuously rewrites into "whichever Pod is alive right now." Everything else in this chapter is deriving why that shape, and exactly how kube-proxy makes a virtual address real.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Every subsystem downstream of this chapter assumes Services exist: Ingress controllers (chapter 10) route HTTP to Services, not Pods; NetworkPolicy (chapter 10) is written against Pod/namespace selectors that Services also use; the Horizontal Pod Autoscaler (chapter 12) changes replica count behind a Service transparently to every client. Get comfortable with "the virtual IP is a lie the kernel tells consistently" now — it's the mental model for the rest of the networking arc.

DEEP CONTEXT · WHY A VIRTUAL IP AT ALL?

Borg's internal naming system (BNS) gave every task a stable name resolved through a naming service, with clients doing their own client-side load balancing against the resolved list. Kubernetes' designers judged that model too demanding for a general-purpose open-source system: it requires every client library, in every language, to implement watch-and-rebalance logic correctly. A kernel-level virtual IP moves that complexity into one place — the node's networking stack — so a plain curl http://my-service just works, with zero client-side awareness that load balancing is happening at all. You pay for that simplicity in kube-proxy's internals, which is the rest of this chapter.

ARC 03 · NAIVE SOLUTION

Attempt #1: script the Pod IPs into a config file

Before accepting that you need a whole new abstraction, try the obvious thing: since kubectl can list every Pod's IP, write a script that polls it and keeps a load balancer's config up to date.

bashsync-pod-ips.sh — the strawman, annotated
#!/usr/bin/env bash
# Poll every 10s, rewrite nginx's upstream block, reload.
while true; do
  ips=$(kubectl get pods -l app=payments -o jsonpath='{.items[*].status.podIP}')
  printf 'upstream payments {\n' > /etc/nginx/upstream.conf
  for ip in $ips; do
    printf '  server %s:8080;\n' "$ip" >> /etc/nginx/upstream.conf
  done
  printf '}\n' >> /etc/nginx/upstream.conf
  nginx -s reload                    # drops in-flight connections on reload!
  sleep 10
done

This is not a joke — it is roughly what people actually did with Consul-template and similar tools before Kubernetes existed, and it gets the shape right: something must watch membership and something must rewrite forwarding state. ARC 04 · WHY IT FAILS

The staleness window is structural, not a tuning bug

Three failures compound, and none of them are fixed by polling faster — they're fixed by not polling at all:

  • The staleness window is bounded below by the poll interval, always. At a 10-second poll, a Pod that dies at t=0 and is replaced at t=1s still has up to 9 seconds where the config points at a dead IP and is missing the new one. Cut the interval to 1 second and you've traded staleness for hammering the API server — with 500 such scripts across a fleet, that's 500 LIST calls/sec against the one component every other control-plane component also depends on (chapter 6).
  • Reload drops connections, and reload frequency now scales with Pod churn. nginx -s reload forks a new master and drains the old one — but "old one" workers keep serving until they finish, so under constant churn you accumulate zombie worker processes, or you reload aggressively and clip in-flight requests. A fleet that reschedules 3 Pods/minute (routine during a rolling update) means a reload every ~20 seconds.
  • Membership is table-stakes, but health is invisible. status.podIP is populated the moment a Pod is scheduled — before the app inside has finished booting. The naive script adds not-yet-ready Pods to rotation immediately, causing a wave of connection-refused errors on every rollout (chapter 15's readiness-probe math is the real fix; a plain poller has no hook for it at all).
THE NUMBERS

Take a Service backed by 20 Pods with a mean Pod lifetime of 4 hours (routine under autoscaling + node rotation). Expected replacement rate: 5/hour ≈ one every 12 minutes. At a 10-second poll that's dozens of 9-second dead-IP windows per day, per client of the script — and every one of those windows is a connection-refused error a real user sees. The fix isn't a faster loop; it's an event-driven membership source (a API server watch, not a poll) feeding a forwarding mechanism that updates in milliseconds, not seconds. That is precisely the Service + kube-proxy design.

ARC 05 · BETTER SOLUTION, EXAMINED

Three candidate shapes for "a stable address that follows live Pods"

Step through the three approaches an architect actually has to choose between, and see why Kubernetes landed where it did.

Choosing a load-balancing shapeSTEP-BY-STEP
THE WINNING SHAPE

A Service object declares a label selector and a virtual IP is allocated for it from a reserved CIDR (commonly 10.96.0.0/12 in kubeadm clusters). A controller in kube-controller-manager continuously watches for Pods matching that selector and maintains an Endpoints (or, since 1.17, EndpointSlice — chapter 10 covers the newer object in depth) object listing their IPs. Every node's kube-proxy watches that object and rewrites local kernel forwarding rules within milliseconds of a change. No polling, no config reload, no dropped connections during a rewrite — because, as §8 shows, the rules are replaced atomically.

ARC 06 · WHY THAT STILL COSTS

A virtual IP solves discovery inside the cluster — and only inside it

Getting kube-proxy's rewrite loop right doesn't make Services free. Three costs are baked into the design and worth naming precisely before you meet the mechanism in §8:

  • ClusterIP only exists inside the cluster's network fabric. It's a forwarding rule programmed into every node's kernel, not a route your office laptop or the public internet knows how to reach. Exposing a Service externally needs a different Service type — NodePort or LoadBalancer — each with its own cost (a port from a fixed, cluster-wide range; a real cloud load balancer with real provisioning latency and real dollars).
  • Every node's kernel carries rules for every Service, whether or not that node runs a matching Pod. kube-proxy doesn't know in advance which node a client Pod will be scheduled on, so it must program identical forwarding rules everywhere. A cluster with 3,000 Services means 3,000 Services' worth of rules on every single node, including ones with zero relevant Pods.
  • The rewrite mechanism itself has a complexity class, and it isn't free at scale. The default mechanism (iptables) evaluates rules in a linear chain per packet. §10 puts real numbers on what that costs as Service count grows into the thousands — and why a second mechanism (IPVS) exists specifically to fix it.
A SERVICE IS NOT AN INGRESS

A common beginner confusion worth killing now: a Service is an L3/L4 (IP/port) abstraction — it knows nothing about HTTP paths, hostnames, or TLS termination. Ten different HTTP APIs behind ten different paths on one domain need one L7 concept sitting in front of Services: an Ingress (or the newer Gateway API), which is itself usually implemented as a Pod running a real reverse proxy (NGINX, Envoy, Traefik) that is, in turn, exposed via — a Service. Ingress is chapter 10's subject; for now, remember the rule: Services balance connections to Pods, Ingress controllers route HTTP requests to Services.

GONE BUT INSTRUCTIVE: THE USERSPACE PROXY

Kubernetes 1.0's original kube-proxy ran in userspace mode: every proxied connection was actually accepted by a Go process and relayed to a Pod — a real extra hop, with the proxy process itself becoming a throughput ceiling and a single point of failure per node. iptables mode (default since 1.2) removed the userspace hop entirely: the kernel's own netfilter engine rewrites packet headers in-place, so kube-proxy's job became "compute the right rules," not "forward the bytes." Every mechanism in this chapter inherits that principle — kube-proxy configures the kernel and gets out of the data path.

ARC 08 · INTERNAL IMPLEMENTATION

The real object shapes, the real chains, the real virtual servers

Four pieces, in order: (a) the API objects as YAML, (b) exactly what iptables mode writes into the kernel, (c) exactly what IPVS mode writes instead, (d) how CoreDNS turns a name into the ClusterIP in the first place.

(a) The API objects

A Service is a thin declaration — selector plus ports. Everything downstream is generated:

yamla ClusterIP Service (the default type)
apiVersion: v1
kind: Service
metadata:
  name: payments
  namespace: orders
spec:
  type: ClusterIP          # default — omit this line and you get the same thing
  selector:
    app: payments        # any Pod with this label becomes a candidate endpoint
  ports:
    - port: 80             # the Service's own port — what clients dial
      targetPort: 8080     # the container's actual listening port
      protocol: TCP

The endpoint controller (in kube-controller-manager) watches for Pods matching selector and whose readiness probe is currently passing (chapter 15), then maintains a companion object with no spec you write by hand:

yamlthe generated Endpoints object (legacy shape, still exists for compatibility)
apiVersion: v1
kind: Endpoints
metadata:
  name: payments             # same name as the Service — that's the binding
subsets:
  - addresses:
      - ip: 10.244.1.12      # ready Pods only
      - ip: 10.244.2.7
    notReadyAddresses:
      - ip: 10.244.3.4       # scheduled, alive, failing readiness — excluded from rotation
    ports:
      - port: 8080

Since 1.17, this is what actually powers kube-proxy — an Endpoints object doesn't scale past a few thousand addresses in one API object, so it's supplemented by sharded EndpointSlice objects (chapter 10 covers the sharding and topology-awareness in full):

yamldiscovery.k8s.io/v1 EndpointSlice — one shard
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: payments-x7q2p
  labels: { kubernetes.io/service-name: payments }
addressType: IPv4
endpoints:
  - addresses: ["10.244.1.12"]
    conditions: { ready: true }
ports:
  - port: 8080

(b) iptables mode: DNAT rules generated per Service, per endpoint

kube-proxy's iptables backend rewrites the kernel's nat table on every relevant change by computing an entirely new rule set and applying it in one atomic call to iptables-restore — never a read-modify-write against live rules, which is exactly what avoids the naive script's reload-drops-connections problem. For the Service above (say ClusterIP 10.96.10.23) with two ready endpoints, the generated rules look like this, faithfully:

iptablesnat table — real chain shape, real trick
# Every packet destined for a ClusterIP:port hits this chain first (reached from PREROUTING/OUTPUT)
-A KUBE-SERVICES -d 10.96.10.23/32 -p tcp -m tcp --dport 80 -j KUBE-SVC-JKA2VXNS7CFMHLNZ

# One chain per Service. Two endpoints ⇒ a "probability chain": each rule fires with
# probability 1/N_remaining, so the OVERALL chance of hitting each endpoint is equal.
-A KUBE-SVC-JKA2VXNS7CFMHLNZ -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-AAAAAAAAAA
-A KUBE-SVC-JKA2VXNS7CFMHLNZ -j KUBE-SEP-BBBBBBBBBB

# One chain per endpoint. DNAT rewrites the destination — after this, the packet is
# indistinguishable from one addressed directly at the Pod.
-A KUBE-SEP-AAAAAAAAAA -p tcp -m tcp -j DNAT --to-destination 10.244.1.12:8080
-A KUBE-SEP-BBBBBBBBBB -p tcp -m tcp -j DNAT --to-destination 10.244.2.7:8080

Two details matter more than they look. First, the chain names are not readable — they're derived from a hash of the Service/endpoint identity, computed once, so kube-proxy can add/remove one endpoint's chain without touching any other's. Second, the "load balancing" here is connection-level, not request-level: the statistic-module dice roll happens once, when a new connection's first packet arrives; every subsequent packet on that same TCP connection follows the same DNAT decision via conntrack, not a fresh coin flip per packet. That single fact explains §11's long-lived-connection incident.

(c) IPVS mode: a real virtual server, not a rule chain

IPVS takes a different approach entirely: instead of a chain kube-proxy has to walk per packet, it creates one virtual server per Service:port, binds every ClusterIP to a dummy interface (kube-ipvs0) so the kernel recognizes the address as local, and looks up the destination via an in-kernel hash table — an O(1) operation regardless of how many Services exist, versus iptables' O(n) linear chain walk. This is exactly what ipvsadm -L -n would show for the same Service:

textipvsadm -L -n — real output shape
IP Virtual Server version 1.2.1 (size=4096)
Prot LocalAddress:Port Scheduler Flags
  -> RemoteAddress:Port           Forward Weight ActiveConn InActConn
TCP  10.96.10.23:80 rr
  -> 10.244.1.12:8080             Masq    1      0          0
  -> 10.244.2.7:8080              Masq    1      0          0

The scheduler field is real and configurable per-cluster via --ipvs-scheduler: rr (round robin — default), lc (least connection — send to whichever real server currently has the fewest active connections), dh/sh (destination/source hashing — pin a given client to the same backend, a cheap approximation of session affinity), sed (shortest expected delay), and nq (never queue). (d) CoreDNS: turning a name into a ClusterIP

None of the above matters until your code has an IP to send packets to. CoreDNS runs as ordinary Pods in kube-system (exposed, for historical compatibility, via a Service still named kube-dns even though the binary is CoreDNS, not the original kube-dns), and every Pod's /etc/resolv.conf is populated by the kubelet to point at it:

text/etc/resolv.conf inside any Pod
nameserver 10.96.0.10
search orders.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

ndots:5 means: if a name has fewer than 5 dots, try each search suffix before treating it as fully qualified — which is why curl http://payments from a Pod in the orders namespace resolves via the search path to payments.orders.svc.cluster.local without you ever typing the long form. ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Where the two mechanisms actually diverge, with numbers

The complexity difference from §8 isn't academic — it shows up as real sync latency and real per-packet cost once a cluster's Service count climbs into the thousands, which is routine for a platform team running many tenants inside one cluster (the same scale envelope this course's ch1 introduced: clusters up to the documented 5,000-node / 150,000-Pod SLO regularly carry Service counts in the thousands).

  • iptables mode: every full resync recomputes the entire rule set and applies it via iptables-restore in one shot — correctness-safe, but the computation and kernel-side load time both scale with total rule count (Services × endpoints). Clusters with several thousand Services have reported full-sync times climbing from milliseconds into tens of seconds, which is precisely the motivation documented in the IPVS proxy mode's original design proposal.
  • IPVS mode: the hash-table VIP lookup itself stays O(1) regardless of Service count, and kube-proxy's IPVS backend only pushes incremental virtual-server/real-server updates rather than a full rule-set rewrite per change — the SIG-network rationale for offering it as an alternative once a cluster outgrows the comfortable range for iptables.
  • Both are governed by a periodic safety-net sync (--iptables-sync-period, default 30s; the IPVS mode has an analogous period) on top of event-driven partial updates — so even a missed watch event self-heals within one sync period, at the cost of that same period being your worst-case propagation delay for a stale rule.
  • conntrack is a shared, finite resource. Every DNAT'd flow gets an entry in the kernel's connection tracking table (net.netfilter.nf_conntrack_max, commonly tens of thousands to a few hundred thousand entries depending on distribution defaults). High-churn, high-fanout UDP traffic — the canonical example is DNS itself — can exhaust it under load, logging nf_conntrack: table full, dropping packet and silently dropping new connections cluster-wide. §11's incidents both trace back to this table.

A SERVICE IS NOT A SECURITY BOUNDARY

kube-proxy's job is pure L3/L4 forwarding — it does not authenticate, authorize, or inspect payloads, and by default any Pod can reach any Service's ClusterIP regardless of namespace. The mechanism that restricts who may talk to whom is NetworkPolicy, enforced by the CNI plugin, not by a Service or kube-proxy at all (chapter 10 covers the default-allow-until-you-opt-in model in depth). Don't reach for Services as an access control tool — they answer "how do I find a Pod," never "who is allowed to."

ARC 11 · REAL-WORLD PRODUCTION

Two incidents you will eventually meet, one you'll meet in depth later

Incident 1: the "5-second DNS lookup" conntrack race

A widely reported, real, and thoroughly documented issue (kubernetes/kubernetes#56903): an application using glibc's default resolver behavior sends its A and AAAA DNS queries as two nearly-simultaneous UDP packets from the same source port. Both get DNAT'd toward CoreDNS by the same kube-proxy rule, and under specific kernel/conntrack timing, the near-simultaneous insertion of two conntrack entries for what the kernel briefly sees as the same 5-tuple can race, causing one query's reply to be dropped. The application then waits out the resolver's full retry timeout — commonly 5 seconds — before the second nameserver or the TCP fallback fires. Fix, in order of leverage: disable parallel A/AAAA lookups where possible (avoid single-request-incompatible resolvers or set the option explicitly), route DNS through the node's local NodeLocal DNSCache (an optional per-node CoreDNS-adjacent cache that removes the DNAT step for DNS entirely), or accept and budget for the tail latency. The root cause is squarely in this chapter: DNS traffic is itself proxied through the same DNAT/conntrack machinery as any other Service.

Incident 2: round-robin doesn't mean what you think for long-lived connections

A team runs a gRPC service behind a ClusterIP with 8 replicas and is confused when, under load, 2 Pods run hot while 6 sit idle. The cause is exactly the mechanism from §8(b): both iptables' probability chain and IPVS's default rr scheduler make their selection decision once per TCP connection, not once per request. gRPC (and any HTTP/2 or persistent-connection client) multiplexes many requests over a small number of long-lived connections — so "round robin" only ever balances the initial handful of connections, and if a client pool opens 2 connections and keeps them alive for hours, exactly 2 of 8 Pods ever see traffic. Fix: either make the client periodically cycle connections, put an L7-aware proxy (a service mesh sidecar, or an Ingress/ gateway that understands HTTP/2 streams) in the path so balancing happens per-request, or switch the IPVS scheduler to lc so at least new connections favor the least-loaded Pod. This is a direct, practical consequence of "Services balance connections, not requests" from §6 — internalize it now, it recurs constantly in production.

Incident 3: CVE-2020-8558 — a preview of chapter 16's incident deep dive

Briefly, because chapter 16 root-causes it in full: kube-proxy's localhost-traffic handling on some kernel configurations allowed traffic that should have been confined to 127.0.0.1 on one node (a Pod's hostPort) to reach the same port on a different node over the cluster network — a martian-packet-style cross-node exposure. It's the right chapter to know exists now, because it lives in exactly the kernel-level forwarding machinery you just learned; chapter 16 walks the exact packet path and the fix that shipped.

Three simplified-but-structurally-faithful walkthroughs. First, the heart of the iptables backend:

gopkg/proxy/iptables/proxier.go — syncProxyRules(), simplified
func (proxier *Proxier) syncProxyRules() {
    // Never mutate live rules in place — build the WHOLE table fresh
    // in memory, then apply it in one atomic call. This is what makes
    // a resync safe to run concurrently with live traffic.
    natRules := newRuleBuffer()

    for _, svc := range proxier.serviceMap {
        svcChain := servicePortChainName(svc)     // KUBE-SVC-
        natRules.Write("-A KUBE-SERVICES -d %s -p %s --dport %d -j %s",
            svc.ClusterIP, svc.Protocol, svc.Port, svcChain)

        endpoints := proxier.endpointsMap[svc.Name]
        for i, ep := range endpoints {
            epChain := servicePortEndpointChainName(svc, ep)  // KUBE-SEP-
            if i < len(endpoints)-1 {
                // The probability trick: P(this endpoint) = 1 / remaining,
                // so the OVERALL chance across all endpoints stays uniform.
                prob := 1.0 / float64(len(endpoints)-i)
                natRules.Write("-A %s -m statistic --mode random --probability %v -j %s",
                    svcChain, prob, epChain)
            } else {
                natRules.Write("-A %s -j %s", svcChain, epChain)  // last one: no dice roll needed
            }
            natRules.Write("-A %s -j DNAT --to-destination %s:%d", epChain, ep.IP, ep.Port)
        }
    }
    iptablesRestore(natRules)   // one atomic replace of the whole nat table
}

        // Bind the ClusterIP to the dummy interface so the kernel treats
        // it as a genuinely local address — this is what makes "ping the
        // ClusterIP" behave differently under IPVS than under iptables.
        proxier.netlinkHandle.EnsureAddressBind(svc.ClusterIP, "kube-ipvs0")

        vs := &VirtualServer{Address: svc.ClusterIP, Port: svc.Port, Scheduler: proxier.scheduler} // e.g. "rr", "lc"
        proxier.ipvs.AddVirtualServer(vs)

        for _, ep := range proxier.endpointsMap[svc.Name] {
            rs := &RealServer{Address: ep.IP, Port: ep.Port, Weight: 1}
            proxier.ipvs.AddRealServer(vs, rs)   // scheduler decides distribution, not kube-proxy
        }
    }
}

Third, how CoreDNS actually answers the query, from a separate codebase entirely:

gocoredns/coredns — plugin/kubernetes/kubernetes.go, simplified
func (k *Kubernetes) ServeDNS(ctx context.Context, w dns.ResponseWriter, r *dns.Msg) (int, error) {
    qname := r.Question[0].Name              // "payments.orders.svc.cluster.local."
    svc, namespace := parseServiceQuery(qname)

    // No etcd round-trip, no API server call per query — this reads a
    // local, informer-maintained cache kept warm by watches (controller.go).
    svcObj := k.svcLister.Get(namespace, svc)
    if svcObj.ClusterIP == "None" {
        return k.answerWithPodIPs(svcObj)   // headless: one A record per ready endpoint
    }
    return k.answerWithClusterIP(svcObj.ClusterIP)
}
WHY BUILT THIS WAY — THREE CHOICES TO STEAL

1. Compute the whole rule set, apply it atomically. Both proxy backends reject incremental read-modify-write against live kernel state — a partial update mid-computation is exactly the class of bug that would intermittently blackhole traffic. Recompute in memory, replace in one call. 2. Never query a remote store on the hot path. Neither kube-proxy nor CoreDNS calls the API server (let alone etcd) per packet or per DNS query — both maintain a local, watch-fed cache and treat the network call as something that happens on change, not on use. 3. Push the decision as low as the kernel will take it. The userspace proxy mode's death and IPVS's rise are the same lesson twice: every layer of Kubernetes networking tries to get out of the data path and let the kernel (or, in eBPF's case, a kernel-verified program) do the actual per-packet work.
