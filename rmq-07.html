RABBITMQ INTERNALS · CHAPTER 07

Streams:
The Log Comes to RabbitMQ

Every queue type this course has covered so far — classic queues (ch. 4), quorum queues (ch. 6) — shares one assumption baked into the word "queue": consuming a message removes it. That assumption is exactly right for task distribution and RPC-shaped work, and it makes three specific workloads either impossible or ruinously expensive: a new consumer replaying history that already happened, fan-out to many independent readers without paying to store N copies, and sustained throughput past what one Erlang process serializing one queue's operations can push. RabbitMQ 3.9 answers all three at once with an idea borrowed openly from Kafka — an immutable, append-only log where consumers hold their own position and reading never mutates storage — built as a new queue type, backed by a standalone library called osiris, and reachable through both the AMQP path you already know and a dedicated binary protocol built for nothing but throughput.

ARC 01 · THE PROBLEM

A buffer that destroys what it delivers cannot replay, fan out cheaply, or outrun one process

Classic queues (ch. 4) and quorum queues (ch. 6) are both, at bottom, destructive, single-pass buffers: a message sits in the queue until some consumer acknowledges it, and once acknowledged it is gone — not archived, not rewindable, gone. That single property, harmless for the task-queue and RPC workloads this course has focused on, quietly rules out three workload shapes that show up constantly in event-driven systems:

  • Replay. A brand-new consumer — a service that just deployed, an analytics job backfilling a report, a bug fix that needs to reprocess yesterday's events — has nothing to read from a destructive queue except whatever hasn't been consumed yet. There is no operation in AMQP 0-9-1's model that says "give me everything published in the last hour, again." The message is either still sitting there unacked, or it is permanently gone.
  • Large fan-out. AMQP's routing model (ch. 3) makes fan-out trivial to declare: bind N queues to one fanout exchange and each gets a full copy of every message. But each of those N queues is its own Erlang process (ch. 4) with its own message-store references and its own queue-index entries — so both storage and the per-publish routing cost (ch. 3's exchange dispatch loop has to reach all N queue processes, not one) scale as O(N). A consumer group of 50 independent readers means 50 fully replicated copies of every message on disk, each governed by whatever durability policy you set on that queue individually.
  • Very high throughput with many independent consumers. Ch. 4 established the ceiling: one queue is one Erlang process serializing every enqueue, dequeue, and ack through its own mailbox. Ch. 6's quorum queues raise that ceiling with batched Raft log appends, but a quorum queue's log still has exactly one leader process appending entries in order — the ceiling moves, it doesn't disappear. Workloads like clickstream ingestion, IoT telemetry, or log aggregation want sustained throughput in the hundreds of thousands of messages per second, read simultaneously by more independent consumers than an O(N)-copies fan-out design could ever afford to keep provisioned.
THE ARITHMETIC THAT MOTIVATES THIS CHAPTER

Take a modest fan-out: 50 independent consumer groups, 1 KB average message size, 10,000 messages/sec sustained. Via N dedicated queues, total write amplification is 50 × 1 KB × 10,000/s ≈ 500 MB/s of duplicated storage traffic before replication factors in — fifty copies of the same bytes, fifty queue indexes to maintain, fifty sets of HA settings to keep consistent. A single shared log storing one copy of the same stream needs only the 10 MB/s the data actually requires; every consumer reads it at its own pace without adding a byte of write traffic. §15's simulator makes this divergence live and clickable.

Kafka's answer to exactly this shape of problem, since its 2011 open-sourcing at LinkedIn, was to stop modeling storage as "destroyed on read": treat a topic-partition as an immutable, append-only log, let consumers track their own read position (an offset) independently of the broker's storage lifecycle, and never mutate the log to serve a read. RabbitMQ 3.9 imports that exact model — same offset semantics, same non-destructive read — as a new native queue type, so it sits behind the AMQP routing topology you already understand instead of requiring a second system next to your broker.

ARC 02 · HISTORICAL CONTEXT

From LinkedIn's activity log to a native RabbitMQ queue type

Streams did not appear in a vacuum — they arrive at the exact moment two separate threads converge: RabbitMQ finally has a real consensus library (ra, ch. 6) to build serious replicated storage on, and the industry has spent a decade proving that an immutable log, not a destructive queue, is the right storage primitive for replay-and-fan-out workloads. DEEP CONTEXT · WHY ONE RELEASE SHIPPED BOTH STREAMS AND A DEPRECATION NOTICE

RabbitMQ 3.9 shipped streams and deprecated mirrored classic queues in the same release — not a scheduling coincidence. Both changes are the same underlying project: give operators a storage model with a real, principled replication story. Quorum queues (3.8, ch. 6) fixed replicated destructive queues by replacing ad hoc mirroring with Raft consensus. Streams fix the workloads destructive queues were never suited to at all, by replacing the destructive-buffer abstraction itself with a log — and, as §6 makes precise, deliberately choosing not to route that log's data path through the same Raft machinery, because a general-purpose consensus protocol is the wrong tool for "just append these bytes, in order, as fast as the disk allows."

ARC 03 · NAIVE SOLUTION

Attempt #1: one dedicated queue per consumer group, provisioned by hand

This is genuinely where every RabbitMQ-literate team starts, because it uses only mechanisms already covered in this course: a fanout (or topic) exchange in front, and one queue per independent readership. When a new consumer group needs "all of it," an operator declares a new queue and binds it. When someone needs history, the workaround is a dedicated, long-retention "audit" queue with a large x-max-length-bytes that gets drained and manually re-published into a fresh queue whenever a new consumer needs to catch up.

pseudocodequeue_per_group.py — the strawman, annotated
class OperatorRunbook:
    # Every time a new team needs "all trade-settlement events," by hand:
    def onboard_new_consumer_group(self, group_name):
        queue = declare_queue(f"settlement.{group_name}", durable=True)
        bind(queue, exchange="settlement.fanout", routing_key="#")
        # starts EMPTY. Anything published before this line is already gone
        # from the group's point of view -- there is nothing to backfill from
        # except the separate audit queue, if it still has it, if it hasn't
        # rolled off its own x-max-length-bytes window.
        return queue

    # "Replay" is a manual, best-effort drain-and-republish against a queue
    # that was never designed to be read twice:
    def best_effort_replay(self, new_queue):
        for msg in peek_without_ack("settlement.audit"):  # fragile: peeking, not consuming
            republish(new_queue, msg)
        # works only for whatever's still inside the audit queue's retention
        # window -- silently incomplete once anything has rolled off

This isn't a strawman built to be knocked down for sport: for two or three long-lived consumer groups that never need history, it is a perfectly reasonable, boring architecture using nothing this course hasn't already justified. ARC 04 · WHY IT FAILS

The math: storage scales as O(N groups), and replay is a lie unless the audit queue happens to still have it

Formalize what the deck just showed. With N independent consumer groups fanned out from one exchange, each needing the full stream of events, this design requires N fully durable, fully replicated queues — and every one of them is provisioned by a human runbook, not derived automatically from the fact that a new reader showed up.

  • Storage grows as O(N), not O(1). 50 consumer groups reading the same logical event stream means 50 independent copies of every message, each with its own queue index (ch. 4) and its own message-store references, each replicated (quorum queue, ch. 6) according to whatever settings that queue was given. Doubling the number of downstream teams doubles broker storage and doubles the exchange's per-publish routing fan-out cost — with zero increase in the amount of information actually being communicated.
  • Replay only ever works by accident. The audit-queue workaround only helps if the specific messages a new consumer needs are still inside that one queue's retention window at the moment someone remembers to drain it. There is no principled "read from offset X" operation anywhere in this design — only "whatever hasn't been consumed or aged out of one specific queue yet," which is not the same guarantee and fails silently the moment retention rolls past what's needed.
  • Onboarding a consumer group is an operational event, not a subscribe call. Every new team needs an operator to declare a queue, bind it, and pick durability/retention settings correctly — get the binding pattern wrong, or forget to make the queue durable, or set x-max-length too small, and the failure is silent until someone notices missing data.
  • The one-process-per-queue throughput ceiling (ch. 4, ch. 6) is completely unaddressed. This design doesn't touch the underlying problem of a single queue process serializing all operations — it just adds more queue processes, which fixes fan-out cost but does nothing for a workload that needs one logical stream to sustain far higher throughput than any single queue (classic or quorum) can push.
THE NUMBERS, MADE CONCRETE

At 10,000 messages/sec average size 1 KB, one queue-per-group design serving 50 groups writes roughly 500 MB/s of broker-side storage traffic for data that, deduplicated, is 10 MB/s. Add replication factor 3 (quorum queues, ch. 6) per group and the true disk write rate is 1.5 GB/s for one logical stream of events. None of that multiplier buys anything except "N teams get a queue" — it buys zero replay capability and zero throughput headroom on the underlying stream itself.

So the fix needs two properties simultaneously, and it's worth separating them the way §1 separated its three failures: (a) storage must stop being duplicated per reader — one physical copy, many independent readers — and (b) reading must stop being destructive, so a reader's position is something it tracks itself, not something the storage layer erases on its behalf. §5 derives exactly that structure.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Fixing the abstraction, not adding more queues

Candidate A: automate queue-per-group provisioning

Script the runbook from §3 — auto-create a queue and binding the moment a new consumer group registers. Genuine operational improvement, and worth doing regardless. But it doesn't touch either failure from §4: total storage still scales O(N), replay is still "whatever's left in the audit queue," and the underlying one-process-per-queue throughput ceiling is untouched. Rejected: automates the toil, leaves the physics unchanged.

Candidate B: run Kafka next to RabbitMQ, bridge the two with a connector

Kafka already solved replay, cheap fan-out, and extreme sustained throughput a decade ago — genuinely the most mature implementation of the log model in the industry, and often the correct operational answer for a green-field, replay-heavy pipeline. But bolting it onto an existing RabbitMQ deployment means running, monitoring, and securing a second distributed system, building and maintaining a bridge/connector process that is itself a new failure point and a new place for messages to be lost or duplicated, and — the part specific to this course — losing AMQP's exchange/binding routing intelligence (ch. 3) in front of the log entirely; Kafka topics don't have topic-exchange-style pattern matching or headers-exchange predicate routing. Rejected as the default answer for teams already standardized on RabbitMQ's routing model — accepted as a real, common choice when a team's needs are Kafka-shaped from day one (§9 returns to this honestly).

Candidate C: make the queue itself non-destructive — an immutable log, inside the broker you already run ✓

Instead of treating "consumed" as "deleted," treat a message as permanently appended once written, and let each consumer track its own read position independently. Nothing about a message changes when it's read; the storage layer for a stream is oblivious to how many consumers exist or where each one currently is. This is precisely Kafka's insight, imported as a queue type behind RabbitMQ's existing exchange/binding routing — so a topic exchange can still filter which events reach which stream, but the stream itself never mutates on read.

There is no point pretending streams are an original idea RabbitMQ invented in isolation — the RabbitMQ team has been explicit that streams are a deliberate import of Kafka's log-and-offset model, built natively into the broker so it can sit behind AMQP 0-9-1 routing instead of requiring a second system. §9 is the honest accounting of what that gets you over actually running Kafka, and what it still doesn't.

ARC 06 · WHY THAT STILL COSTS

The bill for a log wearing a queue's clothing

Making the storage model non-destructive doesn't make it free, and three costs are specific enough to shape how you actually use streams in production:

  • The AMQP 0-9-1 access path pays a real translation tax. A stream, viewed through x-queue-type=stream from an ordinary AMQP client, is made to look like a queue — but underneath, "consume" now means "read forward from an offset," not "pop and delete." The client must set basic.qos prefetch explicitly (an offset-based reader has no natural backpressure signal the way a destructive queue's empty buffer does), and every AMQP frame the client speaks gets translated into the stream's actual offset-read operations by rabbit_stream_queue — CPU and latency spent exclusively on making a log look like a queue for compatibility's sake (§7, §8).
  • A stream is bounded storage, never an infinite archive. Retention is enforced by max-age and/or max-length-bytes, truncated at whole-segment granularity (§8). "Replay from the beginning" only works within whatever window retention has kept — this is not Kafka's occasionally near-infinite tiered storage; it is a broker-local disk budget you set explicitly, and it should be sized the way you'd size any other bounded resource, not treated as a free permanent record.
  • Replication is deliberately simpler than Ra/Raft — and simpler means different guarantees, not just less code. Quorum queues (ch. 6) run every state transition through rabbit_fifo atop the ra Raft library: a write is committed only once a majority of replicas persist it via a full consensus round, with automatic, leaderless-until-elected failover. Streams use their own, much lighter replication protocol — a single writer process appends locally and forwards to followers, acknowledged by a configurable number of replicas, with failover promoting whichever replica has the most complete log — not a general Raft state machine. That's faster for a workload that is 100% sequential appends, but it means the consistency envelope on leader failure is genuinely different from a quorum queue's, and you need to know which one you're relying on (§8 derives exactly why, §9 quantifies the difference).
THE HONEST TRADE

None of this argues against streams — it's the actual price of making "consume" non-destructive without giving up AMQP routing in front of it. A single stream replacing fifty duplicated queues is a dramatic win even paying the AMQP translation tax; for the workloads that need to avoid that tax entirely, RabbitMQ ships a second access path built for nothing else (§7's Stream Protocol). The final architecture, then, needs: a log storage engine that is fast enough to be worth building at all, a queue-type façade so it composes with everything else in this course, and — because "fast enough" here means genuinely fast — its own dedicated binary protocol for clients that don't want AMQP's overhead at all.

DEEP CONTEXT · TWO WAYS IN, ONE LOG

Both access paths ultimately read and write the exact same segment and index files on disk — the difference is entirely in the framing and semantics on the wire. AMQP 0-9-1 clients get compatibility (same channel model, same client libraries, same routing topology as every other queue type in this course) at the cost of per-message protocol translation. Stream Protocol clients get a purpose-built binary frame format — subscribe-with-offset, publish-with-broker-assigned-publishing-id for deduplication, credit-based flow control tuned for a log rather than a destructive buffer — and pay no AMQP tax at all. §9 and §10 quantify the difference; production guidance in §11 gives you the rule of thumb for which to reach for.

ARC 08 · INTERNAL IMPLEMENTATION

Segments, offsets, and a replication protocol that is deliberately not Raft

(a) Storage: segment files plus a sparse index

A stream's on-disk representation is a directory of two file kinds per segment: a segment file (00000000000000000000.log-style, named by its first offset) holding the actual message records back to back — each record a small header (offset, timestamp, entry type, CRC, body length) followed by the body — and a matching index file that does not record every offset's byte position, only a checkpoint every N entries or K bytes. This is the exact same trade Kafka's segment format makes: an exhaustive index would cost nearly as much space as the log itself; a sparse index costs a fraction of that and turns "seek to offset O" into a cheap jump to the nearest checkpoint below O followed by a short linear scan forward — O(log segments) to find the right segment, then O(1) index lookup, then a small bounded scan.

(b) Replication: one writer, several replicas, no Raft log for the data path

Each stream has exactly one osiris writer process (the current leader) accepting publishes, appending them to its own local segment file, and forwarding the same bytes to every osiris replica process on other nodes, which append locally and acknowledge. A publish is confirmed back to the producer once the configured number of replicas have durably appended it — a majority-style acknowledgement discipline, but not a Raft consensus round: there is no leader-election vote, no replicated log of arbitrary state -machine commands, just "write these bytes, in this order, to N places, and tell me when enough of them have it." Who is currently the writer for a given stream is a separate decision, made by rabbit_stream_coordinator — itself a Raft state machine running on ra, the same library quorum queues use — because deciding "which node is leader" cluster-wide is exactly the kind of rare, strongly-consistent decision Raft is built for. The high-volume message data path deliberately never touches that Raft log at all.

THE CONSISTENCY DIFFERENCE, STATED PRECISELY

Because the data path isn't a Raft-replicated log, a writer failure can, in a narrow window, lose the handful of most-recently-appended records that hadn't yet reached the acknowledgement threshold when it died — failover promotes whichever surviving replica has the longest complete log, and any replica with a divergent uncommitted tail truncates to match. Quorum queues, by contrast, only ever expose a write once Raft's own majority-commit rule is satisfied, with a formally specified linearizability guarantee. Streams trade a slice of that guarantee for a replication path fast enough to be worth building — pick the queue type per §9/§11's guidance based on which guarantee your workload actually needs.

(c) The offset model

A consumer attaches to a stream at one of five positions: first (oldest offset retention still has), last (the start of the most recently sealed segment — a fast approximate "near the end"), next (only messages published after this subscribe), a specific numeric offset, or a timestamp (the index is walked to find the nearest offset at-or-after that time). None of these mutate anything — attaching a hundred consumers at first costs nothing extra beyond a hundred independent read cursors over the same bytes.

(d) Server-side offset tracking — without a second topic

Kafka tracks consumer group progress in a dedicated internal __consumer_offsets topic — a second piece of storage, replicated and compacted independently of the data it describes. RabbitMQ's stream protocol instead lets a consumer periodically store its last-processed offset under a name (a "reference"), persisted alongside the stream itself rather than in a separate system, and query it back on reconnect (store_offset / query_offset). Smaller surface area, one less moving part to keep consistent with the stream it describes — the cost is that this tracking lives inside the Stream Protocol rather than being available identically to AMQP 0-9-1 clients, which must track their own offsets application-side if they need resumability across reconnects.

(e) Retention: bounded storage by construction

Retention is governed by max-age (wall-clock) and/or max-length-bytes (total stored bytes), plus stream-max-segment-size-bytes controlling how large a single segment grows before it's sealed and a new one opened. A background reclaim pass deletes the oldest whole segment once the policy is exceeded — truncation never happens mid-segment, only at segment boundaries, which is exactly why segment size is itself a tuning knob: smaller segments mean finer-grained, more frequent reclaim; larger segments mean coarser but cheaper bookkeeping. ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict from the storage model alone

Every property below follows directly from "sequential append, sparse index, consumer-held offsets" — nothing here needs a benchmark to predict the shape of, only the constants:

  • Append is O(1) amortized — a write is a sequential append to the currently-open segment file plus an occasional index checkpoint, the cheapest possible disk access pattern, versus a classic queue's message store plus queue-index bookkeeping (ch. 4) or a quorum queue's per-entry Raft log append (ch. 6).
  • Offset lookup is O(log segments) + O(1) + a small bounded scan — find the right segment by its starting offset (binary search over an ordered, typically small list), consult that segment's sparse index for the nearest checkpoint at or before the target offset, then scan forward a bounded number of records. This is why a stream can serve "subscribe from offset 4,000,000" about as cheaply as "subscribe from the end," a property no destructive queue has any equivalent of.
  • Reads don't compete with writes for the same process's attention the way a classic queue's does. Replica processes serve local reads from their own on-disk copy; a busy consumer group reading from a follower doesn't add load to the writer's mailbox the way registering another consumer on a classic queue process adds work to that one process (ch. 4, ch. 5's credit-flow chapter).
  • Fan-out cost is O(1) in consumer count, not O(N). Storage is written once regardless of how many consumers exist; §1's 50×-duplication math simply doesn't apply once storage is shared rather than per-reader.
  • The Stream Protocol path removes AMQP's per-message framing and channel bookkeeping entirely — RabbitMQ's own published benchmarks put a single stream, driven over the dedicated protocol on suitable multi-core hardware, comfortably an order of magnitude above what a single classic or quorum queue sustains, specifically because there is no channel-level protocol translation left to pay for on that path (§7).

ARC 11 · REAL-WORLD PRODUCTION

Three shapes of story: the benchmark claim, the retention postmortem, the migration

Story 1: the throughput claim streams were built to justify

The RabbitMQ core team has published benchmark results, using the dedicated Stream Protocol against multi-core hardware, showing a single stream sustaining throughput well beyond what a single classic or quorum queue can push — the entire architectural point of §7's second access path. The number that matters for operators isn't the specific benchmark figure (hardware-dependent and always worth re-measuring on your own boxes) but the reason: removing AMQP's per-message channel-level framing and flow control from the hot path, and replacing one queue process's serialized mailbox with sequential-append-plus-replicated-forwarding, changes the shape of the ceiling, not just its height.

Story 2: the retention-misconfiguration postmortem shape

A recurring operational failure mode with streams mirrors one this course already covered for quorum queues (ch. 10 goes deeper on disk alarms generally): an operator sets max-age or max-length-bytes generously — "we might need a week of history" — without accounting for actual publish volume, and disk usage on the stream's nodes grows until disk_free_limit trips a memory/disk alarm that throttles publishers cluster-wide, not just on the stream in question. The fix is boring and specific to this chapter's mechanics: retention is a capacity-planning number, not an aspiration — size max-length-bytes against measured bytes/sec × desired retention window, the same arithmetic §8's segment-and-retention widget lets you play with directly.

Story 3: the fan-out migration this chapter's math predicts

Teams running the queue-per-consumer-group pattern from §3 at real scale — one classic or quorum queue per downstream team off a shared fanout exchange — report exactly the storage and provisioning-toil problem §4 quantified: adding the twentieth or thirtieth consumer group means another fully-replicated queue, another set of durability settings to get right, and still no way to give a new team history that predates their queue's creation. Migrating that fan-out point to a single stream, with each downstream team subscribing at whatever offset (often first, to backfill, then continuing forward) it needs, replaces N duplicated, hand-provisioned queues with one bounded-storage log and a subscribe call — the migration this chapter's arithmetic in §1 and §4 was built to make legible before you attempt it.

Erlangosiris_log.erl — append/2, simplified
append(Log = #{cur_seg := Seg, cur_offset := Offset, bytes_since_ck := B}, Body) ->
    %% Record layout: [offset:8][timestamp:8][type:1][crc:4][size:4][body]
    Record = encode_record(Offset, now_ms(), ?TYPE_SIMPLE, Body),
    :ok = file:write(Seg#seg.fd, Record),

    %% Sparse index: only checkpoint every ?INDEX_INTERVAL bytes, not every
    %% offset -- this is the whole reason seeks stay cheap without an
    %% index nearly as large as the log itself.
    B1 = B + byte_size(Record),
    Log1 = if
        B1 >= ?INDEX_INTERVAL ->
            write_index_entry(Log, Offset, file_position(Seg)),
            Log#{bytes_since_ck => 0};
        true ->
            Log#{bytes_since_ck => B1}
    end,
    maybe_roll_segment(Log1#{cur_offset => Offset + 1}).

Second, the writer process replicating a batch to followers and only confirming once enough of them ack — the piece that is deliberately not a Raft commit round:

Erlangosiris_writer.erl — handle_cast for a publish batch, simplified
handle_cast({publish, Batch, From}, State = #wr{replicas = Reps, acks = AckN}) ->
    %% Append locally first -- the writer's own copy is authoritative
    %% for "did this happen at all," independent of replica speed.
    {ok, State1} = osiris_log:append(State#wr.log, Batch),

    %% Forward the SAME bytes to every replica -- no Raft log entry,
    %% no leader-election vote, just log shipping over an ordinary
    %% Erlang message / TCP frame per replica.
    [ osiris_replica:replicate(R, Batch) || R <- Reps ],

    %% Confirm to the producer once AckN replicas (a configured
    %% threshold, not necessarily a Raft-style strict majority vote)
    %% have durably appended -- track pending confirms by offset.
    State2 = track_pending_confirm(State1, From, AckN),
    {noreply, State2}.

Third, a consumer subscribing at an arbitrary offset — the operation that has no equivalent at all in a destructive queue:

Erlangosiris_log.erl — init_reader/2 (seek to an offset), simplified
init_reader(Log, {offset, TargetOffset}) ->
    %% 1. Find the segment whose [first_offset, next_offset) range
    %%    contains TargetOffset -- binary search over an ordered,
    %%    typically-small list of open segment files.
    Seg = find_segment_for_offset(Log, TargetOffset),

    %% 2. Consult that segment's sparse index for the checkpoint at or
    %%    just before TargetOffset -- O(1) once the segment is known.
    {CkOffset, FilePos} = index_lookup_floor(Seg, TargetOffset),

    %% 3. Scan forward from FilePos, a bounded number of records,
    %%    until reaching TargetOffset exactly.
    scan_forward_to(Seg, FilePos, CkOffset, TargetOffset).
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Pull the log engine out into its own library. Osiris has no RabbitMQ-specific dependency in its core append/read path — it can be (and is) tested, versioned, and reasoned about as "a log," independent of queue-type plumbing, exchanges, or AMQP at all. That separation is what let the team optimize the hot path purely for sequential I/O without AMQP compatibility concerns leaking into it. 2. Keep the data path off the Raft log entirely. Quorum queues need Raft because every operation (enqueue, ack, requeue) is a state transition that must be linearizably ordered and agreed on. A stream's data path is one operation, forever: append. Routing that through a general consensus protocol would spend cycles proving something already true by construction — bytes appended in the order they were sent — so osiris uses the lighter writer/replica log-shipping protocol instead, and reserves Raft (via the coordinator) for the genuinely rare, strongly-consistent decision of who gets to be writer. 3. Make the index sparse on purpose. An exhaustive per-offset index would nearly double storage cost for no benefit past "seek is O(1) instead of O(1)-plus-a-short-scan." Checkpointing every N bytes trades a small, bounded linear scan for a dramatically smaller index file — the same instinct behind B-tree fan-out choices and Kafka's own segment index design.
