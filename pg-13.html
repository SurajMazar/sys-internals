POSTGRESQL INTERNALS · CHAPTER 13

B-Tree Internals:
Lehman & Yao in Production

Every CREATE INDEX you have ever run compiled down to the same data structure: a disk-resident B+-tree descended from Rudolf Bayer and Edward McCreight's 1970s design, made safe for concurrent writers by a 1981 locking protocol from Philip Lehman and S. Bing Yao. This chapter takes nbtree apart page by page — the high key, the right-link, the incomplete split — and shows exactly why a structure that looks like a textbook diagram survives thousands of concurrent inserters without ever locking more than one page at a time.

You will be able toTrace a page split byte-by-byte through nbtinsert.c and nbtsplitloc.c, and say exactly what's on disk before and after.
You will understandWhy a high key and a right-link let a concurrent reader survive a split it raced against — without ever touching the parent's lock.
You will predictFanout and tree depth for any key width and row count, and explain precisely where index bloat comes from.

ARC 01 · THE PROBLEM

Find one row among a billion, in a handful of disk seeks, without stopping the world

Strip away SQL and the problem underneath an index is brutally simple to state and brutally hard to satisfy all at once: given hundreds of millions to billions of key values sitting on a block device, answer "does key K exist, and where" or "give me every row between K1 and K2" while touching as few 8 KB pages as possible, and do it while dozens to thousands of backends are concurrently inserting, deleting, and scanning the same structure — without ever locking the whole thing, or even a large piece of it, for the duration of any single operation.

Three requirements pull in different directions. Boundedness: a lookup must cost a small, predictable number of page reads regardless of table size — O(1) is impossible for an ordered structure, but O(log n) with a large base is the next best thing, and the base is exactly what "fanout" means. Mutability under concurrency: the structure is being inserted into constantly, and an insert that overflows a page must restructure the tree — split a page, possibly cascade upward — while other backends are mid-descent through the very pages being restructured. Crash safety: every mutation must survive an OS crash mid-write, without a multi-page atomic commit primitive to lean on, because none exists at the storage layer — WAL gives you durability of individual records, not atomicity across a page split's several page writes for free.

It is worth being honest about why the obvious data structure — a pointer-chasing binary search tree, one key per node, allocated wherever malloc feels like putting it — is not a scaled-down version of the right answer but a categorically wrong shape for disk. A balanced binary tree over a billion keys is roughly 30 levels deep (log₂ 10⁹ ≈ 30). Each level is a pointer chase to a essentially random location, and on a device where a random read costs a seek (even an NVMe SSD's random-read latency is measured in tens of microseconds versus nanoseconds for a cache hit), thirty dependent random reads per lookup is not a database anyone would use. The fix is not a smarter binary tree — it's rejecting "one key per node" entirely and asking: what if a node were exactly one disk page, holding hundreds of keys, so that fanning out wide collapses the depth from 30 to 3 or 4? That single idea — pack many keys into one page-sized node — is the entire reason B-trees exist, and everything else in this chapter is about making that idea survive concurrent writers and power failures.

WHY THIS MATTERS FOR THE NEXT 8 CHAPTERS

nbtree (src/backend/access/nbtree/) is PostgreSQL's default and by far most heavily used index access method — every primary key, every unique constraint, most foreign keys, and most ad-hoc CREATE INDEX statements land here. Chapter 14 covers the access methods nbtree cannot serve well — full text, geometry, arrays, low-cardinality columns — and every one of those chapters is really an argument of the form "here is a query shape where a single total order over one key domain, which is all a B-tree gives you, stops being enough." Understanding nbtree precisely is what makes GIN, GiST, SP-GiST, and BRIN legible as engineering trade-offs rather than a zoo of acronyms.

DEEP CONTEXT · WHY "B" AND WHY IT'S NOT REALLY A BINARY TREE

Bayer and McCreight never stated what "B" stands for — Boeing (their employer at the time), balanced, and broad have all been offered — but the structure itself answers the question this chapter opened with: a self-balancing tree where each node holds many keys and has many children, sized so that one node fits exactly one page of secondary storage. What PostgreSQL and almost every production database actually implement is a B+-tree: all row-referencing data lives in leaf pages, internal pages hold only navigation keys (downlinks), and leaves are threaded together in a linked list for cheap ordered range scans without ever revisiting internal pages. The plain "B-tree" (data in internal nodes too) is mostly a teaching artifact today; nbtree's own source comments and README call it a B+-tree throughout, and this chapter does the same.

ARC 03 · NAIVE SOLUTION

Attempt #1: lock the whole path before you touch anything

Once you accept "many keys per page, tree of pages" as the shape, the next question is purely about concurrency: how do you keep a page split safe when other backends might be reading or writing the very pages you're restructuring? The textbook answer — the one every algorithms course teaches, and the one that is correct if you don't care about throughput — is conservative lock-coupling ("crabbing") root to leaf: acquire an exclusive lock on the root, then the child, then release the root only once the child is locked, and repeat all the way to the target leaf, holding every lock on the path until the whole operation — including any split it might trigger — is completely finished.

pseudocodenaive_btree_insert() — the strawman, annotated
naive_insert(tree, key, tid)
{
    lock_exclusive(tree.root);              // nobody else may even READ past here
    page = tree.root;
    path = [page];

    while (!page.is_leaf) {
        child = choose_child(page, key);
        lock_exclusive(child);              // hold parent AND child at once
        path.push(child);
        page = child;                          // parent lock released only once we're sure
                                                // this subtree won't need to split upward
    }

    if (page.num_keys < MAX_KEYS) {
        insert_sorted(page, key, tid);
        unlock_all(path);                   // common case: fast
        return;
    }

    // page is full: must split, and the split might cascade all
    // the way to a NEW root -- so every page on `path` stays
    // exclusively locked until the whole cascade resolves
    split_and_propagate(path, key, tid);
    unlock_all(path);
}

This is not a strawman in the sense of being silly — it is exactly what you'd derive from "make every multi-page mutation atomic by holding every lock it might need, for as long as it might need it." It is trivially correct: no reader can ever observe a half-split tree, because no reader can get past a locked ancestor. Every database course presents it first for the same reason PostgreSQL's own README for nbtree presents the same derivation before explaining why production code abandons it.

ARC 04 · WHY IT FAILS

The upper levels are shared by everyone, and lock-coupling locks them for a split's whole duration

To see why crabbing is a throughput catastrophe, you first need the fanout number, because the whole argument hinges on how few upper-level pages there are relative to how many backends touch them. Derive it: an 8 KB PostgreSQL page has a page header (~24 bytes) and, in nbtree specifically, a trailing BTPageOpaqueData "special space" (~16 bytes) that every page pays regardless of level. An index tuple holding, say, an 8-byte bigint key needs roughly 8 bytes for the heap TID plus a handful of bytes of item-pointer/tuple-header overhead — call the whole entry ~24 bytes. nbtree's default fillfactor for non-rightmost pages targets ~90% occupancy, leaving deliberate slack for a few more inserts before the next split. With the default 8-byte bigint key at 90% fill, fanout lands around 300 entries per page. That means the level immediately below the root already holds enough downlinks to address 300² ≈ 90,000 leaf pages, and the level below that addresses 300³ ≈ 27 million leaves — at roughly 300 rows per leaf, a 3-level tree (root + 1 internal level + leaves) already spans on the order of 8 billion rows. In practice you will see 3 to 4 levels for tables from the hundreds of millions into the low billions of rows — which is exactly the number of page accesses a point lookup costs, and it is small because fanout is large.

Now invert that fact and it becomes the argument against crabbing: a tree with only 3–4 levels has, by construction, only a handful of pages at the root and near-root levels — maybe one root page and a few dozen level-1 pages for a billion-row table. Every single insert into every part of that table passes through the same tiny set of upper pages. Lock-coupling holds an exclusive lock on the root (and likely the level-1 page) for the entire duration of a possible cascading split — which is not "acquire, check, release" but "acquire, walk to the leaf, insert, discover the leaf is full, split it, write the new page, insert a downlink into the parent, discover the parent might also be full, possibly repeat, possibly allocate a new root" — a sequence of several page writes' worth of work, all while the very small set of upper pages that every other backend in the system also needs sit exclusively locked. With a few hundred concurrent inserters, the root and its immediate children become a single point of serialization for the entire table, and the fact that splits are rare per-backend (each leaf holds hundreds of rows before splitting) doesn't help — with enough concurrent writers, some split is almost always in flight somewhere, and every one of them holds the same shared ancestor hostage for its full duration.

THE NUMBERS

If a cascading split (leaf split + parent update + occasional grandparent split) takes on the order of a few hundred microseconds to a low single-digit millisecond of critical-section work — several page copies, WAL records, and pointer rewrites — and even 1% of your insert traffic triggers one, then at 10,000 inserts/sec roughly 100/sec need the root's lock for that duration. Every other insert in the system queues behind whichever one got there first. This is not a corner case reached only under pathological load — it is the structural consequence of "few pages control all descents," and it is why every production B-tree implementation abandons naive crabbing.

ARC 05 · BETTER SOLUTION, EXAMINED

Three candidates for "don't hold the parent hostage" — Lehman & Yao win

Step through the three real candidates the literature and production systems actually tried, in the order they get eliminated:

Locking strategies, eliminated one by oneSTEP-BY-STEP

The winning idea, from Philip Lehman and S. Bing Yao's 1981 paper "Efficient Locking for Concurrent Operations on B-Trees," is to change what a page promises rather than how long you lock it. Give every page two extra pieces of information, kept in the page's own special space: a high key — a value that is a guaranteed upper bound on every key the page can ever contain — and a right-link — a pointer to the page's right sibling at the same level. With those two fields, a page split can be decomposed into two independent, separately atomic steps instead of one giant multi-page transaction: step one splits the page and wires the new right sibling's high-key and right-link (this alone leaves the tree fully correct and fully searchable, just via one extra hop); step two, which can happen any time later, inserts the downlink into the parent so future descents find the new page directly. A reader who arrives mid-way — after step one but before step two — lands on the old (left) page exactly where the parent still sends it, notices its search key exceeds the page's high key, and simply follows the right-link one page over. No parent lock was ever needed for that reader to get the right answer.

ARC 06 · WHY THAT STILL COSTS

Lehman & Yao is lock-COUPLING-free, not lock-free — and deletes don't get the same trick

Be precise about what was bought and what wasn't. This protocol never holds two page latches at once during a normal descent — that is the entire throughput win, and it is real. It is not a lock-free algorithm in the general sense: every page you touch is still latched (in PostgreSQL terms, a buffer content lock) for the brief instant you read or modify it. "Only one page latched at a time" is the correct mental model, not "no locking happens."

Three costs remain, and nbtree's design accepts all three deliberately rather than fighting them:

  • A reader may have to move right more than once. If several splits happen on the same level while a search is in flight, the search simply follows the right-link chain as many hops as necessary. This is rare — it requires multiple concurrent splits at the exact level and moment a particular search is passing through — but the protocol has to tolerate it, and does, by making the "is my key past this page's high key?" check a loop, not a single branch.
  • An incomplete split must be detected and repaired lazily, not assumed impossible. Because step one (split + wire the right sibling) and step two (insert the parent downlink) are separate atomic actions, a crash — or simply the backend not getting scheduled again for a while — between them leaves the tree in a state where the new right page is reachable only via the right-link, not via top-down descent from the parent. This is not corruption; the design's entire point is that this state is safe to leave lying around indefinitely and to repair opportunistically the next time anyone's descent walks through it.
  • Deletes don't get a symmetric "split into two atomic steps" trick, so nbtree mostly doesn't merge pages at all. Merging two sparse siblings back together safely, under a protocol built around concurrent top-down descent and right-links, requires coordinating the merge with every backend that might currently hold a reference to either page or be mid-traversal through the parent's downlink to them — a substantially harder problem than a split, which only ever adds structure and never has to invalidate someone's in-flight right-link chase. nbtree's answer is to not attempt it as routine maintenance: deleted entries are removed from their page, but a half-empty leaf simply stays half-empty, and space reclamation across whole pages is deferred to normal vacuum's page-deletion path (conservative, and rare) or, in the worst case, a full REINDEX.
THE HONEST TRADE

Lehman & Yao trade a small, bounded amount of extra work on the read path (occasionally move right, and pay for high-key/right-link bookkeeping on every page) for eliminating the single worst throughput problem a disk-backed B-tree can have: serializing all writers behind the few pages everyone shares. The bill comes due somewhere else — index bloat from unmerged, sparsely-populated pages — and §11 walks through what that bill looks like in production and how it gets paid down.

ARC 07 · FINAL ARCHITECTURE

The nbtree page layout, end to end

Every nbtree page — meta, internal, or leaf — is one 8 KB buffer with the same generic PostgreSQL page header, a body of item pointers and tuples, and a trailing access-method-specific "special space." For nbtree that special space is a BTPageOpaqueData struct, and almost everything this chapter has discussed so far — the high key, the right-link, the level — lives in fields of that one struct. WHY THE META PAGE EXISTS AT ALL

If the root were always block 0, every root split would force a rewrite of block 0 — awkward, and it would make block 0 itself a hot, contended page. Instead nbtree reserves block 0 permanently as a small meta page that simply points at wherever the current root actually lives, plus a cached "fast root" — the topmost page known not to need traversal from the true root for common cases — so that root changes are a single small update to a page nobody else contends over, not a rewrite of a well-known, heavily-cached block.

ARC 08 · INTERNAL IMPLEMENTATION

Anatomy of a page split, field by field

BTPageOpaqueData (src/include/access/nbtree.h) is small and every field earns its place: btpo_prev and btpo_next are the block numbers of the left and right siblings at the same level — leaf pages are threaded as a doubly-linked list, which is what makes backward index scans (ORDER BY x DESC using a forward-built index) possible without re-descending the tree; btpo_level is the page's height above the leaf level (0 for leaves, incrementing upward), used so a page can tell, purely from its own header, whether it's a leaf without consulting anything else; and btpo_flags carries bits like P_LEAF, P_ROOT, and P_META. The high key itself is not a separate field — it is stored as an ordinary-looking index tuple at item offset 1 (P_HIKEY) on every non-rightmost page, which is why "does this page have a high key" is really "is this the rightmost page at its level," tested via a flag rather than a null check.

Three refinements sit on top of that mechanism, each shipped in a specific release, each attacking a different cost:

Suffix truncation of pivot tuples (PG11). A downlink's only job is to be an upper bound that correctly routes a search toward the left or right child — it does not need to be a real, full copy of any row's key. If the last key on the left page is ('smith','alice',102) and the first key on the new right page is ('smith','bob',7), a downlink of ('smith','bob') — dropping the trailing column — is just as correct a separator and several bytes smaller. Doing this on every internal downlink increases how many downlinks fit per internal page, which directly increases fanout at the internal levels — precisely the number this chapter has been computing throughout §4, §8, and §10.

Deduplication with posting lists (PG13). Low-cardinality or heavily-duplicated key columns used to cost one full index tuple per row even when thousands of rows shared the same key. nbtdedup.c's _bt_dedup_pass() opportunistically merges adjacent, identical-key tuples on a leaf page into one logical entry: the key is stored once, followed by a compact list of the heap TIDs that share it (a posting list). This shrinks the on-disk index substantially for duplicate-heavy columns and reduces how often such leaves need to split, at the cost of a small amount of extra CPU to expand a posting list during a lookup and slightly more bookkeeping to keep it MVCC-correct.

Bottom-up index deletion (PG14). Before PG14, a non-HOT update — one that changes an indexed column, or can't reuse space on the same heap page — always adds a brand-new index entry for the new row version, and the old entry becomes dead only once no snapshot can see it. On an update-heavy table this meant leaves accumulated dead duplicate-key entries continuously, forcing splits that vacuum would only clean up much later. Since PG14, before splitting a full leaf, nbtree first makes an opportunistic pass over the page: it checks whether any of the existing entries for the incoming key are now dead by visibility rules (a check against the heap, similar in spirit to what vacuum does, but done inline, synchronously, by the inserting backend) and reclaims that space first. Often that alone is enough room, and the split never has to happen at all — turning "every hot-update creates permanent bloat until the next vacuum" into "bloat is often cleaned up by the very insert that would have caused it."

Notice the fast path nbtsplitloc.c takes for the common case of an ever-increasing key (a serial/identity primary key, or any monotonically inserted timestamp): if the page being split is the rightmost page at its level and the incoming key is larger than everything already on it, there is no reason to search for a balanced 50/50 split point — the algorithm instead does a heavily lopsided split, packing nearly all existing keys onto the left page and putting just the new key (or a small handful) onto the right. This keeps sequentially-inserted data tightly packed at close to 100% fill instead of the usual 90% target, deferring the next split as long as possible — exactly the pattern you will exercise in §15's simulator.

Index-only scans depend on one more piece of state that lives outside nbtree entirely: the visibility map. An index-only scan can return a row using only the index tuple — skipping the heap fetch entirely — only when the heap page that row lives on is marked all-visible in the visibility map (chapter 12). If it isn't, the scan must still fetch the heap page to check MVCC visibility, which erases the whole point of reading the index alone. A table under constant modification, whose visibility map never catches up, gets zero benefit from index-only scans no matter how well-tuned the index itself is.

ARC 09 · TRADEOFFS

Every serious engine faced this exact fork — the answers differ by workload assumption

Lay nbtree next to the three other structures a senior engineer will actually be asked to compare it against. The pattern to notice: every system either update-in-place (accepting split/merge/lock complexity now, in exchange for read-optimized steady state) or defers writes into an append-friendly structure (accepting compaction cost later, in exchange for write-optimized ingest).

SYSTEMSTRUCTUREWHAT THEY BOUGHTWHAT THEY PAID
PostgreSQL nbtreeB+-tree, Lehman-Yao concurrent descent, heap+index MVCC 1 page latched at a time stable low-ms point lookups mature range scans no page merge on delete index bloat between REINDEXes
MySQL / InnoDBClustered B+-tree — the primary key IS the leaf row; secondary indexes store the PK, not a heap TID PK lookups need only the index good locality for PK-ordered scans every secondary index lookup pays a second traversal by PK PK choice materially affects every other index's size
LSM-tree (RocksDB / Cassandra)Sorted immutable SSTables + in-memory memtable; merges deferred to background compaction sequential, batched writes — excellent write throughput no in-place update locking read amplification — may check memtable + many SSTable levels write amplification from repeated compaction

Read the InnoDB row carefully — it is the comparison senior engineers most often get wrong. Because InnoDB's primary key clusters the actual row data at the leaf, a lookup by primary key is a single traversal, no second hop needed — genuinely better than nbtree's heap+index split for that one access pattern. But every secondary index in InnoDB stores the primary key value, not a physical row pointer, so a query through a secondary index needs a second B+-tree traversal, by primary key, to fetch the row — and a wide or frequently-changing primary key inflates every secondary index's size and every non-PK query's cost. PostgreSQL's heap-plus-index design (a physical TID in every index, MVCC handled by storing new row versions rather than updating in place) avoids that particular multiplier, at the cost of needing a heap fetch (or a visibility-map hit for index-only scans) on almost every read.

The LSM comparison is the one that matters most for capacity planning: nbtree's cost is paid steadily, a little on every insert (occasional split) and a little on every read (occasionally move right, or read a slightly-stale-fill leaf); an LSM-tree's cost is paid in two very different currencies — writes are nearly free (append to a memtable, flush sequentially) but reads may have to check several levels of sorted files, and a background compaction process continuously rewrites data to keep that read cost bounded, competing for the same disk bandwidth as foreground traffic. For latency-sensitive, mixed-read-write OLTP — the workload PostgreSQL is built for — a bounded, predictable few-page read cost every time beats a write path so cheap that its true cost shows up later, unpredictably, as a compaction storm.

ARC 10 · PERFORMANCE CHARACTERISTICS

O(log_fanout n), and where the actual disk seeks concentrate

A point lookup or insert costs O(log_fanout n) page accesses — one per tree level, root to leaf. With the fanout numbers from §4 (roughly 200–400 for typical key widths at typical fill factors), that logarithm is base-300-ish, not base-2: fanout^depth ≥ n rearranges to depth ≥ log(n) / log(fanout), and plugging in n = 10⁹ and fanout = 300 gives depth ≈ 3.6, rounding up to 4 levels — 4 page accesses for a point lookup on a billion-row table, regardless of whether that table has 10⁸ or 3×10⁸ rows, because the logarithm barely moves. This is the entire promise of a wide-fanout tree: enormous changes in row count produce tiny changes in depth.

Cache behavior compounds the win. The root is one page and near-root pages number in the dozens — that whole set is read constantly by every backend and essentially never evicted from shared_buffers (or, if it is, from the OS page cache immediately behind it). In steady state, real physical disk seeks concentrate almost entirely in the bottom one or two levels — the leaf level and perhaps its immediate parent — because that's where the working set is too large to stay fully cached. A "4-level tree" therefore rarely costs 4 real I/Os; it typically costs 1–2, with the upper levels served from memory essentially for free.

The I/O pattern, not just the count, also depends heavily on insertion order. A fresh index build (CREATE INDEX or the bulk-load path) processes pre-sorted data and writes leaf pages sequentially, left to right, once — close to ideal sequential I/O, and the reason a bulk CREATE INDEX after a large load is usually dramatically faster than the equivalent stream of individual inserts. Steady-state random-order inserts — the common case for, say, a UUID primary key — cause splits scattered arbitrarily across the file as different, unrelated leaf pages independently fill up and split, turning what could have been sequential writes into scattered ones and fragmenting logically-adjacent keys across physically distant pages.

MODEL, NOT MEASUREMENT

The fanout/depth formula here is a simplified accounting — real IndexTuple overhead varies with alignment, null bitmaps, and TOAST considerations, and nbtree enforces a hard floor of a few tuples per page regardless of what the formula says. The point is the shape: depth grows logarithmically and fanout is the base, so the single highest-leverage number in this whole chapter is "how many bytes does one index entry cost," because it appears inside a logarithm's base, not its argument.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents every operator eventually meets

Incident 1: the index that outgrew its table

A frequently-updated table on PG13 or earlier — say, an orders table with a status column that flips several times per row's life, indexed for dashboard queries — develops an index measurably larger than the table itself, with pg_stat_user_indexes showing a huge ratio of index size to live tuple count. Root cause: every status-changing update is non-HOT (it touches an indexed column), so pre-PG14 it always adds a new index entry, and the old entry only becomes reclaimable once no transaction's snapshot can still see it — under sustained update load and any lingering open transactions, dead entries accumulate faster than autovacuum reclaims them, forcing continual leaf splits that never shrink back. Fixes: upgrading to PG14+ gets bottom-up index deletion, which opportunistically reclaims dead duplicate-key entries before splitting rather than after; as an immediate stopgap on an older version, REINDEX CONCURRENTLY rebuilds the index at its true, compact size without an exclusive lock for the bulk of the work.

Incident 2: hot-page contention on a monotonic bigint primary key

A high-throughput ingest table with a plain ascending bigserial or identity primary key shows unexpectedly poor insert scalability under heavy concurrency — throughput plateaus well below what the hardware should sustain, and wait-event sampling shows backends piling up on buffer content locks for the same handful of blocks. Root cause: every concurrent inserter is targeting the same rightmost leaf page (and its ancestors) at the same moment, because the key is strictly increasing — this is the honest, unavoidable flip side of the "pack sequential keys tightly" fast path from §8: the very same-page locality that keeps the index small and cache-friendly also means every writer contends for the same page. The other side of this trade-off, told fairly: switching to a random key (a UUID, or a hashed identifier) spreads inserts across many leaf pages and eliminates the hot-page contention — but now every insert likely touches a leaf page that isn't in cache, splits happen scattered across the whole file instead of packed at the tail, and the index becomes larger and more fragmented, with worse range-scan locality. Mitigations that keep the ascending key: partitioning by a coarser time bucket so writers spread across several "rightmost" pages (one per active partition) instead of one; or accepting the contention and reducing its blast radius via connection/queue concurrency limits at the application tier.

Incident 3: index bloat pinned by a long-running transaction

A reporting query or an idle-in-transaction session left open for hours holds back the xmin horizon discussed in chapter 12 — and because nbtree cannot reclaim a dead index entry until no snapshot needs the old version, every update or delete against that table during those hours leaves unreclaimable dead entries behind. Once the long transaction finally ends, autovacuum can clean up the heap, but the index pages that split under the bloat pressure don't shrink back down on their own — nbtree, as established in §6, essentially never merges pages. Fix: hunt down and terminate the long-running transaction (pg_stat_activity, xact_start), then run REINDEX CONCURRENTLY to reclaim the bloated space. REINDEX CONCURRENTLY's mechanism is itself worth knowing precisely: it builds an entirely new index from a fresh scan of the table while the old index continues serving reads and writes, briefly takes a stronger lock only to validate the new index against concurrent changes made during the build and to swap it in as the table's active index, then drops the old one — avoiding the exclusive table lock a plain REINDEX would require for the entire rebuild.

├── ● nbtpage.c — _bt_split(), _bt_newroot(): page allocation, high-key/right-link wiring, meta-page updates, page deletion
├── ● nbtsearch.c — _bt_search(), _bt_moveright(): the Lehman-Yao descent loop itself
├── nbtdedup.c — _bt_dedup_pass(): posting-list creation and maintenance (PG13)
├── nbtutils.c — key comparison, pivot/suffix-truncation helpers
└── nbtxlog.c — WAL redo routines: how each of the above replays after a crash

Three simplified-but-structurally-faithful functions, in the order a real insert calls them. First, the overflow check that decides whether a split is needed:

Cnbtinsert.c — _bt_insertonpg(), simplified
void
_bt_insertonpg(Relation rel, Buffer buf, BTStack stack,
                IndexTuple itup, OffsetNumber newitemoff)
{
    Page page = BufferGetPage(buf);
    BTPageOpaque opaque = BTPageGetOpaque(page);

    /* Does the new tuple fit in the page's remaining free space? */
    if (PageGetFreeSpace(page) < IndexTupleSize(itup))
    {
        /* No room: split first, THEN insert into whichever half
         * the new tuple now belongs on. One buffer content lock
         * held at a time -- this is the only page latched right
         * now, per Lehman & Yao.                                  */
        Buffer rbuf = _bt_split(rel, buf, stack, newitemoff, itup);
        return;
    }

    /* Common case: room exists. Insert in sorted position and
     * WAL-log this single page's change -- no other page is
     * touched, so this is trivially atomic.                      */
    PageAddItem(page, (Item) itup, IndexTupleSize(itup),
                 newitemoff, false, false);
    MarkBufferDirty(buf);
    XLogInsert(RM_BTREE_ID, XLOG_BTREE_INSERT_LEAF);
}
Cnbtpage.c — _bt_split(), simplified
Buffer
_bt_split(Relation rel, Buffer lbuf, BTStack stack,
          OffsetNumber newitemoff, IndexTuple newitem)
{
    Page lpage = BufferGetPage(lbuf);
    BTPageOpaque lopaque = BTPageGetOpaque(lpage);

    /* nbtsplitloc.c decides WHERE to cut: 50/50 by default, or a
     * lopsided cut that packs the left page nearly full when this
     * is the rightmost page and the new key is the largest yet.  */
    OffsetNumber firstright = _bt_findsplitloc(rel, lpage, newitemoff, newitem);

    Buffer rbuf = _bt_getbuf(rel, P_NEW, BT_WRITE);
    Page rpage = BufferGetPage(rbuf);
    BTPageOpaque ropaque = BTPageGetOpaque(rpage);

    /* Move the upper half of lpage's tuples onto the new right
     * page. The FIRST tuple that lands on the right page becomes
     * (suffix-truncated, since PG11) the new page's high key AND
     * the eventual downlink value for the parent.                */
    _bt_moveitems(lpage, rpage, firstright, newitem, newitemoff);

    /* Wire the special space: this is the ENTIRE atomic step.
     * After this WAL record commits, the tree is fully correct
     * and fully searchable -- the parent just doesn't know yet.  */
    ropaque->btpo_prev  = BufferGetBlockNumber(lbuf);
    ropaque->btpo_next  = lopaque->btpo_next;    /* inherit old right sibling */
    ropaque->btpo_level = lopaque->btpo_level;
    lopaque->btpo_next  = BufferGetBlockNumber(rbuf);

    MarkBufferDirty(lbuf); MarkBufferDirty(rbuf);
    XLogInsert(RM_BTREE_ID, XLOG_BTREE_SPLIT_L);

    /* Insert the downlink into the parent -- a SEPARATE action.
     * If the parent is also full, this recurses upward, possibly
     * all the way to _bt_newroot(). A crash right here leaves an
     * "incomplete split": rbuf is fully valid and reachable via
     * the right-link, just not yet reachable top-down. §8 walks
     * exactly this window; _bt_moveright() below is how a later
     * descent finds and repairs it.                              */
    _bt_insert_parent(rel, lbuf, rbuf, stack);
    return rbuf;
}
Cnbtsearch.c — _bt_moveright(), simplified
Buffer
_bt_moveright(Relation rel, Buffer buf, ScanKey key)
{
    Page page = BufferGetPage(buf);
    BTPageOpaque opaque = BTPageGetOpaque(page);

    /* The Lehman & Yao core loop: as long as this page has a real
     * high key (isn't the rightmost page) AND our search key is
     * >= that high key, our target -- or the rest of our range --
     * lives further right, possibly because of a split we raced
     * against. Step right and re-check. No parent lock is ever
     * consulted to make this decision.                           */
    while (!P_RIGHTMOST(opaque) &&
           _bt_compare(rel, key, page, P_HIKEY) >= 0)
    {
        BlockNumber rightblk = opaque->btpo_next;
        _bt_relbuf(rel, buf);              /* release old page's latch FIRST */
        buf = _bt_getbuf(rel, rightblk, BT_READ); /* then latch the sibling */
        page = BufferGetPage(buf);
        opaque = BTPageGetOpaque(page);
        /* This loop is exactly what makes an incomplete split safe:
         * whether or not the parent has been updated yet, this
         * page's high-key and right-link are already correct. */
    }
    return buf;
}
WHY THE DEVELOPERS WROTE IT THIS WAY

Incomplete-split repair beats multi-page atomic WAL. Making a split-plus-parent-update atomic across two non-adjacent pages would need a WAL scheme that can roll forward or back a multi-page transaction as one unit — real engineering effort, and a permanent tax on every split's WAL volume. Lehman & Yao's insight makes that unnecessary: each of the two steps is independently correct and independently WAL-logged as an ordinary single/dual-page action, and the "incomplete" state in between is not a bug to prevent but a valid state to tolerate, repaired for free the next time any backend's ordinary descent walks through it via _bt_moveright(). Conservative page-deletion beats aggressive merging. A merge has to prove no concurrent descender holds a stale reference to either page being merged — under a protocol explicitly designed to let descenders proceed without parent locks, that proof is expensive to construct correctly. Leaving pages sparse and reclaiming them later, off the hot path, via vacuum or REINDEX, trades a small amount of space efficiency for never having to reason about merge-safety under concurrent descent at all.
