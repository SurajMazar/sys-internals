Advanced Security:
KMS, Secrets Manager & Automated Response

Professional-level security questions rarely ask "what does KMS do." They hand you a scenario — a cross-account decryption failure, a hardcoded credential, an unactioned threat finding — and ask which service, which policy layer, and which automation actually closes the gap. This chapter builds the exact mental model SAP-C02 tests: envelope encryption's real mechanics, the two-policy gate every KMS key enforces, the rotation story for secrets vs. config, and the finding → response pipeline that turns detection into remediation.

ARC 02 · THE COMMON WRONG INSTINCT

"I gave the role full IAM access to the key — why is decryption still denied?"

Here is the trap almost everyone falls into on their first KMS scenario, and it is a genuinely reasonable instinct: for nearly every AWS resource, IAM is the only access-control gate that matters. Attach an Allow: kms:Decrypt statement on a role, and for most services that's the whole story. Candidates carry that instinct straight into KMS and get baffled by an AccessDeniedException despite a seemingly correct IAM policy.

The second, related wrong instinct: "Secrets Manager and Parameter Store do the same job, so I'll just use whichever is cheaper" — treating Parameter Store's lower price as the deciding factor for a database credential that needs periodic rotation, when rotation support is the actual requirement the scenario is testing.

THE INSTINCT, STATED PLAINLY

"KMS keys are just another IAM-governed resource — grant the permission on the principal's policy and move on." "Parameter Store can store a secret string too, and it's cheaper, so use it for credentials." Both statements are half-true, which is exactly what makes them exam traps: they work often enough in casual use to feel correct, and fail precisely on the scenario detail the question is testing.

ARC 03 · WHY IT'S WRONG

KMS keys enforce a second, mandatory gate — and rotation isn't a feature toggle

KMS is the one AWS service where a resource-based policy — the key policy — is not optional decoration on top of IAM. Every KMS key has a key policy, and unless that key policy explicitly delegates authority to IAM (via the well-known statement that allows arn:aws:iam::<account>:root, which practically every AWS-created default key policy includes), IAM policies alone cannot grant access to that key, no matter how permissive they are. Both the key policy AND an IAM/grant-based permission must allow the action — it is a logical AND, not an OR, and not "either one is enough." A candidate who only ever edits IAM policies and never touches a key policy will eventually hit a wall the moment someone locks down a key policy for a compliance reason, and "give the role more IAM permissions" simply will not fix it.

The Parameter Store instinct fails for a more concrete reason: Parameter Store does not provide built-in automatic secret rotation. You can bolt rotation onto it yourself with a Lambda function and EventBridge schedule, but that is you building what Secrets Manager gives you as a managed feature — native integration with RDS, Redshift, and DocumentDB credential rotation, and a rotation Lambda AWS will generate for you from a template. When a scenario says "credentials must rotate automatically without custom rotation infrastructure," Parameter Store's lower per-parameter cost is irrelevant; it is disqualified by a missing capability, not a suboptimal price.

THE MECHANISM, PRECISELY

Every KMS API call against a customer managed key is evaluated against both the key's resource policy and the caller's identity-based policy (plus any grants). An explicit Deny in either one wins outright. Absent a Deny, the call is allowed only if both the key policy and the IAM side permit it. This is why "I attached AdministratorAccess to my role and decryption still fails" is a real, common production incident, not a hypothetical — and why the exam loves testing it.

ARC 04 · THE CORRECT APPROACH

Envelope encryption, the way KMS actually does it

Every "how does KMS encrypt my data" question resolves to one mechanism: envelope encryption. KMS customer managed and AWS managed keys almost never touch your actual data directly — instead, a much smaller data key encrypts your data locally (fast, symmetric, no size limit), and the KMS key's only job is to encrypt that data key. WHY IT'S BUILT THIS WAY

KMS's Encrypt API caps requests at 4 KB precisely because KMS is not meant to be a bulk encryption engine — it is a key management service. Envelope encryption lets an unlimited amount of data get encrypted locally at memory speed with a plaintext data key that never leaves the caller except in its encrypted form. The KMS key itself never leaves AWS's HSM-backed boundary at all — for a customer managed key you cannot export it (except specific import/export workflows for the narrow "bring your own key material" case); you can only ask KMS to use it. That single design decision is the backbone of nearly every "how does S3/EBS/RDS encryption actually work" answer on this exam.

ARC 06 · LIMITS, QUOTAS & EDGE CASES

Where the correct approach still has sharp edges

  • KMS direct encryption is capped at 4 KB. The Encrypt/Decrypt APIs only accept up to 4,096 bytes of plaintext per call — this is exactly why envelope encryption (GenerateDataKey + local AES) exists for anything larger than a small config blob.
  • Symmetric KMS keys support automatic annual rotation when enabled — KMS rotates the underlying key material roughly once every year while keeping the same key ID and ARN, so nothing referencing the key needs to change. Asymmetric and HMAC key material, and any key with imported key material, cannot use automatic rotation.
  • Secrets Manager secret values top out around 64 KB (65,536 bytes); Parameter Store's Standard tier tops out at 4 KB per parameter value, and its Advanced tier at 8 KB — a real, exam-relevant reason to reach for Secrets Manager or Advanced parameters for larger blobs like full config files or certificates.
  • Parameter Store has no native rotation. You can wire a Lambda + EventBridge schedule to rotate a parameter yourself, but that is custom-built automation, not a managed feature — a scenario asking for "built-in," "managed," or "automatic" rotation is asking for Secrets Manager.
  • GuardDuty is regional and opt-in per Region. Enabling it in us-east-1 does not detect threats against resources in eu-west-1; multi-region coverage needs either enabling it in every Region you operate in, or using a GuardDuty delegated administrator under AWS Organizations to manage it centrally across accounts and Regions.
  • Key policies have a size limit (a few KB of JSON) — a key shared with dozens of individually enumerated account principals can hit that ceiling, which is itself a signal the exam expects you to recognize: use a grant, an IAM condition, or an AWS Organizations condition key instead of an ever-growing list of ARNs in the policy document.
EDGE CASE THE EXAM LOVES

Deleting a KMS key is deliberately hard to do by accident: AWS enforces a mandatory waiting period (configurable between 7 and 30 days) before a scheduled key deletion actually executes, specifically because losing a customer managed key permanently makes every ciphertext it ever protected permanently unrecoverable. A scenario describing "we accidentally scheduled our production key for deletion" is testing whether you know you can still cancel it during that window — not whether you can recover after it's gone.

WHY "DELEGATED ADMINISTRATOR" MATTERS

Rather than logging into every member account to view findings, GuardDuty (and Security Hub, Macie, Detective) support designating one account under AWS Organizations as the delegated administrator, which can see and manage findings across every member account centrally. This is the real answer whenever a scenario says "we need one place to see security findings across 40 accounts" — it is an Organizations feature, not a per-account setting you replicate 40 times.

ARC 09 · DECISION FRAMEWORK

Use X when / use Y when — the single most exam-relevant table in this chapter

DECISIONUSE THIS WHENNOT WHEN
Secrets ManagerThe value needs automatic rotation (native RDS/Redshift/DocumentDB integration, or a custom rotation Lambda AWS scaffolds for you), or you need built-in cross-account resource policies on the secret itself. It's a simple config value (a feature flag, a non-secret setting) that never rotates — Parameter Store is cheaper and simpler for that.
Parameter StorePlain configuration values, feature flags, or secrets that genuinely don't need automatic rotation; Advanced tier when you need parameter policies (expiration, notifications) or values over 4 KB. The scenario explicitly requires managed automatic rotation without you building the Lambda yourself.
KMS (customer managed key)You need control over the key policy, rotation, cross-account sharing via key policy + grants, and CloudTrail visibility into every use of the key. You just need "encryption at rest" with no specific control requirements — an AWS managed key is simpler and free of per-key monthly charges.
CloudHSMA compliance regime requires you to hold and control the actual key material in a dedicated, single-tenant hardware security module you administer, or you need cryptographic operations KMS doesn't expose. KMS's shared, AWS-managed HSM boundary already satisfies your compliance requirement — CloudHSM is more operational overhead than most scenarios need.
GuardDutyContinuous, ML/threat-intel-driven detection across CloudTrail, VPC Flow Logs, DNS logs, S3 data events, and EKS audit logs, with minimal setup. You need a compliance/posture dashboard aggregating findings from many tools — that's Security Hub's job, built on top of GuardDuty's findings rather than replacing them.
MacieThe scenario is specifically about discovering and classifying sensitive data (PII) at rest in S3. The scenario is about network/API-level threat behavior — that's GuardDuty's domain, not Macie's.
EventBridge → Lambda remediationThe scenario says "respond automatically" / "without human intervention" to a finding, alarm, or event. The scenario only asks for a person to be notified — an SNS topic or a Security Hub dashboard is sufficient and the added Lambda step is unnecessary complexity.
ARC 10 · LIMITS & SCALING NUMBERS

Value-size ceilings, charted

One of the few genuinely stable, chartable numbers in this chapter: the maximum value size each configuration/secrets service will hold. This single fact resolves a surprising number of "which service" questions on its own — a value that must exceed 8 KB immediately rules out Parameter Store entirely.

ARC 11 · REAL-WORLD SCENARIO CASE STUDIES

Three constructions in the exam's actual voice

Original scenario constructions written for this course — not real exam content, and not claimed to be.

Case 1: The cross-account decryption failure

A media company's transcoding pipeline runs in a Workloads account and reads encrypted objects from an S3 bucket owned by a Data account. The transcoding role has an IAM policy granting kms:Decrypt on the key's ARN, yet every read fails with AccessDenied. The correct diagnosis: the Data account's KMS key policy does not include a statement granting the Workloads account's role (or its account root, paired with an IAM policy) decrypt permission — cross-account KMS access always requires the key policy to name the external account or principal explicitly, because the "root account has default IAM delegation" shortcut only applies within the key's own account.

Case 2: The hardcoded database password

A security review finds a production RDS password committed in application config years ago, never rotated since. Compliance now requires proof of rotation on a fixed schedule going forward. The correct answer: migrate the credential into Secrets Manager with native RDS rotation enabled (a managed rotation Lambda AWS generates), not Parameter Store with a hand-built rotation script — the scenario's requirement is "managed, provable, scheduled rotation," which is Secrets Manager's specific value proposition over Parameter Store.

Case 3: The unactioned finding

A company's security team already receives GuardDuty findings in a Security Hub dashboard, but a recent incident review found that a credential-exfiltration finding sat unreviewed for six hours before anyone acted. Leadership now demands automatic containment for a defined set of high-confidence finding types, not just visibility. The correct answer: an EventBridge rule matching GuardDuty finding events by severity/type, invoking a Lambda function that takes a specific remediation action (e.g., revoking the credential's active sessions, isolating the instance's security group) — visibility tools (Security Hub, dashboards) do not substitute for an automated response path when the requirement is speed, not just awareness.

ARC 13 · CLI / CODE REFERENCE

Illustrative CLI & policy syntax

Realistic, illustrative AWS CLI v2 and JSON syntax — the shapes you should recognize on sight, not copy verbatim into production without review.

security-automation/
├── key-policy.json — customer managed KMS key policy, cross-account grant
├── secret-with-rotation.sh — aws secretsmanager create-secret + rotate-secret
├── guardduty-remediation-rule.json — EventBridge rule pattern matching GuardDuty findings
└── remediation_lambda.py — example: revoke temporary credentials on a high-severity finding
JSONkey-policy.json — cross-account decrypt grant (illustrative)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnableRootAccountIAMDelegation",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111111111111:root" },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "AllowCrossAccountDecrypt",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::222222222222:role/transcoder-role" },
      /* the calling account's IAM must ALSO allow kms:Decrypt — this is one half of an AND */
      "Action": ["kms:Decrypt", "kms:DescribeKey"],
      "Resource": "*"
    }
  ]
}
bashsecret-with-rotation.sh — illustrative example syntax
# create a secret and let AWS scaffold RDS rotation
aws secretsmanager create-secret \
  --name prod/app/db-credentials \
  --secret-string '{"username":"app","password":"CHANGEME"}' \
  --kms-key-id alias/app-secrets-key

# attach the AWS-managed rotation Lambda and a 90-day schedule
aws secretsmanager rotate-secret \
  --secret-id prod/app/db-credentials \
  --rotation-lambda-arn arn:aws:lambda:us-east-1:222222222222:function:SecretsManagerRDSRotation \
  --rotation-rules AutomaticallyAfterDays=90
JSONguardduty-remediation-rule.json — EventBridge event pattern (illustrative)
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }],
    "type": [{ "prefix": "UnauthorizedAccess:IAMUser" }]
  }
}
WHY THE EXAM CARES ABOUT THIS SYNTAX

You will not be asked to write these files from memory, but you will be shown a snippet like the key policy above and asked "why does decryption still fail" or "what's missing." Recognizing that a key policy needs both a root-delegation statement (or equivalent) and an explicit grant to the external principal — and that the calling account's own IAM policy is a separate, additional requirement — is the actual skill being tested, not JSON syntax memorization.

GATE · EXAM-DAY TAKEAWAYS

Before chapter 20: what to actually remember

If you remember nothing else from this chapter: (1) KMS is a two-gate system — key policy AND identity policy must both allow an action, which is unlike almost every other AWS resource; (2) envelope encryption means a data key does the bulk work and the KMS key only ever protects that small data key; (3) Secrets Manager's differentiator over Parameter Store is native automatic rotation, not price; (4) GuardDuty is regional and needs a delegated administrator for real multi-account visibility; and (5) "automatically" in a scenario means EventBridge triggering a Lambda, not a dashboard a human checks.
