Serverless: Lambda, API Gateway
& Step Functions

Both real exams love a scenario that quietly rules out a whole compute family with one number. This chapter is about the numbers and the wiring: Lambda’s hard timeout ceiling, what actually happens during a cold start, which trigger gives you synchronous vs asynchronous vs poll-based invocation, and why “just have one Lambda call the next Lambda” is almost never the answer once retries and error branching enter the picture.

You will be able toState Lambda’s real timeout ceiling and explain the two distinct places a timeout can bite a serverless design.
You will understandWhy the exam treats hand-chained Lambda invocations as an anti-pattern once a workflow needs retries, branching, or a human-in-the-loop wait.

ARC 01 · EXAM CONTEXT

Where this chapter sits on the real blueprint

This chapter maps to two domains across the two exams: Design High-Performing Architectures on the Associate exam (SAA-C03, 24% of the exam) and Design for New Solutions on the Professional exam (SAP-C02, 29% of the exam — the single largest domain on that exam). On the Associate exam, serverless questions usually test whether you know Lambda’s hard limits well enough to reject it for the wrong workload. On the Professional exam, they go further — expecting you to design the orchestration layer (Step Functions) around several Lambda functions, with retries and compensating actions, as part of a larger new-solution architecture.

Serverless questions are disproportionately represented on both exams because they are cheap for AWS to write as scenario questions: give a workload duration, a trigger type, and a failure-handling requirement, then ask which service correctly satisfies all three. Get comfortable with the vocabulary in this chapter and a large fraction of those questions become mechanical.

ARC 02 · THE COMMON WRONG INSTINCT

"Just have the functions call each other"

Here is the instinct almost every candidate arrives with, usually because it is exactly how you would prototype a multi-step process by hand: a scenario describes an order pipeline — validate the order, charge the card, reserve inventory, ship it, notify the customer — with retries on transient failures and a rollback path if payment fails. The plausible-looking wrong answer has Lambda function A synchronously invoke Lambda function B, which invokes C, which invokes D, with retry loops and try/catch-style logic hand-written inside each function using the AWS SDK to call the next one directly.

A close cousin of the same instinct, tested just as often: a scenario describes a job that clearly runs for longer than a few minutes — a nightly batch reconciliation, a multi-gigabyte video transcode, a report that scans years of data — and the tempting wrong answer is "just raise the Lambda timeout", as if timeout were a dial you can turn indefinitely rather than a hard ceiling.

WHY IT'S TEMPTING

Both instincts feel natural because they mirror how you'd write the same logic as one program with function calls. The exam is specifically testing whether you understand that Lambda functions are not free functions in a program — each invocation is a billed, isolated, time-boxed unit with its own cold-start possibility, and chaining them by hand throws away everything a managed orchestrator gives you for free.

ARC 03 · WHY IT'S WRONG

Two hard ceilings and one coupling problem

Start with the number that rules out the "just raise the timeout" instinct outright: AWS Lambda's maximum function timeout is 900 seconds — 15 minutes — full stop. There is no configuration, support ticket, or service quota increase that raises it. If a scenario's workload can run past 15 minutes under any realistic condition, Lambda is not a legal answer for that step, regardless of how attractive its pricing model or operational simplicity looks otherwise. This single number eliminates an entire answer choice on a meaningful fraction of serverless scenario questions — memorize it as a fact, not a rule of thumb.

A second, independently deadly ceiling sits in front of Lambda whenever the trigger is Amazon API Gateway: a REST API's integration timeout is capped at 29 seconds, regardless of what you set the backing Lambda function's own timeout to. A function configured for 15 minutes behind an API Gateway REST API will still have its client-facing request killed at 29 seconds — the two limits are independent, and the exam loves pairing them in the same question to see if you'll only check one.

THE COUPLING PROBLEM WITH HAND-CHAINED LAMBDAS

Even for workloads that comfortably fit inside 15 minutes per step, direct Lambda-to-Lambda synchronous invocation has a real, quantifiable cost: the calling function is billed and blocked for the entire duration the callee runs, because it is sitting there awaiting a response. Chain four functions this way and your billed compute time is the sum of every step's duration, stacked, with the calling functions doing nothing but waiting. Worse, there is no built-in retry policy, no visual execution history, no per-step error branching, and no durable state if the calling function itself times out mid-chain — the workflow simply vanishes with no record of how far it got.

Both problems point at the same underlying gap: Lambda is a compute primitive for a single unit of work, not an orchestrator for a multi-step business process. §4 derives the correct answer to that gap.

THE ONE-LINE VERSION

Single unit of work, event-triggered, finishes well under 15 minutes → Lambda. Multiple steps with retries, branching, parallelism, or a wait for a human/external callback → Step Functions orchestrating Lambda (or other AWS services directly — Step Functions can call many services without a Lambda at all). A step that genuinely needs longer than 15 minutes or specialized hardware → hand that one step to Fargate, Batch, or EC2 and let Step Functions call it as a task, exactly the way it would call a Lambda.

ARC 06 · LIMITS, QUOTAS & EDGE CASES

What the correct answer still has to respect

Even once you have correctly reached for Lambda + Step Functions, a scenario can bury a second trap in the fine print. The limits below come up constantly because each one has quietly killed a design that looked correct at a glance.

  • Cold starts are real but bounded, and provisioned concurrency is the real fix. A cold start happens when Lambda has to initialize a new execution environment — download your code, start the runtime, run any code outside your handler — before it can run your function for the first time on that environment. For latency-sensitive synchronous paths (an API Gateway-fronted function a user is waiting on), provisioned concurrency keeps a pool of environments pre-initialized and warm, eliminating the cold-start penalty for traffic within that provisioned capacity. It is a capacity you explicitly pay to keep warm, not a free setting — the exam expects you to reach for it specifically when a scenario states a strict, consistent latency requirement, not just "sometimes slow."
  • The deployment package has real size ceilings. A direct zip upload is capped at 50 MB compressed; the unzipped function, together with layers, is capped at 250 MB. Beyond that, container image support lets a function's image go up to 10 GB — the exam's answer whenever a scenario mentions a large dependency tree (e.g. ML libraries) that blows past the zip limits.
  • /tmp is ephemeral, private per environment, and sized between 512 MB and 10,240 MB (configurable) — it does not persist between invocations on a fresh environment and is never shared across concurrent environments. A scenario implying shared or durable scratch space across invocations needs S3, EFS, or a database instead.
  • Event source mapping batches, and a poison-pill record can stall a whole shard or partition. For stream-based sources (DynamoDB Streams, Kinesis), a repeatedly failing record can block progress on its shard until it either succeeds, expires, or you configure bisect-on-error / a destination for discarded batches — the direct analog of a dead-letter queue for stream processing.
  • Step Functions Standard workflows have an execution history ceiling (a firmly bounded number of state transitions per execution) and are billed per state transition — the right choice for durable, long-running, auditable workflows. Express workflows trade that durability and history for high-volume, short-duration execution billed by requests and duration, and are the right answer whenever a scenario says "millions of short-lived events per day" rather than "auditable business transaction."
THE CLASSIC COMBINED TRAP

A scenario describes an API Gateway REST endpoint invoking a Lambda function that "sometimes take a few minutes to complete a report." The tempting answer raises the Lambda timeout and calls it done. The correct read: API Gateway's 29-second integration timeout will kill the client connection long before that, regardless of the Lambda timeout — the fix is to return immediately (202 Accepted) and do the long work asynchronously, typically behind Step Functions or an async Lambda invocation with a callback/polling pattern, not a Lambda timeout increase.

The memory dial: not just a memory setting

Lambda allocates CPU proportionally to configured memory — raising memory doesn't just give a function more RAM, it gives it a proportionally larger slice of CPU, which for CPU-bound work often lowers wall-clock duration enough to make the total billed cost (duration × memory) go down, not up, even though you're paying a higher per-millisecond rate. ARC 10 · SCALING NUMBERS

Memory vs. duration vs. relative cost — a genuinely computed curve

This is the same relationship the slider in §8 let you drive by hand, plotted across the full memory range for a CPU-bound workload. Notice the shape: relative billed cost is not monotonic in memory. It falls as added CPU shortens duration faster than the per-millisecond rate rises, bottoms out at a "sweet spot," then rises again once more memory stops buying proportionally faster execution. Finding that sweet spot for a real function is exactly what AWS's own Lambda Power Tuning tool automates — the exam expects you to know the tradeoff exists, not to memorize a specific number.

ARC 11 · REAL-WORLD SCENARIO CASE STUDIES

Three original vignettes, written the way the real exam phrases them

These are original scenarios written for this course to illustrate the exam's phrasing style — they are not drawn from, and do not claim to reproduce, any real exam question.

Case 1 — the media company with a 40-minute transcode step

A streaming startup ingests user-uploaded video and runs it through validation, thumbnail generation, and transcoding to several bitrates before publishing. Thumbnail generation reliably finishes in a few seconds; transcoding a long-form video reliably takes 25–40 minutes. The team's first design chains three Lambda functions by direct invocation. Correct approach: keep validation and thumbnailing as Lambda steps inside a Step Functions workflow, but route the transcode step to an AWS Fargate or Batch task invoked as a state in the same workflow — Lambda's 900-second ceiling makes it categorically ineligible for that one step, no matter how the rest of the pipeline is built.

Case 2 — the fintech company with a payment step that occasionally times out

A payments platform charges a card, reserves inventory, and ships an order, with a hard business requirement that a failed payment must never leave inventory reserved. The naive design calls each step from the previous Lambda directly with a try/catch. Correct approach: a Step Functions Standard workflow with a Retry policy on the payment step (to absorb transient gateway blips) and a Catch clause routing to a compensating "release reservation" state on permanent failure — exactly the pattern built in §15's simulator, and precisely the kind of multi-constraint design the Professional exam rewards.

Case 3 — the IoT company processing millions of short events per day

An IoT fleet emits telemetry that triggers a short (under one second) three-step validation-and-store workflow, at a volume of tens of millions of executions per day, with no regulatory requirement to retain a full execution audit trail per event. Correct approach: Step Functions Express workflows, not Standard — the volume and per-execution cost profile is exactly what Express is priced and designed for, and Standard's execution-history durability is a cost the scenario explicitly doesn't need.

ARC 16 · EXAM-DAY TAKEAWAYS

What to be sure of before you move on

Five facts carry most of this chapter's exam weight. Lambda's maximum timeout is 900 seconds (15 minutes) — a hard, unconfigurable ceiling that alone eliminates Lambda for long-running steps. API Gateway REST APIs add a second, independent ceiling — a 29-second integration timeout — that can kill a request long before Lambda's own timeout would. Cold starts are mitigated specifically by provisioned concurrency, a paid, explicit capacity choice, not a default behavior. Each trigger has a real, distinct invocation model — API Gateway is synchronous, S3/SNS are asynchronous, DynamoDB Streams/Kinesis/SQS are poll-based — and that model determines how failures surface and where a DLQ or destination belongs. And whenever a scenario describes multiple steps with retries, branching, or parallelism, the correct orchestrator is Step Functions, not a hand-written chain of direct Lambda invocations — Standard for durable, auditable workflows; Express for high-volume, short-duration ones.
