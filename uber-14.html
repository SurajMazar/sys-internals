UBER ENGINEERING INTERNALS · CHAPTER 14

One Engineering Team's
Real, Public, Debated Migration

In July 2016, Uber Engineering published a widely read blog post explaining why it had moved its core datastore from PostgreSQL to MySQL. It became one of the most-discussed database posts of the decade — and also one of the most publicly pushed back on, by name, by PostgreSQL contributors who disagreed with parts of it. This chapter presents Uber's stated reasoning honestly, on its own terms, and then presents the rebuttal just as honestly. The goal is not to tell you which database is better — it's to teach you how to read any engineering blog post like this one: as one team's real experience, at a specific point in time, under specific conditions, not as a universal verdict.

ARC 01 · THE PROBLEM

A trip's core record gets updated constantly, not just written once

Chapter 7 built the trip lifecycle as a state machine: requested → matched → driver en route → arrived → trip started → trip completed, with cancellation and timeout transitions from nearly every state. Read that state machine again with a storage engineer's eyes: every single transition is an UPDATE to an existing row, not an INSERT of a new one. Multiply that by millions of trips a day, each with a handful of status transitions, plus every other update-heavy workload the growing company was running on the same core relational datastore — driver locations, availability flags, account balances — and the workload shape that matters most is not "how fast can we write new rows" but "how cheaply can we update the same row, over and over, many times a second, at full scale."

This is the exact kind of foundational infrastructure decision that a company only makes once, feels the consequences of for years, and — if it turns out wrong for the workload — pays an enormous cost to unwind. Uber's publicly documented answer, and its reception, is this chapter's subject.

A NOTE ON HOW TO READ THIS CHAPTER

What follows is Uber's real, publicly published reasoning from 2016, presented on its own terms — followed, with equal weight, by the real technical pushback it received. Neither side gets the last word here. The lesson this chapter is actually trying to teach is how to evaluate a specific engineering team's specific experience against a specific workload, at a specific point in a specific database's development — not to settle "Postgres vs. MySQL" as a general question, which this single case study cannot do and does not attempt.

WHAT'S REAL HERE, STATED PLAINLY

Uber ran on PostgreSQL in its earlier years, then migrated its core trip/dispatch datastore to a MySQL/InnoDB-based architecture, and Uber Engineering published a public blog post in mid-2016 ("Why Uber Engineering Switched from Postgres to MySQL") explaining five specific technical reasons. That post is real and widely archived. The rebuttals are equally real and public: PostgreSQL core contributor Robert Haas published a detailed response the same season, and Markus Winand (a well-known SQL performance writer) published a specific technical rebuttal titled "On Uber's Choice of Databases," centered on one precise, checkable claim — more on that in §11. This chapter does not need to speculate about any of this; it is on the public record.

ARC 03 · NAIVE SOLUTION

The starting point: a straightforward, heavily indexed trips table

Picture the obvious, reasonable schema an engineering team builds early on, when query flexibility matters more than write-path cost: one core table, with a secondary index on every column anyone ever wants to filter or sort by, because indexes are "free" performance for reads and nobody is thinking about write amplification yet.

SQL (illustrative)trips table — reasonable, heavily-indexed, update-heavy
CREATE TABLE trips (
    id              bigint PRIMARY KEY,
    rider_id        bigint NOT NULL,
    driver_id       bigint,
    status          text NOT NULL,      -- updated on EVERY state transition (ch. 7)
    fare_cents      integer,
    surge_multiplier numeric,
    updated_at      timestamptz NOT NULL
);
CREATE INDEX idx_status     ON trips(status);       -- "find all active trips"
CREATE INDEX idx_driver     ON trips(driver_id);   -- "find this driver's trips"
CREATE INDEX idx_rider      ON trips(rider_id);    -- "find this rider's trips"
CREATE INDEX idx_updated    ON trips(updated_at);  -- "recently changed trips"

Nothing about this schema is careless — every index answers a real, common query. That's precisely what makes it a useful strawman: it's the schema a competent team ends up with by making locally reasonable decisions, without yet reasoning about what an UPDATE to status actually costs underneath, at the storage-engine level, on the specific database engine running it.

ARC 04 · UBER'S STATED CASE

The five reasons Uber's 2016 post gave, in Uber's own framing

Uber's post named five specific, technical pain points it said it hit running this shape of workload on PostgreSQL at its scale. Presented on their own terms, as Uber stated them:

  • 1. Inefficient architecture for writes. Uber's stated argument: PostgreSQL's MVCC design writes a new row version on every update rather than updating in place — and, Uber said, every secondary index on that table then needs a new entry pointing at the new row version too, not just the one index on whatever column actually changed. On a table with a dozen or more indexes and an update-heavy workload, Uber's post described this as significant write amplification: one logical update fanning out into many physical writes across every index, not just the relevant one.
  • 2. Inefficient data replication. Uber's stated argument: because PostgreSQL's built-in replication at the time shipped changes derived from the write-ahead log — closely tied to the physical write volume described above — the amplified write volume from point 1 directly inflated replication bandwidth and replica catch-up time, which Uber said became a real operational cost as write volume grew.
  • 3. Issues with data corruption. Uber's post described encountering cases where a query against a corrupted index or cache returned incorrect results, and said the tooling to detect and diagnose exactly which rows were affected was, in their experience, inadequate at the time.
  • 4. Poor replica MVCC support. Uber's stated argument: a long-running read on a replica could be cancelled by the replica applying replicated writes that conflicted with that read's MVCC snapshot — forcing a choice between letting replicas fall behind or cancelling in-flight replica queries, a tension Uber said it hit in production.
  • 5. Difficulty upgrading to newer releases. Uber's stated argument: major-version upgrades were operationally painful in their environment at the time, without an easy zero-downtime path — a real cost for a company that could not tolerate extended maintenance windows on its core datastore.

Uber's post also named two related operational pain points worth stating precisely because they connect directly to material this course has already covered: connection-handling cost — Uber described needing an external pooler to handle its connection volume, a direct real-world instance of the process-per-connection cost this site's dedicated PostgreSQL Internals course derives from first principles — and schema-migration friction, where certain schema changes locked the whole table for both reads and writes, causing visible service impact during a migration.

READ THIS AS A CLAIM, NOT YET AS A CONCLUSION

Every point above is Uber's own stated experience, in 2016, on the PostgreSQL versions and configuration they were running at the time. That is exactly the right level of confidence to hold each claim at until §11 — where you'll see that some of these points held up to technical scrutiny very well, and others drew specific, substantive, named rebuttal.

ARC 05 · THE MIGRATION

What Uber's post said it moved to, and why that shape

Uber's stated fix followed directly from reason #1: move the update-heavy core datastore onto an engine whose default update path doesn't require touching every secondary index on every write.

From MVCC append-versioning to a clustered, in-place update pathSTEP-BY-STEP

MySQL's InnoDB storage engine organizes a table as a clustered index on the primary key — the table's physical layout IS the primary-key B-tree, and an update that doesn't touch an indexed column can modify that row's data in place within its page. Secondary indexes store the primary-key value, not a raw physical pointer, so they only need new entries when an indexed column's value actually changes. That structural difference is precisely the property Uber's post argued fit their update-heavy trip-status workload better than the schema in §3 running on Postgres's default heap-plus-index-pointers layout.

ARC 06 · WHAT THE MIGRATION COST

Switching engines is not a free upgrade — name the real costs

  • The migration itself was a massive undertaking. Moving a company's core datastore between engines at Uber's real scale means rewriting application data-access code, re-validating every query's behavior under a new engine's semantics, and executing the cutover itself without an unacceptable amount of downtime — work that took real engineering time away from every other roadmap for a sustained period.
  • MySQL/InnoDB has its own, different footguns. InnoDB's default isolation level uses gap locking that can produce surprising deadlocks under concurrent range-based updates; asynchronous replication (the historically common default at the time) can silently lose recently committed writes on an unplanned primary failover unless semi-synchronous replication is deliberately configured and monitored. Switching engines trades one set of operational lessons the team had already learned for a different set it had to learn from scratch.
  • It didn't remove the need to eventually shard. A single MySQL primary has a ceiling on write throughput too — moving to a cheaper per-update cost delays that ceiling, it doesn't eliminate it. Uber's continued growth still required horizontal partitioning, which is exactly what chapter 15's Schemaless was built on top of this same MySQL foundation to provide.
THE HONEST FRAME

Even reading Uber's stated reasons at face value, this was not "Postgres bad, MySQL good" — it was a real, expensive, multi-year engineering bet that a different default update path was worth the cost of a full migration, for one specific, extremely update-heavy workload, at one specific company's scale, running one specific set of database versions and configurations. That framing matters for everything that follows.

ARC 08 · INTERNAL IMPLEMENTATION

Write amplification, made concrete

Here is the mechanism behind Uber's reason #1, stated precisely and just far enough to make the argument checkable — this course's dedicated PostgreSQL Internals series covers MVCC's full tuple-versioning and vacuum machinery in depth and is not repeated here.

Uber's argument, precisely: an UPDATE that changes even one column creates a new physical row version; every secondary index on that table then needs an entry for the new version, because each index's leaf entries point at a specific physical row version, not merely a logical row. A table with k secondary indexes therefore costs, in Uber's framing, roughly 1 (new row version) + k (index entries) physical writes per logical update — versus an engine where an update leaves the row in place and only touches indexes on columns that actually changed.

ARC 09 · TRADEOFFS

What each engine genuinely offered, stated fairly

Several of Postgres's 2016-era gaps (notably logical replication) have since shipped; some of MySQL's operational rough edges (like semi-sync replication tuning) required — and still require — real expertise to run safely. §11 examines exactly how much of this table Uber's critics accepted versus disputed.

ARC 11 · THE DEBATE — REAL, PUBLIC, AND WORTH TAKING SERIOUSLY ON BOTH SIDES

What the Postgres community actually pushed back on, by name

This is the section this chapter exists to get right. Uber's post was widely read and widely discussed — and it received specific, technical, named rebuttal, not just reflexive defensiveness. Two responses matter most:

Robert Haas's response

Robert Haas, a longtime PostgreSQL core contributor, published a detailed public response the same season. He acknowledged some of Uber's pain points as genuine and worth PostgreSQL's community taking seriously, while pushing back on the overall framing — arguing that several of the specific claims (particularly around corruption and the severity of the write-amplification story) reflected specific bugs, specific configurations, or specific tuning choices from that moment in time rather than an unfixable architectural ceiling, and cautioning readers against treating the post as a general verdict that MySQL is simply the better-engineered database.

Markus Winand's "On Uber's Choice of Databases"

Markus Winand, a well-known SQL performance writer, published a specific, checkable technical rebuttal centered on one precise point: Uber's write-amplification argument never mentioned HOT — Heap-Only Tuple updates, a PostgreSQL optimization that existed since version 8.3, released in 2008 — eight years before Uber's post — specifically engineered to avoid touching secondary indexes at all when an update doesn't change an indexed column. Winand's point was precise: the naive schema in §3, with an index on nearly every column, including status itself, is exactly the shape of schema that prevents HOT from ever applying — which means part of what Uber's post presented as an inherent MVCC limitation may instead have been a consequence of specific schema and indexing choices that could, in principle, have been revisited without changing engines at all.

HOW TO HOLD BOTH SIDES AT ONCE — THE ACTUAL LESSON

Both things are true simultaneously, and that's the point of this section, not a contradiction to resolve: Uber's engineers had a real, expensive, update-heavy production problem, measured it honestly, and made a defensible engineering bet given their team's constraints and existing MySQL expertise at the time. And, separately, named technical experts identified specific, checkable gaps in how the problem was framed — gaps that suggest at least part of the pain might have been addressable through schema and configuration changes on the existing engine. Neither fact cancels the other. This is what it looks like to read a real engineering blog post critically: take the team's lived experience seriously, and take the technical pushback just as seriously, without needing either side to be simply "right."

It's also worth stating plainly what has changed since: PostgreSQL shipped native logical replication in version 10 (2017), directly addressing part of Uber's replication complaint, and major-version upgrade tooling has continued to mature industry-wide since 2016. None of that retroactively changes what was true for Uber's team in 2016 — it simply means a reader encountering this same tradeoff table today should re-check which rows in §9 are still current before making their own decision.

ARC 13 · CODE WALKTHROUGH

Reading the shift: illustrative reference schema and migration pattern

Neither Uber's exact original schema nor its internal migration tooling is public. What follows is precise, representative pseudocode for the general pattern a migration like this actually requires — labeled illustrative because it reconstructs the well-documented general technique, not proprietary source.

migration/
├── schema/
│ ├── trips_postgres.sql — original schema (§3)
│ └── ● trips_mysql.sql — InnoDB target schema, clustered on trip id
├── cutover/
│ ├── ● backfill.py — one-time historical copy, Postgres → MySQL
│ ├── ● dual_write.py — every new write goes to BOTH stores during migration
│ └── ● shadow_read_diff.py — compares reads from both stores, flags mismatches
└── cutover_runbook.md — the phased sequence in §14's order-quiz
SQL (illustrative)trips_mysql.sql — clustered on the primary key
CREATE TABLE trips (
    id                BIGINT PRIMARY KEY,      -- clustering key: table IS this B-tree
    rider_id          BIGINT NOT NULL,
    driver_id         BIGINT,
    status            VARCHAR(32) NOT NULL,
    fare_cents        INT,
    surge_multiplier  DECIMAL(4,2),
    updated_at        DATETIME NOT NULL
) ENGINE=InnoDB;
CREATE INDEX idx_driver ON trips(driver_id);   -- secondary indexes store the PK, not a raw pointer
CREATE INDEX idx_rider  ON trips(rider_id);
-- note: no index on `status` alone here — it's usually paired with driver_id/rider_id
-- in real query patterns, and every extra secondary index re-introduces SOME update cost
-- even on this engine — indexing decisions still matter, on any engine (see §11).
pseudocode (illustrative)cutover/dual_write.py — the general safe-migration pattern
def update_trip_status(trip_id, new_status):
    # During migration: write BOTH, but the OLD store stays authoritative
    # for reads until shadow-read validation (below) has run clean for a while.
    postgres.execute("UPDATE trips SET status=%s WHERE id=%s", new_status, trip_id)
    try:
        mysql.execute("UPDATE trips SET status=%s WHERE id=%s", new_status, trip_id)
    except Exception as e:
        metrics.incr("dual_write.mysql_failure")   # NEVER fail the request over this — old store is still truth
        log.warn(f"shadow write to mysql failed: {e}")
WHY A MIGRATION LIKE THIS IS BUILT AS DUAL-WRITE-THEN-CUTOVER, NOT A BIG-BANG SWITCH

Any migration of a company's core, always-on datastore follows the same general risk-reducing shape, documented across the industry for exactly this class of problem: backfill history once, dual-write every new change to both stores while the old one stays authoritative, continuously diff reads between the two stores to catch bugs before they matter, and only then flip which store is authoritative for reads — followed, much later, by retiring the old store once confidence is high. The alternative — a single cutover weekend — makes every bug in the new engine's behavior a full, simultaneous incident with no fallback, which is an unacceptable risk profile for infrastructure this central.
