WHAT'S ACTUALLY RUNNING

This page ships its own from-scratch, synchronous SHA-256 implementation and its own secp256k1 elliptic-curve engine written with native BigInt — the same curve Bitcoin and Ethereum use (p, a=0, b=7, generator point G, order n). Troubleshooting

SYMPTOMCAUSE & FIX
A widget shows "computing…" and never resolves The mining/puzzle-friendliness experiments grind real SHA-256 nonces in a loop on the main thread. High difficulty targets (more than ~20 leading zero bits) can take a while in a browser tab — lower the target bits and re-run.
Numbers look enormous or show n suffix That's a native JavaScript BigInt literal — expected for curve coordinates, scalars, and the curve order. They're printed as decimal or hex strings for readability elsewhere.
Signature verify unexpectedly returns false Usually intentional — the tamper controls in section 2.3 and the nonce-reuse experiment deliberately construct invalid or telling inputs. If it's not intentional, check you generated a fresh keypair after changing the message.

5.1 · Diagnosing a chain split in production

  
Precondition: you run (or depend on) a full node and its reported chain tip suddenly disagrees with a
  block explorer, another node, or a peer service.

  
    
    
  1. Confirm it's real, not a stale cache. Query your node's current best-block hash and height directly, not through an API layer that might be caching.
    2. 
    
  2. Identify the fork point. Walk back from both tips comparing block hashes at each height until they match — that height is the common ancestor.
    3. 
    
  3. Compare cumulative work, not length (experiment 6). A shorter, higher-difficulty branch can legitimately outweigh a longer one; don't assume the branch with more blocks is "the real chain".
    4. 
    
  4. Check for the accidental case first. If the split is only 1–2 blocks deep and both branches have plausible difficulty, this is very likely ordinary propagation-delay forking — wait one more block interval and re-check; it usually self-resolves via fork choice.
    5. 
    
  5. If the split is deep or persistent, check for a partition on your own network path (runbook 5.4) or an actual protocol-rule disagreement (a soft/hard fork you haven't upgraded for — check node version against announced activation heights).
    6. 
    
  6. Do not manually reorg your own state to "fix" it. Let your node's normal fork-choice logic re-converge once connectivity and peer diversity are restored — manual intervention is how nodes end up on a minority fork permanently.
    7.

5.2 · Responding to a suspected 51% attack

  
Precondition: you observe unusually deep reorgs, or off-chain intelligence (hashrate pool
  concentration, a single miner's share spiking) suggests one party controls a majority of hashrate.

  
    
    
  1. Quantify, don't panic. Estimate the attacker's hashrate share q from observed reorg depth using the inverse of the Nakamoto race formula (experiment 4) — a reorg of depth z succeeding is strong evidence q is uncomfortably close to 50%.
    2. 
    
  2. Raise required confirmations immediately for high-value operations (deposits, withdrawals) using the confirmation-depth calculator with the newly estimated, higher q.
    3. 
    
  3. Pause irreversible actions that depend on finality assumptions calibrated to a lower q — most critically, do not release goods/funds against transactions confirmed at the old depth.
    4. 
    
  4. Coordinate rather than unilaterally fork. Emergency consensus-rule changes (checkpointing a block, banning a mining pool at the P2P layer) are governance decisions with real cost to legitimacy — this is not a purely technical call.
    5. 
    
  5. After the fact, use the rewrite-cost calculator (experiment 10) with the observed difficulty and a market hashprice to estimate what the attack actually cost the attacker, which tells you whether it was profit-motivated or a stress test.
    6. 
  

  

    
WHAT A 51% ATTACK CANNOT DO

    
An attacker with a hashrate majority can reorg recent history and double-spend their own coins, and can
    censor specific transactions — but they cannot forge signatures, steal coins from addresses they don't
    control, or change consensus rules (like the block reward). Communicate this precisely; overstating the
    blast radius causes worse decisions than understating it.

  


  
5.3 · Auditing a smart-contract state proof

  
Precondition: a bridge, light client, or off-chain service has accepted a claim of the form
  "account X had value Y at block Z" backed by a Merkle/state proof, and you need to independently verify it.

  
    
    
  1. Get the trusted root independently. Fetch the state root for block Z from a source you trust separately from whoever supplied the proof (your own full node, ideally).
    2. 
    
  2. Recompute the leaf hash yourself from the claimed key and value using the exact same hashing convention the chain uses — do not trust a pre-hashed leaf handed to you.
    3. 
    
  3. Walk the proof path, hashing with each sibling in the stated direction (left/right matters — swapping it silently produces a different, wrong root).
    4. 
    
  4. Compare against the independently-fetched root, not the root embedded in the same payload as the proof (a malicious relayer can supply a self-consistent but wrong root+proof pair).
    5. 
    
  5. Reject on any mismatch — see experiment 8 for exactly what a tampered value does to this check.
    6. 
  


  
5.4 · Recovering from an eclipse-attack partition

  
Precondition: a node's peer set is suspected to be entirely or mostly attacker-controlled (experiment 9) — e.g. it reports a chain tip wildly out of sync with known-good sources, or accepted a transaction later found double-spent elsewhere.

  
    
    
  1. Disconnect all current peers and clear any locally cached peer address table (addr poisoning is part of how eclipse attacks are set up).
    2. 
    
  2. Reseed from out-of-band sources — hardcoded seed nodes, DNS seeds, or manually-specified peers you or a trusted party operate.
    3. 
    
  3. Force outbound-only reconnection to the new peer set rather than accepting inbound connections first, to avoid immediately re-eclipsing from the same address pool.
    4. 
    
  4. Cross-check the chain tip against at least two independently-operated sources before trusting the node's view again.
    5. 
    
  5. Prevent recurrence: increase the number of outbound connections if your software allows it, and prefer peer-discovery mechanisms resistant to address-table flooding (course ch.11 covers the specific defenses that followed the 2015 disclosure).
    6. 
  


  
5.5 · Rotating validator keys safely (proof-of-stake)

  
Precondition: a validator's signing key may be compromised, or you are performing scheduled key rotation. This procedure exists specifically to avoid double-signing, which triggers slashing (experiment 15).

  
    
    
  1. Never run the old and new key simultaneously against the same validator index. Two live signers for one validator is the single most common cause of accidental slashing.
    2. 
    
  2. Stop the old signer completely and confirm (via its own logs and a chain query) that it has stopped signing before starting the new one.
    3. 
    
  3. Wait at least one full finality period past the old signer's last known signature before bringing the new key online, to guarantee no in-flight signature can collide.
    4. 
    
  4. Bring up the new signer and confirm it signs the very next expected duty before decommissioning old key material entirely.
    5. 
    
  5. If using remote signing / HSMs, rotate through a maintenance window with monitoring on slashing-protection database state — most slashing incidents trace back to a cloned or reset slashing-protection database, not the key itself.
    6.

Project 1 · A minimal blockchain in ~100 lines

  
Hash-linked blocks, a real Merkle root per block, and a validation function that actually walks the chain.

  
javascriptchain.js


const crypto = require("crypto");
const sha256 = s => crypto.createHash("sha256").update(s).digest("hex");

function merkleRoot(txs) {
  let layer = txs.map(t => sha256("leaf:" + t));
  if (layer.length === 0) return sha256("");
  while (layer.length > 1) {
    const next = [];
    for (let i = 0; i < layer.length; i += 2) {
      const l = layer[i], r = layer[i+1] ?? layer[i];
      next.push(sha256("node:" + l + r));
    }
    layer = next;
  }
  return layer[0];
}

class Block {
  constructor(index, txs, prevHash) {
    this.index = index;
    this.txs = txs;
    this.prevHash = prevHash;
    this.merkleRoot = merkleRoot(txs);
    this.timestamp = Date.now();
    this.hash = this.computeHash();
  }
  computeHash() {
    return sha256(this.index + this.prevHash + this.merkleRoot + this.timestamp);
  }
}

class Chain {
  constructor() {
    this.blocks = [new Block(0, ["genesis"], "0".repeat(64))];
  }
  addBlock(txs) {
    const prev = this.blocks[this.blocks.length - 1];
    this.blocks.push(new Block(prev.index + 1, txs, prev.hash));
  }
  isValid() {
    for (let i = 1; i < this.blocks.length; i++) {
      const cur = this.blocks[i], prev = this.blocks[i-1];
      if (cur.prevHash !== prev.hash) return false;
      if (cur.hash !== cur.computeHash()) return false;
      if (cur.merkleRoot !== merkleRoot(cur.txs)) return false;
    }
    return true;
  }
}

const chain = new Chain();
chain.addBlock(["alice pays bob 3"]);
chain.addBlock(["bob pays carol 1"]);
console.log("valid before tamper:", chain.isValid());
chain.blocks[1].txs[0] = "alice pays bob 300"; // tamper without recomputing hashes
console.log("valid after tamper:", chain.isValid());

  
WHAT PROVES THIS WORKS


valid before tamper: true
valid after tamper: false

  
Success criteria: isValid() returns true on an untouched chain and false
  the instant any transaction, Merkle root, or hash pointer is altered without a full recompute — matching
  experiment 1's browser demo exactly.


  
Project 2 · Add adjustable-difficulty proof-of-work

  
Extend project 1's Block with a nonce field and a mine() method that grinds until
  the block's hash has the target number of leading zero bits.

  
javascriptappend to chain.js


function leadingZeroBits(hex) {
  let bits = 0;
  for (const ch of hex) {
    const v = parseInt(ch, 16);
    if (v === 0) { bits += 4; continue; }
    bits += Math.clz32(v) - 28;
    break;
  }
  return bits;
}

class MinedBlock extends Block {
  constructor(index, txs, prevHash, difficultyBits) {
    super(index, txs, prevHash);
    this.difficultyBits = difficultyBits;
    this.nonce = 0;
    this.mine();
  }
  computeHash() {
    return sha256(this.index + this.prevHash + this.merkleRoot + this.timestamp + this.nonce);
  }
  mine() {
    do { this.nonce++; this.hash = this.computeHash(); }
    while (leadingZeroBits(this.hash) < this.difficultyBits);
  }
  isValidPoW() {
    return leadingZeroBits(this.hash) >= this.difficultyBits && this.hash === this.computeHash();
  }
}

const t0 = Date.now();
const b = new MinedBlock(1, ["stake pool payout"], "0".repeat(64), 18);
console.log("mined in", Date.now() - t0, "ms, nonce=" + b.nonce, "valid:", b.isValidPoW());

  
Success criteria: isValidPoW() returns true for a mined block and the mining
  time scales roughly with 2^difficultyBits as you raise it — confirm this by timing difficulty 16,
  18 and 20 back to back (same shape as experiment 11's browser mining widget).


  
Project 3 · A 5-node gossip network with fork choice, then a partition and a heal

  
Simulate 5 in-memory "nodes" that gossip newly mined blocks to each other, each independently applying the
  heaviest-chain fork-choice rule (experiment 6), then partition the network and reconnect it.

  
javascriptgossip.js


class Node {
  constructor(id) {
    this.id = id;
    this.chain = [{ index: 0, work: 0, hash: "genesis", parent: null }];
    this.peers = [];
    this.partitioned = false;
  }
  tip() { return this.chain[this.chain.length - 1]; }
  totalWork() { return this.chain.reduce((s, b) => s + b.work, 0); }
  mine(difficultyBits) {
    const parent = this.tip();
    const block = { index: parent.index + 1, work: Math.pow(2, difficultyBits),
                    hash: this.id + "-" + parent.index + "-" + Math.random(), parent: parent.hash };
    this.chain.push(block);
    this.gossip(block);
  }
  gossip(block) {
    if (this.partitioned) return;
    for (const peer of this.peers) peer.receive(block, this);
  }
  receive(block, from) {
    if (this.partitioned) return;
    const candidateChain = [...this.chain.slice(0, block.index), block];
    const candidateWork = candidateChain.reduce((s, b) => s + b.work, 0);
    if (candidateWork > this.totalWork()) { this.chain = candidateChain; this.gossip(block); } // re-gossip on adopt
  }
}

const nodes = [0,1,2,3,4].map(i => new Node("n"+i));
nodes.forEach(n => n.peers = nodes.filter(x => x !== n)); // fully connected for simplicity

nodes[0].mine(16);
console.log("all tips equal after gossip:", new Set(nodes.map(n => n.totalWork())).size === 1);

// partition: split into {n0,n1} and {n2,n3,n4}
const [groupA, groupB] = [nodes.slice(0,2), nodes.slice(2)];
groupA.forEach(n => n.peers = groupA.filter(x => x !== n));
groupB.forEach(n => n.peers = groupB.filter(x => x !== n));

groupA.forEach(n => n.mine(16));               // A mines 1 block
groupB.forEach(n => { n.mine(18); n.mine(18); }); // B mines 2 higher-difficulty blocks

console.log("work while partitioned — A:", groupA[0].totalWork(), "B:", groupB[0].totalWork());

// heal: restore full connectivity and re-gossip each node's current tip
nodes.forEach(n => { n.partitioned = false; n.peers = nodes.filter(x => x !== n); });
nodes.forEach(n => n.gossip(n.tip()));

console.log("converged after heal:", new Set(nodes.map(n => n.totalWork())).size === 1);
console.log("winning total work:", nodes[0].totalWork(), "(should equal groupB's, the heavier side)");

  
Success criteria: before healing, the two groups report different totalWork(); after
  healing and re-gossiping, every node converges to the same total work — and it must equal whichever
  group had more cumulative work, not whichever group mined more blocks (this project's group B has fewer blocks
  but wins on difficulty, mirroring experiment 6).
