ARC 01 · THE PROBLEM

Who is right when two control-plane replicas disagree?

Chapter 6 established the rule: nothing in a Kubernetes cluster talks to etcd except the API server, and the API server treats etcd as the single, durable source of truth for every object. That rule only works if etcd itself can answer one question without ambiguity, even while parts of it are crashing: what is the current, agreed-upon state? That is the general problem of distributed consensus, and it is harder than it looks the moment you write it down precisely.

Unpack "single source of truth" into the five properties it actually requires, and you will see why one machine is never enough and why "just add replicas" is not automatically a fix:

  • Durability — an acknowledged write must survive the crash of any one machine, including the one that accepted it.
  • Fault tolerance — the cluster must keep working with some machines down, without a human intervening at 3 a.m.
  • Consistency — two replicas must never give two different, equally confident answers to "what is the value of this key right now." A scheduler (chapter 8) that reads stale node capacity and a controller that reads fresh capacity must not silently disagree about what's true.
  • Total order — writes must be applied in the same sequence everywhere, so "delete X then create X" and "create X then delete X" are never confused between replicas.
  • Availability under partial failure — the system should keep serving as long as enough of it is healthy, and it must know, precisely, how much is "enough."

These pull against each other. More replicas improve durability and fault tolerance but make agreement slower and harder to reason about; fewer replicas make agreement trivial but reintroduce a single point of failure — exactly the disease Kubernetes exists to cure everywhere else. etcd is the one piece of the control plane that cannot outsource this problem to declarative reconciliation (chapter 9's whole game): reconciliation loops assume there is one true observed state to reconcile toward. Something has to actually agree on what that state is. That something is a consensus protocol — in etcd's case, Raft — running underneath a small, focused key-value store listening on TCP 2379 for clients and 2380 for its peers.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Chapter 9's informers, chapter 8's scheduler cache, and every controller's reconciliation loop are all built on one primitive this chapter derives: etcd's watch, a stream of ordered changes keyed by a monotonically increasing revision number. That revision number only means something because Raft guarantees a single, agreed order of writes. If you understand why revision numbers can be trusted, you understand the foundation the entire event-driven control plane stands on.

DEEP CONTEXT · WHY "UNDERSTANDABLE" WAS THE ACTUAL RESEARCH CONTRIBUTION

Raft's 2014 paper is not claiming a new capability Paxos lacked — the two are provably equivalent in what they guarantee. Its contribution is pedagogical and, it turned out, load-bearing for the whole industry: Paxos's single-decree formulation is famously hard to extend correctly into a real replicated log (Google's own Chubby team wrote about the gap between the Paxos paper and a working implementation), and most real systems ended up implementing ad hoc, unproven variants. Raft was deliberately decomposed into three independently-understandable sub-problems — leader election, log replication, and safety — specifically so that engineers, not just distributed-systems researchers, could implement it correctly. etcd is the direct beneficiary: it shipped Raft correctly on the first attempt at the protocol layer, which is precisely why Kubernetes could bet its entire state store on a project barely a year old in 2014.

ARC 03 · NAIVE SOLUTION

Attempt #1: a primary with asynchronous backups

Derive the architecture honestly, the way an operator reaches for it under deadline pressure. You need a replicated key-value store. The obvious first cut: one primary accepts writes and answers reads immediately; it ships each write to N backups whenever the network gets around to it; if the primary dies, a script (or a human) promotes the freshest-looking backup.

pseudo-Gonaive_store.go — the strawman, annotated
func (s *Store) Put(key, value string) {
    s.data[key] = value                 // 1. apply locally, in memory
    s.log = append(s.log, Entry{key, value})
    ackClient()                    // 2. tell the client "done" -- BEFORE anyone else has it!

    go func() {
        for _, backup := range s.backups {
            backup.Send(key, value) // 3. fire-and-forget replication, whenever TCP gets to it
        }
    }()
}

// promotion.sh, run by a human or a cron job after the primary stops responding:
//   ssh backup-1 "promote-to-primary"   # ...and hope backup-1 was actually the freshest one

This is not a strawman built to be laughed at — it is exactly how many production systems bootstrap replication, and it gets the common case right: writes are fast (one machine, memory-speed), reads are fast, and most of the time backups are only a few milliseconds behind. The failure modes only show up exactly when you can least afford them: during a crash.

ARC 04 · WHY IT FAILS

Acknowledged doesn't mean durable, and "promote a backup" can create two truths

Two independent failure modes, both fatal for something claiming to be a cluster's source of truth:

  • Silent data loss. The primary ACKs the client before replication happens. If it crashes in the window between ack and delivery, an acknowledged write is gone forever — and the client already moved on believing it succeeded. With a replication lag of L milliseconds and a write rate of W writes/sec, the expected number of acknowledged-but-unreplicated writes at any instant is W × L. At a modest 200 writes/sec and 15 ms of lag, that's an expected 3 writes silently at risk at all times — and a crash doesn't sample the average case, it happens exactly when something else (load, network congestion) has already pushed lag higher.
  • Split brain. A network partition separates the primary from every backup. The promotion script, unable to reach the primary, promotes backup B. But the original primary is still running and still reachable by clients on its side of the partition — it keeps accepting writes. When the partition heals, you have two histories that both believe they were authoritative, with no principled way to merge them. For Kubernetes' state store this isn't a data-quality inconvenience — it's two control planes that might each have scheduled a different Pod onto the same port on the same node.
THE IMPOSSIBILITY RESULT THAT MAKES THIS NON-NEGOTIABLE

Fischer, Lynch, and Paterson proved in 1985 ("Impossibility of Distributed Consensus with One Faulty Process") that no deterministic algorithm can guarantee consensus in a purely asynchronous network if even one process can fail — you cannot distinguish "that node is dead" from "that node is just slow," so any protocol that always terminates can be tricked into disagreeing. Real consensus systems escape this not by beating the theorem but by relaxing its assumption: they accept partial synchrony (message delays are usually bounded, even if not provably so) and use randomization to break ties. That is exactly what Raft's randomized election timeout is for, and you'll watch it do its job in the simulator in §15.

So the naive design isn't missing a feature — it's missing a protocol. What's needed is a way for a majority of replicas to agree on both who may write and the exact order of what was written, so that no acknowledged write can vanish and no partition can produce two authoritative histories at once.

ARC 05 · BETTER SOLUTION

Raft, decomposed into three understandable pieces

Raft answers the naive design's two failures with one rule, applied twice: nothing counts until a majority of the cluster has it durably. Step through the three pieces the paper deliberately separates — each is simple in isolation; together they are consensus.

Raft in three piecesSTEP-BY-STEP
THE CLINCHING ARGUMENT: A MAJORITY CANNOT DISAGREE WITH ITSELF

Any two majorities of the same cluster must overlap by at least one member (that's just arithmetic on N). Raft exploits this directly: a leader is elected by a majority vote, and a log entry is committed once a majority has it. Because any future majority necessarily includes at least one member who already knows about a prior majority decision, that decision can never be silently overwritten — the overlap is the mechanism, not an emergent property you have to trust. This is the whole reason etcd needs 2f+1 members to tolerate f failures, and why the number of members is not a knob you turn for "more safety" without doing the arithmetic first (§6, §8).

ARC 06 · WHY THAT STILL COSTS

Consensus is correct, and consensus is not free

Raft closes the naive design's correctness gap completely, but it does so by spending latency and availability on purpose. Every cost below is a direct, physical consequence of "nothing counts until a majority has it durably" — not an implementation shortcoming:

  • Every write pays a majority round trip, serialized by disk. The leader cannot acknowledge a write until ⌊N/2⌋+1 members — including itself — have appended it to their own on-disk write-ahead log and fsync'd it. Write latency is therefore bounded below by network RTT to the slowest required follower plus that follower's fsync time. There is no clever batching that makes a majority-durability write as cheap as a single-node write; you are buying survivability with wall-clock time on purpose.
  • Odd-sized growth can make things strictly worse. Going from 3 members to 4 does not improve fault tolerance at all — both tolerate exactly 1 failure (⌊(N-1)/2⌋) — but it raises the quorum you must wait for from 2 to 3, adding latency for zero durability benefit. This is why etcd's own operational guidance is blunt: run an odd number of members (3, 5, or 7 in nearly all real deployments), never an even one on purpose.
  • Leader loss means a real, bounded outage. While an election runs, the cluster accepts no new writes. etcd's defaults — a 100 ms heartbeat interval and a 1000 ms election timeout — mean a lost leader typically costs on the order of one second of write unavailability before a new leader is serving, not zero.
  • Even reads aren't free if they must be linearizable. A client asking "what is this key's value, guaranteed fresh" forces the leader to confirm, via a fresh round of heartbeats to a majority, that it is still the leader before answering — because a network partition could have silently elected a new leader elsewhere. Only explicitly serializable (possibly stale) reads skip this round trip.
THE HONEST TRADEOFF

None of this is a defect to be optimized away — it is the price of the guarantee. A Kubernetes cluster with a 1-second write stall during a leader election is a cluster that has never, in its entire history, silently lost an acknowledged write or run two disagreeing control planes. The naive primary-backup design in §3 was faster on the happy path specifically because it hadn't paid for either guarantee.

So the final architecture is Raft as the agreement layer, wrapped in exactly the machinery that turns "agreement" into "a key-value store real clients can use": a write-ahead log, a versioned data model, and a watch stream. Let's meet it.

ARC 08 · INTERNAL IMPLEMENTATION

From a client's Put to a committed, queryable revision

Now the actual mechanism: (a) the real message shapes on the wire, (b) the control loop every etcd server runs, (c) the write path step by step, and (d) two things you can only understand by dragging a slider.

(a) The shapes: a log entry, a WAL record, an MVCC key

Raft doesn't know about keys and values — it replicates opaque log entries. etcd's server layer is what turns a client's intent into one of those entries, and turns a committed entry back into a versioned key:

protobuf-shapethe three structures that matter, simplified but faithful
// 1. What the client actually sends (etcdserverpb.PutRequest, over gRPC):
message PutRequest { bytes key = 1; bytes value = 2; int64 lease = 3; }

// 2. What Raft actually replicates (raftpb.Entry) -- the PutRequest above,
//    serialized, is just the opaque `Data` payload. Raft never looks inside it.
message Entry { uint64 Term = 1; uint64 Index = 2; EntryType Type = 3; bytes Data = 4; }

// 3. What lands in the MVCC key space once the entry is applied --
//    every write gets a brand-new (main, sub) revision; nothing is overwritten in place.
struct Revision { int64 main; int64 sub; }   // e.g. {main: 4821, sub: 0}
// treeIndex (in-memory btree):   "/registry/pods/default/web-1" -> [rev@103, rev@4821, ...]
// boltdb (on disk, keyed by revision): rev@4821 -> KeyValue{key, value, create_rev, mod_rev, version}

Two consequences fall straight out of this shape. First, etcd never mutates a value in place — a Put on an existing key creates a new revision and the old one is retained until compaction explicitly removes it, which is exactly the mechanism that lets watch replay history and lets a client ask "what did this key look like at revision 4200." Second, the on-disk write-ahead log is organized as numbered segment files (for example 0000000000000003-0000000004821.wal), each holding a run of Entry records guarded by a CRC32 checksum — the same "append, checksum, fsync" shape you'd design from first principles for any crash-safe log.

(b) The control loop every server runs

Regardless of whether a given server is currently leader, follower, or candidate, its main loop has the same shape — read whatever Raft says is ready, persist it, ship it, apply it, repeat:

pseudo-GoraftNode's core loop — modeled on etcd's Ready() pattern
for {
    rd := <-node.Ready()                 // Raft library says: "here is what changed"

    wal.Save(rd.HardState, rd.Entries)    // 1. PERSIST FIRST -- fsync before anything
                                             //    else touches this data, full stop.
    if !IsEmptySnap(rd.Snapshot) {
        saveSnapshot(rd.Snapshot)         // 2. a slow follower catching up gets a
    }                                        //    full snapshot instead of 10,000 entries

    transport.Send(rd.Messages)          // 3. ship AppendEntries / vote RPCs to peers

    applyToStateMachine(rd.CommittedEntries) // 4. only COMMITTED entries reach the
                                             //    MVCC store -- never merely-appended ones
    node.Advance()                       // 5. tell Raft this batch is fully handled
}

Step 4 is the line worth re-reading: the log can contain entries that are appended but not yet committed (replicated to a majority). Nothing in the log becomes a visible key-value change until it clears that bar — which is exactly the property the simulator in §15 will let you break and watch fail to break.

ARC 09 · TRADEOFFS

The same problem, five ways

etcd's choices — Raft, a single strongly-consistent key space, gRPC — are one point in a well-explored design space. Every serious coordination system has made a version of this same call:

SYSTEMCONSENSUSWHAT THEY BOUGHTWHAT THEY PAID
etcdRaft, one group for the whole key space easy to reason about simple mental model first-class watch every write serialized through one leader whole-keyspace quorum, even for unrelated keys
Apache ZooKeeperZAB (atomic broadcast, Raft-like leader-based log) battle-tested since ~2010 strong ordering guarantees Java GC pauses hit consensus latency no native MVCC/watch-by-revision
HashiCorp ConsulRaft (same family as etcd) integrated service mesh/DNS multi-datacenter gossip on top two protocols to operate (Raft + gossip)

Read the "one group for the whole key space" row honestly: it is etcd's biggest simplifying assumption and its biggest scaling limit at the same time (§10). CockroachDB's per-range groups exist precisely because a single Raft group eventually becomes the bottleneck — the same bottleneck this chapter's brief warns you etcd usually becomes before the API server does. A brief, useful comparison from outside this course: Apache Kafka removed its dependency on ZooKeeper in favor of an in-house Raft variant called KRaft, for exactly the same reason CoreOS reached for Raft over a home-grown protocol in 2013 — a well-specified, provably-safe algorithm beats maintaining one yourself.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Numbers you can predict before you page anyone

etcd's performance envelope, from first principles:

  • Write latency floor = network RTT to the slowest required quorum member + that member's WAL fsync time. On typical cloud SSD-backed nodes this is low single-digit milliseconds; on network-attached or contended disks it can dominate everything else in the cluster.
  • Request size limit: --max-request-bytes defaults to 1.5 MiB — a single Put/Txn above that is rejected outright ("etcdserver: request is too large"). In practice this is also why a single Kubernetes object (a large ConfigMap or Secret) has a hard practical ceiling near that size, and why etcd's own guidance is to keep individual values small — well into the kilobytes, not megabytes — since MVCC retains every historical revision until compaction.
  • Backend size: --quota-backend-bytes defaults to 2 GB; etcd's documented, operator-tested ceiling is 8 GB — past that, compaction/defragmentation pauses and recovery time both grow enough that etcd itself warns you at startup.
  • Snapshotting: by default a Raft snapshot is taken roughly every 100,000 committed entries (--snapshot-count), bounding how much WAL a rejoining or newly added member must replay.
  • At cluster scale: the whole reason this chapter's brief calls out that etcd, not the API server, is "usually the actual bottleneck" — a cluster near Kubernetes' documented 5,000-node / 150,000-pod SLO envelope generates enough watch fan-out and write volume that etcd's single-Raft-group, single-leader design (this section's whole point) becomes the limiting resource well before kube-apiserver CPU does.

Security characteristics

etcd's security model is deliberately narrow but load-bearing for the whole cluster: mutual TLS between peers (port 2380) and between clients and the API (port 2379), and an RBAC layer (added in the v3 API) that can restrict a credential to a specific key prefix — which is exactly how the API server's own service account is scoped so that a compromised, lower-privileged component can never read or write arbitrary keys directly. §11 covers two real vulnerabilities in this exact surface.

ARC 11 · REAL-WORLD INCIDENTS

Four failures you should recognize on sight

CVE-2018-1099: DNS rebinding past the client API

etcd versions through 3.3.1, when serving its HTTP client API without TLS, did not validate the incoming request's Host header. An attacker who controls a DNS record can point a victim's browser at a hostname that resolves to localhost (or any internal address) after the browser's same-origin check has already passed, then have it issue requests straight into etcd's unauthenticated HTTP API — classic DNS rebinding, applied to a coordination service. Root cause: trusting the Host header as an authorization signal. Fix: a host-allowlist check added to the HTTP server wrapper in 3.3.2. Lesson that generalizes: "it's only reachable on localhost/internal network" is not an authentication mechanism — it's exactly the assumption DNS rebinding is designed to defeat.

CVE-2020-15115: no minimum password length

etcd versions before 3.3.23 and 3.4.10 performed no length validation on user passwords in its built-in authentication, permitting one-character passwords and making offline or online brute-forcing of etcd credentials trivially cheap. Root cause: missing input validation on a security-critical field, not a cryptographic flaw. Fix: minimum length enforcement added in the patched releases. Lesson: RBAC and mTLS (§10) are only as strong as the weakest credential policy sitting in front of them — a defense-in-depth gap here undermines every layer built on top.

The quota-exhaustion freeze ("etcdserver: mvcc: database space exceeded")

Because every write creates a new MVCC revision rather than overwriting in place (§8a), a cluster with heavy write churn and infrequent or disabled auto-compaction grows its boltdb file continuously. Once it crosses --quota-backend-bytes (2 GB by default), etcd raises a NOSPACE alarm and — this is the part operators find alarming the first time — stops accepting writes cluster-wide, not just writes to the oversized keys. For Kubernetes specifically, that means the API server can no longer persist anything: no new Pods, no status updates, no lease renewals. Root cause: MVCC history retention with insufficient compaction cadence. Fix: run etcdctl compact to the current revision, then defrag to actually reclaim boltdb pages (compaction alone only marks pages reusable — it does not shrink the file), then clear the alarm. Prevention: enable --auto-compaction-retention and monitor backend size against the quota, not after it, before it.

The membership-math gotcha: adding a member mid-replacement

A documented, real operational trap: an operator replacing a failing node in a healthy 3-member cluster adds the replacement as a 4th member before removing the old one, intending to remove it a moment later. During that window quorum is computed over 4 members (needs 3), not 3 (needed 2) — and the brand-new member hasn't finished replicating the log yet, so it can't usefully contribute to a quorum under load. The cluster's effective fault tolerance during the transition is briefly worse than before the "safety" add began. etcd's own runbook guidance is explicit about this: add or remove members one at a time, and wait for a new member to catch up before touching membership again.

The two functions that define this chapter, simplified from real etcd/raft sources but faithful in shape and naming. First, becoming a candidate:

pseudo-Goraft.go — campaign() and the vote tally
func (r *raft) campaign() {
    r.becomeCandidate()             /* state = candidate, Term++, votedFor = self */

    if r.quorum() == r.poll(r.id, true) {
        r.becomeLeader()             /* single-node cluster: you ARE the majority */
        return
    }
    for id := range r.prs {
        if id == r.id { continue }
        r.send(pb.Message{To: id, Type: pb.MsgVote, Term: r.Term,
                            LogTerm: r.raftLog.lastTerm(), Index: r.raftLog.lastIndex()})
    }
}

/* Each peer answers MsgVote independently -- this is the ONLY place a vote is granted: */
func (r *raft) handleVoteRequest(m pb.Message) bool {
    canVote := r.Vote == m.From || (r.Vote == None && r.lead == None)
    logOK   := m.LogTerm > r.raftLog.lastTerm() ||
               (m.LogTerm == r.raftLog.lastTerm() && m.Index >= r.raftLog.lastIndex())
    return canVote && logOK && m.Term >= r.Term   /* candidate's log must be AT LEAST as fresh */
}

Second, the safety rule that decides when a leader is finally allowed to advance commitIndex — the exact rule the simulator in §15 enforces:

pseudo-Goraft.go — maybeCommit(): the rule that prevents the "Figure 8" problem
func (r *raft) maybeCommit() bool {
    mci := r.prs.Committed()  /* the highest index a QUORUM's matchIndex agrees on */

    /* THE rule: never commit an entry from an OLDER term purely by counting
     * replicas. A later leader could otherwise overwrite it before it's
     * ever safely visible -- committing only CURRENT-term entries directly
     * makes every earlier entry ride along transitively, safely.          */
    return r.raftLog.maybeCommit(mci, r.Term)
}
WHY IT WAS BUILT THIS WAY

1. The algorithm module (raft/) touches no disk and no socket. It communicates exclusively through the Ready()/Advance() channel pair, which means the entire consensus algorithm can be — and in etcd's own test suite is — driven by a fully deterministic, simulated network with zero real I/O. That is precisely the property this chapter's simulator (§15) leans on: a Raft implementation with no hidden I/O dependency is one you can run, pause, and inspect deterministically in a browser tab. 2. Voting requires the candidate's log to be at least as up to date, not just a majority count. This stops a lagging node that's behind on committed data from ever becoming leader and, in doing so, "un-committing" data a majority already agreed on. 3. Only current-term entries are committed directly. Without this rule a leader could replicate an old, uncommitted entry from a previous leader to a majority, believe it's committed, crash, and have a new leader (correctly, per the algorithm) overwrite it — silently violating "once committed, never lost." Ongaro's thesis calls this Figure 8; the one-line fix above is the entire mitigation.
