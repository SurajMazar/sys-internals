Blocks: Header, Merkle
Root & Serialization

Eighty bytes. That is the entire object a miner's ASIC hashes, four billion times a second, to extend the chain — regardless of whether the block behind it carries one transaction or four thousand. This chapter takes those eighty bytes apart field by field, derives why the design is exactly this shape, decodes the compact nBits target encoding against real mainnet blocks, and builds a working block: real double-SHA256, a real Merkle root, and a real nonce grind against a live target.

ARC 01 · THE PROBLEM

Commit to gigabytes; hash eighty bytes

By chapter 6 a node has a UTXO set, a mempool full of candidate transactions, and (chapters 2–5) the tools to build and verify any one of them. Mining (chapter 9) needs something else entirely: a way for a piece of hardware to try on the order of 1020 guesses across the network every ten minutes, each guess a full SHA-256d evaluation, while every one of those guesses must be checkable by every other node on Earth in microseconds. The object being guessed against — the thing miners actually hash — cannot itself be the block. A block today can carry several thousand transactions and approach 4 million weight units. Re-hashing that whole structure for every one of a few billion nonce attempts per second is not a performance inconvenience — it is arithmetically impossible on any hardware that exists.

So the design problem splits into two halves that must both hold at once:

  • A fixed-size, cheap-to-hash object that a miner can grind against at maximum hardware throughput, unaffected by how many transactions are in the block.
  • A binding commitment from that small object to the arbitrarily large one — such that changing even one byte of one transaction, anywhere in the block, changes the small object too, and there is no way to find a substitute transaction set that hashes to the same small object.

Everything in this chapter is the answer to "how do you build that commitment cheaply, verify it cheaply, and update it cheaply when the transaction set changes mid-mining." The answer has three moving parts: a Merkle tree that compresses an arbitrary transaction list into one 32-byte root, a coinbase transaction that turns "which miner, which height, which reward" into ordinary transaction bytes the Merkle tree already knows how to commit to, and an 80-byte header that packages that root together with the chain link, the timestamp, the difficulty target, and the nonce — the only bytes that change between one hash attempt and the next.

WHY THIS MATTERS FOR THE NEXT NINE CHAPTERS

The header is the single object this course keeps returning to. It is what miners grind (chapter 9), what peers gossip and sync before anything else (chapter 10, headers-first sync), what SPV wallets rely on exclusively because they never download a transaction body (chapter 10 again), and what every consensus rule in chapter 8 ultimately validates against. Get its 80 bytes exactly right and the rest of this course's protocol layer stops looking like magic.

DEEP CONTEXT · WHY THE FORMAT NEVER MOVED

Every full node and every SPV client that has ever run parses this exact 80-byte layout. Changing it is not a soft fork — headers are the one structure with zero spare interpretation room once you're past the version field, so resizing any field would be a hard fork touching literally every piece of software that has ever spoken the protocol. That is precisely why SegWit (chapter 12) and Taproot (chapter 13) — both consensus changes to how transactions commit their data — were built to leave the header untouched and instead smuggle their commitments inside the coinbase transaction, which the header already had a slot for. You will see this pattern again and again: when the header can't change, put the new idea somewhere the header already points to.

ARC 03 · NAIVE SOLUTION

Attempt #1: hash the whole block, every attempt

Derive it honestly before reaching for the Merkle tree. The simplest possible proof-of-work scheme needs no header at all: serialize the entire block — every transaction, in full — append a nonce, and hash the lot. If the hash is below the target, you found a block.

pseudocodenaive_mine() — the strawman, annotated
function naive_mine(transactions, prevHash, target) {
    let nonce = 0;
    while (true) {
        // serialize EVERY transaction, every attempt — could be megabytes
        let blob = serialize(prevHash, transactions, nonce);
        let hash = sha256d(blob);           // re-touches all of `transactions`
        if (hash < target) return { nonce, hash };
        nonce++;                              // try again — from scratch
    }
}

This gets the cryptography right: the hash still binds the nonce to every transaction, so it is not a correctness bug. It is a throughput bug, and an economic one — watch §4 quantify exactly how bad, and notice as you read it that the naive scheme also creates a perverse incentive: whichever miner includes fewer transactions gets to try more nonces per second than a competitor building a full block. A proof-of-work scheme that punishes you for filling blocks would have strangled Bitcoin's usefulness before it started.

ARC 04 · WHY IT FAILS

SHA-256 charges by the 64-byte chunk — and that's the whole story

SHA-256 does not hash a message all at once. It pads the input, splits it into 64-byte compression blocks, and runs 64 mixing rounds per block, threading a 32-byte chaining state from one block into the next. An 80-byte header pads to exactly two compression blocks. A 2 MB block pads to roughly 32,768 of them. Every nonce attempt against the naive scheme in §3 costs ~16,000× more compression rounds than one against a fixed 80-byte header — and that multiplier grows with block size, meaning naive mining gets slower precisely as Bitcoin gets more useful.

THE NUMBERS

Take a hash engine capable of 5 billion SHA-256 compressions/sec (a rough single modern ASIC core budget, ignoring pipelining for a moment). Against an 80-byte header (2 compressions/attempt) that is 2.5 billion header hashes/sec. Against a 2 MB naive block (~32,768 compressions/attempt) that collapses to ~152,000 block hashes/sec — five orders of magnitude slower, on identical silicon. And it gets worse: real ASICs exploit a trick unavailable to the naive scheme at all. The first 76 of the header's 80 bytes (everything except the nonce) are identical across every attempt in a mining job, so the first compression block's chaining state — the midstate — is computed once per job and cached in hardware. Every subsequent nonce only pays for the second compression block. Against a growing multi-megabyte blob, no comparable shortcut exists: touching any new transaction means re-walking a chaining state that depends on everything hashed before it.

So the requirement crystallizes: separate a small, fixed, midstate-friendly object from the arbitrarily large one, and bind them with a cryptographic commitment cheap enough to recompute whenever the transaction set changes. That commitment is a Merkle tree.

THE RESULT

An 80-byte header — version, previous block hash, Merkle root, timestamp, nBits, nonce — commits to an unbounded transaction set through exactly one 32-byte field. Grinding the nonce only ever re-hashes those 80 bytes; the Merkle root only needs recomputing when the transaction set itself changes (a new job, not a new nonce attempt), and §8 shows that recomputation costs O(log₂ n) hashes, not O(n).

ARC 06 · WHY THAT STILL COSTS

The Merkle root is cheap to update — but not free, and not innocent

The tree solves the throughput problem completely, but introduces three costs of its own that this course keeps coming back to:

  • Recomputation is O(log₂ n), not O(1). Every time a pool template adds a higher-fee transaction, swaps the coinbase's extranonce, or rolls the timestamp forward, the Merkle root must be recomputed — for a 2,000-transaction block that is ~11 hashes up the tree, not one, and pool infrastructure recomputes it thousands of times a second (chapter 9's Stratum job-update cadence).
  • Malleability propagates upward. Chapter 5 showed that pre-BIP143 a transaction's txid could be mutated without invalidating its signature. Because leaves of the tree are txids, mutating one transaction anywhere in the block changes the Merkle root, which changes the header, which changes the block hash other miners are extending — a purely cosmetic mutation becomes consensus-visible chain instability. This is exactly why malleability mattered enough to fix with a soft fork.
  • The tree's own duplicate-handling rule is not innocent. An odd number of leaves at any level forces a decision — duplicate the last one, as Bitcoin does — and §11 covers a real 2012 vulnerability (CVE-2012-2459) that lived exactly in that decision.
THE FOUR SPARE BYTES BECOME CONTESTED REAL ESTATE

The header still needed a slot to signal "this block supports rule change X" for soft forks (BIP9, 2016) — and the only field with spare bits was nVersion, originally just a monotonically increasing version number. Repurposing it as a 29-bit signalling bitfield (§8) turned out to collide with another demand: ASIC vendors wanted the version field's bits as extra nonce space ("version rolling") once the header's dedicated 4-byte nonce field was exhausted trillions of times per second. §11 covers the resulting 2017–2018 covert-AsicBoost controversy — a fight over four bytes that were never designed to hold this much responsibility.

THE ASYMMETRY THAT MAKES MINING CHEAP

Notice the load-bearing fact: everything in the body is represented by exactly 32 bytes in the header — the Merkle root. A miner's hot loop never looks at the body at all once a job is assembled; it mutates the nonce (and occasionally rolls the timestamp), re-hashes 80 bytes, and compares. The body only gets touched again when the job itself changes — a new transaction, a new extranonce — which is a job-management event, not a per-hash event. That single design choice is the entire reason ASIC hash rate is measured in exahashes/sec rather than blocks/sec.

ARC 08 · INTERNAL IMPLEMENTATION

Every one of the 80 bytes, decoded

This is the level of detail you'd need to write a header parser from a hex dump with no library. Six fields, in wire order.

Version (bytes 0–3) — a number that became a bitfield

Originally a simple incrementing integer: block format version 1 shipped at genesis. BIP9 (2016) repurposed it: if the top 3 bits equal 001 (i.e. version & 0xE0000000 == 0x20000000), the low 29 bits become independent signalling flags, one bit per pending soft fork, so miners can vote for several deployments simultaneously without any of them stepping on the old meaning of "version number" (old clients just see a version number in the billions and ignore it). Real example: mainnet block 800,000 has version = 0x341d6000 — top three bits 001, confirming BIP9 encoding, with the remaining bits recording which deployments that miner was signalling for. The same 29 bits are also the field ASICs grind as extra nonce space once they exhaust the dedicated nonce field (§6's "version rolling") — the two uses are supposed to be compatible by convention (miners are expected to preserve the top 3 bits and the specific deployment bits they don't intend to signal) but §11 covers exactly how that convention was violated.

Previous block hash (bytes 4–35) — the chain link

The double-SHA256 hash of the previous block's header — not the whole previous block, just its 80 bytes. This is the entire mechanism of "the blockchain is a chain": each header cryptographically points backward, so rewriting any historical block means recomputing every header hash from that point forward (and therefore redoing every unit of proof-of-work since), which chapter 8 turns into the precise cost model behind "immutability is economic, not mathematical." Stored in what the codebase calls internal byte order — the raw bytes SHA256d produces — which is the reverse of how block explorers print it; chapter 3 already made you feel this exact reversal for transaction ids.

Merkle root (bytes 36–67) — the commitment

The root of a binary hash tree over every transaction's id in the block, coinbase included, computed with the algorithm walked through below and in the simulator. One 32-byte field standing in for a transaction list that can be multiple megabytes.

Timestamp (bytes 68–71) — looser than it looks

Unix seconds, but validated by two much weaker rules than "the current time," both there to tolerate clock skew across a global, permissionless network with no authority to synchronize it:

  • Median-time-past: a new block's timestamp must exceed the median of the previous 11 blocks' timestamps — not simply be greater than the immediately preceding one. Using a median instead of a strict successor rule makes the check robust to any single miner lying about their block's time.
  • Future tolerance: a node will accept a block timestamped up to 2 hours ahead of its own clock (MAX_FUTURE_BLOCK_TIME) before rejecting it outright. Wide enough to absorb realistic NTP drift across a global miner population; narrow enough that timestamp cannot be used to meaningfully manipulate the difficulty retarget (chapter 9), which depends on comparing timestamps 2016 blocks apart.

nBits (bytes 72–75) — a 32-bit float for a 256-bit number

The compact target encoding: 1 byte of exponent, 3 bytes of mantissa — literally the same floating-point-style trick used elsewhere for representing a huge dynamic range in a small fixed field. Walk it against three real mainnet blocks, with the target computed live by the same BigInt arithmetic a node actually runs:

Expanding nBits — three real blocksSTEP-BY-STEP

The general formula, exactly as arith_uint256::SetCompact() implements it (§13 has the real function): let e = nBits >> 24 (the exponent byte) and m = nBits & 0x007fffff (the 23-bit mantissa magnitude — note only 23 bits, not 24; bit 23 is reserved as a sign flag, never a magnitude bit). Then:

mathcompact → target
target = m × 256^(e − 3)
         = m << (8 × (e − 3))    // e > 3, the normal case
         = m >> (8 × (3 − e))    // e ≤ 3, vanishingly rare in practice

Equivalently: place the 3 mantissa bytes as the most significant non-zero bytes of a 32-byte number, at a position such that they end exactly e bytes from the start — everything before them is zero, everything after them is zero. That is why every mainnet target in the widget above renders as a run of zero bytes, three "interesting" bytes, and then more zeros: it is not decoration, it is what a 3-significant-byte floating-point mantissa placed at a given exponent necessarily looks like.

THE SIGN-BIT QUIRK — A KNOWN OFF-BY-ONE, BY DESIGN

Bitcoin's compact format is inherited from OpenSSL's BN_bn2mpi/BN_mpi2bn, a general-purpose signed-bignum encoding — but Bitcoin targets are never negative. The collision: if the mantissa's own most significant byte happens to have its top bit set (≥ 0x80), that bit reads as the MPI sign flag, silently turning a positive target into what a naive decoder would treat as negative. The encoder's fix is a forced shift: prepend an extra 0x00 byte to the mantissa and increment the exponent by one, so the sign-bit position always lands on a byte that is genuinely zero. You can watch this exact shift happen live in the target-builder below — pick a target whose leading significant byte is 0x80–0xFF and see the encoder insert the padding byte and bump the exponent to compensate, at the cost of one bit of target precision every time it fires.

With the target in hand, three quantities fall out immediately:

  • Difficulty — defined as difficulty_1_target ÷ current_target, where difficulty-1 is the genesis target (nBits = 0x1d00ffff). It is a human-scaled ratio, not a protocol field — nothing in consensus ever reads "difficulty," only the raw target.
  • Expected hashes per block — a single hash succeeds with probability target ÷ 2²⁵⁶, so the expected number of attempts to succeed is its reciprocal, 2²⁵⁶ ÷ target. Since the difficulty-1 target is itself ≈ 2²²⁴, this simplifies to the figure everyone actually uses: expected hashes ≈ difficulty × 2³² (≈ difficulty × 4.295 billion).
  • Implied network hashrate — expected hashes divided by the ~600-second target block interval, chapter 9's starting point for the 2016-block retarget.

Nonce (bytes 76–79) — the field that runs out

A plain 32-bit counter, 0 to 4,294,967,295. At even modest 2024-era ASIC speeds a single machine exhausts the entire nonce space in a fraction of a second — which is precisely why real mining needs the extranonce (coinbase scriptSig) and version-rolling (§6) escape valves. Chapter 9 is the full treatment of nonce exhaustion, job rolling, and Stratum; this chapter only needs you to know the field is small on purpose — it's the one piece of the header that changes on every single hash attempt, so it has to be cheap to mutate and cheap to re-read, and 4 bytes sitting at a fixed offset is as cheap as it gets.

The coinbase transaction: where the miner gets paid, and where BIP34 lives

Every block's first transaction is the coinbase — structurally an ordinary transaction (chapter 3's byte format applies unchanged) with two deliberate irregularities that mark it as special:

  • The null outpoint. Its single input's previous-txid is 32 zero bytes and its previous-output-index is 0xffffffff — a pointer to nothing, because a coinbase doesn't spend an existing UTXO; it creates the block subsidy from nothing but the protocol's own inflation schedule.
  • The scriptSig is not a signature. With no real output being spent, there is nothing to sign. Consensus repurposes the scriptSig field as 2 to 100 bytes of arbitrary miner-controlled data — the only place in the entire protocol where bytes are free-form by design. In practice that space holds the extranonce (§9's grinding beyond the header's 4-byte nonce) and a human-readable pool tag: the genesis block's own coinbase scriptSig embeds the now-famous newspaper headline, "The Times 03/Jan/2009 Chancellor on brink of second bailout for banks."

BIP34 (activated 2012, block v2) narrowed that freedom by exactly one requirement: the scriptSig must begin with the block's own height, minimally encoded and pushed as data. On its face this sounds like a bookkeeping convenience — full nodes can now read a block's claimed height directly out of its coinbase without cross-referencing the chain. Its real consequence was much larger.

HOW A HEIGHT REQUIREMENT RETROACTIVELY FIXED A DIFFERENT BUG

In 2010, two pairs of blocks — heights 91,722 / 91,880 and 91,812 / 91,842 — contained coinbase transactions with byte-for-byte identical content (same scriptSig, same output script, same reward), which meant identical txids. Because the UTXO set is keyed by txid, the second coinbase in each pair silently overwrote the first one's still-unspent entry — a real, exploitable duplicate-txid collision. BIP30 patched this directly: reject any transaction whose txid already exists unspent in the UTXO set. BIP34 then fixed the same class of bug structurally: once every coinbase must embed a distinct block height, two coinbases at different heights can never again be byte-identical, so their txids can never collide — duplicate coinbase txids became not just rare but combinatorially impossible going forward. (Both original colliding block pairs are still hard-coded exceptions in Bitcoin Core's validation logic today, because disabling the BIP30 check entirely — tempting, since BIP34 makes new collisions impossible — would reopen the exact historical replay it fixed.)

The subsidy: 50 BTC, halving every 210,000 blocks, floored at zero

The coinbase's single output value is the block subsidy plus the sum of every included transaction's fee (fee itself being implicit — chapter 3 — the difference between a transaction's input and output values). The subsidy schedule is pure integer arithmetic: start at 50 BTC (5,000,000,000 satoshis), and every 210,000 blocks — roughly four years at the target 10-minute spacing — right-shift it by one bit:

mathsubsidy(height)
halvings = floor(height / 210000)
subsidy  = (halvings >= 64) ? 0 : (50 × 100_000_000) >> halvings   // satoshis

Integer right-shift, not floating-point division, matters here: it is exact, deterministic across every platform and language that has ever implemented the protocol, and it floors to zero rather than approaching it asymptotically forever. 5,000,000,000 satoshis needs only 33 bits, so by the 33rd halving — block height 6,930,000, expected around the year 2140 — the shift has already pushed every bit off the end and the subsidy is exactly zero satoshis. From that block forward, miner revenue is entirely fees, a transition this course returns to when discussing long-run security budget.

Block size, then weight: two limits, one soft fork apart

Nakamoto added a 1 MB serialized-size limit in 2010 — not a design principle from the whitepaper, a quiet anti-spam patch, and one Satoshi himself described as removable later "when we're near the limit." It wasn't removable without a hard fork, and the argument over whether and how to raise it became the multi-year block size war (chapter 15 territory). SegWit resolved it differently: not by raising a size limit, but by replacing "size" with weight, a unit that counts witness data (chapter 12: signatures moved outside the legacy transaction body) at a quarter of its byte cost:

mathblock weight
base_size  = serialized size WITHOUT witness data
total_size = serialized size WITH witness data
weight     = base_size × 3 + total_size          // == base×4 + witness_bytes
limit      = 4,000,000 weight units

A block of pure legacy transactions (no witness data, base_size == total_size) hits the weight limit at exactly 1 MB serialized — full backward compatibility with the old rule. A block entirely of witness-heavy SegWit spends can serialize up to roughly 4 MB before the same weight limit bites — but real blocks are a mix of legacy and SegWit outputs, non-witness overhead (headers, scripts, amounts) that count at full weight regardless of spend type, which is exactly why real-world blocks land around 1.7–2.3 MB rather than either extreme. Block 800,000 is a concrete data point: weight 3,992,881 (essentially at the 4,000,000 cap) at a serialized size of 1,634,536 bytes — a real block, near-maximal by weight, well under 2 MB by byte count.

Sigops: the other resource bound

Byte size and weight bound bandwidth and storage; they say nothing about CPU. A short script can still demand expensive signature-verification work — OP_CHECKMULTISIG with many public keys, for instance — so consensus separately caps signature operations per block at 80,000 (MAX_BLOCK_SIGOPS_COST, itself counted with the same ×4 witness discount as weight). Two independent budgets, two independent attack surfaces: weight bounds "how much data must every node store and relay," sigops bounds "how much CPU must every node spend validating it," and a block must satisfy both simultaneously.

Serialization order: why transactions can't be shuffled freely

A block lists its transactions in one fixed sequence, and that sequence is not arbitrary: if transaction B spends an output created by transaction A, A must appear before B in the same block. This is a topological-ordering constraint, not a total order — many valid orderings can exist for the same transaction set — but violating it is fatal: a validating node processes transactions in list order, updating the UTXO set as it goes, and a node that hasn't yet "seen" A's output cannot verify B's input against it. Miners exploit the freedom within that constraint constantly: chapter 11's CPFP (child-pays-for-parent) works by placing a low-fee parent immediately before the high-fee child that depends on it, satisfying the ordering rule while extracting a fee the parent alone wouldn't have earned.

ARC 09 · TRADEOFFS

Committing to a large structure with a small hash: five answers

"Fixed small header, large body reachable via one commitment field" is a general systems pattern, not a Bitcoin invention. Comparing answers honestly shows what Bitcoin's specific choices bought and cost:

Read it as a spectrum of "how much do you want the small object to know about the large one." Bitcoin's header knows the least it can get away with — one hash of transaction ids, nothing about account balances, nothing about execution results — and that minimalism is exactly what keeps header verification O(1) regardless of what happened inside the block. Ethereum's header knows more (state root) and pays for it with tries an order of magnitude more expensive to maintain per block; that's the tradeoff a state machine architecture forces on you, and it is not a design Bitcoin's own header would tolerate without becoming the naive strawman from §3 all over again, one layer up.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

The numbers a header design is judged by

  • Header hash cost: 2 SHA-256 compressions per attempt (80 bytes padded to 128), independent of block size — the entire point of §4–5.
  • Merkle recompute cost: ⌈log₂ n⌉ sha256d calls up the tree for n transactions — about 11 hash calls for a 2,000-tx block, negligible next to the billions of nonce attempts run against the resulting root.
  • Sigop budget: 80,000 per block — bounds worst-case per-block validation CPU independent of byte size, closing the gap that a pure weight limit leaves open (a small, sigop-dense script is cheap in bytes and expensive in CPU).
  • Header bandwidth vs. block bandwidth: 80 bytes vs. ~1.7–2.3 MB — roughly a 25,000× difference. A full header chain to block 880,000 is ~70 MB total; the corresponding full block chain is several hundred gigabytes. This asymmetry is the entire reason headers-first sync (chapter 10) and SPV clients exist: you can hold and verify an opinion about "which chain has the most work" for the price of a phone's storage.

ARC 11 · REAL-WORLD INCIDENTS

Three bugs that lived in these exact bytes

Incident 1: The duplicate-coinbase collision (2010) — BIP30/BIP34

Already walked through in §8: blocks 91,722/91,880 and 91,812/91,842 produced byte-identical coinbase transactions, and because the UTXO set is keyed purely by txid, the later block's coinbase silently overwrote the earlier one's unspent entry in the database — a real collision, not a theoretical one. BIP30 added an explicit "does this txid already exist unspent?" check (a real per-transaction DB lookup, itself later a minor DoS concern raised on the mailing list), and BIP34 closed the door structurally by making every coinbase's content depend on a unique height. Root cause: a database keyed by a value (txid) that the protocol did not yet guarantee was unique. Lesson: "practically always unique" is not "unique" — it took one coincidence (or one deliberate test) to prove it.

Incident 2: CVE-2012-2459 — the Merkle duplication vulnerability

Bitcoin's duplicate-last-leaf rule for odd-length tree levels (§6) has a subtle consequence: it is possible to construct a block whose transaction list, when Merkle-hashed, produces the identical root as a different transaction list — specifically, one where duplicating a real transaction (creating two identical adjacent leaves) yields the same root as a list where that transaction simply appeared once at an odd position and got auto-duplicated by the algorithm. A block exploiting this could pass Merkle-root validation while carrying an ambiguous, non-unique interpretation of which transactions it actually contained — with some node implementations of the era vulnerable to a crash (an unhandled duplicate-transaction case) when processing such a block. The fix Bitcoin Core shipped was not a new tree algorithm — it added an explicit check in block validation that rejects any block whose transaction list contains two adjacent identical hashes at any level of the tree, closing the ambiguity by rejecting the inputs that create it rather than redesigning the hash function. §13 shows this exact check in the real ComputeMerkleRoot() source, and the simulator in §15 flags this same condition live when you deliberately duplicate a transaction.

Incident 3: Covert AsicBoost (2017–2018) — a fight over four bytes

§6 and §8 both flagged the collision: BIP9 wants the version field's low 29 bits for soft-fork signalling; ASIC vendors want the same bits as extra nonce space once the dedicated 4-byte nonce is exhausted trillions of times a second ("version rolling," an application of the AsicBoost technique, U.S. Patent 9,974,978). Used overtly — publicly, with version bits chosen to avoid colliding with any active soft-fork deployment — this is a legitimate, disclosed optimization. Evidence surfaced in 2017 that it was also being used covertly: some mining hardware appeared to be exploiting a related trick (grinding the Merkle root via coinbase/transaction-order permutations to find internal SHA-256 midstate collisions) without any public signalling at all, undetectable from outside the mining pool. The controversy became entangled with the block size debate because SegWit's transaction-structure changes (chapter 12) happened to make the covert variant of the technique substantially harder to pull off — giving opponents of covert AsicBoost an added reason to push for SegWit's activation, and giving its beneficiaries an added reason to resist. Root cause: the header never allocated separate, non-overlapping bit ranges for "soft-fork signalling" and "hardware optimization," so both interests were forced to compete for the same four bytes, some of it in the open and some of it not.

class CBlockHeader
{
public:
    // header — EXACTLY 80 bytes serialized, never resized since block 0
    int32_t      nVersion;        // bytes 0..3   — BIP9 bitfield since 2016
    uint256      hashPrevBlock;   // bytes 4..35  — the chain link
    uint256      hashMerkleRoot;  // bytes 36..67 — commitment to every tx
    uint32_t     nTime;           // bytes 68..71 — median-time-past + 2h future rule
    uint32_t     nBits;           // bytes 72..75 — compact target
    uint32_t     nNonce;          // bytes 76..79 — the only field that changes per hash attempt

    uint256 GetHash() const
    {
        // SerializeHash == SHA256d over exactly these 80 serialized bytes.
         * No transaction ever touches this call.                        */
        return SerializeHash(*this);
    }
};

The Merkle root, computed by the function that carries the CVE-2012-2459 fix directly in its signature — notice the mutation flag is detected, not prevented by changing the tree shape:

C++consensus/merkle.cpp — ComputeMerkleRoot() (simplified, faithful to source)
uint256 ComputeMerkleRoot(std::vector<uint256> hashes, bool* mutated)
{
    bool mutation = false;
    while (hashes.size() > 1) {
        if (mutated) {
            // Flag any level with adjacent identical hashes BEFORE padding —
             * this is the exact condition CVE-2012-2459 exploited.        */
            for (size_t pos = 0; pos + 1 < hashes.size(); pos += 2)
                if (hashes[pos] == hashes[pos + 1])
                    mutation = true;
        }
        if (hashes.size() & 1)
            hashes.push_back(hashes.back());  // odd level: duplicate the last leaf

        // pairwise SHA256d up one level
        for (size_t i = 0; i < hashes.size(); i += 2)
            hashes[i/2] = Hash(hashes[i], hashes[i+1]);   // SHA256d(concat)
        hashes.resize(hashes.size() / 2);
    }
    if (mutated) *mutated = mutation;
    return hashes.empty() ? uint256() : hashes[0];
}

nBits expansion — the exact 23-bit-mantissa, sign-flag-aware decode from §8:

C++arith_uint256.cpp — SetCompact() (simplified, faithful to source)
uint32_t arith_uint256::SetCompact(uint32_t nCompact, bool* pfNegative, bool* pfOverflow)
{
    int nSize = nCompact >> 24;                    // exponent byte
    uint32_t nWord = nCompact & 0x007fffff;         // 23-bit mantissa magnitude

    if (nSize <= 3) {
        nWord >>= 8 * (3 - nSize);
        *this = nWord;
    } else {
        *this = nWord;
        *this <<= 8 * (nSize - 3);            // place mantissa at the right byte offset
    }
    // bit 23 of nCompact is a SIGN flag, inherited from OpenSSL's MPI
     * bignum format — Bitcoin targets are never actually negative, but
     * an encoder must still avoid accidentally setting this bit (§8's quirk).
    *pfNegative = nWord != 0 && (nCompact & 0x00800000) != 0;
    *pfOverflow = nWord != 0 && ((nSize > 34) ||
                  (nWord > 0xff && nSize > 33) ||
                  (nWord > 0xffff && nSize > 32));
    return nCompact;
}

C++validation.cpp — GetBlockSubsidy() + the BIP34 coinbase check
CAmount GetBlockSubsidy(int nHeight, const Consensus::Params& params)
{
    int halvings = nHeight / params.nSubsidyHalvingInterval;  // 210,000
    if (halvings >= 64) return 0;         // explicit floor — belt over the shift's own floor
    CAmount nSubsidy = 50 * COIN;             // 5,000,000,000 satoshis
    nSubsidy >>= halvings;                    // integer shift — deterministic, hits 0 at halving 33
    return nSubsidy;
}

/* BIP34: reject the block unless its coinbase scriptSig begins with
 * the serialized height as a minimally-encoded CScriptNum push.        */
CScript expect = CScript() << nHeight;
const CScript& scriptSig = block.vtx[0]->vin[0].scriptSig;
if (scriptSig.size() < expect.size() ||
    !std::equal(expect.begin(), expect.end(), scriptSig.begin())) {
    return state.Invalid("bad-cb-height");
}
WHY THE MERKLE FIX IS A VALIDATION CHECK, NOT AN ALGORITHM CHANGE

Bitcoin Core's response to CVE-2012-2459 is worth noticing precisely because of what it didn't do: it didn't switch to a tree design immune to duplicate-leaf ambiguity (which would be a hard fork — every node computing Merkle roots differently). It added a detector inside the existing algorithm and rejected inputs that trigger the ambiguity, which is a policy-level tightening compatible with the existing consensus rule. The general lesson generalizes past this one CVE: when a bug lives in how inputs are interpreted rather than in the hash function itself, the cheapest fix is usually "reject the interpretation," not "replace the cryptography."
