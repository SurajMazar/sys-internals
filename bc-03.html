BLOCKCHAIN FUNDAMENTALS · CHAPTER 03

Merkle Trees &
Authenticated Data Structures

A Bitcoin block header is 80 bytes and commits to every one of the block's thousands of transactions through a single 32-byte field. A phone with a few kilobytes of bandwidth can verify that its payment landed in a block containing millions of dollars of other people's transactions — without downloading any of them. Neither fact is magic. Both are the direct, derivable consequence of one 1979 data structure: the Merkle tree. This chapter builds it from the ground up, breaks it exactly the way Bitcoin broke it in 2012, and generalizes it into the structure that lets Ethereum commit to mutable state.

ARC 01 · THE PROBLEM

Commit to N items with one hash; prove membership without shipping N items

Every serious system that tracks a large, changing collection of things eventually needs to answer the same two questions cheaply: "has this collection changed?" and "is this one item actually in it?" A Bitcoin block holds thousands of transactions. Ethereum's state holds hundreds of millions of accounts. A certificate transparency log holds billions of issued TLS certificates. In every case you want a short, fixed-size fingerprint you can publish once — and you want anyone holding a single item to be able to prove it belongs to the set the fingerprint describes, without handing them (or receiving from them) the whole set.

State that requirement precisely, because the precision is what makes the rest of the chapter derivable rather than memorized. For a set S of N items, you want:

  • A commitment C(S) of O(1) size — 32 bytes, regardless of whether N is 4 or 4 billion — such that it is computationally infeasible to find a different set S′ ≠ S with C(S′) = C(S) (binding), and such that C(S) reveals nothing about the items beyond their existence (hiding is not always required — Bitcoin's tree is not hiding, transactions are public).
  • A proof π(x) of sublinear size — ideally O(log N) — that a verifier holding only C(S) and x can check in O(log N) time, accepting iff x ∈ S, and such that no adversary can construct a valid-looking π for an x that isn't actually a member.

Notice this is a different problem from the one chapter 2 solved. Hashing a whole file and comparing digests proves two parties have the same blob; it says nothing useful about a single piece of a much bigger blob, because checking one piece still means re-hashing everything. This chapter is about decomposing a large committed set into a structure where membership of one element can be checked without touching the other N − 1.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Chapter 5 links blocks together with hash pointers so that history is append-only in evidence — but a hash pointer to a block says nothing about which of that block's thousands of transactions is the one you care about. Chapter 4's signatures authorize a single message; Merkle trees let you authorize — with one signature or one proof-of-work — an entire committed set of messages at once. Every later chapter that says "the header commits to X" is quietly leaning on the machinery you derive today.

ARC 02 · HISTORICAL CONTEXT

1979 to today: one idea, four independent rediscoveries

Ralph Merkle described the hash tree in his 1979 Stanford PhD work on public-key systems, patented as "Method of providing digital signatures" — originally built to make one-time signature schemes reusable, not to build ledgers. It then went dormant in cryptography papers for two decades before four separate engineering communities rediscovered it for four different reasons. Click through — each rediscovery bent the structure to fit a new constraint, and those bends are exactly the variants covered later in this chapter.

DEEP CONTEXT · WHY MERKLE BUILT THIS FOR SIGNATURES, NOT LEDGERS

Merkle's original motivation was to turn a fragile one-time signature scheme (Lamport signatures — sign once, and the private key is burned) into a reusable one: put many one-time public keys at the leaves of a hash tree, publish only the root, and each signature ships the leaf's authentication path alongside it. This is the ancestor of the "Merkle signature scheme," still relevant today as the template for post-quantum, hash-based signatures (SPHINCS+) — because unlike RSA or elliptic-curve signatures, security here rests only on hash-function resistance, which quantum computers do not obviously break. Chapter 4's discrete-log-based signatures and this chapter's hash tree are, historically, siblings from the same 1979 paper.

ARC 03 · NAIVE SOLUTION

Attempt #1: one hash over the concatenation of everything

The obvious commitment scheme is the one every engineer reaches for first: hash the whole set as one blob. Write it down honestly, because it already gets the "commitment" half of the requirement completely right — it's the "proof" half that will fall apart in the next section.

Pythonnaive_commitment.py — the strawman, annotated
import hashlib

def commit(items: list[bytes]) -> bytes:
    # One SHA-256 over every item, concatenated in order.
    # This is a perfectly good O(1)-size, binding commitment —
    # finding a different item list with the same digest means
    # breaking SHA-256's collision resistance (chapter 2).
    h = hashlib.sha256()
    for item in items:
        h.update(item)
    return h.digest()

def prove_membership(items: list[bytes], index: int) -> list[bytes]:
    # To let a verifier check that items[index] is really in the
    # set, what do we hand them? There is no shortcut: verifying
    # commit() requires recomputing it, which requires every item.
    return items   # the ENTIRE list. Every time. For one element.

This is not a joke architecture — SHA-256 over concatenated data is a completely legitimate way to prove "these two parties have byte-identical copies of a dataset," and you will use exactly this pattern for whole-file integrity checks throughout your career. It is also literally how a naive blockchain might first try to commit a block's transaction list to its header: one hash, computed over every transaction, in order.

ARC 04 · WHY IT FAILS

The bandwidth blowup is unbounded, not just inconvenient

Quantify it, because "sending the whole block seems wasteful" undersells how badly this scales. A verifier who wants to confirm one transaction's inclusion under the flat-hash scheme must receive and re-hash all N items — proof size is O(N), with no way to do better, because the commitment function itself has no internal structure a verifier can hook into partway through.

  • A Bitcoin block, concretely. A typical block carries roughly 2,000–3,000 transactions at ~250–500 bytes each — call it 1–2 MB. Proving one transaction is in the block, under the flat scheme, costs transmitting and re-hashing that entire 1–2 MB. A phone on a metered connection pays megabytes to learn one bit of information: "yes/no."
  • A certificate transparency log, concretely. Production CT logs (chapter 11 revisits this) hold billions of certificates. A flat commitment would require downloading gigabytes to check whether a single certificate for your own domain was ever logged — for every check, forever, as the log only grows.
  • The scaling is the actual problem, not the constant. The ratio of "work to prove one item" to "size of the set" is exactly 1 — it never improves. Whatever bandwidth or CPU budget you have today, a dataset that is 10× larger next year costs 10× more to prove against, forever. There is no economy of scale; there is a diseconomy of scale.
THE NUMBERS

At ~2,500 transactions/block, a flat proof costs roughly 1.2 MB. The structure this chapter derives will cost ⌈log₂ 2500⌉ = 12 sibling hashes × 32 bytes = 384 bytes, plus the 80-byte header — 464 bytes total. That is a ~2,650× reduction, and it is not a constant-factor engineering win — the gap is N / log₂N, which diverges as N grows. The naive scheme doesn't just lose today; it loses by more every year the dataset grows. Something better than "hash everything" is required in kind, not just in degree.

The fix has to come from structure: instead of one hash absorbing all N items in a single flat pass, build intermediate checkpoints that let a verifier skip most of the data while still being cryptographically bound to all of it. That's a tree.

ARC 05 · BETTER SOLUTION

Deriving the binary hash tree

Build it bottom-up, in the same order you'd derive it at a whiteboard. Hash every item individually first — these become leaves. Then, instead of hashing all the leaf hashes together in one pass (which is just the naive scheme one level up), pair them and hash each pair separately, producing half as many internal nodes. Repeat pairing-and-hashing until exactly one hash remains: the root. Step through it with genuine SHA-256 output — every hash below is real, computed by the same code that runs in this chapter's simulator.

Building a 4-leaf Merkle tree, with real SHA-256 outputSTEP-BY-STEP

Now state precisely why this buys you what section 4 needed. Call the leaf you care about x. To recompute the root, you do not need every other leaf — you only need, at each level, the one sibling hash required to compute that level's parent. Everything below the sibling is already absorbed into it by hashing; you don't need to see it, you just need to trust the hash that summarizes it.

THE CLAIM, STATED AND PROVED

Claim: an inclusion proof for one leaf out of N requires exactly ⌈log₂ N⌉ sibling hashes. Proof sketch: each level of the tree halves the number of nodes (pairing two into one), so the tree has exactly ⌈log₂ N⌉ levels above the leaves. Walking from a leaf to the root crosses every level exactly once, and at each level you need exactly one piece of information you don't already have — the sibling of the node you just computed — to compute the next node up. One sibling per level × ⌈log₂N⌉ levels = ⌈log₂N⌉ hashes, independent of everything else in the tree. At 2,500 transactions that's 12 hashes; at 4 billion it's 32 — the proof grew by less than 3× while N grew by six orders of magnitude.

Verification is the mirror image of construction: start from the leaf, combine with each supplied sibling hash in the correct left/right order, climb one level, repeat, and compare the final result to the trusted root. Using the tree built above — proving leaf tx2 is included requires exactly two sibling hashes: leaf3 (to its right) and node01 (to its left, one level up):

walkthroughverifying leaf tx2's inclusion proof, real values
given: leaf2 = H(0x00 || "tx2:Carol→Dave:0.75")
       proof = [ (leaf3, RIGHT), (node01, LEFT) ]
       trusted_root = 0f8203831d2bb6d6...d157fa0

step 1:  node23' = H(0x01 || leaf2  || leaf3 )   // leaf3 is on our RIGHT
step 2:  root'   = H(0x01 || node01 || node23')  // node01 is on our LEFT
step 3:  root' == trusted_root ?  →  YES. leaf2 is proven included.

Nobody transmitted tx0, tx1, or tx3's contents — only their hashes, already folded into leaf3 and node01. That is the entire trick, and it is why the mechanism scales logarithmically: every sibling hash you receive is a compressed, tamper-evident summary of everything underneath it.

ARC 06 · WHY THAT STILL HURTS

Three cracks in the plain binary tree

The structure from §5 is correct and is, in fact, exactly what Bitcoin ships. But building it forces three decisions that a naive first pass gets wrong, and each one has produced a real production incident or a real architectural fork in how later systems built on the idea:

  • What do you do with an odd node? Pairing requires an even count at every level. Four, eight, sixteen leaves pair perfectly; five, six, or eleven do not — some level will have a lone, unpaired hash. You need a rule, and §11 shows that Bitcoin's rule (duplicate the odd one) was not a free choice — it was CVE-2012-2459.
  • Inclusion is easy; exclusion is not. This tree proves "x is in S" cheaply. It cannot cheaply prove "x is not in S" — the only way to prove absence is to reveal the entire leaf set and let the verifier confirm x isn't among them, which is right back to O(N). Some applications (revocation lists, sparse account state) need non-membership proofs just as often as membership ones — this motivates the sorted Merkle tree in §9.
  • The tree is a fixed snapshot, not a database. This structure is built once, over a static array, indexed by position. It has no concept of "look up the balance for address 0xAB…" — only "leaf number 7." Ethereum's state is a mutable key→value mapping with hundreds of millions of entries that changes every block; rebuilding a flat binary tree over the whole thing per block is economically absurd. This motivates fusing the hash tree with a search structure — the Merkle-Patricia trie in §9.
A FOURTH CRACK, QUIETER BUT JUST AS REAL

Nothing so far stops a leaf's hash from being confused with an internal node's hash — both are just 32-byte SHA-256 outputs with no marking of what they are. If leaf hashing and internal-node hashing use the identical, unprefixed function, a well-crafted 64-byte "transaction" can be byte-identical to the concatenation of two internal hashes, making it ambiguous whether the tree has one leaf there or two leaves underneath. Bitcoin's original design has exactly this gap (it is the mechanism behind CVE-2017-12842, covered in §11); this chapter's own tree implementation in §8 closes it with domain separation — a one-byte prefix that makes "this is a leaf" and "this is an internal node" cryptographically distinguishable.

ARC 08 · INTERNAL IMPLEMENTATION

Byte layouts, the hash primitive, and the construction algorithm

Now the level of detail you'd need to implement this yourself. Three pieces: (a) the exact byte layout hashed at each node, (b) the SHA-256 primitive itself (implemented for real, in JavaScript, and used by every widget in this chapter — including the simulator in §15), (c) the tree-construction and proof algorithms as a state machine.

(a) Byte layout: domain separation, precisely

This chapter's tree — and RFC 6962's Certificate Transparency log, which specifies this exact convention — hashes leaves and internal nodes with different, explicit prefixes so a 32-byte hash can never be misread as the wrong kind of node:

NODE TYPEPREIMAGE (bytes hashed)WHY THE PREFIX
Leaf0x00 ‖ item_bytesA leaf's hash can never equal an internal node's hash unless SHA-256 collides across the 0x00/0x01 boundary — a strictly harder problem than colliding two arbitrary unprefixed inputs.
Internal node0x01 ‖ left_hash(32B) ‖ right_hash(32B)Fixed 65-byte preimage; the left/right order is part of the hashed data, so swapping children changes the hash — position is authenticated, not just content.
BITCOIN DOES NOT DO THIS — AND THAT'S THE ROOT OF §11's SECOND CVE

Bitcoin's actual leaf hash is SHA256d(serialized_transaction) and its actual internal-node hash is SHA256d(left ‖ right) — no prefix byte, same function, applied to both roles. (SHA256d is SHA-256 applied twice, chosen to blunt certain length-extension and "chosen prefix" concerns Bitcoin's designer wanted to avoid at the primitive level — chapter 2 covers length extension in depth.) The absence of a leaf/internal-node prefix means a 64-byte transaction is exactly the same shape as two concatenated 32-byte hashes — the ambiguity §6 warned about, and the mechanism behind CVE-2017-12842.

(b) SHA-256, implemented — the primitive everything above rests on

Chapter 2 derives SHA-256's compression function round by round; here it is treated as a verified black box H : {0,1}* → {0,1}^256 — except this chapter actually ships the implementation, in full, so that every hash value on this page (including the ones you just read in §5) is a genuine computation, not a plausible-looking placeholder string.

JavaScriptsha256.js — the exact module powering every widget on this page
function sha256Bytes(bytes) {
  const K = new Uint32Array([0x428a2f98, 0x71374491, /* … 62 more round constants,
    the fractional cube roots of the first 64 primes … */]);
  let H = new Uint32Array([0x6a09e667, 0xbb67ae85, /* … fractional square
    roots of the first 8 primes — the fixed IV … */]);
  // 1. Pad: append 0x80, zero bytes, then a 64-bit big-endian bit length,
  //    until the total is a multiple of 64 bytes (512-bit blocks).
  // 2. For each 512-bit block: expand 16 words into 64 via the message
  //    schedule (σ0/σ1 mixing functions), then run 64 compression rounds
  //    (Ch, Maj, Σ0, Σ1 — chapter 2, §8, walks every round live).
  // 3. Add the block's working variables back into H (Davies-Meyer).
  return bigEndianBytes(H);  // 32 bytes, genuinely computed
}

The full, unabridged implementation — padding, message schedule, all 64 rounds, correctly handling messages longer than one block — runs in this page's <script> and has been checked against the standard NIST test vectors (SHA-256("abc"), the empty string, and a million-character stress input) before being used anywhere on this page. The Merkle tree logic in §5, §7, and the simulator in §15 call this exact function; nothing you've seen is a fake-looking hex string.

ARC 09 · TRADEOFFS

Same idea, six shapes: comparative anatomy

§6 identified three cracks in the plain binary tree — odd nodes, no exclusion proofs, no mutable key lookup. Each production system patched a different subset, and none of them is free:

STRUCTURESHAPEWHAT IT BUYSWHAT IT COSTS
Flat hashOne hash over concatenation trivial to implement O(N) proofs no partial verification
Unsorted binary Merkle treeBalanced binary tree, leaves in insertion order (Bitcoin) O(log N) inclusion proofs simple, fast to build no non-inclusion proofs odd-count rule is a real attack surface (§11)
Sorted Merkle treeLeaves sorted by key before hashing non-inclusion proofs — prove x∉S by showing the two neighbors that would bracket it rebuilding on insert shifts positions reveals ordering relationships between leaves
Merkle-Patricia trieRadix trie (16-way, hex nibbles) fused with hashing — Ethereum's state/tx/receipt roots O(log N) key→value lookups with proofs handles mutable state efficiently path compression via extension nodes branch nodes store up to 16 children hashes — proofs carry more bytes per level RLP encoding overhead
Merkle mountain range (MMR)Forest of perfect binary trees, append-only O(1) amortized append consistency proofs between any two sizes append-only — no updates or deletions less familiar, fewer battle-tested implementations
Verkle tree (research / proposed for Ethereum)Vector-commitment tree (KZG or similar polynomial commitments) proof size independent of branching factor — a 16-way node's proof is one small commitment, not 16 hashes needs a trusted setup or pairing-friendly curve not yet in production consensus as of this writing

Read the table as proof by exhaustion, same as chapter 1's execution-model comparison: every variant trades proof size, update cost, or feature (non-inclusion, mutability) against implementation complexity — none dominates. Bitcoin picked the simplest cell in the table because its transaction list is append-only and read-only after mining; Ethereum picked a much more expensive cell because its state is mutated by nearly every transaction and must support point lookups by address, not just position.

The 464-byte SPV proof from §4 is the headline number, but it's worth being precise about what's actually being trusted. The verifier trusts: the block header is valid (chapter 8's proof-of-work check, cheap — one more hash), and SHA-256 is second-preimage resistant (nobody can find a different 32-byte value that hashes to a sibling hash already in the proof). No trust is placed in the peer who handed over the proof — a malicious peer can only fail to produce a valid proof, never forge one for a false claim, without breaking the hash function itself.

WHAT ACTUALLY HAS TO BREAK FOR THIS TO FAIL

Not the hash function — SHA-256's 2^128 birthday bound on collisions and 2^256 preimage cost are far beyond any feasible computation, now or for the foreseeable future (chapter 2's security-margin discussion applies unchanged here). The realistic attack surface is protocol-level ambiguity in how the tree is constructed and validated — exactly the two CVEs in §11, both of which are implementation/specification bugs, not cryptanalysis of SHA-256 itself. This is the pattern to internalize: the primitive is essentially unbreakable; the scaffolding around it is where real systems actually get hurt.

ARC 11 · REAL-WORLD INCIDENTS

Two CVEs and one growth attack, in the trees you just built

Incident 1: CVE-2012-2459 — the odd-node duplication rule

Reported on Bitcointalk in 2012 by Sergio Demian Lerner, assigned CVE-2012-2459, and quietly fixed before it was ever exploited. §6 flagged the rule: when a level has an odd number of hashes, Bitcoin duplicates the last one to make the count even. That single design choice means two different transaction lists can produce an identical Merkle root. Concretely: take a valid 5-transaction block [A, B, C, D, E]. An attacker appends a duplicate of the last transaction to get a 6-transaction list [A, B, C, D, E, E] — invalid, because it double-spends whatever E spent. Under the duplication rule, the level-by-level hashing of both lists produces the same intermediate pairs, and therefore the same root. This chapter's own SHA-256 implementation confirms it is not a theoretical concern — computing both roots with the exact Bitcoin-style (undelimited, no domain separation) construction gives:

verifiedgenuine output from this page's SHA-256 module
listA = [tx0, tx1, tx2, tx3, tx4]              (5 items, odd)
listB = [tx0, tx1, tx2, tx3, tx4, tx4]         (6 items — tx4 duplicated)

root(listA) = 34d63c928ca601f9...15be6d6894aa85757
root(listB) = 34d63c928ca601f9...15be6d6894aa85757
root(listA) == root(listB)  →  true

The exploit path is not "an invalid block gets accepted" — full nodes validate every transaction independently and would reject listB's double-spend regardless of the root. The real damage is a denial-of-service on Bitcoin Core's invalidity cache: a node caches the header hash of blocks it has already proven invalid, to avoid re-validating them. Because the header commits to the root, not the transaction list, an attacker who gets the mutated (invalid, duplicate-transaction) version of a block to a victim node first poisons that node's cache against the block's header hash — the node then refuses the legitimate version of the same block from any honest peer until restarted, an effective way to eclipse a targeted node off a specific block. The fix did not change the tree algorithm — Bitcoin Core still duplicates odd nodes today. Instead, ComputeMerkleRoot() was extended to track a mutated flag: while building each level, it checks whether any adjacent pair of hashes it just duplicated-and-paired are identical, and if so marks the tree mutated; block validation then rejects any block whose Merkle computation is flagged mutated, closing the ambiguity at the validation layer rather than the construction layer.

Incident 2: CVE-2017-12842 — leaves masquerading as internal nodes

The gap §8 called out directly: Bitcoin hashes leaves and internal nodes with the same unprefixed function, so a 64-byte transaction is structurally identical to two concatenated 32-byte hashes. Discovered in 2017, this lets an attacker construct a scenario where a lightweight (SPV) client — which does not download or validate full transactions, only checks that a Merkle proof resolves to the trusted root — can be shown a proof that resolves correctly whether one specific 64-byte value is interpreted as a single transaction or as an internal node summarizing two other, entirely different transactions. A full node is not fooled: it also checks that the number of transactions the peer claims to be sending matches the shape of Merkle tree implied by the proof, and SHA-256d's second-preimage resistance makes it astronomically unlikely that a genuine 64-byte transaction accidentally equals two real internal hashes. SPV clients historically skipped that shape check. Mitigations: honest servers can tell SPV clients the true transaction count so they can validate tree shape themselves; a proposed consensus-layer fix (part of the "consensus cleanup" soft fork discussions) would make 64-byte transactions invalid outright, since a transaction that small cannot carry meaningful value securely anyway.

Incident 3: Ethereum's 2016 state-growth denial-of-service attacks

Not a bug in the Merkle-Patricia trie's math — a demonstration of §9's warning that mutable authenticated structures have a cost proportional to how much state exists, and that cost was under-priced. In mid-2016, attackers exploited gas costs that didn't reflect the real I/O and trie-maintenance cost of certain opcodes (EXTCODESIZE, SLOAD, and contract creation among them), flooding the network with cheap transactions that created millions of near-empty accounts and ballooned the state trie's size and depth, slowing down every node that had to read and update it. The response was EIP-150 (repricing I/O-heavy opcodes to reflect actual trie-access cost) and EIP-161 (removing empty accounts from state entirely, after a grace period, to undo the bloat). The lesson generalizes past Ethereum: when your commitment structure is mutable and its per-operation cost is hidden behind a flat fee, the fee schedule itself becomes an attack surface.

First, the domain-separated construction this chapter uses throughout — note how the proof object carries enough information (sibling hash and its side) to make verification a pure function of the leaf and the proof, nothing else:

Pythontree.py — construction, proof extraction, verification
from dataclasses import dataclass
from hashlib import sha256

LEAF_PREFIX, NODE_PREFIX = b"\x00", b"\x01"

def leaf_hash(item: bytes) -> bytes:
    return sha256(LEAF_PREFIX + item).digest()

def node_hash(left: bytes, right: bytes) -> bytes:
    return sha256(NODE_PREFIX + left + right).digest()

def build_tree(items: list[bytes]) -> list[list[bytes]]:
    # levels[0] = leaf hashes; levels[-1] = [root]
    level = [leaf_hash(i) for i in items]
    levels = [level]
    while len(level) > 1:
        if len(level) % 2:
            level = level + [level[-1]]        # odd-node rule — see bitcoin_style.py for the guarded version
        level = [node_hash(level[i], level[i+1]) for i in range(0, len(level), 2)]
        levels.append(level)
    return levels

@dataclass
class ProofStep:
    sibling: bytes
    is_left: bool   # True → sibling goes on the LEFT of our running hash

def get_proof(levels: list[list[bytes]], index: int) -> list[ProofStep]:
    proof = []
    for level in levels[:-1]:
        is_right_node = index % 2 == 1
        sib_index = index - 1 if is_right_node else index + 1
        sib_index = min(sib_index, len(level) - 1)   # duplicated tail node
        proof.append(ProofStep(level[sib_index], is_left=is_right_node))   # if I'm the right child, my sibling is on the left
        index //= 2
    return proof

def verify_proof(item: bytes, proof: list[ProofStep], root: bytes) -> bool:
    running = leaf_hash(item)
    for step in proof:
        running = node_hash(step.sibling, running) if step.is_left else node_hash(running, step.sibling)
    return running == root   # O(log N) hashes, zero knowledge of any other leaf

Now the piece that actually matters for §11: Bitcoin's construction, translated faithfully from src/consensus/merkle.cpp's ComputeMerkleRoot(). Notice the fix is a side-channel observation during construction, not a change to the pairing rule itself:

Pythonbitcoin_style.py — duplicate-on-odd + the CVE-2012-2459 mutation flag
def compute_merkle_root(tx_hashes: list[bytes]) -> tuple[bytes, bool]:
    """Faithful to ComputeMerkleRoot() in src/consensus/merkle.cpp.
    Returns (root, mutated) — mutated=True means CheckBlock() must
    reject this block outright, regardless of anything else about it."""
    level = list(tx_hashes)
    mutated = False
    while len(level) > 1:
        # THE FIX: before duplicating, check whether this level already
        # contains adjacent identical hashes — that's the exact signature
        # of a transaction list crafted to alias another one's root.
        for i in range(0, len(level) - 1, 2):
            if level[i] == level[i + 1]:
                mutated = True
        if len(level) % 2:
            level.append(level[-1])             # the ORIGINAL duplicate-on-odd rule, unchanged
        level = [sha256d(level[i] + level[i+1]) for i in range(0, len(level), 2)]
    return level[0], mutated
WHY IT WAS BUILT THIS WAY — THE DESIGN DECISION WORTH STEALING

Bitcoin Core's maintainers could have "fixed" CVE-2012-2459 by changing how odd nodes are paired — carry the lone node up unchanged instead of duplicating it, for instance. They didn't, because that would have been a consensus-breaking change: every historical block's Merkle root was computed with the duplicate rule, and changing the rule would invalidate the entire chain's history retroactively. Instead they added a detector for the specific ambiguous condition (adjacent identical hashes at any level) and rejected blocks that trigger it — a fix that changes validation behavior going forward without altering a single historical hash. This is the general pattern for patching a consensus system after the fact: prefer tightening acceptance criteria (a soft fork, chapter 10) over changing the function that produced already-canonized history.

Finally, the shape Ethereum needed instead — a sketch of the Merkle-Patricia trie's node types, enough to see why point lookups by key are native here in a way they never were for the plain binary tree:

Pythonpatricia/nodes.py — the three Merkle-Patricia trie node types, simplified
class LeafNode:      # remaining nibble path + the value itself
    path: bytes; value: bytes

class ExtensionNode: # shared nibble prefix + hash of the single child (path compression)
    shared_nibbles: bytes; child_hash: bytes

class BranchNode:    # 16 child-hash slots (one per hex nibble) + an optional value
    children: list[bytes | None]  # length 16
    value: bytes | None

def get(root_hash: bytes, key: bytes) -> bytes | None:
    nibbles = to_nibbles(key)              # key, split into 4-bit nibbles
    node = load(root_hash)
    while nibbles:
        if isinstance(node, LeafNode):
            return node.value if node.path == nibbles else None
        if isinstance(node, ExtensionNode):
            if not nibbles.startswith(node.shared_nibbles): return None
            nibbles = nibbles[len(node.shared_nibbles):]; node = load(node.child_hash)
        elif isinstance(node, BranchNode):
            child = node.children[nibbles[0]]
            if child is None: return None
            nibbles = nibbles[1:]; node = load(child)
    return node.value if isinstance(node, (LeafNode, BranchNode)) else None

Extension nodes are the trie's answer to §6's "static array, no key lookup" complaint: long runs of shared address bits (extremely common — real addresses cluster far less than uniformly at the bit level once accounts are created in sequence by contracts) collapse into one node instead of 4 or 8 wasted single-child branch levels, which is why real Ethereum state tries are far shallower than a naive full binary trie over 160-bit addresses would be.
