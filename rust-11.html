Modules, Crates &
the Cargo Ecosystem

Every use statement, every line in a Cargo.toml, and every green checkmark from cargo build rests on three separate but tangled ideas: a module system that organizes code inside one crate, a crate that is the unit the compiler actually compiles and the unit crates.io actually distributes, and a resolver that turns a wishlist of version ranges into one exact, reproducible set of versions everyone on your team — and your CI server, and production — builds identically. This chapter derives all three from first principles, then hands you a real semver-and-dependency resolver written in the page's own JavaScript so you can watch Cargo's actual decision procedure run.

You will understandWhat a crate actually is as a compilation unit, what Cargo.toml states versus what Cargo.lock pins, and why those are two different jobs on purpose.
You will predictHow Cargo's resolver reacts to a caret requirement, and when two version constraints on the same crate produce unification, silent duplication, or a real resolution failure.

ARC 01 · THE PROBLEM

One file cannot stay one file, and one program cannot stay one crate

Chapters 1 through 10 built everything you wrote inside a single src/main.rs, plus whichever crates you pulled in with an unexplained [dependencies] line in Cargo.toml. That was a deliberate simplification. A real program — even a modest one — needs answers to five questions that a 40-line main.rs never forces you to confront:

  • Namespacing. Two people (or two crates) will eventually want to name something Config or parse. Something has to keep those apart without renaming everything by hand.
  • Visibility. Not every function is part of your public contract. Some are internal plumbing that callers — including your own code three files over — should not be allowed to depend on, so that you can change them freely.
  • Reuse across projects. The JSON parser you wrote for project A is useful in project B. Copy-pasting the file is reuse in the weakest possible sense: bug fixes in A never reach B.
  • Reproducible builds. If your program depends on ten other people's code, "compiles on my machine" must also mean "compiles identically, with the exact same code, on every other machine" — today, and two years from now when a dependency has published new versions.
  • Safe evolution. A library used by thousands of other crates needs a way to fix bugs and add features without silently breaking every one of them on the next cargo update.

Rust answers the first two with the module system — a tree of named, visibility-controlled namespaces living inside one crate. It answers the last three with the crate-and-Cargo system — crates as the boundary of compilation and distribution, semantic versioning as the shared vocabulary for "is this safe to upgrade to", and Cargo.lock as the mechanism that makes "it built on my machine" also mean "it will build, with these exact bytes, on yours." Keep those two systems distinct in your head as you read — mod organizes code within a crate; Cargo organizes code between crates — because the syntax overlaps just enough (both use the word "module" loosely in casual conversation) to blur them if you're not careful.

WHY THIS MATTERS FOR THE NEXT 11 CHAPTERS

ARC 02 · HISTORICAL CONTEXT

Cargo and crates.io were not always there

It is easy to assume a language's package manager was part of the design from day one. Rust's wasn't — Cargo and crates.io arrived only shortly before Rust 1.0, and several of their most consequential rules (immutable publishing, the default caret requirement, workspaces, the sparse registry protocol) were added in direct response to real pain, some of it borrowed from watching other ecosystems' incidents. DEEP CONTEXT · WHY SEMVER ITSELF NEEDED A SPEC

Before 2011, "version numbers" meant whatever each project's maintainer felt like that week. Tom Preston-Werner's Semantic Versioning 2.0.0 specification (semver.org) gave the ecosystem a shared promise: given a version MAJOR.MINOR.PATCH, bump PATCH for backwards-compatible bug fixes, MINOR for backwards-compatible new functionality, and MAJOR for anything that breaks existing callers. Cargo doesn't just document this convention — it encodes it directly into the default meaning of a version requirement in Cargo.toml, which is the single most load-bearing design decision this chapter explains.

ARC 03 · NAIVE SOLUTION

Attempt #1: everything in one file, and everyone hopes for the best

Derive the module system honestly, the way you'd stumble into needing it. Start a small CLI tool as one flat src/main.rs and just keep adding functions as the program grows — validation helpers, some parsing logic, a couple of small data structures:

Rustsrc/main.rs — the strawman, growing without structure
fn validate(input: &str) -> bool {
    !input.is_empty()
}

// … 40 more lines later, written by "past you" who forgot the function above …

fn validate(input: &str, max_len: usize) -> bool {
    input.len() <= max_len
}

fn main() {
    println!("{}", validate("hello"));
}

This is not a joke architecture — it's exactly how real small programs start, and for a 50-line script it costs nothing. There is no visibility to reason about, no path syntax to learn, no crate boundary to think past. Every name is visible everywhere, which feels like freedom right up until it isn't.

THIS DOES NOT COMPILE

rustc refuses this file outright, before it even reaches type-checking:

cargo build
error[E0428]: the name `validate` is defined multiple times
 --> src/main.rs:6:1
  |
1 | fn validate(input: &str) -> bool {
  | -------------------------------- previous definition of the value `validate` here
...
6 | fn validate(input: &str, max_len: usize) -> bool {
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ `validate` redefined here
  |
  = note: `validate` must be defined only once in the value namespace of this module

Rust has no function overloading — two functions can't share a name distinguished only by parameter list, the way C++ or Java would allow. E0004, E0308, and friends are type errors; E0428 is a namespace collision, and it's the compiler's first hint that "one big flat namespace" runs out of room embarrassingly fast — you will hit this exact error the first time two people on a team both add a validate, or the first time you `git merge` two feature branches that each added one.

ARC 04 · WHY IT FAILS

A flat namespace and a flat build both stop scaling, for related reasons

Push the naive approach further and two independent failure modes show up — one about code you write, one about code you depend on:

  • Namespace collisions compound with size. One file with 40 functions rarely collides. One file with 4,000 — or one team with 12 engineers editing the same flat namespace — collides constantly, and E0428 gives you no information about which of the two validates was "right"; it just refuses to pick.
  • Copy-pasting code between projects doesn't compose. If project B copies project A's JSON parser file and A later fixes a bug in it, B never receives the fix unless a human remembers to re-copy — and by then B may have made local edits that a naive copy would clobber. This failure mode has a name from decades before Rust existed: dependency hell, the exact thing Windows called "DLL hell" and Java called "JAR hell" in the 1990s and 2000s.
  • Without a shared version vocabulary, "upgrade" is a coin flip. If library authors don't commit to any convention about what a version bump means, every upgrade requires reading the changelog line by line — or skipping upgrades indefinitely out of fear, which is how security patches stop propagating.
  • Without a lockfile, "it builds" is a claim about one specific machine at one specific moment. Two developers running cargo build a week apart, against loose version ranges and no pinned file, can silently end up compiling different code — and only discover it when one of them hits a bug the other can't reproduce.
QUANTIFYING IT

A modern Rust project routinely depends, transitively, on 50 to 300+ crates for a normal web service or CLI tool — cargo tree on a project with a handful of direct dependencies (an async runtime, a serialization library, an HTTP client) commonly reveals well over a hundred crates in the full graph. If even 5% of publishers used inconsistent versioning conventions, or if there were no lockfile pinning the graph, every cargo build would be a fresh roll of the dice across a hundred-plus independently evolving pieces of code. The module system and the crate/Cargo system exist to make that number irrelevant to your daily workflow instead of a constant background risk.

ARC 05 · BETTER SOLUTION

Building the module tree, one decision at a time

Rust's module system answers the namespace problem with a tree: the crate root is the trunk, mod declarations are branches, and every item lives at exactly one address in that tree. Step through the evolution from the naive single file to a properly organized crate.

From one flat file to a real module treeSTEP-BY-STEP

A few rules the deck relies on, stated precisely because they trip up every newcomer at least once:

  • Everything is private by default — a function, struct, enum, or module not marked pub is visible only inside the module that defines it and that module's descendants. This is the opposite default from most mainstream languages, and it is deliberate: you should have to opt in to exposing something as part of your API surface.
  • pub exposes an item to anyone who can reach the module that contains it; pub(crate) exposes it to the whole current crate but not to external users; pub(super) exposes it only to the parent module. Reach for the narrowest one that works — it is the visibility equivalent of the borrow checker's "least privilege" instinct from chapter 5.
  • Paths can be absolute or relative. crate:: starts from the crate root, no matter how deep the current module is. self:: starts from the current module. super:: starts from the parent module — useful for a child module reaching back up without hard-coding the crate root's full path.
  • use brings a path into scope under a short name, purely for the humans reading the file — it is erased at compile time and has zero runtime cost. It does not "import" code the way a scripting language's import might trigger side effects; the module and its contents already exist whether or not you use them.
Rustthe same program, addressed with real paths
mod validation {
    pub fn is_nonempty(input: &str) -> bool {
        !input.is_empty()
    }
    pub fn within_limit(input: &str, max_len: usize) -> bool {
        input.len() <= max_len
    }

    mod internal {
        // private helper — only `validation` and its children can see it
        pub(super) fn trim_control_chars(s: &str) -> String {
            s.chars().filter(|c| !c.is_control()).collect()
        }
    }

    pub fn clean_and_check(input: &str) -> bool {
        // `super::` from inside `internal` reached back OUT to `validation`;
        // here we reach IN to a `super`-visible sibling module instead:
        let cleaned = internal::trim_control_chars(input);
        is_nonempty(&cleaned)
    }
}

fn main() {
    // absolute path from the crate root — always unambiguous
    println!("{}", crate::validation::is_nonempty("hello"));

    // `use` just gives us a short name for the same path
    use validation::within_limit;
    println!("{}", within_limit("hello", 10));
}

Two functions can now both be named validate — they just live at different paths, e.g. validation::is_nonempty and parsing::validate. E0428 only fires when two items collide at the same path; the module tree is precisely the mechanism that gives every item a unique address.

FILES ARE A PRESENTATION DETAIL, NOT A LANGUAGE RULE

Nothing above requires separate files — that whole example is one main.rs. When a module grows, you move its body into its own file and replace the inline { ... } with a declaration: mod validation; (note the semicolon, no braces) tells the compiler "find this module's contents in src/validation.rs". If validation itself needs sub-modules, current-edition Rust prefers a src/validation.rs file plus a src/validation/ directory holding its children, rather than the older src/validation/mod.rs convention — both still work, but having a dozen files all named mod.rs open in your editor is exactly the confusion the newer style avoids. Crucially: the file layout is a convenience the compiler maps onto the module tree; the tree, visibility, and paths are the actual language feature.

ARC 06 · WHY THAT STILL HAS COSTS

Modules and crates are not free — be honest about the bill

The module and crate system solves real problems, but it introduces real costs of its own. None of these are reasons to avoid the system — they're the price of the guarantees from §1, and every serious Rust engineer learns to budget for them:

  • Visibility boilerplate. Deciding pub vs pub(crate) vs private for every item is a real design exercise, not a formality — get it wrong (too public) and you can never tighten it without a breaking release; get it wrong (too private) and legitimate callers reach for #[allow(dead_code)] hacks or duplicate your logic.
  • Ambiguous file layout is a hard error, not a warning. If both src/validation.rs and src/validation/mod.rs exist for the same module, rustc refuses to guess which one you meant and fails the build outright — a real, if obscure, footgun for anyone mixing the old and new file-layout conventions in one crate.
  • Compile times scale with the dependency graph, not just your own code. Each crate is compiled separately (in dependency order), and a small direct dependency list can hide a much larger transitive one — §10 puts real numbers on this. This is consistently the most-cited frustration in Rust developer surveys.
  • A dependency is a trust decision, not just a technical one. A crate's build.rs script and any procedural macro it exports run arbitrary code on your machine at compile time — before your program has even been built, let alone run. Adding a dependency is closer to running someone else's installer than to importing a header file. §11 covers a real incident born from exactly this.
  • SemVer is a promise, not a guarantee enforced by the compiler. Nothing stops a maintainer from publishing an accidental breaking change in a patch release — Cargo trusts the version number a human chose. The ecosystem's tooling (cargo-semver-checks, CI diffing) exists precisely because the promise is social, not mechanical.

THE LINE THAT MATTERS MOST IN THIS CHAPTER

Cargo.toml states intent; Cargo.lock states fact. Cargo.toml says "I'm willing to accept any 1.x release of serde" — a range, chosen by you, that can match different exact versions on different days as new releases appear. Cargo.lock says "the last time this resolved, it was exactly 1.0.210, and every subsequent build uses that exact version until something explicitly asks to update." One file expresses a policy; the other freezes a fact. Confusing the two is why people are surprised when cargo build doesn't pick up a brand-new release of a dependency — it isn't supposed to, until you run cargo update.

ARC 08 · INTERNAL IMPLEMENTATION

Cargo.toml, semver arithmetic, the build pipeline, and four load-bearing crates

(a) Anatomy of a real Cargo.toml

Every section has one job. Read this once, carefully — you'll recognize every line for the rest of the course:

tomlCargo.toml — fully annotated
[package]
name = "orders-service"
version = "0.4.2"          # THIS crate's own semver — matters to whoever depends on you
edition = "2021"           # which language-edition rules the compiler applies to your code

[dependencies]
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"
tokio = { version = "1.35", features = ["rt-multi-thread", "macros", "time"] }
clap = { version = "4.4", features = ["derive"] }
rand = "0.8"

[dev-dependencies]      # only compiled for `cargo test` / `cargo bench` — never shipped
proptest = "1.4"

[build-dependencies]    # only used by build.rs, Cargo's pre-compile hook — separate graph entirely
cc = "1.0"

[profile.release]
opt-level = 3
lto = true              # link-time optimization — slower build, often faster/smaller binary

Two things worth internalizing immediately: first, serde = "1.0" is not "exactly version 1.0" — bare version strings are Cargo's default requirement operator, and that default is caret (^1.0), meaning "any 1.x release, as long as it's ≥ 1.0". Second, [dev-dependencies] and [build-dependencies] are genuinely separate graphs from [dependencies] — a heavy testing library in dev-dependencies adds zero bytes and zero compile time to the artifact you actually ship.

(b) The caret rule, worked out precisely

Cargo's default requirement follows real SemVer's own definition of "breaking": for a version ≥ 1.0.0, only the major number is allowed to break compatibility, so caret locks the major number. But SemVer treats 0.x releases as still unstable — so for a 0.y.z version, caret locks the minor number instead (any 0.y.z for a fixed y is fair game), and for a bare 0.0.z it locks the patch number, because there's no minor version left to signal anything with. (d) A tour of four crates that hold up half the ecosystem

"Load-bearing" is not hyperbole for these four — an enormous fraction of production Rust services depend on all four simultaneously. Each solves a problem the standard library deliberately leaves out, because the problem is either too opinionated, too fast-moving, or too platform-specific for std to commit to one answer.

Rustserde — structured (de)serialization, via a generic data model
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
struct Config {
    name: String,
    retries: u32,
}

fn main() -> Result<(), serde_json::Error> {
    let json = r#"{"name":"prod","retries":3}"#;
    let cfg: Config = serde_json::from_str(json)?;
    println!("{:?}", cfg);   // Config { name: "prod", retries: 3 }
    Ok(())
}

serde itself doesn't know about JSON at all — its #[derive(Serialize, Deserialize)] macro generates code against an abstract data model (structs, enums, sequences, maps, primitives), and a separate format crate (serde_json, bincode, toml, serde_yaml…) implements that model for one concrete wire format. That split is why the same #[derive] on Config works for JSON, TOML, and binary formats without touching your struct.

Rusttokio — an async runtime (executor + reactor) for I/O-bound concurrency
#[tokio::main]
async fn main() {
    let (a, b) = tokio::join!(fetch("a"), fetch("b"));
    println!("{a} {b}");
}

async fn fetch(name: &str) -> String {
    tokio::time::sleep(std::time::Duration::from_millis(50)).await;
    format!("{name}-done")
}

Rust's standard library defines the Future trait (chapter 16 covers this precisely) but ships no executor — nothing that actually polls a Future to completion. tokio is that missing piece: a multi-threaded task scheduler plus an OS-event-loop-backed reactor for sockets, timers, and files, exposed as ordinary async fns you .await. It is feature-gated aggressively — the #[tokio::main] macro and tokio::time module above only compile because the Cargo.toml snippet in (a) enabled the rt-multi-thread, macros, and time features; enabling nothing gives you an empty crate that compiles almost instantly.

Rustrand — pluggable random-number generation, not one fixed algorithm
use rand::Rng;

fn main() {
    let mut rng = rand::thread_rng();
    let n: u32 = rng.gen_range(1..=6);
    println!("rolled a {n}");
}

std deliberately ships no random-number generator at all — "good randomness" means different things for a dice-roll game versus a cryptographic nonce, and picking one default would be wrong for someone. rand supplies the trait (RngCore), the ergonomic surface (Rng::gen_range, random), and swappable algorithms, while a separate crate (getrandom) talks to the OS's actual entropy source. §15's simulator uses rand's real 0.7→0.8 breaking release as its version-conflict scenario, because it is a genuine, frequently-hit example of two crates in one dependency tree wanting incompatible majors of the same small crate.

Rustclap — declarative command-line argument parsing
use clap::Parser;

#[derive(Parser)]
struct Args {
    #[arg(short, long)]
    name: String,
    #[arg(short, long, default_value_t = 1)]
    count: u8,
}

fn main() {
    let args = Args::parse();
    for _ in 0..args.count {
        println!("Hello, {}!", args.name);
    }
}

clap's derive API turns a plain struct into a full CLI: --help text, short and long flags, required-vs-optional handling, and typed parsing (that count: u8 field rejects non-numeric or out-of-range input automatically) are all generated from the struct's shape and its #[arg(...)] attributes — you describe the shape of your arguments once, declaratively, instead of hand-rolling std::env::args() parsing.

Read this as proof by exhaustion, the same way chapter 1's process-model table worked: every ecosystem needs a versioning discipline, a resolution strategy, and an opinion about reproducibility — the only real choice is which axis you optimize. Cargo's distinctive bet is maximal unification by default (pick the newest mutually compatible version) paired with a mandatory lockfile; Go's distinctive bet is the opposite direction on the first axis (pick the oldest sufficient version) for the same underlying goal of predictability. Neither is "more correct" — they're different answers to "when in doubt, which way should the resolver round?"

ARC 10 · PERFORMANCE CHARACTERISTICS

Compile time is a function of the whole graph, not your file count

Because Cargo compiles from source and Rust's generics use monomorphization (chapter 8), your build time depends on the full transitive dependency graph, including crates you never typed into Cargo.toml yourself. Two levers dominate: how many direct dependencies you add, and how "heavy" each one's own dependency fan-out is (an async runtime or a full-featured web framework can each pull in dozens more). The curve is an analytic sketch: total crates ≈ direct × (1 + fan-out) with diminishing marginal cost from shared transitive dependencies, clean build time scales with total crates divided by a sub-linear parallelism term (codegen units contend for cores, and the final link step is single-threaded), and incremental rebuilds scale mostly with the number of crates that depend on the one file you changed, not the whole graph. ARC 11 · REAL-WORLD PRODUCTION

Four incidents the module/crate system either caused, prevented, or was designed around

Incident 1: RUSTSEC-2020-0071 — the time crate's unsound local-time lookup

In November 2020, a security advisory (RUSTSEC-2020-0071) landed against the widely used time crate: its 0.1.x strftime/local-time-offset code called into C library functions (localtime_r and friends) that are not safe to call from multiple threads simultaneously with environment-variable mutation happening concurrently — a real soundness gap, not a theoretical one. Because chrono, another near-ubiquitous crate, depended on time, the advisory rippled through cargo audit reports across a huge fraction of the ecosystem at once. The fix eventually meant a major rewrite inside time and a long migration for downstream crates. The lesson for this chapter: your dependency graph's soundness is only as strong as its weakest transitive crate, and a security advisory against a crate two or three levels deep in cargo tree is still your problem.

Incident 2: typosquatted crates on crates.io running code at build time

Because a crate's build.rs and any proc-macro it exports execute arbitrary code the moment cargo build resolves and compiles it, crates.io has repeatedly had to remove typosquatted packages — crates published under names deliberately similar to popular ones — whose build scripts fetched and executed a payload during compilation, before the "real" program had even been written. This is precisely the cost flagged in §6: adding one line to [dependencies] is a trust decision with the blast radius of running an installer, not the blast radius of importing a header.

Incident 3: why crates.io only lets you yank, never delete

In March 2016, a developer removed a tiny 11-line package called left-pad from npm over an unrelated naming dispute — and because thousands of other packages depended on it, large swaths of the JavaScript build ecosystem broke simultaneously, worldwide, within minutes. crates.io's publishing model was designed with that exact failure mode in view: you cannot delete a published version of a crate, ever. You can cargo yank a version to stop new projects from selecting it, but every project that already locked to it in a Cargo.lock keeps building successfully forever. Immutable publishing is a direct, deliberate, cross-ecosystem lesson learned before Rust's own registry had the chance to relearn it the hard way.

Incident 4: the "two versions of the same crate" compile-time tax

Because Cargo allows semver-incompatible versions of the same crate to coexist in one dependency graph (§15 demonstrates exactly when and why), a widely reported real pain point during the Rust ecosystem's syn 1.x→2.x migration was ordinary projects ending up compiling both major versions of syn and proc-macro2 simultaneously — because different procedural-macro crates in the same dependency tree had upgraded on different schedules. cargo tree -d (or cargo tree --duplicates) exists specifically to hunt this down: it lists every crate name appearing more than once in the resolved graph, which is often the single highest-leverage place to look when a project's build time seems disproportionate to its own code size.

Reading a real, multi-module crate — and a real workspace

A realistic small service's layout. Note which files are single modules, which are directories with children, and which items are pub versus pub(crate) on purpose:

my_app/
├── Cargo.toml — [package], [dependencies], [dev-dependencies]
├── Cargo.lock — committed for a binary; the exact resolved graph
├── src/
│ ├── ● main.rs — crate root; `mod` declarations + fn main()
│ ├── config.rs — `pub struct Config`, loaded from env + file
│ ├── error.rs — crate-wide error enum; mostly `pub`, some `pub(crate)`
│ ├── http/
│ │ ├── ● mod.rs — re-exports the public surface of this sub-tree
│ │ ├── routes.rs — `pub(crate) fn` handlers, not part of the crate's public API
│ │ └── middleware.rs
│ └── db/
│ ├── mod.rs
│ └── pool.rs
├── tests/
│ └── integration.rs — compiled as a SEPARATE crate; only sees my_app's `pub` items

The crate root — deliberately thin. Its only job is to declare the module tree and hand off to the real logic:

Rustsrc/main.rs
mod config;
mod error;
mod http;
mod db;

use crate::config::Config;
use crate::error::AppError;

#[tokio::main]
async fn main() -> Result<(), AppError> {
    let cfg = Config::load()?;
    let pool = db::pool::connect(&cfg.database_url).await?;
    http::serve(cfg, pool).await
}

The http sub-tree's mod.rs controls exactly what leaks outside this module — note that middleware is entirely invisible to the rest of the crate on purpose:

Rustsrc/http/mod.rs
mod routes;
mod middleware;   // no `pub` — an implementation detail of `http` alone

// the ONLY thing the rest of the crate is allowed to call:
pub async fn serve(cfg: Config, pool: Pool) -> Result<(), AppError> {
    let router = routes::build(pool).layer(middleware::request_id());
    // … bind + run the router …
    Ok(())
}

Scale past one crate and you reach for a workspace — several crates sharing one Cargo.lock and one target/ directory, so a type shared between them compiles once instead of once per crate:

tomlCargo.toml — workspace root (no [package] section of its own)
[workspace]
members = [
    "crates/orders-api",
    "crates/orders-worker",
    "crates/orders-core",
]
resolver = "2"          # feature unification per-target, not merged across the whole workspace

[workspace.dependencies]
serde = { version = "1.0", features = ["derive"] }   # declared once, referenced by member crates

Both orders-api (a web server) and orders-worker (a background job runner) can now depend on orders-core — a third member crate holding the domain types both need — with orders-core = { path = "../orders-core" } in their own manifests, and both inherit the shared serde requirement from [workspace.dependencies] instead of each pinning it separately and risking drift. As a point of comparison rather than a code excerpt: tokio's own crate root follows the same "thin trunk, heavy branches" shape at ecosystem scale — its top-level modules (net, fs, time, sync, task, runtime) are each gated behind a Cargo feature flag of the same name, which is precisely why enabling only features = ["time"], as this chapter's tokio example implicitly relies on, compiles a small fraction of what features = ["full"] would.
