Log Compaction

A log that grows forever is not a product. But "delete old data" and "keep the latest value for every key, forever" are two different problems with two different mechanisms, two different threads, two different failure modes, and two different sets of operational surprises. This chapter derives both from first principles and then walks the actual code: LogManager's retention sweep, the LogCleaner thread pool, SkimpyOffsetMap's open-addressing probe, the two-pass copy algorithm, the cleaner checkpoint, and the .deleted rename dance.

ARC 01 · THE PROBLEM

Disk is finite; some data is not

Every previous chapter in this course has treated the partition log as an append-only sequence of bytes that only ever grows. That is the source of Kafka's throughput: appends are sequential, reads are sequential, offsets are dense monotonic integers, and the page cache does the rest. It is also, taken literally, a design that fills every disk in the fleet and then stops the broker with KafkaStorageException.

So something has to reclaim space. The instinct is to reach for a single knob — "keep 7 days" — and be done. That instinct is wrong, and the reason it is wrong is the most important idea in this chapter: there are two categorically different kinds of topic, and they want opposite things from a reclamation policy.

The first kind is a stream of events. A click, a page view, a metric sample, an order-placed fact. Each record is independently meaningful, records are never superseded, and their value decays with time. For a topic like this the correct question is "how far back does anyone need to replay?" and the correct answer is a duration or a byte budget. Nothing about record content matters; the broker can be entirely opaque to the payload. This is cleanup.policy=delete.

The second kind is a stream of state changes keyed by identity. Consumer group X committed offset 4471 for partition P. User 91288's shipping address is now this. Row 55 of the accounts table now has balance 1200. Here records do supersede each other: the record with key K at offset 900 makes the record with key K at offset 12 semantically irrelevant. And crucially, the useful lifetime of the latest record for each key is unbounded — you must keep it forever, or at least until the key is explicitly deleted, because a new consumer needs to rebuild the entire table from the log. Time-based deletion is catastrophically wrong for this topic: a key updated once and never again would silently vanish after seven days, and any rebuild after that would produce a table with a hole in it.

THE TWO QUESTIONS

Retention asks: "is this data old enough that nobody will want it?" — a question about time and volume, answerable without reading a single record's key.

Compaction asks: "has this record been superseded by a later record with the same key?" — a question about content and identity, which requires reading and hashing every key in a range of the log.

These are so different that they are implemented by different code, running on different threads, on different schedules, with different failure modes. The retention sweep is a periodic scheduler task inside LogManager (core/src/main/scala/kafka/log/LogManager.scala) that calls UnifiedLog.deleteOldSegments() every log.retention.check.interval.ms (5 minutes by default) and, in the common case, does no I/O at all beyond a few unlink calls. Compaction is a dedicated thread pool — LogCleaner in core/src/main/scala/kafka/log/LogCleaner.scala — that reads, hashes, buffers, and rewrites potentially gigabytes of segment data per pass, and whose throughput is deliberately throttled so it does not starve the request handler threads of page cache and disk bandwidth.

The rest of this chapter builds both mechanisms from scratch. We will start by asking what the obvious implementation would be, prove with arithmetic that it cannot work, and then derive the design Kafka actually uses — including the parts of it that are compromises rather than triumphs. Because the interesting thing about retention and compaction is not that they work; it is precisely where they don't, and both of the classic production incidents in this area are direct, predictable consequences of implementation choices you will be able to reason about by the end of section 8.

A NOTE ON NAMES

The class was called Log for a decade. Since Kafka 3.0 (KIP-405 groundwork) the top-level per-partition object is UnifiedLog, which composes a LocalLog (the on-disk segments) with optional remote-tier metadata. Older material — and much of the surviving code and log output — still says Log. In this chapter UnifiedLog and Log refer to the same thing; where the distinction matters (tiered storage in section 2 and 9) it is called out explicitly.

ARC 02 · HISTORICAL CONTEXT

How a queue became a database

Compaction was not in the original design. Kafka in 2011 was a way to get LinkedIn's activity data from web tier to Hadoop without losing it, and disk was a buffer, not a store. Everything that follows — the log-as-table idea, __consumer_offsets, Kafka Streams, changelog topics, CDC connectors, tiered storage — is the consequence of one conceptual shift: realising that a log with per-key compaction is a table, and that the difference between a stream and a table is only which retention policy you applied.

Evolution of Kafka's reclamation storyCLICK A MILESTONE

The pivotal moment is 0.8.1 in 2014. Before it, consumer offsets lived in ZooKeeper, and ZooKeeper's write throughput was the ceiling on how many consumers a cluster could support: every commit was a znode write, fsynced and replicated by ZAB, and a fleet of a few thousand consumers committing every few seconds was enough to destabilise an ensemble. The fix that shipped — move offsets into a Kafka topic — required a topic whose semantics were "the latest value per (group, topic, partition) key, retained indefinitely." That topic could not use time retention, because a consumer group that goes quiet for a week must not lose its position. Log compaction was built to make __consumer_offsets possible; everything else it enabled came afterwards.

JAY KREPS, "THE LOG" (2013)

The essay that reframed the project argued that a log is the canonical form of a data system's write path, and that databases, replication, and stream processing are all just different ways of reading one. The practical corollary — the one that shows up in LogCleaner — is that if the log is going to be the system of record, it needs a garbage-collection story that preserves final state rather than a time window. Compaction is that story: it is a log-structured merge, restricted to the degenerate case where the "merge" is "last write wins per key."

ARC 03 · NAIVE SOLUTION

The strawman: rewrite the file

Suppose you are handed the requirement cold: "the partition log must not exceed seven days of data, and separately, for keyed topics, only the latest value per key should survive." You have one file per partition — a flat, append-only partition.log — and a broker that is already serving reads from it. The direct implementation writes itself.

SCALA · strawmanNaiveRetention.scala — do not ship this
// Strawman 1: enforce retention by scanning and rewriting the single log file.
def enforceRetention(log: File, retentionMs: Long): Unit = {
  val cutoff = System.currentTimeMillis() - retentionMs
  val tmp = new File(log.getPath + ".rewrite")

  lock.writeLock().lock()            // block ALL appends and ALL reads
  try {
    val in  = new FileInputStream(log)
    val out = new FileOutputStream(tmp)
    var newOffset = 0L
    for (rec <- readRecords(in)) {
      if (rec.timestamp >= cutoff) {
        out.write(rec.withOffset(newOffset).bytes)   // offsets shift!
        newOffset += 1
      }
    }
    out.getFD.sync()
    Files.move(tmp.toPath, log.toPath, REPLACE_EXISTING)
    rebuildAllIndexes(log)          // every index entry is now wrong
  } finally lock.writeLock().unlock()
}

// Strawman 2: enforce compaction the same way, with a full in-memory map.
def compact(log: File): Unit = {
  val latest = new java.util.HashMap[ByteBuffer, Record]()  // unbounded
  for (rec <- readRecords(new FileInputStream(log)))
    latest.put(rec.key, rec)          // last write wins
  val out = new FileOutputStream(new File(log.getPath + ".compacted"))
  latest.values().asScala.toSeq.sortBy(_.offset).foreach(r => out.write(r.bytes))
  Files.move(...)
}

Read that carefully, because almost every line of it encodes an assumption that Kafka's real implementation had to abandon. The strawman assumes: (1) the log is one file; (2) removing a prefix is a rewrite; (3) offsets can be renumbered; (4) the whole key space fits in a HashMap; (5) a global write lock for the duration of the rewrite is acceptable; (6) indexes can be rebuilt afterwards, cheaply.

Each assumption fails, and interestingly they fail for different reasons — some are performance failures, some are correctness failures, and one of them is a correctness failure so total that it invalidates the entire external contract of Kafka. That one is offset renumbering, and it is worth stating explicitly before the arithmetic in section 4: a Kafka offset is an immutable, permanent address. Consumers store it, __consumer_offsets stores it, replicas fetch by it, the index files map it to file positions, transactions record it in LastStableOffset computations. If compaction renumbered offsets so the surviving records were dense, every committed offset in the cluster would silently point at the wrong record. So the very first rule of both mechanisms falls out for free:

INVARIANT #1 — OFFSETS ARE FOREVER

Neither retention nor compaction may ever change the offset of a surviving record. Compaction therefore produces a log with gaps: offsets 0, 3, 7, 11, 12… A consumer that asks for offset 4 in a compacted log gets whatever is at the next existing offset. This is why Fetch semantics have always been "give me everything from offset X onward" rather than "give me record X" — a design decision that predates compaction but which compaction makes load-bearing.

The second observation is subtler. Strawman 2 keeps only the last value per key and renumbers, but it also loses something the real design preserves: relative order. Because the strawman builds a hash map and then writes out its values, it is only accidentally ordered — and it has thrown away the position of each surviving record relative to records with other keys. The real compactor never reorders. A record that survives compaction sits at exactly the offset it always had, in exactly the same relative position to every other surviving record. This matters more than it looks: it means a compacted log is still a valid partial replay of the original stream, so a state machine that replays it converges to the same final state it would have reached by replaying the full log. Reordering would break that for any non-commutative update.

ARC 04 · WHY IT FAILS

The arithmetic that kills it

Take a realistic partition. A mid-sized production topic ingests 20 MB/s per partition, which is unremarkable — a single broker NIC can push twenty times that. Over seven days that is 20 × 10⁶ × 86400 × 7 ≈ 12.1 TB of data on that one partition, before replication. With segment.bytes at its 1 GB default, that is roughly 12,000 segments; on a broker hosting 200 such partitions, 2.4 million segment files. Those numbers are what set the scale for everything that follows.

Cost 1: rewriting a prefix is O(n) in the wrong n

Strawman 1 removes expired records by copying the survivors. If the retention cutoff falls one hour into a seven-day log, you are copying 12.0 TB in order to discard 0.1 TB. Even at a generous 1 GB/s sequential throughput on NVMe, that is 12,000 seconds — 3.3 hours of full-bandwidth disk I/O, per partition, per retention check. With a 5-minute check interval and 200 partitions, the broker would need roughly 8,000× more disk bandwidth than it has. The mechanism cannot be run at all.

Compare with the alternative: if the log is split into 1 GB segment files, discarding the oldest hour means calling unlink() on three or four files. On ext4 or XFS that is a directory-entry removal plus an inode/extent-map free — microseconds of metadata work, no data movement, and the freed extents return to the allocator immediately. The asymptotic difference is not 10× or 100×; it is O(bytes retained) versus O(1).

DO THE DIVISION

Rewrite: 12.1 TB copied to delete 0.1 TB → 121 bytes of I/O per byte reclaimed. Segment unlink: ~4 inode operations to reclaim 4 GB → ≈ 0.000000001 bytes of I/O per byte reclaimed. This single ratio is why segment granularity is not an optimisation, it is the enabling design decision. Everything else about retention — why the active segment survives, why segment.ms exists, why a low-traffic partition over-retains — is downstream of choosing to make deletion a file-level operation.

Cost 2: the global lock is a full outage

Strawman 1 holds a write lock over the rewrite. For those 3.3 hours no producer can append and no consumer can fetch from that partition. Kafka's real appends take a per-log lock for the duration of a memory copy into the tail segment's FileRecords — microseconds. Any reclamation scheme whose critical section scales with log size is disqualified before you evaluate its throughput. The real design's critical sections are: (a) a lock to swap a segment out of the skip-list, (b) a lock to swap a rewritten segment in. Both are O(log n) map mutations on a ConcurrentSkipListMap holding a few thousand entries.

Cost 3: the unbounded HashMap is an OOM

Strawman 2 builds a HashMap[ByteBuffer, Record] over the whole log. Consider __consumer_offsets at LinkedIn scale, or a CDC topic mirroring a 500-million-row table. Take 500 M distinct keys with 24-byte keys. The HashMap.Node overhead alone — object header, hash, key ref, value ref, next ref — is ~48 bytes on a 64-bit JVM with compressed oops, plus the ByteBuffer wrapper (~56 bytes) plus the key bytes plus the table array slot (~8 bytes at 0.75 load factor → ~10.7 bytes amortised). Call it 140 bytes per entry, so 70 GB of heap — for one partition, on a broker whose heap is conventionally 6 GB because Kafka deliberately leaves RAM to the page cache. The JVM dies long before the compaction finishes, and it dies during a GC pause that also fails the ISR heartbeat, so the partition loses leadership on the way down.

This is the constraint that produces Kafka's most distinctive compaction design choice. You cannot bound key cardinality — it is user data. You cannot afford unbounded memory. Therefore the map must be fixed-size and lossy-by-design, and the algorithm must remain correct when the map fills up. The resolution: store only a hash of the key, not the key; store only the offset, not the record; and when the map is full, stop consuming input and compact only the range you managed to index. Correctness is preserved because compacting a prefix of the dirty range is always safe — the un-indexed suffix simply stays dirty and gets picked up next pass. What you lose is not correctness but progress rate, and that is exactly the failure mode section 6 dissects.

Cost 4: index invalidation

Every segment carries three sidecar files: .index (sparse offset → file position, one entry per index.interval.bytes = 4096 by default), .timeindex (timestamp → offset), and for transactional topics .txnindex. Renumbering offsets invalidates all of them everywhere, including on every follower replica, which would have to be told to re-replicate from scratch. Preserving offsets means a rewritten segment only needs its own three sidecars rebuilt, which the cleaner does incrementally as it appends survivors — no cross-broker coordination at all. Followers, in fact, do not replicate compaction: each replica compacts its own copy independently, and because the algorithm is deterministic in its result (last value per key survives) but not in its timing, two replicas of a compacted partition can legitimately hold different byte counts and different intermediate records at the same instant while still being consistent.

ARC 05 · BETTER SOLUTION

Eliminating the candidates

Four designs are on the table. Walk them in order and watch each one die of a specific, nameable cause — the survivor is what Kafka ships.

Candidate elimination: how to reclaim log space6 STEPS

The surviving pair is: segment-granular deletion for the time/size policy, and two-pass out-of-place segment rewriting driven by a bounded offset map for the compaction policy. Note that these share infrastructure — both operate on LogSegment objects held in UnifiedLog's ConcurrentSkipListMap[Long, LogSegment] keyed by base offset, both use the same .deleted-rename protocol to retire a file without breaking a read in flight, and both refuse to touch the active segment. That sharing is not incidental; it is why cleanup.policy=compact,delete can be a comma-separated list rather than a mutually exclusive enum.

WHY BOTH, TOGETHER

cleanup.policy=compact,delete runs the retention sweep and the cleaner on the same log. This is the right setting for a Kafka Streams windowed store changelog: compaction collapses repeated updates to the same window key, and time retention eventually drops whole windows that have fallen out of the retention period, so the changelog does not grow without bound as the window key space rotates. Without the delete half, every window key ever created stays in the log forever — a genuinely unbounded key space, which is the one case where compaction alone does not bound size.

ARC 06 · WHY THAT STILL HURTS

The three surprises the design guarantees

The chosen design is right, and it still produces three operational surprises so reliably that they are effectively part of the product. Each one is a direct, derivable consequence of a decision made in section 5 — which means you can predict them from first principles, and, more usefully, recognise them from a graph at 3am.

Surprise 1: the low-traffic partition that retains data for months

Deletion is segment-granular and the active segment is never deleted. Combine those two facts with a partition that receives 50 records per day and the conclusion is immediate: the active segment never reaches segment.bytes (1 GB), so it never rolls, so there is never a non-active segment to delete, so retention.ms is never enforced at all. The partition happily holds records from 2019 with retention.ms=604800000 set on the topic.

Operators discover this the way you would expect: a GDPR deletion audit, or a consumer that resets to earliest and suddenly replays four years of data into a downstream system sized for a week. The mechanism that saves you is segment.ms (default 7 days): UnifiedLog.maybeRoll rolls the active segment when now - segment.created > segment.ms even if it is nearly empty, producing a sealed segment that the retention sweep can then evaluate. So the real retention floor for any partition is not retention.ms but retention.ms + segment.ms, plus up to log.retention.check.interval.ms of scheduling latency, plus file.delete.delay.ms. For defaults that is 7 days + 7 days + 5 min + 1 min ≈ 14 days, exactly double what the topic config appears to promise.

THE TIMESTAMP DETAIL THAT BITES TWICE

The retention predicate is not "the segment was created more than retention.ms ago." It is segment.largestTimestamp < now - retention.ms, where largestTimestamp comes from the last entry of the .timeindex, falling back to the file's last-modified time if the time index is empty. Which timestamp that is depends on message.timestamp.type: with CreateTime (the default) it is a producer-supplied value. A producer with a skewed clock, or a backfill job replaying historical events with their original timestamps, can therefore make a freshly written segment instantly eligible for deletion — data written two minutes ago, deleted on the next 5-minute tick. The defence is message.timestamp.difference.max.ms (or, in modern releases, message.timestamp.before/after.max.ms), or switching the topic to LogAppendTime.

Surprise 2: compaction that never catches up

The OffsetMap is bounded by log.cleaner.dedupe.buffer.size (128 MB by default, split across log.cleaner.threads, default 1). Each entry costs 16 bytes of MD5 key hash plus 8 bytes of offset = 24 bytes, and SkimpyOffsetMap refuses to exceed a load factor of log.cleaner.io.buffer.load.factor (0.9). So capacity ≈ 128 MB × 0.9 ÷ 24 ≈ 5.0 million distinct keys per pass.

Now put 40 million distinct keys in the dirty portion of a partition. The cleaner indexes keys until the map is full, stops, and compacts only the segments it managed to cover — roughly one-eighth of the dirty range. The rest stays dirty. Meanwhile producers keep appending. If the arrival rate of new distinct keys exceeds the rate at which the cleaner can retire them (limited by the buffer, by log.cleaner.io.max.bytes.per.second throttling, and by having only one cleaner thread), the dirty portion grows monotonically. The disk fills. Nothing in the metrics says "compaction is broken" — it says max-dirty-percent is high and climbing, and cleaner-recopy-percent looks fine.

Worse, the pathology is self-reinforcing: as the dirty section grows, each pass covers a smaller fraction of it, so the ratio of useful work to overhead falls. And the throughput cost is real — the same key gets read, hashed, and re-copied across many passes because it keeps falling outside the indexable prefix.

DIAGNOSING IT

Three JMX gauges tell the story together. kafka.log:type=LogCleanerManager,name=max-dirty-percent pinned near 100 means the cleaner is not keeping up. kafka.log:type=LogCleaner,name=max-clean-time-secs rising means passes are getting longer. And kafka.log:type=LogCleanerManager,name=uncleanable-partitions-count > 0 means the cleaner died on a partition and marked it uncleanable — historically the most common cause of unbounded __consumer_offsets growth, since a single uncaught exception in a cleaner thread used to kill the whole thread and silently stop compaction for every partition on the broker. KIP-346 (Kafka 2.0) added the uncleanable-partition mechanism so one bad partition no longer takes down the pool; before it, the symptom was a broker whose disk grew smoothly until it hit 100%.

Surprise 3: tombstones are not free, and their clock is subtle

A tombstone — a record with a non-null key and a null value — means "this key is deleted." It must survive compaction long enough for every consumer to see it, because a consumer that was offline when the key was written and deleted, and which finds neither record on resume, will keep whatever stale value it had. So the tombstone is retained for delete.retention.ms (24 hours default) and only then removed.

The subtlety is the clock the 24 hours is measured against. It is not the tombstone's own timestamp. A tombstone becomes eligible for removal only after it has been through a compaction pass that marked it, and the deadline is computed from the last-modified time of the segment that contained it when it was first observed clean. Concretely, LogCleaner passes a deleteHorizonMs down to the copy loop; a tombstone whose segment's lastModified plus delete.retention.ms is still in the future gets copied forward. The practical consequence: on a slow-moving topic where compaction runs rarely, tombstones can persist for far longer than 24 hours — the same "the config is a floor, not a ceiling" pattern as surprise 1. KIP-534 tightened the accounting by storing the delete horizon in the record batch header rather than inferring it from file mtime, precisely because file mtime changes when a segment is rewritten and could reset the clock.

Two structural points are worth stating outright, because they explain most of the behaviour you will observe in production.

First, the retention path and the compaction path never share a thread. Retention runs on the kafka-scheduler pool — the same background scheduler that flushes recovery points and checkpoints — as a periodic task named kafka-log-retention, firing every log.retention.check.interval.ms. Compaction runs on kafka-log-cleaner-thread-N, a dedicated ShutdownableThread per cleaner. They can and do operate on the same UnifiedLog concurrently, which is why segment removal from the skip-list is guarded and why the cleaner re-checks segment liveness before it swaps.

Second, the cleaner's unit of decision is a whole log, not a segment. LogCleanerManager.grabFilthiestCompactedLog computes a dirty ratio for every eligible log on the broker, filters those below log.cleaner.min.cleanable.ratio, and hands the single highest-ratio log to the requesting thread, marking it LogCleaningInProgress so no other thread takes it. This is a greedy scheduler with no fairness guarantee: a log that is persistently dirtier than its neighbours will be cleaned repeatedly while a marginally-above-threshold log waits indefinitely. On a broker with one cleaner thread and a hundred compacted partitions, that starvation is not hypothetical.

ARC 08 · INTERNAL IMPLEMENTATION

Two passes, one bounded map, zero moved offsets

Now the machinery. We will take the compaction path in full detail, then return to the retention path's .deleted protocol, which is shorter but contains the one piece of concurrency reasoning that catches most people.

The cleaner point and the three regions of a log

At any instant a compacted log is divided into three regions by two offsets. Everything below the cleaner point (also called firstDirtyOffset) has already been through a compaction pass and is guaranteed to contain at most one record per key — the "clean" region, or "log tail." From the cleaner point up to the base offset of the active segment is the dirty region, which may contain many records per key. And the active segment is a third region that is never touched by anything.

Why is the active segment excluded? Three reasons, all decisive. It is being appended to, so its end moves while you read it; the append path holds a lock and memory-maps its index, and rewriting a file underneath a live FileChannel plus MappedByteBuffer is not something you want to attempt. It has no stable largestOffset to bound the map build. And most importantly, compacting the tail would break the guarantee that a consumer reading the head of a compacted topic sees every update, not just the survivors — Kafka Streams and every CDC consumer depend on the head of a compacted log behaving like an ordinary uncompacted stream. That guarantee is what makes it safe to say "compaction is eventually consistent": a consumer keeping up with the head sees the complete update history; only a consumer that falls behind, or one bootstrapping from earliest, sees the collapsed view.

THE OTHER LOWER BOUND

The cleaner will not compact past the first unstable offset either. With transactional producers, records above the last stable offset (LSO) belong to in-flight transactions whose outcome is unknown, and compacting them would be deciding the transaction's fate. So the real upper bound on a cleaning pass is min(activeSegment.baseOffset, firstUnstableOffset, lastStableOffset), further clamped by min.compaction.lag.ms if set. A long-running or hung transaction therefore blocks compaction on that partition entirely — a subtle coupling between the transaction coordinator's timeout behaviour (transaction.max.timeout.ms, 15 min default) and disk growth on compacted topics.

Pass 1 — building the OffsetMap

SkimpyOffsetMap lives in core/src/main/scala/kafka/log/OffsetMap.scala and it earns its name. It is a single ByteBuffer of memory bytes, treated as an open-addressed table of fixed-width slots. Each slot is hashSize + 8 bytes: the MD5 digest of the key (16 bytes) followed by a long offset. There are no keys stored, no chains, no tombstone slots, no resizing. Insertion computes the digest, derives an initial bucket from the first four bytes of the digest, and linear-probes forward until it finds either a slot whose digest matches (overwrite the offset — this is the "later record wins" step) or an empty slot (claim it). Lookup does the same probe and returns the offset or -1.

Two consequences fall straight out of that layout. Because only the digest is stored, a hash collision is a silent data-loss bug: two distinct keys with identical MD5 digests would be treated as the same key, and the older record would be dropped. Kafka accepts this because a 128-bit digest gives collision probability around 10⁻²⁹ even at 10¹⁰ keys — a lower risk than undetected disk corruption. And because the table never resizes, the capacity is a hard wall: slots = memory / (16 + 8), usable up to load factor 0.9.

Pass 2 — the copy loop, step by step

With the map built and a deleteHorizonMs computed, the cleaner groups the segments it intends to clean and rewrites each group into one new .cleaned segment. The grouping matters: groupSegmentsBySize packs consecutive old segments together so that the union of their surviving records is still under segment.bytes and their offset span still fits in the 32-bit relative offsets used by the index format. Without grouping, compaction would leave you with thousands of tiny segments — each 1 GB original shrinking to a few MB — and segment count is itself a cost (file descriptors, index mmaps, recovery time, and O(segments) scans in the retention sweep).

The retain predicate, exactly

Inside the copy loop, each record is passed to a predicate that answers "keep or drop." Simplified but faithful, it is:

SCALALogCleaner.scala — shouldRetainRecord (paraphrased)
def shouldRetainRecord(map: OffsetMap, retainDeletes: Boolean,
                       batch: RecordBatch, record: Record,
                       stats: CleanerStats, currentTime: Long): Boolean = {
  val pastLatestOffset = record.offset > map.latestOffset
  if (pastLatestOffset) return true   // beyond what the map indexed: always keep

  if (record.hasKey) {
    val key = record.key
    val foundOffset = map.get(key)
    val isLatest = foundOffset == record.offset   // THE test. exact offset match.
    if (isLatest) {
      if (record.hasValue) true            // latest, non-null -> keep
      else {                                // latest, null -> tombstone
        batch.deleteHorizonMs match {         // KIP-534: horizon in batch header
          case OptionalLong.of(h) => currentTime < h   // still inside 24h window
          case _                   => retainDeletes    // first clean: mark, keep
        }
      }
    } else false                            // superseded -> drop
  } else {
    stats.invalidMessage()
    false      // null key in a compacted topic: silently discarded
  }
}

Three lines in there deserve to be memorised. foundOffset == record.offset is the whole algorithm: the map holds the highest offset seen for each key hash, so a record survives if and only if it is that highest offset. No comparison of values, no timestamps, no versioning — pure positional recency. pastLatestOffset => true is the safety valve that makes a partially-built map correct: anything the map did not cover is copied through untouched, which is why a saturated buffer costs progress rather than correctness. And the final false for a keyless record is the one place compaction destroys data unasked: a record with a null key written to a compacted topic is deleted by the first cleaning pass, with no error at produce time and only an invalid-message stat to show for it.

The .deleted rename dance

Now the retention path. Deleting a segment while a consumer is mid-fetch from it would produce an IOException on a live FileChannel, or worse on platforms with mandatory locking. Kafka's protocol, in LocalLog.deleteSegmentFiles, is a three-phase retirement:

  • Phase 1 — unlink from the index, synchronously. Under the log lock, the segment is removed from the ConcurrentSkipListMap. Any read that starts after this point cannot find the segment. Reads already in flight still hold their own reference.
  • Phase 2 — rename to .deleted, synchronously. 00000000000000123456.log becomes 00000000000000123456.log.deleted, and the same for .index, .timeindex, .txnindex. On POSIX a rename does not disturb open descriptors — in-flight readers keep reading the same inode happily. The rename also makes the state crash-safe: if the broker dies now, LogManager's startup scan deletes any *.deleted file it finds, so recovery is idempotent.
  • Phase 3 — actually unlink, asynchronously, after file.delete.delay.ms. A scheduler task named delete-file fires 60 seconds later (default) and calls Files.deleteIfExists plus MappedByteBuffer cleanup on the index mmaps. Sixty seconds is the grace period for any fetch that grabbed the segment before phase 1 to finish. Because unlink on an open file only removes the directory entry, even a reader that outlives phase 3 continues to work — the inode's link count does not hit zero until it closes.
WHY YOUR DISK USAGE LAGS THE METRICS

Between phase 2 and phase 3 the bytes are still on disk and still counted by df, but the segment is gone from Log.size and from the Size JMX gauge. On a broker churning many segments, that discrepancy is file.delete.delay.ms × deletion rate of "invisible" space. And if a consumer holds a very long fetch on a deleting segment, the inode survives phase 3 — df shows space consumed with no corresponding file visible in the directory, the classic "deleted but held open" state you can confirm with lsof +L1.

Compaction uses a mirror-image version of the same protocol in replaceSegments: the new segment is built as .cleaned, then renamed to .swap (the durable "I intend to replace" marker), then the old segments are swapped out of the map and renamed .deleted, then the .swap suffix is stripped. Crash recovery keys off exactly those suffixes — LogLoader deletes stray .cleaned files (a pass that never completed, safe to redo) but completes any .swap it finds (a pass that got far enough to be durable, and whose old segments may already be gone). That asymmetry is the entire crash-consistency argument for compaction, and it is why the .swap rename must be the atomic commit point.

The Pulsar comparison is the instructive one. Pulsar's compaction produces a separate compacted ledger, leaving the original intact; a reader chooses which view it wants. That is strictly more expressive than Kafka — you can still read the full history after compaction — and strictly more expensive, because you now store both. Kafka's choice to compact in place is a statement that the collapsed view is the only one worth paying for, and it is why in Kafka "compacted" is destructive and irreversible while in Pulsar it is a materialised view.

The JetStream/Artemis comparison cuts the other way. Enforcing last-value-per-key at write time is dramatically simpler: no background thread, no map, no dirty ratio, no lag. It works because those systems index by subject/queue and can afford a random-access overwrite. Kafka cannot — an append that had to first locate and invalidate a prior record for the same key would turn a sequential write into a read-modify-write, destroying the sequential-I/O property that the entire system is built on. Kafka's compaction is asynchronous because its writes must stay append-only. That single sentence is the whole tradeoff.

THE COST NOBODY PUTS IN THE TABLE

Compaction is the only part of Kafka whose steady-state CPU and disk cost is proportional to rewrite volume rather than to client traffic. A partition receiving 10 MB/s of updates to a small key space will have the cleaner reading and rewriting far more than 10 MB/s, because every pass re-copies the surviving clean portion in whatever groups it touches. The cleaner-recopy-percent metric measures exactly this: bytes written by the cleaner ÷ bytes read by the cleaner. A high recopy percentage on a low-cardinality topic means you are paying full I/O to reproduce data that was already compact — raise log.cleaner.min.cleanable.ratio to make passes rarer and each one more productive.

ARC 10 · PERFORMANCE

Cost model of a cleaning pass

Let D = bytes in the dirty region, C = bytes in the clean region that get grouped into the pass, k = distinct keys in D, s = mean record size. The two passes cost:

  • Pass 1 (build): read D sequentially, MD5 each key, one open-addressed probe per record. Time O(D/s) record-visits and O(D) bytes read; memory strictly dedupeBufferSize / threads, independent of k. Probe cost is amortised O(1) up to load factor 0.9, degrading toward O(1/(1−α)) as the table saturates — at α=0.9 that is ~10 slot reads per insert, which is why the load factor cap exists at all.
  • Pass 2 (copy): read D + C, look up each record (one more MD5 + probe), write the survivors S. Time O((D+C)/s), I/O O(D + C) read plus O(S) write. Both use log.cleaner.io.buffer.size-sized read/write buffers (512 KB total by default, split in half), so the access pattern is large sequential reads and large sequential writes — friendly to both the page cache readahead and the disk scheduler.

Total: 2 sequential reads of the dirty region, one sequential read of the grouped clean region, one sequential write of the survivors, and 2·(D/s) MD5 computations. That last term is not negligible: MD5 over short keys runs at roughly 400–600 MB/s per core on modern x86 for the digest itself, but with per-record JVM overhead (buffer slicing, MessageDigest state reset) the practical ceiling is a few million records/sec/thread. On a partition with 100-byte records, the cleaner is CPU-bound on hashing long before it is disk-bound.

MEMORY SIZING, WORKED

Entry width = hashSize + 8 = 16 + 8 = 24 bytes. Usable slots = buffer × loadFactor / 24. At the 128 MB default with one thread: 134,217,728 × 0.9 ÷ 24 ≈ 5,033,164 keys. Rule of thumb: ~5 M keys per 128 MB per thread, or ~26.7 bytes of buffer per key once the load factor is accounted for. To compact a 50 M-key partition in a single pass you need ≈ 1.4 GB of dedupe buffer — and since that buffer is allocated off the broker's heap budget (it is a heap ByteBuffer unless you have configured otherwise), you must raise -Xmx alongside it.

The page cache interaction is worth dwelling on, because it is the reason compaction is throttled. The cleaner reads cold data — by definition it works on the oldest dirty bytes, which no consumer has touched in a while. Every one of those reads is a page-cache miss that also evicts a hot page. On a broker whose consumers are all caught up and served entirely from cache, an unthrottled cleaner can convert a 0%-disk-read workload into a heavily disk-reading one and add tens of milliseconds to fetch latency. Hence log.cleaner.io.max.bytes.per.second (default Double.MaxValue, i.e. unthrottled — you are expected to set it), enforced by a Throttler that sleeps the cleaner thread to hold the moving average down. Setting it to, say, 50 MB/s is one of the highest-value tunings on a broker hosting large compacted topics.

ARC 11 · PRODUCTION EXAMPLES

Where this breaks in the real world

__consumer_offsets, the partition that eats the broker

The single most-reported compaction incident in Kafka's history is __consumer_offsets growing without bound. The topic has 50 partitions by default, is compacted, and receives a write for every offset commit from every consumer in the cluster — with auto.commit.interval.ms at its 5-second default and a few thousand consumer instances, that is a sustained several-thousand-writes-per-second of tiny records into a modest key space. It is the ideal compaction workload right up until compaction stops, at which point it is the ideal disk-filling workload.

Historically it stopped for one of three reasons. Before KIP-346 (Kafka 2.0), a single uncaught exception in a cleaner thread — most commonly an IllegalStateException or an OOM from a record whose key exceeded the buffer's per-record assumptions — killed the thread outright, and with log.cleaner.threads=1 that meant compaction silently ceased for every compacted partition on the broker. The only symptom was disk growth; there was no metric that said "the cleaner is dead," and operators frequently found out at 95% disk. KIP-346 introduced the uncleanable-partition list and the uncleanable-partitions-count / uncleanable-bytes gauges so that one poisoned partition no longer stops the pool, and so the condition is at least observable.

The second cause is the message-format transition. Brokers upgrading through 0.10/0.11 hit segments with mixed magic bytes; a cleaner that encountered a v0 record without a timestamp while building a time index could throw, and the partition became permanently uncleanable until the operator deleted the offending segment by hand.

The third and most enduring cause is the undersized dedupe buffer meeting a large group population. A cluster with 20,000 consumer instances across many groups, each committing for dozens of partitions, produces millions of distinct (group, topic, partition) keys. Spread over 50 partitions that is fine; concentrated by an unlucky hash into a few hot partitions, one partition's distinct-key count can exceed the 5 M single-pass capacity, and that partition alone grows forever while the other 49 stay healthy. The tell is a partition-size histogram with one enormous outlier — and the fix is a buffer increase, not a partition-count increase, because repartitioning __consumer_offsets is not something you can safely do on a live cluster.

THE RECOVERY IS WORSE THAN THE INCIDENT

When a compacted __consumer_offsets partition has grown to hundreds of GB, the broker holding it cannot simply be restarted: LogLoader must scan and index every segment on startup, and the GroupMetadataManager must then load the entire partition into the group cache before any group whose coordinator lives there can commit or rebalance. Load times of 30–60 minutes have been reported, during which every affected consumer group is stuck in COORDINATOR_LOAD_IN_PROGRESS. The outage is not the disk filling; the outage is the recovery.

Kafka Streams changelogs and restore time

Every Kafka Streams state store is backed by a compacted changelog topic, and the time to restore a store after a rebalance or a node loss is directly proportional to the compacted size of that changelog, not its logical size. If compaction is keeping up, restoring a 10 M-key RocksDB store means reading roughly 10 M records. If compaction has fallen behind by 4×, it means reading 40 M — and restore happens while the task is unavailable, so compaction lag converts directly into rebalance downtime. This is why large Streams deployments monitor changelog partition size against expected key cardinality and alert on the ratio: a changelog that is 3× the size of the store it backs is a compaction-lag alarm dressed as a storage metric. (Standby replicas, num.standby.replicas, exist precisely to hide this cost, and windowed stores use cleanup.policy=compact,delete so that expired windows leave the changelog rather than accumulating as dead keys forever.)

Scale numbers worth carrying around

  • LinkedIn has publicly described clusters in the range of 7 trillion messages/day across ~100 clusters, with __consumer_offsets and internal metadata topics compacted; their operational guidance has long been to raise log.cleaner.threads above 1 on any broker hosting more than a handful of compacted partitions — the default of 1 is a single-partition-at-a-time greedy scheduler and it is simply not enough.
  • Netflix and Uber have both described multi-thousand-broker footprints where CDC-style compacted topics mirror database tables; the recurring theme in their talks is that the key cardinality of a compacted topic must be a capacity-planning input, exactly like throughput, because it sets the dedupe buffer requirement.
  • A widely-cited operational rule from these deployments: size log.cleaner.dedupe.buffer.size for the largest single compacted partition on the broker, using 26.7 bytes/key, and then multiply by log.cleaner.threads. Under-provisioning here is the one Kafka misconfiguration whose failure mode is silent, gradual, and unrecoverable-in-place.
THE FIVE-MINUTE AUDIT

On any cluster you inherit: list every topic with cleanup.policy=compact; for each, estimate distinct key cardinality; sum the largest per-broker figure; compare to log.cleaner.dedupe.buffer.size × log.cleaner.threads at 26.7 bytes/key. Then check uncleanable-partitions-count is zero on every broker and that max-dirty-percent has a sawtooth rather than a ramp. Those two graphs and one division will find the incident before it happens.

1 — Choosing the filthiest log

SCALALogCleanerManager.scala — grabFilthiestCompactedLog (simplified)
def grabFilthiestCompactedLog(time: Time): Option[LogToClean] = inLock(lock) {
  val lastClean = allCleanerCheckpoints                // TopicPartition -> Long
  val dirtyLogs = logs.filter {
    case (_, log) => log.config.compact                // only cleanup.policy contains compact
  }.filterNot {
    case (tp, _) => inProgress.contains(tp) || uncleanablePartitions(tp)
  }.map {
    case (tp, log) =>
      val (firstDirtyOffset, firstUncleanableOffset) =
        cleanableOffsets(log, lastClean.get(tp), time.milliseconds)
      LogToClean(tp, log, firstDirtyOffset, firstUncleanableOffset)
  }.filter(ltc => ltc.totalBytes > 0)

  val cleanable = dirtyLogs.filter(ltc =>
    ltc.cleanableRatio > ltc.log.config.minCleanableRatio || ltc.needCompactionNow)
  if (cleanable.isEmpty) None
  else {
    val filthiest = cleanable.maxBy(_.cleanableRatio)   // GREEDY. no fairness.
    inProgress.put(filthiest.topicPartition, LogCleaningInProgress)
    Some(filthiest)
  }
}

// cleanableRatio = dirtyBytes / (cleanBytes + dirtyBytes)
// needCompactionNow is set when max.compaction.lag.ms has been exceeded (KIP-354)

Note needCompactionNow. Without it, a log whose dirty ratio never reaches 0.5 is never cleaned — which for GDPR-style "the tombstone must take effect within N days" requirements is unacceptable. KIP-354 added max.compaction.lag.ms (default Long.MAX_VALUE) to force a pass regardless of ratio once the oldest dirty record has aged past it, and KIP-58 earlier added min.compaction.lag.ms (default 0) at the other end, guaranteeing a record stays uncompacted for a minimum time so a consumer has a bounded window in which it is certain to observe every intermediate update.

2 — The map, in all its skimpiness

SCALAOffsetMap.scala — SkimpyOffsetMap (condensed)
class SkimpyOffsetMap(val memory: Int, val hashAlgorithm: String = "MD5")
    extends OffsetMap {
  private val bytes    = ByteBuffer.allocate(memory)
  private val digest   = MessageDigest.getInstance(hashAlgorithm)
  private val hashSize = digest.getDigestLength                // 16 for MD5
  private val hash1    = new Array[Byte](hashSize)
  private val hash2    = new Array[Byte](hashSize)
  val bytesPerEntry = hashSize + 8                        // 16 + 8 = 24
  val slots: Int    = memory / bytesPerEntry
  private var entries  = 0
  private var lookups  = 0L
  private var probes   = 0L
  var lastOffset = -1L

  def put(key: ByteBuffer, offset: Long): Unit = {
    require(entries < slots, "Attempt to add a new entry to a full offset map.")
    lookups += 1
    hashInto(key, hash1)
    var attempt = 0
    var pos = positionOf(hash1, attempt)
    while (!isEmpty(pos)) {                // LINEAR PROBE
      bytes.position(pos); bytes.get(hash2)
      if (Arrays.equals(hash1, hash2)) {   // same key (digest) -> overwrite offset
        bytes.putLong(offset)
        lastOffset = offset
        return
      }
      attempt += 1
      pos = positionOf(hash1, attempt)
    }
    bytes.position(pos)                     // claim empty slot
    bytes.put(hash1); bytes.putLong(offset)
    lastOffset = offset
    entries += 1
  }

  def get(key: ByteBuffer): Long = {
    lookups += 1
    hashInto(key, hash1)
    var attempt = 0
    var pos = 0
    val maxAttempts = slots - entries + probeAttempts
    do {
      if (attempt >= maxAttempts) return -1L
      pos = positionOf(hash1, attempt)
      bytes.position(pos); if (isEmpty(pos)) return -1L
      bytes.get(hash2)
      attempt += 1
    } while (!Arrays.equals(hash1, hash2))
    bytes.getLong()
  }

  def utilization: Double = entries.toDouble / slots
}

Three things to notice. hash1 and hash2 are reused instance arrays — this class is explicitly single-threaded and allocation-free in its hot path, because it is called once per record over potentially billions of records and any per-record allocation would put the cleaner into a GC treadmill. There is no remove — you cannot delete from an open-addressed table without tombstone slots, and the cleaner never needs to, because the map is discarded and clear()ed between passes. And put throws when full rather than growing; the caller (buildOffsetMap) is responsible for stopping before that happens, which it does by checking map.utilization < maxLoadFactor before each segment.

3 — Pass 1: build, and stop when full

SCALALogCleaner.scala — buildOffsetMap (simplified)
def buildOffsetMap(log: UnifiedLog, start: Long, end: Long,
                   map: OffsetMap, stats: CleanerStats): Unit = {
  map.clear()
  val dirty = log.logSegments(start, end).toBuffer
  val maxDesiredMapSize = (map.slots * 0.9).toInt      // io.buffer.load.factor
  var full = false
  var offset = dirty.head.baseOffset

  for (segment <- dirty if !full) {
    checkDone(log.topicPartition)                        // abort/pause cooperation point
    full = buildOffsetMapForSegment(tp, segment, map, offset,
                                    maxDesiredMapSize, stats) 
    if (full) info(s"Offset map is full, +
       ${map.utilization} utilized; stopping at offset $offset")
  }
  info(s"Offset map for log ${log.name} complete.")
}

private def buildOffsetMapForSegment(...): Boolean = {
  var position = 0
  while (position < segment.log.sizeInBytes) {
    checkDone(tp)
    readBuffer.clear()
    val records = segment.log.slice(position, readBuffer.capacity)
    records.readInto(readBuffer, 0)
    throttler.maybeThrottle(records.sizeInBytes)          // io.max.bytes.per.second
    for (batch <- MemoryRecords.readableRecords(readBuffer).batches.asScala) {
      if (batch.isControlBatch) {
        // transaction markers: tracked, not indexed as keys
        transactionMetadata.onControlBatchRead(batch)
      } else for (record <- batch.asScala) {
        if (record.hasKey && record.offset >= startOffset) {
          if (map.size < maxDesiredMapSize) map.put(record.key, record.offset)
          else return true       // FULL — caller stops; rest stays dirty
        }
        stats.indexMessagesRead(1)
      }
    }
    position += records.validBytes
  }
  false
}

return true in the middle of the loop is the entire "compaction never catches up" incident, in one statement. It is not an error, it logs at INFO, and the pass proceeds perfectly correctly over a shorter range. Nothing in the code path knows or cares that it will have to do this again next pass, and the pass after that.

4 — Pass 2: copy the survivors, swap the segments

SCALALogCleaner.scala — cleanSegments (simplified)
private def cleanSegments(log: UnifiedLog, segments: Seq[LogSegment],
                          map: OffsetMap, currentTime: Long,
                          stats: CleanerStats, deleteHorizonMs: Long): Unit = {
  val cleaned = UnifiedLog.createNewCleanedSegment(log.dir, log.config,
                                                   segments.head.baseOffset)  // ".cleaned"
  try {
    for (old <- segments) {
      val retainDeletes = old.lastModified > deleteHorizonMs
      info(s"Cleaning $old in log ${log.name} into ${cleaned.baseOffset} " +
           s"with deletion horizon $deleteHorizonMs, " +
           (if(retainDeletes) "retaining" else "discarding") + " deletes.")
      cleanInto(log.topicPartition, old.log, cleaned, map,
                retainDeletes, log.config.maxMessageSize, stats, currentTime)
    }
    cleaned.onBecomeInactiveSegment()          // trim index, append final time index entry
    cleaned.flush()
    cleaned.lastModified = segments.last.lastModified   // PRESERVE mtime!
    log.replaceSegments(List(cleaned), segments)        // .cleaned -> .swap -> live
  } catch {
    case e: LogCleaningAbortedException =>
      try cleaned.deleteIfExists() finally throw e
  }
}

The single most easily-missed line is cleaned.lastModified = segments.last.lastModified. If the rewritten segment inherited the current wall clock as its mtime, then on a topic with cleanup.policy=compact,delete every compaction pass would reset the retention clock on the data it touched, and time-based deletion would never fire. Preserving the mtime keeps the two policies independent. It is also, incidentally, why KIP-534 moved the tombstone delete horizon out of file mtime and into the batch header: mtime is being used to mean "age of the newest data in this file," and overloading it to also mean "when did we first see this tombstone" was fragile.

WHY THE DEVELOPERS WROTE IT THIS WAY

Every unusual choice in this code traces to one constraint: the cleaner must never allocate proportional to data volume, and must never hold a lock proportional to data volume. That single rule explains the reused hash arrays, the fixed ByteBuffer with no resize, storing digests instead of keys, storing offsets instead of records, the readBuffer/writeBuffer pair sized by config rather than by segment, the checkDone cooperation points sprinkled through both loops, and the decision to build an entire new segment out-of-place and swap it in with a single map mutation. Kafka's broker gives most of its RAM to the page cache on purpose; a cleaner that competed with the page cache for heap would have made compacted topics slower than uncompacted ones, and the feature would have gone unused.

The rejected alternative worth knowing about is an on-disk key index — a persistent per-partition map from key to latest offset, maintained incrementally at append time. It would make compaction O(survivors) instead of O(dirty bytes) and would eliminate the buffer-size failure mode entirely. It was rejected because maintaining it on the append path means a random write per produce, which destroys the sequential-append property that gives Kafka its throughput, and because it introduces a second durable structure that must be kept consistent with the log across crashes. Kafka chose to pay O(n) periodically in the background rather than O(1) synchronously on every write. Redpanda's chunked-index approach is the closest thing to a middle path anyone has shipped.

You can now derive both reclamation policies from their constraints rather than memorising their configs. Retention is segment-granular because unlink is O(1) and rewriting is not; the active segment survives because it is being appended to, which is why segment.ms is the real retention floor. Compaction is a two-pass out-of-place rewrite driven by a fixed-size open-addressed digest map, which is why it is eventually consistent, why offsets keep their gaps, why a null key is silently dropped, and why an undersized dedupe buffer degrades progress rather than correctness — until the disk fills.
