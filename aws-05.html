EBS, Instance Store &
Storage Choices

Almost every SAA-C03 and SAP-C02 scenario question that mentions EC2 also hides a storage decision inside it — and the exam rewards candidates who can separate "this needs consistent IOPS," "this needs cheap sequential throughput," and "this data doesn't need to survive a stop/terminate at all" in about four seconds. This chapter builds exactly that reflex: the real baseline numbers, the real defaults, and the trap the exam asks about more than any other in this domain — what actually happens to a volume when an instance goes away.

ARC 01 · EXAM CONTEXT

Where this sits in the blueprint

Storage selection lives squarely in Design High-Performing Architectures on the Associate exam — 24% of SAA-C03 — and resurfaces on the Professional exam wherever a scenario asks you to migrate, modernize, or right-size an existing workload's storage. On both exams, the specific numbers in this chapter are among the most reliably testable facts in the entire storage domain: they are stable, documented, and easy to write a wrong-but-plausible distractor around.

Why it matters on test day: the exam almost never asks "what is gp3?" ARC 02 · THE COMMON WRONG INSTINCT

"Just pick gp3, it's cheap, and EBS obviously survives termination"

Three related wrong instincts show up constantly in practice exams and in real architecture reviews, and they all sound reasonable until you check the numbers or the flags:

  • "General purpose SSD is fine for everything." A candidate sees a workload needing 20,000 random IOPS with tight, predictable latency and reaches for gp3 anyway, because gp3 is the default and "SSD is SSD." They never check gp3's actual ceiling.
  • "Instance store is basically a fast EBS volume." A candidate sees "this instance type includes NVMe instance storage — fast, free, use it for the database" and treats it like any other attached disk, forgetting to ask what happens to that disk the moment the instance stops.
  • "EBS is persistent storage, so it obviously survives termination." A candidate reads that EBS volumes persist independently of instance lifecycle in general, and generalizes that to every volume on every instance, without checking a single per-volume flag that actually controls it.

Each of these is a half-truth wearing a whole-truth's confidence — which is exactly the shape of a good exam distractor. Section 3 quantifies why each one fails.

ARC 03 · WHY IT'S WRONG

The mechanism behind each trap, with real numbers

gp3's ceiling is real, and it is lower than you think

A gp3 volume gives you 3,000 IOPS and 125 MiB/s of throughput as a fixed baseline, included in the price, regardless of volume size. That baseline does not scale up with a bigger volume the way gp2's burst-credit model did — it is flat. Beyond it, you can provision additional IOPS and throughput independently, for extra cost, up to gp3's per-volume ceiling: 16,000 IOPS and 1,000 MiB/s. A workload that genuinely needs 20,000 IOPS cannot get there on gp3 at any price — the ceiling isn't a pricing tier, it's a hard per-volume limit.

Instance store is ephemeral — genuinely, not as a simplification

Instance store volumes are physically attached NVMe/SSD disks on the underlying host. Their data is lost on stop and on terminate — not just terminate — because stopping an instance can move it to different underlying hardware entirely. Some instance types can also lose instance-store data during certain underlying hardware failure or retirement events even without an explicit stop. This is a real, documented, testable AWS behavior: instance store is correct only for data you can regenerate or afford to lose completely, such as caches, scratch space, or buffer pools rebuilt from durable storage elsewhere.

DeleteOnTermination has different defaults for different volumes — this is the trap

Every EBS volume attached to an EC2 instance carries a per-volume DeleteOnTermination flag. For the root volume, that flag defaults to true — terminate the instance, and the root volume is deleted with it, by design. For additional volumes attached at launch (or attached later), the default is false — they survive termination and become orphaned, billable volumes until you delete them yourself. Candidates who "know EBS is persistent" routinely get this backwards in both directions: they lose data on a root volume they assumed would survive, or they rack up unexpected cost on data volumes they assumed AWS would clean up automatically.

THE EXACT TRAP, STATED ONE MORE WAY

"EBS is persistent storage" is true of the service. It is not automatically true of any given volume attached to any given instance — that depends entirely on one boolean flag, set per block device mapping, defaulting differently for the root volume than for everything else. Read the flag; never assume it.

ARC 06 · LIMITS, QUOTAS & EDGE CASES

What the correct approach still has to respect

  • gp3's provisioning ratio. Beyond the free baseline you can provision up to 16,000 IOPS and 1,000 MiB/s per volume, but throughput is also capped relative to IOPS — roughly 0.25 MiB/s of throughput per provisioned IOPS. Ask for more throughput than that ratio allows and the request is invalid; you need more IOPS provisioned, or a different volume type entirely.
  • io2's ceiling, and Block Express above it. Standard io2 scales to 64,000 IOPS per volume on Nitro-based instances, with 1,000 MiB/s throughput, and is designed for 99.999% annual durability — noticeably higher than the durability design target of other EBS volume types. io2 Block Express raises the ceiling further, to 256,000 IOPS and 4,000 MiB/s per volume, and requires a Nitro-based instance type to attach to.
  • st1/sc1 cannot boot an instance, and have a real minimum size. Both are HDD-backed, throughput- oriented, and start at a 125 GiB minimum volume size (scaling up to the same ~16 TiB ceiling as general-purpose volumes). Neither can be used as a boot/root volume — they exist purely for attached, sequential-workload data. st1 bursts up to roughly 500 MiB/s per volume; sc1, the cheaper and colder tier, bursts up to roughly 250 MiB/s. Neither supports meaningful random IOPS at any price.
  • Multi-Attach's real, narrow scope. Multi-Attach lets you attach a single io1 or io2 volume to up to 16 instances, and only within the same Availability Zone. It is correct only with a cluster-aware filesystem or clustered application that manages concurrent access itself — it is explicitly not a general-purpose shared filesystem, and attaching a plain, non-clustered filesystem to multiple instances through it will corrupt data under concurrent writes. If a scenario wants ordinary shared file access across many instances, the correct service is EFS or FSx, not EBS Multi-Attach.
  • The DeleteOnTermination trap, in full. Root volume default: true. Additional volumes attached at launch: default false. Either default can be overridden — at launch through the block device mapping, or after launch via aws ec2 modify-instance-attribute. An unattended default in either direction is a real production incident: silent data loss on the root volume, or a slow accumulation of orphaned, billed volumes nobody deleted.
  • Snapshots are incremental, but the first one never is. The first snapshot of a volume copies every block; every snapshot after that captures only the blocks that changed since the last snapshot. This is why a second snapshot of a mostly-unchanged multi-terabyte volume is fast and inexpensive relative to the first — but also why deleting an "intermediate" snapshot in a chain requires AWS to preserve whatever blocks later snapshots still depend on; you can't reason about snapshot cost by treating each one as a standalone full copy.

WHY SPLIT VOLUMES AT ALL

Separating the transactional data volume (io2, paying for consistent low-latency IOPS) from the log-archive volume (st1, paying almost nothing per GB for sequential throughput) means you're never paying io2 prices for data that's written once, read rarely, and never touched randomly. It also means a snapshot schedule on the data volume alone is cheap enough to run frequently, since snapshots are incremental after the first.

ARC 10 · LIMITS & SCALING NUMBERS

gp3's provisionable IOPS ceiling, by volume size

gp3 lets you provision IOPS independently of size — but only up to a real ratio: at most 500 IOPS per GiB provisioned, capped at the absolute 16,000 IOPS-per-volume ceiling. That means a small gp3 volume cannot reach the full 16,000 IOPS ceiling no matter how much you're willing to pay for it — you need at least 32 GiB (16,000 ÷ 500) before the ratio limit stops being the binding constraint. ARC 11 · REAL-WORLD SCENARIO CASE STUDIES

Three vignettes, in the exam's own style

Original scenarios, modeled on real service behavior — not reproductions of any actual exam question.

Case 1 — Vantage Analytics

A trading-signals team runs a database that services random point lookups at very high volume: their benchmark shows sustained demand for roughly 40,000 IOPS with tight, predictable latency, and any spike in tail latency causes visible errors downstream. Their current gp3 volume, maxed out at 16,000 provisioned IOPS, cannot keep up. Correct approach: migrate to io2, which scales to 64,000 IOPS per volume with a much tighter, more consistent latency profile than gp3 can offer even at its ceiling — the requirement is squarely inside io2's design point and doesn't yet need io2 Block Express.

Case 2 — Meridian Logs Co.

A logging pipeline ingests events and writes them sequentially to disk in large batches before a nightly batch job scans the entire day's file for aggregation — sustained sequential throughput around 300 MiB/s, essentially zero random IOPS, and a strong cost mandate from finance. Correct approach: st1. The workload is a textbook sequential, throughput-bound pattern with no random-access component, and st1's per-GB cost is far below gp3 or io2 for exactly this shape of work — provisioning gp3 or io2 here would be paying for random-IOPS consistency the workload never uses.

Case 3 — Northwind Retail (the DeleteOnTermination trap)

During a blue/green deployment, an engineer terminates the old fleet of EC2 instances as part of the cutover script. Each instance had exactly one EBS volume — its root volume, launched with default settings, holding a directory of audit logs the team assumed would "obviously persist since EBS is durable storage." After the cutover, the audit logs are gone. What happened: the root volume's DeleteOnTermination flag was left at its default of true; terminating the instance deleted the volume along with it, exactly as designed. Correct approach, going forward: either move anything that must survive onto a separate, additional volume (default false) attached after launch, or explicitly set the root volume's flag to false before any deployment that terminates instances — and take snapshots on a schedule regardless, since a flag someone can flip is not a backup strategy.

bashcreate-gp3.sh — provision a gp3 data volume with explicit performance
# illustrative — fill in your own AZ / size
aws ec2 create-volume \
  --availability-zone us-east-1a \
  --volume-type gp3 \
  --size 500 \
  --iops 6000 \
  --throughput 250 \
  --tag-specifications 'ResourceType=volume,Tags=[{Key=Name,Value=orders-db-data}]'
bashfix-delete-on-termination.sh — close the root-volume trap after launch
# find the root device name first
aws ec2 describe-instances --instance-ids i-0abc123 \
  --query 'Reservations[].Instances[].[RootDeviceName,BlockDeviceMappings]'

# then flip DeleteOnTermination to false for that device
aws ec2 modify-instance-attribute \
  --instance-id i-0abc123 \
  --block-device-mappings '[{"DeviceName":"/dev/xvda","Ebs":{"DeleteOnTermination":false}}]'
bashsnapshot-cycle.sh — incremental backup, then restore into a new AZ
# first snapshot: full copy under the hood; every later one is incremental
aws ec2 create-snapshot --volume-id vol-0abc123 \
  --description "orders-db-data nightly"

# restore into a fresh volume, in any AZ in the same Region
aws ec2 create-volume \
  --availability-zone us-east-1b \
  --snapshot-id snap-0def456 \
  --volume-type gp3
hclebs.tf — illustrative Terraform for a data volume + attachment
resource "aws_ebs_volume" "orders_data" {
  availability_zone = "us-east-1a"
  size              = 500
  type              = "gp3"
  iops              = 6000
  throughput        = 250
}

resource "aws_volume_attachment" "orders_data_attach" {
  device_name = "/dev/xvdf"
  volume_id   = aws_ebs_volume.orders_data.id
  instance_id = aws_instance.orders_app.id
  /* additional (non-root) volumes default DeleteOnTermination=false —
     acceptable here; this data volume should outlive instance replacement */
}
WHY THE EXAM CARES ABOUT THIS SYNTAX

You will not be asked to write CLI from scratch, but questions routinely show you a snippet like the modify-instance-attribute call above and ask what it changes, or show a create-volume call and ask whether the requested IOPS/throughput combination is even valid. Recognizing the flags — --iops, --throughput, --snapshot-id, DeleteOnTermination — and what each one actually controls is the tested skill, not CLI memorization for its own sake.

GATE · EXAM-DAY TAKEAWAYS

Before chapter 6: the five things worth over-learning

If you remember nothing else from this chapter, remember these: gp3's baseline is 3,000 IOPS and 125 MiB/s, flat, regardless of size, with a provisionable ceiling of 16,000 IOPS / 1,000 MiB/s beyond it. Instance store loses its data on stop and on terminate — genuinely, not as a simplification — and is correct only for data you can afford to lose entirely. The root volume's DeleteOnTermination flag defaults to true; additional volumes default to false — this single default-flag distinction is the chapter's signature exam trap, and it runs in both directions (unexpected data loss, or unexpected orphaned cost). Snapshots are incremental after the first one, which is why frequent backup schedules on large volumes are cheaper than they sound. And Multi-Attach is a narrow tool for cluster-aware applications on io1/io2 in a single AZ — never the exam's answer for "share a filesystem across many instances," which is EFS or FSx territory.
