BITCOIN INTERNALS · CHAPTER 04

Script: The Stack Machine

Every Bitcoin output carries a tiny program, and every full node on Earth must execute that program to agree on whether a transaction is valid. That single fact — universal, mandatory execution by strangers — is the design constraint that shaped Script more than any other. This chapter derives the stack machine from that constraint, walks every opcode family, traces P2PK through P2SH byte by byte, and ends with a real interpreter: genuine opcodes, genuine stack effects, genuine secp256k1 signature verification, implemented in this page's JavaScript.

ARC 01 · THE PROBLEM

A spending condition that strangers must all agree runs the same way

Chapter 3 decoded a transaction down to its bytes and found two fields sitting inside every input and output that we deliberately skipped: scriptSig and scriptPubKey. They are not metadata. They are programs — a locking program attached to every output, and an unlocking program supplied by whoever spends it. This chapter is about the language those programs are written in, and why that language looks nothing like a general-purpose one.

State the requirement precisely, because it is unusually harsh. A spending condition must be:

  • Expressive enough to encode "the person who knows the private key for this hash may spend this," and, later, "any 2 of these 3 keys," "only after block 700,000," "only if you can also produce a matching secret."
  • Executed identically by every node — thousands of independent implementations and versions of Bitcoin Core, on different hardware, in different countries, must reach the exact same true/false verdict, or the chain forks.
  • Executed by nodes with no relationship to the spender. A miner in Reykjavik and a hobbyist's Raspberry Pi in Nairobi both run every script in every block they see, for free, forever, whether they like the transaction or not.
  • Bounded in cost. Whatever "execute the program" means, it must take a predictable, small amount of CPU time — because it happens roughly seven times a second, worldwide, on hardware nobody funded for the privilege.

Put those together and you get the design question this whole chapter answers: what is the least powerful language that can still express real spending conditions, given that every verifier is an unpaid, untrusted stranger who cannot be allowed to get stuck? Satoshi's answer, present since the 2009 source drop, is a stack machine: no variables, no memory addresses, no function calls, and, critically, no loops.

WHY THIS MATTERS FOR THE NEXT 12 CHAPTERS

Script is the layer where "the code is the contract" stops being a slogan and starts being literally true — a scriptPubKey is not a description of a spending rule, it is the spending rule, byte for byte, forever. Every advance from here on — SegWit (ch.12), Taproot (ch.13), Lightning (ch.14) — is a change to what programs can say or how cheaply they can say it. None of them add a loop. Understand why now, and the rest of the course reads as a single consistent design philosophy rather than a pile of unrelated soft forks.

ARC 02 · HISTORICAL CONTEXT

Script has been edited by subtraction more than by addition

Most languages grow features over time. Script's history is the opposite: it shipped with a wide, general opcode set in January 2009, and within eighteen months roughly a third of it was permanently switched off. Every addition since has been surgical — one or two opcodes, activated by soft fork, each closing a specific gap. Click through the record.

DEEP CONTEXT · THE DISABLING WAS THE DESIGN DECISION

It is tempting to read the 2010 opcode removals as a bug-fix footnote. Read the other way, they are the moment Script's real design philosophy became visible: when in doubt about whether an opcode's worst case is boundable, remove it rather than sandbox it. Ethereum, fifteen years later, chose the opposite answer to the same fear — meter every instruction and let anything run as long as its owner pays (the blockchain fundamentals course, ch.13, covers gas). Bitcoin's answer was to make the question "how do I meter this opcode?" mostly not arise, by refusing to ship opcodes whose cost isn't obvious by inspection. Both are coherent engineering answers to the identical problem: an untrusted program that a stranger must execute for free.

ARC 03 · NAIVE SOLUTION

Attempt #1: give spending conditions a real programming language

Derive this honestly, the way an engineer arriving fresh at the problem would. "The person who owns this output should be able to specify arbitrary conditions" sounds like a request for a general-purpose language. So imagine Script had shipped with what every other stack-based language of the era had: a jump instruction and a counter.

pseudo-scriptnaive_turing_complete.script — the strawman, annotated
; "unlock if you can find x such that repeated hashing
;  of x eventually produces a value starting with 0x00 —
;  a tiny proof-of-work puzzle baked into one output"
OP_0                    ; loop counter i = 0
loop_top:
  OP_DUP OP_HASH256   ; stack: i, hash(i)
  OP_0x00 OP_EQUAL  ; does the hash start with a zero byte?
  OP_IF OP_JUMP done OP_ENDIF
  OP_1ADD              ; i = i + 1
  OP_JUMP loop_top    ; ← THIS INSTRUCTION DOES NOT EXIST IN BITCOIN
done:
  OP_TRUE

Nothing about this is unreasonable at first glance — OP_JUMP and a counter are exactly what you'd reach for to express "keep trying until a condition holds," and plenty of legitimate contracts want exactly that shape (auctions, escrow with retries, verifiable delay puzzles). A general-purpose stack machine with jumps is strictly more expressive than one without. More expressive sounds strictly better. It is not — and the next section shows precisely where that intuition breaks, with a live model of the failure rather than an assertion of it.

ARC 04 · WHY IT FAILS

One attacker, one transaction, every node on Earth wastes CPU forever

Here is the argument that kills OP_JUMP, stated as a threat model rather than a vibe. A scriptPubKey is permissionless to author: anyone can put any legal opcode sequence in an output. Once mined, that output's script becomes something every future full node — forever, or until the output is spent — must be prepared to execute the instant someone tries to spend it, in order to validate that spend. Now suppose one attacker crafts a scriptPubKey whose loop condition is never true — the simplest possible malicious contract, three opcodes different from the honest one above. Every node that receives a transaction attempting to spend it starts executing, and none of them can finish. Not "finishes slowly" — never returns, by the halting problem's own guarantee that no general algorithm can distinguish "still going" from "will never stop" for arbitrary programs.

THE NUMBERS THAT MAKE THIS A NETWORK ATTACK, NOT A LOCAL ONE

Compare costs. The attacker pays for one transaction's worth of bytes and one fee — cents. Every full node that relays or validates it pays with a CPU thread that never comes back, and there were roughly 15,000+ reachable full nodes in 2024 alone (bitnodes.io), plus every SPV-adjacent service, block explorer, and exchange hot-wallet validator. Attack cost stays flat as the network grows; damage scales with node count. That asymmetry — fixed attacker cost, linearly scaling victim cost — is the signature of a amplification denial-of-service, and it is disqualifying for anything that must run permissionlessly on every node. Metering (charge per instruction, like gas) fixes the economics but not the underlying uncertainty of "when will this finish?" — Bitcoin's designers chose to remove the uncertainty itself.

So OP_JUMP cannot ship. But conditional logic (OP_IF), arithmetic, and cryptographic verification clearly can — nothing about them is unbounded. The next section derives the actual rule: not "no branching," but no way to revisit an instruction, which is a much narrower and more surgical cut than it first sounds.

ARC 05 · THE ACTUAL RULE

Structural termination: forward-only instructions, two stacks, nothing else

Re-derive the constraint precisely instead of just banning the one opcode that broke it. The property Script needs is termination provable by inspection, without running the program — a verifier should be able to look at a script and know its worst-case cost before executing a single opcode. That is achievable if and only if the instruction pointer only ever moves forward. No backward jump means no instruction executes more than once, which means total work is bounded by script length — a number visible on the wire before execution starts. This is termination by construction, not termination by policy: there is no metering step to get wrong, no gas price to misconfigure, because the shape of the language makes infinite loops inexpressible, not merely discouraged.

From that one rule, the rest of Script's shape follows almost mechanically:

  • Conditionals survive. OP_IF/OP_NOTIF/OP_ELSE/OP_ENDIF only ever skip forward to their matching OP_ENDIF — never back. Branching is fine; revisiting is not.
  • No user-defined functions, no recursion. A function call is a jump with a promise to jump back — exactly the primitive that was excluded. Every apparent "function" in Script (a redeem script, later a tapscript leaf) is really "run one flat, straight-line-with-forward-branches program, then stop."
  • Two stacks, not one, because some real conditions need to stash a value mid-computation without a named variable. The main stack does the work; the alt stack (OP_TOALTSTACK / OP_FROMALTSTACK) is scratch space — a way to say "hold this" without inventing named memory, which would reopen the door to addressable, hence loopable, state.
  • scriptSig may only push data — no opcodes that do work. This was tightened over time (see §6, §11) specifically because a scriptSig that could execute logic could inject behavior the scriptPubKey author never wrote, including, historically, opcodes that made outputs' true spending conditions ambiguous.

THE OTHER HALF OF THE RULE: SCRIPTSIG AND SCRIPTPUBKEY RUN SEPARATELY

The original 2009 implementation actually concatenated scriptSig and scriptPubKey into one script and ran it as a single program — simple, and dangerous: nothing stopped a scriptSig from pushing an OP_IF or an OP_RETURN of its own, potentially forcing a different execution path through the scriptPubKey than its author intended, or aborting validation in a way the locking script never asked for. Bitcoin Core has since executed them as two separate, sequential programs: run scriptSig to completion against an empty stack, then run scriptPubKey against whatever stack scriptSig left behind — the stack is carried over by reference, the two scripts' instruction streams never touch. Combined with the modern push-only scriptSig rule (the thinking behind BIP62, made consensus-critical for segwit inputs), the spender can hand over data — signatures, public keys, redeem scripts — but never logic. Only the output's original author's opcodes ever execute. §15's debugger runs scripts exactly this way: two phases, one carried stack.

ARC 06 · WHAT THE RESTRICTION STILL COSTS

Non-Turing-completeness is not free either

Removing loops and jumps buys structural safety, but the bill did not go to zero — it went somewhere else. Four costs are worth being precise about, because each one reappears later in the course as the reason a specific soft fork happened:

  • Bugs still shipped inside the restricted language. A non-Turing-complete instruction set is not automatically a bug-free one. OP_CHECKMULTISIG's off-by-one (§8, §11) is a correctness bug that exists entirely within "safe" opcodes and, because millions of real coins now depend on its exact buggy behavior, can never be fixed without breaking every multisig output ever created.
  • Expressing anything beyond simple predicates gets verbose fast. With no functions and no loops, "2-of-3 multisig" (§8) needs a dedicated opcode (OP_CHECKMULTISIG) rather than being composable from primitives, and anything genuinely recursive — "this output can only be spent into another output with the same script" — was inexpressible at all until very recently (see the CTV/APO discussion below), because expressing it safely without a general jump is a real research problem, not a one-line fix.
  • The fix for "what if we need more expressiveness" is a new opcode via soft fork, not a library update. Every capability added since 2009 — absolute timelocks (OP_CHECKLOCKTIMEVERIFY, BIP65, 2015), relative timelocks (OP_CHECKSEQUENCEVERIFY, BIP112, 2016) — required coordinated network-wide soft-fork activation. A Turing-complete VM lets you write the new logic in the existing language; Script requires a new primitive and a consensus upgrade.
  • Covenants remain contentious precisely because Script was built to resist recursion. A covenant needs a script to reason about the transaction spending it — including, for full generality, the output that transaction creates. OP_CAT (concatenate two stack items) would let scripts build up and compare arbitrary byte strings, a step toward that — which is exactly why it stayed off after 2010, and why its 2023-era proposed return (BIP 347) is still debated: the same operation that enables vaults and better DeFi-style primitives also enables constructions no one has fully modeled the failure surface of. BIP119 (OP_CHECKTEMPLATEVERIFY) and BIP118 (SIGHASH_ANYPREVOUT) are narrower, purpose-built answers to the same demand, and as of this writing neither has achieved the rough consensus Bitcoin soft forks require to activate.
THE HONEST FRAME

Script's restriction did not eliminate the tension between expressiveness and safety — it moved the tension to the opcode-design and soft-fork-activation layer, where it can be argued over in public for years before anything ships. That is slower and more conservative than "add a library function," and it is also why, sixteen years in, Bitcoin has never had a Script-level exploit that stole funds at scale (contrast the blockchain fundamentals course's coverage of EVM-era hacks). Slow is a feature when the alternative is losing money to a bug that shipped last Tuesday.

DEEP CONTEXT · WHY ARITHMETIC IS CAPPED AT 32 BITS

Numeric opcodes operate on CScriptNum, a little-endian, sign-and-magnitude integer capped at 4 bytes for arithmetic inputs — roughly ±2.1 billion. That is not an arbitrary limit: it keeps every arithmetic opcode's output size bounded and predictable regardless of input, which matters when scripts are size-limited (§8) and every byte of stack state has to be accounted for. It is also why OP_MUL and OP_DIV are disabled rather than merely range-checked — multiplying two 32-bit numbers can overflow 32 bits, and 2010-era Bitcoin removed the opcodes rather than add overflow-checking logic whose correctness would itself need auditing across every client.

ARC 08 · INTERNAL IMPLEMENTATION

Bytes, execution order, and the evolution from P2PK to P2SH

Three pieces: (a) how a script is actually encoded on the wire, (b) how the five major script types evolved, each fixing a concrete flaw in the last, and (c) the exact two-phase algorithm P2SH uses to let the spender, not the payer, carry the cost of a complex condition.

(a) Byte layout: pushdata encoding

A script is just a byte string — chapter 3's VarInt-prefixed scriptSig/scriptPubKey fields. Every byte is either an opcode or, for pushes, a length-then-data pair whose encoding depends on size:

Three hard consensus limits bound every script's cost, checked before or during execution — not by metering usage, but by rejecting anything that could exceed them: MAX_SCRIPT_SIZE = 10,000 bytes per script; MAX_SCRIPT_ELEMENT_SIZE = 520 bytes for any single stack item; MAX_OPS_PER_SCRIPT = 201 non-push opcodes; and a combined main+alt stack depth cap of 1,000 elements. (b) The script-type evolution, traced

Five designs solved the same problem — "prove you control this output" — in succession, each patching a concrete weakness in its predecessor. Step through what actually sits on the stack at each point:

P2WPKH/P2WSH (chapter 12) move the same P2PKH/P2SH logic into a separate witness structure outside the txid, fixing malleability and changing fee accounting — the Script rules barely change, the serialization does. P2TR (chapter 13) replaces ECDSA with Schnorr and adds a script tree that lets a spender reveal only the branch they use — a genuinely new execution model (Tapscript), not just a new wrapper. Both build directly on the stack machine this chapter establishes; neither needs re-deriving it.

(c) P2SH's two-phase validation — the spender pays for complexity

BIP16 (Gavin Andresen, activated April 2012) solved a real operational problem: pre-2012, a merchant wanting to be paid into a 2-of-3 multisig had to publish the entire multisig scriptPubKey — long, and paid for in fees by whoever created that output, i.e. usually the payer, forever, every time anyone looks up the output. P2SH inverts who pays: the output just commits to a hash of the real script (the redeem script), and the spender reveals and pays for the real script only when spending it. Validation runs in two distinct passes over the data:

  • Phase 1 — the standard evaluation. Run scriptSig (push signature(s), pubkey(s), and the serialized redeem script), then run the scriptPubKey template OP_HASH160 <20-byte hash> OP_EQUAL against the resulting stack exactly as any other script would run. This only proves "the last item the spender pushed hashes to the value this output committed to" — it says nothing yet about signatures.
  • Phase 2 — triggered only if phase 1 passed AND the scriptPubKey exactly matches the P2SH template. Take the stack as it stood right after scriptSig finished (before phase 1 consumed anything), pop the redeem script off the top, parse those bytes as a new script, and execute that against the remaining stack items. This is the real spending-condition check — the multisig, the timelock, whatever the redeem script actually encodes.

The overall spend is valid only if both phases succeed. Note the elegance: nodes that have never heard of P2SH (pre-2012 software) still validate phase 1 correctly under the old rules, see a normal-looking OP_EQUAL pass, and accept the transaction — this is precisely what made BIP16 deployable as a soft fork. §15's debugger implements exactly this two-phase (in fact three-stage, counting scriptSig) execution.

ARC 09 · TRADEOFFS

Every chain scripting model, compared honestly

Bitcoin is not the only chain that had to answer "how expressive, and at what verification cost?" The spread of real answers shows there is no dominant strategy — only different placements of the same underlying risk:

SYSTEMMODELWHAT THEY BOUGHTWHAT THEY PAID
Bitcoin ScriptNon-Turing-complete stack machine, no loops/recursion termination provable by inspection tiny attack surface covenants need dedicated soft forks verbose multisig pre-Taproot

Read the table as a proof by exhaustion, the same way chapter 9's blockchain-fundamentals equivalent read the consensus table: the expressiveness/verifiability tradeoff cannot be dodged, only priced differently. Bitcoin priced it in 2009 currency, when "every stranger runs everyone's code for free" was a genuinely novel requirement with no existing playbook, and the project's core bet was that boring, inspectable execution beats flexible execution for something meant to hold value for decades.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What script execution actually costs, and where the sigop limit comes from

Script's cost model has two independent axes: raw CPU time to run the stack machine (cheap — bounded by the 201-opcode and 10,000-byte limits from §8), and signature verification, which dominates real-world validation time because elliptic-curve operations are orders of magnitude more expensive than stack pushes. A block isn't limited by "how many opcodes total" so much as by sigops — MAX_BLOCK_SIGOPS_COST = 80,000 (a weight-based figure post-SegWit; pre-SegWit blocks capped at 20,000 sigops per 1 MB block).

MODEL, NOT MEASUREMENT

The curve is an analytic sketch (linear per-signature cost plus a fixed per-block overhead term) tuned to match the shape of published libsecp256k1 ECDSA-verify benchmarks (tens of microseconds per signature on commodity hardware) — the point is the shape: verification is embarrassingly parallel and roughly linear in sigop count, which is exactly why -par multithreaded script verification in Bitcoin Core (since 0.9, 2014) yields near-linear speedup on multicore validation, and why MAX_BLOCK_SIGOPS_COST exists at all — without it, an attacker could craft a small, cheap-to-download block that is deliberately expensive to verify, an asymmetry attack in miniature of §4's loop-bomb argument.

Security-wise, the attack surface Script exposes is narrow by design: no memory corruption is possible (there is no addressable memory), no reentrancy is possible (there is no ability to call back into another script), and the entire class of "arbitrary code execution" bugs that plague general-purpose VMs is structurally absent. What remains are exactly the bug classes you'd expect from a small, fixed instruction set: encoding ambiguities (malleability, chapter 5), off-by-one errors in individual opcodes (§11), and cases where the restricted language is too restrictive and gets worked around in ways that carry their own risk (large OP_RETURN payloads, §11).

ARC 11 · REAL-WORLD INCIDENTS

Every scar Script actually carries

Incident 1: the August 2010 opcode purge

Within the first eighteen months of the network's life, roughly fifteen opcodes — OP_CAT, OP_SUBSTR, OP_LEFT, OP_RIGHT, OP_INVERT, OP_AND, OP_OR, OP_XOR, OP_2MUL, OP_2DIV, OP_MUL, OP_DIV, OP_MOD, OP_LSHIFT, and OP_RSHIFT — were disabled by making them unconditionally invalid. Contemporary accounts describe the immediate trigger as an implementation flaw in the bit-shift opcodes (OP_LSHIFT/OP_RSHIFT): a large or negative shift count could drive the interpreter into undefined behavior rather than a controlled failure — exactly the kind of memory-safety bug a byte-string-manipulation opcode invites, and exactly the kind of thing a stack machine with no addressable memory is supposed to make impossible. Rather than patch each opcode's edge cases individually and hope the audit was complete, the fix removed the entire cluster of string/bitwise/extended-arithmetic opcodes whose worst-case behavior hadn't been proven safe. Root cause, one level up: shipping opcodes whose cost and failure modes hadn't been fully reasoned about, in a context where "we'll patch it later" isn't available once outputs already exist on-chain committing to the old rules.

Incident 2: OP_CHECKMULTISIG's extra-element bug — permanent by construction

The original OP_CHECKMULTISIG implementation pops one more stack item than its own signature-count and pubkey-count arguments require — an unused "dummy" element that every multisig scriptSig must supply and every interpreter must consume, for no semantic reason other than a coding mistake in the first implementation. Because thousands of real multisig and P2SH outputs were created that rely on the interpreter popping exactly that many items, fixing the bug would invalidate every one of them — it is now indistinguishable from a protocol feature. The best the project could do was constrain what value the dummy is allowed to hold: BIP147 (NULLDUMMY, activated alongside SegWit in August 2017) made it consensus-invalid for that element to be anything other than an empty push, closing a transaction-malleability vector (an attacker could previously alter that unused byte, changing the txid without invalidating the signatures — chapter 5's subject). The interpreter in §15 reproduces the extra pop exactly, and lets you toggle NULLDUMMY enforcement on or off to see both eras.

Incident 3: OP_RETURN and the "spam" debates

Once operators realized OP_RETURN creates a script that is provably unspendable — the opcode unconditionally fails execution, so no signature could ever satisfy it — Bitcoin Core added it (2014) as an officially sanctioned way to embed a small amount of arbitrary data (originally 40 bytes, later raised to 80) in an output that nodes could recognize as intentionally prunable, rather than have projects like early colored-coin and Counterparty implementations fake data storage with un-spendable-looking multisig or P2PKH outputs that looked like real spending conditions and bloated the UTXO set (chapter 6) as if they might one day be spent. The policy-level size limit has been argued over repeatedly since (most visibly around the 2023 Ordinals and inscriptions surge, which mostly bypassed OP_RETURN entirely by hiding data in witness script paths instead) — a live illustration of §6's point that a restricted language pushes disputes about "what should be allowed" into policy and social-consensus territory rather than resolving them once in the language design.

Incident 4: Taproot deliberately retires OP_CHECKMULTISIG

Tapscript (BIP342, part of the November 2021 Taproot activation) does not carry legacy OP_CHECKMULTISIG forward for new multisig-style spends — it introduces OP_CHECKSIGADD instead, which checks one signature and accumulates a running count on the stack, letting scripts express "k of n" without the O(n·m) worst-case signature-matching loop or the inherited dummy-element baggage of the original opcode. This is the project explicitly declining to keep dragging a known wart into new script versions even though it could not remove it from the old ones — the incident is really the absence of one, and it is instructive precisely because it shows how the 2010-era "we can never take this back" lesson was internalized into every later opcode design.

C++interpreter.cpp — EvalScript(), the parts that matter
bool EvalScript(std::vector<valtype>& stack, const CScript& script,
                unsigned int flags, const BaseSignatureChecker& checker,
                SigVersion sigversion, ScriptError* serror)
{
    CScript::const_iterator pc = script.begin(), pend = script.end();
    std::vector<bool> vfExec;             // one entry per open OP_IF/OP_NOTIF; forward-only
    std::vector<valtype> altstack;             // §5's second stack
    if (script.size() > MAX_SCRIPT_SIZE)      // §8(a): 10,000-byte consensus limit
        return set_error(serror, SCRIPT_ERR_SCRIPT_SIZE);
    int nOpCount = 0;

    while (pc < pend)
    {
        bool fExec = !count(vfExec.begin(), vfExec.end(), false);  // are we inside a false branch?

        opcodetype opcode;
        valtype vchPushValue;
        if (!script.GetOp(pc, opcode, vchPushValue))
            return set_error(serror, SCRIPT_ERR_BAD_OPCODE);
        if (vchPushValue.size() > MAX_SCRIPT_ELEMENT_SIZE)   // §8(a): 520-byte item limit
            return set_error(serror, SCRIPT_ERR_PUSH_SIZE);
        if (opcode > OP_16 && ++nOpCount > MAX_OPS_PER_SCRIPT)  // §8(a): 201-op ceiling
            return set_error(serror, SCRIPT_ERR_OP_COUNT);

        if (opcode == OP_CAT || opcode == OP_MUL || opcode == OP_LSHIFT /* ... */)
            return set_error(serror, SCRIPT_ERR_DISABLED_OPCODE);  // §11 incident 1, made permanent

        if (fExec && 0 <= opcode && opcode <= OP_PUSHDATA4)
            stack.push_back(vchPushValue);         // pushes only run inside a true branch
        else if (fExec || (OP_IF <= opcode && opcode <= OP_ENDIF))
            switch (opcode) {              // §7: one case per opcode family
                /* OP_IF / OP_NOTIF / OP_ELSE / OP_ENDIF push/flip/pop vfExec — FORWARD ONLY */
                /* OP_DUP / OP_HASH160 / OP_EQUALVERIFY / OP_CHECKSIG / OP_CHECKMULTISIG / ... */
            }
    }
    return vfExec.empty();   // every OP_IF must have found its OP_ENDIF
}

The bug from §11 incident 2, in the actual shape it ships as (simplified from interpreter.cpp's OP_CHECKMULTISIG case):

C++interpreter.cpp — OP_CHECKMULTISIG, the extra pop preserved forever
case OP_CHECKMULTISIG:
{
    int i = 1;
    int nKeysCount = CScriptNum(stacktop(-i), fRequireMinimal).getint();
    /* ... pop nKeysCount pubkeys ... */
    int nSigsCount = CScriptNum(stacktop(-i), fRequireMinimal).getint();
    /* ... pop nSigsCount signatures, verify each against remaining pubkeys in order ... */

    // Off-by-one from the ORIGINAL 2009 implementation: one extra unused
    // stack element must be popped that the opcode's own arguments never
    // asked for. Every multisig scriptSig ever written supplies it. It can
    // never be removed — doing so would change what a valid scriptSig looks
    // like for every multisig output already on the chain.
    if (i > (int)stack.size())
        return set_error(serror, SCRIPT_ERR_INVALID_STACK_OPERATION);
    if ((flags & SCRIPT_VERIFY_NULLDUMMY) && stacktop(-i).size())   // BIP147, 2017
        return set_error(serror, SCRIPT_ERR_SIG_NULLDUMMY);
    popstack(stack);   // the dummy element, discarded, forever mandatory

    stack.push_back(fSuccess ? vchTrue : vchFalse);
}
break;
WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Reject unconditionally rather than sandbox. §11's disabled opcodes are checked and rejected before they ever execute — there is no attempt to run them "safely" with limits, because proving a limit is sufficient is itself hard to get right, and getting it wrong once is permanent. 2. Consensus limits are checked inline, every iteration, not estimated up front. nOpCount increments and is checked on every opcode, not computed once from script length, because push-only data doesn't count against the 201 limit and the difference matters. 3. A bug you can't fix, you can still fence. BIP147 didn't touch the buggy pop — it added a narrower rule (the popped value must be empty) that closes the concrete harm (malleability) without touching the millions of existing outputs that depend on the original, wrong behavior continuing to validate.
