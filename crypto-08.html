APPLIED CRYPTOGRAPHY · CHAPTER 08

Key Derivation: HKDF, PBKDF2
& Argon2

Every primitive in the last six chapters — AES, ChaCha20, HMAC, GCM — takes a uniformly random key of a fixed length as an axiom. Nothing you actually have lying around is that. A password is a short, human-chosen string with maybe 30 bits of real entropy pretending to be a 256-bit key. A Diffie–Hellman shared secret is a specific element of a mathematical group, not a uniform bit string, and you usually need several independent keys from it, not one. This chapter is about the machinery that sits between "a secret exists" and "a cipher can use it": HKDF for turning one high-entropy secret into many clean keys, and PBKDF2 / Argon2 for turning a low-entropy password into something an attacker can't just guess a billion times a second. You will implement a real SHA-256, a real HMAC, and a real HKDF in this browser, verify all three against their official test vectors, and then use real, cited GPU benchmark data to compute exactly how long each choice actually survives an attacker.

ARC 01 · THE PROBLEM

Two different secrets, two different diseases

Chapters 2–7 built a toolbox that assumes keys arrive pre-formed: N uniformly random bytes, generated once, used once for one purpose. In practice a key almost never starts that way. It starts as one of two much messier things, and each is broken for a different reason.

Case one: a password. A human picked it, which means its real entropy is nowhere near its bit length. An 8-character password drawn from lowercase letters has log2(26^8) ≈ 37.6 bits of entropy — and that's the uniform-random-over-that-charset upper bound; real human passwords cluster on dictionary words, keyboard patterns, and "P@ssw0rd1"-style substitutions, so the practical entropy is usually far lower still. An AES-256 key needs 256 bits. You cannot manufacture 256 bits of security out of a string that only encodes 30–40 bits of unpredictability by decree — you can only tax the gap between the two, making each guess expensive enough that trying all of them is impractical. That is a fundamentally different job from encryption.

Case two: a Diffie–Hellman (or ECDH) shared secret. Two parties compute the same group element — g^(ab) mod p in finite-field DH, or a curve point's x-coordinate in ECDH (chapter 11 derives this in full; if you've taken the Blockchain course's elliptic-curve chapters, the arithmetic will be familiar, though this course develops what you need standalone). That value has plenty of entropy, but it is not a uniform bit string — it is a specific residue with algebraic structure inherited from the group operation, and its byte representation is exactly one width, not "however many keys you need." A real protocol needs several independent keys from one DH exchange: a client→server encryption key, a server→client encryption key, one or two MAC keys, IVs. Slicing one fixed-width group element into multiple "keys" by taking different byte ranges reuses correlated material across primitives — precisely the key-reuse mistake chapter 7 spent an entire section showing you how to weaponize against GCM.

Two distinct problems, two distinct tools. Key stretching (PBKDF2, Argon2) attacks the low-entropy problem by making each candidate guess expensive. Key derivation / expansion (HKDF) attacks the multiple-keys-from-one-secret problem by cryptographically stretching a high-entropy secret into as many independent-looking, correctly-sized outputs as a protocol needs. Confusing the two is itself a real vulnerability class — you'll see both directions of that mistake in §11.

WHY THIS MATTERS FOR THE REST OF THIS COURSE

Chapter 11 (Diffie–Hellman/ECDH) produces a shared secret and immediately hands it to HKDF. Chapter 13 (TLS 1.3) derives its entire key schedule — handshake secrets, application traffic secrets, resumption secrets — through nested HKDF calls. Chapter 16's capstone re-derives all of it from scratch. Everything downstream assumes you understand extract-then-expand at the byte level, not just the name. That's this chapter's job.

ARC 03 · NAIVE SOLUTION

Attempt #1: just use the secret as the key

Derive the failure honestly before reaching for the fix. Both flavors of naive key handling look reasonable at a glance:

pythonnaive_kdf.py — the strawman, annotated
# Case A: "the password IS basically the key"
def key_from_password(password: str) -> bytes:
    raw = password.encode("utf-8")
    return raw.ljust(32, b"\x00")[:32]   # pad/truncate to AES-256 width

# Case B: "the DH secret IS basically the key(s)"
def keys_from_dh(shared_secret: int, key_len: int = 32) -> tuple[bytes, bytes]:
    raw = shared_secret.to_bytes(256, "big")   # e.g. a 2048-bit DH group
    enc_key = raw[:key_len]         # first 32 bytes → encryption key
    mac_key = raw[key_len:2*key_len]  # next 32 bytes → MAC key
    return enc_key, mac_key

Both functions type-check. Both "work" in the sense that they deterministically produce 32 bytes any AES or HMAC call will happily accept. Both are broken in ways that have nothing to do with a bug in this code — the bugs are in what these functions are: neither one increases the attacker's cost of finding the input, and neither one removes the structure already present in that input.

ARC 04 · WHY IT FAILS

The gap between "has entropy" and "is a key" is exploitable, quantifiably

Take each naive function and hand it to an attacker who has an offline copy of whatever it produced (a leaked hash, a captured handshake). Both fail, for related but distinct reasons.

Case A: the password path collapses to a dictionary attack

If key_from_password is all that stands between a password and a key, an attacker doesn't attack AES — AES-256 is fine. They attack the 32 bytes you claimed was a key by trying candidate passwords and checking if any produces the value they captured. Each candidate costs exactly one pad/truncate operation — effectively free. Using this chapter's own SHA-256 implementation (verified in §8) as a stand-in cost per guess, and a single consumer GPU's published raw-SHA-256 throughput of ~22 billion hashes/second (hashcat v6.2.6, one RTX 4090, hash-mode 1400 — cited in full in §10), an attacker exhausts every 8-character lowercase password (26^8 ≈ 2.09 × 10^11 candidates) in about 9.5 seconds. Not 9.5 hours — 9.5 seconds, on one consumer graphics card. There is no key length that fixes this; the weakness is entropy, not key size.

Case B: the DH path leaks structure and reuses material

Slicing a raw group element has two separate problems. First, g^(ab) mod p is not uniformly distributed over all 2048-bit strings — depending on the group's construction it can be biased toward quadratic residues, and its top bits are constrained by the modulus p not being a power of two, so naive byte slicing can hand an attacker a distinguisher that a properly whitened key would not have. Second — and this is the practical killer — enc_key and mac_key above are adjacent, correlated slices of the same underlying integer. They are not independent in any provable sense; a proof of AES-GCM's security assumes the encryption key and any auxiliary key material behave as independent uniform random strings. Slicing doesn't give you that guarantee — it gives you two windows into one number, which is exactly the "key separation is not real" mistake behind several of the real incidents in §11.

THE NUMBERS THAT MATTER

Random AES-256 key: 256 bits of entropy, ~1077 candidates — infeasible by any attacker on Earth. 8-character lowercase password used as a key directly: ~37.6 bits, 2.09×10^11 candidates — 9.5 seconds on a single GPU with zero stretching. The entire discipline of this chapter is closing a gap measured not in percentages but in orders of magnitude.

ARC 05 · BETTER SOLUTION

Extract, then expand: turning one lumpy secret into many clean ones

Start with the DH-shared-secret half of the problem, because it has the cleaner fix. You have one high-entropy-but-structured input. You need several fixed-length, independent-looking outputs. Two separate sub-problems, solved in two separate stages:

  • Extract: concentrate whatever entropy the input has into a fixed-size, uniformly-distributed pseudorandom block — call it the PRK (pseudorandom key). This step erases the group-element structure from §4: the output of a good PRF looks nothing like its input.
  • Expand: stretch that one PRK into as many labeled, independent output blocks as the protocol needs — an encryption key, a MAC key, an IV — by hashing the PRK together with a distinct, public "info" label per output. Different label in, unrelated-looking bytes out, from the *same* PRK.

This is exactly HKDF's shape (RFC 5869, Krawczyk & Eronen, 2010), and the primitive underneath both stages is one you already built in chapter 6: HMAC. HKDF adds no new cryptographic assumption — it is a specific, carefully-argued way of calling HMAC twice that gets you extraction and expansion for free from a primitive you already trust.

Now the password half. Extraction alone does not help here — HMAC is fast, and "fast" is precisely the property you do not want when the input might be one of only a few million likely candidates. What the password case needs is not a smarter shape, but a deliberately slow one: iterate a PRF thousands or millions of times (PBKDF2), or force every single guess to allocate a large block of memory (Argon2). Same underlying tool — HMAC — pointed at a completely different design goal. §7 assembles both halves into one architecture.

THE ONE-SENTENCE VERSION

HKDF makes a high-entropy secret go further (one input, many clean outputs) without making it slower to derive — because it doesn't need to be slower, the input already has enough entropy. PBKDF2 and Argon2 make a low-entropy secret harder to guess by making each guess expensive — because entropy is exactly what's missing there, and expense is the only lever left.

ARC 06 · WHY THAT STILL COSTS

"Iterate HMAC a lot" is a cost function a GPU laughs at

PBKDF2 (RFC 2898 / PKCS #5 v2.0, Kaliski, 2000) is the obvious first cut at key stretching: run HMAC-SHA256 c times instead of once, chaining the output back in as input. Raise c, raise the attacker's cost — in theory. In practice, PBKDF2 has a structural weakness that has nothing to do with the iteration count: each iteration needs almost no memory. A single HMAC-SHA256 compression fits comfortably in a GPU thread's registers. That means an attacker doesn't run one guess at a time — they run tens of thousands of guesses in parallel, one per GPU core, limited only by arithmetic throughput, not by how much RAM the chip has.

The real numbers, from a published hashcat v6.2.6 benchmark on a single RTX 4090 (full citation and methodology in §10): raw SHA-256 runs at ~22 billion hashes/second; PBKDF2-HMAC-SHA256 at 999 iterations runs at ~8.87 million derivations/second. That ratio (~2,480×) is almost exactly what you'd predict from the iteration count alone — PBKDF2's cost is linear in c, and a GPU pays that linear cost in parallel across thousands of independent lanes simultaneously. Even at OWASP's 2023-recommended 600,000 iterations, the same single GPU still manages roughly 14,500 guesses/second — enough to exhaust the entire 8-character lowercase keyspace from §4 in about 167 days alone, or under 21 days with a modest 8-GPU rig. That is not "safe," it's "slower than it used to be."

THE STRUCTURAL PROBLEM, NAMED

PBKDF2's cost knob (iteration count) scales attacker cost linearly, and GPUs/ASICs defeat linear cost scaling with parallelism — build more lanes, pay the linear cost on all of them at once, for close to the price of one. A cost function that resists this needs a knob that parallelism cannot cheapen. The obvious candidate: make each single guess require a resource GPUs have comparatively little of per core — memory. That's Argon2's entire thesis, and §7 puts it in the architecture; §8(d) shows the mechanism.

THE RULE THAT TIES THE WHOLE PIPELINE TOGETHER

High-entropy secrets (DH output, a KMS master key) go straight into HKDF — stretching them would waste CPU without adding security, since there's no missing entropy to compensate for. Low-entropy secrets (passwords) go through a stretching function first; its output is high-entropy-looking (fixed-size, PRF-produced) and can itself be fed into HKDF if you need multiple sub-keys from one password. The two stages compose; they are never a substitute for each other. §11 shows what happens when a system uses the wrong one, or skips the stretch entirely.

(a) HMAC-SHA256: the byte layout, block by block

HMAC (RFC 2104, and chapter 6's construction) needs the key padded or hashed to exactly one SHA-256 block — 64 bytes — then XORed with two fixed constants, 0x36 (inner pad) and 0x5c (outer pad), before each of two SHA-256 calls. Step through it on a real 12-byte key:

(b) HKDF: extract, then expand — verified against RFC 5869 Test Case 1

HKDF-Extract is easy to misread: the salt is the HMAC key, and the input keying material (IKM) is the HMAC message — backwards from how you'd probably guess. HKDF-Expand then chains: each output block T(i) is HMAC(PRK, T(i-1) || info || i), with i a single counter byte, and T(0) defined as empty. (d) Argon2id: the memory-hard alternative

Argon2 (Biryukov, Dinu, Khovratovich — Password Hashing Competition winner, fully specified in RFC 9106) attacks PBKDF2's weakness directly: instead of one small HMAC state carried through c iterations, Argon2 allocates a matrix of m KiB of memory, split into 1 KiB blocks, and fills it sequentially with a compression function G built on BLAKE2b. Each block depends on the previous block and on one or more earlier blocks chosen by an address that is itself derived from already-computed data — the data-dependent addressing that Argon2d and the "d" half of Argon2id use. This is the crucial design choice: an attacker who tries to save memory by not storing an earlier block discovers they don't know, ahead of time, which blocks they'll need to recompute — the address depends on data they'd have to have already computed. Argon2id runs one data-independent pass (resistant to certain cache-timing side channels, matters for shared cloud hosts) followed by data-dependent passes, and is the profile RFC 9106 and OWASP recommend for password hashing specifically because it hedges both threat models.

WHY THIS BEATS PBKDF2 EVEN AT "THE SAME CPU TIME"

Configure PBKDF2 and Argon2id to both take, say, 200 ms on your login server's CPU. PBKDF2's 200 ms uses a few hundred bytes of RAM per guess — a GPU with 24 GB of VRAM can run millions of guesses concurrently, each taking its own turn on shared ALUs. Argon2id's 200 ms, at a real 64 MiB memory parameter, ties up 64 MiB for the full 200 ms of every single guess — the same 24 GB VRAM now fits well under 400 concurrent guesses, and VRAM bandwidth (not ALU throughput) becomes the bottleneck. Same CPU-side cost, radically different GPU-side cost. §10 turns this into an exact number.

ARC 11 · REAL-WORLD INCIDENTS

Three ways production systems got key derivation wrong

Incident 1: LinkedIn, 2012 — no KDF at all

LinkedIn stored password hashes as unsalted SHA-1 — a single fast hash, no iteration, no salt, not even the weakest form of stretching. When roughly 6.5 million hashes leaked, crackers built a rainbow table once and matched it against every hash simultaneously; because there was no salt, one precomputed table cracked every account that shared a password, and because SHA-1 is fast, the remainder fell to straight GPU brute force within days. This is the baseline failure this whole chapter exists to prevent: not "PBKDF2 with too few iterations," but skipping the concept of a KDF entirely and using a message-digest function where a cost function belonged.

Incident 2: Ashley Madison, 2015 — a correct KDF undermined by a legacy shortcut

Ashley Madison's primary password store used bcrypt with a reasonable cost factor — by itself, a defensible choice. The breach also exposed a legacy field, $loginkey, computed as MD5(lowercase(username) : password) and left over from an older authentication system that was never fully decommissioned. MD5 has none of bcrypt's cost; researchers (the "CynoSure Prime" group) cracked the MD5 tokens by brute force in bulk, recovered plaintext passwords from them, and then simply verified each recovered password against the correctly-configured bcrypt hash — ultimately recovering upwards of 11 million passwords that bcrypt, used alone, would have kept safe for centuries. The lesson generalizes past this one breach: a strong KDF protects you only if every path to the same secret is equally strong — one weak legacy shortcut anywhere in the system is a full bypass of a correctly-configured KDF everywhere else.

Incident 3: LastPass, 2022 — correct algorithm, stale cost parameter

LastPass's 2022 breach exfiltrated encrypted customer vault backups — data protected by a master password run through PBKDF2-HMAC-SHA256, the right algorithm family for this chapter's lessons. The operational failure was the iteration count: LastPass's own security disclosures and outside researchers established that newer accounts used a much higher default (100,100 iterations) than older accounts, some of which had been created years earlier under defaults as low as a few thousand iterations and were never migrated forward. Exactly as §6 and §10 quantify, a fixed iteration count is only ever "safe against the hardware that existed when it was chosen" — accounts frozen at a stale, low iteration count were offline-crackable at GPU speed years later, while newer accounts at the current default were not. The fix isn't a bigger number; it's a versioned cost parameter that gets bumped forward over an account's lifetime, which §12 and §13 both return to.

HKDF-Extract and HKDF-Expand, as specified in RFC 5869 — this is close to a direct transcription, and matches the JS running in §8(b):

pseudocodeRFC 5869 §2.2–2.3 — Extract and Expand
// §2.2 HKDF-Extract(salt, IKM) -> PRK
function hkdfExtract(salt, IKM):
    if salt is not_provided:
        salt = zeros(HashLen)          // RFC 5869 §2.2: absent salt = zero-filled
    return HMAC-Hash(key=salt, message=IKM)   // note: salt is the KEY argument

// §2.3 HKDF-Expand(PRK, info, L) -> OKM
function hkdfExpand(PRK, info, L):
    N = ceil(L / HashLen)
    T = ""                            // T(0) = empty string
    for i in 1..N:
        T = HMAC-Hash(key=PRK, message=T || info || byte(i))
        okm_blocks.append(T)
    return concat(okm_blocks)[:L]     // truncate to exactly L bytes

PBKDF2, shaped as OpenSSL's PKCS5_PBKDF2_HMAC actually implements it — an outer loop over output blocks, an inner loop over iterations, XOR-accumulated:

Cp5_crpt2.c — PKCS5_PBKDF2_HMAC(), simplified but structurally faithful
int PKCS5_PBKDF2_HMAC(const char *pass, int passlen,
                      const unsigned char *salt, int saltlen,
                      int iter, const EVP_MD *digest,
                      int keylen, unsigned char *out)
{
    HMAC_CTX *hctx = HMAC_CTX_new();
    HMAC_Init_ex(hctx, pass, passlen, digest, NULL);   /* key the HMAC ONCE, reuse the ctx */

    for (i = 1; keylen > 0; i++, keylen -= mdlen) {
        /* U1 = HMAC(P, S || INT32BE(i)) */
        HMAC_CTX_copy(ctx_i, hctx);
        HMAC_Update(ctx_i, salt, saltlen);
        HMAC_Update(ctx_i, itmp /* big-endian i */, 4);
        HMAC_Final(ctx_i, digtmp, NULL);
        memcpy(out_block, digtmp, mdlen);

        for (j = 1; j < iter; j++) {          /* THIS loop is the entire cost knob */
            HMAC_CTX_copy(ctx_i, hctx);
            HMAC_Update(ctx_i, digtmp, mdlen);   /* U(j) = HMAC(P, U(j-1)) */
            HMAC_Final(ctx_i, digtmp, NULL);
            for (k = 0; k < mdlen; k++)
                out_block[k] ^= digtmp[k];             /* XOR-accumulate into T */
        }
        memcpy(out, out_block, min(keylen, mdlen));
    }
}

Argon2's fill loop, shaped as libsodium's argon2-core.c — the part that actually creates the memory-hardness:

Cargon2-core.c — fill_memory_blocks(), simplified but structurally faithful
void fill_memory_blocks(argon2_instance_t *instance) {
    /* memory is ONE flat array of m_cost 1 KiB blocks, laid out
     * as lanes x slices x segments — allocated once, up front.  */
    for (pass = 0; pass < instance->passes; pass++) {
        for (slice = 0; slice < ARGON2_SYNC_POINTS; slice++) {
            for (lane = 0; lane < instance->lanes; lane++) {
                fill_segment(instance, pass, lane, slice);
            }
        }
    }
}

static void fill_segment(instance, pass, lane, slice) {
    for (each block_index in segment) {
        /* Argon2i portion (or the first half-pass of Argon2id):
         * the reference index is a function of (pass, lane, slice,
         * counter) — PUBLIC information, computable in advance.  */
        /* Argon2d portion (rest of Argon2id): the reference index
         * is derived from the CONTENTS of an already-computed
         * block — an attacker cannot precompute which blocks to
         * skip without already having computed them.             */
        ref_block  = resolve_reference(instance, pass, lane, slice, block_index);
        prev_block = memory[prev_index(lane, block_index)];
        /* G is BLAKE2b's compression function, reused here as
         * Argon2's block-mixing primitive.                        */
        memory[cur_index] = G(prev_block, ref_block);
    }
}
WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. HKDF splits into two named halves instead of one monolithic function, because the two halves have genuinely different jobs (concentrate entropy vs. label-expand it) — the split is documented in the API, not just the internals, so callers who only need Extract (e.g. to feed a password-derived key into further processing) aren't forced through Expand. 2. PBKDF2 keys the HMAC context once and clones it per iteration rather than re-deriving the padded key every round — a real performance detail that matters at 600,000 iterations, and a reminder that "the cost function" and "an efficiently-implemented cost function" are different engineering problems. 3. Argon2's memory layout is one flat array with a computed indexing scheme, not a tree of allocations — because the entire point is forcing an attacker to hold the whole thing resident at once; any implementation that let the OS page parts of it out on demand would silently defeat the memory-hardness guarantee the algorithm exists to provide.
