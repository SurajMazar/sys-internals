BEGINNER TIER

Ownership:
The Core Idea

Chapter 3 gave you variables and types that live entirely on the stack, where the compiler always knows exactly how many bytes to reserve and reclaim. This chapter is about the moment that stops being true — a String typed by a user, a Vec that grows as data arrives — and memory has to live on the heap, where nothing frees itself. Rust's answer is ownership: three rules, checked entirely before your program runs, that make an entire class of memory bugs impossible to compile.

You will be able toState Rust's three ownership rules from memory and predict, for any assignment or call, whether it moves or copies.
You will understandWhy String/Vec/Box move on assignment while i32/bool/char copy — and what "does not implement Copy" means to the compiler.

ARC 01 · THE PROBLEM

Every byte of memory needs exactly one boss

Every running program allocates memory it doesn't know the size of in advance — a string typed by a user, a list downloaded from a server, a buffer read from a file. Chapter 3's scalar and compound types never have this problem: an i32 is always 4 bytes, a (bool, char) tuple is always a fixed size, and the compiler reserves and reclaims that space on the stack automatically just by tracking which function call you're inside. The moment a value's size isn't known until runtime, it has to live somewhere else — the heap — and the heap does not clean up after itself. Something, somewhere, has to call the moral equivalent of "I'm done with this" exactly once per allocation.

Unpack "exactly once" and you get the whole design problem in one sentence:

  • Too few frees is a leak. Memory nobody ever releases accumulates until the process is killed for using too much.
  • Too many frees on the same allocation is a double-free — undefined behavior, and (§4 quantifies this) a genuinely dangerous one.
  • Using memory after it's freed is a use-after-free — reading or writing bytes the allocator now considers available for something else entirely.
  • Nobody should have to remember by hand. Real programs allocate thousands of times per second; a rule that depends on every programmer never making a mistake, forever, does not scale.

Two answers to "who calls free, and when?" predate Rust by decades. Manual management (C, C++) makes the programmer decide, with the compiler providing no safety net at all — §3 and §4 show exactly how that goes wrong. Garbage collection (Java, Go, Python, JavaScript) makes a runtime component decide, periodically scanning memory for anything nothing points to anymore and freeing it — which works, but costs CPU cycles, extra memory for bookkeeping, and unpredictable pause times exactly when you don't want them (chapter 1 covered this tradeoff at the language-design level). Rust takes a third path: bake the answer into the type system itself, so the compiler can decide who owns what and when it dies without running anything at all, and without trusting the programmer to remember. That mechanism is ownership, and this chapter derives its three rules from first principles.

WHY THIS MATTERS FOR THE NEXT 18 CHAPTERS

Ownership is not one Rust feature among many — it is the foundation everything else in this course stands on. Chapter 5's borrowing rules exist because ownership alone is too restrictive to write real programs with. Chapter 9's lifetimes are the compiler proving a borrow never outlives the owner it points into. Chapter 12's smart pointers (Rc, RefCell) exist to relax ownership's single-owner rule in controlled, explicit ways. Chapter 15's Send/Sync traits — the rules that let data cross threads safely — are ownership's guarantees extended across concurrency. Learn these three rules solidly now; every later chapter assumes you can recite them without looking them up.

ARC 02 · HISTORICAL CONTEXT

Ownership is older than Rust: from linear logic to a systems language

Ownership looks novel to most programmers meeting it for the first time, but the idea that a value can be "used up" rather than freely duplicated has a three-decade paper trail in academic type theory, plus one language Rust's own creator names as a direct ancestor. Click through the timeline.

DEEP CONTEXT · WHY "AFFINE," NOT "LINEAR"

Type theorists distinguish linear types (a value must be used exactly once — using it zero times is also forbidden) from affine types (a value may be used at most once — using it zero times, i.e. silently dropping it, is fine). Rust's ownership is affine, not linear: you are never forced to read a String before it goes out of scope, you're only forbidden from reading it twice once it's moved or from forgetting to eventually drop it (that part is automatic, not your job). This precise distinction is why academic papers on Rust's type system call it an affine type system, and it's also why "forgetting" a value on purpose — std::mem::forget, covered in §13 — is a safe (if unusual) operation: skipping a use is always allowed for an affine value.

ARC 03 · NAIVE SOLUTION

Attempt #1: whoever calls free() last wins (or loses)

Derive the problem honestly by writing the naive version first. In C, a pointer is just an address — nothing in the language tracks who is "responsible" for an allocation, or how many pointers currently alias it. The simplest possible program demonstrates exactly what goes wrong:

Cdouble_free.c — compiles cleanly, fails at runtime
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *a = malloc(6);      /* one allocation: 6 bytes on the heap   */
    strcpy(a, "hi!");

    char *b = a;               /* b now points at the SAME allocation —  */
                                /* nothing in C tracks that a and b alias */

    free(a);                   /* "a is done with it"                    */
    /* ... a hundred lines of unrelated code could sit here ...          */
    free(b);                   /* "b is done with it" — but it's the     */
                                /* SAME memory, freed a second time       */
    return 0;
}

This compiles without a single warning under gcc -Wall -Wextra: aliasing a pointer and freeing it twice through two different names is completely legal C syntax. The bug isn't a typo — it's the natural result of a pointer being just a number with no attached notion of "who owns this." Watch what actually happens to the heap, step by step:

Note what this "attempt" is not: it isn't a strawman for careless programmers. Two data structures legitimately holding a pointer to the same buffer — a cache and the object it cached, a parent and a child that both think they own a shared resource — is an ordinary, easy-to-reach-for design. The bug is temporal: it doesn't require both frees on adjacent lines, only that both code paths eventually run, possibly separated by thousands of lines and several function calls.

ARC 04 · WHY IT FAILS

Double-free and use-after-free are not edge cases — they're a top-tier bug class

MITRE's Common Weakness Enumeration catalogue gives this bug its own numbers precisely because it recurs so often across so much software: CWE-415 (Double Free) and its sibling CWE-416 (Use After Free) are both perennial entries on MITRE's annually published "CWE Top 25 Most Dangerous Software Weaknesses" list. Security teams at Microsoft and the Chromium project have independently reported, in public talks and blog posts, that roughly 70% of the security patches they ship for their large C/C++ codebases fix a memory- safety bug — and use-after-free/double-free are consistently among the most common shapes within that 70%.

Why is this specific bug worse than "the program crashes"? Because of exactly how a real allocator implements free(). glibc's allocator doesn't erase freed memory — it writes its own bookkeeping (a pointer to the next free chunk) into the very first bytes of the block you just handed back, so it can find it again next time you call malloc(). A double-free means that bookkeeping gets corrupted or, worse, an attacker who controls the freed bytes' contents gets to overwrite that internal free-list pointer — a technique with its own name, tcache poisoning, capable of tricking a future malloc() call into returning a pointer to memory the attacker chose. This is not a hypothetical: it's a standard technique in CTF exploitation and real-world exploit chains against C and C++ software.

WHAT YOU'D ACTUALLY SEE

Run double_free.c from §3 on a modern Linux system and glibc's allocator, which does perform some sanity checks, typically catches it and aborts rather than silently corrupting memory:

free(): double free detected in tcache 2
Aborted (core dumped)

That crash is the friendly outcome. glibc added this detection, and later a mitigation called "safe linking" (obscuring the free-list pointer so it can't be trivially forged, shipped in glibc 2.32, 2020), specifically because double-frees were being weaponized so routinely that the allocator itself needed defenses. That's an admission worth sitting with: the C ecosystem's fix for this bug class is a patch to the memory allocator, applied industry-wide, decades after the bug class was first understood. §11 revisits what happens when a language removes the bug class instead of hardening the allocator around it.

So the requirement is now precise: whatever replaces "the programmer remembers to call free() exactly once" must make it impossible to compile a program with two owners of the same allocation — not merely unlikely, not merely caught by a sanitizer at runtime, but rejected before the program exists as a binary at all.

ARC 05 · THE THREE RULES, DERIVED

Give every allocation exactly one boss, enforced before the program ever runs

Derive it forward. If the compiler tracked, for every value, precisely one variable currently allowed to free it — and refused to compile any program where that stops being true — the double-free class from §3 becomes a compile error instead of a 2 a.m. page. Step through how Rust builds exactly that.

Deriving ownership, one rule at a timeSTEP-BY-STEP

Written out plainly, those are Rust's three ownership rules — memorize these, they are the load-bearing fact of this entire course:

  • Rule 1 — single owner. Every value in Rust has exactly one variable that owns it at any given moment: the binding currently allowed to use, mutate, and eventually free it.
  • Rule 2 — dropped at scope end. When the owner goes out of scope, Rust automatically runs drop on the value — no matching free() call for you to remember, ever, for any type.
  • Rule 3 — ownership moves. Assigning a value to a new variable, passing it to a function by value, or returning it transfers ownership to the new binding. The old binding becomes permanently unusable — not "unusable by convention," but rejected by the compiler if you try.
THE PART THAT SURPRISES BEGINNERS MOST

All three rules are enforced entirely at compile time. There is no runtime "is this still valid?" check inserted into your binary, no reference count incremented and decremented on every assignment (that's a different mechanism — Rc/Arc, chapter 12 — which you opt into explicitly, not the default). The compiler does the bookkeeping once, while compiling, and by the time you have a binary, the concept of "ownership" has entirely evaporated into either nothing or a plain memcpy of a few bytes. §10 makes this claim precise and checkable.

ARC 06 · WHY THAT STILL HURTS

The bill: verbosity, an overused .clone(), and bugs ownership doesn't touch

Be honest about the costs, because you will feel every one of them in your first weeks of Rust:

  • Fighting the borrow checker is a real phase. Code that is obviously safe to a human — "I'm not using s1 anymore, why won't this compile?" — can still be rejected until you've internalized move semantics and, starting next chapter, borrowing. This friction is real and it front-loads onto week one specifically because ownership is the first thing you learn.
  • .clone() becomes a hammer. Beginners reach for .clone() to silence a compiler error even in places a borrow (chapter 5) would have worked for free — which means you can write correct, safe Rust today that is quietly doing more heap allocation than it needs to, purely because you haven't met references yet.
  • Moves aren't always free. A move is only a cheap 24-byte copy (§8 shows exactly why) for heap-backed types like String and Vec, whose actual data stays put on the heap. A large stack-only value — a big array, a struct full of fixed-size fields — genuinely copies every byte on a move, because there's no heap indirection to leave alone. The optimizer often elides this, but "ownership transfer is free" is not a universal law; it's a property of the specific types you reach for most (chapter 20 teaches you to measure instead of assume).
  • Ownership doesn't prevent leaks. A cycle of Rc handles (chapter 12) can keep memory alive forever, because each one thinks someone else will drop first. Rust's safety guarantee is precisely "no use-after-free, no double-free, no data races" — it was never "no leaks." Leaking memory by never freeing it is, by that definition, memory-safe, which surprises people who hear "safe" and assume it means "leak-free."
  • Ownership alone is not enough to write comfortable code. A function that only needs to read one field of a String shouldn't have to take ownership of the whole thing and prevent the caller from using it again — but with only the three rules in this chapter, that's exactly what happens every time you pass anything heap-backed to a function. That gap is real, and it's precisely why chapter 5 exists immediately next: borrowing lets code look at a value without becoming its owner.

ARC 08 · UNDER THE HOOD

What a move actually does to bits in memory

"Ownership moves" is a compile-time concept — but concretely, something has to happen to real bytes when you write let s2 = s1;. Step through String's actual representation to see it.

A move, byte by byteSTEP-BY-STEP

A String is not "the characters" — on the stack, it is exactly three machine words: a pointer to the heap buffer, a length, and a capacity (24 bytes total on a 64-bit target). Moving a String means copying those 24 bytes into the new binding; the heap buffer they point at is never touched, never reallocated, never even read. That's true whether the string holds three characters or three gigabytes. Confirm it by picking a type below:

HOW THE COMPILER ACTUALLY KNOWS S1 WAS MOVED

Under the hood, rustc runs a dataflow analysis over your function: at every point in the code, for every place a value could live, it tracks whether that place is currently "initialized" (has a live value the program is allowed to read or drop) or "moved-out" (its value has been relocated elsewhere, and reading it would either read garbage or read something that no longer belongs to it). A move statement flips a place from initialized to moved-out; any later read of a moved-out place is rejected before code generation ever starts — the exact mechanism §14's quiz and §15's simulator will make you compute by hand. Chapter 19 shows the real intermediate representation, MIR, that this analysis actually runs over, plus the harder version of this problem borrowing introduces: figuring out exactly which program point a borrow ends at, not just whether a value has moved.

ARC 09 · TRADEOFFS

The same problem, five ways: who decides when memory dies

Every language with heap allocation answers "who frees this, and when?" Read the spread as proof that there is no dominant strategy, only different places to pay the same underlying cost:

STRATEGYWHO DECIDES, AND WHENWHAT THEY BUYWHAT THEY PAY
C / raw C++The programmer, by hand, calling free()/delete zero runtime overhead total control double-free / use-after-free / leaks are all one typo away
Modern C++ (RAII, smart pointers)A destructor runs when an object's scope ends — the direct inspiration for Rust's Drop deterministic, automatic-ish nothing stops two smart pointers from both thinking they own the same raw pointer underneath
Java / Go / JavaScriptA tracing garbage collector, periodically, at a time it chooses no manual bookkeeping at all handles cycles unpredictable pause times extra CPU + memory for the collector itself
Swift ARC / Python (default)A hidden reference count, incremented and decremented on every copy of a handle, freed at zero mostly deterministic, no GC pause an atomic increment/decrement on nearly every copy reference cycles leak silently
RustThe compiler, once, at compile time — ownership + moves + Drop zero runtime cost double-free/use-after-free impossible in safe code a real learning curve occasional real (not accidental) clones to satisfy the checker
Region-based (Cyclone, ML Kit — historical/academic)A compiler-inferred lexical "region"; the whole region frees at once when its scope ends no GC, provably safe rigid — a value can't easily outlive the region it was inferred into

Read this table forward, not backward: Rust didn't invent "decide at compile time" — Cyclone and ML Kit did, academically, over a decade earlier (§2). What Rust did was make that decision usable enough, with a small enough set of rules, that it could ship a real systems language on top of it. Chapter 5 is the next piece of "usable enough": borrowing exists precisely because a pure single-owner model, as derived in this chapter, is too rigid to write comfortable code with — the same complaint §9's Cyclone row hints at.

ARC 10 · PERFORMANCE & SAFETY

Zero-cost isn't a slogan here — it's a claim you can check

Ownership's performance story is unusual among safety mechanisms: it costs nothing at runtime, because there is nothing left to check once compilation succeeds. Contrast the three real strategies from §9 on the one metric that matters in production — when the cost is paid:

  • Rust: the "is this move valid?" check happens once, in the compiler, on your machine, before a binary exists. The shipped program contains either nothing (many moves compile to reusing the same stack slot) or a fixed-size memcpy — never a heap traversal, never proportional to the size of the data structure being moved.
  • Reference counting (Swift/Python): pays a small cost on every copy of a handle, forever, in production, on every request — an increment (and a decrement when it's dropped), which for Arc specifically (chapter 12, 15) is an atomic operation, measurably slower than a plain increment under contention.
  • Tracing GC (Java/Go): pays in occasional, unpredictable pauses where the whole program (or a generation of it) stops while the collector walks live objects — the cost is deferred and batched, which is exactly what makes it hard to reason about for latency-sensitive code.

ARC 11 · REAL-WORLD PRODUCTION

Three times this exact idea shipped and mattered

Incident 1: Firefox's style engine rewrite (Project Quantum / Stylo)

Firefox's CSS style system — the code that decides which rules apply to which element, historically one of the gnarlier, most alias-heavy pieces of a browser engine — was rewritten from C++ into Rust as "Stylo" and shipped to all Firefox users in Firefox 57 (November 2017) as part of the Project Quantum initiative. The old C++ style system had been a recurring source of use-after-free and data-race security advisories over the years, the exact bug shapes this chapter and chapter 15 are built around. Mozilla's own public writeups about Quantum credit Rust's ownership and borrowing rules specifically for eliminating that entire recurring category of bug in the rewritten component, not merely reducing its rate.

Incident 2: Android's shifting memory-safety numbers

Google's Android security team has published, in a public 2022 security-blog report ("Memory Safe Languages in Android 13"), that the fraction of Android's total vulnerabilities attributable to memory-safety bugs fell from roughly 76% (2019) to roughly 35% (2022) as an increasing share of new Android platform code shipped in memory-safe languages — Rust chief among the newly adopted ones for low-level components. The causal claim in the report is specific and important: they didn't rewrite old C/C++ code, they simply stopped writing new code in a language where this bug class is possible, and watched the numerator shrink because new code is where new vulnerabilities are overwhelmingly found. It's the same argument as §4, run at the scale of an entire operating system's codebase.

Incident 3: glibc had to defend its own allocator against this exact bug

Section 4 already previewed this one, but it deserves to stand as a production incident in its own right: glibc — the C standard library underneath most of Linux — shipped a dedicated mitigation called "safe linking" in version 2.32 (2020), specifically to make the tcache double-free/poisoning technique harder to exploit, by XOR-obscuring the free-list pointers a double-free lets an attacker read or forge. This is a multi-decade-old, extremely widely deployed allocator adding a defensive feature against a single bug class — the clearest possible admission that the ecosystem could not eliminate double-free by discipline alone, and had to fight it at the allocator layer instead. Rust's approach in this chapter — make the bug unrepresentable in the type system — sidesteps the entire arms race.

ARC 13 · SOURCE CODE WALKTHROUGH

Reading the real thing: how String and Vec actually own their memory

Ownership isn't a special-cased compiler feature bolted onto String — it's built entirely out of ordinary Rust: a struct holding data, and a Drop implementation that runs when that struct's owner goes out of scope. Here is the real shape of the standard library, simplified for space but faithful to the actual field names and layering.

library/alloc/src/
├── ● string.rs — String { vec: Vec<u8> }: owns exactly one heap buffer, indirectly
├── vec/● mod.rs — Vec<T>: the length + the raw allocation that String wraps
├── ● raw_vec.rs — RawVec<T>: the actual pointer + capacity, one layer down
└── vec/mod.rs (same file) — the Drop impl that frees the buffer
library/core/src/
├── mem/● mod.rs — mem::drop(): "drop early," implemented with zero special-cased compiler magic
└── ops/drop.rs — trait Drop { fn drop(&mut self); } — the hook this whole chapter builds on

The layering, outside in — a String is a thin wrapper around a Vec<u8> that guarantees its bytes are valid UTF-8; it doesn't manage memory itself at all:

RUSTlibrary/alloc/src/string.rs — simplified
pub struct String {
    vec: Vec<u8>,
}
// String owns nothing directly — it owns a Vec<u8>, and the Vec
// owns the actual allocation. Ownership composes: if you own a
// struct, you own everything reachable through its fields.
RUSTlibrary/alloc/src/vec/mod.rs — simplified
pub struct Vec<T, A: Allocator = Global> {
    buf: RawVec<T, A>,
    len: usize,
}
// Vec doesn't hold the raw pointer itself either — that's one more
// layer down, in RawVec. Vec just adds "len": how many of the
// allocated slots currently hold a live, initialized T.
RUSTlibrary/alloc/src/raw_vec.rs — simplified
struct RawVec<T, A: Allocator = Global> {
    ptr: Unique<T>,   // the actual heap pointer
    cap: usize,        // how many T's worth of space is allocated
    alloc: A,          // which allocator provided it (Global, by default)
}
// This is the bottom of the stack: ptr + cap. Add Vec's "len" on
// top and you have the pointer + length + capacity trio §8 showed
// moving as a flat 24-byte copy on 64-bit targets.

And the other half of ownership — not creating the value, but destroying it. Here is (a simplified shape of) the real Drop implementation that runs automatically when a Vec's owner goes out of scope:

RUSTlibrary/alloc/src/vec/mod.rs — Drop impl, simplified
unsafe impl<#[may_dangle] T, A: Allocator> Drop for Vec<T, A> {
    fn drop(&mut self) {
        unsafe {
            // First: run every live element's own Drop, if it has one.
            ptr::drop_in_place(self.as_mut_slice());
        }
        // Then RawVec's own Drop impl (not shown) deallocates the
        // buffer itself. Two separate Drop impls, one per layer —
        // exactly like String owning a Vec owning a RawVec.
    }
}

Finally, one small, elegant consequence of Rule 2 you'll use constantly once you meet borrowing: dropping a value early, on purpose, needs no special syntax at all — it's implemented as an ordinary function with an empty body:

RUSTlibrary/core/src/mem/mod.rs — simplified
pub fn drop<T>(_x: T) {}
// Calling mem::drop(v) just MOVES v into this function by value.
// The instant this function's body finishes — which is immediately,
// since the body is empty — its parameter goes out of scope, and
// Rule 2 fires right there. No compiler magic: this is Rule 3 (move
// into a function) and Rule 2 (drop at scope end) composed to build
// a "drop this right now" tool out of ordinary code.
