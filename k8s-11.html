Storage Internals:
PV, PVC & the CSI Boundary

Chapter 4 warned you that emptyDir and hostPath volumes vanish the moment a Pod is rescheduled. This chapter builds the machinery that fixes that: a supply-and-demand model (PersistentVolume/PersistentVolumeClaim) for matching storage to workloads, a plugin boundary (the Container Storage Interface) that lets any vendor's storage system plug into any container orchestrator without either side touching the other's source code, and the exact sequence of gRPC calls that provisions, attaches, and mounts a disk before your container's first write() ever succeeds.

ARC 01 · THE PROBLEM

Containers are disposable. Data, usually, cannot be.

A container's writable layer is deliberately ephemeral — an overlay filesystem's top copy-on-write layer that the kubelet and the OCI runtime discard the moment the container is removed (the Container Internals course covers exactly how that layer is constructed; this chapter starts one level up, at the boundary where Kubernetes decides what gets mounted into a Pod in the first place). That design is correct for the container itself — you want a fresh, byte-identical filesystem every time an image runs — but it means that anything an application needs to survive a restart, a reschedule, or a rolling update has to live somewhere that is not the container's own filesystem.

Kubernetes' answer has to satisfy five requirements simultaneously, and each one rules out an easy shortcut:

  • Durability beyond the Pod. A Pod is not a unit of identity — it is disposable and gets replaced routinely. Storage that matters must outlive the specific Pod object that first attached it.
  • Node independence. The replacement Pod usually lands on a different node. Storage must be reachable from wherever the scheduler puts the next Pod, not just the node it started on.
  • Vendor plurality. A cluster might sit on AWS EBS, GCE Persistent Disk, Azure Disk, a bare-metal Ceph cluster, an NFS export, or a vendor-specific array — and Kubernetes cannot ship first-party code for every storage system that will ever exist.
  • Decoupling request from implementation. An application developer writing a Deployment manifest should be able to say "give me 20Gi, fast, exclusive to one Pod" without knowing or caring whether that becomes an EBS gp3 volume or a Ceph RBD image.
  • Provisioning at scale. A platform team supporting hundreds of teams cannot have a human create a cloud disk by hand for every claim — provisioning has to be an API call a controller can make.

Kubernetes' answer is a two-object supply/demand model — PersistentVolume as supply and PersistentVolumeClaim as demand — plus a plugin boundary, the Container Storage Interface (CSI), that lets the actual attach/mount work happen in code Kubernetes never has to compile. Everything in this chapter derives from making that boundary real: what crosses it, in what order, and what happens when either side lies.

WHERE THIS SITS RELATIVE TO WHAT YOU'VE SEEN

Chapter 6 told you the API server is the only thing anything talks to and that etcd is the only stateful component of the control plane. This chapter is about state outside the control plane — your application's data — which the control plane never stores, only describes and orchestrates. A PersistentVolume object in etcd is a few hundred bytes of metadata; the actual 20Gi disk it describes lives entirely outside Kubernetes, on infrastructure Kubernetes only ever talks to through the CSI plugin boundary.

DEEP CONTEXT · WHY "IN-TREE" WAS A PROBLEM AT ALL

Early Kubernetes shipped volume plugins for AWS, GCE, Azure, Ceph RBD, NFS, and more directly inside k8s.io/kubernetes. That meant: a bug fix in the vendor's disk-attach logic required a Kubernetes PR, a Kubernetes review, and a Kubernetes release — and every cluster operator had to upgrade the entire control plane to get a storage driver fix. Worse, a panic inside one vendor's plugin code ran in the kubelet process itself, so a storage bug could crash the node agent responsible for every Pod on that node. CSI's entire reason for existing is to move that code out of Kubernetes' address space and release cycle entirely.

ARC 03 · NAIVE SOLUTION

Attempt #1: an operator with a runbook and a cloud CLI

Before judging the real design, build the strawman honestly. Without PV/PVC/CSI, "persistent storage for Kubernetes" is a human following a runbook:

bashprovision-by-hand.sh — the strawman, annotated
# Run manually, once, by whoever is on call when a new app needs a disk.
aws ec2 create-volume --size 20 --availability-zone us-east-1a \
    --volume-type gp3 --tag-specifications 'ResourceType=volume,Tags=[{Key=app,Value=orders}]'
# ^ hope you remembered the SAME zone the app's node lives in — nothing checks this

aws ec2 attach-volume --volume-id vol-0abc123 --instance-id i-0def456 --device /dev/xvdf
ssh node-7 'sudo mkfs.ext4 /dev/xvdf && sudo mkdir -p /mnt/orders-data && sudo mount /dev/xvdf /mnt/orders-data'

# Now hand-edit the Pod spec to hardcode a hostPath AND a nodeSelector pinning it to node-7 forever:
volumes:
  - name: data
    hostPath: { path: /mnt/orders-data }
nodeSelector:
  kubernetes.io/hostname: node-7   # the Pod can never move again

This "works" for exactly one app, on one node, provisioned by exactly one careful human — and it already reveals every requirement from §1 by violating it: the Pod is now welded to node-7, nothing records that vol-0abc123 exists or which app owns it, and the next app needs the entire runbook re-run by hand with a new volume ID, a new device path, and a new hardcoded node name.

ARC 04 · WHY IT FAILS

The math of manual provisioning collapses long before 100 apps

Quantify what the runbook costs as the fleet grows, using numbers a platform team would actually see:

  • Node pinning destroys self-healing. Chapter 2 taught you a ReplicaSet reschedules a dead Pod anywhere capacity exists. A hardcoded nodeSelector reduces "anywhere" to "exactly one node" — if node-7 dies, the app has zero eligible nodes and stays Pending forever, capacity elsewhere or not.
  • Orphaned volumes are pure waste, and it compounds. Nobody's script deletes the cloud disk when the app is decommissioned — deleting compute is a habit; deleting the volume it never officially "belonged" to is not. At a modest gp3 rate of ~$0.08/GB-month, 300 orphaned 100Gi volumes left behind over a year is ~$2,400/month in disks nobody is reading from, discovered only during a cost audit.
  • Zone mismatches are silent until attach time. EBS volumes and the instances that attach them must share an availability zone. Nothing in the runbook enforces this — the failure surfaces as an opaque attach-volume API error, at 2am, after the disk and the app are both already "done."
  • Concurrent runs race. Two engineers responding to two tickets simultaneously can create two volumes for the same logical app, attach one each to two different nodes, and now the "second" deploy silently writes to a different disk than the "first" — a split-brain bug with no error message anywhere.
  • There is no reconciliation. If someone manually detaches a volume to debug it and forgets to reattach it, nothing notices. Compare this to chapter 9's controllers, which continuously re-diff desired vs. observed state — the runbook has no analogous loop; drift is permanent until a human happens to look.
THE STRUCTURAL PROBLEM, NOT JUST THE TEDIUM

The deeper failure isn't that this is manual — it's that there is no object model. Nothing in etcd records "this 20Gi disk belongs to the orders app and is currently attached to node-7." Kubernetes' scheduler, its controllers, and its API server have no way to reason about storage that isn't represented as an API object, which means none of chapter 9's reconciliation machinery can apply to it. The fix isn't a better script — it's making storage a first-class API object with a controller that reconciles it, exactly like every other resource in this course.

ARC 05 · BETTER SOLUTION

Supply and demand as API objects: PV, PVC, and the binder

Kubernetes splits the runbook into two declarative objects and a controller that matches them. Step through the model from a cluster with zero volumes to a Pod actually reading and writing its data:

Supply meets demand: PV, PVC & the binderSTEP-BY-STEP

Formally: a PersistentVolume (PV) is cluster-scoped supply — it advertises a capacity, one or more accessModes (ReadWriteOnce, ReadOnlyMany, ReadWriteMany, and the newer ReadWriteOncePod), a persistentVolumeReclaimPolicy, and the mechanics of actually reaching the storage (in modern clusters, a csi block naming a driver and a volumeHandle). A PersistentVolumeClaim (PVC) is namespaced demand — an application only ever writes a PVC, specifying size, access mode, and optionally a storageClassName. The PersistentVolume controller (the binder, part of kube-controller-manager) watches both collections and binds a claim to the smallest Available PV that satisfies it — or, if a StorageClass is named and no PV already exists, triggers dynamic provisioning instead of waiting for an admin to have pre-created one.

THE ONE ABSTRACTION THAT MAKES EVERYTHING ELSE WORK

A Pod's volume spec never mentions AWS, GCE, or Ceph — it says persistentVolumeClaim: {claimName: data-pvc}. Swap the underlying StorageClass's provisioner and every application manifest in the cluster is unchanged. That indirection — object references three layers deep (Pod → PVC → PV → CSI driver) instead of one hardcoded path — is the entire point, and it is the same "declare desired state, let a controller converge it" idiom chapter 9 taught you, applied to storage instead of replica counts.

ARC 06 · WHY THAT STILL COSTS

Dynamic provisioning solves toil — and creates a new failure mode

Static PVs (an admin pre-creates PV objects) still require exactly the manual toil §4 quantified — it just moves the toil earlier. StorageClasses fix that: a StorageClass names a provisioner (a CSI driver) and a set of driver-specific parameters, and the binder provisions a brand-new volume on demand for any PVC naming that class. That erases the admin-toil problem — but introduces a subtler one: when should provisioning happen?

The obvious answer — provision the instant the PVC is created — is the StorageClass's default volumeBindingMode: Immediate. It has a real cost: the provisioner picks a physical location (an availability zone, for cloud block storage) before the scheduler has decided which node the consuming Pod will run on. If the provisioner happens to create the disk in us-east-1a and the scheduler — driven by CPU/memory fit, affinity rules, or simple bin-packing — later prefers a node in us-east-1b, the Pod is now permanently unschedulable: the PV's nodeAffinity is fixed at creation time, block storage cannot cross zones, and no amount of retrying picks a different node because every node outside us-east-1a fails the same constraint forever. That surfaces as the specific, well-known scheduler message node(s) had volume node affinity conflict — not a transient error, a permanent one, because the thing pinning the Pod is a PersistentVolume object, not a Pod-level preference the scheduler can override on a later attempt.

THE FIX HAS A NAME, AND IT'S A ONE-LINE CHANGE

volumeBindingMode: WaitForFirstConsumer defers both binding and provisioning until a Pod that references the PVC is scheduled. The scheduler picks a node using all its normal filter/score logic (chapter 8) with no volume constraint yet, and only then does the provisioner get told which zone to provision in — topology follows the scheduling decision instead of constraining it. The cost of getting this backwards is not a performance tax like chapter 9's polling overhead; it is Pods stuck Pending indefinitely for a reason that looks, to an on-call engineer without this chapter's mental model, exactly like a capacity problem.

CSI's plugin boundary has its own bill, too: every operation — create, attach, stage, publish — is now a gRPC call across a process boundary (kubelet or a sidecar container calling into the driver's Unix domain socket) instead of an in-process function call. Each hop can time out, needs retry logic, and adds real wall-clock latency to Pod startup that a hardcoded hostPath mount never paid. §8 and §10 make that cost exact.

THE SIDECAR PATTERN, EXPLAINED IN ONE SENTENCE

Every sidecar (provisioner, attacher, resizer, snapshotter) is vendor-agnostic, open-source, and identical across every CSI driver on Earth — it watches a generic Kubernetes API object (a PVC, a VolumeAttachment, a VolumeSnapshot) and translates it into a generic CSI gRPC call over a Unix domain socket shared with the driver container in the same Pod. Only the two services behind that socket — Controller and Node — are vendor-specific. This is why a company can write a CSI driver for its storage array without ever touching Kubernetes source, and why Kubernetes never needs a line of code specific to any vendor again.

(c) StatefulSets: stable identity meets per-replica storage

A Deployment's Pods are interchangeable — orders-7d9f8b-x2k4p means nothing and can be replaced by any other replica with no observable difference. Databases and other stateful workloads need the opposite: each replica must keep the same name, the same network identity, and the same storage across every restart. StatefulSet provides all three, and none of them are optional add-ons — they come from one mechanism: ordinal indices.

yamlheadless-service + statefulset.yaml
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  clusterIP: None          # headless — no VIP, no load-balancing (contrast: chapter 3's ClusterIP)
  selector: { app: web }
  ports: [{ port: 80 }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: web }
spec:
  serviceName: web       # must name the headless Service above
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
      - name: app
        image: registry.example/app:1.4
        volumeMounts: [{ name: www, mountPath: /data }]
  volumeClaimTemplates:            # ← one PVC PER REPLICA, stamped from this template
  - metadata: { name: www }
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: fast-ssd
      resources: { requests: { storage: 10Gi } }

Watch the ordinal guarantee in action — pods and their per-replica PVCs are created strictly one at a time, in order, never in parallel like a ReplicaSet's replicas:

StatefulSet rollout: ordinals, identity, storageSTEP-BY-STEP
THREE GUARANTEES, ONE MECHANISM

Stable name: Pods are named <statefulset>-<ordinal> (web-0, web-1, web-2) — never a random suffix, and a replacement Pod for a dead web-1 is created as web-1 again, not a new identity. Stable network identity: the headless Service gives each Pod a DNS A record AND a stable per-Pod name, web-1.web.orders.svc.cluster.local, resolvable even while the Pod is being recreated. Stable storage: the PVC created from volumeClaimTemplates for ordinal 1 is named www-web-1, and a replacement web-1 Pod re-attaches that exact same PVC — not a new, empty one. All three come from the same ordinal index; there is no separate mechanism for each.

Every generation of the plugin model, priced honestly

APPROACHWHAT IT BOUGHTWHAT IT COST

Read the table the same way chapter 1 taught you to: nothing here is free, only differently priced. CSI's extra sidecar containers are the price of never coupling a storage vendor's release cycle to Kubernetes' — a trade the ecosystem judged worth making, which is why in-tree plugins are gone from the codebase entirely as of Kubernetes 1.27, years after CSI Migration made the switch transparent to existing manifests.

ARC 10 · PERFORMANCE & SECURITY

Numbers that matter before you page someone

  • Reconcile cadence: kubelet's volume manager reconciler runs on a fast, sub-second loop driven by informer events, with a periodic full resync as the safety net — the same belt-and-suspenders pattern chapter 9 showed you for every controller: fast path for the common case, an unconditional floor so a missed event can never cause permanent drift.
  • Controller concurrency is bounded on purpose. kube-controller-manager's --concurrent-volume-syncs flag defaults to a small number (5) — the PV controller, like every controller in this course, deliberately limits how many claims it processes at once so one slow provisioner call can't starve the reconcile loop for everything else.
  • Attach limits are a real, often-forgotten ceiling. Cloud block storage caps how many volumes one instance can have attached — historically as low as ~25–39 EBS volumes per Nitro-based EC2 instance, reported to the scheduler via the CSI driver's NodeGetInfo RPC as max_volumes_per_node. A node can hit its volume-attachment ceiling well before it hits the default 110-pod limit from chapter 6 — a storage-heavy StatefulSet fleet can make nodes "full" while CPU and memory sit mostly idle.
  • Every CSI call is a timeout risk. Sidecars commonly default their per-call timeout to the low-teens of seconds, retrying with backoff on failure — reasonable for one volume, but under a burst of simultaneous provisioning requests, a cloud provider's own API rate limits (not Kubernetes) become the bottleneck, and every queued request pays the same timeout-and-retry tax.

MODEL, NOT MEASUREMENT

Per-operation latency is a deliberately simple assumption — roughly the sum of one CreateVolume, one ControllerPublishVolume, one NodeStageVolume, and one NodePublishVolume call at typical cloud-API speed, about 3.4s combined when nothing is contended. Real drivers vary by an order of magnitude depending on the backend. The shape is what matters: batching by a hard concurrency limit turns a burst into stair-steps, and provider-side throttling multiplies every step, exactly the mechanism behind real "mass pod creation during a failover" incidents.

Security characteristics

The CSI node plugin is, by necessity, one of the most privileged things running on a node: performing a real mount syscall and writing into /var/lib/kubelet/plugins and /var/lib/kubelet/pods/<uid>/volumes requires host mount-namespace access and typically CAP_SYS_ADMIN (a one-sentence cross-reference to the Container Internals course's capabilities chapter is worth making here: this is precisely the capability a properly sandboxed container is supposed to lack). A compromised node-plugin container is close to equivalent to node root — which is why CSI driver manifests are one of the few workloads platform teams routinely exempt from their strictest Pod Security Standard and why RBAC on who may create or edit StorageClass objects matters: a class's provisioner and parameters are trusted, uninspected input to a privileged driver. Separately, persistentVolumeReclaimPolicy: Retain — the safe-sounding choice — has a sharp edge: a "Released" PV's underlying disk still contains the previous claimant's data, and nothing forces a wipe before a new PVC is manually bound to it. §11 covers exactly that failure pattern.

ARC 11 · REAL-WORLD PRODUCTION

Three failure modes you will eventually meet

Incident 1: The multi-attach error after a hard node failure

A node running a StatefulSet Pod with an attached EBS volume suffers a kernel panic — it doesn't shut down cleanly, it simply stops heartbeating. Kubernetes wants to reschedule the Pod elsewhere, but the AttachDetach controller cannot safely call ControllerUnpublishVolume for the old attachment: it has no confirmation from the (unreachable) kubelet that the volume is actually unmounted, and detaching a still-mounted block device out from under a wedged-but-not-dead node risks corrupting the filesystem. The new Pod's ControllerPublishVolume call then fails with the specific, well-known message Multi-Attach error for volume "pvc-..." Volume is already exclusively attached to one node and can't be attached to another. Before Kubernetes 1.28, the only fixes were waiting out a conservative cloud-provider timeout or manually deleting the old Node object. Non-graceful node shutdown handling (alpha in 1.24, GA in 1.28) gave operators an explicit, safe escape hatch: applying the node.kubernetes.io/out-of-service taint to a confirmed-dead node tells the AttachDetach controller it may force-detach immediately, because a human has now vouched for the node actually being gone.

Incident 2: CVE-2021-25741 — escaping a volume mount via subPath

Kubernetes lets a container mount just a subdirectory of a volume via subPath. CVE-2021-25741 was a symlink race: kubelet resolved the subPath target, but a malicious container could swap that path for a symlink pointing outside the volume between kubelet's check and its mount — a classic TOCTOU bug — landing a container-writable mount anywhere on the node's filesystem, including paths well outside any volume it was supposed to have access to. It was fixed in kubelet 1.19.15, 1.20.11, 1.21.5, and 1.22.2 by re-validating the resolved path immediately before the mount syscall rather than trusting an earlier check. The lesson generalizes: any code that resolves a path and later acts on it needs to re-check at the point of action, not at the point of decision — the same principle that shows up in scheduler admission logic and RBAC checks elsewhere in this course.

Incident 3: The reclaim-policy data leak

A platform team sets persistentVolumeReclaimPolicy: Retain everywhere, reasoning "safer than Delete — we'll never lose data by accident." Months later, an automation script that recycles "Released" PVs back into the available pool for new claims does exactly what it's told: it re-binds a Released PV — whose underlying disk still contains a previous tenant's database files — to a brand-new PVC, without wiping it first, because nothing in the PV/PVC API model performs that wipe for you (the old, explicitly insecure Recycle reclaim policy that once ran a generic "best-effort" scrub was removed from Kubernetes entirely for exactly this reason — it was never trustworthy). The new tenant's Pod mounts the volume and can read the old tenant's data. The fix is procedural, not a Kubernetes setting: Retain must be paired with a mandatory, verified wipe-or-snapshot-and-destroy step before any Released PV is ever made Available again — treat it as no different from decommissioning a physical disk.

func (ctrl *PersistentVolumeController) syncUnboundClaim(claim *v1.PersistentVolumeClaim) error {
    if claim.Spec.VolumeName == "" {
        // No PV requested by name — search the pool, or provision one.
        volume := ctrl.volumes.findBestMatchForClaim(claim)
        if volume == nil {
            if storageClassProvisions(claim) {
                return ctrl.provisionClaim(claim) // → annotation picked up by external-provisioner
            }
            return ctrl.updateClaimStatus(claim, v1.ClaimPending, "")
        }
        return ctrl.bind(volume, claim)
    }
    // claim.Spec.VolumeName already set — a static, pre-bound claim.
    return ctrl.syncBoundClaim(claim)
}

// pkg/kubelet/volumemanager/reconciler/reconciler.go (simplified)
func (rc *reconciler) reconcile() {
    // 1. Unmount anything in ActualStateOfWorld that's no longer desired.
    for _, vol := range rc.actualStateOfWorld.GetMountedVolumes() {
        if !rc.desiredStateOfWorld.PodExistsInVolume(vol.PodName, vol.VolumeName) {
            rc.operationExecutor.UnmountVolume(vol, rc.actualStateOfWorld) // → NodeUnpublishVolume
        }
    }
    // 2. Mount anything desired that isn't mounted yet.
    for _, v := range rc.desiredStateOfWorld.GetVolumesToMount() {
        if !rc.actualStateOfWorld.PodExistsInVolume(v.PodName, v.VolumeName) {
            rc.operationExecutor.MountVolume(v, rc.actualStateOfWorld) // → NodeStageVolume + NodePublishVolume
        }
    }
}

WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Every reconciler is desired-state-vs-actual-state, always. Chapter 9's controllers, the kubelet volume manager, and the AttachDetach controller are three independent implementations of the exact same idiom — because "diff two sets, converge" is easier to prove correct than tracking every individual mutation event. 2. The gRPC boundary must be idempotent by spec. The CSI spec mandates that calling CreateVolume twice with the same name and parameters must return the same volume, not create a second one — because a network partition between a sidecar and the driver means "did that call actually succeed?" is often unknowable, and retries must be safe by construction, not by luck. 3. Sidecars watch generic objects, never driver internals. external-provisioner only ever looks at a PVC's fields — it has zero knowledge of AWS, GCP, or Ceph — which is exactly what makes it reusable, unmodified, across every CSI driver that has ever shipped.
