UBER ENGINEERING INTERNALS · CHAPTER 01

Genesis: The Marketplace
Matching Problem

Ride-hailing looks, from the outside, like an e-commerce checkout: pick an item, pay for it, get a confirmation. It is not. Every rider request and every driver's availability is a perishable unit of supply or demand that must be found, evaluated, and cleared against its counterpart in seconds, inside a constantly moving geography, with no central catalog to browse. This chapter derives why ride-hailing is fundamentally a real-time, two-sided, geographically-local matching problem — and why that framing, more than any single technology choice, is the reason the rest of this course's architecture looks the way it does.

ARC 01 · THE PROBLEM

Not a catalog. A market that expires every few seconds.

Picture the two most common distributed-systems teaching examples: an e-commerce checkout and a chat application. Neither one prepares you for ride-hailing, because both have a comfortable property that ride-hailing does not: the thing being requested sits still until you deal with it. A product in a warehouse waits on a shelf. A chat message waits in a mailbox. A driver three minutes from a rider is, at this exact moment, still moving, might just have accepted a different trip, and will be somewhere else by the time your query resolves.

Formally, ride-hailing is a two-sided marketplace with five properties that, together, are what make it hard:

  • Perishable supply and demand. A driver who is idle for 4 minutes represents 4 minutes of matching opportunity that no future action can recover. A rider who waits too long cancels. Neither side can be inventoried — there is no warehouse of "available driver-minutes" to draw down later.
  • Continuous motion. Both sides of the market move in physical space, independent of the matching system's decisions. A driver's position at the moment a match is proposed and at the moment it is confirmed are two different points on the map.
  • Bilateral fit, not a single price. A match is only valid if the driver can plausibly reach the rider in bounded time — a driver 40 minutes away is not a candidate, no matter how "available" they are. Distance is a hard constraint, not a soft preference.
  • Locality of clearing. A rider in downtown São Paulo can never be served by a driver idling in downtown Manila. The market must clear against a small geographically relevant slice of supply, not the global population of drivers.
  • One-to-one exclusivity. A driver, once matched, is removed from the pool for every other rider — the opposite of a product listing, which can satisfy an unlimited number of simultaneous "add to cart" actions.

Put those five together and the design question stops being "how do we store and serve inventory" and becomes "how do we run, continuously, a very large number of small, independent, real-time clearing auctions — one per neighborhood, updating every few seconds, each with strict spatial eligibility rules." Every chapter in this course's ride-hailing arc — geospatial indexing (ch. 2), location ingestion (ch. 3), dispatch (ch. 4), ETA (ch. 5), surge pricing (ch. 6), and the trip state machine (ch. 7) — is a piece of machinery built to answer that one reframed question.

WHY THIS MATTERS FOR THE NEXT 17 CHAPTERS

Nearly every hard problem later in this course is a direct consequence of the five properties above. Geospatial indexing (ch. 2) exists because "geographically relevant slice of supply" needs an efficient data structure, not a full scan. Location ingestion (ch. 3) exists because "continuous motion" means positions are stale the instant they're read unless a pipeline keeps refreshing them. Dispatch (ch. 4) exists because "one-to-one exclusivity" under concurrent requests is a genuine distributed-systems race condition, not a UI nicety. Keep the five properties in mind; you will be told to recall them by name later.

DEEP CONTEXT · WHY "MARKETPLACE," NOT "APP"

It is worth being precise about vocabulary this early, because the rest of the course leans on it. An "app" implies a client talking to a server. A "marketplace" implies two independent, self-interested populations whose joint behavior — not just the server's code — determines whether the system works. A server can be perfectly correct and the market can still fail to clear, if there simply aren't enough nearby drivers (a liquidity problem, revisited in §11). That distinction — code correctness vs. marketplace liquidity — recurs constantly in this course, most sharply in the surge-pricing chapter (ch. 6), which exists specifically to fix a liquidity problem, not a bug.

ARC 03 · NAIVE SOLUTION

Attempt #1: one table, one lock, nearest-by-scan

Derive the architecture honestly, the way a reasonable engineer would on day one. You have a table of drivers with a live latitude/longitude and an available flag. A rider requests a trip. The simplest possible matcher locks the table, scans every available driver, computes straight-line distance to each, and assigns the nearest one.

pseudocodenaive_match.psuedo — the strawman, annotated
function requestTrip(rider) {
  lock(GLOBAL_DRIVER_TABLE);          // one lock for the whole fleet, everywhere
  let best = null, bestDist = Infinity;

  for (driver of ALL_DRIVERS) {          // full scan, every driver on Earth
    if (!driver.available) continue;
    const d = euclidean(rider.lat, rider.lng, driver.lat, driver.lng);
    if (d < bestDist) { bestDist = d; best = driver; }
  }

  if (best) {
    best.available = false;              // remove from pool, still holding the lock
    assign(rider, best);
  }
  unlock(GLOBAL_DRIVER_TABLE);
  return best;
}

This is not a strawman built to be knocked down cheaply — it is the version of the design that gets every correctness property right on day one. There is exactly one lock, so two riders can never be assigned the same driver (no double-booking). Distance is computed honestly for every candidate, so "nearest" really is nearest. A small pilot city with a few hundred drivers would never notice a problem with this code.

ARC 04 · WHY IT FAILS

Two independent collapses: O(N) scans and a fleet-wide lock

The naive matcher fails in two distinct, additive ways, and it is worth separating them because they demand different fixes later (§5 fixes one, §7 fixes the other via ch. 4's dispatch design).

Collapse 1: the scan is O(N) in total fleet size, not local supply

Every request scans every available driver on the entire platform, even though a driver on another continent can never be a valid candidate. Consider an illustrative large metro market with on the order of 50,000 concurrently active drivers and roughly 500 ride requests per minute at a busy peak — numbers chosen to be representative of large-market ride-hailing scale, not a specific disclosed internal figure. Each request costs 50,000 distance computations. At 500 requests/minute that is 25,000,000 distance calculations per minute for one city — and a platform operating in thousands of cities multiplies that by however many of them are concurrently near peak. The cost is not a constant per request; it scales linearly with a number (total fleet size) that has nothing to do with the request itself.

Collapse 2: the lock serializes the entire platform, not just one neighborhood

The lock exists to prevent two riders from being assigned the same driver — a real requirement. But a single global lock enforces mutual exclusion between requests that could never have conflicted in the first place: a rider in Chicago and a rider in Nairobi are never contending for the same driver, yet the naive design forces their requests through the same critical section, one at a time.

THE NUMBERS

Model the matcher as a single-server queue (Little's Law, a classic result you'll see used again anywhere a shared resource serializes independent work). If each locked match — scan plus assignment — takes a mean service time S, the whole platform, not one city, is capped at throughput 1/S. If a scan-and-assign over 50,000 drivers takes on the order of 5 ms, the entire global platform tops out around 200 matches per second, regardless of how many independent cities are requesting rides simultaneously. A platform running in thousands of cities cannot clear its markets through one lock — the lock must be scoped to something far smaller than "everywhere," and the scan must be scoped to something far smaller than "everyone." Both fixes point at the same idea: exploit locality.

The next section derives that idea properly: instead of one table and one lock, partition drivers by geography, so both the scan and the lock shrink to the size of a neighborhood instead of the size of the planet.

ARC 05 · BETTER SOLUTION

Exploiting locality: partition the world, then match inside each partition

The core idea costs nothing to state and everything to implement well: a rider in one part of a city can only ever be matched to a driver in a nearby part of that same city, so pre-partition the map into small regions, index drivers by which region they're currently in, and run matching — and locking — per region instead of globally. Step through the evolution from the naive design to a spatially partitioned one.

From one global table to spatially partitioned matchingSTEP-BY-STEP

Notice what partitioning buys, precisely: a request in region R now only scans drivers indexed under R (and perhaps R's immediate neighbors, to cover riders near a boundary) — not the global fleet. And a lock scoped to region R blocks only other requests in region R, so a match clearing in São Paulo and a match clearing in Manila proceed fully in parallel. This is the exact idea this course's chapter 2 formalizes with real geometry: which shape should a region be, and how do you assign any lat/lon point to one instantly? (Spoiler: not a naive rectangular grid — §6 shows why, and chapter 2 derives Uber's real answer, H3.)

THE PATTERN, NAMED

This is spatial sharding — the geographic sibling of the hash-based sharding used in this site's database courses. The sharding key here is "which region is this point in," and the entire rest of this ride-hailing arc depends on that key being cheap to compute and stable under the small measurement noise that real GPS produces.

ARC 06 · WHY THAT STILL HURTS

Partitioning is necessary, not sufficient

Spatial partitioning removes the O(N) global scan and the global lock, but it introduces its own set of costs — real ones you would hit the week you shipped it, not hypothetical ones:

  • Boundary riders exist. A rider standing 20 meters from a region boundary might have their nearest available driver sitting just across that line, indexed under the neighboring region. A matcher that only looks inside one region will systematically miss the objectively best match for anyone near an edge.
  • Regions are not equally loaded. A naive rectangular grid over a city produces regions of equal area but wildly unequal request volume — a financial district cell might see a hundred times the traffic of a residential cell the same size. Fixed-size partitioning does not imply fixed-size load.
  • Distance distortion at the boundary shape. If regions are square cells, a driver in the diagonally adjacent cell is materially farther away (by a factor of √2) than a driver in the cell directly above — but a naive "check my cell and its 8 neighbors" search treats all 8 as equally worth checking, wasting scans on cells that are geometrically much less likely to contain the true nearest driver.
  • Drivers move between regions constantly. Every region-crossing requires an index update — remove from the old region's set, add to the new one — and that update itself needs to be race-free against a match being attempted on the same driver at the same instant (ch. 3 covers the ingestion side of this; ch. 4 covers the assignment race in full).

The first two problems (boundaries, uneven load) are geometry problems, and geometry is solvable with the right choice of region shape and a real hierarchy of resolutions — which is exactly why chapter 2 exists, and why it spends real time on the specific claim that hexagonal cells beat square ones. The third and fourth problems (movement, concurrent updates) are the subject of chapters 3 and 4 respectively. This chapter's job is only to establish why those chapters need to exist — which the final architecture below now assembles into one picture.

A PATTERN YOU WILL SEE ACROSS THE WHOLE COURSE

Nearly every "final architecture" in this course follows the same shape: solve the obvious problem with partitioning, discover partitioning creates boundary and rebalancing problems, and solve those with a purpose-built index or protocol — the same rhythm shows up anywhere a large system is sharded by a key and then has to solve what happens at the shard boundaries. Ride-hailing's version of "the index that makes partitioning honest" is H3 — next chapter.

ARC 08 · INTERNAL IMPLEMENTATION

The one mechanism this chapter owns: locality-scoped candidate search

Even before chapter 2 formalizes the real index, you can implement locality-scoped matching with a plain grid, and every real number below is genuinely computed by that grid, not decorative. The core shape:

pseudocodecell_match.pseudo — locality-scoped candidate search
function cellOf(lat, lng, cellSizeKm) { // coarse equirectangular bucketing
  return [floor(lat / kmToLat(cellSizeKm)), floor(lng / kmToLng(cellSizeKm, lat))];
}

function requestTrip(rider) {
  let [cx, cy] = cellOf(rider.lat, rider.lng, CELL_KM);
  for (ring = 0; ring <= MAX_RING; ring++) {   // expanding ring search
    lock(cellsInRing(cx, cy, ring));         // only THESE cells, not the fleet
    const candidates = driversInRing(cx, cy, ring);
    if (candidates.length) {
      const best = nearest(rider, candidates);
      best.available = false; assign(rider, best);
      unlock(cellsInRing(cx, cy, ring));
      return best;                          // scanned candidates.length, not fleet size
    }
    unlock(cellsInRing(cx, cy, ring));
  }
  return null;                                // no supply within MAX_RING — a liquidity problem, §11
}

Two things to notice. First, the scan cost is now proportional to drivers found within the search ring, not total fleet size — this is the O(N) → O(k) shift that §10 will graph. Second, the lock only covers the ring actually searched, so two requests in different rings of the same city proceed concurrently. Chapter 4 will show this expanding-ring idea is still not quite enough by itself (naive "grab the first ring with any driver" still produces worse-than-optimal global matches) — that's the seed of the batched bipartite-assignment idea chapter 4 builds properly. WHY EXPECTED CANDIDATE COUNT MATTERS OPERATIONALLY

If a search radius is tuned so that the expected candidate count in the first ring is comfortably above 1 in dense areas but the same fixed radius produces an expected count near 0 in a sparse suburb, you have two different operating regimes hiding behind one parameter. This is precisely why a single global "search radius" constant is itself a naive simplification — real systems make the effective radius adapt to local density, which is a direct consequence of the area-vs-driver-count math this widget makes explicit.

ARC 09 · TRADEOFFS

Three matching strategies, compared honestly

STRATEGYSCAN COSTWHAT IT BUYSWHAT IT COSTS
Global lock, full scan (§3)O(N) in total fleet size trivially correct always finds the true nearest throughput capped platform-wide unrelated cities block each other
Fixed grid, per-cell lock (§5–8)O(k), k = drivers in search ring cities clear in parallel scan cost tracks local supply, not global fleet boundary misses near cell edges uneven cell load
Hierarchical spatial index (ch. 2's H3, forward reference)O(k) with cheap, uniform-adjacency neighbor rings no boundary-shape distortion tunable resolution per density more index machinery to build and reason about

Read this table as the chapter's real thesis: every fix here trades implementation complexity for a narrower, cheaper scan — there is no version of this problem where you get O(1) global matching for free. The naive design is not "wrong," it is priced for a fleet size the platform outgrew; chapter 2 exists because the fixed-grid design's boundary and load problems are themselves priced wrong for a platform running in tens of thousands of distinct local markets simultaneously.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

Two classes of failure every two-sided marketplace hits

The cold-start / liquidity problem

This is the best-documented structural challenge in ride-hailing generally, and it is a marketplace failure, not a code bug: when Uber and its competitors have entered a new city, the earliest days consistently show the classic two-sided-marketplace cold-start pattern — too few drivers means riders wait too long and stop opening the app, and too few riders means drivers earn too little and stop logging on, each side's absence reinforcing the other's. This "chicken-and-egg" liquidity problem is widely discussed in the startup and marketplace-design literature (a well-known industry pattern, not a single disclosed internal Uber postmortem), and it is the direct motivation for the demand-side subsidies and driver incentives new-market launches are publicly known to use, and for surge pricing itself (ch. 6) as a mechanism to pull supply toward demand in real time once a market has scale. Chapter 2's H3 resolution choice and chapter 6's surge multiplier both assume a market has crossed this liquidity threshold; below it, no amount of matching-algorithm cleverness fixes an empty map.

Peak-event demand spikes

New Year's Eve, concert let-outs, and severe weather are recurring, publicly visible stress tests of exactly the matching mechanics this chapter describes: demand density in a small number of cells spikes far above the ambient rate the fixed search radius (§8) was tuned for, and the system's response — surge pricing pulling in supply, or riders simply experiencing longer waits — is a direct, observable consequence of the supply/demand ratio inside a small geographic partition, not of a global platform failure. Uber's surge pricing during high-profile demand spikes has drawn real, publicly documented criticism over the years — including sharp reactions to multiplier levels seen during severe weather and other emergencies — and that controversy is substantive enough that chapter 6 devotes a full section to presenting both the mechanism and the criticism fairly, rather than relitigating it here. The relevant point for this chapter: the underlying trigger, in every one of these events, is a local supply/demand imbalance inside one or a few geographic partitions — exactly the unit of locality this chapter argued matching must be scoped to.

THE GENERAL LESSON

Neither failure mode above is a defect in the matching algorithm as such — both are the marketplace itself running out of one side's supply relative to the other's demand, inside a bounded local area. A perfectly efficient O(k) matcher still returns nothing if k is zero. That is precisely why this course treats liquidity (this chapter, and again in ch. 6) as a first-class systems concern, not a business-side afterthought.

The two functions that matter most, expanded from the pseudocode in §8 into a shape closer to production code:

Go-style pseudocodecell_index.go — add/remove + neighbor rings
type CellIndex struct {
    cells map[CellID][]DriverID   // one set of drivers per cell, in-memory
    mu    sync.RWMutex          // per-shard lock, NOT one lock for the whole index
}

func (idx *CellIndex) OnLocationUpdate(d DriverID, oldCell, newCell CellID) {
    if oldCell == newCell { return }        // most pings don't cross a boundary
    idx.mu.Lock()
    idx.cells[oldCell] = remove(idx.cells[oldCell], d)
    idx.cells[newCell] = append(idx.cells[newCell], d)
    idx.mu.Unlock()
}

func (idx *CellIndex) Ring(center CellID, k int) []DriverID {
    var out []DriverID
    for _, c := range neighborsAtDistance(center, k) {  // ch. 2 replaces this with H3's k-ring
        out = append(out, idx.cells[c]...)
    }
    return out
}
Go-style pseudocodematcher.go — the request path
func (m *Matcher) Match(rider Rider) (*Driver, error) {
    center := m.index.CellOf(rider.Lat, rider.Lng)
    for ring := 0; ring <= m.maxRing; ring++ {
        candidates := m.index.Ring(center, ring)
        if len(candidates) == 0 { continue }

        best := m.scorer.Best(rider, candidates)   // straight-line distance today; ETA in ch. 5
        if ok := m.locks.TryClaim(best.ID); !ok {
            continue                            // lost a race to another request in the same ring
        }
        m.events.Publish(MatchedEvent{rider, best})
        return best, nil
    }
    return nil, ErrNoSupplyInRadius              // a liquidity problem, §11 — not a bug
}
WHY THIS SHAPE — TWO DECISIONS WORTH STEALING

1. Per-cell locks, claimed optimistically. TryClaim — rather than taking a lock and holding it through the whole scoring step — means a losing request retries against the next-best candidate instead of blocking. This is the same optimistic-concurrency idea chapter 4 formalizes fully once batched assignment is on the table. 2. "No supply in radius" is a first-class return value, not an error path bolted on later. Treating a liquidity shortfall as an expected outcome, not an exceptional one, is what lets pricing (ch. 6) and driver-incentive systems hook into exactly that signal.
