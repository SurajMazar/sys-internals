STEP 01 · SETUP

A three-node cluster in one command

Three nodes, not one — quorum queues, partitions, and clustering are most of what the theory chapters cover, and none of them mean anything on a single broker. You need Docker with Compose v2 and about 2 GB of free RAM.

The files

Three files in a directory. The Erlang cookie is what lets nodes form a cluster at all — it must be identical everywhere, and it is a shared secret, not a password.

Start node 1, then join the others

Clustering is not automatic — nodes must be explicitly joined, and joining resets the joining node, discarding its local state. That's why the order matters.

  docker exec $n rabbitmqctl stop_app
  docker exec $n rabbitmqctl reset
  docker exec $n rabbitmqctl join_cluster rabbit@rabbit1
  docker exec $n rabbitmqctl start_app

Aliases you'll use constantly

bash

# an Erlang shell attached to the live node — this is the real superpower
ERL() { docker exec -it "${1:-rabbit1}" rabbitmqctl eval "$2"; }

The management UI is at localhost:15672 (lab / lab). Node 2 and 3's UIs are on 15673 and 15674 — useful during the partition experiment, when node 1 may be unreachable.

Teardown

bash
docker compose down        # stop, keep the data volumes
docker compose down -v     # stop and DELETE everything — full reset

Several experiments deliberately damage the cluster. A full reset plus re-join takes about a minute — use it freely rather than fighting a broken state.

Troubleshooting

SYMPTOMCAUSE & FIX
Could not connect: node down on join The Erlang cookies differ, or node 1 isn't up yet. All three must share RABBITMQ_ERLANG_COOKIE; check with docker exec rabbit2 cat /var/lib/rabbitmq/.erlang.cookie. Also confirm node 1 is healthy first.
Join succeeds but the node isn't listed You skipped reset. A node with existing state refuses to join cleanly — stop_app, reset, join, start_app, in that order.
Hostname resolution fails between nodes Erlang distribution addresses nodes as rabbit@<hostname>, so the hostname: key in Compose must match the service name. Don't remove it.
Memory alarm fires immediately on startup Expected with the deliberately low 0.4 watermark on a small Docker VM. Raise it to 0.6 in rabbitmq.conf if it's disruptive, but experiment 11 needs it low.
Port already allocated Change the host side only (e.g. "5682:5672"). The container-side ports stay as they are.
Management UI shows nodes as down after a partition experiment That's the point of the experiment. docker compose restart and re-check cluster_status; if the split persists, do a full reset.

STEP 04 · PRODUCTION BEST PRACTICES

A config cookbook where every number has a reason

Choosing a queue type — the decision that matters most

USEWHENMECHANISM
QuorumDefault for anything that matters. Work queues, commands, events you cannot lose. Raft-replicated (ch.6): an ack is a real durability guarantee backed by a majority. Costs a majority round trip plus fsync per operation. Built-in x-delivery-limit poison protection.
ClassicTransient work, RPC replies, very high throughput on one node, queues always near-empty. One Erlang process, no replication (ch.4). Fastest per-queue, but the queue dies with its node and throughput is capped by one scheduler.
StreamReplay needed, large fan-out, or very high throughput with many independent readers. Append-only log with consumer-held offsets (ch.7). Non-destructive reads mean N consumers cost one copy, not N.
Mirrorednever Deprecated in 3.9, removed in 4.0. No consensus — partitions could diverge silently. Migrate (runbook 5.4).

Connection and channel discipline

  • Long-lived connections, never per-operation. Each connection is a TCP handshake plus TLS plus several Erlang processes. Connection churn is one of the most common self-inflicted production problems.
  • One channel per thread, never shared. Channels are not thread-safe (ch.2) — sharing one interleaves frames and corrupts the stream. Pool connections, open a channel per worker.
  • Separate connections for publishing and consuming. This is the direct consequence of credit-based flow control (ch.9): when a queue blocks its connection, everything on that connection stalls. Keep a blocked publisher from freezing your consumers.
  • Handle connection.blocked. Under a memory or disk alarm the broker blocks publishers. A client that ignores the notification just hangs with no error — indistinguishable from a network problem when you're debugging at 3am.
  • Set heartbeats to 30–60s. Too low and a busy scheduler causes false disconnects; too high and dead connections linger, holding their unacked messages hostage until detection.

Publisher settings

SETTINGGUIDANCEWHY
publisher confirmsalways on for anything that matters The only way to know the broker took responsibility. Use async confirms with an in-flight window — never confirm-per-message, which serialises on a network round trip.
AMQP transactionsnever A synchronous fsync round trip per message, roughly 100× slower than confirms (ch.5). Confirms exist precisely to replace them.
delivery_mode=2for persistent messages One of three conditions for surviving a restart — the exchange and queue must also be durable (ch.11). Setting only one or two is the classic false-durability mistake.
mandatoryon, with a return listener Otherwise a message routed nowhere is silently discarded. A confirm means "the broker took it", not "a queue got it".

Consumer settings

  • Never use auto-ack (noAck=true) for work you cannot lose. It acknowledges on delivery, before your code runs — a crash loses the message with no trace.
  • Set prefetch deliberately. Derive it: prefetch ≈ ceil(round_trip_ms / processing_ms), rounded up for jitter. A common starting point is 20–50 for fast handlers and 1–5 for slow ones. Unlimited prefetch lets one consumer hoard the whole queue.
  • Ack after the work is durable, not after you receive it. The unacked set is your safety net — a channel death requeues everything in it.
  • Always bound retries. Use quorum queues' x-delivery-limit, or dead-letter after N attempts. An unbounded nack-requeue loop is an infinite loop (ch.5).

Queue and policy settings

basha sane baseline policy
# Bound every queue. An unbounded queue is a memory incident waiting to happen.
R set_policy work-queues '^work\.' \
  '{"max-length":1000000,
    "overflow":"reject-publish",
    "dead-letter-exchange":"dlx",
    "delivery-limit":5}' \
  --apply-to quorum_queues

# Auto-delete queues nobody has used in a day (stops RPC-reply-queue sprawl).
R set_policy transient '^rpc\.' \
  '{"expires":86400000}' --apply-to classic_queues

overflow=reject-publish rather than the default drop-head is usually right: a publisher that is told "no" can retry or shed load, whereas silently dropping the oldest message loses data nobody notices until much later.

Anti-patterns and their specific damage

ANTI-PATTERNWHAT IT COSTS
Unbounded queuesworst offender A consumer outage becomes a memory alarm, which blocks all publishers cluster-wide (ch.9). Always set max-length or max-length-bytes.
A two-node clusterpause_minority cannot work — neither side is ever a majority (ch.10). Use 1, 3, or 5 nodes. Never 2.
Sharing one connection across workloadsCredit flow control is per-connection-chain, so one slow queue blocks unrelated publishers on the same connection (ch.9).
Unlimited prefetchOne consumer buffers the entire queue while others idle; a crash then requeues thousands of messages at once (ch.5).
Per-message TTL expecting prompt expiryOnly head-of-queue messages expire (ch.8). A long-TTL message at the head blocks everything behind it, which still counts toward queue length and memory.
DLX pointing back at the source queueCycle detection silently drops the message. Use a separate delay queue with its own DLX (ch.8).
x-max-priority: 255255 sub-queues per queue process. Memory and CPU scale with the level count; 5 is plenty (ch.8).
One very hot queueA queue is one Erlang process (ch.4) — it cannot use more than one scheduler. Shard across queues to scale.
Polling with basic.getA synchronous round trip per message with no prefetch pipelining. Use basic.consume.

STEP 05 · OPERATIONAL RUNBOOKS

  
Procedures for when it's already going wrong


  
5.1 · Rolling restart with no message loss

  
Precondition: quorum queues with 3 members, or you will lose classic queues on the restarted node.

  
bash


for n in rabbit1 rabbit2 rabbit3; do
  echo "== $n =="
  # Move quorum-queue leadership off this node BEFORE stopping it.
  docker exec $n rabbitmq-queues rebalance all 2>/dev/null || true
  docker exec $n rabbitmqctl stop_app      # graceful: connections close, leadership migrates
  docker restart $n
  sleep 15
  docker exec $n rabbitmqctl start_app
  docker exec $n rabbitmqctl await_online_quorum_plus_one -t 120   # THE gate
  echo "   $n back with quorum margin"
done
docker exec rabbit1 rabbitmq-queues rebalance all

  

    
THE GATE THAT MAKES THIS SAFE

    
await_online_quorum_plus_one blocks until every quorum queue has a majority plus one
    spare online. Without it you can stop a second node while the first is still catching up, drop below
    majority, and take every quorum queue offline. It is the exact analogue of waiting for
    under-replicated-partitions to hit zero in Kafka.

  


  
5.2 · A queue is growing without bound

  
    
    
  1. Confirm the direction: R list_queues name messages message_bytes consumers messages_unacknowledged. Publish rate exceeding consume rate, or zero consumers?
    2. 
    
  2. Zero consumers → the consumer application is down or failed to reconnect. Check R list_consumers.
    3. 
    
  3. Consumers present, but messages_unacknowledged is high and static → consumers are stuck mid-processing (blocked on a database, a lock, an external API). The queue is fine; the consumer isn't.
    4. 
    
  4. Consumers present, unacked low, still growing → genuinely too slow. Add consumers (up to the point where the single queue process saturates — ch.4), then shard across queues.
    5. 
    
  5. Emergency relief: apply a temporary max-length policy with drop-head, or shovel the backlog to a holding queue for later reprocessing (5.5). Do not delete the queue.
    6. 
  


  
5.3 · Memory alarm — publishers are blocked

  
bash


# 1. Confirm and find out WHERE the memory went.
R status | grep -A15 'Memory'
D memory_breakdown

# 2. Which queues hold it?
R list_queues name messages message_bytes memory --sort memory | tail -10

# 3. Temporary relief: raise the watermark to unblock publishers while you drain.
R set_vm_memory_high_watermark 0.7

# 4. Real fix: get consumers running, or bound the queue.
R set_policy emergency-cap '^bloated\.' '{"max-length":100000,"overflow":"drop-head"}' \
  --apply-to queues

# 5. Restore the watermark once memory is back down.
R set_vm_memory_high_watermark 0.4

  
If memory_breakdown shows most memory under binary rather than queue_procs,
  you're looking at the refc-binary retention problem (ch.9) — large message bodies held by processes that
  haven't been garbage collected. R force_gc is the blunt instrument.


  
5.4 · Migrating classic mirrored queues to quorum queues

  
Mirrored queues are removed in 4.0, so this migration is mandatory before upgrading. There is no in-place
  conversion — a queue's type is fixed at declaration.

  
    
    
  1. Declare the replacement with a new name: orders.q → orders.qq with x-queue-type=quorum.
    2. 
    
  2. Switch consumers first so they read from both old and new during the transition.
    3. 
    
  3. Switch publishers to the new queue. The old one now only drains.
    4. 
    
  4. Wait for the old queue to reach zero, or shovel the remainder across (5.5).
    5. 
    
  5. Delete the old queue and remove its HA policy.
    6. 
    
  6. Verify: R list_queues name type members shows quorum with 3 members.
    7. 
  

  

    
WHAT CHANGES BEHAVIOURALLY

    
Quorum queues do not support priorities, and their memory tracks unacked messages rather than
    queue depth. Publishing is slower (a majority round trip per operation). In exchange you get a real
    durability guarantee and built-in delivery-limit poison handling. Do not migrate blind —
    check whether anything depended on x-max-priority.

R shovel_status
# src-delete-after=queue-length stops the shovel once the initial backlog is moved.
R clear_parameter shovel drain-old


  
5.6 · Recovering from a network partition

  
    
    
  1. Detect: R cluster_status shows a Network Partition section, or the UI shows a red banner.
    2. 
    
  2. Under pause_minority (recommended): the minority paused itself and there is nothing to reconcile. Restore connectivity, and the paused nodes rejoin automatically. Verify with cluster_status.
    3. 
    
  3. Under ignore: both sides accepted writes and metadata has diverged. You must choose a winner. Stop the losing side, rabbitmqctl reset it, and re-join — this discards its data, which is exactly why ignore is a bad default.
    4. 
    
  4. Quorum queues survive this well by design: the minority side could not commit, so there is nothing to reconcile for them. Classic queues on the losing side are lost.
    5. 
    
  5. Prevent recurrence: confirm cluster_partition_handling = pause_minority, an odd node count, and a stable low-latency network between nodes. Never cluster across a WAN — use federation (ch.10).
    6. 
  


  
5.7 · Poison message burning a consumer

  
    
    
  1. Symptom: one consumer at 100% CPU, queue depth static, messages_unacknowledged oscillating, the same message redelivered endlessly.
    2. 
    
  2. Confirm: R list_queues name messages messages_unacknowledged then get one message with ackmode=ack_requeue_true and inspect its x-death header (ch.8).
    3. 
    
  3. Immediate stop: apply delivery-limit via policy — quorum queues will dead-letter the offender automatically after N attempts.
    4. 
    
  4. If it's a classic queue, there is no built-in counter: stop the consumer, drain the poison message to a DLQ manually, and restart.
    5. 
    
  5. Prevent: every retry path needs a bound. This is the single strongest argument for quorum queues over classic.
    6.

Project 1 · A reliable worker with bounded retries

  
The pattern that gets reinvented badly everywhere: at-least-once processing with confirms, prefetch, a
  bounded retry with backoff, and a final dead-letter queue. Built on the topology from chapter 8.


  
bashtopology


RA() { docker exec rabbit1 rabbitmqadmin -u lab -p lab "$@"; }

RA declare exchange name=work.x type=direct durable=true
RA declare exchange name=retry.x type=direct durable=true
RA declare exchange name=dead.x  type=direct durable=true

# Main queue: quorum, bounded, 5 delivery attempts then dead-letter.
RA declare queue name=work.q durable=true \
  'arguments={"x-queue-type":"quorum","x-dead-letter-exchange":"retry.x",
              "x-delivery-limit":5,"x-max-length":100000,"x-overflow":"reject-publish"}'

# Retry queue: holds messages for 5s, then dead-letters BACK to the main exchange.
RA declare queue name=retry.q durable=true \
  'arguments={"x-queue-type":"quorum","x-message-ttl":5000,
              "x-dead-letter-exchange":"work.x","x-dead-letter-routing-key":"job"}'

# Terminal dead-letter queue: nothing leaves here automatically.
RA declare queue name=dead.q durable=true 'arguments={"x-queue-type":"quorum"}'

RA declare binding source=work.x  destination=work.q  routing_key=job
RA declare binding source=retry.x destination=retry.q routing_key=job
RA declare binding source=dead.x  destination=dead.q  routing_key=job


  
pythonworker.py


import pika, json, sys, time, random

params = pika.ConnectionParameters(
    host="localhost", credentials=pika.PlainCredentials("lab", "lab"),
    heartbeat=30, blocked_connection_timeout=60)

conn = pika.BlockingConnection(params)
ch = conn.channel()

# Prefetch: RTT ~2ms, processing ~100ms → ceil(2/100)=1, round up for jitter.
# Small prefetch keeps work evenly spread across workers (ch.5).
ch.basic_qos(prefetch_count=4)

def handle(chan, method, props, body):
    # x-death accumulates one entry per dead-lettering hop (ch.8).
    deaths = (props.headers or {}).get("x-death", [])
    attempt = deaths[0]["count"] if deaths else 0

    try:
        job = json.loads(body)
        if job.get("poison"):
            raise ValueError("this job always fails")
        time.sleep(0.05)
        print(f"✓ {job['id']} (attempt {attempt})", flush=True)
        chan.basic_ack(method.delivery_tag)

    except Exception as e:
        # requeue=False sends it to the DLX → retry.q → 5s → back here.
        # After x-delivery-limit attempts the broker dead-letters it for good.
        print(f"✗ attempt {attempt}: {e}", flush=True)
        chan.basic_nack(method.delivery_tag, requeue=False)

ch.basic_consume("work.q", handle)
print("worker ready", flush=True)
try:
    ch.start_consuming()
except KeyboardInterrupt:
    conn.close()


  
pythonpublish.py — with confirms and mandatory


import pika, json, sys

conn = pika.BlockingConnection(pika.ConnectionParameters(
    host="localhost", credentials=pika.PlainCredentials("lab", "lab")))
ch = conn.channel()
ch.confirm_delivery()          # Confirm.Select — ch.5

n = int(sys.argv[1]) if len(sys.argv) > 1 else 20
poison_every = int(sys.argv[2]) if len(sys.argv) > 2 else 0

sent = failed = 0
for i in range(n):
    body = json.dumps({"id": i, "poison": poison_every and i %% poison_every == 0})
    try:
        ch.basic_publish(
            "work.x", "job", body.encode(),
            properties=pika.BasicProperties(delivery_mode=2),  # persistent
            mandatory=True)   # unroutable → Basic.Return, not silent discard
        sent += 1
    except pika.exceptions.UnroutableError:
        failed += 1
        print(f"UNROUTABLE: {i}")

print(f"confirmed={sent} unroutable={failed}")
conn.close()

Project 2 · Measure the prefetch curve on your own hardware

  
Chapter 5 derived prefetch ≈ ceil(RTT / processing_time). Verify it rather than trusting it.

  
pythonprefetch_bench.py


import pika, time, threading, statistics, sys

HOST, CREDS = "localhost", pika.PlainCredentials("lab", "lab")
PROC_MS = float(sys.argv[1]) if len(sys.argv) > 1 else 5.0
N, WORKERS = 3000, 4

def setup():
    c = pika.BlockingConnection(pika.ConnectionParameters(HOST, credentials=CREDS))
    ch = c.channel()
    ch.queue_delete("bench.q")
    ch.queue_declare("bench.q", durable=True,
                     arguments={"x-queue-type": "quorum"})
    ch.confirm_delivery()
    for i in range(N):
        ch.basic_publish("", "bench.q", str(i).encode(),
                         properties=pika.BasicProperties(delivery_mode=2))
    c.close()

def worker(prefetch, counts, idx, stop):
    c = pika.BlockingConnection(pika.ConnectionParameters(HOST, credentials=CREDS))
    ch = c.channel(); ch.basic_qos(prefetch_count=prefetch)
    got = 0
    for method, props, body in ch.consume("bench.q", inactivity_timeout=1):
        if method is None or stop.is_set(): break
        time.sleep(PROC_MS / 1000.0)
        ch.basic_ack(method.delivery_tag); got += 1
    counts[idx] = got
    try: c.close()
    except: pass

print(f"processing={PROC_MS}ms  workers={WORKERS}  messages={N}\n")
print(f"{'prefetch':>9} {'msg/s':>9} {'spread':>9}   distribution")
for pf in [1, 2, 5, 10, 30, 100, 500]:
    setup()
    counts = [0]*WORKERS; stop = threading.Event()
    ts = [threading.Thread(target=worker, args=(pf, counts, i, stop)) for i in range(WORKERS)]
    t0 = time.time()
    [t.start() for t in ts]; [t.join() for t in ts]
    dt = time.time() - t0
    total = sum(counts)
    spread = max(counts) - min(counts)      # fairness: lower is fairer
    bar = " ".join(f"{c:4d}" for c in counts)
    print(f"{pf:9d} {total/dt:9.0f} {spread:9d}   {bar}")

pythonbus.py


import pika, sys, random, time

CREDS = pika.PlainCredentials("lab", "lab")
conn = pika.BlockingConnection(pika.ConnectionParameters("localhost", credentials=CREDS))
ch = conn.channel()

if sys.argv[1] == "publish":
    keys = ["order.eu.created", "order.us.created", "order.eu.error",
            "payment.eu.settled", "payment.us.error", "user.eu.signup"]
    for i in range(int(sys.argv[2])):
        k = random.choice(keys)
        ch.basic_publish("events.x", k, f"event-{i}".encode(),
                         properties=pika.BasicProperties(delivery_mode=2))
    print("published")

elif sys.argv[1] == "replay":
    # A stream consumer MUST set prefetch and an offset (ch.7).
    ch.basic_qos(prefetch_count=100)
    offset = sys.argv[2] if len(sys.argv) > 2 else "first"
    n = 0
    for method, props, body in ch.consume(
            "ev.audit", inactivity_timeout=3,
            arguments={"x-stream-offset": offset}):
        if method is None: break
        n += 1; ch.basic_ack(method.delivery_tag)
    print(f"replayed {n} events from offset={offset}")

conn.close()

  
bash


python3 bus.py publish 300
R list_queues name type messages        # each live queue got only its matches

python3 bus.py replay first             # all 300 — the stream kept everything
python3 bus.py replay first             # 300 AGAIN — non-destructive read
R list_queues name type messages        # ev.audit still holds 300

  
That last pair of commands is the whole point of chapter 7: the quorum queues are drained by consuming,
  the stream is not. Replay works because reading a stream doesn't mutate it.
