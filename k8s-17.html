Advanced Scheduling &
Beyond the Single Cluster

Chapter 8 gave you a scheduler that can bin-pack one cluster's nodes correctly. Chapter 9 gave you a reconciliation loop that keeps one object's desired state true. This chapter breaks both assumptions on purpose: what happens when "spread evenly" can't be expressed as a pairwise affinity rule, when the built-in scheduler's bin-packing logic isn't the bin-packing logic your workload needs, and when "desired state" has to stay true not in one cluster but across a fleet of them — some reachable, some not, each capable of drifting independently. You will leave with the exact fields that drive topology-aware placement, the two competing shapes of scheduler extensibility and why one superseded the other, and the meta-reconciliation-loop pattern (Cluster API, GitOps controllers) that makes "the fleet" a reconcilable object in its own right.

ARC 01 · THE PROBLEM

"Spread evenly" and "keep N clusters honest" are both harder than they sound

This chapter is really two problems that turn out to share one shape. The first lives inside a single cluster: as soon as a workload has enough replicas to care about failure domains, "don't collide" (what affinity and anti-affinity express) stops being the question you actually need answered — the question is "how evenly," and pairwise rules cannot say that. The second lives above the cluster boundary entirely: real production is rarely one cluster. Regulatory isolation, blast-radius limits, vendor diversity, and burst capacity routinely mean a team owns five, forty, or four hundred clusters — and chapter 9's reconciliation loop, which keeps one object's desired state true against one API server, has nothing to say about keeping the same desired state true across all of them at once, independently, while some are unreachable.

Problem A: pairwise rules can't express a ratio

Say a Deployment runs 30 replicas of a stateless API across 3 availability zones. Pod anti-affinity (chapter 8) can express "don't put two replicas on the same node" or "prefer not to co-locate with this label" — but it has no concept of counting. Nothing stops the scheduler, filling zones in whatever order nodes report ready, from placing 22 replicas in zone A, 6 in zone B, and 2 in zone C — every anti-affinity rule you wrote is still satisfied (no two Pods share a node), yet a single zone now carries 73% of the service's capacity. Lose zone A and you don't lose a third of capacity — you lose nearly three-quarters of it, with the remaining two zones holding 8 replicas total to absorb 30 replicas' worth of traffic.

Problem B: N clusters, one desired state, independent failure

Now put that same Deployment's manifest in front of 40 clusters — three regions, staging and production tiers, maybe an on-prem cluster for compliance reasons. Every cluster needs the same baseline: the same NetworkPolicy, the same ResourceQuota, the same version of this API's manifest. But each cluster is its own independent API server with its own etcd, its own network reachability from wherever you run your tooling, and its own operators who occasionally run kubectl edit directly against it at 2 a.m. There is no single etcd to write "desired state" into once — desired state must somehow be pushed, and kept pushed, into 40 independently-failing systems, and you need to know which ones currently match and which don't, right now, not at next week's manual audit.

THE SHARED SHAPE

Both problems are instances of the same failure: a mechanism designed for a single, local decision (place this one Pod; converge this one object) is being asked to hold a global, distributed property (an even ratio across N domains; a matching state across N clusters) that no single decision point can see. The fix in both cases is the same shape too — stop trying to encode the global property as a rule evaluated once, and instead give some component continuous visibility into the actual distribution or the actual fleet, so it can keep correcting toward the property rather than assuming a single placement or a single push gets you there.

DEEP CONTEXT · FEDERATION'S FAILED FIRST ATTEMPT

Kubernetes' first multi-cluster answer, Federation v1 ("Ubernetes," 2016–2019), tried to present a single federated API that transparently replicated objects to every member cluster. It was deprecated because it re-derived a second, weaker control plane on top of the real ones — federated objects had their own sync status, their own bugs, and diverged from what kubectl against a member cluster actually showed. Cluster API and GitOps controllers (this chapter's answer) deliberately do not repeat that mistake: they manage or reconcile real cluster-native objects through each cluster's own real API server, never inventing a shadow object model. That one architectural lesson is worth the whole history section.

ARC 03 · NAIVE SOLUTION

Attempt #1: split it by hand, push it by hand

Before reaching for any of this chapter's mechanisms, here is the honest first attempt an operator makes — and it is not unreasonable. Two strawmen, one per problem.

(a) Manual zone-split Deployments, instead of one spread-aware Deployment

YAMLnaive-spread.yaml — three Deployments doing one Deployment's job
apiVersion: apps/v1
kind: Deployment
metadata: { name: api-zone-a }
spec:
  replicas: 10            # hand-picked: 30 / 3 zones
  template:
    spec:
      nodeSelector: { topology.kubernetes.io/zone: us-east-1a }
---
# ...repeated verbatim for api-zone-b (1b) and api-zone-c (1c) ...

Three objects, one per zone, each pinned with nodeSelector and each carrying a third of the target replica count. It works on day one — the distribution really is 10/10/10.

(b) A bash loop over kubeconfigs, instead of a fleet controller

bashfleet-deploy.sh — the strawman for problem B
#!/usr/bin/env bash
CLUSTERS=(prod-us-east prod-eu-west prod-ap-south staging-us-east # ...36 more...)

for ctx in "${CLUSTERS[@]}"; do
  echo "applying to $ctx"
  kubectl --context="$ctx" apply -f manifests/          # one cluster at a time
  if [ $? -ne 0 ]; then
    echo "FAILED: $ctx — continuing to the next one"  # or worse: exit 1 here
  fi
done

Run this from a laptop or a CI job with 40 kubeconfig contexts, and — as long as every cluster is reachable and every apply succeeds — the fleet converges. It is also, like the zone split above, a completely reasonable thing to write first. Both strawmen already get the common case right. Section 4 is about the case that isn't common, but is inevitable at any real scale.

ARC 04 · WHY IT FAILS

Static splits don't survive change; loops don't survive partial failure

Neither strawman is wrong at the instant you write it. Both decay — for precise, quantifiable reasons — the moment the world underneath them moves, which for a scheduler and a fleet is constantly.

  • The zone split can't see the cluster autoscaler. Your 10/10/10 hand-split assumed 3 equally-sized zones. Cluster Autoscaler (chapter 12) scales node groups per zone independently based on pending Pods and cost; a spot-capacity interruption or a scale-down in zone C can leave it with 40% of the nodes zones A and B have. nodeSelector: zone=us-east-1c still pins exactly 10 replicas there — now competing for a shrunken node pool — while zones A and B may be under-packed. The split is a snapshot; the fleet is not.
  • Three Deployments defeat one HPA. A Horizontal Pod Autoscaler (chapter 12) targets one Deployment's average utilization. Split into three, each HPA sees only its zone's third of traffic — if a load balancer happens to route unevenly (it usually does, at least transiently), one zone's HPA scales up while another's scales down, and the global replica count you actually wanted is now the accidental sum of three independent, uncoordinated control loops instead of one.
  • The bash loop has no isolation between clusters. If cluster #23 of 40 is mid-upgrade and its API server returns connection-refused, what happens next is whatever that particular script author wrote: set -e aborts the whole run, leaving clusters 24–40 untouched with no record of that; a bare continue silently proceeds, and now cluster #23 is drifted with no signal anywhere that it is. Either way, "did the fleet converge?" has no answer except re-running a diff against every cluster by hand.
  • The math on drift detection. If nobody automates the audit, someone runs it manually — say, weekly. Between audits, every cluster that a human touched directly (an incident-response kubectl edit, a one-off kubectl scale that nobody reverted) drifts silently. Real fleets that rely on manual push-and-hope routinely carry a double-digit percentage of clusters out of sync with their own "canonical" manifests by the time anyone checks — not because operators are careless, but because nothing was continuously comparing desired state to live state, which is exactly the reconciliation guarantee chapter 9 gave you for one object, silently absent here for the fleet.
THE NUMBERS

At 40 clusters, a serial push averaging even a generous 45 seconds per cluster (context switch, apply, eyeball the output) is 30 minutes of wall-clock time for one change — during which the fleet is, by definition, in a mixed state. A single misconfigured context mid-run doesn't fail loud; it fails quiet, and quiet failures compound. The naive answer to "how do I trust the fleet matches git?" is "I don't, until I go check" — that's not an operational property, it's the absence of one.

THE PATTERN ACROSS ALL FIVE

Every one of these replaces a value computed once, by a human, ahead of time with a value computed continuously, by a controller, against live state. Topology spread recomputes skew at every scheduling decision. An extender or a framework plugin is consulted per-Pod, live. Cluster API's controllers watch actual infrastructure state, not a runbook. A GitOps controller re-diffs the whole cluster on every reconcile tick, not once at deploy time. This is the same lesson chapter 9 taught for one object, now applied one level up.

ARC 06 · WHY THAT STILL COSTS

Every one of these five buys a property and spends something for it

  • Topology spread constraints don't rebalance the past. The PodTopologySpread plugin influences only new placement decisions. If your 22/6/2 skew from §1 already exists, adding a spread constraint today does nothing to the 30 Pods already running — it only stops the skew from getting worse as Pods churn. Fixing existing skew needs something to evict and reschedule (the descheduler project, out of scope here) — the constraint is a brake, not a rebalancer.
  • Scheduler extenders pay a network hop per scheduling decision. Because an extender is an out-of-process HTTP service, every Filter and Prioritize call the scheduler would otherwise make in-process (microseconds) becomes a real network round trip — typically single-digit to tens of milliseconds. At a few pods per second this is invisible; during a burst of hundreds of pending Pods it can dominate scheduling latency, and if the extender is configured non-ignorable, an extender outage doesn't degrade scheduling — it halts it, cluster-wide, because the scheduler synchronously waits on the call.
  • Cluster API needs a cluster to manage your clusters. The management cluster hosting CAPI's controllers is now a hard dependency for provisioning, upgrading, or scaling any workload cluster — and it needs its own backup, HA, and RBAC story, or you've just relocated the single-point-of-failure problem one layer up, not removed it.
  • virtual-kubelet nodes look like nodes but aren't. A virtual-kubelet-backed Node satisfies the scheduler's API contract — it has capacity, allocatable, conditions — but there is no real kubelet underneath running cgroups, no local kube-proxy, and usually no CNI in the cluster's sense. That means DaemonSets don't get scheduled there (nothing runs them), hostPath/hostNetwork have no meaning, and kubectl exec/logs only work if the specific provider chose to implement them by proxying to whatever backend actually runs the container. It is a real, useful capacity extension for a narrow class of stateless, sandboxed workloads — not a substitute node.
  • GitOps controllers concentrate blast radius. A controller with write access to reconcile a fleet necessarily holds credentials with broad — often cluster-admin-equivalent — privilege across every cluster it touches. Whatever can commit to (or manipulate) the repository or Application/Kustomization objects it reads inherits that reach. §11 covers a real, disclosed vulnerability that turned exactly this design point into a file-read primitive.

ARC 08 · INTERNAL IMPLEMENTATION

The real fields, the real wire formats, the real CRDs

(a) Topology spread constraints — the fields that actually compute skew

YAMLtopologySpreadConstraints — the real API shape
spec:
  topologySpreadConstraints:
  - maxSkew: 1                       # max allowed |domain_max - domain_min|
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule    # hard: leave Pod Pending rather than violate
    labelSelector:
      matchLabels: { app: web }
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway   # soft: prefer, but never leave Pending
    labelSelector:
      matchLabels: { app: web }

topologyKey names the node label whose distinct values define "domains" (zone, hostname, a custom rack label — anything the nodes carry). maxSkew bounds the difference between the domain with the most matching Pods and the domain with the fewest, after the Pod being scheduled is placed. whenUnsatisfiable chooses what happens when no domain can accept the Pod without breaching maxSkew: DoNotSchedule is a Filter-time hard constraint (the Pod stays Pending); ScheduleAnyway is a Score-time soft preference (the Pod schedules somewhere, just not necessarily the most even place). Two later additions worth knowing: minDomains (beta 1.25) tells the scheduler "treat fewer than N domains as itself a skew violation" — useful when you're scaling into a region that doesn't have all zones populated yet — and matchLabelKeys (beta 1.27) scopes the calculation to Pods from the same rollout (by pod-template-hash) so an old and new ReplicaSet aren't spread-balanced against each other during a rolling update.

(b) Scheduler extenders — the wire format the modern framework replaced

Before the scheduling framework's in-process plugin interfaces, the only way to inject custom logic without forking kube-scheduler was an extender: an HTTP(S) service registered in the scheduler's policy config, called synchronously at defined points.

JSONthe extender wire contract — ExtenderArgs / ExtenderFilterResult
// scheduler → extender, POST {urlPrefix}{filterVerb}
{ "Pod": { ...full Pod object... },
  "Nodes": { "items": [ ...Node objects that passed in-process filters so far... ] } }

// extender → scheduler, response body
{ "Nodes": { "items": [ ...surviving Node objects... ] },
  "FailedNodes": { "gpu-node-3": "no free GPU matching requested model" },
  "Error": "" }

The registration itself carries the operationally important knobs:

YAMLKubeSchedulerConfiguration — extenders: block
extenders:
- urlPrefix: "https://gpu-extender.kube-system.svc:8443"
  filterVerb: filter
  prioritizeVerb: prioritize
  weight: 5
  enableHTTPS: true
  nodeCacheCapable: true     # send NodeNames only, not full Node objects — less bandwidth
  ignorable: false          # false ⇒ extender failure BLOCKS scheduling (§6, §11)

WHY THE FRAMEWORK REPLACED THIS FOR NEW WORK

The scheduling framework (stable since 1.19) exposes the same idea — Filter, Score, Reserve, Permit, PreBind, Bind, PostBind, plus PreFilter/PostFilter — as Go interfaces compiled into the scheduler binary, not network calls. Same extensibility goal, zero network hop, and a plugin can share the scheduler's cycle-scoped cache instead of re-deriving state per call. Extenders remain exactly one thing the framework never took away: the ability to extend scheduling without recompiling or redeploying kube-scheduler itself — which is still valuable for logic you don't control or don't trust enough to link into the scheduler's process.

(c) Cluster API — cluster lifecycle as CRDs, reconciled recursively

Cluster API (sigs.k8s.io/cluster-api) models a workload cluster the same way Kubernetes models everything else — as objects with a spec, watched by controllers that converge reality toward it:

YAMLthe core CAPI object graph, abbreviated
apiVersion: cluster.x-k8s.io/v1beta1
kind: Cluster
metadata: { name: prod-ap-south }
spec:
  controlPlaneRef:  { kind: KubeadmControlPlane,   name: prod-ap-south-cp }
  infrastructureRef: { kind: AWSCluster,           name: prod-ap-south-infra }
---
apiVersion: cluster.x-k8s.io/v1beta1
kind: MachineDeployment
spec:
  replicas: 6
  template:
    spec:
      bootstrap:     { configRef: { kind: KubeadmConfigTemplate } }
      infrastructureRef: { kind: AWSMachineTemplate }

Watch the recursion: the Cluster controller won't let a MachineDeployment's controller start creating worker Machines until both controlPlaneRef and infrastructureRef report ready — each of which is itself being reconciled by its own controller (the control-plane provider, e.g. KubeadmControlPlane; the infrastructure provider, e.g. the AWS/Azure/GCP provider). (d) virtual-kubelet — implementing the kubelet's contract, not a kubelet

A virtual-kubelet process registers a Node object and then keeps it looking alive with the same heartbeat mechanic a real kubelet uses — but everything below the Node API is a translation layer:

Go (interface shape)virtual-kubelet's PodLifecycleHandler
type PodLifecycleHandler interface {
    CreatePod(ctx context.Context, pod *v1.Pod) error       // → provider API call (e.g. ACI, Fargate)
    UpdatePod(ctx context.Context, pod *v1.Pod) error
    DeletePod(ctx context.Context, pod *v1.Pod) error
    GetPod(ctx context.Context, namespace, name string) (*v1.Pod, error)
    GetPodStatus(ctx context.Context, namespace, name string) (*v1.PodStatus, error)
    GetPods(ctx context.Context) ([]*v1.Pod, error)
}

Every one of those five methods is implemented by translating a Pod spec into calls against whatever backend the provider fronts — Azure Container Instances, AWS Fargate, a batch scheduler, even another Kubernetes cluster. The agent also applies a taint (conventionally virtual-kubelet.io/provider=azure:NoSchedule) so ordinary Pods don't land there by accident — only Pods that explicitly tolerate it, and that don't need anything the provider doesn't implement, are meant to run on it.

(e) GitOps controllers — the meta-reconcile loop, in real objects

YAMLargoproj.io/v1alpha1 Application — desired state one level up
apiVersion: argoproj.io/v1alpha1
kind: Application
spec:
  source:      { repoURL: git@github.com:org/fleet-manifests, path: services/api, targetRevision: main }
  destination: { server: https://prod-ap-south.example:6443, namespace: prod }
  syncPolicy:  { automated: { prune: true, selfHeal: true } }

The reconcile loop underneath, pseudocode-faithful to how ArgoCD's application-controller and Flux's kustomize-controller both actually work:

pseudocodeGitOps controller — one tick, one Application/Kustomization
function reconcileApplication(app):
    rev      = gitFetch(app.source.repoURL, app.source.targetRevision)
    desired  = render(rev, app.source.path)              // raw / kustomize / helm template
    live     = getLiveState(app.destination.server, app.destination.namespace)
    diff     = threeWayDiff(desired, live)              // same shape as ch.5's kubectl apply diff

    app.status.sync   = diff.empty ? "Synced" : "OutOfSync"
    app.status.health  = assessHealth(live)             // independent of sync: Healthy/Progressing/Degraded

    if (!diff.empty && app.syncPolicy.automated):
        applyDiff(app.destination, diff)               // THIS cluster only — see §15
        if (app.syncPolicy.automated.prune):
            deleteOrphans(app.destination, desired)

Read that function signature carefully: it takes one Application, targeting one destination cluster. A fleet of clusters is reconciled by running this function once per Application/cluster pair, on whatever interval or webhook trigger fires it — never as one global computation. §15's simulator makes that literal.

ARC 09 · TRADEOFFS

Three decisions, several honest ways to make each one

Read it as one lesson: push vs pull, and in-process vs out-of-process, are the two axes this whole chapter turns on. Pull-based, continuously-reconciling mechanisms (GitOps, the scheduling framework, Cluster API) trade some up-front simplicity for a running property — "currently matches desired state" — that push-based, one-shot mechanisms simply cannot claim between runs.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Where the latency goes, and where the privilege concentrates

Two independent axes matter here: how long a scheduling decision takes as you add extension points, and how much blast radius accumulates in the components that are allowed to act across an entire fleet.

  • In-process filter/score: dominated by the cost of iterating feasible nodes — roughly linear in node count per plugin, and Kubernetes' own scaling envelope (5,000 nodes / 150,000 Pods as the documented SLO ceiling, 110 Pods/node by default) is calibrated assuming this stays cheap. PodTopologySpread keeps a running per-domain count cache specifically so it doesn't have to rescan every Pod on every decision.
  • Extender webhook: add the network round trip — realistically single-digit to tens of milliseconds per call even on a healthy internal network, times the number of extenders configured, times however the scheduler batches candidate nodes per call. This is the single biggest reason new scheduling logic in 2020+ Kubernetes is written as a framework plugin rather than an extender whenever the source is under your control.
  • Cluster API reconcile cadence: like any controller (chapter 9), each CAPI controller's requeue interval and exponential backoff on error bound how quickly a broken Machine gets noticed and replaced — typically minutes, not seconds, which is the correct trade for infrastructure operations that are themselves slow (a cloud API call to launch an instance is not a microsecond operation).
  • GitOps sync interval vs webhook: polling git every few minutes is simple but adds latency between commit and reconcile; a push webhook from the git host closes that gap to seconds, at the cost of the controller now needing an externally-reachable endpoint — a new piece of attack surface per cluster or hub.

SECURITY: WHERE PRIVILEGE CONCENTRATES

The extender webhook receives full Pod specs and full Node inventories over the network — if enableHTTPS is left false or its certificate isn't verified, that's cleartext scheduling and capacity data crossing the wire, plus an unauthenticated path for something claiming to be the scheduler to influence placement. The Cluster API management cluster holds the cloud-provider credentials needed to create/destroy real infrastructure for every workload cluster it manages — compromise of that one cluster is compromise of your entire fleet's infrastructure control. A GitOps controller commonly needs cluster-admin-equivalent access on every destination cluster to apply arbitrary manifests — which means anyone who can merge to the watched repository, or exploit the controller itself, inherits that reach. §11 covers a real CVE built on exactly this last point.

ARC 11 · REAL-WORLD INCIDENTS

Four ways this chapter's mechanisms fail in production

1. CVE-2022-24348 — Argo CD Helm path traversal

Argo CD's repo-server, when rendering a Helm-based Application, accepted a crafted valueFiles entry (or a chart containing a symlink) that resolved outside the checked-out chart directory. Because the file-loading code trusted the resolved path without verifying it stayed within the chart's root, an attacker who could get any Application definition rendered — including via a public, unauthenticated Helm chart submitted for a legitimately shared Application — could make the repo-server read arbitrary files reachable from its filesystem, including other tenants' Secret-derived values and repository credentials mounted into that same pod. Root cause: path validation happened after path resolution, not before. Fix: canonicalize and verify the resolved path is a descendant of the chart directory before reading it — the same class of bug as a classic web app path-traversal, landing in a component that, per §10, already holds fleet-wide credentials.

2. The GitOps-vs-autoscaler fight

A team pins spec.replicas: 4 in the manifest an auto-syncing Application watches, while an HPA (chapter 12) independently mutates that same field based on live CPU. Every sync tick, the GitOps controller's three-way diff sees replicas as "drifted" from git's 4 and — if selfHeal is on — reverts it, fighting the HPA's own decision every few minutes; the HPA then scales it back up, and the two controllers oscillate the replica count indefinitely. Root cause: two independent reconciliation loops (chapter 9's pattern, doubled) both claim ownership of one field. Fix, and it's a real, documented ArgoCD/Flux feature for exactly this: an ignoreDifferences rule scoped to spec.replicas, telling the GitOps diff to treat live changes to that one field as expected, not drift.

3. A non-ignorable extender outage halts scheduling cluster-wide

A GPU-aware extender, wired in with ignorable: false because "GPU placement must never be wrong," starts timing out under its own load during a burst of GPU-job submissions. Because the scheduler calls extenders synchronously and ignorable: false means a failed call is treated as a hard scheduling failure rather than "skip this extender for this cycle," every pending Pod in the cluster — GPU workload or not — stops binding. Root cause: the availability of one narrow-purpose webhook was wired to be a precondition for all scheduling. Fix: the extender documentation's own recommendation — keep extenders ignorable: true wherever the cost of an occasional bad placement is lower than the cost of cluster-wide scheduling stalling, and move latency-critical, must-not-fail logic into an in-process framework plugin instead.

4. A new spread policy wedges a fleet with pre-existing zone imbalance

An SRE team rolls out maxSkew: 1 / topologyKey: zone / whenUnsatisfiable: DoNotSchedule fleet-wide as a best practice. One region's zone C had already lost a third of its node capacity to a prior spot-interruption wave that nobody had rebalanced (§6: constraints don't retroactively fix skew). The next routine rolling update in that region can no longer place replacement Pods in zone C without breaching maxSkew: 1 against the already-uneven baseline — and with DoNotSchedule, the scheduler does exactly what it's told: it leaves the new Pods Pending rather than violate the constraint, stalling the rollout. Root cause: a hard constraint was introduced without first fixing (or at least measuring) the existing distribution it would be judged against. Fix: roll out spread constraints as ScheduleAnyway first, observe the resulting skew for a full deploy cycle, and only flip to DoNotSchedule once the fleet is already close to even — or set minDomains deliberately to account for zones you know are temporarily thin.

Go (pseudocode)podtopologyspread/filtering.go — the actual skew test
func (pl *PodTopologySpread) Filter(ctx, state, pod, nodeInfo) *Status {
    tpCount := getPreFilterState(state)       // per-domain counts, built once per scheduling cycle
    for _, c := range tpCount.constraints {
        domain := nodeInfo.Node().Labels[c.TopologyKey]
        selfMatchCount := 1                    // this Pod would count toward its own domain
        matchNum := tpCount.NumPods(domain) + selfMatchCount
        minMatchNum := tpCount.MinDomainCount()
        skew := matchNum - minMatchNum
        if skew > c.MaxSkew {
            return Unschedulable("node(s) didn't satisfy topology spread constraint")
        }
    }
    return Success()
}
Go (pseudocode)schedule_one.go — where extenders sit relative to plugins
func (sched *Scheduler) scheduleOne(pod *v1.Pod) {
    feasibleNodes := framework.RunFilterPlugins(pod, allNodes)    // in-process: PodTopologySpread etc.

    for _, ext := range sched.extenders {                     // legacy path, IN ORDER, synchronous
        result, err := ext.Filter(pod, feasibleNodes)             // network hop — §10's latency line
        if err != nil {
            if !ext.Ignorable { return SchedulingFailed(err) }  // §11 incident #3
            continue                                        // ignorable: skip this extender this cycle
        }
        feasibleNodes = result.Nodes
    }

    priorities := framework.RunScorePlugins(pod, feasibleNodes)
    for _, ext := range sched.extenders where ext.PrioritizeVerb != "" {
        priorities = mergeWeighted(priorities, ext.Prioritize(pod, feasibleNodes), ext.Weight)
    }
    best := highestScored(priorities)
    framework.RunReservePermitPreBindBind(pod, best)              // Reserve → Permit → PreBind → Bind → PostBind
}
Go (pseudocode)cluster_controller.go — gating workers on infra + control plane
func (r *ClusterReconciler) reconcile(cluster *Cluster) {
    infra := get(cluster.Spec.InfrastructureRef)          // e.g. AWSCluster — its OWN controller reconciles it
    cp    := get(cluster.Spec.ControlPlaneRef)           // e.g. KubeadmControlPlane — also its own controller

    if !infra.Status.Ready || !cp.Status.Ready {
        cluster.Status.Phase = "Provisioning"
        return requeueAfter(20 * time.Second)      // come back later — never blocks synchronously
    }
    cluster.Status.Phase = "Provisioned"
    cluster.Status.ControlPlaneReady = true              // unblocks MachineDeployment controllers watching THIS field
}
WHY BUILT THIS WAY — TWO CHOICES TO STEAL

1. Extenders run strictly after in-process filters, never before. The cheap, fast, always-available logic narrows the field first; the expensive, possibly-unavailable network call only ever sees the survivors — minimizing how often the slow path runs. 2. Cluster API's controllers never block synchronously on each other. The Cluster controller requeues rather than waiting inline for the control plane — exactly chapter 9's level-triggered pattern, which is why a slow cloud API provisioning a control plane doesn't tie up a goroutine or a worker thread for however long that takes.
