Closures & Iterators:
Behavior as Data, Laziness by Default

Every time you write .sort_by(|a, b| ...), spawn a thread with a move || block, or chain .map().filter().collect(), you are leaning on two mechanisms the compiler builds for you at zero runtime cost: closures — anonymous, environment-capturing functions classified by exactly which of three traits they implement — and the Iterator trait, whose entire combinator ecosystem is built from one required method and a discipline of doing nothing until something actually asks for a value. This chapter derives both from first principles, follows the compiler into how a closure actually becomes a struct, and proves — mechanically, not by assertion — that an iterator chain is lazy all the way down.

ARC 01 · THE PROBLEM

How do you pass "a chunk of behavior" without a garbage collector?

You already know how to pass data as an argument. This chapter is about passing behavior — logic the callee doesn't know in advance, decided by the caller: how to compare two elements for a sort, what to do when a channel receives a message, which transformation to apply to every element of a million-row column. Every language answers this question; the interesting part is what each one has to give up to do it.

Unpack "pass behavior as data" and five real requirements fall out, each pulling in a different direction:

  • Ad hoc logic. The callee (a sort routine, a retry helper, an iterator combinator) must accept caller-supplied logic without the callee's author having predicted every case.
  • Access to local state. The passed-in behavior usually isn't a pure, self-contained function — it needs a threshold, an accumulator, a multiplier that lives in the caller's local scope, not in its own explicit parameter list.
  • No silent allocation. In a garbage-collected language, "just capture it, the collector will figure out when it's safe to free" is a free move. Rust has no collector: whatever a piece of behavior captures must be tracked by the same ownership and borrowing rules as everything else (chapters 4–5), and ideally cost nothing extra at runtime.
  • Composability. You want to chain several small operations — transform, then keep some, then transform again — over a sequence, without hand-writing a bespoke loop and a bespoke intermediate buffer for every single stage.
  • Compile-time verifiability. Whatever gets captured must still obey the borrow checker: no captured reference may outlive what it points to, and no two captured mutable accesses may alias. Passing behavior around cannot become a backdoor around ownership.

Rust's answer is two mechanisms that turn out to be the same idea applied twice. A closure is an anonymous, compiler-synthesized value that packages a function body together with whatever local state it reads or mutates — classified, not by what it captures, but by how invasively calling it touches that captured state, via one of three traits: FnOnce, FnMut, and Fn. The Iterator trait is what happens when you apply that same "package behavior with state" idea to walking a sequence: a tiny required contract, and an entire combinator library built on top of it that runs nothing until something actually pulls a value.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Closures and iterators are not a niche corner of Rust — they are the load-bearing machinery behind ?-based error handling combinators (chapter 13), the Future trait's poll method (chapter 16, which is exactly this chapter's "one required method, lazy until polled" pattern applied to async), and most of the ergonomic API surface of crates like serde and rayon. Understand the Fn hierarchy and the pull-based Iterator model now, and async's state machines in chapter 16 will feel like a rerun, not a new topic.

DEEP CONTEXT · THE "FUNARG PROBLEM"

Early Lisp (1958) let you pass a function as an argument, but a function referencing a free variable from its defining scope had an ambiguous meaning once that scope had returned — the funarg problem, debated through the 1960s–70s. Scheme (1975) settled it with true lexical closures: a function value captures the bindings from its defining environment, not the caller's environment at invocation time, and those bindings stay alive exactly as long as the closure that references them. Rust's borrow checker is, in a real sense, a compile-time proof system for making that same guarantee hold without a garbage collector keeping the captured bindings alive at runtime.

ARC 03 · NAIVE SOLUTION

Attempt #1: a raw function pointer and a context blob

Before closures existed as a language feature, this is how you passed "behavior plus state" — and it is still exactly what a C API looks like today. Step through it; each stage is real, either compiling C or Rust that rustc genuinely rejects for the reason shown.

Function pointers vs. captured stateSTEP-BY-STEP

The C version works — it is the shape of qsort, pthread_create, and most C callback APIs ever written. It also already shows the cost of not having a real closure type: the "captured state" is a raw, untyped void* that the callback must cast back to the right type by hand, and nothing checks that the cast is correct or that the pointed-to memory is still alive.

ARC 04 · WHY IT FAILS

Two failure modes: a real bug class, and a real category error

The C shape and the naive Rust shape fail for different reasons, and both are worth internalizing precisely — they are exactly the two problems closures were designed to solve simultaneously.

THE C BUG CLASS: UNTYPED CONTEXT POINTERS

A void* context parameter is a contract enforced by nothing but convention. Two real, named weaknesses: type confusion (CWE-843) when a callback is registered with the wrong context type and casts it wrong, and use-after-free (CWE-416) when the context is freed before every registered callback holding a pointer to it has finished running. Both classes show up repeatedly in real CVE databases for C libraries with callback-based APIs — not because programmers are careless, but because the type system gives the compiler nothing to check.

The naive Rust attempt fails for a completely different, much more interesting reason: it isn't a missing annotation, it's a fact about representation. A fn pointer type in Rust is exactly a machine word — the address of a chunk of code, nothing else. It has no field, no extra byte, no side-channel in which to smuggle a captured value. A closure that reads or mutates a local variable needs somewhere to store that variable's value or reference between the point it's created and the point it's called — and an address-sized fn pointer has nowhere for that to live. This is why rustc's error isn't "add an annotation," it's "these two things are not the same shape":

rustc — the real diagnostic for the naive attempt
error[E0308]: mismatched types
 --> src/main.rs:2:5
  |
1 | fn make_adder(amount: i32) -> fn(i32) -> i32 {
  |                                --------------- expected `fn(i32) -> i32` because of return type
2 |     |x| x + amount
  |     ^^^^^^^^^^^^^^ expected fn pointer, found closure
  |
  = note: closures can only be coerced to `fn` types if they do not capture any variables

Read that note literally: it is a completely general rule, not specific to this example. Any closure that captures nothing at all — |x| x + 1 — coerces to a plain fn pointer for free, because it truly needs no extra storage. The moment a closure captures so much as one i32, it needs a real payload, and Rust's answer is to give every capturing closure its own compiler-generated struct type instead of trying to force it through a fixed-size function pointer. Section 8 shows exactly what that struct looks like.

ARC 05 · CLOSURES, DERIVED

From "give it storage" to three traits

Derive the real design. If a capturing closure needs its own struct to hold what it captures, two questions follow immediately: how does it capture each variable (by reference? by value?), and how invasively does calling it touch what it captured? Step through five closures, each one real, compiling Rust, each one answering those two questions a little differently.

Building up: capture modes and the Fn hierarchySTEP-BY-STEP
THE RULE THE COMPILER ACTUALLY FOLLOWS

Rust infers the least restrictive capture mode that makes the closure body compile: it tries a shared reference (&T) first, then a mutable reference (&mut T) if the body needs to mutate, and only falls back to taking ownership if the body needs to consume the value or if you force it with the move keyword. This is the same "borrow before you own" instinct chapters 4–5 taught you for ordinary references, applied to an anonymous struct instead of a named one.

ARC 06 · WHY THAT STILL HAS COSTS

The bill: verbosity, boxing, and errors that read like riddles

Closures-as-structs-implementing-traits is a genuinely good design, but be honest about what it costs — every cost below is a direct, traceable consequence of the mechanism from §5, not an oversight:

  • Trait-bound signatures get verbose fast. A function that accepts a closure must spell out which trait and what signature: fn retry<F: FnMut() -> Result<(), Error>>(mut f: F). A dynamically typed or garbage-collected language just writes "a function argument" — Rust's version carries real information (dispatch strategy, mutability requirement) but it is undeniably more to type and more to read.
  • Borrow-checker errors involving closures are some of the least beginner-friendly in the language. Moving a captured, non-Copy value out of an Fn-classified closure body produces error[E0507]: cannot move out of `name`, a captured variable in an `Fn` closure — accurate, but it requires already understanding the Fn/FnMut/FnOnce hierarchy from §5 to parse.
  • Heterogeneous closures reintroduce the exact costs being avoided. A generic, trait-bounded parameter gives one monomorphized, inlinable copy per concrete closure type (chapter 8's mechanism, again) — but a Vec of *different* closures with the same signature (a plugin table, a list of event handlers) cannot be one concrete generic type. The fix, Vec<Box<dyn Fn(i32) -> i32>>, brings back a heap allocation per closure and a vtable-indirected call per invocation — precisely the "GC'd language closure" cost model, opted into deliberately when true runtime polymorphism is required.
  • Iterator chains are only free after optimization. §10 shows the real gap: a chain of .map().filter() compiled with cargo build (debug, no inlining) is measurably slower per element than the same chain built with --release, because "zero-cost" describes what LLVM produces after inlining collapses the adaptor layers — not what the unoptimized call graph looks like.

None of this is a defect in the design so much as an honest accounting: Rust chose to make the cost of behavior-as-data visible in the type signature (which trait, which dispatch strategy) rather than hidden behind a garbage collector and a uniform "function value" type. §9 compares that choice against what other languages did instead.

WHY THE SUPERTRAIT DIRECTION IS FnOnce ⊆ FnMut ⊆ Fn, NOT THE REVERSE

In real Rust, the declarations are trait FnMut<Args>: FnOnce<Args> and trait Fn<Args>: FnMut<Args> — Fn is the most restrictive trait to implement (its call takes only &self, so it must never need unique or owned access to anything), and every Fn closure gets FnMut and FnOnce for free by definition: if you can call something repeatedly through a shared reference, you can trivially also call it once through a mutable reference or by value. The hierarchy is built around "how little access does a call need," and less-invasive access is strictly more broadly usable — which is exactly why generic code that only needs to call a closure once should bound it with the most permissive trait, FnOnce, not reflexively reach for Fn.

(b) The Iterator trait: one method, real code, real laziness

Now the payoff: an entire family of combinators (map, filter, fold, sum, collect, dozens more) is not implemented per-type.   next one. §15's simulator makes that difference impossible to miss.







  
ARC 10 · PERFORMANCE CHARACTERISTICS

  
Testing the zero-cost claim directly

  
"Iterators are a zero-cost abstraction" is a specific, falsifiable claim: that
  for i in 0..v.len() { v[i] = v[i] * 2; } and v.iter_mut().for_each(|x| *x *= 2)

  to see through every layer: Map::next() calling self.iter.next().map(&mut self.f),
  the closure call, the Option matching — and inline all of it into one tight loop with no function
  calls left at all. That inlining is an optimization pass, not a language guarantee, and it is exactly what

ARC 11 · REAL-WORLD PRODUCTION

  
Three stories every working Rust programmer eventually lives through


  
Incident 1: the edition that had to fix its own closures

  
Before the Rust 2021 edition, a closure referencing self.field captured the entire
  self value, not just that field — because pre-2021 closures could only capture whole paths rooted
  at a variable, never a sub-field of one. In real code this produced spurious borrow-checker errors: two closures
  each touching a different field of the same struct would fight over "who borrows self,"
  even though the fields themselves never conflicted. RFC 2229 — disjoint closure captures fixed this by
  making closures capture only the precise fields their body actually uses, and shipped as an edition-gated
  change (opt-in via edition = "2021" in Cargo.toml, since it can change
  Drop order for structs whose fields are individually captured). It is a rare, well-documented
  example of a systems language changing its own core capture semantics after a decade in production, purely to
  fix ergonomics that real codebases kept hitting.


  
Incident 2: combinator-shaped generics and the compile-time tax

  
The same monomorphization mechanism that makes Map<Filter<I, P>, F> zero-cost at
  runtime (§8, §10) has a well-known downside at compile time: crates whose APIs are built from deeply nested,
  combinator-style generics — Diesel's query builder is the community's most commonly cited example — are
  notorious for extremely long, deeply nested type names appearing in error messages, and for measurably
  contributing to whole-crate compile times on large projects. It is not a bug in any one crate; it is the direct,
  structural cost of the same "one new generic type per chained call" design this chapter's iterator adaptors use,
  applied to a much larger combinator surface. Multiple Rust community surveys have repeatedly ranked long compile
  times and hard-to-read generic error messages among the top reported pain points of the language.


  
Incident 3: the "why won't my closure spawn" onboarding wall

  
std::thread::spawn (and tokio::spawn) both require their closure/future argument
  to be 'static — it may not borrow anything from the spawning function's stack, because the spawned
  task can legitimately outlive that function's return. Nearly every Rust programmer's first attempt at spawning
  a thread borrows local data and hits it head-on:

  

    
the single most common early-onboarding compile error in Rust

    
error[E0373]: closure may outlive the current function, but it borrows `data`, which is owned by the current function
 --> src/main.rs:4:33
  |
4 |     let handle = thread::spawn(|| {
  |                                 ^^ may outlive borrowed value `data`
5 |         println!("{:?}", data);
  |                          ---- `data` is borrowed here
  |
help: to force the closure to take ownership of `data` (and any other referenced variables), use the `move` keyword

  

  
The fix rustc suggests — move || — works exactly because §5 explained why: moving transfers
  ownership into the closure's own struct, so there is no longer a borrow that could outlive anything. When the
  data needs to be shared with code that keeps running after the spawn (not just handed away), the standard,
  Tokio-documented next step is cloning an Arc handle before the move block — each
  task then owns its own reference-counted handle instead of borrowing anyone else's stack.

First, the trait hierarchy from §5 and §7, exactly as declared in core::ops::function (the
  extern "rust-call" ABI and the ability to implement these traits yourself both require the
  unstable unboxed_closures/fn_traits features — but the declarations themselves are the
  real, stable-compiled definitions every closure in every Rust program satisfies):


  

    
Rustcore/src/ops/function.rs — the real hierarchy

    
pub trait FnOnce<Args> {
    type Output;
    extern "rust-call" fn call_once(self, args: Args) -> Self::Output;
}

pub trait FnMut<Args>: FnOnce<Args> {
    extern "rust-call" fn call_mut(&mut self, args: Args) -> Self::Output;
}

pub trait Fn<Args>: FnMut<Args> {
    extern "rust-call" fn call(&self, args: Args) -> Self::Output;
}

  

  
The supertrait direction is the whole story: FnMut requires FnOnce, Fn
  requires FnMut. Any type implementing Fn gets a free, trivial FnMut
  impl (call through &mut self by reborrowing the &self the real
  call needs) and a free FnOnce impl (call once, then drop self) — which is
  precisely why every closure you've ever written satisfies FnOnce whether it says so or not.


  
Now the Iterator trait's required method and two of its default combinators, simplified from the real
  core::iter::traits::iterator source but faithful to its actual shape and default-method style:


  

    
Rustcore/src/iter/traits/iterator.rs — simplified

    
pub trait Iterator {
    type Item;

    // THE only required method. Everything else is provided,
    // and every provided method is implemented purely in terms
    // of calls to this one.
    fn next(&mut self) -> Option<Self::Item>;

    fn map<B, F>(self, f: F) -> Map<Self, F>
    where Self: Sized, F: FnMut(Self::Item) -> B {
        Map::new(self, f)          // stores `self` + `f`; does nothing yet
    }

    fn filter<P>(self, predicate: P) -> Filter<Self, P>
    where Self: Sized, P: FnMut(&Self::Item) -> bool {
        Filter::new(self, predicate)   // stores `self` + `predicate`; does nothing yet
    }

    fn fold<B, F>(mut self, init: B, mut f: F) -> B
    where Self: Sized, F: FnMut(B, Self::Item) -> B {
        let mut accum = init;
        while let Some(x) = self.next() {   // the ONLY place this loop pulls from
            accum = f(accum, x);
        }
        accum
    }

    // collect(), sum(), count(), last(), for_each() … ~70 more,
    // nearly all ultimately built on next() or on fold().
}

  


  
And the two adapters that make .map()/.filter() actually pull, matching real
  core::iter::adapters source closely enough to read the originals cold:


  

    
Rustcore/src/iter/adapters/{map,filter}.rs — the real pull mechanism

    
impl<B, I: Iterator, F> Iterator for Map<I, F>
where F: FnMut(I::Item) -> B {
    type Item = B;
    fn next(&mut self) -> Option<B> {
        self.iter.next().map(&mut self.f)   // pull ONE from upstream, transform it
    }
}

impl<I: Iterator, P> Iterator for Filter<I, P>
where P: FnMut(&I::Item) -> bool {
    type Item = I::Item;
    fn next(&mut self) -> Option<I::Item> {
        self.iter.find(&mut self.predicate)  // find() itself loops on next() until
    }                                             // the predicate matches or upstream ends
}

  


  

    
THE LINE THAT PROVES §15's SIMULATOR HONEST

    
Filter::next() is not "check the next element" — it is "pull from upstream, in a loop,
    until one element passes or upstream is exhausted." That single line is the entire mechanical reason one
    call to collect() can trigger many more than one call to the source iterator's next().
    There is no separate "skip" logic anywhere — rejection is just a loop iteration inside find that
    pulls again. §15 makes you watch this line execute, one pull at a time.
