RABBITMQ INTERNALS · CHAPTER 09

Flow Control &
Memory Management

Every RabbitMQ node is, underneath the AMQP model, a chain of ordinary Erlang processes — a reader, a channel, a queue — each with a mailbox that will accept messages forever unless something tells it to stop. Nothing in the BEAM enforces a mailbox ceiling. This chapter is about the subsystem that supplies that "stop": credit-based flow control between processes, and memory/disk alarms at the node level — the two mechanisms that decide whether a publisher outrunning its consumers degrades a node gracefully or kills it.

ARC 01 · THE PROBLEM

An unbounded mailbox is a promise the runtime is happy to keep, right up until the OOM killer arrives

Chapter 1 established the fact this whole course keeps returning to: a RabbitMQ node is not one program juggling shared state, it's a supervision tree of independent BEAM processes — one per connection (rabbit_reader), one per channel (rabbit_channel), one per classic queue (rabbit_amqqueue_process) — each with its own private heap and its own mailbox, talking to each other exclusively by asynchronous message passing. That isolation is the reason a bug in one queue doesn't crash a node. It is also, left unmodified, the reason an overloaded node dies slowly and then all at once.

Here is the mechanism, stated plainly: an Erlang mailbox has no built-in capacity limit. Pid ! Msg always succeeds from the sender's point of view — the runtime will happily let a mailbox grow to millions of entries if nothing ever calls receive fast enough to drain it. A publisher pushing 50,000 messages/second into a queue whose single consumer processes 5,000/second isn't hitting an error; it's accumulating 45,000 unconsumed messages every second inside that queue process's heap, and every one of them is live data the garbage collector cannot discard. Multiply by message size, multiply by how long the mismatch persists, and you get a straight line toward the node's total available memory — with nothing structural stopping it.

  • The mismatch doesn't need to be dramatic. A consumer that's merely 10% slower than its publisher, sustained for an hour, accumulates an hour's worth of the deficit — messages don't need to stop being consumed, they just need to arrive faster than they leave.
  • The failure is not local to the slow queue. Once total node memory pressure rises, the entire node's behavior needs to change — not just the one queue that's the proximate cause — or every other queue's messages get evicted right alongside the culprit's when the OS finally intervenes.
  • "Just add more RAM" doesn't fix the shape of the problem. It moves the wall further away; it doesn't remove the wall. Any fixed amount of memory is finite, and a sustained rate mismatch is, by definition, unbounded over time.
THE FAILURE MODE, UNSOFTENED

Without any counter-pressure, the sequence is: queue process heap grows past sane limits → node-wide memory pressure rises → the BEAM's own garbage collector works harder and more often across every process on the node (not just the growing one) → scheduler latency degrades broadly → eventually the Linux OOM killer (or the container runtime's cgroup limit) kills the beam.smp process outright, taking every connection, channel, and queue on that node down simultaneously — the exact all-or-nothing failure the process-isolation model in chapter 1 was supposed to prevent, reintroduced through the one resource (physical memory) that isolation cannot fence off, because every process's heap still competes for the same finite RAM.

So the problem this chapter solves has two layers, and RabbitMQ answers them with two distinct mechanisms that this chapter treats as a matched pair: (a) stop an individual fast producer from unboundedly outrunning an individual slow consumer, hop by hop, before memory pressure ever becomes node-wide — that's credit-based flow control; and (b) as a last-resort, node-wide backstop, detect when total memory or disk pressure is becoming dangerous regardless of any single hop's behavior, and forcibly stop all publishing until the node drains — that's the memory and disk alarms. §5 onward derives both from first principles.

DEEP CONTEXT · WHY THIS ARRIVED LATE, NOT AT AMQP'S BIRTH

AMQP 0-9-1 itself defines almost nothing about broker-internal backpressure — it defines channel.flow, a coarse per-channel on/off signal a broker can send a client, and that's it. Everything this chapter actually studies — credit_flow, memory watermarks, disk limits — is RabbitMQ's own implementation-side answer to a problem the wire protocol never had to solve, because the protocol doesn't care how a broker manages its own processes' mailboxes internally. That's precisely why this material lives in "internal implementation," not "the protocol": a different AMQP 0-9-1 broker (Qpid, for instance) is free to solve the exact same physical problem completely differently, and does.

ARC 03 · NAIVE SOLUTION

Attempt #1: trust the mailbox, no gate anywhere

Derive it the way it would be written by someone who hasn't yet been burned. A channel receives a Basic.Publish, routes it, and forwards the decoded message to the target queue process with a plain gen_server:cast/2 (or, in real RabbitMQ code, gen_server2's async cast) — fire and forget, no acknowledgement that the queue is keeping up, no throttle if it isn't.

Erlangnaive_channel.erl — the strawman, annotated
handle_cast({method, #'basic.publish'{routing_key = RK}, Content}, State) ->
    QPids = rabbit_exchange:route(State#ch.exchange, RK),
    %% Every target queue gets an async cast, unconditionally.
    %% There is no question asked, no answer waited for, no
    %% signal anywhere that says "that queue is 4 million
    %% messages behind — maybe don't send a 4-million-and-first."
    [gen_server2:cast(QPid, {deliver, Content}) || QPid <- QPids],
    {noreply, State}.

%% naive_reader.erl — the socket loop feeding the channel the same way:
loop(Socket, ChannelPid) ->
    {ok, Data} = gen_tcp:recv(Socket, 0),
    Frame = parse_frame(Data),
    gen_server2:cast(ChannelPid, {frame, Frame}),  %% same story: no throttle
    loop(Socket, ChannelPid).

This is not a strawman built to lose — it's the honest first draft, and for a demo, a load test with a fast consumer, or a queue that's never meaningfully behind, it works fine and is simpler than anything this chapter builds toward. The trouble only shows up under the one condition every production system eventually hits: sustained publish rate above sustained consume rate. The stepper below plays that forward.

ARC 04 · WHY IT FAILS

The math: backlog grows at (publish rate − consume rate), and that number is rarely zero

Formalize what the deck just showed. Let P be the sustained publish rate in messages/second, C be the sustained consume (ack) rate, and S be the average message size in bytes. If P > C, the queue's resident message count grows at (P − C) messages/second, and its memory footprint grows at (P − C) × S bytes/second, indefinitely, with nothing in the naive design ever pushing back.

  • A concrete number. P = 20,000 msg/s, C = 15,000 msg/s, S = 2 KB: backlog grows at 5,000 msg/s × 2 KB = ~10 MB/second. On a node with 4 GB available to RabbitMQ before the watermark bites, that's roughly ~410 seconds — well under seven minutes — from a completely healthy-looking node to the memory alarm, and if nothing intervenes before that, to the OOM killer.
  • The mismatch doesn't require a dramatic failure. A single slow consumer instance restarting for a deploy, a downstream API call inside the consumer's processing loop that starts timing out, a GC pause on the consumer's own runtime — any of these silently flips a previously-balanced P ≈ C into P > C, and the naive design has no way to notice until memory is already critical.
  • It isn't just the one queue's memory. The channel process holding a reference to in-flight Content records, the connection's outbound buffers, and (per chapter 1) the fact that BEAM-wide memory pressure degrades scheduling and GC pause behavior for every process on the node — a single queue's naive unbounded growth is a node-wide risk, not a contained one.
  • There is no natural circuit breaker. TCP itself will eventually apply backpressure to a socket whose reader stops calling recv — but in the naive design above, the reader never stops calling recv. It keeps accepting bytes off the wire and casting them onward regardless of downstream state, so the one piece of natural backpressure the kernel could offer for free is never engaged.
THE NUMBERS, GENERALIZED

Time-to-alarm ≈ available_memory / ((P − C) × S). Every term on the right is something an operator can usually observe (queue depth trend, message size, memory headroom) — which is exactly why RabbitMQ's own operational guidance treats "queue depth trending upward over minutes" as an actionable signal long before memory is actually critical. The naive design's failure isn't that this formula exists — it's that nothing acts on it until the OS does, at which point every process on the node pays the price together.

Two independent fixes are needed, and it's worth separating them the way §5–§6 will: (a) give each hop in the chain a way to say "stop sending to me, I'm behind" before its own mailbox becomes dangerous, and (b) give the node itself a last-resort way to say "no more publishing, anywhere, until I've recovered," in case (a) still isn't enough or a genuinely new failure mode outruns it. §5 builds (a); §7 completes the picture with (b).

ARC 05 · BETTER SOLUTIONS, EXAMINED

Deriving credit-based flow control from the candidates that don't survive contact

Walk the space of fixes in the order a team would actually propose and reject them, arriving at what RabbitMQ actually ships.

From "let the mailbox grow" to a per-pair credit ledgerSTEP-BY-STEP

What survives: credit_flow, a token bucket between every sender/receiver pair

RabbitMQ's actual mechanism, implemented in the shared credit_flow module (in rabbit_common, used by rabbit_reader, rabbit_channel, and rabbit_amqqueue_process alike), is a token bucket tracked per sender/receiver pair, kept in the sending process's own process dictionary. Each receiver grants its senders an initial credit allowance — illustratively 400 messages — and a more-credit threshold — illustratively 200 — meaning: once the sender has consumed half its allowance, the receiver, once it has actually processed that many, tops the sender's credit back up toward 400 rather than waiting for it to hit zero. A sender decrements its own local credit counter by one for every message it forwards; when that counter reaches zero, the sender blocks — it stops forwarding entirely — until a credit-bump arrives.

  • It's symmetric and composable. The exact same credit_flow:send/1 / credit_flow:ack/1 pair is used between reader↔channel and between channel↔queue — one mechanism, reused at every hop in the chain, rather than a bespoke throttle per relationship.
  • It's local and cheap. No global broker-wide lock or coordinator — each pair's credit state lives in the sender's own process dictionary, checked and decremented on the sender's own reduction budget, with no cross-process synchronization beyond the credit-bump message itself.
  • It converts an unbounded mailbox into a bounded one, structurally. A blocked sender simply stops calling gen_server2:cast — the receiving process's mailbox can never grow past whatever was already in flight when credit hit zero, regardless of how far upstream the imbalance originated.
WHY A TOKEN BUCKET, NOT A SYNCHRONOUS QUESTION-ANSWER PROTOCOL

The obvious alternative — have the sender gen_server:call the receiver before every single send, waiting for a "yes, send it" reply — would work, but it round-trips a message for every message sent, doubling inter-process traffic and adding a full mailbox round-trip of latency to every publish, even when the receiver is nowhere near overloaded. A credit ledger amortizes that cost: the sender only needs to hear from the receiver once per hundreds of messages (whenever the more-credit threshold is crossed), not once per message — the same batching insight behind TCP's sliding window, applied between Erlang processes instead of network hosts.

ARC 06 · WHY THAT STILL COSTS

The bill for a shared TCP socket underneath independent credit ledgers

credit_flow solves §4's unbounded-growth problem, but it introduces a structural property that is easy to miss until it costs you an incident: the credit chain is per-connection, not per-queue. Every cost below is a direct consequence of that fact.

  • One reader process serializes the whole connection. A connection has exactly one rabbit_reader, and it reads bytes off exactly one TCP socket, one frame at a time, in order. If the reader's own credit toward even one channel on that connection is exhausted long enough that the reader stops draining the socket, every other channel multiplexed over the same connection stops receiving new frames too — not because those other channels or their queues are unhealthy, but because nothing downstream of a stalled reader can be parsed until the reader resumes reading.
  • This makes "one slow queue" a connection-wide, not queue-wide, incident. A publisher pushing to ten queues over one connection, nine of them perfectly healthy, can have all ten stop making progress because the tenth queue's consumer fell behind — the exact anti-pattern the spec for this chapter calls out, and precisely why sharing one connection across unrelated workloads is a documented operational hazard, not a theoretical one (§9, §11 return to this with real guidance).
  • Credit thresholds themselves are a tuning surface with real failure modes. An initial credit allowance set too high delays the first backpressure signal until a lot of memory is already committed; set too low, and legitimate short bursts trigger blocking (and the client-visible "flow" state) far more often than the actual risk warrants — false positives that look like an outage to an on-call engineer who hasn't seen this state before.
  • credit_flow alone doesn't answer the node-wide question. Even with every individual hop perfectly credit-controlled, a broker with thousands of queues each holding a moderate, "acceptable" backlog can still sum to node-threatening memory pressure — credit flow bounds any one chain's growth, it does not bound the sum across all chains on the node. That's precisely the gap the memory and disk alarms in §7 exist to close.
THE HONEST TRADE

None of this argues against credit_flow — it's the actual price of converting "unbounded mailbox growth" into "bounded, but now connections can stall as a unit." That's a trade RabbitMQ makes deliberately: a stalled connection is recoverable (drain the slow consumer, or reconnect on a different connection) in a way that node death is not. The final architecture, then, needs both layers: credit_flow for hop-by-hop, chain-local backpressure, and a node-wide memory/disk alarm as the backstop for the case credit_flow cannot see — the aggregate. §7 puts both onto one map.

DEEP CONTEXT · THE ONE FRAME THAT LEAVES THE NODE

Everything in the "per-hop credit chain" row is entirely internal — no AMQP 0-9-1 frame on the wire tells a client "channel X is now flow-controlled toward queue Y." The only externally visible signal in this entire subsystem is connection.blocked (and its counterpart connection.unblocked), a RabbitMQ-specific AMQP extension sent when the node-wide alarm fires — and it's connection-wide, not per-channel, which is consistent with everything §6 just derived: the alarm blocks the whole connection's ability to publish, full stop, precisely because by the time it fires, hop-by-hop credit control was insufficient and something coarser is required.

ARC 08 · INTERNAL IMPLEMENTATION

Credit ledgers, alarm thresholds, and the propagation path from queue to socket

(a) The credit_flow protocol, precisely

Two message shapes carry the entire protocol. A sender wraps every unit of work it forwards with credit_flow:send(Msg), which does two things: sends Msg to the receiver as normal, and decrements a counter kept under the key {credit_to, ReceiverPid} in the sender's own process dictionary. When that counter reaches zero, the sender records itself as blocked toward that receiver (key {credit_blocked, ReceiverPid}) and — critically — stops calling send for that receiver until told otherwise. On the receiving side, whenever the receiver has actually processed InitialCredit − MoreCreditAfter messages from a given sender (illustratively, after processing 200 of an initial 400), it calls credit_flow:ack(SenderPid), which sends a small, out-of-band "bump credit" message back to the sender, restoring its counter and unblocking it if it had stopped.

(b) Memory alarms: watermark, paging ratio, and the alarm itself

Independently of any single credit chain, vm_memory_monitor polls total memory in use by the Erlang VM (via erlang:memory/0 and OS-level introspection) against vm_memory_high_watermark — a fraction of detected total system RAM, defaulting to 0.6 (60%). Crossing that threshold makes vm_memory_monitor call rabbit_alarm:set_alarm({{resource_limit, memory, node()}, []}), which every rabbit_reader on the node is subscribed to; each reader responds by sending its clients a connection.blocked frame and — the actual mechanism — stops issuing further {active, N} socket reads, so it simply never asks the kernel for more publish traffic on that connection again until the alarm clears. Consuming is unaffected: deliveries and acknowledgements flow in the other direction and don't grow memory, so the node keeps draining while it refuses new inbound publishes — the entire point of the alarm is to buy the node time to shrink back under the watermark using exactly the traffic (consumption) that reduces pressure, while refusing the traffic (publishing) that increases it.

Before that hard alarm, vm_memory_high_watermark_paging_ratio (default 0.5) defines a softer threshold at watermark × paging_ratio of detected RAM — by default, 30% of total RAM (half of the 60% hard line). Crossing that line doesn't block anyone; it tells classic queues to start paging their message bodies out of the process heap and onto disk (the same on-disk representation rabbit_msg_store uses for persistent messages generally, chapter 5's territory), trading query latency for headroom — the node degrades gracefully in throughput terms well before it has to degrade in availability terms.

DISK ALARMS: THE SAME MECHANISM, A DIFFERENT RESOURCE

rabbit_disk_monitor watches free disk space on the node's data directory against disk_free_limit, whose default is expressed relative to detected RAM rather than a fixed byte count — because the amount of disk headroom you need scales with how much could ever need to be paged out of memory onto disk, which itself scales with installed RAM, not with an arbitrary constant like 50 MB that made sense on one generation of hardware and not the next. Crossing the disk limit raises the exact same rabbit_alarm plumbing and produces the exact same client-visible connection.blocked behavior as the memory alarm — from a client's perspective, "the node is low on memory" and "the node is low on disk" are indistinguishable without checking rabbitmq-diagnostics directly.

The pattern that survives scrutiny: systems that write straight to durable, sequential storage (Kafka, Pulsar's BookKeeper tier, SQS) mostly sidestep this entire chapter's problem, because a slow consumer just reads older data rather than causing broker-process memory to grow. ARC 10 · PERFORMANCE CHARACTERISTICS

What you can predict about cost, before ever running a benchmark

  • Credit-check cost is O(1) per message. A process dictionary lookup and decrement on every send — constant time, independent of how many messages are already queued anywhere in the chain, and independent of how many other sender/receiver pairs exist on the node.
  • Credit-bump cost is O(1) amortized per message, not O(n). Because a bump only fires once per MoreCreditAfter messages processed (illustratively every 200), the actual message rate of "bump credit" signals is a small constant fraction — around 1-in-200 here — of the total throughput, not one control message per data message.
  • Per-process memory during backpressure is bounded, not zero. A blocked sender's own mailbox can still hold whatever was in flight before credit hit zero, plus whatever accumulates from other unrelated senders that haven't yet blocked — credit_flow bounds growth toward one receiver, it does not shrink what's already resident.
  • Paging trades memory for disk I/O and increased consume-path latency. A paged-out message must be read back from rabbit_msg_store before delivery, which is strictly slower than delivering straight from the queue process's heap — paging is a throughput/latency cost accepted specifically to avoid the much worse cost (a full outage) of hitting the hard alarm.
  • Memory alarm checks themselves are cheap and infrequent relative to per-message credit checks — vm_memory_monitor polls on a timer (on the order of every few seconds by default), not on every publish, because total node memory is a slowly-changing aggregate, not a per-message signal.

ARC 11 · REAL-WORLD PRODUCTION

Where this subsystem shows up in real incidents and real diagnosis

Story 1: the "Flow" channel state that on-call engineers misread as broken

RabbitMQ's own management UI and rabbitmqctl list_channels report a channel's state as flow whenever credit_flow has it blocked toward at least one downstream queue — officially documented broker behavior, not a bug. It is one of the most commonly misdiagnosed signals in RabbitMQ operations precisely because it looks alarming ("this channel isn't running!") while actually being the system working as designed: a channel in flow is being deliberately, correctly throttled by a slow queue downstream. RabbitMQ's own documentation devotes an entire section to explaining this exact distinction, because the instinct to "fix" a channel stuck in flow by restarting the connection usually just relocates the same backpressure to a fresh connection without addressing the actual slow consumer.

Story 2: container memory-detection mismatches that make the watermark meaningless

Because vm_memory_high_watermark's default is a fraction of detected RAM, its correctness depends entirely on correct detection — and for years, RabbitMQ nodes running inside Docker containers or other cgroup-limited environments would detect the host's total physical RAM rather than the container's actual cgroup memory limit, computing a watermark against a number many times larger than what the process could actually use. A node configured with a 60% watermark against a falsely-detected 64 GB host, while actually capped at a 2 GB container limit, could be killed by the cgroup OOM killer long before its own internal alarm ever had a reason to fire — the alarm mechanism working perfectly against the wrong denominator. This is real, long-documented behavior that drove RabbitMQ to improve container/cgroup-aware memory detection in later 3.6.x and 3.7.x releases, and it remains a standard checklist item (total_memory_available_override_value as the manual escape hatch) when deploying RabbitMQ under Kubernetes resource limits.

Story 3: binary memory that "won't go away," and the Erlang-wide diagnostic playbook

A recurring, well-documented Erlang operational pattern — not unique to RabbitMQ, but squarely applicable to it — is elevated memory in the binary category of rabbitmq-diagnostics memory_breakdown that doesn't shrink even after queues drain. Reference-counted ("refc") binaries larger than 64 bytes live on a shared binary heap; a process only releases its reference when that process runs a garbage collection, so a long-lived process (a channel or connection that rarely triggers a full sweep) can hold references to large message bodies well after it has any logical use for them, inflating the binary category without any single object being "leaked" in the traditional sense. Fred Hebert's widely-read operational text Erlang in Anger — written from real production Erlang/OTP debugging experience — documents this exact failure mode and the standard remedy using the recon library's recon:bin_leak/1, which forces GC across processes and reports which ones actually release the most binary memory; the same technique applies directly to a RabbitMQ node showing high binary memory with no obvious queue backlog to explain it.

Story 4: lazy queues, and later, the default that made this whole chapter less urgent

RabbitMQ 3.6 (2016) introduced lazy queues (x-queue-mode: lazy) specifically as an operator-facing mitigation for the exact failure mode this chapter opens with: a queue mode that writes messages straight to disk as they arrive and keeps only a small window in memory, trading per-message latency for a queue that simply cannot accumulate an unbounded in-memory backlog regardless of how far its consumer falls behind. That the ecosystem needed a dedicated queue mode for this — rather than relying on credit_flow and the memory alarm alone — is itself evidence for §6's honest admission that hop-by-hop credit control and a coarse node-wide alarm don't fully solve every operational shape of this problem; classic queues' newer message store (introduced as "queue version 2" starting in 3.12) folds much of lazy-queue-like disk-first behavior into the default, reducing how often operators need to reach for the explicit mode at all.

First, the credit_flow ledger itself — the mechanism every hop reuses:

Erlangcredit_flow.erl — send/1 and ack/1, simplified
send(Receiver) ->
    %% Decrement this sender's own credit toward Receiver, kept entirely
    %% in THIS process's dictionary -- no cross-process lock required.
    Credit = get({credit_to, Receiver}, ?DEFAULT_INITIAL_CREDIT) - 1,
    put({credit_to, Receiver}, Credit),
    case Credit =< 0 of
        true  ->
            %% Out of credit: mark ourselves blocked toward this one receiver.
            %% We do NOT crash or drop the message -- we simply stop calling
            %% send/1 again for Receiver until a bump arrives.
            put({credit_blocked, Receiver}, true),
            blocked;
        false -> ok
    end.

ack(Sender, InitialCredit, MoreCreditAfter) ->
    %% Called by the RECEIVER once it has actually processed
    %% MoreCreditAfter messages from Sender -- not on every message.
    Sender ! {bump_credit, {self(), InitialCredit}},
    ok.

%% On the sender side, receiving a bump_credit message restores credit
%% and clears the blocked flag, unblocking any queued sends for that peer:
handle_bump_credit({Peer, Amount}) ->
    put({credit_to, Peer}, Amount),
    erase({credit_blocked, Peer}).

Second, the memory monitor's poll loop, deciding paging vs the hard alarm from the same two numbers:

Erlangvm_memory_monitor.erl — the watermark check, simplified
check_memory(State = #state{total_memory = Total,
                          high_watermark = Watermark,     %% e.g. 0.6
                          paging_ratio   = PagingRatio}) ->  %% e.g. 0.5
    MemUsed      = erlang:memory(total),
    HardLimit    = Total * Watermark,             %% e.g. 0.6 * RAM
    PagingLimit  = HardLimit * PagingRatio,        %% e.g. 0.3 * RAM
    if
        MemUsed >= HardLimit ->
            %% Hard stop: block every publishing connection on the node.
            rabbit_alarm:set_alarm({{resource_limit, memory, node()}, []}),
            set_paging(true, State);
        MemUsed >= PagingLimit ->
            %% Soft stop: keep accepting publishes, but tell classic queues
            %% to start moving message bodies to disk NOW, before the hard limit.
            rabbit_alarm:clear_alarm({resource_limit, memory, node()}),
            set_paging(true, State);
        true ->
            rabbit_alarm:clear_alarm({resource_limit, memory, node()}),
            set_paging(false, State)
    end.

Third, what a connection's reader actually does once the alarm plumbing tells it to stop:

Erlangrabbit_reader.erl — reacting to the memory alarm, simplified
%% rabbit_alarm calls back into every reader process when the alarm
%% state changes -- this is the ENTIRE mechanism behind the client-
%% visible connection.blocked frame:
handle_info({conserve_resources, memory, true}, State) ->
    %% Tell the client explicitly -- clients that check for this frame
    %% can pause publishing on their own before hitting a hard stall;
    %% clients that ignore it (many do) simply hang once the reader
    %% below stops reading and the OS socket buffer fills.
    rabbit_writer:send_command(State#v1.sock,
        #'connection.blocked'{reason = <<"low on memory">>}),
    %% The actual backpressure: stop asking the kernel for more bytes.
    set_recv_active(false, State);

handle_info({conserve_resources, memory, false}, State) ->
    rabbit_writer:send_command(State#v1.sock, #'connection.unblocked'{}),
    set_recv_active(true, State).   %% resume recv -- TCP window reopens, publisher unsticks
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Keep the fast path allocation-free and lock-free. credit_flow's entire state lives in the sender's own process dictionary — no ETS table, no shared counter, no lock — because the fast path (decrement and compare) runs on literally every message forwarded anywhere in the broker, and any shared-state contention there would undo the isolation chapter 1 spent an entire chapter establishing. 2. Prefer a coarse, reliable backstop over a clever, fallible one. The memory alarm doesn't try to identify which queue is the actual offender and throttle only that one — it blocks every publisher on the node, indiscriminately, because a node genuinely low on memory needs to stop all growth immediately, and a more surgical mechanism that tries to be clever about which publisher to blame is one more thing that can be wrong exactly when the node can least afford it. 3. Let the same alarm plumbing serve two independent resources. rabbit_alarm doesn't know or care whether the underlying resource is memory or disk — both vm_memory_monitor and rabbit_disk_monitor raise the same alarm shape, so rabbit_reader only ever needs to implement one reaction (block/unblock), not one per resource type.
