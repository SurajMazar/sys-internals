UBER ENGINEERING INTERNALS · CHAPTER 08

From One Codebase
to Thousands of Services

Chapter 7 quietly assumed dispatch, payments, and notifications were already separate, independently deployed services coordinating through a trip state machine. They were not always separate. Uber's backend began as a single shared codebase, and this chapter is the honest account of exactly how that broke down as the company grew from one city to hundreds — and what it actually cost, in new problems traded for old ones, to fix it.

ARC 01 · THE PROBLEM

One codebase, one deploy, hundreds of teams, wildly different workloads

A monolith is not a mistake — it is almost always the correct starting architecture. One repository, one build, one deploy pipeline, one running binary means one team can reason about the whole system, ship fast, and avoid the very real costs distributed systems impose (chapters 7 and 9 both catalog those costs in detail). The monolith stops being correct only when three specific pressures, each individually survivable, start compounding at the same time.

  • Deploy coupling. Every team's code ships in the same binary, on the same release train. A bug introduced by one team — even in a code path no other team touches — can fail a build, fail a test suite, or trigger a rollback that blocks every other team's changes from shipping until it's fixed.
  • One scaling knob for workloads that don't scale alike. A ride-hailing backend genuinely contains wildly different workloads under one roof: dispatch is latency-sensitive and bursty with rider demand; trip-history analytics is throughput-sensitive and runs in long batches; notifications are I/O-bound and spiky. A monolith has exactly one unit of deployment and one instance shape — you scale the whole binary or none of it, even though these workloads want to scale on completely different axes.
  • Organizational scaling limits. Software architecture and team structure are not independent — this is often called Conway's Law. Hundreds of engineers committing to one repository means merge conflicts, review queues, and a shared mental model of "the whole system" that no individual can actually hold once it's grown past a certain size — the codebase's complexity grows with headcount, not with product surface area alone.
WHY THIS MATTERS FOR THE NEXT 5 CHAPTERS

Chapter 8 through 13 are all, in one way or another, about the machinery a company must build once it accepts this chapter's tradeoff: RPC and service meshes (chapter 9) so thousands of services can call each other safely, an event backbone (chapter 10) so they can communicate asynchronously, observability (chapter 11) so a request crossing hundreds of services can still be understood, a scheduler (chapter 12) to place all those services on shared hardware, and an API gateway (chapter 13) to hide all of it from a mobile client that only wants a stable contract. None of that machinery is needed by a monolith. All of it becomes necessary the moment you decompose — which is exactly why this chapter treats decomposition as a real tradeoff, not an unambiguous upgrade.

DEEP CONTEXT · THIS WAS NOT A SINGLE, PLANNED REWRITE

It's tempting to picture "the microservices migration" as one deliberate project with a start and end date. Uber's own public engineering commentary from this era describes something closer to sustained organic pressure: as more cities launched and more teams were hired, extracting a piece of shared logic into its own service became the path of least resistance for any team blocked by the monolith's release train, over and over, until the aggregate architecture looked nothing like where it started. Section 8's strangler-fig pattern is precisely the incremental technique that kind of organic migration depends on — nobody can schedule a big-bang rewrite of a system serving live traffic in hundreds of cities.

ARC 03 · NAIVE SOLUTION

Attempt #1: everything in one binary, and it's genuinely fine at first

Start from the honest, defensible beginning. One application, one repository, one relational database, one deploy pipeline:

pseudocodemonolith/app.py — the strawman, annotated
# one process, one deploy, imports everything
from dispatch import match_driver
from pricing import compute_fare
from trips import TripRecord
from notifications import push
from analytics import log_event

def handle_request(req):
    # every feature is one function call away — no network, no serialization
    driver = match_driver(req.rider_location)
    fare = compute_fare(req, driver)
    trip = TripRecord.create(req, driver, fare)   # same DB connection pool as everything else
    push(req.rider_id, "Driver found")
    log_event("trip_created", trip.id)
    return trip

# one Procfile, one deploy: `git push` ships dispatch, pricing, trips,
# notifications, and analytics all at once, as one atomic unit.

For a single city with a few dozen engineers, this is not a compromise — it is the fastest possible way to ship, and every cross-feature change (say, changing what data flows from dispatch into pricing) is a single pull request, not a coordinated multi-team rollout. Watch what happens as the org and the traffic both grow by two orders of magnitude.

ARC 04 · WHY IT FAILS

Quantify it: deploy risk, wasted capacity, and communication overhead

  • Deploy-blocking probability compounds with commit volume. If a single team's bad commit has even a small independent chance p of breaking the shared build or triggering a rollback, and N teams are all committing to the same release train, the chance that at least one team blocks that day's deploy for everyone is 1 − (1−p)^N — which climbs toward certainty fast as N grows into the hundreds, even with a fairly small per-team p. At ten teams and p = 0.03, that's already a ~26% chance any given deploy window is blocked; at a hundred teams it's over 95%. The monolith didn't get riskier because engineers got worse — it got riskier purely because N grew.
  • Overprovisioning is a direct, computable waste. If dispatch needs to handle bursts at, say, 10× the average request rate that trip-history analytics needs, but both run in the same binary on the same instance type, you must provision every instance for dispatch's peak — meaning the analytics workload's share of every instance sits mostly idle, and you're paying for capacity that workload will never touch. There is no partial-provisioning option inside one binary.
  • Communication overhead grows faster than headcount. With M engineers all needing to coordinate changes to one shared codebase, the number of pairwise communication paths that can matter for a given change grows on the order of M(M−1)/2 — quadratically. Code review queues lengthen, merge conflicts rise, and the "does this change break something I own" question becomes unanswerable by inspection once the codebase exceeds what any one engineer can hold in their head.
THE CONCRETE FAILURE

Picture the on-call engineer for the payments team, at 2am, staring at a failed deploy — except the failing test belongs to a feature they've never touched, owned by a team nine time zones away, and their own time-sensitive fix (say, a fraud-detection patch) cannot ship until that unrelated failure is resolved. This is not a hypothetical edge case; it is the default steady state of a monolith once enough independent teams share it, and it is precisely the failure mode that made "can we ship independently of each other" the organizing question behind the whole migration.

ARC 05 · BETTER SOLUTION

Decompose along ownership boundaries, not just code structure

The fix is not merely "split the file" — a monolith can already have clean internal module boundaries (as the strawman in §3 arguably does) and still suffer every failure mode in §4, because the deploy unit is what couples teams, not the source-file layout. The real fix decomposes the system into services whose boundaries match team ownership: each service gets its own repository (or an independently deployable path within one), its own deploy pipeline, and — critically — its own datastore, so that no other team's schema change can break it silently.

Drawing the boundaries: from modules to owned servicesSTEP-BY-STEP

Each of dispatch, pricing, trips, notifications, and analytics becomes its own deployable unit, on its own release cadence, scaled to its own resource profile, owned by one team who can change its internals freely as long as its external contract holds. What used to be a function call — compute_fare(req, driver) — becomes a network call to another service. That single change is the entire subject of chapter 9.

ARC 06 · WHY THAT STILL HURTS

You didn't remove the complexity — you relocated it

Be honest about what decomposition costs, because every one of these is a real, ongoing tax, not a one-time migration fee:

  • Function calls become network calls. Every call that used to be microseconds and could never "fail" except by raising an exception in-process is now a network hop that can time out, get dropped, or return a response for a request that technically never happened. Chapter 9's entire subject — retries, timeouts, circuit breaking — is the direct, unavoidable consequence of this one change.
  • Nobody has one mental model of the whole system anymore. With five services and clear ownership, this is manageable. With hundreds or thousands, "what calls what" is no longer something any engineer can answer from memory — it requires dedicated tooling to even visualize (service registries, dependency graphs, and the distributed tracing chapter 11 builds specifically to reconstruct one request's path across services after the fact).
  • Cross-service consistency gets much harder. A monolith could often wrap a multi-step change in one database transaction. Once dispatch, pricing, and trips are separate services with separate datastores, that single transaction becomes a sequence of network calls with no shared transaction boundary — exactly the problem chapter 7's durable state machine and idempotency keys exist to solve for trip state specifically.
  • Operational surface area multiplies. Each independently deployed service needs its own on-call rotation, its own alerting, its own capacity planning, and its own deploy pipeline to maintain — real, recurring organizational overhead that a single shared pipeline didn't require.
THE HONEST FRAME

Decomposition doesn't make a hard problem easy — it trades one company-wide hard problem (deploy coupling, org-scaling limits) for several team-local hard problems (network reliability, cross-service consistency, operational overhead) that are each individually more tractable to solve, in parallel, by the team that owns them. That is a real net win once you're past a certain scale — but it is a trade, not a strict improvement, and a team that decomposes too early pays all of this chapter's costs without yet needing any of its benefits.

ARC 08 · INTERNAL IMPLEMENTATION

The strangler-fig pattern: how you migrate a live system without a big-bang cutover

You cannot schedule downtime to rewrite a backend serving live trips in hundreds of cities. The strangler-fig pattern is the general technique that makes incremental migration possible: put a routing layer in front of the monolith, extract one piece of functionality into a new service, and shift traffic to it gradually while continuously verifying it produces the same results as the code path it's replacing.

ARC 09 · TRADEOFFS

Five points on the same spectrum

ARCHITECTUREWHAT IT BUYSWHAT IT COSTS
Monolith simple mental model transactional consistency for free fastest to build early deploy coupling one scaling knob for all workloads org-scaling ceiling
Modular monolith (enforced internal boundaries, one deploy) clearer ownership than a plain monolith still one transaction boundary deploy coupling remains — still one release train
SOA (fewer, larger services, often with a shared integration bus) some independent scaling and deployment the integration layer itself often becomes a new bottleneck / coupling point
Microservices (this chapter's endpoint) independent deploys independent scaling per workload clear per-team ownership network calls replace function calls operational overhead multiplies requires chapters 9–13's platform investment
"Macroservices" / service groups (fewer, coarser-grained services than pure microservices) less network chatter than fine-grained microservices smaller platform investment boundaries can still cut across team ownership if drawn wrong

Read this table as a spectrum, not a ladder to climb as far as possible. The right point on it is a function of organization size and workload diversity — a five-engineer startup adopting fine-grained microservices is paying this chapter's full cost for none of its benefit, exactly as §6 warned.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

Where this exact tradeoff bites, in public and in general practice

Uber has not published a single detailed postmortem naming an internal monolith-deploy incident with specifics, so this section teaches the realistic, industry-standard incident patterns this exact architectural transition produces — patterns widely discussed across the industry at companies who have gone through the same migration — and says so plainly rather than inventing a specific internal Uber event.

Pattern 1: the shared-build deploy freeze

A single failing test, or a single team's regression, blocks the shared release pipeline for every team relying on it — precisely §4's math. The general industry fix is exactly this chapter's: decouple deploy units so that one team's failure can only block that team's own release train, never anyone else's.

Pattern 2: the "distributed monolith" anti-pattern

A team extracts services on paper but leaves them sharing one database, or calling each other synchronously in long, tightly coupled chains — getting every cost of §6 (network calls, operational overhead) while getting almost none of the benefit of §5 (independent deploys, independent scaling), because a schema change or an outage in one "service" still cascades to all the others exactly as it would have in a real monolith. This is widely recognized across the industry as one of the most common ways a microservices migration fails to deliver its promised benefit — extracting the code without extracting the ownership and the datastore.

Pattern 3: cascading failure from an under-protected internal call

Once services call each other over the network, a slow or failing downstream service can exhaust the calling service's own resources (connection pools, thread pools) while it waits — a failure in one corner of the system propagating to parts of it that have no logical relationship to the original problem. This is exactly why chapter 9's retries, timeouts, and circuit breaking are not optional polish on top of microservices — they are the minimum viable defense against this very common failure mode.

ARC 13 · CODE WALKTHROUGH

Reading the migration: illustrative reference structure

The specifics of Uber's internal migration tooling and repository layout are not public; what follows is precise, representative pseudocode of how a strangler-fig migration is genuinely structured in production — labeled as illustrative throughout.

before/ — one shared repository
└── monolith/dispatch.py · pricing.py · trips.py · notifications.py · analytics.py — one deploy pipeline for all five
during migration/
├── monolith/dispatch.py · trips.py · notifications.py · analytics.py — pricing.py removed, calls the new service now
├── ● strangler-proxy/routes.yaml — % traffic split between monolith's old path and pricing-service
└── pricing-service/
├── ● api/pricing.proto — the service contract (§7) — the only thing callers may depend on
├── ● handler.go — the extracted logic, now independently deployable
└── shadow_compare.go — logs old-path vs new-path results for the same request during migration
after/
└── pricing-service/ — strangler-proxy and monolith's pricing.py both retired once traffic is 100% cut over

The shadow-comparison logic that makes the traffic shift in §8 trustworthy rather than a leap of faith:

Go (illustrative)pricing-service/shadow_compare.go
func HandleFareRequest(ctx Context, req FareRequest) FareResponse {
    oldResult := monolith.ComputeFareLegacy(req)      // still called during migration
    newResult := pricingsvc.ComputeFare(req)          // the new, extracted logic

    if !oldResult.Equal(newResult) {
        metrics.Incr("pricing.shadow_mismatch")   // alert, don't fail the request
        log.Warn("fare mismatch", req.ID, oldResult, newResult)
    }

    // during migration, ALWAYS return the trusted (old) result to the caller —
    // the new path is being validated, not yet trusted with real traffic
    return oldResult
}

The proxy's routing config that shifts real traffic, once shadow comparison has run clean for long enough:

YAML (illustrative)strangler-proxy/routes.yaml
route: /fare/compute
targets:
  - name: monolith_legacy
    weight: 80        # most traffic still served by the battle-tested old path
  - name: pricing_service
    weight: 20         # gradually increased as confidence grows, per §8's stepper
rollback:
  on_error_rate_above: 0.5%
  action: shift_all_traffic_to(monolith_legacy)   # automatic, no human required to fail safe
WHY IT WAS BUILT THIS WAY

Notice that shadow comparison never returns the new path's result to a real caller — it only compares and logs. That's deliberate: validating correctness and shifting real production risk are two separate steps, done in sequence, not at once. And the routing config has an automatic rollback trigger, not just a manual one — because the entire premise of an incremental migration is that a bad extraction should fail small and fail fast, never becoming its own version of the big-bang cutover this whole pattern exists to avoid.
