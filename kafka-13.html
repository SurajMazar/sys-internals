Cluster Sizing

Every Kafka cluster you will ever size has an answer waiting for you before you provision a single broker — if you're willing to walk a produced byte through every resource it touches and find the one that runs out first. This chapter derives a broker-sizing formula from network, disk, page-cache, and CPU ceilings; shows why partition count is the sharpest tradeoff in the system; applies Little's Law to consumer lag; builds an additive latency budget; and explains why Kafka brokers run small JVM heaps on purpose.

ARC 01 · THE PROBLEM

Sizing is a prediction problem, not a reaction problem

Most Kafka clusters are not sized — they are grown. A team picks a broker count that feels reasonable, ships it, and then reacts: adds brokers when CPU alarms fire, adds partitions when a consumer group falls behind, bumps the JVM heap when someone reads a blog post. Reactive sizing works until the workload changes faster than the reaction time, and by then you're doing capacity planning during an incident (chapter 14's subject) instead of during a design review.

This chapter builds the alternative: a small number of first-principles calculations that predict a cluster's ceiling before it exists. Five questions pull in different directions, and answering them honestly is the entire discipline of performance tuning and cluster sizing:

  • Throughput budget. A produced byte does not leave the cluster once — replication and consumer fan-out multiply it — so what looks like a NIC with gigabytes/sec of headroom might have almost none left for your actual workload.
  • Partition count. Partitions are the only unit of consumer parallelism (chapter 7's rebalancing model), but every partition is a standing cost in file handles, controller metadata, and producer buffer memory — paid whether or not it is busy.
  • Consumer lag stability. Whether a consumer group's backlog holds steady or grows without bound is decided by an inequality you can write down in one line, using nothing more than Little's Law.
  • Latency budget. End-to-end produce-to-consume latency is the sum of independently tunable delays — batching, replication acknowledgement, fetch-request parking — and the tail is set by whichever stage is slowest under load, not by any stage's average.
  • JVM/GC headroom. Because the data path lives in the OS page cache, not the JVM heap (chapter 10's sequential-I/O argument), heap sizing is a metadata-and-request-object problem, and getting it wrong triggers cluster instability through session timeouts, not just slow queries.
WHY THIS MATTERS FOR THE REST OF THE COURSE

Everything in this chapter is arithmetic you can do on a whiteboard using facts chapters 2, 5, 7, and 10 already established: the network/thread-pool architecture, ISR replication mechanics, consumer-group rebalancing, and the sequential-write argument for log segments. Sizing doesn't introduce new mechanisms — it prices the ones you already know. Chapter 14 assumes you can do this arithmetic: nearly every production incident it covers is what happens when one of these five budgets was blown and nobody noticed until the cluster told them the hard way.

DEEP CONTEXT · WHY THE PARTITION-COUNT CEILING MATTERED SO MUCH

Before KIP-500, every partition's metadata lived in ZooKeeper and had to be replicated through a Zab quorum on every leader change; the controller held a full in-memory copy and rebuilt it from scratch (a "controller failover") whenever the controller broker itself died. That rebuild's cost scaled with partition count, and community-reported controller failovers on clusters with hundreds of thousands of partitions could take minutes — during which no leader elections could complete. Sizing guidance from that era ("keep partitions per broker in the low thousands", "avoid four-digit partition counts per topic") was as much about controller failover time as it was about file handles. KRaft's event-sourced metadata log and snapshotting change the failover cost model, but the file-handle and RecordAccumulator memory costs from §6 are unrelated to the controller and still apply exactly as before.

ARC 03 · NAIVE SOLUTION

Attempt #1: divide target throughput by NIC line rate

The simplest possible sizing calculation treats the network interface as the only constraint, and treats a produced byte as if it only ever crosses the wire once:

bashnaive_sizing.sh — the strawman, annotated
# "How many brokers do I need?"
target_mb_s=500          # target produce throughput, MB/s
nic_gbit=10               # 10GbE NIC per broker
nic_mb_s=$(( nic_gbit * 1000 / 8 ))   # 10 Gbit/s ≈ 1250 MB/s line rate

brokers=$(( (target_mb_s + nic_mb_s - 1) / nic_mb_s ))
echo "brokers needed: $brokers"
# target_mb_s=500, nic_mb_s=1250  →  brokers needed: 1
# "One 10GbE broker easily handles 500 MB/s. Ship it."

This is not a strawman built to be laughed at — it is the calculation most people actually do, because it is the only number that's easy to find (a NIC's rated bandwidth is on the spec sheet). It also isn't wrong about the NIC's raw capability: a 10GbE link genuinely can move up to ~1.25 GB/s in one direction. The error is treating "500 MB/s target throughput" and "500 MB/s of NIC traffic" as the same number.

ARC 04 · WHY IT FAILS

A byte crosses the NIC more than once — count every crossing

Follow one megabyte from a producer through a broker with replication factor R=3 and N=4 consumer groups each reading the full topic. It crosses that broker's NIC as:

  • 1× inbound, as the producer's bytes arrive (ingress).
  • (R−1) = 2× outbound, as the leader replicates to each in-sync follower (chapter 5's ISR mechanics — every follower runs its own replica fetcher pulling from the leader).
  • N = 4× outbound, once per consumer group reading the full topic (each group fetches independently; Kafka does not de-duplicate fan-out reads across groups — every group re-reads the log from its own offset).

Total NIC traffic generated by one produced megabyte: 1 (in) + 2 (replication out) + 4 (fan-out out) = 7 megabytes of NIC traffic for every megabyte a producer sends. The naive calculation used exactly 1. It was off by 7× before accounting for anything else — TLS overhead, request/response framing, or the fact that many cloud instance types quote a single aggregate bandwidth number shared across both directions rather than independent full-duplex ingress and egress.

THE CORRECTED NUMBER

Re-run the naive script's arithmetic with the 7× multiplier: 500 MB/s target ingest generates 3,500 MB/s of total NIC traffic across the cluster. Spread over brokers with ~1,250 MB/s of usable 10GbE bandwidth each (already discounted for protocol overhead — real sustained throughput on a "10GbE" NIC is closer to 1.1–1.2 GB/s), that is at least 3 brokers just to clear the NIC ceiling — not one. And this says nothing yet about whether disk, page cache, or CPU run out first; §5 works through those systematically, and §8 finishes the fully worked example with concrete broker counts.

The lesson generalizes: any resource that a byte touches more than once per unit produced must be budgeted at its true multiplicity, not at the produce rate. The next section walks through disk, page cache, and CPU as competing hypotheses for "the" bottleneck, and shows why none of them can be assumed — each has to be checked, every time, against your actual replication factor, fan-out, and hardware.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Four candidate bottlenecks — eliminate three, keep the discipline

A correct sizing methodology does not assume which resource limits you. It computes a required-broker-count from each of network, disk, page cache, and CPU independently, then takes the maximum — the cluster is only as large as its weakest resource demands. Step through the four candidates; each step includes the arithmetic that eliminates (or confirms) it as the limiting factor for a representative deployment.

ARC 06 · WHY THAT STILL COSTS

The throughput formula says nothing about partition count — and partition count is its own tradeoff

Suppose §5's formula says 6 brokers. That answers "how much aggregate throughput capacity do I need" — it says nothing about how many partitions to create. Partition count is a second, largely independent sizing axis, and it is the sharpest tradeoff in the system because partitions are the only unit of parallelism a consumer group can exploit (chapter 7: a group can never run more active consumers than it has partitions — extra consumers simply sit idle with nothing assigned), yet every partition is a standing tax paid whether or not it carries traffic:

  • File handles. Each active log segment for a partition holds an open file descriptor for its .log, its offset index (.index), and its time index (.timeindex) — three descriptors per segment, and older segments awaiting deletion or compaction remain open too. A broker with 4,000 partitions and modest segment rollover can easily be holding tens of thousands of open file handles simultaneously.
  • Producer buffer memory. The client-side RecordAccumulator maintains one active ProducerBatch per partition it is currently writing to, sized up to batch.size. A producer publishing to P partitions needs roughly batch.size × P of headroom inside buffer.memory just to avoid blocking on allocate() — configure buffer.memory too small relative to your partition fan-out and the producer stalls waiting for memory it will never get back fast enough.
  • Controller / KRaft metadata. Every partition is a row of metadata (leader, ISR, epoch) that must be replicated through the metadata quorum and cached in every broker's MetadataCache. More partitions means a larger metadata log, more records for each broker to apply on catch-up, and — pre-KRaft especially — longer controller failover (§2's history).
  • Replica fetcher entries. Each follower's replica-fetcher thread tracks a fetch offset per partition it replicates; partition count multiplied by replica count is the true size of the cluster's replication bookkeeping.
  • Leader-election and recovery time scale with partition count. When a broker fails, the controller must elect a new leader for every partition that broker led — thousands of elections instead of dozens. Whether these run serially or in bounded-size batches, more partitions directly means a longer window before the cluster is back to a fully in-sync state, which is exactly the metric an SLA cares about during a failure.
  • Small partitions convert sequential writes into effectively random ones. Recall chapter 10's argument that Kafka's throughput depends on each partition's log being an append-only sequential write. That argument assumes one (or a few) partitions dominate a disk's write pattern at any instant. Round-robin flushing across hundreds of separate partition logs sharing one disk means the disk head (or, for SSDs, the write path's internal buffering) is interleaving many independent append streams — which is no longer sequential in the way a single hot log is. The fix isn't fewer bytes; it's fewer independently-flushing files per spindle.

Practical guidance, with the reasoning attached rather than asserted:

  • Measure per-partition throughput ceiling empirically. "~10 MB/s per partition" is a commonly cited rule of thumb, and it is explicitly empirical, not architectural — it comes from typical record sizes, typical compression ratios, and typical consumer processing costs on typical hardware. It is not a number the Kafka log format enforces; a partition on NVMe with large records and no downstream processing bottleneck can sustain far more, and a partition with slow per-record consumer-side work is a Little's-Law problem (§8) long before it's a partition-count problem. Use it as a starting estimate to check, not a constant to trust.
  • Keep partitions-per-broker in the low thousands. Past that, the file-handle count and metadata-catch-up cost (both of which scale roughly linearly with partition count) start to dominate operational pain — slower broker restarts (every partition's segments must be opened and its indices loaded), slower controller catch-up, and more replica-fetcher bookkeeping per heartbeat cycle.
  • You can add partitions but never remove them, and adding partitions to an existing topic is a one-way door for a reason that has nothing to do with capacity: it silently breaks key-to-partition affinity.
THE MODULO-HASHING TRAP, PRECISELY

The default partitioner routes a keyed record to partition hash(key) % numPartitions. That modulus is baked into every routing decision — it is not "mostly stable", it is a pure function of numPartitions at the moment the record is produced. Increase a topic from 12 partitions to 16 and a key that used to hash to partition 5 (because hash(key) % 12 == 5) may now hash to a completely different partition under % 16 — there is no relationship between the old and new assignment for most keys; it is not a smooth remapping like consistent hashing, it is a discontinuous jump. Every invariant that depended on "the same key always lands on the same partition" breaks the instant you add partitions: compacted changelog topics (a stream-processing state store now has two versions of the same key's history split across two partitions, and compaction — chapter 10 — only removes duplicates within a partition, never across one), and any downstream consumer relying on per-key ordering (which Kafka only guarantees within a single partition) silently starts interleaving that key's events across two independent, unordered partitions. This is why production guidance is to substantially over-provision partition count up front for any topic with key-ordering or compaction requirements — the "cheap fix" of just adding partitions later is only cheap for unkeyed or non-order-sensitive topics.

ARC 08 · INTERNAL IMPLEMENTATION

The arithmetic, worked in full

Three pieces: (a) the fully worked broker-count example combining §4–§5's formula, (b) Little's Law applied to consumer lag, sized live, (c) the additive latency budget, and (d) why brokers run small JVM heaps.

(a) The worked example: 500 MB/s, RF=3, 4 consumer groups, 10GbE

Concrete numbers, computed against each resource in turn:

  • NIC: total traffic = ingest × (1 + (R−1) + fanout) = 500 × (1 + 2 + 4) = 3,500 MB/s. At ~1,150 MB/s usable per 10GbE NIC (line rate minus protocol/TLS overhead), that's ceil(3500/1150) = 4 brokers purely to clear the network ceiling.
  • Disk: total persisted write load cluster-wide is ingest × R — the leader's own copy plus (R−1) followers' copies, every one of them a durable write — not the full fan-out (consumer reads mostly hit page cache, not disk, when consumers are near the tail). That's 500 × 3 = 1,500 MB/s of writes to spread across however many brokers you provision. NVMe (~1,500 MB/s sequential) clears this in a single broker's worth of capacity (ceil(1500/1500) = 1); SATA SSD (~500 MB/s) needs ceil(1500/500) = 3 brokers; spinning HDD (~150–200 MB/s sequential) needs ceil(1500/175) ≈ 9 brokers just to keep up with persisted writes — more than the NIC ceiling of 4. On NVMe or SSD hardware, NIC is the binding constraint at 4 brokers; swap to HDD and disk alone forces 9 — the hardware choice, not the workload, decides which resource binds.
  • Page cache: adequate if RAM (minus JVM heap reservation, §8d) comfortably exceeds the "hot" working set — roughly the last few minutes to hours of each partition's data that active consumers are still reading. If all 4 consumer groups read near the tail, the working set is small and cache hit rate stays high; if even one group is a batch job replaying from hours or days back, it forces disk reads for that group specifically, without affecting the others' cache residency — but it does add read I/O to the disk-bandwidth budget above.
  • CPU: request handling, TLS termination, and compression are the CPU-bound stages (chapter 2's thread pools). At representative compression settings this is rarely the binding constraint below the NIC ceiling — it becomes one specifically when TLS is mandatory cluster-wide and cipher overhead isn't amortized, or when a costlier codec (zstd at a high compression level) is chosen for ratio over CPU cost.

brokers_needed = max(4 NIC, 1 disk-NVMe / 3 disk-SSD / 9 disk-HDD, ~1 page-cache, ~1–2 CPU) — which resolves to 4, NIC-bound, on NVMe or SSD hardware, but to 9, disk-bound, on HDD, for the identical workload and NIC. Change any one input — go to 25GbE NICs, drop to 2 consumer groups, or raise RF to a compliance-driven 5 — and re-run the same four terms; §15's simulator lets you do exactly that live, including watching this exact NIC/disk flip happen as you change the disk-tier toggle.

(b) Little's Law for consumer lag

Little's Law — L = λW — says the average number of items in a system equals the arrival rate times the average time each item spends in the system. Applied to a Kafka consumer group: L is the number of records "in flight" (produced but not yet fully processed), λ is the production rate in records/sec, and W is the mean processing time per record. This one line sizes three separate configuration decisions at once:

  • max.poll.records bounds how many records one poll() call hands the application. Set it so that max.poll.records × W comfortably clears max.poll.interval.ms — too high a value means one batch's total processing time can exceed the interval, and the group coordinator (chapter 7) treats the consumer as dead and triggers a rebalance mid-processing.
  • Consumer count is bounded above by partition count (§6) and below by the requirement that aggregate consumption rate μ (summed across all consumers in the group) must meet or exceed production rate λ.
  • Lag stability follows directly: if μ ≥ λ with margin, the backlog stays bounded and lag oscillates around a small steady-state value. If μ < λ, even by a small amount, lag grows without bound — this is the same queueing-theory result as the iterative-server argument from the PostgreSQL course's Little's-Law callout, applied here to a consumer group instead of a single-threaded server.

Given a current backlog L₀, production rate λ, and consumption rate μ > λ, time to fully drain the backlog is L₀ / (μ − λ) — the same subtraction that makes bathtub-filling word problems work, and just as unforgiving when the denominator is close to zero.

(c) The additive latency budget

End-to-end produce-to-consume latency is not one number — it is a sum of independently configured delays, each of which someone tuned for a different reason. Step through the stages:

Where every millisecond of latency comes fromSTEP-BY-STEP
P99 IS DOMINATED BY THE SLOWEST STAGE, NOT THE AVERAGE OF ALL STAGES

Mean latency is roughly additive across stages, but tail latency is not "sum of means" — it is dominated by whichever single stage has the fattest tail under load. If acks=all replication ack usually takes 2 ms but occasionally waits 400 ms because one in-sync replica had a GC pause (§8d), your p99 end-to-end latency is set almost entirely by that replica's GC pause distribution — shaving milliseconds off linger.ms does nothing for the number that pages someone at 3am. Tune the stage with the fattest tail first; it is very often not the stage with the largest mean.

(d) Why brokers run small heaps, and why large ones are actively dangerous

Because Kafka's data path relies on the OS page cache rather than the JVM heap (chapter 10) — the broker never copies log data into Java objects on the read or write hot path, it uses sendfile()-style zero-copy transfer straight from the page cache to the socket — the heap only needs to hold metadata, in-flight request/response objects, replication bookkeeping, and index structures. A heap of roughly 6 GB is the commonly cited sweet spot with G1GC: comfortably larger than the metadata working set, small enough that a full or mixed collection's stop-the-world pause stays in the tens-of-milliseconds range rather than seconds.

A large heap doesn't just waste RAM that page cache could have used — it actively destabilizes the cluster. A multi-second GC pause means the broker can miss its session heartbeat to the KRaft controller (or, on ZooKeeper clusters, its ZooKeeper session) and get treated as dead: the controller shrinks the ISR for every partition that broker leads or follows (chapter 5), triggers unnecessary leader elections, and — once the broker resumes — those same partitions have to catch back up before rejoining the ISR. On the consumer side, a GC pause during record processing that exceeds max.poll.interval.ms looks identical to a hung consumer to the group coordinator and triggers a full rebalance (chapter 7), even though the consumer was never actually stuck.

The metrics that predict this before it becomes an incident: pause-time distribution (not just mean — a rare 3-second pause is far more dangerous to session timeouts than a steady stream of 50 ms pauses), GC frequency (rising frequency at constant allocation rate suggests shrinking effective heap headroom), and old-generation occupancy trending upward across multiple collection cycles — a classic signature of either a genuine leak (an unbounded internal cache, a metadata structure growing with partition count past what the heap was sized for) or simply an under-provisioned heap for the metadata working set at your current partition and connection count.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

Complexity and physical numbers behind the formulas above:

  • Leader lookup: O(1) — the client's Metadata cache maps partition → leader broker via a plain hash map, refreshed on NotLeaderOrFollower errors.
  • Log append: O(1) amortized — an append is a page-cache write plus an index entry inserted only every log.index.interval.bytes (default 4096), not per record; the sequential-write argument (chapter 10) is what makes this cheap on real disks, not just in big-O terms.
  • Offset lookup within a segment: O(log n) over the sparse offset index (binary search across index entries, each covering ~4 KB of log), then a short linear scan within that interval — this is why log.index.interval.bytes trades index size against lookup cost.
  • Replication fetch loop: O(followers) per partition per fetch round — the leader answers one fetch request per follower per partition per round-trip; num.replica.fetchers controls how many follower connections a broker services in parallel per source broker.
  • Page cache hit math: if the "hot" working set (recent bytes still being read by any consumer) fits in RAM − JVM heap reservation − OS overhead, reads are page-cache hits at RAM speed with zero disk I/O; the instant even one consumer group lags past the cached window, its reads become random-ish disk I/O (page cache is LRU-like — chapter 10 — so cold data has already been evicted).
  • NIC math recap: usable_per_broker ≈ 0.88–0.92 × rated_line_rate (protocol/TLS overhead); total_NIC_demand = ingest × (1 + (R−1) + fanout), exactly as derived in §4.
  • GC behavior: G1GC pause time is roughly proportional to the live-object set scanned in the region being collected, not total heap size — which is precisely why keeping the live set small (§8d: metadata only, no log data) keeps pauses short regardless of how large you're tempted to make the heap "just in case".

ARC 11 · REAL-WORLD PRODUCTION

Three shapes of incident you will eventually meet

Scale reference: LinkedIn, Uber, Netflix

LinkedIn — Kafka's birthplace — has publicly described (in Kafka Summit keynotes and engineering blog posts) fleets running many thousands of brokers moving trillions of messages a day, a scale that only holds together because sizing is treated as arithmetic rather than folklore: every one of §5's four resource terms is tracked per broker, and partition-count ceilings (§2, §6) are a first-class capacity metric, not an afterthought. Uber's public engineering writeups on their Kafka-based streaming platform describe cross-datacenter replication (uReplicator and successors) as its own sizing problem layered on top of this chapter's single-cluster math — replicating between regions is, from the source cluster's point of view, simply another consumer group in the fan-out term of §4's formula. Netflix's public descriptions of its data-platform Kafka usage similarly emphasize per-cluster partition budgets and consumer-group fan-out accounting as the operational levers that keep thousands of independent teams from silently exhausting a shared cluster's NIC or partition budget.

Incident shape 1: the GC-pause → ISR-shrink → rebalance cascade

This is the single most commonly reported Kafka production incident pattern across public postmortems and tuning guides. A broker's heap was sized generously "for safety" well past §8(d)'s ~6 GB guidance, or a metadata working set quietly outgrew a correctly-sized heap as partition count grew. Under load, a full or mixed G1 collection takes multiple seconds; the broker misses its controller session heartbeat; every partition it leads has its ISR shrunk (chapter 5) and, if the miss is long enough, a new leader is elected out from under it. When the broker resumes, those partitions must re-join the ISR from behind, generating a burst of replication traffic that competes with normal fan-out for the same NIC budget just computed in §4-5 — a self-reinforcing spiral if the cluster was already close to its NIC ceiling. On the consumer side, the same GC pause pattern during record processing crosses max.poll.interval.ms and triggers cooperative or eager rebalancing (chapter 7, KIP-429/KIP-848) for a consumer that was never actually stuck — just slow for one collection cycle. Fix, in order of leverage: right-size the heap per §8(d) instead of over-provisioning it; monitor pause-time distribution (not just mean) as a leading indicator; and set replica.lag.time.max.ms with an understanding of your actual GC pause tail, not just your steady-state replication lag.

Incident shape 2: the partition-count wall before KRaft

Community-reported operational experience from the ZooKeeper-controller era repeatedly surfaces the same pattern documented in the motivating rationale for KIP-500: clusters that grew partition count into the hundreds of thousands saw controller failover — the event that happens whenever the controller broker itself restarts or fails — stretch from seconds into minutes, because rebuilding the controller's full in-memory metadata state scaled with total partition count. During that window, no leader elections could complete cluster-wide, which meant any unrelated broker failure during a controller failover compounded into a much longer outage than either failure alone would cause. This is precisely why §6's "keep partitions-per-broker in the low thousands" guidance existed independent of the file-handle argument — it was also a controller-failover-time argument, and KRaft's event-sourced metadata log (chapter and KIP references in §2's timeline) changed, but did not eliminate, that scaling relationship.

Incident shape 3: the silent NIC saturation from an added consumer group

A cluster sized correctly for its original fan-out count quietly grows a fifth, sixth, seventh consumer group as new teams onboard — each one, per §4's formula, adds another full multiple of ingest rate to NIC egress demand with zero change to the producer side. Nothing in a typical dashboard flags "consumer group count" as a capacity metric the way "broker CPU" or "disk usage" are flagged, so the NIC ceiling from §5 is crossed silently, and the first symptom is often replication traffic (§4's 2× term) losing the NIC-bandwidth race to a newly dominant fan-out term — which surfaces as ISR shrink and under-replicated partitions that look, superficially, like a hardware problem rather than an arithmetic one.

First, the client-side batching decision — the exact check that decides whether a new record joins an existing batch or forces one to close early:

JavaRecordAccumulator.java — append(), simplified but faithful to the real decision tree
public RecordAppendResult append(TopicPartition tp, byte[] key, byte[] value, Headers headers) {
    Deque<ProducerBatch> dq = getOrCreateDeque(tp);
    synchronized (dq) {
        ProducerBatch last = dq.peekLast();
        if (last != null) {
            FutureRecordMetadata future = last.tryAppend(key, value, headers, callback);
            if (future != null) return new RecordAppendResult(future, dq.size() > 1, false);
            // batch.size worth of records already, or estimated size would overflow it —
             // this batch is full; fall through and allocate a new one below
        }
    }
    // Allocate from the shared buffer.memory pool — THIS is the call that blocks
     // if too many partitions are simultaneously holding open batches (§6's memory tax)
    int size = Math.max(this.batchSize, AbstractRecords.estimateSizeInBytesUpperBound(...));
    ByteBuffer buffer = free.allocate(size, maxTimeToBlockMs);   // ← blocks here on exhaustion
    synchronized (dq) {
        ProducerBatch batch = new ProducerBatch(tp, new MemoryRecordsBuilder(buffer, ...), time.milliseconds());
        dq.addLast(batch);
        incomplete.add(batch);
        return new RecordAppendResult(batch.tryAppend(key, value, headers, callback), dq.size() > 1, true);
    }
}

Next, the purgatory check behind fetch.min.bytes / fetch.max.wait.ms — this is the mechanism responsible for one entire term of §8(c)'s latency budget:

ScalaDelayedFetch.scala — tryComplete(), the parked-fetch decision
override def tryComplete(): Boolean = {
  var accumulatedSize = 0
  // Walk every partition this fetch requested; sum up how many bytes are
   // now available past the offset the consumer last asked for.
  fetchPartitionStatus.foreach { case (tp, status) =>
    val endOffset = replicaManager.localLogOrError(tp).logEndOffset
    if (endOffset.messageOffset != status.fetchInfo.fetchOffset) {
      accumulatedSize += bytesAvailable(tp, status, endOffset)
    }
  }
  // Released the instant EITHER condition is met — whichever fires first:
  if (accumulatedSize >= fetchMinBytes)               forceComplete()   // fetch.min.bytes reached
  else if (delayMs >= fetchMaxWaitMs)          forceComplete()   // fetch.max.wait.ms elapsed
  else false                                     // keep parked in the timing-wheel purgatory
}

And the partitioner's modulo hazard from §6, in the exact form that makes the "adding partitions breaks affinity" claim checkable:

JavaDefaultPartitioner.java — partition(), the line that breaks on resize
public int partition(String topic, byte[] keyBytes, int numPartitions) {
    // numPartitions is read fresh from cluster metadata on every call —
     // it is NOT cached from when the key was first produced.
    return Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions;
    // numPartitions: 12 → 16 changes almost every key's result. There is no
     // migration step, no rehashing pass — the NEXT produced record for an
     // existing key simply lands somewhere else, silently, forever.
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Batching decisions live entirely client-side, in RecordAccumulator, not the broker. The broker never has to guess whether more records are coming — the producer decides linger.ms and batch.size unilaterally, keeping the broker's request-handling path simple and stateless per request. 2. Purgatory is a generic, reusable mechanism (DelayedOperationPurgatory, backed by a hierarchical timing wheel) shared by delayed fetches, delayed produces under acks=all, and delayed DeleteRecords — one efficient "wait for a condition or a timeout" primitive instead of three bespoke ones. 3. The partitioner takes zero responsibility for migration. Making partition assignment a pure, stateless function of (key, numPartitions) keeps producers simple and stateless — the cost of that simplicity is pushed entirely onto operators, who must know not to resize a keyed, order-sensitive topic casually. Simplicity in the hot path, in all three cases, was chosen over protecting operators from themselves.
