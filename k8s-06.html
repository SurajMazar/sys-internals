The Control Plane
Architecture

Chapters 1 through 5 taught you to describe desired state in YAML and hand it to kubectl. This chapter opens the box that makes that description come true: the small set of processes — kube-apiserver, etcd, kube-controller-manager, kube-scheduler, and, on every node, kubelet and kube-proxy — that together turn "I want 3 replicas" into 3 running Pods, and keep it true forever without anyone watching. You will derive, not memorize, why there is exactly one component allowed to touch the database, why "self-healing" is a specific loop and not a slogan, and where the API server's authority ends and a container runtime's begins.

ARC 01 · THE PROBLEM

Coordinating machines that must never talk to each other directly

A Kubernetes cluster routinely spans hundreds to thousands of machines, and the components that manage it — a scheduler, a fleet of reconciliation loops, a per-node agent on every one of those machines — must agree on one shared truth: which Pods should exist, where they are supposed to run, and whether reality currently matches that intent. None of those components trusts the others' memory. None of them can call a function in another one's process, because they are not in the same process, often not on the same machine, and are expected to keep working even when several of their peers have crashed, rebooted, or lost network connectivity for minutes at a time.

That constraint — coordinate many independent, unreliable actors around one shared state, without any of them calling each other directly — is the entire reason a "control plane" exists as a distinct architectural layer instead of, say, one big program. Unpack the requirements and four things pull in different directions:

  • A single source of truth. If the scheduler thinks a node has 4 CPUs free and the kubelet thinks it has 1, someone is about to oversubscribe a machine. Exactly one answer to "what is true right now" must exist.
  • No component may block another. A slow or wedged kubelet on one node must not stall the scheduler's decisions for every other node; a controller stuck in a bug must not stop the API from accepting new objects.
  • Components must be independently replaceable and restartable. You will upgrade the scheduler, restart a controller-manager, and reboot nodes constantly, in any order, without ever taking the cluster down as a unit.
  • Extensibility without recompilation. Chapter 9 introduces Custom Resource Definitions and Operators — third parties writing entirely new reconciliation loops against the same shared state, without Kubernetes' own source code ever knowing they exist.

Kubernetes' answer is a strict hub-and-spoke architecture: one authoritative, versioned API in front of one consistent datastore, and every other component — scheduler, controllers, kubelets, kube-proxies, and you, via kubectl — is just a client of that API, distinguishable from each other only by what they're authorized to read and write. This chapter derives that shape from scratch, then opens each component far enough to read real Go source with confidence.

DEEP CONTEXT · WHY NOT JUST COPY BORG?

Because Borg's store, Chubby, is a small, low-throughput, strongly-consistent lock service — brilliant for "who is the master" but never designed to hold every object a cluster's users create. Kubernetes needed a store that could hold and watch potentially millions of objects (Pods, Services, ConfigMaps, and later arbitrary CRDs) at reasonable throughput. etcd, built by CoreOS the year before Kubernetes was announced, fit that gap: Raft-based like Chubby's Paxos, but designed from day one as a general key-value store with a first-class watch API — which chapter 7 shows is the single primitive the entire reconciliation model is built on.

ARC 03 · NAIVE SOLUTION

Attempt #1: one script, direct SSH, a cron job

Derive the architecture honestly, the way an operator without Kubernetes would. You have 50 machines and a list of containers that should be running on them. The obvious first move: a script, run from your laptop or a jump box, that SSHes into every machine, checks what's running, and fixes discrepancies.

bashfleet_reconcile.sh — the strawman, annotated
#!/usr/bin/env bash
# "desired state" lives in a flat file this script owns and no one else reads
while read -r host container_image replicas; do
  running=$(ssh "$host" "docker ps --filter ancestor=$container_image -q | wc -l")   # one SSH round trip per host
  if [ "$running" -lt "$replicas" ]; then
    ssh "$host" "docker run -d $container_image"                                    # under-replicated: start one more
  elif [ "$running" -gt "$replicas" ]; then
    ssh "$host" "docker stop \$(docker ps --filter ancestor=$container_image -q | head -1)" # over-replicated: stop one
  fi
done < desired-state.txt
# cron runs this every 60s. That's the whole "control plane."

This is not a joke architecture — every one of its ideas survives into the real system. It already has a desired-state file (the ancestor of a Deployment spec), a reconcile loop (the ancestor of every controller in chapter 9), and a notion of drift correction (the ancestor of self-healing). It is also exactly what most teams actually build first, in exactly this shape, before adopting an orchestrator. Watch it under load: drag the fleet size and see what a single reconcile pass costs.

ARC 04 · WHY IT FAILS

Polling doesn't scale, and two operators are worse than one

The SSH loop has two independent, fatal defects, and both are arithmetic, not opinion:

  • Polling cost is linear in fleet size, and staleness is linear in polling cost. Each host costs one SSH round trip, realistically 150-300 ms once you include auth and command execution. A 50-host fleet takes ~10 s per pass — tolerable. A 2,000-node fleet (a genuinely ordinary production Kubernetes size) takes 5-10 minutes per pass, serially. A container that crashed right after being checked won't be noticed for up to one full pass — minutes, not the seconds Kubernetes' kubelet actually delivers.
  • Two operators running the script is a race, not double safety. Nothing prevents two people (or two cron jobs after a clock skew) from running the loop concurrently. Both see "1 replica, want 3," both start 2 more — you now have 5. There is no compare-and-swap, no single writer, no way to even detect the collision after the fact. This is precisely the problem optimistic concurrency control exists to solve, and §8 shows exactly how Kubernetes' API server implements it with resourceVersion.
THE NUMBERS

At 200 ms/host, serial SSH reconciliation caps at ~5 hosts/second regardless of how idle those hosts are — the cost is round-trip latency, not work. Parallelizing helps but doesn't fix the deeper problem: every host still gets re-checked whether or not anything changed, which is exactly backwards. A cluster running smoothly generates far more "nothing changed" polls than real events. The system this chapter builds replaces polling with watching — a subscription to changes, so idle components cost nothing, and change propagates in milliseconds, not minutes. That single substitution — poll → watch — is arguably the one idea that makes the rest of Kubernetes' architecture affordable at scale.

So the requirements sharpen: one authoritative store that supports both point-in-time reads and subscribing to a stream of future changes, one gatekeeper in front of it enforcing who may write what, and many independent consumers reacting to that stream instead of re-asking the same question forever. The next section builds exactly that, one constraint at a time.

ARC 05 · BETTER SOLUTION

Building the control plane, one constraint at a time

Step through the derivation. Each step below fixes exactly one defect from §4, and nothing more — this is how the real architecture accreted, not a design handed down whole.

From SSH loop to control planeSTEP-BY-STEP
THE ONE RULE THAT HOLDS THE WHOLE THING TOGETHER

Nothing talks to etcd except the API server. Not the scheduler, not any controller, not the kubelet, not you. Every single read and write of cluster state funnels through one process's authorization, validation, and admission logic. This is not a performance optimization — it is what makes "a single source of truth" actually enforceable rather than aspirational. If the scheduler could write to etcd directly, you would need to duplicate the API server's RBAC checks, schema validation, and admission logic inside the scheduler too — and inside every future component. Centralizing the write path is what lets everything else be a simple, stateless client.

ARC 06 · WHY THAT STILL COSTS

The bill: what funneling everything through one API costs you

The hub-and-spoke design is not free, and its costs are structural, not tuning mistakes:

  • Every state change pays a round trip through the API server, no matter how local the effect. A kubelet noticing its own Pod is unhealthy still has to write that observation back through the API server before anything (including that same kubelet's later decisions) can act on it — there is no shortcut for "I already know this."
  • etcd's write throughput is a hard ceiling on the whole cluster's rate of change. The API server can have a dozen replicas behind a load balancer for read/auth throughput, but they all funnel writes to the same etcd cluster, and etcd — chapter 7 derives this precisely — commits writes through Raft consensus among an odd number of members, typically 3 or 5. A slow disk on one etcd member measurably slows every write in the cluster, not just that member's clients.
  • controller-manager runs dozens of independent loops in one process, so it needs its own leader election to avoid double-acting. Run three replicas for high availability, and exactly one must be "active" at a time — accomplished with a Lease object in etcd (the same primitive you'll meet again for node heartbeats), not a special mechanism. The other two sit idle, burning CPU on nothing but watching that Lease, ready to take over the instant the holder stops renewing it.
  • Watch propagation is fast but not instant, and admission webhooks can add real latency to every write. A MutatingAdmissionWebhook or ValidatingAdmissionWebhook (§8 details the chain) is an external HTTP call the API server must wait on before it can persist your object — a slow or down webhook is now on the critical path of every matching write in the cluster, which is exactly why webhook failurePolicy (Ignore vs Fail) is a decision with real availability consequences, not a default to leave unexamined.
THE HONEST TRADE

You are trading direct, cheap, uncoordinated writes for expensive, funneled, coordinated ones — on purpose. The SSH script in §3 had zero coordination overhead and zero correctness guarantees. The control plane this chapter builds has real, measurable overhead on every single write, bought specifically to make "exactly one thing is true" an enforceable property instead of a hope. Chapter 12 revisits this trade quantitatively when tuning the autoscalers that generate a large fraction of a busy cluster's write volume.

With that cost accepted, here is the shape that pays for it.

A DELIBERATE ASYMMETRY: WHY IS THE SCHEDULER "JUST a client"?

The scheduler has no special access to etcd, no private channel to the kubelet, and cannot directly place a container anywhere. Its entire job is to watch for Pods with an empty spec.nodeName, decide which node fits best (chapter 8), and write that decision back through the API server as a Binding subresource — an ordinary authenticated, authorized, admitted API write, indistinguishable in kind from a kubectl command. If the scheduler crashes, existing Pods keep running untouched; only new scheduling decisions stop. That blast radius is a direct consequence of the scheduler being "just a client" with no state of its own.

ARC 08 · INTERNAL IMPLEMENTATION

What actually happens to a kubectl apply

Four pieces, at the level you'd need to reason about a production incident: (a) what an object looks like on the wire and at rest, (b) the exact admission pipeline every write passes through, (c) how controller-manager's independent loops and the scheduler's two-phase design actually work, and (d) the kubelet/kube-proxy/CRI boundary on every node.

(a) An object's two shapes: what you write, what's stored

You write YAML. The API server converts it to an internal Go type, defaults and validates it, then persists a serialized form under a flat key in etcd — chapter 7 opens etcd's storage model in full, but the shape matters here:

yamlwhat you submit
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
  namespace: prod
spec:
  replicas: 3
  selector: { matchLabels: { app: checkout-api } }
  template:
    metadata: { labels: { app: checkout-api } }
    spec:
      containers:
      - name: checkout-api
        image: registry.internal/checkout-api:1.14.2
        resources: { requests: { cpu: "250m", memory: "256Mi" } }
etcdwhat's actually stored — a flat key, a serialized value
key:   /registry/deployments/prod/checkout-api
value: <serialized Deployment object>   // built-in types: protobuf by default;
                                    // CRDs: JSON, unless a conversion webhook says otherwise
// etcd itself stores this as an opaque byte blob under that key, at a
// specific Raft log index — that index becomes this object's resourceVersion.

Two things to internalize: etcd's keyspace is a flat, sorted map from byte-string keys to byte-string values — it has no idea what a "Deployment" is, no schema, no relationships. Every notion of "kind," "namespace," and "owner reference" is a convention the API server enforces on top of a dumb store. And resourceVersion is not arbitrary — for etcd-backed resources it is derived directly from etcd's internal modification counter (chapter 7's mod_revision), which is exactly why it can be used as the compare-and-swap token that fixes §4's race: a write that supplies a stale resourceVersion is rejected with HTTP 409 Conflict, full stop, no partial application.

(b) The admission pipeline: everything a write passes through

REAL PORTS, REAL WIRE FORMAT

The API server listens on 6443 (TLS only — there is no plaintext port for real use). Watches are long-lived HTTP responses using chunked transfer encoding: each chunk is a WatchEvent ({type: ADDED|MODIFIED|DELETED|BOOKMARK, object: <full object>}). BOOKMARK events (KEP-1904) carry no real change — just an updated resourceVersion — sent periodically so a reconnecting client can resume from a recent point without a full re-list, which matters enormously at the node counts §10 discusses. etcd's own client/peer ports, 2379/2380, and kubelet's API port, 10250, are chapter 7's and this section's (d) territory respectively — remember all three; §11's CVEs involve two of them.

(c) controller-manager's independent loops, and the scheduler's two phases

kube-controller-manager is one binary, running dozens of logically independent controllers — the node controller, the ReplicaSet controller, the endpoint/EndpointSlice controller, the namespace controller, the service-account-token controller, and more (chapter 9 gives the exact informer/workqueue pattern every one of them shares). "Independent" is precise here: each has its own informer watching its own resource types, its own workqueue, and its own worker goroutines running on its own cadence — none of them call each other, and one hanging is invisible to the rest. Coordination happens only implicitly, through the shared API server state: the ReplicaSet controller creates Pods; it never talks to the scheduler or the node controller directly. Because all of these loops share one process, only one replica of controller-manager may be active cluster-wide at a time — enforced by leader election over a Lease object, typically a 15-second lease with an 2-second renew deadline. The other replicas block in LeaderElector.Run(), ready to take over the instant a renewal is missed. cloud-controller-manager exists as a separate binary specifically so that cloud-vendor-specific loops (node lifecycle against a cloud API, route provisioning, load-balancer provisioning for type: LoadBalancer Services) don't have to live in Kubernetes' own release cadence or trust boundary.

The scheduler, by contrast, runs exactly one active instance for the same one-writer-per-decision reason, and its algorithm (detailed fully in chapter 8) is a strict two-phase pipeline for every unscheduled Pod: filter (which nodes even satisfy hard constraints — enough allocatable CPU/memory, taints the Pod tolerates, required affinity) followed by score (of the nodes that survive filtering, which is best — spread load evenly, or pack tightly, depending on configured plugins). (d) Every node: kubelet, kube-proxy, and the CRI boundary

kubelet is the only component whose entire job is watching one thing: Pods bound to its own node (spec.nodeName == this-node), via a field-selected watch against the API server on port 6443. For each such Pod, it reconciles the containers that should exist against the containers that do, reports the node's own health back as periodic Node/Lease heartbeat updates, and exposes its own HTTPS API on port 10250 for the API server to reach back for logs, exec, and metrics. Crucially, kubelet does not itself know how to create a Linux container — it delegates every container lifecycle operation across the Container Runtime Interface (CRI), a gRPC API (RuntimeService: RunPodSandbox, CreateContainer, StartContainer…; ImageService: PullImage…) implemented by a pluggable CRI shim such as containerd or CRI-O. What that shim does below the CRI boundary — invoking an OCI-compliant low-level runtime like runc, which is what actually creates the Linux namespaces and cgroups a container runs in — is exactly the machinery the Container Internals course derives from the kernel up; this chapter treats it as a black box the CRI shim owns. kube-proxy is architecturally a peer of kubelet, not a subordinate of it: it independently watches Services and EndpointSlices and programs the node's own packet-forwarding rules (iptables, IPVS, or nftables depending on mode) — chapter 10 opens that mechanism fully. The point to take from this chapter: both are node-local reconcilers with no special control-plane privilege beyond ordinary RBAC-governed API access.

THE PATTERN, NAMED ONCE

Every single component in this chapter — controller-manager's loops, the scheduler, kubelet, kube-proxy — is the exact same shape: watch the API server for objects you care about, decide something, write the result back through the API server. None of them ever calls another one directly. That repetition is not an accident or a lack of imagination; it's the one architectural idea, applied uniformly, that makes the whole system's components independently deployable, restartable, and — critically for chapter 9 — extensible by anyone who can write another program obeying the same rule.

ARC 09 · TRADEOFFS

Every serious orchestrator solved this; the answers differ

"One authoritative store behind one API" is Kubernetes' answer, not the only one. Comparing honestly against its real predecessors and competitors shows there is no dominant design — only different places to put the same costs:

SYSTEMCONTROL-PLANE SHAPEWHAT THEY BOUGHTWHAT THEY PAID
Kuberneteskube-apiserver gatekeeping etcd (Raft); independent watch-driven controllers strong consistency pluggable everything (CRI/CNI/CSI/admission) extensible object model many moving binaries etcd is a sensitive single dependency steep operational surface
Google BorgBorgMaster (Paxos-replicated) + Chubby (Paxos lock service) + per-cell scheduler proven at extreme scale (10,000s of machines/cell) deep scheduling optimization closed, proprietary BCL config language, not a public API
HashiCorp NomadSingle binary; servers use Raft directly for both state and leadership — no separate store operational simplicity, one binary multi-workload (containers, VMs, binaries) smaller plugin ecosystem thinner object/API model than Kubernetes
Docker Swarm modeManager nodes run Raft internally for cluster state; no external store trivial to stand up fully self-contained limited scheduling sophistication ecosystem effectively stalled
Apache Mesos + frameworksMesos master (ZooKeeper for leader election) offers resources to pluggable two-level "frameworks" maximum flexibility — many workload types share one resource pool two-level scheduling adds latency and complexity lower-level framework API

Read the pattern: Kubernetes and Nomad both chose Raft-backed consistency over Borg's proprietary Paxos stack, but Kubernetes kept etcd as a separate, generic process while Nomad embedded consensus directly in its server binary — fewer moving parts, but you can't operate or scale the consensus layer independently of the scheduler, which chapter 7 will show is exactly the kind of independent tuning etcd sometimes needs under load. Mesos's two-level model — offer resources, let frameworks decide — is more flexible than Kubernetes' single built-in scheduler, and lost anyway: one good scheduler with a rich plugin framework (chapter 8) turned out to beat "bring your own scheduler" for the vast majority of real workloads.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

The numbers that define a cluster's ceiling

The control plane's cost structure, stated precisely:

  • Watch fan-out is O(watchers), per write. One write to a Deployment is one etcd commit, but the API server's in-memory watch cache must push that event to every open watch matching it — potentially the controller-manager's Deployment controller, several kubectl get -w sessions, and any third-party operator watching Deployments. Writes are cheap to make; they are not cheap to broadcast at scale.
  • API Priority & Fairness (APF, GA since 1.20) replaced the old blunt --max-requests-inflight limit with weighted queues per priority level (system, leader-election, workload-high, workload-low, catch-all by default) — precisely so one misbehaving controller flooding the API server can't starve node heartbeats or leader-election traffic, the exact failure mode a single global limit couldn't prevent.
  • The official scalability envelope: 5,000 nodes / 150,000 Pods per cluster, with target SLOs like 99th-percentile mutating API call latency under 1 second and list-call latency under 5 seconds for the relevant resource count. Past this, you split into multiple clusters — the control plane's design doesn't get slower gracefully forever, it has a documented ceiling.
  • 110 Pods per node by default (kubelet's --max-pods) — driven partly by per-node IP address budgets under common CNI configurations (a /24 giving 254 usable addresses) and partly by the practical overhead of kubelet and the CRI shim tracking that many sandboxes on one machine.
  • etcd's own limits are the cluster's real ceiling — a recommended <1.5 KB per stored value and a practical multi-GB total database size before latency degrades sharply. Chapter 7 derives exactly why those numbers are what they are, not arbitrary.

SECURITY SURFACE, STATED PLAINLY

The API server (6443) is the cluster's single front door and is TLS-only by design — every credential type (client certificates, bearer/service-account tokens, OIDC) funnels through it, which is exactly why its authentication and authorization code is such high-value attack surface (§11's CVE-2018-1002105). kubelet's port 10250 has, historically, been a source of real incidents when left with anonymous access enabled or weak authorization mode — it can execute arbitrary commands inside any Pod on that node. etcd's client port 2379 should never be reachable from outside the control plane network: it holds Secrets in a form that, absent encryption-at-rest, is not meaningfully protected — a fact chapter 13 returns to for RBAC and chapter 7 returns to for etcd's own access model.

ARC 11 · REAL-WORLD INCIDENTS

When the single front door becomes the single point of failure

CVE-2018-1002105 — the aggregated-API proxy request-smuggling privilege escalation

CVSS 9.8. The API server's aggregation layer lets extra APIs (like the metrics API) register as if they were part of the core API, with the API server proxying matching requests to a backend extension server — including upgrade requests like kubectl exec's. The bug: when a backend responded to a proxied upgrade request with a non-101 status (an error), the API server's proxy code failed to properly terminate the connection and instead left it in a state where the attacker's next requests on that same TCP connection were forwarded straight to the backend, without going back through the API server's own authentication and authorization. An authenticated user with only permission to make one specific proxied request could pivot to arbitrary requests against any backend the aggregation layer could reach — including the kubelet API on every node. Fix: the proxy handler was rewritten to correctly validate and terminate the hijacked connection on any non-success upgrade response, closing the smuggling path entirely. Lesson: the aggregation layer is a second front door layered on the first one, and it inherits every one of §1's requirements — including "no component may act with more authority than the identity making the request."

CVE-2019-11253 — a Billion-Laughs-style YAML/JSON expansion DoS

The API server decodes every incoming YAML/JSON body before running admission or schema validation against it. Before this fix, that decoding step placed no limit on nested anchor expansion or object depth — a small request body (kilobytes) could decode into a data structure many gigabytes in size, exhausting API server memory and CPU before validation ever had a chance to reject the malformed object. Initially reachable by any authenticated user with write access to any namespaced resource (later CVE-2021-25735-adjacent hardening tightened this further). Fix: the decoder now enforces limits on nesting depth and total expansion size before attempting to build the in-memory object. Lesson: admission and schema validation (§8b, steps 5-6) can only reject what successfully decodes — the decode step itself is part of the trusted computing base and needs its own limits, independent of everything downstream.

Production pattern: leader-election flapping under etcd/network stress

A well-documented operational failure mode, distinct from any single CVE: when etcd write latency degrades (disk pressure, network partition, or simply an overloaded cluster — chapter 7's territory) past the leader-election lease's renew deadline, the active kube-controller-manager or kube-scheduler replica can fail to renew its Lease in time. A standby replica then acquires leadership and starts a fresh set of informers and workqueues from scratch — resyncing full object lists — right as the cluster is already under stress, and repeated flapping between replicas causes duplicate or delayed reconciliation (a ReplicaSet controller starting up mid-storm, briefly recomputing decisions the previous leader had already made). Mitigation: lease durations and renew deadlines are tunable (--leader-elect-lease-duration, --leader-elect-renew-deadline) precisely to trade faster failover against tolerance for transient etcd slowness; teams running large clusters widen these values rather than accepting frequent, disruptive leadership changes. Lesson: leader election is itself a client of the same shared, sometimes-degraded store it's trying to protect against split-brain on — there is no coordination mechanism here that sits outside etcd's own availability.

func (c *Controller) Run(workers int, stopCh <-chan struct{}) {
    // Reflector: List() once, then Watch() forever, feeding a DeltaFIFO.
    // The Informer drains that FIFO into a local, always-fresh cache (the Indexer) —
    // so Get()/List() in this process never touches the API server at read time.
    go c.informer.Run(stopCh)
    cache.WaitForCacheSync(stopCh, c.informer.HasSynced)

    for i := 0; i < workers; i++ {
        go wait.Until(c.runWorker, time.Second, stopCh)   // N independent workers, one shared queue
    }
    <-stopCh
}

func (c *Controller) runWorker() {
    for {
        key, shutdown := c.queue.Get()                 // blocks; de-duplicated by key ("ns/name")
        if shutdown { return }
        if err := c.reconcile(key.(string)); err != nil {
            c.queue.AddRateLimited(key)             // exponential backoff retry — no crash, no drop
        } else {
            c.queue.Forget(key)
        }
        c.queue.Done(key)
    }
}

func (c *Controller) reconcile(key string) error {
    obj, exists, _ := c.indexer.GetByKey(key)          // read from LOCAL cache, not the API server
    if !exists { return c.handleDeletion(key) }
    desired := c.computeDesired(obj)
    return c.applyDiff(obj, desired)               // the only step that writes, via the API server
}

And the filter chain every request — yours or a controller's — passes through inside the API server before reaching storage:

Goapiserver's handler chain, simplified from CreateServerChain()
handler := handlerFor(resourceHandler)                          // e.g. create.go's createHandler
handler  = genericapifilters.WithAdmission(handler, admissionChain)   // mutating THEN validating admission plugins
handler  = genericapifilters.WithImpersonation(handler, authorizer)
handler  = genericapifilters.WithAuthorization(handler, authorizer)   // RBAC / Node / Webhook authorizers, in order
handler  = genericapifilters.WithAuthentication(handler, authRequest)  // x509, bearer token, OIDC, webhook
handler  = genericfilters.WithPanicRecovery(handler)
// requests flow DOWN through this chain (auth first) and responses flow back UP —
// admission runs LAST, closest to storage, because only by then is identity fully resolved.
WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Controllers read from a local cache, never from the API server, on the hot path. The Indexer is kept fresh by the watch stream; this is what makes it survivable to run dozens of controllers without dozens of read-heavy polling loops hammering the API server. 2. Retries are exponential-backoff, not crash-and-restart. A reconcile that fails (a transient conflict, a dependency not yet created) just gets re-queued later — the workqueue's de-duplication means a hot-looping failure doesn't multiply into unbounded work. 3. Authentication strictly precedes authorization, which strictly precedes admission. You cannot ask "is this allowed" before you know "who is asking," and you cannot mutate or validate an object on behalf of an identity you haven't yet authorized. Kubernetes' own RBAC (chapter 13) and every third-party admission webhook inherit this ordering for free, precisely because it's enforced once, centrally, in the filter chain — not re-implemented per resource type.
