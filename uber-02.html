UBER ENGINEERING INTERNALS · CHAPTER 02

Geospatial Indexing:
From Geohash to H3

Chapter 1 established that dispatch must answer "which drivers are near this point" without scanning the whole fleet — and that a naive square grid, while a real improvement, has boundary and load problems of its own. This chapter derives the real fix: why raw coordinates and even the well-known geohash scheme both break down, and how Uber's real, open-sourced H3 library — a hexagonal, hierarchical spatial index — solves the same problem with better geometry.

ARC 01 · THE PROBLEM

"Find every driver within 2 minutes of this point" is not a coordinate query

A latitude/longitude pair identifies one point. It does not, by itself, answer a proximity question. If drivers are stored as raw (lat, lng) rows, "find everyone near point P" has no efficient path other than computing the distance from P to every single row — exactly the O(N) collapse chapter 1 built up to and chapter 1's toy grid tried (and partly failed) to fix. What's actually needed is a way to turn "nearby in the real world" into "nearby in a data structure" — a mapping from continuous 2D (really, spherical) space onto discrete, indexable buckets, such that two points close together on Earth are, with very high probability, close together — or in the very same bucket — in the index.

That requirement sounds simple and is deceptively hard to get right, for three reasons this chapter derives in order:

  • The Earth is a sphere (approximately), not a flat plane. Any scheme that treats latitude and longitude as if they were ordinary Cartesian x/y coordinates distorts distance and area — most severely near the poles, where lines of longitude converge.
  • A useful index must support a "neighbors" query cheaply. Given a cell, you need to enumerate its immediate neighbors — and the neighbors of those — without doing a distance calculation against every other cell that exists.
  • Real cities have wildly different densities. A single fixed cell size, as chapter 1 showed, is either too coarse for a dense downtown or too fine — and therefore wastefully numerous — for a sparse suburb. The index needs a resolution hierarchy, not one size.
WHY THIS MATTERS FOR THE REST OF THIS CHAPTER

Two encoding families have been used historically to solve this exact problem: geohashing (interleave latitude and longitude bits into one string) and hierarchical hexagonal or triangular grids, of which Uber's H3 is the most widely known production example. This chapter derives geohash first, shows precisely where it breaks, and then derives why H3's specific geometric choices — hexagons, and a fixed hierarchy of 16 resolutions — fix those specific breaks.

ARC 03 · NAIVE SOLUTION

Attempt #1: interleave the bits (geohash)

The classic, genuinely clever first attempt: take a point's latitude and longitude, binary-search each into a fixed range repeatedly (each bit halves the remaining range), and interleave the resulting bits — longitude bit, latitude bit, longitude bit, latitude bit — into a single binary string, then base32-encode it into a short, human-shareable string. Two points with a shared prefix are, most of the time, geographically close.

pseudocodegeohash_encode.pseudo — bit-interleaving strawman
function geohashBits(lat, lng, totalBits) {
  let latRange = [-90, 90], lngRange = [-180, 180];
  let bits = [], isLng = true;
  for (i = 0; i < totalBits; i++) {
    if (isLng) {
      const mid = (lngRange[0] + lngRange[1]) / 2;
      if (lng > mid) { bits.push(1); lngRange[0] = mid; }
      else          { bits.push(0); lngRange[1] = mid; }
    } else {
      const mid = (latRange[0] + latRange[1]) / 2;
      if (lat > mid) { bits.push(1); latRange[0] = mid; }
      else          { bits.push(0); latRange[1] = mid; }
    }
    isLng = !isLng;                     // alternate lng, lat, lng, lat...
  }
  return bits;                        // base32-encode for the human-readable form
}

This is a real, historically important, and genuinely useful encoding — geohash strings are still used throughout the industry as a compact, human-shareable location key, and "drivers sharing my geohash prefix" is a legitimate cheap proximity filter for many applications. It is worth taking seriously before dismissing it. But ride-hailing's dispatch problem exposes one specific, well-known flaw badly.

ARC 04 · WHY IT FAILS

The boundary discontinuity: adjacent in reality, unrelated in the index

Geohash's fatal flaw for a proximity index is a direct consequence of how it's built: it recursively bisects a fixed, global rectangle — first by longitude, then by latitude, alternating — into a quad-tree of cells. Two points can sit meters apart in physical space yet fall on opposite sides of one of those bisections at a very coarse (early) level of the recursion, which means they diverge in their very first bits and end up with completely different geohash strings, sharing no useful prefix at all despite being neighbors.

Concretely: consider two points 10 meters apart that straddle the boundary lng = 0° (the prime meridian) — one at lng = -0.0001°, one at lng = +0.0001°. The very first bit of the interleaved encoding, which bisects the whole world at lng = 0, differs between them. Every subsequent bit inherits that divergence structurally, because each level's bisection range depends on which side of the previous bisection you landed on. The two points end up in geohash cells that don't just have different strings — they can be geohash "neighbors" only via an explicit, separate neighbor-lookup table, because there is no arithmetic relationship between "close in space" and "close in the encoded string" at a cell boundary.

THE FAILURE, QUANTIFIED

A proximity search built naively on "match my geohash prefix, and maybe its 8 listed neighbor prefixes" will silently miss real candidates near any of the recursive bisection boundaries — not just the prime meridian, but every boundary at every level of the recursion, which is to say: a meaningful fraction of all cell edges, at every resolution, everywhere on the map. For a proximity index whose entire job is "never miss a genuinely nearby driver," an index with structural blind spots at every cell boundary, at every zoom level, is a correctness bug wearing a performance-optimization's clothing. This is qualitatively worse than chapter 1's fixed-square-grid boundary problem (§6 there) — it's the same category of bug, but geohash's boundaries are denser and less predictable because they come from a recursive bisection, not a single flat lattice.

There is a second, related problem worth naming even though it is not the primary failure: non-uniform cell shape. Because geohash bisects a lat/lng rectangle directly, cells are not even close to square in most parts of the world — near the equator a geohash cell is noticeably wider than tall (or vice versa depending on the bit position), and the distortion gets worse toward the poles, where a fixed change in longitude covers much less real-world distance. A proximity index whose cell shape itself varies by latitude makes "nearby in the index" mean a different real-world distance depending on where on Earth you're standing.

ARC 05 · BETTER SOLUTION

Fix the geometry: hexagons, tiled hierarchically over a sphere

The real fix Uber's H3 makes is a deliberate geometric choice, not a bigger version of the same bisection trick. Step through the reasoning:

From a lat/lng rectangle to a hexagonal hierarchySTEP-BY-STEP

Two decisions carry the whole design, and both are worth stating precisely, because interview-level understanding of H3 lives here:

  • Hexagonal cells, not square ones. A hexagon has exactly 6 neighbors, and — unlike a square, whose 4 edge-adjacent neighbors are one cell-width away while its 4 diagonal neighbors are √2 times farther — every one of a hexagon's 6 neighbors shares a full edge and sits at the same distance from the center. "Ring 1 around this cell" means something geometrically consistent in every direction, which a square grid's ring never quite achieves.
  • Project onto an icosahedron, not a flat lat/lng rectangle. Instead of bisecting a rectangle (which is what makes geohash's cells warp near the poles and break at arbitrary bisection lines), H3 projects the sphere onto the 20 faces of a regular icosahedron, tiles each face with hexagons, and then unprojects back onto the globe. This keeps cell size and shape far more uniform across the whole planet than any scheme built directly on lat/lng ever can be.
A HONEST LIMIT, STATED UP FRONT

A hexagon cannot tile a sphere perfectly — this is a real, unavoidable fact of solid geometry (it's the same reason a soccer ball is stitched from hexagons and exactly 12 pentagons). H3's base grid at its coarsest resolution has 122 cells, of which 12 are pentagons, sitting at the icosahedron's 12 vertices. This is not a bug Uber failed to fix — it is a mathematical necessity of covering a sphere with hexagons, and H3's design places those 12 pentagons deliberately over ocean, away from major population centers, specifically to keep them out of the way of real-world queries as much as possible.

ARC 06 · WHY THAT STILL HURTS

Hexagons solve adjacency, not everything

The hexagonal-icosahedral design is a large, genuine improvement, but it is not free of cost, and being honest about the remaining friction is part of understanding why H3's real implementation is as involved as it is:

  • Pentagon distortion is permanent, not eliminated. The 12 pentagon cells (§5) and the cells immediately around them at every finer resolution have subtly different area and neighbor topology than an ordinary hexagon — code that assumes "every cell has exactly 6 neighbors" will be wrong at those specific locations, and a correct implementation has to special-case them.
  • Hexagons don't subdivide as cleanly as squares. A square splits perfectly into 4 smaller squares. A hexagon does not split into a whole number of smaller hexagons that exactly tile it — H3 uses an aperture-7 scheme, where each cell's children only approximately nest inside the parent's boundary. A child cell can straddle two different parent cells at the coarser resolution — "which resolution-8 cells make up this resolution-7 cell" is not simply enumerable the way it would be for a quadtree.
  • Indexing and geometry math are genuinely more complex than bit interleaving. Converting a raw lat/lng into an H3 cell ID requires projecting onto the correct icosahedron face, converting into that face's 2D coordinate system, and quantizing to the requested resolution — meaningfully more compute than geohash's simple bisection loop, and a real reason H3 ships as a maintained C library with bindings, not a one-line formula.

None of these costs undo the fix from §5 — they are the honest price of buying uniform adjacency and sphere-wide consistency. ARC 08 · INTERNAL IMPLEMENTATION

The real resolution hierarchy, and the k-ring search

H3 defines 16 resolutions, 0 (coarsest) through 15 (finest). Each step down the hierarchy multiplies cell count by roughly 7 (the aperture-7 scheme from §6) and shrinks edge length by roughly √7. The table below is H3's real, publicly published resolution table (h3geo.org) — these are documented facts, not illustrative estimates.

Dispatch typically operates at a mid-range resolution (roughly resolution 8–9, tens of meters to a few hundred meters of edge length) — fine enough that "same cell" is a meaningfully tight proximity signal, coarse enough that a k-ring search of a handful of rings covers a realistic dispatch radius without enumerating an unreasonable number of cells. Now walk through what a k-ring search actually does, step by step, on a real hex grid:

k-ring neighbor search, step by stepSTEP-BY-STEP
pseudocodekring.pseudo — axial hex coordinates, real and computable
// Axial coordinates (q, r) address a hex grid with exactly 6 neighbor directions.
const HEX_DIRS = [[1,0],[1,-1],[0,-1],[-1,0],[-1,1],[0,1]];

function kRing(centerQ, centerR, k) {
  if (k === 0) return [[centerQ, centerR]];
  let results = [], [q, r] = [centerQ + HEX_DIRS[4][0]*k, centerR + HEX_DIRS[4][1]*k];
  for (dir = 0; dir < 6; dir++) {
    for (step = 0; step < k; step++) {
      results.push([q, r]);
      q += HEX_DIRS[dir][0]; r += HEX_DIRS[dir][1];   // walk one full ring of 6k cells
    }
  }
  return results;                          // exactly 6k cells at ring k (k>0) — a real, exact count
}
A REAL, EXACT COUNT WORTH MEMORIZING

On a true hex grid, ring k contains exactly 6k cells (for k > 0), and the disk of all rings from 0 through k contains exactly 1 + 3k(k+1) cells. This is genuine, computable geometry — not an approximation — and it's the number that lets you predict, precisely, how many cells a "search out to ring 3" query touches (1 + 3·3·4 = 37 cells) before you write a single line of the real search.

ARC 09 · TRADEOFFS

Three real spatial-indexing families, compared

SCHEMECELL SHAPEWHAT IT BUYSWHAT IT COSTS
GeohashRectangles from recursive bisection simple bit-interleave human-shareable string widely supported boundary discontinuities at every level non-uniform cell shape by latitude
Quadtree / S2-style square subdivisionSquares, hierarchically subdividing clean 4-way subdivision simple containment queries 4 edge-neighbors and 4 diagonal-neighbors are NOT equidistant
H3 (Uber, open source)Hexagons on an icosahedral projection all 6 neighbors equidistant uniform-ish cell size across the globe 16 resolutions, aperture-7 12 unavoidable pentagons non-clean subdivision more complex indexing math

Read this table as this chapter's real thesis: there is no cell shape that is simultaneously perfectly subdividable, perfectly uniform, and boundary-free — geohash gives up uniformity and boundary-safety for simplicity; square subdivision gives up neighbor-equidistance for clean subdivision; H3 gives up clean subdivision and a handful of special-cased pentagons in exchange for the two properties dispatch needs most: uniform adjacency and reasonably uniform area across the whole planet.

HOW THE NUMBERS ARE COMPUTED

For a chosen resolution, the widget takes H3's real published edge length at that resolution (§8), computes how many rings are needed for the ring's radius (ring count × edge length) to reach or exceed the requested search radius, then applies the exact disk formula 1 + 3k(k+1) from §8 to get a real cell count — no fudge factor. The pattern this always produces: too coarse a resolution wastes area (each cell covers far more ground than needed, so you touch few cells but each one is mostly wasted search); too fine a resolution needs an enormous ring count (and cell count) to reach the same physical radius. There is a real sweet spot, and it moves with local density exactly the way chapter 1's §8 predicted a fixed radius would need to.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

The pentagon problem, and the general class of index-rebalance incidents

The 12 pentagons are a documented, permanent special case

H3's own public documentation is upfront about the 12 pentagon cells introduced in §5 — they are a genuine, disclosed mathematical consequence of tiling a sphere with hexagons (there is no way to avoid them; a sphere's Euler characteristic forces exactly 12 "defect" cells in any hexagon-dominant tiling), and H3's real design deliberately places them over remote ocean regions specifically to minimize how often real applications encounter them. Any application built on H3 that assumes "every cell has exactly 6 neighbors" without handling the pentagon case is carrying a latent, documented edge case — and H3's own API exposes a function specifically to check whether a given cell is a pentagon, which is the industry's standard tell that this is a known, designed-around wrinkle rather than an oversight.

The general pattern: reindexing cost when resolution choice turns out wrong

Uber-specific incident reports around H3 resolution changes are not public, so this section states the general, well-understood industry pattern honestly rather than inventing a specific one: any system that chooses a fixed indexing resolution for a workload that later grows unevenly (a rural market whose central business district suddenly densifies, for instance) faces a real operational choice — either keep the coarser resolution and accept degraded search precision in the now-dense area, or re-key every stored record to a finer resolution, which for a live system touching millions of records is a genuine online-migration project, not a config flag flip. This is the same class of problem this site's database courses call a resharding or repartitioning migration, and it is the honest, general cost of any hierarchical spatial index whose resolution is chosen once at design time.

THE GENERAL LESSON

A resolution hierarchy (§8) exists specifically so that resolution can, in principle, vary by area rather than being fixed globally — dispatch can query a finer resolution in a dense downtown and a coarser one in a sparse exurb without changing the underlying index technology. Whether a live storage layer built on top of that index makes changing resolution cheap or expensive is a separate, real engineering decision this chapter flags but does not resolve — it is exactly the kind of tradeoff a Staff-level design review is expected to surface before a resolution choice ships.

ARC 13 · CODE WALKTHROUGH

A representative geospatial-index service layout

H3's real library is open source, but the following is illustrative reference pseudocode for how a service around it is typically built — structured the way an engineering team would genuinely wire H3 (or a library like it) into a dispatch pipeline, not a claim about Uber's exact internal service code.

geo-index-service/ — illustrative layout, not real Uber source
├── h3/
│ ├── ● latlng_to_cell.go — wraps the H3 library's point→cell conversion at a chosen resolution
│ └── ● kring.go — wraps H3's kRing()/gridDisk() neighbor enumeration
├── store/cell_sets.go — in-memory map: cell id → set of driver ids currently indexed there
├── ingest/position_listener.go — consumes location events (ch. 3), re-indexes a driver on cell change
└── api/nearby.handler — "drivers near point P within radius R" — used by dispatch (ch. 4) and pricing (ch. 6)
Go-style pseudocodecell_sets.go — indexing and re-indexing a moving driver
type CellSets struct {
    byCell map[CellID]map[DriverID]bool
    byDriver map[DriverID]CellID   // remember each driver's current cell, to remove it cheaply
}

func (s *CellSets) OnPositionUpdate(d DriverID, lat, lng float64, res int) {
    newCell := h3.LatLngToCell(lat, lng, res)      // the real H3 library call this wraps
    if old, ok := s.byDriver[d]; ok && old == newCell {
        return                                     // same cell — most pings don't cross a boundary
    }
    if old, ok := s.byDriver[d]; ok {
        delete(s.byCell[old], d)
    }
    if s.byCell[newCell] == nil { s.byCell[newCell] = map[DriverID]bool{} }
    s.byCell[newCell][d] = true
    s.byDriver[d] = newCell
}
Go-style pseudocodenearby.handler — the query dispatch and pricing both call
func Nearby(lat, lng float64, res, maxK int) []DriverID {
    center := h3.LatLngToCell(lat, lng, res)
    for k := 0; k <= maxK; k++ {
        ring := h3.GridRingUnsafe(center, k)         // exactly 6k cells for k>0 (§8)
        var found []DriverID
        for _, cell := range ring {
            for d := range s.byCell[cell] { found = append(found, d) }
        }
        if len(found) > 0 { return found }
    }
    return nil
}
WHY THIS SHAPE — TWO DECISIONS WORTH STEALING

1. Track each driver's current cell explicitly (byDriver). Without it, removing a driver from its old cell on every position update would itself require a search — the exact O(N) problem this whole chapter exists to avoid. 2. Skip re-indexing when the cell hasn't changed. Most GPS pings move a driver a few meters, not across a cell boundary; checking that first turns the overwhelmingly common case into a no-op, which matters enormously at the location-update volume chapter 3 describes.
