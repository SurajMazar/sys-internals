POSTGRESQL INTERNALS · CHAPTER 10

WAL: The Physics
of Durability

Every acknowledged commit is a promise that a specific set of bytes will exist tomorrow, even if the machine loses power in the next microsecond. This chapter derives write-ahead logging from that promise alone — why you cannot fsync data pages on every commit, why an append-only log flushed once gives you both speed and durability, and exactly which bytes PostgreSQL writes, in which order, to keep that promise for four decades of workloads.

ARC 01 · THE PROBLEM

A commit is a promise the disk must keep after the power dies

Durability — the D in ACID — is the least forgiving guarantee a database makes. It does not say "we will probably keep your data." It says: once this backend has told the client COMMIT succeeded, the effects of that transaction survive any subsequent failure — a killed process, a kernel panic, a power cut mid-instruction, a whole rack losing power. There is no partial credit. A database that loses one acknowledged commit in a billion has, for that one transaction, failed at the only job a database has.

Now confront the physical shape of the problem. A transaction that updates a handful of rows can dirty pages belonging to the table's heap, one or more B-tree indexes, and the visibility map — pages that are scattered at effectively random byte offsets across gigabytes of files, because rows and index entries for a single transaction have no reason to be physically adjacent. Chapter 9 explained why those dirty pages live in a shared buffer pool and get written back to disk on their own schedule. The naive reading of the durability requirement — force every dirty page to disk before acknowledging the commit — collides head-on with that buffer pool design, and with the physical reality of storage:

  • Scattered writes are the slowest access pattern any storage device has. A spinning disk pays a seek plus rotational latency per random write; even flash, which has no seek, pays firmware and protocol overhead per synchronous operation that a large sequential write amortizes away.
  • An 8 KB PostgreSQL page is not an atomic unit of storage. The hardware guarantees atomicity only at the sector level — traditionally 512 bytes, now often 4 KB. A crash mid-write to a data page can leave a torn page: part new content, part old, silently corrupt. Forcing the write harder doesn't fix this — you need a way to detect and repair it after the fact.
  • Commit latency must stay near-constant regardless of how many pages a transaction touched, or every multi-row UPDATE becomes proportionally slower to commit — an unacceptable coupling between logical work done and physical I/O pattern.

So the real requirement is sharper than "write the data before you ack": it is durably record enough information to reconstruct the change, cheaply enough that every commit can afford it, in a way that lets the buffer pool keep writing dirty pages back whenever it wants. That requirement, taken seriously, is what produces the write-ahead log.

WHY THIS MATTERS FOR THE NEXT CHAPTERS

Everything from here to chapter 19 stands on this one log. Checkpoints (chapter 11) exist to bound how much of it must be replayed after a crash. Streaming replication and logical decoding (chapters 18–19) are, quite literally, processes that read this same byte stream and ship it elsewhere. Point-in-time recovery is "replay the log up to some LSN instead of all of it." If you understand the 24 bytes of an XLogRecord header, you understand the substrate every later chapter builds on.

ARC 02 · HISTORICAL CONTEXT

1978–2001: the recovery algorithm PostgreSQL borrowed, and the year it finally arrived

Write-ahead logging was not invented for PostgreSQL, and PostgreSQL did not have it from day one. The idea traces to IBM's System R in the late 1970s, was formalized into a complete algorithm — ARIES — by C. Mohan and colleagues in 1992, and did not land in PostgreSQL until version 7.1 in 2001, more than a decade after the POSTGRES project began (chapter 1). DEEP CONTEXT · WHY "PHYSIOLOGICAL" LOGGING?

ARIES coined a deliberately odd word to name its middle path. Physical logging records raw bytes changed on a page (simple to redo, but a single-row insert near the front of a page can force logging the whole shifted tail). Logical logging records the SQL-level intent ("insert this row") — compact, but replaying it requires re-deriving physical locations, which is unsafe once concurrent structural changes (a B-tree page split) are possible. Physiological logging — what PostgreSQL's XLogRecord actually contains — names a page plus an operation relative to that page ("insert this tuple at this offset on this page"), giving small records like logical logging with the redo-safety of physical logging. You'll see this exact tradeoff again when chapter 14 covers B-tree page splits.

ARC 03 · NAIVE SOLUTION

Attempt #1: fsync every dirty page, right at commit

Derive it honestly, the way an engineer would in 1978 before ARIES existed. If durability means "the changed pages must survive a crash," the most direct reading is: before acknowledging COMMIT, force every page this transaction dirtied to stable storage.

Cnaive_commit.c — the strawman, annotated
void
naive_commit(Transaction *xact)
{
    foreach (page in xact->dirtied_pages)
    {
        /* one random-offset write into a possibly multi-GB file */
        pwrite(page->fd, page->buf, BLCKSZ, page->file_offset);

        /* one round trip to the device, waiting for the platter/NAND
         * to confirm the bytes are actually durable — not just cached  */
        fsync(page->fd);
    }
    ack_client();      /* only now is COMMIT allowed to return */
}

This is not a strawman built to be knocked down for sport — it is exactly what you'd ship if asked to make a toy database durable this afternoon, and it is correct: every acknowledged commit really is on disk when the client hears about it. Watch it fail under a completely ordinary workload: a stream of small OLTP updates, each touching a handful of scattered pages across a 20 GB table and its indexes.

ARC 04 · WHY IT FAILS

Random I/O has a ceiling, and torn pages don't care how careful you were

Two independent failures, and only one of them is about speed.

Failure 1: the commit-rate ceiling is a hardware constant

A 7200 RPM disk has an average rotational latency of ~4.2 ms plus a seek of several milliseconds — call it ~8–10 ms per random write, a physical constant of the spinning platter, not something SQL tuning touches. If an average transaction dirties even 3 scattered pages, naive per-commit fsync costs ~24–30 ms of pure device latency serialized into the commit path — a hard ceiling around 35–40 commits/sec on that one disk, regardless of CPU, regardless of how simple the SQL is. NVMe flash removes the seek, but it does not remove the fundamental shape of the problem: N scattered pages still means N separate durability round trips unless something batches them, and a busy server touches thousands of distinct pages per second across a working set far larger than any write cache.

THE NUMBERS

By Little's Law, throughput is capped near 1 / (pages_per_txn × device_latency) when every commit pays its own device round trips. At 3 pages × 9 ms ≈ 27 ms/commit, one disk caps out near 37 commits/sec — a number that has nothing to do with query complexity and everything to do with the scatter pattern. Worse: this cost scales with transaction size, so a bulk-loading transaction that touches 500 pages would need 500 fsyncs before it may return — commit latency proportional to work done is precisely the coupling §1 said we must avoid.

Failure 2: forcing the write doesn't make it atomic

Even granting infinite I/O budget, fsync() guarantees the bytes reach stable storage — it says nothing about whether the write completed as a single, all-or-nothing operation. Storage hardware commits writes atomically only at the sector granularity (512 B classically, 4 KB on Advanced-Format and most modern SSDs). PostgreSQL's page is 8 KB — two to sixteen sectors. A crash mid-write can leave a page with some sectors holding new bytes and others holding old bytes: a torn page. Naive fsync-per-commit has no answer to this at all — it has no independent record of what the page should contain, so there is nothing to repair it with. Any real solution needs both a way to avoid paying full I/O cost per commit and a way to reconstruct a torn page after the fact. One mechanism can solve both.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Don't write the data — log the intent

Step back to the actual requirement: durably record enough to reconstruct a change, cheaply, while leaving the buffer pool free to write dirty pages back on its own schedule. Three shapes were on the table historically.

Three candidates, examinedSTEP-BY-STEP
THE CLINCHING ARGUMENT: ONE SEQUENTIAL APPEND REPLACES N RANDOM WRITES

A write-ahead log turns "durably persist this transaction" into "append a few dozen to a few hundred bytes to the end of a file you're already sequentially writing, then fsync that one file." Sequential appends are the single fastest access pattern any storage device has — no seek, and even on SSDs, a large aligned append plays to every optimization the firmware has. Because the log — not the data page — is what's forced to disk at commit, the buffer pool can write dirty pages back lazily, out of order, batched, whenever it wants: this is ARIES's steal (dirty pages may reach disk before commit) and no-force (committed pages need not reach disk at commit) policy pair, and it is the entire reason chapter 9's background writer and checkpointer are allowed to exist as lazy, best-effort processes instead of commit-path participants.

ARC 06 · WHY THAT STILL COSTS

The bill: one invariant you must never violate, forever

Logging the intent buys speed, but it only buys correctness if one rule is enforced with zero exceptions across the entire codebase: a dirty page must never reach disk before the WAL record describing its change is durably flushed. This is the WAL-before-data rule, and it is the reason the log is called write-ahead — ahead of the data, always, no exceptions.

Why is this non-negotiable? Run the counterfactual: if a dirty page reached disk first, and the machine then crashed before the corresponding WAL record was flushed, recovery would replay WAL from the last checkpoint and have no record of a change that is already physically present on disk. For idempotent redo operations this might merely be redundant; but the deeper problem is that the buffer manager's freedom to write pages whenever it likes (steal/no-force, from §5) becomes unsafe the instant "whenever it likes" can mean "before its own justification exists on durable storage." The rule is enforced concretely through the page header: every page carries pd_lsn, the LSN of the last WAL record that modified it. Before FlushBuffer() (src/backend/storage/buffer/bufmgr.c) writes a dirty page — whether triggered by a backend needing a free buffer, by the background writer, or by the checkpointer — it calls XLogFlush() with that page's pd_lsn, which blocks until WAL up to that LSN is confirmed on stable storage. Only then does the page write proceed. Every single page eviction in the system pays this check.

  • A synchronization point on every eviction. The checkpointer and background writer are not truly "free" to write whenever — they may have to wait on a WAL flush first, coupling two subsystems that otherwise look independent.
  • Recovery becomes mandatory, not optional, after any crash. Because pages can lag their WAL by design, the data files alone are not trusted to be self-consistent after an unclean shutdown — WAL replay (chapter 11) is now load-bearing infrastructure, not a fallback.
  • The log itself must be durable and bounded. pg_wal becomes a second thing that can fill a disk, corrupt, or need retention policy — durability risk hasn't vanished, it moved.
A DELIBERATE DIVERGENCE FROM TEXTBOOK ARIES: NO UNDO LOG

ARIES defines both redo logging (reapply committed changes forward) and undo logging (roll back an in-progress or crashed transaction's changes). PostgreSQL implements redo-only WAL. It can, because MVCC (chapter 5) already gives every row version a creating and (if superseded) deleting transaction ID; an aborted transaction's tuples simply become versions that no snapshot will ever consider visible, determined by checking transaction status in pg_xact (the CLOG) — not by physically undoing anything. "Rolling back" costs one CLOG bit flip, not a WAL-driven physical undo pass. The price of skipping undo is deferred, not avoided: those dead-but-undeleted tuples are exactly what chapter 12's vacuum exists to reclaim.

ARC 08 · INTERNAL IMPLEMENTATION

The bytes, the pointer, and the reservation protocol

Five things to internalize at the level you'd need to patch them: the record's byte layout, how full-page writes ride inside that layout, how an LSN becomes a filename, how a record is dispatched to the code that understands it, and how concurrent backends reserve space in one shared stream without serializing on a single lock.

(a) XLogRecord: 24 bytes that precede every change

Every WAL record — whether it describes one heap insert or a whole transaction's commit — begins with the same fixed header, defined in src/include/access/xlogrecord.h:

Cxlogrecord.h — XLogRecord
typedef struct XLogRecord
{
    uint32          xl_tot_len;   /* total length of this record, header+data */
    TransactionId   xl_xid;       /* the inserting transaction's XID */
    XLogRecPtr      xl_prev;      /* ptr to the previous record in the log — a
                                    * backward linked list threaded through the log */
    uint8           xl_info;      /* flag bits: is this a checkpoint? does the
                                    * transaction have subtransactions? etc. */
    RmgrId          xl_rmid;      /* which resource manager understands this record */
    /* 2 bytes of required padding here */
    pg_crc32c       xl_crc;       /* CRC-32C over the whole record */
    /* XLogRecordBlockHeader(s), then XLogRecordDataHeader,
     * then the block data / main data payload follow immediately */
} XLogRecord;

(b) Block references and full-page writes: the torn-page insurance policy

Immediately after the fixed header, one XLogRecordBlockHeader appears per page the record touches, naming the relation fork and block number and — critically — an optional flag: does this block reference include a full copy of the page? That full copy is the full-page write (FPW), and it exists to solve exactly the torn-page problem §4 raised: physiological log records only describe a delta ("insert this tuple at this offset"), which is useless for repairing a page whose sectors are a mix of old and new bytes — you'd be applying a delta to a base you can no longer trust.

PostgreSQL's rule (governed by full_page_writes, on by default): the first time any backend modifies a page after a checkpoint completes, the WAL record for that change carries a full 8 KB (minus the unused "hole" between pd_lower and pd_upper, which needn't be logged) image of the page as it looked right before this change. Every subsequent modification to that same page, before the next checkpoint, only needs the small delta — because redo can now always fall back to "restore the full image, then reapply small deltas from there," and the full image itself is written as one contiguous WAL append, immune to being torn independently of the WAL record's own CRC-checked boundaries. The mechanism that decides "first time since checkpoint" compares the page's pd_lsn against the checkpoint's redo pointer, tracked per-relation-fork in shared memory.

THE COST: WAL VOLUME SPIKES RIGHT AFTER EVERY CHECKPOINT

Full-page writes are why WAL volume is not proportional to logical write volume — it's proportional to logical write volume plus a burst of full-page images concentrated in the seconds after each checkpoint, decaying as the working set's hot pages each get their one mandatory full image and settle into cheap deltas. On a busy server with a small, hot working set, this can mean 3–10× the steady-state WAL rate right after checkpoint_completion_target finishes. wal_compression (compressing the full-page image, not the delta) is the direct mitigation — it trades CPU for a smaller burst, and matters most exactly when the burst is largest.

(c) LSN arithmetic: a filename is just an encoded byte offset

An XLogRecPtr is a 64-bit byte address into the logical WAL stream since time zero — nothing more exotic than that. psql renders it as two hex halves, HIGH32/LOW32. The stream is sliced into fixed-size segments (16 MB by default, chosen at initdb time), and a segment's filename is exactly three 8-hex-digit fields — timeline, then the segment number split across a "logical log" boundary of 4 GB — with no separate index anywhere; the filesystem path is the address. (d) Resource managers: the redo dispatch table

xl_rmid is a small integer — RmgrId — indexing into RmgrTable[] (src/backend/access/transam/rmgr.c, built from src/include/access/rmgrlist.h): one entry per subsystem that can produce WAL, each holding function pointers for redo, description/debug-printing, and a few lifecycle hooks. RM_XACT_ID handles commit/abort records, RM_HEAP_ID and RM_HEAP2_ID handle heap tuple operations, RM_BTREE_ID handles B-tree structure changes, and similarly one ID each for hash, GiST, GIN, SP-GiST, BRIN, sequences, CLOG, multixact, and a generic ID for extensions that need their own WAL. During replay, xlogreader.c parses the raw bytes back into a record and hands it to RmgrTable[record->xl_rmid].rm_redo(record) — a single dispatch, no special casing, which is what lets new access methods add WAL support without touching the replay loop at all.

(f) wal_buffers: how much headroom before a backend must wait

WAL buffers are a small ring in shared memory that backends copy freshly reserved records into; the WAL writer (and any backend calling XLogFlush) drains the ring by writing its contents to the segment file and fsyncing. If reservation outruns draining — buffers full before the writer catches up — the reserving backend must itself force a flush and wait, turning a background optimization into a foreground stall. (g) synchronous_commit: choosing exactly what you're willing to lose

XLogFlush() at commit blocks until WAL is durable — but "durable" is a spectrum PostgreSQL exposes directly as a GUC, because "wait for the fsync" and "wait for a replica to also have it" are different guarantees at different costs:

synchronous_commitACK happens after…WHAT A CRASH CAN LOSE
offthe record is copied into WAL buffers — no flush at all yetup to wal_writer_delay (~200 ms default) of the most recently acknowledged commits. The client was told "success" and it can still vanish.

Note what none of these levels touch: whether the transaction is internally consistent. That's governed entirely by the WAL-before-data rule from §6 and holds regardless of synchronous_commit — this GUC only trades how much recently-acknowledged work a crash can erase, never database integrity itself.

ARC 10 · PERFORMANCE CHARACTERISTICS

The physics of fsync, and why it lies to you sometimes

fsync() is not one operation with one cost — its latency is set by the storage medium, and its correctness depends on a chain of caches that must each actually mean it when they say "done":

  • Spinning disk: ~4.2 ms average rotational latency (7200 RPM) plus several ms of seek — ~8–10 ms per random durability round trip, a mechanical constant.
  • SATA SSD: no seek, but protocol and firmware overhead still land a synchronous flush around ~100–300 µs typically — an order of magnitude better, still far from free.
  • NVMe SSD: deeper queues and a leaner protocol bring well-tuned synchronous writes down to roughly ~10–50 µs.
  • Battery-backed (or supercap/PLP) write cache: the drive or RAID controller can honestly say "durable" the instant bytes land in a cache it knows will survive a power loss — ~10 µs, because the physical media write no longer gates the acknowledgment at all.

That last point matters more than the number suggests: a volatile write cache can also say "done" instantly — the difference is that it's lying about durability. Pull the power and its contents are gone, fsync()'s promise notwithstanding. This is why enterprise storage advice treats BBU/PLP as a correctness lever, not merely a performance one: it's the thing that makes the fast answer also the true one.

PostgreSQL lets you choose which kernel primitive protects WAL writes via wal_sync_method: fsync() flushes data and file metadata (size, mtime); fdatasync() skips the metadata sync when the file size hasn't changed, which is cheaper and is a common Linux default; open_datasync folds durability into the write itself via O_DSYNC, avoiding a second syscall round trip entirely. All three are answering the same question through different kernel doors — none of them can make a volatile disk cache tell the truth.

GROUP COMMIT: AMORTIZING THE ONE COST THAT DOESN'T PARALLELIZE

XLogInsert's copy step scales across 8 insert locks (§8e), but the flush is fundamentally one fsync of one shared log tail. If several backends' commit records are all waiting to be flushed at once, one fsync durably covers all of them — this is group commit, and it is why PostgreSQL's commit throughput under concurrent load is often far higher than 1 / fsync_latency would suggest for a single backend. commit_delay (microseconds) and commit_siblings let you trade a small, deliberate added latency for larger batches — useful when fsync is expensive (spinning disk) and many backends commit concurrently; nearly pointless on a device where fsync is already ~10 µs.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents this chapter explains completely

Incident 1: the 2018 fsync() error-handling scare

Craig Ringer's investigation, discussed at length on pgsql-hackers in 2018, surfaced an uncomfortable fact about Linux: when a buffered write later fails to reach disk (an I/O error, a full device), some kernel/filesystem combinations report the error to only the first fsync() call after the failure — and may drop the affected dirty pages from the page cache regardless, rather than keeping them around to retry. A process that calls fsync() again later can receive a clean return code even though the earlier data was never durably written and is now unrecoverable from cache. PostgreSQL had been treating a failed fsync() as something to log and retry — an assumption that the dirty page would still be sitting in cache to try again, which does not hold universally. The fix, landed for PostgreSQL 12, is blunt on purpose: treat any WAL or data fsync() failure as a PANIC, crash immediately, and force a full recovery cycle rather than silently trusting a kernel that may have already lied once. This is the OS-level sibling of the disk-cache lie discussed in §10 — the write cache isn't the only layer that can quietly drop your durability guarantee.

Incident 2: full_page_writes=off on storage that didn't actually guarantee it

full_page_writes=off is a documented, legitimate optimization — if and only if the underlying storage genuinely guarantees atomic writes at PostgreSQL's full page size (8 KB, or your configured BLCKSZ). Teams running on general-purpose cloud block storage have disabled it assuming "it's redundant, our storage is durable" — conflating durable (survives power loss once acknowledged) with atomic at 8 KB (never partially written). Generic block storage historically guarantees atomicity only at much smaller granularities (a sector, or the underlying device's native block size), not at a full Postgres page. The result, discovered only much later during an unrelated crash: invalid page in block N of relation errors and checksum failures on pages that recovery had no full image to repair, because there was none to fall back to. The operational lesson generalizes: full_page_writes=off requires a written guarantee from the storage vendor about atomic write size, not an assumption from "durable" marketing copy.

Incident 3: asynchronous replication, a failover, and the transactions that were never there

A common production shape: synchronous_commit left at a level that doesn't wait on any standby (or no synchronous standby configured at all), streaming replication running normally with a small, healthy lag of a few WAL records. An unplanned failover promotes the standby. The application had received "COMMIT successful" for the last handful of transactions before the primary died — and those transactions are simply absent on the newly promoted primary, because their WAL never made it across before the failure. From the business's perspective: an order confirmed, a payment recorded, that no longer exists anywhere. This is not a bug; it is precisely what asynchronous replication (and any synchronous_commit level short of one that waits on the standby) advertises it will do under failover. The fix is a deliberate tradeoff, not a patch: adopt synchronous_commit=on or remote_apply together with synchronous_standby_names for the transactions that must survive a failover, accepting the added commit latency as the price of that guarantee — the same tradeoff table from §8g, now with real money attached.

First, how a backend gets bytes into the log — reservation is a tight CAS loop; the copy happens outside any single global lock:

Cxloginsert.c — XLogInsertRecord(), simplified but faithful in structure
XLogRecPtr
XLogInsertRecord(XLogRecData *rdata, XLogRecPtr fpw_lsn, uint8 flags, ...)
{
    uint32 tot_len = CalcSizeOfXLogRecord(rdata);   /* header + block refs + data */

    /* 1. RESERVE: an atomic bump of the shared "current end of log"
     *    pointer. This is the ONLY globally-serialized step — it's a
     *    tiny compare-and-swap, not a memcpy.                        */
    XLogRecPtr StartPos, EndPos;
    ReserveXLogInsertLocation(tot_len, &StartPos, &EndPos, &rechdr.xl_prev);

    /* 2. COPY: take ONE of NUM_XLOGINSERT_LOCKS (8) locks — chosen so
     *    up to 8 backends copy their already-reserved bytes into the
     *    shared WAL buffer ring in parallel, none blocking the others. */
    int slot = MyProc->pgprocno % NUM_XLOGINSERT_LOCKS;
    WALInsertLockAcquire(slot);
    CopyXLogRecordToWAL(tot_len, rdata, StartPos, EndPos);
    WALInsertLockRelease(slot);

    /* Caller decides whether/when to force this durable — a commit
     * record's caller will call XLogFlush(EndPos) right after.       */
    return EndPos;
}

Then the flush — the one genuinely serial step, and the one every commit ultimately waits behind:

Cxlog.c — XLogFlush(), simplified
void
XLogFlush(XLogRecPtr record)
{
    if (XLogCtl->LogwrtResult.Flush >= record)
        return;      /* someone else's flush already covered us — group commit */

    WALWriteLock_Acquire();
    if (XLogCtl->LogwrtResult.Flush < record)
    {
        XLogWrite(WriteRqst);          /* write() the buffered bytes to the segment file */
        if (!issue_xlog_fsync(openLogFile, ...))
            ereport(PANIC, (errmsg("could not fsync WAL segment")));
        XLogCtl->LogwrtResult.Flush = EndPos;
    }
    WALWriteLock_Release();
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Separate the serialized part from the parallel part. Only the pointer bump is globally atomic; everything expensive (the memcpy) happens under one of 8 locks chosen by backend, so most concurrent inserts never contend at all. 2. Make the flush idempotent-checkable. XLogFlush's first line is "did someone already flush past me?" — the mechanism that makes group commit free: a busy server's flushes naturally cover many backends' commit records in one fsync. 3. Treat a failed fsync as unrecoverable, on purpose. The PANIC in XLogFlush (added for PG12 after the incident in §11) encodes "we cannot prove what's actually on disk anymore, so stop and let full recovery re-establish ground truth" — the same philosophy chapter 1's crash protocol uses for a dying backend, applied here to a lying kernel.
