Testing & Tooling:
Proving It Instead of Trusting It

By chapter 13 you can write a function, give it a proper error type, and propagate failures with ?. None of that answers an older, more important question: how do you actually know any of it is correct — today, and still correct after the next five commits touch it? This chapter is about the machinery Rust bakes directly into cargo to answer that question mechanically instead of by inspection: #[test] and the assert! family, integration tests that see your crate the way a real caller does, doc tests that make your documentation's examples fail the build the moment they stop being true, and the three tools — clippy, rustfmt, and criterion — that turned "well-tested Rust" into something closer to a default than an aspiration.

ARC 01 · THE PROBLEM

"It compiled" was never the bar

Every chapter so far has leaned on one enormous safety net: if a program compiles, whole classes of bugs — use-after-free, data races, null dereferences, iterator invalidation — are already ruled out by construction. It is tempting, especially in Rust, to let that safety net quietly become "if it compiles, it's probably fine." It is not fine. The borrow checker proves your memory is used validly; it has no opinion at all on whether is_prime(2) returns true. Logical correctness is a completely separate axis from memory safety, and Rust does not check it for you — you have to build a system that does.

Unpack "know the code is correct, and stays correct" and it splits into five requirements that pull against each other just as hard as any hard engineering tradeoff does:

  • Repeatability. The same input must produce the same verdict every time, on every machine, in CI and on your laptop — not "it worked when I ran it locally five minutes ago."
  • Automatic verdicts. A machine, not a human scanning terminal output, must decide pass or fail from a real comparison. Attention is a scarce, unreliable resource; comparison operators are not.
  • Boundary-accurate coverage. Tests must check what a real caller of your public API can actually do — not just whatever is convenient to reach from inside the same file, where every private field is visible and every invariant is easy to violate by accident.
  • Documentation that cannot quietly lie. An example in a doc comment that nobody re-verifies is not documentation, it's a liability with a countdown timer — every refactor is a chance for it to go stale.
  • Performance claims that are provable, not vibes. "This feels fast enough" is not evidence, and a single stopwatch reading is barely better — §10 makes this precise.

Rust's answer bundles a test harness, a documentation-testing system, a supplementary linter, a deterministic formatter, and a statistical benchmarking ecosystem into (or immediately alongside) the same cargo you already use to build. That bundling — not any one piece of it — is the actual subject of this chapter.

WHY THIS MATTERS FOR THE REMAINING ADVANCED CHAPTERS

Chapter 15 begins the ADVANCED tier with concurrency, and from that point on, "did I get this right" stops being something you can verify by reading the code carefully — data races and deadlocks are exactly the class of bug that hides from a human review and shows up only under real, repeated execution. Chapter 17's unsafe code goes even further: the compiler stops checking large categories of correctness for you entirely, on your explicit promise that you checked instead. Everything in this chapter — the discipline of writing an executable, automatically-run claim about what your code does — is the tool you'll actually reach for to keep that promise honest.

DEEP CONTEXT · WHY CLIPPY IS NAMED CLIPPY

The name is a knowing joke: like Microsoft Office's much-mocked "Clippy" assistant, Rust's clippy watches what you're doing and interrupts with unsolicited advice — the difference is that Rust's version is usually right. It began as Manish Goregaokar's side project around 2014, aimed at catching idiomatic mistakes that are perfectly valid Rust (so rustc has no reason to reject them) but are nonetheless usually wrong: needless clones, single-armed matches, comparing a float to itself. Both clippy and rustfmt spent years as "install this separately" community tools before graduating to official, rustup-distributed components in 2018 — the same year the ecosystem effectively decided that formatting and linting were no longer optional extras but part of what "having Rust installed" means.

ARC 03 · NAIVE SOLUTION

Attempt #1: print it and look at it

Derive the architecture honestly, starting from the simplest thing that could possibly work. Say you've written a small primality-testing function. The naive way to "test" it is to call it a few times from main() and read the output yourself:

Rustsrc/main.rs — the strawman, and it really does compile
fn main() {
    println!("is_prime(2)  = {}", is_prime(2));
    println!("is_prime(3)  = {}", is_prime(3));
    println!("is_prime(4)  = {}", is_prime(4));
    println!("is_prime(17) = {}", is_prime(17));
    // ...then a human reads five lines of terminal output and checks each by eye.
}

fn is_prime(n: u64) -> bool {
    if n <= 2 { return false; }   // looks reasonable at a glance...
    for i in 2..n {
        if n % i == 0 { return false; }
    }
    true
}

This is not a joke architecture — it is exactly how most people write their first program in any language, and at this scale it even mostly works: run it, glance at four lines, ship it. Notice the bug sitting in plain sight: n <= 2 means is_prime(2) prints false, and 2 is the smallest prime number. A careful reader catches it. A tired reader, or a reader checking forty printed lines instead of four, does not — and nothing about this program stops them from shipping it either way.

ARC 04 · WHY IT FAILS

Manual verification doesn't scale — and it doesn't even repeat

The print-and-eyeball approach fails for reasons worth stating precisely, because each one motivates a specific piece of this chapter's machinery:

  • No automatic verdict. Nothing in the program itself knows that is_prime(2) was supposed to print true. The "test" only exists in the reader's head, at the moment they read it — the instant they look away, the check is gone.
  • No re-run. Six months later someone "simplifies" the loop bound and reintroduces the exact same bug. Nobody reruns the mental check from six months ago, because there is nothing to rerun — it was never recorded as an artifact, only performed once as an act of attention.
  • Doesn't scale with the reviewer, only with the codebase. Ten checks fit in a code review comfortably. A thousand do not — but a thousand assertions run by a machine in under a second cost the reviewer nothing at all. The naive approach's cost grows with the number of things you check; the automated approach's does not.
  • Tests nothing about the public boundary. A main() in the same file can call anything, private or not. It cannot tell you whether the function still works the way an external caller — someone who only sees what you marked pub — would actually use it.
  • One panic takes everything down. If an early println! line were replaced with a real check that panics on failure, the very first failing check would abort the process before later checks ever ran — you'd learn about exactly one problem per run, not all of them.
THE NUMBERS

Barry Boehm's long-cited software-economics work puts the relative cost of fixing a defect found in production at roughly an order of magnitude (or more) higher than fixing the same defect during development — the exact multiplier varies by study and era, but the shape is uncontroversial and still widely taught: the later a bug is caught, the more it costs. A print-and-eyeball "test" is the slowest possible way to catch anything, because it only runs when a human remembers to run it and look — which in practice means: rarely, and never automatically, on every single commit.

So we need three things a human-in-the-loop check cannot give us: automatic pass/fail, a record that reruns itself forever, and a way to check the public boundary specifically. Rust's built-in test harness is built to give you exactly those three things, at three different granularities.

ARC 05 · BETTER SOLUTION

From println! to #[test]: the same checks, made real

Walk the naive script through the transformation, one deliberate step at a time.

Turning eyeballed output into an automatic verdictSTEP-BY-STEP

Two more granularities follow the same idea outward from the crate: a doc test makes the example in your own documentation the executable check, and an integration test moves the check outside the crate entirely, so it can only see what you actually decided to make public.

THE THREE GRANULARITIES, AT A GLANCE

Unit tests (usually in a #[cfg(test)] mod tests at the bottom of the same file) run inside your crate and can see private items — best for checking internal logic and edge cases up close. Integration tests (files under a top-level tests/ directory) are compiled as an entirely separate crate that depends on yours the way any real user would, via use your_crate::...; — they can only reach pub items, which is precisely the point. Doc tests (fenced code blocks inside /// or //! comments) are extracted, compiled, and run as their own tiny programs — they double as living proof that your documentation still matches your code. One command, cargo test, runs all three.

ARC 06 · WHY THAT STILL HURTS

The bill arrives: what this machinery costs

None of this is free, and being honest about the costs is part of using the tools well:

  • Compile time multiplies. Every file under tests/ is compiled as its own crate, linked against your library's rlib independently. Ten integration test files means ten separate compilations of (at least) the linking step, not one. Doc tests pay a similar tax — each fenced example becomes its own tiny compiled binary.
  • Parallelism hides state-sharing bugs until it doesn't. cargo test runs tests concurrently, one OS thread per test, by default. Two tests that quietly share global mutable state — a fixed temp-file path, an environment variable set via std::env::set_var, a shared static — can now race, producing a test that fails only sometimes, on some machines, in some thread interleavings. §11 covers a real, ecosystem-wide incident in exactly this shape.
  • Clippy is opinionated, and opinions cause friction. Beyond its default lints, clippy's optional stricter groups (§8) are real and useful but noisier — teams that turn them on without a plan for triaging the results tend to turn them straight back off, which defeats the purpose.
  • rustfmt's configuration surface is deliberately narrow. It settles style arguments by refusing to have most of them — which is exactly why some teams' preferred conventions simply cannot be expressed, on purpose.
  • Criterion benchmarks are slow to run by design. Getting a trustworthy confidence interval instead of one noisy number (§10) means running a function far more times than you'd naively want to, which can turn cargo bench into a multi-minute affair even for a genuinely tiny function.

None of these costs are reasons to skip the machinery — they're reasons to understand what you're actually paying for, so the next two sections can show you the shape you're paying to get.

ARC 08 · INTERNAL IMPLEMENTATION

What cargo test, clippy, and rustfmt actually do

Now the real mechanism, at the level you'd need in order to explain a strange failure to a teammate. Three pieces: (a) how #[test] becomes a runnable program, (b) clippy's real lint categories with real before/after lints, (c) why rustfmt's determinism is the whole point.

(a) #[test] is a compiler attribute, not a macro — and it generates a whole program for you

cargo test compiles your code with an implicit --test flag. That flag tells rustc to synthesize an entire main() you never write, built around a table of every function you marked #[test]. Step through what that table and driver actually look like — simplified, but structurally faithful to the test crate every Rust toolchain ships (library/test in the rust-lang/rust source tree).

From #[test] to a running binarySTEP-BY-STEP
WHY ONE PANIC NEVER TAKES DOWN THE OTHER TESTS

Each #[test] function runs on its own OS thread by default. A panicking assertion unwinds that stack only; libtest wraps every test's call in std::panic::catch_unwind, records the unwind as a failure with its message, and moves on to report the next test's real, independently-computed result. Compare this directly to §3's naive main(): a panic there ends the process immediately, so every check after the first failure simply never runs at all.

(b) Clippy: a second compiler pass, grouped into real, named categories

Clippy is not part of rustc — it's a separate driver (clippy-driver, invoked as cargo clippy) that runs the same front-end compilation up through HIR (a desugared, typed representation of your code) and then walks it with several hundred extra lint passes that plain rustc intentionally doesn't run, because they check idiom and intent, not just validity. They're organized into named groups with different default levels:

  • correctness — deny by default. Patterns that are almost certainly bugs, e.g. clippy::eq_op (comparing an expression to itself, like x == x, usually a copy-paste mistake).
  • suspicious — warn by default. Code that compiles and often does the wrong thing without being outright broken, e.g. clippy::suspicious_arithmetic_impl (an impl Add whose body quietly uses -).
  • style — warn by default. Valid Rust that has a clearer idiomatic form.
  • complexity — warn by default. Code that does something the hard way.
  • perf — warn by default. Correct code with an avoidable runtime cost.
  • pedantic — off by default, opt in with #![warn(clippy::pedantic)]. Real and useful, but opinionated enough that clippy's own maintainers keep it out of the default set.
  • nursery — off by default. Lints still under active development, explicitly allowed to have bugs.

Three real lints, with the actual before/after transformation:

Rustclippy::single_match — style
// clippy flags this: a match with exactly one meaningful arm and a "_ => {}" catch-all
match config.mode {
    Mode::Fast => set_fast(),
    _ => {}
}

// suggested fix — says exactly what it means
if config.mode == Mode::Fast {
    set_fast();
}
Rustclippy::redundant_clone — perf
// clippy flags this: `s` is never used again after the clone, so cloning bought nothing
fn print_len(s: String) {
    let s2 = s.clone();
    println!("{}", s2.len());
}

// suggested fix — s was already owned; just use it, no allocation needed
fn print_len(s: String) {
    println!("{}", s.len());
}
Rustclippy::clone_on_copy — complexity
// clippy flags this: i32 is Copy, so .clone() is already just a bitwise copy in disguise
let x: i32 = 5;
let y = x.clone();

// suggested fix — says exactly what happens, costs nothing different
let x: i32 = 5;
let y = x;

None of these three change what the program computes — that's the point of drawing the line between correctness (near-certain bugs, deny by default) and everything else (idiom and cost, warn by default, always #[allow]-able with a reason).

(c) rustfmt: deterministic by construction, configurable on purpose only a little

rustfmt parses your source into the same kind of AST the compiler itself builds, then re-emits it following a fixed, published style — with no memory of how you originally wrote it. Feed it the same input twice and you get byte-identical output both times (it is idempotent: formatting already-formatted code is a no-op). That determinism is what makes cargo fmt --check enforceable in CI without a human referee:

Rustbefore cargo fmt
fn is_prime(n:u64)->bool{if n<2{return false;}for i in 2..n{if n%i==0{return false;}}true}
Rustafter cargo fmt — deterministic, no second opinion possible
fn is_prime(n: u64) -> bool {
    if n < 2 {
        return false;
    }
    for i in 2..n {
        if n % i == 0 {
            return false;
        }
    }
    true
}

There is exactly one "correctly formatted" version of any given input. A code-review argument about brace placement or line width has, mechanically, nothing left to argue: either the tree matches rustfmt's one answer, or it doesn't.

Six tools, six different bargains

Each layer of §7's model trades something specific for something specific. Read the table as a proof by exhaustion — every tool here buys a guarantee at a real, nameable cost:

It's also worth being honest about how unusual this bundle is. pytest is a third-party install for Python, not part of the language; JUnit needs Maven or Gradle wiring before it runs anything; Jest bundles a runner, assertions, and mocking for JavaScript but is still an opt-in npm package a project chooses (or doesn't). cargo test, cargo fmt, and cargo clippy ship with every rustup install — the ecosystem made "your project has tests, formatting, and linting" closer to a default than an opt-in decision, at the real cost of a narrower, more opinionated surface than any of those bolted-on alternatives allow.

ARC 10 · PERFORMANCE & BENCHMARKING

Why a stopwatch lies to you, and what criterion does instead

Correctness tests answer "does it return the right answer." Benchmarks answer a completely different question — "how expensive is it" — and that question turns out to be much easier to measure wrong. Start with the honest, real complexity gap a benchmark exists to catch: the naive is_prime from §3 checks every integer from 2 up to n - 1, an O(n) function; stopping the loop at ⌈√n⌉ instead (any factor pair of a composite number has one factor ≤ its square root) makes it O(√n) — a difference invisible on small inputs and enormous on large ones.

Knowing that gap exists in theory doesn't tell you whether a specific change made things faster or slower in practice — for that you have to actually time the code, and timing correctly is its own discipline. Walk through it from the naive stopwatch approach to criterion's real one:

Measuring correctly: a real criterion walkthroughSTEP-BY-STEP
NOT A JIT — SOMETHING SUBTLER

If you've benchmarked JVM or V8-hosted code, "warm-up" means letting a just-in-time compiler upgrade your code from an interpreted or lightly-optimized form to fully-optimized machine code over the first several thousand calls — a real, large, one-time effect. Rust has no runtime JIT: the machine code criterion measures is exactly the machine code that shipped, finalized entirely at compile time, before your program ever ran a single instruction. Criterion's warm-up phase exists for entirely different, still-real reasons: modern CPUs run at a reduced clock speed until sustained load asks for more (dynamic frequency scaling), and a cold instruction/data cache genuinely serves the first several thousand iterations slower than the steady state. Skip the warm-up and you measure the CPU spinning up, not your function.

ARC 11 · REAL-WORLD PRODUCTION

Three stories about what happens when this discipline slips — or scales

Incident 1: the actix-web unsoundness saga (early 2020)

A security researcher filed a series of GitHub issues against actix-web, one of the most widely used Rust web frameworks at the time, cataloguing multiple genuinely unsound uses of unsafe — code that could trigger undefined behavior from ordinary, fully safe calling code, not just from deliberate misuse. That distinction matters: unsoundness means the compiler's own safety story is broken for that crate, regardless of how carefully any caller writes their code. The maintainer initially closed several reports without fixing them; the resulting public backlash (extensively discussed across the Rust community at the time) forced a reversal, a real audit, and a much closer relationship afterward between the project and tools like Miri (§7's seventh tool) that exist specifically to catch what compiling cleanly and passing every #[test] cannot.

Incident 2: RUSTSEC-2020-0071 — a real segfault from an environment-variable race

The time crate (and transitively, for a period, chrono) shipped code that called into C's localtime_r to read the local timezone. On Unix, that function is not safe to call concurrently with anything that mutates the process environment — and std::env::set_var does exactly that, with no synchronization against readers on other threads. The result, tracked as the real RustSec advisory RUSTSEC-2020-0071 (and CVE-2020-26235), was a genuine, reproducible segfault class affecting any multi-threaded program that mixed the two. It's the exact hazard §6 named in the abstract — global mutable process state, raced by concurrently-running code — except this time it wasn't a flaky test suite, it was a real advisory that cargo audit would flag for any dependent crate.

Incident 3: the standard library's own doc tests, running on every PR, at enormous scale

A calmer, positive case study: the Rust standard library's own documentation contains thousands of runnable code examples inside /// comments, and they are genuinely compiled and executed as part of the compiler's own test suite on every pull request to rust-lang/rust. This is the same doc-test mechanism from §5, just run at the scale of the language's own standard library — a stale or wrong example in std::vec::Vec's docs is not a hypothetical embarrassment waiting to be noticed by a reader, it's a build failure blocking the PR that introduced it. It's the single largest, longest-running demonstration that "documentation that can't quietly lie" (§1's fourth requirement) is achievable in practice, not just in theory.

Rustsrc/lib.rs — the public API, its doc test, and its unit tests
/// Returns `true` if `n` is a prime number.
///
/// A number is prime if it is greater than 1 and has no positive
/// divisors other than 1 and itself.
///
/// # Examples
///
/// ```
/// use mathkit::is_prime;
///
/// assert!(is_prime(2));
/// assert!(is_prime(17));
/// assert!(!is_prime(1));
/// assert!(!is_prime(8));
/// ```
pub fn is_prime(n: u64) -> bool {
    if n < 2 {
        return false;
    }
    if n == 2 {
        return true;
    }
    for i in 2..n {
        if n % i == 0 {
            return false;
        }
    }
    true
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn two_is_prime() {
        assert_eq!(is_prime(2), true);
    }

    #[test]
    fn four_is_not_prime() {
        assert!(!is_prime(4));
    }
}
Rusttests/prime_integration.rs — a real external-crate consumer
// This file is compiled as an INDEPENDENT crate. It can only see `pub` items —
// exactly what a real downstream Cargo.toml dependency would see.
use mathkit::is_prime;

#[test]
fn primes_under_20() {
    let primes: Vec<u64> = (2..20).filter(|&n| is_prime(n)).collect();
    assert_eq!(primes, vec![2, 3, 5, 7, 11, 13, 17, 19]);
}
Rustbenches/prime_bench.rs — a real criterion harness
use criterion::{criterion_group, criterion_main, black_box, Criterion};
use mathkit::is_prime;

fn bench_is_prime(c: &mut Criterion) {
    c.bench_function("is_prime 999983", |b| {
        b.iter(|| is_prime(black_box(999_983)))
    });
}

criterion_group!(benches, bench_is_prime);
criterion_main!(benches);
TOMLCargo.toml — the wiring that makes cargo bench work at all
[package]
name = "mathkit"
version = "0.1.0"

[dev-dependencies]

This one line is the real, necessary seam between "the built-in test harness" and "a statistically rigorous benchmark harness" living in the same crate.
