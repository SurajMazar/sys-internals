UBER ENGINEERING INTERNALS · CHAPTER 10

The Event Backbone:
Streaming at Uber Scale

A single trip completing at Uber is not one fact consumed by one system — it is one fact that payments, receipts, ratings, fraud detection, and a dozen analytics pipelines all need, on their own schedule, without any of them blocking the others or blocking the trip itself. This chapter derives why that requirement forces an asynchronous, durable, replayable event backbone, what a schema registry and event contract actually buy you once hundreds of independently-deployed services publish and subscribe to it, and how one event fans out to many consumers without becoming a distributed bottleneck.

ARC 01 · THE PROBLEM

One fact, many independent readers, zero shared clock

By the time you reach this chapter, Uber's backend is no longer one program — it is thousands of independently deployed services (chapter 8) talking over synchronous RPC calls routed through a service mesh (chapter 9). Synchronous calls are the right tool when the caller needs an answer to keep going: "is this rider's payment method valid?" But a huge share of what happens inside Uber is not a question that needs an answer — it is an announcement. "This trip just completed." Nobody making that announcement should need to know, or care, who is listening.

Unpack what a single trip-completed announcement actually has to reach:

  • Payments — must charge the rider's stored payment method exactly once.
  • Receipts — must generate and email/push a fare breakdown.
  • Ratings — must open a rating prompt for both rider and driver.
  • Driver payouts — must credit the driver's earnings ledger.
  • Fraud/risk — must score the trip for anomalies (impossible routes, fare manipulation).
  • Analytics & data warehouse — must land the event for dashboards, experimentation, and forecasting, often hours or days later.

Every one of those consumers has a different processing rate, a different failure mode, and a different tolerance for delay. Payments must be fast and exactly-once. The data warehouse is fine processing in batches an hour late. Fraud scoring might briefly fall behind during a traffic spike and catch up overnight with no rider-visible consequence. A single mechanism that forced all of these to consume the event synchronously, in the same request, would be optimizing for the slowest, least available consumer in the entire list — which is exactly the naive design this chapter starts from and dismantles.

THE SHAPE OF THE PROBLEM

This is a classic fan-out problem, and it recurs at every layer of a system this size: trip lifecycle events (chapter 7) firing into this backbone, location pings (chapter 3) streaming through a similar path, and — as chapter 11 will show — even observability data itself flows through comparable pipes. Solve fan-out once, well, and every one of those becomes a special case of the same mechanism.

ARC 02 · HISTORICAL CONTEXT

From point-to-point calls to a shared backbone

The event backbone did not appear on day one — it became necessary at exactly the moment the monolith-to- microservices migration (chapter 8) turned "notify the other systems a trip finished" from a function call inside one process into a cross-service coordination problem involving dozens, and eventually hundreds, of independently owned consumers. DEEP CONTEXT · WHY A LOG, NOT JUST A QUEUE

Uber's real event backbone runs on Apache Kafka's distributed commit log as its transport — the partition, replication, and consumer-group mechanics that make that log durable and horizontally scalable are the subject of this site's dedicated Kafka Internals course and are not re-derived here. What matters for this chapter is the property a log gives you that a plain message queue doesn't: events are retained and replayable, so a brand-new consumer service launched next quarter can read events from days ago, and an existing consumer that crashes can resume from exactly where it left off instead of losing whatever was in flight.

ARC 03 · NAIVE SOLUTION

Attempt #1: the trip service calls everyone directly

Derive it honestly, the way the naive service-mesh caller in chapter 9 would: when a trip completes, the trip service simply calls every downstream service's API, synchronously, in a loop, before returning success to the mobile client.

pseudocodetrip_service.on_trip_completed() — the strawman
function onTripCompleted(trip) {
    // Naive: notify every interested system inline, one call at a time.
    paymentsService.charge(trip.riderId, trip.fare);          // must succeed
    receiptsService.sendReceipt(trip.id);                    // nice to have, now
    ratingsService.openPrompt(trip.id);                      // nice to have, now
    payoutsService.creditDriver(trip.driverId, trip.fare);   // must succeed
    fraudService.score(trip.id);                            // can be slow
    analyticsService.record(trip);                          // can be hours late

    return "trip completed";   // only returns once ALL six calls finish
}

Like every naive solution in this course, this one is not stupid — it is the obvious first cut, and it gets one thing right immediately: it is trivially easy to reason about. There is one code path, one trace, and if everything succeeds, everything is consistent by construction the moment onTripCompleted returns. The problem is what it costs, and the cost is not a rounding error — it compounds with every new consumer anyone ever adds.

ARC 04 · WHY IT FAILS

Coupling six services' availability and six services' latency into one

Two failure modes compound here, and both are quantifiable — this is not a vibe, it's arithmetic you can run on a whiteboard.

Availability multiplies, it doesn't average

If each of the six downstream calls is independently up 99.9% of the time, and the trip-completion path calls all six synchronously and requires all six to succeed, the combined success probability is the product, not the average:

THE MATH

0.9996 ≈ 0.994 — six "three nines" services chained synchronously degrade to roughly 99.4% combined availability, which is worse than any single one of them. Add the eight services chapter 8 says a mid-size Uber deployment already had by the microservices era, and six independent 99.9% dependencies becomes fourteen: 0.99914 ≈ 0.986 — nearly a full order of magnitude more downtime than any individual dependency, purely from chaining. And every new consumer team adds to the product, degrading a metric they don't own and usually can't even see.

Latency is bounded by the slowest call, not the median

The trip-completion response can't return until every call finishes (or times out). If five calls take ~20 ms and fraud scoring occasionally spikes to 4 seconds under load, every rider — including the ones whose trip had nothing unusual about it — waits behind fraud scoring's tail latency. The naive design makes the rider-facing experience hostage to the slowest, least rider-relevant consumer in the list.

The coupling problem compounds structurally

Every new consumer requires a code change and a redeploy of the trip service itself — the one team that owns "did the trip complete" now also owns a growing, unrelated fan-out list, and a bug in any downstream client library (a bad timeout, a thrown exception) can take down trip completion for every rider, not just the feature that broke. This is precisely the deploy-coupling failure mode chapter 8 introduced for code — here it reappears for event delivery.

THE UNDERLYING SHAPE

Generalize it: with N event types and M consumers per type, naive point-to-point wiring needs on the order of N×M integrations, each a synchronous dependency added to whoever produces the event. Every new consumer is a new outage vector for a producer team that has no reason to know the consumer exists. We need to decouple publishing a fact from reacting to it.

ARC 05 · BETTER SOLUTION

Decoupling publish from react, one step at a time

Step through the evolution from tightly-coupled synchronous calls to the architecture Uber actually runs. Each step removes one specific coupling from the naive design.

From direct calls to a shared, replayable logSTEP-BY-STEP

By the last step, the trip service's job has shrunk to exactly one responsibility: publish a well-formed trip.completed event once. It has zero knowledge of who reads it, how many readers there are, or how fast any of them process it — and that ignorance is the entire point. Availability and latency for trip completion no longer depend on payments, receipts, ratings, payouts, fraud, or analytics at all.

ARC 06 · WHY THAT STILL HURTS

Decoupling doesn't delete the hard problems — it relocates them

The backbone removes synchronous coupling, but it introduces its own costs, each traceable to a specific design choice made in §5:

  • Schema drift becomes everyone's problem at once. The moment dozens of teams independently consume the same event stream, a producer renaming or retyping a field silently breaks every consumer that reads it — and because delivery is asynchronous, the breakage surfaces minutes or hours later, far from the deploy that caused it, in a completely different team's on-call rotation.
  • "Eventually" is a real number, and it's not always small. A consumer group that falls behind — because its own dependency is slow, or it just got redeployed and is replaying a backlog — accumulates consumer lag. Payments falling behind by even a few minutes is operationally very different from analytics falling behind by a few hours, but the backbone itself doesn't know that — it just stores bytes.
  • Replay is a superpower and a hazard in the same breath. The ability to replay historical events (new consumer backfilling six months of history, or a consumer recovering from a bug by reprocessing) is exactly what makes a durable log worth the operational cost over a destructive queue — but replaying millions of historical events at full speed against live systems can look, to those systems, exactly like a traffic spike or a duplicate-event storm.
  • Cross-region delivery adds a second network hop with its own failure modes. Uber runs multiple regions (chapter 17 covers this in depth for the datastore layer); an event produced in one region that must reach consumers or a data lake in another has to cross a replication link that can itself lag or partition, on top of whatever lag already exists locally.
THE INDUSTRY'S ANSWER — AND ITS ADMISSION

Every company operating an event backbone at this scale ends up building (or adopting) two things this chapter treats as first-class: a schema registry that makes contract-breaking changes a rejected publish instead of a silent runtime failure, and an audit pipeline that independently counts what was produced against what was consumed, because "the log never drops anything" is a property you have to verify continuously, not a guarantee you get for free.

ARC 08 · INTERNAL IMPLEMENTATION

Event contracts, schema enforcement, and independent fan-out

Three mechanisms do the actual work: (a) the event contract itself, (b) the schema registry's compatibility check that runs on every publish, and (c) the fan-out mechanism that lets four consumers read the same event at four different speeds without contention.

(a) The event contract

An event contract is a versioned, machine-checked schema — the thing that lets a producer team and a dozen consumer teams, none of whom talk to each other day to day, agree on a shape without a meeting:

schematrip.completed — v3, illustrative event contract
{
  "event": "trip.completed",
  "schema_version": 3,
  "fields": {
    "trip_id":      { "type": "string",  "required": true },
    "rider_id":     { "type": "string",  "required": true },
    "driver_id":    { "type": "string",  "required": true },
    "fare_cents":   { "type": "long",    "required": true },
    "currency":     { "type": "string",  "required": true },
    "completed_at": { "type": "timestamp","required": true },
    "surge_multiplier": { "type": "double", "required": false, "default": 1.0 } // added in v2, optional — see (b)
  }
}

(b) Compatibility checking at publish time

The schema registry's core job is to reject a schema change before it can reach a single consumer, by classifying the change against the previous version:

pseudocoderegistry.checkCompatibility() — illustrative, not literal internal source
function checkCompatibility(newSchema, prevSchema) {
    // BACKWARD compatible: consumers still on the OLD schema can read NEW events.
    // This is the bar Uber's real event contracts are held to before a publish is accepted.
    for (field of prevSchema.required) {
        if (!newSchema.has(field))
            return reject(`removed required field '${field}' — old consumers will crash on missing data`);
        if (newSchema.typeOf(field) !== prevSchema.typeOf(field))
            return reject(`changed type of '${field}' — old consumers will misparse it`);
    }
    for (field of newSchema.addedSince(prevSchema)) {
        if (field.required)
            return reject(`new field '${field.name}' is REQUIRED — old producers can't supply it yet`);
        // new OPTIONAL fields with a default are fine: old consumers ignore them,
        // new consumers get the default when reading old events. This is exactly
        // how surge_multiplier was added in v2 without breaking anyone.
    }
    return accept();
}

(c) Independent fan-out and consumer lag

Once an event is durably in the log, every subscribing service reads it through its own independent consumer group — a bookmark into the log that belongs to that service alone. Slow it down, pause it, restart it: no other consumer group is affected, because none of them share that bookmark. ARC 09 · TRADEOFFS

Three ways to move a fact from one service to many

APPROACHWHAT IT BUYSWHAT IT COSTS
Synchronous point-to-point calls simplest mental model immediate consistency availability multiplies down with each consumer latency bounded by slowest call every new consumer redeploys the producer
Traditional message queue (destructive read, competing consumers) decouples producer from consumer timing simple operational model once read, a message is gone — one consumer group only no replay for new or recovering consumers
Durable, partitioned, replayable log (Uber's real approach) any number of independent consumer groups replay for new consumers & recovery producer never learns who reads it schema governance becomes mandatory, not optional operating the backbone itself is a serious systems job

Read this as the fan-out version of the tradeoff table from chapter 1's process model, or chapter 9's mesh: there is no dominant choice, only a different place to pay the cost. Uber's real backbone pays operational complexity — running and auditing a large distributed log — to buy every consumer team the ability to move, fail, and redeploy on its own schedule.

ARC 10 · PERFORMANCE / SCALE CHARACTERISTICS

What the numbers look like at this scale

Uber's engineering blog has publicly described its Kafka-based backbone operating at enormous volume — well over a trillion messages a day flowing across thousands of topics, serving both the trip/rider-facing path and the much larger stream of location pings and analytics events. Exact figures move over time and aren't the point; the point is the shape of the cost as fan-out grows.

  • Storage cost scales with retention × volume, not with consumer count. Ten consumer groups reading the same topic cost the log almost nothing extra — they each just track their own read position. This is the single biggest structural win over point-to-point calls, where every new consumer added onto the producer's own request path.
  • Consumer lag is the operational health signal, not producer-side latency. A producer's publish latency stays flat regardless of how far behind any consumer falls — which is exactly why lag has to be monitored per consumer group explicitly (chapter 11 shows the observability machinery that watches it).
  • Replay cost is proportional to how much history you re-read, not to how the log is organized. Backfilling a new consumer over six months of trip-completed events means reading six months of events — there's no shortcut, which is exactly why retention windows and compaction policies are a real cost decision, not a free knob.

The point that survives any specific number: recovery time is not linear in outage time once the backlog is large enough that catch-up rate matters — this is precisely why "how fast can this consumer drain a backlog" is a capacity-planning question worth answering before the outage happens, not during it.

ARC 11 · REAL-WORLD INCIDENTS

Two failure modes every event-backbone operator eventually meets

Incident 1: the silent schema break

Uber's own engineering blog on Chaperone — the auditing tool built specifically for this backbone — is explicit that undetected data loss and duplication across an asynchronous pipeline was exactly the class of problem that motivated building a dedicated audit system in the first place, precisely because nothing about a distributed log's normal operation tells you, on its own, whether every event that was produced was also faithfully delivered and consumed. The general pattern this defends against is well documented across the industry: a producer narrows a field's type, or renames it, believing "nobody's using the old name anymore" — and one consumer team, on a slightly older schema version, starts silently dropping or misparsing records. Nothing crashes loudly; a report just quietly goes wrong days later. Where the exact internal detection thresholds Uber uses aren't public, the honest general lesson is this: an async pipeline needs an independent count reconciliation between what was produced and what each consumer actually processed — you cannot infer correctness from the absence of errors.

Incident 2: the reconnect-storm-shaped replay

This is a realistic, industry-standard incident pattern for this class of system rather than a specific documented Uber postmortem: a consumer service is redeployed with a bug, falls hours behind, gets fixed, and is restarted to "catch up." Reading a multi-hour backlog at maximum speed generates a burst of downstream calls — database writes, cache invalidations, outbound notifications — at a rate the consumer's own dependencies were never sized for during steady state, and the very consumer meant to recover instead trips its own downstream's rate limits or exhausts a connection pool. The fix pattern operators converge on everywhere this happens: rate-limited replay with backoff, rather than "as fast as the log can serve it," is a deliberate design decision for any consumer that expects to fall behind and catch up.

THE LESSON BOTH INCIDENTS SHARE

Decoupling producers from consumers does not make correctness or capacity planning optional — it moves both problems downstream in time and out of the producer's field of view. A backbone you can't audit and a consumer that can't rate-limit its own catch-up are both forms of the same mistake: treating "the log delivered it" as equivalent to "the business outcome happened correctly."

ARC 13 · CODE WALKTHROUGH

Reading the shape of a real event backbone

Uber's actual production source for this backbone isn't public; what follows is precise, representative pseudocode for how a system in this class is genuinely built, labeled illustrative rather than literal.

event-backbone/
├── contracts/
│ ├── ● trip_completed.schema.json — versioned event contract, checked into source control
│ └── registry_client.* — fetches/validates schema at publish and at consume time
├── producers/
│ └── trip-service/● publish_trip_completed.* — serializes, validates, writes to the log
├── backbone/
│ ├── log-cluster-config/ — topic definitions, retention/replication policy (illustrative — Kafka internals live in the dedicated course)
│ ├── ● cross_cluster_replicator.* — replays each topic into every other region's cluster
│ └── ● audit_pipeline.* — reconciles produced-count vs. consumed-count per time window
└── consumers/
├── payments-service/handle_trip_completed.*
├── receipts-service/handle_trip_completed.*
├── ratings-service/handle_trip_completed.*
└── analytics-ingest/handle_trip_completed.*

The publish path — validate against the registry, then write, and only then consider the event "sent":

pseudocodepublish_trip_completed.* — illustrative
function publishTripCompleted(trip) {
    const event = serialize(trip, SCHEMA_VERSION);
    const verdict = registryClient.checkCompatibility(event.schema, SCHEMA_VERSION);
    if (!verdict.ok)
        throw new SchemaRejected(verdict.reason); // fail the DEPLOY, not a rider's request

    const ack = backbone.write("trip.completed", event, { key: trip.tripId });
    // ack means "durably in the log" — it says NOTHING about payments,
    // receipts, ratings, or analytics having processed it yet.
    return ack;
}

The audit pipeline's core idea — a periodic reconciliation, not a per-event guarantee:

pseudocodeaudit_pipeline.* — illustrative, in the spirit of Uber's real Chaperone
function reconcileWindow(topic, windowStart, windowEnd) {
    const produced = producerAuditCounts.countIn(topic, windowStart, windowEnd);
    for (group of consumerGroupsFor(topic)) {
        const consumed = group.auditCounts.countIn(windowStart, windowEnd);
        if (consumed < produced * 0.999)   // small tolerance for in-flight events at the window edge
            alerting.page(`possible data loss: ${group.name} saw ${consumed}/${produced} in window`);
        else if (consumed > produced * 1.001)
            alerting.page(`possible duplication: ${group.name} saw ${consumed}/${produced} in window`);
    }
}
WHY IT WAS BUILT THIS WAY

1. Reject bad contracts at publish time, not at consume time. A schema check that runs when the producer deploys turns a fleet-wide incident into a failed build for one team. 2. Trust nothing about delivery you haven't independently measured. The audit pipeline doesn't ask the backbone "did you drop anything" — it counts both sides and compares, because a distributed log's own internal accounting is not the same thing as business-level correctness. 3. Keep replication and audit off every consumer's critical path. Both run as their own consumers of the very same topics they're protecting — if either one falls behind, no rider-facing or payment-facing path even notices.
