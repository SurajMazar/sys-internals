KUBERNETES INTERNALS · CHAPTER 18CAPSTONE

Capstone: Build a Mini
Kubernetes Control Plane

Seventeen chapters described five separate pieces: a durable, watchable record of desired state (etcd), a validating boundary in front of it (the API server), a placement decision made independently of the record (the scheduler's filter/score pass), and a fleet of controllers that keep observed state honest against that record, forever, without anyone calling a function named fixIt(). This chapter builds all four, for real, running in your browser: a store with a genuine watch/notify mechanism and resourceVersion bookkeeping, a REST-shaped API server, a scheduler that runs real filter and score passes against simulated Nodes, and a Deployment-style controller running the exact generic reconcile loop chapter 9 derived. Then you break it — kill a Pod object directly in the store, change the desired replica count, starve a Node of capacity — and watch the identical reconcile function put it back together, because proving that is the entire point of the architecture you have spent seventeen chapters learning to trust.

You will be able toExplain, from a working implementation, why an API server sits between every client and the store instead of letting clients write to it directly.
You will understandExactly how a scheduler's filter pass (hard constraints) and score pass (a tiebreaker among survivors) compose into one placement decision, because you will have implemented both.
You will predictWhat state your control plane converges to after any combination of Pod deletion, replica-count change, or Node exhaustion — before you click the button that proves it.

ARC 01 · THE PROBLEM

Five components, one architecture — can you assemble it from memory?

Across seventeen chapters you took Kubernetes apart piece by piece: the object model (chapters 1–5), the control plane's individual organs (chapters 6–12), and the sharp edges that only show up at scale or under attack (chapters 13–17). Taking something apart is not the same skill as building it. This capstone asks a narrower, harder question: if every existing implementation of Kubernetes vanished tonight, could you rebuild the load-bearing mechanism — not the YAML ergonomics, not the ecosystem, just the thing that makes "desired state" become "actual state" and keeps it that way — from the five ideas this course already gave you?

Distilled to its architectural minimum, that mechanism is exactly five requirements, each traceable to a chapter you have already read:

  • A durable, watchable record of desired state (chapters 6–7) — something that outlives any single process's memory and can tell interested parties, incrementally, what changed and when.
  • A uniform, validating write/read boundary in front of that record (chapters 6, 13) — so no client, however well-intentioned, can corrupt the record by writing to it directly, and so every write can be authorized, schema-checked, and versioned the same way regardless of who sent it.
  • A placement decision made independently of the record itself (chapter 8) — something has to decide where a unit of work runs, using live resource accounting, without that logic living inside the store or the API boundary.
  • A continuously-running process that forces reality to match the record (chapter 9) — not a script that reacts to events and hopes it never misses one, but a loop that keeps re-deriving the correct answer from current state, indefinitely, safe to run twice, safe to run after a crash, safe to run when nothing changed.
  • Somewhere for the placed work to actually execute (chapters 2–3, and — one cross-reference sentence — the Container Internals course's namespace/cgroup/CRI chapters for what a real kubelet does below this layer). This capstone simulates that layer as an abstract Node with a CPU/memory budget; it does not re-derive container execution, because that is a different course's job.
WHY BUILD A DELIBERATELY TINY VERSION

Reading pkg/scheduler or tools/cache/reflector.go tells you what the real code does. It does not force you to answer the question that actually tests understanding: if I owned none of that code and had to write the smallest correct version myself, what would I be forced to get right? A toy that is honest about its own simplifications — no Raft, no admission chain, no CRI — but genuinely implements the watch/notify contract, a real filter+score pass, and a real level-triggered reconcile loop, answers that question in a way reading never can. Every simplification below is named explicitly in §9 so you always know which lie you are being told and why it is safe to tell.

ARC 03 · NAIVE SOLUTION

Attempt #1: a babysitter script, no store, no API, no scheduler

Before assembling the real four-part architecture, build the thing an engineer reaches for first: a polling loop that keeps a container count correct on one host, with no persisted desired state and no separation between "decide" and "act."

bashbabysitter.sh — the strawman, annotated
#!/usr/bin/env bash
DESIRED=3                          # lives ONLY in this shell's memory

while true; do
  COUNT=$(docker ps --filter "label=app=web" -q | wc -l)
  if [ "$COUNT" -lt "$DESIRED" ]; then
    docker run -d --label app=web myimage      # decide AND act, same line
  fi
  sleep 5                                # polling, not watching — chapter 4's lesson, again
done

This gets something right, the same way every naive attempt in this course has: it is trivially easy to read, and on a single host, run once, it works. Watch what happens once it meets conditions every real fleet eventually hits.

ARC 04 · WHY IT FAILS

Three missing boundaries, quantified

The deck just showed the failure narratively. Here is why it is structural, not a bug you could patch with a bigger if statement:

  • No durable desired state. $DESIRED is a shell variable. It survives exactly as long as the process does. Restart the host, and the only record of "3" was a number someone remembered or wrote on a wiki page — precisely the failure chapter 6 showed etcd exists to prevent, at the scale of a single number instead of an entire cluster's object graph.
  • No single writer. Run this script on two hosts "for redundancy" and you have created a race: both read COUNT=2 in the same 5-second window, both decide independently that one container is missing, both run docker run. Desired 3 becomes actual 4. With n babysitters polling independently and a decision window of w seconds against a change rate of λ events/second, the probability that two babysitters observe the same stale count and double-correct approaches 1 − e^(−λw(n−1)) — non-trivial the moment more than one copy runs, which is exactly why chapter 6 makes the API server (not any individual controller) the single arbiter of writes.
  • No separation between placement and correction. The script decides "create one more" and "run it right here" in the same statement. There is no layer that could instead ask "which of several hosts has room for this," because there is no concept of multiple hosts at all — the scheduler's entire job (chapter 8) doesn't exist yet.
THE POLLING TAX

Polling every 5 seconds costs one docker ps enumeration regardless of whether anything changed — O(hosts × interval⁻¹) load that scales with wall-clock time, not with actual event rate. A watch-based design (chapter 7's etcd watch, chapter 9's informer) costs O(events): work proportional to what actually happened. At 3 containers this difference is invisible. At the scale this course has discussed throughout — thousands of Pods, the 5,000-node/150,000-pod SLO envelope from chapter 6 — O(interval⁻¹) polling of every object, by every interested party, is the load pattern that makes a naively-built control plane fall over long before a well-built one does.

Fix all three at once and you arrive at the architecture the rest of this course has been describing piece by piece. Assemble it now, deliberately, one layer at a time.

THE INVARIANT THAT MAKES ALL FOUR LAYERS COMPOSE

Every layer above only ever talks to the layer immediately below it, and never skips one. The controller never touches the store directly — only the API server. The scheduler never writes to the store either — it returns a decision that the controller (standing in for the real scheduler's own bind call) turns into a write. This is the same "controllers only coordinate through objects in the API server, never through direct calls" invariant chapter 9 named — repeated here as a hard rule of your own implementation, not just real Kubernetes'.

ARC 06 · WHY THAT STILL COSTS

Even the miniature version isn't free

Assembling four correct layers doesn't mean the result is simple — it means the complexity moved somewhere legible instead of hiding in a race condition. Be honest about what you just bought:

  • Optimistic concurrency has to exist somewhere. The moment more than one writer can touch the store (§15 has exactly two: a human submitting a Deployment, and the controller creating/deleting Pods), you need resourceVersion-style bookkeeping so a stale writer's update doesn't silently clobber a newer one — real Kubernetes enforces this with conditional updates keyed on resourceVersion; this chapter's store exposes the same number for the same reason, even though the toy simulator doesn't yet enforce compare-and-swap on writes (named honestly in §9).
  • The scheduler is now a second, independent point of failure and latency. Every Pod creation now detours through a filter+score pass before anything runs. That pass is O(nodes) per Pod in the naive form this chapter implements — chapter 17's topology-spread and extender material, and the real percentageOfNodesToScore mechanism §11 revisits, exist precisely because that cost stops being negligible at cluster scale.
  • The controller must now be safe to call an unbounded number of times. A level-triggered reconcile loop that runs correctly once and incorrectly the second time is worse than the naive script — it hides its own bug behind a design that's supposed to be self-correcting. Idempotence isn't a nice property here; it's the entire selling point, so it must be provably true, not assumed.

None of this is optional overhead you could strip back out — it is the price of the three guarantees §4's babysitter script could never make: durability across restarts, a single arbiter of truth, and a placement decision that scales past one host. §7 draws the final shape; §8 shows the exact code.

ARC 08 · INTERNAL IMPLEMENTATION

The actual code: store, API shapes, watch, and the filter/score arithmetic

This is the real engine — the same four functions §15's simulator calls on every click. Nothing below is decorative pseudocode; it is what runs.

(a) Object shape and resourceVersion

Every object this control plane stores has the same three-part shape real Kubernetes objects do — metadata, spec, status — plus the resourceVersion the store stamps on every write:

JSONa Deployment and one of its Pods, as this store actually persists them
{
  "kind": "Deployment",
  "metadata": { "namespace": "default", "name": "web" },
  "spec": { "replicas": 3, "requests": { "cpu": 1, "mem": 1 } },
  "status": {},
  "resourceVersion": 7          // stamped by the STORE, not the caller — chapter 6's rule
}
{
  "kind": "Pod",
  "metadata": { "namespace": "default", "name": "web-a1b2c3" },
  "spec": { "owner": "web", "nodeName": "node-2", "requests": { "cpu": 1, "mem": 1 } },
  "status": {},
  "resourceVersion": 8          // every write anywhere in the store bumps ONE global counter
}

Real etcd/Kubernetes gives every key its own revision history (chapter 7's MVCC); this toy store uses one global monotonic counter across all keys for simplicity — enough to prove the watch contract, not enough to support real compaction or point-in-time reads (§9).

(b) The store: watch is not polling in disguise

The core contract a watch API has to honor: every write notifies every current subscriber, synchronously, with the object and the resourceVersion that write produced — no subscriber ever has to re-ask "what's the latest state," because the event tells them.

JavaScriptcreateStore() — real watch/notify, real resourceVersion
function createStore() {
  const objects = new Map();      // key -> stored object
  let rv = 0;                     // ONE global monotonic counter
  const watchers = new Set();     // every open "watch connection"

  function notify(type, key, obj) {
    const event = { type, key, object: obj, resourceVersion: rv };
    watchers.forEach(fn => fn(event));   // EVERY subscriber, EVERY write, no exceptions
    return event;
  }

  return {
    create(key, obj) {
      if (objects.has(key)) throw new Error("AlreadyExists: " + key);
      rv += 1;
      const stored = Object.assign({}, obj, { resourceVersion: rv });
      objects.set(key, stored);
      return notify("ADDED", key, stored);
    },
    watch(fn) { watchers.add(fn); return () => watchers.delete(fn); }
    // get/list/update/delete: full code in §15's live source, same shape
  };
}

(c) The scheduler: filter is a hard veto, score is a tiebreaker

Filtering answers "can this Node possibly run this Pod." Scoring answers "which of the Nodes that can, should." The two must never merge into one number — a Node that fails filtering must never be ranked, no matter how it would score. THIS CHAPTER'S SCORING FUNCTION, PRECISELY

After filtering out any Node whose free CPU or memory is below the Pod's request, each survivor is scored by how tightly placing this Pod would pack it: score = round(100 × (1 − avg(freeCpuFraction, freeMemFraction))) computed after the hypothetical placement. Higher score wins. This is a MostAllocated-style strategy — real Kubernetes ships this as one of several selectable scoring plugins, alongside strategies that instead prefer to spread load thinly across Nodes (LeastAllocated). Neither is universally correct: MostAllocated minimizes the number of Nodes you pay for; LeastAllocated leaves headroom on every Node for load spikes. §15 lets you watch which Node wins under this chapter's chosen strategy.

(d) The controller: one function, called for every reason

The reconcile function that closes this chapter's loop is deliberately uninterested in why it was called. It reads current desired and observed state from the API server, computes one integer, and acts on that integer — nothing else:

JavaScriptreconcileDeployment() — the whole loop, no special cases
function reconcileDeployment(api, nodes, ns, name) {
  const dep = api.get("Deployment", ns, name);
  const pods = api.list("Pod", ns).filter(p => p.spec.owner === name);
  const diff = dep.spec.replicas - pods.length;   // the ENTIRE decision lives in this one number

  if (diff > 0)                                // under-provisioned: schedule + create
    for (let i = 0; i < diff; i++) { /* scheduleOn() then api.create() */ }
  else if (diff < 0)                          // over-provisioned: delete oldest first
    /* pick -diff victims, free their Node capacity, api.delete() */

  return { diff, actions };                    // diff === 0 is the ONLY success state
}
WHY THIS IS THE WHOLE CHAPTER IN ONE FUNCTION

Nothing in reconcileDeployment() asks "was a Pod just deleted?" or "did the user just change replicas?" or "is a Node full?" It asks exactly one question — what is desired − observed right now — and answers it the same way regardless of which of those three things caused the diff to be non-zero. §15 proves this by triggering all three from different buttons and pointing at the identical code path each time.

Every simplification, named honestly

A toy is only pedagogically useful if you know exactly which corners it cut. Here is the full list, compared to what real Kubernetes does instead — and, where relevant, what other orchestrators chose:

Compare this shape to the two other orchestrator lineages this course has occasionally referenced: Docker Swarm chose a far smaller surface — a single reconciliation model baked into the engine, no CRD-style extensibility — trading generality for a dramatically simpler mental model; HashiCorp Nomad separates scheduling into its own first-class service closer to how this chapter's scheduleOn() is decoupled from the controller, but (like this toy) keeps its data model far narrower than Kubernetes' fully generic object/watch/reconcile machinery. Neither choice is wrong — chapter 9's Principal-level interview question about CRDs-vs-bespoke applies here verbatim: generality has to be paid for, and the question is always whether your domain needs it.

ARC 10 · PERFORMANCE CHARACTERISTICS

Where this toy's complexity actually lives

Even at toy scale, the complexity classes are real and worth naming precisely, because they are the same complexity classes that force real Kubernetes' scaling limits:

  • Store list operations: list() is a linear scan over every key with a matching prefix — O(objects) per call. Real etcd's watch cache and client-go's local Indexer (chapter 9) exist specifically so a controller never pays this cost against the network on every reconcile.
  • Scheduler filter+score: O(Nodes) per Pod, since every Node is checked. At the scale this course has cited throughout (the 5,000-node SLO envelope), scoring every Node for every Pod is measurably expensive — the real, documented motivation for the Node-sampling percentage tuning §11 covers.
  • Reconcile: O(owned Pods) per tick to compute the diff, plus O(|diff|) scheduler calls to close it — bounded, predictable, and — critically — the same cost whether the tick was triggered by a watch event or a periodic resync (chapter 9's resync-floor argument, unchanged here).

ARC 11 · REAL-WORLD PRODUCTION

Three real incidents your toy's shortcuts would reproduce

Incident 1: CVE-2019-11253 — the API server never validates, and that's the actual attack

This chapter's createApiServer() accepts any spec shape with zero validation — deliberately, to keep the code short enough to read in one sitting. Real Kubernetes cannot afford that: CVE-2019-11253 was a Billion-Laughs-style YAML/JSON expansion denial-of-service against the API server, where a maliciously crafted, deeply self-referential manifest expanded to consume enormous memory and CPU during parsing, before any RBAC or business logic even ran. The fix constrained decode-time resource usage in the API server's parsing layer itself. The lesson for anyone extending this chapter's toy: the first real hardening job for a homemade API server is never "add more resource kinds" — it's bounding what an unauthenticated or barely-authenticated request is allowed to make your parser do.

Incident 2: the etcd disk-exhaustion pattern — your store never compacts, either

Chapter 7 (and chapter 16) covered a real, recurring operational pattern: etcd's MVCC keyspace grows with every write because old revisions are retained until explicitly compacted, and un-defragmented free pages inflate the on-disk file beyond its logical size — together, a well-documented cause of latency collapse once the backend approaches its quota. This chapter's store has the same root cause in miniature: the global rv counter increments forever, and nothing here ever garbage-collects old state. At toy scale it's invisible; at etcd's actual scale, "when do we throw away old history, and who is allowed to ask for it" is a real, load-bearing design decision this chapter skips entirely rather than half-implements.

Incident 3: scoring every Node stops being free

Real Kubernetes historically scored every Node in the cluster for every unscheduled Pod — correct, but O(Nodes) per Pod, which measurably hurt scheduling throughput as cluster size grew into the thousands. The documented, shipped fix samples a percentage of Nodes once enough of the cluster has already been considered, trading a small chance of a marginally worse placement for bounded scheduling latency at scale — the same filter-then-score shape this chapter's scheduleOn() implements, just applied to a subset instead of every Node. §10's slider makes the underlying O(Nodes) cost this optimization exists to bound directly visible.

The most important line in that tree is the last one. Here is the reconcile function again, this time exactly as §15 calls it — annotated for the one design decision that makes the whole chapter honest:

JavaScriptcontroller.js — reconcileDeployment(), fully annotated
function reconcileDeployment(api, nodes, ns, name) {
  const dep = api.get("Deployment", ns, name);
  if (!dep) return { skipped: true, reason: "deployment not found" };

  const desired = dep.spec.replicas;                       // read from the API server, not a local variable
  const pods = api.list("Pod", ns)
    .filter(p => p.spec.owner === name);              // read CURRENT observed state, every call
  const diff = desired - pods.length;

  const actions = [];
  if (diff > 0) {
    for (let i = 0; i < diff; i++) {
      const placement = scheduleOn(nodes, dep.spec.requests);   // filter + score, real function
      if (!placement.node) { actions.push({ type: "pending" }); continue; }
      // ... api.create() the Pod, account the Node's used capacity ...
    }
  } else if (diff < 0) {
    // ... pick -diff victims deterministically, api.delete(), free capacity ...
  }
  return { desired, observedBefore: pods.length, diff, actions };
}
WHY THE UI FILE IS NOT ALLOWED TO CONTAIN LOGIC — A CHOICE WORTH STEALING

ui.js (§15's rendering code) is only permitted to call the four engine functions and draw their results — it never contains an if statement that changes what the control plane does. This mirrors real client-go: a controller's HTTP handler or CLI wrapper never contains reconciliation logic either — the reconcile function is a pure, independently-callable unit specifically so it can be tested, and trusted, without a browser, a terminal, or a human anywhere near it. §15's node smoke test (referenced in this chapter's build notes) calls exactly these four functions with no DOM involved at all — proof that the separation is real, not aspirational.
