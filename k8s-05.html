ARC 01 · THE PROBLEM

You've been typing a magic incantation. Time to know what it does.

In chapter 1 you ran kubectl apply -f pod.yaml and a Pod appeared. In chapter 2 you edited a Deployment's YAML, ran the same command, and watched a rolling update happen. In chapter 4 you changed a ConfigMap and re-applied it. Every single time, you described what you wanted in a text file and the cluster somehow made itself match. That gap — between a file on your laptop and a set of running objects inside a cluster — is the entire subject of this chapter.

Formalize the two things that must be kept in sync:

  • Desired state — what you wrote down. A YAML (or JSON) document describing a Kubernetes object: its kind, its spec, the values you chose. This is a plan, not a fact — writing replicas: 5 in a file does not make five Pods exist.
  • Actual state — what is really running. The live object stored inside the cluster (chapter 6 shows exactly where — spoiler: etcd), plus whatever the real world has done to it since: a node died and took a Pod with it, the horizontal autoscaler bumped replicas, or an on-call engineer ran kubectl edit at 2 a.m.

Kubernetes' foundational bet — the one idea chapter 1 introduced and every chapter since has assumed — is that you never tell the cluster what to do; you tell it what you want, and something else continuously reconciles reality toward that goal. That "something else" is controllers running reconciliation loops (chapter 9 goes deep on the mechanism). This chapter is about the front door to that model: how your YAML file actually gets from your disk into the object that controllers reconcile against, and — critically — what happens when your file isn't the only thing that has touched that object.

THE QUESTION THIS CHAPTER ANSWERS

You edit a Deployment's YAML to change one field — say, the container image tag — and run kubectl apply -f deploy.yaml again. In between your first apply and this one, the Horizontal Pod Autoscaler (chapter 12) silently changed spec.replicas from 3 to 9 because load spiked. Your file still says replicas: 3. What happens to those 9 replicas? Get this wrong in production and you either fight your own autoscaler in an infinite loop, or you ship a tool that "just deletes stuff nobody told it to delete." This chapter gives you the exact mechanism, not a guess.

The honest starting point is that kubectl is not one command with one behavior — it is a thin client wrapping a REST API, and it exposes at least four genuinely different ways to reconcile a file with a live object: create, replace, edit, and apply. We will derive why apply won by watching the other three fail first — the same method this course has used since chapter 1.

DEEP CONTEXT · THE BORG CONFIGURATION LANGUAGE LINEAGE

Google's Borg (chapter 1's direct ancestor of Kubernetes) already ran on declarative config files (written in a language called BCL — Borg Configuration Language) evaluated into a final desired-state document before being submitted to Borg's API. Kubernetes inherited the declarative-first instinct from that lineage — but crucially, unlike Borg's mostly single-owner internal config, Kubernetes objects are routinely written by multiple independent actors at once (a human's YAML, a CI/CD pipeline, an autoscaler, an admission webhook that injects a sidecar). Almost everything interesting in this chapter is a consequence of that one difference: Kubernetes had to solve multi-writer declarative config; Borg mostly didn't.

ARC 03 · NAIVE SOLUTION

Attempt #1: just re-run the imperative commands

Before apply existed as the tool you reach for by default, the obvious way to "sync a file to the cluster" was to script the imperative commands you already had: check if the object exists, and if it does, delete-and-recreate it (or PUT the whole thing via replace). Here is that script, faithfully:

bashnaive_sync.sh — the strawman, annotated
#!/usr/bin/env bash
# "Sync" a manifest to the cluster the naive way: nuke and repave.
manifest="deploy.yaml"
name=$(yq '.metadata.name' $manifest)

if kubectl get deployment $name >/dev/null 2>&1; then
    # Object exists. Two options, both blunt instruments:
    kubectl delete deployment $name       # (a) drop it, then...
    kubectl create -f $manifest            #     ...recreate from scratch. Pods restart, ClusterIP
                                       #     may change, anything referencing the old object
                                       #     by UID breaks.
    # OR, slightly less destructive:
    kubectl replace -f $manifest           # (b) PUT the whole spec over the existing object.
                                       #     No Pod restart forced, but the ENTIRE spec is
                                       #     replaced by whatever is in the file -- verbatim.
else
    kubectl create -f $manifest            # doesn't exist yet -- straightforward POST
fi

This is not a joke architecture. kubectl create and kubectl replace are real, supported commands, and this script is a fair description of how most teams managed Kubernetes objects in 2015. It even gets something right: it's simple — one file, one clear operation, no hidden state to reason about. The object's spec is always exactly what's in the file. No surprises... as long as nothing else ever touches that object.

ARC 04 · WHY IT FAILS

"The whole object, verbatim" breaks the instant there's a second writer

Quantify exactly what replace (a full HTTP PUT of the entire object body) and create (a one-shot POST, fails if the object exists) get wrong, because the numbers make the failure mode concrete rather than theoretical:

  • PUT is a total-overwrite operation. A PUT to /apis/apps/v1/namespaces/default/deployments/web replaces spec with exactly the JSON body you send. Any field the live object holds that your file doesn't mention is gone after the call returns, in the same request that also applied your intended change — you cannot separate "the field I meant to change" from "the fields I never thought about."
  • Multiple writers is the normal case, not the exception. By chapter 12 you'll have at least three independent actors legitimately mutating one Deployment: your YAML (desired replica baseline), the Horizontal Pod Autoscaler (current replica count, chapter 12), and a mutating admission webhook (chapter 13, injecting a sidecar container into spec.template.spec.containers). A replace that doesn't know about the other two will erase whichever of their changes it doesn't happen to also carry.
  • The concrete number: if the HPA has scaled a Deployment from 3 replicas to, say, 40 during a traffic spike, and an engineer's stale local file still reads replicas: 3, one kubectl replace -f deploy.yaml instantly discards 37 running replicas' worth of capacity — during the spike that justified them. That is not a rare edge case; it is what happens on the very next routine config change if nobody remembers to re-sync the file first.
  • create doesn't even attempt reconciliation. It's a bare POST; if the object already exists, the API server returns 409 Conflict — AlreadyExists. It answers "does this exist yet?" with a hard yes/no, which is why the naive script above needs an if statement just to decide which command to run at all.
THE DEEPER ISSUE: NO WRITER KNOWS WHAT CHANGED

Both create and replace share one root defect: neither command has any concept of "what did I change since last time" versus "what changed on the object since I last looked." They only know two states — the file, and (for replace) the live object right this instant — and they can't tell which differences between those two states are your intentional edits versus someone else's legitimate changes that merely happen to disagree with your stale file. Diffing two states can tell you that they differ; it cannot tell you who is allowed to win. That requires a third state: what the file looked like the last time it was successfully applied. Two-way diffing is provably insufficient — you need three states to assign blame for a conflicting field, which is exactly what §5 introduces.

ARC 05 · BETTER SOLUTION

kubectl apply: remember the last thing you intended, not just the current file

kubectl apply -f fixes the "who's allowed to win" problem by keeping a third document around, not just two. Every time apply successfully writes an object, it stashes the exact manifest it just applied into an annotation on the object itself: kubectl.kubernetes.io/last-applied-configuration. That annotation is the object's memory of "the last thing a human (or pipeline) explicitly asked for" — and it's what turns a two-way diff into a genuine three-way merge:

  • ORIGINAL — the last-applied-configuration annotation: what you asked for last time.
  • MODIFIED — your new manifest on disk: what you're asking for now.
  • CURRENT — the live object in the cluster right now: what's actually running, including anything other writers changed.

With three states you can finally attribute every difference correctly. Walk through the merge's actual decision rule, one field-class at a time:

The three-way merge decision ruleSTEP-BY-STEP
THE CLINCHING ARGUMENT: FIELDS YOU NEVER MENTIONED SURVIVE

Because the merge computes a patch — only the fields that changed between ORIGINAL and MODIFIED — and applies that patch on top of CURRENT rather than overwriting CURRENT wholesale, any field present in CURRENT that was never present in ORIGINAL (the HPA's replica count, a webhook-injected sidecar, an auto-assigned clusterIP) is simply never mentioned in the patch, and therefore survives untouched. That is the entire value proposition of apply over replace in one sentence: it changes only what you changed, and leaves everyone else's changes alone.

ARC 06 · WHY THAT STILL COSTS

The bill for client-side apply: an annotation that lies, and a merge with no memory of who

Classic (client-side) kubectl apply is a genuine improvement, but it computes the entire merge on your laptop, from a single annotation, with no idea which other tool touched which field. That design has real, well-documented costs:

  • The annotation is just another field — and it can go stale or missing. If an object was ever created with kubectl create (no annotation written) and someone later runs apply on it, there is no ORIGINAL to diff against; kubectl falls back to treating the live object itself as ORIGINAL, which silently degrades the three-way merge back into a two-way diff for that one apply — with all of §4's problems.
  • Deletion is unconditional. If a field is present in ORIGINAL but absent from MODIFIED, client-side apply removes it from CURRENT — even if CURRENT's value for that field no longer matches ORIGINAL, meaning some other writer changed it since. Client-side apply has no way to notice this and will silently discard that other writer's change. It computes "what should this field become" purely from your two documents; it never asks "does CURRENT still agree with ORIGINAL for this field."
  • No shared notion of field ownership across tools. If your team applies a Deployment with kubectl and later a teammate applies a different version of the same object with Helm or Terraform, each tool keeps (or reconstructs) its own idea of "last applied" — there is no cluster-side record of which tool is authoritative for which field. Two well-intentioned automated pipelines fighting over one replicas field is one of the most commonly reported operational headaches in multi-tool Kubernetes shops.
  • List merges are coarse. A bare JSON diff would treat spec.template.spec.containers as one opaque array and replace it wholesale on any change — losing a sidecar a webhook injected at position 1. Kubernetes ships strategic merge patch to fix exactly this (merging list elements by a declared key, usually name, instead of by array index) — but that machinery only exists for built-in types with Go struct tags; arbitrary CRDs (chapter 9) don't get it for free.
THE INDUSTRY'S ANSWER — AND ITS ADMISSION

The fix that shipped is Server-Side Apply (KEP-555): move the merge computation into the API server itself, and have the server track, per object, which field manager last set each field (metadata.managedFields). Now two tools touching different fields of the same object coexist peacefully, and a genuine conflict — two managers wanting different values for the same field — is surfaced as an explicit, rejectable HTTP 409 rather than a silent overwrite. That Kubernetes needed a whole new subsystem, tracked by its own KEP, alpha in 1.14 (2019) and GA in 1.22 (2021), to fix "my apply command clobbered a field," is itself the best evidence of how real client-side apply's blind spot was. This chapter focuses on the classic three-way merge because it's still what kubectl apply does by default and what you must understand first; chapter 6 picks up the API server's request pipeline that Server-Side Apply plugs into.

API GROUPS: WHY apps/v1 AND NOT JUST v1

The URL path above — /apis/apps/v1/namespaces/default/deployments/web — encodes an API group (apps) and a version (v1). Kubernetes doesn't have one flat API; it has dozens of groups (apps, batch, networking.k8s.io, rbac.authorization.k8s.io...), each versioned independently so the project can evolve one corner of the API (say, promoting a field from alpha to stable) without touching unrelated resources. The bare v1 group (no group name — the "core" or "legacy" group, path /api/v1/...) holds the oldest objects: Pod, Service, ConfigMap, Secret, Namespace, Node — all predate the group mechanism. Every manifest's apiVersion field is really "group/version" (or just "version" for the core group), and it is not cosmetic: send a Deployment to the API server tagged with a group/version the server doesn't currently serve, and the request is rejected before it ever reaches admission control.

ARC 08 · INTERNAL IMPLEMENTATION

The merge, in the actual shapes it operates on

Now the real mechanism: the exact JSON the annotation holds, the patch format Kubernetes sends over the wire, and the algorithm that turns three documents into one patch.

(a) What the annotation actually contains

After kubectl apply -f deploy.yaml succeeds once, inspect the live object with kubectl get deployment web -o yaml and you'll find your entire submitted manifest, serialized to JSON, stuffed into one annotation value:

yamllive object — metadata.annotations, after one apply
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: default
  resourceVersion: "48213"          # optimistic-concurrency counter — bumped on every write
  uid: 7e2f1a4c-...
  annotations:
    kubectl.kubernetes.io/last-applied-configuration: |
      # the ENTIRE previous manifest, minified to one JSON string:
      {"apiVersion":"apps/v1","kind":"Deployment","metadata":{"name":"web","namespace":"default",
       "labels":{"app":"web","tier":"frontend"}},"spec":{"replicas":3,"selector":{"matchLabels":
       {"app":"web"}},"template":{"metadata":{"labels":{"app":"web"}},"spec":{"containers":
       [{"name":"web","image":"web:1.0","ports":[{"containerPort":8080}]}]}}}}
spec:
  replicas: 9                          # CURRENT differs from the annotation: the HPA changed this
  ...

Notice the object is telling you its own history: the annotation is ORIGINAL, spec.replicas: 9 in the live object is CURRENT, and your edited file on disk is MODIFIED. The merge has everything it needs because Kubernetes stored ORIGINAL inside the very object it describes — a deliberately simple design: no external database of "what did I last apply," just one more field on the object.

(b) The merge algorithm — real function shapes

kubectl's actual Go implementation (k8s.io/apimachinery/pkg/util/strategicpatch) computes this in two calls. First, diff ORIGINAL against MODIFIED to get a patch describing your intent; then merge that patch against CURRENT, honoring per-field merge keys for known list types (like matching containers by name instead of array index):

gostrategicpatch — the shape of CreateThreeWayMergePatch
// original  = last-applied-configuration annotation, as JSON bytes
// modified  = your new manifest, as JSON bytes
// current   = the live object, as JSON bytes (fetched by GET immediately before the merge)
patch, err := strategicpatch.CreateThreeWayMergePatch(
    original, modified, current,
    dataStruct,              // e.g. appsv1.Deployment{} -- supplies patchMergeKey tags
    overwrite,                // true: let modified win outright conflicts (kubectl apply default)
    fns...,                   // per-field patch-merge-key metadata, e.g. "name" for containers[]
)
// patch is itself a JSON document -- a set of adds/changes/deletes, NOT the full object.
// It is then sent as the HTTP body of:
//   PATCH /apis/apps/v1/namespaces/default/deployments/web
//   Content-Type: application/strategic-merge-patch+json
// -- the API server applies THAT patch to whatever CURRENT is at the moment the
// PATCH request lands (which may differ again from the CURRENT kubectl fetched
// a moment earlier -- an unavoidable, tiny race window client-side apply accepts).

Reduced to pseudocode, field by field, this is the decision table the merge actually applies:

pseudocodeper-field merge decision — what §5's deck showed you, formalized
function mergeField(key, original, modified, current):
    inOrig = key in original
    inMod  = key in modified
    inCur  = key in current

    if not inOrig and not inMod:
        return current[key]              # never yours -- untouched (case: HPA-owned field)

    if not inOrig and inMod:
        return modified[key]              # you're adding a brand-new field -- ADD

    if inOrig and not inMod:
        # you removed it from your file -- DELETE, unconditionally
        if current[key] != original[key]:
            warn("deleting a field someone else changed since last apply")
        return DELETE

    if original[key] == modified[key]:
        return current[key]               # you didn't touch it -- leave CURRENT as-is

    # original[key] != modified[key]: you changed it -- CHANGE, even if current already diverged
    return modified[key]

WHY THIS IS A REAL, DOCUMENTED FAILURE MODE

Kubernetes enforces a hard, documented ceiling: the total size of all annotations on one object must stay under 256 KiB (262,144 bytes). Because last-applied-configuration duplicates your entire manifest as one annotation value, a large CRD instance or a Deployment with dozens of sidecars and long env-var lists can push that single annotation close to — or past — the ceiling on its own, well before the rest of the object's metadata is considered. The real, frequently reported symptom is kubectl apply failing outright with metadata.annotations: Too long: must have at most 262144 characters — for an object that would otherwise apply just fine with --server-side, which doesn't need this annotation at all because the server tracks field ownership structurally instead of by storing a whole extra copy of your file.

ARC 09 · TRADEOFFS

create vs replace vs apply vs apply --server-side: an honest comparison

None of these commands is strictly obsolete — each is the right tool for a specific situation. Read the table as a decision guide, not a ranking:

COMMANDWIRE OPERATIONWHAT IT BUYSWHAT IT COSTS
kubectl create -fPOST (fails if exists) simple, unambiguous great for one-shot Jobs/scripts no update path at all no reconciliation semantics
kubectl replace -fPUT (full overwrite) predictable — object becomes exactly the file destroys fields owned by other writers needs resourceVersion or races
kubectl editGET → open $EDITOR → PUT/PATCH fast for one-off manual fixes never recorded anywhere the definition of untracked drift
kubectl apply -f (client-side)PATCH — strategic merge patch, 3-way preserves fields you never mentioned safe to re-run (idempotent) annotation can go stale/oversized unconditional field deletion
kubectl apply --server-sidePATCH — application/apply-patch+yaml, server-computed per-field ownership tracking explicit conflicts, not silent loss requires every writer to declare a field manager newer, less muscle memory
Helm / Kustomize / TerraformUltimately still apply/PUT under the hood templating, packaging, drift-planning UX yet another tool with its own idea of "ownership"

Read the table as proof that "how do I update a Kubernetes object" has no single right answer — only different placements of the same fundamental risk: someone else might have changed the object since you last looked, and every command handles that possibility with a different mix of safety and simplicity. replace ignores the risk entirely (fast, dangerous); classic apply mitigates it heuristically with one annotation (safer, still has blind spots); server-side apply resolves it structurally (safest, requires the whole ecosystem to participate).

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Where the merge actually gets slow, unsafe, or both

Precise complexity and safety facts, not vibes:

  • Client-side apply does a GET, a local diff, then a PATCH — at least two round trips to the API server per invocation, versus one for replace. For a single manifest this is noise; for a CI pipeline running kubectl apply -f across thousands of manifests, it roughly doubles API server request volume compared to a hypothetical direct PUT.
  • No optimistic-concurrency check by default. kubectl replace -f normally requires the file's resourceVersion to match the live object's (or you pass --force, which itself does delete+recreate) — a genuine compare-and-swap. Classic kubectl apply's PATCH request, by contrast, does not set a resourceVersion precondition: the merge is computed against whatever CURRENT the earlier GET returned, and the PATCH is applied to whatever the object has become by the time it lands, even if another write raced in between. In practice this window is small, but it is a real, structural gap that server-side apply's atomic read-modify-write inside the API server closes.
  • The annotation grows every field of your manifest into etcd's per-value cost. The spec's own guidance for etcd recommends keeping individual stored values under roughly 8 KB for healthy read/write latency; a last-applied-configuration annotation that duplicates a multi-KB manifest pushes the object's total stored size upward on every single field this object has — a cost paid on every write and every watch event fan-out (chapter 7 covers etcd's watch mechanism and why large values are expensive there specifically).
  • Security surface: the annotation is plaintext, unauthenticated evidence of past intent. Anyone with read access to the object (RBAC get on that resource, chapter 13) can read exactly what was last applied — including any non-Secret values a manifest author mistakenly put in a ConfigMap or plain field (chapter 4's base64-is-not-encryption lesson generalizes: annotations are just as visible as the rest of the object to anyone who can read it).

ARC 11 · REAL-WORLD INCIDENTS

Three ways this bites in production

Incident 1: CVE-2019-11253 — Billion Laughs, applied straight to the API server

The API server accepts YAML and JSON request bodies for every apply/create/PATCH — including from any authenticated user with write access to a namespace. CVE-2019-11253 is a denial-of-service vulnerability in the API server's YAML/JSON parsing: a maliciously crafted manifest using deeply nested, self-referential structures (the classic "Billion Laughs" XML-entity-expansion pattern, adapted to YAML anchors/aliases) could be submitted via an ordinary kubectl apply -f malicious.yaml and consume enormous amounts of API server memory and CPU during parsing — before any admission or schema validation ever ran, because parsing happens first. The fix added strict limits on YAML document nesting depth and alias expansion during decode. The lesson generalizes directly from this chapter: the API server must treat every manifest body — including ones arriving via the "safe," declarative apply path — as untrusted input, because apply is, at the wire level, just an authenticated user submitting bytes.

Incident 2: the GitOps vs. autoscaler tug-of-war

A very commonly reported class of incident: a GitOps controller (Argo CD or Flux, chapter 17) continuously re-applies manifests from a git repository to keep the cluster matching source control — the "self-healing" promise chapter 1 introduced, now automated. If that same Deployment's spec.replicas is also owned by the Horizontal Pod Autoscaler, the two controllers disagree forever: the GitOps controller applies replicas: 3 from the checked-in manifest, the HPA scales it back up to meet load seconds later, and the next GitOps reconciliation pass applies replicas: 3 again — a visible "flapping" replica count in dashboards, extra churn on the API server and etcd, and — worse — a real availability gap every time the count is forced back down mid-spike. The documented fix (both Argo CD's and Flux's own operational guidance say this explicitly) is to exclude autoscaled fields from the checked-in manifest's ownership, either by omitting spec.replicas from the GitOps-managed source entirely or using Server-Side Apply's field-manager exclusions — the exact mechanism §6 introduced, now load-bearing in production.

Incident 3: "annotations: Too long" on a big CRD, blocking every future apply

Operators of complex custom resources (large Istio VirtualService/Gateway objects, cert-manager Certificate bundles with many DNS names, or hand-rolled CRDs with big embedded configuration blocks) regularly hit the exact 256 KiB annotation ceiling described in §8/§10: the object's spec alone is large, and client-side kubectl apply then tries to also store a full copy of it in last-applied-configuration, pushing total annotation size over the limit and returning metadata.annotations: Too long: must have at most 262144 characters. Because the annotation is written as part of the same apply that's failing, the object gets stuck: you can't shrink the object with the very command that's rejected for being too large. The standard remedy, and the one most teams eventually adopt permanently for large CRDs, is kubectl apply --server-side, which never stores that duplicate annotation at all — the server tracks ownership via managedFields instead, at a fixed, much smaller cost per field manager rather than one full copy of the manifest.

The heart of the classic path, simplified from the real kubectl source but faithful to its structure:

goapply.go — ApplyOptions.Run(), the parts that matter
func (o *ApplyOptions) Run() error {
    for _, info := range o.objects() {           // one per manifest / doc in the -f file

        // 1. Does the object already exist?
        if !info.Namespaced() || objectExists(info) {
            // 2a. It exists: build a patch via a Patcher and PATCH it.
            patcher := newPatcher(o, info)
            patchBytes, err := patcher.Patch(
                info.Object,          // CURRENT -- freshly GET'd
                modifiedBytes,        // MODIFIED -- your file, serialized
                info.Source, ...,
            )
            // Patch() internally reads the last-applied-configuration
            // annotation off info.Object to recover ORIGINAL, then calls
            // strategicpatch.CreateThreeWayMergePatch(original, modified, current, ...)
        } else {
            // 2b. Doesn't exist yet: plain CREATE, and immediately stamp
            // the last-applied-configuration annotation so THIS becomes
            // ORIGINAL for every future apply.
            createAndAnnotate(info, modifiedBytes)
        }
    }
}
WHY THE DEVELOPERS BUILT IT THIS WAY — TWO CHOICES TO STEAL

1. Store ORIGINAL inside the object, not in a side database. No external system to keep in sync, no extra infrastructure, and the annotation travels with the object automatically (backups, cluster migrations, kubectl get -o yaml — all see it for free). The cost, as §6/§8/§11 showed, is that it competes for the same size budget as everything else about the object. 2. Compute the patch client-side, apply it server-side. This kept the API server simple for years — it just executes an ordinary PATCH, unaware that "apply" semantics exist — until Server-Side Apply deliberately inverted this by moving the computation into the server, in exchange for needing to track per-field ownership there. Both are legitimate points on the same "where does the smart logic live" spectrum you'll see again with the scheduler (chapter 8) and admission webhooks (chapter 13).
