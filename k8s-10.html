ARC 01 · THE PROBLEM

Every Pod needs an IP, every Service needs a stable one, and nobody agreed on how

Kubernetes makes one non-negotiable networking promise, stated precisely in the upstream networking model: every Pod gets its own IP address, every Pod can reach every other Pod's IP directly, with no NAT in between, regardless of which node either one is scheduled to. Read that again — it is a much stronger claim than "containers can talk to each other." Docker's default bridge network NATs container ports onto the host; two containers on two different Docker hosts cannot reach each other's container IPs at all without you building something. Kubernetes assumes the opposite is true everywhere, and then builds Services, DNS, NetworkPolicy, and Ingress on top of that assumption.

Unpack what has to be true for that promise to hold, across an arbitrary number of nodes that were never configured to know about each other's Pod ranges in advance:

  • Unique addressing. No two Pods, on any two nodes, anywhere in the cluster, may share an IP — with zero central bottleneck doing the allocation for every Pod creation.
  • Cross-node reachability. A packet from a Pod on node A addressed to a Pod on node B must actually get there — via a real route, an overlay tunnel, or an underlay the cluster's CNI understands.
  • A stable name for something unstable. Pods die and reschedule with new IPs constantly (chapter 9's reconciliation loops guarantee it); nothing that talks to "the API" can hardcode a Pod IP and survive.
  • An admission point from outside. None of the above says how a browser on the public internet reaches anything — that is a deliberately separate problem, layered on top as Services and Ingress.
  • An opt-in way to say no. By default every Pod can reach every other Pod — full mesh, zero isolation. Multi-tenant and compliance-driven clusters need a way to restrict that without re-architecting the network.

Kubernetes answers the first two with a pluggable contract — the Container Network Interface (CNI) — rather than a built-in implementation. The third with the Service object and its supporting EndpointSlices. The fourth with Ingress (and increasingly, the Gateway API). The fifth with NetworkPolicy. This chapter derives all four, in the order the cluster actually needs them: nothing else works until Pods have routable IPs, so that is where we start.

WHERE THIS SITS IN THE STACK

Chapter 6 established that kubelet delegates container lifecycle to a CRI shim. Networking is delegated the same way, to a different plugin family: when kubelet's RuntimeService.RunPodSandbox call creates the Pod's network namespace, kubelet then invokes a separate CNI plugin binary to wire that namespace onto the network. CRI and CNI are two independent plugin boundaries solving two independent problems — one creates the isolated environment, the other connects it. This chapter is entirely about the second one.

DEEP CONTEXT · WHY KUBERNETES NEVER BUNDLED A NETWORK

By 2014, container networking already had two incompatible camps: Docker's libnetwork/CNM (a driver model tied to Docker's own lifecycle) and CoreOS rkt's need for something that didn't assume a Docker daemon existed at all. Kubernetes needed to run on both, plus bare metal, plus every cloud's own VPC fabric. Rather than pick a side, Kubernetes adopted CNI as an external contract: kubelet knows nothing about VXLAN, BGP, or eBPF — it knows how to exec one binary with a JSON blob on stdin. That single design choice is why Flannel, Calico, Cilium, and every cloud's native VPC CNI can all claim "runs on Kubernetes" without any of them touching kubelet's code.

ARC 03 · NAIVE SOLUTION

Attempt #1: wire it by hand, with shell scripts and text files

Derive it honestly, the way an engineer would before knowing the CNI spec exists. You have N nodes, you want every Pod to get a routable IP, and you want a stable name for "the 3 replicas behind this Deployment." A naive first cut:

bashnaive-wire.sh — run by an agent on every node, no coordination
#!/usr/bin/env bash
# --- "IPAM": a shared NFS-mounted counter file, no locking ---
next=$(cat /shared/ipam-counter)
ip="10.244.0.$next"
echo $((next+1)) > /shared/ipam-counter      # read-modify-write, no lock — see §4

# --- wire the netns by hand ---
ip link add veth0 type veth peer name veth1
ip link set veth1 netns $CONTAINER_PID
nsenter -t $CONTAINER_PID -n ip addr add "$ip/16" dev veth1
ip link set veth0 master br0                    # local bridge only — no cross-node route yet

# --- "Service": append this backend to a flat text file ---
echo "$SERVICE_NAME $ip:$PORT" >> /shared/backends.txt

# --- "kube-proxy": a polling loop, rewrites the WHOLE iptables ruleset ---
while true; do
  iptables -t nat -F NAIVE_SVC                 # flush everything, every 2 seconds
  while read svc backend; do
    iptables -t nat -A NAIVE_SVC -d "$(lookup_vip $svc)" -j DNAT --to "$backend"
  done < /shared/backends.txt
  sleep 2
done

This is not a strawman built to be laughed at — it already gets the shape right: allocate an address, wire a virtual cable into the container's namespace, publish a name-to-backend mapping, and translate traffic to it. Every production CNI plugin and kube-proxy mode does exactly these four things. The naive version just does them with a shared file and a polling loop instead of a coordinated, event-driven system.

ARC 04 · WHY IT FAILS

Every shortcut in §3 is a specific, quantifiable outage

Four shortcuts, four failure modes, each with real numbers behind it:

  • The IP counter race is a real collision, not a hypothetical one. Two nodes both cat the counter file at the same instant, both read next=45, both write back 46, and both assign 10.244.0.45 to a different Pod. With C uncoordinated allocations drawn from a namespace of M addresses, the birthday-paradox bound says a ≥50% chance of at least one collision appears once C ≈ 1.2·√M. Even a generous /16 overlay range (65,536 addresses) crosses that threshold after only ~300 allocations cluster-wide — a single busy afternoon of Pod churn, not a rare edge case.
  • Local-only routes mean 100% cross-node packet loss, not degraded performance. ip link set veth0 master br0 only wires the Pod into its own node's bridge. A Pod on node B has never heard of it. This isn't a slow path — it's silent, complete unreachability, discovered the moment you run more than one node.
  • Full-ruleset rewrites cost O(total rules) work for an O(1) event. Flushing and reprogramming the entire NAT table every 2 seconds means a cluster with 500 services × 20 backends redoes 10,000 rule insertions on a timer, whether or not anything changed, and at ~100–300 µs per iptables insertion (not the batched iptables-restore path — real production kube-proxy uses that specifically to avoid this), that is 1–3 seconds of NAT-table downtime every single cycle, during which in-flight connections can hit a half-rewritten table.
  • A flat text file is not a control loop. When a Pod dies, nothing removes its line from backends.txt. Clients keep getting DNAT'd to a dead IP until a human notices — there is no readiness signal, no health check, no reconciliation (chapter 9's entire subject) tying the file to reality.
THE PATTERN TO NOTICE

Every failure above is the same root cause wearing a different costume: state that should be coordinated and event-driven is instead uncoordinated and polling-driven. §5 fixes exactly that, twice — once for "how does a Pod get an IP" (CNI + per-node IPAM ranges) and once for "how does traffic reach the right backend" (kube-proxy watching the API server instead of polling a file).

ARC 05 · CNI & KUBE-PROXY, DERIVED

Two independent fixes: delegate the wiring, watch instead of poll

The naive script conflated two genuinely separate problems — "give this Pod an address and a wire" and "keep a Service's backend list correct." Kubernetes' real architecture splits them into two independently pluggable systems. Step through how each one is actually derived from the naive version's failures.

From shell script to CNI contractSTEP-BY-STEP

The Service side: from a polled text file to a watched API object

kube-proxy runs on every node as a controller in exactly the informer sense chapter 9 derived: it watches Service and EndpointSlice objects through the API server (never touching etcd directly — chapter 6's rule holds here too), maintains an in-memory desired ruleset, and reconciles the kernel's actual packet-forwarding state (iptables, IPVS, or nftables tables) to match it. No polling interval, no full-file rewrite — a watch event for one endpoint triggers a diff against just the rules that endpoint touches.

THE INDIRECTION THAT MAKES THIS CHEAP

kube-proxy's iptables mode never writes one flat rule per backend. It builds three levels: a dispatch chain (KUBE-SERVICES) that jumps to a per-Service chain (KUBE-SVC-<hash>) by destination ClusterIP, which in turn randomly jumps (via iptables' statistic match) to one of several per-endpoint chains (KUBE-SEP-<hash>) that do the actual DNAT. When one Pod's IP changes, only its one KUBE-SEP-* chain and the jump probabilities in its KUBE-SVC-* chain are touched — the top-level dispatch table is untouched. §8 shows the real chain names and rule shapes.

ARC 06 · WHY THAT STILL COSTS

CNI and kube-proxy solved the race and the polling — not everything

Three costs survive into the real architecture, each one a recurring source of production incidents (§11 gives named examples of all three):

  • Overlay encapsulation is not free, and mismatched MTU fails silently. A VXLAN overlay (Flannel's default) wraps every Pod packet in an outer UDP/IP header, adding 50 bytes of overhead. If the Pod's interface MTU stays at the host's usual 1500 instead of being lowered to ~1450, packets that fill the MTU don't get a clean "too big" rejection — they either fragment (extra latency, more failure surface) or, on paths where fragmentation is blocked, vanish. The result is a specific, confusing signature: small packets (a TCP handshake) succeed, large transfers hang. §11 walks a real incident with this exact shape.
  • iptables' evaluation cost is not independent of cluster size. The three-level jump chains from §5 help enormously, but the top-level KUBE-SERVICES chain and the per-service dispatch still grow with the number of distinct Services and, at real scale, full-ruleset iptables-restore syncs (which still happen periodically, and on any bulk change) take measurably longer as the rule count grows into the thousands. This is the direct motivation for kube-proxy's IPVS mode (a kernel hash table, GA in 1.11) and for eBPF-based dataplanes that skip netfilter's chain-walking model entirely. §10 quantifies this.
  • NetworkPolicy is a promise the API server cannot keep by itself. Creating a NetworkPolicy object only ever writes an object to etcd via the API server — nothing about the API server, kube-proxy, or kubelet enforces it. Enforcement is entirely the job of your CNI plugin's own policy engine (Calico's Felix, Cilium's eBPF datapath, or nothing at all if you run plain Flannel). This is arguably the single most common Kubernetes security footgun: teams write and apply a NetworkPolicy, see it accepted with no error, and assume they are now isolated — while their CNI silently ignores it.

§7 draws the complete picture with all these pieces in place; §8 is where the exact object shapes and rule formats live.

THE THREE INDEPENDENT WATCHERS ON EVERY NODE

kubelet, kube-proxy, and a CNI policy engine (if your CNI has one) all independently watch the API server and react to the same underlying objects — none of them talks to each other directly, and none of them has special control-plane privilege beyond ordinary RBAC-scoped API access. A corollary worth internalizing: your CNI's policy engine can be completely absent or broken while kubelet and kube-proxy keep working perfectly — which is exactly how NetworkPolicy silently "does nothing" in §6.

ARC 08 · INTERNAL IMPLEMENTATION

Real object shapes, real rule dumps, real plugin calls

(a) The CNI ADD call: how kubelet actually hands off to a plugin

When kubelet's CRI shim finishes creating a Pod's sandbox (chapter 6), it has an empty network namespace and nothing else — no interfaces beyond loopback. kubelet then execs the CNI plugin binary named in its network config, with the plugin's JSON configuration piped to stdin and the operation described entirely through environment variables:

json/etc/cni/net.d/10-mynet.conflist — what kubelet passes on stdin
{
  "cniVersion": "1.0.0",
  "name": "mynet",
  "plugins": [
    {
      "type": "bridge",           // creates the veth pair, plugs one end into a bridge
      "bridge": "cni0",
      "isGateway": true,
      "ipam": {
        "type": "host-local",       // delegated IPAM sub-plugin — see (b) below
        "subnet": "10.244.4.0/24"  // THIS node's exclusive slice — no cross-node coordination needed
      }
    },
    { "type": "portmap", "capabilities": { "portMappings": true } }
  ]
}
envwhat kubelet actually sets before exec'ing the plugin binary
CNI_COMMAND=ADD                          # ADD | DEL | CHECK | VERSION
CNI_CONTAINERID=7f2a...e91c                # the Pod sandbox's container ID
CNI_NETNS=/var/run/netns/cni-a1b2c3          # path to the (currently empty) network namespace
CNI_IFNAME=eth0                          # interface name to create INSIDE the namespace
CNI_PATH=/opt/cni/bin                    # where to find delegated plugins (e.g. host-local)

The exact mechanics of creating that veth pair and moving one end into the Pod's network namespace are the same netns/veth primitives the Container Internals course derives from the kernel up in its Network Namespaces chapter — CNI's job here is orchestrating that call from a plugin binary invocation, not reinventing it. What CNI adds on top is the delegation contract: the bridge plugin calls the host-local IPAM plugin as a nested process, gets back an IP from this node's exclusive subnet slice, and returns a structured JSON result (IP, gateway, routes, DNS) that kubelet stores against the Pod. That per-node subnet slice is precisely what eliminates §4's counter race: two nodes can never allocate the same address because they were never handed overlapping ranges to allocate from in the first place.

(b) Service → EndpointSlice: the object kube-proxy actually watches

A Service never lists its backends directly — that would mean rewriting a large object on every single Pod readiness flip. Instead, a separate controller (§13) watches Pods matching a Service's selector and maintains one or more EndpointSlice objects on the Service's behalf:

yamlwhat you submit
apiVersion: v1
kind: Service
metadata: { name: checkout-api, namespace: prod }
spec:
  selector: { app: checkout-api }
  ports: [ { port: 80, targetPort: 8080, protocol: TCP } ]
  type: ClusterIP
jsonwhat the EndpointSlice controller maintains for you (discovery.k8s.io/v1)
{
  "apiVersion": "discovery.k8s.io/v1", "kind": "EndpointSlice",
  "metadata": { "name": "checkout-api-x7q2p",
    "labels": { "kubernetes.io/service-name": "checkout-api" } },
  "addressType": "IPv4",
  "ports": [ { "name": "", "protocol": "TCP", "port": 8080 } ],
  "endpoints": [
    { "addresses": ["10.244.4.17"], "conditions": { "ready": true, "serving": true, "terminating": false },
      "nodeName": "node-3", "zone": "us-east-1a" }
    // … up to 100 endpoints per slice by default; a 400-Pod Service gets 4 slices, not 1 giant object
  ]
}

(c) NetworkPolicy: an allow-list that only activates once something selects the Pod

The single most misread detail of the whole spec: a Pod with zero NetworkPolicy objects selecting it accepts all traffic, on every port, from anywhere. Creating a policy that selects a Pod for a given direction (ingress and egress are independent) flips that Pod from default-allow to default-deny-except-what-the-rules-list — for that direction only, and only for that Pod.

yamlnetworking.k8s.io/v1 NetworkPolicy — the shape §15's simulator evaluates for real
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-frontend-to-api, namespace: backend }
spec:
  podSelector: { matchLabels: { app: api } }        # which Pods this policy covers
  policyTypes: [ Ingress ]
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { team: web } } # AND'd with podSelector below —
      podSelector:       { matchLabels: { tier: frontend } } # one peer object = both must match
    ports:
    - { protocol: TCP, port: 8080 }

Two selector-combination rules are easy to get backwards and worth stating precisely, because §15's evaluator implements exactly this: within one from (or to) list entry, a podSelector and a namespaceSelector present together are AND'd — the peer must be a pod matching the pod selector, running in a namespace matching the namespace selector. Separate entries in the same from list are OR'd — any one of them matching is enough. An ingress: [] (present but empty) list means the policy contributes zero allow rules — combined with an empty podSelector: {} matching every Pod in the namespace, that is the standard default-deny-all-ingress pattern.

THE INGRESS ANNOTATION GAP

An Ingress object's portable core is small — host, path, backend Service. Everything an operator actually reaches for (canary traffic splitting, request header rewriting, rate limiting, mTLS to the backend) lives in free-form, controller-specific annotations: nginx.ingress.kubernetes.io/canary-weight means nothing to an AWS ALB controller, which wants alb.ingress.kubernetes.io/target-type instead. Swap Ingress controllers and every annotation-driven behavior silently stops working — no error, no warning, just different behavior. The Gateway API (Gateway, HTTPRoute, GatewayClass) exists specifically to make those behaviors typed, portable API fields instead of string conventions each controller invents independently.

Beyond the chart's curve, three concrete limits worth memorizing:

  • Default pod density and Service scale. The default 110-pods-per-node ceiling and the ~5,000-node / 150,000-pod cluster SLO envelope (chapter 7's etcd numbers apply here too — Services and EndpointSlices are etcd objects) both bound how large a single cluster's east-west mesh can realistically get before you shard into multiple clusters.

  • NetworkPolicy's security value is exactly as strong as your CNI's enforcement, and no stronger. A penetration test or compliance audit that only checks "does a NetworkPolicy object exist" and not "does this CNI actually enforce it" is checking the wrong thing. The correct default posture, once you do have enforcement, is default-deny-all (ingress and egress) per namespace, then explicit allow rules — allow-by-default-with-exceptions inverts the entire point of the object.
ARC 11 · REAL-WORLD PRODUCTION

Four incidents with this chapter's exact fingerprints

Incident 1: the VXLAN MTU black hole

A cluster migrates from bare-metal (host-gw routing, no encapsulation) to a cloud environment defaulting to Flannel's VXLAN mode. Nobody adjusts the CNI's advertised Pod-interface MTU down from 1500. Small requests — health checks, DNS lookups, TCP handshakes — work perfectly. Anything that fills a full-size packet (large API payloads, image pulls between Pods, TLS certificate chains) hangs indefinitely. Root cause: the 50-byte VXLAN header pushes real payloads past the path MTU, and ICMP "fragmentation needed" messages that would normally trigger Path MTU Discovery get dropped by an intermediate security group or firewall — a startlingly common combination. Fix: explicitly set the CNI's MTU to 1500 − encapsulation overhead (typically 1450 for VXLAN) cluster-wide, and treat "TCP connects but hangs mid-transfer" as a standing MTU-mismatch hypothesis.

Incident 2: conntrack and SNAT port exhaustion under connection churn

A service that opens a very large number of short-lived outbound connections through a Service or NodePort (a synchronous fan-out to hundreds of downstream calls per request is a classic trigger) starts seeing intermittent dial tcp: cannot assign requested address errors under load. Each SNAT'd connection consumes one ephemeral source port from a finite per-node range (roughly 32,768–60,999 by common default, further divided among destination IPs); high enough churn exhausts it, or fills the conntrack table first. Fixes, in order of leverage: reduce unnecessary short-lived connection churn (connection pooling / keep-alive to downstreams), raise nf_conntrack_max and monitor nf_conntrack_count as a first-class metric, and route latency-sensitive east-west traffic through a CNI that avoids kube-proxy's SNAT path entirely (Cilium's eBPF mode can preserve source identity without SNAT in more topologies).

Incident 3: default-deny egress silently breaks all DNS

A platform team applies a compliance-driven default-deny-all-egress NetworkPolicy to a namespace and nothing in it — correctly, per spec — can resolve any DNS name anymore, because CoreDNS lives in a different namespace (kube-system) and the default-deny rule blocks egress to it along with everything else. Every symptom looks like an application bug (timeouts, "unknown host") until someone checks whether UDP/53 (and TCP/53, for larger responses) egress to CoreDNS is explicitly allowed. This is one of the single most common first-NetworkPolicy mistakes in the industry, precisely because the policy did exactly what it was told — §15's simulator lets you reproduce and fix this exact failure.

Incident 4: AWS VPC CNI IP exhaustion

AWS's native VPC CNI assigns each Pod a real secondary IP from the node's ENI (Elastic Network Interface) pool — no overlay, real VPC routing, but a hard ceiling: each instance type supports a fixed number of ENIs × IPs-per-ENI. A node running smaller, IP-hungry Pods (many sidecars per Pod is a common trigger) can hit that ceiling well before it hits CPU or memory limits, and new Pods on that node sit in ContainerCreating with "no available IP addresses" — a resource exhaustion class that CPU/memory-based cluster autoscaling (chapter 12) does not know how to see. Fixes: prefix delegation (allocate a whole /28 prefix per ENI slot instead of one IP at a time, multiplying effective density) or choosing instance types with larger ENI budgets for IP-dense workloads.

Gopkg/invoke — invoking a CNI plugin binary (the ADD path)
func (e *rawExec) ExecPlugin(ctx context.Context, pluginPath string, stdinData []byte, environ []string) ([]byte, error) {
    cmd := exec.CommandContext(ctx, pluginPath)
    cmd.Env = environ           // CNI_COMMAND=ADD, CNI_NETNS=..., CNI_IFNAME=eth0, ...
    cmd.Stdin = bytes.NewBuffer(stdinData)   // the conflist JSON from §8(a)
    stdout := &bytes.Buffer{}
    cmd.Stdout = stdout
    if err := cmd.Run(); err != nil {
        return nil, pluginErr(err, stdout.Bytes())   // non-zero exit = ADD failed, Pod stays in ContainerCreating
    }
    return stdout.Bytes(), nil       // JSON result: assigned IP, routes, DNS — kubelet stores this
}
Gopkg/proxy/iptables — syncProxyRules(), the loop replacing §3's polling script
func (proxier *Proxier) syncProxyRules() {
    if !proxier.needsFullSync && len(proxier.endpointsChanges) == 0 {
        return                                    // nothing changed — no work, unlike a fixed-interval poll
    }
    desired := proxier.buildDesiredRules()          // KUBE-SERVICES / KUBE-SVC-* / KUBE-SEP-* in memory
    iptablesRestore(desired, iptables.NoFlushTables)  // atomic, incremental apply — never a bare Flush()
    proxier.deleteStaleConntrackEntries()          // evict conntrack rows pointing at removed endpoints
}
Gopkg/controller/endpointslice — packing Pods into slices
func (r *reconciler) reconcile(svc *v1.Service, readyPods []*v1.Pod, existingSlices []*discovery.EndpointSlice) {
    desired := toEndpoints(readyPods)              // address + ready/serving/terminating conditions
    for chunk := range chunkBy(desired, maxEndpointsPerSlice) { // default 100
        upsertSlice(svc, chunk)                    // touches only the slice(s) that actually changed
    }
    // a single giant Endpoints object (the pre-1.19 model) had to be rewritten,
    // in full, on every Pod readiness flip — this is the fix for that.
}
Goa CNI policy engine's ingress evaluation (Felix/eBPF-shaped, simplified)
func (pe *PolicyEngine) AllowsIngress(src, dst *Pod, proto string, port int) bool {
    selecting := pe.policiesSelecting(dst, Ingress)
    if len(selecting) == 0 {
        return true                              // default-allow — §8(c)'s central rule
    }
    for _, pol := range selecting {
        for _, rule := range pol.IngressRules {
            if rule.MatchesPeer(src) && rule.MatchesPort(proto, port) {
                return true                          // any one matching rule, in any selecting policy, is enough
            }
        }
    }
    return false                                  // selected, but nothing matched — default-deny
}
WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. Exec a binary, don't call a library. A subprocess boundary means a CNI plugin can be written in any language, versioned independently of Kubernetes' own release cycle, and — critically — a crash or hang in the plugin can't take kubelet down with it. The cost (fork+exec latency per Pod) is accepted deliberately, the same trade PostgreSQL's process model makes for query isolation. 2. Three-level iptables indirection instead of one flat rule set. It looks like unnecessary ceremony until you ask "what changes when one Pod's IP changes?" — with indirection, exactly one small chain; without it, every rule referencing that Service. The indirection is what makes incremental, non-disruptive updates possible at all.
