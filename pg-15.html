POSTGRESQL INTERNALS · CHAPTER 15

Query Pipeline I: Parser,
Analyzer & Rewriter

A SQL string is not a plan, and it is not even a data structure the executor could touch. Before a single row moves, PostgreSQL turns text into a tree three separate times: a raw parse tree that knows nothing about your schema, a Query tree that has resolved every name against the catalog, and a rewritten tree where views, rules, and row-level security have already been substituted in. This chapter follows that transformation node by node, through the real structs — Node, RangeTblEntry, Var, A_Expr — that the planner in chapter 16 receives as its only input.

ARC 01 · THE PROBLEM

A string carries no positions, no types, and no names the executor can use

A client library hands libpq a byte string — "SELECT id, total FROM orders WHERE customer_id = $1" — over the wire as a Parse or simple Query protocol message. The executor that eventually runs this query (chapter 17) operates on none of that: it walks a tree of typed expression nodes, calling ExecEvalExpr() against compiled ExprStates, and fetches tuples through a TupleTableSlot whose descriptor already knows every column's type OID, byte width, and alignment. Between "a string arrived on a socket" and "the executor has typed nodes to walk" sits the entire subject of this chapter, and skipping any part of it is not an option — the executor cannot interpret text, and the planner in chapter 16 cannot cost a scan of a table it hasn't resolved to a relation.

Unpack exactly what the string is missing, because each gap is closed by a distinct, purpose-built transformation:

  • No identity. orders is four ASCII bytes. It could be an ordinary table, a view, a foreign table, a partition parent, or nothing at all — and it could be shadowed by a same-named relation earlier on search_path. Nothing in the string decides which.
  • No types. customer_id = $1 says nothing about whether customer_id is int4, bigint, or a domain over numeric — and therefore nothing about which = operator applies, or what $1 must be implicitly cast to.
  • No column addressing. The executor addresses columns by integer offset into a physical tuple, never by name. Every occurrence of total in the string must become a numbered slot before anything can run.
  • No semantics beyond syntax. If orders turns out to be a view, "select from orders" doesn't mean "read a relation" — it means "run whatever query the view was defined as," and that fact lives in a system catalog (pg_rewrite), not in the client's bytes.

Three purpose-built stages close those four gaps, in a fixed order that this chapter derives and then follows structurally. Lexing and parsing — a flex scanner feeding a bison grammar that needs zero database access — resolves syntax into a raw parse tree. Parse analysis resolves that raw tree's names and types against the catalog into a Query tree. The rewriter then substitutes view definitions, rule actions, and row-security policies into that Query before it is ever handed to the planner. Get the order wrong — say, look up orders in pg_class while still deciding whether the token stream is even grammatically valid SQL — and you've coupled two problems that are far cheaper solved separately, which is exactly the mistake §3 makes on purpose so §4 can quantify it.

WHY THIS MATTERS FOR CHAPTER 16 AND BEYOND

The planner never sees your SQL text. Its only input is the Query struct this chapter's pipeline produces — a tree of RangeTblEntry, Var, TargetEntry, and expression nodes, fully resolved and already rewritten. Every planner behavior you study next chapter — join reordering, index selection, the custom-vs-generic plan decision for prepared statements — operates on this tree, never on characters. When something that looks like "the planner did something wrong with my view" turns up in production, the actual cause frequently sits one stage upstream, in what the rewriter substituted before the planner ever ran.

DEEP CONTEXT · WHY THE GRAMMAR HAD TO BE REWRITTEN, NOT PATCHED

Original POSTGRES (1986) spoke POSTQUEL, a query language with its own hand-built parser reflecting Stonebraker and Rowe's own design, not the SQL standard. When Andrew Yu and Jolly Chen replaced it with SQL for Postgres95 (1994-95), they didn't patch the old grammar — they wrote a new one, because POSTQUEL's grammar and SQL's grammar disagree at a structural level (subquery placement, join syntax, aggregate scoping). That new SQL grammar is the direct ancestor of today's gram.y; every standard feature added since — outer joins, CTEs (8.4, 2009), window functions (8.4), LATERAL (9.3), JSON path expressions and MERGE (15, 2022), JSON_TABLE (17) — was accreted onto that 1994 skeleton, which is why the file has grown roughly linearly with the SQL standard itself rather than being redesigned.

ARC 03 · NAIVE SOLUTION

Attempt #1: split the string and look things up as you go

Derive the architecture honestly, the way a reasonable engineer would on day one: SQL looks like it has obvious structure — keywords, commas, an = sign — so why not scan for keywords, split on commas, and resolve each table/column name against the catalog the moment you see it, all in one pass?

Cnaive_sql_frontend.c — the strawman, annotated
bool
naive_parse_and_resolve(const char *sql, Relation *out_rel, char ***out_cols)
{
    /* Step 1: find "FROM", split the substring after it on whitespace.
     * Already wrong for: "FROM (SELECT * FROM foo) x", "FROM \"my from table\"",
     * a column literally named from_date, or a string literal containing
     * the word FROM inside a WHERE clause.                                */
    char *from_kw = strcasestr(sql, "FROM");
    char table_name[64];
    sscanf(from_kw + 4, "%63s", table_name);

    /* Step 2: resolve RIGHT NOW, fused into the scan — this is the crux
     * of the naive design: syntax checking and catalog lookup are the
     * SAME pass, so you cannot tell a syntax error from an unknown-table
     * error until you've already taken a snapshot and touched pg_class. */
    Relation rel = heap_openrv_extended(makeRangeVar(NULL, table_name, -1), AccessShareLock, true);
    if (rel == NULL)
        return false;    /* but WAS it a syntax error or a missing table? we can't say */

    /* Step 3: find the column list by splitting between SELECT and FROM
     * on commas. Breaks on: function calls with commas ("substr(a,1,3)"),
     * a column named "select_count", a subquery target list, CASE
     * expressions containing commas inside IN-lists...                   */
    char *cols_start = sql + 6;              /* skip "SELECT" — hope it's uppercase */
    char *cols_end = from_kw;
    *out_cols = split_on_commas(cols_start, cols_end - cols_start);
    *out_rel = rel;
    return true;
}

This is not a joke architecture — plenty of early tools and ORMs effectively did this for a restricted subset of SQL, and for a fixed, tiny grammar (say, only SELECT col, col FROM table WHERE col = literal) it even works. The naive design gets one thing conceptually right that's worth keeping: name resolution genuinely does need to happen eventually, against real catalog state. Its fatal flaw is fusing that concern with syntax recognition into a single, string-shaped pass.

ARC 04 · WHY IT FAILS

Ambiguous grammar meets live catalog access — a coupling with no good failure mode

Two independent failures compound here, and it's worth pricing each one on its own terms, because they justify two completely different pieces of downstream machinery.

Failure 1: SQL's grammar is not regular, and barely context-free-friendly

SQL is deliberately ambiguous at the token level in ways that defeat naive splitting and even naive recursive-descent parsing without careful lookahead design. A left paren after an identifier can start a function call, a subquery, or a parenthesized expression list — WHERE (a, b) IN (SELECT ...) vs. WHERE a IN (func(b)) vs. SELECT (SELECT max(x) FROM t) all begin identically at the scanner level. Operator precedence and associativity for arithmetic, comparison, and the fifteen-plus precedence levels gram.y declares with %left/%right/%nonassoc directives cannot be resolved by a comma-splitting pass at all — it has no concept of precedence, only of literal delimiter characters, which is exactly why it breaks the moment a comma appears inside a function call argument list or a CASE ... WHEN x IN (1,2,3) expression. A hand-written recursive-descent parser can handle this, but only by manually encoding the same precedence-climbing logic bison generates automatically from the grammar file — and every SQL keyword that is also a valid identifier (there are dozens: PostgreSQL classifies keywords as unreserved_keyword, col_name_keyword, type_func_name_keyword, and reserved_keyword specifically because different contexts allow different overlaps) multiplies the lookahead a hand-written parser needs. Bison's LALR(1) tables encode all of this once, at grammar-compile time, into a fixed-size state machine that a naive string-splitter has no equivalent of.

Failure 2: fusing catalog lookup into syntax checking makes every syntax error a database transaction

The subtler failure is architectural, not algorithmic. If resolving orders against pg_class happens while you're still deciding whether the token stream is grammatically valid, then you cannot check syntax without a live connection, a snapshot, and (per MVCC, chapter 5) a view of catalog state that could be concurrently changing underneath you. This has three concrete costs: (a) tools that want to validate or reformat SQL without a running server — this is precisely why an extracted copy of PostgreSQL's own raw parser, libpg_query, exists as a standalone C library used by pgFormatter, PostgREST, and query-fingerprinting tools like pganalyze's — become structurally impossible if parsing and resolution are fused; (b) every syntax error becomes indistinguishable from a permission error, a missing table, or a stale cache read, because they all surface at the same point in the same pass; (c) a DDL race — another session drops or renames orders mid-parse — can change the meaning of a token stream while you're still inside the "is this valid SQL" question, which should never have needed an answer from any table at all.

THE CATEGORY ERROR, STATED PRECISELY

A syntax error ("unexpected token") is decidable by a pure function of the token stream and the grammar — no I/O, no locks, no catalog, no network. A semantic error ("relation does not exist", "column is ambiguous", "operator does not exist for these types") is only decidable against catalog state that can change between statements. Conflating them doesn't just produce worse error messages — it means you cannot build a syntax checker that runs offline, cannot cache a validated parse independent of schema state, and cannot even define what "the query is well-formed" means without opening a transaction. §5 separates them on purpose.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Candidate A vs. Candidate B — separating "is this valid SQL" from "what does it mean here"

Candidate A: one pass, catalog-aware grammar actions

Keep a real grammar (fixing failure 1 from §4) but let its reduce actions call into the catalog directly — an attribute grammar where, say, the production that recognizes a table reference immediately calls heap_openrv() and attaches the resolved Oid to the parse node on the spot. This is strictly better than the naive strawman, but it inherits failure 2 whole: the grammar can no longer run without a database connection, a raw tree can no longer be produced for tooling that only wants syntax, and a single ambiguous grammar reduction that gets backtracked (LALR parsers can and do explore, then commit, productions) could trigger a catalog lookup for a table reference that turns out not to be the final parse.

Candidate B: a context-free grammar producing an inert tree, analyzed in a separate pass ✓

Make the grammar produce nothing but syntax — a tree of Nodes holding strings and literals, with zero function calls that touch a catalog, a lock manager, or a snapshot. Then run a second, entirely separate pass — parse analysis — over that finished, syntactically-valid tree, resolving every name and type against catalog state. THE CLINCHING ARGUMENT: ERROR CATEGORIES BECOME REAL TYPES

raw_parser() in src/backend/parser/parser.c can run against nothing but a token stream and can fail with exactly one kind of error: a grammar violation, reported by bison's generated error recovery as syntax error at or near "...". Every other error you have ever seen from PostgreSQL — relation "orders" does not exist, column reference "id" is ambiguous, operator does not exist: integer = text — is raised later, by parse_analyze() or the rewriter, and can only be raised there, because only there does catalog state exist to be wrong against. This is not a cosmetic distinction: libpg_query and PostgreSQL's own pg_stat_statements query normalization both operate on the raw tree alone, entirely without a live catalog, precisely because Candidate B made that possible.

ARC 06 · WHY THAT STILL COSTS

Separation isn't free: generic tree infrastructure and a staleness problem

Candidate B is the right architecture, and PostgreSQL has run it since before the community fork existed — but "just add a second pass" hides two real, ongoing costs that show up as entire subsystems elsewhere in the codebase.

  • Every node type needs a full support quartet. A raw tree that outlives its first use — logged for debugging via nodeToString(), walked by an extension's post_parse_analyze_hook, cached for a prepared statement's next execution — needs generic copyObject(), equal(), and serialize/deserialize (outfuncs.c/readfuncs.c, invoked as outNode()) support for every single node typeparsenodes.h and forget to update copyfuncs.c, and you get a copy that silently drops your new field, a bug class the project lived with for two decades.
  • Prepared statements need the raw tree copied, not reused, on every re-analysis. A cached raw parse tree for a prepared statement can be re-entered by parse_analyze() multiple times — different search paths, different row-security contexts, a replan after invalidation — and analysis is not read-only with respect to the tree it's given (it produces a new, separate Query tree by transforming pieces of the input). PostgreSQL's answer is to copyObject() the cached raw tree before each re-analysis rather than mutate the shared original — which is only possible at all because copyObject() exists generically over every node type, which only exists because of the quartet above.
  • A resolved tree can go stale the instant it's built. The moment parse analysis bakes a relation's OID and a column's varattno into a Query tree, that tree is a snapshot of catalog state at one instant. A concurrent ALTER TABLE can invalidate it a millisecond later. Making early name resolution safe to cache at all (chapter 14 covers the catalog cache side of this) requires the relcache/plancache invalidation machinery — CacheInvalidateRelcache() messages flowing through shared-memory sinval queues to callbacks like PlanCacheRelCallback() — whose entire job is detecting "a tree that was correct when built is not correct anymore" and forcing a fresh re-analyze-and-replan before the stale tree is used again.

None of these costs is a reason to prefer Candidate A — they are the price of doing name resolution correctly and separately, and every one of them is a deliberate, bounded piece of machinery rather than an open-ended correctness risk. §7 assembles the final shape.

ARC 08 · INTERNAL IMPLEMENTATION

The real structs: Node, RangeTblEntry, Var, and how a name becomes an integer

Now the mechanism at the level you'd need to patch it. Three pieces: (a) the Node tagging system every one of these trees is built from, (b) the shape of RangeTblEntry and Var — the two structs that turn names into numbers, and (c) the candidate-ranking algorithm that resolves an overloaded operator or function.

(a) Every node is self-describing, on purpose

Every parse-tree, Query-tree, and plan-tree struct in PostgreSQL begins with the same field, always first:

Csrc/include/nodes/nodes.h — the tag every struct carries
typedef enum NodeTag
{
    T_Invalid = 0,
    T_SelectStmt, T_RangeVar, T_ResTarget, T_A_Expr, T_A_Const, T_ColumnRef,   /* raw tree */
    T_Query, T_RangeTblEntry, T_TargetEntry, T_Var, T_Const, T_OpExpr,        /* Query tree  */
    /* … several hundred more, one per struct in parsenodes.h / primnodes.h / plannodes.h */
} NodeTag;

typedef struct Node
{
    NodeTag     type;      /* MUST be the very first field — every node-shaped
                            * struct starts with this, so a bare (Node *) can be
                            * safely inspected before anyone knows its real type. */
} Node;

/* nodeTag(): read the tag out of ANY node-shaped pointer, generically */
#define nodeTag(nodeptr)   (((const Node*)(nodeptr))->type)

/* IsA(): the safe-downcast check every walker in the codebase uses      */
#define IsA(nodeptr,_type_)   (nodeTag(nodeptr) == T_##_type_)

/* castNode(): assert the tag, THEN cast — a checked cast, not a raw one */
#define castNode(_type_,nodeptr) \
    (AssertVariable(IsA(nodeptr, _type_)), (_type_ *) (nodeptr))

Because NodeTag is the first field of every one of these structs, a function that receives a bare void* — a list element, a cached plan fragment, an argument to an extension hook — can safely determine its concrete type by reading four bytes at offset zero, with no separate type-tag table, no RTTI, and no risk of reading past the allocation to find out. copyObject(), equal(), and outNode() all begin the same way: switch on nodeTag(obj), then dispatch to a per-type function. As of PostgreSQL 16, those per-type functions — along with the node tag enum itself and the tag-to-name tables used by outNode() — are no longer hand-written. src/backend/nodes/gen_node_support.pl parses annotated struct definitions directly out of the headers (src/include/nodes/parsenodes.h, primnodes.h, and friends — annotations like pg_node_attr(no_copy) or pg_node_attr(equal_ignore) on individual fields) and generates copyfuncs.c, equalfuncs.c, outfuncs.c, and readfuncs.c at build time. Add a field to a struct today and the generator either handles it correctly by default or forces you to annotate it — the entire "forgot to update one of four files" bug class from §6 is gone by construction.

(b) RangeTblEntry and Var: the numbered namespace

Parse analysis's central data structure is the range table — a List of RangeTblEntry hung off Query.rtable — and every downstream reference to "a table" is an integer index into that list, never a name again.

Csrc/include/nodes/parsenodes.h — RangeTblEntry (fields that matter here, simplified)
typedef struct RangeTblEntry
{
    NodeTag     type;
    RTEKind     rtekind;        /* RTE_RELATION, RTE_SUBQUERY, RTE_JOIN,
                                 * RTE_CTE, RTE_FUNCTION, RTE_VALUES, …        */
    Oid         relid;          /* only if RTE_RELATION: the resolved table/view OID */
    char        relkind;     /* 'r' ordinary table, 'v' view, 'p' partitioned, … */
    Query      *subquery;       /* only if RTE_SUBQUERY: a nested Query — this is
                                 * exactly what a view's body becomes after rewrite  */
    Alias      *eref;           /* the exposed name + column names other nodes see,
                                 * even if the query used no explicit alias         */
    bool        inh;         /* include child partitions/inheritance children?    */
    bool        lateral;
} RangeTblEntry;

typedef struct Var
{
    Expr        xpr;
    int         varno;       /* 1-based index into the ENCLOSING Query's rtable   */
    AttrNumber  varattno;    /* 1-based column number; 0 means "the whole row"     */
    Oid         vartype;     /* resolved type OID — this is what makes it typed    */
    int32       vartypmod;
    Index       varlevelsup; /* 0 = this query; >0 = an outer query (correlated
                                 * subquery reaching up through nesting levels)      */
} Var;

Walk the resolution mechanically: parsing SELECT total FROM orders WHERE customer_id = 42 yields a raw ColumnRef node holding the bare string "total". Parse analysis's transformColumnRef() (src/backend/parser/parse_expr.c) must decide which range-table entry — if more than one is in scope, from joins or nested queries — actually owns a column by that name, using scanRTEForColumn() (src/backend/parser/parse_relation.c) against each candidate RTE's eref column list; found in exactly one place, it becomes Var{varno=1, varattno=3, vartype=1700 /* numeric */} — 1 because orders is range-table entry #1, 3 because total is its third column in catalog order. Found in zero places: column "total" does not exist. Found in more than one unqualified: column reference "total" is ambiguous. Both errors are only computable once the range table is built — which is why they cannot be syntax errors.

(c) Operator and function resolution: ranking candidates, not just matching names

parse_func.c's func_get_detail() (and the parallel path for operators via oper()/compatible_oper) resolves a call like total + tax or round(price, 2) against every same-named, same-arity candidate in pg_proc/pg_operator using a fixed elimination order: an exact type match wins immediately; failing that, candidates are ranked by type category and "preferred type" per category (each type category, e.g. numeric, string, has one designated preferred type that implicit coercion favors); failing that, by cheapest implicit cast (binary-coercible — same physical representation, no function call needed — beats a cast requiring an actual conversion function). If more than one candidate survives every elimination round, PostgreSQL raises function is not unique rather than guessing — an ambiguity error that, like the ones above, is only computable once you have a resolved list of overloads to rank, never during parsing.

THE PG16 SPLIT: RTEPermissionInfo

Through PostgreSQL 15, a RangeTblEntry carried both "what this entry in the FROM list means" (kind, relid, join info) and "what privileges does running this query require against it" (requiredPerms, checkAsUser, per-column selectedCols/modifiedCols bitmaps) in the same struct. PostgreSQL 16 split the permission-relevant fields out into a separate RTEPermissionInfo struct, referenced from the RTE by a perminfoindex into Query.rteperminfos. The motivation is exactly the staleness problem from §6: permission requirements and range-table shape can now be reasoned about, invalidated, and cached independently — a plan that only needs re-checking because a GRANT changed doesn't need its entire range table rebuilt, and inheritance/partitioning expansion (which multiplies RTEs but not permission checks) no longer has to duplicate permission bookkeeping per child.

ARC 09 · TRADEOFFS

The same front-end problem, five ways

Every SQL (and non-SQL) engine has to decide how much of "understand this query" happens before execution, and how tightly text-parsing couples to catalog/schema state. The spread of answers is a proof by exhaustion that there is no dominant strategy, only different placements of the same costs:

Read the row for MongoDB as the real control group: building queries as a native data-structure API from the start eliminates this entire chapter's problem rather than solving it differently — there is no text to lex, so there is no raw-tree/Query-tree distinction to draw. The cost is that every capability a grammar gives you for free (a uniform ambiguity-free precedence model, a single place to enforce type rules, a rewrite layer that applies transparently to any query shape) has to be reinvented ad hoc per query-builder feature. PostgreSQL's bet — pay the grammar-maintenance and staleness-invalidation costs once, get a uniform semantic layer for every query shape forever — is the same bet every mature textual-SQL engine has made independently.

ARC 10 · PERFORMANCE CHARACTERISTICS

Where the microseconds actually go

raw_parser()'s cost is genuinely well-behaved: LALR(1) table-driven parsing is O(n) in token count with a small constant factor — one table lookup and at most one shift or reduce per token, no backtracking, ever (that's the entire point of building the tables at grammar-compile time instead of exploring at runtime). For the overwhelmingly common case — short OLTP statements, a handful of tables — lexing and parsing are not where your time goes.

Parse analysis is where the real, variable cost lives, and it's driven by catalog cache traffic, not by tree-walking arithmetic. Every RangeVar resolved via parserOpenTable(), every column looked up via scanRTEForColumn(), every operator ranked via func_get_detail() is a SearchSysCache() hit against the relcache/syscache (chapter 14) — O(1) amortized once warm, but a genuine disk read (or at minimum a syscache miss triggering a fresh catalog scan) on a cold backend's first touch of a relation. This is precisely why prepared statements exist as a distinct wire-protocol path: the extended query protocol's Parse message runs lex → parse → analyze → rewrite exactly once and stores the resulting tree server-side; subsequent Bind + Execute messages supply only parameter values and skip straight to planning/execution (chapter 16 covers how — and when — PostgreSQL decides between replanning a fresh custom plan per parameter set versus reusing one cached generic plan, governed in part by plan_cache_mode). Every execution under the simple query protocol's single Query message, by contrast, repeats this entire chapter's work from scratch.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents that live in this chapter's code paths

Incident 1: the eleven-deep view stack

A reporting team builds dashboards by layering views on views — monthly_summary selects from daily_summary, which selects from enriched_orders, which selects from orders_with_tax, eleven layers deep, each adding a join or a computed column, each written by a different person who only ever looked at the layer directly below. A single SELECT * FROM monthly_summary now requires rewriteQuery() to recursively substitute eleven nested subquery RTEs, each carrying its own resolved range table, and star-expansion (which happens at parse analysis, not rewrite — see §8) must expand * at every one of the eleven levels independently before the rewriter can even begin substituting. EXPLAIN output balloons to hundreds of plan nodes referencing none of the original view names, and both rewrite time and subsequent planning time (chapter 16's join-order search grows combinatorially with effective join count) spike hard enough to show up as query latency with no single "slow" table anywhere in sight. Fix: materialize the middle layers (a materialized view or an actual summary table refreshed on a schedule) so the rewriter has one physical relation to substitute instead of a ten-deep subquery chain, and audit view stacks for depth the same way you'd audit call-stack depth in application code.

Incident 2: the post-migration latency spike

A connection-pooled application uses prepared statements extensively — each backend's session holds cached, already-analyzed-and-rewritten trees for its hot statements. A routine deploy runs ALTER TABLE orders ADD COLUMN region text. The DDL itself is fast, but every backend's cached plans referencing orders receive an invalidation message via the sinval queue (§6) the moment they next check it, forcing parse_analyze() and the rewriter to run again from the cached raw tree on the very next execution of every affected prepared statement, across every pooled connection, simultaneously. The result is a synchronized latency spike immediately after the migration — not because the query got slower, but because thousands of connections all paid this chapter's full cost again at the same moment. Fix: this is expected and self-healing (the spike is one execution per connection, not sustained), but teams that don't know the mechanism often misdiagnose it as planner regression or index bloat; knowing that invalidation is per-cached-plan and triggers a full re-analysis, not just a re-plan, turns a page-worthy mystery into an expected blip you can call out in the deploy runbook.

Incident 3: the overload that broke a working query

A team adds a new overloaded function, discount(numeric, integer), alongside an existing discount(numeric, numeric) to support a new integer-percentage code path. A previously working call site, discount(total, 10) — where 10 is an untyped integer literal — that used to resolve unambiguously to the numeric overload via implicit coercion now has two equally ranked candidates: the literal binary-coerces to neither type more cheaply than the other once both overloads exist, and func_get_detail()'s elimination process (§8c) survives with two candidates instead of one. The query that shipped fine yesterday now fails with function discount(numeric, integer) is not unique — not because anything about the call site changed, but because the candidate set it's ranked against did. Fix: the immediate patch is an explicit cast (discount(total, 10::numeric)) at the call site; the durable fix is treating new overloads of existing function names as a compatibility-affecting change requiring a search across the codebase for ambiguous call sites, exactly the way you'd treat a change to a function's existing signature.

Four functions, simplified from PostgreSQL 16/17 sources but faithful in structure and naming. First, the entry point that ties lex/parse/analyze/rewrite together for one statement:

Cpostgres.c → analyze.c — the call sequence for one statement
List *
pg_analyze_and_rewrite_fixedparams(RawStmt *raw_tree, const char *query_string,
                                   Oid *paramTypes, int numParams, ...)
{
    Query      *query;
    List       *querytree_list;

    /* raw_tree came from raw_parser() — pure syntax, no OIDs anywhere yet.
     * copyObject() here because a cached raw tree (prepared statement)
     * may be re-entered by analysis more than once — see §6.            */
    ParseState *pstate = make_parsestate(NULL);
    pstate->p_sourcetext = query_string;
    setup_parse_fixed_parameters(pstate, paramTypes, numParams);

    /* THE pivotal call of this chapter: resolves every RangeVar to an
     * OID, builds the range table, resolves every column to a Var.      */
    query = transformTopLevelStmt(pstate, raw_tree);

    if (post_parse_analyze_hook)          /* extension point: pg_stat_statements et al. */
        (*post_parse_analyze_hook) (pstate, query, NULL);

    free_parsestate(pstate);

    /* Rewrite runs even when nothing rewrites anything — views, rules,
     * and RLS policies are all "no matching rule" for a plain table.     */
    querytree_list = QueryRewrite(query);

    return querytree_list;   /* what the planner (ch. 16) receives */
}

Building the range table — the loop that turns a FROM clause of RangeVars into numbered RangeTblEntry structs a Var can point at:

Cparse_relation.c — building one range-table entry
RangeTblEntry *
addRangeTableEntry(ParseState *pstate, RangeVar *relation,
                    Alias *alias, bool inh, bool inFromCl)
{
    RangeTblEntry *rte = makeNode(RangeTblEntry);   /* type = T_RangeTblEntry, set first */

    /* THIS is where "orders" (a string) becomes an Oid. Everything
     * before this line has been syntax; everything after is semantics. */
    Relation rel = parserOpenTable(pstate, relation, AccessShareLock);

    rte->rtekind = RTE_RELATION;
    rte->relid = RelationGetRelid(rel);
    rte->relkind = rel->rd_rel->relkind;             /* 'r', 'v', 'p', … */
    rte->eref = makeAlias(alias ? alias->aliasname : relation->relname,
                          buildRelationColnames(rel));
    rte->inh = inh;

    table_close(rel, NoLock);      /* keep the LOCK, drop the descriptor */

    /* Append to pstate's range table — its position in this list IS
     * the rtindex every Var referencing this entry will carry.          */
    pstate->p_rtable = lappend(pstate->p_rtable, rte);
    return rte;
}

Finally, the rewriter's view-substitution loop — the mechanism behind "querying a view is really querying its base tables":

CrewriteHandler.c — substituting a view's stored rule into the range table
static void
ApplyRetrieveRule(Query *parsetree, RewriteRule *rule, int rt_index,
                  Relation relation)
{
    Query *rule_action = copyObject(linitial(rule->actions));  /* the view's
                                    * ON SELECT DO INSTEAD action, stored in pg_rewrite */
    RangeTblEntry *rte = rt_fetch(rt_index, parsetree->rtable);

    /* The RTE that used to say "this is relation orders_view" now says
     * "this is a subquery" — carrying the view's own analyzed Query,
     * itself already containing ITS OWN resolved range table.           */
    rte->rtekind = RTE_SUBQUERY;
    rte->subquery = rule_action;
    rte->relid = InvalidOid;    /* no longer "a relation" in the plan's eyes  */

    /* Vars in the OUTER query that referenced rt_index by number are
     * UNCHANGED — they still say varno = rt_index. What changed is what
     * rt_index MEANS. This is why EXPLAIN never names the view: by the
     * time the planner sees this tree, there is no view left to name.   */
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. NodeTag first, always. Putting the tag at a fixed offset means every generic tree-walking function — copyObject(), equal(), an extension's expression-tree mutator — can be written once against Node * and dispatch safely, instead of every caller needing to already know what it's holding. 2. Rewrite operates on RTE contents, not on Var identities. Substituting a subquery in place of a relation, while leaving every Var.varno in the surrounding query untouched, is what makes rule substitution composable — nest it eleven views deep (§11) and the mechanism doesn't change, only the tree grows. 3. Permission and shape are separate structs (§8c). Splitting RTEPermissionInfo out means a view's expansion can change rtekind without touching who's allowed to run the query — two different questions, two different invalidation lifetimes.
