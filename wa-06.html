WHATSAPP ARCHITECTURE · CHAPTER 06

Group Messaging
& Sender Keys

Chapter 5 solved delivery from one phone to one other phone. Now make "Bob" into a group of 256 — or 1024 — people. The naive extension of the pairwise Double Ratchet from chapters 3–4 makes every single message cost the sender N encryptions and N times the upload bytes, on a phone, on a mobile network. That cost is not hypothetical arithmetic — it is the reason group messaging needed its own protocol, and this chapter derives that protocol, Signal's sender keys, from the failure of the obvious approach.

ARC 01 · THE PROBLEM

One sender, many recipients, one set of pairwise sessions

Chapters 3 and 4 built a beautiful piece of cryptography: the Double Ratchet, one independent session per pair of devices, each message forward-secret and self-healing against key compromise. That design was optimized for exactly one shape of conversation — one sender, one recipient device. A group chat violates that shape at the root: one sender, potentially hundreds of recipient devices, all needing the same plaintext, all still requiring end-to-end confidentiality and per-sender authentication.

The question this chapter answers is deceptively simple to state and expensive to answer badly: if the server must never see plaintext, and every recipient device has its own independent pairwise session with the sender, how does one message reach N people without the sender doing N times the work?

  • Confidentiality must hold for every member. Anyone not in the group must be unable to read anything, exactly as in a 1:1 chat.
  • Authenticity must be per-member, not per-group. If everyone shared one symmetric key, any member could forge a message and every recipient would be unable to tell who actually sent it — a group needs to know which of its N members authored each message.
  • Cost must not scale catastrophically with group size on the sending device. A phone on a mobile data plan and a finite battery cannot be asked to pay a cost that grows linearly, let alone worse, with a number (group size) that any member might increase at any time.
  • Membership changes must be handled without silently granting new members access to old history, or letting removed members keep decrypting new messages.

Every subsequent section is this chapter's attempt to satisfy all four without contradicting chapters 3–4's core guarantee: the server only ever handles ciphertext it cannot decrypt.

WHY THIS MATTERS FOR THE REST OF THE COURSE

The solution this chapter derives — sender keys — reappears conceptually everywhere group-scale cryptography shows up: Signal's own group protocol, WhatsApp's status/broadcast features, and it is the direct ancestor of the reasoning behind MLS (RFC 9420), the emerging IETF standard this chapter closes with. If you understand why sender keys trade one axis of security property (post-compromise security) for another (per-message cost), you understand the central tension every large-group E2E protocol has to resolve.

DEEP CONTEXT · THE SENDER KEYS PAPER

The mechanism this chapter derives is not a WhatsApp invention — it is Open Whisper Systems' (Signal's) published group messaging design, first described publicly around 2014 as an extension to the Signal Protocol used for Signal's own group chats, and adopted by WhatsApp when it integrated the Signal Protocol wholesale in 2016 (chapters 3–4). The design goal stated in Signal's own documentation is exactly the one derived independently in §5 below: make per-message group-send cost independent of group size on the sender's device, at the acknowledged cost of weaker security properties on membership change — a tradeoff this chapter states honestly rather than glossing over.

ARC 03 · NAIVE SOLUTION

Attempt #1: just reuse the pairwise sessions

The obvious move: a group is just "a list of people," so treat a group message as N individual 1:1 messages, reusing the exact pairwise Double Ratchet sessions chapters 3–4 already built. No new cryptographic machinery needed — the naive extension of what already works.

pseudocodenaive_group_send.ts — the strawman, annotated
function sendGroupMessage(plaintext, group) {
    const devices = group.allMemberDevices();   // e.g. 256 members × ~1.5 devices avg

    for (const device of devices) {
        /* Each iteration is a FULL pairwise Double Ratchet encrypt:
         * its own ratchet step, its own MAC, its own ciphertext —
         * chapters 3-4's machinery, paid in full, N times. */
        const ciphertext = doubleRatchetEncrypt(plaintext, device.session);
        uploadToServer(device.id, ciphertext);   // N separate uploads
    }
}

This is not architecturally wrong — it is exactly what chapters 3–4 already guarantee will work correctly for any single device, and it requires zero new protocol design. Reusing proven, forward-secret, authenticated pairwise sessions is a defensible first instinct. The question is whether the phone sending the message can actually afford to do this N times, for every message, in every group it's a member of.

ARC 04 · WHY IT FAILS

The cost falls entirely on whoever is talking

Quantify it honestly, with real numbers, because the failure is not "somewhat slower" — it is a wall:

  • Encryption cost. A Double Ratchet encryption step (a Diffie-Hellman ratchet or symmetric-key ratchet plus AEAD encryption) costs low-single-digit milliseconds of CPU on a modern phone. Fine once. At 256 members, that's 256 encryptions — hundreds of milliseconds of pure cryptographic work, on a phone, for one text message, before it even leaves the device. At 1024 members, the ceiling WhatsApp eventually shipped, that's over 1,000 sequential encryption operations for a single "on my way."
  • Upload bytes. Even a compact ~200-byte ciphertext, multiplied by 256 recipient devices, is over 50 KB uploaded for one short text message — and multiplied by 1024, over 200 KB. A photo or voice note (chapter 7) uploaded this way would multiply a multi-megabyte payload by group size, which is exactly why media in groups is never sent this way even under the naive model (chapter 7's pointer-based design is assumed here as a given, not re-derived).
  • The asymmetry is the real problem. This cost is paid entirely by whoever hits send — not amortized across the group, not paid by the server, not paid by recipients. A person messaging a 1000-member community group pays a phone-battery and mobile-data tax proportional to a number (group size) they usually don't control and may not even know precisely. That is an unacceptable product experience: the last person to join a group makes every future sender's phone work harder.
THE NUMBERS AT THE LIMIT

At 1024 members with, say, 1.3 devices per member on average (many users have a phone plus a linked desktop or tablet — chapter 8), a single message requires roughly 1,330 independent Double Ratchet encryptions and uploads. At even 2 ms of crypto work per encryption, that is 2.6+ seconds of pure CPU time before the UI can even show "message sent" — on top of the network time to actually push over 250 KB of ciphertext up a mobile uplink. This is not a "make the crypto library faster" problem; it is architecturally impossible to fix by optimization alone, because the number of independent AEAD operations is the bottleneck, not their individual speed.

The naive approach is correct but untenable. The fix has to change what gets encrypted how many times, not how fast each encryption runs.

ARC 05 · CANDIDATES, EXAMINED

Server-side decrypt-and-refan? A shared key? Or something smarter?

Candidate A: let the server decrypt and re-encrypt per member

The sender encrypts once to the server, the server decrypts and re-encrypts individually per recipient device. This trivially solves the cost problem — the phone does one encryption — but it requires the server to hold plaintext, even momentarily. Rejected outright: this is not a group-messaging design decision, it is the abandonment of end-to-end encryption entirely, the exact property chapters 3–4 exist to guarantee. No amount of "we promise to delete it immediately" changes the fact that the server has read access to every group message — a categorically different trust model than anything else in this course.

Candidate B: one shared symmetric key for the whole group

Generate a single symmetric key, distribute it to every member once, and have everyone encrypt and decrypt group messages with that one key — one encryption per message, regardless of group size, solving the cost problem cleanly. Examine why this still fails: a symmetric key shared by everyone cannot authenticate an individual sender. If Alice, Bob, and Carol all hold the same key, any of them can produce a ciphertext that decrypts validly for the others, and there is no cryptographic way to tell which of the three actually sent it — the key that lets you decrypt is, by construction, also a key that lets you forge. A group chat where messages cannot be attributed to a specific member is not a viable product, and it is a real cryptographic gap, not a minor omission.

Candidate C: sender keys — per-member chain key + per-member signature ✓

Split the problem cleanly: use a symmetric, ratcheting chain key for efficient bulk encryption (solving candidate B's cost problem), but pair it with a per-member asymmetric signature key (Curve25519/XEdDSA, the same signature primitive family used elsewhere in the Signal Protocol) so that only the legitimate owner of that sender key can produce a validly-signed ciphertext attributed to them. Symmetric speed, asymmetric attribution — each member's outgoing messages are cheap to encrypt (one symmetric operation) and unforgeable by anyone else in the group (one signature only that member can produce).

THE CLINCHING ARGUMENT: PAY THE N-COST ONCE, AT JOIN, NOT PER MESSAGE

The insight that makes sender keys work architecturally, not just cryptographically: each member's sender key is distributed to every other member exactly once, at the moment they join the group — and that one-time distribution does use the expensive pairwise Double Ratchet channels from chapters 3–4, paying the N-cost honestly, but only a single time. Every message sent after that is one symmetric encryption plus one signature, uploaded once, with the server performing the fan-out replication to every member's queue (chapter 5's per-device queue mechanism, unchanged). The N-cost didn't disappear — it moved from "every message" to "once per membership change," which is the whole game.

ARC 06 · WHY THAT STILL COSTS

The bill for sender keys: rotation, and what it doesn't protect

Sender keys are the correct architecture, but they trade away a security property the pairwise Double Ratchet had, and that trade has to be actively managed, not ignored:

  • Forward secrecy within the group: yes. The chain key ratchets forward with every message sent (§8 details the mechanism), so compromising today's chain key state does not expose yesterday's messages — exactly like the pairwise ratchet's forward secrecy.
  • Post-compromise security: no, not the same way. The pairwise Double Ratchet self-heals after a compromise because every message includes a fresh Diffie-Hellman contribution, continuously injecting new entropy an attacker doesn't have. A sender key's chain key ratchets forward only using purely symmetric derivation — if an attacker captures a member's current chain key state, they can compute every future message in that chain until the key is explicitly replaced. There is no automatic self-healing.
  • Therefore: membership change requires explicit rekeying. When a member leaves or is removed, every remaining member must generate a fresh sender key and redistribute it to everyone else — otherwise the departed member, who still holds the old chain key, could derive and decrypt every future message in that chain forever. When a member joins, they must not be handed the group's existing sender keys (which would let them decrypt history) — new members instead receive only newly-generated keys going forward, or wait for the next rotation.
  • Rotation cost is quadratic under churn. Each rotation is itself an N-cost event: one member generating a new sender key and distributing it to N-1 others over pairwise channels. If M members must rotate (e.g. one member leaves, triggering everyone else to rotate their own sender key as a precaution, or simply the departing member's key needing replacement doesn't remove the need for the others), the total redistribution work is O(N) per rotation, and a group with frequent membership churn pays that O(N) cost repeatedly — for a 1024-member group with high turnover, the aggregate rekeying work across many joins/leaves can approach O(N²) and, in pathological cases, exceed the cost of the actual messaging it supports.
THE HONEST ADMISSION

Sender keys solve the sending-cost problem completely and solve the group-authentication problem completely — but they solve them by accepting a real, named weakness: security after a compromise depends on prompt, correct rotation on every membership change, a protocol obligation rather than an automatic cryptographic guarantee. §9 and §13 return to this honestly when comparing against MLS, whose entire design goal is fixing exactly this gap with logarithmic-cost rotation instead of linear.

WHY SERVER-SIDE FAN-OUT IS SAFE HERE, WHEN CANDIDATE A WASN'T

Candidate A in §5 was rejected because the server needed to decrypt and re-encrypt — plaintext access. The final architecture's server-side fan-out looks superficially similar (the server is copying one message to many destinations) but is fundamentally different: the server replicates the exact same ciphertext byte-for-byte into every recipient's queue, never touching the plaintext, never needing a key. This is the crucial architectural shift the spec calls out: fan-out moves from the sender's phone (candidate C's actual innovation) to the server, but only because the server's job is now "copy bytes," not "re-encrypt," which requires zero trust.

ARC 08 · INTERNAL IMPLEMENTATION

The sender key state, the ratchet, and the rotation protocol

Three pieces: (a) what a sender key actually is and how the chain key ratchets per message, (b) the distribution protocol at join time, (c) the rotation protocol on membership change.

(a) Sender key anatomy and the per-message ratchet

A sender key is two independent pieces of state, generated once per member per group:

  • Chain key — a symmetric secret that ratchets forward with every message: each send derives a message key from the current chain key via a KDF, then advances the chain key itself, one-way, so a past message key cannot be recomputed from a later chain key state (the source of within-group forward secrecy).
  • Signing key pair — a Curve25519 key pair used with XEdDSA to sign every outgoing message; every other member holds only the public half, enough to verify but never to forge.

(b) Distribution: pay the N-cost once, at join

When Alice joins (or creates) a group, she generates her sender key locally, then sends a SenderKeyDistributionMessage — containing her chain key's current state and her signing public key — to every other current member, individually, over each member's already-established pairwise Double Ratchet session (chapters 3–4). This is the one place the full N-cost from §4 is paid honestly: N pairwise-encrypted distribution messages, N uploads. The difference from the naive design is that this happens once, not on every message.

pseudocodesender_key_distribution.ts — paid once, at join
function joinGroup(myDevice, group) {
    const senderKey = generateSenderKey();      // chain key + XEdDSA signing keypair
    const skdm = buildDistributionMessage(senderKey);

    /* THE ONLY N-COST STEP IN THE ENTIRE SENDER-KEY LIFECYCLE.
     * Uses the existing pairwise sessions from chapters 3-4 — no
     * new key-agreement protocol needed, just their transport. */
    for (const member of group.currentMembers()) {
        const ciphertext = doubleRatchetEncrypt(skdm, member.pairwiseSession);
        uploadToServer(member.deviceId, ciphertext);
    }
    myDevice.storeSenderKey(group.id, senderKey);
}

function sendGroupMessage(plaintext, group, mySenderKey) {
    /* ONE symmetric encrypt + ONE signature, regardless of N. */
    const { messageKey, nextChainKey } = ratchetForward(mySenderKey.chainKey);
    const ciphertext = aeadEncrypt(plaintext, messageKey);
    const sig = xEdDSASign(ciphertext, mySenderKey.signingPriv);
    mySenderKey.chainKey = nextChainKey;                 // ratchet state advances

    uploadToServer(group.id, { ciphertext, sig });   // ONE upload; server fans out
}

THE PATHOLOGICAL CASE

A 1024-member community group with frequent membership churn — people joining and leaving sub-communities throughout the day — can spend more aggregate cryptographic and bandwidth work on rekeying than on the actual messages members send to each other. This is precisely the motivating case for MLS's TreeKEM (§9, §13): logarithmic rather than linear rotation cost is not a nice-to-have at this scale, it is the difference between a usable and unusable large, high-churn group.

ARC 10 · PERFORMANCE CHARACTERISTICS

Big-O you can predict before benchmarking

  • Pairwise model, per message: O(N) encryptions, O(N) uploaded ciphertexts, on the sender's device.
  • Sender-key model, per message: O(1) encryption (one symmetric AEAD op), O(1) signature, O(1) upload — on the sender's device. The O(N) work moves entirely to the server's fan-out replication step, which is cheap because it is a byte copy, not a cryptographic operation.
  • Sender-key model, per membership change: O(N) pairwise-encrypted distribution messages for the rotating member's fresh sender key — this is where the "moved, not eliminated" cost from §6 shows up concretely.
  • MLS (TreeKEM), per membership change: O(log N) — the headline improvement, achieved by organizing key material as a binary tree so only the path from a changed leaf to the root needs updating, rather than every other member individually.
  • Memory: pairwise model needs one Double Ratchet session's state per group member per device — O(N) resident session state on the sender's phone just to be in a large group. Sender-key model needs one sender key per member stored locally (to decrypt everyone else's messages) — still O(N) resident state, but no per-message cost attached to it.

ARC 11 · REAL-WORLD PRODUCTION

The group-size ceiling's history is an engineering timeline

100 → 256 → 512 → 1024: each ceiling was a real cost boundary

WhatsApp's publicly visible group-size limit moved several times over the product's life — from a 100-member ceiling in earlier years, to 256, then 512, and eventually 1024 members for regular groups. Each increase followed (not preceded) infrastructure and protocol work that made the new ceiling's fan-out and rekeying cost tolerable — raising the limit is not a config toggle, it's a claim that the sender-key distribution and rotation cost curves from §10 stay acceptable at the new N, on real phones, on real mobile networks, worldwide, including lower-end devices and slower connections in markets with less reliable infrastructure.

Communities: a layer above groups, not a bigger group

Rather than pushing the single-group ceiling arbitrarily higher, WhatsApp introduced Communities: a structure that links multiple separate groups (each with its own bounded membership and its own sender-key set) under one umbrella, plus announcement-only broadcast groups. This is a direct architectural consequence of this chapter's math — since rekeying cost grows with group size (and worse under churn), the scalable way to support "thousands of people in one organization" is federating many bounded sender-key groups, not creating one group whose rekey storms would dominate all its messaging traffic.

Metadata: the server knows who's in the group, honestly stated

End-to-end encryption in this chapter's design protects message content, but the server necessarily knows the group's membership list, its admins, and its group ID — routing and fan-out (§7) cannot function otherwise, since the server has to know which per-device queues to replicate ciphertext into. This is a real, documented metadata exposure, consistent with WhatsApp's own security whitepaper's scope (it protects message content end-to-end; it does not claim to hide group membership from the operator), and it is worth stating plainly rather than glossing over: encrypting message content does not encrypt the social graph the group membership list represents.

ARC 13 · IMPLEMENTATION WALKTHROUGH

The Signal group protocol's actual shape

Signal's sender-key group protocol is publicly documented (Signal's own protocol documentation and open-source libsignal implementation); WhatsApp's exact internal group-service code is not public, so what follows is the published Signal Protocol's structure plus the server-role reasoning derived in §7–§8.

group-protocol/ — published Signal Protocol structure + derived server roles
├── libsignal/groups/
│ ├── ● SenderKeyState — chain key + iteration counter + signing keypair, one per member
│ ├── ● SenderKeyDistributionMessage — join-time payload sent over pairwise sessions
│ └── SenderKeyMessage — per-message wire format: ciphertext + signature + chain iteration
├── server/ — roles, not published internal names
│ ├── ● group_membership.svc — membership list, admins, group ID — server-visible metadata
│ └── fanout_replicator.svc — copies ONE ciphertext into every member's per-device queue (ch. 5)
└── client/
├── ● rotate_on_membership_change.ts — triggers fresh SenderKeyState + redistribution
└── verify_and_decrypt.ts — XEdDSA verify, then chain-key decrypt

The wire message and the chain-key ratchet, simplified but structurally faithful to the published protocol:

pseudocodeSenderKeyMessage — wire layout
struct SenderKeyMessage {
    keyId:            uint32,     // which SenderKeyState this belongs to (rotation epoch)
    iteration:         uint32,     // chain-key ratchet step index — lets receivers catch up if a message was dropped
    ciphertext:        bytes,      // AEAD-encrypted plaintext under the derived message key
    signature:         bytes       // XEdDSA signature over the above, under the sender's signing key
}

function ratchetForward(chainKey, iteration) {
    const messageKey = KDF(chainKey, "message");   // derive THIS message's AEAD key
    const nextChainKey = KDF(chainKey, "chain");      // one-way step — old chainKey is now unrecoverable
    return { messageKey, nextChainKey, iteration: iteration + 1 };
}
pseudocoderotate_on_membership_change.ts
function onMemberRemoved(group, removedMember) {
    /* Every REMAINING member must do this — not just an admin,
     * not just once for the group. Skipping this step leaves
     * removedMember able to derive all future messages via the
     * chain key they already hold. */
    for (const me of group.remainingMembers()) {
        const freshKey = generateSenderKey();
        me.storeSenderKey(group.id, freshKey);
        for (const other of group.remainingMembers()) {
            if (other === me) continue;
            const skdm = buildDistributionMessage(freshKey);
            sendOverPairwiseSession(other, skdm);   // O(N) again, per remaining member
        }
    }
}
WHY THE ENGINEERS CHOSE THIS

1. Reuse pairwise sessions for key transport, don't invent a new channel. Chapters 3-4's Double Ratchet sessions already exist between every pair of members — using them to carry the SenderKeyDistributionMessage means no new trust bootstrap is needed. 2. Separate confidentiality from authenticity cleanly. A symmetric chain key alone cannot prove who sent a message; bolting on a per-member signature key is the minimal addition that fixes exactly that gap without complicating the bulk-encryption path. 3. Make rotation the client's explicit responsibility, not a server-enforced guarantee. Because the server never sees plaintext or keys, it structurally cannot enforce "you must rotate on membership change" — that obligation lives entirely in client logic, which is precisely why chapter 9's tradeoff table lists this as sender keys' named weakness rather than a solved problem.
