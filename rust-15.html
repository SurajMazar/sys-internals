Concurrency:
Threads, Send & Sync

Chapters 4 and 5 spent their entire budget proving one thing: at any point in a single thread's control flow, a value is either owned by exactly one place, or borrowed immutably by many places, or borrowed mutably by exactly one place — never both at once. That proof is airtight for a program with one instruction pointer. This chapter adds a second instruction pointer — a real OS thread, genuinely running in parallel on another core — and asks the question that breaks every language without an answer: what stops that thread from touching the same memory the borrow checker already promised was exclusively yours? Rust's answer is two one-bit marker traits, Send and Sync, derived automatically for almost every type you will ever write, and enforced by the compiler at the handful of places where data actually crosses a thread boundary.

ARC 01 · THE PROBLEM

Ownership solved aliasing in space. Threads reopen it in time.

Every borrow-checker rule you have used so far is a proof about one linear sequence of instructions. "One mutable reference XOR many immutable references" is checked by walking your function's control-flow graph and confirming that at every program point, the live borrows obey the rule. That proof has an unstated assumption baked into it: there is exactly one program counter walking that graph. An OS thread is a second program counter, with its own stack, scheduled independently by the kernel, free to run at the exact same nanosecond as the first — on a different physical core, with no coordination unless you add some. The moment a second thread exists, "no other code path can be touching this memory right now" stops being something the compiler can conclude just by reading one function's body.

Be precise about the two failure modes this creates, because the chapter — and the industry — routinely conflates them:

  • A data race is a specific, formally defined condition: two or more threads access the same memory location, at least one access is a write, and nothing establishes a happens-before ordering between them. In C and C++, a data race is undefined behavior — full stop. Rust's type system is built specifically to make data races a compile-time impossibility in safe code.
  • A race condition is a broader, older term: any situation where the correctness of a result depends on the relative timing of events. Two correctly-synchronized threads can still produce a wrong business outcome if the program logic itself assumes an ordering that isn't guaranteed. Rust eliminates the first category. It says nothing whatsoever about the second — §11 gives you a famous, expensive example of exactly that gap.

Now try the obvious naive move and watch it refuse to even compile. You have a Vec<i32> in main. You want a background thread to read it. Nothing about ownership (chapter 4) or borrowing (chapter 5) forbids handing that thread a reference — except that std::thread::spawn's closure is not guaranteed to finish, or even start, before main's stack frame that created the vector returns. If main returns first, the thread would be holding a reference into freed stack memory — precisely the dangling-reference shape chapter 5 taught you the borrow checker forbids within one function. Threads make that same danger possible across function boundaries that don't share a call stack at all, which is exactly why thread::spawn's signature demands 'static for anything it captures: the captured data must not be tied to any stack frame that could disappear while the thread is still running.

WHY THIS MATTERS FOR THE NEXT SIX CHAPTERS

This chapter's answer — two marker traits checked at exactly the functions that hand data to another thread — is also the scaffolding chapter 16 needs. async fn doesn't invent a new safety model; it reuses Send at the executor boundary the same way thread::spawn uses it here. Get comfortable deriving Send/Sync by hand now, because in three chapters you'll be asked why a MutexGuard held across an .await point makes a future stop being Send — and the derivation is identical to the one you're about to build.

ARC 02 · HISTORICAL CONTEXT

Fifty years of "how do two things run at once safely" — then Rust

Send and Sync did not appear from nowhere. They are Rust's answer to a problem systems programmers have been patching around since the first multiprogrammed operating systems. DEEP CONTEXT · RUST HAD GREEN THREADS, AND KILLED THEM

It's easy to assume Rust always mapped std::thread::spawn directly onto an OS thread. It didn't. Pre-1.0 Rust shipped an M:N green-threading runtime (the libgreen crate) with its own segmented stacks and cooperative scheduler, competing with a 1:1 OS-thread runtime (libnative) as a compile-time choice. In 2014, the core team ripped it out entirely before Rust 1.0 shipped in May 2015. The reasoning is worth internalizing: a language that ships a mandatory runtime and scheduler cannot be embedded in a kernel, cannot replace C in an interrupt handler, and forces one scheduling policy on every user. Removing the runtime made std::thread a thin, predictable wrapper over the OS's real threads — and left the door open for the ecosystem (and eventually the language itself, chapter 16) to build userspace concurrency as a library, opt-in, instead of a load-bearing default.

ARC 03 · NAIVE SOLUTION

Attempt #1: shared memory, no rules

Start where most systems languages start — and where most concurrency bugs are born. Four threads increment one shared counter. No lock, no atomic, nothing. This compiles cleanly and runs in C; that's exactly the problem.

Cnaive_counter.c — compiles, links, runs, lies
#include <pthread.h>
#include <stdio.h>

long counter = 0;                       /* one shared word, zero synchronization */

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;                    /* read counter -> add 1 -> write counter: THREE steps, not one */
    return NULL;
}

int main(void) {
    pthread_t t[4];
    for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, worker, NULL);
    for (int i = 0; i < 4; i++) pthread_join(t[i], NULL);
    printf("counter = %ld (expected 4000000)\n", counter);
    return 0;
}

Compile it (gcc naive_counter.c -lpthread -O2) and run it a dozen times. It will not print 4000000 most of those times — and the exact number changes run to run. Watch why, mechanically, in the visualizer below: counter++ is not one CPU instruction, it's a read-modify-write sequence, and two threads' sequences can interleave.

Two threads racing one counter — liveSTEP-BY-STEP

Now the naive Rust attempt at the same idea — not a data race this time, a compile error, which is the entire point of this chapter:

Rustnaive.rs — does not compile
fn main() {
    let numbers = vec![1, 2, 3, 4, 5];

    let handle = std::thread::spawn(|| {
        println!("from thread: {:?}", numbers);   // borrows `numbers`
    });

    println!("from main:   {:?}", numbers);       // ...and main still wants to use it too
    handle.join().unwrap();
}

The closure doesn't take move, so it captures numbers by reference. That reference is tied to main's stack frame — a frame the spawned thread has no guarantee will still exist while it runs. §4 gives you the exact diagnostic rustc produces and derives, from thread::spawn's real signature, exactly why it must reject this.

ARC 04 · WHY IT FAILS

Quantify both failures: a lost-update measurement and a real rustc error

Two failures, two different flavors of "wrong." Give both the precision this book insists on.

The C counter: a measured, reproducible loss

THE NUMBERS

Four threads × 1,000,000 increments each = 4,000,000 expected. Compiled with -O2 on a typical multi-core machine, repeated runs commonly land 5–35% low — anywhere from a few thousand to over a million increments silently vanish, and the exact figure is different every run because it depends on how the OS scheduler happened to interleave four independent instruction streams that nanosecond. This is CWE-362, the formally catalogued weakness class for exactly this shape of bug, and it is not a corner case — it is the default outcome of naive shared-memory concurrency in any language that permits it. Worse than a wrong number: because a data race is undefined behavior in C, the standard doesn't even guarantee you get "a plausible but wrong" answer — an optimizing compiler is entitled to assume the race can't happen and transform the loop in ways that produce results with no obvious relationship to the source at all.

The mechanism is simple once you see it: counter++ lowers to load counter into a register, add 1, store the register back to counter. If thread A loads 41, and before A stores 42, thread B also loads 41 and stores 42, then A's later store of 42 lands too — one whole increment from A is gone, and neither thread ever saw anything obviously wrong locally. Nothing about this requires a bug in either thread's code; it is a direct consequence of interleaving two independent three-step sequences on one shared word with no ordering guarantee between them.

The Rust attempt: a specific, real compiler error

Feed §3's naive Rust example to rustc and you get, verbatim in shape:

This is not the borrow checker being pedantic — it is reading thread::spawn's real signature (derived precisely in §8) and refusing to let a borrow with an unknown, possibly-short lifetime cross into a closure whose lifetime the compiler cannot bound. Compare the failure shapes: the C compiler accepted the naive program and produced a wrong, non-deterministic answer at runtime, silently, forever, in production. The Rust compiler refused to produce a program at all. That is the trade this whole course keeps re-deriving, now applied to a second axis — time, not just space.

ARC 05 · MOVE, CHANNELS & LOCKS

Three idiomatic fixes, in the order Rust wants you to reach for them

Rust's official guidance, baked into the standard library's ergonomics, is a strict preference order: move ownership when you can, send messages when threads need to coordinate without sharing, and reach for a lock around shared state only when the first two genuinely don't fit. Walk the deck in that order — each step is real, compiling Rust.

ARC 06 · WHY THAT STILL HURTS

What Send/Sync does not save you from

Be honest about the boundary of what you just bought. Send and Sync eliminate one specific, well-defined class of bug — the data race — at compile time, for free, in every safe-Rust program. They do not make concurrent programming easy, and they do not make it correct in the broader sense. Four real costs:

  • Deadlocks are still entirely possible, and entirely your problem. The type system tracks aliasing, not lock ordering. Two threads that acquire the same two mutexes in opposite order will deadlock in Rust exactly as readily as in C++ — nothing in Mutex<T>'s type prevents it, because from the type system's perspective each individual .lock() call is perfectly fine in isolation.
  • Arc::clone(&x)-before-every-move is real, structural verbosity. Sharing mutable state across N threads means writing N clones of the handle before spawning N closures — a pattern idiomatic enough to have its own name ("the shadowing clone dance") and terse enough once you've internalized it, but a genuine first-week stumbling block, and still more lines than the equivalent Go or Java code.
  • Mutex poisoning trades a rare crash for a permanent, chapter-spanning Result. If a thread panics while holding a std::sync::Mutex's guard, the mutex is marked poisoned, and every future .lock() returns Err instead of quietly handing out a guard over possibly-inconsistent data. Correct and honest — and it means .lock().unwrap() is everywhere in real Rust code, an ergonomic tax paid for a genuine safety guarantee.
  • Coarse locking taxes parallelism you thought you bought. Wrapping one big Mutex<HashMap<K,V>> around an entire cache turns N logically-independent lookups into N serialized ones the instant any thread holds the lock — Amdahl's law doesn't care that your CPU has 32 cores if the section it must run serially dominates. §10 makes this a concrete, measured curve, not a slogan.
HONEST LIMIT

RwLock<T>'s fairness policy is explicitly not guaranteed by the standard library — the docs state plainly that the underlying platform's implementation decides reader/writer priority, and a write-starved RwLock under a sustained flood of readers is a real, documented, platform-dependent possibility, not a hypothetical. Send/Sync guarantee the absence of data races. They say nothing about liveness, fairness, or forward progress — three different, harder problems this chapter deliberately does not claim to solve.

thread::spawn and mpsc move ownership between threads over time — at any given instant, exactly one thread owns the value. ARC 08 · COMPILER INTERNALS

How the compiler actually derives Send and Sync — and where they're checked

Here is the whole trick, and it is smaller than most people expect. Send and Sync are auto traits: unsafe, marker-only (zero methods, zero runtime representation), and implemented automatically for a struct or enum if and only if every field already implements it. There are exactly three families of deliberate exceptions in the entire standard library, each an explicit negative impl written by a human who understood exactly why the automatic derivation would be unsound. Everything else — every struct you will ever write, unless it directly contains one of those three exceptions — is Send and Sync for free, with zero annotations, because the compiler proved it by structural induction over your fields.

(b) The three deliberate exceptions

Everything below is a real, load-bearing negative implementation from the standard library — not a rule the compiler invented per-type, a rule the type's author wrote:

Rust (real shape)the three opt-outs that make "auto" trustworthy
// alloc::rc — Rc's refcount is a plain, non-atomic `Cell<usize>`.
// Two threads incrementing it at once is exactly §3's C data race.
impl<T: ?Sized> !Send for Rc<T> {}
impl<T: ?Sized> !Sync for Rc<T> {}

// core::cell — UnsafeCell is the ONLY legal way to get a *mut T from a &T.
// Every interior-mutability type (Cell, RefCell) contains one, and inherits
// !Sync from it automatically — no per-type impl needed, just propagation.
impl<T: ?Sized> !Sync for UnsafeCell<T> {}

// core::marker — raw pointers carry no lifetime and no borrow-checker
// tracking at all, so the compiler refuses to assume ANYTHING about them.
impl<T: ?Sized> !Send for *const T {}
impl<T: ?Sized> !Send for *mut T {}

Notice what is not on this list: Mutex<T>, Arc<T>, and RwLock<T> are not exceptions at all — they are ordinary generic types with unsafe impl Send/unsafe impl Sync blocks conditioned on their type parameter, which is a fundamentally different, composable mechanism §13 shows you verbatim.

THE REAL PATH: FUTEX, NOT A SPIN LOOP

On Linux, std::sync::Mutex is built on a futex (fast userspace mutex): the uncontended fast path is a single atomic compare-and-swap with no syscall at all — genuinely cheap. Only when that CAS fails (someone else holds it) does the thread make a futex_wait syscall, which parks it off the run queue entirely until the holder's futex_wake on unlock. This is why an uncontended Mutex costs nanoseconds and a contended one costs a full context switch — the two-tier design is deliberate, and it's the same futex primitive channels and condition variables build on underneath.

MODEL, NOT MEASUREMENT

The curves are an analytic sketch — throughput ∝ useful parallelism minus a contention penalty that grows with the fraction of exclusive operations — tuned to match the well-known qualitative shape of real lock-contention benchmarks (readers-writer locks pull ahead of a plain mutex precisely as the write fraction drops, and channel-based single-ownership removes contention entirely at the cost of one thread doing all the writing). ARC 11 · REAL-WORLD INCIDENTS

Three stories, three different lessons about races

Incident 1: Dirty COW — a nine-year-old kernel race condition (CVE-2016-5195)

Disclosed in October 2016 but present in the Linux kernel since 2007, Dirty COW is a TOCTOU race in the kernel's memory subsystem: a narrow timing window in how copy-on-write breakage interacted with madvise(MADV_DONTNEED) let an unprivileged local process win a race and write to memory it should only have been able to read — including read-only files owned by root. It was reliably exploitable for privilege escalation on essentially every Linux system in production at the time. It is CWE-362, the same weakness class as §4's naive counter, at kernel privilege level instead of a lost integer.

Incident 2: actix-web's unsound hand-written Send (RUSTSEC-2018-0019 / CVE-2018-25026)

Rust's compile-time guarantee has exactly one escape hatch: unsafe impl Send, where a human overrides the auto-derivation and personally promises the compiler it's safe. In early versions of the popular actix-web framework, an internal type was given unsafe impl Send without actually satisfying the contract — among several related memory-safety issues in the same advisory, patched in 0.7.15. The lesson is precise: Send and Sync are only as trustworthy as the humans who write unsafe impl blocks for them. The compiler enforces the auto-derived 99% of cases perfectly; the moment a library reaches for the unsafe override, you are trusting a person's proof, not the type system's.

Incident 3: Knight Capital, 2012 — a race the type system cannot see

On August 1, 2012, Knight Capital Group lost $460 million in 45 minutes. The proximate cause: a deployment repurposed an old feature flag ("Power Peg") for a new meaning, but one of eight production servers didn't receive the update — so when live order flow arrived, that one server ran old dead code under the new flag's new meaning, firing millions of erroneous orders while the other seven servers behaved correctly. This is, structurally, the exact same shape of bug as §1's race conditions: multiple concurrent actors (eight servers) operating on inconsistent shared state (a flag whose meaning depended on which code version read it) with no synchronization forcing a consistent view. Include it here deliberately as the honest boundary from §6: Send/Sync prevent memory-level data races inside one running program. They have nothing to say about a fleet of independently-deployed processes disagreeing about what a shared flag means — that class of race is a deployment-discipline problem no type system checks.

Reading the real thing: core::marker, std::thread, std::sync

Where every mechanism in this chapter actually lives (paths simplified from the current stable layout; a few modules have shuffled directories across recent releases, but the shapes below are faithful):

The two trait definitions, exactly as they read in core::marker — this is the entire "magic":

Rustlibrary/core/src/marker.rs
/// Types that can be transferred across thread boundaries.
/// Auto-implemented: true for T unless T contains a field that isn't Send,
/// or a human writes an explicit `impl !Send for T`.
pub unsafe auto trait Send {}

/// Types for which it is safe to share `&T` across threads.
/// Equivalently, by definition: T: Sync  iff  &T: Send.
pub unsafe auto trait Sync {}

thread::spawn's real bound — the single function signature that turns these two zero-method traits into an enforced compile-time gate:

Rustlibrary/std/src/thread/mod.rs
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T,
    F: Send + 'static,   // the closure (and everything it captured) must be Send
    T: Send + 'static,   // the RETURN value must also survive the trip back
{ /* allocates f on the heap, calls the platform thread-create shim */ }

And Mutex<T>'s real shape — the detail that makes Rust's locks structurally different from C++'s: the data field is inside the lock, not a separate variable next to it:

Rustlibrary/std/src/sync/mutex.rs (simplified, faithful shape)
pub struct Mutex<T: ?Sized> {
    inner: sys::Mutex,          // the OS-level futex / pthread_mutex_t handle
    poison: poison::Flag,       // set if a thread panicked while holding the guard
    data: UnsafeCell<T>,        // the DATA ITSELF — lives inside the lock, not beside it
}

unsafe impl<T: ?Sized + Send> Send for Mutex<T> {}
unsafe impl<T: ?Sized + Send> Sync for Mutex<T> {}  // only T: Send needed — the lock guarantees exclusivity

pub struct MutexGuard<'a, T: ?Sized + 'a> { lock: &'a Mutex<T> }

impl<T: ?Sized> Deref for MutexGuard<'_, T> {
    type Target = T;
    fn deref(&self) -> &T { unsafe { &*self.lock.data.get() } }
}
impl<T: ?Sized> Drop for MutexGuard<'_, T> {
    fn drop(&mut self) { unsafe { self.lock.inner.raw_unlock(); } }  // unlock is automatic, ordinary Drop
}

There is no way to obtain a &T or &mut T into data without going through lock() first and receiving a MutexGuard — the field is private, and the only legal path in is the one that also takes the OS-level lock. That is Rust's key innovation over C++'s std::mutex m; int data; pattern: the type system, not a comment, is what stops you from touching data unlocked, because there is no way to name the data without the guard in hand.
