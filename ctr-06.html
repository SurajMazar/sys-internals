CONTAINER INTERNALS · CHAPTER 06

The Root Filesystem:
pivot_root & OverlayFS

Every container believes it owns a private / — its own /bin, /etc, /usr — yet that filesystem is usually assembled, in milliseconds, out of a handful of read-only layers shared with dozens of other containers on the same host, plus a thin writable slice unique to this one. This chapter derives that trick from first principles: why chroot() alone is a toy, why pivot_root(2) is the real primitive, and exactly how OverlayFS turns "N containers, N copies of the image" into "N containers, one shared set of blocks."

ARC 01 · THE PROBLEM

A private root filesystem, without a private disk

A container image ships a full userland — a libc, a package manager's leftovers, an application and its dependencies — commonly 50 MB to several gigabytes. A busy host runs dozens to hundreds of containers from a small number of images (the same node:20-slim or python:3.12 base, over and over). The root filesystem problem is really three problems wearing one trenchcoat:

  • View isolation — container A's /etc/passwd must not be container B's, and neither should be able to resolve a path back out to the host's real /.
  • Write isolation — a container that writes a log file, installs a package at runtime, or crashes half-way through a file write must never mutate the image other containers are reading from.
  • Storage efficiency — if 200 containers each run from the same 180 MB image, the host must not need 200 × 180 MB = 36 GB of disk and, ideally, not 36 GB of page cache either. The common case — nobody writes anything — should cost close to zero extra bytes.

Namespaces (chapters 2–4) and cgroups (chapter 5) answer "what can this process see and how much can it use." This chapter answers a narrower, more mechanical question: what does / resolve to inside a container, and how is that view constructed cheaply? The two Linux primitives that answer it — pivot_root(2) for view isolation and OverlayFS for cheap, copy-on-write write isolation — predate Docker by decades and years respectively, and neither was invented for containers. Docker and Podman are, at this layer, both just disciplined callers of the same kernel mechanism.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Chapter 10 (image layers) is this chapter's mirror image at the distribution layer: a Dockerfile instruction becomes exactly one OverlayFS lowerdir. Chapter 7 (capabilities) explains why an unprivileged process cannot call mount() or pivot_root() at all — both require CAP_SYS_ADMIN, which is precisely why rootless containers had to wait for kernel support that didn't ship until 2021. Learn the mount-table mechanics now; the rest of the course keeps citing them.

ARC 02 · HISTORICAL CONTEXT

From a 1979 syscall to a 2014 filesystem

The root-filesystem story spans two almost entirely separate lineages that only merged inside Docker's first storage driver: chroot-style root-swapping (old, simple, escapable) and union-mount filesystems (a research idea that took over a decade to reach a mainline-quality implementation). DEEP CONTEXT · WHY TWO SEPARATE LINEAGES TOOK SO LONG TO MEET

chroot() solves "what does / mean" in one syscall and one line of C — it shipped in Version 7 Unix in 1979 and needed no filesystem support. Union mounting solves an entirely different problem — "let me read through N directories as if they were one, and write only to the top one" — and that requires real filesystem-level bookkeeping: whiteouts, opaque markers, copy-up semantics, atomic renames. It is unsurprising that the easy syscall arrived 35 years before the hard filesystem did, and that early container runtimes (LXC, early Docker) leaned on the syscall and improvised the filesystem with whatever union implementation was lying around — first AUFS, an out-of-tree patch that never merged into mainline Linux despite a decade of trying, because OverlayFS's simpler, cleaner design won the argument inside the kernel community instead.

ARC 03 · NAIVE SOLUTION

Attempt #1: chroot() into an extracted image

Derive the architecture honestly. The oldest, simplest way to give a process "its own" root filesystem is the syscall that has existed since 1979:

Cnaive_jail.c — the strawman, annotated
int main(void)
{
    /* Extract the image tarball to a real directory on the host's disk. */
    system("tar -xf busybox.tar -C /var/jails/c1");    /* full copy: ~5-200+ MB */

    chroot("/var/jails/c1");   /* CAP_SYS_ADMIN or CAP_SYS_CHROOT required.
                                 * Absolute path lookups now resolve under
                                 * /var/jails/c1 instead of the real root.  */
    chdir("/");
    execve("/bin/sh", argv, envp);   /* the "container's" shell */
}   /* ← every container needs its OWN full copy of the image on disk */

This already captures the correct instinct: give the process a directory that looks like a root filesystem, and change what / means for it. It is exactly what real jail tooling (BSD jail(8)'s filesystem piece, old FTP chroots, early LXC) did for years, and it works for the simple case. Watch it fail in two completely different ways — one a security failure, one an efficiency failure.

ARC 04 · WHY IT FAILS

chroot() changes a lookup rule, not a filesystem boundary

chroot() was never designed as a security boundary — the manpage says so plainly — and the escape you just walked through is not a bug, it is the documented behavior of the syscall working exactly as specified. Three properties make it structurally unfit for containers, independent of any particular exploit:

  • It changes path resolution, not filesystem access. chroot(path) sets the process's root directory pointer — the thing consulted when a lookup begins with / or walks .. past it. Any already-open file descriptor, and any surviving hard link outside the jail, is completely unaffected — the escape in §3 is just "use a reference the syscall didn't touch."
  • It requires no new mount, no new namespace. The process is still in the host's one and only mount table. There is no independent concept of "this container's filesystem" for the kernel to protect — only a pointer that a sufficiently privileged process (root, or anyone holding CAP_SYS_CHROOT) can simply overwrite again.
  • It buys zero storage efficiency. chroot() requires a real, fully-populated directory tree to point at. There is no notion of "share the read-only 95% and only materialize the 5% you changed" — that idea does not exist at the chroot layer at all.
THE NUMBERS

Take a realistic fleet: a 180 MB application image, 200 containers per host, churning at one container start every few seconds during a deploy. Naive chroot-per-container needs 200 × 180 MB = 36 GB of disk just sitting there duplicated, and — worse for the deploy's tail latency — every single container start pays a full tar extraction or filesystem copy, commonly hundreds of milliseconds to several seconds depending on disk speed, before the container's PID 1 even executes. Compare that to the overlay-based startup in §7: a container start becomes a handful of mkdirs and one mount() call, independent of image size, because nothing is copied until something is written.

So the real design has two separable problems to solve, and it is worth keeping them separate because the kernel solves them with two different mechanisms: (1) make the root-swap unescapable — solved by pivot_root() plus a mount namespace, next section; (2) make the root filesystem itself cheap to construct per-container — solved by OverlayFS, §7 onward.

ARC 05 · BETTER SOLUTION

pivot_root(2): don't hide the old root, evict it

pivot_root(new_root, put_old), added in Linux 2.3.41 (2000) for the initramfs-to-real-root handoff at boot, does something categorically different from chroot(): it operates on the mount table, not a per-process pointer. It swaps which mount is "the root mount" system-wide (or, combined with a mount namespace, namespace-wide) and relocates the previous root to put_old so it can be explicitly, completely unmounted — with no reachable path back to it left for any file descriptor, any hard link, any relative walk to find.

The sequence any OCI runtime (runc, crun) performs is always the same seven operations, always inside a freshly unshared mount namespace so none of this leaks back to the host:

THE CLINCHING ARGUMENT: THERE IS NOTHING LEFT TO ESCAPE TO

The §3 escape worked by reaching a reference — an open fd, a lingering hard link — that pointed outside the jail while still being inside the same, single mount namespace as the real root. pivot_root() inside a new mount namespace (CLONE_NEWNS, chapter 2) removes that reference at the namespace level: after step 6 below, the old root mount is not merely hidden, it is unmounted from this namespace's mount table entirely (MNT_DETACH). A stray open fd to a file under the old root can still be read from — the kernel keeps inodes alive as long as something references them — but there is no path, no .. walk, no /proc/self/root trick that resolves back to a live mount of the host filesystem, because that mount no longer exists in this namespace. This is why every real runtime uses pivot_root(), and treats plain chroot() (still used as a fallback when pivot_root() is unavailable — some minimal container images, some old kernels) as a known-weaker mode worth flagging.

ARC 06 · WHY THAT STILL COSTS

pivot_root() fixes escape. It does nothing for the copy.

Notice what pivot_root() did not solve: it needs new_root to already be a fully populated directory tree, exactly like chroot() did. If every container still needs its own private, complete copy of the image on disk before it can pivot into it, you have swapped an escapable jail for an unescapable one — and kept the entire storage-efficiency problem from §4 intact.

  • Disk cost is still O(containers × image size). 200 containers from a 180 MB image is still 36 GB, because pivot_root() has no concept of "this tree is 95% identical to that other container's tree" — two mount points into two separately-populated directories share nothing.
  • Start latency is still dominated by the copy. Populating new_root — extracting a tarball, or worse, running cp -a against a template directory — scales with image size, not with what the container actually needs to change. A 1 GB image costs roughly 1 GB of I/O whether the container will write one log line or fill a whole disk.
  • Nothing is shared, including page cache. Two containers each reading their own private copy of libc.so populate two separate sets of page-cache pages for byte-identical content, wasting RAM as well as disk.
THE MISSING PIECE: THE KERNEL NEEDS TO KNOW "MOSTLY SHARED, PARTLY PRIVATE"

What's needed is a way to tell the kernel: "resolve reads through this stack of read-only directories, but any write should land in — and be visible only through — this one small writable directory on top, without me ever copying the read-only part." That is a union mount: present several directories as one merged view, and multiple containers can point their lowerdir stack at the exact same on-disk image directory simultaneously, sharing both the disk blocks and the page cache, while each keeps a private, tiny upperdir for its own changes. This is OverlayFS, and it is what new_root actually points at in every real container runtime.

ARC 07 · FINAL ARCHITECTURE

Four directories, one merged view

OverlayFS (mainline since Linux 3.18, 2014) is the union mount actually used. It is a pseudo-filesystem: you don't format a disk as overlay, you mount it, pointing at ordinary directories that already exist on some real filesystem (ext4, xfs, btrfs — anything with the right xattr support). ARC 08 · INTERNAL IMPLEMENTATION

Copy-up, whiteouts, and opaque directories

Now the mechanism at the level you'd need to reason about a bug report. Three pieces: (a) how a read resolves through the stack, (b) what actually happens on the first write to a file that only exists in a lower layer (copy-up), and (c) how a deletion of a lower-layer file or directory is represented, since a read-only layer cannot literally have a file removed from it.

(a) Lookup: highest layer wins, first match stops the search

A stat("/etc/app.conf") inside the merged view walks the stack top to bottom — upperdir first, then each lowerdir in the order given to mount() — and returns the first hit. If upperdir has no /etc/app.conf, the kernel checks lowerdir #1, then #2, then #3, stopping at the first directory that contains it. Directory listings (readdir) are different: OverlayFS merges the entries from every layer into one union listing, filtering out anything masked by a whiteout (part c) — so ls /etc shows files from all four layers at once, even though each individual file resolves to exactly one of them.

(b) Copy-up: the whole file moves, atomically, on the first write

Step through what the kernel actually does when a process inside the container opens /etc/app.conf (currently only in lowerdir #2) for writing:

THE COST NOBODY BUDGETS FOR: WHOLE-FILE COPY-UP

Copy-up operates on the entire file, not the byte range being written. Appending one line to a 4 GB SQLite database or log file that lives in a lower layer copies all 4 GB up first. This is the single most common OverlayFS performance surprise in production, and the reason official guidance for both Docker and Podman is: put databases, and anything else with large files under heavy random writes, on a bind-mounted volume (a real directory or block device, no overlay involved) rather than inside the container's writable layer. Kernel 4.19 added an optional metacopy=on mode that copies up only metadata immediately and defers data copy-up until an actual write to file contents occurs — it narrows the window but does not change the fundamental whole-file granularity of the eventual data copy.

(c) Deletion: whiteouts and opaque directories

A read-only lower layer cannot have a file removed from it — the layer is, by construction, immutable (it's usually the same directory backing an image layer shared by other containers). So "delete /var/log/old.log, which lives in lowerdir #3" is represented in upperdir as a whiteout: a character device special file at that exact path, with device number 0/0 (major 0, minor 0) — a device number that can never correspond to a real device, which is exactly why OverlayFS repurposes it as a pure marker. When the union lookup finds a whiteout in a higher layer, it stops the search immediately: the file is treated as not existing, regardless of what any lower layer still holds.

Deleting and replacing an entire directory uses a different, coarser marker: OverlayFS sets the extended attribute trusted.overlay.opaque=y on the corresponding directory in upperdir. An opaque directory tells the merge code "stop descending into lower layers below this point in the tree" — so a fresh, empty replacement directory doesn't need one whiteout per formerly-present file, just a single xattr.

THE STACK-DEPTH LIMIT — AND WHY BUILD TOOLING NAGS YOU ABOUT LAYER COUNT

OverlayFS enforces a maximum lower-layer stacking depth — historically capped at 128 layers, raised over subsequent kernel releases but never unbounded — because every additional layer adds a directory-entry lookup to every single path resolution that misses on the layers above it. A Dockerfile with 40 unnecessary RUN instructions doesn't just bloat the image manifest (chapter 10); it makes every cold-cache file lookup inside the running container walk further down the stack. This is one of the concrete, measurable reasons multi-stage builds and layer-squashing exist as more than tidiness.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What overlay buys, what it costs, what it exposes

Performance first, precisely: OverlayFS's win is entirely in container-start latency and shared page cache, not in steady-state I/O — an overlay merged read is a lookup through, at most, one extra layer of indirection (find which layer owns the file), then a normal read against that filesystem; a write to an already-copied-up file is a normal write. Security surface is the harder tradeoff, and it is real, not manufactured:

  • Mount and pivot_root both require CAP_SYS_ADMIN — one of the broadest capabilities that exists (chapter 7 dedicates a whole chapter to why). The container runtime needs it to set up the mount; a well-configured container process itself should not retain it afterward.
  • Whiteout confusion is a real bug class. Because a whiteout is just "a character device with major/minor 0/0 at a path," any code path that copies an upperdir out of context (backup tooling, naive image export scripts) without preserving whiteout semantics can silently "resurrect" files a container believed it had deleted, or corrupt an image layer's intended deletions.
  • Metadata-only copy-up plus network filesystems is a documented sharp edge (§11 covers the CVE): combining metacopy=on with lower layers on NFS creates a window where OverlayFS's cached notion of "which file this is" and NFS's file-handle reuse can disagree.
  • Shared page cache is a security-neutral, pure win worth stating plainly: because unmodified pages are read from the same underlying inode across every container using that layer, the kernel's normal page cache does the deduplication for free — an attacker gains nothing here that isolation techniques elsewhere (namespaces, cgroups) don't already have to prevent.
MODEL, NOT MEASUREMENT

The chart above is an analytic sketch: full-copy time ≈ image_size / disk_throughput per container, linear in both image size and container count; overlay time ≈ a small fixed per-container mount/mkdir cost, essentially flat in image size because nothing is copied at start. Real numbers depend heavily on storage hardware (NVMe vs. network block storage), filesystem choice under the overlay (ext4 vs. xfs), and whether the image's pages are already warm in cache from a previous container — the point is the shape: full copy scales with data moved, overlay scales with container count alone.

ARC 11 · REAL-WORLD INCIDENTS

Three times the abstraction leaked

CVE-2015-1328: copy-up didn't check who was allowed to write

Ubuntu's kernel shipped an OverlayFS implementation where the file created during copy-up inherited permissions in a way that didn't correctly re-check them against the calling process's credentials when that process was operating inside a user namespace with only a mapped, unprivileged UID. The practical result: an unprivileged local user could arrange for a copy-up to happen in a way that let them create a file with elevated privileges (effectively a local privilege-escalation primitive) purely through normal file operations against an overlay mount — no exotic syscalls needed, just exploiting a permission-check gap in the copy-up path itself. It is the canonical example of why "copy-up" is not a cosmetic detail: it is a privileged filesystem operation (someone has to actually create the file in upperdir) done on behalf of a potentially unprivileged caller, and the kernel has to get every permission check in that path exactly right.

CVE-2021-3178: NFS export IDs, metacopy, and cross-container file reads

When OverlayFS's lower layers sit on NFS and metacopy=on is enabled, OverlayFS caches file identity partly by NFS file handle. NFS file handles can be reused after a file is deleted and a new one created, especially across container/pod boundaries in shared storage setups. The bug allowed a process in one container to read the contents of a file it should never have had access to in another container's storage, because OverlayFS's cached identity mapping pointed at stale, reused NFS state. Red Hat's and Kubernetes distributions' response was to disable metacopy=on by default when lower layers could be network filesystems — a direct example of §10's "metacopy plus NFS is a sharp edge" not being theoretical.

The AUFS-to-overlay2 migration: an operational, not a security, incident

When Docker changed its default storage driver from AUFS to overlay2 (Docker 17.06+), the two drivers' on-disk layer representations were not compatible — an AUFS-formatted /var/lib/docker could not simply be read by the overlay2 driver. Hosts that upgraded Docker without re-pulling images or explicitly migrating found every locally cached image effectively invisible, forcing a full re-pull of every image in use — a self-inflicted, fleet-wide cold-cache event that Docker's own upgrade documentation had to call out explicitly. The lesson generalizes: a storage driver is not an implementation detail you can swap silently once there is real data (layers, containers) sitting on disk in the old driver's format.

The two functions that define this chapter, simplified from real kernel and runc source but faithful in shape and naming. First, runc's pivotRoot — the code path behind §5's stepper deck:

Crunc/libcontainer/rootfs_linux.c — pivotRoot(), simplified
int
pivotRoot(const char *newroot)
{
    int oldroot_fd, newroot_fd;
    char put_old[PATH_MAX];

    /* Assumes CLONE_NEWNS already happened and mount propagation
     * was set to MS_PRIVATE recursively on "/" — otherwise this
     * whole dance would still leak back to the host's mount table. */

    snprintf(put_old, sizeof(put_old), "%s/.pivot_root", newroot);
    mkdir(put_old, 0700);

    /* pivot_root() requires new_root to be a mount point in its own
     * right — bind-mount it onto itself if the caller passed a plain
     * directory (this is what makes an overlay merged/ dir eligible). */
    mount(newroot, newroot, NULL, MS_BIND | MS_REC, NULL);

    if (syscall(SYS_pivot_root, newroot, put_old) != 0)
        return -errno;         /* EINVAL if newroot/put_old aren't real mounts */

    chdir("/");              /* cwd was under the OLD root; must move first */

    /* Old root is now mounted at /.pivot_root under the NEW root.
     * Detach it — MNT_DETACH means "unmount once nothing still has
     * it open", but it's gone from the mount TABLE immediately, so
     * no future path lookup can ever reach it again.              */
    umount2("/.pivot_root", MNT_DETACH);
    rmdir("/.pivot_root");
    return 0;
}

And the kernel side of copy-up — the function that decides, on every write, whether a lower-layer file needs to be materialized into upperdir first:

Clinux/fs/overlayfs/copy_up.c — ovl_copy_up_one(), simplified
static int
ovl_copy_up_one(struct dentry *parent, struct dentry *dentry,
                 int flags)
{
    struct path lowerpath, upperpath;
    struct kstat stat;

    ovl_path_lower(dentry, &lowerpath);
    vfs_getattr(&lowerpath, &stat, ...);      /* size, mode, times, xattrs */

    /* Create the file in upperdir first, same mode/owner, ZERO length. */
    ovl_create_upper(upperdentry, stat.mode, stat.uid, stat.gid);

    if (S_ISREG(stat.mode))
        /* metacopy=off (default classic mode): copy ALL data now,
         * not just the byte range about to be written — this is the
         * whole-file cost flagged in §8b's callout.                */
        ovl_copy_up_data(&lowerpath, &upperpath, stat.size);
    else if (S_ISLNK(stat.mode))
        ovl_copy_up_symlink(&lowerpath, &upperpath);

    ovl_copy_xattr(&lowerpath, &upperpath);      /* preserve setxattr'd metadata */

    /* Atomically swap the dentry to point at the new upper copy —
     * done via rename() through workdir/, never in place, so a
     * crash mid-copy leaves the ORIGINAL lower file untouched and
     * the half-written upper copy orphaned in workdir, not visible. */
    ovl_workdir_rename_to_upper(dentry);
    return 0;
}
WHY THE COPY GOES THROUGH workdir, NOT DIRECTLY INTO upperdir

If copy-up wrote the new file directly at its final path in upperdir, a crash midway through the copy (power loss, OOM kill of the writing process) would leave a partially-written file masquerading as the real file — any subsequent lookup would find it, appearing complete but silently truncated or corrupt. Building the copy in workdir first and only rename(2)-ing it into place at the end makes the whole operation atomic from the perspective of any other reader: the merged view either still sees the untouched lower-layer original, or the fully-written upper copy — never a half-finished one. This is the same "build off to the side, rename atomically" pattern WAL-based checkpoints use (PostgreSQL course, chapter 11) and that most crash-safe filesystem operations converge on independently.
