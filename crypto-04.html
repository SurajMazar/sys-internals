APPLIED CRYPTOGRAPHY · CHAPTER 04

Stream Ciphers: RC4's Fall
and ChaCha20's Rise

A stream cipher turns a short key into an arbitrarily long sequence of pseudorandom bytes — a keystream — and produces ciphertext with a single XOR. It is the one-time pad's promise (chapter 1) without the one-time pad's impossible key-length requirement, and it is exactly as dangerous as that promise sounds if the keystream generator is ever weak, or ever reused. This chapter builds RC4 by hand, watches it collapse under real statistical attacks that broke WEP and then TLS, and then builds a real ChaCha20 — the ARX-based generator that replaced it — verifying every keystream byte against RFC 8439's official test vector.

ARC 01 · THE PROBLEM

Confidentiality for data that doesn't come in 16-byte blocks

Chapters 2 and 3 built block ciphers: DES and AES each encrypt exactly one fixed-size chunk (8 or 16 bytes) at a time, keyed by a permutation that is believed hard to invert without the key. But almost nothing you actually encrypt is a tidy multiple of 16 bytes. A voice packet, a video frame, a database connection's TLS record, a single keystroke sent to a remote shell — all arrive as streams of arbitrary, often small, often unpredictable length. Forcing every one of them through a block cipher means padding, a mode of chaining (chapter 5), and per-block overhead that a resource-constrained device — a 1990s wireless NIC, a 2000s feature phone, a modern IoT sensor — may not have cycles to spare for.

Chapter 1 already showed the theoretically perfect answer: the one-time pad. XOR a message with a truly random key of equal length, once, and the ciphertext is information-theoretically indistinguishable from random noise. The problem was never the algorithm — XOR is nearly free — it was the key: you need as much true randomness as you have data, delivered in advance, used exactly once, to both parties. That is unworkable for anything beyond diplomatic cables carried by hand.

A stream cipher is the pragmatic compromise: replace the one-time pad's truly random key with a cryptographically secure pseudorandom generator (CSPRG), seeded by a short key (and, critically, a per-message nonce), and keep the XOR combiner exactly as it was. If the generator's output is truly indistinguishable from random to anyone without the key, you get one-time-pad-shaped security — confidentiality with zero expansion, byte-at-a-time, no padding, no block alignment — from a key you can actually manage. The entire chapter is about how hard "indistinguishable from random" turns out to be to deliver, and what happens the instant it isn't.

THE CONTRACT A STREAM CIPHER MUST HONOR

Two things, non-negotiably: (1) the keystream must be computationally indistinguishable from random bits to anyone without the key — no statistical bias an attacker can measure faster than brute force; and (2) the exact same (key, nonce) pair must never generate keystream that gets XORed with two different messages. Break either promise and you don't get "somewhat weaker" security — as this chapter shows, you get full plaintext recovery. There is no partial credit in stream cipher security.

DEEP CONTEXT · WHY A TRADE SECRET LEAKED CIPHER WON FOR SO LONG

RC4's dominance from 1994 to the mid-2010s is a lesson in Kerckhoffs's principle (chapter 1) playing out in slow motion. Because RC4 was secret, it wasn't publicly cryptanalyzed until after it leaked — two full ciphertext-shipping product cycles (SSL, WEP) had already deployed it before the research community got a real look. Once public, RC4 turned out to be simple enough to analyze thoroughly — which is exactly why its biases were found, quantified, and eventually weaponized. A design that never undergoes public scrutiny isn't safer; it's just untested, and the bill arrives later, at a worse time, against real deployments.

ARC 03 · NAIVE SOLUTION

Attempt #1: RC4 — a keystream generator you can hold in your head

Ron Rivest's 1987 design is astonishing for how little there is to it: a 256-byte permutation, two indices, and a byte-swap. No S-boxes, no field arithmetic, no rounds — just enough motion in an array to look random. It has two phases: the Key Scheduling Algorithm (KSA), which uses the key to scramble an identity permutation of 0..255, and the Pseudo-Random Generation Algorithm (PRGA), which walks that scrambled permutation forever, emitting one keystream byte per step.

C-like pseudocoderc4_naive.c — the entire cipher, annotated
void KSA(uint8_t *S, const uint8_t *key, int keylen) {
    for (int i = 0; i < 256; i++) S[i] = i;      /* identity permutation */
    int j = 0;
    for (int i = 0; i < 256; i++) {
        j = (j + S[i] + key[i % keylen]) % 256;  /* key stirs the permutation */
        swap(&S[i], &S[j]);
    }
}                                             /* 256 iterations, however short the key */

uint8_t PRGA_next_byte(uint8_t *S, int *i, int *j) {
    *i = (*i + 1) % 256;
    *j = (*j + S[*i]) % 256;
    swap(&S[*i], &S[*j]);
    return S[(S[*i] + S[*j]) % 256];   /* one keystream byte, ~4 array ops */
}

void rc4_encrypt(const uint8_t *key, int keylen, uint8_t *data, int len) {
    uint8_t S[256]; int i = 0, j = 0;
    KSA(S, key, keylen);
    for (int n = 0; n < len; n++)
        data[n] ^= PRGA_next_byte(S, &i, &j);   /* the ENTIRE encryption step */
}

That's it — no rounds, no constant tables, byte-at-a-time output that needs no buffering, and it is fast: a handful of array reads and one swap per output byte, which is why it dominated software-only SSL/TLS on 1990s CPUs and made it into WEP, WPA-TKIP, Microsoft's PPTP, and RC4-based Kerberos. Notice, too, a detail that will matter enormously in §4: the algorithm above takes no nonce. Given the same key, rc4_encrypt produces the exact same keystream, byte for byte, every single time.

ARC 04 · WHY IT FAILS

Two independent ways to die: statistical bias, and no nonce at all

RC4 fails for two separable reasons, and conflating them is the single most common mistake in explaining its downfall. One is a flaw in the generator itself; the other is a flaw in how it was used — and the second is the one that generalizes to every stream cipher ever built, ChaCha20 included.

Failure mode 1: the keystream is not actually uniform

An ideal keystream byte should equal any value 0–255 with probability exactly 1/256. RC4's second output byte does not: Andrew Roos observed, and Fluhrer, Mantin and Shamir formalized (2001), that Pr[Z₂ = 0] ≈ 2/256 — twice what randomness predicts — a direct consequence of a step in the KSA that correlates the second permutation swap with the first two key bytes. That's a small bias, but cryptography measures leaks in bits of distinguishing advantage, and small biases compound: by 2013, AlFardan, Bernstein, Paterson, Poettering and Schuldt had catalogued biases at every one of the first 256 output positions, strong enough that observing the same plaintext byte encrypted under ~2²⁴–2³² independently keyed RC4 streams (exactly what a repeatedly-loaded browser cookie in TLS gives an attacker) lets them recover it via simple frequency counting — no cryptanalysis of the permutation required, just statistics.

Failure mode 2: no nonce means the two-time pad, guaranteed

Recall the one-time pad's second name in the literature: it is only safe used once. Reuse the same pad for two messages P₁ and P₂ and an attacker computes:

THE MATH THAT BREAKS EVERY STREAM CIPHER UNDER KEY/NONCE REUSE

C₁ ⊕ C₂ = (P₁ ⊕ K) ⊕ (P₂ ⊕ K) = P₁ ⊕ P₂

The keystream K cancels out completely, algebraically, regardless of how good the generator is. What remains is the XOR of two plaintexts — not random noise, but human-generated text or structured data, which is asymmetric enough (letter frequencies, common words, headers) that a technique called crib-dragging — guessing a likely fragment of one plaintext and XORing it against C₁⊕C₂ to see if the result looks like readable text in the other — recovers long stretches of both messages with no key-recovery step at all. §15's simulator makes you do this by hand.

The base RC4 algorithm in §3 has no nonce input — only a key. Every protocol that used raw RC4 with a static, rarely-rotated key was one accidental key reuse away from a two-time pad. WEP tried to patch this by prepending a 24-bit initialization vector (IV) to the key before each packet's KSA — but the birthday bound on a 24-bit space is √(2²⁴) ≈ 4,096, and a busy access point transmits that many packets in well under a minute. IV collisions — the same effective per-packet key reused — were not a rare edge case, they were a certainty within the first few thousand packets of any session, compounding directly with Failure mode 1's biases (the FMS attack in §11 exploits both together).

ARC 05 · A BETTER GENERATOR, DERIVED

What a stream cipher needs to get right this time

Rather than patch RC4 (RFC 4345's "RC4-drop[3072]," which discards the biased early bytes, was tried and is still not trusted for new designs), Daniel J. Bernstein started over in 2005 with Salsa20, entered into the EU's eSTREAM competition, and refined it in 2008 into ChaCha20 — the version that won on real-world adoption. Walk through the design requirements in order; each one is a direct rebuttal to a way RC4 failed.

Designing ChaCha20 from RC4's failuresSTEP-BY-STEP
THE ARX BET

ChaCha20 uses exactly three operations: 32-bit addition mod 2³², rotation, and xor — "ARX." No S-box lookup tables (AES's SubBytes and, less famously, RC4's whole PRGA loop both depend on data-dependent array indexing), which means no data-dependent memory access pattern for a cache-timing attacker to measure, and no table to be slow on a CPU without dedicated silicon. Every operation is a native, constant-time machine instruction on essentially every processor built since the 1970s. That is precisely the property mobile chips without AES-NI needed, and precisely the property Google's Adam Langley cites for choosing ChaCha20-Poly1305 as Android's TLS default in 2013 (chapter 7 covers the Poly1305 half).

ARC 06 · WHY THAT STILL COSTS

ChaCha20 fixed the generator. It did not — cannot — fix the contract.

Be precise about what changed and what didn't. ChaCha20 eliminates Failure mode 1 from §4: every keystream byte it produces passes every statistical test known, and two decades of public cryptanalysis (it's had far longer public scrutiny than RC4 ever got before deployment) have found no practical distinguisher. But Failure mode 2 — the two-time pad — is not a bug in RC4. It is algebraic, true of XOR-combined keystreams from any generator whatsoever. ChaCha20 cannot repeal it; it can only make reuse harder to trigger by accident, and the engineering cost of "harder to trigger" is real:

  • The nonce is now the security boundary, and it is the caller's job. RFC 8439's ChaCha20 takes a 256-bit key, a 96-bit nonce, and a 32-bit block counter as separate inputs. The cipher itself enforces nothing about nonce uniqueness — a caller that increments a database sequence, reuses a fixed nonce "for simplicity," or races two threads onto the same counter value has reintroduced the exact WEP failure in a cipher that is otherwise unbreakable.
  • Random nonces have a birthday bound, not a guarantee. If nonces are chosen uniformly at random (rather than a coordinated counter) the classic birthday paradox applies: with a 96-bit nonce space, an expected collision appears after roughly 2⁴⁸ messages under one key — about 281 trillion, enormous, but not infinite, and a hyperscale key-management system genuinely needs to reason about this number rather than treat "96 bits" as a magic incantation.
  • The block counter can wrap. A 32-bit counter limits a single (key, nonce) pair to 2³² × 64 bytes ≈ 256 GB of keystream before the counter repeats — fine for a TLS record, dangerous for naively encrypting a multi-terabyte backup under one nonce.
  • No authentication, ever. Because the combiner is linear XOR, flipping a ciphertext bit flips the corresponding plaintext bit predictably — an attacker with no key at all can tamper with a message in a chosen, undetectable way. Raw ChaCha20 (or raw AES-CTR, chapter 5) must never ship without a MAC; chapter 7 builds ChaCha20-Poly1305, the AEAD construction that closes this gap properly.

So the "final architecture" is not just an algorithm — it's the algorithm plus a nonce-management discipline strict enough that the one truly unrepealable failure mode never fires in practice.

RC4 has no analogue of "block counter" or "keystream block": its PRGA is a single running state machine, one byte at a time, with no way to jump to keystream position 10,000 without generating the 9,999 bytes before it. ChaCha20's counter-indexed block function means you can seek — decrypt block 500 of a file directly, in parallel, on 500 different cores — a capability RC4 structurally cannot offer. That parallelizability is itself a reason large systems (disk encryption, QUIC's packet-level independence) prefer counter-based designs.

ARC 08 · INTERNAL IMPLEMENTATION

The real ChaCha20 state, byte by byte

This is the level of detail you'd need to implement it — and this chapter's JavaScript genuinely does, verified against RFC 8439's official test vector at the bottom of this section.

(a) The 4×4 state matrix

ChaCha20 initializes sixteen 32-bit words — 512 bits total — arranged conceptually as a 4×4 matrix:

The four constant words spell out the ASCII string "expand 32-byte k" in four little-endian 32-bit chunks — a domain-separation constant, not a secret, present purely so that no other algorithm's state can be mistaken for a ChaCha20 state. Words 4–11 are the 256-bit key, split into eight little-endian words. Word 12 is the block counter (starts at the value the protocol specifies — 0 or 1 depending on convention; RFC 8439's test vector below starts at 1). Words 13–15 are the 96-bit nonce, three little-endian words.

(b) The quarter round — the only nonlinear step in the whole cipher

Every mixing operation in ChaCha20 is built from one four-word function, applied to (a, b, c, d):

pseudocodeRFC 8439 §2.1 — the quarter round
QR(a, b, c, d):
    a += b;  d ^= a;  d = rotl32(d, 16);
    c += d;  b ^= c;  b = rotl32(b, 12);
    a += b;  d ^= a;  d = rotl32(d, 8);
    c += d;  b ^= c;  b = rotl32(b, 7);
    /* all additions are mod 2^32; rotl32 rotates a 32-bit word left */

Four add-rotate-xor steps, each feeding the next — this is the entire diffusion mechanism of ChaCha20. The rotation constants (16, 12, 8, 7) are not arbitrary: Bernstein selected them by exhaustive search over differential-cryptanalysis resistance, maximizing how fast a single bit flip in the input spreads to the whole state (the avalanche effect chapter 3 showed for AES's SubBytes/MixColumns pair — here achieved with only addition, rotation and XOR).

(c) Twenty rounds = ten "double rounds," then feed-forward

A single round applies four quarter rounds. ChaCha20 alternates two kinds of rounds for 10 iterations (20 rounds total): a column round — QR on each column of the matrix, (0,4,8,12), (1,5,9,13), (2,6,10,14), (3,7,11,15) — and a diagonal round — QR on each diagonal, (0,5,10,15), (1,6,11,12), (2,7,8,13), (3,4,9,14). Column-then-diagonal in the same iteration is what makes the state fully mix both across rows and across the wrap-around diagonals in the minimum number of rounds Bernstein could find margin for. After all 20 rounds, the original input state is added back to the working state, word by word (mod 2³²) — a feed-forward step that defeats a class of attacks that would otherwise invert the last few rounds — and the sixteen resulting words are serialized little-endian into 64 bytes of keystream.

ARC 09 · TRADEOFFS

RC4 vs ChaCha20 vs the block-cipher alternative

The honest comparison — including AES in counter mode, which chapter 5 shows turns a block cipher into a stream cipher and is ChaCha20's main production rival:

CIPHERCORE OPERATIONSWHAT IT BOUGHTWHAT IT COST
RC4Byte permutation + swap (PRGA) tiny code fast in 1990s software no padding, no nonce plumbing provable statistical bias no built-in nonce banned in TLS since 2015 (RFC 7465)
ChaCha20Add-rotate-XOR (ARX), 20 rounds no known practical bias constant-time by construction fast without hardware support needs a MAC (Poly1305, ch.7) nonce discipline is caller's job

Read this as further evidence of chapter 3's thesis: there is no free lunch, only different places to put the cost. ChaCha20 buys software-only speed and side-channel resistance by demanding rigorous nonce management from every caller; AES-CTR buys hardware speed and a decades-long FIPS paper trail at the cost of being genuinely slow (and historically cache-timing-leaky) on hardware without AES-NI. This is precisely why TLS 1.3 ships both AES-128-GCM and ChaCha20-Poly1305 as mandatory-to-implement cipher suites (chapter 13) rather than picking a winner — the "right" stream cipher depends on what silicon you're running on.

ATTACK COST, IN OPERATIONS YOU CAN COMPARE TO A BUDGET
  • Brute-forcing a 256-bit ChaCha20 key: 2²⁵⁶ trials. At an optimistic 2⁴⁰ trials/second across a planet-scale ASIC farm, that's still ~2²¹⁶ seconds longer than the age of the universe — not a real threat model for the key itself.
  • Colliding a 96-bit random nonce: ~2⁴⁸ messages under one key (birthday bound, §6) — reachable by a hyperscale system pushing billions of messages per key per day; this is why real deployments use deterministic counters, not random nonces, whenever coordination between encrypting parties is possible.
  • Colliding WEP's 24-bit IV: ~2¹² ≈ 4,096 packets (§4) — reachable by an idle laptop in seconds. The 72-bit gap between 96 and 24 bits is the entire distance between "theoretically interesting" and "actively exploited within a minute of joining the network."
  • Distinguishing RC4's biased byte 2 from random: a few hundred to a few thousand independently keyed samples of the same plaintext position — which is exactly what a repeatedly-sent HTTP cookie inside millions of TLS/RC4 connections handed attackers in 2013 (§11).
ARC 11 · REAL-WORLD INCIDENTS

When the contract breaks, on the record

Incident 1: WEP, and the Fluhrer-Mantin-Shamir attack (2001)

WEP fed a 24-bit IV plus a static shared key into RC4's KSA for every packet. Fluhrer, Mantin and Shamir showed that certain "weak" IVs leak information about the key's first byte through RC4's KSA in a way that is directly observable from the first output byte, and that collecting enough weak-IV packets (tools like Aircrack-ng automated this to tens of thousands of packets, later refined to fewer) recovers the full WEP key outright — not just a two-time-pad plaintext leak, the actual secret key. Combined with the 4,096-packet IV collision certainty from §4, WEP was crackable from a passively captured coffee-shop's worth of traffic within minutes. It was formally deprecated by the Wi-Fi Alliance in 2004.

Incident 2: RC4 in TLS — from academic bias to the "NOMORE" attack (2013–2015)

AlFardan, Bernstein, Paterson, Poettering and Schuldt's 2013 paper "On the Security of RC4 in TLS" turned the abstract byte-2 bias from §4 into a working cookie-recovery attack against real HTTPS sessions, needing roughly 2²⁴–2³² TLS sessions carrying the same secret (achievable by getting a victim's browser to make many requests via injected JavaScript). Vanhoef and Piessens' 2015 "NOMORE" attack improved the statistics enough to recover a session cookie in about 75 hours against a real browser. The IETF's response was unambiguous: RFC 7465 (February 2015) prohibits RC4 in TLS outright — one of a small number of RFCs whose entire content is "stop using this."

Incident 3: VENONA — the two-time pad broken by hand, before computers helped much

Not a stream-cipher incident technically, but the canonical demonstration of exactly the §4 math, and worth knowing because it predates RC4 by four decades. Soviet intelligence agencies reused one-time pad material under wartime pressure between 1942 and 1945. U.S. and British cryptanalysts (the VENONA project, declassified in 1995) exploited the resulting C₁⊕C₂ = P₁⊕P₂ collisions — by hand, with crib-dragging on Russian-language message structure — to partially decrypt thousands of messages over the following decades, eventually identifying Soviet intelligence assets in the West. It is the historical proof that "the algorithm is unbreakable" and "the system is unbreakable" are different claims — the one-time pad's math held perfectly; the operational discipline of never reusing a pad did not.

Incident 4: WPA-TKIP's Beck-Tews attack (2008)

WPA's TKIP was a stopgap that kept RC4 (for hardware compatibility with existing WEP chipsets) but added a per-packet key-mixing function and a message integrity check ("Michael"). Beck and Tews showed that TKIP's use of RC4 still permitted a chosen-plaintext keystream-recovery attack against short packets (notably ARP), recovering enough keystream to inject a handful of forged frames — not a full key recovery, but proof that patching RC4's deployment without replacing the underlying cipher only closes some of the doors. TKIP was deprecated by the Wi-Fi Alliance in 2012 in favor of AES-CCMP (WPA2).

The reference C shape — structurally identical to this page's JavaScript, differing only in fixed-width integer types:

Cchacha20_ref.c — chacha20_block(), the reference core
#define ROTL32(x,n) (((x) << (n)) | ((x) >> (32-(n))))
#define QR(a,b,c,d) do { \
    a += b; d ^= a; d = ROTL32(d,16); \
    c += d; b ^= c; b = ROTL32(b,12); \
    a += b; d ^= a; d = ROTL32(d,8);  \
    c += d; b ^= c; b = ROTL32(b,7);  \
} while (0)

void chacha20_block(uint32_t out[16], const uint32_t in[16]) {
    uint32_t x[16];
    memcpy(x, in, sizeof(x));           /* working copy of the state */
    for (int i = 0; i < 10; i++) {         /* 10 double-rounds = 20 rounds */
        QR(x[0],x[4],x[8], x[12]);  /* column round */
        QR(x[1],x[5],x[9], x[13]);
        QR(x[2],x[6],x[10],x[14]);
        QR(x[3],x[7],x[11],x[15]);
        QR(x[0],x[5],x[10],x[15]); /* diagonal round */
        QR(x[1],x[6],x[11],x[12]);
        QR(x[2],x[7],x[8], x[13]);
        QR(x[3],x[4],x[9], x[14]);
    }
    for (int i = 0; i < 16; i++) out[i] = x[i] + in[i];  /* feed-forward add */
}
Cstream_chacha20.c — the XOR loop that turns blocks into a stream
void chacha20_xor(uint8_t *out, const uint8_t *in, size_t len,
                  const uint8_t key[32], const uint8_t nonce[12], uint32_t counter) {
    uint32_t state[16], keystream[16];
    chacha20_init_state(state, key, nonce, counter);   /* constants + key + counter + nonce */
    size_t off = 0;
    while (off < len) {
        chacha20_block(keystream, state);
        size_t n = min(64, len - off);
        for (size_t i = 0; i < n; i++)
            out[off+i] = in[off+i] ^ ((uint8_t*)keystream)[i];   /* the ENTIRE cipher, again */
        state[12]++;                                    /* NEVER let this repeat for a given nonce */
        off += n;
    }
}
WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. The counter lives in the state, not as a loop variable outside it. Putting state[12] inside the exact same 16-word layout the block function already mixes means seeking to any offset is just setting one word — no re-derivation, no re-keying, which is what lets SIMD implementations process 4 or 8 independent counter values (and therefore 4 or 8 blocks) in parallel lanes of the same instruction. 2. The reference implementation is intentionally branchless and table-free. Every operation is add/xor/rotate on a fixed-size array with no data-dependent indexing — compare this to RC4's PRGA in §3, where S[*i] and S[*j] are indices derived from secret-dependent data, a textbook cache-timing side channel. ChaCha20's ARX design closes that class of leak by never having a secret-dependent array index in the first place.

ARC 15 · INTERACTIVE SIMULATOR

Keystream reuse lab: break the two-time pad yourself

Encrypt two different messages under the same key and nonce — the exact mistake that broke VENONA and would break ChaCha20 exactly as thoroughly as it broke RC4.
