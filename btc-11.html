BITCOIN INTERNALS · CHAPTER 11

The Mempool: Fees,
Eviction & Replacement

There is no such thing as "the mempool." Every node keeps its own set of valid-but-unconfirmed transactions, shaped by its own memory limits, its own arrival order, and its own policy settings — none of which is consensus. This chapter derives, from first principles, how a resource-bounded node decides what to hold, what to relay, what to throw away, and what to hand a miner, when transactions arrive faster than blocks can ever confirm them.

ARC 01 · THE PROBLEM

There is no "the mempool"

Chapter 8 drew a line through Bitcoin's rulebook: consensus rules are the ones every full node must agree on to agree on the chain, and policy rules are the ones each node applies locally to decide what it will relay and mine, with zero effect on whether a mined block is valid. The mempool is where that distinction stops being abstract and becomes something you can literally observe diverging between two honest, fully-validating nodes sitting next to each other.

Run bitcoin-cli getrawmempool against two different nodes at the same instant and you will get two different answers — and both are correct. Node A has been running for a year with maxmempool=300; node B just restarted with an empty mempool and is still repopulating from its peers. Node A's operator set minrelaytxfee=0.00005; node B kept the default. A transaction reached A's inbound peer three seconds before it reached B's. None of these differences are bugs, and none of them are visible in a block once one is mined — a block is either valid against the consensus rules or it isn't, completely independent of what any node's mempool happened to contain when it arrived.

What the mempool is: a purely local cache of transactions a node has seen, validated against its policy rules (chapter 8's other half — standardness checks, minimum fees, size caps), and is holding in case they get mined or need to be relayed onward. It exists because of a hard resource-allocation problem that has nothing to do with cryptography and everything to do with economics of scarce space:

  • Transactions arrive continuously — every wallet broadcasting a payment, every exchange sweeping deposits, every Lightning channel closing, all landing on every node's doorstep asynchronously.
  • Blocks arrive roughly every 10 minutes and can hold a bounded amount of data (chapter 7's weight limit) — call it on the order of 1.3–3.5 MB of transactions depending how much of that block is witness data.
  • Memory and bandwidth are finite. A node cannot hold, validate, and relay an unbounded queue of transactions that will never be mined without a hostile actor turning "accept every valid transaction" into a trivial memory-exhaustion attack.
  • The transactions are not interchangeable. They vary wildly in size (a single-input payment vs. a 200-input consolidation) and in how much they're willing to pay — and, critically, some depend on others that haven't confirmed yet.

So the real question this chapter answers is: given transactions arrive faster than blocks can include them, which ones does a resource-bounded, self-interested node keep, in what order does it offer them to a miner, and which ones does it throw away first when it runs out of room? The answer the ecosystem converged on is a single scalar that turns a multi-dimensional allocation problem into a sortable list: fee rate, measured in satoshis per virtual byte. Everything else in this chapter — ancestor scoring, eviction, RBF, CPFP, fee estimation — is machinery built around getting that one number right and acting on it consistently.

WHY THIS MATTERS FOR CHAPTERS 12–16

SegWit (ch. 12) rewrites the byte-counting rules that feed directly into the vsize this chapter's feerate depends on. Taproot (ch. 13) changes what a typical transaction looks like and therefore its typical feerate. And Lightning (ch. 14) turns out to have a life-or-death dependency on exactly the ancestor/descendant limits this chapter derives — a channel's time-sensitive commitment transaction can be rendered unbumpable by an adversary who understands mempool policy better than the protocol's early designers assumed anyone would.

ARC 02 · HISTORICAL CONTEXT

From "accept everything" to a real fee market

Bitcoin launched with essentially no fee market at all. The mempool's current shape — feerate ordering, hard package limits, replace-by-fee, a dynamically rising floor — was assembled incrementally, almost always in direct response to an attack, a spam wave, or a genuine congestion event. DEEP CONTEXT · THE FLOOR EXISTS BECAUSE FREE RELAY WAS ABUSED

The very first relay-fee policy wasn't about revenue — it was self-defense. Once transactions could be relayed and mined for free, flooding the network with dust became free too. minRelayTxFee converted an unpriced externality (every node's bandwidth and memory) into a priced one. Every mechanism in this chapter is a descendant of that one move: if a resource is free, someone will consume all of it.

ARC 03 · NAIVE SOLUTION

Attempt #1: any valid transaction, oldest fee-payer wins

Derive it honestly, the way the earliest reference client effectively worked. Accept any transaction that passes signature and script checks. Keep them all in one unbounded list. When it's time to build a block, sort by whichever number is easiest to read off a transaction — its absolute fee in satoshis — and take from the top until the block is full.

pseudocodenaive_mempool — the strawman, annotated
struct Tx { txid, vsize_bytes, fee_satoshis, inputs[] };

list<Tx> pool;                       /* unbounded */

function onTransaction(tx):
    if verifyScriptsAndSignatures(tx):
        pool.append(tx)              /* accept anything valid, forever */
        relayToPeers(tx)

function buildBlockTemplate(max_bytes):
    pool.sortDescendingBy(tx => tx.fee_satoshis)   /* biggest absolute fee first */
    block = []
    used = 0
    for tx in pool:
        if used + tx.vsize_bytes <= max_bytes:
            block.append(tx); used += tx.vsize_bytes
    return block

This gets real things right: it's simple, it's obviously correct with respect to script validity, and "biggest fee first" sounds like exactly the incentive a miner should follow. It is also precisely the naive server pattern you should always start from before you discover what it costs — the same posture chapter 8 took toward validation and chapter 10 took toward flooding relay.

ARC 04 · WHY IT FAILS

Absolute fee measures the wrong resource

A block does not have a limit on total satoshis collectable — it has a limit on bytes (more precisely, weight, which chapter 7 introduced and chapter 12 will fully explain). A miner filling a fixed amount of block space is running exactly one optimization: maximize total fee collected per byte spent. Absolute fee tells you nothing about that ratio without also knowing size, and size varies enormously — a single-input, single-output payment might be ~140 vbytes; a consolidation sweeping 100 old UTXOs into one output can be well over 15,000 vbytes purely from signature and pubkey data repeated per input.

THE NUMBERS: TWO TRANSACTIONS, ONE BLOCK SLOT

Transaction A — a wallet consolidating 40 old outputs: 25,000 sats absolute fee, 12,500 vbytes. Feerate = 25,000 / 12,500 = 2.0 sat/vB.
Transaction B — an ordinary payment: 350 sats absolute fee, 140 vbytes. Feerate = 350 / 140 = 2.5 sat/vB.
A's absolute fee is 71× larger. But feed 12,500 vbytes of block space to B-type transactions instead of one A, and you fit ~89 of them for 89 × 350 = 31,150 sats — 25% more revenue from the identical block space. The naive sort doesn't just under-perform here; it picks the worse option every time size varies enough, which in a real mempool is always.

Formally, a miner filling a block of budget W vbytes from candidate transactions each with fee fi and size wi is solving

maximize Σ fi·xi   subject to   Σ wi·xi ≤ W,   xi ∈ {0,1}

— a 0/1 knapsack problem. For independent items (no dependencies between them) the well-known near-optimal heuristic is greedy-by-value-per-weight — exactly feerate. Absolute fee is value-per-weight only when every item happens to weigh the same, which no real transaction set does. And there's a second failure mode the naive design ignores entirely: an unbounded list accepting any valid transaction forever is a standing invitation to flood a node's RAM with transactions nobody will ever pay enough to mine — free for the attacker, expensive for every node on the network. Both problems point the same direction: rank and bound by feerate, not by raw fee or raw count.

ARC 05 · BETTER SOLUTION, DERIVED

Sort by feerate — then discover transactions have parents

Fixing §4 looks trivial at first: sort candidates by fee/vsize instead of raw fee, and greedily fill the block from the top. That's correct for transactions with no relationship to each other. It breaks the instant one transaction spends an output created by another transaction still sitting, unconfirmed, in the same mempool — because a block can never include a child before its parent, no matter how much the child pays. Step through how the design has to evolve to survive that fact.

From feerate sort to package-aware scoringSTEP-BY-STEP
THE KEY MOVE

Don't score a transaction by its own feerate. Score it by the feerate of itself plus every unconfirmed ancestor it depends on — the package. A high-fee child transaction pulls its low-fee unconfirmed parent up the ranking automatically, because they're now scored as one unit. This single idea is what makes CPFP (child-pays-for-parent, §8) fall out of the mining algorithm for free, with zero special-cased logic — it's the same sort key doing double duty.

ARC 06 · WHY THAT STILL COSTS

Ancestor scoring is correct — and computationally dangerous if left unbounded

Package-aware scoring solves the mining-order problem. It creates a new one: computing "every unconfirmed ancestor of this transaction" is not a fixed-cost operation — it's a graph traversal whose cost grows with how deep and wide the unconfirmed dependency graph is allowed to get. Left unbounded, that traversal has to re-run, in whole or in part, on every single mempool mutation: every new transaction, every eviction, every block template built.

That's the reason Bitcoin Core hard-caps both directions of the graph. A new transaction may not pull in more than 25 unconfirmed ancestors totalling more than 101,000 vbytes; symmetrically, no unconfirmed transaction may accumulate more than 25 descendants totalling more than 101,000 vbytes before the mempool refuses to accept whatever would push it over. Every insertion is checked against both limits — count and size, ancestor and descendant — because a wide, shallow graph and a narrow, deep one are both attacks on the same underlying cost.

The bill the caps themselves create: pinning

A hard limit that protects the network from combinatorial blowup is also a budget an adversary can spend against you. If your unconfirmed transaction already has, say, 20 of its 25 allowed descendant slots consumed by someone else's low-feerate junk, you may simply be unable to attach the CPFP child you need — not because you won't pay enough, but because there's no room left in the package for your transaction to legally exist. This is a pinning attack, and it is not hypothetical: it is the mechanism by which Lightning's time-sensitive commitment transactions (chapter 14) can be rendered unbumpable exactly when bumping them matters most.

Anatomy of a pinning attackSTEP-BY-STEP
NOT FULLY SOLVED

Package limits, RBF, and CPFP together cover most ordinary fee-bumping needs. Pinning against a determined, well-resourced counterparty is a genuinely open engineering problem — the v3/TRUC transaction proposal and package-relay work (§7, §9) narrow it considerably but had not, as of this writing, closed it completely. Say so plainly rather than pretending it's solved: this is one of the few areas of Bitcoin Core development where "we've made the attack much more expensive" is the honest final answer, not "we fixed it."

WHY TWO INDICES OVER ONE SET

Mining and eviction are mirror-image questions asked of the same graph: mining asks "which not-yet-included package earns the most per byte if I add it now?" (walk ancestor_score — pull the whole unconfirmed history along for the ride). Eviction asks "which package would I lose the least by deleting entirely?" (walk descendant_score — delete the whole unconfirmed future along with it). Same entries, opposite traversal direction, because "what should I add" and "what should I remove" are opposite questions.

ARC 08 · INTERNAL IMPLEMENTATION

Feerate, packages, eviction, and the two ways to bump a stuck transaction

(a) The unit that matters: satoshis per virtual byte

Chapter 7 introduced weight and vsize; chapter 12 explains why witness bytes get a 1/4 discount. For this chapter, only the arithmetic consequence matters: every fee decision — what a wallet should attach, what a node will relay, what a miner will include — is made in sat/vB, fee divided by vsize, never fee divided by raw byte count. Drag the sliders: notice that moving bytes from the base transaction into the witness (exactly what SegWit did) lowers vsize for an identical amount of data, and therefore raises the effective feerate for the same absolute fee.

(b) Block templates as a knapsack problem, solved approximately

With dependencies, the miner's optimization from §4 gains a constraint: a transaction can only be selected if every one of its unconfirmed ancestors is also selected. That's a precedence-constrained knapsack problem, and it's NP-hard to solve exactly for arbitrary dependency graphs. Bitcoin Core doesn't try — it uses a greedy heuristic that is fast, good in practice, and not provably optimal. Step through it:

(d) Eviction and the dynamic fee floor

Every acceptance triggers a size check against maxmempool (default 300 MB). If the mempool is over budget, Bitcoin Core walks the descendant_score ordering from the bottom, deletes the entire package (the worst-scoring transaction plus everything depending on it — they die together, since deleting the parent alone would leave orphaned children anyway), and repeats until back under budget. Each eviction updates mempoolminfee: the floor rises to the feerate of whatever just got thrown out, plus the incremental relay fee (1 sat/vB by default). Nobody sets this number by hand during congestion — it emerges purely from what the mempool has been forced to discard. A transaction offered below the current floor is rejected outright with "min relay fee not met," regardless of how it would have ranked yesterday.

A second, unrelated bound protects against stale, unconfirmable transactions that never get evicted by size because the mempool never fills up: mempoolexpiry, default 336 hours (14 days). Anything older than that is dropped on a periodic sweep regardless of feerate — insurance against transactions that will simply never confirm (a bug, a feerate too low to ever win a spot, an input quietly double-spent elsewhere).

(e) Fee bumping, tool one: Replace-By-Fee (BIP125)

A transaction opts in to replaceability by setting any input's sequence number below 0xfffffffe (recall from chapter 7/8 that 0xffffffff also disables BIP68 relative locktime — the replaceable range and the locktime-active range are adjacent but distinct). A proposed replacement that double-spends one or more mempool inputs must satisfy all five of BIP125's rules simultaneously:

  • Rule 1 — signals replaceability. At least one transaction being replaced (or one of its own unconfirmed ancestors) opted in.
  • Rule 2 — no new unconfirmed inputs. The replacement may not spend an unconfirmed output that wasn't already an input of something it conflicts with — otherwise a trivial fee bump could drag in an arbitrary new subgraph for free re-validation.
  • Rule 3 — pays more, absolutely. The replacement's fee must be at least the sum of the fees of everything it replaces.
  • Rule 4 — pays for its own bandwidth too. The fee increase over rule 3's sum must itself meet the incremental relay feerate (1 sat/vB) times the replacement's own vsize — otherwise "replace for +1 satoshi, forever" is free spam that forces unbounded re-relay of the same package.
  • Rule 5 — bounded blast radius. No more than 100 existing transactions (conflicts plus their descendants) may be evicted by one replacement.
FULL RBF: THE DEBATE, HONESTLY STATED

Rule 1 was always a courtesy, not a protocol guarantee — nothing in consensus stops a miner from including whichever conflicting transaction it prefers, opt-in flag or not; "full RBF" relay policy has existed unofficially on some nodes for years. Bitcoin Core 24.0 (2022) added an explicit -mempoolfullrbf option; Core 28.0 (2024) made it the default. Reasonable engineers still disagree about what this changed in practice: proponents argue it merely made honest the assumption a sophisticated attacker could already violate; opponents argue it removed a real, if imperfect, signal that services accepting zero-confirmation payments had relied on for low-value, low-risk transactions. Both are defensible — say so rather than picking a winner.

(f) Fee bumping, tool two: Child-Pays-For-Parent

CPFP needs no protocol feature at all — it's a direct consequence of §5's ancestor-feerate scoring. Attach a new transaction that spends an output of the stuck transaction, pay that child a high fee, and the package's combined ancestor feerate can clear the mining threshold even though the stuck parent alone never would. Its hard limitation: you must control a spendable output of the stuck transaction. A payment's recipient can almost always CPFP (they own the output they were paid to); the sender generally cannot unless they happen to have an unspent change output from the same transaction — which is exactly why RBF exists as the sender-side tool and CPFP as the receiver-side tool. They are complements, not substitutes.

(g) Fee estimation and why it always lags

estimatesmartfee(target) buckets recently confirmed transactions by feerate and tracks a decaying moving average of what fraction confirmed within a given number of blocks, at short, medium, and long time horizons. It returns the lowest feerate bucket whose recent success rate clears a threshold for the requested confirmation target. This is necessarily backward-looking — it is a statistical fit to the very recent past. During a rapid demand spike it under-predicts (yesterday's winning feerate is too low for right now); during a rapid drop it over-predicts (users overpay out of caution). RBF is the operational correction for an estimator that structurally cannot see the future.

(h) The fee market of a full block

When mempool backlog exceeds available block space at the current mining rate, transactions compete on feerate alone — the market clears at whatever rate fills the next several blocks. When backlog is below capacity, the effective floor drifts back toward minrelaytxfee (historically often near 1 sat/vB in quiet periods). ARC 09 · TRADEOFFS

Five ways to rank a mempool, compared honestly

APPROACHWHAT IT OPTIMIZESWHAT IT COSTS
FIFO / arrival order trivial to implement no scoring needed ignores fees entirely first-come spam wins forever
Absolute-fee sort simple, matches naive intuition picks large low-feerate txs over small high-feerate ones (§4)
Feerate-only sort correct for independent transactions true value-per-weight breaks on any parent/child dependency — can rank an unminable child above a minable parent
Ancestor-feerate packages (Core today) correct mining order CPFP falls out for free bounded computation via 25/101kvB caps the caps themselves enable pinning still only an approximate knapsack solver
Package relay / v3 (TRUC) evaluates parent+child atomically narrows pinning restricts topology (1 parent, 1 child, tight size caps) still stabilizing across the network as of this writing

Read this as another instance of chapter 8's proof-by-exhaustion pattern: there is no free lunch between "score accurately" and "bound the computation," and every version above trades one against the other in a different place. Bitcoin Core's current design is the least-bad point found so far, not a final answer.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Complexity, bandwidth, and what an attacker actually pays

  • Ancestor/descendant tracking: maintained incrementally (§8a's CTxMemPoolEntry stats), so a single insertion or removal costs time proportional to the size of the affected package — bounded by the 25-tx/101-kvB caps, not by total mempool size.
  • Eviction: each trimming pass is roughly O(k log n) for a mempool of n entries evicting a package of k transactions — the log n from the descendant-score index, the k from deleting the whole package at once.
  • Relay bandwidth: every accepted transaction is announced to roughly 8 default outbound peers (chapter 10) plus however many inbound peers a node accepts — cost scales with peer count × transaction size, which is exactly why the standardness and fee-floor policy layers (§7) exist upstream of relay, not just upstream of mining.
  • Cost to force N evictions: real money. An attacker must genuinely pay a feerate above the current floor for every transaction they flood with — there is no way to force eviction of higher-feerate transactions without economically out-competing them, which is the fee market working as intended, not a vulnerability.
  • Cost to pin a time-sensitive transaction: comparatively cheap relative to the value it can lock up. Attaching one large, adequately-relayable descendant to consume most of a target's remaining descendant-size budget can cost the attacker only that descendant's own modest relay fee, while blocking a counterparty from cheaply attaching a rescuing child — an asymmetry chapter 14 returns to directly.
THE HONEST SECURITY MODEL

Mempool policy protects nodes (memory, CPU, bandwidth) and shapes miner incentives. It provides no protection at all to anyone treating an unconfirmed transaction as final — that guarantee simply does not exist and was never promised by the protocol; "zero-conf" was always a bet on the good behavior or laziness of whoever might double-spend you, priced by how much they'd have to pay to reach a majority of hashrate or relay path that would prefer their replacement.

ARC 11 · REAL-WORLD INCIDENTS

Five events that shaped the policy you'd deploy today

December 2017: the first mainstream "fees are broken" moment

Bitcoin's price run-up drove transaction volume far past what blocks could absorb. Average fees reportedly exceeded $50 at the peak, with mempool backlogs regularly over 100,000 unconfirmed transactions for weeks. Root cause was not a bug — it was the fee market functioning exactly as designed under sustained excess demand — but the user experience (payments stuck for days, wallets with poor or absent fee estimation) accelerated both SegWit adoption (chapter 12, which had activated months earlier but was barely used yet) and serious investment in RBF-aware wallet software.

2015: stress-test floods and the case for mempool policy

Coordinated "stress test" campaigns deliberately flooded the network with low-fee transactions to study — and, depending who you ask, to deliberately argue a political point about — mempool and block-size behavior under load. The episode hardened the case for explicit, tunable mempool policy (size caps, minimum relay fees) rather than the earlier assumption that "any valid transaction should eventually confirm."

Spring 2023: Ordinals and BRC-20 inscriptions

A wave of demand for embedding arbitrary data in transaction witnesses (Ordinals "inscriptions") and a token-like protocol built on top of them (BRC-20) drove backlogs past 400,000 unconfirmed transactions and median fees above $30. It was also a genuine policy stress test in the chapter-8 sense: none of this activity violated any consensus rule, which is precisely why some operators' preference to discourage it via local policy (datacarrier size limits, filtering) sparked a real and still-unresolved argument about how much legitimate authority node policy has over use cases the block size limit was never written to prevent.

April 2024: the halving that fees nearly out-earned

Block 840,000 (20 April 2024) coincided with the launch of the Runes protocol, designed explicitly to be etched at the halving. The resulting rush of etching transactions pushed average fees briefly past $100 per transaction, and that block's total fee revenue reportedly exceeded the newly halved 3.125 BTC subsidy — an early data point for a question every future halving makes more urgent: as the subsidy trends toward zero, does the fee market alone generate enough miner revenue to keep hashrate — and therefore chapter 8's security budget — where it needs to be?

The full-RBF transition (2022–2024)

Covered mechanically in §8e; listed here because it was as much a governance incident as a technical one. Merchants and services built entire zero-confirmation acceptance policies on the assumption that non-signaling transactions were unlikely to be replaced. Formalizing full RBF as Core's default didn't change any consensus rule — it changed a widely (if quietly) relied-upon social convention, and did so through the same rough, public, occasionally acrimonious mailing-list process that resolves most Bitcoin policy disputes.

First, the entry itself — the incrementally-maintained statistics that make ancestor and descendant scoring cheap instead of a from-scratch graph walk on every query:

C++txmempool.h — CTxMemPoolEntry (simplified)
class CTxMemPoolEntry
{
    const CTransactionRef tx;
    const CAmount nFee;               // fee this tx alone pays
    const int64_t nTxWeight;          // BIP141 weight; vsize = ceil(weight / 4)
    const size_t nUsageSize;          // memory footprint -- counted against maxmempool

    // Maintained INCREMENTALLY as parents/children come and go. Recomputing
    // these from a full graph walk on every insert is the O(n^2) blowup
    // Sec.6's chain-length chart quantifies.
    uint64_t nCountWithAncestors;
    CAmount  nModFeesWithAncestors;     // this tx's fee + every unconfirmed ancestor's fee
    int64_t  nSizeWithAncestors;        // -> ancestor feerate: the score addPackageTxs() mines by

    uint64_t nCountWithDescendants;
    CAmount  nModFeesWithDescendants;
    int64_t  nSizeWithDescendants;      // -> descendant feerate: the score TrimToSize() evicts by
};

The mining side — §8b's knapsack heuristic in its real shape:

C++node/miner.cpp — BlockAssembler::addPackageTxs() (simplified)
void BlockAssembler::addPackageTxs(int& nPackagesSelected, int& nDescendantsUpdated)
{
    // mapTx ordered by ancestor_score: front-to-back is DECREASING ancestor
    // feerate. One index, and the "knapsack" is solved by iteration order.
    auto mi = mempool.mapTx.get<ancestor_score>().begin();

    while (mi != mempool.mapTx.get<ancestor_score>().end()) {
        CTxMemPool::txiter iter = mempool.mapTx.project<0>(mi);
        ++mi;
        if (inBlock.count(iter)) continue;
        if (PackageWeight(iter) + nBlockWeight > nBlockMaxWeight) continue;  // skip, keep scanning

        CTxMemPool::setEntries ancestors;
        mempool.CalculateMemPoolAncestors(*iter, ancestors, noLimit);

        // Ancestors ride in on the descendant's ticket -- CPFP with zero
        // special-case code; it falls straight out of this sort key.
        for (auto& anc : SortByAncestorScore(ancestors)) AddToBlock(anc);
        AddToBlock(iter);
        ++nPackagesSelected;
    }
}

The replacement side — BIP125's five rules as five composable checks:

C++policy/rbf.cpp — CheckReplacement() (simplified)
std::optional<std::string> CheckReplacement(const CTxMemPool& pool, const CTransaction& replacement,
                                              CAmount replacementFees, const CTxMemPool::setEntries& conflicts)
{
    // Rule 1 -- some tx being replaced (or one of ITS unconfirmed ancestors)
    // must have opted in with sequence < 0xfffffffe.
    if (!std::any_of(conflicts.begin(), conflicts.end(), SignalsOptInRBF))
        return "txn-mempool-conflict";

    // Rule 2 -- no brand-new unconfirmed parents the conflicts didn't already
    // have -- otherwise a 1-satoshi bump could drag in an arbitrary new
    // unconfirmed subgraph and force it to be re-validated for free.
    if (!HasNoNewUnconfirmed(replacement, pool, conflicts))
        return "replacement-adds-unconfirmed";

    // Rule 3 -- pay at least what's already on the table.
    CAmount nConflictingFees = SumFees(conflicts);
    if (replacementFees < nConflictingFees)
        return "insufficient fee: rule 3";

    // Rule 4 -- AND cover the replacement's own relay bandwidth at the
    // node's incremental rate, or "replace for +1 satoshi" becomes free
    // spam that forces unbounded re-relay of the same package.
    CAmount nDelta = replacementFees - nConflictingFees;
    if (nDelta < incrementalRelayFee.GetFee(GetVirtualTransactionSize(replacement)))
        return "insufficient fee: rule 4";

    // Rule 5 -- cap blast radius: never evict more than 100 transactions
    // (conflicts + everything descending from them) for one replacement.
    if (CountWithDescendants(pool, conflicts) > MAX_REPLACEMENT_CANDIDATES)
        return "too many potential replacements";

    return std::nullopt;   // all five rules satisfied
}

And the eviction side — §8d's dynamic floor in its real shape:

C++txmempool.cpp — CTxMemPool::TrimToSize() (simplified)
void CTxMemPool::TrimToSize(size_t sizelimit)
{
    CFeeRate maxFeeRateRemoved(0);
    while (!mapTx.empty() && DynamicMemoryUsage() > sizelimit) {
        // descendant_score, not ancestor_score: eviction asks the mirror
        // question of mining -- "how little does the network lose by
        // dropping this tx and everything that spends it?"
        auto it = mapTx.get<descendant_score>().begin();

        setEntries stage;
        CalculateDescendants(mapTx.project<0>(it), stage);   // the whole package dies together

        CFeeRate removed(it->GetModFeesWithDescendants(), it->GetSizeWithDescendants());
        maxFeeRateRemoved = std::max(removed, maxFeeRateRemoved);

        RemoveStaged(stage, false, MemPoolRemovalReason::SIZELIMIT);
    }
    // Anyone relaying at or below this rate gets rejected outright for a
    // while -- the dynamic floor Sec.8d calls mempoolminfee.
    if (maxFeeRateRemoved > CFeeRate(0))
        rollingMinimumFeeRate = maxFeeRateRemoved.GetFeePerK() + INCREMENTAL_RELAY_FEE;
}
WHY IT WAS BUILT THIS WAY

1. Two indices, one entry set. Rather than maintaining separate data structures for "what to mine" and "what to evict," both questions are answered by sorting the same underlying records differently — less code, and the two views can never drift out of sync with each other. 2. RBF's rules are pure, composable functions. Each rule takes the proposed replacement and the conflict set and returns pass/fail independently — exactly the shape that makes the simulator in §15 able to show you which specific rule failed, and the shape that makes each rule independently testable and independently arguable on the mailing list. 3. Eviction and mining are deliberately symmetric code. Once you've built one feerate-package index, building its mirror image is nearly free — an example of a codebase reusing a hard-won abstraction instead of inventing a second one.
