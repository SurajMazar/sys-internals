APACHE KAFKA INTERNALS · CHAPTER 08

Offsets &
Delivery Semantics

A Kafka partition is an immutable, shared log — consuming it never deletes anything and never mutates it. So where does "which message have I already handled" live, who writes it durably, and what exactly can go wrong in the few hundred milliseconds between processing a record and recording that you did? This chapter derives the entire at-most-once / at-least-once / exactly-once taxonomy from one fact: the commit and the processing are two separate operations that a crash can always interleave.

ARC 01 · THE PROBLEM

The log doesn't know who has read it

Every subsystem you've studied so far — the log segment, the replication protocol, the ISR — exists to answer one question: how do we durably append records and agree on which ones are committed? None of that machinery has anything to say about consumption. A partition's log has no concept of "delivered", no per-reader cursor, no acknowledgment bit next to each record. A topic with zero consumers and a topic with five independent consumer groups reading it look byte-for-byte identical on disk. That is a deliberate, load-bearing design choice: it's what lets Kafka support unlimited independent readers at the same storage cost as one, and it's what makes replay ("seek back to yesterday and reprocess") a first-class operation rather than a recovery hack.

But someone still has to track position. A offset is just a monotonically increasing integer per partition; a consumer group is the unit that owns a position in each partition it's assigned. That position needs to satisfy requirements that pull in different directions, same shape as chapter 1's constraints on the log itself:

  • Durability — a consumer process restarting, or being replaced by a completely different machine during a rebalance, must resume roughly where it left off. The position cannot live only in that process's RAM.
  • Scale — a mid-size company easily runs thousands of consumer groups against thousands of topic-partitions: millions of (group, topic, partition) → offset mappings, updated continuously, at every commit interval.
  • Low write latency — committing is on or near the hot path of message processing; it cannot cost more than the processing itself.
  • Observability — operators need to read current positions externally (consumer lag) without coordinating with the consumer process.

Notice the position is really three distinct pointers per partition, and this chapter is largely about the gaps between them: the committed offset (durably recorded, survives a restart), the position (the next offset the client will fetch — advances the instant poll() returns records, whether or not they've been processed), and the high watermark (the boundary the broker allows any consumer to read up to at all — chapter 4's replication invariant, extended by the LSO for read_committed readers, chapter 9). Every failure mode in this chapter is a disagreement between two of these three pointers after an untimely crash.

WHY THIS MATTERS FOR THE NEXT SEVEN CHAPTERS

"Exactly-once" is a phrase people use loosely; by the end of this chapter you'll have the vocabulary to be precise about what it actually promises. Chapter 9 builds Kafka's transactional protocol directly on top of the mechanism this chapter describes — sendOffsetsToTransaction() is nothing more than "write an offset commit record and a data record atomically," and you can't appreciate why that's hard until you've seen exactly how offset commits work when they're not atomic with anything.

A COMMON MIX-UP: THIS IS NOT WHAT KIP-500/KRAFT REMOVED

Students who learn "Kafka removed ZooKeeper" (KIP-500, GA in 2.8–3.x, mandatory since 4.0) sometimes assume that's when consumer offsets left ZooKeeper too. It isn't — that happened a decade earlier, in 0.8.2/0.9 (2015). KIP-500 removed ZooKeeper's role as the cluster metadata store (broker registration, partition leadership, ACLs) in favor of the KRaft controller quorum. Consumer offsets had already been fully migrated to the __consumer_offsets topic you're studying in this chapter years before that project began — two separate migrations, a decade apart, solving different scaling problems.

ARC 03 · NAIVE SOLUTION

Attempt #1: turn on auto-commit and stop thinking about it

The default configuration is also the naive solution, which is worth taking seriously precisely because so much production code runs it unmodified. enable.auto.commit=true (the default) with auto.commit.interval.ms=5000 (the default) gives you this loop, verbatim from what a huge fraction of Kafka consumer applications look like:

Javanaive_consumer.java — the strawman, annotated
try (KafkaConsumer<String, Order> consumer = new KafkaConsumer<>(props)) {
    consumer.subscribe(List.of("orders"));

    for (;;) {
        ConsumerRecords<String, Order> batch = consumer.poll(Duration.ofMillis(500));
        /* enable.auto.commit=true, auto.commit.interval.ms=5000 (both defaults):
         * somewhere INSIDE this poll() call, if 5s have elapsed since the
         * last auto-commit, the client silently fires an OffsetCommit for
         * whatever this consumer has already returned to the app via a
         * PREVIOUS poll() — not for the batch you're about to process now. */

        for (ConsumerRecord<String, Order> r : batch) {
            chargeCard(r.value());        /* side effect with real-world consequences */
            writeToLedger(r.value());     /* could throw, could take 200ms, could half-finish */
        }
        /* no commit call here — there's nothing to call. The next poll()
         * decides, on its own schedule, whether enough time has passed. */
    }
}

This is not an unreasonable place to start. It gets the common case completely right: steady, fast processing, no crashes, no rebalances mid-batch — every record gets processed exactly once from the application's point of view, and you wrote zero commit-handling code. It fails, predictably, exactly where every naive solution in this course fails: at the boundary condition nobody tested — the process dying at an arbitrary instruction.

ARC 04 · WHY IT FAILS

Two failure windows, quantified

Auto-commit doesn't fail randomly — it fails in exactly two shapes, and both are a direct consequence of one fact: the commit and the processing are decoupled in time, and a crash can land in the gap. Put numbers on the gap and the risk stops being abstract.

  • Window 1 — the reprocessing window (bounded, "merely" at-least-once). In the standard synchronous loop, auto-commit for batch N only fires once poll() is called again for batch N+1 — which only happens after batch N is fully processed. So the exposure window is: time since the last successful commit check, up to auto.commit.interval.ms (default 5000 ms) plus one batch's processing time. At a throughput of 10,000 records/s with the 5s default, a crash one instant after finishing a batch but before the next poll()'s commit check can force up to ~50,000 already-processed records to be reprocessed after restart. Every downstream side effect (charged cards, sent emails, ledger rows) that isn't idempotent happens twice.
  • Window 2 — the data-loss window (unbounded, the one that should worry you more). Auto-commit commits the position — offsets already returned to the application — not "offsets confirmed processed." If your application hands records to a thread pool and calls poll() again immediately (a common pattern for throughput), the position advances, and can get committed, before those records finish processing at all. A crash now doesn't reprocess anything — the committed offset already points past those records, so a restarted consumer never fetches them again. They are gone as far as this consumer group is concerned, with no exception thrown, no log line, nothing. This is strictly worse than duplication: silent, permanent loss, and its size is bounded only by how far ahead of processing your fetch pipeline is allowed to run.
THE ASYMMETRY THAT MATTERS

Window 1 is annoying but recoverable if your processing is idempotent (chapter 9 shows how to make it so cheaply). Window 2 is not recoverable by anything downstream — the data never reaches a second attempt. This is precisely why every serious Kafka consumer guide tells you: never combine auto-commit with any form of asynchronous or multi-threaded record processing. It isn't a style preference; it's the difference between a duplicate row and a permanently missing one.

So we need to control exactly when a commit happens relative to processing completion, instead of leaving it to a timer that only knows about deliveries. The next section walks the candidates in order, the same way chapter 1 walked event-loop / threads / processes.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Manual commits — sync, async, and the pattern that survives contact with production

Turn off enable.auto.commit and call the commit API yourself, after processing, so the commit can never race ahead of work you haven't finished. Two APIs, and a third combination, walk through the same elimination process as every "better solution" section in this course.

commitSync → commitAsync → the hazard → the patternSTEP-BY-STEP
THE STANDARD PATTERN, IN CODE

What the deck converges on — commitAsync in the steady-state loop for throughput, commitSync once in the shutdown path for a guaranteed final position:

Javathe pattern every serious consumer converges on
try {
    while (running) {
        var batch = consumer.poll(Duration.ofMillis(500));
        process(batch);                    /* fully synchronous — no handoff to a pool */
        consumer.commitAsync();              /* cheap, non-blocking, doesn't stall the poll loop */
    }
} finally {
    try { consumer.commitSync(); }      /* the LAST commit must be durable before we exit */
    finally { consumer.close(); }
}
ARC 06 · WHY THAT STILL COSTS

Manual commits remove one bug class and introduce a subtler one

Be precise about what you bought and what you still owe:

  • commitSync costs latency, linearly. Each call is a network round trip to the group's coordinator broker and blocks until acknowledged (or retried, or a fatal error is raised). Commit every record and your per-partition throughput ceiling becomes 1 / RTT — at a typical 2–5 ms coordinator RTT that's 200–500 commits/sec, nowhere near the tens of thousands of records/sec a partition can otherwise sustain. This is exactly Little's Law again (chapter 1's iterative-server argument, restated): a blocking call on the hot path caps throughput at its own inverse latency.
  • commitAsync removes the block but is fire-and-forget — you get a callback, not a guarantee, and by the time it fires your application may already be several batches further along. If you retry a failed commitAsync naively, you introduce a new bug: responses can arrive out of order. Suppose you commit offset 500, it's slow; you then commit offset 800, it's fast and succeeds first. If your retry logic now resends the (still outstanding, now stale) request for 500 and it eventually succeeds, it overwrites the coordinator's stored position — 800 regresses to 500. Every record between 500 and 800 that was already durably marked processed is now, from the group's perspective, unprocessed again. The fix is not "don't retry" — it's "never let a stale response apply itself over a newer one," which is exactly the sequencing guard the real client implements internally (§13).
  • Neither one buys exactly-once. Ordering the commit strictly after processing gives you at-least-once at best: a crash between "processing finished" and "commit acknowledged" still reprocesses. Ordering the commit strictly before processing gives you at-most-once: a crash between "commit acknowledged" and "processing finished" still loses work. You cannot fix this by choosing a cleverer point in time to commit — the processing and the commit are two independent operations on two independent systems (your side-effect target, and __consumer_offsets), and no ordering of two independent writes is atomic. That requires either idempotency keyed on something stable, or a real cross-system transaction — chapter 9's entire subject.
SO WHAT DO YOU ACTUALLY GET?

Commit-after-process (whichever API) gives at-least-once: no silent loss, bounded duplication on crash recovery. That is the correct, achievable target for the overwhelming majority of pipelines, provided the processing is either naturally idempotent (an upsert by primary key) or made idempotent deliberately (a dedup table keyed on a stable record id). Commit-before-process gives at-most-once, which is the right choice only when a dropped record is cheaper than a duplicated one — metrics counters you're willing to undercount, not orders you're willing to double-charge.

WHY A "COORDINATOR" AT ALL — WHY NOT JUST PRODUCE TO THE TOPIC DIRECTLY?

A consumer could in principle be handed the identity of the broker leading its __consumer_offsets partition and produce to it directly, exactly like a normal producer. Kafka doesn't do this because the coordinator is also the process managing group membership, generation numbers, and rebalances (chapter 7's subject) — and offset commits must be validated against that state: a commit from a consumer that has already been kicked out of the group (stale generation, or it never joined this generation at all) must be rejected, or two overlapping "generations" of the same group could silently commit conflicting positions during a rebalance. Routing commits through the same broker process that owns membership state lets it reject ILLEGAL_GENERATION and UNKNOWN_MEMBER_ID commits with no extra coordination protocol.

ARC 08 · INTERNAL IMPLEMENTATION

What's actually in the record, and how the coordinator survives failover

Three things to nail down precisely: (a) the exact key/value schema written to __consumer_offsets and why compaction is correct for it, (b) the request path from commitSync() to a durable, replicated append, and (c) how a brand-new coordinator broker rebuilds its in-memory offset cache after a failover — by replaying the log, not by asking anyone.

(a) The key/value schema

__consumer_offsets is an internal topic (default offsets.topic.num.partitions=50, offsets.topic.replication.factor=3, cleanup.policy=compact) whose records are ordinary Kafka records with a purpose-built key and value:

  • Key — OffsetKey: a schema version byte, then (group, topic, partition). This triple is the identity being tracked — deliberately not including a consumer/member id, because the position belongs to the group, and group membership churns across rebalances while the position must not.
  • Value — OffsetCommitValue: the committed offset itself, the leaderEpoch of the partition being tracked (KIP-101 / KIP-320), an opaque metadata string the application may attach to its own commit (audit trail, a checkpoint id — anything up to max.metadata.size), and a commitTimestamp used for retention.
  • Key insight: because the key is always (group, topic, partition) and never includes the offset value itself, every new commit for the same group/topic/partition is a new record with the same key — which is precisely what makes cleanup.policy=compact the correct retention policy: compaction naturally converges the log to exactly one live record per (group, topic, partition) — the latest position — no matter how many thousands of commits preceded it. Time-based retention (like a normal data topic) would be wrong here: you don't want yesterday's commits to expire on a schedule, you want all but the latest to disappear, regardless of when they were written.

(b) The commit request, broker-side

Step through what commitSync() actually does once it leaves the client's network buffer.

OffsetCommit: client call → durable, replicated recordSTEP-BY-STEP
COORDINATOR FAILOVER: REBUILDING STATE BY REPLAY, NOT BY ASKING

When the broker leading a __consumer_offsets partition dies or its leadership moves, the new leader has an empty in-memory offsets cache — GroupMetadataManager keeps that cache purely as a materialized view, never as the source of truth. On becoming leader it calls loadGroupsAndOffsets(), which reads its shard of __consumer_offsets from the log's start to its end and replays every record into the cache, keyed the same way compaction keys them — so the result is identical whether the log has one commit per key or ten thousand. This is the same "rebuild from the log" pattern the whole engine relies on: the cache is disposable; the compacted log is not.

(c) Where a group's __consumer_offsets partition comes from

A group is deterministically mapped to one of the 50 partitions by hashing its id — the same Utils.abs(groupId.hashCode) % offsets.topic.num.partitions formula used since the 0.9 rewrite. Drag the partition count and watch example groups redistribute; this is exactly why offsets.topic.num.partitions is a boot-time-only decision in practice — changing it after the fact reshuffles every group's coordinator assignment.

HARDWARE COROLLARY: WHY OFFSET TRAFFIC IS CHEAP DESPITE BEING FREQUENT

An OffsetCommitValue is tens of bytes; even a busy cluster with 10,000 group-partition pairs each committing every second is only a few MB/s of aggregate offset traffic — negligible next to the GB/s a data plane moves. Because the topic is small and almost entirely resident in page cache, coordinator reads on failover (replaying the log) and fetches from consumers checking their own lag are both effectively free of disk seeks. The one place this bites is if offsets.retention.minutes and low commit rates conspire to leave a huge number of stale keys uncompacted between cleaner passes (§10 has the exact math).

ARC 09 · TRADEOFFS

"Where's my place in the queue?" — five different answers

Every messaging system needs a position-tracking mechanism; the spread of designs below reflects a genuinely different modeling choice — a linear cursor into an immutable log versus a mutable per-message delivery state:

Read this as the same proof-by-exhaustion pattern as chapter 1: ack-based systems buy fine-grained, per-message control at the cost of the message's lifecycle being entangled with its delivery state (once acked, replay requires a separate mechanism, if it exists at all); cursor-based systems buy cheap, batched position tracking and trivial replay at the cost of coarser granularity — you can't selectively "unprocess" one record out of a batch. Kafka's bet — a dumb, durable, replayable log plus an external, equally dumb integer cursor — is what makes both infinite retention and time-travel reprocessing natural instead of exceptional.

ARC 10 · PERFORMANCE CHARACTERISTICS

The commit-interval tradeoff, made quantitative

Offset commits are individually cheap and structurally simple — an append to a small, page-cache-resident, compacted log — but the interval you choose still has a real cost curve on both ends:

  • Append cost: O(1) amortized, same as any log append (chapter 3) — sequential write, no seek, batched with whatever else is flowing to that segment.
  • Compaction cost: the LogCleaner (one thread by default — log.cleaner.threads=1) only compacts a partition once its dirty ratio exceeds log.cleaner.min.cleanable.ratio (default 0.5), rate-limited by log.cleaner.io.max.bytes.per.second. A group that commits rarely but the topic overall commits constantly still gets compacted on the aggregate schedule — individual stale keys can sit uncompacted for a while, which is fine because they're tiny and page-cache-resident, not because they're free to keep forever.
  • Network cost is negligible per commit — an OffsetCommitRequest for a handful of partitions is a few hundred bytes — but request rate is not: every commit is a request/response round trip through the coordinator broker's request-handler thread pool (chapter 2's threading model), competing with every other group's commits and every group's heartbeats for the same threads.

GC AND PAGE-CACHE FOOTNOTE

The coordinator's in-memory offsets cache is a plain JVM hashmap keyed by GroupTopicPartition — small even for a large cluster (millions of keys is tens to low-hundreds of MB), so it's rarely a GC pressure point on its own. The bigger GC interaction is indirect: coordinator broker JVMs run the same request-handler and network threads that serve every other partition's produce/fetch traffic, so a long stop-the-world pause on a coordinator broker delays offset commits and heartbeats together — which can trigger spurious rebalances (session.timeout.ms exceeded) at exactly the moment you least want one.

ARC 11 · REAL-WORLD PRODUCTION

Incidents you will eventually meet

Incident 1: the long-weekend offset reset

A staging or low-traffic consumer group goes quiet — a deploy freeze, a holiday, a disabled feature flag — for longer than offsets.retention.minutes. Before Kafka 2.0, the default was 1440 minutes (24 hours), and worse, the expiry timer was keyed purely off each key's commitTimestamp, so even an actively subscribed group whose members simply hadn't committed recently could have its position silently expired and tombstoned out from under it — a widely reported surprise that KIP-211 ("Revise Expiration Semantics of Consumer Group Offsets") fixed by tying expiration to whether the group is actually empty, and KIP-186 raised the default retention to 10080 minutes (7 days) in the same release. Teams still on defaults from before 2.0, or who explicitly shortened offsets.retention.minutes to save disk, get the Monday-morning version of this: the consumer reconnects, OffsetFetch returns nothing, and auto.offset.reset decides the outcome — earliest means hours of full-history reprocessing hit downstream systems at once; latest means everything produced while the group was idle is silently skipped, permanently.

Incident 2: the naive commitAsync retry regression

A team wrapped commitAsync in its own retry-on-failure logic — reasonable instinct, wrong layer. Under load, some commit callbacks failed transiently (a coordinator reconnect during a rolling broker restart); the wrapper resent the offsets it had last attempted, without regard for whether a later, unrelated commit had already succeeded in the meantime. The result matched exactly the mechanism in §6: a stale retry landed after a newer commit and moved the group's recorded position backward by several batches, and the next rebalance handed those partitions to consumers that dutifully reprocessed everything after the regressed offset — a burst of duplicate writes that looked, from the outside, like an unrelated data-quality incident until someone correlated it with commit-response ordering in the client logs. The fix, matching Kafka's own client internals, was to track a monotonically increasing local sequence number for outstanding async commits and discard any response older than the most recent one already applied — never resend a stale offsets map.

Incident 3: auto-commit plus a thread pool, at scale

A high-throughput ingestion service handed each polled batch to a bounded thread pool to parallelize downstream writes, then immediately called poll() again to keep the pipeline full — a defensible throughput optimization. With enable.auto.commit=true left at its default, the position advanced (and got committed) the moment records were handed off, not when the pool finished them. A rolling deploy that killed instances mid-flight lost exactly the records still sitting in a worker's queue at the instant of termination — Window 2 from §4, at production scale, discovered only because a downstream reconciliation job noticed a gap in sequential order ids days later. This is the canonical, and most cited, argument in Kafka's own consumer documentation for disabling auto-commit the moment your processing becomes asynchronous relative to the poll loop.

First, the broker side: turning a validated commit request into records and appending them:

ScalaGroupMetadataManager.scala — storeOffsets(), simplified
def storeOffsets(
    group: GroupMetadata,
    consumerId: String,
    offsetMetadata: Map[TopicPartition, OffsetAndMetadata],
    responseCallback: Map[TopicPartition, Errors] => Unit
): Unit = {
  // One record per partition being committed. The KEY repeats
  // (group, topic, partition) — the VALUE carries the new offset,
  // leaderEpoch, caller metadata, and commit timestamp.
  val records = offsetMetadata.map { case (tp, offsetAndMetadata) =>
    val key = GroupMetadataManager.offsetCommitKey(group.groupId, tp)
    val value = GroupMetadataManager.offsetCommitValue(offsetAndMetadata)
    new SimpleRecord(time.milliseconds(), key, value)
  }

  val offsetTopicPartition = new TopicPartition(
      Topic.GROUP_METADATA_TOPIC_NAME, partitionFor(group.groupId))

  // Durable + replicated: this is the SAME appendRecords() path a
  // regular producer uses, with acks governed by
  // offsets.commit.required.acks (default -1 / all ISR).
  replicaManager.appendRecords(
    timeout = config.offsetCommitTimeoutMs,
    requiredAcks = config.offsetCommitRequiredAcks,
    entriesPerPartition = Map(offsetTopicPartition -> MemoryRecords.withRecords(records)),
    responseCallback = handleOffsetCommitResponse(group, responseCallback)
  )
}

Second, what a fresh coordinator does the instant it becomes leader of a __consumer_offsets partition — the mechanism behind §8(b)'s "rebuild by replay, not by asking":

ScalaGroupMetadataManager.scala — loadGroupsAndOffsets(), simplified
def loadGroupsAndOffsets(topicPartition: TopicPartition, onGroupLoaded: GroupMetadata => Unit): Unit = {
  val log = replicaManager.getLog(topicPartition).get
  var currentOffset = log.logStartOffset
  val loadedOffsets = mutable.Map.empty[GroupTopicPartition, CommitRecordMetadataAndOffset]

  // Read the ENTIRE shard from log-start to log-end. Because the
  // topic is compacted, replaying it in order and always keeping the
  // LAST value seen for a given key reproduces the exact state that
  // compaction itself converges toward — no special "latest wins"
  // logic is needed beyond ordinary sequential replay.
  while (currentOffset < log.logEndOffset) {
    val fetch = log.read(currentOffset, maxLength = config.loadBufferSize)
    for (record <- fetch.records.records.asScala) {
      GroupMetadataManager.readMessageKey(record.key) match {
        case offsetKey: OffsetKey =>
          if (record.hasValue)
            loadedOffsets(offsetKey.key) = CommitRecordMetadataAndOffset(record.offset,
              GroupMetadataManager.readOffsetMessageValue(record.value))
          else
            loadedOffsets.remove(offsetKey.key)   // tombstone: expired or deleted
        case _ => // group metadata records handled separately
      }
      currentOffset = record.offset + 1
    }
  }
  // loadedOffsets now IS the cache — install it and start serving OffsetFetch.
}

Third, the client-side guard that makes commitAsync safe to use in a loop despite out-of-order network completions — the mechanism §6 promised:

JavaConsumerCoordinator.java — the stale-response guard, simplified
private long generation = 0;  // bumped on every new commitAsync() call

public void commitOffsetsAsync(Map<TopicPartition, OffsetAndMetadata> offsets, OffsetCommitCallback cb) {
    final long thisCommitGeneration = ++generation;
    doCommitOffsetsAsync(offsets, (committed, exception) -> {
        if (thisCommitGeneration != generation) {
            // A NEWER commitAsync() call has been issued since this one was
            // sent. This response is stale — applying it now would move the
            // group's known position BACKWARD. Discard, don't retry blindly.
            log.debug("Ignoring stale commit response for generation {}, current is {}",
                      thisCommitGeneration, generation);
            return;
        }
        if (cb != null) cb.onComplete(committed, exception);
    });
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. The value schema is versioned, not the API. Adding leaderEpoch (KIP-320) meant a new OffsetCommitValue schema version, not a new RPC — old consumers keep working against a coordinator that now writes richer values, and a coordinator can still read old-schema records left over from before an upgrade. 2. The coordinator never trusts the client's ordering — the client guards itself. The broker happily accepts a commit for offset 500 even after accepting one for offset 800; nothing server-side rejects "going backward," because sometimes going backward is exactly what you want (a deliberate seek() + manual re-commit for reprocessing). The safety property everyone actually wants — "my own unintentional stale retries shouldn't undo my own progress" — is a client-side sequencing concern, so that's exactly where it's implemented. 3. Replay, never a second source of truth. The in-memory cache is populated by nothing but reading the log; there is no separate "here's the real answer" reconciliation path to keep in sync, which is the same discipline chapter 4 showed for the ISR itself.
