Collections & Error Handling
Basics

Every real program needs two things the last six chapters haven't given you: a place to put an unknown-at-compile-time number of values, and a disciplined way to say "this might not work" without crashing or silently lying about it. This chapter closes the beginner tier by building Vec<T>, String vs &str, HashMap<K,V>, and the Result/? machinery from first principles — with the exact reallocation arithmetic and the exact desugaring the compiler actually runs, not an approximation of it.

ARC 01 · THE PROBLEM

You don't know how much data you'll have, and not everything works

Chapters 3 through 6 gave you fixed-size values: scalars, tuples, arrays whose length is baked into the type ([i32; 5] is a different type from [i32; 6]), structs and enums with a known shape decided at compile time. That is enough to model a single record. It is not enough to write a real program, because two facts about the real world refuse to fit that mold:

  • You rarely know the size in advance. A list of usernames, the lines of a file, the results of a database query — the count is a runtime fact, sometimes decided by a network response or a user's input. A type whose size is part of the type (like [i32; N]) cannot represent "however many there turn out to be."
  • Text is not one thing. Sometimes you own a buffer of characters and are responsible for its memory (you built it, you'll free it). Sometimes you're just looking at characters someone else owns — a slice of a longer string, a literal baked into the compiled binary. Conflating the two, as most languages do, hides a real cost (an allocation) behind what looks like a free operation (a substring).
  • Not every operation succeeds, and pretending otherwise is a lie. A file might not exist. A string might not parse as a number. A key might not be in a map. Every language has to pick an answer to "what happens when this fails" — and the answer shapes how honest your function signatures are allowed to be.

This chapter is really two problems wearing one chapter number, because they compound: the collections you're about to meet — Vec<T> (a growable array), String (an owned, growable, UTF-8 buffer), HashMap<K,V> (an associative array) — are exactly the data structures whose operations can fail in ordinary, expected ways: an index past the end, a key that isn't there, a byte sequence that isn't valid text. You cannot learn collections without learning how Rust represents failure, and you cannot appreciate Result without a concrete case where "it might not work" is the normal case, not the exceptional one. So this chapter builds both together.

WHAT YOU ALREADY HAVE, AND WHAT'S MISSING

From chapter 6 you already know Option<T> (a value that might be absent) and Result<T,E> (an operation that might fail with an error), plus match's exhaustiveness checking. What's missing is everything that produces an Option or a Result in practice — indexing past a Vec<T>'s end, looking up a missing HashMap key, parsing text that isn't a number — and the ergonomic machinery (the ? operator) that keeps propagating those values from turning every function into a pyramid of match arms.

ARC 02 · HISTORICAL CONTEXT

Two lineages meet in one language: growable arrays and typed failure

Neither idea in this chapter is new to Rust. Growable arrays and principled error types both have decades of prior art, and Rust's specific choices — doubling capacity, splitting owned from borrowed text, making "might fail" part of the type — are each a considered pick from a menu other languages had already tried. DEEP CONTEXT · WHY "AMORTIZED DOUBLING" WON THE GROWTH-FACTOR DEBATE

The choice isn't arbitrary. Grow by a fixed amount (say, +8 each time) and total copying work across n pushes becomes quadratic — chapter's §4 will show the arithmetic. Grow by a multiplicative factor (any factor greater than 1) and the total copying work becomes linear — the factor only changes the constant, not the order of growth. The remaining argument is which factor: too small (say 1.1×) reallocates often for modest memory savings; too large (say 4×) wastes memory fast. C++'s libstdc++ and Rust both settled on 2×; some implementations (older glibc-tuned code, and Facebook's folly library) use ~1.5× to keep freed blocks reusable by a future, slightly-smaller allocation — a real, still-debated tradeoff you'll see quantified in §9.

ARC 03 · NAIVE SOLUTION

Attempt #1: grow by exactly what you need, and trust every syscall

Before judging Rust's answer, build the naive one honestly — it's what most self-taught C programmers actually write the first time, and it compiles and runs (until it doesn't).

Cnaive_vec.c — grow by exactly one element per push
typedef struct {
    int    *data;
    size_t  len;
    size_t  cap;
} DynArray;

void da_push(DynArray *a, int value) {
    a->cap += 1;                                    /* grow by ONE, exactly what's needed */
    a->data = realloc(a->data, a->cap * sizeof(int)); /* may return NULL on failure...      */
    a->data[a->len] = value;                         /* ...never checked before this write */
    a->len += 1;
}

This looks efficient — no memory is ever "wasted" on unused capacity, since cap always equals exactly len. And the second naive habit, error signaling by return value, looks equally reasonable at first glance:

Cnaive_parse.c — the classic error-code convention
int parse_port(const char *s) {
    return atoi(s);       /* atoi("0") == 0, and atoi("banana") == 0 too   */
}                          /* — the two cases are indistinguishable here.  */

int main(void) {
    int port = parse_port(getenv("PORT"));  /* getenv() can return NULL!   */
    bind_socket(port);     /* if PORT is unset: undefined behavior above.  */
}                           /* if PORT is "banana": silently binds to 0.   */

Both snippets compile. Both run correctly on the happy path. Section 4 quantifies exactly what each one costs you the moment reality deviates from the happy path — which, at scale, is constantly.

ARC 04 · WHY IT FAILS

One is a complexity bug, the other is a correctness bug — both are real CWE classes

The growth-by-one array is algorithmically bad, not just "unoptimized"

Growing by exactly one element means the i-th push copies all i-1 existing elements into a freshly resized block (real allocators sometimes extend in place, but the worst case — and the case that dominates once the block moves — copies everything). Summed across n pushes, the total copying work is 1 + 2 + 3 + ... + (n-1), which is n(n-1)/2 — quadratic, O(n²), not O(n). At n = 1,000,000 elements that's roughly 500 billion element-copies, not one million. This is not a micro-optimization gap; it is the difference between a program that returns instantly and one that appears to hang.

The unchecked realloc() and the ambiguous atoi() are real CWE classes

  • CWE-252, Unchecked Return Value: realloc() returns NULL when the allocator cannot satisfy the request. naive_vec.c never checks — it writes to a->data[a->len] unconditionally, which is a write through a null (or, worse, a leaked/dangling) pointer the instant an allocation ever fails. This exact class of bug — trusting a fallible C API's return value without inspecting it — has been a standing line item in CWE's "Top 25 Most Dangerous Software Weaknesses" for years.
  • Ambiguous sentinel values: atoi("banana") and atoi("0") both return 0. There is no way, from the return value alone, to know whether parsing succeeded. This exact ambiguity — a valid value and a failure sharing one sentinel — recurs throughout C's standard library (strtol partially fixes it with errno, which almost nobody checks correctly) and is precisely the design flaw a real Result<T,E> makes structurally impossible: success and failure are different variants, not overlapping values of the same type.
THE PATTERN TO NOTICE

Both bugs share one root cause: the type system has no opinion about failure. An int returned by parse_port looks identical whether it's a real port number or a silently-swallowed error. A pointer returned by realloc looks identical whether it points at valid memory or is null. Nothing forces the caller to branch on success vs. failure — so, under time pressure, many callers don't. The fix isn't "be more careful" (every C programmer already knows to check realloc's return value, and bugs like this ship anyway) — it's making the failure case a different, unavoidable type that the compiler will not let you silently discard. That's the architecture §5 builds.

ARC 06 · WHY THAT STILL HAS COSTS

Be honest: none of this is free

Idiomatic Rust collections and error handling are a large improvement over §3's naive code — but "improvement" is not "zero cost," and pretending otherwise would undercut the very habit of precise thinking this course is trying to build.

  • Reallocation is still real work. Doubling fixes the asymptotic cost (§10 proves it's amortized O(1) per push), but the individual push that triggers a reallocation still copies every existing element — for a Vec<T> holding a million large structs, that one push can take measurably longer than its neighbors. Latency-sensitive code (a real-time audio callback, a hot loop with a hard deadline) sometimes pre-reserves with Vec::with_capacity(n) specifically to avoid that unpredictable spike — a technique §8 quantifies.
  • Capacity never shrinks on its own. Pop every element out of a Vec<T> that once held a million items and its capacity is still whatever it grew to — Rust does not guess whether you're about to push again. You must call .shrink_to_fit() explicitly to give memory back, which means "peak size" silently becomes "steady-state memory footprint" unless you remember to ask.
  • String isn't indexable by position, and that surprises beginners. s[0] does not compile for a String (there is no Index<usize> impl for it) precisely because UTF-8 is a variable-width encoding — "the 3rd character" and "byte offset 3" are different questions with different answers whenever the string contains anything outside plain ASCII. Slicing by byte range (&s[0..3]) compiles but panics at runtime if byte 3 lands inside a multi-byte character instead of between two characters.
  • The default hasher is deliberately not the fastest one. HashMap's default hashing algorithm, SipHash-1-3, is a keyed, DoS-resistant hash — §11 shows exactly the attack it defends against — and it is measurably slower than a non-cryptographic hash like FxHash or AHash. Performance-critical code that doesn't take attacker-controlled keys often swaps hashers deliberately, trading away a safety margin it doesn't need.
  • The borrow checker has opinions about collections specifically. Beginners hit this pattern constantly:
rustthis does NOT compile — error[E0502]
let mut v = vec![1, 2, 3];
let first = &v[0];      // immutable borrow of `v` begins here
v.push(4);              // ERROR: cannot borrow `v` as mutable because it is
                         //        also borrowed as immutable
println!("{first}");    // ...the immutable borrow is used here, later

This is not a false positive. push can trigger a reallocation (§5), which frees the old heap block — if that happened while first still pointed into it, first would be a dangling reference the moment you read it, the exact use-after-free chapter 4 built this whole language to prevent. The fix — reorder the code so the borrow ends before the push, or clone the value out first — is usually one line, but it is a real line every beginner has to learn to write, and it is a genuine verbosity cost relative to a language that would just let the bug happen.

Error handling has its own honest costs, covered in depth in chapter 13: every fallible function's return type must mention Result, custom error enums need boilerplate to convert between error types (the From impls ? relies on), and unwrap() — reaching for the unrecoverable panic! path instead of actually handling an error — is a constant, real temptation under deadline pressure that this course will keep calling out.

THE RULE THAT UNIFIES ALL FOUR

Every "owned, growable" type in Rust follows the same shape: a struct holding a raw pointer to a heap allocation, a len, and (for the growable ones) a cap. Vec<T> IS that shape. String is that shape specialized to u8 plus a UTF-8 validity invariant — it is, almost literally, Vec<u8> wearing a promise. Every "borrowed view" type is a fat pointer: a pointer plus a length, no capacity, no ownership, no Drop. Once you see this, you can predict the layout of any new collection type chapters 8–14 introduce before you've read its definition.

ARC 08 · INTERNAL IMPLEMENTATION

Building up real code, and desugaring ? by hand

(a) Watching capacity change, one push at a time

This program compiles and its printed output is exactly what a current stable Rust toolchain prints for a Vec<i32>, under the simplified "first allocation is capacity 1" teaching model this chapter uses throughout (see the callout below for the one real-world wrinkle it simplifies away):

rustcapacity_trace.rs
fn main() {
    let mut v: Vec<i32> = Vec::new();
    println!("new: len={} cap={}", v.len(), v.capacity());   // new: len=0 cap=0

    for i in 0..9 {
        v.push(i);
        println!("push {i}: len={} cap={}", v.len(), v.capacity());
    }
}

// push 3: len=4 cap=4     <- fits, no reallocation
// push 4: len=5 cap=8     <- reallocation: 4 -> 8
// push 5: len=6 cap=8
// push 6: len=7 cap=8

HONESTY CHECKPOINT — THE ONE SIMPLIFICATION

Real libstd has one refinement this chapter's teaching model (and its §15 simulator) skips for clarity: RawVec's actual first-allocation size is computed by a function conceptually named min_non_zero_cap(element_size), which picks 8 for a 1-byte element (like u8, so a fresh String's first allocation is 8 bytes, not 1), 4 for most small element sizes (up to 1024 bytes — so Vec<i32>'s truly-first allocation is capacity 4, not 1), and 1 for large elements. The reason is practical: allocating room for one 4-byte i32 and immediately reallocating to fit a second one wastes an allocation for essentially free memory savings. The doubling rule after that first allocation is exactly what this chapter teaches, with no simplification — this wrinkle only affects where the sequence starts, not how it grows.

(b) String and &str: one function, either input

ruststring_vs_str.rs
fn shout(name: &str) -> String {
    format!("{}!!!", name.to_uppercase())
}

fn main() {
    let owned = String::from("ferris");
    let literal = "crab";                 // type: &'static str — lives in the binary

    println!("{}", shout(&owned));    // &String -> &str via Deref coercion
    println!("{}", shout(literal));       // already &str

    // The reverse direction is NOT automatic and NOT free:
    let promoted: String = literal.to_string();  // allocates a new heap buffer, copies bytes
}

shout takes &str specifically so it can accept either an owned String (borrowed for the duration of the call) or a &'static str literal, without forcing the caller to give up ownership or pay for an allocation just to call a function. Going the other way — from a borrowed view to an owned buffer — is a real, visible operation (.to_string() or .to_owned()), because it genuinely copies bytes onto the heap. Rust never hides that cost behind an implicit conversion.

(c) HashMap's entry API, beyond a single counter

rustentry_api.rs
use std::collections::HashMap;

fn word_counts(text: &str) -> HashMap<&str, i32> {
    let mut counts = HashMap::new();
    for word in text.split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }
    counts
}

fn group_by_first_letter<'a>(words: &[&'a str]) -> HashMap<char, Vec<&'a str>> {
    let mut groups: HashMap<char, Vec<&'a str>> = HashMap::new();
    for &word in words {
        let key = word.chars().next().unwrap();     // panics only on an empty &str
        groups.entry(key).or_insert_with(Vec::new).push(word);
    }
    groups
}

or_insert_with(Vec::new) only calls Vec::new() if the entry is actually vacant — unlike or_insert(Vec::new()), which would construct a (harmless but wasteful) empty Vec on every call whether or not it's needed. This is a genuinely common beginner pitfall: or_insert takes an already-evaluated value; or_insert_with takes a closure evaluated lazily. For expensive defaults the difference matters.

ARC 10 · PERFORMANCE & SAFETY CHARACTERISTICS

Proving "amortized O(1) push" with real arithmetic

"Amortized" is not a hand-wave — it has a specific, checkable proof, using what algorithms courses call the aggregate method. Here it is, for real doubling starting from an empty Vec<T>:

  • Every push writes exactly one new element: over n pushes, that's n element-writes, no matter what. This part is never in question.
  • A reallocation from capacity c to 2c copies exactly c existing elements. Reallocations happen when the capacity is 1, 2, 4, 8, ..., 2^(k-1) — so the total number of elements ever copied across all reallocations up to roughly n pushes is 1 + 2 + 4 + ... + 2^(k-1) = 2^k - 1 < 2n (a geometric series, bounded by roughly twice the final size).
  • Total work for n pushes: n writes + <2n copies = <3n, which is O(n). Divide by n operations: O(1) amortized per push — even though any individual push that triggers a reallocation costs O(n) in that instant.

Drag n below and watch three real strategies diverge on a log-scaled chart: §3's naive grow-by-one (quadratic total copies), real doubling (linear total copies, proven above), and pre-reserving with with_capacity(n) (zero copies, ever). A SAFETY CHARACTERISTIC WORTH NAMING: BOUNDS CHECKS ARE NOT OPTIONAL

Every Vec<T> index (v[i]) is bounds-checked at runtime by default: an out-of-range index panics with a message like index out of bounds: the len is 3 but the index is 5 rather than reading adjacent heap memory the way an unchecked C array access would. That check costs a comparison and a branch per access — real, measurable, and (per chapter 20) sometimes eliminated by the optimizer when it can prove the index is in range (e.g., inside a for i in 0..v.len() loop). It is never eliminated when the compiler can't prove safety — which is the entire point: the cost buys a deterministic panic instead of the undefined behavior a buffer over-read would be in C.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents that map directly onto this chapter's three collections

Incident 1: CVE-2018-1000657 — an out-of-bounds write in VecDeque::reserve()

A capacity/growth bug in Rust's own standard library, in the Vec family: VecDeque's reserve() method had a capacity-calculation flaw that could produce a buffer overflow — a genuine out-of-bounds write, publicly tracked as capable of enabling arbitrary code execution in the worst case. It was fixed in the standard library and is the canonical proof that "growable collection" and "capacity arithmetic" are still a real attack surface even in a memory-safe language — the safety guarantee is only as good as the arithmetic that decides how big to allocate.

Incident 2: CVE-2018-1000810 — integer overflow in str::repeat()

Directly in String's own machinery (recall: String is Vec<u8> underneath): the final buffer's required capacity was computed by multiplying the input length by the repeat count. On sufficiently large inputs that multiplication could integer-overflow, producing a capacity smaller than what would actually be written — a buffer overflow triggered by nothing more exotic than "x".repeat(huge_number). It was patched by checking the multiplication for overflow before allocating. The lesson generalizes past this one function: any capacity computed by multiplying two attacker-influenced numbers needs an explicit overflow check, in Rust exactly as much as in C — the language stops you from reading past a buffer's bounds, but it can't stop you from asking for the wrong-sized buffer in the first place if the size calculation itself is wrong.

Incident 3: CVE-2011-4885 and CVE-2011-4815 — hash-flooding denial of service

In late 2011, security researchers (the Chaos Computer Club) demonstrated that PHP, Ruby's default Hash, and several other languages' hash tables used predictable, unkeyed hash functions — an attacker who could predict hashes could craft form parameters that all collided into the same bucket, degrading a hash table's average O(1) insert into worst-case O(n) per insert, or O(n²) total for n attacker-supplied keys. A single crafted HTTP request could burn minutes of CPU. This is exactly why Rust's HashMap does not use the fastest available hash function by default: SipHash-1-3 is a keyed pseudorandom function, seeded with a random key generated fresh for each new HashMap, specifically so an attacker who controls the keys you insert (form field names, JSON object keys, HTTP headers) cannot predict which buckets they'll collide into. The performance you give up relative to a non-cryptographic hash (§9) is the price of a mitigation an entire generation of web-facing languages had to retrofit after the fact.

First, the growth decision itself — the function this entire chapter has been describing in prose:

rustlibrary/alloc/src/raw_vec.rs — RawVec::grow_amortized(), simplified
impl<T> RawVec<T> {
    fn grow_amortized(&mut self, len: usize, additional: usize) {
        let required_cap = len.checked_add(additional).expect("capacity overflow");

        // Doubling, with a floor so we don't reallocate for every tiny push
        // on very small vecs (this is the min_non_zero_cap wrinkle from §8).
        let new_cap = std::cmp::max(self.cap * 2, required_cap);
        let new_cap = std::cmp::max(new_cap, Self::min_non_zero_cap(size_of::<T>()));

        let new_layout = Layout::array::<T>(new_cap).expect("layout overflow");
        let new_ptr = if self.cap == 0 {
            alloc::alloc(new_layout)                          // first allocation
        } else {
            let old_layout = Layout::array::<T>(self.cap).unwrap();
            alloc::realloc(self.ptr.as_ptr().cast(), old_layout, new_layout.size())
        };
        // (real code: check new_ptr for null, handle_alloc_error() on failure)

        self.ptr = NonNull::new(new_ptr).unwrap().cast();
        self.cap = new_cap;
    }
}

Then Vec::push(), which asks for growth only when it's actually needed:

rustlibrary/alloc/src/vec/mod.rs — Vec::push(), simplified
impl<T> Vec<T> {
    pub fn push(&mut self, value: T) {
        if self.len == self.buf.capacity() {
            self.buf.grow_amortized(self.len, 1);   // len == cap: must grow first
        }
        unsafe {
            let end = self.as_mut_ptr().add(self.len);
            std::ptr::write(end, value);             // write into now-guaranteed-spare slot
        }
        self.len += 1;
    }
}

String is barely its own type — it is a thin, UTF-8-guaranteeing wrapper:

pub struct String {

impl String {
    pub fn push_str(&mut self, s: &str) {
        self.vec.extend_from_slice(s.as_bytes());   // reuses Vec's own growth logic
    }
    pub fn as_str(&self) -> &str {
        unsafe { std::str::from_utf8_unchecked(&self.vec) }  // safe: invariant upheld by every public method
    }
}

And HashMap's entry API, shaped from the real public interface:

rustlibrary/std/src/collections/hash/map.rs — Entry, simplified
pub enum Entry<'a, K, V> {
    Occupied(OccupiedEntry<'a, K, V>),
    Vacant(VacantEntry<'a, K, V>),
}

impl<'a, K, V> Entry<'a, K, V> {
    pub fn or_insert(self, default: V) -> &'a mut V {
        match self {
            Entry::Occupied(e) => e.into_mut(),
            Entry::Vacant(e) => e.insert(default),
        }
    }
}
A REAL FACT WORTH KNOWING

Since Rust 1.36 (2019), std::collections::HashMap's actual table implementation is not hand-rolled in libstd at all — it's the external hashbrown crate (a Rust port of Google's SwissTable design), vendored into the standard library. HashMap in std is a thin wrapper adding the default SipHash hasher and the stable public API on top. This is a genuine "the ecosystem feeds back into the language" story chapter 11 (modules & crates) will revisit.
