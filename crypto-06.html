APPLIED CRYPTOGRAPHY · CHAPTER 06

MACs & the
Authentication Problem

Chapter 5 gave you three ways to turn a block cipher into something that hides a message. None of them stop an attacker from changing it. This chapter derives, from first principles, why confidentiality and authenticity are different properties that must be bought separately; why the obvious way to build a keyed checksum out of a hash function — H(secret || message) — is catastrophically broken for every hash in the MD5/SHA-1/SHA-256 family; and how HMAC's nested construction survives that exact break. You will implement a real Merkle–Damgård hash in JavaScript, forge a genuine length-extension attack against it, and then watch the identical attack fail against HMAC built on the same broken hash.

ARC 01 · THE PROBLEM

Secrecy is not honesty

Encryption answers one question: can an eavesdropper read this? It does not answer a completely different question that matters just as much: can anyone tamper with this without me noticing? Every mode of operation from chapter 5 — ECB, CBC, CTR — was built and evaluated purely on the first question. Run any of them past their design goal and you find they answer the second question with an unqualified "yes, freely, and I won't even tell you."

Take CTR mode, which chapter 5 praised for turning a block cipher into a fast, parallelizable stream cipher: ciphertext = plaintext XOR Ek(nonce||counter). An attacker who does not know the key can still flip any bit of the ciphertext and know exactly what happens on decryption: XOR is its own inverse, so flipping ciphertext bit i flips plaintext bit i, silently, with no error, no exception, no garbled block — because there is no check for tampering anywhere in the scheme. If the plaintext is amount=00100 and the attacker knows (or guesses) the byte offset of the digits, they can flip ciphertext bits to turn it into amount=90100 without ever learning the key or the original amount. CBC mode is only marginally better: flipping a ciphertext block scrambles the next plaintext block unpredictably but — because of how CBC chaining XORs the previous ciphertext block into the next plaintext block — lets an attacker make controlled, predictable changes to one specific block of the following plaintext by XORing a chosen difference into the preceding ciphertext block. Chapter 10 turns this exact malleability into a full byte-by-byte decryption oracle; for now, the point is narrower and more urgent: a cipher that hides data perfectly can still be undetectably rewritten.

What's missing is a second, independent cryptographic primitive whose only job is integrity and authenticity: given a message and a shared secret, produce a short tag such that anyone holding the secret can verify the tag, and anyone without the secret cannot produce a tag that verifies for any message they didn't get tagged through the legitimate channel — including messages built by tweaking one that was. This primitive is a Message Authentication Code (MAC), and it is not optional plumbing — TLS 1.2 cipher suites, JWT's HMAC-signed tokens, AWS's request-signing scheme, and essentially every authenticated API on the internet are built on getting this one primitive right.

WHY THIS CHAPTER SITS WHERE IT DOES

Chapters 1-5 built confidentiality tools. Chapters 6-7 build integrity tools. Chapter 7 fuses the two into AEAD (GCM, ChaCha20-Poly1305), which is what you should reach for in new designs. You need this chapter first because AEAD's authentication half is, structurally, still a MAC — GCM's GHASH and Poly1305 are both keyed MACs wearing different mathematics than HMAC, and the failure modes you're about to internalize (guessable internal state, unsafe composition, message-length ambiguity) recur there almost unchanged.

ARC 02 · HISTORICAL CONTEXT

From "hash it with a secret" to a proven construction

The hash functions this chapter breaks were not designed to be broken this way — length extension is an emergent property of a specific, once-universal design pattern for building hash functions, discovered and exploited only after the pattern had already shipped inside a decade of production systems. Walk the timeline; each entry is a link in the same causal chain.

DEEP CONTEXT · WHY EVERYONE CONVERGED ON THE SAME SHAPE

Merkle and Damgård's 1989 insight was a genuine engineering breakthrough: if you have a fixed-size compression function that is collision-resistant, you can chain it over arbitrarily long input and the resulting hash inherits collision resistance — a clean, provable reduction from "build one small function" to "hash anything." MD4, MD5, SHA-0/1, and SHA-2 all took this deal. Nobody in 1989-2001 asked "does resistance to collisions also imply resistance to state-recovery-from-output?" — a different, unrelated question the Merkle–Damgård proof says nothing about, and the answer, as you'll derive in §4, is no.

ARC 03 · NAIVE SOLUTION

Attempt #1: just hash the secret with the message

Derive it the way a competent engineer without cryptanalysis training would in 2005. You have a fast, free, standard hash function (MD5 or SHA-1, both ubiquitous at the time) and a shared secret. The obvious construction: glue the secret onto the front of the message and hash the result. Verification just repeats the computation.

pseudocodenaive_sign.* — the strawman, annotated
function sign(secret, message) {
    // "obviously" secure: without `secret`, you can't reproduce the hash
    return SHA256(secret + message);        /* string concatenation, then hash */
}

function verify(secret, message, tag) {
    return SHA256(secret + message) === tag;   /* constant-time compare, ideally */
}

// server-side usage, shaped exactly like a 2009-era REST API:
const req = "GET /photos?user_id=1001&api_key=pub_abc123";
const sig = sign(SERVER_SECRET, req);        /* client includes &sig=... on every call */

This is not a strawman built to be knocked down cheaply — it is exactly what a large number of real API providers shipped in production, because the reasoning is intuitively airtight: SHA-256 is a one-way function; without the secret prefix, you cannot invert it to find one that produces a matching tag. That reasoning is correct as far as it goes. It just answers the wrong question. The attacker in §4 never inverts anything.

A SUBTLER VARIANT, SAME BUG

Some implementations put the secret in the middle, or hash secret + separator + message, or HTTP-signature schemes that concatenate several fields with & before hashing. None of these cosmetic changes matter to the attack in §4 — what matters is only this: is the secret a prefix of the hashed bytes, hashed with a Merkle–Damgård hash, with the raw hash output used directly as the tag? If yes, it's forgeable, regardless of which specific hash or field ordering you picked.

ARC 04 · WHY IT FAILS

The length-extension attack, derived from the padding up

To see the break you have to look at what a Merkle–Damgård hash actually computes, not just its input/output contract. Internally, every hash in this family maintains a fixed-size state (128 bits for MD5, 160 for SHA-1, 256 for SHA-256) and repeatedly runs a compression function state ← C(state, block) over successive fixed-size blocks of the padded message. The very last thing the algorithm does is output the final state, verbatim, as the digest. There is no additional mixing step, no truncation, no secret finalization constant folded in. The digest is the internal state.

That single fact is the entire vulnerability. If the digest is the state, then anyone who has the digest has everything the compression function needs to keep going — they can resume hashing exactly where the original computation left off, appending new blocks, with no knowledge of anything that produced that state. The only two things standing between "attacker has a digest" and "attacker can forge an extension" are (1) knowing — or correctly guessing — how many bytes were absorbed to reach that state, so they can reconstruct the invisible padding bytes that were appended after the original message, and (2) the deterministic padding scheme itself, which is public by design (it is part of the standard, not the secret).

The forgery, step by step

Let secret be unknown, message and tag = H(secret||message) be observed by the attacker (both travel on the wire in the naive API from §3). To forge a valid tag for message || extra for attacker-chosen extra:

  • 1. Decode tag back into the hash's internal state words — trivial, it's just hex.
  • 2. Guess len(secret) (often a small, guessable, or brute-forceable range — see the simulator in §15 for exactly how forgiving this guess needs to be).
  • 3. Compute glue = pad(len(secret) + len(message)) — the exact padding bytes the original hash computation would have appended. This is a pure function of a length, requiring zero knowledge of the secret's actual bytes.
  • 4. Resume the compression function from the decoded state, feeding it extra followed by a fresh padding block computed for the new total length.
  • 5. Submit message || glue || extra with the freshly computed tag. A verifier who recomputes H(secret || message || glue || extra) from scratch will process the exact same sequence of blocks the attacker did from the point the state was captured onward — because Merkle–Damgård is entirely deterministic and block-local — and will therefore arrive at the identical digest. The forged tag verifies.
THE NUMBERS

Forging a length-extended MAC costs the attacker one hash evaluation over the length of `extra` — typically microseconds. Compare that to the security level the tag's bit-length advertises: a 256-bit SHA-256 tag "should" mean an attacker needs on the order of 2256 guesses to forge anything, or 2128 to find a collision. The naive prefix-MAC construction delivers zero bits of the security its digest size implies against this specific, practical, first-query attack — the entire security margin evaporates because the construction, not the hash, is broken. This is precisely why "just use a bigger/newer hash" does not fix it: SHA-256(secret||message) is exactly as forgeable as MD5(secret||message), because both are Merkle–Damgård hashes whose digest exposes the full internal state. §11 shows this exact bug hit a major production API in 2009.

ARC 05 · BETTER SOLUTIONS, EXAMINED

From prefix-MAC to HMACSTEP-BY-STEP
WHY THE PROOF MATTERS, NOT JUST THE SHAPE

Bellare, Canetti, and Krawczyk didn't just propose nesting hash calls — they proved (CRYPTO '96) that HMAC is a secure MAC (specifically, a pseudorandom function) as long as the underlying compression function has a much weaker property than full collision resistance. This is why HMAC-MD5 and HMAC-SHA1 remained considered acceptable for MAC purposes (RFC 6151, 2011) for years after MD5 and SHA-1 were broken as general-purpose collision-resistant hashes for signatures — the specific weaknesses that broke MD5/SHA-1 signatures did not happen to break the weaker property HMAC's proof actually relies on. That said, both are deprecated in current guidance in favor of HMAC-SHA256+ — belt and suspenders, not because HMAC-MD5 has a known practical forgery.

ARC 06 · WHY THAT STILL HURTS

HMAC's bill, and a second construction that fails differently

HMAC is the right default, but it is not free, and it is not the only MAC construction in production. Two things worth internalizing before you treat "use HMAC" as the whole story:

  • HMAC costs two compression passes over the key material. Every call runs the full hash machinery twice — once over ipad_key||message, once over opad_key||inner_digest. For a one-block message this roughly doubles the work versus a single hash call. In practice this is negligible next to network and business-logic latency, but it is measurable at the throughput ceiling of a busy authentication server — §10 quantifies it.
  • Key setup has its own subtlety. A key longer than the hash's block size (64 bytes for MD5/SHA-1/SHA-256) must itself be hashed down first (RFC 2104 §2); a key shorter than the block size is zero-padded. Getting this wrong — e.g. never hashing down an oversized key — silently changes which bytes get XORed with ipad/opad and produces a MAC that is internally consistent but non-interoperable with a correct implementation, a real and annoying class of integration bug.

CBC-MAC: a completely different construction, with its own length-extension cousin

Not every MAC is hash-based. CBC-MAC builds a MAC directly from a block cipher: encrypt the message under CBC chaining with a zero IV, and use only the last ciphertext block as the tag. It is fast, needs no separate hash function, and is provably secure — for fixed-length messages only. The moment you allow variable-length messages under the same key without an additional fix (prepending the length, or the CMAC/OMAC final-block tweak of NIST SP 800-38B), it develops an extension-forgery weakness structurally similar to §4's, derived from the same root cause: CBC-MAC's raw final-block output is, again, resumable state with no finalization step protecting it.

THE LESSON THAT GENERALIZES

Two structurally different MAC families — Merkle–Damgård hash chaining and CBC block-cipher chaining — both fail the same way for the same underlying reason: whenever a MAC's tag is exactly the raw, un-finalized internal chaining state, and the construction allows variable-length or continued input under that state, an attacker who observes one tag can compute the state transition for more input without the key. HMAC and CMAC both fix this — HMAC by wrapping the raw state in a second keyed hash call before exposing it, CMAC by XORing a derived subkey into the final block so the last transformation depends on message length in a way that can't be replayed. Different mechanisms, same principle: never expose raw, resumable state as your final answer.

WHY TWO DIFFERENT CONSTANTS, NOT THE SAME KEY TWICE

ipad (repeated 0x36) and opad (repeated 0x5c) exist so that ipad_key and opad_key are two computationally unrelated-looking values derived from the same key — they differ in every bit position where 0x36 and 0x5c differ. This decorrelation is load-bearing for the security proof: it ensures that learning the inner hash's behavior under ipad_key tells an attacker nothing directly usable about the outer computation under opad_key. A naive H(K||H(K||m)) — same key, no decorrelation — was specifically not what Bellare-Canetti-Krawczyk proved secure, and later analysis (Preneel-van Oorschot's early 1990s work on hash-based MACs) showed such undecorrelated double-hashing schemes could leak more than intended against certain compression functions.

TOY, NOT PRODUCTION

This chapter's hash has a deliberately weak round function and a 128-bit state chosen for pedagogical clarity and to keep every step visible on one screen — it is not vetted, not constant-time, and should never protect anything. Real SHA-256 uses eight 32-bit state words, 64 rounds per block with a message schedule that mixes all 16 input words together (via σ0/σ1 functions) rather than injecting them one at a time, and years of public cryptanalysis. What's real here — and this is the entire pedagogical point — is the architecture: fixed-size state, block-by-block compression, Davies–Meyer feed-forward, and length-based padding. That architecture, not the specific round function, is what length-extension attacks the family.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

What HMAC's extra hash call actually costs, and what tag length actually buys

HMAC's fixed overhead — one extra compression call for the outer hash, plus one extra block absorbed for the opad_key — matters most on short messages and disappears as messages grow, because the double-hash overhead is constant while the single-hash cost of the message body is linear in its size. Tag length is a separate, equally concrete knob. A MAC's brute-force forgery resistance is governed by its output bit length, not the internal state size of whatever built it: with an n-bit tag, blind guessing succeeds with probability q/2n after q attempts. A HISTORICAL DATA POINT: 32-BIT TAGS

TKIP's Michael MIC (§11) uses a 64-bit tag but with a design so weak its effective forgery resistance was far below 264, which is why 802.11i's task group bolted on an out-of-band countermeasure: two MIC failures within 60 seconds triggers a forced re-key and a 60-second connection blackout, compensating in the protocol for what the primitive couldn't guarantee on its own. Compare that operational patch to HMAC-SHA256's situation: at a full 256-bit tag, the birthday-bound-style forgery cost is so far beyond feasible (2128+ operations even under generous cryptanalytic assumptions) that no compensating control is needed — the primitive's own math carries the whole guarantee.

ARC 11 · REAL-WORLD INCIDENTS

This is not a textbook attack — it shipped

Incident 1: Flickr's API signature forgery (2009)

Thai Duong and Juliano Rizzo publicly documented that Flickr's REST API computed request signatures as MD5(secret_key + sorted_parameter_string) — a textbook secret-prefix MAC. Because Flickr's API parameters were visible on the wire (or easily guessed for a given call shape) and MD5 produces exactly the raw 128-bit Merkle–Damgård state as its digest, an attacker who observed one valid (request, signature) pair could apply the exact §4 construction to append arbitrary extra parameters — for example forging a request that changed user_id or added privileged flags — producing a signature the server would accept, without ever learning secret_key. The fix Flickr and the wider industry converged on was exactly this chapter's arc: replace the ad hoc keyed hash with HMAC.

Incident 2: TKIP's Michael MIC (2004 design, 2008-2009 exploited)

When 802.11i needed a message integrity check that could run on the same underage hardware as the WEP-era chips it was patching, Niels Ferguson designed Michael: a fast, 64-bit-tag MAC deliberately weaker than a cryptographically strong construction because the target hardware couldn't afford anything stronger. Ferguson himself flagged the weakness at design time; the working group's compensating control was operational, not cryptographic — two MIC failures within 60 seconds forces a global re-key and a 60-second connection blackout. In November 2008, Beck and Tews published a practical attack combining a ChopChop-style keystream-recovery technique with Michael's algebraic weakness to forge and inject a handful of packets per session; in 2009, Ohigashi-Morii and then Halvorsen et al. extended it to full arbitrary packet injection and, ultimately, complete keystream recovery for practical packet sizes. The root cause is a rolled-your-own MAC shipped with known, accepted weakness as a hardware-constrained tradeoff — the compensating control bought a few years, not indefinite safety.

Pattern, not incident: the class-wide exposure

Flickr was not an isolated bug. Because HMAC only became a widely-taught default relatively late — RFC 2104 is from 1997, but broad framework-level adoption (as the automatic choice a web framework's session-signing or API-key-signing helper reaches for) took another decade to become universal — the 2000s web ecosystem is littered with home-grown hash(secret+data) signing schemes in internal tools, cookie-signing code, and bespoke API authentication layers that were never audited against this exact attack, precisely because it requires knowing to look for it. The generalizable lesson for a Staff engineer reviewing a design doc today: any time you see "we hash the secret with the payload," ask specifically whether it's HMAC — the answer is frequently no, and the gap is not academic.

First, the shape real MD-family padding takes at finalization — this is the code whose logic mdPadding() reproduces:

Cmd5_dgst.c — MD5_Final(), the parts that matter
int MD5_Final(unsigned char *md, MD5_CTX *c)
{
    unsigned char *p = (unsigned char *)c->data;
    size_t n = c->num;

    p[n] = 0x80;              /* the single one-bit-then-zeros marker byte */
    n++;
    if (n > (MD5_CBLOCK - 8)) {
        memset(p + n, 0, MD5_CBLOCK - n);
        md5_block_data_order(c, p, 1);   /* not enough room for the length — flush an extra block */
        n = 0;
    }
    memset(p + n, 0, MD5_CBLOCK - 8 - n);

    /* c->Nl / c->Nh: the running 64-bit bit-count, written little-endian for MD5
     * (SHA-256 uses big-endian here — same idea, opposite byte order) */
    p += MD5_CBLOCK - 8;
    HOST_l2c(c->Nl, p);
    HOST_l2c(c->Nh, p);

    p -= MD5_CBLOCK;
    md5_block_data_order(c, p, 1);   /* final compression call */
    c->num = 0;

    HOST_l2c(c->A, md); HOST_l2c(c->B, md);   /* digest = raw state, verbatim — the entire bug */
    HOST_l2c(c->C, md); HOST_l2c(c->D, md);
    return 1;
}

Second, HMAC's key setup — precomputed once so a long-lived key can sign many messages without re-deriving ipad_key/opad_key every call:

Chmac.c — HMAC_Init_ex(), the ipad/opad setup
int HMAC_Init_ex(HMAC_CTX *ctx, const void *key, int len,
                  const EVP_MD *md, ENGINE *impl)
{
    if (key != NULL) {
        size_t i, j, reset = 0;
        unsigned char pad[HMAC_MAX_MD_CBLOCK];

        if (len > (int)EVP_MD_block_size(md)) {
            /* RFC 2104 §2: oversized keys get hashed down to digest size first */
            EVP_DigestInit_ex(ctx->md_ctx, md, impl);
            EVP_DigestUpdate(ctx->md_ctx, key, len);
            EVP_DigestFinal_ex(ctx->md_ctx, ctx->key, &ctx->key_length);
        } else {
            memcpy(ctx->key, key, len);
            ctx->key_length = len;
        }
        if (ctx->key_length != HMAC_MAX_MD_CBLOCK)
            memset(&ctx->key[ctx->key_length], 0,
                   HMAC_MAX_MD_CBLOCK - ctx->key_length);   /* zero-pad to block size */

        for (i = 0; i < HMAC_MAX_MD_CBLOCK; i++)
            pad[i] = 0x36 ^ ctx->key[i];              /* ipad — precompute once */
        EVP_DigestInit_ex(ctx->i_ctx, md, impl);
        EVP_DigestUpdate(ctx->i_ctx, pad, EVP_MD_block_size(md));

        for (i = 0; i < HMAC_MAX_MD_CBLOCK; i++)
            pad[i] = 0x5c ^ ctx->key[i];              /* opad — precompute once */
        EVP_DigestInit_ex(ctx->o_ctx, md, impl);
        EVP_DigestUpdate(ctx->o_ctx, pad, EVP_MD_block_size(md));
    }
    memcpy(ctx->md_ctx, ctx->i_ctx, sizeof(*ctx->md_ctx)); /* per-message: clone i_ctx, absorb message, later clone o_ctx */
    return 1;
}

Third, this chapter's own compression step — the exact code the deck in §8(a) animates, annotated for the one property that matters most:

JavaScriptcrypto-06.html — compressBlock(), the Davies–Meyer feed-forward
function compressBlock(state, block) {      // block: 16 uint32 words, big-endian
  let [a, b, c, d] = state;
  for (let i = 0; i < 16; i++) {
    const w = block[i];
    const f = ((b & c) ^ (~b & d)) >>> 0;         // MD4/MD5-style choice function
    const t = (a + f + w + TOY_K[i]) >>> 0;
    a = d; d = c; c = b;
    b = (rotl(t, [7,12,17,22][i % 4]) + b) >>> 0;
  }
  // feed-forward: ADD the pre-round state back in — this is what makes the
  // returned state fully resumable, and therefore what length extension exploits.
  return [ (state[0]+a)>>>0, (state[1]+b)>>>0, (state[2]+c)>>>0, (state[3]+d)>>>0 ];
}
WHY IT WAS BUILT THIS WAY — THE DECISION TO STEAL

Davies–Meyer feed-forward exists to make the compression function one-way even if the underlying block-cipher-like round were invertible — without it, knowing the output state and the block would let you trivially recover the input state, breaking preimage resistance outright. It is a genuinely good design choice for the property it targets. The length-extension weakness is not a flaw in Davies–Meyer itself; it's a consequence of a completely separate decision — outputting the raw state as the digest with no further keyed or truncating finalization step. HMAC's contribution is not "avoid Davies–Meyer," it's "add a finalization the attacker can't replay." That's a subtle but interview-worthy distinction: the bug is in what you expose, not in the compression function's internal design.
