STEP 01 · SETUP

A real cluster on your laptop, not a simulator

Every experiment in this lab runs against an actual control plane and actual kubelets — just packed onto one machine. You need Docker Desktop (or Docker Engine on Linux) with at least 4 CPUs and 6 GB of RAM allocated, and about 15 minutes for the whole setup.

Install kubectl

kubectl talks to the API server over HTTPS; it never talks to etcd, the scheduler, or a kubelet directly. Install whichever matches your OS.

bashmacOS
brew install kubectl
kubectl version --client
bashLinux
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl
sudo mv kubectl /usr/local/bin/kubectl
kubectl version --client
powershellWindows
choco install kubernetes-cli
kubectl version --client

Primary path: kind (Kubernetes-in-Docker)

kind runs each cluster node as a Docker container with kubelet and containerd inside it — no VM, no hypervisor. That makes it fast to create, fast to destroy, and easy to build multi-node topologies for the scheduling and node-failure experiments later in this lab. It is also what much of the Kubernetes project's own CI runs on.

bashmacOS / Linux
brew install kind
# or: curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.23.0/kind-linux-amd64 && chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind
kind version

A single-node kind cluster is created with one command. For this lab you want three nodes — one control plane, two workers — because several experiments (scheduling failures, draining, disk pressure) only mean something once there is more than one place a Pod could go.

yamlkind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: lab
nodes:
- role: control-plane
- role: worker
- role: worker
bash
kind create cluster --name lab --config kind-config.yaml
kubectl cluster-info --context kind-lab
kubectl get nodes -o wide
EXPECTED — one control plane, two workers, all Ready
NAME                 STATUS   ROLES           AGE   VERSION
lab-control-plane    Ready    control-plane   64s   v1.30.0
lab-worker           Ready    <none>          41s   v1.30.0
lab-worker2          Ready    <none>          41s   v1.30.0

kind automatically merges a context named kind-lab into ~/.kube/config and switches to it. Confirm with kubectl config current-context — this matters once you also have minikube or a real cluster's context sitting in the same file.

Alternative: minikube

minikube runs each node as a VM (VirtualBox, HyperKit, QEMU) or, on the docker driver, as a container much like kind — but it layers a much larger addon ecosystem on top: a built-in dashboard, an ingress controller, a metrics-server, and a local registry, all one command away. It is slower to start and slower to tear down than kind, which is why this lab defaults to kind, but it is the better choice if you want a persistent "local dev cluster" rather than a disposable lab environment.

bash
brew install minikube
minikube start --driver=docker --nodes=3
minikube status
kubectl config use-context minikube
minikube dashboard          # opens a full web UI — kind has no equivalent
minikube addons list
minikube addons enable metrics-server

Teardown

bash
kind delete cluster --name lab
# minikube equivalent: minikube delete

Several experiments in this lab deliberately damage the cluster — a control-plane container killed, a node's disk filled, a broken admission webhook installed. Recreating from scratch takes under a minute; use it freely rather than fighting a broken state.

Troubleshooting

SYMPTOMCAUSE & FIX
kind cluster can't reach the internet (image pulls or DNS fail inside Pods) containerd inside the kind node inherits Docker's own DNS resolution, which corporate VPNs and proxies frequently break with split-tunnel routing. Check docker exec lab-control-plane cat /etc/resolv.conf — if it points at an address unreachable from inside the container, restart Docker Desktop after disabling the VPN, or configure kind's containerdConfigPatches to point at a reachable resolver.
Unable to connect to the server Your active kubectl context isn't kind-lab. Run kubectl config current-context; if it shows minikube or something else, switch with kubectl config use-context kind-lab. This is the single most common error once you have more than one local cluster installed.
Docker Desktop resource limits too low for a 3-node kind cluster Each kind node is a full containerd+kubelet stack; three of them plus the control plane's static Pods (API server, scheduler, controller-manager, etcd) need roughly 4 CPUs and 6 GB of RAM to stay responsive. Raise Docker Desktop → Settings → Resources, or drop to a single-node cluster (remove the two worker entries from kind-config.yaml) if your machine can't spare it — a handful of experiments that need a second node won't work, but most of the lab will.
kind create cluster hangs on "Starting control-plane" Usually a stale kind network left over from a previous crashed cluster. Run docker network prune and docker ps -a | grep lab to check for orphaned containers, remove them, and retry.
Port already allocated (minikube tunnel / kind extraPortMappings) Change the host-side port only in your kind config's extraPortMappings or minikube's --apiserver-port. The in-cluster port stays as-is.
STEP 02 · ORIENTATION

Ten minutes with the six commands you'll use constantly

Everything below assumes the 3-node kind-lab cluster from setup. Run these once, in order, before touching the experiments — several of them build on state this leaves behind.

1 · Create something — the imperative way, then the real way

kubectl run creates a single bare Pod; it's useful for quick throwaway tests but nothing else manages the Pod once it's up. kubectl create deployment is what you actually want for anything long-lived — it creates a Deployment, which creates a ReplicaSet, which creates the Pods.

bash
kubectl run scratch --image=busybox:1.36 --restart=Never -- sleep 3600
kubectl create deployment web --image=nginx:alpine --replicas=3

kubectl get pods -o wide

bash

Keep kubectl logs <pod> -p in your muscle memory for later — it reads the previous container instance's logs, which is the only way to see why a container crashed once it has already restarted and overwritten current stdout.

STEP 04 · PRODUCTION BEST PRACTICES

A config cookbook where every number has a reason

Resource requests and limits

SETTINGGUIDANCEWHY
CPU requestSet to real steady-state usage, measured, not guessed. The scheduler bin-packs on requests, never on limits or on actual live usage (ch.8). A request set too low over-packs a node — if every Pod's usage spikes together, they starve each other even though the node "had room" on paper.
CPU limitOmit it for latency-sensitive services, or set it well above steady usage. CPU limits are enforced by the kernel's CFS bandwidth controller in fixed 100ms periods. A container that bursts past its quota is throttled for the rest of that period — even when the node has entirely idle CPU sitting right next to it. This shows up as p99 latency spikes that have nothing to do with actual contention.
Memory requestSet close to steady-state usage, with modest headroom. Same bin-packing logic as CPU, but the failure mode is worse: an over-committed node evicts based on requests vs actual usage under memory pressure.
Memory limitAlways set it, above observed peak, never omitted. There is no memory-equivalent of CPU throttling. Exceed the limit and the kernel OOM-kills the container outright (exit code 137, Reason: OOMKilled) — a hard, immediate, unrecoverable-mid-request failure, not a graceful slowdown.
Limit with no request setsurprising default avoid relying on it. If you set a limit but no request, Kubernetes silently defaults the request to equal the limit. That Pod now reserves its full limit's worth of the node's allocatable capacity even if it typically uses a fraction of that — quietly destroying your bin-packing density.

Probe selection

PROBEUSE WHENGETS THIS WRONG AND YOU GET
livenessProbeDetecting a hung or deadlocked process that only a restart fixes. Pointing it at a downstream dependency (a database, another service) turns one dependency outage into a restart storm across every Pod that depends on it — liveness should only ever ask "is my own process alive," never "is the world healthy."
readinessProbeTemporarily can't serve traffic (warming a cache, waiting on a dependency) but the process itself is fine. Skipping it means a Pod that's still initializing receives production traffic the moment its container starts, before it can actually serve anything correctly.
startupProbeSlow-starting applications (JVMs, large in-memory caches) that would otherwise trip liveness during normal startup. Without one, a generous initialDelaySeconds on liveness is a permanent tax on every restart's detection time — a startupProbe disables liveness/readiness checks until it succeeds once, then gets out of the way.

Choosing a workload type

USEWHENMECHANISM
DeploymentStateless, interchangeable replicas — the default choice. Manages a ReplicaSet for you and adds rolling-update strategy on top (ch.2). Pods are fungible; any replica can be replaced by an identical new one.
StatefulSetEach replica needs a stable identity: a stable network name and its own persistent storage that follows it across rescheduling. Ordinal Pod names (db-0, db-1...) and a PVC template that provisions one volume per ordinal and reattaches it to the same ordinal on reschedule (ch.11) — databases, brokers, anything where "which replica am I" matters.
DaemonSetExactly one Pod per matching node, automatically, including nodes added later. Node agents: log shippers, monitoring agents, and the CNI/CSI node-level plugins themselves are almost always DaemonSets.
JobRun-to-completion work — process N items and stop. Tracks successful completions against spec.completions and retries failures up to backoffLimit, unlike a Deployment which restarts forever.
CronJobA Job that should run on a schedule. Creates a new Job object from a template on each scheduled tick — inherits all of Job's completion/retry semantics per run.

RBAC — least privilege by default

  • Prefer Role + RoleBinding over ClusterRole + ClusterRoleBinding whenever the access truly is namespace-scoped. A Role only grants permissions inside its own namespace; a ClusterRoleBinding grants them everywhere, forever, even in namespaces that don't exist yet.
  • A ClusterRole bound with a namespaced RoleBinding is a legitimate middle pattern — define the permission set once as a reusable ClusterRole, then bind it per-namespace with ordinary RoleBindings where it's actually needed, instead of either duplicating Roles or granting it cluster-wide.
  • Scope verbs as tightly as the workload allows. get/list/watch on one resource type is a different risk profile from a blanket * on * — grant exactly what the code calls, not what might be convenient someday.
  • Service account tokens are bound and audience-scoped by default since the 2020+ token model — they expire and are tied to the specific Pod that requested them, unlike the old cluster-lifetime tokens auto-mounted into every Pod. Don't disable this by falling back to a static long-lived token unless you have a specific reason.
  • Never bind to system:masters or grant cluster-admin to a workload identity. That group bypasses RBAC evaluation entirely at the authorizer level — it isn't "very permissive RBAC," it's a bypass of RBAC.

STEP 05 · OPERATIONAL RUNBOOKS

  
Procedures for when it's already going wrong


  
5.1 · Diagnosing a Pod stuck in Pending

  
Precondition: events are retained for a limited window (1 hour by default) — check
  kubectl get events before they age out and the exact reason is lost.

  
    
    
  1. Read the reason, don't guess it: kubectl describe pod <pod> and look at the
    Events section for a FailedScheduling entry. The message is specific — read it verbatim.
    2. 
    
  2. "Insufficient cpu" / "Insufficient memory" → no node's allocatable capacity minus
    already-requested resources can fit this Pod's requests. Confirm with
    kubectl describe nodes | grep -A5 "Allocated resources" on each node.
    3. 
    
  3. "node(s) didn't match Pod's node affinity/selector" → the Pod's nodeSelector or
    affinity rules eliminated every node. Compare against real labels:
    kubectl get nodes --show-labels.
    4. 
    
  4. "node(s) had untolerated taint" → a node has a taint the Pod doesn't tolerate.
    kubectl describe node <node> | grep Taints vs the Pod's spec.tolerations.
    5. 
    
  5. If the Pod also mounts a PVC, check kubectl get pvc first — a Pod cannot be
    scheduled while its claim is unbound, and that failure mode looks identical to a resource shortage until
    you check.
    6. 
    
  6. Fix, then confirm: free capacity, loosen the constraint, or add a matching node — then
    kubectl get pod <pod> -w and watch it move to ContainerCreating.
    7. 
  


  
5.2 · Diagnosing a Pod stuck in CrashLoopBackOff

  
    
    
  1. Confirm the pattern: kubectl get pod <pod> — rising RESTARTS
    with STATUS: CrashLoopBackOff confirms kubelet is repeatedly restarting and backing off.
    2. 
    
  2. Read current logs: kubectl logs <pod> — may be empty if the crash happened
    before anything was written.
    3. 
    
  3. Read the crash itself: kubectl logs <pod> -p (previous container instance)
    — this is almost always where the real error is, since the current instance may have only just started.
    4. 
    
  4. Check the exit code and reason: kubectl describe pod <pod> → Last State.
    Reason: Error with a small exit code is an application crash; Reason: OOMKilled
    with exit code 137 means the memory limit was hit — fix the limit or the leak, not the probe.
    5. 
    
  5. If Last State shows the container being killed by a probe rather than exiting on its own, the
    problem is probe configuration, not the app: check initialDelaySeconds,
    periodSeconds, and failureThreshold against how long the app actually takes to
    become healthy — a slow-starting app needs a startupProbe, not a more lenient liveness probe.
    6. 
    
  6. The backoff itself is exponential (10s, 20s, 40s… capped at 5 minutes) and is entirely local to
    kubelet — no control-plane component decides it. It resets only after the container stays up long enough
    to be considered stable.
    7. 
  


  
5.3 · Safely draining a node for maintenance

  
Precondition: a PodDisruptionBudget exists for anything you can't afford to lose entirely, and
  there's enough spare capacity elsewhere in the cluster to absorb the evicted Pods.

  
    
    
  1. Cordon first: kubectl cordon <node> marks it unschedulable so nothing new
    lands there while you work — it does not touch what's already running.
    2. 
    
  2. Drain: kubectl drain <node> --ignore-daemonsets --delete-emptydir-data —
    this calls the Eviction API for each Pod, which checks every matching PodDisruptionBudget before allowing
    the eviction to proceed.
    3. 
    
  3. If drain hangs, a PDB is refusing to let the last protected replica go — check
    kubectl get pdb for one showing ALLOWED DISRUPTIONS: 0. Either wait for another
    replica to become available elsewhere, or scale up before continuing.
    4. 
    
  4. Perform the actual maintenance — OS patching, kubelet upgrade, hardware work.
    5. 
    
  5. Uncordon when done: kubectl uncordon <node> — the node accepts new
    scheduling again immediately; Pods evicted earlier are not moved back automatically.
    6. 
  


  
5.4 · Recovering a cluster after etcd data loss (from backup)

  
Precondition: a snapshot taken with etcdctl snapshot save while etcd was healthy, and
  you know the cluster's member peer URLs. Without a prior snapshot this runbook cannot help you — there is no
  way to reconstruct etcd's data after the fact.

  
    
    
  1. Stop writes first. On a kubeadm-based control plane (which is what kind runs internally), moving
    etcd's static Pod manifest out of /etc/kubernetes/manifests/ stops the kubelet from running it.
    2. 
    
  2. Restore into a fresh data directory — never restore on top of a live one:
    etcdctl snapshot restore <file> --data-dir=/var/lib/etcd-restored --name=<member>
    --initial-cluster=<peer-list> --initial-advertise-peer-urls=<url>.
    3. 
    
  3. Point etcd at the restored directory by editing its manifest's --data-dir (or the
    systemd unit, on a non-kubeadm install) to the new path, then move the manifest back so kubelet starts it.
    4. 
    
  4. Confirm etcd health before touching anything else: etcdctl endpoint health and
    etcdctl member list.
    5. 
    
  5. Restart the API server (or wait for kubelet to notice the manifest change) and confirm
    kubectl get nodes returns objects as of the snapshot's timestamp — anything created after the
    backup was taken is genuinely gone; there is no partial recovery.
    6. 
    
  6. Expect reconciliation churn. Every controller now compares the restored desired state against
    whatever is actually still running and converges — Pods created after the snapshot but whose controllers
    still exist may effectively "disappear" from the API while their containers keep running until something
    notices and cleans them up.
    7. 
  

  

    
WHY THIS IS THE SCARIEST RUNBOOK IN THE LAB

    
etcd is the only stateful component in the entire control plane (ch.7). Every other piece —
    API server, scheduler, controller-manager — is stateless and disposable; killing and restarting them loses
    nothing. Losing etcd without a backup means losing the cluster's entire desired state, permanently.

  


  
5.5 · Diagnosing ImagePullBackOff / ErrImagePull

  
    
    
  1. kubectl describe pod <pod> → Events. manifest unknown means the
    image or tag doesn't exist — check for a typo. unauthorized means the registry needs
    credentials the Pod doesn't have.
    2. 
    
  2. Private registry: kubectl create secret docker-registry regcred
    --docker-server=<registry> --docker-username=<u> --docker-password=<p>, then
    reference it via spec.imagePullSecrets in the Pod.
    3. 
    
  3. Locally-built image not found: a kind node is an isolated container — it cannot see images only
    present in your host's Docker Desktop unless you load them explicitly:
    kind load docker-image <image>:<tag> --name lab. This is the standard workflow
    for testing local builds against kind, and it's what Build Project 3 in this lab relies on.
    4. 
    
  4. "no route to host" pulling from a registry → the node itself, not your laptop, needs network
    access to that registry; check the same DNS/proxy issue as the setup section's troubleshooting table.
    5. 
  


  
5.6 · A Service isn't routing traffic

  
    
    
  1. Check Endpoints first, always: kubectl get endpoints <svc>. Empty means
    either the selector matches zero Pods, or it matches Pods that aren't Ready — a failing
    readinessProbe removes a Pod from Endpoints without touching the Pod itself.
    2. 
    
  2. Confirm the selector actually matches: kubectl get pods -l <selector>
    --show-labels — a one-character label mismatch is the single most common cause of this whole class
    of bug.
    3. 
    
  3. Confirm the port mapping: kubectl describe svc <svc> — the Service's
    targetPort must match the port the container is actually listening on, not the port you
    intended it to listen on.
    4. 
    
  4. Bisect the layer: from a client Pod, curl the Pod's IP directly (bypasses the Service
    entirely); if that works but the ClusterIP doesn't, the problem is kube-proxy's rules, not the
    application. Check kubectl logs -n kube-system -l k8s-app=kube-proxy for errors.
    5.

BEGINNER  Project 1 · A multi-tier app, entirely hand-written YAML

  
No kubectl create deployment, no kubectl expose — every object below is a file
  you write yourself, which is the only way to actually feel what those shortcuts are generating on your
  behalf. A backend nginx serves a static JSON file from a ConfigMap; a frontend nginx proxies to it.


  
yamlbackend-configmap.yaml


apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-content
data:
  index.html: '{"service":"backend","status":"ok"}'


  
yamlbackend-deployment.yaml


apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  replicas: 2
  selector:
    matchLabels: {app: backend}
  template:
    metadata:
      labels: {app: backend}
    spec:
      containers:
      - name: nginx
        image: nginx:alpine
        ports: [{containerPort: 80}]
        volumeMounts:
        - name: content
          mountPath: /usr/share/nginx/html/index.html
          subPath: index.html
      volumes:
      - name: content
        configMap: {name: backend-content}


  
yamlbackend-service.yaml


apiVersion: v1
kind: Service
metadata:
  name: backend-svc
spec:
  selector: {app: backend}
  ports: [{port: 80, targetPort: 80}]


  
The frontend's ConfigMap holds an nginx config that proxies /api/ to the backend Service by
  DNS name — this is the same CoreDNS resolution mechanism from k8s-03, now doing real work.

  
yamlfrontend-configmap.yaml


apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-conf
data:
  default.conf: |
    server {
      listen 80;
      location = /  { return 200 'frontend: ok\n'; add_header Content-Type text/plain; }
      location /api/ {
        proxy_pass http://backend-svc.shop.svc.cluster.local/;
      }
    }


  
yamlfrontend-deployment.yaml


apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 2
  selector:
    matchLabels: {app: frontend}
  template:
    metadata:
      labels: {app: frontend}
    spec:
      containers:
      - name: nginx
        image: nginx:alpine
        ports: [{containerPort: 80}]
        volumeMounts:
        - name: conf
          mountPath: /etc/nginx/conf.d/default.conf
          subPath: default.conf
      volumes:
      - name: conf
        configMap: {name: frontend-conf}


  
yamlfrontend-service.yaml

metadata:
  name: frontend-svc
spec:
  selector: {app: frontend}
  ports: [{port: 80, targetPort: 80}]

ADVANCED  Project 3 · A real reconciliation loop for a CRD you define

  
The CustomResourceDefinition from experiment 17 comes back here as the load-bearing piece: a
  GreetingConfig whose spec.name/spec.message a small controller
  reconciles into a templated ConfigMap. This is level-triggered reconciliation — the same pattern k8s-09
  describes in every built-in controller — running as ~90 lines of your own Python.

pip install kubernetes

pythoncontroller.py — starter skeleton


import time
from kubernetes import client, config, watch

config.load_kube_config()   # load_incluster_config() if this ever runs as a Pod
core   = client.CoreV1Api()
custom = client.CustomObjectsApi()

GROUP, VERSION, PLURAL = "lab.example.com", "v1", "greetingconfigs"

def desired_configmap(gc):
    meta, spec = gc["metadata"], gc.get("spec", {})
    greeting = f"{spec.get('message','hello')}, {spec.get('name','world')}!"
    return client.V1ConfigMap(
        metadata=client.V1ObjectMeta(
            name=f"{meta['name']}-greeting", namespace=meta["namespace"],
            owner_references=[client.V1OwnerReference(
                api_version=f"{GROUP}/{VERSION}", kind="GreetingConfig",
                name=meta["name"], uid=meta["uid"], controller=True)],
        ),
        data={"greeting.txt": greeting},
    )

def reconcile(gc):
    # idempotent by construction: compute desired state, diff against observed, converge.
    # calling this twice with identical input must be a no-op — that's what "level-triggered" means.
    ns, cm = gc["metadata"]["namespace"], desired_configmap(gc)
    try:
        existing = core.read_namespaced_config_map(cm.metadata.name, ns)
        if existing.data != cm.data:
            core.replace_namespaced_config_map(cm.metadata.name, ns, cm)
            print(f"reconciled: updated {cm.metadata.name}")
    except client.exceptions.ApiException as e:
        if e.status == 404:
            core.create_namespaced_config_map(ns, cm)
            print(f"reconciled: created {cm.metadata.name}")
        else:
            raise

def reconcile_all():
    for gc in custom.list_cluster_custom_object(GROUP, VERSION, PLURAL)["items"]:
        reconcile(gc)

def main():
    w, last_resync = watch.Watch(), 0
    while True:
        # full resync on a timer REGARDLESS of watch events — this is what makes it
        # level-triggered rather than edge-triggered: a missed or dropped watch event
        # can never leave state permanently diverged, only briefly stale.
        if time.time() - last_resync > 30:
            reconcile_all(); last_resync = time.time()
        try:
            for event in w.stream(custom.list_cluster_custom_object, GROUP, VERSION, PLURAL, timeout_seconds=10):
                reconcile(event["object"])
        except Exception as e:
            print("watch error, will resync:", e); time.sleep(2)

if __name__ == "__main__":
    main()

  ConfigMap; (2) editing spec.message updates the ConfigMap's contents without you touching it
  directly; (3) manually deleting the ConfigMap causes your controller to recreate it on its own — the
  behavior every built-in Kubernetes controller exhibits, now visibly running in code you wrote.
