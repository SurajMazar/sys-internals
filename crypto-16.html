ARC 01 · THE PROBLEM

Correct primitives do not compose into a secure protocol by themselves

Here is the fact this entire course has been quietly building toward: every primitive you implemented in the last fifteen chapters can be individually correct, individually test-vector-verified, and the resulting system can still be completely broken. AES-128 (ch.3) is a permutation with no known practical attack under 128-bit keys. GCM (ch.7) is a provably secure AEAD mode given a unique nonce. HKDF (ch.8) is a sound key-derivation function given a high-entropy input. Diffie-Hellman (ch.11) produces a shared secret unknown to eavesdroppers given the two public values genuinely came from the two intended parties. Every one of those italicized clauses is a protocol-level obligation, not a primitive-level one — and nothing about implementing AES correctly tells you how to guarantee a nonce is unique, or that a DH public value wasn't substituted in transit.

This is precisely the gap real-world TLS closes, and precisely the gap this capstone will open on purpose so you can watch it get exploited with your own hands. Concretely, building a secure channel from the primitives you already have means answering four questions no single primitive answers:

  • Key agreement: how do two parties who share nothing derive a common secret over a network an adversary fully controls — and how do they know the other party is who they claim to be?
  • Key separation: one shared secret is not a key. How do you turn it into several independent, purpose-bound keys (handshake vs. application, client-to-server vs. server-to-client) so that compromising one doesn't compromise the others?
  • Framing and sequencing: AEAD encrypts one message under one nonce. A session is thousands of messages. Who assigns nonces, in what order, and what happens when that bookkeeping has a bug?
  • Authentication: DH by itself authenticates nothing — chapter 11 already proved this. Without binding the exchange to a verified identity, a network-level attacker is not a theoretical footnote; they are a first-class participant able to run the entire protocol legitimately, twice, once with each side.
WHAT THIS CHAPTER ACTUALLY BUILDS

A working subset of RFC 8446 (TLS 1.3): a Diffie-Hellman key share exchange, an HKDF-based key schedule that mirrors RFC 8446 §7.1 exactly, and an AES-128-GCM record layer using the same deterministic sequence_number ⊕ static_iv nonce construction TLS 1.3 uses (RFC 8446 §5.3) — the cipher suite is literally TLS_AES_128_GCM_SHA256, TLS 1.3's mandatory-to-implement suite. What it deliberately omits — certificates, signatures, a transcript-bound Finished message — is not an oversight. It is the experiment. §15 shows you exactly what breaks, in exactly the way chapter 11 predicted, the moment those pieces are missing.

ARC 03 · NAIVE SOLUTION

Attempt #1: wire the primitives together directly

You have four verified building blocks sitting in four earlier chapters. The obvious first move — and the one countless real systems have actually shipped, under names like "we rolled a lightweight encrypted transport for internal RPC" — is to wire them together with the least code possible:

pseudocodecapstone_v0.js — the strawman, annotated
function naiveSecureChannel(peer) {
    // 1. Diffie-Hellman, straight out of chapter 11 — no signature, no cert.
    const myPriv = randomExponent();
    const myPub  = modpow(G, myPriv, P);
    send(peer, myPub);
    const theirPub = receive(peer);         // ← trusted on arrival, no way to check WHO sent it
    const sharedSecret = modpow(theirPub, myPriv, P);

    // 2. Skip the KDF — the shared secret becomes the AES key directly.
    const aesKey = bigIntTo16Bytes(sharedSecret);   // ← chapter 8's whole argument, ignored

    // 3. One nonce per message, chosen however is convenient.
    function sendMessage(plaintext) {
        const nonce = random96Bits();             // ← "random" feels safe; §4 quantifies why it isn't enough
        const { ciphertext, tag } = gcmEncrypt(aesKey, nonce, plaintext);
        send(peer, nonce, ciphertext, tag);
    }
    return { sendMessage };
}

Read this charitably, the way §3 of every earlier chapter has asked you to: it is not incompetent code. Every cryptographic call inside it is one you have personally implemented and watched pass a real test vector. modpow is correct square-and-multiply exponentiation. gcmEncrypt is the real, from-scratch AES-128-GCM from chapter 7. If you fuzz-tested this function in isolation — feed it a plaintext, check that the matching key decrypts it correctly — it would pass every time. That is exactly the trap: unit tests on individual calls cannot see the protocol-level properties that are missing, because those properties live in the relationships between calls, not inside any single one.

§15's simulator is a working, expanded version of exactly this function — genuinely computing every value below — so the failures in §4 are not hypothetical.

ARC 04 · WHY IT FAILS

Three failures, each with a number attached

Three separate things are wrong with naiveSecureChannel, and each one is quantifiable rather than merely stylistic. None of them are bugs in the primitives — all three are bugs in the composition.

Failure 1 — the raw shared secret is not a key

A Diffie-Hellman shared secret is a uniformly random-looking group element, but it is not a uniformly random bit string, and it is not scoped to any purpose. Chapter 8 built HKDF specifically because raw keying material — a DH secret, a password, anything with algebraic structure or biased bits — is not safe to feed directly into a block cipher's key schedule: HKDF-Extract's entire job is "take input that might be biased or structured and output something that behaves like a uniform 256-bit key," and HKDF-Expand's entire job is "stretch and separate that into as many independent, purpose-labeled keys as the protocol needs." Skip both steps and you get exactly one key, doing every job in the protocol at once — handshake integrity and every future application record all riding on one undifferentiated value with no domain separation between them.

Failure 2 — random 96-bit nonces have a real, computable collision budget

GCM's entire authentication guarantee — chapter 7's whole chapter — depends on a nonce never repeating under a fixed key. A random 96-bit nonce is not immune to repeating; it is a birthday-bound problem, and the bound is computable, not hand-wavy: with n messages drawn from a 2⁹⁶ nonce space, the probability of at least one collision is approximately n²/2⁹⁷. Drag the slider — this is genuinely computed, not a canned number:

The birthday bound on random 96-bit noncesDRAG SLIDER
2^32

NIST SP 800-38D's own answer to this arithmetic is a hard operational ceiling: no more than 2³² invocations of GCM under one key when nonces are generated at random, precisely because collision probability stops being negligible well before the nonce space is exhausted. The naive channel has no such ceiling anywhere in its code — it will happily run past 2³² messages, and every message beyond it makes a reused nonce measurably more likely.

Failure 3 — nothing here authenticates anyone

This is the failure with no probability attached, because it is not probabilistic — it is deterministic and total. theirPub in the naive channel is accepted the instant it arrives on the wire, with zero verification of who sent it. Chapter 11 proved this abstractly: an active attacker sitting between the two parties can run the entire, cryptographically correct Diffie-Hellman protocol independently with each side, producing two genuine, individually-valid shared secrets — one with each victim — and neither victim has any signal that anything is wrong, because every individual DH computation they perform is completely correct. §15 runs this exact attack against the mini-TLS stack you are about to build, with real BigInt modular exponentiation on both sides of the attacker, and the result is not simulated — it is computed.

THE COMMON THREAD

All three failures share one root cause: the naive channel treats "call the right cryptographic functions" as equivalent to "run a secure protocol." A protocol is a set of ordering, binding, and verification obligations layered around correct primitive calls — HKDF's domain separation, GCM's nonce-uniqueness contract, and DH's need for an external authentication anchor are three separate instances of the same lesson. §5 fixes the first two mechanically. §6 shows why the third one cannot be fixed mechanically — it requires an ingredient (an authenticated identity) that no amount of clever wiring of chapters 3–11's primitives can manufacture from nothing.

ARC 05 · BETTER SOLUTION

Fix the two mechanical failures: a real key schedule, a real nonce discipline

Two of §4's three failures — the undifferentiated key and the collision-prone nonce — have mechanical fixes that require no new trust assumptions, only correct use of chapters you have already built. Step through the transformation from naiveSecureChannel to something structurally much closer to RFC 8446:

From raw secret to a real TLS 1.3-shaped key scheduleSTEP-BY-STEP

Two structural upgrades happened in that walkthrough, and both are things you already own from earlier chapters — this section only wires them into the right place:

  • HKDF-Extract-then-Expand, labeled, RFC 8446 §7.1-style. The raw DH secret goes through HKDF-Extract before it touches anything else, and every derived key comes from HKDF-Expand-Label with a distinct label string ("c hs traffic", "s hs traffic", "c ap traffic", "s ap traffic") baked into the HKDF info field. Compromise of one derived secret now tells an attacker nothing about any sibling secret — that is what "domain separation" bought you, mechanically, for the cost of a few extra HMAC calls.
  • Deterministic per-record nonces, not random ones. Instead of drawing a fresh 96-bit random value per message, each traffic secret also derives a 12-byte static IV via HKDF-Expand-Label(secret, "iv", "", 12), and the actual per-record nonce is static_iv ⊕ sequence_number — RFC 8446 §5.3's exact construction. A monotonically incrementing 64-bit counter, owned by exactly one writer per direction, cannot collide with itself until it wraps at 2⁶⁴ — astronomically past any realistic connection's lifetime, and with zero birthday-bound math involved at all, because there is no randomness left in the nonce to collide.
ARC 06 · WHY THAT STILL COSTS

Two fixes, one failure left standing — and it is not a small one

Re-run §4's three failures against the upgraded channel. Failure 1 (raw secret as key) — fixed, by HKDF. Failure 2 (random nonce collisions) — fixed, by a per-record counter. Failure 3 — completely untouched. Nothing about deriving better keys from a shared secret, or framing records with better nonces, does anything to verify whose shared secret it is. Watch the same active-attacker scenario from chapter 11 play out against the fully-upgraded key schedule and record layer:

Preview: an unauthenticated exchange under active attackSTEP-BY-STEP

The honest cost of actually closing this gap is not small, which is exactly why real TLS 1.3 spends four of its thirteen main handshake messages on it: a Certificate message (a chain up to a trust anchor, chapter 12's PKI model), a CertificateVerify message (a signature over the entire handshake transcript so far, binding the DH exchange to the identity the certificate names), and a Finished message on each side (an HMAC over the full transcript under a transcript-derived key, so that any tampering anywhere in the handshake — including a substituted DH public value — produces a Finished value the other side can detect does not match). None of that machinery improves AES, GCM, HKDF, or DH in isolation. All of it exists purely to answer the one question none of those primitives can answer on their own: is the party on the other end of this key exchange who they claim to be?

WHY THIS CAPSTONE DELIBERATELY SHIPS WITHOUT IT

Building a real certificate chain, a real signature scheme, and a real transcript-bound Finished message is chapters 9, 12, and most of 13 combined — reproducing all of it here would dilute the one lesson this chapter is built to deliver undiluted. Instead, §7 marks authentication as an explicit, labeled gap in the architecture, and §15 lets you toggle a single, deliberately minimal stand-in for it — a pinned expected public key, checked once — specifically so you can watch the difference between "no check" and "one honest check" with real computed values on both sides of the toggle.

ARC 08 · INTERNAL IMPLEMENTATION

The real mechanism: DH keyshare, HKDF key schedule, AEAD record layer

Everything in this section is executed live in this page by the same from-scratch JavaScript that powers §15 — no SubtleCrypto, no canned output. Three pieces, in the order a real handshake computes them: (a) the Diffie-Hellman keyshare exchange, (b) the HKDF key schedule that turns one shared secret into four labeled traffic secrets, and (c) the AES-128-GCM record layer that actually moves application bytes.

(a) The keyshare exchange — real modular exponentiation, both sides

This capstone reuses the exact demo-scale group chapter 11 verified: the 34-bit safe prime p = 8589935363 with generator g = 2. It is far too small to be secure — a real TLS 1.3 handshake uses X25519 (RFC 7748) or a ≥3072-bit finite-field group — but the arithmetic, the protocol role, and the vulnerability this section is building toward are identical at any modulus size. (c) The record layer — deterministic nonces, real AEAD

Per direction, per record: nonce = static_iv XOR seq_num (the sequence number occupies the low 8 bytes, big-endian, XORed in — RFC 8446 §5.3 exactly), associated data is the 5-byte pseudo record header [opaque_type=0x17, legacy_version=0x03 0x03, length_hi, length_lo], and the payload is sealed with the same gcmEncrypt function chapter 7 verified against its NIST test vector. §15 runs this in both directions, with independent sequence counters, for real application data.

WHY THE NONCE IS DERIVED, NOT TRANSMITTED

A classic TLS 1.2 record sent an explicit 8-byte nonce alongside every GCM record — extra bytes on the wire, and (as CVE-2019-1543 showed for a misconfigured ChaCha20-Poly1305 nonce length) another parameter an implementation could get wrong. TLS 1.3 removes the choice: the nonce is a pure function of a secret the peer already has and a counter both sides already maintain, so there is no "nonce field" left to misconfigure, truncate, or accidentally reuse across records — the discipline §5 asked for is now structurally enforced by the protocol rather than left to an implementer's memory.

WHY A WEAK TOY MODULUS DOESN'T INVALIDATE THE LESSON

The MITM demonstration in §15 does not depend on the DH modulus being weak at all — it works identically against a real 3072-bit group or X25519. An attacker who can sit on the wire does not need to break discrete log; they need only run the same protocol twice, which chapter 11 already proved requires zero cryptanalysis. The 34-bit modulus is chosen for JavaScript performance and byte-level inspectability, not because the attack needs it — a point worth internalizing precisely because "our production modulus is huge" is exactly the false sense of security an unauthenticated handshake gives an engineer who hasn't separated these two security properties in their head.

ARC 11 · REAL-WORLD INCIDENTS

When "assemble the primitives yourself" ships to production

Incident 1: the Juniper ScreenOS backdoor (CVE-2015-7755, disclosed 2015)

Juniper's ScreenOS firewall OS shipped VPN code whose Diffie-Hellman-based key exchange relied on a Dual_EC DRBG-derived constant that outside researchers later showed had almost certainly been altered from NIST's published value — most plausibly by a party who then possessed a trapdoor letting them predict "random" values the VPN handshake depended on. Layered on top, an independent, unrelated bug (the CVE number) gave any attacker who knew a specific hardcoded password a full authentication bypass on the SSH/telnet admin interface. The root-cause lesson for this chapter is specific: a correctly-implemented AES/DH-based VPN handshake is only as trustworthy as every constant it depends on, including ones — like a DRBG seed — that look like uninteresting boilerplate. This capstone's toy modulus is deliberately labeled insecure in plain sight; Juniper's compromised constant was not labeled at all.

Incident 2: WEP's IV reuse — the original nonce-reuse-by-design failure (Fluhrer, Mantin & Shamir, 2001)

Years before GCM existed, 802.11 WEP encrypted each frame with RC4 keyed by a 24-bit "initialization vector" concatenated with a fixed shared key — and 24 bits is small enough that on a busy access point, IV reuse was not a rare edge case but a routine, minutes-away event. Fluhrer, Mantin, and Shamir's 2001 paper showed that a specific class of "weak" RC4 keys produced by reused/related IVs leaked key-schedule bits directly, and passive collection of a few million frames recovered the WEP key outright — no active attack needed. This is §4's birthday-bound argument playing out at commercial internet scale fifteen years before this chapter's GCM nonce math: a nonce space too small for the traffic volume, chosen because nobody quantified the collision budget before shipping. WPA and WPA2 exist because of this incident, and TLS 1.3's deterministic per-record nonce (§8) is the direct architectural descendant of the lesson.

Incident 3: Telegram's MTProto 1.0 — correct primitives, broken composition (Jakobsen & Orlandi, 2015)

Telegram's original MTProto protocol combined AES-IGE mode with SHA-1-based integrity checking and its own key-derivation scheme, assembled independently of TLS rather than reusing it. Jakobsen and Orlandi's 2015 paper demonstrated a practical IND-CCA distinguishing attack exploiting exactly the class of gap this chapter has been naming all along: the individual primitives (AES, SHA-1-at-the-time) were not the weak link — the order and manner in which MTProto combined encryption and integrity checking left room for an attacker to manipulate ciphertext and learn information from the server's error behavior. Telegram's own response was telling: rather than patch the composition indefinitely, later MTProto revisions moved toward more conventional, more heavily analyzed AEAD-style constructions — the same convergence toward "use a standardized composition, not a bespoke one" that this entire course's applied half has been arguing for since chapter 6.

THE PATTERN, ONE MORE TIME

Not one of these three incidents is a story about a broken block cipher or a broken hash function. All three are stories about the composition layer — a corrupted constant, an undersized nonce space, a mis-ordered encrypt/authenticate step — exactly the layer §3–§6 of this chapter walked through, and exactly the layer §15 lets you attack with your own hands instead of reading about secondhand.

Three annotated pieces, in the order a real handshake executes them. First, the key schedule — this is not simplified pseudocode, it is close to what §8(b) actually runs:

javascriptkeySchedule() — RFC 8446 §7.1, as implemented in this file
function keySchedule(dheSecret, transcriptBytes) {
    const zero32 = new Uint8Array(32);
    const transcriptHash = sha256(transcriptBytes);   // binds CH ‖ SH — see §16's THINK question

    const earlySecret = hkdfExtract(zero32, zero32);           // no PSK: IKM = 0, per RFC 8446
    const derived1 = hkdfExpandLabel(earlySecret, "derived", sha256(new Uint8Array(0)), 32);
    const handshakeSecret = hkdfExtract(derived1, dheSecret);  // ← the ONE place the DH result enters

    const cHsTraffic = deriveSecret(handshakeSecret, "c hs traffic", transcriptHash);
    const sHsTraffic = deriveSecret(handshakeSecret, "s hs traffic", transcriptHash);

    const derived2 = hkdfExpandLabel(handshakeSecret, "derived", sha256(new Uint8Array(0)), 32);
    const masterSecret = hkdfExtract(derived2, zero32);

    const cAppTraffic = deriveSecret(masterSecret, "c ap traffic", transcriptHash);
    const sAppTraffic = deriveSecret(masterSecret, "s ap traffic", transcriptHash);
    return { cHsTraffic, sHsTraffic, cAppTraffic, sAppTraffic };
}

function sealRecord(key, staticIv, seqNum, plaintext) {
    const nonce = xorSeqIntoIv(staticIv, seqNum);     // static_iv ⊕ seq_num, RFC 8446 §5.3
    const aad = recordHeader(plaintext.length + 16);  // [type=0x17, ver=0x0303, lenHi, lenLo]
    const { C, T } = gcmEncrypt(key, nonce, plaintext, aad);
    return { header: aad, ciphertext: C, tag: T };            // what actually crosses the wire in §15
}

WHY REAL LIBRARIES ENFORCE THIS BOUNDARY IN CODE, NOT JUST IN DOCS

BoringSSL's handshake state machine literally cannot reach SSL_do_handshake() success without passing through a certificate-verification callback — skipping it requires an explicit, loudly-named override (SSL_CTX_set_custom_verify with a callback that always returns success, or SSL_VERIFY_NONE), which is precisely the kind of code a security review greps for. The lesson generalizes past TLS: any protocol with an authentication step should make skipping that step require an equally loud, equally greppable line of code — never a silent default.
