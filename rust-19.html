Chapter 5 gave you the rule: one mutable reference xor many immutable ones, checked at compile time. This chapter opens the box that rule lives in. cargo build does not check borrows against your source text — it checks them against a control-flow graph your source text is compiled down into, four representations deep. You will trace that pipeline end to end, watch the actual dataflow algorithm that decides where a borrow is alive, and see why the biggest usability leap in Rust's history — non-lexical lifetimes — was really a change of representation, not a change of rule.

ARC 01 · THE PROBLEM

A proof, not a scan

Chapter 5 stated the aliasing rule and chapter 9 stated lifetimes as a compile-time proof obligation. This chapter asks the mechanical question underneath both: what, concretely, does the compiler run to produce that proof? It is tempting to imagine the borrow checker as a smart linter — scan the source text, notice two overlapping borrows, reject. That model breaks the instant your function has an if, a match, or a loop, because "overlapping" stops being well-defined on raw text.

Consider the question the checker actually has to answer for every reference in your program: at this exact point in execution, could this reference still be used later? That is not a question about lines of source code. It is a question about reachability in a graph of possible execution paths — the classic formulation is "is there a path from here to a use of this value that does not pass through a redefinition of it?" Answering that for straight-line code is trivial. Answering it once you add a branch that goes one of two ways, or a loop that revisits the same code arbitrarily many times, requires an explicit graph to walk and a systematic algorithm to walk it with — you cannot eyeball it, and neither can a naive text scanner.

  • The program isn't run. rustc must decide safety statically, for every possible input, without executing anything — the general version of "will this pointer be misused" is undecidable, so any static checker must be a sound, deliberately conservative approximation: it may reject a few safe programs (chapter 6 already showed you real ones), but it must never accept an unsafe one.
  • Control flow branches. A reference can be used on one path and dead on another. The checker's verdict about a mutation on the dead path must not depend on the live path — but a single sequential reading of the source conflates the two.
  • The source text carries irrelevant structure. Comments, formatting, macro invocations, sugar like for loops and ? — none of it is what "is this reference still needed" is actually about. The checker needs a representation that has already stripped that away.

rustc's answer is to never check borrows against source text at all. It lowers your function through several representations, each one discarding detail the next question doesn't need, until it arrives at exactly the shape a reachability analysis wants: a directed graph of small, straight-line blocks. That representation is called MIR — the mid-level intermediate representation — and it is the single most important artifact in this chapter. Everything from here on is either building up to MIR, computing over MIR, or explaining what happens to MIR afterward.

THE ROUTE, IN ONE LINE

source → tokens → AST → HIR → THIR → MIR → LLVM IR → machine code. Borrow checking happens at exactly one stop on that route — MIR — and nowhere else. §7 is a full explorer of every stop; §8 opens MIR itself and the dataflow algorithm that runs over it.

DEEP CONTEXT · WHY "NON-LEXICAL"?

"Lexical" describes structure you can see by reading the braces: a lexical scope is exactly the block a variable is declared in. The pre-2018 borrow checker computed a borrow's lifetime as a lexical scope — literally, the nearest enclosing pair of braces. "Non-lexical lifetimes" means exactly what it says: the borrow's lifetime is no longer required to be a syntactic scope at all. It is whatever the dataflow analysis in §8 computes it to be — which, for straight-line code, usually ends far earlier than the enclosing brace, and for branching code can differ per path, as §15's simulator will show you directly.

ARC 03 · NAIVE SOLUTION

Attempt #1: a borrow lives until its enclosing brace

Derive the naive algorithm honestly, because it is exactly what Rust shipped from 1.0 (May 2015) until edition 2018 — it is not a strawman invented for this chapter. Reading source top to bottom, the simplest rule you could write for "how long is this borrow valid" is: a reference is valid from its creation to the end of the lexical block it was created in — the nearest enclosing { }. It requires no graph at all, just a stack of scopes mirroring the parser's brace nesting, so it was a natural fit for the original AST-based checker.

Rustlexical_scope.rs — valid, straight-line code, either algorithm accepts it
fn main() {
    let v = vec![10, 20, 30];
    let first = &v[0];       // borrow of v begins
    println!("{}", first);   // last real use of `first`
}                                // ← lexical algorithm: borrow "ends" HERE

For code shaped like this, the naive rule and the modern one agree — the brace and the last use happen to line up. That agreement is exactly what made the lexical model feel correct for years: most examples in tutorials are short, straight-line, and never expose the gap between "last statement in the block" and "last statement that actually touches the reference." §4 finds the gap.

ARC 04 · WHY IT FAILS

The gap between "last line of the block" and "last use"

Take the same shape and add one line after the reference's last real use — still entirely safe code, because by the time x is mutated, nothing is reading through y anymore:

Rustthe_nll_example.rs — safe code, rejected by the pre-2018 checker
fn main() {
    let mut x = 5;
    let y = &x;            // shared borrow of x begins
    println!("{}", y);    // last use of y — nothing reads y after this line
    x += 1;                // mutate x while y is still lexically "in scope"
    println!("{}", x);
}
UNDER THE PRE-2018 (LEXICAL) BORROW CHECKER

This failed to compile with error[E0506]: cannot assign to `x` because it is borrowed. The checker's reasoning was mechanical and, by its own rule, correct: y's region was computed as "the rest of the enclosing block," which includes the x += 1 line, so any mutable access to x inside that region was flagged — regardless of the fact that y is never read again. Modern rustc compiles this exact function without a warning. Nothing about the aliasing rule changed; what changed is how precisely the compiler can tell where a borrow's region actually ends.

Scale this pattern up and you get real, everyday code that the lexical checker rejected constantly: reading from a HashMap in one if branch and mutating it in the other, holding a borrow across an early-return check that turns out not to be taken, or simply calling a method that reads a field and then, three lines later in the same block, calling a different method that needs &mut self. Niko Matsakis's public survey work ahead of the NLL RFC found this class of false rejection was one of the most common sources of new-user frustration with Rust — not incorrect compiler behavior, but a checker that was measurably more conservative than the actual aliasing rule required.

The deeper problem is structural, not cosmetic: a lexical scope is a property of the AST — where the braces are. "Where a reference is last used" is a property of control flow — which statements can actually execute after which. The moment a function has a branch, those two things can diverge inside a single block (as above) or across blocks entirely (as §15 shows with an if/else). Fixing this for real, not just for the single-block case, needs a representation where control flow is an explicit graph — which is precisely what §5 introduces.

THE ONE-SENTENCE VERSION

Replace "a borrow's lifetime is the block it was written in" with "a borrow's lifetime is the exact set of program points from which a use of it is still reachable" — and compute that set with a graph algorithm instead of reading it off the parser's brace stack. The aliasing rule from chapter 5 is completely unchanged; only the precision of "when is it in effect" improved.

ARC 06 · REMAINING COSTS

Be honest: NLL is a better approximation, not a perfect one

NLL is a huge usability win, and it is still exactly what §1 said any static checker must be: a conservative approximation. Three real costs remain, and naming them honestly is what motivates §11's Polonius discussion.

  • It is flow-sensitive per path, but not alias-sensitive across values. Region inference tracks when a reference-typed local is live; it does not reason about which concrete runtime object two different references actually point to. A pattern where a function returns a borrow through one branch of a match and takes a fresh, non-conflicting borrow through the other is still rejected today, because the region computed for the return type must be valid on every path out of the function, not just the path actually taken. §11 walks a real, still-open example of this.
  • The mental model got harder to hold in your head. "One mutable xor many immutable, checked against the brace you're in" was a rule you could apply by eye. "Live until the backward dataflow fixed point says it's dead, computed over a CFG you don't see" is not — in practice this means more Rust developers trust the compiler's accept/reject verdict directly rather than re-deriving it, which is a reasonable trade but a real shift in how the language is used day to day.
  • It costs real compile time. Building MIR, running region inference, and checking every borrow against the computed regions happens for every function, every build. §10 puts this in proportion against the rest of the pipeline — it is a real but usually modest slice of total compile time, dwarfed by monomorphization and LLVM codegen for most crates.

None of this is an argument against NLL — the alternative is the checker from §3, which was strictly worse on every one of these axes except raw implementation simplicity. It is the honest account of where "solved" still has an asterisk, and that asterisk has a name: Polonius, covered properly in §11.

WHY SO MANY REPRESENTATIONS?

Each lowering step exists to answer a narrower question than the last. The parser only needs to recover structure — it doesn't care about types yet, so AST doesn't have any. Type checking needs every expression's type — so HIR keeps full expression trees, sugar mostly desugared, but macros already expanded. THIR exists purely so pattern-match exhaustiveness (chapter 6's E0004) and constant evaluation have a fully-typed tree to walk without re-deriving types from HIR each time. And MIR exists because none of the earlier stages expose control flow as an explicit graph — which is exactly what borrow checking, and several major optimizations, need and nothing before it provides.

ARC 08 · INTERNAL IMPLEMENTATION

MIR's actual shape, and the algorithm that walks it

Three pieces, in the order you need them: (a) what a MIR function actually looks like once it's built, (b) the backward liveness dataflow that computes borrow regions over it, and (c) what Polonius changes about that computation.

(a) A basic block is straight-line code plus exactly one exit

MIR represents a function as a set of basic blocks, each with two parts: a sequence of statements (assignments, borrows, drops — nothing that can jump) and exactly one terminator at the end (the only thing allowed to transfer control: Goto, SwitchInt, Call, Return, Drop, Assert, Unreachable). Every if, match, and loop in your source becomes a SwitchInt terminator plus a fan-out of target blocks — there is no other way to branch in MIR. (b) Liveness: a backward dataflow fixed point over the whole graph

NLL's core computation, simplified to the version this chapter's simulator implements exactly, is standard backward liveness analysis — the same algorithm every optimizing compiler runs, applied here to reference-typed locals instead of arbitrary registers:

live_out[B] = ∪ live_in[S] for every successor S of block B live_in[B] = uses(B) ∪ (live_out[B] − defs(B)) uses(B) = locals read in B *before* any redefinition within B ("upward-exposed") defs(B) = locals (re)defined anywhere in B Repeat for every block until no live_in/live_out set changes — a FIXED POINT. A local (here: a borrow) is "live" at a point iff it may be read on some path forward from that point without an intervening redefinition.

Two things make this genuinely different from the naive scope-stack approach in §3. First, it is computed per basic block, over the real successor/predecessor edges of the CFG — a branch not taken contributes nothing to a variable's live range on the path that skips it, which is exactly the property §4's example needed and the lexical algorithm structurally could not provide. Second, it is a genuine iterative fixed point: for a CFG with a loop (a back-edge), a single backward pass is not enough — a use inside the loop body can make a variable live at the loop header, which then makes it live at the end of the loop body too, which was the block we just processed. (c) Polonius: reformulating the same question as alias analysis

Everything above is still, fundamentally, "is this local's type alive" — a property of the reference value, not of what it actually points to. Polonius (github.com/rust-lang/polonius, work started around 2018 under Niko Matsakis) reformulates borrow checking as a set of Datalog-style logical facts and rules — things like loan_issued_at, loan_invalidated_at, and subset relations between regions — solved to a fixed point by a small dedicated engine rather than rustc's existing dataflow framework. The reformulation is powerful enough to be genuinely path-sensitive about which loan is live, not just whether some loan of a given region is live — which is exactly what's needed to accept the case in §6 that NLL still rejects. Status today: Polonius is not the default borrow checker. It ships as an alternative implementation you can opt into on nightly with -Z polonius, and the compiler team has been working on a faster, more directly integrated rewrite of the same idea aimed at eventually closing the gap with NLL's performance — but there is no committed date for it becoming Rust's default borrow checker.

WHAT "ALIAS ANALYSIS" ADDS THAT LIVENESS DOESN'T

Liveness answers "is a use of a reference of this type reachable from here." Alias/loan analysis answers the sharper question "is a use of this specific borrow — the one created by this exact statement — reachable from here, given everything we know about which branches lead where." The difference only shows up in code where two different possible borrows could satisfy the same liveness requirement but only one of them is actually still valid on the path taken — precisely the shape of §6's and §11's examples.

Read the row order as a spectrum, not a ranking: static, path-sensitive alias analysis (Polonius) sits at one end, no static aliasing discipline at all (GC languages) sits at the other, and everything in between is a choice about how much of the "is this pointer safe" question you want answered before the program ever runs, traded against how expressive and how implementable that answer needs to be.

ARC 10 · PERFORMANCE & SAFETY CHARACTERISTICS

Where does borrow checking actually sit in your build time?

A number worth internalizing before you blame the borrow checker for a slow build: across the pipeline in §7, MIR construction and borrow checking are consistently one of the smaller line items. The dominant costs are almost always monomorphization (chapter 8 — generating one concrete function body per type/const combination actually used) and LLVM code generation and optimization on the resulting, often much larger, instantiated IR. Drag the sliders — the shape is illustrative (modeled on the general proportions reported by rustc's own -Z self-profile traces across typical crates), not a measurement of one specific build:

The safety side of the ledger is the reason the compile-time bill gets paid at all: every accepted program carries a compile-time proof that its shared/mutable-reference usage is free of data races and dangling accesses, for zero runtime cost — no reference count, no lock, no GC pause enforces it, because nothing needs to. The alternative, checking the same property with a runtime sanitizer, only tells you about the specific execution path you happened to exercise; the borrow checker's guarantee covers every path, once, at build time.

MODEL, NOT MEASUREMENT

The exact split shifts enormously by crate: a small binary with almost no generics spends a comparatively larger share of its (very short) build in parsing and typeck; a generics-heavy library crate like serde-derived code can spend the majority of its time in monomorphization and LLVM, because one generic function can expand into dozens of concrete instantiations. What does not shift much in either case is borrowck's slice — it scales roughly with source size, not with how many times a generic body gets instantiated, because (as chapter 8 covered) borrow checking runs once on the generic MIR, before monomorphization multiplies it.

ARC 11 · REAL-WORLD PRODUCTION

Three episodes from the checker's actual history

Episode 1: two-phase borrows fix the single most-reported false positive

Before NLL fully landed, the single most common "but this is obviously safe!" complaint had a one-line reproduction:

Rusttwo_phase.rs — compiles today, used to be rejected
let mut v = vec![1, 2, 3];
v.push(v.len());   // &mut v needed for push(), &v needed to compute the argument

Vec::push(&mut self, ...) needs a mutable borrow of v; evaluating its argument, v.len(), needs a shared borrow of the same v — and under a naive "the mutable borrow starts the moment the call begins evaluating" model, those two borrows overlap and rustc reports E0502. The fix, two-phase borrows, splits a mutable borrow's lifetime into a reservation phase (present, but behaves like a shared borrow — other shared borrows may coexist with it) and an activation phase (the point it's actually used mutably, i.e. inside push's body, after all arguments are evaluated). It shipped alongside NLL for the 2018 edition and is exactly the kind of fix that only makes sense once borrow validity is a computed, per-point property rather than a single lexical span — it needed the same infrastructure this chapter has been building.

Episode 2: shipping a stricter checker without breaking the ecosystem

Replacing the borrow checker underneath millions of lines of already-published crates is exactly the kind of change that risks breaking the world. The rollout strategy is worth studying on its own: for a transition period, rustc ran both checkers side by side under a -Z borrowck=migrate mode — the old lexical checker remained the actual gate for 2015-edition crates, while NLL ran in parallel purely to compare verdicts and emit a future-compatibility warning wherever NLL would accept something the old checker rejected (never the reverse — NLL was designed to be strictly more permissive, not less, so a case where NLL rejected something the old checker accepted would have signaled a real soundness bug in the new implementation and did in fact surface a handful during the migration, which were fixed before stabilization). NLL became the sole checker for the 2018 edition at its release, and later replaced the lexical checker entirely for all editions in Rust 1.36.0 (2019). The lesson generalizes past compilers: when you tighten or loosen a static check that gates a large ecosystem, ship the new verdict as a warning against the old one before it becomes the only verdict.

Episode 3: the case that's still open

The pattern that motivates Polonius most directly has been tracked in the rustc issue tracker since long before NLL shipped (commonly cited as issue #21906) and still doesn't compile on stable today:

Rustpolonius_case.rs — rejected on stable NLL with E0502, accepted under -Z polonius
fn get_or_insert(map: &mut HashMap<u32, String>) -> &String {
    match map.get(&22) {
        Some(v) => v,
        // v is not live on THIS path — map.get's borrow should be dead here —
        // but stable rustc still rejects the mutable borrow below:
        None => {
            map.insert(22, String::from("hi"));   // error[E0502]
            map.get(&22).unwrap()
        }
    }
}

NLL's region inference must pick a single region for the borrow behind map.get(&22) that is valid everywhere that region's type could flow — including through the Some(v) arm's return — and it does so without distinguishing "this specific loan, on this specific path." Polonius's per-loan, per-path facts are precisely what's needed to see that the None arm never actually needs that loan alive, and accept the mutable insert there. This is the real, working example the Polonius project's own documentation uses to justify the rewrite — not a hypothetical.

ARC 13 · SOURCE CODE WALKTHROUGH

Reading the real thing: rustc_borrowck and friends

rustc's own source tree is organized around exactly the pipeline from §7 — one crate per representation or per transformation between representations. This is the real, current directory shape:

compiler/
├── rustc_ast/ — the AST's type definitions, produced by rustc_parse
├── rustc_hir/ · rustc_hir_analysis/ — HIR types + the type checker that runs over them
├── rustc_mir_build/ ● src/build/mod.rs — builds THIR, then lowers THIR → MIR, one basic block at a time
├── rustc_middle/src/mir/ ● mod.rs — the MIR data types themselves: Body, BasicBlockData, Statement, Terminator
├── rustc_mir_transform/ — MIR-to-MIR optimization passes (inlining, const-prop, simplify-cfg)
├── rustc_mir_dataflow/ ● src/framework/mod.rs — the generic backward/forward dataflow engine §8(b)'s algorithm is an instance of
├── rustc_borrowck/
│ ├── ● src/lib.rs — entry point: type_check() then compute borrow-checking errors from the results
│ ├── ● src/nll.rs — compute_regions(): builds the region-inference constraint set from MIR
│ └── src/region_infer/mod.rs — solves the constraints; this is where NLL's fixed point actually runs
├── rustc_codegen_ssa/ · rustc_codegen_llvm/ — monomorphized MIR → LLVM IR
└── rustc_codegen_cranelift/ — alternative backend, MIR → Cranelift IR, mainly for fast debug builds

The MIR data types themselves, simplified to their load-bearing fields — this is the shape §8(a)'s deck was walking you through building:

Rustrustc_middle::mir — Body and BasicBlockData, simplified
struct Body {
    basic_blocks: IndexVec<BasicBlock, BasicBlockData>,  // the CFG itself
    local_decls:  IndexVec<Local, LocalDecl>,             // _0 (return), _1, _2, ... — every temp & binding
    arg_count:    usize,
}

struct BasicBlockData {
    statements: Vec<Statement>,     // straight-line: Assign, StorageLive/Dead, FakeRead...
    terminator: Terminator,         // exactly one; the ONLY thing that can transfer control
}

enum TerminatorKind {
    Goto { target: BasicBlock },
    SwitchInt { discr: Operand, targets: SwitchTargets },  // if/match/loop compile to this
    Call { func: Operand, args: Vec<Operand>, destination: Place, target: Option<BasicBlock> },
    Return,
    Drop { place: Place, target: BasicBlock },
    Assert { cond: Operand, target: BasicBlock },
    Unreachable,
}

And the shape of the region-inference constraint solver in region_infer/mod.rs — the actual fixed-point loop §8(b) presented as a formula:

Rustrustc_borrowck::region_infer — the solve loop, simplified
fn solve(&mut self) {
    let mut changed = true;
    while changed {
        changed = false;
        for constraint in &self.outlives_constraints {
            // constraint: region `sup` must contain everything region `sub` contains
            if self.region_value_of(constraint.sub)
                .is_not_subset_of(self.region_value_of(constraint.sup))
            {
                self.add_points(constraint.sup, constraint.sub);
                changed = true;   // another block's region grew — must re-check everything again
            }
        }
    }
    // once no region grows on a full pass: fixed point reached, verdict is final
}

Notice the shape is identical to §8(b)'s liveness loop: propagate along edges, grow sets, repeat until nothing changes on a full pass. Liveness feeds the initial region contents (a region must at least contain every point its local is live); the outlives constraints from subtyping and function signatures grow it further. Borrow-check errors are reported only after this loop terminates and every region's final value is known.

The MIR-level borrow tracer

This is the real backward liveness dataflow from §8(b), run live over an actual 5-block control-flow graph with a genuine branch — not a straight-line trace dressed up to look like one. The source function:

Rusttracer_source.rs — one shared borrow, one branch, one merge
fn tracer(cond: bool, v: &mut Vec<i32>) -> i32 {
    let r = &v[0];              // bb0: shared borrow of v, named r
    if cond {
        println!("{}", r);       // bb1 (true branch): uses r
    } else {
        v.push(1);              // bb2 (false branch): mutable access to v — conflict with r?
    }
    v.len() as i32              // bb3 → bb4: merge, then return
}

Use the controls to change what happens in bb1 and bb3, then hit recompute. Every run performs the real fixed-point liveness computation from §8(b) — block by block, edge by edge — and the accept/reject verdict for bb2's mutable access falls straight out of whatever the algorithm actually finds, not a scripted answer.
