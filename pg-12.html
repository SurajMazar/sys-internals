POSTGRESQL INTERNALS · CHAPTER 12

VACUUM, Autovacuum &
the Anatomy of Bloat

MVCC (chapter 5) buys concurrency by never overwriting a row in place: every UPDATE and DELETE leaves the old row version on disk, because some concurrent snapshot might still need it. Nobody ever comes back to erase it synchronously — that job was deliberately deferred to a background process. This chapter derives why that deferral was the only sane choice, and then goes all the way down into vacuumlazy.c: the three-phase algorithm, the line-pointer state machine, the visibility map, and the PostgreSQL 17 rewrite that replaced a hard-coded array with a radix tree.

ARC 01 · THE PROBLEM

MVCC's bill comes due later, and somebody has to pay it

Chapter 5 established the deal: PostgreSQL never blocks a reader on a writer, or a writer on a reader, because every transaction sees a private, consistent snapshot of the database as of some point in time. The mechanism that makes this cheap is equally simple to state and expensive to ignore: an UPDATE does not modify a row — it inserts a brand-new heap tuple with a fresh xmin, and marks the old tuple's xmax as the deleting transaction's ID. A DELETE only ever sets xmax. The old row version is not touched, moved, or freed. It just sits there, on disk, now called a dead tuple.

That is the entire problem in one sentence: PostgreSQL's write path only ever adds bytes; nothing in the write path ever removes them. Every row you update ten times a second leaves ten dead copies per second somewhere in the table's pages, forever, unless a second, independent process comes back later and reclaims them. Three consequences follow immediately, and each is a separate reason the "later" process cannot be optional:

  • Disk usage is unbounded without reclamation. A table that is logically 10 GB of live rows can physically occupy 100 GB if updates outrun cleanup — the classic meaning of bloat.
  • Index entries rot along with the heap. Every non-HOT update to an indexed column adds a new index entry pointing at the new heap tuple and leaves the old entry pointing at the now-dead one. An index scan can walk straight into garbage if nothing ever prunes it — so cleanup is not just a heap problem, it's an index problem with a stricter correctness constraint (§7 derives exactly why).
  • Transaction IDs are a finite, wrapping resource. xmin/xmax are 32-bit counters. If a table's oldest unfrozen row version is never revisited, the 32-bit XID space eventually wraps, and a row that looks "old" can suddenly look "in the future" — transaction ID wraparound, which is not a performance problem, it is a correctness and data-loss threat serious enough that PostgreSQL will shut a database down to read-only mode rather than risk it.

So the question this chapter answers from first principles is: given that MVCC guarantees no in-place overwrite, who cleans up, when, and how do they know it's safe? The answer PostgreSQL chose — a background reclaimer decoupled from the transactions that create the garbage — is not the only possible answer (InnoDB and Oracle both organize "the old version" differently), but every design in this space ends up needing some version of the same background process, for the same underlying reason: you cannot know it is safe to free a row version at the moment you stop needing it, because you don't know what other transaction might still need it.

WHY THIS MATTERS FOR THE REST OF THE COURSE

VACUUM is the process that keeps three separate promises solvent at once: bounded disk usage, correct indexes, and a transaction ID counter that never wraps. Every one of those promises is a background promise — nothing in the foreground query path enforces them. That single design fact explains almost every operational vacuum incident you will ever debug: bloat is always a symptom of the background process falling behind the foreground one, and diagnosing it always means asking why didn't the sweep keep up, or why couldn't it reclaim what it found? — which is exactly the shape of §11's incidents.

DEEP CONTEXT · WHY IT'S CALLED "VACUUM"

The name predates autovacuum by two decades: from the earliest Postgres releases, VACUUM was a DBA-issued SQL command — you ran it in cron, at 3 a.m., against tables you knew were update-heavy, and hoped you picked the right frequency. There was no daemon, no threshold, no notion of "this table needs it now" — only a human's judgment and a crontab. Everything from 8.1 onward is the project incrementally replacing that human judgment with instrumentation: dead-tuple counters, scale factors, freeze ages, and eventually a launcher process that makes the decision no operator has to remember to make.

ARC 03 · NAIVE SOLUTION

Attempt #1: reclaim inline, the moment you delete

Derive it honestly. If the problem is "dead tuples accumulate because nothing reclaims them immediately," the most obvious fix is: make the deleting/updating transaction reclaim the space itself, synchronously, as part of committing. No separate process, no scheduling, no scanning — the transaction that created the garbage cleans up its own garbage before anyone else even notices it existed.

Cstrawman.c — inline reclaim on delete/update
void
heap_delete_naive(Relation rel, ItemPointer tid, TransactionId xid)
{
    HeapTupleHeader tup = fetch_tuple(rel, tid);

    /* Mark it dead — this part is real and necessary either way */
    tup->t_xmax = xid;
    tup->t_infomask &= ~HEAP_XMAX_INVALID;

    /* THE NAIVE PART: reclaim the slot right now, in this transaction,
     * instead of waiting for a background process to notice later.   */
    if (CurrentTransactionCommits())
    {
        MarkLinePointerUnused(rel, tid);   /* free it immediately   */
        RemoveIndexEntriesFor(rel, tid);   /* and its index entries */
    }
}

This is not a silly idea — it is exactly how a naive single-writer key-value store, or a simple B-tree file format with no concurrent readers, would legitimately work: delete a key, free its slot, done. It even has real precedent in the relational world: this is close in spirit to what InnoDB and Oracle appear to do from the outside — a delete looks "gone" almost immediately to new transactions. The naive design's appeal is that it collapses two problems (mark dead, reclaim space) into one code path with no scheduling problem at all: there is no autovacuum to tune, no dead-tuple backlog, no bloat, because nothing is ever allowed to accumulate.

ARC 04 · WHY IT FAILS

You cannot reclaim what a concurrent snapshot might still need

The naive design's fatal assumption is hiding in the phrase "as soon as you delete it." As soon as for whom? MVCC's entire value proposition is that a transaction which began earlier keeps seeing the database as it was when its snapshot was taken — that is what "repeatable read" and "serializable" mean operationally. If transaction A opens a snapshot at time T0, and transaction B deletes a row at T1 > T0, the row must still be visible to A for as long as A's transaction runs, however long that is. Reclaim the line pointer the instant B commits, and the next thing A's query does — a sequential scan, an index lookup that resolves to that tid — reads whatever new tuple has since been written into that slot, or reads freed, reused garbage. That is not merely a bug; it is a correctness violation, and it is silent — no error, just a wrong answer.

So the honest fix to the naive design is: "reclaim it only once no transaction's snapshot could possibly still need it" — which is precisely the condition PostgreSQL calls the xmin horizon (tracked via the shared ProcArray, chapter 5). But computing that horizon requires looking at every other backend's snapshot — which is exactly the kind of shared, contended, global state a per-transaction inline reclaim would have to consult on every single delete. Do the math on what that costs:

THE NUMBERS

Assume a modest OLTP workload: 5,000 row deletions/updates per second, and computing "is it safe to reclaim this tid yet" requires a horizon check against the shared process array — a shared-memory read under a lock that every other backend also needs for its own snapshot. At 5,000 checks/sec you've turned a per-row decision into 5,000 contended shared-memory operations/sec in addition to the snapshot-taking each of those transactions already does for its own reads. And even if you paid that cost, the answer is usually "no, not yet" — a horizon rarely advances between one commit and the next, so most of those checks would do work only to conclude "leave it dead a little longer," meaning the naive design would frequently degrade into exactly the deferred-cleanup shape it was trying to avoid, except now paid per-transaction instead of once in the background. Meanwhile, with zero reclamation of any kind, dead tuples in a table under constant update load grow linearly and without bound: at 5,000 updates/sec sustained, one hour is 18 million dead rows added to that one table, with no mechanism to ever remove them.

Note carefully what InnoDB and Oracle actually do, because it is easy to over-read "looks gone immediately" as "no background process needed." Both systems still relocate the old version somewhere — an undo segment — and both still require a background actor (InnoDB's purge thread, Oracle's undo-retention machinery) to decide when no active read view needs that undo record anymore and reclaim it. They have moved where the old version lives (out of the primary data structure, into a separate log), not eliminated the fundamental problem that reclamation must wait for the oldest concurrent reader. §9 compares the three shapes in detail.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates for "who decides it's safe, and when"

If reclamation must wait for a horizon, the design space narrows to: who computes the horizon and acts on it, and how often? Step through the three candidates PostgreSQL's design space actually contains — the third is what shipped, but the second was seriously prototyped and shelved, which is instructive in its own right.

THE CLINCHING ARGUMENT: DECOUPLING WRITE LATENCY FROM CLEANUP COST

A background sweep with its own independent read of the heap means a fast OLTP transaction never pays for cleanup it didn't ask for — it pays only the small, fixed cost of setting xmax and moving on. Cleanup cost is instead paid later, amortized, by a process that can be paced, throttled, and even skipped under load (§6's cost-based delay). That's the actual shape of the trade: foreground latency stays flat and predictable, and the price is a background process that must scan the whole heap and can fall behind — which is precisely the failure mode the rest of this chapter is about.

ARC 06 · WHY THAT STILL COSTS

A background sweep is not free, and it can lose the race

Choosing "background sweep, own read of the heap" solves the correctness problem from §4, but it inherits two new problems that are the entire subject of the rest of this chapter, and it is worth being precise about both before looking at the architecture that manages them:

  • The sweep itself costs I/O and CPU. To find dead tuples, something has to actually read every page of the heap (or at least every page that might contain one) and every page of every index that might reference one. That is not a free background tick — it competes with foreground queries for buffer-pool slots, disk bandwidth, and CPU, on the very same table that's under active load. Run it flat-out and you can measurably slow down the OLTP traffic you're trying to protect; this is exactly why the shipped design needs a cost-based throttle (vacuum_cost_limit, autovacuum_vacuum_cost_delay, §10) — an admission that "just scan it" is not good enough on its own.
  • If the sweep falls behind, dead tuples accumulate anyway — bloat by a different route. The sweep can only reclaim tuples older than the xmin horizon (§4). If the horizon itself stops advancing — a long-running transaction, an idle-in-transaction session, an unconsumed logical replication slot, or a standby with hot_standby_feedback on all pin it in place — the background process can run continuously and still reclaim nothing, because every dead tuple it finds is still newer than the horizon. This is the single most common real bloat incident in production (§11), and it is a direct, mechanical consequence of the design choice made in §5, not a bug in the sweep.

So the final architecture has to solve a genuinely two-sided problem: run often and cheaply enough that it doesn't fall behind under normal load, and throttle itself enough that it doesn't starve the foreground when it does run — while accepting that neither guarantee holds if something external (a stuck transaction) breaks the horizon assumption entirely. §7 is the architecture built to manage exactly that tension.

ARC 07 · FINAL ARCHITECTURE

Launcher, workers, and the three-phase lazy vacuum

The shipped design has two levels. At the top, a supervisor decides which table needs attention and when — that's the autovacuum launcher/worker machinery. Underneath, for any single table, a fixed three-phase algorithm — heap scan → index vacuum → heap vacuum — does the actual reclamation, in that strict order, for a reason that is worth deriving before you read a line of the implementation: an index entry must never be allowed to reference a heap line pointer that has since been marked reusable, because if it did, a later insert could reuse that slot for an unrelated tuple, and the stale index entry would silently resolve to the wrong row. Every index referencing a dead tid must be cleaned before that tid's heap slot becomes reusable — hence heap scan (find and freeze/mark candidates) must complete before index vacuum (strip references), which must complete before the second heap pass (actually free the slot). Not every dead tuple waits for a vacuum worker. If an UPDATE touches no column referenced by any index, and the new tuple fits on the same heap page as the old one, heap_update() (access/heap/heapam.c) can create a heap-only tuple (HOT, since 8.3) — the new version is chained to the old one via ctid with no new index entries at all. Opportunistic pruning (pruneheap.c's heap_page_prune, invoked whenever a backend dirties that page anyway) can then reclaim the old HOT tuple's line pointer immediately, with no index cleanup required, because no index ever pointed at it. HOT doesn't replace vacuum — it reduces how much work vacuum has to do, and specifically removes index bloat as a side effect of ordinary foreground traffic.

ARC 08 · INTERNAL IMPLEMENTATION

Line pointers, dead-tuple storage, and the three phases in full

Now the mechanism at the level you'd need to patch it: (a) what a line pointer actually is and its state machine, (b) the three-phase algorithm walked on a concrete heap+index, (c) how dead TIDs are stored in memory and why that storage structure is the single biggest scalability lever vacuum has, and (d) page skipping via the visibility/freeze map and aggressive vacuum.

(a) ItemId, LP_NORMAL, LP_DEAD, LP_UNUSED

Every heap page is a header, an array of fixed-size ItemId slots (line pointers) growing down from the top, and variable-length tuple data growing up from the bottom. An index entry never points directly at bytes on disk — it points at a (block, offset) pair, the offset being an index into that page's line-pointer array. That indirection is exactly what makes the whole reclamation scheme possible: the line pointer can change state — or even point somewhere else on the page — without forcing every index that references it to be rewritten, provided the state transitions obey strict rules. A line pointer is always in one of:

LP_NORMAL — live/dead-not-yet-pruned tuple, lp_off points at real tuple bytes
LP_DEAD — tuple bytes gone or ignorable, slot remembers "something used to be here"
LP_UNUSED — slot is free; a future insert may claim it

The critical invariant: a line pointer becomes LP_UNUSED — reusable — only after every index that might reference it has been vacuumed. Until then it sits at LP_DEAD: a tombstone that says "an index might still name this slot; don't you dare reuse it, but you no longer need to keep the tuple's actual data around." This is the entire reason the algorithm needs two heap passes around one index pass, not one.

(c) Where the dead TIDs live between phase 1 and phase 2

Phase 1 cannot vacuum indexes tuple-by-tuple as it finds dead rows — it has to finish scanning (or fill its budget), then hand a batch of collected TIDs to each index's bulk-delete routine, because a full index scan per dead tuple would be absurd. That means every dead TID found in phase 1 has to be held in memory until phase 2 runs. For most of PostgreSQL's history that memory was a single flat, sorted array of ItemPointerData (6 bytes each), allocated once up front and sized off maintenance_work_mem — but capped, in practice, around what a single palloc can hand back (historically bounded near 1 GB), which works out to a hard ceiling of roughly 178 million TIDs no matter how much memory you gave it. Once that array filled, vacuum had no choice but to stop the heap scan early, run an index vacuum + heap vacuum pass immediately to drain it, and then resume scanning — an extra full index scan per array-fill, on every index, for tables bloated enough to need it.

PostgreSQL 17 replaced that array with TidStore (src/backend/access/common/tidstore.c): an adaptive radix tree keyed on block number, storing the set of dead offsets per block far more compactly than 6 bytes/TID once TIDs cluster (which they do — dead rows bunch up on the same pages under real update patterns), with no artificial 1 GB ceiling — it scales with however much maintenance_work_mem you actually grant it, and can be built in shared memory for parallel vacuum workers to share directly. (d) Page skipping: the visibility map and aggressive vacuum

Scanning every page of a huge, mostly-unchanged table on every vacuum run would be wasteful, so lazy_scan_heap consults the visibility map (access/heap/visibilitymap.c, one bit added in 8.4, a second in 9.6) before touching a page at all. The all-visible bit means every tuple on that page is visible to every possible current and future snapshot — no dead tuples, nothing to prune — so a normal vacuum can skip the page's tuple-level scan entirely (it's also what lets index-only scans, added 9.2, skip a heap fetch for visibility checking). The all-frozen bit (9.6) is stricter: it means additionally every tuple's xmin is already frozen, so there is nothing left to do for wraparound purposes either — a normal vacuum can skip such a page completely, for both pruning and freezing.

That second bit exists because of a case the all-visible bit alone couldn't handle: a page can be all-visible (no dead tuples) while still holding un-frozen xmin values, which is exactly what an anti-wraparound (aggressive) vacuum — triggered when a table's age(relfrozenxid) passes autovacuum_freeze_max_age (default 200,000,000) — must still visit and freeze, or the whole point of running it is defeated. An aggressive vacuum is therefore defined precisely as one that may skip only all-frozen pages, never merely all-visible ones; a regular vacuum may skip anything all-visible. This is why an aggressive vacuum on a table that's been all-visible for years but never fully frozen can suddenly do far more I/O than any prior run on the same table — it's visiting pages every previous, non-aggressive vacuum was correctly allowed to ignore.

WHAT "SECOND HEAP PASS" ACTUALLY DOES

After every index has stripped its references to the collected TIDs, lazy_vacuum_heap_rel (or the equivalent inline path when there are no indexes to wait for) revisits exactly those heap pages, flips each reclaimed line pointer from LP_DEAD to LP_UNUSED, records the newly-freed space in the free space map (storage/freespace/freespace.c) so future inserts can find it, and — if the page now has no remaining dead tuples — sets its visibility-map bit. Notice what does not happen: the heap file does not shrink. LP_UNUSED means "available for reuse within this file," not "returned to the operating system." §12 covers why that distinction is the source of a very common misunderstanding about what VACUUM is supposed to do to a table's on-disk size.

ARC 09 · TRADEOFFS

The same deferred-cleanup problem, four ways

Every MVCC system faces exactly the problem §4 derived: old versions must outlive their invalidating transaction, and something must reclaim them once no snapshot needs them anymore. The systems below all chose where the old version lives and who reclaims it — no one avoided the problem entirely:

SYSTEMOLD-VERSION STORAGEWHAT THEY BOUGHTWHAT THEY PAID
PostgreSQLOld row stays in-place in the heap; a background sweep (autovacuum) prunes it later simple heap format no undo replay on crash reads never touch a log table bloat if sweep falls behind two-pass heap/index algorithm needs tuning at scale
MySQL / InnoDBOld versions reconstructed from undo log entries in rollback segments primary table stays compact in-place updates purge thread can fall behind → long history list undo tablespace growth mirrors Postgres's bloat problem, one layer down
OracleOld versions in the UNDO tablespace, retained per undo_retention tunable retention window SMON-assisted space management ORA-01555 "snapshot too old" if a long query outlives its undo undo tablespace sizing is its own tuning discipline
SQLiteWAL-mode: readers see an older WAL snapshot; no per-row MVCC no separate reclaimer process at all trivial single-writer model a long-held read transaction blocks WAL checkpointing — the same "who's still watching?" problem, at file-level granularity
zheap (Postgres, abandoned)Prototype: in-place updates + undo log, closer to InnoDB/Oracle's shape would have shrunk/eliminated update bloat smaller tables for update-heavy workloads undo replay on crash recovery is hard to get right interactions with logical decoding & snapshots shelved ~2021, complexity exceeded the payoff at the time

Read it as a proof by exhaustion again: every MVCC design needs a background reclaimer of some kind; the only real choice is where the "old version" is physically stored and how tightly that storage location couples to the primary data structure. PostgreSQL keeps old versions in the same file as live rows — simpler crash recovery (no undo log to replay before you can trust the heap), no extra I/O structure to maintain — at the cost of the primary table itself being where bloat shows up, directly, in the thing your queries scan. InnoDB and Oracle move that cost into a separate structure (undo/rollback segments), which keeps the primary table compact but doesn't remove the underlying accounting problem — it just relocates it, and gives it a different name (history list length, undo retention) with the same root cause: a snapshot somewhere hasn't let go yet.

ARC 10 · PERFORMANCE CHARACTERISTICS

The big-O, the throttle math, and the shared budget

The cost model for a single lazy vacuum run on one table is straightforward to state and easy to get wrong in practice: the heap scan is O(heap pages) — bounded further by how many pages the visibility map lets it skip — and each index vacuum pass is O(index size), because a B-tree bulk-delete (ambulkdelete) has no way to jump directly to entries for specific TIDs; it walks the whole structure checking each entry against the collected dead-TID set. That second fact is why the index phase, not the heap scan, dominates cost on tables with several large indexes — and why the number of passes (§8c) multiplies an already-expensive O(index size) term. A table needing 3 index-fill passes pays for 3 full scans of every index on it, not one.

Disk access pattern matters as much as big-O: the heap scan is sequential by block, which is cheap on both spinning disks and SSDs, but the visibility-map-guided skip pattern is what actually determines how much of that sequential scan happens at all — a table that is 95% all-visible only pays for scanning the 5% that changed since the last run, which is the entire point of the map. Aggressive vacuums forfeit part of that skip (§8d), which is exactly why they show up as I/O spikes relative to routine ones on the same table.

Foreground impact is bounded by cost-based vacuum delay. Each page a worker touches accrues cost — vacuum_cost_page_hit (already in shared buffers, default 1), vacuum_cost_page_miss (had to be read from disk, default 2 as of PG 16, lowered from 10 in earlier releases to reflect that a cache miss on modern storage is far cheaper relative to a hit than it was on spinning disks), and vacuum_cost_page_dirty (the page had to be written, default 20 — by far the most expensive unit, because dirtying triggers WAL and eventual checkpoint I/O). Once the running total for a worker exceeds vacuum_cost_limit (default 200; autovacuum_vacuum_cost_delay defaults to 2 ms since PG 12, versus 20 ms in older releases — a ten-fold increase in default aggressiveness), that worker sleeps for autovacuum_vacuum_cost_delay milliseconds before resuming. Crucially, the limit is not per-worker in isolation: PostgreSQL divides the effective cost budget across all currently active autovacuum workers, so raising autovacuum_max_workers alone does not raise total vacuum I/O throughput — it slices the same aggregate budget into more, smaller shares, which mostly helps when the bottleneck is which table gets attention rather than how fast any one table gets vacuumed.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: the replication slot nobody dropped

A logical replication consumer (a CDC pipeline, an analytics sync) disconnects and is never reconnected or cleaned up, but its replication slot stays registered. PostgreSQL keeps the slot's catalog_xmin/xmin pinned indefinitely, holding the entire cluster's xmin horizon at the moment the consumer vanished — exactly the scenario §6 predicted. Autovacuum keeps running on schedule, keeps scanning, and keeps finding the same tuples "not yet safe to remove." Tables that see moderate update traffic can bloat 10–50× over days to weeks before anyone notices — usually first as disk usage alerts, or as query plans that suddenly prefer sequential scans over indexes because the planner's row-count estimates no longer match a table whose live rows are now a small fraction of its pages. Diagnosis: pg_replication_slots shows a slot with active = false and a very old restart_lsn/xmin; cross-reference against pg_stat_activity and pg_stat_replication to confirm nothing is consuming it. Fix: drop the orphaned slot (pg_drop_replication_slot) or fix the consumer so it reconnects — then autovacuum's next pass on the affected tables reclaims the entire backlog at once, which is itself worth pacing (see incident 3).

Incident 2: a billion-row table that "never" gets vacuumed

A table sized to a billion rows sits on the default autovacuum_vacuum_scale_factor = 0.2 and autovacuum_vacuum_threshold = 50. The trigger formula is dead_tuples > threshold + scale_factor × reltuples — at a billion rows that's roughly 200 million dead tuples before autovacuum even fires. For an update-heavy table that is an enormous, multi-gigabyte backlog to let build before cleanup starts, and once it does start, the run itself is correspondingly huge and slow, competing with foreground traffic for the whole duration — so operators sometimes see it as "autovacuum never seems to run" when in fact it is running, extremely rarely, on a very long delay, exactly as configured. Fix: per-table overrides via ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_cost_delay = 0, autovacuum_vacuum_cost_limit = 1000) (or similar) — dropping the scale factor makes the trigger fire on a fixed few-million-row backlog regardless of table size, and loosening the cost delay/limit for that one table lets its (now much smaller, more frequent) runs finish before the next backlog builds. This is the standard "large table" tuning pattern: scale-factor-based triggering is calibrated for small-to-medium tables and needs an absolute floor on huge ones.

Incident 3: an anti-wraparound storm across many tables at once

A cluster with many tables created or bulk-loaded around the same time — a common pattern after a migration or a data warehouse refresh — can have their relfrozenxid ages cross autovacuum_freeze_max_age (default 200,000,000) within a short window of each other. Every one of those tables now qualifies for an aggressive vacuum simultaneously, and aggressive vacuums cannot skip all-visible-but-not-all-frozen pages (§8d) — so each one does substantially more I/O than a routine pass would, and several run concurrently (bounded by autovacuum_max_workers), producing a visible I/O and CPU spike that lines up suspiciously with "nothing changed in the application." Mitigation: proactively run VACUUM (FREEZE) on large, slow-changing tables during a maintenance window well before they'd hit the threshold organically, so freezing work is spread out on your schedule rather than the wraparound clock's; alternately, raise vacuum_cost_limit/lower autovacuum_vacuum_cost_delay specifically during the maintenance window so the forced runs complete faster once they do start. The underlying lesson is that anti-wraparound vacuum is not optional or skippable — deprioritizing it only delays it into a larger, more synchronized event.

Four simplified-but-structurally-faithful excerpts. First, the trigger math every autovacuum decision reduces to — this is the function that decides whether your table gets touched at all:

Cautovacuum.c — relation_needs_vacanalyze(), simplified
static void
relation_needs_vacanalyze(Oid relid, AutoVacOpts *opts, PgStat_StatTabEntry *tabentry,
                         bool *dovacuum, bool *doanalyze, bool *wraparound)
{
    float vac_scale_factor = opts->vacuum_scale_factor >= 0
        ? opts->vacuum_scale_factor : autovacuum_vac_scale;      /* default 0.2 */
    float vac_base_thresh   = opts->vacuum_threshold >= 0
        ? opts->vacuum_threshold : autovacuum_vac_thresh;        /* default 50  */

    float reltuples = estimated_live_tuples(relid);   /* from pg_class */
    float vacthresh = vac_base_thresh + vac_scale_factor * reltuples;

    /* The formula every "why isn't autovacuum running" incident reduces to:
     * a table needs (threshold + scale_factor × reltuples) dead rows
     * before it is even a CANDIDATE for a routine vacuum.             */
    *dovacuum = (tabentry->dead_tuples > vacthresh);

    /* Independent of dead-tuple count entirely: age-based forcing.  */
    TransactionId relfrozenxid = get_relfrozenxid(relid);
    if (TransactionIdIsValid(relfrozenxid) &&
        TransactionIdPrecedesOrEquals(relfrozenxid + autovacuum_freeze_max_age,
                                        ReadNextTransactionId()))
    {
        *dovacuum = true;
        *wraparound = true;      /* AGGRESSIVE: cannot skip all-visible-only pages */
    }

    float anl_scale_factor = opts->analyze_scale_factor >= 0
        ? opts->analyze_scale_factor : autovacuum_anl_scale;     /* default 0.1 */
    float anlthresh = (opts->analyze_threshold >= 0
        ? opts->analyze_threshold : autovacuum_anl_thresh) + anl_scale_factor * reltuples;
    *doanalyze = (tabentry->changes_since_analyze > anlthresh);
}

Next, the conceptual core of phase 1's line-pointer classification — real vacuum pruning is more involved (multi-tuple HOT chains, multiple visibility outcomes), but this captures the decision that matters:

Cpruneheap.c — heap_page_prune(), conceptual core
void
heap_page_prune(Relation rel, Buffer buf, TransactionId oldest_xmin, TidStore *dead_items)
{
    Page page = BufferGetPage(buf);
    int nline = PageGetMaxOffsetNumber(page);

    for (int off = 1; off <= nline; off++)
    {
        ItemId lp = PageGetItemId(page, off);
        if (!ItemIdIsUsed(lp))
            continue;

        HeapTupleHeader tup = (HeapTupleHeader) PageGetItem(page, lp);

        /* HEAPTUPLE_DEAD: xmax committed AND older than the xmin horizon —
         * no snapshot anywhere can still need this version.            */
        if (HeapTupleSatisfiesVacuum(tup, oldest_xmin, buf) == HEAPTUPLE_DEAD)
        {
            ItemIdSetDead(lp);                  /* LP_NORMAL -> LP_DEAD  */
            TidStoreSetBlockOffsets(dead_items, BufferGetBlockNumber(buf), off);
        }
        /* HEAPTUPLE_RECENTLY_DEAD: xmax committed but NEWER than the
         * horizon — some snapshot might still need it. Left alone.     */
    }
    /* Note: a LP_DEAD slot here still blocks reuse until every index
     * has had its matching entries stripped in phase 2.                */
}

Finally, the second heap pass — the only code path allowed to turn LP_DEAD into LP_UNUSED, and only because it runs strictly after index vacuum has completed:

Cvacuumlazy.c — lazy_vacuum_heap_page(), conceptual core
static void
lazy_vacuum_heap_page(Relation rel, BlockNumber blkno, Buffer buf,
                       TidStore *dead_items, VacRelStats *stats)
{
    Page page = BufferGetPage(buf);

    /* PRECONDITION, enforced by call order in the driver: every index
     * on `rel` has already run ambulkdelete() against `dead_items`.
     * If that hasn't happened, calling this early is a correctness bug. */
    OffsetNumber *offsets = TidStoreGetBlockOffsets(dead_items, blkno);

    for (int i = 0; offsets[i] != InvalidOffsetNumber; i++)
    {
        ItemId lp = PageGetItemId(page, offsets[i]);
        ItemIdSetUnused(lp);                 /* LP_DEAD -> LP_UNUSED, now reusable */
    }

    PageRepairFragmentation(page);          /* compact free space on the page   */
    MarkBufferDirty(buf);
    XLogInsert(RM_HEAP2_ID, XLOG_HEAP2_VACUUM);

    FreeSpaceMapUpdate(rel, blkno, PageGetFreeSpace(page));   /* FSM: this page has room */
    if (PageIsAllVisible(page, ...))
        visibilitymap_set(rel, blkno, ...VM_ALL_VISIBLE...);
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Two heap passes around one index pass isn't a workaround — it's the only order that's ever correct. Any implementation that reused a line pointer before every index was cleaned would be one INSERT away from a stale index entry pointing at unrelated data. 2. Cost-based delay instead of a hard I/O rate limiter — the cost accounting (hit/miss/dirty) approximates the actual expense of different page operations rather than a blunt "N MB/sec" cap, so a run touching mostly cached, clean pages proceeds fast while one forcing writes (dirty pages) is throttled harder automatically, without the operator having to characterize the workload in advance. 3. Per-table reloptions exist because one global scale factor cannot be right for both a 10,000-row config table and a 10-billion-row events table — the formula in relation_needs_vacanalyze is linear in reltuples, and linear formulas need a knob per table once the table sizes span many orders of magnitude, which real schemas always do.
