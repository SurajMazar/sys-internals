ARC 01 · THE PROBLEM

A tree of arbitrary operators, one uniform way to run it

The planner (chapter 16) hands the executor a Plan tree that can be almost any shape: a lone sequential scan, or a six-level tree mixing scans, hash joins, sorts, aggregates, and a LIMIT on top. The executor's job is to actually produce rows from that tree — correctly, in whatever order the plan specifies, without knowing in advance how many rows the caller actually wants, and without special-casing every possible combination of node types. That last constraint is the hard part: a hash join's output is a sort node's input is an aggregate's input, and none of those three should need to know anything about which specific node feeds it or consumes from it.

This is a general problem in systems that compose: how do you let independently-implemented components connect in arbitrary trees without writing O(n²) glue code for every pair? The database answer, and the answer this chapter derives from scratch, is a uniform protocol every node obeys regardless of its internal complexity — and the specific shape of that protocol (pull, one tuple at a time) has consequences that show up in EXPLAIN ANALYZE's timings, in why LIMIT queries return instantly, and in why an entire category of database engines (DuckDB, ClickHouse) exists specifically to do something else instead.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Every node type you will ever read about — SeqScan, HashJoin, Sort, Agg, Gather — is an implementation of exactly the same three-function interface this chapter derives in §5 and details in §8. Once you understand the interface, reading a new node's source file is a matter of understanding what state it keeps between calls, not learning a new execution model. That is precisely why src/backend/executor/ has over forty node*.c files and almost no node-to-node special-case code connecting them.

DEEP CONTEXT · WHY "VOLCANO"

Goetz Graefe and William McKenna's Volcano project (Colorado State/Oregon, published 1990-1993) wasn't primarily about the iterator interface itself — open()/next()/close() already existed in System R's access-method layer over a decade earlier. Volcano's real contribution was showing that this interface generalizes cleanly to parallel execution via an "exchange" operator that could sit between any two nodes and fan work across processes — which is exactly the shape PostgreSQL's Gather node (§8g) takes twenty-plus years later. The name stuck to the whole iterator paradigm because Volcano's paper was the one that made the model's extensibility legible enough to build a research industry on top of.

ARC 03 · NAIVE SOLUTION

Attempt #1: materialize every stage completely

The simplest possible execution strategy: run each operator to completion, writing its entire output into memory (or a temp file) before the next operator starts reading. A five-stage plan becomes five fully materialized intermediate results, connected in sequence — no interleaving, no partial results, just batch after batch.

Cmaterialize_everything.c — the strawman, annotated
Tuple **
run_seqscan_fully(Relation rel) {
    Tuple **out = palloc(sizeof(Tuple*) * estimate_rows(rel));
    int n = 0;
    while (has_more_pages(rel))
        out[n++] = read_next_tuple(rel);   /* the WHOLE table, in memory */
    return out;                          /* only NOW does the caller get anything */
}

Tuple **
run_hashjoin_fully(Tuple **outer, int n_outer, Tuple **inner, int n_inner) {
    HashTable *ht = build_hash_table(inner, n_inner);   /* fully materialized input */
    Tuple **out = palloc(sizeof(Tuple*) * n_outer * 2);  /* guess capacity */
    int n = 0;
    for (int i = 0; i < n_outer; i++)
        n += probe_and_append(ht, outer[i], out, n);
    return out;                          /* the WHOLE join result, in memory */
}

This gets one thing unambiguously right: it is trivially easy to reason about — every operator has a clean, total function signature (array in, array out), no partial state to track across calls, no protocol to implement beyond "return everything." It is also, not coincidentally, how a first-year systems course would naturally implement a pipeline of transformations, and how many batch ETL tools genuinely operate stage by stage on purpose.

ARC 04 · WHY IT FAILS

Two failures, quantified: memory and latency

Take a five-stage plan — SeqScan → HashJoin → Sort → Agg → Limit 10 — over a table with 10,000,000 rows at roughly 200 bytes/row once projected. Full materialization means:

  • Memory: the scan's output alone is 10,000,000 × 200 bytes ≈ 2 GB, held in memory (or spilled to a temp file, which is its own I/O cost) before the hash join even starts consuming it. The hash join's own output, plus the sort's materialized input and output, plus the aggregate's input, can easily multiply that 2 GB by 3-4× of simultaneously-live intermediate state for one single query — and PostgreSQL runs this multiplied by however many backends have a similar query in flight (chapter 16's peak-memory equation, again).
  • Latency to first row: the final LIMIT 10 only needs ten rows. Under full materialization, it cannot receive any of them until the aggregate has finished, which cannot finish until the sort has finished, which cannot finish until the hash join has fully drained the scan — meaning the client waits for the entire 10,000,000-row scan and join to complete before seeing row one, even though the true answer only needed a handful of rows and could, in principle, stop almost immediately.
THE NUMBERS

If each of the five stages needs even 200 ms to fully materialize its output at this scale, full materialization's time-to-first-row is the sum: on the order of a second before the client sees anything, for a query whose true answer (10 rows, after a selective join) might be producible in a small fraction of that if the executor could stop early and never fully materialize any stage. And that's the good case — many real plans have a LIMIT or an EXISTS semantics that could, correctly, stop after the very first row, turning a full 2GB-plus materialization into pure waste.

The failure isn't that materialization is a bad computational strategy in general — Postgres's own hash join does materialize its inner side (§8d) precisely because that specific case needs it. The failure is materializing every stage unconditionally, when most stages should be able to hand off one tuple at a time and let the consumer decide how many it actually needs.

ARC 05 · THE VOLCANO MODEL

Push vs pull vs the naive batch — and why pull wins

Two live alternatives to full materialization exist, and the design question is which direction data flows and who's in control. Step through them.

Choosing the execution modelSTEP-BY-STEP

The winning shape is the one PostgreSQL has used since its first executor: every node implements open()/next()/close() — in PostgreSQL's actual naming, ExecInitNode(), ExecProcNode(), ExecEndNode(). A parent calls its child's next() whenever it needs one more tuple; the child recurses into its own children exactly the same way; a leaf scan node satisfies the call from a buffer or disk read. The whole tree is driven from the top by demand, one tuple at a time, and no node needs to know anything about which specific node types are above or below it — only that whatever is below answers next() with one tuple or an end-of-data signal, and whatever is above will eventually call next() again.

ARC 06 · WHY THAT STILL HURTS

One function call per tuple per node is not free

Pulling one tuple through n nodes means n function calls per tuple — and modern CPUs are extremely good at processing data but comparatively bad at unpredictable control flow. Three concrete costs follow directly from the tuple-at-a-time granularity:

  • Call overhead multiplies by row count. A five-node plan over ten million rows is fifty million function calls, each with its own stack frame setup, return address, and (for virtual/polymorphic dispatch) an indirect branch the CPU's branch predictor has to guess. That overhead is pure tax — it does no useful work, and it scales with row count regardless of how simple each node's per-row logic actually is.
  • Poor instruction-cache locality. Each call jumps to a different node's code — ExecScan, then ExecHashJoin, then ExecSort — and back, repeatedly, for every single tuple. The CPU's instruction cache is constantly evicting one node's code to fetch another's, instead of staying hot on one tight loop the way a single-operator batch pass would.
  • No SIMD. Because each node processes exactly one tuple's worth of data per call, there is no opportunity to apply a single vector instruction across many rows at once — the fundamental enabling condition for SIMD is having a batch of homogeneous data in hand at once, which the pure per-tuple Volcano model never provides.
WHY THIS IS EXACTLY WHY VECTORIZED ENGINES EXIST

DuckDB, ClickHouse, and the broader "vectorized execution" family (tracing back to MonetDB/X100) process tuples in batches — typically hundreds to a couple thousand at a time — per node call, not one at a time. A single call to a vectorized filter operator applies its predicate across an entire batch using a tight, SIMD-friendly loop, amortizing the call overhead across the whole batch and keeping the CPU in one hot code path far longer. For scan- and aggregate-heavy analytical workloads, this routinely produces order-of-magnitude throughput differences over a pure per-tuple Volcano executor — not because Postgres's executor is badly written, but because tuple-at-a-time is a structurally different point on the same tradeoff curve this section derives, optimized for something else (see below).

PostgreSQL's actual mitigation is narrower but real: ExecProcNode function-pointer specialization. Rather than dispatching every call through one large switch over node tag values (a branch the CPU would have to re-predict every time, across every node type in the plan), ExecInitNode() sets each PlanState's ExecProcNode field directly to the concrete function for its node type once, at initialization. Every subsequent call is then a direct indirect call to a function the branch predictor can specialize per call site, rather than a re-dispatched switch — a real, measurable win that costs nothing in generality, but one that only removes the dispatch overhead, not the fundamental one-tuple-per-call granularity vectorized engines avoid entirely.

ARC 08 · INTERNAL IMPLEMENTATION

The real protocol, the real spill logic, the real parallelism

Eight pieces: (a) the protocol itself, (b) the tuple carrier, (c) Sort and its external merge, (d) Hash Join and multi-batch spilling, (e) Nested Loop and rescan, (f) Materialize and Memoize, (g) parallel query, (h) JIT.

(a) The protocol: ExecInitNode / ExecProcNode / ExecEndNode

Every node type registers three functions. ExecInitNode() (execProcnode.c) walks the Plan tree once, top-down, allocating a matching PlanState for each Plan node, recursively initializing children first, and — critically — assigning that node's concrete ExecProcNode function pointer (the specialization from §6). ExecProcNode(PlanState*) is then the single call site used everywhere in the executor to pull one tuple from any node, regardless of type — it simply invokes whatever function pointer ExecInitNode installed. ExecEndNode() tears down each node's private state (closing scan descriptors, freeing hash tables) in the same recursive shape, bottom-up. This three-function shape is the entire contract; everything else in this chapter is one node type's private implementation of it.

(b) TupleTableSlot: carrying a tuple without copying it

A TupleTableSlot is the object every next() call returns — not the raw bytes of a tuple, but a reference-counted, reusable container that can hold a tuple in one of several physical forms, chosen for whichever is cheapest at that point in the plan: a virtual slot holds a plain array of already-deconstructed Datum/isnull pairs (no on-disk tuple format at all — cheapest when a node just computed values directly); a heap slot wraps a full on-disk-format HeapTuple, typically pointing straight into a shared buffer page without copying; a minimal slot is a heap tuple stripped of some header fields, used for tuples that will only ever be looked at internally (e.g. as a hash join's stored inner tuples) and never need to look like a real on-disk row. Deferring the choice of physical form — and, within a heap tuple, deferring column deforming (parsing the tuple's byte layout into individual Datums) until a specific column is actually referenced — is what keeps a wide table with a narrow WHERE clause cheap: columns nobody asks for are never parsed out of the tuple at all.

(c) Sort: quicksort in memory, external merge on disk

tuplesort.c starts by accumulating incoming tuples in memory and sorting them with an in-memory quicksort (specifically an introsort variant, falling back to heapsort to bound worst-case behavior) whenever the full input fits within work_mem. When it doesn't, tuplesort.c switches to external merge sort: tuples are accumulated up to the memory limit, sorted in memory, and written out as one sorted run to a temp file; this repeats until the whole input has been consumed as a sequence of sorted runs on disk; then a k-way merge — using a binary heap keyed on each run's current head tuple — merges all runs simultaneously, always emitting the globally smallest remaining tuple next, in a single sequential pass over every run's data. This is why sort spilling is a graceful, not catastrophic, degradation: the I/O pattern is sequential writes followed by a sequential (heap-driven) merge read, not random access, and the algorithm's correctness is completely unaffected by whether it took the in-memory or external path — only its speed changes.

Incremental Sort (PostgreSQL 13+) exploits input that's already sorted on a prefix of the required sort key — for example, an index scan delivering rows sorted by (tenant_id, created_at) when the query needs ORDER BY tenant_id, amount. Rather than sorting the whole input as one undifferentiated batch, it sorts each tenant_id group independently, as soon as that group is fully seen, which both reduces the working set that needs to be resident at once and lets rows start flowing to the parent node long before the entire input has been read — the streaming, incremental spirit of the Volcano model, applied inside a single node that would otherwise be a full blocking materialization point.

(d) Hash Join: build, probe, and the multi-batch spill

nodeHashjoin.c runs in two phases. Build: MultiExecHash() pulls every tuple from the inner (typically smaller) child to completion — this is the one place a hash join fully materializes its input, deliberately, because a hash table needs every key present before any probe can be trusted to be complete — hashing each tuple's join key and inserting it into an in-memory hash table sized against work_mem. Probe: the outer child is then pulled one tuple at a time, in true Volcano fashion; each outer tuple's join key is hashed and looked up in the same hash table, emitting one output tuple per match.

When the inner side's estimated (or actual) size doesn't fit work_mem, PostgreSQL doesn't fail — it goes multi-batch: both the inner and outer sides are partitioned by additional bits of the same hash value into N batch files up front, such that any two tuples that could possibly join are guaranteed to land in the same batch (their join keys hash identically on the partitioning bits). Batch 0 is handled in memory immediately; batches 1..N-1 are processed afterward, one at a time, each repeating the same build-then-probe logic against its own slice of the data, small enough to fit — trading one pass of extra partitioning I/O for bounded memory regardless of how badly the size estimate was wrong.

THE SKEW OPTIMIZATION

Hash collisions are unavoidable in principle, but PostgreSQL specifically defends against the common, predictable case of a heavily skewed join key: before the main build phase, it consults the outer relation's pg_statistic MCV list (chapter 16's machinery, reused here) and preloads dedicated skew buckets for the handful of most common outer values, sized generously so those specific hot values never trigger a costly bucket-chain walk or (worse) push the table into multi-batch territory on their own. It is a direct, small-scale reuse of the planner's own statistics infrastructure inside the executor — a rare case of the two systems this course splits across two chapters actually sharing a data structure at runtime.

(e) Nested Loop: parameterized inner scans and ExecReScan

A nested loop with an indexed inner side is the one join method that never materializes anything extra: for every outer tuple, the executor re-invokes the inner side as a parameterized path — the inner index scan's search key is bound to the current outer tuple's join column, and the inner node is asked to restart. That restart runs through ExecReScan(): rather than a full ExecEndNode()/ExecInitNode() cycle (expensive — it would reopen files, rebuild state), ExecReScan resets only what changed (the new parameter value, the scan's position) and reuses everything else (open relations, allocated buffers). This is what makes nested loop with a good inner index the cheapest possible join for a small outer side: O(N × log M) or better, with no build phase and no extra memory, at the cost of re-paying the inner scan's per-call overhead N times — the classic tradeoff that makes it disastrous when N (the outer row count) is badly underestimated, exactly as chapter 16's independence-assumption incidents describe.

(f) Materialize and Memoize: caching a subplan's output

Materialize is the executor's explicit, opt-in version of the naive strawman from §3: it fully buffers its child's output the first time through, specifically so that a repeated rescan (typically the inner side of a nested loop that doesn't have a usable index, or a merge join's inner side) can be replayed from memory instead of recomputing an expensive child subplan from scratch on every outer iteration. Memoize (PostgreSQL 14) is a more targeted version of the same idea: rather than caching one subplan's entire output, it caches parameterized results keyed by the actual parameter value bound on each nested-loop iteration, with an LRU-style eviction policy bounded by work_mem — so when a nested loop repeatedly probes the same small set of distinct outer values (a common pattern once DISTINCT/skewed foreign keys are involved), Memoize turns what would have been N full inner-scan re-executions into a handful of real executions plus many cheap cache hits, without materializing the entire inner relation the way a plain Materialize node would.

(g) Parallel query: the same protocol, across processes

A Gather node is the boundary between serial and parallel execution: everything below it in the plan tree can run concurrently across multiple background workers; everything above it (including Gather itself) runs serially in the original backend, now called the leader. The leader launches workers via dynamic shared memory (a DSM segment created fresh for this query, distinct from the cluster's permanent shared memory segment), into which it serializes the plan subtree, parameter values, and a shared coordination structure each worker needs to reconstruct its own copy of the relevant PlanState tree independently.

A Parallel Seq Scan's workers share a single atomic block-number counter in that DSM segment: each worker claims the next unclaimed block, scans it, and goes back for another — a self-balancing work distribution with no static partitioning and no coordinator overhead beyond one atomic increment per block claimed. Parallel Hash Join (PostgreSQL 11+) goes further: rather than each worker building its own private copy of the inner hash table (wasteful — the same work repeated N times), all workers cooperatively build one shared hash table in the DSM segment, synchronized via barriers so that probing only begins once every worker agrees the build phase is complete.

Tuples flow from workers back to the leader through shm_mq — fixed-size shared-memory ring buffers, one per worker, with the reading and writing sides coordinating via latches (PostgreSQL's cross-process condition-variable-like primitive built on a signal-plus-poll/epoll wait): a worker blocked because its queue is full, or a leader blocked because every queue is empty, sleeps on a latch rather than spinning, and is woken the instant the other side makes progress. The leader itself plays a dual role it must budget for correctly: it is both the coordinator draining worker queues and, if the plan allows, a full participant that executes a share of the parallel portion itself rather than sitting idle waiting on workers it spawned. Gather Merge is the ordered variant of Gather: when each worker's output arrives pre-sorted (typically because the parallel portion ends in a per-worker sort or an index scan), Gather Merge performs a k-way merge across the workers' streams — the exact same heap-driven merge idea from §8c's external sort, just merging across processes instead of across temp files.

Not every function can safely run this way: a function is parallel-unsafe if it reads or writes session-local or transaction-local state a worker wouldn't share correctly with the leader (sequence advancement semantics, temp table access in some contexts, certain non-reentrant C library calls) — such functions force the planner to keep the plan (or the relevant subtree) fully serial, silently forfeiting parallelism the moment one is present anywhere in the parallel portion, which is exactly §11's third incident.

(h) JIT: past interpretation entirely

Ordinary expression evaluation (a WHERE clause, a projection, an aggregate transition function call) runs through ExecInterpExpr() — a generic tree-walking interpreter that dispatches through each expression step at runtime, one step at a time, for every single tuple. For a simple predicate evaluated once, that overhead is negligible; for a complex expression evaluated across a hundred million rows in an analytic query, the interpreter's per-step dispatch and generic tuple-deforming logic becomes a measurable fraction of total query time.

PostgreSQL 11+ can instead JIT-compile a query's expression evaluation and tuple deforming into native machine code via LLVM (src/backend/jit/llvm/): at plan execution start, PostgreSQL emits LLVM IR (intermediate representation) specific to that query's actual expressions and column layout, and LLVM compiles it down to native instructions — specialized for exactly this query, with no generic dispatch loop left at all. Small, frequently-called internal C functions (a type's comparison function, a cast) can even be inlined directly from bitcode PostgreSQL ships alongside its binaries, eliminating a real function-call boundary that the interpreter would otherwise have paid on every tuple.

This isn't free, so it's gated by jit_above_cost (only engage JIT once the planner's own total cost estimate exceeds a threshold) and separate, higher thresholds for the more expensive inlining and optimization passes (jit_inline_above_cost, jit_optimize_above_cost) — LLVM's own compilation and optimization work takes real, non-trivial time, and for a query that turns out to execute quickly despite a high cost estimate (chapter 16's misestimation problem, again), the classic JIT failure mode is compilation time exceeding the entire execution time it was meant to save — a query that would have finished in 50 ms interpreted instead spends 200 ms compiling code for itself before running in 10 ms, net slower. This is precisely why JIT's cost thresholds exist and why some production workloads with many short, frequently-executed queries but occasionally high cost estimates disable it outright (§11's second incident).

ARC 10 · PERFORMANCE CHARACTERISTICS

Where the executor's time actually goes

  • Per-tuple overhead is O(1) per node per tuple in the best case — but that constant includes an indirect function call, slot management, and (pre-JIT) interpreted expression dispatch, which dominates for narrow, simple-predicate queries over many rows exactly as §6 derived.
  • Sort: in-memory quicksort is the familiar O(n log n) comparisons; external merge sort adds O(n) sequential I/O for the initial run-writing pass plus O(n log k) for the k-way merge (with a binary heap of size k, the run count) — the I/O pattern is fully sequential in both directions, which is exactly why sort spilling degrades gracefully on both spinning disks and SSDs rather than falling off a cliff.
  • Hash join: single-batch is O(N + M) — build the inner in O(M), probe the outer in O(N), both with small constants as long as the hash table's working set stays resident. Once it doesn't, cache misses on bucket-chain walks turn "small constant" into "cache-miss-dominated," and multi-batch adds a full extra sequential read-and-write pass over both inputs for the partitioning step.
  • Nested loop: O(N × M) in the worst case (no usable inner index), collapsing to roughly O(N × log M) with one, and to near O(N) amortized when Memoize's cache hit rate is high against a skewed parameter distribution — three very different performance regimes hiding behind one node name, which is exactly why EXPLAIN ANALYZE's loop count matters as much as its row count.
  • Parallel query trades per-worker CPU time for wall-clock time, bounded by Amdahl's law on whatever portion of the plan sits above the Gather and must run serially in the leader, plus real coordination overhead (DSM setup, latch wakeups, tuple-queue serialization) that makes parallelism a net loss below some data-size threshold — which is exactly why the planner (chapter 16) costs parallel paths explicitly rather than always preferring them.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents, one executor each

Incident 1: work_mem tuned globally, spilling under concurrency

A team raises work_mem cluster-wide from 4 MB to 256 MB to fix a slow reporting query's external sort. The reporting query gets faster. Two weeks later, a burst of concurrent OLTP connections each runs a query with two or three sort/hash nodes, and the backend fleet's total in-flight work_mem commitment — chapter 16's peak-memory equation, active_backends × plan_nodes × work_mem — blows past physical RAM, and the OOM killer starts choosing victims (chapter 1's crash protocol, triggered from here). Fix: work_mem is a per-operation, per-backend budget, not a global one — set it conservatively at the cluster level and raise it per-session (SET work_mem) only for the specific reporting connections that need it, exactly the surgical fix the original problem actually called for.

Incident 2: JIT compilation time exceeding the query it was meant to speed up

After upgrading to a PostgreSQL version with JIT enabled by default, a team notices a class of short, frequent queries — individually cheap to execute, but with a planner cost estimate that happens to sit just above jit_above_cost because of a wide SELECT * projection — get measurably slower, not faster. EXPLAIN (ANALYZE, BUFFERS) reveals a JIT block reporting real but substantial "Functions" and "Inlining"/"Optimization" time that exceeds the query's own execution time by several multiples: the query was fast enough that LLVM never got a chance to earn back its own compilation cost. Fix: raise jit_above_cost (and, separately, jit_inline_above_cost/jit_optimize_above_cost) well above this workload's typical cost estimates, or disable JIT entirely (jit=off) for connection pools serving predominantly short OLTP-shaped queries, reserving it for genuinely long-running analytic connections where the amortization actually works in JIT's favor.

Incident 3: a parallel-unsafe function silently serializes an entire report

A reporting query that used to run in parallel across eight workers suddenly runs serially after a schema change adds a new computed column backed by a small PL/pgSQL helper function that reads a session-local configuration setting via current_setting() in a way the planner cannot prove is parallel-safe. No error is raised — the planner simply stops generating parallel paths for any portion of the plan that would need to call this function, and the query silently reverts to a single-process, wall-clock-bound execution that takes eight times as long as it used to, with no log message pointing at the cause. Fix: mark genuinely safe functions explicitly with PARALLEL SAFE (the conservative default is UNSAFE for any function PostgreSQL cannot prove otherwise), and audit newly added function calls in hot report queries with EXPLAIN's worker count whenever a previously-parallel query's plan shape changes after a schema or function update.

ARC 12 · INTERVIEW-LEVEL QUESTIONS

First, the dispatch mechanism §6 described — installed once, called everywhere:

CexecProcnode.c — ExecInitNode() installs the specialized pointer
PlanState *
ExecInitNode(Plan *node, EState *estate, int eflags)
{
    PlanState *result;
    switch (nodeTag(node)) {
        case T_HashJoin:
            result = (PlanState *) ExecInitHashJoin((HashJoin *) node, estate, eflags);
            break;
        case T_SeqScan:
            result = (PlanState *) ExecInitSeqScan((SeqScan *) node, estate, eflags);
            break;
        /* ... one case per node type ... this switch runs ONCE per node,
         * not once per tuple -- that's the whole point.              */
    }
    /* Every node type's Init function sets its OWN ExecProcNode
     * pointer directly, e.g.: */
    // hjstate->js.ps.ExecProcNode = ExecHashJoin;
    return result;
}

/* The ONLY call site the rest of the executor ever uses to pull
 * a tuple, regardless of node type: */
static inline TupleTableSlot *
ExecProcNode(PlanState *node)
{
    if (node->chgParam != NULL)
        ExecReScan(node);          /* parameters changed since last pull */
    return node->ExecProcNode(node);  /* direct call -- no switch, no re-dispatch */
}

Now the hash join's probe loop, where build/probe and the batch/skew logic in §8d actually live:

CnodeHashjoin.c — ExecHashJoin(), simplified
static TupleTableSlot *
ExecHashJoin(PlanState *pstate)
{
    HashJoinState *node = (HashJoinState *) pstate;

    if (!node->hj_HashTable) {
        /* First call: fully drain the inner child ONCE. */
        node->hj_HashTable = ExecHashTableCreate(...);
        MultiExecHash((HashState *) innerPlanState(node));  /* the one blocking phase */
    }

    for (;;) {
        if (!node->hj_MatchedOuter) {
            TupleTableSlot *outer = ExecProcNode(outerPlanState(node)); /* pull, Volcano-style */
            if (TupIsNull(outer)) {
                if (!ExecParallelHashJoinNewBatch(node))  /* more batch files to process? */
                    return NULL;                        /* truly done */
                continue;                              /* start next batch's build+probe */
            }
            node->hj_CurTuple = ExecHashGetHashValue(outer);
        }
        if (ExecScanHashBucket(node, econtext)) {
            return ExecProject(node->js.ps.ps_ProjInfo); /* one match -> one tuple up */
        }
        /* no more matches for this outer tuple; loop back for another */
    }
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Dispatch once, not per tuple. The switch in ExecInitNode runs a number of times proportional to plan node count, not row count — moving the branch-heavy work off the hot, per-tuple path entirely. 2. Blocking phases are explicit and rare. Hash join's build phase is the one deliberate exception to pure streaming in this whole chapter, and the code makes that exception structurally visible (a one-time if guard) rather than hiding it inside a general-purpose "materialize everything" abstraction — precisely the naive strawman §3 rejected, used surgically instead of universally. 3. Batch/skew logic reuses existing machinery rather than inventing new structures — batch files are ordinary temp files, skew buckets reuse the planner's own MCV statistics — minimizing the amount of genuinely new, unproven code in a path this performance-critical.
