POSTGRESQL INTERNALS · CHAPTER 05

MVCC I: Tuple Versions,
Snapshots & Visibility

Every row you have ever read from PostgreSQL without waiting for a writer, and every writer you have ever run without waiting for a reader, was arbitrated by one C function reading a handful of bytes on a tuple header. This chapter opens that tuple header, the snapshot structure a backend carries in its own memory, and the shared transaction log they are both compared against — and derives, from the single constraint "readers never block writers, writers never block readers," exactly why UPDATE never overwrites a byte of a live row in place.

ARC 01 · THE PROBLEM

A reader and a writer want the same row at the same instant

PostgreSQL's documentation makes a blunt promise: "readers never block writers, and writers never block readers." Treat that sentence as an engineering constraint, not a marketing line, and the rest of the transaction subsystem — tuple headers, snapshots, the commit log, vacuum — falls out as a forced consequence.

Take the smallest possible race. Transaction A runs SELECT balance FROM accounts WHERE id = 1 at the exact instant transaction B runs UPDATE accounts SET balance = balance - 100 WHERE id = 1, and B has not yet committed. Two irreconcilable demands land on the same eight bytes of storage: B needs to mutate balance; A needs to read a consistent value without waiting for B to finish, and without seeing an in-flight, possibly-to-be-rolled-back write. A traditional two-phase-locking (2PL) engine resolves this by making A wait — SELECT takes a shared lock, UPDATE needs an exclusive lock, and the lock manager (src/backend/storage/lmgr, chapter 8) serializes the two. That is correct. It is also not the guarantee above — A blocked.

Unpack the requirement and five demands pull in different directions at once:

  • Correctness under concurrency — a reader must never observe a half-written value, no matter how many writers are simultaneously active on the same row.
  • Zero blocking between reads and writes — not "short locks," not "usually fast" — architecturally, a plain read must never wait on a plain write to the same data, and vice versa.
  • Unbounded transaction duration — a transaction that has been open for forty minutes running a batch job must not force every other transaction in the cluster into a degraded state just because it hasn't committed yet.
  • Cheap abort — most transactions commit, but the ones that abort must not be disproportionately expensive; a design that makes rollback slow just to make commit fast is trading the wrong cost.
  • Repeatability within a transaction — depending on isolation level, a transaction reading the same row twice should see a stable, self-consistent world, not a live feed of everyone else's concurrent commits.

No single physical copy of a row can satisfy all five: if there is exactly one copy of the tuple's bytes, then either the writer must wait for readers to finish looking at it, or readers must risk seeing a write mid-flight. The only way out is the one every serious answer to this problem eventually takes: stop trying to give every reader and writer the same bytes. Let more than one physical version of a row exist at once, and give each transaction a rule for deciding which version is "the" row, from where it is standing in time. That rule is a snapshot, and the whole machinery for creating tuple versions, tagging them with the transactions that created and removed them, and testing a version against a snapshot is what this chapter calls MVCC — multi-version concurrency control.

WHY THIS MATTERS FOR THE NEXT CHAPTER

Everything in this chapter has a cost that chapter 6 collects: multiple versions of a row physically exist until something removes them, and "something" is never the transaction that created the newer version — it is a separate process, VACUUM, running later, under its own rules about which versions are safe to discard. Learn the rule for who may still need an old version now (the oldest live snapshot's xmin); chapter 6 is entirely about what happens when that horizon stops moving.

ARC 02 · HISTORICAL CONTEXT

From "keep every version forever" to a 2021 rewrite of the hot path

The tuple-versioning scheme you will read in §8 is not a modern invention bolted onto an old locking engine — it is a direct, if trimmed-down, descendant of Michael Stonebraker's 1986 no-overwrite storage manager, one of POSTGRES's three original research theses (the other two: extensible types, and rules). DEEP CONTEXT · WHAT "NO-OVERWRITE" ORIGINALLY MEANT

Stonebraker's 1987 POSTGRES papers proposed that the database never physically delete or overwrite a tuple: every UPDATE and DELETE just appended a new record with a transaction timestamp, and old records migrated to cheap archival storage (the papers specifically imagined write-once optical disks) rather than being reclaimed. Users could query AS OF a past time and see the database exactly as it existed then — genuine time travel, not just concurrency control. That ambition proved too expensive to keep as a first-class feature (unbounded storage growth, and a query planner that must reason about time as a first-class dimension), and it was cut. What survived, because it turned out to solve a problem nobody had originally been trying to solve, was the mechanism: never overwrite a tuple's data in place; add a new version and let old ones be reclaimed later. That mechanism is exactly what makes readers-never-block-writers possible, and it is why PostgreSQL's heap access method still looks like a (much) more modest time-travel engine.

ARC 03 · NAIVE SOLUTION

Attempt #1: plain two-phase locking

Derive the architecture honestly, the way §1 set it up. The textbook answer to "many readers and writers, one shared row" is two-phase locking: a shared lock for reads, an exclusive lock for writes, held until commit.

pseudocodenaive_2pl.c — the strawman, annotated
void read_row(RowId id) {
    lock_acquire(id, LOCK_SHARED);      /* blocks if anyone holds LOCK_EXCLUSIVE */
    value = storage_read(id);
    lock_release(id, LOCK_SHARED);      /* released as soon as the read is done */
    return value;
}

void write_row(RowId id, Value v, Txn *t) {
    lock_acquire(id, LOCK_EXCLUSIVE);   /* blocks on ANY other reader or writer */
    storage_write(id, v);              /* in place — one physical copy of the row, ever */
    t->held_locks.append(id);        /* released only at COMMIT or ABORT (2PL's "2nd phase") */
}

This is not a strawman built to be knocked down cheaply — it is exactly what you should reach for first, and it already gets the hard part right: with one physical copy of every row and locks enforcing exclusive access, correctness under concurrency (§1's first demand) is essentially free. There is no version to pick, no snapshot to compare against, nothing to reclaim later. Several serious engines — SQL Server's default isolation level, most textbook implementations — start exactly here, and it is not a bad place to be at low contention.

The failure only shows up once you load a realistic workload: a hot row, read constantly, written occasionally, with one of those writes taking longer than a heartbeat.

ARC 04 · WHY IT FAILS

Blocking is not a corner case — it is the common case at any real concurrency level

Run the arithmetic on the naive engine under a completely ordinary mixed workload: 300 short OLTP writers per second against one hot row, average lock hold time 4 ms, plus one analytical reporting query that needs a consistent read across the same rows and holds a shared lock for 2 seconds while it scans.

  • Writer-vs-writer contention alone is already tight: 300/s × 4 ms = 1.2 — the row is under lock more than 100% of the time nominally, meaning writers are already queuing behind each other before the reporting query even starts. (Real systems survive this via finer lock granularity than "the row," but the point holds at whatever granularity actually contends.)
  • The reporting query is catastrophic, not just slow. The instant it acquires its shared lock, every writer needing an exclusive lock on that row queues behind it — for the full 2 seconds. At 300 writers/second, that is ~600 blocked transactions stacked up by the time the reporting query releases, each one now also holding whatever its client connection resources cost, and each one's latency includes someone else's analytics job.
  • The direction of the block is fixed by the lock, not by urgency. The 4 ms writer that arrived last still must wait for the 2-second reader that arrived first — 2PL has no notion that a point read is cheap to reorder around a long scan; it only knows shared vs. exclusive.
THE GENERAL SHAPE

This is not specific to reporting queries — it is structural. Any 2PL system pays a queuing cost proportional to (lock hold time) × (contending transaction rate) on every hot row, and because hold time is bounded below by "however long the transaction takes," a system that must support both sub-millisecond point writes and multi-second analytical reads on overlapping data has no hold-time value that is good for both. PostgreSQL's own predecessor problem, Ingres, lived with exactly this tension throughout the 1970s. The only way to remove the queuing term entirely is to remove the shared lock from the read path altogether — which means readers must stop needing the same bytes writers are touching.

So the requirement sharpens: not "faster locks," but no read-side lock on data at all. §5 examines the two serious ways the industry has done that.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Two ways to keep more than one version of a row alive

Once you accept that a reader and a writer must be allowed to look at different physical bytes for the same logical row, there are exactly two serious places to put the "other" version:

Candidate A: overwrite in place, stash the old value in a rollback/undo segment (Oracle, InnoDB)

Update the row's bytes directly, but before doing so, copy the pre-image into a separate structure — Oracle calls it a rollback segment, InnoDB an undo log. A reader that needs a version older than the current one follows a pointer from the row into that structure and reconstructs the old value by applying undo records in reverse. The live table stays small and current; history lives elsewhere, addressed on demand.

Candidate B: never overwrite; append a whole new version in the main store (POSTGRES's heritage, → Postgres)

Leave the old tuple's data exactly as written. Write a brand-new tuple with the updated values next to it in the same heap, and tag both versions with the transaction IDs that created and superseded them. A reader filters the version chain itself — no reconstruction, no undo replay — it just asks each version in turn "were you already committed, and not-yet-superseded, as of my snapshot?"

WHY POSTGRES TOOK CANDIDATE B

The choice is inherited, not incidental: candidate A requires a query executor that can reconstruct a row from a current version plus a chain of deltas — a whole extra code path, and one that gets more expensive the older the version you need (Oracle's infamous ORA-01555 "snapshot too old" is exactly rollback-segment space running out before a long reader finishes reconstructing). Candidate B needs no reconstruction logic at all: every version is a complete, independently readable tuple; the "old" and "new" values are just two rows in the same heap. That simplicity is what a small 1986 research team could build and maintain. The price, taken up in §6, is that those complete old versions physically occupy space until something removes them — there is no small undo buffer to bound the cost, only a heap that grows until VACUUM catches up.

ARC 06 · WHY THAT STILL HURTS

The bill: bloat, vacuum, and a 32-bit clock that wraps

Append-only versioning buys zero-lock reads by spending disk, and the spending is not hypothetical — it is a cost you can watch accumulate in production:

  • Every dead version is real, physical storage until VACUUM reclaims it. An UPDATE that changes one column of a wide row still writes the entire row again (unless the HOT optimization applies), and every indexed column that changed needs a brand-new index entry pointing at the new physical location — the old entry cannot simply be repointed, because the old tuple might still be visible to some in-flight reader.
  • Cleanup is not automatic on commit — it is deferred to a separate process. VACUUM (chapter 6) walks the heap later and removes versions that no snapshot could possibly still need. Until it runs, dead tuples sit in the table and in every index that referenced them, inflating scan costs for everyone.
  • A single long-running transaction holds back cleanup for the whole database — not just the rows it touches. Because "safe to remove" is defined relative to the oldest xmin any live snapshot might still be using, one session that opened a transaction an hour ago and is now idle pins that horizon in place; every dead tuple newer than its snapshot, anywhere in the cluster, is unreclaimable until it commits or aborts. This is the single most common real-world MVCC bloat incident, and §11 walks through one.
  • Transaction IDs are a 32-bit counter that must eventually wrap. Every tuple's xmin/xmax is a 32-bit XID; after roughly 4 billion transactions the counter wraps around, and a tuple written with an XID that is now "in the future" relative to the wrapped counter would look uncommitted — or worse, look like it was written by a transaction that hasn't happened yet. PostgreSQL's answer, freezing, rewrites old tuples' xmin to a special always-visible sentinel before this can happen — and if autovacuum's freezing falls behind badly enough, the server will eventually refuse new transactions outright rather than risk it. Chapter 6 is that mechanism in full; this chapter only needs you to know the horizon exists.
THE HONEST TRADE

Every cost in this list is the mirror image of a benefit from §5: no reconstruction logic, no undo-segment sizing, no "snapshot too old" errors, and — the payoff — a reader that genuinely never blocks a writer at any row, at any transaction length. The industry's other MVCC lineage (Oracle, InnoDB) traded the opposite way: a bounded, reusable undo area instead of unbounded heap growth, at the cost of a hard ceiling on how old a snapshot can get before it errors out. Neither trade is free; §9 makes the comparison explicit.

ARC 08 · INTERNAL IMPLEMENTATION

The actual bytes and the actual algorithm

Now the mechanism at the level you would need to patch it: the two structs every visibility check reads, and the branch-by-branch logic of HeapTupleSatisfiesMVCC() in src/backend/access/heap/heapam_visibility.c.

(a) The two structs

Csrc/include/access/htup_details.h — HeapTupleHeaderData, simplified
typedef struct HeapTupleFields
{
    TransactionId t_xmin;        /* inserting transaction's XID */
    TransactionId t_xmax;        /* deleting/locking transaction's XID, or 0 */

    union
    {
        CommandId     t_cid;     /* inserting AND/OR deleting command id (cmin/cmax) within that xact */
        TransactionId t_xvac;    /* old-style VACUUM FULL move XID — legacy */
    } t_field3;
} HeapTupleFields;

typedef struct HeapTupleHeaderData
{
    union {
        HeapTupleFields   t_heap;
        DatumTupleFields  t_datum;
    } t_choice;

    ItemPointerData t_ctid;      /* TID of newer version of this row, or self if none */

    /* must binary-match MinimalTupleData from here down */
    uint16 t_infomask2;          /* natts + flag bits */
    uint16 t_infomask;           /* HEAP_XMIN_COMMITTED, HEAP_XMIN_INVALID,
                                  * HEAP_XMAX_COMMITTED, HEAP_XMAX_INVALID, HEAP_XMAX_IS_MULTI, ... */
    uint8  t_hoff;               /* offset to user data */
    bits8  t_bits[FLEXIBLE_ARRAY_MEMBER]; /* NULL bitmap, if any column is null */
} HeapTupleHeaderData;
Csrc/include/utils/snapshot.h — SnapshotData, simplified
typedef struct SnapshotData
{
    SnapshotType snapshot_type;

    TransactionId xmin;      /* XIDs < xmin are all resolved (committed or aborted) — definitely old */
    TransactionId xmax;      /* XIDs >= xmax had not yet been assigned — definitely too new */

    TransactionId *xip;      /* XIDs that were in progress at the moment this snapshot was taken */
    uint32 xcnt;

    TransactionId *subxip;   /* in-progress SUBtransaction XIDs (PG 8.0+, cached from pg_subtrans) */
    int32  subxcnt;
    bool   suboverflowed;    /* too many subxids to cache — falls back to pg_subtrans lookups */

    CommandId curcid;        /* my own transaction's current command id, for own-write visibility */
    /* ... takenDuringRecovery, regd_count, active_count, lsn, whenTaken — omitted for clarity */
} SnapshotData;

Two numbers and one array carry almost the entire algorithm: xmin and xmax bound the "definitely resolved" and "definitely not yet started" ranges, and xip[] is the exception list — everyone who was caught in the middle, neither definitely old nor definitely new, when the snapshot was taken. A transaction ID counts as "still in progress, as far as this snapshot is concerned" if it is >= xmax, or it appears in xip[] — note that this is true even if that transaction has since committed. That single rule is what makes a snapshot a fixed point in time rather than a live view, and it is the crux of §4's promise: once taken, a snapshot never has to ask "what happened after I started?" again.

WHY OWN-TRANSACTION VISIBILITY NEEDS A THIRD NUMBER

xmin/xmax alone cannot answer "can I see my own earlier write?" — from my own snapshot's point of view, my own XID is not in xip[] in the way another transaction's would be, and my transaction obviously hasn't committed yet from the outside. PostgreSQL solves this with cmin/cmax — the command ID of the statement, within my own transaction, that inserted or deleted the row — compared against snapshot->curcid, the command ID of the statement running right now. A row I inserted with an earlier command in this same transaction is visible to a later command; a row inserted by the current command is not (this is exactly the rule that stops UPDATE t SET x = x + 1 from repeatedly re-updating rows it just wrote inside the same statement — each row is evaluated against the snapshot as it stood at the start of that command, not as it is updated row-by-row during the scan).

ARC 09 · TRADEOFFS

The same problem, five engines, five different bills

Every serious engine that promises non-blocking reads faced this exact fork. The spread of answers is a proof by exhaustion that there is no dominant strategy — only different places to put the cost:

SYSTEMVERSIONING SCHEMEWHAT THEY BOUGHTWHAT THEY PAID
PostgreSQLAppend-only new heap tuples; xmin/xmax + clog + snapshot no reconstruction logic unbounded snapshot age every UPDATE writes a full new row needs VACUUM forever 32-bit XID wraparound risk
MySQL / InnoDBIn-place update + undo log (rollback segment) per row smaller primary table indexes usually untouched by pure UPDATE old-version reads reconstruct via undo chain long reads bloat the undo tablespace (purge lag)
OracleIn-place update + rollback segments (System Change Number, SCN, based) mature, tunable undo retention ORA-01555 "snapshot too old" when undo is reused before a long reader finishes
SQL ServerLocking read-committed by default; optional row-versioning (snapshot isolation) via tempdb version store MVCC is opt-in, not mandatory default isolation still takes read locks version store lives in tempdb — a shared bottleneck
SQLiteSingle writer at a time; WAL-mode readers see a consistent prefix of the WAL trivial to reason about zero versioning machinery no true per-row MVCC — one writer, period
Cassandra / RocksDB (LSM)Immutable SSTables; every write is a new timestamped record; tombstones mark deletes writes are always sequential appends compaction reclaims space asynchronously, like VACUUM reads must merge across multiple SSTables last-write-wins by timestamp, not transaction semantics

Read the "what they paid" column as a checklist of what this chapter has already justified: PostgreSQL's bet is that reconstruction logic is a worse place to spend engineering effort than a background reclaimer, and that an engine used for both sub-millisecond OLTP and hours-long analytical transactions cannot afford a hard ceiling on snapshot age. The LSM-tree lineage (Cassandra, RocksDB) independently reinvented "append, don't overwrite, and clean up later" for a completely different reason — write-throughput on spinning and then flash media — which is a useful sign that this is a fundamental tradeoff shape, not a PostgreSQL idiosyncrasy.

ARC 10 · PERFORMANCE CHARACTERISTICS

The cost of a visibility check, before and after the first read

A single call to HeapTupleSatisfiesMVCC() is O(1) against the tuple and the snapshot's xmin/xmax bounds, but membership in xip[] is a linear scan of a backend-local array (bounded by max_connections, typically tiny — tens of entries, not thousands), and — the expensive branch — resolving an XID's actual fate when neither hint bit is set means a call into TransactionIdDidCommit(), which is a pg_xact (clog) lookup through the SLRU cache. That lookup is: compute the clog page number (xid / 32768, since 2 bits/XID pack 32,768 statuses into one 8 KB page), check whether that page is SLRU-resident, and if not, fault it in from disk — an extra shared-buffer-adjacent I/O plus a slot eviction under a dedicated LWLock, entirely separate from the ordinary buffer pool. Once resolved, the answer is cached on the tuple itself as a hint bit, and every subsequent visibility check against that same tuple version is a single memory read — no clog access at all.

  • First full scan after bulk load or restore: every tuple's hint bits are unset — O(n) clog lookups, each potentially an SLRU page fault, and each one dirties the page it touches (see §11's third incident for exactly this on a hot standby).
  • Steady state on a vacuumed, quiescent table: effectively O(1) per tuple — a memory read of t_infomask, no clog access, no extra writes.
  • xip[] scan cost: O(k) where k = concurrently in-progress transactions at snapshot-taking time — this is the term the PostgreSQL 14 rewrite (§2) attacked, because k used to also include every idle connection's slot scan inside GetSnapshotData() itself, not just the xip lookup, turning connection count into a tax on every snapshot in the cluster.
ARC 11 · REAL-WORLD PRODUCTION

Three incidents this chapter explains completely

Incident 1: the idle-in-transaction bloat spiral

An application's ORM opens a transaction, runs one query, and — due to connection-pool misconfiguration or a forgotten commit() in an exception path — leaves it open, idle, for hours. Nothing it touched looks locked; pg_locks is quiet. But its snapshot's xmin was fixed the moment it ran that one query, and every dead tuple created anywhere in the database after that instant is, by definition, newer than a snapshot that might still need to see it — so VACUUM cannot remove any of them, on any table, until that session commits, aborts, or is killed. Table and index bloat climbs continuously; autovacuum runs constantly and reclaims nothing. Fix: idle_in_transaction_session_timeout to cap the damage, application-level fixes to the connection-handling bug, and — for diagnosis — age(backend_xmin) in pg_stat_activity pointed straight at the offending session.

Incident 2: the transaction ID wraparound near-miss

Autovacuum is starved — disabled by a well-meaning "reduce I/O" change, or unable to keep up because a huge table's freeze pass keeps getting cancelled by lock contention. age(datfrozenxid) creeps toward the 2-billion-transaction danger zone; PostgreSQL starts logging increasingly urgent warnings, then, if ignored, forces the database into a state that refuses new transactions rather than risk XID wraparound corrupting visibility (an old committed tuple's XID would otherwise become indistinguishable from a future, not-yet-started one). Recovery is a single-user-mode, all-hands emergency VACUUM FREEZE on the oldest tables, under time pressure, on a production database that is currently refusing writes. Fix, well before the emergency: monitor age(datfrozenxid) per database, alert well under autovacuum_freeze_max_age, and never disable autovacuum on a table without an explicit, monitored manual freeze schedule replacing it.

Incident 3: hint-bit write amplification on a freshly restored read replica

A team restores a base backup (or builds a replica by pg_dump/restore rather than streaming replication) and immediately points a heavy read-only reporting workload at it. The restored pages carry no hint bits — nothing set them during restore — so the very first read of every row triggers a clog lookup and sets a hint bit, dirtying a page that no user-visible write ever touched. On a workload assumed to be "read-only," the checkpointer and background writer suddenly have a large, unexpected burst of dirty pages to flush, disk I/O spikes, and nobody in the incident channel believes a SELECT-only replica could possibly be causing write load. Fix: know this is expected and one-time; optionally run a proactive VACUUM (FREEZE) pass immediately after restore so the hint-bit and freezing cost is paid on your schedule, in a maintenance window, rather than discovered live under production read traffic.

Three functions, simplified from PostgreSQL 16/17 sources but faithful in structure and naming. First, the visibility check itself — this is the same logic §8's deck walked, in real shape:

Cheapam_visibility.c — HeapTupleSatisfiesMVCC(), condensed
static bool
HeapTupleSatisfiesMVCC(HeapTuple htup, Snapshot snapshot, Buffer buffer)
{
    HeapTupleHeader tuple = htup->t_data;

    if (!HeapTupleHeaderXminCommitted(tuple))
    {
        if (HeapTupleHeaderXminInvalid(tuple))
            return false;                          /* known aborted/crashed inserter */

        if (TransactionIdIsCurrentTransactionId(HeapTupleHeaderGetXmin(tuple)))
        {
            if (HeapTupleHeaderGetCmin(tuple) >= snapshot->curcid)
                return false;                      /* inserted by a LATER command of mine */
            if (tuple->t_infomask & HEAP_XMAX_INVALID)
                return true;                       /* my own insert, never touched again */
            /* ... own-xmax handling, see xmax block below ... */
        }
        else if (XidInMVCCSnapshot(HeapTupleHeaderGetXmin(tuple), snapshot))
            return false;                          /* still running (or not yet started) AS OF my snapshot */
        else if (TransactionIdDidCommit(HeapTupleHeaderGetXmin(tuple)))
            SetHintBits(tuple, buffer, HEAP_XMIN_COMMITTED, ...);  /* pays the clog lookup ONCE */
        else
        {
            SetHintBits(tuple, buffer, HEAP_XMIN_INVALID, InvalidTransactionId);
            return false;                          /* aborted or crashed */
        }
    }
    /* by this point, xmin is known-good and committed-before-my-snapshot */

    if (tuple->t_infomask & HEAP_XMAX_INVALID)
        return true;                              /* never deleted/updated away */

    if (!(tuple->t_infomask & HEAP_XMAX_COMMITTED))
    {
        if (TransactionIdIsCurrentTransactionId(HeapTupleHeaderGetXmax(tuple)))
            return HeapTupleHeaderGetCmax(tuple) >= snapshot->curcid;  /* my own delete: cmax rule mirrors cmin */
        if (XidInMVCCSnapshot(HeapTupleHeaderGetXmax(tuple), snapshot))
            return true;                          /* deleter not yet visible to me: deletion hasn't "happened" for me */
        if (!TransactionIdDidCommit(HeapTupleHeaderGetXmax(tuple)))
        {
            SetHintBits(tuple, buffer, HEAP_XMAX_INVALID, InvalidTransactionId);
            return true;                          /* deleter aborted: deletion undone */
        }
        SetHintBits(tuple, buffer, HEAP_XMAX_COMMITTED, HeapTupleHeaderGetXmax(tuple));
    }
    else if (XidInMVCCSnapshot(HeapTupleHeaderGetXmax(tuple), snapshot))
        return true;                              /* deleter committed AFTER my snapshot */

    return false;                                  /* deleter committed before my snapshot: dead to me */
}
Cprocarray.c — GetSnapshotData(), condensed
Snapshot
GetSnapshotData(Snapshot snapshot)
{
    LWLockAcquire(ProcArrayLock, LW_SHARED);

    TransactionId nextXid  = ReadNextTransactionId();  /* becomes snapshot->xmax */
    TransactionId globalxmin = nextXid;
    int count = 0;

    for (int i = 0; i < ProcGlobal->allProcCount; i++)
    {
        PGPROC *proc = &ProcGlobal->allProcs[i];
        TransactionId xid = UINT32_ACCESS_ONCE(proc->xid);

        if (!TransactionIdIsValid(xid) || proc == MyProc)
            continue;                        /* empty slot, or don't let myself block myself */

        snapshot->xip[count++] = xid;
        if (TransactionIdPrecedes(xid, globalxmin))
            globalxmin = xid;                    /* oldest XID still running anywhere */
    }

    snapshot->xmin = globalxmin;
    snapshot->xmax = nextXid;
    snapshot->xcnt = count;
    RecentXmin = globalxmin;                     /* published — this IS vacuum's cleanup horizon */

    LWLockRelease(ProcArrayLock);
    return snapshot;
}
/* Since PG14 (Freund's snapshot-scalability rewrite): the common case skips this O(N) walk
 * entirely — a maintained, incrementally-updated snapshot is cached in shared memory and
 * copied out, only falling back to the full ProcArray scan when the cache is stale. */
Cclog.c — TransactionIdGetStatus(), condensed
XidStatus
TransactionIdGetStatus(TransactionId xid, XLogRecPtr *lsn)
{
    int64 pageno = TransactionIdToPage(xid);   /* xid / 32768 — 2 bits/xid, 8KB pages */
    int   byteno = TransactionIdToByte(xid);
    int   bshift = TransactionIdToBIndex(xid) * 2;

    int slotno = SimpleLruReadPage(XactCtl, pageno, true, xid); /* may fault in from disk, evict LRU slot */
    char *byteptr = XactCtl->shared->page_buffer[slotno] + byteno;

    int status = (*byteptr >> bshift) & 0x03;      /* IN_PROGRESS | COMMITTED | ABORTED | SUB_COMMITTED */

    SimpleLruReleasePage(XactCtl, slotno);
    return status;
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Two bits, not a hash map. A transaction's terminal fate is exactly one of four values, forever; packing that into a flat, page-indexed SLRU array makes lookup a pure address computation, and — just as important — makes the structure truncatable: once every tuple referencing an old XID has been frozen, the clog pages describing it are provably dead and can be deleted outright. A hash map or B-tree would be enormously larger for the same information and would never shrink. 2. Hint bits exist purely to amortize. The clog answer for a given XID never changes once resolved, so caching it on the one structure that's already being read (the tuple header, sitting in a shared buffer you already pinned) turns a repeated shared lookup into a one-time cost — paid for in extra page-dirtying, which is the honest tradeoff, not a bug. 3. Correct first, fast later. GetSnapshotData()'s O(N) ProcArray scan under one lock was the obviously-correct 1999 design and stayed untouched for two decades because it didn't hurt until cloud-era connection counts made it the dominant cost — a textbook case of not paying an optimization's complexity budget before the workload demands it.
