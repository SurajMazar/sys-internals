INTERMEDIATE

Smart Pointers &
Interior Mutability

Rust's ownership rules — one owner, and either many readers or one writer, checked before the program ever runs — are enough for most code. They are not enough for a tree node with two parents, a value two closures both need to hold onto, or a cache that must update itself through a shared, read-only reference. This chapter is about the small set of library types — no compiler magic, no keywords — that let you opt out of parts of that discipline on purpose: Box<T> moves a value to the heap, Rc<T> and Arc<T> replace "one owner" with "an owner count," and Cell<T>/RefCell<T> replace "checked at compile time" with "checked the instant you ask." Every one of them trades a compile-time guarantee for a runtime cost or a runtime panic — and knowing exactly which trade you're making, and what it actually costs in cycles and bytes, is the difference between using these types well and reaching for Rc<RefCell<T>> everywhere out of habit.

You will be able toWrite a recursive data type with Box<T>, share one value across owners with Rc<T>, and mutate it safely through RefCell<T>.
You will understandExactly what Rc::clone and Arc::clone do at the machine level, and why one is measurably cheaper than the other.
You will predictThe precise panic — and its exact message — that a given sequence of borrow()/borrow_mut() calls will trigger, before running the code.
You will simulateA real strong/weak reference-count state machine: clone handles, drop them in any order, and watch deallocation fire at the exact instant the last strong handle goes away.
ARC 01 · THE PROBLEM

Ownership is a great default and a bad universal law

By chapter 11 you have internalized Rust's core deal: every value has exactly one owner, that owner can lend it out as many immutable references or exactly one mutable reference at a time, and the compiler proves this holds at every call site before it will produce a binary. That deal is why Rust code doesn't segfault on a dangling pointer and doesn't need a garbage collector pausing your program to figure out what's still reachable. It is also, deliberately, a conservative approximation of "this program is memory-safe" — and conservative approximations reject real, safe programs along with the unsafe ones.

Three ordinary shapes of program break the single-owner, checked-at-compile-time deal outright:

  • Recursive size. A type that contains itself — a linked list node holding another node, a tree holding subtrees — has no fixed size the compiler can compute. struct Node { next: Node } would need infinite bytes on the stack. The value has to live somewhere with a size the compiler can pin down: a pointer.
  • Ownership that genuinely isn't singular. A graph where two parents legitimately share one child, a cache handed out to several subsystems, a GUI widget referenced by both its parent container and an event dispatcher — these have more than one rightful owner, not a bug where ownership is merely unclear. Rust's "exactly one owner" rule can't express this directly; you need something that counts owners instead of naming a single one.
  • Mutation behind a shared, read-only-looking reference. A struct that memoizes a computed value the first time &self is called, a mock object in a test that records call counts through &self, an observer list a widget appends to when notified — all of these need to mutate state that a caller only ever sees through &T. The borrow checker's whole job is refusing exactly this, at compile time, with no exceptions.
THE SHAPE OF EVERY ANSWER IN THIS CHAPTER

Look closely and every type in this chapter does the same maneuver: it doesn't disable a Rust safety rule, it moves the rule's enforcement point. Box<T> keeps single ownership but moves the value's storage to the heap, fixing the "unknown size" problem without touching the ownership rule at all. Rc<T> keeps the "no two owners can both free this" guarantee, but enforces it by counting live owners at runtime instead of naming exactly one at compile time. RefCell<T> keeps the "one writer XOR many readers" rule, but checks it with a counter each time you ask for access instead of proving it once, statically, before the program runs. Nothing here is a backdoor around safety — it is safety with a different, and more expensive, receipt.

ARC 02 · HISTORICAL CONTEXT

Smart pointers are older than Rust — interior mutability is older still

Neither idea in this chapter was invented for Rust. Reference counting and "a mutable cell behind an otherwise-immutable interface" both have decades of prior art in other languages; Rust's contribution is making both of them library types — ordinary structs implementing ordinary traits — rather than compiler built-ins, and in the case of Rc, doing that by literally ripping a built-in version out of the pre-1.0 language. DEEP CONTEXT · THE @ SIGIL RUST DELETED

Before 1.0, Rust had a built-in pointer sigil, @T, for a garbage-collected, reference-counted "managed box" — sitting alongside ~T (an owned box, the ancestor of today's Box<T>) and &T (a borrow). @T was removed in 2013, years before the 1.0 release, because baking a cycle-collecting GC into the language contradicted the zero-cost-abstraction goal: every program paid for GC machinery whether it used @T or not, and the semantics were hard to reconcile with the borrow checker being developed in parallel. The replacement wasn't a worse feature — it was no language feature at all: Rc<T>, an ordinary struct in a library crate, implementing Clone, Deref, and Drop like any type you could write yourself. That deletion is why this entire chapter is about library types instead of keywords.

ARC 03 · NAIVE SOLUTION

Attempt #1: just write the data structure you want

Derive the need honestly, the way a beginner actually hits it. Say you want the simplest possible recursive data structure — a cons list, the textbook building block of linked lists — with no imports, no special types, just an enum:

rust — does NOT compilenaive_list.rs
enum List {
    Cons(i32, List),   // a cell holding a value and "the rest of the list"
    Nil,               // the empty list
}

fn main() {
    let list = List::Cons(1, List::Cons(2, List::Cons(3, List::Nil)));
}

And say, separately, you want two owners of one struct — the ordinary "share this value" case, attempted the most direct way possible: give the same value to two variables.

rust — does NOT compilenaive_share.rs
struct Config { retries: u32 }

fn main() {
    let cfg = Config { retries: 3 };
    let worker_a = cfg;   // worker_a now owns the Config
    let worker_b = cfg;   // give the SAME Config to worker_b too
    println!("{} {}", worker_a.retries, worker_b.retries);
}

Both are the most natural things a programmer coming from Python, Java, or Go would try. Neither compiles. The next section pins down exactly why, with the real rustc diagnostics.

ARC 04 · WHY IT FAILS

Two different rules, two different rustc errors

naive_list.rs fails at the type level, before ownership even enters the picture:

rustcerror[E0072]
error[E0072]: recursive type `List` has infinite size
 --> naive_list.rs:1:1
  |
1 | enum List {
  | ^^^^^^^^^ recursive type has infinite size
2 |     Cons(i32, List),
  |               ---- recursive without indirection
  |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
  |
2 |     Cons(i32, Box<List>),
  |               ++++    +

This is arithmetic, not pedantry. To lay out List in memory, the compiler must know its size in bytes. Cons(i32, List) requires knowing the size of List to compute the size of List — an equation with no finite solution, the same way "how big is a box that contains another copy of itself" has no answer. Every value with a fixed, known size lives directly inline (on the stack, or inline inside whatever contains it); a value whose size can't be pinned down needs to live behind a pointer, because a pointer's size (one machine word) never depends on what it points to.

naive_share.rs fails for a completely different reason — not a type-size problem, an ownership problem:

rustcerror[E0382]
error[E0382]: use of moved value: `cfg`
 --> naive_share.rs:5:17
  |
3 |     let cfg = Config { retries: 3 };
  |         --- move occurs because `cfg` has type `Config`, which does not implement the `Copy` trait
4 |     let worker_a = cfg;
  |                    --- value moved here
5 |     let worker_b = cfg;
  |                    ^^^ value used here after move

Config doesn't implement Copy (chapter 4), so let worker_a = cfg moves ownership out of cfg — after that line, cfg is not a valid value anymore, and worker_b = cfg tries to move it again from a binding that no longer owns anything. This is the ownership rule working exactly as designed: it would rather reject a legitimate "share this" request than risk two owners each believing they can free the same memory.

THE BUG CLASS RUST IS REFUSING TO SHIP

In a language with manual, unchecked reference counting — the pattern C, Objective-C (pre-ARC), and COM all relied on for decades, where you call retain/release or AddRef/ Release by hand — miscounting by one is silent until it isn't: one missed release leaks memory forever, one extra release frees an object something else still points to, and the next access is a use-after-free. This is not a theoretical risk: Google's Chromium security team has published, repeatedly, that roughly 70% of Chrome's high-severity security bugs are memory-safety issues, and use-after-free from mishandled object lifetimes is consistently the largest single category. E0382 is Rust refusing, at compile time, to let you even approach that failure mode by hand — the cost is that "just give it to two owners" needs a different type, which is exactly what the rest of this chapter builds.

Reach for Box<T> when you need one owner and a value whose size the compiler can't pin down (recursion, or a trait object). Reach for Rc<T> when you need more than one legitimate owner and everyone agrees the value never changes after creation. Reach for RefCell<T>, usually wrapped inside the Rc, only when some of those owners also need to mutate the shared value. Each step is opt-in — you pay for exactly the capability you use, never all three by default.

ARC 06 · WHY THAT STILL HAS COSTS

Be honest about the bill

Nothing here is free, and pretending otherwise is how Rc<RefCell<T>> ends up sprinkled through code that never needed it. The real costs, precisely:

  • Heap allocation, every time. Box::new, Rc::new, and Arc::new all call the global allocator. That's a real system call path (or at least a non-trivial allocator fast-path), or a genuine cost most beginners don't budget for compared to a stack-allocated struct.
  • Rc and Arc cannot see cycles. If node A holds a strong Rc to node B and B holds a strong Rc back to A, neither strong count ever reaches zero, neither value is ever dropped, and the memory leaks for the life of the program. Rust's reference counting has no cycle collector — unlike a tracing garbage collector, it cannot walk the heap and notice the pair is unreachable from anywhere else. §7 and §11 both come back to this.
  • RefCell's safety net has a hole in it. The borrow checker's compile-time proof means a borrow violation simply cannot exist in a program that compiles. Move that proof to RefCell and it becomes a runtime check instead — which means a borrow conflict that only happens down one rarely-taken code path will compile cleanly, ship, and panic in production the first time that path actually runs. You traded "impossible" for "untested."
  • Arc's atomic operations are measurably slower than Rc's plain ones (§8, §10 make this precise) — and Rc<T> is not thread-safe at all, so reaching for Arc "just in case" pays that atomic tax on every clone even in code that never spawns a second thread.
  • Indirection costs cache locality. A Vec<Box<Node>> scatters nodes across the heap instead of packing them contiguously; walking it is a chain of pointer-chasing cache misses that a flat array wouldn't pay.
  • Verbosity and noise. data.borrow_mut().field = x; at every call site is real syntactic weight compared to data.field = x, and it is a visible signal — arguably a useful one — that something less-checked is happening at that line.

ARC 08 · INTERNAL IMPLEMENTATION

What's actually behind the pointer

Three real layouts, then two real costs. This is the level of detail that lets you predict, rather than guess, what a given line of code will do.

(a) One allocation, two hidden counters: the shape of RcBox<T>

Rc::new(v) does not allocate just v. It allocates a single heap block big enough for v plus two counters, and the Rc<T> you hold is a thin pointer to that block:

rust — simplified from library/alloc/src/rc.rsthe real layout
struct RcBox<T> {
    strong: Cell<usize>,   // how many Rc<T> handles are alive
    weak:   Cell<usize>,   // how many Weak<T> handles are alive (+1 while any strong exists)
    value:  T,              // your actual value, inline in the SAME allocation
}

pub struct Rc<T> { ptr: NonNull<RcBox<T>> }   // one pointer, that's it

Rc::clone(&a) never touches the heap again — it reads the same strong field through the same pointer and increments it by one with a plain, non-atomic read-modify-write, because Cell<usize> requires no synchronization: Rc<T> is not Sync, so the compiler already guarantees no other thread could be touching that counter at the same time. Arc<T> is the identical layout with AtomicUsize in place of both Cell<usize> fields — the only difference in the whole data structure — and that one type swap is the entire reason Arc::clone compiles to a locked/atomic increment instruction instead of an ordinary one.

(b) RefCell's borrow flag: a signed counter standing in for the borrow checker

RefCell<T> wraps an UnsafeCell<T> (the one primitive the whole standard library builds interior mutability on — it's the only type the compiler allows to hand out a &mut T from a &self method) plus one signed counter. Zero means unborrowed; a positive count is that many live shared borrows; a negative value means one live mutable borrow. ARC 09 · TRADEOFFS

The same problem, priced five different ways

APPROACHOWNERSHIP MODELWHAT IT BUYSWHAT IT COSTS
Rust Box<T>Single owner, heap-allocated recursive types no runtime check at all one allocation pointer-chasing on access
Rust Rc<T> / Arc<T>Shared ownership, refcounted, no cycle detection deterministic drop timing zero GC pause, ever leaks on reference cycles Arc pays atomic-op cost
Rust RefCell<T>Single logical owner, runtime-checked aliasing mutate through &self still no data races (single-threaded) panics if you're wrong bug surfaces at runtime, not compile time
C++ shared_ptr/unique_ptrSame idea as Rc/Box, unchecked mutation familiar to any Rust dev with C++ background no aliasing enforcement — a shared_ptr's pointee can be mutated through any alias, unchecked, even from another thread
Objective-C ARC / Swift ARCCompiler-inserted retain/release, same refcount idea you never write retain/release by hand nonatomic vs atomic is literally Rc vs Arc also leaks on cycles — needs `weak`/`unowned` by hand, exactly like Rust's Weak<T>
Java / Go / Python (tracing GC)No manual ownership at all — anything reachable stays alive cycles collected automatically zero mental bookkeeping for the programmer unpredictable pause times no deterministic Drop — "when does this close its file handle?" has no exact answer

Read this as a spectrum with one axis: who decides when a cycle is a leak, and when. Rust decides never, automatically, and asks the programmer to break cycles with Weak<T> by hand. A tracing GC decides continuously, automatically, and asks the programmer to accept an unpredictable pause in exchange. Neither is strictly better — Rust's choice is consistent with everything else in the language: pay for exactly what you use, know exactly when it happens, accept that "exactly when" sometimes means "never, if you build a cycle and forget Weak."

ARC 10 · PERFORMANCE / SAFETY CHARACTERISTICS

Numbers you can reason about before profiling

Order-of-magnitude figures worth carrying around, on typical x86_64/ARM64 hardware:

  • Stack allocation: effectively free — a stack pointer bump, sub-nanosecond.
  • Heap allocation (Box::new/Rc::new): tens of nanoseconds on a fast-path allocator (jemalloc/mimalloc-class), more under fragmentation or lock contention in the allocator itself.
  • Rc::clone: one non-atomic increment of a usize in already-hot cache — roughly the cost of any other single-instruction integer add, ~1 cycle when the cache line is local.
  • Arc::clone: one atomic fetch-add — tens of cycles uncontended (the CPU still has to guarantee the operation is indivisible across cores), and dramatically worse under contention, because every core incrementing the same counter forces that cache line to migrate between cores on every single operation (true cache-line ping-pong, sometimes called "cache-line bouncing").
  • RefCell::borrow()/borrow_mut(): one branch on a plain integer, cheaper than a single mispredicted branch — the runtime cost is real but small; the actual price of RefCell is the compile-time guarantee you gave up, not the CPU cycles you spend checking.

ARC 11 · REAL-WORLD INCIDENTS

Three case studies

Incident 1: rustc's own Lrc alias — the atomic tax, taken seriously by the compiler team

The Rust compiler itself is written in Rust, and its internals lean heavily on reference-counted data (ASTs, interned types, query results shared across compiler passes). For most of its life, rustc's front end ran single-threaded, so its internal alias for "the reference-counted pointer type we use everywhere" — historically named Lrc in the compiler's own source — was defined as plain Rc<T>. When the experimental parallel front-end work needed those same structures shared safely across compiler threads, the project didn't blanket-switch every Rc in the codebase to Arc and accept the cost everywhere: it kept Lrc as a type alias that resolves to Rc in the ordinary, single-threaded compiler and to Arc only when the parallel-compiler configuration is enabled. The compiler team engineering an alias specifically to avoid paying Arc's atomic increments in the common, single-threaded case is the clearest possible confirmation that the cost from §8 and §10 is real enough to design around, not a rounding error.

Incident 2: RUSTSEC-2021-0003 (CVE-2021-25900) — smallvec's manual bookkeeping bug

The popular smallvec crate's insert_many method used unsafe code to grow its buffer and shift elements without going through the safe, checked Vec-style API — and miscalculated the buffer's required capacity when the iterator passed to insert_many panicked partway through. The result was a real heap buffer overflow: the tracked length and the buffer's actual allocated capacity disagreed, and writes went past the end of the allocation. This is exactly the failure class that Rust's compile-time-checked types exist to prevent — a length or a count that some piece of manual code is responsible for keeping honest, and one edge case (a panicking iterator mid-loop) where it silently didn't. It's a useful reminder for this chapter specifically: RefCell's borrow flag and Rc's strong count are also "just a counter someone has to keep honest" — the difference is the standard library keeps those particular counters honest for you, in safe code, on every path, including the panicking ones.

Incident 3: the reference-cycle leak, straight from the standard library's own documentation

This one needs no company name because it's built into the language's own docs as a worked example: the std::rc module documentation walks through a parent-child tree where a parent holds strong Rc references down to its children and, if a child is naively given a strong reference back up to its parent, neither the parent's nor the child's strong count can ever reach zero — the whole subtree leaks for the life of the process. It's an extremely common real pattern in GUI widget trees, entity-component graphs in game engines, and any "doubly-linked" shared structure — reported often enough in community postmortems (r/rust, crate issue trackers for GUI and ECS libraries) that "parent uses Rc, child uses Weak" is close to a house rule. §13's source walkthrough shows exactly why Weak breaks the cycle: it increments only the weak count, never the strong one, so it can never be the reference that keeps a value alive.

Reading the real thing: rc.rs, sync.rs, cell.rs

Where these types actually live in the standard library, and the functions that define this whole chapter.

library/

First, Rc::clone — no allocation, just a counter bump and a pointer copy:

rustalloc/src/rc.rs — Rc::clone(), simplified but faithful
impl<T> Clone for Rc<T> {
    fn clone(&self) -> Rc<T> {
        let old = self.inner().strong.get();
        self.inner().strong.set(old + 1);   // plain non-atomic increment
        Rc { ptr: self.ptr }                    // copy the pointer, that's the WHOLE clone
    }
}

Then Rc::drop — the state machine the simulator in §15 implements exactly:

rustalloc/src/rc.rs — Rc::drop(), simplified but faithful
impl<T> Drop for Rc<T> {
    fn drop(&mut self) {
        let strong = self.inner().strong.get() - 1;
        self.inner().strong.set(strong);
        if strong != 0 { return; }        // other Rc handles still alive — nothing to do

        // LAST strong handle: drop the VALUE now, even if Weak handles remain.
        drop_in_place(&mut self.inner_mut().value);

        if self.inner().weak.get() == 0 {
            // no Weak<T> left either — the allocation itself is now garbage.
            dealloc(self.ptr);
        }
        // else: the RcBox<T> allocation survives, empty, until the last
        // Weak::drop also reaches zero — Weak::upgrade() needs it to still
        // exist so it can safely check "is strong still 0?" and return None.
    }
}

And RefCell::borrow_mut — the exact real panic message, produced by the exact real check:

rustcore/src/cell.rs — RefCell::borrow_mut(), simplified but faithful
impl<T> RefCell<T> {
    pub fn borrow_mut(&self) -> RefMut<'_, T> {
        if self.flag.get() != 0 {   // ANY existing borrow — shared or mutable — blocks this
            panic!("already borrowed: BorrowMutError");
        }
        self.flag.set(-1);                    // mark: one live mutable borrow
        RefMut { cell: self, value: unsafe { &mut *self.value.get() } }
    }
    pub fn borrow(&self) -> Ref<'_, T> {
        if self.flag.get() < 0 {     // only a MUTABLE borrow blocks a new shared one
            panic!("already mutably borrowed: BorrowError");
        }
        self.flag.set(self.flag.get() + 1);   // one more shared borrow
        Ref { cell: self, value: unsafe { &*self.value.get() } }
    }
}
// Ref and RefMut's Drop impls decrement `flag` back down when the guard goes out of scope —
// this is WHY the borrow "ends" at the guard's last use, not at some explicit unlock call.
WHY THE GUARDS EXIST AT ALL

borrow() doesn't return &T directly — it returns a Ref<T> guard that Derefs to &T. The guard's whole job is running code when it's dropped: decrementing the flag back down. This is the same RAII shape you'll see again in chapter 15's MutexGuard — "acquiring" returns a value whose Drop impl is the "release," so you cannot forget to release; the borrow checker enforces that the guard's lifetime, and therefore the release, happens exactly when the guard's last use ends.
