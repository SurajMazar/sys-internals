UBER ENGINEERING INTERNALS · CHAPTER 11

Observability at Scale:
M3 & Distributed Tracing

Once a rider's request crosses dozens of services connected by synchronous calls (chapter 9) and an asynchronous event backbone (chapter 10), two questions become disproportionately hard to answer: is the system healthy right now, in aggregate — and what exactly happened to this one request? This chapter derives why tagging metrics per-driver or per-trip explodes conventional monitoring tools, why Uber built and open-sourced its own metrics platform, M3, specifically to survive that cardinality, and why reconstructing one request's path across a hundred services needs a fundamentally different tool — Jaeger, Uber's real distributed tracing system, later donated to the CNCF.

ARC 01 · THE PROBLEM

Two different questions that look like one problem

"Is the system healthy?" and "what happened to this specific request?" feel like the same question asked at different zoom levels, but they demand structurally different tools, and conflating them is the single most common observability mistake at scale.

  • Aggregate health needs numbers you can chart and alert on across the whole fleet: request rate, error rate, latency percentiles, queue depth — the kind of thing a dashboard shows as a line moving over time. This is the domain of metrics.
  • One request's story needs the causal path a single rider's tap-to-request took: which services it touched, in what order, how long each hop took, and — critically — exactly where it went wrong if it did. No amount of aggregated charting answers "why was trip #48213 specifically slow." This is the domain of distributed tracing.

Both get harder in the same specific way as the system Uber built in chapters 8–10 comes into being. A monolith could answer "why was this request slow" by reading one process's log, in order, top to bottom. Once that request crosses dozens of independently deployed services — some synchronous, some via the asynchronous backbone — no single process's log contains the whole story anymore, and the metrics you'd naturally reach for (tag it by driver, by trip, by request) run headlong into a problem most engineers underestimate until it takes down the monitoring system itself: cardinality.

WHY THIS CHAPTER PAIRS TWO SYSTEMS

Uber's engineering org built two real, independently open-sourced systems to answer these two questions: M3, a metrics platform designed from the ground up around extreme cardinality, and Jaeger, a distributed tracing system later donated to the Cloud Native Computing Foundation. They are not competing solutions to the same problem — they are the right tool for two genuinely different questions, and this chapter derives both from first principles.

ARC 03 · NAIVE SOLUTION

Attempt #1: tag every metric with everything you might ever want to filter by

The obvious first move, and a completely reasonable one at small scale: instrument every service call with a metric, and attach whatever identifying tags might later help you slice the data.

pseudocodenaive_instrumentation.* — the strawman
function handleDispatchRequest(req) {
    const start = now();
    const result = doDispatch(req);

    // Tag with everything that might ever be useful for debugging later.
    metrics.recordLatency("dispatch.request.duration", now()-start, {
        driver_id: result.driverId,        // millions of distinct values
        trip_id:   req.tripId,             // a NEW distinct value every single request
        rider_id:  req.riderId,            // millions of distinct values
        city:      req.city,               // thousands of distinct values
        app_version: req.appVersion        // hundreds of distinct values
    });
    return result;
}

This is not a beginner's mistake — it is the natural instinct of an engineer who has been burned by not having enough detail during a past incident, and every individual tag genuinely is useful in isolation. The problem only appears once you multiply them together, and it appears violently.

ARC 04 · WHY IT FAILS

Cardinality multiplies; it does not add

A conventional time-series system typically treats every unique combination of a metric name and its tag values as its own distinct series to index and store. That is the arithmetic that breaks:

THE MATH

One metric, five tags, with cardinalities trip_id (unbounded — a new value every request), driver_id (millions), rider_id (millions), city (thousands), app_version (hundreds) — the number of distinct time series this one metric can produce is the product of those cardinalities, not the sum. Even ignoring the unbounded trip_id field alone, millions × millions × thousands × hundreds is a number with more digits than any conventional in-memory series index was ever designed to hold. Include trip_id and the series count is effectively unbounded — a fresh, never-seen-before series on every single dispatch request.

Concretely, what breaks first is whichever component is holding the full index of "every series that exists" in memory for fast lookup — ingestion slows as the index grows, queries that touch many series get proportionally slower, and eventually the process holding that index runs out of memory and falls over, taking monitoring down at exactly the moment (an incident) when you need it the most. The naive fix — "just don't tag by trip_id" — throws away the exact granularity that made the metric worth instrumenting in the first place. Uber needed both: high-cardinality tagging and a system that doesn't fall over because of it.

THE UNDERLYING SHAPE

This is precisely why Uber's engineering org has publicly described building M3: not as a marginally better dashboard tool, but as a metrics platform architected from the start around the assumption that cardinality would be enormous and would keep growing, rather than treating it as an edge case to guard against with tag-naming conventions alone.

By the final step, the two questions from §1 have two purpose-built answers: M3 for "is the system healthy, sliced any way you need, without falling over from cardinality," and Jaeger for "what exactly happened to this one request, across every service it touched."

ARC 06 · WHY THAT STILL HURTS

Solving cardinality and causality doesn't make them free

  • High cardinality still costs storage and query time, even when the system is designed for it. M3 handling a metric gracefully instead of falling over doesn't mean that metric is free — every additional dimension still means more bytes stored and more work per query, which is why retention policies and rollup/downsampling tiers are a real, deliberate cost decision, not a formality.
  • Tracing every request at full detail is not affordable at full volume. Storing a complete set of spans for every single request, forever, at Uber's real request volume would dwarf the cost of the requests themselves. Some form of sampling is unavoidable — which immediately raises an uncomfortable question: what happens when the exact request you need during an incident wasn't sampled?
  • Running your own observability platform is itself a serious systems problem. M3's architecture (§7) has multiple components — ingestion/aggregation, storage, and query — each of which needs its own capacity planning, on-call rotation, and failure handling. You've traded "a vendor's dashboard fell over" for "we now operate a distributed system whose job is watching our other distributed systems."
  • Sampling decisions made at request-start can be wrong in hindsight. A request that looked completely ordinary when it began (and so was sampled at the default low rate) can turn out, three hops later, to be the exact request that hit a rare bug — and by then the sampling decision has already been made.
THE HONEST TRADEOFF

Neither M3 nor Jaeger makes observability free — they make it survivable at scale, which is a different and more honest claim. The rest of this chapter is about the specific mechanisms that make that true: how M3 keeps a metrics platform from falling over under cardinality it can't predict in advance, and how sampling strategies try to keep the request you'll need during your next incident actually captured.

ARC 08 · INTERNAL IMPLEMENTATION

How a span becomes a trace, and how a tag survives at scale

Three mechanisms: (a) the span data shape and how context propagates hop to hop, (b) how M3's cardinality-aware design keeps ingestion and storage decoupled from raw tag explosion, and (c) the sampling decision itself.

(a) A span, and how it links to its parents

A trace is nothing more than a set of spans that all share one trace_id, each pointing at its immediate parent:

schemaspan — illustrative shape, in the spirit of Jaeger's real model
{
  "trace_id":        "a1b2c3d4",        // shared by every span in this one request
  "span_id":         "7f00a9",
  "parent_span_id": "55e210",          // null only for the very first span
  "operation_name": "dispatch.findNearbyDrivers",
  "service_name":   "dispatch-service",
  "start_time":     1699999000123,
  "duration_us":    18400,
  "tags":           { "h3_cell": "8928308280fffff", "candidate_count": 14 },
  "logs":           [ { "ts": 1699999000130, "msg": "queried H3 ring, radius=2" } ]
}

Context has to survive a network hop, which is the actual mechanism worth understanding:

pseudocodetrace context propagation — illustrative
function callDownstream(currentSpan, request) {
    const childSpan = tracer.startSpan("call.pricing-service", { parent: currentSpan });

    // Inject trace_id + this span's id into outgoing headers — this IS the
    // entire mechanism that lets six independent services agree they're
    // all part of the same one logical request.
    request.headers["trace-id"]  = childSpan.traceId;
    request.headers["span-id"]   = childSpan.spanId;
    request.headers["sampled"]   = childSpan.sampled;   // propagate the sampling DECISION, not just the id

    const response = http.send(request);
    childSpan.finish();
    reportToJaegerAgent(childSpan);   // fire-and-forget — never blocks the real call
    return response;
}

// On the receiving side, the pricing service extracts the same headers
// and starts ITS span as a child of the id it was handed — no shared
// clock or shared process required, only the propagated identifiers.

ARC 09 · TRADEOFFS

Metrics, logs, and traces — three tools, three jobs

TOOLANSWERSWHAT IT COSTS / WHAT IT CAN'T DO
Metrics (M3) aggregate health, any time window cheap to alert on can't reconstruct one request's causal path cardinality must be actively managed
Centralized logs full free-text detail per event no schema required upfront no built-in causal linkage across services without discipline expensive to store and search at full detail
Distributed tracing (Jaeger) exact causal path of one request across every hop precise per-hop timing not affordable at 100% sampling for every request only as complete as the services that were actually instrumented

In practice all three are used together: metrics tell you that something is wrong and roughly where; a trace for a specific slow or failed request tells you exactly which hop and why; logs fill in arbitrary detail a fixed span schema didn't anticipate. None of the three substitutes for the other two.

ARC 11 · REAL-WORLD INCIDENTS

Two failure modes every observability platform operator eventually meets

Incident 1: the cardinality bomb

This is a realistic, industry-standard incident pattern rather than a specific documented Uber postmortem, and it is arguably the single most common way metrics platforms fail everywhere they're run: a routine deploy adds one new tag to an existing, heavily-used metric — often something that looks perfectly innocuous, like a raw internal identifier or a session token — without anyone realizing that identifier is effectively unique per event. Ingestion volume for that one metric explodes overnight, the platform's own resource usage spikes, and if capacity isn't isolated per team or per metric, unrelated teams' dashboards and alerts start failing too. This pattern is precisely why a metrics platform built for Uber's real scale treats cardinality limits and per-team quotas as a first-class safety mechanism rather than an afterthought — the general lesson generalizes far beyond any one company: any tag whose cardinality you haven't explicitly bounded should be treated as a potential incident waiting to ship.

Incident 2: the sampling gap

Also a general, honestly-framed industry pattern rather than a specific public Uber incident: a service runs a fixed low sampling rate — reasonable for its normal traffic and cost profile — and then, during an actual production incident, the engineer on call goes looking for a trace of one of the failing requests and finds that the specific request they need simply wasn't sampled. Fixed-percentage, decided-at-request-start sampling makes exactly this outcome possible, because the decision to keep or discard a trace is made before anything interesting about that request is known. This is the well-known, public critique of naive probabilistic sampling, and it's why more sophisticated strategies — sampling every erroring or slow request regardless of the base rate, for instance — are standard practice at this scale, even though they add complexity to the sampling decision itself.

THE LESSON BOTH INCIDENTS SHARE

An observability platform is itself a system with its own capacity limits and its own failure modes — treating "we have metrics and traces" as a solved problem, rather than an ongoing capacity-planning and governance responsibility, is how both of these incidents happen in the first place.

ARC 13 · CODE WALKTHROUGH

Reading the shape of a real observability pipeline

Neither M3's nor Jaeger's full internals are reproduced here verbatim; what follows is precise, representative pseudocode for how a system in this class is genuinely built, labeled illustrative rather than literal.

observability/
├── client-lib/
│ ├── ● metrics_emitter.* — tagged counter/gauge/histogram emission, cardinality guard
│ └── ● tracer.* — span creation, context propagation, sampling decision
├── metrics-m3/
│ ├── ● aggregator.* — rolls up/downsamples before storage; per-team cardinality limits enforced here
│ ├── m3db-node/ — distributed time-series storage (illustrative, not literal M3DB internals)
│ └── query-coordinator/ — serves aggregate queries against storage
└── tracing-jaeger/
├── agent/ — local span collector per host, batches before forwarding
├── ● collector.* — validates, indexes, and persists spans
└── query-ui/ — reconstructs and renders a full trace from stored spans

The cardinality guard that keeps one bad tag from becoming an incident:

pseudocodeaggregator.* — illustrative cardinality guard
function ingest(metricName, tags, value, team) {
    const seriesKey = metricName + "{" + sortedTagString(tags) + "}";

    if (!knownSeries.has(seriesKey)) {
        if (teamSeriesCount[team] >= teamQuota[team])
            return reject(`team '${team}' exceeded its series quota — new series NOT admitted`);
        knownSeries.add(seriesKey);
        teamSeriesCount[team]++;
    }
    aggregationBuffer.record(seriesKey, value);   // rolled up before ever touching long-term storage
}

The trace query path — grouping stored spans by trace_id and rebuilding the parent/child tree:

pseudocodequery-ui/reconstructTrace.* — illustrative
function reconstructTrace(traceId) {
    const spans = storage.fetchAllSpans(traceId);   // may arrive from many services, any order
    const byId = new Map(spans.map(s => [s.spanId, s]));
    const roots = [];

    for (span of spans) {
        if (!span.parentSpanId) { roots.push(span); continue; }
        const parent = byId.get(span.parentSpanId);
        if (parent) (parent.children ??= []).push(span);
        else roots.push(span);   // parent span not yet received/stored — treat as a temporary root
    }
    return sortByStartTime(roots);   // arrival order is irrelevant; START TIME reconstructs the real sequence
}
WHY IT WAS BUILT THIS WAY

1. Aggregate before you store, not after. Rolling up at the aggregation tier — before data ever lands in long-term storage — is what lets M3 hold cardinality that would sink a system storing every raw point forever. 2. Reconstruction, not real-time ordering, is the tracing contract. Spans are allowed to arrive at the collector in any order, from any number of services, because reassembly happens at query time from each span's own start time and parent pointer — no service has to coordinate timing with any other. 3. Quotas are a governance mechanism, not just a technical one. A per-team series limit turns "one team's tagging mistake" into "one team's rejected metric," instead of "everyone's monitoring platform falls over" — the same blast-radius instinct chapter 1's process model and chapter 9's circuit breakers both apply in their own domains.
