Lifetimes:
How Long Is This Reference Actually Good For?

Every & reference you have written since chapter 5 already had a lifetime — the compiler has been silently computing one for it the entire time. Most of the time that computation is so mechanical it never surfaces at all. This chapter makes it surface on purpose: what a lifetime actually is (a compile-time proof obligation, not a runtime clock), the exact three elision rules that let the overwhelming majority of functions omit lifetime syntax entirely, and the precise, narrow set of cases — two independent input references, a struct that stores a borrow instead of owning its data — where elision runs out of information and you must write 'a yourself.

You will be able toRead and write explicit 'a annotations on functions and structs, and identify which of the three elision rules resolves — or fails to resolve — any given signature.
You will understandWhy a lifetime has zero runtime representation: it is erased before code generation, and its entire job is proving a fact at compile time, never enforcing one while your program runs.
You will predictWhether a signature compiles as elision leaves it, and if not, whether one shared 'a fixes it or the underlying data genuinely does not live long enough for any annotation to help.
You will simulateBuild any function signature you like and watch the real three-rule elision algorithm resolve it automatically or demand an explicit lifetime, computed live, not scripted.
ARC 01 · THE PROBLEM

A reference that outlives what it points to is not a bug class — it is THE bug class

Chapters 4 and 5 gave you ownership and borrowing: every value has exactly one owner, and you can hand out temporary read-only or read-write views (&T, &mut T) without moving the value itself. That machinery solves double-frees and data races. It does not, by itself, solve the oldest memory-safety bug there is: what happens when a reference is still around after the thing it points to is gone?

Rust already committed, in chapter 1, to answering this without a garbage collector and without a runtime reference count on every pointer by default. Unpack what that commitment demands, and it splits into five requirements pulling against each other:

  • No runtime tracking. A plain &T must stay exactly one machine word — no hidden counter, no tag, nothing checked while the program runs. Whatever proves a reference is safe has to be settled before the first instruction executes.
  • References must be first-class. By chapter 5's own design, a reference is not just "look at this and immediately forget it" — it can be stored in a variable, passed to another function, returned from a function, or (this chapter's hardest case) stored inside a struct's field. Each of those is a new place a dangling reference could hide.
  • Per-function analysis. Rust compiles one function at a time and does not re-inline or re-verify a callee's entire body at every call site. A function's signature alone — without the compiler peeking at the body from outside — has to carry enough information for a caller to be checked against it.
  • The common case must stay silent. Chapters 5 through 8 already wrote dozens of functions taking and returning references with zero extra syntax for this. Whatever mechanism enforces the rule cannot force every single reference everywhere to carry visible new syntax, or Rust becomes unusable in practice.
  • The compiler must be able to say no. When there genuinely isn't enough information — two inputs, either of which the output might be borrowed from — silence would just be a guess. The mechanism needs a way to demand the one extra piece of information only the programmer actually has.

The mechanism satisfying all five simultaneously is a lifetime: not a runtime concept at all, but a named span of the program's control flow, attached to a reference type as a kind of second, structurally different generic parameter — one that constrains how long instead of what capabilities. A lifetime parameter lets the compiler check, purely by comparing scopes written down in a signature, that no reference a function hands out could ever be read after what it points to might be gone — before your program runs even once.

WHY THIS MATTERS FOR THE NEXT 13 CHAPTERS

Lifetimes are the reason chapter 10's closures can safely capture a reference to their environment, why chapter 12 offers Rc/RefCell as an escape hatch when static lifetime reasoning becomes too restrictive for a genuinely shared, cyclic data structure, why chapter 16's async functions need 'static bounds or Pin to hold a borrow across an .await point safely, and why chapter 19 exists at all — it goes underneath the label "lifetime" entirely, into the MIR-level analysis and non-lexical lifetimes that actually implement everything this chapter teaches you to read and write. Get comfortable with the vocabulary now; every later chapter assumes it.

ARC 02 · HISTORICAL CONTEXT

Regions, before they were called lifetimes

Rust's lifetime system did not appear from nowhere — it is the practical, syntax-first descendant of two decades of academic work on proving pointer validity at compile time, filtered through one language's specific need to make the common case require zero extra typing. DEEP CONTEXT · WHY AN APOSTROPHE?

Rust's 'a syntax is not arbitrary. The apostrophe-prefixed lowercase letter is the exact convention ML-family languages (SML, OCaml, Haskell's cousins) have used for decades to write an implicit generic type variable — you will see 'a list in an OCaml textbook meaning "a list of some type 'a," in a context that has nothing to do with memory. Rust's designers reused that already-familiar sigil for a second, structurally different kind of generic parameter — one about time instead of type — precisely so it would visually slot into the same angle-bracket list as a type parameter (fn f<'a, T>(...)) without inventing new punctuation.

ARC 03 · NAIVE SOLUTION

Attempt #1: trust the programmer, the way C always has

Derive the problem honestly by looking at how a language with no lifetime system handles it. C has no borrow concept at all — a pointer is just an address, and nothing stops you from returning one that points at memory the function itself is about to release. This is not a contrived example; it is one of the first bugs every C programmer writes:

Cdangle.c — compiles, and is undefined behavior
char *create_greeting(void) {
    char buf[64];                       /* lives on THIS function's stack frame */
    sprintf(buf, "hello, world");
    return buf;                       /* returns a pointer to that frame... */
}                                       /* ...which is popped the instant we return */

int main(void) {
    char *greeting = create_greeting();
    printf("%s\n", greeting);      /* undefined behavior: reads freed stack memory */
}

Compile this with GCC or Clang and it compiles — with, at best, a warning: warning: function returns address of local variable [-Wreturn-local-addr]. It is a warning, not an error, because C's type system has no concept of "how long is this pointer actually good for" to check against — a char* returned from this function looks exactly like a char* to a string literal that really would live forever. Nothing in the type char* distinguishes the two cases. Run the program anyway and it will very likely print "hello, world" correctly — right up until it doesn't, on a different compiler, a different optimization level, or a different day, because the freed stack memory hasn't been overwritten yet. That's the trap: the naive approach doesn't fail loudly and immediately. It fails later, intermittently, and often in production instead of in your editor.

ARC 04 · WHY IT FAILS

This is not a hypothetical — it's a perennial top-of-the-list CVE class

"Trust the programmer" is not a rare failure mode; it is one of the most quantified bug classes in software security. CWE-416, Use After Free, has been a consistently top-ranked entry on MITRE's CWE Top 25 Most Dangerous Software Weaknesses for years running, and Microsoft's own security team has repeatedly reported that roughly 70% of the vulnerabilities it fixes every year trace back to memory-safety issues — dangling pointers and their close relatives — a figure the Chromium security team independently arrived at for their own codebase. This chapter's mechanism exists to make that entire category of bug a compile error instead of a production incident, and §11 revisits the real, published numbers behind that claim in detail.

Translate the C strawman into Rust as literally as possible, and watch it refuse to compile — in two stages, because Rust actually checks two different things here, not one:

STAGE 1 — E0106, MISSING LIFETIME SPECIFIER

Write the direct translation with no lifetime syntax at all:

fn dangle() -> &String {
    let s = String::from("hello");
    &s
}

rustc refuses before it even reaches the interesting question: it can already tell there is no reference parameter at all for an elided output lifetime to come from (§5's elision rule 2 needs at least one input lifetime, and there are zero here), so it can't even guess.

STAGE 2 — E0515, EVEN AFTER YOU "FIX" THE SYNTAX

Suppose you silence stage 1 the way a beginner often does — by adding a lifetime, without stopping to ask what it should be:

fn dangle<'a>() -> &'a String {
    let s = String::from("hello");
    &s
}
error[E0515]: cannot return value referencing local variable `s`
 --> src/main.rs:3:5
  |
3 |     &s
  |     ^^ returns a value referencing data owned by the current function

This is the important half of the lesson: adding <'a> did not fix anything, because there is no scope in this function 'a could ever legally refer to — s is created and destroyed entirely inside dangle's own body. Rust's lifetime system is not satisfied by writing some annotation; it demands one that is actually, provably true. There is no version of this function's signature that compiles, for exactly the reason the C version was unsafe: the data genuinely does not outlive the function. The fix is architectural, not syntactic — return an owned String instead of a reference to one, which is precisely what every idiomatic version of this function does.

ARC 05 · NAMED LIFETIMES

A different failure mode: not "too short," but "ambiguous"

dangle() from §4 fails because the data doesn't live long enough, full stop — no annotation fixes it. There is a second, more common failure mode, and it's the one named lifetime parameters were actually built to solve: the data is completely fine, but the signature doesn't say which of two equally plausible sources the output borrows from. Follow the derivation.

Deriving fn longest, step by stepSTEP-BY-STEP
READ 'a AS A PROMISE, NOT A DURATION

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str does not claim x and y live for the same, exactly-specified span of code. It claims: whichever one comes back out, treat it as valid for only as long as BOTH inputs are guaranteed valid. The compiler is always free to instantiate 'a as the shorter of whatever two actual scopes a given call site provides — that's precisely what makes step 4 of the deck above compile when the two strings have different real lifetimes.

ARC 06 · WHY THAT STILL HAS COSTS

The honest bill for compiler-checked borrow durations

Lifetimes are not free of friction, and every one of these costs is something you will hit personally within your first weeks of writing non-trivial Rust:

  • "Lifetime soup" in generic library code. A struct or function generic over several lifetimes and several types at once — struct Parser<'a, 'b, T> where T: 'a — reads like punctuation noise until you've internalized what each one constrains. Chapter 19's advanced generic code is full of this; it does not get easier by memorizing syntax, only by understanding what each 'a is actually proving.
  • Struct definitions never get elision's help — only their methods do. §8 shows this precisely: a struct that stores a reference must always declare its lifetime parameter explicitly in the struct definition itself, even though methods defined on that struct frequently need no extra annotation at all thanks to elision rule 3. The two are genuinely different scopes, and conflating them is one of the most common early confusions.
  • A very real anti-pattern: reaching for 'static to make an error go away. Beginners confronted with a lifetime error frequently try annotating everything 'static until it compiles. Sometimes that's correct (string literals genuinely are 'static); far more often it's a sign the design should own its data instead of borrowing it, and the "fix" just relocates the bug to wherever the supposedly-'static reference actually gets constructed.
  • Self-referential structs are flatly impossible to write directly. A struct that wants to hold both some data and a reference into that same data, in the same struct, cannot be expressed with ordinary lifetime syntax — the reference's lifetime would have to refer to a sibling field that hasn't finished being constructed yet. §11 discusses the real crates (ouroboros, self_cell) that exist purely to work around this with careful, audited unsafe code underneath a safe-looking API.
  • Learning curve, compounding with generics. Chapter 8's trait bounds and this chapter's lifetime bounds share syntax (the same angle brackets, sometimes the same where clause) while constraining completely different things — capability versus duration — and new Rust developers regularly misread one for the other on first exposure.

None of this is a reason to avoid the mechanism — every cost above is the price of moving a dangling-reference bug from a 3am production incident to a red squiggle in your editor. §9 prices that trade against every alternative a mainstream language has actually shipped.

ARC 08 · STRUCTS & WHAT THE COMPILER ACTUALLY DOES

Storing a borrow, and what survives to machine code

Everything so far has been function signatures. The harder — and more instructive — case is a struct that stores a reference as a field instead of an owned value. And underneath both cases sits a fact worth stating plainly: none of this syntax exists once your program is actually running.

(a) A struct that borrows instead of owning

Step through building ImportantExcerpt, a struct that holds a view into someone else's string data rather than copying it — and the method on it that exercises elision rule 3 for real.

A struct that stores a borrowSTEP-BY-STEP
LIFETIMES ARE ERASED — DON'T CONFUSE THEM WITH LLVM'S OWN "LIFETIME" INTRINSICS

By the time your code reaches LLVM, every 'a you wrote is gone — lifetimes exist purely to let the borrow checker's compile-time analysis pass; there is no register, no tag, no byte in the compiled binary that represents one. Confusingly, LLVM itself emits intrinsics literally named llvm.lifetime.start/llvm.lifetime.end — but those mark when a stack slot's contents stop mattering, purely as a hint for the optimizer to reuse stack space safely. It is an unrelated concept that happens to share a word with this chapter's subject; rustc's own lifetime-checking work has already finished long before LLVM sees your code at all.

(b) A live check: does the borrow actually fit inside the data's scope?

This is the actual rule the borrow checker enforces for a struct like ImportantExcerpt<'a>: the struct's own usage window must fit entirely inside the window during which the data it borrows from is still alive. ARC 09 · TRADEOFFS

Five ways to answer "when is this pointer no longer good?"

Every mainstream language has picked one of a small number of answers to the exact question this chapter answers. Reading them side by side turns the tradeoff into arithmetic: you can check at compile time for free, check at runtime for a fee, or not check at all and pay only when it breaks.

APPROACHWHEN THE CHECK HAPPENSWHAT THEY BOUGHTWHAT THEY PAID
Rust lifetimesCompile time — static analysis, erased before codegen zero runtime cost use-after-free impossible in safe code verbose in nested generics learning curve self-referential structs need workarounds
Tracing GC (Java, Go, Python)Runtime — a collector scans reachability periodically no lifetime reasoning at all, ever dangling pointers structurally impossible pause times tracing/heap metadata overhead collection timing is somewhat unpredictable
Reference counting (Swift ARC, C++ shared_ptr)Runtime — increment/decrement inserted at compile-known points deterministic deallocation no separate collector thread retain/release cost on every copy reference cycles leak — needs manual weak/unowned annotations
Manual management (C, pre-modern C++)Never — pure programmer discipline maximum control, zero abstraction cost the entire use-after-free / double-free / dangling-pointer CVE class, unmitigated
Region inference (ML regions, Cyclone)Compile time, but mostly automatic — regions largely inferred rather than hand-annotated less annotation burden in the common case far less expressive for complex sharing patterns stayed confined to research languages for years

Read the row order as the actual history: region inference is the direct academic ancestor, Rust chose to trade some of its automatic inference for explicit, stability-guaranteed syntax the compiler could always fall back to (this chapter's 'a), and every runtime alternative bought simplicity by moving the check — and its cost — to a point after your program has already started running.

ARC 10 · PERFORMANCE / SAFETY CHARACTERISTICS

The number that matters: when the bug is caught, not how fast the check runs

Lifetime checking itself is essentially free at runtime — it doesn't exist anymore by the time your program executes. The performance story that actually matters here is a different one: how much a memory-safety bug costs depending on which stage of a project's life it's caught in. This is the honest argument for paying the compile-time cost this chapter teaches.

REAL, PUBLISHED NUMBERS

Microsoft's Security Response Center has repeatedly reported that roughly 70% of the CVEs it fixes each year trace back to memory-safety issues — the exact bug class this chapter's mechanism targets — a figure the Chromium project's own security team has independently cited for their C++ codebase. Google's Android security team has published a multi-year trend in the opposite direction: as the fraction of new Android platform code written in memory-safe languages (heavily Rust) rose, the share of Android's discovered vulnerabilities that were memory-safety issues fell sharply year over year — a real, measured correlation between "caught at compile time" and "never became a CVE."

ARC 11 · REAL-WORLD INCIDENTS / CASE STUDIES

Three ways this chapter's problem shows up outside a textbook

Case 1: CVE-2019-5786 — a Chrome use-after-free, exploited before it was patched

In early 2019, Google's Threat Analysis Group discovered CVE-2019-5786, a use-after-free vulnerability in Chrome's FileReader implementation, being actively exploited in the wild, chained with a separate Windows kernel privilege-escalation bug to achieve full system compromise. Google shipped an emergency patch (Chrome 72.0.3626.121) within days of discovery. This is precisely the bug class §4's dangle() example is a toy version of: a reference to freed memory, read after the fact — except in a C++ codebase with no compiler-enforced lifetime system, the mistake shipped to a billion users before anyone caught it. It's one of the concrete incidents that accelerated Chromium's own multi-year investment in memory-safe language tooling.

Case 2: Android's own numbers, published, tracking Rust adoption against vulnerability counts

Google's Android security team has published its internal vulnerability data specifically to make this chapter's argument with real numbers rather than analogy: as Android's codebase increased the fraction of new code written in memory-safe languages — primarily Rust, for exactly the guarantees this chapter derives — the share of Android's platform vulnerabilities attributable to memory-safety bugs fell sharply across the following years, even as total lines of new code kept growing. It's a rare case of a large, real production codebase reporting "we made this specific tradeoff, and here's the vulnerability count before and after."

Case 3: self-referential structs are a genuine limitation, not a hypothetical one

§6 mentioned honestly that a struct holding both data and a reference into that same data cannot be expressed with ordinary lifetime syntax. This isn't a corner case nobody hits — it's common enough that real, actively maintained crates exist specifically to paper over it: ouroboros and self_cell both provide macros that generate the necessary (carefully audited) unsafe code underneath a safe-looking API, and an older crate, rental, solved the same problem before being deprecated in their favor. Parser and async-runtime authors hit this constantly — it's the same underlying issue chapter 16 revisits when an async fn's compiler-generated state machine needs to hold a reference into its own local variables across an .await point, which is exactly why that machinery needs Pin.

ARC 13 · CODE WALKTHROUGH

Reading the real thing: how std's own iterators carry a lifetime

The most common place an ordinary Rust program encounters an explicit lifetime parameter it didn't write itself is a standard-library iterator. All three below borrow from something, and all three use the same trick to represent that borrow honestly even though their real fields are raw pointers with no lifetime of their own.

library/core/src/
├── slice/
│ └── ● iter.rs — Iter<'a, T>: the lifetime lives ONLY in a PhantomData marker, since the real fields are raw pointers
├── str/
│ └── ● iter.rs — Chars<'a>: wraps a byte-level slice::Iter borrowed from the original &'a str
└── option.rs — Option::as_ref/as_deref: converts Option<T> to Option<&T> without moving — a lifetime-shaped pattern used constantly
std::collections::hash_map/
└── ● map.rs — Iter<'a, K, V>: the identical PhantomData-marker shape, one layer up, over key/value pairs
Rustcore::slice::Iter — simplified, faithful to the real shape
pub struct Iter<'a, T: 'a> {
    ptr: NonNull<T>,               // raw pointer — carries NO lifetime by design
    end: *const T,               // one-past-the-end raw pointer, same problem
    _marker: PhantomData<&'a T>,  // ← the ONLY thing tying Iter to 'a
}

impl<'a, T> Iterator for Iter<'a, T> {
    type Item = &'a T;
    fn next(&mut self) -> Option<&'a T> {
        // advances `ptr` toward `end`, returning &'a T each step
        // ...
    }
}

Raw pointers (*const T, NonNull<T>) exist specifically to opt out of lifetime checking — that's what makes them "raw," and it's the escape hatch chapter 17 formalizes. Without the _marker: PhantomData<&'a T> field, nothing would tie Iter<'a, T> to 'a at all, and the borrow checker would happily let an Iter outlive the slice it was built from. PhantomData is a genuinely zero-sized field — it occupies no space in the compiled struct — that exists purely to tell the compiler "treat this struct as if it also owned a real &'a T," inheriting the exact same lifetime rules a literal reference field would enforce, at zero runtime cost.

Rustcore::str::Chars — simplified
pub struct Chars<'a> {
    pub(super) iter: slice::Iter<'a, u8>,   // borrows from the original &'a str
}

impl<'a> Iterator for Chars<'a> {
    type Item = char;
    fn next(&mut self) -> Option<char> {
        // decodes the next UTF-8 scalar value from self.iter
    }
}

"hello".chars() returns a Chars<'a> borrowing from the original &'a str. Call .chars() on a temporary and try to hold onto the resulting iterator past that temporary's scope, and this is the exact borrow-checker machinery — struct field, elided in the method signature by rule 3, explicit in the struct definition — that rejects it.

Ruststd::collections::hash_map::Iter — simplified, same shape one layer up
pub struct Iter<'a, K: 'a, V: 'a> {
    base: hashbrown::hash_map::Iter<'a, K, V>,
}

impl<'a, K, V> Iterator for Iter<'a, K, V> {
    type Item = (&'a K, &'a V);
    fn next(&mut self) -> Option<(&'a K, &'a V)> { /* ... */ }
}

Same pattern, different container: HashMap::iter() hands out an Iter<'a, K, V> that cannot outlive the map it was called on, checked with precisely the tools this chapter just taught you to read.
