BLOCKCHAIN FUNDAMENTALS · CHAPTER 04

Digital Signatures &
Elliptic Curves

Chapter 3 proved that a hash of data lets anyone check that a leaf belongs to a committed set. It says nothing about who put the data there, or whether they meant to. A blockchain must additionally let anyone — with no shared secret and no trusted intermediary — verify that the holder of a specific secret authorized a specific message, while learning nothing about the secret itself, and without that authorization ever transferring to a different message the holder never approved. This chapter derives that primitive from the discrete logarithm problem, builds it concretely on the elliptic curve secp256k1, and implements real key generation, real signing, and real verification with the same arithmetic Bitcoin runs in production.

ARC 01 · THE PROBLEM

Prove you hold a secret, over a channel anyone can read

A Bitcoin transaction is a public message: "move these coins from address X to address Y." It travels over a gossip network (chapter 11) where every participant — honest or not — sees its exact bytes. Anyone who has ever seen a transaction can copy it verbatim. The dangerous move is different: constructing a new, different message — "move X's coins to my address instead" — that the network will accept as equally legitimate. Nothing about hashing (chapter 2) or Merkle commitments (chapter 3) prevents that; both prove data is part of something committed, not that its author was authorized.

Unpack "authorized" into a precise specification, because precision here is the entire chapter:

  • Unforgeability. No one who lacks the secret can produce an authorization for a message the secret's holder never approved — even after seeing many other valid authorizations from that same holder.
  • Public verifiability, no interaction. Any party, holding only public information (no secret of their own, no back-and-forth challenge-response), must be able to check an authorization in one pass.
  • Message-specificity. An authorization for message A must not be usable — directly, or by leaking exploitable structure — as, or towards, an authorization for a different message B.
  • Binding to one identity. Every authorization must be attributable to exactly one keypair, so the network can enforce "only this coin's owner moves it" without knowing who that owner is.
  • Non-repudiation. The signer cannot later credibly claim someone else produced a valid signature under their key — a property symmetric-key schemes cannot offer, as §3–4 show by trying and failing.

That list is the specification of a digital signature scheme: three algorithms, KeyGen() → (d, Q) producing a private key and a public key, Sign(d, m) → σ, and Verify(Q, m, σ) → {valid, invalid}, with the property that Verify is cheap for anyone holding only Q, while producing a σ that verifies is — as far as anyone has ever demonstrated — impossible without d.

WHY THIS MATTERS FOR EVERY REMAINING CHAPTER

Every spending condition you will meet in the Bitcoin course reduces, at its core, to "produce a valid signature under this public key." UTXOs, multisig, Lightning channel states, and Taproot's key-and-script paths are all, structurally, containers around this chapter's primitive. Get the algebra solid now — chapters 13 and beyond spend it, never re-derive it.

DEEP CONTEXT · WHY "secp256k1" AND NOT A NIST CURVE

The "k" in secp256k1 stands for Koblitz curve — a special form (here, a=0) that admits an efficient endomorphism used by production libraries for a genuine ~30–40% scalar-multiplication speedup (the GLV method, §12). Its parameters are also generated transparently: every constant traces to a small, explainable seed, a property cryptographers call rigidity or "nothing up my sleeve." NIST's P-256, by contrast, was seeded from an unexplained hash output published by NSA in 1999 — never a proven backdoor, but after the 2013 revelation that NIST's separate Dual_EC_DRBG random-number standard contained an actual NSA backdoor, "trust the unexplained constant" stopped being a free assumption. Whether this made secp256k1 the more conservative choice, or just a differently-trusted one, is a judgment call — §12 asks you to make it.

ARC 03 · NAIVE SOLUTION

Attempt #1: sign with a secret everyone already has

Derive the architecture honestly, the way §1 demands. The cheapest primitive that "authenticates" a message is one you already know: a keyed MAC. Suppose every validating node and every wallet is provisioned, in advance, with the same shared secret K. A "signature" over a message is just tag = HMAC(K, m); any node re-derives the tag itself to check it.

pythonnaive_authorize.py — the strawman, annotated
def naive_sign(K, m):
    # 'signature' is just a keyed tag — cheap, symmetric
    return hmac_sha256(K, m)

def naive_verify(K, m, tag):
    # every validator needs K to run this same computation
    return hmac_sha256(K, m) == tag

# provisioning: every wallet AND every one of thousands of
# independently-run validating nodes gets a copy of K
provision_everyone(K)

This is not a joke architecture — it is exactly how internal, trusted-network systems authenticate messages every day (an API gateway and its backend sharing an HMAC secret is this scheme, and it's the right tool there). It is cheap, fast, and the mathematics of HMAC's collision resistance is completely solid. The question is whether it satisfies §1's five requirements on an open, adversarial, permissionless network.

ARC 04 · WHY IT FAILS

Whoever can verify a MAC can also forge one

Look at naive_verify again: it recomputes exactly the operation naive_sign ran. There is no operation available to a verifier that isn't equally available to a forger holding the same K. Verifiability and forgeability are the same capability under symmetric cryptography — you cannot grant one without granting the other. This single fact breaks three of §1's five requirements at once:

  • Unforgeability fails structurally. Any of the thousands of independently-operated nodes that must be able to validate a transaction is, by construction, equally able to forge one. Compromise one node's copy of K and every account secured by that shared key is compromised — not probabilistically, completely.
  • Non-repudiation fails. If Alice's signature and a forger's signature are bit-for-bit indistinguishable (both are just HMAC(K,m)), no evidence can ever show which of the K-holders produced a disputed message. Alice can truthfully claim "someone else with K did it" — and so can the actual forger.
  • Public verifiability fails at the definition of "public." The scheme's whole safety rests on K staying secret, yet the scheme requires every validator on a permissionless, anyone-can-join network to hold it. Those two requirements are in direct contradiction the moment the validator set is larger than a handful of parties who fully trust each other.
THE NUMBERS

Distributing K to N validators means N chances for it to leak, but the damage from any single leak is total — 100% of accounts, not 1/N. The alternative, giving each validator a different key so leaks stay local, needs pairwise keys per sender/validator pair — O(N) keys for one honest sender to reach N validators, and a validator cannot check a signature meant for someone else's key without also holding that key, which puts you right back where you started. There is no point on this tradeoff curve where "anyone can verify, nobody untrusted can forge" is achievable with one shared value. You need a mechanism where the ability to check and the ability to produce are provably different capabilities.

That mechanism is asymmetric cryptography: an operation that's easy to run forward, whose output is safe to publish, and where recovering — or forging without — whatever made it possible is infeasible even for someone who watches it happen many times. §5 builds exactly that, from a one-way function upward.

ARC 05 · BETTER SOLUTION, DERIVED

One-way functions, and a hard problem nobody can invert — not even the key's owner

We need a function f that is easy to compute forward but whose output reveals (essentially) nothing about a specific input that produced it — a one-way function. Note precisely what kind of asymmetry a signature scheme needs: it is not the RSA shape, where a trapdoor secret lets its holder invert a function nobody else can invert. It's simpler and stranger — nobody inverts anything, ever. The key's owner never "solves" the hard problem; they simply already know a secret number, because they chose it, and the scheme is built so only someone who knows that number can produce values satisfying a public equation.

ARC 06 · WHY THAT STILL COSTS

Not every discrete-log group is equally cheap to defend

§5 established the shape (a hard discrete-log-style relation) without committing to a specific group. Two candidate groups both give you a mathematically valid signature scheme; they do not cost the same:

  • The multiplicative group (ℤ/pℤ)* (plain modular exponentiation, as in classic DSA) is vulnerable to index calculus, running in subexponential time in the bit-length of p. To reach a security level comparable to a 128-bit symmetric key, NIST recommends p of roughly 3072 bits — every exponentiation manipulates 384-byte numbers, and public keys and signature components inherit that size.
  • The group of points on a well-chosen elliptic curve has no known subexponential attack. The best general attacks — Pollard's rho, baby-step-giant-step — run in O(√n) group operations, where n is the group's order. A 256-bit curve order already gives ~2¹²⁸ operations of work: the same security as 3072-bit DSA, using keys 12× smaller.

Smaller keys are not a cosmetic win — every public key and every signature ships in every transaction, forever, on every full node's disk, for the life of the chain. A 12× size reduction on a value that gets replicated onto tens of thousands of machines and downloaded by every new node is a real, compounding bandwidth and storage cost avoided.

But "pick a curve" is not free either. Not every elliptic curve is safe, and choosing badly reintroduces the exact index-calculus weakness ECC exists to avoid:

  • The group order must be (almost) prime. If n has only small prime factors, the Pohlig–Hellman algorithm solves the discrete log in time bounded by the largest factor, not by n itself. secp256k1's order is prime by design specifically to close this door.
  • The curve must resist pairing-based reductions. Certain curves (supersingular curves, and others vulnerable to the MOV or Frey–Rück attacks) let an attacker map the elliptic-curve discrete log into an ordinary finite-field discrete log — solvable by the cheaper index-calculus methods above. secp256k1 was checked against these transfers before standardization.
  • Implementations leak through time, not math. A private key is never exposed in cleartext, but a naive scalar-multiplication routine takes measurably different time depending on the bits of the scalar it's multiplying by (§8 shows exactly why) — turning a wall-clock stopwatch into a partial key-extraction tool. This is a live, ongoing engineering cost: constant-time code is slower to write, slower to reason about, and the "obvious" implementation is the vulnerable one.
THE HONEST TRADEOFF

Elliptic curves buy 12× smaller keys for equal security than finite-field discrete log, at the price of a much less intuitive group law (§8's geometry) and a much larger space of "looks fine, is secretly weak" curve choices than "pick a big prime p" ever was. The entire remaining value of this section is: you do not get to invent your own curve. You use one that a community of cryptographers has tried, for years, to break — which is exactly what §7 does with secp256k1.

ARC 07 · FINAL ARCHITECTURE

secp256k1: the parameters, piece by piece

Bitcoin's curve is defined by the short Weierstrass equation y² = x³ + a·x + b (mod p) with a = 0 and b = 7 — so simply "y² = x³ + 7" that you can say it out loud. Six named constants make the whole system precise. Click each one — pay special attention to p and n: they are both roughly 2²⁵⁶, they are not the same number, and confusing them is a real, documented class of implementation bug.

WHY p AND n ARE DIFFERENT NUMBERS, USED IN DIFFERENT PLACES

p defines arithmetic on coordinates: every point's x and y live in 𝔽p, and every step of point addition (§8) reduces mod p. n defines arithmetic on scalars: private keys, nonces, and the r,s components of a signature are all reduced mod n, because n is the number of distinct points k·G can ever produce — multiplying a scalar by anything beyond n just wraps back around the same cycle of points. Reduce a private key mod p instead of mod n (or vice versa) and you get a different, wrong key that silently fails only some of the time — a real bug class in early, hand-rolled ECDSA libraries.

ARC 08 · INTERNAL IMPLEMENTATION

The group law, scalar multiplication, and ECDSA — derived, not asserted

Four pieces, in dependency order: (a) how "addition" of two curve points is defined geometrically and algebraically; (b) how a private key becomes a public key via repeated addition, and the timing hazard that creates; (c) the ECDSA signing and verification equations, with the algebra that proves verification actually works; (d) what happens — precisely, mechanically — when a signer reuses a nonce; and (e) Schnorr signatures, whose different algebraic shape is why Bitcoin adopted them for Taproot.

(a) Point "addition" is a geometric rule, dressed up as algebra

Elliptic curve points form a group under an addition law defined by a physical picture: draw the line through two points on the curve; it crosses the curve at exactly one third point (cubic curves and lines always intersect in three points, counted correctly); reflect that third point across the x-axis; call the result the sum. Step through it — the canvas uses real floating-point curve arithmetic, computed live, not a fixed illustration.

The algebra behind the picture, for P=(x₁,y₁), Q=(x₂,y₂), both reduced mod p, on y²=x³+ax+b:

P ≠ Q: λ = (y₂ − y₁) · (x₂ − x₁)⁻¹ mod p
P = Q (doubling): λ = (3x₁² + a) · (2y₁)⁻¹ mod p
x₃ = λ² − x₁ − x₂ mod p
y₃ = λ(x₁ − x₃) − y₁ mod p
special cases: P + O = P (O = point at infinity, the identity) · P + (−P) = O, where −P = (x₁, −y₁ mod p)

Every inverse above (·⁻¹) is a modular inverse — computed with the extended Euclidean algorithm, not division — because 𝔽p has no fractions. This is the entire group law. Nothing else is needed to build a public key, a signature, or a verification from it.

(b) Scalar multiplication: double-and-add, and why its timing leaks

A private key d becomes a public key by adding the base point G to itself d times — but not one addition at a time (d is ~2²⁵⁶; the sun would burn out first). Double-and-add walks the bits of d from most-significant to least, doubling a running point every step and adding G only on bits that are 1:

pythondouble-and-add scalar multiplication
def scalar_mult(k, P):
    R = None                    # point at infinity (identity)
    for bit in bits_of(k):     # most-significant bit first
        R = point_add(R, R)      # always: one doubling per bit
        if bit == 1:
            R = point_add(R, P)  # conditionally: one add, ONLY on a 1-bit
    return R

THE TIMING-ATTACK HAZARD — AND WHY PRODUCTION CODE USES A LADDER

Count the "add" lines that actually execute above: exactly one per 1-bit of k — the Hamming weight of the secret. A naive implementation therefore takes measurably different wall-clock time depending on how many of the secret's bits are set, and — worse — which branch executes leaks through cache and power side channels even when total time is masked. An attacker who can measure signing latency (or power draw, on a smart card or hardware wallet) across many operations recovers bits of the secret without ever seeing a byte of it. The fix is a constant-time ladder — the Montgomery ladder is the standard shape — that performs both a doubling and an addition on every single bit, unconditionally, and uses a constant-time conditional swap to pick which running value is "real." Same instructions execute every time, regardless of the secret; the only cost is the wasted operation on 0-bits. Production libraries (libsecp256k1 included) pay this cost as table stakes.

(c) ECDSA: key generation, signing, verification — and why verification works

Key generation. Pick d uniformly at random from [1, n−1] — this is the entire private key, 32 raw bytes. Compute Q = d·G via §8(b)'s scalar multiplication — this is the public key. Because a curve point has two coordinates and curve points are symmetric about the x-axis ((x,y) and (x, p−y) both satisfy y²=x³+7), a public key can be shipped compressed: one byte encoding whether y is even (0x02) or odd (0x03), followed by x alone — 33 bytes instead of the 65-byte uncompressed form (0x04 + x + y), because the missing coordinate costs only the one bit the prefix already carries.

Signing a message m under private key d:

1. z = Hash(m), truncated/interpreted as an integer of n's bit-length
2. choose a nonce k ∈ [1, n−1] ← never reuse this value (§8d)
3. R = k·G; r = R.x mod n — if r = 0, pick a new k and retry
4. s = k⁻¹ · (z + r·d) mod n — if s = 0, pick a new k and retry
5. output signature σ = (r, s)

Verifying σ=(r,s) against message m and public key Q:

1. check r, s ∈ [1, n−1]; z = Hash(m)
2. w = s⁻¹ mod n
3. u₁ = z·w mod n, u₂ = r·w mod n
4. P = u₁·G + u₂·Q
5. accept iff P ≠ O and P.x mod n == r

That verification succeeds for a genuine signature is not a coincidence to take on faith — it falls straight out of substitution:

WHY VERIFICATION SUCCEEDS — THE ALGEBRA

Start from the signing equation and solve for k:

s = k⁻¹(z + rd) mod n
⟹ k = s⁻¹(z + rd) mod n = s⁻¹z + s⁻¹rd = wz + wrd = u₁ + u₂d (mod n)

Substitute that into the verifier's computed point:

u₁·G + u₂·Q = u₁·G + u₂·(d·G) = (u₁ + u₂d)·G = k·G = R

So the verifier's P is exactly R from signing — hence P.x mod n == R.x mod n == r. Nobody inverted a discrete log; the verifier never learns k or d, only that whoever produced (r,s) must have known a d consistent with Q = dG, because that is the only way the substitution above closes.

(d) Nonce reuse: not a bug class — a key-disclosure equation

Everything above assumes a fresh, secret, unpredictable k every single time. Reuse the same k across two different messages z₁ ≠ z₂, signed with the same d, and both signatures share the same r (it depends only on k, via R.x mod n). Watch what falls out:

s₁ = k⁻¹(z₁ + rd) mod n
s₂ = k⁻¹(z₂ + rd) mod n
s₁ − s₂ = k⁻¹(z₁ − z₂) mod n
⟹ k = (z₁ − z₂) · (s₁ − s₂)⁻¹ mod n — solved with nothing but public values
then, from either equation: d = (s₁·k − z₁) · r⁻¹ mod n

Two signatures, one repeated nonce, four field operations — the entire private key falls out in closed form. There is no partial version of this: nonce reuse doesn't weaken a key, it discloses it, completely, to anyone who notices two signatures share an r. §11 covers two incidents where exactly this happened at scale, and §15's simulator runs this exact recovery on a real keypair you generate yourself.

THE FIX: RFC 6979 — DETERMINISTIC NONCES

If k must never repeat, the least fragile design doesn't generate it randomly at all: derive it deterministically from the private key and the message via an HMAC-based construction (RFC 6979). The same (d, m) pair always yields the same k — but different messages yield unpredictably different k values, so two different messages never collide, and signing the same message twice just reproduces the identical, already-valid signature rather than a fresh, dangerous one. This entirely removes a wallet's signature security from depending on the quality of its random number generator at signing time — closing the exact failure mode of both incidents in §11 — while producing signatures that are ordinary, standard ECDSA and verify with no changes on the receiving end.

(e) Schnorr signatures: a linear equation, and what linearity buys you

ECDSA's s = k⁻¹(z + rd) mod n is not linear in d — the k⁻¹ factor multiplies everything, and r itself is a nonlinear function of k. A signature scheme Claus Schnorr published in 1989 does the same job with a strictly linear equation. Key generation is identical (d, Q=dG). To sign m:

1. choose nonce k; R = k·G
2. e = Hash(R ‖ Q ‖ m) — the "challenge": binds the nonce, the public key, AND the message together
3. s = k + e·d mod n
4. signature = (R, s) — BIP340 stores it as (r=R.x, s), 64 fixed bytes, using an x-only, even-y convention

Verification recomputes e and checks s·G =? R + e·Q — which holds because s·G = (k+ed)G = kG + e(dG) = R + eQ, no different in spirit from ECDSA's proof in (c). The difference that matters is structural: s = k + e·d is additive in the secret.

WHY LINEARITY ENABLES AGGREGATION — AND ECDSA CANNOT FOLLOW

Suppose two signers with keys d₁, d₂ want one signature valid under the combined key Q = Q₁+Q₂ = (d₁+d₂)G. With Schnorr, each independently commits to a nonce, the nonces sum to R=R₁+R₂, each computes a partial signature sᵢ = kᵢ + e·dᵢ using the same shared challenge e, and the plain sum s = s₁+s₂ = (k₁+k₂) + e(d₁+d₂) is already a valid single-key Schnorr signature for Q and R — because addition distributes cleanly through a linear equation. Neither signer ever learns the other's private key. This is the basis of MuSig-style key and signature aggregation, and it is exactly what Taproot (BIP340/341, the Bitcoin course) uses to make an M-of-N multisig indistinguishable on-chain from a single signature. ECDSA's s=k⁻¹(z+rd) has no analogous move: the per-signer k⁻¹ factor is entangled with an r that depends on that same signer's k, and no known efficient transformation combines two such equations into one that a single-key verifier accepts. This is not an oversight in ECDSA — it's the reason NIST's 1991 DSA used a nonlinear variant of Schnorr's already-published, cleaner construction in the first place, sidestepping its still-active patent; Bitcoin got the linear version back only in 2021, once the patent had been expired since 2008 and its aggregation properties had been fully worked out.

Signature malleability. For ECDSA, if (r,s) verifies, so does (r, n−s): replacing s with −s mod n flips the sign of w=s⁻¹, which flips the sign of the verifier's point P — but −P shares P's x-coordinate (negation only flips y), so r still matches. Two different byte strings, same message, same key, both valid — enough to let an attacker mutate a transaction's identifying hash without invalidating it (§11 discusses the real-world fallout). The fix, standardized as "low-S" enforcement (BIP 62 / BIP 146), is to require s ≤ n/2 and reject the other root — canonicalizing exactly one of the two valid signatures as the only relay-acceptable one. Schnorr's BIP340 sidesteps the equivalent ambiguity by convention too: it fixes R's y-coordinate to always be even, removing the analogous two-valid-encodings freedom by construction rather than by a policy filter.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

How hard is breaking secp256k1, actually?

The best publicly known attack on a well-formed elliptic curve discrete log is Pollard's rho, expected to succeed after roughly √(πn/4) ≈ 2¹²⁸ group operations for secp256k1's ~2²⁵⁶ order n — not 2²⁵⁶ (a common misreading), but still a number with no known shortcut, and vastly beyond any plausible computation: the entire Bitcoin network's SHA-256 hashing — a completely different, cheaper operation — runs at roughly 2⁹⁰–2⁹² hashes per year in aggregate across every miner on Earth combined; 2¹²⁸ elliptic-curve group operations is roughly ten million trillion times larger than that annual total.

Key size is the whole reason ECC is practical at blockchain scale. The chart below plots the standardized key-size-for-equal-security correspondence (NIST SP 800-57-style figures): the same security level costs roughly 12× more bits under finite-field discrete log than under elliptic curves.

ARC 11 · REAL-WORLD INCIDENTS

Three times §8(d)'s equation ran in the wild

Incident 1: Sony's PS3 root key (fail0verflow, 27C3, December 2010)

The PlayStation 3's code-signing scheme used ECDSA to authenticate firmware and executables — with a fatal implementation choice: Sony's signing code used a fixed, hardcoded nonce k for every signature it ever produced, instead of a fresh one each time. The security researcher group fail0verflow needed only two signed pieces of firmware to run exactly the recovery algebra from §8(d) and extract Sony's private signing key in full. Because the corresponding public key was already baked into every shipped console's trust chain, the key could not be meaningfully revoked — the PS3's entire code-signing security model was permanently broken for already-sold hardware. It remains one of the cleanest real-world demonstrations that nonce reuse is not a theoretical concern.

Incident 2: Android's SecureRandom and stolen Bitcoin (August 2013)

Several Android Bitcoin wallets (built on the bitcoinj library) generated their ECDSA signing nonces using java.security.SecureRandom. Security researchers found that on affected Android versions, the underlying OpenSSL-based PRNG could be insufficiently seeded, producing repeated or low-entropy output across app restarts. Attackers scanning the public blockchain for transactions sharing an r value from the same address ran §8(d)'s recovery and swept the exposed private keys' funds. Wallet developers shipped emergency patches, and affected users were urged to move remaining funds to freshly generated addresses immediately. The episode is widely credited with pushing wallet software across the ecosystem toward RFC 6979 deterministic nonces — so that a wallet's signature security no longer depends on the quality of whatever RNG happens to be available on the device it runs on.

Incident 3: transaction malleability and the Mt. Gox narrative (2014)

Mt. Gox, then the largest Bitcoin exchange, halted withdrawals in February 2014 citing "transaction malleability" as a contributing factor: because a valid signature (r,s) can be rewritten as the equally valid (r, n−s) (§8e), an attacker could alter an outgoing transaction's serialized bytes — and therefore its transaction ID — after broadcast but before confirmation, without invalidating the signature. Mt. Gox's internal accounting reportedly tracked withdrawals by the pre-mutation transaction ID, so a mutated, still-valid transaction could appear to have "failed," prompting a second payout for the same withdrawal. It is genuinely disputed, and was disputed even at the time, how much of Mt. Gox's roughly 850,000 BTC shortfall this mechanism actually explains versus how much was internal mismanagement or theft unrelated to malleability at all — treat the malleability story as a real, exploitable bug that was also present, not a full accounting of what happened. Its lasting effect on the protocol is unambiguous, though: it accelerated BIP 62's low-S canonicalization and later SegWit's separate fix of moving witness data out of the malleable, hashed portion of a transaction entirely.

ARC 13 · CODE WALKTHROUGH

Reading the reference implementation

Bitcoin Core's actual implementation (libsecp256k1) is hand-optimized C: constant-time field arithmetic, the GLV endomorphism trick mentioned in §2, and assembly-tuned modular reduction for exactly this prime. None of that changes the mathematics — it changes only how fast and how safely it runs. The module layout below is reference pseudocode with the same structure and naming a real implementation would use, faithful to the algorithms derived in §8:

pythoncurve.py — the group law, exactly as derived in §8(a)
def mod(a, m):
    return (a % m + m) % m   # Python's % already does this, JS BigInt doesn't

def modinv(a, m):
    # extended Euclidean algorithm — no division exists in a finite field
    old_r, r = mod(a, m), m
    old_s, s = 1, 0
    while r != 0:
        q = old_r // r
        old_r, r = r, old_r - q * r
        old_s, s = s, old_s - q * s
    return mod(old_s, m)

def point_add(P, Q, p, a):
    if P is None: return Q
    if Q is None: return P
    if P.x == Q.x and mod(P.y + Q.y, p) == 0:
        return None                      # P + (-P) = O
    if P.x == Q.x and P.y == Q.y:
        lam = mod((3*P.x*P.x + a) * modinv(mod(2*P.y, p), p), p)
    else:
        lam = mod((Q.y - P.y) * modinv(mod(Q.x - P.x, p), p), p)
    x3 = mod(lam*lam - P.x - Q.x, p)
    y3 = mod(lam*(P.x - x3) - P.y, p)
    return Point(x3, y3)
pythonecdsa_sign.py — sign / verify, exactly as derived in §8(c)
def sign(d, z, k=None):
    k = k or deterministic_k(d, z)     # RFC 6979-style — see below
    R = scalar_mult(k, G)
    r = mod(R.x, n)
    assert r != 0                        # astronomically unlikely; retry with new k if it fires
    s = mod(modinv(k, n) * (z + r * d), n)
    assert s != 0
    return (r, s)

def verify(Q, z, r, s):
    if not (1 <= r < n and 1 <= s < n): return False
    w = modinv(s, n)
    u1, u2 = mod(z * w, n), mod(r * w, n)
    P = point_add(scalar_mult(u1, G), scalar_mult(u2, Q))
    return P is not None and mod(P.x, n) == r
pythonattacks/nonce_reuse.py — §8(d)'s algebra, verbatim
def recover_privkey_from_shared_k(sig1, sig2, z1, z2):
    r, s1 = sig1                       # same r  ⟺  same k was used
    _, s2 = sig2
    k = mod((z1 - z2) * modinv(s1 - s2, n), n)
    d = mod((s1 * k - z1) * modinv(r, n), n)
    return d                            # the FULL private key, from public data alone
WHY IT WAS BUILT THIS WAY — WHAT TO STEAL

1. Curve arithmetic is isolated from signature logic. curve.py knows nothing about hashing, nonces, or signatures — it is pure group theory, independently testable against known test vectors. 2. The deterministic-nonce path is a drop-in for the random one. sign() accepts an explicit k purely so §15's simulator can force nonce reuse on demand — production code never exposes this parameter. 3. Teaching code is not production code. This module trades libsecp256k1's constant-time guarantees for readability; running it as shown would itself be vulnerable to the exact timing attack §8(b) describes. Real wallets link against libsecp256k1 (or an equivalently hardened library) for exactly this reason — hand-rolling ECDSA in an ordinary high-level language is a well-known way to reintroduce every vulnerability this chapter just spent ten sections closing.
