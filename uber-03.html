UBER ENGINEERING INTERNALS · CHAPTER 03

Real-Time Location
Ingestion at Scale

Chapters 1 and 2 both quietly assumed something this chapter finally interrogates: that a driver's position in the index is correct, right now. In production, a driver's phone reports its GPS position over a mobile network that drops packets, reorders them, duplicates them, and sometimes goes dark entirely — inside a tunnel, an underground garage, a dead zone. This chapter derives why "write the driver's position to a table" is the wrong mental model entirely, and what a real streaming-ingestion pipeline has to do instead to keep chapter 2's index honest.

ARC 01 · THE PROBLEM

A stream of unreliable signals, not a database write

Every driver's phone periodically samples GPS and sends the result — a "ping" — to the backend. It is tempting to think of this as a simple write: "update this driver's row with their new position." That framing quietly assumes every ping arrives, arrives once, and arrives in the order it was generated. None of those three assumptions hold on a real mobile network, and the gap between the assumption and reality is this chapter's entire subject.

Four properties of the real input make this a streaming-ingestion problem rather than a database-write problem:

  • Out-of-order arrival. Mobile networks retry, reroute, and buffer packets; a ping generated at t=10.0s can genuinely arrive at the backend after a ping generated at t=10.4s. Any system that blindly applies "the last write wins" can overwrite a correct, newer position with a stale one that simply took a slower network path.
  • Duplicates. A phone that doesn't receive an acknowledgment for a ping within its retry window will resend it — correctly, from the client's perspective, since it cannot distinguish "the ack was lost" from "the ping was lost." The backend must expect and cheaply discard duplicates rather than treating every arrival as a new fact.
  • Total gaps. A driver entering a tunnel, an underground garage, or a dense urban canyon can lose both GPS lock and network connectivity simultaneously, for anywhere from seconds to minutes. The system has no new information during that window and must have a defined, honest behavior for "I don't currently know where this driver is," rather than silently freezing a stale position and presenting it as current.
  • Volume. Even a moderate ping interval across a large online driver fleet produces a sustained, continuous, high-volume stream — this is a firehose to be processed, not an occasional row update.
WHY THIS MATTERS FOR CHAPTER 2's INDEX

Every one of chapter 2's k-ring searches is only as good as the position data it's built on. An index that faithfully implements H3's real hexagonal geometry is still confidently wrong if the driver it says is in cell X actually left cell X ninety seconds ago. This chapter is, in a real sense, "chapter 2's data-freshness problem, solved properly" — the index's geometry was never the weak link; the pipeline feeding it position updates is.

Fleet telematics, IoT sensor networks, mobile-game state sync, and financial market-data feeds all face a version of this exact problem: many independent, unreliable clients producing a continuous stream of time-stamped facts that must be reconciled into a coherent current view despite arriving late, duplicated, or not at all. ARC 03 · NAIVE SOLUTION

Attempt #1: POST a ping, UPDATE a row

The obvious first design, and a reasonable one to try: each phone, every few seconds, sends an HTTP POST with its current lat/lng; the backend handles the request by updating that driver's row in a positions table.

pseudocodenaive_ping.pseudo — the strawman, annotated
// client (driver phone), every ~4 seconds:
function onGpsSample(lat, lng) {
  httpPost("/api/ping", { driverId, lat, lng, clientTime: now() });
  // fire-and-forget: no retry queue, no local buffering
}

// server, per request:
function handlePing(req) {
  db.execute(
    "UPDATE driver_positions SET lat=?, lng=?, updated_at=NOW() WHERE driver_id=?",
    [req.lat, req.lng, req.driverId]
  );                                    // last write wins, whichever request the DB sees last
}

This design is correct in the easy case — a phone with a stable connection, sending pings in order, none lost — and it is simple enough that a small pilot deployment would likely never notice a problem. It gets the basic shape right: a moving fact (position) becomes a row update. The failures below are not implementation bugs in this code; they are structural consequences of the assumptions baked into "one POST, one UPDATE, last write wins."

ARC 04 · WHY IT FAILS

Three independent collapses, and the math behind each

Collapse 1: write volume at fleet scale

Consider an illustrative large metro market with on the order of 50,000 concurrently online drivers (the same illustrative scale used in chapter 1), each pinging roughly every 4 seconds. That alone is 12,500 writes/second for one city — sustained, continuously, for as long as drivers are online, not a burst. A platform running across thousands of cities multiplies this further. A single-row UPDATE per ping, at this sustained rate, is a very different load profile than the occasional-write pattern most relational schemas are tuned for — and this is before considering that every write also needs to eventually reach chapter 2's index (a further downstream fan-out this naive design doesn't even attempt).

Collapse 2: out-of-order writes silently corrupt the "current" position

"Last write wins" means whichever request the database processes last determines the stored position — not whichever ping was generated most recently by the phone. If ping A (generated at t=10.0s) takes a slower network path than ping B (generated at t=10.4s) and arrives at the server after B, the naive UPDATE overwrites B's newer, correct position with A's older, stale one — silently, with no error, and no way to detect it happened without additional bookkeeping the naive design doesn't have.

Collapse 3: gaps are indistinguishable from "driver hasn't moved"

When a driver enters a tunnel and stops sending pings, the naive design simply stops receiving updates — the stored row keeps its last known position indefinitely, with nothing distinguishing "driver is stationary at this exact spot" from "driver's phone has been silent for the last two minutes and could be anywhere within that window's travel radius." Chapter 2's index, and everything downstream of it, has no way to tell the difference without this chapter's fix.

THE NUMBERS

Even setting aside raw volume, the correctness failure is the sharper problem: any out-of-order pair of pings reaching the naive handler in the wrong sequence corrupts the stored position with no signal that anything went wrong. At a sustained tens-of-thousands-of-writes-per-second rate, even a modest percentage of pings arriving out of order (entirely ordinary on real mobile networks) means a continuous, non-trivial stream of silently wrong positions feeding directly into dispatch's candidate search — precisely the kind of bug that is maddeningly hard to detect from server-side metrics alone, because nothing errors; the data is just wrong.

ARC 05 · BETTER SOLUTION

Treat it as a stream: sequence, batch, and back off

The fix reframes the whole problem: instead of "each ping is an independent write," treat the incoming pings as an ordered stream per driver that must be reconciled, and make the client a cooperative participant in reliability rather than a fire-and-forget emitter. Step through the redesign:

From fire-and-forget writes to a reconciled streaming pipelineSTEP-BY-STEP

Three concrete mechanisms carry this fix, and each maps directly to one of §4's collapses:

  • Client-side batching. Instead of one HTTP round-trip per GPS sample, the client accumulates a short window of samples and sends them together, each tagged with its own client-generated timestamp and a monotonically increasing per-driver sequence number. This amortizes connection overhead and reduces the request volume that drives Collapse 1.
  • Sequence-number/timestamp-guarded acceptance. The server tracks the highest sequence number (or client timestamp) it has accepted per driver, and rejects — or explicitly reorders — any incoming ping older than what it already has. This directly fixes Collapse 2: a slow-arriving old ping can no longer silently overwrite a newer position.
  • Exponential backoff with jitter on retry. When a client's batch send fails (no network, no ack), it waits, retries with a growing delay (capped), and jitters that delay slightly across all clients so that a mass reconnection event (an entire tunnel's worth of cars re-entering signal at once) doesn't produce a synchronized retry storm against the backend.
ARC 06 · WHY THAT STILL HURTS

Streaming ingestion is correct — and still has real, ongoing costs

The redesign in §5 fixes the three collapses from §4, but introduces its own real, ongoing engineering costs that a serious system has to keep paying:

  • Backpressure has to be a first-class concept. If the reconciliation and downstream indexing service (chapter 2) can't keep up with the incoming rate — during a demand spike, a partial outage, or a mass reconnection storm — something has to give: buffer growth (risking memory exhaustion), dropped pings (risking staleness), or explicit backpressure signaled to clients (risking clients backing off exactly when data is most needed). None of these are free, and choosing wrong under load is a real, common incident pattern (§11).
  • Deduplication itself costs work. Recognizing and discarding a duplicate ping requires tracking recently seen sequence numbers or timestamps per driver — a real, ongoing memory and lookup cost, multiplied across the entire online fleet, not a one-time fix.
  • Dead-reckoning during gaps is a genuine estimation problem, not a lookup. When pings stop arriving (a tunnel, a dead zone), a system that wants to present a "current position" rather than an honest "unknown" has to estimate — extrapolating from recent velocity and heading — and that estimate is wrong in proportion to how long the gap lasts and how much the driver's actual path deviates from a straight line during it (a turn taken inside a parking garage, for instance).
  • Partitioning and rebalancing the reconciliation layer itself is real distributed-systems work. A single reconciliation process cannot absorb a whole platform's ping volume; the stream must be partitioned (naturally, by driver ID, so all of one driver's pings land on the same worker and preserve their relative order) — and workers joining or leaving that partitioned pool is its own rebalancing problem, directly analogous to consumer-group rebalancing in any partitioned streaming system.
THE HONEST TRADEOFF, STATED PLAINLY

None of these costs are reasons to prefer the naive design from §3 — that design's correctness failures are strictly worse. They are reasons this chapter treats location ingestion as a genuinely substantial piece of infrastructure, staffed and operated as its own system, rather than "a table with an UPDATE endpoint." The final architecture below names the pieces; §8 makes the reconciliation logic itself concrete.

TWO CONSUMERS, TWO DIFFERENT FRESHNESS NEEDS

Notice the pipeline has two structurally different consumers reading the same reconciled stream: the geospatial index (ch. 2) needs the single freshest position per driver, updated as fast as possible, and can discard history once superseded; analytics and trip-history consumers want the entire sequence of positions, including ones the index has already discarded, to reconstruct a full trip's path later. Designing the reconciliation service to serve both without forcing one to slow down the other is a real architectural decision, not an afterthought.

ARC 08 · INTERNAL IMPLEMENTATION

The reconciliation algorithm, made concrete

The core of this chapter's fix is a small, precise piece of logic run per driver: given a new incoming ping, decide whether to accept it as the new "current position," and update a bounded amount of state to make that decision fast and safe against duplicates and reordering.

pseudocodereconcile.pseudo — sequence-guarded acceptance
type DriverState = { lastSeq: number, lastClientTime: number, lat: number, lng: number,
                     lastServerTime: number, velocity: {vx:number, vy:number} };

function reconcile(state[driverId], ping) {
  const s = state[ping.driverId];
  if (s && ping.seq <= s.lastSeq) {
    return { accepted: false, reason: "duplicate_or_stale" };  // Collapse 2 & duplicates, fixed here
  }
  const dt = s ? (ping.clientTime - s.lastClientTime) : 0;
  const velocity = (s && dt > 0)
    ? { vx: (ping.lat - s.lat)/dt, vy: (ping.lng - s.lng)/dt }
    : { vx: 0, vy: 0 };

  state[ping.driverId] = {
    lastSeq: ping.seq, lastClientTime: ping.clientTime,
    lat: ping.lat, lng: ping.lng,
    lastServerTime: now(), velocity
  };
  return { accepted: true };
}

function estimatePosition(s, atTime) {           // dead reckoning during a gap
  const gap = atTime - s.lastServerTime;
  if (gap > MAX_STALE_SECONDS) return { known: false };  // honest "unknown," not a guess
  return { known: true, lat: s.lat + s.velocity.vx*gap, lng: s.lng + s.velocity.vy*gap, confidence: decay(gap) };
}

ARC 09 · TRADEOFFS

Ordering and delivery strategies, compared honestly

APPROACHORDERING GUARANTEEWHAT IT BUYSWHAT IT COSTS
Fire-and-forget, last-write-wins (§3)None — arrival order, not generation order simplest possible client and server silent position corruption under reordering no duplicate handling
Client timestamp orderingAccept only if client timestamp is newer fixes reordering with minimal state depends on client clock accuracy — clock skew across a fleet of phones is real
Monotonic per-driver sequence number (§8)Accept only if sequence number is strictly increasing immune to client clock skew cheap duplicate detection requires the client to maintain and persist a counter across app restarts
At-least-once delivery + idempotent reconciliation (§8's full design)Sequence-guarded, duplicates cheaply discarded tolerates retries and duplicate sends safely no data loss on ack failure reconciliation service must hold per-driver state, at fleet scale

The throughline: every fix that improves correctness under real network conditions requires the server to remember something about each driver's history — a sequence number, a last-known velocity, a staleness clock. The naive design's appeal was statelessness; the real design's cost is exactly the state it must keep to buy correctness back.

ARC 10 · PERFORMANCE / SCALE CHARACTERISTICS

Backlog growth: with and without backpressure

The single most consequential operational number in an ingestion pipeline is what happens to its backlog (pending pings not yet reconciled) when arrival rate exceeds processing rate — a mass reconnection storm, a partial outage of the reconciliation tier, or simply ordinary peak demand. MODEL, NOT MEASUREMENT

The curve is a simple queueing sketch: backlog accumulates at (arrival − capacity) per second when arrival exceeds capacity; with backpressure engaged, the model caps arrival at capacity once backlog crosses a threshold (clients are told to slow down or drop to lower-frequency reporting), trading fresher-everywhere data for a bounded backlog. Without it, backlog — and therefore the average staleness of every position in it — grows without bound for as long as the imbalance persists. The shape is the lesson: a pipeline with no backpressure strategy doesn't degrade gracefully, it degrades unboundedly.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

Two general, well-documented failure patterns this class of system hits

Uber-specific incident postmortems for its location-ingestion pipeline are not public, so this section states the general, industry-documented failure patterns honestly, as real risks any system built this way must design against — not as specific disclosed Uber events.

The reconnection-storm pattern

Any mobile fleet moving through infrastructure with predictable dead zones (a tunnel, an underground garage, a stadium's parking structure) produces a recurring, well-understood failure shape: a burst of devices lose connectivity together, buffer their pending data locally, and then reconnect and flush that buffer simultaneously the moment signal returns — a classic thundering-herd pattern. Without jittered backoff (§5) and backpressure (§10), this arrives at the ingestion tier as a sharp, synchronized spike that can look, from a monitoring dashboard, indistinguishable from a real traffic surge or an attack, and can genuinely overwhelm a tier sized for steady-state load. This is a generic pattern well documented across mobile and IoT systems generally, not a claim about a specific disclosed Uber incident.

GPS drift and "urban canyon" position noise

Dense urban cores with tall buildings on multiple sides famously degrade consumer GPS accuracy — signals reflect off buildings before reaching a phone's receiver (multipath interference), producing position fixes that can be off by tens of meters, and can even appear to "jump" a driver across a street or a city block between two consecutive pings. This is a widely documented general limitation of consumer GPS in dense urban environments, not a defect in any particular company's ingestion pipeline — and it directly motivates dead-reckoning and smoothing logic (§8) that treats a single ping's raw coordinates with some skepticism rather than as ground truth, especially in exactly the dense downtown areas where ride-hailing demand is highest.

THE GENERAL LESSON

Both patterns share a root cause: the physical world (tunnels, buildings, dead zones) does not politely conform to a pipeline's steady-state assumptions. A production-grade ingestion system has to be designed assuming bursts and noise are normal operating conditions it must absorb gracefully, not edge cases it can treat as rare.

ARC 13 · CODE WALKTHROUGH

A representative ingestion-service layout

location-ingestion/ — illustrative layout, not real Uber source
├── client/ — driver-app side
│ ├── ● batcher.ts — accumulates GPS samples, flushes on size or time threshold
│ └── backoff.ts — exponential backoff with jitter on send failure
├── gateway/ingest_endpoint.go — accepts a batch, validates, hands to the partitioned stream
├── reconcile/
│ ├── ● reconciler.go — sequence-guarded acceptance, per §8's pseudocode
│ └── deadreckon.go — velocity-based position estimation during a gap
├── backpressure/admission.go — caps intake and signals clients to slow down when backlog crosses a threshold

TypeScript-style pseudocodebatcher.ts — client-side batching and sequencing
class PingBatcher {
  private buffer: Ping[] = [];
  private seq = loadPersistedSequence();      // survives app restarts — real sequence, not just in-memory

  onGpsSample(lat: number, lng: number) {
    this.buffer.push({ seq: this.seq++, clientTime: now(), lat, lng });
    if (this.buffer.length >= BATCH_SIZE) this.flush();
  }

  async flush() {
    const batch = this.buffer.splice(0);
    try {
      await httpPost("/api/ping/batch", { driverId, batch });
      persistSequence(this.seq);              // only persist AFTER a successful send
    } catch (e) {
      this.buffer.unshift(...batch);              // re-queue; backoff.ts governs the retry timing
      scheduleRetryWithBackoff();
    }
  }
}
Go-style pseudocodeadmission.go — backpressure at the gateway
func (a *Admission) Accept(batch Batch) AdmissionResult {
    if a.backlog.Size() > a.highWaterMark {
        return AdmissionResult{ Accepted: false, RetryAfter: a.backoffHint() }  // tell the client to slow down
    }
    a.backlog.Push(batch)
    return AdmissionResult{ Accepted: true }
}
WHY THIS SHAPE — TWO DECISIONS WORTH STEALING

1. Persist the sequence counter only after a confirmed send. If the client persisted it before sending and the send then failed, the next attempt would use a higher sequence number than the server ever saw — silently creating a gap the server can't distinguish from lost pings. Persisting after success keeps the client's counter and the server's view honestly in sync. 2. Backpressure returns a signal, not silence. An admission decision that simply drops an over-capacity batch gives the client no way to know to slow down; returning an explicit retry hint is what makes §10's "backpressure vs. unbounded backlog" distinction real in code, not just in a chart.
