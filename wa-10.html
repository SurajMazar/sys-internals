WHATSAPP ARCHITECTURE · CHAPTER 10

Storage: Mnesia, Sharding &
Deleting Everything

Most consumer platforms treat data retention as a growth problem: more users means more rows, more disk, more warehouse. WhatsApp inverted the problem. A message that has been delivered to every one of its recipients' devices is deleted from the server — so the steady-state working set stays small no matter how many billions of messages cross the wire in a day. This chapter derives that architecture from first principles: what actually lives in Mnesia, Erlang's built-in distributed database; how a two-billion-account address space gets sharded by user ID; and what breaks first when an engineer is tempted to keep everything instead.

ARC 01 · THE PROBLEM

Storage that gets smaller as traffic gets bigger

Every platform that stores user-generated content faces the same shape of problem: more users and more engagement means more data, and the data only grows. The default trajectory is a warehouse that must be provisioned, replicated cross-region, and defended forever, expanding without bound for as long as the product exists. A message-delivery system built for roughly two billion people looks, at first glance, like the worst version of this problem: on the order of 100 billion messages a day (WhatsApp's own 2020 public figure), a legal and security surface that regulators scrutinize relentlessly, and a user base that expects delivery within a few hundred milliseconds over flaky mobile radios.

WhatsApp's storage architecture answers this by refusing the premise. A message is not an asset to retain — it is a delivery obligation to discharge. The instant a message reaches every one of its recipients' devices, the server's copy of it is deleted. What remains on the server in steady state is not "every message ever sent" but a small, mostly transient set: messages waiting for a recipient who is briefly offline, session and connection state for currently connected clients, group membership, and account metadata. Traffic and storage decouple. A hundred billion messages a day can flow through a server fleet whose disk footprint for message content is bounded by how many messages are in flight at any instant — not by how many have ever been sent.

Derive what that buys, precisely:

  • No message warehouse. There is no multi-petabyte "chat history" data lake to build, replicate, back up, and defend — the single largest and most expensive subsystem in most social platforms' infrastructure simply does not exist for message bodies.
  • Storage does not grow with account tenure. A ten-year user and a ten-day user impose roughly the same server-side storage cost, because neither has message history sitting on the server. Contrast a platform where the server is the source of truth for history: its storage bill grows monotonically with users × years × messages/day, forever, with no natural ceiling.
  • A drastically smaller compliance and breach surface. If a government subpoenas message content, or an attacker breaches the message store, there is — architecturally, not merely by policy — very little content to hand over or steal. WhatsApp's published law-enforcement guidelines state it can produce basic subscriber records and, for messages that are still undelivered, up to roughly the last 30 days; it cannot produce delivered message content, because delivered message content does not exist on its servers to produce.

And here is the honest ledger this chapter has to fill in — what refusing the premise costs:

  • There is no cloud history. Losing a phone without a backup means losing every conversation on it. There is no "log in on a new phone and see the last five years" experience by default, because the server never held five years of anything.
  • The entire client-side backup problem exists because the server-side history problem was refused. Cross-platform transfer (Android ↔ iOS) was, for most of the product's life, close to impossible — precisely because there was no server-held history to hand to the new device; the migration tooling has to move an entire encrypted local database instead.
  • Search and history features must be built entirely client-side against a local database, not a server-side index, because the server has nothing to index.
THE THESIS OF THIS CHAPTER

Every design decision below is downstream of one sentence: the server's job is to move a message from one place to another and then forget it existed. Hold that sentence next to Mnesia's design, the shard router, the 30-day undelivered-message TTL, and the encrypted-backup story, and each stops looking like an isolated engineering choice and starts looking like the same idea, applied consistently, five different times.

ARC 02 · HISTORICAL CONTEXT

From ejabberd's database to a purpose-shaped cluster

WhatsApp was founded in 2009 on top of an existing open protocol — XMPP — and, initially, an existing open-source XMPP server: ejabberd. That inheritance matters more than it looks: ejabberd's default storage engine is Mnesia, Erlang's built-in distributed database. WhatsApp did not evaluate Mnesia against Cassandra, HBase, and a hand-rolled key-value store and pick a winner — it got Mnesia essentially for free, bundled with the server it started from, in a language (Erlang) chosen because its actor-model concurrency was exactly what "millions of persistent, long-lived, per-user connections" needed, independent of the storage question entirely.

What followed was years of forking and rewriting the connection-handling half of ejabberd almost beyond recognition — replacing verbose XML stanzas with a compact tokenized binary encoding nicknamed FunXMPP (documented from the outside by researchers who reverse-engineered the wire protocol, since WhatsApp never open-sourced it), and rewriting the accept loop to handle millions of concurrent sockets per machine — while keeping Mnesia underneath, because ripping it out would have meant solving distributed storage from scratch with an engineering team that, even at the time of the 2014 Facebook acquisition, numbered only about 32 people for roughly 450 million monthly active users. WHY MNESIA EXISTED AT ALL

Mnesia was not built for messaging apps — it was built inside Ericsson for telecom switches, systems that needed soft-real-time, in-memory, distributed state with transactions and no separate database process to operate, because a telephone exchange cannot depend on an external service staying up. That heritage explains every one of Mnesia's defining properties: it stores ordinary Erlang terms directly (no serialization step, no impedance mismatch between "the data" and "the language"), it replicates tables across a cluster of BEAM nodes with location transparency, and it assumes the whole cluster is one trusted, cooperating fleet — not a database serving arbitrary external tenants. That last assumption is precisely the shape of a messaging backend's own cluster, which is why the fit felt natural rather than forced.

ARC 03 · NAIVE SOLUTION

Attempt #1: treat messages like any other app's rows

Derive the architecture honestly, the way a competent engineer would if handed the problem cold: "build a messaging service" sounds, at first, exactly like "build a CRUD app with a messages table." That is not a straw man invented to be knocked down — it is the default choice, and it is what a large fraction of chat products (including some of WhatsApp's own competitors, revisited in §9) actually ship.

SQLnaive_store.sql — the strawman, annotated
CREATE TABLE messages (
    msg_id       BIGINT PRIMARY KEY,
    sender_id    BIGINT NOT NULL,
    chat_id      BIGINT NOT NULL,     -- 1:1 or group
    ciphertext   BYTEA,                -- Signal-encrypted payload, opaque to the server
    sent_at      TIMESTAMP,
    delivered_at TIMESTAMP NULL,
    read_at      TIMESTAMP NULL
);
-- one row per message, ever sent, by anyone, forever.
-- delivered_at and read_at are just columns you update in place.
-- "give me my chat history" is SELECT ... WHERE chat_id = ? ORDER BY sent_at.
-- this is the obvious design. it is also the opposite of what WhatsApp ships.

This is not a joke architecture, and it already gets several things right: full history is available on any device the user logs into, because the server is the source of truth; search, "jump to shared photos", and analytics all fall out for free once the rows exist; and the engineering model is one every backend engineer already knows — shard the table by chat_id or user_id, add read replicas, move on. Telegram's cloud-chat model and Facebook's own Messenger are close cousins of this design, and both are large, successful products (see §9). It is a legitimate architecture. It is just not the one that gets you a two-person storage team serving two billion accounts.

ARC 04 · WHY IT FAILS

The arithmetic of never deleting anything

Put real numbers against the naive schema from §3. WhatsApp has publicly stated it carries on the order of 100 billion messages a day. A text message's on-the-wire payload, after Signal Protocol framing — a Double Ratchet header, an authentication tag, and protobuf-style framing — commonly adds on the order of 50–100 bytes of overhead to a short text body. Take a conservative blended average of ~200 bytes per message including metadata columns (sender, chat, timestamps, indexes):

THE NUMBERS, IF NOTHING WERE EVER DELETED

100,000,000,000 messages/day × 200 bytes ≈ 20 TB/day of raw message rows — for text alone, ignoring media entirely. Annualized, that's ~7.3 PB/year, accumulating on top of every prior year, forever, with no natural ceiling. A typical durability replication factor of 3 (standard for any serious distributed store) triples the physical bytes to roughly 22 PB/year before you've stored a single photo. And media dominates: if even 10% of messages carry an attachment averaging 300 KB (voice notes, photos, short videos), that's 10,000,000,000 × 300 KB ≈ 3 PB per day — two orders of magnitude beyond the text volume, which is exactly why WhatsApp handles media as an entirely separate, aggressively TTL'd subsystem (§6) rather than folding it into any long-term store at all.

The failure is not just about disk cost, though that alone would fund a large infrastructure org. Three second-order effects matter more to an architect:

  • Resharding never ends and never shrinks. A "retain forever" table's shards only grow. Every rebalancing operation moves more historical data than the last one, because the history itself is what's being moved — compare this to a queue-only table (§5) whose shards stay small by construction regardless of how many years the product has existed.
  • The compliance surface becomes a real, queryable liability. "Produce this user's message history" turns from an honest "we don't have it" into a production database query against petabytes of content that now has to be defended, retained under conflicting jurisdictional data-retention laws, and secured against breach — a permanent operational and legal cost center that scales with cumulative lifetime traffic, not with the number of currently active engineers available to manage it.
  • Every dollar of this cost buys a feature almost nobody asked the server to provide. The client already has full plaintext history in its local database (§6) — a decrypted, complete copy the server could never produce without breaking end-to-end encryption anyway. Server-side retention would mean paying petabyte storage costs for a feature (server-held searchable history) that the security model forbids you from fully offering.

So the naive answer is a coherent, popular architecture that is nonetheless the wrong one for this specific product's stated privacy posture and cost structure. What are the actual candidates for what a message-delivery server should retain, and for how long? §5 works through them in order.

ARC 05 · BETTER SOLUTIONS, EXAMINED

A queue, not a database

Candidate A: full retention, sharded properly (the Telegram/Messenger shape)

Shard the naive table from §3 by chat_id or user_id, throw a wide-column store or a well-sharded relational fleet at it, and accept the cost computed in §4 as the price of a genuinely useful feature: seamless cross-device history. This is a legitimate, load-bearing architecture — it is what Telegram's default cloud chats and Facebook Messenger actually do (§9) — but it is a different product bet than the one this chapter is deriving, and §4's math is the reason WhatsApp's founders explicitly rejected it.

Candidate B: pure relay, store nothing, ever

The opposite extreme: never write a message to disk or even to a queue. If the recipient's socket is open, forward the bytes; if not, the message is gone. This has a real attraction — it is the cheapest possible design, architecturally incapable of building the compliance surface from §4. It fails for an unrelated reason: mobile devices are not continuously connected. Radios sleep, apps get backgrounded and killed by the OS, networks drop for seconds to minutes routinely. A pure relay would silently drop a large fraction of all messages sent to anyone whose phone wasn't, at that exact instant, holding an open socket to the right server — unacceptable for a product whose entire value proposition is "the message arrives." Reliable delivery requires holding a message somewhere between "sent" and "device confirms receipt."

Candidate C: retain only until delivered ✓

Store the message — but treat the store as a queue with a deadline, not a database with a schema. Write it once, to the shard that owns the recipient's account; delete it the instant every recipient device has acknowledged receipt; and bound the maximum wait with a TTL (documented publicly at roughly 30 days) so that an account that never reconnects doesn't hold queue space forever. This gets Candidate A's reliability (nothing is lost while it is still needed) with none of Candidate A's unbounded growth (nothing survives past the point where it is no longer needed) — because retention time is now bounded by how long a device can plausibly stay offline, a number measured in days, rather than by how long an account can exist, a number measured in years. Conflating those two durations is the naive model's actual mistake.

THE CLINCHING ARGUMENT: TWO DIFFERENT CLOCKS

An account's lifetime and a device's offline duration are not the same clock, and the naive model's failure is treating them as one. Bound retention to the shorter of the two — how long a real device plausibly stays disconnected — and you get full delivery reliability at a storage cost that never depends on how many years the product has existed. Everything from here (Mnesia's table types, the shard router, the 30-day TTL) is machinery built to enforce exactly this bound.

ARC 06 · WHY THAT STILL HURTS

The bill for deleting on delivery

Candidate C is not free. Its costs are the honest, unavoidable consequences of the same decision that made §1's numbers look good, and every one of them shows up as a real, still-unsolved-feeling product problem:

  • Chat history lives only on the device, in a local SQLite database, encrypted at rest. There is no server-side copy to fall back on. Lose the phone, and — absent a backup — every conversation on it is gone permanently, with no customer-support recovery path, because the company genuinely does not hold the data anywhere.
  • The backup problem is entirely self-inflicted, and entirely necessary. Because the server refuses to hold history, the product needs an independent, client-managed backup story: for years this meant an unencrypted export to iCloud or Google Drive — the widely publicized hole in the end-to-end story, since the cloud provider (and, in principle, anyone compelling the cloud provider) could read a backed-up chat even though the same chat was unreadable in transit. WhatsApp closed this in 2021 with an optional end-to-end-encrypted backup, secured by a user password or a generated 64-digit key, escrowed through an HSM-backed vault so that a forgotten-password recovery can be rate-limited and made tamper-evident without WhatsApp itself ever learning the key (mechanism detailed in §8 and §13).
  • Cross-platform migration was, for over a decade, close to impossible. Moving from Android to iPhone meant moving an entire local, encrypted history file between two completely different OS storage and backup ecosystems with no server-side copy to broker the transfer — a direct externality of there being no server-held history to hand to the new device, and a frequently cited user complaint until dedicated migration tooling arrived.
  • Group fan-out is a write-amplification event at send time, even though nothing persists. A message to a 1,024-member group must be queued once per recipient who is offline — up to 1,024 transient writes for one logical message — all landing, by the sharding rule in §7, whichever shards those 1,024 accounts happen to live on.
  • Delivery now depends on the phone OS's push infrastructure. Because the server can't simply "keep trying" against an idle radio, waking a backgrounded app to collect a queued message depends on Apple's APNs or Google's FCM — an external dependency, and another small piece of metadata (push tokens per device) that must be stored and kept current.
  • Multi-device (2021+) multiplies queue entries per account. A message must now be delivered — and therefore separately queued — once per linked device, not once per account, so the device list itself becomes state that must be tracked precisely (§7's account/device-list table).
THE ANSWER — AND ITS ADMISSION

WhatsApp's actual fix for the missing-history cost was not to relax delete-on-delivery. It was to build an entirely separate, client-controlled, end-to-end-encrypted backup system (2021) that restores continuity through the user's own iCloud or Google Drive storage, encrypted so that neither WhatsApp nor Apple nor Google can read it. That is a tell: the team judged it cheaper and more consistent with their security posture to build an HSM-backed key-escrow protocol from scratch than to reopen server-side message retention even a little. The cost of the thesis was paid in cryptographic engineering, not in storage policy.

ARC 07 · FINAL ARCHITECTURE

The storage constellation

A running cluster, seen from the storage layer outward, is five tiers: the client's own store, the edge connection layer, the routing layer that decides which shard owns a given account, the sharded Mnesia cluster itself, and a set of auxiliary stores that deliberately live outside Mnesia because they have different size and TTL profiles. THE DELIBERATE ASYMMETRY

Notice which things are not in the Mnesia cluster: media blobs and the backup key vault. Both have size and access-pattern profiles that would violate Mnesia's own sweet spot — media is large, chunked, and CDN-served rather than transaction-shaped; the key vault must survive an entirely different threat model (rate-limited brute-force resistance against a hostile party who has the ciphertext) than "keep BEAM nodes in sync." Keeping them out is the same discipline PostgreSQL's postmaster shows toward query execution: a component earns a place in the core cluster only if its access pattern actually matches what the core cluster is good at.

ARC 08 · INTERNAL IMPLEMENTATION

Wire formats, tables, and the delivery state machine

Four pieces, at the level you'd need to reason about a real incident: (a) the two layers of encryption a stored message sits inside, (b) the actual Mnesia table shapes, (c) the shard-routing function, and (d) the delivery state machine that decides exactly when a row gets deleted.

(a) Two layers of encryption, one opaque blob at rest

A queued message is encrypted twice, for two different threat models, and it is worth being precise about which layer protects what. The Signal Protocol (X3DH key agreement, Double Ratchet) encrypts the message payload end-to-end — sender to recipient device — so that the content is unreadable to the server even while it physically sits in a Mnesia row. Separately, the transport between client and edge server is secured with a handshake built on the Noise Protocol Framework ("Noise Pipes" in WhatsApp's own published description) — this layer defends the client–server hop itself against interception and replay, independent of whatever the payload contains. The consequence for storage: what actually lands in the offline-queue table is an opaque ciphertext blob the server must faithfully store and hand back unmodified — it cannot inspect, index, or deduplicate on content, because it structurally cannot read it.

(b) The tables, in Erlang terms

Mnesia tables are ordinary Erlang records, given a storage strategy at creation time. The illustrative shape below (faithful to Mnesia's real semantics, not a literal WhatsApp source excerpt — the source was never published) captures the offline-queue design this chapter has been deriving:

Erlangillustrative offline-queue table definition
%% one row per (recipient, undelivered message) — NOT one row per account
-record(offline_msg, {
    user_id,      % shard key — the account that owns this queue
    device_id,    % multi-device: one queue entry per linked device
    msg_id,
    from_jid,
    ciphertext,   % opaque Signal-encrypted payload — server never reads it
    enqueued_at,
    expires_at    % enqueued_at + 30 days — the undelivered-message TTL
}).

mnesia:create_table(offline_msg, [
    {type, bag},              % many rows share the same user_id — that IS the queue
    {attributes, record_info(fields, offline_msg)},
    {disc_copies, [node() | ClusterNodes]},   % survive a node restart
    {index, [device_id]}
]).

%% session/presence: small, hot, read far more than written — ram_copies is enough
%% because losing a session on crash just means "reconnect", not "lose a message"
-record(session, {user_id, device_id, node, conn_pid, last_seen}).
mnesia:create_table(session, [
    {type, set}, {attributes, record_info(fields, session)},
    {ram_copies, [node() | ClusterNodes]}
]).

The choice of type is not decoration: bag permits many offline messages per user_id (the whole point of a queue), while set on the session table enforces exactly one live session record per device. The choice of disc_copies versus ram_copies encodes exactly how bad it is to lose the row on a crash — worth losing (session, rebuild on reconnect) versus not worth losing (an undelivered message, which is the one copy of that content that exists anywhere on the server side).

(c) Shard routing: user ID as the natural key

Every one of an account's queues, sessions, and group memberships needs to be reachable from a single lookup, because delivering one message touches exactly one recipient's shard. The routing function is therefore keyed on user ID, not on chat ID or message ID — sharding by chat would force a single message send to touch as many shards as the chat has participants; sharding by user means a send touches exactly the shards its recipients live on, no more.

Erlangillustrative shard router
shard_for_user(UserId, NumShards) ->
    %% consistent hashing in production so NumShards can grow without
    %% remapping every key — shown as a simple mod here for clarity.
    erlang:phash2(UserId, NumShards).

route(UserId) ->
    ShardId = shard_for_user(UserId, num_shards()),
    {ok, Node} = directory:lookup(ShardId),   % shard -> physical node, updated on reshard
    Node.

Because each backend chat-server process holds a connected socket's session state in local process memory, routing must be sticky: the same account should reconnect to a server that can reach its owning shard efficiently, and a reconnect should not have to rediscover state that was, moments ago, already in RAM. Sticky routing is what turns "a shard" from an abstract data-ownership boundary into a physically concentrated hot spot — the exact property §6's resharding pain and §15's simulator both exploit.

WHY dirty_write, NOT mnesia:transaction, ON THE HOT PATH

Enqueuing an offline message uses Mnesia's lighter-weight mnesia:dirty_write/1 rather than a full transaction: it skips the two-phase commit coordination across replicas in exchange for lower latency on the single highest-volume write path in the whole system. The correctness argument is that a queue entry is disposable in a way a bank balance is not — worst case on a crash mid-write, a message is redelivered or briefly delayed, and the client-side protocol already tolerates duplicate delivery. Structural changes — creating a group, changing a device list — do use real transactions, because those really do need atomicity across multiple rows.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before you provision a shard

The model's performance envelope, from first principles:

  • Shard lookup: O(1) — a hash of the user ID (or, with consistent hashing, an O(log N) walk of a sorted ring) resolves directly to an owning node; no scatter-gather across shards is ever needed for a single-recipient send, because the routing key is the recipient.
  • Per-connection memory: an Erlang process backing one open socket typically starts around a few hundred words of heap (well under 1 KB) and grows with mailbox depth and session state — orders of magnitude cheaper than a forked OS process, which is precisely how a single machine can plausibly hold state for on the order of 2 million concurrent TCP connections (the widely cited 2012 figure from WhatsApp's own engineering talks), each backed by its own lightweight Erlang process rather than an OS thread or process.
  • Per-shard table size: bounded by accounts_on_shard × avg_offline_fraction × avg_queue_depth × avg_message_size — every term in that product is small and roughly constant, which is exactly why §8's calculator produces megabytes, not petabytes, regardless of how many total accounts the shard has ever served historically.
  • Network round trips, common case (recipient online): sender → edge server (1 hop, Noise-encrypted) → shard lookup (local, in-memory) → recipient's edge server → recipient device, with acks flowing back the same path — typically 2 server-side hops end to end, no disk write required at all if delivery completes before any TTL-driven persistence kicks in.
  • Recipient offline: add one dirty_write to the owning shard (a local, in-memory-first operation with async disk persistence via disc_copies) at send time, and one read plus N deletes at reconnect time, where N is the number of messages that accumulated during the offline window.

ARC 11 · REAL-WORLD PRODUCTION

What has actually been published

The 2014 numbers (Rick Reed, Erlang Factory)

WhatsApp engineering's own public talks — most notably Rick Reed's Erlang Factory presentations around the time of the Facebook acquisition — are the primary public source for hard numbers about this era: roughly 32 engineers supporting on the order of 450–600 million monthly active users through 2014, running on FreeBSD, with individual machines handling upwards of 2 million concurrent TCP connections each. The same talks describe, in general terms, sharding and patching Mnesia to handle that connection and account volume rather than migrating off it — a decision explained by exactly the small-team, no-impedance-mismatch argument developed in §2, and confirmed as deliberate policy rather than mere legacy inertia.

Growth milestones

Publicly reported user-base milestones — roughly 250 million (2013), 450–600 million around the 2014 acquisition, 1 billion (2016), 2 billion (2020) — chart a user base that grew by roughly an order of magnitude across the period this chapter's architecture had to hold. The company's own 2020 statement of ~100 billion messages per day is the throughput figure used throughout this chapter's math in §4 and §10.

The 2GB dets ceiling, historically

Mnesia's disk-based table format (dets) historically capped a single table file at roughly 2 GB, a consequence of 32-bit file offsets in the on-disk format. This is documented, general Mnesia/dets behavior (see the Erlang/OTP documentation and mailing-list history), not a WhatsApp-specific disclosure — but for any operator running Mnesia at WhatsApp's account volume, that ceiling is not a footnote, it is a forcing function: tables must be split across many shards well before raw data volume alone would otherwise require it, purely to stay under a decades-old file-format limit. This is the honest, less flattering half of "sharding by user ID was the natural choice" — it was also, in part, sharding by necessity.

Encrypted backups and multi-device (2021)

WhatsApp's 2021 security-whitepaper update on end-to-end encrypted backups is the public source for the HSM-backed key-vault design referenced throughout this chapter — a user-chosen password or a generated 64-digit key, escrowed such that recovery attempts are rate-limited and the vault itself cannot exfiltrate the key even under compromise. The same year's multi-device architecture announcement is the public source for devices being tracked as first-class per-account state (§7's account/device-list table) rather than the phone being the sole arbiter of an account's identity.

WHERE THIS CHAPTER MUST BE HONEST ABOUT ITS LIMITS

WhatsApp has not published detailed storage-layer incident postmortems the way some infrastructure-first companies do. Specific figures like exact shard counts, per-node table sizes, or the precise consistent-hashing scheme in production today are not public. Everything in §7, §8, §13, and §15 that goes beyond the documented facts above — the exact routing algorithm, the exact table layouts, the exact resharding protocol — is first-principles derivation from Mnesia's published semantics and the general shape confirmed in engineering talks, clearly labeled as such rather than presented as confirmed internal detail.

Two more code excerpts, illustrative but mechanically faithful — first, the enqueue-then-deliver path that drives every offline message through the state machine from §8(d):

Erlangoffline_queue.erl — enqueue and drain, illustrative
enqueue(UserId, DeviceId, Msg) ->
    Row = #offline_msg{
        user_id = UserId, device_id = DeviceId, msg_id = Msg#msg.id,
        from_jid = Msg#msg.from, ciphertext = Msg#msg.ciphertext,
        enqueued_at = erlang:system_time(second),
        expires_at  = erlang:system_time(second) + 30*24*3600  %% 30-day TTL
    },
    mnesia:dirty_write(Row).   %% hot path — see the "why dirty_write" callout in §8

drain_on_reconnect(UserId, DeviceId) ->
    Rows = mnesia:dirty_index_read(offline_msg, DeviceId, #offline_msg.device_id),
    lists:foreach(fun(Row) ->
        deliver_to_device(Row),                       %% push over the live socket
        %% deletion happens on ACK, not here — see await_ack/1 below
        await_ack(Row)
    end, Rows).

await_ack(Row) ->
    receive
        {delivery_ack, MsgId} when MsgId =:= Row#offline_msg.msg_id ->
            mnesia:dirty_delete_object(Row)           %% delivered ⇒ delete NOW, before any read receipt
    after 5000 ->
        ok  %% no ack yet; row stays, will be retried or age out at expires_at
    end.

Second, the resharding sketch that §6 and §15 both reference — moving a live account's queue and session ownership from one shard generation to the next without ever dropping its connection:

Erlangreshard_worker.erl — live key migration, illustrative
migrate_user(UserId, OldShard, NewShard) ->
    directory:mark_migrating(UserId, OldShard, NewShard),  %% new writes now double-routed
    Rows = mnesia:dirty_match_object(#offline_msg{user_id = UserId, _ = '_'}),
    lists:foreach(fun(R) -> mnesia:dirty_write(NewShard, R) end, Rows),
    Session = mnesia:dirty_read(session, UserId),
    %% the session row carries the connection's owning node — moving it, not the
    %% live socket itself, is what "sticky routing follows the account" means
    mnesia:dirty_write(NewShard, Session),
    directory:commit_move(UserId, NewShard),               %% new lookups resolve to NewShard only
    mnesia:dirty_delete(OldShard, offline_msg, UserId),
    mnesia:dirty_delete(OldShard, session, UserId).
    %% the client's live TCP connection to the edge server never had to drop —
    %% only which shard answers "where does this account's state live" changed.
WHY THE ENGINEERS CHOSE THIS

Three choices worth stealing. 1. Sharding by the recipient, not the message. Any alternative key (chat ID, message ID) would force a single send to fan out across as many shards as the conversation has participants; user-ID sharding keeps a send's shard-touch count equal to its recipient count, never more. 2. Dirty operations on the disposable path, transactions on the structural path. A lost queue entry is redelivered; a half-created group is a data-integrity bug — the two paths earn very different consistency machinery. 3. Migrate ownership, not connections. Sticky routing means a client's live socket stays put during a reshard; only the pointer saying "which shard owns this account" moves, which is why resharding a live cluster is possible at all without a mass-reconnect storm — the same discipline PostgreSQL's postmaster shows by never touching a client socket it didn't accept.
