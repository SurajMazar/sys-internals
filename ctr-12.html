CONTAINER INTERNALS · CHAPTER 12

Architecture Showdown:
Daemon vs Fork-Exec

Every earlier chapter treated "the container process" as a fact already in existence and asked what isolates it. This chapter asks the question underneath all of that: which process on the host is responsible for that container's lifecycle — creating it, remembering it exists, capturing its exit code, restarting it if policy says to, answering an API call about it from a different terminal minutes later? Docker answers with a long-lived root daemon; Podman answers by never running one at all. This is the single deepest Docker-vs-Podman comparison in the course, because almost everything else the two engines disagree about — rootless defaults, pod semantics, systemd integration, even networking — is downstream of this one architectural fork.

ARC 01 · THE PROBLEM

Who is actually running your container, and what happens when they die?

Namespaces answer "what can this process see." Cgroups answer "how much can it consume." Capabilities and seccomp answer "what privileged operations can it invoke." All four chapters quietly assumed the container process was already running, already tracked, already something you could query. Something has to make that true — and that something is not a kernel feature at all. It is a userspace design decision, made independently by Docker and by Podman, and the two answers could hardly be more different.

Strip away branding and ask what any container engine's supervision layer must actually provide, given nothing but the OCI runtime primitives from chapter 9 (runc create / start / kill / delete, and nothing else):

  • Durable identity. A name or ID you can query after the command that created the container has finished and exited — "is web-1 still running" has to work from a shell that didn't create it.
  • stdio capture that outlives the client. Whoever launched the container will typically disconnect — close the terminal, lose the SSH session, exit after -d. The container's stdout/stderr must keep being drained and logged by someone, or the container's own writes start failing (§4 makes this precise).
  • Exit-status capture. When the container's init process eventually exits, something must call wait() on it and durably record the code — docker inspect/podman inspect answering "why did it stop" hours later depends on this.
  • A reachable management surface. Something must expose "list/create/stop/exec" independent of exactly which shell happened to run the original launch command — locally at minimum, often remotely too.
  • Optional: continuous supervision. --restart=always means something is watching for the container to exit unexpectedly and deciding whether to bring it back.

Docker's answer is architecturally simple to state: run one privileged process, continuously, for as long as the machine is up, and let it own every one of those five responsibilities in one place. Podman's answer is the opposite: run nothing continuously except a tiny process per running container; let every podman invocation be an ordinary, short-lived CLI process that reads and writes shared state on disk and then exits. Both engines land on the same low-level runtime (runc or crun, chapter 9), the same OCI bundle format, the same namespaces and cgroups — this chapter is about the layer above all of that, where they diverge completely.

WHY THIS MATTERS FOR THE REST OF THE COURSE

The daemon-vs-fork-exec decision is not cosmetic — it is the load-bearing wall behind chapter 13's networking comparison (who holds the IP-allocation table in memory?), chapter 14's pod/systemd model (why Podman's answer to "keep this running" is systemd, not a container-specific watcher), and the incident patterns in chapter 15 (an always-on root socket is a specific, nameable attack surface that a daemonless engine at rest simply does not present). Get this chapter's mechanism right and the rest of the course's Docker/Podman comparisons stop looking like arbitrary trivia and start looking like consequences.

ARC 02 · HISTORICAL CONTEXT

From one monolithic binary to two competing philosophies

Neither architecture arrived fully formed. Docker's daemon started as a single Go binary doing everything; it was pried apart into layers over several years, mostly under pressure from the OCI standardization effort it itself helped start. Podman's daemonless model was a deliberate, later reaction — built by people who had spent years operating dockerd in production and wanted rootless-by-default and systemd-native operation badly enough to rebuild the client side from scratch. DEEP CONTEXT · CONMON'S ORIGIN STORY

Podman did not invent its per-container monitor process from scratch. conmon was built for CRI-O, Kubernetes' own from-scratch, no-Docker-dependency container runtime, which needed exactly the same thing Podman would later need: a tiny, dependency-free C program that could hold a container's stdio open and record its exit status without itself being a heavyweight daemon. Podman adopted conmon directly. The two projects share it to this day — it is genuinely one component, not a parallel reimplementation, which is part of why Podman's daemonless model reached production maturity faster than a ground-up rewrite would have.

ARC 03 · NAIVE SOLUTION

Attempt #1: a nine-line shell script

Derive the architecture honestly, the way the course always does. Chapter 9 already gave you a fully-functional OCI bundle and a runtime that can create and start it. So: what is the simplest possible "container engine" you could build with nothing but runc and a shell?

shnaive-engine.sh — the strawman
#!/bin/sh
# "docker run" in nine lines. No daemon, no client/server split, no logs.
set -e
id=$(uuidgen)
mkdir -p /run/naive/$id
oci-bundle-gen --image "$1" --out /run/naive/$id   # writes config.json + rootfs
runc create "$id" -b /run/naive/$id
runc start "$id"
echo "$id"
# ...that's the whole engine.

For a single, synchronous, foreground run on the machine you're sitting at, this script is not a joke — it works. oci-bundle-gen did the same layer-flattening and config.json generation chapters 9–10 described; runc create/start do exactly what chapter 9 showed. Every namespace, cgroup limit, and capability drop from chapters 2–8 fires correctly. Watch it start breaking the moment real usage patterns show up.

ARC 04 · WHY IT FAILS

Two failures, quantified: the broken pipe and the amnesiac host

The naive script's failures are not vague "it doesn't scale" hand-waving — they are two specific, nameable mechanisms, and both real engines were built around solving exactly these two things.

  • Failure 1 — EPIPE. The container's stdout/stderr are pipes whose read end is held by whatever process launched it. Close your terminal (or let the invoking shell exit) without something else holding that pipe open, and the very next write() the container's process makes to that fd fails with EPIPE (errno 32). Unless the application explicitly ignores SIGPIPE, the kernel's default disposition for that signal is terminate the process. "My container mysteriously died the instant I closed my SSH session" is not a mystery — it is this mechanism, exactly. Both engines solve it the same way: insert a small process, forked before the client can disappear, whose entire job is to hold the read end of that pipe open forever and drain it to a log file.
  • Failure 2 — the amnesiac host. Ask a second terminal "is that container still running?" and the naive script has no answer — there is no persistent record separating "a container this script created" from any other process. Worse: once a process exits, its exit status is available via wait()/ waitpid() exactly once, to its parent, and only if something calls it before the kernel needs the process-table slot back. If nothing does, the process becomes a zombie — a task_struct using kernel memory but executing nothing — until some ancestor reaps it. If the true parent already exited, that duty silently falls to whatever adopted the orphan (PID 1, or a designated subreaper, §8 shows exactly which process that is for each engine) — and by the time anyone asks, nobody remembers which image, ports, or command produced that exit code.
THE ONE IDEA BOTH ENGINES CONVERGE ON

Fix both failures with a single addition: a small process, forked before the client can vanish, that (a) never exits until the container does, (b) holds the container's stdio pipes open and drains them to durable storage, and (c) calls wait() on the container process and records its exit status somewhere a later command can read. Docker and Podman agree completely that this piece must exist. The entire architectural disagreement this chapter is about is what sits above it: does reaching that piece also require going through one big, continuously-running, privileged daemon — or not?

From monolith to daemonlessSTEP-BY-STEP
THE ACTUAL DISAGREEMENT, STATED PRECISELY

Both engines keep a tiny, per-container, always-detached supervisor process (containerd-shim-runc-v2 for Docker, conmon for Podman) — that piece from §4 is non-negotiable and identical in spirit. The disagreement is entirely about whether there is also a persistent central brain sitting above it, holding state in memory and exposing an always-on API: Docker says yes (dockerd, plus containerd underneath it); Podman says no — the "brain" logic runs once per invocation, inside the ordinary podman CLI process, and throws its process away the moment the command returns.

ARC 06 · WHY THAT STILL COSTS

The daemon's bill, and the fork-exec model's bill

Neither design is free. Read this section slowly — it contains the single most commonly misunderstood operational fact in either engine's architecture.

Docker's split genuinely solved the headline problem: since Docker 1.12 (2016) you can systemctl restart docker — kill and relaunch dockerd, even upgrade its binary — and every running container survives untouched. That works because containerd-shim-runc-v2 completely detaches from dockerd's (and containerd's) process tree the moment it is launched — double-fork, setsid(), reparent to PID 1 — exactly as §8 shows in the real syscalls. On restart, dockerd simply reconnects to containerd, and containerd reattaches to each shim's still-open control socket to rediscover what is running. Container uptime is decoupled from daemon uptime, by design.

But "the container keeps running" is a narrower claim than "the daemon is not a single point of failure," and the gap between those two claims is exactly where production incidents happen. Docker's automatic restart policy is not implemented inside containerd or the shim — it lives in dockerd itself, in the component the Moby source tree calls the restart manager. dockerd's libcontainerd client subscribes to a stream of task-exit events that containerd emits over gRPC; when a monitored container's task exits, dockerd's restart manager — not containerd, not the shim — evaluates the policy, computes a backoff, and issues a new CreateTask call. That subscription and its decision loop exist only while dockerd is running.

SO: IF DOCKERD DIES, DOES --restart=always STILL WORK?

Split answer, and the split is the whole point. A container that is already running when dockerd dies keeps running — the shim owns it, not the daemon. But if that same container's process then crashes while dockerd is still down, nothing restarts it: the restart-policy decision loop lives in the daemon that isn't there. The container sits stopped until dockerd comes back up, reconnects to containerd, and reconciles state — at which point it will restart containers it discovers stopped that should be running. There is a real window, exactly as long as the outage, during which "self-healing" quietly does not happen. This is the precise mechanism behind a genuinely common on-call surprise: an upgrade or crash of dockerd itself coincides with an application crash, and the on-call engineer discovers the restart policy "didn't work" — it worked exactly as designed; the daemon that implements it was simply not running at the moment it mattered.

Podman's fork-exec model pays a structurally similar bill from the opposite direction. Because there is no daemon, there is also no always-on process anywhere watching a standalone container for restart-worthy exits. Podman does support --restart on podman run, but for a container not wrapped in a systemd unit that support is necessarily reconciliation-based, not event-driven: Podman ships a podman-restart.service systemd unit that, at boot, runs podman start against containers whose stored policy says they should be running — i.e. restart-on-crash for a bare podman run --restart=always container is honored at the next boot, not the next second. Podman's own guidance for continuous, live supervision is not "build a better watcher" — it is "stop trying to reinvent one": generate a systemd unit for the container (podman generate systemd, or natively via a Quadlet .container file — chapter 14) and let Restart=always in that unit be enforced by systemd, PID 1, the one process on the box even less likely to be down than dockerd. Same underlying question — who watches for crashes — answered by "make the daemon you already trust do it," rather than "run a container-specific one."

There is a second, quieter cost to deleting the central brain: state that used to be a fast in-memory structure inside dockerd — the bridge network's IP-allocation table, the name→ID index, event subscriptions — has to live on disk instead, read fresh under file locks by every independent podman invocation, because no long-lived process holds it in RAM. For a handful of containers this is invisible; chapter 13 shows it becomes a real, measurable design pressure at scale, and is one reason Podman's networking stack moved to netavark+aardvark-dns specifically to cut that per-invocation cost.

THE DETAIL THAT MAKES ALL OF §6 TRUE

Both containerd-shim-runc-v2 and conmon call prctl(PR_SET_CHILD_SUBREAPER, 1) near startup — a Linux 3.4+ flag that says "orphaned descendants of mine should reparent to me, not skip past me to PID 1." That single syscall is what lets runc/crun exit immediately after handing off the container's init process without that process becoming an untracked orphan: it reparents straight to the shim or to conmon, which is precisely why docker logs/podman logs and docker inspect/podman inspect keep working long after the low-level runtime binary that created the container is gone. §8 walks the exact call sequence.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Fewer hops, smaller idle footprint — and where that matters

Docker's chain crosses two IPC boundaries (a Unix-socket REST call, then a gRPC/ttrpc call) and spawns a shim process before runc even runs; Podman's chain is a direct fork()/exec() from the CLI. For a single interactive run, image pull and rootfs setup dominate total latency and the hop-count difference is close to invisible. It stops being invisible once you are launching hundreds or thousands of short-lived containers back to back — CI runners, serverless-style cold starts, batch fan-out — where the fixed per-launch overhead of each IPC boundary is paid every single time.

Security surface is a similar story, measured differently: with dockerd and containerd both running as always-on root processes, the union of their exposed sockets, loaded plugins, and years of accumulated CVE surface (§11) is present whether or not any container is currently running. A rootless Podman host with zero running containers has, by construction, no equivalent root-owned listener anywhere — there is nothing to scan for on that box until you run something. Neither engine is immune to kernel-level container-escape risk once a container is running (that risk lives in namespaces/capabilities/runc-crun, covered generally in chapter 15) — this section is specifically about the always-present, daemon-shaped surface, which is where the two architectures genuinely diverge.

ARC 11 · REAL-WORLD INCIDENTS

Three incidents this architecture, specifically, produced

CVE-2020-15257: the shim's own socket became the attack surface

containerd-shim-runc-v2 exposes a control socket so containerd can reattach to it after a restart (exactly the mechanism that makes §6's "containers survive dockerd restarts" true). That socket was implemented as an abstract Unix socket — a Linux-specific socket namespace with no filesystem path. Abstract sockets are visible across network-namespace boundaries in a way filesystem-path sockets are not: a container configured with --net=host (or one that otherwise shares the host's network namespace) could see and connect to the shim's abstract socket as if it were the host, and speak the shim's own API to it — effectively asking the process supervising your own container to do things on your behalf, as root, from inside the thing it was supposed to be containing. Root cause: an abstraction that was namespace-scoped for everything else (mount, PID, UTS) leaked across the one namespace (network) that abstract sockets don't respect. Fix: moving away from abstract sockets for this API and hardening host-network-sharing defaults. It is a vulnerability class that exists because of the daemon/shim split's own IPC surface — Podman's conmon, communicating over its own local files/pipes rather than an inter-daemon reattachment socket, was not exposed to this specific class.

The exposed docker.sock/2375: root, no authentication, on the open internet

Because dockerd's API is root-equivalent by construction (anyone who can create a container can mount the host filesystem into it), exposing that API without authentication is one of the most consistently exploited container misconfigurations on record. Docker's remote API, bound to TCP port 2375 without TLS, or a docker.sock accidentally mounted into an untrusted container, has been mass-scanned and hijacked by automated cryptomining campaigns for years (security vendors have repeatedly documented botnets — Doki among them — that specifically fingerprint and exploit exposed Docker APIs within minutes of exposure). The mechanism is not subtle: docker -H tcp://target:2375 run -v /:/host -it alpine chroot /host is root on the target host, no exploit required, because the daemon is the root-equivalent single point of trust this chapter has been describing all along. A daemonless, rootless Podman deployment has no equivalent single socket whose mere reachability equals root.

The restart-policy blind spot during a dockerd upgrade

§6's mechanism is not hypothetical — it is a documented, recurring operational pattern: a rolling dockerd upgrade or an unrelated daemon crash coincides with an application-level crash inside a --restart=always container, and the container does not come back until the daemon does. Because the container's own process legitimately exited (its crash, not the daemon's fault), and because containerd itself often stays up and reports the exit correctly at the task level, the failure looks from the outside like "the restart policy silently didn't fire" rather than "the daemon that evaluates restart policy was unavailable for four minutes" — which is the actual root cause every time this pattern has been reported against Moby's restart-manager issue history. The fix operators converge on is the one §6 already named: don't rely on a single centralized restart brain for anything you cannot tolerate losing during a daemon restart — either enable live-restore and treat daemon upgrades as rarer/shorter, or move supervision to something that isn't coupled to the container engine's own uptime at all (an external orchestrator, or — Podman's answer — systemd).

First, Docker's restart manager — the code path that is inert while dockerd is down:

Godaemon/restart_policy.go — simplified but faithful in shape
func (rm *RestartManager) ShouldRestart(exitCode uint32, hasBeenManuallyStopped bool, execDuration time.Duration) (bool, chan error, error) {
    // Only reachable because dockerd's libcontainerd client is, right now,
    // subscribed to containerd's task-exit event stream. If dockerd is down,
    // this function never runs at all -- not "runs and decides no", never runs.
    if hasBeenManuallyStopped {
        return false, nil, nil
    }
    switch rm.policy.Name {
    case "always":
        return true, rm.backoff(), nil
    case "on-failure":
        return exitCode != 0, rm.backoff(), nil
    default:
        return false, nil, nil
    }
}

Second, the shim's launch sequence — the detachment that makes daemon restarts survivable:

Goruntime/v2/shim.go — spawning a detached shim
func spawnShim(bundle string, id string) (*os.Process, error) {
    cmd := exec.Command("containerd-shim-runc-v2", "-namespace", "moby", "-id", id,
        "-address", "/run/containerd/containerd.sock")
    // SysProcAttr.Setsid detaches the shim into its own session --
    // it will NOT die when containerd's process group does.
    cmd.SysProcAttr = &syscall.SysProcAttr{Setsid: true}
    if err := cmd.Start(); err != nil {
        return nil, err
    }
    // The shim's own first act, inside its new process: mark itself a
    // subreaper so runc's container-init handoff reparents HERE, not to PID 1.
    // (equivalent of: prctl(PR_SET_CHILD_SUBREAPER, 1))
    return cmd.Process, nil
}

Third, conmon's own launch sequence, in the shape of the real C source:

Cconmon.c — the detach-and-supervise sequence
int main(int argc, char *argv[])
{
    parse_conmon_args(argc, argv);           /* -c id -u id -r crun -b bundle --exit-dir ... */

    /* Detach fully from whatever exec'd us (podman's CLI process). */
    setsid();
    prctl(PR_SET_CHILD_SUBREAPER, 1);   /* orphans reparent to conmon, not PID 1 */

    int pty_fd = open_container_terminal();   /* holds stdio open past client exit */

    pid_t child = fork();
    if (child == 0) {
        dup2(pty_fd, STDOUT_FILENO);
        execlp(opt_runtime_path, "crun", "create", opt_container_id,
               "-b", opt_bundle_path, NULL);
        _exit(127);            /* execlp only returns on failure */
    }

    conmon_main_loop(child, pty_fd);   /* epoll: drain stdio -> log file,
                                        * wait() for the container's real exit,
                                        * write the code to --exit-dir          */
}
WHY IT WAS BUILT THIS WAY

Every choice above is the same choice, applied twice. Docker's engineers, needing a persistent per-container watcher without recoupling it to dockerd's own restart cycle, gave the shim its own session and a subreaper flag. Podman's engineers, needing the identical property without a daemon to delegate to at all, gave conmon — a plain ~1000-line C program with no daemon framework underneath it — the exact same two calls: setsid() and prctl(PR_SET_CHILD_SUBREAPER, 1). The detachment primitive is universal Linux process-management plumbing, not a container-specific invention; both engines simply apply it at a different point in their respective chains.
