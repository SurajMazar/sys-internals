APACHE KAFKA INTERNALS · CHAPTER 12

Networking &
the Wire Protocol

Kafka's throughput reputation is usually credited to the log. That is half the story. The other half is a hand-designed binary protocol that has been extended for fifteen years without a single flag day, multiplexes thousands of in-flight requests over a handful of long-lived TCP connections, and pushes backpressure to clients by making them wait rather than making them fail. This chapter takes the wire apart byte by byte.

You will be able to read a raw Kafka frame off the wire — size prefix, request header, tagged fields, compact arrays — and say what every byte is doing there.
You will understand why per-API versioning plus ApiVersions negotiation is the only design that survives a 1000-broker rolling upgrade with heterogeneous clients.
You will predict the request-byte curve for full versus incremental fetch at 10k partitions, and the socket buffer size a 90 ms cross-DC replication link needs.
You will simulate a packet inspector, a fetch-session comparison, and a byte-rate quota driving throttle_time_ms until a client settles at its ceiling.
ARC 01 · THE PROBLEM

A protocol is a contract you cannot recall

Start from the deployment reality rather than the packet. A production Kafka cluster is a long-lived, always-on service. It is spoken to by the Java client, librdkafka and everything wrapping it (Python, Go, Rust, C#, Node), Sarama, kafka-go, Spark and Flink connectors, Kafka Connect workers, MirrorMaker 2, ksqlDB, Schema Registry, five years of internal services nobody owns anymore, and — critically — by other brokers, since replica fetchers are just clients with elevated privileges. Those peers were compiled against protocol definitions spanning a decade of releases, and there is no mechanism on earth that upgrades them simultaneously.

Now add the second constraint: the broker is upgraded by rolling restart, one node at a time, over hours or days. During that window the cluster is internally heterogeneous. A 3.6 broker is replicating from a 3.4 broker while serving a 0.10-era consumer and a brand-new 3.7 producer. Every one of those conversations has to succeed. There is no window in which everyone speaks the same dialect, so "everyone speaks the same dialect" cannot be a precondition for correctness.

The third constraint is the one people forget: the protocol is the cost centre. Kafka moves gigabytes per second per broker. If framing costs 200 bytes per request and you serve 400k requests/sec, that is 80 MB/s of pure overhead on the NIC before a single record moves. If a fetch request has to enumerate every partition it is interested in, and a follower is interested in 6,000 partitions, the question becomes larger than the answer during idle periods. Protocol design decisions here are not aesthetic; they are directly visible in p99 latency and in the cloud bill.

THE ACTUAL PROBLEM STATEMENT

Design a request/response protocol that is (1) compact enough that framing overhead is negligible at 500k req/s, (2) multiplexed so one TCP connection carries many concurrent in-flight requests without head-of-line blocking on the application layer, (3) independently evolvable per operation so a new field in Fetch does not force a redeploy of every producer on the planet, (4) self-describing at connect time so a client can discover what a broker supports before it sends anything it might regret, and (5) self-throttling so a misbehaving tenant degrades gracefully instead of taking down the request handler pool.

Those five requirements pull against each other. Compactness argues for fixed-offset binary structs with no field names on the wire — but fixed layouts are exactly what makes evolution painful. Multiplexing argues for correlation identifiers and out-of-order completion — but out-of-order completion is what breaks per-partition ordering guarantees when a producer retries. Self-throttling argues for the broker rejecting excess load — but rejection pushes retry logic into every client, and clients are the part of the system you do not control. Everything in this chapter is a resolution of one of those tensions.

One more framing note before we descend. Kafka's protocol is not layered on HTTP, gRPC, AMQP, or anything else. It is a bespoke binary protocol over raw TCP, defined today by JSON schema files that are code-generated into Java classes at build time. Every design decision that follows was made by people who could have taken a dependency and chose not to; part of the work in this chapter is reconstructing why each of those refusals was correct — and, in a couple of places, where the refusal has aged badly.

ARC 03 · NAIVE SOLUTION

The strawman: one global version, fixed structs

Suppose you are writing Kafka in 2011 and you need a wire format by Friday. The obvious design — the one nearly every in-house RPC system starts with — is a fixed binary struct per operation, a single global protocol version number in the header, and a switch statement on that version. It is fast to implement, trivially fast to parse, and it works perfectly right up until you have two versions in production at once.

JAVA · STRAWMANNaiveProtocol.java — do not ship this
// One version number for the ENTIRE protocol. Bump it and everything moves.
static final short PROTOCOL_VERSION = 7;

// Fixed header. Every field mandatory, every offset hard-coded.
//  0..3   int32   size (bytes that follow)
//  4..5   int16   apiKey
//  6..7   int16   PROTOCOL_VERSION   <-- global, not per-API
//  8..11  int32   correlationId
// 12..    string  clientId (int16 len + bytes)

void writeFetchRequest(ByteBuffer b, List<TopicPartition> parts, Map<TopicPartition,Long> offs) {
  b.putInt(0);                       // size placeholder, back-filled at the end
  b.putShort(API_FETCH);            // 1
  b.putShort(PROTOCOL_VERSION);     // 7 — the ONE knob
  b.putInt(nextCorrelationId());
  writeString(b, clientId);

  b.putInt(replicaId);
  b.putInt(maxWaitMs);
  b.putInt(minBytes);
  b.putInt(parts.size());           // EVERY partition, EVERY request
  for (TopicPartition tp : parts) {
    writeString(b, tp.topic());     // topic name repeated per partition
    b.putInt(tp.partition());
    b.putLong(offs.get(tp));
    b.putInt(maxBytesPerPartition);
  }
  backfillSize(b);
}

// Parsing: offsets are implicit in the code. Add a field anywhere
// and every reader compiled against the old layout reads garbage.
Fetch parse(ByteBuffer b) {
  short ver = b.getShort(6);
  if (ver != PROTOCOL_VERSION) throw new UnsupportedVersionException();  // !!!
  ...
}

Read the two highlighted lines and the throw together, because they are the whole failure mode in miniature. The throw says: a peer at a different version is an error. The loop says: the cost of asking a question scales with the size of your subscription, not with the size of the answer. Neither is a bug in the code. Both are direct consequences of the design.

The strawman also makes a subtler mistake worth naming now, because Kafka's real protocol makes the opposite choice deliberately: the layout is described only by the code that reads and writes it. There is no machine-readable schema, so the Java client, librdkafka, Sarama and the broker each hand-maintain their own copy of the byte offsets. Three of the four will eventually disagree, and the disagreement will present as a corrupt-record exception in production at 3am, not as a compile error.

ARC 04 · WHY IT FAILS

Three walls, with numbers

Wall 1 — you cannot upgrade 1,000 brokers atomically

A single global protocol version implies a flag day. To move from version 7 to version 8 every broker and every client must switch at the same instant, because a v7 peer talking to a v8 peer throws. On a 1,000-broker cluster a rolling restart with controlled leadership movement takes on the order of 2–6 minutes per broker once you account for graceful shutdown, log recovery, and waiting for under-replicated partitions to return to zero before touching the next node. That is 33 to 100 hours of wall clock in which the cluster is mixed-version. A flag day is not "difficult" here; it is arithmetically impossible without a full outage, and the entire point of a replicated log is that it does not need one.

Worse, brokers are not the long tail — clients are. A large organisation has thousands of client deployments on release cadences ranging from weekly to never. If the wire format is a single version number, the cluster's protocol version is pinned to the oldest client anyone still cares about, forever. New features become un-shippable not for technical reasons but for organisational ones.

Wall 2 — every field change is a breaking change

Under fixed-offset structs, adding rack_id to a fetch request shifts every subsequent byte. There is no "ignore unknown field" because there are no field boundaries at runtime — the reader knows only offsets. So a purely additive, backward-compatible-in-intent change becomes a total protocol break. Kafka has added, by rough count, well over a hundred fields across its APIs since 0.8. Under the strawman that is a hundred flag days.

THE COMPOUNDING FAILURE

The two walls interact multiplicatively. Because every change is breaking, changes get batched into big-bang releases to amortise the pain. Because releases are big-bang, they are risky, so they are rare. Because they are rare, each one carries more changes, so it is riskier still. Protocols designed this way ossify within about three years — which is precisely the observed lifespan of most in-house binary RPC formats before someone proposes "let's just move to gRPC".

Wall 3 — the question costs more than the answer

Take a concrete follower. A dense broker in 2024 hosts 4,000–10,000 partition replicas; suppose this one follows 6,000 partitions from a single leader, with an average topic name of 24 bytes. Per partition the strawman writes: 2 bytes topic-name length + 24 bytes name + 4 bytes partition index + 8 bytes fetch offset + 4 bytes max bytes = 42 bytes. Times 6,000 = 252,000 bytes ≈ 246 KB per fetch request.

Replica fetchers poll continuously; with replica.fetch.wait.max.ms at its 500 ms default and traffic arriving steadily, a follower issues roughly 2–10 fetches per second per leader. At 5 fetches/sec that is 1.2 MB/s of request bytes to a single leader, from a single follower, carrying zero payload. On a 30-broker cluster where every broker follows every other, the aggregate is measured in hundreds of megabytes per second of pure question. During quiet hours, when most of those partitions have no new data, the response is a few hundred bytes and the request is a quarter megabyte — a signal-to-overhead ratio of roughly 1:1000.

THE PART THAT ACTUALLY HURT

Bandwidth was the visible symptom; CPU was the real one. Every one of those 6,000 entries has to be parsed, its topic name UTF-8 decoded into a String, hashed, and looked up in the broker's partition map — on a request handler thread, per fetch, per follower. Before KIP-227, profiles of idle-but-dense clusters showed request-handler threads spending a double-digit percentage of their time deserialising fetch requests for partitions that had no new data. The GC pressure from the transient String and TopicPartition allocations was itself a documented pathology.

So the strawman fails on evolvability (walls 1 and 2) and on scale (wall 3), and the two failures need different fixes: versioning solves evolution, session state solves the metadata tax. Kafka's real protocol contains both, and it is worth noticing that they were introduced six years apart — 2015 and 2018 — which tells you they were felt as separate pains, not designed together.

ARC 05 · BETTER SOLUTION

Candidates, examined and eliminated

Given the walls, four designs are on the table. Three of them are wrong, and being able to say precisely why each is wrong is the difference between knowing Kafka's protocol and understanding it. Step the deck.

Versioning strategies — the elimination tournament5 STEPS

The winning combination is worth stating as a single sentence, because interviewers ask for exactly this sentence: every API is independently versioned; on connect the client sends ApiVersions (itself versioned, and deliberately frozen at v0-compatible framing so it can always be parsed); the broker replies with, for each api_key, the minimum and maximum version it supports; the client intersects that with its own supported range per API and picks the highest common version for every subsequent request. Negotiation is per-API, computed once per connection, and cached.

WHY THE INTERSECTION IS COMPUTED CLIENT-SIDE

The broker could have chosen the version and told the client. It does not, and the reason is asymmetry of knowledge: the broker learns nothing about the client's capabilities from a bare connection, while the client learns everything about the broker's from one ApiVersionsResponse. One round trip, client-side arithmetic, no state on the broker. The broker's only obligation is to answer honestly and to reject requests whose version falls outside its advertised range — UNSUPPORTED_VERSION, error code 35 — which is a defence against buggy clients, not part of the normal path.

Flexible versions (KIP-482) then refine the scheme along an orthogonal axis. Independent per-API versioning solves "I want to add a field to Fetch without touching Produce". It does not solve "I want to add an optional field to Fetch without forcing every implementation to learn a new version number". Tagged fields do: within a flexible version, the encoder appends a varint count of tagged fields followed by (tag, size, payload) triples, and any decoder that does not recognise a tag skips it using the size and moves on. Unknown-but-skippable is the property that turns additivity from a version-bump into a no-op.

The same KIP took the opportunity to fix a decade-old wire inefficiency. Classic Kafka strings are int16 length + UTF-8 bytes; classic arrays are int32 count + elements; nullability is signalled by length -1. Flexible versions replace both with unsigned varint length+1 encodings — a "compact string" of length 8 costs one length byte instead of two, an array of 3 elements costs one byte instead of four, and null is varint 0. On a metadata-heavy response listing 10,000 partitions the saving is single-digit percent, which sounds unexciting until you multiply it by every metadata refresh from every client in a fleet.

ARC 06 · WHY THAT STILL HURTS

What versioning does not buy you

Per-API versioning plus tagged fields makes the protocol evolvable. It makes it neither cheap nor fair, and four separate costs remain — each of which drove a later piece of machinery.

The metadata tax survives versioning entirely

Wall 3 from section 4 is untouched by anything in section 5. FetchRequest v11 with compact arrays is a few percent smaller than v4; it is still O(partitions) per request. Versioning is a schema-evolution mechanism, and the fetch overhead is a protocol semantics problem: the client re-states its entire subscription every time because the protocol is stateless per request. The fix has to change what a fetch means, not how it is encoded — which is exactly what KIP-227 fetch sessions do, and why they needed a KIP rather than a version bump.

Connections are not free, and TLS makes them expensive

A plaintext TCP connection costs one round trip (SYN, SYN-ACK, ACK) plus an ApiVersions round trip plus, usually, a Metadata round trip before the first useful byte moves. On a 1 ms intra-DC link that is ~3 ms of setup — irrelevant if the connection lives for hours, ruinous if your client library opens a connection per request.

Add TLS and the arithmetic changes character. A full TLS 1.2 handshake is two round trips on top of the TCP handshake and, critically, costs an asymmetric-crypto operation on the broker: an RSA-2048 private key operation is on the order of 1–2 ms of CPU (ECDSA P-256 is faster but still tens of microseconds, and RSA remains extremely common in enterprise PKI). TLS 1.3 cuts it to one round trip but the signature cost stands. A broker facing 2,000 reconnects per second because a client fleet has a short idle timeout or a load balancer with an aggressive connection cap is spending entire cores on handshakes. This is the single most common self-inflicted Kafka CPU incident after log compaction misconfiguration.

THE SECOND TLS COST — ZERO COPY DIES

Plaintext fetch responses can be served with FileChannel.transferTo(), which becomes sendfile(2) and moves bytes from page cache straight into the socket buffer without ever entering the JVM heap. TLS requires every byte to be encrypted, which means every byte must be copied into user space, run through the cipher, and written back. As covered in the storage chapter, enabling TLS on a fetch-heavy broker typically costs 20–40% throughput and materially raises GC pressure, because the bytes now transit heap buffers. AES-NI makes the cipher itself cheap; it is the copy and the allocation that hurt.

Nagle's algorithm actively fights a request/response protocol

Nagle (RFC 896) says: if there is unacknowledged data outstanding, buffer small writes until either the ACK arrives or a full MSS accumulates. It exists to stop telnet from sending one-byte packets. It is catastrophic for request/response RPC when it meets delayed ACK (RFC 1122), where the receiver waits up to 200 ms (40 ms on Linux typically) before ACKing in the hope of piggybacking. The interaction is the classic deadlock-ish stall: sender has a small write pending, will not send it because it awaits an ACK; receiver has nothing to send, so it delays the ACK. Result: a 40–200 ms latency spike on a request that should have taken 1 ms, appearing sporadically and only under low load — the hardest possible latency bug to diagnose.

Kafka's answer is to disable Nagle unconditionally (TCP_NODELAY on every socket, both broker and client) and to do coalescing at the application layer instead, where it can be reasoned about: the producer's record accumulator batches by batch.size and linger.ms, and the fetcher batches by fetch.min.bytes and fetch.max.wait.ms. Application-level batching is strictly better than kernel-level batching because the application knows what a logical unit is and the kernel does not.

Fairness is not a property of a protocol

Nothing so far stops one client from consuming the entire broker. A single consumer issuing unbounded fetches will saturate the NIC; a single producer with 100 in-flight requests will monopolise the request handler pool; and in a multi-tenant cluster the victim is a completely unrelated team. You need admission control — and the interesting design question, deferred to section 8, is not whether to throttle but what shape the throttle signal takes, because "return an error" pushes complexity into a thousand clients you do not control.

ARC 07 · FINAL ARCHITECTURE

The network stack, component by component

Kafka's server-side networking is a textbook reactor — a small fixed set of threads doing non-blocking I/O, feeding a bounded queue that a separate, larger pool of worker threads drains. The separation is deliberate and load-bearing: I/O threads must never block, because one blocked selector stalls every connection it owns; work threads may block on disk and on purgatory, because there are many of them and blocking one costs only that one. Kafka network stack explorerCLICK A COMPONENT

Trace one request end to end and the design justifies itself. A TCP SYN lands on a listener socket owned by an Acceptor; the acceptor's selector wakes on OP_ACCEPT, calls accept(), sets TCP_NODELAY and the configured send buffer on the new channel, and hands the SocketChannel to one of its processors by round-robin, pushing it onto that processor's newConnections queue and waking its selector. The acceptor does nothing else — it never reads a byte — because accepting is the one operation that cannot be sharded and must therefore be kept trivially fast.

The processor's loop registers the channel for OP_READ, and from then on all traffic on that connection belongs to exactly one processor thread for the connection's lifetime. That affinity is what makes the per-channel state machines lock-free: only one thread ever touches a given KafkaChannel's receive and send buffers. When a complete frame has been read the processor parses only the header, wraps the remaining bytes in a RequestChannel.Request, and enqueues it. It does not parse the body — body parsing happens on the handler thread, so that deserialisation CPU is charged to the pool sized for CPU work rather than the pool sized for socket readiness.

The queue itself, RequestChannel.requestQueue, is an ArrayBlockingQueue bounded by queued.max.requests (default 500). Boundedness is the whole point: when handlers fall behind, the queue fills, processors block on put, they stop reading from their sockets, the kernel receive buffers fill, the TCP window closes, and the sender is throttled by flow control. Backpressure propagates all the way to the client's socket with no application-level protocol involvement at all. An unbounded queue would convert that clean stall into an unbounded heap growth followed by an OOM.

WHY RESPONSES GO BACK THROUGH THE ORIGINATING PROCESSOR

Each processor has its own response queue, and a response carries the id of the processor that read the request. A handler thread finishing work does not write to the socket itself — it enqueues onto processor.responseQueue and wakes that selector. This preserves single-threaded ownership of the channel (no locking around partial writes) and it is what makes the mute/unmute discipline possible: the processor mutes a channel when it hands a request off and unmutes only when the response has been fully flushed, which is how Kafka enforces at most one in-flight request per connection at the broker while still allowing the client to pipeline into the socket buffer.

ARC 08 · INTERNAL IMPLEMENTATION

Bytes, state machines, and the algorithms on them

Framing: the four bytes that make TCP usable

TCP is a byte stream with no message boundaries; a single read() may return half a request or two and a half requests. Every protocol over TCP must therefore impose framing, and Kafka's choice is the simplest one that works: a 4-byte big-endian signed int32 length prefix giving the number of bytes that follow, then that many bytes. NetworkReceive holds a 4-byte size buffer and a lazily allocated payload buffer; each readable event fills the size buffer first, then allocates exactly size bytes and fills that. A receive is "complete" only when the payload buffer has no remaining capacity.

Two consequences fall straight out. First, the size prefix is validated against socket.request.max.bytes (default 104857600, 100 MB) before allocation — otherwise a hostile or corrupt 4-byte prefix of 0x7FFFFFFF becomes an instant 2 GB allocation and an OOM. Second, big-endian ("network byte order") is not an aesthetic choice: it lets a reader compare and sort byte-wise and matches Java's ByteBuffer default, so no per-field byte swapping is needed in the JVM implementation.

Anatomy of a request frame6 STEPS

The header, and why correlation_id is the multiplexing primitive

Request header v0 is api_key: int16, api_version: int16, correlation_id: int32. v1 adds client_id: nullable_string. v2 is v1 in flexible encoding with a trailing tagged-field section. The response header mirrors it with just correlation_id (v0) or correlation_id plus tagged fields (v1). That is the entire envelope — twelve to twenty bytes, no message type strings, no content negotiation, no framing metadata beyond the length.

correlation_id is a monotonically increasing per-connection integer assigned by the client. It exists for exactly one reason: the client may have N requests outstanding on a connection and responses need not be matched positionally. In practice Kafka brokers do respond in order on a given connection (the mute discipline above guarantees it), so NetworkClient keeps InFlightRequests as an ArrayDeque per node and pops from the tail — O(1), no hash lookup. The correlation id is then used as an assertion: if the id on the response does not equal the id of the request popped from the deque, the client raises IllegalStateException and disconnects, because a mismatch means the stream is desynchronised and nothing after it can be trusted.

A DESIGN YOU SHOULD BE ABLE TO CRITIQUE

Because responses are in-order per connection, Kafka has application-level head-of-line blocking: a slow Fetch sitting in purgatory for fetch.max.wait.ms delays a Metadata response queued behind it on the same connection. HTTP/2 and Pulsar avoid this with true out-of-order completion. Kafka's mitigation is cruder and works: clients open separate connections for separate purposes — the consumer's coordinator connection is distinct from its fetch connections, and the producer's metadata refresh may ride a different node entirely. Node-id-keyed connection maps in NetworkClient, not stream multiplexing, are how the problem is dodged.

Schema-driven serialization: the protocol is data, not code

Since around 2019 Kafka's wire format lives in JSON files under clients/src/main/resources/common/message/ — FetchRequest.json, ProduceResponse.json, ApiVersionsRequest.json and about 150 others. Each declares an apiKey, a validVersions range, a flexibleVersions threshold, and a field list where every field carries its own versions constraint, its type, and optionally a tag and taggedVersions. A Gradle task runs the generator in generator/src/main/java/org/apache/kafka/message/ and emits Java classes with read/write/size methods into clients/build/generated/.

The engineering argument for this is worth spelling out, because it is the same argument that justifies protobuf and is usually made badly. It is not "less boilerplate". It is that the schema becomes a single source of truth that can be mechanically checked: a CI test parses the JSON of the current branch against the JSON of the previous release and fails the build if any field's version range narrowed, if a field changed type, or if a tag was reused. Compatibility stops being a code-review responsibility and becomes a compiler-enforced invariant. When your protocol has 150 APIs at 10+ versions each, human review is not a viable compatibility strategy.

Flexible versions and tagged fields, byte by byte

From flexibleVersions onwards three things change simultaneously. Strings become compact strings: an unsigned varint holding length + 1, then UTF-8 bytes, with 0 meaning null. Arrays become compact arrays: unsigned varint count + 1, then elements, 0 meaning null. And every struct — including the header — gains a trailing tagged-field section: an unsigned varint count of tagged fields, then that many (tag: uvarint, size: uvarint, data: size bytes) triples in ascending tag order.

The skip rule is what makes this work: a decoder reads the tag, and if it does not recognise it, reads the size and advances the buffer position by exactly that many bytes. Ascending tag order lets a decoder short-circuit and it makes the encoding canonical. Because the empty case costs a single 0x00 byte, adding the tagged-field section to every struct cost about one byte per struct — a price the community explicitly weighed and accepted in KIP-482.

A varint encodes seven bits of payload per byte with the high bit as a continuation flag, so values 0–127 cost one byte, 128–16383 cost two, and so on. Since the overwhelming majority of Kafka's arrays and strings are short — topic names are tens of bytes, partition lists per topic are tens of entries — compact encoding replaces a 2- or 4-byte fixed prefix with one byte almost always. It is a small constant factor applied an enormous number of times.

ApiVersions: the one request that can never change shape

There is a bootstrap paradox in any negotiated protocol: to negotiate you must already agree on the negotiation message. Kafka resolves it by treating ApiVersionsRequest as effectively immutable in its parseable prefix. A broker receiving an ApiVersions request at a version it does not support does not disconnect — it replies with an ApiVersionsResponse at version 0 carrying error code 35 (UNSUPPORTED_VERSION) plus its supported range, so the client can retry at a version the broker understands. That special case is hard-coded in KafkaApis.handleApiVersionsRequest and it is the only place in the protocol where an error response is deliberately sent at a different version than the request. Without it, a newer client could never talk to an older broker at all.

The response body is a compact array of {api_key: int16, min_version: int16, max_version: int16}. NodeApiVersions on the client stores it and exposes latestUsableVersion(apiKey, oldestAllowed, latestAllowed), which returns the highest version in the intersection or throws UnsupportedVersionException if the intersection is empty. Since Kafka 2.4 the response also carries the broker's finalized and supported feature ranges as tagged fields (KIP-584) — the same negotiation pattern lifted from wire formats to cluster-wide feature flags, which is what KRaft metadata versioning is built on.

WHERE NEGOTIATION MEETS THE STORAGE FORMAT

Negotiating down is cheap for most APIs and expensive for exactly one: fetch. If a client negotiates an old Fetch version, the broker must serve records in the record-batch format that version implies. When the log on disk holds v2 batches and the client can only read v0/v1, the broker performs down-conversion — the message format conversion cost covered in chapter 10. Down-conversion reads the batch into heap, re-encodes it per record, and thereby destroys the sendfile() zero-copy path for that response. One legacy client can push a broker's CPU and GC into a different regime. This is why FetchMessageConversionsPerSec and ProduceMessageConversionsPerSec are metrics you should alert on: they are the "someone is still on an old client" alarm.

Fetch sessions (KIP-227): making the question incremental

The derivation from section 4 is: fetch requests are O(partitions) because they are stateless, and they are mostly redundant because a follower's partition set changes rarely while its fetch offsets change constantly — and even offsets only change for partitions that actually received data. So make the broker remember.

On the first fetch a client sends session_id = 0, session_epoch = 0 and the complete partition list — a full fetch. The broker's FetchSessionCache allocates a session, stores the partition set with each partition's last-known fetch offset and metadata, and returns a non-zero session_id with session_epoch = 1. Every subsequent fetch is incremental: the client sends that session id, the next epoch, and only (a) partitions whose fetch offset changed since the last request, (b) newly added partitions, and (c) removed partitions listed in ForgottenTopicsData. A steady-state follower on 6,000 partitions where 50 had data sends 50 entries, not 6,000.

Two details carry all the correctness weight. The epoch is a strictly incrementing counter that detects lost or reordered requests: if the broker sees an epoch other than the one it expects, it replies INVALID_FETCH_SESSION_EPOCH (error 71), the client drops to session_id = 0 and re-sends a full fetch, and the system self-heals. It is exactly the fencing-token pattern used elsewhere in Kafka for leader epochs. The cache is bounded by max.incremental.fetch.session.cache.slots (default 1000) with LRU-ish eviction that privileges followers over consumers — because a broker with 5,000 consumers cannot keep state for all of them, and the graceful degradation for a client denied a session is simply session_id = 0 forever, i.e. the pre-KIP-227 behaviour. Degrading to "slower but correct" rather than "error" is the recurring shape of good protocol design.

Quotas: throttling by delay, not by rejection

Kafka enforces two families of quota, both configured per (user, client-id) tuple in ZooKeeper or the KRaft metadata log and both implemented on top of the same Sensor/Quota primitives from org.apache.kafka.common.metrics. Byte-rate quotas (producer_byte_rate, consumer_byte_rate) cap bytes per second. Request-rate quotas (request_percentage, KIP-124/KIP-219) cap the percentage of request-handler and network-thread time a principal may consume — the unit is "percent of one thread", so 200 means two full threads' worth, and it exists because a client can saturate CPU with tiny requests while using almost no bandwidth.

The measurement is a sliding window: quota.window.num samples (default 11) of quota.window.size.seconds each (default 1), giving an ~11-second window with 1-second granularity. When a rate exceeds the bound, ClientQuotaManager.recordAndGetThrottleTimeMs computes how long the client must be silent for the windowed average to fall back to the quota:

SCALAclients/.../metrics/stats/Rate.java + core/.../ClientQuotaManager.scala — the essential arithmetic
// observed  = bytes recorded in the window
// bound     = quota * windowSizeSeconds  (bytes allowed in that window)
// If observed > bound, we must extend the window until the average fits.
def throttleTime(observed: Double, bound: Double, windowMs: Long): Long = {
  ((observed - bound) / bound * windowMs).round        // excess ratio x window
}
// 12 MB observed, 10 MB bound, 11 s window  =>  (2/10) * 11000 = 2200 ms

Now the design question from section 6: why delay rather than reject? Three reasons, in increasing order of subtlety. (1) Rejection requires every client in every language to implement correct backoff; delay requires clients to implement nothing at all, because a slow response is indistinguishable from a busy broker and every client already handles that. (2) Rejection wastes the work already done — the produce request was parsed, maybe even appended; throwing it away converts a throughput problem into a throughput problem plus a duplicate-or-loss problem. (3) Most importantly, delay composes with the client's own flow control: a producer with max.in.flight.requests.per.connection = 5 that is not getting responses back cannot issue a sixth request. The in-flight window is the throttle. No new mechanism, no new failure mode — just latency, which is the resource you actually wanted to trade away.

Mechanically the broker completes the request, computes throttle_time_ms, and hands the response to ClientQuotaManager.throttle, which parks it in a DelayedOperationPurgatory keyed by the throttle deadline. The channel is muted for the duration — so the client cannot even get another request read off the socket for that connection — and on expiry the response is sent with throttle_time_ms populated. Since KIP-219 the throttling happens before the response is sent rather than after, so a well-behaved client's own request.timeout.ms (default 30000) accounting stays sane, and the client additionally self-throttles by muting its own channel for the reported duration in NetworkClient. Belt and braces: broker-side muting handles hostile clients, client-side muting handles cooperative ones efficiently.

Selector and KafkaChannel: the per-connection state machines

org.apache.kafka.common.network.Selector is shared verbatim by broker and client — the same class backs a broker Processor and a producer's Sender thread. Its poll(timeout) is the single point where all I/O happens, and its structure is fixed: register any new connections, call nioSelector.select(timeout), iterate ready keys performing reads and writes, then process the resulting completed receives and sends, then close any connections idle beyond connections.max.idle.ms (default 600000 — ten minutes).

Each connection is a KafkaChannel wrapping a TransportLayer (PlaintextTransportLayer or SslTransportLayer) and an Authenticator. It holds exactly two pieces of I/O state: a NetworkReceive receive (nullable, partially filled) and a NetworkSend send (nullable, partially drained). One send at a time — setSend throws IllegalStateException if a send is already in progress. That invariant is what removes all locking: a channel is either sending or available, never both, and only its owning thread ever asks.

Partial I/O is the normal case, not an error case. read() may fill three bytes of the four-byte size header; the NetworkReceive simply persists across poll calls until complete. write() may drain 40 KB of a 900 KB response into a full socket buffer; the channel then registers OP_WRITE interest and returns, and the remaining bytes go out on later polls as the kernel drains the buffer to the network. Interest in OP_WRITE is removed as soon as the send completes, because a writable socket is almost always writable and leaving the interest set would spin the selector at 100% CPU. That add-on-partial-write / remove-on-completion dance is the classic NIO idiom and getting it wrong is the classic NIO bug.

SSL adds a third buffer layer: SslTransportLayer holds netReadBuffer, appReadBuffer and netWriteBuffer, and a read may return zero application bytes while having consumed network bytes (handshake records, renegotiation, a partial TLS record). The selector must therefore never treat "0 bytes read" as "connection idle", and SslTransportLayer.hasBytesBuffered() exists precisely so that poll re-checks channels holding decrypted-but-undelivered data even when the OS selector reports them not ready — the fix for a real class of stalls where data sat in a TLS buffer waiting for a network event that would never come.

In-flight requests and the ordering trap

max.in.flight.requests.per.connection defaults to 5. NetworkClient.canSendMore(node) checks the deque size against it; when full, the node is not "ready" and Sender skips it. Five is a bandwidth-delay-product choice: with 1 ms RTT and 1 MB batches, one in-flight request caps you at 1 GB/s theoretical but far less in practice once you account for broker-side processing, so pipelining a handful of requests keeps the pipe full without unbounded memory.

The trap: with more than one in-flight request and no idempotence, a retry reorders. Batch A and batch B are sent for the same partition; A fails with a retriable error (say NOT_ENOUGH_REPLICAS) while B succeeds; A is retried and lands after B. The log now holds B then A. Before Kafka 0.11 the only fix was max.in.flight.requests.per.connection = 1, which costs roughly 5x producer throughput on a high-latency link.

The idempotent producer solves it properly: each batch carries a producer_id, a producer_epoch, and a per-partition base_sequence, and the broker's ProducerStateManager tracks the last five sequence numbers per producer per partition. A batch arriving out of sequence is rejected with OUT_OF_ORDER_SEQUENCE_NUMBER, and the client re-sends the whole in-flight window in order. Five in flight is exactly the window the broker tracks, which is why enable.idempotence=true permits max.in.flight up to 5 but not more — the number in the config and the number in ProducerStateManager are the same number. Since Kafka 3.0 idempotence is on by default, so most people get ordering safety and pipelining without knowing this interaction exists.

TCP-level reality: buffers, slow start, keepalive

socket.send.buffer.bytes and socket.receive.buffer.bytes default to 102400 (100 KB) on the broker, and -1 means "use the OS default". They map to SO_SNDBUF/SO_RCVBUF, which bound the in-flight window TCP can sustain. The governing formula is the bandwidth-delay product: max throughput on a single TCP connection is window / RTT. With a 100 KB buffer and a 90 ms cross-region RTT, that is 102400 / 0.09 ≈ 1.14 MB/s — per connection, no matter how much bandwidth the link has. On a 10 Gb/s inter-region link you would be using 0.09% of it, and no amount of tuning replica.fetch.max.bytes would help, because the limit is not Kafka's, it is TCP's.

Hence replica.socket.receive.buffer.bytes (default 65536) is the first config to raise for cross-DC replication: to fill a 90 ms path at 100 MB/s you need 100e6 × 0.09 = 9 MB of window, so buffers on the order of 8–16 MB — and correspondingly raised net.core.rmem_max/wmem_max and net.ipv4.tcp_rmem on the host, since the socket option is clamped by the kernel maximum and setsockopt silently gives you less rather than failing.

Two smaller TCP realities. Slow start: a fresh connection begins with a congestion window of ~10 MSS (~14 KB) and doubles per RTT, so reaching a 9 MB window takes about ten round trips — 900 ms on that same cross-DC link. A client that churns connections pays that ramp every time and never reaches steady-state throughput, which is a large part of why connection reuse matters more than the handshake cost alone suggests. Linux also applies slow-start-after-idle by default (net.ipv4.tcp_slow_start_after_idle=1), collapsing the window on a connection that has been quiet for one RTO — so a bursty producer on a long-lived connection can still get slow-start behaviour; disabling that sysctl is a standard Kafka tuning step. Keepalive: Kafka sets SO_KEEPALIVE on broker sockets so that half-open connections — the ones left behind when a peer is hard-killed or a NAT device forgets its mapping — are eventually reaped, though the Linux default of two hours before the first probe means connections.max.idle.ms is the mechanism that actually does the reaping in practice.

THE IDLE-TIMEOUT COORDINATION BUG

The broker's connections.max.idle.ms (600000) and the client's must not be equal, and the client's should be lower. If both are 10 minutes, there is a race where the broker closes a connection at the same instant the client writes a request into it; the client sees the FIN after the write and reports Disconnected, which for a producer without idempotence means a retry and a possible duplicate. The Java client defaults to connections.max.idle.ms=540000 (9 minutes) for exactly this reason — the same trick as HTTP keep-alive timeout coordination behind a load balancer. When you tune one side, tune both, and keep the client strictly below the broker.

THE STRONGEST EVIDENCE THAT THE DESIGN IS GOOD

Redpanda, WarpStream, Confluent's KORA, AutoMQ, Bufstream and Azure Event Hubs all implement Kafka's wire protocol rather than inventing their own. A protocol that four independent from-scratch reimplementations can hit compatibly — including the negotiation semantics, the fetch-session state machine, and the throttling contract — is a protocol that is genuinely, rigorously specified. Compare AMQP 1.0, where interoperability between compliant implementations is still a running joke.

ARC 10 · PERFORMANCE CHARACTERISTICS

The math you should be able to do at a whiteboard

Full versus incremental fetch: the KIP-227 payoff

Let P be partitions in the session, T average topic-name bytes, and A the fraction of partitions with new data since the last fetch (the activity ratio). Under the classic v4-v6 encoding a full fetch costs approximately:

  • Full fetch ≈ H + P × (2 + T + 4 + 8 + 4) bytes, i.e. O(P). With T=24 that is 42 bytes/partition, ignoring the per-topic grouping saving.
  • Incremental fetch ≈ H + 8 + A × P × 16 bytes — 8 for session id and epoch, and roughly 16 bytes per changed partition under v13+ where the topic is a shared 16-byte UUID amortised over its partitions rather than a name repeated per partition. That is O(A·P).

At P=6000, T=24, A=0.01 (a realistic idle-ish follower): full ≈ 252 KB, incremental ≈ 8 + 60×16 ≈ ~1 KB. A 250x reduction. At A=1.0 — a burst where everything has data — incremental is ~96 KB against full's 252 KB, still better because of the UUID and varint savings, but the dramatic win is entirely a function of low activity ratio. That is the honest framing of KIP-227: it does not make busy clusters faster, it makes large and mostly-idle clusters stop wasting a resource proportional to their size rather than their load.

Framing overhead as a fraction of the wire

A request header v2 is 2+2+4 bytes plus a compact client-id (1 + len) plus one tagged-field byte — about 14–24 bytes, plus the 4-byte size prefix. For a produce request carrying a 1 MB batch that is 0.002% overhead, comfortably invisible. For a produce request carrying a single 100-byte record it is roughly 20% overhead before the produce body's own topic/partition framing, which typically pushes a minimal single-record produce to ~150–200 bytes on the wire. This is the arithmetic behind linger.ms: batching is not primarily about syscalls, it is about amortising per-request framing and per-request broker bookkeeping over more payload.

Bandwidth-delay product, worked

Single-connection TCP throughput is bounded by min(receive_window, congestion_window) / RTT. Three scenarios with the 100 KB default:

  • Same rack, RTT 0.15 ms: 102400 / 0.00015 ≈ 683 MB/s. Default buffer is fine; the NIC is the limit.
  • Cross-AZ, RTT 1.5 ms: 102400 / 0.0015 ≈ 68 MB/s per connection. Already a ceiling for a busy replica fetcher, and the reason dense brokers use num.replica.fetchers > 1 — more fetcher threads means more connections means more aggregate window.
  • Cross-region, RTT 90 ms: 102400 / 0.09 ≈ 1.14 MB/s. To reach 100 MB/s you need a 9 MB window, which means replica.socket.receive.buffer.bytes ≈ 9–16 MB plus net.core.rmem_max raised to match, plus enough replica.fetch.max.bytes that a single fetch can actually fill the pipe.

Where CPU actually goes

On a plaintext broker serving fetches from page cache, the request path costs roughly: selector wakeup and read (a few microseconds), header parse (sub-microsecond), queue hand-off (contended ArrayBlockingQueue put/take — tens of nanoseconds uncontended, worse under load), body parse on the handler thread (proportional to metadata size, which is the KIP-227 lever), the log read (an mmaped index lookup plus building a FileRecords slice — no data copy), and the response write (transferTo, zero copy). The dominant term at high partition counts, before KIP-227, was body parse, not I/O. That is the counterintuitive result worth remembering: for idle-but-dense clusters, Kafka's fetch path was CPU-bound on deserialising the question.

Turn on TLS and the profile changes shape entirely: bytes now flow page cache → heap → cipher → heap → socket. AES-256-GCM with AES-NI runs at multiple GB/s per core, so the cipher is rarely the bottleneck; the copies and the resulting allocation churn are. Expect 20–40% throughput loss and a materially higher young-gen allocation rate. Add mTLS and you also pay a client-certificate verification per handshake, which pushes connection churn from "expensive" to "capacity-defining".

A NUMBER TO CARRY AROUND

A modern broker handles low hundreds of thousands of requests/sec with num.network.threads=8 (default 3) and num.io.threads=8. Per-request fixed cost across the whole path is on the order of 5–20 µs of CPU. At 200k req/s that is 1–4 cores burnt on request handling alone. Anything that multiplies request count — linger.ms=0, tiny fetch.min.bytes, one-record-per-send producers, clients polling metadata every second — multiplies that directly. Most "Kafka is slow" tickets are request-count problems wearing a throughput costume.

ARC 11 · REAL-WORLD PRODUCTION

Incidents, numbers, and what they taught

LinkedIn and the fetch request that ate the cluster

KIP-227 was written by Colin McCabe at Confluent, but the pressure came from the largest deployments — LinkedIn ran clusters with brokers hosting on the order of 4,000–10,000 partition replicas, and their published operational writeups from the 2016–2018 era repeatedly identified fetch request overhead as a scaling limit for partition density. The dynamic they described is the one derived in section 4: with num.replica.fetchers threads each sending full partition lists to each peer several times a second, request bytes and — worse — request parse CPU grew with the square of cluster density (partitions per broker × brokers followed). The KIP's own motivation section states the case plainly: a fetch request with 1,000 partitions costs tens of kilobytes even when nothing has changed, and the incremental design reduces steady-state fetch request size by orders of magnitude at high partition counts. Post-KIP-227 the community reported large clusters comfortably supporting far higher partition-per-broker counts, and the config max.incremental.fetch.session.cache.slots became a standard thing to raise on brokers with many consumers.

INCIDENT PATTERN · THE THUNDERING HERD OF FULL FETCHES

The classic post-KIP-227 failure is a session cache stampede. The cache has 1,000 slots by default. A cluster with 3,000 consumer instances plus follower fetchers exceeds that, so sessions are evicted; an evicted client's next fetch returns FETCH_SESSION_ID_NOT_FOUND (error 70), and it falls back to a full fetch — which is large, which takes longer to parse, which delays handler threads, which slows every other client, which causes more clients to time out and reconnect, which requests more sessions, which evicts more sessions. The system has positive feedback: full fetches cause the conditions that cause full fetches. The signature in metrics is IncrementalFetchSessionEvictionsPerSec climbing while NumIncrementalFetchSessions sits pinned at the cache limit and request-handler idle ratio collapses. The fix is to raise the slot count (memory cost is a few KB per session, so tens of thousands of slots is cheap) — but you must first know the metric exists, and the failure presents as generic latency, not as anything mentioning fetch sessions.

Confluent Cloud and multi-tenant quotas

A multi-tenant cloud Kafka is the hardest possible test of the throttling design, because a single broker hosts partitions for mutually hostile tenants who have paid for specific throughput. Confluent's published material on their cloud-native rearchitecture (the KORA engine) describes exactly the layered approach the protocol enables: byte-rate quotas for bandwidth fairness, request-percentage quotas so a client cannot burn handler CPU with tiny requests while staying under its byte quota, plus additional back-pressure and isolation layers beyond the open-source quota framework. The lesson generalises: byte-rate quotas alone are insufficient, because bytes are not the only scarce resource. A tenant sending one-record produce requests at 50k req/s may use 5 MB/s of bandwidth and 3 full request-handler threads. Without request_percentage quotas (KIP-124) that tenant is invisible to the quota system and lethal to the cluster.

The second observed lesson from multi-tenant operation is the client-id trap. Quotas key on (user, client-id). Many client libraries default client.id to the empty string or to a value derived from hostname, so a fleet of 500 pods either all share one quota bucket (and throttle each other into the ground at 1/500th of the intended rate each) or each gets a full quota (and 500× the intended aggregate). Both failure modes are silent until they are not. The operationally correct pattern is user-level quotas — <user> or <user, client-id> entities — with authentication, precisely because the user principal is the thing an operator controls and the client-id is a string an application developer chose.

TLS rollouts and connection churn

The recurring TLS incident is not the cipher cost, it is churn. Three concrete shapes:

  • The load balancer with an idle timeout. An L4 balancer or cloud NLB in front of brokers with a 350-second idle timeout, versus connections.max.idle.ms=600000 at the broker. Idle connections are silently dropped mid-stream by the middlebox; neither peer learns of it until a write fails. Every producer with a low-traffic partition now reconnects — and under TLS every reconnect is a handshake plus a fresh slow start. Symptom: periodic latency spikes at a fixed cadence, and broker CPU with a sawtooth in the SSL handshake path.
  • The serverless / short-lived client. Lambda-style functions or CLI tools creating an admin client per invocation. Each one costs a TCP handshake, a TLS handshake with an asymmetric key operation, an ApiVersions, and a Metadata — four round trips and 1–2 ms of broker CPU to produce a single record. At a few thousand invocations per second the brokers are spending entire cores on connection setup for a workload whose payload is trivially small.
  • The mTLS rollout. Enabling client-certificate authentication adds certificate-chain verification per handshake and, if CRL or OCSP checking is enabled, potentially a network call inside the handshake path. Teams have discovered the hard way that an OCSP responder outage manifests as a Kafka outage, because handshakes block. The mitigation is stapling or hard-fail-off, but the general principle is: anything synchronous in the handshake path becomes a dependency of your broker's availability.

The counter-measures are unglamorous and effective: long-lived pooled connections, client connections.max.idle.ms strictly below both the broker's and any middlebox's, a sidecar or proxy that owns the long-lived connection when clients are inherently short-lived, and TLS session resumption where the client library supports it.

INCIDENT PATTERN · UNSUPPORTED_VERSION DURING AN UPGRADE

A team upgrades brokers to a new release and a subset of clients begins failing with UnsupportedVersionException. The usual cause is not the broker's supported range — those are additive — but inter.broker.protocol.version or a feature flag being advanced before all brokers are on the new binary, or a client using a new API (a fresh admin operation, or transactions) against brokers that predate it. The diagnostic is kafka-broker-api-versions.sh --bootstrap-server ..., which dumps each broker's advertised min/max per api_key — the literal ApiVersionsResponse, printed. Comparing that output across brokers mid-upgrade shows you exactly which node is the odd one out, and it is the single most underused Kafka CLI tool.

Nagle in the wild

Kafka sets TCP_NODELAY on its own sockets, so the classic Nagle/delayed-ACK stall does not arise between a Kafka client and a Kafka broker. It does arise in the layers people put in between. Service meshes, TCP proxies, SSL-terminating sidecars and VPN tunnels frequently do not set TCP_NODELAY on their upstream sockets, reintroducing the exact 40 ms quantisation Kafka went out of its way to avoid. The signature is unmistakable once you have seen it: a latency histogram with a hard floor and a cluster of samples at ~40 ms and ~80 ms, present only for small requests, absent under load (because under load there is always enough data to fill an MSS and Nagle never engages). If your p99 is 41 ms and your p50 is 1 ms, stop profiling the broker and start reading the proxy's socket options.

SocketServer: acceptor and processor, simplified

SCALAcore/src/main/scala/kafka/network/SocketServer.scala (condensed)
private[kafka] class Acceptor(endPoint: EndPoint, sendBufferSize: Int,
                             processors: Seq[Processor], connectionQuotas: ConnectionQuotas)
  extends AbstractServerThread {

  private val nioSelector = NSelector.open()
  val serverChannel = openServerSocket(endPoint.host, endPoint.port)
  private var currentProcessorIndex = 0

  def run(): Unit = {
    serverChannel.register(nioSelector, SelectionKey.OP_ACCEPT)
    while (isRunning) {
      val ready = nioSelector.select(500)          // 500ms so shutdown is responsive
      if (ready > 0) {
        val it = nioSelector.selectedKeys().iterator()
        while (it.hasNext) {
          val key = it.next(); it.remove()
          val ch = accept(key)   // throws TooManyConnectionsException -> close & drop
          // ROUND-ROBIN: connections are spread across processors blindly.
          // No load awareness — a "hot" connection can land anywhere.
          var retries = 0; var assigned = false
          while (!assigned) {
            val p = processors(currentProcessorIndex % processors.size)
            currentProcessorIndex += 1
            // non-blocking first pass round the ring; only block if ALL are full,
            // so one wedged processor cannot stall the accept loop
            assigned = p.accept(ch, mayBlock = retries > processors.size)
            retries += 1
          }
        }
      }
    }
  }

  private def accept(key: SelectionKey): SocketChannel = {
    val ch = key.channel().asInstanceOf[ServerSocketChannel].accept()
    connectionQuotas.inc(endPoint.listenerName, ch.socket.getInetAddress, ...)
    ch.configureBlocking(false)
    ch.socket().setTcpNoDelay(true)     // Nagle OFF. Always. See section 6.
    ch.socket().setKeepAlive(true)
    if (sendBufferSize != Selectable.USE_DEFAULT_BUFFER_SIZE)
      ch.socket().setSendBufferSize(sendBufferSize)   // socket.send.buffer.bytes
    ch
  }
}

Three details in that fragment repay attention. connectionQuotas.inc enforces max.connections.per.ip (default 2147483647, i.e. off) and max.connections per listener — it throws before any protocol work happens, which is the cheapest possible place to shed load. The mayBlock = retries > processors.size condition means the acceptor tries every processor non-blockingly before it is willing to block on any of them, so a single stuck processor degrades throughput rather than halting accepts. And setTcpNoDelay(true) is unconditional — there is no config to turn Nagle back on, because there is no workload where it would help.

override def run(): Unit = {
  while (isRunning) {
    configureNewConnections()          // drain newConnections queue, register OP_READ
    processNewResponses()              // take from responseQueue, channel.setSend(...)
    poll()                             // selector.poll(300) — the only blocking call
    processCompletedReceives()         // parse HEADER only, enqueue to RequestChannel
    processCompletedSends()            // unmute channel: it may send again
    processDisconnected()
    closeExcessConnections()           // max.connections eviction, LIFO
  }
}

private def processCompletedReceives(): Unit = {
  selector.completedReceives.forEach { receive =>
    openOrClosingChannel(receive.source) match {
      case Some(channel) =>
        val header = RequestHeader.parse(receive.payload)  // header ONLY
        if (header.apiKey == ApiKeys.SASL_HANDSHAKE && channel.maybeBeginServerReauth())
          trace("reauth started")
        else {
          val ctx = new RequestContext(header, receive.source, channel.socketAddress,
                                          channel.principal, listenerName, securityProtocol, ...)
          val req = new RequestChannel.Request(processor = id, context = ctx,
                        startTimeNanos = nowNanos, memoryPool, receive.payload, requestChannel.metrics)
          requestChannel.sendRequest(req)     // BLOCKS if queue full -> TCP backpressure
          selector.mute(receive.source)       // one in-flight request per connection
        }
      case None => // channel closed between read and processing; drop
    }
  }
  selector.clearCompletedReceives()
}

The pairing of requestChannel.sendRequest (blocking on a bounded queue) with selector.mute is the entire backpressure story in two lines. Mute removes OP_READ interest, so this connection contributes nothing further until its response has been written; the blocking put means that if all handlers are saturated the processor stops servicing every connection it owns, kernel receive buffers fill, TCP windows close, and clients slow down without any of them being told anything. Note also what is not here: no body parse. The payload ByteBuffer is carried by reference into the request and deserialised later on a handler thread.

JAVAclients/.../common/network/Selector.java — poll() and the per-channel state machine (condensed)
public void poll(long timeout) throws IOException {
    clear();                                   // reset completedSends/Receives/disconnects
    if (hasStagedReceives() || !immediatelyConnectedKeys.isEmpty()
        || (dataInBuffers && !explicitlyMutedChannels.isEmpty()))
        timeout = 0;    // SSL: bytes may sit decrypted in a buffer with no socket event

    int numReady = nioSelector.select(timeout);
    long endSelect = time.nanoseconds();

    if (numReady > 0 || !immediatelyConnectedKeys.isEmpty() || dataInBuffers)
        pollSelectionKeys(readyKeys, false, endSelect);

    addToCompletedReceives();
    maybeCloseOldestConnection(endSelect);     // connections.max.idle.ms = 600000
}

void pollSelectionKeys(Set<SelectionKey> keys, boolean isImmediatelyConnected, long now) {
  for (SelectionKey key : determineHandlingOrder(keys)) {
    KafkaChannel channel = channel(key);
    try {
      if (isImmediatelyConnected || key.isConnectable()) {
        if (channel.finishConnect()) { connected.add(channel.id()); ... }
        else continue;
      }
      if (channel.isConnected() && !channel.ready())
        channel.prepare();     // SSL handshake + SASL auth, driven incrementally here

      // ---- READ SIDE: a receive may span many polls ----
      if (channel.ready() && (key.isReadable() || channel.hasBytesBuffered())
          && !hasCompletedReceive(channel) && !explicitlyMutedChannels.contains(channel)) {
        NetworkReceive receive;
        while ((receive = channel.read()) != null) {   // null == still partial
          madeReadProgress = true;
          addToStagedReceives(channel, receive);
        }
      }

      // ---- WRITE SIDE: one send at a time, may drain over many polls ----
      if (channel.ready() && key.isWritable() && channel.state() == ChannelState.READY) {
        long bytes = channel.write();
        if (bytes > 0) sensors.recordBytesSent(channel.id(), bytes);
        NetworkSend send = channel.maybeCompleteSend();
        if (send != null) completedSends.add(send);   // only now is OP_WRITE dropped
      }
    } catch (Exception e) {
      close(channel, CloseMode.GRACEFUL);
      this.disconnected.put(channel.id(), channel.state());
    }
  }
}

Read channel.read() returning null as "not an error, just not finished". That single convention is what makes partial reads a non-event: state lives in the NetworkReceive, the loop simply returns and the next poll continues where it stopped. The symmetric fact on the write side is that OP_WRITE interest is registered only while a send is incomplete — a permanently-registered OP_WRITE on an empty socket makes select() return immediately forever, and the resulting 100%-CPU spin is the single most common NIO mistake in the wild.

def throttle(request: RequestChannel.Request, cb: ThrottleCallback, throttleTimeMs: Int): Unit = {
  if (throttleTimeMs > 0) {
    val clientSensors = getOrCreateQuotaSensors(request.session, request.header.clientId)
    clientSensors.throttleTimeSensor.record(throttleTimeMs)
    val op = new ThrottledChannel(time, throttleTimeMs, cb)
    delayQueue.add(op)          // DelayQueue drained by a ThrottledChannelReaper thread
    // cb.startThrottling() mutes the channel; cb.endThrottling() unmutes it
    // AND only then does the response actually go on the wire.
  }
}

math.max rather than a sum is a deliberate and slightly surprising choice: a client that violates both its bandwidth and its request-rate quota is delayed by the larger of the two, not their total. The reasoning is that the two quotas measure the same underlying scarcity from different angles, and summing would over-throttle a client that is merely borderline on both. Note also that ThrottledChannel is a DelayQueue entry drained by a dedicated reaper thread — throttling costs no request-handler thread and no timer wheel slot; a delayed response occupies only heap.

WHY THE DEVELOPERS WROTE IT THIS WAY

Every structural decision in these files reduces to one rule: never let an unbounded thing exist, and never let a blocking thing run on an I/O thread. The request queue is bounded (500). In-flight requests per connection are bounded (1 at the broker via mute, 5 at the client via config). Fetch sessions are bounded (1000 slots). Connections are bounded per-IP and per-listener. Receive size is bounded before allocation (100 MB). Every one of those bounds turns a potential out-of-memory or unbounded-latency failure into a clean, observable backpressure signal. Meanwhile the blocking work — disk reads, purgatory waits, throttle delays — is pushed onto handler threads, the DelayQueue reaper, or the purgatory timer wheel, so that the small fixed set of network threads only ever does non-blocking socket I/O.

The second rule is share the hard code, specialise the easy code. Selector, KafkaChannel, and the whole TLS/SASL transport stack are written once in Java and used by broker and client alike. Getting NIO edge cases right — partial TLS records, buffered-but-unreadable data, the OP_WRITE spin — is genuinely difficult, so it is done in exactly one place. The Scala in core/ contains no NIO at all; it is orchestration over a component that has already solved the hard part.
