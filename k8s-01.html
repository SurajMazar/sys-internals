ARC 01 · THE PROBLEM

One container is a solved problem. A fleet of them is not.

A container is a single running instance of an image — your application plus everything it needs to run, minus the kernel underneath it. docker run -d -p 8080:8080 myapp:1.4 on your laptop is, genuinely, a complete and correct way to run one process in isolation. That command is not the problem this chapter exists to solve. The problem starts the moment a single machine is not enough — and for any application serious enough to have paying users, that moment arrives fast, for two independent reasons: capacity (one machine runs out of CPU/RAM long before your users run out of demand) and availability (one machine, one disk, one power supply, one network link — all of it fails eventually, and "eventually" in a large enough fleet means "most days").

So you buy — or rent — more machines. Say four servers, and twenty containers to spread across them: some API replicas, a background worker, a cache, a couple of internal tools. The instant you have N machines and M containers where N > 1, five questions appear that docker run was never designed to answer, because on one machine they don't exist:

  • Placement — which of the four hosts should run which container, given that hosts have different free CPU/RAM at any given moment? Decide badly and one host is jammed full while another sits idle.
  • Health — a container's process can hang, leak memory, or its host can lose power at 3 a.m. Something has to notice and react — a human watching dashboards does not scale past the first pager alert.
  • Scale — traffic triples during a sale; you need more replicas of the API, right now, without hand-editing four servers' worth of docker run commands.
  • Update — you ship a new image version. Stopping all twenty containers and starting the new ones is an outage. Somebody has to replace them a few at a time, watch for failure, and know when to stop.
  • Discovery — a container's IP address is assigned when it starts and is different every time it restarts. Every other container that needs to talk to it has no stable address to call.

None of these are exotic distributed-systems trivia — they are the direct, mechanical consequence of having more than one container on more than one machine. An orchestrator is simply the name for a system that answers all five continuously, automatically, and correctly even while machines are actively failing. Kubernetes is one specific, extremely well-tested implementation of that idea. This chapter derives why something in that shape has to exist before it shows you what Kubernetes actually is — starting in chapter 2 with the concrete objects (Pods, ReplicaSets, Deployments) that do the work.

WHY THIS MATTERS FOR THE NEXT 17 CHAPTERS

Every Kubernetes object you will meet in this course is an answer to exactly one of the five questions above. A Pod and Deployment (ch. 2) answer placement, health, and scale. A Service (ch. 3) answers discovery. Rolling updates (ch. 2) answer the update problem without an outage. The scheduler (ch. 8) is the placement algorithm made rigorous. If you ever feel lost in a later chapter, come back here and ask: which of these five problems is this component solving? It is always at least one of them.

DEEP CONTEXT · WHY "KUBERNETES"?

The name comes from the Greek κυβερνήτης (kybernḗtēs) — "helmsman" or "pilot," the same root that gives us "cybernetics" and "governor." The project's internal codename at Google was "Seven" (a nod to Star Trek's Seven of Nine — a joking reference to Borg, its ancestor), which is why the Kubernetes logo has seven spokes on its wheel. The name change to the Greek word for helmsman is apt: Kubernetes doesn't do the rowing (running your code) — it steers the fleet, continuously correcting course. You'll see this "steering, not doing" division of labor everywhere: the control plane decides, the nodes execute.

ARC 03 · NAIVE SOLUTION

Attempt #1: SSH, a spreadsheet, and a cron job

Derive this honestly, the way any team actually starts. You have four hosts and twenty containers to run. The simplest possible "orchestrator" is: a text file mapping containers to hosts, a for-loop that SSHes into each host and runs docker run, and a cron job that re-checks everything every few minutes in case something died.

bashfleet.sh — the strawman, annotated
#!/usr/bin/env bash
# placement.txt: "host,image,name" — one line per container, hand-edited
HOSTS=(10.0.0.1 10.0.0.2 10.0.0.3 10.0.0.4)

deploy_all() {
  while IFS=, read -r host image name; do
    ssh "$host" "docker rm -f $name 2>/dev/null; \
              docker run -d --name $name --restart=no $image"   # fire-and-forget
  done < placement.txt
}

healthcheck_sweep() {                          # run from cron every 5 minutes
  while IFS=, read -r host image name; do
    running=$(ssh "$host" "docker inspect -f '{{.State.Running}}' $name 2>/dev/null")
    if [ "$running" != "true" ]; then
      echo "$(date) restarting $name on $host"       # ...usually. see §4.
      ssh "$host" "docker run -d --name $name $image"
    fi
  done < placement.txt
}

deploy_all

This is not a joke architecture — most infrastructure teams write something close to this in their first year, and it is a completely reasonable place to start. It already gets the basics right: containers do run, on the hosts you chose, and a crashed one eventually comes back. Watch it meet reality. ARC 04 · WHY IT FAILS

Every line of that script is a race condition or an outage waiting for a bad day

Each failure mode below is not a bug you could patch away with more bash — it's a structural gap in the model itself. Be precise about the arithmetic, because it's exactly the arithmetic Kubernetes's designers had to beat:

  • Detection latency is a coin flip, not a guarantee. A cron sweep every 5 minutes means a crashed container sits dead for an average of 2.5 minutes and a worst case of 5 minutes before anyone notices — and that's before you add the time your on-call spends reading the cron log. For a customer-facing API replica, that's minutes of reduced capacity, silently.
  • A dead host doesn't fail — it hangs. ssh to an unreachable host doesn't return instantly; it blocks until ConnectTimeout (commonly 10–30s by default). If your sweep script SSHes into four hosts serially and host 3 is dead, hosts 1–2's healthy containers already got checked, but hosts 3–4 wait behind a 10–30 second hang — and every subsequent sweep repeats the wait until someone edits placement.txt.
  • No cross-host coordination means double-launches are structurally possible. If the sweep script is accidentally run twice (a stuck cron job plus a manual run — this happens constantly in practice), two processes can both decide the same container is "down" and both issue docker run for the same name on the same host, or worse, on two different hosts if placement.txt was edited mid-flight — now you have duplicate workers processing the same queue twice.
  • Placement is a spreadsheet, so it never rebalances. Host 2 might be idle at 5% CPU while host 4 sits at 95%, and nothing in this system will ever notice or move a container to fix it — docker run doesn't know what "load" means on a host it wasn't told to check.
  • An update is binary: stop, then start. Re-running deploy_all for a new image version does docker rm -f immediately followed by docker run — there is no "start the new one, wait for it to be healthy, then remove the old one." For a fleet with a single replica per service, an update is a guaranteed outage window equal to the new container's cold-start time.
THE NUMBERS

Put a number on just the detection gap: a fleet running 200 containers with a historical crash rate of 1% per container per day (a realistic figure for a fleet with normal OOMs, bad deploys, and flaky dependencies) sees ~2 crashes/day. At a 5-minute sweep interval, that's ~2 × 2.5 min = 5 minutes of cumulative degraded capacity every day, forever, that nobody has to be paged for because "the cron job will get it" — until the day two crashes overlap with the double-launch race above, and now you're paged for data corruption instead of a slow restart. Tightening the sweep to 30 seconds doesn't fix the model; it just multiplies your SSH fan-out load by 10× and makes the serial-hang problem on a dead host ten times more frequent.

Every one of these gaps has the same root cause: the script has no persistent model of "what should be running" that it reconciles against continuously and safely — it just fires commands and hopes. Fixing that root cause, not patching each symptom, is what the rest of this chapter derives.

ARC 05 · BETTER SOLUTION

Stop issuing commands. Start declaring intent.

The fix is a change of mental model, not a smarter script. Instead of a program that says "SSH to host X and run command Y" (an imperative instruction), you write down what you want to be true — "3 copies of image myapp:1.4 should be running, somewhere" — and a separate, continuously-running program's only job is to keep reality matching that statement. This is the declarative desired-state model, and it is the single idea every other Kubernetes concept in this course builds on top of.

The mechanism that makes a declaration real is called a control loop — sometimes called a reconciler. Step through the shape of one; this exact three-beat rhythm — observe, diff, act — is the mechanism behind every self-healing behavior you will see in this course, from a crashed container restarting (ch. 2) to a failed node's Pods being rescheduled elsewhere (ch. 9).

The reconciliation loop, one beat at a timeSTEP-BY-STEP
THE CLINCHING ARGUMENT: THIS LOOP CANNOT GET "OUT OF SYNC"

Notice what the loop does not do: it never says "start container X because I just watched it crash." It only ever says "there are 2 running but I want 3, so start one more" — a statement computed fresh from current observation, with zero memory of the specific event that caused the gap. This is called level-triggered reconciliation, and it is the reason Kubernetes controllers can miss an update, crash mid-loop, or restart from nothing, and still converge correctly on the next tick — there is no event log to have lost, only a diff to recompute. Chapter 9 names this precisely and contrasts it with the edge-triggered alternative.

ARC 06 · WHY THAT STILL COSTS

A reconciliation loop is the right idea. Building one yourself is still a distributed systems project.

Say your team writes exactly the loop from §5 as one long-running process on a single control machine. It is a real improvement over the cron script — but look at what you've just signed up to build and operate, because each of these is a full subsystem, not a tweak:

  • The desired state itself must survive a crash. If "3 replicas" lives only in the reconciler process's memory, restarting that process loses your entire intent — you need a durable, consistent store that the reconciler reads on every tick. This store becomes the single most important, and single most dangerous, component in the system (chapter 7 is entirely about the one Kubernetes actually uses — etcd).
  • The reconciler itself is now a single point of failure. The exact problem you built this system to solve for your application — "what happens when the thing that's supposed to be running, isn't?" — now applies recursively to the reconciler. You need it to run under its own supervision, ideally with automatic failover, which means leader election among multiple copies (a genuinely hard distributed-systems primitive, also solved inside etcd via Raft — chapter 7).
  • Polling every host doesn't scale. The naive reconciler observes "actual state" by asking every host "what's running?" every tick. At 4 hosts that's fine. At 4,000 hosts, a poll-everything-every-tick design means either a very slow tick interval (bad: slow reaction to failures) or an enormous, constantly repeating fan-out of requests that scales linearly with fleet size for information that mostly hasn't changed since the last tick. §8 works out the actual numbers and the fix (watches, not polls).
  • "Start one more container" still needs a placement decision. Which of 4,000 hosts has room? Are there hosts you must avoid (a database host, a GPU-only node)? A hand-rolled reconciler either hard-codes an answer or re-derives, badly, what chapter 8's scheduler does properly: a two-phase filter-then-score algorithm.
THIS IS NOT A HYPOTHETICAL — GOOGLE ALREADY PAID THIS TAX

Every item above is a real subsystem inside Google's Borg (§2), built and hardened between roughly 2003 and 2013 for internal use only. Kubernetes is, in large part, the публично usable, open-sourced re-derivation of those same hard-won answers: a consistent store for desired state (etcd, not Borg's Paxos-based Chubby-adjacent store), a leader-elected control plane, a watch-based observation model, and a real scheduler. The "cost" in this section is not a design flaw to route around — it is the actual engineering budget an orchestrator has to spend, and the rest of this course is a tour of how Kubernetes spent it.

From kubectl apply to a running process, step by step

(b) The desired state is just JSON, sent over HTTP

There is no magic file format here — a Kubernetes manifest is a serialized description of one API object, and kubectl apply is a thin HTTP client. Chapter 2 dedicates itself to the Pod object's fields; for now, notice only the shape: a kind, an apiVersion namespacing which version of that kind's schema you mean, and a spec (what you want) that the system will populate a matching status (what's actually true) alongside, once observed:

yamlpod.yaml — the smallest real desired-state document
apiVersion: v1                 # which schema version of "Pod" — core objects use v1
kind: Pod                        # which object type this document declares
metadata:
  name: web-7f4c9            # unique within its namespace
  labels: { app: web }         # arbitrary key/value tags — chapter 3 uses these for Service routing
spec:                            # ← the DESIRED state — this is what you write
  containers:
    - name: web
      image: myapp:1.4
      ports: [{ containerPort: 8080 }]
      resources:
        requests: { cpu: "250m", memory: "256Mi" }  # chapter 8: the scheduler's arithmetic
# status: {} ← does NOT exist in your file. The API server fills this in and
#              keeps it updated as reality changes. You never write status.

Every controller in the system — and you will build a toy one yourself in the capstone, chapter 18 — runs the same shaped loop against objects like this one. This is the generic pattern chapter 9 names precisely and implements with real client-go primitives (informers, workqueues); here is its essence:

pseudocodethe reconcile loop every controller runs, in its essential form
function reconcile(objectKey):
    desired  = apiServer.get(objectKey)              // the spec you wrote
    observed = apiServer.get(objectKey).status       // what's actually true right now

    diff = compute_diff(desired.spec, observed)      // e.g. "want 3 replicas, have 2"

    if diff is empty:
        return                                      // nothing to do — this is the common case

    take_smallest_action_toward(diff)                 // e.g. create exactly ONE more replica,
                                                       // never "fix everything at once"
    // no sleep, no "mark as handled" flag — the NEXT event or the NEXT
    // periodic resync just calls reconcile() again and recomputes fresh

(c) Why the API server is watched, not polled

§6 flagged the scaling problem with a reconciler that polls every host on every tick. Kubernetes' actual fix is that etcd exposes a watch API — a long-lived stream of "this key changed" events — and every controller subscribes to it instead of asking "what changed?" on a timer. Drag the sliders below to feel why this decision is not a micro-optimization but the difference between a design that works at 4 nodes and one that works at 5,000.

THE HONEST CAVEAT

Watches are not free lunch — chapter 6's rule ("nothing talks to etcd except the API server") and chapter 7's discussion of etcd's own scaling limits exist precisely because the API server has to fan a single etcd watch stream out to potentially thousands of connected controller and kubelet clients, each wanting a consistent, ordered view. Watches trade an O(cluster size) polling cost for an O(1)-per-change push, at the price of a control plane that must itself be built to hold thousands of long-lived connections open correctly — which is exactly why the API server, not raw etcd access, is the thing every component talks to.

ARC 09 · TRADEOFFS

Kubernetes is one answer among several honest ones

Kubernetes won the orchestration space, but it was not the only serious attempt, and "won" does not mean "strictly better for every case." Read this table as a proof by exhaustion: every system below is solving the same five problems from §1, and every one of them made a real, defensible tradeoff to get there.

SYSTEMMODELWHAT THEY BOUGHTWHAT THEY PAID
SSH + cron scriptsImperative, no shared state store zero infrastructure trivial to understand no self-healing no bin-packing outage on every update (§3–§4)
KubernetesDeclarative desired state + watch-based control loops + a two-phase scheduler self-healing rolling updates huge ecosystem/CNCF standard steep learning curve real operational weight (etcd, control plane HA)
Docker SwarmDeclarative, built into the Docker Engine itself minutes to a running cluster one binary, no separate store to run smaller ecosystem Docker Inc. de-prioritized it after Kubernetes won mindshare
Apache Mesos + MarathonTwo-level scheduling: Mesos offers resources, frameworks (like Marathon) accept/reject them one cluster, many frameworks (batch + services + Spark) proven at extreme scale (Twitter, Apple) two systems to operate, not one community migrated to Kubernetes by ~2019
HashiCorp NomadDeclarative, single lightweight binary, pluggable task drivers (not container-only) much simpler operationally runs VMs/binaries/containers uniformly smaller ecosystem than Kubernetes' CRD/operator model
AWS ECS (Fargate mode)Declarative, but the control plane is entirely AWS-managed and closed no control plane to operate at all deep native AWS IAM/VPC integration locked to one cloud less visibility into scheduling decisions

The pattern to notice: nobody disputes that a reconciliation loop over a declared desired state is the right shape — every serious contender from 2014 onward uses some version of it. The real argument, then and now, is over the second-order questions: how many things should the one system schedule (Mesos's bet: many frameworks; Kubernetes's bet: mostly containers, extended via CRDs — ch. 9), and who operates the control plane (self-hosted etcd vs. a fully managed API, neutrally: EKS/GKE/AKS mainly differ in how much of that control-plane operation — upgrade cadence, etcd visibility — they hide from you, not in the underlying model).

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Numbers you can reason about before you ever run a cluster

Kubernetes publishes real, tested scaling limits rather than leaving them to folklore. The ones worth memorizing now, because later chapters build directly on them:

  • 110 Pods per node — the kubelet's default cap, chosen as a conservative number that keeps per-node overhead (health-check traffic, container runtime bookkeeping) manageable on typical hardware; it's a configurable kubelet flag, not a hard architectural ceiling.
  • The 5,000-node / 150,000-Pod envelope — the officially tested single-cluster scale target the Kubernetes scalability SLOs are validated against. Past it, you're in "it might work, it isn't validated" territory — the honest reason most very large deployments use multiple clusters (ch. 17) rather than one enormous one.
  • etcd's per-value guidance: keep writes under ~8 KB, and watch total database size — etcd is a replicated log first and a database second; a practical multi-gigabyte ceiling on total database size is the real-world threshold past which request latency degrades, which is why chapter 7 treats etcd, not the API server, as the component most likely to be your cluster's actual bottleneck.
  • Every request passes through one funnel. There is no back door: every read and write to cluster state — from your kubectl, from every controller, from every kubelet — goes through the kube-apiserver, which is the single place authentication and authorization are enforced (chapter 13 covers RBAC and admission control in full). Centralizing the funnel is what makes a consistent security model possible at all; it is also, mechanically, why API server availability is the one thing that must never lapse.

The curves are an analytic sketch, not a benchmark: the SSH-sweep line grows with fleet size because a fixed sweep interval's average detection time is constant per-host but the odds of the sweep itself being backed up by a hung, dead host rise with host count (worse still if serial). The point is the shape, which is real; exact constants depend on your specific timeouts.

ARC 11 · REAL-WORLD CASES

Three cases that prove the thesis, not just illustrate it

Case 1: Google's own 2003 scaling crisis — the reason Borg exists

The publicly available Borg paper ("Large-scale cluster management at Google with Borg," Verma et al., EuroSys 2015) is explicit about the motivation: before Borg, Google engineers manually decided which machines ran which jobs, using scripts not unlike §3's strawman, across cells that were already growing into the tens of thousands of machines. The paper reports Borg cells managing on the order of tens of thousands of machines shared by tens of thousands of jobs from thousands of different applications — a scale at which manual placement isn't merely inconvenient, it's mathematically impossible for a human to do well. Borg's central bet — a declarative job spec plus a scheduler that bin-packs automatically — is the direct ancestor of everything in §7.

Case 2: Pokémon GO, July 2016 — the thesis under real, unplanned load

Niantic's launch of Pokémon GO is a widely cited, publicly discussed case study (Niantic and Google Cloud have both spoken about it at public engineering conferences) because actual traffic arrived at roughly 50× the pre-launch capacity estimate within days. The infrastructure was built on Google Kubernetes Engine specifically so that scaling out replicas in response to load was a declarative change (§5's model — "I want more replicas now") rather than a manual per-host provisioning exercise. The specific number worth remembering is not the multiplier itself but what it implies about manual placement: no on-call SSH runbook scales linearly with a 50× surprise; a reconciliation loop that already knows how to add replicas does, bounded only by how fast new machine capacity itself can be added.

Case 3: the cron-sweep failure pattern is real enough to have its own postmortem literature

Google's own Site Reliability Engineering book devotes a full chapter to the operational hazards of cron-driven jobs at scale — including exactly the double-execution race from §4 (a job overlapping with itself because the previous run hadn't finished) and the "silent for one interval, then a pile-up" failure shape. The book's prescription — treat periodic reconciliation as a first-class, monitored, idempotent system rather than an afterthought bolted onto cron — is, in essence, an argument for building exactly the kind of control loop §5 derives, rather than trusting cron with your fleet's health.

The shape of a real controller, before you've seen a real Pod

First, how a controller finds out something changed — it never polls the API server itself; it registers callbacks with an informer, which does the watching centrally and shares one cache across every controller in the same process:

Gosample-controller/controller.go — NewController(), simplified but structurally faithful
func NewController(client kubernetes.Interface, podInformer coreinformers.PodInformer) *Controller {
    c := &Controller{
        client:    client,
        podLister: podInformer.Lister(),          // reads from the LOCAL cache — never the network
        podSynced: podInformer.Informer().HasSynced,
        workqueue: workqueue.NewRateLimitingQueue(/* ... */),
    }

    // Register callbacks. The informer calls these on every watch event —
    // note we don't act here. We only enqueue a KEY, never the object itself.
    podInformer.Informer().AddEventHandler(cache.ResourceEventHandlerFuncs{
        AddFunc:    func(obj interface{}) { c.enqueue(obj) },
        UpdateFunc: func(old, new interface{}) { c.enqueue(new) },
        DeleteFunc: func(obj interface{}) { c.enqueue(obj) },
    })
    return c
}

Second, the worker loop — this is §5's "observe, diff, act" made literal. Notice it pulls a key (namespace/name), not a snapshot of the object — by the time the key is processed, the object may have changed again, and that's fine, because the reconcile function always re-reads current state:

Gosample-controller/controller.go — runWorker() → syncHandler()
func (c *Controller) runWorker() {
    for c.processNextWorkItem() {
    }
}

func (c *Controller) processNextWorkItem() bool {
    key, shutdown := c.workqueue.Get()          // blocks until work exists
    if shutdown {
        return false
    }
    defer c.workqueue.Done(key)

    if err := c.syncHandler(key.(string)); err != nil {
        c.workqueue.AddRateLimited(key)         // retry with exponential backoff — NOT a tight loop
        return true
    }
    c.workqueue.Forget(key)                     // success: reset backoff for this key
    return true
}

func (c *Controller) syncHandler(key string) error {
    namespace, name, _ := cache.SplitMetaNamespaceKey(key)
    obj, err := c.podLister.Pods(namespace).Get(name)   // re-read CURRENT state, not stale data
    if errors.IsNotFound(err) {
        return nil                              // it's gone — nothing to reconcile
    }
    return c.reconcile(obj)                    // §8b's pseudocode, for real
}
WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. Enqueue keys, not objects. If you queued the actual object, a worker could process a stale snapshot from three updates ago. Queueing just the namespace/name and re-reading current state at processing time means the loop is always working from truth, matching the level-triggered guarantee from §5's callout. 2. Rate-limited retry, not a tight loop. A reconcile that fails (a transient network error, a conflicting update) goes back on the queue with exponential backoff, not an immediate retry — this is what stops one broken object from pinning a CPU core or hammering the API server. Both choices generalize far beyond Kubernetes: any at-least-once, retry-driven work-processing system rediscovers them.
