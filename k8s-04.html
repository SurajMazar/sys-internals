KUBERNETES INTERNALS · CHAPTER 04 BEGINNER

Config & Storage Basics:
ConfigMaps, Secrets, Volumes

A container image should never bake in a database hostname, a feature flag, or a password — otherwise every environment needs its own image, and every credential rotation needs a rebuild. Kubernetes solves this by moving configuration and sensitive data out of the image and into API objects the cluster manages: ConfigMaps for plain settings, Secrets for sensitive values, and Volumes for anything a container needs to read or write as files. This chapter derives all three from first principles — and is honest about the single most misunderstood fact in this whole area: a Kubernetes Secret, by default, does not encrypt anything at all.

ARC 01 · THE PROBLEM

An image is a recipe; a running container needs facts about the world

A container image — the thing you built with docker build and pushed to a registry — is a filesystem snapshot plus an entrypoint command. It is, by design, identical everywhere it runs: the same image runs in your laptop's local cluster, in staging, and in production. But the process that image starts almost always needs facts that are not identical everywhere: which database to connect to, which feature flags are on, what log level to use, and — the sharpest case — which password or API key to authenticate with.

If you bake any of that into the image, you get an immediate, compounding problem:

  • One image per environment. myapp:staging, myapp:prod, myapp:eu-prod — now you're rebuilding and re-scanning-for-CVEs the same code three times just to change a hostname.
  • Secrets end up in version control. A password baked into a Dockerfile or committed into an image layer is a password in your registry's history forever, readable by anyone who can pull the image — and image layers are notoriously easy to `docker save` and inspect.
  • Rotating a credential means rebuilding and redeploying. A leaked API key should be revocable in seconds; if it's compiled into the image, revoking it means a full build-test-deploy cycle under pressure.
  • No separation of duties. The engineer who builds the image and the operator who knows the production database password are frequently different people — baking secrets into images forces them to be the same pipeline, the same access list, the same audit trail.

The fix, in outline, is old: the twelve-factor app principle of strict separation between build and config. Kubernetes gives that principle three first-class API objects: ConfigMap for non-sensitive key/value data, Secret for sensitive key/value data, and Volume as the general mechanism that gets either of them — or anything else — onto a container's filesystem, or somewhere the container can write. This chapter builds all three, and is careful about a distinction the ecosystem gets wrong constantly: Secret is a naming and workflow convenience, not a cryptographic guarantee, unless you explicitly turn additional machinery on.

DEEP CONTEXT · WHY SECRET IS A SEPARATE KIND, NOT A CONFIGMAP FLAG

Early proposals considered a single "ConfigMap with a sensitive flag." The API designers split them into two kinds on purpose: separate objects mean separate RBAC rules (you can grant "read ConfigMaps" without granting "read Secrets" in the same namespace), separate storage treatment (Secrets get base64 transport encoding and are the object type encryption-at-rest almost always targets first), and separate tooling signals (`kubectl get secrets` doesn't print values by default; `kubectl get configmaps` does). The split is a permissions boundary baked into the type system — you'll use it directly in chapter 13.

ARC 03 · NAIVE SOLUTION

Attempt #1: bake it into the image, or pass it on the command line

Derive the problem honestly, the way chapter 1 derived orchestration itself. Before ConfigMaps and Secrets existed as a concept anywhere, the obvious moves were: put the config in the image, or pass it as docker run flags read from a plaintext file sitting next to your deploy script.

bashdeploy_by_hand.sh — the strawman, annotated
# secrets.env — plaintext, sitting on whichever box runs this script
export DB_HOST="prod-db.internal:5432"
export DB_PASSWORD="h4x0r-pr00f-2024!"      # in a file, unencrypted, on disk
export API_KEY="sk_live_9f8a7b6c5d4e3f2a1b"

source secrets.env

# bake nothing into the image at all — pass everything as flags,
# copy-pasted by hand into every host that needs to run this container
docker run -d \
  -e DB_HOST=$DB_HOST -e DB_PASSWORD=$DB_PASSWORD -e API_KEY=$API_KEY \
  -v /opt/myapp/config.json:/etc/myapp/config.json \    # hand-copied config file, per host
  myregistry/myapp:latest

This is not unreasonable at the scale of one host — it already fixes the "one image per environment" problem from §1: the image is generic, and the environment supplies the specifics. But look at what has to happen for this to work across even a modest fleet: secrets.env must exist, correctly, on every host that runs this container, kept in sync by hand or by a configuration-management tool you now also have to operate, with no single place to update a value and no record of who changed it or when.

ARC 04 · WHY IT FAILS

The math of "just SSH in and edit the file"

This isn't a style complaint — it's an operational failure mode with numbers attached. Three compounding costs make the by-hand approach collapse well before Kubernetes-scale fleets:

  • Rotation time scales linearly with fleet size, and mistakes scale with it too. If updating one host's secrets.env and restarting its container takes 90 seconds of careful, error-prone manual work, a 200-host fleet is 5 hours of a human doing the same repetitive edit — and the probability that at least one host is missed or gets a typo rises with every repetition, not falls.
  • There is no atomicity across hosts. During a 5-hour manual rotation, some hosts run the old credential and some run the new one. If the old credential must be revoked at the database the moment it's considered compromised, every host still holding it starts failing the instant you revoke — and figuring out "which hosts still have the old value" requires re-deriving the very state you were trying to change.
  • There is no audit trail and no access control finer than "who can SSH into this box." Anyone with shell access to a host can cat secrets.env. There is no way to grant "can deploy this app" without also granting "can read the production database password," and no log of who read it or when.
THE NUMBERS

Take a realistic incident: a leaked API key needs to be revoked and replaced everywhere within an SLA of, say, 15 minutes. At 90 seconds/host by hand, that SLA caps your fleet at 10 hosts before the manual process is mathematically unable to meet it — before accounting for the human needing to notice the leak, decide on the new value, and not make a mistake under pressure. Real incidents (§11 has one) happen exactly at this boundary: an org outgrows what its manual rotation process can do in time.

So configuration and secrets need to be: centrally stored, declaratively described, consistently applied to every Pod that references them, and updatable without rebuilding an image. That's the shape of the solution the next section builds — and it borrows the same declarative, reconciled-by-a-controller pattern chapter 2 used for ReplicaSets, applied to data instead of Pod replicas.

ARC 05 · BETTER SOLUTION

Three objects, one delivery mechanism

Kubernetes' answer has three pieces that compose rather than one monolithic "config service": a place to put non-sensitive key/value data (ConfigMap), a place to put sensitive key/value data (Secret), and a general-purpose way to get either one — or ephemeral scratch space, or a host-backed directory — onto a container's filesystem (Volume). Two ways to consume the same object

Whether it's a ConfigMap or a Secret, a Pod consumes it one of two ways, and the choice matters operationally:

  • As environment variables — simple, but the value is fixed at container start; updating the ConfigMap/Secret does not update already-running environment variables (the process would need to restart to see a new value), and env vars are visible to anything that can read /proc/PID/environ or that your process accidentally logs or forwards to a crash reporter.
  • As a mounted file (via a volume) — the kubelet updates the file in place on a periodic sync (default cache propagation delay up to the kubelet's sync period, commonly under a minute) when the source object changes, without restarting the container. This is why credentials and TLS certificates that need to rotate live are almost always file-mounted, not env-injected: the file changes under the running process, and a well-written app can watch the file and reload.
THE CLINCHING ARGUMENT: ONE SOURCE OF TRUTH, MANY CONSUMERS

A single ConfigMap or Secret object can be referenced by any number of Pods, across any number of Deployments, in the same namespace. Rotate the value once — kubectl apply a new Secret revision — and every Pod that mounts it as a volume picks up the new value on the kubelet's next sync, no rebuild, no manual per-host edit, no SSH. This is the exact fix for §4's math: rotation time stops scaling with fleet size and becomes O(1) — one API write, propagated by the system rather than by a human repeating the same edit hundreds of times.

ARC 06 · WHY THAT STILL HURTS

The bill arrives: what ConfigMaps and Secrets don't give you for free

The declarative model fixes the fleet-scale rotation problem, but it introduces its own costs and — most importantly for a beginner chapter — a genuinely dangerous misconception if you stop reading the manual halfway through the word "Secret":

  • A Secret's default storage is base64, not encryption — full stop. etcd, the API server's database (chapter 7 goes deep on it), stores a plain Secret object's data field as base64-encoded bytes, and base64 is a reversible transport encoding with no key and no security property whatsoever — anyone with read access to etcd's disk, an etcd snapshot backup, or the API (with sufficient RBAC permissions) can decode it in one shell command. §15's lab makes you do exactly that computation yourself so it stops being an abstract warning.
  • RBAC is opt-in, not automatic. Creating a Secret does not, by itself, restrict who can read it beyond whatever RBAC rules already exist in the namespace; a cluster with a permissive default (or no RBAC review process) can let far more principals read Secrets than anyone intended. Chapter 13 covers the full RBAC model; this chapter shows the specific rule shape that matters for Secrets.
  • emptyDir and hostPath volumes don't survive what they look like they should survive. An emptyDir volume is deleted when its Pod is removed from a node — including when the Pod is simply rescheduled elsewhere after an eviction or a node failure. A hostPath volume ties data to one specific node's filesystem, so if the Pod is rescheduled to a different node, the data doesn't come with it; it silently starts fresh (or worse, a stale file from a previous unrelated Pod is still sitting there). Neither is "persistent storage" in the sense chapter 11's PersistentVolume is.
  • Size and count limits are real. A single Secret or ConfigMap is capped at 1 MiB total (a etcd-driven default, since the whole object round-trips through etcd on every read — chapter 7 explains why etcd itself recommends keeping individual values under a few KB), and stuffing large blobs into ConfigMaps is a common anti-pattern that degrades API server and etcd performance for the whole cluster.
THE ECOSYSTEM'S ANSWER — AND ITS ADMISSION

Because "base64 stored in etcd" isn't good enough for regulated or security-conscious workloads, the ecosystem layers real cryptography and real access control on top of the Secret API rather than replacing it: encryption-at-rest providers (the API server encrypts Secret values before writing to etcd, covered in §8), external secret managers (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager) that the cluster fetches from via a CSI driver or an operator instead of storing the value in Kubernetes at all, and sealed-secrets-style tools (Bitnami's Sealed Secrets) that let you commit an encrypted blob to git that only the cluster's private key can decrypt into a real Secret. Every one of these exists because the base Secret object is a workflow convenience, not a vault — that's a design decision, not a bug, and this chapter's job is to make sure you know exactly which side of that line you're on at all times.

So the final architecture layers three things: the two API objects (ConfigMap, Secret) for data, the Volume abstraction for delivery, and — for anyone who needs a real confidentiality guarantee — encryption-at-rest and RBAC on top. Let's assemble it.

CROSS-REFERENCE · WHAT A VOLUME MOUNT ACTUALLY IS, ONE LEVEL DOWN

When the kubelet mounts a ConfigMap or Secret "into" a container, the container itself has no idea any of this machinery exists — from inside, it just sees files at a path. What's really happening is the kubelet populates a directory on the node (backed by a small in-memory tmpfs for Secrets, so their plaintext content never touches the node's persistent disk) and bind-mounts it into the container's mount namespace before the container process starts. If you want the kernel-level mechanics of namespaces and mount propagation, that's the Container Internals course's territory — this course treats "the file appears in the container" as the unit of behavior and moves on.

ARC 08 · INTERNAL IMPLEMENTATION

The real objects, byte for byte

Now the actual shapes. Three pieces: (a) the ConfigMap and Secret API objects as real YAML/JSON, (b) exactly how a Pod spec wires either one into env vars or a mounted volume, (c) what changes, concretely, when encryption-at-rest is enabled — the mechanism behind §6's warning.

(a) The objects themselves

A ConfigMap's data field holds plain UTF-8 strings — no encoding step at all:

yamlconfigmap.yaml — apiVersion v1, kind ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: prod
data:                                # plain strings — no encoding at all
  DB_HOST: "prod-db.internal:5432"
  LOG_LEVEL: "info"
  FEATURE_NEW_CHECKOUT: "true"
  app.properties: |               # a whole file, as one string value
    retry.max=3
    timeout.ms=5000

A Secret's data field looks almost identical — except every value must be base64-encoded before you write it into the manifest, because YAML/JSON require valid UTF-8 text and Secret values are allowed to be arbitrary binary bytes (a TLS private key, for instance):

yamlsecret.yaml — apiVersion v1, kind Secret
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: prod
type: Opaque                       # the generic Secret type; kubernetes.io/tls, 
                                    # kubernetes.io/dockerconfigjson etc. are others
data:
  username: cG9zdGdyZXM=            # base64("postgres") — NOT encrypted
  password: aDR4MHItcHIwMGYtMjAyNCE=  # base64("h4x0r-pr00f-2024!")

Notice the type field — it's metadata that tells tooling (and some controllers, like the one that manages TLS certs for Ingress) what shape to expect, but it changes nothing about the storage or encoding mechanism. Every Secret, regardless of type, is base64 in data and stored the same way in etcd absent encryption-at-rest.

DECODE IT YOURSELF, RIGHT NOW

aDR4MHItcHIwMGYtMjAyNCE= is not a hash, not a ciphertext, not scrambled in any cryptographic sense — it is a lossless, keyless, reversible re-encoding of the exact bytes h4x0r-pr00f-2024!. Anyone can reverse it with a one-liner and no secret information whatsoever: echo aDR4MHItcHIwMGYtMjAyNCE= | base64 -d. §15's simulator does this exact computation live in JavaScript — not a canned reveal, a real decode — precisely so this stops being a claim you take on faith.

(c) Encryption-at-rest: what actually moves

Without any extra configuration, the API server persists a Secret object to etcd with its data values exactly as base64-decoded-then-stored — meaning etcd's on-disk value is the raw plaintext bytes (base64 is a wire/manifest convenience; internally the API server stores the decoded bytes). Turn on an encryption-at-rest provider and the API server transparently encrypts each Secret's value with an envelope-encryption scheme before writing it to etcd, and decrypts it transparently on read — the API you interact with (`kubectl get secret`, the volume-mount mechanism) doesn't change at all. What changes is purely what's sitting on the etcd data directory's disk and in etcd snapshot backups.

WHAT ENCRYPTION-AT-REST DOES NOT DO

It does not stop anyone with legitimate API access (an authenticated, authorized kubectl get secret db-credentials -o yaml) from seeing the plaintext — the API server decrypts on the way out to a permitted caller, by design; that's RBAC's job, not encryption's. It does not stop a process running inside a Pod that has the Secret mounted from reading its own mounted files — that's the Pod's own access, which is the whole point of mounting it. What it stops is exactly one thing: someone who obtains raw access to etcd's storage — a stolen disk, an unencrypted etcd snapshot backup left in an S3 bucket, a filesystem-level compromise of an etcd node — from reading Secret values directly off the disk. Two different threats, two different controls; conflating them is the single most common Kubernetes security misconception, and it's why this chapter's simulator makes you toggle both independently.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Numbers you can predict before it bites you

Concrete limits and costs, not vibes:

  • 1 MiB per object. Both ConfigMap and Secret are capped at 1 MiB total size — a consequence of etcd's recommended value-size envelope (chapter 7: etcd recommends keeping individual values well under 8 KB for good performance, with the API layer imposing a hard outer bound). Store large blobs — TLS certificate bundles are fine; multi-megabyte binaries are not — as an actual volume or artifact, not a ConfigMap.
  • Volume-mounted updates aren't instant. The kubelet syncs mounted ConfigMap/Secret content on a periodic cache-refresh cycle (bounded by the kubelet's configured sync period, commonly under a minute by default, longer if you've set subPath mounts — which, notably, do not get live-updated at all). Never assume a rotated Secret is visible to a running Pod within milliseconds.
  • Every Secret reference is an etcd round-trip class of cost. A Pod with several volume-mounted Secrets means the kubelet fetches each object independently on sync; at very high Pod density per node this is a measurable, if usually small, tax on API server and etcd request volume — one reason very large fleets prefer external secret managers with their own caching layers.
  • Security surface scales with who can read the Secret kind, cluster-wide. A single overly broad ClusterRole granting get/list on secrets across all namespaces is one of the most common real privilege-escalation findings in cluster security audits — because Secrets frequently include not just app credentials but the tokens and certificates that grant access to other systems entirely (chapter 13 formalizes this).

ARC 11 · REAL-WORLD INCIDENTS

Three incidents you will eventually meet

Incident 1: "We thought Secrets were encrypted" — the etcd snapshot leak

A common, recurring class of real incidents: a team backs up etcd (a completely reasonable disaster-recovery practice) and stores the snapshot in an object store bucket — which, at some point, is misconfigured with public or overly broad read access, or simply isn't covered by the same access controls as the live cluster. Because encryption-at-rest was never enabled, every Secret in that snapshot is recoverable with a base64 decode the moment someone gets the file — no cluster access, no RBAC bypass needed, just the backup file. This is exactly the "etcd disk exhaustion" and backup-hygiene territory chapter 16 revisits with the named etcd disk-exhaustion incident pattern; the lesson here is narrower and sharper: a backup of an unencrypted secret store is an unencrypted secret store. Fixes, in order of leverage: enable encryption-at-rest before the first Secret is ever created (retrofitting requires re-writing every existing Secret, since the API server only encrypts on write); treat etcd snapshots with the same access control rigor as production database backups; rotate every credential that was ever stored as a plain Secret if a snapshot's exposure is even suspected.

Incident 2: The overly broad ClusterRole

A platform team grants a CI/CD service account a ClusterRole with get, list, and watch on secrets cluster-wide, intending only to let it read its own deployment's database credentials in one namespace. Months later, an unrelated pipeline running under that same service account — compromised via a malicious dependency in a build step — enumerates every Secret in every namespace it can reach, including unrelated teams' cloud provider credentials and internal API tokens stored as Secrets by other applications. Nothing was misconfigured about encryption; the failure is purely RBAC scope, and it's the everyday version of the privilege-escalation pattern named CVEs like CVE-2018-1002105 (chapter 16) exploit more surgically. Fix: scope Secret-reading Roles to specific namespaces (and ideally specific resource names via resourceNames) rather than cluster-wide ClusterRoles — the least-privilege default chapter 13 teaches as a first-class design constraint, not an afterthought.

Incident 3: The emptyDir that wasn't there after a reschedule

An application writes session cache files to an emptyDir volume, and works flawlessly in testing where the Pod never moves. In production, a node experiences memory pressure; the kubelet evicts the Pod, and the scheduler places its replacement on a different node. The new Pod starts with a completely empty emptyDir — as designed, since emptyDir's lifetime is explicitly tied to the Pod's binding to a specific node, not to the workload's logical identity — and the application, which assumed the cache would persist, serves a burst of cache-miss-driven errors and elevated backend load right as it's already recovering from an eviction. Fix: the volume-type decision from §6 should be a deliberate architectural choice, not a default: genuinely ephemeral scratch space is exactly what emptyDir is for; anything that must survive a reschedule needs a PersistentVolumeClaim (chapter 11) or an external store, full stop.

Two illustrative pieces, simplified from the real structure but faithful to the actual flow. First, the shape of validation every Secret passes through before the API server will persist it:

gopkg/apis/core/validation/validation.go — ValidateSecret(), simplified
func ValidateSecret(secret *core.Secret) field.ErrorList {
    allErrs := ValidateObjectMeta(&secret.ObjectMeta, ...)

    // Total size across all keys — the 1 MiB cap from §10.
    var totalSize int64
    for _, value := range secret.Data {
        totalSize += int64(len(value))
    }
    if totalSize > MaxSecretSize {      // 1 * 1024 * 1024
        allErrs = append(allErrs, field.TooLong(field.NewPath("data"), "", MaxSecretSize))
    }

    switch secret.Type {
    case core.SecretTypeServiceAccountToken:
        validateBasicAuthSecret(secret, allErrs)   // type-specific required keys
    case core.SecretTypeTLS:
        validateTLSSecret(secret, allErrs)        // requires tls.crt + tls.key
        // NOTE: none of these branches touch encryption — that happens
        // later, in the storage layer, completely independent of Type.
    }
    return allErrs
}

Second, where encryption-at-rest actually intercepts the write — a storage-layer decorator, not anything the Secret API type itself knows about:

goapiserver/pkg/storage/value/encrypt/envelope — conceptual shape
// Every etcd write for a configured resource (almost always "secrets")
// passes through a Transformer chain before the bytes hit etcd's Raft log.
type Transformer interface {
    TransformToStorage(ctx context.Context, data []byte, ctxADD value.Context) ([]byte, error)
    TransformFromStorage(ctx context.Context, data []byte, ctxADD value.Context) ([]byte, bool, error)
}

// envelopeTransformer: encrypts the object's serialized bytes with a fast
// symmetric Data Encryption Key (DEK), then encrypts THAT key with a slower
// Key Encryption Key (KEK) held by a local provider or an external KMS —
// classic envelope encryption, so the KEK never has to touch every write.
func (t *envelopeTransformer) TransformToStorage(ctx context.Context, data []byte, _ value.Context) ([]byte, error) {
    dek := generateDataEncryptionKey()
    encryptedData := aesEncrypt(data, dek)
    encryptedDEK := t.kek.Encrypt(ctx, dek)     // local provider or KMS plugin gRPC call
    return envelope(encryptedDEK, encryptedData), nil
    // This ciphertext — NOT plaintext, NOT base64 — is what lands in etcd.
    // A plain kubectl get still works: TransformFromStorage runs the reverse
    // on read, invisibly to any authorized, authenticated caller.
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THE DESIGN TO STEAL

Encryption is a storage-layer concern, not a type-system concern. Notice that ValidateSecret has zero awareness of encryption, and the Transformer interface has zero awareness of what kind of object it's encrypting — it operates on serialized bytes generically, and is wired in via the API server's storage configuration (--encryption-provider-config) rather than by any change to the Secret type itself. This is the same separation-of-concerns instinct you'll see repeatedly in this course: the object model describes what the data is, and an independently pluggable layer (encryption here, admission webhooks in chapter 13, the scheduler's filter/score plugins in chapter 8) decides what happens to it. It's why encryption-at-rest can be turned on for an existing cluster without changing a single Secret manifest, a single line of application code, or the Secret schema itself.
