ARC 01 · THE PROBLEM

You understand every piece. Does it assemble into something correct?

Chapters 1 through 15 each isolated one mechanism: what a hash commits to, what a private key proves, how a transaction's bytes are laid out, how Script evaluates a spending condition, what a signature actually signs, why the UTXO set is the only state that matters, what an 80-byte header commits to, which rules a block must satisfy, how mining finds a valid nonce, how peers exchange blocks, how the mempool prices scarce block space, how SegWit restructured the transaction, how Taproot generalized signing, how Lightning moves payments off-chain, and which bugs taught the network the hard way. That isolation was necessary — you cannot learn eight interacting state machines simultaneously — but it leaves a question chapters 1–15 deliberately dodged: in what order do these pieces have to run, and what is the minimum set of them a program needs before you can call it a node instead of a toy?

Answer that precisely and you get a specification. A program that receives raw bytes from an untrusted network and must independently decide, with no central authority to ask, exactly three things:

  • Is this transaction valid? — its inputs exist, are unspent, and its scripts authorize the spend.
  • Is this block valid? — every transaction in it is valid, the block itself obeys the consensus rules (ch.8), and its proof of work is genuine (ch.9).
  • Which chain is the real one? — when two valid chains disagree, which one does this node believe, and what does believing a different one cost to undo (ch.6, ch.9)?

Everything else — wallets, block explorers, exchanges, Lightning nodes — is built on top of a program that answers those three questions correctly and without trusting anyone. This capstone builds that program. Not a simulation of one: an engine, in the JavaScript running this page, that a browser's <script> tag actually executes when you load this file.

THE SHAPE OF THIS CHAPTER

Sections 1–7 derive the answer to "what must a minimal but correct node do, and in what order" from first principles — the same derive-don't-assert method every chapter in this course has used, applied one level up. Sections 8–13 then build each required component, one at a time, showing you the actual JavaScript source with a stepper deck and naming exactly what a toy running in a browser tab simplifies away. ARC 02 · HISTORICAL CONTEXT

Node software has answered "how much do I verify?" five different ways

The three questions in §1 admit a spectrum of answers, not one. At one extreme, verify everything yourself from the genesis block forward, trusting nobody. At the other, ask a server you trust and believe its answer. Every point on this spectrum keeps the same three components non-negotiable — signature verification, a UTXO view, and proof-of-work comparison — and trades away everything else for speed or bandwidth. That is precisely the dependency order this chapter derives in §5, and precisely the six components §8–§13 implement. ARC 03 · NAIVE SOLUTION

Attempt #1: verify the scripts and call it a day

Derive honestly, the way every chapter in this course has. Chapter 4 gave you a real Script interpreter. Chapter 3 gave you real transaction parsing. It is tempting to believe that stacking those two is "validating Bitcoin" — after all, isn't a valid signature the whole point?

pseudocodenaive_node.js — the strawman
function acceptBlock(block) {
  for (const tx of block.txs) {
    for (const input of tx.vin) {
      const prevTx = fetchTransactionByTxid(input.txid); // ask a peer, trust the answer
      const ok = executeScript(input.scriptSig, prevTx.vout[input.vout].scriptPubKey);
      if (!ok) throw new Error("invalid script");
    }
  }
  appendToChain(block); // done — every signature checked out
}

This is not a strawman built to be knocked down cheaply — it is exactly what chapters 3 and 4 alone equip you to build, and it correctly rejects a forged signature. That is real progress. The question §4 answers with numbers is what it lets through.

ARC 04 · WHY IT FAILS

A perfectly checked signature says nothing about whether the coin still exists

fetchTransactionByTxid is doing all the unexamined work in §3's code. It answers "does a transaction with this txid exist anywhere, ever," not "is this specific output still unspent." Those are different questions, and the gap between them is exactly a double-spend:

  • Replay a spent output. Alice signs a valid transaction spending UTXO X to Bob. The signature over that transaction remains cryptographically valid forever — Script has no notion of "already used." Feed the naive validator that same transaction again and it re-executes the script, finds a good signature, and accepts it a second time. Without a structure that remembers X was already consumed, nothing in §3's code can tell the difference between a fresh spend and a replay.
  • Two conflicting spends. Alice signs two transactions, both spending X — one paying Bob, one paying herself back. Both have perfectly valid scripts in isolation. Only a structure that tracks "is X currently unspent" and updates atomically as each transaction is accepted can tell you that accepting the second one requires rejecting the first.
THE NUMBER THAT MATTERS

Script execution is O(1) per input relative to chain history — it only looks at the referenced output and the spending script. Detecting a double-spend against the entire history naively is O(chain length) per input if you have to search — millions of blocks on mainnet. That asymptotic gap is exactly why chapter 6 insisted the UTXO set is not an optimization, it is the only data structure that makes double-spend detection tractable at all. A node without one either can't detect double-spends, or can only detect them by re-scanning history on every single input — a cost that grows without bound as the chain grows, while a UTXO-set lookup stays O(1) forever.

So §3's naive validator is missing an entire component — not a refinement, a structural gap. Script correctness and value-conservation correctness are independent axes, and Bitcoin needs both.

ARC 05 · BETTER SOLUTION

Order the checks the way an adversary forces you to

Add a UTXO set and the double-spend hole closes. But now a second design question appears, one chapter 8 raised and this chapter must actually resolve in code: given N things to check per block, in what order do you check them? A block can arrive from a hostile or merely buggy peer, so the ordering is not a style preference — it is a defense. Step through the reasoning:

THE RULE THAT FALLS OUT

Cheapest and hardest-to-fake checks first. Proof-of-work costs one double-SHA256 to verify and is computationally expensive to fake — reject 99.9% of garbage in microseconds before touching the UTXO set. Structural checks (coinbase-first, no duplicate txids) are pure arithmetic on the block you already have in memory. Only once a block has survived all of that do you pay for UTXO lookups and — most expensive of all — full script execution with real ECDSA verification. This exact ordering is what §12's validateBlock() implements, rule by rule, and it is not incidental: it is a direct, load-bearing consequence of validating data from adversaries instead of colleagues.

ARC 06 · WHY THAT STILL COSTS

Full verification is correct and expensive — this chapter's engine cheats twice to fit in a tab

The ordered checklist in §5 is what real Bitcoin Core runs, and it works — but "correct" and "free" are different properties, and honesty about the gap between this toy and a production node starts here, before you've read a line of its code:

  • Initial block download is not optional if you want zero trust. A new mainnet node in 2024 downloads and validates roughly 500+ GB across nearly a million blocks — hours to days depending on bandwidth and disk — because "trust nobody" means re-deriving the current UTXO set by replaying every transaction since 2009. assumeutxo (Bitcoin Core 26.0+) lets an operator start from a hash-committed UTXO snapshot instead, trading a small, explicit trust assumption for skipping that replay — the same spectrum §2's timeline showed you, now inside the reference client itself.
  • This chapter's own UTXO lookups are O(chain length), not O(1). Section 12's engine rebuilds a UTXO snapshot for a given block by replaying every block from genesis along that block's ancestry (_utxoAtBlock()) rather than maintaining incremental snapshots per branch the way a real node does. For a browser tab validating dozens of demo blocks this is invisible; for a real node maintaining one canonical UTXO database (chapter 6's LevelDB chainstate) it would be disqualifying. Named here so you recognize it instead of assuming it's how production works.
  • Difficulty and coinbase maturity are scaled down, not scaled wrong. Real Bitcoin retargets every 2016 blocks and matures coinbases after 100 confirmations — numbers chosen so retargeting reacts to genuine hashrate trends and reorgs can't casually un-spend mining rewards. This chapter's engine uses a 10-block retarget window and a 1-block maturity period so you can watch both mechanisms fire inside one browser session. The formulas are real; the constants are windows you can see through, not the ones mainnet uses.

Every one of these simplifications is called out again, specifically, next to the code that makes it, in §8–§13. None of them touch the three load-bearing questions from §1 — they change how fast the toy answers them, never whether the answer is correct.

Each module is implementable only once the ones above it exist: the Script VM needs real hashes and real curve arithmetic to check a signature; sighash needs the transaction codec to know what bytes to hash; the validator needs both the Script VM and the UTXO set to check scripts against the outputs they claim to spend; the miner needs the validator to know what a "valid" candidate even is; fork choice needs the miner's notion of cumulative work to compare chains. WHAT THIS TOY SIMPLIFIES AWAY

Three things a production implementation cannot skip: constant-time execution — this code branches and indexes based on secret data (private keys, nonces), so its timing leaks information that a real wallet library (libsecp256k1) eliminates with constant-time field arithmetic and formally verified assembly. Signing randomness — §11's ECDSA signer uses a simplified HMAC-based deterministic nonce inspired by RFC 6979 but without its full retry loop for edge cases; production libsecp256k1 implements the complete specification. Key generation entropy — newWallet() below uses crypto.getRandomValues when available, which is browser-CSPRNG-grade, but a real wallet adds hardware entropy, BIP39 mnemonics (chapter 2), and hardened derivation paths this capstone doesn't rebuild. None of these affect whether a signature verifies correctly here — they affect whether an attacker watching your CPU or your RNG could extract your key, which is a different and equally real threat model this toy does not defend against.

WHAT THIS TOY SIMPLIFIES AWAY

Real transaction values are 64-bit integers; this codec stores satoshi amounts as JavaScript Number, safe up to 2^53 (about 90 quadrillion — far past the 21 million BTC × 10^8 sats supply cap, so it never actually overflows here) but not using the same 64-bit-integer discipline production code must. It also doesn't implement transaction versions beyond the fields chapters 3 and 12 covered (no BIP68 relative-locktime interpretation of nSequence, mentioned in chapter 8's rule list but not enforced by this engine's validator).

ARC 10 · COMPONENT 3 — chapter 4 in miniature

The Script interpreter: a real stack machine, three real spend types

This is not a lookup table pretending to check scripts — it is a genuine stack machine that parses opcodes one at a time, maintains a real stack of byte arrays, implements OP_IF/OP_ELSE/ OP_ENDIF control flow, and calls back into real secp256k1 verification for OP_CHECKSIG. It executes all three spend types chapter 4 walked through: P2PKH, the BIP16 P2SH special case (execute the scriptSig, check the hash, then re-execute the redeem script it reveals), and P2WPKH (BIP141's implied-P2PKH-script rule for version-0, 20-byte witness programs).

WHAT THIS TOY SIMPLIFIES AWAY

The opcode table implements the ones this course needs — push data, flow control, stack ops, hashing, CHECKSIG/CHECKMULTISIG (including Satoshi's famous off-by-one dummy-element consumption bug, kept intentionally because removing it would make this VM diverge from consensus) — not Script's full ~80-opcode set. There is no P2TR/Tapscript execution (chapter 13's Schnorr path uses BIP340 verification, a different algorithm from the ECDSA this engine implements), no OP_CODESEPARATOR-aware scriptCode trimming (this engine never emits one, so it's a documented no-op rather than a real implementation), and no standardness/policy layer (chapter 11) — anything consensus-valid is accepted here even if a real node's mempool policy would relay-reject it.

ARC 11 · COMPONENT 4 — chapter 5 in miniature

Sighash: what a signature actually commits to, two ways

Chapter 5 derived why legacy sighash is quadratic (every input re-serializes the whole transaction) and how BIP143 fixed it with three cached midstate hashes computed once per transaction instead of once per input. Both algorithms are implemented exactly as specified, and both are exercised for real: legacy sighash is what makes §15's mainnet-signature verification possible at all.

WHAT THIS TOY SIMPLIFIES AWAY

The legacy SIGHASH_SINGLE bug (chapter 5's "hash of 0x00…01") is reproduced faithfully, byte for byte, because it is consensus-critical: a real node that "fixed" it would compute a different hash and reject valid historical blocks. What's missing: Taproot's sighash (BIP341, a third algorithm entirely, used only by Schnorr/Tapscript spends from chapter 13) and any caching optimization beyond BIP143's own — a production node memoizes hashPrevouts/hashSequence/hashOutputs once per transaction validation; this engine recomputes them per input checked, which is correct but not performance-tuned.

ARC 12 · COMPONENTS 5 & 6 — chapters 6, 7 & 8 in miniature

The UTXO set, block assembly, and the consensus checklist

Three tightly coupled pieces. The UTXO set (chapter 6) is a map from outpoint to output, mutated by applyTx() and reversed by undoTx() — the undo path is not a nicety, it is what makes §13's reorg possible at all. Block assembly (chapter 7) computes the 80-byte header, expands nBits into a real target, and builds the merkle root exactly as mainnet does — proven by recomputing the real genesis and block-170 merkle roots in §15 and matching the known-good values byte for byte. Validation (chapter 8) is the ordered checklist §5 derived, implemented as named, individually testable predicate functions run in sequence and short-circuited at the first failure — exactly how a real node's ConnectBlock() behaves, and exactly what lets §15's validation gauntlet name the specific rule any malformed block trips.

WHAT THIS TOY SIMPLIFIES AWAY

Real BIP30 (no duplicate txids ever, checked against the entire UTXO set, not just within one block) is narrowed here to intra-block duplicates only — the historical exploit BIP30 closed involved duplicate coinbases across different blocks at heights 91,842 and 91,880, which needs full chain history this toy doesn't retain indefinitely. ARC 13 · COMPONENTS 7 & 8 — chapter 9 in miniature

Mining and fork choice: real nonce grinding, real cumulative work

Mining tries nonces from 0 upward, hashing the real 80-byte header each time, until hashMeetsTarget() — the same function §12's validator calls — returns true. When the nonce space is exhausted (it isn't, at demo difficulty, but the mechanism is real) the coinbase's extranonce field bumps and the merkle root is rebuilt, exactly the escape valve chapter 9 described. Retargeting recomputes the target every RETARGET_INTERVAL blocks from the ratio of actual to expected elapsed time, clamped to a 4× band, using the real Bitcoin Core formula (GetBlockProof) shrunk to a window you can watch fire in one browser session. Fork choice compares cumulative work — not block count — across every branch this node has ever seen, and reorgs by walking back to the common ancestor, undoing the abandoned branch's blocks with the exact same undoTx() from §12, and returning their non-conflicting transactions to the mempool.

WHAT THIS TOY SIMPLIFIES AWAY

Real Bitcoin's target after the 2024 halving requires roughly 2^80+ expected hashes and is chased by exahash/second ASIC farms — a JS loop in a browser tab does perhaps 10^5–10^6 double-SHA256/second, so this engine's demo target is deliberately many orders of magnitude easier (§6 already named this). There is no version-rolling (miners mutating the header's version bits for extra nonce space), no block-template protocol (getblocktemplate/Stratum, chapter 9's pool mechanics), and reorg's common-ancestor search here walks parent pointers directly rather than using a real node's block index with height-indexed lookups — for the handful of forks this demo creates, that's invisible; for a chain with millions of blocks it wouldn't be.

Where to go from here

  • Jimmy Song, Programming Bitcoin — builds the same components this capstone did, in Python, with more exercises and less time pressure.
  • Andreas Antonopoulos, Mastering Bitcoin — the standard reference text this course's chapter-level structure has been in quiet conversation with throughout.
