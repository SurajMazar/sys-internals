POSTGRESQL INTERNALS · CHAPTER 06

MVCC II: HOT Updates,
Freezing & XID Wraparound

Chapter 5 showed you how MVCC gives every reader a private, consistent view of the database by never overwriting a tuple in place. This chapter shows you the bill for that decision, and the two mechanisms PostgreSQL built to keep the bill payable: Heap-Only Tuples, which quietly cancel most of the index-write cost of an UPDATE, and freezing, which prevents the 32-bit transaction counter that makes MVCC work from wrapping around and taking your data down with it.

ARC 01 · THE PROBLEM

An UPDATE that touches one column re-writes every index on the table

Chapter 5 established the rule that makes MVCC work: UPDATE never overwrites a tuple. It inserts a brand-new tuple version with a fresh t_ctid, gives it a new TID, and leaves the old version in place for any transaction whose snapshot still needs it. That single decision is what makes readers never block writers. It also has a consequence that chapter 5 deliberately deferred: every index on the table stores TIDs, not primary keys. An index entry doesn't say "row 42 is over there somewhere" — it says "the row with this key is at block 118, offset 6." When UPDATE creates offset 7 instead, that promise is now false for every index that made it.

So the naive consequence is unavoidable-looking: if the row moves, every index must learn its new address — not just the index on the column you changed, but every index on the table, including the ones on columns you never touched. A row in a table with five indexes that gets one integer column incremented pays for five B-tree insertions, not one, purely because the physical location changed underneath indexes that never cared about that column.

WHY THIS MATTERS FOR THE NEXT TWO CHAPTERS

This chapter is really two problems that share one root cause — tuples are versions, not places. Problem one: versions multiply write amplification through every index (solved by HOT, §5–§8). Problem two: versions are tagged with a 32-bit counter that must eventually be recycled, and recycling it incorrectly is a correctness bug with cluster-wide blast radius (solved by freezing, §7 onward). Chapter 7 assumes you understand both, because SSI's conflict detection is built directly on the same tuple-versioning substrate.

Put a number on it before reading further, because the naive cost is easy to underestimate. A single-row UPDATE on a table with N indexes that doesn't qualify for HOT costs: one heap insert, one old-tuple header rewrite (to set xmax and the forward pointer), and N index insertions, each of which is a B-tree descent that can dirty O(log n) pages and, on an unlucky day, trigger a page split. On an OLTP table doing thousands of updates per second, that multiplier is the difference between a workload your storage can absorb and one that turns your indexes into the bottleneck.

ARC 02 · HISTORICAL CONTEXT

2008: the release that made UPDATE-heavy OLTP viable

PostgreSQL shipped MVCC in 1999 (chapter 5) and then spent nine years living with its index-amplification tax before shipping the fix. That gap is not laziness — HOT required getting page-level bookkeeping (line-pointer redirection, opportunistic pruning) exactly right, because a bug here corrupts index scans silently. DEEP CONTEXT · WHY "HEAP-ONLY"?

The name describes exactly what's missing: a heap-only tuple exists only in the heap. No index anywhere points to it directly. It is reachable exclusively by following a chain of t_ctid pointers that starts at the root line pointer — the one slot every index entry actually references. That indirection is the entire trick: indexes keep pointing at a stable root forever, while the root's line pointer transparently redirects to wherever the current live version happens to sit on that same page.

ARC 03 · NAIVE SOLUTION

Attempt #1: update the heap, then update every index, unconditionally

Derive it honestly, the way heap_update() would look if HOT didn't exist. This is not a strawman invented for the lesson — it is exactly what PostgreSQL 8.2 and earlier did, and it is exactly what happens today whenever HOT's conditions (§5) aren't met.

Cnaive_update.c — the pre-HOT path, annotated
void
naive_heap_update(Relation rel, ItemPointer otid, HeapTuple newtup)
{
    HeapTuple oldtup = heap_fetch(rel, otid);

    /* 1. Insert the new version somewhere — same page if there's
     *    room, otherwise ANY page with free space at all.        */
    ItemPointerData newtid = RelationPutHeapTuple(rel, newtup);

    /* 2. Retire the old version: stamp xmax = my XID, point its
     *    t_ctid at the new tuple's TID (chapter 5's forward link). */
    oldtup->t_data->t_xmax = GetCurrentTransactionId();
    oldtup->t_data->t_ctid = newtid;

    /* 3. THE EXPENSIVE PART: walk every index on this relation and
     *    insert a (key, newtid) entry — even for indexes whose
     *    indexed columns are byte-for-byte identical in newtup.   */
    foreach(idx, RelationGetIndexList(rel))
    {
        Relation irel = index_open(idx, RowExclusiveLock);
        Datum values[INDEX_MAX_KEYS]; bool isnull[INDEX_MAX_KEYS];
        FormIndexDatum(irel, newtup, &values, &isnull);
        index_insert(irel, values, isnull, &newtid, rel, true, true, ...);
        index_close(irel, RowExclusiveLock);
    }
}

Nothing here is wrong — it is correct, and it is how every index-organized MVCC update has to work in the absence of a special case. It already tells you where the cost lives: step 3 runs once per index, every single time, regardless of which columns actually changed. ARC 04 · WHY IT FAILS

Write amplification you can compute with one multiplication

Quantify what §3 costs before reaching for a fix — the naive path's damage is arithmetic, not anecdote. For a table with N indexes, every UPDATE that doesn't special-case anything performs:

  • 1 heap tuple insert (the new version) + 1 heap tuple header rewrite (the old version's xmax/ctid) — unavoidable, this is MVCC itself.
  • N B-tree (or GiST/GIN/BRIN) insertions, each an O(log n) descent that can dirty several pages and, at some probability per insert, split a full index page — an operation that itself writes WAL and can cascade upward.
  • N stale index entries left behind, each still pointing at the now-dead old TID, inert until a future VACUUM walks the index and removes them.
THE NUMBERS

Take a session table with 4 indexes (primary key, a foreign key, a partial index, a timestamp index for expiry sweeps) doing 10,000 UPDATEs/sec updating only a last_seen column that one of those indexes covers. Naively: 10,000 heap writes/sec plus 40,000 index insertions/sec — four times the logical write rate, most of it wasted on indexes whose keys never moved. Each of those 30,000 unnecessary index insertions also produces WAL, doubles the eventual VACUUM cleanup cost (dead root entries in indexes that never needed touching), and increases B-tree page-split probability, which is itself proportional to insert rate. This is exactly the workload — high-frequency single-row updates against an indexed OLTP table — for which PostgreSQL is otherwise a poor fit without HOT, and it is why chapter 12's bloat discussion keeps returning to this exact multiplier.

The fix cannot be "don't index so much" — real schemas need those indexes for the read paths. It has to be: detect, per UPDATE, whether any index actually needs to know about it, and if not, skip step 3 of §3 entirely. That is a page-local bookkeeping problem, and §5 derives the two conditions under which it is safe.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three ways to avoid touching N indexes — and the one that survived

Candidate A: in-place update with an undo log (the Oracle/InnoDB shape)

Overwrite the tuple in place, and push the old version into a separate undo/rollback segment for readers who still need it. Indexes never move because the row's physical address never changes. This is a real, successful design — it's what InnoDB and Oracle do (§9 compares it properly) — but it does not fit onto PostgreSQL's storage model without inventing an entirely new subsystem: a second write path (the undo store) with its own WAL, its own crash-recovery obligations, and its own space-reclamation problem, precisely mirroring the "vacuum" problem it was meant to avoid. Rejected for PostgreSQL specifically: it would replace one well-understood bookkeeping cost (heap versions + vacuum) with a second one (undo segments + purge), not eliminate a cost — and PostgreSQL's append-only heap plus WAL design predates the appetite to build that.

Candidate B: only re-index indexes whose columns changed

An obvious partial fix: compare old and new tuple, compute which columns differ, and skip index_insert for any index that doesn't reference a changed column. PostgreSQL does do exactly this comparison — but notice it does not solve the problem from §1. The new tuple still has a new TID. Even an index on an untouched column still needs to know that the key it has now points at a dead row; it must either point at the new TID or its old entry becomes permanently wrong. Column-change detection alone reduces N to "the subset of indexes covering changed columns" — still >0 whenever any indexed column changes, and doesn't help the common case of updating one non-indexed column on a row covered by several indexes on other columns, which is precisely the case in §4's numeric example. Necessary but not sufficient.

Candidate C: keep the new version reachable without moving the address at all ✓

Combine two ideas: (1) if the new version can be placed on the same page as the old one, and (2) if no indexed column changed, then no index needs a new entry at all — the existing index entry, which points at the old tuple's line pointer, can be made to lead to the new tuple by redirecting that line pointer inside the page, rather than by asking every index to learn a new address. The index's promise ("the row with this key is at block 118, offset 6") stays literally true forever; offset 6 is repurposed as a stable redirector, and what it redirects to is what changes. This is HOT.

THE CLINCHING ARGUMENT: THE FIX NEEDS NO NEW SUBSYSTEM

HOT's decisive advantage over candidate A is that it needed no new storage layer, no new WAL record types beyond a page-local prune record, and no new crash-recovery path — it is entirely a reinterpretation of two bits already living in the tuple header (t_infomask2) plus one already-existing field (ItemIdData.lp_flags). Every mechanism it touches — line pointers, page pruning, visibility checks — already existed for ordinary heap management. That is why it shipped as one release's headline feature rather than a multi-year storage rewrite.

ARC 06 · WHY THAT STILL COSTS

HOT's fine print: space you must reserve, and chains you must eventually cut

HOT is not free, and its costs are exactly the two conditions it relies on, read backwards:

  • "Same page" only works if the page has room. A freshly bulk-loaded table, packed to the last byte (the default heap fillfactor is 100 — pack pages completely full), has zero free space for a HOT update to land in. The very first UPDATE on such a page cannot be HOT no matter how innocuous the change is, because RelationPutHeapTuple has nowhere to put the new version without moving to another page — which forces a real index update. You must deliberately reserve space you are not yet using (lowering fillfactor) to make future HOT updates possible. That is dead weight on disk and in the buffer cache for the sole purpose of insurance against a future write pattern.
  • Chains still have to be cut sometime. Every HOT update on the same root tuple lengthens a chain of heap-only tuples linked by t_ctid. An index scan that lands on the root line pointer must walk the entire live chain to find the current version — a chain no one has pruned yet is a linear scan cost paid on every lookup. heap_page_prune() reclaims dead members opportunistically (§8), but between updates and the next prune opportunity, the chain is real, unindexed, in-page linked-list traversal cost.
  • An indexed-column change breaks the whole chain immediately. One UPDATE that touches an indexed column forces a real index insertion for that index — and even then, other indexes on unaffected columns can still ride the HOT path for that same UPDATE, so the "all or nothing" framing of §1 is not quite true in practice; it is index-by-index. But it does mean mixed workloads (some updates touch indexed columns, some don't) produce mixed chains — some short, some long — and no single fillfactor setting is right for all of them.
THE INDUSTRY'S UNFINISHED ANSWER — WARM

HOT's remaining gap — indexed-column changes still pay full price — was the target of the WARM (Write Amplification Reduction Method) patch series proposed by Alvaro Herrera, Pavan Deolasee and others around 2017. WARM extended the same page-local redirection idea to permit one indexed-column change per chain by storing multiple index entries pointing at the same root and disambiguating with an extra bit, at the cost of real complexity in the visibility and index-scan code. It was never merged into core — reviewers judged the correctness risk too high relative to the marginal win over HOT plus a sane fillfactor — and the project remains the standing example of "the next 80% is much harder than the first 80%" in this specific corner of the codebase.

So the final architecture is HOT plus fillfactor plus opportunistic pruning plus ordinary VACUUM as the backstop that eventually removes what pruning alone could not. And running alongside it — orthogonal to whether any given UPDATE was HOT — is the second half of this chapter's mandate: every tuple version, HOT or not, still carries a 32-bit transaction id that eventually needs freezing. Let's meet both mechanisms properly.

THE INVARIANT THAT MAKES ALL OF THIS SAFE

HOT chains never span pages. A heap-only tuple is only ever created on the same page as its root, because the entire mechanism depends on the root's line pointer being able to redirect within its own page's line-pointer array — ItemPointerData addresses a page and an offset, and LP_REDIRECT's payload is just another offset on that same page. If a HOT update's new version wouldn't fit on the origin page, PostgreSQL doesn't get clever about cross-page redirects; it simply falls back to a normal, non-HOT update, and pays the full index-insertion price from §3. This is the mechanism's real boundary, and it's why fillfactor (reserving room on the origin page specifically) is the lever that matters, not overall table free space.

(b) The header fields — real layout, real bit positions

HeapTupleHeaderData carries the whole mechanism in two fields that already existed for other reasons. t_ctid normally just says "this is my own TID"; HOT repurposes it, for a chain member, to mean "here is the next, newer version." t_infomask2 normally just packs the tuple's attribute count into its low 11 bits; HOT claims two of its high bits.

Caccess/htup_details.h — simplified but structurally faithful
typedef struct HeapTupleHeaderData
{
    union {
        HeapTupleFields t_heap;      /* xmin, xmax, cid/xvac */
        DatumTupleFields t_datum;
    } t_choice;

    ItemPointerData t_ctid;          /* self, OR next-version TID for a HOT chain member */

    uint16 t_infomask2;         /* low 11 bits: natts. high bits, in part: */
    /* #define HEAP_HOT_UPDATED   0x4000   -- this version was HOT-updated;
     *                                       t_ctid points at its successor       */
    /* #define HEAP_ONLY_TUPLE    0x8000   -- this version IS a heap-only tuple;
     *                                       no index anywhere points at it        */

    uint16 t_infomask;          /* null bitmap flags, xmin/xmax commit status, etc. */
    uint8  t_hoff;               /* offset to tuple data, i.e. header size */
    bits8 t_bits[1];             /* null bitmap, variable length */
} HeapTupleHeaderData;

/* storage/itemid.h — the line pointer every index TID resolves through */
typedef struct ItemIdData
{
    unsigned lp_off:15,    /* byte offset of tuple, or of redirect target */
             lp_flags:2,  /* LP_UNUSED=0 · LP_NORMAL=1 · LP_REDIRECT=2 · LP_DEAD=3 */
             lp_len:15;   /* byte length of tuple; unused/meaningless for REDIRECT */
} ItemIdData;

Read the two flags together and the whole chain becomes legible: a tuple with HEAP_HOT_UPDATED set is not the newest version — follow its t_ctid. A tuple with HEAP_ONLY_TUPLE set is reachable only through that chain — no index entry names it directly, ever, for as long as it lives. The root of a chain has neither bit set on its own tuple (or is a plain LP_REDIRECT line pointer once pruning has run); every non-root member has HEAP_ONLY_TUPLE, and every member except the last has HEAP_HOT_UPDATED.

(c) heap_page_prune() — vacuum's little cousin that runs on every access

Pruning does not wait for VACUUM. Any backend that visits a page — during an ordinary SELECT, an UPDATE, or an INSERT looking for free space — can trigger heap_page_prune() if it notices dead tuples and needs the room. The algorithm walks each HOT chain from its root, using HeapTupleSatisfiesVacuum() to classify each member, and rewrites the line pointer array in place:

Caccess/heap/pruneheap.c — heap_prune_chain(), simplified
static void
heap_prune_chain(Buffer buffer, OffsetNumber rootoffnum, PruneState *prstate)
{
    OffsetNumber offnum = rootoffnum;
    OffsetNumber chain[MaxHeapTuplesPerPage];
    int nchain = 0;
    bool allDead = true;

    /* Walk t_ctid forward while HEAP_HOT_UPDATED is set, classifying
     * every member we pass along the way.                               */
    for (;;)
    {
        ItemId lp = PageGetItemId(page, offnum);
        if (!ItemIdIsNormal(lp)) break;

        HeapTupleHeader htup = (HeapTupleHeader) PageGetItem(page, lp);
        HTSV_Result st = HeapTupleSatisfiesVacuum(htup, prstate->OldestXmin, buffer);

        if (st != HEAPTUPLE_DEAD)
            allDead = false;    /* one live member is enough to keep the chain */

        chain[nchain++] = offnum;
        if (!(htup->t_infomask2 & HEAP_HOT_UPDATED))
            break;             /* reached the newest version */
        offnum = ItemPointerGetOffsetNumber(&htup->t_ctid);
    }

    if (allDead)
    {
        /* Whole chain is invisible to everyone: mark every member
         * LP_UNUSED and the root LP_DEAD (a stub — indexes may still
         * point here, so the slot itself must survive until VACUUM's
         * index cleanup pass removes those index entries too).        */
        heap_prune_record_dead(prstate, rootoffnum);
        for (int i = 1; i < nchain; i++)
            heap_prune_record_unused(prstate, chain[i]);
    }
    else if (nchain > 1)
    {
        /* Some prefix of the chain is dead, but the tail survives:
         * unlink the dead middle, and REDIRECT the root straight to
         * the first live member. Indexes never learn about this —
         * they were pointing at rootoffnum the whole time.            */
        heap_prune_record_redirect(prstate, rootoffnum, first_live_offset(chain, htup));
    }
}

WHY LP_DEAD SURVIVES WHEN LP_UNUSED DOESN'T

Notice the asymmetry in the algorithm above: a fully-dead chain's root becomes LP_DEAD, not LP_UNUSED, while its interior members become LP_UNUSED immediately. The reason is indexes: every index on the table may still hold an entry pointing at that root offset. Recycling the slot (LP_UNUSED) before those index entries are removed would let a future, unrelated tuple reuse the same offset — and a stale index entry would then silently point at the wrong row. Only VACUUM's index-cleanup phase, which physically visits every index and removes entries pointing at dead TIDs, is allowed to downgrade a root from LP_DEAD to LP_UNUSED. heap_page_prune() can reclaim tuple storage without VACUUM; it can never reclaim a line pointer slot that an index might reference without VACUUM. That distinction is the entire reason VACUUM still has a job in a HOT-heavy table.

(d) The other half of the chapter: a 32-bit clock that must never lap itself

Every tuple's xmin and xmax are TransactionId — a plain uint32. PostgreSQL does not compare XIDs with ordinary integer <; it compares them circularly, treating the 232 XID space as a clock face and asking "is id1 within the next 231 ticks ahead of id2?" That single design decision — necessary because XIDs must wrap and be reused, or the counter would exhaust after ~4.29 billion transactions — is also the entire wraparound danger surface:

Caccess/transam.h — the comparison that makes wraparound possible AND dangerous
#define InvalidTransactionId        ((TransactionId) 0)
#define BootstrapTransactionId      ((TransactionId) 1)
#define FrozenTransactionId         ((TransactionId) 2)
#define FirstNormalTransactionId    ((TransactionId) 3)

/* True iff id1 precedes id2 on a 2^32 circle, i.e. id2 is reachable
 * from id1 by advancing fewer than 2^31 steps. Signed 32-bit subtraction
 * does the modular-distance math for free via overflow wraparound.      */
static inline bool
TransactionIdPrecedes(TransactionId id1, TransactionId id2)
{
    int32 diff = (int32) (id1 - id2);
    return diff < 0;
}

The circle is the whole point and the whole danger: any two XIDs less than 231 apart have an unambiguous "earlier/later" relationship. But nothing stops a tuple's xmin from aging past that window if it's simply never revisited — and once the gap between "now" and a stored xmin exceeds 231, TransactionIdPrecedes() flips its answer: a transaction that actually committed in the past now compares as being in the future, which for a visibility check means a row that was dead can appear to spring back to life, or vice versa — silent, undetectable data corruption, not a crash. Freezing exists purely to keep every stored xmin inside a safe distance of the present.

Freezing rewrites a tuple's status, not (in modern PostgreSQL) its raw xmin value: it sets a combination of t_infomask bits (HEAP_XMIN_COMMITTED | HEAP_XMIN_INVALID together, a combination that's otherwise contradictory and is specifically repurposed to mean "frozen — always visible, regardless of what xmin says") so that every future visibility check short-circuits to "definitely visible" without ever running TransactionIdPrecedes() against that xmin again. (Versions before 9.4 physically overwrote xmin with FrozenTransactionId — value 2 — which worked but required a WAL-logged page rewrite for every frozen tuple; the infomask-bit approach folds freezing into work VACUUM is already doing to the page.)

THE HORIZON CAN BE PINNED BY THINGS THAT AREN'T EVEN RUNNING QUERIES

Freezing is bounded not just by GUCs but by OldestXmin — the oldest snapshot any active process might still need — and that horizon can be held back by more than a slow query. A logical or physical replication slot whose consumer has stopped reading keeps every WAL record and every XID since its creation "still needed," indefinitely, with zero visible client connections. A forgotten idle in transaction session pins the horizon just as effectively as an active one. §11 walks through real outages caused by exactly this — the horizon, not the freeze machinery, was the thing that failed.

Read this table the same way chapter 1 read its process-model comparison: every MVCC or version-oriented store must eventually reclaim old versions, and the only real design choice is where the reclamation cost is paid and what fails if you defer it too long. PostgreSQL's answer keeps updates fully in the primary data structure (no separate undo store) at the price of a deferred, occasionally invisible garbage-collection debt — bloat if VACUUM under-runs, wraparound risk if freezing under-runs — both of which are this chapter's subject. InnoDB and Oracle pay a similar bill in a segregated undo area, trading "the main table never bloats from old versions" for "a long-running reader can force a huge undo/rollback footprint, or in Oracle's case, simply fail." LSM systems defer the same debt to compaction and accept read amplification as the ongoing cost of never doing in-place work at all.

ARC 10 · PERFORMANCE CHARACTERISTICS

What HOT actually buys, in Big-O and in bytes

  • Non-HOT update: O(1) heap work + O(N · log(n)) index work, where N is index count and n is index size — dominated entirely by the index term for any table with more than one or two indexes.
  • HOT update: O(1) heap work, O(0) index work. The entire N-index term vanishes. This is why HOT is described as the single biggest OLTP throughput feature in the codebase — it doesn't optimize the index B-tree insert, it skips it.
  • heap_page_prune() cost: O(tuples on the page) per invocation, amortized across ordinary page accesses — no separate scan of the table is needed, and it emits a compact, page-local WAL record (a PRUNE record) rather than one record per reclaimed tuple.
  • Cache/locality effect: because a HOT chain stays on one page, an UPDATE-heavy hot row keeps its entire version history in one buffer-pool page — one pin, one set of cache lines, no extra pread() to a second heap page and no extra random-access write into an index's B-tree leaf level (which, for a large index, is very likely cold relative to the heap page you were already touching).
  • Freezing cost, amortized: heap_freeze_tuple() work is folded into VACUUM passes the table needed anyway under normal operation; the expensive case is the aggressive scan (vacuum_freeze_table_age exceeded) which must visit every page regardless of the visibility map, turning an O(dirty pages) job into an O(table size) one — exactly the scenario a neglected large table hits right when you can least afford a full-table scan.

The curves are an analytic sketch (throughput inversely proportional to per-update index-descent cost, index count as the dominant term) tuned to match the qualitative shape reported in pgbench-style HOT benchmarks since 8.3. ARC 11 · REAL-WORLD PRODUCTION

Three incidents that made "vacuum is boring" a dangerous opinion

Incident 1: Sentry's transaction-ID wraparound scare (2015)

Sentry publicly documented an episode where a heavily-written table's age(relfrozenxid) climbed far faster than autovacuum could bring it back down, driven by a combination of high UPDATE churn (bumping XID consumption) and autovacuum runs that were repeatedly cancelled or starved by competing I/O and lock contention from foreground traffic — the classic pattern where the very system under enough load to need aggressive vacuuming is also the system too busy to let vacuuming finish. The fix followed the mechanism directly: identify the table(s) closest to autovacuum_freeze_max_age, run a manual, throttled VACUUM FREEZE during a quieter window ahead of the automatic forced pass, and tune per-table autovacuum cost-limit settings so that table's vacuum could no longer be starved indefinitely by everything else.

Incident 2: Joyent's Manta outage (2015) — a replication-adjacent horizon pin

Joyent's public postmortem for a major Manta object-storage outage traced the root cause to a PostgreSQL instance approaching transaction ID wraparound: age(relfrozenxid) on a critical metadata table grew until the cluster crossed into the emergency stop-limit region and refused new write transactions outright, exactly as designed — a deliberately blunt, cluster-wide protection against the alternative (silent data corruption from a flipped visibility comparison). Because the affected table sat on the critical path for the entire storage service, a database-level safety mechanism became a regional outage. The structural lesson tracked by the incident is the same one this chapter derives from TransactionIdPrecedes(): nothing about wraparound protection cares how important your service is — the 231 boundary does not negotiate.

Incident 3: the abandoned replication slot

A recurring, less dramatic pattern across many production postmortems (Mailchimp among the companies that have written publicly about variants of it): a logical or physical replication slot is created for a consumer — a CDC pipeline, a reporting replica — and that consumer is later decommissioned without ever dropping the slot. The slot's xmin/catalog_xmin keeps holding the vacuum horizon exactly where it was the day the consumer stopped reading, silently, with no query, no open transaction, and no obvious symptom in pg_stat_activity — you have to know to check pg_replication_slots. Autovacuum keeps running, keeps "succeeding," and keeps making no progress on that table's dead tuples or its frozen-XID horizon, because it correctly refuses to remove anything the slot might still need. Fixes, in order of leverage: alert on pg_replication_slots age/lag independent of connection count; drop slots the moment a consumer is retired, not "eventually"; and monitor age(datfrozenxid) cluster-wide as a first-class metric, not something you discover during an incident.

First, the fork in heap_update() — this is the single most important branch in this chapter:

Caccess/heap/heapam.c — heap_update(), the HOT-eligibility fork (simplified)
TM_Result
heap_update(Relation relation, ItemPointer otid, HeapTuple newtup, ...)
{
    Bitmapset *modified = HeapDetermineColumnsInfo(relation, newtup, oldtup);
    bool use_hot_update = false;

    /* Condition 1: did the UPDATE touch any column referenced by
     * ANY index (including expression & predicate indexes)?         */
    bool indexed_cols_changed =
        bms_overlap(modified, RelationGetIndexAttrBitmap(relation, INDEX_ATTR_BITMAP_ALL));

    if (!indexed_cols_changed)
    {
        /* Condition 2: does the new version fit in the free space
         * already on oldtup's page? PageGetHeapFreeSpace() answers this
         * against pd_lower/pd_upper -- exactly the room fillfactor
         * reserved, if any is left.                                    */
        if (PageGetHeapFreeSpace(page) >= newtup->t_len)
            use_hot_update = true;
    }

    if (use_hot_update)
    {
        newtup->t_data->t_infomask2 |= HEAP_ONLY_TUPLE;
        oldtup.t_data->t_infomask2  |= HEAP_HOT_UPDATED;
        /* new version placed on the SAME page; NO index_insert calls follow. */
    }
    else
    {
        /* fall back to the full path from §3: place anywhere, then
         * insert into every index that needs to know.                  */
        RelationGetIndexList(relation); /* ... index_insert() per index ... */
    }
    ...
}

Next, the wraparound guard itself — the function every single write transaction passes through:

Caccess/transam/varsup.c — GetNewTransactionId(), simplified
TransactionId
GetNewTransactionId(bool isSubXact)
{
    TransactionId xid;

    LWLockAcquire(XidGenLock, LW_EXCLUSIVE);
    xid = ShmemVariableCache->nextXid;

    /* xidStopLimit is computed from the oldest datfrozenxid across every
     * database, plus (2^31 - 1,000,000): once we're within one million
     * transactions of the theoretical wrap point, refuse to allocate.  */
    if (TransactionIdFollowsOrEquals(xid, ShmemVariableCache->xidStopLimit))
    {
        LWLockRelease(XidGenLock);
        ereport(ERROR,
            (errmsg("database is not accepting commands to avoid wraparound data loss in database \"%s\"",
                    oldest_datname),
             errhint("Stop the postmaster and vacuum that database in single-user mode.\n"
                     "You might also need to commit or roll back old prepared transactions, "
                     "or drop stale replication slots.")));
    }
    else if (TransactionIdFollowsOrEquals(xid, ShmemVariableCache->xidWarnLimit))
        ereport(WARNING,
            (errmsg("database \"%s\" must be vacuumed within %u transactions",
                    oldest_datname, ShmemVariableCache->xidWrapLimit - xid)));

    TransactionIdAdvance(ShmemVariableCache->nextXid);   /* wraps via uint32 overflow, skipping 0/1/2 */
    LWLockRelease(XidGenLock);
    return xid;
}
WHY THE DEVELOPERS WROTE IT THIS WAY — TWO CHOICES TO STEAL

1. Encode the decision in bits the visibility check already reads. HOT and freezing both avoid adding a new code path for readers — t_infomask/t_infomask2 are inspected on every tuple visibility check regardless; teaching them two more meanings costs nothing extra per read. 2. Fail loudly, early, and by refusing writes rather than corrupting data. GetNewTransactionId() could have let the counter wrap silently — instead it deliberately takes the whole database read-only well before the mathematically dangerous point, converting an invisible correctness bug into a loud, recoverable operational incident. That's the same "prefer an observable failure over a silent one" instinct chapter 1's crash protocol embodies, applied to a completely different subsystem.
