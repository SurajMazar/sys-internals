APACHE KAFKA INTERNALS · CHAPTER 05

Replication: ISR, High Watermark
& Leader Epochs

Kafka replicates every partition, and yet it runs neither Raft nor Paxos. It runs something older and stranger: a dynamic quorum called the in-sync replica set, arbitrated by an external controller, in which followers pull data from the leader using the same request type a consumer would send. This chapter derives that design from the ground up, proves exactly what durability guarantee it gives you, and walks through the real bug — and the real fix, leader epochs — that it took the project a decade to get right.

ARC 01 · THE PROBLEM

One log, several copies, and a precise definition of "safe"

A Kafka partition is a single ordered, append-only log. The moment you put that log on more than one broker — which you must, because disks and machines fail — you have created a distributed systems problem with a brutally specific correctness bar: a message a producer was told is "committed" must survive the failure of any one broker (or, with the right settings, several), and every consumer must see exactly the same sequence of committed messages in exactly the same order, forever.

Unpack that bar and five requirements pull in different directions, the same shape you will see in every serious replication design:

  • Durability under failure — an acknowledged write must not vanish when the broker that took it dies five milliseconds later.
  • A single, agreed order — replicas must not merely hold the same messages, they must hold them at the same offsets; two brokers disagreeing about what's at offset 4,502,001 is worse than either one losing data, because it's silent.
  • Low, predictable write latency — replication cannot mean waiting on the slowest machine in the fleet for every single record; producers need bounded, tunable latency.
  • Bounded staleness for followers — the system needs an honest, observable answer to "how far behind is replica 3?" — not a guess.
  • Safe recovery after a crash — when a replica restarts after being down, or after losing a leader election, it must reconcile its log with the new truth without ever silently keeping data that was never actually committed, and without ever discarding data that was.

Kafka's partition-level replication protocol is the machinery built to satisfy all five without paying for a textbook consensus algorithm per partition — and a Kafka cluster can easily have hundreds of thousands of partitions. The answer is not Raft. It is not Paxos. It's a leader/follower scheme with a dynamically shrinking and growing quorum — the ISR — whose membership is decided by the leader but whose official record of truth lives in a separate consensus system entirely (the controller, backed historically by ZooKeeper and today by the KRaft Raft quorum you will meet in chapter 6). Understanding why that split design exists, and exactly what it promises, is this chapter.

WHY THIS MATTERS FOR THE NEXT 10 CHAPTERS

Every correctness property Kafka advertises — "no data loss with acks=all", "consumers never see uncommitted data", "exactly-once semantics" (KIP-98, chapter 8 of this course) — is built on top of the exact mechanism in this chapter: the ISR, the high watermark, and the leader epoch. Get this chapter's model wrong and every downstream guarantee you reason about will be wrong too.

DEEP CONTEXT · WHY NO CONSENSUS PAPER SHOWS UP UNTIL LATE

Kafka 0.7 (2011) had no replication at all — each partition lived on exactly one broker, and losing that broker meant losing the partition. Replication landed in 0.8 (2013), designed by Jun Rao, Neha Narkhede, and Jay Kreps under a constraint academic consensus protocols weren't built for: a single cluster with tens of thousands of partitions, each independently needing a leader. Running a full Raft or Paxos leader-election round per partition at that cardinality was — and still would be — prohibitively chatty. The design instead reused a single external coordination service (ZooKeeper) to answer "who's the controller", and let the controller answer "who's the leader" for every partition in bulk. That architectural shortcut is exactly what chapter 6 revisits and eventually replaces with KRaft.

ARC 03 · NAIVE SOLUTION

Attempt #1: replicate to everyone, synchronously, always

Derive it honestly. If N brokers hold a copy of a partition, the simplest correct-looking design is: the leader appends a record locally, then pushes it to every follower over RPC, and only acknowledges the producer once all N-1 followers have confirmed receipt. No bookkeeping, no dynamic membership, no edge cases — every replica is always identical.

pseudo-Scalanaive_leader.scala — the strawman, annotated
class NaiveLeader(followers: List[FollowerRpc]) {

  def append(record: Record): Ack = {
    log.append(record)                        // leader writes to its own local log first

    // synchronously push to EVERY follower and block for ALL replies —
    // no concept of "caught up enough", no timeout-based membership
    val replies = followers.map(f => f.replicateBlocking(record))

    if (replies.forall(_.ok)) Ack.Success
    else Ack.Failure("a replica did not confirm")  // now what? retry forever?
  }
}

This is not a strawman built to be laughed at — it is the correct first thing to reason about, and it already gets the hard part right: with every replica always fully caught up, there is no ambiguity about what "committed" means, no truncation problem on restart, and no possibility of two replicas disagreeing about offset 4,502,001. If you could afford it, you would not need the rest of this chapter.

ARC 04 · WHY IT FAILS

The tyranny of the slowest replica, quantified

The naive design's fatal flaw is arithmetic, not aesthetics: write latency becomes the maximum over all replicas, not the average, and write availability becomes the AND of every replica's availability, not the OR. Both get worse, not better, as you add replicas for durability — which is exactly backwards from what you want a durability knob to do.

  • Latency: with three replicas whose network round-trip + fsync latency is, say, 4 ms, 5 ms, and 40 ms (one follower is on a loaded host, or across a slower link), every single produce call now takes ≥ 40 ms — a tail latency problem you cannot average away, because the naive protocol waits for the max, always.
  • Availability: with RF=3 and independent per-broker availability of 99.9%, the probability all three are simultaneously reachable is 0.999³ ≈ 99.7% — worse than any single replica alone, and the gap widens with every replica you add. Replication was supposed to improve availability of the data; the naive protocol trades data availability (a copy survives) for write availability (you can never write while any copy is down) — precisely the wrong trade for a system whose entire job is accepting writes.
  • No sick-day tolerance: a single follower doing a slow GC pause, a rebalancing disk, or a flaky NIC does not just slow down — it takes the entire partition off the write path for everyone, including producers who never touch that follower's data directly.
THE NUMBERS THAT KILL IT

Model produce latency for RF replicas each with i.i.d. per-request latency drawn from a distribution with a heavy tail (typical of real datacenter networks and disks). The naive protocol's latency is the max order statistic of RF samples — and the expected maximum of RF samples from a heavy-tailed distribution grows with RF, not shrinks. Add a fourth replica for "more durability" and you have guaranteed yourself a worse p50, not just a worse p99. This is the same Little's-Law-adjacent intuition from the PostgreSQL course's chapter 1 (one slow server dictates throughput for everyone) — here it dictates latency for everyone, on every single write, forever.

So the requirement is not "replicate to all N, always" — it is "replicate to enough replicas, and make 'enough' dynamic, observable, and fenced against silent divergence." Section 5 derives what that has to look like.

THE CLINCHING ARGUMENT: WHY PULL, NOT PUSH

Notice a detail buried in candidate C that is easy to skate past: followers pull from the leader by issuing an ordinary Fetch request — the exact same API a consumer uses, differentiated only by the replica ID field (a real client sets it to -1; a follower sets it to its own broker ID). This is a deliberate reuse, not an accident: it means the leader needs exactly one code path for "someone wants data starting at offset X" — the same page-cache-backed, zero-copy log-read path serves consumers and followers alike (chapter 10 quantifies why that path is fast). A push-based design would need a second, separate replication RPC path with its own flow control, its own backpressure story, and its own testing surface. Pull-based replication also hands backpressure to the follower for free: a slow follower simply issues its next fetch later, rather than the leader needing to manage per-follower send buffers and retry queues.

ARC 06 · WHY THAT STILL COSTS

The bill for a dynamic quorum

The ISR design is cheaper and more available than synchronous-to-all, and — as chapter 6 will show — cheaper to run than per-partition Raft. But "dynamic" quorum membership is not free; it introduces three sharp edges that the rest of this chapter exists to blunt:

  • The membership record has two owners with different latencies. The leader decides, locally and instantly, whether a follower still counts as in-sync (by watching its fetch requests). The controller holds the durable, cluster-wide record of ISR membership, and the leader must round-trip to it (historically a ZooKeeper write; in KRaft, an AlterPartition request) to make a shrink or expand official. Between the leader's local decision and the controller's acknowledgment there is a window where the leader's view and the metadata system's view can disagree — and code has to handle that window explicitly (§8).
  • The high watermark itself lags reality by one round trip. A follower only learns the leader's newly-advanced high watermark on its next fetch response — which means at any instant, a follower's locally recorded HW can be stale relative to what the leader has already durably committed. As you'll see in §8, trusting that stale number as a truncation point on restart is precisely the bug KIP-101 exists to fix.
  • The quorum can shrink to something durability-meaningless if you let it. Nothing stops min.insync.replicas from being set to 1 — at which point acks=all is a no-op durability-wise: the ISR can legally consist of just the leader, and "wait for all of the ISR" becomes "wait for the leader alone." This is not a bug; it is a config trap, and §8 derives exactly why.

Section 7 assembles the full architecture that manages all three: leader-tracked ISR with controller-of-record membership, a precisely-defined high watermark advancement protocol, and — the piece that took until 2016's KIP-101 to land — leader epochs as the actual mechanism for safe truncation.

THE NAME KAFKA'S OWN DOCS USE: "ISR"

Kafka never claims to implement Raft or Paxos for partition data — the docs are precise about calling this a "leader and ISR" model. It is closer in spirit to primary-backup replication with an externally-arbitrated view change: the leader is the primary, followers are backups, and "who is currently primary" is a fact stored and fenced by a separate system rather than negotiated among the replicas themselves via ballots and votes. That separation of concerns — replicate data one way, agree on leadership a totally different way — is the single most important architectural fact in this chapter, and chapter 6 is entirely about the second half of it.

ARC 08 · INTERNAL IMPLEMENTATION

ISR mechanics, the high watermark protocol, and the leader-epoch fix

Four pieces, in the order you need them: (a) what "in the ISR" precisely means and why the criterion changed from a message count to a clock; (b) exactly how the high watermark advances, one round-trip at a time; (c) the KIP-101 bug, reproduced; (d) the leader-epoch fix that replaced it.

(a) ISR membership: from a message count to a clock

Before replica.lag.time.max.ms existed, Kafka used replica.lag.max.messages: a follower fell out of the ISR if its fetch offset trailed the leader's log-end offset (LEO) by more than N messages. That criterion is a trap under bursty load: a producer that suddenly bursts 50,000 messages in one batch makes every follower momentarily trail by tens of thousands of messages — not because any follower is actually slow, but because the leader's LEO jumped instantly while followers need one more fetch round-trip to catch up. A message-count threshold cannot tell "genuinely slow replica" apart from "healthy replica measured one instant after a burst," so it would falsely shrink the ISR on every burst, exactly when you can least afford to lose durability headroom. replica.lag.time.max.ms (default 30,000 ms) replaced it with a time-based criterion: a replica stays in the ISR as long as it has caught up to the leader's LEO at some point within the last 30 seconds — bursts cause a brief, bounded lag that resolves within one or two fetch intervals, comfortably under the 30-second window, while a replica that is actually stuck (dead, GC-paused, disk-saturated) will eventually exceed it and be justly removed.

(b) Who writes the ISR, and the min.insync.replicas trap

ISR shrink and expand are both decided locally by the leader — it is the only replica watching every follower's fetch requests — and then propagated: historically the leader wrote the new ISR directly to a ZooKeeper znode (/brokers/topics/<topic>/partitions/<n>/state) and the controller picked up the change via a watch; in KRaft, the leader instead sends an AlterPartition request to the active controller, which appends the change to the metadata log and replies once it's committed. Either way, a produce request with acks=all waits for acknowledgment from every replica currently in the ISR — not the full replication factor. If the ISR has shrunk below min.insync.replicas, the leader rejects the write outright with NotEnoughReplicasException (or, if the ISR shrinks mid-flight after the local append but before followers ack, NotEnoughReplicasAfterAppendException) rather than silently degrading the durability the producer asked for.

THE TRAP: acks=all + min.insync.replicas=1

Derive it precisely. With min.insync.replicas=1, the ISR is legally allowed to shrink to just the leader itself (size 1) without the broker ever refusing writes. acks=all then means "wait for acknowledgment from every member of a set that can legally contain only the leader" — which is exactly acks=1 with extra steps. If the leader now crashes before any follower has replicated the latest records, every message the producer was told succeeded is gone, and nothing was misconfigured according to Kafka's own bookkeeping. Real durability needs both knobs working together: acks=all defines what must be true before an ack is sent; min.insync.replicas (set to at least 2, with replication factor 3) is what stops that requirement from being satisfied by a lone, soon-to-crash leader. Neither knob alone is a durability guarantee — the guarantee is the conjunction.

(c) The high watermark: advancement is a two-hop protocol

The high watermark (HW) is the offset up to which every ISR member — including the leader — has replicated. Consumers may only read offsets strictly below the HW: "committed" is defined, by construction, as "replicated to the whole current ISR." The advancement protocol is precise and worth walking exactly, because its one built-in delay is the root cause of the historical bug in part (d):

  1. Each follower issues a Fetch request carrying its own current fetch offset (implicitly its LEO).
  2. The leader records that offset for that replica, then computes a candidate new HW as the minimum LEO across every replica currently in the ISR (its own LEO included).
  3. The leader advances its local HW to that minimum immediately.
  4. The leader includes the new HW in the FetchResponse it sends back — to whichever follower happens to be fetching at that moment.
  5. A given follower only learns the leader's latest HW on its own next fetch response — there is no broadcast. A follower's locally recorded HW is therefore always at least one fetch round-trip behind the leader's true, current HW.

(d) KIP-101: the divergence bug, and leader epochs as the fix

Pre-2016, when a replica restarted (or lost a leader election and rejoined as a follower), it had no way to know exactly where its log stopped being trustworthy — so it did the seemingly-safe thing: truncate its log down to its own last known high watermark, on the theory that anything above the HW was never proven committed anyway, then resume fetching from there. Walk the divergence this actually permitted:

Before KIP-101: how "truncate to your own HW" loses committed dataSTEP-BY-STEP

The root cause, precisely stated: a follower's own locally recorded HW cannot distinguish "data I hold that was genuinely never committed" from "data I hold that the true leader already committed cluster-wide, but whose HW update I simply haven't received yet" — both look identical from inside the follower: bytes sitting above its last known HW. Truncating to a fundamentally ambiguous number is the bug.

Leader epochs remove the ambiguity by replacing a guess with an authoritative question. Every leader election increments a cluster-wide, monotonically increasing 32-bit leader epoch for that partition. Every record batch appended to the log is tagged, in its header, with the epoch of the leader that wrote it (this reuses the batch header field introduced for KIP-98's exactly-once work, chapter 8). Each broker additionally maintains a small on-disk leader-epoch cache (leader-epoch-checkpoint file) mapping each epoch it has observed to the offset at which that epoch's records began. On rejoining, instead of truncating to its own HW, a replica sends an OffsetsForLeaderEpoch request to the current leader: "for the last epoch I have fully, what is your end offset for that epoch?" The leader answers authoritatively — either the start offset of the next epoch it knows about (meaning: "your epoch ended exactly here, truncate to this point — everything after was written by a leader that never should have been trusted") or its own current LEO (meaning: "your epoch is still the latest one — you don't need to truncate at all"). The follower truncates to exactly that answer: no more, no less, and never a guess.

THE INVARIANT LEADER EPOCHS RESTORE

Two logs that share a prefix of leader epochs are now provably identical over that shared prefix — which is the log-matching property Raft is famous for, achieved here without running an election ballot inside the replication path itself. The epoch is Kafka's fencing token: exactly the mechanism a "zombie writer" problem always needs, and exactly the concept chapter 6's Raft discussion will show you again wearing a different name ("term").

The leader epoch isn't bolted on as metadata beside the log — it's a field in every record batch header (message format v2, introduced alongside KIP-98):

Read the ISR-vs-Raft-per-partition row as the chapter's real thesis: Kafka's design is more available under partial failure than a majority-quorum scheme (it can, worst case, keep accepting writes with only the leader alive), at the cost of that availability being able to silently degenerate into "no real durability" unless you set min.insync.replicas deliberately. Redpanda's bet is the opposite: refuse to ever silently degrade, at the cost of needing a live majority to accept any write at all. Neither is wrong; they are different answers to the same five requirements from §1.

ARC 10 · PERFORMANCE CHARACTERISTICS

What replication actually costs, in cycles and bytes

Because followers fetch through the exact same code path as consumers, replication reads inherit the same performance profile chapter 10's course-mate topic (log storage) derives: sequential disk layout, and — for any data still resident in the page cache — a zero-copy path via sendfile()/transferTo() straight from page cache to the follower's socket, with no trip through the JVM heap and therefore no GC pressure from replication traffic itself.

  • Network fan-out: a leader with RF=3 must egress each byte written twice — once to each follower — in addition to whatever it sends to consumers. At high partition counts this fan-out, not disk I/O, is usually the first thing to saturate a leader's NIC; it's the direct motivation for KIP-392 (follower fetching, below), which lets a nearby follower absorb consumer reads instead of forcing all consumer traffic through the leader too.
  • replica.fetch.max.bytes (default 1 MiB): caps how much data the leader returns to a single follower in one FetchResponse for a given partition, bounding a single slow follower's ability to monopolize the leader's outbound bandwidth or memory in one round-trip.
  • Replication throttling (KIP-73): leader.replication.throttled.rate and follower.replication.throttled.rate cap replication bandwidth explicitly — essential during a partition reassignment, where replication traffic competes directly with live producer/consumer traffic for the same NICs and disks.
  • HW computation is O(|ISR|) per fetch — a linear scan of the current ISR's recorded LEOs to take a minimum. Cheap in isolation, but it runs on every fetch from every follower for every partition the broker leads, which is why brokers with very high leader-partition counts feel this in aggregate CPU, not per-call latency.
  • KIP-392 (fetch from the closest replica): lets a consumer fetch from a nearby in-sync follower instead of always the leader, using client.rack/broker.rack and a pluggable replica.selector.class. It cuts cross-AZ egress cost dramatically — but note the honest subtlety: a follower's own HW is, per part (b) above, always at least one round trip behind the leader's, so reading from a follower can be a hair more stale than reading from the leader. Locality is bought with a small, bounded consistency cost, not a free lunch.

ARC 11 · REAL-WORLD PRODUCTION

Scale, incidents, and the configs that actually mattered

LinkedIn: the birthplace, at trillions of messages a day

LinkedIn — where Kafka originated and where it still runs some of the largest known deployments — has publicly discussed handling well over a trillion messages a day across thousands of brokers. At that scale, the cost model in §10 stops being theoretical: LinkedIn's own engineering posts describe replication fan-out and ISR churn (brokers flapping in and out of the ISR under transient load or GC pauses) as a first-order operational concern, directly motivating the shift from message-count to time-based lag detection this chapter opens with — it wasn't an academic nicety, it was production pain.

Incident pattern 1: the min.insync.replicas=1 trap, in the wild

This is one of the most commonly rediscovered production incidents in the Kafka ecosystem, independently reported across many companies' engineering blogs and conference talks: a team runs acks=all for peace of mind, but leaves min.insync.replicas at its default of 1. Under a rolling restart or a rack outage, the ISR legitimately shrinks to just the leader — the broker keeps accepting and acking writes the entire time, because nothing is misconfigured by Kafka's own rules — and then the leader itself is the broker that goes down next. Every "successfully acked" message since the ISR shrank is gone. The postmortem in every one of these writeups is identical: min.insync.replicas must be set (commonly to 2 with RF=3) as a deliberate, explicit decision, not left at the default and assumed to be handled by acks=all alone.

Incident pattern 2: unclean elections during multi-broker outages

Several publicly documented incidents (Kafka Improvement Proposal discussions and community mailing-list postmortems around KIP-106, which flipped unclean.leader.election.enable's default from true to false in the 0.11 release) describe the same shape: a multi-broker outage or network partition takes every ISR member for a partition offline simultaneously. With unclean election enabled (the old default), the controller elects whichever replica survives and is reachable — even one far out of the ISR — to restore write availability immediately, silently truncating the log to that replica's (stale) state and discarding every record the more up-to-date, now-unreachable replicas held. The KIP-106 discussion is itself the best public record of why the community changed the default: enough operators had been surprised by silent data loss during exactly this scenario that "unavailable but correct" became the safer out-of-the-box default, correctness bar first.

Incident pattern 3: reassignment-driven replication storms

Large operators (Uber, Netflix, and Confluent's own case studies are among those that have discussed this publicly) have documented replication traffic from partition reassignments or broker replacements saturating broker NICs and starving live producer/consumer traffic — the direct motivating case for KIP-73's replication quotas (leader.replication.throttled.rate / follower.replication.throttled.rate), covered in §10, which exist specifically so that "rebalance the cluster" and "serve production traffic" don't have to compete unthrottled for the same wire.

First, the ISR shrink decision — simplified from the real Partition.scala but faithful to its structure and naming:

ScalaPartition.scala — maybeShrinkIsr(), the time-based criterion
def maybeShrinkIsr(): Unit = {
  val now = time.milliseconds()

  // A replica stays in the ISR as long as it caught up to the leader's
  // LEO at some point within replicaLagTimeMaxMs — NOT a message count.
  val laggingReplicas = remoteReplicas.filter { replica =>
    val caughtUpRecently = (now - replica.lastCaughtUpTimeMs) <= replicaLagTimeMaxMs
    !caughtUpRecently
  }

  if (laggingReplicas.nonEmpty) {
    val newIsr = inSyncReplicaIds -- laggingReplicas.map(_.brokerId)
    // Local decision is instant; the durable record needs the controller —
    // this call is exactly the propagation-latency edge from §6.
    alterIsr(newIsr, "replica(s) exceeded replica.lag.time.max.ms")
  }
}

Next, HW advancement — the exact protocol from §8(c), including the round-trip that KIP-101 had to work around:

ScalaPartition.scala — maybeIncrementLeaderHW()
def maybeIncrementLeaderHW(leaderLog: UnifiedLog): Boolean = {
  // The minimum LEO across every replica CURRENTLY in the ISR —
  // this is the entire definition of "committed" in Kafka.
  val newHighWatermark = remoteReplicasMap.values
    .filter(r => inSyncReplicaIds.contains(r.brokerId))
    .map(_.logEndOffsetMetadata)
    .fold(leaderLog.logEndOffsetMetadata)(LogOffsetMetadata.min)

  if (newHighWatermark.messageOffset > leaderLog.highWatermark) {
    leaderLog.updateHighWatermark(newHighWatermark)
    // NOTE: this value only reaches a given follower on ITS next
    // FetchResponse — there is no broadcast. That one-hop delay is
    // exactly what made "truncate to my own HW" unsafe pre-KIP-101.
    true
  } else false
}

And finally, the fix itself: truncation via an authoritative question instead of a locally-remembered guess:

ScalaReplicaFetcherThread.scala — truncate-to-epoch, replacing truncate-to-HW
def truncateToEpochEndOffset(): Unit = {
  // Ask the CURRENT leader, not my own memory, where my last known
  // epoch actually ends.
  val myLastEpoch = epochCache.latestEpoch()
  val response   = leaderEndpoint.offsetsForLeaderEpoch(topicPartition, myLastEpoch)

  // Two possible authoritative answers:
  //  (a) "your epoch is still current" → response.endOffset == my own LEO → no truncation
  //  (b) "your epoch ended here"      → truncate to EXACTLY that offset, no guessing
  if (response.endOffset < log.logEndOffset) {
    log.truncateTo(response.endOffset)
    log.info(s"Truncated to offset ${response.endOffset} using leader epoch $myLastEpoch, " +
             "not the (possibly stale) high watermark")
  }
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Never let a replica truncate based on its own stale knowledge. The HW-based approach failed precisely because it asked "what do I remember?" instead of "what does the authority say?" — the epoch approach always asks the current leader directly. 2. Tag data with provenance, not just position. The leader epoch travels with the bytes (in the batch header) rather than living only in leader election metadata — so any replica, at any time, can answer "which leader wrote this" without an extra round trip for old data. 3. Reuse the fetch code path for the truncation query too. OffsetsForLeaderEpoch is a small, dedicated request type, but it's issued by the same ReplicaFetcherThread that issues ordinary Fetch requests — one thread, one connection, one retry/backoff story, for both jobs.
