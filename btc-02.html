Owning bitcoin is knowing a 256-bit integer. Everything else — the public key, the address, the twelve-word backup phrase — is a deterministic, publicly-auditable transformation of that one number, chosen so that anyone can verify a signature, nobody can forge one, and a human can transcribe the result without a typo silently destroying their money. ARC 01 · THE PROBLEM

Proving ownership with no registry and no identity

A bank account is a row in a database, tied to a legal identity, adjudicated by an institution that can freeze it. Bitcoin's ledger (chapters 6–8) records something much thinner: an output worth X BTC can be spent by whoever satisfies condition C. There is no name field, no identity check, no customer service line. So "ownership" has to be reducible to a fact that is purely mathematical — checkable by any stranger running open-source software, with no coordination and no trusted third party.

Unpack "prove you own this output" into requirements and you get a specification for public-key cryptography, arrived at independently of Bitcoin decades earlier:

  • One-wayness. You need a secret only you know, and a derived public value anyone can see, such that computing the public value from the secret is cheap but the reverse is computationally infeasible.
  • Unforgeability on demand. Given only the public value, nobody should be able to produce a valid proof (a signature) over a message they don't control (a transaction spending your coins) — not even after seeing many of your past proofs.
  • No prior contact. A stranger must be able to send you money having never met you, using only a string you published once. Diffie–Hellman's 1976 insight — that two parties can establish something secret using only public exchanges — is the conceptual ancestor of this requirement.
  • Compact, human-transcribable text. The public value has to survive being typed, read aloud, printed on paper, and put in a QR code — which means it needs to be short, and it needs some built-in way to catch the transcription errors humans inevitably make.

The first three requirements are satisfied by a digital signature scheme: a private key, a public key, and a signing/verifying pair of functions. The fourth requirement is not automatically satisfied by the public key itself — and getting there is most of this chapter.

WHY THIS MATTERS FOR THE NEXT 14 CHAPTERS

Every later security property in this course reduces to one sentence: can you produce a valid signature for this public key? Script (chapter 4) is largely a language for expressing which public keys must sign. Signature hashing (chapter 5) defines exactly what gets signed. The UTXO set (chapter 6) is a table of spending conditions, almost always "a signature from this key." Get comfortable with the private-key-to-address pipeline now; you will reference it in every chapter that follows.

DEEP CONTEXT · WHY secp256k1, NOT A NIST CURVE?

Every parameter of secp256k1 (the field prime, the curve coefficients, the base point) is derived by a short, published, deterministic procedure — a "nothing up my sleeve" construction. NIST's P-256 and siblings, by contrast, are seeded by unpublished random-looking constants handed down from NSA-influenced standardization in the late 1990s — not proven weak, but after the 2007–2013 Dual_EC_DRBG revelations (a NIST-standardized random number generator later shown to likely contain an NSA backdoor), the entire cryptographic community treats unexplained NIST constants as a legitimate, if unproven, risk. Satoshi's choice of a Certicom-specified, royalty-free, rigidly-derived curve was arguably the more conservative decision, not the more exotic one — even though it looked obscure in 2008.

ARC 03 · NAIVE SOLUTION

Attempt #1: your address is just your public key

Derive it honestly. Section 1 established that you need a private/public keypair. The simplest possible design stops right there: publish the public key itself as the "address."

    pub  = scalar_multiply(priv, G)    # a point on secp256k1

This is not a joke architecture — it is exactly what Bitcoin shipped in 2009. The genesis block's 50 BTC coinbase output and the famous first transaction to Hal Finney in block 170 both pay to a raw P2PK public key, not a hashed address. It satisfies every requirement from §1: the key pair gives one-wayness and unforgeability, and a stranger really can send funds to a public key they've only seen once.

WHAT THIS GETS RIGHT

No hashing, no encoding scheme, no checksum machinery — just curve arithmetic. It is the smallest possible system that satisfies "prove ownership without a registry." Everything this chapter adds on top exists to fix a specific, quantifiable failure of this version — not to make it more secure against forgery, which it already resists as well as any later design.

ARC 04 · WHY IT FAILS

A raw public key has zero error detection — quantified

Publishing a raw public key as your "address" fails for reasons that have nothing to do with cryptographic strength and everything to do with being a string a human has to move around correctly.

  • It's long. An uncompressed public key is 65 bytes (130 hex characters); even compressed, 33 bytes (66 hex characters). Compare a phone number or an IBAN — this is 3–5× longer than anything humans routinely transcribe correctly by hand.
  • It has no error detection at all. A raw hex string is pure entropy — every character carries information, so there is no redundancy to check against. Flip one nibble while copying and you get a different, equally well-formed-looking 33-byte string.
  • The failure is silent and total. A point (x, y) is only a valid public key if y² ≡ x³+7 (mod p) — but for a compressedcompletely valid-looking, just one nobody holds the private key for. The funds are not merely delayed — they are gone, mathematically, forever.
THE NUMBERS

With zero bits of the 264-bit (compressed pubkey) address spent on error detection, the probability that a random single-character transcription error is caught before the transaction broadcasts is exactly 0% — the software has no way to distinguish "a key nobody controls" from "a key its owner is about to receive money on." Compare that to the checksum this chapter builds in §5: a 4-byte (32-bit) checksum rejects a corrupted address with probability 1 − 2⁻³² ≈ 99.99999998%. That gap — zero versus a 32-bit guarantee — is the entire justification for every byte Base58Check and Bech32 add on top of the raw key.

There is a second, subtler cost: publishing the public key before you ever spend exposes it to any future attack on the discrete-log problem the moment you receive funds, not just the moment you spend them. Hashing the key first (§5) buys a delay — the public key stays hidden until the instant of spending — which matters if a large quantum computer capable of running Shor's algorithm ever exists (a scenario this course treats as a real, if distant, engineering consideration, not hype). Both problems point the same direction: don't publish the raw key — hash it, and wrap the hash in something that can catch a typo.

ARC 06 · WHY THAT STILL HURTS

Base58Check ships in 2009 — and creates a new problem

Base58Check (built in §5) fixes the catastrophic zero-error-detection failure from §4. It is not, however, free, and living with it for eight years before Bech32 (§8d) is instructive:

  • Detection, not correction. A failed checksum tells you the address is wrong — it cannot tell you what the correct address was. The user has to go back to the source and re-copy, same as a parity bit versus an error-correcting code.
  • Mixed case is hostile to QR codes and voice. Base58's 58-symbol alphabet needs both upper and lowercase letters plus digits, which forces QR encoders into the denser, less efficient "byte mode" instead of the "alphanumeric mode" a case-insensitive, digit-plus-uppercase scheme could use — and it makes reading an address aloud over the phone genuinely error-prone ("was that a capital I or lowercase l?" — even with 0/O/I/l excluded, other confusable pairs across fonts remain).
  • One address, one use, if you care about privacy. Nothing stops you from reusing a Base58Check address for every payment you receive — but every reuse links those payments together on a fully public ledger. Privacy-conscious usage means a new address per invoice, which means a wallet now manages not one key but potentially thousands.
THE NEW PROBLEM: KEY MANAGEMENT AT SCALE

If every incoming payment wants its own fresh keypair, a wallet used for a year of typical activity might hold hundreds of independent, uncorrelated 256-bit secrets. Back up the wallet file today, receive fifty more payments to fifty new keys tomorrow, and that backup is now stale — restoring from it loses every key generated after the backup was taken. Random-per-address key generation and privacy-preserving usage are in direct tension unless there's a way to regenerate the same sequence of keys from one fixed, backed-up secret. That requirement — deterministic, regenerable key sequences — is exactly what BIP32 hierarchical deterministic (HD) wallets solve, and it's the final piece of the architecture.

WHAT THE MNEMONIC ACTUALLY ENCODES

A common misconception: the twelve words are the seed. They are not. The mnemonic encodes the entropy (plus a small checksum) — the 512-bit seed is derived from the mnemonic text via PBKDF2-HMAC-SHA512 with 2048 iterations (§8e). This has a sharp practical consequence: adding an optional passphrase (sometimes called the "25th word") changes the seed — and therefore every derived key and address — without changing the mnemonic at all. The same twelve words with and without a passphrase are two completely unrelated wallets, which is both a deniability feature and a well-documented way to "lose" funds by forgetting a passphrase was ever set.

ARC 08 · INTERNAL IMPLEMENTATION

The algorithms, exactly — curve math, checksums, HD derivation

Everything in §5 and §7 reduces to five algorithms. This section derives each one precisely enough to reimplement from scratch — which is exactly what this chapter's JavaScript does.

(a) secp256k1: the curve, the generator, and double-and-add

The curve is y² = x³ + 7 over the finite field of integers modulo the prime p = 2²⁵⁶ − 2³² − 977. Its order — the size of the cyclic group generated by the base point G — is a 256-bit prime n very close to but not equal to p (Hasse's theorem bounds how far a curve's point count can be from p+1). A private key is any integer d with 1 ≤ d ≤ n−1; the public key is the point Q = d·G, computed not by adding G to itself d times (d can be up to 2²⁵⁶) but by double-and-add: process the bits of d from least to most significant, doubling an accumulator point every bit and adding the current power-of-two multiple of G whenever that bit is 1 — the same trick as fast exponentiation, giving O(log d) point operations instead of O(d).

Compression exploits a property of the curve equation: for any valid x, there are exactly two y values, and they are negatives of each other mod p (y and p−y) — one always even, one always odd, because p is odd. So instead of storing all 32 bytes of y, storing just its parity (a single bit, packed into the prefix byte as 0x02 for even or 0x03 for odd) is enough for the decompressor to recompute the correct root via y = (y²)^((p+1)/4) mod p (valid because p ≡ 3 mod 4). Compressed keys save 32 bytes per public key reference — decisive once SegWit (chapter 12) started charging for every witness byte.

(b) HASH160: two different hash functions, deliberately

HASH160(pubkey) = RIPEMD160(SHA256(pubkey)) — 20 bytes, regardless of whether the input was a 33-byte compressed or 65-byte uncompressed key. Two distinct, independently-designed primitives are chained rather than one hash used twice, for defense in depth: a structural weakness discovered in SHA-256 alone would not automatically break RIPEMD-160, and vice versa. The combination also fixes the output at a fully quantum-symmetric-adjacent 160 bits regardless of which serialization was hashed, standardizing every address format around the same 20-byte payload.

(c) Base58Check: version byte, checksum, and the leading-zero rule

Base58Check wraps an arbitrary payload (here, the HASH160) in three layers: a leading version byte identifying what kind of payload this is (0x00 for mainnet P2PKH, 0x05 for mainnet P2SH, 0x80 for a mainnet WIF-encoded private key — chapter 3 revisits several more), a trailing 4-byte checksum — the first four bytes of SHA256(SHA256(version‖payload)) — and finally Base58 encoding of the whole thing, treating the byte string as one giant big-endian integer and repeatedly dividing by 58.

One subtlety breaks pure "treat it as a big integer" encoding: leading zero bytes don't change the integer's value (they're just zero), so naive big-integer encoding would silently drop them — and dropping bytes changes the decoded length, which is exactly the kind of corruption a checksum system is supposed to prevent. The fix: count leading zero bytes in the input and prepend that many literal "1" characters ('1' being the Base58 digit for zero) to the output — restoring the byte count on decode.

The 58-character alphabet deliberately excludes 0, O, I, and l — four glyphs that are easy to confuse with each other or with digits in many fonts. This is a usability decision, not a security requirement of the checksum; the checksum would work identically over a 62-character alphabet. It costs a slightly less dense encoding (log₂58 ≈ 5.858 bits/character versus log₂62 ≈ 5.954) in exchange for fewer human transcription errors — errors the checksum then catches anyway, but avoiding them in the first place is cheaper than relying on rejection-and-retry.

(d) Bech32 (BIP173) and Bech32m (BIP350): a BCH code, not just a hash

SegWit addresses (chapter 12) replaced Base58Check with an entirely different scheme built on a BCH error-detecting code instead of a cryptographic hash. Bech32 strings use a fixed 32-character alphabet (qpzry9x8gf2tvdw0s3jn54khce6mua7l), are always lowercase — case sensitivity is discarded entirely rather than merely discouraged, closing the "was that a capital I?" problem from §6 outright — and pack more densely into a QR code because Bech32's restricted, uniform-case character set qualifies for QR's efficient "alphanumeric" encoding mode, unlike Base58Check's mixed-case alphabet.

The checksum is 6 characters (30 bits) computed by treating the human-readable part and the data as coefficients of a polynomial over GF(32) and computing its remainder modulo a fixed generator polynomial — the BCH construction. The mathematical payoff, proven rather than empirically hoped for: the code is guaranteed to detect any error pattern touching at most 4 characters, and detects longer burst errors and most other error patterns with overwhelming probability. This is a stronger, structurally-provable guarantee than Base58Check's "1 in 2³²" probabilistic argument from a generic hash checksum.

Bech32 and Bech32m are identical algorithms except for one 32-bit constant XORed into the checksum at the end: Bech32 uses 1, Bech32m uses 0x2bc830a3. The reason for the split, discovered by Pieter Wuille in 2019: Bech32's constant made it possible to take a valid checksummed string and, in specific circumstances, extend it with extra zero-value characters while the checksum remained valid. This was harmless for witness version 0 (SegWit v0 programs are always exactly 20 or 32 bytes — a fixed length rules out the exploit), but witness version 1+ (Taproot, chapter 13, and any future upgrade) permits variable-length programs, where the flaw could let a corrupted or maliciously modified address pass validation. BIP350 changed the constant for any witness version ≥ 1, and by convention wallets must reject a v0 address checksummed as Bech32m or a v1+ address checksummed as plain Bech32 — the encoding itself now signals which witness-version family it belongs to.

(e) BIP32 child key derivation: hardened vs. non-hardened

Both derivation modes compute I = HMAC-SHA512(chainCode, data), split the 64-byte result into I_L (left 32 bytes) and I_R (right 32 bytes), then set child_key = (I_L + parent_key) mod n and child_chainCode = I_R. The only difference is what goes into data:

  • Hardened (child index ≥ 2³¹, written with a trailing ', e.g. 0'): data = 0x00 ‖ parent_private_key ‖ index. Deriving the child requires the parent's private key.
  • Non-hardened (index < 2³¹): data = parent_public_key(compressed) ‖ index. Deriving the child needs only the parent's public key — which is exactly what makes watch-only wallets possible: hand a service the xpub (public key + chain code) and it can compute every non-hardened descendant address without ever touching a private key.

WHY THE LEAK IS ALGEBRA, NOT A BUG

For non-hardened derivation, I_L is a public function of the parent's public key, the chain code, and the index — an attacker holding the xpub can compute it unaided. If that same attacker ever obtains any one child private key k_child (via a signing bug, a compromised co-signer, a side channel — anything), they recover the parent private key directly: parent_private_key = (k_child − I_L) mod n. No cryptographic assumption is broken; it's the exact inverse of the derivation formula, computable because every input except the parent's private key was already public. Hardened derivation blocks this by putting the parent's private key inside the HMAC input for I_L, so an attacker with only the xpub can never compute I_L in the first place. This single algebraic fact is why every standard derivation path (§9, BIP44/49/84/86) hardens the purpose, coin type, and account levels, and lets only the change and address-index levels go non-hardened.

ARC 09 · TRADEOFFS

Five ways to encode the same 20 bytes

Every address format on mainnet ultimately commits to the same thing — a HASH160 (or, for Taproot, a tweaked 32-byte public key). The formats differ only in how that commitment is wrapped for humans and for Script:

A second, orthogonal tradeoff sits inside the HD tree itself: hardened vs. non-hardened derivation, and random-per-address keys vs. one HD seed. Neither trades away cryptographic strength — a BIP32-derived child key is exactly as strong as an independently-generated one, since HMAC-SHA512 doesn't reduce entropy. What changes is operational risk: non-hardened branches gain watch-only capability at the cost of the xpub-leak hazard from §8e; independent random keys avoid that hazard entirely but multiply the backup burden by the number of addresses ever used.

ADDRESS REUSE AND THE GAP LIMIT

Reusing an address for multiple payments is free in every technical sense and expensive in exactly one: privacy. Every transaction touching the same address is trivially linkable on a fully public ledger, turning "who paid this merchant" into "how much does this merchant make in total, and from which other addresses." The standard mitigation — a fresh address per invoice — creates a recovery problem: a wallet restoring from a seed doesn't know in advance how many addresses were ever used, so it scans sequential indices looking for on-chain activity and stops after a run of unused addresses called the gap limit (BIP44 recommends 20). Receive a payment to an address more than 20 indices past the last used one — say, by generating addresses offline in a batch — and a naive restore can miss it entirely, a real, repeatedly reported cause of "my wallet lost funds" support tickets that is actually a scanning-depth misconfiguration, not a cryptographic loss.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

How hard is it to guess a key — and what's actually being attacked

Three distinct hardness assumptions stack up in this chapter's pipeline, and conflating them is a common mistake:

  • ECDLP on secp256k1 — effectively 128-bit security. The best known generic attack against the elliptic curve discrete log problem is Pollard's rho, which costs roughly √n group operations for a curve of order n. With n ≈ 2²⁵⁶, that's ≈ 2¹²⁸ operations — the same order of magnitude as brute-forcing a 128-bit symmetric key, and the actual security level of every Bitcoin private key regardless of its full 256 bits of nominal size.
  • HASH160 preimage resistance — nominally 2¹⁶⁰, practically irrelevant on its own. Finding any input that hashes to a given 160-bit HASH160 costs ≈2¹⁶⁰ by brute force — but that input also has to be a valid serialized public key you know the discrete log of to spend the funds, which pulls the real security of a P2PKH output back down to the weaker 2¹²⁸ ECDLP bound, not the stronger-looking 2¹⁶⁰ hash bound. The hash step buys compactness and a delay in exposing the public key — not extra keyspace.
  • BIP39 checksum strength scales with word count. A 12-word mnemonic carries 4 checksum bits: a mistyped word has a 1-in-16 chance of accidentally landing on a still-valid checksum. A 24-word mnemonic carries 8 checksum bits — a 1-in-256 chance of a typo slipping through undetected, a meaningfully stronger guarantee for the same reason a longer Base58Check/Bech32 checksum would be stronger.

None of these numbers are attacked by brute force in practice — every real-world theft in §11 came from a weakness in randomness, not in the mathematics. The chart below is a sanity check on scale, not a security roadmap:

A COMPARISON THAT ONLY WORKS AS INTUITION

Bitcoin's entire mining network (chapter 9) performs SHA-256 hashing at roughly 10²⁰–10²¹ hashes/second as of the mid-2020s. Even granting an ECDLP-breaking attacker that same raw operation rate — which Pollard's rho does not actually let you do with mining hardware, since it needs a different, non-parallelizable-in-the-same-way computation — exhausting a 128-bit keyspace would still take longer than the age of the universe by many orders of magnitude. Treat this only as an intuition pump for "how big is 2¹²⁸," never as a literal security proof; the chart's y-axis makes the gap visually honest.

ARC 11 · REAL-WORLD INCIDENTS

The math held; the randomness didn't

Incident 1: Android SecureRandom nonce collisions (2013)

ECDSA signing needs a fresh, secret, unpredictable per-signature nonce k. In 2013, a bug in certain Android versions' SecureRandom implementation caused some apps — including several Bitcoin wallets — to generate ECDSA nonces with far less entropy than intended, and in some cases the identical k across two different signatures from the same key. Given two signatures (r, s₁) and (r, s₂) over messages with hashes z₁ and z₂ that share the same r (a direct function of k alone), the private key falls out of pure algebra:

mathnonce-reuse key recovery
k    = (z1 - z2) / (s1 - s2)  mod n
priv = (s1*k - z1) / r        mod n

Attackers wrote scanners that watched the blockchain for duplicate r values across different transactions and drained affected wallets, often within minutes of a vulnerable signature appearing on-chain. This is precisely why BIP32 and modern wallets increasingly use RFC 6979 deterministic nonces — deriving k from an HMAC of the private key and the message hash, removing the OS random number generator from the nonce-generation path entirely (it is still required, unavoidably, for generating the private key itself).

Incident 2: Sony PlayStation 3 static-nonce signing (2010)

Not Bitcoin, but the canonical prior art for the same bug class: Sony's PS3 firmware signing used the identical nonce k for every firmware signature, rather than merely reusing it across two signatures. The fail0verflow team needed only two different signed firmware images to recover Sony's private signing key outright — the same algebra as above, made even easier because k never changed at all. The lesson that took three more years to reach some Bitcoin wallet developers had already been demonstrated in public.

Incident 3: Brainwallets — the fastest sweep in cryptography

A "brainwallet" derives a private key directly from a memorized passphrase — typically priv = SHA256(passphrase) — trading a random 256-bit secret for something a human can remember. Human-chosen passphrases carry nowhere near 256 bits of entropy; bots continuously computed SHA-256 over dictionaries, song lyrics, and common phrases and monitored the resulting addresses. A 2015 academic study (Vasek, Bonneau, Castellucci, Keith & Moore, "The Bitcoin Brain Drain") found that funds sent to brainwallet addresses were, overwhelmingly, swept by automated crackers — frequently within seconds of funding, long before the legitimate owner could spend them.

Incident 4: xpub exposure enabling parent-key recovery

Several wallet vendors and exchange integrations have, over the years, exposed a customer's xpub through a watch-only balance-checking API while a separate bug, a compromised multisig co-signer, or careless key reuse elsewhere led to a single non-hardened child private key leaking. The combination — public xpub, one private leaf — is exactly the algebra demonstrated live in §8e, and it is the concrete, real-world reason every modern wallet hardens the account level of its derivation path by default rather than leaving that decision to the user.

Incident 5: "Milk Sad" — CVE-2023-39910 (August 2023)

The libbitcoin-explorer command-line tool generated BIP39 entropy using a Mersenne Twister PRNG seeded with only a 32-bit value, instead of a cryptographically secure random source. A 32-bit seed space is exhaustively searchable — first in minutes, later optimized to seconds — meaning every wallet ever created with that tool's default seeding was retroactively crackable regardless of how correctly every downstream step (BIP39 word encoding, PBKDF2, BIP32 derivation, Base58Check/Bech32 address encoding) was implemented. A research group calling itself "Milk Sad" responsibly disclosed the flaw and worked to identify and warn holders of at-risk funds. Every cryptographic primitive downstream of the entropy source was textbook-correct; the bug was entirely upstream of all of it.

void CKey::MakeNewKey(bool fCompressed)
{
    do {
        GetStrongRandBytes(keydata);            // OS CSPRNG — the ONLY step
    } while (!secp256k1_ec_seckey_verify(ctx, keydata.data()));
                                              // reject 0 and values >= curve order n

CPubKey CKey::GetPubKey() const
{
    secp256k1_pubkey pubkey_i;
    secp256k1_ec_pubkey_create(secp256k1_context_sign, &pubkey_i, begin());
    size_t publen = CPubKey::SIZE;
    secp256k1_ec_pubkey_serialize(secp256k1_context_sign, pubkey.begin(), &publen,
        &pubkey_i, fCompressed ? SECP256K1_EC_COMPRESSED : SECP256K1_EC_UNCOMPRESSED);
    return pubkey;
}

Base58Check, showing the exact leading-zero handling this chapter derived in §8c:

C++base58.cpp — EncodeBase58Check()
std::string EncodeBase58Check(const std::vector<unsigned char>& input)
{
    // version byte is already part of `input` by the time this is called
    std::vector<unsigned char> vch = input;
    uint256 hash = Hash(vch);                    // SHA256(SHA256(vch)) — double hash
    vch.insert(vch.end(), (unsigned char*)&hash, (unsigned char*)&hash + 4);
    return EncodeBase58(vch);                // leading 0x00 bytes -> leading '1' chars, inside here
}

Bech32/Bech32m, showing where the two algorithms diverge — one constant:

C++bech32.cpp — checksum constant selection
constexpr uint64_t M = 0x2bc830a3;   // BIP350 bech32m constant

uint64_t PolyMod(const data& values); // same generator polynomial for both

std::vector<int> CreateChecksum(Encoding encoding, const std::string& hrp, const data& values)
{
    uint64_t plm = PolyMod(cat(HrpExpand(hrp), values, {0,0,0,0,0,0}));
    plm ^= (encoding == Encoding::BECH32M ? M : 1);   // <<< the entire BIP173/BIP350 diff
    return ExtractBits(plm);
}
WHY BITCOIN CORE BUNDLES ITS OWN secp256k1 LIBRARY

Early Bitcoin Core relied on OpenSSL for ECDSA verification — a serious consensus hazard, because OpenSSL's signature parsing was not guaranteed bit-for-bit identical across versions and platforms (it tolerated non-strictly-DER-encoded signatures inconsistently). Two nodes running different OpenSSL versions could legitimately disagree about whether a signature was valid, which is precisely the kind of divergence that can split a consensus network. Bitcoin Core migrated to its own purpose-built libsecp256k1, whose entire design goal is fully specified, side-channel-resistant, bit-for-bit deterministic validation — trading "reuse a general-purpose crypto library" for "own every consensus-critical bit of behavior," and picking up a roughly 5–7× signature-verification speedup from curve-specific optimizations (the endomorphism trick available specifically because secp256k1 has j-invariant 0) as a side benefit.
