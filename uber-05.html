UBER ENGINEERING INTERNALS · CHAPTER 05

ETA & Routing:
From a Map Dot to a Real Road

Chapter 4's entire cost function leaned on one unexamined number: "predicted ETA between a driver and a rider." This chapter opens that box. A GPS point is not a location on a road — it's a noisy estimate near one. And a road network is not a plane you can measure with a ruler — it's a graph with one-way streets, bridges, and a finite number of ways across a river. Getting from "two dots on a map" to "a trustworthy number of seconds" requires two real algorithmic problems, solved at a speed dispatch can actually afford.

ARC 01 · THE PROBLEM

Two different problems hiding inside one word: "ETA"

Every chapter so far has quietly used the phrase "predicted ETA" as if it were a single lookup. It is actually two distinct, hard problems stacked on top of each other, and conflating them is where naive implementations go wrong first.

  • Problem 1 — map matching. A phone's GPS reports a noisy point: accurate to maybe 5–20 meters under good conditions, far worse near tall buildings ("urban canyon" multipath reflection) or under tree cover. Before you can ask "what's the fastest route from here," you must answer a prior question: which road segment is this vehicle actually on? A raw GPS point 8 meters from a highway is ambiguous — it could be on the highway, or on a frontage road running parallel to it, and those two answers imply very different valid routes and speeds.
  • Problem 2 — shortest path over a graph, with real-world weights. Once you know which road segment a vehicle is on, "closest" or "fastest" has to be computed over the actual road network — a graph of intersections and street segments, with one-way restrictions, turn penalties, and speed limits — not over open space. And the weight on each edge should reflect current conditions, not a fixed distance: a road that takes 40 seconds to cross at 2am can take 4 minutes during rush hour.
WHY CHAPTER 4 COULDN'T AFFORD TO SKIP THIS

Recall chapter 4's cost function: cost(rider, driver) = ETA_seconds(...). Every claim chapter 4 made about batched assignment beating greedy depended on that ETA being a trustworthy measure of real travel time — if it were secretly straight-line distance, the "optimal" assignment computed by an exact solver would just be optimally wrong. This chapter is what makes chapter 4's central assumption actually true in a real system, and it has to do so fast enough that computing it for every candidate edge in a dispatch batch doesn't itself become the bottleneck.

ARC 03 · NAIVE SOLUTION

Attempt #1: straight-line distance, and plain Dijkstra as the "real" fallback

Two naive attempts, worth separating because they fail differently.

Naive attempt 1a: straight-line distance as ETA

pseudocodenaive_eta.js — the strawman
function estimateETA(from, to) {
  const straightLineKm = haversine(from, to);
  const assumedSpeedKmh = 30;              // a single, city-wide constant
  return (straightLineKm / assumedSpeedKmh) * 3600;   // seconds
}

This is the metric chapter 4 warned about. It's cheap — O(1), no graph, no lookup — and it's wrong in exactly the systematic way that matters: it can't see rivers, highways, one-way streets, or traffic, so it's wrong hardest precisely where getting it right would matter most.

Naive attempt 1b: plain Dijkstra over the full road graph, every query

The "obviously correct" fix: model the city as a graph (intersections as nodes, street segments as weighted edges) and run Dijkstra's algorithm from the driver's node, expanding outward until the rider's node is reached. This is genuinely correct — it will find the true shortest path by construction — and it is the right first instinct once you know straight-line distance is wrong. Watch what happens when you have to run it thousands of times per second.

ARC 04 · WHY IT FAILS

Correct is not the same as fast enough

Dijkstra's algorithm from a source node, run to completion (or until the target is popped from the priority queue), visits nodes in increasing order of distance from the source — its worst-case complexity is O((V + E) log V) with a binary-heap priority queue, where V is the number of intersections and E the number of street segments in the graph being searched. On a real city road graph, that's not an abstract cost:

  • City-scale graphs are large. A single dense metro area's drivable road network commonly has on the order of hundreds of thousands to low millions of nodes and a similar or larger number of edges. Even at O((V+E) log V), that's real, non-trivial work per query — milliseconds to tens of milliseconds depending on how far apart the two points are, not microseconds.
  • You don't need one query — you need thousands per second. Chapter 4's candidate generation needs an ETA for every plausible rider×driver pair in every dispatch batch, across every active city, continuously. Multiply a per-query cost that's already measured in milliseconds by that volume, and plain per-query Dijkstra becomes the dominant cost of the entire dispatch pipeline — exactly the bottleneck chapter 4's §6 warned candidate generation could become if routing queries weren't cheap.
  • Far-apart queries are the worst case, and they're common. Dijkstra's search frontier grows roughly with the area covered — a query between two points 15 km apart explores dramatically more of the graph than one between two points 500 m apart, so the naive approach's cost is least predictable exactly when demand is spread out (a driver on the edge of a service area, an airport pickup) rather than when it's dense.
THE NUMBERS

Treat a mid-size city graph as ~500,000 nodes and ~1.2 million edges. Even a well-implemented Dijkstra with a binary heap does work proportional to (V+E)·log(V) ≈ 1.7M × ~19 ≈ 32 million priority-queue operations in the worst case to fully settle the graph — in practice a targeted query to one destination terminates earlier, but a query between two far-apart points on a large, densely connected graph can still legitimately touch hundreds of thousands of nodes before it's done. At even a modest fraction of a millisecond per node visited, a single long-distance query measured in tens of milliseconds, repeated for every candidate pair in every dispatch batch (chapter 4), quickly dominates the whole pipeline's latency budget. Something has to be precomputed ahead of time so that queries, not the whole graph, stay cheap.

ARC 05 · BETTER SOLUTION

Map-match first, then search smarter — not harder

Two independent fixes, one for each of §1's two problems.

Fix 1: map-matching (probabilistic, not just "nearest road")

Naively snapping a GPS point to its geometrically nearest road segment fails in exactly the cases that matter: a point near a highway and a parallel frontage road is genuinely ambiguous from one point alone. The well-established public technique — described in Newson & Krumm's 2009 paper "Hidden Markov Map Matching Through Noise and Sparseness" — treats map-matching as inference over a sequence of GPS points, not a single-point lookup: each candidate road segment is a hidden state, GPS accuracy gives an emission probability (how likely is this reading given the vehicle is really on this segment), and the road graph's connectivity gives transition probabilities (how likely is a real vehicle to have moved from segment A to segment B between two readings). The most likely sequence of road segments across several GPS points, not just the closest single segment to one point, is what map-matching actually solves for.

Fix 2: precomputed shortcuts, so queries stay cheap — A* and contraction hierarchies

A* search (Hart, Nilsson & Raphael, 1968) is the first real speedup: it's Dijkstra with a heuristic that estimates remaining distance to the goal, so the search expands nodes in a direction biased toward the destination rather than uniformly outward in every direction. It helps — often substantially — but its worst-case complexity is still driven by graph size, because the heuristic only prioritizes exploration order, it doesn't reduce the graph itself.

Contraction hierarchies (Geisberger, Sanders, Schultes & Delling, 2008) take a fundamentally different approach: precompute, offline, a hierarchy of "shortcut" edges that represent the shortest path through unimportant intermediate nodes, ranked by importance (a highway interchange is far more important than a residential cul-de-sac). At query time, a bidirectional search that only needs to explore upward into more important shortcuts converges dramatically faster than a full Dijkstra over the original graph — because most of the "boring" middle of a long route was already collapsed into a handful of precomputed shortcuts long before any query happened.

A REAL, PUBLIC EXAMPLE OF THIS EXACT TECHNIQUE

OSRM (Open Source Routing Machine) is a real, publicly available open-source routing engine that implements contraction hierarchies over OpenStreetMap data, and its published benchmarks are a genuine, citable example of the speedup class this technique buys: queries answered in single-digit milliseconds on continent-scale road graphs, after an offline preprocessing pass that can take minutes to hours depending on graph size. This chapter uses OSRM as an honest, real illustration of the general technique — it is not a claim about what routing engine Uber itself runs internally, which isn't public.

ARC 06 · WHY THAT STILL HURTS

Precomputation isn't free, and roads don't hold still

  • Preprocessing cost and staleness. A contraction hierarchy is built offline against a snapshot of the road graph — new roads, closures, and construction all mean the precomputed hierarchy is stale until it's rebuilt, and rebuilding a continent-scale hierarchy is not instantaneous. A routing engine has to decide how to handle the gap between "the world changed" and "the hierarchy caught up."
  • Static shortcuts assume static weights — but traffic isn't static. The entire point of contraction hierarchies is precomputing shortest paths through unimportant nodes ahead of time — but "shortest" depends on edge weights, and if those weights are travel times that change by the hour (rush hour vs. 2am) or the minute (an accident just happened), a hierarchy built against one weight snapshot can recommend a route that is no longer actually fastest. Incorporating live, time-varying traffic into a structure engineered around precomputed static shortcuts is a genuinely hard, actively-studied systems problem — one honest answer is recomputing or partially updating hierarchies on faster cycles for the weights that change fastest, and leaning on structural shortcuts (which change rarely) plus a live traffic-weighted final pass near the query time.
  • Map-matching still costs real computation per GPS ping. Chapter 3 established that a real driver fleet generates a continuous, large-volume ping stream; every one of those pings needs a map-matching pass to keep dispatch's model of "which road segment is this driver actually on" current, which is nontrivial recurring work layered on top of chapter 3's ingestion pipeline, not a one-time cost.
  • None of this eliminates the underlying graph-search complexity class — it amortizes it. Contraction hierarchies don't make shortest-path search polynomially cheaper in a complexity-theory sense; they trade a large one-time (and periodically repeated) offline cost for a much smaller online cost per query. That's the right trade for a system answering millions of queries against a graph that changes slowly relative to query volume — but it is a trade, not a free win.
THE HONEST BOTTOM LINE

A real-time, traffic-aware, always-current shortest path over a road network the size of a metro area is a genuinely hard, still-actively-researched systems problem. Every production routing engine at this scale is making deliberate engineering tradeoffs between hierarchy freshness, traffic-data freshness, and query latency — there is no configuration that makes all three perfect simultaneously, and this chapter does not pretend otherwise.

WHY MAP-MATCHING RUNS BEFORE ROUTING, NOT INSIDE IT

A routing query needs a graph node to start from — not a raw lat/lon. Running map-matching as a distinct upstream stage, rather than folding "guess the nearest road" logic into the router itself, means the router can assume clean graph-node inputs and stay focused purely on the shortest-path problem, while map-matching can independently improve its own accuracy (better GPS noise models, more context from recent pings) without touching routing logic at all — the same separation-of-concerns instinct chapter 4 applied to its own pipeline stages.

ARC 08 · INTERNAL IMPLEMENTATION

A* over the raw graph, and what a contraction hierarchy actually buys

Three pieces: (a) A* as a concrete, implementable improvement over plain Dijkstra, (b) the contraction-hierarchy query in more mechanical detail, (c) a slider that computes the real relative search cost for both approaches on a generated grid graph, not an assumed curve.

(a) A*: Dijkstra plus a heuristic that knows where the goal is

pseudocodeastar.js — informed search
function aStar(graph, start, goal) {
  const gScore = { [start]: 0 };                       // known cost from start
  const fScore = { [start]: heuristic(start, goal) };  // gScore + estimated remaining cost
  const open = new PriorityQueue([[fScore[start], start]]);

  while (!open.isEmpty()) {
    const current = open.popMin();
    if (current === goal) return reconstructPath(current);

    for (const [neighbor, edgeWeight] of graph.edgesFrom(current)) {
      const tentativeG = gScore[current] + edgeWeight;
      if (tentativeG < (gScore[neighbor] ?? Infinity)) {
        gScore[neighbor] = tentativeG;
        // heuristic() MUST be admissible — never overestimate true remaining cost —
        // e.g. straight-line distance divided by the graph's fastest possible speed.
        fScore[neighbor] = tentativeG + heuristic(neighbor, goal);
        open.push([fScore[neighbor], neighbor]);
      }
    }
  }
  return null;   // unreachable
}

The heuristic must be admissible for A* to guarantee the true shortest path, not merely a good-looking one — straight-line distance divided by the fastest possible speed on any road is a standard, safe choice, because no real route can ever be faster than that theoretical bound.

(b) What a contraction-hierarchy query actually does at runtime

Offline, every node is assigned an importance rank and "contracted" in rank order — removed from the graph after adding shortcut edges that preserve shortest-path distances between its remaining neighbors. Online, a query runs a bidirectional search — forward from the origin, backward from the destination — where each direction is only allowed to relax edges going up in rank. The two searches meet at some high-rank node, and because most of any long route's "boring middle" was already collapsed into a few shortcuts spanning important highway-like nodes, the search touches vastly fewer nodes than a full Dijkstra over the original graph.

ARC 09 · TRADEOFFS

Four routing strategies, compared honestly

STRATEGYMECHANISMWHAT YOU GETWHAT YOU PAY
Straight-line + fixed speedHaversine distance ÷ assumed average speed O(1), free systematically wrong near rivers/highways no traffic awareness
Plain Dijkstra / A*Exact shortest-path search over the live graph, every query always exactly correct for the given weights trivially handles weight changes too slow at real query volume on large graphs
Contraction hierarchiesOffline shortcut precomputation + fast bidirectional online query orders-of-magnitude faster queries production-proven (e.g. OSRM) expensive rebuilds; stale between them awkward with fast-changing live weights

The pattern repeats from chapters 1 and 4: every strategy trades query latency against freshness and implementation complexity — none escapes the tradeoff, they just place it differently. Contraction hierarchies are the standard textbook answer for "fast queries over a slowly-changing graph"; techniques like CRP exist specifically because production routing needs the graph's topology to stay stable while its weights (live traffic) change constantly, which plain contraction hierarchies handle awkwardly.

ARC 10 · PERFORMANCE CHARACTERISTICS

The numbers behind the speedup

  • Plain Dijkstra / A*: O((V+E) log V) worst case; in practice, a single query's real cost scales with how many nodes lie within the search frontier before the target is reached — roughly proportional to the area the search has to cover, which grows with the square of query distance on a roughly planar road network.
  • Contraction hierarchies: offline preprocessing is superlinear in graph size (computing an optimal contraction order is itself a hard optimization problem approximated heuristically) but is a one-time or periodic cost; online queries commonly touch a number of nodes on the order of hundreds, largely independent of total graph size, because the search only needs to climb into a small set of high-importance shortcuts regardless of how large the underlying graph is.
  • Map-matching: per-ping cost is small and roughly constant (a local search over a handful of nearby candidate road segments plus a probability update), but it runs continuously against chapter 3's full ping volume — it's a steady-state tax, not a rare one-off.
  • What this buys chapter 4 concretely: a routing engine answering ETA queries in single-digit milliseconds, rather than tens of milliseconds, is the difference between candidate generation being a minor contributor to batch latency versus being the dominant one.

ARC 11 · REAL-WORLD INCIDENTS & CONTROVERSIES

Where routing meets reality

Pattern 1: ETA displayed to riders systematically undershooting real arrival time

Ride-hailing apps across the industry have, at various points, been the subject of user complaints and press coverage about displayed ETAs that consistently ran optimistic compared to actual arrival — riders reporting "3 minutes" turning into 8 or 10. No specific internal Uber postmortem for this is public, so this chapter does not attribute a specific cause with false precision, but the general, well-documented mechanism this class of bug follows is exactly this chapter's subject: an ETA pipeline relying on stale or under-weighted traffic data, or a routing hierarchy answering queries against pre-rush-hour weights, will produce numbers that were true when the weights were computed and false by the time the vehicle actually drives the route. The general fix — the honest answer any engineer at this scale gives — is treating live-traffic freshness as a first-class SLO on the routing pipeline, not just an accuracy nice-to-have.

Pattern 2 (well documented, general industry knowledge): map data errors and "dirt road" routing incidents

Consumer GPS-navigation history broadly (not specific to any one ride-hailing company) is full of well-known, publicly documented incidents where routing engines directed vehicles onto unsuitable roads — closed roads, private property, unpaved tracks — because the underlying map data was wrong or stale, and the shortest-path search faithfully found the "shortest" route through bad data. This is a map-data-quality problem sitting upstream of the algorithm entirely: a contraction hierarchy or A* search is only as trustworthy as the graph it's built on, and production routing engines invest heavily in map data validation and driver-reported corrections precisely because the search algorithm cannot detect that an edge in its own graph shouldn't exist.

Pattern 3 (industry-standard, illustrative): a stale hierarchy after a major road closure

No specific Uber incident of this kind is public, so this is presented as a realistic, industry-standard failure pattern rather than a documented event. A major road — a bridge, a highway segment — closes for emergency repair. Until the routing engine's underlying graph is updated and its contraction hierarchy rebuilt (not instantaneous at continent scale, per §6), queries continue returning routes through the closed segment, because the precomputed shortcuts still assume it's passable. Drivers following those routes hit the closure and have to detour manually, and ETAs for anyone routed through that shortcut become wrong until the hierarchy catches up. The standard mitigation is exactly what §6 named: keeping topology changes (road closures, new roads) on a much faster update cycle than full hierarchy rebuilds, often via smaller incremental patches or penalty overlays applied on top of the precomputed structure rather than waiting for a full recompute.

pseudocodecontraction_builder.js — offline preprocessing
function buildContractionHierarchy(graph) {
  const order = computeContractionOrder(graph);  // heuristic importance ranking
  const shortcuts = [];

  for (const node of order) {
    // For every pair of still-uncontracted neighbors u, w of `node`:
     // if the shortest path from u to w currently goes THROUGH node,
     // add a direct shortcut edge u→w carrying that path's total weight,
     // then remove `node` from the graph for future contractions.
    for (const [u, w] of neighborPairs(graph, node)) {
      if (isShortestPathThrough(graph, u, w, node)) {
        shortcuts.push({ from:u, to:w, weight: pathWeight(u, node, w), via: node });
      }
    }
    graph.contract(node);
  }
  return { originalGraph: graph, shortcuts, order };   // this IS the "contraction hierarchy"
}
pseudocodech_query.js — the fast online query
function chQuery(hierarchy, source, target) {
  // Two simultaneous Dijkstra-like searches, each only relaxing edges
   // that go UP in contraction rank — a tiny fraction of the graph's
   // total edges from any given node, because most low-rank nodes were
   // already folded into shortcuts during preprocessing.
  const fwd = upwardSearch(hierarchy, source);
  const bwd = upwardSearch(hierarchy, target, { reversed: true });

  let best = Infinity, meetNode = null;
  for (const node of fwd.settled()) {
    if (bwd.settled().has(node)) {
      const total = fwd.distTo(node) + bwd.distTo(node);
      if (total < best) { best = total; meetNode = node; }
    }
  }
  return { distance: best, path: unpackShortcuts(hierarchy, fwd, bwd, meetNode) };
}
WHY BIDIRECTIONAL, UP-ONLY SEARCH IS THE WHOLE TRICK

Restricting each direction's search to edges going up in contraction rank means the search space from any node shrinks fast — a low-importance residential street node has almost no upward edges, so the search rockets toward the handful of high-importance highway-like nodes almost immediately, rather than fanning out across every nearby side street the way plain Dijkstra would. Meeting in the middle from both directions means neither search has to reach all the way to the other endpoint — it only has to reach a shared high-rank node somewhere between them, which is precisely why query cost stays close to independent of total graph size, as §10's chart shows.
