WHATSAPP ARCHITECTURE · CHAPTER 07

The Media Pipeline:
Blobs the Server Can't Read

Chapters 3, 5, and 6 built a channel that carries kilobyte text stanzas end to end: X3DH key agreement, a Double Ratchet that mints a fresh key per message, an Erlang/OTP-descended store-and-forward relay that queues those stanzas for offline recipients, and a Noise-Pipes-secured transport underneath all of it. None of that machinery was built with a 40-megabyte video in mind, and none of it needs to change. This chapter derives, from arithmetic rather than assertion, why media has to leave that channel entirely — and exactly how a server ends up hosting gigabytes of photos and video it is cryptographically incapable of reading.

Objective 1The size-vs-fan-out arithmetic that forces every E2E messenger toward the same split architecture — ciphertext in a blob store, key in the message.
Objective 2HKDF key expansion, AES-256-CBC, and the encrypt-then-MAC construction that protects a single attachment.
Objective 3Why content-addressed, opaque blob storage lets an ordinary CDN edge-cache ciphertext it cannot decrypt.
Objective 4What genuinely still leaks — size, timing, identity — even when content never does, and why that matters at nation-state scale.
ARC 01 · THE PROBLEM

A 16 Megabyte Video Doesn't Fit Through a Keyhole Built for Text

Every mechanism established so far in this course was sized for stanzas that fit comfortably in a few kilobytes: a text message, a delivery receipt, a typing indicator, a key-exchange bundle. The Double Ratchet from chapter 3 derives a new symmetric key per message and encrypts the plaintext of that message with it. The offline queue from chapter 5 holds those encrypted stanzas, per recipient, in a store-and-forward mailbox until the recipient's device reconnects. Neither piece of infrastructure was designed against the question this chapter asks: what happens when the plaintext is a 16 megabyte video instead of a 20 byte "on my way"?

The honest answer is that nothing breaks cleanly — the machinery would technically still run. You could AES-encrypt a 16MB buffer with a Double Ratchet message key exactly as you would a text string; ratchets don't care about payload size. The failure isn't a crash, it's an economic and physical collapse across five independent axes at once. Each one alone might be tolerable. Together they are not, and understanding why requires walking through each collision explicitly rather than waving at "it wouldn't scale."

The five colliding constraints

  • Bounded per-message size in the messaging fabric. The wire protocol, the framing, and every intermediate buffer in the store-and-forward path were dimensioned around the idea that a stanza is small — typically capped in the low kilobytes at the protocol layer for line-based framing, flow control, and predictable memory accounting per connection. A single video blowing past that by three orders of magnitude doesn't just use more bandwidth; it invalidates assumptions baked into buffer pools and per-connection memory limits throughout the relay tier.
  • Offline queue storage economics. The offline mailbox exists to hold messages for a recipient who is not currently connected — a phone that is off, out of signal, or simply asleep. At the scale this course has already established (hundreds of millions of concurrent users, a meaningful fraction offline at any given moment), that mailbox is provisioned for kilobyte-scale stanzas held briefly in RAM-resident, Mnesia-style tables. Multiply the average queued-message size by 1,000x and you have not scaled a service, you have changed what class of storage system you need — spinning disk or object storage instead of memory-resident tables, with completely different latency, replication, and cost characteristics.
  • Group fan-out. This is the constraint that breaks the naive design fastest. A message to a 250-member group is not, under the Double Ratchet model established in chapter 3, one ciphertext — it is logically N independent per-recipient ciphertexts, because each pairwise ratchet has its own key schedule. At 1KB that's 250KB of total ciphertext for one group send: fine. At 16MB per recipient, one group send becomes 4 gigabytes of ciphertext the sending device must produce and the network must carry, for a single tap of the send button.
  • Mobile radio and battery reality. A phone is not a datacenter NIC. Re-encrypting and retransmitting the same 16MB payload once per group member — each with a different derived key, because Double Ratchet keys are never reused — means holding the cellular radio in a high-power transmit state repeatedly, burning battery and, in much of the world this app serves, burning metered mobile data the user pays for by the megabyte.
  • Instant preview before any download. A chat list needs to render something — a thumbnail, a duration, a file icon — the instant a media message arrives, before the recipient has chosen to download anything at all. If the only copy of that information lives inside a multi-megabyte ciphertext blob sitting in an offline queue, there is no way to produce a preview without first pulling the entire blob down, which defeats the entire point of a preview.
THE DERIVED SPLIT

Every one of those five constraints points at the same fix. The encrypted media bytes travel over an ordinary HTTPS upload to a content-addressed blob store, exactly once, regardless of how many recipients exist. The tiny symmetric key needed to decrypt those bytes travels through the existing end-to-end encrypted message channel from chapter 3 — the same per-recipient Double Ratchet stanza that used to carry an entire text message now carries a few hundred bytes: a URL, some hashes, a thumbnail, and one 32-byte key. Fan-out cost collapses back to kilobytes per recipient because the only thing actually replicated per recipient is the key and its metadata, not the media itself.

This is not a WhatsApp-specific insight to be clever about — it is the only design that survives the arithmetic above, and every major end-to-end encrypted messenger that supports rich media (Signal, iMessage in its E2E-relevant paths) converges on some variant of the same split: opaque ciphertext in a general-purpose object store, a short-lived key riding the already-encrypted control channel. The interesting engineering is entirely in how that key travels safely and how the blob store stays genuinely unable to read what it hosts — which is exactly what sections 5 through 8 derive.

ARC 03 · NAIVE SOLUTION

The Strawman: Just Make the Stanza Bigger

Before deriving the real design, it's worth taking the naive approach seriously enough to see exactly where it breaks, because every one of its failure modes is precisely what motivates a specific piece of the final architecture. The naive approach: treat the media file as if it were simply a larger text message. Encrypt the whole file with the same per-recipient Double Ratchet message key used for ordinary chat messages, and push the resulting ciphertext through the same store-and-forward relay described in chapter 5.

pseudocodenaive_media_stanza.proto — annotated
// strawman: media as an oversized text message
message NaiveStanza {
  bytes recipient_id      = 1;
  bytes ratchet_header    = 2;  // DH pubkey + counters, same as ch.3
  bytes ciphertext        = 3;  // !! entire 16MB file, AES-encrypted whole
  bytes auth_tag          = 4;
}

// sender-side, per recipient in a group of N=250:
for (recipient in group.members) {
  key = ratchet.nextSendingKey(recipient)      // fresh key, unavoidable — ch.3 invariant
  ciphertext = aesEncryptWhole(video_bytes, key)  // !! re-encrypts all 16MB, N times
  stanza = NaiveStanza{ recipient, header, ciphertext, tag }
  relay.enqueue(stanza)                        // !! 16MB object into a KB-sized mailbox
}
// total ciphertext produced and transmitted for ONE group send: 250 * 16MB = 4GB
// total time on a 1Mbps mobile uplink, sequential: ~250 * 128s ≈ 8.9 hours
// the offline queue above now holds up to 4GB of pending data for one message

Nothing here is cryptographically wrong — the Double Ratchet doesn't care whether the plaintext is 20 bytes or 20 megabytes, and encrypt-whole-then-send is a completely valid pattern for small payloads (it's exactly what ordinary text messages do today). The bug is entirely architectural: this code re-derives and re-runs the encryption N times for something that is, physically, one file, and it hands the store-and-forward relay a payload three to four orders of magnitude larger than anything it was built to hold. Section 4 quantifies exactly how bad that gets.

ARC 04 · WHY IT FAILS

The Arithmetic, Made Explicit

It's tempting to wave at "that wouldn't scale" and move on. A Staff-level review doesn't accept that — it wants the actual numbers, because the numbers are what justify every subsequent design decision in this chapter. Four independent calculations, each using conservative, round figures:

FAILURE 1 — GROUP FAN-OUT

A 16MB video sent to a 250-member group, encrypted per-recipient as the naive design requires: 16MB × 250 = 4,000MB ≈ 4GB of ciphertext produced by one sender for one send action. That 4GB isn't just transmitted once — under store-and-forward, every offline recipient's share of it (up to 16MB × count-of-offline-members) sits resident in that recipient's mailbox until they reconnect. A handful of large-group video shares, at platform scale, would multiply into petabytes of transient queued state that did not exist in the kilobyte-stanza world this infrastructure was designed for.

FAILURE 2 — QUEUE MEMORY PRESSURE AT PLATFORM SCALE

A relay tier processing on the order of 100 million messages per hour, built around mailboxes sized for single-digit-kilobyte stanzas held in RAM-resident process state (the Erlang/OTP, Mnesia-descended model from chapter 5), cannot simply let a fraction of those messages be 1,000x larger without a complete redesign of memory accounting, replication, and eviction policy for that tier. This isn't a "tune a config value" problem — it's a different storage system wearing the same protocol.

FAILURE 3 — MOBILE UPLINK TIME

16MB over a conservative 1 Mbps mobile uplink (a realistic figure for 3G-era or congested-cell conditions, which this platform explicitly had to design for in emerging markets): roughly 16 × 8 / 1 = 128 seconds per transmission. Re-run that per recipient in a 250-member group, sequentially, and the sender's device is looking at over 8 hours of continuous upload just to satisfy one group send under the naive design — and that assumes the connection never drops.

FAILURE 4 — RADIO / BATTERY COST

Cellular radios have a high-power transmit state that is expensive to enter and expensive to sustain; a phone that must hold that state continuously for hours to push out N copies of the same file will visibly drain the battery and — in markets paying per-megabyte for data — visibly drain the user's wallet, N times over for content that is, bit for bit, identical across every copy.

Put together, these four failures say something more general than "video sharing is hard": the architecture from chapters 1–6 carries an implicit assumption that per-message payload size is bounded in the low kilobytes, and media violates that assumption by three to four orders of magnitude. That assumption wasn't a bug in the earlier chapters — bounding message size was the correct call for a system whose primary job is instant text delivery at global scale. It just means media needs its own path, not a bigger version of the existing one.

ARC 06 · WHY THAT STILL COSTS

The Chosen Design Is Not Free

It's easy to present the ciphertext/key split as a clean win and move on — it solves the fan-out arithmetic decisively. But a design that only gets praised and never interrogated is a design nobody has actually operated. Five concrete costs this split introduces that chapters 1–6 never had to deal with:

  • Two systems must now stay consistent. The message-delivery infrastructure (Erlang/OTP relay, offline queues, Double Ratchet sessions) and the blob/CDN infrastructure are operationally distinct systems — different failure modes, different on-call rotations, different scaling curves — and a message referencing a blob is only meaningful if both sides agree the blob exists, is intact, and is still reachable.
  • Upload becomes a precondition of send, on the critical path. The naive design's stanza could be handed to the relay the instant the user tapped send. The split design cannot: the ciphertext blob must finish uploading and be acknowledged by the media server before the chat message itself can be composed, because the message needs the server-returned URL and hash. That's an added network round trip — sometimes several, for large files — sitting directly in the latency the user perceives between "tap send" and "message shows as sent."
  • Orphaned blobs. If the user cancels the send after the upload completes but before the message is composed, or the app crashes in that narrow window, or the recipient's message send simply fails validation, the blob store now holds ciphertext with nothing referencing it. That garbage has to be found and reclaimed eventually — an entirely new background process this architecture didn't need before.
  • Instant preview has to be solved separately. Splitting the blob out means the recipient's chat list can no longer just "peek" at the message payload for a thumbnail — the thumbnail isn't in the blob's reach without a download. This is precisely what motivates inlining a small encrypted thumbnail directly into the message payload in section 8: the preview problem doesn't go away, it gets solved with a deliberately separate mechanism.
  • A whole new geographically distributed tier. The chat-routing tier from earlier chapters can be comparatively centralized because a text stanza is small and latency-tolerant relative to a human typing speed. A blob store serving multi-megabyte video to a global user base cannot be centralized the same way without brutal download latency — it needs genuine geographic distribution and CDN edge caching, which is new infrastructure with its own consistency, invalidation, and cost model layered on top of everything chapters 1–6 already built.
THE HONEST FRAME

This design is correct, not costless. Every subsequent section either shows how a specific cost was engineered down (thumbnails, content-addressing, CDN opacity) or is upfront that the cost was accepted as the price of the alternative being strictly worse (two systems to operate, an added round trip on send).

ARC 08 · INTERNAL IMPLEMENTATION

Key Derivation, Encrypt-Then-MAC, and What the Server Actually Sees

This is the section that makes the split from section 5 rigorous. Every step below is either a documented pattern from the published Signal attachment-encryption scheme (architecturally the closest public analogue), community reverse-engineering of the WhatsApp Web protocol, or a first-principles construction where noted explicitly as reasoning rather than fact.

The eight-step pipeline

Walk the deck below once, then read the detailed rationale beneath it — the deck gives you the shape, the prose gives you the "why" a Staff interviewer will actually probe.

Why encrypt-then-MAC, specifically

Step 4 computes the HMAC over IV ‖ ciphertext — never over the plaintext. This ordering choice (encrypt-then-MAC) is the only one of the three classical compositions that lets the verifier authenticate the bytes before ever handing them to the decryption routine. Compare the alternatives directly:

  • MAC-then-encrypt (compute a MAC over the plaintext, then encrypt plaintext‖MAC together) requires decrypting first to even see the MAC, so an attacker's malformed ciphertext still gets run through the block cipher and its padding logic before anything is rejected — the classic setup for padding-oracle attacks against CBC mode.
  • Encrypt-and-MAC (MAC the plaintext, encrypt the plaintext, send both independently) avoids that specific problem but leaks information: an HMAC computed over plaintext is deterministic for identical plaintexts, which can leak equality between two attachments even without decrypting either.
  • Encrypt-then-MAC computes the authentication tag over data the attacker fully controls the shape of (the ciphertext itself), so verification is a pure function of bytes-on-the-wire with no dependency on the decryption routine at all. A corrupted or forged blob fails a constant-time HMAC comparison and the pipeline halts before a single AES block gets decrypted — closing off both padding-oracle attacks and any bug lurking in the decrypt path itself, because that path is simply never reached with attacker-controlled input.

This is why step 7 below is written as verify, then verify again, then decrypt — never the reverse. A senior engineer who gets this ordering backwards has, in effect, turned an authenticated-encryption scheme back into vanilla CBC with an easily-forged integrity check bolted on as an afterthought.

Byte-layout visualizer

HKDF-SHA256 expands the single 32-byte media key into 112 bytes of key material (a figure consistent with reverse-engineered implementations), split into four fixed-size fields regardless of media type — only the HKDF "info" string differs per type (image/video/audio/document), which cryptographically domain-separates a media key so it can never be reused for the wrong media class even by accident. The message payload stays roughly 200–400 bytes no matter the media size — it never scales with the blob. That's the entire point of the split.

Why the server can host media it cannot read

The media/blob server never possesses the media key — HKDF happens exclusively on the client, and the key travels only through the E2E message channel, which the server relays without decrypting (that's the whole premise of chapters 3 and 6). Without the key, the uploaded bytes are, to any observer at the server or CDN layer, computationally indistinguishable from random data — that's the formal security property AES-256-CBC with a properly random IV is supposed to provide, and it's the entire justification for letting a general-purpose, commercially operated CDN cache this content at all.

WHAT STILL LEAKS — BE HONEST ABOUT THIS

Opaque content is not the same thing as zero information leakage, and a Staff engineer should never let that conflation stand unchallenged in a design review. The media server, and by extension anyone who can subpoena or compromise it, still observes: exact ciphertext file size (which loosely correlates with content type and even duration for video), the declared MIME type, precise upload and download timestamps, the identity of the uploader (an authenticated client), and — because attachment URLs are typically bearer-style tokens rather than requiring a fresh proof of authorization per fetch — the identity and timing of whoever fetches a given blob, including every recipient in a large group and every device a forward reaches. None of that is content. All of it is metadata a well-resourced adversary can use for traffic analysis, social-graph inference, or simply proving two people exchanged a large file at a specific time. This is a genuine, unresolved privacy leak surface even in an architecture that gets the confidentiality of content exactly right.

Deduplicated forwarding — and its security cost

Forwarding a media message does not re-upload anything. The forwarding client already possesses the URL, the media key, and both hashes from the original message; it simply places those same fields into a new message envelope addressed to the new recipient(s) through the ordinary Double Ratchet channel. This is why forwarding a 50MB video feels instantaneous regardless of the sender's upload bandwidth — there is no upload step at all, only a small encrypted message referencing existing ciphertext.

The security consequence deserves to be stated plainly rather than glossed over: the same symmetric media key now protects that blob for an audience the original encryptor never chose and cannot control. Every recipient of every forward — potentially far removed from the original conversation — can decrypt the exact same ciphertext, indefinitely, for as long as the blob and its URL remain valid at the media server. There is no revocation mechanism once a key has been forwarded; the blob is, for practical purposes, immutable and now shared beyond the original sender's knowledge or consent. This single technical property — free, instant, N-way forwarding — is directly responsible for the misinformation-virality dynamics discussed with real incident context in section 11.

Content-addressed storage, GC, and CDN edge caching

The blob store keys objects by a hash of the ciphertext itself (naturally, since fileEncSha256 is computed anyway for integrity verification) — a classic content-addressed storage pattern. This buys two things simultaneously: implicit integrity (the address is the checksum, so any corruption is self-evident on lookup) and natural deduplication (two independent uploads of bit-identical ciphertext collide on the same address, though this happens rarely since IVs are randomly chosen per encryption and change the ciphertext even for identical plaintext). Garbage collection runs on reference counting or TTL expiry — a blob with zero referencing messages, or one that outlives a bounded retention window, becomes eligible for deletion, cleaning up exactly the orphaned-blob problem raised in section 6.

A CDN edge can safely cache these blobs precisely because they are opaque: there is no confidentiality property for the edge to violate, since it never had the key in the first place. Cache poisoning is also self-defeating against this design — a tampered cached blob simply fails the recipient's hash and MAC verification on receipt (this is exactly the "tamper URL" failure mode explored in the simulator), so an attacker gains nothing by corrupting cache contents beyond a denial-of-service against that one blob. This is also why the media/CDN tier can be far more aggressively geo-distributed than the comparatively centralized chat-routing tier from earlier chapters — there is no per-region trust boundary to reason about when the content is uniformly unreadable everywhere.

Client-side transcoding: the cost pushed onto the phone

Because the server can never see plaintext, it can never resize an image or transcode a video on the server's own CPU the way an ordinary (non-E2E) media platform would. Every bit of that work — image re-encoding to a target resolution, video transcoding to a target bitrate, thumbnail extraction — has to happen on the sending device, before encryption, using the phone's own CPU and battery. This is the direct, first-principles explanation for why default media quality was historically compressed aggressively: every megabyte NOT transcoded away is a megabyte the phone must encrypt, upload, and (multiplied across recipients' key material, though not the blob itself) that the whole pipeline must carry. The 2023 introduction of an explicit HD quality toggle (noted in the timeline in section 2) is the direct descendant of this exact tradeoff — giving users a conscious choice between the historical default (aggressive client-side compression) and a higher-fidelity but more expensive-to-produce-and-carry alternative.

Streaming playback and the CBC seeking problem

A "streamable" flag lets a recipient begin video playback before the full ciphertext blob has downloaded, typically paired with a "faststart" container layout — moving the MP4 moov atom (which holds the index the player needs) to the front of the file rather than the end, a standard video-container optimization independent of encryption. Encryption, though, adds a genuine architectural constraint here that is worth being explicit is reasoned from the mechanics of CBC mode rather than a documented implementation detail: because each ciphertext block in CBC mode is XORed with the previous ciphertext block during decryption, decrypting any given block requires having the block immediately before it. True random seeking — jumping to an arbitrary timestamp in the middle of an encrypted video — either requires decrypting sequentially from the nearest available reference point (a keyframe or chunk boundary near the seek target), or requires the encryption scheme to be chunked with an independent IV per segment specifically to support random access. This is a genuine, unavoidable tension between "CBC is simple and well-understood" and "video players expect O(1) seeking" — and it is exactly the kind of tradeoff a Staff-level design review should surface explicitly rather than assume away.

Resumable, chunked uploads over flaky mobile networks

Given the mobile-uplink math from section 4, an upload that has to restart from byte zero after every dropped connection is untenable at any real size. The client instead uploads in fixed-size chunks, with the media server acknowledging each chunk independently; on reconnect after a drop, the client resumes from the last acknowledged chunk rather than re-sending everything already confirmed. This is standard resumable-upload practice (conceptually similar to HTTP range requests or multipart upload protocols used broadly across the industry) — nothing about the encryption changes this, since chunking is a transport-layer concern applied to an already-fully-formed ciphertext blob.

Voice notes, documents, and the three root causes of size ceilings

Voice notes are commonly encoded with the Opus codec, chosen specifically for strong perceptual quality at very low bitrates — a natural fit for speech-only content where the payload is small enough that none of this chapter's fan-out arithmetic is even a concern. Documents sit at the opposite extreme: produced more often on desktop, not photographic or video content that benefits from transcoding, and historically given a much higher size ceiling (moving over time from the original ~16MB media ceiling toward limits described publicly as approaching 2GB for documents). Every size ceiling this chapter has touched — the original ~16MB image and video limit, the far larger document limit — traces back to the same three root causes derived earlier in this chapter: client memory limits (an entire file typically has to be held in memory for CBC processing and MAC computation), mobile network reality (upload and download time, and metered data cost, scale linearly with size), and blob-store economics (storage and, especially, CDN egress cost scale directly with how large a file the platform is willing to host and redistribute).

ARC 10 · PERFORMANCE CHARACTERISTICS

Where the Time and Battery Actually Go

  • Cryptographic cost — O(n) in file size. Both AES-256-CBC encryption/decryption and HMAC-SHA256 computation are linear scans over the file; on modern mobile SoCs with AES-NI-equivalent hardware acceleration this is typically bandwidth-bound rather than compute-bound, but on older/low-end Android devices (a large fraction of this platform's historical install base) software AES can be a meaningfully slower, battery-relevant cost.
  • Client memory footprint. A naive implementation holds the entire plaintext, the entire ciphertext, and possibly the entire post-decryption buffer in memory simultaneously — for a 2GB document that's a non-starter on memory-constrained devices, which is exactly why real implementations stream: encrypt/decrypt in fixed-size chunks, never materializing the whole file in RAM at once. This streaming-vs-buffer-all tradeoff is precisely the same one large-video CBC seeking runs into in section 8.
  • Round trips on the send critical path. At minimum: (1) upload ciphertext, wait for the media server's acknowledgment and hash; (2) compose and send the chat message carrying the key/URL/thumbnail through the existing channel. That's two sequential round trips before the recipient even begins downloading — added latency the naive all-in-one-stanza design (section 3) never had, traded deliberately for the fan-out win from section 4.
  • Radio/battery cost of sustained TX/RX. Uploading or downloading a large file keeps the cellular radio in a high-power state far longer than the sub-second bursts typical of text messaging — a real, measurable battery cost distinct from the CPU cost of the cryptography itself.
  • CDN cache economics diverge sharply by virality. A widely forwarded video (the mechanism from section 8) is, from the CDN's perspective, a single object requested an enormous number of times — a near-100% cache-hit workload that's cheap per-request at the edge. A private photo shared with one person is a cold, single-fetch-then-evict workload hitting origin almost every time. The same infrastructure serves both patterns, but their cost profiles are opposite ends of the CDN economics spectrum.

  • Peak message volume. WhatsApp has publicly cited tens of billions of messages processed on peak days such as New Year's Eve — a scale at which even a small percentage of messages carrying media translates into an enormous absolute volume of blob uploads, each subject to the exact fan-out and radio-cost math derived in sections 1 and 4.
  • Forwarding limits (2018–2019). Forwards were capped to five chats at a time, with an even stricter, visually distinct "highly forwarded" label applied beyond that — a policy change publicly and explicitly motivated by viral-misinformation incidents, notably a wave of mob-violence incidents in India linked to virally forwarded video content. This is the direct policy-layer response to the exact technical property described in section 8: because forwarding relays the same URL and media key with zero re-upload, the marginal cost of forwarding to another 5, or 50, or 500 chats is close to zero for the sender — which is precisely what makes runaway virality technically effortless, and precisely why it became a policy target once the human cost of that effortlessness became visible.
  • Scale after the 2014 acquisition. The service grew rapidly past 900 million and eventually into the billions of users following its acquisition, famously operated for a long stretch by an engineering team reported publicly to be on the order of dozens of engineers — a striking ratio of engineers to blast radius that underscores how much leverage a correctly chosen architecture (like the split derived in this chapter) provides: a small team cannot operate a media pipeline that requires constant per-region, per-file manual intervention at this scale.
  • Emerging-market network conditions. A large fraction of the platform's historical growth came from markets where 2G/3G-era Android devices and metered, expensive mobile data were the norm rather than the exception — real market conditions that map directly onto the aggressive default media compression and resumable-chunked-upload design discussed in section 8, and explain why those engineering choices were not optional polish but core to the product being usable at all for a huge share of its user base.

TypeScriptHkdfExpander + AesCbcHmacCipher — key derivation and encrypt-then-MAC
interface DerivedMediaKeys { iv: Buffer; cipherKey: Buffer; macKey: Buffer; refKey: Buffer; }

function expandMediaKey(mediaKey: Buffer, mediaType: MediaType): DerivedMediaKeys {
  // info string domain-separates by media class so a key can never
  // be reused across image/video/audio/document even by accident
  const info = `WhatsApp Media Keys ${mediaType}`;
  const expanded = hkdfSha256(mediaKey, null, info, 112);
  return {
    iv:        expanded.slice(0, 16),
    cipherKey: expanded.slice(16, 48),
    macKey:    expanded.slice(48, 80),
    refKey:    expanded.slice(80, 112),  // reserved: streaming/sidecar use
  };
}

function encryptThenMac(plaintext: Buffer, keys: DerivedMediaKeys): { blob: Buffer } {
  const ciphertext = aes256CbcEncrypt(plaintext, keys.cipherKey, keys.iv);
  // MAC over IV ‖ ciphertext — NEVER over the plaintext (encrypt-then-MAC, §8)
  const mac = hmacSha256(keys.macKey, Buffer.concat([keys.iv, ciphertext])).slice(0, 10);
  return { blob: Buffer.concat([ciphertext, mac]) };
}
TypeScriptMediaUploader — upload, then build the small message fields
async function sendMediaMessage(file: Buffer, mediaType: MediaType) {
  const plaintextHash = sha256(file);                       // fileSha256 — computed BEFORE encryption
  const mediaKey = randomBytes(32);
  const keys = expandMediaKey(mediaKey, mediaType);
  const { blob } = encryptThenMac(file, keys);
  const thumb = encryptThumbnail(file, keys);              // small, rides inline in the message

  // upload is on the critical path — chunked + resumable (§8, §6)
  const upload = await mediaUploader.uploadChunked(blob);
  // upload.fileEncSha256 is the SERVER's own hash of the ciphertext it stored

  // the actual chat message stays tiny — travels through the existing
  // Double-Ratchet-encrypted channel from chapter 3, unmodified
  return messageChannel.send({
    mediaKey, url: upload.url,
    fileEncSha256: upload.fileEncSha256, fileSha256: plaintextHash,
    mimeType: detectMime(file), sizeBytes: file.length,
    thumbnail: thumb,                                       // zero extra network calls to preview
  });
}
TypeScriptMediaDownloader — the ordering that matters
async function receiveMediaMessage(msg: MediaMessageFields): Promise<Buffer> {
  const blob = await httpsFetch(msg.url);                    // step 1: fetch — still just bytes, no trust yet

  // step 2: verify the SERVER-side hash first — cheap, catches wrong-URL/CDN corruption
  if (sha256(blob) !== msg.fileEncSha256) throw new Error("ciphertext hash mismatch — do not proceed");

  const keys = expandMediaKey(msg.mediaKey, msg.mediaType);
  const ciphertext = blob.slice(0, blob.length - 10);
  const mac = blob.slice(blob.length - 10);

  // step 3: verify the MAC — THIS is what proves authenticity/integrity of the CIPHERTEXT
  const expectedMac = hmacSha256(keys.macKey, Buffer.concat([keys.iv, ciphertext])).slice(0, 10);
  if (!constantTimeEqual(mac, expectedMac)) throw new Error("MAC verification failed — refusing to decrypt");
  // ^ note: we have NOT called the AES decrypt routine yet. Attacker-controlled
  // bytes never reach it unless both hash and MAC already passed.

  // step 4: only now, decrypt
  const plaintext = aes256CbcDecrypt(ciphertext, keys.cipherKey, keys.iv);

  // step 5: defense in depth — catches implementation bugs, not just malice
  if (sha256(plaintext) !== msg.fileSha256) throw new Error("plaintext hash mismatch after decrypt — should never happen");
  return plaintext;
}
WHY THE ENGINEERS CHOSE THIS

Nothing in section 8 is novel cryptography. AES-256-CBC, HMAC-SHA256, and HKDF are all decades-old, heavily analyzed, standard primitives; encrypt-then-MAC is textbook authenticated-encryption composition; content-addressed storage is a well-understood pattern from countless distributed systems before this one. That is the entire point. A Staff-level design instinct treats cryptographic novelty as a cost, not a feature — every non-standard construction is an unaudited attack surface. The interesting engineering here isn't inventing a new cipher mode, it's the boring, disciplined application of well-understood primitives to the one place where this system genuinely had no existing answer: how do you let a server host content it cannot read, and how do you let a recipient trust content it hasn't decrypted yet. Novel only where forced; boring everywhere else.
