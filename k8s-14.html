KUBERNETES INTERNALS · CHAPTER 14ADVANCED

Multi-Tenancy &
Resource Governance

A shared cluster is a shared kernel wearing a declarative API on top. This chapter is about the machinery that lets many teams — or many customers — safely pretend they each have the cluster to themselves: ResourceQuota capping what a namespace can collectively ask for, LimitRange filling in and bounding what an individual object may ask for, and PriorityClass-driven preemption deciding, with real arithmetic, exactly which lower-priority Pods must die so a higher-priority one can live. None of it is a security boundary. All of it is load-bearing.

ARC 01 · THE PROBLEM

One cluster, many strangers, one kernel underneath all of them

Every chapter before this one assumed a cluster serves one coherent workload. Real clusters don't look like that. A platform team runs one Kubernetes cluster and sells (or grants) slices of it to a dozen product teams, or a hundred external customers, each of whom believes — correctly, for their purposes, incorrectly at the kernel level — that they have a private environment. This is multi-tenancy, and it inherits every hard problem from chapter 6's control-plane discussion plus three new ones that only appear once tenants stop trusting each other:

  • Fair sharing. One tenant's Deployment shouldn't be able to consume the CPU, memory, or object count that starves everyone else's — deliberately (an abusive tenant) or accidentally (a misconfigured Job that spawns ten thousand Pods).
  • Predictable arbitration under scarcity. When the cluster genuinely runs out of room, something has to lose — and it must be the thing that matters least, decided by an explicit, auditable rule, not by whichever Pod's create request happened to land on the scheduler last.
  • Isolation the tenants can reason about. A tenant needs to know what is and isn't guaranteed to stay private, because "namespace" sounds like it should mean "sandbox," and treating it as one is a production incident waiting to happen.

That last point is worth being exact about immediately, because getting it wrong is the single most common multi-tenancy mistake this chapter exists to correct. A Namespace is an API-level partition: it scopes object names (two Pods named web can coexist in team-a and team-b), and it's the attachment point for RBAC bindings, ResourceQuota, and NetworkPolicy. It is not a kernel-level security boundary: Pods in team-a and team-b can still be scheduled onto the very same node, sharing the same kernel, the same process table, and the same physical CPU cache and memory bus, unless something below the Kubernetes API — a container runtime's namespace and cgroup configuration, a restrictive Pod Security Standard, or a sandboxed runtime like gVisor or Kata Containers — actually enforces isolation between them, mechanics this course's Container Internals companion covers in depth in its namespace and cgroup chapters. Everything else in this chapter — quota, limits, priority — governs the API object graph: who can ask for what, how much, and who wins when there isn't enough. It is real governance, and production clusters cannot run without it. It is not a substitute for the isolation question, which is a different, harder problem this chapter deliberately sets aside so the resource question gets the depth it deserves.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Chapter 13 answered "who is allowed to do this?" (authentication, RBAC, admission). This chapter answers "how much of the cluster are they allowed to consume, and who yields when two legitimate, authorized requests can't both be satisfied?" Both questions have to be answered synchronously, inside the same admission and scheduling pipeline, before an object is ever persisted or a Pod ever runs — polling and cleaning up after the fact, as §3 will show, is not fast enough to be a real answer.

DEEP CONTEXT · BORG'S SHADOW, AGAIN

Chapter 1 introduced Borg as Kubernetes' direct ancestor. Borg ran Google's shared production fleet across thousands of internal "tenants" (teams) for years before Kubernetes existed, and its published design notes are explicit that priority and quota were not optional add-ons — they were required from day one for a scheduler serving competing teams. Kubernetes shipped without a real answer to either problem in its earliest releases and spent roughly five years catching up, which is precisely why this chapter's primitives arrived piecemeal instead of as one coherent design.

ARC 03 · NAIVE SOLUTION

Attempt #1: police it after the fact, with a script

Before admission-time enforcement existed (and it's exactly what a team without it reinvents today), the obvious approach is an external policing loop: poll the API server, add up what each namespace is using, and clean up violators.

bashtenant-cop.sh — the strawman, annotated
#!/usr/bin/env bash
# Runs every 30s. Sums requested CPU per namespace from a live snapshot,
# and if a namespace is over its (hardcoded) cap, deletes its newest Pod.
while true; do
  for ns in $(kubectl get ns -o name); do
    used=$(kubectl get pods -n "$ns" -o json | jq '[.items[].spec.containers[].resources.requests.cpu] | length')
    if [ "$used" -gt 20 ]; then          # hardcoded cap, same for every namespace
      newest=$(kubectl get pods -n "$ns" --sort-by=.metadata.creationTimestamp -o name | tail -1)
      kubectl delete "$newest" -n "$ns"          # no idea if this frees enough, or too much
    fi
  done
  sleep 30
done

A companion script handles the other half of the problem — making room for something "important" — with the same blunt logic: when a Pod labeled tier=critical sits Pending, delete the oldest Pod belonging to whichever team is hardcoded lowest in a priority list, without checking whether that Pod's resources are anywhere near enough, or on the right node, or even still running.

Like chapter 9's naive controller, this is not a strawman built to be laughed at — it gets the shape of the problem right: someone must count usage, someone must decide who yields. It fails for reasons worth quantifying precisely, because they are exactly the reasons ResourceQuota and preemption are built the way they are.

ARC 04 · WHY IT FAILS

A poll-and-clean loop is a race condition wearing a cron schedule

Three independent failures, each fatal on its own for a production governance system:

  • The overshoot window is bounded only by the poll interval, and it's a wide-open race. Between two polls, the API server keeps accepting kubectl apply calls from every tenant — nothing in the naive design synchronizes with object creation, so two tenants' requests that individually look fine against the last snapshot can both be admitted even though their sum blows through the cap.
  • Victim selection is blind to how much is actually needed. Deleting "the newest Pod" has no relationship to how much CPU or memory that Pod actually holds — you might delete a 100m sidecar when 4 full cores need freeing, or delete a multi-core batch job when 100m would have sufficed and a much less disruptive victim was available.
  • It conflates two different resource behaviors. CPU is compressible: a process can be starved of CPU cycles and merely slow down. Memory is incompressible: you cannot politely ask a process to use less RSS; you can only kill it. A single hardcoded cap treats both the same way, guaranteeing it's wrong for at least one of them.
THE NUMBERS

At a poll interval T = 30s and an average admission rate of λ = 2 Pods/sec across a busy shared cluster, the expected number of Pods admitted past a quota cap before the next poll even notices is λ·T ≈ 60 Pods. During a deploy storm (λ up to 10/sec — ten teams shipping at once) that's up to 300 Pods of overshoot in one window. And convergence back to compliance is just as slow: if the cop script deletes "the newest Pod" (say it requests 250m CPU) to close a 4-core (4000m) deficit, it needs 16 delete-and-repoll cycles to close the gap — at 30s per cycle, 8 minutes of continued overcommitment while the script repeatedly guesses wrong. A real admission-time check, by contrast, has an overshoot window bounded only by optimistic-concurrency retry latency — single-digit milliseconds, not minutes, and it computes the exact deficit instead of guessing at it. §5 builds that.

ARC 05 · BETTER SOLUTION

Move enforcement into the request path, and make victim selection arithmetic

The fix has two independent halves, and it's worth keeping them separate because they solve different halves of §4's failure: (1) quota and limits move from an external poller into synchronous admission control — code that runs inside every kubectl apply, before the object is ever persisted — and (2) "who yields under scarcity" moves from a hardcoded team list into the scheduler's preemption logic, driven by an explicit numeric total order (PriorityClass.value) and real resource arithmetic. THE CLINCHING ARGUMENT: ATOMICITY, NOT SPEED

The real improvement isn't that admission control is "faster" than a cron job — it's that it's synchronous with the write it's protecting. A ResourceQuota object's status.used is read, incremented, and written back with optimistic concurrency (a resourceVersion-gated update) as part of the same request that's asking to consume more of it. Two concurrent requests racing for the last core cannot both win — one's update loses the version race, forcing a re-read of the now-current usage and a correct re-evaluation. There is no window in which the system's own bookkeeping can be observed to be wrong, which is a strictly stronger guarantee than "usually catches it within 30 seconds."

ARC 06 · WHY THAT STILL COSTS

Governing the paperwork isn't governing the hardware

Admission-time quota and priority-based preemption are correct answers to the problem they solve. They do not solve every multi-tenancy problem, and pretending they do is how "we have ResourceQuota configured" turns into a false sense of security:

  • Quota governs requests, not usage. A namespace can sit at 20% of its requests.cpu quota on paper while its Pods are genuinely starving a shared node's CPU in practice, because nothing stops a Pod from bursting far above its request up to its limit (or, with no limit set, arbitrarily far) if the node happens to have idle cycles at that instant. The quota accounting is correct and the noisy-neighbor problem is real — they're just answering different questions.
  • LimitRange only touches objects at admission time. Its default/defaultRequest fill in gaps on new objects; it never retroactively fixes Pods that are already running, and its maxLimitRequestRatio bounds how far one container can overcommit itself — it says nothing about two different namespaces' individually-compliant Pods contending for the same physical node.
  • ResourceQuota is strictly per-namespace. A "tenant" that spans several namespaces (one per environment, or per microservice — extremely common) gets no aggregate governance at all without additional tooling layered on top, because the object was designed around the namespace as the unit of accounting, not around whatever an organization happens to call a tenant.
  • PriorityClass is cluster-scoped, with no default access control. Any identity permitted to set pod.spec.priorityClassName can reference the highest-value class that exists unless an administrator has explicitly RBAC-restricted it — an opt-in fix (§8/§12 cover it), not a default.
  • Preemption can cascade. Evicting a lower-priority Pod frees resources on the node the scheduler is evaluating right now; if that Pod belongs to a Deployment, its controller immediately creates a replacement, which re-enters scheduling and — if priorities were assigned carelessly across many tiers — can itself trigger a further eviction of some other, even-lower-priority Pod, moments later.

None of these are bugs in the design — they are the honest edges of what "govern the API object graph" can promise. §7 assembles the full architecture; §10 puts numbers on the noisy-neighbor gap specifically.

NOTE THE ASYMMETRY

LimitRange and ResourceQuota run inside the write path — a rejection means the object never exists. Preemption runs after an object already exists and already failed to schedule — a decision to evict is a second, separate write (a DELETE on the victim), not a rejection of the original request. That's why quota violations surface as an immediate 403 Forbidden from kubectl apply, while an unschedulable high-priority Pod instead sits briefly Pending, triggers eviction elsewhere, and only then gets bound — a visibly slower, two-step process for a structurally different kind of decision.

  name: team-checkout-quota

  hard:
    requests.cpu: "20"              # sum of every Pod's requested CPU, cluster's real reservation
    requests.memory: 40Gi
    limits.cpu: "40"                # sum of every Pod's CPU ceiling — bounds total burst headroom
    limits.memory: 80Gi
    pods: "50"                      # object-count quota — stops Pod-spam independent of size

  matchExpressions:              # lets you cap "high-priority" consumption separately from the rest
  - operator: In
    scopeName: PriorityClass
    values: ["high-priority"]
yamllimitrange.yaml — per-object defaults and bounds
apiVersion: v1
kind: LimitRange
metadata:
  name: team-checkout-limits
  namespace: team-checkout
spec:
  limits:
  - type: Container
    default:          { cpu: 500m, memory: 512Mi }   # filled in if a container omits limits
    defaultRequest:   { cpu: 100m, memory: 128Mi }   # filled in if a container omits requests
    max:              { cpu: "4",   memory: 8Gi }     # hard ceiling — admission REJECTS above this
    min:              { cpu: 50m,  memory: 64Mi }     # hard floor
    maxLimitRequestRatio: { cpu: "4" }        # limit can be at most 4x the request — bounds overcommit

goplugin/pkg/admission/resourcequota/admission.go — the atomic increment (structure)
func (q *quotaAdmission) Admit(a admission.Attributes) error {
    for _, quota := range q.quotasFor(a.GetNamespace()) {
        if !q.evaluators.Handles(a) { continue }
        for {                                     // optimistic-concurrency retry loop
            usage := q.evaluators.Usage(a.GetObject())      // e.g. {requests.cpu: 500m, pods: 1}
            newUsed := add(quota.Status.Used, usage)
            if exceeds(newUsed, quota.Spec.Hard) {
                return admission.NewForbidden(a, fmt.Errorf("exceeded quota: %s", quota.Name))
            }
            quota.Status.Used = newUsed
            _, err := client.Update(quota)             // fails if quota's resourceVersion moved under us
            if apierrors.IsConflict(err) { continue }  // someone else won the race — re-read, re-check, retry
            return err
        }
    }
    return nil
}

ARC 09 · TRADEOFFS

Five ways to slice one cluster among strangers

"Use Namespaces + Quota + Priority" is one point on a spectrum, not the only answer. Read this as a proof by exhaustion: isolation strength and operational simplicity trade directly against each other.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What scales for free, what doesn't, and the noisy-neighbor gap

Some governance costs are structurally cheap; others are the exact edge §6 warned about, and it's worth putting a number on the difference:

  • Admission-time quota checking is O(1) per request. The plugin compares against a cached status.used counter, not a fresh scan of every Pod in the namespace — it does not get slower as a namespace accumulates objects, which is why it's safe to run on every single write.
  • The background resourcequota-controller IS O(objects in the namespace), because it periodically recomputes status.used from scratch by re-listing everything, purely to self-heal any drift (e.g. from a direct etcd write or a missed replenishment event on delete) — this is a genuine, bounded cost that scales with namespace object count, separate from the cheap per-request path.
  • Preemption's search cost is per-node, per-unschedulable-Pod. FindCandidates evaluates each infeasible node's SelectVictimsOnNode independently; on a default node capped at 110 Pods, that's bounded work per node, but a cluster running many simultaneously-unschedulable high-priority Pods (a genuine failure mode during a capacity crunch) can trigger this search repeatedly across a large fraction of a fleet sized for the 5,000-node / 150,000-Pod SLO envelope.
  • Quota governs a static declaration; the node enforces a live one. This is §6's gap again, now with a shape: the further a namespace's actual CPU usage runs above its requests (which is all quota sees) toward its limits (which the kernel enforces live, per container, every accounting period), the more a shared node's spare capacity gets contested by Pods that are each, individually, fully compliant.

ARC 11 · REAL-WORLD PRODUCTION

Three incident patterns you will eventually meet

Incident 1: Priority inflation

A platform team ships a shared cluster with three PriorityClasses — low, default, high — but never restricts who can reference high. Within weeks, every team's Helm chart sets priorityClassName: high "just to be safe." Preemption logic keeps working exactly as designed — it just no longer means anything, because everyone is now tied at the top of the order, and ties are broken by scheduling mechanics (pod age, node fit) instead of genuine business priority. Root cause: PriorityClass is cluster-scoped with no default access control (§6). Fix: RBAC-restrict the priorityclasses resource with the use verb, scoped by resourceNames, so a team's ability to create Pods doesn't automatically grant it the ability to reference every priority tier that exists — a documented, opt-in Kubernetes control most clusters skip until after this exact incident.

Incident 2: The cascading preemption storm

A cluster mixes latency-sensitive services (priority 1000) with a batch ML training system (priority 2000, default preemptionPolicy: PreemptLowerPriority). A burst of large training Pods each trigger eviction of several priority-1000 services; those services' Deployments immediately recreate replacements, which are now Pending and — because capacity is still tight — some of them preempt yet lower-priority housekeeping Pods in turn. Cluster-wide churn spikes for several minutes with no single root cause other than "priorities were set too close together for the actual capacity headroom available." Fix (the actual, shipped one): this exact failure mode is what motivated Kubernetes' non-preempting priority feature (KEP-441, GA in 1.24) — marking bursty, restart-tolerant batch workloads preemptionPolicy: Never so they queue politely instead of triggering eviction storms, trading admission latency for cluster stability.

Incident 3: CPU-limit throttling mistaken for unhealthiness

A LimitRange default sets a modest CPU limit on every container. Under a legitimate traffic spike, the kernel's CPU bandwidth throttling enforces that per-container ceiling every fixed accounting period — a hard cutoff, not an adaptive one, so a container gets throttled even while the node overall still has spare CPU sitting idle. Latency spikes, the liveness probe (chapter 15) starts failing because the throttled process can't respond in time, and the kubelet restarts the container — turning a capacity-planning problem into a string of confusing restarts that look, from the outside, like an application bug. Fix: for latency-sensitive services, set CPU limits far above requests (or omit them) and rely on requests.cpu plus node-level scheduling for isolation instead — a widely recommended practice precisely because this incident shape is so common.

godefault_preemption.go — PostFilter(), simplified but structurally faithful
func (pl *DefaultPreemption) PostFilter(ctx context.Context, state *framework.CycleState,
    pod *v1.Pod, filteredNodeStatusMap framework.NodeToStatusMap) (*framework.PostFilterResult, *framework.Status) {

    // Only Pods that failed Filter on EVERY node reach here at all.
    candidates := pl.FindCandidates(ctx, state, pod, filteredNodeStatusMap)
    if len(candidates) == 0 {
        return nil, framework.NewStatus(framework.Unschedulable, "no preemption candidates found")
    }
    best := pl.SelectCandidate(candidates)          // best NODE, ranked across all candidates
    if err := pl.PrepareCandidate(best, pod); err != nil {
        return nil, framework.AsStatus(err)
    }
    // Victims are deleted HERE. pod is nominated for best.Name() and re-enters
    // the scheduling queue once its victims actually terminate and free capacity.
    return &framework.PostFilterResult{NominatedNodeName: best.Name()}, framework.Success
}
gopreemption.go — SelectVictimsOnNode(), the real "remove-all-then-reprieve" heuristic
func (pl *Preemptor) SelectVictimsOnNode(ctx context.Context, pod *v1.Pod,
    nodeInfo *framework.NodeInfo) (victims []*v1.Pod, pdbViolations int, ok bool) {

    var potential []*v1.Pod
    for _, p := range nodeInfo.Pods {
        if Priority(p.Pod) < Priority(pod) {
            potential = append(potential, p.Pod)
            nodeInfo.RemovePod(p.Pod)              // simulate: remove ALL lower-priority Pods first
        }
    }
    if fits, _ := pl.fitsOnNode(pod, nodeInfo); !fits {
        return nil, 0, false          // even evicting everyone eligible isn't enough — not a candidate node
    }
    sort.Slice(potential, byDescendingPriority)  // highest-priority-among-the-low first
    victims = append([]*v1.Pod{}, potential...)
    for _, p := range potential {
        nodeInfo.AddPod(p)                        // tentatively reprieve p
        if fits, _ := pl.fitsOnNode(pod, nodeInfo); fits {
            victims = remove(victims, p)          // wasn't needed after all — spare it
        } else {
            nodeInfo.RemovePod(p)                 // still needed — keep it evicted
        }
    }
    return victims, countPDBViolations(victims), true
}
WHY GREEDY, NOT EXACT — AND WHAT §15 DOES DIFFERENTLY

Finding the provably smallest victim set across two resource dimensions (CPU and memory both need to clear the deficit) is a two-dimensional subset-sum problem — combinatorial, and NP-hard in the general case. The real scheduler needs an answer per node, per unschedulable Pod, at cluster scale, so it uses the linear-time "remove everyone lower-priority, then reprieve from the highest-priority-among-them down" heuristic above: fast, good in practice, but not guaranteed to find the global minimum — it can spare a Pod that a smaller total eviction would have covered, because it only ever reprieves in one direction. §15's simulator holds only a handful of Pods per node, small enough that it computes the true minimal-cost victim set by exhaustive search instead — which is how you can watch the exact difference between "provably minimal" and "good enough at scale" side by side.

EXPERIMENTS TO RUN

1. Default scenario: submit the pending Pod as-is and read the log — the algorithm should pick the single lowest-priority Pod that alone frees enough of both CPU and memory, not the first lower-priority Pod it finds. 2. Raise the pending Pod's priority above every running Pod, then shrink the node's capacity — watch the deficit grow until no single Pod suffices and a genuine multi-Pod combination gets selected. 3. Set the pending Pod's priority equal to or below every running Pod's — it should stay Pending even though evicting everyone would technically free enough room, because equal-or-higher priority Pods are never eligible victims. 4.
