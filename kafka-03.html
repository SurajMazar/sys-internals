APACHE KAFKA INTERNALS · CHAPTER 03

Log Internals: Segments,
Indexes & the Record Format

A Kafka partition is sold to you as an infinite, append-only log. On disk it is a directory of bounded files, a pair of sparse binary indexes per file, and a byte format engineered so a broker can validate, route, and retain billions of records a day without ever deserializing most of them. This chapter takes the partition apart at the byte level: LogSegment, OffsetIndex, TimeIndex, and the KIP-98 record batch that everything downstream — the producer, the replica fetcher, the consumer — actually ships over the wire.

ARC 01 · THE PROBLEM

An infinite log has to live in finite files

Every abstraction Kafka sells you — "the partition is an ordered, immutable, append-only sequence of records" — is a promise about logical offsets: 0, 1, 2, 3, … forever. Nothing about that promise says anything about how bytes sit on a disk. The moment you ask "where does record #4,213,009 physically live, and how fast can I get to it," you have left the abstraction and entered this chapter's actual subject: the on-disk representation that UnifiedLog and LogManager build and maintain under <log.dirs>/topic-3/ — a directory named for the topic and partition, e.g. a topic orders partition 3 lives at orders-3/.

Three physical requirements have to be satisfied simultaneously, and they pull in different directions:

  • Append at disk-saturating throughput. Producers write continuously; the write path cannot pay for random I/O or in-place restructuring per record. It must degrade to "append bytes to the end of a file" — the one operation every filesystem and every disk (spinning or flash) does at its fastest.
  • Locate an arbitrary offset in better than O(n). Consumers resume from a committed offset after a restart; replicas fetch from a follower's last-known offset; offsetsForTimes() resolves a timestamp to an offset for time-travel seeks. All of these need "find offset K" to cost far less than reading every byte before it — but K could be anywhere in gigabytes of history.
  • Delete old data for the price of a directory listing. Retention (retention.ms, retention.bytes) must reclaim space continuously, on a partition that may be terabytes, without pausing appends and without rewriting data that survives.

Hold those three requirements in your head — sequential append, sub-linear lookup, cheap deletion — because every design decision in this chapter is a direct, derivable answer to exactly one of them. Nothing here is arbitrary; it is what falls out when you refuse to compromise on any of the three.

WHY THIS MATTERS FOR THE NEXT 12 CHAPTERS

The record batch format you decode in §8 is the same byte layout the producer's RecordAccumulator builds (chapter 4), the same bytes the leader appends without re-encoding (chapter 6 covers replication's fetch/produce paths, which move these bytes verbatim), and the same bytes LogCleaner rewrites during compaction (chapter 5). DEEP CONTEXT · WHY THE INDEX WAS ALWAYS SPARSE, NOT DENSE

Jay Kreps' original 2011 design memo already rejects a dense (per-message) index outright: it would be roughly the same size as the log itself for small messages, defeating the purpose of an index that should be small enough to sit entirely in the page cache. The sparse index — one entry every few KB, not one per record — is the oldest surviving design decision in this chapter, and every later KIP (32/33 for time, 98 for batching) extends the same sparse philosophy rather than replacing it.

ARC 03 · NAIVE SOLUTION

Attempt #1: one file per partition, scan to find anything

Derive it honestly, the way a first-principles engineer would in an afternoon. A partition is an append-only sequence of records — so the simplest possible on-disk representation is literally one file, opened once, appended to forever. To find a record by offset, you scan from the beginning, deserializing each record's framing until you've counted your way to the target.

pseudocodenaive_partition_log.c — the strawman, annotated
struct partition_log {
    int fd;             /* one fd, opened O_APPEND, never closed */
    uint64_t next_offset; /* next logical offset to assign        */
};

/* Append: dumb, and dumb is exactly the point at this stage. */
void append_record(partition_log *p, byte *key, int klen, byte *val, int vlen) {
    write_u64(p->fd, p->next_offset++);   /* offset          */
    write_u32(p->fd, klen + vlen + 8); /* record size     */
    write_u32(p->fd, crc32(key, klen, val, vlen)); /* checksum */
    write(p->fd, key, klen);
    write(p->fd, val, vlen);              /* append() only — always sequential */
}

/* Lookup: the only tool we have is "start from zero and count". */
record *find_offset(partition_log *p, uint64_t target) {
    lseek(p->fd, 0, SEEK_SET);
    uint64_t off; uint32_t size, crc;
    while (read_u64(p->fd, &off) > 0) {       /* O(n): one syscall-heavy   */
        read_u32(p->fd, &size);                    /* pass per candidate offset */
        read_u32(p->fd, &crc);
        if (off == target) return read_record_body(p->fd, size);
        lseek(p->fd, size - 8, SEEK_CUR);  /* skip this record's body  */
    }
    return NULL;  /* fell off the end: offset doesn't exist yet */
}

This already gets the append path right — every write is a sequential append, which is the fastest thing you can ask a disk to do, HDD or SSD. That is not a coincidence; it is the one property naive and production Kafka share. Everything that's about to go wrong is in find_offset and in what "one file, forever" does to deletion.

ARC 04 · WHY IT FAILS

The arithmetic that kills a single unbounded file

Three failure modes, each quantified — because "it doesn't scale" is not an argument until you can put a number on it.

1. Offset lookup is O(n) in bytes, not O(n) in records

The naive scan's cost is proportional to bytes read before the target, not record count — and it must physically read every one of those bytes off disk (or page cache, if you're lucky and it's resident). Consider a 10 GB partition file and a cold-cache lookup near the end:

  • 7,200 RPM HDD, sequential read ≈ 150–200 MB/s: 10 GB / 175 MB/s ≈ 57 seconds for a full scan; on average you'd stop halfway, so ≈ 28 s per lookup — for one client, on one partition, with the disk doing nothing else.
  • SATA SSD, sequential read ≈ 500 MB/s: ≈ 20 s worst case, ≈ 10 s average.
  • NVMe SSD, sequential read ≈ 3 GB/s: ≈ 3.3 s worst case, ≈ 1.7 s average — still absurd for an operation a consumer performs on every rebalance and every restart.

None of these numbers are acceptable for "resume consuming from offset K," which needs to complete in milliseconds. Multiply by dozens of consumer groups rebalancing simultaneously across thousands of partitions and the naive scan doesn't just feel slow — it saturates disk bandwidth that appends need.

2. Retention deletion means rewriting the file — or it doesn't work at all

Retention needs to discard the oldest records once retention.ms or retention.bytes is exceeded. In one giant file, the old data is at the front. No POSIX filesystem exposes "truncate from the head" — ftruncate() only shrinks from the end. The only way to remove the front of a file is to rewrite everything after the deletion point to a new file (or shift it within the same file) — an O(remaining bytes) copy, competing for the same disk bandwidth the append path needs, on every retention pass. fallocate(FALLOC_FL_PUNCH_HOLE) can free space in the middle of a file on some filesystems, but it leaves a hole your reader has to know to skip and does nothing to shrink the byte offsets your index would still need to track — it does not solve the addressing problem.

3. A single ever-growing file cannot be safely or usefully memory-mapped

Memory-mapping is the cheapest way to get page-cache-backed random access without read() syscalls (§8 leans on this hard for the index). But mmap() maps a fixed-size region. A file that grows without bound forces either remapping on every growth (invalidating pointers, costly) or reserving an address-space region far larger than needed up front (wasteful, and eventually wrong anyway). A file with a known, bounded maximum size is a precondition for using mmap safely and simply — which is exactly the tool §8 needs for the index files.

THE NUMBERS, ONE MORE TIME

A retention pass on a 500 GB single-file partition, rewriting the surviving 400 GB at 200 MB/s, costs roughly 2,000 seconds — over half an hour — of disk bandwidth contending directly with live appends and fetches, repeated every time retention needs to reclaim space. That single number is why "one file" is disqualified before you even get to indexing.

So: we need to bound file size, and we need an index. §5 derives what shape both should take.

ARC 05 · BETTER SOLUTION, CANDIDATES EXAMINED

Three candidates, one survivor: the segmented log

Step through the candidates a careful engineer considers, in the order they get eliminated.

Candidate A → B → CSTEP-BY-STEP

Candidate C — the segmented log — is what LogManager and UnifiedLog actually build. A partition directory holds an ordered sequence of segments, each a bounded-size .log file plus its own .index/.timeindex siblings. A segment rolls — closes and a new one opens — when either threshold is crossed:

  • segment.bytes — default 1,073,741,824 (1 GiB). Once the active segment's .log file would exceed this, roll.
  • segment.ms — default 604,800,000 ms (7 days). Even a low-throughput partition rolls at least this often, so retention-by-time has segment-granularity to work with regardless of volume.

Rolling is cheap by construction: it's opening a new file whose name encodes the next base offset, not touching any existing file. Deletion becomes equally cheap in the other direction — once every record in a segment is older than retention.ms (or the segment is behind the retention.bytes cutoff), the whole segment — .log, .index, .timeindex, and friends — is simply unlink()'d. No bytes are rewritten. Deletion cost drops from O(surviving bytes) to O(1) per segment.

ARC 06 · WHY THAT STILL COSTS

Segments solve the big problems; here's what's left

The segmented log doesn't make cost disappear — it relocates and bounds it. Four residual costs, each real and each tunable:

  • The active segment is structurally different from every other segment. Only the last segment in the sequence is ever appended to; every earlier segment is immutable the instant it rolls. That asymmetry is why LogSegment tracks an append() path used exactly once per partition (on the current active segment) and a read() path used on all of them. The active segment's index is also incomplete by definition — it grows incrementally with each append, rather than existing fully-formed the way a rolled segment's index does.
  • A sparse index still means a linear scan phase after the binary search. §8 derives this precisely, but the shape is: index entries are written only every index.interval.bytes (default 4,096) of log data. A lookup gets you to the nearest preceding indexed position for free, then must scan forward through up to ~4 KB of raw log bytes, deserializing record-batch headers, until it finds the target. Smaller intervals shrink that scan at the cost of a larger, more numerous index file — §8's slider makes this tradeoff concrete.
  • Rolling has its own overhead, paid rarely but not for free. On roll: the outgoing segment's index is trimToValidSize()'d (its mmap is shrunk to just the entries actually written, since it was pre-allocated at segment.index.bytes, default 10 MiB, worth of address space) and flushed; a producer-state .snapshot is written (§8); new file handles are opened for the fresh .log/.index/.timeindex. None of this is expensive at 1 GiB cadence, but it is exactly the kind of "rare but synchronous" work that shows up as a p99 latency spike if segment.bytes is set too low relative to throughput (§11 has the incident).
  • Recovery after an unclean shutdown must rebuild or validate at least the active segment's indexes. A crash mid-append can leave the .log file with a torn final record batch and the .index/.timeindex undersized or stale relative to it. Log.loadSegments() re-scans and re-validates on startup — §8 and §13 walk the exact mechanism.
THE KNOB THAT TRADES ALL FOUR AGAINST EACH OTHER

index.interval.bytes is the single tuning lever that sits at the center of this section: smaller values shrink the post-binary-search linear scan (cheaper lookups) but grow the index file and the number of mmap pages touched per lookup (more index overhead, more page-cache pressure); larger values do the reverse. Kafka's default of 4,096 is chosen so a rolled 1 GiB segment's index is a few hundred KB — small enough to live entirely in the page cache, on every segment, indefinitely.

WHY BASE-OFFSET FILENAMES, NOT SEQUENCE NUMBERS

Naming each segment after its own first offset (rather than "segment 0, segment 1, …") means a reader who knows a target offset can locate the right segment with a single lookup: find the largest base offset ≤ target among the directory's segment names. LogSegments keeps these in a ConcurrentSkipListMap<Long, LogSegment> keyed by base offset specifically so that lookup — floorEntry(targetOffset) — is itself O(log(segment count)), before the per-segment index search even begins. Two binary searches nested inside each other: one across segments, one across index entries.

ARC 08 · INTERNAL IMPLEMENTATION

The sparse index, the two-phase lookup, and the record batch

(a) Why the index entry is exactly 8 bytes, and why it's memory-mapped

OffsetIndex (extending AbstractIndex) stores each entry as a fixed 8 bytes: a 4-byte relative offset and a 4-byte physical position within the .log file. Both halves are derived, not arbitrary:

  • Relative, not absolute, offset. An absolute Kafka offset is a signed 64-bit long. But every offset in a given segment differs from that segment's base offset by, at most, however many records fit in segment.bytes — for any sane record size, that delta fits comfortably in 32 unsigned bits (up to ~4.29 billion). Storing offset - baseOffset instead of offset halves this field's width for free, because the expensive 64-bit information (which segment) is already encoded in the filename and needs storing exactly once per segment, not once per index entry.
  • Physical position, not "record number." The whole point of the index is to let a reader seek()/pread() directly into the .log file without scanning from byte 0. A position that isn't a real byte offset would force exactly the linear scan the index exists to avoid — so the index must store what the filesystem actually understands: a byte position.

The whole 10 MiB-preallocated (segment.index.bytes, default 10,485,760) index file is opened via MappedByteBuffer — a memory map, not buffered read()/write() calls. Derive why: a lookup is random access by nature (binary search jumps around), and mmap turns each access into a page-cache-backed memory read serviced by the kernel's existing page cache — no syscall, no buffer copy, and the kernel — not the JVM — decides which pages to keep resident under memory pressure. Because the index is small (a few hundred KB per 1 GiB segment at the 4,096-byte default interval) it tends to stay fully resident, making index lookups effectively free compared to the log read that follows.

(c) .timeindex: the same sparseness, a different key

TimeIndex entries are (8-byte timestamp, 4-byte relative offset) pairs, backing offsetsForTimes() and time-based seeks (auto.offset.reset to a wall-clock time, retention-by-time decisions). It is populated in the same append call as OffsetIndex — every time LogSegment.append() decides bytes-since-last-index-entry has crossed index.interval.bytes, it writes one OffsetIndex entry and one TimeIndex entry together, using the largest timestamp observed since the last entry (maxTimestampSoFar). They are two views onto the identical sampling cadence, not two independently tuned structures — which is why there is no separate "time index interval" config.

(d) The record batch, KIP-98 v2, field by field

Everything the index points into is a stream of record batches. Since KIP-98 (Kafka 0.11, 2017) every batch uses magic value 2 and is framed as follows — hover conceptually over each field as you read the byte offsets:

Two fields deserve special attention. CRC placement: the 4-byte CRC32C covers everything after itself — from attributes through the last record — deliberately excluding baseOffset, batchLength, partitionLeaderEpoch, and the CRC field itself. This lets a broker patch partitionLeaderEpoch when a batch is assigned to a new leader epoch, and lets any component adjust batchLength (e.g. after down-conversion) or read it to skip the whole batch, all without recomputing a checksum the producer already committed to. attributes (2 bytes) packs the compression codec into the low 3 bits (0=none, 1=gzip, 2=snappy, 3=lz4, 4=zstd), plus single bits for timestamp type (create-time vs log-append-time), isTransactional, and isControlBatch — control batches carry transaction markers (commit/abort), not user records, and are what chapter 7's transaction coordinator emits.

Inside a batch, each record is varint-framed, not fixed-width — because within one batch, everything expensive (offsets, timestamps) is stored as a small delta from the batch's own baseOffset/ firstTimestamp, and small deltas fit in 1–2 bytes instead of 8. A record is: length (varint) · attributes (1 byte, currently unused per-record) · timestampDelta (varint, zigzag) · offsetDelta (varint, zigzag) · keyLength (varint) + key bytes · valueLength (varint) + value bytes · headerCount (varint) + headers (each a varint-length key string, varint-length value).

Varint + zigzag, worked example. A varint spends 7 bits of payload per byte, using the 8th (high) bit as a continuation flag. Zigzag encoding maps signed integers to unsigned ones so small negative deltas stay small: zigzag(n) = (n >= 0) ? 2n : -2n - 1. A timestampDelta of +3 ms zigzags to 6 (0000 0110) — one byte, no continuation bit, encoded as 0x06. A delta of -3 ms zigzags to 5 (0000 0101) — also one byte, 0x05: small deltas cost one byte regardless of sign, which is the entire reason zigzag exists (plain two's-complement -3 would be a huge unsigned number and blow the varint out to its full width).

QUANTIFYING V1 → V2: 100 RECORDS OF 100 BYTES EACH

v1 (pre-KIP-98): every message repeated a full per-message envelope — 8-byte offset + 4-byte size + 4-byte CRC + 1-byte magic + 1-byte attributes + 8-byte timestamp ≈ 26 bytes of framing (some published breakdowns count closer to ~34 bytes once wrapper-message overhead for compressed sets is included) — per message, uncompressed. For 100 messages of 100 bytes: 100 × (100 + 26) ≈ 12,600 bytes, of which 2,600 is pure overhead — ~20.6%.
v2 (KIP-98): one ~61-byte batch header, amortized, plus per-record varint framing (roughly 6–8 bytes for small key/value + deltas). For the same 100×100-byte records: 61 + 100 × (100 + 7) ≈ 10,761 bytes, of which 761 is overhead — ~7.1%. The gap widens further once compression is enabled, because v2 compresses the whole batch as one stream (one codec context, shared dictionary state across all 100 records) instead of compressing framing-heavy individual messages.

(e) Recovery, and the producer-state snapshot

On unclean shutdown, Log.loadSegments() (via LogLoader) re-scans segments whose .index/.timeindex are missing, zero-length, or fail a fast sanity check, rebuilding them from the raw .log bytes by replaying every batch header. It also validates the tail: it reads forward batch by batch, checking each CRC, until it hits a batch that fails validation or is truncated mid-write — the file is then hard-truncated at the start of that batch, discarding an in-flight write that never fully landed. This is the same mechanism, run unconditionally at startup, whether or not the prior shutdown was clean — clean shutdowns just find nothing to fix.

ProducerStateManager persists a .snapshot file on every segment roll, holding — per active producer ID on this partition — the last 5 (sequence number, offset) entries, used to detect and drop duplicate retries from an idempotent producer (chapter 4 derives why 5: it's bounded by max.in.flight.requests.per.connection's default). On restart, the manager reloads the most recent snapshot and replays only the small tail of records written after it, rather than replaying the entire log to reconstruct producer state.

Read the table as a spectrum of "who manages the index, and how sparse is it." Kafka's answer — sparse, mmap'd, colocated with the data it indexes, one pair of small files per bounded segment — buys resident-in-cache lookups and unlink()-cheap retention at the cost of accepting a bounded scan per read. Systems with denser or B-tree-shaped indexes (KahaDB) buy more precise lookups at the cost of non-sequential index writes competing with the append path.

ARC 10 · PERFORMANCE CHARACTERISTICS

What you can predict before you benchmark

  • Lookup complexity: O(log(segments)) to find the segment (skip-list floorEntry) + O(log(index entries in that segment)) binary search + O(index.interval.bytes) worst-case linear scan of raw log bytes. The dominant term in practice is the last one — it's bytes read off the page cache or disk, not comparisons.
  • Disk access pattern: appends are always sequential — one FileChannel.write() to the current end of the active segment's .log file, regardless of how many partitions or producers are involved, because each partition's active segment has exactly one writer position. This is why Kafka's write throughput barely differentiates HDD from NVMe for the append path alone — sequential throughput on a modern 7,200 RPM HDD (~150–250 MB/s) is often "enough," while random I/O on the same disk would be orders of magnitude slower.
  • Page cache does double duty for fan-out reads. Multiple consumer groups reading near the tail of the same partition share the same resident page-cache pages — the broker doesn't re-read from disk per consumer, and the OS's read-ahead keeps sequential consumer reads warm without Kafka doing anything explicit. This is the physical basis for "Kafka fan-out is nearly free": it's a page-cache property, not a Kafka-specific cache.
  • Durability doesn't come from fsync-per-write. log.flush.interval.messages (default effectively unbounded, Long.MAX_VALUE) and log.flush.interval.ms (default: rely on the OS's own writeback, i.e. not forced per message) mean Kafka does not fsync on every produce request by default. Durability instead comes from replication — acks=all plus min.insync.replicas — because fsync-per-write would cap throughput at the disk's IOPS-for-small- sync-writes ceiling, which is far below sequential throughput.
  • GC impact: index files are memory-mapped, which means their backing pages live in the OS page cache, outside the JVM heap. A broker holding thousands of segments' worth of index files pays essentially zero extra GC pressure for them — the JVM only holds small MappedByteBuffer/off-heap handle objects, not the index bytes themselves.

The curve is an analytic sketch: index entries ≈ segment.bytes / index.interval.bytes, index file size ≈ entries × 8 bytes, average scan ≈ index.interval.bytes / 2 (uniform arrival assumption). Real workloads have bursty record sizes and compression, which shift the effective bytes-per-record ratio; the shape — linear tradeoff between index size and scan cost — is what to internalize, not the exact constant.

ARC 11 · REAL-WORLD PRODUCTION

Three lessons this design has taught operators

1. LinkedIn's original motivation (2011)

Kreps, Narkhede, and Rao's original Kafka paper describes the exact problem this chapter opened with: existing messaging systems of the era kept per-message or per-consumer metadata (acked/unacked state, in-memory indexes) that didn't scale to LinkedIn's target of hundreds of GB/day per broker. The segmented log with a sparse index and near-zero per-consumer server-side bookkeeping (offsets tracked by the consumer, not the broker, in the original design) was chosen specifically because it lets disk I/O stay sequential regardless of how many consumer groups are reading — a direct ancestor of the page-cache fan-out argument in §10.

2. The segment-count explosion incident

A recurring operational failure mode: setting segment.bytes far below its 1 GiB default (sometimes done to make retention-by-size feel more "granular") on a topic with long retention and many partitions. The result is thousands of tiny segments per partition instead of dozens, each holding open file handles for its .log, .index, and .timeindex — three descriptors per segment. Across many partitions this can multiply into tens of thousands of open file descriptors per broker, colliding with the OS ulimit -n and eventually causing "too many open files" errors on new segment rolls or partition reassignment. The fix is almost always leaving segment.bytes near its default and controlling retention granularity with time instead (segment.ms), since segment count — not retention precision — is what scales with this knob.

3. KIP-98's batch format: the published payoff

Confluent/LinkedIn engineering write-ups around the KIP-98 rollout described the record-batch redesign as delivering substantial overhead reduction specifically for small-message, high-volume workloads — the exact scenario quantified in §8(d), where per-message framing that once cost roughly a fifth of the payload dropped to a small fraction of that once amortized across a batch and compressed once as a unit. The magnitude varies by message size and compression codec, but the direction and mechanism are exactly what §8 derives: fewer repeated fixed-width fields, more shared compression context.

4. Index corruption after unclean shutdown / disk-full mid-write

A broker that loses power or is OOM-killed mid-append can leave a segment's .index undersized relative to its .log, or a .log file with a torn trailing batch, especially if the disk filled up mid-write (a partial write() that never completed). On restart, LogLoader's recovery path (§8e) rebuilds affected indexes and truncates the torn tail — but if the underlying disk itself is failing (not just the process crashing), that recovery can repeatedly fail. log.dir.failure.timeout.ms (default 30,000 ms) bounds how long the broker waits for a log directory to become usable before marking it offline — moving every partition replica on that directory out of service on this broker (triggering leader election elsewhere) rather than letting one bad disk hang the whole broker process indefinitely.

ScalaOffsetIndex.scala — lookup(), the sparse binary search
def lookup(targetOffset: Long): OffsetPosition = {
  maybeLock(lock) {
    val idx = mmap.duplicate()            // each caller gets its own position/limit
    val slot = indexSlotFor(idx, targetOffset)  // binary search over fixed 8-byte entries
    if (slot == -1) OffsetPosition(baseOffset, 0)
    else parseEntry(idx, slot)             // (relativeOffset, physicalPosition) → absolute
  }
}

private def indexSlotFor(idx: ByteBuffer, target: Long): Int = {
  // classic binary search, but comparing against relative offsets —
  // entries are 8 bytes apart: entrySize == 8
  var lo = 0; var hi = entries(idx) - 1
  if (hi < 0) return -1
  while (lo < hi) {
    val mid = ceil((lo + hi) / 2.0).toInt
    val found = relativeOffset(idx, mid)
    if (found <= target - baseOffset) lo = mid else hi = mid - 1
  }
  lo   // the largest indexed offset that is <= target: our scan start
}
ScalaLogSegment.scala — append(), conditionally writing an index entry
def append(largestOffset: Long, largestTimestamp: Long,
           shallowOffsetOfMaxTimestamp: Long, records: MemoryRecords): Unit = {
  if (records.sizeInBytes > 0) {
    val physicalPosition = log.sizeInBytes()          // current end of .log — sequential append
    log.append(records)                              // one FileChannel.write(), no seeking

    // Only write an index entry once bytesSinceLastIndexEntry
    // crosses index.interval.bytes — this IS the sparseness.
    if (bytesSinceLastIndexEntry > indexIntervalBytes) {
      offsetIndex.append(largestOffset, physicalPosition)
      timeIndex.maybeAppend(largestTimestamp, shallowOffsetOfMaxTimestamp)
      bytesSinceLastIndexEntry = 0
    }
    bytesSinceLastIndexEntry += records.sizeInBytes
  }
}
JavaDefaultRecordBatch.java — the v2 header's field offsets (constants, simplified)
class DefaultRecordBatch {
  static final int BASE_OFFSET_OFFSET = 0;               // 8 bytes
  static final int LENGTH_OFFSET = 8;                    // 4 bytes
  static final int PARTITION_LEADER_EPOCH_OFFSET = 12;    // 4 bytes
  static final int MAGIC_OFFSET = 16;                     // 1 byte  (== 2)
  static final int CRC_OFFSET = 17;                       // 4 bytes — covers ATTRIBUTES_OFFSET..end
  static final int ATTRIBUTES_OFFSET = 21;                  // 2 bytes  ← CRC coverage starts HERE
  static final int LAST_OFFSET_DELTA_OFFSET = 23;           // 4 bytes
  static final int FIRST_TIMESTAMP_OFFSET = 27;            // 8 bytes
  static final int MAX_TIMESTAMP_OFFSET = 35;              // 8 bytes
  static final int PRODUCER_ID_OFFSET = 43;                // 8 bytes
  static final int PRODUCER_EPOCH_OFFSET = 51;             // 2 bytes
  static final int BASE_SEQUENCE_OFFSET = 53;              // 4 bytes
  static final int RECORDS_COUNT_OFFSET = 57;              // 4 bytes
  static final int RECORDS_OFFSET = 61;                    // header ends; ~61-byte fixed cost, amortized
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Put the mutable fields before the CRC's coverage, not after. batchLength and partitionLeaderEpoch sit before CRC_OFFSET precisely so a leader (or a down-converting broker) can rewrite them without invalidating a producer's checksum — a deliberate asymmetry, not an oversight. 2. Sparseness is one if, not a separate subsystem. LogSegment.append()'s index write is a single conditional inside the hot append path — no background thread, no separate index-builder service — which is exactly why it can't fall behind or race with the data it's indexing. 3. Binary search against relative offsets, not absolute ones. Every comparison in indexSlotFor subtracts baseOffset first — the same relative-offset trick that shrinks the entry to 4 bytes also keeps the comparison arithmetic entirely in 32-bit space for typical segment sizes.
