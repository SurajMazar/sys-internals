WHATSAPP ARCHITECTURE · CHAPTER 11

Reliability at Scale:
LB, Failover, Spam & Observability

Two billion phones each hold one long-lived, stateful, encrypted TCP connection to a specific chat server, chosen once, kept for hours. There is no per-request do-over. This chapter derives how you load balance a connection instead of a request, what happens to two million sessions when the server holding them dies, why the fix for that is mostly arithmetic (backoff, jitter, admission control), why Erlang lets you dodge the problem entirely for routine deploys, and how you police abuse when the one signal you are forbidden to read — message content — is off the table.

ARC 01 · THE PROBLEM

Load balancing a connection is not load balancing a request

Every load-balancing technique you learned for HTTP assumes the unit of work is a request: milliseconds long, stateless, and free to route differently every single time. Round-robin, least-connections, weighted random, consistent hashing on a URL — all of them get to re-decide on the next request if the last decision was bad. A chat server's connection has none of that freedom. A phone opens one TCP socket, completes a Noise handshake (chapter 2), authenticates, and then holds that socket open for hours — sending keepalives, receiving messages, occasionally going quiet in the background. The load-balancing decision — which physical chat server answers this phone's connect() — is made exactly once, at connect time, and cannot be revisited without tearing the connection down and starting over.

That single fact reshapes the whole problem. Once a phone is attached to a server, that server is not a stateless request handler you can swap transparently — it is holding this device's presence state (online/last-seen), its in-RAM undelivered-message queue head, its Noise session keys for the transport layer, and the process (in Erlang terms, a per-connection process — chapter 1) that will push every future inbound message the instant it arrives. The server is not a cache of that state; for the connection's lifetime, it is the authoritative copy of "is this device currently reachable." That is what "sticky" means here, and it is not an optimization you chose — it is a structural consequence of building a real-time push system on top of long-lived sockets.

So the reliability problem this chapter answers has three layers, each harder than the one below it:

  • Steering connections at all. With ~2 billion devices and no single global switch, how does a phone in Mumbai find a nearby, healthy, non-overloaded chat server without a full-mesh view of the fleet?
  • Surviving one server's death. A single chat server can hold on the order of 2 million live connections (chapter 8's numbers). When it dies — hardware fault, kernel panic, OOM, planned drain — those 2 million phones all discover their socket is gone within seconds of each other, and all try to reconnect. If that reconnect swarm behaves in any correlated way, it does not "just" fail over — it can knock over the servers that were trying to absorb it.
  • Detecting abuse with your hands tied. The one thing this system is contractually forbidden to look at — message plaintext — is exactly what a naive anti-abuse system would want to read. Spam and account-abuse detection has to work on behavior and metadata alone, which is a genuinely different, harder classification problem than "scan the text."

DEEP CONTEXT · WHY "50 ENGINEERS" IS THE LOAD-BEARING FACT

WhatsApp's famous ~50-engineer team at the time of the 2014 Facebook acquisition, serving ~450–900M users, is not a trivia point — it is the reason this chapter's philosophy (few, large, deeply-instrumented machines; the fewest possible moving parts; failure handling pushed into arithmetic and language runtime guarantees rather than into headcount-hungry tooling) exists at all. A team that size cannot operate a bespoke fleet-management control plane with a large SRE organization behind it. It has to buy reliability from BEAM's supervision trees, Erlang's hot code loading, and designs simple enough that a small team can hold the whole failure surface in their heads. That constraint outlived the acquisition and shaped every design choice in this chapter.

ARC 03 · NAIVE SOLUTION

Attempt #1: DNS round-robin + reconnect-immediately clients

Derive it honestly, the way a team with no incident history yet would. The obvious first cut: publish one DNS name for the chat-server fleet, round-robin the A/AAAA records across every server's IP, and write the most naive possible client reconnect logic — if the socket drops, reconnect immediately.

pseudocodenaive_client.c — the strawman reconnect loop
void maintain_connection(void)
{
    for (;;) {
        int fd = connect_to(resolve("chat.example.com"));  /* plain round-robin DNS */
        if (fd < 0) {
            sleep(1);              /* fixed 1s pause — feels "safe" */
            continue;
        }
        run_session(fd);          /* keepalives, message push, blocks for hours */
        /* session ends — server died, network blip, app backgrounded */
        sleep(1);
        /* loop straight back to connect_to() — no state, no memory of past failures */
    }
}

This is not a strawman built to be laughed at — it is the honest zeroth iteration, and for the overwhelming majority of a chat server's life it works fine: DNS spreads new connections roughly evenly, a 1-second retry feels generous, and every engineer's instinct for "just reconnect" is basically correct most of the time. The failure only shows up in one specific, low-probability, catastrophic scenario: what happens to reconnects when a server does not fail gracefully but fails all at once, for everyone connected to it, at the same instant.

ARC 04 · WHY IT FAILS

The thundering herd, quantified

Put real numbers on it. A single chat server, per chapter 8's capacity model, holds on the order of 2,000,000 live connections. It dies — kernel panic, an OOM kill of the whole BEAM node, a rack losing power. Every one of those 2,000,000 phones observes its TCP socket close within roughly one keepalive interval of each other — call it a window of a few seconds, driven far more by "the OS finally noticed the peer is gone" than by anything staggered. With the naive client from §3, every one of them sleeps exactly one second and then reconnects. The result is not "2,000,000 reconnects spread over the retry period" — it is 2,000,000 reconnects arriving in the same one-second bucket, then the same 2,000,000 again a second later if the first wave also fails (because the fleet is now busy from the first wave), and so on: a synchronized pulse that repeats in lockstep.

If those 2,000,000 reconnects distribute uniformly across the remaining N−1 servers, each survivor absorbs roughly 2,000,000 / (N−1) extra connections — on a fleet of, say, 500 servers, that is about 4,000 new connections per survivor, each one a fresh TLS/Noise handshake and an authentication round trip (chapters 2 and 8). That is expensive but survivable if spread over tens of seconds. The catastrophe is correlation: because every client used the same fixed sleep and the same "retry now" trigger, the load does not spread — it arrives as a single spike sized 2,000,000 handshakes in one second, aimed at whichever servers DNS or the balancer happens to send it to.

THE CASCADE MECHANISM

A handshake (asymmetric crypto for Noise, a database round trip for auth) costs orders of magnitude more CPU than steady-state keepalive traffic for an already-connected session. A spike of handshake attempts pins CPU on the receiving servers; requests that don't complete within the client's connect timeout are perceived by the client as "that server failed too" — so it retries again, often immediately, adding to the same spike instead of draining it. This is the textbook definition of a thundering herd cascading into a full outage: the recovery attempt is the outage, self-sustaining because failed attempts generate more attempts faster than successful ones drain the queue. It is exactly the failure mode you will be able to trigger — and prevent — in the §15 simulator.

Three independent defenses are needed, and each one is a direct rebuttal to one part of the mechanism above: break the synchronization (jitter), break the immediate-retry reflex (backoff), and give the receiving side a way to say no cheaply instead of falling over expensively (admission control). §5 derives them.

ARC 05 · BETTER SOLUTION

Backoff, jitter, and admission control — derived, not looked up

Candidate A: fixed backoff (wait longer, still in lockstep)

The obvious first fix: make the retry sleep longer — say 5 seconds instead of 1. This helps only by a constant factor; every client still sleeps the same 5 seconds, so the herd still arrives in lockstep, just five times less often. Rejected: it does not break synchronization, only slows its cadence.

Candidate B: exponential backoff, no jitter (still synchronized)

Double the sleep on each consecutive failure (1s, 2s, 4s, 8s…), capped at some maximum. This correctly reduces the rate of retries from a single client over time — good design in isolation — but every client that failed at the same instant is still doubling from the same starting point at the same instant. The herd is thinner per wave but just as synchronized. Rejected on its own: exponential decay attacks retry rate, not correlation.

Candidate C: exponential backoff + full jitter ✓

Take the exponential backoff ceiling for attempt k, cap·2^k — but instead of sleeping that exact duration, sleep a uniformly random duration between 0 and that ceiling. This is "full jitter" (the term and the analysis come from AWS's widely cited 2015 backoff writeup, itself echoing decades of network backoff theory going back to Ethernet's binary exponential backoff). The insight: the ceiling still shrinks the expected wait as the outage persists (candidate B's virtue), but because each client draws an independent random number, two clients that failed in the same millisecond now retry at different, effectively uncorrelated times. The herd is not slowed — it is spread out in time, which is the only thing that actually fixes correlation.

Full jitter alone protects the client population's arrival pattern. It says nothing about a receiving server that is simply undersized for any spike. The third leg is server-side connection admission rate limiting: each chat server enforces a hard cap — say, N new handshakes accepted per second — and every connection attempt beyond that cap is rejected immediately and cheaply (a TCP-level reject or a fast "retry later" response) rather than accepted and left competing for CPU with everyone else's handshake. A rejected client backs off (with jitter) and tries again; the server never accumulates more concurrent handshake work than it provisioned for. The three defenses compose: jitter spreads the herd in time, backoff shrinks it as the outage persists, and admission control puts a hard, cheap floor under how bad any single server's day can get.

A FOURTH DEFENSE THAT SIDESTEPS THE WHOLE PROBLEM

Every defense so far assumes servers die unpredictably and connections must be re-established. But the single largest source of "a server's connections all move at once" in practice is not a crash — it is a planned deploy. If you could ship new code to a running BEAM node without ever closing its sockets, most reconnect storms would never happen in the first place, because the herd-triggering event (2M connections dropping simultaneously) simply would not occur. §8 shows exactly how Erlang's hot code loading does this.

ARC 06 · WHY THAT STILL COSTS

The bill: latency, blast radius, and what jitter cannot fix

Full jitter plus admission control is the correct design, but it is not free, and a Staff engineer should be able to name the costs precisely rather than wave at "it's more robust now":

  • Jitter trades correlation for tail latency. A client that could have reconnected in 1 second may now wait up to cap·2^k seconds by design — the whole point is to not retry immediately. During a real outage, some legitimate users experience longer visible downtime than a naively-retrying client would have, in exchange for the fleet not falling over. This is a genuine UX cost, not a free lunch.
  • Admission limits convert an overload into visible rejections. A hard per-server cap on new handshakes means that during a real capacity shortfall (not just a synchronization artifact), some fraction of clients get explicit "try again" responses rather than a slow-but-eventually-successful connect. You have converted an invisible slowdown into a visible, countable failure — which is honestly better for on-call, but it is a different failure mode, and dashboards must be built to expect it.
  • DNS-based geographic steering is inherently stale. DNS TTLs (commonly tens of seconds to minutes) mean a client's cached server list can point at a datacenter that has since been drained or that is no longer geographically closest. Anycast and short TTLs help but never eliminate the staleness window — a client can always be holding a server list that reflects the world as it was one TTL ago.
  • None of this repairs correlated behavior that isn't purely time-based. If every client in a country loses connectivity simultaneously (a real undersea-cable cut, a mobile carrier outage) and regains it simultaneously, jitter still works — the random draw doesn't care why they all reconnected at once — but if client software itself has a bug that makes many devices retry on a synchronized wall-clock boundary (e.g. "reconnect at the top of the minute"), jitter must be seeded independently per device, and a shared clock-aligned bug can still reintroduce correlation. The defense only works if the randomness is genuinely per-client.
THE INDUSTRY'S SHARED ANSWER — AND ITS LIMITS

Full jitter is not a WhatsApp-specific invention — AWS's SDKs, Google's client libraries, and countless distributed systems adopted the same math after repeatedly re-deriving it the hard way in production incidents. That convergence is itself evidence: there is no cleverer trick that avoids the latency/correlation tradeoff, only better tuning of the constants (base, cap, admission rate) for your specific fleet size and connection cost. §10 gives you the numbers to tune those constants correctly rather than by folklore.

ARC 08 · INTERNAL IMPLEMENTATION

The mechanism: jitter math, admission limiting, and hot code loading

Three pieces of real mechanism, at the level you'd need to implement or audit: (a) the exact full-jitter formula and why its variants matter, (b) a token-bucket admission limiter's state machine, and (c) how BEAM swaps running code under live connections without dropping a single one.

(a) Full jitter, in the exact form worth memorizing

pseudocodebackoff.c — three variants, only one is correct
/* base = 1s, cap = 60s, attempt = number of consecutive failures so far */

no_jitter(attempt)      = min(cap, base * 2^attempt)
/* every client with the same attempt count sleeps the SAME duration — still synchronized */

equal_jitter(attempt)   = (temp/2) + random_between(0, temp/2)   where temp = min(cap, base*2^attempt)
/* halves the correlation: half the sleep is fixed (a floor under retry latency), half is random */

full_jitter(attempt)    = random_between(0, min(cap, base * 2^attempt))
/* zero fixed component — maximum decorrelation, at the cost of some clients retrying */
 * almost immediately by chance (uniform draw can be near zero) while others wait the
 * full ceiling. In expectation this is exactly what you want: it minimizes the total
 * number of clients retrying in any given instant, which is the entire objective.      */

The counter-intuitive part is why full_jitter beats equal_jitter for this specific goal. Equal jitter gives every client a guaranteed minimum wait, which feels safer, but that guaranteed floor is itself a source of residual correlation — a whole population of clients still has a hard lower bound on when they can possibly retry, clustering activity just above that floor. Full jitter's uniform draw across the entire range, including near zero, spreads retries as widely as the distribution allows, which is what minimizes the peak instantaneous reconnect rate — the exact quantity that determines whether a receiving server's admission limiter gets overwhelmed.

(b) Staggered restarts during deploys

Even with jitter and admission control, a fleet-wide restart of every chat server at once — the naive way to ship new code before hot loading existed, and still the fallback when a change genuinely cannot be hot-loaded (a BEAM VM upgrade, a kernel patch requiring reboot) — would create the exact thundering herd of §4 deliberately. The operational answer is staggered restarts: restart servers in small waves (a few percent of the fleet at a time), each wave's connections draining to the remaining healthy servers (which must therefore be provisioned with headroom for one wave's worth of displaced connections), waiting for the wave to rejoin before starting the next. This converts one enormous correlated event into a sequence of small, individually-absorbable ones — the same principle as jitter, applied by an orchestrator instead of by client-side randomness.

(c) Hot code loading — deploying without dropping connections

BEAM (the Erlang VM) can hold two versions of a module's code simultaneously: the "current" version and the "old" version. When you load a new version, any process still executing old code keeps running it until it makes a fully-qualified call back into the module (e.g. via Module:Function rather than a local call) — at which point it switches to the new version. A per-connection process handling one of 2 million live sessions can therefore be upgraded to new message-handling logic without ever closing its socket: no reconnect, no handshake, no entry in the §4 thundering-herd math at all, because the triggering event (a dropped connection) never occurs.

Erlangconnection handler — code_change/3, the state-migration hook
%% gen_server behaviour: the per-connection process's callback module.
%% Two module versions can coexist; this callback runs on the OLD version's
%% process the moment it's told to adopt the NEW version's code.
code_change(_OldVsn, State = #conn_state{}, _Extra) ->
    %% State was built by the OLD code's record definition. If the new
     %% version adds/removes/reshapes fields, THIS function is the only
     %% place that reconciles old-shape state with new-shape state —
     %% miss a field here and every live connection silently corrupts
     %% its own session state on the next hot-load.
    NewState = #conn_state{
        socket        = State#conn_state.socket,
        device_id     = State#conn_state.device_id,
        ratchet       = State#conn_state.ratchet,
        pending_acks  = State#conn_state.pending_acks,
        rate_limiter  = maps:new()   %% new field introduced this release
    },
    {ok, NewState}.
WHY THIS IS A CAPABILITY ALMOST NO OTHER RUNTIME OFFERS

Contrast with a typical server process in Go, Java, Python, or Node: deploying new code means starting a new process (or container) and terminating the old one, which for a long-lived TCP connection means the socket closes — the client must reconnect, full stop. Kubernetes rolling deploys, connection draining, and graceful shutdown all exist specifically to manage that unavoidable reconnect. BEAM's hot code loading is not a faster version of connection draining — it is a different category of solution: the connection never needs to drain because it never needs to close. The constraint you pay for this: two module versions must be able to coexist correctly, every state-shape change needs an explicit, correct code_change/3, and this only helps for code that doesn't require a full VM/OS restart — kernel upgrades and BEAM version bumps still need the staggered-restart path above.

ARC 10 · PERFORMANCE CHARACTERISTICS

The arithmetic you should be able to reproduce on a whiteboard

  • Reconnect fan-out per server death: 2,000,000 connections / (fleet_size − 1) survivors ≈ new connections each survivor must absorb, if perfectly uniform. At 500 servers that's ~4,000 per survivor — trivial if spread over a minute, an admission-limiter-triggering spike if it arrives in one second.
  • Handshake cost ratio: a fresh Noise handshake + auth round trip costs on the order of 100–1000× the CPU of routing one already-authenticated message (asymmetric crypto vs a RAM lookup and a socket write) — this ratio is why admission control targets new connections specifically rather than aggregate throughput.
  • Per-connection memory: a BEAM process handling one connection costs on the order of a few KB at rest (chapter 1's process-model numbers) — 2,000,000 connections is single-digit gigabytes of process overhead before ratchet state and queues are counted, which is why "just hold everyone's state in RAM" is viable at all on commodity hardware.
  • Keepalive/battery tradeoff: shorter keepalive intervals detect a dead connection (and thus a needed reconnect) faster, at the cost of more radio wake-ups and battery drain on mobile; longer intervals save battery but widen the window where a phone believes it's connected when the server has already reaped it. Mobile OS-level push wake (APNs/FCM) exists specifically to let the app not hold a socket open continuously in the background, trading a persistent connection for a best-effort wake signal.
  • Jitter's latency cost, quantified: with base=2s, cap=60s, a client on its 5th consecutive failed attempt (2·2^5=64s, capped to 60s) waits a uniformly random 0–60s before its next try — mean added latency 30s versus a naive immediate retry, in exchange for removing that client from the synchronized spike entirely.

ARC 11 · REAL-WORLD PRODUCTION

Named incidents: what actually goes wrong at this scale

Incident 1: the October 2021 Facebook/Meta BGP outage

On October 4, 2021, a configuration change during routine maintenance withdrew the BGP routes that told the rest of the internet how to reach Facebook's, Instagram's, and WhatsApp's DNS servers. With those routes withdrawn, DNS resolution for the entire family of services failed globally — clients could not even look up an IP to attempt a connection, let alone complete one. The outage lasted roughly six hours, and the compounding failure that made it so long is the more important lesson for this chapter: Meta's own internal tooling — the systems engineers would normally use to diagnose and fix exactly this kind of routing problem — depended on the same internal network that had just been cut off, and physical access to some datacenter equipment was itself controlled by systems that were now unreachable. The postmortem (published by Meta) explicitly cites this self-dependency as the reason recovery took hours rather than minutes: the tool you'd use to undo the mistake was a casualty of the mistake.

THE LESSON FOR THIS CHAPTER'S ARCHITECTURE

Every defense derived in §5–§8 — jitter, admission control, hot code loading — assumes clients can at least reach a chat server to attempt the handshake. BGP withdrawal is a failure mode one layer below all of them: it doesn't matter how well your reconnect storm is tamed if DNS resolution itself returns nothing. This is why serious operators maintain out-of-band recovery tooling and access paths that do not transit the same network the primary service depends on — the single hardest lesson from this incident, and one directly relevant to the "failure domains" discussion below.

Incident 2: the 2022 two-hour outage

WhatsApp experienced a roughly two-hour global outage in 2022 (reported by users and press across regions); as with most large-scale outages, the company's public statement was brief and did not disclose full root-cause detail. What is instructive is the reconnect dynamics of recovery itself, regardless of root cause: any outage affecting a large fraction of a multi-billion-device fleet simultaneously creates, at the moment service is restored, a reconnect wave far larger and more correlated than any single server's death — every affected client's app has, for the duration of the outage, been running its reconnect loop continuously. The full-jitter and admission-control machinery from §5 and §8 is not just a per-server safety net; it is precisely what stands between "service restored" and "service restored, then immediately re-broken by the recovery attempt."

Incident 3: bringing a billions-of-clients service back from zero

Recovering from a global outage is qualitatively different from recovering one dead server, because every client is simultaneously in retry mode, not just the ~2M that were attached to one dead node. The practical playbook — consistent with the mechanisms this chapter derived — is: bring capacity back online in waves rather than all at once (deliberately re-creating the staggered-restart pattern from §8, but for recovery instead of deploy), rely on each client's own jittered backoff to prevent every device from hammering the service in the same instant the DNS/network layer recovers, and closely watch admission-limiter rejection rates as the leading indicator of whether the fleet is genuinely stabilizing or about to be knocked over again by its own recovering user base — a "recovery reconnect storm" is a real, named risk in incident response for services at this scale, not a theoretical concern.

The full-jitter reconnect state machine, in the shape you'd actually implement it:

Erlangclient_reconnect.erl — the state machine, not just the formula
-record(backoff_state, {attempt = 0, base = 2000, cap = 60000}).  %% ms

on_disconnect(State = #backoff_state{attempt=A, base=B, cap=C}) ->
    Ceiling = min(C, B * math:pow(2, A)),
    Delay   = rand:uniform(trunc(Ceiling) + 1) - 1,   %% uniform[0, Ceiling] — FULL jitter
    timer:send_after(Delay, self(), {retry_connect}),
    State#backoff_state{attempt = A + 1}.

on_connect_success(State) ->
    State#backoff_state{attempt = 0}.   %% reset — a healthy session forgives past failures entirely

The server-side admission limiter — the token bucket that turns "accept everyone and hope" into "accept up to a provisioned rate, reject cheaply beyond it":

Erlangadmission_limiter.erl — token bucket gating new handshakes
-record(bucket, {tokens, capacity, refill_per_sec, last_refill}).

try_admit(Bucket = #bucket{tokens=T, capacity=Cap, refill_per_sec=R, last_refill=Last}) ->
    Now = erlang:monotonic_time(millisecond),
    Elapsed = (Now - Last) / 1000,
    Refilled = min(Cap, T + Elapsed * R),
    if
        Refilled >= 1 ->
            {admit,  Bucket#bucket{tokens = Refilled - 1, last_refill = Now}};
        true ->
            {reject, Bucket#bucket{tokens = Refilled, last_refill = Now}}   %% cheap: no fork, no handshake started
    end.

And the abuse-detection feature vector — every field derivable without reading a single byte of message content:

pseudocodebehavior_features.erl — metadata-only signals
features_for_account(Acct) ->
    #{
        registration_velocity   => accounts_from_same_ip_last_hour(Acct),
        send_rate               => messages_sent_per_minute(Acct),
        fanout_ratio            => distinct_recipients(Acct) / max(1, messages_sent(Acct)),
        unknown_recipient_ratio => sends_to_non_contacts(Acct) / max(1, messages_sent(Acct)),
        group_join_velocity     => groups_joined_last_hour(Acct),
        device_fingerprint_risk => shared_fingerprint_count(Acct),
        recipient_report_count  => user_reports_against(Acct)   %% the one signal that IS content-adjacent,
                                                                     but supplied by the recipient, not read by the server
    }.
WHY THE ENGINEERS CHOSE THIS SHAPE

Every field above is computable from connection and delivery metadata the server already necessarily possesses to route messages (who sent to whom, how often, from what device) — none of it requires decrypting payloads, which the server architecturally cannot do anyway (chapters 3–4). The one field that looks like an exception, user reports, is not the server reading content; it is the recipient voluntarily forwarding what they received, which is their own plaintext to share. This is why "metadata and behavior only" is not a policy promise layered on top of an otherwise-capable system — it is the only category of signal the architecture makes available at all.
