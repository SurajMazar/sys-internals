POSTGRESQL INTERNALS · CHAPTER 04

Heap Storage: Segments, FSM,
Visibility Map & TOAST

A table is not a file — it is a directory of 1 GiB segment files, addressed through a fork abstraction, tracked by a free-space map that is deliberately allowed to be wrong, guarded by a visibility map that is not allowed to be wrong, with an escape hatch — TOAST — for the one thing an 8 KB page can never hold: a value bigger than the page. This chapter takes the heap apart down to the struct fields and the C functions that read and write them.

ARC 01 · THE PROBLEM

A fixed-size page has to hold a variable-sized world

Every heap page in PostgreSQL is exactly BLCKSZ bytes — 8 KiB by default, fixed at compile time, uniform across the entire cluster. That single number collides with three facts about real data that have nothing to do with it: rows vary in width from a few bytes to gigabytes, tables grow from zero rows to billions, and most operating systems and filesystems have historically imposed their own ceilings on how large a single file is allowed to get. Heap storage is the layer that reconciles a rigid, fixed-size page abstraction with data that refuses to be rigid or fixed-size.

Unpack that into four separate problems, because the chapter's four subsystems each answer exactly one:

  • Where does a table's data physically live on disk? — a naming and addressing problem, solved by relfilenode-named files, segmented, and a fork abstraction (§7–8).
  • Where is there room for the next tuple? — a search problem: scanning every page to find one with enough free space does not scale, so PostgreSQL maintains a purpose-built index of free space, the Free Space Map (FSM) (§8).
  • Which pages can a reader skip entirely? — an optimization-and-correctness problem: certain scans (index-only scans, VACUUM) want to avoid touching the heap at all when every tuple on a page is already known-visible, which requires a durable, crash-safe record — the Visibility Map (VM) (§8).
  • What happens when one column's value is bigger than the whole page? — an overflow problem, solved by TOAST: transparently compressing and/or relocating oversized attributes into a side table, so the main heap tuple never has to hold more than a pointer (§8, §15).
WHY THIS MATTERS FOR THE NEXT 17 CHAPTERS

Almost everything downstream reads or writes through this layer. MVCC (chapter 5) stores its visibility metadata in the tuple header this chapter defines. VACUUM (chapter 6) exists largely to maintain the FSM and VM this chapter introduces. Indexes (chapters 7–8) point at heap TIDs whose page layout is fixed here. And every jsonb, text, or bytea column you have ever queried was, at some size threshold, silently rewritten by the TOAST machinery described in §8 and simulated in §15. Get the physical layer right in your head, and the rest of the course has somewhere solid to stand.

DEEP CONTEXT · WHY "TOAST"?

The name is a backronym — The Oversized-Attribute Storage Technique — picked to be memorable rather than descriptive, and it stuck the way "postmaster" did. What it names is not a single mechanism but a coordinated policy across four layers: the tuple's varlena header format (src/include/postgres.h), the per-attribute storage class chosen in pg_attribute, the compression codec, and a side table with the unglamorous name pg_toast.pg_toast_<oid>. You will meet all four in §8.

ARC 03 · NAIVE SOLUTION

Attempt #1: one giant file, no map, no size limit, no compression

Derive the architecture honestly, the way §3 of every chapter in this course does. The simplest possible heap implementation stores a relation as a single, unbounded file, appends new tuples wherever a linear scan finds room, and never compresses or relocates anything — a value is a value, inline, however big it is.

pseudo-Cnaive_heap.c — the strawman, annotated
typedef struct {
    char  data[VARIABLE];   /* one giant, unbounded file per table   */
} NaiveRelationFile;

BlockNumber
naive_find_free_page(Relation rel, Size needed)
{
    /* No map of free space exists anywhere.
     * The only way to find room is to ask every page. */
    for (BlockNumber b = 0; b < naive_nblocks(rel); b++)
    {
        Page p = naive_read_block(rel, b);   /* one syscall per candidate page  */
        if (naive_free_space(p) >= needed)
            return b;
    }
    return naive_extend(rel);       /* give up, grow the file            */
}

void
naive_insert(Relation rel, HeapTuple tup)
{
    /* Whatever size the row is, store it inline, verbatim.
     * A 500 MB text column becomes a 500 MB tuple.       */
    BlockNumber b = naive_find_free_page(rel, tup->t_len);
    naive_write_block(rel, b, tup);
}

This is, again, not a joke — it is exactly where you should start. It already gets the essential job done: data goes in, data comes out, and there is no separate structure to keep consistent with the heap, so nothing can drift out of sync with reality. Small tables on a friendly filesystem never notice a problem. Watch it degrade as both dimensions — table size and row size — grow past what a naive design can absorb.

ARC 04 · WHY IT FAILS

Three independent ceilings, and they all get hit

The naive design does not fail gracefully — it fails in three unrelated ways, each with a quantifiable breaking point, which is exactly why the final architecture needs three separate mechanisms rather than one fix:

  • Filesystem and OS file-size ceilings are real and historically low. Postgres's Unix ancestry runs through machines and filesystems where a single file could not exceed 2 GiB — 32-bit signed byte offsets cap a file at 2³¹−1 bytes, and several widely deployed 1990s filesystems (older ext2 configurations, some FAT variants, certain NFS servers) enforced limits at or below that line. A design that stores a multi-gigabyte table as one file simply cannot be created on such a system, full stop — no amount of query tuning fixes a file the filesystem refuses to extend.
  • Free-space search is O(n) in the number of pages, per insert. With no index of free space, finding room means reading candidate pages until one has enough. On a 10-million-page table (about 80 GB at 8 KB pages) with most pages full, an insert might scan thousands of pages before finding space near the end — and every one of those reads is a real read() syscall or, worse, a buffer-pool miss. Do that for every one of n inserts and the aggregate cost trends toward O(n²) exactly when you can least afford it: heavy insert load into a nearly-full table.
  • A row bigger than a page cannot exist, arithmetically. BLCKSZ is 8192 bytes; subtract the page header (24 bytes), the line pointer array, and per-tuple overhead, and the realistic ceiling for a single heap tuple sits close to MaxHeapTupleSize, a few bytes over 8 KB. A text or jsonb value of 50 KB is not a performance problem under the naive design — it is a hard impossibility. There is no "just make the page bigger": BLCKSZ is fixed cluster-wide at compile time, shared by every table, every index, and the buffer pool's slot arithmetic.
THE ARITHMETIC THAT FORCES THE REDESIGN

Three independent constraints, three independent fixes: the filesystem ceiling forces segmentation (§7–8), the O(n) free-space search forces a maintained map (§8), and the fixed page size forces an out-of-line storage mechanism for oversized values (§8, §15). None of the three problems can be solved by tuning the other two — you cannot compress your way out of a 2 GiB filesystem ceiling, and you cannot segment your way out of an O(n) free-space scan. §5 walks each candidate fix and eliminates the ones that don't survive contact with a multi-terabyte production table.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three problems, three families of candidate fix

For the file-size ceiling: pick a segment size and split

The candidates here are narrow: either raise the theoretical file-size limit by relying on a 64-bit-only filesystem (rejected — Postgres must run on whatever filesystem the operator already has, not the one you wish they had), or split each relation's storage into multiple, independently sized files under one logical identity. PostgreSQL takes the second path: a compile-time constant, RELSEG_SIZE (src/include/pg_config_manual.h), fixes the maximum size of one segment file at 131072 blocks — exactly 1 GiB at the default 8 KiB BLCKSZ — comfortably under every historical filesystem ceiling with a wide safety margin, while keeping the segment count for even a multi-TB table in the low thousands.

For free-space search: cache a hint, or build a real index

Step through the candidates the project actually tried, in order, because the history matters here more than usual — PostgreSQL shipped and later removed an intermediate design:

Free-space tracking: three designs, one survivorSTEP-BY-STEP

For oversized values: reject, chain, or relocate

Three shapes were on the table: (A) reject rows above a hard limit and force applications to use a separate, explicitly-managed large-object API (Postgres actually shipped this first — the pg_largeobject system, still present, chunked into 2 KB pieces manually addressed by lo_import/lo_read); (B) let a row physically span multiple heap pages, chained together (the path Oracle and SQL Server take for very wide rows); (C) keep every heap tuple confined to one page by transparently compressing and/or relocating individual attributes — not whole rows — into a side table, leaving an in-tuple pointer behind. PostgreSQL's answer, arriving in 7.1 (2001), is (C): TOAST. It is worth sitting with why (A) and (B) were rejected, because the reasons are structural, not incidental:

  • (A) large objects work, but they are not transparent: every application has to know a column is "large" and use a different API (lo_import()/lo_export(), large-object file descriptors) instead of ordinary SELECT/UPDATE. That breaks the relational model's promise that a column is a column regardless of size, and it pushes the size-awareness burden onto every client, forever.
  • (B) row chaining across pages keeps ordinary SQL working, but it means the heap access method must handle multi-page tuples everywhere — every scan, every lock, every WAL record for a chained row now spans pages, and pages themselves can no longer be reasoned about independently. It also does nothing for the case that dominates in practice: a handful of oversized columns in an otherwise narrow row, where chaining the entire row is wasteful when only one attribute is the problem.
THE CLINCHING ARGUMENT: PER-ATTRIBUTE, NOT PER-ROW

TOAST's key design decision is granularity: the unit of relocation is one attribute value, not one row. A row with nine narrow columns and one 500 KB jsonb column keeps the nine columns inline, in the heap page, cheap to scan — and only the one oversized value is compressed and/or pushed into pg_toast.pg_toast_<oid>. Every other subsystem — the buffer manager, the heap scan, the line-pointer array — keeps its "one tuple fits in one page" invariant, because by construction it now always does: the in-tuple representation of even a gigabyte-sized value is an 18-byte pointer struct. §8 shows exactly what that pointer contains.

ARC 06 · WHY THAT STILL HURTS

The bill for segments, a maintained map, and a compress-and-relocate policy

Each winning design in §5 trades the original problem for a new, smaller, but very real cost. Being precise about where each cost comes from is what separates "the FSM sometimes misses free space" from actually knowing why, and what you can and cannot do about it:

  • Segmentation adds an indirection to every I/O. Reading block number N is no longer "seek to N × BLCKSZ in one file" — it is "compute N / RELSEG_SIZE to pick the segment file, N % RELSEG_SIZE for the offset within it, and possibly open a file descriptor the storage manager hasn't cached yet." Cheap arithmetic, but it is arithmetic and an open() that a single-file design would not need, on the hottest path in the system.
  • A maintained free-space map can be, and is designed to be, wrong. The FSM is a cache of approximate free-space categories, not exact byte counts, and — critically — its contents are not WAL-logged. A crash can leave it stale relative to the heap; a concurrent transaction that hasn't committed yet can make a page look free when it isn't really available yet. The system tolerates this because the failure mode is bounded: a wasted probe of one page, not corruption. But it means the FSM can never be the sole source of truth about anything, only a hint that saves an O(n) scan most of the time.
  • The visibility map inverts that tradeoff — it must never lie, which is precisely why it costs more to maintain: every bit it sets must be WAL-logged, and every UPDATE/DELETE that touches a page must synchronously clear both of its bits before making the page's data inconsistent with what the bit claims. Get this wrong and index-only scans return rows that were deleted, not "slightly stale performance" — a correctness bug, not an efficiency one. §11 covers a real historical incident from exactly this class of failure.
  • TOAST buys page-size independence by taxing every access to a toasted value. Reading a toasted column means, at minimum, following a pointer into a second relation (pg_toast.pg_toast_<oid>) and its index, reassembling ~2000-byte chunks, and — if the value was compressed — decompressing the whole thing before you can read even one byte of it. An UPDATE that changes one unrelated narrow column on a row with a 200 KB toasted jsonb value does not touch the toasted value at all (TOAST pointers are copied forward, not re-toasted, when the underlying value is unchanged) — but an UPDATE that touches the big column itself re-runs the entire compress/externalize algorithm from scratch and writes an entirely new set of chunk rows, because MVCC (chapter 5) never mutates a tuple in place.
THE PATTERN, STATED ONCE

Every side structure in this chapter buys a fast path for the common case by accepting a slow, expensive, or care-must-be-taken path for the uncommon one. Segments make huge tables possible at the cost of one division per I/O. The FSM makes inserts fast at the cost of being allowed to guess wrong. The VM makes index-only scans and vacuum skip work at the cost of a strict, WAL-logged clearing discipline. TOAST makes "just declare a text column, no size limit" possible at the cost of every access to a big value paying a detour through a second table. None of these are free lunches — they are all different places to put the bill.

WHY THE FORK, NOT A SEPARATE FILE PER FEATURE

An earlier, simpler design could have given each table one file for data and hard-coded a second, differently-named file for free-space tracking. Instead PostgreSQL generalized: ForkNumber (src/include/common/relpath.h) is an enum — MAIN_FORKNUM, FSM_FORKNUM, VISIBILITYMAP_FORKNUM, INIT_FORKNUM — and every storage-manager call (smgrread, smgrwrite, smgrextend, in storage/smgr/smgr.c) takes a fork number alongside the relation and block number. That one abstraction is what let the project add the visibility map in 8.4 without touching a single call site that only cared about the main fork — it just became "one more fork number" to an addressing scheme built to accept it.

ARC 08 · INTERNAL IMPLEMENTATION

The addressing math, the two maps, and the tuple header

Four mechanisms, in the order data actually flows through them: (a) how a block number becomes a file and an offset, (b) the Free Space Map's tree-in-a-page search, (c) the visibility map's two bits and its WAL-logging discipline, (d) the TOAST decision algorithm and the varlena header formats that make it possible.

(a) From (relation, fork, block) to a byte offset in a real file

Every relation's identity for storage purposes is not its OID but its relfilenode (renamed to relfilenumber inside the RelFileLocator struct as of PostgreSQL 16, which also renamed the older RelFileNode). A file's path is built from three pieces — tablespace, database OID, relfilenode — plus a fork suffix and a segment number: base/<dbOid>/<relfilenode> for the main fork's first segment, ..._fsm for the FSM fork, ..._vm for the visibility map, ..._init for the init fork (unlogged tables only), and .1, .2, … appended once a fork exceeds RELSEG_SIZE blocks. (b) The Free Space Map: a binary tree of one-byte hints, stored in pages

The FSM (src/backend/storage/freespace/freespace.c, fsmpage.c) does not store byte counts — it stores one-byte categories, FSM_CATEGORIES = 255 of them, mapped to approximate free-byte ranges by fsm_space_avail_to_cat() and back by fsm_space_cat_to_avail(). Coarsening the value to one byte is deliberate: a search only ever needs "does this subtree contain a page with roughly enough room," never an exact count, and one byte per page reference is what lets an entire FSM page (FSMPageData) hold a complete binary tree covering thousands of heap pages. Each non-leaf node stores the maximum category of its two children, so a search never has to look at more than one node per level: start at the root, and if a child's stored maximum is at least the requested category, descend into it — otherwise there is provably no page with enough space in that whole subtree, and the search backs out. Large relations get more than one FSM page, arranged in their own tree of FSM pages — leaf FSM pages summarizing ranges of heap blocks, and one or two levels above summarizing ranges of FSM pages — so even a relation with millions of pages resolves a free-space search in a handful of page reads.

DELIBERATELY NOT DURABLE

FSM pages are ordinary pages in an ordinary fork, but their contents are not WAL-logged the way heap or index contents are — RecordPageWithFreeSpace() updates the in-memory buffer and marks it dirty, full stop. A crash can lose recent FSM updates entirely; the map is rebuilt lazily as VACUUM and ordinary inserts re-populate it, and VACUUM's FreeSpaceMapVacuum() pass exists specifically to reconcile it against reality. This is the correct tradeoff only because being wrong here costs a wasted page probe, never a wrong answer — contrast with (c).

(c) The Visibility Map: two bits that must never lie

The VM (src/backend/access/heap/visibilitymap.c) stores exactly two bits per heap page: VM_ALL_VISIBLE and, since PostgreSQL 9.6, VM_ALL_FROZEN. ALL_VISIBLE means every tuple on the page is visible to every possible snapshot — no concurrent transaction could still need to see an older, now-invisible version — which is exactly the condition an index-only scan needs before it can skip the heap fetch entirely and trust the index tuple alone. ALL_FROZEN means every tuple's XID has additionally been frozen (chapter 6), letting VACUUM skip the page even during an anti-wraparound sweep. Only VACUUM sets these bits, after confirming the condition holds for every tuple on the page — and setting the bit is itself WAL-logged, because an incorrectly-set ALL_VISIBLE bit is not a performance bug, it is a wrong query result.

The other half of the contract runs in the opposite direction: any UPDATE or DELETE that dirties a page must clear both bits for that page before the change becomes visible — a fresh dead tuple on the page immediately violates "every tuple is visible to every snapshot." heap_update() and heap_delete() call visibilitymap_clear() as part of the same critical section that modifies the page, so the two never drift apart even across a crash.

(d) TOAST: varlena headers, storage classes, and the compress-then-externalize algorithm

Every variable-length value in PostgreSQL is a struct varlena (src/include/postgres.h): conceptually a length word followed by data, but with three physical encodings layered on top so that short values never pay a 4-byte tax and large values never have to be inline at all:

  • 1-byte header, inline, uncompressed — the top bit of the first byte marks this "short" form; the remaining seven bits give the total length (header included), so it covers values up to 126 payload bytes with only one byte of overhead. Unaligned, because paying for alignment on a value this small isn't worth it.
  • 4-byte header, inline — a full 4-byte length word, with a flag bit distinguishing plain uncompressed data from compressed data (in which case a second 4-byte field records the pre-compression size, so decompression knows how large a buffer to allocate).
  • 1-byte header, "external" — a special marker (all-bits pattern reserved for this case) followed by a one-byte tag identifying what kind of external datum this is — an on-disk TOAST pointer (VARTAG_ONDISK) being the common case, with other tags used for in-memory "expanded" object representations unrelated to disk storage.

An on-disk TOAST pointer is a small fixed struct, varatt_external: va_rawsize (the original, uncompressed length), va_extinfo (packing the stored size together with a compression method identifier — pglz or, since PostgreSQL 14, lz4 — so a value keeps working even if the table's default_toast_compression changes later), va_valueid (the OID grouping this value's chunks in the toast table) and va_toastrelid (which toast relation to look in). That whole struct is on the order of 18 bytes — the entire "cost" of storing a value of any size, once it's external, inside the main heap tuple.

Every attribute is declared with one of four storage classes (pg_attribute.attstorage), and the class determines what the toast algorithm is allowed to do to it:

WHY COMPRESS BEFORE EXTERNALIZING, NOT AFTER

It would be simpler to always externalize first (move the biggest attribute out, unconditionally) and compress later if needed. The actual order is compress-first because compression is far cheaper than an extra table's worth of I/O: if compressing the single biggest compressible attribute gets the tuple under the threshold, the row never touches pg_toast.pg_toast_<oid> at all — no second relation, no second index, no extra WAL for chunk rows. Only when compression alone can't close the gap does the algorithm pay for external storage, and even then it compresses before moving out where the storage class allows it, so the toast table holds compressed bytes, not raw ones, whenever possible.

ARC 09 · TRADEOFFS

Every large-value store solves this; almost none solve it the same way

Segmentation is close to universal — the interesting divergence is in how each system handles free-space tracking and oversized values:

SYSTEMLARGE-VALUE STRATEGYWHAT THEY BOUGHTWHAT THEY PAID
PostgreSQLPer-attribute TOAST: compress inline, else relocate to a side table; FSM tree for free space page-size independence narrow rows stay narrow detour + decompress on read whole-value rewrite on any change
MySQL / InnoDBRow formats (DYNAMIC/COMPRESSED) store a prefix in-page and the remainder in off-page overflow pages; free space tracked via per-extent bitmaps clustered index keeps PK-adjacent data together overflow chain length affects read cost page compression is a separate, extra-cost feature
OracleRow chaining/migration across blocks for wide rows; dedicated LOB segments with their own chunked storage for CLOB/BLOB tunable chunk size per LOB row migration adds a hop to every access of a migrated row
SQLiteOverflow pages: a value too big for one page spills into a singly-linked chain of overflow pages; no separate free-space map — just a page-level freelist extremely simple implementation chain traversal is O(chunks), no random access into a large value
RocksDB / Cassandra (LSM)Values stored inline in sorted string tables (SSTables); no in-place free-space tracking at all — space is reclaimed by background compaction, not by tracking holes sequential writes, no in-place free-space bookkeeping large values bloat every level they pass through until compacted read amplification across levels

Read this as more proof-by-exhaustion: a fixed page size and unbounded value sizes are fundamentally in tension, and every serious storage engine pays for the mismatch somewhere — in extra I/O per access (Postgres, InnoDB), in a second storage form entirely (Oracle's LOB segments), in chain-traversal cost (SQLite), or in deferred, batch-amortized reclamation instead of an index at all (LSM engines). PostgreSQL's specific bet — attribute-level granularity plus a strict separation between the "must never lie" visibility map and the "allowed to lie" free-space map — is unusually explicit about which invariants are load-bearing and which are merely helpful hints, a distinction worth stealing regardless of which engine you build.

ARC 10 · PERFORMANCE CHARACTERISTICS

The costs you can predict before you benchmark

  • Segment addressing: O(1) — one integer division and one modulo per I/O (blocknum / RELSEG_SIZE, blocknum % RELSEG_SIZE). The only variable cost is whether the target segment's file descriptor is already open in the storage manager's cache; a cold open() is the dominant term, not the arithmetic.
  • FSM search: O(log n) in the number of heap pages, and in practice bounded by a small constant — the tree is rarely more than three levels deep even for huge tables, and the upper levels are tiny and stay resident in the buffer pool, so a search is typically one or two real page reads.
  • Visibility map check: O(1) — a single bit test replaces an entire heap page fetch (8 KB) plus per-tuple visibility checks against the current snapshot. On a table where most pages are all-visible, this is the difference between an index-only scan touching kilobytes of index data and touching the full row width for every match.
  • TOAST read cost is bimodal, and the discontinuity is the point: reading an inline value costs nothing extra; reading an out-of-line, uncompressed value for a substring() can cost as little as O(range requested) — toast_fetch_datum_slice() in src/backend/access/common/detoast.c computes exactly which ~2000-byte chunks overlap the requested byte range and fetches only those, via an index scan on (chunk_id, chunk_seq). Reading a compressed value — inline or external — is O(size) regardless of how much of it you actually want, because pglz and LZ4 are both byte-stream compressors with no seek points: there is no way to jump to "byte 50,000" of a compressed stream without decompressing everything before it.

CACHE AND DISK ACCESS PATTERN

The main heap fork is accessed with the access pattern of your query — sequential for a seq scan, random for index lookups. The FSM and VM forks, by contrast, are small relative to the heap (roughly one FSM byte per heap page, two VM bits per heap page) and are read repeatedly by every inserting backend and every VACUUM, which pushes them toward the hottest part of the buffer pool almost by accident — they are exactly the kind of small, hot, frequently-reread structure that benefits disproportionately from a healthy cache hit ratio, and their small size is precisely why they can afford to stay resident while the heap itself is far larger than shared_buffers.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents this chapter's mechanics explain completely

Incident 1: mass DELETE, then bloat that VACUUM alone doesn't fix fast enough

A nightly job deletes 80% of a table's rows and reinserts fresh data in the same transaction window. Disk usage does not shrink — and worse, new inserts keep extending the relation with brand-new pages instead of reusing the space the delete just freed. The mechanism: a DELETE only marks tuples dead; it does not update the FSM, and it does not shrink the file. Only VACUUM reclaims dead tuples into free space and calls FreeSpaceMapVacuum() to make that space visible to future inserts. If autovacuum hasn't caught up — cost-limited, or competing with the same I/O the reinsert job is generating — every new tuple's GetPageWithFreeSpace() lookup finds a stale, still-full-looking FSM and the relation grows instead of recycling. Fix, in order of leverage: run an explicit, cost-limit-free VACUUM (not FULL — that rewrites the whole table and takes an exclusive lock; plain VACUUM reclaims space and refreshes the FSM without blocking readers) between the delete and reinsert phases; raise autovacuum_vacuum_cost_limit for this table; and, if the pattern is routine, consider whether the delete-and-reinsert should be a TRUNCATE instead, which drops the relfilenode entirely rather than fighting the FSM at all.

Incident 2: a major-version upgrade and a visibility-map format change

PostgreSQL 9.6 changed the on-disk visibility map format — from one bit per heap page to two (adding ALL_FROZEN) — which is exactly the kind of change that turns "just copy the data files" into a correctness incident. A raw file-level copy across that boundary (skipping pg_upgrade or a logical dump/reload, which know about the format change and rebuild the map) would have every old single-bit entry misread under the new two-bit layout, potentially reporting pages as all-visible or all-frozen when they are neither. Symptom: an index-only scan silently skips heap fetches it should have made, and returns stale or simply wrong rows — with no error, no log line, nothing to alert on. This is precisely why cross-major-version upgrades in PostgreSQL are gated through pg_upgrade (which handles fork-format transitions explicitly) or dump/reload (which never carries old fork files forward at all) rather than any filesystem-level shortcut, and why the release notes for a version that changes an on-disk fork format call it out as a hard compatibility break, not a footnote.

Incident 3: one small update to a huge JSONB column, and the I/O bill that follows

An application stores a 300 KB jsonb "settings blob" per user and updates one nested key on every request. Query plans look fine, indexes are used correctly, and yet write I/O and toast-table growth are far higher than the logical size of the change suggests. The mechanism is structural, not a misconfiguration: MVCC (chapter 5) never mutates a tuple in place, and TOAST has no concept of a partial update — changing one byte inside a toasted value means the whole new value re-runs heap_toast_insert_or_update() from scratch, is (re)compressed, and is (re)chunked into an entirely new set of rows in pg_toast.pg_toast_<oid>, while the old chunk rows become dead tuples waiting on VACUUM. A high-frequency small-field update against a large TOASTed blob is, from the storage layer's point of view, indistinguishable from replacing the entire blob every time. Fixes: normalize the frequently-updated fields out of the large JSON blob into narrow columns of their own (only they get rewritten per update, and TOAST never gets involved); if that's impractical, tune the toast table's own autovacuum settings (ALTER TABLE ... SET (toast.autovacuum_vacuum_scale_factor = ...), since a toast table's bloat characteristics can differ wildly from its parent's); and measure, rather than assume, whether the JSONB column actually needs to cross the ~2 KB toast threshold at all — a smaller, more normalized document might stay inline and avoid the whole detour.

The FSM's tree search, simplified from the real structure but faithful to the algorithm — descend while a child's stored maximum category is large enough, back out the instant it isn't:

Cfsmpage.c — fsm_search_avail(), simplified
int
fsm_search_avail(Page page, uint8 min_cat, bool advancenext)
{
    int nodeno = 0;                     /* start at the root of the tree-in-a-page */
    FSMPageData *fsmpage = (FSMPageData *) PageGetContents(page);

    if (fsmpage->fp_nodes[0] < min_cat)
        return -1;    /* root already tells us: nothing here is big enough */

    while (!fsm_is_leaf(nodeno))
    {
        int left  = fsm_left_child(nodeno);
        int right = fsm_right_child(nodeno);

        /* Each non-leaf slot caches max(left, right) — one comparison
         * per level is enough to know which subtree can possibly help. */
        if (fsmpage->fp_nodes[left] >= min_cat)
            nodeno = left;
        else if (fsmpage->fp_nodes[right] >= min_cat)
            nodeno = right;
        else
            return -1;     /* both children too small — dead end, caller tries
                                 * the next FSM page or extends the relation      */
    }
    return fsm_leaf_to_slot(nodeno);   /* leaf index → a real heap BlockNumber */
}

The visibility map's set path — note the WAL record, which the FSM's equivalent update never takes:

Cvisibilitymap.c — visibilitymap_set(), simplified
void
visibilitymap_set(Relation rel, BlockNumber heapBlk, Buffer heapBuf,
                  XLogRecPtr recptr, Buffer vmBuf, TransactionId cutoff_xid,
                  uint8 flags)
{
    /* Unlike an FSM update, this runs inside a critical section and,
     * outside of recovery, WRITES ITS OWN WAL RECORD before the bit
     * is considered set — because a lost VM bit after crash is merely
     * a missed optimization, but a bit that SURVIVES a crash while
     * claiming ALL_VISIBLE for a page that recovery just changed
     * would be a silently wrong answer to every index-only scan.     */
    if (RelationNeedsWAL(rel) && !InRecovery)
        recptr = log_heap_visible(rel, heapBuf, vmBuf, cutoff_xid, flags);

    PageSetLSN(BufferGetPage(vmBuf), recptr);
    vm_set_bits(vmBuf, heapBlk, flags);   /* ALL_VISIBLE and/or ALL_FROZEN */
}
WHY THE DEVELOPERS WROTE IT THIS WAY — TWO CHOICES TO STEAL

1. Durability is a per-structure decision, not a blanket policy. The FSM and the VM live in structurally identical forks — same fork abstraction, same page format, same buffer pool — and yet one is WAL-logged and one deliberately is not. The project didn't pick a durability policy for "auxiliary forks" as a category; it asked, for each one, "what does it cost if this is wrong after a crash?" and let the answer (a wasted probe vs. a wrong query result) decide. 2. Compress before you pay for a second relation. toast_tuple_try_compression() runs before toast_save_datum() ever gets a chance, for exactly the reason §8's callout gives: a CPU-bound compression pass that avoids an entire extra table and its index is close to free by comparison.
