STEP 01 · SETUP

Three brokers, KRaft, one command

A real replicated cluster — not a single broker. Replication factor 3 is what makes the ISR, leader-election, and durability experiments meaningful. You need Docker with Compose v2 and about 4 GB of free RAM.

WHY THREE BROKERS AND NO ZOOKEEPER

A single broker can't demonstrate replication, ISR shrink, leader election, or min.insync.replicas — which is most of what the theory chapters are about. And ZooKeeper is gone as of Kafka 4.0 (ch.6), so this lab runs KRaft with each node in combined broker,controller mode. That's fine for a lab; production separates the roles.

THE LISTENER RULE, STATED ONCE

A broker tells clients where to reach it via advertised.listeners — and the client then connects to that address, not the one it originally dialed. So a container asking on the Docker network must be told kafka1:9092, while your laptop must be told localhost:19092. One listener can't serve both. If you ever see a client connect successfully and then hang or fail on the very next request, this is why: bootstrap worked, then the client followed a bad advertised address.

Aliases you'll use constantly

Every Kafka CLI tool lives in /opt/kafka/bin inside the containers. Define these once.

bash
# Run any kafka-*.sh tool against the cluster:  K topics --list
K() { docker exec -i kafka1 /opt/kafka/bin/kafka-"$1".sh --bootstrap-server localhost:9092 "${@:2}"; }

# Interactive variant (for console producer/consumer):  KT topics --list
KI() { docker exec -it kafka1 /opt/kafka/bin/kafka-"$1".sh --bootstrap-server localhost:9092 "${@:2}"; }

# A shell inside a broker (for looking at files on disk)
KSH() { docker exec -it "${1:-kafka1}" bash; }

From your host, the bootstrap string is localhost:19092,localhost:29092,localhost:39092. The web UI is at localhost:8080.

Teardown

bash
docker compose down          # stop, keep the log dirs
docker compose down -v       # stop and DELETE all data — full reset

Several experiments deliberately damage the cluster. docker compose down -v && docker compose up -d returns you to a clean cluster in well under a minute. Use it freely.

Troubleshooting

SYMPTOMCAUSE & FIX
Client connects then times out on every request Advertised-listener mismatch. From the host you must use the EXTERNAL ports (19092/29092/39092); from inside a container use kafka1:9092. Check with docker exec kafka1 env | grep ADVERTISED.
InconsistentClusterIdException A log dir was formatted with a different CLUSTER_ID. This happens if you change the ID after first boot. docker compose down -v and start again.
Quorum never forms / node stuck starting KAFKA_CONTROLLER_QUORUM_VOTERS must list every node with matching KAFKA_NODE_IDs and the controller port. One typo and the quorum can't elect.
Brokers OOM or restart-loop Three JVMs plus the UI on a small Docker VM. KAFKA_HEAP_OPTS is capped at 512 MB each; raise Docker Desktop's memory to ≥ 4 GB.
Port already allocated Change the host side of the mapping only (e.g. "19192:19092") and update the EXTERNAL advertised port to match — they must agree.
NOT_ENOUGH_REPLICAS on a fresh cluster Expected if a broker is still starting: min.insync.replicas=2 means at least two must be in the ISR. Wait for all three, then retry.

STEP 04 · PRODUCTION BEST PRACTICES

A config cookbook where every number has a reason

Topic design — the decisions you can't undo

DECISIONGUIDANCEMECHANISM & CONSEQUENCE
partition counttarget throughput ÷ per-partition throughput, then round up; plan for 2–3× growth Partitions bound consumer parallelism — a group can never have more active consumers than partitions. But each costs file handles, controller metadata, a replication fetch entry, and turns sequential disk writes into scattered ones (ch.10, ch.13). You can add partitions but never remove them, and adding breaks key→partition affinity, so a key that lived on partition 2 may move to 5 and its ordering guarantee with prior messages is lost.
replication.factor3 Survives one broker loss while still satisfying min.insync.replicas=2. RF=2 means any single failure blocks acks=all writes.
min.insync.replicas2 With acks=all, this is what actually delivers durability (ch.5). acks=all with min.insync=1 is a trap: it degrades silently to single-copy durability when the ISR shrinks.
key selectionthe entity whose ordering you need Ordering is per-partition, and the key picks the partition via murmur2. Choose the key = the ordering domain (account id, device id). Beware low-cardinality keys — 4 distinct keys over 12 partitions leaves 8 idle.
cleanup.policydelete for events, compact for state Delete = a time-ordered stream of facts. Compact = a replayable changelog / table (ch.11). Compacted topics need bounded key cardinality or the cleaner's offset map can never keep up.
unclean.leader.electionfalse (default) True trades acknowledged data for availability — a stale replica can become leader and committed records vanish (experiment 6).

Producer

propertiesa durable, efficient default
acks=all                        # wait for the full current ISR (ch.5)
enable.idempotence=true         # default since 3.0; dedups retries broker-side
max.in.flight.requests.per.connection=5   # max that still preserves ordering w/ idempotence
retries=2147483647              # bounded in practice by delivery.timeout.ms
delivery.timeout.ms=120000      # the ONE timeout that actually bounds a send()
request.timeout.ms=30000

linger.ms=10                    # 10ms of latency buys much larger batches (ch.4)
batch.size=65536                # 64KB; raise with linger for high throughput
compression.type=zstd           # best ratio; lz4 if CPU-bound, snappy for legacy
buffer.memory=67108864          # send() blocks when this fills — watch for it

linger.ms=0 does not mean "no batching" — batches still form while a request is in flight. But a small non-zero linger is usually free throughput: it costs bounded latency and can multiply batch size several-fold under moderate load (experiment 3).

Consumer

properties
enable.auto.commit=false        # commit after processing, deliberately (ch.8)
isolation.level=read_committed  # if any producer to this topic is transactional
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
group.instance.id=   # static membership: no rebalance on restart

max.poll.records=500            # MUST satisfy: records × per-record time < max.poll.interval.ms
max.poll.interval.ms=300000     # detects "processing is stuck"
session.timeout.ms=45000        # detects "the process died"
heartbeat.interval.ms=3000      # ~1/3 of session.timeout.ms
auto.offset.reset=earliest      # 'latest' silently skips data after an offset expiry
THE THREE TIMEOUTS, AND WHAT EACH ACTUALLY DETECTS

session.timeout.ms — the heartbeat thread stopped, so the process is dead or partitioned. max.poll.interval.ms — heartbeats continue but poll() hasn't been called, so processing is stuck. heartbeat.interval.ms — how often the background thread checks in. Confusing these is the root of most rebalance-storm misdiagnosis: if your consumer is being evicted while the process is clearly alive, it's max.poll.interval.ms, and the fix is fewer records per poll or faster processing — not a bigger session timeout.

Broker & cluster

  • Heap ~6 GB, no more. Kafka deliberately keeps no application cache — the OS page cache does the work (ch.10). A large heap buys nothing and costs GC pauses long enough to drop the broker out of the ISR (experiment 5, incident 1).
  • Give the machine RAM, not the JVM. Page cache should comfortably hold the tail of every active partition, because tail-reading consumers then never touch disk.
  • One log dir per physical disk, and keep partitions-per-broker in the low thousands — beyond that, leader election and recovery time grow and sequential I/O degenerates toward random.
  • Never set log.flush.interval.messages unless you know exactly why. Kafka's durability model is replication, not fsync (ch.10); forcing flushes trades a large throughput loss for a guarantee replication already gives you.
  • Leave auto.create.topics.enable=false in production. Auto-created topics get cluster defaults, which is how you end up with RF=1 topics holding real data.

Anti-patterns and their specific damage

ANTI-PATTERNWHAT IT COSTS
One transaction per recordsevere Every transaction writes markers to each partition plus two coordinator log writes. Per-record transactions can cut throughput by an order of magnitude (ch.9). Batch hundreds of records per transaction.
acks=all with min.insync.replicas=1Reads as durable, behaves as single-copy the moment the ISR shrinks. The two settings only mean something together.
Auto-commit for anything that mattersCommits offsets for records that may not have finished processing — silent data loss on crash (experiment 9).
Very many tiny messages, no batchingPer-record overhead dominates: request headers, CRCs, network round trips. Batching is where nearly all of Kafka's throughput comes from.
Unbounded key cardinality on a compacted topicThe cleaner's offset map can't hold all distinct keys, so compaction processes a shrinking fraction per pass and never catches up (experiment 12).
Using Kafka as a databaseNo random access by key, no queries, no updates in place. A compacted topic is a changelog you materialize elsewhere — not a store you read from.
Adding partitions to a keyed topic in productionRehashes every key. Messages for a given key land on a new partition, breaking ordering against everything already written.
Consumers with heavy processing inside poll()Breaches max.poll.interval.ms → eviction → rebalance → the remaining consumers get more load → cascade (experiment 8).

5.1 · Rolling restart with zero data loss

  
The rule: one broker at a time, and never start the next until under-replicated partitions is back
  to zero. Breaking that rule is how a routine restart becomes an outage.

  
bash


urp() { docker exec kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
          --describe --under-replicated-partitions | wc -l; }

for b in kafka1 kafka2 kafka3; do
  echo "== restarting $b =="
  docker restart "$b"                      # controlled.shutdown.enable=true by default:
                                           # the broker migrates its leadership first
  until [ "$(urp)" -eq 0 ]; do
    echo "   under-replicated: $(urp) — waiting"; sleep 5
  done
  echo "   $b healthy, URP=0"
done

# afterwards, restore balanced leadership
docker exec kafka1 /opt/kafka/bin/kafka-leader-election.sh \
  --bootstrap-server localhost:9092 --election-type PREFERRED --all-topic-partitions

  
Verify: URP is 0 and leadership is spread across all three brokers.
  Rollback: none needed — if a broker fails to rejoin, stop the rollout and investigate before touching another.


  
5.2 · Diagnosing consumer lag — the decision tree

  
bash


K consumer-groups --describe --group my-group

  
Read the output as a decision tree rather than a number:

  
    
    
  1. Lag concentrated on a few partitions? → key skew. One key (or a few) dominates. Fix the key, or accept the hot partition and scale it separately.
    2. 
    
  2. Lag even across all partitions, and CONSUMER-ID is populated? → consumers are simply too slow. Compare production rate against consumption rate; add consumers up to the partition count. Beyond that, add partitions.
    3. 
    
  3. Some partitions have no CONSUMER-ID? → fewer consumers than partitions, or a rebalance is in progress. If it never resolves, the group is stuck rebalancing — see 5.3.
    4. 
    
  4. Lag growing while consumers are idle? → they're blocked downstream (a database, an API), not on Kafka. The fix is not a Kafka fix.
    5. 
    
  5. Consumers at 100% CPU? → decompression or deserialization cost. Check the compression codec and payload size.
    6. 
  

  
bash


# Emergency: skip the backlog entirely (accepting data loss) — group must be STOPPED
K consumer-groups --group my-group --topic orders --reset-offsets --to-latest --execute

# Or rewind to a point in time
K consumer-groups --group my-group --topic orders \
  --reset-offsets --to-datetime 2026-07-31T09:00:00.000 --execute


  
5.3 · A group is stuck rebalancing

  
    
    
  1. Confirm: K consumer-groups --describe --group g --state shows PreparingRebalance or CompletingRebalance persistently.
    2. 
    
  2. Read a consumer's log for "member ... has failed, removing it from the group" — the reason field tells you whether it was a session timeout (process dead) or a poll-interval breach (processing stuck).
    3. 
    
  3. If poll-interval: reduce max.poll.records and redeploy. This is the fix in the large majority of cases.
    4. 
    
  4. Adopt CooperativeStickyAssignor so future rebalances stop the world only for the partitions that actually move (experiment 8).
    5. 
    
  5. Add group.instance.id so rolling deploys don't trigger a rebalance at all.
    6. 
  


  
5.4 · Replacing a dead broker

  
    
    
  1. Start the replacement with the same node.id and an empty log dir. It will re-replicate its partitions from the current leaders.
    2. 
    
  2. Watch progress: K topics --describe --under-replicated-partitions should shrink steadily to zero.
    3. 
    
  3. Throttle the catch-up so it doesn't starve live traffic:
      K configs --alter --entity-type brokers --entity-name 3 --add-config follower.replication.throttled.rate=52428800
    4. 
    
  4. When URP hits zero, remove the throttle and run a preferred-leader election.
    5. 
  


  
5.5 · Reassigning partitions (adding a broker)

  
bash


# 1. Describe the current placement and generate a proposal
echo '{"topics":[{"topic":"orders"}],"version":1}' > /tmp/t.json
docker cp /tmp/t.json kafka1:/tmp/t.json
K reassign-partitions --topics-to-move-json-file /tmp/t.json \
  --broker-list "1,2,3,4" --generate

# 2. Save the proposed plan, then execute WITH A THROTTLE.
#    Un-throttled reassignment saturates the network and starves producers.
K reassign-partitions --reassignment-json-file /tmp/plan.json \
  --throttle 52428800 --execute

# 3. Poll until complete, then ALWAYS verify (this also removes the throttle)
K reassign-partitions --reassignment-json-file /tmp/plan.json --verify

  

    
THE STEP PEOPLE SKIP

    
--verify is not optional. It's what removes the replication throttle. Skip it and the throttle
    stays applied indefinitely, quietly capping replication bandwidth — which then shows up weeks later as
    mysterious ISR shrink under load.

  


  
5.6 · A broker's disk is full

  
    
    
  1. Do not delete log segments by hand. You will corrupt the partition. Kafka must do it.
    2. 
    
  2. Find the offenders: K log-dirs --describe --bootstrap-server localhost:9092 and sort by size.
    3. 
    
  3. Reduce retention on the largest topic — it takes effect within log.retention.check.interval.ms:
      K configs --alter --entity-type topics --entity-name big-topic --add-config retention.ms=3600000
    4. 
    
  4. If compaction is the problem, check whether the cleaner is stuck (experiment 12) — raise log.cleaner.dedupe.buffer.size.
    5. 
    
  5. Once space is recovered, restore the original retention and address the root cause (usually retention set far longer than anyone needs).
    6. 
  


  
5.7 · Draining a topic before deletion

  
    
    
  1. Stop producers. Confirm the end offsets stop moving: K get-offsets --topic t --time -1 twice.
    2. 
    
  2. Wait for every consumer group to reach lag 0.
    3. 
    
  3. Verify no group is still subscribed: K consumer-groups --list then describe each.

  4. Delete: K topics --delete --topic t. Confirm the log dirs disappear on all brokers.

Project 1 · Exactly-once consume-transform-produce

  
The canonical EOS pipeline (ch.9): read from one topic, transform, write to another, and commit the offset
  inside the same transaction as the output — so a crash can neither duplicate nor drop.

  
bashsetup


K topics --create --topic eos-in  --partitions 3 --replication-factor 3
K topics --create --topic eos-out --partitions 3 --replication-factor 3


  
pythoneos.py


import sys, os, signal
from confluent_kafka import Consumer, Producer, KafkaException
from confluent_kafka import TopicPartition, OFFSET_INVALID

BOOT = "localhost:19092,localhost:29092,localhost:39092"
# transactional.id must be STABLE per instance — it is the fencing identity (ch.9).
TXN_ID = os.environ.get("TXN_ID", "eos-worker-1")

consumer = Consumer({
    "bootstrap.servers": BOOT,
    "group.id": "eos-group",
    "enable.auto.commit": False,        # the producer commits, not us
    "auto.offset.reset": "earliest",
    "isolation.level": "read_committed",
})
producer = Producer({
    "bootstrap.servers": BOOT,
    "transactional.id": TXN_ID,
    "enable.idempotence": True,
})

producer.init_transactions()      # bumps the epoch, fencing any zombie with this id
consumer.subscribe(["eos-in"])
print(f"EOS worker {TXN_ID} started", flush=True)

try:
    while True:
        msgs = consumer.consume(num_messages=100, timeout=1.0)
        if not msgs:
            continue

        producer.begin_transaction()
        try:
            for m in msgs:
                if m.error():
                    raise KafkaException(m.error())
                out = m.value().decode().upper().encode()   # the "transform"
                producer.produce("eos-out", key=m.key(), value=out)

            # CRUCIAL: the offsets go through the PRODUCER, making the
            # offset commit atomic with the output writes.
            positions = consumer.position(consumer.assignment())
            producer.send_offsets_to_transaction(
                [p for p in positions if p.offset != OFFSET_INVALID],
                consumer.consumer_group_metadata())

            producer.commit_transaction()
            print(f"committed {len(msgs)} records", flush=True)
        except Exception as e:
            print(f"aborting: {e}", flush=True)
            producer.abort_transaction()
            raise
except KeyboardInterrupt:
    pass
finally:
    consumer.close()


  
The test that proves it works. Produce 10,000 numbered records, run the worker, and kill it
  repeatedly mid-flight:

  
bash


# produce 10k numbered records
seq 1 10000 | docker exec -i kafka1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic eos-in

# run the worker and SIGKILL it a few times while it works
python3 eos.py & sleep 3; kill -9 %1
python3 eos.py & sleep 3; kill -9 %1
python3 eos.py            # let this one finish, then ctrl-C

# count DISTINCT outputs — must be exactly 10000, no duplicates
docker exec kafka1 /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic eos-out --from-beginning \
  --isolation-level read_committed --timeout-ms 15000 2>/dev/null | sort -n | uniq | wc -l

  
Then run the same test with --isolation-level read_uncommitted and compare — you'll see the
  aborted records that read_committed filtered out.

  
Extensions: start a second worker with the same TXN_ID and watch the first get
  fenced with ProducerFenced; time the pipeline with one transaction per record versus one per
  batch of 100 and quantify the EOS cost.


  
Project 2 · Prove zero loss under broker failure

  
A harness that kills brokers on a timer while a producer/consumer pair verifies every acknowledged record
  survives. This is the experiment that tells you whether your durability config is real.

  
pythonchaos.py


import threading, time, subprocess, random, sys
from confluent_kafka import Producer, Consumer

BOOT = "localhost:19092,localhost:29092,localhost:39092"
TOPIC = "chaos"
N = 20000

acked, failed = set(), []

def on_delivery(err, msg):
    if err:
        failed.append(err)                      # NOT acked — allowed to be missing
    else:
        acked.add(int(msg.value()))            # acked — MUST survive

def chaos(stop):
    while not stop.is_set():
        time.sleep(7)
        b = random.choice(["kafka1", "kafka2", "kafka3"])
        print(f"  !! killing {b}", flush=True)
        subprocess.run(["docker", "restart", b], capture_output=True)

p = Producer({
    "bootstrap.servers": BOOT,
    "acks": "all",                 # with min.insync.replicas=2 → real durability
    "enable.idempotence": True,
    "delivery.timeout.ms": 120000,
    "linger.ms": 5,
})

stop = threading.Event()
t = threading.Thread(target=chaos, args=(stop,), daemon=True); t.start()

for i in range(N):
    while True:
        try:
            p.produce(TOPIC, value=str(i).encode(), on_delivery=on_delivery); break
        except BufferError:
            p.poll(0.5)                          # accumulator full — backpressure
    p.poll(0)
p.flush(120)
stop.set()

print(f"\nacked={len(acked)}  failed={len(failed)}")

c = Consumer({"bootstrap.servers": BOOT, "group.id": f"verify-{time.time()}",
              "auto.offset.reset": "earliest", "enable.auto.commit": False})
c.subscribe([TOPIC])
seen, idle = set(), 0
while idle < 10:
    m = c.poll(1.0)
    if m is None: idle += 1; continue
    if not m.error(): seen.add(int(m.value())); idle = 0
c.close()

lost = acked - seen
dupes = len([1]) if False else None
print(f"consumed distinct={len(seen)}")
print(f"LOST ACKED RECORDS = {len(lost)}")
assert not lost, f"DURABILITY VIOLATION: {sorted(lost)[:20]}"
print("✓ every acknowledged record survived")

Project 3 · A compacted topic as a materialized view

  
Log compaction (ch.11) turns a topic into a replayable table. Build the changelog, then materialize it.

  
bash


K topics --create --topic accounts-changelog --partitions 3 --replication-factor 3 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.1 \
  --config segment.ms=10000 \
  --config delete.retention.ms=60000

  
pythonview.py


import json, sys, random
from confluent_kafka import Producer, Consumer

BOOT = "localhost:19092,localhost:29092,localhost:39092"
T = "accounts-changelog"

if sys.argv[1] == "write":
    p = Producer({"bootstrap.servers": BOOT, "acks": "all"})
    for i in range(5000):
        acct = f"acct-{random.randint(1,50)}"       # low cardinality → heavy compaction
        p.produce(T, key=acct.encode(),
                  value=json.dumps({"balance": random.randint(0,10000)}).encode())
    # a tombstone: null value deletes the key once compacted
    p.produce(T, key=b"acct-7", value=None)
    p.flush()
    print("wrote 5000 updates + 1 tombstone across 50 keys")

elif sys.argv[1] == "materialize":
    # Replay the whole log into a dict. THIS is what a state store does.
    c = Consumer({"bootstrap.servers": BOOT, "group.id": f"view-{random.random()}",
                  "auto.offset.reset": "earliest", "enable.auto.commit": False})
    c.subscribe([T])
    view, records, idle = {}, 0, 0
    while idle < 8:
        m = c.poll(1.0)
        if m is None: idle += 1; continue
        if m.error(): continue
        idle = 0; records += 1
        k = m.key().decode()
        if m.value() is None: view.pop(k, None)     # tombstone
        else: view[k] = json.loads(m.value())
    c.close()
    print(f"replayed {records} records → {len(view)} live keys")

  
bash


python3 view.py write
python3 view.py materialize      # ~5001 records replayed, 49 live keys

sleep 90                         # give the log cleaner time to run

python3 view.py materialize      # FAR fewer records replayed — SAME 49 keys

  
That is the whole point of compaction: the number of records you must replay collapses, while the state you
  reconstruct is identical. It's why Kafka Streams state stores, __consumer_offsets, and CDC
  snapshots all sit on compacted topics.

  
Extensions: raise the key cardinality to 500,000 and watch the cleaner fall behind (experiment 12);
  verify the tombstone disappears after delete.retention.ms and reason about why a consumer offline
  longer than that would miss the deletion.
