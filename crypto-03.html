ARC 01 · THE PROBLEM

DES is dead. What replaces it, and by what process?

By the mid-1990s the block cipher chapter 2 built — DES, 16 Feistel rounds, a 56-bit key — was no longer a cryptographic question but an arithmetic one. A 56-bit keyspace is 2⁵⁶ ≈ 7.2 × 10¹⁶ keys. In 1998 the Electronic Frontier Foundation's Deep Crack — 1,856 custom ASICs on a single board — brute forced a DES key in 56 hours for a hardware cost of about $250,000. Moore's Law was not going to reverse itself. The successor needed a key space so large that no foreseeable improvement in silicon, algorithms, or budget would matter, and it needed a larger 128-bit block (DES's 64-bit block has its own weakness — chapter 9's tradeoffs table returns to exactly this point with a named CVE).

The industry's stopgap, Triple-DES (three DES encryptions with two or three keys), bought time but not elegance: roughly 112 bits of effective security for a two-key variant, at three times the computation of single DES, while still carrying DES's undersized 64-bit block. It was never meant to be permanent.

So NIST — the same body that had adopted DES in 1977 — faced a design problem with much higher stakes than DES's had ever had, because this time the answer needed to satisfy requirements DES's Feistel structure did not cleanly provide:

  • Key sizes that scale past any credible future attack — 128, 192, and 256-bit options, not one fixed size.
  • A 128-bit block — large enough that generic block-cipher-mode weaknesses (chapter 5's ECB/CBC/CTR chapter, and the birthday-bound math behind Sweet32 in chapter 9) don't bite for a very long time.
  • Efficiency across radically different hardware — from 8-bit smartcards to 64-bit servers, in both software and dedicated silicon — something DES's bit-level permutations (chapter 2's IP/FP tables) were never designed for.
  • Total public transparency. DES's S-boxes were altered by the NSA before standardization with no public justification given at the time; it took until 1990 (Biham and Shamir's differential cryptanalysis paper) for the outside world to learn the changes had actually strengthened DES against an attack the NSA already knew and the public didn't. That thirteen-year trust gap was itself a design failure NIST wanted to never repeat.
WHY THIS MATTERS FOR THE NEXT 13 CHAPTERS

Every symmetric primitive after this chapter — the AEAD modes of chapter 7, the key derivation of chapter 8, even the mini TLS stack you build in chapter 16 — has AES (or, per chapter 4, its software-friendly cousin ChaCha20) sitting underneath it as the actual work of confidentiality. Get comfortable with GF(2⁸) arithmetic and the round structure now; you will read a diagram of "AES-GCM" or "AES-256 key wrap" in every future chapter and need to know what's physically happening inside that box.

DEEP CONTEXT · WHY "RIJNDAEL" BECAME "AES"

Rijndael (pronounced roughly "rain-doll," a portmanteau of its designers' surnames) is a family of ciphers supporting variable block and key sizes in 32-bit increments from 128 to 256 bits. FIPS 197 standardizes only the subset with a fixed 128-bit block and 128/192/256-bit keys — that constrained subset is what the world calls "AES." The distinction matters once you read OpenSSL or BoringSSL source in §13: you'll see rijndael in symbol names precisely because the underlying algorithm is broader than the standard that adopted a slice of it.

ARC 03 · NAIVE SOLUTION

Attempt #1: substitute every byte, add the key, repeat

Derive the round function honestly, the way Daemen and Rijmen's design report does. AES needs a nonlinear step — without one, the whole cipher is a linear function of the key and plaintext, solvable with linear algebra in milliseconds. The obvious nonlinear building block is a fixed substitution box: a lookup table that maps each of the 256 possible byte values to another byte, chosen so the mapping has no useful algebraic structure for an attacker (AES's real S-box, derived from a GF(2⁸) multiplicative inverse, is built in §8).

So the naive first draft: split the 128-bit block into 16 bytes, substitute every byte through the S-box, XOR in 16 bytes of round key, and repeat for several rounds. No byte ever talks to any other byte.

JSnaive_cipher.js — the strawman, annotated
function naiveRound(state, roundKey) {
  // state: 16 bytes. roundKey: 16 bytes. Both indexed 0..15, no structure.
  for (let i = 0; i < 16; i++) {
    state[i] = SBOX[state[i]];        // substitute — nonlinear, but LOCAL to byte i
    state[i] ^= roundKey[i];          // mix in key material — also LOCAL to byte i
  }
  return state;                    // notice: byte 0 of the output depends on
}                                    // byte 0 of the input and NOTHING else, ever

This looks reasonable — it's nonlinear, it mixes in key material every round, and stacking ten rounds of it feels like it should be as strong as ten rounds of anything. Chapter 2's Feistel network similarly looked reasonable before its 16 rounds and 48-bit-per-round key schedule were examined closely. ARC 04 · WHY IT FAILS

No diffusion means sixteen independent 1-byte ciphers

The widget above is the whole argument in one interaction. In the naive round, output byte i is a function of input byte i and key byte i alone: out[i] = SBOX[in[i]] ^ key[i]. Sixteen bytes, computed in complete isolation, is not a 128-bit cipher — it is sixteen parallel 8-bit substitution ciphers that happen to be evaluated together. Every weakness of a single-byte substitution cipher applies independently, sixteen times over:

  • Frequency analysis works per byte position. If byte position 4 of many plaintext blocks is biased (ASCII text, structured binary formats, repeated headers), the corresponding ciphertext byte position inherits exactly that bias, S-box-permuted but statistically intact.
  • Known-plaintext recovers the key one byte at a time. Given one (plaintext, ciphertext) pair, key[i] = SBOX[plaintext[i]] ^ ciphertext[i] for every i, independently — for a single naive round this is not a 2¹²⁸ search, it is sixteen trivial 256-entry table lookups.
  • Stacking rounds doesn't help. Composing N of these rounds still keeps every byte position independent — out[i] is always some fixed function of in[i] and the round keys at position i only. You can add a thousand rounds and byte 0 of the ciphertext will never depend on byte 1 of the plaintext.
THE NUMBER THAT MATTERS: AVALANCHE

Claude Shannon's 1949 diffusion criterion, stated precisely: flipping one input bit should flip roughly half of the 128 output bits, unpredictably. In the naive cipher, one flipped plaintext bit can only ever touch one byte's worth of output — at most 8 of 128 bits, or 6.25%, and typically fewer once you account for S-box outputs that happen to share bit patterns. The widget's real-AES column, by contrast, saturates toward the theoretical 50% within a handful of rounds — you can watch the exact percentage computed live. Diffusion isn't an aesthetic property; it's the mathematical reason a single-byte attack can't be assembled into a whole-block attack. §5 derives the two operations that buy it.

ARC 05 · BETTER SOLUTION

Two more operations: shuffle bytes across columns, then mix them algebraically

The fix has to make every output byte depend on multiple input bytes, not just its own position. Rijndael's answer is two linear operations, each cheap, each serving a distinct half of the diffusion job. THE DIVISION OF LABOR

SubBytes supplies all of AES's nonlinearity (everything else in the cipher is linear over GF(2⁸)). ShiftRows is diffusion between columns — it guarantees that after one more MixColumns step, every output byte in a column has contributions from four different original columns. MixColumns is diffusion within a column — it is a fixed 4×4 matrix multiply over GF(2⁸) that spreads each of a column's 4 bytes into all 4 output bytes of that column. Applied together for enough rounds, the two guarantee that changing any single input bit eventually influences every output bit — full diffusion is provably reached within 4 rounds for AES's specific matrices, which is exactly why the standard uses more than 4.

ARC 06 · WHY THAT STILL HURTS

Diffusion isn't free, and neither is "enough of it"

Adding ShiftRows and MixColumns solves §4's failure, but it opens two new questions any serious implementer has to answer with numbers, not vibes: how many rounds is enough, and what does computing this cheaply cost you?

  • Full diffusion at round 4 does not mean "secure" at round 4. Diffusion is necessary but not sufficient — it defeats naive per-byte attacks, but differential and linear cryptanalysis — the same attack families chapter 2 used against reduced-round DES — can still exploit residual statistical bias for many rounds after diffusion first saturates. AES's actual round counts (10/12/14, tied to key length via Nr = Nk + 6) were chosen with a security margin well beyond the last round any public cryptanalysis could touch, not the minimum for diffusion alone.
  • MixColumns is real arithmetic, every round, every column. Each column multiply is 4 GF(2⁸) multiplications and additions per output byte — cheap individually, but multiplied across 4 columns × 9 or 11 rounds × billions of blocks, it dominates a naive software implementation's cost. §8 shows the GF(2⁸) math directly; §13 shows how real libraries avoid recomputing it per byte.
  • A table-based software shortcut creates a side channel. The fast software trick — precompute SubBytes+ShiftRows+MixColumns into four 256-entry, 32-bit lookup tables ("T-tables") — replaces per-byte field arithmetic with array indexing. It is much faster, and it is exactly what made 2005's cache-timing attacks possible (§11): the CPU cache reveals *which* table index was accessed, and the index is derived from secret key-dependent data. Speed and side-channel safety pulled in opposite directions for a full decade before hardware closed the gap.
THE INDUSTRY'S ANSWER — AND ITS ADMISSION

Intel's fix, shipped in 2010, was to stop computing AES in software at all: AES-NI, six new x86 instructions (AESENC, AESENCLAST, AESDEC, AESDECLAST, AESKEYGENASSIST, AESIMC) that perform an entire round — or an entire key-schedule step — in dedicated silicon, with no secret-indexed memory access at all. That it took hardware, not a software patch, to fully close the cache-timing class is itself an admission: table-based AES and side-channel safety were fundamentally in tension, and only removing the table won.

WHY THE BLOCK SIZE NEVER CHANGES

Notice what does not vary across AES-128/192/256: the block size is always 128 bits, and the round structure is identical — only the key schedule length and round count change. This is a deliberate, auditable design decision: it means every mode of operation (chapter 5), every AEAD construction (chapter 7), and every hardware AES-NI instruction works identically regardless of which key size you chose. The only thing a bigger key buys you is more rounds and a larger key schedule — never a different state layout.

ARC 08 · INTERNAL IMPLEMENTATION

The real arithmetic: GF(2⁸), the S-box, and the key schedule

Everything below runs as genuine JavaScript on this page — the same functions power every widget in this chapter, including the simulator in §15, and they are verified against FIPS 197 Appendix B before this file ships. No fake-looking hex; every value you see was actually computed.

(a) GF(2⁸): why AES needs a different kind of multiplication

A byte is 8 bits, so ordinary addition/multiplication overflows past 255 in ways that don't invert cleanly — you can't always "divide back out." AES instead treats each byte as a polynomial with binary coefficients (bit 7 is the x⁷ term, bit 0 is the constant term) and does arithmetic modulo the irreducible polynomial x⁸+x⁴+x³+x+1, written as the byte 0x11B. Addition is just XOR (no carries). Multiplication is the schoolbook "multiply the polynomials, then reduce" — and because every nonzero element has a multiplicative inverse in this field, MixColumns' matrix is invertible (needed for decryption) and the S-box's core step (a multiplicative inverse) is well-defined for every byte except zero, which is mapped to zero by convention.

(b) SubBytes: the S-box, built from an inverse, not chosen by hand

AES's S-box is not an arbitrary lookup table — it is S(x) = A · x⁻¹ ⊕ 0x63: take the multiplicative inverse in GF(2⁸) (a highly nonlinear operation with no useful algebraic shortcuts — this is what defeats linear/differential cryptanalysis at the byte level), then apply a fixed GF(2)-linear affine transformation and XOR the constant 0x63 (chosen specifically so the S-box has no fixed points — no byte maps to itself — and no "opposite fixed points"). The 256-entry result is public, fixed forever by FIPS 197, and identical for every AES key size:

(c) The key schedule: turning one key into 11, 13, or 15 round keys

  
AES needs one 128-bit round key per round plus one more for the initial whitening — Nr+1
  keys total, all derived from the single input key via KeyExpansion. Every 4th word gets a nonlinear
  twist (RotWord rotates the word's 4 bytes, SubWord runs each byte through the same
  S-box as SubBytes, then XORs in a round constant from the Rcon table) specifically so the schedule
  isn't a simple repeating or linear function of the key — a linear key schedule would let an attacker who

Read the table as NIST's actual tradeoff: Serpent's designers (Anderson, Biham, Knudsen) explicitly chose a
  32-round margin so large that even a dramatic cryptanalytic advance would likely fail against it — a "we will
  not be the one that got broken" bet. Rijndael's designers instead argued that a smaller, well-understood margin
  with excellent performance was the more useful standard, since a cipher nobody deploys because it's too
  slow protects nothing. NIST's selection report explicitly weighed performance across the full spectrum from
  8-bit smartcards to 64-bit servers as a first-class criterion, not an afterthought — and it is the reason Rijndael,
  not the more conservative Serpent, is the algorithm inside every device you own today.







  
ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

  
How much margin, and what does breaking it actually cost?

  
Two numbers matter for a cipher: how fast it runs, and how expensive the best known attack against it is.
  Start with the second, because it's the one people misstate:

  
    
    
  • Brute force is 2ⁿ for an n-bit key — 2¹²⁸ ≈ 3.4 × 10³⁸ for AES-128. There is no known attack that
      meaningfully beats this for a randomly chosen, independent key.
    • 
    
  • The best published academic shortcut is a 2011 biclique attack
      against the full round count: roughly 2¹²⁶·¹ for AES-128, 2¹⁸⁹·⁷ for AES-192, 2²⁵⁴·⁴ for AES-256 — a
      constant-factor speedup over brute force (about 4× for AES-128), not a structural break. It changed no
      recommendation anywhere; it is purely of academic interest.
    • 
    
  • Related-key attacks on AES-256's key schedule (Biryukov, Khovratovich, and Nikolić, 2009) are more
      interesting and more misunderstood: under a related-key model — the attacker gets ciphertexts encrypted
      under several keys mathematically related to each other, not just one unknown key — the full 14-round AES-256
      falls in roughly 2⁹⁹·⁵ time. This exploits AES-256's key schedule being "too linear" relative to AES-128's.
      It has no bearing on AES-256 used correctly (one key per session, derived independently, per chapter
      8) — but it is precisely why some protocol designs that accidentally create related keys (a poorly designed
      key-derivation scheme, for instance) deserve real scrutiny, not just "AES-256 is used, so we're fine."
    • 
  

  

    
MAKE 2¹²⁸ CONCRETE

    
Suppose you had a trillion (10¹²) dedicated ASICs, each testing a trillion (10¹²) AES keys per second —
    roughly the combined guessing throughput of every specialized brute-force chip ever fabricated, multiplied by
    a thousand. That's 10²⁴ keys/second. Exhausting 2¹²⁸ ≈ 3.4 × 10³⁸ keys still takes ~3.4 × 10¹⁴ seconds ≈
    10.8 million years — over 780,000 times the age of the universe (≈13.8 billion years). AES-256's 2²⁵⁶
    keyspace makes the same calculation absurd rather than merely enormous. This is why every real AES break in
    §11 attacks an implementation (timing, power, a flawed protocol around it) — never the cipher's
    mathematics directly.

ARC 11 · REAL-WORLD INCIDENTS

  
Every real AES break has been a side channel, not the math


  
Incident 1: Bernstein's 2005 remote cache-timing attack

  
Daniel J. Bernstein's "Cache-timing attacks on AES" (2005) recovered a full OpenSSL AES key over a
  local network purely by timing how long encryption requests took. Root cause: table-based software AES ("T-tables")
  looks up SubBytes/MixColumns results in 256-entry arrays indexed by secret key-dependent byte values. Which
  cache line gets loaded — and therefore how long the memory access takes — leaks bits of that index. No plaintext
  or ciphertext content was inspected at all; the attack watched only elapsed time.


  
Incident 2: Osvik, Shamir & Tromer's local cache attacks (2006)

  
"Cache Attacks and Countermeasures: The Case of AES" pushed the same root cause further with
  Prime+Probe and Evict+Time techniques, recovering full AES keys from a co-resident process — including across
  hyper-threading siblings — in well under a second in some configurations. This paper is a direct ancestor of the
  cross-tenant cloud side-channel concerns (and later Spectre/Meltdown-style cache attacks) that shaped how
  seriously the industry now treats "your code and the attacker's code share a CPU cache."


  
Incident 3: the fix was hardware, not a patch — AES-NI (2010)

  
Both attacks above share one root cause: secret-indexed table lookups. Software mitigations (bitsliced,
  table-free implementations like OpenSSL's vpaes) existed but cost real performance. Intel's actual
  fix, shipped in Westmere (2010) and mirrored later in ARMv8's Cryptography Extensions (2013), was to compute
  SubBytes/ShiftRows/MixColumns/AddRoundKey inside the CPU with fixed, non-secret-dependent circuitry — closing
  the vulnerability class by construction while also making AES roughly an order of magnitude faster than
  table-based software. Security and performance, for once, pointed the same direction.


  
Incident 4: physical side channels on embedded AES (differential power analysis)

  
Cache timing requires a shared cache; it doesn't apply to an isolated smartcard or payment chip. But those
  devices have their own leak: differential power analysis (DPA),
  pioneered against DES and RSA by Kocher, Jaffe, and Jun, and extended to AES implementations throughout the
  2000s. An unprotected embedded AES implementation's power draw correlates measurably with the Hamming weight of
  its S-box outputs; enough traces recover the key without ever seeing a ciphertext. The lesson generalizes past
  cache lines and power meters: any physically observable, secret-correlated signal is a side channel —
  timing, power, electromagnetic emission, even sound. Modern smartcard and HSM implementations defend with
  masking (randomizing intermediate values so no single measurement correlates with the real key) — the physical
  analogue of the constant-time software discipline chapter 15 covers for CPUs.

First, the key expansion in the shape every reference implementation shares — this is the same algorithm §8(c)
  ran live, expressed as C-like pseudocode faithful to FIPS 197's own presentation:


  

    
CKeyExpansion() — FIPS 197 §5.2 structure

    
void KeyExpansion(const uint8_t *key, uint32_t *w, int Nk, int Nr)
{
    for (int i = 0; i < Nk; i++)
        w[i] = word(key[4*i], key[4*i+1], key[4*i+2], key[4*i+3]);

    for (int i = Nk; i < 4*(Nr+1); i++) {
        uint32_t temp = w[i-1];
        if (i % Nk == 0)
            /* the ONLY nonlinear step in the whole schedule: */
            temp = SubWord(RotWord(temp)) ^ (Rcon[i/Nk] << 24);
        else if (Nk > 6 && i % Nk == 4)
            /* AES-256 ONLY: one extra SubWord every 8 words — */
            temp = SubWord(temp);     /* narrows the 2009 related-key gap slightly   */
        w[i] = w[i-Nk] ^ temp;
    }
}

  


  
Then the cipher loop itself — the structural mirror of the FIPS 197 pseudocode and of §7's explorer:


  

    
CCipher() — FIPS 197 §5.1 structure

    
void Cipher(uint8_t *state, const uint32_t *w, int Nr)
{
    AddRoundKey(state, w, 0);

    for (int round = 1; round < Nr; round++) {
        SubBytes(state);
        ShiftRows(state);
        MixColumns(state);            /* the ONLY difference vs the final round */
        AddRoundKey(state, w, round);
    }

    SubBytes(state);
    ShiftRows(state);
    AddRoundKey(state, w, Nr);          /* no MixColumns — see the S7 callout */
}

  


  
And the hardware path that replaces almost all of the above with three instructions per round:


  

    
C (intrinsics)AES-NI: one round in one instruction

    
// _mm_aesenc_si128(state, roundKey) performs, in fixed-latency silicon:
//    SubBytes -> ShiftRows -> MixColumns -> AddRoundKey(roundKey)
// with ZERO secret-indexed memory access -- the entire cache-timing
// class from S11 has no mechanism to exploit here.
state = _mm_xor_si128(state, roundKeys[0]);              /* initial AddRoundKey */
for (int r = 1; r < Nr; r++)
    state = _mm_aesenc_si128(state, roundKeys[r]);       /* main rounds       */
state = _mm_aesenclast_si128(state, roundKeys[Nr]);      /* final round: no MixColumns, baked into the "last" variant */

  


  

    
WHY THREE IMPLEMENTATIONS COEXIST — THE ENGINEERING CALL

    
1. aes_core.c stays because OpenSSL must run on architectures with no AES instructions and no time
    invested in hand-tuned assembly — portability has to have a floor. 2. vpaes exists because "no AES-NI"
    doesn't mean "side channels are acceptable" — vpaes uses vector-permute instructions to implement the S-box as
    a small set of table lookups small enough to fit entirely in one cache line, eliminating the secret-dependent
    cache-line signal at a real but bounded performance cost. 3. aesni-x86_64.pl is selected whenever available
    because it is simultaneously the fastest and the safest option — the rare case with no tradeoff at all.
    The dispatch happens once, at library init, via a CPU feature-detection bitmask — not a runtime branch per
    block, which would itself risk timing variance.
