RABBITMQ INTERNALS · CHAPTER 11

Persistence, Disk Layout
& Recovery

"Durable" is not a checkbox — it is a conjunction of three independent conditions that must all hold at once, and getting one of them wrong is the single most common way production RabbitMQ deployments silently lose messages. This chapter opens the node's data directory, reads the actual bytes of the message store and the queue index, derives the garbage-collection algorithm that keeps disk usage from growing forever, and walks the exact startup sequence that rebuilds a queue's state after a crash.

ARC 01 · THE PROBLEM

Durability is an AND, not an OR

Ask ten engineers "how do I make a RabbitMQ message durable?" and most will answer "set delivery_mode=2." That answer is necessary and almost never sufficient. A message survives a broker restart if and only if three independent conditions all hold at once: the exchange it was published through was declared durable, the queue it landed in was declared durable, and the message itself carried delivery_mode=2 (the AMQP 0-9-1 property that means "persistent"). Every one of those three is a separate piece of metadata, set in a separate place, by a separate call, and RabbitMQ enforces none of them on your behalf — it will happily accept a persistent message into a non-durable queue bound to a durable exchange, and drop every copy of it the instant the node stops.

Unpack why each condition is independently necessary, because each one protects a different piece of state:

  • Exchange durability protects routing metadata. A durable exchange's existence and type are recorded in the metadata store (Mnesia, or Khepri from 4.0) and survive a restart; a transient exchange is recreated empty, with no bindings, the moment the node comes back — so even if the queue and message were both durable, nothing routes to the queue anymore because the exchange that pointed at it is gone.
  • Queue durability protects the queue's own existence and its bindings. A durable queue's declaration is written to the metadata store, so rabbit_amqqueue_process is respawned for it on startup and its bindings are restored. A transient queue simply does not exist after restart — there is no queue for a recovered persistent message to be placed into, even if that message's bytes are sitting safely on disk in the shared message store.
  • Message delivery_mode=2 protects the message body itself. Only messages published with this flag are written to the message store's .rdq files at all. A delivery_mode=1 ("transient") message published into a fully durable topology is held only in the queue process's own memory (and, if the queue is a classic queue under memory pressure, spilled to a transient-only message store that is deliberately deleted on every startup) — it was never written anywhere that survives.
THE PRODUCTION MISTAKE, PRECISELY STATED

The overwhelmingly common failure mode is not "we forgot persistence entirely" — it's "we got 2 of 3." Teams declare their queues durable (it shows up in the management UI as a reassuring padlock icon) and set delivery_mode=2 on every publish, and stop there — because the exchange was declared once, years ago, by a deploy script that didn't pass durable: true, and nobody has looked at it since. The queue survives a restart. The bindings do not. Messages published after that restart route into a black hole with no error, because publishing to an exchange with no matching binding is, by AMQP 0-9-1 design, a silent no-op unless the publisher is using the mandatory flag. The bug is invisible until the exact moment it matters most — a crash.

This chapter derives the on-disk mechanism that makes the "AND" true when all three conditions are met: what a message store file actually contains, what a queue index segment records, how the two cross-reference each other, how space is reclaimed from an append-only structure that never overwrites in place, and exactly what happens between "process receives SIGTERM" and "the first post-recovery message is delivered." Chapter 12 will use every one of these mechanics inside a real, running toy broker.

From Mnesia disk tables to a dedicated append-only store

Interactive timeline — building a broker's storage layerCLICK EVENTS
DEEP CONTEXT · WHY MNESIA WAS NEVER GOING TO WORK FOR MESSAGE BODIES

Mnesia is a schema'd, transactional, replicated Erlang term database — superb for small, structured records like exchange and binding definitions, which is exactly what RabbitMQ still uses it (or, since 4.0, Khepri) for today. It was never built to hold millions of opaque binary blobs of wildly varying size with high write throughput; every write goes through Mnesia's transaction manager and its own on-disk log format, which adds overhead completely unrelated to "append these bytes to a file." The first persistence rewrite's entire thesis was: split metadata from message bodies. Metadata — small, relational, needs transactions — stays in Mnesia/Khepri. Message bodies — large, opaque, need raw throughput — get a purpose-built store. That split is the single most important architectural decision this chapter explains.

ARC 03 · NAIVE SOLUTION

Attempt #1: one file per message, fsync every write

Derive the architecture honestly, the way every chapter in this course has. If your only requirement is "a persistent message must survive a crash," the simplest possible mechanism is obvious: write each message to its own file, and call fsync() before acknowledging the publish.

pseudo-erlangnaive_store.erl — the strawman, annotated
publish(QueueName, MsgId, Body) ->
    Path = filename:join(["/var/lib/rabbitmq/naive", QueueName,
                            integer_to_list(MsgId) ++ ".msg"]),
    {ok, Fd} = file:open(Path, [write, raw, binary]),
    file:write(Fd, Body),
    file:sync(Fd),           %% fsync(2) — do not return until this message
    file:close(Fd),          %% is physically on the platter/flash, every time
    ok.

ack(QueueName, MsgId) ->
    Path = filename:join(["/var/lib/rabbitmq/naive", QueueName,
                            integer_to_list(MsgId) ++ ".msg"]),
    file:delete(Path),      %% reclaiming space is just unlink(2)
    ok.

This gets the core property right: every acknowledged publish is genuinely on disk before the confirm is sent, and reclaiming space on ack is a single, instantaneous unlink() — no compaction, no bookkeeping, nothing left behind. For a system publishing a few messages a second, this is not a bad design at all. The trouble is what happens as throughput rises, which the next section quantifies.

ARC 04 · WHY IT FAILS

Three failures, and they compound

The naive design fails along three independent axes, and — unlike some naive solutions in this course — none of them is subtle; all three show up in the first load test.

  • fsync latency caps throughput at 1/latency, per writer. A single fsync() on a spinning disk costs roughly 5–15 ms (a full rotation to get the write head where it needs to be, plus the write itself); even on an NVMe SSD with power-loss protection it is commonly 0.1–0.5 ms because the drive still has to flush its own write buffer to durable media. At 10 ms per fsync, one writer caps at 100 messages/second, full stop — no amount of CPU, network, or Erlang scheduler tuning moves that number, because the bottleneck is a physical write barrier, not compute.
  • File-per-message wastes space and inodes at small sizes. Filesystems allocate in blocks — typically 4 KB. A 200-byte message consumes a full 4 KB block plus an inode, meaning a queue holding a million small messages can consume 4 GB of block allocation for a few hundred MB of actual payload, a >10x amplification, and can exhaust the filesystem's inode table entirely on some configurations well before it exhausts disk space.
  • Directory operations degrade as file count grows. Even on filesystems with reasonably efficient directory indexes, a directory holding millions of entries makes readdir-based recovery scans (exactly what startup needs to do — "what messages exist for this queue?") measurably slower, and many real-world deployments still see ext4/XFS directory metadata contention under concurrent create/unlink at this rate.
THE NUMBERS, AND WHY BATCHING IS THE ONLY WAY OUT

A production exchange doing 50,000 msg/s of persistent traffic needs an effective fsync cost of 20 microseconds to keep up if every message pays its own fsync — three orders of magnitude faster than even a good NVMe drive's real flush latency. The only way to reconcile "every acknowledged message is durable" with "the disk cannot fsync 50,000 times a second" is to stop fsyncing per message: batch many messages' writes together and pay one fsync for the whole batch, then confirm all of them at once. That single idea — batch, don't serialize — is what §5 builds toward, and it is the same idea that makes publisher confirms asynchronous rather than a call-and-block round trip per message.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates, and why the third one wins

Step through the candidates the same way real RabbitMQ development did — each one fixes the previous candidate's most glaring problem and exposes a new one.

Eliminating the fieldSTEP-BY-STEP
THE WINNING SHAPE, IN ONE SENTENCE

Separate what was published (a shared, append-only, reference-counted message store keyed by message id) from where and in what state each copy of it sits (a small per-queue index recording publish/deliver/ack positions). Neither structure alone solves persistence; together, they let ten queues fed by a fanout exchange share one on-disk copy of a message while independently tracking their own delivery progress against it — which is exactly rabbit_msg_store plus rabbit_queue_index, the pair §7 and §8 open up in full.

ARC 06 · WHY THAT STILL COSTS

Append-only never gets cheaper on its own — someone has to clean up

The shared, reference-counted, append-only store from §5 solves throughput and space amplification, but it introduces a new problem it cannot avoid: an append-only file never shrinks. Every ack decrements a reference count and, at refcount zero, marks that message's bytes as garbage — but the bytes are still sitting in the middle of a file that other, still-referenced messages also live in. You cannot simply ftruncate() a hole out of the middle of a file.

  • Fragmentation grows monotonically under churn. A queue that publishes and acks continuously accumulates holes throughout every .rdq file it has ever written to; without intervention, disk usage grows forever even though the number of live messages is stable or falling.
  • Reclaiming those holes means rewriting live data. The only way to actually free disk space is to copy the still-valid messages out of two fragmented files into one, then delete the originals — which is write amplification: you pay disk I/O for data that didn't change, purely to compact around data that did.
  • Doing this too eagerly defeats the point of batching. If compaction ran on every single ack, you'd be back to a per-message disk operation — the exact throughput ceiling §4 identified. Compaction has to be a background, threshold-triggered process, which means it necessarily lags behind the actual message count — the disk usage graph in §15 will show you exactly how much.

So the final architecture needs one more component beyond "shared store + per-queue index": a background garbage collector that decides when two files are fragmented enough to be worth compacting, and does the rewrite without blocking publishers or consumers. That is exactly what §8 derives.

ONE STORE, MANY QUEUES: WHY THE HASH-BASED DIRECTORY NAMES

Vhost and queue names are arbitrary UTF-8 strings that can contain characters unsafe for filesystem paths (slashes, unicode, arbitrary length) — so RabbitMQ never uses the name directly as a directory name. Instead it hashes the name to a fixed-format, filesystem-safe identifier and keeps the name→hash mapping in the metadata store. This is also why you cannot identify a queue's on-disk files by eyeballing the data directory — you need rabbitmq-diagnostics (§13) or the queue's own recorded index location to map a name back to a path.

ARC 08 · INTERNAL IMPLEMENTATION

Bytes on disk: the message store, the queue index, and the GC that keeps them small

(a) The message store: append-only .rdq files, reference-counted by message id

rabbit_msg_store is a gen_server2 — one instance per vhost per store class (persistent / transient) — that owns a single "current" file it appends to. Each file is capped at msg_store_file_size_limit (16 MB by default); when the current file would exceed that, the store rolls to a new file with the next integer name (0.rdq, 1.rdq, …). Every write is a flat record: the message id, the serialized message (properties, headers, and body, in the same external binary format used on the wire), and enough length information to read the record back without consulting anything else. Because the store is content-addressed by message id rather than by queue, publishing one message to a fanout exchange bound to five queues writes the body to disk once — an in-memory index (an ETS table, rabbit_msg_store_ets_index, itself checkpointed to disk) maps each message id to {File, Offset, TotalSize, RefCount}, and every additional queue that references the same message id merely increments RefCount. The message is only eligible for garbage collection once RefCount reaches zero — i.e., every queue that ever held a copy has acked it.

(b) The queue index: per-queue segments of exactly 16,384 entries

Alongside the shared store, every classic queue owns its own rabbit_queue_index under queues/<hash>/: a sequence of fixed-size segment files, each covering exactly 16,384 consecutive queue sequence ids. A segment entry does not duplicate the message body — for messages routed through the shared store it records only the message id (a reference) and three bits of state: published, delivered, acked. For small messages below queue_index_embed_msgs_below (default 4,096 bytes), the queue index embeds the entire serialized message inline in the segment entry itself, skipping the message store entirely — the reasoning being that for small messages, the fixed overhead of a message-store round trip (an ETS lookup, a separate file write, a reference-count bookkeeping update) costs more than just duplicating the few hundred bytes directly into the structure you were going to write anyway. This is a real, tunable space/time tradeoff: raising the threshold shifts more messages into inline storage, trading message-store indirection for slightly larger, less deduplicated index segments — the slider below makes the split concrete.

A queue's index also tracks its journal of pending changes in memory (a batched write-behind buffer) before flushing to the segment file, precisely so that a burst of publish/ack activity against the same sequence id range doesn't force a disk write per event — the same batching principle from §4, applied one layer up.

(c) Garbage collection by compaction — reclaiming holes without blocking anyone

The message store never edits a file in place; it only appends and, separately, tracks per-file bookkeeping in rabbit_msg_store's file_summary ETS table: for every .rdq file, the total bytes written and the bytes still valid (referenced by at least one live queue). As acks drive RefCount to zero across a file's messages, its valid-byte count falls further and further below its total size — the file fills up with holes. rabbit_msg_store_gc runs as a background process that periodically inspects adjacent file pairs; when the combined valid data of two neighboring files falls below a configured fraction of one file's capacity, it triggers a compaction pass: read every still-valid message out of both files in file order, append them contiguously into whichever of the two files has more room (or a fresh file), update the ETS index's {File, Offset} for every message that moved, and finally delete the now-empty source file. Crucially, this happens entirely in the background relative to publishers and consumers — a message being actively read out of a file mid-compaction is unaffected because the compactor copies bytes, it never mutates a message a reader might be holding an offset into concurrently without first updating the index those readers consult.

THE SUPPORT TICKET THIS EXPLAINS

"We drained the queue completely and disk usage didn't drop" is one of the most common RabbitMQ operations questions, and it is not a bug: acking a message only marks it as garbage in the bookkeeping; the bytes are freed from disk only when the GC's threshold trips for the specific file pair those particular messages happened to land in. If your queue's messages are spread thinly across many mostly-full files, no single pair may cross the compaction threshold for a long time. Disk usage genuinely, correctly, lags message count — the chart above is the shape of that lag, not a leak.

(d) fsync batching: why publisher confirms are asynchronous

Neither the message store nor the queue index calls fsync() per write. Both batch: writes accumulate in the OS page cache / the process's own buffer, and an fsync is issued either on a timer interval or when a configured number of bytes have been buffered — whichever comes first. A publisher confirm (the AMQP extension that lets a publisher know a message is safely handled) is only sent back once the relevant fsync covering that message's write has actually completed, which is precisely why confirms are delivered asynchronously and out of publish order relative to when you called publish — the broker is deliberately holding your confirm until it can batch it with others. This single design decision is the entire reason publisher confirms are commonly cited as roughly two orders of magnitude faster in aggregate throughput than the old AMQP 0-9-1 transactions (tx.commit), which forced a round trip — and, in most naive client implementations, a synchronous disk flush — per transaction rather than per batch.

(e) Quorum queues: a different, stricter disk contract

Quorum queues do not use rabbit_msg_store or rabbit_queue_index at all — each quorum queue is a replicated Raft log driven by rabbit_fifo (the state machine) on top of the ra library. Every accepted command (enqueue, ack, etc.) is first appended to a per-node, shared write-ahead log (ra_log_wal) before it is applied to any state machine, and periodically rolled into per-Ra-server segment files by ra_log_segment_writer, with periodic snapshots (ra_snapshot) letting old log segments be deleted once their entries are reflected in a snapshot every replica has durably stored. Because Raft's correctness proof depends on "a majority of replicas have durably persisted an entry" as the precise definition of "committed," a quorum queue must fsync its WAL before acknowledging a write to its Raft peers — there is no equivalent of "batch and confirm later" available to skip, because the durability isn't cosmetic, it's the mechanism that makes leader election and log matching safe after a crash. This is why quorum queues are consistently measured as fsync'ing more aggressively, and at somewhat lower steady-state throughput, than classic queues under the same publish load — the extra durability guarantee (survives loss of a minority of the cluster, not just of disk) is bought with strictly more disk-flush work per accepted write.

ARC 09 · TRADEOFFS

Persistence, compared

Neither is "more correct" — they are solving different problems, and §13 of chapter 12 makes that precise.

ARC 10 · PERFORMANCE CHARACTERISTICS

What you can predict before benchmarking

  • Message store write: O(1) amortized — an append plus an ETS index insert; the per-message cost is independent of how many messages already exist in the store.
  • Message store read: O(1) — one ETS lookup for {File, Offset, Size}, then one pread at that offset. No scanning, ever, in steady state.
  • Queue index lookup for the next deliverable message: O(1) amortized against the in-memory journal for hot (recently written) entries; a cold segment not currently resident costs one segment-file read (a few hundred KB at most, since a segment covers 16,384 entries).
  • Garbage collection pass: O(valid bytes in the two files being compacted) — proportional to how much live data survives, not to how much garbage is being discarded, which is why compaction of a mostly-dead file pair is cheap and compaction of a mostly-live pair (rare, since it wouldn't have crossed the threshold) would be expensive.
  • Per-queue memory overhead: a classic queue keeps a bounded in-memory window of its index journal plus whatever messages are held for immediate delivery; the bulk of a very deep queue's backlog lives on disk, not in the Erlang process heap, which is exactly why RabbitMQ can hold queues far larger than available RAM without OOMing (at the cost of read-back latency for old messages, since they're no longer hot in any cache).
  • Recovery time: dominated by the queue index — replaying and cross-checking every segment for every queue with a persistent backlog — not by the message store, since store recovery is a single directory scan building one index rather than replaying per-queue delivery state. §15 makes this scaling visible directly.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents this chapter explains

Incident 1: the disk-usage alarm that wouldn't clear

A team purges a multi-million-message backlog queue during an incident, expecting disk usage to drop immediately and the disk_free_limit alarm to clear. It doesn't — for nearly an hour, disk usage stays flat, publishers remain blocked (RabbitMQ blocks all publishing connections cluster-wide when the disk alarm trips, by design, since accepting more persistent writes while already low on disk risks losing exactly the messages you're trying to protect), and the on-call engineer nearly restarts the node under the mistaken theory that "something is stuck." Nothing is stuck: §8(c)'s compaction is background and threshold-triggered, and a purge of live entries doesn't force an immediate rewrite of every file they happened to live in. The actual fix in the moment is to wait (compaction does eventually run) or to trigger it more aggressively by understanding which files are fragmented; the durable fix is provisioning disk headroom well above what a single large backlog could ever consume, specifically because reclaiming space is not instantaneous.

Incident 2: quorum queue disk growth during a network partition

During a partition that isolates one node from the majority, that node's Ra log for every quorum queue it hosts keeps accepting local WAL writes for entries it cannot get acknowledged by a majority, and — more importantly — the log cannot be trimmed via snapshot until the node rejoins and catches up, because a snapshot can only discard log entries that are known to be durably replicated. A long partition on a busy quorum queue cluster shows up as one node's disk usage climbing steadily with no obvious cause in the application logs; the rabbitmq-diagnostics output for that queue's Ra members shows a large, growing commit_index/last_applied gap. The lesson generalizes: any Raft-backed system pays for partition tolerance in local log growth on the minority side, and operators need disk headroom sized for "longest tolerable partition," not just "steady-state throughput."

Incident 3: "durable" queue, transient messages, silent loss after a routine restart

A rolling upgrade restarts brokers one at a time, as documented. On the first node restart, a queue believed fully durable loses every message that was in flight. Post-incident review finds the publisher library's default was delivery_mode=1 — nobody had explicitly set persistence at the message level, because the team's mental model was "the queue is durable, so messages in it are safe." The exchange and queue were both correctly durable; the message property, the third independent condition from §1, was never set. The actual fix was trivial (set the property) but took hours to diagnose because every piece of visible configuration — the queue's durability flag in the management UI — looked correct.

Simplified but faithful in structure and naming. First, writing a persistent message into the store:

erlangrabbit_msg_store.erl — write/3, simplified
write(MsgId, Msg, State = #msstate{current_file = CurFile,
                                    current_offset = Offset,
                                    index_ets = IndexEts}) ->
    Bin = rabbit_msg_file:serialize(MsgId, Msg),
    Size = byte_size(Bin),
    %% append-only: always write at the current file's end offset
    ok = append_to_current_file(State, Bin),
    %% one ETS row per message id: where it lives, how many queues reference it
    case ets:lookup(IndexEts, MsgId) of
        [] ->
            ets:insert(IndexEts, {MsgId, CurFile, Offset, Size, _RefCount = 1});
        [{MsgId, F, O, S, RefCount}] ->
            %% same message id published again (e.g. fanout to another queue) —
            %% do NOT write the bytes twice, just bump the refcount
            ets:insert(IndexEts, {MsgId, F, O, S, RefCount + 1})
    end,
    maybe_roll_file(State#msstate{current_offset = Offset + Size}).

Then, the compaction pass — the code that actually reclaims the holes §6 and §8(c) describe:

erlangrabbit_msg_store_gc.erl — attempt_compaction/3, simplified
attempt_compaction(FileA, FileB, State) ->
    #file_summary{valid_total = ValidA} = summary(FileA),
    #file_summary{valid_total = ValidB} = summary(FileB),
    Threshold = State#gcstate.file_size_limit * State#gcstate.gc_ratio,
    case ValidA + ValidB < Threshold of
        false ->
            {skip, "not fragmented enough yet"};
        true ->
            %% read every still-referenced message out of BOTH files, in file order —
            %% dead (refcount==0) messages are simply never re-read, i.e. discarded
            LiveMsgs = read_live_messages(FileA) ++ read_live_messages(FileB),
            {ok, DestFile} = open_compaction_target(State),
            NewLocations = append_all(DestFile, LiveMsgs),
            %% update the ETS index BEFORE deleting the old files — readers must
            %% never observe a location that points at a file that no longer exists
            update_index_locations(NewLocations),
            delete_file(FileA), delete_file(FileB),
            {ok, compacted}
    end.

Finally, the recovery entry point — reconciling queue index against message store at boot:

erlangrabbit_queue_index.erl — recover_segment/2, simplified
recover_segment(SegmentPath, MsgStore) ->
    {ok, Bin} = file:read_file(SegmentPath),
    Entries = parse_entries(Bin),      %% may raise on a torn trailing record
    case Entries of
        {ok, Parsed, TornTailBytes} ->
            case byte_size(TornTailBytes) > 0 of
                true  -> rabbit_log:warning("discarding torn trailing entry, ~p bytes",
                                                [byte_size(TornTailBytes)]);
                false -> ok
            end,
            %% cross-check: every message id this segment references must actually
            %% exist in the message store, or it was never durably written
            [Entry || Entry <- Parsed,
                      rabbit_msg_store:contains(MsgStore, Entry#entry.msg_id)]
    end.
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Update the index before deleting anything. The GC pass always makes the new location durable and visible before removing the old one — an ordering that guarantees a crash mid-compaction leaves either the old files intact (if the crash was before the index update) or the new file intact with a correct index (if after), never a dangling reference. 2. Recovery trusts nothing it can't cross-check. A queue index entry referencing a message id is not proof the message exists — a crash could have truncated the message store's own write. Recovery reconciles both structures rather than trusting either alone. 3. Torn writes are expected, not exceptional. The last segment written before a crash may contain a partial record; the parser is written to detect and discard it cleanly rather than fail recovery outright — a design borrowed from write-ahead logging in general and reused nearly verbatim in ra_log_wal's own recovery path.

Operationally, rabbitmq-diagnostics exposes most of this without reading raw files: rabbitmq-diagnostics observer for live process/queue-index memory, and management-plugin metrics for message-store file counts and per-queue disk-message counts. Topology — exchanges, queues, bindings, policies — can be exported and imported via rabbitmqctl export_definitions / import_definitions, but this is explicitly not a message backup: it recreates the empty shape of your broker, not its data. The honest operational posture, stated plainly: RabbitMQ is a message broker, not a database of record. Treat topology as reproducible infrastructure-as-code, and treat "the broker cluster is permanently destroyed" as a scenario your application design — not your backup strategy — must be able to tolerate, typically by having producers able to replay from an upstream source of truth.
