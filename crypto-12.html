ARC 01 · THE PROBLEM

Authentication without a shared secret still isn't enough

Chapter 6 built MACs — proof that a message came from someone holding a shared secret. Chapter 11 built Diffie–Hellman key exchange — a shared secret conjured from nothing, over a channel an attacker can read completely. Both left the same hole: neither one authenticates who you're talking to. A MAC only proves the other party knows the key — worthless until you already share one. Raw Diffie–Hellman proves nothing about identity at all: chapter 11's own closing demo inserted a man-in-the-middle who silently substituted both halves of the exchange, and neither honest party could tell.

Public-key digital signatures attack the asymmetry directly. Instead of a shared secret, one party holds a private key and the other verifies against the matching public key — no secret needs to travel between them at all. A valid signature over a message proves three things simultaneously: the message hasn't been altered since signing (integrity), it was produced by whoever holds the private key (authentication), and — unlike a MAC, where either side could have produced the tag — the signer cannot later deny having produced it, because nobody else could have (non-repudiation).

But solving authentication this way creates a new problem, and it is the entire subject of this chapter: a signature only proves the message came from whoever holds a particular private key. It proves nothing about whose key that is. If you connect to your-bank.com and the server hands you a public key and a perfectly valid signature over some handshake data, you have cryptographically proven that the response came from the holder of that specific key — and you have proven nothing at all about whether that key belongs to your bank or to whoever is sitting between you and it. Binding a public key to a real-world identity, at scale, without every client having to personally verify every server's key by hand, is the problem X.509 and the PKI trust model exist to solve.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Every HTTPS connection you have ever made ran this exact chapter's logic before a single application byte was exchanged: a signature check per certificate, a validity-window check per certificate, an authorization check (basicConstraints) per certificate, walked from a server's leaf certificate up to a root your browser was configured, out of band, to already trust. Chapter 13 shows precisely where in the TLS 1.3 handshake this chain gets sent and verified. Get this chapter's model right and chapter 13 is mostly plumbing around it.

DEEP CONTEXT · WHY "CERTIFICATE"?

The word predates computing entirely — a paper certificate is a trusted third party's written assertion ("I attest that X is true"). Loren Kohnfelder's 1978 MIT thesis proposed the digital analogue almost exactly as it works today: a trusted authority signs a statement binding a name to a public key, and anyone who trusts the authority's own key transitively trusts the binding. Every certificate you have ever relied on is still, structurally, that same idea — a bureaucratic paper-trail concept, implemented in modular exponentiation.

ARC 03 · NAIVE SOLUTION

Attempt #1: just trust whatever key the server sends you

Derive it honestly. You have signatures now — so surely the fix for chapter 11's MITM is simple: have the server sign its handshake data, send its public key alongside, and verify. Here is that "fix," and it is not a strawman built to be obviously wrong — it is what an engineer who has just learned RSA, and nothing else, will reach for first:

pythonnaive_connect.py — trust-on-first-response
def connect(host, port):
    sock = tcp_connect(host, port)

    # server just... sends its public key over the wire
    server_pubkey = sock.recv(PUBKEY_SIZE)

    # and a signature proving it holds the matching private key
    challenge = random_bytes(32)
    sock.send(challenge)
    sig = sock.recv(SIG_SIZE)

    if not rsa_verify(server_pubkey, challenge, sig):
        raise Exception("signature check failed")

    # "the signature is valid, so this must really be my bank" — is it?
    session_key = generate_random_key()
    sock.send(rsa_encrypt(session_key, server_pubkey))
    return encrypted_channel(sock, session_key)

Every cryptographic operation here is executed correctly. The signature genuinely proves the responder holds the private key matching server_pubkey. That is exactly the trap: correctness of the math says nothing about correctness of the binding between that key and your-bank.com. The client never asked "is this the key your bank uses" — it asked "does whoever responded on this TCP connection hold some private key," and the answer to that question is trivially yes for absolutely anyone who can intercept the connection and generate a fresh key pair of their own.

ARC 04 · WHY IT FAILS

Zero cryptographic work required — and it has happened for real

Quantify the failure precisely, because the contrast with the rest of this course is the whole point. Breaking RSA-2048 by brute force costs on the order of 2112 operations (chapter 10's estimate). Breaking §3's naive protocol costs zero cryptographic operations — the attacker doesn't touch the signature scheme at all. They intercept the connection (on-path) or redirect it to themselves (off-path), generate their own RSA key pair in milliseconds, and answer the challenge with a perfectly valid signature under a key they made up. The victim's code has no field, no fact, no prior state to check that key against — so it accepts.

This is not a hypothetical attacker position. Every one of the following is a documented, repeatable way to sit on the path between a client and a server, none requiring breaking any cryptography:

  • ARP spoofing on a shared LAN (coffee-shop Wi-Fi, a compromised office network) — trivial, tool-assisted, decades old.
  • Rogue access points — an attacker's Wi-Fi hotspot named to look legitimate; the "connection" to the real server never happens at all.
  • DNS cache poisoning — pre-DNSSEC, Kaminsky's 2008 attack showed off-path DNS forgery was practical at internet scale.
  • BGP hijacking — announcing someone else's IP prefix from the wrong network; demonstrated repeatedly in the wild (see §6's MyEtherWallet case).
WHEN THE "TRUST ANCHOR" ITSELF IS THE ATTACK: SUPERFISH & eDellRoot (2015)

The naive model's failure mode got a real, mass-market instance that is worse than plain MITM. In 2015, Lenovo shipped consumer laptops with Superfish VisualDiscovery adware that installed its own trusted root certificate into Windows — and reused the identical root private key across every affected machine. Anyone who extracted that one key (researchers did, within days) could forge a validly-signed certificate for any domain that every Superfish-infected laptop would silently accept, no MITM position even required to fabricate the cert — just a network position to serve it. Dell's eDellRoot incident the same year repeated the mistake with a different reused root. Both are the naive model's core flaw in its most concentrated form: a "trust this key" decision made once, at the factory, with catastrophic and durable blast radius. §7 onward is the industry's answer to *how* a key should be allowed to earn trust — and how that trust can be revoked.

ARC 05 · A SIGNATURE SCHEME, THEN A CHAIN OF TRUST

Deriving the fix in two moves

The naive protocol's flaw was never the signature scheme — RSA/ECDSA signatures are exactly as sound here as everywhere else in this course. The flaw was trusting a key with no basis. Fix it in two moves, each of which is itself just "apply a signature one more time":

Move 1 — someone you already trust signs the binding

Instead of the server asserting its own key is legitimate, have a third party — a Certificate Authority (CA) — verify that the server genuinely controls your-bank.com, then sign a small, structured document (a certificate) stating "this public key belongs to your-bank.com, as of this date, according to me." Now the client's question changes from the unanswerable "is this key legitimate?" to the answerable "do I trust the CA that signed this binding?"

Move 2 — bootstrap trust in the CA itself, out of band

That just moves the problem one level up: how does the client trust the CA's key? The answer is definitional, not cryptographic — the client's operating system or browser ships a fixed list of root CA public keys, installed by the OS/browser vendor through a completely different channel (a software update, verified by its own separate signing chain, ultimately grounded in a decision a human vendor made to include that CA). This is the one non-cryptographic leap in the entire system: at some point, trust has to be planted rather than derived. Everything else — every certificate you will ever see — is signatures, chained, all the way back to one of those planted roots.

A ONE-SENTENCE NOTE ON WHICH SIGNATURE SCHEME

Nothing about the chain-of-trust idea cares whether the signature underneath is RSA or elliptic-curve. A CA signs a certificate the same way regardless of algorithm: hash the certificate's contents, apply a private-key operation, attach the result. §8 derives RSA-PSS vs the older RSA-PKCS#1 v1.5 in full, and touches ECDSA briefly — the elliptic-curve math itself (point addition, scalar multiplication, why the discrete-log problem is hard on a well-chosen curve) is derived in depth in the Blockchain course's chapter on digital signatures and curves (bc-04); this course assumes that grounding and spends its depth budget on what's unique to PKI instead.

ARC 06 · WHY THAT STILL COSTS

The bill for outsourcing trust to ~100 organizations

The chain-of-trust model works, and it is what actually secures the web — but "trust is planted, not derived" has real, recurring costs. Be precise about each one; §11 shows two of them detonating in production.

  • Every trusted root is equally powerful for every domain. A browser's trust store holds roughly 100–150 CAs, and the trust model gives every one of them equal authority to validly certify any domain on Earth — a small CA that mostly issues certificates for regional government sites is, cryptographically, just as able to mint a certificate for google.com as Google's own preferred CA is. Compromise the weakest of 150 links and you have compromised the guarantee for all of them. §11's DigiNotar case is this property causing real, targeted harm.
  • Domain validation checks control of a name, not intent or identity. The cheapest, most common issuance tier (Domain Validation, DV) proves the requester can respond to a challenge at the domain — serve a file at a well-known path, or answer a DNS query — nothing more. That control-of-the-network-path check is exactly what a BGP hijack can forge: in April 2018, an attacker announced a fraudulent BGP route through Amazon's infrastructure, hijacked traffic for a slice of the internet toward myetherwallet.com's DNS, and used the resulting control of the name to obtain a validly domain-validated Let's Encrypt certificate — then intercepted user sessions and stole roughly $150,000 in cryptocurrency, all without forging any signature or breaking any key.
  • Revocation is soft by default. §8 and §9 detail why, but the summary cost is: browsers mostly do not hard-fail a connection when a revocation check (CRL or OCSP) can't be completed, because hard-failing on every network hiccup would break the web for everyone whenever a CA's infrastructure has a bad day. An attacker who can also interfere with revocation-checking traffic often gets a revoked certificate accepted anyway.
  • Chain-building is genuinely complex. A server may have several valid certification paths (cross-signed roots during a transition, multiple intermediates), a client may need to fetch a missing intermediate over the network via the Authority Information Access extension, and different trust stores (Chrome's vs. an embedded device's five-year-old firmware) can validly disagree about which chains terminate in trust — a frequent cause of "works in my browser, fails on this one device" incidents during CA root rotations.
THE HONEST TRADE

None of this is a reason to prefer the naive model from §3 — that model has zero of these costs precisely because it has zero security. The chain-of-trust model's costs are the price of a real, if imperfect, answer to an unavoidable question: who do you trust, and on what basis? §7 assembles the full architecture that those costs actually buy you, and §9 gives an honest tradeoff table for the specific mechanisms involved.

ARC 08 · INTERNAL IMPLEMENTATION

Signatures, byte layout, and the validation algorithm — for real

Four pieces, in order: (a) RSA-PSS vs RSA-PKCS#1 v1.5, computed for real; (b) the real X.509 field-by-field structure; (c) the chain-validation algorithm precisely stated; (d) revocation mechanics — CRL, OCSP, and stapling.

(a) RSA-PSS vs RSA-PKCS#1 v1.5 — the same key, two paddings, one real difference

Textbook RSA (chapter 9) signs a message by computing signature = hash(m)d mod n and verifies by checking signaturee mod n == hash(m). That's the mathematical core of both schemes below — what differs is entirely in how the hash gets encoded into the number that actually gets raised to the power d, and that encoding difference is the entire security story.

RSA-PKCS#1 v1.5 (RFC 8017 §9.2) encodes deterministically: 0x00 0x01 [0xFF padding] 0x00 [DigestInfo || hash]. For a fixed message and key, this byte string is identical every single time. That determinism isn't a bug by itself, but the scheme has no tight security proof of existential unforgeability, and its rigid, hand-parsed structure produced real implementation-level breaks — Bleichenbacher's 2006 forgery exploited verifiers that accepted a signature after checking only a signature's prefix matched the expected padding, ignoring trailing garble, letting an attacker construct a forgery for public exponents as small as e=3.

RSA-PSS (RFC 8017 §9.1, EMSA-PSS) folds a fresh random salt into the hash input before encoding, so the same message and key produce a different encoded block on every signature. That randomization is what gives PSS a tight security proof — existential unforgeability under adaptive chosen-message attack (EUF-CMA) in the random oracle model (Bellare–Rogaway, 1996) — which PKCS#1 v1.5 lacks. RFC 8017 explicitly recommends PSS for new RSA signature deployments; PKCS#1 v1.5 remains supported chiefly for backward compatibility with the enormous installed base that predates PSS.

THE THREE-CLAUSE STRUCTURE — WORTH INTERNALIZING

    
A certificate has exactly three top-level parts: the tbsCertificate ("to be signed" — version through
    extensions, everything above), the signatureAlgorithm identifier, and the signatureValue itself.
    The issuer signs only the tbsCertificate bytes — which means every field inside it, including every
    extension, is cryptographically bound by the signature. Change any of them post-issuance — the subject name,
    the validity dates, the SAN list, even the basicConstraints CA flag — and the stored signature no longer matches;
    §15's simulator makes this concrete by making you do exactly that.

  


  
(c) Chain validation — the algorithm, precisely

  
Given a presented chain (leaf, then zero or more intermediates) and a trust store of root certificates, a
  validator walks from the leaf toward a root, running three checks against every certificate and a fourth
  against every non-leaf certificate:


  

    
pseudocodeverify_chain() — the algorithm every real validator implements

    
verify_chain(chain, trust_store, now):
    for i in range(len(chain)):
        cert = chain[i]
        issuer = chain[i + 1] if i + 1 < len(chain) else find_in(trust_store, cert.issuer)
        if issuer is None:
            return REJECT("no path to a trusted root")

        # check 1 — validity window, independent of signature or authorization
        if now < cert.notBefore or now > cert.notAfter:
            return REJECT("certificate expired or not yet valid")

        # check 2 — the signature, verified against the NEXT cert's public key
        if not rsa_or_ecdsa_verify(cert.tbsCertificate, cert.signature, issuer.publicKey):
            return REJECT("signature does not verify against issuer's public key")

        # check 3 — authorization: a non-leaf signer MUST be a CA
        if i + 1 < len(chain) and not issuer.basicConstraints.isCA:
            return REJECT("issuer is not authorized to sign certificates (CA:FALSE)")

    # check 4 — the root itself must already be a trust anchor, self-signature included
    root = chain[-1]
    if root not in trust_store or not rsa_or_ecdsa_verify(root.tbsCertificate, root.signature, root.publicKey):
        return REJECT("root is not a recognized trust anchor")

    return ACCEPT

  

  
Three points that trip engineers up on first reading, all load-bearing: (1) a certificate's own signature
  is checked against the next certificate's public key, never its own — a certificate cannot vouch for itself
  except the root, which is a special case by definition, not by exception; (2) the CA:TRUE check applies to
  the issuer, evaluated once per link, and is entirely independent of whether that issuer's own signature
  happens to verify — a validly-signed certificate that simply isn't authorized as a CA must still be rejected as a
  signer; (3) path length constraints (basicConstraints.pathLenConstraint) additionally cap how
  many more CA certificates may follow an intermediate — real validators track a running count and reject a chain
  that exceeds any ancestor's declared limit, even with every signature and every CA flag correct.


  
(d) Revocation: CRLs, OCSP, and stapling

  
A signature and a validity window tell you a certificate was legitimately issued and hasn't expired —
  neither tells you the private key wasn't stolen an hour ago. Revocation is the missing "and it hasn't been
  un-vouched-for since." Three mechanisms, in the order they were invented:

  
    
    
  • CRL (Certificate Revocation List). The CA periodically republishes a signed list of every serial
      number it has revoked, at a URL embedded in the certificate's CRL Distribution Points extension. A relying
      party fetches and parses the entire list to check one certificate — for a large CA, that list can run
      into megabytes, and it only gets larger over a cert's lifetime.
    • 
    
  • OCSP (Online Certificate Status Protocol, RFC 6960). Instead of a bulk list, the client asks the CA's
      OCSP responder a single, targeted question — "is serial number X revoked?" — and gets a small, freshly-signed
      answer. Far fresher than a CRL, at the cost of a live network round trip per certificate, per relying party,
      and a structural privacy leak: the CA (or anyone watching that traffic) learns exactly which sites you're
      visiting, in real time.
    • 
    
  • OCSP stapling (RFC 6066's status_request extension). The server — not the client
      — periodically queries OCSP itself, caches the signed, timestamped response, and "staples" it directly onto
      the TLS handshake. The client verifies the CA's signature on the stapled response but never contacts the CA
      or its OCSP responder at all: no round trip added to the handshake, no per-connection privacy leak. Chapter 13
      shows precisely where the staple attaches in the TLS 1.3 Certificate message.
    • 
  

  

    
THE UNCOMFORTABLE COMMON THREAD

    
All three mechanisms share the same soft-fail reality described in §6: if the revocation check can't be
    completed — the CRL server is down, the OCSP responder times out, the staple is simply absent because the
    server never fetched one — the overwhelming majority of clients proceed with the connection rather than reject
    it, because a hard-fail default would make the entire web fragile against ordinary infrastructure hiccups. §9
    compares the three honestly, including this shared weakness.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

  
Why 256 elliptic-curve bits beat 3072 RSA bits

  
Two independent axes matter here: how expensive each operation is in software, and how expensive it is for an
  attacker to break the key without it. Neither axis is symmetric between RSA and ECDSA.

  
    
    
  • RSA's sign/verify costs are asymmetric by design. Signing (the private-key operation) is a full
      modular exponentiation with a full-size exponent d — roughly 1–2 ms for RSA-2048 in software (far
      less with the CRT optimization real libraries use). Verifying uses the tiny public exponent e=65537
      (17 bits) — a handful of squarings, tens of microseconds. That asymmetry is a deliberate, useful property:
      verification (done constantly, by everyone) is made cheap; signing (done once, by the key holder) can afford
      to be relatively expensive.
    • 
    
  • ECDSA has no such asymmetry. Both sign and verify require a scalar multiplication on the curve —
      roughly comparable cost in each direction (tens to low hundreds of microseconds for P-256 in optimized
      software). Neither operation gets to be "the cheap one."
    • 
    
  • The attacker's cost is where the two algorithms diverge most sharply. The best known classical attack
      on RSA is the General Number Field Sieve, with sub-exponential complexity in the key size. The
      best known classical attack on the elliptic-curve discrete-log problem, for a well-chosen curve, is
      Pollard's rho, with fully exponential complexity — roughly 2n/2 group
      operations for an n-bit curve, with no known sub-exponential shortcut. That single complexity-class
      difference is the entire reason a 256-bit elliptic-curve key and a 3072-bit RSA key land at roughly the same
      ~128-bit security level (NIST SP 800-57 Part 1's equivalence table) — RSA needs a much bigger haystack because
      its best attack searches it much faster per unit of key size.
    • 
  

  
Concrete anchor for "how big is 2112, actually": the largest classically factored RSA modulus on
  public record, RSA-250 (829 bits), was factored in February 2020 at an estimated cost of roughly 2,700 CPU
  core-years. RSA-2048's estimated ~112-bit security level represents a gap of many, many orders of magnitude
  beyond that record — comfortably outside any publicly demonstrated classical capability. Plot both algorithms'
  real published key-size/security equivalences on a log scale and the shapes make the point visually:

ARC 11 · REAL-WORLD INCIDENTS

  
Two ways to lose trust in a CA — a break-in, and a slow decay


  
DigiNotar, 2011 — one intrusion, nationwide surveillance

  
DigiNotar was a small Dutch CA (a subsidiary of VASCO Data Security) whose signing infrastructure was breached
  starting around June 2011. The root-cause report that followed (commissioned from Fox-IT) was blunt: all of
  DigiNotar's certificate-issuing servers sat on one poorly segmented Windows domain, ran outdated and unpatched
  software, and had no effective intrusion detection — so once the attacker had a foothold, nothing internally
  distinguished a legitimate issuance request from a forged one. Over the following weeks the attacker issued more
  than 500 fraudulent certificates for domains including *.google.com, login.yahoo.com,
  addons.mozilla.org, and even intelligence-adjacent domains like *.cia.gov.

  
The fraudulent *.google.com certificate wasn't just minted and forgotten — it was used in the
  wild. Google and Fox-IT's subsequent analysis found requests consistent with active man-in-the-middle interception
  of Gmail traffic from roughly 300,000 distinct IP addresses, overwhelmingly located in Iran — a pattern strongly
  indicative of state-level surveillance rather than opportunistic fraud. The breach came to light only because
  Chrome shipped a hardcoded expectation (an early precursor to public-key pinning) for what Google's own
  certificates should look like, and a user's browser flagged the mismatch. Within days, every major browser vendor
  permanently distrusted DigiNotar's root; the company filed for bankruptcy about a month after disclosure.


  
Symantec, 2015–2017 — no single breach, a pattern the industry stopped tolerating

  
Symantec's CA business lost its trust for a completely different reason: not an intrusion, but a multi-year
  pattern of mis-issuance that Certificate Transparency logs — built partly in direct response to DigiNotar
  — made impossible to hide. In February 2015, CT monitoring surfaced unauthorized certificates Symantec had issued
  for google.com without Google's request, produced during internal testing. In September 2015,
  Symantec disclosed roughly 30,000 test certificates issued over several years without proper domain validation —
  again first surfaced through CT. A subsequent investigation found Symantec had delegated substantial issuance
  authority to registration-authority partners and resellers that were not held to the same audit standard as
  Symantec itself, compounding the risk of further undetected mis-issuance.

  
In March 2017, Google's Chrome team publicly announced a gradual, staged distrust of Symantec-issued
  certificates, explicitly citing "a long-running pattern of issues" rather than any one incident. Symantec sold its
  CA business to DigiCert later that year so existing customers could migrate to newly issued, independently audited
  certificates; the old Symantec roots were phased out of trust through Chrome 66 (April 2018, covering certificates
  issued before June 2016) and completed by Chrome 70 (October 2018).

  

    
TWO FAILURE MODES, ONE STRUCTURAL LESSON

    
DigiNotar failed to an external intrusion in weeks; Symantec failed to internal process decay over years —
    and yet both land on the same structural point from §6: every publicly trusted root is equally authorized to
    certify any domain, so a failure anywhere in a 100+ member trust store is everyone's problem, not just that
    CA's customers'. Certificate Transparency exists specifically because "wait for someone's browser to notice a
    mismatch," DigiNotar's actual discovery mechanism, does not scale as a detection strategy — CT turned mis-issuance
    from a years-long secret (Symantec) or a lucky accident (DigiNotar) into a publicly auditable log any domain
    owner can monitor for their own name, from any CA, within hours.

Cx509_vfy.c — X509_verify_cert(), the outer loop

    
int
X509_verify_cert(X509_STORE_CTX *ctx)
{
    /* Step 1: build a candidate chain from ctx->cert (the leaf) up
     * toward something in ctx->store — following issuer/subject DN
     * matches, and fetching missing intermediates via the Authority
     * Information Access (AIA) extension if the caller allows it.    */
    if (!build_chain(ctx))
        return verify_cb_cert(ctx, 0, X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT);

    /* Step 2: for every cert in the built chain, in order:        */
    return check_chain(ctx);   /* → check_cert_time(), internal_verify(),
                                 * check_chain_extensions() — §8(c)'s
                                 * pseudocode, in production form      */
}

  


  

    
Cv3_purp.c — check_chain_extensions(), the basicConstraints gate

    
static int
check_chain_extensions(X509_STORE_CTX *ctx)
{
    int plen = 0;   /* running path-length budget, tightened by
                     * each intermediate's own pathLenConstraint      */

    for (int i = sk_X509_num(ctx->chain) - 1; i >= 0; i--) {
        X509 *x = sk_X509_value(ctx->chain, i);
        int is_leaf = (i == 0);

        if (!is_leaf) {
            /* THE check from §8(c): a non-leaf signer MUST carry
             * basicConstraints CA:TRUE — independent of whether its
             * own signature verified cleanly.                       */
            if (!(x->ex_flags & EXFLAG_CA))
                return verify_cb_cert(ctx, x, X509_V_ERR_INVALID_CA);

            if (x->ex_pathlen != -1 && plen > x->ex_pathlen)
                return verify_cb_cert(ctx, x, X509_V_ERR_PATH_LENGTH_EXCEEDED);
            plen++;
        }
    }
    return 1;
}

  


  

    
Crsa_pss.c — RSA_verify_PKCS1_PSS_mgf1(), the EMSA-PSS check

    
int
RSA_verify_PKCS1_PSS_mgf1(RSA *rsa, const unsigned char *mHash,
                            const EVP_MD *Hash, const EVP_MD *mgf1Hash,
                            const unsigned char *EM, int sLen)
{
    /* EM = maskedDB || H || 0xbc  (RFC 8017 §9.1.2)                 */
    unsigned char *DB   = recover_via_mgf1(EM, mgf1Hash);     /* unmask     */
    unsigned char *salt = extract_salt(DB, sLen);              /* last sLen bytes of DB */
    unsigned char *Hp   = Hash("\0\0\0\0\0\0\0\0", mHash, salt);  /* recompute H' */

    /* accept iff the recomputed hash matches the embedded one —
     * note the salt is recovered, not re-derived deterministically:
     * PSS verification has to work for a DIFFERENT salt every time.  */
    return memcmp(Hp, H_field_of(EM), Hash->len) == 0;
}

  


  

    
WHY IT'S STRUCTURED THIS WAY — TWO CHOICES WORTH STEALING

    
1. Chain-building is separated from chain-checking. build_chain() can fail or find multiple
    candidate paths (cross-signed roots, several valid intermediates); check_chain() then evaluates one
    concrete, ordered path against the algorithm from §8(c). Conflating "find a path" with "is this path valid" is
    exactly the kind of ambiguity that produces path-building bugs mistaken for verification bugs. 2. The
    basicConstraints check is a completely separate function from signature verification (internal_verify(),
    not shown, does the actual modular exponentiation). That separation in the codebase mirrors the separation in
    the specification: a validator that only checked signatures would accept the exact misissuance scenario §15 lets
    you construct — a validly-signed certificate that simply isn't authorized to sign anything.
