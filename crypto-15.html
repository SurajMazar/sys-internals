the Physics of Side Channels

Chapters 2–13 assumed the attacker only sees ciphertext. In production, the attacker also sees how long your code took, where your keys live, and what happens when a key must change. This chapter is about the two failure modes that survive a mathematically perfect algorithm: comparing secrets in a way that leaks them one byte at a time, and managing secrets in a way that makes one leaked key catastrophic instead of contained.

ARC 01 · THE PROBLEM

A perfect cipher does not protect a careless comparison

Suppose your team has done everything right so far: AES-256-GCM for data at rest (chapter 7), HKDF for key derivation (chapter 8), TLS 1.3 on the wire (chapter 13). None of that protects the following fifteen-character line, which shows up in real codebases with disturbing regularity:

pseudocodethe line that undoes chapters 2–13
if (requestSignature == computeHmac(secretKey, requestBody)) {
    grantAccess();
}

Nothing here is cryptographically wrong — the HMAC itself is unforgeable. What is wrong is how the two values are compared. On almost every runtime, == between byte strings (or a hand-rolled loop that returns the moment it finds a mismatched byte) takes measurably less time when the strings differ in their first byte than when they differ in their last byte. That timing difference is a side channel: an oracle that answers the question "is byte i of your guess correct?" without ever revealing a single bit of the secret directly. Repeat the question enough times, byte by byte, and the entire secret falls out — the algorithm was never attacked at all.

This chapter treats that as one instance of a broader problem. A secret is not safe merely because the algorithm protecting it is strong; it is safe only if every operation that touches it — comparison, branching, table lookup, storage, and eventual replacement — is designed with the assumption that an adversary is watching something other than the ciphertext. Two threads run through everything below:

  • Verification side channels. How you check a secret against an expected value can leak the secret itself, byte by byte, through timing (this section, §3–§6, §10, §15) — and the same discipline extends to RSA and ECDSA private-key operations, where a secret-dependent branch or table index can leak key bits through instruction timing or CPU cache behavior.
  • Custody and lifecycle. Where a long-term key physically lives, how many systems can read it, and what happens when it must be replaced determines the blast radius of an eventual compromise — this is envelope encryption, KMS/HSM design, and rotation without downtime (§7–§9).
THIS IS NOT THEORETICAL

Kocher demonstrated practical timing attacks on RSA, DSS and Diffie-Hellman implementations in 1996. Boneh and Brumley recovered an OpenSSL RSA private key over a network in 2003. The Xbox 360's own hypervisor was compromised in 2007 through a timing leak in its own signature check. Lucky13 broke TLS's CBC-mode MAC verification in 2013 — and a 2016 OpenSSL patch (CVE-2016-2107) meant to close that exact class of bug reopened a padding oracle instead. Every one of these was found in production code written by competent engineers who trusted the algorithm and didn't think about the comparison.

Chapter 14 covered Heartbleed (CVE-2014-0160) as a memory-disclosure bug — a buffer over-read that handed an attacker raw process memory. The failures in this chapter are different in kind: no memory is ever disclosed, no bounds are ever violated, and every byte returned to the attacker is one they already guessed. The only thing that leaks is time, or its cousins — cache state, branch-predictor state, power draw. Defending against that requires a discipline most engineers never learn, because it isn't taught as "correctness" — a timing side-channel bug passes every unit test you will ever write.

DEEP CONTEXT · WHY 1996 AND NOT EARLIER

Timing side channels are as old as computing, but Paul Kocher's 1996 paper was the first to show they were exploitable against modern public-key cryptography, not just a curiosity. Before Kocher, "the algorithm is secure" and "the implementation is secure" were treated as the same claim. After 1996 they were permanently different claims, and a correct proof of the first buys you nothing about the second — a distinction this entire chapter, and modern secure-coding practice generally, is built on.

ARC 03 · NAIVE SOLUTION

The two defaults every language and every cloud console hands you

Derive the failure honestly — nobody sets out to write a timing oracle. Two naive defaults, taken separately, are each individually reasonable-looking code:

Naive #1: compare secrets the way you compare everything else

pseudocodenaive_verify.* — looks correct, passes every test
function verifyToken(provided, expected) {
    if (provided.length !== expected.length) return false;
    for (let i = 0; i < provided.length; i++) {
        if (provided[i] !== expected[i]) return false;  // ← exits the instant it finds a mismatch
    }
    return true;
}
// or, worse, the one-liner that hides the same bug:
function verifyTokenShort(provided, expected) { return provided === expected; }

Every unit test passes. The function is correct by every functional definition of correctness: given matching inputs it returns true, given non-matching inputs it returns false. Nothing in a typical code review flags it, because nothing about its output is wrong. The defect is entirely in its timing, a dimension almost no test suite measures.

Naive #2: one key, forever, in a config file

The second default is organizational rather than algorithmic: generate one symmetric key or one API secret, paste it into an environment variable or a config file, and reference it directly everywhere it's needed — in the application, in the backup job, in the analytics pipeline that was bolted on eighteen months later. There is no key identifier, no version, and no plan for what happens the day it needs to change (an employee with access leaves, a laptop with a .env file is stolen, a contractor's repo turns out to be public). "Rotate the key" becomes a synchronized, all-at-once, all-consumers-simultaneously event — which is precisely the kind of change nobody wants to run during business hours, so in practice it doesn't happen until an incident forces it.

BOTH ARE "OBVIOUSLY FINE" UNTIL MEASURED AGAINST THE RIGHT THREAT MODEL

Naive #1 is fine if the attacker cannot observe timing — true for a same-process function call, false the instant the comparison result is observable over a network, a shared cache line, or even a sufficiently precise same-machine measurement. Naive #2 is fine until the key must be revoked, and every key eventually must be revoked — an employee offboards, a vendor is breached, a compliance auditor asks "when did you last rotate this," and the honest answer is "never, because we can't without downtime." §4 puts numbers on both.

ARC 04 · WHY IT FAILS

Quantifying the leak: signal, noise, and the sample budget

Start with the comparison. The naive loop's running time is, to first order, proportional to the index of the first mismatched byte: comparing a token that's wrong in byte 0 takes one iteration; comparing one that's correct through byte 7 and wrong in byte 8 takes nine. On modern hardware that difference per byte is tiny — often single-digit nanoseconds to a few hundred nanoseconds, swamped by network jitter, OS scheduling noise, and garbage-collection pauses on any real request path. This is the fact naive implementations lean on, usually without saying so out loud: "the difference is too small to matter." It is exactly wrong, because of one property of averages.

THE STATISTICS THAT MAKE "TOO SMALL TO MEASURE" FALSE

If a single measurement has noise with standard deviation σ, the mean of N independent measurements has standard deviation σ/√N — the standard error shrinks with the square root of your sample count, with no floor. To reliably distinguish a true timing difference Δ from noise at roughly 5-sigma confidence (a reasonable bar when you're about to test 256 candidate byte values and don't want a false positive), you need N ≈ (5σ/Δ)² repeated measurements. A Δ of 50 nanoseconds against σ of 50 microseconds of network jitter needs roughly (5 × 50,000 / 50)² ≈ 2.5 million samples per byte guess — a lot, but utterly achievable for an automated script with network access and no rate limit. §10 turns this formula into an interactive chart.

This is also precisely what made Boneh and Brumley's 2003 result land as a shock: they recovered a 512-bit-class OpenSSL RSA private key over an actual local network, purely from how long the server took to respond to crafted requests, needing on the order of hundreds of thousands of timed queries — a number that sounds enormous until you remember an attacker's script can send that many overnight. Lucky13, a decade later, needed on the order of hundreds of thousands to tens of millions of TLS sessions depending on the exact configuration and refinement of the attack — again, automatable, again, not a theoretical curiosity.

Now quantify the second naive default. A single long-lived key shared by every consumer has a blast radius equal to everything that key touches — by construction, since nothing distinguishes one consumer's access from another's. Revocation is binary and global: you cannot invalidate the key for one compromised service without invalidating it for all of them simultaneously, which means the "cost of rotation" is not a gradual, schedulable expense — it is a step function that only gets paid during an incident, under the worst possible conditions, by the most stressed version of your team.

ARC 05 · THE FIX, DERIVED

Constant-time code: same work, every time, regardless of the secret

The fix for the comparison is not "make it faster" — it's "make its timing independent of the data." Constant-time code is a discipline, not a single trick: never branch on a secret bit, never index memory with a secret value, and never let the number of loop iterations, of compression-function calls, or of table lookups depend on anything an attacker is trying to learn. Step through the fix, from a single comparison up to RSA and ECDSA.

THE PATTERN BEHIND EVERY STEP

Replace "branch on the secret" with "compute both outcomes and select between them using arithmetic or bitmasks." A conditional becomes a multiplication by 0 or 1; a table lookup by secret index becomes a scan of the entire table with a mask applied at every entry; a variable number of loop iterations becomes a fixed number with dummy work on the iterations that "don't count." Every one of these costs more instructions than the fast path it replaces — §6 is honest about that bill.

ARC 06 · WHY THAT STILL COSTS

Constant-time is not free, and it is not even complete

Three honest costs, each one a reason people cut corners in practice — and why cutting them is a mistake:

  • Raw performance. Constant-time big-integer routines do the full-width operation every time instead of taking early exits or skipping zero limbs — OpenSSL's BN_mod_exp_mont_consttime is measurably slower per call than a variable-time modular exponentiation. For a TLS handshake's RSA/ECDSA operations that cost is a rounding error against network latency; for a hot loop doing millions of comparisons per second it is a real line item.
  • The compiler can undo your discipline. An optimizing compiler is allowed to reintroduce a branch your source code doesn't have, if it can prove the two paths are equivalent for some inputs it samples during optimization — dead-code elimination can delete a defensive "extra" XOR that looked redundant, and auto-vectorization can short-circuit a loop it decides is only ever checking equality. This is why real implementations (libsodium's sodium_memcmp, BoringSSL's constant_time.h) use volatile-adjacent tricks and heavy compiler-flag testing rather than trusting that "the loop looks constant-time in source" is the same claim as "the binary is constant-time."
  • Constant instruction timing does not mean constant cache behavior. A branch-free AES implementation that still indexes a 256-entry S-box lookup table with a secret byte is constant-time in the sense of "no secret-dependent branches" and still leaks, because which cache line gets pulled in depends on the secret index — this is exactly Bernstein's 2005 cache-timing attack on AES, and it's why chapter 3's S-box lookup table becomes a liability on shared hardware and why real constant-time AES either uses dedicated hardware instructions (AES-NI) or bitsliced implementations that touch every table entry uniformly.
"CONSTANT-TIME" HAS A SCOPE, AND YOU MUST KNOW IT

Constant-time code defends against timing and simple cache-line side channels observable by a remote or co-located software attacker. It says nothing about power analysis, electromagnetic emission, or an attacker with physical hardware access — different threat models, different (usually hardware-level) defenses. And it says nothing about speculative-execution side channels like Spectre, which can leak data across the very branches constant-time code was written to avoid, by executing code paths the CPU merely speculates might be taken. Constant-time discipline is necessary and, for its stated threat model, close to sufficient — it is not a universal side-channel amnesty.

On the custody side, the equivalent honest cost is architectural: routing every encrypt/decrypt operation through a remote KMS or HSM adds network latency (typically single-digit to double-digit milliseconds per call) and a hard availability dependency — if the KMS is unreachable, so is every secret it guards. §7 derives the standard answer to exactly this cost.

ARC 07 · FINAL ARCHITECTURE

The full lifecycle: verify, encrypt, custody, rotate

Put the two threads together into one system. A request arrives; its signature is checked with a constant-time comparison (never a branch on the secret). The payload it authorizes is encrypted with a per-object data encryption key (DEK), which is itself wrapped by a key encryption key (KEK) that never leaves a KMS/HSM boundary. THE INVARIANT THAT MAKES THIS SURVIVABLE

Exactly one class of secret is designed to never exist in plaintext outside the HSM boundary: the KEK. Everything else — DEKs, session tokens, TLS session keys — is deliberately short-lived, scoped to one object or one session, and cheap to regenerate. An attacker who fully compromises an application host gets the plaintext DEKs currently resident in that host's memory (bounded: only the objects actively being processed) and every wrapped DEK it can read from storage (useless without HSM access to unwrap them). They do not get the KEK, and they do not get every other tenant's data. This is the same "isolate the blast radius" instinct as process-per-connection in the PostgreSQL course or fault domains in the Kafka course — applied to key material instead of compute.

The KMS is called exactly twice per object lifetime — once to mint the DEK, once (much later) to unwrap it for reading — never once per byte of data. That's the entire economic argument for envelope encryption: bulk symmetric crypto happens locally at memory bandwidth; only the tiny, precious DEK ever crosses the network to the boundary that holds the KEK.

WHY VERSIONING BEATS "JUST SWAP THE KEY"

Every wrapped DEK and every rotating credential carries an explicit key-version identifier. Decrypt paths accept any version still inside its validity window; encrypt paths always use the newest. This turns "rotate the key" from a synchronized global event into an ordinary background job: old ciphertexts keep decrypting with the old version until a sweep re-encrypts them, new ciphertexts immediately use the new version, and at no point does a live request fail because "the key changed." The same pattern — dual-write, backfill, cutover, retire — is how you'd migrate a database column's format without downtime; secrets rotation is a special case of the general online-migration problem.

Read this as a spectrum, not a menu with one right answer: constant-time comparison is close to a free lunch and belongs everywhere secrets are checked; envelope encryption and versioned rotation cost real engineering effort and are worth it in proportion to how catastrophic a single-key compromise would be. Short-lived dynamic secrets are the strongest answer to the rotation problem specifically because they make the question "how do we rotate this" disappear — but they demand infrastructure most teams don't build until they've already been burned once.

ARC 10 · PERFORMANCE & ATTACK COST

Turning §4's formula into a knob you can feel

The naive comparison's per-byte complexity is O(k) where k is the index of the first mismatch — best case 1 iteration, worst case the full length. The constant-time comparison is O(n) always, by construction — that fixed cost is the entire security property. What turns the naive function's O(k) into a practical attack is the sample-count formula from §4: N ≈ (kσ/Δ)² measurements to reliably detect a per-byte timing difference Δ against measurement noise σ. READ THE CURVE, NOT JUST THE POINT

N grows with the square of 1/Δ — halving the timing signal quadruples the required samples, but never makes the attack impossible, only more expensive. This is why constant-time code aims for Δ = 0 exactly rather than "small": any nonzero, consistent Δ is eventually recoverable given a patient-enough attacker with unmetered access, and internet-facing endpoints should assume exactly that attacker exists. Internal, same-host comparisons face far lower σ (nanoseconds instead of microseconds of jitter) — which makes them easier to attack from a co-located process, not safer, a fact worth remembering the next time "it's an internal service" is offered as a reason to skip constant-time comparison.

ARC 11 · REAL-WORLD INCIDENTS

Five incidents, five different places the timing leaked from

1. Boneh & Brumley, 2003 — RSA over the actual network

"Remote Timing Attacks Are Practical" (USENIX Security 2003) recovered an OpenSSL server's RSA private key purely by timing its responses to crafted ciphertexts, over a real LAN. Root cause: the server's modular reduction (via Montgomery arithmetic) took a data-dependent extra subtraction step whose frequency correlated with the private key's bits. The fix that shipped industry-wide was RSA blinding — multiply the input by a random value before the private-key operation and divide it back out afterward, so the operation's internal timing no longer correlates with the actual message being processed. Blinding is still the standard countermeasure in every serious RSA implementation today.

2. The Xbox 360 hypervisor, 2007 — an early-exit HMAC check in your own bootloader

Documented publicly by Michael Steil and Felix Domke, the Xbox 360's hypervisor verified signed code updates with an HMAC comparison that — like this chapter's naive strawman — returned as soon as it found a mismatched byte. Attackers with physical access to the console could measure that timing difference and forge a valid signature for unsigned code, byte by byte, defeating a signature scheme that was itself never broken mathematically. The lesson generalizes past game consoles: a boot-time or firmware verification path is exactly the kind of code that's tested for correctness constantly and reviewed for timing almost never.

3. Lucky13, 2013 — a MAC-verification timing side channel, not a padding oracle

This is worth stating precisely, because it's commonly mis-described. TLS's CBC-mode record format places padding before the MAC is checked, so decryption must first interpret the padding to know where the MAC-covered plaintext ends. An attacker who flips bits in the ciphertext can manipulate what the server believes the padding length is — and OpenSSL's (and other implementations') MAC computation, HMAC, is built from a compression function called once per input block. A longer apparent plaintext (shorter apparent padding) means more HMAC compression-function calls before the MAC comparison even happens. That difference in the number of hash operations performed — not a "valid padding" vs. "invalid padding" error message — is what Lucky13 (AlFardan & Paterson, 2013) measured: a MAC-verification timing side channel. It required on the order of hundreds of thousands of sessions in the original result to fully exploit, refined significantly by follow-on work. Compare this to POODLE and BEAST (earlier chapters' territory): those are genuine padding oracles — an explicit distinguishable error. Lucky13 leaks through timing alone, even when the error messages themselves reveal nothing.

4. CVE-2016-2107 — fixing Lucky13 broke something else

OpenSSL's generic C code path adopted constant-time padding removal in response to Lucky13. Its separate, hand-optimized AES-NI code path for combined AES-CBC-HMAC-SHA1 — written for performance, not by the same reasoning — had its own padding-length handling, and a bug there reintroduced exactly the class of oracle Lucky13's fix was supposed to close, this time in a way that produced a directly observable decryption error rather than pure timing. The lesson: a security fix living in one code path does not protect a second, independently optimized code path implementing the same protocol logic — every fast-path reimplementation is a fresh opportunity to reintroduce a bug that was already fixed once.

5. The timing-attack CVE class never closes

The 2023 "Marvin Attack" research demonstrated that Bleichenbacher-style RSA PKCS#1 v1.5 timing oracles — first described in 1998 — were still present, in some form, across a wide range of TLS libraries a quarter century later, each requiring its own CVE and its own patch. Separately, several early open-source crypto wrapper libraries, including Google's own Keyczar project, shipped non-constant-time comparison helpers that were only caught by later audits. The pattern across all of it: this is not a class of bug that gets fixed once industry-wide. It gets fixed once per implementation, and every new implementation is a new chance to reintroduce it — which is exactly why "use a vetted, audited constant-time primitive from your language's standard cryptography library" is the practical recommendation this chapter ends on, not "understand the math and write your own."

First, the comparison primitive itself — this is the shape every serious library converges on:

Cconstant-time byte comparison — faithful to BoringSSL's CRYPTO_memcmp() shape
int CRYPTO_memcmp(const void *in_a, const void *in_b, size_t len) {
    const unsigned char *a = in_a, *b = in_b;
    unsigned char x = 0;

    /* No early return, ever — the loop always runs `len` times,
     * regardless of where (or whether) a and b first differ.   */
    for (size_t i = 0; i < len; i++)
        x |= a[i] ^ b[i];          /* accumulate; never branches on the result */

    return x;   /* 0 iff every byte matched — caller checks == 0 */
}

Next, the branchless selection primitive that lets constant-time code express an "if" without a branch — this is the building block behind constant-time RSA/ECDSA control flow from §5:

Cconstant_time.h — the branchless select, faithful to BoringSSL's shape
/* Returns all-1-bits if a == b, all-0-bits otherwise — a MASK, not a bool. */
crypto_word_t constant_time_eq_w(crypto_word_t a, crypto_word_t b) {
    crypto_word_t d = a ^ b;
    return constant_time_is_zero_w(d);   /* bit-trick, no branch inside either */
}

/* Selects `a` if mask is all-1s, `b` if mask is all-0s — NO if/else. */
crypto_word_t constant_time_select_w(crypto_word_t mask, crypto_word_t a, crypto_word_t b) {
    return (mask & a) | (~mask & b);
}

Finally, the envelope-encryption call pattern — this is pseudocode faithful to the shape shared by every major KMS's SDK, not any single vendor's exact API:

pseudocodeenvelope_crypto.* — the two KMS calls per object lifetime
function encryptObject(plaintext, kekId) {
    const { plaintextDek, wrappedDek } = kms.generateDataKey(kekId);  // 1 network call
    const { nonce, ciphertext, tag } = aes256gcm.seal(plaintextDek, plaintext);
    wipe(plaintextDek);                        // best-effort zero; see §6's compiler caveat
    return packEnvelope(kekId, wrappedDek, nonce, ciphertext, tag);
}

function decryptObject(blob) {
    const { kekId, wrappedDek, nonce, ciphertext, tag } = unpackEnvelope(blob);
    const plaintextDek = kms.decrypt(kekId, wrappedDek);   // 1 network call; KEK never leaves the HSM
    const plaintext = aes256gcm.open(plaintextDek, nonce, ciphertext, tag);
    wipe(plaintextDek);
    return plaintext;
}
WHY IT WAS BUILT THIS WAY

1. The comparison never returns early — not "usually," never, by construction of the loop. 2. Selection uses arithmetic masks, not conditionals — this is what lets the same code compile to the same instruction sequence regardless of the secret value being processed. 3. The KMS is called exactly twice, never once per byte of data — this is a latency and cost decision as much as a security one: bulk AES-GCM runs at local memory bandwidth, while every KMS round-trip pays real network latency, so the design minimizes crossings of that boundary to the two moments they're unavoidable: mint the key, and later, unwrap it.
