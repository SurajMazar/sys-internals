WHATSAPP ARCHITECTURE · CHAPTER 05

The Message
Delivery Pipeline

Chapters 3 and 4 built the cryptography: every message Alice sends is already sealed, per recipient device, before it leaves her phone. This chapter is about the unglamorous plumbing that gets that sealed envelope from Alice's phone to Bob's — reliably, exactly once as far as the UI is concerned, in order, even though Bob's phone might be off, asleep, or in a dead zone for a week. The server never opens the envelope. It just has to not lose it, not duplicate it (visibly), and not keep it a moment longer than necessary.

ARC 01 · THE PROBLEM

Two phones, no shared clock, no guaranteed connection

Strip away the cryptography for a moment and look at the raw distributed-systems problem: Alice's phone wants to hand a payload to Bob's phone. Neither device is reachable by the other directly — both sit behind NAT, on cellular radios that sleep to save battery, on networks that partition constantly. There is exactly one thing both phones can reliably reach: a server operated by the messaging provider. Everything in this chapter is the consequence of that one constraint.

Unpack what "reliable delivery" has to mean for a product used for coordinating funerals, closing business deals, and reporting emergencies:

  • Durability across disconnection. Bob might be on a flight, in a village with no signal, or simply have his phone off for a week. The message cannot simply vanish because his socket wasn't open at the instant Alice hit send.
  • No duplicate visible to the user. The network between phone and server is unreliable — packets drop, TCP connections reset mid-handshake, mobile radios hand off between towers. Retries are inevitable, so something must ensure Bob doesn't see "hey are we still on for lunch" three times.
  • Per-chat ordering that matches human intuition. If Alice sends "yes" then "at 7pm", Bob's screen must not show them swapped, even if the underlying transport reorders packets.
  • Confirmation that means something. Alice needs to know whether her message left her phone, reached the server, reached Bob's phone, or was actually read — four different facts, encoded today as one/two/blue ticks.
  • Minimal custody. The server is handling ciphertext it cannot read (chapters 3–4), but it still has a responsibility, cost, and legal exposure for every byte it stores, for however long it stores it. The right amount of storage is the minimum that makes delivery reliable — not one byte more.

The rest of this chapter derives the mechanism that satisfies all five simultaneously: store-and-forward. It is a boring name for the single most load-bearing subsystem in the whole product — the one that turns "a phone with a socket" into "a messaging service."

WHY THIS MATTERS FOR THE REST OF THE COURSE

Every other chapter assumes this pipeline works. Group messaging (chapter 6) is fan-out on top of it. Media (chapter 7) is a pointer through it. Multi-device (chapter 8) is N queues instead of one. If you cannot explain, from first principles, why a message queue per device (not per user) sits between Alice and Bob, and why it is deleted on ack rather than kept, you cannot reason about anything built on top of it.

DEEP CONTEXT · WHY ERLANG

The founding engineering team (ex-Yahoo infrastructure engineers) chose Erlang/OTP specifically because the delivery problem is a supervision-and-messaging problem: millions of lightweight processes, each modeling one connected device, that need to survive individual crashes and pass messages between each other without shared mutable state. The original chat server used ejabberd, an Erlang XMPP server, forked and rewritten as the protocol diverged (internally called FunXMPP) — but the process-per-connection, let-it-crash philosophy of Erlang/OTP is the reason a single chat server process can hold millions of live device connections (published figures: ~2 million concurrent TCP connections per physical server, and a landmark ~1 million on a single machine as early as 2011, documented in the WhatsApp engineering blog post "1 million is so 2011").

ARC 03 · NAIVE SOLUTION

Attempt #1: relay it live or don't bother

The simplest possible design treats the chat server as a pure switchboard: if the recipient's socket is open, forward the bytes; if not, the message is lost, and it is the client's problem to notice and resend. No queue, no disk, no state beyond "who is connected right now."

pseudocodenaive_relay — the strawman, annotated
function onMessageFromAlice(msg) {
    const bobSocket = liveConnections.get(msg.to);      // in-memory map only

    if (bobSocket) {
        bobSocket.send(msg.ciphertext);          // forward the sealed envelope, unopened
        ackToSender(msg.from, msg.id);           // tick 1: "left the server"
    } else {
        /* Bob isn't connected right now. There is nowhere to put this.
         * It is dropped on the floor. Alice's client will eventually
         * time out and... do what, exactly? */
        nackToSender(msg.from, msg.id, "recipient offline");
    }
}

This is not a strawman built to be laughed at — it is exactly right for a large class of systems: a live screen-share cursor, a "user is typing…" indicator, a stock ticker. If the recipient isn't there to see it right now, the datum has no value later. The mistake is applying that same logic to a chat message, where the whole point is that it retains meaning arbitrarily far in the future.

ARC 04 · WHY IT FAILS

Mobile devices are offline far more than intuition suggests

The naive relay's failure rate is not an edge case — it is the common case, once you look at real numbers instead of a desk-tested demo where both clients stay connected the whole time:

  • Radios sleep by design. To conserve battery, a phone's cellular and Wi-Fi radios drop to low-power states aggressively; the OS reclaims background network sockets; a "connected" app is not always holding an open TCP connection to the chat server at every instant, even while running.
  • Coverage is not continuous. Subways, elevators, rural areas, international roaming with data disabled, flights, dead batteries — a device can be genuinely unreachable for minutes to weeks. WhatsApp's own published retention behavior (chapter's §6) assumes offline windows up to 30 days as a normal case, not a bug.
  • The sender cannot hold the retry burden alone. If losslessness depended on Alice's phone retrying until Bob appears, Alice's phone would need to stay resident, awake, and holding the plaintext (or re-encrypting on each attempt) for potentially a week — burning her battery and data for a delay that has nothing to do with her device at all. The cost of Bob's absence would be paid by Alice. That is exactly backwards: the actor best positioned to wait indefinitely, cheaply, is a data-center server, not a phone in someone's pocket.
THE NUMBERS

Model it simply: if a device is reachable (socket-open, radio-awake) only p fraction of the time it is logically "online," and Alice sends at a uniformly random moment, the naive relay's single-attempt delivery probability is just p. For a phone that is asleep/backgrounded/off even 20% of the day — a conservative estimate — that's a 20% loss rate on first attempt, every single message, with no mechanism to recover the lost 20% short of the sender manually re-sending and the user noticing it never arrived. At WhatsApp's scale (published figures: over 100 billion messages/day as of the early 2020s), a 20% naive loss rate is not a degraded experience — it is not a product.

So something has to hold the message durably, outside of both phones, for as long as it takes. That "something" is the server — but how it holds the message, and for how long, is exactly the design space the next section works through.

ARC 05 · CANDIDATES, EXAMINED

Who holds the message, and for how long?

Candidate A: sender-side infinite retry

Keep the naive relay, but make Alice's client remember every unacknowledged message and retry periodically — hours, days, whenever the app gets a chance to run in the background. Rejected for the reason given in §4: mobile OSes aggressively restrict background execution (iOS background app refresh budgets are minutes, not days), so "Alice's phone retries for a week" is not a real capability she has. It also means every unread message multiplies Alice's battery and data cost by however many times Bob is offline, for a delay that is entirely about Bob.

Candidate B: full cloud history (the iMessage/Telegram-cloud shape)

Store every message server-side, indefinitely, associated with the conversation — not just until delivery, but as permanent history the way Apple's iCloud-backed iMessage or Telegram's cloud chats do. This solves delivery trivially: Bob's client just fetches everything since his last sync, whenever he reconnects, no matter how long that takes. Examine why WhatsApp's engineering culture rejected this as the default, even though it is architecturally simpler:

  • Storage cost compounds forever. 100B+ messages/day, kept indefinitely, is an unbounded and ever-growing storage bill — for data the operator has structured its entire security story around not being able to read (chapters 3–4). Keeping it "just in case" undercuts the value proposition of encrypting it at all.
  • Privacy and legal exposure scale with what you hold. Every stored ciphertext blob is a byte that a subpoena, a breach, or an insider can be pointed at — even encrypted, metadata about its existence, size, and timing has value to an attacker. The WhatsApp security whitepaper's central claim — "we don't have your messages" — is only true if the statement is literally, mechanically true, not "true once we delete our backups eventually."
  • It doesn't match how phones already work. Chat history already lives durably on-device (and, optionally, in the user's own cloud backup, a separate and explicitly opt-in mechanism with its own key-management story) — duplicating that permanently server-side is redundant custody of the same data.

Candidate C: store-and-forward with delete-on-ack ✓

Accept custody of the ciphertext just long enough to guarantee delivery, in a durable, per-recipient-device queue — and delete the copy the instant the recipient's device confirms receipt. This is the shape that satisfies every requirement from §1 without paying candidate B's storage/privacy bill or candidate A's battery/impossibility bill: the server is a relay with a a temporary buffer, not an archive.

THE CLINCHING ARGUMENT: DELETE-ON-ACK IS A SECURITY PROPERTY, NOT JUST A COST SAVING

The reason store-and-forward with immediate deletion is the right answer, not merely a cheaper one: once a message is deleted from the queue, it cannot later be compelled, leaked, or breached from that server — because it is not there. Combined with per-device end-to-end encryption, the server's window of custody shrinks to "between send and the recipient's next connection," typically seconds. That window is the entire attack surface the storage layer contributes to message confidentiality, and store-and-forward minimizes it on purpose.

ARC 06 · WHY THAT STILL COSTS

The bill for store-and-forward

Store-and-forward is the right shape, but it is not free, and every cost below is a physical consequence of holding state on behalf of a device that might not come back soon:

  • Queue growth for chronically offline devices. A device that is off for a week accumulates every message sent to it in that window. A user in a hundred active group chats can accumulate tens of thousands of queued messages before reconnecting — the queue must be sized and paged for that burst, not just the steady state.
  • Multi-device multiplies queues, not messages. Chapter 8 covers this in depth, but the shape matters here: because encryption is per-recipient-device (chapters 3–4), a user with a phone, a linked desktop client, and a linked tablet has three queues, each holding its own copy of every ciphertext until that specific device acks. A message isn't "delivered to Bob" — it's delivered to each of Bob's devices independently.
  • A hard TTL is mandatory. Without an expiry, a permanently-abandoned device (a broken phone whose owner never re-registers) leaves a queue that grows forever with no consumer. WhatsApp's documented behavior expires undelivered messages after roughly 30 days — the queue is a buffer for temporary absence, not a mailbox for someone who never comes back.
  • Reconnect is a thundering-herd risk. A device returning after a long absence must drain its entire backlog, and the server must avoid dumping tens of thousands of messages down one socket in one burst — both for the server's own fairness across connections and for the receiving device's ability to process, decrypt, and render that many messages without freezing the UI.
  • Push notifications are a dependency on someone else's infrastructure. Waking a backgrounded phone requires Apple's or Google's push service (APNs/FCM) — a system WhatsApp does not control, with its own payload-size limits, best-effort delivery guarantee, and rate constraints. The delivery pipeline's reliability is now partly bounded by a third party's SLA.
THE HONEST ADMISSION

Store-and-forward converts "the message might be lost" into "the message is durable, but delivery latency is now unbounded and queue depth is a live operational metric." That is a strictly better problem to have — but it is still a problem, and every subsystem in §7–§8 exists to bound it: TTLs bound storage, batched drains bound burst load, and push notifications bound how long a device stays unreachable in the first place.

WHY "PER-DEVICE" QUEUE AND NOT "PER-USER"

Because the unit of encryption is a device's Signal session (chapters 3–4), the unit of undelivered-message storage has to be a device too — Bob's phone and Bob's linked desktop each need their own copy of a group of ciphertexts, acked independently, because each device decrypts with its own session state. "Deliver to Bob" is really "deliver to every one of Bob's registered devices," each tracked and expired on its own schedule.

ARC 08 · INTERNAL IMPLEMENTATION

Wire formats, the tick state machine, and the queue

Three pieces: (a) the tick model as an explicit end-to-end state machine, (b) idempotency and ordering under at-least-once delivery, (c) the queue itself and what happens as it grows.

(a) The tick model — four states, not three UI glyphs

The single/double/blue-tick UI is a rendering of an underlying state machine with real edge cases. Step through it — including the states most users never think about explicitly:

The delivery state machine, end to endSTEP-BY-STEP
THE ANOMALY EVERY USER HAS SEEN

"One grey tick for six hours, then suddenly two" is not a bug — it is the state machine working exactly as designed. A single tick means "the server has custody and is holding it in Bob's queue"; it says nothing about how close Bob is to seeing it. The tick flips to double only on Bob's device's explicit ack, which requires Bob's device to actually connect — an event with no upper bound on latency. Symmetrically, a blue tick can appear from a read receipt generated when Bob's notification is expanded or auto-previewed by the OS in some configurations, without Bob consciously "reading" the chat — which is precisely why read receipts are a contested privacy feature and, when disabled by Bob, WhatsApp's documented behavior is reciprocal: Bob stops seeing other people's blue ticks too, not just hiding his own — the protocol turns the same field off in both directions rather than let one user surveil while opting out themselves.

(b) At-least-once delivery, client-side dedup, and why exactly-once is impossible

Every message carries a client-generated unique ID before it is ever encrypted or sent. This single design decision is what makes the rest of the reliability story tractable. Consider the ambiguous-failure case: Alice sends, the server persists the message into Bob's queue and even forwards it — but the acknowledgment back to Alice is lost to a flaky connection. Alice's client, having received no ack, must assume the send failed and retry. Now Bob's queue has received the same logical message twice.

This is not a corner case to be engineered away — it is the Two Generals Problem, and it is mathematically unsolvable over an unreliable network with no upper bound on message delay. No protocol fixes it; every reliable-messaging system on Earth works around it the same way: retry aggressively (accepting duplicates as the price of not losing anything), and push the responsibility for recognizing duplicates onto the receiving side, which has the one piece of information the network lost — the message ID. Bob's device (and, before that, Bob's server-side queue) checks incoming ciphertext against recently-seen client message IDs and drops exact repeats before they ever render. The honest name for the resulting guarantee is at-least-once delivery with client-side dedup, yielding effectively-exactly-once at the UI — a precise, defensible claim, unlike the informal "exactly-once delivery" marketing shorthand that the theory forbids.

(c) Ordering: per-chat is guaranteed, global is not — and cannot be

Within one conversation, the sender attaches a monotonic per-sender sequence counter, and the recipient's client sorts by that counter (falling back to server receipt timestamp for cross-sender interleaving in a group). This guarantees "Alice's messages render in the order Alice sent them" — a property enforceable because there is one authority (Alice's own device) issuing the sequence numbers. It does not guarantee that if Alice sends at T and Carol sends at T+1ms in the same group, Alice's arrives first — there is no global clock across independent devices on independent networks, and Lamport's original observation about distributed systems applies without modification: you can only order events that are causally related. The visible anomaly is two people's messages in a fast-moving group chat appearing "out of turn" relative to wall-clock send time — an artifact users learn to read past, not a defect the client can fully hide.

QUEUE GROWTH AS A FAILURE MODE

A device that connects but never acks — a client bug that receives and renders but fails to send the delivery receipt back — is worse than one that never connects at all. A never-connecting device's queue is bounded by the 30-day TTL and a known cause (device offline). A connected-but-non-acking device looks alive to routing, keeps receiving pushes suppressed (it appears reachable), yet its queue never drains, because nothing ever tells the server it is safe to delete. This is a real operational pathology: monitoring on queue depth per device, not just aggregate queue size, is what catches it — a small number of devices in this state can quietly accumulate a disproportionate share of total queued bytes.

ARC 10 · PERFORMANCE CHARACTERISTICS

Costs you can predict before you measure them

  • Queue insert/delete: O(1) amortized per message — a per-device queue is fundamentally an append + indexed-delete structure (in the classic architecture, an Mnesia table keyed by device ID, held in RAM with disk-backed replication for durability across node restarts).
  • Memory per queued message: ciphertext size (typically under 1 KB for text) plus fixed envelope overhead (sender/recipient device IDs, message ID, sequence number, timestamp) — call it a small constant factor over payload size; media (chapter 7) is stored out-of-band as an encrypted blob with only a pointer in the message envelope, keeping queue entries small even for a photo.
  • Network round trips per message, happy path: one — Alice → server → Bob, with acks flowing back asynchronously over the same already-open persistent connections (no new TCP/TLS handshake per message).
  • Battery/radio cost: the dominant cost is not sending the message — it is keeping the radio's data path warm enough to receive a push wake-up promptly. This is exactly what APNs/FCM solve: one shared, OS-managed persistent connection per device services wake-ups for every app, instead of every app (WhatsApp included) holding its own always-on socket and draining the battery independently.
  • Push payload constraints: APNs and FCM both cap notification payload size (historically ~4 KB class limits) and are explicitly best-effort, not guaranteed — which is why the notification carries only a wake signal or a small encrypted hint, never enough to reconstruct the message, and never a substitute for the client's own connection back to the chat server.

The curve is an analytic sketch — queue depth grows linearly with offline duration times arrival rate, and drain time is dominated by whichever is scarcer: server-side flow control (batching sends so a phone's UI thread and radio aren't asked to process thousands of messages in one tick) or the device's own decrypt-and-render throughput. The point is the shape: unflow-controlled drains create a visible "burst then freeze" pattern users have all experienced returning from a flight; flow control trades a few extra seconds of wall-clock drain time for a UI that never stalls.

ARC 11 · REAL-WORLD PRODUCTION

Incidents and milestones that prove the model

Milestone: 900 million users, one architecture

At the time of its 2014 acquisition by Facebook for roughly $19 billion, WhatsApp was serving several hundred million users with a famously small engineering team (widely reported at around 50 engineers), a ratio that is direct evidence for the architecture's efficiency: a store-and-forward pipeline built on Erlang/OTP's process model needed comparatively little operational headcount per connected device, because per-device state (a queue, a connection process) is cheap and supervised automatically rather than hand-managed.

Incident: the October 2021 global outage

A BGP configuration change withdrew routes to Facebook's (Meta's) own data centers, taking WhatsApp, Instagram, and Facebook fully offline for roughly six hours. This is instructive for the delivery pipeline specifically: it is a reminder that store-and-forward's guarantees are conditional on the chat servers being reachable at all — a durable per-device queue is worthless if routing to the data center holding it is gone. The incident also produced a predictable side effect this chapter should let you predict yourself: when the network returned, a synchronized reconnect storm across hundreds of millions of devices hit the same infrastructure simultaneously — exactly the thundering-herd risk named in §6, at a scale few systems ever experience.

Scaling milestone: the "two million connections" server

WhatsApp's engineering blog documented, across several posts in the early 2010s, pushing a single FreeBSD box running the Erlang chat server past one million, then two million, concurrent TCP connections — each connection a lightweight Erlang process holding session state and a reference into that device's queue. The headline number matters less than what it proves architecturally: because the delivery pipeline keeps per-device state small and supervised (not per-connection threads with OS-level overhead), horizontal capacity scaled by adding commodity servers rather than by re-architecting the queue model as the user base went from millions to over a billion.

ARC 13 · IMPLEMENTATION WALKTHROUGH

Protocol messages, queue structure, and the dedup path

There is no public C source tree for WhatsApp's server internals — what follows is protocol-level structure consistent with the published engineering blog posts, the Signal protocol specs this system builds on, and first-principles derivation from the constraints in §1–§8. Where WhatsApp's exact internal service names are not public, roles are described instead of invented identifiers.

delivery-pipeline/ — roles, not published internal names
├── chat-server/
│ ├── ● connection.erl — one lightweight process per live device socket (Erlang/OTP)
│ ├── ● router.erl — resolves recipient device list + owning shard/queue
│ └── ack_handler.erl — tick-1/tick-2/read-receipt state transitions
├── queue/
│ ├── ● device_queue.erl — per-device Mnesia table: insert, drain, TTL sweep
│ └── dedup_index.erl — recently-seen client message IDs per device
├── push-gateway/
│ ├── ● apns_client.erl — wake-signal envelopes to Apple Push Notification service
│ └── fcm_client.erl — wake-signal envelopes to Firebase Cloud Messaging
└── client/(reference behavior, not server code)
├── ● send_queue.ts — per-message-ID retry with exponential backoff on ambiguous failure
└── dedup_render.ts — drops any incoming message ID already rendered

The router's core decision, simplified to the shape that matters:

Erlang-flavored pseudocoderouter — deliver-or-enqueue
route(Envelope) ->
    Devices = lookup_devices(Envelope#msg.to),         %% one entry per linked device
    [ deliver_to_device(D, Envelope) || D <- Devices ],
    ack_sender(Envelope#msg.from, Envelope#msg.id).      %% tick 1: server has custody

deliver_to_device(Device, Envelope) ->
    case connection_registry:find(Device) of
        {ok, Pid} ->
            Pid ! {push, Envelope};                      %% live socket: push immediately
            device_queue:enqueue_pending_ack(Device, Envelope);  %% held until THIS device acks
        not_found ->
            device_queue:enqueue(Device, Envelope),   %% durable, TTL'd store
            push_gateway:wake(Device)               %% APNs/FCM: hint only, no content
    end.

Note the detail easy to miss: even a "live" push down an open socket is provisionally kept in the queue until that device's ack arrives — the tick-1→tick-2 transition is what triggers deletion, not the act of sending. This is what makes retries safe: if the send succeeded but the ack was lost, the message is still safely queued and will be retried or redelivered, and the dedup index (keyed by client message ID) on the receiving device absorbs the duplicate.

pseudocodedevice receive path — dedup before render
onIncoming(envelope) {
    if (dedupIndex.has(envelope.id)) {
        ackServer(envelope.id);        // still ack — the server may not have seen our first ack
        return;                    // do NOT render again
    }
    const plaintext = decrypt(envelope);       // per-device Double Ratchet, chapters 3-4
    dedupIndex.add(envelope.id);
    render(plaintext);
    ackServer(envelope.id);            // tick 2: delivered
}
WHY THE ENGINEERS CHOSE THIS

1. Ack idempotency, not send idempotency. Rather than try to prevent duplicate sends (impossible under the Two Generals Problem), the design makes receiving a duplicate cheap and harmless. 2. The device owns dedup, not the server. The server would need to remember every delivered ID forever to dedup centrally, re-introducing the storage problem §5 eliminated; the device already has to remember its own render history for the UI, so dedup piggybacks on state that has to exist anyway. 3. Push is a hint, never a payload. Keeping APNs/FCM out of the trust and content path means a third-party outage degrades wake-up latency, never message confidentiality or durability — the queue and the encrypted connection are still the source of truth.
