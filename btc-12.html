SegWit: Restructuring
the Transaction

Chapter 5 diagnosed transaction malleability and patched its symptoms with BIP143's rewritten sighash algorithm. This chapter fixes the disease: move the signatures outside the data the transaction ID commits to. One sentence, and an entire cascade of consequences — a stable txid, a new second identifier, a new capacity metric, a backward-compatibility trick borrowed from P2SH, and a two-year governance fight that is one of the best-documented consensus-change case studies in distributed systems.

ARC 01 · THE PROBLEM

A transaction's identity depends on data it doesn't need to depend on

Chapter 5 established the mechanism precisely: a transaction's txid is a hash of its entire serialized byte layout — version, inputs, scriptSigs, outputs, locktime. The scriptSigs contain the unlocking data: signatures and public keys. And signatures, by the nature of ECDSA, are not unique per message — a single valid (message, pubkey) pair has a whole equivalence class of valid signature encodings (an alternate but still-valid DER length byte, a flipped high/low S value, padding bytes a lenient parser accepts). Change any byte inside the scriptSig without invalidating it, and you change the txid, because the txid hashes the scriptSig too.

This is transaction malleability, and by itself it sounds like a curiosity. It becomes a systemic problem the moment you build anything on top of an unconfirmed transaction's txid — which is exactly what every proposal for off-chain scaling needs to do. A payment channel (chapter 14 builds one) works by pre-signing a chain of transactions that reference each other's txids before any of them are broadcast. If a third party — or even an honest relay node with a slightly different script-encoding tolerance — can alter a transaction's txid before it confirms, every transaction downstream that referenced the old txid now points at an outpoint that no longer exists on the eventual chain. The entire pre-signed chain is invalidated by an attack that spends no money and steals nothing directly — it just breaks references.

  • The malleator gains nothing directly. They cannot steal funds or change amounts — script validation still requires a genuinely valid signature. This is a reference-integrity attack, not a theft.
  • The victim is anything holding a pre-broadcast txid. Wallets tracking "my payment," exchanges crediting deposits by txid, and — critically — any protocol chaining unconfirmed transactions together.
  • BIP143 (chapter 5) fixed the sighash algorithm's O(n²) hashing cost, not malleability itself. A transaction can have a perfectly efficient, linear-time signature hash and still be malleable — the two problems are adjacent but separate. Malleability needed a structural fix.

The question this chapter answers: what is the smallest structural change that makes txid stability an invariant, provable from the format itself, rather than a property you hope holds because you patched every malleability vector you found? And can that change ship without asking every node on the network to upgrade in lockstep — the hard-fork alternative that chapter 10 showed splits chains?

THE ONE-SENTENCE IDEA, STATED NOW

Move the data that authorizes a transaction (signatures, redeem scripts, witness stack items) outside the data whose hash becomes the txid. Call the moved data the witness. Everything else in this chapter — the wtxid, the coinbase commitment, weight, bech32 addresses, the two-year activation fight — is a direct, derivable consequence of that one relocation.

ARC 02 · HISTORICAL CONTEXT

2011–2017: from an annoying bug report to a two-year governance fight

SegWit is unusual among Bitcoin upgrades in how long the gap was between "we know the fix" (the core idea was understood by late 2015) and "the fix is live" (August 2017). The delay was almost entirely political, not technical — a useful case study in how a permissionless network with no central authority actually changes its rules. Click through the timeline.

A DISPUTED DATA POINT, HANDLED HONESTLY

Mt. Gox's February 2014 collapse publicly blamed transaction malleability for its losses, and the bug is real and was genuinely exploitable against Mt. Gox's specific (insecure) practice of trusting txids from its own non-final broadcast attempts to track withdrawals. But independent analysis (Decker & Wattenhofer, 2014, "Bitcoin Transaction Malleability and MtGox") found malleated transactions accounted for only a small fraction of Mt. Gox's ~850,000 BTC shortfall — the majority is now understood to be internal mismanagement or theft over years, not a single protocol bug. Malleability was a real, worth-fixing problem; it was not, by itself, the reason Mt. Gox failed. Both things are true at once, and conflating them was common at the time.

ARC 03 · NAIVE SOLUTION

Attempt #1: whitelist the malleability vectors (BIP62)

Before anyone proposed restructuring the transaction format, the obvious first move was tried: catalogue every known way to mutate a scriptSig without invalidating it, and reject transactions that don't use the single canonical encoding. This shipped piecemeal as policy rules and the never-fully-activated BIP62 ("Dealing with malleability"). Strict DER enforcement (BIP66, which did activate as a consensus rule in 2015) is the surviving fragment of this approach.

pseudocodebip62_style_checks.py — the whack-a-mole strawman
def is_canonical(tx):
    for txin in tx.inputs:
        sig, pubkey = parse_scriptsig(txin.scriptSig)
        if not is_strict_der(sig):            # BIP66: reject non-canonical DER length/padding
            return False
        if sig.s_value > CURVE_ORDER // 2:      # low-S rule: only ONE of two valid S values allowed
            return False
        if not is_compressed_or_expected_form(pubkey):
            return False
        if has_extra_push_data(txin.scriptSig):    # no-op pushes, unnecessary OP_DROP, etc.
            return False
    return True   # if this ever misses one vector, malleability is back

This is a legitimate engineering instinct: constrain the input space until only one encoding survives, and a hash of a canonical encoding is stable. It even partially worked — low-S enforcement and strict DER did ship and did close two real vectors. It is the same defensive posture as OP_RETURN standardness rules or dust limits: don't change the format, just narrow what's accepted through it.

ARC 04 · WHY IT FAILS

Whitelisting is chasing a combinatorial space you cannot enumerate

The canonicalization approach fails for a structural reason, not a diligence reason: the txid formula itself hashes signature bytes, and DER encoding has multiple genuinely legal degrees of freedom that a strict-mode parser can close one at a time but never prove closed as a set.

  • DER's own spec permits variation. Length fields, leading-zero padding on the R and S integers when their high bit is set, and (pre-BIP66) trailing garbage bytes some clients tolerated — each is a knob an attacker can turn while a signature remains cryptographically valid for the same message and key.
  • Two S values are mathematically valid for every ECDSA signature — s and curve_order − s both satisfy the verification equation. Low-S enforcement picks one by convention; until it activated (as a soft fork, 2015) every existing signature had a free malleability bit, for free, no parser bug required.
  • Script gives you push-data flexibility deliberately. The same 33 bytes of a compressed pubkey can be pushed via several equivalent opcodes; nonstandard-but-valid scripts can insert no-op data your canonicalizer didn't anticipate. Non-standardness policy filters relay, but miners are not obligated to follow policy — a miner or the transaction's own author can always construct a nonstandard-but-consensus-valid malleated version and get it mined directly.
  • You are enumerating an adversarial search space, not a fixed list. Every canonicalization rule that ships closes the vectors known at that time. The failure mode is symmetric with a firewall of regex blocklists: each patch narrows the space, none of them prove it's empty, and the cost of being wrong is not "slightly annoying" — chained pre-signed transactions (payment channels) need a hash that is provably stable, not empirically stable-so-far.
THE STRUCTURAL DIAGNOSIS

Every one of these vectors shares a root cause: the txid function hashes bytes whose exact encoding does not affect what the transaction economically does — which inputs it spends, which outputs it creates, how much value moves. A signature's specific DER byte pattern carries zero economic information; it only proves authorization. Whitelisting tries to make the encoding of non-economic data deterministic. The alternative — explored next — is to stop hashing that data into the identifier at all.

ARC 05 · BETTER SOLUTION

Segregate the witness: derive the whole design from one move

Pieter Wuille, Eric Lombrozo, and Johnson Lau's insight, formalized as BIP141: stop trying to constrain the encoding of authorization data, and instead remove it from the hash entirely. Split every transaction into two parts — the base transaction (what moves, from where, to where) and the witness (proof you're allowed to move it) — and hash only the base part into the txid. Step through the derivation; each step is forced by the one before it.

WHY THIS IS A COMPLETE FIX, NOT A NARROWER WHITELIST

Compare the guarantee. BIP62-style canonicalization says: "txid is stable provided no known malleability vector was missed." Witness segregation says: "txid is stable because the hash function never receives the bytes that vary." The second is a proof, not an empirical claim — it holds regardless of how creative a future malleation vector is, because there is no longer any path from "change the witness" to "change the txid." This is the difference between patching a parser and removing an input from a function.

ARC 06 · WHY THAT STILL HURTS

The witness now has no commitment of its own — and it needs one

Removing the witness from the txid solves malleability, but it creates a new gap: nothing on-chain commits to the witness data at all. The block header's Merkle root is built from txids — and txids, by construction, no longer see the witness. A block could ship with any witness bytes whatsoever for a given set of txids, and as far as the header's Merkle root is concerned, nothing changed.

  • Consequence 1 — witness malleability moves up a layer. A relay node, a miner, or an attacker could swap a transaction's witness for a different valid one (e.g. the still-permitted high-S signature) after the fact. The txid is stable, but two blocks with byte-identical headers and Merkle roots could now carry different total witness data — a new ambiguity that didn't exist before, at the block level instead of the transaction level.
  • Consequence 2 — SPV and compact-block relay need a way to know which witnesses "belong" to a block. Without a commitment, there is no cryptographic binding between a specific block's advertised transactions and the specific witness bytes that were supposed to accompany them.
  • Consequence 3 — this must not require a new block header field. The 80-byte header format (chapter 7) is read and validated by every piece of software on the network, including hardware wallets, mining pool firmware, and blockchain explorers that don't participate in full validation. Adding a field changes the header's serialization for literally everyone — that is a hard fork by definition (chapter 10), and a hard fork is exactly the contentious, network-split-risking path the project was trying to avoid in 2015–2016 (see §11).
THE CONSTRAINT THAT SHAPES EVERYTHING IN §7

Whatever commits to the witness data must live somewhere an unupgraded node already knows how to parse and ignore — not a new header field, not a new message type old nodes reject outright. The only place that satisfies "structurally new, but syntactically old" is inside a transaction's own body, in a script an old node already knows how to skip past without understanding: an OP_RETURN output, and specifically, one inside the coinbase transaction, since the coinbase is the one transaction present in literally every block.

ARC 07 · FINAL ARCHITECTURE

The complete shape: two hashes, one commitment, one soft-fork trick

Assemble the pieces. A SegWit block carries: (1) transactions with a base part (hashed into txid) and a witness part (hashed, together with the base part, into a second identifier — the wtxid); (2) a witness Merkle root, built from wtxids, committed via a special output in the coinbase transaction; (3) new output script forms — OP_0 <hash> — that old nodes read as trivially spendable and new nodes read as "spend requires a witness satisfying this hash." The soft-fork trick: one script, two readingsSTEP-BY-STEP
"ANYONE-CAN-SPEND" FEARS: OVERSTATED, BUT NOT BASELESS

Critics correctly observed that, to a node running pre-BIP141 software, a P2WPKH output really is consensus-legal to spend with an empty scriptSig and no valid signature at all — it is, by that software's rules, unconditionally spendable. The fear "old miners could just steal SegWit outputs" is not paranoia; it is a literally true statement about unupgraded validation logic. What makes it not a practical threat is that Bitcoin's security model was never "whatever the majority of hashpower currently runs" — it is "whatever rule the economically relevant nodes enforce." An upgraded exchange, merchant, or fellow miner's full node rejects a block that spends a witness program without a valid witness, full stop, regardless of that block's proof-of-work. The attacking miner's blocks would be orphaned by everyone who matters economically. Section 11 shows this was not a hypothetical guarantee — it was the explicit mechanism BIP148 threatened to invoke.

ARC 08 · INTERNAL IMPLEMENTATION

Byte layouts, the weight formula, and where the 1.7–2.3 MB comes from

Now the mechanism at the byte level: exactly how a SegWit transaction serializes on the wire, and the formula that converts "how many witness bytes did we include" into "how much this counts against the block limit."

(a) Two serializations of the same transaction

BIP144 defines a second wire format, distinguished by two bytes inserted right after the version field. Step through building one, field by field.

Serializing a SegWit transactionSTEP-BY-STEP
THE RULE THAT MAKES THIS BACKWARD-COMPATIBLE

A pre-BIP144 node has never heard of the marker byte. When it deserializes a SegWit transaction, byte 5 (0x00) looks like "zero inputs" — a syntactically bizarre but not immediately-rejected transaction shape in some contexts, which is precisely why marker+flag were chosen to be values a legacy parser would treat as unusual/invalid input count rather than crash on. In practice, pre-BIP144 nodes simply never see raw SegWit-serialized transactions on the wire at all — BIP144 also defines new P2P messages so peers negotiate whether to send the witness-inclusive form, meaning an old peer is only ever handed the witness-stripped (legacy-compatible) serialization, which parses perfectly normally. Old nodes stay functional; they just never see, store, or relay witness data.

(b) Weight: witness bytes are ¼ the cost of base bytes

Bitcoin Core's actual definition, from consensus/validation.h and consensus/tx_verify.cpp:

C++consensus/tx_verify.cpp — GetTransactionWeight()
static const int WITNESS_SCALE_FACTOR = 4;

int64_t GetTransactionWeight(const CTransaction& tx)
{
    // base size: serialize WITHOUT witness data (the pre-SegWit-compatible form)
    int64_t base_size = GetSerializeSize(tx, PROTOCOL_VERSION | SERIALIZE_TRANSACTION_NO_WITNESS);
    // total size: serialize WITH marker, flag, and every witness stack
    int64_t total_size = GetSerializeSize(tx, PROTOCOL_VERSION);

    return base_size * (WITNESS_SCALE_FACTOR - 1) + total_size;
    // == base_size * 3 + total_size
}

Since total_size = base_size + witness_size, the formula is equivalently weight = base_size × 4 + witness_size — every base byte costs 4 weight units; every witness byte costs 1. The block limit is MAX_BLOCK_WEIGHT = 4,000,000, and vsize = ⌈weight / 4⌉ is the number fee-rate math (chapter 11, sat/vB) actually uses, because it reduces to "1" for a pure pre-SegWit byte and to "0.25" for a pure witness byte.

Notice the corollary before it's stated for you: since total_size ≥ base_size, weight = base_size × 3 + total_size ≥ base_size × 4, so base_size ≤ weight / 4 ≤ 1,000,000 — always, for any block, regardless of how much witness data it carries. The classic "1 MB block size" didn't disappear; it became a hard ceiling specifically on the non-witness portion, falling directly out of the weight arithmetic rather than being written down as its own rule. THE INCENTIVE DESIGN IS DELIBERATE, NOT INCIDENTAL

Making witness bytes 4× cheaper than base bytes isn't just an accounting convenience for the malleability fix — it's a second, quieter policy goal. Spending an existing UTXO requires a witness (the unlocking proof); creating a new UTXO (an output) does not — outputs live entirely in the base part of the transaction. The discount therefore makes spending relatively cheaper than creating, nudging the fee market (chapter 6 showed why UTXO set growth is a systemic cost every node pays forever) toward consolidating old outputs rather than endlessly minting new dust. It's a Pigouvian-style discount: cheapen the behavior (spending, i.e. UTXO cleanup) you want more of.

CRITICS' FRAMING: "A BLOCK SIZE INCREASE DISGUISED AS A BUG FIX"

Part of SegWit's controversy (§11) was precisely this side effect: fixing malleability required a new accounting metric, and that metric happens to let real blocks grow to roughly 1.7–2.3 MB depending on the transaction mix's witness share — a de facto capacity increase without the base-size hard fork that competing proposals (Bitcoin Classic, Bitcoin Unlimited) were arguing for directly. Opponents called this a backdoor block-size increase smuggled inside a technical fix; proponents countered that the increase was an honest side effect of a needed structural change, sized moderately by design (unlike the 8 MB, 32 MB, or unlimited proposals circulating at the time), and delivered without a contentious hard fork. Both framings describe the same arithmetic; they disagree about intent and about whether the trade was worth making.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What changed, quantified

  • Validation complexity: unchanged asymptotically — script execution is still linear in script size per input; SegWit doesn't add new cryptographic operations, it relocates where bytes are counted.
  • Signature hashing cost: this is where a real complexity class improved, and it happened in chapter 5, not here — BIP143's sighash algorithm made hashing O(n) in transaction size instead of the legacy algorithm's O(n²) for transactions with many inputs, closing a real DoS vector (a >1 GB CPU-hashing transaction was constructible pre-BIP143). SegWit's witness programs are what made using BIP143's algorithm mandatory rather than optional.
  • Bandwidth for non-relaying software: SPV wallets and block explorers that only need txids and amounts (not witness data) now transfer meaningfully less — the witness, often 40–70% of a P2WPKH transaction's bytes, is only needed by full validators.
  • Attack cost — the anyone-can-spend window: at no point after mainnet activation did a majority of economically relevant nodes fail to enforce witness validity, so the theoretical "old-rule" spend of a witness output never had a viable market to cash out into — any chain built on it would be rejected by exchanges and merchants, making the mined blocks' rewards (and the theft) worthless to everyone but a chain nobody accepts.

WHERE THE FORMULA COMES FROM

Let f = witness bytes ÷ total bytes for a block. Then base = total × (1−f), and substituting into weight = base×3 + total gives weight = total×(3(1−f)+1) = total×(4−3f), so total = weight ÷ (4−3f). At f=0 (a pre-SegWit-style block, no witness data): total = 4,000,000/4 = 1,000,000 bytes exactly — the historical 1 MB limit, reproduced as a special case. At f=0.65, a realistic contemporary mix dominated by P2WPKH spends: total ≈ 1.95 MB. At f=0.75: total ≈ 2.29 MB. This is exactly the 1.7–2.3 MB range observed on real mainnet blocks — not a coincidence, the direct algebraic consequence of §8's weight formula.

ARC 11 · REAL-WORLD INCIDENTS

The activation fight, as a governance case study

SegWit's technical design was largely settled by December 2015. It did not activate on mainnet until August 24, 2017 — twenty months later. What happened in between is one of the clearest illustrations available of how Bitcoin actually changes its own rules when miners, businesses, and users disagree about the mechanism of a change everyone agrees is technically sound.

Incident 1: Miner signaling stalls, well under the 95% BIP9 threshold

SegWit deployed via BIP9 versionbits in October 2016, requiring 95% of blocks in a rolling 2016-block window to signal support. Signaling stalled in the 30–40% range for months. The root cause was not technical disagreement about SegWit's design — it was that several large mining pools were simultaneously being courted to support a competing, larger-block-size roadmap, and had no obligation to signal for a change they hadn't agreed to prioritize. A 95% threshold, chosen precisely to require overwhelming consensus before a soft fork activates, was doing exactly what it was designed to do: block activation when consensus wasn't actually overwhelming.

Incident 2: the New York Agreement, SegWit2x, and the UASF response

In May 2017, roughly 58 companies and a majority of mining pools signed the New York Agreement (NYA): activate SegWit now, and separately schedule a 2 MB base-size hard fork ("SegWit2x") for November. Parts of the developer and user community objected strongly — a hard fork carries chain-split risk (chapter 10) and NYA was negotiated among businesses and miners without the same open-BIP process other changes went through.

The response was BIP148, the "User-Activated Soft Fork" (UASF): a piece of node software that would, starting August 1, 2017, simply reject any block that didn't signal SegWit support — regardless of how much hashpower mined it. This inverts the normal activation logic: instead of asking miners for permission, a UASF is a credible threat that a subset of the economic network will unilaterally enforce a rule and orphan anyone who doesn't comply, betting that enough of the economy (exchanges, merchants, other nodes) will follow. Crucially — and this is the game-theoretic core of the incident — BIP148 never needed to activate in earnest to work. Its mere credibility, and the real possibility of a chain split that would leave non-signaling miners' blocks economically worthless to a meaningful fraction of the network, was the entire mechanism.

Incident 3: BIP91, lock-in, and the coincident Bitcoin Cash split

Faced with the UASF deadline, miners rapidly adopted BIP91 — a lower-threshold (80%, over a shorter 336-block window), miner-driven fast-track that effectively guaranteed SegWit's BIP9 lock-in ahead of August 1, defusing the standoff without anyone's node needing to actually enforce BIP148 against a non-compliant majority. BIP91 locked in within days. SegWit itself locked in on the original chain shortly after and activated at block height 481,824 on August 24, 2017. Separately — and this is a common point of confusion worth stating precisely — a different, unrelated contentious faction that rejected the SegWit approach entirely hard-forked away on August 1, 2017 to form Bitcoin Cash, favoring larger base blocks with no witness segregation. The two events shared a calendar window and general subject matter but were separate chains reaching separate conclusions, not one event.

The postscript: SegWit2x's scheduled November 2017 hard fork was cancelled days before its planned activation. Its organizers cited a lack of consensus (much of the technical community and a large share of node operators had never signed on) and, critically, the absence of two-way replay protection — the same category of omission that made Ethereum Classic's 2016 split messy (a transaction valid on one chain being accidentally valid and re-broadcastable on the other, chapter 10's replay-protection discussion). Rather than force a split with an unresolved technical hazard and uncertain support, the SegWit2x signatories stood down.

THE LESSON, STATED NEUTRALLY

Miner signaling (hashpower) proposes; economically relevant full nodes (exchanges, businesses, individual validators) dispose. A soft fork with overwhelming validating-node support but stalled miner signaling can still be forced through by a credible UASF, because miners are economically rational actors who need their blocks to be accepted by an economy that can simply choose not to. This is not a claim that UASFs are without risk — a failed or narrowly-supported UASF can itself cause a split — only that in this specific, well-documented instance, the threat's credibility was sufficient and it was never tested to destruction.

First, the structural change: witness data does not live inside CTxIn the way scriptSig does — it lives in a parallel array, deliberately excluded from the legacy-compatible serialization path:

C++primitives/transaction.h — the witness lives beside the input, not inside it
class CScriptWitness
{
public:
    // Each element is one item pushed onto the witness stack for this input.
    std::vector<std::vector<unsigned char>> stack;

    bool IsNull() const { return stack.empty(); }
};

class CTxIn
{
public:
    COutPoint prevout;
    CScript scriptSig;       // legacy field — EMPTY for a pure-segwit input
    uint32_t nSequence;
    CScriptWitness scriptWitness;  // NOT serialized by the legacy/base path at all
};

Second, how an old-looking output gets new rules enforced — Solver() classifies the exact byte pattern a witness program produces, and the interpreter branches on it:

C++script/standard.cpp — recognizing a witness program (simplified)
bool IsWitnessProgram(const CScript& script, int& version, std::vector<unsigned char>& program)
{
    // A witness program is EXACTLY: one push-version opcode (OP_0 or OP_1..OP_16)
    // followed by a single data push of 2 to 40 bytes. Nothing else.
    if (script.size() < 4 || script.size() > 42) return false;
    if (script[0] != OP_0 && (script[0] < OP_1 || script[0] > OP_16)) return false;
    if ((size_t)(script[1] + 2) == script.size()) {
        version = (script[0] == OP_0) ? 0 : script[0] - (OP_1 - 1);
        program.assign(script.begin() + 2, script.end());
        return true;
    }
    return false;
}
// version 0, 20-byte program  -> P2WPKH   (this IS the "OP_0 <hash>" from §7)
// version 0, 32-byte program  -> P2WSH
// (version 1, 32-byte program -> taproot output, chapter 13 — same trick, next version byte)

Third, the coinbase commitment that closes the gap from §6 — the exact spot BIP141 requires every SegWit block to carry:

C++validation.cpp — GenerateCoinbaseCommitment() (simplified)
CTxOut GenerateCoinbaseCommitment(CBlock& block, const CBlockIndex* pindexPrev)
{
    // 1. Build the witness Merkle tree from every tx's wtxid, EXCEPT the
    //    coinbase itself, whose wtxid is defined to be 32 zero bytes here.
    uint256 witnessroot = BlockWitnessMerkleRoot(block);

    // 2. Append the 32-byte "witness reserved value" (the coinbase's own
    //    single witness stack item; Core uses 32 zero bytes by convention).
    uint256 commitment = SHA256d(witnessroot, witness_reserved_value);

    // 3. Wrap it in an unspendable, instantly-recognizable output:
    //    OP_RETURN  PUSH(36)  0xaa21a9ed  <32-byte commitment>
    CScript script;
    script << OP_RETURN << Concat(COMMITMENT_HEADER /* 0xaa21a9ed */, commitment);
    return CTxOut(0, script);   // value 0 — this output is pure metadata
}
// An old node sees: "some coinbase output, OP_RETURN, provably unspendable." It skips
// it entirely — OP_RETURN outputs have been standardly unspendable since 2014. A new
// node finds the 0xaa21a9ed marker and verifies it against its own computed witness root.
WHY IT WAS BUILT THIS WAY

1. Every new rule is expressed as "old software already knows how to skip this." A witness program looks like anyone-can-spend to old validation; a witness commitment looks like a provably-unspendable output. Neither requires an old node to understand anything new — that's the entire definition of a soft fork. 2. The coinbase is the one guaranteed location. Every block, by consensus rule, has exactly one coinbase transaction; nothing else is present in literally 100% of blocks, which is why it — and not some arbitrary other transaction — carries the commitment. 3. Versioned witness programs future-proof the trick. OP_0 means "version 0, interpret this program as P2WPKH/P2WSH"; reserving OP_1..OP_16 as legal-but-currently-undefined versions meant a future soft fork (taproot's version 1, chapter 13) could ship new semantics using the exact same anyone-can-spend-to-old-nodes mechanism, without re-litigating the soft-fork trick from scratch.
