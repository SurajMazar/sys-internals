POSTGRESQL INTERNALS · CHAPTER 08

The Lock Manager: Heavyweight,
LWLocks & Spinlocks

Every shared structure you met in earlier chapters — the buffer pool, the WAL insert pointer, the ProcArray, a table's row set — is mutated by dozens of backends at once, and each one needs a different kind of mutual exclusion. This chapter derives, from first principles, why PostgreSQL runs three separate locking systems instead of one, exactly how each is implemented in C, and how the heavyweight lock manager detects and breaks deadlocks without ever scanning the data it protects.

ARC 01 · THE PROBLEM

One mutual-exclusion primitive cannot serve nanoseconds and hours

Chapter 1 drew the line between private backend memory and the one shared memory segment every backend attaches to. Everything on the shared side of that line — buffer descriptors, the WAL insert pointer, the ProcArray, the lock table itself — is mutated concurrently by up to max_connections processes with no thread scheduler to serialize them for you. Something has to make each mutation atomic, and that something has wildly different jobs depending on what it's protecting.

Consider the spread. Flipping one flag in a BufferDesc's state word takes a handful of CPU instructions — you want a primitive with near-zero overhead, and you can tolerate it being unfair or dumb because it's held so briefly nobody ever queues long. Protecting the shared buffer-mapping hash table while you insert an entry is longer — a few dozen instructions, maybe a comparison against several hash chain entries — long enough that spinning burns real CPU if someone loses their timeslice mid-hold, so you'd rather the waiter go to sleep. And a lock on a row a user is updating with UPDATE ... WHERE id = 1 might be held for the entire wall-clock duration of an interactive transaction — seconds, minutes, sometimes hours if someone leaves a psql session open mid-edit — where busy-waiting of any kind is unthinkable and you need real scheduling, real fairness, and a way to detect that two such locks have deadlocked each other.

Three requirements fall out of that spread, and they are in tension with each other:

  • Overhead must match hold time. A primitive cheap enough for a 5-instruction critical section (no syscall, no memory allocation, ideally no cache-line traffic beyond the lock word itself) is unusable for something held across a network round-trip — and a primitive safe for hour-long holds (queueing, fairness, deadlock detection) is far too expensive to pay on every buffer pin.
  • Semantic richness must match what's being protected. A flag bit needs nothing but atomicity. A shared hash table needs shared/exclusive modes so concurrent readers don't block each other. A row or a table needs a whole taxonomy of modes — a SELECT and an UPDATE on the same table are compatible; two UPDATEs on the same row are not — plus a notion of which locks are held by a transaction rather than by a single instruction.
  • Failure handling must match risk. Code holding a low-level lock must never be allowed to ereport(), allocate memory, or block indefinitely — those operations can themselves take locks or run arbitrary error-handling code, and a lock held across them is a lock that can be held forever if something goes wrong. Code taking a table or row lock is expected to potentially wait, potentially error out, and potentially participate in a cycle of mutual waiting that has to be found and broken.

PostgreSQL's answer is not one lock manager but three, each a distinct point on the cost/capability curve: spinlocks (src/backend/storage/lmgr/s_lock.c) for the shortest, must-never-block critical sections; LWLocks (lwlock.c) for shared-memory data structures held for microseconds with real sleep but no deadlock detection; and heavyweight locks (lock.c, lmgr.c) for the logical objects — tables, rows, pages, transactions themselves via advisory locks — that a SQL statement actually reasons about, complete with a deadlock detector. Everything else in this chapter derives from why that split exists and what each layer is not allowed to do.

THE RULE THAT EXPLAINS THE WHOLE CHAPTER

Hold time and capability move together, on purpose: spinlocks < LWLocks < heavyweight locks in both overhead and what they can safely protect. Every design decision below — no deadlock detection in LWLocks, the fast path bypassing the shared hash table, the one-second delay before the DFS deadlock check even runs — is that curve being paid for deliberately rather than discovered by accident.

DEEP CONTEXT · WHY SPINLOCKS PREDATE EVERYTHING ELSE

Spinlocks are the oldest layer because they map directly onto a CPU intrinsic — a test-and-set or compare-and-swap instruction — and every architecture PostgreSQL has ever targeted has had some atomic read-modify-write primitive. s_lock.c's job has always been to hide the per-architecture assembly (tas() on x86, load-linked/store-conditional on ARM/PowerPC) behind one portable macro, SpinLockAcquire(). LWLocks and heavyweight locks are both built on top of spinlock-style atomics — an LWLock's state word is manipulated with the same compare-and-swap primitive, just wrapped with a wait queue and a semaphore. You cannot build the higher layers before the lowest one exists.

ARC 03 · NAIVE SOLUTION

Attempt #1: one mutex for all of shared memory

Derive it honestly, the way §1 demands. If shared memory is the thing under contention, the simplest fix is the most obvious one: wrap every access to it — buffer pin, WAL insert, lock-table lookup, ProcArray scan — in a single global mutex.

Cnaive_globallock.c — the strawman
static pthread_mutex_t g_shmem_lock = PTHREAD_MUTEX_INITIALIZER;

void TouchAnythingShared(void (*work)(void *), void *arg)
{
    pthread_mutex_lock(&g_shmem_lock);   /* one lock, no matter what "work" touches */
    work(arg);
    pthread_mutex_unlock(&g_shmem_lock);
}

/* Every one of these funnels through the same mutex: */
/*   PinBuffer(buf)               — bump a refcount             */
/*   XLogInsertRecord(rec)        — append 200 bytes of WAL      */
/*   LockAcquire(&tag, EXCLUSIVE) — take a table lock for a txn  */
/*   GetSnapshotData()            — scan the ProcArray           */

This is not a joke architecture — it is trivially correct. There is exactly one lock, so there can be no lock-ordering deadlock between two different shared structures, and reasoning about correctness is as easy as reasoning gets: at most one backend is ever inside shared memory at a time. ARC 04 · WHY IT FAILS

A shared bottleneck with the wrong shape at both ends

The single global mutex fails in two directions simultaneously, and both are quantifiable:

  • It serializes unrelated work. A backend pinning a buffer for table A and a backend inserting a WAL record for an unrelated transaction on table B have nothing to do with each other, yet the global mutex forces them into a queue of one. On an N-core machine, once any two of the N backends are both trying to touch shared memory, N−1 of them are stalled doing nothing — throughput collapses to what a single core can push through the critical section, regardless of how many cores you bought.
  • It has the wrong hold-time profile for the thing held longest. A row lock legitimately needs to survive for the duration of a client's transaction — the global mutex cannot be held that long without freezing every other backend in the cluster for the same duration. So the naive design either (a) never lets row/table locks use this mutex, which means you need a second mechanism anyway, or (b) lets them use it, which means one idle-in-transaction session with an open row lock stalls the entire server. There is no correct choice inside the single-mutex model — you are forced out of it.
THE NUMBERS

Model it as an M/M/1 queue with one server: if the mutex is held for even 200 ns per acquisition and the cluster performs 2,000,000 shared-memory touches/sec in aggregate across 64 cores (a modest OLTP number — buffer pins alone run into the millions/sec), the critical section alone needs 400 ms of serialized CPU time per second — already over capacity before you've done a single byte of actual work inside it. The 63 idle cores are not a rounding error; they are most of the machine you paid for, sitting in a wait queue for a mutex.

Two failures, two different fixes needed: contention on short operations wants partitioning and cheaper primitives; contention on long-held logical locks wants queueing, fairness, and deadlock detection. §5 looks at the candidates for supplying both.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates, examined against the two failure modes

Candidate A: a single OS mutex (pthread_mutex / futex) per structure

Replace the one global mutex with one OS mutex per shared structure — one for the buffer mapping table, one for the WAL insert pointer, one for the lock table itself. This fixes the "unrelated work serialized" problem: buffer work and WAL work no longer contend with each other. But a pthread_mutex_lock() call is not free even in the uncontended case — it's a function call into libc that, on Linux, touches a futex word and, if contended, makes a futex(2) syscall to actually sleep. For a critical section that flips one flag bit in a few nanoseconds, the mutex's own overhead (tens of nanoseconds even uncontended, hundreds to thousands if it has to fall into the kernel) can be several times the cost of the work it protects. Rejected for the shortest critical sections — not because it's unsafe, but because the primitive costs more than the job.

Candidate B: one reader/writer lock per structure, no further partitioning

Upgrade each per-structure lock to a shared/exclusive (reader/writer) lock — multiple readers of the buffer mapping table can proceed together, only a writer excludes everyone. This helps read-heavy structures, but a single lock guarding, say, "the entire buffer mapping hash table" or "the entire heavyweight lock table" still makes every insert or delete in any bucket contend with every other bucket's insert or delete — 500 backends hammering unrelated tables still funnel through one exclusive-mode acquisition each time any of them needs to add or remove a hash entry. Rejected as insufficiently partitioned for structures accessed by every backend on every query.

Candidate C: three primitives, matched to hold-time and capability ✓

Stop looking for one primitive and instead build exactly as many as the requirement spread in §1 demands, each cheap in proportion to how briefly it's held and rich in proportion to what it needs to express:

SPINLOCKRaw CAS/TAS loop. No queue, no OS involvement while spinning. For critical sections measured in CPU instructions, not microseconds. s_lock.c.
LWLOCKAtomic state word + a real wait queue of sleeping PGPROCs. Shared/exclusive modes. For shared-memory data structures held microseconds to low milliseconds. lwlock.c.
HEAVYWEIGHT LOCKA tracked, named object with 8 conflict-aware modes, per-transaction ownership, queueing, and deadlock detection. For logical objects held up to a whole transaction. lock.c, lmgr.c.

THE CLINCHING ARGUMENT: PARTITIONING MULTIPLIES EACH LAYER

None of the three primitives is used as a single instance either. The buffer mapping table is split across NUM_BUFFER_PARTITIONS (128) LWLocks; the heavyweight lock table is split across NUM_LOCK_PARTITIONS (16) LWLocks; WAL insertion uses a small array of insertion-slot LWLocks so concurrent backends can reserve independent ranges of WAL space. Partitioning is orthogonal to which primitive you use, and PostgreSQL applies it wherever one structure is popular enough that even the cheap primitive starts to contend.

ARC 06 · WHY THAT STILL COSTS

Each layer buys speed or capability by giving something up

None of the three primitives is free, and the price is paid at a different place in the system for each one:

  • Spinlocks can livelock the whole machine if misused. A spinlock is a busy-wait loop — if the holder is descheduled by the OS while holding it (a stalled timeslice, a page fault), every other backend spinning on it burns CPU making zero progress, and on a machine with more waiters than free cores this can starve the holder from ever getting scheduled back in to release it. This is precisely why the rule exists: you may not ereport(), palloc(), or block on I/O while holding a spinlock — any of those can take an arbitrarily long time or re-enter the lock manager, turning a five-instruction hold into an unbounded one. Contended spinlocks also thrash a cache line between cores — every failed compare-and-swap invalidates the line on every other core probing it, producing real memory-bus traffic even though "nothing" is happening logically.
  • LWLocks buy sleep-instead-of-spin, but explicitly opt out of deadlock detection. An LWLock's wait queue lets a blocked backend sleep on a semaphore instead of burning CPU — correct for microsecond-to-millisecond holds — but the LWLock subsystem does no cycle detection at all. Safety instead comes from a strict, code-reviewed lock-ordering discipline: every code path that needs two LWLocks at once must acquire them in the same global order every time. Get that discipline wrong in a rarely-exercised path and you get a cluster-wide hang with no detector to catch it — the cost of skipping deadlock detection is that humans are the detector.
  • Heavyweight locks buy deadlock detection, fairness, and per-transaction bookkeeping — at real overhead. Every heavyweight lock request means a hash lookup (partition-protected), allocation of a PROCLOCK entry, and — if it can't be granted — being linked into a wait queue that a background timer and a graph search algorithm both know how to inspect. That bookkeeping is exactly what a spinlock cannot afford and what most LWLock users don't need; heavyweight locks pay it because table and row locks really can deadlock across unrelated transactions and someone has to notice.
THE PRICE OF DEFERRING DEADLOCK DETECTION

Even within the heavyweight layer, full deadlock detection is too expensive to run on every wait — a depth-first search of the waits-for graph touches every blocked backend in the cluster. So PostgreSQL defers it: a waiter only triggers the search after sitting blocked for deadlock_timeout (default 1 second). That means a genuine deadlock is guaranteed to sit unresolved for up to a full second — an eternity for an OLTP system — a direct, deliberate trade of detection latency for not running an O(waiters) graph search on every single lock wait, which happens millions of times a second on a busy server. §8 shows exactly why 1 second was the chosen default and what changing it costs in both directions.

WHAT DOESN'T EXIST: LOCK ESCALATION

Many engines that start with fine-grained row locks quietly escalate them to a table lock once a transaction holds "too many" — trading precision for lock-table memory. PostgreSQL deliberately has no such mechanism. Row locks are nearly free (they live in the tuple's own header, not in shared-memory lock structures, until contended — see §8), so there is no memory pressure pushing toward escalation, and escalating would silently convert "I'm updating row 4" into "nobody else may touch this table," which breaks the very MVCC promise — readers never block writers, writers of unrelated rows never block each other — that the rest of the engine is built around. The absence is a design decision, not an oversight.

ARC 08 · INTERNAL IMPLEMENTATION

The three layers, in the actual C

Now the mechanism at patch-level detail: (a) spinlocks and the exponential backoff that keeps them from wrecking the machine under contention, (b) the LWLock state word and its fast/slow acquisition paths, (c) the heavyweight lock table, its partitioning, the fast-path optimization for relation locks, and the deadlock detector's depth-first search.

(a) Spinlocks: compare-and-swap with a backoff ladder

A spinlock is, at its core, one atomically-manipulated word — slock_t, typically a single byte or int depending on platform — and a hand-written assembly primitive, TAS() (test-and-set) or a compiler intrinsic doing compare-and-swap, that either wins the lock or doesn't. The naive version would spin forever retrying TAS(); the real implementation in s_lock() escalates: spin a handful of times purely in userspace (cheapest possible retry, good for locks about to be released in nanoseconds), then start inserting increasing delays, and if the lock is still not free after enough attempts, actually yield the CPU via a short sleep — trading a busy-wait for a scheduler-mediated wait once contention looks sustained rather than transient.

Cs_lock.c — the acquisition ladder, simplified
int
s_lock(volatile slock_t *lock, const char *file, int line, const char *func)
{
    SpinDelayStatus delayStatus;
    init_spin_delay(&delayStatus, file, line, func);

    while (TAS_SPIN(lock))          /* still not free? */
    {
        /* First few iterations: pure spin, no delay at all — cheapest
         * possible retry for a lock about to be released in
         * nanoseconds. Beyond that: exponentially increasing usleep(),
         * capped, plus randomized jitter so many spinners don't
         * resonate and all retry in lockstep.                        */
        perform_spin_delay(&delayStatus);
    }
    finish_spin_delay(&delayStatus);   /* feeds spins_per_delay's
                                        * adaptive tuning for next time */
    return delayStatus.delays;
}

Two rules follow directly from what a spinlock cannot do. First, never call anything that can allocate, error, or block while holding one — ereport(ERROR, ...) longjmps out through arbitrary cleanup code, palloc() can trigger a context switch into the memory-context machinery, and any I/O wait could hold the spinlock for the wait's entire duration, which is precisely the unbounded-hold scenario spinlocks are built to never have. Second, keep the critical section provably short — a handful of instructions, no loops over unbounded data. The convention throughout the codebase is that any code between SpinLockAcquire() and SpinLockRelease() is auditable at a glance.

CACHE-LINE BOUNCING, MADE CONCRETE

Every failed TAS() attempt is a cache-coherency event: the spinlock's cache line must be in Modified or Exclusive state for the CAS to succeed, so contending cores repeatedly invalidate each other's copy of that line via the MESI protocol. On a machine with many sockets this is worse than it looks — a remote-socket cache-line fetch costs far more cycles than a local one, so a spinlock hot enough to bounce across NUMA nodes can cost more in interconnect traffic than the work it protects. This is also false sharing's home turf: if two unrelated spinlocks happen to land in the same 64-byte cache line (because a struct packed them tightly), contention on one manifests as latency on the other. PostgreSQL pads performance-critical shared arrays (LWLock arrays, buffer descriptors) to cache-line boundaries specifically to prevent this.

(b) LWLocks: an atomic state word, a wait queue, semaphore sleep

An LWLock packs everything it needs into one pg_atomic_uint32: an exclusive-held flag, a count of concurrent shared holders, and flag bits recording whether anyone is queued and whether a wake-up is pending — plus a proclist (a doubly-linked list built out of offsets into the PGPROC array, not pointers, so it survives being stored in shared memory) of waiting backends. Acquisition tries a lock-free fast path first: atomically compare-and-swap the state word from "free" (or "shared, below the max count") to "held," and if that CAS wins, you're done — no queue, no syscall, no sleep, just the cost of one atomic RMW instruction.

Clwlock.c — LWLockAttemptLock(), simplified
static bool
LWLockAttemptLock(LWLock *lock, LWLockMode mode)
{
    uint32 old_state = pg_atomic_read_u32(&lock->state);

    for (;;)
    {
        uint32 desired_state = old_state;
        bool lock_free;

        if (mode == LW_EXCLUSIVE)
        {
            lock_free = (old_state & LW_LOCK_MASK) == 0;   /* no shared, no excl */
            if (lock_free)
                desired_state += LW_VAL_EXCLUSIVE;
        }
        else   /* LW_SHARED */
        {
            lock_free = (old_state & LW_VAL_EXCLUSIVE) == 0;
            if (lock_free)
                desired_state += LW_VAL_SHARED;      /* one more reader */
        }

        /* Single atomic CAS: either we win outright (fast path, no
         * queue, no sleep) or we retry — the loop is only for the
         * benign case where another CAS raced us, not for waiting.   */
        if (pg_atomic_compare_exchange_u32(&lock->state, &old_state, desired_state))
            return lock_free;    /* true = got it; false = must queue */
    }
}

When the fast path fails — an exclusive request meets any holder, or a shared request meets an exclusive holder — the backend adds itself to the wait queue (protected by a short internal spinlock on the queue itself, the one place LWLock still leans on tier 0), sets a flag so the eventual releaser knows someone is waiting, and calls PGSemaphoreLock() on its own per-backend semaphore. The releaser, seeing the "has waiters" flag, walks the queue and posts exactly the semaphores of the backends it's releasing to — shared releases wake every queued shared waiter up to the first exclusive request; an exclusive release wakes only the next single waiter (or a contiguous run of shared waiters at the queue head). One deliberate fairness rule prevents starvation here: a new shared-lock request that arrives while an exclusive request is already queued does not jump the queue — it queues behind the waiting exclusive locker instead of joining the currently-held shared holders, or every exclusive request could be starved forever by a steady stream of readers.

LWLocks are grouped into tranches — named collections sharing one purpose, so pg_stat_activity and wait-event reporting can say "waiting on BufferMapping" rather than an anonymous address. The tranches you'll meet constantly: the BufferMapping partitions (128 LWLocks guarding the buffer lookup hash table, chapter 9), WALInsertLock (a small array so concurrent backends can each reserve a private range of WAL space without serializing on one pointer), and ProcArrayLock (guarding the list of running transactions that snapshots are built from).

(c) Heavyweight locks: partitioned hash table, fast path, and the deadlock DFS

A heavyweight lock is a shared LOCK struct (one per distinct lockable object actually contended — keyed by a LOCKTAG identifying a relation, page, tuple, transaction, or advisory-lock number) plus one PROCLOCK struct per (lock, holding-backend) pair recording which mode that backend holds. Both live in a shared hash table split across NUM_LOCK_PARTITIONS (16) LWLocks, so a backend touching table A and a backend touching unrelated table B hash into different partitions and never contend on the partition lock itself, only (rarely) on the specific object both happen to want.

Locking has 8 modes forming a fixed conflict matrix — from AccessShareLock (a plain SELECT takes this) up to AccessExclusiveLock (DROP TABLE, most forms of ALTER TABLE). Most relation locks in a real workload are weak and non-conflicting — a SELECT's AccessShareLock conflicts with almost nothing. Paying a full partitioned-hash-table insert and a PROCLOCK allocation for every single one of those would waste exactly the effort §6 warned about. The fast path exists to skip it: each backend's PGPROC carries FP_LOCK_SLOTS_PER_BACKEND (16) private slots, and a weak relation-lock request that finds a free slot is recorded there directly — no shared hash table touched at all, just a compare-and-swap into the backend's own memory. The catch is correctness: if another backend later wants a strong lock mode on that same relation (one that could actually conflict with a fast-path entry — e.g., AccessExclusiveLock for a schema change), it cannot safely ignore locks it can't see. So requesting a strong lock forces a fast-path transfer: every backend's fast-path slots for that relation are walked and copied into the real shared hash table before the strong request proceeds, at which point ordinary conflict checking applies.

Fast-path lock life cycleSTEP-BY-STEP

When a request cannot be granted — the object is already held in a conflicting mode — the requester is queued on the LOCK's wait list and calls ProcSleep(), blocking on its own semaphore exactly like an LWLock waiter, except this queue is inspected by more than just the releaser: after deadlock_timeout (1 second by default) of unbroken waiting, the waiter itself invokes the deadlock detector.

Cdeadlock.c — DeadLockCheck(), simplified
bool
DeadLockCheck(PGPROC *checkProc)
{
    /* Build the waits-for graph on the fly: for every proc blocked
     * on some lock, add an edge to every proc that currently holds
     * a conflicting mode on that same lock. "Soft" edges additionally
     * capture waiters that COULD be reordered without violating
     * anyone's request — useful because breaking a soft edge by
     * queue-reordering can resolve a cycle without aborting anyone. */
    numCycles = FindLockCycle(checkProc, possibleConstraints, &nConstraints);

    if (numCycles == 0)
        return true;              /* no cycle — just ordinary queueing, keep waiting */

    /* Before giving up: try every combination of soft-edge
     * reorderings to see if SOME valid wait order exists that
     * breaks every cycle. This is why two txns racing on lock
     * ORDER, not just lock IDENTITY, can sometimes self-resolve.    */
    if (DeadLockCheckRecurse(checkProc))
        return true;              /* a valid reordering exists — no real deadlock */

    return false;                  /* hard cycle: no reordering escapes it — genuine deadlock */
}

The victim is always the backend that ran the check — the one that happened to be the one still waiting when deadlock_timeout expired. That is not arbitrary: DeadLockCheck() runs synchronously inside the waiting backend's own ProcSleep(), so the only safe, immediate action it can take is to make itself return an error from its own wait — reaching across the cycle to abort a different backend would require asynchronously interrupting a process that isn't expecting it, a much less contained operation. Aborting yourself is always correct: your own transaction can always be rolled back safely by definition, because it's your own stack unwinding through your own cleanup path.

Row-level locks (SELECT ... FOR UPDATE/SHARE/NO KEY UPDATE/KEY SHARE) mostly avoid the shared lock manager altogether: the locking transaction's identifier is written straight into the tuple's own header — packed into t_infomask/t_infomask2 bits (HEAP_XMAX_EXCL_LOCK, HEAP_XMAX_KEYSHR_LOCK, HEAP_XMAX_LOCK_ONLY in combination) alongside the tuple's xmax. A single locker just becomes the tuple's xmax; when more than one transaction needs to hold a lock on the same row concurrently (two FOR SHARE lockers, or a FOR SHARE alongside a FOR UPDATE-holding foreign key check), xmax becomes a MultiXactId — an entry in the multixact SLRU that expands to the full set of transaction IDs and lock strengths currently holding that row. Only when a second transaction actually has to wait on a row-locked tuple does a real heavyweight LOCKTAG_TUPLE lock get created — purely as the queueing mechanism for that wait, not as the row lock's primary representation.

ARC 09 · TRADEOFFS

The same problem, five ways: comparative anatomy

Every serious storage engine builds some form of tiered mutual exclusion. The differences are revealing about what each engine's architecture makes cheap or expensive:

The engines that skip the richer layer (SQLite, Cassandra) do so because their concurrency model sidesteps the need for it entirely, not because they found a cheaper way to build it.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

Complexity and cost, layer by layer:

  • Spinlock acquire, uncontended: O(1) — one CAS instruction, a handful of nanoseconds. Contended: cost scales with the number of other cores spinning on the same cache line, dominated by cache-coherency traffic rather than instruction count — effectively O(contending cores) in bus transactions.
  • LWLock acquire, fast path: O(1) — one atomic CAS on the state word, no queue touched. Slow path: O(1) to enqueue plus a semaphore syscall (context switch cost, roughly 1–5 µs) — still bounded, just much more expensive than the fast path, which is exactly why the fast path exists and why LWLocks are designed so the common case avoids it entirely.
  • Heavyweight lock acquire: O(1) average via hash partition lookup (amortized, assuming a well-spread hash function across the 16 partitions), plus fast-path O(1) slot scan (bounded at FP_LOCK_SLOTS_PER_BACKEND = 16 entries) for the common weak-relation-lock case.
  • Deadlock detection: O(V+E) depth-first search over the waits-for graph, where V is the number of currently-blocked backends and E the conflicting-lock edges between them — but this only runs once per waiter per deadlock_timeout interval, not per lock acquisition, which is what keeps its asymptotic cost from mattering under normal load.

Cache and NUMA effects compound at every layer. A hot spinlock or LWLock state word bounces between core caches exactly as described in §8; the heavyweight lock hash table's 16-way partitioning caps how many backends can contend on the partition lock itself, but many backends repeatedly locking the same popular relation (a hot lookup table) still serialize on that one LOCK struct's PROCLOCK list — partitioning spreads unrelated contention, it does not eliminate contention on a genuinely hot single object. MODEL, NOT MEASUREMENT

The curve is an analytic sketch shaped to match the qualitative behavior documented by the PostgreSQL project's own fast-path locking work (2012): without the fast path, every relation touch — even a plain SELECT — contends on the shared, partitioned lock table, and that contention grows with backend count; with it, the overwhelming majority of relation locks never touch shared memory at all, and throughput stays flat until a strong (DDL-class) locker forces a transfer. The point is the shape, not exact numbers — measure your own workload with pg_stat_activity's wait events (chapter 20's methodology).

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: the idle-in-transaction row lock that froze a queue table

An application opens a transaction, runs SELECT ... FOR UPDATE to claim a job row, then makes an outbound HTTP call before committing. The HTTP call hangs. The transaction sits idle-in-transaction, holding its row lock (recorded via the tuple's xmax, per §8) indefinitely. Every other worker trying to claim the same row queues behind it — and because heavyweight lock wait queues are strictly ordered, workers that only wanted different rows but happened to request a table-level lock behind the stuck request queue too. Within minutes the job queue's throughput drops to zero and pages start firing. Fix: idle_in_transaction_session_timeout, set aggressively on connections that make external calls mid-transaction; the deeper lesson is that a lock's cost is measured in wall-clock hold time, and application code — not the database — controls that clock for row locks acquired via FOR UPDATE.

Incident 2: one ALTER TABLE, queued behind a long report, blocks every SELECT

A routine ALTER TABLE ... ADD COLUMN requests AccessExclusiveLock on a busy table. A long-running analytical SELECT already holds AccessShareLock on it, so the ALTER queues, waiting for the report to finish. So far, expected. What surprises teams the first time: every subsequent SELECT against that table — even though AccessShareLock does not conflict with another AccessShareLock — also queues behind the pending ALTER, because heavyweight lock grants are strictly FIFO within a lock's wait list to prevent writer starvation, not granted opportunistically around a pending stronger request. One slow report plus one routine schema change turns into a full table outage. Fix: lock_timeout around DDL so a stuck ALTER aborts instead of blocking the queue forever, and scheduling schema changes away from long-running report windows.

Incident 3: deadlock_timeout storms under heavy row contention

A batch job updates many rows across several tables in inconsistent per-row order across worker threads, producing genuine deadlocks at a low but steady rate — normal, and exactly what the detector exists for. The surprising part shows up in monitoring: total CPU attributable to DeadLockCheck() spikes far higher than the deadlock rate alone would suggest, because every waiter that individually crosses deadlock_timeout runs its own DFS over the current waits-for graph to check whether it personally sits on a cycle — including waiters that are just experiencing ordinary queueing delay under heavy contention, not an actual deadlock. Under enough concurrent blocking, many of these "false-alarm" checks fire in the same window. Fix: reduce genuinely conflicting cross-table update ordering at the application layer (the root cause), and treat deadlock_timeout as a real tuning knob — lowering it detects deadlocks faster but runs the DFS more often under contention; raising it does the opposite.

First, the conflict table itself — the ground truth every heavyweight lock request is checked against:

Clock.c — the conflict table (conceptually)
static const LOCKMASK LockConflicts[] = {
    /*                AS RS RE SUE  S SRE  E AE */
    /* AccessShare  */ 0b10000000,
    /* RowShare     */ 0b11000000,
    /* RowExclusive */ 0b11101100,
    /* ShareUpdEx   */ 0b11111100,
    /* Share        */ 0b10111100,
    /* ShareRowEx   */ 0b11111100,
    /* Exclusive    */ 0b11111100,
    /* AccessExcl   */ 0b11111111,
};
/* One bit per row means: "if I already hold ROW mode, does a
 * request for COLUMN mode conflict?" LockAcquire() consults this
 * once per PROCLOCK on the object — no locking theory, just a
 * lookup table computed once at design time and never touched
 * again. Simplicity here is deliberate: correctness of concurrency
 * control should never depend on a fast path being clever.        */

Next, the fast-path check that most relation locks actually take — no shared hash table, no partition lock:

Clock.c — FastPathGrantRelationLock(), simplified
static bool
FastPathGrantRelationLock(Oid relid, LOCKMODE lockmode)
{
    int i;

    /* Only WEAK modes are eligible — anything that could conflict
     * with another backend's own fast-path entry must go through
     * the shared table, where conflict checking actually happens.  */
    if (!FastPathLockModeEligible(lockmode))
        return false;

    LWLockAcquire(&MyProc->fpInfoLock, LW_EXCLUSIVE);   /* private, uncontended */
    for (i = 0; i < FP_LOCK_SLOTS_PER_BACKEND; i++)
    {
        if (MyProc->fpRelId[i] == InvalidOid)
        {
            MyProc->fpRelId[i] = relid;             /* claim a private slot     */
            MyProc->fpLockBits |= (lockmode << (i * FASTPATH_BITS_PER_SLOT));
            LWLockRelease(&MyProc->fpInfoLock);
            return true;         /* shared hash table never touched */
        }
    }
    LWLockRelease(&MyProc->fpInfoLock);
    return false;                    /* all 16 slots full — fall back to the shared table */
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Push the common case out of shared memory entirely. A PGPROC's fast-path slots are private to the backend that owns them — no partition lock, no cache-line contention with any other backend, for the overwhelming majority of lock requests a normal workload issues. 2. Make the rare case (a strong locker) pay the transfer cost, not the common case. Someone requesting AccessExclusiveLock is already about to do something disruptive (a schema change); asking it to walk every backend's fast-path array and migrate matching entries into the shared table is a cost paid exactly where the operation is already expensive, never on the hot path. 3. Keep the deadlock detector's victim rule dead simple. By always aborting the backend that ran the check, DeadLockCheck() never needs a cross-process abort mechanism, never needs to prove another backend's rollback is safe from the outside — it only ever unwinds its own stack, which every backend already knows how to do correctly via its own error-handling path.
