APPLIED CRYPTOGRAPHY · CHAPTER 09

Public-Key Cryptography:
RSA Internals

Every chapter so far assumed Alice and Bob already share a secret key. This chapter asks the question the first eight dodged: how do two parties who have never met, over a wire an adversary can read, agree on anything secret at all? RSA's answer is a trapdoor: a function anyone can compute in one direction, that only the holder of a hidden secret can invert. We derive it from two prime numbers, watch its naive form fail in two distinct and mathematically exact ways, and rebuild it as OAEP — with real generated BigInt keys, real modular exponentiation, and a real multiplicative-malleability break, computed live in your browser, not simulated with fake-looking hex.

ARC 01 · THE PROBLEM

Eight chapters of secrets, zero chapters of how you got the key

Go back and look at every cipher in this course so far. AES (chapter 3) needs a 128-bit key both sides already hold. ChaCha20 (chapter 4) needs the same. HMAC (chapter 6), AES-GCM (chapter 7), HKDF (chapter 8) — every one of them takes a shared secret as a precondition and does something clever with it. None of them explain how that secret got from Alice to Bob in the first place, over a network that Eve controls.

Naively, this looks solvable with logistics: meet in person, exchange a USB drive, use a courier. It does not scale. For n parties who might ever need to talk privately, pairwise pre-shared keys require roughly n(n-1)/2 secret exchanges — 5,000 pairwise secrets for 100 people, 500 million for 32,000. Every browser that opens a padlock icon against a server it has never contacted before is solving this exact problem, thousands of times a second, with strangers.

In 1976, Whitfield Diffie and Martin Hellman named the shape of a solution before anyone had built one: a trapdoor one-way function — an operation that is cheap to compute forwards for anyone, and computationally infeasible to invert unless you hold a secret trapdoor. Think of a padlock a stranger can snap shut on a box using only your public, openly-published key, but which only you can open, using a private key you never send anywhere. If such a function exists, key distribution collapses: publish your public key in a directory (or just send it over the insecure channel — it doesn't need to be secret), and anyone can lock a message only you can open. No prior meeting required.

WHERE RSA FITS

Diffie and Hellman described the shape and, in the same 1976 paper, solved a related-but-different problem — agreeing on a shared secret via the hardness of the discrete logarithm (chapter 11) — but did not publish a working public-key encryption function. Ron Rivest, Adi Shamir, and Leonard Adleman found one in 1977, built from a much older piece of number theory: multiplying two large primes is cheap; recovering the two primes from their product — factoring — is, as far as anyone has proven, not. That asymmetry is the entire trapdoor. Everything else in this chapter is the engineering required to turn "multiplication is a one-way function" into a safe encryption scheme — which, as you're about to see, is far more work than the one-line math suggests.

ARC 02 · HISTORICAL CONTEXT

A function hiding in plain sight since Euler

The mathematics RSA needed — Fermat's Little Theorem, Euler's generalization of it — is 250 years older than the algorithm. What took until 1977 was realizing multiplication-of-primes was a trapdoor, not just an interesting one-way function. Click through the record.

DEEP CONTEXT · THE CLASSIFIED SEVEN-YEAR HEAD START

In 1997, GCHQ declassified documents showing that Clifford Cocks, a British mathematician, had described the mathematical equivalent of RSA in an internal memo in 1973 — four years before Rivest, Shamir, and Adleman — while working on a problem posed by James Ellis (who had himself sketched the trapdoor-function idea in 1970, before Diffie and Hellman's public paper). Because it was classified signals-intelligence work, none of it influenced the public research community, and Cocks received no academic credit for two decades. The lesson for working engineers: intelligence agencies and academia have independently rediscovered the same hard mathematics more than once — assume adversary sophistication, not adversary ignorance.

ARC 03 · NAIVE SOLUTION

Attempt #1: multiply, then just raise to a power

Derive it the way Rivest, Shamir, and Adleman did: start from Euler's theorem and stop as soon as something computes. Euler's theorem says that for any integer m coprime to n, m^φ(n) ≡ 1 (mod n), where φ(n) is Euler's totient. If you pick two exponents e and d such that e·d ≡ 1 (mod φ(n)), then for any message m: (m^e)^d ≡ m^(e·d) ≡ m^(1 + k·φ(n)) ≡ m (mod n) — raising to e and then to d gets you back where you started. That's the whole trick: e is public, d is private, and finding d from e requires knowing φ(n), which requires knowing the factorization of n — the one thing only the key's owner computed.

pseudocodetextbook_rsa.txt — the entire idea, unadorned
// Key generation — done once, by the key's owner
generate_keys():
    p, q   := two large random primes
    n      := p * q
    phi    := (p - 1) * (q - 1)
    e      := 65537                     // public exponent — fixed, well-known
    d      := modular_inverse(e, phi)   // e·d ≡ 1 (mod phi) — the ONLY secret
    return public(e, n), private(d, n)

// Anyone with the public key can do this
encrypt(m, e, n):
    return pow(m, e, n)              // c = m^e mod n — that's it

// Only the private-key holder can do this
decrypt(c, d, n):
    return pow(c, d, n)              // m = c^d mod n

This is genuinely correct mathematics — worked by hand on Wikipedia's own textbook example: p=61, q=53 gives n=3233 and φ(n)=3120; picking e=17 and solving for d gives d=2753. Encrypting m=65 with 6517 mod 3233 yields c=2790, and decrypting 27902753 mod 3233 gives back exactly 65. Section 8 walks through both computations digit by digit. It looks like the whole algorithm — five lines, no keys to synchronize, no rounds, no S-boxes. That simplicity is exactly what makes it dangerous: nothing in these five lines says anything about what m is allowed to be, and the function itself is a bare mathematical map with no randomness anywhere in it.

ARC 04 · WHY IT FAILS

Two fatal leaks, both provable, neither a bug

"Textbook RSA" — raw modular exponentiation with no padding — is not broken because someone implemented it wrong. It fails because it is exactly what the pseudocode says it is: a fixed, deterministic, algebraically structured permutation of the integers mod n. Every property that makes RSA's correctness provable also makes its naive use as encryption provably unsafe.

Leak 1 — determinism: the same input always produces the same output

encrypt(m) is a pure function of m, e, and n — no random input anywhere. Encrypt the string "BUY" under a given public key today, tomorrow, and next year, and you get the identical ciphertext every time. If an eavesdropper suspects the message space is small — a trading signal ("BUY"/"SELL"/"HOLD"), a yes/no flag, one of a known list of account numbers, a 4-digit PIN — they precompute encrypt(candidate) for every candidate once and get a permanent lookup table: from then on, decryption is a dictionary lookup, with zero knowledge of the private key. This is not a low-probability edge case; it is the default behavior of every application that encrypts anything with a message space smaller than the modulus. Leak 2 — multiplicative malleability: ciphertexts form a ring under the same operation as plaintexts

RSA's encryption function is a ring homomorphism for multiplication: for any two messages m1, m2 under the same public key,

THE MATH, EXACTLY

c1 · c2 mod n = (m1^e mod n) · (m2^e mod n) mod n = (m1 · m2)^e mod n = encrypt(m1 · m2 mod n)

Multiplying two ciphertexts together, mod n, produces a valid ciphertext for the product of the two original plaintexts — and decrypting it recovers m1 · m2 mod n without the attacker ever learning m1 or m2 individually. Concretely: if Eve intercepts a ciphertext c for a wire-transfer amount m she cannot read, she can still compute c' = c · encrypt(k) mod n for any integer k she chooses, without factoring anything or touching the private key. When Bob decrypts c', he gets k·m mod n — Eve just multiplied a transfer amount she never saw by a factor of her choosing. The live simulator in §15 runs this exact attack on real generated keys.

A third, sharper consequence of the same flaw is Håstad's broadcast attack: if a small public exponent (e=3, historically common for performance) is used with no padding to send the same message m to three recipients with three different, pairwise-coprime moduli n1, n2, n3, an eavesdropper who collects all three ciphertexts can combine them via the Chinese Remainder Theorem to recover m^3 mod (n1·n2·n3) — and because the real m satisfies m^3 < n1·n2·n3 (m is smaller than any single modulus, so its cube is smaller than their product), that value is m^3 over the integers, not just mod something. An ordinary integer cube root recovers m exactly. No factoring, no private key, no brute force — just arithmetic anyone can run in milliseconds.

ARC 05 · BETTER SOLUTION

First fix: make the input unpredictable before you exponentiate

Both leaks share a root cause: encrypt() sees the raw message and nothing else. The obvious fix is to transform the message first — pad it with structure and randomness — so that (a) the same plaintext produces different padded blocks each time, killing determinism, and (b) a forged or manipulated ciphertext almost never decrypts to something with valid structure, making forgeries detectable. This is exactly what PKCS#1 v1.5 (RFC 8017, and its predecessors back to 1993) does. Step through its construction:

Two identical plaintexts now produce different ciphertexts almost certainly (the padding string PS is re-randomized every call), which kills the dictionary-lookup attack from §4. And a ciphertext an attacker constructs by multiplying two valid ciphertexts together will, after decryption, almost never begin with the required 00 02 bytes and contain a 00 separator in the right place — random garbage passes that specific structural check with vanishingly small probability. This is real progress: it is exactly the fix a working engineer would reach for.

ARC 06 · WHY THAT STILL HURTS

"Almost never" is exactly the crack an oracle needs

Notice the hedge in the last section: forged ciphertexts almost never pass the padding check. For a cryptographic proof, "almost never" is not zero, and — far worse — real servers tell you when it happens. A TLS server implementing PKCS#1 v1.5 decryption has to do something when the padding check fails versus succeeds: raise a different error, take a measurably different code path, or simply take different time. Any observable difference is a one-bit oracle: "was this ciphertext's padding valid or not?"

WHAT AN ORACLE ENABLES — THE HEADLINE, NOT THE MECHANISM

In 1998, Daniel Bleichenbacher showed that an attacker who can ask a server "is this ciphertext's PKCS#1 v1.5 padding valid?" a few hundred thousand to a million times, adaptively choosing each next query from the previous answer, can fully decrypt an intercepted RSA ciphertext — without ever learning the private key. The attack turns a single leaked bit per query into the entire plaintext, byte by byte, using exactly the multiplicative-malleability property from §4: each query multiplies the target ciphertext by a chosen s^e mod n and asks whether the result still looks like valid padding. Chapter 10 builds this attack from scratch, query by query, against a live padding oracle — this chapter only needs you to see why a structural check is not a security proof.

The deeper cost: PKCS#1 v1.5 padding was never accompanied by a formal security proof — it predates the provable-security methodology (semantic security, chosen-ciphertext security) that became standard practice in the 1990s. It is a plausible-looking construction that happened to have a devastating, exploitable gap nobody had proven absent. Nineteen years later, §11 shows the same oracle resurfacing in production TLS stacks that thought they had patched it. What the field actually needed was a padding scheme with a mathematical argument for why no such oracle can exist — which is what OAEP is.

ARC 07 · FINAL ARCHITECTURE

OAEP: padding with a proof, not a hope

Optimal Asymmetric Encryption Padding (Bellare & Rogaway, 1994; standardized as RFC 8017 §7.1) is built specifically so that recovering any information about m from a ciphertext — without the private key — is provably as hard as inverting RSA itself, in the random-oracle model. WHY THE DOUBLE MASKING, NOT JUST ONE XOR

Notice the seed masks the data block, and then the (already-masked) data block masks the seed right back — a small Feistel-like network of exactly two rounds. This is deliberate: it means every bit of the final EM depends on every bit of the seed and every bit of the message. Flip a single bit anywhere in a ciphertext and, after decryption, the recovered EM decodes to unrelated garbage almost everywhere — not a localized, attacker-predictable change the way naive padding schemes can produce. This "diffusion of a plaintext-independent random seed across the whole block" is precisely what makes the scheme's security proof possible, and precisely what defeats the homomorphic multiplication attack from §4: the attacker's chosen multiplier no longer produces a predictable change in the decoded message, it produces decoding failure.

ARC 08 · INTERNAL IMPLEMENTATION

The four pieces of real math, worked by hand

Everything RSA needs reduces to four operations: finding large primes, computing a modular inverse, computing a modular exponentiation, and — for OAEP — masking bytes with a hash-based stream. All four are implemented for real in this chapter's JavaScript (BigInt throughout, no floating point) and exercised live by §15's simulator. This section derives each one using the chapter's running p=61, q=53 example.

(a) Finding p and q: nobody can test primality "for certain" at these sizes — so don't

There is no known efficient algorithm to prove a 1024-bit number prime with total certainty in production time budgets (deterministic tests like AKS exist but are impractically slow). Real implementations — and this chapter's — use the Miller–Rabin probabilistic test: pick a random witness a, and check an identity that every prime satisfies and that a composite number fails with probability at least ¾ for a randomly chosen witness. Repeat with k independent random witnesses; a composite that fools all k rounds has probability at most 4⁻ᵏ — negligible well before k=40. Drag the sliders to see the tradeoff, then generate a real prime and watch how many random odd candidates it actually took (most composites are rejected by trial division against small primes before Miller–Rabin even runs, which is why this finishes in milliseconds even in a browser tab).

(b) The modular inverse: extended Euclid, run backwards

With φ(n)=3120 and e=17, we need d such that 17d ≡ 1 (mod 3120). The extended Euclidean algorithm finds it in two passes: run ordinary Euclid forward to get the GCD (confirming e and φ(n) share no common factor — if they did, no inverse would exist and e would have to be rejected), then substitute backward to express that GCD as a combination of the two original numbers.

(c) Modular exponentiation: square-and-multiply, not a million multiplications

Computing 65^17 mod 3233 the naive way means 16 multiplications by 65 followed by 16 modulus reductions — for a real 2048-bit exponent that is astronomically too slow. Square-and-multiply (exponentiation by squaring) does it in about log₂(e) squarings plus one multiply per set bit of e, by walking the exponent's binary representation. 17 in binary is 10001 — five bits, so five squarings and two multiplications total, regardless of how large e's value is, only how many bits it has.

THE COST OF PADDING, IN BYTES

OAEP's overhead is exactly 2·hLen + 2 bytes, unconditionally, no matter how short your message is. At 2048 bits (256 bytes) with SHA-256 (hLen=32), that is 66 bytes of fixed overhead, leaving 190 bytes for the message — which is why RSA is essentially never used to encrypt data directly at scale. Real systems use RSA-OAEP to encrypt a short, fixed-size symmetric key (a "key transport" or "envelope encryption" pattern, chapter 15) and let AES-GCM or ChaCha20-Poly1305 handle the actual payload — RSA does the one thing only it can do (solve the key-distribution problem from §1) and hands off immediately to primitives built for bulk speed.

Read this as the field's actual, converged answer: nobody uses RSA-OAEP to encrypt bulk data, and nobody uses AES with no key-exchange story. Production TLS is a composition — an asymmetric step solves distribution once per session, a symmetric cipher does the actual work — and RSA's specific role in that composition has been steadily shrinking in favor of ECDH (ch. 11) precisely because of the forward-secrecy row above.

THE NUMBERS BEHIND THE DOTS

RSA-155 (512 bits, 1999), RSA-768 (2009, ~2000 CPU-years via GNFS, Kleinjung et al.), and RSA-250 (829 bits, February 2020, ~2700 CPU-core-years, Boudot et al. — the current public record) are real, published factorizations. The one caveat that matters for a staff engineer's roadmap, not this year's incident review: Shor's algorithm (1994) factors integers in polynomial time on a sufficiently large, fault-tolerant quantum computer — a threat model classical GNFS numbers say nothing about. No such machine exists today at the scale required, but "harvest now, decrypt later" — recording today's RSA-encrypted traffic to decrypt once a capable quantum computer exists — is why NIST's post-quantum migration timeline (chapter 15 touches this) treats long-lived confidential data as more urgent than short-lived sessions.

ARC 11 · REAL-WORLD INCIDENTS

Four ways RSA has actually failed in production

1998 & 2017: Bleichenbacher's oracle, twice

Daniel Bleichenbacher's original 1998 attack against SSL's PKCS#1 v1.5 decryption (§6) forced an entire round of TLS defensive redesign. Nineteen years later, ROBOT ("Return Of Bleichenbacher's Oracle Threat," 2017, Böck/Somorovsky/Young) found the identical class of oracle alive in the TLS stacks of major vendors — F5 BIG-IP (CVE-2017-6168), Citrix (CVE-2017-17427), Radware, and others — affecting roughly 2.8% of the top one million HTTPS domains at disclosure. Root cause: implementers had patched the specific 1998 symptom (a distinguishable error message) but left subtly different timing or code paths on the "invalid padding" branch — a different channel carrying the exact same one-bit signal. The lesson generalizes past RSA: patching a leak's symptom does not remove the leak if the underlying decision is observable through any side channel at all. Chapter 10 builds the full attack.

2012: "Mining Your Ps and Qs" — factoring by accident, at internet scale

Heninger, Durumeric, Wustrow, and Halderman (USENIX Security 2012) scanned the public internet, collected millions of live RSA public keys from TLS and SSH servers, and ran a batch GCD across the entire set — computing pairwise greatest common divisors across millions of moduli in roughly n·log(n) time using a product-tree trick, with no factoring algorithm involved at all. They found that roughly 0.75% of TLS hosts and about 1% of SSH hosts shared one of their two primes with another host's key — entirely by accident. Any pair sharing a prime factors instantly: gcd(n1, n2) = p. Root cause: not RSA's math, which worked exactly as designed — the failure was almost universally low-entropy embedded devices (routers, appliances) seeding their random number generator immediately at boot, before enough environmental entropy had accumulated, so two different devices' generatePrime() calls occasionally drew from the same narrow pool of "random" bits and produced the same prime. RSA is only as strong as the randomness feeding key generation — see §8's own generatePrime for the honest, uniformly-random alternative.

2017: ROCA (CVE-2017-15361) — a performance shortcut with a mathematical cost

Infineon's RSALib, embedded in millions of smartcards, TPMs, and government ID chips, generated RSA primes with a specific structural form chosen to speed up on-chip key generation. Nemec et al. showed that structure made the primes fingerprintable and factorable via a Coppersmith-style lattice attack dramatically faster than generic factoring — practical for 512- and 1024-bit keys, and expensive-but-feasible even at 2048 bits on rented cloud compute. Chapter 14 does the full root-cause teardown of the number theory; the one-line version for this chapter: performance shortcuts inside prime generation are exactly where real RSA implementations go wrong — which is precisely why §8's generatePrime does nothing clever: uniformly random candidates, Miller–Rabin, nothing structured, nothing fast-pathed.

Håstad's broadcast attack, in the wild

The §4 broadcast-attack math is not purely academic: e=3 with inadequate or absent padding was common enough in early 1990s implementations (and in some embedded/IoT stacks much later) that Håstad's 1988 attack and its refinements remain a standard item in modern penetration-testing checklists whenever a system reuses one message across multiple recipients' public keys — the fix, as this chapter has now derived twice over, is always the same: never exponentiate a message directly; encode it first with fresh randomness.

Crsa_gen.c — the probable-prime search, simplified
static int
rsa_keygen(RSA *rsa, int bits, BIGNUM *e_value, BN_CTX *ctx)
{
    BIGNUM *p = BN_new(), *q = BN_new(), *p1 = BN_new(), *gcd = BN_new();

    do {
        BN_generate_prime_ex(p, bits / 2, 0, NULL, NULL, NULL);  /* Miller-Rabin, ~64 rounds  */
        BN_sub(p1, p, BN_value_one());
        BN_gcd(gcd, p1, e_value, ctx);
    } while (!BN_is_one(gcd));  /* gcd(p-1, e) MUST be 1, or e has no inverse mod p-1 */

    do {
        BN_generate_prime_ex(q, bits / 2, 0, NULL, NULL, NULL);
        /* ... same gcd(q-1, e) == 1 check ...                        */
        /* ... AND |p - q| must be large: too close and n = p*q      */
        /*     becomes vulnerable to Fermat's factorization method    */
        /*     (search near sqrt(n) for a perfect-square difference). */
    } while (too_close(p, q) || !BN_is_one(gcd));

    BN_mul(rsa->n, p, q, ctx);
    /* d = e^-1 mod lcm(p-1, q-1) via BN_mod_inverse() — §8b's algorithm, at scale */
    return 1;
}

/* Naively: m = c^d mod n  — one full-size modular exponentiation.        */
/* Instead, split the work across the two half-size primes and combine:  */

{
    lHash = Hash(param, plen);                                  /* SHA-256(label)     */
    DB    = lHash || zeros(k - flen - 2*hLen - 2) || 0x01 || from;
    RAND_bytes(seed, hLen);                                       /* CSPRNG, not Math.random */
    dbMask    = MGF1(seed, k - hLen - 1);
    maskedDB  = DB XOR dbMask;
    seedMask  = MGF1(maskedDB, hLen);
    maskedSeed = seed XOR seedMask;
    EM = 0x00 || maskedSeed || maskedDB;
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. CRT is fast, so verify after. The recombination step above ends with re-encrypting the result and checking it equals the original ciphertext. This exists because of the Boneh–DeMillo–Lipton fault attack (1997): a single injected hardware fault (a bit flip from a voltage glitch, historically demonstrated against smartcards) during one of the two CRT exponentiations produces an m1/m2 pair whose recombination reveals a factor of n via a simple gcd — turning a single faulty computation into a total private-key compromise. The verify-after-decrypt step catches exactly this, at the cost of one "wasted" public-key operation per decryption — a trade every serious implementation makes. 2. Constant-time exponentiation. A Montgomery ladder performs the identical sequence of multiplications regardless of the secret exponent's bit pattern, specifically so that measuring how long decryption takes reveals nothing about d (chapter 15 covers timing side-channels in depth). 3. Blinding. Before exponentiating, multiply the ciphertext by a fresh random r^e mod n, then divide the result by r afterward — the mathematics is unaffected, but every decryption now processes a value the attacker cannot predict, defeating timing attacks that rely on correlating specific ciphertext bit patterns with specific timing. All three are defenses against attacks that have nothing to do with factoring — the algebra was never the weak point; the implementation surface was.
