RABBITMQ INTERNALS · CHAPTER 05

Delivery: ACK, NACK,
Confirms & Prefetch

Every RabbitMQ deployment eventually asks the same question twice, on two different wires, and conflates the two answers into one mental model when it shouldn't. On the consumer side: has the broker actually been told a message was handled, or did it just get pushed onto a socket? On the publisher side: has the broker actually made the message durable, or did the client just finish a local write() call? These are independent contracts — Basic.Ack/Basic.Nack answer the first, publisher confirms answer the second — and the valve that sits between "how fast can the broker push" and "how fast can a consumer actually keep up" is Basic.Qos, prefetch. This chapter derives all three from first principles, then builds a delivery lab where you can crash consumers, feed them poison messages, and watch the fairness-versus-throughput tradeoff move under your own prefetch slider.

ARC 01 · THE PROBLEM

"Delivered" is not the same event as "handled"

A TCP send() returning successfully tells you exactly one thing: the kernel on the sending machine copied your bytes into a socket buffer. It says nothing about whether the receiving process ever read them, nothing about whether that process is still alive by the time it would have, and nothing about whether whatever business logic was supposed to run against that data actually ran. A message broker built on top of "the socket write succeeded" as its notion of delivery is building reliability on a signal that was never designed to carry that meaning.

Concretely: Basic.Deliver is the AMQP method the broker uses to hand a message to a consumer on a channel. The instant the broker has framed that method and its content onto the wire, has anything actually been guaranteed? No — the consumer's process could be killed by the OOM killer one microsecond after the bytes land in its socket buffer, before a single line of the handler runs. If the broker's bookkeeping treats "sent" as "done" — removes the message from the queue the moment it writes the frame — that message is gone. Not redelivered, not logged, not recoverable. Silently gone.

Symmetrically, on the publish side: a producer calling channel.basic_publish(...) and having that call return without an exception tells you the client library successfully wrote a frame to its own local socket buffer. It does not tell you the broker received it, routed it to a durable queue, or wrote it to disk before a subsequent node restart. Two separate "did this actually happen" questions, on two separate wires, each needing its own explicit protocol answer — not because AMQP is being pedantic, but because at every one of these boundaries a real, physical failure (a crashed process, a partition, an unflushed page cache) can turn "sent" and "done" into two different truths.

WHY THIS CHAPTER SPLITS CLEANLY IN TWO

Consumer acknowledgement and publisher confirmation are mechanically independent — different frames, different delivery tags, different failure modes, and (critically) no ordering relationship between them imposed by the protocol. A message can be acked by its consumer while its publisher's confirm is still in flight; a message can be Basic.Returned to its publisher as unroutable and still receive a publisher ack, because "routed to zero queues" and "safely handled by the broker" are, again, two different questions (§6 makes this exact interaction precise). Keep the two halves separate in your head throughout this chapter — conflating them is the single most common production RabbitMQ misunderstanding.

ARC 02 · HISTORICAL CONTEXT

Acks were in the protocol from day one; confirms were not

Unlike some of RabbitMQ's later engineering (quorum queues, streams), consumer acknowledgement is original AMQP 0-8/0-9-1 protocol machinery — the working group considered "did the consumer handle this" a first-class concern from the start. Publisher-side confidence took a different, more interesting path: the spec's original answer (transactions) worked but was priced out of practicality, and RabbitMQ's team shipped a pragmatic extension years later that the rest of the ecosystem eventually treated as a de facto standard. DEEP CONTEXT · BASIC.NACK IS NOT IN THE ORIGINAL SPEC

It's a common surprise: Basic.Reject is the AMQP 0-9-1 standard method for "I will not accept this message" — one delivery tag at a time, no multiple flag, requeue true or false. Basic.Nack is a RabbitMQ-specific extension layered on afterward specifically to add the multiple flag (batch-nack a whole range the way Basic.Ack already could) — a gap the original spec simply didn't cover. It's now supported so widely (most 0-9-1 client libraries, other brokers that emulate RabbitMQ's extensions) that engineers routinely assume it was always part of the standard. It wasn't; it's a case study in how a popular implementation's extension becomes ecosystem convention.

ARC 03 · NAIVE SOLUTION

Attempt #1: auto-ack — trust the socket write

The simplest possible consumer configuration in AMQP sets no_ack=true (most client libraries call this auto_ack). Under this mode the broker considers a message fully delivered — and removes it from the queue — the instant it writes the Basic.Deliver frame. There is no delivery tag the consumer is expected to do anything with; there is no unacked set for this consumer at all.

pythonnaive_consumer.py — auto_ack=True, annotated
def on_message(channel, method, properties, body):
    # By the time this callback is even INVOKED, the broker has already
    # forgotten this message existed — it was removed from the queue
    # the moment the frame was written to the socket, not when this
    # function returns, or even starts.
    result = process_payment(body)          # ← if the process dies HERE...
    write_to_ledger(result)                   # ...or dies HERE, the message is unrecoverable.

channel.basic_consume(
    queue="payments",
    on_message_callback=on_message,
    auto_ack=True,                            # the entire naive solution is this one flag
)

It is not an unreasonable starting point — it gets one thing right: zero protocol chatter beyond the delivery itself, no Basic.Ack frames, no broker-side bookkeeping of an unacked set per channel. For metrics counters and other truly loss-tolerant streams, auto-ack is the correct choice, not a shortcut. The problem is that most consumers are not metrics counters, and the stepper below plays forward exactly the failure auto-ack cannot detect, let alone recover from.

ARC 04 · WHY IT FAILS

The math: the loss window is unbounded, and there is no valve

Quantify what the deck just showed. Under auto-ack, define the in-flight window as every message the broker has written to the socket but the consumer's application code has not yet finished processing. Under explicit acknowledgement this window is bounded by prefetch (§8 derives the exact number); under auto-ack, nothing bounds it at all — the broker will write frames onto the socket as fast as the kernel accepts them, which is usually far faster than any real handler can process them.

  • Unbounded loss on crash. If a consumer's process dies after accepting N messages from its local socket/library buffer but before finishing them, all N are gone — not requeued, because the broker already considered them delivered and discarded its only record of them. N is bounded only by how far ahead of processing the socket buffer and client library got, which under auto-ack is exactly the quantity nothing is designed to limit.
  • No back-pressure signal exists. Basic.Qos (prefetch) is defined in terms of the unacknowledged message count on a channel — under auto-ack that count is definitionally always effectively zero from the broker's perspective (messages are "acked" the instant they're sent), so prefetch has nothing to gate. A slow consumer cannot signal "stop sending" to the broker at the protocol level; it can only build an ever-larger backlog in its own process memory.
  • The failure is invisible until it's catastrophic. Nothing errors, nothing logs, no queue depth alarms fire — from the broker's point of view every one of those messages was successfully delivered. The first symptom is usually a downstream data-consistency bug discovered days later, not an operational alert at the moment of loss.
THE NUMBERS

A consumer processing 500 messages/sec can easily have a client-library prefetch/OS-buffer window of several thousand messages already "delivered" and sitting in local memory or the library's internal queue at any given instant, especially if a downstream call (a slow HTTP request, a lock-contended DB write) stalls processing for even a second or two. Under auto-ack, a crash during that stall doesn't lose a handful of messages — it loses every message the socket and client library had already accepted and forgotten about, with zero broker-side visibility that anything went wrong.

The fix needs two independent pieces, worth separating cleanly exactly the way we did in the naive-fanout chapters: (a) the broker must not consider a message "done" until the consumer explicitly says so, and (b) once that's true, something has to bound how many "not yet done" messages the broker is allowed to have outstanding to any one consumer at a time, or a slow consumer just accumulates an unbounded backlog instead of losing one. §5 derives both.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Two separate derivations: explicit acks with a credit window, and asynchronous confirms

These are genuinely two different problems wearing similar clothes. Work through the consumer side first — how does the broker know a message was handled, and how does it avoid flooding a slow consumer — then the publisher side — how does a producer know a message is safely durable without paying for a synchronous round trip on every single message.

Consumer side: from "trust the socket" to "explicit, tagged, credit-limited"

Deriving delivery tags, Basic.Ack and prefetchSTEP-BY-STEP

The deck's final state is the real protocol: every message delivered on a channel carries a delivery tag — a 64-bit counter, monotonically increasing, scoped to that one channel. The consumer calls Basic.Ack(delivery_tag, multiple) when done; the broker only then removes the message from the durability-relevant part of its bookkeeping. Basic.Qos(prefetch_count) caps how many unacked messages the broker will let accumulate before it stops delivering more — the credit window that turns "unbounded backlog" into "a number you chose."

WHY PER-CHANNEL, NOT GLOBAL OR PER-CONNECTION

A delivery tag only has meaning as an instruction back to the channel that issued it — Basic.Ack is sent on a channel, and the broker interprets the tag against that channel's own unacked-set, not some node-wide table. Making the counter per-channel means two independent channels — even on the same connection, even in the same process — never contend on a shared atomic increment, and never need to coordinate at all: rabbit_channel is already a single-threaded gen_server2 process handling one channel's protocol traffic serially, so a private, unshared counter is simply a field in that process's own state, incremented with zero synchronization cost. A global counter would force every publish and every ack across the entire node through one contended piece of shared state for no semantic benefit — acks are inherently a channel-scoped conversation, not a node-scoped one.

Publisher side: from "hope" to synchronous transactions to asynchronous confirms

Deriving publisher confirms from AMQP transactions' failureSTEP-BY-STEP

The AMQP 0-9-1 spec's own answer to "does the publisher know it's safe" is the Tx class: Tx.Select puts a channel into transaction mode; every publish since the last commit is only durably applied when Tx.Commit returns. It works, and it is honest — but §6 quantifies exactly why it was abandoned in practice. Confirms (Confirm.Select) are RabbitMQ's answer: the broker assigns each published message on a confirm-mode channel a sequence number, and asynchronously sends back Basic.Ack (reusing the same method name as consumer acks, on the publisher's channel this time) once the message is safely handled — persisted to disk if the message and its queue are durable, or simply enqueued if not. The publisher never blocks a socket write waiting for it; it tracks outstanding sequence numbers and reconciles as acks stream back, possibly batched via multiple, possibly out of order relative to publish order.

ARC 06 · WHY THAT STILL COSTS

Requeue storms, poison loops, mistuned prefetch, and a durability triad nobody checks at runtime

Explicit acks plus a credit window plus asynchronous confirms is the right architecture — and it has four real, physical costs that every operator eventually meets in production:

1. Channel/connection death requeues everything, all at once, near the head

This is the entire durability contract for in-flight work, stated precisely: if a channel or its owning connection terminates for any reason while messages are in its unacked set, the broker automatically requeues every one of them. That's the safety property — but it has a sharp edge. A consumer with prefetch_count=500 that crashes mid-batch doesn't lose work (good), but it also doesn't requeue those 500 messages gently: they reappear as a burst, and because a requeued message is reinserted essentially at the front of its queue rather than the back, ordering is not preserved across a redelivery — a fact applications that assume strict FIFO consistently get wrong. A message published fifth can be redelivered ahead of a message published third, because "put it back roughly where a not-yet-delivered message would sensibly go" was never a promise to preserve the original global sequence, only to not lose the message.

2. The poison-message loop is a mathematical certainty, not an edge case

Consider a message that will always fail processing — a malformed payload, a foreign-key reference that will never resolve, a bug in the handler triggered by this specific input. The naive, "safe-looking" fix is: catch the exception, call Basic.Nack(requeue=true) so the message "isn't lost." Follow that logic forward: the broker puts the message back, near the head, immediately eligible for redelivery; the very next available consumer (often the same one, an instant later) receives it again; it fails again; it's nacked with requeue again. Nothing in this loop terminates. There is no decrementing counter, no backoff, no escape hatch — just an infinite cycle bounded only by the round-trip latency of deliver→process→nack, consuming 100% of one consumer's capacity (or, worse, blocking an entire single-consumer queue if the poison message sits at the head) while contributing zero completed work.

THE TWO REAL FIXES — NEITHER IS "TRY HARDER IN THE HANDLER"

Dead-lettering with a delivery limit (chapter 8's territory): quorum queues can track a delivery count and, once it exceeds x-delivery-limit, automatically route the message to a configured dead-letter exchange instead of redelivering it again — the loop is broken by the broker itself, with no client cooperation required. Client-side counting: stamp an attempt counter into message headers on first failure (or use the broker-provided x-delivery-count header on quorum queues), and once a threshold is hit, nack with requeue=false and publish to a manual retry/dead-letter queue instead. Both fixes share the same shape: something must count, because redelivered alone (next paragraph) cannot.

3. The redelivered flag is a hint, not a count

redelivered is a single boolean the broker sets on a Basic.Deliver when it believes this message has been sent to some consumer before — it is not a counter, it does not distinguish a first redelivery from a fiftieth, and the broker itself documents it as best-effort (a broker crash and restart can legitimately cause a message to be redelivered without the flag surviving, or set when, strictly, it needn't be). Treating redelivered as a retry counter — "reject it if redelivered is true twice" — is a category error; it can be true on attempt two exactly as often as attempt two hundred.

4. Prefetch is a single knob balancing two things that pull in opposite directions

5. The durability triad is silent about which piece you forgot

A message survives a broker restart only if all three of the following hold: the message was published with delivery_mode=2 (persistent), the queue it landed in was declared durable=true, and the exchange it was routed through was declared durable=true. Miss any one — publish transient to a durable queue, or route a persistent message through a transient exchange whose binding doesn't survive a restart — and you silently lose the guarantee with no runtime error at publish time. The broker accepts the publish, confirms it (confirms only promise "safely handled given the durability you configured," not "durable regardless of what you configured"), and the gap only becomes visible at the next restart, which by definition is the worst possible moment to discover it.

DEEP CONTEXT · WHY THE UNACKED SET LIVES ON THE CHANNEL, NOT THE QUEUE

A message can be delivered from a queue to any of several consumers spread across several channels and connections. Once delivered, whether it's "done" is entirely a fact about that specific delivery — which channel it went out on, which delivery tag it got there. The queue process's job is producing an ordered stream of messages and eventually being told "this one's done, drop it" or "this one's back, requeue it"; it doesn't need to track deliveries itself once handed off. The channel process is the natural owner because it's already the thing that assigned the delivery tag and is already being monitored for liveness by the queues it consumes from — when it dies, the queues it delivered to are exactly the queues that need to hear about it.

ARC 08 · INTERNAL IMPLEMENTATION

Delivery tags, the unacked set, requeue-on-death, and deriving the right prefetch

(a) The delivery tag: a per-channel counter, nothing more

Inside rabbit_channel's gen_server2 state is an integer, next_tag, starting at 1 and incremented by exactly one for every Basic.Deliver (and every Basic.Get) the channel sends. There is no encoding trick — no queue identity, no timestamp, no node id packed into the bits. It is deliberately the simplest possible monotonic counter, because its only job is to be a key the channel itself can look up later in its own unacked table. That table — conceptually #{DeliveryTag => {QueuePid, MsgId}} — is exactly what a Basic.Ack(delivery_tag=N) resolves against: find the entry for N, tell that queue "this one's confirmed handled, you can drop your copy," and remove the entry.

(b) Basic.Ack, Basic.Nack, Basic.Reject, and the multiple flag

The multiple flag exists purely to amortize round trips: acking (or nacking) delivery tag 500 with multiple=true is a single frame that resolves every outstanding tag from the last ack point through 500 — the standard pattern for a consumer that processes a batch and acks once at the end rather than once per message.

(c) What actually happens when a channel dies mid-delivery

Every queue a channel has consumed from holds a monitor on that channel's process. When the channel terminates — a client disconnect, an uncaught protocol violation, the process crashing — every monitoring queue receives a 'DOWN' message and walks its own record of what it delivered to that channel's consumer(s), reinserting anything still unacked. This is not a special recovery code path bolted on after the fact: it's the ordinary supervision/monitor mechanism from chapter 1, applied to "messages this process was trusted with." No coordinator process polls for dead channels; the queues that care are already watching.

(d) Deriving the correct prefetch value

Model one consumer's steady-state throughput as a function of prefetch_count (P), the network round-trip time to send an ack and receive the next batch of deliveries (RTT), and the per-message processing time (T). With prefetch P, the broker keeps up to P messages outstanding, so the consumer can be processing message k while message k+1...k+P-1 are already sitting in its local buffer — the ack round trip for early messages in the window overlaps with processing later ones, provided the window is wide enough to hide the RTT entirely: that requires P·T ≥ RTT, i.e. P ≥ RTT / T. Round up for jitter (network variance, GC pauses, occasional slow messages) and you get the practical rule: prefetch ≈ ⌈RTT / T⌉, rounded up further for safety margin. Below that value, the consumer periodically drains its window and stalls waiting on an ack round trip it hasn't overlapped — throughput becomes RTT-bound instead of processing-bound.

Both extremes are real, deliberate operating points, not mistakes: prefetch=1 gives every competing consumer on a shared queue perfectly fair round-robin access (nobody can grab a second message until they've acked the first) at the cost of paying a full RTT per message when RTT is non-trivial relative to processing time. prefetch=0 (unlimited) removes the flow-control valve entirely: the broker pushes every ready message as fast as the socket accepts writes, so whichever consumer's socket drains fastest — often simply whichever connected first — can end up buffering the queue's entire backlog locally while siblings sit idle, and that consumer's crash then requeues (and redelivers, ordering-scrambled per §6) the whole hoard at once.

(e) Global vs per-consumer QoS

Basic.Qos(prefetch_count, global) has meant, since RabbitMQ 3.3 (2014), global=false by default: the prefetch limit applies per consumer registered on that channel — each consumer on a multi-consumer channel gets its own independent window of P unacked messages. Set global=true and the same limit instead caps the sum across every consumer sharing the channel — useful when you want one shared, bounded in-flight budget regardless of how many consumers happen to be registered, at the cost of one busy consumer being able to starve its siblings' share of that shared window.

ARC 09 · TRADEOFFS

Delivery guarantees, seven systems' worth

"At-least-once with explicit acknowledgement and a flow-control credit window" is RabbitMQ's specific answer; read the spread below as proof that every other serious system answers "how do you know it was handled, and how do you keep a consumer from being flooded" with a genuinely different mechanism and a genuinely different price.

The recurring pattern: everyone needs some mechanism to say "this specific piece of work is not yet confirmed done" (a delivery tag, an offset, a visibility timeout, a pending-entries list) and some mechanism to bound how much unconfirmed work can pile up on one consumer (prefetch, `MaxAckPending`, poll batch size, client flow control). RabbitMQ's specific trade is granularity: per-message tags with a multiple batching flag are more precise than an offset or a visibility timeout, at the cost of more protocol chatter than a pure offset commit.

ARC 10 · PERFORMANCE CHARACTERISTICS

What you can predict about throughput and memory before benchmarking

From §8's derivation alone, several concrete performance properties follow:

  • Throughput under prefetch P, RTT R, processing time T: approximately min(1/T, P/R) messages/sec — processing-bound once P is large enough to hide the round trip, RTT-bound below that. The chart below makes the knee in this curve visible.
  • Unacked-set memory is O(prefetch × message-reference-size) per consumer, not O(message body size) — classic queues keep the actual payload in the message store/queue index (chapter 4); the channel's unacked table holds lightweight references, so raising prefetch by 10× costs kilobytes, not megabytes, on the channel process — the real cost of high prefetch is the fairness/ordering exposure from §6, not memory.
  • Confirm-tracking memory is O(unconfirmed publishes) on the publisher's client side — an application publishing faster than the broker confirms accumulates its own unbounded backlog symmetric to §4's consumer problem; well-behaved publisher libraries apply their own outstanding-confirm limit for exactly this reason.
  • Dead-lettering (delivery-limit) adds one extra internal republish per poison message before it's out of the hot path for good — cheap relative to an unbounded loop, but not free; it's still a re-route-and-requeue operation on the broker's critical path once per exhausted message.

ARC 11 · REAL-WORLD PRODUCTION

Three stories: a forgotten ack, a poison loop, and a default nobody read

Story 1: the "prefetch=0 by default" trap that RabbitMQ's own docs now warn about

For years, many client library quickstarts and tutorials shipped examples with no Basic.Qos call at all — meaning unlimited prefetch, the default when a consumer never sets it. Teams that copy-pasted those examples into production workloads with multiple consumers on a shared queue routinely discovered, only after a round of complaints about "why is one worker doing all the work while the others sit idle," that unlimited prefetch means the broker delivers as fast as sockets accept — one fast-draining consumer can vacuum an entire backlog before its slower siblings receive a single message. RabbitMQ's own documentation has since added an explicit callout recommending a bounded prefetch (starting guidance is commonly cited as "somewhere between 10 and a few hundred, tuned to your processing time," directly following this chapter's RTT/T derivation) as a default operational practice, not an edge-case tuning exercise.

Story 2: consumer_timeout (RabbitMQ 3.12, 2022) — turning a silent leak into a loud failure

Before 3.12, a consumer that received a message and simply never acked it (a bug, a deadlock, a forgotten code path) left that message parked in the channel's unacked set indefinitely — invisible unless an operator went looking at per-channel unacked counts, and meanwhile counting against that channel's prefetch window forever, quietly reducing its effective throughput to zero without any error being raised anywhere. RabbitMQ 3.12 introduced consumer_timeout (default 30 minutes, configurable): if a delivery isn't acked within that window, the broker force-closes the channel with a protocol error, requeueing the stuck message via the exact channel-death mechanism §8 describes — converting an invisible, permanent stall into a loud, immediately diagnosable failure. Several teams migrating to 3.12+ discovered long-running batch-style consumers (deliberately holding messages unacked for tens of minutes by design) tripping this new default and had to explicitly raise the timeout — a reminder that a safety default protecting the common case can surprise the deliberately unusual one.

Story 3: an under-provisioned retry queue turns one poison message into a five-alarm incident

A commonly reported shape (echoed across CloudAMQP's and Bloomberg's public operational writeups on RabbitMQ consumer patterns): a single malformed message — often the result of a schema change on the publisher side that the consumer's older deserializer can't parse — enters a queue whose consumer code catches the deserialization exception and nacks with requeue=true, exactly the §6 poison loop. Because the queue in question had only one consumer and no dead-letter configuration, that one bad message pinned 100% of the consumer's throughput in an infinite redeliver-fail-requeue cycle, and every legitimate message published behind it queued up unprocessed for the duration — turning a single malformed record into what looked, from a monitoring dashboard, like a total processing outage. The fix in every one of these postmortems is the same: a dead-letter exchange with a delivery limit (or client-side attempt counting) is not an optional hardening step, it is the difference between a single bad record and a total consumer outage.

First, the shape of the channel's unacked bookkeeping and what Basic.Ack actually does to it, simplified but structurally faithful:

Erlangrabbit_channel.erl — handling Basic.Ack, simplified
handle_method(#'basic.ack'{delivery_tag = Tag, multiple = Multiple}, _, State) ->
    %% unacked_message_q is THIS channel's own table — private state,
    %% never shared with any other channel, never touched by another process.
    {Acked, Remaining} = collect_acks(State#ch.unacked_message_q, Tag, Multiple),

    %% Tell each queue that delivered one of these messages: it's handled.
    lists:foreach(fun({_Tag, QPid, MsgId}) ->
        rabbit_amqqueue:ack(QPid, [MsgId], self())
    end, Acked),

    {noreply, State#ch{unacked_message_q = Remaining}}.

Second, what a queue does when it receives the monitor 'DOWN' for a channel that still had unacked deliveries outstanding — the actual requeue-on-death mechanism:

Erlangrabbit_amqqueue_process.erl — channel death handling, simplified
handle_info({'DOWN', _Ref, process, ChPid, _Reason}, State) ->
    %% Every message this queue delivered to ChPid and never heard an
    %% ack for is still sitting in THIS queue's own "pending ack" set —
    %% the channel never held the message itself, only the bookkeeping.
    Unacked = rabbit_variable_queue:pending_ack_for_channel(State#q.backing_queue_state, ChPid),

    %% Reinsert near the front — these were already "ready to go" a
    %% moment ago, so they don't go through fresh-publish ordering.
    %% This is exactly why redelivery does not preserve global FIFO (ch.5 §6).
    BQS1 = rabbit_variable_queue:requeue(Unacked, State#q.backing_queue_state),

    {noreply, State#q{backing_queue_state = BQS1}}.

Third, the QoS limiter's core decision — whether the channel is currently allowed to accept another delivery from a queue at all:

Erlangrabbit_limiter.erl — the prefetch gate, simplified
can_send(Limiter = #limiter{prefetch_count = Prefetch, in_flight = InFlight}, _QPid) when
    Prefetch =:= 0 orelse InFlight < Prefetch ->
    %% Prefetch 0 means "no limit" — the historically dangerous default
    %% Story 1 (§11) describes. Otherwise: only say yes while there is
    %% still room under the credit window.
    {true, Limiter#limiter{in_flight = InFlight + 1}};
can_send(Limiter, _QPid) ->
    {false, Limiter}. %% queue holds the message; consumer gets it once an ack frees credit
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Put the credit-tracking state as close as possible to the thing being throttled. The limiter lives on the channel, right next to the unacked table it's gating — no separate coordinator process, no round trip to ask permission; a queue asking "can I deliver?" is a synchronous, in-process check against the channel's own counters. 2. Let the queue keep owning the actual message until it's provably safe to forget it. The channel's unacked table never holds message bodies, only identifiers — the queue (backed by the message store, chapter 4) is the durable source of truth throughout, so a channel crash loses only bookkeeping, never data. 3. Make the dangerous default explicit in the code path, not buried in a config file. prefetch_count =:= 0 as a guard clause reads, in the source itself, as "no limit" — the same fact §11's Story 1 shows engineers routinely miss when it's just a number in documentation.
