POSTGRESQL INTERNALS · CHAPTER 09

Buffer Manager &
the Clock-Sweep Algorithm

The kernel already caches your files. PostgreSQL builds an entire second cache on top of it anyway — and that decision, plus the algorithm it uses to decide which page to evict when the cache is full, shapes every read and write your queries perform. This chapter derives why a database cannot simply trust the OS page cache, walks ReadBuffer()'s exact path from a hash lookup to a pinned page, and shows why clock-sweep — not true LRU — is the only replacement policy that scales.

ARC 01 · THE PROBLEM

The OS already caches your files. Why build a second cache?

Every table and index PostgreSQL manages is, at the filesystem level, just a set of files made of fixed-size 8 KB pages. Linux (and every other production OS) already caches recently-read file pages in free RAM via its own page cache, transparently, for free. A database engine that simply called read()/write() for every page access would get OS-level caching for nothing — so why does PostgreSQL maintain its own buffer pool, an entire parallel cache sitting on top of one the kernel already provides?

Three requirements the OS page cache cannot satisfy, no matter how well-tuned:

  • Control over eviction order. The kernel's page cache is shared across every process and every file on the machine, and its eviction policy has no idea that this particular 8 KB page is the root of a B-tree index touched by every query, while that one is a page from a one-time bulk import scanned once and never again. PostgreSQL, by contrast, knows exactly how each page has been used and can make a database-aware eviction decision the OS structurally cannot.
  • Knowing which pages are dirty, precisely. Durability depends on a specific ordering: a page's changes must never reach the underlying data file before the WAL record describing that change has been flushed. The OS page cache's own dirty-page tracking and writeback timing are opaque to PostgreSQL and offer no way to enforce "flush WAL up to LSN X before this exact page is written" — that ordering can only be guaranteed by a cache PostgreSQL itself controls.
  • Pinning. While a backend is actively reading or modifying a page's bytes, that page must not be evicted or relocated out from under it — not by another backend, not by memory pressure elsewhere on the machine. The OS page cache has no concept of "this page is in use right now by this process and may not be dropped"; only an application-level cache can offer that guarantee.

There is also a plain efficiency argument underneath all three: even a page cache hit inside the kernel still costs a read(2) syscall — a mode switch into the kernel, a copy from kernel page-cache memory into a user-space buffer, and back. A cache PostgreSQL controls entirely in its own shared memory lets a hit skip the syscall and the copy altogether once the page is already resident.

WHY THIS MATTERS FOR THE NEXT DOZEN CHAPTERS

The buffer pool is the single most contended shared structure in the entire server — nearly every operation a backend performs touches it, which is exactly why chapter 8's three-tier lock hierarchy exists in the first place. Everything below builds directly on that chapter: buffer pins use atomics faster than any lock, the buffer mapping table is partitioned by LWLocks exactly like the heavyweight lock table, and eviction obeys the same WAL-before-data discipline that makes crash recovery (chapter 11) possible at all.

DEEP CONTEXT · WHY "CLOCK," NOT "LRU"

The clock algorithm — approximating least-recently-used behavior with a circular scan and a per-page "second chance" counter instead of an exactly-ordered list — predates PostgreSQL by decades; it traces to Corbato's work on Multics-era virtual memory management in the 1960s and 70s. PostgreSQL's clock sweep is a direct descendant of that operating-systems lineage, adapted with a multi-level usage_count (0–5) instead of a single reference bit, precisely because a database's access pattern skew is sharper than a generic VM system's and one bit of "was this used recently" isn't enough signal.

ARC 03 · NAIVE SOLUTION

Attempt #1: trust the OS, cache nothing yourself

Derive it honestly. If the kernel already caches file pages, the simplest architecture skips a second cache entirely and issues a plain read()/write() per page access, leaning on the OS for everything.

Cnaive_pager.c — the strawman
char *
ReadPageNaive(int fd, BlockNumber blocknum)
{
    char *buf = malloc(BLCKSZ);           /* 8 KB, fresh every call */
    pread(fd, buf, BLCKSZ, (off_t)blocknum * BLCKSZ);
    /* Trust: the OS page cache already has this block resident
     * if it was recently touched, so this "read" is often just a
     * kernel-memory copy, not a disk seek. No pin, no dirty
     * tracking, no eviction policy of our own — none needed,
     * right?                                                      */
    return buf;
}

void
WritePageNaive(int fd, BlockNumber blocknum, char *buf)
{
    pwrite(fd, buf, BLCKSZ, (off_t)blocknum * BLCKSZ);
    free(buf);           /* no cache to keep it in — next reader re-reads it */
}

This is not absurd — it is exactly how many simple tools (a one-shot ETL script, cp) operate, and it inherits the kernel's own considerable engineering for free: readahead, writeback coalescing, and a cache that's already sized to available RAM. Watch where it falls apart the moment a database's actual access pattern — repeated random access to a working set, with strict durability requirements — is applied to it.

ARC 04 · WHY IT FAILS

Syscalls, double copies, and no way to keep a promise

The naive design fails in ways that are each individually disqualifying for a database:

  • Syscall overhead on every touch, even cache hits. A pread() that the kernel satisfies entirely from its page cache still costs a full user/kernel mode transition plus a memory copy from kernel space into the caller's buffer — commonly hundreds of nanoseconds to low microseconds even with zero disk I/O. A hot index root page touched thousands of times per second pays that tax every single time.
  • No pinning means no safety. Nothing stops the kernel from evicting a page's cached copy the instant after you read it and before you finish working with the bytes you copied out — which sounds harmless (you already have your own copy) until you consider that every backend re-reads and re-copies independently, with zero sharing of in-flight work, and zero way to say "don't let this go away, I'm mid-modification."
  • No enforceable write ordering. Durability requires WAL describing a change to reach stable storage strictly before the changed data page does. The OS page cache's writeback (via pdflush-style kernel threads, or explicit fsync()) has no concept of "wait for this other file's fsync first" tied to a specific page — that ordering guarantee has to live in a layer PostgreSQL itself controls end-to-end.
  • Double buffering, with no coordination. Every backend's private malloc()'d 8 KB copy plus the kernel's own page-cache copy means the same page's bytes exist in at least two places in RAM simultaneously, for every backend touching it — memory spent without a matching benefit, since neither copy is shared with anyone.
THE NUMBERS

At even a modest 200,000 buffer touches/sec (unremarkable for an OLTP system with a decent-sized working set) and ~300 ns of avoidable syscall + copy overhead per touch on an already-cached page, that's 60 ms/sec of pure overhead paid for work that provides zero additional caching benefit over an application-level cache — and that number climbs steeply, not linearly, once contention and copy costs compound under real concurrency. The naive design isn't slow because disk is slow; it's slow because it re-pays for a cache hit it should get almost for free.

Durability and pinning aren't optimizations you can add on top of this design later — they require a cache PostgreSQL owns and can reason about precisely. §5 looks at what shape that cache should take.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Fixed pool, yes — but replaced by what rule?

Candidate A: mmap() the whole file, let the OS manage everything

mmap() each relation's file and let page faults do the work of "reading" — no explicit read() calls at all, and the kernel's own page cache is the buffer pool. This eliminates the double-copy from §4, but reintroduces every other problem: no pinning (the kernel can still evict or the process can still be sent a SIGBUS on I/O error mid-access, which is far worse than a controlled failure), no enforceable WAL-before-data ordering (msync semantics don't give you fine per-page write ordering relative to a separate WAL file), and no database-aware eviction. Rejected — it solves the copying inefficiency and reintroduces the two harder problems (durability ordering, pinning) at the same time.

Candidate B: an application-level cache with a global, exact LRU list

Keep a fixed array of buffers in shared memory (solves control-over-eviction and pinning), and track recency with a classic doubly-linked LRU list: every access moves its buffer to the head, eviction always takes the tail. This is the textbook "correct" answer to cache replacement and is the resting assumption of most data-structures courses. Rejected in practice for reasons quantified in §6 — a global list requires a lock on every single access to reorder it, and it has no defense against one large sequential scan pushing an entire working set out of cache.

Candidate C: fixed pool + partitioned hash lookup + clock-sweep approximation ✓

Keep the fixed array and the mapping-table idea from B, but replace exact LRU tracking with an approximation that needs no reordering on every hit: each buffer carries a small saturating counter (usage_count), bumped on access and decremented by a circulating "clock hand" looking for a victim. No global list to maintain, no lock taken on the common-case hit path beyond a pin — the eviction scan itself is the only place that walks buffers in order, and it does so lazily, only when a free buffer is actually needed.

Exact LRU vs. clock-sweep approximationSTEP-BY-STEP
THE CLINCHING ARGUMENT: HITS SHOULD NOT PAY WRITE COSTS

The core insight clock-sweep encodes: the overwhelmingly common operation is a cache hit, and a hit should be as close to a pure read as possible. An exact LRU list turns every hit into a write (unlink + relink at the head), which means every hit needs exclusive access to shared list-pointer state — precisely the kind of avoidable contention chapter 8 spent an entire chapter eliminating. Clock-sweep's hit path is a single atomic increment of a small counter; its only "list maintenance" work happens lazily, during the rarer event of needing to evict something.

ARC 06 · WHY THAT STILL COSTS

What a global LRU list actually costs, quantified

It's worth being precise about exactly why candidate B is rejected, because the reasons generalize far beyond buffer management:

  • A lock on every access, full stop. Moving a node to the head of a doubly-linked list on every touch — including every read-only hit — means every single buffer access, the hottest operation in the entire server, must take an exclusive lock on the shared list structure. This recreates precisely the single-global-bottleneck failure mode chapter 8 derived and rejected, just relocated to the buffer pool instead of the lock table.
  • Sequential-scan pollution. True LRU treats "most recently touched" as synonymous with "most valuable to keep," which is false for a one-time sequential scan: a SELECT * over a 500 GB table touches every page exactly once, and under exact LRU every one of those pages becomes the most-recently-used entry as it streams through — evicting the actual hot working set (frequently-reused index pages, hot rows) to make room for pages that will never be touched again. The scan "pollutes" the cache with data that has zero future value while displacing data with high future value.
  • Move-to-front itself is a cache-unfriendly operation. Every LRU update touches at least three list nodes (the moved node and its old neighbors) — three more cache lines to potentially fault or bounce between cores, on top of whatever work the actual buffer access needed.
CLOCK-SWEEP'S OWN COSTS, HONESTLY STATED

Clock-sweep is not free either. It is only an approximation of LRU — under certain access patterns (a working set slightly larger than the buffer pool, cycled through repeatedly) it can perform measurably worse than exact LRU would, because a full circular sweep can pass over a page more than once before deciding to evict it, and does not perfectly distinguish "used once a while ago" from "used constantly until a moment ago" beyond the saturating counter's small range (0–5). And the "victim search" itself is O(buffers examined) in the worst case — if every buffer in the pool has a nonzero usage_count, the hand must make a full circuit, decrementing every counter, before finding a victim. The trade is deliberate: pay an occasional, bounded, lock-cheap sweep cost in exchange for never paying a lock on the hit path.

DOUBLE BUFFERING IS ACCEPTED, NOT ELIMINATED

Even with its own buffer pool, PostgreSQL still reads and writes through the OS, so the same page can still sit in both the shared buffer pool and the kernel's page cache simultaneously — the "double buffering" problem from §4 is reduced, not eliminated (a cache hit in shared_buffers skips the syscall, but a miss that falls through to a page still resident in the OS cache is cheaper than a real disk read). This is exactly why effective_cache_size exists as a planner hint: it tells the query planner roughly how much total RAM (shared_buffers plus what the OS is likely caching on top of it) is probably available for caching this database's data, so index-scan cost estimates aren't pessimistically assuming every page miss hits disk.

ARC 08 · INTERNAL IMPLEMENTATION

ReadBuffer(), the state word, and the sweep

Patch-level detail on: (a) the BufferDesc struct and its packed atomic state word, (b) the full ReadBuffer() path from hash lookup to pinned page, (c) the clock-sweep algorithm itself, and (d) buffer access strategies (ring buffers) that keep large scans from evicting the working set.

(a) BufferDesc: one atomic word instead of a per-buffer spinlock

Each buffer's metadata lives in a BufferDesc — its BufferTag (identifying which relation, fork, and block number occupies this slot), a content LWLock (protecting the actual 8 KB of page data during reads/writes), and, critically, one pg_atomic_uint32 state word packing several fields that older PostgreSQL versions protected with a dedicated per-buffer spinlock. The state word bundles a refcount (how many backends currently have this buffer pinned — up to 18 bits, far more than realistic concurrent pins), a 4-bit usage_count (capped at BM_MAX_USAGE_COUNT, 5), and flag bits including BM_DIRTY, BM_VALID, BM_TAG_VALID, BM_IO_IN_PROGRESS, and BM_JUST_DIRTIED.

Cbuf_internals.h — BufferDesc, simplified
typedef struct BufferDesc
{
    BufferTag   tag;                /* relfilenode + fork + blocknum: which page */
    int         buf_id;             /* index into BufferDescriptors[]/BufferBlocks[] */

    /* One atomic word replaces the old per-buffer spinlock:
     *   bits  0..17  refcount        (pin count, up to ~262K)
     *   bits 18..21  usage_count     (0..BM_MAX_USAGE_COUNT=5)
     *   bits 22..    flags: BM_DIRTY | BM_VALID | BM_TAG_VALID |
     *                       BM_IO_IN_PROGRESS | BM_JUST_DIRTIED | ...  */
    pg_atomic_uint32 state;

    int         wait_backend_pgprocno;   /* who's waiting for our pin to clear */
    int         freeNext;                /* freelist link */
    LWLock      content_lock;       /* protects the ACTUAL page bytes, not this struct */
} BufferDesc;

The move from a per-buffer spinlock to a single atomic word matters for exactly the reason chapter 8 predicts: pinning and unpinning are the single hottest operations in the server, executed on every page touch by every backend, and a compare-and-swap on one packed word is cheaper and less contention-prone than acquiring a spinlock, mutating several separate fields, and releasing it — especially since several of those fields (bump usage_count, increment refcount) can now be updated together in one CAS instead of as sequential protected steps.

(b) ReadBuffer(): the full path from request to pinned page

THE RULE THAT MAKES CRASH RECOVERY POSSIBLE: WAL BEFORE DATA

If the victim buffer chosen for eviction is dirty, its WAL record(s) — everything up to the page's current LSN — must be flushed to durable storage before the page itself is written out. Get this order backwards even once and a crash between the data write and the WAL flush leaves a data file reflecting a change whose WAL record doesn't exist to describe it — recovery replays WAL from the last checkpoint forward and has no way to represent "undo this data-file change, I never told you about it." This single ordering rule, enforced inside FlushBuffer() on every eviction, is what makes chapter 11's crash recovery a sound reconstruction rather than a best-effort guess.

(c) Clock sweep: the circular scan with second chances

When no buffer is available from the free list, StrategyGetBuffer() advances a shared nextVictimBuffer "hand" around the buffer array (wrapping at NBuffers) and, for each candidate, applies one rule: if the buffer's usage_count is above zero, decrement it and move on — a "second chance" recording that this page has been used recently enough to deserve one more pass before eviction; if usage_count is already zero and the buffer is unpinned, it becomes the victim. A buffer touched constantly keeps getting its counter bumped back up by ordinary access faster than the hand can drain it, so it survives indefinitely; a buffer touched once and never again has its counter drained to zero on the hand's very next pass and gets reclaimed quickly.

(d) Buffer access strategies: ring buffers for bulk operations

Clock-sweep alone still lets a sufficiently large sequential scan or bulk load eventually drain every buffer's usage_count to zero as the hand keeps passing without those pages ever being revisited — the scan doesn't need to touch every buffer to cause damage, just enough of them repeatedly. PostgreSQL's defense is a buffer access strategy: an operation that knows in advance it will touch far more pages than fit productively in cache requests a small private ring of buffers — BAS_BULKREAD uses roughly 256 KB (about 32 buffers at 8 KB each), BAS_BULKWRITE and BAS_VACUUM have their own sized rings — and reuses those same few buffers in a loop for the entire scan, evicting only its own ring members instead of touching the shared pool's clock sweep at all for the bulk of its work.

Ring buffer strategy in actionSTEP-BY-STEP

One refinement matters: StrategyRejectBuffer() lets a ring give back a buffer rather than reuse it if that buffer turns out to already be a popular, high-usage_count page that happened to fall into the ring's path — the ring's whole purpose is protecting the shared pool from the scan's pages, not stealing pages the shared pool already values highly.

ARC 09 · TRADEOFFS

The same problem, five ways: comparative anatomy

Every engine that maintains its own page cache on top of the OS solves scan pollution and replacement differently — the differences map directly onto each engine's dominant workload assumptions:

SYSTEMREPLACEMENT POLICYSCAN-POLLUTION DEFENSENOTES
PostgreSQLclock-sweep (usage_count 0–5, circular hand) buffer access strategies (ring buffers) Hit path is a single atomic increment; no global list to maintain.
MySQL / InnoDBmodified LRU with a midpoint insertion point (~5/8 old sublist, ~3/8 new sublist) new pages enter mid-list, not head — must be reused within a window to reach the hot end A genuinely different solution to the identical pollution problem — insertion point, not a separate ring.
OracleLRU list + touch-count-aware placement large/full table scans placed at LRU end directly; direct-path reads bypass the cache entirely "Bypass the cache for known-bad-fit access patterns" is the same instinct as a ring buffer, applied more bluntly.
SQLitesimple LRU over a much smaller page cache limited — relies on the OS cache underneath for the bulk of caching Single-process, single-writer model means contention isn't the driving design pressure it is for PostgreSQL.
RocksDBconfigurable block cache: LRU or a clock-based ("ClockCache") implementation workload-dependent; LSM compaction reads can be routed around the cache Being an LSM engine (not in-place page updates) changes what "dirty" and "eviction" even mean.
CassandraOS page cache reliance + an off-heap row/key cache layer limited built-in defense; relies on off-heap sizing and workload isolation SSTable immutability changes the caching problem shape significantly versus in-place B-tree pages.

Read the table as convergent evolution: every engine that owns its own cache ends up defending it from large one-time scans, whether via a midpoint-insertion LRU variant, a direct bypass, or (PostgreSQL's choice) a dedicated small ring that isolates the scan's own churn from the shared pool entirely.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

  • Buffer mapping hash lookup: O(1) average, partitioned across NUM_BUFFER_PARTITIONS (128) LWLocks — a hit only ever contends with other backends hashing into the same partition, not the whole pool.
  • Pin/unpin (the hot path): O(1) — one atomic CAS on the BufferDesc state word, no lock acquisition beyond the (already-held, brief) mapping partition lock during the initial lookup.
  • Clock-sweep victim search: amortized O(1) per allocation under normal working-set behavior, but worst case O(NBuffers) if every buffer in the pool currently has a nonzero usage_count — the hand must make a full circuit decrementing everything before it can claim a victim.
  • Cache/TLB/NUMA effects at scale: a large shared_buffers means the BufferDescriptors array itself — one entry per buffer, touched on every access — spans many cache lines; a working set that doesn't fit in L2/L3 turns "hit in shared_buffers" into a real memory latency event even without touching disk. On multi-socket NUMA hardware, buffers physically allocated near one socket cost more to touch from another, the same effect chapter 1 described for the whole shared memory segment.
  • Disk access patterns: a cache miss on a random OLTP lookup is a random 8 KB read; a miss during a sequential scan benefits from OS/storage readahead the buffer manager doesn't have to orchestrate itself — one more reason double buffering with the OS cache is tolerated rather than fought.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: shared_buffers too small for the working set

A schema grows past what shared_buffers was originally sized for; the same "hot" pages that used to survive clock-sweep indefinitely now cycle in and out as the pool churns to fit a working set larger than it is. pg_stat_database shows blks_hit/blks_read ratio degrading over months as data grows, invisible until it crosses a threshold where read latency spikes system-wide. Fix: size shared_buffers against the actual working set (not total data size — the working set is what's repeatedly touched), track the hit ratio as a trending metric rather than a one-time setting, and remember that raising shared_buffers requires a restart (chapter 1) — this is not a same-day fix once discovered.

Incident 2: backend-initiated writes spike — the sign the background writer is losing

Under sustained write load, the clock sweep increasingly finds its victim candidates dirty, and if the background writer (which is supposed to dribble dirty pages out just ahead of the sweeping hand, per bgwriter_delay) hasn't kept pace, an ordinary foreground backend doing a plain read is forced to perform the eviction's write itself — flushing WAL and issuing the page write synchronously, inline, before it can even complete the read it originally wanted. This is the buffer-manager equivalent of an OOM cascade: a backend just trying to do a cheap operation gets stuck doing an expensive one because a background process fell behind. Fix: tune bgwriter_lru_maxpages/bgwriter_lru_multiplier more aggressively, watch pg_stat_bgwriter.buffers_backend vs. buffers_clean as the direct signal of who is doing the writing, and treat a rising buffers_backend share as an early-warning metric, not a curiosity.

Incident 3: an unprotected bulk scan tanks OLTP latency

Before ring-buffer strategies were applied consistently (and still today, for operations that bypass them), a large sequential scan or bulk load can push enough pages through the clock sweep that genuinely hot OLTP pages get evicted despite having been touched constantly moments before — the sweep simply cannot distinguish "touched a million times over the last hour" from "touched a million times because a scan is currently passing through" using only a 0–5 counter under sufficiently sustained pressure. Application teams see a nightly batch job or an ad-hoc analytical query correlate with an OLTP latency spike that has nothing to do with lock contention or CPU — pure cache-eviction collateral damage. Fix: confirm the operation actually uses a ring-buffer-eligible access pattern (most sequential scans and VACUUM do automatically), isolate genuinely adversarial workloads onto a replica, and treat a scheduled batch job's cache impact as a capacity question, not just a CPU/IO one.

First, the hash-lookup fast path — most buffer requests are a hit and never reach the replacement algorithm at all:

Cbufmgr.c — BufferAlloc(), the hit path, simplified
static BufferDesc *
BufferAlloc(SMgrRelation smgr, ForkNumber forkNum, BlockNumber blockNum,
             BufferAccessStrategy strategy, bool *foundPtr)
{
    BufferTag  newTag;
    INIT_BUFFERTAG(newTag, smgr->smgr_rlocator, forkNum, blockNum);

    uint32 hash = BufTableHashCode(&newTag);
    LWLock *partitionLock = BufMappingPartitionLock(hash);   /* 1 of 128 */

    LWLockAcquire(partitionLock, LW_SHARED);
    int bufId = BufTableLookup(&newTag, hash);
    if (bufId >= 0)
    {
        /* HIT. Pin it — an atomic CAS on the state word bumps
         * refcount and usage_count together, no separate lock at
         * all beyond the partition lock we're about to release.  */
        BufferDesc *buf = GetBufferDescriptor(bufId);
        bool valid = PinBuffer(buf, strategy);
        LWLockRelease(partitionLock);
        *foundPtr = true;
        return buf;
    }
    LWLockRelease(partitionLock);

    /* MISS. Must find a victim, evict it, and read the new page —
     * the expensive, rarer path. See the ReadBuffer deck in §8b.   */
    return BufferAllocMiss(smgr, forkNum, blockNum, strategy, foundPtr, &newTag, hash);
}

Next, the clock sweep itself — the algorithm that decides which buffer becomes available when a miss forces an eviction:

Cfreelist.c — StrategyGetBuffer(), the clock-sweep core, simplified
static BufferDesc *
ClockSweep(void)
{
    for (;;)
    {
        /* Advance the shared, atomically-incremented hand -
         * wraps around NBuffers, so the "clock" is circular.       */
        int victimId = pg_atomic_fetch_add_u32(&StrategyControl->nextVictimBuffer, 1) % NBuffers;
        BufferDesc *buf = GetBufferDescriptor(victimId);

        uint32 state = pg_atomic_read_u32(&buf->state);

        if (BUF_STATE_GET_REFCOUNT(state) != 0)
            continue;                       /* pinned right now — never touch it */

        if (BUF_STATE_GET_USAGECOUNT(state) != 0)
        {
            /* Second chance: decrement and keep sweeping. A page
             * touched often gets its counter bumped back up by
             * ordinary access faster than the hand can drain it.  */
            pg_atomic_fetch_sub_u32(&buf->state, BUF_USAGECOUNT_ONE);
            continue;
        }

        return buf;      /* usage_count == 0 AND unpinned: victim found */
    }
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Make the common case (a hit) touch as little shared state as possible. A hit only ever takes a shared-mode partition LWLock briefly during lookup, then pins via a lock-free atomic CAS — no exclusive lock, no list maintenance, on the single most frequent operation the buffer manager performs. 2. Make the replacement decision lazy and self-correcting, not exact. Rather than maintaining a perfectly-ordered recency list at write cost on every access, clock-sweep defers all the "which page matters more" reasoning to the rare moment a victim is actually needed, and encodes recency crudely-but-cheaply (a 4-bit counter) rather than precisely-but-expensively (list position). 3. Separate "in danger of eviction" from "currently in use." The refcount and usage_count fields answer two different questions — is this buffer safe to touch at all right now, versus has this buffer earned a reprieve — and packing both into one atomically-updated word means neither question needs its own separate lock.
