BLOCKCHAIN FUNDAMENTALS · CHAPTER 05

The Ledger:
Hash Chains & Tamper Evidence

Chapters 2 through 4 gave you a way to commit to one piece of data, a way to commit to an entire set of data in a single short digest, and a way to authorize an action so nobody can forge it in your name. None of that says anything about history — whether the fact you're looking at now is the same fact that was true yesterday, or whether it quietly changed. This chapter builds history: it links records by hash so that altering any one of them is detectable by anyone holding a later hash, and it is relentlessly precise about the difference between detectable and prevented — a distinction the rest of this course depends on.

ARC 01 · THE PROBLEM

Three primitives, and still no history

Take stock of what you can already build. A cryptographic hash function (chapter 2) lets you commit to one piece of data with a short fingerprint nobody can forge or invert. A Merkle tree (chapter 3) lets you commit to an entire set of data — millions of records — in one hash, with logarithmic proofs of membership. A digital signature (chapter 4) lets a key holder authorize a specific action so nobody else can forge it, and anyone can verify who authorized what. That is commitment, aggregation, and authorization. None of the three says anything about time and order — whether the thing you authorized five minutes ago is still the last word, or whether it has since been quietly replaced by something else claiming the same identity.

That gap is not new. Long before computers, bookkeepers solved a version of it with the double-entry ledger: a ledger is not a snapshot of balances, it is an ordered, append-only record of transactions from which balances are derived by replay. An auditor doesn't trust a stated balance; they trust a balance they can recompute themselves from an unbroken transaction history, because a history is much harder to fabricate consistently than a single number is to overwrite. This distinction has a name in software architecture too, and it is worth stating precisely because the rest of this course rests on it:

  • State-based systems store current values and overwrite them in place. A row in an ordinary relational table — UPDATE accounts SET balance = balance - 10 WHERE id = 42 — has no memory of what the balance was a moment ago unless something else (a separate audit table, a write-ahead log) chose to keep it. This is the default shape of nearly every database you have ever operated.
  • Transaction-based (event-sourced) systems store the sequence of operations and derive current state by folding over that sequence — replaying every debit and credit from the beginning, or from the last trusted checkpoint. Nothing is ever overwritten; corrections are new entries that reference what they correct. Double-entry bookkeeping has worked this way since the 14th century, for exactly the reason a modern architect would give: an event log is auditable in a way a mutable balance is not.

A blockchain is a transaction-based ledger with periodically derived state — a fact this chapter will make concrete and chapter 13 will formalize as the UTXO and account models. But being transaction-based buys you nothing on its own unless the log itself resists silent editing. So state the actual technical problem this chapter solves:

THE PRECISE REQUIREMENT

Given a growing sequence of records, make it so that any modification to any past record — changing it, deleting it, reordering it, or inserting a fabricated one — is detectable by a verifier who remembers only a small, fixed amount of information, not the entire history. Four sub-requirements fall out of that sentence: the structure must be append-only (writes add, never edit in place); it must be order-preserving (the sequence itself is part of what's being committed to); it must be tamper-evident with O(1) trusted state, not O(n); and it must be independently verifiable by anyone holding a copy of the data, without asking the data's custodian to vouch for it.

Everything from here to the end of the course is either building toward satisfying that requirement or dealing with the consequences of having satisfied it. Consensus (chapter 6) exists because once you have a structure worth agreeing on, mutually distrusting parties need a protocol to agree on which one. Proof of work (chapters 7–8) exists because a hash chain by itself, as you're about to see, detects tampering without preventing it — and preventing it turns out to require making history expensive to rewrite, not just expensive to check.

ARC 02 · HISTORICAL CONTEXT

1991: solving timestamping before anyone said "blockchain"

The mechanism this chapter derives is not a Satoshi Nakamoto invention. It was solved, in essentially its modern form, seventeen years before the Bitcoin whitepaper, by two researchers at Bellcore — Stuart Haber and W. Scott Stornetta — working on a problem with no cryptocurrency in sight: how do you prove a document existed at a given time, and that it has not been altered since, when the only party who can vouch for either fact is whoever is holding the document — the exact party with every incentive to lie about both? DEEP CONTEXT · TIMESTAMPING WITHOUT A TRUSTED PARTY

Haber and Stornetta's 1991 protocol is more subtle than "hash the document with a timestamp." Each new client's certificate incorporates hash-based links to the certificates of other, unrelated recent clients — strangers who happened to request a timestamp around the same time. The effect: the timestamping service itself does not hold enough of the chain to quietly rewrite it, because doing so would make its records disagree with the private copies held by every other client who was linked in. It is a decentralization idea from 1991, built entirely from hash pointers, with no proof-of-work, no token, and no network consensus protocol — just the observation that many mutually indifferent strangers, each holding a small independent fragment of the truth, are collectively very hard to fool.

ARC 03 · NAIVE SOLUTION

Attempt #1: a sequence number and an independent hash per record

Derive this honestly, the way an engineer meeting the problem cold would. You have an append-only store — a file, a table, a log. Give every record a monotonic index, a timestamp, its data, and a hash of its own contents so a reader can check that the row hasn't been corrupted in transit.

Pythonnaive_ledger.py — the strawman, annotated
import hashlib, time, json

class Record:
    def __init__(self, index, data):
        self.index = index
        self.ts = int(time.time())
        self.data = data
        # hash covers ONLY this row's own fields
        self.hash = self._compute_hash()

    def _compute_hash(self):
        payload = json.dumps({"index": self.index, "ts": self.ts, "data": self.data})
        return hashlib.sha256(payload.encode()).hexdigest()

    def verify_self(self):
        # does the stored hash match THIS row's current content?
        return self.hash == self._compute_hash()

ledger = []
ledger.append(Record(0, "alice opens account, balance 100"))
ledger.append(Record(1, "alice pays bob 10"))
ledger.append(Record(2, "bob pays carol 4"))
# each record verifies independently — nothing here looks at ANY other record

This is not a strawman built to be laughed at — it already gets something real right. If I hand you record #1 and its stored hash, you can independently confirm the two match: nobody can hand you a corrupted copy of record #1 (mangled in transit, or partially overwritten by a disk fault) without you noticing, because the hash is a commitment to that record's exact bytes (chapter 2). What it does not do is connect record #1 to record #0 or record #2 in any way. Verification is entirely local to a row. That gap is about to matter a great deal.

ARC 04 · WHY IT FAILS

Local integrity is not history integrity

Suppose whoever controls this store — the operator, or an attacker who has obtained write access — wants to change record #1 from "alice pays bob 10" to "alice pays bob 10,000". They edit the data field and call _compute_hash() again. The new hash matches the new content perfectly, because that is exactly what a hash of a record's own fields does — it describes whatever is currently there, with no memory of what used to be there. Every verifier who checks "does this row's hash match this row's bytes" gets a clean green light. There is no cascading effect on record #0 or record #2, no visible trace, and critically, no cost beyond the price of one hash computation you were always going to pay anyway.

Try it yourself. Edit any row below — the hash recomputes live, in your browser, using a real SHA-256 implementation, not a placeholder — and watch that "valid" never turns red, no matter what you write:

The naive ledger, tamperable liveEDIT ANY ROW

Every row's own hash always matches its own content, because that's the only thing it was ever a commitment to. "Valid" here means precisely nothing about history — only that the bytes haven't been corrupted since the hash was last taken.

Quantify the actual gap. To catch a single-record tamper with this structure, a verifier needs to have separately and previously recorded that specific record's correct hash, out of band, before the tamper happened — comparing today's hash against yesterday's independently-kept copy. Protecting a history of n independently-hashed records this way means an external party must have independently retained n hashes ahead of time, one per record. That is exactly Haber and Stornetta's starting complaint in their 1991 paper, restated as an engineering cost: the naive scheme needs O(n) units of externally-trusted state to guard n records. The goal — restated from §1 — is O(1): remember one small thing, catch a tamper anywhere.

THE NUMBERS

A history of 10 million independently-hashed records offers zero resistance to a single-record edit unless some other party independently recorded and retained 10 million hashes beforehand — which is not a ledger design, it's just moving the entire trust problem to whoever holds that side-channel. The fix, coming up next, gets that number from 10,000,000 down to 1.

ARC 05 · THE HASH CHAIN

Make each record's hash depend on the one before it

The fix is almost embarrassingly small once you see it, which is usually the sign of a good primitive. Don't hash a record in isolation. Hash it together with the hash of the record immediately before it:

Hi = SHA-256( Hi−1 ‖ recordi )

Record i's own hash is now a function of literally everything that came before it, transitively, all the way back to record 0 — because Hi−1 is itself a function of Hi−2, which is a function of Hi−3, and so on. Changing anything, anywhere in history, changes every hash from that point forward, including the very last one. Formalize what you just built: this is Haber and Stornetta's 1991 linked timestamping, reduced to its essence. Verifying the entire chain — all n records — now requires exactly one remembered value: the final tip hash (or the genesis hash, if you'd rather walk forward from a known start and don't yet trust anyone's claimed tip). Any single-record edit anywhere in the history changes the tip. No proof-of-work, no network, no signatures were needed to get this property — it's pure function composition over a one-way hash.

ARC 06 · WHY THAT STILL ISN'T ENOUGH

Tamper-evident to whom? The recomputation problem

Look carefully at who is able to produce that reassuring tip hash in the first place: whoever controls the storage of the entire chain. If that party — an operator, an attacker who has since gained full write access, or simply the sole custodian of the only copy — decides to alter record 42, nothing about the hash chain stops them from also recomputing H43, H44, … all the way to the current tip, and handing out the new tip as if it had always been that value. SHA-256 is fast: a single modern CPU core computes tens of millions of small-message hashes per second without any special hardware support. Recomputing a chain suffix of even a million blocks is a sub-second operation. You'll measure this yourself, on your own machine, in §8 and again in §15 — these are not claimed numbers, they're numbers your browser will produce.

State this plainly, because it is the single most over-claimed idea in this entire field, and every later chapter depends on you not believing the sloppy version:

SAY THIS OUT LOUD, THEN DO NOT FORGET IT

A hash chain gives you a way to check a claimed history against a reference value — it does not give you a way to stop the party who produces both the claim and the reference from rewriting both, consistently, in the time it takes to run a loop. Tamper evidence means: if someone else remembers the true tip, they will catch you. Tamper resistance means: rewriting is not just detectable, it is costly, even for the party who holds every byte of the data. Hash-linking alone buys you the first. It buys you none of the second. Anyone who tells you a hash chain — on its own — makes data "immutable" has skipped this paragraph.

Haber and Stornetta's actual answer to this — in 1991, decades before proof-of-work existed — was social and distributional, not economic: make the tip hard to rewrite unnoticed by ensuring many independent, mutually indifferent parties each hold a piece of the truth.

  • Linked timestamping across strangers (1991): as described in §2, each new certificate embeds hashes from other clients' recent, unrelated certificates. No single client — not even the timestamping service itself — holds a version of history that isn't cross-checked by dozens of others.
  • Publish the tip somewhere expensive to quietly alter (Surety, 1995): once a week, hash the entire linking database down to one digest and print it in the classified advertisements of the Sunday New York Times. Altering millions of already-printed newspapers, sitting in millions of homes and library archives, is not a hash-cracking problem — it's a logistics problem so absurd it functions as a security guarantee.

Both strategies are witnessing strategies: get many independent parties to remember the tip, so that no single party's local rewrite goes unnoticed. Neither one makes rewriting computationally expensive — they make it socially and logistically implausible to do without getting caught by someone who kept a copy.

WHERE CHAPTERS 7–8 GO NEXT

Proof-of-work introduces a third strategy that needs no witnesses at all: make producing each valid block require real, unavoidable, externally-verifiable resource expenditure, so that even a party with zero outside observers cannot cheaply produce an alternative chain that looks as "expensive" as the honest one. That is the actual origin of the sentence you will hear forever after — "the blockchain is immutable" — and you should now be permanently suspicious of it. It is not immutable in the mathematical sense: anyone holding the full dataset can trivially recompute it, exactly as you just watched happen. What proof-of-work buys is that rewriting costs real, external, unavoidable resources, and out-competing the honest chain requires more of those resources than everyone else combined holds. Immutability, in every blockchain you will ever operate, is an economic property enforced by cost — not a mathematical property enforced by impossibility. You will see this sentence again, deliberately, more than once.

WHY THE HEADER/BODY SPLIT EXISTS AT ALL

Notice that "block header" and "block body" are separate cards, hashed and chained separately. The header is small — a few dozen bytes — and contains a Merkle root (chapter 3) that commits to the potentially huge body without needing the body present. This is exactly what makes SPV (simplified payment verification, ch3) possible: a lightweight client can hold and verify an entire chain of headers — proving order and tamper-evidence for the whole history — while asking a full node for only the specific Merkle proofs it needs, on demand, instead of downloading every transaction ever made.

(a) The block header — the part that gets chained

This is Bitcoin's actual 80-byte header layout — a real, widely deployed artifact, not a teaching simplification — because it is the cleanest illustration of which fields exist purely to satisfy this chapter's requirement versus which ones won't matter until chapters 7–8:

Three of these six fields — prevBlockHash, merkleRoot, and, loosely, time — are exactly what this chapter's requirement needs: an unbroken pointer to predecessor, a commitment to contents, an ordering signal. The other three don't do anything for tamper evidence at all; they exist purely to make producing a valid header expensive, which is a different problem this chapter has deliberately not solved yet.

GENESIS: THE ONE BLOCK NOTHING POINTS BACKWARD FROM

Block 0 has no predecessor, so its prevBlockHash field is, by convention, 32 zero bytes. That means the genesis block's own validity cannot be established by this chapter's mechanism at all — there is nothing for it to chain against. Its hash must instead be trusted out-of-band, distributed with the client software itself. Bitcoin's real genesis block hash — 000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f — is hardcoded directly into every implementation's source. It is, quite literally, the practical instantiation of the "witness" idea from §6, reduced to a single universally-distributed constant: everyone who runs the software has independently agreed, out of band, on where history begins.

ARC 09 · TRADEOFFS

The same idea, reinvented independently, at least six times

Hash-chained, append-only structures are one of the most widely reinvented shapes in systems software — which is a good sign for a primitive; it means many independent groups hit the same requirement and converged on the same answer. Read the last row carefully: a database's write-ahead log is checksummed and strictly sequential, but it is not cryptographically hash-chained the way the others are — each record's checksum protects against accidental corruption, not against a party with legitimate write access who wants to make a deliberate, self-consistent edit. That's a reasonable choice for a WAL, whose threat model is disk and power failures, not a malicious database administrator — but it is precisely the gap this chapter's mechanism closes when the threat model changes to "don't trust the custodian at all."

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What rewriting costs, with and without proof-of-work

Verifying a chain of n blocks from genesis is O(n) hash operations — one recomputation and one comparison per header, as walked through in §8(b). That is also, unavoidably, exactly the cost of rewriting a suffix of the chain, which is the uncomfortable symmetry at the heart of §6: whatever makes verification cheap makes forgery cheap too, for anyone who already has write access to the data.

  • Plain hash chain, no proof-of-work: cost to rewrite the last k blocks ≈ k × (time to compute one SHA-256 hash). At the throughput you measured in §8(c) — tens of millions of hashes per second per core — rewriting a thousand blocks costs a rounding error of CPU time.
  • Chain secured by proof-of-work (preview of ch7–8): cost to rewrite the last k blocks ≈ k × (expected number of hash attempts to satisfy the current difficulty target) — and that expected attempt count is deliberately tuned, network-wide, to represent a large, real amount of computation and electricity per block. Chapter 8 derives the exact math, including why an attacker's odds of catching up shrink exponentially with each additional confirmation once they're behind — but the shape you need now is just this: difficulty turns "k multiplications by a hash's cost" into "k multiplications by a deliberately expensive cost," and that's the entire mechanism by which economic security gets attached to a structure that, on its own, offers none.

ARC 11 · REAL-WORLD INCIDENTS

Three times this exact mechanism mattered in production

Incident 1: Certificate Transparency catches Symantec (2015–2017)

Certificate Authorities occasionally issue TLS certificates they shouldn't — for domains they don't control, or as improperly-scoped test certificates. Because Certificate Transparency (RFC 6962, §9's table) requires every publicly trusted certificate to be logged in an append-only, hash-chained Merkle structure that anyone can audit, independent monitors were able to prove, from the public logs, that Symantec-affiliated CAs had issued certificates — including test certificates for domains they had no authorization over — without the issuance ever being disclosed by Symantec itself. Google's response, phased through Chrome over 2017–2018, was a gradual distrust of Symantec-issued certificates, and Symantec's CA business was subsequently sold to DigiCert. Root cause, in this chapter's terms: CT did not stop the mis-issuance — it made mis-issuance provable after the fact to parties who had no prior relationship with the CA at all. That is tamper evidence, exactly as defined in §6, operating on a real, non-cryptocurrency system.

Incident 2: the 2011 kernel.org compromise

In August 2011, attackers gained root access to several servers hosting the Linux kernel's official Git repositories, using stolen developer credentials. The operational nightmare this raises is obvious: if attackers have root on the machine holding your source history, how do you know they didn't insert a backdoored commit? The answer the kernel team relied on is exactly this chapter's mechanism: Git's object store is a hash-chained Merkle DAG — every commit's identifier is a hash that includes its parent commit's hash and the hash of its entire file tree (chapter 3's structure, applied to source code instead of transactions). Thousands of developers around the world held independent clones of the same history. Comparing the compromised servers' commit hashes against those independently-held copies — the exact "many witnesses" pattern from §6 — let the team confirm, quickly and without re-auditing every line of code by hand, that no commit reachable from any known-good tag had been altered. The credential-theft root cause was unrelated to cryptography; what this chapter's mechanism bought was fast, high-confidence forensics afterward.

Incident 3: Bitcoin Gold's 51% double-spends (May 2018, repeated January 2020)

This is the incident that makes §6's central claim impossible to dismiss as academic. Bitcoin Gold's total network hash rate was low enough, relative to hash power rentable on the open market, that an attacker could rent enough compute to briefly exceed the honest network's rate for that specific chain. In May 2018 the attacker used that temporary majority to rewrite several already-confirmed blocks, double-spending deposits at exchanges before the reorganization was noticed — losses were reported on the order of $18 million. A smaller repeat attack followed in January 2020. Root cause, stated in this chapter's exact vocabulary: Bitcoin Gold's chain was never mathematically immutable — it was economically expensive to rewrite, and for a period, the price of doing so became affordable relative to the loot. Chapter 8 derives the 51% threshold and the exponential decay of reorg probability with confirmation depth that this incident violated; file this away as the concrete, dollar-denominated proof that "immutability is economic, not mathematical" is not a rhetorical flourish — it is a risk you can price, and in this case, someone did.

Pythonhashutil.py — why we hash twice
import hashlib

def sha256d(data: bytes) -> bytes:
    # Bitcoin's actual choice: hash the hash. A single SHA-256 pass built on
    # the Merkle-Damgard construction (chapter 2) is vulnerable to length-
    # extension: given H(m), an attacker can compute H(m || pad || suffix)
    # WITHOUT knowing m. Hashing again collapses that structure — the
    # output of the inner hash is fixed-size and opaque, so there is no
    # internal state left to extend.
    return hashlib.sha256(hashlib.sha256(data).digest()).digest()
Pythonblock.py — canonical serialization matters as much as the hash
from dataclasses import dataclass
from hashutil import sha256d

@dataclass
class Block:
    index: int
    timestamp: int
    merkle_root: bytes      # from chapter 3, over this block's transactions
    prev_hash: bytes        # the H(i-1) from Section 5 — 32 zero bytes for genesis

    def serialize_header(self) -> bytes:
        # FIXED-WIDTH, FIXED-ORDER fields. This is not a style preference —
        # an ambiguous serialization (e.g. delimiter-joined variable-length
        # strings) can let two DIFFERENT logical headers produce IDENTICAL
        # bytes, which breaks the hash's guarantee not by attacking SHA-256
        # but by attacking the encoding around it.
        return (
            self.index.to_bytes(4, "big") +
            self.timestamp.to_bytes(4, "big") +
            self.merkle_root +
            self.prev_hash
        )

    def compute_hash(self) -> bytes:
        return sha256d(self.serialize_header())
Pythonchain.py — the §8(b) algorithm, made executable
class Chain:
    def __init__(self, genesis_hash: bytes):
        # the one value that CANNOT be validated by this chapter's mechanism —
        # trusted out-of-band, exactly like Bitcoin's hardcoded genesis hash
        self.trusted_genesis_hash = genesis_hash
        self.blocks: list[Block] = []

    def append(self, block: Block):
        expected_prev = (self.blocks[-1].compute_hash()
                         if self.blocks else self.trusted_genesis_hash)
        if block.prev_hash != expected_prev:
            raise ValueError(f"block {block.index}: prev_hash does not match — reject")
        self.blocks.append(block)

    def validate(self) -> bool:
        prev = self.trusted_genesis_hash
        for b in self.blocks:
            if b.prev_hash != prev:
                return False          # break found — everything from here is untrusted
            prev = b.compute_hash()
        return True

    def tip_hash(self) -> bytes:
        return self.blocks[-1].compute_hash() if self.blocks else self.trusted_genesis_hash
FOUR CHOICES WORTH STEALING

1. Header/body split. Hashing a small, fixed-shape header separately from a potentially huge body (via a Merkle root) makes header-only verification cheap and enables SPV — you don't have to reimplement this to benefit from having understood why it exists. 2. Double-hashing. One extra SHA-256 pass closes a real structural weakness (length-extension) for the cost of one more hash — cheap insurance. 3. Hardcoded genesis. Every chain has exactly one block whose validity this chapter's mechanism cannot establish; making that fact explicit, rather than pretending genesis is "just block 0," is more honest engineering. 4. Canonical, fixed-width serialization. The moment two different objects can serialize to the same bytes, your hash is no longer a commitment to the object — it's a commitment to an encoding that happens to collide. This bug class has nothing to do with SHA-256's cryptographic strength and everything to do with sloppy framing.
