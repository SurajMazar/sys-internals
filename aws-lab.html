STEP 01 · READ THIS BEFORE YOU CREATE ANYTHING

This lab spends real money. Here is how you get it all back to zero.

Every other course on this site simulates. This lab does not — every command below, if you run it, creates or costs something in your actual AWS account. Almost everything here fits inside the AWS Free Tier if you tear it down within a day or two, but "almost" is the operative word, and one component (a NAT Gateway) is never free regardless of tier. Bookmark this section — the floating ⚠ Teardown checklist button in the bottom-right corner of every page in this lab jumps back here instantly.

THE THREE RULES OF THIS LAB

1. Do exercises 1 and 2 first, always — the Budget alert and billing alarm are your safety net, not optional extras. Set them up before you touch EC2, DynamoDB, or the VPC exercise.

2. Tear down in the order below, not the order you created things — AWS enforces dependency order (you cannot delete a VPC while a subnet, NAT Gateway, or Internet Gateway still lives inside it), and this checklist is already sequenced to respect it.

3. Check every region you touched. EC2, NAT Gateways, and VPCs are billed per-region. The single most common source of a surprise AWS bill is a resource left running in a region you forgot you switched to. Run aws ec2 describe-instances --query "Reservations[].Instances[].{ID:InstanceId,State:State.Name}" --region <region> against every region you used, not just your default one.

IF YOU ONLY DO ONE THING BEFORE CLOSING THIS TAB

Terminate any EC2 instance and delete any NAT Gateway you created. EC2 outside the free tier's 750 monthly t2.micro/t3.micro hours and a running NAT Gateway are the two items in this lab capable of running up real charges hour by hour, unattended, indefinitely.

STEP 02 · SETUP

A real account, the CLI, and an identity that isn't your root user

You need an AWS account with a valid payment method on file (required even for Free Tier usage), AWS CLI v2 installed, and — this matters for exercise 3 later — an IAM identity to run commands as that is not your account's root user.

Install AWS CLI v2

curl "https://awscli.amazonaws.com/AWSCLIV2.pkg" -o "AWSCLIV2.pkg"
sudo installer -pkg AWSCLIV2.pkg -target /
aws --version

curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip
sudo ./aws/install
aws --version
powershellWindows

aws --version
EXPECTED
aws-cli/2.x.x Python/3.x.x darwin/arm64 exe/x86_64

Create an IAM identity for this lab — never use root access keys

The root user can create IAM users, so use it exactly once, from the console, to create an administrative IAM user for everything else in this lab. Root access keys are a standing exam trap for a reason: a leaked root key cannot be scoped down, only deleted.

bashrun as root, once, then never again
aws iam create-user --user-name lab-admin
aws iam attach-user-policy --user-name lab-admin \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess
aws iam create-access-key --user-name lab-admin

Save the AccessKeyId and SecretAccessKey from that last command's output — AWS shows the secret exactly once. Configure a named profile with them and use that profile for the rest of this lab:

bash
aws configure --profile lab-admin
# AWS Access Key ID: AKIA...
# AWS Secret Access Key: ...
# Default region name: us-east-1
# Default output format: json

export AWS_PROFILE=lab-admin
aws sts get-caller-identity
EXPECTED — confirms you're lab-admin, not root
{
    "UserId": "AIDA....",
    "Account": "<your 12-digit account ID>",
    "Arn": "arn:aws:iam::<account-id>:user/lab-admin"
}

Every command in this lab assumes AWS_PROFILE=lab-admin is exported in your shell, and that us-east-1 is your default region — the billing exercises specifically require us-east-1 regardless of where you run everything else, since AWS billing metrics and alarms are only published there.

Enable MFA on the root user

This step has no CLI equivalent — it's a one-time console action (IAM → Users → root → Security credentials → Assign MFA device) but belongs here because it's the single highest-leverage security step in the entire lab: root can bypass every IAM policy you write for the rest of these exercises.

Note your account ID — you'll need it constantly

bash
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
echo $ACCOUNT_ID
