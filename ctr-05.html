CONTAINER INTERNALS · CHAPTER 05

cgroups v2:
The Unified Resource Hierarchy

Chapters 2 through 4 gave a containerized process a private view of the machine — its own PID tree, its own network stack, its own root-mapped identity. None of that stops it from allocating every byte of RAM, pegging every core, forking until the process table is exhausted, or saturating the disk queue for everyone else on the box. Namespaces answer what can this process see and touch. This chapter answers the orthogonal question: how much of the shared machine can it actually take — and shows you the exact files, the exact kernel paths, and the exact failure modes of the mechanism that enforces the answer: cgroups v2.

ARC 01 · THE PROBLEM

One host, many tenants, one finite machine

A container process that has been through chapters 2–4 is thoroughly isolated: its own PID namespace hides every other process, its own network namespace hides every other socket, and — if it's rootless — its "root" is a fiction that maps to an unprivileged host UID. None of that isolation puts a ceiling on anything. That same process can still malloc() until the host's RAM is gone, spin a tight loop across every core, fork() in a loop until the kernel's task table is full, or issue enough write() calls to saturate the block device's queue. Every other tenant on that host — other containers, the host's own daemons, the orchestrator's own agent — shares that same finite CPU, RAM, PID space, and I/O bandwidth. Isolation of view says nothing about isolation of consumption.

That is a different kind of problem from anything namespaces solve, and it pulls in four directions that any correct mechanism has to satisfy simultaneously:

  • Hierarchical grouping. A container is rarely one process — an entrypoint script, its children, maybe a sidecar — and you want to cap that whole cooperating group as a single accounting unit, not hand-track individual PIDs that come and go.
  • Multiple, unrelated resources. CPU time, resident memory, task count, and block I/O bandwidth are metered by four different kernel subsystems — the scheduler, the page allocator and reclaim path, the PID allocator, and the block layer's request queue. A general solution has to plug into all four without becoming four unrelated, inconsistent mechanisms.
  • Live observability. An operator — or an orchestrator's autoscaler — needs to read current usage in real time, and needs to know not just that a limit exists but how many times and how severely it has actually bitten.
  • Enforcement, not advice. A limit a process can quietly ignore isn't a limit. The kernel has to be able to say no — atomically, at the exact page-fault or scheduling decision where the resource is claimed.
A DIFFERENT AXIS FROM CHAPTERS 2–4

Chapter 4 closed by drawing a line: user namespaces answer who is allowed to do what; this chapter's mechanism answers how much of the machine can they do it with. Those two axes are deliberately orthogonal — a process can be a fully unprivileged, rootless, mapped-root process and still be capped at 256 MB of RAM; a fully privileged host-root daemon can be capped exactly the same way. Conflating identity isolation with resource isolation is a design smell — the kernel keeps them as separate subsystems on purpose, and this course teaches them as separate chapters for the same reason.

ARC 02 · HISTORICAL CONTEXT

2006: Google's scheduling problem becomes a kernel feature

Long before "containers" were a product category, Google ran many unrelated jobs on shared machines and needed the kernel itself to stop one job from starving another. In 2006, Google engineers Paul Menage and Rohit Seth submitted a patch series called "process containers" — Paul Jackson objected that "container" was already overloaded in the kernel, and the mechanism was renamed control groups, or cgroups, before merge. What shipped in 2008 solved the resource-limiting half of the problem this course has been building toward since chapter 1 — and, like cgroups v1's eventual successor, it took a decade of production scars to get the hierarchy design right. DEEP CONTEXT · SYSTEMD'S PARALLEL DISCOVERY

Around the same years cgroups were maturing, systemd independently needed a reliable way to track "every process belonging to this service, however many times it forked" — /proc alone can't answer that once a daemon double-forks and reparents to PID 1. systemd adopted cgroups as its own bookkeeping substrate, organizing every unit into system.slice, user.slice, and (for VMs and containers) machine.slice. That choice is why, decades later, Docker and Podman both have to decide whether to manage cgroups directly (cgroupfs) or hand the job to systemd (systemd driver) — §9 makes that decision concrete, and it's the same delegation mechanism chapter 4 promised you for rootless resource limits.

ARC 03 · NAIVE SOLUTION

Attempt #1: the POSIX toolkit you already have

Before reaching for a kernel subsystem, derive the naive answer honestly: Unix already ships resource controls. nice(2)/setpriority(2) adjust CPU scheduling priority. setrlimit(2) caps a process's address space, open file count, or number of children. ionice(1) adjusts block I/O priority. None of this requires a single kernel patch — it's been there since the 1980s–90s. Here is the strawman: cap a container's memory the way any sysadmin would have in 1995.

Cnaive_limits.c — the strawman, annotated
void launch_contained(char *const argv[])
{
    struct rlimit mem_limit = { .rlim_cur = 256*1024*1024, .rlim_max = 256*1024*1024 };
    struct rlimit proc_limit = { .rlim_cur = 64, .rlim_max = 64 };

    pid_t pid = fork();
    if (pid == 0) {
        setrlimit(RLIMIT_AS,    &mem_limit);   /* cap virtual address space   */
        setrlimit(RLIMIT_NPROC, &proc_limit);  /* cap this real UID's tasks   */
        setpriority(PRIO_PROCESS, 0, 10);   /* deprioritize CPU scheduling */
        execv(argv[0], argv);
    }
    /* parent just waits */
}

This is not a joke — it already gets something right: it requires zero new kernel infrastructure, it works on every Unix built in the last three decades, and for a single, well-behaved process it does exactly what its name says. RLIMIT_AS genuinely stops one process from mapping more than 256 MB; nice genuinely lowers one process's claim on the CPU scheduler relative to its peers. The strawman fails the moment the workload is a group of cooperating processes rather than one — which is precisely what a container is.

ARC 04 · WHY IT FAILS

The POSIX toolkit was never designed for groups

Every one of the naive mechanisms shares the same structural flaw: it attaches to a single process (or a single real UID), not to a group that can grow, shrink, and reparent unpredictably — exactly what a container's process tree does. Walk through each one quantitatively:

  • RLIMIT_AS doesn't survive fork() composing. The limit is per-process. A process capped at 256 MB that forks 10 children, each also capped at 256 MB by inheritance, can collectively map 2.56 GB — the kernel enforces each process's own ceiling faithfully and has no concept of their sum. A build container spawning a compiler per translation unit blows through any "per-container" budget in the time it takes to spawn its second worker.
  • RLIMIT_NPROC is scoped to a real UID, not a workload. Two containers sharing a subuid range (routine under rootless delegation, chapter 4) share one counter — container A's fork bomb starves container B's legitimate process creation, because the kernel is counting "tasks owned by UID 100000," not "tasks belonging to this container."
  • nice/setpriority set a relative weight, not a ceiling. On an otherwise idle 8-core box, a process niced to the bottom of the scale can still claim up to 100% of a core — niceness only changes what happens under contention, it never says "never more than 25%, even if you're the only runnable thing." That "hard ceiling regardless of contention" guarantee is precisely what a noisy neighbor needs capped, and POSIX has no primitive for it.
  • There is no I/O primitive at all. Classic POSIX has no rlimit for block-device bandwidth. One container's sequential write can drive the request queue's latency for every other tenant's random reads into the tens of milliseconds — measurable in iostat, uncappable with anything in this toolkit.
  • No atomic, group-level observability. "How much memory is container X using right now" means walking every PID under it (which requires already knowing them all, races with forks), reading /proc/[pid]/status for each, and summing by hand — with no guarantee the set of PIDs didn't change mid-sum.
THE NUMBERS

A 4-core host running four containers each "capped" at one core's worth of niceness has no way to stop a fifth, misbehaving container from bursting to 400% CPU the instant the other four go idle for even one scheduler tick — and no way to observe, after the fact, how many tick-periods that happened in. The primitives exist per-process; the workload is per-group. Something has to sit above the process and account for the group as a first-class kernel object.

ARC 05 · BETTER SOLUTION

Groups as directories, limits as files

The fix Google shipped — and the kernel eventually converged on as cgroups v2 — reuses an instinct you've already seen in chapter 2's /proc/<pid>/uid_map: instead of a new syscall for every resource, represent the group as a directory in a special filesystem (cgroupfs, mounted at /sys/fs/cgroup), and represent every operation — creating the group, adding a process, reading usage, setting a limit — as an ordinary open()/read()/write() on a plain file inside it. Membership is a list of PIDs in one file; a hard memory ceiling is a number in another file. There is no new syscall family to learn — there is a directory tree to navigate.

WHY FILES, NOT SYSCALLS

This is a deliberate, load-bearing choice. Files compose with everything Unix already has: shell scripts, cat, inotify/poll() for change notification, standard file permissions for delegation (§9 and §11 both hinge on exactly this). Adding a new resource controller means adding new files in an existing directory, not a new syscall number that every language runtime needs new bindings for. §13 shows the one deliberate exception to "everything is a file" — and the race it was built to close.

ARC 06 · WHY THAT STILL HURTS

v1 built the right idea on the wrong hierarchy

Cgroups existed from 2008, but the mechanism you just walked through — one unified tree — is not what shipped first. cgroups v1 mounted each controller as its own, independent hierarchy: /sys/fs/cgroup/memory, /sys/fs/cgroup/cpu,cpuacct, /sys/fs/cgroup/blkio, /sys/fs/cgroup/pids, /sys/fs/cgroup/freezer, /sys/fs/cgroup/devices, and half a dozen more — each with its own directory tree, and nothing requiring a process's position in one tree to have any relationship to its position in another.

  • No unified view of a container's footprint. A process could be grouped under memory/docker/<id> for memory accounting and under a completely different grouping — say, a systemd-managed cpu/system.slice/... — for CPU. Asking "what does this container actually cost, total" meant cross-referencing PIDs across N independent trees by hand.
  • Hierarchy ownership fights. systemd wanted the whole tree for its own service bookkeeping; Docker's early cgroup driver wanted to write directly into cgroupfs. Two managers mutating the same mount point produces exactly the class of bug you'd expect: units disappearing from systemd's view, or containers whose limits silently stop applying after a systemd daemon-reload.
  • A live footgun: release_agent. Each v1 hierarchy supported notify_on_release: when a cgroup became empty, the kernel would execute the path written in that hierarchy's release_agent file — with full kernel privilege, in the initial namespace, regardless of which container asked for it. That single writable file is the root cause of a real CVE this chapter revisits in §11 with full detail.
THE INDUSTRY DID NOT WAIT FOR A CLEAN FIX

Kubernetes, Docker, and every cgroup-aware tool of the 2010s shipped workarounds: co-mounting controllers that were "usually" managed together, conventions for where container engines vs. systemd were "allowed" to write, and operational runbooks for the day the two disagreed. None of that fixed the underlying design — it made the multi-hierarchy model survivable, the same way connection poolers make PostgreSQL's process-per-connection cost survivable rather than eliminating it. The actual fix required redesigning the tree itself.

ARC 07 · FINAL ARCHITECTURE

One tree, delegated top-down

cgroups v2 replaces N independent hierarchies with exactly one: every controller — memory, cpu, pids, io, and others — lives in the same directory tree, and every process belongs to exactly one cgroup, full stop. Controllers aren't implicitly everywhere; a parent cgroup must explicitly delegate a controller down to its children by writing to cgroup.subtree_control, which is also precisely the mechanism systemd uses to hand a slice of the tree to an unprivileged user session (chapter 4's rootless delegation promise) or to Docker/Podman's own cgroup driver. DOCKER AND PODMAN WRITE THE SAME FILES

Neither engine invents its own resource-limit mechanism. A docker run --memory=256m and a podman run --memory=256m both terminate in the identical kernel act: a write of 268435456 to some leaf cgroup's memory.max. This is a kernel contract, not an engine feature — where the two genuinely differ is which path they write to and who created it (§9), not what the file means once written.

ARC 08 · INTERNAL IMPLEMENTATION

Enforcement, byte by byte and microsecond by microsecond

"Files, not syscalls" describes the interface. The enforcement underneath is not file I/O at all — it fires inside the hottest paths in the kernel: the page-fault handler and the CPU scheduler. Three mechanisms, in the order you'll actually hit them.

(a) Memory: charged on every page fault, not polled

memory.max is not a periodic check — the memory controller (memcg) charges every page a process in the cgroup touches, at the moment of the page fault, via an internal function conventionally called try_charge(). If the charge would push the cgroup's counter past memory.max, the kernel first attempts reclaim scoped to that cgroup — evicting clean, reclaimable pages (page cache) that belong to processes in the same group. Only when reclaim can't free enough does the cgroup's own, cgroup-scoped OOM killer fire — a full parallel of the host-wide OOM killer, but its candidate list is exactly the tasks in that one cgroup. (b) CPU: a runtime ledger refilled every period

cpu.max holds two numbers, quota and period, both in microseconds: "$MAX $PERIOD". Writing "50000 100000" means "50,000 µs of CPU time per 100,000 µs (100 ms) wall-clock window" — 50% of one CPU core, averaged over that window; writing "max 100000" removes the ceiling entirely (the default). The kernel's CFS bandwidth controller gives the cgroup a runtime balance that starts each period at the quota value and is debited as its tasks actually run on a CPU.

(c) The "no internal processes" rule, precisely

cgroup v2 enforces a structural constraint v1 never had: once a cgroup has enabled a controller for its children (written +memory or similar into its own cgroup.subtree_control), that cgroup itself may no longer hold member processes directly for a controller it has delegated downward — it must either stay a pure "router" with all real work living in child (leaf) cgroups, or keep its processes and not delegate. The kernel enforces this at the file-write layer, not as documentation:

  • Writing a PID to a cgroup's cgroup.procs fails with EBUSY if that cgroup already has controllers enabled in its own cgroup.subtree_control.
  • Writing a controller name into cgroup.subtree_control fails with EBUSY if that cgroup currently has member processes of its own.
  • The root cgroup is exempt — it is a special, implicit "resource domain" allowed to hold processes and delegate to children simultaneously.

The rationale is not security (a distinction chapter 4's closing question specifically set up): with domain resources like CPU and memory, a controller has to know whether a given unit of usage belongs to this cgroup's own tasks or should be attributed to a child cgroup's tasks. Letting both coexist in the same node makes hierarchical accounting and limiting ambiguous — which bucket does a process running directly in a non-leaf cgroup count against once its sibling leaf cgroups also have limits? Rather than define an under-specified answer, the kernel simply disallows the ambiguous state.

HARDWARE COROLLARY: WHY memory.stat MATTERS MORE THAN memory.current

memory.current is a single number; memory.stat breaks it into anon (private, unshareable, unreclaimable-under-pressure memory — heap, stacks) versus file (page cache backing memory-mapped or read files — cheaply reclaimable). Two containers can show identical memory.current and have wildly different OOM risk: one that's 90% page cache reclaims its way out of pressure gracefully; one that's 90% anonymous memory has nowhere to go but the OOM killer the instant it crosses memory.max. §11 covers the production incident this distinction causes when nobody reads past memory.current.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

The throttling cliff nobody's dashboard shows

Cgroup accounting itself is cheap — memcg uses per-CPU counters that only synchronize globally when crossing a batch boundary, and production measurements of the overhead land in the low single-digit percent for memory and CPU controllers combined. The expensive part isn't the accounting — it's a correctness surprise in how quota enforcement interacts with bursty, multi-threaded workloads.

cpu.max's quota is consumed across all of a cgroup's threads combined, but it's checked within each 100 ms period independently. A four-thread service that bursts to use all four cores for 20 ms and then goes idle for 80 ms has a perfectly healthy 100 ms-average of 0.8 cores — but if its quota is set to 0.8 cores ("80000 100000"), that 20 ms burst alone consumes the entire period's budget in a fifth of the window, and throttle_cfs_rq() stalls every thread in the cgroup for the remaining 80 ms — even though, averaged over the second, the workload never came close to its quota. ATTACK SURFACE: WHAT v2 REMOVED, WHAT REMAINS

v2's biggest security win is subtractive: no release_agent, no notify_on_release — an entire class of "empty cgroup triggers a privileged script" bugs simply has no file to exploit (§11). What remains: a cgroup namespace (CLONE_NEWCGROUP, kernel 4.6) hides a container's true path in the host's tree from processes inside it — cosmetic isolation, not a resource boundary, and its absence in an unaware runtime just means a container sees its real /sys/fs/cgroup/machine.slice/libpod-... path rather than a cleaner-looking /. And any process with write access to another cgroup's interface files — a delegation misconfiguration — can rewrite that cgroup's limits, which is why cgroupfs permissions and correct delegation boundaries matter as much as the numbers written into the files.

ARC 11 · REAL-WORLD INCIDENTS

Three incidents this mechanism actually caused

Incident 1: CVE-2022-0492 — the release_agent escape

Disclosed by researchers at Unit 42 in early 2022, this CVE targeted the exact footgun §6 named: v1's release_agent file. The kernel's permission check for writing it verified only that the calling process held CAP_SYS_ADMIN — using the general capable() check, which succeeds against a process's own (possibly container-local, unprivileged-mapped) user namespace, rather than ns_capable() checked against the host's initial user namespace. A process that had CAP_SYS_ADMIN inside its own namespace — reachable via certain over-privileged container configurations, not a fully default container — could write a malicious script's path into release_agent, then make some cgroup under its control empty to trigger it. The kernel executed that script with genuine host-root privilege in the initial namespace: a full container escape. The fix restored the ns_capable(&init_user_ns, ...) check. cgroups v2 was never vulnerable to this class at all — there is no file to write, because there is no release_agent mechanism, period.

Incident 2: the cgroup-driver mismatch

For years, mixing a Kubernetes node's kubelet configured for one cgroup driver with a container runtime configured for the other was a known, recurring source of node instability: the two managers write and read the same cgroupfs paths with different assumptions about which of them owns unit lifecycle, producing everything from cgroup accounting drift to nodes that fail to report pod resource usage correctly. Kubernetes' own container-runtime guidance now explicitly recommends the systemd driver end-to-end whenever systemd is the init system precisely because — as §2's deep-context callout foreshadowed — a host can only sensibly have one manager of its cgroup tree. "Which driver is this cluster using" became, and remains, a standard first question in cluster-stability triage.

Incident 3: the OOM kill despite "plenty of free memory"

The single most common cgroups-v2 production surprise: a container gets killed by the cgroup OOM path while the host's free -m shows gigabytes free. The cause is exactly §8's memory.stat callout — memory.current counts reclaimable page cache the same as unreclaimable anonymous memory until reclaim is actually attempted, and a workload that mmaps large files or writes heavily buffered logs can sit right at memory.max long before its working set is actually under pressure. When an allocation spike arrives faster than reclaim can evict cache, the cgroup OOM killer fires against a container that was never truly short on usable memory. The fix operators converge on: use memory.high (a soft ceiling that triggers aggressive reclaim and scheduling throttle, but never invokes the OOM killer by itself) a comfortable margin below the hard memory.max, and actually read memory.stat's anon field before sizing a limit off memory.current alone.

Go (runc, simplified)fs2/memory.go — setMemory()
func setMemory(dirPath string, r *Resources) error {
    if r.MemoryLimit != 0 {
        // A negative sentinel means "no limit" — write the literal string
        // the kernel expects, not a numeric encoding of infinity.
        val := strconv.FormatInt(r.MemoryLimit, 10)
        if r.MemoryLimit == -1 { val = "max" }
        if err := fscommon.WriteFile(dirPath, "memory.max", val); err != nil {
            return err
        }
    }
    if r.OomKillDisable {
        // memory.oom.group: kill the WHOLE cgroup together, not one victim —
        // used when partial survival would leave a container half-alive.
        fscommon.WriteFile(dirPath, "memory.oom.group", "1")
    }
    return nil
}

void place_in_cgroup(const char *leaf, pid_t pid, long mem_max, const char *cpu_max)
{
    mkdir(leaf, 0755);                       /* creating a cgroup IS mkdir(2) — no special syscall */

    char path[PATH_MAX], buf[64];
    snprintf(path, sizeof(path), "%s/memory.max", leaf);
    int fd = open(path, O_WRONLY);
    int n  = snprintf(buf, sizeof(buf), "%ld", mem_max);
    write(fd, buf, n);                          /* EINVAL if mem_max is below current usage */
    close(fd);

    snprintf(path, sizeof(path), "%s/cpu.max", leaf);
    fd = open(path, O_WRONLY);
    write(fd, cpu_max, strlen(cpu_max));      /* e.g. "50000 100000" */
    close(fd);

    snprintf(path, sizeof(path), "%s/cgroup.procs", leaf);
    fd = open(path, O_WRONLY);
    n  = snprintf(buf, sizeof(buf), "%d", pid);
    write(fd, buf, n);                          /* moves an ALREADY-RUNNING process in */
    close(fd);
}

 * where it exists in the parent's cgroup and briefly evades limits before
 * a subsequent cgroup.procs write catches up to it.                       */
WHY clone3(CLONE_INTO_CGROUP) WAS BUILT — THE RACE IT CLOSES

The traditional sequence is fork() then write the child's PID into cgroup.procs — two separate steps with a window between them. For long-lived processes that window is harmless. For workloads that spawn thousands of very short-lived processes (a build system, a shell-heavy CI job, a fork-bomb-style attack probing pids.max), a child can run, consume resources, and exit entirely within that window — before the parent's write ever lands — invisible to the very limits meant to constrain it. Kernel 5.7 added CLONE_INTO_CGROUP to clone3() specifically to make placement atomic with creation: exactly the same motivation as this course's recurring theme of collapsing a "create, then configure" race into one operation the kernel guarantees can't be observed half-done.
