KUBERNETES INTERNALS · CHAPTER 12INTERMEDIATE

Scaling:
HPA, VPA & the Cluster Autoscaler

Every chapter so far assumed the number of replicas and the size of the cluster were facts someone else decided. This chapter opens up the three control loops that decide those facts for you: the Horizontal Pod Autoscaler, which changes how many Pods a workload gets by computing a real ratio from live metrics; the Vertical Pod Autoscaler, which changes how big each Pod is instead; and the Cluster Autoscaler, which changes how many nodes exist underneath all of it. None of these are magic — each is a reconciliation loop (chapter 9) with a formula you can compute by hand, and this is the last INTERMEDIATE chapter before the course turns to security internals.

ARC 01 · THE PROBLEM

A replica count is a guess, and guesses are wrong twice a day

Chapter 2 showed you a Deployment's spec.replicas — a plain integer, hand-written by whoever authored the YAML. That number was correct for exactly one load level. Real traffic is not one load level: it has a diurnal curve (day vs. night), a weekly curve (weekday vs. weekend), marketing-driven spikes, and — for anyone running batch or ML workloads — bursts that have nothing to do with the clock at all. A fixed replicas: 12 is either wasting money at 3 a.m. or falling over at 9 a.m., and usually both in the same week.

Unpack "pick the right number of replicas" and you find three separable problems, each solved by a different control loop in this chapter:

  • How many copies of this Pod should exist right now? — answered by the Horizontal Pod Autoscaler (HPA), reacting to a live metric (usually CPU or memory utilization, but also request rate, queue depth, or any custom signal).
  • How big should each copy be? — a Pod's resources.requests is also a guess, made once at YAML-authoring time, and workloads' actual footprints drift over months. The Vertical Pod Autoscaler (VPA) answers this by recommending — and optionally applying — better request/limit values from observed usage history.
  • Is there even room to run more copies? — the scheduler (chapter 8) can only place a Pod on a node that already exists. When every node is full, adding replicas doesn't help; the Cluster Autoscaler (CA) answers this by growing — or shrinking — the node pool itself.

These three loops are independent, run on different clocks, read different signals, and — as §6 and §11 will show in uncomfortable detail — can actively work against each other if you point two of them at the same metric. The goal of this chapter is to derive each one's real formula and real trigger conditions, not just name them.

WHERE THE METRICS ACTUALLY COME FROM

Every autoscaler in this chapter ultimately reads the same raw numbers: per-container CPU and memory usage that the kubelet's embedded cAdvisor derives from cgroup accounting files (cpu.stat, memory.current — the same primitives the Container Internals course covers at the kernel level). Chapter 15 covers exactly how metrics-server and Prometheus scrape that data; this chapter starts one layer up, at the control loops that act on it.

DEEP CONTEXT · WHY HPA AND CA LIVE IN DIFFERENT REPOSITORIES

The Horizontal Pod Autoscaler controller ships inside kube-controller-manager — it's part of kubernetes/kubernetes. The Cluster Autoscaler and the Vertical Pod Autoscaler both live in the separate kubernetes/autoscaler repository and are deployed as ordinary Deployments you install, with their own release cadence. The split is deliberate: HPA only ever touches the autoscaling/v2 API and a workload's /scale subresource — both cluster-agnostic. CA has to speak to a specific cloud's node-group API (AWS Auto Scaling Groups, GCP Managed Instance Groups, Azure VMSS), which is exactly the kind of provider-specific code the core project keeps out of its own binary — the same boundary chapter 6 drew around the Container Runtime Interface.

ARC 03 · NAIVE SOLUTION

Attempt #1: a cron job and a threshold

Before reaching for HPA, derive what an operator would actually write. You have kubectl top (backed by the same metrics-server data HPA will eventually use), a cron schedule, and a hunch about what "busy" means:

bashautoscale.sh — cron, every 5 minutes
#!/usr/bin/env bash
# The "we don't have HPA yet" script. Runs from cron every 5 minutes.
set -euo pipefail

DEPLOY=web
NS=prod
TARGET_CPU=50   # % — picked once by eyeballing a Grafana panel

# kubectl top reads from metrics-server — the SAME data source the
# real HPA controller reads in §5. The difference is entirely in
# what happens to the number next.
AVG_CPU=$(kubectl top pods -n "$NS" -l app="$DEPLOY" --no-headers \
  | awk '{gsub("%","",$3); sum+=$3; n++} END {print sum/n}')

CUR=$(kubectl get deploy "$DEPLOY" -n "$NS" -o jsonpath='{.spec.replicas}')

if (( $(echo "$AVG_CPU > $TARGET_CPU" | bc -l) )); then
  NEW=$((CUR + 2))                       # "add two, seems reasonable"
  kubectl scale deploy "$DEPLOY" -n "$NS" --replicas="$NEW"
elif (( $(echo "$AVG_CPU < $TARGET_CPU / 2" | bc -l) )); then
  NEW=$((CUR - 1))                       # "remove one, be conservative"
  kubectl scale deploy "$DEPLOY" -n "$NS" --replicas="$NEW"
fi
# Whatever happens between now and the next cron tick — a flash sale,
# a dead dependency, a traffic cliff — this script finds out in 5 minutes.

This is not a strawman built to be laughed at — it is genuinely how autoscaling was done (and often still is, for workloads nobody has migrated to HPA) before Kubernetes 1.1. It gets the shape right: observe a metric, compare to a target, adjust replica count. Its failures are entirely in the arithmetic and the timing, which is exactly what §5 fixes.

ARC 04 · WHY IT FAILS

Blunt steps and a 5-minute blind spot, quantified

Two independent defects compound in the naive script, and both are fixable by better arithmetic, not more infrastructure — which is exactly why HPA can be "just" a controller instead of a bespoke system.

  • Fixed step size, no notion of magnitude. NEW=$((CUR + 2)) adds exactly two replicas whether CPU is 51% over target or 400% over target. A workload that needs to go from 4 replicas to 32 (an 8× spike — not exotic for a flash sale) needs ceil((32-4)/2) = 14 cron ticks at 5 minutes each to fully scale: 70 minutes of running under-provisioned, even though the script fired every single cycle and did exactly what it was told.
  • A 5-minute-wide blind spot. The script only ever sees the world at the instant it runs. If traffic doubles 30 seconds after a tick, nothing reacts until the next one. Using a back-of-envelope queueing estimate (excess-rate × blind-spot-duration), a 200 req/s capacity shortfall sustained for the worst-case 300 seconds until the next tick is ~60,000 requests served late, queued, or dropped — from one scheduling gap, recurring every cycle traffic is rising.
  • No memory of the recent past. The moment average CPU dips under 25% (half of the 50% target) the script removes a replica — even if that dip is a 90-second lull in the middle of a spike. It then may need to scale back up next tick. Nothing here is malicious or even unreasonable per line of code; the script simply has no concept of hysteresis.
THE FIX ISN'T "RUN IT MORE OFTEN"

Shortening the cron interval to 30 seconds does not fix the step-size problem — you'd still add two replicas at a time, just more often, and you'd add operational risk (a flaky metrics call every 30s instead of every 5min). The real fix is computing the right number directly from the ratio of current to target, which is exactly what the HPA control loop does — never guess-and-check, always compute-and-apply. §5 derives that formula.

THE FORMULA, IN FULL

desiredReplicas = ceil[ currentReplicas × ( currentMetricValue / desiredMetricValue ) ], applied only when the ratio falls outside a ±10% tolerance band around 1.0 (the --horizontal-pod-autoscaler-tolerance flag on kube-controller-manager, default 0.1), and rate-limited by a behavior policy that lets scale-up react immediately but makes scale-down remember the highest recent recommendation for 300 seconds by default (stabilizationWindowSeconds). §8 shows this running against sliders you control, and §15's simulator runs it continuously against a live fleet.

ARC 06 · WHY THAT STILL COSTS

The formula is correct; the world around it still bites

Getting the arithmetic right does not make autoscaling free. Four costs remain, and they are the reason production Kubernetes clusters run more than just HPA:

  • Metrics are always stale. The number HPA reacts to already includes the kubelet's cAdvisor scrape interval, metrics-server's own --metric-resolution cache window (commonly 15–60s), and the HPA controller's own --horizontal-pod-autoscaler-sync-period (default 15s). A genuinely instantaneous spike can be 30–90 seconds old by the time a decision is made on it.
  • HPA has no idea whether there's room. Computing desiredReplicas = 40 and patching the Deployment's replica count does nothing if the cluster only has capacity for 25 — the new Pods simply go Pending. HPA and the scheduler share no feedback channel; that gap is exactly what the Cluster Autoscaler exists to close (§7 onward).
  • Cold starts eat the exact window you needed capacity in. A brand-new replica still has to be scheduled, pull its image (if not cached), pass its readiness probe, and warm any in-process caches before it accepts real traffic — seconds to tens of seconds during which the "fix" isn't actually helping yet.
  • Running HPA and VPA on the same metric makes them fight. Both loops read the same CPU number and can reach opposite conclusions about what to do with it. Watch it happen:
HPA and VPA, pointed at the same metricSTEP-BY-STEP

So the final architecture isn't one loop — it's three, each solving a distinct sub-problem, deliberately kept loosely coupled through ordinary Kubernetes objects (the Deployment, the Pod, the Node) rather than talking to each other directly.

WHY THE SCALE SUBRESOURCE MATTERS

HPA does not know the difference between a Deployment, a ReplicaSet, a StatefulSet, or a custom resource with a scale-like shape. It only knows how to GET and PATCH the tiny autoscaling/v1 Scale object (spec.replicas, status.replicas, status.selector) that each scalable type's API registration exposes as a subresource. This is the same "operate through a small, stable seam instead of the full object" pattern the CSI interface uses for storage (chapter 11) and the CRI interface uses for container runtimes (chapter 6) — narrow interfaces are how Kubernetes lets independently-versioned components cooperate.

An HPA that reacts fast to load and slow to quiet, exactly the asymmetry §5 derived:

yamlhpa.yaml — autoscaling/v2

  name: web

  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 40
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50          # desiredMetricValue
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0     # react immediately — users are waiting
      policies:
      - type: Percent
        value: 100                    # at most double per period
        periodSeconds: 15
      - type: Pods
        value: 4                      # or +4 pods, whichever is MORE (selectPolicy: Max)
        periodSeconds: 15
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300   # remember the highest recommendation for 5 min
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15
      selectPolicy: Max

(c) The Cluster Autoscaler's numeric thresholds

CA's behavior is entirely governed by a small set of flags with real, memorable defaults:

  • --scan-interval (default 10s) — how often CA looks for unschedulable Pods and underutilized nodes.
  • --scale-down-utilization-threshold (default 0.5) — a node is a scale-down candidate only if its Pods' summed requests are below 50% of allocatable capacity.
  • --scale-down-unneeded-time (default 10m) — how long a node must stay under that threshold, continuously, before CA acts — the node-level analogue of HPA's stabilization window.
  • --max-node-provision-time (default 15m) — how long CA waits for a cloud API's promised node before giving up and trying a different node group.
A NODE IS NEVER "UNNEEDED" IN ISOLATION

Low utilization alone is not sufficient. CA also simulates whether every Pod currently on that node could be rescheduled onto the remaining nodes' spare capacity. A node running one Pod at 10% utilization is not a scale-down candidate if that Pod is the only thing that fits anywhere (e.g., it needs a GPU only that node has, or a restrictive PodDisruptionBudget forbids evicting it) — §11 covers exactly this failure mode as a real operational trap.

Beyond one workload's reaction curve, three cluster-wide ceilings are worth memorizing because CA and HPA both run into them at scale:

  • 110 Pods per node is the kubelet's default cap (--max-pods) — a real bin-packing ceiling CA's scheduling simulation respects, independent of raw CPU/memory headroom.
  • The 5,000-node / 150,000-Pod envelope is Kubernetes' documented per-cluster SLO target. A Cluster Autoscaler aggressively growing toward that ceiling adds control-plane load (more Nodes and Pods for the API server and etcd to track, chapter 7) on top of whatever workload growth it's accommodating.
  • Node provisioning is minutes, not seconds. Even a fast cloud API typically takes 30s–3min to hand back a running VM, and the kubelet needs time after that to register and pass its first health checks — the single biggest reason CA cannot be "instant" the way HPA's in-cluster replica change can be.
ARC 11 · REAL-WORLD INCIDENTS

Four documented ways autoscaling bites in production

Autoscaling doesn't have a CVE roster the way the API server does — its failure modes are documented operator traps, several called out explicitly in the projects' own FAQs. That makes them no less real.

1. The cold-start gap during a genuine spike

HPA computes a correct desiredReplicas within one sync period (≤15s), but if the cluster has no spare capacity, the new Pods go Pending and Cluster Autoscaler's own scan-and-provision cycle (§8c) adds 30 seconds to several minutes before a new node is Ready. A workload that needed capacity now — a flash sale, a viral post — spends that entire window degraded or erroring. The documented mitigation is over-provisioning with deliberately low-priority "pause" Pods that CA can always evict first (chapter 14's PriorityClass preemption, running here in reverse: cheap placeholder Pods hold slack capacity so real Pods schedule instantly, and CA only has to replace the placeholders on its own time.

2. VPA's Recreate mode fighting HPA mid-spike

The kubernetes/autoscaler project's own documentation explicitly advises against running HPA and VPA on the same resource metric for the same workload. The mechanism (§6's deck): under load, HPA scales replica count up while VPA's updater — seeing the same rising CPU per Pod — evicts and recreates Pods to give them bigger requests. Each recreation is a Pod restart: cold caches, a fresh readiness-probe warm-up window, and one fewer Pod actually serving traffic for the duration — precisely when the fleet can least afford it. The fix isn't disabling either autoscaler; it's scoping them to different metrics (VPA on memory, HPA on CPU or a custom request-rate metric) or running VPA in recommendation-only mode.

3. A PodDisruptionBudget silently pins a node forever

The Cluster Autoscaler FAQ lists this as one of the most common "why won't my cluster scale down" reports: a singleton Pod protected by a PodDisruptionBudget with maxUnavailable: 0 can never be evicted, so any node holding it can never be drained, so CA — correctly, by its own rules from §8c — leaves that node running indefinitely even at 5% utilization. The cluster isn't broken; it's honoring an availability guarantee nobody remembered they'd set. The fix is auditing PDBs on singleton workloads, or accepting that a workload without redundancy cannot both guarantee availability and permit its node to be reclaimed.

4. metrics-server itself falls over

metrics-server is just another Deployment, sized by someone's own resource requests. On a cluster that has grown well past its original node count, an under-provisioned metrics-server starts missing scrapes or gets OOMKilled. The HPA controller's response is visible and specific: the HPA object's Status.Conditions reports ScalingActive: False with reason FailedGetResourceMetric, and — critically — replica count simply freezes at whatever it last was, silently, with no scale-up or scale-down happening until metrics recover. A cluster that "stopped autoscaling" a week before a traffic event, with nobody noticing because nothing crashed, is a real and recurring on-call story.

The formula itself, close to its real shape in replica_calculator.go:

goreplica_calculator.go — GetResourceReplicas() (simplified, faithful)
func (c *ReplicaCalculator) GetResourceReplicas(
    currentReplicas int32, targetUtilization int32,
    usageRatios []float64, tolerance float64,
) (desiredReplicas int32) {

    // usageRatios[i] = currentMetricValue_i / desiredMetricValue, one per Pod.
    // Average them first — HPA scales on the FLEET's average, not one Pod's.
    ratio := average(usageRatios)

    // The tolerance band: do nothing if we're already close enough.
    // Default 0.1 — a fleet sitting at 45-55% against a 50% target never churns.
    if math.Abs(ratio-1.0) <= tolerance {
        return currentReplicas
    }

    // THE FORMULA. Always ceil — a fractional replica means guaranteed
    // under-capacity if you round down.
    raw := math.Ceil(float64(currentReplicas) * ratio)
    return int32(raw)
}
gohorizontal.go — reconcileAutoscaler() (simplified)
func (a *HorizontalController) reconcileAutoscaler(hpa *v2.HorizontalPodAutoscaler) error {
    // 1. Fetch current state from the Scale subresource — HPA never reads
    //    the Deployment/StatefulSet object directly.
    scale, _ := a.scaleClient.Scales(hpa.Namespace).Get(hpa.Spec.ScaleTargetRef)
    currentReplicas := scale.Spec.Replicas

    // 2. Pull metrics — from metrics.k8s.io, custom.metrics.k8s.io, or
    //    external.metrics.k8s.io, depending on hpa.Spec.Metrics[].Type.
    raw := a.computeReplicasForMetrics(hpa, scale, hpa.Spec.Metrics)

    // 3. Apply the behavior policy: immediate for scale-up, windowed-max
    //    for scale-down (§5's asymmetry, made concrete).
    desired := a.stabilizeRecommendation(hpa, raw, currentReplicas)
    desired = a.clampToMinMax(hpa, desired)

    // 4. Only write if something actually changed.
    if desired != currentReplicas {
        scale.Spec.Replicas = desired
        a.scaleClient.Scales(hpa.Namespace).Update(scale) // patches /scale
    }
    return nil
} // re-run every --horizontal-pod-autoscaler-sync-period (default 15s)
WHY IT WAS BUILT THIS WAY

1. HPA writes to the Scale subresource, never the workload's full spec. This is the same narrow-interface discipline as CSI and CRI — HPA's code has zero knowledge of Deployment- or StatefulSet-specific fields, so new scalable types need only implement /scale, not register with HPA. 2. The tolerance and behavior logic lives entirely in the controller, not the metrics pipeline. metrics-server reports raw numbers; every scaling decision — tolerance, stabilization, rate limits — is centralized in one place, auditable and unit-testable independent of which metrics backend is plugged in. 3. Cluster Autoscaler reuses the scheduler's own predicate code to simulate fit instead of re-implementing "does this Pod fit on this node" — the exact same anti-duplication instinct that keeps CRI, CSI, and the Scale subresource thin.
