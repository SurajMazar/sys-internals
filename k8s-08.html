The Scheduler: Filtering,
Scoring & Binding

Every Pod that has ever run in a Kubernetes cluster was assigned to exactly one node by a single component making one decision, twice: first which nodes could possibly run this (a hard filter), then which of those is actually best (a weighted score). This chapter derives that two-phase design from first principles, walks the real scheduling-framework extension points a Pod passes through, and ends with a simulator that runs the actual arithmetic — not a cartoon of it — against six candidate nodes.

ARC 01 · THE PROBLEM

One decision, thousands of times a day, with no do-over

By chapter 6 you know the control plane's shape: the API server as the single source of truth, etcd underneath it, and a scheduler that watches for Pods with no .spec.nodeName set. This chapter is about exactly what happens between "a Pod exists with nowhere to run" and "a Pod is bound to a specific node." That decision looks simple from the outside — pick a node — and is genuinely hard once you unpack what it must satisfy simultaneously.

Unpack it into five pulling-apart requirements:

  • Feasibility, not just availability. A node with free CPU is not automatically a legal home — it might carry a NoSchedule taint reserving it for another team, lack a label the Pod's nodeAffinity requires, or already be marked unschedulable. Placing a Pod somewhere it cannot legally or physically run is worse than not scheduling it at all — the kubelet will simply refuse it (or worse, the Pod will run somewhere it was never supposed to).
  • Optimization among the feasible set. Usually more than one node qualifies. "Best" is not a fact — it depends on whether the operator wants to pack workloads tightly (fewer nodes running, lower cloud bill, easier scale-down) or spread them thinly (survive a node failure, avoid noisy-neighbor contention). These two goals actively conflict, and a scheduler has to pick a stance.
  • Freshness under constant churn. Every scheduling decision anywhere in the cluster changes every node's free capacity. A scheduler that decides against state that is even a few hundred milliseconds stale risks recommending a node that another decision already filled.
  • No double-booking. Two Pods must never be simultaneously convinced they own the same slice of a node's CPU and memory — that is a correctness bug, not a performance one.
  • Throughput under load. A cluster autoscaling event or a large Deployment rollout can produce hundreds of pending Pods at once. One Pod with an impossible-to-satisfy constraint (say, a typo'd node selector) must not stall the queue behind it.

The kube-scheduler's answer is a strict two-stage pipeline — filter, then score — implemented as a pluggable framework, backed by an internal cache that trades a little staleness for a lot of throughput, and finished off with an intentionally asynchronous bind. This chapter derives that shape, in that order, and then follows one concrete Pod through it.

WHERE THIS SITS IN THE COURSE

Chapter 6 showed you the scheduler as one box in the control-plane diagram. Chapter 9 will show you that nothing the scheduler decides is permanent — controllers continuously reconcile desired vs. observed state, and a scheduling decision is just one more piece of observed state that a controller might act on later (for example, if the bound Pod never becomes Ready). Everything in this chapter answers "where," never "how many" or "keep it running" — those are chapter 9's job.

DEEP CONTEXT · THE BORG PAPER'S DIRECT FINGERPRINT

Google's 2015 EuroSys paper "Large-scale cluster management at Google with Borg" describes Borg's scheduler as running feasibility checking first, then scoring the feasible machines — the exact two-phase shape this chapter derives. Several of Kubernetes' founding engineers had worked on Borg or its sibling Omega; the two-phase design wasn't rediscovered independently, it was carried over on day one, in the same way the postmaster/backend split you saw in the PostgreSQL course wasn't invented in a vacuum either — proven shapes get reused.

ARC 03 · NAIVE SOLUTION

Attempt #1: hand a Pod to the next free-looking node

Derive it honestly. Before predicates and priorities existed as a concept, imagine you had to write the simplest possible placer yourself. You have a list of nodes; a Pod needs a home; assign it to the next node in the list and move on.

bashnaive_scheduler.sh — the strawman, annotated
# poll for unscheduled Pods, round-robin them across nodes,
# with NO check of capacity, taints, or affinity
i=0
nodes=($(kubectl get nodes -o name))

while true; do
  pod=$(kubectl get pods --field-selector=spec.nodeName= \
          -o jsonpath='{.items[0].metadata.name}')
  if [ -n "$pod" ]; then
    node=${nodes[$(( i % ${#nodes[@]} ))]}       # just... the next one
    kubectl patch pod "$pod" --subresource=status \
      --patch "{\"spec\":{\"nodeName\":\"$node\"}}"   # no capacity check!
    i=$(( i + 1 ))
  fi
  sleep 1
done

This is not a strawman built to be laughed at — it is exactly where you should start. It solves the actual minimum problem ("every Pod eventually gets a nodeName") with the least code possible, and for a homogeneous cluster running identically-sized workloads with no isolation requirements at all, it would even work passably. Watch it fail once those assumptions break.

ARC 04 · WHY IT FAILS

Round-robin ignores exactly the facts that matter, quantified

Three concrete failure modes, each with real numbers, because "it doesn't check capacity" undersells how fast this goes wrong:

  • Silent overcommit on requests. A 4-node cluster, 8 vCPU / 32 Gi each = 32 vCPU / 128 Gi total capacity. A Deployment scales to 100 replicas, each requesting 1 vCPU / 2 Gi. Round-robin lands 25 Pods per node: 25 vCPU requested against 8 vCPU capacity — 312% oversubscribed, before a single Pod has done any real work. Nothing checked this at placement time, so nothing rejects it: the kubelet dutifully tries to admit all 25, the kernel's CFS scheduler time-slices the CPU thin enough that every Pod's actual throughput collapses, and once real memory usage (not just requests) exceeds 32 Gi, the kernel's OOM killer starts picking victims essentially at random.
  • Taint-blindness is a policy violation, not just a resource problem. Say one node in that cluster carries dedicated=gpu:NoSchedule because it has an attached GPU reserved for an ML team. Round-robin does not know taints exist. One in four Pods lands there anyway, consuming CPU/memory the GPU team's actual workload needed, and — depending on what's running — potentially reading memory alongside a workload it was never meant to share a node with. This is a security and capacity-planning failure wearing a scheduling bug's clothes.
  • No notion of "better." Even when every node has room, round-robin cannot express "pack these three batch jobs onto one already-busy node so the other three can scale to zero" or "spread these five replicas across three availability zones so a zone outage takes at most two." There is no score, so there is no way to encode an objective at all — every placement is equally arbitrary.
THE PATTERN

Every one of these failures has the same root cause: the naive placer only ever asks "is there a next node," never "can this node legally and physically host this Pod, and if several can, which one should." Those are two different questions with two different cost profiles — one is a hard yes/no per node, the other is a ranking across survivors — and conflating them is exactly what round-robin does. Split them, and you have the real scheduler's shape.

ARC 05 · FILTER, THEN SCORE

Deriving the two-phase pipeline

Step through the derivation the way Borg's designers (and later, Kubernetes') actually reasoned about it: first fix correctness, then, only among correct choices, optimize.

From round-robin to filter + scoreSTEP-BY-STEP
THE KEY INSIGHT

Filtering and scoring are not two flavors of the same check — they are different kinds of question with different failure semantics. A filter is a boolean veto: any single failing filter plugin removes a node from consideration, full stop, no partial credit. A score is a continuum: every surviving node gets ranked, and "worst surviving node" is still a legal, if suboptimal, choice. Conflating them — letting a soft preference accidentally behave like a hard requirement, or vice versa — is one of the most common real-world Kubernetes misconfigurations (an operator writes preferredDuringSchedulingIgnoredDuringExecution when they meant requiredDuringSchedulingIgnoredDuringExecution, and wonders why Pods land somewhere "wrong" instead of staying Pending).

ARC 06 · WHY THAT STILL COSTS

Filter-then-score is correct — it is not free

Three costs the two-phase design does not eliminate, each of which shows up as a real operational concern at scale:

  • Scoring every feasible node doesn't scale linearly forever. At 50 nodes, scoring all of them per pending Pod is trivial. At 5,000 nodes with thousands of Pods arriving from a large rollout, scoring every feasible node for every Pod is wasted work the moment you already have several good-enough candidates. The scheduler's actual answer — an adaptive percentageOfNodesToScore — is explored with real numbers in §10; the short version is it trades a small chance of missing the global optimum for a large win in decision latency.
  • The scheduler decides against a cache, not live truth. To avoid hitting the API server (and, transitively, etcd) on every single filter check, the scheduler keeps its own in-memory NodeInfo snapshot, refreshed from the same watch mechanism chapter 7 covered. Binding is then deliberately asynchronous — the scheduler "assumes" a Pod is placed in its cache and moves on to the next Pod immediately, rather than blocking the whole pipeline on a network round trip to the API server. That asynchrony is what makes throughput possible, and it is exactly what creates the race window §11 examines under a real incident pattern.
  • Preemption — the escape hatch for "nothing fits" — is another full pass, and it can cascade. When zero nodes survive filtering, the scheduler doesn't just give up: its PostFilter stage asks "if I evicted some lower-priority Pod, would this Pod then fit?" Answering that means re-running filter logic against hypothetical states, one candidate victim (or victim set) at a time — itself another filter-shaped computation layered on top of the first one, gated by whether evicting the victim would violate its PodDisruptionBudget.

WHY A FRAMEWORK, NOT A FUNCTION

Before KEP-624, "predicates" and "priorities" were hardcoded lists inside the scheduler binary — adding one meant patching and recompiling kube-scheduler itself, which is exactly why scheduler extenders (webhook callouts, §9) existed as a workaround. The framework turned every stage — including the built-ins — into the same plugin interface, so a cluster operator who needs custom placement logic implements Filter/Score/etc. against a stable Go interface and compiles it into their own scheduler binary (or the community's scheduler-plugins repository), instead of forking kube-scheduler or paying a network round trip per decision.

(b) Requests, limits, and what "fits" actually means

The Filter phase's NodeResourcesFit plugin never compares a Pod against a node's raw hardware capacity — it compares against Allocatable, which is capacity minus what the platform has deliberately carved out for itself:

formulakubelet's Node.Status.Allocatable
Allocatable = NodeCapacity - kube-reserved - system-reserved - eviction-hard threshold

kube-reserved protects the kubelet, container runtime, and node-level Kubernetes daemons; system-reserved protects sshd, systemd, and the rest of the OS; the eviction-hard threshold (default memory.available<100Mi, tunable) is capacity the kubelet holds back so it can evict Pods gracefully before the kernel's OOM killer has to. THE GAP THE SCHEDULER LEAVES OPEN, ON PURPOSE

NodeResourcesFit sums requests against Allocatable — it never looks at limits. That is a deliberate design choice, not an oversight: requests are the guaranteed reservation a Pod is promised, and limits are a per-container ceiling the kubelet enforces via cgroups (chapter 2 of the Container Internals course covers the cgroup mechanics; this course does not re-derive them). Kubernetes explicitly allows sum(limits) > Allocatable — that's how "burstable" QoS Pods share slack capacity — but it means a node that passed every filter check can still hit real memory pressure if enough Pods burst simultaneously. §10 and §11 both return to exactly this gap.

ARC 09 · TRADEOFFS

The same placement problem, five ways

"Use a custom scheduler" is not one option — it is a spectrum, and each point on it prices extensibility against operational simplicity differently:

Multiple schedulers (schedulerName)Run a second scheduler process alongside the default, Pods opt in isolate risky logic from the default path must partition nodes (labels/taints) or both schedulers race for the same capacity
Batch/gang schedulers (Kueue, Volcano)Built as framework plugins or a coordinating extra control loop gang scheduling, queueing & quota for ML/batch jobs another control-plane component to run and upgrade in lockstep

Read this table the way you read chapter 1's process-model comparison: there is no dominant strategy, only different placements of the same underlying cost — someone pays for extensibility, either in operational surface area (run more components) or in engineering effort (write and maintain Go plugins).

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Numbers you can predict before you hit 5,000 nodes

Complexity, stated precisely: filtering one Pod costs roughly O(nodes × filter-plugins) — each plugin is typically O(1) per node (a label comparison, a taint scan, an arithmetic check). Scoring costs O(scored-nodes × score-plugins), where scored-nodes is the piece the scheduler can shrink.

  • percentageOfNodesToScore. Clusters at or below 50 nodes score every feasible node (100%). Above 50, the default adaptive percentage shrinks roughly linearly with cluster size down to a floor of 5% — so a 5,000-node cluster scores on the order of a few hundred nodes per decision, not five thousand, once "enough" feasible candidates have been found. This is a genuine accuracy-for-latency trade: the chosen node is "good," not provably globally optimal.
  • Default pod density: kubelet's --max-pods defaults to 110 Pods per node — a real ceiling the scheduler's Filter phase respects (a node at 110 Pods fails every subsequent Pod on a dedicated NodeResourcesFit-adjacent check, regardless of remaining CPU/memory).
  • The documented cluster envelope: Kubernetes' own scalability thresholds target up to 5,000 nodes and 150,000 Pods per cluster as a supported SLO boundary — well past that, cluster federation or multi-cluster patterns (chapter 17) become the answer, not scheduler tuning alone.
  • etcd's shape still matters here. Chapter 7 covered etcd's recommended <1.5 KB per key and multi-GB total-size ceiling; every Bind is a write through the API server into etcd, so etcd's own latency envelope is a hard floor under the scheduler's throughput no plugin tuning can remove.

Security characteristics

The scheduler is a high-privilege component by necessity: writing pod.spec.nodeName via the pods/binding subresource is, in the default RBAC bindings, restricted to the system:kube-scheduler identity precisely because where a Pod lands can matter for security — a Pod that lands on a node holding another tenant's secrets-bearing workload, or a node with elevated host access, can matter even if the Pod itself looks innocuous (chapter 13 covers the full RBAC/admission pipeline this identity flows through; one cross-reference sentence is enough here). A compromised custom scheduler with binding rights is therefore a node-placement attack primitive, not just an availability risk — which is exactly why the "multiple schedulers" tradeoff row in §9 calls out node partitioning as a requirement, not a nicety.

ARC 11 · REAL-WORLD INCIDENTS

Three ways scheduling breaks in production

Incident 1: scheduler throughput collapses at extreme node counts

OpenAI's publicly documented work scaling Kubernetes clusters to roughly 7,500 nodes (their 2021 engineering blog on running large ML training clusters) is a direct, real case study in exactly the tradeoff §10 models: at that scale, naive full-node scoring and control-plane request volume both become bottlenecks, and the documented levers are the same ones this chapter names — tuning percentageOfNodesToScore, watching API server and etcd request latency as leading indicators, and, where the workload allows it, using nodeSelector/affinity to shrink the feasible set the scheduler has to reason about per Pod in the first place. The lesson generalizes: scheduler tuning is not a "set once" default, it is a knob you revisit as cluster size crosses documented thresholds.

Incident 2: the assume-cache race — a Pod briefly "scheduled" twice

Because Bind is asynchronous (§6), the scheduler's internal cache marks a node's resources as consumed the moment it decides, not the moment the API server confirms the write. Under API server or etcd latency — a genuinely documented operational condition, not a hypothetical — two back-to-back scheduling cycles can both compute a stale, still-fits view of the same node before either Bind call lands, assume the Pod is placed, and race to bind two Pods against resources that only exist once. The actual failure mode operators see is not silent corruption: the second Bind either succeeds (temporarily oversubscribing the node until the kubelet or the next reconciliation notices) or is rejected, and the losing Pod is requeued and re-scheduled — cheap, but visible as a brief flap between Pending and a bound state in cluster events. Recognizing the mechanism (optimistic concurrency, not a bug) is what lets you stop chasing it as a mystery and instead watch API server/etcd latency as the actual root cause.

Incident 3: preemption thrash in mixed-priority, multi-tenant clusters

A common, well-documented operational pattern in clusters mixing latency-sensitive services with high-PriorityClass batch or ML training jobs: the batch scheduler keeps submitting large jobs at high priority, each triggering DefaultPreemption to evict lower-priority service Pods to make room, and the evicted services churn (restart, re-warm caches, briefly fail readiness) faster than they can stabilize. The fix path is exactly the vocabulary this chapter introduced: non-preempting PriorityClass (preemptionPolicy: Never, GA since 1.24) for jobs that should queue rather than evict, PodDisruptionBudgets on the latency-sensitive services so preemption respects a minimum available count, and — often the real fix — separate node pools via taints so batch and serving workloads never compete for the same feasible set at all.

Four functions, simplified from the real 1.28+ source but faithful in structure and naming. First, the per-Pod cycle's shape:

Goschedule_one.go — ScheduleOne(), the parts that matter
func (sched *Scheduler) ScheduleOne(ctx context.Context) {
    pod := sched.NextPod()                    // pop from the priority queue (QueueSort)

    // PreFilter: run once per cycle, not once per node — plugins
    // precompute pod-level state (e.g. total requested resources)
    state := framework.NewCycleState()
    sched.Framework.RunPreFilterPlugins(ctx, state, pod)

    feasible, diagnosis := sched.findNodesThatFitPod(ctx, state, pod)  // Filter

    if len(feasible) == 0 {
        // PostFilter: is there a Pod we could evict to make room?
        sched.Framework.RunPostFilterPlugins(ctx, state, pod, diagnosis)
        return   // Pod stays Pending either way this cycle
    }

    // PreScore + Score + NormalizeScore, then a weighted sum per plugin
    scoredNodes := sched.prioritizeNodes(ctx, state, pod, feasible)
    host := sched.selectHost(scoredNodes)               // highest weighted score wins

    // Reserve + Permit run synchronously; Bind does NOT —
    // assume() marks the cache as consumed, then binding is a goroutine
    sched.Cache.AssumePod(pod)
    go sched.bind(ctx, pod, host)     // PreBind → Bind → PostBind, off the hot path
}

The plugin doing the arithmetic from §8(b):

Goframework/plugins/noderesources/fit.go — Filter() + Score()
func (f *Fit) Filter(ctx context.Context, state *CycleState, pod *v1.Pod, nodeInfo *NodeInfo) *Status {
    requested := sumContainerRequests(pod)             // cpu, memory, ephemeral-storage…
    allocatable := nodeInfo.Allocatable                       // §8(b)'s formula, already computed
    used := nodeInfo.Requested                                // sum of already-bound Pods' requests

    for _, r := range []Resource{CPU, Memory} {
        if used[r]+requested[r] > allocatable[r] {
            return Unschedulable("Insufficient %s", r)   // hard veto, no partial credit
        }
    }
    return Success()
}

func (f *Fit) Score(ctx context.Context, state *CycleState, pod *v1.Pod, nodeName string) (int64, *Status) {
    // LeastAllocated (default): reward nodes with MORE headroom left over.
    // MostAllocated: reward nodes with LESS headroom — bin-packing.
    frac := (used[r] + requested[r]) / allocatable[r]
    if f.ScoringStrategy == LeastAllocated {
        return int64((1.0 - frac) * MaxNodeScore), Success()   // MaxNodeScore = 100
    }
    return int64(frac * MaxNodeScore), Success()
}

The taint check that eliminates a node outright:

Goframework/plugins/tainttoleration/taint_toleration.go — Filter()
func (pl *TaintToleration) Filter(ctx context.Context, _ *CycleState, pod *v1.Pod, nodeInfo *NodeInfo) *Status {
    for _, taint := range nodeInfo.Node().Spec.Taints {
        if taint.Effect != NoSchedule && taint.Effect != NoExecute {
            continue   // PreferNoSchedule only affects Score, never Filter
        }
        if !tolerationsTolerateTaint(pod.Spec.Tolerations, &taint) {
            return UnschedulableAndUnresolvable("node has untolerated taint {%s: %s}", taint.Key, taint.Value)
        }
    }
    return Success()
}
WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Filters are pure boolean vetoes with no shared mutable state across nodes. That is what makes them trivially parallelizable — RunFilterPlugins can (and does) evaluate multiple nodes concurrently, because no filter's answer for node A depends on what happened for node B. 2. Scores are normalized to a fixed 0–100 range before combination. This lets the framework combine wildly different plugins — a resource ratio, a label match, a topology-spread deviation — with one honest weighted sum, instead of every plugin author inventing an incompatible scale. 3. Assume-then-async-bind decouples decision speed from network speed. The main scheduling loop's throughput is bounded by CPU (filter/score math), not by API server round trips — the same "don't let a slow I/O operation block the supervisor" instinct chapter 1 of the PostgreSQL course applied to authentication happening in a forked child, not the postmaster.
