Chapter 6 told you the controller-manager runs "dozens of independent control loops." Chapter 8 showed you one of them — the scheduler — deciding where a Pod goes. This chapter opens up the loop itself: the exact mechanism, shared by the ReplicaSet controller, the Deployment controller, every operator you will ever install, and your own custom controllers, that turns "I want 3 replicas" into "there are 3 replicas," and keeps it true forever, without anyone ever calling a function named fixIt().

ARC 01 · THE PROBLEM

Someone has to make "3 replicas" stay true

A Deployment's YAML says replicas: 3. That number is a wish, not a fact. The moment you kubectl apply it, the API server writes it to etcd (chapter 6) and does nothing else — the API server's entire job is to validate and persist objects, never to act on them. Something else has to notice the wish, compare it against reality, and change reality until the two match. That something is a controller, and getting this one mechanism right is arguably the single idea Kubernetes contributes to distributed systems that didn't already exist in a mature form.

Unpack "make it stay true" and the requirements pull in different directions, all at once:

  • Nothing notifies you reliably. A node can lose network for ten minutes and the API server's watch stream to your controller silently reconnects with a gap. Any event that happened during the gap is gone.
  • The world changes out from under you. A human runs kubectl delete pod by hand, a node dies mid-reconcile, another controller (or a webhook) mutates the object you're working on — you cannot assume your last observation is still true.
  • Failures must be retryable without becoming duplicated work. If your reconcile function creates a Pod and then crashes before recording success, restarting it must not create a second Pod for the same slot.
  • Thousands of controllers run concurrently against the same objects — ReplicaSet, HPA, PodDisruptionBudget, your own operator — each caring about a different slice of the same state, none of them coordinating directly with each other.
  • The controller itself can crash and restart at any point, with zero in-memory state, and must resume correct behavior from nothing but "what does the API server say right now."
WHY THIS MATTERS FOR THE REST OF THIS COURSE

Every "self-healing" claim you have heard about Kubernetes cashes out to exactly one mechanism: a controller comparing desired vs. observed state on a loop and issuing corrective API calls. ReplicaSet replacing a dead Pod (this chapter), the HPA changing a replica count (chapter 12), the Cluster Autoscaler adding a node (chapter 12), cert-manager renewing a certificate, ArgoCD reconciling a cluster against git (chapter 17) — all the same loop, different desired/observed pair. Understand this chapter and every one of those stops being magic and starts being a diff.

ARC 02 · HISTORICAL CONTEXT

The idea is older than Kubernetes — the API-driven form isn't

Control loops that converge toward a setpoint are not a 2014 invention — thermostats do it, TCP congestion control does it, Google's internal Borg did it for a decade before Kubernetes existed. What Kubernetes contributed was making the loop generic and declarative over a uniform object model: any controller, for any resource type, talks to the same API server the same way, watches the same event stream format, and stores its desired state as a plain object a human can read and edit. DEEP CONTEXT · WHY "CONTROLLER," NOT "TRIGGER" OR "HANDLER"

The naming is deliberate and borrowed from control theory: a thermostat controller doesn't "handle a temperature-drop event," it continuously measures and corrects. Kubernetes' designers (many ex-Borg/Omega engineers) chose that framing specifically to avoid the failure mode of event-driven systems: a handler that fires once, on one edge, and has no way to notice it was wrong. You'll feel the difference concretely in §5.

ARC 03 · NAIVE SOLUTION

Attempt #1: react to the event that told you something changed

The obvious design for "keep 3 replicas running" is event-driven: subscribe to Pod delete/create notifications, and when you see one, adjust. Here is that strawman as a script, annotated with exactly where it will bite you:

bashnaive_controller.sh — the edge-triggered strawman
#!/bin/bash
# "Keep 3 nginx Pods running" — react only to events, never re-check.
DESIRED=3

# Subscribe to a live event stream. Reacts ONCE per delete event.
kubectl get events --watch --field-selector reason=Killing | while read line; do
    # A Pod died — create exactly one replacement. Nothing double-checks
    # that we're actually still short of DESIRED, or that the replacement
    # we made a minute ago for a DIFFERENT event actually landed.
    kubectl run nginx-replacement-$RANDOM --image=nginx
done

# Runs once at startup only — never again. If this process was down
# for the last 20 minutes and missed 3 delete events, it never finds out.

Like the iterative database server you'd derive in a systems course, this is not a joke — it's the honest first attempt. It is cheap (idle almost all the time, wakes only on an event), simple to read, and for a demo where the watch connection never drops and every event arrives exactly once, it even works. ARC 04 · WHY IT FAILS

Missed events are not an edge case — they're the normal case at scale

Event-driven ("edge-triggered") automation has one structural weakness: an event is a claim about a single transition, with no memory of the state before or after it. If you miss the claim, you have no way to reconstruct what you missed — unless you keep re-checking the actual state, at which point you've reinvented reconciliation and the event stream becomes just an optimization.

  • Watch connections drop, by design. The API server closes long-lived watch connections after --min-request-timeout (default window randomized around 5–10 minutes) specifically to spread load and rotate apiserver instances behind a load balancer. Every controller reconnects constantly — this is normal operation, not a failure.
  • The gap between disconnect and reconnect is real time with zero visibility. A controller process restarting after an OOM-kill, a node running the controller-manager rebooting, or simply a slow reconnect all create a window where events are simply never delivered.
  • Events can coalesce or be dropped upstream. The Events API itself is best-effort and rate-limited; relying on the Kubernetes Event object type (as the naive script does) for control decisions is doubly wrong — Events are diagnostic breadcrumbs, not a delivery-guaranteed queue.
  • Multiple causes can produce the same net effect, un-observably. A Pod might be deleted and a replacement created by a human, then deleted again — three events, net effect zero — while your handler, firing once per event, creates one extra replacement anyway.
THE NUMBERS

Assume a controller reconnects its watch every 8 minutes on average (a typical relist/rewatch window) and a reconnect takes 200 ms during which any delete/create events are invisible. Over a 30-day month that's roughly 5,400 reconnects × 200 ms ≈ 18 minutes of pure blind spot — and that's the best case, ignoring actual outages, node reboots, or the controller pod itself being rescheduled (which happens to controller-manager itself during every upgrade). A cluster running for a year will, with certainty, have a delete event vanish into one of these gaps. An edge-triggered controller that never re-checks reality will simply run one Pod short — forever, silently — until someone notices a symptom two layers up the stack.

So the fix cannot be "make the event stream more reliable" — no event stream is perfectly reliable across process restarts, network partitions, and years of uptime. The fix has to be an architecture that doesn't depend on having seen every event to reach the correct state.

ARC 05 · BETTER SOLUTION

Level-triggered reconciliation: stop trusting the event, trust the diff

Borrow a term from hardware interrupt design, because it's exactly the right one. An edge-triggered signal fires on a transition (0→1) — miss the pulse and the information is gone forever. A level-triggered signal reflects the current state — check it any time, even long after the transition, and you get the right answer. Kubernetes controllers are level-triggered by design: an event is treated only as a hint that something might be different now — a nudge to go re-read reality — never as the payload itself.

Edge-triggered vs level-triggered, side by sideSTEP-BY-STEP

The mechanical shape every Kubernetes controller shares is a four-stage pipeline. Later sections implement each stage for real, but the shape is worth stating up front:

  • Observe — an informer keeps a local, continuously-updated cache of the objects you care about (via a long-lived watch, §8), so reading "current state" never touches etcd or the API server on the hot path.
  • Enqueue — whenever anything might be relevant (an object changed, OR nothing changed but it's just time to double-check), the object's key goes into a workqueue. Keys, not events — deliberately throwing away the "what changed" detail (§8).
  • Reconcile — a worker pops a key, reads the current object from the local cache (not from the queue!), computes what corrective action (if any) makes reality match spec, and issues it.
  • Repeat, forever, on a floor — even with zero events, the queue gets the key back on a resync period (commonly every 30 seconds to 10 minutes depending on the controller) so a missed or lost event is self-correcting: the very next tick re-derives the same answer from scratch.
THE CLINCHING ARGUMENT: IDEMPOTENCE FOR FREE

Because reconcile always recomputes "what should exist right now" from the current desired and observed state — never from "what just happened" — running it twice for the same underlying cause produces the same result as running it once. You get at-least-once delivery semantics on top of a function that only needs to be correct when called with stale, duplicated, or entirely fabricated inputs. That is a dramatically easier correctness bar than "never miss an event and never process one twice," and it's the reason a Kubernetes cluster keeps converging correctly through node reboots, controller-manager restarts, and network partitions that would break a purely event-driven design outright. §15's simulator makes this concrete: you will kill state behind the controller's back and watch the *same* function, unaware anything special happened, put it back.

ARC 06 · WHY THAT STILL COSTS

The bill: what level-triggering costs you in latency and load

Level-triggering isn't free — trading "never miss anything" for "re-derive everything" has real, quantifiable costs that show up in production tuning knobs you will actually touch:

  • Convergence is not instant. Between "the world changed" and "the controller notices and acts" there is inherent latency: watch propagation delay (usually milliseconds, via the informer's event handlers), workqueue processing time, and — worst case, if the triggering watch event was itself lost — up to a full resync period (the sync period default is commonly configured around 30 seconds for many built-in controllers, though it varies by controller and can be tuned via --min-resync-period). A reconciliation loop is fundamentally an eventually-consistent system, and "eventually" has a real number attached to it that operators must reason about.
  • Periodic full resyncs are real API-server and etcd load. Every controller's informer periodically relists (or resyncs from cache) every object it watches, regardless of whether anything changed — this is the cost of the safety net. At cluster scale (thousands of controllers × thousands of objects) this is a dominant, measurable source of API server QPS, which is exactly why chapter 7's etcd watch mechanism and this chapter's client-go caching layer are designed together, not separately.
  • Reconcile functions must be written idempotently, which is a real engineering discipline. "Just make an API call when you see a diff" is not automatically safe — creating a Pod twice because reconcile ran twice before the first creation was observed is a classic controller bug (client-go's OwnerReference and object UID checks exist specifically to prevent this — §8 shows the actual pattern).
  • You cannot special-case "this looks like the thing that just happened." Precisely because the reconcile function must treat every invocation identically regardless of cause, it cannot take shortcuts based on "I already know what changed" — every tick pays the full cost of reading current state and recomputing the diff, even when the actual delta is nothing.
HOW THE ECOSYSTEM ANSWERS THIS

Kubernetes doesn't eliminate these costs — it layers optimizations on top of a level-triggered core rather than abandoning it. Informers cache aggressively so "read current state" is a local map lookup, not an API call (§8). Workqueues deduplicate keys so a burst of ten events for one object costs one reconcile, not ten (§8). Resync periods are tunable per-controller so hot, cheap-to-check resources can resync often and expensive ones rarely. The architecture is: be level-triggered for correctness, be event-driven for latency — use watch events purely as a low-latency hint to reconcile sooner, never as the sole source of truth.

ARC 08 · INTERNAL IMPLEMENTATION

From a watch event to a reconcile call: the real client-go pipeline

Now the actual mechanism, at the level you'd need to write a controller against. Three pieces: (a) the object shapes a controller reads and writes, (b) the informer/workqueue pipeline that turns a watch stream into reconcile calls, and (c) the reconcile function's own contract.

(a) What a controller actually reads and writes

A ReplicaSet is the plainest possible example of desired-vs-observed living in one object. spec is what you asked for; status is what the controller last observed and reported back — and critically, only the controller writes status, via a dedicated /status subresource, so a user editing spec can never accidentally clobber the controller's own bookkeeping:

yamla ReplicaSet mid-reconciliation — spec is the wish, status is the observation
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-7d9c4f
  uid: 3f2a9c10-...            # stable identity — see OwnerReference below
  generation: 4                  # bumped by the API server on every spec write
spec:
  replicas: 3                    # DESIRED — only a human/Deployment controller writes this
  selector:
    matchLabels: { app: web, pod-template-hash: 7d9c4f }
  template: { /* Pod spec to stamp out */ }
status:                          # OBSERVED — only the ReplicaSet controller writes this,
  replicas: 2                    # via the /status subresource
  readyReplicas: 2
  availableReplicas: 2
  observedGeneration: 4          # "I have reconciled generation 4" — lets clients tell
                                     # stale status from current status
  conditions:
    - type: ReplicaFailure
      status: "False"

status.replicas: 2 against spec.replicas: 3 is the entire problem statement in one object: create one more Pod. Notice observedGeneration — this is how a controller (or a human running kubectl rollout status) distinguishes "the controller hasn't gotten to my latest edit yet" from "the controller processed my edit and this is the honest result."

WHY KEYS, NOT OBJECTS, GO IN THE QUEUE

The workqueue holds strings like "default/web-7d9c4f" — namespace/name — never the object itself. This is deliberate: by the time a worker pops the key and looks it up in the informer's cache, the object may have changed again (or been deleted). Storing the key forces every reconcile to re-fetch current state from the cache rather than acting on a stale snapshot captured whenever the event fired — the same discipline as §5's "trust the diff, not the event," enforced structurally by the data structure itself.

func (rsc *ReplicaSetController) syncReplicaSet(key string) error {
    // 1. Split the key back into namespace/name and fetch CURRENT
    //    state from the informer's local cache — never from the API
    //    server directly, and never from whatever triggered this call.
    namespace, name, _ := cache.SplitMetaNamespaceKey(key)
    rs, err := rsc.rsLister.ReplicaSets(namespace).Get(name)
    if errors.IsNotFound(err) {
        return nil // deleted since being queued — nothing to do, not an error
    }

    // 2. List CURRENT observed Pods matching this ReplicaSet's selector —
    //    again from the shared informer cache, an O(1)-ish indexed lookup.
    allPods, _ := rsc.podLister.Pods(namespace).List(selectorFor(rs))
    myPods := filterActive(allPods)             // exclude Pods already terminating

    // 3. THE ENTIRE ALGORITHM: diff desired vs observed, correct the delta.
    diff := len(myPods) - int(*rs.Spec.Replicas)
    switch {
    case diff < 0:
        rsc.createPods(-diff, rs)              // too few — create |diff| more
    case diff > 0:
        victims := rsc.selectVictims(myPods, diff) // too many — delete diff of them
        rsc.deletePods(victims)
    // diff == 0: nothing to do. Reconcile is a no-op MOST of the time —
    // that's the expected steady state, not a wasted call.
    }

    // 4. Report what we observed, via the /status subresource ONLY.
    return rsc.updateReplicaSetStatus(rs, len(myPods))
}
WHY THIS FUNCTION NEVER NEEDS AN "ELSE, DO NOTHING SPECIAL" BRANCH FOR MISSED EVENTS

Read step 3 again: there is no code path that asks "what caused this call?" It doesn't matter whether syncReplicaSet ran because a Pod died, because the resync timer fired, because a human edited spec.replicas, or because the controller-manager itself just restarted and is reconciling everything from a cold cache. Every one of those triggers produces the identical call with the identical correct outcome, because the function only ever looks at current desired and current observed state. This is precisely the property §15's simulator will let you verify by hand.

ARC 10 · PERFORMANCE & SCALING CHARACTERISTICS

Numbers you can predict before you hit them in production

  • Informer cache reads are O(1)-ish, not O(watched objects). The Indexer stores objects in an in-memory map keyed by namespace/name (plus secondary indices, e.g. by label selector or node name), so a reconcile's "list my Pods" call is a local lookup, never a network round trip — this is precisely why the pattern scales to controllers that reconcile on every tick without melting the API server.
  • Workqueue depth, not object count, predicts convergence lag. A workqueue with exponential backoff on requeue (client-go's default: base 5ms, cap 1000s) means a single flaky reconcile only sees geometrically spaced retries — but if thousands of objects genuinely need reconciling at once (a mass Node failure), queue depth becomes the real bottleneck, bounded by --concurrent-x-syncs worker-count flags per controller.
  • The API server's watch cache is what makes N controllers cheap. Every controller's Reflector doesn't hit etcd directly (chapter 6/7) — the API server maintains its own in-memory watch cache per resource type that all watchers share, so 50 controllers watching Pods cost roughly the same etcd load as 1.
  • Real scaling envelope. The Kubernetes scalability SLOs (5,000-node clusters, 150,000 Pods) are, in practice, gated as much by controller-manager reconcile throughput and API server watch-cache pressure as by etcd's own <8 KB-per-value write-path limits (chapter 7) — a cluster can be etcd-healthy and still fall over from workqueue backlog if a controller's reconcile function is too slow per call.

ARC 11 · REAL-WORLD PRODUCTION INCIDENTS

Three ways reconciliation goes wrong in the field

Incident 1: the hot-loop reconcile that never reaches diff==0

A common operator bug: the reconcile function updates a field on the object it's reconciling (e.g. a status annotation) using a plain Update() instead of the /status subresource. That write triggers the informer's own "object updated" handler, which re-enqueues the same key, which reconciles again, which writes again — a self-inflicted infinite loop that pins a worker goroutine at 100% and floods the API server with writes for one object. The fix is structural, not a rate limit: write status only through the /status subresource (which doesn't bump metadata.generation, chapter 6) and compare against the last-known value before writing at all — reconcile should be a no-op write when nothing actually changed.

Incident 2: resync storms after a controller-manager restart

Every upgrade or crash of kube-controller-manager restarts every controller's informers from a cold cache: each one does a full LIST of its watched resource type before it can start watching incrementally again. On a large cluster (tens of thousands of Pods, ConfigMaps, Secrets) with many controllers restarting simultaneously, this produces a genuine LIST-request storm against the API server and its etcd-backed watch cache, sometimes visible as a latency spike across the whole control plane for the seconds to low minutes it takes every informer to relist. Mitigations in practice: the API server's watch cache serving LISTs from memory instead of etcd wherever possible (a real optimization path, not universal), staggered controller-manager rollouts, and generous --kube-api-qps/--kube-api-burst tuning on the controller-manager itself so it doesn't self-throttle into an even slower recovery.

Incident 3: a stuck finalizer holds an object "deleting" forever

An object with a metadata.finalizers entry (commonly added by an Operator that needs to clean up an external resource — a cloud load balancer, a database) is not actually deleted by kubectl delete — the API server only sets deletionTimestamp and waits for every finalizer to be removed by its owning controller. If that controller's reconcile logic has a bug (or the external API it depends on is down) and never removes the finalizer, the object sits in "Terminating" indefinitely — a level-triggered loop that has gotten stuck specifically because its own corrective action can never succeed. This is one of the few places where "the reconcile loop will eventually converge" is false in practice, and it is precisely why finalizer logic must include its own bounded-retry/give-up-and-alert path rather than looping forever on an external dependency that may never recover.

First, how a shared informer turns one watch stream into calls on every registered handler — this is the fan-out that lets many independent controllers (RS controller, HPA, PodDisruptionBudget controller) all watch Pods without each one opening its own connection to the API server:

Goshared_informer.go — the shape of HandleDeltas()
func (s *sharedIndexInformer) HandleDeltas(obj interface{}) error {
    // obj is a Deltas list from DeltaFIFO — one or more coalesced
    // changes (Added/Updated/Deleted/Sync) for a single object's key.
    for _, d := range obj.(Deltas) {
        switch d.Type {
        case Sync, Replaced, Added, Updated:
            s.indexer.Add(d.Object)              // keep the local cache current FIRST
            s.distribute(updateNotification{d.Object}, false) // then fan out to handlers
        case Deleted:
            s.indexer.Delete(d.Object)
            s.distribute(deleteNotification{d.Object}, false)
        }
    }
    return nil
}

// distribute() calls every registered ResourceEventHandler's
// OnAdd/OnUpdate/OnDelete — this is where a controller's own code
// typically does nothing but: workqueue.Add(key). The handler is
// deliberately "dumb" — all real logic lives in the reconcile step.

Goreplica_set.go — the worker loop pattern every controller shares
func (rsc *ReplicaSetController) worker(ctx context.Context) {
    for rsc.processNextWorkItem(ctx) {
    }
}

func (rsc *ReplicaSetController) processNextWorkItem(ctx context.Context) bool {
    key, quit := rsc.queue.Get()          // blocks until a key is available
    if quit {
        return false
    }
    defer rsc.queue.Done(key)          // mark done EVEN ON ERROR — required for dedup

    err := rsc.syncHandler(ctx, key.(string)) // → syncReplicaSet(), §8c
    if err == nil {
        rsc.queue.Forget(key)             // success — reset this key's backoff
        return true
    }

    // Failure: requeue with EXPONENTIAL BACKOFF, not immediately.
    // A transient API server hiccup gets retried in ~5ms; a key that
    // keeps failing backs off toward the ~1000s ceiling — protects
    // the API server from a hot-looping bad object (Incident 1, §11).
    rsc.queue.AddRateLimited(key)
    return true
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Separate "notice something changed" from "act on it." ResourceEventHandlers only touch the workqueue; they never call business logic directly — this means the queue, not the watch stream, controls concurrency and ordering, and a slow reconcile can never block the informer from keeping its cache fresh. 2. Deduplicate by key, not by event. If the same object changes five times before a worker gets to it, the workqueue's set semantics collapse that to one pending key — you reconcile current state once, not five stale snapshots. 3. Retry with backoff is a first-class primitive, not an afterthought. Every controller gets exponential-backoff retry for free from the shared workqueue package, which is exactly why a single flaky reconcile degrades gracefully instead of hot-looping (§11's Incident 1 is what happens when a controller accidentally defeats this protection).

This is also precisely the machinery you use, unmodified, when you write a custom controller for a CustomResourceDefinition: register a CRD, get a generated informer/lister for it via client-gen/controller-gen, and write one syncHandler. That combination — a CRD plus a controller that reconciles it — is the entire definition of the Operator pattern: domain logic (provision a database, roll a certificate, scale a Kafka cluster) expressed as a level-triggered loop over a Kubernetes-native object, getting crash-safety and self-healing for free from infrastructure you didn't have to build.
