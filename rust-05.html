RUST · CHAPTER 05BEGINNER

Borrowing &
References

Chapter 4 gave every value exactly one owner and made that owner's function boundary a one-way door: pass a String into a function and it is gone from the caller unless the callee hands it back. That is not a corner case — it is unworkable as a general rule. This chapter derives the fix: references (&T and &mut T), the compile-time aliasing XOR mutability rule that governs them, and the exact class of memory bugs that rule eliminates before your program ever runs.

ARC 01 · THE PROBLEM

Nothing can look at data without taking it

Take chapter 4's ownership rules exactly as given — one owner, moves transfer it, the owner's drop frees it — and try to write a normal program with only those tools. You will hit the same wall within minutes: a function that only wants to read a value has no way to do that without becoming its owner.

Rustownership-only.rs — compiles, but watch what it costs
fn calculate_length(s: String) -> (String, usize) {
    let length = s.len();
    (s, length)   // forced to hand ownership back, just to keep using `s`
}

fn main() {
    let s1 = String::from("hello");
    let (s1, len) = calculate_length(s1);
    println!("The length of '{}' is {}.", s1, len);
}

This compiles and runs — Rust's real ownership rules from chapter 4 permit exactly this. But look at what it demands: calculate_length never wanted to change s, never wanted to keep it, it only wanted to call .len() on it — and yet the only way to give it access was to transfer full ownership, which means main loses s1 the instant it calls the function. The only way to keep using s1 afterward is to have the callee package it back up in a tuple and hand it to the caller again. Now imagine three helper functions each needing to inspect the same String — every single one needs this return-it-back dance, and the caller's code fills up with tuple destructuring that has nothing to do with the actual logic.

Scale that up and it gets worse, not better. A function that wants to inspect an element of a Vec<String> without consuming the whole vector, a data structure that wants to hold a pointer to part of another structure it doesn't own, a loop that wants to read a counter that ten other pieces of code also need to read — none of this is expressible with "the owner moves, or you clone it." Something has to let code look at data it does not own, without invalidating the owner and without paying to copy the data every time. That something is a reference: a value that points at data owned by someone else, carrying a compiler-checked promise about what it is and is not allowed to do to that data.

WHAT THIS CHAPTER ACTUALLY BUILDS

Two new types, &T ("a shared reference to a T") and &mut T ("an exclusive reference to a T"), plus exactly one rule the compiler enforces about how many of each may exist over any given span of the program. That one rule is doing an enormous amount of work: it is the single mechanism behind Rust's claims about both memory safety (no dangling pointers) and, later in the course, thread safety (no data races). Chapter 9 builds the machinery (lifetimes) that lets references be stored in structs and returned from functions; this chapter is everything you need to use references correctly inside a function body, which is most of the code you will ever write.

ARC 02 · HISTORICAL CONTEXT

Aliasing is an old, well-studied problem — Rust just enforced the answer

The idea that "a pointer that can both alias and mutate is dangerous" did not start with Rust. Compiler writers and language researchers had been circling it for decades; Rust's contribution was making the rule mandatory and checking it at compile time for ordinary application code, not just for optimizer hints or research prototypes. Click through the road to today's borrow checker — the last two stops explain exactly why the simulator in §15 needs two different rule-sets to model correctly.

DEEP CONTEXT · CYCLONE, THE MISSING LINK

Cyclone (AT&T Labs / Cornell, early-to-mid 2000s) was a research dialect of C aimed at memory safety, and its region-based pointer system is the direct academic ancestor of Rust's borrow checker — Rust's early designers, including Niko Matsakis, explicitly studied it. Cyclone proved the idea could work on real, C-shaped code; Rust's job (2010 onward) was making it ergonomic enough that application programmers, not just safety researchers, would tolerate it. The 2018 non-lexical-lifetimes rewrite — which §7 and §15 make concrete — is the biggest single step in that ergonomics campaign.

ARC 03 · NAIVE SOLUTION

Attempt #1: fake a reference with a raw address

If ownership-only Rust is too rigid, the obvious escape hatch — the one C reached for in 1972 and never left — is a raw memory address: a pointer that says "the data lives over there," with no rules attached about how long "there" stays valid. Here is the naive solution in the language that has run it as its default for fifty years:

Cdangling.c — compiles clean under `cc -O2` (no `-Wall`), corrupts silently
int *make_counter(void) {
    int local_value = 42;      /* lives on THIS function's stack frame */
    return &local_value;         /* hand the caller its ADDRESS, not its value */
}   /* frame is popped HERE — the address above now points at freed stack space */

int main(void) {
    int *p = make_counter();
    printf("%d\n", *p);     /* UB: reads memory that is no longer "ours" */
    return 0;
}

This is a completely ordinary-looking function. It answers exactly the question §1 posed — "let me hand out access without transferring ownership" — with the simplest tool C offers: an address. And for a while, on your machine, today, it will probably even print 42, because nothing has overwritten that stack slot yet. That "probably, for now" is the entire problem, and §4 quantifies it.

ARC 04 · WHY IT FAILS

A dangling reference is a real, named, quantified bug class

The C example in §3 is not a strawman invented for this course — it is the textbook shape of CWE-562 (Return of Stack Variable Address), a sibling of the far more infamous CWE-416 (Use After Free). Both share the same anatomy: a pointer keeps pointing at memory after whatever guaranteed its validity has ended. The compiler frequently stays silent (plain cc gives no diagnostic for the code above at all; -Wall catches this specific pattern, but the equivalent bug through a heap pointer, a linked-list node, or a closure capture routinely slips past every warning flag that exists), and the failure is deferred to whatever unlucky moment another stack frame happens to reuse that memory:

  • Best case: the value hasn't been overwritten yet — the bug is invisible, and ships to production.
  • Common case: a later function call reuses the freed stack slot, and the "counter" silently becomes garbage — wrong answers, no crash, no log line.
  • Worst case: an attacker who controls the timing or size of nearby allocations grooms that freed memory into something they chose — the mechanism behind a large share of real-world memory-corruption exploits, including CVE-2019-5786, a Chrome FileReader use-after-free that was actively exploited in the wild before it was patched.
THE NUMBERS THE INDUSTRY ACTUALLY REPORTS

Microsoft's own security team reported (BlueHat IL, 2019) that roughly 70% of the CVEs it fixes every year trace back to memory-safety bugs — dangling pointers, use-after-free, and buffer overruns. The Chromium security team published a near-identical figure the following year: about 70% of Chrome's high-and-critical-severity security bugs are memory-safety issues. This is not a rare edge case that careful C/C++ programmers avoid — it is the dominant source of serious security defects in two of the largest, most heavily-reviewed C/C++ codebases on Earth.

Now write the equivalent function in Rust, honestly, with no references yet — you literally cannot produce the C bug's shape, because there is no way to spell "return the address of a local" without the compiler refusing to compile it:

Rustdangle.rs — rejected before it runs
fn dangle() -> &String {
    let s = String::from("hello");
    &s
}   // error[E0106]: missing lifetime specifier
    //  --> src/main.rs:1:16
    // 1 | fn dangle() -> &String {
    //   |                ^ expected named lifetime parameter
    //   = help: this function's return type contains a borrowed value,
    //           but there is no value for it to be borrowed from

Even if you satisfy the compiler with an explicit lifetime annotation (chapter 9's territory), the underlying problem doesn't disappear — it just moves to a different, more precise error:

Rustdangle2.rs — same bug, a sharper diagnosis
fn dangle<'a>() -> &'a String {
    let s = String::from("hello");
    &s
}   // error[E0515]: cannot return value referencing local variable `s`
    //   |     &s
    //   |     ^^ returns a value referencing data owned by the current function

Same bug shape as the C code, two different rustc diagnoses depending on exactly how you tried to spell it — and in both cases the failure happens at cargo build, on your laptop, seconds after you wrote the bug, instead of at 3 a.m. in production after an attacker found the timing window. That is the entire value proposition of a compile-time borrow checker in one paired example.

ARC 05 · BETTER SOLUTION

References: look without owning, and let the compiler prove it's safe

Rust's actual answer keeps the raw-address idea's convenience — "point at data you don't own" — but attaches two compiler-enforced promises to it that C's raw pointers never made: a reference can never outlive the data it points to, and a reference's read/write privileges are declared in its type, not discovered by reading the whole function. Step through how the two reference types are built, from the fix for §1's problem to the exact rule that makes §4's bug unrepresentable.

THE RULE, STATED PRECISELY

At any point in a running program, for a given piece of data, exactly one of these may be true: (a) there are zero or more active &T shared references to it, or (b) there is exactly one active &mut T exclusive reference to it. Never both categories at once. Borrow-checker folklore calls this "many readers XOR one writer," and it is enforced the same way regardless of whether the "reader" and "writer" are two function calls in the same thread or two different OS threads — which is exactly why chapter 15 can build data-race freedom on top of this same rule instead of inventing a new one.

ARC 06 · WHY THAT STILL HAS COSTS

Be honest: the borrow checker is not free

References solve §1's and §4's problems completely, but they are not a magic wand — every Rust programmer spends real time paying these costs, and a beginner chapter that pretends otherwise is lying to you:

  • "Fighting the borrow checker" is a real, named experience. The checker is sound but deliberately conservative — it must reject some patterns that are, in fact, memory-safe, because proving safety for the general case is undecidable. Splitting two disjoint fields of the same struct into two simultaneous &mut borrows through two separate method calls is a classic beginner wall: the fields don't alias, but the checker (reasoning one method call at a time) can't always see that, and you end up restructuring code or calling a helper like the real standard library's own split_at_mut (§13) just to get past it.
  • Verbosity. Every function signature must now say, explicitly, whether it borrows shared or exclusive, and for how long (chapter 9). That's more to type and more to read than a language where "just pass the object" always works, even if what it buys you is knowing the contract without reading the body.
  • Escape hatches exist because the checker can be too strict for legitimate designs. Genuinely shared, genuinely mutable graph-shaped data (a GUI widget tree, a doubly-linked list) doesn't fit "one writer XOR many readers" checked at compile time at all — chapter 12's Rc<RefCell<T>> moves the same rule to a runtime check (a real panic if you violate it) specifically because the compile-time version has no way to represent these shapes. That is Rust admitting a real limit, not dodging one.
  • Compile times. Borrow-check analysis (dataflow over the whole function body — you'll see the real shape of it in chapter 19) is one more pass the compiler must run on every build, and it is part of why cargo build is measurably slower than an equivalent C compile.

None of this is a reason to avoid references — §1 already showed the alternative is unworkable, and §4 showed the alternative's failure mode. It is a reason to expect a real learning curve, and to know, honestly, which parts of that curve are "you'll get faster at this" versus "this is a genuine, permanent limitation the language accepts on purpose."

WHY "XOR," SPECIFICALLY — THE DATA RACE CONNECTION

A data race, by the definition used in the C++ and LLVM memory models Rust also relies on, requires three things at once: two-or-more accesses to the same memory, at least one of them a write, with no synchronization ordering them. Look at what "many shared XOR one exclusive" removes: if every live reference is &T, there is no write in the mix — case closed, no race possible, however many readers there are. If there is a write (&mut T), the rule guarantees it is the only live reference — no second accessor exists to race with. The rule isn't aimed at threads at all in this chapter (everything above is single-threaded), but it is exactly strong enough that chapter 15 can reuse it, unchanged, as the foundation of Rust's compile-time data-race freedom across threads too.

ARC 10 · PERFORMANCE & SAFETY CHARACTERISTICS

A compiled reference is a pointer — nothing more, nothing less

This is the payoff for all of §6's honesty about the learning curve: at the machine-code level, a Rust &T or &mut T compiles down to exactly the same thing a raw C pointer does — one machine word holding an address, dereferenced with a plain load or store instruction. All of the aliasing checking happens in the compiler, at build time, and leaves zero trace in the binary. There is no hidden refcount, no runtime flag, no lock. Compare that to the two runtime-checked alternatives from §9:

  • Rc/Arc (reference counting): every clone and drop is an increment/decrement of a counter — atomic (a real CPU fence, tens of cycles) for Arc, plain for single-threaded Rc.
  • RefCell (runtime-checked borrows): every .borrow()/.borrow_mut() call checks and updates a small runtime flag, and panics — a real, observable cost plus a crash risk — if the same XOR rule this chapter teaches is violated.
  • Tracing GC: ordinary access is often as cheap as a raw pointer, but the collector must periodically stop some or all threads to trace live objects — a real, occasionally large, unpredictable pause.

ARC 11 · REAL-WORLD INCIDENTS

This isn't academic — it's a documented, ongoing industry pattern

Incident 1: CVE-2019-5786, a Chrome use-after-free exploited in the wild

A FileReader object in Chrome's Blink rendering engine held onto a reference that outlived the buffer it pointed into — precisely the shape §3/§4 walked through with a stack address, except here the freed memory was on the heap and reachable from untrusted web content. Google confirmed active exploitation before a patch shipped, and it was serious enough to trigger an out-of-band Chrome update. The bug's shape — a live pointer surviving the deallocation of what it pointed to — is exactly what the aliasing rule in this chapter, applied at compile time, makes structurally impossible to express in safe Rust: there is no way to hold a &T past the point its owner is dropped, full stop.

Incident 2: Android's multi-year, measured bet on memory-safe languages

Google's Android security team has published year-over-year data since roughly 2019 showing the share of Android's severe security vulnerabilities attributable to memory-safety bugs falling sharply — from the high-70-percent range down toward the mid-30s — as an increasing fraction of new Android platform code shipped in Rust rather than C/C++, with existing C/C++ code left untouched. Their explanation lines up exactly with this chapter: it isn't that Rust programmers write fewer logic bugs, it's that an entire category of bug (including the dangling/aliasing shape from §3-§4) is rejected before code review even starts, and — per their reporting — zero memory-safety vulnerabilities had been found in Android's Rust code as of that report.

Incident 3: Production systems choosing Rust specifically for this guarantee

AWS Firecracker, the microVM that backs AWS Lambda's multi-tenant sandboxing, was written in Rust from its first line specifically because a memory-safety bug in a hypervisor is a tenant-isolation bug — a dangling reference there is a potential cross-customer data leak, not just a crash. Cloudflare's Pingora proxy, which replaced a large fraction of Cloudflare's nginx-based edge fleet in 2022, was built in Rust for the same stated reason: the previous C-based stack's worst incidents traced back to memory-safety bugs in request-parsing code that handles untrusted input from the entire internet — the highest-stakes place for exactly the bug class this chapter's aliasing rule eliminates.

ARC 13 · CODE WALKTHROUGH

The standard library is built entirely on this rule

Once you know the aliasing rule, a pattern jumps out everywhere in the standard library: methods come in matched shared/exclusive pairs, and the exclusive half is the only one that can hand you something you're allowed to mutate. Here's the shape (simplified and paraphrased from real, current core/alloc source — not verbatim, but structurally faithful):

library/core/src/
├── slice/
│ └── ● mod.rs — get()/get_mut(), first()/first_mut(), split_at()/split_at_mut(): the shared/exclusive pairing pattern, everywhere
├── ● option.rs — Option<T>::as_ref()/as_mut(): borrow the inside of an Option instead of consuming it
└── cell/mod.rs — Cell<T>/RefCell<T> (chapter 12): the SAME xor rule, moved to a runtime check
library/alloc/src/
└── vec/mod.rs — Vec::push(&mut self, ...): mutation always spelled as an exclusive borrow of the receiver
Rustcore/src/slice/mod.rs — the shared/exclusive pair, simplified
impl<T> [T] {
    // Shared: read-only access, returns a SHARED reference to the element.
    pub fn get(&self, i: usize) -> Option<&T> {
        if i < self.len() { Some(&self[i]) } else { None }
    }

    // Exclusive: the &mut self receiver is what LETS this return &mut T at all —
    // the compiler will not let you call this while any &T from get() is still live.
    pub fn get_mut(&mut self, i: usize) -> Option<&mut T> {
        if i < self.len() { Some(&mut self[i]) } else { None }
    }
}

The most interesting case is split_at_mut: it hands out two separate &mut slices from the same underlying slice at once — which looks like exactly the "two exclusive borrows" pattern §7 marked illegal. It's legal here only because the two halves are provably disjoint (they don't overlap), and the standard library proves that with a small amount of unsafe code the borrow checker can't verify on its own — a preview of chapter 17's whole subject:

Rustcore/src/slice/mod.rs — split_at_mut, simplified from the real implementation
pub fn split_at_mut(&mut self, mid: usize) -> (&mut [T], &mut [T]) {
    let len = self.len();
    let ptr = self.as_mut_ptr();
    assert!(mid <= len);
    // SAFETY: `mid <= len` was just checked, so [0, mid) and [mid, len) are two
    // disjoint, in-bounds regions of the SAME allocation — the aliasing rule
    // isn't violated, but the borrow checker has no way to see "disjoint" on
    // its own; the programmer proves it once, here, behind `unsafe`.
    unsafe {
        (std::slice::from_raw_parts_mut(ptr, mid),
         std::slice::from_raw_parts_mut(ptr.add(mid), len - mid))
    }
}
THE PATTERN TO CARRY FORWARD

"Method that borrows, plus a _mut sibling that exclusively borrows" is not a naming convention someone chose for style — it is the aliasing rule made visible in every API signature you will read for the rest of this course. When you see iter()/iter_mut(), first()/first_mut(), or lock() on a Mutex (chapter 15), you are looking at the exact same rule this chapter derived, applied consistently for a decade across a standard library with thousands of contributors.
