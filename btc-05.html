BITCOIN INTERNALS · CHAPTER 05

Signature Hashing:
SIGHASH & the Malleability Bug

Every OP_CHECKSIG in Bitcoin verifies a signature against a 32-byte number — but a transaction signs itself, scriptSig and all, which is a contradiction until you look at exactly which bytes get hashed and which get blanked out first. This chapter derives the sighash algorithm from that contradiction, walks its four flags and one catastrophic bug, and follows the single design flaw — transaction malleability — that blocked payment channels for six years and became bitcoin's most misreported incident.

ARC 01 · THE PROBLEM

A signature signs a message. What's the message?

Chapter 4 built ECDSA from the discrete-log problem and showed the mechanics: a signer computes (r, s) from a private key d and a 256-bit number z; a verifier checks (r, s) against a public key Q and that same z. Everything about ECDSA's security rests on one assumption you glossed over at the time: both parties agree, byte for byte, on what z is. For a login challenge or a signed email, that's trivial — z is the hash of the message. A Bitcoin transaction's scriptSig exists specifically to hold a signature over the transaction that is spending this input. So: what, precisely, is being signed?

Try to answer literally and you hit a wall immediately. "Sign the transaction" seems to mean z = SHA256d(serialize(tx)) — double-SHA256 of the raw bytes from chapter 3. But the raw bytes of the transaction include the scriptSig, and the scriptSig is where the signature itself will be written. To compute the hash you need the final transaction bytes; to know the final transaction bytes you need the signature; to compute the signature you need the hash. The naive definition is circular before you write a single line of code.

This chapter is entirely about breaking that circularity — and about what happens when the fix is subtly wrong. Three things fall out of the same root cause once you see it clearly:

  • SIGHASH flags — a signature doesn't have to commit to the whole transaction; Satoshi's original design lets a signer choose exactly which pieces it authorizes, for legitimate protocol reasons.
  • The SIGHASH_SINGLE bug — one specific flag combination has an edge case the original code handles by returning a fixed, meaningless hash instead of an error, and it is now permanently part of consensus.
  • Transaction malleability — because the signature is inside the thing being hashed for the transaction ID, and a signature has more than one valid byte-encoding, anyone who can see a transaction in flight can change its ID without invalidating it. This blocked an entire category of application — payment channels — until BIP143 restructured the hash algorithm in 2017.
WHY THIS MATTERS BEYOND BITCOIN

Every blockchain that signs structured data containing its own signature field hits this same self-reference problem — Ethereum's transaction hashing, Solana's message signing, even TLS's CertificateVerify all have their own version of "exclude the thing you're about to write." The specific mechanism differs, but the shape of the problem — and the shape of the malleability bug that follows from an incomplete fix — recurs everywhere a signature is embedded in the object it authorizes.

ARC 02 · HISTORICAL CONTEXT

From Satoshi's four flags to Taproot's rewrite

The sighash algorithm has one of the longest incident histories of any piece of Bitcoin's consensus code: designed in 2009, exploited in theory for years, blamed (largely wrongly) for the largest exchange collapse in the currency's history, and only structurally fixed by a soft fork eight years after launch. DEEP CONTEXT · THIS WAS NEVER A SECRET BUG

Unlike most incidents in chapter 15, transaction malleability was documented and discussed publicly on Bitcointalk as early as 2011 — developers understood the ECDSA symmetry and the non-canonical DER issue long before Mt. Gox made headlines. The gap between "known issue" and "fixed in consensus" was eight years, because the fix required a new script version (SegWit) rather than a simple patch — a recurring lesson: in a system with no central upgrade authority, a known flaw in a consensus rule can outlive several general election cycles before the coordination to fix it completes.

ARC 03 · NAIVE SOLUTION

Attempt #1: hash the finished transaction

Derive it honestly, the way a competent engineer would on first contact with the problem. You have a transaction with one input to sign. The obvious instinct: serialize the whole thing — inputs, outputs, the works — hash it, sign that hash, and drop the signature into the scriptSig you just pretended was empty.

pseudo-codenaive_sign.py — the strawman
def naive_sign(tx, input_index, privkey):
    # "just hash the transaction" — but which transaction?
    tx_bytes = serialize(tx)             # includes every scriptSig, including this one
    z = sha256d(tx_bytes)
    sig = ecdsa_sign(privkey, z)
    tx.vin[input_index].scriptSig = encode(sig)   # ← mutates the very bytes we just hashed
    return tx

# Problem, stated precisely:
#   z depends on tx_bytes
#   tx_bytes depends on scriptSig[input_index]
#   scriptSig[input_index] depends on sig
#   sig depends on z
# → z depends on z. There is no fixed point to compute without first
#   assuming a value for the very field you're trying to fill in.

This isn't a beginner's mistake — it's the correct first attempt, and writing it down is what makes the circularity impossible to miss. Every workable answer has to break the loop the same way: define "the message" as a transformation of the transaction that never includes the field you're about to write. Concretely, that means the scriptSig — for every input, not just the one you're signing — has to be replaced by something fixed and known before signing starts.

THE ONE-INPUT WRINKLE

A single transaction can have several inputs, each potentially spent by a different key, each requiring its own signature. That signature has to authorize the whole transaction's shape (so a third party can't swap out the outputs after the fact) while excluding the exact bytes of every scriptSig — including the other inputs', which haven't been signed yet either, and might not even be signed by the same party (multi-party transactions, precursors to CoinJoin, existed in Satoshi's original design intent). The fix has to handle N simultaneous, mutually-referencing blanks — not just one.

ARC 04 · WHY IT FAILS

Circularity isn't a performance problem — it's a non-existence problem

It's worth being precise about the failure mode here because it's a different species of failure than most of this course's "naive solution" sections. Usually a naive approach works but doesn't scale, or is correct but slow. Here, the naive approach doesn't even type-check: there is no function f such that z = f(tx) and tx (fully signed) is well-defined, because tx's definition depends on z through the signature.

Formally: let T be the space of possible fully-serialized transactions. Naive signing asks for a fixed point of tx = insert_sig(tx, ecdsa_sign(d, sha256d(tx))) — an equation of the form x = g(x) where g composes a cryptographic hash and a cryptographic signature. Both are designed to be one-way and unpredictable; that's the whole point of using them. A fixed point would mean you could predict your own signature's effect on its own hash — which is exactly the property a secure signature scheme must not have. The naive approach fails not by accident but by the correctness property the primitives are supposed to guarantee. There is no clever engineering fix within this framing — only a different framing.

THE ONLY WAY OUT

Stop trying to hash the transaction that will exist. Instead, deterministically construct a different, throwaway transaction — call it the sighash preimage — that (a) is fully computable before any signature exists, (b) captures everything you actually intend to authorize (which outputs, which other inputs, in what order), and (c) is standardized so every verifier reconstructs the identical bytes when checking the signature later. The scriptSig gets replaced by something else entirely for the purpose of this one computation. §5 derives exactly what that "something else" is.

ARC 05 · BETTER SOLUTION

Derive the legacy algorithm, one substitution at a time

Here is the actual algorithm Satoshi's original client implements (and every node still runs today for pre-SegWit inputs). It's four operations applied to a full copy of the transaction, then one hash. Step through it — each step exists to close one specific hole in the naive attempt.

Deriving SignatureHash() — legacy algorithm, step by stepSTEP-BY-STEP

Formally, for input index nIn and sighash type byte hashType:

algorithmlegacy SignatureHash(txTo, nIn, scriptCode, hashType)
txCopy = deep_copy(txTo)
for i in range(len(txCopy.vin)):
    txCopy.vin[i].scriptSig = b""                 // blank EVERY scriptSig first
txCopy.vin[nIn].scriptSig = scriptCode           // then substitute the one being signed

// hashType-specific transforms happen here — see §6

serialized = serialize(txCopy) + little_endian_u32(hashType)
return sha256(sha256(serialized))                  // z, the value ECDSA actually signs
SUBTLETY 1 · WHY BLANK EVERY SCRIPTSIG, NOT JUST YOURS

If you left other inputs' real scriptSigs in place, the hash you're signing would depend on signatures that don't exist yet (for inputs signed after yours) or that were computed by a different party (for multi-signer transactions) — reintroducing exactly the circularity from §4, just relocated to a different input. Blanking every scriptSig to an empty byte string makes the preimage independent of signing order and independent of who signs first, at the cost of needing a substitution step for the one input actually being authorized right now.

SUBTLETY 2 · WHY SUBSTITUTE scriptCode, NOT THE REAL scriptPubKey VERBATIM

scriptCode is usually just the scriptPubKey of the output being spent — but not always. If that script contains OP_CODESEPARATOR, the rule is: use only the portion of the script after the last OP_CODESEPARATOR that executed before this OP_CHECKSIG; everything before it, including the separator itself, is dropped. This lets a single scriptPubKey contain multiple independent signature checks, each committing to a different suffix of the script — a rarely-used but consensus-critical feature. (A related historical wrinkle: the reference client also runs FindAndDelete on the scriptCode, stripping any byte-for-byte occurrence of the signature itself, guarding against a signature that accidentally reappears as literal script data. BIP143 later dropped both quirks for witness inputs — see §7.)

ARC 06 · FLAGS, THE SINGLE BUG & MALLEABILITY

The algorithm works. It also ships three landmines.

§5's algorithm answers "what is the message?" completely for SIGHASH_ALL — commit to everything. But Satoshi's original design deliberately made commitment selectable, and that flexibility is where the landmines live.

The four SIGHASH flags

The low byte of hashType selects a base type; bit 0x80 is an independent modifier. Each one changes how txCopy is built in the "hashType-specific transforms" gap in §5's code:

FLAGVALUECOMMITS TOREAL USE
SIGHASH_ALL0x01Every input (by reference) and every output, in order. The default — "this exact transaction and nothing else."Virtually every transaction ever broadcast. The only sane default when you don't have a specific reason to weaken it.
SIGHASH_NONE0x02The inputs, but zero outputs — txCopy.vout is emptied entirely."Spend this coin, I don't care where it ends up." Almost never used alone — it lets anyone who sees the transaction in the mempool attach any outputs they like before it confirms and it still verifies. Its narrow legitimate use is in protocols where a later step fills in outputs that don't exist yet, with other commitments (multisig co-signers, a separate escrow layer) providing the actual safety.
SIGHASH_SINGLE0x03Only the output at the same index as the input being signed; all earlier outputs are truncated to value 0xFFFFFFFFFFFFFFFF and an empty script (kept as placeholders so indices still line up), later outputs are dropped entirely."I authorize spending this input only if my corresponding output is exactly this." Useful when several independent parties are each contributing one input and claiming one output at the same position — an early building block for what became CoinJoin-style construction, where nobody wants to authorize outputs they didn't propose.
SIGHASH_ANYONECANPAY0x80 (modifier)Reduces txCopy.vin to just the one input being signed — every other input is dropped from the preimage entirely, not merely blanked. "I authorize spending only my own input; I don't care what else gets bundled in." Combined with ALL, this is the classic crowdfunding / assurance-contract pattern: each contributor signs "my coin goes into this pot with these specific outputs," and anyone can later append more ANYONECANPAY-signed inputs from other contributors without invalidating earlier signatures — the pot only becomes a valid transaction once enough inputs accumulate to cover the outputs. It's also the basis of pre-segwit CoinJoin: independent participants each sign their own input under ANYONECANPAY, and a coordinator assembles everyone's inputs into one shared transaction that none of them could have produced alone.

The other two inputs-side rule that both NONE and SINGLE share, easy to miss: because neither type commits to (all of) the outputs, the reference implementation also zeroes the nSequence field of every input except the one being signed, inside the copy used for hashing. It's not a security feature — it simply reflects that those fields aren't meaningfully authorized under this flag anyway, so the real values can change post-signature without touching a hash that already ignores them.

Landmine 1: the SIGHASH_SINGLE bug

SIGHASH_SINGLE assumes the output at the same index as the input exists. Nothing stops a transaction from having more inputs than outputs — a 3-input, 1-output consolidation transaction is completely ordinary. Sign input index 2 under SIGHASH_SINGLE in that transaction, and "the output at the same index" doesn't exist. The original code's answer, verbatim in spirit:

C++ (original, ~2009)the exact bug
if (nIn >= txTo.vout.size())
{
    // out of range — instead of raising an error…
    return uint256(1);   // …return the fixed 32-byte value "1"
}

Read that literally: instead of failing loudly, SignatureHash() returns the constant 0x0000…0001 — a value that depends on nothing about the transaction: not the inputs, not the outputs, not the amounts, not even which transaction it is. Whatever key signs this ends up producing a valid ECDSA signature over a publicly-known, always-identical message. That signature carries zero information about what its signer believed they were authorizing — it is, cryptographically, a blank check that happens to look like a normal signature. §8's slider lets you trigger this exact condition and watch the fixed hash appear.

WHY IT CANNOT BE PATCHED — ONLY WORKED AROUND

This isn't a bug in a client's software you can update — it's part of the definition of when a signature is valid, which is a consensus rule: every full node must compute the exact same buggy digest for a legacy SIGHASH_SINGLE input with nIn ≥ vout.size(), or nodes would disagree about whether historical and future legacy transactions are valid — precisely the definition of a hard fork (chapter 10 covers why hard forks split chains). The bug is permanent for every non-segwit input, forever. What actually neutralized it was BIP143 (§7): new, witness-tagged inputs use a structurally different algorithm where the fixed-hash degenerate case cannot arise the same way, deployed as a soft fork that old nodes never had to validate the new rule to stay compatible.

Landmine 2: transaction malleability

This is the chapter's centerpiece, and it follows from a fact you already have: the transaction ID (txid) is SHA256d of the entire serialized transaction, including every real scriptSig — the thing §5 spent four paragraphs explaining you must exclude when computing the sighash, but which is very much present in the finished, broadcastable transaction. The scriptSig contains the signature. Ask the obvious question: can a third party — anyone who merely observes the transaction on the network, with no private key — alter the signature bytes without invalidating the signature? If yes, they've changed the txid without the sender's consent, cooperation, or even knowledge, and the "changed" transaction remains perfectly valid.

The answer is yes, for at least three independent reasons, all present in the original protocol:

  • ECDSA's own s ↔ n−s symmetry. Recall verification only checks that R = u1·G + u2·Q has x-coordinate r, where u1 = z·s⁻¹ mod n and u2 = r·s⁻¹ mod n. Flip s → n−s: both u1 and u2 negate mod n, so the resulting point is −R — and curve point negation only flips the y-coordinate, leaving x, and therefore r, unchanged. (r, n−s) verifies exactly as well as (r, s), for the identical message and key, with no private key required to compute it — just modular subtraction. §15's simulator does this arithmetic for real and shows both signatures verifying.
  • Non-canonical DER padding. The signature is DER-encoded before broadcast; DER requires an integer's encoding to have no unnecessary leading zero bytes, but before BIP66 (2015) made strict encoding a consensus rule, node software tolerated extra leading zero padding on r or s — different bytes, mathematically the same integers, same signature validity, different serialized transaction, different hash.
  • Extra or non-minimal pushdata. Historically, nothing enforced that scriptSig pushes use the shortest possible push opcode (a direct length byte vs. OP_PUSHDATA1 for the same short payload) or forbade harmless extra data on the stack — more bytes, same execution result, different hash.

Every one of these lets a third party — no cooperation from the sender needed — produce a different, equally valid serialization of the same economic transaction, with a different SHA256d and therefore a different txid. The transaction that confirms on-chain may not have the txid the sender's own wallet computed and displayed the moment it was broadcast.

TWO CONSEQUENCES THAT ACTUALLY MATTERED

1. Chains of unconfirmed transactions break. If transaction B spends an output of transaction A while A is still unconfirmed, B's input names A by txid. If a third party malleates A before it confirms, the confirmed version of A has a different txid than the one B references — B now points at a UTXO that will never exist, and is permanently invalid. This is precisely why naive multi-step protocols built on chained, not-yet-confirmed transactions — including the earliest ideas for payment channels — were unsafe before this was fixed; chapter 14 picks this up directly, because Lightning's whole channel-opening design had to be built around (and eventually benefit from) a fixed txid. 2. Mt. Gox. Publicly blamed almost entirely on malleability in 2014; §11 gives the accurate, less dramatic story.

FROM FLAG MATRIX TO ARCHITECTURE: BIP143'S NEW COMMITMENT

Every one of these flags still exists after BIP143 — the semantics Satoshi designed didn't change. What changes is how the commitment is computed. Instead of copying and mutating the whole transaction per input (§5's approach), BIP143 pre-hashes three reusable pieces once per transaction — hashPrevouts, hashSequence, hashOutputs — and every input's sighash preimage just references them. Zero flag semantics changed; the entire cost and malleability profile did. §8 builds this preimage byte by byte.

(b) The BIP143 preimage, assembled piece by piece

Ten fields, concatenated once, hashed once. The three fields marked "cached" are computed once per transaction, not once per input — that single change is what fixes the quadratic-hashing problem in §10.

Assembling the BIP143 sighash preimageSTEP-BY-STEP
algorithmBIP143 SegwitSignatureHash(txTo, nIn, scriptCode, amount, hashType)
hashPrevouts = anyonecanpay ? ZERO32 : sha256d(concat(vin[i].prevout for i in vin))
hashSequence = (anyonecanpay or none or single) ? ZERO32
                                             : sha256d(concat(vin[i].nSequence for i in vin))
hashOutputs  = (none or single) ?
                 (single and nIn < len(vout) ? sha256d(serialize(vout[nIn])) : ZERO32)
                 : sha256d(concat(serialize(o) for o in vout))

preimage = LE32(version) + hashPrevouts + hashSequence
         + outpoint(nIn) + varint(len(scriptCode)) + scriptCode
         + LE64(amount) + LE32(vin[nIn].nSequence)
         + hashOutputs + LE32(locktime) + LE32(hashType)

return sha256d(preimage)
WHAT CHANGED, PRECISELY, AND WHY IT MATTERS

The amount is now committed. Item 6 — the 8-byte value of the coin being spent — was never present in the legacy algorithm; a legacy signature says nothing about how much money is actually moving, which is why an offline signer had to fetch and trust the entire previous transaction just to know the fee it was paying. The witness is outside the txid entirely. A SegWit input's legacy-format scriptSig field, the one that feeds into the classic SHA256d(serialize(tx)) txid computation, is now always empty — the actual signature lives in a separate witness structure that a pre-SegWit node cannot even see, and that the txid computation ignores completely. Malleating the signature can no longer touch the txid, because the signature is no longer part of what the txid hashes. §15 proves this by construction.

ARC 09 · TRADEOFFS

Three sighash algorithms, honestly compared

Bitcoin has shipped three distinct sighash algorithms without ever removing the first. Legacy inputs (P2PKH, bare multisig, P2SH without witness) still use §5's algorithm today, unmodified, bug included.

Read the table as a lesson in incremental consensus engineering: BIP143 fixed the two flaws that were actually costing money and blocking applications (quadratic cost, malleability) while deliberately leaving the cross-input commitment gap and the flag semantics untouched — a smaller, safer soft fork. BIP341 closed the remaining gap four years later, once Schnorr made a bigger rewrite worthwhile anyway. Neither BIP touched the legacy algorithm itself, which is why §6's bug is not a historical footnote — it is live, exploitable-in-principle consensus code today, for anyone still constructing non-witness transactions.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Quadratic hashing was a real, exploitable cost — not a theoretical one

Under the legacy algorithm, verifying one signature means serializing a copy of the (almost) entire transaction and running it through SHA256d. Verifying all n inputs' signatures means doing that n times — and BIP143's own rationale is blunt about the consequence it measured on real hardware: a 1 MB block took roughly 2 seconds to verify on typical 2015 hardware, but a single 1 MB transaction engineered with 5,569 signature operations took around 25 seconds to verify — an order of magnitude worse, from one transaction, because each of its ~5,500 signature checks re-hashed a large fraction of the same megabyte. In the worst case, each byte of transaction data can be re-hashed once per sigop, so a 1 MB transaction can force on the order of tens of megabytes of actual SHA256 input — a single crafted transaction turning into a targeted, if modest, denial-of-service cost against every validating node.

SECURITY DIMENSION: WHY MALLEABILITY IS A SECURITY PROPERTY, NOT JUST AN ANNOYANCE

A txid that can change post-broadcast without the owner's consent breaks an implicit assumption nearly every higher layer relies on: "if I've seen this txid accepted into the mempool, I can safely reference it." That assumption underlies fee-bumping tools, wallet UIs that track "pending" payments by txid, exchange withdrawal-processing pipelines (§11), and — most consequentially — any protocol that pre-signs a transaction spending an output that doesn't exist on-chain yet. Removing malleability isn't a performance optimization; it converts a hash that identified "the money that moved" into a hash that also identifies "the specific bytes that authorized it," closing a class of confused-deputy bugs in exactly the systems that handle real value.

ARC 11 · REAL-WORLD INCIDENTS

Mt. Gox, the malleability flood, and what actually happened

Incident 1: the February 2014 malleability flood

In the weeks before Mt. Gox halted withdrawals, unknown actors systematically malleated large numbers of outstanding transactions across the network — flipping DER encodings and pushdata to change txids at scale, essentially demonstrating the bug in the wild rather than exploiting it for direct profit. Wallets and exchange backends that tracked "did my withdrawal confirm?" purely by the txid they had originally computed and stored started seeing those transactions appear to vanish, because a mutated version with a different txid was the one that actually confirmed. This was less an attack on any individual party's funds than a stress test of every system's assumption that a broadcast txid is stable — an assumption this entire chapter has now shown is false for legacy transactions.

Incident 2: Mt. Gox's own withdrawal bug — and the real root cause

Mt. Gox, then the largest Bitcoin exchange, suspended withdrawals in February 2014 and filed for bankruptcy days later, publicly attributing the collapse to transaction malleability: the claim was that attackers repeatedly exploited a mutated, differently-txid'd confirmation to trick Mt. Gox's own software into believing a withdrawal had failed, causing it to resend the funds — a real bug in Mt. Gox's specific implementation (trusting a client-observed txid instead of watching the UTXO actually being spent), not a flaw unique to Mt. Gox's wallets. Mt. Gox reported roughly 744,000 customer BTC and 100,000 of its own missing — at the time, worth several hundred million dollars.

The subsequent forensic analysis told a very different story. Independent researcher Kim Nilsson (WizSec), reconstructing Mt. Gox's actual wallet history from the blockchain and leaked internal data over the following year, found that the overwhelming majority of the missing coins had been leaking out of Mt. Gox's hot wallet gradually since as early as 2011 — years before malleability was ever publicly discussed — consistent with an ongoing, undetected external compromise rather than a malleability-driven run in the exchange's final weeks. Malleability-triggered double-processing of withdrawals accounted for only a small fraction of the total loss — on the order of a couple thousand BTC at most, a small percentage of the roughly 650,000 BTC that had actually disappeared over the preceding years. The bug this chapter describes is real, and Mt. Gox's withdrawal code really did mishandle it — but it was a minor contributor to a years-long theft, not its cause. The public narrative fixed on malleability anyway, in part because it was the explanation Mt. Gox itself offered, and in part because it was a real, technically legitimate protocol flaw that made a convenient, blame-deflecting story — a caution about accepting an incident's stated root cause at face value, one worth remembering the next time a postmortem arrives from the party under investigation.

Incident 3: the payment-channel dead end

Before malleability was fixed, the most natural design for a bidirectional payment channel — fund a 2-of-2 multisig with an on-chain transaction, then exchange a series of off-chain "commitment" transactions that each spend that funding output — was fundamentally broken, for exactly the reason §6 derives: every commitment transaction has to reference the funding transaction's txid as an input outpoint, but the funding transaction isn't confirmed yet (that's the whole point of building the channel off-chain first), and its txid can still be mutated by anyone who observes it on the network before confirmation. If that happens, every pre-signed commitment transaction becomes permanently invalid — its named input no longer exists under the confirmed txid — and the channel can't be closed cooperatively or unilaterally. This dead end sat unsolved from roughly 2013 designs onward until BIP143 shipped in 2017, which is precisely why Lightning Network's mainnet launch didn't happen until 2018: it needed a stable txid to build on, and chapter 14 shows exactly how Lightning's commitment-transaction design exploits that stability once it exists.

The precomputed-hash cache is the entire reason BIP143 is O(n) instead of O(n²) in a real node, not merely on a whiteboard:

C++interpreter.h — PrecomputedTransactionData (simplified, faithful to structure)
struct PrecomputedTransactionData
{
    uint256 m_prevouts_single_hash, m_sequences_single_hash,
            m_outputs_single_hash;                    // §8's hashPrevouts / hashSequence / hashOutputs
    bool m_bip143_segwit_ready = false;

    // Computed ONCE, in the constructor, before any input's SignatureHash() runs —
    // not recomputed per input. This is the single change that turns the whole
    // transaction's verification cost from O(n^2) into O(n).
    explicit PrecomputedTransactionData(const CTransaction& tx)
    {
        m_prevouts_single_hash  = GetPrevoutsSHA256(tx);
        m_sequences_single_hash = GetSequencesSHA256(tx);
        m_outputs_single_hash   = GetOutputsSHA256(tx);
        m_bip143_segwit_ready = true;
    }
};
C++interpreter.cpp — SignatureHashSchnorr / BIP143 path (simplified, faithful to structure)
uint256 SignatureHash(const CScript& scriptCode, const CTransaction& txTo,
                       unsigned int nIn, int nHashType,
                       const CAmount& amount, SigVersion sigversion,
                       const PrecomputedTransactionData* cache)
{
    if (sigversion == SigVersion::WITNESS_V0)
    {
        uint256 hashPrevouts, hashSequence, hashOutputs;
        bool anyoneCanPay = nHashType & SIGHASH_ANYONECANPAY;
        int baseType = nHashType & 0x1f;

        // Reuse the cache instead of re-serializing every input, every time.
        if (!anyoneCanPay)
            hashPrevouts = cache ? cache->m_prevouts_single_hash : GetPrevoutsSHA256(txTo);
        if (!anyoneCanPay && baseType != SIGHASH_SINGLE && baseType != SIGHASH_NONE)
            hashSequence = cache ? cache->m_sequences_single_hash : GetSequencesSHA256(txTo);
        if (baseType != SIGHASH_SINGLE && baseType != SIGHASH_NONE)
            hashOutputs = cache ? cache->m_outputs_single_hash : GetOutputsSHA256(txTo);
        else if (baseType == SIGHASH_SINGLE && nIn < txTo.vout.size())
            hashOutputs = SerializeHash(txTo.vout[nIn]);   // per-input — cheap, one output

        CHashWriter ss(SER_GETHASH, 0);
        ss << txTo.nVersion << hashPrevouts << hashSequence
           << txTo.vin[nIn].prevout << scriptCode << amount
           << txTo.vin[nIn].nSequence << hashOutputs
           << txTo.nLockTime << nHashType;
        return ss.GetHash();
    }
    // … legacy SigVersion::BASE path: §5's algorithm, byte-identical since 2009 …
}
WHY IT WAS BUILT THIS WAY

1. The cache lives on the transaction, not the input. Because hashPrevouts/hashSequence/hashOutputs depend only on transaction-wide data, not on which input is currently being checked, one PrecomputedTransactionData built at the start of validation serves every input's SignatureHash() call — the O(n²)→O(n) fix is a caching decision, not a new cryptographic idea. 2. The legacy path was never touched. Bitcoin Core still contains §5's exact 2009 algorithm, selected by SigVersion::BASE, because changing it would silently alter which historical signatures are valid — a hard fork by definition. New behavior only had to be additive — a new SigVersion enum value gated by whether the input is a witness program — which is precisely the soft-fork discipline chapter 10 formalizes. 3. Verification results are memoized too. sigcache.cpp's CSignatureCache means a signature checked once during mempool acceptance isn't re-verified from scratch when the same transaction is later included in a block — a second, orthogonal optimization layered on top of BIP143's algorithmic fix.
