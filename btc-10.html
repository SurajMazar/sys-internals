BITCOIN INTERNALS · CHAPTER 10

The P2P Protocol:
Messages on the Wire

Every block and transaction you have studied so far arrives at a node over a plain TCP socket, as a stream of bytes with no built-in framing. This chapter is about the 24 bytes that impose structure on that stream, the handshake two strangers run before trusting each other, and the announce-then-fetch discipline that lets ten thousand nodes gossip a multi-megabyte block without ten thousand copies crossing the wire. We will decode the wire format byte by byte, implement its checksums for real, and simulate headers-first sync exactly as Bitcoin Core runs it.

ARC 01 · THE PROBLEM

Strangers, a hostile network, and no coordinator

Every earlier chapter assumed a block or transaction simply arrives. Chapter 7 built the 80-byte header; chapter 8 validated it; chapter 9 mined it. None of that explains how bytes travel from the miner who found the block to the ten thousand other nodes that must agree it happened. That is a distributed systems problem with an unusually hostile threat model: any peer may be lying, slow, or actively adversarial, there is no central directory of participants, and the transport underneath — plain TCP — gives you only an ordered, reliable stream of bytes with no concept of "message" at all.

Unpack what a node needs, purely from first principles, before it can do anything useful:

  • Find peers. A brand-new node knows nobody. There is no DNS record for "the Bitcoin network" — only for a handful of volunteer-run seed servers, and even those can be censored, wrong, or gone.
  • Agree on a language before trusting data. Two nodes must establish which protocol version, which optional features (compact blocks? witness data? fee filtering?), and which network (mainnet? testnet? somebody's private regtest sandbox?) they are speaking, before either one interprets a single block or transaction from the other.
  • Carve a byte stream into messages. TCP delivers bytes, not messages. Both sides need a shared, unambiguous rule for "where does this message end and the next one begin" — get this wrong and a single dropped byte desynchronizes the connection forever.
  • Not waste bandwidth. A block can run past a megabyte and every node has, on average, dozens of peers. Push every object to every peer unconditionally and the network multiplies its own load by its average connectivity — for no benefit, since most peers already have most objects a few seconds after they appear anywhere.
  • Leak as little as possible about who originated what. The first node to announce a transaction is very often the transaction's own wallet. An observer well-positioned in the peer graph can turn "who announced this first" into "whose IP address created this transaction" — a direct privacy failure with no cryptographic fix, because the leak happens at the network layer, below anything a signature or a script can protect.

This chapter derives the wire protocol that solves all five: the 24-byte message envelope, the version/verack handshake, peer discovery via DNS seeds and address gossip, announce-then-fetch relay via inv/getdata, headers-first synchronization, BIP152 compact blocks, and the still-unresolved tension between efficient relay and transaction-origin privacy.

Satoshi's original client discovered peers through an IRC channel and a short hardcoded seed list; nearly every efficiency and privacy mechanism in this chapter was bolted on later, in response to a specific, dated failure. DEEP CONTEXT · WHY THERE WAS NO "V1" WIRE SPEC

Bitcoin has no independent protocol specification body — the wire format is whatever src/net_processing.cpp and src/protocol.h in Bitcoin Core implement, documented after the fact on the Bitcoin wiki and formalized incrementally through BIPs (Bitcoin Improvement Proposals). That means every mechanism in this chapter was added as a backward-compatible extension: old nodes that don't understand sendcmpct or wtxidrelay simply ignore the unfamiliar command name and keep working under the old rules. This additive-only discipline is why a 2011 node and a 2026 node can still complete a handshake — a constraint you will see shape nearly every design choice below.

ARC 03 · NAIVE SOLUTION

Attempt #1: push raw bytes over the socket

Derive the protocol the way an engineer would on day one, before knowing what breaks. Two nodes have a TCP connection. The obvious first move: whenever you have a new transaction or block, serialize it and write the bytes straight to the socket. No envelope, no handshake, no negotiation — just data.

pseudo-Cnaive_relay.c — the strawman, annotated
void on_new_block(Block *blk, int *peer_fds, int n_peers)
{
    uint8_t *raw = serialize_block(blk);      /* header + all txs, ~1-2 MB */
    size_t len = serialized_len(blk);

    for (int i = 0; i < n_peers; i++)
        write(peer_fds[i], raw, len);      /* fire and forget, to EVERY peer,
                                                whether or not they already have it */
}

void on_socket_readable(int fd)
{
    uint8_t buf[2 * 1024 * 1024];
    ssize_t n = read(fd, buf, sizeof(buf));   /* how much of "a message" did we just get? */
    try_parse_as_block(buf, n);          /* …or a tx? or garbage? no way to tell. */
}

This is not a joke architecture — every P2P system starts here, and it already gets the core idea right: peers relay data to each other with no central server. The bug is everything it left unstated. What tells the receiver where one object ends and the next begins? What tells it whether the bytes are even meant for this network — mainnet, testnet, someone's regtest sandbox — rather than an unrelated protocol that happens to share the port? What happens when the read splits a block across two read() calls, or a peer sends a transaction while a block is mid-transfer? And what stops the sender from blasting the same megabyte block at fifty peers who mostly already have it?

ARC 04 · WHY IT FAILS

Four failures, quantified

Each gap in §3 is not cosmetic — it is either a correctness bug or a bandwidth bill, and both are measurable:

  • No framing means one bad byte desynchronizes forever. TCP guarantees ordered, reliable delivery of a byte stream — it makes no promise about where your read() calls will cut it. If the receiver doesn't know a message's exact length in advance, it cannot tell "the block ended here and a transaction started right after" from "the block is still arriving." One misjudged boundary and every subsequent byte is misinterpreted, permanently, for that connection.
  • No network tag means silent cross-network corruption. Bitcoin runs at least four networks on the same default port pattern conceptually (mainnet, testnet3, signet, regtest) plus every altcoin fork derived from the same codebase. Without a tag identifying which one a message belongs to, a misconfigured or malicious peer can hand a testnet node mainnet-shaped bytes (or vice versa) and — absent a check — the node will attempt to parse and possibly act on data from a chain with entirely different validity rules.
  • No checksum means undetected corruption is indistinguishable from truth. TCP's own checksum is a 16-bit sum, designed to catch line noise, not deliberate or subtle corruption, and it never protects data once it has left the kernel's TCP stack (e.g. a bug in a middlebox, a proxy, or the node's own buffering). Silently accepting a subtly corrupted block is not a performance problem — it's a correctness problem that compounds, because bad data can build on bad data before anyone notices.
  • Push-to-everyone multiplies network load by average connectivity. A Bitcoin node maintains roughly 8 outbound and up to 125 inbound connections by default — call it a node with 20 active peers as a round number. If every peer pushes every new block unconditionally, a 1.5 MB block costs each node 20 × 1.5 MB = 30 MB of inbound traffic per block instead of the ~1.5 MB it actually needs — a 20× bandwidth multiplier purely from redundant delivery, before any compression scheme is even considered. At one block roughly every 10 minutes that is still a meaningful, permanent tax on every full node on Earth, and it gets strictly worse as the network grows more connected.
THE ARITHMETIC THAT FORCES A REDESIGN

Bandwidth wasted by naive push scales with the product of block size and average peer degree, both of which the protocol wants to grow over time (larger blocks as usage increases, more peers as the network strengthens against partition and eclipse attacks — chapter 11's fee market and this chapter's §11 eclipse discussion both assume a well-connected graph). Any fix that doesn't decouple "how many peers I have" from "how many full copies of each object cross the wire" does not scale. That is exactly what an announce-then-fetch protocol buys, and framing plus checksums plus a network tag are the prerequisites for building one safely.

ARC 05 · THE MESSAGE ENVELOPE

Fixing §4 with 24 fixed bytes

Every Bitcoin P2P message — version, tx, block, all of them — is preceded by the same fixed-size header. It is deliberately boring: four fields, each solving exactly one problem from §4. WHY DOUBLE-SHA256 FOR A MERE CHECKSUM

Bitcoin uses SHA-256 applied twice — SHA256(SHA256(x)) — everywhere it needs a hash: block headers (ch. 7), transaction ids (ch. 3), and here, the message checksum. The double application defends against a specific structural weakness of the Merkle–Damgård construction called length-extension: given only SHA256(x), an attacker can compute SHA256(x || suffix) for a suffix of their choosing, without ever knowing x, because a Merkle–Damgård hash's output doubles as its complete internal state for the next block. Hashing the hash again destroys that property at negligible extra cost — a few extra microseconds against a payload you were about to hash for other reasons anyway. It is not the cryptographic strength that changes (both are "SHA-256-strong" for typical purposes); it is that reusing SHA-256's raw output as if it were opaque would have been a latent, needless attack surface. Only the first 4 of the 32 resulting bytes are kept — this checksum only needs to catch accidental corruption, not resist deliberate forgery (a forger who controls the payload can always recompute a valid checksum; the checksum's job is bit-flip detection, not authentication — nothing here is signed).

ARC 06 · WHY THAT STILL HURTS

Framing solves parsing. It does not solve topology or privacy.

The envelope from §5 makes messages parseable and network-tagged. It says nothing about which peer to ask for a block, how many peers to ask, or when to tell your peers about a transaction you just created. Three costs remained — one purely architectural, one a real historical bug, one an open, unsolved privacy problem — and each motivated a specific mechanism covered in §8.

Cost 1: "blocks-first" sync could not tell a long chain from a short one

Before Bitcoin Core 0.10 (early 2015), a syncing node fetched blocks directly: ask a peer for block hashes via getblocks, then getdata each one, entirely from whichever peer you happened to be talking to. There was no cheap way to compare that peer's chain against alternatives before paying the full download cost of a multi-megabyte block chain, because the only proxy for "how much work is behind this chain" was the full blocks themselves. Two consequences, both severe: a single unresponsive or adversarial peer could stall an entire initial sync — there was no parallel fallback — and a node had no defense against being fed a short, low-work chain first while a longer one existed elsewhere, other than downloading both in full and comparing. §11 covers the incident and the fix (headers-first, §8) in detail.

Cost 2: announcing a transaction the instant you create it leaks your IP

The most bandwidth-efficient thing a wallet could do is announce a new transaction to every peer immediately. It is also close to the most privacy-hostile thing it could do: whichever peer is directly connected to the transaction's true origin will, on average, see and relay it measurably earlier — and more consistently — than peers connected only indirectly. An adversary who runs many listening nodes spread across the network and simply records first-arrival timestamps can use that timing skew to guess, with real accuracy, which IP address originated which transaction. Biryukov, Khovratovich & Pustogarov's 2014 paper "Deanonymisation of Clients in Bitcoin P2P Network" demonstrated exactly this against the network as it then existed. §8 covers the trickle-delay mitigation Bitcoin shipped, and §11 covers why it is only a partial fix.

Cost 3: naive relay wastes bandwidth even after framing is fixed

Framing tells a receiver where a message ends; it does not stop a sender from pushing a full block to a peer that already has it. The 20× redundancy multiplier from §4 survives entirely intact even with a perfect envelope — the envelope only fixed parsing, not topology-awareness.

THE PATTERN TO NOTICE

Every mechanism in §8 exists because "make it parseable" and "make it efficient and private" are different problems solved at different layers: the envelope is a syntax layer; peer discovery, announce-then-fetch, headers-first sync, and relay-timing privacy are all policy layers built on top of a already-solved syntax. This separation — wire format stable since 2009, policy evolving continuously via BIPs — is precisely what let Bitcoin add compact blocks (2016) and fee filtering (2016) without touching a single byte of the 24-byte header you just built.

Notice the shape: discovery finds candidates, the handshake establishes a mutually-understood feature set before any application data is trusted, and steady-state relay is entirely announce-then-fetch — never push-unsolicited, except where a peer has explicitly opted in (high-bandwidth compact blocks, §8d). A node that receives a message beginning with the wrong magic for its configured network drops the connection immediately, before spending a single CPU cycle interpreting the payload as anything meaningful. This buys three things simultaneously: a misconfigured node that accidentally dials a peer on the wrong network fails fast and loudly instead of feeding foreign-chain bytes into validation logic that assumes a different genesis block and different consensus rules; a firewall or IDS can trivially fingerprint and separate the four networks' traffic by a fixed 4-byte prefix; and — subtly — it means the magic bytes function as a very cheap first-line filter against random port-scanning noise and unrelated protocols that happen to connect to the same TCP port.

THE NONCE'S REAL JOB: CATCHING YOURSELF

Each side's version message carries a random 64-bit nonce. Every outbound connection attempt a node makes remembers the nonce it sent; if a version message ever arrives carrying a nonce the node itself generated, that connection is talking to itself — usually via a NAT loopback, a misconfigured port forward, or a network topology that routed an outbound attempt back to the same process. The node disconnects immediately. This is the entire purpose of the nonce: not authentication (nothing here proves identity — see §9), just detecting a degenerate accidental self-connection before wasting a peer slot talking to yourself.

A WIRE QUIRK WORTH KNOWING

Nearly every multi-byte field in the protocol is little-endian. The addr_recv/addr_from fields inside version are the exception: their port field is big-endian (network byte order), a fossil of directly serializing a BSD sockaddr_in struct in 2009. §15's byte-by-byte decoder flags this explicitly — it is exactly the kind of off-by-endianness bug that breaks a hand-rolled parser on the first real message.

(c) Peer discovery: DNS seeds, fixed seeds, and the address manager

A node with zero peers bootstraps in a fixed order. DNS seeds first: Bitcoin Core's mainnet chainparams.cpp hardcodes about a dozen seed hostnames run by volunteer developers (seed.bitcoin.sipa.be, dnsseed.bluematt.me, seed.bitcoinstats.com, and others) — an ordinary DNS A-record query against any of them returns a handful of currently-reachable node IPs, selected by the seed operator's own crawler. If DNS resolution itself is unavailable or censored, the client falls back to a small hardcoded list of fixed seed nodes — IP:port pairs frozen into the binary at release time, stale by construction but enough to bootstrap one connection and start real discovery from there.

Once connected to even one peer, a node asks for more via getaddr and receives addr (or the BIP155 addrv2, which adds Tor v3 and I2P address formats) — vectors of (timestamp, services, IP, port) that get folded into the address manager: two hash tables Bitcoin Core calls new (addresses heard about but never successfully connected to) and tried (addresses that have accepted a connection at least once). An address's bucket is computed from a keyed hash of its own IP, its source peer's IP, and a random secret generated once per node — the same keyed-hash idea you will meet again in §8(d)'s compact blocks, there to stop precomputation attacks; here, to stop an attacker from predicting or steering which bucket their addresses land in. (d) Compact blocks (BIP152): short IDs from a keyed hash

Once two peers are synced to the same tip, relaying a whole new block again is wasteful for a different reason than §4's naive push: the receiver almost certainly already has most of the block's transactions in its mempool — they were relayed individually, minutes earlier, exactly as designed. BIP152 exploits this: instead of sending full transactions, the sender computes a short 6-byte identifier for each transaction and sends those; the receiver looks each one up in its own mempool and reconstructs the block locally, falling back to a targeted re-request only for the few it's missing.

The short ID is SipHash-2-4(k0, k1, txid) truncated to 48 bits, where the 128-bit SipHash key (k0, k1) is derived per connection, per block as SHA256(header || nonce) — a fresh nonce chosen by whichever side is sending the compact block. This is not incidental: if every connection reused the same fixed hash function, an attacker could precompute transactions whose short IDs collide with real ones — cheaply, offline, once — and use the collision to make a node reconstruct the wrong transaction into a block it is about to accept. A key that changes every block and every connection makes that precomputation worthless: the attacker cannot know the key until the exact message they'd need to attack has already been sent. HIGH-BANDWIDTH VS LOW-BANDWIDTH MODE

During sendcmpct negotiation each side can request to be the other's high-bandwidth peer (BIP152 recommends capping this at 3 peers). To a high-bandwidth peer, a node sends a cmpctblock completely unsolicited the instant it validates a new block — lowest possible latency, at the cost of receiving it redundantly from up to three peers. Everyone else is low-bandwidth: they get a normal inv announcement first and must getdata the cmpctblock explicitly — one extra round trip, but zero redundant bytes. When reconstruction still misses transactions (evicted from mempool, arrived out of order, or — vanishingly rarely, at roughly 1-in-2⁴⁸ per transaction — a genuine short-ID collision), the receiver sends getblocktxn naming the missing indexes and gets back blocktxn with exactly those transactions in full, avoiding a full block re-fetch.

Read this table as a proof by exhaustion, same as every prior chapter's tradeoffs section: there is no mechanism here that is simply better in every dimension than its predecessor — headers-first is strictly better at sync robustness but strictly more complex to implement correctly; high-bandwidth compact blocks trade bytes for latency and low-bandwidth trades it back. The one asymmetry worth remembering: Bitcoin Core has consistently chosen the option that is simpler to reason about under adversarial conditions over the option that is marginally more bandwidth- or latency-efficient — which is exactly why Dandelion++, despite published, peer-reviewed privacy gains, remains outside Core (§11 revisits this decision directly).

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Bandwidth, attack cost, and the numbers behind both

Three quantifiable properties, in order of how directly they trace back to mechanisms in §8:

  • Relay bandwidth collapses with each layer of the stack. §4 computed a 20× multiplier for naive push at 20 peers. inv/getdata collapses that to roughly 1× the object's real size plus 36 bytes × peer count of announcement overhead (4-byte type + 32-byte hash per inv entry) — for a 1.5 MB block across 20 peers, about 720 bytes of invs against a single ~1.5 MB fetch, a >95% reduction versus naive push before compact blocks even enter the picture. Compact blocks then shrink the ~1.5 MB itself to roughly 15–20 KB in the common case (§8d's slider makes the arithmetic explicit) — combined, a multi-megabyte, twenty-peer redundant broadcast becomes a double-digit-kilobyte transfer to most peers.
  • Eclipse attack cost is bounded by outbound diversity, not brute force. Heilman et al. (2015) showed that an attacker who could fill enough of a victim's tried table with attacker-controlled addresses — across the victim's connection churn or a restart — could arrange for all of the victim's limited outbound slots to land on attacker nodes, isolating it from honest network view entirely (§11 covers the mechanism in detail). Post-fix, the attacker's cost is no longer "own a few IPs" but "own or route through enough distinct address groups (roughly, distinct /16 network ranges) to dominate and win the race against periodic feeler connections and anchor-connection persistence" — a materially higher, ongoing cost rather than a one-time setup.
  • Header-spam DoS is bounded by proof-of-work cost, not message count. A peer cannot cheaply flood a node with a long fake header chain to exhaust memory or CPU, because every header must carry valid proof-of-work for its claimed difficulty (ch. 7-9) — producing even a short low-difficulty-looking header chain that could plausibly extend anywhere costs real hashes. Core additionally enforces a minimum-chain-work threshold and a headers-sync timeout, disconnecting peers that fail to make sync progress, bounding the damage a single slow or hostile peer can do to one connection slot rather than the whole node.

ARC 11 · REAL-WORLD INCIDENTS

Three episodes that rewrote this chapter's protocol

Incident 1: the blocks-first stalling pathology (pre-2015)

Root cause, precisely: initial block download asked one peer for block hashes and fetched blocks from whichever peer answered, with no cheap proof of that peer's chain quality available before paying the full download cost. A stalling or malicious peer that simply stopped responding mid-sync could leave a node stuck indefinitely, and — separately — there was no efficient way to detect that a different peer was offering a chain with strictly more accumulated proof-of-work until both had been downloaded far enough to compare. The fix, landed as part of the Bitcoin Core 0.10 release cycle (2014–2015) alongside BIP130's sendheaders, restructured sync into headers-first: fetch the cheap 80-byte header chain from many peers in parallel, validate cumulative proof-of-work on headers alone, commit to the best chain, and only then fetch blocks — in parallel windows across multiple peers, with per-peer stall timeouts that reassign a stuck block to a different peer automatically. §15's sync visualizer runs exactly this sequence.

Incident 2: eclipse attacks on the address manager (Heilman et al., 2015)

"Eclipse Attacks on Bitcoin's Peer-to-Peer Network" (Heilman, Kosba, Goldberg & Saxena) demonstrated that an attacker controlling enough IP addresses could, over time and across a victim's restarts, insert enough attacker-controlled entries into the victim's tried table that — the next time the victim needed to make its 8 outbound connections — every one of them landed on an attacker node, giving the attacker complete control over the victim's view of the network: which blocks and transactions it sees, in what order, or whether it sees new ones at all. The root cause was addrman's original bucket-selection and eviction logic making tried-table takeover cheaper than intended, combined with there being no mechanism to periodically re-test new addresses that weren't currently being chosen. The response, phased in over several Core releases: more restrictive, network-group-aware bucket selection so a single attacker-controlled IP range can't dominate; periodic low-priority feeler connections that quietly test random new-table addresses and promote good ones, diluting an attacker's grip over time; and, from Core 0.21 (2020), anchor connections — a node persists a couple of its current outbound peers across a restart specifically so an attacker cannot rely on a restart handing them a clean slate of connections to capture.

Incident 3: transaction-relay deanonymization (Biryukov, Khovratovich & Pustogarov, 2014)

Already introduced in §6: an adversary running many listening "supernodes" spread across the peer graph recorded which of their connections first delivered each new transaction, and showed that first-arrival timing correlates strongly enough with true origin to deanonymize a meaningful fraction of transactions in practice — entirely at the network layer, with no cryptographic weakness involved anywhere in the transaction itself. The direct response Bitcoin Core shipped was randomized, Poisson-distributed per-peer relay delay (trickling), which blurs — but does not eliminate — the timing signal, because a sufficiently well-positioned, patient observer can still average away random delay given enough repeated observations. Dandelion (Fanti & Viswanath, 2017) and its hardened successor Dandelion++ (Fanti et al., 2018) propose a structurally different fix — §9's tradeoff table and §12's interview questions come back to exactly why Bitcoin Core has, as of this writing, still not merged it.

First, the header struct itself — the four fields from §8(a), simplified from Core's actual class but faithful to layout and field order:

C++protocol.h — CMessageHeader
class CMessageHeader {
public:
    static constexpr size_t MESSAGE_SIZE_SIZE = 4;
    static constexpr size_t COMMAND_SIZE      = 12;
    static constexpr size_t CHECKSUM_SIZE     = 4;
    static constexpr size_t MESSAGE_START_SIZE = 4;

    uint8_t  pchMessageStart[MESSAGE_START_SIZE];  // magic — set once from chainparams
    char     pchCommand[COMMAND_SIZE];           // NUL-padded ASCII, e.g. "version\0\0\0\0\0"
    uint32_t nMessageSize;                       // payload length, host order in memory
    uint8_t  pchChecksum[CHECKSUM_SIZE];         // first 4 bytes of SHA256(SHA256(payload))

    bool IsCommandValid() const;  // rejects non-NUL bytes after the first NUL
};

Next, the version-message handler — the shape of the self-connection check and the services/height it records, simplified from net_processing.cpp:

C++net_processing.cpp — ProcessMessage(), case NetMsgType::VERSION
if (msg_type == NetMsgType::VERSION) {
    if (pfrom.nVersion != 0) {
        // Peer sent version twice on one connection — protocol violation, disconnect.
        pfrom.fDisconnect = true;
        return;
    }

    int nVersion; uint64_t nServices; int64_t nTime;
    CAddress addrMe, addrFrom; uint64_t nNonce = 1;
    vRecv >> nVersion >> nServices >> nTime >> addrMe;
    if (nVersion >= 106) {
        vRecv >> addrFrom >> nNonce;
        // Self-connection check: did I generate this exact nonce myself?
        if (nNonce != 0 && connman.CheckIncomingNonce(nNonce)) {
            LogPrintf("connected to self — disconnecting\n");
            pfrom.fDisconnect = true;
            return;
        }
    }
    std::string strSubVer; vRecv >> strSubVer;      // user agent, e.g. "/Satoshi:26.0.0/"
    int nStartingHeight = -1; vRecv >> nStartingHeight;

    pfrom.nServices = nServices;
    pfrom.nVersion  = std::min(nVersion, PROTOCOL_VERSION);
    // … negotiate fRelay, feature flags, then reply:
    connman.PushMessage(&pfrom, CNetMsgMaker(pfrom.GetCommonVersion()).Make(NetMsgType::VERACK));
}

Finally, the compact-block short-ID computation — the concrete SipHash call from §8(d):

C++blockencodings.cpp — GetShortID()
CBlockHeaderAndShortTxIDs::CBlockHeaderAndShortTxIDs(const CBlock& block) {
    uint64_t shorttxidk0, shorttxidk1;
    CSHA256 hasher;
    hasher.Write(block.GetBlockHeader());
    hasher.Write(nonce);                 // fresh per compact block — see §8(d)
    uint256 shorttxidhash = hasher.Finalize();
    shorttxidk0 = shorttxidhash.GetUint64(0);
    shorttxidk1 = shorttxidhash.GetUint64(1);

    for (const auto& tx : block.vtx)
        shorttxids.push_back(GetShortID(shorttxidk0, shorttxidk1, tx->GetWitnessHash()));
}

uint64_t GetShortID(uint64_t k0, uint64_t k1, const uint256& txhash) {
    return SipHashUint256(k0, k1, txhash) & 0xffffffffffff;   // truncate to 48 bits
}
WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. Reuse the wire's own primitives for security properties. The compact-block key is derived with plain SHA-256 — the same primitive already used for hashing every block and transaction — rather than introducing a new cryptographic dependency. SipHash itself is the one departure, and it earns its place narrowly: it is a keyed pseudorandom function designed for exactly this "short authenticated tag, fast, resistant to hash-flooding" niche, unlike SHA-256, which is deliberately slow relative to SipHash and would make computing thousands of short IDs per block needlessly expensive. 2. Every new feature negotiates, nothing is assumed. sendcmpct, sendheaders, wtxidrelay, and feefilter are all no-ops to a peer that doesn't recognize them — Core never assumes a peer supports a feature without that peer opting in first. This is the same additive-only discipline from §2's "why there was no v1 spec" callout, applied at the message level instead of the header level.
