APPLIED CRYPTOGRAPHY · CHAPTER 10

Padding Oracles &
Real RSA/CBC Attacks

Chapter 5 built CBC mode and mentioned, in passing, that it "sets up a padding-oracle vulnerability class explored later." This is later. A padding oracle is one of the strangest results in applied cryptography: a server that leaks a single bit — "was this ciphertext's padding well-formed, yes or no?" — is enough, with no knowledge of the key, to decrypt the entire ciphertext, one byte at a time, in time linear in its length. You will derive Serge Vaudenay's 2002 attack from first principles, implement a genuine CBC cipher and a genuine padding oracle in JavaScript, and then run the real byte-recovery algorithm against your own oracle — no shortcuts, no peeking at the plaintext — until it reveals every byte your "server" was supposedly keeping secret.

ARC 01 · THE PROBLEM

A single bit of information should not be enough to break a cipher

Here is the setup. A server holds a symmetric key K. A client sends it a ciphertext, encrypted with CBC mode and padded with PKCS#7 padding. The server decrypts, checks the padding is well-formed, and — this is the entire vulnerability — tells the client, in some observable way, whether the padding was valid. Maybe it's an explicit error message ("bad padding" vs "bad MAC"). Maybe it's an HTTP 500 vs 400. Maybe it's nothing more than a few microseconds of extra processing time. Whatever form it takes, that single bit is called a padding oracle, and the question this chapter answers is: what is the worst thing an attacker can do with access to one, assuming they can query it as many times as they want and never see the key or the plaintext directly?

The intuitive answer most engineers give is "not much — it's one bit, and the plaintext is 128 or more bits per block." That intuition is catastrophically wrong, and understanding exactly why is the point of this chapter. The honest answer, proven constructively below, is: the attacker recovers the entire plaintext, byte by byte, using on the order of 256 queries per byte — polynomial in the ciphertext length, with no dependence at all on the key size. A padding oracle doesn't weaken AES-256 to AES-200; it makes key size irrelevant. The lock on the door doesn't matter if the house tells you, one digit at a time, whether each guess of the combination was "close."

WHY THIS IS THE HARDEST CHAPTER SO FAR TO GET RIGHT IN PRODUCTION

Every other failure in this course (weak RC4 keystreams, ECB's structure leak, HMAC forgery without the key) is something you can point at in the ciphertext or the protocol. A padding oracle is different: the cryptography can be flawless — real AES, a real random IV, a correctly implemented PKCS#7 check — and the vulnerability lives entirely in how the error is communicated. That is why this bug class kept reappearing for two decades (1998 → 2002 → 2010 → 2013 → 2014 → 2017) against different protocols, different languages, and different companies: it isn't a bug in a cipher, it's a bug in an interface.

ARC 02 · HISTORICAL CONTEXT

Twenty years of the same bit leaking in new places

The padding-oracle story is unusual in cryptography for how repeatable it is. The same underlying mathematical weakness — an adaptive chosen-ciphertext oracle over a padding check — was rediscovered, patched, and rediscovered again in new guises for almost two decades. DEEP CONTEXT · WHY VAUDENAY'S PAPER WAS A SHOCK IN 2002

Vaudenay's CRYPTO 2002 paper, "Security Flaws Induced by CBC Padding — Applications to SSL, IPSEC, WTLS…", was startling because CBC mode itself was — and remains — considered secure under the standard IND-CPA definition. Vaudenay's insight was that real deployments don't just encrypt — they also decrypt attacker-supplied ciphertexts and react differently based on what they find, which is a strictly stronger attack model (chosen-ciphertext) that the IND-CPA proof never covered. The lesson generalizes far beyond CBC: a primitive proved secure under one attacker model can fail completely once you build a system that gives the attacker a slightly stronger one — which is exactly why chapter 7's AEAD definitions (IND-CCA2-flavored) were designed to close this gap by construction rather than by discipline.

ARC 03 · NAIVE SOLUTION

Attempt #1: a perfectly reasonable-looking decrypt endpoint

Derive the vulnerability the way a real engineer stumbles into it: by writing an endpoint that decrypts an encrypted session token and reports what went wrong, because that's what good error handling looks like everywhere else in software.

JavaTokenController.java — looks defensible, isn't
byte[] decryptToken(byte[] ivAndCiphertext) {
    try {
        Cipher cipher = Cipher.getInstance("AES/CBC/PKCS5Padding");
        cipher.init(Cipher.DECRYPT_MODE, sessionKey, extractIv(ivAndCiphertext));
        byte[] plaintext = cipher.doFinal(extractCiphertext(ivAndCiphertext));
        byte[] mac = extractMac(plaintext);            // MAC embedded after decrypting — MAC-then-Encrypt
        if (!Hmac.verify(macKey, plaintext, mac))
            throw new SecurityException("bad MAC");
        return plaintext;
    } catch (BadPaddingException e) {
        respond(400, "invalid padding");        // ← distinct message #1
    } catch (SecurityException e) {
        respond(401, "authentication failed");  // ← distinct message #2
    }
}

This code is idiomatic, readable, and shipped in production systems for over a decade — Java's own BadPaddingException, .NET's CryptographicException, and OpenSSL's distinguishable error codes all made this pattern the path of least resistance, not an exotic mistake. It even looks like it's doing the right thing: decrypt, then verify a MAC, then reject on failure. The problem is the two catch blocks. Whatever the client can observe that differs between them — the message text, the HTTP status, the response size, or (as chapter 6 will remind you) even which order the checks run in — is a padding oracle, and section 4 shows exactly how little of a difference is required.

ARC 04 · WHY IT FAILS

From one bit to the whole plaintext: the arithmetic

Recall PKCS#7: if a block cipher's block size is n bytes, padding appends p bytes each holding the value p, where 1 ≤ p ≤ n. A block 03 03 03 at the end (for n=8: .. .. .. .. .. 03 03 03) is valid padding of length 3; almost any other trailing byte pattern is not. CBC decryption is Pi = DK(Ci) ⊕ Ci-1 — the plaintext block is the block cipher's raw decryption of the ciphertext block, XORed with the previous ciphertext block (or the IV, for the first block).

Now the key move: the attacker doesn't need to know Ci-1 is fixed. If the oracle will decrypt any two blocks the attacker sends it, the attacker can substitute their own chosen byte string A in place of Ci-1 and ask: does DK(Ci) ⊕ A have valid padding? Define the intermediate value Ii = DK(Ci) — the raw block-cipher decryption, before any XOR. The oracle answers a question about Ii ⊕ A, and because the attacker chose every byte of A, they can force the last byte of that XOR to equal 1 by trying all 256 possible values of A[n-1] until the oracle says "valid." The value of A[n-1] that worked tells you Ii[n-1] = A[n-1] ⊕ 1 — one intermediate byte recovered, with at most 256 oracle queries and no key. Once you know one intermediate byte, you can force the padding to be 02 02, then 03 03 03, and so on, recovering the block right to left.

THE NUMBERS THAT SHOULD ALARM YOU

Per byte: at most 256 oracle queries, expected ~128. Per block of n bytes (16 for AES, 8 for legacy DES/3DES): at most 256n queries, expected ~128n. For a full ciphertext of m blocks: at most 256nm queries — linear in the message length, with zero dependence on whether the key is AES-128 or AES-256. A 32-byte AES-encrypted session cookie (2 blocks) costs at most 256 × 16 × 2 = 8,192 queries, typically half that. Compare that to a brute-force key search over 2128 keys — the padding oracle doesn't attack the key at all, it routes around it entirely. This is why Vaudenay's result reads less like a cryptanalysis paper and more like a lesson in system design: the strength of the 128-bit key was never the bottleneck — the interface was.

ARC 06 · WHY THAT STILL LEAKS

Timing survives because computers do variable amounts of work

Uniform error text and uniform status codes attack the content of the response. They do nothing about the time it took to produce it, and time is a much harder channel to close than it looks, for reasons rooted in how MAC-then-encrypt style constructions are actually implemented:

  • The code paths are genuinely different lengths. In the naive handler, an invalid padding length causes an exception on the very first check; an invalid MAC requires decrypting the whole block, stripping the (valid-looking) padding, then running a full HMAC computation over the recovered plaintext. Those are measurably different amounts of CPU work, even with identical error messages.
  • Networks are noisy, but noise averages out. A single request's timing is useless — network jitter dwarfs a microsecond CPU difference. But an attacker who can send millions of requests (trivial for a script, or for JavaScript running in a victim's browser against their own TLS session) can average away the jitter and recover a timing signal measured in nanoseconds. This is exactly the technique chapter 15 formalizes as a general side-channel methodology.
  • "Constant time" is not a property of intent, it's a property of machine code. A loop written to "always do the same work" can still branch differently after compiler optimization, hit different cache lines depending on secret-dependent array indices, or get a different CPU branch-predictor outcome. The 2013 Lucky13 attack (CVE-2013-0169, Al Fardan & Paterson) exploited exactly this: OpenSSL's own attempt at a uniform-time CBC MAC check leaked a few dozen clock cycles depending on the (secret) padding length, and that was enough, over enough TLS sessions, to fully decrypt CBC-protected traffic.
THE ASYMMETRY THAT MAKES THIS EXPENSIVE TO DEFEND

The defender must close every channel — text, status, size, timing, cache behavior, even TCP retransmission patterns — and must keep it closed through every future refactor, dependency upgrade, and compiler update. The attacker needs exactly one that a defender missed. This asymmetry, not any weakness in AES itself, is the actual cost center of choosing MAC-then-encrypt-with-CBC as an architecture: you are signing up for an indefinite, adversarial code-review burden on a code path most teams treat as plumbing.

THE RECOMMENDATION THIS CHAPTER ACTUALLY ENDS ON

If you are writing new code in 2026: use AES-GCM or ChaCha20-Poly1305 (chapter 7) and never implement a padding check on attacker-supplied ciphertext yourself. AEAD removes the entire question — there is no separate "is the padding valid" decision to leak, because the authentication tag is checked in one constant-time comparison before a single byte of plaintext is released, and a failed check yields exactly one outcome: reject, with no distinguishable reason. If you are stuck maintaining a legacy CBC-based protocol for interoperability, the correct discipline is Encrypt-then-MAC (verify the MAC over the ciphertext, in constant time, and refuse to even attempt decryption — let alone a padding check — if it fails), exactly as RFC 7366 retrofitted onto TLS's CBC suites in 2014, four years too late for the systems already breached.

ARC 08 · INTERNAL IMPLEMENTATION

The Vaudenay algorithm, byte by byte, for real

This section is the mechanism at the level you'd need to implement it — which is exactly what the simulator in §15 does, using the identical algorithm described here, in real JavaScript, against a real (if pedagogically simplified) block cipher.

(a) The byte layout you are attacking

A CBC ciphertext is IV, C1, C2, …, Cm. To attack block Ci in isolation, the attacker only ever needs two blocks at a time: an attacker-controlled block A standing in for "the previous ciphertext block," and the real target block Ci. The oracle computes DK(Ci) ⊕ A and reports only whether the result ends in valid PKCS#7 padding — never the bytes themselves.

WHY THE ALGORITHM PROCESSES BYTES LAST-TO-FIRST

PKCS#7 padding's defining property is that the value of the last byte tells you how many bytes at the end must share that value. That gives the attacker a one-byte lever: force everything after position p to already read as some target padding value using bytes you've already solved, then brute-force just position p against a target padding value one larger than last time. Going first-to-last would give you no such lever — you'd need to know the padding length before you could even ask a meaningful question, and the padding length is exactly what you don't know yet for a full, unpadded interior block. The one edge case — the very first byte you attack, at the true last position, where a coincidental 02 02 can masquerade as the genuine 01 — is exactly what step 6 of the deck above handles by corrupting a neighboring byte and re-querying.

WHAT "SECURITY" MEANS HERE, PRECISELY

Under the standard IND-CPA and even IND-CCA1 definitions, CBC with a strong block cipher is exactly as secure as the underlying cipher — there is no flaw in the mathematics of encryption itself. The vulnerability is entirely in the threat model mismatch: real servers offer an adaptive chosen-ciphertext decryption oracle (IND-CCA2 territory) that the CPA proof never accounted for. This is why the numbers above look absurd next to a "256-bit key is secure" claim — both statements are true simultaneously, about two different attacker capabilities. Chapter 15 will generalize this into a broader principle: a system's real security level is the minimum over every observable channel, not the maximum over the strongest primitive it uses.

ARC 11 · REAL-WORLD INCIDENTS

The same bit, leaked six different ways, over twenty years

Bleichenbacher's Million-Message Attack (1998) and ROBOT (2017)

Daniel Bleichenbacher's 1998 attack against RSA PKCS#1 v1.5 padding (used in SSL's RSA key exchange) is the RSA sibling of this chapter's CBC attack: a server that reveals whether a decrypted RSA ciphertext begins with the required 0x00 0x02 padding prefix gives an attacker an oracle that, through a clever multiplicative search over the ciphertext (Bleichenbacher's core mathematical contribution), lets them decrypt an RSA-encrypted secret — such as a TLS pre-master secret — without ever factoring the modulus or learning the private key. The original attack needed roughly a million adaptive queries; later refinements cut that dramatically. Nineteen years later, ROBOT (Böck, Somorovsky & Young, 2017; multiple CVEs including issues in F5 BIG-IP and Citrix products) found the identical class of oracle still present in production TLS stacks from major vendors — not because Bleichenbacher's math was forgotten, but because each implementation's specific error handling reintroduced a distinguishable signal, one line of C at a time, decades after the fix was well understood.

Vaudenay's CBC Padding Oracle (2002) and Canvel's Timing Refinement (2003)

Vaudenay's CRYPTO 2002 paper first demonstrated the exact attack this chapter implements, against SSL, IPsec, and WTLS implementations of the day. Within a year, Brice Canvel and colleagues ("Password Interception in a SSL/TLS Channel," CRYPTO 2003) showed the attack didn't even need a distinguishable error message — a measurable timing difference between "padding failed immediately" and "padding passed, now computing a MAC" was enough over a real network, foreshadowing Lucky13 by a decade.

The ASP.NET Padding Oracle: CVE-2010-3332 / MS10-070

In 2010, Thai Duong and Juliano Rizzo released POET (Padding Oracle Exploitation Tool) and demonstrated it live against ASP.NET, which encrypted ViewState and other tokens with CBC and returned a distinguishable "yellow screen of death" cryptographic exception versus a generic error page. The practical impact went far beyond decrypting a cookie: because ASP.NET used the same padding oracle to decrypt arbitrary attacker-chosen ciphertext, the researchers chained it into requesting arbitrary files from the server — including web.config, which could contain further secrets — turning a padding bug into full application compromise. Microsoft's emergency out-of-band patch, MS10-070, is a rare case of a purely cryptographic-interface bug forcing an unscheduled security release.

Lucky13 (CVE-2013-0169) and POODLE (CVE-2014-3566)

Lucky13 (Nadhem Al Fardan and Kenny Paterson, 2013) targeted TLS's CBC ciphersuites after a decade of "fixes": by then, error messages were uniform and gross timing differences were patched, but the MAC computation itself still took a few dozen CPU cycles longer or shorter depending on the (secret) amount of padding — because HMAC's block-based processing genuinely does variable work near a block boundary. The fix required OpenSSL and others to compute the HMAC over the maximum possible padded length always, discarding unneeded work, rather than stopping early — a real, shipped constant-time engineering technique you'll see in §13. POODLE (Bodo Möller, Thai Duong, Krzysztof Kotowicz at Google, 2014, CVE-2014-3566) found something worse in SSL 3.0 specifically: SSLv3's padding format only constrained the last byte's value, never validated the content of the other padding bytes at all, so an attacker could force a byte of their choosing into the padding-check position and get a ~1-in-256 chance of "valid" purely by luck — no timing needed. Combined with a protocol-downgrade attack forcing modern browsers to renegotiate down to SSLv3, POODLE effectively ended SSL 3.0's use across the entire internet within months.

ARC 13 · SOURCE CODE WALKTHROUGH

Reading the real fix: constant-time padding removal

Where this chapter's defenses actually live in production TLS libraries. The files marked ● are where Lucky13's fix landed.

└── crypto/● constant_time.h — CRYPTO_memcmp(): the constant-time comparison every MAC check must use

First, the vulnerable shape — this is structurally what shipped before Lucky13, simplified to the essential bug:

Cnaive_unpad.c — branches on secret data, timing leaks
int remove_padding_naive(const unsigned char *block, size_t block_len) {
    unsigned pad = block[block_len - 1];
    if (pad == 0 || pad > block_len)
        return -1;                       /* early return: FAST path on bad padding length */
    for (size_t i = block_len - pad; i < block_len; i++)
        if (block[i] != pad)
            return -1;                   /* early return: variable-length loop, secret-dependent trip count */
    return block_len - pad;              /* SLOW path: ran the whole loop, then caller computes a MAC */
}

The real fix, structurally faithful to BoringSSL's EVP_tls_cbc_remove_padding(): touch every byte of the block regardless of the real padding length, and use branchless selection so the CPU's instruction stream is identical on every input:

Ctls_cbc.c (structure) — constant-time padding check
int remove_padding_ct(const unsigned char *block, size_t block_len) {
    unsigned pad = block[block_len - 1];
    unsigned good = constant_time_ge(block_len, (unsigned)pad + 1);  /* no branch: arithmetic mask, all-1s or all-0s */

    /* Touch EVERY byte, every time — the loop's length must never depend on `pad`. */
    for (size_t i = 0; i < block_len; i++) {
        unsigned in_pad_region = constant_time_ge(i, block_len - pad);
        unsigned mismatch = constant_time_eq_8(block[i], pad) ^ 1;
        good &= ~(in_pad_region & mismatch);      /* AND into the mask, never an `if` */
    }
    return constant_time_select(good, block_len - pad, 0);  /* single branchless result */
}

And the comparison primitive every MAC check in this codebase is required to route through — never memcmp(), which is explicitly permitted to short-circuit on the first differing byte:

Cconstant_time.h — CRYPTO_memcmp()
int CRYPTO_memcmp(const void *a, const void *b, size_t len) {
    const unsigned char *ap = a, *bp = b;
    unsigned char diff = 0;
    for (size_t i = 0; i < len; i++)
        diff |= ap[i] ^ bp[i];        /* accumulate — never stop, never branch on `diff` mid-loop */
    return diff;                    /* zero iff every byte matched */
}
WHY IT WAS BUILT THIS WAY — THE ENGINEERING DISCIPLINE, NOT JUST THE FIX

1. Never let loop length depend on secret data. The naive version's for loop trip count depends on pad, which is derived from decrypted (secret-adjacent) data — an attacker measuring wall-clock time is measuring that trip count. 2. Replace every if on secret data with an arithmetic mask. constant_time_select/constant_time_ge compute both possible outcomes and select via bitwise AND/OR, so the CPU's branch predictor has nothing to learn and nothing to mispredict. 3. Do the maximum amount of work, always, and discard what you don't need. Lucky13's actual OpenSSL fix went further than padding removal — it made the subsequent HMAC computation itself run over the worst-case message length unconditionally, because "check padding in constant time" is worthless if the very next line of code re-introduces a timing signal. This is the same discipline chapter 15 will name explicitly: constant-time code is a property of the entire call path, not any single function.
