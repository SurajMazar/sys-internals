BITCOIN INTERNALS · CHAPTER 03

Transactions:
The Byte Format

A Bitcoin transaction is not a JSON document, not a protobuf message, not anything with a schema registry. It is a flat sequence of bytes — the same 275 bytes, in the same order, whether you're Satoshi's own client in 2009 or a hardware wallet today — and every rule in this course eventually bottoms out in exactly where a byte sits in that sequence. This chapter teaches you to read that sequence by hand: field by field, byte by byte, until raw hex stops looking like noise and starts looking like a structure you can parse in your head.

ARC 01 · THE PROBLEM

What does a transaction have to say, to whom, with no one in charge?

Strip away every implementation detail and a Bitcoin transaction has exactly one job: move value from some previous outputs to some new outputs, in a way that any stranger on Earth can verify without asking anyone for permission. No bank ledger, no API call to a central server, no schema registry to consult. The transaction itself has to carry everything needed to check it.

Unpack "carry everything needed" and you get a short, unforgiving list of requirements:

  • Reference prior value precisely. It must point at exact previous outputs — not "Alice's balance" (there is no such record) but a specific output of a specific earlier transaction, byte-identified.
  • Prove the right to spend it. A cryptographic unlocking condition, satisfied inline, checkable by anyone with only the transaction and the output it references — no oracle, no lookup service.
  • Declare new value, unambiguously. New outputs, each with an exact amount and an exact new spending condition, with no rounding, no floating point, no currency-conversion ambiguity.
  • Hash to one canonical identity. Every node that ever sees this transaction — now, or replaying history in 2035 — must compute the same identifier from it, byte for byte, or the entire chain of "this output was already spent" bookkeeping (chapter 6) falls apart.
  • Cost almost nothing to store, forever. Every full node keeps every transaction ever confirmed. A format that's 2× fatter than necessary is a permanent 2× tax on every node that will ever exist.

That last requirement — canonical, exact, minimal bytes — is the one people underestimate. It's also the one this chapter is really about: not "what fields exist" (you could learn that from a table), but why the encoding of those fields had to be exactly this shape, and what breaks if it isn't.

WHY THIS MATTERS FOR THE NEXT 13 CHAPTERS

Every later chapter reasons about specific bytes in this layout. Script execution (chapter 4) consumes the scriptSig/scriptPubKey byte ranges you'll parse today. Signature hashing (chapter 5) is defined as "serialize the transaction a certain way, then hash it" — you cannot understand SIGHASH flags without first knowing what serialization means at the byte level. The UTXO set (chapter 6) is keyed by exactly the (txid, index) pair that lives in every input's outpoint. Get comfortable with this layout now; everything else is a variation on it.

ARC 02 · HISTORICAL CONTEXT

A format frozen in 2009, patched around ever since

Unlike almost anything else in software, Bitcoin's base transaction layout has never had a breaking redesign. It has been extended — new meanings squeezed into old fields, new data bolted on in backward-compatible ways — but the core four-field skeleton you'll decode today (version, inputs, outputs, locktime) is what shipped in January 2009. Every entry on that timeline is a soft fork: a way to add meaning without changing what old nodes see as valid. BIP68 hid a new feature inside a field (nSequence) that used to mean almost nothing. SegWit hid an entirely new section (the witness) behind a marker byte that looks like an empty input list to software that doesn't know to look for it. This is the recurring shape of Bitcoin's evolution: the wire format is nearly immutable, so cleverness goes into making old bytes carry new weight.

ARC 03 · NAIVE SOLUTION

Attempt #1: just use JSON

Before defending the binary format, take the strawman seriously — it's what most engineers would reach for first, and for good reason. A transaction is structured data with nested arrays; JSON is the obvious tool:

JSONnaive_tx.json — the strawman, annotated
{
  "version": 2,
  "inputs": [
    {
      "txid": "0437cd7f8525ceed2324359c2d0ba26006d92d856a9c20fa0241106ee5a597c9",
      "vout": 0,
      "scriptSig": "47304402204e45e169...01",
      "sequence": 4294967295
    }
  ],
  "outputs": [
    { "value": 1000000000, "scriptPubKey": "4104ae1a62fe...ac" },
    { "value": 4000000000, "scriptPubKey": "410411db93e1...ac" }
  ],
  "locktime": 0
}

This is not a foolish design — it's self-describing (field names travel with the data), it parses with a one-liner in every language ever made, it's diffable in a code review, and a human can read it without a spec open in another tab. Every blockchain explorer's API returns something close to this on purpose, because for humans, it's strictly better than hex. The question is whether it can be the format transactions actually take on the wire and in the hash that identifies them.

ARC 04 · WHY IT FAILS

Self-describing text has no canonical form — and that's fatal here

JSON fails a Bitcoin transaction for a reason that has nothing to do with verbosity and everything to do with a property JSON was never designed to have: a single value has more than one valid JSON encoding. Whitespace, key order, number formatting (1000000000 vs 1e9 vs 1000000000.0), Unicode escaping — none of these are specified to be canonical. Two parsers can read the same conceptual transaction from two byte-different JSON documents and agree it's "the same" while your hash function, which only sees bytes, computes two different digests from it.

That single property is disqualifying, because the txid is a hash of the serialized transaction (§8 derives this precisely). If serialization isn't canonical, the identifier isn't stable, and "has this output already been spent" — the entire point of the UTXO model (chapter 6) — stops being answerable. You could bolt on a canonicalization scheme (JSON Canonicalization Scheme, RFC 8785, exists today — it didn't in 2009, and even it only constrains JSON's own ambiguities, not the deeper problem below).

Then there's the size tax, which is not hypothetical — it compounds over every node, forever:

THE NUMBERS

The real transaction decoded in §8 is 275 bytes in binary. Written as the JSON strawman above — hex-encoded byte strings, field names, punctuation — it comes to roughly 620–650 bytes, a ~2.3× blow-up, and that's being generous (no pretty-printing). Multiply by the number of transactions a full node stores forever: as of this writing that's on the order of a billion, and Bitcoin's on-disk block data is already several hundred gigabytes. A 2.3× tax on that is not a rounding error — it changes who can afford to run a full node, which is the entire security model. And it doesn't even solve the problem: a 64-bit integer like a satoshi value can exceed Number.MAX_SAFE_INTEGER in JavaScript's JSON parser at 253 (9,007,199,254,740,992) — Bitcoin's max supply in satoshis, 2.1 × 1015, is under that ceiling today, but any format whose numeric type has a silent precision cliff is a bad place to put money. (This is precisely why JSON-RPC APIs like Bitcoin Core's return amounts as strings or as BTC floats with known 8-decimal rounding — a workaround for a real defect.)

So: self-describing text is out. What we actually need is fixed binary fields for anything of known size, and something else — the subject of §5 — for anything of variable size. That "something else" is the single most useful trick in this whole chapter.

ARC 05 · BINARY, DERIVED FROM SCRATCH

Building CompactSize (what everyone calls "VarInt") from first principles

Fixed-width binary is the easy 80%: a version number is always 4 bytes, a locktime is always 4 bytes, an output value is always 8 bytes. The hard 20% is the parts whose length varies — how many inputs, how long is this particular unlocking script. Step through the reasoning a 2009-era systems programmer would go through, because the answer they landed on is used constantly for the rest of this course.

The result is what Bitcoin's own source (src/serialize.h) names CompactSize — the community almost universally calls it "VarInt," and this chapter will too, but keep the source name in your back pocket for §13, because Bitcoin Core also has a second, differently-shaped variable-length integer (base-128, continuation-bit style, used internally for on-disk chainstate — not on the wire) that is confusingly also called VarInt in the code. Learn this table once and you can parse the length-prefixed parts of almost anything in the Bitcoin protocol — block headers' transaction counts, P2P message vectors (chapter 10), all of it.

ARC 06 · WHAT STILL HURTS

The warts that shipped in 2009 and are now permanent

CompactSize solves the length-prefix problem cleanly. It does not fix several other design choices baked into the same 2009 format — choices that are still consensus rules today because changing them would be a hard fork. Four of them matter enough to name now; you'll meet the consequences in §11.

1. The fee is never written down — anywhere

Scan every field in this chapter's layout: version, inputs, outputs, locktime. There is no fee field. The fee is sum(input values) − sum(output values), computed by every validator independently by looking up the values of the outputs being spent (which requires the UTXO set — chapter 6 — since a transaction's inputs only carry a reference, not a value). Get the arithmetic wrong on either side and the difference silently becomes the miner's fee — with no sanity check anywhere in consensus that a fee "looks reasonable." §11 covers two real, expensive versions of this exact mistake.

2. Locktime's dual meaning is a magic number, forever

The 4-byte locktime means "block height" if its value is below 500,000,000 (LOCKTIME_THRESHOLD), and "Unix timestamp" if at or above it. That threshold was picked because block heights wouldn't reach 500 million for centuries (at ~10 minutes/block, 500M blocks is on the order of 9,500 years) while Unix timestamps passed 500,000,000 in November 1985 — comfortably before Bitcoin existed. It works, but it's a constant frozen into consensus rules that every implementation must match exactly, forever, with no room to ever raise it without a hard fork.

3. nSequence: one 32-bit field, three unrelated jobs

4. Coinbase transactions are exceptions, everywhere, forever

A coinbase transaction — the block reward payment every miner includes first in every block — reuses the exact same byte layout with a null outpoint standing in for "no real input." That's elegant in one sense (no separate coinbase format to define) and a permanent complication in another: every piece of validation logic that walks a transaction's inputs (chapters 6 and 8) must special-case "is this the coinbase?" before doing normal input processing, because a null outpoint isn't a real previous output and must never be looked up as one. §8 shows the exact bytes; §11 shows what went wrong before this was airtight.

Endianness: the single most confusing sentence in this chapter

Every multi-byte integer in this format is little-endian on the wire — least significant byte first. That includes the 32-byte outpoint hash. But the txid you see on every block explorer, in every wallet, in every chapter of this course, is displayed reversed — big-endian hex. These are not two different representations chosen for convenience; they're the same 32 bytes, read in opposite directions, and mixing them up is the single most common bug when hand-rolling Bitcoin code.

Concretely, from the transaction above: the first input's outpoint bytes on the wire, exactly as they appear in the hex, are:

hexoutpoint txid — as serialized (little-endian)
c9 97 a5 e5 6e 10 41 02 fa 20 9c 6a 85 2d d9 06 60 a2 0b 2d 9c 35 24 23 ed ce 25 85 7f cd 37 04

Reverse the byte order — not the hex-character order, the byte order, i.e. read the 32 bytes back to front — and you get what every block explorer displays as this transaction's input's previous txid:

hexthe same 32 bytes, reversed — this is what you'd search for on-chain
04 37 cd 7f 85 25 ce ed 23 24 35 9c 2d 0b a2 60 06 d9 2d 85 6a 9c 20 fa 02 41 10 6e e5 a5 97 c9

The rule, stated once so you never have to re-derive it: a txid is computed by treating the transaction's bytes as a number to hash (little-endian, as always), but the convention for human-facing hex display is to print hashes in reversed-byte order. That convention almost certainly traces back to Satoshi treating the 256-bit hash output as a big integer for early difficulty comparisons; every explorer, wallet, and block header since has inherited it. The outpoint field inside a transaction stores the hash exactly as it appears internally (little-endian) — so if you ever hand-construct a transaction spending a specific output, you must take the txid you copied from an explorer and reverse its bytes before writing it into the outpoint. Get this wrong and you reference a transaction that doesn't exist; the failure is usually silent until validation.

Values are satoshis — and always fit comfortably in a signed 64-bit field

Each output's 8-byte value field is a little-endian integer counting satoshis (10−8 BTC), not BTC and not any floating-point unit. Bitcoin's fixed 21,000,000 BTC supply cap, in satoshis, is 21,000,000 × 108 = 2,100,000,000,000,000 — about 2.1 × 1015. A signed 64-bit integer (int64_t, which is what Bitcoin Core's CAmount actually is) tops out at 9,223,372,036,854,775,807 — roughly 9.2 × 1018, over 4,000× headroom above the entire possible money supply. That headroom is not accidental generosity; §11 covers the one time in Bitcoin's history that a signedness assumption around this exact field was violated, and what it took to fix it.

Coinbase transactions: the input that spends nothing

A coinbase input's outpoint is a null outpoint: 32 zero bytes for the "previous txid," and 0xFFFFFFFF for the index. There is no earlier transaction being referenced — the miner is creating value, not moving it — and the format doesn't get a special case for that; it just fills the same 36-byte outpoint field with sentinel values that can never collide with a real (txid, index) pair. The scriptSig, freed from needing to unlock anything, is filled with arbitrary miner-chosen data, 2–100 bytes, and since BIP34 (2012) must begin with the current block height as a minimal-length pushed script number — this is how a block's height became cryptographically bound into its own coinbase transaction. Verified from a real coinbase (block 300,000, txid b39fa6c3…4b983): the scriptSig opens with bytes 03 e0 93 04 — a push of 3 bytes (03), which as a little-endian script number decodes to 0x0493e0 = 300,000, exactly the block's height, followed by pool-specific tag bytes filling out the rest of the 72-byte scriptSig.

WHY BIP34 EXISTS: A REAL TXID COLLISION

Before BIP34, nothing forced coinbase scriptSigs to be unique, and a coinbase transaction's txid is computed the same way as any other — hash of its bytes. In 2010, two pairs of blocks (heights 91,722/91,812 and 91,880/91,842) mined by the same pool with an unvaried scriptSig template produced byte-identical coinbase transactions — same txid appearing twice on the chain. That's not merely confusing; the reference client's UTXO bookkeeping assumed txids were unique, and a careful attacker could exploit the collision to make a fully-confirmed transaction revert to a single confirmation. BIP30 (2012) patched the immediate hole by banning duplicate txids outright, grandfathering in the two already-mined collisions. BIP34 then removed the root cause by forcing the block height into every coinbase's scriptSig — after which two coinbases can never collide unless they're at the same height, which consensus already forbids on one chain.

Spent coinbase outputs carry one more rule that lives outside the byte format but depends on parsing it correctly: the 100-block maturity rule. A coinbase output cannot be spent until 100 blocks have been mined on top of it (chapter 8 covers the exact consensus check). The reasoning is pure reorg defense: if a short reorg (chapter 7) ever un-mines the block containing this coinbase, that reward — and any transaction that already spent it — must vanish cleanly. A 100-block buffer makes that scenario astronomically unlikely before the reward is treated as final.

ARC 09 · TRADEOFFS

The same encoding problem, five ways

Bitcoin's transaction format is one point in a design space every serialization format occupies. None of the alternatives are wrong — they optimize for different things:

FORMATVARIABLE-LENGTH SCHEMEWHAT IT BUYSWHAT IT COSTS
Bitcoin CompactSize1/3/5/9-byte prefix by magnitude minimal for small counts trivial to hand-decode frozen by consensus — no new fields, ever, without a fork
Protocol BuffersLEB128 varint (7 bits/byte, continuation bit) schema evolution — add fields freely cross-language codegen requires a shared .proto schema to interpret bytes at all
Ethereum RLPlength-prefixed nested byte arrays, recursively handles arbitrary nesting uniformly no schema needed to parse structure semantic meaning of fields still needs external knowledge
MessagePack / CBORtype-tagged length prefixes, JSON-like data model self-describing like JSON, much smaller canonical-encoding rules must be bolted on separately for hashing use cases
JSON (the §3 strawman)none — delimiters and commas human-readable, zero tooling to inspect no canonical byte form; unusable as a hash preimage without extra machinery

Read this table as a proof by exhaustion: every format trades schema flexibility against byte-level determinism. Bitcoin picked the extreme of the determinism axis — zero schema, zero flexibility, permanent bytes — because the one property it cannot compromise on is that two honest nodes, anywhere, at any time, compute the identical hash from the identical transaction. Protobuf and RLP are excellent formats for systems that expect to evolve their schema (which is most systems); Bitcoin deliberately is not one of them at the base-transaction layer, and treats every new field as a hard-fork-only event.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Size, parsing cost, and what a malformed CompactSize can do to you

Parsing this format is O(n) in the number of bytes — a single linear pass, no backtracking, no lookahead beyond the current CompactSize prefix. The performance story here isn't about CPU cost (it's negligible); it's about size, because size is what every node pays for forever, and about trusting length prefixes, because a CompactSize is exactly the kind of field a hostile peer controls.

On the security side: every CompactSize you decode is an attacker-controlled length claim before you've validated anything else about the message. A parser that does read(claimedLength) without first checking claimedLength ≤ bytesRemaining can be made to over-read, and one that blindly pre-allocates a buffer of claimedLength before reading a single further byte can be made to allocate gigabytes from a handful of attacker bytes — a classic memory-exhaustion vector. Bitcoin Core's real reader (§13) defends on two fronts simultaneously: it rejects any CompactSize that isn't minimally encoded (encoding 5 as the 3-byte form 0xFD 0x05 0x00 throws "non-canonical ReadCompactSize()" even though the value is technically correct — one value, one legal encoding, no ambiguity to exploit), and vector-reading code allocates in bounded batches rather than trusting the claimed size up front.

ARC 11 · REAL-WORLD INCIDENTS

When the byte format's blind spots cost real money

August 2010 — the value overflow (CVE-2010-5139)

Block 74,638 contained a transaction with two outputs whose values, added together as signed 64-bit integers, overflowed and wrapped around — producing two outputs worth roughly 92,233,720,368.54 BTC each, a total of over 184 billion BTC conjured from nothing, against a 21 million cap. The root cause is exactly the field this chapter decodes: the reference client's sum-of-outputs check didn't account for the wraparound behavior of signed 64-bit addition at those magnitudes. Satoshi and the network patched it within hours via an emergency soft fork rejecting the offending block and any chain built on it — the earliest example of Bitcoin's "the code is buggy, humans intervene, then a rule change prevents recurrence" pattern. (Chapter 15 gives this incident the full root-cause treatment alongside its siblings; it's introduced here because it is, precisely, a byte-format and arithmetic-on-that-format bug.)

April 2016 — the 291 BTC fee (block 409,008)

Recall §6's warning: the fee is never a field, only an implicit difference. In April 2016, a transaction set its outputs so low relative to its inputs that the implicit fee came to 291.2410 BTC — worth roughly $136,000 at the time — for what should have been an ordinary payment. Nothing in consensus flags "this fee looks insane"; the transaction was perfectly valid, and the mining pool BitClub Network collected the windfall simply by including it in the block they happened to mine. There is no cryptographic proof the sender meant to do this — the most likely explanation, per contemporaneous reporting, was custom transaction-building software that swapped a fee value and a change-output value. BitClub stated its intent to return the funds if the sender came forward.

November 2023 — the $3.1 million fee (block 818,087)

The same failure mode, seven years and roughly two orders of magnitude of price appreciation later: a sender intending to move 139.42 BTC constructed a transaction that delivered only 55.78 BTC to its recipient, with the remaining 83.65 BTC — about $3.1 million at the time, the largest transaction fee ever recorded on Bitcoin — going to the miner, AntPool, as an implicit fee. The wallet involved had been created minutes before the transfer, consistent with automated or unfamiliar tooling misplacing a decimal or a field. Unlike April 2016's BitClub, AntPool made no public commitment to return the funds. Two months earlier, in September 2023, a similar (smaller) mistake by Paxos — an 19.8 BTC fee on a roughly $2,000 transfer, misconfigured automated wallet software — was voluntarily refunded by the mining pool F2Pool. The pattern across all three: the format makes an oversized implicit fee just as valid as a correct one, and whether the miner returns the windfall is a matter of goodwill, not protocol.

First, the shapes themselves — simplified from current Bitcoin Core but faithful to the real structure and naming:

C++primitives/transaction.h — the four structs this chapter decoded
// An outpoint: a previous transaction's hash plus the index of the output claimed.
class COutPoint {
public:
    Txid hash;         // 32 bytes — the previous tx's id, stored little-endian
    uint32_t n;      // which output of that transaction
    static constexpr uint32_t NULL_INDEX = 0xFFFFFFFF;
    bool IsNull() const { return hash.IsNull() && n == NULL_INDEX; }
};

// One input: what it claims, the proof it can claim it, and its sequence number.
class CTxIn {
public:
    COutPoint prevout;
    CScript   scriptSig;   // CompactSize-prefixed on the wire; opaque bytes until chapter 4
    uint32_t  nSequence;  // §6: three overlapping meanings in one field
};

// One output: how much, and the condition that must be satisfied to spend it.
class CTxOut {
public:
    CAmount  nValue;         // int64_t — satoshis; §8 shows why this never overflows in practice
    CScript  scriptPubKey;   // CompactSize-prefixed, like scriptSig
};

class CTransaction {
public:
    const std::vector<CTxIn>  vin;
    const std::vector<CTxOut> vout;
    const uint32_t version;
    const uint32_t nLockTime;

    bool IsCoinBase() const {
        return vin.size() == 1 && vin[0].prevout.IsNull();   // §8's null-outpoint rule, verbatim
    }
};

Then the codec that makes every count in this chapter's layout self-delimiting — this is the real logic behind §5's table and §10's non-canonical-encoding rejection, lightly trimmed for readability:

C++serialize.h — WriteCompactSize() / ReadCompactSize()
void WriteCompactSize(Stream& os, uint64_t nSize) {
    if (nSize < 253)                        ser_writedata8(os, nSize);
    else if (nSize <= 0xFFFF)             { ser_writedata8(os, 253); ser_writedata16(os, nSize); }
    else if (nSize <= 0xFFFFFFFF)         { ser_writedata8(os, 254); ser_writedata32(os, nSize); }
    else                                     { ser_writedata8(os, 255); ser_writedata64(os, nSize); }
}

uint64_t ReadCompactSize(Stream& is) {
    uint8_t chSize = ser_readdata8(is);
    if (chSize < 253)  return chSize;
    if (chSize == 253) {
        uint64_t n = ser_readdata16(is);
        if (n < 253) throw std::ios_base::failure("non-canonical ReadCompactSize()"); // §10: reject padding
        return n;
    }
    // chSize == 254 / 255 branches mirror the pattern with uint32_t / uint64_t
     // and the equivalent "would have fit in fewer bytes" rejection each time.
}

The piece that decides §6's coinbase problem never gets easier — the real serializer branches on whether witness data (chapter 12) needs to be written, but the base fields you decoded in §8 flow through unchanged in either path:

C++primitives/transaction.h — SerializeTransaction() (trimmed)
template<typename Stream, typename TxType>
void SerializeTransaction(const TxType& tx, Stream& s, bool allowWitness) {
    s << tx.version;                          // §7: 4 bytes, always first
    unsigned char flags = 0;
    if (allowWitness && tx.HasWitness()) flags |= 1;
    if (flags) { std::vector<CTxIn> empty; s << empty; s << flags; } // BIP144 marker+flag (ch. 12)
    s << tx.vin;                               // CompactSize count, then each CTxIn in turn
    s << tx.vout;                              // CompactSize count, then each CTxOut in turn
    if (flags & 1)
        for (auto& in : tx.vin) s << in.scriptWitness.stack;
    s << tx.nLockTime;                         // §7: 4 bytes, always last
}

And finally, the txid itself — the payoff of §8's endianness discussion:

C++primitives/transaction.cpp — ComputeHash()
Txid CTransaction::ComputeHash() const {
    return (CHashWriter{} << TX_NO_WITNESS(*this)).GetHash();
    // CHashWriter feeds every serialized byte through SHA-256 twice (CHash256)
     // and GetHash() returns the 32-byte digest in the SAME little-endian byte
     // order it was computed in. The "reversed" txid you see in explorers is
     // purely a display-layer choice made when formatting that digest as hex —
     // exactly the distinction §8 walked through with real bytes.
}
WHY IT WAS BUILT THIS WAY — TEMPLATED SER/UNSER, ONE CODEPATH

Notice that Serialize and the equivalent Unserialize logic aren't two hand-written, easy-to-drift-apart functions — Bitcoin Core generates both from one templated body (SerializeTransaction<Stream, TxType> is written once; the reading direction reuses the identical field order via a matching Unserialize that's mechanically kept in lockstep by the project's SERIALIZE_METHODS macro pattern). The engineering insight worth stealing: whenever a format must be both written and read, and drift between the two would be a consensus-splitting bug, encode the field order and types once, in a form the compiler can specialize for both directions, rather than trusting two humans to keep hand-written encode/decode functions in sync across years of edits. It's the same instinct behind schema-driven codecs (protobuf, Avro) — Bitcoin just gets there with C++ templates instead of a code generator, because the schema itself is permanently frozen (§9).
