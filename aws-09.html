AWS CERTIFICATION PREP · CHAPTER 09

DynamoDB
Deep Dive

DynamoDB scales horizontally by physically splitting a table across partitions — and which partition any given item lands on is decided entirely by one attribute you choose at design time: the partition key. Choose it well and DynamoDB genuinely does look infinitely scalable. Choose it badly — a low-cardinality field a lot of items happen to share — and you can get throttled while the table's overall provisioned capacity sits nowhere near exhausted. This chapter is about making that one choice correctly, plus the real mechanics (item size limits, GSI vs LSI, capacity modes) the exam builds around it.

It's also the chapter where "NoSQL means design discipline doesn't matter" gets corrected — DynamoDB rewards upfront access-pattern modeling at least as much as a relational schema does, just along a different axis: instead of normalizing data and letting SQL join it back together at query time, you design your keys and indexes around the specific queries your application will actually run, ahead of time.

WHY THIS MATTERS ON TEST DAY

If you remember nothing else from this chapter: the partition key is a physical placement decision, not just a logical identifier. Every fact in this chapter — hot partitions, GSIs, capacity modes, DAX — is a consequence of that one sentence. Both exams also expect you to recognize DynamoDB by name whenever a scenario's real bottleneck is simple, high-volume, key-based access rather than complex relational querying — which is precisely the boundary chapter 8 drew from the relational side and this chapter now draws from the non-relational side.

ARC 02 · THE COMMON WRONG INSTINCT

"DynamoDB scales automatically, so the partition key barely matters"

Here's the plausible-sounding wrong instinct: DynamoDB is famous for scaling to enormous size without capacity planning, so a candidate assumes any attribute that's roughly present on every item — a status flag, a country code, a signup date — is fine as a partition key, because "DynamoDB will spread the load around automatically no matter what I pick." That instinct treats partition key choice as cosmetic, like naming a variable.

It's an understandable mistake, because DynamoDB's marketing and documentation genuinely emphasize "virtually unlimited scale," and that's true in aggregate — but aggregate table capacity and per-item access patterns are two different things. A table can have enormous total capacity and still throttle badly if a large fraction of requests target the same handful of key values.

THE TELL

Watch for scenario language like "most requests filter on a status field with only a few possible values," "the leaderboard shows a small number of celebrity accounts getting most of the traffic," or "one tenant is far larger than the others in a multi-tenant table." Each is describing low key cardinality or skewed access — exactly the shape of problem a naive partition key choice cannot survive.

There's a second, quieter version of the same wrong instinct worth naming: assuming that because DynamoDB is "NoSQL," normal database design discipline doesn't apply — that you can bolt on indexes and fix key mistakes after the fact the way you might add an index to a relational table post-launch. GSIs genuinely can be added later, which reinforces this illusion; LSIs cannot, and a bad partition key choice on the base table itself usually can't be fixed without a data migration to a new table. "NoSQL" describes the data model, not a promise that design decisions are free to defer.

ARC 03 · WHY IT'S WRONG

The mechanism: the partition key decides physical placement

DynamoDB determines which physical partition an item lives on by hashing its partition key value. Every item sharing the same partition key value lands in the same item collection, on the same physical partition, sharing that partition's slice of the table's total throughput.

  • Low cardinality concentrates traffic by construction. If a partition key has only a handful of distinct values, every item sharing one of those values is physically stuck together — no amount of overall table capacity helps if the requests hitting one value's partition exceed what that single partition can serve.
  • Adaptive capacity helps, but it isn't unlimited or instantaneous. DynamoDB's adaptive capacity feature automatically shifts a larger share of a table's throughput toward frequently accessed partitions — it measurably reduces the hot-partition problem versus older behavior, but it does not make key design irrelevant. A sufficiently skewed access pattern (a tiny number of item values receiving a wildly disproportionate share of requests) can still throttle before it's absorbed, and the exam expects you to treat "design a good key" as the primary fix, with adaptive capacity as a real but secondary safety net rather than a substitute.
  • The failure mode is specific and testable: throttling on a subset of requests, not on the whole table. A scenario describing "some requests succeed instantly, others get throttled, and it correlates with a specific attribute value" is describing a hot partition, and the fix is a better key — higher cardinality, or a composite/sharded key that spreads a hot logical entity across multiple physical item collections.
QUANTIFY IT

DynamoDB's real, stable, hard limit regardless of key design: maximum item size is 400 KB. That number is unrelated to hot partitions — it's a per-item ceiling that applies no matter how well or badly your key is chosen — but it's exactly the kind of fact the exam pairs with a hot-partition question to see if you can tell "a limit on one item" apart from "a throughput problem across many items sharing a key value."

ARC 06 · LIMITS, QUOTAS & EDGE CASES

What the correct approach still has to respect

  • Maximum item size: 400 KB, hard and real, unrelated to key design — large attributes (documents, blobs) need to be stored elsewhere (typically S3) with only a reference kept in the item.
  • LSIs must be created at table creation and cannot be added or removed later. If a scenario describes adding a new query pattern to an existing table that needs the same partition key but a different sort key, and the table wasn't built with that LSI from day one, the answer is a GSI instead (which can be added at any time) or a new table design — not "just add an LSI now."
  • LSIs share the base table's throughput and its 10 GB per-partition-key-value item collection limit — a real constraint on how much data can accumulate under one partition key value when LSIs are in use, distinct from the per-item 400 KB limit.
  • GSIs have their own provisioned throughput (in provisioned mode) and are only ever eventually consistent — never strongly consistent, even if the base table read is. A scenario requiring strongly-consistent reads on a query that only a GSI's shape can satisfy is describing a real design tension worth flagging, not silently resolving.
  • A table's default quotas include a limited number of GSIs and LSIs per table (commonly cited as up to 20 GSIs and 5 LSIs by default) — the exam-relevant point is that these are real, checkable quotas, not that you need the exact figure memorized cold.
  • Reads default to eventually consistent; strongly consistent reads are opt-in, cost more read capacity, and aren't available on GSIs or across regions — a scenario emphasizing "must always read the very latest write" is pointing at this setting specifically.
  • Switching between provisioned and on-demand capacity mode is not unlimited-frequency — AWS constrains how often you can switch a given table's mode, so treat the choice as a real architectural decision made with some deliberation, not a dial to flip casually multiple times a day.
  • A Query is efficient; a Scan reads the entire table (or GSI) and filters afterward. A scenario describing slow, expensive, or throttling-prone access that turns out to be doing a full-table scan for what should be a targeted lookup is testing whether you'll recognize that the fix is redesigning the access pattern around Query, not just adding more capacity to make the scan finish faster.
  • DynamoDB Streams capture an ordered, time-limited change log per table (a rolling window, commonly cited as 24 hours) and are the real mechanism behind cross-region Global Tables replication and behind event-driven patterns feeding Lambda (chapter 10) — a scenario describing "react to every write to this table" is pointing at Streams, not at polling the table on a schedule.
  • Time to Live (TTL) deletes expired items automatically and for free in terms of write capacity — a scenario describing session data, temporary tokens, or any data with a natural expiry is testing whether you'll reach for TTL instead of a manually scheduled cleanup job.

WHY THE SHAPE MATTERS

The partition key (CustomerId) is high-cardinality — there are many customers, so orders spread naturally across partitions. The sort key gives free, efficient range queries ("this customer's orders in order"). The GSI answers a genuinely different access pattern (all orders in a given status, across all customers) that the base key can't serve. DAX absorbs the small number of product lookups that get hit far harder than everything else, without changing the table's key design at all.

THE ONE-SENTENCE FILTER

For nearly any DynamoDB scenario question, ask: "is this about where an item physically lives (partition key), how it's ordered within that location (sort key), a different way to query it (GSI/LSI), how fast a hot read is (DAX), or how much capacity is paid for and when (provisioned vs on-demand)?" Every fact in this chapter sorts cleanly into exactly one of those five buckets.

ARC 11 · REAL-WORLD SCENARIO CASE STUDIES

Three original vignettes, in the exam's own phrasing style

Case 1 — the social feed startup. A social app stores posts in DynamoDB using CountryCode as the partition key, reasoning that "grouping by country makes regional queries easy." After launch, over half of all traffic comes from users in one country, and that single partition's requests start throttling while the table's overall provisioned throughput is barely half used. A candidate might first reach for "just raise the table's provisioned capacity" — which doesn't fix a hot-partition problem, since more aggregate capacity doesn't help a single overloaded physical partition. Answer shape: redesign the key — for example a composite partition key combining CountryCode with a hash of the user ID, or partitioning by UserId directly with a GSI for the country-based query pattern — to spread that country's posts across many physical partitions instead of one.

Case 2 — the customer-orders table. An e-commerce team needs each customer's orders returned in chronological order efficiently, and separately needs support staff to look up all orders in a given status across every customer. Answer shape: partition key CustomerId with sort key OrderTimestamp for the first pattern (a natural range query within one partition key), plus a GSI keyed on OrderStatus (with OrderTimestamp as its sort key) for the second — two genuinely different access patterns, resolved by two different key structures on the same base data.

Case 3 — the gaming leaderboard. A game needs to display the current top 100 players by score, updated frequently, alongside each individual player's own personal stats page. A candidate might assume a single table design with PlayerId as the partition key can serve both — but "top N across everyone" is not something a per-player partition key can answer efficiently at all. Answer shape: keep PlayerId as the partition key for personal stats lookups, and add a GSI with a low-cardinality partition key (like a fixed "LEADERBOARD" value) and Score as its sort key specifically to serve the top-N query — a deliberate, small, intentionally low-cardinality key used only because the query pattern genuinely needs one shared, sorted collection, not because cardinality was an accidental afterthought.

NOTE

These three vignettes are original constructions written for this course to model the real exam's scenario style — they are not reproductions of any actual exam question. Notice Case 3 in particular: a low-cardinality key isn't always wrong — it's wrong when it's accidental. Used deliberately, with a known, bounded write rate, it's a legitimate pattern.

One more pattern worth naming across all three cases: in every one, the fix layered a new mechanism (a reshaped key, a second GSI, a deliberately narrow index) alongside the original design rather than discarding it. Case 1 kept the country-based query need alive via a GSI even after fixing the base key. Case 2 kept the natural per-customer ordering while adding an entirely separate status-based access path. Case 3 kept per-player lookups untouched while adding a narrow, purpose-built index for the one query that genuinely needed a shared, low-cardinality key. Good DynamoDB design is rarely "replace the key" — it's usually "add the right index for the access pattern that doesn't fit the base key," which is precisely why GSIs exist as a first-class, frequently-reached-for tool rather than an edge case.

WHY THE EXAM CARES

Not the exact flags — the exam checks whether you recognize KeyType=HASH as the partition key and KeyType=RANGE as the sort key, that GSIs are added via a table update (not at creation only), and that a query against a partition key is the efficient, intended access pattern DynamoDB is built around — as opposed to a full table scan, which reads every item and is almost never the right exam answer for a targeted lookup.

ARC 16 · EXAM-DAY TAKEAWAYS

What to actually remember on test day

Anchor everything to one fact: the partition key is a physical placement decision — high cardinality and evenly distributed access are what make DynamoDB's horizontal scale actually materialize, and adaptive capacity is a real but bounded safety net, not a substitute for good key design. Remember the hard, stable ceiling: 400 KB maximum item size, unrelated to key design. Remember GSIs can be added anytime but are always eventually consistent, while LSIs must be defined at table creation but support strong consistency. And remember capacity mode is a real, deliberate choice between predictable-traffic provisioning and unpredictable-traffic on-demand pricing — not a knob to flip casually. When a scenario describes throttling correlated with a specific attribute value, the answer is almost always "redesign the key," not "add more capacity."

Keep the five-bucket filter from §9 in your pocket for the rest of both exams, not just this chapter: every DynamoDB fact you'll meet going forward — Streams, Global Tables, Transactions, PartiQL, DAX item and query caching — is a variation on where data physically lives, how it's ordered, how else it can be queried, how fast a hot path is, or how capacity is paid for. New vocabulary will keep appearing; the five buckets won't.
