APPLIED CRYPTOGRAPHY · CHAPTER 14

Real-World Crypto Failures:
Heartbleed, ROCA & the Debian Bug

Every primitive in this course so far has come with a proof or a decade of unbroken cryptanalysis. None of that stopped four of the most consequential security disasters in the internet's history — and none of them broke the math. Heartbleed (CVE-2014-0160) leaked private keys through a missing bounds check. ROCA (CVE-2017-15361) made smartcard RSA keys factorable through a "clever" key-generation shortcut. The 2008 Debian OpenSSL bug (CVE-2008-0166) turned every generated key into one of 32,768 guesses through a single well-intentioned deletion. Dual_EC_DRBG may have been a seven-year NSA-engineered backdoor sitting inside a NIST standard in plain sight. This chapter dissects all four at the byte and bit level, and builds a real Heartbleed replay you can run against a simulated heap.

ARC 01 · THE PROBLEM

The math was never the bug

AES has withstood two and a half decades of cryptanalysis. RSA's hardness rests on integer factorization, unbroken at usable key sizes since 1977. TLS 1.3's handshake carries a machine-checked security proof. And yet four of the internet's most consequential cryptographic disasters — one that exposed the private keys of roughly half a million servers overnight, one that quietly generated brute-forceable keys for two years, one that made a whole class of smartcard-generated RSA keys factorable, and one that may have been an intentional trapdoor sitting inside a NIST standard for seven years — broke none of that math. They broke the code that implements it, the randomness that feeds it, or the standard that specifies it.

Nobody attacks AES's S-box. In production, attackers go after:

  • The parsing code around the primitive — a length field trusted without a bounds check (Heartbleed).
  • The randomness feeding the primitive — a "harmless" cleanup commit that silently deleted the only real entropy source (the Debian OpenSSL PRNG bug).
  • The parameter-generation shortcut taken for performance — a structurally patterned RSA key that trades cryptographic strength for smartcard CPU cycles (ROCA).
  • The standard itself — a NIST-blessed random bit generator whose public constants nobody could prove were chosen honestly (Dual_EC_DRBG).

Four different failure classes share one root cause worth naming up front: each one moved a security-critical decision out of a place where it could be reviewed, tested, or proven, and into a place where a single mistake — or a single dishonest actor — was invisible until someone went looking. That is the lens for the rest of this chapter: not "was the cipher broken" (never), but "where did trust get placed without verification."

WHY THIS MATTERS FOR THE NEXT TWO CHAPTERS

Once you accept that implementations, not algorithms, are where crypto systems actually fail in production, three questions follow naturally: how do you store secrets so a heap bug like Heartbleed can't reach them through a completely different code path, how do you stop an attacker from reading a secret through timing or power consumption instead of a buffer over-read, and how do you write constant-time code so branching itself doesn't leak. This chapter supplies the motivating case studies; chapter 15 supplies the engineering discipline — secrets management, side channels, and constant-time code.

ARC 03 · THE VULNERABLE CODE

RFC 6520's heartbeat, implemented the way that seemed obviously fine

RFC 6520 (2012) added a small keepalive/path-MTU-discovery feature to TLS and DTLS: a client sends a HeartbeatMessage containing arbitrary payload bytes, and the peer must echo that exact payload back. It exists mainly for DTLS, which runs over unreliable UDP and needs a cheap way to confirm the peer is alive and to probe path MTU without a full renegotiation. The wire format is deliberately simple:

  • type — 1 byte: 1 = heartbeat_request, 2 = heartbeat_response.
  • payload_length — 2 bytes, a 16-bit unsigned integer declaring how many bytes of payload follow.
  • payload — exactly payload_length bytes, to be echoed back unchanged.
  • padding — at least 16 bytes of random data, required by the RFC so the message can't be trivially fingerprinted by length.

The receiving side's job sounds trivial: read the header, allocate a response buffer, copy the payload into it, send it back. Here is that logic exactly as it shipped in OpenSSL 1.0.1 through 1.0.1f — simplified from the real tls1_process_heartbeat() / dtls1_process_heartbeat() functions, but faithful to the fatal omission:

Ct1_lib.c — tls1_process_heartbeat(), OpenSSL 1.0.1–1.0.1f (2012–2014)
int
tls1_process_heartbeat(SSL *s)
{
    unsigned char *p = &s->s3->rrec.data[0], *pl;
    unsigned short hbtype;
    unsigned int payload;
    unsigned int padding = 16; /* required by RFC 6520 */

    /* Read type and payload length first */
    hbtype = *p++;
    n2s(p, payload);           /* reads 2 bytes, big-endian, into `payload` — 
                                   ATTACKER-CONTROLLED, 0..65535, NEVER CHECKED  */
    pl = p;                    /* pl now points at "the rest of the record"     */

    if (hbtype == TLS1_HB_REQUEST) {
        unsigned char *buffer, *bp;
        int r;

        /* Allocate a response exactly as large as the CLAIM, not the
           actual record — this line trusts `payload` completely.       */
        buffer = OPENSSL_malloc(1 + 2 + payload + padding);
        bp = buffer;

        *bp++ = TLS1_HB_RESPONSE;
        s2n(payload, bp);
        memcpy(bp, pl, payload);   /* <-- THE BUG: copies `payload` bytes starting
                                   at pl, regardless of how many bytes actually
                                   followed the header in this TLS record.       */
        bp += payload;
        RAND_bytes(bp, padding);

        r = ssl3_write_bytes(s, TLS1_RT_HEARTBEAT, buffer, 3 + payload + padding);
        OPENSSL_free(buffer);
        if (r < 0) return r;
    }
    return 0;
}

Read it the way a reviewer in 2011 would have: it compiles cleanly, it does exactly what the RFC describes, and every individual line looks reasonable — allocate a buffer sized to the request, copy the payload, send it back. The bug is not a typo or an off-by-one. It is a missing comparison that was never written: nowhere does this function check payload against s->s3->rrec.length, the number of bytes the TLS record layer actually received. payload is whatever the attacker wrote into two bytes of the wire format — it can be 65535 while the attacker sent a total record of 20 bytes, and this code will still try to copy 65535 bytes starting at pl. This shipped in OpenSSL 1.0.1, released March 14, 2012, and stayed in every production TLS stack that linked it for a little over two years.

ARC 04 · WHY IT FAILS, QUANTIFIED

64 kilobytes of someone else's memory, on request, silently

Quantify exactly what that missing check costs:

  • Maximum over-read per request: payload_length is a 16-bit field, so the attacker can claim up to 65535 bytes. Subtract the 3-byte header the attacker is required to actually send and the process gets almost 65 KB of adjacent heap memory copied into a response, for one crafted TLS record.
  • No rate limit, no authentication requirement. The heartbeat extension is negotiated during the handshake and can be sent before or after full authentication in many configurations; nothing in the protocol or the vulnerable code throttles repetition. An attacker can send the request thousands of times per second, each one a fresh, independent draw of whatever the process's heap allocator currently has adjacent to the TLS record buffer.
  • Invisible at the protocol level. A malicious heartbeat request is syntactically identical to a legitimate one — same message type, same fields, just an inflated length. There is no anomalous byte pattern to alert on; pre-patch logging saw nothing unusual.
  • Two years, undetected. Merged into OpenSSL at the end of 2011, shipped in the 1.0.1 release on March 14, 2012, publicly disclosed April 7, 2014 by Google's Neel Mehta and independently by Codenomicon researchers, who coined the name and the (in retrospect understated) bleeding-heart logo.
  • Blast radius at disclosure. Netcraft's widely cited April 2014 survey estimated that roughly 17% of the ~800,000 SSL-secured sites it surveyed — around half a million servers — ran a vulnerable OpenSSL build at the moment of disclosure.
THE NUMBERS THAT MATTER MOST

A private key is typically a few hundred bytes. A single successful heartbeat response over-read of ~64 KB is, in expectation, large enough to contain one if the key happens to sit in a heap region the allocator reuses for TLS record buffers — which OpenSSL's internal free-list allocator made more likely than a naive malloc/free model would suggest, because freed buffers of similar size were recycled into new allocations rather than returned to the OS. CloudFlare's own Heartbleed Challenge in April 2014 confirmed private-key extraction was practical: independent researchers (Fedor Indutny and Ilkka Mattila submitted essentially simultaneously) recovered CloudFlare's private key using nothing but repeated heartbeat requests against an otherwise-unmodified nginx + OpenSSL stack.

ARC 06 · WHY THAT STILL HURTS

Patching the code is the easy 10%

Each fix in §5 stops the bug from recurring. None of them undoes what already happened — and the cleanup cost dwarfs the size of the diff in every single case.

  • Heartbleed: a patch doesn't revoke a stolen key. Every private key that was ever exposed to a heartbeat request while a vulnerable OpenSSL was running has to be treated as compromised forever — there is no way to prove, after the fact, that it wasn't read. That means new keys, new certificates, and CRL/OCSP revocation of every old certificate at a scale (hundreds of thousands of certs) the CA ecosystem had never handled in that short a window. Session tickets and any plaintext that happened to be in memory during an attack window are unrecoverable exposures with no cleanup step at all.
  • Debian: the blast radius is every key ever generated on the affected systems. From the patch landing in 2006 to public disclosure in May 2008, every SSH host and user key, every SSL/TLS certificate, every OpenVPN and DKIM key generated on a Debian- or Ubuntu-based system with the broken package was drawn from a pool of at most 32,768 possibilities per key type and size. The fix wasn't just reverting the patch — Debian had to ship a blocklist of every one of those ~32,768 precomputed weak keys per algorithm/size so tools like ssh and package managers could refuse them outright, and every affected key had to be regenerated. Years later, forgotten embedded devices and appliances built from that window were still found with weak keys.
  • ROCA: you cannot "patch" a sealed smartcard. The flawed key generation ran inside Infineon's closed-source RSALib on hardware security modules, TPMs, and smartcards — silicon that, in many deployments, cannot have its key-generation firmware field-upgraded at all. Estonia had to physically re-key roughly 750,000 national ID cards; Microsoft, Google, Lenovo, Fujitsu, and HP had to issue guidance and in some cases firmware updates for affected TPMs; Yubico ran a token-replacement program for the affected YubiKey 4 series. "Redeploy the fix" here means a multi-year, partly physical logistics operation.
  • Dual_EC: you cannot un-suspect a standard. NIST withdrew Dual_EC_DRBG from SP 800-90A in 2014, but RSA Security's BSAFE toolkit had shipped it as the default random number generator for seven years, reportedly after a $10 million agreement with the NSA (per 2013 Reuters reporting following the Snowden leaks). No cryptographic analysis can retroactively prove whether any specific TLS session protected by a Dual_EC-seeded key was ever actually attacked — the trust damage is permanent precisely because the mechanism, if exploited, would have been silent and left no forensic trace.
THE PATTERN

In every case, the size of the code fix is inversely proportional to the size of the cleanup. A three-line bounds check, a one-line revert, a rewritten key-generation routine, and a standards-committee vote each closed the door — but none of them could reach back through time and un-expose what had already leaked, been guessed, or been generated with a trapdoor in place.

(b) ROCA: primes with a fingerprint baked in

Standard RSA key generation picks two large primes essentially uniformly at random and tests each for primality (typically Miller-Rabin rounds) until two are found — a search over an enormous, structureless space. Infineon's RSALib v1.02.013 instead generated primes of the restricted form:

THE ROCA CONSTRUCTION

p = k·M + (65537a mod M)

where M is a primorial — a fixed product of the first several hundred small primes — and k and a are the only values actually searched over. On an 8-bit smartcard CPU with no hardware big-number unit, this is a real engineering win: instead of generating and primality-testing huge random candidates, the device searches a tiny (k, a) space and gets primes with useful algebraic structure almost for free.

That structure is exactly what makes the modulus fingerprintable: because every affected prime's residue modulo each small factor of M is constrained to lie in the tiny multiplicative subgroup generated by 65537, a quick discrete-log-style test against N mod mi for the small primes mi dividing M reveals — without factoring anything — whether a given public key was generated this way. Once flagged, the small unknowns k and a turn factoring N = p·q into exactly the kind of "recover an RSA factor when part of its structure is already known" problem that Coppersmith's method was built to solve — turning what should be an infeasible search into a bounded lattice computation.

(c) The Debian bug: an entropy pool with one working input

OpenSSL's PRNG (in crypto/rand/md_rand.c) is a hash-based "entropy juicer": RAND_add() mixes new bytes into a running MD5/SHA1 state via MD_Update(); RAND_bytes() extracts pseudo-random output from that state. Deliberately, in three separate places, the OpenSSL developers mixed in buffers that were only partially initialized — reasoning that any real entropy in the uninitialized tail of a buffer could only help, never hurt, and honestly declaring less entropy than the buffer's full size to the running estimate. This was clever, but it made every one of those call sites trigger Valgrind/Purify warnings about "conditional jump depends on uninitialised value" in any application linked against OpenSSL.

In 2006, a Debian maintainer, chasing those warnings, asked the openssl-dev mailing list whether it was safe to delete the offending line inside ssleay_rand_add(). Two replies, in essence, said "go ahead." He removed it — and, because both flagged call sites looked nearly identical in the source, the removal took out the only line that actually fed real entropy into the pool on Debian's systems. What remained still called MD_Update() inside ssleay_rand_bytes() with one genuinely variable input: the process ID. On Linux, the default maximum PID is 32,768 — roughly 15 bits of entropy — meaning every key generated on an affected Debian or Ubuntu system for nearly two years came from one of at most 32,768 possible seeds per key type and architecture.

(d) Dual_EC_DRBG: a state machine with an optional trapdoor

Dual_EC_DRBG's internal state s is a scalar; its two steps use fixed public elliptic-curve points P and Q on a NIST curve (P-256/P-384/P-521):

THE STATE MACHINE

si+1 = x( si · P ) (next internal state)
outputi = truncate( x( si · Q ) ) (bits actually returned, a few bits dropped)

If you know the secret scalar e such that Q = e·P — and only if you know it — a single output block lets you brute-force the handful of dropped bits (a search space of roughly 216), reconstruct x(si·Q) exactly, compute e-1·(si·Q) = si·P, and recover si+1 — the entire future output stream, from one sample. Without e, this requires solving the elliptic-curve discrete-log problem on a 256-bit curve, believed to need on the order of 2128 operations: infeasible.

Dan Shumow and Niels Ferguson, both Microsoft researchers, presented exactly this observation at the CRYPTO 2007 rump session — not a proof of a backdoor, but a demonstration that the design is only safe if nobody who chose the standard's P and Q constants also knows the discrete log relating them. NIST never published a "nothing-up-my-sleeve" derivation for those constants — the one governance step that would have made the suspicion moot.

DUAL_EC AND HEARTBLEED, BY THE SAME YARDSTICK

Heartbleed's attack cost is essentially zero — a single crafted TLS record, no computation, no cryptanalysis, just a network round trip; the "cost" is entirely in how many attempts it takes to land on interesting memory, which is a matter of luck against the allocator, not math. Dual_EC's attack cost is bimodal: with the secret scalar e, recovering all future output from one sample is near-instant arithmetic; without it, you are back to a ~2128-operation elliptic-curve discrete-log problem — believed infeasible with any known method. There is no middle ground, which is exactly what makes a backdoor like this so dangerous: it does not weaken security gradually, it flips a single bit from "unbreakable" to "trivial" for whoever holds the key.

ARC 11 · REAL-WORLD INCIDENTS

What actually happened once these went public

Heartbleed: the challenge, and the breach

Within hours of CloudFlare launching its public Heartbleed Challenge (April 2014) — daring researchers to extract its nginx server's private key using nothing but the bug — two independent teams succeeded: Fedor Indutny and Ilkka Mattila, and separately Rubin Xu, both recovered the key using only repeated heartbeat requests, settling the debate over whether private-key extraction was merely theoretical. Months later, Community Health Systems disclosed a breach affecting approximately 4.5 million patient records, reportedly traced in part to attackers exploiting Heartbleed against a vulnerable device to gain network access — one of the first large breaches publicly linked to the bug.

ROCA: national ID cards and hardware tokens

Because Infineon's RSALib shipped inside embedded secure elements across the industry, ROCA's reach went far beyond web servers: Estonia had to suspend and then physically re-key roughly 750,000 national ID cards; Slovakia faced a similar national eID exposure; Microsoft flagged affected TPMs used for BitLocker and Windows Hello; Google, Lenovo, Fujitsu, and HP issued advisories for laptops with affected TPM chips; and Yubico confirmed the YubiKey 4 series (which used an affected on-chip RSA generator) was impacted, running a token-replacement program for customers relying on RSA-generated keys on those devices.

The Debian bug: quiet, then everywhere at once

Discovered by Luciano Bello in May 2008 after he noticed suspiciously repeated "random" prime numbers, the bug had been shipping since 2006 in every Debian and Ubuntu derivative. The practical fallout was immediate and huge: security researchers published tools that could check any SSH host key or SSL certificate against the full precomputed set of ~32,768 possible keys per type/size/architecture in well under a second, effectively making every affected key public. GitHub's own postmortem at the time found users who had unknowingly generated identical SSH keys to complete strangers.

Dual_EC and Juniper: the backdoor that got hijacked

In December 2015, Juniper Networks disclosed "unauthorized code" in its ScreenOS firmware (CVE-2015-7755 and a related VPN-traffic-decryption flaw) that had modified the constant used with Dual_EC_DRBG in its VPN products. Researchers concluded that whoever planted the code had effectively swapped in their own Q — meaning a third party had converted Dual_EC's theoretical backdoor into a working one, and possibly hijacked a mechanism originally intended for someone else's exclusive use. It remains the clearest real-world demonstration that Shumow and Ferguson's 2007 warning was not academic.

The fix that closed CVE-2014-0160 — two added bounds checks, nothing else:

Ct1_lib.c — the patch, OpenSSL 1.0.1g (7 April 2014)
int
tls1_process_heartbeat(SSL *s)
{
    unsigned char *p = &s->s3->rrec.data[0], *pl;
    unsigned short hbtype;
    unsigned int payload;
    unsigned int padding = 16;

    /* Read type and payload length first */
    if (1 + 2 + 16 > s->s3->rrec.length)
            return 0; /* silently discard, per RFC 6520 §4 */

    hbtype = *p++;
    n2s(p, payload);

    if (1 + 2 + payload + padding > s->s3->rrec.length)
            return 0; /* THE bounds check that was missing: reject any claim
                         the record could not physically contain */

    pl = p;
    /* ... rest of the function is unchanged ... */
}

ROCA-style vulnerable generation contrasted with the FIPS 186-4-compliant approach it should have used:

pseudocodevulnerable structured search vs. standard random generation
// Infineon RSALib v1.02.013 (vulnerable): tiny, fast, FINGERPRINTABLE search
for k in small_range:
  for a in small_range:
    p = k * M + pow_mod(65537, a, M)   // M = primorial, fixed per key size
    if is_probable_prime(p): return p

// FIPS 186-4 Appendix B.3 (compliant): large, slow, STRUCTURELESS search
loop:
  p = random_odd_integer(bitlength / 2)   // full-width CSPRNG draw, no small M
  if miller_rabin(p, rounds=many): return p
WHY IT WAS BUILT THIS WAY

The heartbeat extension exists because DTLS runs over UDP: without TCP's connection state, a peer needs a cheap, explicit "are you still there, and what's the usable packet size" mechanism — hence RFC 6520. The uninitialized-memory-as-entropy trick in md_rand.c existed on the theory that "it can't hurt, and might help" — a reasonable-sounding heuristic that, per Russ Cox's contemporaneous analysis of the fiasco, obscured the code enough that nobody defending it could say with confidence which of two near-identical lines was load-bearing. Infineon's structured primes existed purely for smartcard CPU budgets — full Miller-Rabin over uniformly random 1024-bit candidates is expensive on an 8-bit microcontroller with no big-number hardware. Every one of these choices was defensible in isolation and catastrophic in combination with a missing check, a hasty deletion, or a lack of independent review.

ARC 15 · INTERACTIVE SIMULATOR

Heartbleed replay — a real over-read, computed live

Below is a simulated 512-byte slice of a TLS server's heap. It contains your own request data plus several "secrets" placed by other, unrelated heap allocations — exactly the situation OpenSSL's allocator created in practice by recycling freed buffers. Craft a heartbeat request: type a short real payload, then claim a much larger payload_length. The response is generated by an actual buffer-read function that copies claimed length bytes starting right after your payload — there is no scripted reveal here; if the claimed length reaches far enough into the heap, whatever is really there comes back.
