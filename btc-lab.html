STEP 01 · SETUP

A regtest node in Docker

Regtest is a private, instant blockchain you fully control — no peers required, no sync wait, and blocks are mined on demand with a single RPC call. Every experiment below runs against a real Bitcoin Core daemon, the same binary that runs mainnet. You need Docker with Compose v2, Python 3 on your host (for the small JSON-parsing and hex-manipulation snippets), and about 500 MB of free disk.

Mine the first 101 blocks

A brand-new chain has zero spendable coins — every satoshi in existence on regtest is one you mine yourself.

bash
C createwallet "lab"
ADDR=$(C getnewaddress "" legacy)
echo "mining to: $ADDR"
C generatetoaddress 101 $ADDR
C getbalance
EXPECTED
[
  "1a2b3c...  ← block 1 hash",
  "4d5e6f...  ← block 2 hash",
  ...
  "9f8e7d...  ← block 101 hash"
]
50.00000000
WHY 101, NOT 1

Every block's coinbase output — the newly-created subsidy — is immature for 100 confirmations (Bitcoin Core's COINBASE_MATURITY constant). Mine exactly one block and getbalance reports zero: the 50 BTC exists, but it is consensus-invalid to spend for another 100 blocks. Mine 101 blocks and block 1's coinbase now sits 100 confirmations deep — it just crossed the maturity threshold — while blocks 2 through 101's own coinbases remain immature. That one mature 50 BTC output is what every other experiment in this lab spends from. Run C getbalances to see the split between trusted and immature directly.

Teardown

bash
docker compose down        # stop, keep the chain and wallet
docker compose down -v     # stop and DELETE everything — full reset back to block 0

Several experiments deliberately corrupt state (a forced reorg, a flooded mempool with a shrunk cap). A full reset plus re-mining 101 blocks takes under a minute — use it freely.

Troubleshooting

SYMPTOMCAUSE & FIX
error code: -28 "Loading block index..." The node is still finishing startup. Wait a few seconds and retry — or poll with C -rpcwait getblockchaininfo, which blocks until the RPC server is actually up.
Insufficient funds on a send You haven't mined 101 blocks yet, or your wallet's mature balance is genuinely spent. Check C getbalances — the immature field explains most of these.
error code: -18 "Requested wallet does not exist" Wallets are not auto-loaded across a node restart unless started with -wallet=lab. Run C loadwallet "lab" after any restart.
error code: -19 "Wallet file verification failed" / already loaded createwallet only works once. On every subsequent startup use C loadwallet "lab", not createwallet again.
"min relay fee not met" (code -26) The historical name for this was "insufficient priority" in Bitcoin Core versions before 0.12 — the wording changed, the mechanism (a feerate floor below which the node won't even accept the transaction into its mempool) didn't. Raise the fee or pass an explicit fee_rate to sendtoaddress.
getrawtransaction: "No such mempool or blockchain transaction" Without -txindex=1, this RPC only finds transactions belonging to a loaded wallet or currently sitting in the mempool. Confirm txindex=1 is set — if you enabled it on an existing datadir rather than a fresh one, you also need -reindex once.
Port already allocated Change the host side only, e.g. "18453:18443". Update every -p flag or client config that referenced the old host port.

STEP 04 · PRODUCTION BEST PRACTICES

A cookbook where every number has a reason

Fee estimation — estimatesmartfee

MODEWHENMECHANISM
CONSERVATIVE default Payments that must confirm reliably even through a sudden fee spike — exchange withdrawals, time-sensitive settlement. Weighs a longer confirmation history and biases the estimate upward. Fewer missed targets, costs more on average.
ECONOMICAL Batch payments, internal transfers, anything that can tolerate an occasional extra block of delay. Reacts to a shorter, more recent window of blocks. Cheaper on average, more likely to miss the target during a demand spike.
bash
C estimatesmartfee 6 CONSERVATIVE
REGTEST HAS NO FEE MARKET

With no real, contested mempool history, estimatesmartfee on a fresh regtest node returns {"errors":["Insufficient data or no feerate found"]}. This is expected, not broken — the estimator needs a genuine sample of confirmed feerates to extrapolate from. Generate a batch of varied-fee transactions and confirm several blocks before it produces real numbers, or rely on fallbackfee for lab purposes.

Confirmation counts by value at risk

VALUE TIERCONFIRMATIONSWHY
Low-value / retail0–1The cost of successfully double-spending or reorging one block usually exceeds what's being risked. Many point-of-sale integrations accept zero-conf with double-spend monitoring instead of waiting.
Mid-value3–6Balances user wait time against the (rare but real) cost of a 1–2 block reorg. Six confirmations is the long-standing convention for "final enough" on mainnet.
High-value / treasury moves6–100+Matches or exceeds the deepest reorgs ever observed on mainnet. At sufficient depth, reversing the payment costs more in proof-of-work than the payment is worth.
Coinbase spends100 enforcedNot a policy choice — COINBASE_MATURITY is a consensus rule every node enforces identically.

Address types

TYPEREGTEST PREFIXUSE WHENTRADEOFF
Legacy (P2PKH)m / nMaximum compatibility with very old wallets and services.Largest input size (~148 vB); no weight discount on the signature.
Nested SegWit (P2SH-P2WPKH)2Wallets/exchanges that don't yet parse bech32 but need the SegWit fee discount.Middle ground: witness discount plus a P2SH wrapper you pay for (~91 vB input).
Native SegWit (P2WPKH)bcrt1qDefault for anything new. Cheapest widely-supported standard input (~68 vB) and immune to legacy transaction malleability.Requires bech32-aware software — universal today, wasn't in 2017.
Taproot (P2TR)bcrt1pBest privacy (multisig and single-sig spends look identical on-chain) and the cheapest key-path input (~57.5 vB).Newest — verify every piece of your stack (hardware wallet, exchange, service) actually supports bech32m before relying on it.

Anti-patterns and their specific cost

ANTI-PATTERNWHAT IT COSTS
Trusting 0-conf for high valueclassic mistake An unconfirmed transaction can be replaced (RBF) or double-spent until it's mined. Fine for a coffee, not for a car.
Address reuseEvery reuse links payments together on the public ledger. For legacy ECDSA specifically, a nonce reused across two signatures from the same key leaks the private key outright (the exact class of bug that recovered Sony's PS3 signing key).
Assuming getrawtransaction finds anythingWithout -txindex=1 it only sees wallet and mempool transactions — an arbitrary historical txid returns an error, not an empty result.
A hardcoded fixed feeStuck transactions the moment demand rises. Use estimatesmartfee dynamically, or sign with replaceable=true so you can bumpfee later.
Losing a multisig's redeemScript/descriptorThe keys alone are not enough — without the exact script, the funds are unspendable even though you provably control every private key.
Oversized OP_RETURN payloadsBitcoin Core's default relay policy caps standard OP_RETURN size; oversized ones are non-standard and won't propagate through default-policy nodes even though they're not a consensus violation.

STEP 05 · OPERATIONAL RUNBOOKS

  
Procedures for running Bitcoin infrastructure


  
5.1 · Diagnosing a stuck low-fee transaction

  
Precondition: you have the txid and access to the mempool it was broadcast to.

  
    
    
  1. Confirm it's actually underpaying: bitcoin-cli getmempoolentry <txid> — divide fees.base by vsize and compare against getmempoolinfo's current mempoolminfee and against estimatesmartfee 6.
    2. 
    
  2. Check the ancestor chain: the same entry's ancestorcount / ancestorsize — a long chain of unconfirmed parents can suppress relay even if this one transaction's own feerate looks adequate, because miners evaluate package feerate.
    3. 
    
  3. Confirm it actually propagated: check getrawmempool on more than one node, or a block explorer. A transaction can sit alone in your local mempool if it was ever non-standard and never relayed past your own node.
    4. 
    
  4. Choose the remedy: your own wallet-tracked transaction, signaled replaceable → bumpfee (5.2). Someone else's stuck payment to you → CPFP, spending the unconfirmed output yourself at a high fee.
    5. 
    
  5. If you'd rather cancel and RBF is available, replace it with a trivial-value send back to your own address at a high fee — a full self-double-spend, cheaper than waiting.
    6. 
  


  
5.2 · Safely bumping fees with RBF or CPFP

  
Precondition: RBF requires you to hold the signing key for an input (BIP125 opt-in via a sequence number below 0xfffffffe). CPFP works even for a payment you only received.

  
bash


# RBF — the wallet builds an entirely new transaction spending the same inputs
bitcoin-cli -regtest bumpfee "<stuck-txid>"

# CPFP — spend the unconfirmed output yourself, at a feerate high enough that
# the AVERAGE feerate of parent+child clears the current mempoolminfee
bitcoin-cli -regtest -named sendtoaddress address="<your-address>" amount=0.001 fee_rate=50

  

    
WHAT MINERS ACTUALLY EVALUATE

    
A miner's block template doesn't compare individual transaction feerates in isolation — it evaluates
    ancestor and descendant package feerate. CPFP works precisely because a high-fee child pulls its
    low-fee, unconfirmed parent along with it into the same block. RBF instead replaces the original outright,
    which requires it to have opted in and requires the replacement to pay a strictly higher absolute fee.

  


  
5.3 · Responding to a chain reorg in production

  
    
    
  1. Detect: getchaintips shows more than one branch, or getbestblockhash changes without the expected height increase.
    2. 
    
  2. Treat shallow deposits as reversible. Any credit seen with fewer confirmations than your policy's threshold (5.3 of this lab's own cookbook, §4) must not be treated as final — a reorg can and will un-confirm it.
    3. 
    
  3. Re-verify balances after the reorg settles, once depth is restored. Query the specific outputs you credited via gettxout — if it now returns null, that output no longer exists on the winning chain.
    4. 
    
  4. Corroborate against a second, independently-operated node before making high-value decisions. A single node's view during an active reorg is not authoritative for anyone but itself.
    5. 
    
  5. Alert on getchaintips showing a valid-fork branch within a few blocks of your active tip — that's an early warning a reorg may be forming, before it actually overtakes you.
    6. 
  


  
5.4 · Verifying index requirements before enabling a service

  
Precondition: know exactly which RPCs your service calls before choosing indexes — adding one after initial sync is not free.

  
    
    
  1. Any code path calling getrawtransaction for a txid that isn't the service's own wallet's needs -txindex=1 set at node startup.
    2. 
    
  2. Enabling -txindex=1 on a datadir that has already synced without it requires a one-time -reindex — a full re-scan, not a quick restart.
    3. 
    
  3. Address- or script-level lookups without a full txindex can use compact block filters instead: -blockfilterindex=1, queried with getblockfilter. Cheaper to maintain than a full txindex, but still needs a -reindex if turned on after the fact.
    4. 
    
  4. Confirm what's actually active before assuming: bitcoin-cli getindexinfo reports every enabled index and its sync height.
    5. 
    
  5. For one-off address/UTXO queries with no ongoing index at all, scantxoutset works against the live UTXO set — O(UTXO set size) per call, fine occasionally, not for a hot path (project 2 of this lab uses exactly this).
    6. 
  


  
5.5 · Backing up and restoring a wallet safely

  
    
    
  1. Confirm the wallet type: getwalletinfo's descriptors field. Descriptor wallets and legacy wallets back up differently.
    2. 
    
  2. Descriptor wallet: listdescriptors true — the true reveals private-key-bearing descriptors. Treat that output exactly like a seed phrase; it is one.
    3. 
    
  3. Legacy wallet: backupwallet "/path/to/backup.dat" while the wallet is loaded — this RPC produces a consistent snapshot. Never copy wallet.dat directly off disk while bitcoind is running; you can capture it mid-write.
    4. 
    
  4. Restore: descriptor wallets via restorewallet "name" "backup-path"; legacy wallets by placing the file in the wallets directory and loadwallet.
    5. 
    
  5. Verify before trusting it: check the restored balance and listtransactions against what you expected. If any transaction predates the wallet's recorded birth time, run rescanblockchain to be sure nothing was missed.
    6.

Project 1 · A raw P2PKH send without sendtoaddress

  
Reproduce what the wallet's convenience RPC does internally: pick a UTXO, build the raw transaction, sign
  it, broadcast it — all three steps issued yourself, over the wire, with no library beyond Node's own
  http.

  
javascriptsend.js


const http = require("http");

const RPC = { host: "127.0.0.1", port: 18443, user: "lab", pass: "labpass" };

function rpc(method, params = []) {
  const body = JSON.stringify({ jsonrpc: "1.0", id: "lab", method, params });
  const auth = Buffer.from(RPC.user + ":" + RPC.pass).toString("base64");
  return new Promise((resolve, reject) => {
    const req = http.request({
      host: RPC.host, port: RPC.port, path: "/", method: "POST",
      headers: {
        "Content-Type": "text/plain",
        "Authorization": "Basic " + auth,
        "Content-Length": Buffer.byteLength(body)
      }
    }, res => {
      let data = "";
      res.on("data", c => { data += c; });
      res.on("end", () => {
        const parsed = JSON.parse(data);
        if (parsed.error) reject(parsed.error); else resolve(parsed.result);
      });
    });
    req.on("error", reject);
    req.write(body);
    req.end();
  });
}

(async () => {
  const unspent = await rpc("listunspent");
  if (!unspent.length) throw new Error("no spendable UTXOs — mine 101 blocks first");
  const utxo = unspent[0];
  const dest = await rpc("getnewaddress", ["", "legacy"]);
  const sendAmount = (utxo.amount - 0.0001).toFixed(8);

  const raw = await rpc("createrawtransaction", [
    [{ txid: utxo.txid, vout: utxo.vout }],
    { [dest]: sendAmount }
  ]);
  const signed = await rpc("signrawtransactionwithwallet", [raw]);
  if (!signed.complete) throw new Error("signing incomplete: " + JSON.stringify(signed.errors));

  const txid = await rpc("sendrawtransaction", [signed.hex]);
  console.log("broadcast:", txid);
})().catch(e => { console.error(e); process.exit(1); });

  
Success criteria: node send.js prints a real 64-character txid, and
  bitcoin-cli getmempoolentry <txid> against the container confirms it landed. Extension:
  skip createrawtransaction too — build the version, input, and output bytes yourself per chapter 3's
  serialization format, and confirm decoderawtransaction parses your hand-built hex identically to
  the RPC's own output (experiment 2 walks through exactly this parsing in the other direction).


  
Project 2 · A minimal block explorer

  
List recent blocks, drill into a block's transactions, and look up the UTXOs for an address — three routes,
  no framework, no database of your own.

  
javascriptexplorer.js


const http = require("http");
// reuse rpc() from send.js above

const server = http.createServer(async (req, res) => {
  try {
    const parts = req.url.split("/").filter(Boolean);
    if (parts.length === 0) {
      const tip = await rpc("getblockcount");
      const from = Math.max(0, tip - 10);
      const rows = [];
      for (let h = tip; h > from; h--) {
        const hash = await rpc("getblockhash", [h]);
        rows.push(await rpc("getblockheader", [hash]));
      }
      res.end("<h1>Recent blocks</h1><ul>" + rows.map(b =>
        "<li><a href=\"/block/" + b.hash + "\">" + b.height + "</a> — " +
        (b.nTx || "?") + " tx — " + b.time + "</li>").join("") + "</ul>");

    } else if (parts[0] === "block") {
      const block = await rpc("getblock", [parts[1], 2]);   // verbosity 2: full tx objects inline
      res.end("<h1>Block " + block.height + "</h1><p>merkleroot: " + block.merkleroot +
        "</p><ul>" + block.tx.map(t =>
        "<li>" + t.txid + " — " + t.vout.length + " outputs</li>").join("") + "</ul>");

    } else if (parts[0] === "utxos") {
      const addr = parts[1];
      const scan = await rpc("scantxoutset", ["start", ["addr(" + addr + ")"]]);
      res.end("<h1>UTXOs for " + addr + "</h1><p>total: " + scan.total_amount +
        " BTC across " + scan.unspents.length + " outputs</p><ul>" + scan.unspents.map(u =>
        "<li>" + u.txid + ":" + u.vout + " — " + u.amount + " BTC (height " + u.height + ")</li>").join("") + "</ul>");

    } else {
      res.writeHead(404); res.end("not found");
    }
  } catch (e) { res.writeHead(500); res.end(String(e)); }
});
server.listen(3000, () => console.log("explorer on http://localhost:3000"));

  
Success criteria: the index page lists the last 10 blocks with working links, /block/<hash>
  shows every transaction in that block, and /utxos/<address> matches what
  bitcoin-cli listunspent reports for that same address. Note: scantxoutset
  needs no address index at all — it's a one-shot scan of the live UTXO set, which is why this route works even
  without -txindex, but it's O(UTXO set size) per call. Fine on regtest; on mainnet you'd want a
  real index (5.4) or a dedicated indexing service instead.
