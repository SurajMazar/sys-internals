ARC 01 · EXAM CONTEXT

Where this shows up on test day

S3 storage-class and lifecycle questions map directly onto the two heaviest-weighted domains on the Associate exam, and resurface on the Professional exam wrapped in migration and multi-account constraints. Get comfortable here — it is not a minor topic.

On SAA-C03 this chapter's material is graded primarily against Design Cost-Optimized Architectures (20%) — every storage-class and lifecycle question is a cost question in disguise — and Design Secure Architectures (30%), the single largest domain on the exam, which is where the encryption-option and access-control questions live. The other two domains, Design Resilient Architectures (26%) and Design High-Performing Architectures (24%), round out the 65-question exam (50 scored + 15 unscored, unscored questions indistinguishable from scored ones), 130 minutes, pass mark 720 out of 1000, exam fee $150 at the time of writing.

On SAP-C02 the same S3 mechanics reappear inside larger scenarios — a 500-bucket migration hitting an account quota, a multi-account org needing an unbreakable public-access guardrail — tested against Design for New Solutions (29%), Design Solutions for Organizational Complexity (26%), Continuous Improvement for Existing Solutions (25%), and Accelerate Workload Migration and Modernization (20%). That exam runs 75 questions (65 scored + 10 unscored), 180 minutes, pass mark 750 out of 1000, fee $300 at the time of writing.

WHY THIS TOPIC IS HIGH-YIELD

Almost every S3 scenario question is secretly asking one of three things: (1) which storage class fits this access pattern, (2) which encryption option satisfies this security constraint, or (3) which access-control mechanism (bucket policy / IAM policy / Block Public Access) actually wins when two of them disagree. Master those three decision trees and you will answer the large majority of S3 questions on both exams correctly, including the ones dressed up as EC2 or Lambda questions that happen to read from an S3 bucket.

ARC 02 · THE COMMON WRONG INSTINCT

"Just leave it in Standard, and lock it down with an ACL"

Two instincts show up constantly from candidates who haven't internalized S3's cost and access-control mechanics, and both are plausible-sounding enough to pick under exam time pressure.

Instinct #1 — storage class: "S3 Standard is the default, it's simple, and storage is cheap — just put everything there and don't overthink it." This feels safe because Standard genuinely is the right answer for frequently-accessed data, so candidates anchor on it and stop analyzing the access pattern the scenario is actually describing.

Instinct #2 — access control: "I need to grant one specific principal access to one specific object, so I'll attach an ACL directly to that object." This feels precise and surgical — grant exactly what is needed, on exactly the object that needs it — which is exactly why it is such a durable wrong instinct.

Instinct #3 — encryption: "The bucket has encryption at rest turned on, so the data is secure and access control is a secondary concern." This conflates two independent controls that the exam deliberately tests as separate: encryption protects data on disk; it says nothing about who is allowed to call GetObject through the API with valid credentials.

WHY THESE FEEL RIGHT

Each instinct optimizes for one dimension a candidate can see immediately (simplicity, precision, "it's encrypted") while ignoring the dimension the question is actually testing (cost over time, operational scale, and the fact that authorization and confidentiality are different problems). §3 quantifies exactly why each one fails.

ARC 03 · WHY IT'S WRONG

The mechanism behind each trap

Why "everything in Standard" fails on cost. S3 Standard is priced for frequent, low-latency access with no retrieval fee and no minimum storage duration — exactly right for hot data, and a real cost disadvantage for anything accessed rarely. The IA and Glacier tiers trade a lower per-GB storage cost for a real minimum storage duration commitment and a real per-GB retrieval fee: you are billed as if the object stayed for the minimum period even if you delete or transition it sooner, and you pay to read it back. Misapplied in the other direction — putting frequently-accessed data into an IA or Glacier tier to save on storage — the retrieval fees can erase the storage savings entirely, because you're now paying a per-GB fee on every read of data you touch constantly. The exam tests both directions of this mistake.

Why ACLs fail on access control. S3 access control list entries are per-object (or per-bucket) grants with no central place to audit "who can read what" across a bucket with millions of objects — you would need to inspect ACLs object by object. AWS's own current guidance is to avoid ACLs in nearly all cases and use bucket policies (one JSON document, one place to audit, applies to every object by prefix or in full) or IAM policies (attached to the principal, works across every bucket that principal touches) instead. ACLs also predate IAM and interact awkwardly with cross-account ownership — a legacy mechanism kept for backward compatibility, not a recommended pattern.

Why "it's encrypted, so it's secure" fails. Server-side encryption protects the bytes sitting on disk from someone who somehow obtains the raw storage medium — it does nothing to stop a principal with a valid, overly broad IAM policy from calling GetObject through the normal S3 API and receiving the decrypted plaintext, because S3 decrypts transparently for any request that is authorized. Encryption-at-rest and access control are orthogonal controls: one protects against physical/storage compromise, the other protects against API misuse. The exam constructs scenarios specifically to test whether you conflate the two.

THE PATTERN TO INTERNALIZE

Every one of these traps is a version of "one control looks sufficient, but it only covers one axis." Storage class controls cost-for-a-given-access-pattern. Encryption controls confidentiality-at-rest. Bucket/IAM policy plus Block Public Access controls who can call the API at all. Three separate levers; the exam expects you to reach for the right one, not the most familiar one.

The real storage-class decision tree

Storage-class decision treeSTEP-BY-STEP

The same "which one satisfies the constraint" logic applies to encryption. A short version of that decision:

  • Default, no special requirement: SSE-S3 — AWS manages the keys entirely, zero configuration, encryption is on by default for every bucket today.
  • Need an audit trail of every key use, or per-key access policies / rotation control: SSE-KMS — every decrypt call against the KMS key is logged to CloudTrail, and the key itself has its own IAM-style policy independent of the bucket.
  • Need to supply and control the encryption key yourself, with AWS never persisting it: SSE-C — you send the key with every request; S3 uses it once and does not store it.
  • Need AWS to never see the plaintext or the key at all: client-side encryption — encrypt before the object ever leaves your application.

DURABILITY DOESN'T CHANGE — AVAILABILITY DOES

Every S3 storage class except One Zone-IA is designed for 99.999999999% ("11 nines") durability — the same number, regardless of class, because durability comes from redundancy across multiple Availability Zones. One Zone-IA trades that AZ redundancy away for a lower price: your objects live in a single AZ, and a full AZ loss can mean object loss. That's a deliberate, real tradeoff the exam will test — it is never the right answer for data you cannot regenerate.

ARC 06 · LIMITS, QUOTAS & EDGE CASES

The fine print the correct approach still has to respect

Bucket quota — lead with the current number. As of this writing, the default quota is 10,000 buckets per account, raised from the old default of 100 in November 2024. The exam may still reference the old 100-bucket figure in older material — if you see "100 buckets," treat it as a stale assumption, not a hard current limit. Either way, the deeper lesson holds regardless of the number: a "bucket per tenant/customer" pattern that scales into the thousands is usually the wrong design — prefer key prefixes inside fewer buckets, and request a quota increase only when you have a genuine reason to need more buckets, not as a workaround for a bad naming pattern.

Other limits and edge cases the exam likes to test:

  • Minimum storage duration charges are real. Standard-IA and One Zone-IA bill for a minimum period even if you delete or transition an object earlier; Glacier's tiers carry longer minimums still. Design lifecycle transitions with these commitments in mind — transitioning an object into IA one week before deleting it does not save money.
  • Small objects get penalized in IA/Glacier tiers. AWS bills IA and Glacier-tier objects as if they were at least a certain minimum size — commonly cited as roughly 128 KB for the IA classes, with additional small per-object overhead in the Glacier tiers. Archiving a directory of many tiny log files into Glacier can transition those objects into "billed at the minimum" territory and quietly erase most of the expected savings — a genuine, testable edge case, not a rounding error.
  • MFA Delete requires root, not just any MFA-enabled IAM user. Once enabled on a versioned bucket, permanently deleting an object version or changing the bucket's versioning state requires the bucket owner's root account credentials plus a valid MFA code — an IAM user with their own MFA device enabled is not sufficient. This is a deliberate, high-friction control for exactly the operations that matter most.
  • Versioning is one-way to "on." Once you enable versioning on a bucket, you cannot fully disable it again — you can only suspend it, which stops creating new versions going forward but keeps every version already created. Plan for this before enabling it on a bucket where storage growth from version history is a concern.

WHY THIS SHAPE, NOT A SIMPLER ONE

Every layer here answers a different exam question. Versioning + lifecycle answers "how do we recover from accidental overwrite without paying to keep every old version in Standard forever." No single control does all three jobs — that's precisely why the exam layers them.

ARC 09 · DECISION FRAMEWORK

The single most exam-relevant table in this chapter

Access control: which mechanism actually wins

MECHANISMSCOPEUSE WHENEXAM TRAP
Bucket policyOne JSON doc, applies to the bucket (and objects by prefix) You need one auditable, centrally-managed access rule for a bucket — cross-account grants, VPC-endpoint-only access, deny-by-default baselines. exam-favored answer for "control access to this bucket" scenarios.
IAM policyAttached to a user/role/group, applies across every bucket that principal touches The access rule is really about what a principal (an application role, a team) can do everywhere, not about one specific bucket. Candidates under-use this when the real constraint is on the principal, not the bucket.
ACL (legacy)Per-object or per-bucket grant, no central audit view Almost never for new designs — AWS's own current guidance is to avoid ACLs in favor of policies. the "surgical grant" trap — feels precise, is actually unauditable at scale.
Block Public AccessAccount- or bucket-level switch, four independent settings You want a guarantee that overrides any policy or ACL that would otherwise allow public access — the correct answer whenever a scenario says "must never become public, even by accident." Candidates assume a permissive bucket policy "wins" — it does not, if Block Public Access is on.

ARC 13 · CLI / CODE REFERENCE

The documents the exam expects you to recognize on sight

reference-bucket-config/
├── ● lifecycle-policy.json — multi-stage transitions + expiration rule
├── ● bucket-policy.json — deny-by-default, allow only a VPC endpoint + one role
├── ● encryption-config.json — default SSE-KMS with a customer-managed key
└── public-access-block.json — all four Block Public Access settings enabled
JSONlifecycle-policy.json — illustrative example syntax
{
  "Rules": [
    {
      "ID": "archive-old-versions",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      // current version: age into cheaper tiers before expiring
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 90,  "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 },
      // noncurrent (old) versions: age faster, then delete
      "NoncurrentVersionTransitions": [
        { "NoncurrentDays": 30, "StorageClass": "GLACIER" }
      ],
      "NoncurrentVersionExpiration": { "NoncurrentDays": 180 }
    }
  ]
}
JSONbucket-policy.json — deny public, allow only the VPC endpoint
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnlessFromVpce",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::reference-bucket", "arn:aws:s3:::reference-bucket/*"],
      "Condition": {
        "StringNotEquals": { "aws:sourceVpce": "vpce-0123456789abcdef0" }
      }
    }
  ]
}
bashillustrative AWS CLI v2 syntax
# apply the lifecycle policy
aws s3api put-bucket-lifecycle-configuration \
  --bucket reference-bucket --lifecycle-configuration file://lifecycle-policy.json

# enable default encryption with a customer-managed KMS key
aws s3api put-bucket-encryption \
  --bucket reference-bucket --server-side-encryption-configuration file://encryption-config.json

# block all four public-access vectors, account-wide
aws s3api put-public-access-block \
  --account-id 111122223333 \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
WHY THE EXAM CARES ABOUT THIS SYNTAX

You will not be asked to write JSON from scratch on the multiple-choice exam, but you will be shown a policy or lifecycle document and asked "what does this actually do" or "what's missing." Recognizing that NoncurrentVersionExpiration only affects old versions, that a Deny statement with a Condition is how you pin access to one VPC endpoint, and that put-public-access-block can run at the account level (not just per-bucket) are exactly the reading-comprehension skills these questions test.

GATE · EXAM-DAY TAKEAWAYS

The five things most likely to be tested

If you remember nothing else from this chapter, remember these: (1) unknown or changing access pattern → Intelligent-Tiering, not a guess between Standard and an IA class. (2) IA and Glacier tiers carry a real minimum storage duration and a real per-GB retrieval fee — cheap storage is not free storage. (3) bucket policies and IAM policies are the current recommended access-control tools; ACLs are legacy and Block Public Access overrides all of them when enabled. (4) encryption-at-rest and access control are independent controls — SSE-KMS buys you an audit trail via CloudTrail, not a substitute for a correct bucket/IAM policy. (5) the default bucket quota is 10,000 per account today (not the old 100), but a bucket-per-tenant design is still the wrong pattern regardless of the number.
