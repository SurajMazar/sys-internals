ARC 13 · CODE WALKTHROUGH

Where the enforcement actually lives

Lightning itself is not in Bitcoin Core — it is a separate peer-to-peer protocol (specified by the BOLTs and implemented by LND, Core Lightning, Eclair, and others) that only ever touches the base layer at open and close. What is in Core, and load-bearing for every claim this chapter makes, are the two opcodes that make timelocked, revocable outputs enforceable by consensus rather than by promise: OP_CHECKSEQUENCEVERIFY (the relative delay on to_local) and OP_CHECKLOCKTIMEVERIFY (the absolute HTLC timeout). Read those first, then the BOLT #3 script text they enforce.

First, the two consensus primitives. Both are soft-fork opcodes — before their respective BIPs they were OP_NOP3/OP_NOP2, no-ops that scripts could include harmlessly; the soft fork redefined them to fail the script unless a condition holds, which is why old, non-upgraded nodes still accept these transactions (they see a no-op) while upgraded nodes enforce the new rule:

C++script/interpreter.cpp — OP_CHECKSEQUENCEVERIFY (simplified, faithful to structure)
case OP_CHECKSEQUENCEVERIFY:
{
    // BIP112: the top stack item is the relative-locktime an input
    // MUST have waited before this script can succeed -- e.g. Lightning's
    // to_self_delay guarding a commitment's to_local output.
    if (!(flags & SCRIPT_VERIFY_CHECKSEQUENCEVERIFY)) {
        break; // pre-fork: behaves as OP_NOP3, always succeeds
    }
    if (stack.size() < 1)
        return set_error(serror, SCRIPT_ERR_INVALID_STACK_OPERATION);

    const CScriptNum nSequence(stacktop(-1), fRequireMinimal, 5);
    if (nSequence < 0)
        return set_error(serror, SCRIPT_ERR_NEGATIVE_LOCKTIME);
    if (nSequence.GetInt64() & CTxIn::SEQUENCE_LOCKTIME_DISABLE_FLAG)
        break; // script author explicitly opted out of the check

    // checker delegates to the actual spending input's nSequence field
    // and the UTXO's confirmation depth -- this is where "has enough
    // blocks actually passed since this output confirmed" gets decided.
    if (!checker.CheckSequence(nSequence))
        return set_error(serror, SCRIPT_ERR_UNSATISFIED_LOCKTIME);
    break;
}
C++script/interpreter.cpp — OP_CHECKLOCKTIMEVERIFY (simplified)
case OP_CHECKLOCKTIMEVERIFY:
{
    // BIP65: the top stack item is an ABSOLUTE block height or
    // timestamp before which this script cannot succeed -- Lightning's
    // HTLC timeout branch: "Bob can reclaim after block T if Carol
    // never revealed the preimage."
    if (!(flags & SCRIPT_VERIFY_CHECKLOCKTIMEVERIFY)) {
        break; // pre-fork: OP_NOP2, always succeeds
    }
    const CScriptNum nLockTime(stacktop(-1), fRequireMinimal, 5);
    if (nLockTime < 0)
        return set_error(serror, SCRIPT_ERR_NEGATIVE_LOCKTIME);
    if (!checker.CheckLockTime(nLockTime))
        return set_error(serror, SCRIPT_ERR_UNSATISFIED_LOCKTIME);
    break; // note: this only VERIFIES -- it does not consume the
                // stack item, so scripts follow it with OP_DROP
}

Now the scripts BOLT #3 actually builds from those two opcodes. This is the offered-HTLC witness script — the one Alice's commitment holds, giving Bob two ways in and giving Alice one, exactly matching §8(c)'s derivation:

Script (BOLT #3)offered_htlc_script — three spending branches, annotated
# Branch 1 (fastest path): remote node reveals the preimage and
# claims immediately -- this is Bob claiming from Alice's HTLC.
OP_DUP OP_HASH160 <RIPEMD160(revocationkey)> OP_EQUAL
OP_IF
    # Branch 0 (always available): counterparty proves it holds the
    # REVOCATION key for this exact commitment -- i.e. this state was
    # revoked and is being cheated with. Immediate, no delay, no HTLC
    # condition at all: revocation always wins.
    OP_CHECKSIG
OP_ELSE
    <remote_htlcpubkey> OP_SWAP OP_SIZE 32 OP_EQUAL
    OP_NOTIF
        # Branch 2 (timeout path): NOT a 32-byte preimage on the stack --
        # must be Alice reclaiming after CLTV expiry.
        OP_DROP 2 OP_SWAP <local_htlcpubkey> 2 OP_CHECKMULTISIG
    OP_ELSE
        # Branch 3 (success path): a real 32-byte value was given --
        # verify it actually hashes to H before allowing the claim.
        OP_HASH160 <RIPEMD160(SHA256(R))> OP_EQUALVERIFY
        OP_CHECKSIG
    OP_ENDIF
OP_ENDIF
WHY THIS WASN'T BUILT INTO BITCOIN CORE ITSELF

Three reasons, and they generalize to most Layer 2 design: (1) iteration speed — Lightning's protocol has revised its transaction formats, added anchor outputs, and is still evolving PTLC support; a consensus change to Bitcoin Core requires the entire network to upgrade, which takes years, while a BOLT revision only needs the participating Lightning nodes to agree. (2) minimality — Core's job is to provide the smallest stable set of primitives (timelocks, multisig, hash locks) that many different Layer 2 protocols can build on; baking Lightning-specific logic into consensus would privilege one design over channel factories, statechains, or whatever comes next. (3) failure containment — a bug in a Lightning implementation can lose funds in channels using that implementation; a bug in Core's script interpreter is a critical vulnerability across every Bitcoin holder simultaneously. Keeping the enforcement primitives generic and small in consensus, and the actual protocol logic in independently-implemented, independently-upgradable software, is the same minimal-trusted-computing-base instinct chapter 4's Script chapter argued for when explaining why loops were excluded.
