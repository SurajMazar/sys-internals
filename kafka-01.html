Genesis: Why a Log,
Not a Queue

Every topic you have ever produced to or consumed from is, underneath, a directory of append-only files and a single integer — an offset — that a consumer, not the broker, owns. This chapter derives that architecture from the actual integration problem LinkedIn had in 2010: why a unified log beats a mesh of point-to-point pipelines, why a log beats a classic message queue too, and exactly which files and classes make the append-only guarantee real.

ARC 01 · THE PROBLEM

LinkedIn, 2010: every pipe was somebody's weekend project

By 2010, LinkedIn had dozens of systems that produced data — user activity trackers, the primary member-profile database, application server logs, monitoring counters — and dozens of systems that consumed it: full-text search indexing, the "People You May Know" recommendation engine, fraud and security review, and the Hadoop data warehouse feeding offline analytics. Every one of those needed a live feed from every relevant source, and in the absence of a shared integration layer, engineers built exactly what you'd expect: a bespoke, direct connection for each pair.

Unpack what "bespoke" means in practice, because the cost is not just the wiring, it's what has to be decided independently for every single pair:

  • Serialization format — the activity-tracking team picks a hand-rolled binary format; the DB-change team ships JSON; nobody agrees, so every consumer writes its own deserializer for every producer it talks to.
  • Delivery semantics — is it push (the producer calls the consumer) or pull (the consumer polls the producer)? At-least-once or best-effort? Every pair answers this independently, usually by accident rather than design.
  • Backpressure and retry — if the consumer is slow or down, what does the producer do? Buffer in memory and risk an OOM? Drop data? Every team wrote its own answer, and most of those answers were "we'll deal with it later."
  • Operational ownership — each pipeline is a distinct thing that pages someone at 3 a.m. There is no shared runbook, because there is no shared system — just N² independent one-off integrations, each fragile in its own particular way.

Now do the arithmetic every engineer at LinkedIn was implicitly doing in their head. With P distinct producer systems and C distinct consumer systems, and every consumer needing data from every relevant producer, the number of point-to-point pipelines you need in the worst case is P × C — not P + C, not P + log(C), the full product. Add one new producer (say, a new mobile-app event stream) and you don't add one connection — you add up to C new connections, one bespoke integration per existing consumer, each with its own format and failure mode. Add one new consumer (a new fraud-detection service) and symmetrically you add up to P new connections, one per existing producer. Growth is multiplicative on both axes at once — this is the textbook shape of an O(N²) integration explosion, and it is the single fact that makes ad hoc point-to-point data plumbing an organizational dead end, independent of how good any individual pipeline is engineered.

The insight that resolves this — the one Jay Kreps, Neha Narkhede, and Jun Rao built Kafka around — is disarmingly simple to state and expensive to have not had: make every producer write to one shared place, and make every consumer read from that same place, independently, at its own pace. Integration work then scales as P + C, not P × C — a new producer writes to the log once, a new consumer reads from the log once, and neither has to know or care how many systems sit on the other side. Sections 3 through 6 re-derive why this specific shape — a durable, ordered, replayable log, not a database and not a classic message queue — is the one that actually delivers on that promise.

WHY THIS MATTERS FOR THE NEXT 14 CHAPTERS

Everything else in this course is a consequence of one decision made here: the log is the product, and the broker's job is to store and serve it, not to babysit consumers. Chapter 2's broker architecture, chapter 3's partitioning and replication model, and chapter 4's producer internals are all downstream of the fact that Kafka chose "dumb broker, smart client, shared durable log" over "smart broker with per-consumer state." Learn that framing now; every internal mechanism in this course refers back to it.

DEEP CONTEXT · WHY "THE LOG" ESSAY MATTERS

Jay Kreps' December 2013 essay, "The Log: What every software engineer should know about real-time data's unifying abstraction," is not marketing copy — it is the clearest existing explanation of why Kafka is shaped the way it is, written by one of its designers after two years of production experience. Its central claim, which this chapter re-derives from first principles rather than takes on faith, is that a log is simultaneously a storage mechanism and a messaging mechanism — and that collapsing those two historically separate concerns onto one abstraction is what makes the unified-integration story actually work end to end.

ARC 03 · NAIVE SOLUTION

Attempt #1: wire every producer to every consumer directly

Derive the architecture honestly, the way LinkedIn's engineers actually arrived at it — incrementally, pair by pair, each connection solving a real and urgent problem in isolation. Here is what that looked like, rendered as an illustrative configuration sketch of five real data sources feeding four real downstream systems, each pair wired with whatever protocol was fastest to ship that quarter:

pseudocodenaive_pipeline.py — the strawman, annotated (illustrative of LinkedIn's pre-Kafka shape)
# Five producers, four downstream systems. Every arrow below is a SEPARATE,
# hand-rolled integration — its own protocol, its own retry logic, its own on-call.

SOURCES = {
    "user_activity_events":  push_to(["search_index", "recommendation_svc", "warehouse_etl"],
                                    proto="custom_tcp"),
    #   custom_tcp: the "good" link -- until the schema changes and both ends
    #   must redeploy in lockstep, because there is no shared contract to check against.

    "member_profile_db_changes": push_to(["search_index", "fraud_review", "warehouse_etl"],
                                    proto="jdbc_poll"),
    #   jdbc_poll: consumer polls a MySQL changelog table every 30s. Missed updates
    #   under load are silent; a schema migration breaks the query with no warning.

    "app_server_logs":       push_to(["monitoring_svc", "warehouse_etl"],
                                    proto="syslog_forward"),
    #   syslog_forward: UDP, best-effort. "Best effort" quietly becomes "lossy"
    #   the moment the network or the receiver is under any real pressure.

    "ad_click_events":       push_to(["fraud_review", "recommendation_svc", "warehouse_etl"],
                                    proto="rest_callback"),
    #   rest_callback: consumer exposes an HTTP endpoint; producer retries on 5xx
    #   with backoff logic it wrote itself. Nobody agreed on idempotency semantics.

    "search_query_log":      push_to(["recommendation_svc", "warehouse_etl", "monitoring_svc"],
                                    proto="nfs_file_drop"),
    #   nfs_file_drop: producer writes hourly files to a shared mount; consumer
    #   polls the directory. File-naming races and partial-read bugs are routine.
}
# Thirteen distinct producer -> consumer edges above, FIVE distinct wire
# protocols, and not one shared answer to "what happens when the consumer is down?"

Nothing here is a strawman built to be knocked down cheaply — every one of these integration styles is a legitimate, widely used pattern in isolation. jdbc_poll is how countless CDC pipelines still start life; rest_callback is a completely reasonable choice for a single low-volume integration. The failure is not any individual link — it's what happens when you need thirteen of them, each carrying a different, unstated contract about format, delivery guarantee, and failure behavior, and then you need a fourteenth next quarter.

ARC 04 · WHY IT FAILS

Quantify it: the exact formula, and where LinkedIn actually landed on it

Be precise about which topology produces which formula, because the two get conflated constantly. If every one of N systems is a symmetric peer that might need to talk to any other — a full mesh — the worst-case edge count is the familiar N(N-1)/2. That is not quite LinkedIn's shape. LinkedIn's systems were overwhelmingly either producers (activity trackers, the profile database, ad-click capture) or consumers (search, recommendations, fraud review, the warehouse) — a bipartite graph, not a full mesh. For P producer systems and C consumer systems, the worst-case edge count is P × C: every consumer potentially needs a direct line to every producer whose data it depends on. Both formulas are quadratic in the number of systems; the bipartite P×C framing is simply the more accurate description of which specific pairs of systems were actually exchanging data.

Watch how fast this compounds as an organization grows past its first few pipelines:

Each of those pipelines is not a fixed one-time cost — it's a standing liability. Every one of them has its own serialization format to keep in sync as schemas evolve, its own retry and backpressure behavior (usually under-specified), and its own operational surface: something that pages a specific team when it breaks, with no shared tooling or shared mental model for diagnosing the failure. Multiply "several hundred pipelines" by "each one occasionally breaks in a way only its original author fully understands," and you get an organization that spends more engineering time maintaining plumbing than building the products the plumbing was supposed to serve.

THE NUMBERS THAT MOTIVATED KAFKA

Twenty pipelines already means twenty independent decisions about serialization, delivery semantics, and failure handling — a small team can just about hold that in its head. At LinkedIn's actual reported scale, "several hundred" point-to-point pipelines meant several hundred independent decisions, several hundred places schema drift could silently break a consumer, and several hundred distinct on-call burdens with no shared runbook. The fix on offer wasn't "write better point-to-point pipelines" — it was to change the topology from P×C to P+C by inserting one shared, durable, replayable layer that every producer writes to once and every consumer reads from independently. That reframing — plumbing as a first-class piece of infrastructure, not a byproduct of whichever two teams needed to talk this month — is the entire reason Kafka exists.

ARC 06 · WHY THAT STILL HURTS

Even "one central broker" has a fatal flaw — if it thinks in queues

Candidate (c) from §5 — a single central message broker in the classic JMS/AMQP sense — genuinely solves the topology problem: every producer sends to one broker, every consumer reads from that same broker, and you're down to P+C connections. It fails for a completely different reason, and understanding why is what makes the log's design feel inevitable rather than arbitrary.

A classic queue's core contract is consume-deletes: when a consumer successfully processes a message and acknowledges it, the broker removes it (or, in some queue implementations, marks it consumed and eventually garbage-collects it). That single design decision — delete or mark on ack — forces the broker to maintain, for every message currently in flight, per-message, per-consumer acknowledgment state: a flag, a pointer, or an entry in a delivery-tracking table that says "has consumer X seen this message yet?" This is fundamentally different from a pure sequential append. It's random-access, mutable metadata that grows with the number of unacknowledged messages in flight, and it has to be consulted and updated on every single ack, every single redelivery timeout, every single consumer that might be behind.

Now ask the question that actually breaks this model for LinkedIn's use case: what happens when two independent teams — search indexing and the data warehouse — both need to read the same stream of activity events, at wildly different rates, for different purposes? In a classic queue, once search indexing acks a message, it's gone — the warehouse job, if it's running an hour behind, can no longer see it unless the broker was configured with a separate durable queue (and thus a separate physical copy of every message) per consumer group. Multiply that by every one of LinkedIn's dozens of consumer systems and you've reintroduced a form of the fan-out problem you were trying to eliminate — now paid for in duplicated storage and duplicated per-message ack-bookkeeping, rather than duplicated point-to-point wiring.

  • Replay becomes structurally impossible. Once a message is acked and deleted, there is nothing left to reread. A new consumer that wants to backfill from history, or an existing consumer recovering from a bug that silently corrupted its last hour of processing, simply cannot — the data isn't there anymore, by design.
  • The ack-state itself caps throughput. Per-message-per-consumer flags are exactly the kind of structure that stays fast while small and in memory, and degrades — toward effectively random-access I/O — as the number of unacknowledged messages and the number of independent consumer groups both grow. The broker's hot path now does real bookkeeping work per message per consumer, not just "write these bytes."
  • Multiple independent consumer groups at different speeds are the common case, not the exception. Search indexing, fraud review, and the warehouse were never going to read at the same rate — a design that only works cleanly for a single consumer group, or that requires N physical copies of the data for N groups, does not fit LinkedIn's actual shape.

Section 7 introduces the architecture that resolves this by making one inversion: instead of the broker tracking, per message, which consumers have seen it, the consumer tracks, for itself alone, how far into an immutable, never-deleted-on-read log it has read. That single inversion is the entire subject of §8.

ARC 08 · INTERNAL IMPLEMENTATION

The append-only log, derived from first principles, and the inversion that makes it work

(1) The append-only log as a data structure

Start from the simplest possible durable, ordered structure you could build and ask what it has to look like. Writes must be pure sequential appends — no seeking, no in-place mutation, nothing but "write these bytes after the last bytes." Reads must be positional — given an offset, an integer index not unlike an array index, return the record at that position. And critically: a read must never mutate the structure. Once you accept that constraint, a remarkable property falls out for free — because reading never changes anything, an arbitrary number of independent readers can read the same log, at wildly different positions, at wildly different rates, and impose zero additional cost on the write path and zero coordination cost between readers. This is precisely what Kafka's UnifiedLog (core/src/main/scala/kafka/log/UnifiedLog.scala) and its constituent LogSegment objects implement: a partition's data lives as a sequence of segment files, each pair consisting of a .log file of the records themselves and a sparse .index file mapping a small sample of offsets to byte positions, rolled to a new segment at a configured size or time boundary and managed end-to-end by LogManager.

(2) Contrast with the classic JMS/AMQP queue broker model

Re-examine §6's queue broker with this data-structure lens. A queue deletes (or marks-and-later-reclaims) a message on consumer acknowledgment. To support that, the broker must maintain, per message, per consumer, a flag or pointer recording delivery/ack state — and because acks can arrive out of order, get redelivered on timeout, or come from any of several competing consumers in a work-queue pattern, that bookkeeping structure is randomly accessed and repeatedly mutated, not appended once and left alone. It is the structural opposite of a pure append: where the log's write path is "always the tail, never revisit," the queue's ack path is "look up this specific message's state, for this specific consumer, and flip it" — over and over, for every message, for every consumer. That is what caps a classic broker's throughput as unacked volume or consumer count grows, and it is precisely why deleting a message on ack makes replay structurally impossible: the bytes are gone, not just marked as read.

(3) Kafka's inversion: the consumer owns its offset, not the broker

Here is the single design decision this whole chapter has been building toward. Instead of the broker tracking, per message, which consumers have seen it, the consumer group tracks, for itself alone, a single integer — its current offset in a given partition — and periodically commits that integer back to Kafka. That commit is itself just a write to another partitioned log: the internal, compacted __consumer_offsets topic, keyed by (group, topic, partition), with the current offset as the value, handled broker-side by the GroupCoordinator role (chapter 5 covers group coordination and rebalancing in full). The consequence: the broker's per-consumer-group state is one committed integer, not a growing table of per-message flags. Whether one consumer group or fifty are reading a partition, the broker's produce path and the bytes on disk are completely unaffected — every group is simply asking to be handed bytes starting at whatever offset it names in its next Fetch request.

(4) Consequences of the inversion

  • Replay is free. Rewind a consumer group's committed offset (to 0, to a timestamp, to any earlier value still within the retention window) and the exact same on-disk bytes are simply reread from there — no special "replay mode," no broker-side reconstruction, because the data was never deleted on read.
  • New consumers can always backfill from the beginning. A brand-new fraud-detection service can start at offset 0 on day one and process a full history of retained events with the exact same Fetch mechanism a live, caught-up consumer uses.
  • A buggy consumer's fix is "reprocess." If a consumer shipped a bug that mis-handled the last six hours of data, the fix is: rewind its committed offset by six hours and let it reprocess with corrected code — nothing else in the system needs to be touched.
  • The broker's write path is invariant to consumer count and speed. Whether zero consumer groups or fifty are attached, whether they're all caught up or all badly behind, the produce path is the same single sequential append it always was.

(5) The log as a unification of messaging and storage

This is Jay Kreps' central framing in "The Log": a durable, ordered log is simultaneously a storage mechanism (a system of record you can query positionally, replay, and audit) and a messaging mechanism (a real-time feed you can tail for new arrivals) — the same bytes, the same abstraction, serving both roles at once, rather than a database for one and a message bus for the other. This isn't a novel invention so much as a recognition of a pattern that already existed twice, in different disguises: a database's write-ahead log (WAL) is exactly this shape — an append-only, ordered record of intent to change state, from which the actual table state is derived. And state-machine replication — the classic distributed-systems technique where a deterministic state machine fed the same ordered sequence of inputs on every replica converges to the same state — is the same idea applied to whole systems rather than one database's internals. Event sourcing takes it a step further as an application-architecture pattern: the log is the single source of truth, and every materialized view, cache, or downstream table is simply a deterministic computation over that log, rebuildable from scratch at any time. Kafka's partition log is the general-purpose, horizontally scaled infrastructure version of all three ideas.

(6) Partitions: the unit of parallelism, and the one ordering guarantee you actually get

A single, globally ordered log sounds appealing until you cost it out: a single total order across all writers implies, in the limit, a single writer, appending to a single physical location — one disk, one lock, one thread of control deciding what happens next. That's a hard ceiling on throughput no matter how good the hardware is, and it's exactly the constraint Kafka refuses to accept. The resolution is to split a topic into partitions — independent, individually ordered logs, each of which can live on a different broker, on a different disk, and be appended to and read from fully in parallel with every other partition. The guarantee you keep is precise and worth stating exactly: total order is guaranteed only within a single partition — its offsets form a strictly increasing sequence — and there is no ordering guarantee across partitions of the same topic, even for messages produced by the same producer. What you get in exchange for giving up global order is the thing that actually matters in practice: a Partitioner hashes a message's key (when one is supplied) to a partition number, so every record for a given key — a given user ID, a given order ID — always lands in the same partition, in append order, forever (as long as partition count is stable — chapter 3 covers what changes when you repartition). Per-key ordering, which is what most real applications actually need, survives fully parallel writes and reads.

HARDWARE COROLLARY: WHY SEQUENTIAL I/O IS THE WHOLE GAME

A modern spinning disk does 100-200 random seeks per second but can stream sequentially at hundreds of MB/s — a gap of several orders of magnitude that SSDs narrow but do not eliminate (random writes still cost more than sequential ones, and the OS page cache rewards sequential access patterns regardless of the underlying device). Because every partition's append is purely sequential and every read is a bounded seek plus a sequential scan forward, Kafka's broker gets near-hardware-limit throughput essentially for free, without exotic buffer-pool engineering. A classic queue broker, by contrast, is doing random-access reads and writes against its per-message ack-bookkeeping structure on every operation — the exact pattern sequential logs are designed to avoid. §10 turns this into a quantified performance comparison.

ARC 10 · PERFORMANCE CHARACTERISTICS

Big-O, and why the gap between the two models grows with scale

State the complexity precisely rather than by vibes. An append to the log's active segment is O(1) amortized — it is a buffered, sequential write to the tail, occasionally rolling to a new segment file, a bounded and infrequent cost. A positional read at a given offset is effectively O(1) I/O in practice: locate the correct segment by its base-offset (a directory lookup among a small number of open segments), then binary-search the segment's small, sparse in-memory .index — technically O(log k) over k index entries, where k is deliberately kept small (an index entry every few KB of log, not every record) — to find the nearest indexed byte position, then scan forward a bounded distance. None of this cost depends on how many consumer groups are reading, or how far behind any of them are.

Now compare the classic queue's per-message-per-consumer ack bookkeeping. Each individual ack lookup or update can be made O(1) with a good enough hash structure — but the aggregate working set of that metadata grows with (unacknowledged messages) × (consumer groups), and once that working set exceeds what fits comfortably in memory, it starts behaving like random-access I/O: exactly the access pattern sequential disk and page-cache design is built to avoid. The log model is insensitive to consumer-group count by construction; the queue model's effective cost per operation grows with it. That is the whole performance story of this chapter, and the chart below makes it concrete rather than asserted.

ARC 11 · REAL-WORLD PRODUCTION

From one company's integration crisis to an industry default

LinkedIn: the origin, and the scale it grew into

LinkedIn's own engineering blog and public talks by Kreps, Narkhede, and Rao describe the pre-Kafka state candidly: dozens of point-to-point pipelines feeding search, recommendations, fraud review, monitoring, and the Hadoop warehouse, each hand-built and hand-maintained. LinkedIn has publicly described running Kafka, in the years after its internal adoption, at a scale reaching trillions of messages per day across its data centers — an order-of-magnitude figure repeated across multiple LinkedIn engineering blog posts over the years rather than a single precise benchmark, which is the honest way to state it. Whatever the exact daily figure at any given point, the qualitative claim that matters for this chapter is unambiguous: the same append-only, offset-owned-by-the-consumer design that resolved a few hundred pipelines' worth of integration pain in 2010 scaled, without a change in its core abstraction, to become the backbone of essentially all of LinkedIn's real-time data movement.

Netflix: the keystone pipeline

Netflix has publicly described Kafka as the backbone of its "keystone" real-time data pipeline — the shared infrastructure that ingests and routes the enormous volume of playback events, UI interaction events, and operational telemetry that feeds everything from personalization to A/B-test analysis to operational alerting. The pattern is the same one this chapter derived: rather than every producing service wiring up its own delivery path to every consuming team, Netflix's producers write once to Kafka topics, and consuming systems — reporting, machine learning feature pipelines, real-time monitoring — each read independently, at their own pace, off the same underlying logs.

Uber: real-time data movement at ride-hailing scale

Uber has described using Kafka as core infrastructure for its real-time data pipeline, moving trip, location, and pricing-relevant events between the many independent services that make up its marketplace (matching, pricing, fraud detection, and analytics all consume overlapping event streams). The same structural argument applies: a marketplace this decomposed into independent services would, absent a shared log, reproduce LinkedIn's original P×C integration problem services deep — and the reason it doesn't is the same append-only, independently-consumed log this chapter has been deriving.

Illustrative incident: hitting the wall before adopting a log

The following is a composite, illustrative narrative — not a specific citable postmortem — but it is a realistic shape of what teams report before migrating to Kafka, and it mirrors LinkedIn's own documented experience closely enough to be worth walking through concretely. A mid-size e-commerce company grows from 3 backend services to 20 over four years. Each new service that needs order events, inventory changes, or clickstream data gets its own point-to-point integration — a Kafka-shaped hole nobody had filled yet, so teams reach for whatever's fastest: a shared database table one team polls, a webhook another team calls, a message queue a third team stands up just for their pair. By year four, an audit turns up over 80 distinct point-to-point data flows. A single schema change to the order-events format — adding one field — requires coordinating deploys across 11 consuming teams because there is no shared, versioned contract, only 11 independent bilateral agreements. The incident that finally forces a rethink: a webhook-based integration silently drops messages for six hours during a traffic spike, and because there was no durable, replayable record of what was sent, the affected downstream system has a permanent, undetectable gap in its data — the exact failure mode a shared, retained, replayable log exists to make structurally impossible.

Three simplified-but-structurally-faithful sketches, in the spirit of the real Scala/Java without pulling in the full production error handling, locking, and replication machinery. First, the shape of an append:

ScalaUnifiedLog.scala — append(), simplified to the core mechanism
class UnifiedLog(dir: File, config: LogConfig) {

  // The only mutable pointer this class needs for writes: the log-end-offset.
  private var nextOffsetMetadata: LogOffsetMetadata = readRecoveryPointFromDisk()
  private var activeSegment: LogSegment = segments.lastSegment

  /* Append a batch of records. No per-consumer state is read or written here —
   *  this method has never heard of a consumer group. */
  def appendAsLeader(records: MemoryRecords): LogAppendInfo = this.synchronized {
    val baseOffset = nextOffsetMetadata.messageOffset

    // Assign monotonically increasing offsets, starting at the current tail.
    val validated = assignOffsetsAndValidateCrc(records, startingOffset = baseOffset)

    // Roll to a fresh segment file if this batch would exceed segment.bytes / segment.ms.
    if (activeSegment.size + validated.sizeInBytes > config.segmentSize)
      activeSegment = rollToNewSegment()

    // The actual write: append bytes to the end of the active segment's .log file.
    activeSegment.append(largestOffset = validated.lastOffset, records = validated)

    // Update the sparse index only periodically (e.g. every 4KB), not every record —
    // this keeps the index small enough to binary-search entirely in memory.
    if (activeSegment.bytesSinceLastIndexEntry > config.indexInterval)
      activeSegment.index.append(validated.lastOffset, activeSegment.sizeInBytes)

    nextOffsetMetadata = LogOffsetMetadata(validated.lastOffset + 1)
    LogAppendInfo(baseOffset, validated.lastOffset)
  }
}
WHY THE DEVELOPERS WROTE IT THIS WAY

Notice what appendAsLeader does not take as a parameter: any notion of which consumer groups exist, how far behind any of them are, or whether anyone is even subscribed yet. That absence is the design, not an oversight — it's the direct implementation of §8's inversion. The one piece of mutable state the append path touches is nextOffsetMetadata, a single pointer, updated once per batch, under a lock scoped to this partition alone (other partitions on the same broker append completely independently).

Second, the shape of consumer offset tracking — deliberately the mirror image of the append path above:

JavaConsumerCoordinator.java / GroupCoordinator.scala — offset commit, simplified
// Client side: the consumer's ENTIRE positional state for a partition is one long.
class ConsumerCoordinator {
  private final Map<TopicPartition, long> positions = new HashMap<>();

  void commitOffsets(Map<TopicPartition, long> toCommit) {
    // This is a normal produce to the internal, compacted __consumer_offsets topic —
    // key = (groupId, topic, partition), value = (offset, metadata, commitTimestamp).
    for (var entry : toCommit.entrySet())
      sendOffsetCommitRequest(groupId, entry.getKey(), entry.getValue());
  }
}

// Broker side: GroupCoordinator's view of a group is just this table, sourced from
// replaying __consumer_offsets on startup — it is a cache of a log, not new state.
class GroupCoordinator {
  // group -> (topic-partition -> committed offset). One long per (group, partition).
  offsetsCache: Map[String, Map[TopicPartition, Long]]

  def handleFetchOffsets(groupId: String, partitions: Seq[TopicPartition]) =
    offsetsCache(groupId).filterKeys(partitions.contains)
}
WHY THE DEVELOPERS WROTE IT THIS WAY

The offset commit path is implemented as just another produce to a normal (internal) partitioned log — __consumer_offsets gets the same append-only, replicated, retained-by-compaction treatment as any user topic. That's a deliberate refusal to build a second, bespoke storage mechanism for consumer state: the same durability and replication guarantees the log already provides for user data are reused, for free, to make group offsets durable across broker restarts and failovers.

Third, for contrast, a tiny illustrative sketch of what the classic queue's ack bookkeeping actually has to maintain — the structure §6 and §8 argued against, made concrete:

Javanaive_queue_ack.java — illustrative, NOT real Kafka code
// A classic queue broker's per-message bookkeeping, sketched to show the shape of
// the cost this chapter has been arguing against.
class NaiveQueueBroker {
  // One entry PER MESSAGE, PER CONSUMER GROUP subscribed to it. This grows with
  // (messages in flight) x (consumer groups) -- and every ack mutates one entry.
  Map<MessageId, Map<ConsumerGroupId, AckState>> ackTable = new HashMap<>();

  void onAck(MessageId msg, ConsumerGroupId group) {
    ackTable.get(msg).put(group, AckState.ACKED);
    if (allGroupsHaveAcked(msg)) {
      deleteMessageBytes(msg);          // gone. no replay, for anyone, ever again.
      ackTable.remove(msg);
    }
  }
}
THE CONTRAST, MADE EXPLICIT

ackTable is exactly the random-access, per-message-per-consumer mutable structure §6 and §8 describe in prose, now visible as a data structure you could actually profile: a nested map, mutated on every single ack, whose size is proportional to in-flight messages times subscribed groups. Compare its shape directly against UnifiedLog.appendAsLeader above — one has no consumer-facing state at all in its write path; the other's entire write path is consumer-facing state.
