Security: RBAC, Admission
Control & Pod Security

Every kubectl command, every controller's reconcile write, every kubelet heartbeat is a request through the exact same front door: kube-apiserver's request pipeline. This chapter takes that pipeline apart stage by stage — authentication, authorization, admission, persistence — and derives, from the real object shapes, exactly how a Role, a ClusterRole, and their bindings compute an allow/deny decision; how a mutating or validating webhook plugs into that pipeline and what "fail open" really costs you; and precisely what a Pod Security Standard restricts (and what it doesn't).

ARC 01 · THE PROBLEM

One API, many tenants, and a verb that can delete anything

By chapter 12 you have watched the control plane do remarkable things automatically: schedule pods, heal replicas, scale deployments. All of it happens through one funnel — kube-apiserver — and that funnel accepts exactly one kind of instruction from the outside world: a REST verb against an object path, over HTTPS, on port 6443. kubectl delete namespace production and a CI pipeline's routine kubectl apply are, to the API server, the same shape of thing: a client, a verb, a resource, maybe a name. Nothing in HTTP tells the server that one of those is catastrophic and the other is Tuesday.

A single cluster routinely serves many different trust levels at once: platform engineers who need to modify cluster-scoped objects, application teams who should touch only their own namespace, CI/CD service accounts that need narrow create/update rights and nothing else, controllers and operators running as in-cluster service accounts with their own credentials, and the kubelet on every node — itself an API client — which should only ever be able to read and write objects related to the Pods actually scheduled to it. Get this wrong in either direction and you fail differently but equally badly: too permissive, and a compromised CI token or a curious intern can read every Secret in the cluster; too restrictive, and legitimate controllers time out waiting on API calls they should have been allowed to make, and the whole reconciliation model from chapter 9 grinds to a halt.

Three genuinely different questions hide inside "is this request allowed?", and conflating them is the single most common source of security bugs in this part of the system:

  • Who are you? — authentication. A client certificate's Common Name, a bearer token's subject, an OIDC claim.
  • Are you allowed to do this specific thing? — authorization. Verb + resource + namespace + (sometimes) object name, checked against policy.
  • Is the object you're submitting itself acceptable? — admission control. You might be fully authorized to create Pods, and the cluster might still reject (or silently rewrite) a Pod that requests a privileged container, or lacks a resource limit, or targets a node no one meant to expose.
WHY THIS MATTERS FOR THE REST OF THE COURSE

Every capability you've built up through chapter 12 — controllers reconciling state, the scheduler binding Pods, the kubelet pulling images — runs through this exact pipeline with its own identity. A misconfigured RBAC rule doesn't just block a human; it can silently stall a controller's watch, and because reconciliation loops (chapter 9) retry forever without complaint, a permissions bug here often looks like "the cluster is slow" rather than "the cluster is refusing." Learn this pipeline and you can read almost any production Kubernetes incident report and know within thirty seconds which of the three stages actually failed.

DEEP CONTEXT · WHY RBAC BEAT ABAC

ABAC shipped first because it was the smallest possible thing that could work: a flat file of policy statements, read once at kube-apiserver boot. RBAC shipped second because ABAC's policies were not themselves API objects — you couldn't kubectl get them, couldn't audit who changed one, couldn't scope one to a namespace the way you scope a Deployment. RBAC's core design move was to make permissions first-class Kubernetes objects, stored in etcd, watched, versioned, and — critically — bindable by the same declarative model you already use for everything else. §3 makes the ABAC failure mode concrete before §5 shows RBAC's answer.

ARC 03 · NAIVE SOLUTION

Attempt #1: a flat policy file, loaded once

Kubernetes' own first authorization mode is the honest strawman here — it is not hypothetical, it shipped, and some clusters still run it. ABAC is a text file of newline-delimited JSON objects, one policy statement per line, loaded by kube-apiserver --authorization-policy-file=policy.jsonl --authorization-mode=ABAC:

jsonlpolicy.jsonl — the real ABAC format, three statements
{"apiVersion":"abac.authorization.kubernetes.io/v1beta1","kind":"Policy",
 "spec":{"user":"alice","namespace":"*","resource":"*","apiGroup":"*","readonly":true}}
{"apiVersion":"abac.authorization.kubernetes.io/v1beta1","kind":"Policy",
 "spec":{"user":"admin","namespace":"*","resource":"*","apiGroup":"*"}}
{"apiVersion":"abac.authorization.kubernetes.io/v1beta1","kind":"Policy",
 "spec":{"group":"system:serviceaccounts:billing","namespace":"billing",
         "resource":"pods","apiGroup":""}}

Read it the way kube-apiserver does: on every request, walk every line looking for one whose user/group, namespace, resource, and apiGroup fields each match (or are "*") — and, unless readonly narrows it, treat any single matching line as a grant. This is not a caricature: it is a real, still-supported authorization mode, and it already gets the core idea right — a declarative allow-list, evaluated per request, is exactly the shape RBAC keeps. What ABAC gets wrong is everything about how that list is managed.

ARC 04 · WHY IT FAILS

A file is not an API, and that difference compounds

None of ABAC's failures are about the matching logic being wrong — union-of-matching-statements is a perfectly reasonable policy model, and RBAC keeps it. The failures are entirely about the fact that the policy lives outside the API:

  • No live updates. The file is read once, at kube-apiserver startup. Granting one new permission means editing a file on every control-plane node's disk and restarting kube-apiserver on each — in a 3-node HA control plane, that is three rolling restarts to add one line. Compare RBAC: kubectl apply -f rolebinding.yaml, live in milliseconds, no restart, ever.
  • No audit trail, no ownership. The file has no author, no timestamp, no diff history beyond whatever your own config-management tooling bolts on. A RoleBinding is an etcd-backed object with a resourceVersion, a creationTimestamp, and (if audit logging is on — chapter 15) a durable record of exactly who created and last modified it.
  • No namespace citizenship. ABAC's namespace field is a string comparison, not a relationship to a real namespaced object. You cannot list "every policy that applies to namespace billing" the way you can kubectl get rolebindings -n billing — the file has no index, no API, no RBAC-on-RBAC (you cannot restrict who is allowed to edit the policy file using the same permission model it enforces).
  • Combinatorial line growth. To give each of U teams full CRUD on their own namespace's core resources, and nothing else, ABAC needs roughly U lines only if you can express "my own namespace" generically — which the format cannot do (each statement's namespace field is a fixed string or a wildcard, not "the caller's own namespace"). In practice teams end up writing one statement per (user × namespace × resource-group) combination they need, and that count grows as U × N for U users and N namespaces, hand-maintained in one file with no schema validation beyond "is this valid JSON."
THE OPERATIONAL NUMBER

Picture a platform team onboarding 40 new application teams over a quarter — a normal pace at a fast-growing company. Under ABAC that is 40 file edits, each requiring a rolling restart of every kube-apiserver replica to take effect, each restart briefly dropping that replica's capacity from the load-balanced control plane. Under RBAC it is 40 kubectl apply calls against a running cluster, live immediately, individually revertible, individually auditable. The gap isn't matching-logic sophistication — it's the difference between policy as a deployment artifact and policy as data.

RBAC's actual design move, then, isn't a cleverer matching algorithm — ABAC's union-of-matching-statements idea survives almost unchanged. The move is making the statements themselves into Kubernetes objects. §5 builds that model up from the same union logic, this time bindable, watchable, and namespace-native.

ARC 05 · BETTER SOLUTION

RBAC: four objects, one union rule

Role-Based Access Control ships as exactly four API objects, all in the rbac.authorization.k8s.io/v1 group, split along two independent axes: namespaced vs cluster-scoped, and the rules themselves vs who they apply to.

OBJECTSCOPEHOLDS
RolenamespacedA list of rules (verbs × resources × apiGroups, optionally resourceNames) — valid only within its own namespace.
ClusterRolecluster-scopedThe same rule shape, but reusable — can be bound cluster-wide or narrowed to one namespace at bind time (this asymmetry is the single most-misunderstood fact in RBAC — §8 makes it precise).
RoleBindingnamespacedAttaches a Role or a ClusterRole to a list of subjects (User / Group / ServiceAccount), scoped to the binding's own namespace.
ClusterRoleBindingcluster-scopedAttaches a ClusterRole to subjects, cluster-wide — cannot reference a namespaced Role at all.

THE RULE THAT MAKES EVERYTHING ELSE PREDICTABLE

RBAC is purely additive. There is no deny verb, no rule ordering, no "most specific rule wins." The effective permission for a subject is the union of every rule in every Role/ClusterRole reached through every RoleBinding/ClusterRoleBinding whose subjects include that user, that ServiceAccount, or any group the caller belongs to. If any one bound rule allows the request, the request is allowed — full stop, regardless of how many other bindings stay silent. §8 gives you the literal matching function; §15's simulator lets you compute this union by hand against a real toy cluster.

ARC 06 · WHY THAT STILL COSTS

What RBAC buys you, and what it still doesn't

RBAC solves ABAC's operational failures completely — permissions are live, auditable, namespace-native API objects. It does not solve everything §1 asked for. Four gaps are worth internalizing now, because each one is the reason some other tool exists:

  • No explicit deny. You cannot express "everyone in edit except Bob." The only way to remove access is to not grant it, or to restructure bindings so Bob isn't a member of the group that has it.
  • No data-level or field-level authorization. RBAC answers "can this subject update deployments" — it cannot say "…but only the spec.replicas field" or "…only Pods this subject itself created." That granularity requires an admission webhook or a policy engine (Kyverno, OPA Gatekeeper) inspecting the object body, which is exactly what §7 introduces next in the pipeline.
  • No conditions. No time-of-day windows, no MFA-level checks, no rate limits. RBAC's decision is a pure function of (subject, verb, resource, apiGroup, resourceName) — nothing about when or how the request arrived.
  • Binding sprawl doesn't disappear, it relocates. RBAC removes the per-user dimension of sprawl (bind a Group once, add/remove members at your identity provider, done) but the per-namespace dimension is structural: a Role only exists in one namespace, so granting the same permission shape in 200 namespaces genuinely requires 200 RoleBinding objects (even if they all reference one shared ClusterRole).

The RoleBinding count is namespaces × roles-per-namespace, full stop — groups don't touch that number, because a Role's scope is the namespace it lives in, not the size of its subject list. What groups eliminate is the subject-list churn: without them, every hire or transfer means editing every RoleBinding that team touches by hand; with them, it means one membership change at the identity provider, and every binding that references that group is correct on the next read — zero Kubernetes API calls.

THE INDUSTRY'S ANSWER — AND ITS ADMISSION

Real clusters layer policy engines (OPA Gatekeeper, Kyverno) and admission webhooks on top of RBAC specifically to cover the gaps above: field-level checks, cross-object conditions, "deny unless labeled," mandatory resource limits. That an entire CNCF sub-ecosystem exists to add a deny rule and some conditionals to an authorization system is itself the tell — RBAC is deliberately minimal, and the minimalism is what makes it fast and auditable (§10 quantifies exactly how fast). §7 shows where that admission layer actually sits in the request pipeline.

ARC 08 · INTERNAL IMPLEMENTATION

The real object shapes, the real matching function, the real wire format

Three pieces, in pipeline order: (a) the RBAC objects and the union-matching algorithm that resolves them, (b) the admission webhook wire format and its failure-policy math, (c) Pod Security Standards and bound service account tokens — the two identity/policy mechanisms that ride on top of everything above.

(a) RBAC: real YAML, and the real matching function

A concrete, complete example — a Role scoped to one namespace, and the RoleBinding that grants it to a ServiceAccount:

yamla namespaced Role + RoleBinding, byte-accurate to the real API shape
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: billing
  name: deployment-manager
rules:
- apiGroups: ["apps"]           # "" means the core group (pods, services, secrets…)
  resources: ["deployments"]
  verbs:     ["get", "list", "watch", "update", "patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: billing            # the binding's OWN namespace — this is the scope, not the role's
  name: release-engineers-deploy
subjects:
- kind: Group
  name: release-engineers        # any user whose token/cert carries this group
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role                    # could be ClusterRole instead — same binding shape
  name: deployment-manager
  apiGroup: rbac.authorization.k8s.io

Notice the field that decides scope: it is the binding's own metadata.namespace, not anything on the role. Bind a ClusterRole through a RoleBinding and you get a cluster-wide rule set narrowed to one namespace — genuinely useful (reuse one canonical "edit" ClusterRole everywhere, bind it per-team) and genuinely dangerous to get backwards: swap that RoleBinding for a ClusterRoleBinding by habit or by a bad copy-paste and the exact same ClusterRole now grants cluster-wide access. §11 covers a real incident class built entirely from this one confusion.

The evaluation itself, simplified from plugin/pkg/auth/authorizer/rbac but faithful to the real control flow:

gorbac.go / rules.go — RBACAuthorizer.Authorize(), simplified
func (r *RBACAuthorizer) Authorize(attr authorizer.Attributes) authorizer.Decision {
    var ruleErrors []error
    if RulesAllow(attr, r.getClusterRoleBindingRules()...) {
        return authorizer.DecisionAllow   // ClusterRoleBindings: cluster-wide subjects
    }
    if RulesAllow(attr, r.getRoleBindingRules(attr.GetNamespace())...) {
        return authorizer.DecisionAllow   // RoleBindings: scoped to attr.GetNamespace()
    }
    return authorizer.DecisionNoOpinion       // neither list had a matching rule
}

// RuleAllows: the actual field-by-field match — verb, apiGroup, resource, resourceName
func (r *PolicyRule) RuleAllows(requestAttr authorizer.Attributes) bool {
    if !has(r.Verbs, requestAttr.GetVerb()) && !has(r.Verbs, "*") {
        return false
    }
    if !has(r.APIGroups, requestAttr.GetAPIGroup()) && !has(r.APIGroups, "*") {
        return false
    }
    if !has(r.Resources, requestAttr.GetResource()) && !has(r.Resources, "*") {
        return false
    }
    // resourceNames, when set, restrict to specific named objects — and can never
    // match a request with no name at all, e.g. "list" or "create"
    if len(r.ResourceNames) > 0 {
        if requestAttr.GetName() == "" || !has(r.ResourceNames, requestAttr.GetName()) {
            return false
        }
    }
    return true
}
THE UNION-OF-AUTHORIZERS LAYER ABOVE RBAC

kube-apiserver almost never runs RBAC alone. --authorization-mode is a comma-separated chain — typically Node,RBAC, sometimes with a Webhook authorizer appended — combined by staging/src/k8s.io/apiserver/pkg/authorization/union: try each authorizer in order, return immediately on the first DecisionAllow, remember any explicit DecisionDeny, and if nobody allows, the overall result is deny. The Node authorizer is a special-purpose, non-RBAC authorizer that restricts each kubelet's own credentials to objects related to Pods actually bound to that node — a kubelet reading a Secret is authorized only if that Secret is mounted by a Pod scheduled to it. The NodeRestriction admission plugin closes the remaining gap by preventing a kubelet from, say, relabeling its own Node object to defeat a scheduler taint. This is the concrete answer to "how does a compromised kubelet stay contained": least privilege enforced at both the authorization and admission layers.

(b) Admission webhooks: the wire format and the fail-open/fail-closed choice

A dynamic admission webhook is registered as a MutatingWebhookConfiguration or ValidatingWebhookConfiguration — an API object naming a URL (or in-cluster Service), which resources/verbs it matches, and its failure policy. For every matching request, kube-apiserver POSTs an AdmissionReview and expects one back:

jsonAdmissionReview — request in, response out, real field names
{
  "apiVersion": "admission.k8s.io/v1", "kind": "AdmissionReview",
  "request": {
    "uid": "705ab4f5-6393-11e8-b7cc-42010a800002",
    "operation": "CREATE", "userInfo": { "username": "system:serviceaccount:billing:ci-bot" },
    "resource": { "group": "", "version": "v1", "resource": "pods" },
    "namespace": "billing", "object": { /* the full Pod being created */ }
  }
}
// mutating response: a base64 JSONPatch, applied before validation ever runs
{ "response": { "uid": "705ab4f5-…", "allowed": true,
    "patchType": "JSONPatch", "patch": "W3sib3AiOiJhZGQiLCJwYXRoIjoiL3NwZWMv…" } }
// validating response: a bare allow/deny, optionally with a human-readable reason
{ "response": { "uid": "705ab4f5-…", "allowed": false,
    "status": { "message": "container 'app' must set resources.limits.memory" } } }

Two mechanical facts here decide most webhook incidents. First: mutating webhooks run sequentially — each one might change the object, so the next must see the result — while validating webhooks run in parallel, because none of them may mutate. Second: every webhook carries its own failurePolicy — Ignore (treat a timeout or connection error as "allowed"; fail open) or Fail (treat it as "denied"; fail closed) — with a default timeoutSeconds of 10 (maximum 30) per webhook, in the v1 admissionregistration API. (c) Pod Security Standards and bound service account tokens

Two more mechanisms complete this chapter's picture, both consumed as admission/authentication inputs rather than as new pipeline stages. Pod Security Standards define three cumulative profiles — Privileged (unrestricted), Baseline (blocks known privilege escalations but stays broadly compatible), and Restricted (enforces current Pod hardening best practice) — enforced by the built-in Pod Security admission controller (KEP-2579, GA in 1.25, the direct replacement for the removed PodSecurityPolicy) via a namespace label:

yamlenforcing Restricted on one namespace — no controller to install
apiVersion: v1
kind: Namespace
metadata:
  name: billing
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit:   restricted   # log violations without blocking
    pod-security.kubernetes.io/warn:    restricted   # surface a kubectl warning

Restricted is, mechanically, a validating admission check against the Pod spec's declared fields — it requires runAsNonRoot: true, forbids privileged: true and hostNetwork/hostPID/hostIPC, restricts the Linux capability set to a drop-all baseline, and requires a seccomp profile be set. It is a YAML gate, evaluated once at admission time. Whether the kernel actually honors privileged: true by granting every capability, and precisely which capability a dropped/added entry maps to — that mechanism lives one layer down, at the container runtime and kernel, and is the Container Internals course's territory, not this pipeline's.

Finally, service account tokens: before roughly 1.22, every ServiceAccount got a non-expiring JWT auto-mounted from a Secret — valid forever, valid for any audience, and painful to rotate. The TokenRequest API (alpha 1.10, beta 1.12) plus bound, audience-scoped tokens (KEP-1205, default since 1.22) replaced this: a projected volume token is minted per-Pod, carries an expiry (default one hour, auto-refreshed by the kubelet), is cryptographically bound to that specific Pod object (it becomes invalid the moment the Pod is deleted, not just when it expires), and is scoped to an explicit audience list rather than being universally valid. A leaked bound token is a much smaller blast radius than a leaked legacy Secret token — it dies with its Pod and cannot be replayed against an unintended audience.

ARC 09 · TRADEOFFS

Seven mechanisms, one job each — and where they overlap on purpose

None of these compete for the same layer; the confusion in real postmortems is almost always "we reached for the wrong one," not "the one we used is bad":

MECHANISMWHAT IT DECIDESBUYSCOSTS
ABACidentity → allow, from a flat file zero extra moving parts apiserver restart per change no audit trail
RBACidentity → verb/resource allow live, auditable, namespace-native no deny rule no field/data-level checks
Node authorizerkubelet → only its own node's objects contains a compromised kubelet kubelet-specific; not a general mechanism
Webhook authorizeridentity → allow, via external service arbitrary custom identity logic network hop on every request availability dependency
Admission webhooksobject body → mutate/allow/deny field-level, cross-object, org-specific policy latency (§10) fail-open/closed choice per hook
Pod Security admissionPod spec → allow, by fixed profile built-in, zero deployment, can't fail-open from an outage only three fixed profiles — not customizable rules
PodSecurityPolicy (removed, 1.25)Pod spec → allow, via a cluster-scoped policy object fully customizable, predates the above its own confusing RBAC-of-RBAC binding model — the reason it was replaced

Read this as a stack, not a menu: a well-run multi-tenant cluster typically layers RBAC (who can call which verb), Pod Security admission (what a Pod spec may declare), and one policy engine (org-specific rules RBAC and PSS don't express) — each answering a question the others structurally cannot.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

What's cheap, what's synchronous, and where the real ceiling is

  • RBAC evaluation is an in-memory scan, not an etcd round-trip. Roles, ClusterRoles, RoleBindings, and ClusterRoleBindings are cached in kube-apiserver via the same watch/informer mechanism from chapter 9 — evaluating a request costs O(bindings × rules) against RAM, typically sub-millisecond even with thousands of bindings. Individually, Role/RoleBinding objects are tiny — well under etcd's recommended 8 KB per value guideline — so RBAC's storage footprint is essentially never the bottleneck; the bottleneck, when there is one, is what runs synchronously in the hot path instead: admission webhooks.
  • Aggregated ClusterRoles add an eventual-consistency window. A ClusterRole with an aggregationRule (label selector over other ClusterRoles) is recomputed by a controller watching for label matches, not synchronously on every request — a newly labeled ClusterRole's rules become visible after one controller reconcile tick, not instantly.
  • Admission webhooks are a real network hop, per matching request, in the write path. Each matched mutating webhook adds its full round-trip latency sequentially; matched validating webhooks run in parallel, so their contribution is the slowest one, not the sum. A chain of five mutating webhooks at 40 ms each is 200 ms added to every single matching Pod create, cluster-wide — invisible until someone asks "why did kubectl apply get slower this quarter."
  • At fleet scale, fail-closed webhooks become a single point of failure. In an SLO-conformant cluster near Kubernetes' documented ceiling — roughly 5,000 nodes / 150,000 Pods — a misbehaving failurePolicy: Fail webhook doesn't fail one request, it can block every matching create/update cluster-wide until it recovers, because the pipeline runs synchronously per request with no queueing or backpressure of its own.

ARC 11 · REAL-WORLD INCIDENTS

Four ways this pipeline has actually failed in production

CVE-2018-1002105 — the proxy request-smuggling privilege escalation

Kubernetes' most severe CVE to date (CVSS 9.8), found by Darren Shepherd. The API server's aggregation layer proxies certain requests (like exec and extension API server calls) upstream over a connection authenticated with the API server's own credentials. A specially crafted request could keep that upstream connection open after an error and send further, arbitrary requests over it — fully authenticated as the API server itself, with cluster-admin-equivalent trust, completely bypassing whatever RBAC would otherwise have decided for the original caller. The fix closed the connection reuse path; the lesson generalizes: any component that proxies on your behalf with elevated credentials is itself part of your authorization boundary, not exempt from it.

CVE-2019-11247 — cluster-scoped access via the wrong scope

A pure RBAC-scoping bug, and the cleanest illustration of §8(a)'s "binding's own namespace decides scope" rule going wrong inside the API server itself: kube-apiserver would, under certain conditions, allow a cluster-scoped custom resource to be accessed as if it were namespaced — meaning a RoleBinding meant to grant access only within one namespace could inadvertently authorize access to the cluster-scoped object of the same name, cluster-wide. The fix tightened the resource-scope check inside the authorizer path. This is the exact bug class §8(a)'s callout warned about, discovered in Kubernetes' own code rather than a user's YAML.

CVE-2019-11253 — Billion Laughs, before authorization even finishes deciding anything

A maliciously crafted, deeply self-referential YAML or JSON manifest — the classic "billion laughs" expansion attack — submitted to kube-apiserver could consume enormous CPU and memory during parsing, before RBAC or admission ever get to render a verdict. Because parsing happens ahead of authorization in the request's lifecycle, even a caller with minimal, narrowly-scoped RBAC permissions (just enough to submit some object) could degrade the whole control plane. The fix added parsing-time limits. The lesson: the pipeline in §7 has an implicit stage-zero — "can the request even be parsed cheaply" — that has to be defended independently of every authorization decision downstream.

The Tesla cluster cryptojacking incident (2018)

Not a CVE — a configuration incident, and the most common real-world failure mode of all four. A Kubernetes dashboard was left reachable without authentication required, exposing credentials for a Pod's service account that, per this chapter's model, was bound to permissions far beyond what a public-facing dashboard should ever need. Attackers used those credentials to run cryptomining workloads inside the cluster, including a specifically low-and-slow CPU footprint designed to stay under alerting thresholds. The root cause was not a bug in RBAC's matching logic — it was the same design mistake §6 warned about: granting a workload's ServiceAccount broader access "to be safe" instead of scoping a dedicated Role to exactly what that one workload needs.

The union authorizer's actual control flow, simplified but structurally faithful:

gounion.go — unionAuthzHandler.Authorize()
func (u unionAuthorizer) Authorize(ctx context.Context, a authorizer.Attributes) (authorizer.Decision, string, error) {
    var reasons []string
    for _, authz := range u.Authorizers {           // e.g. [Node, RBAC, Webhook]
        decision, reason, err := authz.Authorize(ctx, a)
        if decision == authorizer.DecisionAllow {
            return decision, reason, nil       // first ALLOW short-circuits — order matters for latency, not correctness
        }
        if decision == authorizer.DecisionDeny {
            reasons = append(reasons, reason)         // remember; a later authorizer could still allow
        }
    }
    return authorizer.DecisionDeny, strings.Join(reasons, "\n"), nil  // no one allowed → deny
}

And the mutating dispatcher's sequential-vs-parallel split, the exact mechanical fact §8(b) and §10 build on:

gomutating/dispatcher.go vs validating/dispatcher.go — the split, simplified
// mutating: MUST run one at a time — each hook may rewrite the object the next one sees
for _, hook := range mutatingHooks {
    patched, err := invoke(hook, currentObject)
    if err != nil {
        if hook.FailurePolicy == Fail { return deny(err) }   // fail-closed
        continue                                          // fail-open: Ignore, proceed unmodified
    }
    currentObject = patched
}

// validating: safe to run concurrently — none of them may mutate the object
var wg sync.WaitGroup
for _, hook := range validatingHooks {
    wg.Add(1)
    go func(h Webhook) {
        defer wg.Done()
        if err := invoke(h, currentObject); err != nil && h.FailurePolicy == Fail {
            firstDenyErr.Store(err)
        }
    }(hook)
}
wg.Wait()
WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. Additive-only, no ordering. RBAC's designers deliberately excluded deny rules and rule precedence — both invite the classic firewall-rule-ordering bug class ("why did rule #47 shadow rule #12"). A pure union has exactly one failure mode to reason about: an unwanted grant, findable by searching bindings, never an ordering puzzle. 2. Fail-open is opt-in, never the silent default for a broken configuration. Every webhook registration must explicitly choose failurePolicy; there is no ambient "if unsure, allow." Combined with the built-in Pod Security admission running in-process (no network hop, cannot itself go down independent of the API server), Kubernetes structurally biases security-critical checks away from mechanisms that can fail silently open due to an external outage.
