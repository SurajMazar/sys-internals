APACHE KAFKA INTERNALS · CHAPTER 09

Transactions &
Exactly-Once Semantics

A consume-transform-produce application reads from topic A, writes to topic B, and commits its offset. Those are three independent RPCs against two different subsystems, and a crash between any two of them turns "exactly once" into either a duplicate or a silent gap. This chapter derives KIP-98's transaction protocol from that single failure mode — the coordinator, the epoch-fencing that kills zombies, the two-phase commit that writes markers into your own data log, and the exact boundary of what "exactly once" does and does not mean.

ARC 01 · THE PROBLEM

Three RPCs, one atomicity requirement, zero built-in coordination

Consider the single most common shape of stream processing: consume, transform, produce. An application polls records from topic orders, computes something (say, a running total), writes the result to topic totals, and — once the write is acknowledged — commits its consumer offset so it never reprocesses those records. Every stream processor, every Kafka Streams topology, and a large fraction of hand-written consumer/producer pairs reduce to this loop.

Examined closely, that loop is three separate effects against two separate systems: a produce request to the leader(s) of one or more partitions of totals, and an offset-commit request to the consumer group coordinator recording progress against orders. Kafka's core replication protocol (chapters 4–6) guarantees each of those individually: a produce with acks=all is durable once min.insync.replicas replicas have it; an offset commit is durable once its coordinator's log has it. What the base protocol promises nothing about is what happens between them.

  • Crash after produce, before offset commit. The output landed in totals. On restart the consumer resumes from the last committed offset — which is still behind — so it re-reads the same input records and re-produces the same output. Downstream sees duplicates.
  • Crash after offset commit, before produce is acknowledged (or the produce silently fails and the commit races ahead in a badly-ordered implementation). The consumer's position has advanced past records whose output never landed. Downstream has a gap — data that was consumed but never produced.
  • Multi-partition writes are not atomic with each other. If the transform fans out to three partitions of totals, a crash mid-fan-out can leave the write half-applied: two partitions have the new records, the third doesn't. There is no cross-partition write barrier in the base protocol at all.

You already know a mechanism that looks related: the idempotent producer from chapter 4, which uses a producer ID and a per-partition sequence number so retries of the same batch are deduplicated by the broker. It is necessary here but nowhere near sufficient. Idempotence guarantees this producer's retries into one partition don't duplicate. It says nothing about a second partition, nothing about the consumer offset commit, and nothing at all about what happens when the producer process itself restarts and is replaced by a new instance with no memory of the sequence numbers the old one was using. Solving this properly requires a construct that spans partitions, spans the produce/consume boundary, and survives the producer's own death — which is exactly what KIP-98 built, and what the rest of this chapter derives piece by piece.

THE STAKES

This is not a cosmetic bug. In a payments pipeline, a duplicate is a double charge; a gap is a lost transaction. "At least once with idempotent downstream writes" is a legitimate alternative (§5), but it pushes a hard distributed-systems problem onto every application team, forever. Kafka's transactions exist to make the platform solve it once, correctly, for the specific case of Kafka-to-Kafka pipelines.

ARC 02 · HISTORICAL CONTEXT

From "duplicates are a fact of life" to KIP-98

Kafka shipped in 2011 with an unapologetically at-least-once contract: producers retried on timeout, and a retried batch could be appended twice. For years the accepted mitigation was "make your consumer idempotent" — fine advice for a single team's database sink, useless as a platform-wide guarantee once Kafka became the backbone connecting dozens of teams' pipelines to each other. DEEP CONTEXT · WHY THE COORDINATOR IS A BROKER, NOT A NEW SERVICE

KIP-98's authors (Guozhang Wang, Jason Gustafson, Jay Kreps and others at Confluent) made a decision that shaped everything downstream: the transaction coordinator is not a new kind of process — it is an ordinary broker playing a role, exactly like the group coordinator you met in chapter 7. Transaction state itself lives in an internal Kafka topic, __transaction_state, replicated and compacted like any other log. Kafka solved a distributed-transactions problem using Kafka's own replication primitive to store the transaction log — there is no separate consensus system, no external XA resource manager. You'll see this "eat your own dog food" pattern again in KRaft (chapter 14), which stores cluster metadata in a Kafka-shaped log instead of ZooKeeper.

ARC 03 · NAIVE SOLUTION

Attempt #1: consume, produce, commit — and hope

The straightforward implementation, before transactions exist, looks like this. It is not a joke — it is what most consumer/producer applications actually run, and it is worth being precise about exactly where the atomicity gap sits.

JavaNaiveCTP.java — the strawman, annotated
while (running) {
    ConsumerRecords<String,String> recs = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String,String> r : recs) {
        String out = transform(r.value());               /* pure CPU, assume correct */
        producer.send(new ProducerRecord<>("totals", r.key(), out));
        /* ← CRASH HERE: output landed (or is in flight), offset not yet moved.
             Restart re-polls this record from the last COMMITTED offset → duplicate write. */
    }
    producer.flush();                                    /* wait for broker acks       */
    consumer.commitSync();                               /* ← CRASH HERE: output landed,
             offset now committed. This ordering is actually the SAFE side — but only
             because we flushed first. Reverse the order and a crash here loses data. */
}

Notice the code is already trying to be careful — flush before commit, not after — and it still can't close the gap, because producer.flush() and consumer.commitSync() are two unrelated network round-trips to two unrelated coordinators. ARC 04 · WHY IT FAILS

Quantifying the damage: it is not a rare event

It is tempting to file this under "acceptable rare edge case." The math says otherwise. A stream-processing fleet does not crash rarely by the standards of a single instance — it crashes routinely by the standards of the fleet:

  • Rolling deploys are crashes, on purpose. A team deploying twice a day across 50 processing instances performs 100 ungraceful-equivalent stop events daily if shutdown hooks race with in-flight batches — every one is a chance to hit the gap between produce and commit.
  • Rebalances multiply the exposure. Chapter 7 showed that a consumer group rebalance revokes and reassigns partitions; if a partition moves mid-transform, work in flight for the old owner and the resumed offset for the new owner can disagree unless the hand-off is exact.
  • The failure is silent. Unlike a crash that pages someone, a duplicate write or a skipped record produces no error — the pipeline looks healthy. You find out from a reconciliation job days later, or from a customer complaint about a double charge.
THE NUMBERS

Take a modest fleet: 200 stream-processing instances, each restarting on average once every 6 hours from routine deploys, OOMs, and rebalances (a conservative estimate for a JVM fleet under real load). That is ~800 restarts/day fleet-wide. Even if only 1 in 20 restarts lands exactly in the produce/commit gap — plausible, since the gap is open for the full network round-trip of a produce plus a commit, not an instant — that is ~40 duplicate-or-gap events per day, each silently propagating downstream. "Make consumers idempotent" is real advice, but it means every single downstream team must implement, test, and maintain dedup logic keyed on business semantics — a tax paid forever, by everyone, for a problem with one general solution.

So the requirement crystallizes: we need one atomic commit that spans a produce to N partitions and an offset commit to a consumer group — and that commit must survive the producer process crashing at any instruction. §5 walks through what does and doesn't get there.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Four candidates, one survivor

Step through the candidates in the order a design team would actually consider them — each one is eliminated for a specific, instructive reason.

Candidate solutions, eliminated in orderSTEP-BY-STEP

The surviving design needs exactly four capabilities, each answering one failure mode from §1: (1) a durable, replicated place to record "which partitions are part of this transaction and what state is it in" that outlives any single producer instance; (2) a way to make the consumer-group offset commit part of the same commit as the data writes, rather than a second unrelated RPC; (3) a way to detect and reject a zombie — an old producer instance that hung (GC pause, network partition) and wakes up after a replacement has already taken over the same logical role; and (4) a way for a reader to skip the output of a transaction that never committed, without the broker deleting or rewriting anything. Kafka's answer to all four is one component: the transaction coordinator, backed by a compacted internal topic and a set of control records written into the data log itself.

ARC 06 · WHY THAT STILL COSTS

Atomicity is not free: what you pay for it

Before the architecture, be honest about its price — the rest of the chapter will make these numbers concrete:

  • Extra round-trips per transaction. InitProducerId once per producer session, AddPartitionsToTxn the first time each partition is touched, then at commit an RPC to write markers into every participating partition. None of this existed in the non-transactional path.
  • Extra durable writes. The coordinator appends PREPARE and COMPLETE records to __transaction_state; every data partition gets a control batch (the commit/abort marker) that consumes a real offset in that partition's log — offsets in a transactional topic are not contiguous per-record for exactly this reason.
  • Blocking downstream readers. A read_committed consumer cannot see past the earliest still-open transaction on a partition (the LSO, §8) — so a slow or hung transaction throttles every consumer of that data, not just the producer that opened it.
  • Per-record transactions are pathological. If you open and commit a transaction for every single record, you pay the full RPC and marker overhead per record — throughput can fall by an order of magnitude or more versus batching hundreds or thousands of records per transaction (quantified in §10).
THE HONEST SCOPE

None of this buys you "exactly once" against the outside world. It buys exactly-once semantics for Kafka-to-Kafka effects within one cluster: writes to output partitions and the input offset commit, atomically. A database write, an email send, a call to a payment gateway triggered by processing a record is outside the transaction unless that side effect is itself idempotent or participates in its own two-phase protocol with Kafka (rare, and not what KIP-98 provides out of the box). Every vendor pitch that says "exactly-once end to end" is quietly assuming one of those two things. Keep this boundary sharp — §9 and §11 return to it.

ARC 07 · FINAL ARCHITECTURE

The transaction coordinator and its participants

A transactional pipeline is five roles talking to each other. The coordinator is a broker — determined deterministically by hashing the application's transactional.id to a partition of __transaction_state; whichever broker leads that partition is the coordinator for that transactional id, and coordinator failover is just leadership failover of that one partition (chapter 6's machinery, reused). WHY THE OFFSET COMMIT GOES THROUGH THE PRODUCER

The single strangest-looking API in this protocol is producer.sendOffsetsToTransaction(offsets, groupMetadata) — why does a producer object commit consumer offsets? Because that is the only way to make the offset commit a participant in the same transaction as the data writes. The producer's TransactionManager forwards the offsets to its transaction coordinator as one more "partition" of the transaction (the __consumer_offsets partition owning that group), so when the coordinator later writes commit markers, it writes one into the offsets topic too. The group coordinator and the transaction coordinator cooperate through that shared write — not by one calling the other synchronously.

ARC 08 · INTERNAL IMPLEMENTATION

The protocol, precisely: from InitProducerId to COMPLETE_COMMIT

Now the mechanism at the level you would need to debug it. There are four phases: (a) establishing a fenced identity, (b) declaring participants, (c) the two-phase commit itself, (d) what a read_committed reader must do to only ever see committed data.

(a) initTransactions(): the epoch bump that fences zombies

The producer calls initTransactions() exactly once at startup. It sends InitProducerId to its coordinator carrying the configured transactional.id. The coordinator looks up (or creates) that id's metadata in __transaction_state and returns a (producerId, producerEpoch) pair — critically, the epoch is incremented every time this call succeeds for this transactional id. Any producer instance still holding the previous epoch is now stale: the next request it sends carrying that old epoch is rejected with PRODUCER_FENCED. This is the entire zombie-fencing mechanism — no distributed lock, no lease renewal, no heartbeat timeout race. A hung instance (a 40-second GC pause, a stuck thread, a partition that heals late) that wakes up and tries to write finds its epoch is old and is refused, full stop, regardless of how "alive" it feels from its own perspective. This is why the classic split-brain failure mode — two instances of the same logical processor both believing they own a partition — cannot corrupt output here: only one epoch is ever current.

(b) AddPartitionsToTxn and sendOffsetsToTransaction: declaring the participant set

beginTransaction() itself is purely client-local — it just flips a state flag in the TransactionManager, no RPC. The first record sent to each partition within the transaction triggers an AddPartitionsToTxn request (batched if several partitions are new at once) so the coordinator's transaction metadata accumulates the exact partition set it is responsible for marking at commit time. If your transform fans out to totals-0 and totals-1, the coordinator learns about both the moment each is first written. sendOffsetsToTransaction(offsets, groupId) — usually called once, right before commit — adds the consumer group's offsets-topic partition to that same participant set, which is exactly how the offset commit becomes part of the atomic unit rather than a bolt-on afterthought.

(c) commitTransaction(): two-phase commit against your own data partitions

Step through the commit sequence — this is the part worth having memorized cold:

commitTransaction() — the two-phase commitSTEP-BY-STEP

The markers are not metadata bolted alongside the log — they are control batches, record batches with the control bit set in the batch attributes, carrying a key that encodes version and type (COMMIT = 0, ABORT = 1) and consuming a real offset in the partition, exactly like a data record. This is precisely why a transactional topic's offsets are not one-per-message: every committed (or aborted) transaction leaves one marker offset behind per participating partition, permanently.

(d) The read side: LSO and client-side filtering

A consumer with isolation.level=read_committed is not shown records past the LSO, the offset of the earliest transaction still open on that partition — even if later, non-transactional or already-committed records physically exist beyond it in the log. The broker computes the LSO from the set of open producer states it is tracking (ProducerStateManager) and caps read_committed fetch responses there. This has an immediate, sharp consequence: an open transaction blocks every read_committed consumer from advancing past it, no matter how much unrelated, already-committed data sits after it in the log — a real head-of-line-blocking hazard, why transaction.timeout.ms (default 60000 ms) exists as a hard backstop that aborts a transaction the coordinator hasn't heard from in too long, unsticking readers. For data that is below the LSO but belongs to an aborted transaction, the consumer buffers fetched records client-side and filters using the partition's aborted-transaction index (built from control batches the fetch response includes), dropping any batch whose producer/epoch/sequence matches an abort marker before ever handing a record to application code.

Coordinator-side, transaction metadata lookup by transactional.id is a hash-map access — O(1). The per-partition producer-state tracking the broker uses to validate sequence numbers and compute the LSO is also a hash map keyed by producer ID, capped by producer.id.expiration.ms so it doesn't grow unbounded with churn. None of the correctness machinery is algorithmically expensive; the cost is entirely in round-trips and durable writes, which is why batching is the lever that matters (§10).

ARC 10 · PERFORMANCE CHARACTERISTICS

The overhead, quantified

Per transaction, independent of how many records it contains, you pay: one AddPartitionsToTxn round-trip per newly-touched partition, one EndTxn request to the coordinator, one WriteTxnMarkers RPC fanned out to every participating partition's leader, and two appends to __transaction_state (PREPARE_COMMIT, then COMPLETE_COMMIT). That is a fixed cost per transaction — call it roughly 4–6 extra round-trips plus a handful of small durable writes. It does not grow with the number of records the transaction contains. The immediate engineering consequence: the way to amortize a fixed cost is to spread it over more work, i.e. batch many records into each transaction rather than committing per record.

The read side pays a different tax: end-to-end latency for a read_committed consumer is bounded below by how long the producer keeps the transaction open, because records only become visible once the LSO passes them, which only happens once the coordinator's markers land. A producer batching for one second per transaction imposes at least that much added latency on every downstream reader — a direct throughput/latency trade the operator chooses via how aggressively the application batches (or via transaction.timeout.ms as a hard ceiling on how long a stuck transaction can hold readers back).

  • GC interaction: a long GC pause in the producer doesn't corrupt anything (the epoch protects that), but it can trip transaction.timeout.ms, aborting the in-flight transaction — connect to chapter 5's discussion of GC pauses causing ISR flapping; here the same pause causes transaction aborts instead.
  • Disk/network: control batches are tiny (a handful of bytes) but still real appends subject to the same acks/ISR replication path as data — no shortcuts are taken for markers.
  • Big-O: validating a batch's sequence number against ProducerStateManager is O(1); LSO computation is a min-aggregation over currently-open producer states on that partition, proportional to concurrently open transactions, which in practice is small (one transactional producer rarely holds many transactions open per partition simultaneously).
ARC 11 · REAL-WORLD PRODUCTION

What actually happens at scale

Incident class 1: the hanging transaction

A producer crashes (or a bug leaves a transaction neither committed nor aborted) while holding a transaction open on a partition. Every read_committed consumer of that partition stalls at the LSO until transaction.timeout.ms expires and the coordinator force-aborts it — or, in versions before recent hardening, in some pathological client-bug scenarios a transaction could be left "hanging" indefinitely, requiring operator intervention via kafka-transactions.sh --abort to unstick consumers. This exact failure class motivated KIP-890 ("Transactions Server-Side Defense"), which added broker-side verification of a producer's transaction state before appending, closing several edge cases where a delayed or duplicated request from a fenced/zombie producer could otherwise corrupt or hang a transaction. The operational lesson repeated in postmortems across the ecosystem: set transaction.timeout.ms deliberately, not at the default, once you understand it is also your maximum consumer-stall window.

Incident class 2: throughput regressions from over-eager transactions

Teams migrating Kafka Streams jobs to exactly_once_v2 (KIP-447, Kafka 2.5+) have published numbers showing the earlier exactly_once (v1) design — one producer per task — multiplied the fixed per-transaction coordination overhead by task count, since each task independently opened, committed, and paid the RPC/marker overhead on its own schedule. KIP-447 consolidated to one producer per stream thread, amortizing that fixed cost across every task the thread owns and materially reducing coordinator load and marker volume in high-task-count topologies. Confluent's own published EOS benchmarks report transactional overhead in the single-digit percent range when batched properly (hundreds to thousands of records per commit interval, the Streams default commit interval being 100 ms in EOS mode) — and an order of magnitude worse when applications naively commit a transaction per record.

Incident class 3: transactional.id collisions during rolling restarts

An application that derives transactional.id from a stable per-instance identity (e.g. orders-processor-3) relies on exactly one live process ever using that id at a time. A deploy that briefly runs old and new instances of "processor 3" side by side (a common blue/green misconfiguration) causes the second one to fence the first via the epoch bump — which is the correct outcome, but is frequently misdiagnosed as a bug ("why is my old pod throwing ProducerFencedException and dying?") rather than the safety mechanism working exactly as designed. This is the single most common source of confused support tickets around transactions in production Kafka Streams deployments.

ScalaTransactionCoordinator.scala — handleInitProducerId(), simplified
def handleInitProducerId(transactionalId: String,
                       txnTimeoutMs: Int,
                       expectedPidAndEpoch: Option[ProducerIdAndEpoch]): InitProducerIdResult = {
  val metadata = txnManager.getTransactionState(transactionalId) match {
    case None =>
      // brand-new transactional.id: allocate a producer id, epoch starts at 0
      TransactionMetadata(producerId = pidGenerator.generate(), producerEpoch = 0, state = Empty)
    case Some(existing) =>
      // KEY LINE: bump the epoch on every successful init. This is zombie fencing —
      // no lock, no lease, just "the newest caller wins, everyone older is stale forever".
      existing.copy(producerEpoch = (existing.producerEpoch + 1).toShort)
  }
  // if a previous transaction was left open, fence it first: bump epoch, then
  // asynchronously write abort markers for whatever it had in flight.
  if (metadata.pendingState.isDefined) abortPendingTransaction(metadata)
  txnManager.append(metadata)  // durable to __transaction_state before replying
  InitProducerIdResult(metadata.producerId, metadata.producerEpoch, Errors.NONE)
}

    if (!partitionsInTransaction.contains(tp)) {
        partitionsInTransaction.add(tp);

WHY THE DEVELOPERS WROTE IT THIS WAY

1. Epoch, not lease. A lease needs a clock and a timeout race between renewal and expiry; an epoch needs neither — it's a monotonic counter compared with >=, immune to clock skew, and the comparison is a single integer check on every request. 2. Durable metadata before replying. handleInitProducerId appends to __transaction_state before returning success — exactly the WAL-before-ack discipline you've seen for produce acks and offset commits throughout this course; the transaction subsystem doesn't get a special exemption. 3. Partition declared before data. Requiring AddPartitionsToTxn to complete before the first record for that partition is sent means the coordinator's participant set is always a superset of what actually has data — it can safely write an abort marker to a partition it never actually got data into; the reverse (data arriving before the coordinator knows about the partition) would leave orphaned, un-marked data with no way to signal it was ever transactional.
