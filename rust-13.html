Error Handling In Depth:
One ? Operator, Many Error Types

A function signature in Rust can declare exactly one error type. Real programs fail in layers — a file might not exist, a number might not parse, a business rule might reject the result — and each of those is a genuinely different type with its own fields and its own meaning. This chapter is about the machinery that reconciles those two facts: designing a custom error enum that implements std::error::Error, understanding exactly what the ? operator does when it crosses a type boundary, and knowing when to reach for thiserror, when to reach for anyhow, and when neither is the right tool because the correct response to the failure is to panic!.

ARC 01 · THE PROBLEM

One return type, three ways to fail

Consider a function that loads a small configuration file: it reads bytes from disk, parses one of those bytes into a number, then checks that number against a business rule. Three operations, three independent ways to fail — and three completely different Rust types describing those failures: std::io::Error from the filesystem call, std::num::ParseIntError from the parse, and whatever type you invent for "that number is out of range." A Rust function's signature can declare exactly one error type in its Result<T, E> return — E is one concrete type, not "io::Error or ParseIntError, whichever happens." Reconciling those two facts honestly, without throwing away information, is this chapter's entire subject.

Chapter 7 introduced Result and a first look at ?. This chapter goes past the basics into the four requirements that a real, multi-source error strategy actually has to satisfy, all at once:

  • One return type per function. The compiler needs a single, concrete E to type-check against — there is no way to write "returns io::Error sometimes and ParseIntError other times" as a function signature.
  • Callers need to react differently to different failures. A caller might want to retry a transient I/O failure, reject a request outright on a validation failure, and crash loudly on a failure that should be impossible — three different responses that require knowing which kind of failure occurred, not just that "something" failed.
  • No information may be silently discarded. The original io::Error carries an OS error code; the original ParseIntError carries a specific IntErrorKind. A good error strategy keeps that data reachable, not flattened into an unstructured message the instant it's created.
  • The solution can't be "have fewer fallible operations." Files, network calls, user input, and business rules are fallible in every real system; the strategy has to scale to dozens of call sites across a whole crate, not just the one three-line example above.
WHY THIS MATTERS FOR THE REST OF THIS COURSE

Chapter 14's tests will assert on specific Result variants. Chapters 15 and 16's concurrency and async code propagate errors across thread boundaries and .await points using this exact same Result/?/From machinery — nothing new is invented for concurrent code. And the two crates this chapter centers on, thiserror and anyhow, are two of the most downloaded crates in the entire Rust ecosystem precisely because almost every nontrivial program hits this exact problem. Get the mental model right here and it never needs revisiting.

Notice the shape of the history: every generation invents a mechanism that's either too implicit (C's errno, C++/Java exceptions — you can't tell what a function might do wrong just by reading its signature) or explicit but untyped (early Go — you see the error, but it's just a string-producing interface with no structure). Rust's bet, inherited partly from ML-family languages via Haskell's Either, is that errors should be values, visible in the type signature, exhaustively matchable — and that bet is also why the ecosystem needed a second decade to figure out the ergonomics (thiserror/anyhow, both 2019) on top of the type-system foundation that shipped in 2015.

ARC 03 · NAIVE SOLUTION

Attempt #1: flatten everything to a String

Derive the architecture honestly. The three-step config loader from §1, written the way most people write it the first time — every failure mode converted to a human-readable string as soon as it happens:

rustsrc/config.rs — attempt #1, compiles and runs correctly
use std::fs;

pub struct Config { pub max_retries: u32 }

fn load_config(path: &str) -> Result<Config, String> {
    let contents = match fs::read_to_string(path) {
        Ok(s) => s,
        Err(e) => return Err(format!("couldn't read {}: {}", path, e)),
    };

    let max_retries: u32 = match contents.trim().parse() {
        Ok(n) => n,
        Err(e) => return Err(format!("couldn't parse max_retries: {}", e)),
    };

    if max_retries == 0 || max_retries > 10 {
        return Err(format!("max_retries must be 1..=10, got {}", max_retries));
    }

    Ok(Config { max_retries })
}

This is not a joke architecture — every one of the three failure modes is caught, and the messages are perfectly readable in a log line. If load_config is called from exactly one place (say, main, which just prints the string and exits), this code is arguably fine. The naive solution already gets the hard part — noticing all three failure modes — right. What it gets wrong only shows up once something downstream needs to react to a specific failure rather than just display it.

ARC 04 · WHY IT FAILS

A String is not a type — it's the absence of one

Three concrete failures follow directly from collapsing every error into String, and each one gets qualitatively worse as the codebase grows:

  • Callers can't branch on failure kind without parsing English. If a caller wants to retry only on the I/O failure and reject immediately on validation failure, its only lever is if msg.starts_with("couldn't read") — a coupling to exact wording that a future refactor of the error message (even just fixing a typo) silently breaks. The code still compiles; it just stops working. This is precisely the failure mode Go's standard library hit at scale and had to retroactively patch with typed sentinel/wrapped errors and the errors.Is/errors.As functions in Go 1.13 (2019) — Rust's type system makes the same mistake available, but not the default.
  • The root cause is destroyed at the point of failure. format!("...{}", e) calls e's Display exactly once and then drops e. The io::Error's raw OS error code (reachable via .raw_os_error()) and the ParseIntError's specific IntErrorKind are gone forever once the String exists — there is no path back from the message to the structured data, ever, for any caller, including a future version of the very function that produced the string.
  • It doesn't compose with the rest of the ecosystem. String deliberately does not implement std::error::Error — the standard library could have added a blanket impl for convenience, but chose not to, precisely to keep Error meaning "a structured, chainable failure type" rather than "any text." One concrete, checkable consequence: a function returning Result<T, Box<dyn std::error::Error>> (a common signature for main and for glue code) cannot use ? on a Result<T, String> value, because the required impl From<String> for Box<dyn Error> doesn't exist for the same reason.
A REAL COMPILE FAILURE, CITED EXACTLY

Try to ? a Result<T, String> value inside a function returning Result<T, Box<dyn std::error::Error>> and rustc rejects it with E0277 — the trait bound `String: std::error::Error` is not satisfied, followed by a note that ? requires a From conversion into the declared error type and that no such conversion exists because Box<dyn Error>'s blanket impl is bounded on E: std::error::Error. This is the exact rustc error code you'll see again in this chapter's simulator (§15) whenever a needed From impl is missing — it is the single most common compile error produced by naive, string-based error handling meeting real glue code.

So the fix is not "give up on structure" and it's not "hand-roll a different string format." It's to keep each failure mode as its own real type all the way to wherever it's finally handled, and give the compiler a mechanical way to convert between them at each ?. That's a custom error enum — built next.

ARC 06 · WHY THAT STILL HAS COSTS

The bill: what a custom error enum costs you

Be honest about what this buys and what it doesn't. None of the following is a reason to go back to String — but pretending they're free would be dishonest:

  • Verbosity scales with variant count. By the tenth failure mode, a hand-written enum has ten Display match arms and ten From impls. thiserror removes the mechanical typing but not the design work — you still have to write ten accurate #[error("...")] strings, and nothing checks that they're good messages, only that they compile.
  • A crate-local enum doesn't help across crate boundaries. thiserror is built for a single crate's own public error type. An application that calls into five different libraries, each with its own thiserror enum, still needs either five variants and five From impls in one application-level enum (still boilerplate, just centralized) or something that erases the differences — which is exactly the gap anyhow fills, at a real cost described next.
  • anyhow trades matchability for convenience — and moves the failure mode, doesn't remove it. Downstream code can still ask "was this specifically a ValidationError?" via err.downcast_ref::<ValidationError>(), but that's a runtime check with a fallible outcome: a typo'd turbofish or a wrapped type one layer deeper than expected just silently returns None instead of failing to compile. It is the same "hope you matched the right thing" fragility from §4, moved from string-matching to type-matching, and moved from compile time to runtime.
  • Compile-time cost is real, if usually acceptable. Both crates are small, but both are proc-macro or macro-adjacent dependencies, and on a workspace with hundreds of crates each deriving Error, that's measurable wall-clock time on every clean build — see §11's third incident and §14's tooling chapter.
  • "When to panic! instead of Result" is a judgment call, not a rule. Over-wrapping things that genuinely cannot fail at runtime (indexing a literal, known-in-bounds array with a Result "just in case") clutters signatures with unreachable Err arms callers must still handle. Under-wrapping — panicking on an expected, recoverable failure like a missing config file — takes down an entire process instead of returning a value a caller could act on. The rule of thumb that holds up: panic! for violated invariants a correct caller could never trigger (an internal assertion, a genuinely unreachable match arm); Result for anything an external actor — a filesystem, a network peer, a user — can cause.
ARC 07 · FINAL ARCHITECTURE

The boundary model: concrete inside, erased at the edge

The final mental model is not "always use thiserror" or "always use anyhow" — it's a placement rule based on who is calling your code. THE RULE OF THUMB

If you're writing a library, or any code whose caller you don't control, make errors matchable — a concrete enum, typically via thiserror, implementing std::error::Error. If you're writing an application's top layer — main, a CLI, a request handler that only ever logs or displays the failure — erase the type with anyhow::Error and attach human-readable context as the error travels up. The ? operator is what makes both layers coexist in one call stack without either one knowing about the other's error type.

ARC 08 · INTERNAL IMPLEMENTATION

What ? actually does, and what your enum actually costs

Two mechanisms, both invisible from the call site. First: the real desugaring of ? — the exact reason a missing From impl is a compile error rather than a runtime surprise. Second: what a growing error enum costs in memory, on every Result that uses it — including the successful ones.

(a) The ? operator's real desugaring

WHY YOU CAN'T MAKE YOUR OWN TYPE WORK WITH ? ON STABLE

The Try/FromResidual machinery that powers ? generically is real, but it's gated behind the unstable try_trait_v2 feature. On stable Rust, only Result, Option, ControlFlow, and Poll implement it — which is exactly why the classic mental model from step 4 above (a match plus From::from) has stayed completely accurate for Result since Rust 1.0, even though the trait machinery underneath it was redesigned twice.

(b) What a growing error enum costs — even on the success path

Result<T, E> is a single Rust value; its size is fixed at compile time and must be big enough to hold either arm, discriminant included. That size applies to every Result<T, E> your function returns or holds on the stack — the Ok path pays for the size of your error type too, even when nothing fails. Drag the sliders to see it:

ARC 09 · TRADEOFFS

The same problem, five ways

Every language that predates Rust — and Rust's own two-crate ecosystem answer — made a different placement of the same underlying costs. Read the table as a proof by exhaustion: nobody has made "tell the caller what went wrong" free.

The pattern to notice: typed, matchable errors and cheap, generic propagation are in genuine tension — every system either picks one or, like Rust's ecosystem, ends up with two complementary tools instead of one universal answer.

ARC 10 · PERFORMANCE CHARACTERISTICS

The one number that actually matters: cost when nothing fails

Result-based error handling has a property exceptions do not: the success path and the failure path cost the same. A ? is a branch and a move — the same instructions execute whether the branch is taken or not. Exception-based systems are the opposite: throwing is disproportionately expensive relative to a normal return, because it walks the stack looking for a handler and, in managed runtimes, often captures diagnostic state along the way. ARC 11 · REAL-WORLD PRODUCTION

Three incidents that shaped how the ecosystem actually handles errors

Incident 1: the failure crate's rise and deprecation

Before thiserror and anyhow existed as a pair, the failure crate (2017, by Rust core contributor "withoutboats") tried to solve both problems — matchable library errors and convenient application-level propagation — with one Fail trait and one failure::Error wrapper that automatically captured a backtrace on construction. It was widely adopted. It was also, in practice, the wrong shape: a single trait tried to serve two audiences with genuinely conflicting needs (concrete-and-matchable vs. erased-and-convenient), and the automatic backtrace capture on every error added cost even to call sites that never wanted one. failure's own documentation now directs users to thiserror for library errors and anyhow for application errors — a real, public admission that splitting the concern into two focused crates was the correct design, arrived at only after a widely-used single-trait alternative had been tried and found wanting at scale.

Incident 2: a panic in one request must not take the whole server down

Result handles expected failure. It does nothing for the other failure mode this chapter's §6 discussed — a panic!, whether from an explicit invariant check or an .unwrap() on attacker-controlled input reaching deep into a call stack. A panic unwinds straight past every Result-returning function in its path; none of this chapter's machinery catches it. This is a well-known, repeatedly-hit class of production incident in Rust web services: a single malformed request triggers a panic in request-handling code, and if nothing bounds the blast radius, one bad client takes down every other connection sharing that worker. It's exactly why async runtimes and web frameworks build an explicit boundary around it — a spawned tokio task that panics fails only its own JoinHandle rather than crashing the runtime, and frameworks built on top (such as actix-web) additionally wrap request dispatch so one handler's panic doesn't propagate to sibling in-flight requests on the same worker. The lesson generalizes past any one framework: Result and panic! are not two flavors of the same thing — they need entirely different containment strategies, and a system is only as safe as its weaker one.

Incident 3: derive-macro-heavy error handling is a documented compile-time tax

Both thiserror and serde_derive are proc-macro crates, and proc-macro compilation — parsing your enum, running arbitrary macro code, generating and re-parsing new source — is measurably slower than compiling equivalent hand-written code. This isn't a rumor: it's exactly why Cargo shipped a stabilized --timings flag (stable since Rust 1.60, 2022), specifically so teams could see which dependencies — frequently the derive-macro-heavy ones sitting at the base of nearly every dependency graph — dominate a clean build's wall time. The honest takeaway for this chapter: reaching for #[derive(Error)] on every small crate in a large workspace is a real, cumulative build-time decision, not a free ergonomic win — usually still worth it, but worth measuring with --timings rather than assuming.

Reading the real thing: std::error::Error, thiserror, and anyhow

Where this chapter's machinery actually lives, simplified from real source but faithful in structure and naming.

First, the trait everything else is built on — simplified to the parts stable Rust actually uses:

ruststd/src/error.rs — the Error trait, simplified
pub trait Error: Debug + Display {
    /* The one method with real behavior. Default: no underlying
     * cause. A variant WRAPPING another error overrides this to
     * hand back a reference to it — this is the "error chain".  */
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        None
    }
    // cause() and description() existed historically; both are
    // deprecated in favor of source() and Display, respectively.
}

impl From<std::io::Error> for ConfigError {
    fn from(e: std::io::Error) -> Self { ConfigError::Io(e) }
}
impl From<std::num::ParseIntError> for ConfigError {
    fn from(e: std::num::ParseIntError) -> Self { ConfigError::Parse(e) }
}
impl From<ValidationError> for ConfigError {
    fn from(e: ValidationError) -> Self { ConfigError::Validation(e) }
}

anyhow solves a completely different problem the same crate author also cared about: making the erased type as cheap as possible to pass around. A Box<dyn std::error::Error> is a fat pointer — two machine words, one to the data and one to its vtable. anyhow::Error is deliberately just one word:

rustanyhow/src/error.rs + kind.rs — simplified, faithful in structure
pub struct Error {
    // ONE pointer. The vtable pointer lives INSIDE the heap
    // allocation (as ErrorImpl's first field) instead of beside
    // this handle — the classic "thin trait object" trick.
    inner: ManuallyDrop<Box<ErrorImpl<()>>>,
}
struct ErrorImpl<E> {
    vtable: &'static ErrorVTable,   // hand-built: drop / debug / display / source / downcast fn ptrs
    backtrace: Option<Backtrace>,
    _object: E,
}
// THE line that makes `?` work for ANY std error, with zero
// per-error-type glue code required from the caller:
impl<E> From<E> for anyhow::Error
where
    E: std::error::Error + Send + Sync + 'static,
{
    fn from(error: E) -> Self { Error::from_std(error) }
}
WHY THIS EXPLAINS §7's RULE OF THUMB

That blanket impl<E: Error + Send + Sync + 'static> From<E> for anyhow::Error is the entire reason anyhow feels "automatic" at the application boundary — any type that correctly implements std::error::Error (which is exactly what §5's hand-written or thiserror-derived enum does) already satisfies it, so ? converts into anyhow::Error for free. This is also precisely why a library should still implement std::error::Error properly even if it expects most callers to use anyhow — skipping it would silently break that conversion for every downstream application.
