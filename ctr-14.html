CONTAINER INTERNALS · CHAPTER 14

Pods & systemd:
Grouping and Keeping Containers Alive

Chapter 12 established that Docker keeps one persistent daemon and Podman keeps none. Chapter 13 showed each engine's answer to "how do containers reach each other over a network." This chapter asks two questions neither of those answered: how do you make several containers behave like one unit — sharing a loopback interface, a hostname, a slice of System V shared memory — and how do you make any of this survive a reboot without a control-plane cluster sitting on top of it? Podman's answers are the pod abstraction and Quadlets; Docker's are Compose and a daemon that must simply stay up. Both answers are consequences of the daemon/fork-exec split you already understand — this chapter shows exactly how.

ARC 01 · THE PROBLEM

"Keep this running" is actually two unrelated questions

Every earlier chapter in this course treated a container as a single, standalone thing: one process tree, one set of namespaces, one cgroup. Real workloads are rarely that tidy. A web application usually ships with a log-shipping sidecar that needs to read the same files; an API server is deployed next to a metrics-scraping helper that needs to reach it over localhost, not a routed network hop; a database container is paired with a backup agent that needs to see the same IPC segment for a hot-standby handshake. And none of that matters at 3 a.m. during a host reboot if nothing brings any of it back.

Pull those two concerns apart, because engineers reliably conflate them and the conflation is where the interesting engineering lives:

  • Grouping. Several containers need to behave, from each other's point of view, like separate processes on one machine rather than separate machines on a network — reachable over localhost, sharing a hostname, optionally sharing a System V or POSIX IPC segment. This is a namespace problem: which kernel namespaces do these containers hold in common?
  • Persistence. Whatever you built — one container or a group of them — needs to still be running (or be automatically restarted) after the process that created it has long since exited, after the operator has logged out, and after the machine has rebooted. This is a supervision problem: what long-lived component notices absence and acts on it?

Chapters 1–13 gave you every primitive these two problems are built from — namespaces (2–4), the OCI runtime lifecycle (9), and each engine's process architecture (12) — but never asked either question directly. Docker's ecosystem answers grouping with Compose and persistence with the daemon simply being expected to stay up (plus --restart policies the daemon enforces, per chapter 12 §6). Podman answers grouping with a native pod object structurally identical to a Kubernetes Pod, and persistence by handing the whole problem to systemd — first through an imperative code-generation command, later through a declarative unit format called Quadlets. Neither engine's answer is a container-runtime feature at all; both are userspace decisions about which existing primitive to reuse rather than reinvent.

WHY THIS MATTERS FOR THE REST OF THE COURSE

This chapter is where the course's Docker/Podman comparison turns from "two engines with different clients" into "two engines with different opinions about what belongs in a container runtime at all." Podman's answer — reuse the namespace-sharing trick Kubernetes already validated, and hand persistence to the init system that's already PID 1 — is a direct architectural consequence of chapter 12's no-daemon decision: with no daemon to hold pod state or restart policy in memory, something else has to, and Linux already has exactly one thing that has held "which services should be running" for every process on the box since boot.

DEEP CONTEXT · THE "PAUSE" CONTAINER'S FAMILY TREE

Kubernetes' pause container and Podman's infra container are not parallel inventions — Podman's engineers deliberately copied Kubernetes' mechanism because it was already battle-tested at enormous scale. Both are processes whose entire executable is a loop that does nothing but wait for a signal; both exist purely to be a /proc/<pid>/ns/* anchor that other containers can borrow namespaces from. The difference is provenance, not mechanism: Kubernetes' pause binary is a tiny static C program shipped in a registry.k8s.io/pause image pulled from a registry; Podman compiles its own equivalent internally and materializes it as a local image (localhost/podman-pause) with no registry pull at all — a change motivated by exactly the kind of air-gapped-network incident §11 covers.

ARC 03 · NAIVE SOLUTION

Attempt #1: share namespaces by hand, one flag at a time

Derive it honestly, the way this course always does. Chapters 2–4 already told you that docker run and podman run both expose flags that let one container join another specific container's namespace instead of getting a fresh one: --network container:<name>, --ipc container:<name>, and --pid container:<name> have existed on both engines for years, predating any notion of a "pod." So: why not just use them?

shnaive-pod.sh — hand-rolled namespace sharing, no pod object at all
#!/bin/sh
# "give me a pod" attempt #1 — plain docker run, container by container.
set -e
docker run -d --name app app-image
docker run -d --name sidecar \
  --network container:app \
  --ipc     container:app \
  sidecar-image
# app and sidecar now share ONE network namespace (sidecar can reach
# app's ports on 127.0.0.1) and ONE IPC namespace (SysV/POSIX segments
# app creates are visible to sidecar). Two flags, two namespaces, done...
# ...almost. Try the same trick for the THIRD namespace a pod needs.
docker run -d --name sidecar2 \
  --uts container:app \
  sidecar2-image
# docker: Error response from daemon: invalid UTS mode: container:app
# --uts only ever accepts "host" — there is no --uts=container:.

For exactly two containers and exactly two namespace types, this script is not a joke — it works, today, on both engines, and plenty of production Compose files quietly rely on the same network_mode: "service:app" trick under the hood. It already demonstrates the core idea correctly: namespace sharing is a create-time reference, not a runtime negotiation. Watch what happens the moment you need it to work for more than two containers, or for the one namespace type that Docker's CLI never exposed a reference flag for.

ARC 04 · WHY IT FAILS

Two failures: a missing flag, and an ordering problem that gets worse with N

The naive script's problems are specific and nameable, not vague hand-waving about "it doesn't scale":

  • Failure 1 — no CLI reference for UTS. Docker's --network, --ipc, and --pid flags all accept a container:<name> value; --uts does not — it accepts only host (share the host's UTS namespace, a very different and much less safe thing) or the default of a fresh private one. There is structurally no way, using docker run flags alone, to give two independent containers the same hostname the way a real pod would. Any script that "shares everything a pod shares" using only hand-picked flags is silently incomplete — it shares two of the three namespaces a pod needs and has no path to the third.
  • Failure 2 — the reference target must already exist and stay alive. Every container:app reference is resolved once, at the moment the second container is created, against whatever process is app's namespace owner right now. There is no independent, disposable anchor — app itself is doing double duty as a real workload container and the thing every sidecar's namespaces depend on. Restart app (a new PID, a new set of namespaces) and every container that referenced the old app is now pointing at namespaces nobody occupies — Docker's own docs describe this exact case as leaving dependents with a dead reference. Scale this to N sidecars around one "anchor" container and you've built a system where the anchor cannot ever be restarted independently of everything that depends on it — the opposite of the fault-isolation this course has spent thirteen chapters establishing namespaces exist to provide.
THE NUMBERS: WHAT "GROUPED" ACTUALLY COSTS WITHOUT A POD

Take 100 logical three-container groups (app + sidecar + metrics-helper) built the naive way, one --network container: chain each. That's 100 independent network namespaces (one per group, correctly shared) — the sharing itself is cheap. The real cost is operational: 100 separate "which container is the anchor" facts an operator must remember, 100 places where restarting the wrong container in the wrong order breaks two siblings, and zero of the 100 groups can share a hostname, because the flag to do that does not exist. Compare that to Compose's approach in the next section, which sidesteps the ordering trap entirely by not sharing any of these namespaces at all — a different, equally real cost you'll quantify in §9.

Two shapes emerge from this failure. One gives up on sharing namespaces at all and links containers purely over the network — that's Docker Compose. The other builds a purpose-made, disposable anchor whose only job is holding namespaces open — that's the pod. §5 derives the second one properly.

ARC 05 · BETTER SOLUTION

Give the group its own namespace owner that does nothing else

Restate the requirement precisely, because the fix follows directly from precision: a pod must let N containers behave, from each other's point of view, as if they were N ordinary processes started on one already- running machine — same loopback, same hostname, same visibility into SysV/POSIX IPC objects. That is exactly three namespace types (network, UTS, IPC), held in common, for the lifetime of the group. Step through how Podman builds that.

Building a pod, conceptuallySTEP-BY-STEP
THE DEFAULT SHARE SET, PRECISELY

podman pod create's default --share value is cgroup,ipc,net,uts — not pid, not mount, not user. Each container in a pod still gets its own private PID namespace (so pid 1 inside container A is not visible to container B — a crash in one doesn't corrupt the other's process tree) and its own private mount namespace (so container A's filesystem layout is invisible to container B). This is the exact set Kubernetes shares by default too — network and IPC, plus the hostname — which is precisely why the phrase "structurally identical to a Kubernetes Pod" is not marketing, it's a namespace-for-namespace match.

ARC 06 · WHY THAT STILL COSTS

Pods solve grouping. They say nothing about persistence.

A pod is a real improvement over the naive script — one purpose-built anchor instead of an overloaded workload container, a defined and complete share set instead of two-thirds of one. But look at what it has not solved, and notice that none of its remaining costs are namespace problems:

  • The shared network namespace is also a shared port space. Because every container in the pod sees the same loopback and the same set of bound sockets, two containers in one pod cannot both bind port 80 — a constraint that simply does not exist for two Compose services, each with their own network namespace. Grouping and port isolation are now in direct tension; you trade one for the other.
  • The anchor is a new single point of failure for the group. If the infra container is OOM-killed or crashes, the kernel keeps its namespaces alive only as long as some other process still references them (each namespace is refcounted) — but nothing is left responsible for that reference, and Podman marks the pod degraded: new containers cannot join, and pod-scoped operations start failing. A bug in a two-line pause loop can now take an entire application's networking down with it.
  • Pods do not survive process exit, let alone a reboot. podman pod create and podman run --pod are just commands. The moment the terminal that ran them closes — or the machine reboots — nothing about "there was a pod called myapp" persists as a running thing unless some other, longer-lived component is told to recreate it. A pod, on its own, is exactly as ephemeral as the naive script from §3; it has only solved which namespaces get shared, not who notices this should still be running.
THE HONEST COMPARISON WITH DOCKER'S SIDE OF THIS BILL

Docker Compose's multi-service applications never hit the port-collision or degraded-anchor problems above, because they never share those namespaces in the first place — each service gets a private network namespace and reaches its neighbors over the project's bridge network by name. Compose's bill is the one chapter 12 and 13 already charged you: an extra network hop and DNS lookup per cross-service call, and dependence on dockerd being alive for its restart policy to fire. Podman's bill is this section's three items. Neither bill is smaller — they are different bills for a genuinely different feature. §9 puts both side by side honestly.

Persistence is the piece nothing in this chapter has provided yet. Linux already has a component whose entire job, since boot, is "notice a unit isn't running and start it, in dependency order, without anyone logged in" — and it is not part of either container engine. §7 shows the constellation that results from handing the problem to it.

THE DETAIL THAT MAKES §9 MAKE SENSE

Notice which boxes are "generated." A Quadlet .container/.pod file is not itself a systemd unit — it is source text that a systemd generator (a program systemd runs automatically very early in boot, and again on every daemon-reload) reads and turns into an ordinary transient .service file. Delete the Quadlet source and the next daemon-reload makes the generated unit disappear with it. That regenerate-from-source relationship is precisely what makes Quadlets immune to the stale-reference bug §11 documents for the older podman generate systemd command, which instead wrote a unit file once and then never touched it again.

Quadlets replace the generation command with a generation daemon-adjacent process: you write a small declarative file, and /usr/lib/systemd/system-generators/podman-system-generator — an ordinary systemd generator, invoked automatically, not a background process — regenerates the real unit from it every time systemd asks.

(c) Rootless persistence: loginctl enable-linger, and why Docker still needs a daemon here too

Neither engine's rootless story is "no process is ever required." Both require exactly one thing to still be alive after you log out: for Podman, that thing is the ordinary user systemd instance (user@<uid>.service) that runs your Quadlet units; for Docker rootless, it is a copy of dockerd running as your unprivileged user, itself started as a systemctl --user-managed service. Without loginctl enable-linger <user>, systemd-logind tears down a user's systemd instance — and everything under it — the moment their last login session ends; with it, user@<uid>.service starts at boot and stays up regardless of whether anyone is logged in.

THE NUANCE THAT SURPRISES PEOPLE

Docker's own rootless documentation recommends loginctl enable-linger too — for exactly the same logind reason. So both engines' rootless modes need lingering enabled to survive logout. The difference is what lingering is keeping alive: for Podman, it's a systemd instance that would need to exist for any rootless user service, container or not — Podman adds no daemon of its own to that bill. For Docker, lingering is keeping a whole second copy of the container engine — dockerd, per user, as an unprivileged persistent process with its own restart-manager decision loop (chapter 12 §6) — resident for as long as any container needs to be reachable. "Needs lingering" is the same requirement on paper; "what lingering is holding up" is not the same system.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

Fewer namespaces, fewer objects — but a new one to trust

Grouping into pods changes two numbers you can predict before benchmarking: how many kernel namespace objects a fleet creates, and how many long-lived processes exist to attack.

  • Namespace count scales with grouping strategy, not container count. A fleet of G logical three-container groups creates 3·G network namespaces under Compose (one per service, always) but only G under Podman pods (one per pod, shared by all three members) — a 3× reduction in objects the kernel's namespace-refcounting and network stack has to track, and a matching reduction in the number of independent iptables/nftables chains and veth pairs at scale.
  • The infra container is a new component in the trust chain, but not a new privileged one. It runs no application code, holds no capabilities beyond what any unprivileged container gets, and its entire attack surface is "a static binary that calls pause() in a loop." Compromising it buys an attacker nothing that compromising any pod member wouldn't already buy them, since they'd land in the same shared network and IPC namespace either way.
  • Rootless Docker's daemon is a persistent process regardless of privilege level. Chapter 12 already established that an always-on daemon is a nameable attack surface at rest; dropping to an unprivileged user shrinks the blast radius of a compromise but does not remove the daemon from the process table. Rootless Podman has no equivalent resident engine process between invocations — only conmon, one per running container, each holding only that one container's file descriptors.

ARC 11 · REAL-WORLD INCIDENTS

Four incidents this chapter's mechanics explain exactly

Incident 1: the systemd unit that pointed at a container that no longer existed

Before Quadlets existed, Podman's own documentation for podman generate systemd (non---new mode) carried an explicit warning: the generated unit's ExecStart=podman start <id> line hard-codes a specific container ID at generation time. Run podman rm and recreate the container by hand — or let an automated cleanup job do it — and the unit silently starts pointing at nothing. systemctl start myctr.service then fails with "no such container," and the failure mode looks like a systemd problem when the actual cause is a stale reference baked into a file nobody thought to regenerate. The --new flag was introduced specifically to make the unit recreate its target on every start instead of assuming it still exists; Quadlets remove the class of bug entirely, since the unit is never hand-frozen in the first place — it's rebuilt from source on every daemon-reload.

Incident 2: containers that stopped the moment the SSH session ended

The single most common rootless-Podman support question is some variant of "my containers were running, I closed my terminal, and now they're gone." The mechanism is exactly §8(c): without loginctl enable-linger <user>, systemd-logind considers the user's systemd instance — and everything running under it, Quadlet-managed containers included — tied to that user having an active session. Close the last session and logind tears the instance down. Every Podman quickstart guide now leads with the loginctl enable-linger command precisely because omitting it produces a failure that looks intermittent and environment-specific but is actually a single, well-understood, one-line fix.

Incident 3: the air-gapped host that couldn't create a pod

Early Podman releases resolved a pod's infra container the same way Kubernetes resolves its pause container — by pulling a pause image from a public registry. On a locked-down enterprise or air-gapped host with an application image already staged locally, podman pod create would still fail outright on a registry pull it had no business needing, for an image that runs no application logic at all. Podman's fix was to stop depending on a registry-hosted pause image and instead compile a minimal static binary into the podman executable itself, materializing it as a locally-built localhost/podman-pause image with zero network dependency — turning a networking incident into a non-issue by removing the namespace requirement's dependency on the network at all.

Incident 4: "the container looks healthy" during a rootless networking outage

Rootless Docker's userspace networking stack (RootlessKit plus a port-forwarding driver — slirp4netns or the newer, faster pasta, both covered in chapter 13) runs as a separate process from dockerd itself. If that forwarding process dies or wedges while the daemon and the container's own process keep running, docker ps reports the container healthy and running — because it genuinely is — while every inbound connection to a published port silently fails. The blind spot exists because container health and port-forwarding health are tracked by two different processes with no shared health check between them; rootless Podman's equivalent forwarding path has the same structural exposure, but with fewer moving parts per container since there's no always-on daemon layer sitting above the forwarder to have its own, separate opinion about whether everything is fine.

gopkg/specgen/generate/pod_create.go — MakePod(), simplified
func MakePod(p *specgen.PodSpecGenerator, rt *libpod.Runtime) (*libpod.Pod, error) {
    // Default --share: cgroup,ipc,net,uts — NOT pid, NOT mount, NOT user.
    nsOpts, err := GetNamespaceOptions(p.SharedNamespaces)
    if err != nil { return nil, err }

    options := append([]libpod.PodCreateOption{
        libpod.WithPodName(p.Name),
        libpod.WithInfraContainer(),   // every pod gets one unless --infra=false
    }, nsOpts...)

    pod, err := rt.NewPod(context.Background(), rt.SystemContext(), options...)
    if err != nil { return nil, err }

    // The infra container is a NORMAL OCI bundle whose config.json requests
    // fresh net/ipc/uts namespaces (Path == ""). runc/crun create() allocates
    // them via clone(CLONE_NEWNET|CLONE_NEWIPC|CLONE_NEWUTS|...) the same way
    // any standalone container would — nothing about the infra container's
    // OWN creation is special. What's special is what happens next.
    infraSpec := newInfraContainerSpec(p)
    infraCtr, err := rt.NewInfraContainer(context.Background(), infraSpec, pod)
    return pod, err
}
gopkg/specgen/generate/container_create.go — joinPodNamespaces(), simplified
func joinPodNamespaces(pod *libpod.Pod, g *generate.Generator) error {
    infra := pod.InfraContainer()
    shared := map[string]bool{"net": true, "ipc": true, "uts": true}

    for ns := range shared {
        if !pod.SharesNamespace(ns) { continue }
        path := fmt.Sprintf("/proc/%d/ns/%s", infra.PID(), ns)
        // This is the ENTIRE mechanism: config.json gets a namespace entry
        // with a concrete Path instead of an empty one. runc/crun read that
        // and call setns(open(path, O_RDONLY), CLONE_NEWNET) — or IPC/UTS's
        // equivalent flag — BEFORE this container's own clone() runs, so its
        // private PID and mount namespaces are still created fresh.
        g.AddOrReplaceLinuxNamespace(ns, path)
    }
    return nil
}
WHY THE DEVELOPERS BUILT IT THIS WAY — TWO CHOICES TO STEAL

1. The infra container is created through the exact same code path as any other container. No special "pod-mode" branch exists in the OCI runtime; the only difference is that its namespaces are requested fresh (empty Path) while everyone else's config.json requests the infra container's namespaces by path. Reusing one mechanism for both "create" and "join" is what makes the model easy to reason about — there is exactly one way any container's network namespace comes to exist, either owned or borrowed. 2. Quadlets make regeneration a systemd concern, not a Podman concern. podman-system-generator is a systemd generator, invoked by systemd's own generator protocol — Podman doesn't need to watch for file changes, run a background reconciliation loop, or ship any daemon of its own to keep units in sync. It only needs to correctly implement one contract (read source files, emit unit files, exit) and let systemd's existing machinery call it at the right times. That is the same "reuse the trusted supervisor's mechanism, don't build a parallel one" instinct that runs through this entire chapter.
