Unsafe Rust & FFI:
The Five Promises You Sign

The word unsafe does not turn Rust off. The borrow checker still runs, moves are still tracked, types are still checked — unsafe unlocks exactly five additional operations the compiler cannot prove safe on its own, and asks you, the programmer, to uphold the invariant it can no longer verify. This chapter names all five precisely, derives why raw pointers exist alongside references, shows the real syntax for calling C from Rust and Rust from C, and studies a real CVE that happened when one of those five promises was broken in the wild.

ARC 01 · THE PROBLEM

Rust's proof system has a boundary, and reality lives past it

Every guarantee this course has built on so far — one mutable reference xor many immutable ones, no dangling references, no data races across threads without explicit opt-in — is a proof the compiler constructs at compile time, using only information visible inside your Rust source. That proof is extraordinarily good at what it covers. It is also, provably, incomplete: there exist entire categories of correct, necessary programs whose correctness depends on facts the type system cannot see.

Four concrete examples, none of them exotic:

  • Talking to hardware. A memory-mapped UART register at a fixed physical address is, to the borrow checker, just an integer. Reading it might return a different value than you wrote — an ordinary Rust reference is not allowed to behave that way (aliasing an immutable reference must be stable), but a device register must.
  • Talking to C. Roughly every operating system syscall, most GPU drivers, and the overwhelming majority of extremely mature numerical, cryptographic, and compression libraries (OpenSSL, zlib, BLAS, SQLite) expose a C ABI and only a C ABI. The borrow checker has never seen that code and never will.
  • Building the safe abstractions themselves. Vec<T> grows its buffer by asking the allocator for raw memory and manually tracking how much of it is initialized. Nothing about "ask the OS for a pointer to N uninitialized bytes" is expressible in terms of borrows and lifetimes — someone has to drop down and say so explicitly.
  • Squeezing out a proof the checker is just too conservative to find. Sometimes you, the programmer, know an index is in bounds from an invariant three functions away that the compiler has no way to see, and you want to skip a bounds check it would otherwise insert.

A language with no escape hatch for these cases is not a safer language — it is a language people abandon for the task, or silently work around with dark patterns (global mutable state disguised as something else, transmute-free but semantically identical hacks). Rust's actual answer is narrower and more honest: a single keyword, unsafe, that unlocks exactly five specific operations — no more — and nothing else. Everything else in the language, including inside an unsafe block, remains fully checked. This chapter is about naming those five precisely, understanding the promise each one asks you to make, and seeing what happens — with a real CVE — when the promise is broken.

THE CENTRAL DISTINCTION THIS CHAPTER TURNS ON

Unsafe code is not incorrect code, and safe code is not automatically correct code that never crashes. unsafe means "the compiler cannot check this for you"; it does not mean "anything goes." A correct unsafe block upholds every invariant the compiler would have checked, just without its help. An incorrect one produces undefined behavior — not a controlled panic, not a wrong-but-bounded answer, but a program the Rust abstract machine has no defined semantics for at all, exactly like undefined behavior in C. That distinction — soundness — is the vocabulary this entire chapter builds toward.

DEEP CONTEXT · WHY NOT JUST "TRUST EVERYTHING", C's ANSWER

C's model is simpler and older: every pointer operation is exactly as trusted (and exactly as unchecked) as every other. There is no way to mark 5% of a C codebase as "the part that needs a human to verify by hand" — by default, all of it does. Rust's bet, inherited from the region-based and capability research of the 2000s, is that if 95% of a codebase can be mechanically proven safe, the remaining 5% becomes a tractable, groppable, code-review-able surface — grep -r unsafe — instead of an undifferentiated haystack the size of the whole program.

Notice what these five have in common structurally: none of them is a syntax error, a type error, or a borrow-checker rejection in the usual sense. Each one is memory- or thread-safe most of the time — the compiler is refusing not because it has proven the code wrong, but because it has proven it cannot prove the code right, and Rust's rule is that unprovable operations require an explicit, visible signature from a human before they run.

ARC 04 · WHY IT FAILS

What each rejection is actually protecting against

The five compile errors are not arbitrary compiler pedantry — each guards a specific, well-documented bug class that has cost the software industry real money and real security incidents for decades:

  • Raw pointer dereference (E0133). Guards against dereferencing a pointer that is null, dangling, or misaligned — the mechanism behind the majority of C/C++ memory-corruption CVEs (buffer overflow, use-after-free, type confusion — CWE-119, CWE-416, CWE-843).
  • Calling an unsafe fn (E0133). Guards against violating a precondition the function's author could not encode in its type signature (e.g. "this slice must be non-empty," "this index must be in bounds," "this pointer must have come from this specific allocator").
  • Mutable static access (E0133). Guards against a data race — undefined behavior in Rust's memory model exactly as in C's, and one of the two bug classes (alongside use-after-free) that a garbage-collected or borrow-checked language exists specifically to eliminate.
  • Implementing an unsafe trait (E0200). Guards against violating a semantic invariant the trait promises that the compiler has no way to check — the canonical example being Send ("values of this type can be safely transferred to another thread") and Sync ("references to this type can be safely shared between threads"), both of which are themselves unsafe traits in the standard library.
  • Union field access (E0133). Guards against type confusion: a union's fields all occupy the same bytes, so reading one after writing another reinterprets the bit pattern with zero compiler-enforced correspondence between the two.
THE NUMBERS THAT MOTIVATED THIS WHOLE LANGUAGE

Independent audits at both Microsoft and Google's Chrome security teams, published years apart, converged on the same figure: roughly 70% of the high-severity security vulnerabilities fixed each year in their C and C++ codebases are memory-safety bugs — the exact bug class the five rejections above exist to fence off. That is not a Rust marketing number; it is why Microsoft, Google, and the Linux kernel each independently started adopting Rust in security-critical components in the years that followed. Every one of the five "unsafe superpowers" in §7 is a place where that 70% figure gets to happen again, on purpose, under audit — unless the programmer upholds the promise.

So the five operations cannot simply be forbidden — real programs need all five, for the reasons in §1 — and they cannot be permitted unconditionally either, or Rust degrades to C's blanket-trust model. The next section derives Rust's actual answer: permit them, but only inside an explicit, lexically-scoped, greppable marker.

THE PATTERN EVERY IDIOMATIC UNSAFE-USING CRATE FOLLOWS

Vec, String, Mutex, and essentially every "safe abstraction over unsafe internals" in the standard library follows the identical shape you just stepped through: perform the unsafe operation in the smallest possible scope, verify every precondition it depends on before that scope (with a real runtime check, an assertion, or a type-level guarantee), and expose only a fully safe function signature to callers. The unsafe keyword never appears in the public API — it appears only in the implementation, once, next to a comment explaining exactly which invariant justifies it. That comment is not optional style; the Rust standard library's own contribution guidelines require a // SAFETY: comment on every unsafe block for precisely this reason.

ARC 06 · WHY THAT STILL HAS COSTS

Be honest: unsafe does not make the problem go away

It is tempting to read §5 and conclude the problem is solved — wrap the dangerous part, expose a safe API, done. That is necessary but not sufficient, and pretending otherwise is how real CVEs happen (§11). Four costs that do not disappear:

  • The compiler checks nothing extra inside unsafe — it checks strictly less. A common misconception is that unsafe "turns on" some special verification mode. It does the opposite: it turns off the one compiler check (E0133/E0200) that would have stopped you, and every other check — types, moves, ordinary borrows — still runs, but none of them were the check that mattered here. You are now the entire verification pipeline for this one operation.
  • The aliasing rules inside unsafe are still real, just unchecked. Rust's memory model (formalized by the Stacked Borrows and, since 2023, Tree Borrows research models) still forbids things like a &mut T and any other live reference to the same memory existing simultaneously — unsafe lets you construct raw pointers that violate this, and doing so is undefined behavior even though rustc will happily compile it and the binary may run correctly for years before a compiler upgrade changes an optimization and the bug surfaces.
  • Unsoundness is not contained to the block it appears in. If one unsafe block violates an invariant, the undefined behavior it causes can manifest anywhere in the program — a corrupted allocator freelist from one bad unsafe block might crash a completely unrelated, perfectly safe function ten thousand lines away. This non-locality is exactly why tools like Miri (an interpreter that catches Stacked-Borrows violations dynamically) and cargo geiger (which counts and reports every unsafe usage in your dependency tree) exist as near-mandatory tooling for any codebase that uses unsafe seriously.
  • The FFI boundary specifically adds a second, independent hazard: panics. A Rust panic unwinding across an extern "C" boundary into C — code with no concept of Rust's unwinding mechanism — is undefined behavior. Any Rust function exposed to C must either guarantee it cannot panic, or wrap its body in std::panic::catch_unwind at the boundary. §8 and §15 make this concrete.

None of this is an argument against unsafe — §1 already established that a language without it cannot do systems programming at all. It is an argument for treating every unsafe block as a hand-written proof obligation, reviewed with the same rigor as a security patch, not a way to make the borrow checker's complaint disappear.

THE BOUNDARY DRAWN AS A SENTENCE

Safe Rust is the load-bearing wall; unsafe blocks are the small number of doors cut into it, each one exactly wide enough for one specific operation, each one requiring a signature. Everything on either side of a door is still checked by the same compiler, under the same rules — the door itself is the only place trust was manually extended. That is the entire mental model this chapter wants you to leave with.

ARC 08 · INTERNAL IMPLEMENTATION

What the compiler actually does with the word unsafe — and the real FFI syntax

Three pieces: (a) where in the compiler pipeline unsafe is checked (and how little it changes about codegen), (b) the real syntax for crossing the Rust↔C boundary in both directions, and (c) why struct layout — repr(Rust) vs repr(C) — is a live FFI correctness issue, not a cosmetic one.

(a) unsafe is a front-end permission check, erased before codegen

A common intuition — that unsafe code compiles to different, less-checked machine code — is wrong. unsafe exists entirely in the compiler's early, type-aware stages; by the time code reaches LLVM there is no "unsafe" bit left anywhere. Step through the pipeline:

Where "unsafe" lives in rustcSTEP-BY-STEP

(b) Calling C from Rust: extern "C" blocks

To call a foreign function, you declare its signature in an extern block — a promise to the compiler about what the symbol looks like, which it cannot verify (the real definition lives in someone else's compiled object file). Calling anything declared this way is always unsafe — operation ② from §7, since the compiler cannot check that your declared signature actually matches the C side:

RUSTcalling libc's abs() from Rust
extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    unsafe {
        // SAFETY: abs() from the C standard library takes and returns a
        // plain i32 by value — no pointers, no lifetime, nothing to uphold
        // beyond "the C runtime is linked", which it always is.
        println!("Absolute value of -3 according to C: {}", abs(-3));
    }
}

The "C" string is the application binary interface (ABI) — it tells rustc which calling convention to generate call-site code for. On Windows, code calling the Win32 API should use extern "system" instead of extern "C", because that string resolves to whichever convention the platform's system libraries actually use (historically stdcall on 32-bit Windows, identical to "C" everywhere else) — getting this string wrong does not fail to compile; it silently generates a call that reads the wrong registers, which is exactly the kind of bug unsafe cannot protect you from.

(c) Calling Rust from C: #[no_mangle] pub extern "C" fn

The reverse direction needs two things: a fixed calling convention (extern "C" again, this time on the definition) and a fixed, unmangled symbol name, since C's linker has no idea what to do with Rust's default name-mangling scheme:

RUSTexposing a Rust function to C
#[no_mangle]
pub extern "C" fn rust_add(a: i32, b: i32) -> i32 {
    a + b
}
Cthe matching header a C caller would use
// rust_add.h — hand-written, or generated by cbindgen
int32_t rust_add(int32_t a, int32_t b);

Without #[no_mangle], rustc's default v0 mangling scheme (the legacy scheme before it, still seen in older binaries) folds the crate name, module path, and a compiler-chosen disambiguating hash into the symbol — something shaped like _ZN8my_crate8rust_add17h2b4b6c1f4a5e3d21E — unique enough to let two different crates each export a function called add without a linker collision, but useless to a C compiler that has no idea what that string means and was told to link against literally the name rust_add. #[no_mangle] switches that off for one symbol: what you write is exactly the name the linker sees, in exchange for giving up Rust's collision protection for that one name process-wide.

THE HAZARD SECTION 6 PROMISED: PANICS AT THE BOUNDARY

rust_add above can never panic (integer overflow aside, and that's a separate, checked-in-debug concern). A function that can panic — anything doing a slice index, an unwrap(), a division — must not be exposed to C directly: an unwinding panic that reaches the extern "C" boundary is undefined behavior, because C's stack has no unwind tables Rust's unwinder understands. The fix is std::panic::catch_unwind, wrapping the body and converting any panic into an error code before it ever reaches the boundary — a real, necessary line of ceremony that every FFI-exposing crate needs and naive tutorials frequently omit.

Struct layout at the boundary: why repr(C) exists

C has one struct layout rule: fields in declaration order, each aligned to its own size, with padding inserted to satisfy alignment. Rust's default layout (repr(Rust), what you get with no attribute) makes no such promise — the compiler is explicitly free to reorder fields to minimize padding, and does. That is a safe, transparent optimization for Rust-only structs and an active FFI bug the moment a C caller expects declaration order. Drag the toggle:

HARDWARE COROLLARY: #[repr(transparent)] AND bool

Two more real FFI-layout gotchas worth knowing. 1. A single-field wrapper struct like struct Meters(f64) is guaranteed layout-identical to its inner f64 only if marked #[repr(transparent)] — without it, repr(Rust) makes no such promise even for a single field. 2. Rust's bool is guaranteed to be exactly one byte with bit pattern 0x00 or 0x01 and is safe to pass to C's _Bool — but a raw pointer or FFI value that produces any other byte pattern and gets read as a Rust bool is instant undefined behavior, since the compiler is permitted to assume that byte is never anything else.

ARC 10 · PERFORMANCE & SAFETY CHARACTERISTICS

What actually costs time at an FFI boundary — and what doesn't

A persistent myth: "unsafe/FFI code is fast, safe wrappers are slow." Measure it honestly and the picture is sharper. The safe wrapper around an FFI call is, in the overwhelming majority of cases, free — it inlines away entirely, because it's just a null check and a type conversion around a call that happens either way. What actually costs time is marshalling: converting Rust's owned, GC-free types into the flat buffers and null-terminated strings C expects, which is real, unavoidable, and grows with payload size.

ARC 11 · REAL-WORLD INCIDENTS

When one of the five promises was broken: three real cases

Case study 1: RUSTSEC-2020-0071 — the time crate's segfault (CVE-2020-26235)

The time crate's pre-0.2.23 Tm::local()/at_utc() functions computed local time by calling into C's localtime_r. On Unix, glibc's localtime_r internally reads the TZ environment variable via getenv — and reading an environment variable concurrently with another thread calling setenv/putenv (which is exactly what Rust's std::env::set_var does under the hood) is a data race in the C library itself, with no lock protecting it. In a multithreaded Rust program, one thread calling time::at_utc while another called std::env::set_var could segfault, or worse, silently read a corrupted string — undefined behavior triggered not by a bug in the time crate's own logic, but by an unstated precondition of the C function it called across an FFI boundary: "do not call this concurrently with anything that mutates the environment." Nothing about that precondition is visible in localtime_r's C signature, and nothing in Rust's type system could have caught it — it is exactly operation ② from §7 (calling an unsafe function) with a violated, undocumented-in-the-type-system precondition.

The long tail of this one advisory is unusually visible: it is a direct reason std::env::set_var and std::env::remove_var were themselves changed to unsafe fn in the Rust 2024 edition timeframe — the standard library concluding, years later, that mutating global process environment state was never actually safe to expose as an ordinary safe function in a multithreaded program, full stop.

Case study 2: RUSTSEC-2018-0018 — smallvec's insert_many buffer overflow

The smallvec crate's insert_many method computed how much to grow its backing buffer using an iterator's declared size_hint(), then used that number to justify an unsafe ptr::copy that shifted existing elements out of the way. The bug: size_hint() is explicitly documented, by contract, as advisory only — an iterator is always allowed to yield more or fewer items than it hinted. A caller passing an iterator whose real length exceeded its hint (or one that panicked partway through) could cause insert_many to write past the buffer it had actually allocated: a textbook out-of-bounds write, reachable from perfectly ordinary safe-looking calling code. The fix, landed in smallvec 0.6.3, stopped trusting size_hint() as a hard bound. This is the canonical shape of an unsafe-soundness bug that has nothing to do with FFI: an internal unsafe block whose safety argument silently depended on a trait contract (Iterator::size_hint) that the trait itself does not actually guarantee.

Case study 3: the 2020 actix-web unsoundness episode

Across 2019–2020, an independent researcher filed a string of RustSec advisories against actix-web and its supporting crates for genuine unsafe-soundness bugs (memory-unsafety reachable from safe-looking public APIs). The maintainer initially dismissed several reports as non-issues; the resulting public dispute — and the fact that one of Rust's most widely deployed web frameworks had accumulated real, exploitable unsoundness in its unsafe internals — became the field's reference case for why "it's just a web framework, it barely uses unsafe" is not a safety argument. The advisories were eventually fixed and the maintenance team broadened; the episode is cited in nearly every serious discussion of unsafe-code review practice in the Rust community since.

THE COMMON THREAD

None of these three incidents involved a programmer writing unsafe and immediately doing something obviously wrong inside it. Each involved a safety argument that was locally plausible and globally wrong — trusting a C function's undocumented threading precondition, trusting a trait method's advisory-only contract, or simply auditing less carefully than the surface area demanded. That is precisely the cost §6 warned about: unsafe code is a proof obligation, and proof obligations fail exactly where the assumptions they rest on turn out to be false.

First: the shape every safe wrapper follows, simplified from Vec::push's real structure:

RUSTalloc/src/vec/mod.rs — Vec::push(), simplified but faithful
pub fn push(&mut self, value: T) {
    if self.len == self.buf.capacity() {
        self.buf.grow_one();           // may reallocate; RawVec's problem, not ours
    }
    unsafe {
        // SAFETY: grow_one() above guarantees capacity > len, so
        // this pointer offset is in-bounds of the allocation, and the
        // slot at `len` is uninitialized memory we are about to fill —
        // ptr::write (not a plain store) is required specifically
        // because writing through `*mut T` would try to drop whatever
        // "was already there," which is uninitialized garbage.
        let end = self.as_mut_ptr().add(self.len);
        std::ptr::write(end, value);
    }
    self.len += 1;   // only now does the safe world know this slot exists
}

Second: the safe boundary type that makes FFI string-passing not a minefield:

RUSTstd/src/ffi/c_str.rs — the shape of CString, used at nearly every string-passing FFI boundary
let path = std::ffi::CString::new("/etc/hosts")
    .expect("path contained an interior NUL byte");

extern "C" {
    fn open(path: *const std::os::raw::c_char, flags: i32) -> i32;
}

unsafe {
    // SAFETY: `path` outlives this call (it's a local binding still in
    // scope), as_ptr() returns a valid NUL-terminated pointer for exactly
    // as long as `path` is alive, and open()'s documented contract only
    // reads through that pointer — it does not retain it past the call.
    let fd = open(path.as_ptr(), 0);
}

CString::new returns an error rather than silently truncating if the input contains an embedded NUL byte — a real, load-bearing check, since C's open() would otherwise interpret only the bytes before that NUL, silently opening a different path than the one Rust thought it passed.

Third: what a real libc-style declaration file looks like — this is the actual shape hand- verified against POSIX headers by the libc crate's maintainers:

RUSTlibc crate — src/unix/mod.rs, representative excerpt
extern "C" {
    pub fn malloc(size: size_t) -> *mut c_void;
    pub fn free(p: *mut c_void);
    pub fn getpid() -> pid_t;
    pub fn write(fd: c_int, buf: *const c_void, count: size_t) -> ssize_t;
}

Every one of these is, structurally, exactly the naive example from §8(b) — a promise about a symbol's signature that the compiler cannot check, verified instead by the crate's maintainers against the actual C headers on every supported platform, and re-verified whenever a platform changes its ABI.

In "C calls Rust" mode, turn #[no_mangle] OFF and watch the exported symbol name change — that's the exact reason your C linker would fail with "undefined reference". 4. Compare the register assignment for an f64 parameter against an i32 parameter — floats and integers use entirely separate register files under the System V AMD64 ABI.

Chapter 17 complete

You can now name the exact five operations unsafe unlocks, explain why a raw pointer trades away aliasing and lifetime guarantees, write a real extern "C" declaration in both directions, and point to a real CVE caused by one of the five promises being broken. Chapter 18 turns to a completely different kind of code generation: macro_rules! and procedural macros write Rust code that writes more Rust code — and, as you'll see, a macro that expands into an unsafe block is quietly asking every one of its callers to trust an invariant they may never read, since the macro's expansion is usually invisible at the call site. Chapter 17's discipline of a visible, audited unsafe block gets a lot harder to enforce once the block can be generated by someone else's macro.
