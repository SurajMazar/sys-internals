AWS CERTIFICATION PREP · CHAPTER 02

IAM & Account Security Fundamentals

Design Secure Architectures is the single highest-weighted domain on either exam, and almost every question in it eventually reduces to one skill: read a stack of policies and predict, exactly, whether a request is allowed. This chapter builds that skill from the ground up — users vs groups vs roles, identity vs resource policies, the real evaluation order, and the STS mechanism that makes temporary, cross-account access possible without a single long-lived secret changing hands.

You will be able tochoose user, group, or role correctly for any principal described in a scenario, human or workload.
You will understandexactly how AWS evaluates a stack of identity-based, resource-based, and boundary policies into one decision.
You will predictthe Allow/Deny outcome of a request given an arbitrary combination of policy statements, on paper, before the exam does it for you.
You will simulatea real STS AssumeRole flow and a live policy evaluator that computes its verdict from whatever statements you toggle on.
ARC 01 · EXAM CONTEXT

The domain that quietly runs through every other domain

This chapter maps directly to Design Secure Architectures on the Solutions Architect Associate exam (SAA-C03) — at 30% of the exam, it is the single highest-weighted domain across all four Associate domains (Secure 30%, Resilient 26%, High-Performing 24%, Cost-Optimized 20%). On the Professional exam (SAP-C02) the same material resurfaces constantly inside Design Solutions for Organizational Complexity (26%) — cross-account access, multi-account identity, and permission delegation are essentially an IAM problem wearing an "organizational" hat.

IAM is disproportionately tested for a structural reason: almost nothing else in either exam's blueprint is "correct" if the identity design underneath it is wrong. A perfectly resilient multi-AZ architecture that runs on a root-user access key is not a passing answer. A cost-optimized Spot fleet whose instances carry AdministratorAccess is not a passing answer either. Every domain assumes the IAM layer is sound, which is exactly why this is chapter two and not chapter twelve.

IAM, MFA, and roles — a brief, hedged timelineCLICK A POINT

Exact dates here are hedged deliberately — the exam does not test IAM's release history. What it does test is the resulting shape of the service: users/groups/roles as a layer in front of the root account, and MFA as something that was retrofitted onto identities almost as early as IAM itself existed, which is your first signal about how seriously AWS — and the exam — takes it.

ARC 02 · THE COMMON WRONG INSTINCT

"One user, one key, AdministratorAccess, done"

Faced with "an application needs to talk to AWS," the instinct that feels fastest — and that the exam loves to dangle as a wrong-but-plausible option — looks like this: create one IAM user per application, generate a long-lived access key pair for it, and attach AdministratorAccess "to keep things simple and avoid permission errors later." The key gets dropped into a config file, an environment variable, or baked directly into an AMI so every instance launched from it is already authenticated. For a human operator doing something urgent, the equivalent shortcut is simpler still: just sign in as the root user and do the work directly, because root can obviously do anything.

None of this is exotic or careless-looking in the moment. It works on the first try, nothing throws an access-denied error, and the team moves on. That is precisely why it is the instinct the exam tests against — wrong answers on the real exam are rarely absurd; they are the thing that would actually ship in a rushed sprint.

ARC 03 · WHY IT'S WRONG

Every shortcut above is a standing liability, not a one-time risk

A long-lived IAM user access key is a secret with no built-in expiry and no automatic rotation. It sits in exactly the places secrets leak from in practice: committed into a git history, left in a plaintext config file, baked into an AMI that later gets shared or copied. Once it leaks, it is valid until someone notices and manually revokes it — there is no clock quietly working in your favor the way there is with STS temporary credentials.

AdministratorAccess compounds the exposure rather than mitigating it. It is the textbook violation of least privilege — granting an identity every permission it could ever conceivably need "just in case" — and it means that whichever leak happens first (the key in the git repo, the AMI someone forgot was public, the laptop that got compromised) is no longer a contained incident. It is a full account compromise, because the leaked credential can do anything the root user could do, short of a small set of root-only actions.

Using the root user for day-to-day work is its own category of risk: root cannot be restricted by any IAM policy, so there is no way to scope it down after the fact. The correct posture is the opposite of "use root because it can do anything" — lock the root credentials away, enable MFA on root specifically, and reserve root sign-in for the small number of actions that genuinely require it (this course treats the exact list as an evolving AWS detail rather than something to memorize verbatim; the exam fact worth knowing cold is simply that day-to-day operations should never run as root).

MECHANISM — WHY EC2 ROLE CREDENTIALS NEED PROTECTING TOO

Even a correctly-issued EC2 instance role isn't automatically safe from every attack. The instance metadata service is how an instance fetches its role's temporary credentials — and IMDSv1 answered plain, unauthenticated GET requests to that endpoint. That made it vulnerable to SSRF-class attacks: if application code on the instance could be tricked into making an outbound HTTP request to an attacker-influenced URL, and that URL pointed back at the metadata service, the attacker could exfiltrate the role's temporary credentials through the vulnerable app itself.

IMDSv2 closes this by requiring a session-oriented flow (an initial PUT to fetch a token, then GET requests that must present that token) that plain SSRF requests generally can't reproduce. AWS has moved newer EC2 instance types — broadly, ones launched since around mid-2024 — to IMDSv2-only by default. Treat that as the direction AWS has moved, not as a guarantee that every running instance you'll ever encounter, including older ones, is IMDSv2-only already.

ARC 06 · LIMITS, QUOTAS & EDGE CASES

The correct approach still has to respect real ceilings

Even a well-designed IAM setup runs into documented AWS default quotas — the exam likes to test whether you know a limit exists, not necessarily its exact current value (these are account-level defaults and can often be raised via AWS Support, and the exact figures below should be read as "documented AWS default quotas, subject to change or increase," not permanent constants):

  • Managed policies per user/group/role — up to 10 managed policies can be attached directly to a single principal by default.
  • Inline policy size — differs by entity type: inline policies on users and groups have a smaller character ceiling (a few kilobytes) than inline policies on roles, which get a larger allowance.
  • Managed policy document size — a customer-managed policy document tops out around 6,144 characters of the actual JSON policy text (whitespace-adjusted).
  • Access keys per user — an IAM user can have at most 2 active access keys at any one time (this cap is what makes zero-downtime key rotation possible: create key #2, roll it out, then deactivate key #1 — you're never blocked from having a second key while retiring the first).
  • Users / roles / groups per account — large-scale entity counts (users, roles, groups) default to limits in the thousands per account and are increasable via a support request; don't expect the exam to ask for an exact number here.
  • STS session duration — an assumed role's temporary credentials default to a 1-hour session unless the role's configured maximum session duration (itself settable from 1 to 12 hours) allows a longer session to be requested.
EDGE CASE THE EXAM LOVES — PERMISSIONS BOUNDARIES CAP THE ENTITY'S OWN POLICIES, NOT WHAT OTHERS CAN GRANT IT

A permissions boundary is a managed policy attached to a user or role that sets the maximum permissions that entity's own identity-based policies can grant it. It does not itself grant anything, and it does not restrict what a resource-based policy can grant that entity from the outside. In other words: if an S3 bucket policy independently grants a bounded role access, that grant is evaluated on its own terms — the boundary only limits what the role's own attached policies can hand it. Mixing this up is one of the most common professional-level trap answers.

ARC 11 · REAL-WORLD SCENARIO CASE STUDIES

Three original vignettes, in the exam's own phrasing style

Case 1 — the audit contractor. A financial-services company hires an outside audit firm for a two-week engagement. The auditors need read-only access to a single S3 bucket of financial reports that lives in the company's AWS account, and nothing else — not the console, not any other bucket, not any compute resource. The company doesn't want to create IAM users for four auditors it will never see again after the engagement ends, and it wants access to stop working automatically the moment the engagement is over. Correct approach: the auditors' own organization has them assume a cross-account IAM role in the company's account, created specifically for this engagement, scoped to s3:GetObject/ s3:ListBucket on exactly that bucket via its trust policy and an attached scoped identity policy. When the engagement ends, the company simply deletes the role — there is no standing user, no key to revoke, and no console access was ever granted.

Case 2 — the hardcoded Lambda keys. A retail company's order-processing Lambda function reads an IAM user's access key and secret key from an environment variable to call DynamoDB and SNS. A new engineer notices this during a security review and is told "it works, don't touch it." The access key belongs to a user with AdministratorAccess, created two years ago by someone who has since left the company, and nobody is sure whether it has ever been rotated. Correct approach: create a Lambda execution role scoped to exactly the DynamoDB table actions and SNS topic the function actually needs, attach it as the function's execution role, remove the environment-variable credentials entirely, and deactivate — then delete — the old IAM user's access key once the migration is confirmed working. The Lambda service itself now handles credential issuance and rotation automatically via STS.

Case 3 — single sign-on across fifty accounts. A fast-growing SaaS company has scaled from three AWS accounts to roughly fifty (one per environment per product line) and now has over 300 employees who need some level of AWS access. Managing fifty sets of IAM users, one set per account, has already caused duplicate/stale accounts and at least one incident where an offboarded employee's IAM user in a rarely- audited account was never deactivated. Correct approach: adopt IAM Identity Center as the single place employees authenticate, define permission sets that map job functions to permissions (e.g. "read-only billing viewer," "developer in non-production accounts"), and assign those permission sets to users/groups against the specific member accounts they need — one central identity, many scoped, temporary, centrally-revocable sessions, instead of fifty independent identity stores.

WHY THE EXAM CARES

Reading a stack of policy JSON and predicting whether a specific request is Allowed or Denied is directly and repeatedly tested — it's not a "nice to have" skill, it's arguably the single most common question shape in the Secure Architectures domain. The document above is exactly the pattern: a broad Allow, narrowed by an explicit Deny on a more specific resource pattern. If you can read that and know instantly that the Deny wins for anything under confidential/ while the Allow still holds everywhere else, you've internalized the core rule this chapter teaches.

ARC 16 · EXAM-DAY TAKEAWAYS

What to actually remember on test day

Five things carry more of this chapter's exam weight than everything else combined: an explicit Deny anywhere always wins, full stop, regardless of how many Allows exist elsewhere in the stack; absent any explicit Deny, an explicit Allow anywhere in an applicable identity-based or resource-based policy grants access; absent both, the default is implicit Deny. Roles, never long-lived keys, for workload identity — EC2 instance profiles, Lambda execution roles, ECS/EKS task roles are the only exam-correct answer for "how does my compute call AWS APIs." MFA and least privilege are the two most heavily tested security principles on both exams, and they show up constantly as the differentiator between a tempting wrong answer and the correct one. And remember the one true edge case worth memorizing: a permissions boundary caps what an identity's own policies can grant it — it never limits what a resource-based policy can grant that identity from the outside.
