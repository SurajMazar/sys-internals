ARC 01 · THE PROBLEM

The rules are not the text — they're what every node actually computes

Ask an engineer what Bitcoin's consensus rules are and you'll usually get an answer that starts with the whitepaper or the BIPs: the 21 million cap, the difficulty adjustment, the block size limit, the signature checks. All true, and all incomplete in a way that has cost real money nine times over. The actual rule that governs the network at any moment is not a document. It is whatever every economically relevant node, running whatever software it happens to be running, will independently compute and agree on — bugs, library quirks, resource limits, and all.

That gap between the specified protocol and the executing software is invisible until it isn't. In ordinary distributed systems, a bug in one node's implementation is a bug — you find it, you patch it, you redeploy, the fleet converges because you control the fleet. In Bitcoin there is no fleet operator. There are thousands of independently-operated nodes running a handful of different codebases (Bitcoin Core overwhelmingly, but also long-tail implementations), each one a sovereign arbiter of what it will accept as valid. When a bug in how a majority of that software validates transactions accidentally becomes the operative rule — because everyone's software agrees on the buggy behavior — the bug is the protocol until someone notices, and un-noticing it requires coordinating a rule change across every one of those sovereign parties without a company, a release manager, or a forced-upgrade mechanism to make it happen.

  • Validation code is consensus-critical in a way ordinary code is not. A bug in a web server's request parser is a bug. A bug in CheckTransaction() that lets an invalid transaction pass is, the moment enough hashpower and enough nodes build on top of it, the new rule — indistinguishable from an intentional protocol change until it's reverted.
  • You cannot force an upgrade. There is no central server pushing a patch to every client. A fix only takes effect on the fraction of the network that chooses, voluntarily and at its own pace, to run it.
  • Dependencies inherit consensus authority. Chapter 8 defined validity in terms of Bitcoin Core's logic; §2 of this chapter shows that logic was, for six hours in 2013, actually defined by an undocumented lock-table limit inside a database library nobody had audited for that purpose.
  • "Fixing" a rule and "changing" a rule can be the same act observed from different sides. A bug fix that makes previously-valid data invalid is, mechanically, identical to a soft fork — and needs the same coordination discipline chapter 10 built for deliberate rule changes.
WHY THIS CHAPTER IS THE SYNTHESIS, NOT AN APPENDIX

Every incident below is explainable only in terms of a mechanism you already have: the value-range checks from chapter 8's transaction validation, the UTXO model's assumption that an outpoint is spent at most once, the difference between a full node and an SPV client from chapters 9–10, and the four-actor tug-of-war — developers, miners, node operators, and the businesses that give bitcoin its economic meaning — that decides, with no single vote and no single leader, whether a proposed rule change actually becomes the rule. This chapter does not introduce a ninth mechanism. It stress-tests the eight you already have against real failures, at the byte level, with the actual numbers.

Consensus bug — the validation rule itself was wrong or absent, and different software versions could disagree about whether the same block is valid (1, 2, 4, 8 below). Policy dispute — every node agrees on what's valid; they disagree only on what they'll voluntarily relay or mine before it's confirmed (9 below, and the datacarrier debate in §11). Mixing these categories is the single most common analytical error in how the press — and postmortems written under pressure — describe what happened.

ARC 03 · NAIVE SOLUTION

Attempt #1: treat a consensus bug like any other production bug

Derive the response honestly, the way you'd derive it for any other system you operate. A critical bug is found in software you run. The standard, correct, battle-tested playbook for that situation is not mysterious — every engineer in this course has executed it:

pseudocodethe ordinary incident-response playbook — the strawman
function handleCriticalBug(bug) {
  const fix = developPatch(bug);           // write and test the fix
  codeReview(fix);                        // get it reviewed
  deployToProduction(fix);                // push it out — you control the fleet
  verifyRollout();                        // confirm 100% of instances run the fix
  publishAdvisory(bug, fix);              // tell users what happened, for trust
  return "incident closed";
}

Nothing here is wrong in general — it is, in fact, almost exactly what a well-run software company does every Patch Tuesday, and chapter 5's playbook will keep three of these five steps essentially intact. The naive model gets one thing devastatingly right and one thing catastrophically wrong. Right: developPatch and codeReview transfer unchanged — writing a correct fix and getting a second pair of eyes on it is universal engineering practice, consensus system or not. Wrong: deployToProduction and verifyRollout assume something that is true of literally every other system in this course and false of this one — that you control the fleet. You don't. You can publish a patch. Whether it runs anywhere is a decision made independently, at their own pace, by every node operator and every mining pool on Earth, none of whom report to you, none of whom are contractually obligated to upgrade, and some fraction of whom will still be running the vulnerable version five years later.

ARC 04 · WHY IT FAILS

"Verify the rollout" is not a step you get to perform

Quantify the gap. In a company you operate, "verify 100% of instances run the fix" might take minutes (a fleet restart) to days (a staged rollout with canaries). In Bitcoin, upgrade adoption follows a voluntary diffusion curve — node operators upgrade when they notice, when their distro packages a new version, when a peer nags them, or never. Historically, a meaningful fraction of reachable nodes on the network run software that is months to years out of date at any given time, and some fraction of hashpower has, in every past contentious upgrade, been slower to move than the median node.

This matters differently depending on what kind of fix you're shipping, and the distinction is the spine of this entire chapter:

  • A pure bug fix that only tightens validity (chapter 10's soft fork shape: previously-valid blocks stay valid, some previously-valid blocks become invalid) can, in principle, be adopted gradually — unupgraded nodes still agree with upgraded nodes about everything except the narrow new case, and as long as a hashpower majority enforces the tightened rule, the chain that violates it gets orphaned. This is exactly the shape of the CVE-2018-17144 fix in §8.
  • A fix that requires loosening validity (chapter 10's hard fork shape) has no such grace period: a node running the old rules will reject blocks the new rules accept, and if hashpower splits, the chain splits — not metaphorically, two permanently divergent ledgers, as BIP50 and, later, the 2017 Bitcoin Cash split both demonstrate.
  • A fix nobody has fully adopted yet is not "fixed." Every day between disclosure and majority adoption is a day the exploitable behavior is still, functionally, part of the live rule set for anyone who hasn't upgraded — which is precisely why responsible disclosure (§5) treats the adoption curve, not the patch release, as the actual finish line.

THE NUMBER THAT MATTERS ISN'T "PATCHED" — IT'S "ENFORCED"

A tightened rule is only load-bearing once the hashpower majority enforces it, because that's what determines which chain accumulates the most proof-of-work — chapter 8's Nakamoto-consensus tie-breaker. A rule with 30% of nodes patched but 60% of hashpower still mining the old way is not "30% fixed." It is unfixed, full stop, because the unpatched majority's chain is the one that wins ties. This is exactly why §5's playbook obsesses over quietly reaching miners and major infrastructure operators before talking to the wider public — node count is a vanity metric next to hashpower share and economic-node share.

ARC 05 · THE PLAYBOOK THAT EMERGED

Responsible disclosure, re-derived for a network with no owner

Across the incidents in this chapter — most explicitly codified after CVE-2018-17144 — Bitcoin Core's security process converged on a sequence that keeps the two survivable steps from §3's naive playbook (developPatch, codeReview) and replaces the two that assumed a controllable fleet with something that respects §4's diffusion problem: fix in silence, disclose in stages, measure adoption before you measure "done."

THE PRINCIPLE UNDERNEATH EVERY STEP

Silence is not dishonesty here — it is the only tool available for solving §4's diffusion problem before an adversary can exploit the gap. A public CVE the instant a fix exists tells every attacker on Earth about a vulnerability that 95% of hashpower hasn't patched against yet. The entire playbook is an exercise in getting the people who can actually enforce a rule (miners, major exchanges, infrastructure operators) to a safe adoption threshold before the people who might exploit it learn there's anything to exploit.

ARC 06 · WHAT THE PLAYBOOK COSTS

The bill for silence: opacity, bottlenecks, and no formal spec to check against

The playbook in §5 is the correct answer to §4's problem, and it is not free. Every cost below is a direct, physical consequence of trading transparency for coordinated safety — not an oversight anyone could tune away:

  • Pre-disclosure privilege is itself a centralization risk. Deciding who gets early warning — which mining pools, which exchanges, which infrastructure operators — is a judgment call made by a small group of maintainers with commit access to the reference implementation. That group did not run for election and cannot be voted out; their trustworthiness is the load-bearing assumption underneath the entire disclosure process, exactly the kind of informal, personality-dependent authority a "trustless" system is supposed to avoid needing.
  • There is no formal specification to check a fix against. Bitcoin's consensus rules are defined operationally — by what the reference implementation does — not by a machine-checkable formal spec. Every alternative implementation (a different node, a different mining pool's software) has to reverse-engineer the fix's exact edge-case behavior from source and hope they matched it, which is precisely the kind of gap that produced §8's incident 2.
  • Vague changelogs are a real cost, paid by defenders too. Shipping a fix as "various minor improvements" to avoid tipping off attackers also denies defenders — exchanges' security teams, alternative client maintainers, researchers — the information they'd need to independently verify the fix is complete or to detect in-the-wild exploitation before public disclosure.
  • The bottleneck doesn't scale. A handful of people capable of triaging a consensus-critical bug correctly, under time pressure, with the judgment to know who needs to hear about it and in what order, is a bus-factor problem that has not meaningfully improved since 2010 — it has just become a more explicitly acknowledged one.
THE HONEST TRADE, STATED PLAINLY

A fully public, fully transparent disclosure process is the correct default for almost all software, and Bitcoin Core deliberately does not use it for consensus-critical bugs, because the cost of an opportunistic attacker learning about an unpatched inflation bug before the network reaches a safe adoption threshold is categorically worse than the cost of a temporarily opaque process. Both costs are real. The playbook picked the smaller one, and every incident in §8 and §11 is, among other things, a test of whether that judgment call was made correctly in that specific instance.

ARC 08 · INTERNAL IMPLEMENTATION

Four bugs, traced to the byte and the block

These are the four incidents where the software itself disagreed with itself — the purest form of "the rules are not the text." Each one maps directly onto a mechanism from chapters 8–10: transaction value validation, the database backing chain state, the assumption that an outpoint is spent once per transaction, and the difference between validating a block and merely trusting its header.

(a) August 2010 — the value overflow, CVE-2010-5139, block 74638

Chapter 8 established the invariant that makes Bitcoin scarce at all: a transaction is valid only if the sum of its output values does not exceed the sum of its input values, with the difference collected as a miner fee. On 15 August 2010, a transaction with two outputs of roughly 92.2 billion BTC each — a combined total just over 184 billion BTC, nearly nine thousand times the entire 21 million cap — passed that check and was mined into block 74638. For about eight hours, before the chain was manually reorganized past it, that supply genuinely existed as far as any node running the vulnerable software was concerned.

The mechanism is a straightforward, almost quaint integer overflow. Output values (CAmount) were stored as signed 64-bit integers. The reference client's per-output validation at the time checked that no single output's value was negative, but the code path that mattered here — the accumulation of the total output value across a transaction, and the comparison of that total against the sum of inputs — had no upper bound at all: no per-output ceiling, and no check that the accumulated sum stayed inside the representable range of a signed 64-bit integer. The two crafted output values individually fit inside a positive int64_t. Summed together, they overflowed it. Two's-complement arithmetic doesn't raise an exception on that overflow — it wraps silently, and the attacker chose the two values so the wrapped sum landed just under zero. A negative "total output value" trivially satisfies "outputs ≤ inputs" against almost any input total, so the transaction sailed through every check that existed at the time.

(b) March 2013 — the BIP50 chain fork: your consensus rules include your dependencies' bugs

  
Bitcoin 0.8 switched the chainstate database backend from BerkeleyDB (BDB) to LevelDB. On 11 March 2013, at
  block height 225,430, a mining pool produced a block containing a transaction with an unusually large number
  of inputs. Nodes running 0.8 (LevelDB) accepted it without incident. Nodes running 0.7 and earlier (BDB)
  rejected it — not because the block violated any documented Bitcoin rule, but because processing it required
  more concurrent database locks than BerkeleyDB's compiled-in set_lk_max_locks ceiling (10,000 in
  the default build Bitcoin Core shipped) permitted. BDB's lock manager returned an error; the 0.7 code path
  treated that as "this block is invalid"; and for about six hours the network ran two genuinely divergent
  chains — one that accepted the large block and kept extending it, one that rejected it and mined around it.

  
Model the lock accounting yourself — this is a simplified estimate, not BerkeleyDB's literal lock-table
  bookkeeping, but it reproduces the qualitative result: past a certain input/output count, 0.7's database layer
  refuses a block that 0.8's does not, and neither refusal has anything to do with a Bitcoin consensus rule as
  anyone had written it down.

    Resolution required active, real-time coordination: core developers and major mining pools communicated
    directly (largely over IRC) and the pools with the most hashpower agreed to downgrade back to
    0.7-compatible mining — deliberately choosing the older, more limited chain over the newer, more capable one
    — purely because reconverging on whichever chain the rest of the economically relevant network already
    trusted mattered more than which chain was "better." BIP50 documents the incident and the fix: chainstate
    moved fully to LevelDB, and the episode became the canonical argument for treating storage-layer resource
    limits as consensus-relevant surface area requiring the same scrutiny as the validation code itself.

  




  
(c) September 2018 — CVE-2018-17144: a check that was there, then wasn't, then was again

  
Chapter 8's UTXO model rests on a quiet assumption you may not have noticed you were relying on: within a
  single transaction, the same previous output cannot be referenced twice as an input. A transaction that spends
  UTXO X and then, later in its own input list, spends UTXO X again is not "spending twice" in the
  double-spend sense chapter 8 defends against across transactions — it's a malformed transaction that shouldn't
  parse as sane at all. A duplicate-input check enforcing exactly this had existed in Bitcoin's validation code
  for years. During a large refactor of block-connection logic landed in Bitcoin Core 0.14 (released March 2017),
  that check was inadvertently dropped — consolidated away as part of restructuring how inputs were iterated,
  with nothing in the new code path re-asserting the invariant. It went unnoticed, in fully public, widely
  reviewed open-source code, for roughly eighteen months, until an anonymous report reached Bitcoin Core
  developers in September 2018.

  
The visible symptom was a denial-of-service: a specially constructed transaction referencing the same
  outpoint twice would cause a node connecting the block to attempt to mark that outpoint spent a second time,
  tripping an internal consistency assertion and crashing the process — reliably, remotely, against any
  vulnerable node that received the block. That alone was serious enough to fix immediately. What made it
  alarming enough to handle under the full weight of §5's disclosure discipline was the second, quieter variant:
  because the same input could be referenced twice, a transaction could be built so that its value is
  credited toward covering its outputs twice while the underlying UTXO is only actually debited
  once — the exact value-accounting failure from incident (a), reachable through a completely different door.
  Done correctly, that shape does not just crash a node. It creates spendable value that was never backed by a
  real, single-spent input — an inflation bug, in code every full node on the network was already running.

WHY THIS ONE WAS HANDLED DIFFERENTLY FROM A NORMAL CVE

    
The crash (DoS) half of the bug was disclosed and patched quickly, framed publicly as "a bug that could
    crash nodes" — true, and urgent, but also a description precise enough to protect users without handing
    an attacker a roadmap to the far more dangerous inflation variant. The inflation-capable half of the same
    root cause was described in detail only after enough of the network had upgraded to the fixed release
    (0.16.3) that the exploit window had meaningfully closed. This is §5's playbook executed under real
    pressure: two disclosures of different completeness, timed to the adoption curve rather than to a fixed
    calendar date, because the honest severity of "this bug can print money" would have been actively dangerous
    to state plainly on day one.

  


  
(d) July 2015 — the SPV-mining fork: mining without validating, priced in blocks

  
Chapter 9 distinguished a full node, which downloads and validates every rule against every block, from an
  SPV (simplified payment verification) client, which trusts that the chain with the most cumulative
  proof-of-work is valid and checks only that its own transactions are included via a Merkle proof. That
  distinction is supposed to be a client-side tradeoff — SPV wallets accept a small trust assumption in exchange
  for not downloading the whole chain. In July 2015 it became a mining-side shortcut instead, with much larger
  consequences.

  
BIP66 (strict DER signature encoding) activated as a soft fork around block height 363,725 once it crossed
  the 95% miner-signaling threshold defined by the pre-BIP9 rolling-majority mechanism from chapter 10. Once
  active, any block containing a transaction with a non-strict-DER signature became invalid under the new rule.
  Shortly after activation, a large mining pool produced exactly such a block — invalid under BIP66, valid under
  the old rules. Full validating nodes rejected it immediately. But a meaningful share of hashpower was running
  SPV mining (sometimes called "mining on faith"): rather than waiting the extra seconds it takes to fully
  download and validate a new block before starting work on the next one, these miners began hashing on top of
  the header of the latest block they'd heard about, trusting its proof-of-work as a proxy for its
  validity, purely to shave a competitive sliver off their average time-to-next-block. They kept doing this for
  six blocks, extending an invalid chain nobody among them had actually validated.

Once enough full nodes and correctly-validating miners kept building the honest, BIP66-compliant chain, it
  overtook the invalid branch in cumulative work within hours, and the six invalid blocks — along with any
  transaction whose only confirmations lived there — were orphaned. Anyone who treated an SPV wallet's "6
  confirmations" as final during that window learned, the hard way, that a confirmation count is only as
  trustworthy as the validation performed by whoever produced it.

  

    
AN ECONOMICALLY RATIONAL SHORTCUT WITH A SYSTEMIC PRICE TAG

    
No miner in this incident was malicious. SPV mining is a straightforward, individually rational
    optimization: full validation takes measurable time, and in a game where the first miner to extend the tip
    captures the block reward, shaving that time off is worth real money to whoever does it — right up until the
    tip they extended turns out to be invalid, at which point the entire shortcut's savings are wiped out by
    however many blocks get orphaned. This is chapter 9's proof-of-work race and chapter 10's fork-resolution
    rule colliding with an incentive that individually makes sense and collectively degrades the network's
    validation guarantees. The practical fix was social and operational, not protocol-level: major pools reduced
    or eliminated pure SPV mining, typically adding at minimum a check that a new tip doesn't violate a small set
    of cheaply-checkable recent soft-fork rules before building on it — trading back some of the speed advantage
    for a bound on how badly a shortcut can fail.

ARC 10 · SECURITY CHARACTERISTICS

  
Racing the honest chain: the math behind "how many blocks is safe"

  
Both the March 2013 fork and the July 2015 SPV-mining fork were, mechanically, a race between two competing
  chains for cumulative proof-of-work — exactly the race Satoshi analyzes in §11 of the whitepaper for
  double-spend safety. The same math tells you how likely a minority branch was ever to catch up, which is
  precisely the question every node operator watching either fork in real time was actually asking.

  
Treat it as a classical gambler's ruin: a chain controlling a fraction q of hashpower is
  z blocks behind an honest chain controlling p = 1 − q. In the simplified,
  confirmation-style version of this race (each side finds blocks as a memoryless Poisson competition), the
  probability the minority chain ever closes a z-block gap is (q / p)^z — the
  same shape chapter 8 used for double-spend confirmation depth, applied here to an accidental fork instead of a
  deliberate attack. Drag both sliders; the chart plots catch-up probability against blocks-behind for the
  hashpower share you choose, with the actual depths from March 2013 (roughly 24 blocks before full
  reconvergence) and July 2015 (6 blocks) marked for reference.

WHY BOTH REAL FORKS RESOLVED WITHIN HOURS, NOT DAYS

    
In both 2013 and 2015, the "minority" branch was never close to a genuine 50/50 hashpower split — the
    vast majority of hashpower and every fully-validating node was, from the moment of divergence, already
    enforcing the correct rule (BDB-compatible in 2013, BIP66-compliant in 2015). At q much below
    50%, (q/p)^z collapses toward zero within single-digit blocks, which is exactly why both
    incidents resolved in hours rather than requiring the kind of sustained, deliberate, roughly-even split that
    §11's block size war eventually produced as a permanent chain divergence — that split held because it
    reflected a genuine, sustained disagreement about the rule itself, not a transient database error or a
    validation shortcut.

  







  
ARC 11 · REAL-WORLD INCIDENTS

  
The record's other half: a war with no bug, and four more worth knowing


  
Postmortem: the block size war, 2015–2017 — a governance failure, not a bug

  
No code disagreed with any other code at the start of this one. Every implementation validated blocks
  correctly against the rules it was built to enforce. The disagreement was entirely about what the rule
  should be, and it consumed roughly two years of the project's attention because — per §7 — no actor had
  the unilateral authority to settle it.

  
The technical argument for larger blocks, stated fairly: the 1 MB block size limit (itself an
  anti-spam constant Satoshi added in 2010, not an original design parameter) caps on-chain transaction
  throughput at a level that, as adoption grew, produced a persistent backlog and rising fees — pricing ordinary
  users out of the base layer for a currency whose stated purpose was peer-to-peer electronic cash. Bandwidth
  and storage had grown enormously since 2010 by Moore's-law-adjacent trends; raising the cap, proponents argued,
  simply let the protocol use capacity that already existed. Bitcoin XT (BIP101, 2015, Mike Hearn and Gavin
  Andresen) proposed scheduled doubling toward 8 MB; Bitcoin Classic proposed a flat 2 MB; Bitcoin
  Unlimited proposed removing a hard-coded cap entirely in favor of miner-configured "emergent consensus."

  
The technical argument for keeping blocks small, stated fairly: chapter 9 established that a full
  node's ability to independently validate every rule — the entire security model — depends on running a full
  node being affordable in bandwidth, storage, and initial-sync time. Raising the block size raises all three,
  pushing full validation toward fewer, larger, better-resourced operators and weakening the "anyone can verify"
  property that gives the other guarantees their teeth. Larger blocks, before efficient relay protocols existed,
  also propagate more slowly across the peer-to-peer network, which chapter 11's propagation-delay analysis ties
  directly to higher orphan rates for anyone not extremely well-connected — a centralizing pressure on mining,
  layered on top of the centralizing pressure on validation. The alternative offered was two-layered: Segregated
  Witness (SegWit), which fixes the transaction-malleability bug blocking reliable off-chain payment channels
  and delivers an effective capacity increase (a 4-million weight-unit limit, roughly 1.7–4× the old
  cap depending on transaction mix) — deployable as a soft fork, meaning it does not require every node to
  upgrade in lockstep to avoid a split — plus the Lightning Network (chapter 14) to move volume off-chain
  entirely without raising every full node's validation cost.

  
Both arguments were, and remain, technically legitimate engineering positions with real costs on each side;
  what turned this into a war rather than a debate was that the disagreement fractured along social and
  political lines faster than it converged technically. Bitcoin XT nodes were hit with sustained denial-of-service
  attacks not long after launch — widely attributed to opponents of the proposal, never definitively attributed
  to anyone — and the proposal lost momentum amid the pressure. On the other side, moderation of the primary
  r/bitcoin discussion forum removed large-block advocacy and criticism of Bitcoin Core with a heavy hand
  extensive enough that a large fraction of the big-block community split off to a separate forum (r/btc) in
  late 2015, each side afterward experiencing the other's space as an echo chamber rather than a discussion.
  Bitcoin Unlimited, the most aggressive big-block client, suffered a remotely triggerable crash bug in March
  2017 that was actively exploited against a meaningful share of its running nodes — a concrete embarrassment
  that damaged confidence in the alternative-implementation approach generally, independent of the underlying
  block-size argument's merits.

  
In May 2017, a coalition of businesses and mining pools representing a large majority of hashpower signed
  the New York Agreement (NYA): activate SegWit, then follow with a coordinated 2 MB hard fork
  ("SegWit2x"). Much of the Core-aligned developer and node-operator community saw this as an attempt to settle
  a protocol rule change through corporate and mining-pool agreement, bypassing the open developer process
  entirely — and, per §7, exactly the kind of unilateral move that three-out-of-four actors agreeing cannot
  actually force through. The response was BIP148, a User-Activated Soft Fork (UASF): a grassroots commitment,
  organized among node operators and businesses with no mining hardware at all, to have their nodes reject any
  block from 1 August 2017 onward that did not signal SegWit support — regardless of whether miners had reached
  the normal signaling threshold. This directly tested §7's claim that economic nodes hold real power over
  miners: a miner's block is worthless if the economically relevant nodes won't accept it, so the credible threat
  of BIP148 enforcement pushed miners to actually activate SegWit (via the faster BIP91 mechanism) ahead of the
  flag day, avoiding the chain split UASF was explicitly willing to cause. SegWit locked in and activated in
  August 2017. The 2 MB hard-fork half of the NYA deal — SegWit2x — collapsed in November 2017 for lack of
  suffient community support once businesses recognized that forcing it through without broader consensus would
  itself be the kind of contentious, potentially chain-splitting move the whole affair had been fighting over.
  Separately, a coalition of big-block proponents who wanted neither SegWit's design nor Core's roadmap executed
  their own hard fork on 1 August 2017, creating Bitcoin Cash (BCH) as a fully independent chain and asset with
  an 8 MB block size.

  

    
THE ACTUAL LESSON — HOW RULES CHANGE WHEN THERE IS NO LEADER

    
Nobody won a vote, because there was no vote to win. What happened is that four actors with different,
    partially overlapping interests — developers who controlled the reference implementation but not its
    adoption, miners who controlled block production but needed their blocks accepted to earn anything, node
    operators who controlled what "accepted" meant but had no direct say over what miners chose to mine, and
    businesses/exchanges whose valuation of each candidate chain ultimately decided which one was "real" bitcoin
    — pushed against each other for two years until the configuration that satisfied enough of all four
    simultaneously (SegWit, activated via the UASF threat, without the contentious hard fork) became the one
    that stuck, and the configuration that couldn't gather all four (a 2 MB hard fork with insufficient
    node-operator and developer buy-in) simply failed to happen even after major businesses had signed an
    agreement promising it. Bitcoin Cash proves the release valve was real: when a faction cannot get the base
    chain to adopt its preferred rules, it can fork off with a new chain and let the market decide which one
    accumulates economic value — which is a genuine resolution mechanism, just not the one anyone entered the
    debate hoping to reach. Whether the block-size-war outcome was the objectively correct engineering call
    remains genuinely disputed within the community to this day; what's not disputed is the governance mechanism
    that produced it — and that same mechanism, not a vote or an authority, is what will resolve the next
    contentious change too.

  




  
Briefly: the 2010 opcode disabling

  
In the same emergency window as the value-overflow fix, Satoshi disabled a large set of Script opcodes —
  among them OP_CAT, OP_SUBSTR, OP_LSHIFT, OP_RSHIFT,
  OP_MUL, OP_DIV, OP_MOD, and several bitwise/string operators — leaving
  them present in the opcode table but making the interpreter immediately fail any script that referenced them.
  This was defensive engineering triggered by the same audit that found the overflow bug: several of these
  opcodes had implementations that could exhaust resources or behave in non-obviously-bounded ways, and with
  Script deliberately not Turing-complete (chapter 6), removing operators nobody could yet prove safe was judged
  a smaller cost than leaving a second value-overflow-shaped bug undiscovered in the interpreter. OP_RETURN
  has a separate, later history worth not confusing with this one: it was added in 2014 specifically to give
  operators a way to embed a small, bounded, provably-unspendable data payload without abusing other opcodes or
  bloating the UTXO set — the deliberate, sanctioned answer to "where should arbitrary data go," which §11.4
  below revisits from a very different angle in 2023–24.


  
Briefly: the 2013 Android SecureRandom key theft

  
In August 2013, a flaw in Android's SecureRandom pseudorandom number generator — insufficient
  entropy seeding on affected builds — caused several popular Android Bitcoin wallets to occasionally generate
  ECDSA signatures reusing the same secret nonce k across different signed transactions. ECDSA is
  fatally fragile against exactly this: two signatures sharing a nonce (visible on-chain as two signatures
  sharing the same r value) let anyone solve directly for the private key with a few lines of
  modular arithmetic — no cryptographic breakthrough required, just algebra. Researchers and attackers alike
  scanned the blockchain for duplicate-r signatures, and vulnerable wallets lost funds within days
  of the flaw becoming known. Google patched SecureRandom's seeding; wallet vendors shipped
  emergency updates and told users to sweep funds to freshly generated addresses. The durable lesson —
  deterministic nonce generation (RFC 6979) removes the entropy dependency entirely, and Schnorr signatures
  (chapter 13's Taproot) go further by making nonce derivation part of the signature scheme's design rather than
  an implementation detail every wallet has to get right independently — is a direct architectural response to
  this exact failure mode.


  
Briefly: the 2011 MtGox flash crash — not a protocol incident at all

  
On 19 June 2011, MtGox — then handling the large majority of BTC trading volume — was compromised through a
  hacked account with trading privileges, which was used to place a massive sell order that drove the exchange's
  quoted price from around $17 to $0.01 in minutes before trading was halted and the incident reversed. This is
  included deliberately, and briefly, because it is the cleanest illustration of the taxonomy from §2: the
  Bitcoin network's consensus rules, block validation, and ledger were completely unaffected throughout. Nothing
  about this event involved a bug in the protocol, a validation failure, or a fork of any kind — it was a
  centralized service's internal database and access controls being breached, exactly the kind of incident that
  could happen to any exchange trading any asset. Financial press coverage at the time, and often since, described
  it simply as "Bitcoin crashes," which is precisely the category error this chapter's taxonomy exists to
  prevent you from making.


  
Briefly: Ordinals, Runes, and the 2023–24 fee events — a policy-versus-consensus case study

  
Starting in early 2023, the Ordinals protocol popularized embedding arbitrary data — images, text, and
  later fungible-token-like metadata via the Runes protocol launched at the April 2024 halving — inside the
  witness portion of Taproot transactions, using an "envelope" of unexecuted OP_FALSE OP_IF … OP_ENDIF
  script that a node must still fully download and verify even though the branch never executes. Because
  witness bytes have long received a discount under SegWit's weight accounting (chapter 14), this let large data
  payloads ride at a lower effective cost than the same bytes would carry outside the witness. Nothing about
  this violates a single consensus rule: the script is valid, the fee paid is real, and the block fits within
  the weight limit chapter 8 defines — this is entirely a story about policy, not consensus. Bitcoin
  Core's mempool relay policy has long included a default cap on OP_RETURN output size specifically
  to discourage using the chain as generic data storage, but that cap targets one narrow encoding; hiding data
  in unexecuted witness script sidesteps it completely, because from a policy filter's perspective the
  transaction looks like an ordinary, if witness-heavy, payment. The resulting fee spikes — sustained periods of
  materially elevated average fees through 2023 and intensifying around the Runes launch — reignited a
  still-unsettled debate inside the Bitcoin Core project over whether tightening mempool policy can meaningfully
  discourage a use of block space the consensus rules already permit, or whether policy-layer filtering just
  pushes the same economic demand into a less efficient, harder-to-filter encoding, wasting more block space per
  byte of payload without changing the underlying incentive at all. Bitcoin Core 28 (2024) moved toward the
  latter view, relaxing several long-standing datacarrier-related policy defaults on the reasoning that consensus,
  not policy, is the only enforcement layer that actually binds — a judgment call that remains genuinely
  contested within the community as this chapter is written, and is presented here as unresolved because it is.

  

    
CONSENSUS vs. POLICY, STATED ONE MORE TIME BECAUSE IT KEEPS MATTERING

    
Consensus rules are what every node must agree on to stay on the same chain — changing them is a
    fork, coordinated exactly as chapters 10 and this one describe. Policy is what an individual node
    chooses to relay or mine before confirmation — purely local, purely advisory, trivially overridden by
    running different software or a direct connection to a miner, and enforceable on precisely nobody. The
    Ordinals fee episode is what happens when a social preference about "legitimate" block usage is expressed
    only at the policy layer: it can shape behavior at the margin, but it cannot bind, because the actual rule —
    the one that matters — was never at stake.

First, the type and the bound that incident (a) taught the project to make explicit. Simplified but faithful
  to the shape of the real header:


  

    
C++consensus/amount.h — CAmount, MAX_MONEY, MoneyRange()

    
typedef int64_t CAmount;

/* 21,000,000 BTC × 100,000,000 satoshis/BTC — the entire supply cap,
 * expressed as the largest value ANY single field is ever allowed
 * to hold. Before August 2010 nothing enforced this on output
 * values or their running sum — only individual negativity was
 * checked, which a signed 64-bit overflow can trivially fake.    */
static const CAmount COIN      = 100000000;
static const CAmount MAX_MONEY = 21000000 * COIN;

inline bool MoneyRange(const CAmount& nValue)
{
    /* Both bounds matter. ">= 0" alone is exactly what the pre-fix
     * code effectively relied on — and exactly what a wrapped
     * int64 sum can satisfy while still being catastrophically
     * wrong. The upper bound is what actually closes incident (a). */
    return (nValue >= 0 && nValue <= MAX_MONEY);
}

  


  
Second, the check that closes incident (a) at the point it must run — on every individual output and
  on the accumulated total, so a wrap can't hide behind either check alone:


  

    
C++consensus/tx_verify.cpp — CheckTransaction(), the value-range half

    
bool CheckTransaction(const CTransaction& tx, TxValidationState& state)
{
    CAmount nValueOut = 0;
    for (const auto& txout : tx.vout) {
        if (!MoneyRange(txout.nValue))
            return state.Invalid("bad-txns-vout-toolarge");   // catches a single huge output

        nValueOut += txout.nValue;
        if (!MoneyRange(nValueOut))
            return state.Invalid("bad-txns-txouttotal-toolarge"); // catches the ACCUMULATED sum,
                                                                     // which is where the 2010 wrap
                                                                     // actually happened — two individually
                                                                     // in-range values summing out of range
    }
    /* … duplicate-input check lives here too; see below. */
    return true;
}

  


  
Third, the check that vanished during the 0.14 refactor and was restored for CVE-2018-17144 — placed early,
  before any input is touched, so the invariant "each outpoint is spent at most once per transaction" is
  structural rather than incidental:


  

    
C++consensus/tx_verify.cpp — CheckTransaction(), the duplicate-input half

    
/* Restored in 0.16.3. Present since early Bitcoin Core, silently
 * dropped when block-connection input iteration was consolidated
 * during the 0.14 refactor (~March 2017), rediscovered by an
 * external report in September 2018 — roughly 18 months later,
 * in code every full node was already running.                  */
std::set<COutPoint> vInOutPoints;
for (const auto& txin : tx.vin) {
    if (!vInOutPoints.insert(txin.prevout).second)
        return state.Invalid("bad-txns-inputs-duplicate");
    /* Without this: a coin gets CREDITED once per reference but
     * DEBITED from the UTXO set only once — the DoS variant hits
     * an assertion on the second removal; the inflation variant
     * lets the transaction's apparent input value exceed what was
     * actually, once, spent.                                     */
}

  


  

    
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

    
1. Cheap, structural checks run before expensive ones. Both fixes are O(n) scans over inputs or
    outputs that run before signature verification, which is orders of magnitude more expensive per input — reject
    the malformed transaction on the cheapest possible check first. 2. Both fixes are tightenings, not
    loosenings. Every transaction valid after either fix was already intended to be invalid before it — which
    is exactly chapter 10's soft-fork shape, and is why neither fix needed a hard fork's all-or-nothing upgrade
    discipline, even though the 2010 fix, deployed before any formal activation mechanism existed, still required
    real-time human coordination to get miners building on the corrected chain. 3. Regression tests exist
    specifically because a fix, once, is not a fix forever. The 0.14 refactor did not remove the duplicate-input
    check out of ignorance — it removed a check that had no accompanying test making its absence loudly,
    immediately visible. Every incident in this chapter that involves Bitcoin Core's own code left behind not
    just a patch but a permanent, CI-enforced test asserting the specific invariant that broke — the actual
    lesson operationalized, not just documented.
