CONTAINER INTERNALS · CHAPTER 08

Seccomp & LSMs:
Filtering the Syscall Surface

Chapter 7 split root into forty bits and dropped twenty-six of them by default. This chapter asks the question that split doesn't answer: of the roughly 450 syscalls a Linux process can attempt, exactly which ones is a container even allowed to try, independent of which capabilities or file permissions it holds — and who else, besides the kernel's own permission checks, gets a vote on whether a given operation proceeds? The answers are seccomp-bpf, a kernel-enforced allow/deny filter evaluated before a syscall's own logic ever runs, and two mandatory access control systems — AppArmor and SELinux — layered on top of everything DAC and capabilities already decided.

You will be able toRead a process's Seccomp: field in /proc/pid/status and its LSM label in /proc/pid/attr/current, and explain exactly what each governs.
You will understandWhy a syscall can return EPERM for three structurally different reasons — DAC, a missing capability, or a seccomp filter — before a single line of the syscall's own code runs.
You will predictWhich layer blocks a given container command: mount, keyctl, and ptrace each fail for a different reason, and you'll be able to say which before testing it.
You will simulateLoading Docker's and Podman's default seccomp profile against a bank of real syscalls, and toggling AppArmor/SELinux enforcement to see mandatory access control deny what discretionary checks would allow.
ARC 01 · THE PROBLEM

Capabilities answer "is this bit set?" — not "should this syscall exist here at all?"

Give a container process Docker's or Podman's default fourteen capabilities and drop the rest, per chapter 7, and you have solved a real problem: that process can no longer mount() a filesystem, load a kernel module, or reboot the host, because the kernel's capable() check for each of those operations returns false. But capabilities are a permission system layered onto specific privileged operations that some kernel developer, at some point, remembered to gate behind a capability check. Not every syscall works that way. A large fraction of the roughly 450 entries in the Linux syscall table require no capability at all — they are ordinary, unprivileged operations available to any UID, exactly like read() or write() — and a handful of them are exactly the kind of thing you would not want an arbitrary container image to be able to invoke against a shared kernel.

keyctl() is the cleanest example, and it recurs through this chapter because it makes the point so precisely: managing entries in the kernel's in-memory key-management facility requires zero capabilities under the normal Unix permission model. A process calling keyctl(KEYCTL_JOIN_SESSION_KEYRING, ...) is doing something completely ordinary from DAC's point of view — no file is being opened, no owner check applies, no capability bit is consulted, because the operation was never designed with "should an untrusted container be allowed to do this" in mind. Chapter 7's whole toolkit — the five capability sets, the bounding-set ratchet, the default fourteen — is structurally incapable of saying no to keyctl(), because keyctl() was never wired into that toolkit in the first place.

  • Capabilities only gate what someone remembered to gate. Dozens of syscalls carry no capability check whatsoever, and the kernel's syscall surface grows every release.
  • A container's threat model is different from a login shell's. A shell run by a trusted human doesn't need syscall-level filtering; a container running an arbitrary, possibly-compromised image from a registry is exactly the process you'd like to constrain to "the syscalls this specific workload actually uses," not "everything DAC and capabilities happen to allow."
  • Even a fully DAC/capability-legal action can still be a bad idea to allow. A capability check answers "is this process privileged enough," never "does this specific policy want to permit this specific operation, on this specific host, for this specific workload" — that is a mandatory-access-control question, not a discretionary one, and it is a second, independent gap capabilities cannot close.
  • The boundary has to be enforceable before the operation's own logic runs, cheaply, for every syscall a process might attempt — not just the ones somebody anticipated needing a permission check.
WHERE THIS SITS IN THE STACK

This is the third and fourth of four privilege-reduction layers a container engine stacks on a root-equivalent UID: namespaces (chapters 2–4) bound what the process can see; capabilities (chapter 7) bound which privileged operations UID 0 may still perform; seccomp-bpf (this chapter, first half) bounds which raw syscalls the process may even attempt, independent of capability or DAC outcome; and AppArmor/SELinux (this chapter, second half) add mandatory access control — policy-driven checks that run in addition to, and can only further restrict, whatever discretionary access control (DAC: file owner/mode bits) and capabilities already decided. Four orthogonal layers, and — foreshadowing chapter 9 — all four are expressed identically in the OCI Runtime Spec's config.json, which is where runc and crun read them from before a container's first instruction ever runs.

ARC 02 · HISTORICAL CONTEXT

Two lineages that predate containers by a decade, merging into one stack

Neither seccomp nor either mandatory-access-control system was built for containers — both lineages are fifteen-to-twenty years older, built for different threat models, and containers simply became their most visible consumer once Docker wired them in by default. DEEP CONTEXT · SECCOMP'S NAME IS LITERAL

"seccomp" is short for secure computing mode, and Andrea Arcangeli's original 2005 patch was built for a specific, narrow purpose: letting a machine donate idle CPU cycles to distributed-computing projects (in the mold of SETI@home) without trusting the donated binary at all. The original mode — later named SECCOMP_MODE_STRICT — permitted exactly four syscalls: read(), write() on already-open file descriptors, _exit(), and rt_sigreturn(). Nothing else, ever. That is unusably strict for a container running a real application, which is precisely why 2012's seccomp-bpf (SECCOMP_MODE_FILTER) exists — but the lineage explains seccomp's whole design philosophy: start from nothing, add back only what's proven necessary, and make the kernel — not the application — the enforcement point.

ARC 03 · NAIVE SOLUTION

Attempt #1: trust DAC and capabilities to be enough

Derive it honestly. Chapters 2 through 7 already built a serious defense: private namespaces, resource limits, and a capability set cut from ~40 bits to 14. The naive next step is to declare victory — ship a container runtime that applies exactly those controls and lets every syscall through unfiltered, trusting that "no capability, no privileged operation" already covers the threat model. This is precisely what --security-opt seccomp=unconfined gives you today, and it is worth understanding as a real, named configuration rather than a strawman nobody runs.

shellthe naive baseline — namespaces + cgroups + capabilities, no syscall filter
# everything from chapters 2-7, and nothing from this one
docker run --rm \
  --cap-drop=ALL --cap-add=NET_BIND_SERVICE \  # chapter 7: down to 1 capability
  --security-opt seccomp=unconfined \          # <- every syscall reaches the kernel unfiltered
  --security-opt apparmor=unconfined \         # <- no MAC profile either
  nginx:latest

# the process can attempt ANY of the ~450 syscalls; only DAC + the
# 1 remaining capability stand between it and the kernel's own logic

This gets something real right: a process with one capability and tight namespaces genuinely cannot do most of what a legacy privilege-escalation exploit needs. For a fully trusted image, on a fully trusted host, running a workload you wrote yourself, "just use capabilities well" is not an unreasonable starting position — it is, after all, exactly where chapters 2 through 7 leave you. The naive model breaks down the moment you ask it to defend against a syscall that capabilities were never designed to gate.

ARC 04 · WHY IT FAILS

The gap is not hypothetical — it has a name and a CVE

Quantify the exposure precisely. Of the roughly 450 syscalls a modern x86_64 kernel exposes, Docker's default seccomp profile (moby/moby/profiles/seccomp/default.json) explicitly names on the order of 40–50 of them for denial or conditional restriction — mount, umount2, unprivileged pivot_root, keyctl, add_key, request_key, ptrace, reboot, swapon/swapoff, open_by_handle_at, init_module/delete_module/finit_module, perf_event_open, quotactl, acct, bpf, and certain clone/unshare invocations carrying CLONE_NEWUSER, among others. Podman's equivalent, sourced from the shared containers/common library, names the same syscalls for the same reasons — the two engines converged independently on almost the identical list because the underlying kernel attack surface is the same regardless of which engine is asking.

THE NUMBERS

Run the naive configuration from §3 and every one of those ~45 syscalls is reachable by any process holding even a single capability or none at all — keyctl and add_key need zero capabilities under DAC, full stop. CVE-2016-0728 — a use-after-free in the kernel keyring's session-join path, reachable purely through keyctl() by an ordinary unprivileged user — is the concrete proof that this gap is not theoretical: a container with the tightest possible capability set and the naive seccomp=unconfined configuration was exactly as exposed to it as a process running with full root, because capabilities were never in the code path that mattered. §11 returns to this incident with the full root-cause detail.

Two more failure modes compound the gap, and neither is about a missing deny rule: (1) some syscalls are legal under DAC and every capability check, yet still represent a policy decision a specific environment wants to forbid — "no process in this container should ever open /etc/shadow, even one running as a UID that technically owns it" is not expressible in DAC or capabilities at all, because DAC's whole design principle is that the resource's owner decides, and capabilities only ever ask "is this UID privileged enough," never "does policy permit this specific access." (2) a capability check happens deep inside a syscall's own implementation, after real kernel work may already have started — filtering needs to happen earlier, at the syscall's very entry, for operations that should never be attempted in the first place. Both point to the same conclusion: the naive model needs two more layers, not a bigger capability list.

ARC 05 · BETTER SOLUTION, DERIVED

Filter the syscall itself, at the kernel's front door

The fix for the first gap is to intercept every syscall before the kernel dispatches to its implementation, evaluate a policy against the syscall number and its raw arguments, and return a decision the kernel enforces unconditionally — independent of what capability or DAC check the syscall's own body might have performed. That is exactly what seccomp-bpf (SECCOMP_MODE_FILTER, Linux 3.5, 2012) is: a small BPF program, attached to a process via prctl(PR_SET_SECCOMP, ...) or the newer seccomp(2) syscall, that the kernel runs against a struct seccomp_data — syscall number, target architecture, and the six raw argument words — on every single syscall that process or its descendants attempt. Step through how a single check site (suser(), then capable()) became a filter the kernel consults before either of those.

From "no filter" to seccomp-bpfSTEP-BY-STEP

Applied to containers: Docker (via libseccomp, feeding runc) and Podman (via crun's own BPF generator, reading the same profile shape from containers/common) both attach a filter to every container's init process before it execve()s the entrypoint. The filter's default action for anything not on its allow-list is SECCOMP_RET_ERRNO carrying EPERM — so a blocked syscall doesn't crash the process or look mysterious, it returns exactly the same errno a permission failure would, at the syscall's very first instruction, before mount()'s or keyctl()'s own logic — including whatever capability check it might otherwise have run — ever executes.

THE PART CAPABILITIES COULD NEVER DO

Because the filter tests the raw syscall number, it can deny keyctl() and add_key() outright — no capability check to fail, because none is ever consulted; the BPF program returns SECCOMP_RET_ERRNO(EPERM) before the kernel's keyring code runs at all. This is the exact mechanism that closes §4's gap, and it is why every serious container engine ships a default seccomp profile even after capabilities are already tightened to 14.

ARC 06 · WHY SECCOMP ALONE STILL FAILS

A filter that can only see numbers, not meaning

Seccomp-bpf closes the "syscall nobody gated" gap completely, but it has a structural blind spot baked into its own definition: the BPF program only ever sees struct seccomp_data — the syscall number, the architecture, and six raw integer argument words. When an argument is a pointer — a filename, a path, a buffer — seccomp sees the pointer's numeric value, never what it points to. Step through why that makes an entire class of policy unenforceable at the seccomp layer, no matter how the filter is written.

Why seccomp can't filter "don't mount /etc/shadow"STEP-BY-STEP

Three more costs compound the blind spot:

  • Coverage is a moving target. fsopen(), fsconfig(), fsmount(), and move_mount() — the "new mount API" landed in Linux 5.2 (2019) — do most of what the legacy mount() syscall does, through entirely different syscall numbers. A profile written before 2019 that carefully denies mount says nothing about them; §11's CVE-2022-0185 incident is exactly this gap, exploited in the wild years after the legacy syscall was already covered.
  • A syscall-number filter can't express "who" or "which resource," only "which operation." Seccomp can say "no process may call ptrace()," but it cannot say "this container's processes may ptrace() each other but not a sibling container's processes" — that is a question about identity and resource labeling, categorically outside what a per-syscall-number BPF program can evaluate.
  • It is entirely off by default in the naive configuration from §3, and one misconfigured --security-opt seccomp=unconfined in a compose file or Kubernetes pod spec silently removes the entire layer with no other symptom until something exploits exactly the gap it was covering.

Every one of these needs a check that understands labels, paths, and relationships between processes and resources — not just syscall numbers. That is precisely what mandatory access control adds, and precisely why AppArmor and SELinux exist as a fourth, independent layer rather than a bigger seccomp profile.

THE ORDER THESE ACTUALLY RUN IN

It is tempting to read the four layers top-to-bottom as the order the kernel checks them — it is almost the reverse. Seccomp's BPF program runs first, in the syscall entry path (arch/x86/entry/common.c on x86_64), before the syscall's own implementation — and therefore before any DAC or capability check inside it — ever executes. If seccomp allows the syscall through, the syscall's own body runs its usual DAC checks, then any capable() calls it needs, and then, interleaved with those, the LSM hook chain — security_file_open(), security_sb_mount(), and dozens of others — runs AppArmor's or SELinux's policy check. §8 walks this exact sequence with a live example.

OPERATIONAL GOTCHA WORTH KNOWING

Seccomp filters are a one-way ratchet, exactly like chapter 7's capability bounding set: seccomp(2) can only ever add a filter, and the syscall's actual verdict for any process with multiple attached filters is the most restrictive result among all of them (kill dominates trap dominates errno dominates log dominates allow). A process can never loosen a filter another layer already installed — which is exactly why a container engine can safely attach its default profile and trust that nothing the containerized process does can widen it afterward.

ARC 09 · TRADEOFFS

Four gates, four different jobs

LAYERWHAT IT BUYSWHAT IT COSTS / MISSES
DAC only zero configuration, universal Unix semantics root bypasses it entirely owner-controlled, not policy-controlled
+ capabilities (ch. 7) splits root into 40 gated operations only covers syscalls someone remembered to gate — keyctl, add_key untouched
+ seccomp-bpf blocks the raw syscall itself, no capability check needed near-zero runtime cost blind to pointer contents (paths, labels) coverage must keep pace with new syscalls
+ AppArmor / SELinux (MAC) policy-driven, path- or label-aware, binds even root separate policy language to author and audit SELinux requires a labeled filesystem

Read the table as strictly additive, not competing: each layer catches exactly what the one above it cannot express. A hardened container stacks all four, and — as with chapter 7's capability layers — the honest claim is that the syscall coverage and profile shape are close to identical between Docker and Podman; the divergence is entirely in the mandatory-access-control layer and in how the filter itself gets built.

The honest takeaway mirrors chapter 7's: at the seccomp layer, Docker and Podman are separately-implemented but nearly identical in outcome — both express the result as an OCI-shaped linux.seccomp object (chapter 9) before runc or crun ever runs it. At the MAC layer, the difference is not a matter of one engine being more secure than the other; it is a direct consequence of which Linux distribution each engine's default install target ships with which LSM enabled by default.

ARC 10 · PERFORMANCE & ATTACK SURFACE

Near-free filtering, and what strictness actually buys you

A cBPF seccomp program is JIT-compiled by the kernel on attach and runs on every syscall entry as a tight, bounded loop of comparisons — commonly cited overhead is in the range of tens to a couple hundred nanoseconds per syscall for a profile with dozens of rules, which is immaterial next to the cost of the syscall itself for anything that touches the filesystem or network. LSM hook evaluation (AppArmor's path matching, SELinux's security-server policy lookup, itself backed by an access-vector cache) costs more per check than a seccomp bitmask test, but both are dwarfed by the I/O the syscall is usually doing anyway. The number worth optimizing is not latency — it's how much of the kernel's surface remains reachable.

ARC 11 · REAL-WORLD INCIDENTS

Three times the specific layer in this chapter was the whole story

Incident 1: CVE-2016-0728 — the keyring refcount overflow

A use-after-free in the kernel's key-management facility, reachable entirely through keyctl(KEYCTL_JOIN_SESSION_KEYRING, ...) called in a loop until an internal reference count overflowed — a syscall requiring, as §1 established, zero capabilities under the normal permission model. A container running with capabilities dropped to Docker's default 14 (or even fewer) was exactly as exposed as one running as full root, because the vulnerable code path was never gated by anything chapter 7 covers. The reason this incident is a footnote rather than a routine container-escape headline is precisely this chapter's default profile: both Docker's and Podman's default seccomp lists deny keyctl and add_key outright, so any container running under the default profile — not unconfined — was never able to reach the vulnerable code at all. It is the single clearest real-world demonstration that seccomp closes a gap capabilities structurally cannot.

Incident 2: CVE-2022-0185 — the new mount API outran an old profile

A heap buffer overflow in legacy_parse_param(), part of the kernel's newer filesystem-context API (fsopen()/fsconfig()/fsmount(), landed in Linux 5.2, 2019), exploitable by a process holding CAP_SYS_ADMIN — which an unprivileged user can obtain for free inside its own user namespace via unshare(CLONE_NEWUSER) (chapter 4), no host privilege required. This is §6's "coverage must keep pace" cost made concrete: seccomp profiles written with the legacy mount() syscall in mind said nothing about fsconfig(), a different syscall number entirely, so the mount-family deny rule that had protected containers for years quietly stopped covering the new attack surface the moment the kernel grew a second way to mount a filesystem. Root cause distilled: a syscall-number allow-list is only as good as its last update, and this incident is why current seccomp default profiles explicitly restrict the fsopen/fsconfig/fsmount/move_mount family alongside the legacy calls.

Incident 3: CVE-2019-16884 — an AppArmor and SELinux bypass in the same bug

A flaw in how runc exec re-attached to a running container allowed a malicious container — one that had replaced its own /proc mount in a specific way — to cause a later runc exec invocation to apply its LSM label incorrectly, letting the exec'd process escape both AppArmor's and SELinux's confinement simultaneously. The root cause was not a weakness specific to either policy language; it was a gap in when runc applied the label relative to when the target process's namespace context was resolved — proof that MAC's guarantee is only as strong as the runtime code that wires the label onto the right process at the right moment, and that "which LSM" matters less here than "did the runtime get the sequencing right." Both runc and the affected LSM configurations were patched by fixing the label-application ordering, not by changing either AppArmor's or SELinux's policy model.

Ca minimal seccomp-bpf filter, hand-written (no libseccomp)
/* Deny mount(2) with EPERM; allow everything else. Real struct
 * shapes from linux/seccomp.h and linux/filter.h. */
struct sock_filter filter[] = {
    /* load the syscall number into the BPF accumulator */
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),
    /* if it's __NR_mount, jump to the deny instruction */
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_mount, 0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | (EPERM & SECCOMP_RET_DATA)),
    /* fallthrough: allow */
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
};
struct sock_fprog prog = { .len = ARRAY_SIZE(filter), .filter = filter };

prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);   /* required before an unprivileged filter */
prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog);

WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Seccomp's default-deny shape. The profile's defaultAction is SCMP_ACT_ERRNO, not SCMP_ACT_ALLOW — an allow-list of ~300+ ordinary syscalls, not a deny-list of ~45 dangerous ones. A deny-list is only as safe as its last update (exactly §11's CVE-2022-0185 lesson); an allow-list fails safe against syscalls nobody has thought about yet. 2. AppArmor's explicit denies, even under a broad file rule. The profile above grants broad file access, then explicitly re-denies /proc/sysrq-trigger and friends — defense in depth against the broad grant, written by people who assumed the broad rule would eventually be too permissive somewhere. 3. SELinux's MCS categories as automatic per-instance isolation. Every container gets a fresh, unique category pair with no operator configuration required — multi-tenant isolation as a side effect of how the labels are allocated, not a policy someone has to remember to write per container.

EXPERIMENTS TO RUN

1. Load the default profile and try every syscall — note which fail at seccomp versus which fail later, at the capability check, once seccomp lets them through. 2. Switch to unconfined and retry keyctl — it now succeeds, because nothing was ever gating it but seccomp. 3. Retry mount under unconfined — it still fails, but for a different reason: the capability check inside mount() itself, since the default 14 capabilities never included CAP_SYS_ADMIN. 4. Cycle MAC to none and try the AppArmor- and SELinux-specific probes — they succeed only when the matching LSM is off, proving MAC is enforced independently of both DAC and seccomp. 5. Load hardened and confirm the ptrace family now fails at the seccomp layer instead of the capability layer — same visible EPERM, earlier and cheaper gate.

Chapter 08 complete

You can now read a process's seccomp and LSM state from /proc, explain why capabilities and seccomp catch different classes of syscall, and say precisely why AppArmor and SELinux exist as a fourth layer even after the first three are correctly configured. Every layer from chapters 2 through 8 — namespaces, cgroups, capabilities, seccomp, MAC labels — is, in the end, just fields in one file: chapter 9 opens config.json, the OCI Runtime Spec's bundle format, and shows how runc and crun — the low-level runtimes underneath Docker and Podman respectively — consume exactly that file to actually create a container, with no engine in the loop at all.
