BLOCKCHAIN FUNDAMENTALS · CHAPTER 12

Scaling: The Trilemma,
Sharding & Layer 2

Every design decision in chapters 1–11 — Nakamoto consensus, block propagation, gossip, the fork-choice rule — was made under one constraint you have not yet had to name: a blockchain is a global broadcast medium in which every full node processes every transaction. That single structural fact, not a policy choice, is why Bitcoin settles roughly seven transactions per second and Ethereum a few dozen. This chapter derives the bound, states the scalability trilemma precisely enough to argue with it, and builds the two families of real fixes — bigger base layers and Layer 2 — while pricing exactly what each one costs.

ARC 01 · THE PROBLEM

Why a ledger that everyone checks can't be a ledger that everyone uses

Start from the mechanism, not the complaint. In every design this course has built so far, a transaction is not "processed by the network" the way a request is processed by a load-balanced fleet of interchangeable servers. It is broadcast to every full node, and every full node independently validates and applies it. There is no partitioning, no sharding-by-default, no server that handles only its slice of traffic — that is precisely the property (chapter 6) that lets an untrusted, permissionless set of participants agree on one history without a coordinator. The moment you accept that property, you have also accepted its price: aggregate throughput cannot exceed what the least capable node you still want to be able to validate can process, because that node must, eventually, process everything.

This is worth sitting with, because it inverts the usual scaling intuition. A web service scales by adding machines — more servers, more capacity, roughly linearly, because different servers handle different requests. A validating blockchain node cannot be "added" the way a web server can, because adding a node does not remove work from any other node; every existing node still has to validate the new block, and now one more node does too. Full replication is the whole security model — an attacker cannot rewrite history because thousands of independent parties, not one operator, hold and check it — and full replication is the whole scaling problem, because none of those parties' work is optional.

  • Bitcoin, derived, not quoted. A block is capped at roughly 1 MB of base size (4M weight units with SegWit's discount, chapter 11's fork-choice rule notwithstanding) and arrives on average every 600 s (the difficulty retarget target from chapter 8). A typical legacy P2PKH transaction is ~250 bytes. That's 1,000,000 / 250 = 4,000 transactions per block, and 4,000 / 600 s ≈ 6.7 tx/s — the "~7 tx/s" figure you've seen quoted is this division, not a measurement of anything more mysterious.
  • Ethereum, derived. A block's total computation is capped by its gas limit (~30,000,000 gas as of recent mainnet history) with a ~12 second slot time. A bare ETH transfer costs 21,000 gas: 30,000,000 / 21,000 ≈ 1,428 transfers per block, / 12 s ≈ ~119 tx/s — but that is the ceiling for the cheapest possible transaction. Real usage is dominated by contract calls (an ERC-20 transfer is ~65,000 gas; a DEX swap can be 150,000–300,000+), which is why observed sustained throughput is the commonly cited ~15–30 tx/s: the same gas budget, spent on heavier transactions.
  • Visa, for scale, and why the comparison is slippery. Visa's own published materials cite a network capacity in the tens of thousands of transactions per second (a figure widely reported around 24,000–65,000 depending on the benchmark cited and year), while day-to-day average throughput is far lower — commonly cited around 1,700 tx/s. Both numbers describe something categorically different from a confirmed Bitcoin transaction: a card swipe is an authorization — a provisional, reversible hold checked against a issuer's ledger in milliseconds — while actual fund movement between banks is settlement, batched and reconciled later, often the next business day, through entirely different systems (ACH, wire, correspondent banking). A block six confirmations deep is closer to a settled wire transfer than to an authorized card swipe.
WHY THE UNFAIR COMPARISON IS STILL THE RIGHT ONE

You can object that comparing tx/s across authorization and settlement systems compares apples to oranges — and you'd be correct. But the objection doesn't make the constraint go away: whatever category you put it in, a user who wants base-layer finality for a payment is bounded by the ~7 or ~20 tx/s ceiling, full stop. The "unfair" comparison is the one that matters operationally, because it's the one your application actually hits. The honest response isn't to reject the comparison; it's to ask which workloads truly need base-layer settlement at all — which is exactly the question Layer 2 (§5 onward) answers.

DEEP CONTEXT · WHO NAMED THE TRILEMMA?

"Blockchain trilemma" is popularly attributed to Vitalik Buterin, who used it in talks and posts around 2017–2018 to summarize a pattern he and others had observed empirically across Bitcoin, early altcoins, and Ethereum's own roadmap: every attempt to buy more of one property (usually scalability) seemed to cost one of the other two. It is not — and this matters for how you should use it — a proven impossibility result like FLP (chapter 6) or CAP. It is closer to an engineering heuristic backed by a resource argument, which §4 makes precise. Treat claims that it is a "law" with the same skepticism you'd apply to "the blockchain is immutable."

ARC 03 · NAIVE SOLUTION

Attempt #1: turn the obvious dials

If throughput is block_size / avg_tx_size / block_interval, the naive fix reads itself off the formula: increase the numerator, decrease the denominator. This is not a strawman invented for this chapter — it is the literal engineering position of Bitcoin XT (2015), Bitcoin Classic (2016), Bitcoin Unlimited, and ultimately Bitcoin Cash (2017), and it is the default posture of most "high-throughput" Layer-1 chains that advertise tens of thousands of TPS.

pseudo-codenaive_scale.py — turn the two obvious knobs
def throughput_tx_per_sec(block_size_bytes, avg_tx_bytes, block_interval_s):
    txs_per_block = block_size_bytes // avg_tx_bytes
    return txs_per_block / block_interval_s

# Bitcoin today, for reference:
throughput_tx_per_sec(1_000_000, 250, 600)      # ≈ 6.7 tx/s

# "Just fix it": 100x the block, 10x faster blocks.
throughput_tx_per_sec(100_000_000, 250, 60)   # ≈ 6,667 tx/s — arithmetically, done.

# Nothing else in the protocol needs to change... on paper.

Read that last comment literally, because the naive solution's appeal is real: it requires touching almost nothing. No new cryptography, no new trust assumptions, no new failure modes that don't already exist at smaller scale — just bigger numbers into the same formula that already works. Every serious scaling proposal starts by ruling this out explicitly, which means you should understand exactly what breaks, not just that something does.

ARC 04 · WHY IT FAILS

Three failures, in the order they bite: propagation, sync, and state

Turning the dials doesn't break correctness — a 100 MB block is still a valid, verifiable block. It breaks the population of participants who can keep up, which is a different and more insidious failure because it degrades gradually and rewards whoever can absorb the cost. Watch propagation delay first — the animation below floods a toy 12-node gossip network (chapter 11's topology) with blocks of increasing size over identical links:

Three distinct failures stack up as the size dial rises, and only the third one is actually unbounded:

  • 1. Propagation delay → orphan rate (recoverable, but regressive). Using the Decker–Wattenberg model from chapter 11 (propagation time ≈ fixed per-hop latency + size/bandwidth, summed across the gossip path's hop count), a block that takes materially longer than the network's typical inter-block gap to reach most miners is more likely to be orphaned by a competing block found elsewhere. Crucially, this cost is not evenly distributed: a miner with a fat, well-peered connection to the rest of the hash power propagates fast and rarely orphans; a miner on a residential or distant link pays the orphan tax disproportionately. Bigger blocks don't just raise the average orphan rate — they widen the gap between well-connected and poorly-connected miners, which is a centralizing force with no cryptography involved at all.
  • 2. Initial block download (IBD) time (recoverable, but a growing barrier to entry). A new node must download and validate the entire history before it can independently verify anything. If throughput rises, chain growth rate rises proportionally — Bitcoin's ~600 GB (2025-era, base + witness) at ~7 tx/s becomes, roughly, tens of terabytes per year at Visa-average throughput. This doesn't corrupt anything, but it prices out casual node operators, who default instead to trusting a remote node (a light client, an exchange, a block explorer) — quietly re-centralizing verification onto whoever can still afford to run a full node.
  • 3. State growth (the real long-run constraint). This is qualitatively different from the first two. Chain history can in principle be pruned once spent, and IBD time can be attacked with checkpoints and snapshots. But the current, live, must-be-in-fast-storage state — Bitcoin's UTXO set, Ethereum's account/storage trie — only grows. Nothing meaningfully expires from it: a UTXO sits there until spent, which may be never; an Ethereum account or contract's storage slots persist until explicitly cleared, which almost nothing does. There is no garbage collector for a decentralized ledger's live state, because "collecting" it would mean some authority deciding data is safe to forget — precisely the kind of decision the whole system exists to avoid delegating. §10 quantifies exactly how this compounds over years, independent of any block size choice.
THE NUMBERS THAT MATTER

Raise Bitcoin's block size 100× to hit Visa-average throughput and you have not fixed anything — you have relocated the bottleneck from "block space" to "who can afford the bandwidth, disk, and RAM to independently verify." At the extreme, only data-center-grade operators can keep up, which converts a permissionless peer-to-peer network into a permissioned club of well-capitalized validators that happens to still use the same consensus rule — the decentralization you paid for with §1's broadcast-to-everyone design is gone, and you paid the throughput bill without receiving the security property that throughput was supposed to preserve.

ARC 05 · BETTER SOLUTION

The trilemma, stated precisely — then the actual fix

Before the fix, state the tradeoff as an argument you could defend, not a slogan you repeat. Three properties, pairwise in tension:

  • Decentralization — a large, permissionless, geographically and organizationally diverse set of participants can independently validate every rule, with no reliance on trusting any subset of them.
  • Security — the cost to violate a validated rule (rewrite history, forge a balance, censor transactions) is prohibitively high, which in an open-membership system (chapter 7) means it must be backed by a large, broadly-held scarce resource — hashpower, stake — rather than by vetting who gets to participate.
  • Scalability — the system processes a high volume of transactions relative to its resource footprint.

The precise version of the trilemma is this chain of implication, not a mystical law: raising throughput by raising the per-transaction or per-block work each validating node must perform (§3's naive lever) shrinks the population of participants who can afford to run a validating node (§4) which concentrates validation into fewer, larger, better-resourced operators which erodes the property — broad, low-cost, permissionless verifiability — that made "security without trusting anyone in particular" true in the first place. It is a resource argument: each step follows from the previous one given real hardware and bandwidth costs, not from a proof that no protocol could ever do better. No one has published a formal impossibility proof of the trilemma the way Fischer–Lynch–Paterson proved consensus impossibility under asynchrony (chapter 6); treat it as a strong empirical regularity that any scaling proposal must argue around, not assume away.

Given that, the fix that has actually held up is not "raise per-node work less aggressively." It's a change of strategy: keep the base layer's per-node work bounded and small, and move most execution somewhere that doesn't require universal, immediate broadcast at all — while still settling the outcome, when it matters, back onto the base layer's security. ARC 06 · WHAT LAYER 2 STILL COSTS

Moving the work off-chain doesn't make it free — it changes who pays and when

Be as honest about Layer 2's bill as §4 was about bigger blocks. Every approach below inherits some, but never all, of the base layer's guarantees, and the gap is exactly where the real engineering is:

  • Payment channels need locked, idle capital and liveness. Opening a channel means committing funds to a multisig output that is useless for anything else until the channel closes; a channel can only route a payment up to whatever capacity is provisioned on that specific path (the routing problem); and a channel participant who goes offline for too long while a counterparty tries to cheat can lose funds if they don't come back online before the dispute window closes (§8 makes this concrete). None of this is a base-layer transaction fee problem — it's a capital-efficiency and availability problem.
  • Rollups still publish data on-chain — and that data is the actual bottleneck. Both optimistic and ZK rollups execute transactions off-chain but must publish enough data on the base layer for anyone to reconstruct the resulting state (and, for optimistic rollups, to construct a fraud proof if the operator lies). If that data were not published — or published but withheld from anyone trying to check it — the system's safety collapses even if every computation was correct, because no one else could verify or exit with their true balance. This is the data availability problem, and it is the binding constraint on rollup throughput, not proof verification cost: a rollup is only as decentralized and trustworthy as its guarantee that the data behind its state actually got published where anyone could check it.
  • Optimistic rollups trade capital lock-up for cheap-when-honest execution. Fraud proofs only need to run if someone actually cheats, which is computationally efficient in the common case — but the corollary is a challenge window (commonly ~7 days in production systems) during which a posted state root cannot yet be treated as final, because a fraud proof might still arrive. Withdrawals back to the base layer either wait out that window or pay a liquidity provider to front the funds early, at a fee.
  • ZK rollups trade expensive, unconditional proving for instant finality. A validity proof must be generated for every batch, honest or not — there's no "only when someone objects" discount — and proof generation for a large batch of general-purpose EVM execution is computationally heavy, historically requiring specialized provers and, for some proof systems, minutes of wall-clock time per batch. Some SNARK constructions (e.g. Groth16) additionally require a trusted setup, trading a one-time ceremony-based assumption for smaller, faster proofs; STARKs and other transparent-setup systems avoid that specific assumption at the cost of larger proofs.
  • Sharding reintroduces the distributed-transactions problem chapter 6 already made you respect. Splitting validation across committees genuinely reduces per-node work — no single validator processes the whole chain's state — but a transaction touching accounts on two different shards now needs a cross-shard protocol with its own atomicity and consistency guarantees, and that protocol is, structurally, the same two-phase-commit-shaped problem distributed databases have wrestled with for decades, now happening between mutually distrusting committees instead of trusted machines in one datacenter.
THE PATTERN TO NOTICE

Every Layer 2 approach narrows which property gets stressed — capital efficiency, latency to finality, proving cost, cross-domain composability — but none of them make the trilemma's underlying resource argument disappear. §9 builds the comparison table that prices each tradeoff side by side, honestly.

DEEP CONTEXT · "MODULAR" VS "MONOLITHIC"

This stack is what the ecosystem now calls a modular blockchain design — separate systems specialize in consensus, data availability, and execution, communicating through well-defined interfaces (Ethereum plus its rollups is the largest deployed example; Celestia was purpose-built as a standalone DA layer other chains can settle to). The alternative, monolithic design — one chain does consensus, DA, and execution together, scaled by raising per-node hardware requirements (high-throughput L1s in the Solana lineage) — is a direct, still-live continuation of §3's naive lever, made viable by accepting a smaller, more homogeneous validator set as the price of simplicity. Neither is strictly "right"; they sit at different points on the same trilemma surface, and §11 shows what happens when each one's specific assumption breaks.

ARC 08 · INTERNAL IMPLEMENTATION

The mechanisms, precisely: revocable state, fraud windows, and sampling

Three mechanisms carry the entire chapter's weight. (a) how a payment channel updates state off-chain without letting either party cheat; (b) the two rollup designs' actual dispute/proof machinery; (c) why erasure coding turns data availability sampling from theater into a real guarantee — with genuine modular arithmetic, not illustrative hex.

(a) Payment channels: state updates with revocation, not just multisig

A channel is not merely "a shared account." The hard part is preventing either party from later broadcasting an old, more-favorable-to-them state after a new one has been agreed. Step through a Lightning-style channel's full lifecycle, including an attempted cheat:

WHY REVOCATION, NOT JUST A TIMELOCK

A simpler design would let either party unilaterally close with their latest signed state after a timelock, with no punishment. That fails against a rational cheater: broadcasting an old, favorable state costs them nothing but a delay, so a party who falls behind (loses a later dispute) has every incentive to try the old state and see if their counterparty is watching. Revocation makes cheating strictly dominated: every state update comes bundled with the previous state's revocation secret, so publishing an old state hands your counterparty the exact information needed to take all the channel's funds, not just dispute the balance. The security model shifts from "prevent cheating" to "make watching for cheating (a watchtower can do this for you) sufficient to punish it," which is a much easier property to actually operate.

(c) Data availability sampling: real erasure coding, real probabilities

Here is the actual argument, computed rather than asserted. Encode a small "block" of k field elements as a degree-(k−1) polynomial over the prime field GF(257), then publish n = 2k evaluations of it (a systematic Reed–Solomon-style erasure code at rate 1/2 — the same rate class used by Ethereum's proto-danksharding, EIP-4844). Any k of the n evaluation points suffice to recover the original data via Lagrange interpolation — real modular arithmetic, computed below, not a metaphor. THE ARGUMENT IN ONE SENTENCE

Erasure coding doesn't make sampling reconstruct the data — it changes how much an attacker must hide to matter. Without coding, hiding one single needed chunk out of k breaks availability, so a sampler must check nearly everything to catch it. With a rate-1/2 code, an attacker must withhold more than half of all n chunks before reconstruction is impossible — and hiding over half of a large, randomly-indexed set is exactly the kind of thing a handful of random samples, taken independently by many light clients across the network, will almost certainly catch. The code doesn't hide the attack; it makes the attack loud.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

The one curve that never bends back down: state growth

Block size and interval are policy knobs — a hard fork can change them tomorrow, in either direction. State size is not a policy knob in the same sense: it is the accumulated record of every UTXO never spent and every contract storage slot never cleared, and it can only be reduced by an active pruning/witness mechanism, never by simply choosing smaller blocks going forward. Project it out, at a few illustrative throughput levels, with average state growth per transaction held roughly constant (~150 bytes/tx for a UTXO output; Ethereum accounts and contract storage run comparably per write, before indexing overhead):

Two categories of response exist, and neither one raises throughput — they both attack the storage/verification cost instead:

  • Pruning & witness discarding. A node can discard historical block data once it has independently derived the current state from it — Bitcoin's -prune mode, or Ethereum clients that drop old state tries. This shrinks the history line in the chart above, but not the live-state line: a pruned node still needs the full current UTXO set or state trie in fast storage to validate new blocks.
  • UTXO commitments and stateless clients. If the current state is itself committed to inside every block header (a UTXO commitment — proposed but never adopted for Bitcoin, notably by Peter Todd, and practically realized via accumulator constructions like Utreexo), a node can validate a transaction by checking a compact membership proof instead of holding the entire state. Ethereum's long-discussed move to Verkle trees targets the same outcome: a stateless client that verifies blocks using proofs shipped alongside them, shifting the burden of holding full state onto a smaller set of specialized "state provider" nodes.
SECURITY COROLLARY: FEWER FULL STATE-HOLDERS, MORE TRUST CONCENTRATION

Every one of these mitigations trades some verification cost for some trust concentration. A stateless client checks a proof instead of the state itself — which is sound as long as the proof system is sound and *someone* is honestly maintaining the full state to generate proofs from. This is the same shape of tradeoff as §7's modular-vs-monolithic split: cheaper individual verification, contingent on a smaller set of specialized parties doing the expensive part correctly. None of it is free; it is simply a different place to put the bill than "everyone stores everything forever," which was never sustainable regardless of block size.

ARC 11 · REAL-WORLD INCIDENTS

Four times the trilemma sent a bill

Incident 1: CryptoKitties and Ethereum's first real congestion event (December 2017)

A single popular application — a game trading non-fungible digital cats — pushed Ethereum's pending-transaction backlog high enough that gas prices spiked several-fold and unrelated applications' transactions stalled for hours. The root cause is exactly §1's structural fact: every application on Ethereum shares one global execution resource (the gas market), so a single popular contract can price out every other user of the same chain. This event is widely credited as the moment mainstream attention turned to "Ethereum needs to scale," and it predates essentially every rollup deployed today.

Incident 2: the Bitcoin block-size wars and the August 2017 split

Years of disagreement over whether to raise Bitcoin's block size directly (§3's naive lever) culminated in SegWit's activation (BIP141, August 2017 — a soft fork restructuring transaction serialization, chapter 11's witness discount) followed, days later, by a minority of the ecosystem hard-forking to Bitcoin Cash with an 8 MB block size — a direct, literal instantiation of the naive lever this chapter opened with. Both chains still run today, and the throughput/decentralization gap between them is an ongoing, empirically observable version of §4's argument rather than a hypothetical.

Incident 3: the Ronin Bridge hack (March 2022, ~$625M)

Axie Infinity's Ronin sidechain (§7) was secured by a 9-validator multisig requiring 5 signatures to approve withdrawals back to Ethereum. Attackers compromised enough validator keys (5 of 9, including one via a fake job offer that led to a compromised node granted emergency access months earlier) to forge withdrawal approvals and drain the bridge. This is not a bug in cryptography — the multisig worked exactly as specified. It is §9's tradeoff row for sidechains made concrete: a sidechain's security is only as strong as its own validator set, fully decoupled from Ethereum's, and a 9-key multisig is a dramatically smaller, more concentrated trust set than the L1 it bridges to.

Incident 4: repeated Solana network outages (2021–2024)

Solana's design is the monolithic end of §7's spectrum — very high throughput achieved largely by raising per-validator hardware requirements (high-bandwidth, high-CPU nodes) rather than by moving execution to a Layer 2. Several multi-hour outages (notably September 2021 and again in 2022) were triggered by resource exhaustion under transaction floods — including, in one case, bot-driven spam during an NFT mint saturating the network's scheduling — that a smaller, more homogeneous validator set struggled to recover from without coordinated manual intervention. This is the flip side of the Bitcoin/Bitcoin-Cash comparison in Incident 2: pushing per-node work up can deliver real throughput, but the same concentration §4 predicts shows up as fragility under load rather than (only) as a slow, gradual decline in node count.

        # 2. THEN — and only then — each party reveals the revocation SECRET
        #    for the state they just superseded. This ordering is load-bearing:
        #    revealing early would let a counterparty who hasn't signed yet
        #    walk away with a state they can still cheat with.
        self.reveal_revocation_secret(self.state_index)
        self.state_index += 1

    def handle_broadcast_commitment(self, txid, state_index):
        if state_index < self.state_index and state_index in self.revoked_secrets:
            # Counterparty published an OLD, revoked state. We now hold the
            # secret that derives its private key — sweep ALL of its outputs
            # before the tx's own timelock even expires.
            self.broadcast_penalty_tx(txid, self.revoked_secrets[state_index])
            return "cheater punished: entire channel balance claimed"
        return "latest state — normal cooperative or timelocked close"

Second, the data-availability sampler from the ftree above, in full — genuine GF(257) modular arithmetic and Lagrange interpolation, the same primitives driving §8(c)'s widget:

pythondas_sampler.py — real erasure coding over a small prime field
P = 257  # prime > 255: every byte value has a unique residue

def modinv(a, p=P):
    return pow(a, p - 2, p)  # Fermat's little theorem — real modular inverse

def eval_poly(coeffs, x, p=P):
    y = 0
    for c in reversed(coeffs):
        y = (y * x + c) % p
    return y

def encode(message, n, p=P):
    # message = k coefficients ⇒ degree (k-1) polynomial.
    # Evaluate at n > k points ⇒ a systematic rate-k/n erasure code.
    return [eval_poly(message, x, p) for x in range(1, n + 1)]

def lagrange_reconstruct(points, p=P):
    # points: list of (x, y) — needs >= k of them. Recovers f(0) == message[0]
    # for a constant-term probe; the full loop rebuilds all k coefficients
    # by evaluating the interpolated polynomial at k target x-values.
    def at(x_target):
        total = 0
        for i, (xi, yi) in enumerate(points):
            term = yi
            for j, (xj, _) in enumerate(points):
                if i == j: continue
                term = term * (x_target - xj) % p * modinv((xi - xj) % p, p) % p
            total = (total + term) % p
        return total % p
    return at

# A light client never runs lagrange_reconstruct itself — it only checks
# that s random SAMPLED points are retrievable at all. Reconstruction is
# what a full/"repair" node does once enough samples confirm availability.
WHY IT WAS BUILT THIS WAY — THREE CHOICES TO STEAL

1. Revocation over pure timelocks (Lightning). A protocol that only delays a cheater is weaker than one that makes cheating self-punishing — moving from "prevent" to "detect and destroy the incentive" is a recurring pattern anywhere a counterparty can go temporarily offline (watchtowers, chapter 13's oracle problem, even postgres's crash protocol from the PostgreSQL course: judge by observable outcome, not by policing every step). 2. Optimistic-by-default, prove-only-on-dispute. Fraud proofs exploit the fact that verifying a claim is usually cheaper than proving it unconditionally — the same asymmetry that makes NP problems interesting, applied to economic security instead of complexity theory. 3. Sampling instead of downloading. DAS is a direct application of the classical result that you can gain high confidence about a large population's property by checking a small random subset — the same statistical logic behind audit sampling in accounting, applied here with an erasure code specifically chosen to make the "bad" outcome (majority withheld) large and hence easy to catch randomly.
