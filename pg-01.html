Every query you have ever run against PostgreSQL was executed by a dedicated operating-system process, born from a fork() in a loop that has been accepting connections since 1986. This chapter derives that architecture from first principles: why one process per connection, why not threads, what it costs, and exactly which lines of C make it happen.

ARC 01 · THE PROBLEM

One machine, many clients, zero trust between them

A relational database server has the least forgiving concurrency problem in systems software. It must run arbitrary, untrusted, long-running computations (queries) from many simultaneous clients against a single shared mutable state (the data), while guaranteeing that no client ever observes a half-applied change and that a power cut loses nothing that was acknowledged.

Unpack that and you get five requirements pulling in different directions:

  • Concurrency — hundreds of clients, each expecting the database to feel private.
  • Isolation of state — client A's session variables, prepared statements, and half-finished sorts must be invisible to client B.
  • Shared state — yet all clients read and write the same tables, so some memory must be shared: the buffer cache, the lock table, the transaction status.
  • Fault containment — a bug triggered by one client's query (a segfault in an extension, a corrupted pointer) must not silently corrupt other clients' results.
  • Crash consistency — the server must be killable at any instruction and still recover to a consistent state.

The execution model — what runs the query? — is the first decision a database architect makes, and it constrains everything downstream: memory management (chapter 2), buffer caching (chapter 9), locking (chapter 8), and even how crash recovery works (chapter 11). PostgreSQL's answer is the process-per-connection model: a parent process — the postmaster — that owns nothing but sockets and children, and a fleet of worker processes sharing one region of memory.

WHY THIS MATTERS FOR THE NEXT 20 CHAPTERS

Every subsystem you will study lives in one of exactly two places: the shared memory segment (buffer pool, WAL buffers, lock table, process array) or a backend's private memory (catalog caches, plan cache, executor state, work_mem). Which side of that line a data structure lands on determines what locks protect it, what happens when a process dies holding it, and how it scales with connection count. Learn the line now; everything else references it.

ARC 02 · HISTORICAL CONTEXT

1986: the world PostgreSQL was designed for

PostgreSQL's process model is not a modern choice — it is a 1986 choice that survived because it was robust. To judge it fairly you must load the context: Michael Stonebraker's team at UC Berkeley had just finished Ingres and started POSTGRES ("post-Ingres") on Unix systems where threads did not portably exist. POSIX threads were standardized in 1995 — nine years after POSTGRES began. The only portable concurrency primitive on BSD Unix was fork(), and the only portable shared state was System V shared memory.

DEEP CONTEXT · WHY "POSTMASTER"?

The name is a Unix joke that became load-bearing: like a post office's postmaster, the process routes incoming mail (connections) to clerks (backends) but never serves a customer itself. That discipline — the postmaster never touches a client socket's data, never runs a query, never acquires a data lock — is the key invariant that keeps the whole cluster supervisable. If the postmaster stays simple, it stays alive; if it stays alive, crashed children can always be reaped and restarted. You will see the same supervisor pattern again in Erlang/OTP (RabbitMQ course, chapter 1) — invented independently for the same reason.

ARC 03 · NAIVE SOLUTION

Attempt #1: one process, one client at a time

Derive the architecture honestly. The simplest possible database server is an iterative server: one process, one accept() loop, handle each client to completion before taking the next.

Cnaive_server.c — the strawman, annotated
int main(void)
{
    int lfd = socket(AF_INET, SOCK_STREAM, 0);
    bind(lfd, ...);              /* port 5432 */
    listen(lfd, 64);             /* kernel accept queue: 64 pending  */

    for (;;) {
        int cfd = accept(lfd, ...);      /* blocks until a client arrives   */
        handle_session(cfd);             /* auth, then query loop — could   */
                                         /* take MILLISECONDS or HOURS      */
        close(cfd);
    }   /* ← client #2 waits here the entire time client #1 is connected */
}

This is not a joke architecture — it is how you should start reasoning, and it already gets several things right: there is no concurrency, so there are no locks, no races, no isolation bugs. Every query is trivially serializable because everything is serial. SQLite is essentially this model (a library, one writer at a time) and it is the most widely deployed database on Earth.

ARC 04 · WHY IT FAILS

Head-of-line blocking is fatal for a database in particular

Every server architecture course tells you iterative servers suffer head-of-line blocking. For a database the problem is qualitatively worse than for, say, a web server, for three reasons that are worth internalizing because they justify the entire cost of the process model:

  • Sessions are stateful and long-lived. An HTTP request lasts milliseconds; a database session lasts minutes to days and holds server-side state — open transactions, cursors, prepared statements, temp tables, session GUCs. You cannot multiplex stateful sessions onto one handler without storing per-session state somewhere anyway.
  • Query duration is unbounded and unpredictable. The planner might estimate 10 ms and deliver 10 minutes (chapter 16 shows exactly how). A model that serializes clients turns one misestimated query into a full outage.
  • Queries block on I/O constantly. A cold-cache query is mostly pread() waits. An iterative server leaves the CPU idle while one client waits on disk and forty others wait on the CPU that is waiting on the disk. Utilization collapses to whatever one session can drive.
THE NUMBERS

Little's Law (you'll use it again in the Kafka course): with mean service time S and one server, throughput caps at 1/S. At S = 30 ms that is ~33 queries/sec total — one modern core can do thousands. And the tail is worse than the mean: one 8-second query in the stream doesn't lower average throughput by a little — it inserts an 8-second window where throughput is zero and every client's p99 latency includes someone else's analytics job.

So we need concurrency. In 1986 — and arguably still — there were three candidate shapes: an event loop in one process, threads in one process, or multiple processes. The next section eliminates them in order.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Event loop vs threads vs processes — the 1986 decision, re-derived

Candidate A: single-process event loop (the Redis/nginx shape)

Keep one process, but make it never block: put every client socket in select()/epoll/kqueue, and handle whichever connection has data. This is a superb architecture when request handling never blocks — which is precisely what a database cannot promise. A query blocks on disk reads, on locks held by other transactions, on sorts spilling to disk. In 1986 there was no usable async file I/O on Unix (there barely was until io_uring, 2019). Making the event loop truly non-blocking would have required rewriting every internal wait — buffer reads, lock waits, WAL flushes — as a state machine. That is a heroic engineering style (it is roughly what ScyllaDB does with seastar, with reactor-per-core), and it was simply unavailable to a 1986 research group. Rejected: the workload is blocking by nature.

Candidate B: threads in one process (the MySQL shape)

One process, one thread per connection. All memory is shared by default; the buffer cache is just a global variable. This is what MySQL chose in 1995 — with pthreads newly available — and it is genuinely cheaper: creating a thread costs microseconds, a context switch between threads doesn't flush the TLB the way a process switch can, and there is no per-process page-table overhead. But look at what "all memory shared by default" means for the five requirements from §1:

  • Fault containment inverts. One thread dereferencing a bad pointer can scribble on any other session's data structures before crashing — and when it does crash (or hits an assertion), the OS kills the entire process: every connection, the buffer cache, everything, with no supervisor left alive to restart it. In the process model, the same bug kills one process, and the damage radius of its private memory is architecturally zero.
  • Everything must be thread-safe. Every global variable, every cache, every third-party library (and PostgreSQL was designed for user-defined C extensions from day one — that was the research thesis!) must handle concurrent access. A single non-thread-safe extension crashes or corrupts all sessions.
  • 1986 reality: there were no portable threads at all. This candidate did not exist.

Candidate C: process per connection + explicit shared memory ✓

Fork a process per client. Each backend gets a private address space by default — session state, caches, and scratch memory are isolated for free, enforced by the MMU, not by programmer discipline. Then share only what must be shared, explicitly, by mapping one named region — the shared memory segment — into every process. The sharing boundary becomes a deliberate, auditable design decision per data structure rather than the default state of all memory.

THE CLINCHING ARGUMENT: CRASH SEMANTICS

Here is the argument that has kept the model alive for four decades. When a process dies, the kernel guarantees cleanup of its private resources — memory unmapped, file descriptors closed, and the parent gets a SIGCHLD with the exit status. The postmaster therefore has a reliable, kernel-enforced signal that a child died and how it died. A thread that corrupts memory and deadlocks gives you nothing: no signal, no cleanup, no living supervisor. PostgreSQL's famous behavior — "one backend crashed, so I'm restarting everyone" — is only possible because processes make death observable. §8 shows the exact code path.

ARC 06 · WHY THAT STILL HURTS

The bill arrives: what process-per-connection costs

The process model is not free, and you operate its costs every day. Be precise about where they come from — each one is a physical consequence, not a tuning oversight:

  • Connection establishment is heavyweight. Each connection = fork() (copy page tables, ~100–500 µs even with copy-on-write) + authentication round-trips + catalog cache warm-up: the new backend must load pg_class, pg_attribute, pg_proc entries for every relation it touches. First queries on a fresh connection are measurably slower. Total: ~1–10 ms of pure overhead per connection, thousands of times more than a thread.
  • Caches are duplicated N times. The relcache, syscache, and plan cache live in private memory. 500 backends touching the same 1,000 tables hold 500 copies of the same metadata. A thread model would hold one. This is pure architectural waste — often tens of MB per backend on schema-heavy workloads.
  • Idle connections are not free. Every live backend occupies a PGPROC slot that other backends must consider when computing MVCC snapshots (chapter 5). Before PostgreSQL 14 rewrote GetSnapshotData(), going from 100 → 5,000 idle connections measurably slowed active ones — the snapshot loop scanned every slot. (Andres Freund's PG14 work made snapshots mostly skip inactive backends; the principle — connection count taxes everyone — still holds.)
  • The kernel scheduler becomes your query scheduler. 2,000 runnable backends on 64 cores means the OS decides who runs, with no idea that one backend holds a hot LWLock everyone else needs. Result under overload: context-switch thrash and priority-inversion-like collapses (chapter 8 revisits this with lock queues).
THE INDUSTRY'S ANSWER — AND ITS ADMISSION

The ecosystem's fix is the external connection pooler (PgBouncer, pgpool, RDS Proxy): accept 10,000 client connections on an event loop (candidate A! — poolers can use it because they never run queries), and multiplex them onto ~50–200 real backends. It works so well it is considered mandatory at scale — and it is a standing admission that the process model's connection cost is real. Meanwhile the hackers list has an active, multi-year effort (started 2023 by Heikki Linnakangas) to make PostgreSQL multi-threaded; the main obstacles are ~2,000 global variables, the memory-context allocator, and every extension ever written — which is itself the best evidence of how deeply the process assumption is baked in.

So the final architecture is the process model plus the machinery that makes it survivable: a supervisor that never blocks, explicit shared memory, and a scorched-earth crash protocol. Let's meet it.

GONE BUT INSTRUCTIVE: THE STATS COLLECTOR

Until PostgreSQL 15 there was one more process: the statistics collector, which received activity counters from every backend over a UDP socket to localhost — because a process, unlike a thread, can't just write to a shared counter without shared-memory plumbing. PG 15 replaced it with a shared-memory stats subsystem built on dynamic shared memory. The episode is a perfect miniature of the process model's tax: what a threaded server does with an atomic increment, a process model did for 20 years with UDP datagrams.

ARC 08 · INTERNAL IMPLEMENTATION

From main() to the query loop: the real code path

Now the actual mechanism, at the level you'd need to patch it. Three pieces: (a) the startup and connection call chain, (b) the shared memory segment's creation and layout, (c) the signal machinery — including the crash protocol.

WHY AUTH RUNS IN THE CHILD — A DESIGN DECISION WORTH STEALING

The postmaster forks before reading a single byte from the client socket. Authentication — TLS handshake, password exchange, LDAP/RADIUS round-trips — all happens in the child. Consequence: a slow, hung, or malicious client can burn one child (bounded by authentication_timeout, default 60s) but can never stall the postmaster's accept loop. The tradeoff, visible in every connection storm: you pay the fork before you know whether the client is even legitimate. pg_hba.conf rejection is the cheapest thing a backend ever does — but it still cost a fork.

(b) Shared memory: one mmap, sliced by a boot-time allocator

During startup the postmaster calls CreateSharedMemoryAndSemaphores() (src/backend/storage/ipc/ipci.c), which asks every subsystem to estimate its size (CalculateShmemSize()), allocates one region — since 9.3 via mmap(MAP_SHARED|MAP_ANONYMOUS), with a vestigial System V segment kept only as a data-directory interlock — and then hands out pieces via ShmemInitStruct(). There is no shared-memory free(): the layout is fixed at boot, which is why changing shared_buffers needs a restart. Children inherit the mapping through fork() — same virtual addresses, so raw pointers into shared memory are valid in every process.

HARDWARE COROLLARY: HUGE PAGES & NUMA

A 32 GB shared_buffers mapped with 4 KB pages needs ~8.4M page-table entries — per process, because each backend has its own page table for the shared mapping. Hundreds of backends × millions of PTEs = gigabytes of page tables and constant TLB misses. huge_pages=on (2 MB pages) cuts PTE count 512× and measurably improves large-memory boxes. On multi-socket NUMA machines the segment is physically allocated on first touch — mostly by the postmaster's socket — so backends on the other socket pay remote-memory latency for every buffer access. This is why chapter 9's buffer manager cares about which core runs your backend.

(c) Signals: the postmaster's control plane

Processes can't call each other's functions, so PostgreSQL's control plane is Unix signals — with a strict discipline: signal handlers only set flags; real work happens synchronously in the main loop (this avoids async-signal-safety bugs — handlers can't safely malloc, take locks, or write WAL).

WHY NUKE EVERYONE? THE HONEST ANSWER

Because the postmaster cannot prove innocence. The dead backend had write access to the buffer pool, the lock table, and the ProcArray. If it died mid-update inside a critical section — holding a spinlock, half-way through linking a buffer into the free list — shared memory is now a lie. Any surviving backend that reads that lie could write corrupt pages to disk, converting a transient crash into permanent data corruption. Killing every child and rebuilding shared memory from WAL trades minutes of availability for a guarantee of integrity. Note the precise trigger: it is not the SQL error, not even elog(FATAL) (clean exits, code 0/1) — it is abnormal termination: signals (SIGKILL, SIGSEGV) or exit codes ≥ 2. This is why kill -9 on a backend restarts the cluster but pg_terminate_backend() (SIGTERM → clean exit) does not — a distinction you can act on in production, and the simulator in §15 lets you feel it.

ARC 09 · TRADEOFFS

The same problem, five ways: comparative anatomy

Every serious database faced this exact decision. The spread of answers tells you there is no dominant strategy — only different placements of the same costs:

SYSTEMEXECUTION MODELWHAT THEY BOUGHTWHAT THEY PAID
PostgreSQLProcess per connection + explicit shm fault isolation extension safety observable death heavy connections duplicated caches needs pooler

Read the table as a proof by exhaustion: the isolation/efficiency tradeoff cannot be dodged, only priced. PostgreSQL priced it in 1986 currency — memory was small but bugs were fatal, and the project's core bet was user-extensibility (custom types, custom functions, in C!). Process isolation is what makes it survivable to run strangers' C code in your database. That bet paid off: PostGIS, TimescaleDB, pgvector, and citus exist because a buggy extension usually costs a backend, not the cluster.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

The model's performance envelope, from first principles. Costs per connection:

  • fork(): ~100–500 µs. Copy-on-write means memory isn't copied — but page tables are, and that cost scales with the parent's mapped memory (large shared_buffers → slower forks, unless huge pages shrink the table).
  • Backend warm-up: catalog cache misses on first use of each relation — first query on a fresh connection commonly 2–10× slower than steady-state.
  • Per-backend RSS: ~1–3 MB baseline, growing with relcache/plan cache — 10–50 MB each is routine on wide schemas. 500 idle connections can quietly hold 10+ GB of duplicated cache.
  • Work memory is per-operation, per-backend: work_mem (default 4 MB) can be used by each sort/hash node in each running query. Peak memory ≈ active_backends × plan_nodes × work_mem — the classic OOM equation.
  • Context switches: ~1–5 µs each; with thousands of runnable backends, switching + TLB pressure can eat double-digit % of CPU before any query work happens.

Drag the connection count and watch throughput follow the classic hump — rising with parallelism, collapsing under scheduling and contention overhead. Toggle the pooler to see why the fix works:

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: The OOM-killer cascade

Linux overcommits memory by default. A report query fans out hash joins, each allocating work_mem; RSS climbs; the kernel's OOM killer wakes and — scoring by memory — SIGKILLs the fattest backend. SIGKILL is abnormal termination: the postmaster runs the crash protocol, every connection drops, recovery replays WAL. The application's connection pool stampedes back, forking hundreds of backends into a cold cache, and the spike re-triggers the OOM. A one-query problem became a site outage loop. Fixes, in order of leverage: cap concurrency at the pooler; set vm.overcommit_memory=2 so allocations fail (a caught, per-backend FATAL) instead of getting killed; protect the postmaster with oom_score_adj (the PG docs ship instructions); right-size work_mem against the peak-memory equation from §10.

Incident 2: The failover reconnect storm

A primary fails over. Ten thousand app-server connections all reconnect within seconds — each one a fork + TLS handshake + auth + cold catalog caches, against a replica that is simultaneously replaying WAL. CPU pins at 100% in connection setup; health checks time out; the orchestrator concludes this node is bad too. This is why serious deployments put PgBouncer (or RDS Proxy) between apps and Postgres, add reconnect jitter, and keep max_connections modest: the database's cliff is exactly where the process model's per-connection cost says it is. GitLab's public architecture docs — PgBouncer tiers in front of every Postgres cluster — are a canonical example, and Instagram was famously running PgBouncer within its first scaling year.

Incident 3: "FATAL: remaining connection slots are reserved"

Under load, connections hit max_connections. The last superuser_reserved_connections (default 3) slots are held back for superusers — which is the only reason the DBA can still get in to run pg_terminate_backend(). Two operational lessons hide here: (1) the limit exists because each slot is a pre-allocated PGPROC in fixed shared memory — it cannot stretch at runtime; (2) terminate with SIGTERM (clean, one session) — a panicked kill -9 on a "stuck" backend converts one bad session into a full cluster restart. You now know exactly why.

The four functions that define the model, simplified from PostgreSQL 16/17 sources but faithful in structure and naming. First, the boot sequence:

Cpostmaster.c — PostmasterMain(), the parts that matter
void
PostmasterMain(int argc, char *argv[])
{
    /* Signal discipline: handlers ONLY set volatile flags.
     * All real work happens synchronously in ServerLoop.       */
    pqsignal(SIGHUP,  handle_pm_reload_request_signal);
    pqsignal(SIGCHLD, handle_pm_child_exit_signal);   /* → reaper  */
    pqsignal(SIGINT,  handle_pm_shutdown_request_signal);

    /* Read postgresql.conf into GUC variables. */
    SelectConfigFiles(userDoption, progname);

    /* Listen sockets BEFORE shared memory: if the port is
     * taken, fail before allocating gigabytes.                 */
    foreach(addr, ListenAddresses)
        StreamServerPort(addr, PostPortNumber, &ListenSockets);

    /* ONE region: every subsystem declares its size, then
     * mmap(MAP_SHARED|MAP_ANONYMOUS) the sum. Children will
     * inherit this mapping — same virtual addresses — so raw
     * pointers into shared memory work in every process.       */
    reset_shared();        /* → CreateSharedMemoryAndSemaphores() */

    /* First child: the startup process. It replays WAL from
     * the last checkpoint. Only when it signals completion do
     * we open the doors — this IS crash recovery (ch. 11).     */
    StartupPID = StartChildProcess(B_STARTUP);

    ServerLoop();          /* never returns */
}

The loop itself. Notice what is absent: no query logic, no reads from client sockets, no shared-memory data access. Boring on purpose:

Cpostmaster.c — ServerLoop() + BackendStartup()
static int
ServerLoop(void)
{
    for (;;)
    {
        /* Sleep until: a socket is ready, a timer fires, or a
         * signal flag was set. (select() for 30 years; a
         * WaitEventSet — epoll/kqueue — since PG 16.)          */
        nevents = WaitEventSetWait(pm_wait_set, timeout, events, ...);

        foreach(ready listen socket)
        {
            Port *port = ConnCreate(listen_sock);   /* accept() */
            BackendStartup(port);                   /* fork()!  */
            StreamClose(port->sock);  /* parent drops its copy;
                                       * the fd lives on in the child */
        }

        if (pending_pm_child_exit)      /* SIGCHLD flag set? */
            process_pm_child_exit();    /* reap, judge, react */
    }
}

static int
BackendStartup(Port *port)
{
    Backend *bn = malloc(sizeof(Backend));    /* tracking slot */

    pid = fork_process();
    if (pid == 0)      /* ─────────── child ─────────── */
    {
        ClosePostmasterPorts(false);  /* drop listen sockets   */
        BackendInitialize(port);      /* startup packet, TLS,
                                       * pg_hba.conf, AUTH — all
                                       * here, in the child      */
        BackendRun(port);             /* → PostgresMain(): the
                                       * query loop. No return.  */
    }
    /* ─────────── parent: just bookkeeping ─────────── */
    bn->pid = pid;
    dlist_push_head(&BackendList, &bn->elem);
}

And the reaper — the code that decides between "a session ended" and "burn it all down." This is the crash protocol from §8(c) in its actual shape:

Cpostmaster.c — the reaper and HandleChildCrash()
static void
process_pm_child_exit(void)
{
    while ((pid = waitpid(-1, &exitstatus, WNOHANG)) > 0)
    {
        /* Exit code 0 or 1 = controlled exit (even FATAL errors
         * exit(1) after proper cleanup). Anything else — a
         * signal, an assert, exit(2)+ — is a crash.            */
        if (EXIT_STATUS_0(exitstatus) || EXIT_STATUS_1(exitstatus))
            CleanupBackend(pid, exitstatus);      /* one funeral */
        else
            HandleChildCrash(pid, exitstatus, ...); /* everyone's */
    }
}

static void
HandleChildCrash(int pid, int exitstatus, const char *procname)
{
    ereport(LOG, (errmsg("%s (PID %d) was terminated by signal %d",
                          procname, pid, WTERMSIG(exitstatus))));

    /* The dead child could have died holding a spinlock or
     * mid-write in shared memory. We cannot verify billions of
     * bytes of shared state — so we assume the worst.          */
    TerminateChildren(SIGQUIT);   /* quickdie(): no cleanup,
                                   * do NOT touch shared memory  */
    FatalError = true;

    /* Once all children are reaped, the state machine runs:
     *   reset_shared()               — brand-new shared memory
     *   StartChildProcess(B_STARTUP) — WAL replay from last
     *                                  checkpoint (chapter 11)
     * Clients see: "the database system is in recovery mode".  */
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Flags, not work, in signal handlers. Only async-signal-safe code may run in a handler; the flag + main-loop pattern makes every state change happen at one auditable place. 2. Judge children by exit status, not by content. The postmaster never inspects shared memory to decide if it's corrupt — undecidable — it uses the kernel's ground truth about how the child died. 3. The supervisor holds no locks. The postmaster can always run the crash protocol because it can never be a participant in the deadlock or corruption it is cleaning up. Erlang/OTP supervisors, Kubernetes controllers, and systemd all rediscovered this shape.

Finally, note what the child becomes: PostgresMain() in tcop/postgres.c — a loop of ReadCommand() → exec_simple_query() that is the subject of chapters 15–17. The EXEC_BACKEND path (Windows, no fork()) achieves the same result by CreateProcess + re-attaching shared memory at the same address and restoring ~100 global variables from a parameter file — a 500-line reminder of how much state fork() silently copies for free.
