RUST · CHAPTER 06 BEGINNER

Structs, Enums &
Pattern Matching

Every real program needs two things: a way to bundle related values together, and a way to say "this is one of several possible shapes of data." Rust's answer — struct for the first, enum for the second — looks familiar coming from C or Java, and is quietly one of the most powerful type-system features in any mainstream language. This chapter builds both from first principles, meets the two enums you will use every single day (Option<T> and Result<T,E>), and ends with the compiler behavior that makes it all safe: match's exhaustiveness check.

ARC 01 · THE PROBLEM

Two problems every program has: grouping, and "one of several kinds"

Almost everything you model in code reduces to two separate needs. The first is grouping: a point has an x and a y; a user has a name and an age and an email — related values that only make sense together. The second is choice: a shape is a circle or a rectangle or a triangle; a network message is a connect request or a data frame or a disconnect notice — exactly one of several distinct possibilities, often each carrying different data.

Most languages you've used solve the first problem well — a struct in C, a class in Java, an object literal in JavaScript, all bundle fields together with no drama. The second problem is where languages diverge sharply, and where a huge, well-documented class of real bugs lives. If your language's only tool for "one of several kinds" is a loose tag (an int, a string, an enum of bare integer constants) plus separately-declared fields for each kind's data, nothing connects the tag to which fields are actually valid. The tag and the data can drift apart, and the type checker — if there is one — has no way to notice.

  • A struct is a product type — you always have the x and the y.
  • An enum, done right, is a sum type — you have a circle's radius or a rectangle's width-and-height, never a meaningless mix of both, and the compiler always knows which.

Rust's struct and enum are the two halves of this same problem, and they were designed together with match — a control-flow construct that the compiler statically proves handles every possibility. That last part is the chapter's real payload: not "Rust has enums," which is unremarkable, but "Rust's compiler will not let you forget a case," which is the property most languages cannot offer you at all.

WHY THIS MATTERS FOR THE NEXT 16 CHAPTERS

Once you can name "this data is exactly one of these N shapes, and the compiler enforces that every consumer handles all N," you have the vocabulary for state machines (an HTTP connection is Connecting or Open or Closed), for error handling (chapters 7 and 13 are built entirely on the enum you'll meet today, Result<T,E>), for collections (chapter 7's Vec::get returns Option<&T>, not a crash), and even for the trait objects and generics of chapter 8. Structs and enums are not "syntax to learn" — they are the material every later chapter is built from.

ARC 02 · HISTORICAL CONTEXT

From the billion-dollar mistake to a hard compiler error

Rust's enum-and-match pair did not appear from nowhere. It is the direct descendant of a 50-year academic lineage — algebraic data types from the ML family of languages — arriving in a systems language for the first time at 1.0, right next to the ownership model from chapter 4. DEEP CONTEXT · WHY "SUM TYPE"?

In type theory, if type A has a possible values and type B has b possible values, a struct { a: A, b: B } (a product) has a × b possible values — every combination is reachable. An enum Either { A(A), B(B) } (a sum) has a + b possible values — you get an A's worth of possibilities or a B's worth, never both at once. This arithmetic is exactly why the naive "tag plus loose optional fields" approach in §3 is wrong: it accidentally builds a product (every field independently present or absent) to represent something that is really a sum (exactly one case at a time) — and the product has far more possible values than the sum, most of them nonsensical.

ARC 03 · NAIVE SOLUTION

Attempt #1: a tag, and some fields that may or may not apply

Derive it honestly, the way most people actually reach for it the first time. You need to represent a Shape that's either a circle or a rectangle. In C, without a real sum type, the standard pattern is a struct holding a tag and an (anonymous) union of each variant's fields:

Cshape.c — the tagged-union strawman (compiles under C11)
enum shape_tag { CIRCLE, RECTANGLE };

typedef struct {
    enum shape_tag tag;
    union {
        struct { double radius; }          circle;
        struct { double width, height; }   rectangle;
    };
} shape_t;

double area(shape_t *s)
{
    switch (s->tag) {
        case CIRCLE:    return 3.14159265 * s->circle.radius * s->circle.radius;
        case RECTANGLE: return s->rectangle.width * s->rectangle.height;
    }
    /* no default, no return here — gcc -Wswitch MIGHT warn if a case is missing,
     * but only if you remembered to pass -Wswitch, and it is a WARNING, not an error. */
}

int main(void)
{
    shape_t s;
    s.tag = CIRCLE;
    s.rectangle.width  = 3.0;   /* wrong union member for tag == CIRCLE */
    s.rectangle.height = 4.0;
    printf("%f\n", area(&s));    /* reads circle.radius as reinterpreted bytes of
                                 * width/height: undefined behavior, not a crash */
    return 0;
}

This compiles cleanly and runs — that's the trap. Nothing in the type system connects tag to which union member is valid; that connection lives only in the programmer's discipline. Beginners moving to Rust often reach for a structurally identical anti-pattern that does compile, just with Rust's own optional type standing in for "maybe present":

Rustshape.rs — compiles, but the same disease
struct Shape {
    is_circle: bool,
    radius: Option<f64>,
    width: Option<f64>,
    height: Option<f64>,
}

fn area(s: &Shape) -> f64 {
    if s.is_circle {
        std::f64::consts::PI * s.radius.unwrap() * s.radius.unwrap()
    } else {
        s.width.unwrap() * s.height.unwrap()
    }
}

fn main() {
    // Nothing stops this: is_circle says "circle" but width/height were set instead.
    let bad = Shape { is_circle: true, radius: None, width: Some(3.0), height: Some(4.0) };
    println!("{}", area(&bad));   // panics: called `Option::unwrap()` on a `None` value
}

rustc has no complaint about this program — every type checks. Shape really can hold is_circle: true next to radius: None; the language sees four independent fields, not one coherent choice. The bug only appears at runtime, and only if the exact wrong combination gets exercised. §4 makes that "only if" precise, and §5 fixes it structurally.

ARC 04 · WHY IT FAILS

Quantifying "illegal states are representable"

Two distinct failure classes come out of §3's shape, and it's worth separating them because Rust attacks them differently:

  • The C version is memory-unsafe. Reading circle.radius after writing rectangle.width/height reinterprets the same bytes as a different type — this is exactly CWE-843, Type Confusion, a perennial entry on real vulnerability lists, and the root cause behind a long, ongoing string of real CVEs in C/C++ codebases that use tagged unions for performance (JavaScript-engine and media-parser type-confusion bugs are a recurring category in browser security advisories for exactly this reason: a tag and a payload that the type system does not keep in sync).
  • The naive Rust version is memory-safe but logically wrong. No undefined behavior is possible — Option::unwrap() on None is a checked panic, not a wild memory read. But the underlying design flaw — a tag that doesn't structurally constrain which fields exist — is identical, and it still produces wrong programs, just ones that fail loudly instead of silently.

Now quantify the real problem: how much bigger is the space of representable-but-meaningless states than the space of actually-valid ones? Every independent bool/Option field you bolt on to fake a sum type doubles the number of representable combinations, while the number of genuinely valid shapes stays fixed. A NAME FOR THIS: "PARSE, DON'T VALIDATE"

This is the exact failure the Rust community's well-known phrase targets: if your type can represent invalid data, every function that touches it must re-check validity, forever, at every call site — and the one time someone forgets, that's your bug. The fix is not "add more runtime checks." It's "change the type so the invalid states have nowhere to live." That's precisely what an enum with data-carrying variants buys you, for free, at compile time. §5 builds it.

WHAT ACTUALLY CHANGED

Nobody added a runtime check. Shape::Circle(f64) physically cannot carry a width and a height — the type has one field, a radius, full stop. The compiler enforces the sum-type arithmetic from §2 (exactly one variant's data, never more) at the level of what you're even allowed to write, and then match's exhaustiveness check (real error code E0004, which you'll trigger yourself in §15) enforces that every consumer of the type handles every variant. ARC 06 · WHY THAT STILL HAS COSTS

Be honest: this isn't free

Enums and exhaustive matching are a genuinely good default, but they have real, non-hypothetical costs you will hit in your first week of writing Rust:

  • Adding a variant is a real refactor, everywhere. Add a fourth Shape variant and every existing match over Shape without a wildcard arm now fails to compile with E0004 — which is the safety net working as designed, but it does mean a "small" change to a widely-used enum can ripple into dozens of files in one commit. Compare to a dynamically-typed language, where adding a new case silently does nothing until (if ever) someone notices the missing branch in production.
  • Recursive enums need explicit indirection. The classic linked-list shape, enum List { Cons(i32, List), Nil }, does not compile — rustc must know every type's size at compile time, and a List containing a List containing a List… has no finite size. rustc's real diagnostic is error[E0072]: recursive type List has infinite size, and the fix — Cons(i32, Box<List>) — is exactly the kind of "why do I need this Box thing" question that trips up beginners before smart pointers are covered (chapter 12).
  • Matching interacts with ownership, and that interaction is not obvious at first. Matching a value you own moves the fields you bind by value out of it; matching by reference (match &x or the match-ergonomics behavior you'll see in §8) borrows instead. Beginners regularly hit "error[E0382]: use of moved value" the first time they match an owned enum twice, a direct consequence of chapter 4's move semantics meeting today's material head-on.
  • It is more verbose than duck typing, and rustc is not free to compile. A quick script in Python that just assumes a dict has the keys it expects has no equivalent ceremony. You are trading upfront structure and compile time for the runtime guarantee — a trade this whole course keeps returning to.

THE RULE OF THUMB

Reach for a struct when you always have all of a fixed set of fields at once. Reach for an enum the moment you catch yourself writing a comment like "// only valid if kind == X" next to a field, or adding a bool/tag field whose value determines which other fields matter. That sentence is the tell that you're modeling a sum type with a product type's tools.

(b) What's actually in memory: the discriminant, and niche optimization

An enum's value in memory is, conceptually, a hidden integer tag (the discriminant) next to enough bytes for the largest variant's payload. But Rust's default enum layout is unspecified — not guaranteed by the language — which frees rustc to apply a real, load-bearing optimization: if a payload type has bit patterns it can never legally hold (a reference is never the null address; a Box<T> is never null; a std::num::NonZeroU32 is never zero), rustc can store None inside that impossible bit pattern instead of adding a separate tag byte. This is niche-filling optimization, and the standard library's docs explicitly guarantee it for Option<&T>, Option<Box<T>>, Option<fn()>, and the Option<NonZero*> family. Read this as the same proof-by-exhaustion pattern the rest of this course keeps surfacing: every one of these languages solved a version of "one of several kinds," but only a few made the compiler responsible for catching a forgotten case, and fewer still made it a hard error instead of an opt-in lint.

ARC 10 · PERFORMANCE & SAFETY CHARACTERISTICS

Dispatch cost: what a naive tag check costs vs. what match compiles to

A common worry: "doesn't checking a tag on every access cost something?" The honest answer has two parts. First, §8's niche optimization means many Option<T> values cost zero extra bytes over the bare payload. Second, match over an enum's discriminant is exactly the same operation a hand-written C switch compiles to — and when the compiler's backend (LLVM, in rustc's case) judges the discriminant values dense enough, it emits a single indirect jump table: one memory load, one jump, regardless of how many variants exist. Contrast that with the naive habit of tagging with a string and comparing it in an if/else chain — which is genuinely O(n) in the number of cases, because string comparison can't be turned into a jump table at all. The curve's shape is the point: match is never worse than a hand-rolled chain, and is very often a small constant number of instructions no matter how many variants your enum grows to.

ARC 11 · REAL-WORLD INCIDENTS

Three stories that are really about this chapter

Incident 1: Tony Hoare's "billion-dollar mistake"

In a 2009 QCon London keynote, Tony Hoare — who added the null reference to ALGOL W in 1965 "simply because it was so easy to implement" — called it his billion-dollar mistake, citing the sheer volume of null-pointer bugs it produced across the following four decades of software built on languages that inherited the idea. NullPointerException (Java), null/undefined confusion (JavaScript), and null-pointer segfaults (C) are, structurally, the exact same bug: a value of type T that can secretly also be "nothing," with every single use site responsible for remembering to check. Option<T> doesn't patch this — it deletes the category. There is no hidden "nothing" state inside a plain T; if a value might be absent, its type says so, and §4's illegal-state argument applies directly: the compiler, not convention, keeps the "might be absent" bit attached to the value everywhere it travels.

Incident 2: type confusion as a recurring browser CVE category

Type confusion (CWE-843) — reading memory written as one type through a pointer or reference of a different, incompatible type — has been a recurring root cause in security advisories for JavaScript engines and media parsers for years, precisely because these codebases are written in C/C++ and use hand-rolled tagged unions for performance in exactly the shape shown in §3. It remains a fixture on aggregate weakness-ranking lists (CWE's own Top 25 has featured it repeatedly) for the same structural reason this chapter opened with: nothing in C's type system connects a discriminant to which union member is currently valid. A Rust enum makes the analogous mistake a compile error instead of a security advisory — if you stay in safe Rust; chapter 17 revisits exactly how unsafe can reopen this exact hole on purpose.

Incident 3: Discord's 2020 move off Go, and why sum types were part of the pitch

Discord's engineering team published a widely read 2020 postmortem ("Why Discord is switching from Go to Rust") explaining their decision to rewrite the "Read States" service — the thing that tracks which messages you've seen — in Rust after garbage-collection pause spikes caused periodic latency cliffs under load. Memory management was the headline reason, but the post is explicit that Rust's stronger type system, including exhaustive enums for representing service state, reduced an entire class of "we forgot to handle a case" incidents that had shown up in the Go version's more permissive interface-based modeling. It's a useful real-world data point that this chapter's "compiler catches a forgotten case" property is not just a teaching device — production teams cite it as a reason to migrate.

ARC 13 · SOURCE CODE WALKTHROUGH

Reading the real thing: Option and Result in core

Option<T> and Result<T,E> are not compiler built-ins with hidden magic syntax — they are ordinary public enums defined in library/core, the dependency-free foundation beneath the standard library. Here is where they live, and their real (lightly simplified) declarations:

library/core/src/
├── ● option.rs — Option<T>: None | Some(T) — the type that replaces null
│ └── option/iter.rs — IntoIterator for Option<T> (yields 0 or 1 items — chapter 7 uses this)
├── ● result.rs — Result<T,E>: Ok(T) | Err(E) — the type that replaces exceptions
└── convert/mod.rs — From/Into: what the `?` operator (chapter 13) uses to convert error types
your_crate/src/
├── main.rs — entry point
└── shapes.rs — the Shape enum + impl block built in §5 / §8
Rustlibrary/core/src/option.rs — simplified, but the real shape
// Several derive/cfg/doc-attribute lines omitted for space; the variants
// and their names are exactly as shipped.
#[derive(Copy, Clone, PartialEq, Eq, PartialOrd, Ord, Debug, Hash)]
#[rustc_diagnostic_item = "Option"]
pub enum Option<T> {
    /// No value.
    None,
    /// Some value of type `T`.
    Some(T),
}
Rustlibrary/core/src/result.rs — simplified, but the real shape
#[derive(Copy, Clone, PartialEq, Eq, PartialOrd, Ord, Debug, Hash)]
#[must_use = "this `Result` may be an `Err` variant, which should be handled"]
pub enum Result<T, E> {
    /// Contains the success value.
    Ok(T),
    /// Contains the error value.
    Err(E),
}

Two details worth noticing. First, Option and Result derive ordinary traits like Debug and PartialEq the exact same way your own Shape can — there is no special-cased "built-in enum" concept in the language, only an enum that happens to ship in every crate's prelude automatically. Second, #[must_use] on Result is a real, load-bearing attribute: it's why parse_age(input); without doing anything with the return value produces a compiler warning (not an error) telling you an Err might be silently ignored — the standard library leaning on the same "make mistakes visible" philosophy as E0004, just via a lint instead of a hard stop.

Rustyour_crate/src/shapes.rs — this chapter's running example, complete
enum Shape {
    Circle(f64),
    Rectangle(f64, f64),
    Triangle(f64, f64, f64),   // base, height, third side
}

impl Shape {
    fn area(&self) -> f64 {
        match self {
            Shape::Circle(radius)            => std::f64::consts::PI * radius * radius,
            Shape::Rectangle(width, height)  => width * height,
            Shape::Triangle(base, height, _) => 0.5 * base * height,
        }
    }
}

fn main() {
    let shapes = vec![Shape::Circle(2.0), Shape::Rectangle(3.0, 4.0), Shape::Triangle(6.0, 2.0, 5.0)];
    for s in &shapes {
        println!("{:.2}", s.area());
    }
}
