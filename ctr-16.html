CONTAINER INTERNALS · CHAPTER 16 · CAPSTONE

Build a Container Runtime
From Scratch

Fifteen chapters have described what dockerd, containerd, runc, conmon, and crun do to a process on your behalf. This chapter takes those verbs away from them. You will call unshare() yourself, write your own bytes into /sys/fs/cgroup/.../memory.max, pivot_root into a filesystem tree you built by hand, drop capabilities out of your own bounding set, and install a seccomp-bpf filter that can no longer be undone — in that exact order, because the kernel does not forgive the wrong order. The payoff isn't a toy: by the end, a real binary runs in real isolation, enforced by the same eleven syscalls runc's nsexec uses, and you can point at the precise place where your hand-rolled runtime stops being "a container" and becomes "an OCI-compliant one" — which is exactly the gap Docker and Podman spent a decade closing, in different ways, documented at every layer across this course.

You will be able toSequence the exact syscalls — clone()/unshare(), uid/gid mapping, pivot_root, cgroup writes, capset(), seccomp install, execve() — and explain why reordering any two of them breaks or weakens isolation.
You will understandPrecisely which of the four isolation primitives (namespaces, cgroups, capabilities, seccomp) is responsible for which specific guarantee, and why a runtime offering only three of the four is not "mostly safe" — it is missing an entire threat class.
You will predictWhat a hand-built runtime is still missing to be genuinely OCI Runtime Spec compliant, and why "it ran my binary" is a dangerously low bar to call a runtime finished.
You will simulateA working state machine that enforces cgroup limits with real OOM/throttle logic, denies privileged syscalls by capability and by seccomp filter with real EPERM/ENOSYS semantics, and diffs your runtime's process tree against simulated Docker and Podman runs of the identical workload.
ARC 01 · THE PROBLEM

"A container" is not a kernel object. Prove it by building one without Docker or Podman.

Grep the Linux kernel source for struct container. It doesn't exist. There is no syscall named container_create(), no /proc/containers, no data structure the scheduler consults to ask "is this process containerized?" What you have been calling a container for fifteen chapters is a label for a process that happens to have five independent, unrelated kernel mechanisms applied to it at once: it was clone()d or unshare()d into a set of namespaces (chapters 2–4), it was placed in a cgroup with resource limits (chapter 5), its root filesystem was swapped out from under it via pivot_root onto an overlay of image layers (chapter 6), its capability bounding set was cut down from root's ~40 to a curated 14 (chapter 7), and a seccomp-bpf filter plus an LSM policy now stand between it and roughly 300 of the kernel's ~450 syscalls (chapter 8). Docker and Podman are, underneath all their tooling, opinionated automation around exactly those five primitives, plus an image format (chapter 10) and a wire protocol for fetching one (chapter 11).

This chapter's exercise is the sharpest test of whether you actually understand that claim: if you called the right ~20 syscalls yourself, in the right order, would you have "a container"? What exactly would be missing compared to what docker run or podman run hands you? And — the detail every tutorial-blog "build your own Docker in 100 lines" skips — does the order of those syscalls matter, or is it just style? It matters enormously. Get it wrong and you don't get a crash; you get a container that looks isolated in a demo and is not isolated at all under a hostile workload. That gap — between code that runs the happy path and code that is actually safe to hand an adversarial payload — is the entire reason runc is tens of thousands of lines long, crun is tens of thousands of lines long, and this chapter's runtime, honest about its scope, will still fall well short of both.

WHAT "FROM SCRATCH" MEANS HERE, PRECISELY

You are not writing a kernel patch — every primitive you use (unshare(), cgroup v2 files, capset(), seccomp()) already exists and is exactly what runc and crun call. "From scratch" means: no docker, no podman, no runc, no crun, no OCI config.json — just a small C-shaped program (rendered here as pseudocode and, in §15, as a live JS state machine) that drives the same kernel interfaces those tools drive, so that every claim this course has made about mechanism becomes something you can point to in code you traced yourself.

ARC 02 · WHY THE BUILD ORDER IS NOT ARBITRARY

Six kernel landmarks that turned "isolate a process" into a spec-mandated sequence

DEEP CONTEXT · WHY THE OCI SPEC CODIFIES A LIFECYCLE, NOT JUST A CONFIG FORMAT

The single most underrated design decision in the OCI Runtime Spec (chapter 9) is that it separates create from start. create must set up every namespace, mount, and cgroup — without running the user's process yet — so that an external tool (a CNI plugin wiring a veth, chapter 3; a systemd unit recording the PID, chapter 14) can act on a fully-isolated-but-not-yet-running container. A runtime that fuses "set up" and "run the workload" into one atomic step, as this chapter's naive first attempt will in §3, cannot be composed with anything else in the ecosystem — which is precisely why that two-phase lifecycle exists as a spec requirement and not a suggestion.

ARC 03 · NAIVE SOLUTION

Attempt #1: the "container in 40 lines of C" blog-post special

This is the version that actually gets written and shared, because it looks convincing: it changes the root directory, it forks, it runs a shell, and the shell's prompt genuinely looks different. Derive it honestly before tearing it apart — every one of its omissions is a chapter you have already read.

Cminirun_v0.c — the strawman, annotated
int main(int argc, char **argv)
{
    /* "isolation": change the filesystem root. That's it. */
    chroot("/var/lib/minirun/rootfs");
    chdir("/");

    /* fork so the shell we exec doesn't replace this process */
    if (fork() == 0) {
        execve("/bin/sh", argv, environ);   /* inherits: EVERY namespace,
                                               * EVERY capability, NO cgroup,
                                               * NO seccomp filter — all host  */
    }
    wait(NULL);
    return 0;
}

It compiles. It runs. Inside the shell, ls / shows the fake rootfs, not the host's — so it feels like a container. Nothing else about the process changed: no new PID namespace, no new mount namespace (the chroot happened in the host's mount namespace), no network namespace, no cgroup, no capability drop, no seccomp filter. This is, almost exactly, what chroot(8) gave Unix administrators in 1979 — chapter 1's starting point — with none of the forty-five years of primitives layered on top that this course has spent fifteen chapters deriving.

ARC 04 · WHY IT FAILS

Four failures, each quantified, each a chapter you already have the fix for

Run minirun_v0 and enumerate exactly what an occupant of that shell can do. Every item below is not "bad practice" — it is a specific, exploitable capability the naive version left switched on by omission.

  • Total PID and process visibility (no PID namespace). ps aux inside the "container" lists every process on the host — the database's PID, the SSH daemon's PID, other tenants' workloads. Worse, kill(-1, SIGTERM) from inside can signal any process the caller's UID can reach, which as UID 0 (we never dropped privilege) is every process on the box. Zero containment, not partial.
  • chroot is escapable with nothing more exotic than an open file descriptor (classic 1990s technique). Because we never called the namespace-aware, one-way pivot_root (chapter 6), a process that opened a directory before calling chroot() — or that still holds CAP_SYS_CHROOT and can call chroot() a second time — can escape: mkdir("x"); chroot("x"); for (i=0;i<256;i++) chdir(".."); chroot("."); walks .. past the chroot's root (chroot changes the root pointer, not the process's notion of "top of tree"), eventually reaching the real host /. This is exactly why pivot_root was added in kernel 2.3.41 (1999) — it swaps the mount at / itself and, combined with a mount namespace, leaves no host directory reachable via any chain of ...
  • No cgroup means no resource isolation at all. A workload that allocates memory in a loop is scored by the systemwide OOM killer against every other process on the host — chapter 5's whole point, that a cgroup scopes the OOM killer's blast radius to one group of processes, doesn't apply because there is no cgroup. One runaway workload can and will take down unrelated host services.
  • Full capability set, full syscall surface. We never called capset() or prctl(PR_CAPBSET_DROP, …), so the process retains all ~40 capabilities including CAP_SYS_ADMIN (mount arbitrary filesystems, including /proc with permissive options) and CAP_SYS_MODULE (load a kernel module). We never installed a seccomp filter, so all ~450 syscalls on this kernel are reachable, including unshare(), keyctl(), and ptrace(). This process is not "a slightly weaker root" — for every practical purpose that matters to an attacker, it is root.
THE NUMBERS

Namespaces alone (no cgroup, no cap drop, no seccomp) block zero privilege escalations that don't depend on visibility — they only change what the process can see, not what it's permitted to do once it sees it. A process with an intact capability set and an unfiltered syscall table that merely can't see the host's PIDs is still one mount(MS_BIND) of a host path away from reading anything on disk it has DAC permission for. Isolation is a conjunction of four independent gates, not a single switch — §7 diagrams exactly which gate blocks which class of attack, because §16 will ask you to defend that claim for the whole course.

ARC 05 · THE CORRECT BUILD ORDER

Eight steps, and the order is the design

Fix the naive version by adding every primitive this course covered — but the fix isn't just "add four more syscalls." Two of the four gates, done in the wrong position, actively sabotage the ones after them. Step through the corrected sequence; each step's caption explains why it cannot move.

minirun's actual construction orderSTEP-BY-STEP
THE ONE RULE THAT EXPLAINS THE WHOLE ORDERING

Every step that reduces what the calling process itself can still do — dropping capabilities, installing the seccomp filter — must happen last, immediately before execve(), because the calling process is bound by its own restrictions the instant it applies them. Every step that needs a privilege you're about to give up — mounting the rootfs and calling pivot_root needs CAP_SYS_ADMIN; writing cgroup interface files needs write access to /sys/fs/cgroup — must happen before you drop that privilege. Reorder steps 6/7 before step 3 and the mount setup gets EPERM against its own filter. That single ordering constraint is why runc's nsexec.c and crun's libcrun/container.c read, superficially, almost identically to the deck above — there is only one sequence that actually works.

ARC 06 · WHY THAT STILL COSTS

You can run a binary in real isolation now. You still don't have an OCI runtime.

Sit a security reviewer in front of minirun after §5's fix and they will find, correctly, that it is not safe to hand to a multi-tenant scheduler or a CI system running arbitrary Dockerfiles. None of these gaps are exotic — they are the specific line items the OCI Runtime Spec added because someone shipped a runtime without them:

  • No create/start split. §2's callout already flagged this: fusing setup and exec into one call means nothing external — no CNI plugin, no bind-mount added post-hoc, no monitoring agent — can act on the container's namespaces before the workload starts running inside them.
  • No masked or read-only paths. The real default profile masks /proc/kcore (a window onto raw physical memory even from inside a PID namespace), /proc/keys, /proc/timer_list, and read-only-bind-mounts /proc/bus, /proc/fs, /proc/irq, /proc/sys, /sys/firmware. Skip this and a fresh mount namespace alone leaves a handful of host-information leaks and, in kernels with certain misconfigurations, write paths back to host state that namespacing alone does not close.
  • No default rlimits. RLIMIT_NOFILE, RLIMIT_NPROC — without them a workload can exhaust file descriptor tables independent of anything cgroups.pids.max catches.
  • No hooks. prestart/createRuntime/poststart/poststop hooks are how the entire CNI ecosystem (chapter 3) and Podman's Quadlet generation (chapter 14) attach to a runtime without patching it. A runtime with no hook points cannot be composed into either ecosystem.
  • No architecture-aware seccomp handling. A filter written only for the native x86-64 ABI can be bypassed via the x32 syscall ABI's overlapping numbers on kernels where it's enabled — a real historical class of seccomp-filter bypass, which is why production seccomp profiles explicitly enumerate per-architecture syscall tables rather than trusting one number to mean one syscall everywhere.
  • We hand-built the rootfs. Nothing here extracts an OCI image, verifies layer digests against a manifest (chapter 10), or resolves a tag through the distribution API (chapter 11) — this runtime consumes a directory somebody already prepared, which is a fraction of what docker pull or podman pull does before a runtime ever sees a bundle.

None of this is a knock on the exercise — it is the honest reason runc is ~15,000 lines of Go and crun is tens of thousands of lines of C even though the "happy path" you just built is a few hundred. §16 returns to this list and asks you to extend it from memory.

ARC 08 · INTERNAL IMPLEMENTATION

The mechanism, at the level you'd need to patch it

Three pieces, each the actual code path: (a) pivot_root's exact effect on the mount tree, (b) the cgroup v2 interface files your runtime writes and the arithmetic the kernel applies to them, (c) the five capability sets capset() manipulates and what a seccomp-bpf filter actually evaluates.

(a) pivot_root: what actually moves in the mount tree

chroot() changes a per-process pointer; the kernel's global mount tree is untouched, which is exactly what makes it escapable (§4). pivot_root(new_root, put_old) is a mount-namespace-level operation: it makes new_root the mount namespace's root, and — the part every explanation skips — it does not delete the old root, it relocates it as a mount underneath new_root/put_old. Isolation only completes once you separately umount2(put_old, MNT_DETACH) and remove the now-empty directory. Skip that last unmount and the entire host filesystem remains reachable, just one cd away, under /oldroot.

pivot_root, one mount-tree operation at a timeSTEP-BY-STEP
A REAL PRECONDITION EVERY IMPLEMENTATION TRIPS ON

pivot_root requires new_root to be a mount point in its own right — a plain directory doesn't qualify. The standard fix, used by runc, is a self bind-mount: mount(new_root, new_root, NULL, MS_BIND|MS_REC, NULL) before calling pivot_root. And because mount propagation defaults to shared, every mount you make inside the new root would otherwise propagate back to the host's view of the same filesystem — hence the mandatory mount(NULL, "/", NULL, MS_REC|MS_PRIVATE, NULL) that must run first, in the new mount namespace, before touching anything else. Both of these are exactly the kind of step a "container in 40 lines" strawman omits and a real incident (§11) later exploits the absence of.

(b) cgroup v2: the arithmetic behind three interface files

Your runtime writes three files into a cgroup directory it creates under the unified hierarchy (/sys/fs/cgroup/minirun/<id>/) before moving the workload's PID into cgroup.procs. Each file's format is a kernel ABI, not a convention:

  • memory.max — a single integer in bytes, or the literal string max for unlimited. When the cgroup's charged memory would exceed this value, the kernel invokes the cgroup-scoped OOM killer, which selects a victim from within that cgroup only — the systemwide OOM killer never enters the picture, which is the entire point of running workloads in cgroups at all (chapter 5).
  • cpu.max — two space-separated integers, "$MAX $PERIOD" in microseconds (or "max $PERIOD" for unlimited), read by the CFS bandwidth controller. A cgroup may consume at most MAX microseconds of CPU time in every PERIOD-microsecond window; once exhausted, every task in the cgroup is throttled — held runnable-but-not-running — until the next period refills the quota. "50000 100000" is exactly one half of one core, regardless of how many cores the host has.
  • pids.max — a single integer or max, capping the number of tasks the cgroup may ever contain. This is the direct fix for fork-bomb workloads, and it is enforced independently of both memory and CPU limits.

Drag the sliders — this writes the literal file contents your runtime would produce, and runs the exact comparison the kernel runs to decide whether a given workload gets OOM-killed or CPU-throttled. This is the same arithmetic §15's live simulator uses to actually enforce these limits against a moving workload.

(c) The five capability sets, and what a seccomp filter actually evaluates

Chapter 7 introduced the five capability sets; here is exactly what your runtime's setup code manipulates before execve(). Permitted is the ceiling of what the process could enable. Effective is what's active right now. Inheritable survives an execve() only onto a binary with matching file capabilities. Bounding is a hard ceiling no descendant can ever exceed — this is the set your runtime shrinks with prctl(PR_CAPBSET_DROP, cap, 0,0,0), once per capability you're removing, before the final execve(). Ambient (added in kernel 4.3) lets specific capabilities survive execve() into a binary without file capabilities, which is what lets container runtimes hand a plain, unmarked binary a small set of capabilities without needing setcap on the image.

A seccomp-bpf filter, installed via prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog) (after prctl(PR_SET_NO_NEW_PRIVS, 1, 0,0,0) — mandatory for an unprivileged process to install one at all), is a small BPF program the kernel runs on every syscall entry, inspecting the syscall number and, optionally, its arguments, and returning an action — commonly SECCOMP_RET_ALLOW or SECCOMP_RET_ERRNO (fail the call with a chosen errno, usually EPERM, without ever reaching the kernel function that implements it). The filter is evaluated before capability checks — a syscall a seccomp filter blocks never gets far enough to ask "does this process have the capability for this?" §15's engine implements exactly that ordering.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Fewer hops is faster and smaller — but "smaller" isn't automatically "safer"

Startup latency for this eight-step sequence is dominated by process creation and mount setup, not by the syscalls themselves — each individual unshare(), cgroup write, or capset() call is sub-millisecond. What differs sharply across runtimes is how many process hops sit between the invocation and the workload, because every hop is itself a fork/exec plus, in Docker's case, a gRPC round-trip.

Fewer lines of privileged code between your command and the running container is a genuine, defensible security argument for crun over runc and for Podman's fork-exec model over a long-lived daemon holding root for its entire uptime — this is not vendor boosterism, it's the same "reduce what a single bug can reach" logic behind capability drops and seccomp filters. Fewer lines of code is necessary for a small attack surface; it is not sufficient for a correct one.

ARC 11 · REAL-WORLD INCIDENTS

Three incidents that live exactly in the code you just wrote

CVE-2024-21626 — "Leaky Vessels": a leaked working-directory file descriptor

Disclosed January 2024 (Snyk, Rory McNamara). runc's internal process-launching code opened an file descriptor for the container's working directory as part of its own setup — before the process fully transitioned into the new root — and that fd could, under specific conditions (an attacker-controlled WORKDIR in a Dockerfile, or a malicious runc exec target), end up referring to a path on the host rather than inside the container's rootfs. A subsequent operation using that fd — for instance /proc/self/fd/N as a working directory for the actual container process — read or wrote host files instead of container files, breaking out of the isolation §8's pivot_root section was supposed to guarantee. Fixed in runc 1.1.12. The root cause is a category this chapter's own rootfs code is exposed to as well: any file descriptor opened before pivot_root completes and not explicitly re-validated afterward is a potential path back to the host — which is exactly why real runtimes re-check paths after every mount-namespace transition rather than trusting a descriptor opened earlier in the sequence.

CVE-2021-30465 — a symlink-exchange race during bind-mount setup

runc resolved a container-specified mount source path, then performed the actual mount() using that resolved path — with a window between resolution and use. A malicious container process (or a crafted image) could replace a path component with a symlink pointing outside the rootfs in that window, so the eventual mount() call operated on a host path runc believed was still safely inside the container. Fixed by switching to safer, race-free path-resolution primitives (the same category of fix underlying openat2()'s RESOLVE_* flags, added in kernel 5.6). This is a textbook time-of-check-to-time-of-use (TOCTOU) bug, and it lives in precisely the step §8(a) called out as easy to get subtly wrong: resolving a mount path is not the same instant as using it, and anything the container controls in between is attacker-controlled state.

The exposed docker.sock cryptojacking wave (Kinsing, TeamTNT, ongoing since ~2019)

Not a kernel bug at all — a deployment mistake, repeated at internet scale for years. Binding the Docker daemon's API socket to 0.0.0.0:2375 without TLS, or bind-mounting /var/run/docker.sock into an untrusted container, hands the caller root-equivalent control of the host: create a new container with --privileged and a host bind mount, and you have host root without ever touching a kernel vulnerability. Botnets including Kinsing and TeamTNT have scanned for exactly this misconfiguration for years, installing cryptominers on every host they find. The lesson this course has built toward: this is the daemon's API surface being the vulnerability, not the container runtime's isolation primitives — and it is why chapter 12's observation that Podman ships with no equivalent long-lived socket unless you explicitly enable podman.socket is a genuine, if narrow, security argument, not marketing. It narrows further than it first appears: an exposed, unauthenticated podman.socket is exactly as dangerous as an exposed docker.sock — the property that matters is opt-in versus on-by-default, not "daemon versus no daemon" per se. §16 asks you to hold that distinction precisely.

WHAT THE INDUSTRY BUILT IN RESPONSE

All three incidents above are failures within the namespaces+cgroups+capabilities+seccomp model, not failures of an alternative to it. The industry's other response — gVisor (Google, a userspace kernel intercepting syscalls in Go, rewriting their handling entirely) and Kata Containers (a real, lightweight VM per "container", using hardware virtualization as the isolation boundary instead of namespaces) — is a structural admission that for genuinely hostile, multi-tenant workloads, namespaces plus seccomp plus capabilities is defense in depth on a single shared kernel, and a shared kernel is, irreducibly, a shared attack surface. Neither Docker nor Podman requires either; both can be configured to use gVisor (runsc) or Kata as a drop-in low-level runtime, because both consume the same OCI Runtime Spec this chapter's minirun only partially implements.

Reading minirun: the actual eight steps in C

(1) main.c — the process split. clone() with a flag word is how you get a child born already inside new namespaces, rather than forking and calling unshare() a moment later (which leaves a race window where the child briefly shares namespaces with the parent):

Cmain.c — clone() with the namespace flag set
static char child_stack[1 << 20];   /* 1 MB, clone() needs a stack it doesn't allocate */

int main(int argc, char **argv)
{
    int flags = CLONE_NEWUSER | CLONE_NEWPID  | CLONE_NEWNS
             | CLONE_NEWUTS  | CLONE_NEWIPC | CLONE_NEWNET
             | SIGCHLD;                        /* SIGCHLD: how the parent gets notified on exit */

    pid_t pid = clone(child_main, child_stack + sizeof(child_stack), flags, argv);
    if (pid < 0) { perror("clone"); return 1; }

    write_uid_gid_map(pid);      /* MUST happen from the PARENT, targeting the child's
                                 * /proc/<pid>/uid_map — an unprivileged process can only
                                 * write its OWN child's map, never its own            */
    setup_cgroup(pid, &limits);  /* parent still has CAP_SYS_ADMIN on the host; do
                                 * privileged host-side setup before releasing the child */
    kickoff(pid);                /* signal the child: maps and cgroup are ready, proceed */

    int status; waitpid(pid, &status, 0);
    return WEXITSTATUS(status);
}

(2) rootfs/pivot.c — inside the child, after namespaces exist but before anything runs:

Crootfs/pivot.c — the mount-tree swap
void enter_rootfs(const char *new_root)
{
    mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL);   /* stop mount events
                                                       * propagating back to host */
    mount(new_root, new_root, NULL, MS_BIND | MS_REC, NULL); /* new_root must BE a
                                                       * mountpoint for pivot_root */

    chdir(new_root);
    mkdir(".oldroot", 0700);
    syscall(SYS_pivot_root, ".", ".oldroot");   /* new_root becomes "/", old
                                                       * root relocates to /.oldroot */
    chdir("/");

    umount2("/.oldroot", MNT_DETACH);              /* detach — without this the WHOLE
                                                       * host tree is still reachable */
    rmdir("/.oldroot");

    mount("proc", "/proc", "proc", 0, NULL);  /* fresh /proc — PID-namespace aware,
                                                       * shows only this ns's PIDs   */
}

(3) cgroup/limits.c — run from the parent (host-side CAP_SYS_ADMIN), before the child is released:

Ccgroup/limits.c — writing the unified-hierarchy interface files
void setup_cgroup(pid_t pid, struct limits *l)
{
    char dir[256];
    snprintf(dir, sizeof(dir), "/sys/fs/cgroup/minirun/%d", pid);
    mkdir(dir, 0755);                                  /* mkdir under cgroup2 IS "create a cgroup" */

    write_file(dir, "memory.max", "%llu", l->mem_bytes);
    write_file(dir, "cpu.max",    "%llu %llu", l->quota_us, l->period_us);
    write_file(dir, "pids.max",   "%d", l->max_pids);
    write_file(dir, "cgroup.procs", "%d", pid);   /* the actual join — must be
                                                            * done from OUTSIDE the pid
                                                            * namespace, using the real
                                                            * host-visible PID           */
}

(4) sandbox/lockdown.c — the child's last act before it stops being able to undo anything:

Csandbox/lockdown.c — capabilities, then seccomp, then no return
void lock_down_and_exec(char **argv, char **keep_caps, int n_keep)
{
    for (int c = 0; c <= CAP_LAST_CAP; c++)
        if (!in_list(c, keep_caps, n_keep))
            prctl(PR_CAPBSET_DROP, c, 0, 0, 0);   /* shrink the BOUNDING set —
                                                    * a hard ceiling nothing after
                                                    * this line can ever re-raise  */

    prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);   /* mandatory before an unprivileged
                                                    * seccomp install                */
    install_seccomp_filter();                     /* prctl(PR_SET_SECCOMP, ...) — from this
                                                    * instruction on, THIS process too
                                                    * is bound by the filter         */

    execve(argv[0], argv, environ);      /* point of no return: image replaced,
                                                    * caps/seccomp/cgroup/mounts all
                                                    * already committed              */
}
WHY IT'S BUILT THIS WAY — THREE CHOICES TO STEAL

1. Host-side privileged work happens in the parent, not the child. Writing the child's uid_map and the cgroup files needs privilege the child is about to permanently shed — doing it from the still-fully-privileged parent, targeting the child by PID, avoids ever having the child hold capabilities it doesn't need even transiently. 2. Capabilities drop before seccomp installs, seccomp installs before execve, and nothing reorders that. Each step narrows what's still possible for everything after it — narrowing in the wrong order can lock you out of a step you haven't finished yet. 3. The cgroup join happens from outside the PID namespace. cgroup.procs takes a real, host-visible PID; writing it from inside a PID namespace where the process sees itself as PID 1 would target the wrong process entirely.
