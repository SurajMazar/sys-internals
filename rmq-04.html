RABBITMQ INTERNALS · CHAPTER 04

Classic Queues:
The Queue Process Internals

Chapter 3 ended with routing solved: an exchange decides which queues get a copy of a message. This chapter asks the next question — once a message lands in a queue, what is that queue, as a running thing? The answer is one sentence, and this entire chapter is what falls out of taking that sentence literally: a classic queue is one Erlang process, a gen_server called rabbit_amqqueue_process, that owns every byte of that queue's state. No lock, no shared table, no distributed coordination — just one process with a mailbox, and everything about classic-queue behavior, performance, and failure modes derives from that fact.

ARC 01 · THE PROBLEM

Something has to hold the messages — what, exactly?

Chapter 3's exchange is deliberately stateless: rabbit_exchange:route/2 is a pure function, a routing key in, a list of queue names out. It stores nothing about any individual message. Somewhere, though, an actual buffer has to exist — something that remembers "these 40,000 messages arrived, in this order, and none of them has been acknowledged yet." That something is the queue, and chapter 1 already told you the shape of the answer: RabbitMQ needs to support potentially hundreds of thousands of these buffers on one node, each independently created, destroyed, and stateful, without one buffer's behavior ever corrupting another's. The only primitive chapter 1 gave you that satisfies "independently stateful, isolated, cheap to multiply" is the BEAM process.

So a classic queue is a process: rabbit_amqqueue_process, a gen_server2 (Rabbit's own priority-aware variant of the standard gen_server behaviour). Committing to that one design choice is not a detail — it is the entire chapter, because a gen_server is, at its core, nothing more than a private heap and a mailbox that messages are handled from one at a time, in arrival order. Three consequences fall out immediately, before you've written a single line of storage logic:

  • Total ordering within a queue is free. There is exactly one process reading exactly one mailbox in exactly one order. You do not need a sequence number, a version vector, or a consensus round to know "which message came first" — the mailbox already answers that question by construction.
  • There is no lock anywhere in this queue's critical path. A lock exists to arbitrate between multiple threads that might touch the same state concurrently. A gen_server's state is touched by exactly one scheduler-selected execution context at a time — the process itself — so "concurrent access to queue state" is not a case this design has to handle, because it cannot happen.
  • Throughput is capped at whatever one BEAM scheduler can push through one process. The flip side of "one mailbox, handled sequentially" is that this queue's messages will never be processed by two CPU cores at once, no matter how many cores the node has. A single hot queue cannot use 64 cores. This is not a bug to fix later — it is the direct, unavoidable cost of the exact design that made ordering and lock-freedom free, and it is why §5 onward keeps returning to sharding across queues, not parallelizing inside one, as the scaling answer.
THE REAL DIAGNOSTIC SURFACE: THE MAILBOX ITSELF

Because rabbit_amqqueue_process handles its mailbox strictly sequentially, that mailbox is where backpressure actually lives. If publishes arrive faster than the process can apply them to its internal state (§8), unhandled {deliver, ...} messages queue up in the Erlang process mailbox — not conceptually, literally, as an in-memory linked list the BEAM maintains per process. A growing mailbox is memory RabbitMQ isn't otherwise accounting for in the same place your monitoring dashboards look (which typically show messages_ready/messages_unacknowledged, the AMQP-visible queue depth) — an operator who has never heard of "process message queue length" can still be blindsided by it. RabbitMQ's own management stats and rabbitmqctl status surface it explicitly as a per-queue-process metric precisely because it is the earliest, truest signal that this one process is falling behind its incoming rate, before RAM, disk, or CPU alarms even notice anything is wrong.

DEEP CONTEXT · WHY "JUST BUY MORE RAM" WAS NEVER THE FIX

Every one of these revisions is solving the same underlying tension: RAM is fast but finite and expensive per byte; disk is slow (relatively) but effectively unbounded and cheap per byte. A queue that never pages to disk is simple to reason about and fast right up until a slow consumer, a bursty producer, or a genuinely large backlog exceeds available memory — at which point the failure mode isn't "a bit slower," it's the node's vm_memory_high_watermark tripping (default 40% of available RAM) and blocking every publisher on the node, or in the worst historical cases, an out-of-memory kill of the whole Erlang VM. §5 and §8 derive the state machine that exists specifically to make that failure mode gradual and controllable instead of sudden and catastrophic.

ARC 03 · NAIVE SOLUTION

Attempt #1: the queue's state is just a list, entirely in RAM

Derive it honestly. You've accepted "one process per queue." The simplest possible thing that process could do with its state is hold an ordinary in-memory FIFO — an Erlang queue:queue() (a purely functional two-list queue, O(1) amortized push/pop) — of every message, full stop. No disk, no index, no separate store.

Erlangnaive_queue.erl — the strawman, annotated
-record(state, {
    %% Every message this queue currently holds, front = oldest, full stop.
    %% Content, properties, everything — all of it, always, in this one
    %% process's heap. Nothing ever touches disk.
    messages :: queue:queue(#basic_message{}),
    next_delivery_tag = 1 :: non_neg_integer()
}).

handle_cast({publish, Msg}, State = #state{messages = Q}) ->
    %% O(1) amortized push. Simple. Fast. Nothing checks how big Q has become.
    {noreply, State#state{messages = queue:in(Msg, Q)}};

handle_call({get}, _From, State = #state{messages = Q}) ->
    case queue:out(Q) of
        {{value, Msg}, Q2} -> {reply, {ok, Msg}, State#state{messages = Q2}};
        {empty, Q2}        -> {reply, empty, State#state{messages = Q2}}
    end.

This is not a strawman to mock — it is what RabbitMQ's very first queue implementation actually resembled, and for a queue that stays shallow (thousands of small messages, a consumer that keeps pace), it is arguably correct: no I/O on the hot path at all, and every operation is O(1). ARC 04 · WHY IT FAILS

The math: RAM-only queues turn a slow consumer into an OOM, quantified

Formalize what the deck just showed. If a queue holds N messages of average size S bytes, entirely in its process heap, its RAM footprint grows as N × S with no ceiling of its own — the only ceiling is the node's physical memory, shared across every other queue, channel, and connection process on that node.

  • A single hot queue can starve a whole node. 5 million messages at a modest 2 KB average (a typical JSON event payload) is 10 GB in one queue's heap alone. A node with several such queues, or one queue with a genuinely large backlog, can exhaust available RAM well before disk, CPU, or network becomes the bottleneck.
  • Memory pressure is node-wide, but the cause is often one queue. RabbitMQ's vm_memory_high_watermark (default 0.4, i.e. 40% of detected available RAM) trips a node-wide alarm that blocks all publishers on that node, not just the ones feeding the offending queue — a single misbehaving consumer on one queue can degrade completely unrelated producers.
  • Durability and RAM residency get conflated. A durable queue's persistent messages must survive a broker restart, which means they need to reach disk regardless — but the naive design above only writes to disk implicitly, at OS page-cache eviction time, which is not a moment RabbitMQ controls or can rely on for a durability guarantee.
  • Per-process GC gets expensive on a giant heap. Chapter 1 sold "per-process GC is cheap because it's local" — true, but its cost still scales with that process's own live data. A queue process holding 10 GB of messages has a 10 GB heap to trace on its next garbage collection, which is no longer the sub-millisecond pause chapter 1 promised for a typically-sized process.
THE NUMBERS

This is not a hypothetical edge case — it is the single most common classic-queue production incident: a consumer goes offline for maintenance, or simply can't keep up with a traffic spike, publishers keep publishing (because nothing tells them not to), and a queue that was a few megabytes an hour ago is now a meaningful fraction of the node's RAM. §11 covers this exact pattern as a named, repeatedly-observed failure mode. The fix can't be "hope queues stay small" — it has to be a queue implementation that pages itself to disk automatically, before the node's memory alarm has to intervene on its behalf.

So the fix has two independent parts: (a) stop assuming disk writes are optional — durability requires them for persistent messages regardless — and (b) make RAM residency a reclaimable resource, not a permanent commitment, so a queue can shed memory under pressure without losing messages. §5 walks through the storage designs actually considered for both.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Two stores, not one — and a state machine to move between them

Candidate A: always write everything to disk immediately

The simplest fix for §4's RAM problem: never hold a message purely in RAM at all — write it to disk on arrival, every time, for every queue. This is durable by construction and its RAM footprint is bounded and predictable. But it throws away the one advantage the naive design had: for the overwhelmingly common case of a small, fast-draining queue (a task queue whose consumer is keeping up fine), you now pay a disk write and, typically, a disk read for every single message that would otherwise never have needed to touch a spinning or even solid-state device at all. Rejected as a universal default: correct, but pays I/O cost even when there is no memory pressure to justify it — though as §8 covers, this is exactly the behavior RabbitMQ offers deliberately as an opt-in (and, since 3.12, the effective default) via lazy queues, for workloads where it's the right trade.

Candidate B: one file per queue, holding both metadata and message bodies together

Keep everything durable, but write it into a single per-queue log: publish records, delivery/ack records, and full message bodies all interleaved in one file per queue. This solves durability without a second system to build, but it creates a subtler problem the moment routing (chapter 3) is remembered: a fanout exchange can route the same published message to ten different queues. If each queue's file stores its own full copy of the body, a 1 MB message fanned out to ten queues costs 10 MB of disk — the exchange's "one message, many queues" semantics get multiplied into real storage cost on the way down. Rejected: correct but wasteful under fan-out, the single most common pattern rich routing (ch. 3) exists to support.

Deriving index + store from one constraint: fan-out shouldn't multiply disk costSTEP-BY-STEP

Candidate C: split "where is this message in my ordering" from "where are its bytes" ✓

Separate two genuinely different concerns into two genuinely different subsystems. Per-queue metadata — publish/deliver/ack sequence, which is small and queue-specific — lives in rabbit_queue_index, one index per queue. Message bodies — potentially large, and potentially shared across many queues from one fan-out publish — live in rabbit_msg_store, one store per node, content-addressed and reference-counted so ten queues bound to the same fanout publish share one on-disk copy of the body, not ten. §8 opens both file formats precisely.

THE PATTERN, GENERALIZED

This is the same move chapter 3's exchange/binding/queue split made at the routing layer, applied one layer down at storage: separate the thing that's small and per-entity (a queue's ordering) from the thing that's potentially large and shared (a message's bytes), and let each scale on its own terms. It's also why a classic queue's process state can stay comparatively small even when its backlog is enormous — the process holds index/pointer structures, not necessarily every message body, which is precisely what §8's alpha/beta/gamma/delta machine formalizes.

ARC 06 · WHY THAT STILL COSTS

The bill for a two-store, paging design

Splitting index from store and adding a paging state machine solves §4's crisis, but it is not free, and understanding the cost is what lets you tune x-queue-mode and memory watermarks deliberately instead of by folklore:

  • State transitions themselves cost CPU and I/O. Moving a message from RAM-resident (alpha) toward disk-resident (beta → gamma → delta) under memory pressure means writing an index segment record and, unless the body is small enough to embed (§8), a separate message-store write — real work done on a process that could otherwise be handling the next publish.
  • Paging is decided per-queue, reactively, not globally in advance. Each rabbit_amqqueue_process watches its own memory footprint against the node's watermark and pages itself independently — there is no global scheduler deciding in advance which queue should page first, which means many queues under pressure simultaneously can all start paging at once, each contending for the same disk.
  • A crashed queue process still has to recover from two places, not one. On restart, a durable classic queue rebuilds its in-memory view by replaying rabbit_queue_index segments and cross-referencing rabbit_msg_store for bodies — more moving parts than the naive single-file design, and more surface area for the specific disk-layout bugs chapter 11 covers in depth.
  • One busy queue's paging cannot be parallelized across cores. Exactly §1's ceiling again: even though the storage engine underneath got more sophisticated, it's still driven by one sequential process — paging a backlog faster is a job for reducing that one queue's load or sharding to more queues, never for adding threads to this one.
THE HONEST TRADE

None of this is an argument against the design — it's the real price of turning §4's sudden OOM into a graceful, observable degradation instead. A queue under memory pressure gets slower and starts showing more of its backlog in gamma/delta states (visible in the simulator, §15) rather than crashing the node outright. The final architecture, then, is: one process per queue (§1), backed by a state machine (rabbit_variable_queue) that decides, message by message, how much of it lives in RAM right now — talking to two on-disk subsystems that split "ordering" from "bytes" for exactly the reason §5 derived.

DEEP CONTEXT · WHY THE PROCESS ITSELF STAYS DUMB

rabbit_amqqueue_process deliberately delegates almost everything about how messages are stored to rabbit_variable_queue — the process handles AMQP-level concerns (consumer registration, acks, flow control, policy like x-max-length) and calls into the variable queue module as a library, not a separate process. That's a real design choice: it keeps the storage state machine unit-testable in isolation (it's pure-ish data-in, data-out Erlang, no process boundary to mock) while still running inside the one process per queue that chapter 1's isolation guarantee requires.

ARC 08 · INTERNAL IMPLEMENTATION

rabbit_variable_queue: four states, and what moves between them

Every message a classic queue is holding is, at any instant, in exactly one of four states. The names are historical (they trace back to the module's original author's notes) but the mechanics are precise and worth learning exactly:

  • alpha — the message content and its queue-index entry are both resident in RAM. This is where every message starts. Fastest possible state for both publish and deliver: nothing touches disk to serve a consumer from here (persistent messages are still written to the message store for durability in parallel, but nothing needs to be read back from disk to deliver an alpha message).
  • beta — the message body has been pushed out to disk (embedded in the index or written to rabbit_msg_store, §8b decides which), but the queue-index entry describing it is still held in RAM. Delivering a beta message costs one disk read for the body; the queue still knows exactly where that message sits in its ordering without consulting disk.
  • gamma — like beta, except the index entry itself has now also been flushed to the on-disk rabbit_queue_index segment file, with only a small, compact in-RAM summary remaining. Both the body and the index record are on disk; RAM holds bookkeeping, not the entries themselves.
  • delta — fully disk-resident. Neither the body nor any individual index entry is materialized in RAM; the queue holds a single compact record describing a range of sequence IDs that live entirely on disk. This is the cheapest possible RAM footprint per message — effectively a handful of bytes amortized across an entire contiguous run, regardless of how many messages that run contains.
Paging under memory pressure: alpha → beta → gamma → deltaSTEP-BY-STEP

Transitions only ever move messages from a cheaper-for-latency, more-expensive-for-RAM state toward a cheaper-for-RAM, more-expensive-for-latency one — alpha toward delta — and only under actual memory pressure, starting from the oldest messages (the ones least likely to be consumed imminently). A queue whose consumer keeps pace never needs to page at all; every message it ever holds might live and die entirely as alpha.

(a) rabbit_queue_index: segment files of 16,384 entries

rabbit_queue_index is per-queue, and it records exactly three kinds of event against a message's position in that queue's sequence: publish, deliver, and ack. It splits its records across segment files, each holding a fixed 16,384 entries. That fixed size is not arbitrary bookkeeping — it means a sequence ID's segment file and its offset within that file are both computable directly by division and remainder (segment = seq_id div 16384, offset = seq_id rem 16384), so looking up or appending a record never requires searching an index-of-indexes. It's O(1) by construction, the same trick a hash table uses, applied to a monotonically increasing sequence instead of a hash.

(b) The embedding threshold: queue_index_embed_msgs_below

Not every message needs two files. If a message body is smaller than queue_index_embed_msgs_below (default 4096 bytes), rabbit_queue_index stores the body inline, directly inside the segment file record itself, alongside its publish/deliver/ack metadata. Only bodies at or above that threshold get written out to the separate rabbit_msg_store, with the index instead holding a small reference (message ID, file, and offset). The threshold exists because, for small messages, a second file's I/O — a separate open, a separate seek, a separate fsync policy to reason about — costs more in overhead than it saves in space: you'd be paying two write amplifications and two read round-trips to move a handful of hundred-byte payloads that could have ridden along with metadata you were already writing anyway.

(c) rabbit_msg_store: node-wide, content-addressed, reference-counted

Unlike the index, there is no "one message store per queue." rabbit_msg_store (in practice, two of them per node — one for persistent messages, one for transient) is shared by every queue that needs it. A message is written once, keyed by a message ID, with an in-RAM index (an ETS table) mapping that ID to {file, offset, ref_count}. When a fanout exchange (ch. 3) routes one published message into ten queues, all ten queues' index entries point at the same message-store record, and its reference count becomes 10 — the body is written to disk exactly once, not ten times, and is only actually deleted from the store once every referencing queue has acknowledged (or otherwise discarded) its copy and the ref count reaches zero. This is precisely §5's fan-out cost problem, solved structurally rather than avoided.

(d) Lazy queues, and why 3.12 stopped trusting the RAM-first default

Historically, x-queue-mode=lazy (added in 3.6, 2016) was an opt-in policy: instead of letting messages start as alpha and paging only under memory pressure, a lazy queue moves messages to disk essentially immediately, keeping only a small, bounded amount of RAM per message regardless of backlog size. The trade is explicit — a lazy queue trades best-case delivery latency (a disk read even for a message published a moment ago) for a RAM footprint that barely grows no matter how deep its backlog gets. It was purpose-built for workloads that are inherently bursty or batch-shaped: import/export pipelines, queues that intentionally buffer hours of work, anywhere a slow consumer is the expected steady state, not an incident.

RabbitMQ 3.12 changed the default posture entirely: classic queues gained a new on-disk layout, classic queue version 2 (CQv2), and adopted lazy-like, eager-to-disk behavior by default, no x-queue-mode declaration required. The reasoning is exactly §4's math made into policy: the old RAM-first default kept every message as alpha for as long as memory allowed, which meant a queue behaved perfectly right up until a slow consumer or a burst pushed it over the watermark — at which point what had been a minor, boring operational hiccup (a consumer running behind) could become a node-wide memory alarm or, in the worst historical cases, an out-of-memory kill. Defaulting to eager persistence trades a small amount of best-case latency, always, for removing the cliff entirely.

QUEUE DECLARATION PROPERTIES THAT SHAPE ALL OF THIS

Three properties are set at declaration time and never change for that queue's lifetime: durable (queue metadata — and persistent messages published into it — survive a broker restart; a durable queue with an empty message store on restart still exists as a queue), exclusive (usable only by the declaring connection, auto-deleted the instant that connection closes — no supervision restart brings an exclusive queue back), and auto-delete (deleted once its last consumer unsubscribes, regardless of connection state). None of these interact with the alpha/beta/gamma/delta machine directly — durability decides whether a message must reach the message store at all; the four states describe how much of an already-decided-durable (or transient) message currently sits in RAM.

Two more knobs bound a queue's growth directly, independent of memory pressure: x-max-length (and its byte-oriented sibling x-max-length-bytes) caps how many messages a queue will hold at all, and x-overflow decides what happens once that cap is hit — drop-head (the default: silently discard the oldest message to make room for the new one, favoring recency), reject-publish (refuse the new publish outright, returned to the publisher as a basic.nack if publisher confirms are in use, favoring never silently losing anything already accepted), or reject-publish-dlx (reject the publish exactly like reject-publish, but additionally route the rejected message to the queue's configured dead-letter exchange so it isn't simply lost, just redirected). §15's simulator lets you flip between all three and watch which messages survive.

MEMORY COST PER QUEUE PROCESS

Even an empty, idle classic queue costs something: the baseline gen_server2 process heap (low kilobytes, per chapter 1's arithmetic), plus rabbit_variable_queue's own bookkeeping structures — priority-ordered pending-ack tracking, consumer state, policy caches — which scale with the number of messages currently resident as alpha or beta, not with the (potentially enormous) count of messages parked in delta. This is precisely why RabbitMQ's operational guidance is "avoid declaring tens of thousands of mostly-idle queues" — the marginal RAM cost of one more queue is small, but it is not zero, and it multiplies by every queue you declare regardless of whether it ever carries traffic.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict from the design alone

From §7's architecture and §8's state machine, several performance properties follow directly, without needing to benchmark anything first:

  • Queue index lookup/append is O(1), not O(log n): the fixed 16,384-entry segment size makes a sequence ID's file and offset a direct computation (division and remainder), never a search through an index-of-indexes the way a B-tree-backed structure would need.
  • Message-store lookup is O(1) average-case: an in-RAM ETS hash table maps message ID to {file, offset, ref_count}, the same complexity class as any hash-table-backed cache.
  • Per-queue-process RAM scales with alpha+beta count, not total backlog: messages parked in delta contribute a near-constant amortized cost per contiguous range, which is precisely why a queue with millions of delta-resident messages doesn't necessarily cost millions of times more RAM than an empty one — bounded growth is the entire point of pushing messages toward delta under pressure.
  • One reduction budget, one queue: chapter 1's ~2,000-reduction scheduling slice applies here exactly as it does to any BEAM process — a queue handling a very large batched ack still gets forcibly rotated off its scheduler if it runs long, but the work itself is still fundamentally serialized through that one process; there is no parallel path through rabbit_amqqueue_process, ever.
  • Disk access pattern is mostly sequential, by design: both rabbit_queue_index segment writes and rabbit_msg_store writes are append-oriented, which is exactly the access pattern spinning and solid-state disks both handle best. Reads for a beta/gamma/delta message can be less predictable, but the message store keeps a small in-RAM cache of just-written entries specifically to avoid an immediate disk round-trip for the extremely common "publish, then deliver almost immediately" case.

MODEL, NOT MEASUREMENT

The curve models write count, the clearest way to see the embedding threshold's effect, not absolute latency (which depends heavily on disk hardware, fsync policy, and batching). Below 4096 bytes, a paged message costs one write (the index segment record, body embedded inline); at or above it, a paged message costs two (an index reference plus a separate message-store write). An alpha-resident message costs zero synchronous reads on the delivery path regardless of size — the step only matters once a message has actually paged out of alpha, which is exactly why lazy/CQv2-eager mode — which pages essentially everything immediately — feels the threshold's effect on nearly every message, while a healthy, RAM-first queue may rarely feel it at all.

ARC 11 · REAL-WORLD PRODUCTION

Three ways this design meets — and sometimes loses to — reality

Story 1: the slow-consumer-to-OOM pattern that motivated lazy queues in the first place

Lazy queues were introduced specifically because operators kept hitting the same shape of incident: a consumer falls behind (a deploy, a downstream dependency slows down, a bug causes silent message piling), and a classic queue that defaults to keeping everything RAM-resident as alpha grows unboundedly until the node's memory watermark — or, in the worst cases, the OS's OOM killer — steps in. The RabbitMQ team's own guidance from that era was blunt about the trade: if you know a queue is going to buffer a large, bursty backlog by design (an import job, a batch pipeline, anything where "the consumer is behind" is the expected steady state rather than an incident), tell the queue to behave that way up front with x-queue-mode=lazy instead of letting it discover the problem reactively under pressure.

Story 2: the 3.12 default change, and what it implies about the ecosystem's queue depths

RabbitMQ making classic queues eager-to-disk by default in 3.12, via the CQv2 storage format, is a quiet but telling admission: enough production traffic hit §4's failure mode, across enough different operators, that the safer default stopped being "optimize for the common case where nothing goes wrong" and became "don't let the worst case be an OOM." The trade every classic-queue user now accepts by default — a small latency cost on messages that would previously have stayed alpha — is treated as cheaper than the tail risk it removes. That's a genuinely different philosophy from the original 2007-era design, and it's a direct line back to §2's history: RAM-first sounded obviously faster right up until it wasn't.

Story 3: fan-out topologies and the message-store reference count in practice

A widely observed operational pattern in RabbitMQ deployments that lean heavily on fanout or topic exchanges with many bound queues: because rabbit_msg_store reference-counts a shared body across every queue that received a copy, a body is only actually deleted from disk once every referencing queue has acknowledged its copy (or otherwise discarded it, e.g. via TTL or x-max-length overflow). A single slow or stuck consumer on just one of ten fanned-out queues can keep a message-store file's reference count above zero indefinitely, preventing that file from being reclaimed even though nine of the ten queues have long since moved on — a subtle, easy-to-miss coupling between one lagging queue and disk usage that looks, at a glance, like every queue's problem. Chapter 11's disk-layout material covers the file compaction mechanics this interacts with in full.

Erlangrabbit_amqqueue_process.erl — handling a delivered message, simplified
handle_cast({deliver, Delivery = #delivery{message = Msg}}, State = #q{variable_queue = VQ}) ->
    %% The process itself knows almost nothing about WHERE this message
    %% will physically live. It hands the decision entirely to the state
    %% machine module — this call is a plain function call, not a message
    %% send, because rabbit_variable_queue is a library, not a process.
    VQ1 = rabbit_variable_queue:publish(Msg, Delivery#delivery.msg_seq_no, VQ),
    State1 = maybe_enforce_max_length(State#q{variable_queue = VQ1}),
    {noreply, State1}.

maybe_enforce_max_length(State = #q{max_length = undefined}) -> State;
maybe_enforce_max_length(State = #q{max_length = Max, overflow = Overflow, variable_queue = VQ}) ->
    case rabbit_variable_queue:len(VQ) > Max of
        true  -> enforce_overflow(Overflow, State);   %% drop_head | reject_publish | reject_publish_dlx
        false -> State
    end.

Second, the shape of a state transition inside rabbit_variable_queue — this is what "paging" looks like as code, simplified to the decision logic:

Erlangrabbit_variable_queue.erl — alpha->beta transition under pressure, simplified
maybe_page_out(VQ = #vqstate{ram_msg_count = RamCount, target_ram_count = Target})
    when RamCount > Target ->
    %% Pull the OLDEST alpha entry — least likely to be wanted next —
    %% and push its body out of the process heap.
    {{MsgId, Msg}, VQ1} = pop_oldest_alpha(VQ),
    Ref = case byte_size(Msg#basic_message.content) < VQ1#vqstate.embed_below of
        true  -> rabbit_queue_index:embed(MsgId, Msg, VQ1#vqstate.index_state);      %% one write
        false -> rabbit_msg_store:write(MsgId, Msg, VQ1#vqstate.msg_store_client)   %% index ref + store write
    end,
    VQ2 = record_as_beta(MsgId, Ref, VQ1),
    maybe_page_out(VQ2);  %% keep going while still over target
maybe_page_out(VQ) -> VQ.

Third, why the segment size is a compile-time constant, not a tunable — the whole point is that no lookup structure is needed:

Erlangrabbit_queue_index.erl — segment addressing, simplified
-define(SEGMENT_ENTRY_COUNT, 16384).

segment_and_offset(SeqId) ->
    %% O(1): pure arithmetic, no tree walk, no index-of-indexes.
    {SeqId div ?SEGMENT_ENTRY_COUNT, SeqId rem ?SEGMENT_ENTRY_COUNT}.

write_entry(SeqId, Entry, State) ->
    {Segment, Offset} = segment_and_offset(SeqId),
    File = segment_file_name(Segment),   %% e.g. ".../3.rdq" for segment 3
    append_at_offset(File, Offset, Entry, State).
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Make the hot decision arithmetic, not structural. A fixed segment size turns "where does this entry live" into division and remainder instead of a B-tree traversal — the same instinct behind any fixed-width bucket scheme, applied to an append-only log instead of a hash table. 2. Keep the state machine a data structure, not a process. rabbit_variable_queue is plain Erlang data transformed by plain functions — it never needs its own mailbox or supervision entry because it has no independent lifecycle; it lives and dies with the one rabbit_amqqueue_process that owns it, which keeps testing and reasoning about it far simpler than a second process would. 3. Decide storage destination by a threshold, not a policy the operator must set per message. queue_index_embed_msgs_below is evaluated automatically per message at the moment it pages — nobody has to annotate individual publishes as "small" or "large"; the size check does that work once, cheaply, exactly when it's needed.
