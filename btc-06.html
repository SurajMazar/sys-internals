BITCOIN INTERNALS · CHAPTER 06

The UTXO Set:
Bitcoin's Real Database

A running Bitcoin node has no column called balance, no row keyed by an address, and no concept of an account. What it keeps — the only state it needs to validate the next block — is a set of currently unspent transaction outputs. This chapter takes that sentence apart: why the model was chosen, exactly how Bitcoin Core stores it on disk in a LevelDB database with a genuinely strange obfuscation trick, why the set only ever grows, and why picking which coins to spend is a real algorithms problem that most wallets get wrong.

ARC 01 · THE PROBLEM

What does a node actually have to remember?

Strip away every abstraction and ask the sharpest possible version of the question: a fully synced node receives a brand-new block over the wire. To decide whether it is valid, what information does the node need to have sitting in memory or on disk, right now, before it looks at a single byte of that block? Not "what would be nice to know" — what is strictly, minimally required.

For each transaction in the candidate block, and for each input in that transaction, the node must answer three questions:

  • Does the coin being spent exist? The input names a previous output — a specific (txid, index) pair, called an outpoint — and that output must have been created by some earlier transaction and must not already have been spent by any other transaction that is part of the accepted chain.
  • Is the spender authorized? The output carries a locking script; the input carries an unlocking witness. Executing both together must succeed (chapter 8 covers the full rule set; for now, assume "the signature checks out").
  • Does value balance? The sum of the values of the inputs being consumed must be greater than or equal to the sum of the values of the outputs being created — the difference is the miner's fee.

Look closely at those three checks. None of them mentions an account. None of them mentions "the sender's balance" or "the recipient's balance." Every one of them is phrased entirely in terms of individual, discrete chunks of money — coins — and whether one specific chunk is currently spendable. That observation is the entire chapter: a Bitcoin node does not store balances, and there is no account for any address. The only state a node must keep, the only thing that has to be fast to query and correct at every instant, is the answer to one question, repeated millions of times: is this specific outpoint currently unspent? That answer, for every outpoint that has ever existed, is the UTXO set — the Unspent Transaction Output set.

WHY THIS MATTERS FOR THE NEXT 10 CHAPTERS

Everything from here to the capstone leans on this distinction. Blocks (chapter 7) are a Merkle-committed history of how the UTXO set changed over time. Validation (chapter 8) is, almost entirely, a sequence of UTXO-set lookups and updates. Mining (chapter 9) races to append the next valid change to it. The mempool (chapter 11) is a queue of proposed changes that haven't been accepted yet. If you get comfortable with "the UTXO set is the database, the blockchain is the write-ahead log," the rest of the internals fall into place almost mechanically.

ARC 02 · HISTORICAL CONTEXT

From a Berkeley DB spent-flag to a purpose-built coin database

The UTXO set was not designed on a whiteboard and then implemented once. It evolved under load, mostly driven by the same pressure you'll feel in the simulator later in this chapter: the set only grows, and growth that outpaces your database's ability to stay fast is an existential problem for a peer-to-peer system with no administrator to call. DEEP CONTEXT · THE SET WAS ALWAYS THERE, JUST NOT NAMED

Even the very first Bitcoin client tracked spentness — it had to, or double-spends would validate. What changed over 15 years is not whether a UTXO concept existed but how explicitly it was modeled, how efficiently it was stored, and how much of the client's performance budget was spent servicing it. By 2017 the coin database was important enough to justify a from-scratch restructuring (§8); by 2023 it was important enough to get its own fast-bootstrap mechanism (assumeutxo, §9) precisely because rebuilding it from genesis had become the single largest cost of running a new full node.

ARC 03 · NAIVE SOLUTION

Attempt #1: give every address a balance, like a bank ledger

If you came to Bitcoin from a conventional systems background — or from the account-based model the Blockchain Fundamentals course's smart-contract chapter builds toward — the obvious first design is a ledger: one row per address, one integer column for balance, update it in place on every transfer. It is exactly how Ethereum's state trie works, and exactly how you'd build this in a SQL schema on day one.

pseudo-Cnaive_ledger.c — the strawman, annotated
struct Ledger {
    unordered_map<Address, uint64_t> balances;   /* one row per address */
};

bool ApplyTransfer(Ledger &ledger, Address from, Address to, uint64_t amount)
{
    if (ledger.balances[from] < amount)
        return false;                 /* insufficient funds */

    ledger.balances[from] -= amount;      /* mutate sender's row   */
    ledger.balances[to]   += amount;      /* mutate receiver's row */
    return true;
}

/* "What's my balance?" is now a single, cheap read: */
uint64_t GetBalance(Ledger &ledger, Address a) { return ledger.balances[a]; }

This is not a strawman built to be knocked down for sport — it is the model most engineers reach for first, it is what every bank's core ledger looks like, and it gives you something the UTXO model conspicuously does not give you for free: a balance is a field you read, not a query you compute. Keep that advantage in mind; §6 comes back to it honestly.

ARC 04 · WHY IT FAILS

A shared mutable row is a lock, and locks don't scale to "trust no one"

The ledger model's fatal flaw only shows up once you drop the assumption every bank makes: a single trusted operator serializing all writes. Bitcoin has no such operator — every node must independently arrive at the same answer, from the same inputs, with no coordination. Three consequences follow directly from "balance is a mutable cell":

  • Validation gets an ordering dependency it doesn't need to have. To apply transaction B, which spends from address X, you must already have applied every earlier transaction that touched X's balance — including ones inside the same block. Two transactions from the same busy address (an exchange hot wallet, a payment processor) cannot be checked independently; they must be serialized through that one shared cell. A UTXO input, by contrast, names a specific prior output, not an address — validating it never depends on any other input's outcome unless one transaction literally spends another's output.
  • Spending conditions have nowhere to attach. "This chunk of money needs 2-of-3 signatures" or "this chunk cannot move until block 900,000" are properties of a specific coin. A balance model has no coin — only an identity with a number next to it — so every such condition becomes a property of the address, which means every future transfer from that address inherits it, whether or not that's the intent. Bitcoin's Script (and the multisig, timelock, and Lightning-channel constructions built on it across chapters 12–14) needs conditions to be attached to individual coins, not accounts.
  • Proving "this coin is real" degenerates into proving the whole ledger is real. In the ledger model, trusting a balance means trusting every mutation that ever touched that row, transitively, back to genesis — there is no local, self-contained fact you can check. A UTXO's validity is a single, local set-membership question: is this exact outpoint currently unspent? That question has one right answer that doesn't require re-deriving anyone else's balance to compute.
A NUMBER TO ANCHOR THIS

A typical Bitcoin block confirms on the order of 2,000–4,000 transactions with roughly 1.5–2.5 inputs each — call it ~5,000 independent coin-existence checks per block, illustratively. In the UTXO model every one of those checks is a standalone hash-table lookup with no relationship to any other lookup in the block, so a validating node is free to check them in parallel across cores, limited only by I/O to the coin database. In the ledger model, any two of those 5,000 checks that touch the same address must be serialized — and popular addresses (exchanges, payment processors, the very entities that generate the most transaction volume) are exactly the ones most likely to collide. The model that scales worst under load is the one applied to the accounts that see the most load.

So the requirement crystallizes: represent money as something that can be validated locally and independently, with spending conditions attached to the money itself rather than to an identity. That is exactly what a discrete, non-fungible "coin" gives you — derived properly in §5.

ARC 05 · BETTER SOLUTION, DERIVED

Money as discrete chunks, not a number in a cell

Step through the derivation. Each step removes exactly the assumption that broke in §4.

Deriving the UTXO modelSTEP-BY-STEP
THE DEFINITION, PRECISELY

A transaction output is a (value, locking-script) pair. A transaction destroys zero or more existing outputs (its inputs, each naming a prior outpoint) and creates one or more new outputs, subject to value conservation. The UTXO set is the set of outputs that have been created and not yet named as an input by any transaction in the accepted chain. There is no other state. An address is not a row in a table — it is just a pattern a locking script can be written against; nothing in consensus ever groups outputs by address, and nothing has to.

ARC 06 · WHY THAT STILL COSTS

The bill: everything a balance gave you for free, you now compute

The UTXO model is not a free lunch — it is a deliberate transfer of complexity from validation, where it is cheap and parallel, to wallets and applications, where it is expensive and manual. Be honest about the price, the same way §6 in a ledger-based system would have to be honest about serialization bottlenecks:

  • "What's my balance?" is no longer a field — it's a scan. A wallet's balance is sum(value) for every UTXO whose locking script the wallet can satisfy. For a wallet with thousands of received payments (an exchange, a merchant), that is thousands of records to enumerate and sum, every single time, unless the wallet software maintains its own cached index — which is exactly the account-style bookkeeping §3 wanted, just rebuilt client-side instead of in consensus.
  • Change outputs are structurally forced. Coins are indivisible and non-fungible: you cannot spend "0.3 of a 1 BTC output." You must consume the whole output and, if you owed less than its value, create a new output back to yourself for the remainder. Every UTXO transaction that doesn't land on an exact match is one input consumed and (at minimum) two outputs created — one payment, one change — which is pure overhead the ledger model never has (§9's tradeoff table quantifies this).
  • Smart contracts lose persistent, addressable storage. An account model gives a contract a standing "self" with mutable storage slots that later calls can read and write — that's how a token contract's balance mapping or an AMM's reserve variables work. A UTXO has no notion of "call this coin again later and mutate its internal state" — each spend destroys the coin outright. This is precisely why Ethereum chose accounts and why Bitcoin's own smart-contract surface (covered from chapter 12 onward — multisig, timelocks, payment channels) is built from one-shot spending conditions rather than persistent contract state. Chapter 13 of the Blockchain Fundamentals course covers what the account model buys you at exactly this cost.
THE HONEST TRADE

Every one of these costs is downstream of the same design choice: consensus validates coins, not identities. That choice is what makes per-input validation local, parallel, and order-independent — and it is also exactly what makes "how much do I have" a computation instead of a lookup, forces the existence of change outputs (§10 shows what that does to the size of the UTXO set over time), and rules out persistent contract storage at the base layer. §9 tabulates this trade against the account model in full.

A PERMANENT ASTERISK

Bitcoin Core's block-connection logic special-cases height 0: the genesis block's 50 BTC coinbase output is never inserted into the UTXO set at all — a quirk baked in from the earliest code and preserved as consensus ever since, because "fixing" it would be a hard fork. Those 50 BTC have never been part of the UTXO set and never can be. "The UTXO set sums to the circulating supply" is true up to exactly one permanent exception.

ARC 08 · INTERNAL IMPLEMENTATION

Byte for byte: how one coin is actually stored

Now the mechanism at patch-level detail. Bitcoin Core's chainstate is a single LevelDB database — an ordered key-value store with no schema, no SQL, no query planner, just sorted-byte-string keys mapping to byte-string values. Every unspent output gets exactly one record.

(a) The key and the value, step by step

Step through building one real record — key, then raw value, then what actually lands in the LevelDB SST files after obfuscation. The compression math below is computed live by the same functions used in the widgets further down; the bytes you see are genuine, not illustrative hex.

Building a chainstate recordSTEP-BY-STEP

Two encoding tricks make these records small. Both exploit real-world regularities in what a coin actually looks like.

(b) CompressAmount — exploiting the fact that money is round

A raw satoshi amount is a fixed 8-byte integer. But look at any block explorer: most output values are round — whole bitcoin, whole cents' worth, exact fee-rate multiples — because humans and payment software both gravitate toward round numbers. Bitcoin Core's CompressAmount() exploits this directly: it factors out trailing decimal zeros (up to nine of them) and stores how many zeros were removed instead of the zeros themselves, then VARINT-encodes what's left. A perfectly round amount like 1.00000000 BTC collapses to a single byte; a maximally irregular amount (a value with no trailing zero at all) costs no more than the worst case, which is still smaller than 8 raw bytes for anything under about 1.8 BTC. (c) The compressed script — and the outputs it doesn't help

CScriptCompressor recognizes five standard shapes and stores each as one type byte plus the minimum data needed to reconstruct it: 0 pay-to-pubkey-hash (20-byte hash), 1 pay-to-script-hash (20-byte hash), 2/3 pay-to-compressed-pubkey (32-byte X-coordinate, sign in the type byte), 4/5 pay-to-uncompressed-pubkey (same 32 bytes — the uncompressed point is reconstructed on read). Anything else — including every native SegWit and Taproot output in existence, since this scheme predates BIP141 — falls through to a generic path that stores the script's exact length and raw bytes with no compression at all. That's a real, quietly important fact: the majority of UTXOs created since 2021 get zero script compression, only amount compression — the scheme's biggest win applies to an ever-shrinking share of new coins.

(d) The obfuscation key — a wonderfully mundane reason

Every value written to chainstate — never the keys, only the values — is XORed byte-for-byte against a fixed, randomly generated 8-byte key that Bitcoin Core creates once and stores in the database itself, under its own reserved entry. This was added in Bitcoin Core 0.15 for a reason that has nothing to do with cryptography: some antivirus software's heuristic scanners were flagging the raw, unobfuscated LevelDB files because their byte patterns happened to trip generic signature matching, causing chainstate files to be quarantined or deleted out from under a running node. XORing every value against a key scrambles those byte patterns just enough to stop the false positives. It provides no security whatsoever — the key sits in plaintext in the same database — it is pure byte-pattern noise, added to placate antivirus heuristics, not attackers.

Obfuscation in actionREAL XOR

A fixed example value XORed against a fixed example 8-byte key, repeated cyclically across the whole value — exactly what CCoinsViewDB does to every byte before it reaches disk, and undoes on every read.

(e) 2017: from one record per transaction to one record per output

Before Bitcoin Core 0.15, chainstate stored one CCoins record per transaction: a vector of all that transaction's outputs plus a bitvector marking which ones were already spent. Reading or updating a single output meant deserializing the entire vector — including sibling outputs nobody asked about — and rewriting the whole record even if only one output changed. The 0.15 restructuring gave every unspent output its own independent record, keyed by its own outpoint. Reads and writes now touch exactly the bytes they need, in-memory cache eviction (governed by -dbcache) operates at the granularity that actually matters — one coin — and a transaction with 50 outputs where only 2 are still unspent no longer drags the other 48 through memory on every access.

(f) -dbcache: the lever behind most "why is IBD slow" questions

The in-memory coins cache (CCoinsViewCache) sits between block validation and the on-disk LevelDB. During initial block download, every block's inputs must be looked up and its outputs inserted; if the cache is too small to hold the working set, each lookup risks a random disk read and each flush writes dirty coins back to LevelDB more often — and during IBD this random I/O, not signature verification, is usually the bottleneck. A larger -dbcache keeps more of the actively-touched slice of the tens-of-gigabytes UTXO set resident in RAM, directly trading memory for wall-clock sync time.

ARC 10 · PERFORMANCE & SECURITY

A set that only grows, and the coins too small to be worth spending

The UTXO set is not just a database — it is the working set every validating full node on the network must keep fast to query, forever. Unlike the block files, it cannot be pruned: pruning deletes historical blocks you no longer need to re-serve, but the chainstate is precisely the state you need right now to validate the very next block, so a validating node must always keep the whole thing, or (§9-adjacent) accept a different trust model entirely (SPV, discussed in chapter 10).

And it is monotonic in a specific sense: any output can be removed only once (when spent), but new transactions keep creating new outputs faster than old ones are consumed, so the set has grown, in round figures, from roughly 50,000 unspent outputs in Bitcoin's first year to somewhere in the neighborhood of 80 to 190 million today, occupying several gigabytes on disk — the wide range reflects genuinely different eras of usage (ordinary payments vs. the 2023 surge in inscription-carrying outputs) and the fact that the exact count drifts block by block.

Dust: coins that cost more to spend than they're worth

An output is dust when the fee required to spend it as an input exceeds its own value — spending it would cost more than it's worth, so rational wallets never do, and it sits in the UTXO set indefinitely. Bitcoin Core's relay policy computes a dustRelayFee-based threshold: roughly three times the fee to spend a typical input at that feerate. At historically common relay fees this works out to about 546 satoshis for a legacy P2PKH output and roughly half that, around 294 satoshis, for a SegWit P2WPKH output (witness data is discounted). Dust is not just an efficiency nuisance — sending unsolicited dust to addresses is a known privacy attack: if the recipient's wallet ever spends the dust alongside other coins, the common-input- ownership heuristic (§12, §15) links whatever else was in that transaction back to the recipient.

UTXO commitments: why Bitcoin doesn't do what Ethereum does

Ethereum's block header includes a state root — a Merkle-Patricia hash committing to every account balance and every contract's storage. Any client holding just the header can get a cryptographic proof of any account's state without downloading the whole trie. Bitcoin's 80-byte header (chapter 7) commits to nothing about the UTXO set at all — only to the block's own transactions via the Merkle root. This is a deliberate, and genuinely debated, absence. Committing to a rapidly-mutating set in every block means recomputing an authenticated structure on every single state change — real overhead Ethereum clients pay on every transaction, and a meaningful contributor to the difficulty of Ethereum state growth and statelessness efforts. Bitcoin's tradeoff runs the other way: validating a block costs only the deltas it introduces, but no light client can get a succinct proof that "this coin is unspent" — it must trust a full node or run one itself.

Research projects target this gap without changing consensus. Utreexo (proposed by Tadge Dryja, 2019) replaces the flat UTXO set with a forest of Merkle trees — a dynamic hash-based accumulator — so that a nodes can hold only a small set of roots while "bridge nodes" that keep the full set hand out logarithmic-size inclusion proofs alongside each transaction; the tradeoff is that every transaction must now carry proof data, and someone still has to maintain the full set to generate proofs. assumeutxo (shipped in Bitcoin Core, 2023) takes a different, more pragmatic angle: a new node loads a UTXO snapshot whose hash it trusts from its software distribution, starts serving and validating new blocks immediately from that height, and verifies the entire snapshot against genesis in the background — because there is no in-consensus UTXO commitment, that trust is placed in the snapshot's hash the way old-style checkpoints placed trust in a hard-coded block hash, not in anything the chain itself proves.

ARC 11 · REAL-WORLD INCIDENTS

Three episodes the chainstate design lived through

Incident 1: The 2015 UTXO stress tests

In mid-2015, during the early block-size debate, several parties (publicly, entities operating under names like "coinwallet.eu") ran deliberate stress-test campaigns: floods of transactions with large numbers of tiny outputs, engineered to swell the mempool and grow the UTXO set as a demonstration that block capacity was binding. The direct effect was days of elevated mempool backlogs and a visible jump in low-value UTXO creation. The indirect effect mattered more: it hardened the community's appreciation that UTXO growth is a shared, externally-imposed cost — anyone can create outputs for a few satoshis of fee, but every full node pays to store and index them forever — and it sharpened the policy discussion around dust limits and standardness rules that followed.

Incident 2: Chainstate corruption after unclean shutdowns

LevelDB, like any embedded database relying on write-ahead logging and periodic compaction, is not immune to corruption when a process is killed mid-write or when it runs on top of filesystem configurations that don't honor the fsync guarantees it assumes (certain network filesystems and some copy-on-write filesystem configurations have both been reported as culprits over the years). The symptom operators see is a "Corrupted block database detected" error on startup, with the standard recovery being a full -reindex-chainstate — replaying every block from the last valid checkpoint back through the coin database, which for a pruned or IBD-in-progress node can mean hours of recompute. The operational lesson is unglamorous but important: chainstate is precisely the state you cannot afford to lose, and unclean shutdowns (OOM kills, `kill -9`, power loss) are the one class of event that reliably threatens it.

Incident 3: assumeutxo's trust model, debated in the open

When assumeutxo was proposed and reviewed on the Bitcoin Core mailing list and in GitHub review, a real and still-live disagreement surfaced: is trusting a hash-checked UTXO snapshot shipped by the software you already trust meaningfully different from the historical practice of hard-coded checkpoints, which the project spent years trying to move away from? Proponents point out the snapshot is fully re-verified against genesis in the background and discarded if wrong, so the exposure window is temporary and bounded; critics note that a user who never waits for background verification to finish is, in the meantime, trusting a number they did not derive themselves. This is a genuinely disputed tradeoff, not a settled one — precisely because Bitcoin has no in-consensus UTXO commitment (§10) to make the snapshot self-certifying.

First, the shape of a stored coin — simplified from coins.h but faithful in structure and naming:

C++coins.h — Coin::Serialize()
class Coin {
    CTxOut out;              /* value + locking script            */
    unsigned int nHeight   : 31;
    unsigned int fCoinBase :  1;

    template<typename Stream>
    void Serialize(Stream &s) const {
        assert(!IsSpent());
        /* height and the coinbase flag are packed into ONE VarInt —
         * exactly the "packed into a VarInt" trick this chapter describes. */
        uint32_t code = nHeight * 2 + fCoinBase;
        ::Serialize(s, VARINT(code));
        ::Serialize(s, Using<TxOutCompression>(out));   /* amount + script compression */
    }
};

The amount compressor — this is the actual algorithm behind §8(b)'s live widget:

C++compressor.cpp — CompressAmount() / DecompressAmount()
uint64_t CompressAmount(uint64_t n)
{
    if (n == 0) return 0;
    int e = 0;
    while (((n % 10) == 0) && e < 9) { n /= 10; e++; }  /* strip trailing zeros */
    if (e < 9) {
        int d = (n % 10);          /* last remaining digit, 1..9 */
        n /= 10;
        return 1 + (n * 9 + d - 1) * 10 + e;
    } else {
        return 1 + (n - 1) * 10 + 9;    /* no trailing zero at all — worst case */
    }
}
/* DecompressAmount() runs this exactly in reverse. A round amount like
 * 1.00000000 BTC (8 zeros stripped) VARINT-encodes in a single byte. */

The obfuscation applied by the storage layer — simplified from txdb.cpp:

C++txdb.cpp — obfuscation, applied on every read/write
std::vector<unsigned char> obfuscate_key;  /* 8 random bytes, generated once, stored
                                        * under its own key inside this same DB */

template<typename K, typename V>
bool Write(const K& key, const V& value) {
    auto raw = Serialize(value);
    for (size_t i = 0; i < raw.size(); i++)
        raw[i] ^= obfuscate_key[i % obfuscate_key.size()];   /* NOT a security control —
                                                                * pure byte-pattern noise so AV
                                                                * heuristics stop flagging .ldb files */
    return db->Put(key, raw);
}
WHY IT WAS BUILT THIS WAY — THE SEPARATION OF CONCERNS TO STEAL

Consensus requires exactly one thing of a spend: sum(inputs) >= sum(outputs), checked against outpoints that exist and are unspent. Which specific outpoints get chosen to satisfy that sum is never a consensus question — it's entirely a wallet-policy decision, invisible to the network except through its downstream fee and privacy consequences. That's why coinselection.cpp lives under wallet/, nowhere near validation.cpp: a node with no wallet at all validates every block exactly as well as one running the fanciest coin-selection algorithm ever written. §15's simulator plays entirely inside that wallet-policy space.
