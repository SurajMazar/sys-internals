ARC 01 · THE PROBLEM

You've read the internals. Can you build the log?

Understanding an architecture by reading about it and understanding it by building it are different, transferable skills, and only the second one survives an interview whiteboard or a 3am incident. This capstone's job is to force the second kind: not "explain the ISR" but make an ISR shrink in front of you and then explain why the produce call you just issued failed. Every subsystem from chapters 1–14 gets rebuilt here in miniature, and — critically — wired together, because none of Kafka's guarantees hold in isolation. A segmented log means nothing without a sparse index cheap enough to search. A high watermark means nothing without followers that actually fetch. A consumer group means nothing without a coordinator that can fence a zombie member. This chapter stops isolating subsystems and starts assembling a system.

Define the target precisely, because "build a mini Kafka" is meaningless until you say what "working" requires. A minimum viable log must genuinely provide five properties, each one earned by a real chapter and each one testable in code, not just assertable in prose:

  • Durable, ordered, sequential storage per partition — an append-only log of immutable records, findable by offset without scanning from byte zero every time (ch. 3's segments + sparse index).
  • A byte-exact wire format — records must actually serialize to bytes and parse back, with a checksum that catches corruption, because "the network is reliable" and "disks never bit-rot" are both false (ch. 3–4).
  • At-least-once delivery that behaves like exactly-once under retries — a producer that retries a timed out batch must not create a duplicate (ch. 4's idempotence).
  • Survivable replica loss without serving unacknowledged data — followers that fall behind must be evicted from the commit path, and a consumer must never observe a record no majority of replicas has (ch. 5's ISR and high watermark).
  • Cooperative, fault-tolerant multi-consumer reading — a group of readers must partition the work, detect a dead member, and reassign without losing or duplicating partitions (ch. 7–8's coordinator), while the log itself stays bounded forever (ch. 11's retention and compaction).

Kafka's own design documents lean on this instinct. Jay Kreps' 2013 essay "The Log: What every software engineer should know about real-time data's unifying abstraction" (referenced again in §16) makes the case that a replicated log is a small, learnable primitive — offsets, append, read-by-offset — and that almost every piece of "real" distributed infrastructure (databases, caches, stream processors) is that primitive plus bookkeeping. ARC 03 · NAIVE SOLUTION

Attempt #1: an array, a push, and a prayer

Derive the architecture honestly, the way chapter 3 first derived the segmented log. The simplest possible "distributed log" isn't distributed at all: one JavaScript array, one process, no persistence, no replicas.

JSnaive_log.js — the strawman, annotated
class NaiveLog {
  constructor() { this.records = []; }        // everything lives in RAM, in one array

  append(key, value) {
    const offset = this.records.length;   // "offset" is just the array index
    this.records.push({ offset, key, value });
    return offset;                       // no disk write, no ack from anyone else
  }

  read(offset) {
    return this.records[offset];        // O(1) — arrays are wonderful, until they aren't
  }
}
// one producer, one process, one array. no crash survives. no second copy exists.

This is not a joke architecture — every one of the six components in §8–§13 is a refinement of exactly this idea, and the naive version already gets the core abstraction right: an offset is just "how many records came before this one," and reading by offset is trivially fast. That single insight survives all the way to real Kafka. What doesn't survive is everything the array is quietly assuming. ARC 04 · WHY IT FAILS

Quantify the collapse before you fix it

Each failure mode from §3 has a number attached, and the numbers are why "just be careful" is not an engineering strategy:

  • Unbounded memory. At 500 bytes/record and 50,000 records/sec (a modest single-partition Kafka workload from ch. 10's throughput math), the array grows ~25 MB/sec. A 7-day retention window — Kafka's own default — needs ~15 TB of live heap for one partition. No process holds that in RAM; you were never going to avoid disk, you were only delaying the reckoning.
  • Zero durability. kill -9 the process and every acknowledged write is gone — not "might be gone," certainly gone, because nothing left the process's address space. Chapter 3's segments-on-disk design exists entirely to make "committed" and "durable" the same word.
  • Zero fault tolerance. One process is one failure domain. There is no replica to promote, because there is no replica — this is the entire reason ch. 5 exists, and §11 rebuilds it.
  • Retries duplicate. If a producer's append() call times out on the network before the ack arrives and it resends, the naive log has no way to recognize "this is the same batch again" — it just pushes a second copy. At-least-once becomes at-least-twice, silently, which is exactly the bug ch. 4's idempotent producer (§10) was invented to close.
  • No concept of "committed." A reader calling read(offset) sees whatever was pushed last, including data no other copy has ever seen. There is no high watermark because there is nothing to watermark against — a single copy is definitionally always "fully replicated to itself."
THE NUMBERS THAT FORCE THE NEXT DESIGN

Little's Law and a back-of-envelope memory budget both point the same direction: a log that only exists in RAM cannot outlive the process, and a log that only exists once cannot outlive the machine. Fixing the first problem (persist to disk, in segments, with an index) is §5–§8's job. Fixing the second (replicate to other machines without destroying latency) is §5–§6 and §11's job. Neither fix is free — that is precisely why Kafka ships six cooperating subsystems instead of one clever data structure.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three candidates, eliminated in order

Re-derive the fix the way §5 of every chapter in this course has: propose the obvious next step, then find exactly where it still isn't enough.

Candidate A: persist the array to one file

Append each record's bytes to a single growing file, fsync on every write. Durability: solved — a crash loses nothing acknowledged. But finding offset 4,000,000 in a 15 TB file means scanning from byte zero unless you keep an index, and that index also needs to live somewhere durable. Worse: fsync per record costs a disk-rotation-or-flash-flush's worth of latency on every single write — hundreds of microseconds to low milliseconds — which caps throughput at roughly 1/fsync_latency, the same Little's-Law wall chapter 4 hits when deriving why batching exists. Solved: durability. Not solved: fast lookup, fast writes.

Candidate B: chunk into segments with a coarse index

This is ch. 3's actual answer and §8 below builds it for real: roll the file into bounded segments, and build a sparse index — not every offset, just every N bytes — mapping offset → byte position. Reads become binary-search-the-index, then a short linear scan. Segments roll at a size limit so old ones can be dropped wholesale by retention (§13) without rewriting anything. This is a genuine, permanent fix for the storage half of the problem. It does nothing at all for the fact that there is still only one copy, on one disk, on one machine.

Candidate C: replicate the whole file, synchronously, to every copy

Fix fault tolerance the naive way: on every write, block until N other machines have also written the same bytes. Now a single disk failure doesn't lose data. But the write latency is now max() over every replica, not min() — one slow disk, one GC pause, one saturated NIC on any replica stalls every producer in the cluster. There is also no answer yet for "what if a replica is down entirely" (block forever?) or "what if a replica is behind and then becomes leader" (silently lose acknowledged writes?). THE SHAPE THAT SURVIVES: ACKNOWLEDGE FROM A SHRINKING, HONEST SET

The fix isn't "replicate to everyone" or "replicate to no one" — it's replicate to a tracked, dynamic subset of replicas that are provably caught up, called the ISR, and only acknowledge once every member of that subset has the data. A replica that falls behind is evicted from the ISR rather than being allowed to slow everyone down or silently break the durability guarantee. That single idea — a membership set you shrink and grow rather than a fixed replication factor you block on — is ch. 5's entire contribution, and §11 below implements it against the segmented log from §8.

ARC 06 · WHY THAT STILL HURTS

The bill for segments + ISR replication

Candidates B and C, combined, are most of the way to Kafka — but combining them exposes costs that a single component's design never has to answer alone:

  • The index itself must stay sparse. An index entry per record is just the naive array again, moved into a second file. Every N bytes trades index size for scan length — §8's stepper shows the actual binary search + linear scan and reports bytes scanned so this tradeoff stops being abstract.
  • The HW cannot be "most replicas" — it must be "the ISR." If the high watermark advanced whenever a simple majority had the data, a replica outside the ISR could still be promoted to leader later and diverge from what consumers already read as committed. The HW is defined as the minimum fetch offset across exactly the current ISR, which is why ISR membership and HW computation cannot be two unrelated pieces of code — §11 computes them together.
  • Membership changes need a fencing token. If a leader dies and a new one is elected, and the old leader later un-partitions and starts accepting writes again believing it's still leader, you get two writers. The leader epoch (KIP-101) is the fencing token; §11 bumps it on every election and uses it to decide exactly how far a returning stale replica must truncate.
  • Consumers are now a distributed system too. Once there are multiple partitions, a single consumer reading all of them serially throws away all the parallelism replication was supposed to unlock. Multiple consumers cooperating need their own membership protocol — joins, leaves, a leader that computes assignment, a way to fence a zombie that missed a rebalance — which is §12's coordinator.
  • None of this is free to keep around forever. An ISR-replicated, indexed, infinitely-retained log still runs out of disk. §13's retention clock and compacting cleaner are what make "keep this log forever" actually mean "keep the useful part of this log forever."
THE HONEST SUMMARY

Every fix in §5 solved one failure and revealed the next one's shape. That is not a design flaw — it is what an honestly-derived distributed system looks like: durability forces segments, segments force a sparse index, fault tolerance forces replication, replication forces an ISR and epochs to stay safe, multiple consumers force a coordinator, and infinite retention forces compaction. Six problems, six components, one dependency chain. §7 draws the resulting architecture as a whole; §8–§13 build each box for real.

ARC 08 · IMPLEMENTATION 1/6

Component 1: the segmented append-only log

This is ch. 3's LogSegment/Log in miniature: a partition's data lives in a sequence of segments, each a growing byte buffer with its own sparse index — an entry every indexIntervalBytes bytes, not every record. append() rolls a new segment once the active one exceeds segmentMaxBytes. read(offset) binary-searches the sparse index for the closest entry at-or-before the target, then linearly scans batch headers forward from there — and reports exactly how many bytes it had to scan, so the sparsity/scan-length tradeoff stops being theoretical.

TOY VS REAL: kafka.log.LogSegment / OffsetIndex

Real Kafka backs each segment with two memory-mapped files — NNNN.log (the batches) and NNNN.index (the sparse offset→position map, plus a parallel .timeindex for time-based lookups) — so the index survives a restart without replaying the log, and lookups are mmap page-cache hits, not JS array scans. log.index.interval.bytes (default 4096) is the real config name behind this demo's slider. Real segments also track a RollParams deadline (segment.ms, default 7 days) so a low-traffic partition still rolls periodically — this toy only rolls on size, which the callout in the stepper above calls out at the exact line it's missing from.

ARC 09 · IMPLEMENTATION 2/6

Component 2: the record batch encoder / decoder

This is what actually sits inside every segment's byte buffer: not individual records, but batches. A batch has one shared header (base offset, base timestamp, producer id/epoch/sequence, a CRC) and then each record inside stores only deltas — offset delta and timestamp delta from the batch's base, varint/zigzag-encoded so small deltas cost a single byte. This is real bytes, genuinely serialized and genuinely parsed back, with a CRC32 covering everything from the attributes field to the end of the batch — exactly the region real Kafka's CRC32C covers.

TOY VS REAL: DefaultRecordBatch / MemoryRecordsBuilder

Real Kafka's record batch (magic v2, since 0.11 / KIP-98) additionally carries: a compression codec in the attributes byte (gzip/snappy/lz4/zstd — this toy never compresses, so its bytes-on-the-wire numbers in §10 are honestly worse than production Kafka's); a transactional bit and a control-batch bit for exactly-once transactions (KIP-98's TransactionCoordinator writes control batches this toy has no concept of); and per-record headers (arbitrary key/value metadata) — this toy writes a headers-count of zero and stops. Also note real Kafka's CRC is CRC-32C (Castagnoli, hardware-accelerated on modern CPUs via SSE4.2), not the CRC-32 (IEEE 802.3, used in zip/ethernet) this demo uses — same idea, different polynomial, chosen for real Kafka because CRC-32C has a dedicated CPU instruction and this one doesn't need it.

ARC 10 · IMPLEMENTATION 3/6

Component 3: producer batching + idempotence

This is ch. 4's RecordAccumulator and Sender in miniature. Records handed to send() don't go anywhere immediately — they sit in a per-partition buffer until either linger.ms elapses or the buffer reaches batch.size, at which point the whole buffer is handed to §9's encoder as one batch. Idempotence rides on top of that same batch boundary: every batch carries a base sequence number for this producer's (PID, partition) pair, and the partition (§11) remembers the last sequence range it accepted — so if the producer never got the ack and retries the identical batch, the broker recognizes the duplicate and returns the cached result instead of appending twice.

TOY VS REAL: RecordAccumulator / TransactionManager

Real Kafka's accumulator is a pool of pre-allocated, size-bounded buffers per partition (BufferPool, governed by buffer.memory) so producers under backpressure block or throw rather than growing memory unboundedly — this toy's buffer is just a JS array. Real idempotence (KIP-98) also tracks the last five batches per producer-partition (not one), because acks can arrive out of order across in-flight requests when max.in.flight.requests.per.connection > 1; this toy keeps a one-batch window, which is enough to prove the mechanism but would falsely reject a legitimate out-of-order retry in production. Full exactly-once (transactions, KIP-98) additionally needs a TransactionCoordinator, a transactional id, and control batches — a different, larger mechanism this capstone doesn't attempt.

ARC 11 · IMPLEMENTATION 4/6

Component 4: ISR replication, the high watermark, and leader epochs

This is ch. 5's core: every partition has a fixed replica set, one of which is leader. Followers don't get pushed data — they run a fetch loop, pulling new batches from the leader starting at their own log end offset (LEO) and appending them locally. The leader tracks every follower's reported LEO and computes the high watermark as the minimum LEO across exactly the current ISR — never higher, because that would expose data fewer than the required replicas hold. A follower that stops fetching for longer than replica.lag.time.max.ms is evicted from the ISR. A leader election bumps a monotonic epoch and records the offset it started at; a stale replica returning after a partition asks OffsetsForLeaderEpoch for the safe truncation point and cuts its log back to it before resuming — the mechanism that keeps replicas from silently diverging.

TOY VS REAL: ReplicaManager / Partition / LeaderEpochFileCache

Real followers fetch continuously on a dedicated thread pool (ReplicaFetcherThread), pipelining requests and honoring fetch.min.bytes/fetch.max.wait.ms so a fetch can also wait briefly for enough new data — this toy's followerFetch() is invoked explicitly by the console or the tick loop, with no batching-of-fetches. The leader epoch cache is a real durable file (leader-epoch-checkpoint) surviving restarts, not an in-memory array. Real Kafka also lets followers serve reads directly since KIP-392 (rack-aware follower fetching) — this toy always reads from the leader. And KIP-227's fetch sessions let a follower avoid re-sending its full partition set on every fetch request; this toy's fetchFrom() is a full, stateless request every time.

ARC 12 · IMPLEMENTATION 5/6

Component 5: the consumer group coordinator

This is ch. 7–8's GroupCoordinator: a group of consumers joinGroup(), the first joiner becomes the group leader and computes a range assignment — partitions divided as evenly as possible across members — which every member fetches via syncGroup(). Every membership change (a join, a leave, a session timeout) bumps a generation id; any heartbeat, commit, or sync carrying an old generation is rejected as coming from a zombie — a member the group has already given up on and reassigned, but which doesn't know that yet. Offset commits aren't just numbers in memory: they're appended as records to an internal log — __consumer_offsets in real Kafka — which is itself compacted by §13's cleaner, keeping only the latest committed offset per (group, topic, partition) key.

TOY VS REAL: GroupCoordinator / assignors / KIP-848

Real Kafka supports pluggable assignors — Range, RoundRobin, Sticky, and CooperativeSticky (KIP-429), which reassigns only the changed partitions instead of a full stop-the-world rebalance (this toy always fully recomputes, an "eager" rebalance in Kafka's own terminology). KIP-848's next-generation consumer protocol goes further and removes client-side assignment entirely — the group coordinator computes and pushes assignments incrementally, without a synchronized rebalance barrier at all. This toy's session-timeout detection is also a manual "advance clock and check" call; real Kafka runs this on a coordinator-side purgatory of delayed operations, firing exactly at the timeout without polling.

ARC 13 · IMPLEMENTATION 6/6

Component 6: retention and log compaction

This is ch. 11's two-part answer to "does this log grow forever": time-based retention deletes whole segments once their newest record is older than retention.ms (never the active segment — you don't delete what you're still writing to), and key-based compaction rewrites a log so that only the latest record per key survives, using an OffsetMap built by scanning every batch once. A record with a null value is a tombstone — "this key is deleted" — and once compaction has processed it, the key disappears from the log entirely rather than the tombstone lingering forever (real Kafka delays that removal by delete.retention.ms so slow consumers still see the tombstone; this toy removes it immediately, and the callout below says so).

TOY VS REAL: LogCleaner / OffsetMap / log.cleaner.min.cleanable.ratio

Real Kafka's cleaner is a background thread pool that only compacts once the dirty ratio — bytes written since the last clean, divided by total log bytes — exceeds log.cleaner.min.cleanable.ratio (default 0.5), and it never touches the active segment being written to, splitting the log into a "clean" prefix and a "dirty" tail. The real OffsetMap is a fixed-size in-memory hash map (log.cleaner.dedupe.buffer.size) — if there are more distinct keys than the map can hold, cleaning runs in multiple passes over the segment range. Retention and compaction can also both be enabled on the same topic (cleanup.policy=compact,delete) — compaction keeps the latest value per key, and retention still expires the compacted result after retention.ms. This toy runs each independently for clarity.
