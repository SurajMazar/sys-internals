STEP 01 · SETUP

A two-node cluster in one command

Everything in this lab runs against a primary plus a streaming replica, with the inspection extensions preinstalled. You need Docker with Compose v2 and about 2 GB of free RAM.

Create the project

Make a directory and drop in three files. Nothing else is required — no local PostgreSQL install, no package manager.

bash
mkdir -p pg-lab/initdb && cd pg-lab

docker-compose.yml

The primary runs with logical WAL level (needed for the CDC project in §6), a preloaded pg_stat_statements, and deliberately small shared_buffers so the buffer-cache experiments show eviction quickly. The replica is built by pg_basebackup on first start.

yamldocker-compose.yml
services:
  primary:
    image: postgres:16
    container_name: pg-primary
    shm_size: 512mb
    environment:
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: lab
      POSTGRES_DB: labdb
      POSTGRES_INITDB_ARGS: "--data-checksums"
    ports: ["5442:5432"]
    volumes:
      - ./initdb:/docker-entrypoint-initdb.d:ro
      - pgprimary:/var/lib/postgresql/data
    command: >
      postgres
      -c shared_preload_libraries=pg_stat_statements
      -c wal_level=logical
      -c max_wal_senders=10
      -c max_replication_slots=10
      -c hot_standby=on
      -c shared_buffers=128MB
      -c work_mem=4MB
      -c maintenance_work_mem=64MB
      -c track_io_timing=on
      -c log_min_duration_statement=500
      -c log_lock_waits=on
      -c log_checkpoints=on
      -c logging_collector=off
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lab -d labdb"]
      interval: 5s
      timeout: 5s
      retries: 20

  replica:
    image: postgres:16
    container_name: pg-replica
    shm_size: 256mb
    depends_on:
      primary:
        condition: service_healthy
    environment:
      PGPASSWORD: lab
    ports: ["5443:5432"]
    user: postgres
    volumes:
      - pgreplica:/var/lib/postgresql/data
    entrypoint:
      - bash
      - -c
      - |
        set -e
        if [ ! -s "$$PGDATA/PG_VERSION" ]; then
          echo "seeding replica from primary..."
          rm -rf "$$PGDATA"/*
          until pg_basebackup -h primary -U lab -D "$$PGDATA" -Fp -Xs -R -P; do
            echo "waiting for primary..."; sleep 2
          done
          chmod 0700 "$$PGDATA"
        fi
        exec postgres -c hot_standby=on -c hot_standby_feedback=off

volumes:
  pgprimary:
  pgreplica:

initdb/01-extensions.sql

Runs once, on first boot of the primary. These extensions are the whole point of the lab — they are what let you look inside the engine rather than at its results.

sqlinitdb/01-extensions.sql
-- Inspection extensions. All ship in postgres:16's contrib.
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;  -- query-level stats (ch.20)
CREATE EXTENSION IF NOT EXISTS pageinspect;         -- raw page/tuple/btree reader (ch.3,5,13)
CREATE EXTENSION IF NOT EXISTS pgstattuple;         -- bloat measurement (ch.12)
CREATE EXTENSION IF NOT EXISTS pg_buffercache;      -- shared buffer contents (ch.9)
CREATE EXTENSION IF NOT EXISTS pg_freespacemap;     -- FSM contents (ch.4)
CREATE EXTENSION IF NOT EXISTS pg_visibility;       -- visibility map (ch.4,12)
CREATE EXTENSION IF NOT EXISTS amcheck;             -- index structural verification (ch.13)
CREATE EXTENSION IF NOT EXISTS pg_prewarm;          -- load relations into cache (ch.9)
CREATE EXTENSION IF NOT EXISTS btree_gin;
CREATE EXTENSION IF NOT EXISTS pg_trgm;             -- for the GIN experiment (ch.14)

-- Replication role used by the replica's pg_basebackup.
ALTER ROLE lab WITH REPLICATION;

initdb/02-seed.sql

A schema with enough rows that plans, pages, and vacuum behaviour are all meaningful. accounts is the OLTP table, events is the big append-mostly table with a deliberately correlated timestamp (BRIN needs that in §3.11), and docs feeds the full-text and TOAST experiments.

sqlinitdb/02-seed.sql
CREATE TABLE accounts (
  id        bigserial PRIMARY KEY,
  owner     text        NOT NULL,
  balance   numeric(14,2) NOT NULL DEFAULT 0,
  status    text        NOT NULL DEFAULT 'active',
  region    text        NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE events (
  id         bigserial PRIMARY KEY,
  account_id bigint      NOT NULL,
  kind       text        NOT NULL,
  amount     numeric(12,2),
  created_at timestamptz NOT NULL,
  payload    text
);

CREATE TABLE docs (
  id    bigserial PRIMARY KEY,
  title text,
  body  text            -- long values here exercise TOAST (ch.4)
);

-- 50k accounts
INSERT INTO accounts (owner, balance, region)
SELECT 'owner_' || g,
       (random()*10000)::numeric(14,2),
       (ARRAY['us-east','us-west','eu-central','ap-south'])[1 + (g %% 4)]
FROM generate_series(1, 50000) g;

-- 500k events, physically ordered by created_at (correlation ~1.0 for BRIN)
INSERT INTO events (account_id, kind, amount, created_at, payload)
SELECT 1 + (random()*49999)::int,
       (ARRAY['deposit','withdraw','fee','transfer'])[1 + (g %% 4)],
       (random()*500)::numeric(12,2),
       timestamptz '2024-01-01' + (g * interval '30 seconds'),
       repeat('x', 40)
FROM generate_series(1, 500000) g;

-- 2k docs with bodies large enough to be TOASTed
INSERT INTO docs (title, body)
SELECT 'doc ' || g,
       repeat('the quick brown fox jumps over the lazy dog ', 200 + (g %% 800))
FROM generate_series(1, 2000) g;

CREATE INDEX ON events (account_id);
CREATE INDEX ON events (created_at);
ANALYZE;
NOTE ON THE %% IN THE SEED FILE

If you copy the SQL above into a plain .sql file, replace every %% with a single %. The doubling is only needed when the SQL is embedded in a Compose command: block, where % can be interpreted. In a standalone file a single % is correct.

Two shells you'll use constantly

Define these once. Nearly every command in this lab starts with P (primary) or R (replica).

bash
# psql into each node. -X skips ~/.psqlrc so output is predictable.
alias P='docker exec -it pg-primary psql -X -U lab -d labdb'
alias R='docker exec -it pg-replica  psql -X -U lab -d labdb'

# a shell inside the primary container (for file-level inspection)
alias PSH='docker exec -it pg-primary bash'

If you prefer a local psql client, the ports are mapped: psql -h localhost -p 5442 -U lab labdb for the primary and -p 5443 for the replica (password lab).

Teardown

bash
docker compose down          # stop, keep data volumes
docker compose down -v       # stop and DELETE all data — full reset

Several experiments deliberately damage the cluster (filling the disk with WAL, crashing mid-write). docker compose down -v && docker compose up -d always gets you back to a clean seeded state in under a minute. Use it freely.

Troubleshooting

SYMPTOMCAUSE & FIX
Port is already allocated Something already listens on 5442/5443. Change the host side of the mapping ("5542:5432") or stop the other service. The container-side port stays 5432.
Replica logs "waiting for primary" forever The primary hasn't finished initdb, or ALTER ROLE lab WITH REPLICATION didn't run. Check docker compose logs primary; if the init scripts were skipped it's because the volume already existed — run docker compose down -v and start over.
could not resize shared memory segment Docker's default 64 MB /dev/shm is too small for parallel query. The compose file sets shm_size: 512mb — make sure you didn't drop that line.
Init scripts didn't run /docker-entrypoint-initdb.d only executes when the data directory is empty. Any prior boot means it's skipped. docker compose down -v is the fix.
First start takes minutes The seed inserts 550k rows. Normal on the first boot only; subsequent starts reuse the volume.
psql: FATAL: role "lab" does not exist You're connecting to a stale volume from a different compose file. Reset with -v.

STEP 04 · PRODUCTION BEST PRACTICES

A config cookbook where every number has a reason

Most tuning guides hand you a list of settings. This one names the mechanism behind each recommendation and the failure it prevents — so you can tell when the advice doesn't apply to you.

Memory

SETTINGSTART ATMECHANISM & FAILURE PREVENTED
shared_buffers25% of RAM
(cap ~16 GB)		 The buffer pool from ch.9. Higher isn't linearly better: PostgreSQL double-buffers with the OS page cache, so past ~25% you're mostly duplicating pages the kernel already holds, while making checkpoints flush more at once and every backend's page table larger (ch.1). Above ~16 GB, turn on huge_pages or the per-backend PTE cost dominates.
effective_cache_size50–75% of RAM Not an allocation — a hint to the planner (ch.16) about how much of an index is likely cached, feeding the Mackert-Lohman formula. Set too low, the planner avoids index scans it should choose. Costs nothing to set correctly.
work_memRAM ÷ (max_connections × 3)
then round down		 Per sort or hash node, per backend — not per query and not per connection (ch.17). A query with 4 hash joins and 2 sorts can use 6× work_mem. Too low: hash joins go multi-batch and sorts spill (visible in EXPLAIN ANALYZE). Too high: OOM killer, which in the process model means a full cluster restart (ch.1).
maintenance_work_mem512 MB – 2 GB The dead-TID budget for VACUUM (ch.12) and the build memory for CREATE INDEX. Too small and vacuum makes multiple index passes over the same table — the single most common cause of vacuum never finishing on a large table.
huge_pagestry Cuts page-table entries 512× for the shared mapping. Matters above ~8 GB shared_buffers; measurable on fork cost and TLB pressure (ch.1).
THE work_mem TRAP, QUANTIFIED

200 connections × 4 MB looks like 800 MB. But if 50 of them run a query with 5 memory-using nodes, that's 50 × 5 × 4 MB = 1 GB from those queries alone, on top of everything else. The formula that actually bounds you is peak ≈ active_backends × nodes_per_query × work_mem. Set work_mem conservatively globally, then raise it per-session for the specific reporting queries that need it: SET LOCAL work_mem = '256MB'; inside their transaction.

Checkpoints and WAL

SETTINGSTART ATMECHANISM & FAILURE PREVENTED
checkpoint_timeout15min Longer means fewer full-page writes (ch.10) and less repeated flushing of hot pages, at the cost of longer crash recovery (ch.11). The default 5min is too aggressive for most write workloads.
max_wal_size4–16 GB The size trigger. If checkpoints fire on size rather than time, you get the "checkpoints are occurring too frequently" warning and a storm of full-page writes. Raise until checkpoints are time-driven.
checkpoint_completion_target0.9 (default in PG14+) Spreads the flush over 90% of the interval instead of dumping it at once — turns an I/O spike into a plateau (experiment 9).
wal_compressionlz4 (PG15+) Compresses full-page images. Trades a little CPU for a large reduction in WAL volume right after each checkpoint — which also shrinks replication bandwidth and archive size.
synchronous_commiton Turn off only if you can genuinely tolerate losing the last wal_writer_delay-ish window of committed transactions on a crash. It's a per-transaction setting — use it selectively for low-value writes rather than globally.

Autovacuum

The defaults are tuned for a small database and are actively harmful on a large one. The trigger is threshold + scale_factor × reltuples, so with the default 0.2 a 100-million-row table waits for 20 million dead tuples before vacuum starts — by which point the work is enormous and the bloat is done.

sqlglobal defaults, then per-table overrides
-- Global: more workers, far less throttling than the ancient defaults.
ALTER SYSTEM SET autovacuum_max_workers = 5;
ALTER SYSTEM SET autovacuum_vacuum_cost_limit = 2000;   -- default 200 assumes 2010 disks
ALTER SYSTEM SET autovacuum_vacuum_cost_delay = '2ms';
ALTER SYSTEM SET autovacuum_naptime = '15s';

-- Per-table: big, hot tables need a fixed threshold, not a percentage.
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor  = 0.01,   -- 1% instead of 20%
  autovacuum_vacuum_threshold     = 5000,
  autovacuum_analyze_scale_factor = 0.005,
  autovacuum_vacuum_insert_scale_factor = 0.01  -- PG13+: append-only tables need VM updates too
);
NO AMOUNT OF AUTOVACUUM TUNING BEATS A HELD XMIN HORIZON

Experiment 8 proved it: if anything pins the horizon, vacuum runs and reclaims nothing. The four culprits, in order of how often they cause outages: idle-in-transaction sessions (set idle_in_transaction_session_timeout), abandoned replication slots (set max_slot_wal_keep_size and alert on inactive slots), long analytics queries (route them to a replica), and prepared transactions left by a crashed 2PC coordinator. Monitor the horizon age directly, not just dead tuple counts.

Planner

SETTINGSTART ATMECHANISM
random_page_cost1.1 on SSD/NVMe The default 4.0 encodes a 1990s spinning-disk seek penalty. On SSD, random reads cost nearly the same as sequential, and leaving it at 4.0 systematically pushes the planner toward sequential scans (experiment 12).
default_statistics_target100, raise to 500–1000 on skewed columns Controls MCV list and histogram size (ch.16). Raise per-column with ALTER TABLE … ALTER COLUMN … SET STATISTICS rather than globally — bigger samples make ANALYZE slower everywhere.
CREATE STATISTICSon correlated column pairs Fixes the independence assumption, which is the #1 source of misestimation. If two columns are functionally related (city/state, model/manufacturer), the planner multiplies their selectivities and underestimates by orders of magnitude.

Schema design rules

  • Order columns widest-first to minimize MAXALIGN padding (ch.3). bigint, bigint, int, smallint, bool, text beats alternating wide and narrow types — worth several percent of table size on wide rows, for free.
  • Leave fillfactor headroom on hot-update tables. ALTER TABLE t SET (fillfactor=85) gives HOT updates room to keep the new version on the same page, avoiding index writes entirely (ch.6, experiment 5).
  • Index the columns you filter and join on, and stop. Every index is write amplification on INSERT and non-HOT UPDATE, plus a vacuum pass. Find unused ones with pg_stat_user_indexes.idx_scan = 0.
  • Don't index low-cardinality columns alone. A boolean or 4-value status column has selectivity ~25% — the planner will correctly ignore the index. Use a partial index on the rare value instead: CREATE INDEX ON t (id) WHERE status = 'pending'.
  • Partition only for a reason. Good reasons: dropping old data by detaching a partition instead of a mass DELETE (which creates enormous bloat), vacuum parallelism, and pruning huge scans. Bad reason: "the table is big." Planning time grows with partition count (ch.19).
  • Prefer timestamptz over timestamp, always. Same storage, no ambiguity.
  • Use text, not varchar(n), unless the limit is a real business constraint — they're the same type internally, and changing the limit is a catalog change with locking implications.

Anti-patterns and their specific damage

ANTI-PATTERNWHAT IT ACTUALLY COSTS
Long-running transactionsworst offender Pins the xmin horizon so vacuum can't reclaim anything cluster-wide; drives bloat and, eventually, wraparound pressure (ch.6, ch.12).
kill -9 on a backendAbnormal termination triggers the crash protocol: every connection dropped, shared memory rebuilt, WAL replayed (ch.1). Use pg_terminate_backend(), which is SIGTERM and a clean exit.
DDL without lock_timeoutALTER TABLE takes ACCESS EXCLUSIVE and queues behind any running query — then every subsequent query queues behind the ALTER. One slow SELECT becomes a total outage (ch.8, runbook §5.1).
ORM N+1 queriesEach round trip is a network hop plus a parse/plan cycle. 1,000 tiny queries where one join would do is the most common "the database is slow" that isn't the database.
SELECT * on TOASTed tablesForces detoasting and transfer of large values you discard (ch.4). On the docs table that's the difference between reading a heap page and reading dozens of TOAST chunks.
Mass DELETE for retentionCreates dead tuples equal to the deleted rows, and the space is only reusable after vacuum — the table never shrinks. Partition and DETACH instead.
Thousands of idle connectionsEach is a process with duplicated catalog caches and a PGPROC slot taxing snapshot computation (ch.1). Use a pooler.
Retry loops without backoff on serialization failuresAt SERIALIZABLE, conflicting transactions abort by design (ch.7). A tight retry loop turns contention into a livelock.

5.1 · Schema migration under load

  
Precondition: the table is actively queried. Risk: ACCESS EXCLUSIVE queuing behind a long
  query, blocking everything (ch.8).

  
sql


-- ALWAYS bound the wait. Without this, your migration is a hostage situation.
SET lock_timeout = '3s';

-- Safe in PG11+: adding a column with a default no longer rewrites the table.
ALTER TABLE accounts ADD COLUMN tier text DEFAULT 'standard' NOT NULL;

-- If it fails with "canceling statement due to lock timeout", retry in a loop:
DO $$
DECLARE i int := 0;
BEGIN
  LOOP
    BEGIN
      SET LOCAL lock_timeout = '3s';
      ALTER TABLE accounts ADD COLUMN tier2 text;
      RAISE NOTICE 'succeeded on attempt %%', i;
      EXIT;
    EXCEPTION WHEN lock_not_available THEN
      i := i + 1;
      IF i > 20 THEN RAISE EXCEPTION 'gave up after %% attempts', i; END IF;
      PERFORM pg_sleep(3);
    END;
  END LOOP;
END $$;

  
For indexes, never block writes:

  
sql


CREATE INDEX CONCURRENTLY idx_accounts_tier ON accounts (tier);

-- CONCURRENTLY can leave an INVALID index if it fails. Always check:
SELECT indexrelid::regclass, indisvalid
FROM pg_index WHERE NOT indisvalid;
-- Drop and recreate any invalid index (also CONCURRENTLY).

  
Verify: \d accounts shows the column; indisvalid is true.
  Rollback: ALTER TABLE accounts DROP COLUMN tier; — also ACCESS EXCLUSIVE, so use
  lock_timeout again.


  

    
OPERATIONS THAT STILL REWRITE THE WHOLE TABLE

    
Changing a column's type (except a few binary-coercible cases like varchar(50)→text),
    SET NOT NULL on a large table without a validated CHECK constraint first, and
    ALTER TABLE … SET TABLESPACE. For type changes on big tables, the safe pattern is: add a new
    column, backfill in batches, add a trigger to keep both in sync, swap, drop.

  


  
5.2 · Promote the replica (planned failover)

  
bash


# 1. Check lag is near zero BEFORE promoting.
docker exec pg-primary psql -X -U lab -d labdb -c \
  "SELECT replay_lag, pg_current_wal_lsn() - replay_lsn AS bytes_behind FROM pg_stat_replication;"

# 2. Stop writes to the primary (in real life: take it out of the load balancer).
docker stop pg-primary

# 3. Promote.
docker exec pg-replica psql -X -U lab -d labdb -c "SELECT pg_promote(wait => true);"

# 4. Verify it is now a primary on a NEW timeline.
docker exec pg-replica psql -X -U lab -d labdb -c \
  "SELECT pg_is_in_recovery(), timeline_id FROM pg_control_checkpoint();"

  
EXPECTED


 pg_is_in_recovery | timeline_id
-------------------+-------------
 f                 |           2

  
Verify: writes now succeed on the ex-replica. Rollback: there isn't one — the timeline has
  forked. The old primary must be re-attached with pg_rewind or rebuilt from a base backup
  (§5.6). This is why you verify lag before promoting.


  
5.3 · A query is running away

  
sql


-- 1. Find it, and find what it's blocking.
SELECT pid, now()-query_start AS runtime, state, wait_event_type, wait_event,
       left(query, 90) AS query
FROM pg_stat_activity
WHERE state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY query_start;

-- 2. Is it the root of a blocking tree?
SELECT pid, pg_blocking_pids(pid) AS blocked_by, left(query,60)
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- 3. Cancel first — this only aborts the query, session survives.
SELECT pg_cancel_backend(<pid>);

-- 4. Only if cancel is ignored, terminate. SIGTERM: clean, one session.
SELECT pg_terminate_backend(<pid>);

  

    
NEVER ESCALATE TO kill -9

    
If a backend ignores both cancel and terminate, it is stuck somewhere that doesn't check for interrupts —
    typically uninterruptible disk I/O or a tight loop inside a C extension. kill -9 restarts the
    entire cluster (ch.1). Diagnose instead: SELECT * FROM pg_stat_activity WHERE pid = …
    to see the wait event, and check whether the underlying storage is hung.

  


  
5.4 · Bloat is out of control

  
    
    
  1. Confirm it's real bloat, not just a large table: SELECT * FROM pgstattuple('events'); — look at dead_tuple_percent and free_percent.
    2. 
    
  2. Find what's blocking reclamation before doing anything else — run the xmin-horizon query from experiment 8. If something pins the horizon, VACUUM is pointless until you clear it.
    3. 
    
  3. Clear the blocker: terminate idle-in-transaction sessions, drop the abandoned replication slot, or wait out the legitimate long query.
    4. 
    
  4. Vacuum aggressively, with generous memory and no throttling:
      SET maintenance_work_mem='1GB'; VACUUM (VERBOSE, ANALYZE) events;
    5. 
    
  5. If space must be returned to the OS, you need a rewrite. VACUUM FULL takes ACCESS EXCLUSIVE for the whole rewrite — unacceptable on a live table. Use pg_repack instead, which rewrites online and swaps at the end with a brief lock.
    6. 
    
  6. Prevent recurrence: per-table autovacuum settings from §4, plus idle_in_transaction_session_timeout.

5.5 · Wraparound warnings in the log

  
The log says database "labdb" must be vacuumed within N transactions. You have real time
  before shutdown, but the clock is running (ch.6).

  
sql


-- 1. How close are we, per table? Highest age first.
SELECT c.relname,
       age(c.relfrozenxid) AS xid_age,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE c.relkind IN ('r','m') AND n.nspname NOT IN ('pg_catalog','information_schema')
ORDER BY age(c.relfrozenxid) DESC LIMIT 20;

-- 2. Clear the horizon blocker FIRST — same as bloat. Usually this is the whole fix.
SELECT pid, age(backend_xmin) FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL ORDER BY 2 DESC;
SELECT slot_name, active, age(xmin) FROM pg_replication_slots;

-- 3. Freeze the worst offenders explicitly, biggest age first.
VACUUM (FREEZE, VERBOSE) <table>;

-- 4. Watch the age drop.

  
Do not disable autovacuum to "reduce load" — that is how clusters reach the read-only shutdown.
  If you're already in single-user mode, the emergency path is
  postgres --single -D $PGDATA labdb then VACUUM FREEZE; per table.


  
5.6 · Disk full from a replication slot

  
Symptom: pg_wal is enormous and growing; the server may have already PANICed on write.

  
sql


-- Identify: an inactive slot with huge retention is the culprit.
SELECT slot_name, slot_type, active,
       pg_size_pretty(pg_current_wal_lsn() - restart_lsn) AS retained,
       wal_status, safe_wal_size
FROM pg_replication_slots ORDER BY 4 DESC;

-- Fix: drop the abandoned slot. WAL is released at the next checkpoint.
SELECT pg_drop_replication_slot('<slot_name>');
CHECKPOINT;

  

    
PREVENTION — SET THIS ON EVERY CLUSTER

    
ALTER SYSTEM SET max_slot_wal_keep_size = '64GB'; (PG13+). A slot that falls further behind
    than this is invalidated rather than allowed to fill the disk. You lose that consumer — which is the correct
    trade, because a full pg_wal takes down the entire primary. Alert on
    pg_replication_slots WHERE NOT active.

  


  
5.7 · Base backup and point-in-time restore

  
bash


# Take a base backup (in the lab, into the container's /tmp).
docker exec pg-primary bash -lc \
  'rm -rf /tmp/base && pg_basebackup -U lab -D /tmp/base -Fp -Xs -P'

# Note the point you want to recover to, BEFORE the mistake:
docker exec pg-primary psql -X -U lab -d labdb -c "SELECT now(), pg_current_wal_lsn();"

# To restore: start a postgres on the backup directory with a recovery target,
# e.g. recovery_target_time = '2026-07-31 12:00:00+00' in postgresql.conf
# plus an empty recovery.signal file in the data directory.

  
In production use pgBackRest or Barman rather than raw pg_basebackup — they
  handle WAL archiving, retention, compression, parallelism, and verification. The mechanism is identical
  (ch.11): a base copy plus WAL replayed forward to a target.

Project 1 · A change-data-capture consumer

  
Logical decoding (ch.18) turns the WAL into a stream of row-level changes. This is the mechanism behind
  Debezium and every "stream my database into Kafka" product. You'll build the consumer directly, with no
  framework, so the machinery is visible.


  
sqlP — create the slot


-- test_decoding ships with contrib and emits human-readable output,
-- which is perfect for learning. Production would use pgoutput or wal2json.
SELECT pg_create_logical_replication_slot('cdc_lab', 'test_decoding');

-- Make sure UPDATE/DELETE carry enough to identify the row (ch.18).
ALTER TABLE accounts REPLICA IDENTITY FULL;


  
Now generate some changes and consume them:

  
sqlP — make changes


BEGIN;
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
INSERT INTO accounts (owner, balance, region) VALUES ('cdc-demo', 500, 'us-east');
DELETE FROM accounts WHERE owner = 'cdc-demo';
COMMIT;

-- Peek does not advance the slot; get_changes consumes.
SELECT lsn, xid, data FROM pg_logical_slot_peek_changes('cdc_lab', NULL, NULL);

  
EXPECTED — the WAL, decoded into rows


    lsn    | xid |                         data
-----------+-----+------------------------------------------------------
 0/6A1B2C0 | 892 | BEGIN 892
 0/6A1B2C0 | 892 | table public.accounts: UPDATE: old-key: id[bigint]:1
           |     |   balance[numeric]:1234.00 ... new-tuple: id[bigint]:1
           |     |   balance[numeric]:1244.00 ...
 0/6A1B3F8 | 892 | table public.accounts: INSERT: id[bigint]:50001
           |     |   owner[text]:'cdc-demo' balance[numeric]:500.00 ...

Note what this shows: the reorder buffer (ch.18) has assembled a complete transaction and emitted it
  in commit order, even though the WAL interleaves concurrent transactions. Now a real consumer that
  streams continuously:


  
pythoncdc.py — run on the host: pip install psycopg2-binary


import psycopg2, psycopg2.extras, sys, time

conn = psycopg2.connect(
    host="localhost", port=5442, user="lab", password="lab",
    dbname="labdb", connection_factory=psycopg2.extras.LogicalReplicationConnection)
cur = conn.cursor()

class Consumer:
    def __call__(self, msg):
        # msg.payload is the decoded change; msg.data_start is its LSN.
        print(f"[{msg.data_start}] {msg.payload}", flush=True)
        # Acknowledging advances the slot's restart_lsn, letting the
        # primary recycle that WAL. Forget this and you get incident 5.6.
        msg.cursor.send_feedback(flush_lsn=msg.data_start)

try:
    cur.start_replication(slot_name="cdc_lab", decode=True)
except psycopg2.ProgrammingError:
    cur.create_replication_slot("cdc_lab", output_plugin="test_decoding")
    cur.start_replication(slot_name="cdc_lab", decode=True)

print("streaming… (ctrl-c to stop)")
try:
    cur.consume_stream(Consumer())
except KeyboardInterrupt:
    print("\nstopped. Slot still exists — drop it when done:")
    print("  SELECT pg_drop_replication_slot('cdc_lab');")


  
Run it in one terminal, then run UPDATEs in psql in another and watch them appear within milliseconds.

  
Extensions to try: swap test_decoding for pgoutput and parse the binary
  protocol; stop acknowledging and watch pg_replication_slots.retained grow (that's incident 5.6
  in miniature); kill the consumer mid-transaction and restart it to prove the slot resumes exactly where it
  left off.

Now change exactly one thing, with a prediction. shared_buffers is 128 MB against a 750 MB

bashchange one variable

Then attribute the change. Where did the time actually go?

  
sqlP


SELECT substring(query,1,50) AS query, calls,
       round(mean_exec_time::numeric,3) AS mean_ms,
       shared_blks_hit, shared_blks_read,
       round(100.0*shared_blks_hit/nullif(shared_blks_hit+shared_blks_read,0),1) AS hit_pct
FROM pg_stat_statements
WHERE query LIKE '%%pgbench%%' OR query LIKE '%%UPDATE%%' OR query LIKE '%%SELECT abalance%%'
ORDER BY total_exec_time DESC LIMIT 8;

  
The hit percentage is the causal link. If TPS rose and hit_pct rose with it, your mechanism
  explanation was right. If TPS rose but hit_pct didn't, something else changed and you should find out what.

  -P 5 and watch for periodic dips at checkpoints), for synchronous_commit=off (huge
  TPS gain, real durability loss — quantify both), and for -c 300 to find the connection-count
  hump from chapter 1 empirically.


  
Project 3 · A wait-event profiler

  
PostgreSQL has no built-in continuous profiler, but pg_stat_activity exposes what every
  backend is waiting on right now. Sample it fast enough and you get a statistical profile — the same
  idea as a sampling CPU profiler, applied to database waits. This is the single most useful diagnostic tool
  you can build in twenty lines.


  
pythonwaitprof.py — run on the host while a workload runs


import psycopg2, time, collections, sys

DURATION = int(sys.argv[1]) if len(sys.argv) > 1 else 30
HZ = 100  # samples per second

conn = psycopg2.connect(host="localhost", port=5442, user="lab",
                        password="lab", dbname="labdb")
conn.autocommit = True
cur = conn.cursor()

counts = collections.Counter()
samples = 0
end = time.time() + DURATION

while time.time() < end:
    cur.execute("""
        SELECT coalesce(wait_event_type,'CPU'), coalesce(wait_event,'running')
        FROM pg_stat_activity
        WHERE state = 'active' AND pid <> pg_backend_pid()
          AND backend_type = 'client backend'
    """)
    for t, e in cur.fetchall():
        counts[(t, e)] += 1
    samples += 1
    time.sleep(1.0 / HZ)

total = sum(counts.values()) or 1
print(f"\n{samples} samples over {DURATION}s — {total} active-backend observations\n")
print(f"{'PCT':>7}  {'COUNT':>7}  WAIT")
for (t, e), n in counts.most_common(20):
    bar = "█" * int(40 * n / total)
    print(f"{100*n/total:6.1f}%  {n:7d}  {t}:{e}  {bar}")


  
Run it against a pgbench load:

# terminal 1
docker exec pg-primary pgbench -U lab -c 32 -j 4 -T 60 labdb
# terminal 2
