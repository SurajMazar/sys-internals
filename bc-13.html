BLOCKCHAIN FUNDAMENTALS · CHAPTER 13

Beyond Currency:
Smart Contracts, State & Tokens

Every chapter so far has been about one question: can a network of strangers agree on the order of payments? Once you have an answer — a chain that totally orders transactions and makes rewriting history cost real work — you have, almost by accident, solved a much bigger problem: a network that can agree on the order of any state transitions can execute arbitrary programs and call the result a fact. This chapter is about what happens when you point that machinery at general computation instead of currency: the two ways to represent state, why determinism is non-negotiable, why execution needs a meter, and why the resulting systems keep failing in the same few ways.

ARC 01 · THE PROBLEM

If you can order payments, you can order anything

Chapters 5 through 11 built a specific machine: a set of nodes that, without trusting each other, agree on a single append-only sequence of payment transactions. Strip away the word "payment" and look at what the machine actually guarantees: given a starting state and a proposed transition, every honest node computes the same next state, and the network agrees on one sequence of transitions out of all the ones anyone proposed. Nothing in that guarantee is about money. It is a guarantee about ordering and determinism — which is exactly the definition of a replicated state machine, the same abstraction Lamport formalized for classical distributed systems in the 1970s and Schneider surveyed in 1990, decades before anyone called it a blockchain.

So the generalization is almost forced: if "Alice pays Bob 3 coins" is a state transition on a ledger of balances, there is no principled reason the transition function has to be "subtract from one balance, add to another." It can be arbitrary code, as long as every node runs the same code on the same inputs and gets the same output. A smart contract is just a state-transition function that got a name and an address. The blockchain becomes a distributed computer whose CPU cycles are replicated across every participant, and whose memory is the shared state that outlives any single node.

This idea predates any working implementation by two decades. In 1994, the cryptographer and legal scholar Nick Szabo coined the term "smart contract" to describe exactly this: a computerized protocol that executes the terms of an agreement, using the classic vending machine as the intuition — a piece of hardware that enforces a contract (coin in, snack out) without needing a clerk, a judge, or trust in the counterparty. Szabo had no chain to run it on; Bitcoin's Script (chapter 4 of the Bitcoin course) is deliberately not Turing-complete, and nothing existed that could safely execute arbitrary, attacker-supplied programs at global scale. The gap between "smart contracts" the idea (1994) and smart contracts the working system (Ethereum's Frontier launch, July 2015) is the entire subject of this chapter: what has to be true of a computer before you can let it run anyone's code, charge them for it, and trust the result without trusting them.

THE REFRAME, STATED PRECISELY

A blockchain-with-contracts is not "Bitcoin plus a scripting language." It is a machine with three properties that have nothing to do with currency: (1) its state is public and append-only-in-evidence; (2) its transition function is whatever code you deploy, and it runs identically on thousands of independent machines; (3) nobody — not a majority of validators, not the deployer — can unilaterally change what the code does once it runs, because "the code" and "the record of what it did" are the same replicated artifact. Everything in this chapter is downstream of making property (2) safe without giving up (1) or (3).

DEEP CONTEXT · WHY BITCOIN SCRIPT WASN'T ENOUGH

Bitcoin already has a scripting language (chapter 4, Bitcoin course) and it is deliberately limited: no loops, no persistent contract-level storage, one-shot evaluation per input. That is not an oversight — it is the safest available answer to a question this chapter spends its next four sections deriving: how do you let strangers submit arbitrary programs to run on every node on Earth without one bad program stalling the network forever? Ethereum's contribution was not "add loops" — it was building the metering system that makes loops survivable. That system is called gas, and §5 derives why it has to exist.

ARC 03 · NAIVE SOLUTION

Attempt #1: just let nodes run arbitrary code

Derive it honestly, the way the field actually had to. You have a replicated state machine; you want to let users deploy programs, not just move coins. The obvious first design: accept a transaction containing bytecode or source, have every node execute it against the current state, and adopt whatever new state a majority computed. No limits, no fees beyond a flat per-transaction charge — just "run the program."

pythonnaive_vm.py — the strawman, annotated
def apply_transaction(state, tx):
    # tx.code is attacker-supplied. Every node runs it identically
    # against the SAME starting state, and the result becomes consensus.
    program = compile(tx.code)              # arbitrary Turing-complete code
    result  = execute(program, state, tx.args)  # … just run it. No limits.
    return result                        # new state, whatever it turned out to be

# A user submits:
tx = Transaction(code="""
    total = 0
    while True:          # a typo, or a bomb — the VM can't tell which
        total += 1
""", fee=0.001)   # flat fee, unrelated to how much work runs

This is not a joke architecture — every field starts with the version that ignores the hard constraint to see what breaks. It already gets the essential idea right: state transitions are computed by code, and consensus is "every honest node computed the same result." What it is missing is any theory of cost.

ARC 04 · WHY IT FAILS

The halting problem is not a metaphor here

The naive design fails for a reason with a name: Alan Turing proved in 1936 that there is no general algorithm that decides, for an arbitrary program and input, whether that program halts. A blockchain node about to execute a submitted contract is in exactly this position — it cannot statically decide "will this finish?" for arbitrary code, only run it and find out. Three consequences follow immediately, each one fatal on its own:

  • Every node must execute every transaction to validate it. Unlike simple payment scripts, a contract's effect on state is not knowable without running it — so validation cost equals execution cost, multiplied by every node in the network. A single submitted program's cost is paid thousands of times over.
  • Undecidability means no static filter works. You cannot write a checker that rejects "programs that run forever" and accepts everything else — that checker would solve the halting problem. Any filter you write either rejects valid programs (false positives) or misses a bad one (false negatives, by Rice's theorem applied to any non-trivial semantic property of programs).
  • A flat fee makes attack the dominant strategy. If cost is independent of work performed, an attacker pays $0.001 to submit an infinite loop, and if even 10% of nodes attempt to fully validate it before giving up, that attacker has purchased an unbounded amount of the network's aggregate CPU time for a fixed, tiny price. This is a classic denial-of-service asymmetry, and it scales without bound as more attackers join.
THE NUMBERS

Suppose one malicious transaction contains a loop that runs 109 iterations of a trivial operation before a node gives up (assume no timeout — the naive design has none). At even 108 ops/sec per node, that's 10 seconds of full-node CPU time purchased for a fixed submission fee. Ten attackers submitting once a second each now demand 100 seconds of CPU per second of wall-clock time from every single validating node — an unboundable multiplier, because nothing in the fee schedule scales with the work requested. The network doesn't degrade; it halts, because "halt" is precisely the property nobody could decide in advance.

You cannot fix this by writing a smarter compiler. You have to change what "submitting a program" costs, and tie that cost to the actual work performed rather than to intent. That is the entire content of the next section — and, not coincidentally, the reason the resulting mechanism is named after a physical resource that runs out.

ARC 05 · METERING THE MACHINE

Gas: pricing the halting problem out of existence

You cannot decide in advance whether a program halts. But you can charge for every step it takes and refuse to take the next step once the payer stops paying. That sidesteps the undecidability entirely: the question is no longer "will this halt?" but "will this run out of money before it halts?" — a question with a trivial, always-computable answer, checked continuously during execution rather than predicted beforehand.

Metering: it converts "how much computation did this transaction perform?" into a single comparable number, so nodes can bound execution without understanding the program's logic. DoS pricing: it makes the cost of consuming network resources fall on whoever consumes them, proportional to consumption, closing the exact asymmetry from §4. These are separable ideas that happen to be solved by the same accounting trick — which is why "gas" survives as one word even though block-space auction dynamics (gas price, set by a market) are a completely different concern from gas cost (a fixed, protocol-defined constant per opcode). Confusing the two is the single most common category error newcomers to this material make.

ARC 06 · WHY THAT STILL COSTS

Gas solves the halting problem and opens three new ones

Metering execution is necessary and it works — no chain with a working gas mechanism has ever been halted by an infinite loop. But pricing computation as a first-class resource creates its own failure surface, and the three problems below are not edge cases; they are the headline incidents of §11.

  • Determinism becomes an absolute, not an aspiration. If ten thousand nodes must reach byte-identical state after executing the same contract, the execution environment cannot contain anything that could differ between machines: no floating point (IEEE 754 rounding differs subtly across hardware and compiler flags), no wall-clock reads, no filesystem or network access, and — critically — no true randomness, because a random number is by definition a value nodes cannot independently reproduce. Every one of these is a completely normal thing for a general-purpose program to want, and every one is banned.
  • Randomness becomes an unsolved boundary problem. Contracts that need unpredictability (lotteries, NFT trait assignment, game mechanics) cannot call a random-number generator, so early designs reached for the only "unpredictable" value visible on-chain: the current block's hash. This is exactly wrong — the miner or validator producing that block chooses which transactions and nonce go into it, and can therefore compute several candidate block hashes before publishing and pick whichever produces the outcome they want. Block hashes are miner/validator-manipulable, not random, and this exact bug has been exploited against dozens of on-chain "provably fair" gambling contracts. The two accepted fixes are structurally different: a VRF (verifiable random function) lets a party generate randomness off the manipulable path with a checkable proof, while a commit–reveal scheme forces every input to be locked in before any output is visible, so no single participant can bias the result by waiting to see it first.
  • Shared mutable state reopens every concurrency bug systems engineers thought they'd priced already. The account model (introduced properly in §7–8) makes contract storage a global key-value map that any transaction can read and write mid-execution — which means one contract calling another can hand back control before its own bookkeeping finishes. That single fact is the root cause of reentrancy, and it is the mechanism behind the largest incident in this chapter's history.

None of these three problems has a purely technical fix that makes them disappear — they are priced, coded around, or fenced off with patterns, never eliminated. The final architecture in §7 is the version of this machine that ships with all three constraints acknowledged rather than ignored.

ARC 07 · FINAL ARCHITECTURE

Two ways to represent "who owns what"

Before going inside the execution engine, meet the decision that shapes everything downstream of it: how does the chain represent state at all? There are exactly two answers in production use, and they generalize the two ways any database can represent ownership — as a set of discrete, immutable records, or as a table of mutable balances. Neither model is strictly better — each makes a different set of bugs structurally impossible and a different set of expressions structurally awkward. The rest of the chapter builds on top of the account model (because that is where contracts, gas, the EVM, and the incidents of §11 all live) but §9's comparison table returns to UTXO seriously, and §15's simulator runs the identical operation through both models so you can see the tradeoff rather than take it on faith.

THE SAME OPERATION, TWO MODELS

"Alice sends 5 tokens to Bob" under UTXO: Alice's wallet finds unspent outputs summing to ≥5 that are provably hers (valid signatures against their locking scripts), constructs a new transaction consuming them and creating two new outputs — 5 to Bob, the remainder back to Alice as "change" — and the whole thing is valid or invalid independent of any other in-flight transaction. Under the account model: a transaction says "from Alice, to Bob, value 5, nonce N"; a node checks Alice's account balance is ≥5 right now, checks the nonce is exactly one more than Alice's last transaction, then decrements Alice's balance and increments Bob's in the shared map. The UTXO transaction carries its own proof of validity; the account transaction's validity depends on the current state of a shared structure other transactions are also mutating. That single difference is the fork this whole chapter turns on.

ARC 08 · INTERNAL IMPLEMENTATION

Inside the machine that runs the code

Now the mechanism at the level you'd need to reason about a real exploit. Four pieces: (a) the UTXO and account models compared byte-for-byte, (b) the EVM as a concrete stack machine, (c) where gas is actually spent, and (d) the CALL family — the single opcode group that both enables composability and creates reentrancy.

(a) UTXO vs account, side by side

Two Python-level sketches of the identical transfer, showing exactly what each model checks and stores.

pythonutxo_transfer.py — no shared mutable state
def apply_utxo_tx(utxo_set, tx):
    # tx.inputs reference PAST outputs by (prior_txid, index)
    total_in = 0
    for ref in tx.inputs:
        out = utxo_set[ref]                       # must exist and be UNSPENT
        verify_signature(out.locking_script, ref, tx)  # proof of ownership
        total_in += out.value
        del utxo_set[ref]                     # consumed — gone forever
    assert total_in >= sum(o.value for o in tx.outputs)
    for i, out in enumerate(tx.outputs):
        utxo_set[(tx.txid, i)] = out                # brand-new, unspent
    # NOTHING here reads or writes a "balance." There is no such object.
    # Two transactions spending DIFFERENT prior outputs never touch each
    # other's data — they can validate on separate cores with zero locking.
pythonaccount_transfer.py — one shared map, everyone touches it
def apply_account_tx(state, tx):
    sender = state[tx.frm]
    assert tx.nonce == sender.nonce + 1          # replay protection — MUST be exact
    assert sender.balance >= tx.value + tx.gas_cost
    sender.balance -= (tx.value + tx.gas_cost)
    sender.nonce += 1                                # next tx from Alice must use nonce+1
    receiver = state[tx.to]                          # SAME map — any other tx could be mid-edit
    receiver.balance += tx.value
    # If tx.to is a CONTRACT, its code runs here, can call OTHER contracts,
    # which can call back into the ORIGINAL caller before this function
    # returns. That reentry is impossible to even express in the UTXO version.

Read the two side by side and the tradeoff is exact, not hand-wavy: UTXO validation needs no global lock because each transaction names its own inputs explicitly and consumes them atomically; the price is that expressing shared mutable state — an order book, a total-supply counter, a token balance map used by dozens of unrelated contracts — is awkward to impossible without layering an account-like abstraction on top (which is what Cardano's eUTXO datums and validators do). The account model gives you that shared state for free and reads like ordinary imperative code; the price is that every transaction touching an account serializes against every other transaction touching the same account, nonces must be exactly sequential (skip one and every later transaction from that sender is stuck), and any contract call can be re-entered mid-execution.

(b) The EVM: a 256-bit word stack machine

Ethereum's execution engine is not a general CPU emulator — it is a comparatively small, purpose-built stack machine whose native word size is 256 bits — chosen so that a single word can hold a Keccak-256 hash or a secp256k1-sized value without splitting it across words. It has three regions of storage with three completely different cost and persistence profiles, and confusing them is a common source of both bugs and wasted gas:

REGIONPERSISTENCEACCESS PATTERNAPPROX. GAS
Stackexecution only1024 slots max, top-of-stack only (PUSH/POP/DUP/SWAP)3 (cheap, near-free)
Memoryexecution only, expandablebyte-addressable scratch space, zeroed on entry3 + quadratic growth cost past 724 bytes
Calldataread-only, caller-suppliedthe transaction's input bytes — cheapest region to read~4 per zero byte, ~16 per non-zero byte (input)
Storagepersists in the block's state root256-bit key → 256-bit value, per-contract20,000 to set a fresh slot; 100–2,900 to touch an existing one

The four-order-of-magnitude gap between a stack operation (3 gas) and a fresh storage write (20,000 gas) is not an accident of implementation — it is a direct price signal for the actual cost each region imposes on every node forever. Storage is replicated, must be included in every future state-root computation, and must be synced by every new node joining the network years later; a stack push is forgotten the instant the call returns. Gas cost is, in this sense, an honest accounting of externalities.

(d) The CALL family: composability's engine, reentrancy's door

A contract calling another contract is what makes composability possible — a decentralized exchange calling a token contract's transfer, which calls a fee-splitter, which calls a treasury, all inside one transaction, all-or-nothing. That power runs through a small family of opcodes with different trust semantics:

OPCODECONTEXT (storage/balance)msg.sender SEEN BY CALLEERISK
CALLcallee's own storagethe calling contractcallee can execute arbitrary code, including calling back — reentrancy's door
STATICCALLcallee's own storage, no writes allowedthe calling contractread-only; state-changing reentrancy is impossible through this path
DELEGATECALLcaller's storage and balancepreserved from the original callerthe callee's code runs as the caller — a malicious or buggy library can overwrite the caller's storage directly (see the Parity incident, §11)

Every one of these hands control flow to code the calling contract does not own. That handoff — control leaving your contract before your own bookkeeping is finished — is the single mechanical fact behind reentrancy, and §11 shows exactly how it was exploited for roughly 3.6 million ETH in June 2016.

THE PATTERN THAT PREVENTS IT: CHECKS-EFFECTS-INTERACTIONS

Order every function so that (1) it checks all preconditions, (2) it updates its own state to reflect the outcome, and only then (3) it interacts with any external contract or address. A withdrawal function should zero out the caller's recorded balance before sending them funds, not after — because "after" is a window during which the recipient's fallback code, triggered by the very act of receiving funds, can call back into the withdrawal function and find the old, not-yet-zeroed balance still there. §13 walks the vulnerable and fixed versions of this function line by line.

ARC 09 · TRADEOFFS

UTXO vs account vs the alternatives, honestly

Every chain that supports programmability had to make this choice, and the spread of answers is evidence there is no dominant strategy — only different placements of the same costs.

Read the table as a proof by exhaustion: parallelism and shared expressive state pull in opposite directions, and every serious design either accepts one cost, or spends real engineering (Move's linear types, Solana's declared access lists, Cardano's datum model) trying to claw back the property the base model gave up. Nobody has found a free lunch — only better prices.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What reentrancy actually does to a balance, second by second

The DAO-style reentrancy attack is not subtle arithmetic — it is a recursive call that repeats faster than the victim contract's own bookkeeping can catch up. Model it precisely: a vulnerable withdraw() sends funds via a low-level call before zeroing the caller's recorded balance. The attacker's fallback function, invoked automatically on receipt, calls withdraw() again — and because the balance hasn't been zeroed yet, the check still passes. Beyond reentrancy, three numbers are worth internalizing for any account-model security review:

  • Attack cost for consensus-level attacks is separate from contract-level attacks. Rewriting history still costs whatever the chain's consensus mechanism prices it at (proof-of-work hashrate or proof-of-stake capital, chapters 8–9) — reentrancy and its cousins bypass consensus entirely and attack the application layer running on top of otherwise-correct consensus. A perfectly secure chain can still host a contract that loses everything in one transaction.
  • Gas bounds worst-case computation, not worst-case loss. The block gas limit caps how much CPU work a block can demand (bounding the DoS from §4), but it says nothing about how much value a single, cheap-to-execute transaction can move — The DAO's draining loop was gas-cheap per iteration; the damage was economic, not computational.
  • Bandwidth and storage cost is asymmetric between validating and joining. A node that has followed the chain since genesis pays storage costs incrementally; a node syncing from scratch must execute or verify the entire history (or trust a snapshot), which is why state growth — driven directly by the 20,000-gas storage write from §8 — is treated as a systemic cost in chapter 12's scaling discussion, not just a per-user fee.

ARC 11 · REAL-WORLD INCIDENTS

The failures that taught this field its rules

Incident 1: The DAO reentrancy (June 2016, ≈3.6M ETH)

The DAO was a venture-fund contract holding roughly 12% of all ETH in existence at the time, with a splitDAO withdrawal path that sent ETH to the caller via a raw call before updating the caller's internal token balance. An attacker's contract, invoked as the recipient of that ETH transfer, used its fallback function to call back into splitDAO recursively — each reentry saw the still-unupdated balance and was allowed to withdraw again, draining roughly 3.6 million ETH (on the order of $50M at the time) into a child DAO before the recursive calls exhausted available gas. The Ethereum Foundation and community responded with a contentious hard fork that effectively moved the drained funds to a recovery contract; the chain that rejected the fork continues today as Ethereum Classic. The technical fix that generalizes from this incident is the checks-effects-interactions pattern from §8(d); the fork itself remains one of the field's most debated events precisely because it traded "code is law" for "the community can override the ledger," a tension chapter 10's fork-choice discussion frames more generally.

Incident 2: The Parity multisig — two separate failures

Parity's multisig wallet contracts produced two distinct incidents worth separating cleanly. In July 2017, an initialization function on the wallet contract could be called by anyone after deployment (it was not restricted to run-once-by-the-deployer), letting an attacker become the wallet's owner and drain roughly 150,000 ETH from several multisig wallets. In November 2017, a user (widely reported under the handle "devops199") accidentally triggered a selfdestruct on the shared library contract that every Parity multisig wallet delegate-called into for its core logic — because that library's initialization function had the same missing-access-control flaw as the July incident, and DELEGATECALL means the library's code executes with the caller's permissions. Once the library self-destructed, every wallet that depended on it via DELEGATECALL lost access to its own logic, freezing roughly 513,000 ETH permanently — not stolen, simply unreachable, because the code that knew how to move it no longer existed anywhere on-chain. Both incidents trace to the same root cause: an unprotected initializer, and DELEGATECALL's precise semantic that "the callee's code runs with the caller's storage and identity" from §8(d).

Incident 3: Integer overflow token bugs (2018, the BEC "batchOverflow")

The EVM's 256-bit words wrap on overflow unless a contract checks explicitly (this was the default in Solidity before version 0.8.0 introduced automatic checked arithmetic). In April 2018, the BeautyChain (BEC) token's batchTransfer function multiplied a per-recipient amount by a recipient count without an overflow guard; supplying a sufficiently large amount caused the multiplication to wrap around to a tiny number that passed the balance check, while the actual transferred amount recorded per recipient was the original enormous value — effectively minting an arbitrary token balance from nothing. Multiple ERC-20 tokens sharing the same unguarded pattern were hit by nearly identical "batchOverflow" transactions within days of each other, because the vulnerable code had been copy-pasted across projects, which is its own lesson about interface-layer risk in §11's closing note on token standards.

TOKEN STANDARDS: THE INTERFACE LAYER, WITH ITS OWN BUGS

ERC-20 (fungible tokens — one balance per address) standardized transfer, balanceOf, and a separate approve/transferFrom pair so a user could authorize a contract to move tokens on their behalf. That two-step design has its own well-known race: calling approve again to change an existing allowance (say, from 100 to 50) can be front-run — a spender who sees the pending approval transaction can quickly spend the old allowance (100) before it lands, then spend the new allowance (50) after, extracting 150 instead of the intended 50. The mitigation is to always set an allowance to zero before setting it to a new nonzero value, or use increase/decreaseAllowance variants that avoid the race entirely. ERC-721 standardized non-fungible tokens — each token ID individually owned and transferable, the interface layer that made on-chain provenance for unique assets a solved, composable problem rather than a bespoke one per project.

Reading the mechanism: a metering loop and a reentrancy fix

First, the interpreter's outer loop — notice that the gas check happens before every single opcode, not once per transaction:

pythoninterpreter.py — the metering loop, simplified but structurally faithful
def run(code, gas_limit, state, msg):
    pc, stack, memory = 0, [], bytearray()
    gas_remaining = gas_limit

    while pc < len(code):
        op = OPCODES[code[pc]]

        # THE CENTRAL TRICK: charge before executing, every single step.
        # No lookahead, no static analysis of the WHOLE program — just a
        # running balance checked one instruction at a time.
        if gas_remaining < op.cost(stack, memory):
            raise OutOfGas()          # revert ALL state changes this call made
        gas_remaining -= op.cost(stack, memory)

        if op.name == "SSTORE":
            key, val = stack.pop(), stack.pop()
            # 20,000 gas if this key was never set before, far less to update —
            # the fee schedule prices "grows replicated state forever" specially.
            state.storage[msg.to][key] = val
        elif op.name == "CALL":
            # hands the REMAINING gas (or less, per EIP-150's 63/64 rule) to
            # the callee — control leaves this function here.
            sub_gas = min(gas_remaining, stack.pop())
            result, gas_used = execute_call(stack, memory, state, sub_gas)
            gas_remaining -= gas_used
            stack.append(result)
        # … PUSH/POP/ADD/JUMPI/etc. handled the same uniform way …

        pc = op.next_pc(pc, stack)

    return gas_limit - gas_remaining     # gas actually consumed

Now the vulnerable pattern, in Solidity-flavored pseudocode, and its fix. This is the exact shape of The DAO's bug, reduced to its essential four lines:

solidityvault_vulnerable.sol — interactions BEFORE effects
function withdraw() external {
    uint amount = balances[msg.sender];
    require(amount > 0);

    // (1) INTERACTION happens here — control transfers to msg.sender's
    //     code. If msg.sender is a contract, ITS fallback function runs
    //     NOW, synchronously, before this function's next line executes.
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok);

    // (2) EFFECT happens LAST — but the attacker already re-entered
    //     withdraw() from their fallback, saw the OLD balances[msg.sender]
    //     (still nonzero!), and withdrew again. And again. And again.
    balances[msg.sender] = 0;
}
solidityvault_fixed.sol — checks → effects → interactions
function withdraw() external {
    uint amount = balances[msg.sender];   // CHECK
    require(amount > 0);

    balances[msg.sender] = 0;             // EFFECT — before any external call.
                                            // A reentrant call now sees balance == 0
                                            // and require(amount > 0) fails immediately.

    (bool ok, ) = msg.sender.call{value: amount}("");  // INTERACTION, last
    require(ok);
}
WHY IT WAS BUILT THIS WAY — THE PATTERN GENERALIZES

Checks-effects-interactions is not an EVM-specific trick; it is the same ordering principle as validating a request, committing the transaction, and then sending the confirmation email — commit your own state before you hand control to something you don't own, because you may not get control back in the state you left it. The EVM makes the danger sharper than a typical web backend because "handing control to something you don't own" (a plain ETH transfer to any address) is not an opt-in API call, it is the default behavior of sending value to any contract with a fallback function — composability's core feature is also its default attack surface, and the pattern above is the entire industry's converged answer, later hardened further by reentrancy-guard modifiers (a per-call boolean lock) as defense in depth.
