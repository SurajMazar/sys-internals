ARC 01 · THE PROBLEM

Shipping a filesystem is a distribution problem, not a storage problem

Chapter 6 showed you how a container gets its root filesystem on one machine: overlay lowerdirs stacked under a fresh upperdir, assembled by pivot_root(). That machinery has an unstated assumption baked into it — that the lowerdirs already exist, sitting on local disk, ready to be mounted. Something has to put them there. An image is the answer to "how do those bytes get from a developer's laptop, through a build, through a registry, onto a thousand machines, without re-sending everything every time and without any machine trusting bytes it can't verify."

Unpack that into the actual constraints an image format must satisfy, because each one eliminates a whole category of naive design:

  • Deduplication. Ten thousand images built FROM ubuntu:22.04 share the same base filesystem. A format that can't recognize "I already have this" re-stores and re-transmits it ten thousand times.
  • Integrity. A build artifact crosses an untrusted network (the registry, a CDN, a mirror) before it is unpacked as root — as chapter 9's OCI runtime bundle — on a production machine. Silent corruption or tampering in transit must be detectable, not just unlikely.
  • Incremental change. A one-line code change should not force a multi-hundred-megabyte re-upload and re-download of a dependency tree that didn't change.
  • Separation of recipe from bytes. Metadata that never touches the filesystem — the default command, environment variables, exposed ports — shouldn't cost you a filesystem diff to change.
  • Portability across architectures. One human-facing name (myapp:1.4) must resolve to different bytes on an amd64 build server and an arm64 laptop, correctly, automatically.

The mechanism that satisfies all five at once is content addressing: every blob in the system — a layer, a config, a manifest — is named by the SHA-256 digest of its own bytes. That single idea is this chapter's spine. Everything else — Dockerfile-to-layer mapping, multi-stage builds, BuildKit's build cache, manifest lists for multi-architecture images — is a consequence of taking content addressing seriously and following it all the way through.

WHERE THIS SITS IN THE COURSE

Chapters 1–9 built and ran a single container's isolation boundary. This chapter and the next (11: registries and the Distribution Spec) are about everything that happens before a runtime ever calls clone(): how the bundle chapter 9 consumes gets built, named, and moved. The OCI Runtime Spec (ch. 9) and the OCI Image Spec (this chapter) are deliberately separate documents maintained by the same body — a runtime never needs to know how an image was built, and a builder never needs to know how a runtime executes it. That seam is why dockerd/containerd and Buildah/Podman can both produce images that runc and crun run identically.

DEEP CONTEXT · WHY TWO ALMOST-IDENTICAL SCHEMAS STILL EXIST

You will see both application/vnd.docker.distribution.manifest.v2+json and application/vnd.oci.image.manifest.v1+json in the wild. They are structurally near-twins because the OCI manifest was deliberately modeled on Docker's schema2 (2015) rather than invented from scratch — OCI's founding compromise was "standardize what already works," not "design something new." A registry, and every tool in this chapter, must handle both mediaTypes as first-class citizens; §11 shows what happens when a consumer guesses the schema instead of reading the mediaType field.

ARC 03 · NAIVE SOLUTION

Attempt #1: an image is just a tarball of the whole filesystem

Derive it honestly. You have a running container's filesystem (chapter 6) and you want to hand it to someone else. The obvious move: freeze the merged overlay view into one archive, upload it under a human-readable name, and let anyone with that name download and extract it.

bashnaive_publish.sh — the strawman
# "build": snapshot an entire running container's merged rootfs
tar -czf myapp-v1.tar.gz -C /var/lib/containers/mycontainer/merged .

# "push": upload the whole blob under a mutable name
curl -T myapp-v1.tar.gz https://registry.example/images/myapp:latest

# "pull": whoever wants it downloads the entire thing, every time
curl -o myapp.tar.gz https://registry.example/images/myapp:latest
tar -xzf myapp.tar.gz -C /var/lib/containers/newcontainer/rootfs

This is not a strawman built to be laughed at — it is genuinely how the earliest container image tooling worked, and it gets the core job done: a self-contained filesystem moves from one machine to another. It is also exactly how docker export still works today for the single case it's honest about — a flat filesystem snapshot with no layers, no history, no image config. The naive model's failure isn't that the idea is wrong; it's that it stops one step too early.

myapp:latest is a bare string pointing at whatever bytes were last uploaded under that name. Two people pulling "the same" tag five minutes apart may get different bytes with no way to know it happened.

ARC 04 · WHY IT FAILS

The naive tarball fails on every one of §1's five constraints

Put real numbers on it. Say your base image (OS packages + language runtime) is 180 MB and your application code is 2 MB, and your team ships 40 deploys a day — a conservative number for an active service.

THE ARITHMETIC OF NOT DEDUPING

No incremental transfer: every deploy re-uploads and every machine re-downloads the full 182 MB, even though 180 of those megabytes are byte-identical to yesterday's. At 40 deploys/day that's 7.28 GB/day of pure waste versus the 80 MB/day (40 × 2 MB) actually needed — a 91× overpay, before you even count fan-out to N runtime hosts. No dedup across images: 200 microservices built from the same base image store 200 independent copies of that 180 MB on the registry's disk and in every host's local cache — 36 GB where content addressing needs one copy plus 200 tiny manifests.

  • No integrity guarantee. Nothing in the naive flow lets a puller verify the bytes it received are the bytes that were pushed. A corrupted download, a compromised mirror, or a registry bug that serves the wrong blob for a name is silently accepted and pivot_root()'d into as root.
  • No name stability. :latest is a pointer, reassigned on every push. "Roll back to what was running last Tuesday" requires you to have kept your own separate record of which tarball that was — the registry itself remembers nothing.
  • Metadata costs a full re-upload. Changing the container's default command or an environment variable — zero filesystem bytes — still means re-tarring, re-uploading, and re-downloading the entire filesystem, because metadata and filesystem are the same undifferentiated blob.
  • No architecture story. One tag, one blob, one architecture. Supporting amd64 and arm64 means either two different tag names (a client-side, error-prone convention) or nothing at all.

Every one of these is fixable, and every fix is a variant of the same idea: stop naming things by human intent and start naming them by their own content. §5 derives the format that does that.

THE ONE-SENTENCE VERSION

An OCI image is a small JSON manifest that points to one JSON config blob and an ordered list of tar-diff layer blobs — and every one of those four kinds of thing (manifest, config, layer, eventually the image index in §8) is named by the SHA-256 digest of its own bytes, never by anything a human typed.

ARC 06 · WHY THAT STILL COSTS

Content addressing solves distribution and creates new sharp edges

None of these are arguments against the model — they are the bill for taking "name it by its bytes" literally, and every one of them explains a real, frequently-misdiagnosed production symptom.

  • Compression breaks digest stability across tools. The layer digest that appears in the manifest is a hash of the compressed (gzip) blob — and gzip is not a pure function of its input alone; different gzip implementations, compression levels, or even library versions can produce different compressed bytes from identical uncompressed content. Two builders that produce byte-identical filesystem diffs can legitimately disagree on the layer's manifest digest. This is exactly why the config blob separately records a diff_id per layer — the digest of the uncompressed tar stream — as the content identity that's actually stable. §8 makes this precise.
  • Cache invalidation cascades. Classic sequential builders invalidate a linear chain: the moment one instruction's cache key misses (because its own command or input changed), every instruction after it is treated as a miss too, even if a later instruction's own inputs are completely unaffected — because the builder only knows "the state I'd be building on top of has changed," not "this specific downstream step doesn't care." A one-line change near the top of a 20-line Dockerfile can force a multi-minute dependency reinstall that produces byte-identical output to what was already cached.
  • Deleted bytes aren't reclaimed across a layer boundary. Recall chapter 6: a whiteout file hides a lower layer's file from the merged view — it does not shrink the lower layer's own tar. RUN apt-get install ... followed by a separate RUN rm -rf /var/lib/apt/lists/* leaves the downloaded package cache's bytes permanently inside the first layer's blob, still transferred and stored on every pull, forever, unless you rewrite history.
  • Content addressing doesn't imply access control. A digest proves "these are the bytes that hash to this value" — it says nothing about whether those bytes should be trusted or who was allowed to push them. Integrity and authenticity are different properties; §11 (next chapter) covers signing, and §10 of this chapter covers what a digest specifically does not protect against (a secret baked into an intermediate layer is still fully recoverable from that layer's own content, digest and all).

ARC 08 · INTERNAL IMPLEMENTATION

The actual bytes: manifest, config, layers, and how a Dockerfile becomes them

Four pieces, in the order they compose: (a) the real JSON shapes of manifest and config, (b) how each Dockerfile instruction maps to a layer or to pure metadata, (c) multi-stage builds as a graph of discarded and kept stages, (d) what consolidating instructions costs and saves.

(a) The manifest and the config, annotated field by field

A manifest is deliberately tiny — it exists so a client can decide what it needs to fetch before fetching anything large. It never contains filesystem content, only descriptors: mediaType, digest, size.

jsonimage manifest — application/vnd.oci.image.manifest.v1+json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {                                  // ← descriptor for the config blob below
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:9a8f4b2c...e21d",        // hash of the config JSON's own bytes
    "size": 1857
  },
  "layers": [                                  // ← ordered bottom (base) to top (newest)
    { "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:c1e2f0...aa41", "size": 28572160 },
    { "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:77bd91...0c3f", "size": 412007 }
  ]
}

The config is where the recipe lives — everything a runtime needs to turn layers into a runnable process, plus a full build history for humans:

jsonimage config — application/vnd.oci.image.config.v1+json
{
  "architecture": "amd64", "os": "linux",
  "config": {
    "Env": ["PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin", "NODE_ENV=production"],
    "WorkingDir": "/app", "Cmd": ["node", "server.js"], "ExposedPorts": { "3000/tcp": {} }
  },
  "rootfs": {
    "type": "layers",
    "diff_ids": [                              // ← hash of UNCOMPRESSED tar per layer, same order as manifest
      "sha256:5e2f88...1b90",
      "sha256:0af73c...d417"
    ]
  },
  "history": [                                  // ← one entry per Dockerfile instruction, even metadata-only ones
    { "created_by": "WORKDIR /app", "empty_layer": true },
    { "created_by": "COPY package*.json ./" },        // no empty_layer key ⇒ false, this one has bytes
    { "created_by": "ENV NODE_ENV=production", "empty_layer": true }
  ]
}
THE FIELD EVERYONE CONFUSES: digest VS diff_id

The manifest's layers[].digest hashes the compressed blob — what's actually stored and transferred by the registry. The config's rootfs.diff_ids[] hashes the same layer's uncompressed tar stream, in the same order. They are deliberately two different digests for the same logical content, because compression isn't deterministic across tools but the filesystem diff itself is — diff_id is what you'd compare to know "is this actually the same content," and it's also the input to the chain ID algorithm your local store uses to key its layer cache (§13 shows the exact recursive formula, real from Docker's image/layer package).

(c) Multi-stage builds: a DAG of stages, most of which never ship

A multi-stage Dockerfile has several FROM lines, each starting a fresh, independent stage. COPY --from=<stage> pulls specific files out of an earlier stage's filesystem into the current one. Only the final stage's layers end up in the pushed image — every earlier stage, compilers, build caches and all, is computed, used, and then thrown away.

HARDWARE COROLLARY: HASHING IS NOT FREE

Every layer that crosses a trust boundary — written by a builder, verified by a puller — gets its SHA-256 computed at least once, sometimes twice (compressed digest on the wire, diff_id after decompression). Unaccelerated software SHA-256 runs at roughly 400–600 MB/s per core; a 1 GB layer costs on the order of 2 seconds of single-core CPU just to verify, before decompression or extraction. Modern x86 (SHA-NI) and ARMv8 crypto extensions push this into the multi-GB/s range in hardware, which is why build and pull throughput on cheap CI runners without those extensions can visibly lag identical work on newer silicon — a real, frequently misdiagnosed "why is our CI slower on this runner class" bug.

ARC 09 · TRADEOFFS

BuildKit vs Buildah: same output format, different builder architecture

The image format in §8 is identical either way — that's the entire point of a shared spec. What differs is how the builder gets there:

ASPECTDOCKER (BuildKit)PODMAN (Buildah)
Execution model Parses the Dockerfile into an LLB DAG (low-level build graph); a solver executes independent vertices — including independent FROM stages — in parallel, and caches per-vertex keyed on content, not position. Executes instructions sequentially, top to bottom, inside a real working container backed by containers/storage; each step is an actual run/copy against that container, then a commit.
Default builder BuildKit has been the default for docker build since Docker 23.0 (opt-in via DOCKER_BUILDKIT=1 since 18.09). Always Buildah — podman build is a thin CLI over the containers/buildah library; there is no separate legacy builder to opt out of.
Cache granularity Content-keyed per op in the DAG: a downstream step can stay cached even if an unrelated upstream step changed, as long as that step's own inputs are unchanged (§15's simulator shows this exactly). Sequential, position-keyed: a cache miss at step n invalidates every step after it, matching the classic pre-BuildKit Docker behavior described in §6.
Dockerfile-less builds Requires a frontend (the Dockerfile frontend is default and shipped in-tree; other frontends like Mockerfile/Nix exist but are not mainstream). first-class — Buildah's own primitives (buildah from/run/copy/commit) let you script an image build in plain shell with no Dockerfile at all; podman build is one specific way to drive those same primitives.
Build-time secrets RUN --mount=type=secret — the secret is mounted only for that one RUN, never written into any layer. --secret with the equivalent RUN --mount=type=secret syntax — same capability, same underlying guarantee, because both consume the same Dockerfile RUN --mount syntax and neither writes the secret's bytes into a committed layer.
Rootless building Rootful dockerd builds by default; rootless Docker mode supports BuildKit but with more historical friction (cgroup/network setup) than Podman's rootless-first design. rootless by default — Buildah has supported unprivileged builds via user namespaces since early releases, consistent with Podman's rootless-by-default posture (chapter 4).
Multi-arch cross-build docker buildx build --platform ... integrates QEMU user-mode emulation directly into the BuildKit workflow — one command, one Dockerfile, N architectures. podman build --platform shells out to qemu-user-static binfmt handlers the same way; assembling the resulting manifest list is a separate, explicit step via podman manifest (§8's index concept, mechanics in ch. 11).
Remote/registry cache export native — --cache-to/--cache-from can push and pull the build cache itself as registry blobs, sharing cache across CI runners. indirect — typically achieved by pushing intermediate tagged images and pulling them back with --layers, reusing the same content-addressed layer store rather than a dedicated cache export format.

Read this table the way §9 tables in earlier chapters read: neither builder is strictly better. BuildKit's DAG buys parallelism and precise cache reuse at the cost of a second, more complex build system living inside the daemon. Buildah's imperative model buys simplicity, scriptability without a Dockerfile, and reuse of the exact same storage library Podman already needs for running containers — consistent with Podman's whole design philosophy of composing existing containers/* libraries instead of running a monolithic daemon (a theme chapter 12 covers head-on).

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

What a digest actually protects — and what it doesn't

Integrity, not authorization or secrecy. A digest proves the bytes you have are the bytes that hash to that value — nothing more. It says nothing about whether those bytes should be trusted, and it does not make anything inside a layer unrecoverable.

THE SECRET-IN-A-LAYER TRAP

ARG API_KEY or ENV API_KEY=... followed later by RUN unset API_KEY does not remove the key from the image. The value was written into the config's history (build args and env are recorded there) and, if used inside a RUN, potentially into that layer's own tar bytes — and a later instruction only hides earlier content via overlay semantics (chapter 6); it never rewrites an earlier, already-hashed, already-pushed blob. Anyone who can docker save or skopeo copy the image and inspect its layers and config history gets the secret back, digest and all. The only real fix is never writing the secret to any layer or history entry in the first place — exactly what RUN --mount=type=secret (§9) is for.

ARC 11 · REAL-WORLD INCIDENTS

Three ways the image layer has actually been the attack surface

CVE-2014-9356 — path traversal during layer extraction

Before content-addressed verification was universal in the tooling of the day, Docker's image-loading path applied a layer's tar archive to the target directory largely trusting the paths inside it. A crafted layer containing path-traversal sequences (../ segments in file names) or malicious symlinks could, on vulnerable versions, cause files to be written outside the intended extraction directory during docker pull/docker load — a straightforward consequence of treating "apply this archive" as a filesystem operation without validating that every resulting path stayed inside the sandbox. Fixed in Docker 1.3.3 (December 2014) alongside a batch of related image-handling advisories. The durable lesson: content addressing tells you the blob you fetched matches its digest — it says nothing about whether the tar parser safely applies that blob's contents, which is a separate piece of code that must be hardened on its own.

CVE-2021-41190 — manifest ambiguity ("Manifest Confusion")

The OCI Distribution Spec and Docker Registry HTTP API v2 allow a single JSON document to be structurally valid as either a single-platform image manifest or a multi-platform manifest list/index, distinguished properly only by the mediaType field. Some tools in the ecosystem inferred which kind of document they were looking at by sniffing its structure (does it have a config key? does it have a manifests array?) rather than trusting mediaType strictly. That gap meant two different, spec-compliant consumers could examine the "same" manifest and validate or execute different content as trusted — a real content-confusion vulnerability class, not a hypothetical one. The fix, coordinated across the image-spec, distribution-spec, containerd, and CRI-O projects, tightened the spec language and consuming code to require strict mediaType-driven parsing. The lesson generalizes well beyond this CVE: a content-addressed system's safety depends on every consumer agreeing on what a blob means, not only on being able to verify its bytes.

2018 — cryptomining images hiding in plain sight on Docker Hub

Security researchers at Kromtech reported that 17 images published under a single Docker Hub account had been pulled a cumulative ~5 million times over roughly a year while quietly running cryptocurrency miners, with an estimated ~$90,000 in Monero mined using other people's compute. Nothing about the image format was exploited — every layer digest was perfectly valid and every manifest perfectly well-formed; the attack targeted the layer upstream of what a digest can ever protect: the decision to trust an unfamiliar publisher's tag in the first place. This is precisely the gap digest-pinning and image signing (cosign/Sigstore, podman --sign-by — chapter 11) close: a digest tells you the bytes weren't tampered with in transit; it never tells you the publisher who produced those exact bytes was trustworthy to begin with.

First, the OCI manifest and image config structs — this is the literal Go shape behind every JSON example in §8(a):

gospecs-go/v1/manifest.go & config.go — simplified, field-faithful
type Manifest struct {
    SchemaVersion int        `json:"schemaVersion"`
    MediaType     string     `json:"mediaType,omitempty"`
    Config        Descriptor   `json:"config"`
    Layers        []Descriptor `json:"layers"`
}

type Descriptor struct {
    MediaType string `json:"mediaType"`
    Digest    digest.Digest `json:"digest"`   // "sha256:" — content address
    Size      int64  `json:"size"`
}

type Image struct {
    Architecture string    `json:"architecture"`
    OS           string    `json:"os"`
    Config       ImageConfig `json:"config"`
    RootFS       RootFS      `json:"rootfs"`
    History      []History   `json:"history,omitempty"`
}

type RootFS struct {
    Type    string          `json:"type"`       // always "layers"
    DiffIDs []digest.Digest `json:"diff_ids"` // UNCOMPRESSED per-layer hash, base→top order
}

type History struct {
    Created    *time.Time `json:"created,omitempty"`
    CreatedBy  string     `json:"created_by,omitempty"`
    EmptyLayer bool       `json:"empty_layer,omitempty"`  // true ⇒ metadata-only instruction
}

Next, the real chain-ID recursion — how a local store turns "N diff_ids in order" into one stable cache key per stack depth, so alpine → alpine+curl and alpine → alpine+wget can each be cached independently while both reusing the identical bottom layer:

goimage/layer/layer.go — CreateChainID(), the real algorithm
// ChainID identifies a STACK of layers (not just one layer) by folding
// each diff_id into the running hash of everything beneath it.
func CreateChainID(dgsts []digest.Digest) digest.Digest {
    return chainID(dgsts)
}

func chainID(dgsts []digest.Digest) digest.Digest {
    if len(dgsts) == 1 {
        return dgsts[0]                 // base case: chain of 1 IS that layer's diff_id
    }
    // recursive case: hash " "
    parent := chainID(dgsts[:len(dgsts)-1])
    input  := parent.String() + " " + dgsts[len(dgsts)-1].String()
    return digest.FromString(input)   // sha256 of that string — a NEW real digest
}
WHY IT WAS BUILT THIS WAY

BuildKit's DAG exists because Dockerfile execution is not inherently linear — independent stages in a multi-stage build have no data dependency on each other, and a solver that models the build as a graph can discover and exploit that parallelism automatically, plus key its cache on which inputs actually changed rather than how far down the file you got. Buildah's imperative model exists because Podman's entire design thesis is "don't invent a new engine — compose the same containers/storage and containers/image libraries that Podman, CRI-O, and skopeo already share," so a sequential run-then-commit loop that reuses the exact same layer store Podman uses for running containers was the lower-risk, higher-code-reuse choice. The chain-ID recursion is built to fold, not just hash the list directly, so that two images sharing a long common prefix of layers also share every intermediate chain ID — the local store can answer "do I already have layers 1–5 as a stack" in one lookup instead of five.

EXPERIMENTS TO RUN

1. Build image A, then rebuild with no toggles flipped — every layer is a cache hit, digests are byte-for-byte identical. 2. Flip only "edit app.js" and rebuild — only the COPY . . layer (and everything whose command literally references it) changes; the npm ci layer keeps its old digest because its own input, package.json, didn't move. 3. Flip only "bump express" and rebuild — now the dependency-install layer changes too, because its content is a real function of package.json's bytes in this simulation, exactly like real npm ci output depends on the lockfile. 4. Compare the final manifest digest and config digest between builds — even a single changed layer changes both, because the config's diff_ids array and the manifest's layers array both include every layer's identity.
