ARC 01 · THE PROBLEM

Not a new problem — the same problem, integrated

Every chapter so far handed you one subsystem in isolation, with everything else held constant. Chapter 2 built the connection layer assuming the crypto layer already existed. Chapter 3–4 built the crypto layer assuming a reliable byte pipe was already there to carry ciphertext. Chapter 5 built delivery assuming sessions were already established. That's the correct way to teach a system — but it is not how the system actually has to work, because in the real thing every layer's assumptions are another layer's job, and a design review doesn't get to hold anything constant. The capstone's job is to put all eleven pieces back in the same room and ask the question a Staff-level design review actually asks: does this compose, under load, under failure, and under a real numbers budget — or does it just work in the demo?

Concretely, the brief: design and build a system where two people can exchange end-to-end encrypted text and media, in groups as well as one-to-one, at a scale of hundreds of millions of concurrent connections, that survives a server dying mid-conversation, a shard losing all of its in-memory state, a device going offline for days, and an attacker who steals a device's keys after the fact — without silently violating any guarantee the first eleven chapters established along the way. Six layers, and six explicit non-negotiables inherited from the chapters that derived them:

  • Connection (ch. 2, 11) — a device is reachable through a long-lived, cheap-per-connection socket, not a request/response poll, and the server must survive far more concurrent sockets than it has cores.
  • Crypto (ch. 3–4) — the server must be unable to read message content even if fully compromised, and a stolen key must not retroactively unlock past traffic (forward secrecy) or, ideally, future traffic once rotated (post-compromise security).
  • Delivery (ch. 5) — a message sent while the recipient is offline is not lost; it is durable until delivered or it expires, and duplicate transmissions never produce duplicate delivery.
  • Groups (ch. 6) — an N-member group message costs the sender one encryption, not N, and removing a member must provably deny that member all future plaintext.
  • Media (ch. 7) — large blobs are stored once, addressed by content, and never handed to a decryptor before their integrity is verified.
  • Routing / storage (ch. 10, 11) — no single process holds the whole user base in memory; a shard can die, and its users must reattach elsewhere without silent data loss.
WHAT "DESIGN IT" MEANS HERE

This chapter does not invent a new architecture — it re-derives the one this course has been building, chapter by chapter, and shows the seams where the layers actually meet: what crosses the wire between the connection layer and the crypto layer, what the delivery layer stores about a ciphertext it cannot read, what a group rekey has to push through the connection layer to every remaining member. Those seams are where real system designs succeed or quietly rot, and they are usually invisible if you only ever study one layer at a time.

WHY REAL FLEETS RUN MORE SERVERS THAN THE MINIMUM

The theoretical minimum — concurrent connections ÷ 2M — is a connection-count bound only. It ignores CPU spent on the crypto layer's per-message ratchet step (§9), the delivery layer's queue scans (§10), and the fact that chapter 11's reconnect-storm math means losing one connection server does not lose its users — it redistributes them onto the survivors within seconds, so every server must run below its ceiling with headroom to absorb its neighbors' users during a failure. That headroom is exactly the N+2 toggle above: real capacity planning budgets for the fleet to survive losing its two largest members simultaneously, not just to fit today's traffic.

ARC 03 · NAIVE SOLUTION

The strawman: one server, four wrong decisions at once

Derive honestly, as every chapter before this one has: what is the simplest thing that could plausibly be called "a messenger"? A single server, a single database table, and — for every one of the six layers — the cheapest possible choice, made in isolation, with no thought for what the other five layers need from it.

jsnaive-messenger.js — the strawman, annotated
// CONNECTION: no persistent socket at all — the client asks "anything new?" on a timer.
async function poll(user) {
  return db.query("SELECT * FROM messages WHERE to_user=? AND ts>?", [user, lastPoll[user]]);
}

// CRYPTO: transport security only. The server sees every plaintext, by construction.
function sendMessage(from, to, text) {
  db.insert({ from, to, text, ts: Date.now() });   // `text` is plaintext, at rest, in one table
}

// DELIVERY: fire-and-forget. If `to` isn't polling right now, the row just sits there —
// forever, or until someone adds a TTL nobody has thought through yet.

// GROUPS: "loop over members" — server-side, and only workable at all because there's no E2E.
function sendGroup(from, groupId, text) {
  for (const to of membersOf(groupId)) sendMessage(from, to, text);  // N writes, N rows, same plaintext N times
}

// MEDIA: base64 the photo into the same `text` column. It works, technically.

// ROUTING: one process, one database, one machine. There is no "which shard" question yet
// because there is only one place anything can be.

Exactly like chapter 1's fork()-loop strawman or chapter 3's "just use TLS" strawman, this is not a joke — it is where you are supposed to start. It also isn't wrong about everything: it is trivially consistent (one table, no races), it is the easiest possible thing to operate, and for a group project with ten users it would work fine for years. The next section prices exactly where and why it stops working, using the same kind of arithmetic §2 just built.

ARC 04 · WHY IT FAILS, QUANTIFIED

Six failures, six numbers, six chapters

Each of the naive design's four-at-once bad choices fails for a reason this course already quantified once, in isolation. Put back together, the failures compound:

  • Polling instead of persistent connections (ch. 2). At 100M concurrent devices polling every 5s, that's 20M requests/sec of pure "anything new?" overhead — before a single message is sent — against a database that chapter 2 showed a single event-driven connection server could instead hold as 2M idle, nearly-free sockets. Polling turns idle presence, which should cost ~nothing, into a standing DDoS against your own backend.
  • Server-readable plaintext (ch. 3–4). One database compromise — a leaked backup, an insider, a misconfigured replica — exposes every message ever sent, retroactively, forever. There is no key rotation that helps, because there was never a key the server didn't already have. This is the exact failure X3DH and the Double Ratchet exist to make structurally impossible, not just operationally unlikely.
  • Fire-and-forget delivery (ch. 5). Any device offline for even one poll interval loses every message sent during that window, silently — no retry, no queue, no TTL, no sent → delivered → read distinction. At real mobile connectivity rates (radios sleep, apps get killed, subways happen), that is not an edge case; it is a large, constant fraction of all traffic.
  • O(N) group fan-out server-side (ch. 6). A 250-person group message becomes 250 plaintext writes to the same table the server can already read in full — the group problem and the plaintext problem compound into "the server holds a full transcript of every group, forever," which is precisely what sender keys (§11) are built to avoid while still keeping the sender's cost at one encryption.
  • Base64 media in a text column (ch. 7). A 2 MB photo becomes ~2.7 MB of base64 text duplicated into every recipient's row with no dedup, no content addressing, and — because it's in the same plaintext column — no separation between "the server can move this blob around" and "the server can look inside it."
  • One machine (ch. 10, 11). A single process cannot hold 100M devices' presence state in memory, and when it dies — hardware fault, OOM, a bad deploy — everyone loses their session simultaneously, with no other shard to reattach to and no plan for what "come back online" even means for the survivors.
THE COMPOUND FAILURE

None of these six failures is subtle on its own — each was probably obvious to you before this course. What the eleven preceding chapters actually taught was that fixing them one at a time, in the wrong order, produces a system that still doesn't work: encrypting the naive design's plaintext column without first fixing delivery just means encrypted messages get lost instead of plaintext ones; sharding it without first fixing groups just means an O(N) fan-out now crosses shard boundaries N times. The next two sections derive the correct choice for each layer, and then the correct order to build them in.

ARC 05 · BETTER, LAYER BY LAYER

Six decisions this course already made — recomposed

Step through the six layers in dependency order: each one only becomes buildable once the layer before it exists. This is also, not coincidentally, the build order §8–§13 follow.

WHY THIS ORDER, NOT ANOTHER

Crypto has to exist before delivery, because the delivery layer's job is to durably queue ciphertext it cannot interpret — building it against plaintext and retrofitting encryption later is exactly backwards, and is a real trap teams fall into. Groups depend on crypto (sender keys are themselves Double-Ratchet-encrypted when distributed, chapter 6). Media depends on delivery (a media key travels inside a normal E2E message, chapter 7). Routing/shards is last because it is the one layer that is nearly orthogonal to the other five — it decides where a device's state lives, not what shape the state is — but it is not free, which §6 prices next.

ARC 06 · WHAT THE RIGHT ANSWER STILL COSTS

Nothing here is free — five bills that come due

Each "correct" per-layer decision in §5 is strictly better than the naive one, and every one of them still has a real, chapter-quantified cost that a design review has to accept, not paper over:

  • Connections aren't zero-cost either (ch. 2, 11). 2M idle sockets per server is a FreeBSD/Erlang achievement, not a law of nature — it needed a kernel tuned for file-descriptor scale, a per-connection process cheap enough in memory to multiply by two million, and it still means a single server failure now needs to shed two million reconnects onto its neighbors inside chapter 11's reconnect-storm window.
  • Forward secrecy costs prekeys and multi-device complexity (ch. 3, 4, 9). The Double Ratchet's forward secrecy depends on one-time prekeys that are consumed and never reused — run out, and new sessions degrade to using only the signed prekey, weakening (not breaking) the forward-secrecy guarantee for that handshake until the device replenishes its bundle. Multiple devices per account (chapter 9) multiply the number of ratchets a sender must maintain per contact.
  • Durable queues cost storage and dedup logic, forever (ch. 5). Store-and-forward means every offline device is a standing liability on server storage until TTL expiry, and at-least-once retry — the only sane choice once you accept a network can silently drop an ack — means the receiving side must dedup by a client-generated message ID or double-deliver.
  • Sender keys cost a full rekey on every membership change (ch. 6). Removing one member from a 10,000-person group forces the sender to generate a fresh chain key and redistribute it — pairwise, E2E-encrypted — to every one of the 9,999 remaining members. That redistribution is itself O(N) fan-out through the delivery layer, and it has to complete before the next group message can rely on being unreadable to the removed member.
  • Sharding costs statefulness (ch. 10, 11). The moment presence and queues live per-shard instead of on one machine, a shard failure doesn't just drop connections — it drops in-memory routing state, and every affected client's next reconnect has to re-resolve which shard now owns it, correctly, without a stale answer from a shard that's still coming back up.

None of these five bills is a reason to prefer the naive design — they are the price of the properties §1 demanded. But a design review that can't name them hasn't actually finished the design. §7 draws the final picture with all five bills visible.

Real WhatsApp connection servers are Erlang processes over kqueue/epoll, each holding a live TCP socket with TLS (Noise Pipes in the newer client protocol) already terminated, a per-device keepalive timer far more adaptive than a fixed interval (tuned per radio type — WiFi vs. cellular — to trade battery for latency), and a supervisor tree that restarts a crashed connection handler without taking any other connection down with it — chapter 1's process-per-connection isolation lesson, reapplied. ARC 09 · COMPONENT 2 — chapter 3 & 4 in miniature

The crypto layer: X3DH agreement, then a Double Ratchet that never stops turning

This is the component with zero tolerance for "close enough": the X3DH key agreement and Double Ratchet below are real curve arithmetic — an RFC 7748 Montgomery-ladder X25519 implementation, running on actual BigInt math, not a lookup table pretending to be Diffie-Hellman — composed with a from-scratch SHA-256, HMAC-SHA256, and HKDF (RFC 5869). Two independently-instantiated devices run this code and provably derive the identical 32-byte shared secret, then keep deriving fresh per-message keys forever via the ratchet, exactly as chapters 3 and 4 specified.

Forward secrecy, demonstrated rather than asserted: encrypt three messages on Alice's ratchet, let Bob receive message #3 first (which forces him to cache the skipped keys for #1 and #2 — chapter 4's out-of-order delivery mechanism), then delete message #1's cached key and try to decrypt it again.

WHAT REAL WHATSAPP/SIGNAL DOES THAT THIS TOY SKIPS

Real X3DH signs the signed prekey with an XEdDSA identity signature so a device can prove it, not just an active man-in-the-middle, generated the bundle — this toy omits signature verification entirely (a labeled simplification, not an oversight). This toy's AEAD is a from-scratch HMAC-keystream construction so the whole stack has zero external dependencies; real deployments use AES-256-GCM or ChaCha20-Poly1305, hardware-accelerated and constant-time. And the X25519 ladder here, while arithmetically faithful to RFC 7748, is not constant-time — a real implementation must resist timing side-channels that this teaching version makes no attempt to hide.

ARC 10 · COMPONENT 3 — chapter 5 in miniature

Store-and-forward delivery: per-device queues, ticks, dedup

Every device gets its own durable queue. Enqueuing is idempotent-safe: a client-generated message ID means an at-least-once retry that duplicates the enqueue call still results in exactly one delivered copy, because drain() checks a per-device seen set before handing anything to the caller. Each queued message also carries WhatsApp's familiar three-state tick lifecycle — sent → delivered → read — and a TTL past which an undelivered message is simply gone, the queue's answer to "the recipient never comes back."

WHAT REAL WHATSAPP DOES THAT THIS TOY SKIPS

Real store-and-forward persists to disk (chapter 10's Mnesia-derived storage, historically) so a full server restart doesn't lose queued messages — this toy's queue is an in-memory Map, gone on page reload. Real delivery also fans a single logical message out across every one of a recipient's devices (chapter 9's multi-device architecture) rather than one queue per account, and real TTL policy differs by message type and is tuned against measured reconnect-time distributions, not a single fixed constant.

ARC 11 · COMPONENT 4 — chapter 6 in miniature

Group layer: one encryption, server fan-out, rekey on membership change

A group's sender key chain lets any member encrypt a message once — one HMAC-derived message key, one AEAD call — and the server fans the single ciphertext out to every member's delivery queue unmodified; the server never decrypts, never re-encrypts, and never needs to. Each receiving member's local view of the sender's chain advances in lockstep with the sender's own chain, purely from the iteration counter carried in the message. Removing a member and calling rekey() generates a fresh chain key that is redistributed — pairwise, E2E — only to the members who remain.

Real sender-key distribution is itself wrapped in a pairwise Double Ratchet message per recipient (chapter 6), so this toy's distributeSenderKey() — a direct in-memory copy — stands in for what is actually N real E2E-encrypted control messages sent through §9 and §10. Real WhatsApp also caps group size and batches rekey fan-out to avoid a single membership change generating an fan-out storm against the delivery layer, and real clients cache multiple chain-key generations briefly to tolerate a member receiving messages slightly out of rekey-order.

ARC 12 · COMPONENT 5 — chapter 7 in miniature

Media layer: content-addressed blobs, MAC-before-decrypt

A photo is encrypted client-side with a fresh, random media key before it ever leaves the device. The server stores only ciphertext, addressed by the SHA-256 hash of that ciphertext — content addressing means identical encrypted blobs (the same photo forwarded twice) are stored once. The media key itself never touches the server: it travels only inside the normal E2E message (§9's ratchet), alongside the content hash. On fetch, the MAC is verified before a single byte is decrypted — a tampered blob is rejected outright, never partially decrypted into garbage.

WHAT REAL WHATSAPP DOES THAT THIS TOY SKIPS

Real media pipelines stream-cipher large files in chunks so a device never needs the whole plaintext in memory at once, and serve ciphertext from a CDN edge — chapter 7's point that the CDN, unlike the messaging backend, never needs the key at all. Thumbnails are generated client-side before encryption and sent as a separate small blob, and real deployments garbage-collect content-addressed blobs by reference count once every referencing message has expired from every recipient's device, which this toy's Map has no equivalent of.

ARC 13 · COMPONENT 6 — chapter 10 & 11 in miniature

Routing & shards: hash a user to a shard, lose the shard, reroute

Every user ID hashes (SHA-256, taking the first four bytes as an unsigned integer, modulo the shard count) to exactly one shard, deterministically — the same routing function every client and every other shard can compute independently, with no lookup table to keep consistent. Each shard holds in-memory presence state for the users routed to it. Killing a shard drops that in-memory state immediately (chapter 11's point: a shard is not durable storage, it is a cache of who's currently attached), while a separate durable queue — spanning all shards — is untouched, so queued messages for that shard's users survive the shard's death even though their live presence does not.

Real routing uses consistent hashing (not plain modulo) precisely so that changing the shard count — scaling the fleet up or down — remaps only a small fraction of users instead of nearly all of them; this toy's userId % numShards is the simple version chapter 10 introduces before deriving why consistent hashing wins at fleet-resize time. Real shard "death" is also usually graceful — a rolling restart drains connections with a reconnect hint before dying — with hard crashes handled by the reconnect-storm mitigations (jittered backoff, admission limiting) that §8 and chapter 11 cover; this toy models only the hard-crash case.

WHERE TO GO NEXT

Read the actual Signal Protocol specifications. signal.org/docs publishes the X3DH and Double Ratchet specs this chapter's crypto layer miniaturizes — read them now with a working mental model already in place, and the notation will read as familiar rather than abstract. Pay particular attention to the parts this toy labeled as simplifications: XEdDSA signature verification on the signed prekey, and the exact KDF chaining constants.

Read WhatsApp's security whitepaper. It documents, at the level of an engineering disclosure rather than a marketing page, exactly how X3DH and the Double Ratchet are deployed across WhatsApp's real client and server architecture — the closest published source to "how chapters 3, 4, and 9 actually fit together in production."

Study Erlang/OTP and its Code BEAM talks. Chapter 1's process-per-connection philosophy and chapter 11's supervisor-restart discipline are BEAM's native idioms; the annual Code BEAM and former Erlang Factory talks include multiple WhatsApp-engineering presentations on exactly the connection-layer and reliability numbers this capstone built a numbers budget around.

Read RFC 9420, the Messaging Layer Security (MLS) protocol. MLS is the IETF's answer to the group-layer problem §11 miniaturized with sender keys — it generalizes group key agreement to a tree-based structure (TreeKEM) that gets rekey cost down from O(N) to O(log N) per membership change, the natural next question after building sender keys yourself and feeling that O(N) rekey cost directly.

Build a real toy messenger. Take this chapter's engine outside the browser: swap the in-memory `Map`-backed queue for a real database, the simulated sockets for real WebSockets, and the toy AEAD for AES-256-GCM from a real crypto library. Every design decision in this course will re-derive itself the moment you have to make it hold up against a real network instead of a `setTimeout`.
