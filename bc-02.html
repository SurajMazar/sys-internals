BLOCKCHAIN FUNDAMENTALS · CHAPTER 02

Hash Functions: Commitment
and Puzzle-Friendliness

Every artifact you will study in this course — the block header, the Merkle root, the address derived from a public key, the proof-of-work itself — is a hash output. This chapter builds the primitive from first principles: what a cryptographic hash function must guarantee, how those guarantees are constructed and where they structurally leak, and exactly how SHA-256 turns a message into 32 bytes, round by round. By the end you will have a working SHA-256 implementation you wrote the logic for, verified against the official test vector.

ARC 01 · THE PROBLEM

You need a function that commits, and a function that costs

Strip away every other piece of blockchain machinery and ask what is actually needed at the very bottom. A distributed ledger has to let a party commit to some data now and reveal or prove facts about it later, without a trusted intermediary — and it has to impose a real, unavoidable cost on anyone who wants to influence whose version of history is used. Two needs, and it turns out one primitive supplies both.

The first need is a commitment scheme: a way to seal a value in an envelope you hand over now, such that you cannot swap what's inside later, and nobody can peek before you open it. Block headers commit to every transaction in a block this way; digital signatures commit a signer to a message; a Merkle root (chapter 3) commits to an entire data set. The second need is a puzzle that can only be solved by search — a computation with no shortcut, where the only way to find an input satisfying some condition is to try inputs one at a time. That is what makes proof-of-work meaningful: if there were an algorithm to jump straight to a qualifying nonce, "spending work" would mean nothing.

Remarkably, a single primitive — a cryptographic hash function — supplies both properties simultaneously, for reasons this chapter derives rather than asserts. Formally, a hash function is a map

maththe object of study
H : {0,1}* → {0,1}ⁿ

// arbitrary-length input, FIXED-length n-bit output.
// For SHA-256, n = 256. That's it: one deterministic function,
// no keys, no randomness, no state carried between calls.

Determinism and fixed output length are trivial to achieve — return 0 satisfies the signature. Everything interesting about a cryptographic hash function lives in three adversarial games it must be hard to win, plus one more property blockchains specifically lean on. Defining those games precisely, and seeing exactly where naive constructions fail them, is the rest of this chapter.

WHY THIS MATTERS FOR THE NEXT 12 CHAPTERS

Merkle trees (ch. 3) are repeated hashing. Digital signatures (ch. 4) sign a hash of the message, never the message itself. The ledger's tamper evidence (ch. 5) is a hash chain. Proof-of-work (ch. 8) is a search over hash outputs for one below a target. If you understand what a hash function actually promises — and, just as importantly, what it does not promise — the rest of the course is mostly application of this one idea.

DEEP CONTEXT · WHY BITCOIN PICKED SHA-256, NOT SOMETHING NEWER

When Satoshi Nakamoto wrote the Bitcoin whitepaper in 2008, SHA-256 (published 2001, NSA design, NIST standard) was seven years old, had survived cryptanalytic attention, and — critically — had an existing hardware ecosystem and was already trusted in TLS and IPsec. SHA-3 did not exist yet (the Keccak team wouldn't win NIST's competition until 2012, standardized 2015). Choosing a boring, heavily-reviewed primitive over something newer and more elegant is a pattern you will see again in this course: consensus systems cannot patch a hash function without a hard fork, so the bar for "good enough to bet a monetary system on" is conservatism, not novelty.

ARC 03 · NAIVE SOLUTION

Attempt #1: a checksum is "basically" a hash, right?

Before reaching for SHA-256, ask the honest naive question: don't we already have functions that map arbitrary data to a fixed-size fingerprint? Yes — CRC32, universal in Ethernet frames, ZIP files, and disk sectors. It is fast, standardized, and produces a compact 32-bit fingerprint. Could it serve as a commitment — "I commit to this transaction by publishing its CRC32"?

pythonnaive_commit.py — the strawman
def commit(data: bytes) -> int:
    # CRC32: division of the message polynomial by a fixed
    # generator polynomial over GF(2). 32 bits of output.
    return crc32(data)

# Alice publishes commit(tx) today, reveals tx tomorrow.
# Anyone can recompute crc32(tx) and check it matches.
# Looks exactly like a commitment scheme... until you
# ask what it costs an adversary to CHEAT.

This is not a silly strawman — CRC32 genuinely is a hash function by the definition in §1: arbitrary input, fixed 32-bit output, deterministic. It is fast enough to run at wire speed inside network cards. If "arbitrary input → fixed output" were the whole specification, this section would end here.

ARC 04 · WHY IT FAILS

CRC32 is linear — and linearity is fatal to a commitment

CRC32 was designed to catch accidental corruption — flipped bits from noisy links or scratched disks — not to resist an adversary who is trying to find a collision on purpose. The reason it fails as a commitment is structural, not a matter of degree: CRC is a linear function over GF(2). Treat the message as a polynomial M(x) over the field with two elements; CRC32 is division by a fixed generator polynomial G(x) of degree 32, and the remainder is the checksum. Linearity means:

maththe break, in one line
CRC(A ⊕ B) = CRC(A) ⊕ CRC(B)      // ⊕ = XOR, bitwise

// Consequence: given any message M and its CRC, an attacker who
// wants a DIFFERENT message M' with the SAME crc need only find a
// "patch" P such that CRC(P) = CRC(M) ⊕ CRC(M'_target), then set
// M' = M'_target ⊕ P. Solving for P is one linear-algebra step —
// Gaussian elimination over a 32-bit space. No search required.

Quantify what that means for Alice's commitment: to forge a message with a chosen CRC32, an attacker does not search 2³² candidates — they solve one system of linear equations, in microseconds, on a laptop, using the reference algorithm built into `zlib`. There is a name for this specific attack: appending or inserting bytes so a file's CRC comes out to an attacker-chosen value is a textbook technique used against firmware update checks and archive integrity checks that mistake CRC32 for a security control. The failure mode is total: not "somewhat weaker than expected," but zero effective collision resistance, because collision resistance was never part of the design brief.

THE NUMBERS

A 32-bit output space has 4.29 billion possible checksums — already too small for safety even with an ideal, non-linear hash (§6 derives why). But CRC32's real weakness has nothing to do with output size: it would fail identically at 256 bits, because the exploitable property is algebraic structure, not shortage of bits. This is the first lesson a cryptographic hash function must satisfy: a real hash function's output must depend on the input in a way with no exploitable algebraic relationship whatsoever — informally, it must behave like a random oracle.

So the requirement is not "hash the data" — CRC32 already does that — it is "hash the data with a function that has been engineered specifically to resist an adversary hunting for the three kinds of forgery below." Time to define them precisely.

ARC 05 · THE THREE PROPERTIES (PLUS ONE)

Preimage, second-preimage, collision — and puzzle-friendliness

A cryptographic hash function is defined not by what it computes but by which adversarial games are computationally infeasible to win against it. Step through all four — the first three are the textbook triad; the fourth is the property that makes hashing double as a proof-of-work primitive, which no textbook on general-purpose cryptography needs to name, but which every blockchain depends on.

The four games a hash function must winSTEP-BY-STEP
THE IMPLICATION CHAIN — AND WHY IT ONLY GOES ONE WAY

Collision resistance implies second-preimage resistance for any hash function whose input space is larger than its output space (which is every practical hash function): if you could find a second preimage for an arbitrary target message, you would immediately have a collision — that target and your found message. But collision resistance does not imply preimage resistance in general, and second-preimage resistance does not imply collision resistance at all (an attacker choosing both messages has strictly more freedom than one stuck matching a fixed target). Treat all three as independent design requirements — good hash functions happen to deliver all three from the same construction, but that is a design achievement, not a logical necessity.

ARC 06 · THE REAL COSTS

Even a perfect hash function has a price — two of them

Suppose, for a moment, you had access to a genuine random oracle — the theoretical best case, with none of CRC32's algebraic weaknesses. You would still pay two costs, one information-theoretic and unavoidable, one structural and avoidable by a different construction.

Cost 1: the birthday bound halves your collision security for free

This is not a weakness of any specific algorithm — it's a fact about search over a finite output space, and it applies to a perfect random oracle exactly as it applies to SHA-256. The question: how many random samples from an n-bit output space until two of them collide?

maththe birthday bound, derived
// N = 2ⁿ possible outputs. After k samples, probability of
// NO collision yet ≈ product of (1 - i/N) for i = 1..k-1
// ≈ exp(-k(k-1)/2N)  for k << N   (standard approximation)
//
// Set P(collision) = 1/2 and solve for k:

exp(-k²/2N) = 1/2
   k²/2N    = ln 2
   k        = √(2N · ln2)  ≈  1.1774 · √N  ≈  √N

// For an n-bit hash, N = 2ⁿ, so k ≈ 2^(n/2).
// SHA-256: n = 256  →  expected collision after ~2¹²⁸ tries.
// Compare to preimage search: no shortcut exists, so finding
// ONE specific target still costs the full 2²⁵⁶ tries.

This is why cryptographers always describe a 256-bit hash as offering "128 bits of collision security" but "256 bits of preimage security." The birthday bound is not a flaw to patch — you cannot patch arithmetic — it is why hash functions are built with output lengths twice the security level you actually want against collision attacks. It is also the direct reason MD5's 128-bit output (64-bit collision security, ≈1.8×10¹⁹ operations) fell to practical attack while its full 128-bit preimage resistance has never been broken in practice: collisions are the birthday-bound's cheap target, preimages are the expensive one.

Cost 2: the Merkle–Damgård chaining structure leaks itself

The construction almost every classical hash function uses (detailed fully in §7) processes a message in fixed-size blocks, feeding each block's output in as the next block's starting state. That internal state, right before the final block is processed, is the hash of everything so far — and for an unkeyed hash, that intermediate state is exactly what gets published as the digest. This single structural fact enables the length-extension attack: because the published digest of M literally is the internal chaining state after processing M, anyone can resume the compression function from that state and keep hashing — computing H(M ‖ padding ‖ X) for attacker-chosen X, without ever having seen M, as long as they know len(M) (which is usually public or guessable).

This breaks a construction that looks obviously safe at first glance: a homemade MAC built as tag = H(secret ‖ message). An attacker who intercepts (message, tag) and knows or guesses the secret's length can forge a valid tag for message ‖ padding ‖ extra — a longer message the sender never authorized — without ever learning secret. Watch it happen for real below: this widget runs an authentic SHA-256 implementation on both sides. The "server" computes a real digest of a secret it never shows you; the "attacker" panel, given only that digest and the secret's length, forges a hash for an extended message using nothing but chain-resumption — and the two digests match, byte for byte.

WHY HMAC AND SHA-3'S SPONGE DON'T HAVE THIS PROBLEM

HMAC sidesteps length extension without changing the underlying hash at all: it computes H(key ⊕ opad ‖ H(key ⊕ ipad ‖ message)) — the outer hash's input is itself a full hash output plus a second derived key, so an attacker who chain-resumes from the published tag is resuming the outer hash's state, which was never built from a message with a guessable, extendable suffix; there is no secret hiding at the front of a message the attacker can quietly extend. SHA-3 / Keccak fixes it architecturally: its sponge construction keeps part of its internal state (the "capacity") forever hidden — only the "rate" portion is ever exposed as output — so the full internal state is never disclosed the way Merkle–Damgård's chaining value is. You cannot resume a computation from state you never got to see.

ARC 07 · FINAL ARCHITECTURE

The Merkle–Damgård construction, piece by piece

Given the costs above are either unavoidable (birthday bound) or acceptable with the right usage discipline (length extension, fixed by HMAC/sponge constructions when needed), the industry's answer for SHA-1, SHA-256, and the whole MD family is the Merkle–Damgård construction — proven by Merkle and Damgård independently in 1989 to turn any collision-resistant compression function into a collision-resistant hash function over arbitrary-length messages. The critical invariant, visible directly in the diagram: the chaining value is the state, block after block, and the very last chaining value is published verbatim as the hash. Nothing is done to obscure or mix that final state further before it becomes the output — which is precisely the structural fact §6 exploited for length extension, and precisely what a sponge construction changes by keeping a portion of state permanently internal.

MERKLE'S 1989 PROOF, INFORMALLY

Ralph Merkle's meta-theorem: if the compression function ƒ is collision-resistant on its fixed-size inputs, then the iterated construction is collision-resistant on arbitrary-length inputs — provided the padding injects the message length (this is called Merkle–Damgård strengthening, and its absence is what makes naive length-extension-style attacks on unpadded iterated constructions even worse). The proof works by contradiction: a collision in the full hash on messages of equal padded length implies a collision somewhere in the chain of compression calls, which is exactly a compression-function collision. This is why 1980s and 1990s hash function design concentrated almost entirely on building one strong fixed-size compression function and trusting the iteration to inherit its strength — and why finding a compression-function weakness (as Wang did against MD5 in 2004) is enough to break the whole hash.

ARC 08 · SHA-256 INTERNALS

Inside the compression function, bit by bit

Now the concrete instance. SHA-256 (FIPS 180-4) fixes the abstract Merkle–Damgård skeleton from §7 with a specific compression function operating on eight 32-bit words. Everything below is exactly what the simulator in §15 executes — this is not simplified pseudocode standing in for "real" logic elsewhere; it is the logic.

(a) Padding, concretely — the byte layout

A message of any length is padded to a multiple of 512 bits (64 bytes) before processing:

layoutSHA-256 padding, byte-exact
[ ...original message bytes... ][ 0x80 ][ 0x00 × k ][ 8-byte big-endian bit-length ]

// k is chosen so the TOTAL length ≡ 56 (mod 64) bytes —
// leaving exactly 8 bytes for the length field, so the
// grand total is always a multiple of 64 bytes (one or
// more full 512-bit blocks). The 0x80 byte is a single
// set bit (10000000) followed by zeros: unambiguous
// end-of-message marker no valid message content can fake,
// since it's byte-aligned padding, not raw message bytes.

For the three-byte message "abc" (0x61 0x62 0x63), padding produces exactly one 64-byte block: 1 message byte... three bytes, then 0x80, then 52 zero bytes, then the 8-byte value 24 (the bit-length of "abc") — 3 + 1 + 52 + 8 = 64 bytes, one block.

(b) Eight working variables and the initial hash values

SHA-256 keeps eight 32-bit registers, conventionally named a through h. Their starting values, H₀ through H₇, are not arbitrary — they are the fractional parts of the square roots of the first eight prime numbers (2, 3, 5, 7, 11, 13, 17, 19), taken to 32 bits:

constantsinitial hash values — "nothing up my sleeve"
H0 = 6a09e667   // frac(√2)  × 2³²
H1 = bb67ae85   // frac(√3)  × 2³²
H2 = 3c6ef372   // frac(√5)  × 2³²
H3 = a54ff53a   // frac(√7)  × 2³²
H4 = 510e527f   // frac(√11) × 2³²
H5 = 9b05688c   // frac(√13) × 2³²
H6 = 1f83d9ab   // frac(√17) × 2³²
H7 = 5be0cd19   // frac(√19) × 2³²

This is deliberate: NIST/NSA designers derived these constants from a simple mathematical rule rather than choosing arbitrary hex, so the design could not plausibly contain a hidden backdoor value chosen to weaken the function — a "nothing-up-my-sleeve" number. The 64 round constants K[0..63] use the same discipline: fractional parts of the cube roots of the first 64 primes (2 through 311).

(c) The message schedule: 16 words become 64

Each 512-bit block is split into sixteen 32-bit words, W[0..15]. SHA-256 expands these into 64 words using two "sigma" functions built from rotations and shifts — this expansion is what makes every output bit depend on every input bit after enough rounds (the avalanche effect):

pseudocodemessage schedule expansion
for t in range(16, 64):
    σ0 = rotr(W[t-15], 7) ^ rotr(W[t-15], 18) ^ (W[t-15] >> 3)
    σ1 = rotr(W[t-2],  17) ^ rotr(W[t-2],  19) ^ (W[t-2]  >> 10)
    W[t] = (W[t-16] + σ0 + W[t-7] + σ1) mod 2³²

(d) The round function itself

Each of the 64 rounds mixes the eight working variables using two logical functions and two rotation-based "big sigma" functions:

pseudocodeone compression round, t = 0..63
Σ1  = rotr(e,6) ^ rotr(e,11) ^ rotr(e,25)
Ch  = (e AND f) XOR (NOT e AND g)          // "choose": e picks between f and g, bitwise
T1  = h + Σ1 + Ch + K[t] + W[t]

Σ0  = rotr(a,2) ^ rotr(a,13) ^ rotr(a,22)
Maj = (a AND b) XOR (a AND c) XOR (b AND c) // "majority" vote of a,b,c, bitwise
T2  = Σ0 + Maj

h,g,f,e,d,c,b,a = g,f,e,(d+T1) mod 2³², c,b,a,(T1+T2) mod 2³²

Ch and Maj are non-linear boolean functions — the direct fix for CRC32's fatal flaw in §4. Ch(e,f,g) uses e as a bitwise selector between f and g; Maj(a,b,c) outputs the majority bit across three inputs. Neither function commutes cleanly with XOR the way CRC's linear structure does, so there is no equivalent of "solve a linear system to forge a collision." After all 64 rounds, the working variables are added back into H0..H7 (mod 2³²) to produce the chaining value that feeds the next block, exactly as diagrammed in §7.

(e) Puzzle-friendliness: search is the only path in

Blockchains lean on a property that is really just preimage resistance restated for a range instead of a point: given a target T, finding any input x such that H(x) < T should require, on average, work proportional to 2ⁿ / (number of qualifying outputs) — with no better strategy than trying candidate inputs and checking. This is exactly what an ideal random oracle guarantees: since outputs are uniformly distributed and uncorrelated with inputs, there is no way to compute backwards from "output below T" to a qualifying input, and no way to group candidate inputs so that testing one tells you anything about another. COMMITMENT AND PUZZLE FROM THE SAME PRIMITIVE

Notice the two properties are the same underlying fact viewed from two directions. Collision/preimage resistance says: given output, you learn nothing about input — that's what makes a hash a binding, hiding commitment (publish H(x) now, reveal x later — nobody could have found a different x' with the same hash, and nobody could reverse-engineer x from the hash alone). Puzzle-friendliness says: given a target region of outputs, you learn nothing about which inputs land there except by trying — that's what makes hashing a fair, ungameable computational puzzle. Both are consequences of the same design goal: an output that behaves like a random oracle. This is why blockchains don't need two different primitives for "commit to a block" and "prove you did work" — one hash function, used twice, does both jobs.

ARC 09 · TRADEOFFS

Not all hash functions are interchangeable

Every widely deployed hash function is a different point in the same design space — output size, internal structure, and how much scrutiny it has survived. Read this as an honest ledger of what each buys and what it costs, not a ranking:

Two patterns are worth internalizing. First, Merkle–Damgård dominated for two decades because Merkle's proof made it easy to reason about, but its length-extension property and its total reliance on one compression function's strength are exactly why NIST ran an open competition (2007–2012) for something structurally different — the sponge. Second, Bitcoin's choice of both SHA-256 and RIPEMD-160 in the address derivation is deliberate defense-in-depth: even if RIPEMD-160 were someday weakened, an attacker would first need a SHA-256 preimage to even attempt exploiting it, because addresses hash the SHA-256 output, not the raw public key.

THE QUANTUM CAVEAT

Grover's algorithm gives a quadratic speedup for unstructured search, which includes preimage search: a sufficiently large quantum computer could find a SHA-256 preimage in roughly 2¹²⁸ operations instead of 2²⁵⁶ — serious, but nowhere near the existential threat Shor's algorithm poses to elliptic-curve signatures (chapter 4). No known quantum algorithm improves meaningfully on the classical birthday bound for collisions. This is one reason the "quantum-resistance" conversation for blockchains centers overwhelmingly on signatures, not hash functions — hashing already has generous margin against the best known quantum attack.

ARC 11 · REAL-WORLD BREAKS

When these properties actually failed, in production

Incident 1: MD5 collisions and the Flame malware (2012)

Xiaoyun Wang's team published practical MD5 collision attacks in 2004, reducing collision search from the birthday-bound ~2⁶⁴ to a differential-path attack costing minutes on ordinary hardware. The theoretical break sat mostly unexploited for years — until 2012, when the Flame espionage malware was found using a previously unknown chosen-prefix MD5 collision to forge a Microsoft Terminal Server Licensing Service certificate, making Flame's malicious binaries appear validly signed by Microsoft. The attack was different from — and more powerful than — Wang's original: a chosen-prefix collision lets an attacker start from two arbitrary, attacker-chosen prefixes (a legitimate certificate request and a malicious one) and find suffixes making both hash identically, rather than needing to control the entire colliding message. Microsoft's incident response (Security Advisory 2718704) revoked the intermediate CA and disabled MD5 for code-signing certificates fleet-wide. The lesson generalizes directly to this chapter: a broken collision resistance property doesn't stay academic — it becomes a forged trust anchor the moment anyone has a strong enough incentive to weaponize it.

Incident 2: SHAttered — the first practical SHA-1 collision (2017)

In February 2017, a joint Google/CWI Amsterdam team (Stevens, Bursztein, Karpman, Albertini, Markov) published SHAttered: two distinct PDF files with identical SHA-1 hashes, the first publicly demonstrated SHA-1 collision. The computational cost was enormous — over 9.2 quintillion (9.2×10¹⁸) SHA-1 computations, roughly 6,500 CPU-years and 100 GPU-years, run across Google's infrastructure — but "enormous and finite" is exactly the category a cryptographic break needs to move into to matter: it converts "theoretically weaker than ideal" into "one well-resourced actor away from forgery." Git, which historically used SHA-1 object identifiers, was directly implicated — not because Git's object model was itself broken by SHAttered (Git's usage pattern differs from raw hashing), but because the event forced the ecosystem to confront it, leading to the SHA-1DC (SHA-1 "detect collision") mitigation merged into Git and the ongoing SHA-256 object-format transition. Certificate authorities had already begun sunsetting SHA-1 certificates years earlier, precisely because cryptanalytic progress against SHA-1 (theoretical attacks dated to 2005) was trending toward exactly this outcome.

Incident 3: the CA/Browser Forum's proactive SHA-1 deprecation

Unlike the two incidents above, this one is notable for happening before a practical break: browser vendors and CAs began phasing out SHA-1 certificates starting around 2014–2015, years ahead of SHAttered, based purely on the trajectory of academic cryptanalysis (theoretical collision cost estimates had been falling steadily since 2005). It is the closest thing this chapter has to a genuinely happy ending, and the operational lesson is explicit: do not wait for a demonstrated break to retire a hash function whose security margin is visibly eroding — a lesson blockchain protocol designers who hard-code a specific hash function into consensus rules take especially seriously, since replacing it later requires a coordinated hard fork.

pythonpadding.py — byte-exact padding
def pad(message: bytes) -> bytes:
    bit_len = len(message) * 8
    out = message + b'\x80'                    # the single terminating 1-bit
    while len(out) % 64 != 56:
        out += b'\x00'                        # zero-fill to 8 bytes short of a block
    out += bit_len.to_bytes(8, 'big')          # length ALWAYS included — Merkle–Damgård
    return out                                # strengthening (§7) — this is what blocks
                                              # naive extension without knowing len(message)
pythonschedule.py — 16 words become 64
def expand(block16: list[int]) -> list[int]:
    W = block16[:] + [0] * 48
    for t in range(16, 64):
        s0 = rotr(W[t-15], 7) ^ rotr(W[t-15], 18) ^ (W[t-15] >> 3)
        s1 = rotr(W[t-2],  17) ^ rotr(W[t-2],  19) ^ (W[t-2]  >> 10)
        W[t] = (W[t-16] + s0 + W[t-7] + s1) & 0xFFFFFFFF
    return W  # length 64 — every later word depends on 4 earlier ones,
             # which is what spreads a single input-bit change across
             # the whole schedule (the avalanche effect from §8c)
pythoncompress.py — the 64-round main loop
def compress(H: list[int], W: list[int]) -> list[int]:
    a, b, c, d, e, f, g, h = H
    for t in range(64):
        S1  = rotr(e,6) ^ rotr(e,11) ^ rotr(e,25)
        ch  = (e & f) ^ (~e & g)
        t1  = (h + S1 + ch + K[t] + W[t]) & 0xFFFFFFFF
        S0  = rotr(a,2) ^ rotr(a,13) ^ rotr(a,22)
        maj = (a & b) ^ (a & c) ^ (b & c)
        t2  = (S0 + maj) & 0xFFFFFFFF
        h, g, f, e = g, f, e, (d + t1) & 0xFFFFFFFF
        d, c, b, a = c, b, a, (t1 + t2) & 0xFFFFFFFF
    # fold the working variables back into the chaining value —
    # THIS SUM is the length-extension hinge point from §6: the
    # result below is published verbatim as the digest if this
    # is the last block, with no further mixing applied to it.
    return [(x + y) & 0xFFFFFFFF for x, y in zip(H, [a,b,c,d,e,f,g,h])]
WHY IT WAS BUILT THIS WAY — THREE DECISIONS TO STEAL

1. Separate the message-independent (constants) from the message-dependent (schedule). Precomputing K[0..63] once and deriving it from an auditable rule (cube roots of primes) means anyone can verify the design isn't hiding a weakness, and implementations can treat it as a static table for speed. 2. Prefer bitwise, non-linear mixing over arithmetic mixing wherever possible. Ch and Maj are boolean functions specifically because boolean non-linearity resists the algebraic collision-finding techniques that killed CRC32 in §4 — arithmetic addition (used only for combining, not selecting) is comparatively easy to analyze, so the design isolates where addition is allowed. 3. Make the compression function reusable and the iteration mechanical. Every block runs the exact same 64-round procedure regardless of position in the message — no special-casing the first or last block beyond the padding that already happened — which is exactly what makes Merkle's collision-resistance proof (§7) apply uniformly.
