Codecs & Compression:
H.264, VP9 & AV1

Chapter 2 derived the I/P/B-frame model in the abstract — the shape every codec shares. This chapter asks the question a real engineering team has to answer: which actual, standardized implementation of that model do you ship, to which of the many device types your subscribers own, at what encode and licensing cost? Netflix's real codec history — H.264/AVC as the universal baseline, VP9 and HEVC as the generation that meaningfully improved efficiency, and AV1 (built by the real Alliance for Open Media, which Netflix co-founded) as the current royalty-free frontier — is the case study for a tradeoff every large video platform eventually has to make explicitly.

ARC 01 · THE PROBLEM

A shared frame model isn't a shared implementation

Chapter 2 showed that every modern codec is built from the same basic moves: exploit spatial redundancy with block-based transform coding, exploit temporal redundancy with motion-compensated I/P/B frames. Knowing the shape of the solution doesn't ship a product. A real codec has to be a fully specified, standardized format — precise enough that a chip manufacturer in Seoul and a software team in Los Gatos produce byte-for-byte compatible decoders — and it has to run, in real time, on hardware ranging from a brand-new flagship phone to a television that shipped years before the codec existed.

That is a genuinely hard, two-sided engineering problem, and it only gets harder over time: video quality expectations keep rising (SD → HD → 4K → HDR), which keeps raising the raw-bitrate floor chapter 2 derived, while compression research keeps finding better ways to squeeze that floor down — at the cost of needing more computation to both encode and decode the result. Netflix has to keep picking a point on that moving frontier, repeatedly, across a device fleet that never fully turns over. This chapter is the real history of how the industry — Netflix very much included — has actually navigated that choice.

WHY THIS MATTERS FOR THE NEXT 15 CHAPTERS

Once video is encoded in a specific codec, everything downstream treats that choice as a given: adaptive bitrate (ch. 4) switches between renditions that are each in some codec; per-title encoding (ch. 5) optimizes a bitrate ladder within a chosen codec's rate-distortion behavior; manifests (ch. 6) advertise which codec each rendition uses so a client can pick renditions it can actually decode. Get the codec layer wrong and every later optimization is built on the wrong foundation for some slice of your device fleet.

DEEP CONTEXT · NETFLIX'S REAL, PUBLIC ROLE

Netflix is a genuine, founding member of the Alliance for Open Media (AOMedia), formed in 2015 alongside Google, Amazon, Microsoft, Mozilla, Intel, and others, specifically to develop AV1 as a royalty-free alternative to the increasingly fragmented, expensive HEVC patent landscape (§11 covers that fragmentation as a real incident). This is public, documented fact — not an inference — and it's the direct organizational reason Netflix had early access to, and motivation to invest in, AV1 adoption.

ARC 03 · NAIVE SOLUTION

Attempt #1: just always use the newest, most efficient codec

Given chapter 2's I/P/B foundation and the knowledge that newer codecs compress better, the naive next move is obvious: encode the entire catalog in whichever codec has the best compression efficiency today, for everyone, and retire the older formats.

pseudocodenaive_codec_choice.txt — the strawman, annotated
// "newest is best, so use only the newest" — ignores who's actually asking
function chooseCodecForEncode(title):
    return BEST_AVAILABLE_CODEC        // e.g. "always AV1" — highest compression
                                       // efficiency available today, full stop

function serveManifest(title, device):
    return manifestFor(title, BEST_AVAILABLE_CODEC)
                                       // no check whether `device` can even decode it

This gets the compression math right and the deployment reality catastrophically wrong. §4 quantifies exactly how wrong, using real, public facts about codec adoption and device decode support.

ARC 04 · WHY IT FAILS

A codec nobody's device can decode is worth nothing

Video decoding at consumer scale overwhelmingly relies on dedicated hardware decoder chips — fixed-function silicon baked into a TV, phone, or set-top box at manufacture time. Unlike an encoder (which can run as flexible software on a data-center CPU/GPU Netflix controls), a decoder frequently cannot be upgraded after the device ships. A codec's real efficiency is irrelevant to a device whose chip cannot decode it in real time at all.

THE NUMBERS THAT MAKE "JUST USE THE NEWEST CODEC" FAIL

Chapter 16 covers the full scale of Netflix's device fleet, but the shape is already visible here: a streaming service's device base spans years, often a decade or more, of hardware generations at any given time, because televisions and set-top boxes are replaced far less often than phones. A codec finalized this year has, by construction, zero hardware decode support on any device manufactured before it existed — software-only decoding of a demanding modern codec on an old, low-power chip is frequently not feasible in real time at all, and even where technically possible, burns dramatically more battery and CPU than dedicated silicon. Publicly available encoder benchmarks also consistently show AV1 encoders taking meaningfully longer per frame than mature H.264 encoders of equivalent maturity — often several times slower and, for the most exhaustive encoder settings, considerably more — a real, additional data-center compute cost multiplied across an entire catalog if applied indiscriminately.

Scale sharpens the failure rather than softening it: a global streaming service's subscriber base spans every device generation simultaneously, so "just use the newest codec" doesn't fail for a small unlucky minority — it fails for every subscriber on a device whose chip predates the codec, which at any point in time is a real and substantial fraction of the fleet. Zero playback for a meaningful slice of your subscriber base is a worse outcome than merely-suboptimal compression for all of them, no matter how good the compression ratio looks in a lab benchmark.

ARC 05 · BETTER SOLUTION

Ship a portfolio, and let the client's decoder decide

The real fix generalizes chapter 1's core lesson (let the client decide, based on its own real conditions) to a new axis: instead of one universal codec, encode each title in several codecs, and let each client request the best one it can actually decode, negotiated before any manifest is even served.

This is the same architecture idea chapter 1 introduced for bitrate and chapter 2 implicitly assumed for frame structure: the server's job is to make correct options available; the client is the only party that actually knows its own real constraints — here, decode capability, rather than network throughput. Chapter 4's adaptive bitrate logic and this chapter's codec negotiation are the same design principle applied to two different axes of client-side variation.

ARC 06 · WHY THAT STILL COSTS

A portfolio strategy multiplies almost everything

Serving multiple codecs is the right fix, and it is not free. Every one of the following costs is real and scales with how many codecs you support simultaneously:

  • Storage and encode cost multiply by codec count. Each title now needs a full bitrate ladder (chapter 5) encoded separately, per codec — three codecs isn't three times the work in practice (codecs share some preprocessing), but it is a real, large multiple of both encode compute and stored bytes on origin/CDN infrastructure.
  • Licensing and royalty complexity, especially for HEVC. Unlike the royalty-free VP9 and AV1, H.264 and HEVC carry patent licensing obligations, and HEVC in particular saw multiple, competing, overlapping patent pools emerge (MPEG LA, HEVC Advance, Velos Media) — a real, publicly documented source of licensing friction and cost uncertainty that §11 covers as a genuine industry incident, and part of what motivated AV1's royalty-free design.
  • QA and testing burden multiply by the device/codec matrix. Every supported codec has to be verified against every device class it might be served to — chapter 16's device-certification problem, multiplied by however many codecs are in play.
  • Decode quality is not guaranteed uniform across devices even within one codec. Cheap or older hardware decoders can cut corners on optional codec features, so "supports codec X" is not a single, uniform guarantee — real-world testing across the device fleet remains necessary regardless of which codecs are offered.
THE HONEST TRADE

A multi-codec portfolio buys universal reach and a path to better compression for capable devices, at the cost of a real, ongoing multiplication of encode compute, storage, licensing exposure, and QA surface. No streaming platform escapes this trade — they only choose, deliberately, how many codecs and which ones are worth that multiplied cost, informed by exactly the device-support data chapter 16 discusses.

THE REAL LEVERS BEHIND "BETTER COMPRESSION"

Across H.264 → VP9/HEVC → AV1, three concrete mechanisms account for most of the real, measured efficiency gains: finer/more flexible block partitioning (H.264's fixed 16×16 macroblocks give way to VP9/HEVC's variable quad-tree partitions and AV1's even more flexible partitioning, letting the encoder match block size to local content complexity), richer prediction (more reference frames, more prediction modes, better sub-pixel motion estimation), and more efficient entropy coding (H.264's CABAC refined further in later standards). None of this replaces chapter 2's I/P/B model — it's the same pipeline, executed with more options to choose from at higher computational cost, exactly as chapter 2's closing knowledge-check questions predicted.

Read this table the way a real encoding-strategy meeting reads it: there is no single "best" row — H.264 remains the correct choice specifically because of its universal reach when a device's capability is unknown or old, while AV1 is correct specifically for the newer, capable slice of the fleet where its efficiency gains translate into real bitrate savings. A serious streaming platform ships several rows of this table simultaneously, which is exactly §6's cost and §7's architecture.

ARC 11 · REAL-WORLD INCIDENTS / HISTORY

The HEVC patent-pool fragmentation — a real, industry-shaping incident

HEVC/H.265 achieved real, meaningful compression gains over H.264 — and then ran into a genuinely well-documented licensing problem: rather than one clear patent pool the way H.264 had settled into, HEVC ended up with multiple, separate, overlapping patent-licensing pools (MPEG LA, HEVC Advance, and Velos Media among them), each claiming royalties on different subsets of the standard's patents. For a company trying to ship HEVC-encoded content at scale, this meant real uncertainty about total royalty exposure and, in some cases, the practical risk of needing to negotiate with multiple separate licensing bodies to be confident of legal coverage — friction that a single, unified H.264-era pool never created.

This fragmentation is real, public, and widely discussed in the streaming and hardware industry, and it is directly relevant to why the Alliance for Open Media formed in 2015: a coalition of major technology and content companies, Netflix among the founding members, explicitly building a royalty-free alternative (AV1) specifically to avoid a repeat of exactly this licensing fragmentation for the next codec generation. This is the honest, documented version of "why AV1 exists" — not purely a technical compression-efficiency story, but partly a direct, rational response to a real licensing incident in the codec immediately before it.

THE GENERAL LESSON

A codec's technical merits and its licensing model are both first-class engineering inputs, not a afterthought bolted onto a purely technical decision. A platform operating at Netflix's scale has to weight real legal and financial risk alongside compression efficiency and device compatibility — all three matter, and HEVC's history is the clearest public case where the licensing axis, not the technical one, became the deciding friction point for many adopters.

ARC 13 · CODE WALKTHROUGH

Reconstructing codec negotiation and rate-distortion cost selection

As with previous chapters, nothing below is real Netflix or any codec's actual reference-encoder source — it is illustrative pseudocode representative of the kind of decision logic a real multi-codec pipeline needs.

codec-pipeline/ — illustrative reconstruction
├── negotiation/
│ ├── ● deviceCapabilities.* — what can THIS device's hardware actually decode?
│ ├── ● pickCodec.* — best codec this device supports, from the available portfolio
├── encode/
│ ├── ● rdCost.* — rate-distortion cost function guiding encoder mode decisions
│ └── blockPartition.* — choose block size/shape per region (generation-dependent flexibility)
pseudocodepickCodec.* — negotiation, not assumption
// Illustrative: replaces §3's naive "always use the best codec" with a real check.
CODEC_PRIORITY = ["av1", "hevc", "vp9", "h264"]   // most to least efficient

function pickCodec(deviceCapabilities, availableRenditions):
    for codec in CODEC_PRIORITY:
        if deviceCapabilities.supportsHardwareDecode(codec)
           and availableRenditions.has(codec):
            return codec               // richest codec THIS device can actually decode
    return "h264"                      // universal fallback — every real device supports this
pseudocoderdCost.* — the actual decision function behind "compression efficiency"
// Illustrative rate-distortion cost — the function an encoder minimizes when
// choosing between candidate block partitions, motion vectors, or QP values.
function rdCost(candidate, lambda):
    bits = estimateBitsToEncode(candidate)         // the "rate" — how expensive is this choice?
    distortion = measureQualityLoss(candidate)     // the "distortion" — how much worse does it look?
    return distortion + lambda * bits          // lambda: the QP-driven quality/size trade-weight

function chooseBestPartition(candidates, lambda):
    return argmin(candidates, c => rdCost(c, lambda))
                                                    // a newer codec generation simply has MORE candidates
                                                    // to search here — same function, bigger search space
WHY IT'S BUILT THIS WAY

1. Negotiate, don't assume. pickCodec replaces §3's hard-coded "always the best codec" with an explicit fallback chain ending in the one format essentially every real device can decode — a direct, load-bearing fix for §4's failure mode. 2. One cost function, reused everywhere. The same rate-distortion cost function (bits vs. quality loss, weighted by a QP-derived lambda) governs partition choice, motion-vector selection, and quantization decisions across every codec generation — what changes between generations is the size and richness of the candidate set being searched, not the underlying decision rule. 3. Fallback is a first-class path, not an error case. Because chapter 4's ABR logic and this negotiation both assume a correct fallback always exists, "no capable codec found" is designed to be unreachable in practice, not merely unlikely.
