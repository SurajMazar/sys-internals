UBER ENGINEERING INTERNALS · CHAPTER 12

Deployment & Scheduling:
Peloton and the Internal PaaS

Thousands of stateless service instances need to run somewhere — and so do large batch jobs and ML training runs, on the very same fleet of machines, at completely different times of day. This chapter derives why running separate siloed clusters per workload type wastes a fleet's capacity, how Peloton — Uber's real Mesos-based unified scheduler — bin-packs both workload classes onto shared hardware instead, and how a staged canary rollout uses live health signals to decide, automatically, whether a deploy should finish or reverse itself.

ARC 01 · THE PROBLEM

One fleet, two workload shapes, wildly different clocks

By this point in the course, Uber's backend is thousands of independently deployed stateless services (chapter 8) talking over a mesh (chapter 9) and an event backbone (chapter 10), observed by M3 and Jaeger (chapter 11). None of that runs on air — every service instance is a process that has to be placed on an actual machine, and so does something this course hasn't discussed yet: the large batch jobs and machine learning training runs that consume Uber's own event and trip data to compute things like ETA models, fraud models, and demand forecasts.

These two workload classes have almost opposite shapes:

  • Stateless services — must be up continuously, respond in milliseconds, and their demand tracks rider and driver activity: it peaks during commute hours and Friday/Saturday nights, and troughs overnight.
  • Batch and ML jobs — run for minutes to hours, don't need to respond to anyone in real time, and are usually scheduled (deliberately or by convenience) to run when spare capacity exists — which, for a rides business, is disproportionately overnight, exactly when stateless demand troughs.

Those opposite demand curves are the entire opportunity this chapter is about: if the two workload classes could share one fleet, the batch/ML class's overnight peak could run on exactly the capacity the stateless class isn't using. The naive answer — give each workload class its own separate, statically-sized cluster — throws that opportunity away, and §4 shows precisely how much.

WHY THIS IS A SCHEDULING PROBLEM, NOT JUST A CAPACITY PROBLEM

Even with enough total machines, which task runs on which machine, and what happens when two tasks both want the same one is a genuine algorithmic problem — bin-packing, which is provably hard to solve exactly at any real scale. Every unified scheduler, this chapter's included, is really a story about which heuristics it uses and which guarantees it's willing to trade away for speed.

DEEP CONTEXT · WHY MESOS

Peloton is Uber's real unified scheduler, built on top of Apache Mesos — a cluster resource manager that abstracts a fleet of machines into offers of available CPU/memory that a scheduler can accept or decline. Mesos itself doesn't decide bin-packing policy; it hands resource offers to whichever scheduler framework is registered above it. Peloton is the scheduling policy layer built specifically to make that shared resource pool safe for mixing stateless services with batch and ML workloads — the placement heuristics, resource pools, and preemption rules this chapter derives are Peloton's job, not Mesos's.

ARC 03 · NAIVE SOLUTION

Attempt #1: two clusters, sized for their own peaks

The obvious first cut: give stateless services their own fixed-size cluster, sized for peak rider demand, and give batch/ML its own separate fixed-size cluster, sized for its own peak job volume.

configfleet_allocation.yaml — the strawman
clusters:
  stateless-services:
    machine_count: 4000     # sized for peak Friday-night rider demand
    workload: "dispatch, pricing, trip, payments, ... (chapters 8-11)"
  batch-ml:
    machine_count: 1500     # sized for peak overnight training-job volume
    workload: "ETA model training, fraud scoring, demand forecasting"
# Two separate pools. Neither can ever use the other's idle capacity.

This is a completely reasonable starting point: each cluster is simple to reason about, capacity planning for each workload class is independent, and a batch job gone haywire can't starve a rider-facing service of resources by accident, or vice versa. The problem is what those two fixed sizes actually cost, all day, every day.

ARC 04 · WHY IT FAILS

Two peaks that never overlap waste each other's troughs

Quantify it. Suppose (illustrative numbers, chosen to make the shape clear rather than to claim Uber's real published figures) the stateless cluster's real utilization looks like this over 24 hours: near 90% during evening peak, but only ~25% at 4am. The batch/ML cluster's utilization is the mirror image: near 85% overnight running training jobs, but only ~15% during evening peak when engineers are busy elsewhere and fewer jobs are scheduled.

THE MATH

Average utilization of the stateless cluster across 24 hours, in this illustrative model, comes out around 50–55%; the batch/ML cluster, run separately and sized for its own peak, averages a similar figure. Neither cluster can ever borrow the other's idle capacity, because they are separate pools of machines — the stateless cluster's 4am idle capacity and the batch cluster's evening-peak idle capacity are both stranded, unusable by the workload that could actually use them at that hour. The fleet as a whole is paying for two peaks' worth of hardware while running, on average, closer to one peak's worth of real work. This is not a tuning problem within either cluster — it's a structural consequence of the partition itself, and no amount of resizing either cluster individually fixes it, because the waste is exactly the non-overlap between the two demand curves.

Generalize it: any time two workload classes have demand curves that peak at different times, a static partition forces the fleet to be provisioned for the sum of their two peaks, while the combined peak — if the two workloads shared one pool — is usually meaningfully lower than that sum, because they rarely peak simultaneously. Capturing that gap is exactly what a unified scheduler buys you, and exactly why Uber built one.

THE UNDERLYING SHAPE

We need one shared pool of machines and a scheduler that can safely place both workload classes onto it — which immediately raises the question the naive design avoided entirely: what stops a batch job from starving a rider-facing service of resources at exactly the moment rider demand spikes?

ARC 06 · WHY THAT STILL HURTS

Sharing a fleet doesn't make scheduling free

  • Bin-packing is NP-hard, so real schedulers use heuristics, not optimal solutions. A placement engine choosing which host runs which task is provably not solvable optimally at scale in reasonable time — real systems use fast approximations (first-fit, best-fit, bin-packing scored by several dimensions at once), which means the fleet is never packed as tightly as a hypothetical optimal solver could pack it.
  • Preemption has to be safe, not just decisive. Evicting a lower-priority batch task to free capacity for a latency-sensitive service is the whole point of sharing the pool — but evict too aggressively and a batch job that was 95% done gets killed and has to restart from scratch, wasting real compute; evict too conservatively and the latency-sensitive service waits.
  • Colocation creates noisy-neighbor interference. Two workloads sharing a physical host, even with separate resource reservations, can still contend for shared hardware resources (memory bandwidth, cache, disk I/O) in ways a scheduler's accounting doesn't fully capture — a batch job doing heavy sequential I/O can measurably slow a latency-sensitive neighbor even while staying within its own allocated CPU share.
  • Running the scheduler itself is a new operational responsibility. A unified scheduler is now load-bearing infrastructure for both workload classes at once — its own bugs, its own scaling limits, and its own on-call rotation replace what used to be two smaller, more independent operational surfaces.
THE INDUSTRY'S ANSWER — AND ITS ADMISSION

Every operator running mixed workloads at scale accepts these costs deliberately, because the alternative — the static partition from §3 — has a cost that's worse and, worse still, invisible on a capacity spreadsheet: hardware sitting idle. Choosing "hard, occasionally messy sharing" over "clean, wasteful isolation" is the same tradeoff this course has now made for processes (chapter 1), and it recurs here at the level of an entire fleet.

ARC 08 · INTERNAL IMPLEMENTATION

Resource pools, placement, preemption, and canary rollout

Four mechanisms: (a) hierarchical resource pools and admission control, (b) the placement engine's bin-packing heuristic, (c) the preemption decision, and (d) the canary rollout controller that watches live health signals.

(a) Hierarchical resource pools

Rather than one flat quota per team, resource pools form a tree — an org's pool contains its teams' pools, each with a reservation (guaranteed minimum), a limit (hard ceiling), and a share (how unused fleet-wide capacity is split when there's a surplus):

pseudocoderesource_manager.admit() — illustrative
function admit(task, pool) {
    const used = pool.currentUsage();
    if (used + task.resources <= pool.reservation)
        return accept(task);            // always honored — this is the GUARANTEED slice

    if (used + task.resources <= pool.limit && fleet.hasSpareCapacity())
        return accept(task, { preemptible: true }); // elastic — can be evicted later

    return queue(task);                 // pool is at its limit; wait for capacity
}

This is the mechanism that makes sharing safe: a team's reservation is never taken away, regardless of how busy the rest of the fleet is — exactly the guarantee a latency-sensitive stateless service needs. Everything above the reservation, up to the limit, is elastic capacity borrowed from the shared pool, and explicitly marked preemptible.

(b) Placement: a bin-packing heuristic

pseudocodeplacement_engine.place() — illustrative best-fit heuristic
function place(task, hostOffers) {
    const fits = hostOffers.filter(h =>
        h.availableCpu >= task.cpu && h.availableMem >= task.mem &&
        satisfiesConstraints(h, task.constraints));  // e.g. GPU required, anti-affinity with a peer task

    if (fits.length === 0) return null;   // no host fits; task waits for the next offer round

    // BEST-FIT: choose the host that leaves the LEAST leftover capacity,
    // packing tightly rather than spreading thin — the classic bin-packing
    // heuristic tradeoff (tight packing vs. leaving room for large future tasks).
    return fits.reduce((best,h) =>
        (h.availableCpu - task.cpu) < (best.availableCpu - task.cpu) ? h : best);
}

(c) Preemption: evicting safely, not just decisively

pseudocodepreemptor.considerEviction() — illustrative
function considerEviction(pendingTask, host) {
    const candidates = host.tasks
        .filter(t => t.preemptible)
        .sort((a,b) => a.priority - b.priority);   // evict LOWEST priority first

    let freed = 0;
    const toEvict = [];
    for (t of candidates) {
        if (freed >= pendingTask.resources) break;
        toEvict.push(t); freed += t.resources;
    }
    if (freed < pendingTask.resources) return null;   // evicting everything preemptible still isn't enough — don't evict for nothing

    toEvict.forEach(t => t.evict({ gracePeriod: t.gracePeriodSec }));  // SIGTERM-style grace, not instant kill
    return toEvict;
}

ARC 09 · TRADEOFFS

Three ways to schedule a fleet

APPROACHWHAT IT BUYSWHAT IT COSTS
Separate siloed clusters per workload type simple capacity planning zero interference between workload classes fleet sized for the SUM of two peaks that never overlap idle capacity in each silo is unusable by the other
One shared pool, no priority tiers (first-come, first-served) higher average utilization simplest possible scheduler a large batch job can starve a latency-sensitive service with no recourse
Unified scheduler with resource pools + preemption (Uber's real Peloton) high utilization AND protected latency-sensitive capacity elastic borrowing when idle capacity exists bin-packing is a heuristic, not optimal preemption must be tuned to avoid wasting near-complete batch work running the scheduler is itself a serious operational responsibility

Read this the same way as every tradeoff table in this course: there is no dominant option, only a different place to accept cost. Uber's real Peloton design pays scheduling complexity — resource pools, placement heuristics, careful preemption — to buy back the utilization that a static partition permanently strands.

MODEL, NOT MEASUREMENT

In siloed mode, required capacity is the sum of each curve's own peak, held fixed all day; in shared mode, it's the peak of the two curves' sum at each hour — provably less than or equal to the siloed sum, and usually meaningfully less whenever the two peaks don't coincide. That inequality, not any specific number, is the result worth remembering.

ARC 11 · REAL-WORLD INCIDENTS

Two failure modes every shared-fleet operator eventually meets

Incident 1: the canary that lied

This is a realistic, industry-standard incident pattern for this class of system rather than a specific documented Uber postmortem: a bad deploy passes its canary stage cleanly, because the canary's 5% of traffic happened not to exercise the one code path that was actually broken — a rare input, a specific region, a specific app version — and the rollout completes to 100% before the problem shows up at full production load and volume. The general lesson this incident pattern teaches, independent of any one company: a canary reduces risk, it does not eliminate it, and its usefulness is bounded by how representative the canary traffic actually is of the full fleet's traffic — which is exactly why serious canary systems watch signals well past the initial stage, keep the rollout at partial completion for a meaningful soak period, and treat a clean canary as reduced risk rather than proof of correctness.

Incident 2: preemption evicts too aggressively

Also a general, honestly-framed industry pattern rather than a specific documented Uber incident: a latency-sensitive service's demand spikes, the scheduler correctly preempts lower-priority batch tasks to free capacity — but a long-running ML training job that was 95% complete gets evicted along with everything else preemptible, and has to restart from its last checkpoint (or from scratch, if it wasn't checkpointing frequently), wasting hours of compute for a preemption decision that, from the scheduler's narrow point of view, was completely correct. The standard mitigation this pattern teaches across the industry: preemption policies that account for a task's progress and checkpoint frequency, not just its static priority number — and encouraging (or requiring) long-running batch/ML jobs to checkpoint regularly specifically so a preemption event costs minutes of recomputation, not hours.

THE LESSON BOTH INCIDENTS SHARE

A scheduler's decisions are only as good as the signals and policies it's given — a canary is only as trustworthy as its traffic sample, and preemption is only as cheap as the preempted task's own resilience to being evicted. Neither problem is really "the scheduler is wrong" — both are "the inputs to the scheduler's decision were incomplete."

Reading the shape of a real unified scheduler

Peloton's full internals aren't reproduced here verbatim; what follows is precise, representative pseudocode for how a system in this class is genuinely built — organized to mirror Peloton's real, publicly described component names — labeled illustrative rather than literal.

peloton/
├── resmgr/
│ ├── ● resource_pool_tree.* — hierarchical pools: reservation/limit/share per org/team
│ └── ● admission_control.* — admits, marks elastic/preemptible, or queues a task
├── jobmgr/
│ └── job_task_tracker.* — desired-state bookkeeping: what SHOULD be running
├── placement/
│ ├── ● placement_engine.* — bin-packing heuristic matching tasks to host offers
│ └── ● preemptor.* — evicts lowest-priority preemptible tasks with a grace period
├── hostmgr/
│ └── mesos_offer_adapter.* — translates Mesos resource offers into Peloton's host state (illustrative)
└── deploy/
└── ● canary_controller.* — stages a rollout, compares live error rate to baseline, promotes or rolls back

The canary controller — the core decision loop behind §15's simulator:

pseudocodecanary_controller.* — illustrative
function evaluateCanary(canary, baseline) {
    const canaryRate  = canary.errors / canary.requests;
    const baseRate    = baseline.errors / baseline.requests;

    // Require BOTH a minimum sample size (small samples are noisy) AND a
    // meaningful relative jump over baseline — not just "more than zero".
    if (canary.requests < MIN_SAMPLE)
        return { verdict: "WAIT", reason: `only ${canary.requests} requests — too few to trust yet` };

    if (canaryRate > baseRate * REGRESSION_MULTIPLIER)
        return { verdict: "ROLLBACK", reason: `error rate ${(canaryRate*100).toFixed(2)}% vs baseline ${(baseRate*100).toFixed(2)}% — exceeds ${REGRESSION_MULTIPLIER}x threshold` };

    if (canary.stage < 100)
        return { verdict: "PROMOTE", reason: "healthy — advance to next stage (e.g. 5% → 25% → 100%)" };

    return { verdict: "COMPLETE", reason: "fully rolled out and healthy" };
}
WHY IT WAS BUILT THIS WAY

1. Reservations are promises; everything else is a loan. Splitting a pool's guarantee (reservation) from its ceiling (limit) is what lets latency-sensitive workloads coexist with elastic ones — the guarantee is never subject to renegotiation under load, exactly when it matters most. 2. A heuristic placement engine trades optimality for speed, deliberately. Waiting for a provably optimal bin-packing solution is not compatible with placing tasks in real time at fleet scale — a fast, good-enough heuristic beats a slow, perfect one every time a task is actually waiting to run. 3. A canary's verdict needs a statistical floor, not just a threshold. Requiring a minimum sample size before trusting an error-rate comparison is what stops a tiny, noisy canary sample from producing a confident-sounding but meaningless verdict either way.
