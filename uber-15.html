UBER ENGINEERING INTERNALS · CHAPTER 15

No New Database Engine —
Just MySQL, Sharded, With No Schema

Chapter 14 left Uber's engineering team with a MySQL foundation they trusted and knew how to operate — and a growing realization that trust alone doesn't scale a single instance forever. Rather than build or adopt an entirely new distributed database engine, Uber's real, publicly documented answer was almost contrarian in its restraint: keep MySQL as the storage engine, strip the schema down to almost nothing, and shard aggressively. This chapter derives Schemaless from first principles and then shows you the real, documented design Uber's engineering blog published in 2014.

ARC 01 · THE PROBLEM

A cheaper per-update engine still has one machine's ceiling

Chapter 14 closed on an honest note: migrating to a storage engine with cheaper per-update costs raised the ceiling on how much load a single MySQL primary could absorb — it did not remove the ceiling. Uber's real growth in trip volume, driver locations, and every other update-heavy dataset this course has built kept climbing, and a single machine, however efficient its write path, has finite CPU, memory, and disk throughput. The next problem was therefore unavoidable: how do you keep scaling a relational workload horizontally, across many machines, without either operating a brand-new, unproven distributed database engine, or freezing your schema in place because every change now has to run against dozens of independent database instances at once?

Two requirements pulled in different directions, and naming them precisely is the whole chapter:

  • Horizontal write scale. Data has to be split across many independent MySQL instances (shards), each handling only a fraction of the total dataset, so total write capacity grows by adding machines rather than hitting one machine's ceiling.
  • Schema agility. New product features constantly need new fields on existing entities, and a traditional ALTER TABLE against a table sharded across dozens of MySQL instances means coordinating dozens of simultaneous schema changes — each one, per chapter 14's own stated pain point, capable of locking a table for reads and writes while it runs.
WHY NOT JUST ADOPT AN EXISTING DISTRIBUTED DATABASE?

This is the real, documented judgment call Uber's engineering blog described making: rather than adopt an unfamiliar distributed database engine, the team chose to build a comparatively thin layer on top of infrastructure — MySQL — that its operators already deeply understood from the migration chapter 14 covered. That's a real, deliberate tradeoff (operational familiarity over a purpose-built engine's native features), and this chapter presents it as exactly that — not as proof that this is always the right call for every company at this scale.

It's worth being precise about what "operational familiarity" actually buys a team under pressure: by this point, Uber's operators already knew how a MySQL primary fails over, how replication lag behaves under load, how backups and point-in-time recovery work, and how to read a slow-query log — a whole runbook's worth of accumulated, hard-won knowledge from chapter 14's migration. Adopting an unfamiliar distributed database engine instead would have meant relearning all of that from scratch, under real production pressure, for a system the team had comparatively little operational history with. Schemaless's entire design can be read as an attempt to get horizontal scale and schema flexibility while deliberately not spending that hard-won operational capital twice in a row.

WHAT'S REAL HERE, STATED PLAINLY

Schemaless is real, well-documented Uber engineering: a datastore built as an append-only layer on top of sharded MySQL, where the smallest unit of data is called a cell — an immutable JSON blob addressed by a row key, a column name, and a ref key (a version identifier), plus an auto-incrementing added ID used for ordering within a shard. Uber's engineering blog published this design across three public posts in 2014: "Designing Schemaless," an architecture deep-dive, and a piece on "triggers" — an asynchronous, pub-sub-style change-notification mechanism used to build secondary indexes. This chapter's §7 and §13 present that documented design directly, not a reconstruction.

ARC 03 · NAIVE SOLUTION

Attempt #1: shard a normal, rigid-schema table across many MySQL instances

The obvious first move: keep the traditional relational schema from chapter 14, and just split rows across more MySQL instances by some sharding key, so no single instance holds the whole dataset.

SQL (illustrative)trips table, naively sharded across 8 MySQL instances
-- Shard 0 through Shard 7, each an independent MySQL instance, same rigid schema:
CREATE TABLE trips (
    id            BIGINT PRIMARY KEY,
    rider_id      BIGINT NOT NULL,
    driver_id     BIGINT,
    status        VARCHAR(32),
    fare_cents    INT
) ENGINE=InnoDB;

-- Six months later, product wants a new field: "promo_code_applied".
-- This ALTER must run against ALL 8 shards, each one a separate operation:
ALTER TABLE trips ADD COLUMN promo_code_applied VARCHAR(64);  -- × 8, one per shard

This works, and for a while it's genuinely fine — sharding a rigid schema is a completely standard technique. The trouble is what happens to that one, simple ALTER TABLE line as both the shard count and the pace of product change keep growing.

ARC 04 · WHY IT FAILS

Every schema change now multiplies by shard count, forever

  • Schema-change cost multiplies by shard count. One ALTER TABLE against one database becomes N coordinated operations across N shards — each one, per chapter 14's own stated pain point, a potential table lock affecting reads and writes on that shard for its duration. As shard count grows to keep up with data volume, so does the blast radius and coordination cost of every single schema change.
  • Product velocity and shard count pull against each other. The more successful the product is, the more shards you need for capacity — and the more shards you have, the more expensive and risky every new field, every renamed column, every schema evolution becomes. The naive approach makes horizontal scale and schema agility directly opposed, when a growing company needs both simultaneously.
  • Partial-rollout risk. An ALTER TABLE that succeeds on 7 shards and fails or times out on the 8th leaves the fleet in an inconsistent schema state — application code now has to handle "does this shard have the new column yet or not," a correctness hazard with no equivalent when there was only ever one schema to reason about.
THE CONCRETE FAILURE

A team wants to ship a new feature requiring one new field on the trips record. What should be a five-minute change becomes a coordinated, carefully-scheduled, multi-shard migration — repeated for every shard, for every future field, indefinitely, with real risk of leaving shards in different schema states along the way. The friction doesn't come from any one shard being hard to change — it comes from having to change all of them, identically, every time, which grows directly with the very success that made sharding necessary in the first place.

ARC 05 · BETTER SOLUTION

Schemaless: make "adding a field" a write, not a migration

The fix Uber's real, documented design chose: collapse the rigid, wide table into one generic schema that never needs an ALTER TABLE again, no matter how many new kinds of data the product adds. Instead of columns, the unit of data becomes a cell: an immutable JSON blob, identified by a row key (which entity this belongs to), a column name (which piece of information this is), and a ref key (which version of it this is).

From a wide rigid table to Schemaless's generic cell schemaSTEP-BY-STEP

"Adding a new field" now means nothing more than writing a new column_name value that has never been used before — no DDL, no per-shard coordination, no partial-rollout risk, because the underlying MySQL table structure never changes at all. Sharding is handled the same way: each row key hashes to exactly one shard, independent of how many different column names get written under it over the entity's lifetime.

ARC 06 · WHY THAT STILL HURTS

What Schemaless deliberately gave up to buy this

  • No cross-shard queries, joins, or transactions. Because a row key deterministically maps to exactly one shard, and shards are independent MySQL instances with no cross-shard query engine, any access pattern that needs data from multiple row keys that hash to different shards simply cannot be expressed as one query — the application has to fan out itself, or precompute an index.
  • No database-enforced schema or constraints. The body blob is opaque to MySQL — there's no column type checking, no foreign keys, no NOT NULL constraint on any field inside the JSON. Every guarantee about shape and validity that a rigid schema gave you for free now has to be enforced entirely in application code.
  • Secondary indexing requires real, separate infrastructure. "Find all trips for this driver" is trivial when driver_id is an indexed column — but Schemaless has no indexed columns inside the blob at all. Uber's real, documented answer was triggers: an asynchronous, pub-sub-style mechanism that notifies subscribers when a cell is written, so a separate process can build and maintain a purpose-built index table (itself just another Schemaless table) — real infrastructure, not a free byproduct.
  • Storage grows with every version, by design. Because cells are immutable and addressed by ref key, "updating" a value doesn't overwrite it — it writes a new cell under a new ref key. Old versions accumulate unless a deliberate compaction or retention policy reclaims them.
THE HONEST FRAME

Schemaless doesn't remove complexity — it relocates it. Schema and index maintenance move out of the database and into application code and purpose-built asynchronous infrastructure (triggers, index tables) that Uber's engineers had to design, build, and operate themselves. That's a real, worthwhile trade for a company whose bottleneck was schema-change friction and horizontal scale specifically — not a strictly simpler system in any absolute sense.

ARC 08 · INTERNAL IMPLEMENTATION

The cell schema, shard resolution, and the write/read path

Uber's real documented schema identifies each cell by three fields, with a compound index across them for efficient lookup, plus an auto-incrementing added ID for ordering within a shard:

SQLSchemaless core table — the real, documented shape
CREATE TABLE schemaless_cells (
    added_id     BIGINT AUTO_INCREMENT PRIMARY KEY,  -- per-shard ordering
    row_key      VARBINARY(255) NOT NULL,     -- which entity (e.g. a UUID)
    column_name  VARCHAR(255) NOT NULL,      -- which piece of information
    ref_key      VARBINARY(255) NOT NULL,     -- which VERSION (e.g. a timestamp)
    body         BLOB NOT NULL,                     -- the opaque payload, typically JSON
    UNIQUE KEY cell_lookup (row_key, column_name, ref_key)
);

Every cell is immutable once written — there is no UPDATE in this model, only new inserts under a new ref_key. Reads for "the current value" fetch the newest ref_key for a given (row_key, column_name) pair.

ARC 09 · TRADEOFFS

Four ways to store fast-growing, evolving data at scale

APPROACHWHAT IT BUYSWHAT IT COSTS
Rigid sharded relational (§3) full SQL, constraints, and secondary indexes per shard schema changes multiply by shard count, forever (§4)
Schemaless (this chapter's endpoint) schema changes are just writes — zero DDL, zero per-shard coordination reuses mature, well-understood MySQL operations no cross-shard joins/transactions secondary indexing requires separate trigger-built infrastructure
Purpose-built distributed NoSQL (Cassandra/Dynamo-style) native secondary-index and multi-region support in many implementations purpose-built distributed consistency model an entirely new engine to operate, with its own failure modes, unfamiliar to a MySQL-experienced team
Docstore (chapter 16, Schemaless's real successor) real secondary-index support multi-region replication LSM-tree (MyRocks) write path suited to write-heavy load index consistency and cross-region conflict handling to solve, in exchange (ch. 16)

Read this the same way as chapters 9 and 13's spectrums: Schemaless is a genuinely well-reasoned point on this spectrum for a team with deep MySQL operational expertise and a schema-agility problem specifically — not a universal best datastore design, and Uber's own later investment in Docstore (chapter 16) is itself documented evidence that Schemaless's tradeoffs eventually needed revisiting as requirements grew.

Notice, too, how this table connects back across the whole database arc of this course: chapter 14 was about which storage engine to trust with individual updates; this chapter is about how to keep trusting that engine as data outgrows any single instance of it. Neither decision made the other unnecessary — Schemaless is built directly on top of chapter 14's migrated MySQL foundation, inheriting both its per-update efficiency and its operational maturity, and adds a second, independent axis of scale (horizontal sharding) rather than replacing anything chapter 14 already solved.

ARC 10 · PERFORMANCE / SCALE CHARACTERISTICS

Why horizontal sharding actually scales where one instance can't

The core scaling argument is simple and worth stating precisely: total write capacity is roughly the number of shards times one shard's capacity, as long as writes are spread evenly across shards — the entire scalability story collapses the moment row keys aren't well distributed, which is exactly what §8's slider demonstrated.

ARC 11 · REAL-WORLD INCIDENTS / OPERATIONAL CHALLENGES

One documented resilience feature, and one well-known industry-wide pattern

Uber's own Schemaless documentation described a real resilience mechanism worth naming directly, and this chapter also names one industry-standard sharding failure pattern honestly flagged as a general pattern rather than a specific documented Uber incident.

Documented: buffered writes for a failing shard master

Uber's engineering writing on Schemaless described building buffered writes specifically to tolerate a transient failure of a shard's MySQL master — absorbing writes rather than failing them outright while a shard's primary is temporarily unavailable or undergoing failover, then applying them once the shard recovers. This is a real, documented design decision, not a reconstruction.

General pattern: the hot shard from a poorly chosen row key

This specific failure isn't tied to a named public Uber incident, so it's presented plainly as the well-known, industry-wide sharding failure pattern it is: choosing a row key with low cardinality or skewed popularity (a sequential ID, a single heavily-used tenant, a "trending" entity that suddenly gets far more writes than any other) sends a disproportionate share of traffic to one shard, which then becomes the ceiling on total system throughput regardless of how many other shards sit comparatively idle — exactly the failure §8 and §10's widgets let you reproduce directly.

THE OPERATIONAL LESSON

A sharded system's throughput ceiling is set by its most loaded shard, not its average shard — which means shard-key selection is not an implementation detail decided once and forgotten, but an ongoing capacity concern that needs monitoring for skew as real-world usage patterns (which entities get popular, which customers grow fastest) shift over the system's lifetime.

ARC 13 · CODE WALKTHROUGH

Reading the real, documented design

The schema below is the real, publicly documented Schemaless design. The client-library and trigger-consumer pseudocode is illustrative reference code, representative of the documented general mechanism rather than a copy of Uber's actual internal source.

schemaless/
├── schema/
│ └── ● schemaless_cells.sql — the real documented (row_key, column_name, ref_key) → body schema (§8)
├── client/
│ ├── ● shard_resolver.py — hashes row_key to a shard (illustrative)
│ └── ● schemaless_client.py — put_cell() / get_latest_cell() (illustrative)
├── triggers/ — real, documented: async pub/sub on cell writes ("Part 3" of Uber's blog series)
│ ├── ● trigger_dispatcher.py — notifies subscribers after a cell commits (illustrative)
│ └── ● driver_index_builder.py — a subscriber maintaining an index table (illustrative)
└── buffered_writer.py — absorbs writes during a transient shard-master failure (documented capability)
pseudocode (illustrative)client/shard_resolver.py + schemaless_client.py
def shard_for(row_key):
    return consistent_hash(row_key) % NUM_SHARDS      # deterministic: same row_key ALWAYS maps to the same shard

def put_cell(row_key, column_name, body):
    shard = shard_for(row_key)
    ref_key = now_timestamp()                        # new version, never overwrites an existing cell
    mysql[shard].execute(
        "INSERT INTO schemaless_cells (row_key, column_name, ref_key, body) VALUES (%s,%s,%s,%s)",
        row_key, column_name, ref_key, body)
    notify_triggers(row_key, column_name, ref_key, shard)   # §13's async trigger mechanism

def get_latest_cell(row_key, column_name):
    shard = shard_for(row_key)                       # same deterministic mapping — no lookup service needed
    return mysql[shard].query_one(
        "SELECT body FROM schemaless_cells WHERE row_key=%s AND column_name=%s ORDER BY ref_key DESC LIMIT 1",
        row_key, column_name)
pseudocode (illustrative)triggers/driver_index_builder.py — building a secondary index the hard way
class DriverIndexBuilder:
    # Subscribes to writes on column_name="trip_driver_assignment".
    # Schemaless has no native secondary index — this IS the index,
    # built and kept current entirely in application-owned code.
    def on_cell_written(self, row_key, column_name, ref_key, body):
        if column_name != "trip_driver_assignment": return
        driver_id = body["driver_id"]
        # A SEPARATE Schemaless table, row-keyed by driver_id instead of trip_id —
        # this is the only way to answer "find this driver's trips" efficiently.
        put_cell(row_key=driver_id, column_name=f"trip:{row_key}", body={"trip_id": row_key})
WHY IT WAS BUILT THIS WAY

Notice that the "index" in the second code block is not a database feature at all — it's just another ordinary Schemaless table, row-keyed differently, kept current by application-level code reacting to writes asynchronously. This is the direct, honest consequence of §6's tradeoff: Schemaless doesn't have a concept of a secondary index, so if you need one, you build it out of the exact same primitive the rest of the system uses — consistent, but entirely your own responsibility to keep correct and current.
