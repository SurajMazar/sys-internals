WHATSAPP ARCHITECTURE · CHAPTER 04

Signal Protocol II:
The Double Ratchet

X3DH (chapter 3) hands Alice and Bob exactly one 32-byte shared secret, SK, computed once and never again. A conversation that runs for five years and ninety thousand messages cannot be protected by one secret — a single compromised key must not unlock yesterday's history, and a single theft must not buy an attacker a permanent subscription to tomorrow's messages either. This chapter derives the Double Ratchet: the mechanism, published by Trevor Perrin and Moxie Marlinspike, that turns X3DH's one secret into an endless stream of unique per-message keys — cheap enough to run on every message, and self-healing every time the conversation changes direction.

ARC 01 · THE PROBLEM

One secret was never going to be enough

Chapter 3 ended with a single 32-byte value, SK = HKDF(F ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4), independently derived by Alice and Bob. Treat that as fixed and ask the next question a Staff engineer has to ask before shipping anything: what do we do with SK for the remaining life of this conversation? The honest answer is that SK by itself is not a messaging protocol — it is one bootstrap value, and the real design problem is what evolves it across the next ninety thousand messages two people might exchange over the next five years.

State the requirement precisely, as two separate properties, because conflating them is the most common mistake engineers make reading the Signal documentation for the first time:

  • Forward secrecy. Compromising the key material in use today must not let an attacker decrypt messages sent in the past. This is the property chapter 3 already needed and X3DH already partially buys via fresh ephemeral keys — but X3DH only covers session establishment. Something has to keep buying forward secrecy for message #2, #3, and #89,999.
  • Post-compromise security (also called future secrecy, or — in Signal's own terminology — a self-healing ratchet). Compromising the key material in use today must not let an attacker decrypt messages sent in the future, once enough fresh, unobserved randomness has been exchanged. This property has no analogue in TLS or X3DH as chapter 3 left it — it only makes sense for a protocol that keeps running for the entire lifetime of a relationship between two people, which describes a messaging conversation exactly and describes a one-shot handshake not at all.

These are genuinely different properties, and a construction can have either one without the other. Section 3 builds the obvious candidate — reuse SK as a hash chain — and section 4 shows, with real numbers, exactly which of the two properties it buys and which one it silently fails to provide.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Every remaining chapter assumes the Double Ratchet is already running underneath. Chapter 5's delivery pipeline has to move ciphertext reliably without ever seeing a plaintext or a long-lived key; later chapters on groups and multi-device all have to reconcile multiple independent ratchets running per device pair. Get this chapter's mental model wrong — treat the ratchet as "one session key, refreshed occasionally" instead of "two interlocking state machines with different triggering conditions" — and every later chapter's edge cases stop making sense.

ARC 02 · HISTORICAL CONTEXT

From opportunistic re-keying to a formally proven ratchet

The Double Ratchet is not one person's invention arriving fully formed — it is the synthesis of a decade of chat-protocol engineers converging, independently, on the same shape once they took post-compromise security seriously as a design requirement rather than a nice-to-have. DEEP CONTEXT · WHY OTR DIDN'T FINISH THE JOB

OTR (2004) already had a DH ratchet — every message could opportunistically carry a fresh DH public value, and the next key derivation mixed it in. That is real post-compromise security, decades before WhatsApp existed. What OTR does not have is any workable story for asynchronous delivery: its ratchet assumes both parties are live enough to exchange fresh DH values close together in time, and it has no header field encoding "which message number, on which chain" for a receiver to make sense of a message that arrives wildly out of order after a week offline. The Double Ratchet's actual novelty over OTR is not the DH ratchet idea itself — it is bolting a symmetric-key ratchet and an explicit (N, PN) header scheme onto it, so the whole thing survives exactly the offline, store-and-forward conditions chapter 3 already established as non-negotiable.

ARC 03 · NAIVE SOLUTION

Attempt #1: a one-way hash chain seeded from SK

Derive honestly from the simplest thing that could work. SK is 32 bytes of good entropy. The obvious move: never reuse it directly as a message key (chapter 3 already showed static-key reuse is fatal) — instead, run it through a one-way key-derivation function once per message, and use each output as that message's unique key.

pseudocodehash_chain.txt — the strawman
// SK arrives once from X3DH (chapter 3). Never used directly as a message key.
k = SK

function sendMessage(plaintext):
    k = KDF(k)                          // advance the chain — one-way, cannot be undone
    msg_key = k
    ciphertext = AEAD_encrypt(msg_key, plaintext)
    // msg_key is used exactly once, then never referenced again
    send(ciphertext)

// Bob mirrors the identical chain, one KDF step per message received, in order
function receiveMessage(ciphertext):
    k = KDF(k)
    msg_key = k
    return AEAD_decrypt(msg_key, ciphertext)

This is a real, working idea, and it is a strict improvement over chapter 3's static SK reuse: a one-way KDF means that given k_i, nobody can compute k_{i-1} — the function only runs forward. That already buys forward secrecy that static-key DH did not have: steal the chain state at message 1,000 and messages 1–999 remain safe, because deriving them backward would require inverting a cryptographic hash. Every message gets its own unique key, generated with negligible compute (a single KDF call, microseconds), with no network round trip and no extra bytes on the wire beyond a message counter. It is exactly the kind of solution that looks complete on a whiteboard.

ARC 04 · WHY IT FAILS

Forward secrecy without post-compromise security is half a guarantee

Run the same "steal a key, count the damage" exercise chapter 3 ran on static DH, but forward in time instead of backward. The hash chain is completely deterministic from its current state: given k_i, anyone can compute k_{i+1} = KDF(k_i), then k_{i+2}, then every key the chain will ever produce, without needing anything else — no further device access, no further observation of network traffic, no further anything. The chain has no mechanism for injecting fresh randomness that the thief didn't also receive.

  • One theft, unbounded future access. An attacker who extracts the chain state k_i at message 1,000 of a 90,000-message, five-year conversation can compute k_1001, k_1002, ... forever — every message either party ever sends again, for as long as the conversation continues to use this chain, with zero further access to either device. This is qualitatively worse than it sounds: it converts a single, point-in-time device compromise (a stolen unlocked phone for ninety seconds; a forensic extraction) into a permanent, silent wiretap that survives the phone being locked again, returned, or even factory reset — as long as the chain itself isn't reset.
  • No self-healing at any point. Reinstalling the app, changing the phone's passcode, or simply time passing does nothing to the math — KDF is a pure function of its input, and the input the attacker holds never expires. The only way this scheme recovers is a brand-new X3DH handshake producing a brand-new SK, which chapter 3 established happens once per new session, not on any schedule that responds to "have I possibly been compromised."
  • The failure is invisible to both parties. Nothing about ciphertext, message size, or timing changes when an attacker is silently following the chain. There is no error, no dropped message, no safety-number change — the exact failure mode chapter 6 revisits when discussing what a compromise notification even could look like for a purely passive attacker.
THE NUMBERS

Same model as chapter 3: two people, five years, ~50 messages/day, ~91,000 messages total. Under the hash chain, a single key-extraction event at message 1,000 costs the remaining ~90,000 messages — every future message in the conversation, decryptable the moment it's sent, with the device never touched again. Compare the two failure shapes directly: static-key DH (chapter 3) leaks the entire history from one compromise; a bare hash chain leaks the entire future from one compromise. Neither is remotely acceptable at the duration and scale a real relationship's message history implies — which is exactly why the real design needs both properties from the same construction, not a choice between them.

The gap is precise and worth naming exactly: a hash chain has no way to inject randomness the attacker never saw. The fix has to be "occasionally mix in fresh secret material that the chain-state thief could not have captured, because it didn't exist yet at the moment of the theft." That's a Diffie-Hellman exchange run again, mid-conversation — section 5 works out exactly how often, and against what candidates that get eliminated first.

ARC 05 · BETTER SOLUTION, CANDIDATES EXAMINED

How often should fresh DH material get mixed in?

The hash chain buys forward secrecy almost for free. Post-compromise security needs fresh, unpredictable randomness periodically injected — and the only primitive on the table that manufactures fresh shared randomness between two parties is Diffie-Hellman, exactly as it was in chapter 3. The design question is entirely about cadence: how often does a DH exchange have to run to heal a compromise, without destroying the cheap, offline-friendly properties the hash chain already earned? Step through the candidates:

Candidates for injecting fresh randomnessSTEP-BY-STEP

The elimination leaves exactly one workable shape: keep the cheap symmetric hash chain running for every message (it costs almost nothing and needs no reply), but treat every incoming message that carries a new Diffie-Hellman public value as a trigger to fold fresh DH output into the chain and start over. Because ordinary back-and-forth conversation already involves each party regularly sending the other something fresh, this "trigger" fires naturally, roughly once per direction change, with zero extra round trips and zero extra messages — the DH material simply rides along in a header field every message already needs to carry anyway. That combination — a symmetric ratchet advancing every message, and a DH ratchet advancing every direction change — is the Double Ratchet, and section 7 assembles it precisely.

ARC 06 · WHY THAT STILL COSTS

Combining two ratchets is not free either

Be honest about what the combined design costs before assembling it formally — every item below reappears later in this chapter as a named, quantified tradeoff or a live failure injection in section 15:

  • Messages don't arrive in order, and the ratchet has to know which chain and which position a given ciphertext belongs to. A phone that's been offline for two days can receive five messages in a burst, in whatever order the delivery layer (chapter 5) happens to hand them over. The header has to carry enough information — a message number N and a "previous chain length" PN — for the receiver to derive the right key even when messages 4, 2, 5, 1, 3 show up in that literal order.
  • Skipped message keys have to be cached, and that cache is a real attack surface. If message 2 hasn't arrived yet but message 4 has, the receiver must derive and store keys for the messages it skipped over (2 and 3) so it can decrypt them whenever they do show up — potentially never. An adversary who can induce large gaps (a manipulated N, or simply a lot of genuinely dropped messages) can force this cache to grow without bound unless the protocol caps it — which is exactly the MAX_SKIP bound section 8 derives and section 15 lets you overflow on purpose.
  • There is no clock or timestamp anywhere in the ratchet, by design — and that absence has to be compensated for elsewhere. Without a timestamp, the protocol can't say "this message is too old, discard it"; it can only bound things by count (MAX_SKIP), not by elapsed time, because trusting a device's local clock would open a manipulation surface and because deliberately encoding time creates a side channel (an observer could infer online/offline patterns from clock-derived metadata). Section 8(f) returns to this tradeoff directly.
  • A device restored from an old backup can hold stale ratchet state that no longer matches where the live conversation actually is — the peer kept advancing the real chain with real messages the backup snapshot never saw. Section 11 walks the resulting "waiting for this message" user experience end to end.
  • The DH ratchet step itself isn't free — two X25519 scalar multiplications and two HKDF calls, versus the symmetric ratchet's single HMAC call per message. Bounded and cheap in absolute terms (section 10 quantifies it), but it is real, non-zero compute that a "just hash the key forward" design from section 3 never had to pay.
THE ACCEPTED TRADE

None of these costs are eliminated by the final design — they're bounded and priced, the same pattern chapter 3 established for one-time prekeys. MAX_SKIP caps the memory an adversary can force a client to spend; header fields add a handful of bytes per message, dwarfed by the message itself; DH ratchet compute is amortized against direction changes, not every message. The alternative — refusing forward secrecy or post-compromise security to avoid these costs — is not actually on the table once you accept section 1's two requirements as non-negotiable for a billion-user, multi-year messaging product.

ARC 08 · INTERNAL IMPLEMENTATION

Two ratchets, interlocked

Both ratchets reuse primitives chapter 3 already introduced — HMAC-SHA256, HKDF, and X25519 — no new cryptographic building blocks are needed, only a new way of chaining them together across the life of a session.

(a) The symmetric-key ratchet: KDF_CK, one call per message

A chain key CK advances by a single HMAC call, and every advance also emits a message key, using distinct constant bytes so the two outputs are cryptographically independent even though they come from the same input:

pseudocodesymmetric_ratchet.txt — KDF_CK
function KDF_CK(CK):
    MK       = HMAC-SHA256(key=CK, data=0x01)   // this message's one-time key
    CK_next  = HMAC-SHA256(key=CK, data=0x02)   // the chain moves forward — CK is now discarded
    return (CK_next, MK)

This is exactly section 3's hash chain, just formalized with domain-separated outputs instead of reusing the chain key as the message key directly. MK is consumed by the AEAD construction in (e) below and then deleted — never stored, never reused. Two independent chains run at once per session: CKs for messages you send, CKr for messages you receive, because the two directions must be allowed to advance independently — Alice sending three messages in a row before Bob replies must not disturb Bob's copy of Alice's receiving chain expectations.

(b) The Diffie-Hellman ratchet: KDF_RK, triggered by direction change

Whenever an incoming header carries a ratchet public key DHr different from the one you already have on file, that's the signal that the sender has rotated — run the DH ratchet once, immediately, before processing the message itself:

pseudocodedh_ratchet.txt — triggered on a new incoming DH public key
function KDF_RK(RK, dh_out):
    output = HKDF(salt=RK, ikm=dh_out, info="WhisperRatchet", len=64)
    return (output[0:32] // new RK, output[32:64] // new chain key)

function DHRatchet(state, newDHr):
    state.PN  = state.Ns;  state.Ns = 0;  state.Nr = 0
    state.DHr = newDHr
    (state.RK, state.CKr) = KDF_RK(state.RK, DH(state.DHs, state.DHr))   // heals the RECEIVING side using the OLD DHs
    state.DHs = generateCurve25519Keypair()                       // fresh randomness — never observed by any past thief
    (state.RK, state.CKs) = KDF_RK(state.RK, DH(state.DHs, state.DHr))   // heals the SENDING side using the NEW DHs

Read that sequencing carefully, because it's the entire post-compromise security argument in five lines: the new receiving chain is derived using the ratchet keypair you already had, so if that keypair was stolen before this step, the attacker can still follow the receiving chain one more hop (the new peer public key is visible on the wire regardless). But the new sending chain is derived using a keypair generated after the theft — material the attacker never saw and cannot reconstruct. One direction heals immediately; the other heals one round trip later, once the same logic runs again using the now-fresh key. That gap — "healed after one round trip of unobserved DH material" — is precisely what section 15 lets you watch happen, byte by byte.

(d) Out-of-order delivery, skipped keys, and MAX_SKIP

Every header carries (DH, PN, N): the sender's current ratchet public key, the length of the sender's previous sending chain (so the receiver knows how many trailing keys from the old chain might still be in flight), and this message's position in the sender's current chain. A receiver that sees N=5 when it expected N=2 derives and caches message keys for 2, 3, and 4 before it can produce the key for 5 — those cached keys are exactly what let messages 2, 3, 4 still decrypt correctly whenever they eventually arrive, in any order. MAX_SKIP IS A MEMORY-EXHAUSTION DEFENSE, NOT A CORRECTNESS FEATURE

Without a cap, a sender (malicious, or a client with a corrupted counter) can claim N = 4,000,000 and force a receiver to derive and store four million message keys it will almost certainly never use — a trivial denial-of-service against that session's memory footprint, and if repeated across many contacts, against the device itself. MAX_SKIP makes this an explicit, bounded failure: exceeding it throws immediately rather than allocating unbounded memory. Signal's reference implementation documents a bound on the order of hundreds to low thousands of entries; the exact figure WhatsApp ships is not publicly confirmed, so treat any specific number as an illustrative reference value, not a disclosed production constant.

(e) The message header and the AEAD construction

Once MK is derived, it is never used to encrypt directly — it is expanded once more into three independent values, exactly as chapter 3's SK was expanded via HKDF rather than used raw:

Signal's own classic construction (documented in the published Double Ratchet and Signal Protocol specs) pairs this with AES-256-CBC for confidentiality and HMAC-SHA256 for the authentication tag — an encrypt-then-MAC construction rather than a single combined AEAD primitive like AES-GCM, chosen when the protocol was first specified for its conservative, well-analyzed building blocks. This chapter's live simulator (section 15) substitutes an HMAC-based keystream for the AES-256-CBC step specifically because implementing AES correctly and at constant time in a few dozen lines of teaching JavaScript is its own hazard-prone project outside this course's scope — every other part of the construction above (the HKDF split, the independent MAC key, the associated-data binding) is implemented exactly as shown and is what the smoke test in this chapter's build verifies.

(f) Edge cases engineers actually hit

  • Stale backup restore. A device restored from a backup taken a week ago has ratchet state frozen at that point — its Ns/Nr counters and chain keys don't know about anything the real conversation did in the meantime. The very next incoming message looks like it's arriving from "the future" relative to the restored state, which either forces a large, possibly over-MAX_SKIP jump, or (if the peer has since performed DH ratchet steps the backup never captured) simply fails to derive a matching key at all — the client-visible "waiting for this message" state section 11 covers.
  • No clock, on purpose. The header carries no timestamp anywhere. This is deliberate: trusting a device's local clock as a security parameter is a manipulation surface (an attacker who can skew a clock could influence key-expiry logic), and a real wall-clock time in every header would leak metadata about exact send times to anyone who can see ciphertext, including a passive network observer, independent of what the server itself logs. The cost is that "how stale is too stale" can only be expressed as a message-count bound (MAX_SKIP), never a time bound — an intentional and specific tradeoff, not an oversight.
  • Quantifying a one-time key theft, message by message. Say an attacker extracts a device's full ratchet state right after message k is sent. They can compute every subsequent message in the same, still-active sending chain the compromised party uses next — because the chain is deterministic forward, exactly like section 3's naive design — until the compromised party's peer sends something that forces a DH ratchet step incorporating a freshly generated private key the attacker never saw. In the ordinary back-and-forth cadence of a real chat, that is typically the very next reply: one message, sometimes two, leak; then the ratchet heals. Section 15 lets you measure this exactly, on demand, rather than take the claim on faith.
ARC 09 · TRADEOFFS

Ratcheting, five ways

Every protocol serious about forward secrecy over long-lived sessions has had to answer "how often do we mix in fresh DH material," and the answers diverge sharply based on what each protocol was willing to give up:

SYSTEMRATCHET DESIGNWHAT THEY BOUGHTWHAT THEY PAID
WhatsAppDouble Ratchet (Signal protocol library) — symmetric ratchet per message, DH ratchet per direction change forward secrecy every message post-compromise security every direction flip tolerates unbounded offline gaps skipped-key cache management no timestamp, count-bounded only
SignalDouble Ratchet (reference implementation; the spec's origin) identical guarantees same MAX_SKIP tuning tradeoff

Telegram (Secret Chats, MTProto)One long DH-derived key per chat; manual or usage/time-threshold rekey, not automatic per-message simple key schedule forward secrecy granularity is "per rekey," not per message cloud chats have no E2E ratchet at all
Matrix (Olm)Olm implements the Double Ratchet directly, per-device, Signal-derived same guarantees as Signal group chats (Megolm) trade the per-message ratchet for a different, weaker-forward-secrecy sender-key scheme
OTRDH-only ratchet, opportunistic per-message when both parties are live; no symmetric-key ratchet, no offline header scheme real post-compromise security while both are online no asynchronous / offline delivery model at all no defined behavior for arbitrarily out-of-order messages

The pattern repeats from chapter 3: wherever a design commits to "forward secrecy and post-compromise security, continuously, across an unbounded offline gap," it converges on something shaped like the Double Ratchet — a cheap chain for every message, a DH exchange for healing. Where a product settles for less (Telegram's cloud chats, iMessage pre-2024, Discord and Slack's plaintext-at-rest-on-server models entirely), it's an explicit scope decision about the threat model, not a cheaper way to get the same guarantee.

ARC 10 · PERFORMANCE CHARACTERISTICS

Amortizing the expensive operation against direction changes, not messages

The entire performance argument for the Double Ratchet's design is that the expensive operation — a Diffie-Hellman scalar multiplication — runs proportional to how often the conversation changes direction, not proportional to how many messages are sent. A burst of ten messages in a row from the same person costs ten cheap HMAC calls and zero DH operations.

  • Compute per message (symmetric ratchet): 2 HMAC-SHA256 calls (advance the chain, derive the message key) plus one HKDF call to split the message key into encryption/auth/IV material — all sub-microsecond on a modern mobile CPU.
  • Compute per direction change (DH ratchet): 2 Curve25519 scalar multiplications plus 2 HKDF calls — tens of microseconds total, and it happens once per reply, not once per message.
  • Memory per session: a handful of 32-byte keys (RK, CKs, CKr, DHs keypair) plus the bounded skipped-key cache — worst case MAX_SKIP entries at roughly 40 bytes each, so on the order of tens of kilobytes per session in the worst case, not per message. The real mobile constraint is this multiplied across every open conversation a device maintains simultaneously, not the cost of any single session.
  • Network: zero additional round trips. The DH ratchet's fresh public key rides inside a header field of a message that was already being sent — there is no separate handshake message, unlike a synchronous re-key negotiation would require.
  • Battery/radio: negligible marginal cost — the CPU work happens while the radio is already awake to transmit or receive the message itself; there is no additional wakeup this protocol causes on its own.

ARC 11 · REAL-WORLD PRODUCTION

Where the ratchet's edge cases show up in production

"Waiting for this message" — a real, named failure state

Both Signal and WhatsApp have historically surfaced a client-visible message — "Waiting for this message. This may take a while." — when a client receives ciphertext it cannot yet derive a key for. Reasoning from this chapter's model: that string is the user-facing symptom of a ratchet whose receiving-chain state does not line up with what the sender's header claims, which the client cannot resolve on its own (it does not have a resend mechanism inside the cryptographic layer itself — chapter 5's delivery pipeline owns retries). The specific root cause of any individual occurrence — a corrupted local session record, a race in session storage across a multi-device fan-out, or a genuinely-too-large skip — is not something either company publishes a postmortem for; treat the mechanism above as reasoned from the published protocol design, not as a confirmed root-cause breakdown of any specific incident.

Multi-device ratchet desync

WhatsApp's 2021 multi-device architecture (introduced in chapter 3's section 11) means a linked desktop or web client runs its own independent Double Ratchet session against each of a contact's devices — there is no single shared ratchet state "for the account." A crash mid-write to a linked device's session storage, or a message fan-out that reaches one of Bob's devices but not another before a crash, is exactly the class of bug that produces "this device is out of sync" symptoms — and it is a session-storage and fan-out reliability problem layered on top of a mathematically sound ratchet, not a flaw in the Double Ratchet algorithm itself. This distinction — protocol correctness versus storage/orchestration correctness — is the one a Staff engineer is expected to draw immediately when triaging this bug class.

Backup-restore breakage

WhatsApp's end-to-end encrypted chat backups (rolled out from 2021) back up message content; whether and how live ratchet/session state is captured and restored is not something WhatsApp's public documentation details at the level of this chapter's state machine. Reasoning from the architecture generally: a backup that faithfully restored frozen ratchet state without also being able to bring it forward to the conversation's real, current position would recreate exactly the stale-state problem section 8(f) describes, which is consistent with why restoring an account onto a new device commonly triggers fresh session establishment (and the accompanying "security code changed" notice for all contacts) rather than resuming old ratchet state silently — treat this as reasoned from public architecture, not an officially documented mechanism.

What's publicly known vs. speculation

The Double Ratchet Algorithm specification itself (Perrin & Marlinspike, 2016, revised since) is public and is the primary documented source for every mechanism in this chapter. What is not publicly documented: the exact MAX_SKIP value WhatsApp ships, the internal structure of its session-storage layer, and the precise behavior of its backup system with respect to live ratchet state. Signal's own reference library (libsignal) documents an illustrative bound on skipped keys on the order of hundreds to low thousands — treat that figure, and any number in this section beyond the published protocol mechanics, as a reasonable reference point reasoned from the public record, not a confirmed WhatsApp production constant.

A real implementation keeps more state than the textbook description in section 8 — worth calling out explicitly, because it's exactly the kind of detail that separates "read the spec once" from "operated this in production":

WHY THE ENGINEERS CHOSE THIS — TWO DECISIONS TO STEAL

1. Retain a short, bounded history of previous receiver chains, not just the current one. The textbook description in section 8 only tracks the single current DHr/CKr pair; but a message can legitimately arrive so late that two or more DH ratchet steps have happened on the sender's side since it was sent — its header's DH value won't match the current DHr or derive correctly from it. Production session state keeps a small, bounded number of recent receiver-chain generations (not unbounded — bounded exactly the way MAX_SKIP bounds message keys within one chain) so these still-plausible late arrivals decrypt instead of silently failing. 2. Make "too many skipped keys" a typed error path, not a crash. Because a hostile or buggy peer inflating N is an expected adversarial input, not an unreachable case, real implementations model exceeding MAX_SKIP as an explicit, catchable error — exactly the same defensive-by-construction pattern chapter 3 highlighted for one-time prekey exhaustion.

The three functions that matter most, in annotated pseudo-TypeScript:

typescriptsession_cipher.ts — ratchetEncrypt()
function ratchetEncrypt(state: RatchetState, plaintext: Uint8Array, ad: Uint8Array): Envelope {
  const [nextCK, mk] = kdfCK(state.CKs);              // symmetric ratchet: one HMAC step
  state.CKs = nextCK;                                // old CK is gone — cannot be recovered

  const header: Header = { dh: state.DHs.pub, pn: state.PN, n: state.Ns };
  state.Ns += 1;                                    // advance this chain's message counter

  const { ciphertext, tag } = aeadEncrypt(mk, plaintext, concat(ad, encode(header)));
  return { header, ciphertext, tag };                 // mk is never included on the wire or returned again
}
typescriptsession_cipher.ts — ratchetDecrypt(), the branch that matters
function ratchetDecrypt(state: RatchetState, env: Envelope, ad: Uint8Array): Uint8Array {
  const cached = trySkippedMessageKeys(state, env.header);   // out-of-order fast path (d)
  if (cached) return aeadDecrypt(cached, env.ciphertext, env.tag, concat(ad, encode(env.header)));

  if (!state.DHr || !bytesEqual(env.header.dh, state.DHr)) {   // direction just flipped
    skipMessageKeys(state, env.header.pn);       // drain the OLD chain's stragglers first
    dhRatchet(state, env.header.dh);             // §8(b): heals recv now, send after the NEXT flip
  }
  skipMessageKeys(state, env.header.n);          // derive+cache anything skipped in the CURRENT chain

  const [nextCK, mk] = kdfCK(state.CKr);
  state.CKr = nextCK;  state.Nr += 1;
  return aeadDecrypt(mk, env.ciphertext, env.tag, concat(ad, encode(env.header)));
}
typescriptsession_cipher.ts — skipMessageKeys(), the MAX_SKIP boundary
function skipMessageKeys(state: RatchetState, until: number): void {
  if (state.Nr + MAX_SKIP < until) {
    throw new Error("MAX_SKIP exceeded — refusing to derive unbounded message keys");
  }
  if (state.CKr != null) {
    while (state.Nr < until) {
      const [nextCK, mk] = kdfCK(state.CKr);
      state.CKr = nextCK;
      state.skipped.set(key(state.DHr, state.Nr), mk);   // cached — deleted the instant it's used (d)
      state.Nr += 1;
    }
  }
}

These three functions, plus dhRatchet() from section 8(b), are the entirety of the Double Ratchet's runtime logic — no additional state machine complexity beyond bookkeeping the counters and the bounded skipped-key cache.
