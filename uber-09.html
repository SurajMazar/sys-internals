UBER ENGINEERING INTERNALS · CHAPTER 09

Every Arrow Is Now
a Network Call: RPC & the Service Mesh

Chapter 8 ended by decomposing one monolith into independently deployed services and casually drawing arrows between them. This chapter takes that phrase seriously: an arrow between two services is a network call, which can time out, get dropped, or arrive at an instance that no longer exists — and at a scale of thousands of independently deployed services, no team can be allowed to hand-roll its own answer to that problem. This chapter derives, from first principles, why that pressure produces first a shared client library and eventually the sidecar-proxy service-mesh pattern, and exactly what each layer costs.

ARC 01 · THE PROBLEM

Thousands of services, all needing the same five things, none of them free

Once dispatch, pricing, trips, notifications, and analytics are separate, independently deployed services (chapter 8), every call any one of them makes to another crosses a real network boundary. That single change quietly imports an entire category of problems that a function call never had: the callee might be slow, might be down, might not exist at the address you expected anymore because it just autoscaled, and the network itself might simply drop your request with no signal at all.

Every one of those calls needs the same five capabilities to be handled correctly, and — crucially — every one of those capabilities needs to be handled consistently across the whole fleet, not per-team:

  • Service discovery. "Where is a healthy instance of the pricing service right now?" — an answer that changes continuously as instances autoscale, deploy, and crash.
  • Load balancing. Spreading requests across all healthy instances rather than hammering one.
  • Retries with backoff. A single dropped request shouldn't become a user-visible failure if the callee was simply, transiently slow.
  • Timeouts. A caller cannot wait forever for a callee that will never answer — but the "right" timeout value is a judgment call every single caller has to make.
  • Transport security. Traffic between services carries real user and payment data (chapter 7) and needs encryption and mutual authentication, not an implicit trust that "it's all internal."
WHY "EVERY TEAM IMPLEMENTS THIS THEMSELVES" DOESN'T SCALE

With five services owned by one platform-savvy team, five slightly different retry implementations are an annoyance. With thousands of services, owned by hundreds of teams, written in more than one language, "every team hand-rolls this" guarantees wildly inconsistent timeout values, retry policies that amplify rather than absorb failures (§4 makes this precise), and zero uniform way to even ask "which services are currently unhealthy" across the fleet. This chapter is the account of how that pressure forces cross-cutting network concerns out of application code entirely — first into a shared library, and ultimately into infrastructure that runs alongside, not inside, every service.

ARC 03 · NAIVE SOLUTION

Attempt #1: every service calls every other service directly

Start from the honest beginning: a service just calls another service's HTTP endpoint, with whatever retry and timeout logic its own author happened to write:

pseudocodedispatch_service/pricing_client.py — the strawman, annotated
def get_fare(trip_request):
    # hardcoded address — whichever instance this happened to be pointed at
    url = "http://pricing-service-3.internal:8080/fare"

    for attempt in range(3):        # "3 retries" — chosen because it felt reasonable
        try:
            resp = http.post(url, json=trip_request, timeout=2.0)  # 2s — also just felt reasonable
            return resp.json()
        except Timeout:
            continue              # retry immediately, no backoff, no jitter

    raise PricingUnavailable()

Written by one engineer, for one caller, this is completely reasonable — it works, it's simple, and it handles the case that matters most (a transient blip) in the most obvious way. The trouble starts when every other service writes its own version of this same function, independently, with its own guesses for retry count and timeout.

ARC 04 · WHY IT FAILS

Retry amplification: the math behind a self-inflicted outage

The single most dangerous property of naive, uncoordinated retries is that they can turn a small, transient problem into a large, sustained one — through simple multiplication across call depth.

  • Retry amplification compounds with call depth. If service A calls B, which calls C, which calls D, and every hop independently retries up to 3 times on failure, then a single failure deep in the chain can cause up to 3 × 3 × 3 = 27 total attempts to reach the failing service from just one original request — and at four hops of depth, 3^4 = 81. When the callee is failing because it's overloaded, not because of a random blip, this amplified retry traffic is additional load on an already-struggling service, driving it further into overload rather than giving it room to recover.
  • No backoff means retries arrive in lockstep. If every caller retries "immediately" on failure with no delay, and many callers hit the same failure at roughly the same moment (a deploy, a GC pause, a brief network blip), their retries all arrive back at the callee at roughly the same moment too — a synchronized retry storm indistinguishable, from the callee's perspective, from a sudden traffic spike.
  • Inconsistent timeouts break in non-obvious ways. If service A's timeout for calling B is shorter than B's own internal processing time for some request, A gives up and (per the naive code above) retries — while B is still working on the original request. B now has two units of work in flight for what was conceptually one logical request, and neither A nor B has any way to know that.
THE CONCRETE FAILURE

A downstream service takes a brief, real capacity hit — a deploy, a slow database query, a garbage-collection pause. Under naive, uncoordinated retries, every caller at every level of the call graph starts retrying against it simultaneously and without backoff, multiplying effective load by the product of each hop's retry count. What would have been a two-second blip, visible to a small fraction of requests, becomes a sustained overload that keeps the service unhealthy long after the original trigger has passed — a self-inflicted outage, caused entirely by well-intentioned retry logic with no fleet-wide coordination.

ARC 05 · BETTER SOLUTION

First a shared library — then, because that's not enough, a sidecar

The obvious first fix: stop letting every team write its own retry/timeout logic. Put it in one shared client library that every service links against, with sane defaults for backoff, jitter, and circuit breaking, chosen once by a platform team instead of guessed independently by every caller.

From per-team code, to a shared library, to a sidecarSTEP-BY-STEP

A shared library is a genuine improvement — it stops five different teams from inventing five different backoff formulas. But it has a structural limit worth naming precisely: it only helps services written in the languages the library supports, and upgrading its logic (say, fixing a bug in the circuit breaker) requires every service to pull a new library version and redeploy — you're back to needing hundreds of independent deploys to roll out one cross-cutting fix. The sidecar-proxy pattern is the answer to that specific limitation: move the logic out of the application's process entirely, into a separate proxy process running alongside it, so it can be upgraded once, fleet-wide, independent of which language any given service happens to be written in.

ARC 06 · WHY THAT STILL HURTS

The sidecar isn't free — name the costs precisely

  • Every call now takes an extra hop. Traffic goes app → local sidecar → network → remote sidecar → remote app, instead of app → network → remote app directly. That's real, measurable added latency per call (§10 quantifies it), paid on every single request in the system, forever.
  • Resource overhead, multiplied by every instance. A sidecar process runs alongside every single service instance — thousands of extra processes fleet-wide, each consuming its own memory and CPU, purely for infrastructure that adds no product value directly.
  • A whole new control plane to operate. Sidecars need central configuration — routing rules, retry policies, certificates for mutual TLS — pushed out consistently to every instance. That control plane is now itself critical, fleet-wide infrastructure: if it misconfigures or fails to propagate an update, every service in the mesh is affected simultaneously, which is a new, mesh-specific single point of failure that didn't exist when each service simply called another directly.
  • Debugging gets a new dimension of ambiguity. A failed request might have failed in the calling application, the callee application, or the mesh layer sitting between them (a misapplied timeout, a stale service-discovery entry, a circuit breaker that tripped for the wrong reason) — and telling which one requires the observability chapter 11 builds specifically to reconstruct a request's path across every hop it took.
THE HONEST FRAME

The sidecar pattern doesn't remove the cost of thousands of independently deployed services calling each other — it standardizes and centralizes that cost so it can be paid, measured, and improved once, by one team, instead of being paid inconsistently, invisibly, and often incorrectly by every team independently. That's a real, valuable trade at Uber's scale. It is not a free upgrade, and a small fleet of services should think hard before adopting the full weight of a mesh for the same reason chapter 8 warned against adopting microservices too early.

ARC 08 · INTERNAL IMPLEMENTATION

Backoff with jitter, and the circuit breaker's state machine

Two mechanisms do almost all of the real work: a retry policy that spreads retries out over time instead of synchronizing them, and a circuit breaker that stops sending traffic to a callee that's clearly already unhealthy.

(a) Exponential backoff with jitter — defusing the retry-storm math from §4

Instead of retrying immediately, each retry waits a randomized delay that grows with attempt number:

pseudocode (illustrative)backoff.compute_delay()
def compute_delay(attempt, base_ms=50, cap_ms=2000):
    # exponential growth, capped, then randomized ("full jitter")
    max_delay = min(cap_ms, base_ms * (2 ** attempt))
    return random.uniform(0, max_delay)   # jitter: never the same delay across callers

The jitter matters as much as the exponential growth: without it, every caller that failed at the same moment computes the same delay and retries in lockstep anyway — a synchronized retry storm, just delayed by a fixed offset instead of eliminated. Randomizing within the window spreads retries out over time, converting a spike into a smoother trickle the recovering callee can actually absorb.

(b) The circuit breaker — stop calling something that's already down

A circuit breaker tracks a callee's recent success/failure rate and moves through three states, exactly the way an electrical circuit breaker protects a circuit from a persistent fault rather than continuously retrying it:

STATEBEHAVIORTRANSITIONS OUT
CLOSEDRequests pass through normally; failures are counted.Failure rate over a rolling window exceeds a threshold → OPEN
OPENRequests fail immediately, locally, without even attempting the network call — protecting both the caller (no wasted wait) and the struggling callee (no added load).After a cooldown timer elapses → HALF-OPEN
HALF-OPENA small number of trial requests are allowed through to test if the callee has recovered.Trial requests succeed → CLOSED. Trial requests still fail → back to OPEN.

ARC 09 · TRADEOFFS

Four ways to standardize cross-cutting network logic

APPROACHWHAT IT BUYSWHAT IT COSTS
Per-team hand-rolled logic (§3) zero infrastructure investment total flexibility per team retry-storm amplification (§4) wildly inconsistent behavior fleet-wide
Shared client library one, consistent, well-tested implementation low added latency (in-process) only helps services in supported languages a fix requires every service to redeploy
Sidecar proxy / service mesh (this chapter's endpoint) language-agnostic upgradeable fleet-wide without app redeploys uniform mTLS, observability hooks added latency per hop resource overhead per instance a new control plane to operate
In-process "library plus a dedicated routing tier" (Uber's own early, publicly documented approach) avoids per-instance sidecar resource overhead still couples cross-cutting upgrades to library versions in supported languages

Read this the same way as chapter 8's spectrum: there is no row that is simultaneously cheap, language-agnostic, and instantly upgradeable — each later row buys back one of the earlier row's limitations at a real, ongoing infrastructure cost, and the right point on the spectrum depends on fleet size and language diversity, not on which pattern is newest.

ARC 10 · PERFORMANCE / SCALE CHARACTERISTICS

The hop tax, and what a circuit breaker actually buys back

Two numbers matter most when evaluating a mesh at scale: the per-hop latency it adds, and how much overload it prevents during a partial outage compared to uncoordinated retries.

  • Per-hop latency is small but compounds with call depth. A sidecar hop typically adds low-single-digit milliseconds of overhead per call (proxying, mTLS handshake amortization, policy evaluation) — a widely cited, general industry figure for this class of proxy, not a specific measured Uber number. That's negligible for one hop; on a request that fans out across four or five services in sequence, it becomes a real, additive contributor to end-to-end latency that a team must budget for explicitly.
  • A circuit breaker's value shows up specifically under partial failure, not steady state. In healthy conditions, a mesh with a circuit breaker and one without behave identically. The entire benefit appears exactly when a downstream service starts failing — bounding the retry amplification from §4's math rather than letting it compound freely.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

Retry storms are one of the industry's most common self-inflicted outages

Uber has not published a detailed public postmortem naming a specific internal retry-storm incident, so this section teaches the realistic, industry-standard incident pattern this class of system produces — one of the most commonly discussed failure modes across the entire industry of companies running large service fleets — and says so plainly rather than inventing a specific internal Uber event.

Pattern 1: the retry storm that outlasts its own trigger

A downstream dependency has a brief real problem — a slow database query, a deploy, a garbage-collection pause — lasting only seconds. Uncoordinated retries across the fleet, without backoff or jitter, amplify total load on that dependency (§4's math) well past what it can handle, and the resulting overload persists long after the original trigger has resolved, because the retry traffic itself is now the problem. The general fix — exponential backoff with jitter, plus a circuit breaker that stops sending traffic once failure rate crosses a threshold — is precisely §8's mechanism.

Pattern 2: cascading failure from one slow (not down) dependency

A dependency that's merely slow, not failing outright, is often more dangerous than one that's cleanly down: callers wait on connection pools and threads that don't free up, and that resource exhaustion propagates to parts of the system with no direct relationship to the original slow dependency — a failure "in one corner" becoming an outage everywhere calls eventually route through that corner. Aggressive timeouts and circuit breaking are the general defense, precisely because they convert "slow and eventually might respond" into "fast, clean failure now" — which callers can actually recover from.

Pattern 3: an over-aggressive circuit breaker causing its own outage

A poorly tuned breaker — threshold too low, or a rolling window too short and noisy — can trip on a brief, ordinary blip and stay open longer than the real problem justified, refusing perfectly healthy traffic and turning a minor hiccup into a self-inflicted, breaker-caused outage. This is the honest counterpoint to §8: a circuit breaker is a real safety mechanism, but its parameters need the same careful, load-tested tuning as any other production safety system — badly configured protection is its own incident category.

ARC 13 · CODE WALKTHROUGH

Reading a sidecar: illustrative reference implementation

The specifics of any single company's current internal mesh implementation are not fully public; what follows is precise, representative pseudocode of how a sidecar proxy of this shape is genuinely built in production — labeled as illustrative throughout.

sidecar/
├── ● discovery/client.go — polls or streams the control plane's health registry for live instances
├── lb/round_robin.go · least_conn.go — chooses among currently healthy instances
├── ● retry/backoff.go — exponential backoff + full jitter (§8a)
├── ● circuitbreaker/breaker.go — CLOSED/OPEN/HALF-OPEN state machine (§8b)
├── tls/mtls_handshake.go — mutual TLS using certs issued by the control plane's CA
└── observability/trace_headers.go — attaches trace context for chapter 11's distributed tracing
control-plane/
├── health_registry.go — tracks which instances are alive and healthy, fleet-wide
├── routing_config.go — pushes retry/timeout/routing policy to every sidecar
└── ca.go — issues and rotates the certificates every sidecar's mTLS depends on

The circuit breaker's core state machine, matching §8(b)'s table exactly:

Go (illustrative)circuitbreaker/breaker.go
type State int
const (Closed State = iota; Open; HalfOpen)

func (b *Breaker) Allow() bool {
    switch b.state {
    case Open:
        if time.Since(b.openedAt) > b.cooldown {
            b.state = HalfOpen
            return true          // let exactly one trial request through
        }
        return false              // fail fast, don't even attempt the network call
    case HalfOpen:
        return b.trialInFlight == false
    default: // Closed
        return true
    }
}

func (b *Breaker) RecordResult(ok bool) {
    switch b.state {
    case HalfOpen:
        if ok { b.state = Closed; b.resetCounters() } else { b.state = Open; b.openedAt = time.Now() }
    default:
        b.recordInWindow(ok)
        if b.failureRate() > b.threshold {
            b.state = Open; b.openedAt = time.Now()
        }
    }
}

The backoff-and-retry loop the sidecar runs on the caller's behalf, replacing every team's hand-rolled version from §3:

Go (illustrative)retry/backoff.go
func CallWithRetry(ctx Context, req Request, breaker *Breaker) (Response, error) {
    for attempt := 0; attempt < maxAttempts; attempt++ {
        if !breaker.Allow() {
            return Response{}, ErrCircuitOpen   // don't even try — §8b
        }
        instance := lb.PickHealthyInstance()      // discovery + load balancing
        resp, err := transport.Send(instance, req, perAttemptTimeout)
        breaker.RecordResult(err == nil)
        if err == nil { return resp, nil }

        delay := backoff.ComputeDelay(attempt)    // exponential + full jitter — §8a
        time.Sleep(delay)
    }
    return Response{}, ErrMaxRetriesExceeded
}
WHY IT WAS BUILT THIS WAY

Notice the circuit breaker is checked before a new instance is even picked — an open breaker means the sidecar doesn't waste time on load balancing or attempt a network call it already has strong evidence will fail. And every retry re-runs PickHealthyInstance() rather than hammering the same instance again — a retry is only useful if it has a real chance of reaching a healthy target, which is exactly what the mesh's unified discovery and load-balancing layer, sitting outside any single application, is positioned to guarantee.
