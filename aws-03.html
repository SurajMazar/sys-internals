AWS CERTIFICATION PREP · CHAPTER 03

VPC Networking Fundamentals

Almost every scenario question on either exam eventually asks you to trace a request through a network — and almost every wrong answer on those questions comes from one of three specific misunderstandings about how a VPC actually decides what a subnet, a gateway, or a firewall rule will do. This chapter builds the mental model from the ground up: CIDR blocks and subnets, the route-table mechanism that actually defines "public" and "private," the one-directional truth about NAT gateways, and the Security Group/NACL pair the exam never tests in isolation.

You will be able todetermine whether a subnet is public or private purely by reading its route table, never by looking for a flag on the subnet itself.
You will understandexactly why a NAT Gateway lets a private instance reach out to the internet but never lets the internet reach in.
You will predictthe allow/deny outcome of a request through a stack of Network ACL and Security Group rules, given their real evaluation-order differences.
You will simulatea full hop-by-hop trace of a packet through a route table, a Network ACL, and a Security Group whose rules you configure yourself.
ARC 01 · EXAM CONTEXT

The domain underneath both of the other domains

This chapter maps to two Associate-exam domains at once. Design Secure Architectures (SAA-C03, 30%) — the single highest-weighted domain on the Associate exam — leans on VPC networking constantly, because "secure" almost always means "correctly isolated": which subnets can reach the internet, which can't, and which security controls sit between a request and the resource it's targeting. Design Resilient Architectures (SAA-C03, 26%) leans on it just as hard from the other direction — a resilient design spans multiple Availability Zones, and a subnet is bound to exactly one AZ, so multi-AZ resilience is, mechanically, a VPC subnetting decision before it's anything else.

Put those two domains together and VPC networking accounts for more exam weight, indirectly, than any single service chapter in this course. A question about an Auto Scaling group spanning two AZs, a database failover, or a public-facing load balancer all quietly assume you already know which subnet each of those things belongs in and why — this chapter is where that assumption gets made true.

Exact dates are hedged deliberately — the exam does not test VPC's release history. What it does test is the resulting shape of the service, and the shape below is worth noticing: AWS kept adding ways to reach the internet (or AWS services) without exposing a private subnet directly, which is exactly the design tension this whole chapter is about.

ARC 02 · THE COMMON WRONG INSTINCT

"Public means public, private means private, and a NAT box is basically a mini internet gateway"

Three plausible-sounding instincts show up constantly in wrong answers on this topic. First: that "public subnet" and "private subnet" are a setting — a flag you flip, a checkbox in the console, or simply a consequence of giving an instance a public IP address. Under this instinct, an instance with a public IP address sitting in any subnet should be reachable from the internet, full stop.

Second: that a NAT Gateway is a general-purpose bridge between a private subnet and the internet — since it clearly lets private instances "get out," the instinct assumes it must symmetrically let internet traffic "get in," the same way a home router with port forwarding might. Third, and more subtle: that a Security Group needs its own explicit outbound-allow rule mirroring every inbound-allow rule, the way a traditional on-premises stateless firewall would require — otherwise, the reasoning goes, how would the response traffic ever get permission to leave?

None of these instincts are careless. They match how firewalls and NAT worked in on-premises networking for decades, and a candidate who has never had to configure an actual VPC will often reason from that older mental model — which is exactly why the exam plants scenario questions that only resolve correctly if you replace it with AWS's actual mechanism.

ARC 03 · WHY IT'S WRONG

The mechanism, not the vibe, decides every one of these

A subnet has no internal "public" or "private" property anywhere in its own configuration. What actually exists is a route table associated with that subnet, and a route table is just a list of destination-CIDR-to-target mappings. A subnet is public if and only if its associated route table contains a route sending 0.0.0.0/0 (or another relevant public destination) to an Internet Gateway. Assigning a public IP address to an instance in a subnet whose route table has no such route changes nothing about reachability — the address exists, but nothing in the network path knows how to deliver traffic to or from the internet for it. The route table lookup is the entire decision; everything else is a side effect of that lookup.

A NAT Gateway is architecturally a one-directional, initiator-side address-translation service. It sits in a public subnet with its own Elastic IP, and when an instance in a private subnet opens an outbound connection, the NAT Gateway translates that instance's private address to its own public one, forwards the request out through the Internet Gateway, and — critically — tracks that specific connection so it can route the response back to the instance that opened it. There is no listener process on the NAT Gateway accepting brand-new, unsolicited inbound sessions from the internet; it only ever forwards traffic that corresponds to a connection an inside host initiated. That is the exact mechanism behind the classic exam trap named in this chapter's brief: a NAT Gateway lets a private subnet reach the internet outbound, and it does not let the internet reach in.

A Security Group doesn't need a mirrored outbound rule because it performs connection tracking. Once an inbound (or outbound) request matches an allow rule and is permitted, the Security Group remembers that specific connection and automatically waves through its return traffic in the opposite direction — no separate rule required. That single mechanism is the entire reason Security Groups are described as "stateful" and is the load-bearing fact behind half of this chapter's quiz.

THE TRAP, STATED PLAINLY

If a scenario says "instances in a private subnet must not be reachable from the internet, but must be able to download software patches," the correct design gives that subnet's route table a route to a NAT Gateway (or a VPC endpoint, for AWS-service traffic specifically) — never a route to an Internet Gateway. Adding an Internet Gateway route to a subnet's route table is, definitionally, what makes it public, regardless of anything else about the subnet's instances.

ARC 06 · LIMITS, QUOTAS & EDGE CASES

Ceilings the correct approach still has to respect

Some of what follows is architectural — true regardless of any account setting, and safe to state with full confidence. The rest is a documented AWS default quota, worth knowing as "a limit exists here," but treated as illustrative and increasable rather than a number to memorize to the digit.

  • VPC CIDR block size — architectural. A VPC's CIDR block can range from /16 (the largest, roughly 65,536 addresses) down to /28 (the smallest, 16 addresses) per AWS documentation. Every subnet you carve out of the VPC has to fit inside that block.
  • One subnet, one Availability Zone — architectural. A subnet cannot span multiple AZs. This is exactly why multi-AZ resilience is a subnetting decision: you need at least one subnet per tier per AZ you want to span, not one subnet with instances "spread across" AZs.
  • Five reserved addresses per subnet — architectural. AWS reserves exactly five IP addresses in every subnet: the network address, the VPC router address, two reserved for DNS and future use, and the broadcast address — reserved even though IPv4 doesn't support broadcast inside a VPC. This gives the real, computable formula this chapter's calculators use: usable host addresses in a subnet of prefix length p = 2^(32-p) − 5.
  • VPC peering is non-transitive — architectural, a hard limit, not a soft quota. No quota increase or configuration change makes a peering connection transitive; see the callout below.
  • VPCs per Region — documented default quota. Accounts default to a modest number of VPCs per Region (commonly cited as five), raisable via a service quota increase request — don't expect the exam to demand the exact current figure, only that you know a per-Region ceiling exists and is raisable.
  • Security Group rules per group — documented default quota. Each Security Group defaults to a two-digit ceiling on inbound rules and a separate two-digit ceiling on outbound rules (commonly cited as around 60 of each), also raisable by request.
  • NACL rules per direction — documented default quota. Each Network ACL defaults to a modest ceiling on rules per direction (commonly cited as around 20), also raisable by request — and remember that rule numbers, not the count itself, are what determines evaluation order.
EDGE CASE THE EXAM LOVES — PEERING DOES NOT CHAIN

If VPC A peers with VPC B, and VPC B separately peers with VPC C, A cannot reach C through B — full stop, regardless of route tables, regardless of how the peering connections are configured. VPC peering connects exactly two VPCs and is explicitly non-transitive. The two correct fixes a scenario is testing for are: create a direct A↔C peering connection, or replace the whole mesh with a Transit Gateway acting as a central hub so every attached VPC can reach every other attached VPC through one place. This course treats Transit Gateway's deeper design here only briefly — it earns its own dedicated treatment in a later, more advanced chapter.

ARC 11 · REAL-WORLD SCENARIO CASE STUDIES

Three original vignettes, in the exam's own phrasing style

Case 1 — the "private" subnet that wasn't. A logistics company's security team discovers, during a routine audit, that instances in a subnet named app-private-1a are directly reachable from the internet on port 22. Nobody changed a Security Group, and the instances were never assigned Elastic IPs on purpose. Diagnosis: a teammate, while debugging an unrelated connectivity issue weeks earlier, added a 0.0.0.0/0 → igw-xxxx route directly to that subnet's route table "temporarily" and never removed it. The subnet's name and its instances' configuration never changed at all — the route table entry alone made it public, which is precisely the mechanism this chapter opened with. Correct fix: remove the errant IGW route, confirm the subnet's route table instead sends 0.0.0.0/0 to the NAT Gateway (if outbound access is still needed), and audit every other "private" subnet's route table the same way — the subnet's name is not evidence of anything.

Case 2 — patching without paying for a NAT Gateway around the clock. A small startup runs a handful of private-subnet instances that only need outbound internet access a few times a month, to pull OS security patches. The NAT Gateway's hourly charge (it bills whether or not traffic is flowing, on top of a per-GB data charge) feels disproportionate to how rarely it's actually used, and the founders ask for a cheaper alternative. Correct approach: if the only destinations are AWS services (e.g. patches served from an S3-backed repository), a Gateway VPC Endpoint to S3 removes the need for any internet path at all, at no additional charge. If genuine general-internet reachability is required, a self-managed NAT Instance that's started only during a maintenance window (or a smaller, cheaper instance the team accepts as a single point of failure) is the honest cost/availability trade a NAT Gateway's continuous hourly billing doesn't offer. Either way, the NAT Gateway's cost is real and worth acknowledging plainly rather than treating it as the free default.

Case 3 — three VPCs, peered in a chain. A media company peers VPC A (shared services) with VPC B (staging), and separately peers VPC B with VPC C (a partner's VPC, for a joint project). A partner engineer reports that resources in VPC C cannot reach a shared logging service that lives in VPC A, even though C↔B and B↔A both show as active peering connections in the console. Diagnosis: this is the non-transitivity trap named directly in this chapter's brief — A↔B and B↔C being active does not give A↔C reachability, no matter how the route tables in B are configured. Correct fix: either create a direct A↔C peering connection (fine for three VPCs), or, if the company expects this mesh to keep growing, replace all of it with a Transit Gateway that A, B, and C each attach to once — the professional-level answer once "how many VPCs will eventually need to reach each other" stops being a small, fixed number.

ARC 16 · EXAM-DAY TAKEAWAYS

What to actually remember on test day

Five things carry more of this chapter's exam weight than everything else combined. "Public" and "private" are a route-table fact, never a subnet flag — a subnet is public only if its route table sends 0.0.0.0/0 to an Internet Gateway, and a public IP address on an instance in a subnet without that route changes nothing. A NAT Gateway is one-directional — it lets a private subnet's instances initiate outbound connections and receive the responses, and it never accepts an unsolicited inbound connection from the internet. Security Groups and NACLs are opposites on every axis that matters — stateful vs. stateless, instance-level vs. subnet-level, allow-only vs. allow-and-deny, evaluate-all vs. evaluate-in-numbered-order-first-match — and the exam tests them as a pair far more often than either one alone. VPC peering never chains — A↔B and B↔C give you nothing between A and C; that needs a direct A↔C connection or a Transit Gateway. And VPC endpoints are the "skip the NAT Gateway entirely" answer whenever the actual destination is an AWS service rather than the general internet — Gateway endpoints for S3/DynamoDB at no extra charge, Interface endpoints (PrivateLink) for the rest at an hourly-plus-data cost.
