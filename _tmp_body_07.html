RABBITMQ INTERNALS · CHAPTER 07

Streams: The Log Comes to RabbitMQ

Every queue you have met so far — classic, mirrored, quorum — shares one property: consuming a message removes it. That single decision, correct for a work queue, makes three entire workloads either impossible or brutally expensive. RabbitMQ 3.9 answered by importing an idea from outside the AMQP world entirely: an immutable, append-only log, bolted onto the broker as a new queue type called a stream. This chapter derives why, and then goes inside osiris — the library that makes it real.

ARC 01 · THE PROBLEM

Destroy-on-consume is a feature — until it isn't

A classic or quorum queue is, at its core, a FIFO with acknowledgement: a message sits in the queue until some consumer takes delivery and acks it, at which point rabbit_variable_queue (or rabbit_fifo for quorum queues) removes it from the data structure entirely. That is exactly the right model for a work queue — a task should be done by exactly one worker, then gone. But it is the wrong model for at least three workloads that show up constantly in real systems, and no amount of clever queue configuration fixes them, because the limitation is structural, not tunable.

  • Replay. A new consumer — a fresh analytics job, a rebuilt read model, a developer debugging yesterday's incident — cannot read history. The messages it needs were already acked and destroyed by whichever consumer got them first. There is no "rewind" on a queue, because a queue has no notion of a position; it only has "what's currently in here."
  • Large fan-out. If five independent teams each need every message (an order-events stream feeding billing, fulfillment, analytics, fraud, and a data warehouse), the only AMQP-native way is five separate queues, each bound to the same exchange, each holding its own full copy of every message. Storage and the routing/enqueue cost inside rabbit_exchange_type_* both scale linearly with the number of consumer groups, not with the number of distinct messages.
  • Very high throughput with many consumers. Chapter 4 derived the one-process-per-queue ceiling: every classic queue is a single Erlang process (rabbit_amqqueue_process) executing a receive loop, and every consumer attached to it is more work funneled through that one mailbox — credit accounting, delivery bookkeeping, per-consumer dispatch. Quorum queues spread writes across a Raft group but still funnel client-facing delivery through one leader-side process. Past a few thousand messages/sec fanned out to dozens of consumers, that single process becomes the bottleneck no matter how much CPU the box has spare.

All three symptoms have the same root cause: a queue is a mutable collection with delivery baked into removal. What you actually want for these workloads is something Kafka proved out years earlier — an append-only log where reading is a pure function of a position, and that position lives with the reader, not with the data. RabbitMQ's answer is not "become Kafka"; it's "add a log-shaped queue type that lives inside the broker you already run, wired into the exchange/binding model you already use."

WHY THIS MATTERS FOR THE REST OF THIS CHAPTER

Everything below follows from one substitution: replace "remove on ack" with "append forever (until retention), track a reader's position separately." Storage, replication, the wire protocol, even the failure model — all of it is downstream of that one structural change. Keep asking, section by section: what did we have to build because the data is no longer removed?

DEEP CONTEXT · WHY NOT JUST EMBED KAFKA?

The RabbitMQ core team considered and rejected running an embedded log engine borrowed wholesale from another project. The reasoning: RabbitMQ's value proposition is routing (exchanges, bindings, topic patterns) plus operational simplicity (one broker, one clustering story, one protocol family with an optional second one). Bolting on a foreign storage engine would mean two replication systems, two consistency models, and two sets of operational runbooks glued together at the seams. Building osiris as a small, purpose-specific Erlang library — reusing the existing cluster membership, the existing exchange/ binding layer for routing messages into a stream, and a new coordinator built on the Raft library already in the codebase — kept the "one broker" promise intact. You'll see the cost of that choice in §6.

ARC 03 · NAIVE SOLUTION

Attempt #1: fan out to N durable queues

Before osiris existed, this was the actual production workaround, and it is worth taking seriously because it already gets the routing half right: bind a durable queue per consumer group to the exchange that carries your events. Each group gets a private, ordered, fully-acknowledged copy of the stream. No new broker feature required — just topology.

bashnaive_fanout.sh — one queue per consumer group, wired to a topic exchange
# the exchange every "order.events" message is published to already exists
rabbitmqadmin declare exchange name=order.events type=topic durable=true

# billing, fulfillment, analytics, fraud, warehouse — five teams, five private copies
for GROUP in billing fulfillment analytics fraud warehouse; do
  rabbitmqadmin declare queue name=order.events.$GROUP durable=true
  rabbitmqadmin declare binding source=order.events destination=order.events.$GROUP \
    routing_key="#"
done

# replay for a NEW group ("a 6th team joins next quarter")? declare queue #6 —
# and it only ever sees messages published AFTER it was created. History is gone.

This is not a bad instinct — it is the correct AMQP-native pattern for fan-out, and RabbitMQ's exchange layer (chapter 2) is genuinely good at replicating one publish into N bindings cheaply at the routing layer. The topology above will run in production today, will preserve per-group ordering, and needs zero new broker code. It already handles fan-out for the groups that exist at publish time. The two things it cannot do are the two things §1 called out: a group created after the fact has no history, and every group past the first is a full second (third, fourth…) copy of the data sitting on disk.

ARC 04 · WHY IT FAILS

The math: storage and process cost scale with N, not with the data

Quantify what "five copies" actually costs, and what happens as N grows or throughput rises.

THE STORAGE ARITHMETIC

A stream of 50 million 2 KB events (≈100 GB of payload) fanned out to 5 consumer groups via the naive topology needs 5 × 100 GB = 500 GB — not because the data changed, but because AMQP queues have no concept of "the same message, read from two positions." Add a 6th consumer group next quarter and you're at 600 GB, permanently, for data that is logically identical across all six copies. A stream holding that same 100 GB serves 6, 60, or 600 independent readers from one stored copy — storage is a function of retention, not of consumer count. That is the single biggest line item this chapter justifies.

  • No replay, ever, for anyone. Once a message is acked in any of the five queues, it is gone from that queue specifically — but more importantly, there is no queue anywhere holding "everything since the beginning" unless you deliberately create one and never consume from it (and then you've just invented, badly, an append-only log — which is the point of this chapter).
  • Per-process fan-out cost. Five queues means five rabbit_amqqueue_process (or five Raft groups for quorum queues) each independently doing routing acceptance, confirms, and per-consumer credit bookkeeping for the same logical event. At high publish rates this is 5× the CPU and 5× the replication I/O of a single logical write — the fan-out cost is paid at write time, on every node that mirrors or replicates each of the five queues.
  • Consumer scaling within one group still hits the ch.4 ceiling. Even a single one of those five queues, if 200 independent consumers attach to it for parallel processing, funnels all 200 consumers' credit and delivery bookkeeping through the same one queue process (or Raft leader). More queues do not fix a throughput ceiling inside any one of them.

So the naive topology is not wrong, exactly — it is the correct AMQP-native answer to a question ("how do I fan out to today's known consumers") that is narrower than the one that actually matters ("how do I let anyone, present or future, read this data at their own pace without multiplying storage"). Something has to change about what "consuming" means.

ARC 06 · WHY THAT STILL HURTS

Streams are not free replay — read the fine print

A native log solves §1's three problems, but it is not a magic "infinite, free, instant" primitive. Every cost below is a direct consequence of building the log inside the AMQP broker rather than as a standalone system, and you will hit each one operationally:

  • Bounded storage, always. A stream is not a substitute for a data warehouse. max-age and max-length-bytes are mandatory-in-practice retention limits — without them a stream grows until it fills the disk. "Replay" means "replay within retention," not "replay since the dawn of time."
  • Protocol translation tax over AMQP 0-9-1. A stream exposed to an ordinary AMQP client looks like a queue (x-queue-type=stream), which means every message still gets individually framed, individually delivered, and subject to normal channel/connection machinery — none of the chunk-level batching that makes the native path fast. You pay full AMQP overhead per message unless you switch clients.
  • Replication is intentionally lighter than Raft. Osiris's leader→follower push is faster than Ra's per-entry consensus, but it does not give you Ra's log-matching guarantee. §8 makes this precise: there is a narrow window around leader failure where an unacknowledged tail can be lost, a guarantee quorum queues do not have to make.
  • Super streams add a partitioning problem you now own. Splitting one stream into K partitioned streams for scale-out means picking a partition key and a K up front; like Kafka partitions, K is operationally painful to change later without a migration, because a partitioning key's mapping to partitions is a function of K itself.
  • Single active consumer adds a failover pause. Ordered processing across a consumer group means only one member is active at a time — which means a promotion delay (detect death → pick next → resume) every time that member disconnects, exactly the class of pause partition-based Kafka consumer groups also have to manage.

None of this is an argument against streams — it's the honest cost side of the ledger you need before choosing them over a quorum queue for a given workload. §9 makes the choice explicit.

This is deliberate reuse: a stream's queue record is bound to exchanges exactly like a classic or quorum queue. rabbit_exchange_type_topic and friends route a message to a stream the same way they'd route to any other queue — by appending it to the queue's mailbox for enqueue. The divergence starts one layer down, inside rabbit_stream_queue's implementation of the standard queue-type callbacks, which hands the message to osiris_writer instead of to a variable-queue or a Raft log.

ARC 08 · INTERNAL IMPLEMENTATION

Inside osiris: chunks, segments, replication, offsets

Four mechanisms to get precise about: (a) the on-disk chunk/segment/index format, (b) leader→follower replication and why it isn't Raft, (c) the offset model, and (d) retention.

(a) Chunks are the unit of everything

Osiris never writes one message at a time to disk or over the wire — it batches pending messages into a chunk: a header (chunk id = the offset of its first message, message count, a CRC32, a timestamp, the writer's epoch) followed by the messages themselves, back to back. The chunk, not the message, is what gets fsynced, what gets shipped to followers, and — critically for the stream protocol — what gets handed to a subscriber verbatim. This is the direct analogue of the Kafka course's chapter 3 (segments + index files): same idea, same reason (sequential I/O, batched fsyncs, batched network sends), independently arrived at.

Life of a published messageSTEP-BY-STEP

On disk, a stream's data directory holds a sequence of <offset>.segment files (each capped by stream_max_segment_size_bytes, default 500 MB) and a matching <offset>.index file per segment: a sparse table of {offset → file position, timestamp} entries written every N chunks, letting a reader seeking to an arbitrary offset or timestamp binary-search the index instead of scanning the segment from byte zero. Exactly the same trade Kafka makes — sparse index, linear scan for the last few entries — because it's the same problem (bounded index size vs. seek precision).

(b) Replication: leader-push, not Raft consensus

This is the nuance worth over-learning. osiris_writer runs on the stream's leader node: it accepts writes, appends the chunk to its own local segment, and pushes the chunk to every osiris_replica process (one per follower node) over a plain TCP connection — no leader election per write, no majority-commit-before-ack on the write path itself. Each replica appends what it receives to its own local segment and periodically reports back the offset it has durably written. The writer tracks the highest offset acknowledged by enough replicas to consider it "committed" for the purposes of consumer visibility. Membership and leader placement — who is the leader, which nodes are replicas, what happens when a node needs to be replaced — is a separate concern, handled by rabbit_stream_coordinator, which is a Ra (Raft) state machine. So: metadata about the stream is Raft-consistent; the message data itself is not.

THE GUARANTEE THIS TRADES AWAY

Quorum queues (rabbit_fifo over ra) commit every write through Raft's log-matching property: a write is only visible once a majority of the group has it in identical log order, and Raft's election rules guarantee the new leader after a failure has every committed entry. Osiris skips that consensus round on the hot path for throughput — so on leader failure, rabbit_stream_coordinator promotes the replica with the most advanced matching log tail, but any chunk the old leader had accepted and started replicating, without enough followers yet acknowledging it, can be lost. Streams trade a small, bounded durability window for the batching and throughput that make the dedicated protocol fast. Choose quorum queues, not streams, when every acknowledged write must survive any single failure with zero exceptions.

(c) Offsets: server-tracked, stored with the stream, not in a side topic

A consumer can attach at first, last, next, a specific numeric offset, or a timestamp (osiris resolves a timestamp to the nearest chunk via the sparse index). Unlike Kafka, which persists committed offsets in a dedicated internal topic (__consumer_offsets) replicated and compacted independently, RabbitMQ streams let a consumer commit its offset under a name (a "reference"), and osiris stores that name→offset mapping colocated with the stream's own log infrastructure — no second replicated topic, no second retention policy to manage. The tradeoff: offset tracking data lives and dies with the stream it belongs to, which is exactly the coupling you want for a broker-embedded feature, and exactly the coupling Kafka's operators avoid on purpose to let offset topics be reasoned about independently of any single topic's retention.

(d) Retention: segment-granularity, not message-granularity

Both max-age and max-length-bytes are enforced by deleting whole segment files — never by truncating a live segment mid-file. This falls directly out of (a): a segment is written append-only and read concurrently by any number of consumers holding raw file offsets into it; rewriting it in place to drop old entries would race every open reader. So retention is coarse by design: the oldest segment is dropped only once its newest entry crosses the age or size boundary, meaning actual retained data is always somewhat more than the configured limit — bounded by segment size, not by the limit itself.

SUPER STREAMS AND SINGLE ACTIVE CONSUMER

A super stream is not a new storage primitive — it is K ordinary streams, each independently leader- elected and replicated, presented to producers and consumers as one logical name. A producer hashes a partitioning key to choose one of the K underlying streams, exactly like a Kafka partitioner; consuming "the super stream" means running K independent stream consumers, one per partition, in your client library. Within any single stream (partitioned or not), single active consumer lets a named group of consumers agree that only one of them is delivered messages at a time — the others sit warm on standby — giving you strict total order across the whole group at the cost of not parallelizing within that one stream. Parallelism at scale therefore comes from the super stream's partition count, not from SAC.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

  • Append: O(1) amortized — sequential write of a chunk, batched fsync. Independent of stream size, unlike a queue whose enqueue cost is tied to a mutable in-memory/on-disk structure that also has to track per-consumer delivery state.
  • Sequential read (a consumer tailing near the end): effectively O(1) per chunk — the OS page cache almost always has the recent segment resident, and reads are pure sequential I/O.
  • Random/offset seek (replay from an old offset or a timestamp): O(log S) to find the right segment and index bucket via the sparse index, then a short linear scan within the bucket — same shape as Kafka's index lookup.
  • Per-process memory: an osiris_writer/osiris_replica holds small in-memory state (open file handles, a write buffer, offset trackers) — most of the working set lives in the OS page cache, not the BEAM heap, which is why streams handle many more concurrent consumers per GB of broker memory than a classic queue holding the same messages resident.
  • Disk access pattern: pure sequential for both writer and any consumer at (or near) the tail; degrades toward random I/O only for consumers reading far behind the tail across many old segments — exactly the same "slow consumer becomes a disk-bound consumer" curve as Kafka.
  • Message rate: published benchmarks from the RabbitMQ core team routinely show single-digit-million messages/sec aggregate through the dedicated stream protocol on modest hardware — a large multiple of what the same hardware sustains over AMQP 0-9-1, purely from chunk-level batching and avoiding per-message protocol framing.

ARC 11 · REAL-WORLD PRODUCTION

What teams actually hit

Incident 1: super-stream retention multiplies silently

A team migrates a high fan-out telemetry topic to a super stream with 8 partitions, sets max-length-bytes to their previous single-stream budget (say 50 GB), and is surprised when disk usage lands near 400 GB. The setting applies per partition, because each partition is an independent stream with its own retention — the super-stream abstraction is purely a producer/consumer convenience, not a shared storage budget. The fix is arithmetic, not code: divide the target total by the partition count before setting max-length-bytes, and reserve headroom for the fact that retention is enforced at segment granularity, so actual usage always overshoots the configured limit somewhat.

Incident 2: forgetting to open the stream protocol port

Teams that enable the stream plugin (rabbitmq-plugins enable rabbitmq_stream) commonly leave port 5552 out of their load balancer/security-group configuration, since every other RabbitMQ client traffic runs over 5672 (or 5671 for TLS). AMQP clients connect fine — a stream still looks like a queue over AMQP — and the failure only surfaces when someone adopts a stream-protocol client library for the throughput win, and gets connection timeouts that look unrelated to the broker at all.

Incident 3: migrating off mirrored queues straight into streams for the wrong workload

With classic mirrored queues deprecated in 3.9 and removed in 4.0, teams migrating in bulk sometimes route every queue that needs replication toward streams, on the assumption that "streams are the new replicated queue." For genuine work-queue semantics — one consumer processes one task, exactly once from that consumer's point of view, with dead-lettering and priorities available (chapter 8) — a quorum queue is almost always the right target, not a stream, which lacks per-message ack/requeue and dead-lettering entirely. The postmortem pattern is consistent: streams adopted for their throughput story on queues that actually needed quorum queues' delivery semantics, discovered only once a poison message needed dead-lettering and there was nowhere for it to go.

Simplified but structurally faithful: writing a chunk and replicating it.

erlangosiris_writer.erl — accept a batch, append, replicate
handle_call({write, Entries}, _From, #state{log = Log0, replicas = Reps} = State) ->
    %% Batch pending entries into ONE chunk: header (offset, count, crc,
    %% timestamp, epoch) + entries back to back. Chunk, never message,
    %% is the unit of fsync and of replication.
    Chunk = osiris_log:make_chunk(Entries, State#state.epoch),
    Log1  = osiris_log:write_chunk(Log0, Chunk),  %% local append + fsync

    %% Push, don't consense: no per-write leader election, no majority
    %% ack required before returning to the caller. Just fan the bytes out.
    [osiris_replica:send_chunk(R, Chunk) || R <- Reps],

    {reply, {ok, Chunk#chunk.next_offset}, State#state{log = Log1}}.
erlangosiris_replica.erl — receive, append, report progress (no consensus vote)
handle_info({tcp, _Sock, ChunkBin}, #state{log = Log0} = State) ->
    Chunk = osiris_log:parse_chunk(ChunkBin),
    Log1  = osiris_log:write_chunk(Log0, Chunk),  %% same append path as the leader

    %% Tell the writer how far we've durably written — this is a plain
    %% progress report, not a Raft AppendEntries acknowledgement; there is
    %% no log-matching check against the writer's history here.
    osiris_writer:replica_ack(State#state.writer_pid, self(), Chunk#chunk.next_offset),
    {noreply, State#state{log = Log1}}.
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Chunks, not messages, are the unit of I/O. Batching amortizes fsync and network round-trip cost across many messages — the same insight as Kafka's producer-side batching, applied here on the broker's write and replicate path instead. 2. Keep data-path replication out of Raft on purpose. Ra's consensus gives quorum queues correctness guarantees a work queue needs, at a latency cost per write; streams are for high-volume append/replay, so osiris spends that budget on throughput instead, and pushes the harder consistency question (who's the leader) into a separate, lower-frequency Ra machine (rabbit_stream_coordinator) where consensus overhead barely matters. 3. Reuse the existing routing layer. rabbit_stream_queue implements the same callback interface as every other queue type specifically so exchanges never need a special case for streams.
