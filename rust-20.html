Performance & Real-World Rust:
Verifying the Zero-Cost Promise

Every Rust pitch deck, README badge, and conference talk repeats the same three words: zero-cost abstractions. This chapter is where you stop taking that on faith. You will benchmark real code the way that actually produces trustworthy numbers — warm-up, std::hint::black_box, and the statistical machinery chapter 14 introduced you to — and then use that discipline to answer two separate, sharper questions: where does "zero-cost" hold exactly as advertised (an iterator chain compiling to the identical machine code as a hand-written loop), and where does it quietly not (a bounds check the optimizer cannot prove away)? Then you'll leave the microbenchmark behind entirely and look at three real companies who bet real production systems on Rust — what specifically justified each bet, what it cost them, and one honest read on when the bet isn't worth making at all.

ARC 01 · THE PROBLEM

"Fast" is not a property of a language — it's a claim you either verified or didn't

Nineteen chapters have built toward a specific set of guarantees: memory safety without a garbage collector (chapters 4–9), fearless concurrency (chapter 15), and a compiler that, chapter after chapter, has been shown to generate code you didn't have to hand-optimize yourself. Somewhere in that accumulation of good news, "Rust is fast" quietly turned from a conclusion you derived into an axiom people repeat. That shift is the actual problem this chapter exists to fix — not because the axiom is false, but because treating it as an axiom produces two opposite, equally expensive mistakes in real engineering organizations.

The first mistake: a team decides to rewrite a working service in Rust because "Rust is faster," pays months of compile-time and hiring-curve cost, and ships something whose actual bottleneck — a database round trip, a network call, a lock held too long — was never CPU-bound in the first place. The rewrite "feels" faster because greenfield code is always cleaner than the legacy system it replaced, and nobody ever isolates how much of the win was "Rust" versus "we finally fixed the N+1 query." The second mistake runs the other direction: a team assumes the compiler's "zero-cost" reputation covers everything, skips profiling a genuinely hot loop, and ships code that pays a real, measurable, avoidable cost — a bounds check the optimizer had no way to eliminate, an allocation hiding inside an innocent-looking iterator adaptor — because nobody checked.

Both mistakes have the same root cause: a performance claim was acted on before it was measured. This chapter gives you the two things that close that gap. First, a benchmarking methodology rigorous enough that the numbers it produces are actually true (§3–§6) — building directly on chapter 14's introduction to criterion, but going one level deeper into why its methodology works and where even correct methodology still has costs. Second, a precise, checkable map of where Rust's "zero-cost" claim is a proven fact about generated machine code and where it's a proof obligation you still have to discharge yourself (§7– §10). The chapter closes by testing all of it against reality: three real, named production stories (§11) where real engineers had to answer "is Rust actually the right call here" with money and deadlines on the line — and one honest answer for when it wasn't.

THE PATTERN THIS CHAPTER IS BUILT TO STOP

Search any large Rust codebase's git blame for a commit message like "switch to iterator chain, should be faster" with no benchmark attached, or a design doc that justifies a rewrite with "Rust is a systems language" and no measured bottleneck. Neither claim is necessarily wrong — but neither is verified, and by the end of this chapter you'll have the specific, cheap habits (§5, §7) that turn "should be faster" into a number with a confidence interval, and "Rust is a systems language" into a documented, falsifiable reason (§11).

The principle Rust inherited is usually paraphrased, but Bjarne Stroustrup's original formulation in The Design and Evolution of C++ (1994) is worth reading precisely, because Rust's own team quoted it almost verbatim when justifying the iterator design chapter 10 covered: "What you don't use, you don't pay for. ARC 03 · NAIVE SOLUTION

Attempt #1: trust a stopwatch

Derive the problem honestly, the way you'd actually stumble into it. You have a function you suspect is a hot path. The obvious first move — completely reasonable, and every working engineer has done it — is to time it with std::time::Instant around a big loop:

Rustsrc/main.rs — the "obvious" benchmark
use std::time::Instant;

fn digit_sum(mut n: u64) -> u64 {
    let mut sum = 0;
    while n > 0 {
        sum += n % 10;
        n /= 10;
    }
    sum
}

fn main() {
    let start = Instant::now();
    for i in 0..1_000_000u64 {
        digit_sum(i);
    }
    println!("{:?}", start.elapsed());
}

This compiles and runs under any current stable Rust toolchain, and it already gets one thing right: you picked a real, non-trivial, CPU-bound function (digit_sum sums the base-10 digits of a number — bounded, deterministic, no I/O) rather than benchmarking something dominated by network or disk latency. Run it with cargo run --release — the --release flag matters enormously here and you'll see exactly why in §4 — and watch what number comes back.

ARC 04 · WHY IT FAILS

Three failures, three different mechanisms — and one of them isn't a measurement problem at all

§3's deck surfaced three distinct numbers from the "same" benchmark, and it's worth naming exactly why each one is untrustworthy, because they demand three completely different fixes:

  • Single-sample noise. One Instant::now()/elapsed() pair captures whatever the OS scheduler, CPU frequency governor, and cache state happened to be doing during that one run. A context switch landing mid-benchmark, a page fault on first touch, or the CPU still ramping up from an idle P-state can each swing a single sample by an order of magnitude. This is a statistics problem: one draw from a noisy distribution is not an estimate of its mean.
  • No warm-up. The very first iterations of any loop run colder than the rest — instruction and data caches haven't filled, and on real hardware the CPU's own frequency-scaling logic hasn't yet ramped to its sustained clock. Rust has no JIT to "warm up" the way a JVM or V8 does (chapter 14 makes this same point) — the machine code was already final before main() ran — but the hardware
  • Dead-code elimination — not a measurement problem at all. This is the one that actually breaks the digit_sum example, and it's categorically different from noise: the compiler didn't measure wrong, it proved something true and acted on it. digit_sum is a pure function — no I/O, no shared state, a provably bounded loop — and its result inside main()'s loop is never used anywhere. LLVM's optimizer is entitled to conclude that a call whose result is discarded and which has no observable side effect contributes nothing to the program's behavior, and delete it — and once every call is gone, the now-empty loop gets deleted too. On a release build this reliably reports a "time" of a few picoseconds per call: not because digit_sum is fast, but because it no longer runs at all.
THIS IS A REAL, EXTREMELY COMMON FAQ

"Why does my benchmark show 0 nanoseconds" is one of the most frequently repeated questions on the Rust users forum and Stack Overflow, always with some variant of this exact shape: a pure function, an unused result, a release build. It is common enough that it directly motivated a stable standard-library API. Before Rust 1.66 (December 2022), the only portable way to defeat this optimization was test::black_box — part of the test crate, usable only on the nightly compiler, because it existed for libtest's unstable #[bench] harness. std::hint::black_box stabilized that exact tool for everyone, on stable, outside any test harness — which is precisely the API chapter 14 showed you and this chapter now explains the mechanism of.

Note the asymmetry worth sitting with: reasons one and two are about your measurement apparatus being imprecise. Reason three is about the compiler being correct — it is not a bug that dead code gets eliminated, that is exactly what an optimizing compiler is supposed to do. The fix, therefore, cannot be "make the compiler less aggressive." The fix has to be "give the compiler a true reason to believe the code isn't dead" — which is exactly what black_box does, and exactly why §5 introduces it first.

ARC 06 · WHY THAT STILL HAS COSTS

Correct methodology is not free, and it doesn't answer every question

Be honest about what §5's fix actually costs, because a chapter that only celebrates rigor and never prices it would be exactly the kind of unverified claim this chapter argues against:

  • Statistical rigor takes real wall-clock time. Criterion's defaults are a 3-second unmeasured warm-up followed by a 5-second measured sampling window per benchmark function. A suite of 100 benchmarks — not unusual in a performance-sensitive crate — costs on the order of 13+ minutes of pure cargo bench time before you've even looked at a number, and that's before --release compilation itself, which is its own line item below. Teams that skip benchmarking under CI time pressure aren't being lazy; they're making a real tradeoff this chapter should acknowledge rather than lecture past.
  • A microbenchmark measures a function in isolation — production never runs anything in isolation. A hot loop benchmarked alone is cache-resident and branch-predictor-warm in a way it frequently is not embedded in a large binary competing for the same L2/L3 cache with a hundred other call sites. A change that "wins" by 15% in criterion can be a rounding error — or occasionally even a regression — once profiled inside the real process under real load. This is exactly why §7's pipeline doesn't stop at the benchmark step.
  • The environment you benchmark on is part of the measurement, whether you account for it or not. Criterion's confidence interval describes noise within one run on one machine. It says nothing about a shared CI runner's noisy-neighbor CPU steal time, a laptop's thermal throttling after two minutes of sustained load, or a cloud VM's burstable-CPU credits running out mid-suite — any of which can shift results 2× or more between otherwise identical runs. "It got faster in CI" and "it got faster" are different claims.
  • Reading generated code is a separate skill from writing Rust, and most teams under-invest in it. §7 and §8 will show you how to actually confirm a "zero-cost" claim by reading assembly — but that skill doesn't come from knowing the borrow checker or the trait system. Verifying performance claims for your own code, rather than trusting a blog post about someone else's, requires deliberately building a habit most Rust curricula (this course included, until now) treat as optional.
  • None of this makes compile times shorter. The release profile most serious performance work turns on — lto = "fat", codegen-units = 1 — trades a slower, more thorough optimization pass for better generated code, and can multiply a crate's release build time several-fold. That cost is real, it compounds across a large workspace, and chapter 11's crate-organization advice (splitting a monolith into smaller crates) is one of the few real levers against it.

None of this is an argument against rigor — it's the honest ledger §1 promised. The next four sections (§7–§10) are where that ledger starts paying dividends: a repeatable pipeline, a precise map of where zero-cost genuinely holds, and real numbers instead of vibes.

WHY THE ORDER MATTERS

Each stage is ordered by cost and blast radius, not importance. Skipping straight to stage 5 (ship it, see what happens) is how "should be faster" commits get merged on vibes. ARC 08 · INTERNAL IMPLEMENTATION

Where zero-cost genuinely holds, and where it structurally can't

(a) The claim that holds: an iterator chain and a hand-written loop can compile to the same code

Chapter 10 first showed you the two sides of this comparison. Here they are again, because this chapter's job is to actually verify the claim rather than restate it:

Rusttwo ways to sum a slice
pub fn sum_loop(xs: &[i32]) -> i32 {
    let mut total = 0;
    for i in 0..xs.len() {
        total += xs[i];
    }
    total
}

pub fn sum_iter(xs: &[i32]) -> i32 {
    xs.iter().sum()
}

Step through what actually happens to each version between source and machine code. This is the same pipeline chapter 19 introduced for the borrow checker's MIR — here it's the same intermediate representation, used for a different question: not "is this borrow valid," but "did two different-looking programs converge to the same instructions."

Convergence: loop vs. iterator, source to assemblySTEP-BY-STEP

This is not folklore — the Rust project's own 2015 blog post "Abstraction without overhead: traits in Rust" (Aaron Turon) benchmarked a heavily trait-and-iterator-based Rust program against hand-written C for the same algorithm and found them within measurement noise of each other, which is exactly the claim §8(a)'s deck just walked through mechanically. The caveat that post itself was careful about, and that the callout below repeats, is that this convergence is a property of this specific compiled output, not a law of the language.

(b) The claim that structurally doesn't hold: bounds checking on an unprovable index

sum_loop's bounds check disappeared for a specific, narrow reason: LLVM's range analysis can prove that i, for the entire lifetime of that loop, is always less than xs.len() — because the loop's own bound is xs.len(). That proof is fragile in a way that matters in practice. Compare:

Rustan index the optimizer cannot relate to the slice's length
pub fn get_or_panic(xs: &[i32], idx: usize) -> i32 {
    xs[idx]   // idx came from a caller — no relationship to xs.len() is visible here
}

pub fn get_or_zero(xs: &[i32], idx: usize) -> i32 {
    *xs.get(idx).unwrap_or(&0)
}

get_or_panic's xs[idx] lowers to a runtime comparison — idx < xs.len() — followed by either the element load or a call into core::panicking::panic_bounds_check, which formats and prints "index out of bounds: the len is N but the index is M" and aborts or unwinds (chapter 13's territory). Nothing in get_or_panic's signature or body gives the optimizer any fact connecting idx to xs.len() — idx is an arbitrary caller-supplied value, and eliminating the check would let a caller read past the end of the slice, which is exactly the memory safety Rust's entire type system exists to forbid (chapters 4–9). The check is not a missed optimization; it is the safety guarantee, made visible as an instruction. get_or_zero performs the identical comparison — .get() is implemented with the same bounds check — but branches to a plain default value on failure instead of calling into panic machinery, which is typically cheaper in code size and slightly friendlier to the branch predictor and to inlining heuristics, without changing what's actually being verified.

A NUANCE INSIDE THE NUANCE: NOT EVERY Option<T> IS FREE EITHER

"Zero-cost" claims need the same scrutiny for data layout, not just control flow. Option<&T>, Option<Box<T>>, and Option<NonZeroU32> really are free — the same size as the inner type — because Rust's layout optimizer can steal an otherwise-impossible bit pattern (a null pointer, a zero) to represent None, a trick called niche-filling. Option<i32> is not free: every i32 bit pattern is a valid i32, there's no spare niche to steal, so the compiler must add a discriminant and the type grows past 4 bytes. Chapter 8's dyn Trait vs. generics tradeoff is the same idea from another angle: monomorphized generics are zero-cost dispatch bought with compile-time code duplication, while dyn Trait's vtable indirection is a real, accepted, not eliminable-by-proof cost — you chose dynamic dispatch, so Stroustrup's principle says you pay for it, on purpose.

This curve is an illustrative sketch, not a captured benchmark from one specific machine — exactly the distinction §6 insisted on. It's calibrated to the general, widely repeated finding among Rust performance writers: a bounds check is a single, well-predicted compare-and-branch, and next to a cache miss (tens to hundreds of cycles) it's nearly free — which is why memory-bound code (streaming once through a large array, dominated by RAM latency) rarely shows a measurable difference. In a tight, compute-bound kernel that stays entirely in L1 cache — the check is now a real fraction of a very short loop body — the gap becomes visible, typically in the single-digit percent range in published community benchmarks on this exact topic. The only way to know which regime your loop is in is §7's pipeline, not this chart.

ARC 11 · REAL-WORLD CASE STUDIES

Three real bets on Rust, and one honest reason to pass

Discord (2020): eliminating garbage-collector pauses, not chasing raw speed

Discord's widely read 2020 engineering post, "Why Discord is switching from Go to Rust," is a useful case study precisely because its stated motivation was not "Rust is faster." Their Read States service — which tracks, for every user and every channel, which messages have been read — held a large, constantly growing in-memory cache in Go. Their own latency graphs showed a distinctive sawtooth: memory climbing steadily as the cache grew, then a sharp latency spike as Go's garbage collector ran a collection cycle, repeating on a roughly fixed period. The spikes tracked the GC cycle almost exactly. Rewriting the service's core cache in Rust — with no garbage collector and deterministic, ownership-based deallocation (chapters 4–6) — replaced the sawtooth with a flat latency graph, because there was no longer a periodic stop-the-world pause to cause one. The honest framing in their own post matters: the fix targeted tail-latency predictability, a property GC'd runtimes structurally struggle to guarantee under sustained memory pressure (§9's table), not average throughput — and most of Discord's stack at the time remained Elixir, Go, and Python. Rust was deployed surgically where GC-pause elimination had outsized, measurable value, not as a wholesale platform mandate.

Cloudflare (2022): Pingora — resource efficiency and memory safety at extreme scale

Cloudflare's public write-up on Pingora, the Rust HTTP proxy framework they built to replace large parts of their NGINX-plus-Lua edge fleet, is a different shape of bet: not eliminating a specific pause source, but reclaiming resource efficiency at a scale where small per-connection savings multiply across an enormous fleet. Their public account reports substantial fleet-wide CPU and memory savings from consolidating what had been NGINX processes plus custom Lua scripting into a single Rust binary with connection pooling designed for their actual traffic patterns rather than NGINX's more general-purpose model. The safety angle was real too: NGINX and the wider C ecosystem it's built on have a genuine historical CVE record in memory-unsafe parsing code, the exact bug class chapters 4–9's ownership model structurally rules out at compile time. Pingora is a case where "Rust is faster" and "Rust is safer" were both true and both mattered, but the decision was still made the way §7's pipeline recommends: against a specific, measured, fleet-wide resource bill, not a general reputation.

Microsoft (2019–present): a safety-first bet where performance had to merely tie, not win

Microsoft's public Rust adoption inside Windows is the cleanest illustration of a case where raw speed was not the deciding factor. In 2019, Microsoft's own security team publicly stated — a frequently cited figure since — that roughly 70% of the CVEs Microsoft assigns every year trace back to memory-safety bugs in C and C++ code. That single statistic, not a performance benchmark, is what drove Microsoft to begin rewriting specific, security-critical, untrusted-input-parsing Windows components (including parts of the GDI graphics subsystem and font/format-parsing code) in Rust, with further public statements through 2023 about expanding Rust's footprint in the kernel and core components. Microsoft's own engineers have been explicit in public talks that the bar for these rewrites was performance parity with the C/C++ they replaced, not a performance win — the entire business case was memory safety, and Rust's ownership model (chapters 4–9) delivered that without the tracked-generation garbage collector Windows' own compatibility and latency requirements would have made unacceptable.

The honest other side: when the bet isn't worth making

All three of the case studies above share a trait worth naming explicitly: each had a specific, quantified, already-identified pain point — a measured GC pause pattern, a measured fleet-wide resource bill, a measured CVE distribution — that a language choice was evaluated against. The generic, widely voiced counter-case in the Rust community itself is exactly the mirror image: a short-lived internal script, an early-stage product's CRUD API doing mostly I/O-bound orchestration, or a small team without existing Rust experience, where the borrow checker's learning curve (chapters 4–5) and release-mode compile times (§6) are a real, ongoing tax paid every single day against a runtime win nobody has measured and nobody is asking for. In that situation, a mature garbage-collected runtime's engineering velocity — faster iteration, a larger immediately-hireable pool, less time spent satisfying the borrow checker instead of shipping — is very often the objectively better trade, and "but Rust is faster" is exactly the kind of unverified performance claim §1 opened this chapter to stop.

Rustsrc/naive.rs
/// The "obvious" loop. Compiles to a tight, bounds-check-eliminated
/// scan because `i` is derived directly from `0..xs.len()` — see §8
/// for exactly why LLVM can prove that range is always in bounds.
pub fn sum_naive(xs: &[i64]) -> i64 {
    let mut total: i64 = 0;
    for i in 0..xs.len() {
        total += xs[i];
    }
    total
}
Rustsrc/iter_sum.rs
/// The idiomatic version. Should compile to the identical loop as
/// sum_naive — that equivalence is what §8's deck verified, not
/// assumed, by walking the actual MIR-to-assembly pipeline.
pub fn sum_iter(xs: &[i64]) -> i64 {
    xs.iter().copied().sum()
}
Rustsrc/chunked.rs
/// Hand-optimized: process 8 elements per loop iteration so the
/// loop-control overhead (increment, compare, branch) is paid once
/// per 8 adds instead of once per add. Entirely safe Rust — no
/// unsafe, no get_unchecked. chunks_exact's own invariant (every
/// chunk has EXACTLY 8 elements) is what lets the optimizer drop
/// the bounds checks on c[0]..c[7] once it can see that invariant
/// after inlining — verify it for your own build via §7's pipeline,
/// don't assume it (the bounds-check lab in §8 marks this pattern "0*").
pub fn sum_chunked(xs: &[i64]) -> i64 {
    let mut total = 0i64;
    let mut chunks = xs.chunks_exact(8);
    for c in &mut chunks {
        total += c[0]+c[1]+c[2]+c[3]+c[4]+c[5]+c[6]+c[7];
    }
    for &x in chunks.remainder() {
        total += x;   // fewer than 8 elements left over
    }
    total
}
Rustbenches/sum_bench.rs — a real criterion harness, three ways
use criterion::{criterion_group, criterion_main, black_box, Criterion};
use perf_lab::{sum_naive, sum_iter, sum_chunked};

fn make_data(n: usize) -> Vec<i64> {
    (0..n as i64).collect()
}

fn bench_sum(c: &mut Criterion) {
    let data = make_data(100_000);
    let mut group = c.benchmark_group("sum_100k");
    group.bench_function("naive",   |b| b.iter(|| sum_naive(black_box(&data))));
    group.bench_function("iter",    |b| b.iter(|| sum_iter(black_box(&data))));
    group.bench_function("chunked", |b| b.iter(|| sum_chunked(black_box(&data))));
    group.finish();
}

criterion_group!(benches, bench_sum);
criterion_main!(benches);

One more real crate worth naming here even without a fourth code listing: when a hot loop is embarrassingly parallel — independent work per element, no shared mutable state — the ecosystem's answer is rarely "hand-roll more unrolling," it's rayon. Its ParallelIterator trait gives you xs.par_iter().sum() as a drop-in replacement for xs.iter().sum() that fans the work across a work-stealing thread pool (chapter 15's territory), with the same iterator-adaptor ergonomics this chapter has been benchmarking. Reach for it before reaching for unsafe hand-tuning — it's a real dependency, not a language feature, so it costs a Cargo.toml line and a compile-time addition, not new unsafe surface area.

Before chapter 21: the ADVANCED tier closes, the TAURI arc opens

This is the last ADVANCED chapter. Chapters 1–20 treated performance and safety as properties of a single Rust process you could benchmark, disassemble, and reason about start to finish.
