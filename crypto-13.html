APPLIED CRYPTOGRAPHY · CHAPTER 13

TLS 1.3: The Handshake,
Byte by Byte

Every prior chapter in this course built one ingredient: AES and ChaCha20 (confidentiality), HMAC and AEAD (integrity), HKDF (key derivation), RSA and (EC)DHE (public-key exchange), X.509 and signatures (authentication). TLS is where all of it gets assembled into a single wire protocol that two strangers, over a network an attacker fully controls, use to agree on secret keys, authenticate a server, and start exchanging encrypted application data — in as few round trips as the security properties allow. This chapter derives TLS 1.3 (RFC 8446) from its predecessor's failures, then builds the real HKDF-based key schedule in JavaScript so the traffic secrets your browser derives on every HTTPS connection are values you compute yourself, not diagrams you take on faith.

ARC 01 · THE PROBLEM

Assemble everything, over a hostile network, in as few round trips as possible

Strip away the acronyms and TLS is answering one question: two parties who have never spoken before, communicating over a channel where every packet passes through equipment neither of them controls, need to agree on a set of secret keys that only the two of them know — and one of them needs to prove which organization it actually is. Everything from chapters 6 through 12 is an ingredient in that answer. None of them is the answer by itself.

Unpack "agree on keys and authenticate, over a hostile network" into the requirements a real protocol has to satisfy simultaneously, and you get a list that pulls in different directions exactly the way chapter 1's database concurrency requirements did:

  • Confidentiality and integrity for the data — chapter 7's AEAD ciphers (AES-GCM, ChaCha20-Poly1305), but only once both sides have a shared symmetric key, which doesn't exist yet when the connection starts.
  • A way to get that shared key without ever transmitting it — chapter 11's Diffie–Hellman / ECDH, run fresh for every connection so no long-lived secret governs every session's confidentiality.
  • Proof of identity for at least the server — chapter 12's X.509 certificates and signatures, so the client isn't just deriving a secret key with some party, it's deriving one with the party whose hostname it typed or whose domain it was redirected to.
  • Every derived key actually usable — chapter 8's HKDF, because a raw Diffie–Hellman shared secret is exactly the kind of structured, non-uniform value chapter 8 taught you not to feed directly into a cipher — and TLS needs not one key but several: separate keys for each direction, for the handshake phase and the application phase, computed from one shared secret without ever reusing key material across roles.
  • All of the above in the minimum number of round trips — every extra round trip is latency added to literally every new HTTPS connection on the internet, multiplied by billions of connections per day.

The tension in that last bullet is what makes TLS interesting as an engineering artifact rather than a simple composition exercise. You could satisfy every security property above with three or four round trips of careful, separately-negotiated steps. TLS 1.3's actual achievement — and the reason this chapter exists as a synthesis chapter rather than a survey — is fitting a full Diffie–Hellman exchange, a certificate chain verification, a transcript-bound signature, and four independent derived key schedules into one round trip, while removing an entire decade of the previous version's exploited weaknesses in the process.

WHY THIS MATTERS FOR THE REST OF THIS COURSE

This chapter is where chapters 6 (MACs/HMAC), 7 (AEAD), 8 (HKDF), 11 (Diffie–Hellman/ECDH), and 12 (signatures/certificates) stop being independent tools and become one running protocol. If any earlier chapter felt abstract, TLS is where you see exactly which real bytes on the wire each of those primitives produces, in what order, and why. Chapter 14 then shows what happens when an otherwise-correct protocol like this one sits on top of an implementation with a single missing bounds check (Heartbleed) or a hardware RNG with structurally weak output (ROCA, the Debian OpenSSL bug) — a reminder that this chapter's guarantees are only as strong as the code underneath them.

1995–2021: two decades of patching one protocol until it needed a redesign

ARC 03 · NAIVE SOLUTION

Attempt #1: reuse the server's key pair to transport the secret

Put yourself in the position of an early-1990s protocol designer who already has the server authenticated via an RSA certificate (chapter 12) and needs to get a symmetric key to both sides. The obviously efficient idea: the server already has an RSA key pair for signing — its certificate's key pair — so let the client pick the symmetric key material itself, encrypt it under the server's existing RSA public key, and send it over. One key pair, two jobs: authentication and key transport. This is exactly TLS 1.0–1.2's TLS_RSA_WITH_* cipher suite family, and it is worth writing out exactly as it shipped for over a decade:

pseudocodenaive_handshake.c — TLS 1.2's static RSA key exchange
bytes naive_tls_handshake_client(hostname host)
{
    send(ClientHello(client_random, cipher_suites = [TLS_RSA_WITH_AES_128_CBC_SHA, ...]));

    /* Server replies with its certificate — the SAME RSA key pair it uses
     * for every connection, for as long as the certificate is valid
     * (commonly 1-2 years before TLS 1.3; historically much longer). */
    (server_random, cert, ServerHelloDone) = recv();
    pubkey = extractRSAPublicKey(cert);

    /* THE key-transport step: the CLIENT invents the entire secret and
     * encrypts it to the server's long-lived public key. Nothing about
     * this value is ephemeral — it depends on nothing except pubkey. */
    pre_master_secret = randomBytes(48);
    encrypted_pms = RSA_PKCS1_Encrypt(pubkey, pre_master_secret);   /* ch. 9 */
    send(ClientKeyExchange(encrypted_pms));

    master_secret = PRF(pre_master_secret, "master secret", client_random || server_random);
    send(ChangeCipherSpec, Finished(master_secret));
    Finished_server = recv();          /* 2 round trips total before application data */
    return master_secret;
}

Nothing here looks wrong at first glance. RSA encryption is the primitive chapter 9 taught you to trust; the server's certificate is the same one already used for authentication, so no extra PKI machinery is needed; and the master secret derivation runs through a proper PRF rather than being used raw. This is precisely the reasoning that shipped as the default, most widely deployed TLS 1.0–1.2 cipher suite family for roughly two decades — RFC 5246 §7.4.7.1 specifies it in exactly this shape.

ARC 04 · WHY IT FAILS

One static key pair doing two jobs means one compromise breaks every session it ever touched

Four separate, independently-exploited weaknesses live inside TLS 1.2's design, and it matters that they are independent — fixing any one of them individually (as the industry tried, repeatedly, for a decade) left the others standing. Each is worth quantifying, because the numbers are what eventually made "patch TLS 1.2 again" lose the argument to "replace it."

1. No forward secrecy — the retroactive-decryption problem

Look again at naive_tls_handshake_client: pre_master_secret is encrypted under the server's long-lived RSA key. That key is the same for every connection the server ever serves until the certificate is rotated — commonly one to two years, sometimes longer for internal or legacy systems. Now consider an adversary who is not trying to break the live connection at all, but is simply recording encrypted traffic and storing it. The moment that RSA private key is ever compromised — by theft, by a legal order, by a future cryptanalytic advance, or simply by the server operator selling old hardware without wiping it — every session ever recorded under that key becomes decryptable, instantly and retroactively, no matter how many years have passed. This exact strategy, often summarized as "harvest now, decrypt later," is precisely the capability attributed to signals-intelligence bulk collection programs revealed in 2013 (the Snowden disclosures, including the NSA's Bullrun program), and it is the single fact that reframed forward secrecy from "a nice property" to "a requirement" across the entire industry within about two years.

Contrast the ephemeral (EC)DHE case (chapter 11): each connection generates a fresh, random DH private exponent, uses it once, and discards it the moment the handshake finishes. Compromising the server's long-term signing key afterward lets an attacker impersonate the server going forward — a real and serious problem — but it does not hand over a single byte of any past session's plaintext, because no past session's confidentiality ever depended on that signing key; it depended only on an ephemeral value that no longer exists anywhere. That is the entire, quantifiable difference: static RSA key exchange has an exposure window equal to the key's entire operational lifetime; ephemeral key exchange has an exposure window of zero, for any session, once that session's handshake completes.

2. CBC mode's decade of incremental breaks

TLS 1.0–1.2's non-AEAD cipher suites use AES/3DES in CBC mode (chapter 5) combined via MAC-then-Encrypt (chapter 7 dissected exactly why that composition is fragile). Three real, independently disclosed attacks exploited different facets of the same underlying decision:

  • BEAST (2011, CVE-2011-3389, Duong & Rizzo). TLS 1.0's CBC mode used the previous record's last ciphertext block as the next record's IV — a predictable, attacker-visible value. Combined with a way to make a victim's browser send adaptively chosen plaintext (malicious JavaScript issuing cross-origin requests), an attacker could verify byte-by-byte guesses of secret data (session cookies) via a chosen-boundary trick, recovering a real HTTPS session cookie in a practical demonstration in under 10 minutes.
  • Lucky 13 (2013, AlFardan & Paterson). Even after implementations moved to explicit, unpredictable IVs (TLS 1.1+), the MAC-then-Encrypt ordering (chapter 7 §4) still forced the receiver to remove CBC padding before checking the MAC — and the amount of time that removal takes depends measurably (at the microsecond level) on how much padding was present. Averaging timing measurements over many requests per byte (published estimates ranged from roughly 2¹⁹ to 2²³ requests depending on network conditions and implementation) let an attacker recover plaintext one byte at a time with no chosen-plaintext requirement at all.
  • POODLE (2014, CVE-2014-3566). SSL 3.0's CBC padding is barely specified — the receiver only checks the length byte of the padding, not the padding bytes' contents — reopening a classical padding-oracle attack (chapter 10) with roughly 256 requests per byte in the worst case. The practical danger wasn't that anyone still preferred SSL 3.0; it's that many clients and servers supported a protocol downgrade fallback to SSL 3.0 for compatibility with buggy middleboxes, so an active attacker could simply force that fallback and then run the padding oracle regardless of what stronger versions both endpoints actually supported.

Three different research teams, three different years, one shared root cause: CBC mode plus MAC-then-Encrypt keeps producing exploitable timing and padding side channels no matter how carefully any single implementation is patched, because the vulnerability lives in the composition, not in any one codebase (this is exactly chapter 7 §4's theorem, playing out against a real, decade-long stream of CVEs).

3. Renegotiation: an unauthenticated reset point in the middle of a session

TLS allowed either side to trigger a renegotiation — a fresh handshake, layered on top of an existing connection, to rotate keys or step up to client-certificate authentication mid-session. The 2009 flaw (CVE-2009-3555, publicly reported by Marsh Ray and Steve Dispensa) was that the renegotiated handshake had no cryptographic binding to the connection it was renegotiating. An active man-in-the-middle could open its own connection to the server, inject attacker-chosen application data, and then splice a victim's genuine renegotiation onto that same connection — the server had no way to tell "this renegotiated session continues the attacker's earlier request" from "this is a fresh, unrelated handshake." Within weeks of disclosure, a working proof-of-concept demonstrated injecting attacker-chosen content into an authenticated HTTPS session against a real production service. The fix — RFC 5746's renegotiation_info extension, cryptographically binding each renegotiation to the Finished value of the handshake before it — closed the specific bug, but renegotiation as a concept (an unauthenticated reset point mid-stream) remained an architectural attack surface that kept resurfacing in different forms for years afterward.

4. Cipher-suite sprawl turns "supports a weak option" into "is broken"

By the TLS 1.2 era, the IANA TLS Cipher Suite registry listed several hundred combinations of {key exchange: RSA / DHE / ECDHE / PSK / SRP} × {authentication: RSA / DSA / ECDSA / anonymous} × {bulk cipher: RC4 / 3DES / AES-CBC / AES-GCM / Camellia / ...} × {PRF hash}. Two real attacks show precisely why registry size itself is a vulnerability, independent of what any well-configured client or server would voluntarily choose:

  • FREAK (2015, CVE-2015-0204). 1990s-era US export-control law once required American software to ship deliberately weakened "export-grade" RSA cipher suites (512-bit RSA) for use outside the US. That law was repealed, but the cipher-suite code points — and buggy client code that would still accept an export-grade key even when it hadn't asked for one — survived for two more decades. An active man-in-the-middle could force a connection down to RSA_EXPORT, factor the resulting 512-bit modulus (a matter of hours on rented cloud compute by 2015), forge the handshake, and read or modify traffic. Measurement at disclosure found roughly a third of browser-trusted HTTPS sites still willing to negotiate the export suite.
  • Logjam (2015, Adrian et al.). The same idea applied to Diffie–Hellman: many servers still offered 512-bit export-grade DHE groups, and because a huge fraction of servers in practice reused a small number of standard 512-bit primes, an attacker could perform one expensive precomputation per prime and then break any individual connection using that prime in a short, cheap final step — turning what looked like "512-bit DH, factor it every time" into "512-bit DH, mostly precomputed already."

Both attacks work regardless of what a careful client and a careful server would agree to on their own — the mere continued existence of the weak option in the negotiable set is what an active attacker exploits.

THE PATTERN THAT SETTLED THE ARGUMENT FOR A REDESIGN

Four independent root causes — no forward secrecy, a fragile cipher-mode composition, an unauthenticated mid-session reset point, and a negotiable surface that never shrinks — produced a wave of distinct, named, real-world attacks (BEAST, CRIME, Lucky 13, POODLE, FREAK, Logjam) across 2011–2015 alone. Patching each one individually kept the negotiable surface just as large for the next attack. TLS 1.3's actual design principle, motivated directly by this pattern, is to stop patching and instead remove entire vulnerability classes structurally — delete CBC mode outright, delete renegotiation outright, delete static RSA key exchange outright, and shrink the cipher-suite space from hundreds of combinations to five. §5 derives that redesign step by step.

ARC 05 · EPHEMERAL KEY EXCHANGE & AEAD-ONLY

Four structural removals, derived one at a time

Rather than patch §4's four weaknesses individually, step through the redesign as four sequential removals — each one closing an entire vulnerability class rather than one CVE, and each one a real, dated evolution the protocol actually went through:

From TLS 1.2's RSA key exchange to TLS 1.3's 1-RTT handshakeSTEP-BY-STEP

Generalize the pattern across all four steps: every single one takes a place where TLS 1.2 offered a choice — RSA or DHE key exchange, CBC or AEAD, renegotiate or don't, pick from hundreds of suites — and replaces the choice with a single mandatory answer. That is not a coincidence; it is the design philosophy RFC 8446's authors state explicitly: remove negotiable surface area first, then optimize what's left.

THE INVARIANT TLS 1.3 ENFORCES STRUCTURALLY, NOT BY CONVENTION

Every TLS 1.3 handshake is forward-secret and AEAD-protected — there is no configuration that turns either property off. TLS 1.2 could, in principle, be configured this way too (ECDHE key exchange + a GCM cipher suite + no renegotiation), but it was a choice an operator had to make correctly and an attacker could sometimes force away from (§4's downgrade attacks). TLS 1.3 removes the choice: static RSA key exchange, every CBC cipher suite, compression, and renegotiation are simply absent from the protocol. You cannot misconfigure your way back into 2011.

ARC 06 · WHY THAT STILL COSTS

One round trip is still a round trip — and skipping it reopens a different problem

Collapsing the handshake to 1-RTT is a genuine achievement, but "1 round trip" is not "0 round trips," and for some workloads that remaining round trip is exactly where the next round of engineering pressure lands. Three costs are worth being precise about, because each one motivates a real piece of the final design in §7–§8:

  • A full network round trip, every time, before the first byte of application data. On a same-datacenter link (~1 ms) this is noise. On a realistic cross-continental path (~120–150 ms) or a satellite/geostationary link (~600 ms one-way, well over a second round trip), one mandatory RTT before any response is a measurable, user-visible cost — and it compounds with the TCP handshake TLS normally rides on top of, so a cold HTTPS connection over TCP is at minimum two round trips before the first response byte, before the server has done any actual work.
  • The 1-RTT handshake's speed depends on a guess. The client sends key_share entries for the groups it thinks the server will accept, before the server has said anything. If the server's preferred group isn't among the client's guesses, the server must respond with a HelloRetryRequest — a special ServerHello asking the client to try again with a different group — turning that connection's handshake back into 2 round trips. This is not a design flaw so much as an honest admission: shaving the round trip to 1 requires speculating, and speculation is sometimes wrong.
  • Removing negotiable surface area doesn't remove the incentive to skip the round trip entirely. For returning clients — a browser reconnecting to a site it visited minutes ago — the industry wants to send application data in the very first flight, using a previously-established secret (a resumption PSK) instead of running the Diffie–Hellman exchange fresh. That's 0-RTT, and it reopens exactly the problem §5 had just closed: without a round trip in which the server can demand a fresh, unpredictable value from the client before processing anything, the server has no protocol-level way to distinguish a legitimate request from a captured copy of that exact same request, replayed verbatim by a network attacker. This is not an implementation bug to be patched later — it is the direct, unavoidable consequence of eliminating the round trip that would otherwise prove freshness, and RFC 8446 §8 is explicit that 0-RTT data carries no replay protection at the protocol layer at all. §8 and §15 make this concrete with the actual key-schedule branch that makes 0-RTT possible, and exactly what an application must guarantee (idempotency) before it's safe to use.

One more cost, easy to overlook: collapsing to 1-RTT only helps if an active attacker can't quietly force a downgrade back to the round-trip count and cipher menu of TLS 1.2 — exactly §4's FREAK/Logjam playbook, aimed now at the version number itself instead of the cipher suite. §7–§8 show the specific mechanism (a sentinel value baked into ServerHello.random) that makes such a downgrade detectable by a client that actually supports 1.3, even though the raw bytes of that downgraded handshake look, to anyone else, identical to a real TLS 1.2 negotiation.

THE ENCRYPTION BOUNDARY IS THE WHOLE POINT

In TLS 1.2, the certificate, the signature, and every extension traveled in the clear — anyone on the network path could see which certificate a server presented and which extensions it supported, useful metadata for fingerprinting and censorship. In TLS 1.3, the server's Certificate and CertificateVerify are encrypted the instant ServerHello's key material is available — before the client has even verified the certificate is valid. §8 shows exactly which key makes that possible this early: the handshake traffic secret, derived from nothing but the (EC)DHE shared secret and the two Hello messages, with no dependency on anything that comes later in the flow.

ARC 08 · INTERNAL IMPLEMENTATION

Wire bytes, the real key schedule, and the record layer

Three pieces, at the level of detail you'd need to write an interoperable implementation: (a) the exact bytes of a ClientHello and its key_share extension, (b) the HKDF-based key schedule that turns one (EC)DHE shared secret into four independent traffic secrets — implemented for real, not sketched — and (c) the per-record AEAD framing that protects every byte after the handshake.

(a) ClientHello and key_share, byte by byte

Step through the message a browser actually sends first. Two backward-compatibility quirks are worth noticing as you go: legacy_version is frozen at 0x0303 (TLS 1.2's value) so that middleboxes which choke on unrecognized version numbers don't drop the connection — the real version travels inside the supported_versions extension instead — and the cipher-suite list has shrunk from TLS 1.2's hundreds of combinations to exactly five, because TLS 1.3 separates "which AEAD cipher" from "which key-exchange group" and "which signature algorithm," negotiating each independently via its own extension instead of one combinatorial cipher-suite code point.

THE DOWNGRADE SENTINEL, HIDING IN PLAIN SIGHT

§6 promised a mechanism to detect a forced version downgrade. It lives in ServerHello.random: if a server capable of TLS 1.3 ever ends up negotiating TLS 1.2 or below (because it's talking to an older client, or an active attacker stripped the supported_versions extension), RFC 8446 §4.1.3 requires it to overwrite the last 8 bytes of its 32-byte random field with a fixed sentinel — 44 4F 57 4E 47 52 44 01 ("DOWNGRD\x01") for a downgrade to 1.2, or the same prefix with \x00 for 1.1 or below. A genuinely TLS-1.3-capable client checks for this sentinel on every handshake; if it appears without a legitimate reason, the client aborts. Cost: 8 bytes of an already-random field. Benefit: an active downgrade attacker can strip the extension, but cannot forge a value indistinguishable from randomness and matching the sentinel by chance (2⁻⁶⁴ odds) — turning an invisible downgrade into a detectable one.

(b) The key schedule: one HKDF chain, four traffic secrets

This is the chapter's mathematical core, and it is the one piece of TLS 1.3 this chapter implements for real. The key schedule takes exactly two secret inputs — a pre-shared key (all-zero if there isn't one) and the (EC)DHE shared secret from chapter 11 — and a record of every handshake message exchanged so far (the transcript), and produces every key TLS 1.3 ever uses, through a strict linear chain of HKDF-Extract and HKDF-Expand-Label calls (chapter 8's HKDF, RFC 5869, plus RFC 8446's own labeling convention on top of it):

Here is the exact JavaScript this chapter runs — the same function powering the slider below and the full simulator in §15:

javascriptHKDF-Expand-Label, exactly as RFC 8446 §7.1 specifies it
// HkdfLabel struct (RFC 8446 §7.1):
//   uint16 length;               -- the requested output length
//   opaque label<7..255> = "tls13 " + Label;
//   opaque context<0..255> = Context;
// HKDF-Expand-Label(Secret, Label, Context, Length)
//   = HKDF-Expand(Secret, HkdfLabel, Length)
function hkdfExpandLabel(secret, label, context, length) {
  const fullLabel = utf8("tls13 " + label);
  const head = new Uint8Array(2 + 1 + fullLabel.length + 1 + context.length);
  const dv = new DataView(head.buffer);
  dv.setUint16(0, length, false);            // length, big-endian
  head[2] = fullLabel.length;  head.set(fullLabel, 3);
  head[3+fullLabel.length] = context.length;
  head.set(context, 3+fullLabel.length+1);
  return hkdfExpand(secret, head, length);     // chapter 8's HKDF-Expand, RFC 5869
}
function deriveSecret(secret, label, transcriptBytes) {
  return hkdfExpandLabel(secret, label, sha256(transcriptBytes), 32);
}

WHY "DERIVE-SECRET(., \"DERIVED\", \"\")" EXISTS BETWEEN STAGES

Look closely at the diagram: handshake_secret isn't computed directly from early_secret — there's an extra Derive-Secret(., "derived", "") hop first. This is domain separation, and it earns its keep: without it, early_secret (which, on a resumed connection, is keyed by a PSK an attacker might partially influence via ticket-related mechanisms) would feed directly into the next HKDF-Extract call as its salt, alongside attacker-influenced protocol state. Passing it through one more labeled expansion first means handshake_secret depends on early_secret only through a fixed, independent transformation — breaking any structural relationship an attacker might otherwise try to exploit between the PSK-derived branch and the DHE-derived branch. It is the same "add a finalization the attacker can't replay" instinct chapter 6 taught you for HMAC, reapplied at the level of an entire key schedule.

(c) The record layer: one AEAD call per record, nonce derived from a sequence number

Every traffic secret above is expanded once more — via HKDF-Expand-Label(secret, "key", "", key_len) and HKDF-Expand-Label(secret, "iv", "", 12) — into an actual AEAD key and a 12-byte static IV. From there, TLS 1.3 protects each record with a structure deliberately designed to hide even the record's real type from a passive observer:

The outer TLSCiphertext header — type, legacy_record_version, length — travels in the clear, and type is always 0x17 (application_data), even while carrying encrypted Certificate or Finished messages during the handshake. The real content type is the last unpadded byte inside the AEAD-encrypted payload — so a network observer sees a uniform stream of "application data" records and cannot tell a handshake message from a real HTTP response by record type alone.

0 bytes

TLS 1.3 lets a sender add arbitrary zero-padding inside the encrypted inner plaintext before the AEAD seals it — purely to obscure the true length of short messages from traffic analysis. It costs bandwidth and buys nothing cryptographically; it is a mitigation for a metadata leak (message length), not a confidentiality property of the cipher itself.

ARC 09 · TRADEOFFS

Five handshake shapes, compared honestly

"TLS 1.3 is strictly better" is close to true but hides one real tradeoff — 0-RTT trades replay resistance for latency, and that trade is only safe for some requests. Read the table as five real, still-relevant configurations rather than a straight upgrade ladder:

HANDSHAKE SHAPEROUND TRIPSFORWARD SECRECYREPLAY RESISTANCEWHAT IT COSTS / RISKS
TLS 1.2, static RSA key exchange2-RTT none yes (no 0-RTT concept) one server-key compromise decrypts every past recorded session (§4)
TLS 1.2, (EC)DHE + CBC cipher suite2-RTT yes yes CBC + MAC-then-Encrypt still exposed to Lucky 13-class timing attacks (§4)
TLS 1.2, (EC)DHE + AEAD (RFC 5288/5289, best case)2-RTT yes yes still exposed to renegotiation-class and downgrade attacks; per-record nonce construction left to the implementation (§8c)
TLS 1.3, full 1-RTT (EC)DHE handshake1-RTT yes, mandatory yes still one full round trip before application data; HelloRetryRequest costs a second RTT if the client's key_share guess misses (§6)
TLS 1.3, 0-RTT PSK resumption0-RTT for early data forward-secret for the resumed connection's later traffic if psk_dhe_ke is used; the early data itself is not independently forward-secret from the PSK none for early data — RFC 8446 §8 states this explicitly early data MUST be limited to idempotent operations; server must bound or reject replays itself (§6, §15)

Read the last row as the honest cost of the fastest option: 0-RTT is not "TLS 1.3, but faster" — it is a distinct security posture that a server operator opts into, request type by request type, and it only makes sense where "this exact request might be processed twice" is an acceptable outcome.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Latency you can predict, and what a broken ephemeral key actually costs an attacker

Two independent numbers matter here: how much wall-clock time each handshake shape actually costs before application data flows, and — the security question — exactly how much an attacker gains from breaking any single piece of key material.

MODEL, NOT MEASUREMENT

The lines are round-trip arithmetic — each "RTT" costs one full there-and-back network delay, TCP's own handshake is one more RTT that TLS rides on top of, and 0-RTT is defined as sending application data in the very first flight — not a captured production trace. Real deployments add TCP congestion-window slow-start, OS scheduling jitter, and (for 0-RTT) server-side anti-replay bookkeeping on top of this; the shape — TLS 1.3 removing one full RTT relative to TLS 1.2, and 0-RTT removing the TLS RTT entirely for resumed connections — is the lesson, and it is exactly why CDNs measured double-digit percentage improvements in time-to-first-byte after enabling 1.3 broadly.

What breaking one ephemeral key actually buys an attacker

This is the quantitative payoff of forward secrecy, made concrete. Suppose an attacker fully breaks the discrete-log instance for one specific session's ephemeral (EC)DHE key — the same computational hardness chapter 11 quantified for X25519/P-256. What do they get?

  • Under TLS 1.3 (or TLS 1.2 with ECDHE): exactly that one session's traffic. The broken key was generated fresh, used once, and discarded; it has no mathematical relationship to any other session's ephemeral key, past or future, even between the same two endpoints seconds apart.
  • Under TLS 1.2's static RSA key exchange: breaking the single long-term RSA private key — not even a per-session computation, just one factoring effort against one modulus — decrypts every session ever protected by that key, forward and backward in time, for as long as the certificate has been in service.

That asymmetry — attacker effort scales with one session in one design and with the server's entire operational history in the other — is forward secrecy's entire quantitative content, and it is why this course treats it as a hard requirement rather than a nice-to-have (chapter 11 §10 covers the underlying hardness numbers in full).

ARC 11 · REAL-WORLD INCIDENTS

The failures that built the case for a redesign

CVE-2009-3555 — the renegotiation injection

Covered in mechanism in §4(3); the operational aftermath is worth adding here. Because the flaw affected the protocol, not any one implementation, the fix (RFC 5746) had to be deployed across essentially every TLS stack on the internet simultaneously, and for a transition period servers had to support both the old, vulnerable renegotiation behavior and the new, bound behavior for interoperability — meaning the vulnerable path stayed reachable in practice for years after a fix existed. TLS 1.3's response was structural rather than procedural: it removes renegotiation from the protocol entirely, replacing key updates with a KeyUpdate message that is cryptographically derived from the existing traffic secret (via one more HKDF-Expand-Label call, labeled "traffic upd") rather than being a fresh, independently-authenticated handshake — there is no "new session" for an attacker to splice a victim's request onto.

2015 — FREAK and Logjam, the same downgrade shape twice in one year

Detailed in §4(4). The shared lesson both incidents drove home industry-wide: a cryptographic weakness doesn't need to be in a suite anyone chooses — it needs to be in a suite anyone's peer is willing to accept, because an active attacker controls the negotiation, not the honest endpoints. This is precisely why TLS 1.3's cipher-suite list was cut to five AEAD-only entries rather than deprecating weak suites one at a time as had been tried (repeatedly, and unsuccessfully at internet scale) throughout the TLS 1.2 era.

2016 — DROWN (CVE-2016-0800): a legacy protocol on an unrelated service breaks TLS

DROWN (Aviram et al.) is the cipher-suite-sprawl lesson taken cross-protocol. Many servers in 2016 still supported SSLv2 — obsolete since the late 1990s — on some service sharing the same RSA key and certificate as a modern TLS-only web server, for example an old mail server on the same host. SSLv2's handshake is vulnerable to a Bleichenbacher-style padding oracle (chapter 10) against RSA key exchange. An attacker could send crafted SSLv2 handshakes to the unrelated mail service, use the resulting oracle to recover the shared RSA private key's decryption capability, and use that to break TLS sessions to the main website — a complete break of a modern, correctly-configured web server caused entirely by an old service nobody thought to disable, three protocol versions removed from the one actually in use. The lesson generalizes past TLS: a cryptographic key's security is bounded by every protocol that key is ever exposed through, not just the one you're auditing.

WHAT THIS CHAPTER DELIBERATELY DOESN'T COVER — SEE CHAPTER 14

None of the incidents above are implementation bugs — they are protocol-level design weaknesses, which is why this chapter's fix was a protocol redesign. Chapter 14 covers the other category entirely: real, catastrophic vulnerabilities in implementations of otherwise-sound cryptography — Heartbleed (CVE-2014-0160), a single missing bounds check in OpenSSL's heartbeat extension that leaked server memory including private keys; ROCA (CVE-2017-15361), an RSA key-generation weakness in specific hardware that made keys factorable despite every protocol-level check in this chapter passing; and the 2008 Debian OpenSSL PRNG bug (CVE-2008-0166), which silently collapsed key-generation entropy to a guessable range. A perfectly designed protocol running on top of any of those bugs is not protected by anything you've learned in this chapter — §16 asks you to predict exactly why.

First, the shape of the secret-generation primitive every stage of §8(b)'s chain calls through — notice it is a thin, generic wrapper, not four different functions for four different stages:

Ctls13_enc.c — tls13_generate_secret(), the shape behind every HKDF-Extract in §8(b)
int tls13_generate_secret(SSL *s, const EVP_MD *md,
                          const unsigned char *prevsecret,
                          const unsigned char *insecret,
                          size_t insecretlen,
                          unsigned char *outsecret)
{
    size_t mdlen = EVP_MD_size(md);           /* 32 for SHA-256, 48 for SHA-384 */
    unsigned char preextractsec[EVP_MAX_MD_SIZE];

    if (prevsecret != NULL) {
        /* the "Derive-Secret(., "derived", "")" hop from §8(b) — ALWAYS run
         * before the next Extract, whether the previous stage was PSK-keyed
         * or DHE-keyed. One code path serves both a full handshake and a
         * resumption handshake; only what feeds insecret differs.        */
        static const char DERIVED_LABEL[] = "derived";
        unsigned char hash[EVP_MAX_MD_SIZE];
        EVP_Digest(NULL, 0, hash, NULL, md, NULL);      /* Transcript-Hash("") */
        tls13_hkdf_expand(s, md, prevsecret, DERIVED_LABEL, sizeof(DERIVED_LABEL)-1,
                          hash, mdlen, preextractsec, mdlen);
        prevsecret = preextractsec;
    }
    if (insecret == NULL) {
        insecret = default_zeros_of_length(mdlen);      /* the bare "0" inputs in §8(b)'s diagram */
        insecretlen = mdlen;
    }
    return EVP_PKEY_derive_set_peer(...)  /* HKDF-Extract(salt=prevsecret, ikm=insecret) via EVP_PKEY_HKDF, mode EXTRACT_ONLY */
        && EVP_PKEY_derive(..., outsecret, &mdlen);
}

Second, the point where a derived traffic secret stops being an abstract 32-byte value and becomes an installed AEAD key + IV pair — this is the function that runs once per key-schedule milestone in §8(b)'s diagram (after ServerHello, and again after the server's Finished):

Ctls13_enc.c — tls13_change_cipher_state(), simplified
int tls13_change_cipher_state(SSL *s, int which)
{
    unsigned char key[EVP_MAX_KEY_LENGTH], iv[EVP_MAX_IV_LENGTH];
    const unsigned char *secret = secret_for_stage(s, which);  /* one of §8(b)'s 4+ traffic secrets */

    tls13_hkdf_expand_label(s, secret, "key", NULL, 0, key, keylen);
    tls13_hkdf_expand_label(s, secret, "iv",  NULL, 0, iv,  12);

    /* From here the record layer (tls13_meth.c) owns these: every record's
     * nonce is `iv XOR left_pad(seq_num)`, and seq_num resets to 0 for
     * EACH newly installed secret — never shared across key-schedule
     * stages, exactly the "separate keys per direction and per epoch"
     * argument chapter 7 §16 previewed.                                  */
    return EVP_CipherInit_ex(cipher_ctx_for(which), NULL, NULL, key, iv, ...);
}
WHY IT WAS BUILT THIS WAY — THREE DECISIONS TO STEAL

1. One generic secret-derivation function, called four-plus times. Nothing about tls13_generate_secret() knows whether it's computing early_secret or master_secret — the caller supplies which bytes go in. This is exactly why a resumption (PSK-based) handshake and a full handshake share the same code path in a real implementation: they differ only in what feeds the first Extract call, not in any of the machinery downstream. 2. The "tls13 " label prefix is domain separation against the whole rest of the world, not just against other TLS stages — any other protocol that happens to derive keys via HKDF from a similar-shaped secret cannot produce output that collides with TLS 1.3's, because the label string itself is baked into the HKDF-Expand input. 3. Key installation is a separate step from key derivation, deliberately — the traffic secret is retained (and reused for a later KeyUpdate derivation) even after the AEAD key and IV derived from it are installed and the record layer starts using them, which is exactly what makes TLS 1.3's key updates a single HKDF-Expand-Label call rather than a fresh handshake.
