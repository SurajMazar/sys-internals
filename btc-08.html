Validation: Every Rule
a Block Must Satisfy

Chapters 1–7 built the ingredients — keys, the raw transaction format, Script, sighash, the UTXO set, and the 80-byte header. None of it means anything until it is checked. This chapter is the one that actually defines what "Bitcoin" is: not a brand, not a price, but an exact, ordered, deterministic list of predicates that every fully-validating node on Earth evaluates identically, with zero communication between them, forever. Get one predicate wrong in your own implementation and you are not running Bitcoin — you are running something that forks off it the first time a block exercises the difference.

ARC 01 · THE PROBLEM

A block is just bytes. What makes it true?

Anyone can construct 80 bytes shaped like a block header and a list of records shaped like transactions. Nothing about the bytes distinguishes a legitimate block from a forgery that mints a trillion coins, double-spends someone's payment, or claims another miner's reward. The entire security model of a system with no central authority rests on one property: every node, acting alone, applying the same deterministic function to the same bytes, arrives at the same accept-or-reject answer — without asking anyone, without trusting anyone, and without exception across fifteen years of adversarial input.

Unpack that sentence and four requirements fall out, each harder than it looks:

  • Agreement without trust. A node cannot ask a peer "is this block valid?" and believe the answer — a lying peer is indistinguishable from an honest one over the wire. Every node must derive the answer itself, from the block's bytes and its own chain state, or the entire trust model collapses to "trust whoever you happen to be connected to."
  • Agreement without communication. Two nodes that have never spoken to each other, running different versions of different implementations on different continents, must independently compute the identical verdict on the identical block. That is a far stronger requirement than "the logic is correct" — it demands that the logic be specified precisely enough to have no ambiguity, because any ambiguity is a standing invitation for two honest nodes to disagree, which is a fork.
  • Totality. The function must have a defined answer for every possible input, including bytes no one has ever constructed before, adversarially chosen specifically to find the one edge case the implementers forgot. "Undefined behavior for malformed input" is not an option — the function must reject cleanly, every time.
  • It must stay cheap enough to run forever. Every full node re-executes this exact function on every block, including all ~900,000+ blocks mined since 2009 during initial sync. A validation rule that is correct but too expensive is a real cost with a real name — §6 and §10 quantify it.
WHY THIS CHAPTER IS THE CENTER OF THE COURSE

Every other chapter describes a format — how a key, a transaction, a script, or a block is laid out in bytes. This chapter describes the law that decides which of those bytes are allowed to exist inside the chain that everyone agrees is Bitcoin. If you memorize nothing else from this course, memorize this: a blockchain is not a data structure that happens to be hard to alter — it is a data structure whose validity is continuously re-derived from a fixed rule set that every participant enforces independently. Change the rule set and you have not upgraded Bitcoin; you have defined a different currency that happens to share its history up to the point of divergence. That is precisely what a fork is, and this chapter is where forks are born.

DEEP CONTEXT · SOFT FORKS ARE HOW THE RULEBOOK GROWS

Notice the shape of nearly every entry below: a rule gets stricter, never looser. That is not an accident — it is the definition of a soft fork: shrink the set of valid blocks, and old nodes — who only ever check "is this still within the old, larger set?" — keep agreeing with new nodes without upgrading. A hard fork (loosening a rule, or changing the format) requires every node to upgrade or be forcibly split off, which is why every rule in this chapter's checklist was added as a soft fork wherever humanly possible.

ARC 03 · NAIVE SOLUTION

Attempt #1: "if the hash meets the target, accept it"

Reason from first principles, the way an engineer meeting this problem cold would. Proof of work (chapter 9 covers its mechanics) is expensive to produce and free to check — so the obvious first cut at isValidBlock() is: recompute the header hash, compare it against the difficulty target, done.

pseudocodenaive_validate.py — the strawman
def is_valid_block(block):
    header_hash = sha256d(block.header)          # 80 bytes → 32-byte digest
    target = bits_to_target(block.header.bits)  # compact → 256-bit number
    return header_hash <= target                # ...and that's the whole function.

This is not a strawman built to be laughed at — it is exactly right about one thing, and that thing matters: proof of work is real, expensive, and worth checking first, because it's the cheapest check that filters out the overwhelming majority of garbage (nobody without real hash power can produce a passing header at all). But it is silent about everything else a block contains. Watch what it lets through.

ARC 04 · WHY IT FAILS

"Meets the target" says nothing about money, ownership, or history

Proof of work answers exactly one question: did the miner spend real energy on this specific set of bytes? It says nothing about whether those bytes describe a legal transfer of value. A miner with enough hash power to find a valid header can put any transaction list underneath it — and every one of the following has actually happened on real Bitcoin mainnet, which is precisely why each is now a hard consensus rule rather than a hopeful convention:

  • Mint coins from nothing. A coinbase output — or any output, if per-transaction value checks are skipped — can simply claim a value with no backing input. Nothing about "the hash is below target" checks that outputs are backed by inputs of equal or greater value.
  • Overflow the accounting. Values are stored as signed 64-bit integers. Summing several outputs whose individual values are each below the maximum can overflow the accumulator and wrap around — producing a total that looks small (or negative) even though the individual outputs are each enormous. §11 walks through exactly this happening on August 15, 2010, at block height 74,638.
  • Double-spend. Nothing stops an input from referencing an output that was already spent by an earlier transaction, unless something explicitly checks the current UTXO set.
  • Duplicate an existing, unspent transaction id. Two different blocks can — and in August 2010, did — produce coinbase transactions with byte-for-byte identical serializations, hence identical txids, silently overwriting an existing UTXO set entry. §11 covers the two real incidents that made this a named rule.
  • Break every script ever written. Signatures can be encoded in more than one byte-valid way for the same mathematical signature (an ECDSA malleability surface); if the interpreter accepts all of them, different implementations built on different cryptography libraries can legitimately disagree about whether a signature checks out — a consensus split waiting to happen. §6 and §11 cover exactly this failure mode.
THE NUMBERS · WHAT ONE OVERFLOWED SUM ACTUALLY PRODUCED

Bitcoin's supply cap is 21,000,000 BTC = 2,100,000,000,000,000 satoshis — the constant MAX_MONEY in every implementation. On August 15, 2010, block 74,638 contained a transaction whose two outputs each carried a value of 92,233,720,368.54277039 BTC — very close to 2⁶³ satoshis apiece. Individually, neither value exceeded the signed-64-bit range, so a check on each output in isolation passed. But their sum, computed into the same signed 64-bit accumulator used for the total-output check, wrapped past 2⁶³ and came back around to a small, innocuous-looking number that cleared the "total ≤ MAX_MONEY" test. A PoW-only validator has no such test at all and would have accepted this without even noticing an accounting step happened. This single incident is why the modern checklist explicitly separates "each value in range" from "no negative or overflowing sums" as two distinct predicates, both mandatory, and why both are computed in a wide accumulator with an explicit range check after every addition.

So proof of work is necessary but nowhere near sufficient. What actually needs checking, and in what order — because order determines how cheaply an invalid block can be thrown out — is the subject of §5.

ARC 05 · THE VALIDATION PIPELINE

Layer the checks by how much state they need

The key design insight, and the one that lets Bitcoin Core (and every serious reimplementation) stay fast, is that not all rules need the same information. Some need only the 80-byte header. Some need the chain of previous headers. Some need the full block body. Some need the entire current UTXO set. Ordering checks from least state required to most lets a node reject most garbage before it ever touches the expensive parts — and it lets lightweight nodes that don't keep a UTXO set at all (chapter 10's SPV clients) still perform the cheaper layers on their own.

THE GENERAL PRINCIPLE

Cheapest and most state-independent checks run first; the checks that require the full UTXO set — the single most expensive piece of shared state a node maintains (chapter 6) — run dead last, and only for blocks that survived everything cheaper. This is not a performance nicety bolted on afterward; it is why an attacker flooding a node with garbage headers or malformed blocks costs the node almost nothing per rejection, and why a real attack has to actually solve real proof of work before it can waste any of a node's UTXO-lookup time at all.

ARC 06 · WHY THAT STILL COSTS

Layering isn't free, and neither is getting it right the first time

The pipeline from §5 is the correct architecture, and every serious node runs a version of it. It still has three costs worth being precise about, because each one has bitten real deployments:

  • A bug in a consensus rule becomes a permanent feature, not a bug ticket. The original OP_CHECKMULTISIG implementation has an off-by-one: it pops one more stack item than the signature count actually requires, so every multisig script must push a throwaway extra element (by convention, OP_0) purely to be discarded by the bug. This has been understood as a bug since at least the mid-2010s. It has never been fixed, because "fixed" means every multisig script ever written — and every coin currently locked behind one — would suddenly execute differently, which is precisely the definition of a hard fork nobody is willing to trigger. The closest thing to a fix, BIP62's NULLDUMMY rule, only makes the dummy element's value mandatory to be exactly zero — it does not remove the extra pop. The bug is permanent. §9 returns to this as the canonical proof that consensus code and ordinary code are governed by different physics.
  • Full validation is genuinely expensive, and skipping it is genuinely tempting. Verifying every signature in a block that contains several thousand transactions is thousands of elliptic-curve operations; before Bitcoin Core adopted libsecp256k1 in 2015-2016 (replacing OpenSSL's general-purpose, non-Bitcoin-specialized curve code), signature verification alone could be the dominant cost of both block validation and initial block download, with published measurements showing multiple-times speedups from the switch. Sigop limits (§8, §10) exist specifically because, before such limits, a small block packed with worst-case OP_CHECKMULTISIG calls could demand a wildly disproportionate amount of CPU relative to its byte size — a denial-of-service angle a byte-size limit alone does not close.
  • Skipping validation for speed is exactly how a chain split happens. A miner who assembles a block template and starts hashing the next block on top of a peer's announced header — without first fully downloading and validating that peer's block body — is called SPV mining. It is faster (you start hashing sooner) and it is a real practice some pools have used. It is also exactly how several miners spent real hash power extending an invalid chain for roughly six blocks on July 4, 2015, immediately after a new consensus rule activated — covered in full in §11.

None of this argues against the pipeline — it argues for taking it exactly this seriously, which is what the rest of the chapter now does.

Median-time-past: why not just compare to the previous block's timestamp?

Every miner sets its own block timestamp from its own clock, and consensus only requires it to be no more than two hours ahead of the network's view of "now." A naive rule — "timestamp must exceed the immediately previous block's timestamp" — sounds sufficient but is not: a miner sitting at the tip could set a timestamp far in the future (within the two-hour slack) to manipulate anything that reads block time — most importantly, time-based consensus logic — and then every subsequent block only has to clear that single inflated value, not a value reflecting genuine elapsed time. The fix is the median time past (MTP): take the timestamps of the last 11 blocks, sort them, take the middle value. A single dishonest miner controls at most one of those eleven values; moving the median requires controlling a majority of the last eleven blocks — i.e., requires the same hash-power dominance that would let an attacker rewrite history anyway. Coinbase maturity: why 100 blocks?

A coinbase output pays a miner for a block that might not stay on the best chain — a competing block at the same height could still win the race (chapter 7's fork-choice territory). If coinbase outputs were spendable immediately, spending one and then having its parent block reorganized out would leave the spending transaction referencing an output that never existed on the winning chain — a paradox no re-validation could cleanly repair. COINBASE_MATURITY = 100 blocks — roughly 16.7 hours at the target 10-minute spacing — was chosen as a depth at which an organic reorg is already extraordinarily unlikely (chapter 9 quantifies exactly how unlikely, as a function of an attacker's hash share). SIGOP COST, BRIEFLY, BECAUSE §10 NEEDS IT

Every script operation that can require a signature check (OP_CHECKSIG, and each key slot an OP_CHECKMULTISIG could check) is counted toward a per-block budget. Pre-SegWit, the legacy limit was MAX_BLOCK_SIGOPS = 20,000 (derived as the 1,000,000-byte block size limit divided by 50). Post-SegWit the accounting switched to a weight-based sigop cost, capped at MAX_BLOCK_SIGOPS_COST = 80,000, with legacy sigops weighted 4× and witness-program sigops weighted 1× — a deliberate discount that makes packing a block with expensive multisig checks via the newer script types comparatively cheaper to verify per byte, nudging usage toward the cheaper-to-validate script types without banning the old ones outright.

ARC 09 · TRADEOFFS

Consensus vs. policy: the line that must never blur

Every rule this chapter has covered so far is consensus: bit-for-bit identical, enforced by every fully-validating node, unchangeable except by a network-wide fork. But a running Bitcoin node also enforces a second, entirely different rulebook: policy — the minimum fee it will relay, which script shapes it considers standard, the dust threshold below which an output isn't worth relaying, and which transactions its mempool will accept at all. Confusing the two is the single most dangerous category error you can make working on this codebase, because they fail in completely different ways:

The practical, load-bearing consequence: a non-standard transaction can still be perfectly valid inside a block. If a miner — running custom software, or accepting an out-of-band fee arrangement — includes a transaction that most nodes' default policy would refuse to relay (an oversized OP_RETURN, an unusual bare-multisig shape, a fee below the going relay rate), every node on Earth will still accept the block containing it, because consensus doesn't care what policy would have done. This asymmetry is deliberate, not an oversight: policy is a spam filter you can tune locally; consensus is the law you cannot. A spam filter that occasionally lets something through is an inconvenience. A "law" that two implementations interpret differently is a currency that just split in two.

WHY THIS MAKES REIMPLEMENTING BITCOIN GENUINELY DANGEROUS

A from-scratch reimplementation (Bitcoin Core alternatives have existed in Go, Rust, and elsewhere) must reproduce every consensus predicate in this chapter — including its bugs — with bit-for-bit fidelity, or it risks accepting a block the rest of the network rejects (harmless to everyone else, catastrophic for that implementation's users) or rejecting a block everyone else accepts (that implementation silently forks itself off the real chain, with no warning beyond its own logs). This is exactly why Bitcoin Core extracted libbitcoinconsensus in the 0.10.0 release (February 2015): a standalone library exposing just the script-verification subset of consensus logic, so other software could delegate the single riskiest piece — Script execution, with all its historical quirks — to Bitcoin Core's own tested implementation rather than re-deriving it. Even that only covers script execution; the rest of this chapter's checklist — value conservation, maturity, the size/weight limits, BIP30/34's exact activation heights — still has to be reproduced independently, bug for bug, by anyone who wants their software to agree with the network it's trying to speak to.

ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What full validation actually costs, and what skipping it costs more

Every block's per-transaction phase (§7's UTXO row) does real, non-trivial work per input: a UTXO-set lookup, a value-conservation addition, and — the dominant cost — a full script execution including an elliptic-curve signature verification for the common single-sig case. None of this is free, and the numbers explain several design decisions you've already seen:

  • Signature verification dominates CPU cost. A single ECDSA verification over secp256k1 costs on the order of tens of microseconds with a specialized implementation; a block with several thousand transactions averaging just over one input each means several thousand such verifications, parallelizable across cores (Bitcoin Core's CCheckQueue exists specifically to fan script checks out across worker threads) but still real, measurable CPU time per block, every block, forever.
  • The library matters enormously. Bitcoin Core's move from OpenSSL's general-purpose curve arithmetic to the purpose-built libsecp256k1 (merged in stages across 0.10–0.12, roughly 2015–2016) produced multi-times speedups on signature verification specifically because a library written for one curve with one specific use pattern can make optimizations a general-purpose crypto library never would.
  • Sigop limits exist because size alone is a bad proxy for CPU cost. A small transaction can still contain an OP_CHECKMULTISIG with up to 20 public keys, each demanding its own signature check attempt in the worst case — cheap in bytes, expensive in CPU. The sigop budget (§8) exists to bound worst-case per-block CPU independently of the byte-size limit.
  • Initial block download is validation cost multiplied by chain history. Syncing from genesis means running every layer of this chapter's pipeline on every block ever mined. Modern Bitcoin Core ships an assumevalid default (a hardcoded, widely-attested block hash below which script signature checks are skipped, though every other rule — value conservation, structure, PoW — is still fully enforced) specifically to remove the single most expensive, and most redundant, part of that replay: re-verifying signatures on transactions whose validity is already attested by an enormous amount of cumulative proof-of-work built on top of them.

ARC 11 · REAL-WORLD INCIDENTS

Four times a validation gap became a permanent rule

Incident 1: The value overflow, block 74,638 (August 15, 2010)

Covered mechanically in §4: a transaction's two outputs each carried roughly 92.2 billion BTC, and their sum overflowed a signed 64-bit accumulator, sailing past the total-value check. Root cause: per-output range checks existed, but the check on the sum of outputs used unchecked 64-bit addition. Fix: a patched client (0.3.10) was released and the network re-organized away from the offending block within about five hours of its discovery — one of only a small number of times Bitcoin's history has required an emergency, coordinated rewrite of already-mined blocks. Permanent rule added: value-conservation checks now accumulate in a range that cannot silently wrap, with an explicit bounds check after every addition — precisely the "no negative or overflowing sums" predicate in this chapter's checklist.

Incident 2: Duplicate coinbase transactions (August 2010) — the reason BIP30 exists

Two separate real incidents produced coinbase transactions whose serialized bytes — and therefore txids — exactly duplicated an existing, still-unspent coinbase already in the chain: block 91,842's coinbase duplicated block 91,812's, and block 91,880's duplicated block 91,722's. Root cause: nothing in the original rules forbade two different blocks from producing identical transactions; a coinbase's inputs contain no prior output reference to make it naturally unique, and at the time nothing else guaranteed uniqueness either. Writing the second transaction's outputs into the UTXO set silently overwrote the first's entry. Fix: BIP30 (proposed by Gavin Andresen), enforced as a soft fork — reject any transaction whose txid duplicates an existing, unspent transaction already in the chain — with the two already-mined violations hardcoded as historical exceptions rather than retroactively invalidating years of subsequent blocks built on top of them. Later superseded in practice by BIP34 (2013): once every coinbase must commit its own block height as the first item pushed in its scriptSig, two coinbases can only collide if they somehow share a height, which cannot happen on one chain — making a genuine BIP30 violation practically impossible going forward, though the BIP30 check itself remains active for defense in depth.

Incident 3: The July 4, 2015 SPV-mining fork — BIP66's accidental hard fork

Root cause: BIP66 (strict DER signature encoding) locked in and began enforcement at block height 363,725. Shortly after, a large mining pool — widely reported to be F2Pool — produced a block containing a signature encoded in the older, looser (non-strict) format that the new rule now rejected. Several other pools, practicing SPV mining to shave seconds off their own block-finding latency, extended that invalid block without validating it, and kept extending the resulting chain for roughly six blocks. Meanwhile, every fully-validating node correctly rejected the entire branch. Fix: none needed at the protocol level — the rule was working exactly as designed. The honest, rule-following chain caught up and overtook the invalid branch once enough fully-validating miners resumed extending it, and the network reorganized back to the valid chain, at the cost of roughly six blocks' worth of confirmations being reversed for anyone who had trusted the invalid branch in the interim. The real lesson is not about BIP66 — it's that SPV mining converts "a rule I haven't personally checked yet" into hash power extending an invalid chain, which is exactly the failure mode §6 predicted before this section named it.

Incident 4: CVE-2018-17144 — the duplicate-input bug (disclosed September 2018)

Root cause: a refactor of the input-checking logic in Bitcoin Core 0.14.0 through 0.16.2 inadvertently dropped a check — present since shortly after the 2010 incidents — that rejected transactions referencing the same input outpoint more than once. A specially crafted transaction with a duplicated input could cause a full node to crash (a straightforward denial-of-service), and in principle exposed a path toward exactly the class of inflation bug this checklist's "value conservation" predicate exists to prevent. Fix: discovered by a developer auditing the codebase, reported privately, and patched in 0.16.3, which was released and distributed for roughly a day before the full technical details were published — a deliberate, coordinated delay specifically to give node operators a window to upgrade before an exploit could be reverse-engineered from a public disclosure. Rule reinforced: "no duplicate inputs within a single transaction" is now checked explicitly and separately, rather than being an emergent property of some other check that a future refactor could once again accidentally remove.

The header-only layer first — everything a node can check with nothing but the 80 bytes in hand:

C++validation.cpp — CheckBlockHeader(), simplified but faithful
bool CheckBlockHeader(const CBlockHeader& block, BlockValidationState& state,
                      const Consensus::Params& params)
{
    /* Context-free: needs ONLY these 80 bytes. No chain, no UTXO set. */
    if (!CheckProofOfWork(block.GetHash(), block.nBits, params))
        return state.Invalid("high-hash");      /* hash > target */

    if (block.GetBlockTime() > GetAdjustedTime() + MAX_FUTURE_BLOCK_TIME)
        return state.Invalid("time-too-new");   /* MAX_FUTURE_BLOCK_TIME = 2h */

    return true;
}

Then the contextual header layer — needs the chain of previous headers, not the block body:

C++validation.cpp — ContextualCheckBlockHeader(), simplified
bool ContextualCheckBlockHeader(const CBlockHeader& block, BlockValidationState& state,
                               const CBlockIndex* pindexPrev, int64_t now)
{
    if (pindexPrev == nullptr)
        return state.Invalid("bad-prevblk");   /* orphan — parent unknown to us */

    if (block.nBits != GetNextWorkRequired(pindexPrev, &block, params))
        return state.Invalid("bad-diffbits");  /* must match the retarget schedule exactly — ch.9 */

    if (block.GetBlockTime() <= pindexPrev->GetMedianTimePast())
        return state.Invalid("time-too-old");   /* MTP of the last 11 blocks, not just the previous one */

    return true;
}

And the heaviest function in the whole codebase: ConnectBlock()'s per-transaction loop, where the UTXO set finally enters the picture:

C++validation.cpp — ConnectBlock(), the per-input loop, simplified
for (const CTransactionRef& ptx : block.vtx) {
    const CTransaction& tx = *ptx;
    if (tx.IsCoinBase()) { AddCoins(view, tx, height); continue; }

    CAmount valueIn = 0;

            return state.Invalid("bad-txns-premature-spend-of-coinbase");  /* 100 blocks */

        valueIn += coin.out.nValue;                        /* wide accumulator, range-checked — §4/§11 */
    }
    if (valueIn < tx.GetValueOut())
        return state.Invalid("bad-txns-in-belowout");   /* sum(inputs) >= sum(outputs) */

    nSigOpsCost += GetTransactionSigOpCost(tx, view, flags);
    if (nSigOpsCost > MAX_BLOCK_SIGOPS_COST)
        return state.Invalid("bad-blk-sigops");

    CScriptCheck check(coin.out, tx, i, flags);       /* flags include DERSIG (BIP66), CLTV (BIP65), CSV (BIP68/112) */
    if (!check())
        return state.Invalid("mandatory-script-verify-flag-failed");

    view.SpendCoin(in.prevout);
    AddCoins(view, tx, height);
}
WHY IT'S SPLIT INTO FIVE FUNCTIONS, NOT ONE

Splitting header checks (context-free, then contextual) from body checks (structure, then per-transaction) means a node can validate — and reject — a header before ever requesting the block body from a peer, which is exactly what happens during headers-first sync (chapter 10) and what lets pruned or SPV-style clients get meaningful protection from a subset of this pipeline without storing a UTXO set at all. It also means the single most expensive function, ConnectBlock(), is only ever reached for blocks that already passed every cheaper filter — an attacker cannot make a node do expensive UTXO-set work without first producing genuine, real proof of work, exactly the ordering principle §5 derived from scratch.
