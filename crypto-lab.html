STEP 01 · SETUP

OpenSSL is the lab — no cluster required

Every chapter in this course is provable from a terminal with OpenSSL installed. No Docker Compose file, no multi-node anything. A handful of experiments write a ~30-line Node.js script; everything else is the openssl CLI you already have.

Check your OpenSSL — version matters

Real AEAD ciphers, the openssl kdf command, and full TLS 1.3 support all depend on having OpenSSL 1.1.1 or later, and some of this lab (the kdf command, modern pkeyutl padding-mode options) specifically needs OpenSSL 3.x.

openssl version -a

Apple's system /usr/bin/openssl is actually LibreSSL (commonly reporting something like LibreSSL 3.3.6) — a fork that diverged from OpenSSL years ago. It lacks the kdf command entirely, has an older pkeyutl, and its s_client flags drift from upstream. Install real OpenSSL 3.x and put it first in your PATH for this lab:

Troubleshooting

SYMPTOMCAUSE & FIX
bad decrypt / wrong final block length on openssl enc -d Almost always a wrong key/password, a wrong -md (OpenSSL changed its default password-derivation digest from MD5 to SHA-256 between 1.0.2 and 1.1.0 — old ciphertext needs -md md5 to redecrypt), or a truncated/corrupted file that isn't a multiple of the block size. It is not an authentication failure — plain enc ciphers have no integrity check at all, so garbage input can sometimes even "succeed" and hand you garbage plaintext.
openssl enc -aes-256-gcm refuses to run, or silently does the wrong thing By design. The enc command does not support AEAD modes (GCM, CCM, ChaCha20-Poly1305) at all — see orientation walkthrough 2. Use a short script (Node's crypto or Python's cryptography) for real AEAD from the command line.
macOS: unknown option '-pbkdf2' or missing kdf subcommand You're running LibreSSL, not OpenSSL — see the callout above. Install openssl@3 via Homebrew and fix your PATH.
Ciphers not supported for this operation using -rc4, -des, etc. OpenSSL 3.0 moved legacy algorithms into a separate legacy provider that isn't loaded by default. Add -provider legacy -provider default to the command. This is deliberate friction — those ciphers are legacy for a reason.
openssl rsautl prints a deprecation warning, or is missing entirely rsautl is deprecated in OpenSSL 3.0+ in favor of pkeyutl. Every rsautl command in this lab has a pkeyutl equivalent — use that instead; some downstream distros have started removing rsautl altogether.
s_client/s_server hang with no output Pipe </dev/null into s_client when you just want the handshake and not an interactive session, or pass -connect_timeout 5. For s_server, confirm the port isn't already bound by another process.
Certificate decode shows unable to load certificate You handed x509 a DER file without -inform DER, or a PEM file that's actually a full chain when the tool expected one certificate. Split multi-cert PEM bundles with csplit or awk before decoding each one.

This is your key source for the rest of the lab. /dev/urandom underneath (or the OS CSPRNG equivalent) — never seed key material from $RANDOM, a timestamp, or anything without a documented security guarantee.

2 · The AEAD gap in openssl enc — and how to actually get authenticated encryption

Every "openssl AES-GCM one-liner" you'll find in a search result is wrong. Try it:

bash
KEY=$(openssl rand -hex 32)
IV=$(openssl rand -hex 12)
echo -n "transfer $500 to acct 44821" > plain.txt

openssl enc -aes-256-gcm -K $KEY -iv $IV -in plain.txt -out ct.bin
EXPECTED — a hard failure, by design
80B5B47F7A7F0000:error:1C800069:Provider routines:cipher_generic_einit:invalid mode:
providers/implementations/ciphers/ciphercommon.c:171:
(exact wording differs by version; older OpenSSL just refuses the mode)

This isn't a bug you can flag your way around. The enc command streams ciphertext to stdout as it encrypts, but an AEAD tag can only be verified after the entire ciphertext has been seen — letting a pipeline consume unauthenticated bytes before the tag check would defeat the entire point of authentication. OpenSSL's maintainers have declined to add GCM/CCM support to enc for exactly this reason.

Path A — build AEAD by hand from primitives you already have (encrypt-then-MAC)

bash
ENCKEY=$(openssl rand -hex 32)
MACKEY=$(openssl rand -hex 32)
IV=$(openssl rand -hex 16)

# 1. encrypt with a plain (unauthenticated) mode — CTR turns AES into a stream cipher
openssl enc -aes-256-ctr -K $ENCKEY -iv $IV -in plain.txt -out ct.bin

# 2. MAC the ciphertext (NOT the plaintext) — this is what "encrypt-THEN-mac" means
TAG=$(openssl dgst -sha256 -mac hmac -macopt hexkey:$MACKEY -binary ct.bin | xxd -p -c 64)
echo "tag: $TAG"

# ship IV || ciphertext || tag together; verify the tag BEFORE ever decrypting

This is the exact composition chapter 7 derives as safe — MAC-then-encrypt and encrypt-and-MAC both have documented attacks; encrypt-then-MAC lets you reject a forged ciphertext without decrypting a single byte of it.

Path B — real AES-256-GCM, via a nine-line script

nodegcm.js
const crypto = require('crypto');
const key = crypto.randomBytes(32), iv = crypto.randomBytes(12);
const c = crypto.createCipheriv('aes-256-gcm', key, iv);
const ct = Buffer.concat([c.update('transfer $500 to acct 44821', 'utf8'), c.final()]);
const tag = c.getAuthTag();
console.log('ciphertext:', ct.toString('hex'));
console.log('tag:      ', tag.toString('hex'));

const d = crypto.createDecipheriv('aes-256-gcm', key, iv);
d.setAuthTag(tag);
console.log('decrypted:', Buffer.concat([d.update(ct), d.final()]).toString());
EXPECTED
ciphertext: 5e2a9f... (28 bytes for a 28-byte plaintext — GCM is a stream cipher underneath)
tag:       a13f0c9e2b7d4415f9a0c6e2d1b87340
decrypted: transfer $500 to acct 44821

STEP 04 · PRODUCTION BEST PRACTICES

A cookbook where every recommendation names its mechanism

Cipher and mode selection for new systems

CHOICEWHENMECHANISM
AES-256-GCMdefault choice for new systems with hardware AES support (AES-NI on x86, Crypto Extensions on ARM64) AEAD in one primitive — CTR-mode confidentiality plus GHASH authentication (ch.7). Nonce must never repeat per key (experiment 8); hardware acceleration makes it faster than software ChaCha20 on server CPUs.
ChaCha20-Poly1305mobile/embedded targets without AES hardware, or as a fallback cipher suite alongside GCM Pure ARX operations (add-rotate-XOR) run fast in software with no lookup tables, which also removes an entire class of cache-timing side channel that table-based AES software implementations are prone to.
AES-CBC (any key size)never, for new code No built-in authentication, and PKCS#7 padding plus a decrypt-then-authenticate design is the exact setup a padding oracle exploits (experiment 12). Only acceptable already-deployed inside a correctly-implemented encrypt-then-MAC composition.
AES-ECBnever No IV, no chaining — identical plaintext blocks always produce identical ciphertext blocks (experiment 3). Leaks structure directly.
RC4never Documented keystream biases (ch.4); removed from TLS entirely as of RFC 7465.
3DESnever 64-bit block size makes it vulnerable to birthday-bound collisions (Sweet32) well within the data volume a modern connection can carry.

KDF selection by use case — these are not interchangeable

INPUTUSEWHY
A human passwordArgon2id (preferred) or bcrypt (acceptable legacy); PBKDF2 only where FIPS validation is mandatory Passwords have low entropy and must resist offline GPU/ASIC cracking (experiment 10) — Argon2's memory-hardness specifically defeats the parallel cracking that makes GPUs so effective against fast or even iterated-but-memory-light KDFs.
A high-entropy secret (DH/ECDH shared secret, an existing 256-bit key)HKDF (RFC 5869) The input is already unguessable — there's nothing to slow an attacker down from, so a fast extract-then-expand construction is correct, not a security compromise (experiment 9).
Deriving several independent keys from one master keyHKDF-Expand with a distinct info label per purpose Domain separation: HKDF-Expand(PRK,"encryption") and HKDF-Expand(PRK,"authentication") are cryptographically independent even though they share a PRK, so compromising one derived key doesn't compromise the others.
A fast hash used AS a KDF (raw sha256(password))never Zero cost multiplier for the attacker — exactly the failure experiment 10 measures directly.

TLS configuration hardening checklist

  • Disable TLS 1.0 and 1.1 entirely. Both are formally deprecated by RFC 8996; neither supports AEAD-only cipher suites, and both carry legacy CBC-suite baggage.
  • Prefer TLS 1.3; support 1.2 only where a real client population needs it. 1.3 removes static-RSA key exchange, all CBC suites, and compression — entire vulnerability classes gone by construction, not by configuration discipline.
  • On TLS 1.2, allow only AEAD suites with ECDHE key exchange. ECDHE-RSA-AES128-GCM-SHA256 and better; forbid anything with CBC, RC4, 3DES, or a static RSA key-exchange prefix (no forward secrecy).
  • Forward secrecy is mandatory, not optional. Static RSA key exchange means one future private-key compromise decrypts every past session ever recorded. ECDHE/DHE keys are ephemeral per-connection.
  • Turn on OCSP stapling. The server fetches and attaches its own revocation proof, so the client doesn't leak which sites it visits to a third-party OCSP responder and doesn't fail open when that responder is unreachable.
  • Ship HSTS with a long max-age, includeSubDomains, and consider preload. Without it, the very first plaintext HTTP request before any redirect is an SSL-stripping opportunity.
  • Disable TLS compression and renegotiation you don't need. Compression enabled CRIME; unrestricted renegotiation enabled a real injection vulnerability (CVE-2009-3555) before RFC 5746 fixed the binding.

Certificate lifetime and rotation policy

CERTIFICATETYPICAL LIFETIMEWHY
Public leaf/server certs≤ 398 days (CA/Browser Forum baseline); industry direction is toward far shorter (Let's Encrypt defaults to 90 days) Shorter validity bounds the damage window of an undetected key compromise and forces automation — a cert that must be renewed manually every few years is a cert nobody remembers how to rotate under pressure (runbook 5.1).
Internal / mTLS service certsDays to weeks, fully automated (step-ca, Vault PKI, SPIFFE/SPIRE) Internal CAs can issue as often as needed with no external validation delay — there's no reason to accept the same multi-month blast radius you'd tolerate for a public cert.
Intermediate CA3–5 years Long enough to amortize the operational cost of issuing one, short enough that a compromised intermediate doesn't stay trusted for a decade.
Root CA10–20 years, kept offline except to sign intermediates The root's private key signs your entire trust chain (ch.12) — it is the highest-value target in the system and the one most worth taking offline entirely between uses.
Any key you suspect is compromisedImmediately — see runbook 5.1 There is no partial-credit option here; assume the worst and rotate.

Anti-patterns and their specific damage

  

    
ANTI-PATTERNWHAT IT COSTS

    
Rolling your own crypto primitiveworst offender Every attack in this lab's experiments exists because someone's home-grown construction skipped a step a standard one wouldn't have (experiments 6, 7, 12). Compose vetted primitives; never invent new ones.

    
Comparing secrets with ==/.equals()A timing side channel that leaks the secret one byte at a time to a patient attacker (experiment 16). Use crypto.timingSafeEqual or your language's constant-time compare.

    
Reusing a nonce/IV under AEADTotal authentication break under GCM (experiment 8), not just reduced confidentiality — this is a correctness bug with catastrophic severity, not a tuning tradeoff.

    
A fast hash for password storageSix-plus orders of magnitude cheaper for an attacker to crack per guess (experiment 10).

    
MAC-then-encrypt or encrypt-and-MACSets up the exact decrypt-before-authenticate ordering a padding or timing oracle exploits (experiments 7 and 12). Always encrypt-then-MAC, or use AEAD.

    
Trusting client-supplied algorithm identifiers"Algorithm confusion" — e.g. accepting an attacker-chosen alg:none JWT, or letting a client downgrade to a weak cipher suite. Pin the algorithm server-side.

    
Long-lived static API keys with no rotation pathThe blast radius of a leak is unbounded in time. Short-lived, automatically rotated credentials cap it (runbook 5.1).

  







  
STEP 05 · OPERATIONAL RUNBOOKS

  
Procedures for when it's already going wrong


  
5.1 · Rotating a compromised TLS private key/certificate under time pressure

  
Precondition: you have (or can get, urgently) access to issue a replacement certificate — either your CA's API/portal or an internal CA.

  
    
    
  1. Assume the worst immediately. Do not wait for confirmation of exploitation — a suspected private-key exposure (leaked in a repo, on a decommissioned host, in a crash dump) is treated as a confirmed compromise from the first minute.
    2. 
    
  2. Revoke the old certificate with your CA (OCSP/CRL) even though revocation propagation is not instant and not universally checked by clients — it's still a necessary signal, not a complete fix.
    3. 
    
  3. Generate a brand-new keypair. Never reissue a certificate for the same private key — the point of rotation is that the compromised key stops being trusted for anything, ever.
    4. 
    
  4. Issue and deploy the new certificate, then reload (not just restart, unless your server only picks up certs on start) every terminating endpoint — load balancers, ingress controllers, and any service terminating TLS directly.
    5. 
    
  5. Rotate anything the old key might have protected in transit if there's a plausible window where traffic was interceptable — session tokens, API keys exchanged over connections terminated by the compromised cert.
    6. 
    
  6. Verify from outside: openssl s_client -connect host:443 -showcerts </dev/null | openssl x509 -noout -fingerprint -serial — confirm every edge is serving the new serial number, not a cached old one.
    7. 
    
  7. Post-incident: find out how the key was exposed (repo scan, log scrubbing, host decommission checklist) and close that specific gap — rotation without a root cause fix just buys time until the next leak.
    8. 
  


  
5.2 · Responding to a padding-oracle or timing-oracle finding from a pentest report

  
Precondition: the report identifies a specific endpoint and request parameter, not just "the site may be vulnerable."

  
    
    
  1. Reproduce it yourself before touching code — build the minimal decryption/comparison oracle exactly as experiment 12 or 16 does, confirm you can distinguish valid/invalid or fast/slow with the reported parameter.
    2. 
    
  2. Identify the exact code path. For a padding oracle: find where ciphertext is decrypted and where/how padding errors surface (a distinct HTTP status, a different error message, or even a timing difference between padding-check failure and MAC-check failure). For a timing oracle: find the comparison function handling the secret.
    3. 
    
  3. Fix the primitive, not the symptom. Switching from CBC+MAC-then-encrypt to an AEAD cipher removes the padding oracle by construction — don't just make the two error paths return identical-looking messages while leaving decrypt-then-authenticate order intact, because a sufficiently patient attacker can still find a timing gap between them.
    4. 
    
  4. For a timing oracle, replace the comparison with a constant-time function (crypto.timingSafeEqual, `hmac.compare_digest`, or your language's equivalent) and confirm both branches now take statistically indistinguishable time under repeated measurement (experiment 16's methodology).
    5. 
    
  5. Regression test the fix by re-running your reproduction from step 1 against the patched endpoint — it should now be indistinguishable from random guessing, not just "harder."
    6. 
    
  6. Disclose the fix window and CVE/advisory (if applicable) to the reporter, and check whether the same primitive/pattern is duplicated elsewhere in the codebase (it usually is).
    7. 
  


  
5.3 · Auditing a codebase for non-constant-time secret comparisons

  
    
    
  1. Grep broadly, then narrow by hand. Search for equality operators (==, .equals(, strcmp, ===) within a few lines of identifiers like token, secret, signature, hmac, password, apikey, csrf.
    2. 
    
  2. Check webhook and callback signature verification specifically — this is the single most common place a naive == survives, because it's often copy-pasted from a vendor's sample code that never mentioned timing safety.
    3. 
    
  3. Watch for indirect leaks, not just direct equality. A lookup keyed by a secret prefix (cache[token.slice(0,8)]), an early-exit loop that stops at the first mismatched character, and a database query using the secret as a WHERE clause with an index (query planner timing differs by match) all leak the same kind of signal as a naive string compare.
    4. 
    
  4. Replace with the language's constant-time primitive: Node's crypto.timingSafeEqual, Python's hmac.compare_digest, Go's subtle.ConstantTimeCompare, Java's MessageDigest.isEqual. Confirm the buffers are equal-length first via a length check that doesn't itself leak (comparing lengths is normally considered acceptable, since length usually isn't the secret).
    5. 
    
  5. Verify with a timing measurement, not just a code read — run experiment 16's methodology against the actual patched function to confirm the fix removed the measurable gap rather than just looking safer.
    6. 
    
  6. Extend the audit to native/FFI code and third-party dependencies — a constant-time wrapper around a non-constant-time underlying comparison (or a JIT that optimizes away the "constant-time" loop) defeats the whole point silently.
    7. 
  


  
5.4 · Verifying a KMS/HSM envelope-encryption setup actually protects the DEK

  
Precondition: you can read the IAM/key-policy configuration and at least one real encrypted object's storage format.

  
    
    
  1. Confirm the DEK (data encryption key) is never persisted in plaintext anywhere outside process memory during active use — grep storage and logs for anything that looks like a raw symmetric key, not just the wrapped (encrypted) form.
    2. 
    
  2. Confirm the CMK/KEK (key-encryption key) never leaves the KMS/HSM boundary. The service should only expose Encrypt/Decrypt/GenerateDataKey operations on the CMK — if there's an Export or raw-key-retrieval path enabled anywhere, the "H" in HSM isn't buying you anything.
    3. 
    
  3. Check the envelope structure on disk/in the database: it should be encrypted_DEK || ciphertext, where encrypted_DEK is only usable by calling back into the KMS — never a locally-cached plaintext DEK reused across many records without an expiry.
    4. 
    
  4. Audit IAM/key-policy grants for least privilege. The principal calling Decrypt should be scoped as tightly as the data it protects — a service-wide "any authenticated request can decrypt" policy defeats the purpose of per-tenant or per-record envelope encryption.
    5. 
    
  5. Test that key rotation doesn't break old ciphertexts. Rotate the CMK, then confirm a record encrypted under the previous CMK version still decrypts — KMS services typically retain old key material specifically so wrapped DEKs from before rotation remain unwrappable.
    6. 
    
  6. Confirm every Decrypt call is logged (CloudTrail, Vault audit log, or equivalent) with enough context to answer "who decrypted which record, when" during an incident — this is often the only forensic trail that survives a breach.
    7. 
    
  7. Confirm the DEK is zeroized from memory after use where the runtime allows it, and that it isn't captured in a crash dump, core dump, or verbose debug log during the window it's held in plaintext.
    8.

Project 1 · A correct AEAD command-line tool

  
The pattern every "encrypt this file" script gets wrong somewhere: a fresh random nonce per message, and a hard failure — not a best-effort partial decrypt — the instant authentication fails.

  
nodeaead-cli.js


#!/usr/bin/env node
'use strict';
const crypto = require('crypto');
const fs = require('fs');

const [, , cmd, keyHex, inPath, outPath] = process.argv;
if (!cmd || !keyHex || !inPath || !outPath) {
  console.error('usage: aead-cli.js    ');
  process.exit(1);
}
const key = Buffer.from(keyHex, 'hex');
if (key.length !== 32) {
  console.error('key must be 32 bytes (64 hex chars) -- generate one with: openssl rand -hex 32');
  process.exit(1);
}

if (cmd === 'enc') {
  const plaintext = fs.readFileSync(inPath);
  const nonce = crypto.randomBytes(12);              // NEVER reuse a nonce under the same key
  const cipher = crypto.createCipheriv('aes-256-gcm', key, nonce);
  const ct = Buffer.concat([cipher.update(plaintext), cipher.final()]);
  const tag = cipher.getAuthTag();                     // 16-byte GCM tag
  fs.writeFileSync(outPath, Buffer.concat([nonce, tag, ct]));  // nonce || tag || ciphertext
  console.log(`encrypted ${plaintext.length} bytes -> ${outPath}`);
} else if (cmd === 'dec') {
  const blob = fs.readFileSync(inPath);
  const nonce = blob.subarray(0, 12), tag = blob.subarray(12, 28), ct = blob.subarray(28);
  const decipher = crypto.createDecipheriv('aes-256-gcm', key, nonce);
  decipher.setAuthTag(tag);
  try {
    const pt = Buffer.concat([decipher.update(ct), decipher.final()]);  // throws on tag mismatch
    fs.writeFileSync(outPath, pt);
    console.log(`authenticated + decrypted -> ${outPath}`);
  } catch (e) {
    console.error('REJECTED: authentication failed --', e.message);
    process.exit(1);
  }
} else {
  console.error('unknown command:', cmd);
  process.exit(1);
}

# tamper with one byte and confirm it is REJECTED, not silently corrupted
python3 -c "d=bytearray(open('secret.enc','rb').read()); d[-1]^=1; open('tampered.enc','wb').write(d)"
node aead-cli.js dec $KEY tampered.enc tampered.out

  

    
WHAT PROVES THIS WORKS

    
(1) The round trip matches byte for byte. (2) Encrypting secret.txt twice in a row produces two different ciphertexts each time — proof the nonce is really random per call. (3) Decrypting the tampered file prints REJECTED: authentication failed and exits non-zero — it never writes partial or garbage plaintext to tampered.out at all.

  

  
Extension: at high message volume under one key, a random 96-bit nonce has a meaningful collision probability well before 2^96 messages (the birthday bound puts real risk around 2^32 messages) — add a monotonic counter into the low bits of the nonce instead of pure randomness, and document the key's maximum safe message count.

Project 3 · A mini TLS-1.3-shaped handshake — then MITM your own unauthenticated version

  
Combine every primitive from this lab: X25519 key exchange, an HKDF key schedule, and AES-256-GCM records. Build it once without authentication, prove it's silently MITM-able, then add back exactly the certificate/signature step that fixes it.

  
nodemini-tls.js — shared primitives


'use strict';
const crypto = require('crypto');

function deriveSecret(sharedSecret, label) {
  return Buffer.from(crypto.hkdfSync('sha256', sharedSecret, Buffer.alloc(32), Buffer.from(label), 32));
}
function makeParty() {
  return crypto.generateKeyPairSync('x25519');        // { publicKey, privateKey }
}
function handshake(myPriv, peerPub, label) {
  const shared = crypto.diffieHellman({ privateKey: myPriv, publicKey: peerPub });
  return deriveSecret(shared, label);
}
function seal(key, seq, plaintext) {
  const nonce = Buffer.alloc(12); nonce.writeUInt32BE(seq, 8);   // sequence-number nonce, TLS 1.3-style
  const c = crypto.createCipheriv('aes-256-gcm', key, nonce);
  const ct = Buffer.concat([c.update(plaintext), c.final()]);
  return Buffer.concat([ct, c.getAuthTag()]);
}
function open(key, seq, blob) {
  const nonce = Buffer.alloc(12); nonce.writeUInt32BE(seq, 8);
  const ct = blob.subarray(0, blob.length - 16), tag = blob.subarray(blob.length - 16);
  const d = crypto.createDecipheriv('aes-256-gcm', key, nonce);
  d.setAuthTag(tag);
  return Buffer.concat([d.update(ct), d.final()]);
}
module.exports = { makeParty, handshake, seal, open };

WHAT THIS PROVES — AND WHY IT MATTERS

    
Both demos print entirely successful-looking output. The client and server in mitm_demo.js never see an error, never see a mismatched key, and have no protocol-level signal that Mallory is reading and relaying every message. This is experiment 13's DH-with-openssl result again, now against a real X25519+AEAD stack.

  

  
The fix: bind the exchange to an identity the client already trusts

  
nodeadd a signature over the transcript


const serverIdentity = crypto.generateKeyPairSync('ed25519');  // long-term key, trusted out-of-band (simulates a CA-signed cert)

function signTranscript(identityPriv, clientPub, serverPub) {
  const transcript = Buffer.concat([
    clientPub.export({ type: 'spki', format: 'der' }),
    serverPub.export({ type: 'spki', format: 'der' })
  ]);
  return crypto.sign(null, transcript, identityPriv);    // Ed25519 hashes internally -- pass null
}
function verifyTranscript(identityPub, clientPub, serverPub, sig) {
  const transcript = Buffer.concat([
    clientPub.export({ type: 'spki', format: 'der' }),
    serverPub.export({ type: 'spki', format: 'der' })
  ]);
  return crypto.verify(null, transcript, identityPub, sig);
}

  
Re-run the MITM: Mallory can still substitute her own ephemeral X25519 public key, but she cannot produce signTranscript's output for a transcript containing her key, because she does not hold serverIdentity.privateKey. The client calls verifyTranscript(serverIdentity.publicKey, client.publicKey, mallory.publicKey, malloryForgedSig) — since Mallory has no way to produce a valid malloryForgedSig for a transcript containing her own substituted key, this returns false, and the client aborts before ever sending anything sensitive.

  

    
WHAT PROVES THIS WORKS

    
The unauthenticated version: MITM succeeds silently, both logs show matching keys, neither party detects tampering. The signed version: the client's transcript verification returns false the instant Mallory's key is substituted, using the exact same X25519 exchange underneath — the only change is one signature check bound to an identity key the client already trusted before the connection started. That one check is, structurally, exactly what a real TLS certificate chain (chapter 12, experiment 14) provides.
