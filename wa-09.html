WHATSAPP ARCHITECTURE · CHAPTER 09

Multi-Device: Sessions
Without a Phone Proxy

For its first decade, WhatsApp had exactly one true endpoint per identity: the phone. The browser you used at your desk was a window into that phone, nothing more. This chapter derives, from the Signal Protocol's own constraints, why that had to change, why the obvious fixes don't work, and exactly what it costs to give one identity a set of independent, cryptographically equal devices — none of which is allowed to be a single point of failure, and none of which is allowed to be a hole in the encryption.

ARC 01 · THE PROBLEM

One identity, one phone, one Signal session — and the web tab that broke it

The original WhatsApp trust model was beautifully simple: identity = phone number = one physical device = exactly one Signal Protocol session per contact. Every cryptographic guarantee the app made — forward secrecy, deniability, the safety-number fingerprint you could compare in person — was reasoned about against a single X3DH key agreement and a single Double Ratchet chain per conversation. That simplicity is not an accident; it is the entire reason the 2016 rollout of end-to-end encryption across a billion-plus-user app was tractable at all.

But users wanted to type on a laptop keyboard, and "open WhatsApp Web" long predates the encryption rollout. The constraint the architecture had to satisfy was brutal in its specificity: add a second, third, fourth screen to a conversation without adding a second identity, without weakening the one-session-per-contact model, and — eventually — without requiring the phone to be reachable at all. That last clause is the one that forces a real redesign, and this chapter is about deriving it from first principles rather than describing it as a feature.

  • Multiplicity without duplication. A message sent from the laptop must be indistinguishable, to the recipient, from one sent by the phone — same identity, same trust anchor — yet the laptop cannot literally be the phone.
  • No shared mutable secret across devices. Whatever lets device #2 encrypt on the user's behalf cannot simply be a copy of device #1's private key material sitting in a browser's memory — that would make browser compromise equivalent to compromising the user's entire cryptographic identity, forever, unrevocably.
  • No new trusted intermediary. The server routes ciphertext; it must not gain a decryption capability it didn't already have just because the user added a second screen.
  • The device set is discoverable, and that discoverability is itself an attack surface. Someone has to tell Alice "Bob now has 3 devices" — and whoever controls that answer can lie.

Every subsequent section is this problem, solved layer by layer: §2 explains why the industry started with phone as proxy anyway, §3–§6 show why the two obvious multi-device designs both fail for different reasons, and §7 onward assembles the architecture WhatsApp actually shipped in its 2021 multi-device rearchitecture — each device with its own identity key, and the device list itself promoted to signed, security-critical state.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Chapter 6 showed you group messaging's sender-key fan-out — one sender, many recipients. This chapter is the orthogonal fan-out: one identity, many devices. Multi-device and groups compose multiplicatively — a message to a 200-member group where every member runs 2–3 devices is not 200 ciphertexts, it can be 400–600 — and chapter 10 revisits exactly this compounding when it covers storage and Mnesia-style replication of per-device state at scale.

DEEP CONTEXT · WHY "PROXY" WAS THE RIGHT FIRST ANSWER

In 2015 there was no E2E encryption to protect yet — the Signal Protocol integration didn't complete until April 2016. WhatsApp Web could therefore be shipped as exactly what it looked like: a second screen mirroring a live session, authenticated by scanning a QR code that handed the browser a token good for one authenticated WebSocket. Once encryption landed, the team faced a choice: retrofit multi-device support into the encryption layer immediately, or keep the proxy shape and have the phone perform all encryption/decryption, relaying plaintext to the browser over that already-authenticated channel. They chose the second path — it required zero changes to the just-shipped identity/session model, preserved exactly one Signal session per user, and shipped in weeks instead of years. That deferred cost is the subject of §4.

ARC 03 · NAIVE SOLUTION

Attempt #1: hand the browser the same ratchet the phone uses

Derive it honestly, the way a reasonable engineer would in 2020 facing "make Web work without the phone being online." The Double Ratchet state for a conversation — root key, sending chain key, receiving chain key, skipped message-key cache — is just a data structure. If the phone can serialize it, transmit it once over the already-established QR-authenticated channel, and let the browser advance the same ratchet independently, then both devices are first-class participants in the same Signal session. No new sessions, no new fan-out, no change to the wire protocol other than "sync the state once."

TypeScriptnaive_shared_ratchet.ts — the strawman, annotated
interface RatchetState {
  rootKey: Uint8Array;
  sendingChainKey: Uint8Array;
  sendingCounter: number;          // Nth message on this chain
  receivingChains: Map<string, ChainState>;
  identityKeyPriv: Uint8Array;      // the LONG-TERM secret
}

// Phone, on QR pairing: hand the browser the whole session.
function pairCompanion(qrChannel: SecureChannel, state: RatchetState) {
  qrChannel.send(serialize(state));   // ← identity key AND ratchet, verbatim
}

// Browser: now it just... is the same session.
function encryptOutgoing(state: RatchetState, plaintext: Uint8Array) {
  const mk = kdf(state.sendingChainKey, "message-key");
  state.sendingChainKey = kdf(state.sendingChainKey, "chain-advance");
  state.sendingCounter++;
  return aeadEncrypt(mk, plaintext);   // looks identical to a phone-sent message
}

This is not a strawman built to be laughed at — it is the design that gets the most obvious requirement right: zero new sessions, zero fan-out, and messages from either device are wire-identical. It fails for a reason that has nothing to do with engineering effort and everything to do with what a ratchet is. §4 quantifies exactly where it breaks.

ARC 04 · WHY IT FAILS

A ratchet has exactly one writer, by construction

The Double Ratchet's entire security argument rests on a single-writer invariant: each message consumes the current chain key and derives the next chain key, deterministically, and then the old key is deleted. That deletion is forward secrecy — it is not an optimization, it is the mechanism. Two devices independently holding a copy of sendingChainKey and advancing it without coordination is not a performance bug, it is a correctness violation with a name: key reuse.

  • The race, quantified. Say the phone and the laptop each send a message within the same 200 ms window with no coordination. Both read sendingChainKey = K, both derive messageKey = KDF(K), both encrypt different plaintexts under the same message key, and both advance to K' = KDF(K, "next") — except now two "next" states exist and neither device knows the other one moved. The receiver's ratchet, which expects a strictly increasing counter per chain, now sees two messages claiming counter N. One is silently undecryptable, or — depending on how strictly the skipped-key cache is bounds-checked — the implementation could accept both under the reused key, which is the actual cryptographic failure, not just a UX glitch.
  • Fixing the race reintroduces the exact problem you were escaping. The only way to make two writers of one mutable ratchet safe is a lock: some arbiter that serializes "phone wants to send" against "laptop wants to send." Signal sessions do not have network access to a lock server built in — you would have to build one. And the natural place to put it is the device the user considers "primary," i.e. the phone. You have re-derived the phone must be reachable to send from any device — the exact constraint multi-device was commissioned to remove.
  • Copying the long-term identity private key multiplies blast radius instead of dividing it. §1 already flagged this: a browser tab is a lower-assurance execution environment than a phone's OS keystore (extensions, dev tools, XSS in any co-hosted script, disk-based session storage). If every companion device holds a literal copy of identityKeyPriv, compromising the weakest device compromises the identity permanently — there is no way to revoke "the browser's copy" without rotating the identity key for every device including the phone, which breaks every existing contact's safety number simultaneously.
THE NUMBERS

Model concurrent sends as a birthday-style collision problem over a send window w: with k devices each independently able to send within the same w-millisecond window (typical inter-device clock skew plus network jitter, easily 50–300 ms on real mobile + Wi-Fi links), the probability that at least two devices advance the chain in the same window rather than serially is non-negligible for any active multi-device user texting from both a phone and a laptop in the same conversation — a scenario, not an edge case. A production messenger cannot ship a design whose failure mode is "sometimes silently reuses key material," no matter how rare "sometimes" is, because the AEAD's security proof assumes non-reuse unconditionally, not probabilistically.

So sharing one ratchet across devices is out — not because it is inefficient, but because it is not a well-formed cryptographic object once two writers exist. The only sound fix is to stop pretending there is one session at all: give each device its own identity and its own ratchet per contact. §5 walks the candidates, including that one, and shows what each still costs.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three shapes for "many devices," one identity

Step through the three real candidates the way the WhatsApp and Signal engineering teams effectively had to. Each stage compares the same conversation — Alice, from her laptop, sending to Bob — under a different architecture.

Candidate architectures for multi-deviceSTEP-BY-STEP

Why "identity = set of devices" wins

Give every device — phone, laptop, tablet — its own long-term identity key pair, its own signed prekey, its own batch of one-time prekeys, and let it run independent Double Ratchet sessions with every device of every contact, established via ordinary X3DH exactly as chapter 8 of the Signal spec describes for a single device. There is no shared mutable ratchet, so §4's race cannot occur — each device is the sole writer of its own chains. There is no shared long-term private key leaving a phone's secure storage, so compromising a laptop compromises exactly that laptop's sessions, nothing upstream and nothing on other devices. This is precisely the model Signal's own Sesame algorithm formalizes, and it is the model WhatsApp's 2021 multi-device architecture adopted.

THE CLINCHING ARGUMENT: NO SHARED WRITABLE SECRET, ANYWHERE

The instant you accept "one identity key + one ratchet per device pair," every device's cryptographic state becomes fully local and single-writer again — exactly the invariant Double Ratchet requires. The problem of "how do multiple devices act as one identity" is pushed entirely into a different layer: who is allowed to claim membership in Alice's device set, and how does everyone else find out. That is a much more tractable problem — it's a signed-list distribution problem, not a shared-secret problem — and §7 builds it.

ARC 06 · WHY THAT STILL COSTS

Per-device sessions are correct — and naively applied, expensive and exploitable

Adopting "one Signal session per device pair" is the right direction, but stopping there ships a system with four unresolved bills, each of which §7–§8 exists to pay down:

  • Fan-out multiplies, and it multiplies on both sides. A message from a user with N devices to a contact with M devices requires N×M device-pair sessions in the general case — and the sender must also encrypt to their own other devices (so their laptop shows messages sent from their phone), adding N×(N−1) more. For Alice with 3 devices messaging Bob with 4 devices: 3×4 = 12 cross sessions, plus 3×2 = 6 self-sessions, an 18-way fan-out for what used to be one ciphertext. Chapter 6's group fan-out math and this chapter's device fan-out math compose multiplicatively for a multi-device user in a group.
  • The device list is now security-critical, and naively it's just server-asserted state. If Bob's device list is whatever the server says it is, a compromised or coerced server can inject a device Bob never linked, and Alice's client will happily open a fresh X3DH session and start encrypting to it — a textbook device-injection attack. Nothing in "just add per-device sessions" prevents this by itself.
  • A newly linked device has no history, and history is exactly the thing E2E encryption makes hard to backfill. The server never had plaintext to hand over. Someone has to transfer potentially gigabytes of encrypted conversation history to a brand-new device, over a channel that must itself be end-to-end secure, without the server ever seeing a key that unlocks it.
  • Cross-device consistency has no free lunch. Read receipts, deletions, and "seen on which device" state must now propagate between a user's own devices — there is no shared database row to update; every such sync is itself an encrypted message to your own device set, ordered by nothing more authoritative than whatever each device's local clock and per-sender counters say.
THE HONEST TRADE

None of these four costs is optional to solve — skip device-list authentication and you've built a government-request backdoor by omission; skip history sync and multi-device is unusable (a new laptop opens to an empty chat list); skip fan-out engineering and message send latency scales with your most over-provisioned contact's device count. §7 is the architecture that pays all four bills; §8 is the wire formats and algorithms that make the payment cheap enough to run at WhatsApp's scale.

THE DELIBERATE ASYMMETRY

Exactly one device is designated primary — historically the phone — and it alone can authorize new companions by signing their identity key. Companions are cryptographically equal once linked (any of them can send and receive independently, and, more recently, act as a companion phone too), but the authorization chain is not symmetric: every device's membership in the set traces back to a signature by the primary's identity key. That asymmetry is what makes the device list auditable at all — without a single signing root, "who is allowed to add a device" has no answer.

ARC 08 · INTERNAL IMPLEMENTATION

Wire formats, state machines, and the fan-out algorithm

Three mechanisms carry the whole design: (a) the signed device-list structure and how a sender uses it, (b) the QR/Noise pairing handshake that admits a new device, and (c) the fan-out encryption loop and its cost, which you can drive live with the sliders below.

(a) The device list: the object every send starts with

Before encrypting to a contact, a client must resolve that contact's current device set. Model it as a signed structure the server stores and serves, but cannot forge, because every entry is signed by the owning primary's identity key — the server is a distribution channel, not an issuer:

TypeScriptdevice_list.ts — the structure every sender fetches and verifies
interface DeviceEntry {
  deviceId: number;              // small int, stable per device
  registrationId: number;         // disambiguates re-registrations
  identityKeyPub: Uint8Array;     // this device's OWN long-term public key
  signedPreKey: SignedPreKey;      // rotated periodically, signed by identityKeyPub
  addedAt: number;
}

interface DeviceList {
  owner: string;                   // account identifier
  devices: DeviceEntry[];
  version: number;                 // monotonic — every add/remove bumps it
  signature: Uint8Array;           // Sign(primaryIdentityKeyPriv, hash(devices, version))
}

// Every sender runs this before the FIRST message to a contact in a session,
// and again whenever the contact's list version changes.
function resolveRecipientDevices(contact: string): DeviceEntry[] {
  const list = server.fetchDeviceList(contact);
  if (!verify(list.signature, list.owner.knownPrimaryIdentityKey(), hash(list.devices, list.version)))
    throw new Error("device list signature invalid — treat as compromised");
  if (list.version > localCache.lastSeenVersion(contact))
    ui.surfaceSafetyNumberChangeWarning(contact);   // ← the user's ONLY defense against a lying server
  return list.devices;
}
WHY SIGN THE LIST INSTEAD OF TRUSTING THE SERVER TRANSPORT

The transport to the server is already encrypted — WhatsApp's client-server link runs the Noise Protocol Framework (documented in WhatsApp's security whitepaper). But transport security only protects data in flight to a server the client already trusts to relay bytes — it says nothing about whether the server told the truth about whose devices are in the list. Signing the list with a key the server never possesses is what makes a subpoenaed, compromised, or malicious server unable to add a silent listener: it can lie about the list, but it cannot forge a valid signature over a lie, and clients that verify will show the safety-number change warning instead of silently accepting a new device. §15's simulator lets you inject exactly this attack and watch the warning fire — or, if you disable verification, watch it silently fail to.

CONSISTENCY WITHOUT A GLOBAL CLOCK

Read receipts and deletions must reach every one of the user's own devices, and there is no shared database row to update — each device is a separate Signal peer, even to its owner's other devices. The practical answer is a self-sync channel: a message addressed to your own device set (using exactly the per-device sessions from (c)) carrying an ordered, per-sender-device monotonic counter — "message X, read at local time T on device D." Ordering across devices is therefore causal, not global: a device applies sync events in the order its own counters imply, and UI-level conflicts (marked read on phone after already being marked unread on laptop) are resolved last-write-wins on a per-conversation basis, not with a Lamport clock spanning the whole account — a deliberately weaker but tractable guarantee, the same trade every offline-tolerant sync system makes. A device that has been offline for months returns with badly stale ratchet state: if the number of undelivered messages on any chain exceeds the skipped-message-key cache bound (Signal implementations typically cap this, commonly on the order of a low thousand keys), the session cannot catch up and must be re-established from scratch via a fresh X3DH handshake rather than replayed — §15 lets you force exactly this.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before instrumenting a client

The device-set model's performance envelope, derived rather than measured:

  • Per-message CPU: O(N×M + N×(N−1)) AEAD encryptions, where N is the sender's device count and M the recipient's — each an independent Double Ratchet step (a KDF chain advance plus an AEAD seal), cheap per-op (microseconds) but linear in a quantity that is no longer 1.
  • Per-message bytes on the wire: roughly proportional to the same N×M + N×(N−1) count — each device gets its own ciphertext envelope, though implementations can share a single symmetric payload key wrapped per-device (a "sender-key"-like optimization borrowed from chapter 6's group fan-out) to avoid re-encrypting the full plaintext body per device while still needing one small per-device wrap.
  • Network round trips for a brand-new device pair: one prekey-bundle fetch (X3DH) per new device pair before the first send — amortized to zero afterward since the ratchet then runs statelessly forward, but a real cost the very first time a user messages a contact who just linked a new device.
  • Battery/radio cost on mobile: every additional linked device your contacts add costs YOUR phone extra CPU cycles (more encryptions) and extra radio/wake time (more bytes to transmit) for messages you send them — a cost that is invisible to the contact who added the device and entirely borne by everyone who messages them. This externality is a big part of why device caps exist at all.
  • Memory: one Double Ratchet state (root key, 2 chain keys, skipped-key cache) per device pair, held per active conversation — for a heavy user with hundreds of contacts each averaging 2 devices, that's low hundreds of small session objects, not a memory problem on a modern phone, but a real one on constrained IoT-class hypothetical clients.

MODEL, NOT MEASUREMENT

The curve is a first-principles sketch — sessions scale as N×M + N×(N−1), bytes scale similarly except the shared-payload-key toggle collapses the body cost to O(1) and leaves only O(N×M) small key-wraps. WhatsApp's exact production numbers for device-linking limits and per-message overhead are not public; treat the specific curve shape as a derived estimate, not a disclosed benchmark. The point that is load-bearing and published-record-consistent: device fan-out is why WhatsApp historically capped companion devices at four, and why "how many devices can one identity have" is a real capacity-planning question, not a cosmetic UI limit.

ARC 11 · REAL-WORLD PRODUCTION

What shipping this actually looked like

Milestone 1: the multi-device beta (2021)

WhatsApp's 2021 multi-device beta was explicitly framed by the engineering team as removing the phone as a single point of failure for linked devices, while preserving end-to-end encryption on every device — the two requirements this chapter derives from first principles in §1. The beta rolled out gradually, gated per account, a standard pattern for a change this deep in the trust model: any correctness bug in device-list verification or session establishment is a confidentiality bug, not a crash, so the blast radius of a bad rollout is qualitatively different from a UI feature flag.

Milestone 2: raising the device ceiling and dropping the phone dependency

Early multi-device still leaned on the phone periodically for certain operations; subsequent iterations moved toward linked devices continuing to function even if the phone stays offline for extended periods (WhatsApp's public help documentation describes a multi-week grace window before a companion is unlinked for phone inactivity — treat the exact current threshold as subject to change and consult current documentation rather than this chapter for an operational number). The direction is the important, durable fact: each iteration reduced how much the primary phone's liveness mattered, converging toward the "no phone proxy" property in this chapter's title.

Milestone 3: companion phones

WhatsApp progressively extended linking to allow a second phone as a companion device rather than only desktop/web/tablet clients — collapsing the historical distinction between "the phone" (special, primary) and "a companion" (secondary, capped) toward a more uniform device-set model closer to what Signal's Sesame algorithm already treats symmetrically. This is consistent with, and a natural next step from, the architecture derived in §7: once every device carries its own full identity and session set, there is no remaining cryptographic reason one of them must be a phone.

Milestone 4: scale context

WhatsApp crossed 2 billion users around 2020 and has published figures in the tens of billions of messages handled daily across its history; multi-device shipped into that installed base incrementally and reversibly (per-account gating, ability to roll back a given account to single-device semantics during the beta) — the same operational discipline chapter 1 of this course's sibling PostgreSQL material calls "boring on purpose" applied to a cryptographic migration instead of a process model.

WHAT ISN'T PUBLIC — LABELED AS SUCH

WhatsApp has not published the exact internal names, storage engine, or precise current device caps and grace-period numbers referenced above with the same rigor as the Signal Protocol's own public specification. Where this section states a number or threshold, treat it as best-available public reporting or product documentation at time of writing, not a guaranteed-stable engineering constant — unlike X3DH, Double Ratchet, and the Sesame algorithm, which are precisely specified public documents.

TypeScriptfanout-encryptor — the send-time algorithm (§8c, made concrete)
async function sendMessage(plaintext: Uint8Array, contact: string) {
  const myDevices = await localDeviceList();               // includes THIS device
  const theirDevices = await resolveRecipientDevices(contact); // §8a — verified & signature-checked
  const targets = [
    ...theirDevices,
    ...myDevices.filter(d => d.deviceId !== thisDevice.id)   // so MY other devices see my own sent message
  ];

  for (const device of targets) {
    let session = sessionStore.get(device.deviceId);
    if (!session) {
      // first message ever to this specific device: run X3DH once
      session = await x3dhInitiate(device.identityKeyPub, device.signedPreKey, device.fetchOneTimePreKey());
      sessionStore.put(device.deviceId, session);
    }
    const ciphertext = doubleRatchetEncrypt(session, plaintext);   // §4's single-writer chain, now safe: ONE session per device pair
    await server.enqueue(device.deviceId, ciphertext);
  }
}

   // the blob store never sees bundleKey, so it never sees plaintext, ever.
  const session = sessionStore.get(newDevice.deviceId);
  const keyMsg = doubleRatchetEncrypt(session, encode({ blobRef, bundleKey }));
  await server.enqueue(newDevice.deviceId, keyMsg);
}
WHY THE ENGINEERS CHOSE THIS SHAPE

1. Reuse published primitives instead of inventing new cryptography. X3DH, Double Ratchet, and Sesame already solve "establish and manage per-device sessions" for Signal; adopting the same shapes means WhatsApp inherits a reviewed, public security analysis instead of fielding a bespoke protocol under load. 2. Push trust decisions to signatures, not transport. Exactly like postmaster judging children by exit status (chapter 1 of the PostgreSQL course) rather than inspecting shared memory, a client judges a device list by its signature, not by which server happened to answer — the server is deliberately kept unable to assert facts about identity. 3. Reuse the blob-plus-key-delivery pattern from chapter 7 rather than building a bespoke history channel. History sync is not a new problem — it's "transfer a large encrypted object and deliver its key over an already-trusted channel," which chapter 7 already solved for media attachments. The same shape, applied to a zip of chat history instead of a photo.
