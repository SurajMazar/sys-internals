ARC 01 · THE PROBLEM

Isolation and connectivity are opposites, and a container needs both

Chapter 2 isolated a process's view of the world: its own PID tree, its own hostname, its own mount table, its own IPC namespace. Networking is the namespace where isolation is most obviously in tension with the point of running the workload at all. A web server in a container that cannot accept a single inbound TCP connection, or reach a database over the network, is isolated so thoroughly it is useless.

Unpack what "network isolation" has to mean for a container runtime to be usable in practice:

  • Private address space. Two containers on the same host must be able to both bind port 80 without conflict — which is impossible if they share one network stack.
  • Private routing and firewall state. A container's own iptables/nftables rules, routing table, and ARP cache must not be the host's — otherwise one container's firewall change is every container's firewall change.
  • Yet the host must still reach it, and it must still reach the host and the internet — deliberately, through a boundary the operator controls, not accidentally through shared kernel state.
  • The isolation must be real, not cosmetic. chroot-style "just hide it" isn't available for a network stack — sockets, routes, and interfaces are kernel objects with global names (eth0, port 80) that two independent processes cannot share without collision.

Linux's answer is the network namespace (CLONE_NEWNET, merged in kernel 2.6.29, 2009 — notably four years after the mount namespace and years before it was production-hardened): give each isolated context its own complete copy of every network-facing kernel data structure — interface list, routing tables, ARP/neighbor tables, iptables/nftables rule sets, /proc/net, and its own socket namespace so two namespaces can each own TCP port 80. The catch, and the entire subject of this chapter: a freshly created network namespace is not connected to anything. Deriving how it gets connected — and what that costs — is what Docker's docker0 bridge and Podman's netavark-managed bridges are both, at bottom, doing.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Every "container networking" feature you will ever configure — port publishing, user-defined bridge networks, container-to-container DNS, --network host, service meshes sitting inside containers — is built on exactly two primitives introduced in this chapter: the network namespace (the isolation boundary) and the veth pair (the only way to cross it while keeping it a boundary). Chapter 13 goes wide (CNI, netavark, macvlan, overlay networks); this chapter goes deep on the two things underneath all of them. Chapter 4, next, revisits isolation from a different angle — who is allowed to create a network namespace and configure it at all when the calling process isn't root on the host.

DEEP CONTEXT · WHY VETH CAME FIRST

The veth driver (drivers/net/veth.c) actually predates full network-namespace support — it landed in the 2.6.24-ish era of early namespace prototyping specifically because the kernel developers knew that virtualizing the network stack would be worthless without a way to connect two of them. A namespace that isolates but can never be wired to anything is a curiosity, not infrastructure. Design the boundary and the bridge across it together — the same lesson recurs in every later chapter about attaching an isolated thing to a host (overlayfs's lowerdir/upperdir split, chapter 6; the whole of chapter 13's networking models).

ARC 03 · NAIVE SOLUTION

Attempt #1: just call unshare(CLONE_NEWNET) and go

Derive it honestly, the way you'd derive it at a whiteboard before reading any container-runtime source. You know namespaces isolate kernel state (chapter 2). Networking is kernel state. So: create a network namespace, exec the workload inside it, done?

ARC 04 · WHY IT FAILS

An empty network namespace is provably unreachable — quantified

This isn't a configuration oversight to patch with a flag. Trace exactly what network namespace creation copies versus what it deliberately leaves empty, per the kernel's copy_net_ns() (net/core/net_namespace.c):

  • Interfaces: only loopback, and it starts down. copy_net_ns() calls loopback_dev creation for the new struct net, but does not bring it up — that's userspace's job (ip link set lo up), because bringing an interface up is a configuration decision, not a namespace-creation side effect. No physical or virtual NIC is ever auto-created in a new namespace; the kernel has no way to know which one you'd want, and giving it a real NIC would mean stealing that NIC from every other namespace, including the host's.
  • Routing table: empty except a loopback route. There is no default route, so any packet destined off-loopback returns ENETUNREACH ("Network is unreachable") before a single byte leaves the process — this is what the naive program actually hits.
  • ARP/neighbor table: empty. Nothing to resolve to, because there is no L2 segment reachable yet.
  • iptables/nftables rules: independent, defaulting to ACCEPT-everything on the (nonexistent) traffic. A fresh namespace's firewall being wide open is irrelevant when there is no path for packets to travel.
THE NUMBERS: ZERO REACHABLE HOSTS

Quantify the naive attempt's connectivity precisely: it can reach exactly one address, 127.0.0.1, and only after a second syscall the naive program never issued (ip link set lo up, i.e. an RTM_SETLINK netlink message) — loopback is present but administratively down at creation. Every other destination, including the namespace's own host machine one fork() away, is unreachable — not slow, not filtered, topologically absent. There is no tuning knob inside the namespace that fixes this: reachability has to be built from the outside, by something with access to both namespaces at once.

So the missing piece is a bridge between the isolated namespace and the world outside it — one endpoint that lives in each namespace and forwards frames across the boundary. Linux gives you exactly one primitive purpose-built for that: the veth pair.

ARC 05 · BETTER SOLUTION

veth: two interfaces that are secretly one wire

A veth pair (ip link add veth-host type veth peer name veth-ctr) creates two network interfaces at once, permanently linked at the kernel level: whatever one transmits, the other receives, as if a physical Ethernet cable connected two NICs. Nothing is copied or queued through userspace — the veth driver (drivers/net/veth.c) hands an skb (socket buffer) directly from one interface's transmit path to the peer's receive path inside the kernel. Critically, each end of the pair can live in a different network namespace — that's the entire trick. Move one end into the container's namespace, leave the other in the host's (or a bridge's) namespace, and you have a wire crossing the isolation boundary without breaking it: the container still can't see the host's routes, ARP table, or other interfaces — it only sees its own end of one cable.

THE KEY INSIGHT

A veth pair only gives you a point-to-point link — good enough for exactly one container. The moment you have two containers that both need to reach the internet and each other, point-to-point links stop scaling: you'd need a full mesh of veth pairs, one per container-pair, and re-cabling every time a container starts or stops. The fix borrows a decades-old networking answer: don't wire hosts to each other, wire them all to a switch. Linux's software switch is the bridge device, and that's exactly what docker0 and Podman's netavark bridges are.

ARC 06 · WHY THAT STILL HURTS

One veth pair per container doesn't scale — and the bridge has its own bill

Introducing a bridge fixes the N² cabling problem, but it isn't free, and understanding its costs up front explains almost every default in Docker's and Podman's networking stacks:

  • The bridge is itself a Linux device with an IP — it must own an address in the container subnet (conventionally the .1 address, e.g. 172.17.0.1) to act as the containers' default gateway. That's one more thing to allocate, track, and avoid colliding with existing networks — the exact cause of the "Docker's 172.17.0.0/16 collides with our corporate VPN" incident in §11.
  • Every frame between containers now takes an extra hop through kernel bridge code — L2 forwarding table lookups, and, if net.bridge.bridge-nf-call-iptables=1 (the default your container runtime sets), a full netfilter/iptables traversal per bridged frame, not just per routed packet. This is deliberate — it's what lets you firewall container-to-container traffic at all — but it is measurable overhead versus a bare veth pair (§10 quantifies it).
  • Outbound-to-the-internet still doesn't work by itself. The bridge only solves L2 reachability between containers and the host. Containers' IPs (typically RFC1918 private addresses like 172.17.0.2) are not routable on the internet — something must rewrite the source address to the host's routable IP. That something is NAT via iptables MASQUERADE, another piece of state the runtime must install and keep correct.
  • Inbound is the mirror problem, worse. A client outside the host has no route to 172.17.0.2 at all. Publishing a port means installing a destination NAT (DNAT) rule that rewrites "host IP, port 8080" to "container IP, port 80" — port publishing is not a runtime feature, it's an iptables rule, and §8 shows you the exact one.
THE HONEST ADMISSION

Every mainstream container network on a single host — Docker's default bridge, Docker user-defined bridge networks, and Podman's netavark bridge — is this exact stack: netns + veth + Linux bridge + iptables/nftables NAT. There is no fourth primitive. Everything that looks different between the two engines (bridge naming, DNS resolution, per-network isolation defaults) is policy layered on the same four mechanisms, and §9 makes the comparison precise rather than hand-wavy.

WHO CREATES ALL OF THIS, AND WHEN?

Not runc or crun. The OCI runtime's job (chapter 9) is narrow: given config.json naming a network namespace, call clone()/setns() to place the container's process into it. The veth pair, bridge attachment, IP assignment, and iptables rules are installed by a separate networking layer — Docker's libnetwork (bridge driver) or Podman's netavark — invoked after the namespace exists but before the container's main process starts, via the OCI runtime's hook mechanism. §13 shows the exact source-level call sequence.

ARC 08 · INTERNAL IMPLEMENTATION

The real files, the real rules, the real numbers

Three pieces: (a) the namespace + veth lifecycle in terms of real files and netlink operations, (b) the bridge's forwarding behavior, (c) the exact iptables chain that makes a published port work.

(a) Namespace and interface state, byte for byte

WHY THIS SHOWS UP IN PRODUCTION AT SCALE

Each container attach is a fixed handful of netlink calls (create veth pair, move one end into the netns, rename it, assign an IP, add a default route, attach the host end to the bridge) plus one or more iptables rule insertions. Both scale linearly per container — but iptables rule evaluation is a linear scan of the chain per packet by default, so a host running hundreds of containers with per-container DNAT/isolation rules pays a real per-packet cost that grows with container count. This is the concrete, measurable reason nftables (hashed rule sets, used by newer Docker/Podman iptables backends) and eBPF-based dataplanes exist — same architecture, faster rule lookup.

(b) The bridge: a real, if simple, Ethernet switch

The Linux bridge (net/bridge/) is not a NAT device and does not route — it operates at L2, maintaining a forwarding database (FDB) of MAC-address-to-port mappings learned by inspecting source addresses on incoming frames, exactly like a physical switch. bridge fdb show lists it. A frame destined for an unknown MAC is flooded to every port except the one it arrived on; once the bridge learns where a MAC lives, traffic to it is forwarded to that single port only. This is why two containers on the same bridge can reach each other directly, at full L2 speed, with zero NAT involved — NAT only enters the picture when traffic needs to cross into or out of the bridge's subnet.

Because DNAT happens in the PREROUTING chain — evaluated before most host firewall tools' rules, which typically live in the INPUT chain or a separate ufw-managed table — a container engine's port-publishing rule can make a container reachable from the internet even when a host firewall tool reports the port as blocked. ARC 10 · PERFORMANCE & SECURITY CHARACTERISTICS

What isolation costs, and what it exposes

Performance first. A veth pair itself is close to free — it's a pointer hand-off inside the kernel with no copy. The costs accumulate in what surrounds it:

  • Bridge + NAT (rootful default): near-native throughput — typically 90–98% of host-network throughput on a 10G+ NIC — because packets still traverse real kernel network-stack code paths, just with one extra L2 hop and a conntrack lookup for established NAT flows.
  • --network host (no namespace at all): literally 100% by definition — zero isolation, the container's process binds host sockets directly, which is precisely why it's a deliberate opt-out with real security consequences, not a free lunch.
  • Rootless via slirp4netns: a userspace TCP/IP stack reading/writing a TUN device — every packet crosses the kernel/userspace boundary twice more than the bridge path, often costing 50–70% of throughput versus rootful bridge networking on older setups, and adding real, measurable per-packet latency.
  • Rootless via pasta (Podman's newer default on supporting systems): avoids a full userspace TCP stack by translating packets at the socket layer instead of emulating a NIC end to end, closing most of the gap back to near-native — the concrete architectural reason it's replacing slirp4netns as the default.

Security surface, in the same order the mechanism was introduced:

  • Network namespace boundary: genuinely strong — a process cannot see or affect another namespace's sockets, routes, or firewall rules without an explicit fd (setns()) or a wired link (veth) into it. This is a real kernel-enforced boundary, not policy.
  • The bridge is a shared L2 segment — and shared L2 segments have always been vulnerable to classic L2 attacks: ARP spoofing, and — the real CVE covered in §11 — spoofed IPv6 Router Advertisements from one container redirecting another container's default route. Putting multiple tenants' containers on one bridge without additional controls reintroduces problems the networking world solved (badly) decades ago with VLANs and port security.
  • iptables/nftables NAT and DNAT rules are host-wide, ordering-sensitive state — a container engine inserting rules ahead of a firewall tool's own chain is, from a security-review standpoint, a privileged write to shared kernel state, exactly the kind of thing chapter 7's capability model (CAP_NET_ADMIN, CAP_NET_RAW) exists to gate.
  • Rootless networking's smaller attack surface: because slirp4netns/pasta run as an unprivileged process and never touch the host's real interfaces or global iptables rules, a compromised rootless container's networking blast radius is architecturally smaller — it can't rewrite host NAT rules it never had permission to write in the first place. This is chapter 4's rootless story showing up concretely in the networking layer.
ARC 11 · REAL-WORLD INCIDENTS

Three incidents this chapter's mechanism explains completely

Incident 1: "Docker bypasses my firewall" (moby/moby#4737, still relevant a decade later)

Operators enable ufw or a hand-rolled iptables policy, block inbound traffic to a port, then run a container publishing that exact port with -p — and traffic gets through anyway. §8(c) is the entire explanation: Docker (and Podman, identically) install DNAT rules in the PREROUTING chain, which the kernel evaluates before ufw's rules in INPUT even see the packet — because a DNAT'd packet is, by the time INPUT would apply, already destined for a bridge interface and a container IP, following a completely different netfilter path (FORWARD, not INPUT). This is not a bug being silently tolerated; it is documented, debated for years, and the practical fix is operating at the level the engine actually operates at — engine-native network policies, or firewalling at a perimeter the container host doesn't control iptables for (a cloud security group, a separate firewall appliance) — rather than assuming host-level firewall tools see every packet.

Incident 2: CVE-2020-13401 — spoofed IPv6 Router Advertisements between containers

Docker's user-defined bridge networks enable IPv6 by configuration in some setups without also enabling the bridge-level protections that would prevent one container from sending Router Advertisement (RA) or Neighbor Discovery Protocol traffic to another. Because the bridge is a genuine shared L2 segment (§10), a malicious or compromised container on the same bridge network could send crafted ICMPv6 RA messages, causing sibling containers to install a bogus default gateway or route — a textbook L2 man-in-the-middle, executed entirely through the mechanism this chapter derived, with no exploit of the namespace or veth code itself. The fix (RA-guard-equivalent bridge configuration, disabling unneeded IPv6 router-solicitation acceptance on container interfaces) is a policy patch on top of the same architecture, not a redesign — confirming that the primitive is sound and the exposure was in default configuration.

Incident 3: "The container platform can't reach the VPN" — the 172.17.0.0/16 collision

Docker's historically fixed default bridge subnet, 172.17.0.0/16, and similarly-sized default pools used by other engines, silently collide with corporate networks or VPN-assigned CIDRs that also live in RFC1918 space. When that happens, the host's routing table has to choose between "route to the Docker bridge" and "route to the VPN," and whichever route is more specific or installed later wins — silently breaking either container networking or VPN connectivity, often intermittently as VPN routes come and go. This isn't a defect in veth or bridge mechanics; it's the operational cost of §6's observation that the bridge needs a real, globally-unique-enough subnet, and a fixed default can't know what else is on your network. Both engines now support configuring the default subnet/pool explicitly for exactly this reason — the fix is operational awareness of a namespace/bridge design decision, not a networking bug.

First, the shape of what any network plugin must implement — CNI's contract, in the plugin binary's entrypoint, simplified but structurally faithful:

Gobridge.go — cmdAdd(), the CNI ADD operation
func cmdAdd(args *skel.CmdArgs) error {
    n, cniVersion, err := loadNetConf(args.StdinData)  // bridge name, subnet, MTU

    // 1. Ensure the bridge exists on the HOST side (idempotent).
    br, err := setupBridge(n)                        // netlink.LinkAdd(&Bridge{...})

    // 2. Open the container's netns by the path the runtime handed us
    //    (e.g. /proc/<pid>/ns/net) — this is the file from §8(a).
    netns, err := ns.GetNS(args.Netns)

    // 3. Create the veth pair, then move ONE end into that netns and
    //    rename it (conventionally to "eth0" from the container's view).
    hostIface, contIface, err := setupVeth(netns, br, args.IfName, n.MTU)

    // 4. Ask the configured IPAM plugin (host-local, dhcp, etc.) for an
    //    address, then assign it and a default route INSIDE the netns.
    result, err := ipam.ExecAdd(n.IPAM.Type, args.StdinData)
    err = netns.Do(func(_ ns.NetNS) error {
        return ipam.ConfigureIface(args.IfName, result)
    })

    return types.PrintResult(result, cniVersion)
}

    // and RTM_SETNS netlink messages.
    let (host_veth, container_veth) =
        create_veth_pair(&bridge, netns_path, &config.container_iface)?;

    // Install the DNAT/MASQUERADE rules for this container directly —
    // netavark owns nftables/iptables plumbing itself; no libnetwork.
    configure_nat_and_port_forwarding(&config, &host_veth)?;

    // Register the container's name + IP with aardvark-dns so sibling
    // containers on this network can resolve it (§9's DNS row).
    register_with_aardvark(&config)?;
    Ok(())
}

Third, the exact netfilter rule both stacks converge on when a port is published — hand-writeable, and worth typing once so it stops being a black box:

iptablesthe DNAT rule a published port actually installs
# container has address 172.17.0.2, listens on 80;
# host publishes it as 0.0.0.0:8080 -> 172.17.0.2:80
iptables -t nat -A DOCKER \
  -d 0/0 -p tcp --dport 8080 \
  -j DNAT --to-destination 172.17.0.2:80

# and the corollary that makes the REPLY path work: traffic FROM
# the container back to the internet gets the host's routable
# source address, or the reply would never find its way home.
iptables -t nat -A POSTROUTING \
  -s 172.17.0.0/16 ! -o docker0 \
  -j MASQUERADE
WHY IT WAS BUILT THIS WAY — TWO CHOICES TO STEAL

1. Separate the isolation primitive from the policy engine. The kernel's network namespace and veth driver know nothing about bridges, DNS, or Docker/Podman — they're generic. Both engines build container-specific policy (naming, DNS, port publishing) as a layer entirely in userspace on top of generic kernel primitives, which is exactly why two independently-developed engines converge on the same four mechanisms: there was only ever one sane way to use them. 2. Do the networking setup between namespace creation and process start, as a hook — not inside the runtime. This keeps runc/crun genuinely runtime-agnostic (chapter 9): they don't need to know what a bridge is, only that "run this executable with this netns path" is a valid pre-start action, which is also what lets entirely different networking stacks (CNI, netavark, Cilium's eBPF dataplane) plug into the same OCI runtimes unmodified.
