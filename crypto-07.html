APPLIED CRYPTOGRAPHY · CHAPTER 07

AEAD: GCM, Poly1305 &
the Encrypt-then-MAC Principle

Chapter 5 gave you confidentiality (block cipher modes). Chapter 6 gave you integrity (MACs, HMAC). Neither alone is a usable cryptosystem, and — this is the part most engineers learn the hard way — simply running both is not automatically safe either. There are exactly three ways to combine an encryption scheme with a MAC, and cryptographers proved in 2000 that only one of them is safe for arbitrary secure primitives. This chapter derives that result, then builds the modern answer: a single primitive, Authenticated Encryption with Associated Data (AEAD), that fuses encryption and authentication so the composition mistake becomes structurally impossible to make. You will implement the actual GF(2128) field arithmetic behind GCM's authentication step in JavaScript, and use it to run the exact attack — nonce reuse — that breaks GCM's authentication guarantee completely.

ARC 01 · THE PROBLEM

"Just use both" is not a security architecture

By the end of chapter 6 you have two working, independently-secure tools: a block cipher mode (say, AES-CBC or AES-CTR) that gives you confidentiality — ciphertexts leak nothing about plaintext content — and HMAC, which gives you integrity — nobody without the key can produce a MAC for a message they didn't see. A natural next question follows immediately: if I need both properties on the same message, which every real protocol does, do I just... use both?

The honest answer is: it depends entirely on how you combine them, and two of the three obvious ways to do it have been the root cause of real, exploited vulnerabilities in deployed cryptographic protocols. Given a plaintext P, a cipher key Ke, and a MAC key Km, there are exactly three generic compositions:

  • MAC-then-Encrypt (MtE): compute tag = MAC(Km, P), then encrypt P || tag together. This is what SSL/TLS did with its CBC cipher suites for over a decade (RFC 5246 §6.2.3.2) — and it is exactly the shape that Serge Vaudenay's 2002 padding-oracle attack exploits, which chapter 10 dissects byte by byte.
  • Encrypt-and-MAC (E&M): compute C = Encrypt(Ke, P) and separately tag = MAC(Km, P) (over the plaintext, not the ciphertext), and send both. This is what the original SSH binary packet protocol did.
  • Encrypt-then-MAC (EtM): compute C = Encrypt(Ke, P), then tag = MAC(Km, C) — the MAC covers the ciphertext, not the plaintext.

These look interchangeable at a glance — same two primitives, same two keys, same total work — which is precisely why the mistake is so easy to make and so hard to notice in a code review. This chapter exists because the difference is not stylistic. It is the difference between a scheme with a machine-checked security proof for any secure cipher and any secure MAC, and a scheme that is only as safe as the specific primitives you happened to plug in — and even then, often isn't.

There is a second gap naive composition can't close cleanly: real protocols need to authenticate data that must stay visible — a TLS record's sequence number, an IP packet's header, a database WAL record's length field. You cannot encrypt these (the receiver needs to read them before it can even locate the ciphertext), yet an attacker who can flip a header bit undetected can often redirect, replay, or truncate a message regardless of how well the payload itself is protected. A generic "cipher plus MAC" toolkit has no natural slot for "authenticate this, but don't encrypt it." Solving both problems at once — safe composition, and mixed encrypted/visible authenticated data — is exactly what AEAD (Authenticated Encryption with Associated Data, a term and formal security definition introduced by Phillip Rogaway in 2002) was built to do.

WHY THIS MATTERS FOR THE NEXT 9 CHAPTERS

Every protocol from here forward — TLS 1.3's record layer (chapter 13), the key-derivation material feeding it (chapter 8), even the padding-oracle post-mortems (chapter 10) — is explainable as either "used an AEAD correctly" or "didn't have one yet and paid for it." AES-GCM and ChaCha20-Poly1305, the two ciphers this chapter builds from first principles, are the ones you will use in production for the rest of your career unless you have a very specific reason not to.

DEEP CONTEXT · WHY GCM AND NOT SOMETHING ELSE

NIST's competition-style processes gave us Rijndael (chapter 3) and SHA-3, but GCM was never put through an open multi-year competition — David McGrew and John Viega designed it at Cisco specifically to meet an urgent, concrete need: 802.1AE (MACsec) and IPsec needed a high-throughput AEAD mode that could run at line rate in hardware, and CCM (the 2003-era alternative, built from CBC-MAC and CTR) requires two passes over the data because CBC-MAC cannot process a block until it has fully processed every block before it. GCM's authentication step, GHASH, is parallelizable and pipelines with CTR encryption in a single pass — the engineering constraint, not a cryptanalytic one, is why GCM won the standardization slot in NIST SP 800-38D (2007).

ARC 03 · NAIVE SOLUTION

Attempt #1: MAC-then-Encrypt, the "obvious" answer

Put yourself in the position of a protocol designer in the mid-1990s who has read chapters 5 and 6 (in spirit) and needs both properties. The most natural thing to write is: authenticate the message first, then encrypt the whole bundle so an eavesdropper can't even see the tag. This is precisely the reasoning that produced TLS's CBC cipher suites, and it is worth writing out exactly as an engineer of that era would have:

pseudocodenaive_send.c — MAC-then-Encrypt, the TLS 1.0–1.2 CBC-suite shape
bytes naive_secure_send(bytes plaintext, key Ke, key Km, bytes iv)
{
    /* Step 1: authenticate the DATA as the caller wrote it. Feels obviously
     * correct — "prove nobody tampered with what I actually meant to send." */
    bytes tag = HMAC_SHA256(Km, plaintext);           /* chapter 6 */

    /* Step 2: PKCS#7-pad plaintext||tag to a multiple of the block size,
     * then encrypt the whole bundle with CBC so an eavesdropper sees
     * neither the message NOR the tag. */
    bytes bundle = pkcs7_pad(plaintext || tag, 16);
    bytes ciphertext = AES_CBC_Encrypt(Ke, iv, bundle);     /* chapter 5 */

    return iv || ciphertext;         /* looks airtight: encrypted AND authenticated */
}

Nothing here looks wrong. Both primitives are the ones you were told to trust; the tag is inside the ciphertext where nobody can see it without the key; the whole bundle is padded and encrypted correctly per chapter 5's rules. This exact reasoning is why RFC 5246 (TLS 1.2) specifies MAC-then-Encrypt for its CBC-based cipher suites, and TLS 1.0 shipped in 1999 with essentially this construction. It took the field roughly a decade to fully appreciate why it was wrong.

ARC 04 · WHY IT FAILS

The receiver has to decrypt before it can check the tag — and that order is the bug

Walk through what the receiver of naive_secure_send's output must do, in order: decrypt the CBC ciphertext, strip PKCS#7 padding, split off the trailing tag, then finally verify the HMAC. Notice the ordering constraint: padding is removed before the MAC is ever checked, because the MAC can't be located inside the plaintext until the padding is stripped. That means "is the padding well-formed?" is answered before "is this message authentic?" — and if those two answers are observable separately (a different error message, a different response time, even just a closed connection at a different protocol stage), you have handed an attacker an oracle.

This is precisely the padding-oracle attack Serge Vaudenay published in 2002, which chapter 10 builds byte by byte; the quantitative cost is worth previewing here because it is the direct, measurable consequence of choosing MAC-then-Encrypt: with a working padding oracle, an attacker recovers one byte of unknown CBC plaintext in an average of ~128 oracle queries (worst case 256, one per possible padding-byte value) — so a single 16-byte block costs on the order of 2,048–4,096 queries, and the attack requires no knowledge of the encryption key at all. The MAC's cryptographic strength is irrelevant; the leak happens one abstraction layer below it, in the decryption/unpadding step the MAC-then-Encrypt ordering forces to run first.

Encrypt-and-MAC has a different, simpler failure: because step 2 computes tag = MAC(Km, plaintext) and transmits it in the clear alongside the ciphertext, and most MACs (plain HMAC included) are deterministic functions of their input, identical plaintexts always produce identical tags — regardless of how good the encryption is. An attacker who intercepts many (ciphertext, tag) pairs can, with zero cryptanalysis, detect exactly which sessions carried the same underlying plaintext just by comparing tags — a structural leak of the "does this equal that" kind, the MAC-layer analogue of the ECB penguin from chapter 5. This is a real property of the SSH2 binary packet protocol that Bellare, Kohno, and Namprempre analyzed formally in 2002 ("Breaking and Provably Repairing the SSH Authenticated Encryption Scheme"), leading to the scheme being tightened in later SSH revisions.

THE THEOREM THAT SETTLES IT

Mihir Bellare and Chanathip Namprempre's 2000 paper "Authenticated Encryption: Relations among Notions and Analysis of the Generic Composition Paradigm" proved this is not a coincidence of bad implementations: Encrypt-then-MAC achieves strong authenticated-encryption security (IND-CCA + INT-CTXT) for ANY IND-CPA cipher combined with ANY secure MAC. MAC-then-Encrypt and Encrypt-and-MAC do not have this property in general — they only happen to be safe if the specific primitives you chose have extra properties the generic proof doesn't require. You cannot verify "does my specific cipher have that extra property" in a code review; you can trivially verify "did I use Encrypt-then-MAC." That is the entire argument for standardizing on one ordering.

ARC 05 · THE PROVABLY SAFE COMPOSITION

Encrypt-then-MAC, derived and stepped through

Flip the order. Encrypt first, then authenticate the ciphertext — and critically, the receiver now verifies the tag before attempting to decrypt anything. Step through why this single reordering closes both failures from §4 at once:

MAC-then-Encrypt vs Encrypt-and-MAC vs Encrypt-then-MACSTEP-BY-STEP

Generalize the pattern: Encrypt-then-MAC is not one algorithm, it is a composition rule — "compute the tag over the ciphertext (and anything else you need authenticated), and never decrypt until that tag verifies." IPsec's ESP (in its EtM configurations), the fixed SSH2 scheme, and TLS 1.2's optional encrypt_then_mac extension (RFC 7366, a direct response to a decade of CBC padding-oracle incidents) are all this same rule applied by hand. GCM and ChaCha20-Poly1305, which the rest of this chapter builds, are what happens when you take that rule and standardize it into a single object with one key and one nonce — turning "remember to do this in the right order" into an API that cannot be called in the wrong order.

THE INVARIANT WORTH MEMORIZING

Verify before you decrypt. If a receiver ever runs decryption logic (padding removal, cipher block chaining, anything data-dependent) on bytes whose authenticity it hasn't checked yet, an attacker can use the receiver's own error behavior as an oracle into that logic — no matter how strong the underlying primitives are. Every attack in §4, and the entire padding-oracle vulnerability class in chapter 10, reduces to a violation of this one invariant.

ARC 06 · WHY THAT STILL COSTS

Doing Encrypt-then-MAC correctly, by hand, is still expensive and still error-prone

Bellare–Namprempre's theorem tells you Encrypt-then-MAC is safe, not that it is free or foolproof when engineers implement it as two separate library calls glued together:

  • Two full passes over the data, with two different algorithms. AES-CBC encryption and HMAC-SHA256 each touch every byte of the message once, with separate initialization, separate keys, and (absent careful pipelining) separate cache passes. Measured on the same hardware, an honest EtM(AES-CBC + HMAC-SHA256) implementation typically costs on the order of 1.5–2× a fused single-pass AEAD cipher doing comparable work, because the CPU touches the same memory twice instead of once.
  • Two keys to manage, distribute, and rotate — correctly, in lockstep. A live incident category: using the same key for both the cipher and the MAC (to "save" a key) can reintroduce exploitable relationships between the two operations that neither primitive's individual security proof accounts for.
  • What exactly goes into the MAC input is a decision you can get wrong. If the IV/nonce itself is not included under the MAC, an attacker who can swap IVs between two ciphertexts encrypted under the same key can splice a valid-looking authenticated message from parts of two legitimate ones — the MAC verifies because it never covered the one field that changed. Getting the MAC's input format exactly right (what's covered, in what order, with what length encoding) is exactly the kind of ad hoc engineering decision a specified, standardized construction removes from your plate entirely.
  • EtM buys authenticity and confidentiality — nothing more. It does not give you replay protection or ordering guarantees; a captured, still-valid (ciphertext, tag) pair can be resent verbatim unless an outer protocol layer tracks sequence numbers or timestamps. TLS's record sequence counter and WireGuard's packet counter exist precisely because AEAD's job stops at "this exact byte string was produced by someone holding the key," not "this byte string hasn't been seen before."

Every one of these is a real class of implementation bug that a hand-assembled EtM pipeline can reintroduce even after you've picked the right composition order. The fix the industry converged on is to stop assembling EtM from two general-purpose primitives at all, and instead specify — once, precisely, with test vectors — a single object that takes a key, a nonce, associated data, and a plaintext, and returns ciphertext plus tag with no seams for an implementer to get wrong. That object is an AEAD cipher.

ARC 07 · FINAL ARCHITECTURE

One object, one call: the AEAD interface and its two production implementations

An AEAD cipher's public interface is deliberately small: Seal(K, N, P, A) → (C, T) and Open(K, N, C, T, A) → P or ⊥. N is a nonce that must never repeat under the same key (§8 makes precise exactly how badly this can go wrong); A is associated data — authenticated but transmitted in the clear, exactly the "authenticate the header, encrypt the body" gap §1 identified. Click through the two real constructions hiding behind that interface — they look different internally but implement the identical Encrypt-then-MAC shape from §5, fused into a single pass:

Both paths are "encrypt with a stream of keystream blocks, then run a universal hash function keyed by a value derived from K over the ciphertext and associated data." The interesting engineering difference is the algebraic structure underneath the hash: GCM's GHASH works in the binary field GF(2128) — ideal for hardware carry-less multiplication (Intel's PCLMULQDQ instruction, added specifically to accelerate GCM). Poly1305 works over the prime field GF(2130 − 5) — ideal for fast, constant-time software arithmetic on CPUs with no such instruction, which is exactly the mobile/software-only scenario chapter 4 introduced ChaCha20 to solve. §8 builds the GCM path's field arithmetic for real, in JavaScript.

ARC 08 · INTERNAL IMPLEMENTATION

GCM byte by byte: counters, GHASH, and the field it runs on

This is the level of detail you'd need to implement GCM from the NIST specification. Three pieces: (a) the counter-block layout, (b) GHASH as Horner's-rule polynomial evaluation, and (c) the GF(2128) multiplication those evaluations run on — which we will implement for real, not fake.

(a) From a 96-bit nonce to a stream of counter blocks

GCM is built on the CTR mode from chapter 5, with one specific convention. Given a 96-bit (12-byte) nonce N — the case NIST recommends and the overwhelming majority of deployments use — the initial counter block is J0 = N || 0x00000001: the nonce, followed by a 4-byte big-endian counter starting at 1. Encryption of the plaintext runs CTR mode starting at inc32(J0) — counter value 2 — while J0 itself (counter value 1) is reserved to mask the final authentication tag. Only the low 32 bits of the block increment; the nonce portion never changes within one message.

One GCM invocation, end to endSTEP-BY-STEP
THE 32-BIT COUNTER IS A HARD LIMIT, NOT A STYLE CHOICE

Because only 32 bits increment, a single (key, nonce) invocation can address at most 2³²−2 blocks before the counter wraps and starts repeating keystream within the same message — NIST SP 800-38D caps this at a plaintext length of 2³⁹−256 bits, just under 64 GiB. That number is a direct, computable consequence of the 32-bit field width you just saw, not an arbitrary NIST preference — §10 turns this into a slider you can push against the limit.

(b) GHASH: authentication as one polynomial evaluation

GHASH takes a per-message subkey H = AESK(0128) — the block cipher encrypting an all-zero block, computed once per key — and a sequence of 128-bit blocks: the associated data (zero-padded to a block boundary), the ciphertext (zero-padded likewise), and a final block encoding the bit-lengths of each as two 64-bit big-endian integers. It evaluates them against H using Horner's method, entirely inside GF(2128):

mathGHASH as Horner's rule
Y₀ = 0
Yᵢ = (Yᵢ₋₁ ⊕ Xᵢ) · H          for each 128-bit block X₁..Xₘ, multiplication in GF(2¹²⁸)
GHASH_H(A, C) = Yₘ
tag T = MSB_t( AES_K(J0) ⊕ GHASH_H(A, C) )

Every "multiplication" in that loop is a genuine field operation — not modular integer multiplication, but polynomial multiplication modulo the irreducible polynomial x¹²⁸ + x⁷ + x² + x + 1, the same binary-field construction GF(2⁸) used inside AES's MixColumns (chapter 3), just 16× wider.

(c) GF(2128) multiplication, implemented for real

NIST's bit convention for a 128-bit block is subtle and a frequent source of implementation bugs: bit b₀ — the first bit written out, i.e. the most-significant bit of the block's big-endian byte representation — is defined as the coefficient of x⁰, not x¹²⁷. Multiplication is the standard shift-and-conditionally-reduce ("Russian peasant") algorithm, walking the multiplier's bits from b₀ to b₁₂₇:

javascriptthe exact function powering §15's simulator
// X, Y: BigInt in [0, 2^128) — standard big-endian integer reading of the 16-byte block.
// R encodes the reduction polynomial's low-order terms (x^7+x^2+x+1) placed at the
// top byte, because NIST's bit-0-is-MSB convention maps them there.
function gf128Mul(X, Y) {
  let Z = 0n, V = Y;
  const R = 0xE1n << 120n;                 // 0b11100001 || 0^120
  for (let i = 127n; i >= 0n; i--) {
    if ((X >> i) & 1n) Z ^= V;             // bit b_i of X selects whether V contributes
    if (V & 1n) V = (V >> 1n) ^ R;          // shift, and reduce mod the field polynomial
    else      V = V >> 1n;
  }
  return Z;                               // Z === X · Y  in GF(2^128)
}

This is a genuine field: multiplication is associative, commutative, and distributes over XOR (the field's addition); every nonzero element has a unique multiplicative inverse (via Fermat's little theorem for finite fields, a⁻¹ = a2¹²⁸−2) and a unique square root (√a = a2¹²⁷, because squaring is the field's Frobenius automorphism). §15's attack needs exactly those last two facts — it is not a metaphor, it is load-bearing algebra you can verify yourself below.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Two independent numbers matter for an AEAD cipher in production: how fast it runs on your hardware, and how many messages you can safely encrypt under one key before random-nonce collisions become a real risk rather than a theoretical one.

The bars are an analytic sketch tuned to the commonly published order of magnitude for each configuration — multi-GB/s per core for AES-GCM with AES-NI and PCLMULQDQ, roughly comparable throughput for software ChaCha20-Poly1305 on a core with no AES hardware acceleration (exactly the mobile/embedded scenario that motivated its adoption, per chapter 4), and a measurable step down for AES-GCM once you take the hardware away — its GHASH step depends much more heavily on a carry-less-multiply instruction than ChaCha20-Poly1305 depends on any single instruction. Real numbers vary by CPU generation; the shape is the lesson.

The birthday bound on random nonces

Most deployments generate GCM's 96-bit nonce randomly rather than from a coordinated counter, because coordinating counters across distributed, stateless workers is its own operational hazard (see §11's cloud incident). But random nonces collide — it's a birthday-paradox calculation, not a hypothetical: with n messages and a 96-bit nonce space, the probability of at least one repeat is approximately 1 − e−n²/2·2⁹⁶ ≈ n²/2⁹⁷ for small probabilities. NIST SP 800-38D's operational guidance — no more than 2³² invocations for a given key under randomly generated 96-bit nonces — is exactly this calculation kept at a conservative safety margin, not a round number chosen for convenience.

ARC 11 · REAL-WORLD INCIDENTS

The forbidden attack, in theory and in the wild

2006 — Antoine Joux's "Forbidden Attack"

Shortly after GCM was submitted to NIST, cryptographer Antoine Joux circulated a short, devastating note: reuse a (key, nonce) pair even once under GCM and you can algebraically recover the authentication subkey H from two intercepted (ciphertext, tag) pairs, after which you can forge a valid tag for any ciphertext under that nonce, with no further access to the key. This is not a side channel or an implementation bug — it is a direct algebraic consequence of GHASH being a fixed polynomial evaluation in H, exactly the field arithmetic §8 built and §15 exploits. Joux's note is the reason NIST SP 800-38D's nonce-uniqueness requirement is phrased as absolute ("shall not be reused"), not merely recommended.

2016 — "Nonce-Disrespecting Adversaries" (Böck, Zauner, Devlin, Somorovsky, Jovanovic, USENIX WOOT)

This paper turned Joux's theoretical result into an internet-scale measurement: scanning production HTTPS deployments and several JOSE (JSON Object Signing and Encryption) libraries, the authors found real, exploitable GCM nonce reuse caused by ordinary implementation bugs — flawed random-nonce generation, broken counter state after a restart, and copy-pasted code paths that silently reset a supposed-to-be-monotonic counter. The root cause in almost every case was mundane: nonce generation was treated as an implementation detail rather than the single hardest invariant the entire cipher's security rests on.

CVE-2019-1543 — OpenSSL's ChaCha20-Poly1305 long-nonce bug

OpenSSL's EVP interface allowed an application to configure a ChaCha20-Poly1305 nonce length longer than the RFC 8439 standard 12 bytes. When it did, OpenSSL's internal handling of the excess bytes could cause part of the nonce to be silently truncated or mishandled — meaning two different application-supplied "distinct" nonces could collapse to the same internal nonce actually used by the cipher, reintroducing exactly the reuse condition this chapter is about, from a completely different root cause (an API surface with more flexibility than the underlying construction can safely support) than Joux's algebraic attack or Böck et al.'s buggy RNGs.

A DESIGN LESSON THAT SHAPED TLS 1.3

TLS 1.2's GCM cipher suites (RFC 5288) let implementations choose their own scheme for constructing the 8-byte "explicit" part of the nonce per record, on top of a 4-byte per-connection salt — flexibility that created room for exactly the kind of counter-management mistakes §11 above describes. TLS 1.3 (chapter 13) removes the choice entirely: the per-record nonce is deterministically sequence_number XOR derived_iv, with no implementation decision left to get wrong. That is the same lesson as §6's critique of hand-rolled EtM, one level up the stack: wherever a security-critical value has more than one way to be constructed, someone eventually constructs it wrong.

First, the shape of the GCM context — notice it stores function pointers for the multiply/hash step, chosen once at initialization based on detected CPU features:

Cgcm128.h — dispatch, not a fixed algorithm
struct gcm128_context {
    /* Xi: the running GHASH accumulator (Yi in the math above).
     * H:  the authentication subkey, AES_K(0^128), computed once.        */
    union { u64 u[2]; u8 c[16]; } Xi, H;

    /* Htable[16]: PRECOMPUTED multiples of H, indexed by 4-bit nibble —
     * turns the 128-iteration bit loop from §8(c) into 32 table lookups
     * per block. This is the classic time/space tradeoff, nothing more. */
    u128 Htable[16];

    void (*gmult)(u64 Xi[2], const u128 Htable[16]);
    void (*ghash)(u64 Xi[2], const u128 Htable[16], const u8 *inp, size_t len);
    /* At init time: if the CPU reports PCLMULQDQ (checked via CPUID,
     * cached in OPENSSL_ia32cap), these point at hand-written assembly
     * that does the SAME field multiplication in a handful of
     * instructions. Otherwise, fall back to the 4-bit table version.
     * Same math as §8(c) — just three implementations of it.            */

    unsigned int mres, ares;
    block128_f block;               /* the underlying AES_encrypt, reused for CTR too */
};

The encrypt driver interleaves CTR encryption and GHASH accumulation in one pass — this single-pass property, not any cryptanalytic advantage, is GCM's whole reason for existing over two-pass CCM (§2):

Cgcm128.c — CRYPTO_gcm128_encrypt(), simplified
int CRYPTO_gcm128_encrypt(GCM128_CONTEXT *ctx, const u8 *in, u8 *out, size_t len)
{
    for (size_t i = 0; i < len; i += 16) {
        ctx->block(ctx->Yi.c, ctx->EKi.c, key);   /* AES_K(counter block) — CTR keystream    */
        ctr128_inc(ctx->Yi.c);                    /* increment ONLY the low 32 bits (§8a)    */

        for (int j = 0; j < 16 && i+j < len; j++)
            out[i+j] = in[i+j] ^ ctx->EKi.c[j];    /* ciphertext block, produced right here   */

        /* Feed the JUST-PRODUCED ciphertext block into GHASH immediately —
         * no second pass over the buffer needed.                        */
        ctx->Xi.u[0] ^= load64(out+i);   ctx->Xi.u[1] ^= load64(out+i+8);
        ctx->gmult(ctx->Xi.u, ctx->Htable);        /* one GF(2^128) multiply — §8(c)'s math   */
    }
    return 1;
}

Poly1305, for contrast, never touches GF(2128) at all — it accumulates a polynomial modulo the prime 2¹³⁰ − 5 using "clamped" 128-bit halves of its one-time key:

Cpoly1305.c — the shape of one_time_auth(), reference form
void poly1305_auth(u8 tag[16], const u8 *msg, size_t len, const u8 key[32])
{
    u130 r = clamp(key[0..16]);   /* zero specific bits so r*acc never overflows the limb layout */
    u128 s   =                key[16..32];
    u130 acc = 0;

    for (each 16-byte block m of msg, last block padded with a leading 1 bit)
        acc = (acc + m) * r  mod (2^130 - 5);    /* Horner's rule again — same shape as GHASH, different field */

    tag = (acc + s) mod 2^128;             /* s masks the result; r is never reused across messages */
}
WHY IT WAS BUILT THIS WAY

1. The math in §8 and the code here are the same algorithm at three speeds. The 128-iteration bit loop, the 4-bit lookup-table version, and the PCLMULQDQ assembly all compute the identical field multiplication — production code chooses among them at startup based on CPUID, purely for speed, never for correctness. 2. Poly1305's "clamping" — forcing specific bits of r to zero — exists so the running accumulator's limbs (26-bit chunks in Bernstein's reference layout) never grow large enough to overflow a machine word during multiplication, letting the whole MAC run in fixed-size integer registers with no heap allocation and no data-dependent branches — both a performance and a side-channel-resistance decision (chapter 15 returns to constant-time code generally). 3. Neither construction calls a generic bignum library. Both hand-unroll their field arithmetic into fixed-width operations specifically so the code's timing depends only on message length, never on secret values — exactly the property a general-purpose arbitrary-precision library does not, and cannot, guarantee.

THE ALGEBRA YOU JUST RAN

Both messages share H and the same tag mask EK(J0), because both are a function only of K and the reused nonce. With equal-length messages and empty associated data, the GHASH length-block term is identical for both, so it cancels under XOR, leaving (T1 ⊕ T2) = (C1 ⊕ C2) · H² — one equation, one unknown. The simulator solves it exactly as written: invert (C1 ⊕ C2) in GF(2128), multiply by (T1 ⊕ T2) to get H², then take the unique field square root to recover H itself. From there, the tag mask falls out of either original equation, and forging a third message — even one with entirely different content, spliced from message 1's known plaintext — requires no further contact with K at all. This is exactly what "AEAD's security guarantee is void under nonce reuse" means, made concrete.
