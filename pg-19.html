POSTGRESQL INTERNALS · CHAPTER 19

Connections, Partitioning
& Extensibility

Three subsystems, one thread connecting them: each is a layer built on top of a fixed, expensive primitive from earlier chapters, designed to make that primitive behave as if it were cheaper, more flexible, or more general than it actually is. Poolers hide the true cost of chapter 1's backend. Partitioning reframes "one big relation" as a routing problem over many small ones. And the extension mechanism turns "a hardcoded C program" into a platform other people's code can plug into — which, historically, is the single decision responsible for PostgreSQL's ecosystem existing at all.

ARC 01 · THE PROBLEM

Three walls the process model, the relation, and the core codebase all hit

Chapter 1 built a backend that is safe, isolated, and expensive. Chapters 4–9 built a relation as a heap of 8 KB pages plus indexes, uniform in structure regardless of size. And the core codebase itself is one C program, compiled once, that cannot possibly anticipate every data type or storage need in advance. Each of those choices is correct in isolation and becomes a wall at scale:

  • Connections don't scale linearly with clients. Ten thousand application-server connections against a database sized for hundreds of real backends is not a tuning problem — it's a structural mismatch between how cheap a client thinks a connection is and how expensive chapter 1 showed a backend actually is.
  • One giant relation eventually becomes unmanageable as a single physical object. A 10-billion-row events table forces every maintenance operation — vacuum, an index rebuild, an old-data purge — to either operate on the whole table or not at all, even though the actual access pattern ("give me last week's rows," "delete everything older than two years") is naturally aligned to a subset.
  • A closed-source core cannot ship every extension the world will ever want. Geospatial types, vector similarity search, foreign-table access to other databases, custom index strategies — none of it can live in core without core becoming unmaintainable, yet all of it needs to interoperate with core's planner, executor, and storage exactly as if it were built in.

Each of the three sections in this chapter is the answer to one of those walls — and each answer works the same way: rather than changing the expensive primitive underneath, build a layer that routes around its cost or its rigidity. A pooler routes connections onto fewer backends. Partitioning routes a query onto a subset of physical relations. And the extension mechanism routes planner/executor control to code that was never compiled into postgres at all.

THE UNIFYING QUESTION FOR THIS CHAPTER

For each subsystem, ask: what invariant does the underlying primitive (a backend, a relation, the planner) provide, and what does the new layer have to give up to route around its cost? A transaction pooler gives up "the session is the connection." Partitioning gives up "the table is one physical object." And an extension gives up "everything in the query path was written and tested by core" — replacing it with hook contracts and shippability tests. None of these are free lunches; all three tradeoffs recur throughout the rest of this chapter.

DEEP CONTEXT · THE EXTENSION MECHANISM PREDATES ALL OF IT

User-defined types and functions were part of the original 1986 POSTGRES research thesis — chapter 1's timeline already told you the project's entire premise was "a database users extend with their own C code." CREATE EXTENSION (9.1, 2011) didn't invent extensibility; it packaged twenty-five years of ad hoc "run this SQL script, then that shared library" folklore into one versioned, dependency-tracked object. The hook system and FDW API are the same story: mechanisms that existed piecemeal for years, formalized once enough real extensions (PostGIS chief among them) proved the pattern was load-bearing.

ARC 03 · NAIVE SOLUTION

Attempt #1: one backend per client, one table per table, one binary for everything

The strawman for all three problems is simply: don't build the layer. Let every application connection open its own backend (chapter 1's default). Let a growing table just keep growing as one relation. Let anyone who needs a new data type propose it to the mailing list and wait for a core release.

SQLthe strawman — no pooler, no partitions, no extension
-- Every application server opens its own connections directly to Postgres.
-- 200 app servers x 50 connections each = 10,000 backends, if Postgres let you get that far.

CREATE TABLE events (
  id bigserial primary key,
  created_at timestamptz not null,
  payload jsonb
);
-- One relation, forever. Ten billion rows in, deleting last year's
-- data means DELETE ... WHERE created_at < ... : a full-table scan,
-- a huge burst of dead tuples, and a vacuum that takes hours.

-- Need geospatial queries? Wait for a core Postgres release that
-- adds a `point`-like type with the operators and index support you
-- need -- or fork Postgres and maintain your own patched build forever.

Just as with chapter 1's iterative server, this isn't a joke — it's correct, and it's what a small application should actually do. The strawman fails the same way every strawman in this course fails: not because it's wrong at small scale, but because none of its costs are visible until the input size crosses a threshold, and by then the fix is a migration project instead of a config change.

ARC 04 · WHY IT FAILS

Three thresholds, three walls

Quantify each failure the way chapter 1 quantified head-of-line blocking:

  • Connections: chapter 1 priced a backend at ~1–3 MB baseline RSS growing to 10–50 MB with warm caches, plus a fork costing page-table copy time proportional to shared_buffers. At 10,000 real backends against 32 GB shared_buffers, you are not merely using a lot of RAM — you're inside the regime where GetSnapshotData()'s pre-PG14 ProcArray scan and raw scheduler contention degrade every active session, the exact hump chapter 1's performance model plotted. Direct-to-Postgres connections from a large application fleet hit that hump on ordinary growth, not on any pathological event.
  • Partitioning: a single 500 GB table's VACUUM is one long-running operation touching every page; there is no way to vacuum "just last week," parallelize by natural boundary, or drop old data other than a page-by-page DELETE that itself generates a wave of dead tuples for that same vacuum to clean up later. Retention policies ("keep 90 days") become O(rows-to-delete) operations instead of O(1) metadata operations.
  • Extensibility: without a plugin surface, every specialized need — geospatial (PostGIS), vector similarity (pgvector), foreign-database access (postgres_fdw, oracle_fdw) — either never exists, or exists only as a hard fork of core that must be rebased against every point release forever. The transaction cost of "propose a change to core Postgres" (mailing-list review, multi-year commitment, C-level competence) is simply too high for the majority of use cases the ecosystem eventually needed.
THE NUMBERS: WHEN DOES EACH WALL BITE?

Connections: past roughly 2–4× core count in concurrently active backends, chapter 1's throughput hump already turns over — most fleets cross this within their first year of real traffic. Partitioning: practical pain (slow DELETE-based retention, single-vacuum bottlenecks) shows up once a table passes roughly tens of millions of rows with a retention or time-range access pattern — well before you'd call the table "big" by storage size alone. Extensibility: the wall isn't a number, it's qualitative — the moment your requirement (a new operator class, a new wire protocol to another system) has no SQL-level expression at all.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Routing layers, examined one at a time

Step through the shape each subsystem actually took, and the alternative it beat:

Four routing layersSTEP-BY-STEP
THE COMMON SHAPE

Every winning design here inserts a thin layer BETWEEN the client and the expensive primitive, rather than changing the primitive: PgBouncer sits between app and backend; the partitioned table's parent is a routing fiction sitting between the query and its real child relations; hooks sit between the planner/executor's fixed call sites and arbitrary loaded code. None of them make a backend cheaper, a relation smaller, or core Postgres itself pluggable at the source level — they make the EXPENSIVE THING'S COST avoidable in the common case, which is a different, cheaper problem to solve.

ARC 06 · WHY THAT STILL HURTS

Routing layers leak their own seams

Every layer that hides a cost also hides an invariant the layer above was relying on. Naming the leaks precisely is the entire practical content of this chapter:

  • Transaction pooling breaks "the session is the connection." A session-scoped feature — a prepared statement, a SET, an advisory lock, LISTEN/NOTIFY, a WITHOUT HOLD cursor, a temp table — assumes the backend it was created on is the same backend serving your next statement. Transaction pooling returns the backend to the pool between transactions, so that assumption silently stops holding, and the failure mode ranges from a confusing error to quietly wrong behavior.
  • Partition pruning is a plan-time optimization first, an execution-time one second — and the gap between them is where most operational confusion lives. A constant predicate lets the planner eliminate partitions before execution even starts; a parameterized predicate (a prepared statement's bind parameter, a nested-loop's inner side, a parallel worker's runtime value) cannot be resolved until execution, so pruning has to happen again, later, with different machinery and different limits.
  • Hooks and FDWs only help if the operation can actually be pushed down or the loaded code plays by the planner's rules. A custom type without a written cost function, or a foreign-table predicate the FDW's shippability test rejects, silently falls back to the slow path — a full local re-evaluation, or worse, a full remote-table transfer — with no error, just a much slower query.
WHY THIS IS THE RIGHT PLACE TO END THE COURSE'S TECHNICAL ARC

Notice that every leak above is explainable using machinery from earlier chapters: session state lives in per-backend memory (chapter 2) and shared structures like the lock table (chapter 8) and LISTEN/NOTIFY's SLRU queue; partition pruning is planner/executor cost estimation (chapters 15–16) applied per-partition; hooks and FDWs are just more call sites into the same planner and executor internals this course has spent eighteen chapters building a mental model of. There is no new physics in this chapter — only new places the old physics shows up.

THE THREAD THAT TIES IT TOGETHER

A single query against a partitioned foreign table with pg_stat_statements loaded touches every mechanism in this chapter at once: it arrives through a pooled connection, the planner calls partprune.c to eliminate partitions, ExecutorStart_hook lets pg_stat_statements observe the plan without core knowing pg_stat_statements exists, and any surviving partition that happens to be a foreign table goes through postgres_fdw's shippability tests before deciding whether its predicate travels to the remote server or drags the whole remote table home. None of this required a single change to postgres's core source — that is the entire point of building it this way.

ARC 08 · INTERNAL IMPLEMENTATION

Pool sizing math, the routing algorithm, and the hook contract

(a) Why PgBouncer can be single-threaded — and what that buys and costs

PgBouncer's entire architecture is a single-threaded epoll event loop — chapter 1's "candidate A" (the Redis/nginx shape), rejected for Postgres itself because query execution blocks unpredictably. PgBouncer can use exactly that shape because it never runs a query: it only relays bytes between a client socket and a server socket, deciding at transaction (or session, or statement) boundaries which server connection a client is bound to. Since it never blocks on disk I/O, a lock wait, or a sort spill, one thread juggling thousands of file descriptors is not just adequate — it's the same reasoning that made an event loop wrong for Postgres but right for a proxy in front of it.

FORMULA (the same one PgBouncer's own docs and Baron Schwartz's writing both converge on)

pool_size ≈ effective_spindles × (cores / cores) ... in practice: pool_size ≈ 2–4× CPU cores for CPU-bound OLTP, adjusted upward toward cores + effective_spindles when queries actually wait on disk I/O rather than saturating CPU — because a backend blocked on a pread() isn't consuming a core, so a few extra concurrent backends beyond core count let the kernel overlap I/O wait with other backends' CPU work, up to the point where the underlying storage's IOPS ceiling becomes the new bottleneck. Sizing off client count instead of this formula is the single most common pooler misconfiguration in production.

(b) Partition routing and pruning: two different pieces of code, two different times

A partitioned table's catalog entry for each partition carries a partition bound — the range, list value set, or hash modulus/remainder that partition owns (partbounds.c). At INSERT time, execPartition.c's tuple routing walks that bound structure to find the single partition a new row belongs in — a search, not a scan, so routing cost grows with partition count but not with data size. Pruning is the mirror operation for reads: given a query's predicate, which partitions could possibly contain a matching row? partprune.c answers this at plan time when the predicate is a constant; when it depends on a bind parameter, a correlated subquery, or a nested-loop join's changing inner value, the same logic has to run again — inside the executor, per rescan — because the value simply didn't exist yet when the plan was built.

WHY enable_partitionwise_join IS OFF BY DEFAULT

If two partitioned tables are partitioned identically (same bounds on the join key), the planner CAN join matching partition pairs independently instead of joining the two logical tables as a whole — real parallelism and smaller working sets per join. It's off by default because proving two tables are partition-compatible (identical bounds, matching partition-key data types and collations) and then planning N independent joins instead of one costs real planning time — for tables with few partitions the win rarely pays for the extra planning, but for wide, evenly partitioned fact tables it can be substantial. This is the same plan-time-cost-vs-runtime-win tension chapters 15–16 raised for every other optimizer decision, applied to partitions.

(c) Hooks: function pointers the planner and executor promise to check

PostgreSQL's extension surface for controlling query processing is, at the mechanical level, disarmingly simple: global function-pointer variables (planner_hook, ExecutorStart_hook, ExecutorRun_hook, ProcessUtility_hook, shmem_request_hook, and others) that default to NULL and are called, if non-NULL, at fixed points in the normal code path — usually wrapping the default behavior rather than replacing it outright, so an extension can observe or augment processing and then call through to what core would have done anyway. pg_stat_statements installs an ExecutorStart_hook/ExecutorEnd_hook pair purely to time and fingerprint queries; auto_explain does the same to conditionally log slow plans; neither patches a single line of core.

HOW THIS BECOMES POSTGIS'S GIST INDEX SUPPORT

A custom type (say, a geometry) defines its on-disk representation using the varlena rules from chapter 4, then registers an operator class that teaches an existing access method (GiST, from chapters 13–14) how to compare, bound, and split values of that type — implementing the access method's small set of required support functions (consistent, union, compress, penalty, picksplit, same). Nothing about GiST's core B-tree-of-boxes algorithm changes; PostGIS simply supplies the type-specific glue GiST was designed to accept. This is the exact mechanism, not an analogy, by which geometry columns get R-tree-like spatial indexing without one line of PostGIS code living inside the Postgres repository.

ARC 10 · PERFORMANCE CHARACTERISTICS

Where the costs actually live

  • Pooling: a pooled connection's overhead is proxy-side bookkeeping (~2 KB per queued client in PgBouncer) instead of a full backend fork — the savings are exactly chapter 1's per-backend costs, avoided for every client beyond the real pool size.
  • Partition planning time: grows with partition count because the planner must still open, lock, and consider each partition individually during planning (even ones later pruned) — historical practical ceilings sat near a few hundred to roughly 1,000 partitions before planning latency became noticeable; successive releases (partition-bound binary search, faster locking, pruning improvements) have pushed that ceiling up substantially without eliminating the underlying O(partitions) planning cost.
  • Locking every partition during planning: even a query that will prune down to one partition at execution time must take at least an AccessShareLock on every partition considered during planning — a real, if usually cheap, cost that scales with partition count regardless of how good pruning later is.
  • Indexes are per-partition: there is no single physical index spanning all partitions, hence no way to enforce a UNIQUE constraint across the whole logical table unless the partition key itself is part of the uniqueness — the "global unique index gap."
  • FDW pushdown collapses network and remote-CPU cost: a pushed-down WHERE/LIMIT/aggregate means the remote server does the filtering and only matching rows cross the network; a non-shippable predicate means the entire remote table crosses the wire before local Postgres ever gets to filter it — the difference between these two paths is easily two or three orders of magnitude in bytes transferred for a selective query.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: The prepared-statement errors that only happened in production

An application used server-side prepared statements (via a driver's default) against PgBouncer configured in transaction pooling mode. In staging (direct-to-Postgres, no pooler) everything worked; in production, intermittent "prepared statement ... does not exist" errors appeared under load. Root cause: a prepared statement lives in the backend's private plan cache (chapter 2/15), but transaction pooling can hand a client's next transaction to a different real backend that never saw the PREPARE. Fixes: disable server-side prepared statements in the driver for pooled connections, use PgBouncer's newer protocol-level prepared-statement support (tracking statements per-pool since later PgBouncer versions), or move to session pooling for workloads that can't give up the feature — accepting the lower connection multiplexing ratio that comes with it.

Incident 2: The partitioned table nobody could add a unique constraint to

A team partitioned an orders table by month for retention, then tried to add a global UNIQUE(order_uuid) constraint spanning all partitions and discovered PostgreSQL flatly rejects it unless the partition key is part of the uniqueness — because there is no single physical index to enforce it against; each partition only knows about its own rows. They'd designed the partition key (a date) independently of their actual uniqueness requirement (a UUID) and had to retrofit UNIQUE(order_uuid, created_at) plus application-level assumptions that a UUID collision across differently-dated partitions was acceptably rare — a compromise that should have been a day-one design decision, not a week-two surprise.

Incident 3: The postgres_fdw query that transferred an entire remote table

A reporting query joined a local table against a postgres_fdw foreign table with a WHERE remote_col ILIKE '%term%' predicate. ILIKE with a leading wildcard has no sargable form the remote planner can use, and more importantly postgres_fdw's shippability tests don't push down expressions it can't prove produce identical results under the remote server's collation and operator semantics — so the entire foreign table streamed across the network before any filtering happened locally, once the query ran against a materially larger remote table than during testing. Fixes: rewrite the predicate to a form known to be shippable (exact match, range predicates on indexed columns), inspect EXPLAIN (VERBOSE) for the "Remote SQL" line to confirm what actually crosses the wire, and treat any foreign-table query without a visible pushed-down filter as a full-transfer query until proven otherwise.

The core of plan-time pruning — deciding, from a constant predicate, which partitions can be skipped before execution ever begins:

Cpartprune.c — get_matching_partitions(), simplified
static Bitmapset *
get_matching_partitions(PartitionPruneContext *context, List *pruning_steps)
{
    Bitmapset *result = bms_make_empty();

    foreach(step, pruning_steps)
    {
        /* A step is something like: partition_key = $const, or
         * partition_key BETWEEN $const1 AND $const2 -- resolved using
         * the partition bound catalog (partbounds.c), NOT by touching
         * any partition's actual data.                                */
        Bitmapset *matched = perform_pruning_combine_step(context, step);
        result = bms_add_members(result, matched);
    }

    /* Callers use this bitmap two different ways depending on WHEN
     * the predicate's values are known:
     *   - at PLAN time, for constant predicates: partitions outside
     *     `result` are simply never added to the plan at all.
     *   - at EXECUTION time (ExecFindMatchingSubPlans, in the executor),
     *     for parameterized predicates: the same bitmap is recomputed
     *     once the actual parameter value is bound, and only THOSE
     *     child plans are initialized/executed.                       */
    return result;
}

And the hook contract — the entire mechanism by which pg_stat_statements observes every query without one line of core being aware of it:

Cexecutor/execMain.c + pg_stat_statements.c — the hook pattern
/* In core Postgres (executor/execMain.c) -- this exists whether or
 * not any extension is loaded. Default value: NULL.                */
ExecutorStart_hook_type ExecutorStart_hook = NULL;

void
ExecutorStart(QueryDesc *queryDesc, int eflags)
{
    if (ExecutorStart_hook)
        (*ExecutorStart_hook) (queryDesc, eflags);   /* extension's code runs FIRST */
    else
        standard_ExecutorStart(queryDesc, eflags);
}

/* In pg_stat_statements.c -- loaded via shared_preload_libraries.   */
void
_PG_init(void)
{
    prev_ExecutorStart = ExecutorStart_hook;   /* save whatever was there (chain-friendly) */
    ExecutorStart_hook = pgss_ExecutorStart;
}

static void
pgss_ExecutorStart(QueryDesc *queryDesc, int eflags)
{
    if (prev_ExecutorStart)
        prev_ExecutorStart(queryDesc, eflags);
    else
        standard_ExecutorStart(queryDesc, eflags);   /* still runs core's real logic */

    /* ...then pg_stat_statements' own bookkeeping: start a timer,
     * install ExecutorEnd_hook to record duration+call count keyed
     * by a normalized query fingerprint. Core never imported a
     * single pg_stat_statements symbol to make this work.            */
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Function pointers, not a plugin registry. The simplest possible extension point is a global variable core already checks — no registration API, no ordering metadata, just "is it non-NULL." 2. Chain, don't clobber. Every well-behaved hook implementation saves the previous value and calls it, so multiple extensions can stack (pg_stat_statements AND auto_explain both hooking ExecutorStart, in either load order). 3. No ABI promise beyond a major version. Because hooks are plain C function pointers into evolving internal structs, an extension compiled against PG15 is not guaranteed to load against PG16 — the tradeoff for a mechanism this simple and this deeply embedded is that extensions rebuild per major version, which is exactly why every serious extension ships version-specific binaries.
