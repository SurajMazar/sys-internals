UBER ENGINEERING INTERNALS · CHAPTER 16

Docstore: What a Database
Looks Like When You Design It Twice

Chapter 15 built Schemaless — a deliberately dumb opaque-blob store bolted onto sharded MySQL, and it worked precisely because it refused to promise secondary indexes or cross-region writes. This chapter is about what happens when those two refusals stop being acceptable: Docstore, Uber's real next-generation datastore, built to succeed Schemaless by trading MySQL's InnoDB B-tree for MyRocks — a MySQL storage engine running on RocksDB's log-structured-merge tree — specifically because an LSM-tree's append-only write path fits Uber's write-heavy workloads in a way B-tree in-place updates never could, and by building real secondary indexes and multi-region replication directly into the engine instead of leaving them to application code.

ARC 01 · THE PROBLEM

Schemaless's two refusals become two requirements

Schemaless (chapter 15) earned its scalability by being honest about what it gave up: no native secondary indexes — look up a row only by the shard key, cell name, and row key you wrote it with — and no multi-region story beyond running independent Schemaless clusters per region. Both refusals were correct engineering for the problem Schemaless was solving in 2014. Neither refusal survives contact with Uber's continued growth.

Two concrete pressures make this precise, not aspirational:

  • "Find all trips for this rider" is not a primary-key lookup. A service that needs to query by any attribute other than the exact key it wrote with — rider ID, driver ID, a status field, a timestamp range — has no way to ask Schemaless that question directly. Every such query becomes either a full shard scan (fine at small scale, ruinous at Uber's real row counts) or a hand-maintained secondary index table the application team must keep in sync themselves, by hand, forever.
  • A single service increasingly needs to serve more than one region well. Schemaless's per-region cluster model means a service that wants its data available with low latency in more than one geography is on its own for keeping those clusters consistent — there is no built-in replication story between them at all.
WHY NOT JUST FIX SCHEMALESS IN PLACE

Secondary indexes and cross-region replication are not features you bolt onto an opaque-blob store after the fact — they need the storage engine itself to understand structure (so it can maintain an index atomically with the row it indexes) and to understand write ordering (so replication has something coherent to ship). Schemaless was deliberately blob-agnostic: MySQL's InnoDB never knew a JSON blob had a rider_id field worth indexing. Getting both capabilities right meant building a new engine, not patching the old one — which is exactly what Docstore is.

ARC 03 · NAIVE SOLUTION

Attempt #1: bolt both requirements onto Schemaless as-is

Before reaching for a new storage engine, take the honest first step: can secondary indexes and multi-region replication be added to Schemaless without changing its engine at all?

pseudocodenaive_index_and_replicate.py — the strawman, annotated
def write_trip(trip):
    schemaless.put(shard_key=trip.rider_id, cell="trips", row_key=trip.trip_id, blob=trip.to_json())

    # "secondary index" = just another Schemaless row, kept in sync by hand
    schemaless.put(shard_key=trip.driver_id, cell="trips_by_driver", row_key=trip.trip_id, blob=trip.to_json())
    # nothing enforces these two writes happen together — if the second one fails, the
    # index silently drifts out of sync with the row it was supposed to point to

    # "multi-region" = the application fires the same write at every region, synchronously
    for region in ["us-east", "us-west", "eu-west"]:
        schemaless_client[region].put(shard_key=trip.rider_id, cell="trips", row_key=trip.trip_id, blob=trip.to_json())

Both halves of this are exactly the kind of thing an application team reaches for first — and both are reasonable, until you look at what happens under real failure and real network physics.

ARC 04 · WHY IT FAILS

Two failures, quantified: index drift and cross-region latency

  • The manual index has no atomicity guarantee. Writing the primary row and its "index" row are two independent Schemaless puts. If the process crashes, the network blips, or the second write simply fails after the first succeeds, the index now points at nothing, or is missing an entry that genuinely exists. At Uber's real write volume — millions of trip-related writes per day — even a failure rate of a fraction of a percent compounds into a steadily growing population of silently incorrect index rows, discovered only when a query using that index returns a wrong answer.
  • Synchronous multi-region writes are bounded by the speed of light, not by engineering effort. A round trip between, say, a US and a European datacenter is commonly in the 100–150 ms range on real backbone networks — physics, not a tunable parameter. If a write must be acknowledged by every region synchronously before the caller's request returns, every write anywhere in the system now costs at least the slowest region's round-trip time. For a trip-state write inside a request budget measured in tens of milliseconds (chapter 7), a mandatory 150 ms cross-ocean round trip is not a performance regression — it is disqualifying.
THE NUMBERS

If each of N independent writes in the naive fan-out has an independent failure probability p, the probability that all of them succeed is (1-p)^N — which shrinks fast as N grows even for small p. Two writes (row + index) at p = 0.1% failure each already gives roughly a 0.2% chance of a silently inconsistent pair per write; at Uber's real write volume that is thousands of drifted index rows per day, discovered only by a wrong query result. And synchronous three-region replication doesn't fail silently — it fails by making every write in the system pay the round-trip cost of whichever region is momentarily slow or unreachable, converting a regional network blip into a global latency spike.

ARC 05 · BETTER SOLUTION

Move both requirements into the engine: MyRocks and its LSM-tree

The fix for both failures has the same shape: stop asking application code to fake a guarantee the storage layer should provide, and instead choose a storage engine that can offer it natively. Docstore's answer is MyRocks — RocksDB's LSM-tree wearing a MySQL-compatible storage-engine interface — plus index maintenance and replication logic built into Docstore's own layer above it.

Why an LSM-tree, specifically, for this workloadSTEP-BY-STEP
THE CLINCHING ARGUMENT: WRITES BECOME SEQUENTIAL, NOT RANDOM

A B-tree (InnoDB's engine) satisfies a write by locating the exact page the key belongs on and updating it in place — for a large table with a cold cache, that page is essentially a random location on disk. An LSM-tree never does that on the write path: every write is appended to an in-memory memtable (backed by a write-ahead log for durability) in whatever order it arrives, and only later — in a background process called compaction — does the engine do the work of merging and reorganizing data into sorted, immutable SSTables on disk. Writes become sequential appends; the expensive reorganization work is deferred and batched. That single structural choice is why Uber's write-heavy trip, location, and event data fits an LSM-tree's shape better than a B-tree's.

ARC 06 · WHY THAT STILL HURTS

The LSM-tree's bill: read amplification, space amplification, and compaction cost

  • Reads get more expensive, not less. A key you wrote recently might still be in the memtable; if not, it might be in any of several SSTables at multiple levels, each of which must be checked (bounded by a Bloom filter that avoids most unnecessary disk reads, but not all of them). A single point read may need to consult the memtable plus several SSTables before it can be sure it has the newest version of a key — this is read amplification, and it is the direct price paid for deferring write-time reorganization.
  • Old versions and deleted keys linger until compaction removes them. An update doesn't overwrite a key in place — it appends a new version; a delete appends a tombstone marker. Both the old version and the tombstone occupy real disk space until a compaction pass merges them away — space amplification, the LSM-tree's mirror image of a B-tree's index bloat problem (chapter 14's Postgres MVCC bloat is the same phenomenon in a different engine).
  • Compaction itself is not free — it is real, sustained background I/O and CPU. Merging SSTables means reading multiple files, merging their sorted contents, and writing new files — work proportional to the data being merged, running continuously in the background, competing with foreground reads and writes for the same disk and CPU.
  • Secondary indexes and cross-region replication are still hard — just hard inside the engine instead of inside application code. Docstore has to maintain each secondary index atomically with the row it indexes (via RocksDB's atomic write-batch primitive) and has to decide how asynchronous cross-region replication handles two regions writing to related keys at close to the same time — moving the problem into infrastructure doesn't make the problem disappear, it makes it one team's problem to solve well, once, instead of every application team's problem to solve badly, independently.
THE HONEST FRAME

An LSM-tree is not simply "faster" than a B-tree — it moves cost from the write path to the read path and to a background process, which is exactly the right trade for a write-heavy workload and exactly the wrong trade for a read-heavy, write-light one. Docstore's design bet is that Uber's workload — high write volume from trips, locations, and events — sits firmly on the write-heavy side of that line.

def put_with_index(row_key, row, indexed_field="driver_id"):
    batch = rocksdb.WriteBatch()                          # one atomic unit — all or nothing
    batch.put(primary_key(row_key), row.encode())
    old_value = read_old_indexed_value(row_key)          # needed to remove any stale index entry
    if old_value is not None and old_value != row[indexed_field]:
        batch.delete(index_key(indexed_field, old_value, row_key))
    batch.put(index_key(indexed_field, row[indexed_field], row_key), row_key)
    rocksdb.write(batch)                                  # single atomic commit to the WAL — index can never drift from the row

ARC 10 · PERFORMANCE / SCALE CHARACTERISTICS

What happens when writes outrun compaction

The single number that predicts an LSM-tree's health under load is simple: is the compaction throughput keeping up with the incoming write rate? If not, the number of files waiting to be compacted (and therefore the number a read must check) grows without bound.

  • Write path: O(1) amortized — an append to the memtable and the WAL, regardless of table size.
  • Read path: O(levels × log(entries per SSTable)) in the worst case — the memtable plus a bounded number of SSTables per level, each narrowed by a Bloom filter and binary search within the level.
  • Compaction backlog: grows whenever sustained write rate exceeds sustained compaction throughput — exactly the queueing-theory shape chapter 4 (dispatch) and chapter 9 (retry storms) both already taught you to recognize.

ARC 11 · REAL-WORLD INCIDENTS / CONTROVERSIES

Write stalls: a real, well-documented RocksDB/MyRocks operational pattern

Uber has not published a chapter-specific postmortem naming an internal Docstore incident, so this section is honest about that and instead teaches the real, publicly documented operational pattern that RocksDB's own project documentation describes for any engine built this way — the pattern any team running MyRocks or RocksDB at scale needs to plan for.

Pattern: the write stall, straight from RocksDB's own documented behavior

RocksDB's own public documentation describes exactly the failure mode §10's chart models: when the number of unflushed memtables or the number of L0 SSTables grows past configured thresholds — meaning the write rate has outrun compaction for long enough — RocksDB deliberately stalls or throttles incoming writes rather than let the backlog (and therefore read amplification) grow without bound. This is a documented, intentional safety mechanism, not a bug — but from the caller's point of view it looks exactly like the database suddenly got much slower, exactly when write volume was highest.

Why this matters operationally

A write stall triggered by a burst of write traffic (a viral event driving a spike in trip creation, for example) is a self-limiting problem in one sense — it protects the engine from unbounded read-amplification collapse — and a real availability problem in another — callers see elevated write latency exactly during the traffic spike they most needed the database to absorb. The standard, industry-documented mitigations are the same ones any LSM-tree operator reaches for: provision compaction throughput (I/O bandwidth, background threads) with real headroom above sustained write rate, not just average write rate, and treat "compaction backlog" as a first-class monitored signal, not an afterthought.

ARC 13 · CODE WALKTHROUGH

Reading an LSM-backed store: illustrative reference implementation

Docstore's actual internal source is not public. What follows is precise, representative pseudocode of how an LSM-tree-backed store with schema-aware secondary indexes is genuinely built in production — labeled as illustrative throughout, matching the real, public architecture of engines like RocksDB and MyRocks.

docstore/
├── ● engine/memtable.go — in-memory sorted write buffer + WAL append (§8a)
├── ● engine/compaction.go — leveled compaction: merge SSTables, drop old versions & tombstones
├── engine/sstable.go · bloomfilter.go — immutable on-disk sorted runs + per-file existence filters
├── ● index/maintainer.go — atomic write-batch: primary row + secondary index entries (§8b)
├── schema/registry.go — field definitions or a document schema is not the opaque-blob model anymore
├── shard/router.go — routes a key to its owning shard/region
└── replication/async_stream.go — ships committed writes toward other regions (ch. 17)

The core compaction loop, matching §8's leveled-compaction shape:

Go (illustrative)engine/compaction.go
func (c *Compactor) CompactLevel(level int) {
    inputs := c.pickOverlappingFiles(level, level+1)   // files whose key ranges overlap
    merged := mergeSorted(inputs, func(a, b Entry) Entry {
        if a.Seq > b.Seq { return a }             // keep only the newest version of a key
        return b
    })
    merged = dropTombstonesOlderThan(merged, c.gcHorizon)   // tombstones can finally be dropped once no read needs them
    newFiles := writeSSTables(merged, level+1)
    c.atomicallyReplace(inputs, newFiles, level+1)   // old files removed, new ones visible, in one metadata swap
}
WHY IT WAS BUILT THIS WAY

Compaction never mutates a file in place — it always reads inputs and writes brand-new SSTables, then swaps which files are "live" in one atomic metadata update. That discipline is what lets reads keep running against the old files while compaction is in flight, and it's what makes a crash mid-compaction harmless: the old files are still valid until the swap commits, so a crash before that point simply means the compaction attempt is retried, never that data is lost or half-merged. It's the same "never mutate, always replace" discipline chapter 15's Schemaless got from MySQL's own crash-safe writes — Docstore just applies it one layer lower, inside the engine itself.
