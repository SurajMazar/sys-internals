POSTGRESQL INTERNALS · CHAPTER 18

Replication: Streaming,
Logical & Slots

Chapter 10 showed that WAL already contains a complete, ordered description of every change made to the cluster. This chapter asks the obvious follow-on question: if another server simply consumed that same byte stream and replayed it, wouldn't it become a live copy of the database — for free? That single observation is the entire subsystem. Everything else — walsender, slots, logical decoding, timelines, pg_rewind — is engineering built to make that idea survive real networks, real disks filling up, and real failovers.

ARC 01 · THE PROBLEM

Durable is not the same as available

Chapters 10 and 11 solved a narrower problem than the one operators actually have. WAL plus checkpoints plus crash recovery guarantee that a single machine never loses a committed transaction — even across a power cut. They say nothing about what happens when that machine's disk controller dies, its data center loses power for six hours, or someone rm -rfs the wrong directory. Durability within one failure domain and availability across failure domains are different guarantees, and the second one is only obtainable by having the data exist, independently, somewhere else.

State that precisely and the requirements fall out:

  • A second, independent copy of every committed byte — on different disks, ideally a different host, ideally a different rack or region.
  • Bounded staleness — the copy should lag the primary by a known, small amount, so a failover loses a known, small amount of data (this is RPO — recovery point objective).
  • A fast path to promotion — turning the copy into the new primary should take seconds, not the hours of a restore-from-backup (this is RTO — recovery time objective).
  • Useful even when nothing has failed — read traffic offloaded to copies, and eventually, copies that hold a filtered or transformed view of the data for other consumers (analytics, CDC, search indexes).

PostgreSQL's answer starts from an observation you already have all the machinery for: WAL is a complete, ordered change feed of the entire cluster. If a second server can receive that feed and apply it in the same order, it ends up in the same state — and it ends up there continuously, not as a periodic snapshot. Replication, in other words, is not a new mechanism bolted onto Postgres; it is chapter 10's WAL, exported.

WHY THIS MATTERS FOR THE REMAINING CHAPTERS

Everything in this chapter is a consequence of one design fork: do you ship the physical byte stream (WAL exactly as written, page-oriented, version- and platform-locked to the sender) or do you ship a logical reconstruction of the row-level changes those bytes imply (portable, filterable, but requiring real machinery to rebuild)? Physical replication is nearly free — it reuses recovery's own replay loop. Logical replication is expensive and delicate — it has to invert WAL back into INSERT/UPDATE/DELETE semantics using a component, the reorder buffer, that doesn't exist anywhere else in the codebase. Keep that fork in view; every tradeoff in §9 traces back to it.

DEEP CONTEXT · WHY LOGICAL CAME SEVEN YEARS AFTER STREAMING

Physical streaming (9.0) was "just" teaching the existing recovery code path to read WAL from a socket instead of a file — a modest change to xlogrecovery.c and a new backend type. Logical decoding (9.4) had to solve a genuinely hard problem: WAL records physical byte changes to 8 KB pages, interleaved across every concurrently running transaction, with no obligation to record anything human-readable. Turning that into "table orders, row with id 42, column status changed from 'pending' to 'shipped'" requires a catalog snapshot as of the moment the WAL record was written (snapbuild.c) and a way to buffer a transaction's changes until it commits, since you cannot emit them if the transaction later aborts (reorderbuffer.c). Both are 9.4-and-later inventions; nothing like them existed in the original recovery code.

ARC 03 · NAIVE SOLUTION

Attempt #1: ship completed WAL files

Before streaming existed (and still a valid fallback today), the obvious approach is: every time the primary finishes writing a 16 MB WAL segment, copy that file somewhere the standby can pick it up, and have the standby's recovery process apply segments as they arrive. This is log shipping / warm standby, configured with archive_command on the primary and restore_command on the standby.

inipostgresql.conf — the file-shipping strawman
# On the primary: run whenever a WAL segment is complete
archive_mode = on
archive_command = 'rsync -a %p standby:/var/lib/pgsql/wal_inbox/%f'

# On the standby: pull segments back out of the inbox
restore_command = 'cp /var/lib/pgsql/wal_inbox/%f %p'
standby_mode = on  -- pre-12 syntax; recovery.conf existed as a separate file

This already delivers the headline feature: a second copy of the data, continuously updated, that survives the primary's disk dying. It is simple, requires no open TCP connection between the servers, and — because it reuses restore_command, the exact mechanism PITR base-backup recovery uses — it is really "recovery that never stops," not a new code path. That reuse is elegant. The strawman's failure mode is not correctness; it is granularity.

ARC 04 · WHY IT FAILS

You can only ship what's already a complete, closed file

archive_command fires when a WAL segment fills up or archive_timeout elapses — whichever comes first. Either way, the unit of transfer is a whole file, and that fact alone bounds how fresh the standby can ever be:

  • The staleness floor is your segment/timeout policy, not your workload. At the default 16 MB segments and a busy primary, a segment might fill every few seconds — fine. At a quiet primary you'd set archive_timeout (say, 60s) to force a segment closed periodically, meaning up to 60 seconds of committed transactions exist only on the primary at any instant. That is your RPO, and it is a policy knob, not a physical limit — which means someone has to tune it correctly, and it always trades off against archive volume.
  • The standby cannot serve reads while "warm." Before Hot Standby (9.0) a warm standby is receiving files but is not open for queries at all — it exists purely as a failover target, not a read-scaling mechanism. Every read still hits the primary.
  • Detecting a stuck pipeline is indirect. If rsync starts failing at 3am, nothing on the primary blocks — WAL archiving failures don't stop the primary from accepting writes, they just accumulate unarchived segments in pg_wal (a slow-motion disk-full incident you will meet again as a named incident in this very chapter). The standby, meanwhile, silently falls further behind with no signal beyond "the file I'm waiting for hasn't appeared yet."
THE NUMBERS

At a modest 200 write TPS with 200-byte average WAL records, the primary generates roughly 40 KB/s of WAL — a 16 MB segment closes every ~400 seconds without archive_timeout forcing it sooner. Left alone, your RPO is six-plus minutes of data, entirely as an artifact of file granularity — the hardware and network could ship every byte in milliseconds. The gap between "what the network can do" and "what file-oriented shipping delivers" is exactly what streaming closes.

The fix is obvious once stated: stop waiting for files to close. Open a connection and stream the bytes as they are generated. That is 9.0's contribution — and once you have an open connection, entirely new capabilities (synchronous acknowledgment, live lag measurement, feedback from standby to primary) become possible that file-shipping structurally cannot offer.

Four replication shapesSTEP-BY-STEP

PostgreSQL's actual path: ship physical WAL over a streaming connection as the default, general-purpose mechanism (fast, exact, nearly free to build) — then, seven years later, add logical decoding as an additional, opt-in layer above it for the cases where an exact byte-for-byte copy is the wrong tool.

THE CLINCHING ARGUMENT: REUSE THE REPLAY LOOP YOU ALREADY TRUST

Physical streaming won as the default because it needed almost no new correctness logic: the standby's startup process already knows how to replay WAL records idempotently (that's crash recovery, chapter 11) — streaming just feeds it records from a socket instead of files, continuously, and never stops. The trust you already have in recovery's correctness transfers directly. Trigger-based logical replication (Slony, Londiste) and statement-based replication (early MySQL) had to build and separately prove correct an entirely new code path with its own bug class (trigger overhead, non-deterministic statements like NOW() or random() replaying differently on each replica). Reusing recovery was the cheap, safe choice — and it's why physical replication shipped first.

ARC 06 · WHY THAT STILL HURTS

Exact copies are inflexible copies

Streaming physical replication is fast and correct by construction — and it buys you exactly one shape of standby: a byte-identical clone. That precision is also its ceiling:

  • All or nothing. You replicate the entire cluster — every database, every table — because WAL doesn't know about "just this schema." Want to replicate one tenant's tables into a reporting replica and nothing else? Physical replication cannot do it.
  • Version- and platform-locked. WAL's byte layout is tied to the primary's PostgreSQL major version, page format, and often CPU architecture assumptions (alignment, endianness). A physical standby cannot run a newer major version than its primary — which makes physical replication useless for online major-version upgrades.
  • Read-only, full stop. A hot standby can run SELECTs; it cannot accept independent writes to different rows, because there is exactly one WAL stream and one replay order — there is no room for a second writer without redefining what "the database" means.
  • Nothing outside PostgreSQL can consume it. The bytes are meaningless to Kafka, a search index, or a data warehouse. Every downstream consumer that isn't itself a PostgreSQL standby is locked out.
THE ANSWER, AND WHAT IT COSTS

Logical decoding (9.4) and logical replication (10) answer every one of those limits: publish a subset of tables, feed heterogeneous consumers (Kafka via Debezium, a data warehouse, a differently-versioned Postgres), and allow independent writes on the subscriber. The price is the reorder buffer, output plugins, an apply worker, initial data sync, and a long list of things that quietly do not replicate (DDL, and — before PG16 — sequence state). You are trading the "free, trusted" property of physical replication for flexibility, and every operational surprise in this chapter's incidents traces to someone forgetting that trade was made.

THE ASYMMETRY WORTH NOTICING

Every logical subscriber is, underneath, a physical-style client: it opens a replication connection and receives a byte stream over the exact same CopyBoth/XLogData protocol a physical standby uses. The difference is entirely in what the primary puts into that stream — raw WAL for a physical standby, versus the output of running WAL through a decoding pipeline (reorder buffer → output plugin) for a logical one. One walsender implementation, two very different payloads, selected by whether the replication slot backing the connection is physical or logical.

ARC 08 · INTERNAL IMPLEMENTATION

The wire protocol, the slot contract, and the decoding pipeline

Three mechanisms to internalize at implementation depth: (a) exactly what flows over the replication connection and how lag is measured from it, (b) what a replication slot guarantees the primary — and what that guarantee costs, (c) how the reorder buffer turns interleaved WAL into per-transaction row changes.

(b) Slots: a promise the primary makes about WAL retention

A replication slot (storage/slot.c, backed by ReplicationSlotPersistentData on disk under pg_replslot/) is the primary's side of a contract: "I will not remove WAL, nor — for a logical slot — vacuum away the catalog rows a decoder might need, until you (the consumer) tell me you no longer need them." A physical slot tracks only restart_lsn. A logical slot tracks restart_lsn and a catalog_xmin, because logical decoding must be able to look up what a table's columns looked like at the moment of an old WAL record — which means VACUUM on system catalogs cannot remove rows a lagging decoder still needs (this is the same xmin-pinning mechanism chapter 12 introduced for long transactions and hot_standby_feedback, wearing a different hat).

(c) Logical decoding: rebuilding transactions from interleaved WAL

WAL is written by every backend into one physical stream, in whatever order their commits happen to interleave — a decoder reading it sequentially sees transaction A's insert, then transaction B's update, then another A record, then A's commit. To hand a subscriber "here is everything transaction A did," the decoder must buffer per-transaction changes and only flush them when that transaction's commit record is seen — never before, because an abort must produce nothing. This is the reorder buffer (logical/reorderbuffer.c), fed by logical/decode.c's per-record-type dispatch and a catalog-consistent view of table structure built by logical/snapbuild.c.

WHAT DETERMINES A ROW'S IDENTITY: REPLICA IDENTITY

An UPDATE or DELETE's WAL record contains the new tuple, but a decoder producing a row-level change stream also needs to say which existing row changed — and the primary key columns aren't automatically old-tuple data in physical WAL. REPLICA IDENTITY (DEFAULT — the primary key; USING INDEX — a specific unique index; FULL — the entire old row; NOTHING — updates/deletes can't be decoded at all) controls how much of the old tuple wal_level=logical asks the executor to log alongside the new one. REPLICA IDENTITY FULL is the safety net for tables without a stable key, at the cost of logging (and shipping) the entire old row on every change — a real WAL-volume tax you pay for tables that need it.

Two more pieces close the loop from "decoded change" to "row applied on a subscriber": an output plugin turns the reorder buffer's internal representation into a wire format — pgoutput (built in, binary, used by native CREATE PUBLICATION/CREATE SUBSCRIPTION) or wal2json/decoderbufs (third-party, text/JSON/protobuf, the basis of Debezium-style CDC into Kafka) — and an apply worker (logical/worker.c) on the subscriber reads that stream and issues ordinary INSERT/UPDATE/DELETE through the normal executor, tracking its position via a replication origin so a restart resumes exactly where it left off rather than re-applying already committed changes.

ARC 10 · PERFORMANCE CHARACTERISTICS

Lag is a queueing problem, not a mystery

Three numbers explain almost every replication performance question you'll be asked to diagnose:

  • write_lag — time between the primary writing a WAL record and the standby's walreceiver acknowledging it's received and written to the standby's own WAL (not yet durable, not yet applied).
  • flush_lag — additional time until the standby has fsync'd that WAL to disk — the point at which a synchronous commit at level on can be acknowledged.
  • replay_lag — additional time until the startup process has actually applied those records to shared buffers — the point at which a read query on the standby would see the change, and the level remote_apply waits for.

Each of these is a queueing delay compounding across a pipeline: network transit time, the standby's disk write throughput, and the startup process's single-threaded replay rate (a hot standby's redo loop is fundamentally serial — it cannot parallelize across a data-dependency graph as freely as the primary's many backends did when they generated those changes). Drag the knobs below and watch lag diverge exactly the way Little's Law predicts: latency grows without bound once any one stage's throughput is exceeded.

WHY BYTE-LAG LIES ON AN IDLE SYSTEM

The naive metric — pg_wal_lsn_diff(sent_lsn, replay_lsn) — is zero whenever there's simply no new WAL being generated, whether the standby is perfectly caught up or has been disconnected for an hour and just hasn't received anything new to be behind on. The time-based lag columns (pg_stat_replication.write_lag etc., PG10+) fix this because they're computed from timestamps piggybacked on standby status updates, not from LSN arithmetic — but they still only update when traffic flows. Toggle "idle system" above and watch byte-lag flatline at zero while the connection is, in this scenario, actually stalled — the reason production monitoring should always pair lag metrics with a freshness check (last message received, replication connection still active in pg_stat_replication).

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: The forgotten slot that filled the disk

A team wired up Debezium against a logical replication slot to stream changes into Kafka. Months later the Kafka Connect worker crashed and was never restarted — nobody noticed because nothing downstream alerted on it. The slot, however, kept its promise: it retained every byte of WAL generated since the crash, because a consumer might still come back for it. pg_wal grew without bound until the primary's disk filled, at which point writes stopped entirely — a disconnected consumer of a side-channel feature took down primary write availability. Fixes, in order of leverage: alert on pg_replication_slots.active = false combined with growing restart_lsn distance; set max_slot_wal_keep_size (PG13+) as a hard backstop so a slot is invalidated rather than allowed to consume unbounded disk; treat "drop the orphaned consumer's slot" as a first-class incident-response runbook entry, not an afterthought.

Incident 2: Synchronous replication that quietly became a single point of failure

synchronous_standby_names was configured with a single named standby (not a quorum set). When that standby's availability zone had a network partition, every commit on the primary — from every application, every session — blocked indefinitely waiting for an acknowledgment that could not arrive. On-call engineers, seeing hung queries, cancelled them; the queries returned errors to their callers, who dutifully retried — except the original transactions had already committed locally before the wait began, so the retries silently double-applied. Fixes: use quorum syntax (ANY 1 (standby_a, standby_b, standby_c)) so no single standby's outage can block all commits; make application-level retries idempotent regardless of replication topology; monitor pg_stat_activity.wait_event = 'SyncRep' as a leading indicator before it becomes a full outage.

Incident 3: A failover without fencing — the old primary that wouldn't stay dead

An automated failover promoted a standby after the primary's health checks failed, but the failure was a transient network blip, not a real crash — the old primary came back reachable seconds later, still believing it was primary, and a stale connection-pool entry in one application tier kept sending it writes. Two "primaries" now had diverging timelines, each accepting commits the other never saw — classic split brain. Recovery required treating the old primary as permanently demoted, taking it offline entirely, and running pg_rewind against the new, real primary before it could safely rejoin as a standby. Fixes: STONITH-style fencing (forcibly power off or network-isolate a demoted node before promoting its replacement), a dedicated failover controller (Patroni, repmgr) that owns a single source of truth for who's primary, and treating "can I reach it" as insufficient evidence for "it's safe to write to it."

First, the sender's core loop — deliberately boring, because "boring and correct" beats "clever" for a piece of infrastructure every standby depends on:

Cwalsender.c — WalSndLoop(), simplified
static void
WalSndLoop(void)
{
    for (;;)
    {
        /* Standby asked to stop, or we've hit our target LSN */
        if (got_STOPPING() && NoMoreDataAvailable())
            break;

        /* New WAL since we last looked? Send it as an XLogData ('w') message */
        if (sentPtr < GetFlushRecPtr())
            XLogSendPhysical();          /* or XLogSendLogical() for a logical slot */

        /* No new data: sleep on the socket, but wake for a keepalive interval
         * even if idle -- standbys must not think we vanished.            */
        wakeEvents = WalSndComputeSleeptime(now);
        WaitLatchOrSocket(MyLatch, wakeEvents, ...);

        if (pq_is_send_pending())
            ProcessPendingWrites();

        /* Standby sent a status update ('r') or a reply to our keepalive?
         * Update its LSN bookkeeping and, if it's a sync standby, wake
         * any backend in SyncRepWaitForLSN() that's now satisfied.        */
        if (pq_getmessage() == 'r')
            ProcessStandbyReplyMessage();
    }
}

The slot's retention contract, which is what makes a forgotten consumer a disk-full incident rather than a silent no-op:

Cslot.c — ReplicationSlotsComputeRequiredLSN(), simplified
void
ReplicationSlotsComputeRequiredLSN(void)
{
    XLogRecPtr result = InvalidXLogRecPtr;

    for (int i = 0; i < max_replication_slots; i++)
    {
        ReplicationSlot *s = &ReplicationSlotCtl->replication_slots[i];
        if (!s->in_use)
            continue;

        XLogRecPtr restart_lsn = s->data.restart_lsn;   /* set at last confirm/acquire */
        if (result == InvalidXLogRecPtr || restart_lsn < result)
            result = restart_lsn;      /* the OLDEST need across every slot wins */
    }

    /* checkpointer/background writer consult this before ever recycling
     * a WAL segment -- a segment younger than `result` cannot be removed,
     * no matter how old it is or how full pg_wal has become.             */
    XLogCtl->replicationSlotMinLSN = result;
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. The primary trusts the slot, not the consumer. There's no heartbeat-based timeout in the base protocol — the primary keeps every byte a slot says it needs, forever, because a false "the consumer is dead" judgment would silently corrupt a replication stream, which is worse than a full disk (an operational problem with alarms and runbooks) — hence max_slot_wal_keep_size being an explicit, opt-in backstop rather than a default. 2. Retention is a MIN across all slots, computed once, cheaply. Instead of every checkpoint scanning consumer state, one cached LSN answers "can I recycle this segment?" in O(1). 3. Logical slots pin catalog xmin using the exact same "oldest need wins" pattern as physical slots pin WAL — one mental model, reused, is why chapter 12's bloat discussion and this chapter's disk-full discussion are the same failure shape wearing different clothes.
