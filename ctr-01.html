CONTAINER INTERNALS · CHAPTER 01

Genesis: From chroot
to the OCI Spec

A "container" is not a technology. It is a name we gave, after the fact, to a combination of kernel primitives that were invented decades apart, by different people, solving different problems, that nobody originally intended to be used together. This chapter reconstructs that combination piece by piece — chroot() in 1979, cgroups in 2006, namespaces trickling in across a decade, Docker's 2013 packaging of all of it — so that when later chapters open each primitive up, you already know exactly which gap it was invented to close and why the others weren't enough.

ARC 01 · THE PROBLEM

One kernel, many tenants, zero trust between them

Strip away every buzzword and a "container" is an answer to one very old operating-systems question: how do you run someone else's untrusted program on your machine without giving them your machine? Not a new machine — that's what a hypervisor sells, at the cost of an entire second kernel, second scheduler, second driver stack. The container's promise is narrower and cheaper: keep one kernel, and make N processes running under it believe, as convincingly as the kernel can arrange, that each one has the whole box to itself.

Unpacked, "believe it has the whole box" is actually four separate lies the kernel has to tell, and a real isolation technology has to tell all four or it isn't finished:

  • Filesystem lie. "Your / is the only filesystem." In reality it's a directory somewhere on the host, and every other tenant's files live one .. away.
  • Process-tree lie. "You are PID 1, and ps shows only your own descendants." In reality there are hundreds of other tenants' PIDs in the same flat kernel PID space.
  • Resource lie. "The CPU and RAM are yours." In reality every tenant shares the same physical cores and the same physical memory, and one greedy tenant can starve the rest — the classic noisy neighbor.
  • Privilege lie. "Root inside your world is root." In reality, if that's literally true, escaping to the real root outside is one kernel bug away.

What makes this hard is that no single kernel feature tells all four lies. Each one was solved by a different subsystem, invented for a different original purpose, at a different point in Unix history — and a "container" is simply the name the industry settled on, around 2013–2014, for the specific bundle of answers that turned out to compose cleanly. Nothing in this bundle required a new kernel concept invented specifically for containers; every primitive already existed for something else. That is the thesis of this chapter, and by §7 you'll be able to defend it precisely.

WHY THIS MATTERS FOR THE NEXT 15 CHAPTERS

Every later chapter is a deep dive into one of these four lies: chapters 2–4 cover namespaces (the process-tree, filesystem-visibility, and privilege lies), chapter 5 covers cgroups (the resource lie), chapter 6 covers the filesystem lie's storage layer (overlayfs), and chapters 7–8 cover capabilities and seccomp/LSMs (hardening the privilege lie further). Keep this chapter's four-lies framing in your head — it's the map for the whole course, and it's also exactly how DOCKER and PODMAN diverge: both tell the same four lies using the same kernel primitives, then differ entirely in who tells them — a root daemon, or your own shell.

ARC 02 · HISTORICAL CONTEXT

Forty-six years, four unrelated research threads

The primitives that make up a modern container were not co-designed. They came from four largely unconnected lineages — Bell Labs filesystem hacking, BSD security research, Sun's commercial Unix, and Google's internal datacenter scheduler — and only converged because Linux happened to accumulate all four. DEEP CONTEXT · CONVERGENT EVOLUTION, NOT A MASTER PLAN

chroot() (1979) solved a build-isolation problem inside AT&T's own toolchain. FreeBSD jails (2000) and Solaris Zones (2004) were built by commercial Unix vendors chasing multi-tenant hosting revenue — a completely different industry than Linux kernel development at the time. Linux cgroups (2006) came out of Google's need to schedule thousands of internal jobs on shared machines — a scheduling problem, not a security problem. Linux namespaces trickled in as separate patches from separate authors across nearly a decade (mount, 2002; UTS/IPC/PID, 2006; network, 2009; user, 2013) each solving one narrow visibility problem. Nobody at any of these four points was building "Docker." The convergence is the story.

ARC 03 · NAIVE SOLUTION

Attempt #1: chroot() alone

Derive it honestly, starting from the oldest tool in the box. Bill Joy added chroot() to Unix in 1979 (it shipped in 7th Edition, 1979, and BSD picked it up in 1982) so that a build could compile inside a directory tree that looked like / without touching the real one. The syscall does exactly one thing: it changes what a process — and every path it resolves afterward — considers to be its filesystem root.

Cnaive_container.c — the strawman, annotated
int main(void)
{
    /* 1. Point the process root at an extracted "image" directory. */
    chroot("/var/lib/naive/rootfs");      /* root inode changes; nothing else does */

    /* 2. Mandatory: chroot() does NOT change the cwd. Forget this
     *    line and relative-path lookups can still walk out.        */
    chdir("/");

    /* 3. Hand off to the "containerized" program. */
    execve("/bin/sh", argv, envp);
                                       /* ← still UID 0 if we started as root,      */
                                       /*   still sees every PID on the host,        */
                                       /*   still shares the host's every CPU/RAM    */
                                       /*   limit, still has every capability root   */
                                       /*   has, unrestricted.                       */
}

This already solves a real slice of the filesystem lie: ls / inside now shows the image's root, not the host's. That is genuinely useful and it is why chroot-based tools (BSD's jail ancestor chroot(8), countless build systems, early game servers) stayed in production use for decades. ARC 04 · WHY IT FAILS

chroot was never a security boundary — the kernel documentation says so

The manual page for chroot(2) on every modern Linux distribution contains, almost verbatim since the 1990s, a warning that this call "is not intended to be used for any kind of security purpose." Three concrete, reproducible reasons back that up, and each one maps directly onto one of §1's four lies still being unsolved:

  • The escape is a two-syscall trick, not a bug. A process with CAP_SYS_CHROOT (which root has by default) can call open("/", O_RDONLY) before chrooting to stash a file descriptor on the real root, then after chrooting into a fake root, call fchdir(fd) to jump the current directory back outside the jail, then chroot(".") again — because chroot() changes the root inode but leaves the current working directory exactly where it was if you engineer the order of operations. A handful of lines of C, no CVE required, no kernel vulnerability — this is the syscall working exactly as specified.
  • Zero resource isolation. A fork() bomb or a memory-hogging process inside the chroot is a fork bomb or a memory hog on the host — same PID space, same scheduler run queue, same physical RAM. The resource lie is entirely unaddressed; chroot was never trying to solve it.
  • Zero process-tree isolation. ps aux inside the chroot still walks /proc and sees every PID on the host, because /proc is a kernel-wide view unless something else (a mount namespace, chapter 2) gives each process its own. A "contained" process can kill() any host PID it has permission to signal.
THE NUMBERS

Quantify the blast radius, not just qualify it: a default Linux host commonly runs with ~40 POSIX capabilities available to root (chapter 7 enumerates them), zero memory or CPU ceiling on a bare process, and a PID space shared 1:1 with the host. A chroot-only "container" changes exactly one of those numbers — the filesystem root — and leaves the other three untouched. If your mental model is "4 lies to tell," chroot alone tells 0.25 of one lie convincingly and the rest not at all.

So the 1979 primitive is necessary but wildly insufficient. Two commercial Unix vendors noticed this within the following two decades and built purpose-made jails; Linux, arriving late to the isolation-as-a-feature party, eventually assembled something structurally similar out of independently-invented parts. §5 walks that assembly.

ARC 05 · BETTER: LAYER PRIMITIVES ON TOP

FreeBSD jails, Solaris Zones, and Linux's slower, piecewise answer

Candidate A: FreeBSD jail(8), 2000 — chroot, hardened into an actual boundary

Poul-Henning Kamp and Robert Watson designed jail() specifically to close chroot's escape hatches: a jailed process cannot chroot() back out (the syscall is restricted), gets its own bound IP address for network isolation, and has an explicit, enforced ceiling on which superuser operations it can perform at all — jail root is deliberately weaker than real root, checked by the kernel at each privileged call site, not by convention. This was the first widely-deployed system where "container-like isolation" was a designed security feature rather than a filesystem convenience.

Candidate B: Solaris Zones, 2004 — full OS-level virtualization, one kernel

Sun went further: each zone gets its own view of process IDs, its own filesystem namespace, its own network stack, and (paired with Solaris Resource Manager) enforced CPU and memory caps — the resource lie is finally addressed, years before Linux had an equivalent. Zones are, structurally, closer to what we'd today call a "container" than anything Linux had before 2008. The catch: Solaris's market share was shrinking exactly as this technology matured, so the ecosystem effect it might have had never fully materialized outside Sun shops.

Candidate C: Linux, piece by piece, 2002–2008

Linux took the slow, unglamorous route: instead of one integrated "container" subsystem, distinct kernel patches from distinct authors solved distinct slices of the four-lies problem, on their own schedules, for their own reasons:

  • Mount namespaces (2002) — Al Viro's work let each process group have its own view of the mount table, a real generalization of what chroot only half-solved.
  • cgroups (2006) — started inside Google as "process containers," renamed control groups before merge (Paul Menage, Rohit Seth); the first Linux mechanism to actually cap and account for CPU, memory, and I/O per group of processes — solving the resource lie that chroot never touched.
  • UTS, IPC, PID namespaces (2006–2008) — hostname, SysV IPC, and finally process-ID isolation, landing across several kernel releases as separate, independently-reviewed patch sets.
  • LXC, 2008 — the first tool to combine namespaces + cgroups + chroot-style rootfs switching into one user-facing command. This is the real milestone: not a new kernel primitive, but the first successful composition of existing ones into something usable.
Building LXC's isolation out of independent partsSTEP-BY-STEP
THE CLINCHING REALIZATION

By 2008, Linux had every primitive needed to tell all four lies from §1 — it just required a user to manually assemble seven or eight separate syscalls and cgroup filesystem writes, get the ordering right, and remember all of it every time. LXC was the first project to package that assembly as a single command. This is the exact gap Docker will walk into five years later — and note precisely what's left to invent at that point: nothing at the kernel level. The remaining problem is entirely one of packaging, distribution, and ergonomics.

ARC 06 · WHY THAT STILL HURTS

LXC solved isolation; it left "how do I ship this to someone else" completely unsolved

By 2010, a systems engineer who knew the incantations could build an LXC container that told all four lies competently. That did not make containers popular — LXC adoption outside a narrow band of Linux power users stayed limited for years, for reasons that have nothing to do with isolation quality:

  • No standard image format. An LXC container was a directory tree plus a hand-written config file. Moving "my container" to a colleague's machine meant tarring a rootfs and hoping paths, UIDs, and library versions lined up. There was no content-addressed layering, no registry, no notion of a reusable base image.
  • Configuration was expert-only. Correctly composing namespace flags, cgroup hierarchies, capability drops, and AppArmor profiles by hand was error-prone even for kernel-literate engineers — one missed flag and you had a chroot-only false sense of security again.
  • No developer workflow. There was no equivalent of "one file describes how to build this, one command builds it, one command runs it, one command ships it." Each of those steps existed as a pile of separate, unglamorous shell scripts per team.
  • No shared ecosystem. Nothing like a public registry of prebuilt, versioned, comparable base systems existed — every shop's LXC templates were bespoke.
THIS IS THE GAP DOCKER ACTUALLY FILLED

Docker, launched by dotCloud in March 2013, initially used LXC directly as its execution backend (it switched to its own libcontainer, later extracted as runc, in 2014-2015 — covered in chapter 9). Read Docker's real 2013 contribution precisely, because getting this exactly right is the point of this chapter: Docker did not invent namespaces, cgroups, or chroot-style rootfs switching — all of that existed and worked. Docker invented the Dockerfile (a build recipe), layered, content-addressed images (build once, share layers, diff cheaply), Docker Hub (a public registry), and a three-command workflow — build, push, run — that took container adoption from a niche Linux practice to a default developer expectation within about two years. The isolation story didn't change; the distribution story did, completely.

ARC 07 · FINAL ARCHITECTURE

The stack you actually run today

Docker's rapid rise created an obvious commercial risk: if "container" meant "whatever Docker's proprietary format does," every other vendor (Red Hat, Google, CoreOS, Amazon) was building on someone else's private spec. The industry's answer, June 2015, was the Open Container Initiative (OCI), a Linux Foundation project that split the problem into three independent, versioned specifications and — critically — Docker donated its container-execution code, extracted as runc, as the OCI's founding reference runtime. THE ASYMMETRY THAT DEFINES THE REST OF THIS COURSE

Both engines sit on the identical kernel-primitive floor and the identical OCI specs — that floor is not where Docker and Podman differ, and this course will say so plainly every time it's true. Where they diverge is the two rows above it: DOCKER talks to a long-running, typically root-owned background daemon (dockerd) that in turn talks to containerd, which execs runc; PODMAN has no daemon at all — the podman command is itself the process that forks and execs crun directly, in your own user session by default. Chapter 12 dissects this split down to the process tree; for now, know that it exists and that it is an architectural choice layered on top of identical primitives, not a different set of primitives.

ARC 08 · INTERNAL IMPLEMENTATION

The actual syscalls, in the actual order

Time to be precise about mechanism. Modern container creation is not chroot() plus config — it is almost entirely one syscall, clone(), called with a bitmask of namespace flags, followed by cgroup filesystem writes and capability-set manipulation. Here is the real sequence a low-level runtime (runc or crun) executes.

(a) clone() with namespace flags — one syscall, up to eight isolated views

Unlike fork() (no flags — the child just gets a full copy) or chroot() (touches only the filesystem root), clone(2) takes an ORed bitmask telling the kernel exactly which namespaces to create fresh for the new process, versus which to inherit from the parent. Step through what each flag actually buys, in the order a real runtime typically requests them:

clone(2) flag by flagSTEP-BY-STEP
THE REAL SIGNATURE

long clone(int (*fn)(void *), void *stack, int flags, void *arg, ...); — the flags argument for a full container is typically CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWUSER | CLONE_NEWCGROUP | SIGCHLD. Since Linux 5.3 (Christian Brauner's work), the same effect is reachable more safely and atomically via clone3() with a struct clone_args, avoiding some historical argument-ordering foot-guns of the original clone(). Both runc and crun support both call shapes depending on kernel version.

(b) cgroup limits — writing files, not calling syscalls

Unlike namespaces, cgroups v2 (chapter 5's full subject) are configured through a virtual filesystem, not a syscall: the runtime mkdirs a directory under /sys/fs/cgroup/, then writes plain text into interface files. ARC 11 · REAL-WORLD PRODUCTION

  
Three moments where "just chroot it" got someone paged


  
Incident 1: the chroot-escape talks that never stop recurring (ongoing since the 1990s)

  
Variations of the fchdir()-based chroot escape from §4 have been rediscovered and published
  as "new" findings for over two decades — precisely because the underlying behavior is not a bug, it's the
  documented contract of chroot(2). Any tool built after ~2010 that advertises security by chroot
  alone (some early PaaS sandboxes, some FTP daemons' "jailed" modes) has had a public writeup demonstrating an
  escape. The root cause is always the same one line in the man page nobody read: chroot changes the root
  inode, not the security model.


  
Incident 2: the 2014 "Shocker" exploit and Docker's early hardening response

  
In mid-2014, researcher Sebastian Eggert (and, separately, other public writeups the same year) demonstrated
  that a default Docker container of that era — which at the time ran with a very permissive capability set and
  no seccomp filtering by default — could access the host's /dev device nodes with sufficient
  capabilities to read raw block devices and escape container boundaries entirely. It wasn't a kernel
  vulnerability; it was Docker shipping isolation primitives without turning on enough of them by default. The
  direct consequence, landing across Docker 1.10–1.12 (2016), was a much more conservative default capability
  drop-list and a default seccomp profile blocking ~44 syscalls — the profile chapter 8 has you build by hand.
  This is the moment "secure by default" became a stated Docker design goal rather than an assumption.


  
Incident 3: the cgroups v1 "no internal processes" confusion and silent resource-limit misses

  
Under cgroups v1's multi-hierarchy design (superseded by the unified v2 hierarchy this course uses
  throughout — chapter 5), it was possible to attach a process to a cgroup that also had child cgroups with
  their own limits, in a way where the parent's own memory accounting silently undercounted work happening in a
  child hierarchy a monitoring tool wasn't watching. Teams running early container platforms on cgroups v1
  reported containers that blew past intended memory ceilings during exactly this kind of hierarchy
  misconfiguration, with the OOM killer's behavior appearing "random" until the actual hierarchy was
  audited. cgroups v2's single unified tree and "no internal processes" rule (chapter 5) were designed
  specifically to make this class of mistake structurally impossible rather than merely documented against.

And the lifecycle every OCI-compliant low-level runtime — runc, crun, or anything else — must implement
  identically, regardless of which higher-level engine drives it:


  

    
shellthe OCI runtime lifecycle, called directly — no Docker, no Podman

    
# create: sets up namespaces/cgroups/mounts, does NOT start the user process yet
runc create --bundle ./my-oci-bundle mycontainer

# start: execs process.args inside the already-prepared environment
runc start mycontainer

# state: query the container's current lifecycle state (creating|created|running|stopped)
runc state mycontainer

# kill / delete: send a signal, then tear down cgroup + namespace bookkeeping
runc kill mycontainer SIGTERM
runc delete mycontainer

  


  

    
WHY THE SPEC SPLITS "CREATE" FROM "START" — A DESIGN CHOICE WORTH STEALING

    
Separating create (build the sandbox) from start (run the payload) exists so a
    higher-level engine — Docker's containerd-shim, Podman's conmon — can attach
    monitoring, set up stdio streaming, and register the container's state before the user's actual
    command executes, closing a race window where a fast-exiting process could finish before anything was
    watching it. Both Docker and Podman's supervisor processes (chapter 12) depend on this exact two-phase
    lifecycle; it's an OCI Runtime Spec requirement, not an implementation detail either engine invented.
