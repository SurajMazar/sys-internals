CONTAINER INTERNALS · CHAPTER 09

The OCI Runtime Spec:
runc, crun & config.json

Strip away docker run and podman run entirely and there is still a working container underneath: a directory holding a root filesystem and one JSON file, handed to a small binary that knows exactly four verbs. Everything Docker and Podman do on top — image pulls, networking, compose files, pods — is orchestration bolted onto that one narrow, versioned contract. This chapter hand-writes the contract.

ARC 01 · THE PROBLEM

Every engine needs the same primitive — but whose?

By 2015, "container" already meant several incompatible things. Docker shipped its own libcontainer, CoreOS's rkt ran its own appc-format containers with its own launcher, and every PaaS and scheduler that wanted to "run a container" had to either shell out to a specific engine's CLI or vendor that engine's internal Go packages directly into its own codebase. None of these low-level launchers agreed on an image format, a filesystem-bundle layout, or even what "running" versus "created" meant for a container process.

This is a familiar shape of problem: a specific mechanism (namespaces + cgroups + capabilities + a chrooted filesystem — chapters 2 through 7 gave you every primitive involved) has stabilized, but the interface to that mechanism has not. Every orchestrator that wants to launch a container — Kubernetes' kubelet, Docker's engine, a CI runner, a bare shell script — faces the same three questions with no shared answer:

  • What does "the container to run" look like on disk? A directory? A tarball? Which file names, which layout?
  • What does "run it" mean as an API? One blocking call? A background daemon? What are the valid states a container can be in, and what are their names?
  • Who is allowed to write a different implementation of the launcher — a Go one, a C one, a Rust one, one that uses a microVM instead of namespaces — and still be a legitimate participant in the ecosystem?

The Open Container Initiative's answer is not a piece of software — it's a contract. The OCI Runtime Specification defines exactly two things with no room left for interpretation: the on-disk shape of a bundle (a root filesystem plus one config.json), and a small set of lifecycle operations — create, start, kill, delete — that any conforming runtime binary must expose and any conforming higher-level engine can drive. runc (Docker's donated reference implementation, Go) and crun (Red Hat's from-scratch reimplementation, C, and Podman's default) are two independently written binaries that both satisfy that one contract — which is the entire point: you can swap one for the other underneath Docker, Podman, containerd, or CRI-O, and nothing above the runtime boundary needs to know or care.

WHY THIS MATTERS FOR THE NEXT SEVEN CHAPTERS

This chapter is the floor everything else in the second half of the course stands on. Chapter 10's image layers exist to produce the rootfs half of a bundle. Chapter 11's registries exist to distribute the layers that become that rootfs. Chapter 12's daemon-vs-fork-exec comparison is really a comparison of what sits above the exact four verbs you'll call by hand in this chapter's simulator. Once you've run a container with zero Docker and zero Podman involved, every later "under the hood, this calls runc" sentence stops being a hand-wave.

DEEP CONTEXT · WHY DOCKER GAVE THIS AWAY

Donating libcontainer to become runc, under a foundation Docker didn't unilaterally control, looks like giving up leverage — and it was, deliberately. By 2015 Docker's real business risk wasn't a competitor cloning its CLI; it was the ecosystem fragmenting around rkt's incompatible format and Kubernetes needing a runtime interface it didn't have to reverse-engineer from Docker's changing internals. A shared, boring, versioned spec that Docker no longer fully owned was the price of staying the default — and it worked: containerd, CRI-O, and eventually every Kubernetes CRI shim standardized on OCI runtimes, which is precisely why Podman, a project with zero Docker code in it, can run the exact same bundles Docker produces.

ARC 03 · NAIVE SOLUTION

Attempt #1: every engine ships its own bespoke launcher

Derive the failure honestly by building the thing the spec replaced. Before a shared contract, the obvious approach is: each engine hardcodes its own isolation logic directly against the kernel, with its own ad hoc on-disk format and its own notion of "running."

bashbespoke_launcher.sh — the strawman, annotated
# Engine A's private launcher — invented, versioned, and understood by nobody but Engine A
launch() {
    local id=$1 rootfs=$2 cmd=$3
    # Namespaces, mounts, cgroup paths — all hand-rolled, all Engine A's private conventions
    unshare --pid --mount --uts --ipc --net --fork \
        chroot "$rootfs" $cmd &
    echo $! > "/var/run/enginea/$id.pid"   # "running" = a PID file exists. That's the whole state machine.
}
# Engine B, written independently, invents a DIFFERENT directory layout, a DIFFERENT
# state file format, and has no idea Engine A's launcher, or its containers, exist.

This is not a strawman built to be knocked down cheaply — it is exactly what Docker's own internals looked like pre-2014, and what rkt's launcher looked like in parallel. It gets the isolation itself right (the primitives from chapters 2–7 don't care who calls them); what it gets wrong is legibility to anyone else. Watch it fail as soon as a second party needs to interoperate with it.

ARC 04 · WHY IT FAILS

The integration math: O(N×M) versus O(N+M)

Quantify what "everyone invents their own launcher" actually costs an ecosystem. Let N be the number of container engines/runtimes (Docker's libcontainer, rkt, LXC-based tools, a cloud provider's proprietary launcher…) and M be the number of things that want to drive one (Kubernetes, Nomad, a CI system, a PaaS control plane, systemd). With no shared contract, every orchestrator must write and maintain a bespoke adapter per engine it wants to support:

  • Integration surface: N × M adapters. Kubernetes alone, supporting Docker and rkt in its earliest multi-runtime era, needed engine-specific code paths inside kubelet itself — not a plugin boundary, a fork in the control-plane logic. Add a third runtime and every orchestrator that cares about portability pays again.
  • No shared verification. "Is this container running?" has a different true answer depending on which bespoke state file format you're parsing — a PID file, a lock file, a database row. There is no single command any tool can run against any runtime to get a trustworthy answer.
  • Innovation is gated by the incumbent. A new, better low-level runtime (say, one written in a memory-safe language, or one that starts 2× faster) has no path to adoption without also either cloning an incumbent's entire private API or convincing every orchestrator to add a bespoke adapter just for it.
THE NUMBERS

With a shared spec, the integration surface collapses from N × M to N + M: each runtime implements the spec once, each orchestrator implements calling the spec once, and the two sets meet at a single, versioned interface neither side controls unilaterally. This is exactly the argument that let Kubernetes retire dockershim in 2022 without breaking clusters: kubelet had already moved to speaking CRI against any OCI-compliant runtime years earlier — Docker's engine became one implementation choice among several (via cri-dockerd), not a hardcoded dependency.

So the fix is not "pick the best bespoke launcher and standardize on it" — that just relabels the N×M problem with N=1 today and a hard fight over who gets to be N=2 tomorrow. The fix has to be a contract nobody privately owns. §5 derives its minimum viable shape.

ARC 05 · BETTER SOLUTION

Deriving the minimum viable contract

Work out, from first principles, the smallest interface that lets any runtime and any orchestrator interoperate without either seeing the other's source code. It needs exactly three things: a description of what to run, a description of where it is on disk, and a fixed, small vocabulary of verbs with unambiguous state transitions. Step through the derivation:

Building the OCI runtime contract from nothingSTEP-BY-STEP

Two runtimes — runc and crun — are the two implementations this course cares about, because they're the ones Docker and Podman actually ship by default. Neither is "the" reference in a privileged sense any more; both are simply judged against the same spec text:

  • runc — Go, the direct descendant of Docker's original libcontainer, donated to OCI in 2015. Docker/containerd's default low-level runtime today.
  • crun — C, written from scratch in 2018–2019 by Giuseppe Scrivano at Red Hat specifically to be smaller and faster to start than runc. Podman's default low-level runtime since around Podman 2.0 (2020) on Fedora-family distributions.
THE CLINCHING PROPERTY: THE SAME JSON COMES OUT

Ask runc state mycontainer and crun state mycontainer about the exact same container and — running under the exact same engine — you get structurally identical JSON: ociVersion, id, status, pid, bundle. Two teams, two languages, zero shared code, and the output is indistinguishable at the schema level. That convergence is not a coincidence of good taste — it's the spec doing exactly its job. §8 shows you the schema; §15 lets you generate it from both runtimes yourself.

ARC 06 · WHY THAT STILL COSTS

A shared interface is not a shared guarantee

The spec solves the interoperability problem completely and solves almost nothing else. Be precise about what "OCI compliant" does not promise, because every one of these gaps becomes an operational surprise eventually:

  • Compliance is a schema, not a security level. A runtime that starts a full hardware-virtualized guest per container — Kata Containers, wrapping a microVM around the workload — can be just as OCI-compliant as runc, because the spec only mandates the bundle format and the four verbs, never how isolation is achieved. Same for gVisor's runsc, which intercepts syscalls in a userspace kernel instead of trusting the host kernel's namespace boundary directly. "OCI compliant" tells you nothing about blast radius if the container escapes.
  • Feature adoption is not synchronized. When the spec adds a field — say, a new hook type, or a new linux.resources sub-object for a kernel feature that just landed — runc and crun implement it on their own schedules. A config.json built assuming the newest field silently no-ops on an older runtime binary that doesn't recognize it, or hard-fails, depending on how strict that runtime's parser is.
  • The spec covers Linux almost exclusively in practice. Runtime-spec technically has provisions for Windows and Solaris containers, but the overwhelming majority of real usage, tooling, and this course's depth is Linux namespaces/cgroups — treat non-Linux OCI runtimes as a footnote, not a parallel universe with equal engineering investment.
  • Two compliant runtimes can still disagree at the edges. Default capability lists, exact error message text, and behavior on malformed-but-not-technically-invalid input are all under-specified enough that runc and crun occasionally diverge on corner cases — which is precisely why §9's comparison table exists instead of a single "OCI runtime" row.
THE HONEST TAKEAWAY

"This runtime is OCI compliant" answers exactly one question — can my orchestrator drive it without engine-specific code — and answers zero questions about performance, memory safety, or how hard it is to escape from. Treat the spec as what it is: a wire-format and lifecycle contract, not a security certification. §10 makes the security comparison explicit and honest instead of assuming compliance implies equivalence.

ARC 08 · INTERNAL IMPLEMENTATION

The bundle, the state machine, and the two binaries that consume both

Three pieces, in order: (a) what actually lives inside config.json, field by field; (b) the exact state machine create/start/kill/delete drive a container process through, including the synchronization primitive that makes the create/start split meaningful rather than cosmetic; (c) what a resource-limit slider actually turns into on disk.

(a) config.json, field by field

(b) The lifecycle: create, start, kill, delete

The OCI runtime spec defines exactly four states a container can report through status: creating, created, running, stopped. The interesting engineering is in the gap between created and running — it exists on purpose, and it's implemented with a real synchronization primitive, not a sleep.

WHY SPLIT CREATE AND START AT ALL?

Because networking has to happen in between. A container's network namespace exists the instant create returns — but the workload hasn't executed a single instruction yet. That gap is exactly when a CNI plugin (chapter 13) wires up the interface, assigns an address, and installs routes — entirely from the host side, entirely before the container's own code could possibly observe or interfere with its own network setup. If create and start were one call, there would be no window in which "the namespace exists but nothing has run inside it yet" — and every orchestrator would need its own racy workaround.

On attack surface: runc's codebase is larger (the Go standard library plus vendored namespace/cgroup
  packages) but memory-safe outside its cgo boundary; crun's is smaller (easier to audit end-to-end) but written
  in a language where a single missed bounds check is a memory-corruption bug, not a panic. Neither property has
  historically dominated — §11's incidents are almost all logic bugs (race conditions, path handling)
  that could occur in either language, which is the honest conclusion: implementation language changes the
  kind of bug you should expect, not whether bugs happen.







  
ARC 11 · REAL-WORLD INCIDENTS

  
When the runtime binary itself is the vulnerability

  
CVE-2019-5736 — the runc binary overwrite (full syscall trace in chapter 15)

  
A malicious container, given the chance to run as PID 1 during runc exec/start,
  could exploit a race on /proc/self/exe to overwrite the host's own runc binary with
  attacker-controlled content — turning "I can run a container" into "I can run arbitrary code as root the next
  time anyone on this host invokes runc." This is the runtime-spec chapter's version of the story: the
  bug lived in the exact create/start code path §8(b) just walked — the moment between namespace setup and the
  final execve() of the user's process is precisely where the vulnerable file handle existed.
  Chapter 15 replays the exact syscall sequence; here, the lesson is architectural: the runtime binary and
  the untrusted workload briefly share a trust boundary during that exact create→start window, and getting
  that window's file-descriptor hygiene wrong is catastrophic precisely because the runtime runs privileged.

  
CVE-2019-16884 — masked/read-only paths bypassed via a crafted mount

  
linux.maskedPaths exists specifically to hide procfs/sysfs files a container shouldn't read
  even from inside its own PID namespace (/proc/kcore, /proc/keys, and similarly
  sensitive nodes). This runc advisory showed that a specially crafted mount destination could interact badly
  with AppArmor/SELinux label application during mount setup, letting a container's process influence a path the
  masking was supposed to fully own — a reminder that maskedPaths/readonlyPaths are
  only as strong as the mount-setup code that applies them, not an independent enforcement layer.

  
CVE-2021-30465 — a symlink TOCTOU in mount-path resolution

  
runc resolved a mount's destination path, then performed the mount — with a window between the two in
  which a malicious container process (racing against its own creation) could swap a directory for a symlink
  pointing at the host filesystem, causing the runtime to bind-mount into a host path instead of the intended
  container path. The root cause is a class every implementation of the mounts-array handling in §8(a) has to
  defend against: resolve-then-act path handling is inherently racy against a party who controls the
  filesystem being resolved. The fix added safe, symlink-aware path resolution (rather than resolve-once,
  trust-forever) directly into runc's mount-setup code — the same lineage of fix that later informed
  library-level safe-path APIs across the ecosystem.

  

    
THE PATTERN ACROSS ALL THREE

    
None of these are cryptography failures or capability-list mistakes — they're all races or trust-boundary
    slips in the narrow window where the runtime, running privileged, is still setting up isolation around
    a process that already exists and is already attacker-controlled. That window is unavoidable — you cannot
    isolate a process before it exists — which is exactly why "OCI compliant" (§6) says nothing about how
    carefully a given implementation guards that window. crun's smaller, newer codebase has a shorter public CVE
    history than runc's, but that reflects less accumulated scrutiny more than a proven architectural advantage —
    an honest comparison neither runtime's advocates like to hear.

runc's create/start split, simplified but structurally faithful to the real dispatch:

  

    
Gorunc — create.go / standard_init_linux.go, the barrier

    
// create.go — "runc create": sets everything up, does NOT run the user's command yet
func createContainer(context *cli.Context, id string, spec *specs.Spec) error {
    config, _ := specconv.CreateLibcontainerConfig(&specconv.CreateOpts{
        Spec: spec,           // the parsed config.json
    })
    factory, _ := libcontainer.New("/run/runc")      // state dir root
    container, _ := factory.Create(id, config)     // namespaces + cgroup dirs created HERE

    // Start(process, /*isInit=*/true) forks the container's init process into the
    // new namespaces, then RETURNS as soon as that process is blocked — not
    // once it's running the real command.
    return container.Start(spec.Process)
}

// standard_init_linux.go — this function's goroutine is now living INSIDE the
// new PID/mount/UTS/IPC/net namespaces. It does every remaining namespace-
// internal setup (pivot_root, capability drop, seccomp load — chapters 6–8),
// then blocks:
func (l *linuxStandardInit) Init() error {
    /* ... pivot_root, mount the bundle's mounts[], drop capabilities,
         apply seccomp filter ... */

    fifoFd, _ := unix.Open(execFifoPath, unix.O_RDONLY|unix.O_CLOEXEC, 0)
    var buf [1]byte
    unix.Read(fifoFd, buf[:])     // BLOCKS here — this IS the "created" state.
                                //    "runc start" opens this fifo for WRITING,
                                //    which is the only thing that unblocks this read.

    return unix.Exec(spec.Process.Args[0], spec.Process.Args, spec.Process.Env)  // execve() — NOW it's "running"
}

  


  
crun's equivalent shape — a plain sync socket instead of a named fifo, same purpose:

  

    
Ccrun — src/libcrun/container.c, the same barrier in C

    
int
libcrun_container_run(libcrun_container_t *container, int detach, libcrun_error_t *err)
{
    int sync_socket[2];
    socketpair(AF_UNIX, SOCK_STREAM, 0, sync_socket);

    pid_t pid = crun_clone(container_init, get_namespace_flags(container), args);
    /* get_namespace_flags() turns linux.namespaces[] into the actual
       CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | ... bitmask — chapter 2/3's clone() flags,
       literally read out of config.json */

    write_cgroup_files(container, pid);     /* memory.max, cpu.max, pids.max — §8(c) */

    if (!detach)
        wait_for_container_ready(sync_socket[0]);   /* "created" */

    return pid;
}

static int
container_init(void *args)
{
    /* pivot_root, mount() the mounts[] array, capset(), seccomp load — same
       kernel-facing work as runc's Init(), different language */

    notify_ready(sync_socket[1]);      /* tell the parent: I'm set up, waiting */
    wait_for_start_signal(sync_socket[1]);  /* BLOCKS — "crun start" writes the go-ahead byte here */

    return execve(process->args[0], process->args, process->env);  /* "running" */
}

  


  

    
WHY BOTH TEAMS BUILT A BARRIER, INDEPENDENTLY

    
1. The state must be observable from outside the process being created. A named fifo (runc) or a
    socketpair (crun) both give the parent a synchronous, kernel-mediated signal — no polling, no races against
    "has it execve'd yet." 2. The barrier lives on the child side of every namespace boundary. By the time
    either implementation blocks, pivot_root, capability drop, and seccomp load have already happened — so the
    blocked process is already fully caged before it ever runs untrusted code, which is exactly the property
    CVE-2019-5736 (§11) turned out to depend on getting right. 3. Splitting create/start cleanly maps to two
    CLI verbs instead of flags on one command, because the OCI spec mandates them as separate, independently
    invocable operations — an orchestrator can call create from one code path (provisioning) and
    start from a completely different one (scheduling), months of API design compressed into two
    verbs neither team had to negotiate with the other to agree on.
