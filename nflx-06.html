Manifests & Streaming
Protocols: HLS & DASH

Chapter 4 gave the client a menu of quality renditions to choose from every few seconds. Chapter 5 showed that menu can be a genuinely optimized, per-title ladder rather than a generic one. Neither chapter said how the player actually learns what's on that menu, where each chunk of video physically lives, or what happens on the wire the instant it decides to order something different. That's the manifest's job — and the deliberate, almost boring choice to deliver everything it points to over plain HTTP is one of the more consequential design decisions in this entire course.

ARC 01 · THE PROBLEM

The player has a menu. It still needs an order form.

Put the last two chapters' outputs side by side. Chapter 5 leaves you with a per-title bitrate ladder: a handful of resolution/bitrate renditions of the same title, each already chopped into short segments by an encoder. Chapter 4 leaves you with a client that is supposed to look at its own buffer health and measured throughput and decide, chunk by chunk, which rendition to request next. Neither chapter says how the client discovers that ladder, or how "request the next chunk" becomes an actual, addressable action over a network it doesn't control.

Unpack "discovers the ladder" into what a player concretely needs to know before it can make a single correct request:

  • Which renditions exist for this title, right now. Chapter 5 established that the ladder is per-title — a talking-head interview and a fast-motion action film do not get the same rungs. A player cannot hardcode "there are six renditions at these six bitrates"; it has to be told, per title, per encode.
  • Where each chunk actually lives. A rendition is not one file — it's dozens or hundreds of small segments. The player needs an address (a URL, or enough information to construct one) for every segment of every rendition it might ever request, including ones it hasn't chosen yet.
  • How the segments line up in time. To play chunk 47 of the 1080p rendition after chunk 46 of the 720p rendition — the literal mechanics of a mid-stream quality switch — the player needs to know that both chunks cover the identical span of playback time. Nothing about a bare list of file names guarantees that.
  • How much of this to fetch, and when. All of that information must itself be retrievable cheaply, once, up front — not re-derived by guesswork on every single chunk request.

That is the manifest problem, stated precisely: a machine-readable index of every quality rendition of a title and the address of every chunk inside each one, published somewhere the player can fetch it before playback starts. HLS calls this index an .m3u8 playlist; DASH calls it an .mpd — a Media Presentation Description. Both are, underneath very different syntaxes, answers to the exact same four bullets above. This chapter derives why that index has to exist, why two different, real, widely-deployed standards answer the question differently, and exactly what a mid-stream quality switch looks like once the player has one in hand.

WHY THIS MATTERS FOR THE REST OF THIS ARC

Every request this course has discussed so far as an abstraction — "the client requests a chunk at a given quality" (ch. 4), "the encoder produces this ladder" (ch. 5) — becomes, starting this chapter, a literal HTTP GET against a literal URL. Chapter 7 (Open Connect) is entirely about where that URL actually resolves to on the network and why plain HTTP is what makes that placement problem tractable at Netflix's scale. Nothing in chapter 7 makes sense without first accepting this chapter's central design choice: segments are just static files, fetched with the same verb your browser uses to load an image.

DEEP CONTEXT · WHY "JUST HTTP" WAS A REAL FIGHT, NOT A DEFAULT

It's easy, from today's vantage point, to think HTTP-delivered video was always inevitable. It wasn't. The generation of engineers who built RTSP and RTMP were solving a real problem — continuous media genuinely behaves differently from a static document — with the tools of their era: dedicated streaming servers, custom wire protocols, and persistent stateful connections built for exactly this job. The HTTP-segmented approach this chapter teaches won not because it's a more elegant protocol (arguably it's a cruder one — video reduced to a folder of static files and a text index) but because it externalizes almost the entire hard distribution problem onto infrastructure the rest of the internet had already spent two decades making fast, cacheable, and firewall-friendly. Chapter 7 is the payoff of that bet.

ARC 03 · NAIVE SOLUTION

Attempt #1: no manifest, just conventions

Derive the design honestly. You already have chapter 5's encoder output: a per-title ladder of renditions, each chopped into segments on disk. The simplest possible way to let a player consume that, without inventing an index file at all, is to make the player guess URLs from a fixed naming convention and let the server (not the client) decide which quality to hand back.

pseudocodenaive_playback.pseudo — the strawman, annotated
function startPlayback(titleId) {
  // No index fetched. The client just assumes a fixed layout it was told about once,
  // out of band, by whoever built the app — not by anything the server publishes.
  let seg = 0;
  while (true) {
    // The URL is guessed by convention: title, then a zero-padded segment number.
    // Which QUALITY comes back is not the client's decision at all —
    // the server inspects the request (User-Agent, a guessed "region speed", whatever)
    // and picks a rendition on the client's behalf.
    const url = `/videos/${titleId}/segment_${pad(seg, 4)}.ts`;
    const chunk = await httpGet(url);   // hope the server guesses well
    if (chunk.status === 404) break;         // ...this is how the client learns playback ended
    appendToBuffer(chunk);
    seg++;
  }
}

Notice what this design gets right before dismissing it: it is genuinely simple, it requires zero index parsing, and if the server's quality guess happens to be good and the fixed convention happens to match what the encoder actually produced, playback works. A single-quality pilot deployment, serving one device type, could ship this today and nobody would notice a problem in the demo.

But look at what had to be true for that demo to work, and how much of it is silently assumed rather than known: the client had to be handed the segment-naming convention out of band (in app code, not in anything the server publishes); the server had to guess a quality without ever learning the client's actual, currently measured throughput or buffer state — precisely the signal chapter 4's client-side ABR algorithm exists to use; and the client has no way to ask for a specific different rendition even if it wanted to. Section 4 turns each of those silent assumptions into a concrete, quantified failure.

ARC 04 · WHY IT FAILS

Every piece of missing information causes one specific, nameable failure

The naive design's problems are not vague "it doesn't scale" hand-waving — each missing piece of information maps to exactly one broken capability this course has already told you the system needs:

  • No enumeration of renditions → chapter 4's ABR engine has nothing to choose from. Client-side adaptive bitrate streaming means the client decides which rendition to request based on its own measured throughput and buffer occupancy. If the client doesn't know how many renditions exist, at what bitrates, at what resolutions, it cannot make that decision — the naive design's answer is to let the server guess instead, which throws away the entire premise of chapter 4.
  • No enumeration of segments → no seeking, no accurate progress bar, no "how much is left." A convention like segment_0001.ts, segment_0002.ts, … tells you nothing about how many segments exist, how long each one plays for, or where in the title a given segment falls. Scrubbing to minute 42 becomes "guess a segment number and hope."
  • No declared bitrate/resolution/codec per rendition → the device-compatibility problem (a running theme of this course, formalized in chapter 16) has no data to work with. Thousands of real device types support different codecs and resolutions. A player needs to know a rendition's codec before requesting it, or it risks fetching megabytes of video its decoder cannot play.
  • Server-side quality selection removes the exact signal that makes ABR work at all. Chapter 4's whole argument was that only the client has real-time visibility into its own throughput and buffer — a server making a one-shot guess per request has none of that, and worse, has to guess it for every one of Netflix's hundreds of millions of concurrently streaming clients at once, blind.
  • Renditions can change per title, per encode, even per re-encode — a hardcoded convention cannot track that. Chapter 5 established that the ladder itself is optimized per title. A fixed URL convention assumes every title has the same rungs at the same bitrates, which chapter 5 already proved false.
THE NUMBERS

Model it directly: with, illustratively, a five-rung ladder and 6-second segments across a two-hour film, that's roughly 1,200 individual segment files just for one title's video track, before audio and subtitle tracks are counted. Multiply by a catalog with many thousands of titles, each independently re-ladder-ed per chapter 5's per-title logic, and the set of "valid" segment URLs for the whole catalog is both enormous and constantly changing as titles are re-encoded. A convention baked into client app code cannot track a server-side catalog that changes shape this often — the information has to be published, per title, in a form the client fetches fresh at playback start. That published index is the manifest, and section 5 builds it up piece by piece.

ARC 05 · BETTER SOLUTION

Building the manifest, one requirement at a time

Every requirement from §4 has the same shape: the client is missing some piece of information it needs before it can act correctly. The fix is to publish all of that information in one small, parseable document the client fetches exactly once, at the very start of playback. Step through how that document has to be built up, piece by piece, to satisfy each requirement in turn.

Assembling the manifest, requirement by requirementSTEP-BY-STEP

Notice the shape that fell out of this exercise, entirely from following the requirements: a two-level structure — one top-level list of renditions (with their declared bitrate/resolution/codec), and, nested under each rendition, a list of segments (with their duration and address). That two-level shape is not an implementation detail either standard chose arbitrarily — it is the minimum structure that answers every bullet from §4 at once. HLS calls the two levels the master playlist and each rendition's media playlist; DASH calls them an AdaptationSet's Representations and each one's segment list. Different vocabulary, identical shape, because the shape was forced by the problem, not chosen by either committee.

THE PATTERN, NAMED

This is a declarative catalog — the same idea a package registry's index file or a DNS zone file serves: don't make every consumer guess or probe; publish the one document that answers every question a well-behaved client will ever need to ask, and let it fetch that document exactly once.

ARC 06 · WHY THAT STILL HURTS

A manifest solves discovery. It creates its own, real costs.

Publishing a manifest is unambiguously the right fix for §4's failures — but it is not free, and a fair chapter has to name exactly what it costs before showing the final architecture:

  • Live content makes the manifest a moving target. This course's streaming focus is overwhelmingly video-on-demand — a finished, fully-encoded title with a known, fixed segment count. Live content (not this chapter's focus, but worth being honest about) has to keep appending to the manifest as new segments are encoded, and the client has to re-fetch a growing manifest on a schedule rather than parsing one static document once. Everything this chapter derives assumes the simpler, VOD case unless stated otherwise.
  • Manifest size and parse cost are real, not hypothetical, at extreme segment counts. A two-hour film at 6-second segments across five renditions is on the order of a few thousand lines of playlist text or XML — trivial to parse. A many-hours-long live event, or a manifest that (incorrectly) keeps every segment ever produced instead of a sliding window, can grow into a genuinely expensive document to re-fetch and re-parse on every update. §10 puts real numbers on this.
  • Two competing, incompatible standards exist, for real, structural reasons — not because nobody could agree on one. HLS originated at Apple and is what Apple's own platforms require; DASH is a vendor-neutral ISO/IEC standard built to be codec-agnostic from day one. A codec that plays on one device family may not decode on another (this course's chapter 3 theme, recurring here) — which is a real, structural reason a single universal manifest format never fully materialized, and why any real catalog-scale service ends up publishing both formats from the same underlying encodes.
  • The manifest's promise of a clean mid-stream switch has a hidden precondition. Nothing about declaring five renditions in one document guarantees that segment 47 of rendition A and segment 47 of rendition B cover exactly the same span of playback time, down to frame accuracy, or that both start on a clean decodable keyframe. If the encoder that produced those renditions (chapter 5) didn't deliberately align segment boundaries and keyframes across the whole ladder, the manifest can declare a switch is possible while the actual bitstreams make it visually rough. §8 and §11 both come back to this.
A PATTERN YOU WILL SEE AGAIN IN THIS COURSE

Solve the discovery problem with a published index, and you immediately inherit a staleness problem (what if the thing being indexed changes?), a scale problem (what if the index itself gets big?), and a fragmentation problem (what if more than one index format is needed for different consumers?). Open Connect's content-placement decisions (ch. 7–8) run into the same shape of tradeoff at the level of "which titles live on which cache," not "which segments belong to which rendition" — same pattern, different layer.

None of this argues against having a manifest — the alternative in §3–4 was strictly worse. It argues for a final architecture that treats the manifest as one deliberately-scoped piece of a larger pipeline, which is exactly what §7 assembles.

ARC 08 · INTERNAL IMPLEMENTATION

The real formats, and what actually happens on the wire

Now the real mechanism, at the syntax level. HLS's manifest is .m3u8 — an extended plain-text M3U playlist format, originally Apple's, later standardized by the IETF as an informational RFC. DASH's manifest is .mpd — a Media Presentation Description, an XML document defined by the formal ISO/IEC MPEG-DASH standard. Both are real, checkable, publicly documented formats; what follows is genuinely correct syntax for each, not an approximation.

(a) HLS: a master playlist pointing at per-rendition media playlists

An HLS player's first request is for the master playlist — the document that plays the role of §5's top-level rendition list. Each #EXT-X-STREAM-INF tag declares one rendition's bandwidth, resolution, and codec, immediately followed by the URI of that rendition's own playlist:

m3u8master.m3u8 — the top-level rendition list
#EXTM3U
#EXT-X-VERSION:7

#EXT-X-STREAM-INF:BANDWIDTH=422000,AVERAGE-BANDWIDTH=395000,RESOLUTION=426x240,CODECS="avc1.4d400d,mp4a.40.2"
240p/rendition.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=850000,AVERAGE-BANDWIDTH=780000,RESOLUTION=640x360,CODECS="avc1.4d401e,mp4a.40.2"
360p/rendition.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=1650000,AVERAGE-BANDWIDTH=1500000,RESOLUTION=960x540,CODECS="avc1.4d401f,mp4a.40.2"
540p/rendition.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=3200000,AVERAGE-BANDWIDTH=2950000,RESOLUTION=1280x720,CODECS="avc1.64001f,mp4a.40.2"
720p/rendition.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=6500000,AVERAGE-BANDWIDTH=6000000,RESOLUTION=1920x1080,CODECS="avc1.640028,mp4a.40.2"

BANDWIDTH is the peak bits-per-second a client should provision for; CODECS lets a player reject a rendition its decoder can't handle before ever requesting a byte of video — precisely the device-compatibility check §4 said was impossible without a manifest. Having picked one line, the player fetches that rendition's own media playlist — the second level, listing every actual segment:

segment_000.ts
#EXTINF:6.006,
segment_001.ts
#EXTINF:6.006,

… seven more #EXTINF / segment pairs …

Every fact §4 said was missing is now present and checkable: #EXT-X-TARGETDURATION bounds how long any one segment can run (useful for buffering strategy); each #EXTINF gives the exact duration of the segment that follows it, so a player can compute elapsed and remaining time without probing anything; #EXT-X-ENDLIST is the explicit, declared end of a VOD title — no more guessing a 404 to learn playback is over, as the naive design in §3 had to. Historically these segments were MPEG-2 transport-stream (.ts) files, as shown; HLS today equally supports fragmented MP4 (fMP4) segments, which matters directly for §9 and §11.

(b) DASH: one XML document, nested the same way

MPEG-DASH expresses the identical two-level shape in a single XML document instead of a text file plus per-rendition sub-files. AdaptationSet groups renditions of one media type; each Representation inside it is one rendition; SegmentTemplate describes how to construct every segment's URL from a numeric pattern rather than listing each one by hand:

xmlmanifest.mpd — the same two levels, as one XML document
<?xml version="1.0" encoding="UTF-8"?>
<MPD xmlns="urn:mpeg:dash:schema:mpd:2011"
     type="static"
     mediaPresentationDuration="PT1M0S"
     minBufferTime="PT2S"
     profiles="urn:mpeg:dash:profile:isoff-on-demand:2011">
  <Period>
    <AdaptationSet mimeType="video/mp4" segmentAlignment="true" startWithSAP="1">
      <Representation id="240p" bandwidth="422000" width="426" height="240" codecs="avc1.4d400d">
        <SegmentTemplate media="240p/seg-$Number$.m4s" initialization="240p/init.mp4"
                         duration="6" startNumber="1"/>
      </Representation>
      <Representation id="360p" bandwidth="850000" width="640" height="360" codecs="avc1.4d401e">
        <SegmentTemplate media="360p/seg-$Number$.m4s" initialization="360p/init.mp4"
                         duration="6" startNumber="1"/>
      </Representation>
      <Representation id="540p" bandwidth="1650000" width="960" height="540" codecs="avc1.4d401f">
        <SegmentTemplate media="540p/seg-$Number$.m4s" initialization="540p/init.mp4"
                         duration="6" startNumber="1"/>
      </Representation>
      <Representation id="720p" bandwidth="3200000" width="1280" height="720" codecs="avc1.64001f">
        <SegmentTemplate media="720p/seg-$Number$.m4s" initialization="720p/init.mp4"
                         duration="6" startNumber="1"/>
      </Representation>
      <Representation id="1080p" bandwidth="6500000" width="1920" height="1080" codecs="avc1.640028">
        <SegmentTemplate media="1080p/seg-$Number$.m4s" initialization="1080p/init.mp4"
                         duration="6" startNumber="1"/>
      </Representation>
    </AdaptationSet>
    <AdaptationSet mimeType="audio/mp4">
      <Representation id="audio" bandwidth="128000" codecs="mp4a.40.2">
        <SegmentTemplate media="audio/seg-$Number$.m4s" initialization="audio/init.mp4"
                         duration="6" startNumber="1"/>
      </Representation>
    </AdaptationSet>
  </Period>
</MPD>

Two things worth naming explicitly because they recur later. First, segmentAlignment="true" on the AdaptationSet is DASH declaring, as a formal attribute, exactly the precondition §6 flagged: all Representations in this set are time-aligned segment-for-segment. Second, SegmentTemplate means DASH never lists a thousand individual URLs by hand the way HLS's media playlist does — the player computes 240p/seg-1.m4s, 240p/seg-2.m4s, and so on, by substituting into the $Number$ pattern. Same information (§5's segment list), delivered by formula instead of enumeration.

ARC 09 · TRADEOFFS

HLS vs. DASH: the same problem, two real standards

DIMENSIONHLSDASH
Origin & standardization Apple, first shipped 2009; later published as an informational IETF document (RFC 8216, 2017) MPEG/ISO working group effort; a formal ISO/IEC standard (23009-1), ratified 2012
Manifest format Plain text, extended M3U (.m3u8) — a master playlist plus one media playlist per rendition XML (.mpd) — one document, Period → AdaptationSet → Representation

Codec assumptions Originally tied to H.264/AAC in transport streams; fMP4 support broadened this considerably Codec-agnostic by design — the standard never assumed one codec family
Native platform support Required by Apple's own platforms (Safari, iOS/tvOS native players); Apple's App Store review guidance has long required HLS for substantial video played over cellular Broad support on Android/web via widely used player libraries (e.g. ExoPlayer, dash.js), but no single OS mandates it the way Apple mandates HLS
Segment addressing Enumerated — every segment gets its own line in a media playlist Enumerated (SegmentList) or computed by formula (SegmentTemplate's $Number$/$Time$ substitution)
Live support Real, mature — media playlists append and slide as new segments encode Real, mature — type="dynamic" MPDs with periodic refresh
Practical consequence mandatory on Apple platforms two container formats to support (TS legacy + fMP4) one container story, codec-agnostic no platform mandates it outright

Read this table as evidence, not a verdict: neither format is strictly better, because they were built to satisfy different constraints — Apple's own ecosystem versus a vendor-neutral standard meant to outlive any one company's codec preferences. The practical consequence, confirmed for real in §11, is that any streaming service with a broad device footprint ends up publishing both formats from the same underlying encodes rather than picking a winner — which is exactly why a convergence effort like CMAF exists at all.

ARC 10 · PERFORMANCE / SCALE

Small documents, an enormous number of them

Nothing about a manifest or a segment is individually expensive. The scale argument for this chapter is entirely about volume — how many of these small, cheap requests actually happen — and it is exactly this argument that makes chapter 7's CDN design non-optional rather than a nice-to-have.

  • Manifest size stays small even at real segment counts. A two-hour title at 6-second segments is about 1,200 segments per rendition; a five-line-per-segment HLS media playlist for that rendition is on the order of a few thousand lines of plain text — comfortably tens of kilobytes, parsed once at playback start. The DASH equivalent, using SegmentTemplate, is dramatically smaller still, because it never enumerates segments individually.
  • Segment request volume, not manifest size, is where the real numbers live. At 6-second segments, one continuously playing stream issues roughly 10 segment requests per minute for its video track alone (plus separate audio, and possibly subtitle, requests). Multiply by an illustrative tens-of-millions order of magnitude of concurrent streams at a global peak, and the platform-wide HTTP request rate for video segments alone lands in the tens of millions of requests per minute — a volume that is only survivable because each request is cacheable, static, and served by ordinary HTTP infrastructure rather than requiring a specialized streaming server to hold state per client.
  • This is precisely the argument chapter 7 depends on. A CDN (or, at Netflix's real scale, Open Connect's purpose-built appliances) can cache a video segment exactly like it would cache any other static HTTP object — using ordinary Cache-Control and ETag semantics, and serving partial reads via the Range header when a client only needs part of a segment. None of that infrastructure needs to understand video at all. That is the entire payoff of choosing plain HTTP delivery back in §1 — and it is why this chapter's design choice, not any clever caching trick, is what makes chapter 7's CDN economics work.

ARC 11 · HISTORY & REAL-WORLD PATTERNS

Two real formats colliding, and one realistic failure mode

The real fragmentation, and the real convergence attempt

HLS and DASH did not fragment the industry by accident — §9 already showed the structural reasons (an Apple-originated, Apple-mandated format on one side; a vendor-neutral, codec-agnostic ISO standard on the other). The real, documented consequence for years of the streaming industry was that any service with a meaningfully broad device footprint had to run two full packaging pipelines from the same source video — producing both .m3u8/TS-or-fMP4 output and .mpd/fMP4 output — and maintain both. This is precisely why real, publicly available multi-format packaging tools exist at all: Google's open-source Shaka Packager, for instance, is a genuine, widely used tool built specifically to take one set of encodes and emit both HLS and DASH manifests referencing them. CMAF (Common Media Application Format, ISO/IEC 23000-19, first published around 2018, with real industry participation including Apple's) is the real, documented attempt to close this gap from the format side: it standardizes one fMP4 segment shape that both HLS and DASH manifests can reference, so a service can maintain one set of media segments and generate two thin, mostly-metadata manifests on top — rather than two entire sets of segmented video. CMAF has meaningfully reduced, but not entirely eliminated, the packaging duplication — encryption-scheme and manifest-detail differences between the two ecosystems still exist even where the underlying segments are shared.

A realistic industry-standard incident pattern: misaligned segment boundaries

A specific, named, publicly disclosed Netflix incident of this exact shape isn't something this course can point to — so this is presented plainly as a realistic industry-standard incident pattern for any packaging pipeline of this kind, not a documented Netflix postmortem. §6 and §8 both flagged the precondition: a clean mid-stream switch requires every rendition in the ladder to share identical segment boundaries and, ideally, aligned keyframes. A packaging bug — a segmenter that drifts by a few milliseconds between renditions under certain frame-rate or variable-frame-rate source material, or a re-encode of just one rung of the ladder without re-running the whole batch through the same segmenter pass — can silently break that alignment for one title, one rendition pair, without touching the manifest's declared correctness at all. The manifest still correctly lists both renditions' segment durations; what breaks is the actual bitstream content underneath. The visible symptom is exactly what you'd predict from §8's mechanism: a brief visual glitch, a repeated or skipped frame, or a momentary black flash, precisely at the moment a quality switch occurs — because the decoder was handed two chunks that don't actually cover the same span of time, or the second chunk doesn't start on a clean keyframe. This is why real packaging pipelines treat segment-boundary and keyframe alignment across an entire ladder as a validated, automatically checked property of the encode — not something reviewed by eye per title.

THE GENERAL LESSON

A manifest can be syntactically perfect and still describe a broken mid-stream switch, because the manifest only declares what should be true about segment alignment — it cannot, by itself, enforce that the encoder actually produced bitstreams that honor that declaration. Validating alignment is a property of the encoding pipeline (chapter 5), and its absence is invisible until exactly the moment a switch happens.

The normalized model both parsers produce is deliberately format-agnostic — everything downstream (the ABR scheduler, the resolver, the fetcher) works against one shape regardless of whether the source was .m3u8 or .mpd:

JS-style pseudocodehls_parser.js — normalizing a master + media playlist
function parseHls(masterText, fetchMediaPlaylist) {
  const renditions = [];
  for (line of masterText.split("\n")) {
    if (!line.startsWith("#EXT-X-STREAM-INF:")) continue;
    const attrs = parseAttrList(line);              // BANDWIDTH, RESOLUTION, CODECS…
    const uri = nextNonCommentLine(masterText, line); // the media playlist URL
    renditions.push({ bandwidth: +attrs.BANDWIDTH, resolution: attrs.RESOLUTION,
                       codecs: attrs.CODECS, mediaPlaylistUrl: uri });
  }
  // Normalize each rendition's OWN media playlist into the same segment shape DASH will use.
  for (r of renditions) {
    const mediaText = await fetchMediaPlaylist(r.mediaPlaylistUrl);
    r.segments = extinfPairs(mediaText).map((p, i) => ({ index: i, duration: p.duration, uri: p.uri }));
  }
  return { renditions };                              // same shape a DASH parser would return
}
JS-style pseudocodesegment_resolver.js — DASH's $Number$ template vs. HLS's plain URI
function resolveSegmentUrl(rendition, index) {
  if (rendition.segmentTemplate) {                  // DASH SegmentTemplate case
    const num = rendition.startNumber + index;
    return rendition.segmentTemplate.media.replace("$Number$", num);
  }
  return rendition.segments[index].uri;             // HLS case: already an explicit URI per segment
}
JS-style pseudocodeswitch_scheduler.js — where the ABR decision actually lands
function scheduleNextSegment(model, currentRenditionId, nextIndex, measuredKbps, marginPct) {
  const budget = measuredKbps * (marginPct / 100);
  // Chapter 4's rule, applied here: highest bandwidth that still fits under budget.
  const target = model.renditions
    .filter(r => r.bandwidth / 1000 <= budget)
    .sort((a, b) => b.bandwidth - a.bandwidth)[0] || model.renditions[0];
  // CRITICAL: the target only ever applies to the NEXT segment index — never the one
  // already mid-flight. A switch decision made now cannot rewrite a request in progress.
  return { renditionId: target.id, index: nextIndex, url: resolveSegmentUrl(target, nextIndex) };
}
WHY THIS SHAPE — THE DECISION WORTH STEALING

The ABR scheduler never touches a segment that's already been requested — it only ever chooses the rendition for the next index. That's not a stylistic choice; it's the direct consequence of §8's mechanism: a switch can only happen at a segment boundary, because that's the only point where the decoder is between fully-decoded chunks and can cleanly accept a different rendition's bitstream. Encoding that constraint directly into the scheduler's function signature — it takes a future index, never the current one — makes an entire class of "switched mid-chunk and glitched" bugs structurally impossible rather than something to catch in testing.
