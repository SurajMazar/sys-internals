ARC 01 · THE PROBLEM

A backend allocates constantly, and must never leak

A single client backend, over one session, will call something that allocates memory millions of times: once per parse-tree node, once per expression-evaluation scratch buffer, once per tuple deformed out of a page, once per hash-table entry, once per sort run. Some of those allocations must outlive the query that made them — a cached catalog entry, a prepared-statement plan. Most must die within microseconds of being created and never be thought about again.

A general-purpose allocator (malloc()/free()) is the wrong tool for this specific shape of workload, for a reason that has nothing to do with speed: correctness under abnormal exit. A SQL error — a constraint violation, a division by zero, a statement timeout — is implemented as a C longjmp() back to a top-level handler (PG_TRY/PG_CATCH, built on sigsetjmp), unwinding an arbitrary number of nested function calls in the parser, planner, or executor without running any of their local cleanup code. If cleanup for one C function's temporary buffer is "call free() before returning," and the function never returns normally, that free() never runs. Multiply by every function in the call stack at the moment of the error, for every error, across a server than runs for weeks: this is not a rare edge case, it is the normal way queries end once you count constraint violations, cancellations, and timeouts.

  • Lifetime diversity. One session, one instant in time, has live allocations that must survive the connection (catalog cache), the transaction (transaction status), the query (sort/hash state), and the single tuple currently being processed (expression scratch) — four different lifetimes, all active at once.
  • Bulk death, not individual death. At the end of a query, the executor doesn't want to free ten thousand individual objects one at a time — it wants to say "everything this query touched is gone" in one cheap operation.
  • Abnormal exit is routine. Any allocation strategy that depends on every code path reaching its matching free() is a strategy that will leak in production, because elog(ERROR) guarantees some code paths never will.
  • Extensibility. PostgreSQL is designed to run untrusted C extensions (chapter 1's founding thesis). An extension author who forgets one free() should not be able to slowly leak a long-running backend to death.
THE REFRAME THAT SOLVES IT

Stop tracking objects. Track arenas with a lifetime, and let objects belong to whichever arena matches how long they need to live. Freeing becomes "discard the arena," which is correct regardless of how many objects are inside it or whether the code that created them ever got to run a destructor. This is the entire idea behind PostgreSQL's MemoryContext — and, not coincidentally, the same idea behind region-based memory management in ML/Rust-adjacent research and arena allocators in game engines. PostgreSQL has been running this pattern in production C code since before most of that literature existed.

DEEP CONTEXT · WHY "PALLOC" AND NOT "MALLOC"

The name traces to the project's Ingres-lineage habit of prefixing memory routines for the "current" allocation scope — palloc() is short for "context-scoped alloc." From day one it was never a synonym for malloc(); it always meant "allocate in whichever arena is currently active," where that arena is named by a single per-backend global, CurrentMemoryContext. Every subsystem you'll meet in later chapters — the parser, planner, executor, WAL machinery — spends a surprising fraction of its code just swapping that one pointer in and out with MemoryContextSwitchTo() before doing work.

ARC 03 · NAIVE SOLUTION

Attempt #1: plain malloc/free, discipline enforced by hand

Derive it honestly, same as chapter 1. The obvious way to write a recursive expression evaluator is to malloc() scratch space on entry and free() it before returning:

Cnaive_eval.c — the strawman, annotated
Datum
EvalExpr(Expr *e, TupleTableSlot *slot)
{
    char *scratch = malloc(256);       /* per-call temp buffer */
    Datum lhs = EvalExpr(e->left,  slot);   /* recurse... */
    Datum rhs = EvalExpr(e->right, slot);   /* ...and again */

    if (would_overflow(lhs, rhs))
        elog(ERROR, "integer out of range");  /* longjmp()s OUT of this
                                            * function -- the line below
                                            * never executes.            */

    Datum result = compute(scratch, lhs, rhs);
    free(scratch);                       /* skipped on the error path,
                                             * and skipped in EVERY caller
                                             * still on the stack above us   */
    return result;
}

This is not a strawman built to be laughed at — it is exactly how you'd write this function in isolation, and it works perfectly in the happy path: every call mallocs, computes, frees, returns. The bug is invisible in code review and invisible in testing that never triggers an error. It only appears once elog(ERROR) fires from arbitrarily deep inside a large call tree — which, in a query planner and executor with dozens of nested node types, is a when, not an if.

WHY YOU CAN'T JUST "TRY/FINALLY" YOUR WAY OUT

C has no destructors and no finally. PostgreSQL's PG_TRY/PG_CATCH macros exist, but wrapping every single allocation site in the parser, planner, and executor in a try/catch that manually frees on both the normal and error path would mean touching thousands of call sites, forever, perfectly, with zero tolerance for a missed one anywhere in the codebase — including in third-party extensions the core team doesn't control. That's not a maintenance cost you accept once; it's a maintenance tax that compounds with every new line of C anyone ever writes against this API.

ARC 04 · WHY IT FAILS

Quantify it: leaks, allocator overhead, and the bulk-free that doesn't exist

Three independent failure modes, each fatal on its own:

  • Leak accumulation is a function of error rate, not bug rarity. Say one in every 200 queries hits an abort path (a constraint violation, a serialization failure, a statement timeout — all completely normal in production OLTP) and leaks an average of 4 KB of scratch state across the frames that were on the stack. At 2,000 queries/sec on a busy backend fleet, that's 10 leaked queries/sec × 4 KB ≈ 40 KB/sec per busy backend, with no way to reclaim it short of restarting the process. Over a day that's several gigabytes per long-lived connection — and connections in pooled deployments can live for days.
  • Per-call allocator overhead dominates at small sizes. A single moderately complex query can perform hundreds of thousands of small allocations (one per expression node evaluation, one per tuple's deformed attributes). Even a fast allocator spends tens of nanoseconds per call on bookkeeping — size-class lookup, free-list search, boundary tags for coalescing. At 300,000 alloc+free pairs and a conservative 40 ns per call, that's 24 ms of pure allocator bookkeeping before the query has done a single byte of real work — and this repeats on every execution of every query.
  • There is no bulk-free primitive. To free "everything this query touched" with plain malloc/free, the program would first have to track every pointer it ever allocated — which itself requires more allocations (a list, a hash set) that then also need freeing. Freeing becomes for (p in tracked) free(p): a loop with cost proportional to the number of individual objects, potentially millions, rather than to the number of blocks backing them.
THE NUMBERS, STATED PLAINLY

Plain malloc/free gives you O(1) leaks-per-error (guaranteed), O(allocation count) cleanup cost, and zero structural protection against a forgotten free() anywhere in an enormous and constantly-growing codebase. None of these are tuning problems. They are consequences of tracking the wrong unit — the object instead of its lifetime. §5 tries three fixes at that root cause.

ARC 05 · BETTER SOLUTIONS, EXAMINED

GC, one big arena, or a tree of arenas — the real 1986-onward decision

Candidate A: reference counting or tracing garbage collection

Let a runtime track object liveness automatically — Java, Go, and the JVM-family databases (candidate for Cassandra-style engines, §9) all do this. It genuinely eliminates the leak-on-error problem: nothing needs explicit freeing at all. But it requires either per-object metadata (a refcount word on every allocation — real overhead at the scale of "millions of small objects per query") or a tracing collector with stop-the-world (or at best concurrent-with-overhead) pauses — unacceptable in C without a managed runtime underneath it, and a wholesale rewrite of the execution model that 1980s Unix C simply didn't offer as a library. Rejected: no portable, low-overhead GC existed for C, and per-object bookkeeping cost cuts against a workload that is millions of tiny, short-lived objects per second.

Candidate B: one global arena, bump-allocated, reset per query

Simpler idea: allocate everything from one big block with a bump pointer; at the end of each query, rewind the pointer to zero. Trivial, extremely fast (allocation is a pointer add), and bulk-free is genuinely O(1). The flaw appears the moment you have two different lifetimes active at once — which is always: the catalog cache entry for a table you looked up must survive past this query's end, but the per-tuple scratch buffer must not. One arena, one reset point, cannot serve both without either leaking the long-lived object out of the reset (defeating the point) or destroying the long-lived object early (a dangling-pointer bug). Rejected: granularity mismatch — real workloads need several independent reset points, not one.

Candidate C: a tree of arenas, one per natural lifetime ✓

Generalize B: instead of one arena, keep many, nested to mirror the natural nesting of database work — a connection contains transactions, a transaction contains queries, a query contains tuples. Give each level its own arena (a MemoryContext), parented to the level above it, and let code allocate into whichever context matches what it's building. Resetting the innermost, most short-lived context (say, per-tuple) happens constantly and cheaply without touching anything above it in the tree.

THE CLINCHING ARGUMENT: LIFETIME MATCHES SCOPE, NOT OBJECT COUNT

A tree of contexts turns "did I forget to free this?" into "did I allocate it into the right context?" — a question you answer once, at the call site, by picking which context is current, rather than tracking it for the rest of the object's life. And because resetting or deleting a context frees everything inside it regardless of how execution got there — normal return or longjmp() out of an error — the entire leak-on-abnormal-exit class from §4 disappears structurally. You don't have to remember to clean up on the error path; the error path's PG_CATCH just resets a context or two, and everything allocated since is gone.

ARC 06 · WHY THAT STILL COSTS

The bill: wrong-context bugs, fragmentation, and manual bookkeeping

The context tree is not free. Four costs you will meet in production, each a direct consequence of the design:

  • Wrong-context allocation is a new, sneaky bug class. If code allocates a struct meant to outlive a query into the per-tuple ExprContext instead of the query's own ExecutorState, the struct looks completely fine until the context resets — at which point every pointer into it becomes a dangling reference into memory that may already be handed out to something else. This fails intermittently, often only under load (because that's when contexts reset while something is still mid-use), and is one of the most common classes of bugs in third-party C extensions.
  • The tree, and which context is "current," is manual, global, mutable state. CurrentMemoryContext is one pointer; code must explicitly MemoryContextSwitchTo() before allocating and switch back afterward. Forgetting the "switch back" half leaves unrelated code allocating into a context it never meant to touch — a bug that (again) is invisible until that context resets or grows unexpectedly.
  • Freed space inside a context isn't necessarily reusable by the next request. As §8 shows, small chunks freed within a context go onto a size-classed freelist and are only reused by a future request of the same size class. A context that allocates many different sizes and frees them out of order can accumulate freelist entries that never get reused before the whole context resets — memory that is "freed" by the program's accounting but not available to satisfy a differently-sized request. This is internal fragmentation, and it's structurally different from (and in addition to) glibc-style heap fragmentation.
  • A context that's never reset (a long-lived cache) gets none of the reset advantage. CacheMemoryContext lives for the whole session; if it churns — entries added and removed continuously as different tables are accessed — it behaves like an ordinary long-running allocator, with all of plain malloc's fragmentation concerns, just with extra chunk-header overhead layered on top.
THE HONEST TRADE

The context tree converts "did every free() run?" (a correctness question you can get wrong silently) into "did every allocation land in the right context?" (a design question you can get wrong just as silently, but which is auditable at the call site and — crucially — MEMORY_CONTEXT_CHECKING builds and pg_get_backend_memory_contexts() give you tools to debug). It doesn't eliminate the hard problem; it relocates it somewhere more tractable. §7 shows the architecture that resulted.

ARC 07 · FINAL ARCHITECTURE

The context hierarchy, and the allocators that back it

A running backend's private memory is a tree of named contexts rooted at one that lives as long as the process, with progressively shorter-lived contexts nested inside for progressively narrower scopes. ARC 08 · INTERNAL IMPLEMENTATION

Structs, chunk headers, and the algorithms that make palloc cheap

Three pieces: (a) the context object itself and how the tree is walked, (b) the default allocator's block/freelist layout and the 8-byte chunk header, (c) block-doubling growth and its cost.

(a) MemoryContextData: a node in the tree, dispatched through a vtable

Every context — regardless of which allocator backs it — starts with the same header, which is how palloc(), pfree(), MemoryContextReset(), and MemoryContextDelete() can all be generic over aset/generation/slab/dsa without an if-ladder anywhere in the hot path:

Csrc/include/utils/memnodes.h — simplified but faithful
typedef struct MemoryContextData
{
    NodeTag     type;              /* T_AllocSetContext, T_GenerationContext... */
    bool        isReset;           /* true = nothing allocated since last reset */
    const MemoryContextMethods *methods;  /* alloc/free/reset/delete vtable   */
    MemoryContext parent;          /* NULL only for TopMemoryContext    */
    MemoryContext firstchild;
    MemoryContext prevchild;
    MemoryContext nextchild;       /* siblings, doubly linked            */
    const char *name;      /* static string: "ExecutorState" etc */
    const char *ident;     /* optional per-instance detail        */
    MemoryContextCallback *reset_cbs;  /* run just before this context resets */
} MemoryContextData;

typedef struct MemoryContextMethods
{
    void *(*alloc)   (MemoryContext ctx, Size size);
    void  (*free_p)  (void *pointer);
    void *(*realloc) (void *pointer, Size size);
    void  (*reset)   (MemoryContext ctx);
    void  (*delete_context)(MemoryContext ctx);
    Size  (*get_chunk_space)(void *pointer);
} MemoryContextMethods;

(b) AllocSetContext: blocks, an 8-byte chunk header, and 8 freelists

aset.c ("AllocSet" — the default, general-purpose implementation) backs the majority of contexts you'll ever create. Each context owns a linked list of blocks — plain malloc()'d regions — and carves chunks out of them for individual palloc() requests:

Csrc/backend/utils/mmgr/aset.c — simplified but faithful
typedef struct AllocSetContext
{
    MemoryContextData header;
    AllocBlock  blocks;              /* newest block first */
    AllocChunk  freelist[ALLOCSET_NUM_FREELISTS];  /* 8 size-classed freelists */
    Size        initBlockSize;       /* size of the first block            */
    Size        maxBlockSize;        /* doubling stops here                */
    Size        nextBlockSize;       /* size the NEXT block will be        */
    Size        allocChunkLimit;     /* above this: dedicated block, no freelist */
    AllocBlock  keeper;               /* first block -- survives Reset()    */
} AllocSetContext;

typedef struct AllocBlockData
{
    AllocSet    aset;
    AllocBlock  next;
    char       *freeptr;    /* next free byte in this block  */
    char       *endptr;     /* one past the block's end      */
} AllocBlockData;

Every live chunk — used or on a freelist — starts with a compact header that PostgreSQL 16 shrank from roughly 16 bytes to a single bit-packed 64-bit word, because every single allocation the server ever makes pays this tax:

Csrc/include/utils/memutils_internal.h — MemoryChunk (PG16+)
typedef struct MemoryChunk
{
    uint64  hdrmask;
    /* bit layout (low bits first):
     *   bits 0-2   : MemoryContextMethodID -- which allocator owns this
     *                chunk (aset / generation / slab / ...), so pfree()
     *                and repalloc() can dispatch without walking the tree
     *   bit  3     : "external" flag -- this chunk has its own dedicated
     *                block (it was bigger than allocChunkLimit, or it's
     *                a dsa.c-backed allocation) and stores a real
     *                back-pointer just before this header instead of
     *                an offset
     *   bits 4-63  : block-relative BYTE OFFSET back to the owning
     *                AllocBlockData, when the external flag is clear --
     *                enough bits that a chunk anywhere in an 8 MB block
     *                can find its block header without storing a full
     *                8-byte pointer                                    */
} MemoryChunk;   /* sizeof == 8 bytes on 64-bit builds */
BYTE LAYOUT, VISUALLY

Below: a chunk holding a 40-byte payload. The header is fixed cost regardless of payload size — which is exactly why shrinking it from 16 to 8 bytes mattered: on a workload dominated by small chunks (a few dozen bytes each, which most executor scratch allocations are), header overhead is a double-digit percentage of total memory, not a rounding error.

Requests that don't fit any freelist's size class at all — anything bigger than allocChunkLimit — skip the block/freelist machinery entirely: aset.c just malloc()s a dedicated block sized exactly to the request (rounded for alignment) and marks the chunk "external." pfree() on one of these calls free() on the whole block immediately — the only case where this allocator gives memory back to the OS before a context reset.

(c) Block growth: doubling, and the slider below shows the exact sequence

A context's first block is sized initBlockSize (the shipped default is 8 KB via ALLOCSET_DEFAULT_SIZES). Every time a block runs out of room, aset.c allocates a new one sized nextBlockSize, then doubles nextBlockSize for next time — up to maxBlockSize (default 8 MB), after which growth stops and every subsequent block is that same max size. This is the same doubling-array trade every language runtime's dynamic array makes: fewer, larger malloc() calls as a context grows, at the cost of some unused tail space in the last block.

ARC 10 · PERFORMANCE CHARACTERISTICS

Big-O, cache behavior, and where NUMA does and doesn't matter

  • palloc() — O(1) amortized. Freelist hit: pop one entry, O(1). Freelist miss with room left in the current block: bump freeptr, O(1). Freelist miss with no room: one malloc() for a new (doubled) block — amortized O(1) across all the allocations that block will eventually serve, exactly like a dynamic array's amortized push.
  • MemoryContextReset() — O(number of blocks), not O(number of chunks). The reset loop in §8's AllocSetReset() walks the block list and either frees or rewinds each block — it never visits individual chunks, because nothing tracks chunks outside of the (already O(1)-cleared) freelist array. A context holding one million small chunks across four blocks resets in four iterations, not a million.
  • Spatial locality. Sequential palloc() calls into the same block land in adjacent memory — excellent for the executor's own access pattern (deform a tuple's columns one after another, right after allocating the tuple's slot) and friendly to hardware prefetch. A general allocator's size-classed free lists, by contrast, hand back whatever chunk happened to be freed last, which is essentially arbitrary with respect to what you're about to touch next.
  • TLB and huge pages. Per-backend memory contexts are ordinary process heap (brk/anonymous mmap), not backed by huge_pages (that GUC only affects the one fixed shared_buffers segment from chapter 1). A backend that palloc's tens of megabytes of private scratch during a large sort touches thousands of ordinary 4 KB pages, and — unlike the shared segment — pays no extra multi-process page-table cost, because this memory exists in exactly one process.
  • NUMA. Private memory is first-touched by whichever core the owning backend is running on at allocation time — which is usually the right node for that same backend's later accesses, since nothing else in the system holds pointers into it. This is the one place chapter 1's cross-socket shared-memory penalty doesn't apply, precisely because this memory was never shared in the first place.

MODEL, NOT MEASUREMENT

The curves are an analytic sketch: malloc/free cost scales linearly with allocation count (per-call bookkeeping every time); palloc cost is mostly amortized O(1) allocation plus one flat O(blocks) reset at the end, so its curve is nearly flat until chunk sizes get large enough to force many block-doubling events. ARC 11 · REAL-WORLD PRODUCTION

Three incidents this chapter explains

Incident 1: work_mem times parallel workers times concurrent nodes

A reporting query gets a parallel hash join plan with four workers after max_parallel_workers_per_gather was raised for a different, unrelated query. Each of the four parallel workers builds its own hash table, each entitled to up to work_mem — the GUC's own documentation is explicit that "the total amount of memory used can be many times the value of work_mem" once concurrent sort/hash nodes and parallel workers are counted. A plan the DBA sized for one backend at 256 MB work_mem actually peaks near 256 MB × 4 workers × however many sort/hash nodes coexist in the plan — and the box OOMs on a query that "should" have fit easily. Fix: size work_mem against worst-case concurrent node × worker count, not against a single node's needs; consider hash_mem_multiplier (which scales hash operations specifically) separately from sort-heavy budgeting.

Incident 2: CacheMemoryContext growth from churny temporary-table workloads

An application creates and drops a temporary table per transaction (a common ORM anti-pattern for "scratch" tables). Each CREATE TEMP TABLE registers new relcache and syscache entries — allocated out of CacheMemoryContext, which lives for the entire session and is never reset the way per-query contexts are. Dropping the table removes the catalog rows, but the corresponding cache entries' chunks return to aset.c's freelists rather than to the OS, and if the next transaction's temp table has even slightly different attribute counts (different chunk sizes), the freed chunks from the previous round often don't get reused — the freelist accumulates entries for sizes nothing asks for again. RSS for that one long-lived pooled connection climbs steadily over the day. Fix: avoid per-transaction temp tables in hot paths (use real tables with an owning-transaction column, or ON COMMIT DROP sparingly); periodically recycle pooled connections (PgBouncer's server_lifetime) so CacheMemoryContext growth is bounded by connection age, not session length.

Incident 3: logical decoding's reorder buffer before logical_decoding_work_mem

A long-running transaction on a busy OLTP table accumulates a huge number of row changes while a logical replication slot is active. Every change has to be held, in commit order, until the transaction commits or aborts (the walsender from chapter 1 can't ship changes out of order). This is exactly the workload generation.c and slab.c were built for — many same-shaped objects, FIFO lifetime — but even a well-fitted allocator can't shrink an unbounded number of objects: the walsender process's memory climbs with transaction size, and before the logical_decoding_work_mem GUC existed to force a spill to disk past a configurable budget, one sufficiently large transaction could push a walsender into an OOM kill (which, per chapter 1, takes down the whole cluster if it's a regular backend, though a walsender's death alone is more contained). Fix: set logical_decoding_work_mem deliberately below available headroom, monitor replication slot lag as a proxy for reorder-buffer size, and avoid single transactions that touch millions of rows on tables with active logical replication slots.

First, the dispatch every allocation goes through — thin on purpose, so the common case (one existing context, one alloc call) stays cheap:

Cmcxt.c — MemoryContextAlloc() and the palloc() front door
void *
MemoryContextAlloc(MemoryContext context, Size size)
{
    Assert(MemoryContextIsValid(context));
    context->isReset = false;       /* this context now has live state */
    return context->methods->alloc(context, size);  /* one indirect call, vtable dispatch */
}

/* palloc.h -- the call site every backend C function uses: */
static inline void *
palloc(Size size)
{
    return MemoryContextAlloc(CurrentMemoryContext, size);  /* implicit context! */
}

Then the allocator that actually carves memory. This is AllocSetAlloc()'s real shape, simplified for readability but faithful to the freelist-then-block-then-new-block order:

Caset.c — AllocSetAlloc(), simplified but faithful
void *
AllocSetAlloc(MemoryContext context, Size size)
{
    AllocSet set = (AllocSet) context;

    /* Big request: skip the freelist machinery, get a dedicated block */
    if (size > set->allocChunkLimit)
        return AllocSetAllocLarge(set, size);

    int fidx = AllocSetFreeListIndex(size);   /* round up to a size class */

    /* Freelist hit -- reuse a chunk this context pfree'd earlier */
    if (set->freelist[fidx] != NULL)
    {
        AllocChunk chunk = set->freelist[fidx];
        set->freelist[fidx] = *(AllocChunk *) chunk;   /* pop: reuses the freed
                                                          * chunk's own bytes to
                                                          * store the list link   */
        return MemoryChunkGetPointer(chunk);
    }

    /* Freelist miss -- carve fresh space out of the current block */
    Size chunk_size = 1 << (fidx + ALLOC_MINBITS);
    if (set->blocks == NULL ||
        set->blocks->freeptr + chunk_size + ALLOC_CHUNKHDRSZ > set->blocks->endptr)
        AllocSetAllocBlock(set, chunk_size);  /* malloc()! doubles nextBlockSize */

    MemoryChunk *chunk = (MemoryChunk *) set->blocks->freeptr;
    set->blocks->freeptr += chunk_size + ALLOC_CHUNKHDRSZ;
    MemoryChunkSetHdr(chunk, context, fidx);
    return MemoryChunkGetPointer(chunk);
}

And the reset that makes bulk-free cheap — the single most important function in this chapter:

Caset.c — AllocSetReset(), simplified but faithful
void
AllocSetReset(MemoryContext context)
{
    AllocSet set = (AllocSet) context;
    if (context->isReset) return;     /* nothing allocated: free lunch */

    AllocBlock block = set->blocks;
    while (block != NULL)
    {
        AllocBlock next = block->next;
        if (block == set->keeper)
        {
            /* rewind, don't free -- avoids a malloc() the very next
             * time this context is used, which matters enormously for
             * contexts reset once per tuple (ExprContext!)             */
            block->freeptr = ((char *) block) + ALLOC_BLOCKHDRSZ;
            block->next = NULL;
        }
        else
            free(block);         /* ONE call per block, not per chunk */
        block = next;
    }
    set->blocks = set->keeper;
    memset(set->freelist, 0, sizeof(set->freelist));  /* O(1): fixed 8-slot array */
    context->isReset = true;
}

Finally, why parallel workers can't just pass each other raw pointers the way a single backend passes pointers between its own contexts — dsa_pointer is a segment+offset handle, resolved separately in every process that attached the segment:

Cdsa.c — dsa_allocate(), simplified
dsa_pointer
dsa_allocate(dsa_area *area, Size size)
{
    /* size-classed like aset.c, but carved from DSM segments instead
     * of malloc'd blocks -- and returned as (segment index, offset)
     * packed into one 64-bit handle, never a raw C pointer, because
     * every backend attached this DSM segment at its OWN, independently
     * chosen virtual address                                          */
    int size_class = dsa_size_class(size);
    dsa_pointer p = alloc_from_segment_freelist(area, size_class);
    if (!DsaPointerIsValid(p))
        p = make_new_segment_and_allocate(area, size_class);  /* dsm_create() */
    return p;
}

/* every access needs an explicit translation, in whichever process: */
void *ptr = dsa_get_address(area, p);  /* segment_base[p.segment] + p.offset */
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Keep a "keeper" block instead of freeing everything on reset. A context that resets once per tuple (millions of times per query) would otherwise pay a malloc() + free() pair every single time — the keeper trick amortizes that to zero for the common case. 2. Make chunk headers small enough that nobody thinks about them, then keep shrinking them anyway. The PG16 header rework happened specifically because a "small, fixed" cost multiplied across billions of daily allocations stops being small. 3. Never let a shared-memory pointer look like a private one. dsa_pointer is deliberately not pointer-shaped in C's type system, specifically so it can't be dereferenced by accident in a process that hasn't translated it — a static, structural guard against the exact class of bug that would otherwise be trivial to introduce.
