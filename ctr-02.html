CONTAINER INTERNALS · CHAPTER 02

Namespaces I: PID, UTS,
Mount & IPC

A container is not a new kernel object. It is an ordinary process wearing a set of masks — each mask a namespace, a kernel data structure that changes what one syscall's worth of "the world" looks like from inside. This chapter builds four of those masks by hand, with the real syscalls (clone(), unshare(), setns()) and the real flags (CLONE_NEWPID, CLONE_NEWUTS, CLONE_NEWNS, CLONE_NEWIPC), and hits the two problems every from-scratch container implementer hits on day one: PID 1's zombie-reaping obligation, and the fact that /proc will keep lying to you until you remount it in exactly the right place, in exactly the right order.

ARC 01 · THE PROBLEM

One kernel, one PID space, one hostname, one mount table

Chapter 1 established that Linux containers share a kernel — there is no hypervisor, no second copy of the scheduler, no virtualized CPU. That leaves an uncomfortable question standing: by default, every process on a Linux box sees the exact same global state for almost everything that matters. There is one PID space (run ps aux anywhere and you see every process on the machine). There is one hostname (uname -n returns the same string to every process, because it is one kernel-global string). There is one mount table inherited at boot and mutated in place by every subsequent mount() call from any process with permission. There is one pool of System V and POSIX IPC objects, addressed by small integer keys that any two unrelated programs can collide on.

None of that is a bug — it is exactly how Unix has worked since 1969, and it is precisely right for a single multi-user machine where "sees everything" is the point. It is exactly wrong for a container, whose entire promise is that a process believes it is alone on the machine: PID 1 of its very own tiny world, its own hostname, its own filesystem view, its own IPC namespace so a stale semaphore from an unrelated program can never collide with its own. The problem this chapter solves is mechanical and specific: how does the kernel let one process see a private, self-consistent version of PIDs, hostname, mounts, and IPC objects, without cloning the kernel itself?

  • Process identity — a process needs to believe it is PID 1 (or some small number), with only its own descendants visible to it, even though the real kernel-wide PID space contains thousands of unrelated processes.
  • Host identity — hostname/domainname must be independently settable per container without one container's sethostname() call reaching every other process on the box.
  • Filesystem view — mounting, unmounting, and remounting inside a container must not appear in — or disappear from — the host's mount table, and vice versa.
  • IPC isolation — System V semaphores, message queues, and shared memory segments (all addressed by a small integer key via ftok()) must not collide between unrelated containers that happen to pick the same key, which legacy software does constantly.

The answer Linux settled on — arrived at piecemeal, over six years, by different engineers solving different narrow problems who only later realized they were building one general mechanism — is the namespace: a kernel object, one per resource class, that a process is a member of, and that the kernel consults on every relevant syscall. This chapter covers the first four kinds — PID, UTS, mount, and IPC — chosen because they are the oldest, the ones a container's init process must set up correctly before anything else can work, and the ones most likely to bite you with subtle, half-working isolation if you get the order of operations wrong. Network namespaces (chapter 3) and user namespaces (chapter 4) build on the exact same mechanism and are deliberately deferred so this chapter can go deep on the primitive itself.

WHY THIS MATTERS FOR THE NEXT 14 CHAPTERS

Every namespace in this course is the same shape: a kernel struct, a counter of how many tasks/mounts/fds reference it, and a rule for what a process inside it can address. Learn that shape once — on PID, UTS, mount, and IPC, where the state being isolated is small and easy to reason about — and network namespaces (chapter 3), user namespaces (chapter 4), and cgroup namespaces (chapter 5's neighbor) are the identical mechanism applied to harder resource classes. This is also the chapter where the course's central discipline starts paying off: we will say exactly what is isolated (addressing/visibility) and exactly what is not (the underlying kernel, the CPU scheduler, the physical devices) — never "it's like a lightweight VM."

DEEP CONTEXT · THE "NEWNS" NAMING TRIVIA

CLONE_NEWNS is not an abbreviation of anything to do with mounts. It is short for "new namespace", full stop — because when it was added in Linux 2.4.19 (2002), mount namespaces were the only namespace type in existence, so "new namespace" and "new mount namespace" were the same sentence. Every namespace type added afterward needed its own, more specific name (CLONE_NEWUTS, CLONE_NEWIPC, CLONE_NEWPID...), leaving the original with a name that reads as a bug report about itself. It is one of the most-asked "why is this called that" questions in the container-tooling world, and now you know: it is a first-mover artifact, not a design choice.

ARC 03 · NAIVE SOLUTION

Attempt #1: chroot and a prayer

Chapter 1 already introduced chroot() as 1979's answer to filesystem isolation, and it is the natural first thing anyone reaches for when asked to "isolate a process." Here is the honest naive attempt at a container using only what chapter 1 gave us — no namespaces of any kind yet:

bashnaive_container.sh — chroot only, no namespaces
#!/bin/bash
# "Containerize" a process using nothing but chroot(). This is genuinely
# attempt #1 that most people try before learning namespaces exist.

mkdir -p /rootfs/myapp
tar -xf myapp-rootfs.tar -C /rootfs/myapp    # extract an image's filesystem

echo "myapp-container" > /rootfs/myapp/etc/hostname   # hope this "sets" the hostname

chroot /rootfs/myapp /bin/myapp                 # jump the filesystem root, exec the app

Writing a file named /etc/hostname inside the chroot feels like it should isolate the hostname — it is, after all, the file most Linux distros read at boot to call sethostname(). But nothing in this script actually calls sethostname(), and even if it did, that syscall changes one kernel-global string with no notion of "for this chroot only." Similarly, nothing here touches process visibility or IPC at all — chroot only ever changes what / resolves to for path lookups. Everything else about the process's view of the machine is completely unchanged.

WHAT THIS GETS RIGHT

Don't dismiss it — chroot's filesystem-root trick is real, cheap, and still part of every container runtime's final rootfs setup today (via pivot_root, chapter 6's sharper version of the same idea). The naive attempt's failure mode is not "wrong tool" — it's "incomplete tool": chroot solves exactly one of the four problems from §1, and nothing here even attempts the other three.

ARC 04 · WHY IT FAILS

Run it, and watch three kinds of leakage — quantified

Run naive_container.sh and then poke at it from inside the chroot. Every one of these is a real, reproducible command, not a hypothetical:

  • ps aux inside the chroot lists every process on the host — not a handful, all of them. On a modestly busy host that is 150–300 lines, complete with other users' command lines, full argv (which routinely contains secrets passed as flags), and real PIDs. Worse: if the containerized process runs as root, those real PIDs are directly addressable — kill -9 <host-pid> from inside the "container" terminates a host process, because there is no PID namespace stopping the signal from being delivered.
  • hostname is a global write, not a local one. If the naive script's app calls sethostname() to actually apply that /etc/hostname file, it changes the real kernel's hostname string — the one uname -n returns for every process on the machine, including the host's own monitoring agents. Run two of these "containers" wanting two different hostnames on one host and the second one to call sethostname() wins, silently, for everyone.
  • mount inside the chroot is mount everywhere. mount -t tmpfs tmpfs /tmp run inside the chroot adds a line to the kernel's one global mount table — visible in cat /proc/self/mountinfo from a completely unrelated host shell, immediately. Unmounting it from the host, or from a second "container," removes it for the first one too.
  • IPC keys collide. Two unrelated legacy applications both calling ftok("/app", 'A') compute the same System V IPC key by construction — ftok()'s whole design is a deterministic hash of a pathname and a project id, and pathnames repeat constantly across images built from similar bases. Without an IPC namespace, the second app's semget(key, ..., IPC_CREAT|IPC_EXCL) returns EEXIST against the first app's semaphore set — or worse, a non-exclusive shmget() silently attaches to the wrong shared memory segment and the two unrelated programs start corrupting each other's data with zero error at all.
THE PATTERN TO NOTICE

Every one of these failures has the identical shape: a syscall that mutates or queries global kernel state, with no parameter anywhere in its signature for "which container." sethostname(const char *name, size_t len) has no container argument. Neither does mount(), nor semget(), nor the PID-addressing half of kill(). You cannot fix this by writing more userspace code around these calls — there is nothing to pass. The only fix is a kernel-side one: make the syscall itself resolve against per-process state instead of one global. That is precisely what a namespace is.

ARC 05 · THE REAL PRIMITIVES

clone(), unshare(), setns() — and the four flags

Three syscalls create and join namespaces. Get their difference straight now, because the simulator in §15 and the incidents in §11 both hinge on it:

  • clone(int (*fn)(void*), void *stack, int flags, void *arg, ...) — like fork(), but flags can include one or more CLONE_NEW* bits. The new child is placed into brand-new namespaces of exactly those kinds at the moment it is created. This is what container runtimes actually call.
  • unshare(int flags) — moves the calling process itself out of its current namespaces and into new ones, with no new process created. The catch, and it is a real gotcha covered in depth in §8 and §12: for CLONE_NEWPID specifically, unshare() does not change the caller's own PID or its own view of /proc — it only sets up a new PID namespace for the caller's future children. The calling process's own getpid() is unaffected because a running process's PID cannot change out from under it.
  • setns(int fd, int nstype) — joins an existing namespace, given an open file descriptor to one of the /proc/[pid]/ns/* files (§8 shows the real paths). This is the syscall behind nsenter and behind docker exec/podman exec: joining a namespace that some other, already-running process created.

Every syscall that used to consult one global now consults current->nsproxy->whatever_ns instead. That one-line conceptual change is the entire mechanism — everything else in this chapter is consequences of it.

ARC 06 · WHY THAT STILL HURTS

Congratulations, your process is now PID 1

Namespacing a process solves the four isolation problems from §1 — and immediately hands you a fifth problem that chroot never had to face, because chroot never made anything believe it was init. Every PID namespace's first process is, from the kernel's point of view, that namespace's PID 1 — and PID 1 carries obligations that ordinary processes don't.

On real Unix, PID 1 (the system's actual init) has one full-time job: reap every process whose parent has died, so they never become permanent zombies. When a process's parent dies before calling wait() on it, the kernel reparents the orphan to the nearest living ancestor that has marked itself a subreaper (via prctl(PR_SET_CHILD_SUBREAPER), Linux 3.4, 2012), or, failing that, all the way up to PID 1 of its namespace. A PID namespace's PID 1 inherits this responsibility automatically and completely, whether or not the program running as PID 1 was ever written with that in mind — and almost none are. A web server, a Node script, a Python entrypoint: none of them call wait() on processes they never spawned. Watch what happens:

There is a second, independent PID-1 surprise, and it is the one that generates far more support tickets: the kernel gives any namespace's PID 1 the exact same special signal treatment the real, global init has always had — any signal for which PID 1 has not explicitly installed a handler is silently ignored, with the sole exception of SIGKILL and SIGSTOP, which can never be blocked or ignored by anyone. Most application binaries never call sigaction() for SIGTERM — they rely on the default disposition, which for every non-PID-1 process is "terminate the process." As PID 1, that default silently flips to "do nothing at all."

WHY tini AND dumb-init EXIST

Both problems have the same fix, and it is exactly what a real init does: run a tiny, purpose-built binary as PID 1 instead of the application. tini (Meltwater/krallin, MIT-licensed) and dumb-init (Yelp) both (a) install real signal handlers for the signals that matter and forward them to the actual application process, and (b) run a wait()/waitpid(-1, ...) loop that reaps every exited child, including ones reparented to them that they never spawned directly. The application then runs as PID 1's child instead of PID 1 itself, and inherits none of PID 1's kernel-special treatment. §9 covers exactly which binary each engine ships by default — and it is not the same one.

NAMESPACE LIFETIME IS REFERENCE-COUNTED, NOT PROCESS-COUNTED

A namespace is destroyed only when its reference count hits zero — and there are three independent kinds of reference: (1) a running task whose nsproxy points at it, (2) a bind-mount of one of these /proc/[pid]/ns/* files onto a persistent path (exactly how ip netns add keeps a network namespace alive with zero processes in it — a technique chapter 3 uses directly), and (3) a plain open file descriptor to one of these files, held by any process for any reason (a monitoring agent that opened one to inspect a container and never closed it). All three keep the namespace — and everything it isolates — alive after the container's last process exits. §11 covers the real operational incident this causes.

WHY 32 LEVELS, EXACTLY

The kernel constant is MAX_PID_NS_LEVEL = 32 (include/linux/pid_namespace.h). It is not derived from any deep theoretical bound — it is a deliberately generous, fixed safety cap chosen because every process needs one struct upid (a per-namespace PID mapping entry) for every level of nesting it is visible at, and every cross-namespace operation — delivering a signal, resolving a PID for /proc, reaping in wait() — must walk that chain of ancestors. Unbounded nesting means unbounded per-process memory and unbounded worst-case syscall latency; 32 was picked as "more than anyone sane will nest containers-in-containers" rather than computed from a formula.

ARC 10 · PERFORMANCE / SECURITY CHARACTERISTICS

Cheap to create, not free to trust

Two independent claims, and it matters that you keep them separate:

  • Namespace creation is fast. Each CLONE_NEW* flag allocates one small, reference-counted kernel struct and (for mount and IPC) walks existing state to copy or reset it — work measured in microseconds, not milliseconds, and utterly dwarfed by the cost of booting an actual virtual machine's kernel and device model (typically hundreds of milliseconds to low seconds). This is the honest, mechanism-level version of "containers start fast" — not because a container is a smaller VM, but because creating a namespace is orders of magnitude cheaper than booting a kernel, since it is just kernel bookkeeping against a kernel that is already running.
  • Namespace isolation is not a privilege boundary. A process inside a fresh PID/UTS/mount/IPC namespace is still running on the exact same kernel, under the exact same scheduler, subject to the exact same syscall table as everything else on the box. Namespaces restrict what a process can address by name — which PIDs it can target with kill(), which hostname string it reads, which mount table it sees. They say nothing at all about what a process is permitted to do once it has found a way to reach something — that is capabilities' job (chapter 7) and seccomp/LSM's job (chapter 8), both still ahead. A process with CAP_SYS_ADMIN and a private mount namespace can still, for example, load a kernel module or flip a non-namespaced sysctl that affects the entire host.

THE ATTACK-SURFACE COROLLARY

Because every namespaced process still shares one kernel, a single kernel vulnerability in namespace-aware code (a bug in the PID-translation path, the mount-propagation logic, or the IPC key lookup) is a vulnerability against every container on the host simultaneously — there is no second kernel instance to contain the blast radius the way a hypervisor would. This is precisely why chapter 15's incident catalog is dominated by kernel-level and runtime-level escapes rather than "a container guessed another container's password": the shared kernel is both the entire reason containers are cheap and the entire reason a namespace escape is catastrophic rather than merely embarrassing.

ARC 11 · REAL-WORLD PRODUCTION

Four incidents this chapter's mechanics fully explain

Incident 1: "Every deploy hangs for exactly 10 seconds"

A team notices every rolling deploy pauses for precisely ten seconds per container before the next one starts — long enough to matter at fleet scale, short enough to be easy to shrug off. Root cause, directly from §6: the application is PID 1, it never installed a SIGTERM handler, and PID 1's kernel-special default disposition for an unhandled signal is ignore, not terminate. The container runtime's stop command sends SIGTERM, waits for a configurable grace period (10 seconds is both Docker's and Podman's default stop.timeout), gets no response, and finally sends the un-ignorable SIGKILL. Fix: add --init (injecting tini or catatonit per §9), or have the application install its own handler — either converts PID 1 from "silently immune" to "actually listening."

Incident 2: slow, silent zombie accumulation until fork() fails

A long-running container that shells out to short-lived helper processes (a cron-like scheduler, a build agent invoking compilers) accumulates Z (defunct) entries in its own ps output at a low, easy-to-miss rate. Weeks later, new process creation inside that container starts failing with EAGAIN ("Resource temporarily unavailable") from fork() — exactly the mechanism the §8(c) slider makes concrete: the namespace's pid_max has been silently consumed by zombies that were never wait()-ed on, because the application, acting as PID 1, was never written to reap processes it didn't directly spawn. Fix: the same one as Incident 1 — a real init as PID 1 that reaps everything reparented to it, not just its direct children.

Incident 3: mount events leaking from container to host

In the early years of container tooling on systemd-managed hosts, a container's own internal mount() calls were observed appearing in the host's mount table — despite the container correctly having its own mount namespace. The mechanism: Linux mount namespaces support propagation modes (shared, private, slave, unbindable), and a namespace's mounts default to whatever propagation the parent mount had at the moment the namespace was created. Because systemd mounts / as MS_SHARED by default, a naively created container mount namespace inherited shared propagation too — a private namespace in name, but one still wired into the host's propagation peer group. The fix that container runtimes converged on: explicitly run mount --make-rprivate / (or the equivalent MS_REC|MS_PRIVATE remount) inside the new mount namespace before doing anything else, severing the propagation link. Every modern container runtime does this unconditionally now — it is why this specific failure mode is largely historical, but the propagation-mode concept it exposed is not optional knowledge for anyone debugging a bind-mount that "shouldn't" be visible somewhere.

Incident 4: "Bus error" from a 64 MB /dev/shm

Applications that lean on POSIX shared memory under /dev/shm — most visibly, PyTorch/TensorFlow data-loader workers and headless Chrome/Selenium — crash with SIGBUS ("bus error") under real workloads that ran fine on bare metal. Cause: /dev/shm is a tmpfs mount, and a fresh mount namespace's default size for it is a conservative 64 MB, far smaller than the multi-gigabyte /dev/shm most bare-metal hosts are configured with. It is not an IPC-namespace bug — POSIX shared memory segments under /dev/shm are files on a namespaced tmpfs mount, so this is really a mount namespace default colliding with an application's undocumented assumption. Fix: both Docker (--shm-size) and Podman (--shm-size, identical flag name) let you raise the tmpfs size explicitly per container.

First, a minimal namespaced launcher — everything from §5 and §8(a) in about thirty real lines:

Cminimal_init.c — hand-rolled namespace setup, no runtime involved
int main(void)
{
    /* One call, four namespaces. The calling process's own PID is
     * unaffected by CLONE_NEWPID here -- see the callout in §5. */
    if (unshare(CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWNS | CLONE_NEWPID) == -1)
        err(1, "unshare");

    pid_t child = fork();          /* THIS process enters the new PID namespace as PID 1 */
    if (child == 0) {
        sethostname("my-container", 12);      /* safe now: private UTS ns   */

        mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL);  /* sever propagation (§11)  */

        /* THE fix for the /proc lie: mount a FRESH procfs now that we
         * are both inside the new mount ns AND the new pid ns. The
         * inherited /proc mount still points at the OLD pid ns.     */
        mount("proc", "/proc", "proc", 0, NULL);

        execve("/bin/myapp", argv, envp);   /* becomes PID 1 for real   */
    }
    waitpid(child, &status, 0);   /* the ORIGINAL process reaps its one known child */
    return WEXITSTATUS(status);
}

Second, the reaping loop that turns any binary into a namespace-safe PID 1 — the actual shape of tini's core, simplified but structurally faithful:

Ctini_core.c — signal forwarding + the reap-everything loop
static pid_t child_pid;

static void forward_signal(int sig) {
    kill(child_pid, sig);        /* PID 1 now HAS a handler: SIGTERM is no longer ignored */
}

int main(int argc, char *argv[]) {
    for (int s = 1; s < NSIG; s++) signal(s, forward_signal); /* except SIGCHLD */
    signal(SIGCHLD, SIG_DFL);

    child_pid = fork();
    if (child_pid == 0) execvp(argv[1], argv + 1);   /* the REAL app, now NOT PID 1 */

    int app_exit_code = 0;
    for (;;) {
        int status;
        pid_t reaped = waitpid(-1, &status, 0); /* -1: reap ANY child, including ones we never spawned --
                                                 this IS the zombie-prevention fix from §6           */
        if (reaped == child_pid) app_exit_code = WEXITSTATUS(status);
        if (reaped == -1 && errno == ECHILD) break;   /* no children left at all */
    }
    return app_exit_code;
}

Third, why runc writes its namespace-joining logic in C rather than Go — a real, well-known design constraint rather than a style choice:

Cnsenter.c — a constructor that runs before the Go runtime exists
/* The Go runtime is heavily multithreaded from the moment it starts --
 * it spins up OS threads for the scheduler and garbage collector before
 * main() ever runs. setns() into a PID namespace only affects a process's
 * FUTURE children (§5's unshare() gotcha applies to setns() too), and
 * joining some namespace types correctly is only well-defined while the
 * calling process is still single-threaded. A cgo constructor runs
 * before Go's runtime has spawned anything: */
__attribute__((constructor)) static void nsenter_init(void) {
    int fd = open("/proc/1234/ns/pid", O_RDONLY);
    setns(fd, CLONE_NEWPID);          /* single-threaded: this is safe here      */
    /* ... setns() for mnt, uts, ipc, net, user, cgroup similarly ... */
    syscall(SYS_clone, ...);          /* now fork the process that becomes PID 1 */
    /* control returns to Go's main() only inside the correctly-namespaced child */
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Order is not negotiable. Mount namespace before PID namespace before procfs remount — reverse any two of those and /proc ends up bound to the wrong PID namespace, silently, with no error at all (this is exactly why §11's incidents are so easy to introduce and so hard to notice in code review). 2. Never assume default signal disposition on PID 1. tini's entire reason to exist is one sentence: the kernel's PID-1 special-casing is a feature for real init systems and a footgun for arbitrary application binaries pressed into that role. 3. Single-threaded windows are load-bearing. runc's C constructor trick is not incidental style — some namespace operations are only well-defined before a process has spawned additional OS threads, which is exactly what a Go binary does automatically and immediately.
