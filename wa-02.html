WHATSAPP ARCHITECTURE · CHAPTER 02

The Connection Layer:
2M Sockets Per Server

"One million, then two million, concurrent connections on a single FreeBSD box" is the single most-cited number in this course's source material — and the number most often repeated without anyone reconstructing where it actually comes from. This chapter builds it back up from the kernel outward: what a TCP connection costs in bytes, why select() and poll() cannot survive at this density, why kqueue was the only viable readiness-notification model in 2011, and why none of that matters if you ignore what a cellular radio does to a phone's battery every time it wakes up for a keepalive.

You will understandWhy kqueue's O(1), batched readiness model is the only fit at this density, and how it maps onto BEAM's own scheduler.
You will predictExactly which kernel or BEAM limit fails first as connections ramp — and the literal error message each one emits.

ARC 01 · THE PROBLEM

A TCP connection is not free — and you are about to hold two million of them

Chapter 1 established why WhatsApp bet on Erlang/OTP and FreeBSD. This chapter is about what it actually took to make "two million concurrent connections on one box" true, rather than aspirational — a budget with a kernel side, a runtime side, a wire-protocol side, and a mobile-radio side, all of which have to balance simultaneously.

  • Kernel memory per connection is not optional overhead — it's the primary constraint. A socket, a TCP control block, and send/receive buffers exist for every connection whether or not it is doing anything, and at 2 million connections even small per-connection numbers multiply into the dominant cost on the box.
  • Readiness notification must be O(1), not O(n). Something has to tell the runtime which of two million sockets have data waiting, on every scheduler tick, without re-scanning all two million each time.
  • Every byte on the wire is expensive twice over. Once in server-side bandwidth and CPU to parse it, and once — far more expensively — in the seconds of high-power cellular radio state a phone burns to send or receive it at all.
  • The network itself is actively hostile. Carrier-grade NATs silently forget idle mappings; cellular radios aggressively power down between bursts; and any of the phones on the other end of these two million sockets can vanish and reappear at any moment, indistinguishable at the TCP layer from a slow client.

Get any one of these four wrong and "2 million connections per box" stops being a real number — either the kernel runs out of memory, the event loop stops keeping up, the wire protocol saturates the radio link, or every phone's battery drains keeping a socket alive that carries almost no data. This chapter derives the budget that keeps all four in balance.

WHY THIS MATTERS FOR THE REST OF THIS COURSE

Every later chapter — offline delivery, multi-device fanout, end-to-end encryption — assumes this transport layer as a given: a connection that is cheap enough to hold at scale, fast enough to establish that a handshake doesn't dominate perceived latency, and robust enough to survive a phone moving from Wi-Fi to a 2G cell tower mid-conversation. Get this chapter's budget right and everything above it is a design problem; get it wrong and everything above it is a performance-firefighting problem.

ARC 02 · HISTORICAL CONTEXT

From "it forks" to "it holds two million sockets"

Chapter 1 ended with a decision: fork ejabberd onto Erlang/OTP and FreeBSD. That decision bought a working presence/routing skeleton and a process model capable, in principle, of extreme connection density — but reaching the actual published numbers took roughly three more years of kernel tuning, protocol replacement, and (later) a full handshake redesign as mobile networks and cryptography requirements evolved. DEEP CONTEXT · kqueue's HEAD START

kqueue shipped in FreeBSD in 2000, roughly two years before Linux's epoll arrived in kernel 2.5.44 (2002). By 2009–2011, when this connection layer was being tuned, kqueue was the more mature, more battle-tested implementation of the same underlying idea — one more small piece of corroborating evidence for the FreeBSD bet chapter 1 described, independent of the founders' prior operational familiarity with it.

ARC 03 · NAIVE SOLUTION

Attempt #1: stock kernel defaults, a simple event loop

Derive the budget honestly. Take a fresh FreeBSD (or Linux) install, write a straightforward event-driven TCP server, and change nothing about the kernel's default networking parameters:

Cnaive_conn_server.c — the strawman, annotated
int lfd = socket(AF_INET, SOCK_STREAM, 0);
bind(lfd, ...); listen(lfd, 128);   /* default backlog, default everything */

fd_set readfds;
for (;;) {
    FD_ZERO(&readfds);
    FD_SET(lfd, &readfds);
    for (int i = 0; i < nclients; i++)
        FD_SET(clients[i], &readfds);        /* rebuild the whole set, every tick */

    select(maxfd+1, &readfds, NULL, NULL, NULL);  /* kernel rescans everything too */

    for (int i = 0; i < nclients; i++)
        if (FD_ISSET(clients[i], &readfds))
            handle_client(clients[i]);         /* default 64 KB send+recv buffers,
                                                   default file-descriptor limit (~1024) */
}

This is not an unreasonable starting point — it's precisely how most TCP servers are written, and for a server handling a few hundred or even a few thousand connections it is entirely adequate. The kernel's defaults exist because they're sane for the overwhelming majority of workloads that never approach internet-scale connection density. The question, as always in this course, is what happens at two million.

ARC 04 · WHY IT FAILS

Three independent walls, each hit before you reach a fraction of the target

  • select() has a hard, uncrossable ceiling. fd_set is a fixed-size bitmap, conventionally capped at FD_SETSIZE — typically 1024 file descriptors. There is no tuning parameter that gets a standard select()-based server to two million connections; the API itself refuses to represent that many descriptors.
  • poll() removes the hard cap but not the cost. poll() accepts an arbitrarily large array of descriptors, but the kernel must linearly rescan the entire array on every single call to find the ready ones — O(n) per tick. At two million descriptors, most of them idle at any instant, that is millions of wasted comparisons every scheduler tick, collapsing throughput as connection count grows, long before any actual message traffic does.
  • Default socket buffers alone blow the memory budget. Stock BSD/Linux defaults commonly allocate on the order of 64 KB each for the send and receive buffers per TCP socket — call it ~128 KB per connection before a single byte of application state. At 2,000,000 connections: 2,000,000 × 128 KB ≈ 256 GB for socket buffers alone, on hardware where "big" meant a few hundred gigabytes total. Real messaging traffic is bursty and tiny per message — paying full-size buffers for every idle connection is almost entirely waste.
  • The file-descriptor table itself is capped by default. Most Unix defaults limit a process to on the order of 1,024–4,096 open file descriptors unless kern.maxfiles/kern.maxfilesperproc (or Linux's equivalent ulimit/fs.file-max) are explicitly raised. Out of the box, the process cannot even accept its two-thousandth connection, let alone its two-millionth.
THE ARITHMETIC, IN ONE PLACE

select(): hard cap around 1,024 descriptors — categorically ruled out. poll(): no hard cap, but O(n) rescanning per tick makes it effectively unusable well before a million idle connections on any single core. Socket buffers at stock defaults: ~256 GB for 2 million connections — larger than the RAM in most single machines of the era. File descriptor limits: refuse to let you open more than a few thousand sockets at all without explicit configuration. Every one of these has to be individually solved before the other three even become visible as problems — which is exactly why §5–§8 solve them one at a time rather than pretending one clever trick fixes all four.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Readiness notification: four models, one survivor at this density

Candidate A: select()

Already eliminated in §4 — a fixed-size bitmap conventionally capped around 1,024 descriptors cannot represent two million connections at all. Rejected outright, not merely inefficient.

Candidate B: poll()

Removes the hard cap but keeps an O(n) per-call scan of the entire descriptor array, whether or not any given descriptor changed state since the last call. At high connection counts with a low fraction of "hot" (ready) descriptors at any instant — the normal case for a messaging server, where most phones are idle most of the time — the wasted work dominates. Rejected: doesn't scale past roughly tens of thousands of descriptors on a single core before the rescan cost swamps actual I/O handling.

Candidate C: Linux epoll

The kernel maintains the interest set itself (registered once via epoll_ctl), and epoll_wait returns only the descriptors that actually became ready — O(1) amortized per event rather than O(n) per call. A real, proven solution at this density (and the one the rest of the industry converged on). Two catalog notes for this course specifically: it didn't exist on FreeBSD, the platform chapter 1 already committed to, and each readiness check is still a separate epoll_wait syscall.

Candidate D: FreeBSD kqueue ✓

The same O(1) amortized-cost idea as epoll, registered via a persistent kernel-side interest set — but kevent() unifies registering new interest and retrieving ready events into a single syscall that can batch many changes and many results at once, and generalizes the same mechanism across sockets, timers, signals, and file-system events through one consistent API. Given chapter 1's FreeBSD commitment, this was the natural and, by every available account, effective choice.

THE CLINCHING ARGUMENT: THE RUNTIME NEVER SEES THE SYSCALL

None of this machinery is visible to an Erlang application programmer. BEAM's own I/O subsystem (the inet driver) registers every socket with the kernel's readiness mechanism itself, and when kqueue reports a socket readable, the runtime delivers that as an ordinary message into the owning connection process's mailbox. The BEAM scheduler that chapter 1 described — reduction-counted, preemptive, one thread per core — is the same scheduler that reacts to this event. You get chapter 1's isolation guarantees and this chapter's O(1) readiness efficiency simultaneously, because the runtime — not the application, and not the OS alone — is doing the multiplexing.

ARC 06 · WHY THAT STILL COSTS

kqueue solves one problem. Three more remain.

  • Buffer sizing still has to be tuned by hand. kqueue tells you a socket is readable; it says nothing about how large that socket's kernel buffers should be. Left at defaults, the ~256 GB problem from §4 doesn't go away — net.inet.tcp.sendspace/recvspace and buffer auto-sizing have to be deliberately tuned down for a fleet of mostly-idle, small-message connections (§8).
  • The mbuf cluster budget must be sized to match, or the kernel runs out of network memory first. FreeBSD allocates packet buffers from a fixed-size pool of mbuf clusters; undersizing that pool means new connections or packets start failing well before the box's total RAM is exhausted.
  • BEAM's own process and port limits must be raised to match the kernel's. The kernel can be tuned to hold two million sockets, but the VM flags +P (max processes) and +Q (max ports) default to values far below that — raise the kernel ceiling without raising BEAM's, and the runtime refuses new connections while the kernel still has headroom.
  • None of this touches the mobile side of the wire. Even a perfectly tuned kernel and runtime still have to talk to a phone behind a carrier-grade NAT that silently forgets idle mappings, and to a cellular radio that treats every keepalive as an expensive wake-up event (§8g). Kernel tuning buys you the server's half of the budget; the client's half is a separate, equally real cost.
THE HONEST TRADE

Every one of these costs is a configuration and protocol-design problem, solvable once and encoded into deployment tooling and client behavior — not a per-connection operational burden that grows with traffic. That is precisely the same "bounded, learnable cost vs. cost that scales with headcount" trade chapter 1 made about Erlang and FreeBSD generally, applied here one layer down the stack.

ARC 08 · INTERNAL IMPLEMENTATION

The full budget, line by line

(a) What a TCP connection actually costs the kernel

Four structures exist for every open connection, active or not: a socket structure, a tcpcb holding the TCP state machine's variables (sequence numbers, congestion window, RTT estimation), a pair of socket buffers (sockbuf), and a file-descriptor table slot. The socket buffers dominate: at stock defaults (commonly ~64 KB send + ~64 KB receive), that's the ~256 GB problem quantified in §4. Real deployments at this density tune net.inet.tcp.sendspace and recvspace down dramatically — to a few kilobytes per idle connection is realistic for a protocol whose messages are small and infrequent — and rely on FreeBSD's socket-buffer auto-sizing to grow a specific connection's buffers temporarily under real load rather than paying the maximum for every idle one.

(b) kqueue vs. the alternatives, mechanically

select() and poll() require the caller to hand the kernel the entire set of descriptors to check, every single call — the kernel has no memory of what you asked about last time. kqueue flips this: you register interest once (EV_ADD), and the kernel maintains that interest set indefinitely, notifying you only of descriptors that actually changed state, retrieved via kevent() — a single syscall that can simultaneously submit new registrations and collect a batch of ready events. This batching matters enormously at high event rates: one syscall handling hundreds of state changes has a fundamentally different cost profile than hundreds of individual syscalls, and syscall overhead (context switch into and out of kernel mode) is one of the largest fixed costs an event loop pays per unit of work.

(c) The combined memory budget: kernel + BEAM, at 2 million connections

Putting chapter 1's runtime number and this chapter's kernel number in the same place:

  • BEAM process state: ~3 KB × 2,000,000 ≈ 6 GB (chapter 1).
  • Tuned socket buffers: a few KB × 2,000,000 ≈ roughly 10–20 GB, versus ~256 GB at stock defaults — the single largest lever this chapter pulls.
  • tcpcb + socket structure + fd table overhead: low hundreds of bytes each × 2,000,000 ≈ a few hundred MB to low GB — small relative to the buffer budget, but not zero.
  • mbuf cluster pool: sized via kern.ipc.nmbclusters to match expected in-flight packet volume — undersized, and the kernel starts dropping packets or refusing new connections well before RAM is exhausted, independent of how much free memory top reports.

Total: on the order of tens of gigabytes for the entire connection layer — comfortably inside a machine with a few hundred gigabytes of RAM, which is exactly the "few big machines" philosophy chapter 1 named paying off in practice.

(e) FunXMPP: binary framing in place of XML

Chapter 1 named the cost; here is the fix. FunXMPP replaces XMPP's textual, self-describing XML stanzas with a dictionary-based binary encoding: the small, fixed vocabulary of tag names, attribute names, and common attribute values that appear in almost every stanza (message, to, from, type, chat...) are each replaced with a single token byte from a shared dictionary known to both client and server, with a length-prefixed binary structure replacing angle brackets and closing tags entirely. The result is commonly on the order of a 10× reduction in bytes on the wire for a typical stanza, and — just as importantly for a runtime processing millions of frames per second — no XML parser has to run at all; decoding becomes a small table lookup and a memory copy.

Illustrativethe same stanza, two encodings
// XMPP (raw XML) — 71 bytes for this fragment alone
<message to="14155550123@s.whatsapp.net" type="chat">
  <body>hey</body>
</message>

// FunXMPP (illustrative binary framing) — roughly a tenth the size
[TAG:MESSAGE] [ATTR:TO][LEN:7][14155550123] [ATTR:TYPE][VAL:CHAT]
  [TAG:BODY] [LEN:3]"hey"
[END]

(f) Noise Protocol Framework and Noise Pipes: cutting round trips that cost seconds, not milliseconds

WhatsApp's original transport-security handshake was a custom design; it was later replaced with a handshake built on the Noise Protocol Framework. Where a full TLS-style handshake typically needs a round trip to negotiate parameters and exchange certificates before any application data can flow, a Noise handshake pattern tailored to a known relationship between client and server (the two sides already know or can quickly verify each other's long-term keys) can establish an encrypted, mutually authenticated channel in fewer round trips — and Noise Pipes add a fast-resumption path (conceptually similar in spirit to TLS 1.3's 0-RTT resumption) for a client reconnecting with a previously-established identity, letting steady-state reconnects skip straight to a lightweight confirmation rather than a full handshake. On a data-center link a saved round trip is a rounding error; on a 2G connection in a coverage-marginal area, a single round trip can cost hundreds of milliseconds to multiple seconds (§10), so this redesign is a direct, load-bearing latency optimization, not a cryptographic nicety.

(g) The mobile radio: why keepalive frequency is a battery-life decision

A cellular radio does not stay in a high-power state continuously — it moves through RRC states to save battery: IDLE (radio mostly off, periodically waking to check for paging), promoted to CONNECTED/active the instant any data needs to move, and held there for a tail time — commonly several seconds to tens of seconds, depending on carrier configuration — after the last packet, before dropping back down. A TCP keepalive sent every few seconds looks harmless from a server's perspective (a few bytes) but from the phone's perspective it can mean re-promoting the radio and holding it in its most power-hungry state for the entire tail window, repeatedly, all day — a meaningfully different battery cost than the same bytes sent over Wi-Fi. This is precisely why keepalive interval is not a "set it and forget it" constant but a tuned, carrier-and-network-aware parameter.

RRC radio state machineCLICK TO STEP

The other half of the mobile-network story is the carrier-grade NAT sitting between the phone and the internet. Its address-mapping table entry for an idle TCP connection is reclaimed after a timeout the carrier chooses — often on the order of minutes — with no notification to either endpoint. If no keepalive crosses that mapping before it's reclaimed, the client believes the connection is still open (no RST was ever sent — the NAT just quietly forgets), and the next real message vanishes into a mapping that no longer exists. The fix is an adaptive keepalive interval: shorter than whatever NAT timeout the client empirically observes on its current network, but no shorter than necessary, to minimize the RRC cost above.

Reconnection after any disruption — a NAT timeout, a tower handoff, a server restart — needs exponential backoff with jitter: each client waits a randomized, growing interval before retrying, so that a large population of clients disconnected simultaneously (say, by a server dying) does not reconnect in one synchronized burst that looks, to the surviving infrastructure, exactly like a denial-of-service attack. §15 lets you feel this failure mode directly.

ARC 10 · PERFORMANCE CHARACTERISTICS

Big-O, bytes, round trips, and the number nobody puts on a slide: seconds of radio-on time

(a) Readiness notification, formally

The practical delta between epoll and kqueue at this density is smaller than the delta between either of them and poll() — both are O(1)-amortized, production-proven designs. kqueue's edge here is a single unified syscall for combined registration-and-retrieval versus epoll's two distinct calls, plus (in 2011) kqueue being the only one of the two that existed on FreeBSD at all.

(b) Memory and CPU per connection

  • Kernel side, tuned: a few KB of socket buffer (down from ~128 KB stock) plus ~0.5–1 KB of tcpcb/socket-structure overhead — call it 4–10 KB per idle connection, not the ~128 KB stock default.
  • BEAM side: ~2–3 KB of process heap per connection (chapter 1's number), scheduled by reduction counting rather than OS preemption, so the cost of having two million of them idle is memory, not scheduler time — an idle BEAM process consumes no CPU at all until a message arrives.
  • Contrast with a thread-per-connection design: a native OS thread's default stack reservation is commonly megabytes (8 MB is a typical Linux default, though much of it is never touched and backed only on demand) — at 2 million threads, even mostly-unfaulted stacks pressure the kernel's page tables and address-space accounting in a way 2 million ~3 KB BEAM processes simply don't.

(c) Round trips: the cost measured in time, not just bytes

A generic TLS-class handshake — negotiate parameters, exchange and validate certificates, derive keys — commonly costs on the order of 2 round trips before application data can flow (more with certificate chain validation or session-ticket misses). A Noise Protocol Framework handshake pattern chosen for a client and server that already share long-term key material can complete mutual authentication and key derivation in as little as 1 round trip, and Noise Pipes' resumption path lets a returning client send data essentially immediately, confirmed by the server's first reply — closer to 0 additional round trips of pure handshake waiting beyond the underlying transport's own connect.

(d) The number that doesn't fit on a latency dashboard: RRC-driven battery cost

Take a keepalive every 30 seconds versus every 4 minutes, and a representative RRC tail time of ~11 seconds after each promotion to the radio's active state (illustrative — actual tail timers are carrier- and generation-specific and not uniformly published). At 30-second keepalives: 2,880 radio promotions per day × 11 s ≈ 8.8 hours of high-power radio-on time attributable to keepalives alone. At 4-minute keepalives: 360 promotions × 11 s ≈ 1.1 hours. That roughly 8× difference, for a parameter most engineers would default to "whatever feels safe," is why adaptive, empirically-tuned keepalive intervals are a first-class design decision in this chapter rather than a config-file afterthought.

ARC 11 · REAL-WORLD PRODUCTION

The published numbers, and what they imply happened in between

Milestone: "1 million is so 2011"

WhatsApp's own engineering blog documented sustaining roughly one million concurrent connections on a single server in 2011 — the first public confirmation that the FreeBSD/Erlang bet from chapter 1 was paying off at real scale, not just architecturally sound on paper.

Milestone: two million, and the talk that is the source of this chapter's headline number

WhatsApp engineer Rick Reed's widely cited Erlang Factory SF talk, "Scaling to Millions of Simultaneous Connections," documents the progression from roughly one million to two million concurrent connections sustained on a single FreeBSD/Erlang box — the exact number this chapter has spent eight sections reconstructing from first principles rather than repeating as trivia.

Milestone: the team and user-base numbers that make the connection budget matter

By the Facebook acquisition announcement in February 2014, WhatsApp is widely and consistently reported to have had roughly 50 engineers serving upward of 450 million monthly active users — a ratio chapter 1 built its entire argument around. That user base crossed 900 million monthly active users by 2015 and passed 1 billion in early 2016. By a July 2017 company engineering post, WhatsApp described processing on the order of 100 billion messages a day — a volume that is only survivable with a connection layer whose per-connection cost was solved once, in this chapter's terms, rather than re-fought at every order of magnitude of growth.

Grounded reconstruction: a reconnect storm after a backbone failure

This specific incident is a first-principles reconstruction, not a confirmed WhatsApp postmortem — labeled as such. It is grounded in a real, published event: Meta's own October 2021 engineering postmortem of the outage that took Facebook, Instagram, and WhatsApp offline for roughly six hours described not just the initial BGP route withdrawal that caused the outage, but a second-order effect once routes were restored — "a surge of legitimate traffic" returning all at once, which itself briefly threatened to prolong recovery. Applied to this chapter's model: every one of the millions of phones that had been holding a connection to a now-unreachable connection-layer server is, from its own perspective, indistinguishable from a client whose keepalive just failed — and by §8g's design, every one of them is independently running exponential backoff with jitter rather than retrying immediately. That single design decision is the difference between "traffic gradually ramps back to normal over tens of seconds" and "the exact same failure mode that just ended recurs immediately against whatever server came back up first." §15's storm simulator lets you tune the jitter yourself and watch the difference.

Grounded reconstruction: undersized mbuf clusters

Also a first-principles reconstruction rather than a confirmed public incident report. WhatsApp's own 2011/2012 engineering accounts of reaching one and two million connections describe an iterative process of raising kernel limits well past FreeBSD's stock defaults — implying, by construction, that early attempts at scale ran into exactly the kind of wall §6 and §8d describe: a kernel limit (most plausibly the mbuf cluster pool, or the file-descriptor ceiling) refusing new connections or dropping packets while the box still reported free RAM, because the specific pool that ran out wasn't RAM as `top` reports it, but a bounded sub-allocation carved out of it at boot. §15's ramp simulator reproduces this exact failure mode and shows you the real error text for each limit, one at a time.

(a) The connection lifecycle as a state machine

This is the state machine described in prose throughout §1–§8, now as one artifact. Every transition is driven either by a network event (a packet arrived) or a timer (keepalive due, handshake timeout, backoff elapsed):

Erlang (gen_statem, illustrative)conn_session.erl — the full lifecycle
%% States: tcp_connected -> noise_handshake -> authenticating
%%       -> steady_state -> draining -> closed
%% (resume path: tcp_connected -> noise_handshake(resume) -> steady_state)

tcp_connected(info, {tcp, Sock, Bin}, Data) ->
    %% first bytes in: either a full Noise handshake init,
    %% or a Noise Pipes resume token
    case noise_handshake:classify(Bin) of
        full_handshake ->
            {next_state, noise_handshake, Data#{buf => Bin}};
        {resume, Token} ->
            {next_state, steady_state, Data#{session => Token},
             [{next_event, internal, resumed}]}
    end;

noise_handshake(info, {tcp, Sock, Bin}, Data) ->
    case noise_handshake:step(Data#{buf => Bin}) of
        {continue, Reply, Data2} ->
            gen_tcp:send(Sock, Reply),
            {keep_state, Data2};
        {done, Data2} ->
            {next_state, authenticating, Data2, [{state_timeout, 5000, auth_timeout}]}
    end;

authenticating(info, {tcp, Sock, Bin}, Data) ->
    case auth:verify(Bin, Data) of
        {ok, Session} ->
            {next_state, steady_state, Data#{session => Session},
             [{{timeout, keepalive}, keepalive_timer:initial(), fire}]};
        {error, _} ->
            {stop, {shutdown, auth_failed}}
    end;
authenticating(state_timeout, auth_timeout, _Data) ->
    {stop, {shutdown, auth_timeout}};                 %% one process dies; nobody else notices

steady_state(info, {tcp, Sock, Bin}, Data) ->
    %% FunXMPP frames decode here; each is routed to the
    %% messaging/presence layer this chapter treats as a black box
    Frames = funxmpp_codec:decode_all(Bin),
    [route(F) || F <- Frames],
    {keep_state, Data};
steady_state({timeout, keepalive}, fire, Data) ->
    gen_tcp:send(Data#session.sock, funxmpp_codec:ping()),
    Next = keepalive_timer:adapt(Data),          %% §8g — learn per-network interval
    {keep_state, Data, [{{timeout, keepalive}, Next, fire}]};
steady_state(info, {tcp_closed, _Sock}, Data) ->
    {stop, {shutdown, tcp_closed}}.                    %% mailbox drains, process exits, ~3 KB freed

(b) FunXMPP: decoding a frame without ever running an XML parser

Erlang (illustrative)funxmpp_codec.erl — binary pattern matching against the shared dictionary
decode(<<TagByte:8, Rest/binary>>) ->
    %% TagByte is a table lookup, not a parse: 1 = MESSAGE, 2 = IQ, ...
    Tag = tag_dict:lookup(TagByte),
    decode_attrs(Rest, Tag, #{});

decode_attrs(<<AttrByte:8, Len:16, Val:Len/binary, Rest/binary>>, Tag, Acc)
  when AttrByte =/= 0 ->
    Attr = attr_dict:lookup(AttrByte),               %% another table lookup
    decode_attrs(Rest, Tag, Acc#{Attr => Val});
decode_attrs(<<0:8, Rest/binary>>, Tag, Acc) ->
    {#{tag => Tag, attrs => Acc}, Rest}.               %% END marker; no closing-tag string to match

Every step is a fixed-width read and a dictionary lookup — no allocation-heavy tokenizer, no recursive-descent grammar, no closing-tag matching. At millions of frames per second across the fleet, replacing a general XML parser with table lookups is not a micro-optimization; it changes the CPU-per-message constant by roughly an order of magnitude, which is exactly where the ~10× wire-size reduction from §8e also lands.

(c) A Noise handshake pattern, in Noise notation

Noise Protocol Framework notationa 1-RTT pattern suited to a client that already knows the server's static key
// Simplified illustrative pattern (Noise "IK"-family shape):
// client already has the server's long-term static public key
// (fetched/pinned out of band), so it can encrypt its own
// identity in the very first message — no separate "who are
// you" round trip is needed.

<- s                              // (pre-message: client already has server's static key)
-> e, es, s, ss                   // msg 1: client → server (ONE flight)
<- e, ee, se                      // msg 2: server → client — handshake COMPLETE, channel live

// Noise Pipes resume path, for a client with a valid prior session:
-> resume_token                   // msg 1: client → server
<- ok                             // msg 2 (or piggybacked on the first real reply)

The exact production pattern and message names were never published in this level of detail by WhatsApp; the notation above illustrates the class of pattern (an IK-shaped, pre-shared-static-key handshake) that the Noise Protocol Framework's own public specification documents as achieving mutual authentication and forward secrecy in one flight each way — which is the structural property that matters for this chapter's round-trip arithmetic in §10c, independent of the precise token names used in production.

(d) Client-side: adaptive keepalive and jittered backoff

TypeScript (illustrative client logic)reconnect.ts — the client half of §8g
function nextBackoff(attempt: number, base = 500, cap = 60_000): number {
  const raw = Math.min(cap, base * Math.pow(2, attempt));
  const jitter = raw * (Math.random() * 0.5);      // full jitter, roughly
  return raw * 0.5 + jitter;                    // §15 lets you feel WHY this matters
}

function adaptKeepalive(state: ConnState): number {
  // Shrink toward the last interval that survived without an
  // unexpected TCP RST/timeout on THIS network; grow cautiously
  // otherwise. Never below a battery-safe floor (§8g/§10d).
  if (state.lastKeepaliveSurvived) {
    return Math.min(state.interval * 1.2, state.observedNatTimeoutEstimate * 0.8);
  }
  return Math.max(15_000, state.interval * 0.6);   // back off toward safety fast
}
WHY THE ENGINEERS CHOSE THIS SHAPE — THREE DECISIONS TO STEAL

1. One state machine per connection, not one event loop shared by all connections. A gen_statem per socket means a hung or malicious client can only ever corrupt its own ~3 KB of state and dies alone — the same isolation argument chapter 1 made about the process model generally, applied one layer down. 2. Binary framing chosen for CPU, not just bytes. FunXMPP's win isn't only the ~10× wire reduction — it's deleting an XML parser from the hot path entirely, at a frame rate where "a few hundred nanoseconds per tag" is a real, multiplying cost. 3. Handshake round trips are treated as a latency budget, not a security afterthought. Choosing a Noise pattern by round-trip count, and adding a dedicated resume path (Noise Pipes), is a direct acknowledgment that the slowest, most contended part of the entire system is the cellular link between the server and the phone — every other optimization in this chapter is in service of not wasting a single one of those expensive round trips.
