APACHE KAFKA INTERNALS · CHAPTER 10

Storage Performance: Page Cache,
Zero-Copy & Sequential I/O

A Kafka broker is a JVM process, yet it routinely saturates a 10 GbE NIC serving data straight from disk — while keeping a heap smaller than your laptop's. This chapter derives why: no application-level message cache, an append-only log that turns random access into a streaming problem, and a system call that lets the kernel hand bytes from disk to network without ever copying them through user space. Every one of these decisions is inseparable from the wire format you met in chapter 3.

ARC 01 · THE PROBLEM

Disk is slow, the JVM is not free, and the NIC doesn't care about either

Kafka's job is to move bytes from producers, onto disk, and back out to consumers — often the same bytes, read many times by many different consumer groups, sometimes seconds after they were written and sometimes days later. The naive framing treats this as a database problem: build a cache, serve hot reads from memory, fall back to disk on a miss. But Kafka runs inside a JVM, on commodity disks, serving potentially many gigabytes per second across thousands of partitions — and every one of those three facts fights the naive framing.

  • The JVM already has a garbage collector to worry about. Any data structure you deliberately keep resident — a hand-built LRU cache of recent records — is heap the collector must scan, and chapter 5 already showed that long GC pauses cause ISR flapping. Growing the heap to cache gigabytes of message data directly trades cache-hit rate for GC risk.
  • Disks are not equally fast at everything. A magnetic disk seek costs single-digit milliseconds; the same disk, asked to write sequentially, can sustain ~100 MB/s or more. The same hardware is 100× worse at random small writes than at sequential ones (quantified in §4). Any design that treats storage as a uniform "slow" resource misses the one lever that matters most.
  • Copying bytes costs real CPU and real memory bandwidth — and a broker that must serve many consumers of the same partition (fan-out is normal in Kafka: one write, many independent reads) pays that copy cost once per read unless something clever is done.

The question this chapter answers is not "how do we make a fast cache" but a more radical one: what if the broker deliberately builds no cache at all, and instead arranges every other piece — the log format, the write pattern, the network path — so that the operating system's existing, already-tuned machinery does the job for free? That is Kafka's actual answer, and it is why chapter 3's on-disk record batch format and this chapter's network path are the same design decision viewed from two angles.

THE CONCRETE TARGET

LinkedIn's original Kafka papers targeted commodity hardware serving hundreds of megabytes per second per broker with millisecond-scale latency, using disks that individually could not randomly seek anywhere near that fast. The gap between "what one disk can do randomly" and "what the fleet needs to sustain" is not closed by more RAM for a cache — it's closed by never generating random I/O in the first place.

ARC 02 · HISTORICAL CONTEXT

Zero-copy is older than Kafka; Kafka just needed it more

None of this chapter's mechanisms were invented for Kafka. sendfile() predates Kafka by over a decade; the OS page cache is as old as virtual memory itself. What Kafka's designers did was refuse to duplicate either — a discipline most application databases don't have the luxury of, because they typically need to transform, index, or randomly update data the OS can't reason about. DEEP CONTEXT · WHY THIS WAS A DESIGN CHOICE, NOT A DISCOVERY

Jay Kreps' 2013 essay "The Log" (and the original Kafka paper, Kreps/Narkhede/Rao, NetDB 2011) are explicit that the append-only log and the decision to lean on the kernel were chosen together, for the same reason: a message queue that behaves like a database (random access, in-place updates, application-level caching) forces you to fight the OS. A message queue that behaves like a file being streamed lets you stop fighting it. This chapter is that argument made mechanical.

ARC 03 · NAIVE SOLUTION

Attempt #1: an application-level message cache

The instinctive design, borrowed from database engineering: keep recently-produced and recently-requested messages in a JVM-managed cache (a ConcurrentHashMap of segment/offset to byte buffer, with an LRU or LFU eviction policy), and serve reads from there before ever touching disk.

JavaNaiveMessageCache.java — the strawman, annotated
class NaiveMessageCache {
    // keyed by (partition, baseOffset) → decoded batch, evicted LRU
    private final Map<SegmentKey, RecordBatch> cache = new LinkedHashMap<>(16, 0.75f, true);
    private final long maxBytes = 4L * 1024 * 1024 * 1024;  // 4 GB heap budget

    RecordBatch fetch(SegmentKey key) {
        RecordBatch hit = cache.get(key);
        if (hit != null) return hit;              // cache hit: no disk touched
        RecordBatch loaded = readFromDisk(key);       // cache miss: pread(), then DECODE into objects
        cache.put(key, loaded);
        evictIfOverBudget();
        return loaded;
    }
}

This looks reasonable, and it is exactly what a naive port of "how a database buffer pool works" produces. It already has two decisions baked in that will turn out to be expensive: it decodes bytes into Java objects to make them cacheable/usable, and it duplicates whatever the OS is already caching, since the same disk blocks are sitting in the kernel's page cache the moment they're read. ARC 04 · WHY IT FAILS

Quantifying the damage: duplication, decode cost, and cold restarts

  • Memory is spent twice. Every byte held in the JVM cache is also sitting in the OS page cache (the broker still had to read it via a syscall that populates the page cache on the way past) — unless you go out of your way to bypass the page cache with O_DIRECT, which brings its own alignment and complexity costs. A 4 GB application cache on a machine also running with the OS caching the same hot data can mean roughly 8 GB spent to hold 4 GB of useful bytes.
  • Java object overhead compounds it. A decoded record represented as Java objects (header fields, boxed offsets, byte array copies) commonly runs ~2× the size of the same data in its raw serialized form — object headers, alignment padding, and pointer overhead on every field add up fast at scale.
  • The cache is cold after every restart. A rolling deploy or crash-restart empties the JVM heap cache entirely; the broker returns to full disk-read latency for every partition until the cache re-warms — precisely the "backend cold-cache" problem from the PostgreSQL course's chapter 6, reappearing here for the identical structural reason: private, process-owned state does not survive the process.
  • GC pressure scales with cache size. A multi-gigabyte heap with a high object-allocation rate (every cache miss decodes fresh objects) is exactly the regime that produces long GC pauses — and chapter 5 already established that a long enough pause causes a broker to miss ZooKeeper/KRaft session heartbeats and drop out of the ISR. The cache built to make the broker faster can make it get kicked out of the cluster.
THE NUMBERS

Take a broker serving 200,000 fetch requests/sec of already-committed data with a naive 8 GB heap cache at 2× object overhead: you're paying for roughly 16 GB of heap-adjacent memory to represent 4 GB of logical cached data, on top of whatever the OS is independently caching for the same files. A machine with 64 GB of RAM now has a meaningfully smaller share of memory actually available to cache the working set, not more — and every one of those cached objects is scanned on every GC cycle.

The naive cache doesn't just cost memory — it fights a cache the kernel is already maintaining, for free, correctly, and warm across restarts of everything except the kernel itself. §5 asks the obvious next question: what if we just... use that one?

Four ways to touch the disk, one that wins

Candidate I/O strategies, eliminated in orderSTEP-BY-STEP

The winning design rests on a claim that must be justified, not assumed: the broker never needs to inspect or transform the bytes it serves. That claim is only true because chapter 3's on-disk record batch format is the wire format — a fetch response is, byte for byte, a slice of the log file. If the broker had to decompress, re-encode, or filter records on the way out, none of what follows would work, and §6 makes the two cases where that assumption breaks (TLS, old message formats) very concrete.

ARC 06 · WHY THAT STILL COSTS

The two ways "never touch the bytes" breaks

Relying entirely on the OS is not a free lunch either — it has sharp edges worth knowing before you hit them in production:

  • Encryption forces a copy. If the broker terminates TLS, the kernel cannot encrypt page-cache pages in place before handing them to the NIC — the bytes must pass through user space to be encrypted, which is precisely the copy zero-copy was built to avoid. §8 quantifies exactly how much this costs and what kernel TLS (kTLS) does to partially claw it back.
  • Format conversion forces a copy. A consumer built against an old message format (pre-0.11 v0/v1) talking to a broker storing v2 batches forces the broker to decompress, convert, and recompress on the fly — a documented, sometimes severe performance cliff that operators hit unexpectedly when a long-tail old client connects to a modern cluster.
  • The page cache is a shared, best-effort resource. It is not partitioned per topic or per consumer group; a bursty batch job scanning cold, old segments can evict the hot working set that real-time consumers depend on, and a badly lagging consumer can force reads from disk that would otherwise have been free (the "one lagging consumer poisons the cache" effect explored live in §15).
  • Sizing still matters. None of this works if the machine doesn't have enough free RAM for the OS to cache the working set in the first place — leaning on the page cache is a strategy, not a substitute for adequate hardware.
THE HONEST TRADE

Kafka's design bet is that the common case — plaintext or kernel-accelerated TLS, modern clients, enough RAM for the working set — dominates in practice, and it's worth losing zero-copy in the uncommon cases (old clients, user-space TLS without kTLS) rather than building a broker-side cache that pays a tax on every request to subsidize a minority of requests that need transformation anyway.

ARC 08 · INTERNAL IMPLEMENTATION

The mechanism, precisely: page cache sizing, sequential I/O, and sendfile()

(a) Sizing: give the machine to the page cache, not the heap

Because the broker keeps no application-level message cache, the right way to give it more caching capacity is not a bigger JVM heap — it's more free RAM for the kernel to use. Production Kafka brokers commonly run a JVM heap around 6 GB even on a 64 GB box, leaving the remaining tens of gigabytes entirely to the OS page cache. A larger heap here buys nothing for message-serving performance and actively costs you: more GC scanning work, longer pause tails, and — per chapter 5 — a real risk of ISR flapping under GC-induced stalls. This is a case where "use less of your own memory" is the performance-tuning advice, which surprises engineers arriving from database backgrounds where a bigger buffer pool is almost always better.

(b) Sequential vs random: the numbers that justify the append-only log

A spinning disk's random-access performance is dominated by seek + rotational latency — commonly several milliseconds per random 4 KB access, which caps random small-write throughput around ~1 MB/s on commodity spinning media. The same disk, asked to write or read sequentially, needs no repositioning between operations and can sustain on the order of ~100 MB/s or more — a two-orders- of-magnitude difference on identical hardware, purely from access pattern. NVMe narrows this gap dramatically (no mechanical seek at all), but queue depth and write amplification still meaningfully favor sequential access patterns even there. An append-only log where every write is "add to the end of the current segment" and every read within a partition walks forward through offsets converts Kafka's entire I/O workload into the sequential case — this is arguably the single deepest reason Kafka is fast: not a clever cache, not a clever data structure, but refusing to generate the access pattern that is expensive.

(c) The zero-copy path: sendfile() and why it only works here

Compare the two paths a fetch response can take. A naive read() into a user buffer followed by write() to a socket costs four copies and four context switches: disk → page cache (DMA, no CPU copy), page cache → user-space buffer (CPU copy, context switch into the kernel and back), user buffer → socket buffer (CPU copy, another context switch), socket buffer → NIC (DMA). sendfile() — exposed to the JVM as FileChannel.transferTo() — collapses this to two DMA copies and two context switches: disk → page cache (DMA), then page cache → NIC directly, with only a descriptor (pointer + length) crossing into kernel space, never the payload itself.

This only works because the broker never needs to look at the bytes — no per-record processing, no filtering, no transformation happens on the hot path. That is only true because the on-wire fetch-response format and the on-disk log-segment format are identical (chapter 3): a fetch response is a byte-for-byte slice of a log segment file, so shipping "the file" and shipping "the response" are the same operation.

THE TWO THINGS THAT BREAK IT

TLS: if the broker terminates encryption, the kernel cannot encrypt the page-cache pages in place before handing them to the NIC — the plaintext bytes must be copied into user space to be encrypted (or the encrypted result copied back), reintroducing the user-space copy zero-copy removed. Kernel TLS (kTLS) partially claws this back by moving the encryption step itself into the kernel so sendfile()-style transfers can still avoid a user-space round-trip, at the cost of kernel/NIC support and configuration complexity most Kafka deployments have not adopted by default. Old message formats: a consumer requiring v0/v1 record format against a broker storing v2 batches forces decompression, conversion, and recompression — a real, measured performance cliff, not a theoretical one, and a documented reason to finish client upgrades.

(d) Flush policy: durability comes from replication, not fsync

log.flush.interval.messages and log.flush.interval.ms exist but are, deliberately, normally left unset (effectively relying on the OS's own write-back schedule) in production clusters — Kafka's durability story is built on replication (chapter 5's ISR and acks=all/min.insync.replicas), not on forcing every write to disk before acknowledging it. Forcing an fsync per message or per small batch would reintroduce exactly the random-ish, latency-dominated I/O pattern §4 spent its whole argument avoiding, in exchange for a durability guarantee replication already provides more cheaply (surviving N-1 broker failures is a stronger guarantee than one broker's disk being synced, and is what most deployments actually rely on). This is a deliberate, debatable trade — a single-broker, single-disk deployment with the OS write-back window open really can lose unflushed data on a full power loss, which is exactly why acks=all across multiple brokers, not local fsync, is the recommended durability lever.

Other tuning knobs that follow directly from this model: vm.dirty_ratio and vm.dirty_background_ratio control how much dirty (unwritten) page-cache data the kernel tolerates before it starts throttling writers or forcing write-back — tuned too loose, a burst of writes can force a large synchronous write-back stall; vm.swappiness should be low so the kernel doesn't swap out page-cache- resident hot data under memory pressure; and filesystem choice (XFS is the most common recommendation over ext4 for Kafka's workload of large sequential appends and infrequent metadata operations) affects allocation and metadata overhead at the margins.

WHY MANY PARTITIONS ON ONE DISK UNDOES EVERYTHING ABOVE

Each partition is its own append-only segment file, sequential on its own. But when many active partitions on the same physical disk are all being appended to concurrently, the disk head (or the SSD's internal scheduling) is interleaving writes across files — from the disk's point of view, that interleaving looks like random access even though every individual partition is logically sequential. This is precisely why Kafka's partition-count guidance is not "just add more partitions freely" and why co-locating too many active partitions per disk is a well-known way to silently undo §8(b)'s entire argument.

The recurring theme: every system in this table that tries to out-cache or out-schedule the kernel is making a bet that its application-specific knowledge beats generic OS heuristics for its specific access pattern. Kafka's bet is the opposite — that its access pattern (mostly sequential, mostly tail-read, high fan-out) is exactly what the kernel's page cache and read-ahead are already tuned for, so the highest-leverage move is getting out of the way.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

Big-O first: a fetch from the tail of a partition that's resident in the page cache is O(1) relative to partition size — the kernel serves it from RAM regardless of how large the underlying log is. A fetch for old, evicted data costs a real disk read, whose latency is dominated by the sequential-vs-random distinction from §8, not by the total log size (log segments are bounded by log.segment.bytes, so "how big is this partition" doesn't change how expensive one sequential read is). GC cost is essentially decoupled from message throughput specifically because the broker isn't allocating message-sized objects on the hot path — the allocation-heavy work is elsewhere (request objects, small buffers), which is exactly why the heap can stay small (§8a) without message throughput suffering.

ARC 11 · REAL-WORLD PRODUCTION

What actually happens at scale

Incident class 1: enabling TLS cuts throughput and nobody knew why

A team enables inter-broker and client-broker TLS for compliance and sees broker CPU utilization jump and achievable throughput per broker drop noticeably at the same load — the classic symptom of losing sendfile()'s zero-copy path, since every byte now has to be copied into user space to be encrypted. This is a widely discussed operational reality in the Kafka community (Confluent and LinkedIn engineering posts on the topic have quantified double-digit percentage throughput reductions in some configurations), and it is precisely why kernel TLS (kTLS) and careful benchmarking before a blanket "TLS everywhere" rollout are standard advice for latency- or throughput-sensitive clusters.

Incident class 2: too many partitions per disk turns sequential into random

Operators chasing parallelism sometimes provision far more partitions per broker (and per disk) than the workload needs, reasoning "more partitions, more parallelism, more throughput." Once enough partitions are concurrently active on one disk, their interleaved appends produce an access pattern indistinguishable from random I/O at the disk level, and throughput collapses toward the random-I/O numbers from §8(b) instead of the sequential ones — a failure mode extensively documented in Kafka partition-sizing guidance (LinkedIn and Confluent both publish per-broker partition-count recommendations explicitly grounded in this effect, alongside the separate concerns of controller/metadata overhead and replication fan-out per partition).

Incident class 3: the lagging consumer that poisons the cache

A single consumer group falls significantly behind (a slow downstream sink, a redeployment that pauses consumption for hours) and starts requesting old, cold segments that have long since been evicted from the page cache. Serving that consumer forces real disk reads competing for the same disk and cache space that near-real- time consumers depend on for cheap, cache-resident tail reads — a well-known operational pattern often described informally as the lagging consumer "poisoning the cache" for everyone else on that broker. The standard fixes are operational (alerting on consumer lag well before it reaches cold-segment territory, isolating batch/replay workloads onto separate clusters or at least separate disks) rather than a broker configuration knob, because the page cache is intentionally a shared, unpartitioned resource — §15's simulator lets you watch this happen.

Incident class 4: LinkedIn's own published throughput numbers

LinkedIn's original Kafka papers and later engineering blog posts describe production clusters sustaining hundreds of megabytes per second to low gigabytes per second per broker on commodity hardware, explicitly attributing this to the combination of sequential I/O and zero-copy — figures that would be very difficult to reach with a naive read/write path and an application-level cache competing with the kernel for the same memory.

JavaFileRecords.java — writeTo(), simplified
public long writeTo(TransferableChannel destChannel, long offset, int length) throws IOException {
    long newSize = Math.min(channel.size(), end);
    long position = start + offset;
    long count = Math.min(length, newSize) - position;
    // The load-bearing call: on a plaintext channel this resolves all the way down
    // to sendfile(2) — the kernel moves bytes disk→page-cache→socket without a
    // user-space buffer ever being allocated for the payload itself.
    return channel.transferTo(position, count, destChannel);
}
JavaTransportLayer — why SSL can't take this path, simplified
interface TransportLayer {
    long transferFrom(FileChannel fileChannel, long position, long count) throws IOException;
}

class PlaintextTransportLayer implements TransportLayer {
    public long transferFrom(FileChannel fileChannel, long position, long count) {
        // direct pass-through to the OS zero-copy primitive
        return fileChannel.transferTo(position, count, socketChannel);
    }
}

class SslTransportLayer implements TransportLayer {
    public long transferFrom(FileChannel fileChannel, long position, long count) {
        // MUST read into a user-space buffer: the bytes have to exist in
        // application memory to be fed through the TLS engine's encrypt() call.
        // This single method is where zero-copy dies for an encrypted connection.
        ByteBuffer buf = readInto(fileChannel, position, count);
        return sslEngine.wrapAndSend(buf, socketChannel);
    }
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. One interface, two implementations, one honest limitation. Rather than hiding the cost of TLS, the codebase makes the zero-copy-vs-not distinction an explicit type-level fork (TransportLayer implementations), so the tradeoff is visible in the code, not buried in a config flag with surprising runtime behavior. 2. FileRecords never decodes. writeTo() takes a byte range and a destination — it never parses a single record, which is what makes the "the broker never inspects the bytes" claim literally true in the implementation, not just conceptually. 3. The read path returns file-backed views, not copies. LogSegment.read() returns a FetchDataInfo that wraps a FileRecords slice — position and length into an already-open file descriptor — so nothing is copied until (and unless) writeTo() is eventually called on the actual response path.
