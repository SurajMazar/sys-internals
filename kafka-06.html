APACHE KAFKA INTERNALS · CHAPTER 06

The Controller:
From ZooKeeper to KRaft

Chapter 5 assumed a controller existed — some authority that could answer "who's the leader for partition 7" and make it official. This chapter builds that authority from nothing. It's a second consensus problem hiding behind the first one: brokers must agree on cluster metadata itself, with the same fencing, ordering, and failure-recovery guarantees partition replication needed — and for eight years Kafka solved it by borrowing another distributed system, ZooKeeper, before replacing it with a Raft implementation of its own.

ARC 01 · THE PROBLEM

Someone has to agree on the truth about the cluster

Every fact chapter 5 depended on — which broker leads partition 7, what its current ISR is, which topics exist, how many partitions each has, which brokers are alive — is cluster metadata. Unlike a single partition's data, this metadata has one crucial property: every broker in the cluster needs to agree on it, in the same order, without a single point of failure, and any broker that falls behind must be able to answer "how stale is my view?" honestly rather than silently serving wrong answers.

That is a full consensus problem, with the same five requirements from chapter 5's opening, restated one layer up:

  • A single agreed leader for the metadata itself — you cannot have two brokers both believing they're authorized to assign partition leaders; that's split-brain at the level that would corrupt everything downstream.
  • Durability — cluster metadata (topic configs, ACLs, partition assignments) must survive the failure of whichever machine is currently in charge of it.
  • Fencing against zombies — a controller that appears dead (GC pause, network blip) but is actually still running must never be able to act as if it's still in charge once a new one has taken over.
  • Fast, bounded recovery — every broker in the cluster is blocked on metadata being correct; a slow controller failover is a cluster-wide outage, not a localized one.
  • Bounded staleness, made observable — exactly chapter 5's high-watermark idea, one level up: a broker needs an honest, checkable answer to "how far behind is my metadata view?"

For its first eight years, Kafka answered all five by renting a consensus system that already existed — ZooKeeper — rather than building one. This chapter derives why that was the right call in 2013, precisely what it cost by 2019, and how KRaft (KIP-500) eventually replaced it by turning cluster metadata into exactly the kind of thing chapter 5 already knows how to replicate: a Kafka log.

WHY THIS MATTERS

Notice the shape: this chapter is chapter 5, one level up. A "leader" now means "active controller." An "ISR" now means "a Raft quorum's committed log." A "leader epoch" now means a Raft "term." If chapter 5's mental model is solid, this chapter mostly reuses it — the hard part is seeing which pieces generalize and which genuinely don't (a hint: majority quorums, deferred in chapter 5 because of per-partition cardinality, become entirely affordable here because there's only one metadata log for the whole cluster).

DEEP CONTEXT · WHY ZOOKEEPER WAS THE OBVIOUS CHOICE IN 2011

Kafka was born inside LinkedIn's infrastructure, and LinkedIn — like most of the 2011 Hadoop-ecosystem world — already ran ZooKeeper for other systems (HBase, Hadoop's own NameNode HA). ZooKeeper offered exactly the primitives a controller needs off the shelf: ephemeral znodes (a node that disappears automatically when its owning process dies — a free failure detector), watches (push notifications on znode changes), and sequential znodes (useful for elections and leases). Building a bespoke Raft implementation in 2011, when the Raft paper itself wasn't published until 2014, was not a realistic alternative — reusing a battle-tested, already-deployed consensus system was the obviously correct engineering call, not a shortcut taken lightly.

ARC 03 · NAIVE SOLUTION

Attempt #1: whoever notices first, wins — no fencing

Before reaching for any external system, derive the naive design honestly: every broker watches for the absence of a controller and races to claim the role, with no notion of terms, epochs, or leases.

pseudo-Scalanaive_controller.scala — the strawman, annotated
class NaiveController(brokerId: Int, peers: List[Broker]) {

  def tryBecomeController(): Boolean = {
    // "Lowest broker ID wins" — no term, no epoch, no lease, no fencing token.
    val aliveIds = peers.filter(_.isReachable).map(_.id) :+ brokerId
    if (brokerId == aliveIds.min) {
      isController = true                 // just... declare it
      startAssigningPartitionLeaders()
    }
    isController
  }

  // Runs periodically. No coordination with anyone else's clock,
  // no shared notion of "how long since I last confirmed I'm still it".
  def heartbeatLoop(): Unit = while (true) {
    if (!isController) tryBecomeController()
    sleep(1000)
  }
}

This gets the easy 90% right: most of the time, exactly one broker believes it's the controller, and it works. The failure mode it doesn't handle is exactly the one that matters — what happens when a broker believes it's still the controller, and is wrong.

ARC 04 · WHY IT FAILS

The zombie controller, quantified

The naive design's fatal flaw is not the election logic — "lowest ID wins" is a perfectly fine tie-breaker. The flaw is that nothing fences a controller that has been deposed but doesn't know it yet.

  • The GC-pause scenario: controller broker C1 hits a 20-second stop-the-world GC pause. Every peer concludes C1 is dead (it's unreachable) and broker C2 becomes the new controller, reassigning several partition leaders. C1's GC pause ends; C1 has no idea any of this happened. It resumes its heartbeat loop, sees itself still marked as controller in its own local state, and keeps issuing LeaderAndIsr updates based on stale cluster state — updates that can directly conflict with what C2 just decided.
  • Two controllers, two truths: for the window until brokers notice C1's messages are stale (and with no fencing token, how would they even know?), some brokers may apply C1's instructions and others C2's — genuine split-brain in the metadata layer, which is far more damaging than split-brain in a single partition, because every partition's leadership can be affected at once.
  • No bound on detection time: "lowest ID wins" re-evaluated every second gives you no guarantee about how long two controllers can coexist, especially under a slow, partial network partition rather than a clean crash.
THE NUMBERS

Model it as a race: a network partition or GC pause of duration T creates a window of exactly length T during which two brokers can simultaneously believe they are the controller, with zero mechanism to shorten that window or detect it from the outside. Every additional millisecond of T is additional time for the two controllers to issue conflicting instructions to the same set of brokers — and conflicting instructions about partition leadership are exactly the kind of bug that shows up as data divergence, not a clean crash. You cannot fix this by making the heartbeat faster; you can only fix it by making "who's really in charge" a fenced, monotonically-ordered fact instead of a locally-held belief.

The fix needs a fencing token — precisely the leader-epoch idea from chapter 5, applied to controllers instead of partition leaders. Section 5 walks the real candidates for building that token cluster-wide.

ARC 05 · BETTER SOLUTIONS, EXAMINED

External lock service vs. gossip vs. embedded Raft

Step through the three real candidates, in the order the ecosystem actually tried them.

Three ways to fence "who's really in charge"STEP-BY-STEP
WHAT ZOOKEEPER ACTUALLY BOUGHT KAFKA IN 2013

Ephemeral znodes gave Kafka a free, correct failure detector (a session that expires means the process is gone, full stop — no ambiguity). A monotonic controller epoch, stored in ZooKeeper and incremented on every election, gave brokers a fencing token: any LeaderAndIsr or metadata update carries the controller epoch that issued it, and brokers reject anything tagged with a lower epoch than the highest they've seen. This closes the exact zombie-controller hole from §4 — C1 resuming after its GC pause finds its epoch is now stale and its instructions get ignored. ZooKeeper's Zab protocol (its own internal consensus algorithm, itself a close relative of Multi-Paxos) is what makes the epoch counter and the znode tree durable and linearizable in the first place.

ARC 06 · WHY THAT STILL COSTS

The ZooKeeper era's real, well-documented pathologies

The controller-epoch fence solves §4's zombie problem. It does not solve a second-order set of costs that accumulated over years of running Kafka-on-ZooKeeper at real scale, and which collectively motivated KIP-500:

  • Controller failover reloads everything, from scratch, every time. When a new controller takes over, it has no cached state — it must read the entire metadata tree from ZooKeeper: every topic, every partition's assignment, every partition's ISR. That's O(partitions) ZooKeeper reads before the new controller can do anything, and on clusters with hundreds of thousands of partitions this measured in minutes, not seconds — an outage window sized by your partition count, not by how fast your hardware is.
  • Metadata propagation is push-based and asynchronous. The controller doesn't just decide new state — it must separately push UpdateMetadataRequest/LeaderAndIsr RPCs to every broker. Between "the controller decided X" and "every broker has heard about X," brokers can legitimately hold divergent views of the cluster, for an unbounded (if usually short) window — there's no offset, no "as-of" marker, just "did the RPC arrive yet."
  • ZooKeeper watch herd effects. Many brokers watching the same znode for changes all get notified simultaneously and all re-read the changed state at once — a thundering herd against ZooKeeper itself, worse exactly when the cluster is already stressed (e.g., during a large reassignment).
  • A second distributed system, with its own failure modes, to operate. ZooKeeper needs its own JVM tuning, its own quorum (typically 3 or 5 nodes), its own disk latency sensitivity, its own upgrade path, and its own on-call runbook — entirely separate from Kafka's. Every Kafka outage retro that starts with "the brokers looked fine, but ZooKeeper session timeouts spiked" is this cost made concrete.
  • A practical partition-count ceiling. Combining the first two costs, clusters were commonly reported (in KIP-500 discussions and Kafka Summit talks) to become operationally painful somewhere in the low hundreds of thousands of partitions cluster-wide — not because brokers couldn't handle the data, but because controller failover and metadata propagation degraded badly at that scale.

Every one of these costs has the same root cause: metadata is a separate system from the thing it describes. Section 7 shows what happens when you stop treating it that way.

ARC 07 · FINAL ARCHITECTURE

KRaft: metadata becomes a Kafka topic

KIP-500's central idea, stated plainly: stop storing cluster metadata in a separate system with separate consistency semantics, and instead store it as a Kafka topic — __cluster_metadata, a single-partition log, replicated by a dedicated Raft quorum of controller nodes using Kafka's own replication primitives. This is the single biggest qualitative change KRaft makes, and it's easy to undersell: because metadata is now a log with offsets, every broker has a well-defined metadata offset — exactly how far into __cluster_metadata it has replayed. "How stale is broker 7's view of the cluster" changes from an unanswerable question (in the ZK era, propagation was push-based RPCs with no sequence number) to a subtraction of two integers. This is the exact upgrade chapter 5 gave you for partition data (an offset-bounded notion of "committed") — chapter 6 gives the same upgrade to the metadata layer itself.

ARC 08 · INTERNAL IMPLEMENTATION

Raft, properly, and exactly how KafkaRaftClient differs

Two things need to happen here: (a) Raft itself, explained rigorously enough that "term," "log matching property," and "commit by majority" stop being buzzwords; (b) the specific ways KafkaRaftClient departs from the textbook algorithm, and why each departure is a deliberate, motivated engineering choice rather than a shortcut.

(a) Raft, for engineers who half-know it

Raft solves exactly the problem §4 identified: a cluster of nodes must agree on a single leader and a single, totally-ordered log, and must do so safely even when nodes crash or the network misbehaves, without ever letting two nodes believe they're leader for the same term at the same time.

  • Terms are Raft's name for exactly the fencing token chapter 5 called a leader epoch: a monotonically increasing integer, incremented every time an election happens. Every RPC carries the sender's term; any node that sees a higher term than its own immediately steps down and adopts it. This is the whole fencing mechanism — no locks, no leases, just "bigger number wins, always."
  • Leader election with randomized timeouts: every node starts as a follower and expects periodic heartbeats from a leader. If a follower hears nothing for a randomized timeout (this randomization is not decorative — it's what makes split votes rare: if every node timed out at exactly the same instant, they'd all become candidates simultaneously and repeatedly tie), it becomes a candidate, increments its term, votes for itself, and sends RequestVote RPCs to every peer.
  • The up-to-date check: a node grants its vote only if the candidate's log is at least as up-to-date as its own (comparing last log term, then last log index) — this is what prevents a node with a shorter or staler log from ever becoming leader and overwriting genuinely committed entries.
  • Winning: a candidate that receives votes from a majority of the cluster (including itself) becomes leader for that term and starts sending heartbeats (empty AppendEntries RPCs), which double as the mechanism that suppresses everyone else's election timers.
  • The log matching property: Raft's core safety invariant — if two logs contain an entry with the same index and term, every preceding entry in both logs is guaranteed identical. Leaders enforce this by having followers reject an AppendEntries unless its immediately preceding entry matches; a mismatch forces the leader to walk backward and resend from an earlier point, exactly the kind of prefix-matching chapter 5's leader-epoch mechanism achieves for partition data.
  • Commit by majority: a log entry is considered committed once it's replicated to a majority of the cluster — not all of it. This is the fixed-size-majority-quorum design chapter 5 deliberately deferred for individual partitions (too many of them), but which is entirely affordable here, because there's exactly one metadata log for the whole cluster.

(b) How KafkaRaftClient departs from textbook Raft

The single biggest departure, and it should feel familiar: KRaft is pull-based. In the Raft paper, the leader actively pushes AppendEntries RPCs to followers. In KafkaRaftClient, voters instead fetch the log from the leader, using — deliberately — the same Fetch API and replication machinery Kafka already uses for ordinary partition replication. This is precisely chapter 5's "followers pull" argument, one layer up, and for the same reasons: one code path serves both ordinary partition replication and metadata replication (fewer distinct RPC types to build, test, and operate), and backpressure is free — a lagging voter simply issues its next fetch later, rather than the leader needing per-voter send-buffer management. The design further reuses the broker's existing SocketServer networking stack and request-handling threads instead of standing up a second, parallel network path just for consensus traffic.

Other deliberate departures worth naming: KRaft's leader still needs to know when it's safe to actually start serving reads/writes as the new active controller (a Raft leader in the paper can start immediately once elected, but a freshly-elected KRaft leader must first replay enough of the log to be sure it isn't missing recent committed metadata — handled via a dedicated "leader ready" check after election, not before). And KRaft integrates snapshots as a first-class part of the protocol rather than a bolt-on optimization, because a metadata log that includes every topic/partition change since cluster genesis would otherwise grow forever.

Metadata snapshots: why a log alone isn't enough

A brand-new controller node (or a broker that's been offline for a long time) cannot be expected to replay every metadata change since the cluster's creation — that's the exact O(history) problem chapter 5's log compaction (a different course topic) solves for ordinary topics, applied here to the metadata log itself. KRaft periodically writes a snapshot: a complete, point-in-time image of cluster metadata as of some log offset, after which the log up to that offset can be trimmed. A new controller or a badly-behind broker loads the latest snapshot, then replays only the (much shorter) tail of the log since that snapshot's offset — turning "reload everything since genesis" (§6's ZK-era cost) into "load one snapshot plus a short tail," which is the direct mechanism behind the millisecond-scale failover numbers in §10.

ARC 10 · PERFORMANCE CHARACTERISTICS

Milliseconds instead of minutes, quantified

  • ZK-era controller failover: dominated by O(partitions) ZooKeeper reads to rebuild in-memory controller state from scratch. Publicly discussed KIP-500 motivating figures put large, real clusters at failovers measured in minutes once partition counts reach the hundreds of thousands.
  • KRaft controller failover: the new active controller already has the replicated log (or a recent snapshot plus a short tail) locally, because it was a voter the whole time — there is no separate "go fetch everything from a store" step. Publicly discussed KRaft benchmarks describe failover in the hundreds-of-milliseconds to low-seconds range, essentially bounded by Raft's election-timeout randomization window, not by cluster size.
  • Partition-count ceiling: KIP-500 and subsequent KRaft benchmark talks describe clusters supporting an order of magnitude (or more) beyond the practical ZK-era ceiling — figures in the range of millions of partitions have been publicly discussed at Kafka Summit as achievable with KRaft, versus the low hundreds of thousands that were operationally painful under ZooKeeper.
  • Snapshot loading is O(metadata size at a point in time), not O(history). This is precisely why a broker that's been offline for a week can rejoin without replaying a week of individual metadata deltas — it loads one snapshot and a short tail.

ARC 11 · REAL-WORLD PRODUCTION

The migration, at scale

The KIP-500 rollout timeline, in production

KRaft was marked production-ready starting with Kafka 3.3 (2022), after roughly three years of development and staged rollout beginning with KIP-500's 2019/2020 proposal. Confluent and the wider Kafka community published migration guides and case studies describing a dual-write bridge mode for existing clusters: a cluster keeps running its ZooKeeper-based controller while a parallel KRaft controller quorum is stood up and begins receiving the same metadata, letting operators validate the new path before cutting brokers over — precisely the kind of staged migration a decade-old, massively deployed piece of infrastructure needs, rather than a flag-day rewrite.

Reported failover-time improvements

Public Kafka Summit talks and Confluent engineering blog posts on KRaft describe controller failover times dropping from the ZK-era's minutes-at-scale down to sub-second ranges in KRaft deployments, alongside substantially higher supported partition counts — the exact two numbers this chapter's §10 models. These are the headline metrics the KIP-500 authors set out to fix, and the ones most consistently cited across the ecosystem's public writeups of the migration.

Kafka 4.0: ZooKeeper support removed

Kafka 4.0 (2024) completed the arc this chapter's timeline traces: ZooKeeper mode was removed entirely, and KRaft became the only supported metadata implementation. The multi-year overlap between "KRaft is available" and "ZooKeeper is finally gone" is itself a case study in how carefully a foundational architectural dependency has to be replaced under a live, massively deployed distributed system — the same caution the PostgreSQL course's chapter on the multi-threading effort discusses for a differently-shaped but equally foundational change.

Operational lesson from the transition period

During the years both modes were supported, community discussion repeatedly surfaced one operational reality worth internalizing: running the ZK-to-KRaft migration bridge correctly requires understanding both systems' failure modes simultaneously, not just the destination state — exactly the kind of "two systems in flight at once" complexity that motivated eliminating the external dependency in the first place.

First, the core of a Raft vote decision — simplified from KafkaRaftClient but faithful to its structure:

JavaKafkaRaftClient.java — handleVoteRequest(), the up-to-date check
VoteResponse handleVoteRequest(VoteRequest request) {
    if (request.candidateEpoch() < quorumState.epoch()) {
        // Stale candidate — a lower term can never win a vote. This is
        // the ENTIRE fencing mechanism: bigger term always wins, no locks.
        return voteResponse(false, quorumState.epoch());
    }
    if (request.candidateEpoch() > quorumState.epoch()) {
        quorumState.transitionToUnattached(request.candidateEpoch());   // step down, adopt the higher term
    }

    boolean logIsUpToDate =
        request.lastOffsetEpoch() > log.lastFetchedEpoch() ||
        (request.lastOffsetEpoch() == log.lastFetchedEpoch() &&
         request.lastOffset() >= log.endOffset());

    boolean notYetVoted = quorumState.votedForId().isEmpty();

    if (logIsUpToDate && notYetVoted) {
        quorumState.grantVoteTo(request.candidateId());
        return voteResponse(true, quorumState.epoch());
    }
    return voteResponse(false, quorumState.epoch());
}

Next, the detail that makes this chapter's central architectural claim concrete — replication is fetch-driven, not push-driven:

JavaKafkaRaftClient.java — handleFetchRequest(), voters PULL the log
FetchResponse handleFetchRequest(FetchRequest request) {
    // A VOTER sends this — same request TYPE brokers use for ordinary
    // partition replication and consumers use to read data (ch.5, §5).
    // One fetch code path, reused a second time at the metadata layer.
    if (request.replicaEpoch() < quorumState.epoch()) {
        return fetchResponse(Errors.FENCED_LEADER_EPOCH);
    }
    if (!quorumState.isLeader()) {
        return fetchResponse(Errors.NOT_LEADER_OR_FOLLOWER);
    }

    var records = log.read(request.fetchOffset(), request.maxBytes());
    updateHighWatermark();  // same min-across-quorum idea as ch.5's HW — just "quorum" now means "majority", not "ISR"
    return fetchResponse(records, log.highWatermark());
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Reuse the fencing pattern, don't reinvent it. The vote handler's epoch check is structurally identical to chapter 5's leader-epoch check on record batches — "does this claim carry the highest number we've seen? if not, reject" is the one idea doing all the safety work in both places. 2. Reuse the transport, don't build a second one. Metadata replication rides the exact same Fetch request type, SocketServer, and request-handling threads as partition data — meaning KRaft shipped without Kafka needing to build, test, and operate an entirely separate RPC and networking stack just for consensus. 3. Reuse the commit definition. "Committed" still means "replicated to a quorum, then exposed via a high watermark" — chapter 5's vocabulary, with "ISR" swapped for "Raft majority," because the underlying question ("what may a reader safely observe?") never changed.
