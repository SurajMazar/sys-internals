RABBITMQ INTERNALS · CHAPTER 06

Quorum Queues:
Raft Inside the Broker

Chapter 1 named the moment RabbitMQ stopped trusting mirrored queues: a GitHub cluster partition in 2014 that let both sides of a split brain keep serving writes. This chapter is the fix. Classic mirrored queues replicated a queue's bytes without ever agreeing on who is allowed to write — quorum queues replace that with an actual Raft cluster, running RabbitMQ's own ra library underneath a state machine called rabbit_fifo. Every publish, every ack, every redelivery becomes a command appended to a replicated log and applied only once a majority has durably persisted it. That single sentence explains every property this chapter derives — the durability, the latency, the odd replica counts, and exactly which failures a quorum queue survives that a mirrored queue could not.

ARC 01 · THE PROBLEM

Why mirrored queues had to die

RabbitMQ's original answer to "what happens to a queue's messages if the node hosting it dies" was queue mirroring: an HA policy that replicated a classic queue's state to one or more mirror nodes, designating one copy the master and the rest slaves. It shipped early, it was simple to reason about in the common case, and it survived in production for the better part of a decade. It is also, in hindsight, an object lesson in why "replicate the data" and "reach consensus about who owns the data" are not the same problem — and why only the second one is actually safe.

Mirroring replicated a queue's operations to every mirror over Erlang's own inter-node messaging, using a broadcast primitive (gm, guaranteed multicast) that gives you a strong, useful property: every mirror in the group either sees an operation or the group's membership view changes to exclude whoever missed it. What it does not give you is anything resembling consensus. There is no term number. There is no concept of "a majority of the group agreed this write happened before any client saw it acknowledged." Each side of a network partition simply keeps its own view of who's in the group and carries on — which is exactly the shape of bug that stays dormant for years and then costs you a very bad day.

  • No consensus, so a partition could produce two masters. If the cluster splits and both halves still have a live queue process willing to call itself the master (the original master on one side, a promoted slave on the other), both sides keep accepting publishes. There is no majority check anywhere in the protocol to stop this, because the protocol was never designed to need one.
  • ha-sync-mode=automatic blocked the queue entirely. When a new or rejoining mirror needed to catch up, the master would synchronise the entire message backlog to it — and while that sync ran, the master queue process blocked all other operations. A multi-gigabyte backlog turned "a mirror rejoined" into "the queue stopped answering for minutes."
  • Promotion of an unsynchronised mirror silently lost messages. If the master died before a given mirror finished syncing, and that mirror was promoted anyway (a real, supported configuration — ha-promote-on-failure=always), whatever the old master had that the new one didn't simply never existed as far as any client could tell. No error, no dead-letter, no log line a consumer would ever see — the messages were just gone.
  • Failure modes were data-dependent and impossible to reason about in advance. Whether a given partition or crash lost messages, blocked the queue, or (in the lucky, common case) did neither depended on exactly which mirror was synced to what point when the fault happened — not something you could compute ahead of time from the topology alone.
THE VERSION HISTORY THAT MATTERS

Mirrored classic queues were deprecated in RabbitMQ 3.9 (2021) and removed entirely in 4.0 (2024). That is not a routine feature sunset — it is the RabbitMQ team concluding, in public, that the underlying algorithm could not be patched into safety. The replacement, quorum queues (introduced in 3.8, 2019), doesn't tweak the replication mechanism. It replaces it with a different algorithm class entirely: each quorum queue is a Raft cluster, its state machine is rabbit_fifo, and it runs on ra — RabbitMQ's own general-purpose Raft library, built specifically because no amount of engineering on top of unreplicated-consensus mirroring could close the split-brain gap. Everything from here to the end of this course assumes that lesson: replication without a majority quorum is not durability, it's a race condition with good uptime most of the time.

DEEP CONTEXT · WHY RAFT AND NOT PAXOS

Diego Ongaro and John Ousterhout titled their 2014 paper "In Search of an Understandable Consensus Algorithm" — understandability was the explicit design goal, not an accident. Multi-Paxos is provably equivalent in the guarantees it can offer, but its leader election is a separate concern bolted on to a voting protocol that is notoriously easy to implement subtly wrong; production-grade Paxos systems (Chubby, Spanner's underlying layer) are famous for the gap between "the paper" and "the system that actually works." Raft decomposes into three named, separately-understandable sub-problems — leader election, log replication, safety — specifically so that a team implementing it from scratch has a fighting chance of getting it right the first time. RabbitMQ's ra library is exactly that: an from-scratch Erlang implementation the team could build, test, and trust because the algorithm was designed to be buildable.

ARC 03 · NAIVE SOLUTION

The design mirrored queues actually shipped with

It's worth looking at the strawman honestly, because it isn't a strawman someone invented for this chapter — it is, in simplified form, the real logic classic mirrored queues ran for years. Promote "the oldest mirror," optionally block on a full resync, and hope no two nodes ever do this at the same time on opposite sides of a network fault.

pseudocodenaive_ha_promotion.erl — mirrored queues, annotated
handle_master_down(Mirrors, HaSyncMode) ->
    %% Pick "the oldest" mirror and promote it. No term number, no vote,
    %% no check that some OTHER node isn't doing the exact same thing
    %% right now on the other side of a partition.
    [Oldest | _Rest] = Mirrors,
    promote_to_master(Oldest),

    case HaSyncMode of
        automatic ->
            %% The ENTIRE backlog copies over before this queue answers
            %% anything else. A 4 GB backlog is a multi-minute outage.
            block_all_queue_ops(),
            sync_full_backlog_from(Oldest),
            unblock_queue();
        manual ->
            %% Oldest may simply be missing messages the dead master had.
            %% Nobody is notified. There is no error. They are just gone.
            unblock_queue()
    end.

This isn't incompetence — it's what "replicate the data" looks like when you don't also solve "agree on who's allowed to accept new data." ARC 04 · WHY IT FAILS

Quantifying the blast radius

Formalize what the deck just showed, because "it can lose messages" undersells how mechanically inevitable that was once you write the two decisions down as an algorithm.

  • Split-brain is not a rare edge case, it's the default outcome of a symmetric partition. If a 3-node mirrored group splits 2-vs-1 (or, worse, roughly 1.5-vs-1.5 during a flaky link where both sides intermittently see each other), each side independently runs the same promotion logic. There is no shared state that would let one side know the other is doing the same thing — by construction, because gm's guaranteed multicast is a per-group broadcast, not a majority vote.
  • The blocking window during ha-sync-mode=automatic scales with backlog size, not with anything the operator controls in the moment. A queue holding 2 GB of unconsumed messages at the moment a mirror needs to (re)sync will block for however long copying 2 GB over the cluster network takes — often minutes — during which every publisher and consumer of that queue is stalled, not just the syncing mirror.
  • Silent loss on promotion is proportional to replication lag, and replication lag is unbounded. If the promoted mirror was one heartbeat behind the dead master, you lose a handful of messages. If it had just joined and was mid-sync, you can lose the entire backlog the master held. The failure mode is data-dependent: identical topology, identical crash, wildly different blast radius depending on timing you don't control.
  • None of this shows up until the fault actually happens. A healthy mirrored queue under normal operation looks and behaves identically whether it's one dropped connection away from splitting brains or not — there's no metric that tells you "this cluster's mirroring design cannot survive the partition it's about to have."
THE GITHUB 2014 NUMBERS, REVISITED

Chapter 1 introduced GitHub's public 2014 postmortem of a RabbitMQ cluster partition as evidence Erlang's process model doesn't prevent operational incidents by itself. The mechanism behind that incident is exactly this section's math: nodes disagreed about membership during a network fault, and depending on cluster_partition_handling configuration (ignore, autoheal, pause_minority), mirrored queues on each side of the split could diverge before anyone could intervene. pause_minority is itself a workaround, not a fix — it makes the minority side stop serving entirely, trading availability to avoid divergence, because the mirroring protocol has no cheaper way to guarantee safety. A real consensus protocol gets you that same safety and keeps the majority side serving, for free, as a consequence of the algorithm rather than an operator's configuration choice.

So the fix has to be a different algorithm, not a tuned version of the same one. §5 walks the candidates that were actually on the table, and why Raft — specifically because of the paper's stated goal of being understandable enough to implement correctly — is the one RabbitMQ built on.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Replication that requires a majority to agree before anything is "done"

Candidate A: patch gm with a majority check bolted on afterward

The tempting minimal fix: keep the existing guaranteed-multicast broadcast, and just refuse to promote a mirror unless it can see "enough" of the group. The problem is that gm's per-side view updates happen independently and there is no shared, monotonically increasing term number anywhere in the design to let two independently-promoted masters recognize that the other is stale once the partition heals. Bolting a majority check onto a protocol that was never built to carry the metadata a majority check needs isn't a patch — by the time you've added terms, log indices, and a rule for resolving conflicting histories, you've built Raft with extra steps. Rejected: not actually smaller than doing it properly.

Candidate B: primary/backup with an external fencing coordinator

Systems like some SQL HA setups solve this by handing the "who's allowed to be primary" decision to an external coordinator (a ZooKeeper ensemble, a STONITH fencing device) that can forcibly kill a demoted primary before a new one takes writes. This works, but it reintroduces exactly the kind of mandatory external dependency RabbitMQ has always avoided — a cluster of RabbitMQ nodes is supposed to be self-contained, and "you also need to correctly operate a separate consensus system just to make queues safe" is a worse operational story than solving consensus inside the broker. Rejected: solves safety, reintroduces an external dependency.

Candidate C: (Multi-)Paxos

Paxos offers the same fundamental guarantee — a value is chosen only once a majority of acceptors agree — and has decades of production use (Chubby, Spanner's underlying log). But Paxos as originally specified doesn't include leader election as part of the core protocol; production systems layer it on separately, and the resulting systems are notorious for the gap between "the algorithm on paper" and "a correct from-scratch implementation," precisely because the paper is famously subtle to reason about. For a team building a Raft- class library from scratch inside Erlang, that implementation risk was judged too high. Rejected: same guarantee, materially higher risk of getting the implementation wrong.

Candidate D: Raft ✓

Raft gives you the identical safety property — an entry is committed only once a strict majority of the cluster has durably stored it — but decomposes the problem into three named pieces designed to be understood and implemented independently: leader election (exactly one leader per term, chosen by randomized-timeout elections so at most one candidate can win a given term), log replication (the leader is the only node that accepts new entries; it replicates them to followers in order), and safety (a committed entry can never be lost or overwritten, proven via the log's structure rather than asserted). RabbitMQ built ra — a general-purpose Raft library in Erlang — specifically to get this right, and quorum queues are rabbit_fifo, a state machine running on top of it.

THE SAFETY ARGUMENT, IN ONE PARAGRAPH

A log entry is committed once the leader has replicated it to a majority of the cluster and each of those replicas has durably persisted it (fsync'd) to its own log. Because any two majorities of the same cluster must overlap by at least one member (that's just arithmetic on "more than half"), any future leader — elected only if a majority of the cluster voted for it, and Raft refuses to vote for a candidate whose log is behind the voter's own — is guaranteed to already hold every previously committed entry. A committed entry therefore survives as long as a majority of the cluster survives, full stop, independent of which specific nodes crash or when.

ARC 06 · WHY THAT STILL COSTS

Consensus is not free, and pretending otherwise is how you get surprised in production

Every cost below is a direct, physical consequence of requiring a majority to agree before anything is durable — understanding them is what lets you use quorum queues where they earn their keep instead of everywhere by default.

  • Every operation costs a majority round trip plus an fsync. A classic queue's publish can be acknowledged as soon as the local queue process (and, if durable, the local disk) accepts it. A quorum queue's publish is not durably committed until a majority of replicas — not just the leader — have written it to disk. That's real network latency to at least one remote node, every single publish, that a single-node queue simply doesn't pay.
  • A minority partition can make zero progress, by design — and "by design" doesn't make it free to operate around. If a network fault leaves a quorum queue's leader (or any subset of replicas) unable to reach a majority, that side of the cluster correctly refuses to commit new writes rather than risk divergence. That's exactly the safety property you wanted, but it means publishers on the wrong side of a partition see failures or timeouts, not degraded-but-working — your application has to handle that.
  • Log compaction (snapshotting) is background work you now operate. An ever-growing Raft log would make both disk usage and restart-time replay unbounded, so ra periodically snapshots rabbit_fifo's state and truncates the log before it — real CPU and disk I/O that a classic queue's simpler on-disk format doesn't need to do.
  • Replica placement and network topology now matter in a way they didn't for a single-process queue. Cross-AZ or cross-region round-trip time is added directly to every commit's latency, because "majority" means "wait for the slower of however many remote acks you need," not "wait for local disk."
THE HONEST TRADE

None of this is an argument against quorum queues — it's the actual price of the safety that eliminated §4's split-brain and silent-loss failure modes. A classic queue is faster precisely because it never pays a network round trip to decide whether a write happened; a quorum queue is slower precisely because it refuses to call a write "done" until a majority could survive losing any one member. §9 makes this trade quantitative against other systems; §7 first nails down exactly which components host that trade inside the broker.

ARC 07 · FINAL ARCHITECTURE

A quorum queue, as objects you can click

A quorum queue is not one process the way a classic queue is — it's a small distributed system: one ra server process per replica, a shared state machine definition (rabbit_fifo) that every replica runs identically, a replicated log each maintains independently on disk, and a client-facing module (rabbit_quorum_queue) that makes the whole cluster look like one AMQP queue to a producer or consumer who never needs to know how many replicas exist. DEEP CONTEXT · WHAT "THE QUEUE" ACTUALLY MEANS NOW

When a client declares a quorum queue, RabbitMQ doesn't create one Erlang process — it creates an x-quorum-initial-group-size-member ra cluster (default 3), each member running on a node chosen by the queue's leader-locator policy, each holding an identical copy of the replicated log and an identical rabbit_fifo state machine derived from replaying it. A producer's Basic.Publish doesn't talk to "the queue" as a single thing — it talks to whichever replica the channel believes is currently the leader, via rabbit_fifo_client, which also handles finding a new leader automatically if that guess turns out to be stale.

ARC 08 · INTERNAL IMPLEMENTATION

Every operation is a command; every command is a Raft log entry

This is the idea the whole chapter has been building to, stated precisely: publish, consume (checkout), ack (settle), requeue (return), and reject (discard) are not queue-process state mutations — they are commands appended to a Raft log and applied to rabbit_fifo only after that command's log index is committed. That single design decision is why a quorum queue's ack means something a classic queue's ack never quite could, and it's why the queue is slower — you're paying for that guarantee on every operation, not just the ones you'd intuitively call "important."

(a) The log entry: term, index, command

Every entry in a quorum queue's Raft log is, conceptually, a triple: the term during which it was appended (a monotonically increasing epoch number — Raft's mechanism for letting any node recognize a stale leader without ambiguity), its index (a strictly increasing position in the log), and a command — a rabbit_fifo protocol record describing exactly one queue operation:

Erlang (simplified)rabbit_fifo.erl — the command shapes that become log entries
%% Every one of these, once appended at some {Term, Index}, is what
%% "the log" actually contains. Nothing is applied to queue state
%% directly -- only via one of these going through commit first.
-record(enqueue,  {pid, seq, msg}).                 %% a publish
-record(checkout, {consumer_id, spec, meta}).       %% a consumer wants messages
-record(settle,   {consumer_id, msg_ids}).          %% an ack
-record(return,    {consumer_id, msg_ids}).          %% a nack/requeue
-record(discard,  {consumer_id, msg_ids}).          %% reject, no requeue

(b) Snapshots: why the log can't just grow forever

A log that only ever grows would eventually make two things unbounded: disk usage, and the time it takes a restarted or newly-joined replica to catch up by replaying every entry since the beginning of time. ra fixes this the way every serious consensus implementation does — it periodically has rabbit_fifo serialize its entire current state into a snapshot, records the log index that snapshot covers, and then discards every log entry at or before that index. A replica that falls far enough behind that the leader has already discarded the entries it needs is caught up with an InstallSnapshot transfer — the whole current state in one shot — rather than replaying history that no longer exists on disk anywhere.

WHY MEMORY TRACKS UNACKED MESSAGES, NOT QUEUE DEPTH

Here's the detail that catches people who assume a quorum queue behaves like a classic one: snapshotting only discards log entries for commands that are fully resolved — an enqueue whose message has since been acked can be compacted away, because the snapshot itself no longer needs to represent it. A message that is still sitting in the queue unconsumed, or has been delivered to a consumer but not yet acked, is still live state — it has to be part of every snapshot until it's settled, because a new leader elected after a crash needs to know it exists. So a million already-acked messages that flowed through cleanly cost you almost nothing once compacted; ten thousand messages stuck unacked because a consumer stalled cost you real, persistent memory on every single replica, for as long as they stay unacked. x-max-in-memory-length and x-max-in-memory-bytes exist specifically to cap this: past the configured threshold, message bodies are pushed out to disk-only storage while rabbit_fifo keeps just enough metadata in memory to still track and redeliver them — bounding memory growth independent of how deep the backlog gets.

(c) x-delivery-limit: poison-message protection built into the state machine

Chapter 5 covered the classic-queue reality: detecting a "poison message" — one that a consumer keeps nacking or crashing on, forever — required application-level bookkeeping, because a classic queue's redelivery count is not durably, centrally tracked anywhere the queue itself can act on. rabbit_fifo fixes this structurally: every message carries a delivery_count that the state machine itself increments on every redelivery, as part of the same committed log entry that performs the redelivery. Once delivery_count would exceed the queue's configured x-delivery-limit, the checkout command that would have redelivered the message instead drops it (or routes it to the queue's dead-letter exchange, if one is configured) — automatically, durably, and identically on every replica, with zero application code required.

Erlang (simplified)rabbit_fifo.erl — delivery-limit enforcement inside apply/3
checkout_one(Msg = #msg{delivery_count = Count}, Limit, State) when Limit =/= undefined, Count > Limit ->
    %% The state machine itself refuses to redeliver -- this decision
    %% is made identically by every replica once THIS command commits,
    %% not by whichever consumer happens to be connected right now.
    case State#state.dlx of
        undefined -> {drop(Msg, State), {reason, delivery_limit_exceeded}};
        _DlxCfg    -> {dead_letter(Msg, delivery_limit_exceeded, State), ok}
    end;
checkout_one(Msg = #msg{delivery_count = Count}, _Limit, State) ->
    {deliver(Msg#msg{delivery_count = Count + 1}, State), ok}.
ARC 09 · TRADEOFFS

Replicated durability, priced eight different ways

Every system that replicates queue or log state chooses how strict its commit rule is, and that choice is the whole tradeoff. Read the table as a spectrum from "no consensus at all" to "strict majority on every write":

Read the RabbitMQ row against the Redis row and the point of this whole chapter is right there: an acknowledged write is only as durable as the weakest link in how it got replicated. Async replication (Redis Streams' default, and what classic mirroring effectively was) can always lose an acknowledged write to a badly timed failover. Majority-quorum replication (quorum queues, Kafka with a floor on ISR size, Pulsar's BookKeeper, NATS JetStream) cannot — not "rarely," cannot, as a mathematical consequence of requiring overlap between any two majorities of the same cluster.

ARC 10 · PERFORMANCE CHARACTERISTICS

The bill, itemized

Every number here follows directly from "commit requires a majority round trip plus an fsync":

  • Per-operation cost: O(1) to append to the leader's local log, but O(majority) messages to replicate and O(majority) acks to wait for before the entry is committed — the leader must hear back from ⌈(N+1)/2⌉ − 1 followers (it counts itself), not just fire-and-forget to all N.
  • Per-replica process footprint: each replica is its own ra_server Erlang process plus supporting write-ahead-log processes, running the full rabbit_fifo state machine — a quorum queue with N replicas is meaningfully more BEAM processes and more per-node memory than one classic queue process, before you even account for the unacked-message memory model from §8.
  • Disk access pattern: sequential appends to each replica's write-ahead log, batched where possible, with an fsync on the durability-critical path for every committed entry — a fundamentally different (and heavier) disk profile than a classic queue's simpler message-store-plus-index layout.
  • Leader election cost: O(N) vote-request messages, bounded in time by the randomized election timeout range — the mechanism that guarantees at most one leader per term without a fixed, brittle timing assumption about the network.
  • Throughput scales across queues, not within one queue. A single quorum queue's ceiling is set by how fast a majority can round-trip and fsync; getting more aggregate throughput on quorum queues means spreading load across more queues (and therefore more independent Raft clusters, ideally with staggered leaders across nodes), not expecting one queue to get faster by adding replicas — more replicas raises the majority size, if anything adding latency, not throughput.

ARC 11 · REAL-WORLD PRODUCTION

Three stories from the mirrored-to-quorum migration

Story 1: the GitHub 2014 partition, revisited from the fix's side

Chapter 1 covered GitHub's publicly documented 2014 incident, where network flakiness between clustered RabbitMQ nodes caused a partition and, depending on cluster_partition_handling configuration, divergent mirrored-queue state on each side. It's one of the most-cited real-world justifications operators give for moving critical queues onto quorum queues — not because Raft would have made the network flakier link behave better, but because a quorum queue's minority side mechanically cannot accept writes during the same fault, which converts "silent divergence discovered later" into "visible, immediate write failures on one side" — a strictly easier failure to detect, alert on, and reason about.

Story 2: hosted-RabbitMQ providers documenting the sync-blocking problem in public

CloudAMQP, one of the larger hosted-RabbitMQ providers, has published operator-facing guidance comparing classic mirrored queues to quorum queues that calls out exactly the ha-sync-mode=automatic blocking behavior this chapter derived in §1 and §4 as a top reason for migrating: a mirror rejoining after a restart or a rebalance could stall an entire queue's traffic for the duration of a full backlog copy, on customer-facing production queues, with no way to make it non-blocking short of switching mechanisms entirely. Teams running large mirrored-queue fleets (a pattern reported across multiple large-scale RabbitMQ deployments in this era, including in financial services) hit this repeatedly enough that it became a standard line item in "why we migrated" writeups industry-wide, well before mirrored queues were formally deprecated.

Story 3: quorum-queue memory growth from stalled consumers — a recurring operational surprise

§8's memory model — quorum queue memory tracks unacked messages, not total queue depth — is not a corner case operators read about and file away; it is a recurring class of production incident. A consumer that stalls (a deploy gone wrong, a downstream dependency timing out, a bug that stops acking) doesn't just build up a backlog the way it would on a classic queue — it holds an ever-growing set of "still live" state resident across every replica, because none of it can be snapshotted away while unsettled. Operators who assume "queue depth looks fine, so memory must be fine" have been caught by exactly this gap, which is why x-max-in-memory-length/x-max-in-memory-bytes and per-queue memory alerting on unacked count (not just queue depth) are now standard advice in quorum-queue operational runbooks, and why x-delivery-limit — capping how long a message can stay "unsettled but repeatedly redelivered" — is recommended as a default rather than an opt-in.

Simplified but structurally faithful Erlang. First, the behaviour contract every Raft-backed state machine — rabbit_fifo included — must implement:

Erlangra_machine.erl — the behaviour contract, simplified
%% Every ra_machine callback module (rabbit_fifo is one) implements this.
%% Note what's absent: no networking, no persistence code, no leader
%% election logic. The state machine only ever sees ALREADY-COMMITTED
%% commands -- ra guarantees that by the time apply/3 runs.
-callback init(Config) -> State.
-callback apply(Meta, Command, State) -> {State, Reply, Effects}.
-callback state_enter(RaftState, State) -> Effects.  %% e.g. becoming leader

Second, the shape of rabbit_fifo's apply/3 for an enqueue — this is what "the command is only applied after commit" looks like as code:

Erlangrabbit_fifo.erl — apply/3 for an enqueue, simplified
apply(_Meta, #enqueue{pid = Pid, seq = Seq, msg = Msg}, State0) ->
    %% This function only ever runs once ra has already determined the
    %% entry containing this command is committed -- majority-persisted,
    %% fsync'd, on every replica that's reachable. There is no "maybe"
    %% left by the time this line executes.
    State1 = dedupe_by_seq(Pid, Seq, State0),      %% idempotent re-application on replay
    State2 = enqueue_message(Msg, State1),
    Effects = maybe_deliver_to_waiting_consumer(State2),
    {State2, ok, Effects}.

Third, the safety-critical part of leader election — a candidate is only granted a vote if its log is at least as up to date as the voter's own, which is the mechanism §5's safety argument actually depends on:

Erlangra_server.erl — vote handling, simplified
handle_vote_request(#request_vote{term = Term, last_log_index = CandIdx,
                                   last_log_term = CandTerm}, State) ->
    MyLastTerm  = last_log_term(State),
    MyLastIndex = last_log_index(State),
    %% "At least as up to date" -- compare TERM first, then INDEX.
    %% This is the entire mechanism that stops a candidate who's
    %% missing committed entries from ever becoming leader.
    LogIsOk = (CandTerm > MyLastTerm) orelse
              (CandTerm =:= MyLastTerm andalso CandIdx >= MyLastIndex),
    case Term >= current_term(State) andalso LogIsOk andalso not_voted_yet(State, Term) of
        true  -> {grant_vote(State, Term), vote_granted};
        false -> {State, vote_denied}
    end.
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Separate "is this committed" from "what does this command do." ra_server owns every question about terms, votes, and log replication; rabbit_fifo's apply/3 never has to think about consensus at all — by the time it runs, the answer to "did a majority agree to this" is already yes. This is the same instinct as separating a supervisor's restart policy from a worker's business logic (ch. 1): keep the hard, general problem in one reusable layer, and let the specific state machine be almost boring. 2. Make the state machine's apply function pure and idempotent. Because a replica might replay its log from a snapshot after a restart, or a leader might resend an entry a follower already has, apply/3 is written to tolerate being called again with a command it already processed (dedupe_by_seq above) — essential for a function that will be re-run during recovery, not an edge case someone forgot. 3. Build the general-purpose consensus library first, the queue second. ra is deliberately not RabbitMQ-specific — it's a reusable Raft implementation that rabbit_fifo happens to be the first major consumer of (Khepri, RabbitMQ's newer metadata store, is the second). Investing in a correct, general Raft library once and building multiple features on it is a direct rejection of the "patch the existing thing" instinct that produced mirrored queues' original design.
