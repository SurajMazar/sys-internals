WHATSAPP ARCHITECTURE · CHAPTER 03

Signal Protocol I:
X3DH Key Agreement

Every WhatsApp conversation begins before either person has said a word — with a key exchange run against a recipient whose phone might be off, in a drawer, out of signal range for a week. Classic Diffie-Hellman and TLS assume both parties are reachable right now. This chapter derives, from that single broken assumption, the Extended Triple Diffie-Hellman (X3DH) protocol that lets Alice encrypt to an offline Bob with no plaintext — and no session key — ever touching the server.

ARC 01 · THE PROBLEM

Encrypting to someone who isn't there

Take Diffie-Hellman as given — both sides pick a secret exponent, exchange public values, and arrive at a shared secret no eavesdropper can compute. It is one of the cleanest ideas in computer science, and it is useless as written for a messaging app, because it has a hidden precondition: both parties must be online, at the same time, to exchange those ephemeral public values. TLS makes the same assumption — the handshake is a live, interactive round trip between a client and a server that is, by definition, listening.

A messaging app cannot make that assumption even once. Alice wants to send Bob a message right now. Bob's phone is off — dead battery, airplane mode, buried in a drawer for a week while he's on a research station in Antarctica. WhatsApp's actual constraint, stated precisely:

  • Bob may be unreachable indefinitely. There is no bound on how long a device can stay offline before the first message needs to go out — could be seconds, could be months.
  • The message must still be end-to-end encrypted on first send. Not "encrypted once Bob comes online" — Alice's client has exactly one shot to produce ciphertext the moment she hits send, because the UI can't block on Bob's connectivity.
  • The server must not see plaintext, and must not be able to compute the session key either. It is explicitly modeled as an untrusted relay — it stores and forwards bytes, full stop.
  • Whatever mechanism solves this must still give the two parties a strong key exchange — mutual authentication of identity, resistance to a passive eavesdropper, and (ideally) forward secrecy — not a watered-down version because one side is asleep.

This is the actual first design problem of any asynchronous end-to-end encrypted system, and it long predates WhatsApp: how do you run a key exchange protocol against a party who isn't running anything? The answer the industry converged on — pre-published, pre-signed key material a client can fetch and use unilaterally — is X3DH, and this chapter derives it by trying and failing at the obvious alternatives first.

WHY THIS MATTERS FOR THE NEXT TWO CHAPTERS

X3DH runs exactly once per new conversation (per device pair) to produce a single 32-byte shared secret. Everything after that — the years of messages two people might exchange — is handled by a completely different mechanism, the Double Ratchet (chapter 4), which evolves that one secret into an endless stream of unique per-message keys. Keep the boundary clear: X3DH solves "how do two parties agree on a first secret when one is offline"; the ratchet solves "how do we keep that secret from becoming a liability as the conversation continues." Conflating the two is the single most common confusion when engineers first read the Signal protocol docs.

DEEP CONTEXT · WHY PGP DOESN'T SOLVE THIS

PGP looks like it already solved async E2E encryption in 1991 — you can encrypt an email to someone's long-term public key without them being online. It does solve confidentiality. It does not solve forward secrecy: PGP messages are encrypted directly to a long-term identity key that never rotates, so a single key compromise, any time in the future, decrypts every PGP message ever sent to that key. X3DH's entire design is what you get when you insist on PGP's async delivery model and OTR's forward secrecy at the same time — sections 3–5 show exactly why you can't get both by patching either one alone.

ARC 03 · NAIVE SOLUTION

Attempt #1: DH straight between long-term identity keys

Derive honestly, from the simplest thing that could work. Every user already has a long-term identity key — Alice has IK_A, Bob has IK_B, and both public halves are sitting on the server already (they have to be published somewhere for anyone to find them). So: skip the whole "ephemeral exchange" idea. Just run DH directly on the identity keys.

pseudocodestatic_identity_dh.txt — the strawman
// Alice wants to message Bob for the first time. Bob may be offline forever —
// doesn't matter, his IDENTITY KEY is already sitting on the server.

fetch(IK_B_pub)                          // one static public key, published at registration
SK = DH(IK_A_priv, IK_B_pub)               // Alice's classic DH computation
msg_key = KDF(SK)
ciphertext = AEAD_encrypt(msg_key, plaintext)
send(ciphertext)                          // zero round trips needed beyond fetching one public key

// Bob, whenever he comes back online:
SK = DH(IK_B_priv, IK_A_pub)               // same shared secret, by DH's commutative property
msg_key = KDF(SK)
plaintext = AEAD_decrypt(msg_key, ciphertext)

This is not a silly idea — it is exactly the shape of what makes DH attractive here: zero interaction with Bob is required to send the first message, because a static public key needs no live round trip to fetch and use. It even mutually authenticates: only someone holding IK_B_priv can ever compute the same SK, so if that check passes, Alice knows she encrypted to the real Bob (assuming she trusts the server's copy of IK_B_pub, a caveat section 5 comes back to). Every message, forever, reuses the same SK — cheap, simple, and it is precisely this reuse that section 4 shows is fatal.

ARC 04 · WHY IT FAILS

Zero forward secrecy is not a small gap — it's the whole game

Static identity-key DH is not slow, not expensive, not hard to implement. It fails on the one axis that matters most for a messaging system operating at WhatsApp's scale and duration: forward secrecy — the guarantee that compromising today's keys does not expose yesterday's messages.

  • One key, one compromise, entire history. SK = DH(IK_A, IK_B) never changes. If IK_A_priv or IK_B_priv is ever extracted — a stolen device, a court order compelling key extraction, a future cryptographic break of Curve25519 — every message the two of them ever exchanged, recorded by a passive eavesdropper years earlier, decrypts at once. This is exactly the "store now, decrypt later" threat model nation-state adversaries are explicitly known to budget for.
  • No deniability. Because the same static SK is reused for every message, ever, there is a standing cryptographic relationship between Alice and Bob's identity keys that looks the same whether it's message #1 or message #100,000. Signal's design goal (borrowed from OTR) is that neither party should be able to prove to a third party which messages the other actually sent — a static shared key undermines the reasoning needed for that property, discussed properly in section 6.
  • No per-session isolation. Multi-device support (a phone plus linked desktop and web clients) means each of Bob's devices needs its own session; a single static IK_B shared across a whole account doesn't even model "which of Bob's five devices should decrypt this" without extra bookkeeping bolted on top.
THE NUMBERS

Model a single active WhatsApp conversation: two people, five years, roughly 50 messages/day — ~91,000 messages. Under static-key DH, every one of those 91,000 ciphertexts is protected by exactly one secret. A single key-extraction event — at any point in those five years, against either party — doesn't cost the attacker "today's messages." It costs 91,000 messages, atomically, including messages sent when the device that was eventually compromised didn't even exist yet. Forward secrecy is precisely the property that turns that one catastrophic event into "the attacker gets tomorrow's messages, and only tomorrow's" — worth an entire second protocol (chapter 4) once X3DH is solved.

So the identity-key-only design is out. We need per-session ephemeral key material mixed in — which is exactly what classic DH already does for online exchanges. The only new constraint is that the ephemeral exchange has to work without Bob present. Section 5 tries the honest candidates for solving that.

ARC 05 · BETTER SOLUTION, CANDIDATES EXAMINED

Three ways to get ephemeral material without Bob present

We need fresh, per-session key material — not just the static identity keys — mixed into the shared secret, but Bob cannot generate a fresh ephemeral key on demand because he isn't running. Three candidates, each eliminated for a specific, quotable reason:

Candidates for offline ephemeral key agreementSTEP-BY-STEP

None of the three candidates work, but each failure teaches a requirement for the real design: (A) shows we need Bob's ephemeral contribution pre-published, not live; (B) shows the server must never hold anything that lets it compute the session key; (C) shows the design must tolerate Bob being offline for the entire message's lifetime, not just milliseconds. Put those three requirements together and you get exactly one shape: Bob pre-generates and pre-signs a batch of ephemeral-ish public keys, publishes them to the (untrusted) server in advance, and Alice consumes one unilaterally — the prekey bundle. That's X3DH.

ARC 06 · WHY THAT STILL COSTS

Pre-publishing key material is not free

Before assembling the final protocol, be honest about what "publish a batch of keys in advance" costs — every one of these costs shows up later in this chapter as a named, quantified tradeoff:

  • The server now stores private-adjacent state. Not private keys — only public halves — but it must store, serve, and correctly delete-on-use potentially hundreds of millions of one-time prekeys cluster-wide. Get the delete-on-use step wrong (a race, a retry, a replicated read of stale data) and two different sessions can be issued the same one-time prekey — quietly destroying the forward-secrecy property that key existed to provide. Section 15 lets you trigger exactly this failure.
  • One-time prekeys are a consumable resource, and they run out. If Bob is offline for long enough that more people message him than he has prekeys pre-generated (his phone was off for a month during a busy group chat's worth of new 1:1 conversations), the pool hits zero. The protocol needs a defined, safe degradation — not a hard failure — for this case.
  • Trusting the server's copy of a public key is a standing risk. Alice never talks to Bob directly to confirm IK_B_pub is really his. If the server is compromised or coerced, it can hand Alice an attacker's identity key instead, and the protocol's math will happily "succeed" — the attacker just becomes a man in the middle. This is not a flaw unique to X3DH; it's the trust-on-first-use problem inherent to any system that bootstraps identity through a directory service, and section 8 shows the only honest mitigation (out-of-band verification) and how rarely anyone actually uses it.
  • Signed prekeys must rotate, which means re-signing, which means the identity key's signing operation is now a recurring liability surface — if the rotation job breaks silently, clients keep serving a medium-term key well past its intended lifetime, quietly widening the forward-secrecy window it was meant to bound.
THE INDUSTRY'S ANSWER — AND ITS ADMISSION

None of these costs are eliminated — they're priced and bounded. Servers cap one-time prekey pools and ask clients to top them up opportunistically; signed prekeys rotate on a schedule (weekly in Signal's reference design) rather than never; and the identity-key trust problem is solved not cryptographically but socially — safety-number verification, which almost nobody performs, is a standing admission that X3DH alone cannot detect a malicious directory service. The protocol's actual job is narrower than "solve trust": it is "given a public key you were handed, prove a matching private key was used, efficiently, without either party being online." Whether that public key was the right one is explicitly out of scope, and out-of-band verification is the only real answer — a distinction worth stating plainly in an interview.

WHY FOUR, NOT TWO

A single DH between ephemeral keys would give forward secrecy but no authentication (anyone could run that DH with anyone). A single DH between identity keys authenticates but gives no forward secrecy (section 4). X3DH needs both properties simultaneously, from both directions of trust — Alice must be sure she's talking to Bob, and Bob (once online) must be sure the message came from Alice — which is why the design mixes identity keys against ephemeral keys in both combinations rather than picking just one pairing. Section 8 walks each of the four operations and states, precisely, what breaks if you remove it.

ARC 08 · INTERNAL IMPLEMENTATION

The handshake, operation by operation

Curve25519 is the workhorse underneath every operation in this chapter: a Montgomery curve chosen (by Bernstein, 2005) specifically because its scalar multiplication has a uniform, branch-free ladder — no variable-time table lookups, no special-cased points — which makes constant-time implementation the natural way to write it rather than something bolted on after a timing side-channel is found. Keys are 32 raw bytes, no ASN.1, no curve-parameter negotiation: you cannot accidentally pick a weak curve, because there is only one curve. Signing reuses the same Curve25519 key material via XEdDSA (a Signal-designed scheme that lets a Curve25519 key sign messages Ed25519-style) — one keypair per identity, used for both key agreement and signatures, rather than shipping two separate keys.

(a) The four DH operations, and what each one buys

The order of concatenation and the KDF's domain separation are not cosmetic. SK = KDF(F ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4), where F is a constant 32-byte string of 0xFF prepended specifically to keep this key-derivation domain cryptographically separate from any other protocol that might reuse Curve25519 points as input to a hash (a form of cross-protocol domain separation). The KDF itself is HKDF: an extract step with a fixed all-zero salt (there is no per-session randomness to salt with — the four DH outputs already provide that), followed by an expand step whose info parameter is a fixed, protocol-specific ASCII string. Change the concatenation order and two implementations of the "same" protocol silently derive different keys from identical DH outputs — which is precisely why X3DH is a specification with an exact byte order, not just "combine these four numbers somehow."

(b) Associated data: binding the session to both identities

Every message encrypted under SK carries AD = Encode(IK_A) ‖ Encode(IK_B) as associated data fed into the AEAD. This prevents an identity-binding confusion attack: without AD, a ciphertext produced for one Alice↔Bob session could potentially be replayed as if it belonged to a session between different identities, if the raw symmetric keys ever collided across sessions. Binding both public identity keys into every decryption operation means a ciphertext only decrypts correctly under the AD it was actually created with.

GRACEFUL DEGRADATION, NOT FAILURE

Once the pool is empty, the server serves a bundle with no one-time prekey field. Alice's client computes SK from just DH1 ‖ DH2 ‖ DH3 — three operations instead of four — and the session proceeds normally. The accepted cost: no protection against a future compromise of this specific signed prekey in the narrow window until it next rotates. This is a deliberate, documented tradeoff, not a bug — refusing to send the message would be strictly worse (an outage) for a marginal, bounded reduction in forward secrecy that the signed-prekey rotation schedule already limits in duration.

Where products skip it (iMessage pre-2024, Telegram's default cloud chats, Slack), it's because they made a different, explicit call about the offline and forward-secrecy requirements — not because they found a cheaper way to get the same guarantees.

ARC 10 · PERFORMANCE CHARACTERISTICS

Why one round trip beats "wait for Bob"

The entire performance argument for X3DH is a single number: it needs exactly one network round trip — Alice to the server, to fetch a bundle — regardless of how long Bob has been offline. Every synchronous alternative's round-trip count is a function of Bob's offline duration, which is unbounded. Costs, precisely:

  • Compute per session: exactly 4 Curve25519 scalar multiplications (or 3, degraded mode) plus one HKDF call — on a modern mobile CPU each X25519 operation is tens of microseconds; the whole handshake's crypto cost is sub-millisecond and happens once per new conversation, never per message.
  • Bandwidth per bundle fetch: one identity key (32B) + one signed prekey (32B) + one signature (64B) + one one-time prekey (32B, optional) ≈ 160 bytes down, plus the registration ID and key IDs — trivial next to a photo or even a text message's TLS overhead.
  • Server storage: O(k) one-time prekeys per registered device, k typically ~100 in reference clients, replenished opportunistically when the pool drops low — a few KB per device, dwarfed by media storage.
  • Battery/radio: a bundle fetch is one small HTTPS-equivalent request — radio wakeup dominates the actual bit cost on modern mobile baseband, and this is the same wakeup the client already pays to open the app or receive a push notification, so X3DH adds no additional radio state transition in the common case.

ARC 11 · REAL-WORLD PRODUCTION

From a 2014 partnership to a billion-user default

The rollout, in public numbers

In November 2014, WhatsApp and Open Whisper Systems announced they were integrating what was then called the TextSecure protocol into WhatsApp, starting with Android-to-Android messages. By April 5, 2016, WhatsApp announced that full end-to-end encryption — X3DH plus the Double Ratchet, exactly as this chapter and the next describe — was live by default for every message, call, photo, and video across every supported platform, for a user base the company stated at over one billion people. That is very likely the largest single deployment of an X3DH-style handshake in existence, and the accompanying WhatsApp Security Whitepaper (updated repeatedly since) remains the primary public documentation of what was actually shipped, since the client and server code are closed source.

Key management at that scale

Reference client implementations (Signal's own, published as libsignal) pre-generate on the order of 100 one-time prekeys at registration and top up the pool from the client whenever the server reports it's running low — an entirely client-driven replenishment, since the server cannot generate valid prekeys itself (it doesn't hold Bob's identity signing key). Signed prekeys rotate on a periodic schedule (documented as roughly weekly in Signal's reference design, with old signed prekeys retained briefly to decrypt in-flight messages before final deletion) — a concrete instance of the rotation tradeoff from section 6.

Multi-device, the hard follow-on problem

WhatsApp's 2021 multi-device architecture (allowing a linked desktop or web client to work without the phone staying connected) multiplies this chapter's problem: X3DH-style sessions must now be established and maintained per device, not per account, and a message to "Bob" is really fan-out encryption to every one of Bob's linked devices' identity keys independently. WhatsApp's public multi-device security documentation describes an additional device-linking authorization step precisely because adding a new device is, from a cryptographic standpoint, indistinguishable from an attacker registering a new "device" for Bob unless something authenticates the linking event out of band (a QR-code scan between Bob's own devices).

What's publicly known vs speculation

WhatsApp's exact production numbers for one-time prekey pool sizes, replenishment thresholds, and internal service names for the directory that serves prekey bundles are not publicly documented — the whitepaper describes protocol behavior, not operational internals. Treat the ~100-key batch and weekly rotation figures above as Signal's documented reference values, reasonably assumed (not confirmed) to be similar in WhatsApp's implementation since both are built on the same underlying protocol family.

ARC 13 · SOURCE CODE WALKTHROUGH

Reading the real thing: libsignal's session builder

WhatsApp's client implementation is closed source, but it is built on the same published Signal protocol that Signal's own open-source reference library — libsignal (github.com/signalapp/libsignal) — implements. The module layout below reflects libsignal's real structure; treat it as "the protocol's canonical open implementation," not "WhatsApp's actual source," which is not public.

rust/protocol/src/
├── ● session.rs — process_prekey_bundle(): the Alice-side X3DH entry point
├── ● ratchet.rs — initialize_alice_session() / initialize_bob_session(): the 4-DH → HKDF derivation
├── curve/
│ ├── ● curve25519.rs — X25519 scalar multiplication (Montgomery ladder), clamping
│ └── ● curve.rs — XEdDSA sign/verify: Ed25519-style signatures over Curve25519 keys
├── state/
│ ├── ● prekey_bundle.rs — the wire struct: registration id, identity key, signed prekey + signature, optional one-time prekey
│ ├── prekey_store.rs / signed_prekey_store.rs — server-facing storage traits; one-time prekey delete-on-use lives here
│ └── session_record.rs — the derived session state handed off to the Double Ratchet (chapter 4)
└── kdf/hkdf.rs — HKDF-SHA256 extract/expand, used both here and by the ratchet

Alice's side, simplified from the published X3DH spec's own reference pseudocode:

pseudocodesession.rs — process_prekey_bundle(), the parts that matter
function processPrekeyBundle(bundle):
    // 1. Verify Bob didn't just get a fabricated signed prekey from a bad server
    if not XEdDSA_verify(bundle.IK_B, bundle.SPK_B, bundle.SPK_signature):
        throw "invalid signed prekey signature — abort session"

    // 2. Generate one fresh ephemeral keypair for this session only
    EK_A = generateCurve25519Keypair()

    // 3. The four DH operations (§8)
    DH1 = X25519(IK_A.priv,  bundle.SPK_B)
    DH2 = X25519(EK_A.priv,  bundle.IK_B)
    DH3 = X25519(EK_A.priv,  bundle.SPK_B)
    DH4 = bundle.OPK_B ? X25519(EK_A.priv, bundle.OPK_B) : ""  // degrade gracefully (§8c)

    // 4. Domain-separated KDF — F is 32 bytes of 0xFF, salt is zero, info is fixed
    SK = HKDF(salt=0x00*32, ikm=F ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4, info="WhisperText_X3DH", len=32)

    AD = encode(IK_A.pub) ‖ encode(bundle.IK_B)
    return SessionState(SK, AD, usedOPKid: bundle.OPK_id)

And Bob's side, run whenever he next comes online and receives Alice's first message (which must carry IK_A_pub, EK_A_pub, and the ID of the one-time prekey used, since Bob has no other way to know which of his many prekeys Alice consumed):

pseudocodesession.rs — Bob's mirrored derivation
function processInitialMessage(header):
    OPK_B = lookupAndDeleteOneTimePrekey(header.opk_id)  // consumed exactly once, ever

    // mirrored DH operations — same four values, computed from the other side
    DH1 = X25519(SPK_B.priv, header.IK_A)
    DH2 = X25519(IK_B.priv,  header.EK_A)
    DH3 = X25519(SPK_B.priv, header.EK_A)
    DH4 = OPK_B ? X25519(OPK_B.priv, header.EK_A) : ""

    SK = HKDF(salt=0x00*32, ikm=F ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4, info="WhisperText_X3DH", len=32)
    // identical SK to Alice's, by Diffie-Hellman's commutativity — §15 proves this live
WHY THE ENGINEERS CHOSE THIS — TWO DECISIONS TO STEAL

1. Verify the signature before doing any DH work. A forged signed prekey is the one thing standing between "the server tampered with a key" and "you never notice" — checking it first means a bad bundle fails loudly and immediately, not silently inside a derived key nobody double-checks. 2. Let the one-time prekey be optional at the type level, not a special-cased error path. Because exhaustion is an expected, common condition (not a bug), the real implementation models "no OPK available" as a normal branch in the same function — exactly the graceful-degradation design from section 8(c), reflected directly in the code shape.
