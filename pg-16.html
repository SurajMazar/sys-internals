POSTGRESQL INTERNALS · CHAPTER 16

Query Pipeline II:
The Cost-Based Planner

The parser and rewriter (chapter 15) hand the planner a tree that says what the query means. The planner's entire job is to decide how to compute it — and it must do that without ever looking at the actual data, using only statistical summaries collected in advance. This chapter derives why that has to be a cost model rather than a rulebook, walks through exactly what ANALYZE collects and how selectivity is estimated from it, and then builds the cost formulas, path search, and join-order algorithm that turn a parsed query into the one plan PostgreSQL believes is cheapest.

ARC 01 · THE PROBLEM

The same SQL text, six orders of magnitude apart

Take one query and change nothing about its text: SELECT * FROM orders o JOIN customers c ON c.id=o.customer_id WHERE c.region=$1 AND o.status=$2. Bind region='eu-west', status='cancelled' and the right plan touches a few hundred rows through two indexes in a fraction of a millisecond. Bind region='us-east', status='completed' — the common case — and the same two-index plan would fetch nine million rows one random heap page at a time, while a sequential scan finishes in a controlled, linear pass. The SQL is identical. The schema is identical. The only thing that changed is which values happen to be common versus rare in the data — and that single fact flips the optimal strategy by two to three orders of magnitude on each side of the join, which compound multiplicatively once you add a third table.

This is not a contrived example; it is the normal condition of a general-purpose query engine serving parameterized, ad hoc, and ORM-generated SQL against a live data distribution the query text itself says nothing about. A planner has exactly two ways to know which case it is in: (a) guess, using rules that don't depend on the data, or (b) know, using a summary of the data collected in advance. Chapter 16 is the argument for, and the machinery behind, choice (b) — the cost-based optimizer — and everything that follows is a consequence of taking that choice seriously: statistics collection, selectivity estimation, a calibrated cost model, and a search over the space of physical execution strategies that a syntax-driven planner would never need.

WHAT "COST-BASED" ACTUALLY COMMITS YOU TO

It is not a vague philosophy — it is three concrete obligations, and this chapter is organized around them: (1) you must collect a statistical model of every column's data distribution ahead of time, because sampling at plan time is too slow (§5); (2) you must turn that statistical model into a predicted row count for arbitrary predicates and joins — selectivity estimation — and that step is where almost all real-world bad plans originate (§6, §8); (3) you must have a calibrated numeric cost for every physical strategy (scan method, join method, join order) so that "cheaper" is a comparable number and not a vibe (§8). Get any one of the three wrong and the planner produces a plan that is syntactically valid and catastrophically slow — which is exactly why EXPLAIN ANALYZE's estimated-vs-actual rows column (§8, §15) is the single most important diagnostic in this entire course.

DEEP CONTEXT · THE ROAD NOT TAKEN

Oracle's first optimizer (mid-1980s) was rule-based: a fixed table ranking ~15 access paths by priority, evaluated top to bottom with no notion of row counts. It shipped because it was simpler to implement and its plans were at least predictable — a DBA could reason about them without statistics. Oracle kept selling it alongside the cost-based optimizer (introduced 1992, Oracle 7) for over a decade, and only formally desupported the rule-based optimizer in Oracle 10g (2003). That fourteen-year overlap is the single best piece of evidence that "just use a rule" is not a strawman — it is a real, shipped, commercially successful design that the entire industry eventually abandoned for the same reason §3–§4 derive below.

ARC 03 · NAIVE SOLUTION

Attempt #1: a fixed rulebook

Derive the architecture honestly, the same way §1 of every chapter in this course does. The simplest planner imaginable applies a small, fixed, data-independent priority list: if a usable index exists on a predicate column, use it; join relations in the order they appear in the FROM clause; always use nested loop. No statistics, no arithmetic, no ANALYZE — just a lookup table of "when in doubt, do X."

Crule_based_plan.c — the strawman, annotated
Plan *
plan_query_rulebased(Query *q)
{
    Plan *result = NULL;

    /* Rule 1: an index on a filtered column always wins.
     * No row-count estimate is consulted — none exists.        */
    foreach(rel, q->rtable) {
        Plan *p;
        if (has_usable_index(rel, q->quals))
            p = make_index_scan(rel);       /* rule: index > seq, always */
        else
            p = make_seq_scan(rel);

        /* Rule 2: join relations in FROM-clause order, always
         * nested loop — the only join method this planner knows. */
        result = result ? make_nestloop(result, p) : p;
    }
    return result;
}

This is not a joke architecture. It already gets something right: it is fast to plan — no sampling, no arithmetic, no search over alternatives — and for a fixed, well-understood workload with a DBA who hand-tunes each query shape, it can even be made to work (this is precisely the operating model SQLite and early rule-based Oracle shipped, and thousands of hand-tuned OLTP systems still run this way informally, one index hint at a time). The strawman is worth taking seriously before you reject it.

ARC 04 · WHY IT FAILS

Quantify it: the same rule is wrong by 2-3 orders of magnitude on each side

Take the strawman's rule 1 — "an index on a filtered column always wins" — and run the actual arithmetic against a concrete table. orders has 10,000,000 rows at roughly 50 rows/page, so 200,000 pages. The predicate is status = $1, and status is skewed: 'cancelled' matches 0.001% of rows (100 rows), 'completed' matches 92% (9.2M rows). Using PostgreSQL's own unit costs (derived properly in §8): seq_page_cost=1.0, random_page_cost=4.0, cpu_tuple_cost=0.01.

  • Sequential scan cost (same for both binds): 200,000 pages × 1.0 + 10,000,000 rows × 0.01 ≈ 300,000 cost units.
  • status='cancelled', index scan: ~100 matching rows, each a random heap fetch: 100 × 4.0 ≈ 400 cost units plus a few for the index descent. The index scan is roughly 750× cheaper than the sequential scan the rule would also have to consider for the join above it.
  • status='completed', index scan: ~9,200,000 matching rows, each — in the worst case, an uncorrelated index — a separate random heap fetch: 9,200,000 × 4.0 ≈ 36,800,000 cost units. The sequential scan at 300,000 is now ~123× cheaper.

Rule 1 ("index always wins") is therefore wrong for at least one of these two binds by two full orders of magnitude, and it is the identical SQL text. Now compound it: this predicate feeds a join. If the planner's join-order rule ("preserve FROM-clause order, always nested loop") also happens to pick the wrong side to drive the loop from — which it will, roughly half the time, since it has no data to prefer one side — nested loop's cost scales with the outer row count times the inner access cost. Getting the outer side wrong by the 100×-to-1 skew above, multiplied through two or three join levels each contributing their own selectivity swing, is exactly how a fixed rule reaches the "six orders of magnitude" difference this chapter's title problem describes — not as a single dramatic number, but as several honest 10-100× errors compounding up a join tree (this compounding effect is formalized in §6 and simulated live in §15).

THE DEEPER FAILURE

Notice what's actually missing: not cleverness, but information. The rulebook doesn't fail because "index scan" or "nested loop" are bad ideas — they are frequently the correct answer, exactly as they were for the 'cancelled' bind above. It fails because the same fixed decision cannot be correct for every data distribution a column might have, and the query text carries zero information about that distribution. The only fix is to give the planner the distribution — which is precisely what ANALYZE exists to do, and §5 derives why that has to happen ahead of time rather than per-query.

ARC 05 · MAKING IT DATA-DRIVEN

Four candidates for "know the distribution," three eliminated

If the fix is information about the data, the design question becomes: when and how is that information obtained? Step through the candidates in the order any team would naturally propose them.

Getting the planner the data it needsSTEP-BY-STEP

The winning shape — precompute a statistical summary once, reuse it for every future plan — is exactly what ANALYZE does. It reads a random sample of the table (mechanism in §8), computes a compact statistical profile, and stores it in the system catalog pg_statistic, keyed by column. Every subsequent planning of every future query touching that column reads the summary in microseconds instead of re-scanning the table. The cost of learning the distribution is paid once, off the critical path of any single query, and amortized across however many times that column is ever filtered on again.

ARC 06 · WHY THAT STILL HURTS

Precomputed statistics are a snapshot, and a lossy one

Precomputing solves the latency problem but introduces two new failure modes that account for the overwhelming majority of real-world "the planner picked a terrible plan" incidents (§11 has three of them):

  • Staleness. A snapshot is only accurate until the data changes. PostgreSQL re-triggers ANALYZE automatically via autovacuum once roughly 10% of a table's rows have changed (autovacuum_analyze_scale_factor=0.1 plus autovacuum_analyze_threshold rows), which means a table can drift meaningfully out of date between runs — and a bulk load, a TRUNCATE+reload, or a sudden shift in value distribution (a new status value appearing, a promotion making one region suddenly dominant) can be invisible to the planner until the next analyze completes.
  • The independence assumption. This is the single largest source of planner misestimation in production PostgreSQL, and it deserves the full derivation below.

Consider a people table with 10,000,000 rows. city = 'San Francisco' matches 400,000 rows (4%). state = 'CA' matches 3,900,000 rows (39%). Ask for both: WHERE city='San Francisco' AND state='CA'. With no per-combination statistics, the planner's only option (absent extended statistics, §7-§8) is to multiply the two selectivities as if the columns were statistically independent: 0.04 × 0.39 = 1.56%, i.e. an estimate of 156,000 rows.

But every San Francisco row is in California — the columns are not independent, they are functionally dependent — so the true answer is 400,000 rows, 2.6× more than the independence estimate. Real schemas correlate far harder than city/state (a composite key's prefix columns, a denormalized snapshot column, a derived status field): factors of 10-50× are routine, and this single wrong number then propagates upward: it becomes the estimated cardinality feeding a join above it, whose own estimate — now built on a bad input — compounds the error again. A 5× underestimate at a base filter reliably becomes a 25-125× underestimate three joins up, which is why bad plans in production almost always trace back to one bad estimate deep inside the tree, not a globally miscalibrated cost model.

WHY THIS IS THE #1 SOURCE, NOT JUST A SOURCE

Sampling error and staleness are noisy but roughly unbiased — they scatter around the truth and average out across many queries. The independence assumption is systematically biased in one direction whenever columns are positively correlated (which most real schemas are, because that's what "designing a schema" usually means): it always underestimates the joint selectivity of correlated predicates. A systematic, one-directional bias that happens to concentrate on exactly the multi-predicate, multi-join queries that are also the most expensive to get wrong is precisely the profile of a chronic production problem rather than an occasional oddity — which is why PostgreSQL 9.6 shipped CREATE STATISTICS specifically to attack it (§7-§8), rather than, say, investing further in sampling precision.

THE KEY INVARIANT

Every stage only ever estimates. Nothing in this pipeline touches the actual table during planning — that would defeat the entire point established in §5. The planner's output is a bet, priced in the currency of stage 3's cost units, placed using stage 2's probability estimates, which are themselves only as good as stage 1's snapshot. EXPLAIN ANALYZE's "rows=X actual=Y" is, precisely, an audit of this bet against reality — and the gap between X and Y tells you exactly which stage lied (§8, §15).

ARC 08 · INTERNAL IMPLEMENTATION

The real structs, the real formulas, the real search

Six pieces, in the order data actually flows through them: (a) what ANALYZE samples and stores, (b) how selectivity is estimated from it, (c) the cost model's unit costs and formulas, (d) the Path/RelOptInfo abstractions the search operates over, (e) join order search — dynamic programming and GEQO, (f) generic vs custom plans for prepared statements.

(a) ANALYZE: reservoir sampling into pg_statistic

ANALYZE (src/backend/commands/analyze.c) does not read every row. It reads a bounded random sample of 300 × default_statistics_target rows (default default_statistics_target=100 → 30,000 rows, regardless of table size) using a two-stage algorithm: first it samples blocks using algorithm S / reservoir sampling over the block numbers, then within the sampled blocks it samples rows using Vitter's reservoir sampling algorithm (Algorithm Z) — a single sequential pass that maintains a fixed-size reservoir and replaces entries with decreasing probability as more rows are seen, guaranteeing every row in the table has equal probability of ending up in the final sample without needing to know the row count in advance. This is why ANALYZE's cost is roughly constant regardless of table size — it is bounded by the sample target, not by SELECT count(*).

The sample is reduced to one row per column in pg_statistic, with fields (simplified from the real catalog):

pg_statistic { starelid, staattnum, stanullfrac, -- fraction of NULLs stadistinct, -- n_distinct: positive = exact count, negative = -(fraction of rows), e.g. -0.2 means "distinct values scale with table size, 20% as many" stakind1..stakind5, -- which "slot" holds what (MCV, histogram, correlation, ...) -- up to 5 stats kinds per column stavalues1..stavalues5, -- e.g. the Most Common Values array stanumbers1..stanumbers5 -- e.g. each MCV's frequency, or correlation }

Four kinds of "slot" matter most: the Most Common Values (MCV) list — up to statistics_target of the most frequent values in the sample, each with its observed frequency; an equi-depth histogram of the remaining (non-MCV) values — boundaries chosen so each bucket holds roughly equal sample mass, giving cheap range-selectivity interpolation; correlation — the statistical correlation between a column's logical (sorted) order and its physical (on-disk) storage order, ranging from -1 to 1, which is the single biggest factor in whether an index scan touches one heap page per row or a handful of sequential ones (§8c, and directly exposed in the §15 simulator); and null fraction. Note this correlation is a completely different concept from the cross-column correlation that breaks the independence assumption in §6 — same English word, two distinct statistics, and mixing them up is a common source of confusion when reading planner code.

EXTENDED STATISTICS: THE INDEPENDENCE ASSUMPTION'S DIRECT FIX

CREATE STATISTICS (PG 9.6+) lets an operator declare that specific columns are correlated, and PostgreSQL then computes and stores multivariate statistics keyed to that column group instead of falling back to per-column independence: ndistinct (the true distinct-combination count instead of the product of per-column counts), dependencies (functional-dependency degree — "knowing city tells you state with what confidence"), and mcv (a most-common-values list over the combination of columns, so the city/state pair from §6 gets its own frequency entry instead of being reconstructed by multiplication). This is opt-in and per-column-group precisely because computing and maintaining multivariate stats for every possible column combination would be combinatorially expensive — the DBA has to know (or discover via EXPLAIN ANALYZE divergence) which column pairs are actually correlated.

(b) Selectivity estimation: from pg_statistic to a fraction

selfuncs.c turns a predicate into a selectivity — a number in [0,1] — using different logic per operator:

  • eqsel() (equality, col = const): if the constant appears in the MCV list, return its stored frequency directly — exact, no guessing. If it doesn't appear (or there's no MCV list), fall back to (1 - mcv_total_frequency) / (n_distinct - mcv_count), essentially 1/n_distinct spread across the non-MCV tail — an assumption of uniformity within the tail that is usually far better than assuming uniformity across the whole distribution, precisely because the MCV list already carved out the skew.
  • scalarltsel()/scalargtsel() (range predicates, col < const): locate which histogram bucket the constant falls into, then linearly interpolate within that bucket assuming uniform density — the equi-depth construction (§8a) means each bucket already represents equal sample mass, so the interpolation error is bounded by how non-uniform the data is inside a single bucket, not across the whole column.
  • eqjoinsel() (join equality, a.x = b.y): compares both sides' MCV lists directly against each other for the overlapping values (getting an exact contribution for the most frequent matches), then estimates the non-MCV remainder using both sides' n_distinct, roughly 1 / max(n_distinct_a, n_distinct_b) — the classic containment assumption that every value on the smaller-domain side has a match on the larger.

Every one of these is a local estimate for one predicate or one join edge. The planner then combines multiple predicates on the same table by multiplying their selectivities — the independence assumption from §6, applied mechanically — and it combines join selectivities up the join tree, meaning an error at a leaf is inherited, not corrected, by every ancestor node. A histogram misestimate of 3× at the bottom of a four-way join tree, multiplied through three more join-selectivity estimates each contributing their own smaller errors, routinely reaches the 100-1000× range at the top — this is the precise mechanism behind the "errors compound multiplicatively" claim in §1, and it is why the single most useful planner debugging technique is reading EXPLAIN ANALYZE from the bottom of the plan up, looking for the first node where estimated and actual rows diverge sharply — everything above it is downstream noise.

(c) The cost model: page and CPU unit costs

Every path's cost is a sum of terms in one currency: an abstract unit calibrated so that one sequential page fetch = 1.0 (seq_page_cost). Every other constant is defined relative to it, in postgresql.conf:

GUCDEFAULTMEANING

On SSD/NVMe there is no seek arm, so the physical gap shrinks to near 1:1 for pure random reads — many operators running on SSD/cloud block storage set this to 1.1-1.5, and the difference materially shifts the seq-vs-index breakeven point (§15 lets you feel this directly).

cost_seqscan() is the simplest: pages × seq_page_cost + rows × cpu_tuple_cost (plus per-row qualifier evaluation cost). cost_index() is where effective_cache_size earns its keep, via the Mackert-Lohman formula (from a 1986 IBM paper on index scan costing with a finite LRU buffer): a large index scan re-reads some pages it already fetched, and the fraction of re-reads that hit cache versus hit disk again depends on how the index's working set compares to the effective cache size — the formula interpolates between "everything cached, cost ≈ pages" and "nothing cached, cost ≈ pages × random_page_cost" based on that ratio, which is exactly why a bigger effective_cache_size setting makes index scans look cheaper without touching a single actual byte of memory.

Pricing one index scan, term by termSTEP-BY-STEP

Two more distinctions matter for everything downstream: every path carries both a startup_cost (work before the first row can be returned — building a hash table, sorting) and a total_cost (cost to exhaust the path). A plan with a cheap startup but expensive total (e.g. an index scan) can beat a plan with a cheap total but expensive startup (e.g. a hash join needing to build first) whenever a LIMIT means most rows are never fetched — which is precisely why adding LIMIT 10 to a query can flip an entire plan from hash join to nested-loop-with-index, a fact every senior engineer has seen and this is the exact mechanism behind it.

(d) Path and RelOptInfo: cheap to create, one per strategy

Every base relation in the query gets a RelOptInfo (src/include/nodes/pathnodes.h) — a struct holding everything the planner knows about that relation: estimated rows, width, the list of restriction clauses, and — critically — a pathlist: every candidate physical strategy discovered so far for producing that relation's rows, each represented by a lightweight Path node carrying just startup_cost, total_cost, rows, pathkeys (the sort order it happens to produce, if any, for free), and parallel_safe/parallel_aware flags. A Path is deliberately not an executable plan — it carries no expression trees, no target lists, nothing expensive to build — precisely so the planner can generate many of them cheaply and only convert the single winner into a full Plan tree at the very end (createplan.c, stage 5 in §7).

add_path() is what keeps the search tractable: every time a new Path is proposed for a RelOptInfo, it is compared against every existing path in that relation's pathlist using Pareto dominance across (startup_cost, total_cost, sort order, parallel safety) — if an existing path is at least as good on every dimension, the new one is discarded; if the new one dominates an old one, the old one is discarded. A path only survives if it is the best on some dimension nothing else covers — this is why a slow-to-start, cheap-in-total hash join and a fast-to-start, expensive-in-total index scan can coexist in the same pathlist even though the hash join has a lower total cost: neither dominates the other once LIMIT or an outer nested loop might only need a few rows.

(e) Join order search: the exponential problem, tamed two ways

For n relations in a join, there are more distinct join orders and shapes than is practical to enumerate exhaustively once n grows past single digits. PostgreSQL's default strategy, standard_join_search() (joinpath.c/allpaths.c), is a bottom-up dynamic program in the System R tradition: build every possible RelOptInfo for joining 2 base relations (level 2), keeping only the non-dominated paths for each distinct pair via add_path; then build every way to join a level-2 result with one more base relation to reach level 3; and so on up to level n. Because each level only needs the surviving (non-dominated) paths from the level below, the DP prunes aggressively — but the number of distinct relation subsets it must consider still grows combinatorially, which is why join_collapse_limit and from_collapse_limit (default 8) exist: they cap how many explicit and implicit joins get flattened into one planning problem before the planner instead treats sub-groups as fixed units, trading optimality for tractability.

Past geqo_threshold (default 12) relations, PostgreSQL gives up on exhaustive DP entirely and switches to GEQO (src/backend/optimizer/geqo/) — a genetic algorithm that represents each candidate join order as a "chromosome" (a permutation of relations), evaluates its cost, and evolves a population of candidates through selection, crossover, and mutation across generations, converging on a good-but-not-guaranteed-optimal order in time that scales far better than factorial growth. This is a deliberate accuracy-for-speed trade: a 20-table ORM-generated join would take the DP path an impractical amount of planning time to solve exhaustively, so GEQO trades a small, usually-tolerable risk of a suboptimal join order for planning time measured in milliseconds instead of minutes.

(f) Generic vs custom plans: prepared statements

A parameterized prepared statement (PREPARE, or any protocol-level extended query with parameters) can be planned two ways: a custom plan, replanned fresh for the actual bound parameter values every execution (accurate selectivity, but pays planning cost every time), or a generic plan, planned once using generic assumptions about parameter selectivity and reused for every execution (near-zero planning cost, but blind to parameter skew). PostgreSQL's default (plan_cache_mode=auto) applies the 5-execution rule: it plans custom for the first five executions, tracks their average cost, and on the sixth execution compares that average against what a generic plan would cost — switching permanently to the generic plan only if it isn't meaningfully more expensive. This is exactly the kind of adaptive heuristic the rest of this chapter argues for: rather than assuming one strategy is always right, measure and decide per prepared statement. It is also a well-known trap for skewed parameters (§11's third incident) — if the first five executions happen to bind common values, the generic plan gets locked in and then silently misestimates every subsequent execution that binds a rare one.

MongoDB's row is worth dwelling on: instead of estimating selectivity at all, it measures candidate plans against real execution for a trial window and keeps the observed winner. That is a legitimate answer to the exact problem this chapter is about — it just moves the cost from "planning time, every time" (custom replanning) to "first few executions of each query shape" and trades statistical estimation error for actual measurement error, which is zero once trials complete. PostgreSQL's cost-based model chose the opposite bet: pay a small, amortized offline cost (ANALYZE) and get a plan without ever running the query twice — a good trade when query shapes are numerous and ad hoc (typical OLTP/analytics mix), a worse one when a small, stable set of query shapes run millions of times each (where measurement genuinely beats estimation).

ARC 10 · PERFORMANCE CHARACTERISTICS

Planning time itself has a cost curve

This chapter has spent nine sections on the cost of execution paths. Planning time has its own, separate performance envelope, and it's easy to forget it exists until an ORM-generated 20-table join spends more time being planned than executed:

  • DP join order search grows combinatorially in the number of relations: each level's join count depends on how many distinct, non-dominated sub-joins survived the level below, and in the worst case (no useful pruning from join clauses) the number of subsets considered approaches the classic bushy-tree enumeration bound — effectively exponential in relation count. join_collapse_limit/from_collapse_limit (default 8) exist purely to keep this bounded for typical queries.
  • GEQO past geqo_threshold=12 is polynomial in population size × generations, not combinatorial in relation count — the entire point of switching algorithms, at the cost of a small, usually acceptable chance of missing the true optimum.
  • Selectivity estimation is cheap per call (a catalog cache lookup plus a small binary search over an MCV list or histogram) but is called per predicate per candidate path — a query with many joins and many candidate paths per join can call it thousands of times during planning, which is measurable for genuinely huge queries even though each call is individually fast.
  • Generic plans amortize this to zero after the 5-execution threshold (§8f) — the entire reason they exist is that repeated planning of the identical query shape is pure waste once the risk of parameter-skew misestimation is judged acceptable.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents that all trace back to one bad number

Incident 1: the nightly reload that forgot to ANALYZE

A staging-to-production ETL job runs nightly: TRUNCATE staging_orders; COPY ten million fresh rows in. TRUNCATE resets the table's statistics visibility but does not itself trigger a fresh ANALYZE — the old pg_statistic row (or, on a brand-new table, PostgreSQL's built-in default guesses) persists until autovacuum's insert/analyze thresholds trip or someone runs it manually. A report query joining staging_orders against a small lookup table, planned against stale (tiny or default) row-count estimates, chooses a nested loop expecting a handful of outer rows. Against the real ten million, the same query that ran in 40 ms in a live-data test runs for 45 minutes in production. Fix, in order of leverage: an explicit ANALYZE staging_orders; as the last step of the load job (the correct fix — never rely on autovacuum's timing for a bulk operation you control); confirm via pg_stat_user_tables.last_analyze; consider autovacuum_analyze_scale_factor tuned lower for volatile tables.

Incident 2: the correlated columns that silently spilled a hash join

A logistics platform's shipments table has origin_country and origin_city — functionally dependent, exactly like §6's city/state example. A report filters both. The independence-assumption estimate is 15× too low; the planner sizes the build side of a hash join against that estimate and picks a work_mem-fitting single-batch plan. At execution, the real row count blows the hash table well past work_mem, forcing an unplanned multi-batch spill mid-query (chapter 17 explains the mechanism) — I/O the plan never budgeted for, on a query that ran fine for months until data volume crossed the threshold where the misestimate's absolute size started to matter. Fix: CREATE STATISTICS (dependencies, mcv) ON origin_country, origin_city FROM shipments; followed by ANALYZE — directly attacking the independence assumption rather than raising work_mem and hoping (which only delays the next crossing).

Incident 3: the prepared statement that only misbehaved for whale tenants

A multi-tenant SaaS app uses server-side prepared statements (via a connection pooler in session mode) for SELECT * FROM events WHERE tenant_id = $1 AND created_at > $2. tenant_id is extremely skewed: thousands of small tenants, a handful of whale tenants with 1000× the row count. The first five executions after a connection pool cycle happen to bind small tenants; PostgreSQL's 5-execution rule (§8f) locks in a generic plan tuned for the average (small) case — an index-driven nested loop. When a whale tenant's request lands on that same backend, the generic plan still runs, now scanning the index for a tenant matching a huge fraction of the table, one random heap fetch at a time — the exact 'completed' disaster from §4, self-inflicted by the plan cache's own heuristic. Fix: plan_cache_mode=force_custom_plan for this statement (accepting the replanning cost every execution in exchange for parameter-aware selectivity), or restructure so tenant identity is known at the SQL-text level rather than purely as a bind parameter.

First, the cost of a plain sequential scan — the baseline every other strategy is judged against:

Ccostsize.c — cost_seqscan(), simplified but faithful
void
cost_seqscan(Path *path, PlannerInfo *root, RelOptInfo *baserel)
{
    double spc_seq_page_cost;
    get_tablespace_page_costs(baserel->reltablespace,
                              NULL, &spc_seq_page_cost);

    /* Pure I/O term: every page, sequentially. */
    double run_cost = baserel->pages * spc_seq_page_cost;

    /* CPU term: evaluate quals + project every row that
     * survives the disk fetch -- this is why row width and
     * qual complexity matter even for a "simple" scan.        */
    double cpu_per_tuple = cpu_tuple_cost + baserel->baserestrictcost.per_tuple;
    run_cost += cpu_per_tuple * baserel->tuples;

    path->startup_cost = baserel->baserestrictcost.startup;
    path->total_cost = path->startup_cost + run_cost;
}

Now an index scan, where effective_cache_size enters via a Mackert-Lohman-style interpolation:

Ccostsize.c — cost_index(), simplified
void
cost_index(IndexPath *path, PlannerInfo *root, double loop_count)
{
    double indexSelectivity, indexCorrelation;
    amcostestimate(root, path, loop_count,
                     &indexStartupCost, &indexTotalCost,
                     &indexSelectivity, &indexCorrelation);

    double tuples_fetched = clamp_row_est(indexSelectivity * baserel->tuples);

    /* Mackert-Lohman: as the working set (pages_fetched) grows
     * past effective_cache_size, the EXPECTED fraction of
     * re-reads that hit cache falls -- this is what makes a
     * big index scan cost more per row than a small one, and
     * why effective_cache_size (never actually allocated!)
     * still changes the winning plan.                         */
    double pages_fetched = index_pages_fetched(tuples_fetched, baserel->pages,
                                          (double) path->indexinfo->pages, root);
    double max_IO_cost = pages_fetched * spc_random_page_cost;
    double min_IO_cost = 1.0 * spc_random_page_cost +
                        (pages_fetched - 1) * spc_seq_page_cost;

    /* indexCorrelation from pg_statistic: near 1.0 (physical
     * order tracks logical order) slides run_cost toward
     * min_IO_cost -- fewer distinct pages actually touched.    */
    double csquared = indexCorrelation * indexCorrelation;
    run_cost += max_IO_cost + csquared * (min_IO_cost - max_IO_cost);
}

Finally, the pruning rule that keeps path generation from exploding — every candidate strategy for a relation passes through this before it's allowed to survive:

Cpathnode.c — add_path(), the Pareto-dominance filter
void
add_path(RelOptInfo *parent_rel, Path *new_path)
{
    foreach(old_path, parent_rel->pathlist) {
        /* Does the OLD path dominate the new one on every axis
         * that matters -- cost, useful sort order, parallel
         * safety?  If so the new path can never win; drop it.  */
        if (costs_dominate(old_path, new_path) &&
            pathkeys_contained_in(new_path->pathkeys, old_path->pathkeys) &&
            old_path->parallel_safe >= new_path->parallel_safe)
        {
            return;  /* discard new_path -- it's strictly worse */
        }
        if (costs_dominate(new_path, old_path) && /* symmetric check */ ...)
            remove_old_path(parent_rel, old_path); /* old_path is now pointless */
    }
    parent_rel->pathlist = lappend(parent_rel->pathlist, new_path); /* survives */
}
WHY THE DEVELOPERS WROTE IT THIS WAY

1. Costs are estimates, so keep near-ties. add_path uses a small fuzz factor rather than exact comparison — two paths within ~1% of each other on cost are treated as tied and both may survive briefly, because the cost is only ever an estimate and a "definitely worse" path might actually win once real data disagrees with the statistics. 2. Separate cheap representation (Path) from expensive representation (Plan). Generating and comparing thousands of candidate Paths is affordable exactly because a Path carries no expression trees or target lists; only the single survivor pays the cost of becoming a full Plan in createplan.c. 3. Push physical properties (sort order, parallel safety) into the dominance test itself rather than bolting them on afterward — this is precisely why a slightly more expensive path that happens to produce useful sort order survives to be used for free by a merge join or an ORDER BY above it.
