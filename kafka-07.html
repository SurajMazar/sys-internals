APACHE KAFKA INTERNALS · CHAPTER 07

Consumer Groups &
the Rebalance Protocol

A consumer group is a set of independent JVMs, on different hosts, with no shared memory and no distributed lock, that must agree — continuously, as members come and go — on exactly which partitions each of them owns. This chapter derives the protocol that makes that agreement possible: the GroupCoordinator, the JoinGroup/SyncGroup handshake, the generation id that fences zombies, and the eager-vs-cooperative rebalancing decision that determines whether adding one consumer pauses your entire pipeline or just a tenth of it.

ARC 01 · THE PROBLEM

Who reads partition 7? Nobody can just ask.

A consumer group is Kafka's way of turning "N independent processes" into "one logical reader" of a topic. Every partition must be read by exactly one member of the group at a time — not zero (a stalled partition), not two (duplicate processing, out-of-order commits) — and that assignment must keep re-forming correctly as processes join, leave, crash, hang, or get redeployed, all without any of them sharing memory, without a distributed lock service most teams want to avoid operating, and without a human in the loop.

Unpack that and you get five requirements that pull against each other, the same way the process model's requirements did for a database server:

  • Exclusive ownership — for any partition, at most one live member processes it at a time, so an at-least-once pipeline doesn't become a knowingly-duplicate one.
  • Dynamic membership — consumers scale up and down with load, deploy in rolling fashion, and crash without warning; the group must reconverge on a new assignment every time.
  • Failure detection with no false negatives that hang forever — a dead member's partitions must eventually be reassigned, but a merely-slow member must not be evicted for being busy.
  • Fencing of zombies — a member presumed dead might not actually be dead (a long GC pause, a network partition); if it wakes up and keeps committing offsets under a stale view of the world, it must be rejected, not trusted.
  • Bounded disruption — the mechanism that reconverges the group should not itself become the outage; it should touch as little of the group's throughput as the membership change actually requires.

Unlike PostgreSQL's process model, there is no kernel here to hand you SIGCHLD and a guaranteed cleanup. Consumers run on different machines, possibly in different data centers, connected only by a TCP session to a broker. The entire problem is distributed coordination with an unreliable network, and Kafka's answer is to make one broker the single source of truth for one group's membership: the Group Coordinator.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Everything in this chapter is a special case of a problem you will meet again under other names: leader election (chapter 4's ISR), distributed locking (chapter 11's transaction coordinator), and cluster membership (chapter 14's KRaft controller quorum). Kafka solves all of them the same way — elect one arbiter, give it a durable log to record decisions in, and fence stale actors with a monotonically increasing epoch/generation number. Learn the shape here; you'll recognize it three more times.

DEEP CONTEXT · WHY THE ORIGINAL DESIGN WAS ZOOKEEPER-NATIVE

Kafka's earliest consumer (LinkedIn, 2011) didn't have a broker-side coordinator at all because it didn't need one yet — ZooKeeper was already in the cluster for broker metadata, and it offered ephemeral znodes and watches, which look exactly like "membership plus failure detection" for free. The mistake, visible only at scale, was letting every consumer instance independently recompute the full assignment from raw ZK reads whenever a watch fired. That's not a coordinator — it's N uncoordinated computations that happen to usually agree. §3 makes this concrete.

ARC 03 · NAIVE SOLUTION

Attempt #1: everyone computes their own assignment and hopes

Derive the architecture honestly, the way the original high-level consumer did. Keep a registry of live consumer ids (a directory of ephemeral files, or ZK znodes) and a known partition count. Every consumer, independently, on every membership change, recomputes: sort the consumer ids, sort the partitions, deal them out deterministically — no messages exchanged, no arbiter, just "if everyone reads the same inputs, everyone computes the same outputs."

pseudo-Javanaive_rebalance.java — the strawman, annotated
class NaiveConsumer {
    void onMembershipChanged() {
        // Every instance reads the SAME shared registry independently.
        List<String> liveIds  = registry.listConsumerIds(groupId);   // e.g. znode children
        List<Integer> parts   = metadata.partitionsFor(topic);

        Collections.sort(liveIds);
        int myIndex = liveIds.indexOf(myConsumerId);
        int share   = parts.size() / liveIds.size();

        /* No broker, no lock, no exchanged message — just local arithmetic
         * on a locally-read snapshot that is assumed to match everyone
         * else's locally-read snapshot at the SAME instant.            */
        myPartitions = parts.subList(myIndex*share, (myIndex+1)*share);
        stopConsuming(oldPartitions);
        startConsuming(myPartitions);
    }
}

This is not a strawman built to be knocked down cheaply — it is exactly what shipped in Kafka's 0.7/0.8 "high-level consumer," and it gets the common case right: when membership is quiet, every instance reads the same registry state and independently derives the same partition split, with zero coordinator load and zero round trips. ARC 04 · WHY IT FAILS

Agreement without communication is not agreement

The naive design's entire correctness argument rests on one unstated assumption: every consumer reads the registry at the same logical instant and computes the same list. Distributed systems theory has a name for why that assumption is false in practice — there is no shared clock, ZK watch delivery is not synchronized across clients, and a consumer can be slow to notice a change for reasons that have nothing to do with whether it is alive (a stop-the-world GC pause, a saturated NIC, a scheduler hiccup on a noisy-neighbor VM).

  • Split-brain windows are not rare edge cases, they're the normal transition state. Between "consumer C died" and "every survivor's watch has fired, re-read the registry, and recomputed," there is a window, often hundreds of milliseconds to seconds under load, during which some survivors still believe the old assignment and some believe the new one. Two consumers legitimately believe they own partition 7.
  • There is no fencing token. A consumer that computed the OLD assignment keeps committing offsets for partition 7 under that belief. If its commit lands after the new owner's commit, it silently overwrites a fresher committed offset with a stale one — the next restart re-processes everything since the stale mark, with no error, no log line, nothing to grep for.
  • The failure mode compounds with group size. Every membership change is an N-way herd: losing 1 of 200 consumers means all 200 refire their watch, all 200 re-list the registry, all 200 recompute. ZooKeeper serves 200 reads for a change that logically affects one consumer's share.
THE NUMBERS

Take a 200-consumer group reading 2,000 partitions, 10 per consumer at steady state, processing 5,000 messages/sec per partition. One consumer pauses for a 4-second GC (not even a crash — a normal G1 mixed collection under memory pressure). Its 10 partitions look "dead" to the registry watchers, who reassign them; when the paused consumer resumes, it doesn't know it was declared dead, and for whatever window remains before its own next watch fires, it keeps processing and committing those same 10 partitions concurrently with their new owner. At 5,000 msgs/sec × 10 partitions, that's up to 50,000 messages/sec of duplicate processing with no ordering guarantee between the two writers' offset commits — and the 200-way herd means the registry and its watch-delivery path, not the actual data plane, becomes the bottleneck during every such event.

Two structural defects, then: (1) no single arbiter whose decision is authoritative, so "who owns partition 7" has no canonical answer during a transition, and (2) no fencing token, so a stale actor cannot be told "you are wrong" — it has to independently discover it. §5 evaluates the candidates that fix this.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Three ways to get one authoritative answer

Whatever replaces "everyone computes independently" needs exactly one thing the naive design lacked: a single place where "the current assignment" is a fact, not an inference. Step through the candidates Kafka's designers actually had on the table circa the 0.9 redesign.

Candidates for "one authoritative answer"STEP-BY-STEP
THE CLINCHING ARGUMENT: A LOG YOU ALREADY HAVE, AN EPOCH YOU CAN CHECK CHEAPLY

Kafka already has a durable, replicated, ordered log primitive — it's the whole product. Candidate C reuses it: group state (membership, generation, committed offsets) is written to a partition of the internal __consumer_offsets topic, replicated exactly like any other partition, and the broker leading that partition is the coordinator, for free, with no new consensus system to operate. And because every request carries a generation id, the coordinator can reject a zombie's request in O(1) — an integer comparison — without ever having to prove the zombie is actually dead. §8 shows the exact fencing check.

ARC 06 · WHY THAT STILL HURTS

A correct coordinator still has to stop the world to change its mind

Centralizing the decision in a GroupCoordinator fixes correctness — there is now exactly one answer to "who owns partition 7," and stale answers are fenced by generation id. It does not, by itself, fix the cost of changing the answer. The original coordinator protocol (still the default many teams run today) pays a specific, quantifiable tax every time membership changes:

  • Every member must revoke everything before anyone gets anything back. The first design decision was the simplest correct one: when a rebalance starts, every member first gives up all of its partitions (calls the application's onPartitionsRevoked for its full set), rejoins with an empty ownership claim, and only then receives a brand-new assignment. Simple to reason about — there is never a moment where two generations' assignments coexist — but it means the entire group stops consuming for the duration of the rebalance, even the 99% of members whose partitions aren't moving at all.
  • The rebalance waits for the slowest member, by design. The coordinator can't finalize an assignment until it has heard from every member it currently believes is alive, or until rebalance.timeout.ms (in practice, max.poll.interval.ms) elapses. One straggler — a consumer mid-way through a slow batch — holds the whole group's JoinGroup phase open.
  • Assignment computation itself is serial and single-threaded. One elected member (the "leader") runs the assignment algorithm locally and ships the result back through the coordinator; for a large group this is still fast in absolute terms, but it's one more sequential step inserted into a path that already blocks every other member.
THE COST, MADE CONCRETE

Picture a 100-consumer group over 1,000 partitions, steady state, and one consumer is added to absorb growth — the most benign possible membership change, not a failure. Under the "revoke everything first" protocol, all 1,000 partitions stop being consumed, across all 100 consumers, for the full duration of the rebalance (typically hundreds of milliseconds to a few seconds, longer if any member is slow to rejoin or the group is large). That is a full-pipeline pause to accommodate a single, healthy, capacity-adding join. §8 quantifies exactly how much of that pause is structurally necessary and how much KIP-429 eliminates.

The fix keeps the coordinator (it's correct) and keeps generation fencing (it's cheap and correct) but changes exactly one thing: which partitions must be revoked before the group can make progress. That's the final architecture.

ARC 08 · INTERNAL IMPLEMENTATION

The state machine, the handshake, and who computes what

Four pieces, in order: (a) the group state machine and the JoinGroup/SyncGroup handshake that drives it, (b) the generation id fencing mechanism, (c) the assignor family and the eager-vs-cooperative split (KIP-429), (d) static membership (KIP-345).

(a) The group state machine and the join protocol

Every group lives in exactly one of five states, tracked by GroupMetadata on the coordinator broker: Empty → PreparingRebalance → CompletingRebalance → Stable, with Dead reachable from any of them once the last member leaves and the group is cleaned up. Step through a join from a cold start.

WHY ASSIGNMENT RUNS ON THE LEADER, NOT THE BROKER — A DELIBERATE CHOICE

The coordinator hands the full member list and subscriptions to exactly one member (the "leader" — ordinarily whichever member's JoinGroupRequest the coordinator processed first for this generation) and receives back only opaque assignment bytes in SyncGroupRequest. The broker never runs a line of assignment logic. This buys two things a broker-side implementation would not: assignment strategy can change (a new ConsumerPartitionAssignor) purely by upgrading the client jar, with zero broker changes or restarts, and teams can ship custom assignors (rack-aware, workload-aware) as ordinary application code. The price, which KIP-848 later decided was worth paying to remove, is that the broker has no visibility into why an assignment looks the way it does, and buggy client-side assignors are a client-side outage, not a broker-side one to patch centrally.

(b) Generation id: the fencing token that makes zombies harmless

Every successful rebalance increments the group's generationId by exactly one. From that point, every Heartbeat, OffsetCommit, and SyncGroup request a member sends must carry the generation it believes is current. The coordinator's check is a single integer comparison: if the request's generation is stale, it is rejected with ILLEGAL_GENERATION (or the member itself is unknown post-rebalance: UNKNOWN_MEMBER_ID). This is exactly the naive design's missing piece from §4 — a consumer that resumes from a long GC pause believing it still owns partition 7 will have its next offset commit rejected outright, rather than silently corrupting a fresher commit. The zombie doesn't need to be detected as dead; it only needs to be told it's wrong, cheaply, every time it tries to act.

(c) Assignors, and the eager/cooperative fork in the protocol (KIP-429)

The assignment algorithm is pluggable (partition.assignment.strategy); the assignment protocol (how much gets revoked before a rebalance can proceed) is a property of the algorithm's declared RebalanceProtocol. Play with the four shipped assignors below against a deliberately uneven subscription to see why the choice matters beyond just "balance."

Now the protocol split. Eager (the original protocol, and what RangeAssignor/ RoundRobinAssignor/StickyAssignor all use): every member revokes all of its partitions before rejoining, full stop. Cooperative incremental rebalancing (KIP-429, CooperativeStickyAssignor): members report their currently owned partitions in JoinGroupRequest; the coordinator/leader compute a target assignment; a member only revokes the specific partitions it's actually losing — everything it keeps, it keeps consuming from, uninterrupted, across two rebalance rounds instead of a single stop-the-world one.

(d) Static membership: skip the rebalance entirely (KIP-345)

Every rebalance so far assumed membership genuinely changed. But the single most common trigger in production is a consumer that is coming right back: a rolling deploy, a Kubernetes pod eviction and reschedule, a brief network blip. Setting group.instance.id to a stable string turns a member from dynamic (identity = an ephemeral member.id the coordinator hands out per session) to static (identity = your own configured string, valid across sessions). Two consequences follow directly: a static member's clean close() does not send a LeaveGroupRequest by default (suppressing the immediate rebalance a dynamic member's shutdown would trigger), and when it reconnects with the same group.instance.id before session.timeout.ms elapses, the coordinator recognizes it as the same member and hands back its same assignment — no JoinGroup, no new generation, no partition movement anywhere in the group. The rolling restart of a 200-consumer fleet, which under dynamic membership would fire roughly 200 sequential rebalances (one per pod as it restarts), becomes zero rebalances, provided each pod is back within the session timeout window.

SESSION.TIMEOUT.MS, HEARTBEAT.INTERVAL.MS, MAX.POLL.INTERVAL.MS — THREE TIMERS, THREE DIFFERENT FAILURES

These are not three redundant knobs for the same thing; each detects a different failure and fires on a different thread. heartbeat.interval.ms (default 3000 ms) is how often the client's dedicated background heartbeat thread — separated from the poll thread since KIP-62 — proactively pings the coordinator; it does no application work. session.timeout.ms (default 45000 ms) is the coordinator-side budget: if no heartbeat arrives within it, the member is presumed dead — this catches process crashes, network partitions, and (importantly) a JVM-wide stop-the-world pause that freezes the heartbeat thread too. max.poll.interval.ms (default 300000 ms = 5 minutes) is checked entirely client-side, on the heartbeat thread, independently of session timeout: if too long has elapsed since the application's own thread last called poll(), the client concludes its own processing loop is stuck or too slow, and proactively sends a LeaveGroupRequest itself — this is the one that fires when your record handler is doing something slow, not when the process or network has failed. Confusing these three is the single most common cause of the rebalance storms in §11.

ARC 09 · TRADEOFFS

Every message queue solves "who reads what," differently

Kafka's answer — client-computed assignment, broker-arbitrated membership, generation fencing — is one point in a design space every competing system also occupies. None of these dominate; each buys balance/ordering at a different price:

Read the table as a proof by exhaustion, the same way chapter 1 of the Postgres course reads its process-model table: per-partition ordering plus horizontal scale is not free anywhere — every system either drops ordering (SQS, RabbitMQ) or pays a coordination protocol to keep it (Kafka, Pulsar's key_shared, Kinesis's leases). Kafka's specific bet — durable log as the coordination substrate, client-computed assignment — is what makes rebalancing simultaneously correct and customizable, at the cost of a client-visible pause that §8's KIP-429 work exists entirely to shrink.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before you trigger a rebalance

The costs, from first principles:

  • Coordinator lookup: O(1) — Utils.abs(groupId.hashCode) % offsets.topic.num.partitions (default 50 partitions) picks the partition; its leader is the coordinator. Every client caches this after one FindCoordinatorRequest.
  • Assignment computation: O(P) for Range and RoundRobin (P = total partition-subscriptions, a single sorted pass); Sticky and CooperativeSticky do more work — a balancing pass that also minimizes movement against the previous assignment, closer to O(P log P) in practice — but this runs once, on one JVM (the leader), and is rarely the bottleneck.
  • Rebalance wall-clock time: bounded below by roughly two network round trips (JoinGroup, then SyncGroup) plus the leader's assignment compute time, and bounded above by rebalance.timeout.ms if any member is slow to rejoin. In practice: hundreds of milliseconds for small groups, low seconds for groups in the hundreds of members.
  • Heartbeat overhead: O(1) per member, every heartbeat.interval.ms; coordinator load scales O(M) with group size M, but a HeartbeatRequest is a handful of bytes — this is not where rebalancing costs come from.
  • The real cost is partition-seconds of paused consumption, not CPU or network: eager rebalancing pauses every partition in the group for the rebalance's duration; cooperative rebalancing pauses only the subset actually changing hands. The chart below makes that curve explicit.

MODEL, NOT MEASUREMENT

The curves are an analytic sketch: eager cost ≈ (total partitions) × (rebalance duration, which itself grows slowly with group size from coordinator/network fan-out); cooperative cost ≈ (partitions actually moved) × (rebalance duration) — and for a single member joining or leaving a group of size N, roughly 1/(N+1) of the partitions move. Note the honest edge case: for a mass event where every member restarts at once (a full rolling redeploy without static membership), cooperative's advantage shrinks, because "everyone's assignment changes" is close to eager's worst case too — cooperative rebalancing wins biggest on the routine, incremental churn (autoscaling, single-instance restarts), which is also the overwhelmingly common case in production.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents you will eventually meet

Incident 1: Uber's rebalance storms and the birth of uReplicator

Uber's engineering blog documented, in the mid-2010s, exactly the failure class §3–§4 derive: the original ZooKeeper-based high-level consumer's rebalancing caused cascading "rebalancing storms" in their Kafka-based replication pipeline (uReplicator), where a single consumer hiccup triggered a group-wide re-read-and-recompute that could itself take long enough to trigger further churn. Their fix was to move consumer group management for that specific replication workload onto Apache Helix, a purpose-built cluster-management framework, rather than keep fighting the herd effect inside the old consumer. It is a direct, published illustration of §4's math: at Uber's scale, the coordination overhead of the naive model, not the data plane, was the bottleneck.

Incident 2: KIP-345's motivating case — rolling restarts as a self-inflicted rebalance storm

The KIP-345 (static membership) proposal itself documents the production pattern that motivated it: routine operational events — a rolling deploy, a Kubernetes pod rescheduling after a node drain — were, under dynamic membership, indistinguishable from real failures to the coordinator. Every restarting pod's clean shutdown fired a LeaveGroupRequest, triggering a rebalance; multiplied across a fleet doing a rolling restart, this produced one rebalance per pod, back to back, each one pausing consumption for the whole group under the eager protocol that predated KIP-429. Static membership's entire value proposition, adopted widely once available in Kafka 2.3+, is turning "the fleet restarted" back into a non-event for the coordinator.

Incident 3: the silent-cascade rebalance storm from an oversized max.poll.records

A recurring, widely reported operational pattern (documented across Confluent's and multiple SRE teams' troubleshooting guides): a consumer's per-record processing time creeps up — a downstream call gets slower, a batch enrichment step is added — until max.poll.records (default 500) worth of processing routinely exceeds max.poll.interval.ms (default 300000 ms, but often tuned down without matching the workload). The client itself detects this and sends LeaveGroupRequest with reason "consumer poll timeout has expired"; the group rebalances; the evicted member's partitions land on survivors already close to their own processing budget, which then also trip the same timeout — a cascade that looks, from a lag-monitoring dashboard, like the whole cluster is unhealthy, when the actual defect is a single tuning mismatch. §15's simulator lets you trigger and then tune out exactly this pattern.

Scale context

LinkedIn — where Kafka and this consumer group protocol originated — has published, across multiple years of its engineering blog, throughput figures in the multiple-trillions-of-messages-per-day range across thousands of topics and consumer groups running the exact JoinGroup/SyncGroup machinery this chapter describes; at that scale, even a rebalance protocol that costs low single-digit seconds per event, multiplied across thousands of groups reorganizing during a data-center-wide deploy, is a capacity-planning line item, not a rounding error — the motivation behind both KIP-429 and the further broker-side rework in KIP-848 (§8, §13).

The state machine that everything else revolves around, simplified from GroupMetadata.scala but faithful to its shape:

ScalaGroupMetadata.scala — the group's five states
sealed trait GroupState { def validPreviousStates: Set[GroupState] }

case object Empty extends GroupState {          // no members; offsets may still be held
  val validPreviousStates = Set(PreparingRebalance)
}
case object PreparingRebalance extends GroupState { // waiting for (re)joins
  val validPreviousStates = Set(Stable, CompletingRebalance, Empty)
}
case object CompletingRebalance extends GroupState { // leader computing/shipping assignment
  val validPreviousStates = Set(PreparingRebalance)
}
case object Stable extends GroupState {         // steady state: everyone has an assignment
  val validPreviousStates = Set(CompletingRebalance)
}
case object Dead extends GroupState {          // group metadata removed / migrated
  val validPreviousStates = Set(Stable, PreparingRebalance, CompletingRebalance, Empty, Dead)
}

def transitionTo(groupState: GroupState): Unit = {
  assertValidTransition(groupState)   // throws if the edge isn't in validPreviousStates
  state = groupState
}

The coordinator's join handling, simplified from GroupCoordinator.scala — notice it dispatches on the group's current state, not just "did a JoinGroup arrive":

ScalaGroupCoordinator.scala — handleJoinGroup(), simplified
def handleJoinGroupRequest(groupId: String, memberId: String,
                          groupInstanceId: Option[String],
                          protocols: List[(String, Array[Byte])], ...): Unit = {
  group.inLock {
    group.currentState match {
      case Dead =>
        responseCallback(joinError(UNKNOWN_MEMBER_ID))

      case Empty | Stable =>
        // brand-new member, or membership genuinely changed -> start a rebalance
        addMemberAndRebalance(memberId, groupInstanceId, protocols, group)

      case PreparingRebalance =>
        // a rebalance is already being assembled -> fold this join into it
        updateMemberAndRebalance(memberId, protocols, group)

      case CompletingRebalance =>
        // leader is mid-SyncGroup; an unchanged member rejoining just gets
        // its pending assignment -- a CHANGED subscription forces a new round
        if (group.member(memberId).matches(protocols))
          completeAndScheduleNextHeartbeat(group, memberId)
        else
          addMemberAndRebalance(memberId, groupInstanceId, protocols, group)
    }
  }
}

private def maybeCompleteJoin(group: GroupMetadata): Unit = {
  if (group.notYetRejoinedMembers.isEmpty)     // everyone (re)joined
    completeJoin(group)                       // -> CompletingRebalance, pick leader
  // else: DelayedJoin keeps waiting, forced complete at rebalanceTimeoutMs
}

The client side: the leader — and only the leader — actually runs assignment logic, entirely inside its own JVM, simplified from ConsumerCoordinator.java:

JavaConsumerCoordinator.java — performAssignment(), simplified
protected Map<String, ByteBuffer> performAssignment(
        String leaderId, String assignmentStrategy,
        List<JoinGroupResponseMember> allSubscriptions) {

    ConsumerPartitionAssignor assignor = lookupAssignor(assignmentStrategy);
    Map<String, Subscription> subscriptions = parse(allSubscriptions);

    // Runs ENTIRELY on the leader's JVM. The broker never executes this --
    // it only relays the serialized result below via SyncGroupRequest.
    GroupAssignment assignment = assignor.assign(metadata, new GroupSubscription(subscriptions));

    return serialize(assignment.groupAssignment());
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Assignment logic ships in the client, not the broker. A new assignor is a jar upgrade, not a broker deploy — and it's the direct reason custom, workload-aware assignors are ordinary application code rather than a broker patch. 2. Fence by counting, not by proving. The coordinator never tries to determine whether a member is "really" alive or "really" still holds a partition — it just rejects anything tagged with a stale generationId. Cheap, and correct regardless of how wrong the zombie's internal state has become. 3. Separate the liveness signal from the progress signal. KIP-62 moved heartbeats to their own thread specifically so that "is the process alive" (heartbeat thread, session.timeout.ms) and "is the application keeping up" (poll thread, max.poll.interval.ms) could be independently tuned failure detectors instead of one conflated timeout — the exact distinction §8(d)'s callout and §11's Incident 3 depend on.
