Producer Internals: Batching,
Compression & Idempotence

Every producer.send(record) you have ever called returns almost instantly — not because the record reached a broker, but because a background thread you never see took over. This chapter opens KafkaProducer from the inside: the RecordAccumulator that buffers your records into per-partition batches, the BufferPool that recycles memory instead of feeding the GC, the Sender thread that drains and ships those batches, and the sequence-number machinery (KIP-98) that makes retrying a batch after a network failure safe instead of a duplicate.

ARC 01 · THE PROBLEM

One record, one round trip, is a throughput crime

Picture the most naive possible producer: your application calls send(), and that call opens a socket to the partition's leader broker, writes exactly one record, blocks until the broker replies, and only then returns. It is easy to write, easy to reason about — and it caps your entire producer's throughput at the network's round-trip time, no matter how fast your disks, your NIC, or your broker's CPU are. That is the problem this chapter exists to solve: how do you make record production a network-bandwidth-bound operation instead of a network-latency-bound one, without losing the guarantees an application actually needs?

Unpack "without losing the guarantees" and you get a short but demanding list, in tension with each other:

  • The calling thread must never block on the network for long. A web request handler, a stream processor's poll loop, an ETL job — none of them can afford to stall on a broker round trip for every record. send() has to return almost immediately, handing back a Future.
  • Eventual delivery must still be guaranteed. The record has to actually reach the broker's log, surviving transient network failures, a leader election, or a broker restart, via retries.
  • Per-partition ordering must survive those retries. If batch 2 for partition P is retried and lands before a not-yet-retried batch 1, every consumer of P now sees out-of-order data — silently.
  • Exactly-once semantics must be achievable for the applications that need it (financial ledgers, exactly-once stream topologies) despite the same unreliable network that makes retries necessary in the first place — a retry that actually succeeded server-side must not become a duplicate.

Batching, background threading, and idempotence are not three unrelated Kafka features. They are one coherent answer to one problem: decouple the application's timeline from the network's timeline, while keeping delivery and ordering guarantees intact across that decoupling. The rest of this chapter derives that answer from first principles, then reads the real Java client that implements it.

WHY THIS MATTERS FOR THE REST OF THE COURSE

Everything downstream of the producer — the broker's request-handling threads (chapter 8 of a full broker course), replication and the in-sync-replica set (chapter 6), and the consumer's fetch path and offset management (chapter 5, next) — is shaped by decisions this chapter makes. acks, retries, and idempotence are producer-side knobs, but their consequences (duplicate records, reordering, data loss windows) are what every consumer-side guarantee has to be built to tolerate or prevent. Get the producer's model right in your head, and the consumer chapter's hardest question — "how do I preserve ordering across a rebalance?" — will already have half its answer.

DEEP CONTEXT · THE PAPER THAT STARTED IT

Kreps, Narkhede & Rao's 2011 NetDB paper, "Kafka: a Distributed Messaging System for Log Processing," is explicit that per-message request/response overhead was the enemy from day one: LinkedIn's activity-tracking volume made batching — on both the produce and fetch paths — a stated design requirement, not an optimization bolted on later. The RecordAccumulator/Sender split you'll read in §13 is a much more disciplined descendant of that original idea, but the motivating math (amortize one network round trip over many records) has not changed in over a decade.

ARC 03 · NAIVE SOLUTION

Attempt #1: send, block, repeat

Derive it honestly, the way you would before ever seeing KafkaProducer's real source. The simplest correct producer opens one connection to a partition's leader and does exactly one thing per record: writes it, waits for the acknowledgment, then returns control to the caller.

pseudocodenaive_producer.pseudo — the strawman, annotated
function send(record):
    conn = connectionFor(record.partition.leader)   // one TCP conn per broker
    req  = buildProduceRequest([record])          // exactly ONE record inside
    conn.write(req)                               // blocking socket write
    resp = conn.readResponse()                    // BLOCKS until broker replies —
                                                    // this is one full network round trip
    if resp.error: retry(record)                // still on the SAME calling thread
    return resp.offset                            // caller resumes only now

// application code:
for event in stream:
    send(event)   // ← the whole app thread is idle here, every single call

This is not a strawman built to be knocked down for sport — it is the architecture you should arrive at first, and it already gets the hard part right: correctness. There is no reordering risk (nothing is ever in flight concurrently), no partial-batch bookkeeping, and no memory-pool accounting. Every record is durably acknowledged before the next line of application code runs. If your entire workload is a few records per second, this design is arguably correct enough and simple enough to ship. It fails the instant you need throughput, and §4 puts a number on exactly how badly.

ARC 04 · WHY IT FAILS

Throughput capped at 1/RTT, independent of message size

With exactly one outstanding request at a time, the calling thread's loop is: write, wait one round trip R, read, repeat. No matter how small the payload or how much spare bandwidth the NIC has, you cannot issue request n+1 until request n's response arrives. Throughput is therefore capped at 1/R requests per second — a pure latency bound, structurally incapable of using available bandwidth.

THE NUMBERS

At R = 2 ms (a same-datacenter round trip — realistic for a broker a few hops away), the ceiling is 1 / 0.002 = 500 requests/sec, full stop — whether each record is 50 bytes or 50 kilobytes. Batch 1,000 records into that same request and the ceiling becomes 500,000 records/sec at the same network cost, because the round trip is now amortized over 1,000× more payload. Cross-region, where R ≈ 40 ms is common, the naive design's ceiling collapses to ~25 requests/sec — and batching is no longer an optimization, it is the only way to get usable throughput out of a WAN link at all.

There is a second, independent cost that batching also happens to fix: per-request overhead that has nothing to do with the network wire. Each write is a separate syscall (write()/send() crossing into kernel space), a separate TCP/TLS framing operation, and on the broker side a separate pass through request parsing, log-append bookkeeping, and (if acks=all) a separate replication round trip to followers. A tiny record pays the same fixed CPU tax as a large one — so sending a million one-record requests burns roughly a million times that fixed cost, whereas sending a thousand thousand-record requests burns it a thousand times. The naive design isn't just RTT-bound; it is also paying the maximum possible multiple of a fixed per-request CPU overhead on both ends of the connection.

So the requirement is now precise: keep records flowing to the broker in large, infrequent requests instead of small, frequent ones — without making the calling application thread respsonsible for assembling that batch synchronously. §5 works through the candidate shapes for doing that, in order of increasing sophistication, and eliminates the ones that don't hold up.

ARC 05 · BETTER SOLUTIONS, EXAMINED

Queue vs synchronous batching vs a decoupled two-thread pipeline

Three shapes are worth taking seriously before landing on the real one. Step through the deck; each candidate is rejected for a concrete, specific reason, not vibes.

Candidates for decoupling send() from the networkSTEP-BY-STEP

The design that survives is a fully decoupled two-thread pipeline. The calling application thread does the cheap, CPU-only work synchronously — serialize the key/value, run the partitioner, append the serialized bytes into an in-memory structure — and then returns a Future immediately. A single dedicated background thread, the Sender, is the only thread that ever touches a socket; it continuously drains whatever batches have accumulated and ships them, independently of how many application threads are calling send() or how fast they're calling it.

WHY THE DECOUPLING HAS TO BE STRUCTURAL, NOT JUST "ASYNC"

It is tempting to think "just make the network call async" is enough — fire the write, register a callback, move on. But that alone doesn't produce batching: it produces N concurrent one-record requests instead of N sequential ones, which fixes latency-boundedness but not the per-request overhead problem from §4, and creates a much harder ordering problem (N requests racing to the same partition with no ordering discipline between them). The RecordAccumulator exists precisely to convert "many application threads calling send() whenever they want" into "one dense, ordered, per-partition byte buffer that a single I/O thread drains deterministically." Batching requires a buffer with an owner; async alone only requires a callback.

ARC 06 · WHY THAT STILL COSTS

The bill: bounded memory, held-open batches, and a new ordering hazard

Decoupling the application thread from the network does not make buffering free. Three costs are load-bearing for the rest of this chapter, and each one maps directly to a producer config you already set without, perhaps, knowing precisely why it exists.

  • The accumulator's memory is finite, on purpose. buffer.memory (default 33554432 — 32 MB) bounds how much unacknowledged data the producer will hold in client-side RAM at once. When every byte of that pool is allocated to batches still awaiting an acknowledgment (broker slow, network congested, or a partition's leader unreachable), the next call to send() cannot get a buffer — and blocks the calling thread for up to max.block.ms (default 60000) before throwing a TimeoutException. This is back-pressure, and it is the classic symptom operators learn to recognize: application threads stuck inside send(), not because Kafka is "down," but because nothing has freed accumulator memory fast enough.
  • Held batches cost real memory for real time. A batch sits in the accumulator from its first appended record until its acknowledgment is processed — under acks=all that includes the full round trip to the leader and the leader's wait for in-sync-replica acknowledgment. Slow followers or a struggling leader directly inflate how long buffer memory stays pinned, which is exactly how a downstream slowdown becomes a producer-side memory problem (§11 has the incident).
  • Compression trades CPU for those held bytes — smaller batches in memory and on the wire, at the cost of CPU cycles spent compressing (and, on the broker, sometimes decompressing) every batch. §8 works through which codec buys how much of which trade.
  • Retries reopen the ordering question §1 already flagged. If a batch to partition P fails and is retried while a later batch to the same partition is already in flight on a different connection slot, and max.in.flight.requests.per.connection > 1, the retried (earlier) batch can land at the broker after the later one — silent reordering, with no error raised anywhere. Idempotence (§8) is precisely the mechanism that closes this hole, which is why increasing in-flight concurrency was historically dangerous and is now safe.

None of these costs are defects — they are the visible price of the throughput §4 demanded. §7 lays out the architecture that pays that price deliberately, and §8 goes inside each piece.

Exactly one thread — the Sender — ever writes to a broker socket or reads a broker response. Every other thread's job ends at RecordAccumulator.append(). ARC 08 · INTERNAL IMPLEMENTATION

Inside send(): accumulation, batching economics, partitioning, compression, idempotence

This is the deep core of the chapter — five mechanisms that together make the architecture in §7 actually work, in the order data flows through them.

(a) The two-thread design, precisely

KafkaProducer.send() runs almost entirely on the calling thread, synchronously: it invokes the configured serializers on the key and value, calls the partitioner to choose a TopicPartition, and then calls RecordAccumulator.append(). Inside append(), the accumulator looks up (or lazily creates) the Deque<ProducerBatch> for that partition in its ConcurrentMap<TopicPartition, Deque<ProducerBatch>>, and — holding only that one partition's deque lock, never a global lock — tries to append to the last (newest) batch in the deque. If that batch has room, the bytes are copied in and append() returns a Future immediately: the calling thread never touches the network. If the last batch is full or doesn't exist yet, the accumulator must allocate a fresh ProducerBatch, and that means asking the BufferPool for memory.

BufferPool.allocate(size, maxTimeToBlock) is the mechanism worth understanding precisely, because it is where §6's "held-open memory" cost becomes a concrete blocking call. For the common case — requesting exactly batch.size bytes, the standard allocation unit — the pool keeps a free list of already-allocated, same-sized ByteBuffers that were returned when earlier batches were fully acknowledged and released. Handing back a pooled buffer is a list-pop, not a fresh allocation — this is the whole point: without pooling, a high-throughput producer would allocate and then garbage-collect one new direct/heap buffer per batch, continuously, which is exactly the kind of allocation churn a low-latency system cannot afford. Only when the free list is empty and the pool's total outstanding memory is below buffer.memory does it perform an actual new allocation. When neither is possible — the pool is fully committed and nothing has been freed — the calling thread blocks on a condition variable inside allocate(), waiting for another thread to deallocate space, for up to max.block.ms (default 60000). Exceed that and allocate() throws, which surfaces to the application as the send() call itself throwing TimeoutException.

(b) Batching economics: what linger.ms actually buys

batch.size (default 16384 bytes, 16 KB) is a per-partition ceiling on a single ProducerBatch's byte size — not a global cap, and not a record-count cap. linger.ms (default 0) is deliberately added latency: even a batch with room left will be considered "ready" to send once it has sat for linger.ms milliseconds, trading a few milliseconds of application-visible latency for a chance to accumulate more records first. The throughput payoff is exactly the RTT-amortization math from §4 — more records per request means fewer requests to pay the fixed per-request cost (network framing, broker log-append bookkeeping, and under acks=all, one full ISR replication round trip) against.

THE COUNTERINTUITIVE FACT: linger.ms=0 STILL BATCHES UNDER LOAD

Set linger.ms=0 and a batch is "ready" the instant it has any data — but "ready" only means eligible to be drained by the Sender thread, not "closed to further appends." A batch keeps accepting new records for as long as it has room and the Sender hasn't gotten around to draining it yet. Under load, while one request for partition P is in flight to its broker (occupying one of P's limited in-flight slots), new records for P keep arriving and appending into whatever batch is now at the back of P's deque — so by the time a slot frees up and the Sender drains the next batch, it may already contain far more than one record. Batching under load is therefore a consequence of the async pipeline's drain cadence relative to the append rate — not of the linger timer, which only matters when arrivals are too sparse to fill a batch between drains on their own.

(c) Partitioning: murmur2 hashing vs the sticky partitioner (KIP-480)

For a keyed record, DefaultPartitioner's built-in hashing takes murmur2(key) % numPartitions — deterministic, so every record with the same key always lands on the same partition, which is what makes per-key ordering meaningful downstream. For an unkeyed record, there is no key to hash, and the original behavior (pre-2.4) was strict round robin: record 1 to partition 0, record 2 to partition 1, record 3 to partition 2, and so on. Round robin looks fair, but it is catastrophic for batching: at a low-to-moderate production rate, by the time record 4 comes back around to partition 0, partition 0's previous batch has almost certainly already been drained (it only had one record in it) — so nearly every batch ships with a single record, regardless of batch.size.

KIP-480's sticky partitioner fixes this by inverting the strategy: pick one partition at random and send every unkeyed record to it until its current batch is actually sent, only then picking a new random partition for the next batch. Concretely: with 10 partitions, a 16 KB batch.size, and a modest production rate, round robin can produce roughly 10× more requests, each carrying roughly a tenth as much data, compared to sticky partitioning funneling the same records into full or near-full batches on whichever single partition is currently "it." The records still spread evenly across partitions over time (each partition gets its turn), but the request-count and CPU-overhead cost of that spreading drops by roughly an order of magnitude at typical batch sizes.

(d) Compression: applied per batch, not per record

The producer compresses an entire ProducerBatch's bytes as one unit — never individual records — which matters for two reasons: compression works far better with more context (a whole batch of similarly-shaped records compresses much better than each record alone), and the broker stores and serves the compressed batch as-is on the normal path. Consumers fetch the same compressed bytes the producer sent; the broker does not decompress and recompress per request. This is why compression is close to free for the broker in steady state — it never touches the payload bytes at all on the happy path.

THE MESSAGE-FORMAT-CONVERSION CLIFF

The "broker never touches the payload" property only holds when the batch's on-disk record format and compression can be served to a fetch request unchanged. If a broker must down-convert a batch — most commonly because an old consumer only understands an older message format, or a topic still has segments written under an older on-disk magic byte — it has no choice but to decompress the whole batch, rewrite per-record fields (offsets, timestamps), and recompress before it can serve the response. That is genuine CPU work happening synchronously on a request-handling path that is normally near-zero-cost, and it is a real, recognizable category of production incident: broker CPU spikes and request queues back up the moment a legacy consumer (or a topic straggling on an old format) forces conversion at scale.

(e) Idempotence: PIDs, epochs, and sequence numbers (KIP-98)

With enable.idempotence=true (the default since Kafka 3.0), the producer's first act on initialization is an InitProducerId request to a broker acting as transaction coordinator, which returns a Producer ID (PID) and an initial epoch. From then on, every ProducerBatch sent for a given partition carries (PID, producerEpoch, baseSequence), with the sequence number simply incrementing per batch, per partition. On the broker, the partition leader's ProducerStateManager keeps, for each PID it has seen on that partition, the metadata (sequence range) of the last five batches it accepted. When a batch arrives:

  • If its sequence range exactly matches one already recorded — this is a retried batch that actually succeeded server-side before the producer's timeout fired and triggered a retry — the broker returns success without appending it again. The duplicate is silently absorbed.
  • If its sequence range has a gap relative to what's recorded (a batch appears to be missing), the broker rejects it with OutOfOrderSequenceException, because accepting it would mean a hole in the partition's data that the producer can never fill in later once the PID's sequence has moved past it.

Why five entries specifically? It has to cover the maximum number of batches that could plausibly be in flight to one broker simultaneously for one PID — and Kafka enforces max.in.flight.requests.per.connection ≤ 5 whenever idempotence is enabled (default is exactly 5), so five tracked entries is sufficient headroom to recognize a duplicate no matter which of the up-to-five outstanding batches is the one being retried. Before KIP-98, safe ordering under retries required capping in-flight requests at exactly 1 — one outstanding request per connection, so a retry could never race past something sent later. Idempotence is precisely what makes 5-way pipelining safe again: the broker's own bookkeeping, not the producer's request ordering, is now what guarantees no duplication and no silent gap.

(f) acks, retries, and delivery.timeout.ms

Three settings govern how hard the producer tries, and how it defines "given up":

  • acks=0 — fire and forget. The producer doesn't wait for any broker response at all; a dropped connection or a down leader loses the record with no error ever surfacing to the application.
  • acks=1 — the leader acknowledges after appending to its own local log, before followers have replicated it. If the leader crashes before replication completes, an already-acknowledged record can be lost when a follower without it is elected leader.
  • acks=all (-1, the default since KIP-679 / Kafka 3.0) — the leader withholds acknowledgment until the record is replicated to enough in-sync replicas to satisfy min.insync.replicas. This is the strongest durability the producer can ask for, at the cost of waiting on the slowest replica in the in-sync set on every batch.

retries defaults to an effectively unbounded value (Integer.MAX_VALUE), which sounds alarming until you see what actually bounds it: delivery.timeout.ms (default 120000, introduced by KIP-91 to replace an earlier, ambiguous combination of retry-count and per-request timeout configs) is a single overall budget covering linger time + all retry attempts + all request round trips for a batch, from the moment it's first ready to send. Once that budget is exhausted, the batch's Future fails — regardless of how many individual retries remain available — which gives applications one clean, predictable number to reason about instead of multiplying out retry count by per-request timeout by hand. And the ordering hazard from §6 remains real background context here: retries with max.in.flight.requests.per.connection > 1 and idempotence disabled can still reorder batches at the broker — which is exactly why the modern default pairs acks=all with enable.idempotence=true rather than leaving either as an opt-in.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

RecordAccumulator.append() is amortized O(1) per record: a deque lookup by partition key (hash map, O(1) average) plus an append to the tail batch's backing buffer (a bounded memcopy). Draining is O(batches currently ready) per Sender iteration — it never has to scan records, only batch headers. Neither operation's cost scales with how many records have accumulated total, only with how many are touched this call or this drain — which is exactly why the design tolerates arbitrarily high sustained throughput as long as buffer.memory and broker acknowledgment keep pace.

  • Compression's CPU/bytes trade, worked: a batch of JSON-ish event records (moderate field repetition) at roughly 200 bytes/record typically compresses to somewhere around 90–120 bytes/record with snappy or lz4 (roughly 2×), and closer to 55–75 bytes/record with gzip or a mid-level zstd (roughly 3×) — at correspondingly higher CPU cost per batch for the latter two. The bytes saved reduce both network egress and the broker's on-disk footprint identically, since the broker stores the batch compressed.
  • GC behavior: without BufferPool's free list, a sustained-throughput producer would allocate one new batch.size-sized buffer per ProducerBatch, continuously — direct allocation churn that either pressures the GC (heap buffers) or fragments native memory (direct buffers). The free list of pre-sized, already-allocated buffers turns that into pop/push against an existing pool, so steady-state throughput does not correlate with GC pause frequency the way a naive per-batch allocator would.
  • Throughput vs RTT, restated as a formula: for one partition with a single in-flight request, throughput ≈ (average batch bytes) / (RTT + broker processing time). Growing average batch bytes — via linger.ms, via a larger batch.size, or simply via more load naturally filling batches faster (§8b) — is the only lever that increases throughput without also increasing RTT itself.

The curve is an analytic sketch — batch bytes ≈ min(batch.size, arrival-rate × (linger.ms + effective RTT)), throughput ∝ batch bytes / (RTT + fixed per-request overhead), latency ≈ linger.ms + RTT + overhead — tuned to match the qualitative shape reported in Kafka's own producer-tuning benchmarks. ARC 11 · REAL-WORLD PRODUCTION

Four incidents you will eventually meet

Incident 1: batching as a founding requirement, not an afterthought

Kreps, Narkhede & Rao's original 2011 Kafka paper is explicit that LinkedIn's activity-tracking pipeline made per-message request overhead a first-order design constraint from the start — the paper calls out batching on both produce and consume paths as central to achieving the throughput their tracking volume demanded, at a time when comparable messaging systems paid a full request/response round trip per message. Every config this chapter covers is a descendant of that founding requirement.

Incident 2: BufferPool exhaustion cascading into application thread-pool exhaustion

A common, recognizable operational pattern at scale: a downstream slowdown — an in-sync replica falling behind, a broker under disk or network pressure, or simply a spike in acks=all latency — causes batches to sit unacknowledged in the accumulator longer than usual. Because buffer.memory is finite, sustained production against a slow broker fills it; new send() calls start blocking inside BufferPool.allocate(). If the calling application is, say, a web service that publishes to Kafka synchronously from a bounded HTTP request-handling thread pool, those blocked threads pile up one by one until the pool itself is exhausted — and now HTTP requests are timing out for reasons that have nothing to do with Kafka's own availability. This exact shape — a slow downstream dependency exhausting an upstream bounded thread pool through a blocking client call — is a recurring theme in large-scale engineering postmortems (the pattern shows up under different names at companies like Uber and Netflix in their public backpressure writeups), and the producer-side fix is almost always the same: keep max.block.ms tight, monitor buffer.available.bytes/bufferpool-wait-time metrics as a leading indicator, and use a bounded async queue in front of the producer rather than calling send() synchronously from a latency-critical request path.

Incident 3: the message-format-conversion CPU cliff

The category of incident flagged in §8d is a real and recurring one: a broker upgraded ahead of its consumers, or a topic with segments still written under an older on-disk record format, forces down-conversion on every fetch a lagging consumer makes. Because that conversion means decompress → rewrite per-record metadata → recompress, done synchronously on what is normally a near-zero-cost request path, broker CPU can spike sharply and request queues back up cluster-wide — not because of a bug, but because an assumption ("the broker just streams bytes off disk") silently stopped holding for one consumer group. The standard operational guidance — upgrade consumers before (or at worst, alongside) brokers, and monitor the broker's MessageConversionsPerSec/format-conversion metrics — exists directly because of this incident shape.

Incident 4: defaulting to correctness over raw throughput

Kafka 3.0 flipping enable.idempotence and acks to their safer defaults (KIP-679) codifies guidance the community and Confluent had already been giving for years: the throughput cost of acks=all plus idempotence, versus acks=1 with idempotence off, is commonly in the range of roughly single digits to on the order of 20% lower throughput and a few extra milliseconds of p99 latency within a single datacenter — a cost most pipelines should happily pay, because the alternative is data loss or silent duplication that is far more expensive to detect and repair after the fact than to prevent up front. Cross-region, where RTT dominates far more than the replication wait itself, the relative cost of acks=all shrinks further, since you were already RTT-bound. The operational lesson: only opt back out of the safe defaults for the specific minority of pipelines (best-effort metrics, high-volume telemetry where an occasional lost or duplicated record is genuinely inconsequential) where the throughput is worth more than the guarantee — and say so explicitly in the config, rather than inheriting a weaker guarantee by accident from an old default.

JavaRecordAccumulator.java — append(), simplified
public RecordAppendResult append(TopicPartition tp, byte[] key, byte[] value, long maxTimeToBlockMs) {
    Deque<ProducerBatch> dq = getOrCreateDeque(tp);      // per-partition, from a ConcurrentMap
    synchronized (dq) {                                // lock is scoped to ONE partition's deque
        ProducerBatch last = dq.peekLast();
        if (last != null) {
            FutureRecordMetadata frm = last.tryAppend(key, value, this.time.milliseconds());
            if (frm != null) return new RecordAppendResult(frm, false);  // fit — no network involved
        }
    }
    // last batch didn't exist or didn't have room: allocate fresh memory
    ByteBuffer buffer = this.free.allocate(this.batchSize, maxTimeToBlockMs);   // MAY BLOCK the calling thread
    synchronized (dq) {
        ProducerBatch batch = new ProducerBatch(tp, buffer, this.time.milliseconds());
        FutureRecordMetadata frm = batch.tryAppend(key, value, this.time.milliseconds());
        dq.addLast(batch);                              // new batch becomes the tail — future appends target it
        return new RecordAppendResult(frm, true);
    }
}
JavaBufferPool.java — allocate(), the blocking-wait path
public ByteBuffer allocate(int size, long maxTimeToBlockMs) throws InterruptedException {
    synchronized (this) {
        if (size == poolableSize && !free.isEmpty())
            return free.pollFirst();                 // free-list hit: no allocation at all

        int freeListBytes = free.size() * poolableSize;
        if (this.availableMemory + freeListBytes >= size)
            return freeUp(size);                        // enough headroom: allocate fresh (or reclaim)

        /* Pool is fully committed. Park this thread on a per-request Condition
         * until another thread's deallocate() frees enough bytes, or time out. */
        Condition moreMemory = this.lock.newCondition();
        long remainingMs = maxTimeToBlockMs;
        while (this.availableMemory < size) {
            boolean woken = moreMemory.await(remainingMs, MILLISECONDS);
            if (!woken) throw new TimeoutException(
                "Failed to allocate memory within the configured max.block.ms.");
        }
        return freeUp(size);
    }
}
JavaSender.java — run(), one iteration
void runOnce() {
    // 1. Which partitions have a batch ready (full OR linger elapsed) AND a free in-flight slot?
    ReadyCheckResult ready = this.accumulator.ready(this.metadataCache, now);

    // 2. Pull those batches out of the accumulator, grouped by destination broker —
    //    one Produce request per broker, carrying many partitions' batches at once.
    Map<Integer, List<ProducerBatch>> batches =
        this.accumulator.drain(this.metadataCache, ready.readyNodes, this.maxRequestSize, now);

    for (Map.Entry<Integer, List<ProducerBatch>> e : batches.entrySet())
        sendProduceRequest(e.getKey(), e.getValue());   // occupies one in-flight slot per request

    // 3. Poll the network client — this is where responses complete batch Futures / callbacks.
    this.client.poll(pollTimeout, now);
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Lock scope is per-partition, never global. append() only ever synchronizes on one partition's deque, so a burst on partition 7 never blocks an append to partition 2 — throughput scales with partition count, not with a single global mutex. 2. Blocking lives at the memory boundary, not the network boundary. The calling thread can only ever be made to wait inside BufferPool.allocate() (a local resource with a clear, bounded budget, max.block.ms) — never inside a socket read, which would have an unboundable wait tied to broker/network health instead of a config the caller controls. 3. The broker owns the safety net idempotence needs. Rather than trusting the producer to never double-send (impossible to guarantee over an unreliable network), ProducerStateManager puts the deduplication decision on the one side of the connection that actually knows what was durably committed — the same "judge by ground truth, not by client-side promises" instinct you'll see again in the consumer's offset-commit protocol next chapter.
