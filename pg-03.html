POSTGRESQL INTERNALS · CHAPTER 03

The Page:
On-Disk Layout, Byte by Byte

Every row you have ever inserted, updated, or deleted eventually resolves to a write inside an 8 KB region of bytes — the page — whose internal geometry has been essentially unchanged since the 1980s. This chapter takes one page apart field by field: the header that describes it, the array of pointers that indexes it, the tuples that fill it, and the arithmetic that decides when it's full.

ARC 01 · THE PROBLEM

Rows are not bytes until something decides how

A relation is a logical abstraction — an unordered set of rows with named, typed columns. A disk is a physical abstraction — a flat address space of fixed-size blocks that can only be read or written a whole block at a time. Between those two abstractions sits a problem every storage engine must solve exactly once, and get exactly right: given a variable number of variable-length rows, some of which must physically coexist in multiple versions at once, pack them into fixed-size blocks such that any single row can be found, added, or removed without rewriting its neighbors.

Unpack the constraints and each one independently rules out a lot of obvious designs:

  • Rows vary in length. A text column might hold 3 bytes or 3,000. A row store cannot assume a fixed stride the way an array of C structs can.
  • Rows must be found cheaply, by physical address. Every index entry, every t_ctid chain link (chapter 4), and every cached execution plan needs a way to say "this exact row" that survives the page being rewritten around it — otherwise every index would need updating every time a neighboring row moved.
  • The unit of I/O is not the unit of data. The storage manager (chapter 9) reads and writes in block-sized units — 8 KB by default — completely independent of how big any one row is. A 40-byte row and a 4,000-byte row both live inside some 8 KB block, sharing it with whatever else fits.
  • Deletions and updates must not require rewriting the block. A page that held 40 rows a minute ago and holds 38 now cannot shift 8 KB of memory on every delete — the physical layout has to tolerate holes.
  • The layout must be self-describing. A page read cold from disk, with no other context, must carry enough metadata inside itself to reconstruct where every row starts, how long it is, and how much room is left — because the process reading it might not be the process that wrote it.

Every one of these constraints is answered, in PostgreSQL, by a single artifact: the page, laid out with a discipline called the slotted page. Every subsystem you will study from here forward — MVCC visibility (chapter 4), the buffer manager (chapter 9), the free space map, index access methods, even the WAL record format (chapter 10) — is defined in terms of operations on this one structure. Get the page wrong in your mental model and everything built on top of it stops making sense; get it right and an enormous amount of PostgreSQL's behavior becomes derivable rather than memorized.

WHY THIS MATTERS FOR THE NEXT 18 CHAPTERS

Heap pages, B-tree pages, GiST pages, hash pages, even the pages inside pg_xact's SLRU segments — all of them share the same first 24 bytes (PageHeaderData) and the same line-pointer-array convention. Learn one page format and you can read the hex dump of almost anything PostgreSQL ever writes to disk. That is exactly what this chapter's simulator lets you practice.

ARC 02 · HISTORICAL CONTEXT

The slotted page is older than PostgreSQL itself

The page format you're about to dissect was not invented for PostgreSQL — it is a refinement of an idea already a decade old when the POSTGRES project began. Understanding where it came from clarifies why certain design choices (indirection through a pointer array, growth from opposite ends of the block) were never really up for debate; they were the accumulated lesson of the systems that came before.

DEEP CONTEXT · WHY THE INDIRECTION SURVIVED FOUR DECADES

Every one of these systems converged on the same shape independently because the underlying constraints — fixed block size, variable row size, physical addresses that must remain stable while the block's contents shuffle around — don't change with the decade. What has changed is what gets layered on top: MVCC (1999), HOT (2008), and page checksums (2013) are all additive refinements to the same 1970s skeleton — none of them required changing the fundamental header/line-pointer/tuple-data shape you'll build byte-by-byte in §8.

ARC 03 · NAIVE SOLUTION

Attempt #1: an array of fixed-size C structs

Derive it honestly, the way an engineer would who had never seen a database internals course. If every row has the same shape, storage is trivial: define a C struct, and a table is just fwrite()-ing an array of them. Addressing a row is a multiplication.

Cnaive_rowstore.c — the strawman, annotated
typedef struct {
    int32  id;
    char   name[32];      /* fixed-width — pad or truncate */
    int32  balance_cents;
} FixedRow;             /* sizeof(FixedRow) == 40, ALWAYS */

void write_row(FILE *f, int64 row_num, FixedRow *r)
{
    /* addressability is a multiplication — no metadata needed */
    fseek(f, row_num * sizeof(FixedRow), SEEK_SET);
    fwrite(r, sizeof(FixedRow), 1, f);
}

void delete_row(FILE *f, int64 row_num)
{
    /* no room to mark "deleted" separately from "never written" —
     * zero the slot and hope zero id never means a real row      */
    FixedRow empty = {0};
    fseek(f, row_num * sizeof(FixedRow), SEEK_SET);
    fwrite(&empty, sizeof(FixedRow), 1, f);
}

This is not a joke architecture — Ingres itself started closer to this than you might expect, and countless embedded and log-structured formats still use fixed-slot arrays for genuinely fixed-shape records (a ring buffer of sensor readings, for instance). It gets real things right: O(1) addressing with no metadata lookup, no pointer chasing, and trivial sequential scans. The problem is what it assumes away.

ARC 04 · WHY IT FAILS

Three assumptions the fixed-slot array makes, and how each collapses

Every one of these is quantifiable — this is not aesthetic disapproval, it's arithmetic that a storage engineer has to be able to produce on a whiteboard.

1. Fixed width forces you to pay for the worst case, every row, forever

A char name[32] field must be sized for the longest name you will ever store. Suppose the true distribution of names averages 11 bytes. Every row pays for 32 regardless:

THE NUMBERS

Waste per row ≈ 32 − 11 = 21 bytes. Across 10,000,000 rows that's 210 MB of pure padding for one column — and that's before counting the mirror-image failure: the one customer whose name is 40 bytes long, which the fixed-width field cannot store at all without truncation or an escape hatch (an overflow pointer, which is exactly the indirection this design was trying to avoid).

2. Deletion creates holes with no bookkeeping for reuse

Zeroing a slot doesn't shrink the file — balance.dat is still N × 40 bytes, most of it now representing rows that don't exist. A future insert must either scan the file for a zeroed slot (an O(n) scan in the worst case, competing with every other backend doing the same scan) or simply append forever, in which case the file grows without bound even while the live row count stays flat — the exact failure mode operators call bloat, arrived at here from first principles rather than from a MVCC-specific cause.

3. There is nowhere to put a second version of a row

This is the one that actually kills the design for a transactional database, and it previews chapter 4 directly. Suppose transaction A opens a snapshot and reads row 42. Transaction B then updates row 42 and commits. If an update is implemented as "overwrite in place" — the only thing a fixed-slot array supports — transaction A's next read of row 42 sees B's committed value, a value that did not exist when A's snapshot was taken. That is a non-repeatable read, and no amount of locking fixes it without serializing every reader behind every writer (the same head-of-line blocking chapter 1 already rejected for a different reason). A general-purpose transactional store needs somewhere for the old version to keep living until no active snapshot can see it — and a rigid array of same-size, same-address slots has no spare room to keep a second copy of anything.

So the requirements sharpen: variable-length storage, address stability across compaction, and room for multiple physical versions of one logical row. Three candidate designs try to answer this. Two get eliminated.

ARC 05 · BETTER SOLUTION, CANDIDATES EXAMINED

Overflow chains vs. log-structured vs. the slotted page

Step through the three real candidates. Each solves the fixed-slot array's problems differently, and each has a production database built around it today (§9 makes the comparison concrete) — but only one was available to, and chosen by, the 1986 POSTGRES design.

Three ways to hold variable-length, addressable, versionable rowsSTEP-BY-STEP
THE CLINCHING ARGUMENT: A LEVEL OF INDIRECTION

The slotted page's genius is one sentence: a physical row address is not a byte offset — it's a small integer that names a slot, and the slot holds the byte offset. Compacting a page (moving tuple bytes around to merge holes) only ever rewrites the slot's stored offset; every index entry and every t_ctid that references "block 402, slot 7" stays valid, because slot 7's identity never changes even when the bytes it points to move. This is the same trick as a filesystem inode, a Java object handle, or a page table entry — indirection is how you get mobility without invalidating references, and it's exactly what §7 formalizes as the line-pointer array.

ARC 06 · WHY THAT STILL COSTS

The slotted page's own bill

The winning design is not free either — internalize these costs now, because §10 and §11 quantify and troubleshoot exactly these effects in production.

  • Every tuple pays a 4-byte tax. Each ItemIdData line pointer costs 4 bytes regardless of how small the tuple is. A table of 8-byte rows (say, a bare integer primary key with no other columns) pays roughly 50% overhead just for indirection, on top of the ~23-byte tuple header itself (§8) — the true minimum cost of one heap row is closer to 30-something bytes no matter how small the payload.
  • Dead slots don't disappear on delete — they wait. A DELETE cannot immediately erase a line pointer, because a concurrent index scan might still be mid-flight holding that TID (chapter 4's MVCC visibility rules again). The slot is marked LP_DEAD and lingers until VACUUM proves no index references it, then flips to LP_UNUSED. Until that happens, the tuple's bytes still occupy the page — visible bloat that a naive reader of pd_lower/pd_upper would not expect.
  • Compaction is not free, and it must hold an exclusive lock. Reclaiming the holes left by dead tuples (PageRepairFragmentation()) means physically shifting bytes within the page while holding its buffer content lock exclusively — a real, if brief, pause for anyone else wanting to touch that page.
  • External fragmentation is real even when total free bytes look sufficient. Ten small holes of 20 bytes each sum to 200 free bytes, but a new 150-byte tuple can't use any of them individually — only a compaction (or the next vacuum pass) turns scattered holes into one usable gap.
THE CENTRAL TENSION THIS CHAPTER RESOLVES

Every subsequent design decision in this chapter is a negotiation between three things pulling in different directions: keep the header small (so it doesn't eat into usable space), keep tuple addresses stable (so indexes never need updating just because a page got tidied up), and keep the free-space calculation a single cheap subtraction (so every insert doesn't have to walk the page to find room). §7 shows the shape that satisfies all three; §8 shows the exact bytes.

ARC 07 · FINAL ARCHITECTURE

One page, four regions

Every PostgreSQL page — heap, B-tree, GiST, hash, sequence, even the pages backing an SLRU like pg_xact — is divided into the same four regions, in the same left-to-right order, with two of them growing toward each other. Click any region to see exactly what lives there, which struct governs it, and what happens when it fills up.

Notice the deliberate asymmetry that makes this work: the line-pointer array and the tuple-data area grow toward each other from opposite ends of the same block. That single design choice is what makes free space a one-line calculation rather than something that has to be tracked separately as items come and go — as long as both arrays only ever grow (never get compacted mid-flight without updating both boundaries atomically), the gap between them is the free space, exactly.

WHY THIS GENERALIZES TO INDEX PAGES TOO

A B-tree leaf page uses the identical header, the identical line-pointer array, and the identical grows-toward-each-other layout — the "tuples" are just index tuples (key + heap TID) instead of full rows, and the special space holds a BTPageOpaqueData with sibling-page links and a page-split cycle ID. One page format, reused for every access method PostgreSQL ships, is why bufpage.c's functions (PageAddItem, PageGetFreeSpace, PageIndexTupleDelete) are called from heap, B-tree, hash, and GiST code alike.

ARC 08 · INTERNAL IMPLEMENTATION

The real bytes: three structs and one algorithm

Now the mechanism at the level you'd need to patch it: (a) PageHeaderData field by field, (b) the ItemIdData line pointer's packed bit layout, (c) HeapTupleHeaderData's 23-byte header and the null bitmap, and (d) exactly how PageAddItemExtended() decides where a new tuple goes.

(a) PageHeaderData — 24 bytes that describe the whole page

Csrc/include/storage/bufpage.h — PageHeaderData
typedef PageXLogRecPtr PageXLogRecPtr;  /* split into two 32-bit halves —
                                             see callout below */

typedef struct PageHeaderData
{
    PageXLogRecPtr  pd_lsn;             /* [0..7]   LSN of last change to this page  */
    uint16          pd_checksum;        /* [8..9]   FNV-1a page checksum, or 0     */
    uint16          pd_flags;           /* [10..11] PD_HAS_FREE_LINES | PD_PAGE_FULL
                                             | PD_ALL_VISIBLE                */
    LocationIndex   pd_lower;           /* [12..13] offset to end of line pointer array */
    LocationIndex   pd_upper;           /* [14..15] offset to start of tuple data       */
    LocationIndex   pd_special;         /* [16..17] offset to start of special space    */
    uint16          pd_pagesize_version;/* [18..19] page size (assumed multiple of 256)
                                             packed with the layout version  */
    TransactionId   pd_prune_xid;       /* [20..23] oldest XID that MIGHT make some
                                             tuple here prunable, or 0       */
    ItemIdData      pd_linp[FLEXIBLE_ARRAY_MEMBER]; /* line pointers start at byte 24 */
} PageHeaderData;

Every field earns its place. pd_lower and pd_upper are the two numbers that matter most operationally: free space is pd_upper − pd_lower, full stop — no scan, no separate free space counter to keep in sync, just a subtraction of two 2-byte integers already sitting in the buffer you have pinned. pd_flags' PD_HAS_FREE_LINES bit is a pure optimization: without it, finding a reusable LP_UNUSED slot for a new tuple would mean scanning the whole line-pointer array on every insert; the flag lets an insert skip straight to appending when it's known there's nothing to reuse. pd_prune_xid plays the same role one level up: it lets a backend decide, in O(1), whether scanning this page's tuples for prunable garbage is even worth attempting (§16 asks you to derive exactly how).

WHY pd_lsn IS SPLIT INTO TWO 32-BIT HALVES

An XLogRecPtr is a 64-bit integer, which on most platforms wants 8-byte alignment. If PageHeaderData started with a naturally-aligned 8-byte field, the whole struct would need to begin at an 8-byte-aligned address for every field access to be efficient — a constraint the buffer manager would then have to guarantee everywhere a Page pointer is taken. Splitting the LSN into two uint32 halves (PageXLogRecPtr) sidesteps the requirement entirely: the struct only ever needs 4-byte alignment, which is trivially true for buffers allocated as arrays of BLCKSZ-sized chunks. A small, deliberate sacrifice of "natural" typing for a layout guarantee.

(b) ItemIdData — a 4-byte pointer, packed to the bit

Csrc/include/storage/itemid.h — the line pointer
typedef struct ItemIdData
{
    unsigned   lp_off:15,      /* byte offset of tuple, from page start   */
               lp_flags:2,   /* LP_UNUSED=0 LP_NORMAL=1 LP_REDIRECT=2
                                 LP_DEAD=3 — see below                  */
               lp_len:15;    /* byte length of tuple                    */
}
__attribute__((packed))
ItemIdData;                       /* exactly 32 bits, no padding */

/* LP_NORMAL:   lp_off/lp_len describe a live tuple
 * LP_REDIRECT: lp_off holds the OFFSET NUMBER of another line pointer
 *              on this same page (the HOT-chain "follow me" pointer,
 *              not a byte address!) — lp_len is unused
 * LP_DEAD:     the tuple is gone, but the SLOT is kept because an
 *              index might still hold this TID; data isn't reclaimed
 *              until PageRepairFragmentation() runs
 * LP_UNUSED:   an empty slot available for PageAddItemExtended() to
 *              reuse without growing pd_lower                       */

Fifteen bits gives a maximum addressable offset of 215 = 32,768 — comfortably larger than the default 8,192-byte page and still larger than the maximum page size PostgreSQL supports at all (32 KB, via --with-blocksize). That headroom is not an accident: the field width was chosen to exactly cover the compile-time-configurable range of BLCKSZ, and not one bit more, because every spare bit here is multiplied by every tuple on every page in the cluster.

(c) HeapTupleHeaderData — 23 bytes, then an optional bitmap, then MAXALIGN

Csrc/include/access/htup_details.h — the tuple header
typedef struct HeapTupleHeaderData
{
    union {
        struct {
            TransactionId t_xmin;      /* [0..3]   inserting transaction's XID   */
            TransactionId t_xmax;      /* [4..7]   deleting/locking XID, or 0     */
            union {
                CommandId    t_cid;    /* [8..11] command id within xmin's xact, */
                TransactionId t_xvac;  /*         OR old-style VACUUM FULL xid   */
            } t_field3;
        } t_heap;
        DatumTupleFields t_datum;      /* alt. view when used as a bare Datum    */
    } t_choice;

    ItemPointerData t_ctid;            /* [12..17] TID of newer version, or self */

    uint16 t_infomask2;             /* [18..19] #attrs (11 bits) + HOT/KEYS   */
                                        /*          bits — see below              */
    uint16 t_infomask;              /* [20..21] HEAP_HASNULL, HEAP_HASVARWIDTH,
                                             HEAP_XMIN_COMMITTED, HEAP_XMAX_*,
                                             HEAP_UPDATED, HEAP_COMBOCID ...  */
    uint8  t_hoff;                  /* [22]     header size incl. null bitmap,
                                             MAXALIGN'd — where columns start */
    /* ^^^^^^^^^^^^^^^^^^^^^^^ 23 bytes, fixed ^^^^^^^^^^^^^^^^^^^^^^^ */

    bits8 t_bits[FLEXIBLE_ARRAY_MEMBER]; /* NULL bitmap — present only if
                                                HEAP_HASNULL is set          */
    /* column data begins at byte t_hoff, MAXALIGN'd */
} HeapTupleHeaderData;

Twenty-three bytes and not one more: t_xmin and t_xmax (4 bytes each) are the two fields chapter 4's entire visibility engine is built on — every "can transaction X see this row" question reduces to comparing these against a snapshot. t_ctid is 6 bytes (a BlockIdData pair of uint16s plus an OffsetNumber) and self-referential on an untouched tuple — it only points elsewhere once an update creates a newer version and needs to chain to it. The null bitmap is the one genuinely variable-length part of the header: it exists at all only if HEAP_HASNULL is set in t_infomask, costs ceil(natts / 8) bytes when present, and is followed by padding out to a MAXALIGN boundary (8 bytes on essentially every modern platform) before the first column's bytes begin — t_hoff is precisely that final, aligned offset.

WHY COLUMN ORDER CHANGES ROW SIZE — DERIVE IT

Each column's bytes must start at an address matching its type's alignment requirement (1 byte for bool/char, 2 for smallint, 4 for int/real, 8 for bigint/timestamp/double precision). PostgreSQL lays columns out in declared order — unlike some engines, it never silently reorders your CREATE TABLE to minimize padding. Put a boolean immediately before a bigint and up to 7 padding bytes get inserted between them to satisfy the bigint's 8-byte alignment; repeated across a table with that column order and a table with columns sorted widest-first, the difference compounds row by row. HARDWARE COROLLARY: FREE SPACE ISN'T ALWAYS USABLE FREE SPACE

PageGetHeapFreeSpace() — the function hio.c's RelationGetBufferForTuple() actually calls before committing to a page — doesn't just return pd_upper − pd_lower. If there is no reusable LP_UNUSED slot (PD_HAS_FREE_LINES unset), it subtracts sizeof(ItemIdData) up front, because inserting will need a brand-new line pointer too. And the space actually consumed for the tuple itself is MAXALIGN(size), not the raw tuple length — so pd_upper can drop by a few bytes more than the tuple's own lp_len suggests. Both details matter the moment you're debugging why a page reports "enough" free space yet an insert still fails.

ARC 09 · TRADEOFFS

The same problem, five storage engines, five answers

Every serious database engine solves "pack variable rows into fixed blocks, keep addresses stable" — the differences reveal what each system optimized for at design time.

RocksDBImmutable, sorted SSTable blocks; no in-place update, ever writes are always sequential appends no line-pointer bookkeeping needed reads may check multiple levels (read amplification) background compaction instead of VACUUM

Read it as a proof by exhaustion: somewhere, every engine pays for the fact that rows don't naturally line up with blocks. PostgreSQL's specific bet — keep multiple physical tuple versions in the heap itself rather than reconstructing old versions from an undo log — trades disk-space bloat (fixed by a background process, VACUUM) for lock-free, undo-free reads and near-instant transaction rollback (an aborted transaction simply leaves its tuple invisible; nothing needs to be undone). InnoDB and Oracle made the opposite bet: keep the primary structure lean, pay the cost on the read path when a transaction needs an old version. Neither bet is wrong; they optimize for different steady states.

ARC 10 · PERFORMANCE CHARACTERISTICS

Numbers you can predict before benchmarking

The page format's performance envelope, derived rather than measured:

  • Lookup within a page: O(1) given a line-pointer index (offset number) — dereferencing ItemIdData[i] is one array access. Finding a row by value within a page, with no index, is O(n) in the number of live line pointers — exactly the cost a sequential scan pays per page.
  • I/O granularity matches page size by design. A single pread() pulls in the entire 8 KB page — header, line-pointer array, and tuple data together — so once a page is in the buffer pool, every tuple on it is already resident; there is no second I/O to "fetch the row" the way there might be with a pointer to external storage.
  • Cache-line locality is decent, by accident of size. PageHeaderData (24 bytes) fits comfortably in a single 64-byte CPU cache line; the line-pointer array is a tight, contiguous 4-bytes-per-tuple run that prefetches well when scanning sequentially through offset numbers — a deliberate side benefit of packing ItemIdData into exactly 32 bits rather than a more "natural" 8-byte struct.
  • Tuple density is the real lever on sequential scan throughput. A page holds roughly (BLCKSZ − 24) / (MAXALIGN(tuple_size) + 4) tuples. Halving the average tuple size roughly doubles tuples-per-page, which roughly doubles rows delivered per pread() — the chart below makes this concrete against a fixed disk bandwidth budget.
  • NUMA/TLB effects live one layer up, in the buffer pool (chapter 9) — the page format itself has no opinion about which core touches which buffer, but a page's small, fixed size is exactly what makes the buffer pool's bookkeeping (one BufferDesc per 8 KB frame) tractable at gigabyte-to-terabyte scale.

ARC 11 · REAL-WORLD PRODUCTION

Three incidents this chapter explains completely

Incident 1: silent corruption nobody could prove, until checksums existed

A storage-layer bit flip — bad DIMM, RAID controller firmware bug, a cloud block-storage glitch — corrupts one byte inside an already-written page. Without data_checksums enabled, PostgreSQL has no way to detect this until something downstream notices: a B-tree traversal that walks off into garbage, a tuple whose t_hoff now points past the page, or — the genuinely dangerous case — nothing crashes at all, and a query just returns a subtly wrong number for months. Checksums (introduced in 9.3, 2013) close this gap: every page write computes an FNV-1a-based checksum over the page (with pd_checksum itself zeroed during the calculation) and stores it in pd_checksum; every read back into a buffer recomputes and compares, raising "invalid page in block %u of relation %s" on mismatch rather than serving corrupt bytes. PostgreSQL 18 changed initdb's default to enable checksums on new clusters — a tacit admission that the historical "off by default" stance had cost more in silent corruption than it saved in the small (roughly low-single-digit percent) CPU overhead of computing them. Operationally: pg_checksums (added in 12) can enable or verify checksums offline; pg_stat_database.checksum_failures tracks how many mismatches a running cluster has caught.

Incident 2: the column-order storage surprise

A team runs pg_total_relation_size() against a table and finds it meaningfully larger than summing declared column widths would suggest — sometimes 15–20% larger for tables that interleave boolean and timestamp columns. The root cause, once traced through pg_column_size() on individual rows, is exactly §8's alignment padding: every bool sitting immediately before an 8-byte-aligned column wastes up to 7 bytes per row, and PostgreSQL never reorders your declared column order to fix this for you (unlike, say, a columnar engine's storage-layer optimizer). This is a well-documented, independently rediscovered pattern in the community — reordering a table's columns from narrowest-mixed-in to widest-first, with no semantic change whatsoever, has repeatedly been shown to shrink storage by measurable double-digit percentages on wide, padding-heavy tables. The fix requires an actual table rewrite (there is no ALTER TABLE ... REORDER COLUMNS) — typically a CREATE TABLE ... AS SELECT with columns re-listed in alignment-friendly order, then a rename swap.

Incident 3: "database files are incompatible with server" after a binary swap

An operator restores a physical backup — pg_basebackup output or a filesystem snapshot — taken from a server compiled with a non-default --with-blocksize (some data-warehouse-style deployments build with a larger BLCKSZ specifically to shrink the line-pointer-to-tuple overhead ratio on huge, append-mostly tables) onto stock packaged binaries. The server refuses to start: the control file and every page's pd_pagesize_version encode the compiled-in page size, and there is no negotiation — unlike, say, SQLite, which stores its page size in the file itself and can in principle be read by a build compiled for a different default. BLCKSZ is a whole-cluster, compile-time invariant: every replica and every binary that will ever touch a given data directory must agree on it, which is precisely why cloud providers who offer a non-default block size ship it as a distinct product tier rather than a runtime knob.

Cbufpage.h — the accessor macros everything else calls
#define PageGetLower(page) \
    (((PageHeader) (page))->pd_lower)
#define PageGetUpper(page) \
    (((PageHeader) (page))->pd_upper)

static inline Size
PageGetHeapFreeSpace(Page page)
{
    Size space = PageGetUpper(page) - PageGetLower(page);
    if (space < sizeof(ItemIdData))
        return 0;             /* couldn't even fit one more line pointer */

    /* PD_HAS_FREE_LINES unset ⇒ no reusable slot ⇒
     * an insert will need a BRAND NEW line pointer, so
     * pre-charge it against the space we report          */
    if (!PageHasFreeLinePointers(page))
        space -= sizeof(ItemIdData);
    return space;
}
Cbufpage.c — PageAddItemExtended(), the placement decision
OffsetNumber
PageAddItemExtended(Page page, Item item, Size size, OffsetNumber offnum, int flags)
{
    PageHeader phdr = (PageHeader) page;
    Size    alignedSize = MAXALIGN(size);          /* pad up to 8-byte boundary */
    int     lower, upper;
    OffsetNumber limit = PageGetMaxOffsetNumber(page) + 1;

    /* 1. Find a place in the line-pointer array: reuse the
     *    first LP_UNUSED slot if PD_HAS_FREE_LINES says one
     *    exists, otherwise this tuple gets offset "limit"
     *    (append) and pd_lower must grow.                   */
    OffsetNumber targetOff = FindReusableLinePointer(page, limit);
    bool reusing = (targetOff != InvalidOffsetNumber);
    if (!reusing) targetOff = limit;

    lower = phdr->pd_lower + (reusing ? 0 : sizeof(ItemIdData));
    upper = phdr->pd_upper - alignedSize;           /* tuple data grows DOWN     */

    if (lower > upper)
        return InvalidOffsetNumber;             /* not enough room, caller
                                                    * tries another page        */

    /* 2. Copy the tuple's bytes just below the new pd_upper. */
    memcpy((char *) page + upper, item, size);

    /* 3. Point the (possibly reused) line pointer at it.      */
    ItemId itemId = PageGetItemId(page, targetOff);
    ItemIdSetNormal(itemId, upper, size);

    /* 4. Commit both boundaries together — this is the moment
     *    "free space" changes for every future reader.        */
    phdr->pd_lower = lower;
    phdr->pd_upper = upper;
    return targetOff;
}
Cchecksum_impl.h — the mixing function (simplified, faithful in structure)
#define N_SUMS 32                        /* 32 parallel FNV-1a-style accumulators */

static inline uint32
pg_checksum_mix(uint32 sum, uint32 next_word)
{
    sum ^= next_word;
    sum *= 0x01000193;                   /* FNV prime — cheap, well-mixed */
    return sum;
}

uint16
pg_checksum_page(char *page, BlockNumber blkno)
{
    uint32 sums[N_SUMS];
    checksum_init_sums(sums, blkno);        /* seed with block number so two
                                             identical pages in different
                                             blocks checksum differently  */

    /* Sweep the whole page as 32-bit words, round-robin across
     * the 32 accumulators — spreads any single-bit corruption
     * across the final combined value instead of hiding it in
     * one accumulator's blind spot.                            */
    for (int i = 0; i < BLCKSZ / sizeof(uint32); i++)
        sums[i % N_SUMS] = pg_checksum_mix(sums[i % N_SUMS], ((uint32 *) page)[i]);

    uint32 result = checksum_combine(sums);   /* fold 32 accumulators into 1 */
    return (uint16) (result ^ (result >> 16)) ?: 1; /* never return 0 —
                                             0 means "no checksum" */
}
WHY THE DEVELOPERS WROTE IT THIS WAY — THREE CHOICES TO STEAL

1. Commit both boundaries in one place, at the end. pd_lower and pd_upper are only ever updated together, after the tuple's bytes are already safely copied — a reader that glimpses the page mid-modification (which shouldn't happen under the buffer content lock, but defense in depth matters) never sees a half-updated boundary pair. 2. Reuse is a search, not a pointer. FindReusableLinePointer() walking for an LP_UNUSED slot — gated by the PD_HAS_FREE_LINES flag so it's skipped entirely when known-empty — keeps the common case (no reuse available) cheap while still bounding line-pointer-array growth in workloads with steady churn. 3. Checksums spread the damage on purpose. Round-robining across 32 accumulators means a corruption anywhere in the page perturbs the final checksum unpredictably rather than being diluted by a single running sum — cheap insurance against the specific failure mode of "a whole class of corruption happens to leave a simple checksum unchanged."
