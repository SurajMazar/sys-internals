UBER ENGINEERING INTERNALS · CHAPTER 04

The Dispatch Problem:
Matching Riders to Drivers

Chapter 2 gave you a way to ask "which drivers are near this rider?" in microseconds. Chapter 3 gave you a trustworthy, reconciled answer to "where is each driver, right now?" Neither chapter told you which driver should actually get which rider. That decision — dispatch — is where a spatial index and a location pipeline turn into an actual marketplace clearing trades, thousands of times a second, under constraints that make it far subtler than "give the rider whichever car is closest."

ARC 01 · THE PROBLEM

Assignment, not lookup

"Find nearby drivers" (chapter 2) is a lookup problem: one query, one answer, no side effects. Dispatch is an assignment problem: deciding which of several riders gets which of several drivers, where every assignment you make changes what's available for every assignment you make next. That distinction is the entire reason this chapter exists as a separate, harder problem from geospatial search.

State the constraints precisely, because every design in this chapter is a response to exactly these five:

  • Exclusivity. A driver can serve at most one rider at a time. Assigning driver D to rider A and rider B simultaneously is not a rare bug to tolerate — it is a correctness violation with a real-world consequence (a driver shows up for the wrong person, or two people).
  • Locality. An assignment across town is useless — the rider waits longer than if no car had been sent. Every candidate match is implicitly bounded by a maximum acceptable pickup distance or time.
  • Perishability. A rider who waits too long cancels; a driver who idles too long goes offline. Neither side of this market can be "held in inventory" — an unmatched request is a lost/degraded outcome, not a queued one.
  • Continuous arrival. Requests and idle drivers appear and disappear asynchronously and constantly — there is no natural "batch boundary" handed to you by the problem; any batching is a design decision this chapter has to justify.
  • Global vs. local optimality. The obviously simple strategy — assign each request to its closest idle driver, one request at a time — optimizes each decision in isolation while potentially producing a worse total outcome than a strategy that looks at several requests together. Section 4 makes this precise with a worked numeric counterexample.
WHY THIS IS A MARKETPLACE PROBLEM, NOT A ROUTING PROBLEM

It is tempting to think dispatch is "just" a shortest-path query — send the closest car. Chapter 5 shows that even measuring "closest" correctly requires real routing. But dispatch itself is a level above that: it is a combinatorial assignment over a live two-sided market, where the objective (minimize total rider wait, maximize fulfilled requests, keep drivers utilized) is a property of the whole assignment, not any one match. That is precisely the kind of problem where greedy, one-at-a-time decisions are provably suboptimal — and where the fix costs real latency, which riders can feel.

ARC 02 · HISTORICAL CONTEXT

From a dispatcher's radio to an assignment solver

Ride-hailing did not invent the dispatch problem — taxi and livery dispatch is a decades-old operations research topic. What changed was scale and latency budget: a human dispatcher matching a handful of radio-equipped cars became, within a few years, a real-time optimization problem running continuously across an entire city. WHAT'S PUBLIC AND WHAT ISN'T

Uber has never published the literal source of its production dispatch/matching engine, and this chapter does not pretend otherwise. What is public: the general shape of the problem (a real-time constrained bipartite assignment over a two-sided marketplace) is decades-old operations-research territory, well documented in academic literature on taxi dispatch, kidney-exchange matching, and online bipartite matching; Uber's own engineering blog and conference talks have described the existence of a marketplace-optimization discipline and the general batching/assignment approach at a high level, without open-sourcing the algorithm the way H3, M3, or Jaeger were open-sourced. Where this chapter gets specific about mechanism, it is teaching the general technique any company at this scale would need — not reproducing Uber's undisclosed internals.

ARC 03 · NAIVE SOLUTION

Attempt #1: assign the closest idle driver, immediately

The obvious first design: the instant a ride request arrives, scan idle drivers within some radius (chapter 2's index makes this scan fast), pick the closest one by straight-line distance, mark it busy, done. One request in, one decision out, no waiting.

pseudocodenaive_dispatch.js — the strawman, annotated
function onRideRequested(rider) {
  // idleDrivers: a live set, mutated by every match and every driver's status change
  const candidates = kRingSearch(idleDrivers, rider.cell, MAX_RADIUS);
  if (candidates.length === 0) return noDriversAvailable(rider);

  // (1) READ: pick the closest candidate right now
  let best = null, bestDist = Infinity;
  for (const d of candidates) {
    const dist = haversine(rider.pos, d.pos);      // straight-line, not road distance
    if (dist < bestDist) { bestDist = dist; best = d; }
  }

  // (2) WRITE: commit the match — a separate step, separated in time from the read
  idleDrivers.delete(best);
  best.status = "assigned";
  notify(rider, best);
  return best;
}

This is not a strawman built to be knocked down for sport — it is the correct starting point. It is simple to reason about, it has no configuration knobs, and under light load, with few simultaneous requests, it behaves exactly as you'd want: every rider gets the closest available car, instantly. Watch it hold up as load rises.

ARC 04 · WHY IT FAILS

Three independent ways greedy-immediate matching breaks

1. The read-then-write gap is a race condition, not an edge case

Look again at the pseudocode's two numbered steps. Step (1) reads the current idle-driver set and picks a winner; step (2) writes the commit. Between those two steps — even if it's microseconds — the system does other work: other requests are being processed, possibly concurrently, possibly on other machines entirely, all reading from the same idle-driver set before any of their commits land. If requests from rider A and rider B both arrive within that window and both see driver D as the closest idle candidate, both can compute "assign D" before either write happens. Whichever write lands second either overwrites the first (driver D is now double-booked) or must be caught by a compensating check — but that check is exactly the distributed-locking problem chapter 7's state machine has to solve properly. A single-process, single-threaded prototype can paper over this by locking the whole read-modify-write section; a system partitioned across many hosts serving overlapping geographic cells cannot, without deliberate distributed coordination this naive design doesn't have.

2. Straight-line distance is not what a rider experiences

"Closest by haversine distance" and "closest by actual arrival time" are different orderings, and they diverge exactly where it matters most: rivers, highways with limited crossings, one-way street grids, and traffic. A driver 400 meters away on the far side of a river can have a longer real ETA than a driver 1.1 km away with a clear road. Optimizing the wrong metric doesn't fail loudly — it fails by consistently picking the second-best or third-best real choice while reporting confidently that it found the closest one. Chapter 5 derives exactly what "closest" should mean; for now, take as given that straight-line distance is a proxy that's wrong often enough to matter at scale.

3. Greedy per-request optimization is not globally optimal

This is the subtlest failure and the one that justifies the rest of this chapter. Consider two riders, R1 and R2, and two idle drivers, D1 and D2, with these distances:

DRIVER D1DRIVER D2
Rider R12 minutes3 minutes
Rider R22.5 minutes8 minutes

Greedy processes requests in arrival order. If R1 arrives first, greedy correctly gives R1 its closest driver, D1 (2 min) — that decision looks perfect in isolation. But now R2's only option is D2, at 8 minutes. Total wait: 2 + 8 = 10 minutes. The globally optimal assignment instead gives D1 to R2 (2.5 min) and D2 to R1 (3 min): total wait 2.5 + 3 = 5.5 minutes — 45% less total waiting, achieved by making R1's match slightly worse than the greedy choice in exchange for making R2's match dramatically better. Greedy cannot see this trade because by the time R2 arrives, D1 is already gone. Seeing it requires looking at multiple requests and multiple drivers together — which is precisely what a lookup-per-request architecture structurally cannot do.

THE NUMBERS AT SCALE

This isn't a rare 2×2 curiosity. Millions of trip requests per day translate to sustained request rates of hundreds to thousands per second in a single dense metro during peak demand. At that arrival rate, in any given one-second window, dozens of riders and drivers in the same neighborhood are legitimate candidates for each other — and greedy's per-request tunnel vision throws away the option to compare them. The pathological case in the table above isn't an occasional accident; it is the statistically expected outcome whenever two or more requests and two or more candidate drivers are geographically close in time, which at Uber's request volume in any major city is most of the time, not an edge case.

So the fix has to attack the exclusivity race with real coordination, attack the metric problem with real routing (chapter 5), and attack the greedy-suboptimality problem by looking at more than one request at a time — which means, deliberately, not deciding the instant a request arrives.

ARC 05 · BETTER SOLUTION

Windowed batch matching: trade a little latency for a much better assignment

The fix that directly answers §4's global-optimality failure: instead of matching the instant one request arrives, hold a short window — commonly on the order of a few hundred milliseconds to a couple of seconds — collecting every unmatched rider request and every idle driver that becomes available during that window. At the window's close, solve one bipartite graph assignment problem over the whole batch at once, then commit every match atomically.

Windowed batch matching, step by stepSTEP-BY-STEP

Three design decisions make this work, each answering one of §4's failures directly:

  • One solve, one commit. Because the whole batch is assigned in a single computation against a single snapshot of idle drivers, and the commit writes every match atomically before the next batch reads the driver set, there is no read-then-write gap for two riders to race into — the race in §4.1 is closed by construction, not by locking.
  • A real objective function, not a per-request heuristic. The solver minimizes a stated quantity — total wait time, or a weighted combination of wait time and driver idle distance — over all matches in the batch simultaneously. That is exactly the lever the 2×2 example in §4 needed and greedy didn't have.
  • A hard locality constraint. Any rider-driver pair further apart than a maximum radius or ETA is simply not a candidate edge in the graph — the solver is free to leave a rider or driver unmatched this round rather than produce a technically-optimal-but-useless cross-town assignment.
THIS IS A KNOWN CLASS OF PROBLEM — NAME IT

A bipartite graph with weighted edges where you want to select a set of edges covering as many nodes as possible while minimizing (or maximizing) total edge weight, with each node used at most once, is the assignment problem, solvable exactly in polynomial time by the Hungarian algorithm (Kuhn, 1955, refined by Munkres) in O(n³) for an n×n cost matrix, or heuristically and faster at very large n by min-cost max-flow relaxations and auction-style algorithms. Section 8 implements the exact algorithm and runs it live — this is not hand-waving; the assignments you will see computed later in this chapter are real solved instances of this problem, not scripted animations.

ARC 06 · WHY THAT STILL HURTS

Batching doesn't remove costs — it relocates them

Nothing here is free. Batch matching converts §4's correctness and optimality problems into a smaller, more manageable, but still real set of costs:

  • Added latency, felt by every rider. Holding a window means every request waits at least the window length before it can be matched, even the request that arrived one millisecond before the window closed. A 500 ms window costs every rider up to 500 ms of pure waiting that greedy-immediate wouldn't have cost them. Riders perceive "finding your driver" latency directly; this is a real, felt tax, not an internal metric.
  • Solver cost grows faster than linearly. The Hungarian algorithm is O(n³) in the size of the cost matrix. Doubling the batch size (which a longer window does, roughly linearly with arrival rate) more than doubles solve time — at some batch size, in some dense city center during a demand spike, the solver itself becomes the latency bottleneck the window was trying to avoid.
  • Building the cost matrix isn't free either. A naive implementation computes a candidate edge — and hence a real routing-engine ETA query (chapter 5) — for every rider×driver pair in the batch, which is quadratic before the solver even starts. Production systems must prune this aggressively using the geospatial index from chapter 2 (only consider drivers within a few H3 rings) rather than considering every driver in the city for every rider.
  • Starvation at the edges. A rider in a sparsely served area, or a driver willing to travel further than most, can be systematically deprioritized by a solver optimizing total system wait time — the individually best outcome for the whole batch is not guaranteed to be a good outcome for every individual in it. Real systems need fairness constraints or aging (a request's priority rises the longer it's waited) layered on top of pure cost minimization.
THE TUNABLE THAT OWNS THIS TRADEOFF: WINDOW SIZE

Every cost above is a function of one number: how long the window stays open. A near-zero window degenerates back toward greedy-immediate (§3/§4's failures return); a very long window approaches a better and better assignment but imposes latency riders will not tolerate and a solver workload that scales against you. There is no value-free choice here — production systems tune window size empirically per city and per time of day, and section 8's slider lets you feel exactly why that's true with real computed numbers, not an assumed curve.

So the final architecture keeps the batch-and-solve core, but wraps it with: geo-pruned candidate generation so the cost matrix stays small, a tuned (and likely adaptive) window, and the coordination needed to commit a batch's matches without racing the next one.

WHY THE WINDOWER IS ITS OWN STAGE

Separating "collect a batch" from "solve a batch" from "commit a batch" is a deliberate isolation of concerns that mirrors the postmaster/backend separation seen elsewhere on this site: the windower's only job is faithfully accumulating unmatched demand and supply without ever making a matching decision itself, so that it can be simple, fast, and hard to get wrong. All of the complexity — and all of the tunable behavior — lives in the solver stage, which can be swapped, tuned, or fall back to a cheaper heuristic under extreme load without touching how requests are collected.

ARC 08 · INTERNAL IMPLEMENTATION

Building the batch: candidates, cost, and the solver

Three pieces, in the order data flows through them: (a) pruning riders×drivers down to a tractable candidate set, (b) the cost function that turns a candidate pair into a number the solver can minimize, (c) the assignment solver itself, stepped through on a small worked example.

(a) Candidate generation: don't build the full matrix

A batch with R unmatched riders and D idle drivers has up to R×D possible pairs. At realistic batch sizes during a busy window in a dense city (tens of riders, tens of drivers), that's already thousands of pairs; naively computing a real routing ETA (chapter 5) for every one of them is wasteful and slow. Production systems restrict candidates using chapter 2's H3 index: for each rider, only consider drivers within a small ring of hex cells around the rider's cell — say, the rider's cell plus its immediate neighbors, expanding outward only if too few candidates are found. This turns an R×D dense problem into a sparse graph with only the edges worth evaluating.

pseudocodecandidate_gen.js — sparse edge construction
function buildCandidateEdges(riders, idleDrivers, maxRingExpansions) {
  const edges = [];
  for (const r of riders) {
    let ring = 1, found = [];
    while (found.length < MIN_CANDIDATES && ring <= maxRingExpansions) {
      found = h3KRing(r.cell, ring).flatMap(cell => idleDrivers.get(cell) ?? []);
      ring++;
    }
    for (const d of found) {
      edges.push({ rider: r, driver: d, cost: null });   // cost filled in by (b)
    }
  }
  return edges;   // sparse: only geographically plausible pairs
}

(b) The cost function: what the solver is actually minimizing

Every candidate edge needs a single number. The simplest honest choice is predicted pickup ETA in seconds (chapter 5's routing engine, not straight-line distance — that was §4's second failure). Real systems weight in more terms: a small penalty for how long the rider has already waited (so the solver doesn't let one unlucky rider get repeatedly skipped in favor of marginally better matches for others — this is the fairness/starvation concern from §6), and sometimes a term reflecting driver preference or upcoming destination. A representative shape:

formulacost(rider, driver)
cost(r, d) = ETA_seconds(driver_pos, rider_pos)          // chapter 5's routing engine
           − FAIRNESS_WEIGHT × already_waited_seconds(r)  // aging: longer-waiting riders get cheaper edges
           + (ETA_seconds(r, d) > MAX_RADIUS_SECONDS ? BIG_M : 0)  // hard locality cutoff

That BIG_M term is doing real work: rather than removing far-apart pairs from the graph entirely (which complicates a solver that expects a well-formed matrix), an infeasible pair is simply given a cost so large the solver will never choose it over leaving the rider unmatched this round — enforcing the hard radius constraint from §5 without special-casing the solver's math.

WHAT PRODUCTION SYSTEMS ACTUALLY DO WITH THIS KNOB

Uber has not published the exact window-sizing policy its dispatch system uses today, and this chapter does not claim otherwise. What's a safe, general, well-established technique any system in this class would use: make the window adaptive rather than fixed — shrink it when supply is abundant and match quality is already near-optimal even with few candidates, widen it when demand is dense enough that batching more requests clearly improves the solver's options. That adaptive-batching idea is standard in streaming-systems design broadly, not a fact specific to Uber's undisclosed implementation.

ARC 09 · TRADEOFFS

Four matching strategies, compared honestly

STRATEGYMECHANISMWHAT YOU GETWHAT YOU PAY
Greedy nearest-firstMatch the instant a request arrives to the closest idle driver zero added latency trivial to implement race conditions / double-booking provably suboptimal total wait
Windowed batch assignmentCollect a short window, solve one bipartite assignment, commit atomically exact global optimum per batch race-free by construction added latency = window length solver cost grows superlinearly with batch size
Continuous re-optimizationRe-solve a rolling assignment on every new arrival/departure, not just at window boundaries lower added latency than fixed windows reacts instantly to new supply constant solver churn — expensive at high arrival rates risk of "match flapping" — a rider's assignment changing before pickup
Decentralized auction / biddingDrivers bid for nearby requests independently; highest bid (lowest cost) wins per request naturally parallel, no central batch solver degrades gracefully under partition still needs coordination to avoid double-award approximate, not exactly optimal

Read this as another proof by exhaustion, in the same shape as chapter 1's process-vs-thread table: latency and assignment quality trade against each other, and no strategy escapes that trade — only prices it differently. The windowed-batch approach this chapter focused on is the standard textbook answer because it makes the trade explicit and tunable (one number: window size) rather than implicit and hard to reason about.

ARC 10 · PERFORMANCE CHARACTERISTICS

The numbers behind the tradeoff

  • Solver complexity: the Hungarian algorithm on an n×n cost matrix is O(n³) time (and the common potential-based implementation used in this chapter's simulator is O(n² · m) for an n×m rectangular problem). Geo-pruning (§8a) keeps the effective matrix sparse and small rather than letting n grow with total city-wide idle-driver count.
  • Candidate generation cost: without pruning, R riders × D drivers pairs, each needing a routing-engine ETA call (chapter 5) — a real system budgets this as the dominant cost of the whole pipeline and prunes hard.
  • Window-length latency floor: every rider's minimum wait for a match decision is at least half the window length on average (a request arriving uniformly within the window waits, on average, half of it before the window closes) — this is a hard floor no amount of solver speed removes.
  • Throughput at real scale: millions of trips per day translate to a sustained global request rate in the hundreds per second, concentrated heavily into the world's densest metro areas and into daily peak windows — the system must be partitioned geographically (by city or by region) so that no single batch solve ever has to consider the whole world's supply and demand at once.

ARC 11 · REAL-WORLD INCIDENTS & CONTROVERSIES

Where dispatch design meets reality

Pattern 1: driver-side double-booking complaints

Riders and drivers on ride-hailing platforms have publicly reported (in app-store reviews, driver forums, and news coverage of ride-hailing operations over the years) being matched to a driver who was simultaneously servicing another rider, or arriving to find "their" driver had already picked someone else up. Uber has not published a postmortem naming a specific internal race condition behind any particular report, so this chapter does not attribute a cause with false precision — but §4.1's read-then-write race is the textbook mechanism by which any greedy, uncoordinated dispatch design produces exactly this symptom, and it is why batched atomic commit (§5) or equivalent distributed locking is considered mandatory at this class of scale, not an optional hardening.

Pattern 2: event-driven demand spikes overwhelming local supply

Large, geographically concentrated events — a concert or stadium letting out, severe weather, a transit outage — routinely produce a demand spike that badly outstrips locally available drivers for the minutes immediately following. This is a well-documented, industry-wide pattern across ride-hailing operators, reported repeatedly in the press as "surge" or long wait times after major events; chapter 6 covers the pricing side of the response in detail. From a pure dispatch perspective, the honest lesson is that no matching algorithm — greedy, batched, or otherwise — creates supply that doesn't exist; batching can only make the best possible use of the drivers actually available in the area, which is why the pricing and supply-repositioning incentives in chapter 6 exist as a complementary mechanism, not a substitute for good matching.

Pattern 3 (industry-standard, illustrative): a batch solver runaway under a traffic spike

No specific Uber postmortem for this exact scenario is public, so it is presented as a realistic, industry-standard incident shape rather than a documented Uber event. A sudden, large influx of ride requests (a major event ending, a transit disruption) drives batch size up sharply in one region; if window length is fixed rather than adaptive, the solver's O(n²·m)-ish cost grows faster than the arrival rate, and solve time for that region's batches starts exceeding the window length itself — batches back up, effective matching latency balloons well past what the configured window would suggest, and riders in that region see dispatch delays that look like an outage even though every individual component is technically "up." The general, industry-standard fixes are exactly what §8's callout describes: adaptive window sizing that shrinks under load, hard caps on batch size with overflow spilling into the next window, and load shedding that falls back to a cheaper greedy match rather than let the exact solver become the bottleneck.

pseudocodebatch_windower.js — accumulate, then close
class BatchWindower {
  constructor(windowMs, maxBatchSize) {
    this.windowMs = windowMs;
    this.maxBatchSize = maxBatchSize;
    this.pendingRiders = [];
    this.pendingDrivers = [];
  }

  onRiderRequest(rider) {
    this.pendingRiders.push(rider);
    if (this.pendingRiders.length >= this.maxBatchSize) this.closeNow();  // overflow cap — §11's runaway-prevention
  }

  onDriverIdle(driver) { this.pendingDrivers.push(driver); }

  start() {
    setInterval(() => this.closeNow(), this.windowMs);   // fixed window; §8 shows the adaptive variant conceptually
  }

  closeNow() {
    if (this.pendingRiders.length === 0) return;
    const batch = { riders: this.pendingRiders, drivers: this.pendingDrivers };
    this.pendingRiders = []; this.pendingDrivers = [];
    emit("batch-ready", batch);          // → candidate_gen.js, then hungarian.js
  }
}
pseudocodeatomic_commit.js — closing the §4.1 race for good
function commitBatch(assignment, driverVersions) {
  // Each driver row carries a version stamped when it entered the batch's snapshot.
   // The commit is a single compare-and-swap transaction per driver — if ANY driver's
   // version changed since the snapshot (e.g. it was hand-dispatched elsewhere, went
   // offline, or — impossible by construction here, but defensively checked — was
   // somehow claimed by a concurrent process), that one match is rejected and the
   // rider is re-queued into the NEXT batch rather than silently double-booked.
  const accepted = [], rejected = [];
  for (const { rider, driver } of assignment) {
    const ok = compareAndSwap(driver.id, driverVersions.get(driver.id), "assigned");
    if (ok) accepted.push({ rider, driver });
    else { rejected.push(rider); }   // re-enters next window's pendingRiders
  }
  return { accepted, rejected };
}
WHY A COMPARE-AND-SWAP COMMIT, NOT A GLOBAL LOCK

A single lock around the entire commit step would work correctly but would serialize every batch's commit behind every other batch's commit system-wide — exactly the kind of global bottleneck this whole chapter has been trying to avoid. Per-driver compare-and-swap gives the same correctness guarantee (no driver is ever committed to two riders) while allowing unrelated batches, in different geographic regions with disjoint driver sets, to commit fully in parallel. This is the same "isolate the lock to the smallest thing that actually needs protecting" instinct chapter 1 applied to shared memory versus private backend state.
